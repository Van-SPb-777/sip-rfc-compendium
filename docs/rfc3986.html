Abstract
Аннотация
A Uniform Resource Identifier (URI) is a compact sequence of characters that identifies an abstract or physical resource. This specification defines the generic URI syntax and a process for resolving URI references that might be in relative form, along with guidelines and security considerations for the use of URIs on the Internet. The URI syntax defines a grammar that is a superset of all valid URIs, allowing an implementation to parse the common components of a URI reference without knowing the scheme-specific requirements of every possible identifier. This specification does not define a generative grammar for URIs; that task is performed by the individual specifications of each URI scheme.
Универсальный идентификатор ресурса (URI) — это компактная последовательность символов, идентифицирующая абстрактный или физический ресурс. Настоящая спецификация определяет общий синтаксис URI и процесс разрешения ссылок URI, которые могут быть в относительной форме, а также руководящие принципы и соображения безопасности при использовании URI в Интернете. Синтаксис URI определяет грамматику, являющуюся надмножеством всех допустимых URI, что позволяет реализации разбирать общие компоненты ссылки URI, не зная требований, специфичных для схемы каждого возможного идентификатора. Настоящая спецификация не определяет порождающую грамматику для URI; эта задача выполняется отдельными спецификациями каждой схемы URI.
1. Introduction
1. Введение
A Uniform Resource Identifier (URI) provides a simple and extensible means for identifying a resource. This specification of URI syntax and semantics is derived from concepts introduced by the World Wide Web global information initiative, whose use of these identifiers dates from 1990 and is described in "Universal Resource Identifiers in WWW" [RFC1630]. The syntax is designed to meet the recommendations laid out in "Functional Recommendations for Internet Resource Locators" [RFC1736] and "Functional Requirements for Uniform Resource Names" [RFC1737].
Универсальный идентификатор ресурса (URI) предоставляет простое и расширяемое средство идентификации ресурса. Настоящая спецификация синтаксиса и семантики URI выведена из понятий, введённых глобальной информационной инициативой World Wide Web, которая использует эти идентификаторы с 1990 года и описана в документе «Universal Resource Identifiers in WWW» [RFC1630]. Синтаксис разработан с учётом рекомендаций, изложенных в документах «Functional Recommendations for Internet Resource Locators» [RFC1736] и «Functional Requirements for Uniform Resource Names» [RFC1737].
This document obsoletes [RFC2396], which merged "Uniform Resource Locators" [RFC1738] and "Relative Uniform Resource Locators" [RFC1808] in order to define a single, generic syntax for all URIs. It obsoletes [RFC2732], which introduced syntax for an IPv6 address. It excludes portions of RFC 1738 that defined the specific syntax of individual URI schemes; those portions will be updated as separate documents. The process for registration of new URI schemes is defined separately by [BCP35]. Advice for designers of new URI schemes can be found in [RFC2718]. All significant changes from RFC 2396 are noted in Appendix D.
Настоящий документ делает устаревшим [RFC2396], который объединил «Uniform Resource Locators» [RFC1738] и «Relative Uniform Resource Locators» [RFC1808], чтобы определить единый общий синтаксис для всех URI. Он делает устаревшим [RFC2732], который ввёл синтаксис для адреса IPv6. Он исключает те части RFC 1738, которые определяли конкретный синтаксис отдельных схем URI; эти части будут обновлены отдельными документами. Процесс регистрации новых схем URI определён отдельно в [BCP35]. Рекомендации для разработчиков новых схем URI можно найти в [RFC2718]. Все существенные изменения по сравнению с RFC 2396 отмечены в Приложении D.
This specification uses the terms "character" and "coded character set" in accordance with the definitions provided in [BCP19], and "character encoding" in place of what [BCP19] refers to as a "charset".
Настоящая спецификация использует термины «символ» (character) и «кодированный набор символов» (coded character set) в соответствии с определениями, данными в [BCP19], а также «кодировка символов» вместо того, что в [BCP19] называется «charset».

1.1. Обзор URI

Uniform
Единообразие (Uniform)
Uniformity provides several benefits. It allows different types of resource identifiers to be used in the same context, even when the mechanisms used to access those resources may differ. It allows uniform semantic interpretation of common syntactic conventions across different types of resource identifiers. It allows introduction of new types of resource identifiers without interfering with the way that existing identifiers are used. It allows the identifiers to be reused in many different contexts, thus permitting new applications or protocols to leverage a pre- existing, large, and widely used set of resource identifiers.
Единообразие даёт несколько преимуществ. Оно позволяет использовать различные типы идентификаторов ресурсов в одном и том же контексте, даже если механизмы доступа к этим ресурсам могут различаться. Оно допускает единообразную семантическую интерпретацию общих синтаксических соглашений для разных типов идентификаторов ресурсов. Оно позволяет вводить новые типы идентификаторов ресурсов, не затрагивая способ использования существующих идентификаторов. Оно позволяет повторно использовать идентификаторы во многих разных контекстах, что даёт новым приложениям или протоколам возможность опираться на уже существующий, большой и широко используемый набор идентификаторов ресурсов.
Resource
Ресурс (Resource)
This specification does not limit the scope of what might be a resource; rather, the term "resource" is used in a general sense for whatever might be identified by a URI. Familiar examples include an electronic document, an image, a source of information with a consistent purpose (e.g., "today's weather report for Los Angeles"), a service (e.g., an HTTP-to-SMS gateway), and a collection of other resources. A resource is not necessarily accessible via the Internet; e.g., human beings, corporations, and bound books in a library can also be resources. Likewise, abstract concepts can be resources, such as the operators and operands of a mathematical equation, the types of a relationship (e.g., "parent" or "employee"), or numeric values (e.g., zero, one, and infinity).
Настоящая спецификация не ограничивает круг того, что может быть ресурсом; напротив, термин «ресурс» используется в общем смысле для всего, что может быть идентифицировано посредством URI. Знакомые примеры включают электронный документ, изображение, источник информации с постоянным назначением (например, «сегодняшний прогноз погоды для Лос-Анджелеса»), службу (например, шлюз HTTP-to-SMS) и совокупность других ресурсов. Ресурс не обязательно доступен через Интернет; например, ресурсами могут быть люди, корпорации и переплетённые книги в библиотеке. Равным образом ресурсами могут быть абстрактные понятия, такие как операторы и операнды математического уравнения, типы отношения (например, «родитель» или «сотрудник») или числовые значения (например, ноль, единица и бесконечность).
Identifier
Идентификатор (Identifier)
An identifier embodies the information required to distinguish what is being identified from all other things within its scope of identification. Our use of the terms "identify" and "identifying" refer to this purpose of distinguishing one resource from all other resources, regardless of how that purpose is accomplished (e.g., by name, address, or context). These terms should not be mistaken as an assumption that an identifier defines or embodies the identity of what is referenced, though that may be the case for some identifiers. Nor should it be assumed that a system using URIs will access the resource identified: in many cases, URIs are used to denote resources without any intention that they be accessed. Likewise, the "one" resource identified might not be singular in nature (e.g., a resource might be a named set or a mapping that varies over time).
Идентификатор воплощает информацию, необходимую для того, чтобы отличить идентифицируемое от всех остальных вещей в пределах области его идентификации. Использование нами терминов «идентифицировать» и «идентификация» относится именно к этой цели — отличить один ресурс от всех других ресурсов, независимо от того, как эта цель достигается (например, по имени, адресу или контексту). Эти термины не следует понимать как предположение, что идентификатор определяет или воплощает тождество того, на что он ссылается, хотя для некоторых идентификаторов это может быть так. Не следует также предполагать, что система, использующая URI, обратится к идентифицированному ресурсу: во многих случаях URI используются для обозначения ресурсов без какого-либо намерения к ним обращаться. Равным образом идентифицируемый «один» ресурс может не быть единичным по своей природе (например, ресурсом может быть именованный набор или отображение, меняющееся со временем).
A URI is an identifier consisting of a sequence of characters matching the syntax rule named <URI> in Section 3. It enables uniform identification of resources via a separately defined extensible set of naming schemes (Section 3.1). How that identification is accomplished, assigned, or enabled is delegated to each scheme specification.
URI — это идентификатор, состоящий из последовательности символов, соответствующей синтаксическому правилу <URI> в разделе 3. Он обеспечивает единообразную идентификацию ресурсов посредством отдельно определённого расширяемого набора схем именования (раздел 3.1). Способ достижения, назначения или обеспечения такой идентификации оставлен на усмотрение спецификации каждой схемы.
This specification does not place any limits on the nature of a resource, the reasons why an application might seek to refer to a resource, or the kinds of systems that might use URIs for the sake of identifying resources. This specification does not require that a URI persists in identifying the same resource over time, though that is a common goal of all URI schemes. Nevertheless, nothing in this specification prevents an application from limiting itself to particular types of resources, or to a subset of URIs that maintains characteristics desired by that application.
Настоящая спецификация не накладывает никаких ограничений на природу ресурса, на причины, по которым приложение может стремиться сослаться на ресурс, или на типы систем, которые могут использовать URI для идентификации ресурсов. Настоящая спецификация не требует, чтобы URI сохранял идентификацию одного и того же ресурса с течением времени, хотя это и является общей целью всех схем URI. Тем не менее ничто в настоящей спецификации не мешает приложению ограничиться определёнными типами ресурсов или подмножеством URI, обладающим нужными этому приложению характеристиками.
URIs have a global scope and are interpreted consistently regardless of context, though the result of that interpretation may be in relation to the end-user's context. For example, "http://localhost/" has the same interpretation for every user of that reference, even though the network interface corresponding to "localhost" may be different for each end-user: interpretation is independent of access. However, an action made on the basis of that reference will take place in relation to the end-user's context, which implies that an action intended to refer to a globally unique thing must use a URI that distinguishes that resource from all other things. URIs that identify in relation to the end-user's local context should only be used when the context itself is a defining aspect of the resource, such as when an on-line help manual refers to a file on the end- user's file system (e.g., "file:///etc/hosts").
URI имеют глобальную область действия и интерпретируются единообразно независимо от контекста, хотя результат этой интерпретации может зависеть от контекста конечного пользователя. Например, «http://localhost/» имеет одинаковую интерпретацию для каждого пользователя этой ссылки, даже если сетевой интерфейс, соответствующий «localhost», может быть разным для каждого конечного пользователя: интерпретация не зависит от доступа. Однако действие, совершаемое на основе этой ссылки, будет происходить в связи с контекстом конечного пользователя, что означает, что действие, направленное на нечто глобально уникальное, должно использовать URI, отличающий этот ресурс от всех остальных вещей. URI, которые идентифицируют в связи с локальным контекстом конечного пользователя, следует использовать только тогда, когда сам контекст является определяющим аспектом ресурса, — например, когда интерактивное руководство пользователя ссылается на файл в файловой системе конечного пользователя (например, «file:///etc/hosts»).
1.1.1. Generic Syntax
1.1.1. Общий синтаксис
Each URI begins with a scheme name, as defined in Section 3.1, that refers to a specification for assigning identifiers within that scheme. As such, the URI syntax is a federated and extensible naming system wherein each scheme's specification may further restrict the syntax and semantics of identifiers using that scheme.
Каждый URI начинается с имени схемы, определённого в разделе 3.1, которое ссылается на спецификацию назначения идентификаторов в рамках этой схемы. Таким образом, синтаксис URI представляет собой федеративную и расширяемую систему имён, в которой спецификация каждой схемы может дополнительно ограничивать синтаксис и семантику идентификаторов, использующих эту схему.
This specification defines those elements of the URI syntax that are required of all URI schemes or are common to many URI schemes. It thus defines the syntax and semantics needed to implement a scheme- independent parsing mechanism for URI references, by which the scheme-dependent handling of a URI can be postponed until the scheme-dependent semantics are needed. Likewise, protocols and data formats that make use of URI references can refer to this specification as a definition for the range of syntax allowed for all URIs, including those schemes that have yet to be defined. This decouples the evolution of identification schemes from the evolution of protocols, data formats, and implementations that make use of URIs.
Настоящая спецификация определяет те элементы синтаксиса URI, которые требуются для всех схем URI или являются общими для многих схем URI. Тем самым она определяет синтаксис и семантику, необходимые для реализации механизма разбора ссылок URI, не зависящего от схемы, благодаря которому обработку URI с учётом схемы можно отложить до момента, когда семантика, зависящая от схемы, действительно понадобится. Равным образом протоколы и форматы данных, использующие ссылки URI, могут ссылаться на настоящую спецификацию как на определение диапазона синтаксиса, допустимого для всех URI, включая те схемы, которые ещё не определены. Это отделяет развитие схем идентификации от развития протоколов, форматов данных и реализаций, использующих URI.
A parser of the generic URI syntax can parse any URI reference into its major components. Once the scheme is determined, further scheme-specific parsing can be performed on the components. In other words, the URI generic syntax is a superset of the syntax of all URI schemes.
Анализатор общего синтаксиса URI может разобрать любую ссылку URI на её основные компоненты. После определения схемы над компонентами можно выполнить дальнейший разбор с учётом схемы. Иными словами, общий синтаксис URI является надмножеством синтаксиса всех схем URI.

1.1.3. URI, URL, and URN
1.1.3. URI, URL и URN
A URI can be further classified as a locator, a name, or both. The term "Uniform Resource Locator" (URL) refers to the subset of URIs that, in addition to identifying a resource, provide a means of locating the resource by describing its primary access mechanism (e.g., its network "location"). The term "Uniform Resource Name" (URN) has been used historically to refer to both URIs under the "urn" scheme [RFC2141], which are required to remain globally unique and persistent even when the resource ceases to exist or becomes unavailable, and to any other URI with the properties of a name.
URI может быть далее классифицирован как локатор, имя или и то и другое. Термин «универсальный локатор ресурсов» (Uniform Resource Locator, URL) обозначает подмножество URI, которые, помимо идентификации ресурса, предоставляют средство его локализации путём описания основного механизма доступа к нему (например, его сетевого «местоположения»). Термин «универсальное имя ресурса» (Uniform Resource Name, URN) исторически использовался для обозначения как URI в схеме «urn» [RFC2141], которые должны оставаться глобально уникальными и постоянными даже после того, как ресурс прекращает существовать или становится недоступным, так и любого другого URI со свойствами имени.
An individual scheme does not have to be classified as being just one of "name" or "locator". Instances of URIs from any given scheme may have the characteristics of names or locators or both, often depending on the persistence and care in the assignment of identifiers by the naming authority, rather than on any quality of the scheme. Future specifications and related documentation should use the general term "URI" rather than the more restrictive terms "URL" and "URN" [RFC3305].
Отдельная схема не обязана классифицироваться как нечто только «имя» или только «локатор». Экземпляры URI любой данной схемы могут обладать свойствами имён, локаторов или того и другого, что часто зависит от постоянства и тщательности назначения идентификаторов органом именования, а не от какого-либо качества схемы. Будущие спецификации и связанная документация должны использовать общий термин «URI», а не более узкие термины «URL» и «URN» [RFC3305].
1.2. Design Considerations
1.2. Соображения по проектированию
1.2.1. Transcription
1.2.1. Переписывание
The URI syntax has been designed with global transcription as one of its main considerations. A URI is a sequence of characters from a very limited set: the letters of the basic Latin alphabet, digits, and a few special characters. A URI may be represented in a variety of ways; e.g., ink on paper, pixels on a screen, or a sequence of character encoding octets. The interpretation of a URI depends only on the characters used and not on how those characters are represented in a network protocol.
Синтаксис URI разрабатывался с учётом глобального переписывания как одного из главных соображений. URI — это последовательность символов из весьма ограниченного набора: букв базового латинского алфавита, цифр и нескольких специальных символов. URI может быть представлен разными способами: например, чернилами на бумаге, пикселями на экране или последовательностью октетов кодировки символов. Интерпретация URI зависит только от используемых символов, а не от того, как эти символы представлены в сетевом протоколе.
The goal of transcription can be described by a simple scenario. Imagine two colleagues, Sam and Kim, sitting in a pub at an international conference and exchanging research ideas. Sam asks Kim for a location to get more information, so Kim writes the URI for the research site on a napkin. Upon returning home, Sam takes out the napkin and types the URI into a computer, which then retrieves the information to which Kim referred.
Цель переписывания можно описать простым сценарием. Вообразите двух коллег, Сэма и Кима, сидящих в пабе на международной конференции и обменивающихся исследовательскими идеями. Сэм спрашивает Кима, где получить дополнительную информацию, и Ким записывает URI исследовательского сайта на салфетке. Вернувшись домой, Сэм достаёт салфетку и вводит URI в компьютер, который затем извлекает информацию, на которую ссылался Ким.

o A URI is a sequence of characters that is not always represented as a sequence of octets.
o URI — это последовательность символов, которая не всегда представляется последовательностью октетов.
o A URI might be transcribed from a non-network source and thus should consist of characters that are most likely able to be entered into a computer, within the constraints imposed by keyboards (and related input devices) across languages and locales.
o URI может быть переписан из не-сетевого источника и поэтому должен состоять из символов, которые с наибольшей вероятностью можно ввести в компьютер в рамках ограничений, накладываемых клавиатурами (и связанными с ними устройствами ввода) в разных языках и регионах.
o A URI often has to be remembered by people, and it is easier for people to remember a URI when it consists of meaningful or familiar components.
o URI часто приходится запоминать людям, а людям легче запомнить URI в том случае, если он состоит из осмысленных или привычных компонентов.
These design considerations are not always in alignment. For example, it is often the case that the most meaningful name for a URI component would require characters that cannot be typed into some systems. The ability to transcribe a resource identifier from one medium to another has been considered more important than having a URI consist of the most meaningful of components.
Эти соображения по проектированию не всегда согласуются между собой. Например, часто бывает так, что наиболее осмысленное имя для компонента URI требовало бы символов, которые нельзя набрать в некоторых системах. Возможность переписать идентификатор ресурса с одного носителя на другой считалась более важной, чем состав URI из наиболее осмысленных компонентов.
In local or regional contexts and with improving technology, users might benefit from being able to use a wider range of characters; such use is not defined by this specification. Percent-encoded octets (Section 2.1) may be used within a URI to represent characters outside the range of the US-ASCII coded character set if this representation is allowed by the scheme or by the protocol element in which the URI is referenced. Such a definition should specify the character encoding used to map those characters to octets prior to being percent-encoded for the URI.
В локальных или региональных контекстах и по мере совершенствования технологий пользователям могло бы быть полезно использовать более широкий диапазон символов; такое использование настоящей спецификацией не определено. Процентно-экранированные октеты (раздел 2.1) могут использоваться внутри URI для представления символов за пределами кодированного набора символов US-ASCII, если такое представление допускается схемой или элементом протокола, в котором содержится ссылка на URI. Такое определение должно указывать кодировку символов, используемую для отображения этих символов в октеты до их процентного экранирования для URI.
1.2.2. Separating Identification from Interaction
1.2.2. Разделение идентификации и взаимодействия
A common misunderstanding of URIs is that they are only used to refer to accessible resources. The URI itself only provides identification; access to the resource is neither guaranteed nor implied by the presence of a URI. Instead, any operation associated with a URI reference is defined by the protocol element, data format attribute, or natural language text in which it appears.
Распространённое заблуждение относительно URI состоит в том, что они используются только для ссылки на доступные ресурсы. Сам URI обеспечивает лишь идентификацию; доступ к ресурсу не гарантируется и не подразумевается наличием URI. Напротив, любая операция, связанная со ссылкой URI, определяется тем элементом протокола, атрибутом формата данных или текстом на естественном языке, в котором она встречается.
Given a URI, a system may attempt to perform a variety of operations on the resource, as might be characterized by words such as "access", "update", "replace", or "find attributes". Such operations are defined by the protocols that make use of URIs, not by this specification. However, we do use a few general terms for describing common operations on URIs. URI "resolution" is the process of determining an access mechanism and the appropriate parameters necessary to dereference a URI; this resolution may require several iterations. To use that access mechanism to perform an action on the URI's resource is to "dereference" the URI.
Имея URI, система может попытаться выполнить над ресурсом разнообразные операции, которые можно охарактеризовать словами «доступ», «обновление», «замена» или «поиск атрибутов». Такие операции определяются протоколами, использующими URI, а не настоящей спецификацией. Однако мы действительно используем несколько общих терминов для описания типичных операций с URI. «Разрешение» URI — это процесс определения механизма доступа и соответствующих параметров, необходимых для разыменования URI; такое разрешение может потребовать нескольких итераций. Использовать этот механизм доступа для выполнения действия над ресурсом URI — значит «разыменовать» URI.
When URIs are used within information retrieval systems to identify sources of information, the most common form of URI dereference is "retrieval": making use of a URI in order to retrieve a representation of its associated resource. A "representation" is a sequence of octets, along with representation metadata describing those octets, that constitutes a record of the state of the resource at the time when the representation is generated. Retrieval is achieved by a process that might include using the URI as a cache key to check for a locally cached representation, resolution of the URI to determine an appropriate access mechanism (if any), and dereference of the URI for the sake of applying a retrieval operation. Depending on the protocols used to perform the retrieval, additional information might be supplied about the resource (resource metadata) and its relation to other resources.
Когда URI используются в системах поиска информации для идентификации источников информации, наиболее распространённой формой разыменования URI является «извлечение» (retrieval): использование URI для того, чтобы получить представление связанного с ним ресурса. «Представление» — это последовательность октетов вместе с метаданными представления, описывающими эти октеты, которая представляет собой запись состояния ресурса на момент, когда это представление формируется. Извлечение достигается процессом, который может включать использование URI в качестве ключа кэша для проверки локально кэшированного представления, разрешение URI для определения подходящего механизма доступа (если таковой имеется) и разыменование URI для применения операции извлечения. В зависимости от протоколов, используемых для выполнения извлечения, может предоставляться дополнительная информация о ресурсе (метаданные ресурса) и о его отношении к другим ресурсам.
URI references in information retrieval systems are designed to be late-binding: the result of an access is generally determined when it is accessed and may vary over time or due to other aspects of the interaction. These references are created in order to be used in the future: what is being identified is not some specific result that was obtained in the past, but rather some characteristic that is expected to be true for future results. In such cases, the resource referred to by the URI is actually a sameness of characteristics as observed over time, perhaps elucidated by additional comments or assertions made by the resource provider.
Ссылки URI в системах поиска информации проектируются с поздним связыванием: результат доступа обычно определяется в момент обращения и может меняться со временем или из-за других аспектов взаимодействия. Эти ссылки создаются для использования в будущем: идентифицируется не какой-то конкретный результат, полученный в прошлом, а скорее некоторая характеристика, которая, как ожидается, будет верна для будущих результатов. В таких случаях ресурс, на который ссылается URI, фактически представляет собой неизменность характеристик, наблюдаемых с течением времени, возможно, поясняемую дополнительными комментариями или утверждениями, сделанными поставщиком ресурса.
Although many URI schemes are named after protocols, this does not imply that use of these URIs will result in access to the resource via the named protocol. URIs are often used simply for the sake of identification. Even when a URI is used to retrieve a representation of a resource, that access might be through gateways, proxies, caches, and name resolution services that are independent of the protocol associated with the scheme name. The resolution of some URIs may require the use of more than one protocol (e.g., both DNS and HTTP are typically used to access an "http" URI's origin server when a representation isn't found in a local cache).
Хотя многие схемы URI названы по именам протоколов, это не означает, что использование таких URI приведёт к доступу к ресурсу через названный протокол. URI часто используются просто ради идентификации. Даже когда URI используется для извлечения представления ресурса, этот доступ может осуществляться через шлюзы, прокси, кэши и службы разрешения имён, независимые от протокола, связанного с именем схемы. Разрешение некоторых URI может требовать использования более одного протокола (например, для доступа к исходному серверу URI «http», когда представление не найдено в локальном кэше, обычно используются и DNS, и HTTP).
1.2.3. Hierarchical Identifiers
1.2.3. Иерархические идентификаторы
The URI syntax is organized hierarchically, with components listed in order of decreasing significance from left to right. For some URI schemes, the visible hierarchy is limited to the scheme itself: everything after the scheme component delimiter (":") is considered opaque to URI processing. Other URI schemes make the hierarchy explicit and visible to generic parsing algorithms.
Синтаксис URI организован иерархически, компоненты перечисляются в порядке убывания значимости слева направо. Для некоторых схем URI видимая иерархия ограничивается самой схемой: всё, что идёт после разделителя компонента схемы («:»), считается непрозрачным для обработки URI. Другие схемы URI делают иерархию явной и видимой для общих алгоритмов разбора.
The generic syntax uses the slash ("/"), question mark ("?"), and number sign ("#") characters to delimit components that are significant to the generic parser's hierarchical interpretation of an identifier. In addition to aiding the readability of such identifiers through the consistent use of familiar syntax, this uniform representation of hierarchy across naming schemes allows scheme-independent references to be made relative to that hierarchy.
Общий синтаксис использует символы косой черты («/»), знака вопроса («?») и решётки («#») для разделения компонентов, значимых для иерархической интерпретации идентификатора общим анализатором. Помимо облегчения читаемости таких идентификаторов за счёт единообразного использования привычного синтаксиса, это единообразное представление иерархии для всех схем именования позволяет делать ссылки, не зависящие от схемы, относительно этой иерархии.
It is often the case that a group or "tree" of documents has been constructed to serve a common purpose, wherein the vast majority of URI references in these documents point to resources within the tree rather than outside it. Similarly, documents located at a particular site are much more likely to refer to other resources at that site than to resources at remote sites. Relative referencing of URIs allows document trees to be partially independent of their location and access scheme. For instance, it is possible for a single set of hypertext documents to be simultaneously accessible and traversable via each of the "file", "http", and "ftp" schemes if the documents refer to each other with relative references. Furthermore, such document trees can be moved, as a whole, without changing any of the relative references.
Часто бывает так, что группа или «дерево» документов создаётся для общей цели, причём подавляющее большинство ссылок URI в этих документах указывают на ресурсы внутри дерева, а не вне его. Аналогично документы, расположенные на определённом сайте, гораздо чаще ссылаются на другие ресурсы этого сайта, чем на ресурсы удалённых сайтов. Относительные ссылки URI позволяют деревьям документов быть частично независимыми от их местоположения и схемы доступа. Например, один набор гипертекстовых документов может быть одновременно доступен и обходим посредством каждой из схем «file», «http» и «ftp», если документы ссылаются друг на друга относительными ссылками. Более того, такие деревья документов можно перемещать целиком, не изменяя ни одной относительной ссылки.
A relative reference (Section 4.2) refers to a resource by describing the difference within a hierarchical name space between the reference context and the target URI. The reference resolution algorithm, presented in Section 5, defines how such a reference is transformed to the target URI. As relative references can only be used within the context of a hierarchical URI, designers of new URI schemes should use a syntax consistent with the generic syntax's hierarchical components unless there are compelling reasons to forbid relative referencing within that scheme.
Относительная ссылка (раздел 4.2) ссылается на ресурс, описывая различие в пределах иерархического пространства имён между контекстом ссылки и целевым URI. Алгоритм разрешения ссылок, представленный в разделе 5, определяет, как такая ссылка преобразуется в целевой URI. Поскольку относительные ссылки можно использовать только в контексте иерархического URI, разработчикам новых схем URI следует применять синтаксис, согласующийся с иерархическими компонентами общего синтаксиса, если только нет веских причин запрещать относительные ссылки в этой схеме.
NOTE: Previous specifications used the terms "partial URI" and "relative URI" to denote a relative reference to a URI. As some readers misunderstood those terms to mean that relative URIs are a subset of URIs rather than a method of referencing URIs, this specification simply refers to them as relative references.
ПРИМЕЧАНИЕ. В предыдущих спецификациях термины «частичный URI» (partial URI) и «относительный URI» (relative URI) использовались для обозначения относительной ссылки на URI. Поскольку некоторые читатели поняли эти термины так, будто относительные URI являются подмножеством URI, а не способом ссылки на URI, настоящая спецификация называет их просто относительными ссылками.
All URI references are parsed by generic syntax parsers when used. However, because hierarchical processing has no effect on an absolute URI used in a reference unless it contains one or more dot-segments (complete path segments of "." or "..", as described in Section 3.3), URI scheme specifications can define opaque identifiers by disallowing use of slash characters, question mark characters, and the URIs "scheme:." and "scheme:..".
Все ссылки URI при использовании разбираются анализаторами общего синтаксиса. Однако, поскольку иерархическая обработка не влияет на абсолютный URI, используемый в ссылке, если только он не содержит один или несколько точечных сегментов (полных сегментов пути «.» или «..», как описано в разделе 3.3), спецификации схем URI могут определять непрозрачные идентификаторы, запрещая использование символов косой черты, символов знака вопроса и URI «scheme:.» и «scheme:..».
1.3. Syntax Notation
1.3. Нотация синтаксиса
This specification uses the Augmented Backus-Naur Form (ABNF) notation of [RFC2234], including the following core ABNF syntax rules defined by that specification: ALPHA (letters), CR (carriage return), DIGIT (decimal digits), DQUOTE (double quote), HEXDIG (hexadecimal digits), LF (line feed), and SP (space). The complete URI syntax is collected in Appendix A.
Настоящая спецификация использует нотацию расширенной формы Бэкуса — Наура (ABNF) из [RFC2234], включая следующие основные синтаксические правила ABNF, определённые в этой спецификации: ALPHA (буквы), CR (возврат каретки), DIGIT (десятичные цифры), DQUOTE (двойная кавычка), HEXDIG (шестнадцатеричные цифры), LF (перевод строки) и SP (пробел). 2. Characters
2. Символы
The URI syntax provides a method of encoding data, presumably for the sake of identifying a resource, as a sequence of characters. The URI characters are, in turn, frequently encoded as octets for transport or presentation. This specification does not mandate any particular character encoding for mapping between URI characters and the octets used to store or transmit those characters. When a URI appears in a protocol element, the character encoding is defined by that protocol; without such a definition, a URI is assumed to be in the same character encoding as the surrounding text.
Синтаксис URI предоставляет способ кодирования данных — предположительно с целью идентификации ресурса — в виде последовательности символов. Символы URI, в свою очередь, часто кодируются как октеты для передачи или представления. Настоящая спецификация не предписывает какой-либо конкретной кодировки символов для отображения между символами URI и октетами, используемыми для хранения или передачи этих символов. Когда URI появляется в элементе протокола, кодировка символов определяется этим протоколом; при отсутствии такого определения предполагается, что URI имеет ту же кодировку символов, что и окружающий текст.
The ABNF notation defines its terminal values to be non-negative integers (codepoints) based on the US-ASCII coded character set [ASCII]. Because a URI is a sequence of characters, we must invert that relation in order to understand the URI syntax. Therefore, the integer values used by the ABNF must be mapped back to their corresponding characters via US-ASCII in order to complete the syntax rules.
Нотация ABNF определяет свои терминальные значения как неотрицательные целые числа (кодовые точки) на основе кодированного набора символов US-ASCII [ASCII]. Поскольку URI — это последовательность символов, мы должны обратить это отношение, чтобы понять синтаксис URI. Поэтому целочисленные значения, используемые ABNF, должны быть отображены обратно в соответствующие символы посредством US-ASCII, чтобы завершить синтаксические правила.
A URI is composed from a limited set of characters consisting of digits, letters, and a few graphic symbols. A reserved subset of those characters may be used to delimit syntax components within a URI while the remaining characters, including both the unreserved set and those reserved characters not acting as delimiters, define each component's identifying data.
URI составляется из ограниченного набора символов, состоящего из цифр, букв и нескольких графических символов. Зарезервированное подмножество этих символов может использоваться для разделения синтаксических компонентов внутри URI, а остальные символы, включая как незарезервированный набор, так и те зарезервированные символы, которые не выступают разделителями, определяют идентифицирующие данные каждого компонента.
2.1. Percent-Encoding
2.1. Процентное экранирование
A percent-encoding mechanism is used to represent a data octet in a component when that octet's corresponding character is outside the allowed set or is being used as a delimiter of, or within, the component. A percent-encoded octet is encoded as a character triplet, consisting of the percent character "%" followed by the two hexadecimal digits representing that octet's numeric value. For example, "%20" is the percent-encoding for the binary octet "00100000" (ABNF: %x20), which in US-ASCII corresponds to the space character (SP). Section 2.4 describes when percent-encoding and decoding is applied.
Механизм процентного экранирования используется для представления октета данных в компоненте, когда соответствующий этому октету символ находится вне разрешённого набора или используется в качестве разделителя компонента либо внутри него. Процентно-экранированный октет кодируется как триплет символов, состоящий из символа процента «%», за которым следуют две шестнадцатеричные цифры, представляющие числовое значение этого октета. Например, «%20» — это процентное экранирование двоичного октета «00100000» (ABNF: %x20), который в US-ASCII соответствует символу пробела (SP). В разделе 2.4 описано, когда применяется процентное экранирование и декодирование.
pct-encoded = "%" HEXDIG HEXDIG
pct-encoded = "%" HEXDIG HEXDIG
The uppercase hexadecimal digits 'A' through 'F' are equivalent to the lowercase digits 'a' through 'f', respectively. If two URIs differ only in the case of hexadecimal digits used in percent-encoded octets, they are equivalent. For consistency, URI producers and normalizers should use uppercase hexadecimal digits for all percent- encodings.
Шестнадцатеричные цифры верхнего регистра «A»–«F» эквивалентны, соответственно, цифрам нижнего регистра «a»–«f». Если два URI различаются только регистром шестнадцатеричных цифр, используемых в процентно-экранированных октетах, они эквивалентны. Для единообразия производители и нормализаторы URI должны использовать шестнадцатеричные цифры верхнего регистра для всех процентных экранирований.
2.2. Reserved Characters
2.2. Зарезервированные символы
URIs include components and subcomponents that are delimited by characters in the "reserved" set. These characters are called "reserved" because they may (or may not) be defined as delimiters by the generic syntax, by each scheme-specific syntax, or by the implementation-specific syntax of a URI's dereferencing algorithm. If data for a URI component would conflict with a reserved character's purpose as a delimiter, then the conflicting data must be percent-encoded before the URI is formed.
URI включают компоненты и подкомпоненты, разделяемые символами из «зарезервированного» набора. Эти символы называются «зарезервированными», поскольку они могут (а могут и не) быть определены как разделители общим синтаксисом, синтаксисом конкретной схемы или синтаксисом конкретной реализации алгоритма разыменования URI. Если данные для компонента URI противоречили бы назначению зарезервированного символа как разделителя, то противоречащие данные должны быть процентно экранированы до формирования URI.

The purpose of reserved characters is to provide a set of delimiting characters that are distinguishable from other data within a URI. URIs that differ in the replacement of a reserved character with its corresponding percent-encoded octet are not equivalent. Percent- encoding a reserved character, or decoding a percent-encoded octet that corresponds to a reserved character, will change how the URI is interpreted by most applications. Thus, characters in the reserved set are protected from normalization and are therefore safe to be used by scheme-specific and producer-specific algorithms for delimiting data subcomponents within a URI.
Назначение зарезервированных символов — предоставить набор разделяющих символов, отличимых от других данных внутри URI. URI, различающиеся заменой зарезервированного символа соответствующим процентно-экранированным октетом, не эквивалентны. Процентное экранирование зарезервированного символа или декодирование процентно-экранированного октета, соответствующего зарезервированному символу, изменит интерпретацию URI большинством приложений. Таким образом, символы из зарезервированного набора защищены от нормализации и потому безопасны для использования алгоритмами, специфичными для схемы и для производителя, при разделении подкомпонентов данных внутри URI.
A subset of the reserved characters (gen-delims) is used as delimiters of the generic URI components described in Section 3. A component's ABNF syntax rule will not use the reserved or gen-delims rule names directly; instead, each syntax rule lists the characters allowed within that component (i.e., not delimiting it), and any of those characters that are also in the reserved set are "reserved" for use as subcomponent delimiters within the component. Only the most common subcomponents are defined by this specification; other subcomponents may be defined by a URI scheme's specification, or by the implementation-specific syntax of a URI's dereferencing algorithm, provided that such subcomponents are delimited by characters in the reserved set allowed within that component.
Подмножество зарезервированных символов (gen-delims) используется в качестве разделителей общих компонентов URI, описанных в разделе 3. Синтаксическое правило ABNF компонента не будет напрямую использовать имена правил reserved или gen-delims; вместо этого каждое синтаксическое правило перечисляет символы, допустимые внутри этого компонента (то есть не разделяющие его), и любые из этих символов, которые также входят в зарезервированный набор, «зарезервированы» для использования в качестве разделителей подкомпонентов внутри компонента. Настоящей спецификацией определены только наиболее распространённые подкомпоненты; другие подкомпоненты могут быть определены спецификацией схемы URI или синтаксисом конкретной реализации алгоритма разыменования URI при условии, что такие подкомпоненты разделяются символами из зарезервированного набора, допустимыми внутри этого компонента.
URI producing applications should percent-encode data octets that correspond to characters in the reserved set unless these characters are specifically allowed by the URI scheme to represent data in that component. If a reserved character is found in a URI component and no delimiting role is known for that character, then it must be interpreted as representing the data octet corresponding to that character's encoding in US-ASCII.
Приложения, производящие URI, должны процентно экранировать октеты данных, соответствующие символам из зарезервированного набора, если только эти символы не разрешены специально схемой URI для представления данных в этом компоненте. Если в компоненте URI обнаружен зарезервированный символ и для него не известно разделяющей роли, он должен интерпретироваться как представляющий октет данных, соответствующий кодированию этого символа в US-ASCII.
2.3. Unreserved Characters
2.3. Незарезервированные символы
Characters that are allowed in a URI but do not have a reserved purpose are called unreserved. These include uppercase and lowercase letters, decimal digits, hyphen, period, underscore, and tilde.
Символы, допустимые в URI, но не имеющие зарезервированного назначения, называются незарезервированными. К ним относятся буквы верхнего и нижнего регистра, десятичные цифры, дефис, точка, знак подчёркивания и тильда.
unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"
unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~"
URIs that differ in the replacement of an unreserved character with its corresponding percent-encoded US-ASCII octet are equivalent: they identify the same resource. However, URI comparison implementations do not always perform normalization prior to comparison (see Section 6). For consistency, percent-encoded octets in the ranges of ALPHA (%41-%5A and %61-%7A), DIGIT (%30-%39), hyphen (%2D), period (%2E), underscore (%5F), or tilde (%7E) should not be created by URI producers and, when found in a URI, should be decoded to their corresponding unreserved characters by URI normalizers.
URI, различающиеся заменой незарезервированного символа соответствующим процентно-экранированным октетом US-ASCII, эквивалентны: они идентифицируют один и тот же ресурс. Однако реализации сравнения URI не всегда выполняют нормализацию перед сравнением (см. раздел 6). Для единообразия процентно-экранированные октеты в диапазонах ALPHA (%41-%5A и %61-%7A), DIGIT (%30-%39), дефиса (%2D), точки (%2E), знака подчёркивания (%5F) или тильды (%7E) не должны создаваться производителями URI и, будучи обнаруженными в URI, должны декодироваться нормализаторами URI в соответствующие незарезервированные символы.
2.4. When to Encode or Decode
2.4. Когда кодировать или декодировать
Under normal circumstances, the only time when octets within a URI are percent-encoded is during the process of producing the URI from its component parts. This is when an implementation determines which of the reserved characters are to be used as subcomponent delimiters and which can be safely used as data. Once produced, a URI is always in its percent-encoded form.
При обычных обстоятельствах единственный случай, когда октеты внутри URI процентно экранируются, — это процесс формирования URI из его составных частей. Именно тогда реализация определяет, какие из зарезервированных символов будут использоваться в качестве разделителей подкомпонентов, а какие можно безопасно использовать как данные. После формирования URI всегда находится в своей процентно-экранированной форме.
When a URI is dereferenced, the components and subcomponents significant to the scheme-specific dereferencing process (if any) must be parsed and separated before the percent-encoded octets within those components can be safely decoded, as otherwise the data may be mistaken for component delimiters. The only exception is for percent-encoded octets corresponding to characters in the unreserved set, which can be decoded at any time. For example, the octet corresponding to the tilde ("~") character is often encoded as "%7E" by older URI processing implementations; the "%7E" can be replaced by "~" without changing its interpretation.
Когда URI разыменовывается, компоненты и подкомпоненты, значимые для процесса разыменования, зависящего от схемы (если таковые имеются), должны быть разобраны и отделены, прежде чем процентно-экранированные октеты внутри этих компонентов можно будет безопасно декодировать, иначе данные могут быть приняты за разделители компонентов. Единственное исключение — процентно-экранированные октеты, соответствующие символам из незарезервированного набора, которые можно декодировать в любой момент. Например, октет, соответствующий символу тильды («~»), часто экранируется как «%7E» более старыми реализациями обработки URI; «%7E» можно заменить на «~» без изменения интерпретации.
Because the percent ("%") character serves as the indicator for percent-encoded octets, it must be percent-encoded as "%25" for that octet to be used as data within a URI. Implementations must not percent-encode or decode the same string more than once, as decoding an already decoded string might lead to misinterpreting a percent data octet as the beginning of a percent-encoding, or vice versa in the case of percent-encoding an already percent-encoded string.
Поскольку символ процента («%») служит индикатором процентно-экранированных октетов, он должен быть процентно экранирован как «%25», чтобы этот октет можно было использовать как данные внутри URI. Реализации не должны процентно экранировать или декодировать одну и ту же строку более одного раза, поскольку декодирование уже декодированной строки может привести к ошибочной интерпретации октета данных процента как начала процентного экранирования, или наоборот — при процентном экранировании уже процентно-экранированной строки.
2.5. Identifying Data
2.5. Идентифицирующие данные
URI characters provide identifying data for each of the URI components, serving as an external interface for identification between systems. Although the presence and nature of the URI production interface is hidden from clients that use its URIs (and is thus beyond the scope of the interoperability requirements defined by this specification), it is a frequent source of confusion and errors in the interpretation of URI character issues. Implementers have to be aware that there are multiple character encodings involved in the production and transmission of URIs: local name and data encoding, public interface encoding, URI character encoding, data format encoding, and protocol encoding.
Символы URI предоставляют идентифицирующие данные для каждого из компонентов URI, служа внешним интерфейсом для идентификации между системами. Хотя наличие и природа интерфейса формирования URI скрыты от клиентов, использующих его URI (и потому выходят за рамки требований совместимости, определённых настоящей спецификацией), он часто является источником путаницы и ошибок в интерпретации вопросов, связанных с символами URI. Реализаторы должны осознавать, что в формировании и передаче URI участвует несколько кодировок символов: кодирование локальных имён и данных, кодирование публичного интерфейса, кодирование символов URI, кодирование формата данных и кодирование протокола.
Local names, such as file system names, are stored with a local character encoding. URI producing applications (e.g., origin servers) will typically use the local encoding as the basis for producing meaningful names. The URI producer will transform the local encoding to one that is suitable for a public interface and then transform the public interface encoding into the restricted set of URI characters (reserved, unreserved, and percent-encodings). Those characters are, in turn, encoded as octets to be used as a reference within a data format (e.g., a document charset), and such data formats are often subsequently encoded for transmission over Internet protocols.
Локальные имена, например имена файловых систем, хранятся в локальной кодировке символов. Приложения, производящие URI (например, исходные серверы), обычно используют локальную кодировку как основу для создания осмысленных имён. Производитель URI преобразует локальную кодировку в кодировку, подходящую для публичного интерфейса, а затем преобразует кодировку публичного интерфейса в ограниченный набор символов URI (зарезервированные, незарезервированные и процентные экранирования). Эти символы, в свою очередь, кодируются как октеты, которые используются как ссылка внутри формата данных (например, кодировки документа), а такие форматы данных часто затем кодируются для передачи по протоколам Интернета.
For most systems, an unreserved character appearing within a URI component is interpreted as representing the data octet corresponding to that character's encoding in US-ASCII. Consumers of URIs assume that the letter "X" corresponds to the octet "01011000", and even when that assumption is incorrect, there is no harm in making it. A system that internally provides identifiers in the form of a different character encoding, such as EBCDIC, will generally perform character translation of textual identifiers to UTF-8 [STD63] (or some other superset of the US-ASCII character encoding) at an internal interface, thereby providing more meaningful identifiers than those resulting from simply percent-encoding the original octets.
Для большинства систем незарезервированный символ, появляющийся внутри компонента URI, интерпретируется как представляющий октет данных, соответствующий кодированию этого символа в US-ASCII. Потребители URI предполагают, что буква «X» соответствует октету «01011000», и даже если это предположение неверно, вреда от него нет. Система, которая внутренне предоставляет идентификаторы в виде другой кодировки символов, например EBCDIC, обычно выполняет преобразование текстовых идентификаторов в UTF-8 [STD63] (или какое-либо иное надмножество кодировки US-ASCII) на внутреннем интерфейсе, тем самым предоставляя более осмысленные идентификаторы, чем те, что получаются при простом процентном экранировании исходных октетов.
For example, consider an information service that provides data, stored locally using an EBCDIC-based file system, to clients on the Internet through an HTTP server. When an author creates a file with the name "Laguna Beach" on that file system, the "http" URI corresponding to that resource is expected to contain the meaningful string "Laguna%20Beach". If, however, that server produces URIs by using an overly simplistic raw octet mapping, then the result would be a URI containing "%D3%81%87%A4%95%81@%C2%85%81%83%88". An internal transcoding interface fixes this problem by transcoding the local name to a superset of US-ASCII prior to producing the URI. Naturally, proper interpretation of an incoming URI on such an interface requires that percent-encoded octets be decoded (e.g., "%20" to SP) before the reverse transcoding is applied to obtain the local name.
Например, рассмотрим информационную службу, которая предоставляет данные, хранящиеся локально в файловой системе на основе EBCDIC, клиентам в Интернете через HTTP-сервер. Когда автор создаёт в этой файловой системе файл с именем «Laguna Beach», ожидается, что URI «http», соответствующий этому ресурсу, будет содержать осмысленную строку «Laguna%20Beach». Если же этот сервер формирует URI с помощью чрезмерно упрощённого прямого отображения октетов, результатом будет URI, содержащий «%D3%81%87%A4%95%81@%C2%85%81%83%88». Внутренний интерфейс перекодирования решает эту проблему, перекодируя локальное имя в надмножество US-ASCII до формирования URI. Естественно, правильная интерпретация входящего URI на таком интерфейсе требует декодирования процентно-экранированных октетов (например, «%20» в SP) до применения обратного перекодирования для получения локального имени.
In some cases, the internal interface between a URI component and the identifying data that it has been crafted to represent is much less direct than a character encoding translation. For example, portions of a URI might reflect a query on non-ASCII data, or numeric coordinates on a map. Likewise, a URI scheme may define components with additional encoding requirements that are applied prior to forming the component and producing the URI.
В некоторых случаях внутренний интерфейс между компонентом URI и идентифицирующими данными, которые он должен представлять, гораздо менее прямолинеен, чем преобразование кодировки символов. Например, части URI могут отражать запрос к не-ASCII данным или числовые координаты на карте. Равным образом схема URI может определять компоненты с дополнительными требованиями к кодированию, которые применяются до формирования компонента и создания URI.
When a new URI scheme defines a component that represents textual data consisting of characters from the Universal Character Set [UCS], the data should first be encoded as octets according to the UTF-8 character encoding [STD63]; then only those octets that do not correspond to characters in the unreserved set should be percent- encoded. For example, the character A would be represented as "A", the character LATIN CAPITAL LETTER A WITH GRAVE would be represented as "%C3%80", and the character KATAKANA LETTER A would be represented as "%E3%82%A2".
Когда новая схема URI определяет компонент, представляющий текстовые данные, состоящие из символов Универсального набора символов (Universal Character Set, UCS), данные должны сначала быть закодированы как октеты в соответствии с кодировкой символов UTF-8 [STD63]; затем процентно экранироваться должны только те октеты, которые не соответствуют символам из незарезервированного набора. Например, символ A был бы представлен как «A», символ LATIN CAPITAL LETTER A WITH GRAVE — как «%C3%80», а символ KATAKANA LETTER A — как «%E3%82%A2».
3. Syntax Components
3. Синтаксические компоненты
The generic URI syntax consists of a hierarchical sequence of components referred to as the scheme, authority, path, query, and fragment.
Общий синтаксис URI состоит из иерархической последовательности компонентов, называемых scheme (схема), authority, path (путь), query (запрос) и fragment (фрагмент).
URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ] hier-part = "//" authority path-abempty / path-absolute / path-rootless / path-empty
URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ] hier-part = "//" authority path-abempty / path-absolute / path-rootless / path-empty
The scheme and path components are required, though the path may be empty (no characters). When authority is present, the path must either be empty or begin with a slash ("/") character. When authority is not present, the path cannot begin with two slash characters ("//"). These restrictions result in five different ABNF rules for a path (Section 3.3), only one of which will match any given URI reference.
Компоненты схемы и пути обязательны, хотя путь может быть пустым (не содержать символов). Когда authority присутствует, путь должен быть либо пустым, либо начинаться с символа косой черты («/»). Когда authority отсутствует, путь не может начинаться с двух символов косой черты («//»). Эти ограничения приводят к пяти различным правилам ABNF для пути (раздел 3.3), из которых только одно будет соответствовать любой данной ссылке URI.

3.1. Scheme
3.1. Схема
Each URI begins with a scheme name that refers to a specification for assigning identifiers within that scheme. As such, the URI syntax is a federated and extensible naming system wherein each scheme's specification may further restrict the syntax and semantics of identifiers using that scheme.
Каждый URI начинается с имени схемы, определённого в разделе 3.1, которое ссылается на спецификацию назначения идентификаторов в рамках этой схемы. Таким образом, синтаксис URI представляет собой федеративную и расширяемую систему имён, в которой спецификация каждой схемы может дополнительно ограничивать синтаксис и семантику идентификаторов, использующих эту схему.
Scheme names consist of a sequence of characters beginning with a letter and followed by any combination of letters, digits, plus ("+"), period ("."), or hyphen ("-"). Although schemes are case- insensitive, the canonical form is lowercase and documents that specify schemes must do so with lowercase letters. An implementation should accept uppercase letters as equivalent to lowercase in scheme names (e.g., allow "HTTP" as well as "http") for the sake of robustness but should only produce lowercase scheme names for consistency.
Имена схем состоят из последовательности символов, начинающейся с буквы и продолжающейся любой комбинацией букв, цифр, знака плюс («+»), точки («.») или дефиса («-»). Хотя схемы нечувствительны к регистру, канонической формой является нижний регистр, и документы, определяющие схемы, должны использовать строчные буквы. Реализация должна принимать буквы верхнего регистра как эквивалентные нижнему в именах схем (например, допускать «HTTP» наряду с «http») ради устойчивости, но для единообразия должна создавать только имена схем в нижнем регистре.
scheme = ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )
scheme = ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )
Individual schemes are not specified by this document. The process for registration of new URI schemes is defined separately by [BCP35]. The scheme registry maintains the mapping between scheme names and their specifications. Advice for designers of new URI schemes can be found in [RFC2718]. URI scheme specifications must define their own syntax so that all strings matching their scheme-specific syntax will also match the <absolute-URI> grammar, as described in Section 4.3.
Отдельные схемы настоящим документом не определяются. Процесс регистрации новых схем URI определён отдельно в [BCP35]. Реестр схем поддерживает отображение между именами схем и их спецификациями. Рекомендации для разработчиков новых схем URI можно найти в [RFC2718]. Спецификации схем URI должны определять собственный синтаксис, чтобы все строки, соответствующие их синтаксису, специфичному для схемы, также соответствовали грамматике <absolute-URI>, как описано в разделе 4.3.
When presented with a URI that violates one or more scheme-specific restrictions, the scheme-specific resolution process should flag the reference as an error rather than ignore the unused parts; doing so reduces the number of equivalent URIs and helps detect abuses of the generic syntax, which might indicate that the URI has been constructed to mislead the user (Section 7.6).
Если предъявлен URI, нарушающий одно или несколько ограничений, специфичных для схемы, процесс разрешения, специфичный для схемы, должен отметить ссылку как ошибку, а не игнорировать неиспользуемые части; это уменьшает число эквивалентных URI и помогает выявлять злоупотребления общим синтаксисом, которые могут указывать на то, что URI построен так, чтобы ввести пользователя в заблуждение (раздел 7.6).
3.2. Authority
3.2. Компонент authority
Many URI schemes include a hierarchical element for a naming authority so that governance of the name space defined by the remainder of the URI is delegated to that authority (which may, in turn, delegate it further). The generic syntax provides a common means for distinguishing an authority based on a registered name or server address, along with optional port and user information.
Многие схемы URI включают иерархический элемент для органа именования, так что управление пространством имён, определяемым остатком URI, передаётся этому органу (который, в свою очередь, может передать его дальше). Общий синтаксис предоставляет общее средство различения authority на основе зарегистрированного имени или адреса сервера вместе с необязательными сведениями о порте и пользователе.
The authority component is preceded by a double slash ("//") and is terminated by the next slash ("/"), question mark ("?"), or number sign ("#") character, or by the end of the URI.
Компоненту authority предшествует двойная косая черта («//»), и он завершается следующим символом косой черты («/»), знаком вопроса («?») или знаком решётки («#»), либо концом URI.
authority = [ userinfo "@" ] host [ ":" port ]
authority = [ userinfo "@" ] host [ ":" port ]
URI producers and normalizers should omit the ":" delimiter that separates host from port if the port component is empty. Some schemes do not allow the userinfo and/or port subcomponents.
Производители и нормализаторы URI должны опускать разделитель «:», отделяющий host от port, если компонент порта пуст. Некоторые схемы не допускают подкомпоненты userinfo и/или port.
If a URI contains an authority component, then the path component must either be empty or begin with a slash ("/") character. Non- validating parsers (those that merely separate a URI reference into its major components) will often ignore the subcomponent structure of authority, treating it as an opaque string from the double-slash to the first terminating delimiter, until such time as the URI is dereferenced.
Если URI содержит компонент authority, то компонент пути должен быть либо пустым, либо начинаться с символа косой черты («/»). Непроверяющие анализаторы (те, что лишь разделяют ссылку URI на основные компоненты) часто игнорируют структуру подкомпонентов authority, рассматривая его как непрозрачную строку от двойной косой черты до первого завершающего разделителя, вплоть до момента разыменования URI.
3.2.1. User Information
3.2.1. Сведения о пользователе
The userinfo subcomponent may consist of a user name and, optionally, scheme-specific information about how to gain authorization to access the resource. The user information, if present, is followed by a commercial at-sign ("@") that delimits it from the host.
Подкомпонент userinfo может состоять из имени пользователя и, необязательно, информации, специфичной для схемы, о том, как получить авторизацию для доступа к ресурсу. Сведения о пользователе, если они присутствуют, сопровождаются коммерческим знаком «эт» («@»), который отделяет их от host.
userinfo = *( unreserved / pct-encoded / sub-delims / ":" )
userinfo = *( unreserved / pct-encoded / sub-delims / ":" )
Use of the format "user:password" in the userinfo field is deprecated. Applications should not render as clear text any data after the first colon (":") character found within a userinfo subcomponent unless the data after the colon is the empty string (indicating no password). Applications may choose to ignore or reject such data when it is received as part of a reference and should reject the storage of such data in unencrypted form. The passing of authentication information in clear text has proven to be a security risk in almost every case where it has been used.
Использование формата «user:password» в поле userinfo не рекомендуется. Приложения не должны отображать открытым текстом данные после первого символа двоеточия («:»), найденного в подкомпоненте userinfo, если только данные после двоеточия не являются пустой строкой (что указывает на отсутствие пароля). Приложения могут игнорировать или отклонять такие данные при получении в составе ссылки и должны отклонять хранение таких данных в незашифрованном виде. Передача аутентификационной информации открытым текстом оказалась угрозой безопасности почти во всех случаях её использования.
Applications that render a URI for the sake of user feedback, such as in graphical hypertext browsing, should render userinfo in a way that is distinguished from the rest of a URI, when feasible. Such rendering will assist the user in cases where the userinfo has been misleadingly crafted to look like a trusted domain name (Section 7.6).
Приложения, отображающие URI для обратной связи с пользователем, например при графическом просмотре гипертекста, должны, когда это осуществимо, отображать userinfo так, чтобы он отличался от остальной части URI. Такое отображение поможет пользователю в случаях, когда userinfo был обманчиво сформирован так, чтобы выглядеть как доверенное доменное имя (раздел 7.6).
3.2.2. Host
3.2.2. Компонент host
The host subcomponent of authority is identified by an IP literal encapsulated within square brackets, an IPv4 address in dotted- decimal form, or a registered name. The host subcomponent is case- insensitive. The presence of a host subcomponent within a URI does not imply that the scheme requires access to the given host on the Internet. In many cases, the host syntax is used only for the sake of reusing the existing registration process created and deployed for DNS, thus obtaining a globally unique name without the cost of deploying another registry. However, such use comes with its own costs: domain name ownership may change over time for reasons not anticipated by the URI producer. In other cases, the data within the host component identifies a registered name that has nothing to do with an Internet host. We use the name "host" for the ABNF rule because that is its most common purpose, not its only purpose.
Подкомпонент host компонента authority идентифицируется IP-литералом, заключённым в квадратные скобки, IPv4-адресом в точечно-десятичной форме или зарегистрированным именем. Подкомпонент host нечувствителен к регистру. Наличие подкомпонента host в URI не означает, что схема требует доступа к данному host в Интернете. Во многих случаях синтаксис host используется лишь для повторного использования существующего процесса регистрации, созданного и развёрнутого для DNS, что позволяет получить глобально уникальное имя без затрат на развёртывание другого реестра. Однако такое использование имеет свою цену: право собственности на доменное имя может со временем измениться по причинам, не предусмотренным производителем URI. В других случаях данные внутри компонента host идентифицируют зарегистрированное имя, не имеющее отношения к интернет-хосту. Мы используем имя «host» для правила ABNF потому, что это его наиболее частое назначение, а не единственное.
host = IP-literal / IPv4address / reg-name
host = IP-literal / IPv4address / reg-name
The syntax rule for host is ambiguous because it does not completely distinguish between an IPv4address and a reg-name. In order to disambiguate the syntax, we apply the "first-match-wins" algorithm: If host matches the rule for IPv4address, then it should be considered an IPv4 address literal and not a reg-name. Although host is case-insensitive, producers and normalizers should use lowercase for registered names and hexadecimal addresses for the sake of uniformity, while only using uppercase letters for percent-encodings.
Синтаксическое правило для host неоднозначно, поскольку оно не полностью различает IPv4address и reg-name. Чтобы устранить неоднозначность синтаксиса, мы применяем алгоритм «первое совпадение выигрывает»: если host соответствует правилу IPv4address, он должен считаться литералом IPv4-адреса, а не reg-name. Хотя host нечувствителен к регистру, производители и нормализаторы должны для единообразия использовать нижний регистр для зарегистрированных имён и шестнадцатеричные адреса, используя буквы верхнего регистра только для процентных экранирований.
A host identified by an Internet Protocol literal address, version 6 [RFC3513] or later, is distinguished by enclosing the IP literal within square brackets ("[" and "]"). This is the only place where square bracket characters are allowed in the URI syntax. In anticipation of future, as-yet-undefined IP literal address formats, an implementation may use an optional version flag to indicate such a format explicitly rather than rely on heuristic determination.

Это единственное место в синтаксисе URI, где допускаются символы квадратных скобок. В ожидании будущих, пока ещё не определённых форматов литералов IP-адресов реализация может использовать необязательный флаг версии, чтобы явно указать такой формат, а не полагаться на эвристическое определение.
IP-literal = "[" ( IPv6address / IPvFuture ) "]"
IP-literal = "[" ( IPv6address / IPvFuture ) "]"
IPvFuture = "v" 1*HEXDIG "." 1*( unreserved / sub-delims / ":" )
IPvFuture = "v" 1*HEXDIG "." 1*( unreserved / sub-delims / ":" )
The version flag does not indicate the IP version; rather, it indicates future versions of the literal format. As such, implementations must not provide the version flag for the existing IPv4 and IPv6 literal address forms described below. If a URI containing an IP-literal that starts with "v" (case-insensitive), indicating that the version flag is present, is dereferenced by an application that does not know the meaning of that version flag, then the application should return an appropriate error for "address mechanism not supported".
Флаг версии не указывает версию IP; скорее он указывает будущие версии формата литерала. Поэтому реализации не должны предоставлять флаг версии для существующих форм литералов IPv4 и IPv6, описанных ниже. Если URI, содержащий IP-literal, начинающийся с «v» (без учёта регистра), что указывает на наличие флага версии, разыменовывается приложением, которое не знает значения этого флага версии, то приложение должно вернуть подходящую ошибку «address mechanism not supported».
A host identified by an IPv6 literal address is represented inside the square brackets without a preceding version flag. The ABNF provided here is a translation of the text definition of an IPv6 literal address provided in [RFC3513]. This syntax does not support IPv6 scoped addressing zone identifiers. A 128-bit IPv6 address is divided into eight 16-bit pieces. Each piece is represented numerically in case-insensitive hexadecimal, using one to four hexadecimal digits (leading zeroes are permitted). The eight encoded pieces are given most-significant first, separated by colon characters. Optionally, the least-significant two pieces may instead be represented in IPv4 address textual format. A sequence of one or more consecutive zero-valued 16-bit pieces within the address may be elided, omitting all their digits and leaving exactly two consecutive colons in their place to mark the elision.
Host, идентифицируемый литералом IPv6-адреса, представляется внутри квадратных скобок без предшествующего флага версии. Приведённая здесь ABNF является переводом текстового определения литерала IPv6-адреса из [RFC3513]. Этот синтаксис не поддерживает идентификаторы зон области действия IPv6 (scoped addressing zone identifiers). 128-битный IPv6-адрес делится на восемь 16-битных частей. Каждая часть представляется численно в шестнадцатеричном виде без учёта регистра, с использованием от одной до четырёх шестнадцатеричных цифр (ведущие нули допускаются). Восемь закодированных частей приводятся от старшей к младшей, разделённые символами двоеточия. Необязательно две младшие части могут быть вместо этого представлены в текстовом формате IPv4-адреса. A host identified by a registered name is a sequence of characters usually intended for lookup within a locally defined host or service name registry, though the URI's scheme-specific semantics may require that a specific registry (or fixed name table) be used instead. The most common name registry mechanism is the Domain Name System (DNS). A registered name intended for lookup in the DNS uses the syntax defined in Section 3.5 of [RFC1034] and Section 2.1 of [RFC1123]. Such a name consists of a sequence of domain labels separated by ".", each domain label starting and ending with an alphanumeric character and possibly also containing "-" characters. The rightmost domain label of a fully qualified domain name in DNS may be followed by a single "." and should be if it is necessary to distinguish between the complete domain name and some local domain.
Host, идентифицируемый зарегистрированным именем, — это последовательность символов, обычно предназначенная для поиска в локально определённом реестре имён хостов или служб, хотя семантика, специфичная для схемы URI, может требовать использования вместо него конкретного реестра (или фиксированной таблицы имён). Наиболее распространённым механизмом реестра имён является система доменных имён (Domain Name System, DNS). Зарегистрированное имя, предназначенное для поиска в DNS, использует синтаксис, определённый в разделе 3.5 [RFC1034] и разделе 2.1 [RFC1123]. Такое имя состоит из последовательности доменных меток, разделённых «.», причём каждая доменная метка начинается и заканчивается буквенно-цифровым символом и может также содержать символы «-». За крайней правой доменной меткой полного доменного имени в DNS может следовать одна «.», и она должна следовать, если необходимо отличить полное доменное имя от некоторого локального домена.
reg-name = *( unreserved / pct-encoded / sub-delims )
reg-name = *( unreserved / pct-encoded / sub-delims )
If the URI scheme defines a default for host, then that default applies when the host subcomponent is undefined or when the registered name is empty (zero length). For example, the "file" URI scheme is defined so that no authority, an empty host, and "localhost" all mean the end-user's machine, whereas the "http" scheme considers a missing authority or empty host invalid.
Если схема URI определяет значение по умолчанию для host, это значение по умолчанию применяется, когда подкомпонент host не определён или когда зарегистрированное имя пустое (нулевой длины). Например, схема URI «file» определена так, что отсутствие authority, пустой host и «localhost» означают машину конечного пользователя, тогда как схема «http» считает отсутствующий authority или пустой host недопустимыми.
This specification does not mandate a particular registered name lookup technology and therefore does not restrict the syntax of reg- name beyond what is necessary for interoperability. Instead, it delegates the issue of registered name syntax conformance to the operating system of each application performing URI resolution, and that operating system decides what it will allow for the purpose of host identification. A URI resolution implementation might use DNS, host tables, yellow pages, NetInfo, WINS, or any other system for lookup of registered names. However, a globally scoped naming system, such as DNS fully qualified domain names, is necessary for URIs intended to have global scope. URI producers should use names that conform to the DNS syntax, even when use of DNS is not immediately apparent, and should limit these names to no more than 255 characters in length.
Настоящая спецификация не предписывает конкретную технологию поиска зарегистрированных имён и поэтому не ограничивает синтаксис reg-name сверх того, что необходимо для совместимости. Вместо этого она передаёт вопрос соответствия синтаксису зарегистрированных имён операционной системе каждого приложения, выполняющего разрешение URI, и эта операционная система решает, что она допустит для целей идентификации host. Реализация разрешения URI может использовать DNS, таблицы хостов, yellow pages, NetInfo, WINS или любую другую систему для поиска зарегистрированных имён. Однако для URI, предназначенных иметь глобальную область действия, необходима глобально масштабируемая система имён, такая как полные доменные имена DNS. Производители URI должны использовать имена, соответствующие синтаксису DNS, даже когда использование DNS не очевидно, и ограничивать длину этих имён не более чем 255 символами.
The reg-name syntax allows percent-encoded octets in order to represent non-ASCII registered names in a uniform way that is independent of the underlying name resolution technology. Non-ASCII characters must first be encoded according to UTF-8 [STD63], and then each octet of the corresponding UTF-8 sequence must be percent- encoded to be represented as URI characters. URI producing applications must not use percent-encoding in host unless it is used to represent a UTF-8 character sequence. When a non-ASCII registered name represents an internationalized domain name intended for resolution via the DNS, the name must be transformed to the IDNA encoding [RFC3490] prior to name lookup. URI producers should provide these registered names in the IDNA encoding, rather than a percent-encoding, if they wish to maximize interoperability with legacy URI resolvers.
Синтаксис reg-name допускает процентно-экранированные октеты, чтобы единообразно, независимо от лежащей в основе технологии разрешения имён, представлять не-ASCII зарегистрированные имена. Не-ASCII символы должны сначала быть закодированы согласно UTF-8 [STD63], а затем каждый октет соответствующей последовательности UTF-8 должен быть процентно экранирован, чтобы представляться как символы URI. Приложения, производящие URI, не должны использовать процентное экранирование в host, если только оно не служит для представления последовательности символов UTF-8. Когда не-ASCII зарегистрированное имя представляет интернационализированное доменное имя, предназначенное для разрешения через DNS, имя должно быть преобразовано в кодировку IDNA [RFC3490] до поиска имени. Производители URI должны предоставлять такие зарегистрированные имена в кодировке IDNA, а не в виде процентного экранирования, если они хотят максимально повысить совместимость со старыми распознавателями URI.
3.2.3. Port
3.2.3. Порт
The port subcomponent of authority is designated by an optional port number in decimal following the host and delimited from it by a single colon (":") character.
Подкомпонент port компонента authority обозначается необязательным номером порта в десятичном виде, следующим за host и отделённым от него одним символом двоеточия («:»).
port = *DIGIT
port = *DIGIT
A scheme may define a default port. For example, the "http" scheme defines a default port of "80", corresponding to its reserved TCP port number. The type of port designated by the port number (e.g., TCP, UDP, SCTP) is defined by the URI scheme. URI producers and normalizers should omit the port component and its ":" delimiter if port is empty or if its value would be the same as that of the scheme's default.
Схема может определять порт по умолчанию. Например, схема «http» определяет порт по умолчанию «80», соответствующий её зарезервированному номеру порта TCP. Тип порта, обозначаемого номером порта (например, TCP, UDP, SCTP), определяется схемой URI. Производители и нормализаторы URI должны опускать компонент port и его разделитель «:», если порт пуст или если его значение совпадало бы со значением по умолчанию для схемы.
3.3. Path
3.3. Путь
The path component contains data, usually organized in hierarchical form, that, along with data in the non-hierarchical query component (Section 3.4), serves to identify a resource within the scope of the URI's scheme and naming authority (if any). The path is terminated by the first question mark ("?") or number sign ("#") character, or by the end of the URI.
Компонент пути содержит данные, обычно организованные в иерархической форме, которые вместе с данными в неиерархическом компоненте query (раздел 3.4) служат для идентификации ресурса в пределах области действия схемы URI и органа именования (если таковой имеется). Путь завершается первым символом знака вопроса («?») или знака решётки («#»), либо концом URI.
If a URI contains an authority component, then the path component must either be empty or begin with a slash ("/") character. If a URI does not contain an authority component, then the path cannot begin with two slash characters ("//"). In addition, a URI reference (Section 4.1) may be a relative-path reference, in which case the first path segment cannot contain a colon (":") character. The ABNF requires five separate rules to disambiguate these cases, only one of which will match the path substring within a given URI reference. We use the generic term "path component" to describe the URI substring matched by the parser to one of these rules.
Если URI содержит компонент authority, то компонент пути должен быть либо пустым, либо начинаться с символа косой черты («/»). Если URI не содержит компонента authority, то путь не может начинаться с двух символов косой черты («//»). Кроме того, ссылка URI (раздел 4.1) может быть ссылкой с относительным путём, и в этом случае первый сегмент пути не может содержать символ двоеточия («:»). ABNF требует пяти отдельных правил для устранения неоднозначности этих случаев, и только одно из них будет соответствовать подстроке пути в данной ссылке URI. Мы используем общий термин «компонент пути» для описания подстроки URI, сопоставленной анализатором одному из этих правил.
path = path-abempty ; begins with "/" or is empty / path-absolute ; begins with "/" but not "//" / path-noscheme ; begins with a non-colon segment / path-rootless ; begins with a segment / path-empty ; zero characters path-abempty = *( "/" segment ) path-absolute = "/" [ segment-nz *( "/" segment ) ] path-noscheme = segment-nz-nc *( "/" segment ) path-rootless = segment-nz *( "/" segment ) path-empty = 0<pchar> segment = *pchar segment-nz = 1*pchar segment-nz-nc = 1*( unreserved / pct-encoded / sub-delims / "@" ) ; non-zero-length segment without any colon ":" pchar = unreserved / pct-encoded / sub-delims / ":" / "@"

A path consists of a sequence of path segments separated by a slash ("/") character. A path is always defined for a URI, though the defined path may be empty (zero length). Use of the slash character to indicate hierarchy is only required when a URI will be used as the context for relative references. For example, the URI <mailto:fred@example.com> has a path of "fred@example.com", whereas the URI <foo://info.example.com?fred> has an empty path.
Путь состоит из последовательности сегментов пути, разделённых символом косой черты («/»). Путь всегда определён для URI, хотя определённый путь может быть пустым (нулевой длины). Использование символа косой черты для указания иерархии требуется только тогда, когда URI будет использоваться как контекст для относительных ссылок. Например, URI <mailto:fred@example.com> имеет путь «fred@example.com», тогда как URI <foo://info.example.com?fred> имеет пустой путь.
The path segments "." and "..", also known as dot-segments, are defined for relative reference within the path name hierarchy. They are intended for use at the beginning of a relative-path reference (Section 4.2) to indicate relative position within the hierarchical tree of names. This is similar to their role within some operating systems' file directory structures to indicate the current directory and parent directory, respectively. However, unlike in a file system, these dot-segments are only interpreted within the URI path hierarchy and are removed as part of the resolution process (Section 5.2).
Сегменты пути «.» и «..», также известные как точечные сегменты, определены для относительных ссылок внутри иерархии имён пути. Они предназначены для использования в начале ссылки с относительным путём (раздел 4.2), чтобы указать относительное положение в иерархическом дереве имён. Это похоже на их роль в структурах файловых каталогов некоторых операционных систем, где они обозначают, соответственно, текущий каталог и родительский каталог. Однако, в отличие от файловой системы, эти точечные сегменты интерпретируются только внутри иерархии пути URI и удаляются как часть процесса разрешения (раздел 5.2).
Aside from dot-segments in hierarchical paths, a path segment is considered opaque by the generic syntax. URI producing applications often use the reserved characters allowed in a segment to delimit scheme-specific or dereference-handler-specific subcomponents. For example, the semicolon (";") and equals ("=") reserved characters are often used to delimit parameters and parameter values applicable to that segment. The comma (",") reserved character is often used for similar purposes. For example, one URI producer might use a segment such as "name;v=1.1" to indicate a reference to version 1.1 of "name", whereas another might use a segment such as "name,1.1" to indicate the same. Parameter types may be defined by scheme-specific semantics, but in most cases the syntax of a parameter is specific to the implementation of the URI's dereferencing algorithm.
Помимо точечных сегментов в иерархических путях, сегмент пути считается непрозрачным для общего синтаксиса. Приложения, производящие URI, часто используют зарезервированные символы, допустимые в сегменте, для разделения подкомпонентов, специфичных для схемы или для обработчика разыменования. Например, зарезервированные символы точки с запятой («;») и знака равенства («=») часто используются для разделения параметров и значений параметров, применимых к этому сегменту. Зарезервированный символ запятой («,») часто используется для аналогичных целей. Например, один производитель URI может использовать сегмент вида «name;v=1.1», чтобы указать ссылку на версию 1.1 «name», тогда как другой может использовать сегмент вида «name,1.1» для обозначения того же. Типы параметров могут определяться семантикой, специфичной для схемы, но в большинстве случаев синтаксис параметра специфичен для реализации алгоритма разыменования URI.
3.4. Query
3.4. Запрос
The query component contains non-hierarchical data that, along with data in the path component (Section 3.3), serves to identify a resource within the scope of the URI's scheme and naming authority (if any). The query component is indicated by the first question mark ("?") character and terminated by a number sign ("#") character or by the end of the URI.
Компонент query содержит неиерархические данные, которые вместе с данными в компоненте пути (раздел 3.3) служат для идентификации ресурса в пределах области действия схемы URI и органа именования (если таковой имеется). Компонент query обозначается первым символом знака вопроса («?») и завершается символом знака решётки («#») или концом URI.
query = *( pchar / "/" / "?" )
query = *( pchar / "/" / "?" )
The characters slash ("/") and question mark ("?") may represent data within the query component. Beware that some older, erroneous implementations may not handle such data correctly when it is used as the base URI for relative references (Section 5.1), apparently because they fail to distinguish query data from path data when looking for hierarchical separators. However, as query components are often used to carry identifying information in the form of "key=value" pairs and one frequently used value is a reference to another URI, it is sometimes better for usability to avoid percent- encoding those characters.
Символы косой черты («/») и знака вопроса («?») могут представлять данные внутри компонента query. Имейте в виду, что некоторые более старые, ошибочные реализации могут обрабатывать такие данные некорректно, когда они используются как базовый URI для относительных ссылок (раздел 5.1), по-видимому, потому что они не различают данные query и данные пути при поиске иерархических разделителей. Однако, поскольку компоненты query часто используются для переноса идентифицирующей информации в виде пар «key=value», а одним из часто используемых значений является ссылка на другой URI, иногда для удобства использования лучше избегать процентного экранирования этих символов.
3.5. Fragment
3.5. Фрагмент
The fragment identifier component of a URI allows indirect identification of a secondary resource by reference to a primary resource and additional identifying information. The identified secondary resource may be some portion or subset of the primary resource, some view on representations of the primary resource, or some other resource defined or described by those representations. A fragment identifier component is indicated by the presence of a number sign ("#") character and terminated by the end of the URI.
Компонент идентификатора фрагмента URI позволяет косвенно идентифицировать вторичный ресурс посредством ссылки на первичный ресурс и дополнительной идентифицирующей информации. Идентифицируемый вторичный ресурс может быть некоторой частью или подмножеством первичного ресурса, некоторым представлением представлений первичного ресурса или иным ресурсом, определённым или описанным этими представлениями. Компонент идентификатора фрагмента обозначается наличием символа знака решётки («#») и завершается концом URI.
fragment = *( pchar / "/" / "?" )
fragment = *( pchar / "/" / "?" )
The semantics of a fragment identifier are defined by the set of representations that might result from a retrieval action on the primary resource. The fragment's format and resolution is therefore dependent on the media type [RFC2046] of a potentially retrieved representation, even though such a retrieval is only performed if the URI is dereferenced. If no such representation exists, then the semantics of the fragment are considered unknown and are effectively unconstrained. Fragment identifier semantics are independent of the URI scheme and thus cannot be redefined by scheme specifications.
Семантика идентификатора фрагмента определяется набором представлений, которые могут быть получены в результате действия извлечения по первичному ресурсу. Поэтому формат и разрешение фрагмента зависят от типа носителя [RFC2046] потенциально извлекаемого представления, даже если такое извлечение выполняется только при разыменовании URI. Если такого представления не существует, семантика фрагмента считается неизвестной и фактически неограниченной. Семантика идентификатора фрагмента не зависит от схемы URI и потому не может быть переопределена спецификациями схем.
Individual media types may define their own restrictions on or structures within the fragment identifier syntax for specifying different types of subsets, views, or external references that are identifiable as secondary resources by that media type. If the primary resource has multiple representations, as is often the case for resources whose representation is selected based on attributes of the retrieval request (a.k.a., content negotiation), then whatever is identified by the fragment should be consistent across all of those representations. Each representation should either define the fragment so that it corresponds to the same secondary resource, regardless of how it is represented, or should leave the fragment undefined (i.e., not found). As with any URI, use of a fragment identifier component does not imply that a retrieval action will take place. A URI with a fragment identifier may be used to refer to the secondary resource without any implication that the primary resource is accessible or will ever be accessed.
Отдельные типы носителей могут определять собственные ограничения или структуры в синтаксисе идентификатора фрагмента для указания различных типов подмножеств, представлений или внешних ссылок, идентифицируемых этим типом носителя как вторичные ресурсы. Если первичный ресурс имеет несколько представлений, как часто бывает с ресурсами, представление которых выбирается на основе атрибутов запроса извлечения (иначе говоря, согласования содержимого), то, что идентифицируется фрагментом, должно быть согласовано во всех этих представлениях. Каждое представление должно либо определять фрагмент так, чтобы он соответствовал одному и тому же вторичному ресурсу независимо от способа представления, либо оставлять фрагмент неопределённым (то есть ненайденным). Как и в случае любого URI, использование компонента идентификатора фрагмента не подразумевает, что действие извлечения будет выполнено. URI с идентификатором фрагмента может использоваться для ссылки на вторичный ресурс без какого-либо предположения о том, что первичный ресурс доступен или когда-либо будет доступен.
Fragment identifiers have a special role in information retrieval systems as the primary form of client-side indirect referencing, allowing an author to specifically identify aspects of an existing resource that are only indirectly provided by the resource owner. As such, the fragment identifier is not used in the scheme-specific processing of a URI; instead, the fragment identifier is separated from the rest of the URI prior to a dereference, and thus the identifying information within the fragment itself is dereferenced solely by the user agent, regardless of the URI scheme. Although this separate handling is often perceived to be a loss of information, particularly for accurate redirection of references as resources move over time, it also serves to prevent information providers from denying reference authors the right to refer to information within a resource selectively. Indirect referencing also provides additional flexibility and extensibility to systems that use URIs, as new media types are easier to define and deploy than new schemes of identification.
Идентификаторы фрагментов играют особую роль в системах поиска информации как основная форма косвенного указания на стороне клиента, позволяя автору конкретно указать аспекты существующего ресурса, которые предоставляются владельцем ресурса лишь косвенно. Таким образом, идентификатор фрагмента не используется при обработке URI, специфичной для схемы; вместо этого идентификатор фрагмента отделяется от остальной части URI до разыменования, и потому идентифицирующая информация внутри самого фрагмента разыменовывается исключительно пользовательским агентом, независимо от схемы URI. Хотя такая отдельная обработка часто воспринимается как потеря информации, особенно для точного перенаправления ссылок при перемещении ресурсов с течением времени, она также не позволяет поставщикам информации лишать авторов ссылок права выборочно ссылаться на информацию внутри ресурса. Косвенное указание также придаёт дополнительную гибкость и расширяемость системам, использующим URI, поскольку новые типы носителей проще определить и развернуть, чем новые схемы идентификации.
The characters slash ("/") and question mark ("?") are allowed to represent data within the fragment identifier. Beware that some older, erroneous implementations may not handle this data correctly when it is used as the base URI for relative references (Section 5.1).
Символы косой черты («/») и знака вопроса («?») допускаются для представления данных внутри идентификатора фрагмента. Имейте в виду, что некоторые более старые, ошибочные реализации могут обрабатывать эти данные некорректно, когда они используются как базовый URI для относительных ссылок (раздел 5.1).
4. Usage
4. Использование
When applications make reference to a URI, they do not always use the full form of reference defined by the "URI" syntax rule. To save space and take advantage of hierarchical locality, many Internet protocol elements and media type formats allow an abbreviation of a URI, whereas others restrict the syntax to a particular form of URI. We define the most common forms of reference syntax in this specification because they impact and depend upon the design of the generic syntax, requiring a uniform parsing algorithm in order to be interpreted consistently.
Когда приложения ссылаются на URI, они не всегда используют полную форму ссылки, определённую синтаксическим правилом «URI». Чтобы сэкономить место и воспользоваться преимуществами иерархической локальности, многие элементы протоколов Интернета и форматы типов носителей допускают сокращение URI, тогда как другие ограничивают синтаксис определённой формой URI. В настоящей спецификации мы определяем наиболее распространённые формы синтаксиса ссылок, поскольку они влияют на проектирование общего синтаксиса и зависят от него, требуя единообразного алгоритма разбора для согласованной интерпретации.
4.1. URI Reference
4.1. Ссылка URI
URI-reference is used to denote the most common usage of a resource identifier. URI-reference = URI / relative-ref
URI-reference применяется для обозначения наиболее частого случая использования идентификатора ресурса. URI-reference = URI / relative-ref
A URI-reference is either a URI or a relative reference. If the URI-reference's prefix does not match the syntax of a scheme followed by its colon separator, then the URI-reference is a relative reference.
URI-reference — это либо URI, либо относительная ссылка. Если префикс URI-reference не соответствует синтаксису схемы, за которым следует её разделитель-двоеточие, то URI-reference является относительной ссылкой.
A URI-reference is typically parsed first into the five URI components, in order to determine what components are present and whether the reference is relative. Then, each component is parsed for its subparts and their validation. The ABNF of URI-reference, along with the "first-match-wins" disambiguation rule, is sufficient to define a validating parser for the generic syntax. Readers familiar with regular expressions should see Appendix B for an example of a non-validating URI-reference parser that will take any given string and extract the URI components.
Обычно URI-reference сначала разбирается на пять компонентов URI, чтобы определить, какие компоненты присутствуют и является ли ссылка относительной. Затем каждый компонент разбирается на свои части и проверяется их допустимость. ABNF для URI-reference вместе с правилом устранения неоднозначности «первое совпадение выигрывает» достаточно для определения проверяющего анализатора общего синтаксиса. Читателям, знакомым с регулярными выражениями, следует обратиться к Приложению B, где приведён пример непроверяющего анализатора URI-reference, который примет любую заданную строку и извлечёт компоненты URI.
4.2. Relative Reference
4.2. Относительная ссылка
A relative reference takes advantage of the hierarchical syntax (Section 1.2.3) to express a URI reference relative to the name space of another hierarchical URI.
Относительная ссылка использует иерархический синтаксис (раздел 1.2.3), чтобы выразить ссылку URI относительно пространства имён другого иерархического URI.
relative-ref = relative-part [ "?" query ] [ "#" fragment ] relative-part = "//" authority path-abempty / path-absolute / path-noscheme / path-empty
relative-ref = relative-part [ "?" query ] [ "#" fragment ] relative-part = "//" authority path-abempty / path-absolute / path-noscheme / path-empty
The URI referred to by a relative reference, also known as the target URI, is obtained by applying the reference resolution algorithm of Section 5.
URI, на который ссылается относительная ссылка, — он также называется целевым URI, — получается путём применения алгоритма разрешения ссылок, описанного в разделе 5.
A relative reference that begins with two slash characters is termed a network-path reference; such references are rarely used. A relative reference that begins with a single slash character is termed an absolute-path reference. A relative reference that does not begin with a slash character is termed a relative-path reference.
Относительная ссылка, начинающаяся с двух символов косой черты, называется сетевой ссылкой (network-path reference); такие ссылки используются редко. Относительная ссылка, начинающаяся с одного символа косой черты, называется ссылкой с абсолютным путём (absolute-path reference). Относительная ссылка, не начинающаяся с символа косой черты, называется ссылкой с относительным путём (relative-path reference).
A path segment that contains a colon character (e.g., "this:that") cannot be used as the first segment of a relative-path reference, as it would be mistaken for a scheme name. Such a segment must be preceded by a dot-segment (e.g., "./this:that") to make a relative- path reference.
Сегмент пути, содержащий символ двоеточия (например, «this:that»), нельзя использовать как первый сегмент ссылки с относительным путём, поскольку его можно принять за имя схемы. Такому сегменту должен предшествовать точечный сегмент (например, «./this:that»), чтобы получилась ссылка с относительным путём.
4.3. Absolute URI
4.3. Абсолютный URI
Some protocol elements allow only the absolute form of a URI without a fragment identifier. For example, defining a base URI for later use by relative references calls for an absolute-URI syntax rule that does not allow a fragment.
Некоторые элементы протоколов допускают только абсолютную форму URI без идентификатора фрагмента. Например, определение базового URI для последующего использования относительными ссылками требует синтаксического правила absolute-URI, которое не допускает фрагмент.
absolute-URI = scheme ":" hier-part [ "?" query ]
absolute-URI = scheme ":" hier-part [ "?" query ]
URI scheme specifications must define their own syntax so that all strings matching their scheme-specific syntax will also match the <absolute-URI> grammar. Scheme specifications will not define fragment identifier syntax or usage, regardless of its applicability to resources identifiable via that scheme, as fragment identification is orthogonal to scheme definition. However, scheme specifications are encouraged to include a wide range of examples, including examples that show use of the scheme's URIs with fragment identifiers when such usage is appropriate.
Спецификации схем URI должны определять собственный синтаксис так, чтобы все строки, соответствующие их синтаксису, специфичному для схемы, также соответствовали грамматике <absolute-URI>. Спецификации схем не определяют синтаксис или использование идентификатора фрагмента, независимо от его применимости к ресурсам, идентифицируемым через эту схему, поскольку идентификация фрагмента ортогональна определению схемы. Однако спецификациям схем рекомендуется включать широкий спектр примеров, в том числе примеры использования URI этой схемы с идентификаторами фрагментов, когда такое использование уместно.
4.4. Same-Document Reference
4.4. Ссылка на тот же документ
When a URI reference refers to a URI that is, aside from its fragment component (if any), identical to the base URI (Section 5.1), that reference is called a "same-document" reference. The most frequent examples of same-document references are relative references that are empty or include only the number sign ("#") separator followed by a fragment identifier.
Когда ссылка URI ссылается на URI, который, если не считать его компонента фрагмента (если таковой имеется), идентичен базовому URI (раздел 5.1), такая ссылка называется ссылкой «на тот же документ» (same-document). Наиболее частыми примерами ссылок на тот же документ являются относительные ссылки, которые пусты или содержат только разделитель — знак решётки («#»), — за которым следует идентификатор фрагмента.
When a same-document reference is dereferenced for a retrieval action, the target of that reference is defined to be within the same entity (representation, document, or message) as the reference; therefore, a dereference should not result in a new retrieval action.
Когда ссылка на тот же документ разыменовывается для действия извлечения, цель этой ссылки определяется как находящаяся внутри той же сущности (представления, документа или сообщения), что и ссылка; поэтому разыменование не должно приводить к новому действию извлечения.
Normalization of the base and target URIs prior to their comparison, as described in Sections 6.2.2 and 6.2.3, is allowed but rarely performed in practice. Normalization may increase the set of same- document references, which may be of benefit to some caching applications. As such, reference authors should not assume that a slightly different, though equivalent, reference URI will (or will not) be interpreted as a same-document reference by any given application.
Нормализация базового и целевого URI перед их сравнением, как описано в разделах 6.2.2 и 6.2.3, допускается, но на практике выполняется редко. Нормализация может увеличить набор ссылок на тот же документ, что может быть полезно некоторым приложениям кэширования. Поэтому авторы ссылок не должны предполагать, что немного отличающийся, хотя и эквивалентный URI ссылки будет (или не будет) интерпретирован как ссылка на тот же документ каким-либо данным приложением.

В результате суффиксные ссылки ограничены местами, где нет определённого базового URI, — например, диалоговыми окнами и офлайновыми рекламными объявлениями.
5. Reference Resolution
5. Разрешение ссылок
This section defines the process of resolving a URI reference within a context that allows relative references so that the result is a string matching the <URI> syntax rule of Section 3.

Aside from fragment-only references (Section 4.4), relative references are only usable when a base URI is known. A base URI must be established by the parser prior to parsing URI references that might be relative. A base URI must conform to the <absolute-URI> syntax rule (Section 4.3). If the base URI is obtained from a URI reference, then that reference must be converted to absolute form and stripped of any fragment component prior to its use as a base URI. Базовый URI должен быть установлен анализатором до разбора ссылок URI, которые могут быть относительными. Базовый URI должен соответствовать синтаксическому правилу <absolute-URI> (раздел 4.3). 5.1.1. Base URI Embedded in Content
5.1.1. Базовый URI, встроенный в содержимое
Within certain media types, a base URI for relative references can be embedded within the content itself so that it can be readily obtained by a parser. This can be useful for descriptive documents, such as tables of contents, which may be transmitted to others through protocols other than their usual retrieval context (e.g., email or USENET news).
В некоторых типах носителей базовый URI для относительных ссылок может быть встроен в само содержимое, чтобы анализатор мог легко его получить. Это может быть полезно для описательных документов, таких как оглавления, которые могут передаваться другим через протоколы, отличные от их обычного контекста извлечения (например, электронная почта или новости USENET).
It is beyond the scope of this specification to specify how, for each media type, a base URI can be embedded. The appropriate syntax, when available, is described by the data format specification associated with each media type.
Определение того, как для каждого типа носителя может быть встроен базовый URI, выходит за рамки настоящей спецификации. Подходящий синтаксис, когда он имеется, описывается спецификацией формата данных, связанной с каждым типом носителя.
5.1.2. Base URI from the Encapsulating Entity
5.1.2. Базовый URI из инкапсулирующей сущности
If no base URI is embedded, the base URI is defined by the representation's retrieval context. For a document that is enclosed within another entity, such as a message or archive, the retrieval context is that entity. Thus, the default base URI of a representation is the base URI of the entity in which the representation is encapsulated. A mechanism for embedding a base URI within MIME container types (e.g., the message and multipart types) is defined by MHTML [RFC2557]. Protocols that do not use the MIME message header syntax, but that do allow some form of tagged metadata to be included within messages, may define their own syntax for defining a base URI as part of a message.
Если базовый URI не встроен, он определяется контекстом извлечения представления. Для документа, заключённого в другую сущность, например сообщение или архив, контекстом извлечения является эта сущность. Таким образом, базовый URI по умолчанию для представления — это базовый URI сущности, в которую инкапсулировано представление. Механизм встраивания базового URI в типы контейнеров MIME (например, типы message и multipart) определён в MHTML [RFC2557]. Протоколы, которые не используют синтаксис заголовков сообщений MIME, но допускают включение в сообщения некоторой формы помеченных метаданных, могут определять собственный синтаксис для определения базового URI как части сообщения.
5.1.3. Base URI from the Retrieval URI
5.1.3. Базовый URI из URI извлечения
If no base URI is embedded and the representation is not encapsulated within some other entity, then, if a URI was used to retrieve the representation, that URI shall be considered the base URI. Note that if the retrieval was the result of a redirected request, the last URI used (i.e., the URI that resulted in the actual retrieval of the representation) is the base URI.
Если базовый URI не встроен и представление не инкапсулировано в какую-либо другую сущность, то, если для извлечения представления использовался URI, этот URI следует считать базовым URI. Обратите внимание, что если извлечение было результатом перенаправленного запроса, базовым URI является последний использованный URI (то есть URI, в результате которого было выполнено фактическое извлечение представления).
5.1.4. Default Base URI
5.1.4. Базовый URI по умолчанию
If none of the conditions described above apply, then the base URI is defined by the context of the application. As this definition is necessarily application-dependent, failing to define a base URI by using one of the other methods may result in the same content being interpreted differently by different types of applications.
Если ни одно из описанных выше условий не применимо, базовый URI определяется контекстом приложения. Поскольку это определение неизбежно зависит от приложения, неспособность определить базовый URI одним из других методов может привести к тому, что одно и то же содержимое будет по-разному интерпретироваться разными типами приложений.
A sender of a representation containing relative references is responsible for ensuring that a base URI for those references can be established. Aside from fragment-only references, relative references can only be used reliably in situations where the base URI is well defined.
Отправитель представления, содержащего относительные ссылки, несёт ответственность за то, чтобы базовый URI для этих ссылок мог быть установлен. Помимо ссылок, состоящих только из фрагмента, относительные ссылки можно надёжно использовать только в ситуациях, когда базовый URI хорошо определён.
5.2. Relative Resolution
5.2. Относительное разрешение
This section describes an algorithm for converting a URI reference that might be relative to a given base URI into the parsed components of the reference's target. The components can then be recomposed, as described in Section 5.3, to form the target URI. This algorithm provides definitive results that can be used to test the output of other implementations. Applications may implement relative reference resolution by using some other algorithm, provided that the results match what would be given by this one.
В настоящем разделе описывается алгоритм преобразования ссылки URI, которая может быть относительной, в разобранные компоненты цели этой ссылки для заданного базового URI. Затем компоненты можно собрать заново, как описано в разделе 5.3, чтобы образовать целевой URI. Этот алгоритм даёт однозначные результаты, которые можно использовать для проверки вывода других реализаций. Приложения могут реализовывать разрешение относительных ссылок с помощью какого-либо другого алгоритма при условии, что результаты совпадают с тем, что даёт этот.
5.2.1. Pre-parse the Base URI

6. Normalization and Comparison
6. Нормализация и сравнение
One of the most common operations on URIs is simple comparison: determining whether two URIs are equivalent without using the URIs to access their respective resource(s). A comparison is performed every time a response cache is accessed, a browser checks its history to color a link, or an XML parser processes tags within a namespace. Extensive normalization prior to comparison of URIs is often used by spiders and indexing engines to prune a search space or to reduce duplication of request actions and response storage.
Одна из наиболее распространённых операций над URI — простое сравнение: определение того, эквивалентны ли два URI, без использования URI для доступа к их соответствующим ресурсам. Сравнение выполняется каждый раз, когда происходит обращение к кэшу ответов, когда браузер проверяет свою историю, чтобы раскрасить ссылку, или когда анализатор XML обрабатывает теги в пространстве имён. Обширная нормализация перед сравнением URI часто используется поисковыми роботами и индексирующими машинами для сокращения пространства поиска или уменьшения дублирования запросов и хранения ответов.
URI comparison is performed for some particular purpose. Protocols or implementations that compare URIs for different purposes will often be subject to differing design trade-offs in regards to how much effort should be spent in reducing aliased identifiers. This section describes various methods that may be used to compare URIs, the trade-offs between them, and the types of applications that might use them.
Сравнение URI выполняется для какой-то определённой цели. Протоколы или реализации, сравнивающие URI для разных целей, часто будут иметь разные компромиссы в проектировании в отношении того, сколько усилий следует тратить на уменьшение числа псевдонимных идентификаторов. В настоящем разделе описаны различные методы, которые могут использоваться для сравнения URI, компромиссы между ними и типы приложений, которые могут их использовать.
6.1. Equivalence
6.1. Эквивалентность
Because URIs exist to identify resources, presumably they should be considered equivalent when they identify the same resource. However, this definition of equivalence is not of much practical use, as there is no way for an implementation to compare two resources unless it has full knowledge or control of them. For this reason, determination of equivalence or difference of URIs is based on string comparison, perhaps augmented by reference to additional rules provided by URI scheme definitions. We use the terms "different" and "equivalent" to describe the possible outcomes of such comparisons, but there are many application-dependent versions of equivalence.
Поскольку URI существуют для идентификации ресурсов, предположительно их следует считать эквивалентными, когда они идентифицируют один и тот же ресурс. Однако это определение эквивалентности не имеет большого практического применения, поскольку реализация не может сравнить два ресурса, если только она не обладает полным знанием о них или контролем над ними. По этой причине определение эквивалентности или различия URI основано на сравнении строк, возможно, дополненном ссылкой на дополнительные правила, предоставляемые определениями схем URI. Мы используем термины «различные» и «эквивалентные» для описания возможных результатов таких сравнений, но существует множество зависящих от приложения вариантов эквивалентности.
Even though it is possible to determine that two URIs are equivalent, URI comparison is not sufficient to determine whether two URIs identify different resources. For example, an owner of two different domain names could decide to serve the same resource from both, resulting in two different URIs. Therefore, comparison methods are designed to minimize false negatives while strictly avoiding false positives.
Даже если можно определить, что два URI эквивалентны, сравнения URI недостаточно, чтобы определить, идентифицируют ли два URI разные ресурсы. Например, владелец двух разных доменных имён мог бы решить обслуживать один и тот же ресурс по обоим, в результате чего получились бы два разных URI. Поэтому методы сравнения разработаны так, чтобы минимизировать ложноотрицательные результаты, строго избегая при этом ложноположительных.
In testing for equivalence, applications should not directly compare relative references; the references should be converted to their respective target URIs before comparison. When URIs are compared to select (or avoid) a network action, such as retrieval of a representation, fragment components (if any) should be excluded from the comparison.
При проверке эквивалентности приложения не должны напрямую сравнивать относительные ссылки; ссылки должны быть преобразованы в свои соответствующие целевые URI до сравнения. Когда URI сравниваются для выбора (или избежания) сетевого действия, например извлечения представления, компоненты фрагмента (если таковые имеются) следует исключать из сравнения.
6.2. Comparison Ladder
6.2. Лестница сравнений
A variety of methods are used in practice to test URI equivalence. These methods fall into a range, distinguished by the amount of processing required and the degree to which the probability of false negatives is reduced. As noted above, false negatives cannot be eliminated. In practice, their probability can be reduced, but this reduction requires more processing and is not cost-effective for all applications.
На практике для проверки эквивалентности URI используется множество методов. Эти методы образуют диапазон, различающийся объёмом требуемой обработки и степенью, в которой снижается вероятность ложноотрицательных результатов. Как отмечено выше, ложноотрицательные результаты нельзя устранить. На практике их вероятность можно снизить, но такое снижение требует больше обработки и не является экономически эффективным для всех приложений.
If this range of comparison practices is considered as a ladder, the following discussion will climb the ladder, starting with practices that are cheap but have a relatively higher chance of producing false negatives, and proceeding to those that have higher computational cost and lower risk of false negatives.
Если рассматривать этот диапазон практик сравнения как лестницу, то последующее обсуждение будет подниматься по этой лестнице, начиная с практик, которые дешевы, но имеют относительно более высокую вероятность дать ложноотрицательный результат, и переходя к тем, которые имеют более высокую вычислительную стоимость и более низкий риск ложноотрицательных результатов.
6.2.1. Simple String Comparison
6.2.1. Простое сравнение строк
If two URIs, when considered as character strings, are identical, then it is safe to conclude that they are equivalent. This type of equivalence test has very low computational cost and is in wide use in a variety of applications, particularly in the domain of parsing.
Если два URI при рассмотрении их как символьных строк идентичны, то можно безопасно заключить, что они эквивалентны. Этот тип проверки эквивалентности имеет очень низкую вычислительную стоимость и широко используется в различных приложениях, особенно в области разбора.
Testing strings for equivalence requires some basic precautions. This procedure is often referred to as "bit-for-bit" or "byte-for-byte" comparison, which is potentially misleading. Testing strings for equality is normally based on pair comparison of the characters that make up the strings, starting from the first and proceeding until both strings are exhausted and all characters are found to be equal, until a pair of characters compares unequal, or until one of the strings is exhausted before the other.
Проверка строк на эквивалентность требует некоторых элементарных предосторожностей. Эту процедуру часто называют сравнением «побитовым» (bit-for-bit) или «побайтовым» (byte-for-byte), что потенциально вводит в заблуждение. Проверка строк на равенство обычно основана на попарном сравнении символов, составляющих строки, начиная с первого и продолжая, пока обе строки не исчерпаны и все символы не признаны равными, либо пока какая-то пара символов не окажется неравной, либо пока одна из строк не исчерпается раньше другой.
This character comparison requires that each pair of characters be put in comparable form. For example, should one URI be stored in a byte array in EBCDIC encoding and the second in a Java String object (UTF-16), bit-for-bit comparisons applied naively will produce errors. It is better to speak of equality on a character-for- character basis rather than on a byte-for-byte or bit-for-bit basis. In practical terms, character-by-character comparisons should be done codepoint-by-codepoint after conversion to a common character encoding.
Такое сравнение символов требует, чтобы каждая пара символов была приведена к сравнимой форме. Например, если один URI хранится в байтовом массиве в кодировке EBCDIC, а второй — в объекте Java String (UTF-16), то побитовые сравнения, применённые наивно, дадут ошибки. Лучше говорить о равенстве на уровне символ за символом, а не на уровне байт за байтом или бит за битом. На практике сравнение символ за символом следует выполнять кодовая точка за кодовой точкой после преобразования к общей кодировке символов.
False negatives are caused by the production and use of URI aliases. Unnecessary aliases can be reduced, regardless of the comparison method, by consistently providing URI references in an already- normalized form (i.e., a form identical to what would be produced after normalization is applied, as described below). Protocols and data formats often limit some URI comparisons to simple string comparison, based on the theory that people and implementations will, in their own best interest, be consistent in providing URI references, or at least consistent enough to negate any efficiency that might be obtained from further normalization.
Ложноотрицательные результаты вызываются созданием и использованием псевдонимов URI. Ненужные псевдонимы можно уменьшить, независимо от метода сравнения, за счёт последовательного предоставления ссылок URI в уже нормализованной форме (то есть в форме, идентичной той, которая была бы получена после применения нормализации, как описано ниже). Протоколы и форматы данных часто ограничивают некоторые сравнения URI простым сравнением строк, исходя из теории, что люди и реализации в своих собственных интересах будут последовательны в предоставлении ссылок URI или, по крайней мере, достаточно последовательны, чтобы свести на нет любую эффективность, которую можно было бы получить от дальнейшей нормализации.
6.2.2. Syntax-Based Normalization
6.2.2. Нормализация на основе синтаксиса

6.2.2.1. Case Normalization
6.2.2.1. Нормализация регистра
For all URIs, the hexadecimal digits within a percent-encoding triplet (e.g., "%3a" versus "%3A") are case-insensitive and therefore should be normalized to use uppercase letters for the digits A-F.
Для всех URI шестнадцатеричные цифры в триплете процентного экранирования (например, «%3a» против «%3A») нечувствительны к регистру и поэтому должны нормализоваться с использованием букв верхнего регистра для цифр A–F.
When a URI uses components of the generic syntax, the component syntax equivalence rules always apply; namely, that the scheme and host are case-insensitive and therefore should be normalized to lowercase. For example, the URI <HTTP://www.EXAMPLE.com/> is equivalent to <http://www.example.com/>. The other generic syntax components are assumed to be case-sensitive unless specifically defined otherwise by the scheme (see Section 6.2.3).
Когда URI использует компоненты общего синтаксиса, всегда применяются правила эквивалентности синтаксиса компонентов; а именно, схема и host нечувствительны к регистру и поэтому должны нормализоваться к нижнему регистру. Например, URI <HTTP://www.EXAMPLE.com/> эквивалентен <http://www.example.com/>. Остальные компоненты общего синтаксиса считаются чувствительными к регистру, если только схема не определяет иное (см. раздел 6.2.3).
6.2.2.2. Percent-Encoding Normalization
6.2.2.2. Нормализация процентного экранирования
The percent-encoding mechanism (Section 2.1) is a frequent source of variance among otherwise identical URIs. In addition to the case normalization issue noted above, some URI producers percent-encode octets that do not require percent-encoding, resulting in URIs that are equivalent to their non-encoded counterparts. These URIs should be normalized by decoding any percent-encoded octet that corresponds to an unreserved character, as described in Section 2.3.
Механизм процентного экранирования (раздел 2.1) является частым источником расхождений между в остальном идентичными URI. Помимо отмеченной выше проблемы регистра, некоторые производители URI процентно экранируют октеты, которые не требуют процентного экранирования, в результате чего получаются URI, эквивалентные своим неэкранированным аналогам. Такие URI следует нормализовать, декодируя любой процентно-экранированный октет, соответствующий незарезервированному символу, как описано в разделе 2.3.
6.2.2.3. Path Segment Normalization
6.2.2.3. Нормализация сегментов пути
The complete path segments "." and ".." are intended only for use within relative references (Section 4.1) and are removed as part of the reference resolution process (Section 5.2). However, some deployed implementations incorrectly assume that reference resolution is not necessary when the reference is already a URI and thus fail to remove dot-segments when they occur in non-relative paths. URI normalizers should remove dot-segments by applying the remove_dot_segments algorithm to the path, as described in Section 5.2.4.
Полные сегменты пути «.» и «..» предназначены только для использования в относительных ссылках (раздел 4.1) и удаляются как часть процесса разрешения ссылок (раздел 5.2). Однако некоторые развёрнутые реализации ошибочно полагают, что разрешение ссылок не требуется, когда ссылка уже является URI, и потому не удаляют точечные сегменты, когда они встречаются в неотносительных путях. Нормализаторы URI должны удалять точечные сегменты, применяя алгоритм remove_dot_segments к пути, как описано в разделе 5.2.4.

Реализации могут использовать правила, специфичные для схемы, с дополнительными затратами на обработку, чтобы уменьшить вероятность ложноотрицательных результатов. Another case where normalization varies by scheme is in the handling of an empty authority component or empty host subcomponent. For many scheme specifications, an empty authority or host is considered an error; for others, it is considered equivalent to "localhost" or the end-user's host. When a scheme defines a default for authority and a URI reference to that default is desired, the reference should be normalized to an empty authority for the sake of uniformity, brevity, and internationalization. If, however, either the userinfo or port subcomponents are non-empty, then the host should be given explicitly even if it matches the default.
Ещё один случай, когда нормализация зависит от схемы, — обработка пустого компонента authority или пустого подкомпонента host. Для многих спецификаций схем пустой authority или host считается ошибкой; для других он считается эквивалентным «localhost» или host конечного пользователя. Когда схема определяет значение по умолчанию для authority и желательна ссылка URI на это значение по умолчанию, ссылку следует нормализовать к пустому authority ради единообразия, краткости и интернационализации. Если же подкомпоненты userinfo или port непусты, то host должен быть указан явно, даже если он совпадает со значением по умолчанию.

Нормализация не должна удалять разделители, когда связанный с ними компонент пуст, если только спецификация схемы не даёт на это права. Например, URI «http://example.com/?» нельзя считать эквивалентным ни одному из примеров выше. Равным образом наличие или отсутствие разделителей внутри подкомпонента userinfo обычно значимо для его интерпретации. Компонент фрагмента не подвержен никакой нормализации на основе схемы; таким образом, два URI, различающиеся только суффиксом «#», считаются разными независимо от схемы.
Some schemes define additional subcomponents that consist of case- insensitive data, giving an implicit license to normalizers to convert this data to a common case (e.g., all lowercase). For example, URI schemes that define a subcomponent of path to contain an Internet hostname, such as the "mailto" URI scheme, cause that subcomponent to be case-insensitive and thus subject to case normalization (e.g., "mailto:Joe@Example.COM" is equivalent to "mailto:Joe@example.com", even though the generic syntax considers the path component to be case-sensitive).
Некоторые схемы определяют дополнительные подкомпоненты, состоящие из данных, нечувствительных к регистру, что даёт нормализаторам неявное право преобразовывать эти данные к общему регистру (например, к нижнему). Например, схемы URI, определяющие подкомпонент пути для хранения имени интернет-хоста, такие как схема URI «mailto», делают этот подкомпонент нечувствительным к регистру и, следовательно, подлежащим нормализации регистра (например, «mailto:Joe@Example.COM» эквивалентен «mailto:Joe@example.com», даже хотя общий синтаксис считает компонент пути чувствительным к регистру).
Other scheme-specific normalizations are possible.

7. Security Considerations
7. Соображения безопасности
A URI does not in itself pose a security threat. However, as URIs are often used to provide a compact set of instructions for access to network resources, care must be taken to properly interpret the data within a URI, to prevent that data from causing unintended access, and to avoid including data that should not be revealed in plain text.
URI сам по себе не представляет угрозы безопасности. Однако, поскольку URI часто используются для предоставления компактного набора инструкций для доступа к сетевым ресурсам, необходимо проявлять осторожность, чтобы правильно интерпретировать данные внутри URI, не допускать, чтобы эти данные вызывали непреднамеренный доступ, и избегать включения данных, которые не следует раскрывать открытым текстом.
7.1. Reliability and Consistency
7.1. Надёжность и согласованность
There is no guarantee that once a URI has been used to retrieve information, the same information will be retrievable by that URI in the future. Nor is there any guarantee that the information retrievable via that URI in the future will be observably similar to that retrieved in the past. The URI syntax does not constrain how a given scheme or authority apportions its namespace or maintains it over time. Such guarantees can only be obtained from the person(s) controlling that namespace and the resource in question. A specific URI scheme may define additional semantics, such as name persistence, if those semantics are required of all naming authorities for that scheme.
Нет гарантии, что после того, как URI был использован для извлечения информации, та же информация будет доступна по этому URI в будущем. Нет также гарантии, что информация, доступная через этот URI в будущем, будет наблюдаемо похожа на ту, что была извлечена в прошлом. Синтаксис URI не ограничивает, как данная схема или authority распределяет своё пространство имён или поддерживает его с течением времени. Такие гарантии могут быть получены только от лиц, контролирующих это пространство имён и рассматриваемый ресурс. Конкретная схема URI может определять дополнительную семантику, например постоянство имён, если эта семантика требуется от всех органов именования для этой схемы.
7.2. Malicious Construction
7.2. Злонамеренное конструирование
It is sometimes possible to construct a URI so that an attempt to perform a seemingly harmless, idempotent operation, such as the retrieval of a representation, will in fact cause a possibly damaging remote operation. The unsafe URI is typically constructed by specifying a port number other than that reserved for the network protocol in question. The client unwittingly contacts a site running a different protocol service, and data within the URI contains instructions that, when interpreted according to this other protocol, cause an unexpected operation. A frequent example of such abuse has been the use of a protocol-based scheme with a port component of "25", thereby fooling user agent software into sending an unintended or impersonating message via an SMTP server.
Иногда можно сконструировать URI так, что попытка выполнить кажущуюся безобидной идемпотентную операцию, например извлечение представления, фактически вызовет потенциально опасную удалённую операцию. Небезопасный URI обычно конструируется путём указания номера порта, отличного от зарезервированного для соответствующего сетевого протокола. Клиент непреднамеренно связывается с сайтом, на котором работает служба другого протокола, а данные внутри URI содержат инструкции, которые при интерпретации в соответствии с этим другим протоколом вызывают неожиданную операцию. Частым примером такого злоупотребления было использование схемы на основе протокола с компонентом port «25», что вводило программное обеспечение пользовательского агента в заблуждение, заставляя его отправить непреднамеренное сообщение или сообщение с подделкой личности через SMTP-сервер.
Applications should prevent dereference of a URI that specifies a TCP port number within the "well-known port" range (0 - 1023) unless the protocol being used to dereference that URI is compatible with the protocol expected on that well-known port. Although IANA maintains a registry of well-known ports, applications should make such restrictions user-configurable to avoid preventing the deployment of new services. When a URI contains percent-encoded octets that match the delimiters for a given resolution or dereference protocol (for example, CR and LF characters for the TELNET protocol), these percent-encodings must not be decoded before transmission across that protocol. Transfer of the percent-encoding, which might violate the protocol, is less harmful than allowing decoded octets to be interpreted as additional operations or parameters, perhaps triggering an unexpected and possibly harmful remote operation.
Приложения должны предотвращать разыменование URI, указывающего номер TCP-порта в диапазоне «хорошо известных портов» (0–1023), если только протокол, используемый для разыменования этого URI, не совместим с протоколом, ожидаемым на этом хорошо известном порту. Хотя IANA поддерживает реестр хорошо известных портов, приложениям следует делать такие ограничения настраиваемыми пользователем, чтобы не препятствовать развёртыванию новых служб. Когда URI содержит процентно-экранированные октеты, совпадающие с разделителями для данного протокола разрешения или разыменования (например, символы CR и LF для протокола TELNET), эти процентные экранирования не должны декодироваться до передачи по этому протоколу. Передача процентного экранирования, которая может нарушить протокол, менее вредна, чем допущение, что декодированные октеты будут интерпретированы как дополнительные операции или параметры, возможно, вызывая неожиданную и потенциально вредную удалённую операцию.
7.3. Back-End Transcoding
7.3. Внутреннее перекодирование
When a URI is dereferenced, the data within it is often parsed by both the user agent and one or more servers. In HTTP, for example, a typical user agent will parse a URI into its five major components, access the authority's server, and send it the data within the authority, path, and query components. A typical server will take that information, parse the path into segments and the query into key/value pairs, and then invoke implementation-specific handlers to respond to the request. As a result, a common security concern for server implementations that handle a URI, either as a whole or split into separate components, is proper interpretation of the octet data represented by the characters and percent-encodings within that URI.
Когда URI разыменовывается, данные внутри него часто разбираются как пользовательским агентом, так и одним или несколькими серверами. В HTTP, например, типичный пользовательский агент разберёт URI на пять основных компонентов, обратится к серверу authority и отправит ему данные из компонентов authority, path и query. Типичный сервер возьмёт эту информацию, разберёт путь на сегменты, а query — на пары ключ/значение, а затем вызовет обработчики, специфичные для реализации, чтобы ответить на запрос. В результате общей проблемой безопасности для серверных реализаций, обрабатывающих URI целиком или разделённым на отдельные компоненты, является правильная интерпретация октетных данных, представляемых символами и процентными экранированиями внутри этого URI.
Percent-encoded octets must be decoded at some point during the dereference process. Applications must split the URI into its components and subcomponents prior to decoding the octets, as otherwise the decoded octets might be mistaken for delimiters. Security checks of the data within a URI should be applied after decoding the octets. Note, however, that the "%00" percent-encoding (NUL) may require special handling and should be rejected if the application is not expecting to receive raw data within a component.
Процентно-экранированные октеты должны быть декодированы на некотором этапе процесса разыменования. Приложения должны разделить URI на компоненты и подкомпоненты до декодирования октетов, иначе декодированные октеты могут быть приняты за разделители. Проверки безопасности данных внутри URI следует применять после декодирования октетов. Однако обратите внимание, что процентное экранирование «%00» (NUL) может требовать особой обработки и должно отклоняться, если приложение не ожидает получить необработанные данные внутри компонента.
Special care should be taken when the URI path interpretation process involves the use of a back-end file system or related system functions. File systems typically assign an operational meaning to special characters, such as the "/", "\", ":", "[", and "]" characters, and to special device names like ".", "..", "...", "aux", "lpt", etc. In some cases, merely testing for the existence of such a name will cause the operating system to pause or invoke unrelated system calls, leading to significant security concerns regarding denial of service and unintended data transfer. It would be impossible for this specification to list all such significant characters and device names. Implementers should research the reserved names and characters for the types of storage device that may be attached to their applications and restrict the use of data obtained from URI components accordingly.
Особая осторожность требуется, когда процесс интерпретации пути URI включает использование внутренней файловой системы или связанных системных функций. Файловые системы обычно придают эксплуатационное значение специальным символам, таким как «/», «\», «:», «[» и «]», а также специальным именам устройств, таким как «.», «..», «...», «aux», «lpt» и т. п. В некоторых случаях простой проверки существования такого имени достаточно, чтобы операционная система приостановилась или вызвала посторонние системные вызовы, что приводит к серьёзным проблемам безопасности, связанным с отказом в обслуживании и непреднамеренной передачей данных. Было бы невозможно перечислить в настоящей спецификации все такие значимые символы и имена устройств. Реализаторы должны изучить зарезервированные имена и символы для типов устройств хранения, которые могут быть подключены к их приложениям, и соответствующим образом ограничить использование данных, полученных из компонентов URI.
7.4. Rare IP Address Formats
7.4. Редкие форматы IP-адресов
Although the URI syntax for IPv4address only allows the common dotted-decimal form of IPv4 address literal, many implementations that process URIs make use of platform-dependent system routines, such as gethostbyname() and inet_aton(), to translate the string literal to an actual IP address. Unfortunately, such system routines often allow and process a much larger set of formats than those described in Section 3.2.2.
Хотя синтаксис URI для IPv4address допускает только обычную точечно-десятичную форму литерала IPv4-адреса, многие реализации, обрабатывающие URI, используют зависящие от платформы системные процедуры, такие как gethostbyname() и inet_aton(), для преобразования строкового литерала в фактический IP-адрес. К сожалению, такие системные процедуры часто допускают и обрабатывают гораздо больший набор форматов, чем описанные в разделе 3.2.2.
For example, many implementations allow dotted forms of three numbers, wherein the last part is interpreted as a 16-bit quantity and placed in the right-most two bytes of the network address (e.g., a Class B network). Likewise, a dotted form of two numbers means that the last part is interpreted as a 24-bit quantity and placed in the right-most three bytes of the network address (Class A), and a single number (without dots) is interpreted as a 32-bit quantity and stored directly in the network address. Adding further to the confusion, some implementations allow each dotted part to be interpreted as decimal, octal, or hexadecimal, as specified in the C language (i.e., a leading 0x or 0X implies hexadecimal; a leading 0 implies octal; otherwise, the number is interpreted as decimal).
Например, многие реализации допускают точечные формы из трёх чисел, где последняя часть интерпретируется как 16-битная величина и помещается в два крайних правых байта сетевого адреса (например, сеть класса B). Аналогично точечная форма из двух чисел означает, что последняя часть интерпретируется как 24-битная величина и помещается в три крайних правых байта сетевого адреса (класс A), а одно число (без точек) интерпретируется как 32-битная величина и сохраняется непосредственно в сетевом адресе. Дополнительно усугубляя путаницу, некоторые реализации позволяют интерпретировать каждую точечную часть как десятичную, восьмеричную или шестнадцатеричную, как определено в языке C (то есть ведущие 0x или 0X означают шестнадцатеричное число; ведущий 0 означает восьмеричное; в противном случае число интерпретируется как десятичное).
These additional IP address formats are not allowed in the URI syntax due to differences between platform implementations. However, they can become a security concern if an application attempts to filter access to resources based on the IP address in string literal format. If this filtering is performed, literals should be converted to numeric form and filtered based on the numeric value, and not on a prefix or suffix of the string form.
Эти дополнительные форматы IP-адресов не допускаются синтаксисом URI из-за различий между реализациями платформ. Однако они могут стать проблемой безопасности, если приложение пытается фильтровать доступ к ресурсам на основе IP-адреса в формате строкового литерала. Если такая фильтрация выполняется, литералы следует преобразовывать в числовую форму и фильтровать по числовому значению, а не по префиксу или суффиксу строковой формы.
7.5. Sensitive Information
7.5. Конфиденциальная информация
URI producers should not provide a URI that contains a username or password that is intended to be secret. URIs are frequently displayed by browsers, stored in clear text bookmarks, and logged by user agent history and intermediary applications (proxies). A password appearing within the userinfo component is deprecated and should be considered an error (or simply ignored) except in those rare cases where the 'password' parameter is intended to be public.
Производители URI не должны предоставлять URI, содержащий имя пользователя или пароль, которые предполагается держать в секрете. URI часто отображаются браузерами, сохраняются в закладках открытым текстом и регистрируются в журналах истории пользовательского агента и промежуточных приложений (прокси). Пароль, присутствующий в компоненте userinfo, не рекомендуется использовать и должен считаться ошибкой (или просто игнорироваться), за исключением тех редких случаев, когда параметр «password» предполагается общедоступным.
7.6. Semantic Attacks
7.6. Семантические атаки
Because the userinfo subcomponent is rarely used and appears before the host in the authority component, it can be used to construct a URI intended to mislead a human user by appearing to identify one (trusted) naming authority while actually identifying a different authority hidden behind the noise. For example ftp://cnn.example.com&story=breaking_news@10.0.0.1/top_story.htm
Поскольку подкомпонент userinfo используется редко и появляется перед host в компоненте authority, его можно использовать для построения URI, предназначенного ввести человека в заблуждение, создавая видимость идентификации одного (доверенного) органа именования, тогда как в действительности идентифицируется другой authority, скрытый за шумом. Например, ftp://cnn.example.com&story=breaking_news@10.0.0.1/top_story.htm может
might lead a human user to assume that the host is 'cnn.example.com', whereas it is actually '10.0.0.1'. Note that a misleading userinfo subcomponent could be much longer than the example above.
заставить человека предположить, что host — «cnn.example.com», тогда как на самом деле это «10.0.0.1». Обратите внимание, что вводящий в заблуждение подкомпонент userinfo может быть намного длиннее, чем в примере выше.

User agents may be able to reduce the impact of such attacks by distinguishing the various components of the URI when they are rendered, such as by using a different color or tone to render userinfo if any is present, though there is no panacea. More information on URI-based semantic attacks can be found in [Siedzik].
Вводящий в заблуждение URI, подобный приведённому выше, является атакой на предвзятые представления пользователя о значении URI, а не атакой на само программное обеспечение. Пользовательские агенты могут уменьшить воздействие таких атак, различая различные компоненты URI при их отображении, например используя другой цвет или тон для отображения userinfo, если он присутствует, хотя панацеи не существует. Appendix C. Delimiting a URI in Context
Приложение C. Ограничение URI в контексте
URIs are often transmitted through formats that do not provide a clear context for their interpretation. For example, there are many occasions when a URI is included in plain text; examples include text sent in email, USENET news, and on printed paper. In such cases, it is important to be able to delimit the URI from the rest of the text, and in particular from punctuation marks that might be mistaken for part of the URI.
URI часто передаются через форматы, не обеспечивающие ясного контекста для их интерпретации. Например, есть много случаев, когда URI включается в обычный текст; примеры включают текст, отправляемый по электронной почте, в новостях USENET и на печатной бумаге. В таких случаях важно уметь отделить URI от остального текста и, в частности, от знаков препинания, которые могут быть ошибочно приняты за часть URI.
In practice, URIs are delimited in a variety of ways, but usually within double-quotes "http://example.com/", angle brackets <http://example.com/>, or just by using whitespace: http://example.com/
На практике URI ограничивают разными способами, но обычно в двойных кавычках "http://example.com/", в угловых скобках <http://example.com/> или просто используя пробельные символы: http://example.com/
These wrappers do not form part of the URI.
Эти обрамляющие элементы не являются частью URI.
In some cases, extra whitespace (spaces, line-breaks, tabs, etc.) may have to be added to break a long URI across lines. The whitespace should be ignored when the URI is extracted.
В некоторых случаях может потребоваться добавить лишние пробельные символы (пробелы, разрывы строк, табуляции и т. п.), чтобы разбить длинный URI на несколько строк. При извлечении URI эти пробельные символы следует игнорировать.
No whitespace should be introduced after a hyphen ("-") character. Because some typesetters and printers may (erroneously) introduce a hyphen at the end of line when breaking it, the interpreter of a URI containing a line break immediately after a hyphen should ignore all whitespace around the line break and should be aware that the hyphen may or may not actually be part of the URI.
После символа дефиса («-») не следует вводить пробельные символы. Поскольку некоторые наборщики и печатные устройства могут (ошибочно) вставлять дефис в конце строки при её разрыве, интерпретатор URI, содержащего разрыв строки сразу после дефиса, должен игнорировать все пробельные символы вокруг разрыва строки и учитывать, что дефис может как входить, так и не входить в URI.
Using <> angle brackets around each URI is especially recommended as a delimiting style for a reference that contains embedded whitespace.

Appendix D. Changes from RFC 2396
Приложение D. Изменения по сравнению с RFC 2396
D.1. Additions
D.1. Дополнения
An ABNF rule for URI has been introduced to correspond to one common usage of the term: an absolute URI with optional fragment.
Введено правило ABNF для URI, соответствующее одному распространённому употреблению этого термина: абсолютный URI с необязательным фрагментом.
IPv6 (and later) literals have been added to the list of possible identifiers for the host portion of an authority component, as described by [RFC2732], with the addition of "[" and "]" to the reserved set and a version flag to anticipate future versions of IP literals. Square brackets are now specified as reserved within the authority component and are not allowed outside their use as delimiters for an IP literal within host. In order to make this change without changing the technical definition of the path, query, and fragment components, those rules were redefined to directly specify the characters allowed.
Литералы IPv6 (и более поздних версий) добавлены в список возможных идентификаторов для части host компонента authority, как описано в [RFC2732], с добавлением «[» и «]» в зарезервированный набор и флага версии для предвосхищения будущих версий литералов IP. Квадратные скобки теперь определены как зарезервированные внутри компонента authority и не допускаются вне их использования в качестве разделителей IP-литерала внутри host. Чтобы внести это изменение, не меняя технического определения компонентов path, query и fragment, эти правила были переопределены так, чтобы напрямую задавать допустимые символы.
As [RFC2732] defers to [RFC3513] for definition of an IPv6 literal address, which, unfortunately, lacks an ABNF description of IPv6address, we created a new ABNF rule for IPv6address that matches the text representations defined by Section 2.2 of [RFC3513]. Likewise, the definition of IPv4address has been improved in order to limit each decimal octet to the range 0-255.
Поскольку [RFC2732] передаёт [RFC3513] определение литерала IPv6-адреса, в котором, к сожалению, отсутствует ABNF-описание IPv6address, мы создали новое правило ABNF для IPv6address, соответствующее текстовым представлениям, определённым в разделе 2.2 [RFC3513]. Аналогично было улучшено определение IPv4address, чтобы ограничить каждый десятичный октет диапазоном 0–255.
Section 6, on URI normalization and comparison, has been completely rewritten and extended by using input from Tim Bray and discussion within the W3C Technical Architecture Group.
Раздел 6, посвящённый нормализации и сравнению URI, был полностью переписан и расширен с использованием материалов Tim Bray и обсуждения в Technical Architecture Group консорциума W3C.

Section 2, on characters, has been rewritten to explain what characters are reserved, when they are reserved, and why they are reserved, even when they are not used as delimiters by the generic syntax. The mark characters that are typically unsafe to decode, including the exclamation mark ("!"), asterisk ("*"), single-quote ("'"), and open and close parentheses ("(" and ")"), have been moved to the reserved set in order to clarify the distinction between reserved and unreserved and, hopefully, to answer the most common question of scheme designers. Likewise, the section on percent-encoded characters has been rewritten, and URI normalizers are now given license to decode any percent-encoded octets corresponding to unreserved characters. In general, the terms "escaped" and "unescaped" have been replaced with "percent-encoded" and "decoded", respectively, to reduce confusion with other forms of escape mechanisms.
Раздел 2, посвящённый символам, был переписан, чтобы объяснить, какие символы зарезервированы, когда они зарезервированы и почему они зарезервированы, даже когда они не используются общим синтаксисом в качестве разделителей. Символы mark, которые обычно небезопасно декодировать, включая восклицательный знак («!»), звёздочку («*»), одинарную кавычку («'»), а также открывающую и закрывающую круглые скобки («(» и «)»), были перемещены в зарезервированный набор, чтобы уточнить различие между зарезервированными и незарезервированными символами и, будем надеяться, ответить на самый частый вопрос разработчиков схем. Равным образом был переписан раздел о процентно-экранированных символах, и нормализаторам URI теперь дано право декодировать любые процентно-экранированные октеты, соответствующие незарезервированным символам. В целом термины «экранированный» (escaped) и «неэкранированный» (unescaped) заменены соответственно на «процентно-экранированный» и «декодированный», чтобы уменьшить путаницу с другими формами механизмов экранирования.
The ABNF for URI and URI-reference has been redesigned to make them more friendly to LALR parsers and to reduce complexity. As a result, the layout form of syntax description has been removed, along with the uric, uric_no_slash, opaque_part, net_path, abs_path, rel_path, path_segments, rel_segment, and mark rules. All references to "opaque" URIs have been replaced with a better description of how the path component may be opaque to hierarchy. The relativeURI rule has been replaced with relative-ref to avoid unnecessary confusion over whether they are a subset of URI. The ambiguity regarding the parsing of URI-reference as a URI or a relative-ref with a colon in the first segment has been eliminated through the use of five separate path matching rules.
ABNF для URI и URI-reference была переработана, чтобы сделать их более удобными для LALR-анализаторов и уменьшить сложность. В результате была удалена «layout»-форма описания синтаксиса вместе с правилами uric, uric_no_slash, opaque_part, net_path, abs_path, rel_path, path_segments, rel_segment и mark. Все упоминания «непрозрачных» (opaque) URI заменены более точным описанием того, как компонент пути может быть непрозрачным для иерархии. Правило relativeURI заменено на relative-ref, чтобы избежать ненужной путаницы по поводу того, являются ли они подмножеством URI. Неоднозначность разбора URI-reference как URI или как relative-ref с двоеточием в первом сегменте устранена за счёт использования пяти отдельных правил сопоставления пути.
The fragment identifier has been moved back into the section on generic syntax components and within the URI and relative-ref rules, though it remains excluded from absolute-URI. The number sign ("#") character has been moved back to the reserved set as a result of reintegrating the fragment syntax.
Идентификатор фрагмента возвращён в раздел об общих компонентах синтаксиса и в правила URI и relative-ref, хотя он по-прежнему исключён из absolute-URI. Символ знака решётки («#») возвращён в зарезервированный набор в результате повторного включения синтаксиса фрагмента.
The ABNF has been corrected to allow the path component to be empty. This also allows an absolute-URI to consist of nothing after the "scheme:", as is present in practice with the "dav:" namespace [RFC2518] and with the "about:" scheme used internally by many WWW browser implementations. The ambiguity regarding the boundary between authority and path has been eliminated through the use of five separate path matching rules.
ABNF исправлена так, чтобы компонент пути мог быть пустым. Это также позволяет absolute-URI состоять из ничего после «scheme:», как на практике бывает с пространством имён «dav:» [RFC2518] и со схемой «about:», используемой внутри многих реализаций браузеров WWW. Неоднозначность границы между authority и path устранена за счёт использования пяти отдельных правил сопоставления пути.
Registry-based naming authorities that use the generic syntax are now defined within the host rule. The server, hostport, hostname, domainlabel, toplabel, and alphanum rules have been removed.
Органы именования на основе реестра, использующие общий синтаксис, теперь определяются в правиле host. Правила server, hostport, hostname, domainlabel, toplabel и alphanum удалены.
