Abstract
Аннотация
This document presents an extension to the Session Initiation Protocol (SIP)-Specific Event Notification mechanism for subscribing to a homogeneous list of resources. Instead of sending a SUBSCRIBE for each resource individually, the subscriber can subscribe to an entire list and then receive notifications when the state of any of the resources in the list changes.
В настоящем документе представлено расширение механизма уведомления о событиях, специфичного для протокола инициирования сессий (SIP), для подписки на однородный список ресурсов. Вместо отправки SUBSCRIBE для каждого ресурса по отдельности подписчик может подписаться на весь список и затем получать уведомления при изменении состояния любого из ресурсов в списке.
1. Introduction
1. Введение
The SIP-specific event notification mechanism [2] allows a user (the subscriber) to request to be notified of changes in the state of a particular resource. This is accomplished by the subscriber generating a SUBSCRIBE request for the resource, which is processed by a notifier that represents the resource.
Механизм уведомления о событиях, специфичный для SIP [2], позволяет пользователю (подписчику) запросить уведомления об изменениях состояния конкретного ресурса. Для этого подписчик формирует запрос SUBSCRIBE для ресурса, который обрабатывается уведомителем, представляющим этот ресурс.
In many cases, a subscriber has a list of resources they are interested in. Without some aggregating mechanism, this will require the subscriber to generate a SUBSCRIBE request for each resource about which they want information. For environments in which bandwidth is limited, such as wireless networks, subscribing to each resource individually is problematic. Some specific problems are:
Во многих случаях у подписчика есть список интересующих его ресурсов. Без некоторого механизма агрегирования это потребует от подписчика формирования запроса SUBSCRIBE для каждого ресурса, о котором он хочет получать информацию. В средах с ограниченной пропускной способностью, таких как беспроводные сети, подписка на каждый ресурс по отдельности проблематична. Некоторые конкретные проблемы таковы:
o Doing so generates substantial message traffic, in the form of the initial SUBSCRIBE requests for each resource and the refreshes of each individual subscription.
o Это порождает значительный объём трафика сообщений в виде первоначальных запросов SUBSCRIBE для каждого ресурса и обновлений каждой отдельной подписки.
o The notifier may insist on low refresh intervals, in order to avoid a long-lived subscription state. This means that the subscriber may need to generate SUBSCRIBE refreshes faster than it would like to or has the capacity to.
o Уведомитель может настаивать на коротких интервалах обновления, чтобы избежать долговременного состояния подписки. Это означает, что подписчику, возможно, придётся формировать обновления SUBSCRIBE быстрее, чем он хотел бы или способен.
o The notifier may generate NOTIFY requests more rapidly than the subscriber desires, causing NOTIFY traffic at a greater volume than is desired by the subscriber.
o Уведомитель может формировать запросы NOTIFY быстрее, чем желает подписчик, вызывая трафик NOTIFY в объёме большем, чем нужно подписчику.
To solve these problems, this specification defines an extension to RFC 3265 [2] that allows for requesting and conveying notifications for lists of resources. A resource list is identified by a URI, and it represents a list of zero or more URIs. Each of these URIs is an identifier for an individual resource for which the subscriber wants to receive information. In many cases, the URI used to identify the resource list will be a SIP URI [1]; however, the use of other schemes (such as pres: [10]) is also foreseen.
Для решения этих проблем в настоящей спецификации определяется расширение RFC 3265 [2], позволяющее запрашивать и передавать уведомления для списков ресурсов. Список ресурсов идентифицируется URI и представляет собой список из нуля или более URI. Каждый из этих URI является идентификатором отдельного ресурса, по которому подписчик хочет получать информацию. Во многих случаях URI, используемый для идентификации списка ресурсов, будет SIP URI [1]; однако предусматривается также использование других схем (например, pres: [10]).
The notifier for the list is called a "resource list server", or RLS. In order to determine the state of the entire list, the RLS will act as if it has generated a subscription to each resource in the list.
Уведомитель для списка называется «сервером списков ресурсов» (resource list server, RLS). Чтобы определить состояние всего списка, RLS действует так, как если бы он сформировал подписку на каждый ресурс в списке.
The resource list is not restricted to be inside the domain of the subscriber. Similarly, the resources in the list are not constrained to be in the domain of the resource list server.
Список ресурсов не ограничен требованием находиться внутри домена подписчика. Аналогичным образом ресурсы в списке не ограничены требованием находиться в домене сервера списков ресурсов.
2. Terminology
2. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [5].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны толковаться так, как описано в RFC 2119 [5].
The following terms are used throughout the remainder of this document.
Следующие термины используются в остальной части настоящего документа.
Back-End Subscription: Any subscription (SIP or otherwise) that an RLS creates to learn of the state of a resource. An RLS will create back-end subscriptions to learn of the state of a resource about which the RLS is not an authority. For back-end subscriptions, RLSes act as a subscriber.
Внутренняя подписка (back-end subscription): любая подписка (SIP или иная), которую RLS создаёт для получения сведений о состоянии ресурса. RLS создаёт внутренние подписки, чтобы узнать состояние ресурса, в отношении которого RLS не является источником полномочий. При внутренних подписках RLS действует как подписчик.
List Subscription: A subscription to a resource list. In list subscriptions, RLSes act as the notifier.
Подписка на список (list subscription): подписка на список ресурсов. В подписках на список RLS действует в роли уведомителя.
Resource: A resource is any logical entity that has a state or states that can be subscribed to. Resources are identified by URIs.
Ресурс (resource): ресурс — это любая логическая сущность, имеющая одно или несколько состояний, на которые можно подписаться. Ресурсы идентифицируются с помощью URI.
Resource List: A list of zero or more resources that can have their individual states subscribed to with a single subscription.
Список ресурсов (resource list): список из нуля или более ресурсов, на индивидуальные состояния которых можно подписаться одной подпиской.
RLMI: Resource List Meta-Information. RLMI is a document that describes the state of the virtual subscriptions associated with a list subscription.
RLMI: метаинформация списка ресурсов (RLMI) — это документ, который описывает состояние виртуальных подписок, связанных с подпиской на список.
RLS: Resource List Server. RLSes accept subscriptions to resource lists and send notifications to update subscribers of the state of the resources in a resource list.
RLS: сервер списков ресурсов. RLS принимает подписки на списки ресурсов и отправляет уведомления, чтобы сообщать подписчикам о состоянии ресурсов в списке ресурсов.
Virtual Subscription: A Virtual Subscription is a logical construct within an RLS that represents subscriptions to the resources in a resource list. For each list subscription it services, an RLS creates at least one virtual subscription for every resource in the resource list being subscribed to. In some cases, such as when the RLS is not the authority for the state of the resource, this virtual subscription will be associated with a back-end subscription. In other cases, such as when the RLS is the authority for the state of the resource, the virtual subscription will not have a corresponding back-end subscription.
Виртуальная подписка (virtual subscription): виртуальная подписка — это логическая конструкция внутри RLS, представляющая подписки на ресурсы в списке ресурсов. Для каждой обслуживаемой подписки на список RLS создаёт как минимум одну виртуальную подписку для каждого ресурса в списке ресурсов, на который оформлена подписка. В некоторых случаях, например когда RLS не является источником полномочий для состояния ресурса, эта виртуальная подписка будет связана с внутренней подпиской. В других случаях, например когда RLS является источником полномочий для состояния ресурса, виртуальная подписка не будет иметь соответствующей внутренней подписки.
3. Overview of Operation
3. Обзор принципов работы
This section provides an overview of the typical mode of operation of this extension. It is not normative. When users wish to subscribe to the resource of a list of resources, they can use the mechanisms described in this specification. The first step is the creation of a resource list. This resource list is represented by a SIP URI. The list contains a set of URIs, each of which represents a resource for which the subscriber wants to receive information. The resource list can exist in any domain. The list could be manipulated through a web page, through a voice response system, or through some other protocol. The specific means by which the list is created and maintained is outside the scope of this specification.
В этом разделе даётся обзор типичного режима работы этого расширения. Он не является нормативным. Когда пользователи хотят подписаться на ресурс из списка ресурсов, они могут использовать механизмы, описанные в настоящей спецификации. Первым шагом является создание списка ресурсов. Этот список ресурсов представляется SIP URI. Список содержит набор URI, каждый из которых представляет ресурс, по которому подписчик хочет получать информацию. Список ресурсов может существовать в любом домене. Список может управляться через веб-страницу, через систему голосового ответа или через какой-либо иной протокол. Конкретные средства создания и сопровождения списка выходят за рамки настоящей спецификации.
To learn the resource state of the set of elements on the list, the user sends a single SUBSCRIBE request targeted to the URI of the list. This will be routed to an RLS for that URI. The RLS acts as a notifier, authenticates the subscriber, and accepts the subscription.
Чтобы узнать состояние ресурсов набора элементов списка, пользователь отправляет один запрос SUBSCRIBE, адресованный URI списка. Этот запрос будет маршрутизирован в RLS для данного URI. RLS действует как уведомитель, аутентифицирует подписчика и принимает подписку.
The RLS may have direct information about some or all of the resources specified by the list. If it does not, it could subscribe to any non-local resources specified by the list resource.
RLS может располагать непосредственной информацией о некоторых или всех ресурсах, указанных в списке. Если нет, он может подписаться на любые нелокальные ресурсы, указанные в списке ресурсов.
Note that subscriptions to non-local resources may or may not be SIP subscriptions; any mechanism for determining such information may be employed. This document uses the term "back-end subscription" to refer to such a subscription, regardless of whether SIP is used to establish and service it.
Обратите внимание, что подписки на нелокальные ресурсы могут быть, а могут и не быть SIP-подписками; может использоваться любой механизм определения такой информации. В настоящем документе термин «внутренняя подписка» используется для обозначения такой подписки независимо от того, применяется ли SIP для её установления и обслуживания.
As the state of resources in the list change, the RLS generates notifications to the list subscribers. The RLS can, at its discretion, buffer notifications of resource changes and send the resource information to the subscriber in batches, rather than individually. This allows the RLS to provide rate limiting for the subscriber.
По мере изменения состояния ресурсов в списке RLS формирует уведомления подписчикам списка. RLS может по своему усмотрению буферизовать уведомления об изменениях ресурсов и отправлять информацию о ресурсах подписчику пакетами, а не по отдельности. Это позволяет RLS обеспечивать ограничение скорости для подписчика.
The list notifications contain a body of type multipart/related. The root section of the multipart/related content is an XML document that provides meta-information about each resource present in the list. The remaining sections contain the actual state information for each resource.
Уведомления для списка содержат тело типа multipart/related. Корневая часть содержимого multipart/related — это XML-документ, предоставляющий метаинформацию о каждом ресурсе, присутствующем в списке. Остальные части содержат фактическую информацию о состоянии каждого ресурса.
4. Operation of List Subscriptions
4. Работа подписок на списки ресурсов
The event list extension acts, in many ways, like an event template package. In particular, any single list subscription must be homogeneous with respect to the underlying event package. In other words, a single list subscription can apply only one event package to all the resources in the resource list. Note that it is perfectly valid for an RLS to allow multiple subscriptions to the same list to use differing event packages.
Расширение списка событий во многом действует как пакет-шаблон событий. В частности, любая отдельная подписка на список должна быть однородной в отношении базового пакета событий. Иными словами, одна подписка на список может применять только один пакет событий ко всем ресурсам в списке ресурсов. Обратите внимание, что RLS вполне может разрешать нескольким подпискам на один и тот же список использовать разные пакеты событий.
The key difference between a list subscription and templates in general is that support for list subscriptions indicates support for arbitrary nesting of list subscriptions. In other words, elements within the list may be atomic elements, or they may be lists themselves.
Ключевое отличие подписки на список от шаблонов вообще состоит в том, что поддержка подписок на список означает поддержку произвольной вложенности подписок на список. Иными словами, элементы внутри списка могут быть атомарными элементами или самими списками.
The consequence of this is that subscription to a URI that represents a list actually results in several virtual subscriptions to a tree of resources. The leaf nodes of this tree are virtual subscriptions of the event type given in the "Event" header field; all other nodes in the tree are list subscriptions that are serviced as described in this section and its subsections.
Следствием этого является то, что подписка на URI, представляющий список, фактически приводит к нескольким виртуальным подпискам на дерево ресурсов. Листовые узлы этого дерева — это виртуальные подписки типа события, указанного в поле заголовка «Event»; все остальные узлы дерева — это подписки на список, обслуживаемые так, как описано в этом разделе и его подразделах.
Keep in mind that these virtual subscriptions are not literal SIP subscriptions (although they may result in SIP subscriptions, depending on the RLS implementation).
Помните, что эти виртуальные подписки не являются буквальными SIP-подписками (хотя в зависимости от реализации RLS они могут приводить к SIP-подпискам).
4.1. Negotiation of Support for Resource Lists
4.1. Согласование поддержки списков ресурсов
This specification uses the SIP option tag mechanism for negotiating support for the extension defined herein. Refer to RFC 3261 [1] for the normative description of processing of the "Supported" and "Require" header fields and the 421 (Extension Required) response code.
В настоящей спецификации используется механизм тегов опций SIP для согласования поддержки определяемого здесь расширения. Нормативное описание обработки полей заголовков «Supported» и «Require» и кода ответа 421 (Extension Required) см. в RFC 3261 [1].
A non-normative description of the implications of the use of option tags follows. Any client that supports the event list extension will include an option tag of "eventlist" in a "Supported" header field of every SUBSCRIBE message for a subscription for which it is willing to process a list. If the subscription is made to a URI that represents a list, the RLS will include "eventlist" in a "Require" header field of the response to the SUBSCRIBE, and in all NOTIFY messages within that subscription. Use of "Require: eventlist" in NOTIFY messages is applied by the notifier to satisfy the RFC 3261 requirement that a UAC MUST insert a Require header field into a request if the UAC wishes to insist that a UAS understand an extension in order to process the request. Because the NOTIFY would not be usable without applying the eventlist option, the notifier is obligated to include it.
A non-normative description of the implications of the use of option tags follows. Any client that supports the event list extension will include an option tag of "eventlist" in a "Supported" header field of every SUBSCRIBE message for a subscription for which it is willing to process a list. If the subscription is made to a URI that represents a list, the RLS will include "eventlist" in a "Require" header field of the response to the SUBSCRIBE, and in all NOTIFY messages within that subscription. Use of "Require: eventlist" in NOTIFY messages is applied by the notifier to satisfy the RFC 3261 requirement that a UAC MUST insert a Require header field into a request if the UAC wishes to insist that a UAS understand an extension in order to process the request. Because the NOTIFY would not be usable without applying the eventlist option, the notifier is obligated to include it.
Including "eventlist" in a "Require" header field in a SUBSCRIBE request serves no purpose except to break interoperability in certain cases, and is consequently NOT RECOMMENDED. Sending of "Supported: eventlist" in a NOTIFY message is meaningless and silly. Implementations SHOULD NOT include "Supported: eventlist" in any requests except for SUBSCRIBE.
Включение «eventlist» в поле заголовка «Require» в запросе SUBSCRIBE не имеет иной цели, кроме нарушения взаимодействия в некоторых случаях, и поэтому НЕ РЕКОМЕНДУЕТСЯ. Отправка «Supported: eventlist» в сообщении NOTIFY бессмысленна и нелепа. Реализациям НЕ СЛЕДУЕТ включать «Supported: eventlist» в какие-либо запросы, кроме SUBSCRIBE.
There is nothing in a SIP URI that indicates whether it represents a list of resources or a single resource. Therefore, if a subscriber sends a request to a URI that represents a list resource but does not include a Supported header field listing the "eventlist" token, the notifier will typically return a 421 (Extension Required) response code. RFC 3261 [1] advises that servers avoid returning a 421 and instead attempt to process the request without the extension. However, in this case, the URI fundamentally represents a list resource, and therefore the subscription cannot proceed without this extension.
В SIP URI нет ничего, что указывало бы, представляет ли он список ресурсов или один ресурс. Поэтому, если подписчик отправляет запрос на URI, представляющий список ресурсов, но не включает поле заголовка Supported со словом «eventlist», уведомитель обычно возвращает код ответа 421 (Extension Required). RFC 3261 [1] рекомендует серверам избегать возврата 421 и вместо этого пытаться обработать запрос без расширения. Однако в данном случае URI принципиально представляет список ресурсов, и поэтому подписка не может быть продолжена без этого расширения.
4.2. Subscription Duration
4.2. Длительность подписки
Since the primary benefit of the resource list server is to reduce the overall messaging volume to a subscriber, it is RECOMMENDED that the subscription duration to a list be reasonably long. The default, when no duration is specified, is taken from the underlying event package. Of course, the standard techniques [2] can be used to increase or reduce this amount.
Поскольку основное преимущество сервера списков ресурсов заключается в сокращении общего объёма сообщений подписчику, РЕКОМЕНДУЕТСЯ, чтобы длительность подписки на список была достаточно большой. Значение по умолчанию, когда длительность не указана, берётся из базового пакета событий. Разумеется, стандартные методы [2] можно использовать для увеличения или уменьшения этой величины.
4.3. NOTIFY Bodies
4.3. Тела NOTIFY
An implementation compliant to this specification MUST support the multipart/related and application/rlmi+xml MIME types. These types MUST be included in an Accept header sent in a SUBSCRIBE message, in addition to any other types supported by the client (including any types required by the event package being used).
Реализация, совместимая с настоящей спецификацией, ДОЛЖНА поддерживать типы MIME multipart/related и application/rlmi+xml. Эти типы ДОЛЖНЫ быть включены в заголовок Accept, отправляемый в сообщении SUBSCRIBE, в дополнение к любым другим типам, поддерживаемым клиентом (включая типы, требуемые используемым пакетом событий).
4.4. RLS Processing of SUBSCRIBE Requests
4.4. Обработка запросов SUBSCRIBE сервером RLS
Once the subscriber is authenticated, the RLS performs authorization per its local policy. In many cases, each resource list is associated with a particular user (the one who created it and manages the set of elements in it), and only that user will be allowed to subscribe. Of course, this mode of operation is not inherent in the use of resource lists, and an RLS can use any authorization policy it chooses.
После аутентификации подписчика RLS выполняет авторизацию согласно своей локальной политике. Во многих случаях каждый список ресурсов связан с определённым пользователем (тем, кто его создал и управляет набором элементов в нём), и только этому пользователю будет разрешено подписаться. Разумеется, такой режим работы не является неотъемлемым свойством использования списков ресурсов, и RLS может применять любую выбранную им политику авторизации.
4.5. RLS Generation of NOTIFY Requests
4.5. Формирование запросов NOTIFY сервером RLS
This specification leaves the choice about how and when to generate NOTIFY requests at the discretion of the implementor. One of the differentiators between various RLS implementations is the means by which they aggregate, rate-limit, or optimize the way in which notifications are generated. As a baseline behavior, the RLS MAY generate a NOTIFY to the RLS subscriber whenever the state of any resource on the list changes.
Настоящая спецификация оставляет выбор того, как и когда формировать запросы NOTIFY, на усмотрение разработчика. Одним из отличий между различными реализациями RLS являются средства, с помощью которых они агрегируют, ограничивают скорость или оптимизируют способ формирования уведомлений. В качестве базового поведения RLS МОЖЕТ формировать NOTIFY подписчику RLS всякий раз, когда изменяется состояние любого ресурса в списке.
It is important to understand that any given subscription is a subscription either to a single resource or to a list of resources. This nature (single resource versus list of resources) cannot change during the duration of a single subscription. In particular, this means that RLSes MUST NOT send NOTIFY messages that do not contain RLMI for a subscription if they have previously sent NOTIFY messages in that subscription containing RLMI. Similarly, RLSes MUST NOT send NOTIFY messages that do contain RLMI for a subscription if they have previously sent NOTIFY messages in that subscription which do not.
Важно понимать, что любая данная подписка является подпиской либо на один ресурс, либо на список ресурсов. Эта природа (один ресурс в сравнении со списком ресурсов) не может измениться в течение срока действия одной подписки. В частности, это означает, что RLS НЕ ДОЛЖНЫ отправлять сообщения NOTIFY, не содержащие RLMI для подписки, если они ранее отправляли в этой подписке сообщения NOTIFY, содержащие RLMI. Аналогично RLS НЕ ДОЛЖНЫ отправлять сообщения NOTIFY, содержащие RLMI для подписки, если они ранее отправляли в этой подписке сообщения NOTIFY, которые его не содержат.
List representations necessarily contain RLMI documents for two reasons. Importantly, they identify the resource to which the event state corresponds. Many state syntaxes do not fully identify the resource to which the state applies, or they may identify the resource in a different way than it is represented in the list; for example, PIDF documents may contain resource URIs that are not identical to the URI used to retrieve them. Further, RLMI documents serve to disambiguate multiple instances of a single resource.
Представления списков обязательно содержат документы RLMI по двум причинам. Важно, что они идентифицируют ресурс, которому соответствует состояние события. Многие синтаксисы состояний не полностью идентифицируют ресурс, к которому относится состояние, или могут идентифицировать ресурс иначе, чем он представлен в списке; например, документы PIDF могут содержать URI ресурсов, не совпадающие с URI, использованным для их извлечения. Кроме того, документы RLMI служат для устранения неоднозначности нескольких экземпляров одного ресурса.
See Section 5 for a detailed definition of the syntax used to convey the state of resource lists. For the purposes of the following discussion, it is important to know that the overall list contains zero or more resources, and that the resources contain zero or more instances. Each instance has a state associated with it (pending, active, or terminating) representing the state of the virtual subscription.
Подробное определение синтаксиса, используемого для передачи состояния списков ресурсов, см. в разделе 5. Для целей последующего обсуждения важно знать, что общий список содержит ноль или более ресурсов, а ресурсы содержат ноль или более экземпляров. С каждым экземпляром связано состояние (pending, active или terminating), представляющее состояние виртуальной подписки.
Notifications contain a multipart document, the first part of which always contains meta-information about the list (e.g., membership, state of the virtual subscription to the resource). Remaining parts are used to convey the actual state of the resources listed in the meta-information.
Уведомления содержат составной документ multipart, первая часть которого всегда содержит метаинформацию о списке (например, состав и состояние виртуальной подписки на ресурс). Остальные части используются для передачи фактического состояния ресурсов, перечисленных в метаинформации.
The "state" attribute of each instance of a resource in the meta-information is set according to the state of the virtual subscription. The meanings of the "state" attribute are described in RFC 3265 [2].
Атрибут «state» каждого экземпляра ресурса в метаинформации устанавливается в соответствии с состоянием виртуальной подписки. Значения атрибута «state» описаны в RFC 3265 [2].
If an instance of a resource was previously reported to the subscriber but is no longer available (i.e., the virtual subscription to that instance has been terminated), the resource list server SHOULD include that resource instance in the meta-information in the first NOTIFY message sent to the subscriber following the instance's unavailability. The RLS MAY continue to do so for future notifications.
Если экземпляр ресурса ранее передавался подписчику, но больше не доступен (т. е. виртуальная подписка на этот экземпляр была завершена), сервер списков ресурсов СЛЕДУЕТ включить этот экземпляр ресурса в метаинформацию в первом сообщении NOTIFY, отправленном подписчику после того, как экземпляр стал недоступен. RLS МОЖЕТ продолжать делать это в последующих уведомлениях.
When sending information for a terminated resource instance, the RLS indicates a state of "terminated" and an appropriate reason value. Valid reason values and their meanings are described in RFC 3265 [2]. If the RLS will attempt to recover the resource state again at some point in the future (e.g., when the reason in the meta-information is "probation"), then the instance of the resource SHOULD remain in the meta-information until the instance state is available, or until the RLS gives up on making such state available.
При отправке информации о завершённом экземпляре ресурса RLS указывает состояние «terminated» и соответствующее значение причины. Допустимые значения причины и их смысл описаны в RFC 3265 [2]. Если RLS намерен в какой-то момент в будущем снова попытаться получить состояние ресурса (например, когда причина в метаинформации — «probation»), то экземпляр ресурса СЛЕДУЕТ оставлять в метаинформации до тех пор, пока состояние экземпляра не станет доступным или пока RLS не откажется от попыток сделать такое состояние доступным.
When the first SUBSCRIBE message for a particular subscription is received by an RLS, the RLS will often not know state information for all the resources specified by the resource list. For any resource for which state information is not known, the corresponding "uri" attribute will be set appropriately, and no <instance> elements will be present for the resource.
Когда RLS получает первое сообщение SUBSCRIBE для конкретной подписки, RLS часто не знает информации о состоянии всех ресурсов, указанных в списке ресурсов. Для любого ресурса, информация о состоянии которого неизвестна, соответствующий атрибут «uri» будет установлен надлежащим образом, а элементы <instance> для этого ресурса присутствовать не будут.
For an initial notification, sections corresponding to resources for which the RLS does have state will be populated with appropriate data (subject, of course, to local policy decisions). This will often occur if the resource list server is co-located with the server for one or more of the resources specified on the list.
В первоначальном уведомлении части, соответствующие ресурсам, состояние которых RLS действительно знает, будут заполнены соответствующими данными (с учётом, разумеется, решений локальной политики). Это часто происходит, если сервер списков ресурсов размещён совместно с сервером для одного или нескольких ресурсов, указанных в списке.
Immediate notifications triggered as a result of subsequent SUBSCRIBE messages SHOULD include an RLMI document in which the full state is indicated. The RLS SHOULD also include state information for all resources in the list for which the RLS has state, subject to policy restrictions. This allows the subscriber to refresh their state, and to recover from lost notifications.
Немедленные уведомления, вызванные последующими сообщениями SUBSCRIBE, СЛЕДУЕТ включать документ RLMI, в котором указано полное состояние. RLS СЛЕДУЕТ также включать информацию о состоянии для всех ресурсов в списке, состояние которых RLS знает, с учётом ограничений политики. Это позволяет подписчику обновлять своё состояние и восстанавливаться после потерянных уведомлений.
4.6. Subscriber Processing of NOTIFY Requests
4.6. Обработка запросов NOTIFY подписчиком
Notifications for a resource list can convey information about a subset of the list elements. This means that an explicit algorithm needs to be defined in order to construct coherent and consistent state.
Уведомления для списка ресурсов могут передавать информацию о подмножестве элементов списка. Это означает, что для построения связного и согласованного состояния необходимо определить явный алгоритм.
The XML document present in the root of the multipart/related document contains a <resource> element for some or all of the resources in the list. Each <resource> element contains a URI that uniquely identifies the resource to which that section corresponds. When a NOTIFY arrives, it can contain full or partial state (as indicated by the "fullState" attribute of the top-level <list> element). If full state is indicated, then the recipient replaces all state associated with the list with the entities in the NOTIFY body. If full state is not indicated, the recipient of the NOTIFY updates information for each identified resource. Information for any resources that are not identified in the NOTIFY is not changed, even if they were indicated in previous NOTIFY messages. See Section 5.6 for more information.
XML-документ, присутствующий в корне документа multipart/related, содержит элемент <resource> для некоторых или всех ресурсов списка. Каждый элемент <resource> содержит URI, однозначно идентифицирующий ресурс, которому соответствует эта часть. Когда приходит NOTIFY, он может содержать полное или частичное состояние (как указано атрибутом «fullState» элемента <list> верхнего уровня). Если указано полное состояние, получатель заменяет всё состояние, связанное со списком, сущностями из тела NOTIFY. Если полное состояние не указано, получатель NOTIFY обновляет информацию для каждого идентифицированного ресурса. Информация для любых ресурсов, не идентифицированных в NOTIFY, не изменяется, даже если они были указаны в предыдущих сообщениях NOTIFY. Дополнительные сведения см. в разделе 5.6.
When full state is indicated, note that it applies only to the RLMI document in which it occurs. In particular, one of the <resource> elements in the document may in turn refer to another list of resources. Any such sub-lists will be detailed in their own RLMI documents, which may or may not have full state indicated.
Когда указано полное состояние, обратите внимание, что оно относится только к документу RLMI, в котором оно встречается. В частности, один из элементов <resource> в документе может, в свою очередь, ссылаться на другой список ресурсов. Любые такие подсписки будут подробно описаны в их собственных документах RLMI, в которых полное состояние может быть указано или не указано.
Further note that the underlying event package may have its own rules for compositing partial state notification.
Далее обратите внимание, что базовый пакет событий может иметь собственные правила компоновки уведомлений о частичном состоянии.
When processing data related to those packages, their rules apply (i.e., the fact that they were reported as part of a list does not change their partial notification semantics).
При обработке данных, относящихся к таким пакетам, применяются их собственные правила (то есть то, что они были переданы в составе списка, не меняет семантику частичных уведомлений).
Finally, note that as a consequence of the way in which resource list subscriptions work, polling of resource state may not be particularly useful. While such polls will retrieve the resource list, they will not necessarily contain state for some or all of the resources on the list.
Наконец, отметим, что вследствие того, как работают подписки на список ресурсов, опрос состояния ресурсов может быть не особенно полезен. Хотя такой опрос и вернёт список ресурсов, он не обязательно будет содержать состояние некоторых или всех ресурсов списка.
4.7. Handling of Forked Requests
4.7. Обработка разветвлённых запросов
Forking makes little sense with subscriptions to event lists, since the whole idea is a centralization of the source of notifications. Therefore, a subscriber to a list MUST NOT install multiple subscriptions when the initial request is forked. If multiple responses are received, they are handled using the techniques described in Section 4.4.9 of RFC 3265 [2].
Разветвление имеет мало смысла при подписках на списки событий, поскольку вся идея состоит в централизации источника уведомлений. Поэтому подписчик на список НЕ ДОЛЖЕН устанавливать несколько подписок, когда первоначальный запрос разветвляется. Если получено несколько ответов, они обрабатываются с использованием методов, описанных в разделе 4.4.9 RFC 3265 [2].
4.8. Rate of Notifications
4.8. Частота уведомлений
One potential role of the RLS is to perform rate limitations on behalf of the subscriber. As such, this specification does not mandate any particular rate limitation, and rather leaves that to the discretion of the implementation.
Одна из возможных ролей RLS — выполнять ограничение частоты от имени подписчика. Поэтому настоящая спецификация не предписывает какого-либо конкретного ограничения частоты, а оставляет это на усмотрение реализации.

5.2. List Attributes
5.2. Атрибуты списка
The <list> element present in a list notification MUST contain three attributes.
Элемент <list>, присутствующий в уведомлении для списка, ДОЛЖЕН содержать три атрибута.
The first mandatory <list> attribute is "uri", which contains the uri that corresponds to the list. Typically, this is the URI to which the SUBSCRIBE request was sent.
Первый обязательный атрибут <list> — «uri», содержащий URI, соответствующий списку. Обычно это URI, на который был отправлен запрос SUBSCRIBE.
The second mandatory <list> attribute is "version", which contains a number from 0 to 2^32-1. This version number MUST be 0 for the first NOTIFY message sent within a subscription, and MUST increase by exactly one for each subsequent NOTIFY sent within a subscription.
Второй обязательный атрибут <list> — «version», содержащий число от 0 до 2^32-1. Этот номер версии ДОЛЖЕН быть равен 0 для первого сообщения NOTIFY, отправленного в рамках подписки, и ДОЛЖЕН увеличиваться ровно на единицу для каждого последующего NOTIFY, отправленного в рамках подписки.
The third mandatory attribute is "fullState". The "fullState" attribute indicates whether the NOTIFY message contains information for every resource in the list. If it does, the value of the attribute is "true" (or "1"); otherwise, it is "false" (or "0"). The first NOTIFY sent in a subscription MUST contain full state, as must the first NOTIFY sent after receipt of a SUBSCRIBE request for the subscription.
Третий обязательный атрибут — «fullState». Атрибут «fullState» указывает, содержит ли сообщение NOTIFY информацию о каждом ресурсе в списке. Если содержит, значение атрибута — «true» (или «1»); в противном случае — «false» (или «0»). Первый NOTIFY, отправленный в подписке, ДОЛЖЕН содержать полное состояние, как и первый NOTIFY, отправленный после получения запроса SUBSCRIBE для этой подписки.
Finally, <list> elements MAY contain a "cid" attribute. If present, the "cid" attribute identifies a section within the multipart/related body that contains aggregate state information for the resources contained in the list. The definition of such aggregate information is outside the scope of this document and will be defined on a per- package basis, as needed. The cid attribute is the Content-ID for the corresponding section in the multipart body.
Наконец, элементы <list> МОГУТ содержать атрибут «cid». Если он присутствует, атрибут «cid» идентифицирует часть тела multipart/related, содержащую агрегированную информацию о состоянии ресурсов, входящих в список. Определение такой агрегированной информации выходит за рамки настоящего документа и будет определяться для каждого пакета по мере необходимости. Атрибут cid — это Content-ID для соответствующей части тела multipart.
The cid attribute MUST refer only to top-level parts of the multipart/related document for which the RLMI document in which it appears is the root. See Section 5.5 for an example.
Атрибут cid ДОЛЖЕН ссылаться только на части верхнего уровня документа multipart/related, для которого документ RLMI, в котором он появляется, является корневым. Пример см. в разделе 5.5.
5.3. Resource Attributes
5.3. Атрибуты ресурса
The resource list contains one <resource> element for each resource being reported in the notification. These resource elements contain attributes that identify meta-data associated with each resource.
Список ресурсов содержит один элемент <resource> для каждого ресурса, о котором сообщается в уведомлении. Эти элементы resource содержат атрибуты, идентифицирующие метаданные, связанные с каждым ресурсом.
The "uri" attribute identifies the resource to which the <resource> element corresponds. Typically, this will be a SIP URI that, if subscribed to, would return the state of the resource. This attribute MUST be present.
Атрибут «uri» идентифицирует ресурс, которому соответствует элемент <resource>. Обычно это SIP URI, который при подписке на него возвращал бы состояние ресурса. Этот атрибут ДОЛЖЕН присутствовать.
5.4. Name Attributes
5.4. Атрибуты имени
Each list and resource element contains zero or more name elements. These name elements contain human-readable descriptions or names for the resource list or resource. The contents of these elements are somewhat analogous to the "Display Name" present in the SIP name-addr element.
Каждый элемент list и resource содержит ноль или более элементов name. Эти элементы name содержат удобочитаемые описания или имена для списка ресурсов или ресурса. Содержимое этих элементов в некоторой степени аналогично «Display Name», присутствующему в элементе name-addr SIP.
Name elements optionally contain the standard XML "xml:lang" attribute. The "xml:lang" attribute, if present, specifies the language of the human-readable name. If this attribute is present, it MUST contain a valid language tag. Language tags are defined in RFC 3066 [6]. The language tag assists applications in determining which of potentially several name elements should be rendered to the user.
Элементы name необязательно содержат стандартный атрибут XML «xml:lang». Атрибут «xml:lang», если он присутствует, задаёт язык удобочитаемого имени. Если этот атрибут присутствует, он ДОЛЖЕН содержать допустимый тег языка. Теги языка определены в RFC 3066 [6]. Тег языка помогает приложениям определить, какой из потенциально нескольких элементов name следует отобразить пользователю.
5.5. Instance Attributes
5.5. Атрибуты экземпляра
Each resource element contains zero or more instance elements. These instance elements are used to represent a single notifier for the resource. For event packages that allow forking, multiple virtual subscriptions may exist for a given resource. Multiple virtual subscriptions are represented as multiple instance elements in the corresponding resource element. For subscriptions in which forking does not occur, at most one instance will be present for a given resource.
Каждый элемент resource содержит ноль или более элементов instance. Эти элементы instance используются для представления одного уведомителя для ресурса. Для пакетов событий, допускающих разветвление, для данного ресурса может существовать несколько виртуальных подписок. Несколько виртуальных подписок представляются несколькими элементами instance в соответствующем элементе resource. Для подписок, в которых разветвление не происходит, для данного ресурса будет присутствовать не более одного экземпляра.
The "id" attribute contains an opaque string used to uniquely identify the instance of the resource. The "id" attribute is unique only within the context of a resource. Construction of this string is an implementation decision. Any mechanism for generating this string is valid, as long as uniqueness within the resource is assured.
Атрибут «id» содержит непрозрачную строку, используемую для однозначной идентификации экземпляра ресурса. Атрибут «id» уникален только в контексте ресурса. Построение этой строки — решение реализации. Любой механизм генерации этой строки допустим при условии обеспечения уникальности в пределах ресурса.
The "state" attribute contains the subscription state for the identified instance of the resource. This attribute contains one of the values "active", "pending", or "terminated". The meanings for these values are as defined for the "Subscription-State" header field in RFC 3265 [2].
Атрибут «state» содержит состояние подписки для идентифицированного экземпляра ресурса. Этот атрибут содержит одно из значений «active», «pending» или «terminated». Смысл этих значений определён для поля заголовка «Subscription-State» в RFC 3265 [2].
If the "state" attribute indicates "terminated", then a "reason" attribute MUST also be present. This "reason" attribute has the same values and meanings as those given for the "reason" parameter on the "Subscription-State" header field in RFC 3265 [2]. Note that the "reason" attribute is included for informational purposes; the list subscriber is not expected to take any automated actions based on the reason value.
Если атрибут «state» указывает «terminated», то также ДОЛЖЕН присутствовать атрибут «reason». Этот атрибут «reason» имеет те же значения и смысл, что и для параметра «reason» в поле заголовка «Subscription-State» в RFC 3265 [2]. Обратите внимание, что атрибут «reason» включается в информационных целях; подписчик списка не обязан предпринимать какие-либо автоматические действия на основе значения причины.
Finally, the "cid" attribute, which MUST be present if the "state" attribute is "active", identifies the section within the multipart/related body that contains the actual resource state. This state is expressed in the content type defined by the event package for conveying state. The cid attribute is the Content-ID for the corresponding section in the multipart body.
Наконец, атрибут «cid», который ДОЛЖЕН присутствовать, если атрибут «state» равен «active», идентифицирует часть тела multipart/related, содержащую фактическое состояние ресурса. Это состояние выражается в типе содержимого, определённом пакетом событий для передачи состояния. Атрибут cid — это Content-ID для соответствующей части тела multipart.
The cid attribute MUST refer only to top-level parts of the multipart/related document for which the RLMI document in which it appears is the root.
Атрибут cid ДОЛЖЕН ссылаться только на части верхнего уровня документа multipart/related, для которого документ RLMI, в котором он появляется, является корневым.

5.6. Constructing Coherent Resource State
5.6. Построение связного состояния ресурсов
The resource list subscriber maintains a table for each resource list. The table contains a row for each resource in the resource list. Each row is indexed by the URI for that resource. That URI is obtained from the "uri" attribute on each <resource> element. The contents of each row contain the state of that resource as conveyed in the resource document. For resources that provide versioning information (which is mandated by [2] for any formats that allow partial notification), each row also contains a resource state version number. The version number of the row is initialized with the version specified in the first document received, as defined by the corresponding event package. This value is used when comparing versions of partial notifications for a resource.
Подписчик списка ресурсов ведёт таблицу для каждого списка ресурсов. Таблица содержит строку для каждого ресурса в списке. Каждая строка индексируется по URI этого ресурса. Этот URI берётся из атрибута «uri» каждого элемента <resource>. Содержимое каждой строки содержит состояние этого ресурса в том виде, в каком оно передано в документе ресурса. Для ресурсов, предоставляющих информацию о версии (что требуется в [2] для любых форматов, допускающих частичные уведомления), каждая строка также содержит номер версии состояния ресурса. Номер версии строки инициализируется версией, указанной в первом полученном документе, как определено соответствующим пакетом событий. Это значение используется при сравнении версий частичных уведомлений для ресурса.
The processing of the resource list notification depends on whether it contains full or partial state.
Обработка уведомления для списка ресурсов зависит от того, содержит ли оно полное или частичное состояние.
5.6.1. Processing Full State Notifications
5.6.1. Обработка уведомлений о полном состоянии
If a notification contains full state, indicated by the <list> attribute "fullState" set to "true", the notification is used to update the table. A check is first made to ensure that the "version" attribute of the <list> attribute in the received message is greater than the local version number. If not, the received document is discarded without any further processing. Otherwise, the contents of the resource-list table are flushed and repopulated from the contents of the document. A new row in the table is created for each "resource" element.
Если уведомление содержит полное состояние, обозначенное атрибутом <list> «fullState», установленным в «true», уведомление используется для обновления таблицы. Сначала выполняется проверка, что атрибут «version» атрибута <list> в полученном сообщении больше локального номера версии. Если нет, полученный документ отбрасывается без дальнейшей обработки. В противном случае содержимое таблицы списка ресурсов очищается и заново заполняется из содержимого документа. Для каждого элемента «resource» создаётся новая строка таблицы.
5.6.2. Processing Partial State Notifications
5.6.2. Обработка уведомлений о частичном состоянии
If a notification contains partial state, indicated by the <list> attribute "fullState" set to "false", a check is made to ensure that no list notifications have been lost. The value of the local version number (the "version" attribute of the <list> element) is compared to the version number of the new document.
Если уведомление содержит частичное состояние, обозначенное атрибутом <list> «fullState», установленным в «false», выполняется проверка, что ни одно уведомление для списка не было потеряно. Значение локального номера версии (атрибут «version» элемента <list>) сравнивается с номером версии нового документа.
o If the value in the new document is exactly one higher than the local version number, the local version number is increased by one, and the document is processed as described below.
o Если значение в новом документе ровно на единицу больше локального номера версии, локальный номер версии увеличивается на единицу, а документ обрабатывается так, как описано ниже.
o If the version in the document is more than one higher than the local version number, the local version number is set to the value in the new document, and the document is processed as described below. The list subscriber SHOULD also generate a refresh request to trigger a full state notification.
o Если версия в документе более чем на единицу больше локального номера версии, локальный номер версии устанавливается в значение из нового документа, а документ обрабатывается так, как описано ниже. Подписчику списка СЛЕДУЕТ также сформировать запрос на обновление, чтобы вызвать уведомление о полном состоянии.
o If the version in the document is less than or equal to the local version, the document is discarded without any further processing.
o Если версия в документе меньше или равна локальной версии, документ отбрасывается без какой-либо дальнейшей обработки.
For each resource listed in the document, the subscriber checks to see whether a row exists for that resource. This check is done by comparing the Resource-URI value with the URI associated with the row. If the resource doesn't exist in the table, a row is added, and its state is set to the information from that "resource" element. If the resource does exist, its state is updated to be the information from that "resource" element, as described in the definition of the event package. If a row is updated or created such that its state is now "terminated," that entry MAY be removed from the table at any time.
Для каждого ресурса, перечисленного в документе, подписчик проверяет, существует ли строка для этого ресурса. Эта проверка выполняется путём сравнения значения Resource-URI с URI, связанным со строкой. Если ресурс отсутствует в таблице, добавляется строка, и её состояние устанавливается по информации из этого элемента «resource». Если ресурс существует, его состояние обновляется информацией из этого элемента «resource», как описано в определении пакета событий. Если строка обновлена или создана так, что её состояние теперь «terminated», эта запись МОЖЕТ быть удалена из таблицы в любое время.

7. Security Considerations
7. Вопросы безопасности
Note that the mechanisms for obtaining state information for resources in a list are generally left to the RLS implementor. Some of the security issues below are specific to the circumstance in which a SIP back-end subscription is used for such a purpose. Non- SIP mechanisms for obtaining state information of resources in a list will typically have their own security issues associated with doing so; however, exhaustively enumerating such access methods is not possible in this document. Implementors using such mechanisms must analyze their chosen access methods for relevant security issues.
Обратите внимание, что механизмы получения информации о состоянии ресурсов в списке обычно оставляются на усмотрение разработчика RLS. Некоторые из описанных ниже вопросов безопасности специфичны для случая, когда для этой цели используется внутренняя подписка SIP. Механизмы, не основанные на SIP, для получения информации о состоянии ресурсов в списке обычно имеют собственные связанные с этим вопросы безопасности; однако исчерпывающе перечислить такие методы доступа в настоящем документе невозможно. Разработчики, использующие такие механизмы, должны проанализировать выбранные ими методы доступа на предмет соответствующих вопросов безопасности.
7.1. Authentication
7.1. Аутентификация
If back-end subscriptions are required to retrieve resource state information, the end user is no longer the direct subscriber to the state of the resource. This means that direct authentication of the user is no longer possible.
Если для получения информации о состоянии ресурса требуются внутренние подписки, конечный пользователь больше не является непосредственным подписчиком на состояние ресурса. Это означает, что прямая аутентификация пользователя становится невозможной.
7.1.1. RLS and Subscriber in the Same Domain
7.1.1. RLS и подписчик в том же домене
It is expected that the most common deployment of RLSes entails that the subscribers to the RLS will be in the same domain as the RLS. When this is the case, the RLS then has the ability to act as an authentication service. The role of authentication service is defined in "Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)" [7].
Ожидается, что при наиболее распространённом развёртывании RLS подписчики RLS будут находиться в том же домене, что и RLS. В этом случае RLS имеет возможность действовать как служба аутентификации. Роль службы аутентификации определена в документе «Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)» [7].
At a high level, under this system, the RLS authenticates the subscriber and then includes an "Identity" header field in all of the back-end subscriptions performed on behalf of that authenticated user. This "Identity" header field cryptographically asserts that the request has been authorized to be made on behalf of the user indicated in the "From" header field. Because the ability to authenticate requests is central to the proper functioning of the network, any RLS that uses SIP back-end subscriptions to acquire information about the resources in a resource list MUST be able to act as an authentication service as defined in [7], provided that local administrative policy allows it to do so.
В общих чертах, в рамках этой системы RLS аутентифицирует подписчика, а затем включает поле заголовка «Identity» во все внутренние подписки, выполняемые от имени этого аутентифицированного пользователя. Это поле заголовка «Identity» криптографически подтверждает, что запрос авторизован для выполнения от имени пользователя, указанного в поле заголовка «From». Поскольку способность аутентифицировать запросы имеет центральное значение для правильного функционирования сети, любой RLS, который использует внутренние подписки SIP для получения информации о ресурсах в списке ресурсов, ДОЛЖЕН иметь возможность действовать как служба аутентификации, определённая в [7], при условии, что локальная административная политика это позволяет.
In other words, all RLS implementations that support back-end SIP subscriptions also must include the ability to be configured to act as an authentication service. Whether any given administrator chooses to activate such a feature is completely up to them. Of course, lacking the ability to act as an identity server, any RLS so configured will behave as described in the following section, since it is effectively acting as if it were in a different domain than the user.
Иными словами, все реализации RLS, поддерживающие внутренние подписки SIP, также должны включать возможность настройки для работы в качестве службы аутентификации. Захочет ли конкретный администратор активировать такую функцию, полностью зависит от него. Разумеется, при отсутствии возможности действовать как сервер идентификации любой настроенный таким образом RLS будет вести себя так, как описано в следующем разделе, поскольку фактически он действует так, как если бы находился в другом домене, нежели пользователь.
7.1.2. RLS and Subscriber in Different Domains
7.1.2. RLS и подписчик в разных доменах
In the general case, the SIP Authenticated Identity extensions do not provide a means for the RLS to securely assert that subscriptions are being performed on the end user's behalf. Specifically, when the subscriber and the RLS are in different domains, the RLS will have no means by which it can vouch for the user's identity. Mechanisms by which back-end subscriptions in such circumstances can be authenticated are left for future study.
В общем случае расширения аутентифицированной идентификации SIP не предоставляют RLS средств для безопасного подтверждения того, что подписки выполняются от имени конечного пользователя. В частности, когда подписчик и RLS находятся в разных доменах, RLS не будет иметь средств, с помощью которых он мог бы поручиться за личность пользователя. Механизмы, с помощью которых можно было бы аутентифицировать внутренние подписки в таких обстоятельствах, оставлены для дальнейшего изучения.
Until such general solutions are developed, RLSes that are in a different domain than the subscriber on whose behalf they are creating back-end subscriptions SHOULD subscribe to the resources using their own identity. By doing so, the RLS will generally obtain only the resource information that is made publicly available.
До разработки таких общих решений RLS, находящимся в домене, отличном от домена подписчика, от имени которого они создают внутренние подписки, СЛЕДУЕТ подписываться на ресурсы, используя собственную идентичность. Поступая так, RLS обычно получает только ту информацию о ресурсах, которая сделана общедоступной.
Absent such general solutions, implementations of subscriber user agents MAY attempt direct subscriptions to resources in the resource list when subscribing to an RLS outside of their domain (either directly or by way of another resource list subscription). The resources to be subscribed to will be those indicated in the "uri" attribute of the <resource> elements present in the RLMI document returned by the RLS. Directly subscribing to the resources allows proper authentication of the user to take place, which will generally authorize them to receive more complete state information. Implementations that choose to perform such direct subscriptions SHOULD use the data retrieved instead of any information about the resource obtained via the list subscription.
При отсутствии таких общих решений реализации пользовательских агентов подписчика МОГУТ пытаться выполнять прямые подписки на ресурсы в списке ресурсов при подписке на RLS вне своего домена (непосредственно или через другую подписку на список ресурсов). Подписываться следует на ресурсы, указанные в атрибуте «uri» элементов <resource>, присутствующих в документе RLMI, возвращённом RLS. Прямая подписка на ресурсы позволяет провести надлежащую аутентификацию пользователя, что обычно даёт ему право получать более полную информацию о состоянии. Реализациям, которые решают выполнять такие прямые подписки, СЛЕДУЕТ использовать полученные данные вместо любой информации о ресурсе, полученной через подписку на список.
7.2. Risks of Improper Aggregation
7.2. Риски неправильного агрегирования
A resource list server typically serves information to multiple subscribers at once. In many cases, resources may be present in several lists; additionally, it is quite possible that resource list servers will have two users subscribe to the same list.
Сервер списков ресурсов обычно обслуживает информацию для нескольких подписчиков одновременно. Во многих случаях ресурсы могут присутствовать в нескольких списках; кроме того, вполне возможно, что на одном сервере списков ресурсов два пользователя подпишутся на один и тот же список.
In these cases, misguided RLS implementations may attempt to minimize network load by maintaining only one back-end subscription to a resource in a list and presenting the result of such a subscription to more than one user. Of course, doing so circumvents any authorization policy that the notifier for the resource maintains. Keep in mind that authorization is often much more than a simple binary "allowed/not allowed" decision; resources may render very different -- and even conflicting -- resource states, depending on the identity of the subscribing user.
В этих случаях ошибочные реализации RLS могут пытаться минимизировать сетевую нагрузку, поддерживая только одну внутреннюю подписку на ресурс в списке и представляя результат такой подписки более чем одному пользователю. Разумеется, это обходит любую политику авторизации, которую поддерживает уведомитель ресурса. Помните, что авторизация часто представляет собой нечто гораздо большее, чем простое бинарное решение «разрешено/не разрешено»; ресурсы могут отображать совершенно разные — и даже противоречивые — состояния в зависимости от личности подписывающегося пользователя.
To prevent the transmission of event information to anyone other than the intended recipient, implementations MUST NOT present the result of one back-end subscription to more than one user, unless:
Чтобы предотвратить передачу информации о событиях кому-либо, кроме предполагаемого получателя, реализации НЕ ДОЛЖНЫ представлять результат одной внутренней подписки более чем одному пользователю, если только:
a. The RLS has adequate access to the complete authorization policy associated with the resource to which the back-end subscription has been made, AND
a. RLS имеет надлежащий доступ к полной политике авторизации, связанной с ресурсом, для которого создана внутренняя подписка, И
b. The RLS can and has determined that presenting the information to more than one user does not violate such policy.
b. RLS может и уже определил, что представление информации более чем одному пользователю не нарушает такую политику.
Note that this is a very difficult problem to solve correctly. Even in the cases where such access is believed possible, this mode of operation is NOT RECOMMENDED.
Обратите внимание, что эту проблему очень трудно решить правильно. Даже в случаях, когда считается, что такой доступ возможен, этот режим работы НЕ РЕКОМЕНДУЕТСЯ.
7.3. Signing and Sealing
7.3. Подписание и запечатывание
Implementors should keep in mind that any section of the MIME body may be signed and/or encrypted as necessary. Resource List Servers should take care not to modify any MIME bodies they receive from any back-end subscriptions, and should not generally rely on being able to read them.
Разработчикам следует помнить, что любая часть тела MIME может быть подписана и/или зашифрована по мере необходимости. Серверам списков ресурсов следует заботиться о том, чтобы не изменять любые тела MIME, получаемые из внутренних подписок, и обычно не следует рассчитывать на возможность их чтения.
In order to facilitate security, resource list servers SHOULD pass along indication for support of "multipart/signed" and "application/ pkcs7-mime" content types to any SIP back-end subscriptions, if the subscriber includes them in the initial SUBSCRIBE message. Not doing so may actually result in resources refusing to divulge state (if notifier policy requires encryption, but the RLS fails to convey support), or subscribers discarding valid state (if subscriber policy requires a signature, but the RLS fails to convey support). Note that actual implementation of encryption and signing by the RLS is not necessary to be able to pass through signed and/or encrypted bodies.
Чтобы способствовать безопасности, серверам списков ресурсов СЛЕДУЕТ передавать указание о поддержке типов содержимого «multipart/signed» и «application/pkcs7-mime» во все внутренние подписки SIP, если подписчик включает их в первоначальное сообщение SUBSCRIBE. Невыполнение этого может фактически привести к тому, что ресурсы откажутся раскрывать состояние (если политика уведомителя требует шифрования, а RLS не передаёт сведения о поддержке), или подписчики будут отбрасывать допустимое состояние (если политика подписчика требует подписи, а RLS не передаёт сведения о поддержке). Обратите внимание, что фактическая реализация шифрования и подписания в RLS не требуется для возможности пропускать подписанные и/или зашифрованные тела.
7.4. Infinite Loops
7.4. Бесконечные циклы
One risk introduced by the ability to nest resource lists is the possibility of creating lists that ultimately contain themselves as a sub-list. Detection and handling of such a case is trivial when the RLS services all the virtual subscriptions internally. When back-end subscriptions are created to service virtual subscriptions, however, detection of such situations becomes a more difficult problem.
Один из рисков, связанных с возможностью вложения списков ресурсов, — возможность создания списков, которые в конечном счёте содержат сами себя в качестве подсписка. Обнаружение и обработка такого случая тривиальны, когда RLS обслуживает все виртуальные подписки внутри себя. Однако когда для обслуживания виртуальных подписок создаются внутренние подписки, обнаружение таких ситуаций становится более сложной задачей.
Implementors of RLSes that create back-end subscriptions MUST implement safeguards to prevent such nestings from creating an infinite loop of subscriptions. Typically, such mechanisms will require support in the back-end subscription protocol. In particular, applying filters to the back-end subscriptions can be an effective way to preclude such problems.
Разработчики RLS, создающих внутренние подписки, ДОЛЖНЫ реализовать меры защиты, предотвращающие создание такими вложениями бесконечного цикла подписок. Обычно такие механизмы требуют поддержки в протоколе внутренней подписки. В частности, применение фильтров к внутренним подпискам может быть эффективным способом предотвращения таких проблем.
