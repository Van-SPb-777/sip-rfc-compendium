Abstract
Аннотация
A Session Initiation Protocol (SIP) User Agent (UA) does not always trust all intermediaries in its request path to inspect its message bodies and/or headers contained in its message. The UA might want to protect the message bodies and/or headers from intermediaries, except those that provide services based on its content. This situation requires a mechanism called "end-to-middle security" to secure the information passed between the UA and intermediaries, which does not interfere with end-to-end security. This document defines a set of requirements for a mechanism to achieve end-to-middle security.
Пользовательский агент (UA) протокола инициирования сессий (SIP) не всегда доверяет всем посредникам на своем пути запроса для проверки тела сообщения и/или заголовков, содержащихся в его сообщении. UA может захотеть защитить тела и/или заголовки сообщений от посредников, за исключением тех, которые предоставляют услуги на основе его содержимого. Эта ситуация требует механизма, называемого «сквозная безопасность», для защиты информации, передаваемой между UA и посредниками, который не мешает сквозной безопасности. Этот документ определяет набор требований к механизму достижения сквозной безопасности.
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [2] supports hop-by-hop security using Transport Layer Security (TLS) [3] and end-to-end security using Secure MIME (S/MIME) [4]. Use of TLS assumes that a SIP UA trusts all proxy servers along its request path to inspect the message bodies contained in the message, and use of S/MIME assumes that a SIP UA does not trust any proxy servers to do so.
Протокол инициирования сессий (SIP) [2] поддерживает пошаговую безопасность с использованием Transport Layer Security (TLS) [3] и сквозную безопасность с использованием Secure MIME (S/MIME) [4]. Использование TLS предполагает, что UA SIP доверяет всем прокси на своем пути запроса для проверки тела сообщения, содержащегося в сообщении, а использование S/MIME предполагает, что UA SIP не доверяет никаким прокси в этом отношении.
However, there is a model in which trusted and partially-trusted proxy servers are mixed along a message path. The partially-trusted proxy servers are only trusted to provide SIP routing, but these proxy servers are not trusted by users to inspect its data, except the routing headers. A hop-by-hop confidentiality service using TLS is not suitable for this model. An end-to-end confidentiality service using S/MIME is also not suitable when the intermediaries provide services based on reading the message bodies and/or headers. This problem is described in Section 23 of [2].
Однако существует модель, в которой на пути сообщения смешаны доверенные и частично доверенные прокси. Прокси с частичным доверием доверяют только обеспечение SIP-маршрутизации, но пользователи не доверяют этим прокси проверять свои данные, за исключением заголовков маршрутизации. Пошаговая служба конфиденциальности с использованием TLS не подходит для этой модели. Служба сквозной конфиденциальности с использованием S/MIME также не подходит, когда посредники предоставляют услуги, основанные на чтении тел сообщений и/или заголовков. Эта проблема описана в разделе 23 книги [2].
In some cases, a UA might want to protect its message bodies and/or headers from proxy servers along its request path, except from those that provide services based on reading its message bodies and/or headers. Conversely, a proxy server might want to view the message bodies and/or headers to sufficiently provide these services. Such proxy servers are not always the first hop from the UA. This situation requires a security mechanism to secure message bodies and/or headers between the UA and the proxy servers, while disclosing information to those that need it. We call this "end-to-middle security".
В некоторых случаях UA может захотеть защитить тела и/или заголовки своих сообщений от прокси на своем пути запроса, за исключением тех, которые предоставляют услуги на основе чтения тел и/или заголовков сообщений. И наоборот, прокси может захотеть просмотреть тела и/или заголовки сообщений, чтобы в достаточной степени предоставить эти услуги. Такие прокси не всегда являются первым переходом от UA. Эта ситуация требует механизма безопасности для защиты тел и/или заголовков сообщений между UA и прокси, одновременно раскрывая информацию тем, кто в ней нуждается. Мы называем это «сквозной безопасностью».

2.2. Service Examples
2.2. Примеры услуг
We describe here several services that require end-to-middle security.
Здесь мы описываем несколько сервисов, требующих комплексной безопасности.
2.2.1. Logging Services for Instant Messages
2.2.1. Службы регистрации мгновенных сообщений
Logging Services are provided by the archiving function, which is located in the proxy server, that logs the message content exchanged between UAs. The archiving function could be located at the originator network and/or the destination network. When the content of an instant message contains private information, UACs (UA Clients) encrypt the content for the UASes (UA Servers). The archiving function needs to log the content in a message body in bidirectional MESSAGE requests in such a way that the data is decipherable. The archiving function also needs a way to verify the data integrity of the content before logging.
Услуги ведения журнала предоставляются функцией архивирования, расположенной на прокси и регистрирующей содержимое сообщений, которыми обмениваются UA. Функция архивирования может быть расположена в сети отправителя и/или сети назначения. Когда содержимое мгновенного сообщения содержит личную информацию, UAC (клиенты UA) шифруют содержимое для UAS (серверов UA). Функция архивирования должна регистрировать содержимое тела сообщения в двунаправленных запросах MESSAGE таким образом, чтобы данные можно было расшифровать. Функция архивирования также нуждается в способе проверки целостности данных содержимого перед записью в журнал.
This service might be deployed in financial networks, health care service provider's networks, as well as other networks in which archiving communication is required by their security policies.
Эта услуга может быть развернута в финансовых сетях, сетях поставщиков медицинских услуг, а также в других сетях, в которых политика безопасности требует архивирования связи.
2.2.2. Non-emergency Call Routing Based on the Location Object
2.2.2. Non-emergency Маршрутизация вызовов на основе объекта местоположения
The Location Object [6] includes a person's geographical location information that is privacy-sensitive. Some proxy servers will have the ability to provide routing based on the geographical location information. When UAs want to employ location-based routing in non-emergency situations, the UAs need to connect to the proxy servers with such a capability and disclose the geographical location information contained in the message body of the INVITE request, while protecting it from other proxy servers along the request path. The Location Object also needs to be verified for data integrity by the proxy servers before location-based routing is applied. Sometimes the UACs want to send the Location Object to the UASes. This is another good example that presents the need for UACs to simultaneously send secure data to a proxy server and to the UASes.
Объект местоположения [6] включает в себя информацию о географическом местоположении человека, которая является конфиденциальной. Некоторые прокси будут иметь возможность обеспечивать маршрутизацию на основе информации о географическом местоположении. Когда UA хотят использовать маршрутизацию на основе местоположения в нечрезвычайных ситуациях, UA необходимо подключиться к прокси с такой возможностью и раскрыть информацию о географическом местоположении, содержащуюся в теле сообщения запроса INVITE, одновременно защищая ее от других прокси на пути запроса. Объект местоположения также должен быть проверен на целостность данных прокси перед применением маршрутизации на основе местоположения. Иногда UAC хотят отправить объект местоположения на UAS. Это еще один хороший пример, показывающий необходимость того, чтобы UAC одновременно отправляли защищенные данные на прокси и на UAS.
2.2.3. User Authentication
2.2.3. Аутентификация пользователя
2.2.3.1. User Authentication Using the AIBs
2.2.3.1. Аутентификация пользователя с использованием AIB
The Authenticated Identity Bodies (AIBs) [7] is a digitally-signed data that is used for identifying users. Proxy servers that need to authenticate a user, verify the signature. When the originator needs anonymity, the user identity in the AIB is encrypted before being signed. Proxy servers that authenticate the user need to decrypt the body in order to view the user identity in the AIB. Such proxy servers can be located adjacently and/or non-adjacently to the UA.
Органы аутентификации (AIB) [7] представляют собой данные с цифровой подписью, которые используются для идентификации пользователей. Прокси, которым необходимо аутентифицировать пользователя, проверяют подпись. Когда отправителю необходима анонимность, личность пользователя в AIB шифруется перед подписанием. Прокси, которые аутентифицируют пользователя, необходимо расшифровать тело, чтобы просмотреть личность пользователя в AIB. Такие прокси могут быть расположены смежно и/или несмежно с UA.
The AIB could be included in all request/response messages. The proxy server needs to view it in request messages in order to authenticate users. Another proxy server sometimes needs to view it in response messages for user authentication.
AIB может быть включен во все сообщения запроса/ответа. Прокси необходимо просмотреть его в сообщениях запроса для аутентификации пользователей. Другому прокси иногда необходимо просмотреть его в ответных сообщениях для аутентификации пользователя.
2.2.3.2. User Authentication in HTTP Digest Authentication
2.2.3.2. Аутентификация пользователя при дайджест-аутентификации HTTP
User authentication data for HTTP Digest authentication [8] includes potentially private information, such as a user name. The user authentication data can be set only in a SIP header of request messages. This information needs to be transmitted securely to servers that authenticate users, located either adjacently and/or non-adjacently to the UA.
Данные аутентификации пользователя для аутентификации HTTP Digest [8] включают потенциально конфиденциальную информацию, такую ​​как имя пользователя. Данные аутентификации пользователя могут быть установлены только в заголовке SIP сообщений запроса. Эту информацию необходимо безопасно передавать на серверы, которые аутентифицируют пользователей, расположенные рядом и/или несмежно с UA.
2.2.4. Media-related Services
2.2.4. Media-related Услуги
Firewall traversal is an example of services based on media information in a message body, such as the Session Description Protocol (SDP) [9]. A firewall entity that supports the SIP protocol, or a midcom [10] agent co-located with a proxy server, controls a firewall based on the address and port information of media streams in the SDP offer/answer. The address and port information in the SDP needs to be transmitted securely to recipient UAs and the proxy server operating as a midcom agent. Therefore, there is a need for a proxy server to be able to decrypt the SDP, as well as to verify the integrity of the SDP.
Обход брандмауэра является примером услуг, основанных на медиа-информации в теле сообщения, таких как протокол описания сессии (SDP) [9]. Объект брандмауэра, который поддерживает протокол SIP, или агент Midcom [10], расположенный рядом с прокси, управляет брандмауэром на основе информации об адресе и порте медиапотоков в предложении/ответе SDP. Информация об адресе и порте в SDP должна быть безопасно передана UA-получателям и прокси, работающему в качестве промежуточного агента. Следовательно, существует необходимость в прокси, который сможет расшифровывать SDP, а также проверять целостность SDP.
When the SDP includes key parameters for Secure RTP (SRTP) [11], the key parameters need to be encrypted only for end-to-end confidentiality.
Когда SDP включает ключевые параметры для безопасного RTP (SRTP) [11], ключевые параметры необходимо шифровать только для обеспечения сквозной конфиденциальности.
3. Scope of End-to-Middle Security
3. Объем безопасности End-to-Middle
End-to-middle security consists of user authentication, data integrity, and data confidentiality. Providing data integrity requires authenticating peer who creates the data. However, this document only describes requirements for data confidentiality and data integrity, since end-to-middle authentication is covered by existing mechanisms such as HTTP Digest authentication, S/MIME Cryptographic Message Syntax (CMS) SignedData body [12], or an AIB.
End-to-middle безопасность состоит из аутентификации пользователя, целостности данных и конфиденциальности данных. Обеспечение целостности данных требует аутентификации узла, создающего данные. Однако в этом документе описаны только требования к конфиденциальности и целостности данных, поскольку сквозная аутентификация обеспечивается существующими механизмами, такими как дайджест-аутентификация HTTP, тело SignedData синтаксиса криптографических сообщений S/MIME (CMS) [12] или AIB.
As for data integrity, the CMS SignedData body can be used for verification of the data integrity and authentication of the signer by any entities. The CMS SignedData body can be used for end-to- middle security and end-to-end security simultaneously. However, a proxy server generally does not verify the data integrity using the CMS SignedData body, and there is no way for a UA to request the proxy server to verify the message. Therefore, some new mechanisms are needed to achieve data integrity for end-to-middle security.
Что касается целостности данных, тело CMS SignedData может использоваться для проверки целостности данных и аутентификации подписывающего лица любыми объектами. Тело CMS SignedData можно использовать для обеспечения сквозной и сквозной безопасности одновременно. Однако прокси обычно не проверяет целостность данных с помощью тела CMS SignedData, и у UA нет возможности запросить прокси для проверки сообщения. Поэтому необходимы некоторые новые механизмы для достижения целостности данных и обеспечения сквозной безопасности.
This document mainly discusses requirements for data confidentiality and the integrity of end-to-middle security.
В этом документе в основном обсуждаются требования к конфиденциальности данных и целостности сквозной безопасности.
4. Requirements for a Solution
4. Требования к решению
We describe here requirements for a solution. The requirements are mainly applied during the phase of a dialog creation or sending a MESSAGE request.
Здесь мы описываем требования к решению. Требования в основном применяются на этапе создания диалога или отправки запроса MESSAGE.
4.1. General Requirements
4.1. Общие требования
The following are general requirements for end-to-middle confidentiality and integrity.
Ниже приведены общие требования к сквозной конфиденциальности и целостности.
REQ-GEN-1: The solution SHOULD have little impact on the way a UA handles S/MIME-secured messages.
REQ-GEN-1: решение СЛЕДУЕТ оказывать небольшое влияние на то, как UA обрабатывает сообщения S/MIME-secured.
REQ-GEN-2: It SHOULD NOT have an impact on proxy servers that do not provide services based on S/MIME-secured bodies in terms of handling the existing SIP headers.
REQ-GEN-2: НЕ ДОЛЖНО влиять на прокси, которые не предоставляют услуги на основе тел S/MIME-secured с точки зрения обработки существующих заголовков SIP.
REQ-GEN-3: It SHOULD NOT violate the standardized mechanism of proxy servers in terms of handling message bodies.
REQ-GEN-3: НЕ ДОЛЖНО нарушать стандартизированный механизм прокси с точки зрения обработки тел сообщений.
REQ-GEN-4: It SHOULD allow a UA to discover security policies of proxy servers. Security policies imply what data is needed to disclose and/or verify in a message. This requirement is necessary when the UA does not know statically which proxy servers or domains need disclosing data and/or verification.
REQ-GEN-4: СЛЕДУЕТ позволять UA обнаруживать политики безопасности прокси. Политики безопасности подразумевают, какие данные необходимо раскрывать и/или проверять в сообщении. Это требование необходимо, когда UA не знает статически, какие прокси или домены нуждаются в раскрытии данных и/или проверке.
4.2. Requirements for End-to-Middle Confidentiality
4.2. Требования к End-to-Middle конфиденциальности
REQ-CONF-1: The solution MUST allow encrypted data to be shared with the recipient UA and a proxy server, when a UA wants.
REQ-CONF-1: решение ДОЛЖНО разрешать передачу зашифрованных данных UA-получателю и прокси, когда UA этого захочет.
REQ-CONF-2: It MUST NOT violate end-to-end encryption when the encrypted data does not need to be shared with any proxy servers.
REQ-CONF-2: НЕ ДОЛЖНО нарушаться сквозное шифрование, если зашифрованные данные не нужно передавать каким-либо прокси.
REQ-CONF-3: It SHOULD allow a UA to request a proxy server to view specific message bodies. The request itself SHOULD be secure; namely it SHOULD be authenticated for the UA and verified for the data integrity.
REQ-CONF-3: СЛЕДУЕТ разрешить UA запрашивать прокси для просмотра определенных тел сообщений. Сам запрос ДОЛЖЕН быть безопасным; а именно, он ДОЛЖЕН быть аутентифицирован для UA и проверен на целостность данных.
REQ-CONF-4: It MAY allow a UA to request that the recipient UA disclose information to the proxy server to which the requesting UA is initially disclosing information. The request itself SHOULD be secure; namely it SHOULD be authenticated for the UA and verified for the data integrity. This requirement is necessary when a provider operating the proxy server allows its security policies to be revealed to the provider serving the recipient UA.
REQ-CONF-4: МОЖЕТ позволить UA запрашивать, чтобы UA-получатель раскрывал информацию прокси, которому запрашивающий UA первоначально раскрывает информацию. Сам запрос ДОЛЖЕН быть безопасным; а именно, он ДОЛЖЕН быть аутентифицирован для UA и проверен на целостность данных. Это требование необходимо, когда провайдер, управляющий прокси, позволяет раскрыть свою политику безопасности провайдеру, обслуживающему UA-получателя.
4.3. Requirements for End-to-Middle Integrity
4.3. Требования к целостности End-to-Middle
This section enumerates the requirements for the end-to-middle integrity. Verifying the data integrity requires checking that the data is created by the authenticated user and not forged by a malicious user. Therefore, verification of the data integrity requires the user authentication. REQ-INT-1: The solution SHOULD work even when the SIP end-to-end authentication and integrity services are enabled.
В этом разделе перечислены требования к сквозной целостности. Проверка целостности данных требует проверки того, что данные созданы пользователем, прошедшим проверку подлинности, а не подделаны пользователем-злоумышленником. Поэтому проверка целостности данных требует аутентификации пользователя. REQ-INT-1: Решение ДОЛЖНО работать, даже если включены службы сквозной аутентификации и целостности SIP.
REQ-INT-2: It SHOULD allow a UA to request a proxy server to verify specific message bodies and authenticate the user. The request itself SHOULD be secure; namely it SHOULD be authenticated for the UA and verified for the data integrity.
REQ-INT-2: СЛЕДУЕТ разрешить UA запрашивать прокси для проверки определенных тел сообщений и аутентификации пользователя. Сам запрос ДОЛЖЕН быть безопасным; а именно, он ДОЛЖЕН быть аутентифицирован для UA и проверен на целостность данных.
REQ-INT-3: It SHOULD allow a UA to request the recipient UA to send the verification data of the same information that the requesting UA is providing to the proxy server. The request itself SHOULD be secure; namely it SHOULD be authenticated for the UA and verified for the data integrity. This requirement is necessary when a provider operating the proxy server allows its security policies to be revealed to the provider serving the recipient UA.
REQ-INT-3: СЛЕДУЕТ разрешить UA запрашивать UA-получателя отправить данные проверки той же информации, которую запрашивающий UA предоставляет прокси. Сам запрос ДОЛЖЕН быть безопасным; а именно, он ДОЛЖЕН быть аутентифицирован для UA и проверен на целостность данных. Это требование необходимо, когда провайдер, управляющий прокси, позволяет раскрыть свою политику безопасности провайдеру, обслуживающему UA-получателя.
5. Security Considerations
5. Вопросы безопасности
This document describes the requirements for confidentiality and integrity between a UA and a proxy server. Although this document does not cover any requirements for authentication, verifying the data integrity requires peer authentication. Also, peer authentication is important in order to prevent attacks from malicious users and servers.
В этом документе описаны требования к конфиденциальности и целостности между UA и прокси. Хотя этот документ не охватывает никаких требований к аутентификации, проверка целостности данных требует одноранговой аутентификации. Кроме того, одноранговая аутентификация важна для предотвращения атак со стороны злоумышленников и серверов.
The end-to-middle security requires additional processing on message bodies, such as unpacking MIME structure, data decryption, and/or signature verification to proxy servers. Therefore, the proxy servers that enable end-to-middle security are vulnerable to a Denial-of-Services attack. A threat model is where a malicious user sends many complicated-MIME-structure messages to a proxy server, containing user authentication data obtained by eavesdropping. Another threat model is where a malicious proxy server sends many complicated-MIME-structure messages to a proxy server, containing the source IP address and the Via header of an adjacent proxy server. These attacks will slow down the overall performance of target proxy servers.
Комплексная безопасность требует дополнительной обработки тела сообщения, такой как распаковка структуры MIME, расшифровка данных и/или проверка подписи на прокси. Таким образом, прокси, обеспечивающие сквозную безопасность, уязвимы для атаки Denial-of-Services. Модель угрозы заключается в том, что злонамеренный пользователь отправляет на прокси множество сложных MIME-structure сообщений, содержащих данные аутентификации пользователя, полученные путем подслушивания. Другая модель угрозы заключается в том, что вредоносный прокси отправляет на прокси множество сложных сообщений-MIME-structure, содержащих исходный IP-адрес и заголовок Via соседнего прокси. Эти атаки замедлят общую производительность целевых прокси.
To prevent these attacks, user and server authentication mechanisms need to be protected against replay attacks, or the user and server authentication always need to be executed simultaneously with protection of data integrity. In order to prevent these attacks, the following requirements should be met. o The solution MUST support mutual authentication, data confidentiality, and data integrity protection between a UA and a proxy server.
Чтобы предотвратить эти атаки, механизмы аутентификации пользователей и серверов должны быть защищены от атак повторного воспроизведения, или аутентификация пользователя и сервера всегда должна выполняться одновременно с защитой целостности данных. Чтобы предотвратить эти атаки, необходимо соблюдать следующие требования. o Решение ДОЛЖНО поддерживать взаимную аутентификацию, конфиденциальность данных и защиту целостности данных между UA и прокси.
o It SHOULD support protection against a replay attack for user authentication.
o Ему СЛЕДУЕТ поддерживать защиту от атаки воспроизведения для аутентификации пользователя.
o It SHOULD simultaneously support user authentication and data integrity protection. These last two requirements are met by HTTP Digest authentication.
o Он ДОЛЖЕН одновременно поддерживать аутентификацию пользователей и защиту целостности данных. Этим последним двум требованиям отвечает аутентификация HTTP Digest.
o It MUST support mutual authentication, data confidentiality, and data integrity protection between proxy servers.
o Он ДОЛЖЕН поддерживать взаимную аутентификацию, конфиденциальность данных и защиту целостности данных между прокси.
o It SHOULD support protection against a replay attack for server authentication.
o Ему СЛЕДУЕТ поддерживать защиту от атаки повторного воспроизведения для аутентификации сервера.
o It SHOULD simultaneously support server authentication and data integrity protection. These last three requirements are met by TLS.
o Он ДОЛЖЕН одновременно поддерживать аутентификацию сервера и защиту целостности данных. Этим последним трем требованиям отвечает TLS.
