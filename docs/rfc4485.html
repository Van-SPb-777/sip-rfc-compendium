Abstract
Аннотация
The Session Initiation Protocol (SIP) is a flexible yet simple tool for establishing interactive communications sessions across the Internet. Part of this flexibility is the ease with which it can be extended. In order to facilitate effective and interoperable extensions to SIP, some guidelines need to be followed when developing SIP extensions. This document outlines a set of such guidelines for authors of SIP extensions.
Протокол инициирования сессий (SIP) — это гибкий, но простой инструмент для установления сессий интерактивной связи через Интернет. Частью этой гибкости является легкость, с которой ее можно расширить. Чтобы обеспечить эффективные и совместимые расширения SIP, при разработке расширений SIP необходимо следовать некоторым рекомендациям. В этом документе изложен набор таких рекомендаций для авторов расширений SIP.

1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [2] is a flexible yet simple tool for establishing interactive communications sessions across the Internet. Part of this flexibility is the ease with which it can be extended (with new methods, new header fields, new body types, and new parameters), and there have been countless proposals that have been made to do just that. An IETF process has been put into place that defines how extensions are to be made to the SIP protocol [10]. That process is designed to ensure that extensions are made that are appropriate for SIP (as opposed to being done in some other protocol), that these extensions fit within the model and framework provided by SIP and are consistent with its operation, and that these extensions solve problems generically rather than for a specific use case. However, [10] does not provide the technical guidelines needed to assist that process. This specification helps to meet that need.
Протокол инициирования сессий (SIP) [2] представляет собой гибкий, но простой инструмент для установления сессий интерактивной связи через Интернет. Частью этой гибкости является простота, с которой ее можно расширить (с помощью новых методов, новых полей заголовков, новых типов тела и новых параметров), и было сделано бесчисленное множество предложений, направленных именно на это. Был введен в действие процесс IETF, который определяет, как следует вносить расширения в протокол SIP [10]. Этот процесс предназначен для обеспечения того, чтобы были созданы расширения, подходящие для SIP (а не для какого-либо другого протокола), чтобы эти расширения вписывались в модель и структуру, предоставляемые SIP, и соответствовали его работе, а также чтобы эти расширения решали проблемы в целом, а не для конкретного варианта использования. Однако [10] не содержит технических рекомендаций, необходимых для содействия этому процессу. Данная спецификация помогает удовлетворить эту потребность.
This specification first provides a set of guidelines to help decide whether a certain piece of functionality is appropriately done in SIP. Assuming the functionality is appropriate, it then points out issues that extensions should deal with from within their specification. Finally, it discusses common interactions with existing SIP features that often cause difficulties in extensions.
Эта спецификация сначала предоставляет набор рекомендаций, которые помогут решить, правильно ли реализована определенная часть функциональности в SIP. Предполагая, что функциональность соответствует требованиям, затем указываются проблемы, которые расширения должны решать в рамках своей спецификации. Наконец, обсуждаются общие взаимодействия с существующими функциями SIP, которые часто вызывают трудности при расширениях.

3. Should I Define a SIP Extension?
3. Должен ли я определить расширение SIP?
The first question to be addressed when defining a SIP extension is whether a SIP extension is the best solution to the problem. SIP has been proposed as a solution for numerous problems, including mobility, configuration and management, QoS control, call control, caller preferences, device control, third-party call control, and MPLS path setup, to name a few. Clearly, not every problem can be solved by a SIP extension. More importantly, some problems that could be solved by a SIP extension probably shouldn't.
Первый вопрос, который необходимо решить при определении расширения SIP, заключается в том, является ли расширение SIP лучшим решением проблемы. SIP был предложен в качестве решения многочисленных проблем, включая мобильность, настройку и управление, контроль QoS, контроль вызовов, предпочтения вызывающих абонентов, контроль устройств, контроль сторонних вызовов и настройку пути MPLS, и это лишь некоторые из них. Очевидно, что не каждую проблему можно решить с помощью расширения SIP. Что еще более важно, некоторые проблемы, которые можно решить с помощью SIP-расширения, вероятно, не будут решены.
To assist engineers in determining whether a SIP extension is an appropriate solution to their problem, we present two broad criteria. First, the problem SHOULD fit into the general purview of SIP's solution space. Secondly, the solution MUST conform to the general SIP architectural model.
Чтобы помочь инженерам определить, является ли расширение SIP подходящим решением их проблемы, мы представляем два общих критерия. Во-первых, проблема ДОЛЖНА вписываться в общий круг решений SIP. Во-вторых, решение ДОЛЖНО соответствовать общей архитектурной модели SIP.
Although the first criteria might seem obvious, we have observed that numerous extensions to SIP have been proposed because some function is needed in a device that also speaks SIP. The argument is generally given that "I'd rather implement one protocol than many". As an example, user agents, like all other IP hosts, need some way to obtain their IP address. This is generally done through DHCP [11]. SIP's multicast registration mechanisms might supply an alternate way to obtain an IP address. This would eliminate the need for DHCP in clients. However, we do not believe such extensions are appropriate. We believe that protocols should be defined to provide specific, narrow functions, rather than be defined for all protocols needed between a pair of devices. The former approach to protocol design yields modular protocols with broad application. It also facilitates extensibility and growth; single protocols can be removed and changed without affecting the entire system. We observe that this approach to protocol engineering mirrors object-oriented software engineering.
Хотя первый критерий может показаться очевидным, мы заметили, что были предложены многочисленные расширения SIP, поскольку в устройстве, которое также поддерживает SIP, необходимы некоторые функции. Обычно это делается через DHCP [11]. Механизмы многоадресной регистрации SIP могут предоставить альтернативный способ получения IP-адреса. Это устранит необходимость в DHCP для клиентов. Однако мы не считаем, что такие расширения уместны. Мы считаем, что протоколы должны быть определены для обеспечения конкретных, узких функций, а не для всех необходимых протоколов. между парой устройств. Первый подход к разработке протоколов обеспечивает модульные протоколы с широким применением. Он также способствует расширению и расширению; отдельные протоколы могут быть удалены и изменены, не затрагивая всю систему. Мы видим, что этот подход к разработке протоколов отражает объектно-ориентированную разработку программного обеспечения.
Our second criteria, that the extension must conform to the general SIP architectural model, ensures that the protocol remains manageable and broadly applicable.
Наш второй критерий — соответствие расширения общей архитектурной модели SIP — гарантирует, что протокол останется управляемым и широко применимым.
3.1. SIP's Solution Space
3.1. Пространство решений SIP
In order to evaluate the first criteria, it is necessary to define exactly what SIP's solution space is, and what it is not.
Чтобы оценить первый критерий, необходимо точно определить, что такое пространство решений SIP, а что нет.
SIP is a protocol for initiating, modifying, and terminating interactive sessions. This process involves the discovery of users, (or, more generally, entities that can be communicated with, including services, such as voicemail or translation devices) wherever they may be located, so that a description of the session can be delivered to the user. It is assumed that these users or communications entities are mobile, and that their point of attachment to the network changes over time. The primary purpose of SIP is a rendezvous function, to allow a request initiator to deliver a message to a recipient wherever they may be. Such a rendezvous is needed to establish a session, but it can be used for other purposes related to communications, such as querying for capabilities or delivery of an instant message.
SIP — это протокол для инициирования, изменения и завершения интерактивных сессий. Этот процесс включает в себя обнаружение пользователей (или, в более общем плане, объектов, с которыми можно взаимодействовать, включая такие службы, как голосовая почта или устройства перевода), где бы они ни находились, чтобы описание сессии могло быть доставлено пользователю. Предполагается, что эти пользователи или объекты связи являются мобильными и что их точка подключения к сети со временем меняется. Основная цель SIP — функция рандеву, позволяющая инициатору запроса доставить сообщение получателю, где бы он ни находился. Такое рандеву необходимо для установления сессии, но его можно использовать и для других целей, связанных со связью, таких как запрос возможностей или доставка мгновенного сообщения.
Much of SIP focuses on this discovery and rendezvous component. Its ability to fork, its registration capabilities, and its routing capabilities are all present for the singular purpose of finding the desired user wherever they may be. As such, features and capabilities such as personal mobility, automatic call distribution, and follow-me are well within the SIP solution space.
Большая часть SIP фокусируется на этом компоненте обнаружения и встречи. Его способность разветвляться, его возможности регистрации и возможности маршрутизации — все это предназначено для единственной цели — найти нужного пользователя, где бы он ни находился. Таким образом, такие функции и возможности, как личная мобильность, автоматическое распределение вызовов и функция «следуй за мной», вполне вписываются в пространство SIP-решений.
Session initiation also depends on the ability of the called party to have enough information about the session itself to make a decision on whether to join. That information includes data about the caller, the purpose for the invitation, and parameters of the session itself. For this reason, SIP includes this kind of information.
Инициирование сессии также зависит от способности вызываемой стороны иметь достаточно информации о самом сессии, чтобы принять решение о присоединении. Эта информация включает в себя данные о вызывающем абоненте, цели приглашения и параметрах самого сессии. По этой причине SIP включает в себя такую ​​информацию.
Part of the process of session initiation is the communication of progress and the final results of establishment of the session. SIP provides this information as well.
Частью процесса инициирования сессий является сообщение о ходе и окончательных результатах установления сессии. SIP также предоставляет эту информацию.
SIP itself is independent of the session, and the session description is delivered as an opaque body within SIP messages. Keeping SIP independent of the sessions it initiates and terminates is fundamental. As such, there are many functions that SIP explicitly does not provide. It is not a session management protocol or a conference control protocol. The particulars of the communications within the session are outside of SIP. This includes features such as media transport, voting and polling, virtual microphone passing, chairman election, floor control, and feedback on session quality.
Сам SIP не зависит от сессии, а описание сессии доставляется в виде непрозрачного тела в сообщениях SIP. Сохранение независимости SIP от сессий, которые он инициирует и завершает, имеет фундаментальное значение. Таким образом, существует множество функций, которые SIP явно не предоставляет. Это не протокол управления сессией или протокол управления конференцией. Детали связи внутри сессии находятся за пределами SIP. Сюда входят такие функции, как транспортировка мультимедиа, голосование и опросы, передача виртуального микрофона, выборы председателя, контроль за аудиторией и обратная связь по качеству сессии.
SIP is not a resource reservation protocol for sessions. This is fundamentally because (1) SIP is independent of the underlying session it establishes, and (2) the path of SIP messages is completely independent from the path that session packets may take. The path independence refers to paths within a provider's network and the set of providers itself. For example, it is perfectly reasonable for a SIP message to traverse a completely different set of autonomous systems than the audio in a session SIP establishes.
SIP не является протоколом резервирования ресурсов для сессий. Это принципиально потому, что (1) SIP не зависит от базового сессии, который он устанавливает, и (2) путь сообщений SIP полностью независим от пути, по которому могут идти пакеты сессии. Независимость путей относится к путям внутри сети провайдера и самому набору провайдеров. Например, совершенно разумно, чтобы сообщение SIP проходило через совершенно другой набор автономных систем, чем аудио в сессии SIP.
SIP is not a general purpose transfer protocol. It is not meant to send large amounts of data unrelated to SIP's operation. It is not meant as a replacement for HTTP. This is not to say that carrying payloads in SIP messages is never a good thing; in many cases, the data is very much related to SIP's operation. In those cases, congestion-controlled transports end-to-end are critical.
SIP не является протоколом передачи общего назначения. Он не предназначен для отправки больших объемов данных, не связанных с работой SIP. Он не предназначен для замены HTTP. Это не значит, что передача полезных данных в SIP-сообщениях никогда не будет хорошей вещью; во многих случаях данные во многом связаны с работой SIP. В таких случаях решающее значение имеет сквозная транспортировка с контролем перегрузок.
SIP is not meant to be a general Remote Procedure Call (RPC) mechanism. None of its user discovery and registration capabilities are needed for RPC, and neither are most of its proxy functions.
SIP не предназначен для использования в качестве общего механизма удаленного вызова процедур (RPC). Ни одна из возможностей обнаружения и регистрации пользователей не требуется для RPC, как и большинство его прокси-функций.
SIP is not meant to be used as a strict Public Switched Telephone Network (PSTN) signaling replacement. It is not a superset of the Integrated Services Digital Network (ISDN) User Part (ISUP). Although it can support gatewaying of PSTN signaling and can provide many features present in the PSTN, the mere existence of a feature or capability in the PSTN is not a justification for its inclusion in SIP. Extensions needed to support telephony MUST meet the other criteria described here.
SIP не предназначен для использования в качестве строгой замены сигнализации телефонной сети общего пользования (PSTN). Это не расширенная версия пользовательской части цифровой сети с интеграцией служб (ISDN) (ISUP). Хотя он может поддерживать шлюзование сигнализации PSTN и может предоставлять множество функций, присутствующих в PSTN, само существование функции или возможности в PSTN не является оправданием для ее включения в SIP. Расширения, необходимые для поддержки телефонии, ДОЛЖНЫ соответствовать другим критериям, описанным здесь.
SIP is a poor control protocol. It is not meant to be used for one entity to tell another to pick up or answer a phone, to send audio using a particular codec, or to provide a new value for a configuration parameter. Control protocols have different trust relationships from that assumed in SIP and are more centralized in architecture than SIP is, as SIP is a very distributed protocol.
SIP — плохой протокол управления. Он не предназначен для использования одним объектом для указания другому взять трубку или ответить на вызов, отправить аудио с использованием определенного кодека или предоставить новое значение для параметра конфигурации. Протоколы управления имеют отношения доверия, отличные от предполагаемых в SIP, и более централизованы по архитектуре, чем SIP, поскольку SIP является очень распределенным протоколом.
There are many network layer services needed to make SIP function. These include quality of service, mobility, and security, among others. Rather than build these capabilities into SIP itself, they SHOULD be developed outside of SIP and then used by it. Specifically, any protocol mechanisms that are needed by SIP, but that are also needed by many other application layer protocols SHOULD NOT be addressed within SIP.
Для работы SIP необходимо множество сервисов сетевого уровня. К ним относятся, среди прочего, качество обслуживания, мобильность и безопасность. Вместо того, чтобы встраивать эти возможности в сам SIP, их СЛЕДУЕТ разрабатывать вне SIP и затем использовать им. В частности, любые механизмы протокола, необходимые для SIP, а также для многих других протоколов прикладного уровня, НЕ ДОЛЖНЫ рассматриваться в SIP.
3.2. SIP Architectural Model
3.2. Архитектурная модель SIP
We describe here some of the primary architectural assumptions that underlie SIP. Extensions that violate these assumptions should be examined more carefully to determine their appropriateness for SIP. Session independence: SIP is independent of the session it establishes. This includes the type of session, be it audio, video, game, chat session, or virtual reality. SIP operation SHOULD NOT depend on some characteristic of the session. SIP is not specific to voice only. Any extensions to SIP MUST consider the application of SIP to a variety of different session types.
Здесь мы описываем некоторые основные архитектурные предположения, лежащие в основе SIP. Расширения, нарушающие эти предположения, следует проверять более тщательно, чтобы определить их пригодность для SIP. Независимость от сессии: SIP не зависит от сессии, который он устанавливает. Сюда входит тип сессии: аудио, видео, игра, сессия чата или виртуальная реальность. Работа SIP НЕ ДОЛЖНА зависеть от некоторых характеристик сессии. SIP не предназначен только для голосовой связи. Любые расширения SIP ДОЛЖНЫ учитывать применение SIP к различным типам сессий.
SIP and Session path independence: We have already touched on this once, but it is worth noting again. The set of routers, networks, and/or autonomous systems traversed by SIP messages are unrelated to the set of routers, networks, and/or autonomous systems traversed by session packets. They may be the same in some cases, but it is fundamental to SIP's architecture that they need not be the same. Standards-track extensions MUST NOT be defined that work only when the signaling and session paths are coupled. Non- standard P-header extensions [10] are required for any extension that only works in such a case.
Независимость от SIP и пути сессии. Мы уже однажды касались этого вопроса, но стоит отметить это еще раз. Набор маршрутизаторов, сетей и/или автономных систем, через которые проходят сообщения SIP, не связан с набором маршрутизаторов, сетей и/или автономных систем, через которые проходят сеансовые пакеты. В некоторых случаях они могут быть одинаковыми, но для архитектуры SIP принципиально важно, чтобы они не были одинаковыми. Расширения Standards-track НЕ ДОЛЖНЫ определяться, которые работают только тогда, когда пути сигнализации и сессии связаны. Нестандартные расширения P-header [10] требуются для любого расширения, которое работает только в таком случае.
Multi-provider and multi-hop: SIP assumes that its messages will traverse the Internet. That is, SIP works through multiple networks administered by different providers. It is also assumed that SIP messages traverse many hops (where each hop is a proxy). Extensions MUST NOT work only under the assumption of a single hop or specialized network topology. They SHOULD avoid the assumption of a single SIP provider (but see the use of P-Headers, per RFC 3427 [10]).
Multi-provider и многопереходный режим: SIP предполагает, что его сообщения будут проходить через Интернет. То есть SIP работает через несколько сетей, администрируемых разными провайдерами. Также предполагается, что сообщения SIP проходят через множество переходов (где каждый переход является прокси). Расширения НЕ ДОЛЖНЫ работать только в предположении, что существует однопереходная или специализированная топология сети. Им СЛЕДУЕТ избегать предположения об одном SIP-провайдере (но см. использование P-Headers, согласно RFC 3427 [10]).
Transactional: SIP is a request/response protocol, possibly enhanced with intermediate responses. Many of the rules of operation in SIP are based on general processing of requests and responses. 4.1. Backward Compatibility
4.1. Обратная совместимость
One of the most important issues to consider is whether the new extension is backward compatible with baseline SIP. This is tightly coupled with how the Require, Proxy-Require, and Supported header fields are used.
Одним из наиболее важных вопросов, которые следует учитывать, является наличие обратной совместимости нового расширения с базовым SIP. Это тесно связано с использованием полей заголовков Require, Proxy-Require и Supported.

o The Proxy-Require header field SHOULD be avoided at all costs. The failure likelihood in an individual proxy stays constant, but the path failure grows exponentially with the number of hops. On the other hand, the Require header field only mandates that a single entity, the UAS, support the extension. С другой стороны, поле заголовка Require требует, чтобы расширение поддерживал только один объект, БПЛА. Таким образом, использование Proxy-Require считается экспоненциально худшим, чем использование поля заголовка Require.

o Если расширение использует либо Require, либо Proxy-Require, расширение ДОЛЖНО обсудить, как вернуться к базовой работе SIP, если запрос отклонен с ответом 420.
Extensions that define new methods do not need to use the Require header field. SIP defines mechanisms that allow a UAC to know whether a new method is understood by a UAS. This includes both the OPTIONS request and the 405 (Method Not Allowed) response with the Allow header field. It is fundamental to SIP that proxies need not understand the semantics of a new method in order to process it. If an extension defines a new method that must be understood by proxies in order to be processed, a Proxy-Require header field is needed. As discussed above, these kinds of extensions are frowned upon.
Расширениям, определяющим новые методы, не требуется использовать поле заголовка Require. SIP определяет механизмы, которые позволяют UAC узнать, понятен ли UAS новый метод. Сюда входят как запрос OPTIONS, так и ответ 405 (Метод не разрешен) с полем заголовка Allow. Для SIP принципиально важно, чтобы прокси не нужно было понимать семантику нового метода для его обработки. Если расширение определяет новый метод, который должен быть понят прокси для его обработки, необходимо поле заголовка Proxy-Require. Как обсуждалось выше, такого рода расширения не одобряются.
In order to achieve backwards compatibility for extensions that define new methods, the Allow header field is used. There are two types of new methods - those that are used for established dialogs (initiated by INVITE, for example), and those that are sent as the initial request to a UA. Since INVITE and its response both SHOULD contain an Allow header field, a UA can readily determine whether the new method can be supported within the dialog. For example, once an INVITE dialog is established, a user agent could determine whether the REFER method [12] is supported if it is present in an Allow header field. If it wasn't, the "transfer" button on the UI could be "greyed out" once the call is established.
Для достижения обратной совместимости расширений, определяющих новые методы, используется поле заголовка Allow. Существует два типа новых методов — те, которые используются для установленных диалогов (инициированных, например, INVITE), и те, которые отправляются в качестве первоначального запроса к UA. Поскольку INVITE и его ответ ДОЛЖНЫ содержать поле заголовка Allow, UA может легко определить, может ли новый метод поддерживаться в диалоге. Например, как только диалог INVITE установлен, пользовательский агент может определить, поддерживается ли метод REFER [12], если он присутствует в поле заголовка Allow. В противном случае кнопка «transfer» в пользовательском интерфейсе могла бы стать «серой» после установления вызова.
Another type of extension is that which requires a proxy to insert header fields or header field parameters into a request as it traverses the network, or for the UAS to insert header fields or header field parameters into a response. For some extensions, if the UAC or UAS does not understand these header fields, the message can still be processed correctly. These extensions are completely backwards compatible.
Другим типом расширения является то, которое требует, чтобы прокси вставлял поля заголовка или параметры полей заголовка в запрос при его прохождении по сети, или чтобы UAS вставлял поля заголовка или параметры полей заголовка в ответ. Для некоторых расширений, если UAC или UAS не понимают эти поля заголовка, сообщение все равно может быть обработано правильно. Эти расширения полностью обратно совместимы.
Most other extensions of this type require that the server only insert the header field or parameter if it is sure the client understands it. In this case, these extensions will need to make use of the Supported request header field mechanism. This mechanism allows a server to determine if the client can understand some extension, so that it can apply the extension to the response. By their nature, these extensions may not always be able to be applied to every response.
Большинство других расширений этого типа требуют, чтобы сервер вставлял поле заголовка или параметр только в том случае, если он уверен, что клиент его понимает. В этом случае эти расширения должны будут использовать механизм поля заголовка поддерживаемого запроса. Этот механизм позволяет серверу определить, может ли клиент понять какое-либо расширение, чтобы он мог применить расширение к ответу. По своей природе эти расширения не всегда можно применить к каждому ответу.
If an extension requires a proxy to insert a header field or parameter into a request and this header field or parameter needs to be understood by both UAC and UAS to be executed correctly, a combination of the Require and the Supported mechanism will need to be used. The proxy can insert a Require header field into the request if the Supported header field is present. An example of such an extension is the SIP Session Timer [13].
Если расширение требует, чтобы прокси вставил поле или параметр заголовка в запрос, и это поле или параметр заголовка должны быть поняты как UAC, так и UAS, чтобы правильно выполняться, необходимо использовать комбинацию механизма Require и Supported. Прокси может вставить поле заголовка Require в запрос, если поле заголовка Supported присутствует. Примером такого расширения является таймер сессии SIP [13].
Yet another type of extension is that which defines new body types to be carried in SIP messages. According to the SIP specification, bodies must be understood by user agents in order to process a request. As such, the interoperability issues are similar to new methods. However, the Content-Disposition header field has been defined to allow a client or server to indicate that the message body is optional [2]. Extensions that define or require new body types SHOULD make them optional for the user agent to process.
Еще одним типом расширения является то, которое определяет новые типы тела, которые будут передаваться в сообщениях SIP. Согласно спецификации SIP, для обработки запроса пользовательские агенты должны понимать тела. Таким образом, проблемы совместимости аналогичны новым методам. Однако поле заголовка Content-Disposition было определено, чтобы позволить клиенту или серверу указать, что тело сообщения является необязательным [2]. Расширения, которые определяют или требуют новых типов тела, ДОЛЖНЫ сделать их необязательными для обработки пользовательским агентом.
When a body must be understood to properly process a request or response, it is preferred that the sending entity know ahead of time whether the new body is understood by the recipient. For requests that establish a dialog, inclusion of Accept in the request and its success responses is RECOMMENDED. This will allow both parties to determine what body types are supported by their peers. Subsequent messaging between the peers would then only include body types that were indicated as being understood.
Когда тело должно быть понято для правильной обработки запроса или ответа, предпочтительно, чтобы отправляющий объект заранее знал, понятно ли новое тело получателю. Для запросов, которые устанавливают диалог, РЕКОМЕНДУЕТСЯ включение Accept в запрос и его успешные ответы. Это позволит обеим сторонам определить, какие типы телосложения поддерживаются их коллегами. Последующий обмен сообщениями между участниками будет включать только те типы телосложения, которые были указаны как понятные.
4.2. Security
4.2. Безопасность
Security is an important component of any protocol. Designers of SIP extensions need to carefully consider if additional security requirements are required over those described in RFC 3261. Frequently, authorization requirements and requirements for end-to- end integrity are the most overlooked.
Безопасность является важным компонентом любого протокола. Разработчикам расширений SIP необходимо тщательно продумать, потребуются ли дополнительные требования безопасности помимо описанных в RFC 3261. Зачастую больше всего упускают из виду требования авторизации и требования сквозной целостности.
SIP extensions MUST consider how (or if) they affect usage of the general SIP security mechanisms. Most extensions should not require any new security capabilities beyond general-purpose SIP. If they do, it is likely that the security mechanism has more general-purpose application and should be considered an extension in its own right.
Расширения SIP ДОЛЖНЫ учитывать, как (или влияют ли) они влияют на использование общих механизмов безопасности SIP. Большинству расширений не требуется каких-либо новых возможностей безопасности, помимо SIP общего назначения. Если да, то вполне вероятно, что механизм безопасности имеет более широкое применение и его следует рассматривать как самостоятельное расширение.
Overall system security requires that both the SIP signaling and the media sessions it established be secured. The media sessions normally use their own security techniques, which are quite distinct from those used by SIP itself. Extensions should take care not to conflate the two. However, specifications that define extensions that impact the media sessions in any way SHOULD consider the interactions between SIP and session security mechanisms.
Общая безопасность системы требует, чтобы как сигнализация SIP, так и установленные ею мультимедийные сессии были защищены. Медиа-сессии обычно используют свои собственные методы безопасности, которые сильно отличаются от тех, которые используются самим SIP. Расширениям следует позаботиться о том, чтобы не смешивать эти два понятия. Однако спецификации, определяющие расширения, которые каким-либо образом влияют на мультимедийные сессии, ДОЛЖНЫ учитывать взаимодействие между SIP и механизмами безопасности сессии.
4.3. Terminology
4.3. Терминология
RFC 3261 has an extensive terminology section that defines terms such as caller, callee, user agent, and header field. All SIP extensions MUST conform to this terminology. They MUST NOT define new terms that describe concepts already defined by a term in another SIP specification. If new terminology is needed, it SHOULD appear in a separate section towards the beginning of the document.
RFC 3261 имеет обширный раздел терминологии, в котором определяются такие термины, как вызывающий абонент, вызываемый абонент, пользовательский агент и поле заголовка. Все расширения SIP ДОЛЖНЫ соответствовать этой терминологии. Они НЕ ДОЛЖНЫ определять новые термины, описывающие концепции, уже определенные термином в другой спецификации SIP. Если необходима новая терминология, она ДОЛЖНА появиться в отдельном разделе в начале документа.
Careful attention must be paid to the actual usage of terminology. Many documents misuse the terms header, header field, and header field values, for example. Document authors SHOULD do a careful review of their documents for proper usage of these terms.
Особое внимание необходимо уделять фактическому использованию терминологии. Например, во многих документах неправильно используются термины «заголовок», «поле заголовка» и «значения поля заголовка». Авторам документов СЛЕДУЕТ тщательно просмотреть свои документы на предмет правильного использования этих терминов.
4.4. Syntactic Issues
4.4. Синтаксические проблемы
Extensions that define new methods SHOULD use all capitals for the method name. Method names SHOULD be shorter than 10 characters and SHOULD attempt to convey the general meaning of the request. Method names are case sensitive, and therefore, strictly speaking, they don't have to be capitalized. However, using capitalized method names keeps with a long-standing convention in SIP and many similar protocols, such as HTTP [15] and RTSP [16].
Расширениям, определяющим новые методы, СЛЕДУЕТ использовать все заглавные буквы в имени метода. Имена методов ДОЛЖНЫ быть короче 10 символов и ДОЛЖНЫ пытаться передать общий смысл запроса. Имена методов чувствительны к регистру, поэтому, строго говоря, их не обязательно писать с заглавной буквы. Однако использование имен методов с заглавной буквы соответствует давнему соглашению в SIP и многих подобных протоколах, таких как HTTP [15] и RTSP [16].
Extensions that define new header fields that are anticipated to be heavily used MAY define a compact form if those header fields are more than six characters. "Heavily used" means that the percentage of all emitted messages that contain that header field is over thirty percent. Usage of compact forms in these cases is only a MAY because there are better approaches for reducing message overhead [20]. Compact header fields MUST be a single character. When all 26 characters are exhausted, new compact forms will no longer be defined. Header field names are defined by the "token" production in RFC 3261, Section 25.1, and thus include the upper and lowercase letters, the digits 0 through 9, the HYPHEN-MINUS (-), FULL STOP (.), EXCLAMATION MARK (!), PERCENT SIGN (%), ASTERISK (*), LOW LINE (_), PLUS SIGN (+), GRAVE ACCENT (`), APOSTROPHE ('), and TILDE (~). They SHOULD be descriptive but reasonably brief. Although header field names are case insensitive, a single common capitalization SHOULD be used throughout the document. It is RECOMMENDED that each English word present in the header field name have its first letter capitalized. For example, "ThisIsANewHeader".

4.5. Semantics, Semantics, Semantics
4.5. Семантика, Семантика, Семантика
Developers of protocols often get caught up in syntax issues, without spending enough time on semantics. The semantics of a protocol are far more important. SIP extensions MUST clearly define the semantics of the extensions. Specifically, the extension MUST specify the behaviors expected of a UAC, UAS, and proxy in processing the extension. This is often best described by having separate sections for each of these three elements. Each section SHOULD step through the processing rules in temporal order of the most common messaging scenario.
Разработчики протоколов часто увлекаются проблемами синтаксиса, не уделяя достаточно времени семантике. Семантика протокола гораздо важнее. Расширения SIP ДОЛЖНЫ четко определять семантику расширений. В частности, расширение ДОЛЖНО указывать поведение, ожидаемое от UAC, UAS и прокси при обработке расширения. Часто это лучше всего описать, если для каждого из этих трех элементов имеются отдельные разделы. Каждому разделу СЛЕДУЕТ выполнять правила обработки во временном порядке наиболее распространенного сценария обмена сообщениями.
Processing rules generally specify actions to be taken (in terms of messages to be sent, variables to be stored, and rules to be followed) on receipt of messages and expiration of timers. If an action requires transmission of a message, the rule SHOULD outline requirements for insertion of header fields or other information in the message. The extension SHOULD specify procedures to be taken in exceptional conditions that are recoverable, or that require some kind of user intervention. Handling of unrecoverable errors does not require specification.
Правила обработки обычно определяют действия, которые необходимо предпринять (с точки зрения отправляемых сообщений, сохраняемых переменных и правил, которым необходимо следовать) при получении сообщений и истечении таймеров. Если действие требует передачи сообщения, правило ДОЛЖНО описывать требования для вставки полей заголовка или другой информации в сообщение. Расширению СЛЕДУЕТ указывать процедуры, которые следует выполнять в исключительных условиях, которые можно восстановить или которые требуют какого-либо вмешательства пользователя. Обработка неисправимых ошибок не требует спецификации.

4.9. Document-Naming Conventions
4.9. Document-Naming Соглашения
An important decision to be made about the extension is its title. The title MUST indicate that the document is an extension to SIP. It is RECOMMENDED that the title follow the basic form of "A [summary of function] for the Session Initiation Protocol (SIP)", where the summary of function is a one- to three-word description of the extension. For example, if an extension defines a new header field, called Make-Coffee, for making coffee, the title would read, "Making Coffee with the Session Initiation Protocol (SIP)". It is RECOMMENDED that these additional words be descriptive rather than naming the header field. For example, the extension for making coffee should not be named "The Make-Coffee Header for the Session Initiation Protocol".
Важным решением, которое необходимо принять в отношении расширения, является его название. Заголовок ДОЛЖЕН указывать, что документ является расширением SIP.
