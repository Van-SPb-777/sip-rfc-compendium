Abstract
Аннотация
The Presence Information Data Format (PIDF) defines a basic XML format for presenting presence information for a presentity. The Contact Information for the Presence Information Data format (CIPID) is an extension that adds elements to PIDF that provide additional contact information about a presentity and its contacts, including references to address book entries and icons. 'urn:ietf:params:xml:ns:pidf:cipid' 6.2. Schema Registration for Schema
Формат информации о присутствии (PIDF) определяет базовый формат XML для представления информации о присутствии для презентити. Контактная информация для формата информации о присутствии (CIPID) — это расширение, которое добавляет к PIDF элементы, предоставляющие дополнительную контактную информацию о презентити и его контактах, включая ссылки на записи адресной книги и значки. 1. Introduction
1. Введение
Presence information facilitates communication; its usefulness can be enhanced by providing basic information about a presentity or contact. This specification describes a basic set of information elements that allow a watcher to retrieve additional information about a presentity or contact.
Информация о присутствии облегчает связь; её полезность можно повысить, предоставляя базовую информацию о презентити или контакте. В настоящей спецификации описывается базовый набор информационных элементов, позволяющих наблюдателю получать дополнительную информацию о презентити или контакте.
This specification defines extensions to the PIDF [9] Extensible Markup Language [7][8][10] (XML) document format.
Настоящая спецификация определяет расширения формата документов на языке расширяемой разметки (XML) [7][8][10] для PIDF [9].
We describe elements for providing a "business card", references to the homepage, map, representative sound, display name, and an icon. This additional presence information can be used in PIDF [9] documents, together with Rich Presence Information Data format [11] (RPID), future-status [12], and other PIDF extensions.
Мы описываем элементы для предоставления «визитной карточки», ссылок на домашнюю страницу, карту, характерный звук, отображаемое имя и значок. Эта дополнительная информация о присутствии может использоваться в документах PIDF [9] вместе с форматом информации о расширенном присутствии [11] (RPID), информацией о будущем статусе [12] и другими расширениями PIDF.
All elements extend the <person> or, less commonly, <tuple> element in the presence data model [13]. The <tuple> element is only extended with Contact Information for the Presence Information Data format (CIPID) elements if the information describes a service referring to another person that is marked by an RPID <relationship> element with a value other than 'self'. All elements described in this document are optional. RPID and CIPID both provide "rich" presence that goes beyond the basic 'open' and 'closed' status information in PIDF. The presence information described in these two documents can be supplied independently, although in practice, both will often appear in the same PIDF document. CIPID elements describe the more static aspects of somebody's presence information, while RPID focuses on elements that will likely change throughout the day. Thus, CIPID information can often be statically configured by the user through the graphical user interface of a presence client; this is less likely to be sufficient for RPID.
Все элементы расширяют элемент <person> или, реже, элемент <tuple> в модели данных присутствия [13]. Элемент <tuple> расширяется элементами контактной информации для формата информации о присутствии (CIPID), только если информация описывает службу, относящуюся к другому человеку, который помечен элементом <relationship> RPID со значением, отличным от 'self'. Все элементы, описанные в настоящем документе, являются необязательными. RPID и CIPID оба обеспечивают «расширенную» информацию о присутствии, выходящую за пределы базовой информации о состоянии 'open' и 'closed' в PIDF. Информация о присутствии, описанная в этих двух документах, может предоставляться независимо, хотя на практике обе часто будут присутствовать в одном документе PIDF. Элементы CIPID описывают более статические аспекты информации о присутствии человека, тогда как RPID сосредоточен на элементах, которые, вероятно, будут меняться в течение дня. Таким образом, информация CIPID часто может статически настраиваться пользователем через графический интерфейс клиента присутствия; для RPID это менее вероятно окажется достаточным.

3. CIPID Elements
3. Элементы CIPID
Unless otherwise noted below, each element may only appear at most once.
Если ниже не указано иное, каждый элемент может появляться не более одного раза.
3.1. Card Element
3.1. Элемент <card>
The <card> element includes a URI pointing to a business card, e.g., in LDAP Data Interchange Format [15] (LDIF) or vCard [14] format.
Элемент <card> содержит URI, указывающий на визитную карточку, например в формате LDAP Data Interchange Format [15] (LDIF) или vCard [14].
3.2. Display-Name Element
3.2. Элемент <display-name>
The <display-name> element includes the name identifying the tuple or person that the presentity suggests should be shown by the watcher user interface. It is left to the watcher user interface design to choose whether to heed this suggestion or to use some other suitable string. The CIPID information MAY contain multiple display names, but only if they are labeled with different 'xml:lang' attributes. This allows a Korean-speaking presentity to convey its display name in different languages, Latin and Hangul, for example.
Элемент <display-name> содержит имя, идентифицирующее кортеж или человека, которое, по мнению презентити, следует показывать в пользовательском интерфейсе наблюдателя. Выбор, следовать ли этому предложению или использовать какую-либо другую подходящую строку, оставляется на усмотрение дизайна пользовательского интерфейса наблюдателя. Информация CIPID МОЖЕТ содержать несколько отображаемых имён, но только если они помечены разными атрибутами 'xml:lang'. Это позволяет презентити, говорящему по-корейски, передавать своё отображаемое имя на разных языках, например латиницей и хангылем.
3.3. Homepage Element
3.3. Элемент <homepage>
The <homepage> element provides a URI pointing to general information about the tuple or person, typically a web home page.
Элемент <homepage> предоставляет URI, указывающий на общую информацию о кортеже или человеке, обычно на веб-домашнюю страницу.
3.4. Icon Element
3.4. Элемент <icon>
The <icon> element provides a URI pointing to an image (icon) representing the tuple or person. The watcher can use this information to represent the tuple or person in a graphical user interface. Presentities SHOULD provide images of sizes and aspect ratios that are appropriate for rendering as an icon. Support for JPEG, PNG, and GIF formats is REQUIRED.
Элемент <icon> предоставляет URI, указывающий на изображение (значок), представляющее кортеж или человека. Наблюдатель может использовать эту информацию для представления кортежа или человека в графическом пользовательском интерфейсе. Презентити СЛЕДУЕТ предоставлять изображения таких размеров и пропорций, которые подходят для отображения в виде значка. Поддержка форматов JPEG, PNG и GIF ОБЯЗАТЕЛЬНА.
3.5. Map Element
3.5. Элемент <map>
The <map> element provides a URI pointing to a map related to the tuple or person. The watcher can use this information to represent the tuple or person in a graphical user interface. The map may be either an image, an HTML client-side image map, or a geographical information system (GIS) document, e.g., encoded as GML. Support for images formatted as PNG and GIF is REQUIRED.
Элемент <map> предоставляет URI, указывающий на карту, связанную с кортежем или человеком. Наблюдатель может использовать эту информацию для представления кортежа или человека в графическом пользовательском интерфейсе. Карта может быть изображением, картой изображения HTML на стороне клиента или документом географической информационной системы (GIS), например закодированным в GML. Поддержка изображений в форматах PNG и GIF ОБЯЗАТЕЛЬНА.
3.6. Sound Element
3.6. Элемент <sound>
The <sound> element provides a URI pointing to a sound related to the tuple or person. The watcher MAY use the sound object, such as a MIDI or MP3 file, referenced by the URL to inform the watcher that the presentity has assumed the status OPEN. Implementors are advised to create user interfaces that provide the watcher with the opportunity to choose whether to play such sounds. Support for sounds coded as MPEG-2 Layer 3 (MP3) is RECOMMENDED. The sound object might also be used to indicate how to pronounce the presentity's name.
Элемент <sound> предоставляет URI, указывающий на звук, связанный с кортежем или человеком. Наблюдатель МОЖЕТ использовать звуковой объект, например файл MIDI или MP3, на который ссылается URL, чтобы сообщить наблюдателю, что презентити принял статус OPEN. Разработчикам рекомендуется создавать пользовательские интерфейсы, предоставляющие наблюдателю возможность выбирать, воспроизводить ли такие звуки. Поддержка звуков, закодированных как MPEG-2 Layer 3 (MP3), РЕКОМЕНДУЕТСЯ. Звуковой объект также может использоваться, чтобы указать, как произносится имя презентити.

7. Internationalization Considerations
7. Вопросы интернационализации
CIPID delivers only URLs, except for the <display-name> element. The resolution of the URLs can negotiate appropriate language and character sets within the URL-designated protocol.
CIPID передаёт только URL, за исключением элемента <display-name>. При разрешении URL можно согласовать подходящие языки и наборы символов в рамках протокола, заданного URL.
For the display name and to handle Internationalized Resource Identifiers (IRIs) [16], since CIPID is represented in XML, it provides native support for encoding information using the Unicode character set and its more compact representations including UTF-8. Conformant XML processors recognize both UTF-8 and UTF-16. Though XML includes provisions to identify and use other character encodings through use of an "encoding" attribute in an <?xml?> declaration, use of UTF-8 is RECOMMENDED in environments where parser encoding support incompatibility exists.
Для отображаемого имени и для обработки интернационализированных идентификаторов ресурсов (IRI) [16], поскольку CIPID представлен в XML, обеспечивается встроенная поддержка кодирования информации с использованием набора символов Unicode и его более компактных представлений, включая UTF-8. Соответствующие XML-процессоры распознают как UTF-8, так и UTF-16. Хотя XML включает средства для идентификации и использования других кодировок символов с помощью атрибута "encoding" в объявлении <?xml?>, в средах, где существует несовместимость поддержки кодировок парсером, РЕКОМЕНДУЕТСЯ использовать UTF-8.
The XML 'xml:lang' attribute can be used to identify the language and script for the <display-name> element. The specification allows multiple occurrences of this element so that the presentity can convey display names in multiple scripts and languages. If no 'xml: lang' attribute is provided, the default value is "i-default" [3].
Атрибут XML 'xml:lang' может использоваться для идентификации языка и письменности для элемента <display-name>. Спецификация допускает множественные вхождения этого элемента, чтобы презентити мог передавать отображаемые имена на нескольких письменностях и языках. Если атрибут 'xml: lang' не указан, значением по умолчанию является "i-default" [3].
8. Security Considerations
8. Вопросы безопасности
The security issues are similar to those for RPID [11]. Watchers need to restrict which content types of content pointed to by <icon>, <homepage>, <map>, <sound>, and <vcard> elements they render.
Вопросы безопасности аналогичны вопросам для RPID [11]. Наблюдателям необходимо ограничивать, какие типы содержимого, на которое указывают элементы <icon>, <homepage>, <map>, <sound> и <vcard>, они отображают.
Also, when a watcher accesses these URIs, the presentity may deduce that the watcher is currently using the presence application. Thus, a presence application concerned about leaking this information may want to cache these objects for later use. (A presentity could easily customize the URLs for each watcher, so that it can tell who is referencing the objects.) This caching behavior may cause the information to become stale, out-of-sync with the current data until the cache is refreshed. Fortunately, the elements in CIPID are expected to retain the same content for periods measured in days, so that privacy-conscious applications may well decide to perform caching over durations that reveal little current activity information. Presentities need to keep in mind that clients may cache the content referenced by URIs for long periods as they use their presence system to construct presence documents using this extension. If the referenced content needs to change frequently, the presentity could, for example, update the presence document with a new URI to encourage clients to notice. Icons and other URIs in this document could be used as a covert channel to convey messages to the watcher, outside the content monitoring that might be in place for instant messages or other communications channels.
Кроме того, когда наблюдатель обращается к этим URI, презентити может заключить, что наблюдатель в настоящее время использует приложение присутствия. Поэтому приложение присутствия, обеспокоенное утечкой этой информации, может пожелать кэшировать эти объекты для последующего использования. (Презентити мог бы легко настроить URL для каждого наблюдателя, чтобы определять, кто ссылается на объекты.) Такое поведение кэширования может привести к устареванию информации, её рассинхронизации с текущими данными до обновления кэша. К счастью, ожидается, что элементы CIPID сохраняют одинаковое содержимое в течение периодов, измеряемых днями, поэтому приложения, заботящиеся о конфиденциальности, вполне могут решить выполнять кэширование в течение сроков, которые раскрывают мало информации о текущей активности. Презентити должны иметь в виду, что клиенты могут длительное время кэшировать содержимое, на которое ссылаются URI, когда они используют свою систему присутствия для построения документов присутствия с помощью этого расширения. Если содержимое, на которое делается ссылка, должно часто меняться, презентити мог бы, например, обновить документ присутствия новым URI, чтобы побудить клиентов это заметить. Значки и другие URI в настоящем документе могут использоваться как скрытый канал для передачи сообщений наблюдателю в обход мониторинга содержимого, который может быть установлен для мгновенных сообщений или других каналов связи.
Thus, entities that worry about such channels may want to prohibit the usage of URLs pointing to resources outside their domain, for example.
Таким образом, объекты, которых беспокоят такие каналы, могут, например, пожелать запретить использование URL, указывающих на ресурсы за пределами их домена.
Implementors must take care to adhere to the mechanisms for verifying the identity in the referenced server's certificate against the URI. For instance, if the URI scheme is https, the requirements of RFC 2818 [5], section 3.1, must be met. In particular, the domain represented in the URI must match the subjectAltName in the certificate presented by the referenced server. If this identity check fails, the referenced content SHOULD NOT be retrieved and MUST NOT be used.
Разработчики должны тщательно соблюдать механизмы проверки идентичности в сертификате указанного сервера и URI. Например, если схема URI — https, должны выполняться требования RFC 2818 [5], раздел 3.1. В частности, домен, представленный в URI, должен совпадать с subjectAltName в сертификате, представленном указанным сервером. Если эта проверка идентичности не удаётся, содержимое, на которое делается ссылка, НЕ СЛЕДУЕТ извлекать, и его НЕ ДОЛЖНО использоваться.
