Abstract
Аннотация
Instant Messaging (IM) refers to the transfer of messages between users in near real-time. These messages are usually, but not required to be, short. IMs are often used in a conversational mode, that is, the transfer of messages back and forth is fast enough for participants to maintain an interactive conversation.
Мгновенные сообщения (Instant Messaging, IM) означают передачу сообщений между пользователями почти в реальном времени. Эти сообщения обычно, но не обязательно, короткие. Мгновенные сообщения часто используются в разговорном режиме, то есть передача сообщений туда и обратно достаточно быстра, чтобы участники могли поддерживать интерактивную беседу.
This document proposes the MESSAGE method, an extension to the Session Initiation Protocol (SIP) that allows the transfer of Instant Messages. Since the MESSAGE request is an extension to SIP, it inherits all the request routing and security features of that protocol. MESSAGE requests carry the content in the form of MIME body parts. MESSAGE requests do not themselves initiate a SIP dialog; under normal usage each Instant Message stands alone, much like pager messages. MESSAGE requests may be sent in the context of a dialog initiated by some other SIP request. Terminology
Настоящий документ предлагает метод MESSAGE — расширение протокола инициирования сессий (SIP), позволяющее передавать мгновенные сообщения. Поскольку запрос MESSAGE является расширением SIP, он наследует все возможности маршрутизации запросов и безопасности этого протокола. Запросы MESSAGE несут содержимое в форме частей тела MIME. Запросы MESSAGE сами по себе не инициируют диалог SIP; при обычном использовании каждое мгновенное сообщение является самостоятельным, во многом как сообщения пейджера. Запросы MESSAGE могут отправляться в контексте диалога, инициированного некоторым другим запросом SIP.
In this document, the key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" and "OPTIONAL" are to be interpreted as described in BCP 14, RFC 2119 [6] and indicate requirement levels for compliant SIP implementations.
В настоящем документе ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «NOT RECOMMENDED», «MAY» и «OPTIONAL» должны толковаться так, как описано в BCP 14, RFC 2119 [6], и указывать уровни требований для совместимых реализаций SIP.
1. Introduction
1. Введение
Instant Messaging (IM) is defined as the exchange of content between a set of participants in near real time. Generally, the content is short text messages, although that need not be the case. Generally, the messages that are exchanged are not stored, but this also need not be the case. IM differs from email in common usage in that instant messages are usually grouped together into brief live conversations, consisting of numerous small messages sent back and forth.
Мгновенные сообщения (IM) определяются как обмен содержимым между набором участников почти в реальном времени. Обычно содержимое — это короткие текстовые сообщения, хотя это не обязательно. Обычно обмениваемые сообщения не сохраняются, но это также не обязательно. IM отличается от электронной почты по обычному использованию тем, что мгновенные сообщения обычно группируются в короткие живые беседы, состоящие из множества небольших сообщений, отправляемых туда и обратно.
Instant messaging as a service has been in existence within intranets and IP networks for quite some time. Early implementations include zephyr [11], the UNIX talk application, and IRC. More recently, IM has been used as a service coupled with presence and buddy lists; that is, when a friend comes online, a user can be made aware of this and have the option of sending the friend an instant message. The protocols for accomplishing this are all proprietary, which has seriously hampered interoperability.
Мгновенные сообщения как служба существуют внутри интранетов и IP-сетей довольно давно. Ранние реализации включают zephyr [11], приложение UNIX talk и IRC. В последнее время IM использовались как служба вместе с информацией о присутствии и списками собеседников; то есть, когда друг появляется в сети, пользователь может быть уведомлён об этом и получить возможность отправить другу мгновенное сообщение. Протоколы для этого все проприетарны, что серьёзно затрудняет взаимодействие.
The integration of instant messaging, presence, and session-oriented communications is very powerful. The Session Initiation Protocol (SIP) [1] provides mechanisms that are useful for presence applications, and for session-oriented communication applications, but not for instant messages.
Интеграция мгновенных сообщений, присутствия и связи, ориентированной на сессии, очень мощна. Протокол инициирования сессий (SIP) [1] предоставляет механизмы, полезные для приложений присутствия и для приложений связи, ориентированной на сессии, но не для мгновенных сообщений.
This document proposes an extension method for SIP called the MESSAGE method. MESSAGE requests normally carry the instant message content in the request body.
Настоящий документ предлагает метод расширения SIP, называемый методом MESSAGE. Запросы MESSAGE обычно несут содержимое мгновенного сообщения в теле запроса.
RFC 2778 [3] and RFC 2779 [2] give a model and requirements for presence and instant messaging protocols. Implementations of the MESSAGE method SHALL support all the instant message requirements in RFC 2779 relevant to its scope of applicability.
RFC 2778 [3] и RFC 2779 [2] дают модель и требования для протоколов присутствия и мгновенных сообщений. Реализации метода MESSAGE ДОЛЖНЫ поддерживать все требования к мгновенным сообщениям в RFC 2779, относящиеся к области его применимости.
2. Scope of Applicability
2. Область применимости
This document describes the use of the MESSAGE method for sending instant messages using a metaphor similar to that of a two-way pager or SMS enabled handset. That is, there are no explicit association between messages. Each IM stands alone--any sense of a "conversation" only exists in the client user interface, or perhaps in the user's own imagination. We contrast this with a "session" model, where there is an explicit conversation with a clear beginning and end. In the SIP environment, an IM session would be a media session initiated with an INVITE transaction and terminated with a BYE transaction.
Настоящий документ описывает использование метода MESSAGE для отправки мгновенных сообщений, используя метафору, похожую на метафору двустороннего пейджера или аппарата с поддержкой SMS. То есть между сообщениями нет явной связи. Каждое мгновенное сообщение является самостоятельным — любое ощущение «беседы» существует только в пользовательском интерфейсе клиента или, возможно, в воображении самого пользователя. Мы противопоставляем это «сессионной» модели, где есть явная беседа с чётким началом и концом. В среде SIP сессия IM была бы медиасессией, инициированной транзакцией INVITE и завершённой транзакцией BYE.
There is value in each model. Most modern IM clients offer both user experiences. The user can choose to send an IM to a contact, or he can choose to invite one or more contacts to join a conversation. The pager model makes sense when the user wishes to send a small number of short IMs to a single (or small number of) recipients. The session model makes sense for extended conversations, joining chat groups, if there is a need to associate a conversation with some other SIP initiated session, etc.
В каждой модели есть ценность. Большинство современных клиентов IM предлагают оба варианта пользовательского опыта. Пользователь может выбрать отправку мгновенного сообщения контакту либо пригласить один или несколько контактов присоединиться к беседе. Модель пейджера имеет смысл, когда пользователь желает отправить небольшое число коротких мгновенных сообщений одному (или небольшому числу) получателю. Сессионная модель имеет смысл для продолжительных бесед, присоединения к чат-группам, если есть необходимость связать беседу с некоторой другой сессией, инициированной SIP, и т. д.
This document addresses the pager model only. We recognize the value of the session model as well, but we do not define it here. Such a solution will require additional work beyond that of this document. The SIMPLE work group currently plans to address IM sessions in a separate document. There may be a temptation to simulate a session of IMs by initiating a dialog, then sending MESSAGE requests in the context of that dialog. This is not an adequate solution for IM sessions, in that this approach forces the MESSAGE requests to follow the same network path as any other SIP requests, even though the MESSAGE requests arguably carry media rather than signaling. IM applications are typically high volume, and we expect the IM volume in sessions to be even higher. This will likely cause congestion problems if sent over a transport without congestion control, and there is no clear mechanism in SIP to prevent some hop from forwarding a MESSAGE request over UDP.
Настоящий документ рассматривает только модель пейджера. Мы признаём ценность сессионной модели, но здесь её не определяем. Такое решение потребует дополнительной работы сверх настоящего документа. Рабочая группа SIMPLE в настоящее время планирует рассмотреть сессии IM в отдельном документе. Может возникнуть соблазн смоделировать сессию мгновенных сообщений путём инициирования диалога и последующей отправки запросов MESSAGE в контексте этого диалога. Это не является адекватным решением для сессий IM, поскольку такой подход заставляет запросы MESSAGE следовать тому же сетевому пути, что и любые другие запросы SIP, хотя запросы MESSAGE, возможно, несут медиа, а не сигнализацию. Приложения IM, как правило, имеют высокий объём, и мы ожидаем, что объём IM в сессиях будет ещё выше. Это, вероятно, вызовет проблемы перегрузки при отправке по транспорту без управления перегрузкой, и в SIP нет чёткого механизма, предотвращающего передачу запроса MESSAGE по UDP на каком-либо переходе.
Additionally, MESSAGE requests sent over an existing dialog must, by the nature of SIP, go to the same destination as any other request sent in that dialog. This prevents any separation between the IM endpoint and the signaling endpoint. This is not an acceptable limitation for the session-model of instant messaging.
Кроме того, запросы MESSAGE, отправленные в существующем диалоге, должны по природе SIP идти тому же адресату, что и любой другой запрос в этом диалоге. Это препятствует любому разделению между оконечным пунктом IM и оконечным пунктом сигнализации. Это неприемлемое ограничение для сессионной модели мгновенных сообщений.
The authors recognize that there may be valid reasons to send MESSAGE requests in the context of a dialog. For example, one participant in a voice session may wish to send an IM to another participant, and associate that IM with the session. But implementations SHOULD NOT create dialogs for the primary purpose of associating MESSAGE requests with one another.
Авторы признают, что могут быть веские причины отправлять запросы MESSAGE в контексте диалога. Например, один участник голосовой сессии может пожелать отправить мгновенное сообщение другому участнику и связать это сообщение с сессией. Однако реализациям НЕ СЛЕДУЕТ создавать диалоги с основной целью связать запросы MESSAGE друг с другом.
Note that this statement does not prohibit using SIP to initiate a media session made up of IMs, just like any other session. Indeed, we expect the solution for IM sessions to use that metaphor. The reader should avoid confusing the concepts of a SIP dialog and a media session.
Обратите внимание, что это утверждение не запрещает использовать SIP для инициирования медиасессии, состоящей из мгновенных сообщений, как и любой другой сессии. Действительно, мы ожидаем, что решение для сессий IM будет использовать эту метафору. Читателю следует избегать путаницы понятий диалога SIP и медиасессии.
3. Overview of Operation
3. Обзор работы
When one user wishes to send an instant message to another, the sender formulates and issues a SIP request using the new MESSAGE method defined by this document. The Request-URI of this request will normally be the "address of record" for the recipient of the instant message, but it may be a device address in situations where the client has current information about the recipient's location. For example, the client could be coupled with a presence system that supplies an up to date device contact for a given address of record. The body of the request will contain the message to be delivered. This body can be of any MIME type, including message/cpim [7]. Since the message/cpim format is expected to be supported by other instant message protocols, endpoints using different IM protocols, but otherwise supporting message/cpim body types, should be able to exchange messages without modification of the content by a gateway or other intermediary. This helps to enable end-to-end security between endpoints that use different IM protocols.
Когда один пользователь желает отправить мгновенное сообщение другому, отправитель формирует и выдаёт запрос SIP с использованием нового метода MESSAGE, определённого в настоящем документе. Request-URI этого запроса обычно будет «адресом записи» получателя мгновенного сообщения, но может быть и адресом устройства в ситуациях, когда клиент располагает актуальной информацией о местоположении получателя. Например, клиент может быть связан с системой присутствия, предоставляющей актуальный контакт устройства для данного адреса записи. Тело запроса будет содержать сообщение, подлежащее доставке. Это тело может быть любого типа MIME, включая message/cpim [7]. Поскольку ожидается, что формат message/cpim поддерживается другими протоколами мгновенных сообщений, оконечные пункты, использующие разные протоколы IM, но иначе поддерживающие типы тела message/cpim, обеспечить, чтобы содержимое не изменялось шлюзом или другим посредником. Это помогает обеспечить сквозную безопасность между конечными точками, использующими разные протоколы IM.
The request may traverse a set of SIP proxies, using a variety of transports, before reaching its destination. The destination for each hop is located using the address resolution rules detailed in the Common Profile for Instant Messaging (CPIM) [8] and SIP specifications. During traversal, each proxy may rewrite the request URI based on available routing information.
Запрос может проходить через набор SIP-прокси, используя разнообразные транспорты, прежде чем достичь места назначения. Адресат каждого перехода определяется с использованием правил разрешения адресов, подробно описанных в Общем профиле для мгновенных сообщений (CPIM) [8] и спецификациях SIP. При прохождении каждый прокси может переписать URI запроса на основе доступной информации о маршрутизации.
Provisional and final responses to the request will be returned to the sender as with any other SIP request. Normally, a 200 OK response will be generated by the user agent of the request's final recipient. Note that this indicates that the user agent accepted the message, not that the user has seen it.
Предварительные и окончательные ответы на запрос будут возвращены отправителю, как и для любого другого запроса SIP. Обычно ответ 200 OK генерируется пользовательским агентом конечного получателя запроса. Обратите внимание, что это указывает на то, что пользовательский агент принял сообщение, а не на то, что пользователь его увидел.
MESSAGE requests do not establish dialogs.
Запросы MESSAGE не устанавливают диалогов.
4. UAC Processing
4. Обработка у UAC
Unless stated otherwise in this document, MESSAGE requests and associated responses are constructed according to the rules in section 8.1 of the SIP specification [1].
Если в настоящем документе не указано иное, запросы MESSAGE и связанные ответы строятся согласно правилам раздела 8.1 спецификации SIP [1].
All UACs which support the MESSAGE method MUST be prepared to send MESSAGE requests with a body of type text/plain. They may send bodies of type message/cpim [7].
Все UAC, поддерживающие метод MESSAGE, ДОЛЖНЫ быть готовы отправлять запросы MESSAGE с телом типа text/plain. Они могут отправлять тела типа message/cpim [7].
MESSAGE requests do not initiate dialogs. User Agents MUST NOT insert Contact header fields into MESSAGE requests.
Запросы MESSAGE не инициируют диалогов. Пользовательские агенты НЕ ДОЛЖНЫ вставлять поля заголовка Contact в запросы MESSAGE.
A UAC MAY associate a MESSAGE request with an existing dialog. If a MESSAGE request is sent within a dialog, it is "associated" with any media session or sessions associated with that dialog.
UAC МОЖЕТ связать запрос MESSAGE с существующим диалогом. Если запрос MESSAGE отправлен в пределах диалога, он «связан» с любой медиасессией или сессиями, связанными с этим диалогом.
If the UAC receives a 200 OK response to a MESSAGE request, it may assume the message has been delivered to the final destination. It MUST NOT assume that the recipient has actually read the instant message. If the UAC receives a 202 Accepted response, the message has been delivered to a gateway, store and forward server, or some other service that may eventually deliver the message. In this case, the UAC MUST NOT assume the message has been delivered to the final destination. If confirmation of delivery is required for a message that has been responded to with a 202 Accepted, that confirmation must be delivered via some other mechanism, which is beyond the scope of this specification. Note that a downstream proxy could fork a MESSAGE request. If this occurs, the forking proxy will forward one final response upstream, even though it may receive multiple final responses. The UAC will have no way to detect whether or not a fork occurs. Therefore the UAC MUST NOT assume that a given final response represents the only UAS that receives the request. For example, multiple branches of a fork could have resulted in 2xx responses. Even though the UAC only sees one of those responses, the request has in fact been received by the second device as well.
Если UAC получает ответ 200 OK на запрос MESSAGE, он может предполагать, что сообщение доставлено конечному адресату. Он НЕ ДОЛЖЕН предполагать, что получатель фактически прочитал мгновенное сообщение. Если UAC получает ответ 202 Accepted, сообщение доставлено шлюзу, серверу хранения и пересылки или какой-либо иной службе, которая в конечном итоге может доставить сообщение. В этом случае UAC НЕ ДОЛЖЕН предполагать, что сообщение доставлено конечному адресату. Если для сообщения, на которое был дан ответ 202 Accepted, требуется подтверждение доставки, это подтверждение должно быть доставлено каким-либо иным механизмом, что выходит за рамки настоящей спецификации. Обратите внимание, что нижестоящий прокси может разветвить запрос MESSAGE. Если это произойдёт, разветвляющий прокси перешлёт наверх один окончательный ответ, даже если может получить несколько окончательных ответов. UAC не будет иметь способа обнаружить, произошло ли ветвление. Поэтому UAC НЕ ДОЛЖЕН предполагать, что данный окончательный ответ представляет единственный UAS, получивший запрос. Например, несколько ветвей разветвления могли дать ответы 2xx. Даже если UAC видит только один из этих ответов, запрос фактически был получен и вторым устройством.
The UAC MAY add an Expires header field to limit the validity of the message content. If the UAC adds an Expires header field with a non-zero value, it SHOULD also add a Date header field containing the time the message is sent.
UAC МОЖЕТ добавить поле заголовка Expires, чтобы ограничить срок действия содержимого сообщения. Если UAC добавляет поле заголовка Expires с ненулевым значением, ему СЛЕДУЕТ также добавить поле заголовка Date, содержащее время отправки сообщения.
5. Use of Instant Message URIs
5. Использование URI мгновенных сообщений
An instant inbox may be most generally referenced by an Instant Message URI [8] in the form of "im:user@domain". IM URIs are abstract, and will eventually be translated to concrete, protocol- dependent URI.
Входящий ящик мгновенных сообщений чаще всего может быть указан посредством URI мгновенного сообщения [8] в форме «im:user@domain». URI IM абстрактны и в конечном итоге преобразуются в конкретные URI, зависящие от протокола.
If a UA is presented with an IM URI as the address for an instant message, it SHOULD resolve it to a SIP URI, and place the resulting URI in the Request-URI of the MESSAGE request before sending. If the UA is unable to resolve the IM URI, it MAY place the IM URI in the Request-URI, thus delegating the resolution to a downstream device such as proxy or gateway. Performing this translation as early as possible allows SIP proxies, which may be unaware of the im: namespace, to route the requests normally.
Если UA получает URI IM в качестве адреса для мгновенного сообщения, ему СЛЕДУЕТ разрешить его в URI SIP и поместить полученный URI в Request-URI запроса MESSAGE перед отправкой. Если UA не может разрешить URI IM, он МОЖЕТ поместить URI IM в Request-URI, тем самым делегировав разрешение нижестоящему устройству, такому как прокси или шлюз. Выполнение этого преобразования как можно раньше позволяет SIP-прокси, которые могут не знать пространства имён im:, маршрутизировать запросы обычным образом.
MESSAGE requests also contain logical identifiers of the sender and intended recipient, in the form of the From and To header fields. These identifiers SHOULD contain SIP (or SIPS) URIs, but MAY include IM URIs if the SIP URIs are not known at the time of request construction.
Запросы MESSAGE также содержат логические идентификаторы отправителя и предполагаемого получателя в форме полей заголовков From и To. Эти идентификаторы СЛЕДУЕТ содержать URI SIP (или SIPS), но МОГУТ включать URI IM, если URI SIP неизвестны на момент построения запроса.
Record-Route and Route header fields MUST NOT contain IM URIs. These header fields contain concrete SIP or SIPS URIs according to the rules of SIP [1].
Поля заголовков Record-Route и Route НЕ ДОЛЖНЫ содержать URI IM. Эти поля заголовков содержат конкретные URI SIP или SIPS согласно правилам SIP [1].
6. Proxy Processing
6. Обработка у прокси
Proxies route MESSAGE requests according to the rules of SIP [1]. Note that the MESSAGE request MAY fork; this allows for delivery of the message to several possible terminals where the user might be. A proxy forking a MESSAGE request follows the normal SIP rules for forking a non-INVITE request. In particular, even if the fork results in multiple successful deliveries, the forking proxy will only forward one final response upstream.
Прокси маршрутизируют запросы MESSAGE согласно правилам SIP [1]. Обратите внимание, что запрос MESSAGE МОЖЕТ разветвляться; это позволяет доставить сообщение нескольким возможным терминалам, где может находиться пользователь. Прокси, разветвляющий запрос MESSAGE, следует обычным правилам SIP для разветвления запроса, отличного от INVITE. В частности, приводит к нескольким успешным доставкам, прокси, выполняющий разветвление, перешлёт вверх только один окончательный ответ.
7. UAS Processing
7. Обработка у UAS
A UAS that receives a MESSAGE request processes it following the rules of SIP [1].
UAS, получающий запрос MESSAGE, обрабатывает его согласно правилам SIP [1].
A UAS receiving a MESSAGE request SHOULD respond with a final response immediately. Note, however, that the UAS is not obliged to display the message to the user either before or after responding with a 200 OK. That is, a 200 OK response does not necessarily mean the user has read the message.
UAS, получающему запрос MESSAGE, СЛЕДУЕТ немедленно ответить окончательным ответом. Однако обратите внимание, что UAS не обязан отображать сообщение пользователю ни до, ни после ответа 200 OK. То есть ответ 200 OK не обязательно означает, что пользователь прочитал сообщение.
A 2xx response to a MESSAGE request MUST NOT contain a body. A UAS MUST NOT insert a Contact header field into a 2xx response.
Ответ 2xx на запрос MESSAGE НЕ ДОЛЖЕН содержать тело. UAS НЕ ДОЛЖЕН вставлять поле заголовка Contact в ответ 2xx.
A UAS which is, in fact, a message relay, storing the message and forwarding it later on, or forwarding it into a non-SIP domain, SHOULD return a 202 (Accepted) [5] response indicating that the message was accepted, but end to end delivery has not been guaranteed.
UAS, который фактически является ретранслятором сообщений, сохраняющим сообщение и пересылающим его позже либо пересылающим его в домен, отличный от SIP, СЛЕДУЕТ вернуть ответ 202 (Accepted) [5], указывающий, что сообщение принято, но сквозная доставка не гарантирована.
A 4xx or 5xx response indicates that the message was not delivered successfully. A 6xx response means it was delivered successfully, but refused.
Ответ 4xx или 5xx указывает, что сообщение не было успешно доставлено. Ответ 6xx означает, что оно было успешно доставлено, но отклонено.
A UAS that supports the MESSAGE method MUST be prepared to receive and render bodies of type "text/plain", and may support reception and rendering of bodies of type "message/cpim" [7].
UAS, поддерживающий метод MESSAGE, ДОЛЖЕН быть готов принимать и отображать тела типа «text/plain» и может поддерживать приём и отображение тел типа «message/cpim» [7].
A MESSAGE request is said to be expired if its expiration time has passed. The expiration time is determined by examining the Expires header field, if present. MESSAGE requests without an Expires header field do not expire. If the MESSAGE request containing an Expires header field also contains a Date header field, the UAS SHOULD interpret the Expires header field value as delta time from the Date header field value. If the request does not contain a Date header field, the UAS SHOULD interpret the Expires header value as delta time from the time the UAS received the request.
Говорят, что запрос MESSAGE истёк, если истекло его время истечения. Время истечения определяется путём исследования поля заголовка Expires, если оно присутствует. Запросы MESSAGE без поля заголовка Expires не истекают. Если запрос MESSAGE, содержащий поле заголовка Expires, также содержит поле заголовка Date, UAS СЛЕДУЕТ интерпретировать значение поля заголовка Expires как дельта-время от значения поля заголовка Date. Если запрос не содержит поля заголовка Date, UAS СЛЕДУЕТ интерпретировать значение Expires как дельта-время от момента получения запроса UAS.
If the MESSAGE expires before the UAS is able to present the message to the user, the UAS SHOULD handle the message based on local policy. This policy could mean: the message is deleted undisplayed, the message is still displayed to the user, or some other policy may be invoked. If the message is displayed, the UAS SHOULD clearly indicate to the user that the message has expired.
Если сообщение MESSAGE истекает до того, как UAS сможет представить его пользователю, UAS СЛЕДУЕТ обработать сообщение на основе локальной политики. Эта политика может означать: сообщение удаляется без отображения, сообщение всё равно отображается пользователю либо вызывается какая-либо иная политика. Если сообщение отображается, UAS СЛЕДУЕТ чётко указать пользователю, что сообщение истекло.
If the UAS is acting as a message relay, and is unable to deliver the message before expiration, it chooses an action based on local policy. This action could involve deleting the message undelivered, delivering it as is, logging the expired message, or any other local policy.
Если UAS действует как ретранслятор сообщений и не может доставить сообщение до истечения срока, он выбирает действие на основе локальной политики. Это действие может включать удаление сообщения недоставленным, доставку как есть, регистрацию истёкшего сообщения или любую другую локальную политику.
8. Congestion Control
8. Управление перегрузкой
Existing IM services have a history of very high volume usage. Additionally, MESSAGE requests differ from other sorts of SIP requests in that they carry media, in the form of IMs, as payload. Conventional SIP payloads carry signaling information about media, but not media itself. There is potential that when a SIP infrastructure is shared between call signaling and instant messaging, the IM traffic will interfere with call signaling traffic. Congestion control in general is an issue that should be addressed at the SIP specification level rather than for an individual method. But since the traffic patterns are likely to be different for MESSAGE than for most other methods, it makes sense to give MESSAGE special consideration.
Существующие службы IM имеют историю очень высокого объёма использования. Кроме того, запросы MESSAGE отличаются от прочих запросов SIP тем, что несут медиа в форме мгновенных сообщений как полезную нагрузку. Обычные полезные нагрузки SIP несут сигнальную информацию о медиа, но не сами медиа. Существует потенциал того, что когда инфраструктура SIP совместно используется для сигнализации вызовов и мгновенных сообщений, трафик IM будет мешать трафику сигнализации вызовов. Управление перегрузкой в целом является вопросом, который следует рассматривать на уровне спецификации SIP, а не отдельного метода. Но поскольку модели трафика для MESSAGE, вероятно, отличаются от большинства других методов, имеет смысл уделить MESSAGE особое внимание.
Whenever possible, MESSAGE requests SHOULD be sent over transports that implement end-to-end congestion control, such as TCP or SCTP. However, SIP does not provide a mechanism to prevent a downstream hop from sending a request over UDP. Even the requirement to use TCP for requests over a certain size can be overridden by the receiver. Therefore use of a congestion-controlled transport by the UAC is not sufficient.
Когда это возможно, запросы MESSAGE СЛЕДУЕТ отправлять по транспортам, реализующим сквозное управление перегрузкой, например TCP или SCTP. Однако SIP не предоставляет механизма, предотвращающего отправку запроса по UDP нижестоящим переходом. Даже требование использовать TCP для запросов сверх определённого размера может быть отменено получателем. Поэтому использования UAC транспорта с управлением перегрузкой недостаточно.
The size of MESSAGE requests outside of a media session MUST NOT exceed 1300 bytes, unless the UAC has positive knowledge that the message will not traverse a congestion-unsafe link at any hop, or that the message size is at least 200 bytes less than the lowest MTU value found en route to the UAS. Larger payloads may be sent as part of a media session, or using some type of content-indirection.
Размер запросов MESSAGE вне медиасессии НЕ ДОЛЖЕН превышать 1300 байт, если только UAC не располагает достоверным знанием того, что сообщение не пройдёт ни на одном переходе по каналу, небезопасному с точки зрения перегрузки, либо что размер сообщения как минимум на 200 байт меньше наименьшего значения MTU, обнаруженного на пути к UAS. Большие полезные нагрузки могут отправляться как часть медиасессии или с использованием некоторого типа косвенной адресации содержимого.
At the time of this writing, there is no mechanism for a UAC to gain such knowledge outside of trivial network architectures, or networks that are wholly controlled by a single administrative domain. But if a mechanism for ensuring congestion-control at each hop is created in the future, MESSAGE clients can relax the size limit without requiring a change to this specification. The authors expect that such a mechanism or mechanism will be created in the near future. There have been discussions on making the 1300 byte limit based on the path MTU to the next hop SIP device. The SIP specification does exactly that, choosing the limit 200 bytes less than the path MTU, or 1300 bytes if the device does not know the path MTU. Transport decisions are made on a per-hop basis. However, the point of this limit is to make sure that no upstream proxy chooses to send a MESSAGE request with large content over UDP.
На момент написания не существует механизма, позволяющего UAC получить такое знание вне тривиальных сетевых архитектур или сетей, полностью контролируемых одним административным доменом. Но если в будущем будет создан механизм обеспечения управления перегрузкой на каждом переходе, клиенты MESSAGE смогут ослабить ограничение размера без необходимости изменения настоящей спецификации. Авторы ожидают, что такой механизм или механизмы будут созданы в ближайшем будущем. Велись обсуждения о том, чтобы сделать ограничение в 1300 байт основанным на MTU пути до следующего устройства SIP. Спецификация SIP делает именно это, выбирая предел на 200 байт меньше MTU пути, или 1300 байт, если устройство не знает MTU пути. Решения о транспорте принимаются на основе каждого перехода. Однако суть этого ограничения — обеспечить, чтобы ни один вышестоящий прокси не выбрал отправку запроса MESSAGE с большим содержимым по UDP.
Since, except in trivial circumstances, a MESSAGE client is very unlikely to know the MTU for upstream devices beyond the next hop, an MTU based limit is not very useful.
Поскольку, кроме тривиальных обстоятельств, клиент MESSAGE вряд ли знает MTU для вышестоящих устройств за следующим переходом, ограничение на основе MTU не очень полезно.
A UAC MUST NOT initiate a new out-of-dialog MESSAGE transaction to a given URI if there is a previous out-of-dialog transaction pending for the same URI. Similarly, A UAC SHOULD NOT initiate overlapping MESSAGE transactions inside a dialog, and MUST NOT do so unless the route set for that dialog uses a congestion-controlled transport at every hop.
UAC НЕ ДОЛЖЕН инициировать новую транзакцию MESSAGE вне диалога к данному URI, если для того же URI уже есть ожидающая транзакция вне диалога. Аналогично UAC НЕ СЛЕДУЕТ инициировать перекрывающиеся транзакции MESSAGE внутри диалога и НЕ ДОЛЖЕН делать это, если только набор маршрутов для этого диалога не использует транспорт с управлением перегрузкой на каждом переходе.
The prohibition against overlapping MESSAGE request provides some degree of congestion-safe behavior. A request and its associated response must each cross the full path between the UAC and the UAS. The time required for this will increase as networks become congested. This provides an adaptive mechanism to slow the introduction of new MESSAGE requests to the same destination.
Запрет перекрывающихся запросов MESSAGE обеспечивает определённую степень поведения, безопасного с точки зрения перегрузки. Запрос и связанный с ним ответ должны каждый пройти полный путь между UAC и UAS. Требуемое для этого время будет расти по мере перегрузки сетей. Это обеспечивает адаптивный механизм замедления введения новых запросов MESSAGE к одному и тому же адресату.
It has been suggested that provisional responses should not be allowed for pager-model MESSAGE requests. However, it is not possible to require special treatment for MESSAGE, since many proxy servers will not be aware of the MESSAGE method. Therefore MESSAGE requests will receive the same provisional response treatment as any other non-INVITE method, as described in the SIP specification.
Было предложено не допускать предварительных ответов для запросов MESSAGE модели пейджера. Однако невозможно требовать особой обработки для MESSAGE, поскольку многие прокси-серверы не будут знать метода MESSAGE. Поэтому запросы MESSAGE будут получать такую же обработку предварительных ответов, как и любой другой метод, отличный от INVITE, как описано в спецификации SIP.

SIP/2.0 200 OK Via: SIP/2.0/TCP user1pc.domain.com;branch=z9hG4bK776sgdkse; received=1.2.3.4 From: sip:user1@domain.com;;tag=49394 To: sip:user2@domain.com;tag=ab8asdasd9 Call-ID: asd88asd77a@1.2.3.4 CSeq: 1 MESSAGE Content-Length: 0

11. Security Considerations
11. Вопросы безопасности
In normal usage, most SIP requests are used to setup and modify communication sessions. The actual communication between participants happens in the media sessions, not in the SIP requests themselves. The MESSAGE method changes this assumption; MESSAGE requests normally carry the actual communication between participants as payload. This implies that MESSAGE requests have a greater need for security than most other SIP requests. In particular, UAs that support the MESSAGE request MUST implement end-to-end authentication, body integrity, and body confidentiality mechanisms.
При обычном использовании большинство запросов SIP служат для установления и изменения сессий связи. Фактическая связь между участниками происходит в медиасессиях, а не в самих запросах SIP. Метод MESSAGE изменяет это допущение: запросы MESSAGE обычно несут фактическую связь между участниками как полезную нагрузку. Это подразумевает, что запросы MESSAGE имеют бо́льшую потребность в безопасности, чем большинство других запросов SIP. В частности, UA, поддерживающие запрос MESSAGE, ДОЛЖНЫ реализовать механизмы сквозной аутентификации, целостности тела и конфиденциальности тела.
11.1. Outbound Authentication
11.1. Исходящая аутентификация
When local proxies are used for transmission of outbound messages, proxy authentication, as specified in RFC 3261, is RECOMMENDED. This is useful to verify the identity of the originator, and prevent spoofing and spamming at the originating network.
Когда для передачи исходящих сообщений используются локальные прокси, РЕКОМЕНДУЕТСЯ аутентификация прокси, как указано в RFC 3261. Это полезно для проверки идентичности отправителя и предотвращения подделки и спама в исходной сети.
11.2. SIPS URIs
11.2. URI SIPS
The SIPS URI mechanism [1] allows a UA to assert that every hop must occur over a secure connection. This provides some level of integrity and privacy protection. However, this requires the users to trust that each proxy in the request path is well-behaved, that is, they do not violate the rules for routing SIPS URIs. Also, any unencrypted bodies are fully exposed to the proxies.
Механизм URI SIPS [1] позволяет UA заявить, что каждый переход должен осуществляться по защищённому соединению. Это обеспечивает определённый уровень целостности и защиты конфиденциальности. Однако это требует от пользователей доверия к тому, что каждый прокси на пути запроса ведёт себя корректно, то есть не нарушает правил маршрутизации URI SIPS. Кроме того, любые незашифрованные тела полностью открыты прокси.
Additionally, the possibility of a forking proxy allows a MESSAGE request to be delivered to additional endpoints without the knowledge of the UAC. If only hop-by-hop protection is used, the users must trust all proxies in the chain to not fork requests to unauthorized destinations.
Кроме того, возможность разветвляющего прокси позволяет доставить запрос MESSAGE дополнительным оконечным пунктам без ведома UAC. Если используется только защита «переход за переходом», пользователи должны доверять всем прокси в цепочке в том, что они не будут разветвлять запросы неавторизованным адресатам.
11.3. End-to-End Protection
11.3. Сквозная защита
When the goal is to remedy the concerns stated above, the MESSAGE bodies MUST be secured with S/MIME. If bodies specified in future to be carried by the MESSAGE method have different means of providing end-to-end security, their specification MUST describe the usage. SIP MESSAGE endpoints MUST support encryption (CMS EnvelopeData) and S/MIME signatures (CMS SignedData).
Когда цель состоит в устранении вышеуказанных проблем, тела MESSAGE ДОЛЖНЫ быть защищены с помощью S/MIME. Если в будущем для тел, переносимых методом MESSAGE, будут определены иные средства обеспечения сквозной безопасности, их спецификация ДОЛЖНА описывать использование. Оконечные пункты SIP MESSAGE ДОЛЖНЫ поддерживать шифрование (CMS EnvelopeData) и подписи S/MIME (CMS SignedData).
The S/MIME algorithms are set by RFC 3369 [4]. The AES [10] algorithm should be preferred, as it is expected that AES best suits the capabilities of many platforms. However, an IETF specification for this is still incomplete as of the time of this writing.
Алгоритмы S/MIME заданы в RFC 3369 [4]. Алгоритму AES [10] следует отдавать предпочтение, поскольку ожидается, что AES наилучшим образом соответствует возможностям многих платформ. Однако спецификация IETF для этого на момент написания всё ещё не завершена.
11.4. Replay Prevention
11.4. Предотвращение повторного воспроизведения
To prevent the replay of old SIP requests, all signed MESSAGE requests and responses MUST contain a Date header field covered by the message signature. Any message with a date older than several minutes in the past, or which is more than several minutes in the future, SHOULD be answered with a 400 (Incorrect Date or Time) message, unless such messages arrive repeatedly from the same source, in which case they MAY be discarded without sending a response. Obviously, this replay attack prevention mechanism does not work for devices without clocks.
Чтобы предотвратить повторное воспроизведение старых запросов SIP, все подписанные запросы и ответы MESSAGE ДОЛЖНЫ содержать поле заголовка Date, охватываемое подписью сообщения. На любое сообщение с датой старше нескольких минут в прошлом или более чем на несколько минут в будущем СЛЕДУЕТ отвечать сообщением 400 (Incorrect Date or Time), если только такие сообщения не поступают повторно из одного источника, и в этом случае их МОЖНО отбрасывать без отправки ответа. Очевидно, что этот механизм предотвращения атак повторного воспроизведения не работает для устройств без часов.
Note that there are situations where an stale Date header field is normal. For example, the MESSAGE request may have been stored in a store and forward server while the recipient was offline. When the recipient returns, that server might then forward the message. Final receipt of the message would then occur some time after it was originally sent. If a UAS receives a stale message that can be confirmed to have come from a known store and forward server (perhaps over a TLS connection), it makes sense for it to accept the message normally. Also, if one or more stale messages arrive shortly after an offline period, the UAS MAY accept the message, but SHOULD warn the user that there is a risk the message has been replayed.
Обратите внимание, что есть ситуации, когда устаревшее поле заголовка Date является нормальным. Например, запрос MESSAGE мог быть сохранён на сервере хранения и пересылки, пока получатель был не в сети. Когда получатель возвращается, этот сервер может переслать сообщение. Тогда окончательное получение сообщения произойдёт спустя некоторое время после его первоначальной отправки. Если UAS получает устаревшее сообщение, которое можно подтвердить как пришедшее от известного сервера хранения и пересылки (возможно, по соединению TLS), имеет смысл принять сообщение обычным образом. Также, если одно или несколько устаревших сообщений прибывают вскоре после периода нахождения не в сети, UAS МОЖЕТ принять сообщение, но СЛЕДУЕТ предупредить пользователя о риске того, что сообщение было воспроизведено.
11.5. Using message/cpim Bodies
11.5. Использование тел message/cpim
The message/cpim format [7] allows for the S/MIME protection of metadata in addition to the message payload itself. In many cases, this metadata is redundant with SIP header fields. Still, message/cpim adds value in that the protection of metadata can extend across protocol boundaries. For example, a signed message/cpim body can provide sender authentication using the message/cpim From header field, even if the message crosses a gateway to another CPIM compliant instant message service that does not understand SIP header fields.
Формат message/cpim [7] допускает защиту S/MIME метаданных в дополнение к самой полезной нагрузке сообщения. Во многих случаях эти метаданные избыточны с полями заголовков SIP. Тем не менее message/cpim добавляет ценность тем, что защита метаданных может распространяться через границы протоколов. Например, подписанное тело message/cpim может обеспечить аутентификацию отправителя с использованием поля заголовка From message/cpim, даже если сообщение проходит через шлюз к другой службе мгновенных сообщений, совместимой с CPIM, которая не понимает поля заголовков SIP.
