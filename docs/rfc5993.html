Abstract
Аннотация
This document specifies the payload format for packetization of Global System for Mobile Communications Half Rate (GSM-HR) speech codec data into the Real-time Transport Protocol (RTP). The payload format supports transmission of multiple frames per payload and packet loss robustness methods using redundancy.
Настоящий документ определяет формат полезной нагрузки для пакетизации данных речевого кодека Global System for Mobile Communications Half Rate (GSM-HR) в протокол передачи реального времени (RTP). Формат полезной нагрузки поддерживает передачу нескольких кадров в одной полезной нагрузке, а также методы повышения устойчивости к потере пакетов с помощью избыточности.

3. GSM Half Rate
3. GSM с половинной скоростью
The Global System for Mobile Communications (GSM) network provides with mobile communication services for nearly 3 billion users (statistics as of 2008). The GSM Half Rate (GSM-HR) codec is one of the speech codecs used in GSM networks. GSM-HR denotes the Half Rate speech codec as specified in [TS46.002].
Сеть Global System for Mobile Communications (GSM) предоставляет услуги мобильной связи почти 3 миллиардам пользователей (статистика на 2008 год). Кодек GSM Half Rate (GSM-HR) — один из речевых кодеков, используемых в сетях GSM. GSM-HR обозначает речевой кодек с половинной скоростью, определённый в [TS46.002].
Note: For historical reasons, these 46-series specifications are internally referenced as 06-series. A simple mapping applies; for example, 46.020 is referenced as 06.20, and so on. The GSM-HR codec has a frame length of 20 ms, with narrowband speech sampled at 8000 Hz, i.e., 160 samples per frame. Each speech frame is compressed into 112 bits of speech parameters, which is equivalent to a bit rate of 5.6 kbit/s. Speech pauses are detected by a standardized Voice Activity Detection (VAD). During speech pauses, the transmission of speech frames is inhibited. Silence Descriptor (SID) frames are transmitted at the end of a talkspurt and about every 480 ms during speech pauses to allow for a decent comfort noise (CN) quality on the receiver side.
Примечание: по историческим причинам эти спецификации серии 46 внутри системы называются серией 06. Действует простое соответствие; например, 46.020 упоминается как 06.20 и так далее. Кодек GSM-HR имеет длину кадра 20 мс; узкополосная речь дискретизируется с частотой 8000 Гц, то есть 160 отсчётов на кадр. Каждый речевой кадр сжимается в 112 бит речевых параметров, что эквивалентно скорости передачи 5,6 кбит/с. Речевые паузы обнаруживаются стандартизованным детектором активности речи (VAD). Во время речевых пауз передача речевых кадров подавляется. Кадры дескриптора тишины (SID) передаются в конце периода речи и примерно каждые 480 мс во время речевых пауз, чтобы обеспечить достойное качество комфортного шума (CN) на стороне приёмника.
The SID frame generation in the GSM radio network is determined by the GSM mobile station and the GSM radio subsystem. SID frames come during speech pauses in the uplink from the mobile station about every 480 ms. In the downlink to the mobile station, when they are generated by the encoder of the GSM radio subsystem, SID frames are sent every 20 ms to the GSM base station, which then picks only one every 480 ms for downlink radio transmission. For other applications, like transport over IP, it is more appropriate to send the SID frames less often than every 20 ms, but 480 ms may be too sparse. We recommend as a compromise that a GSM-HR encoder outside of the GSM radio network (i.e., not in the GSM mobile station and not in the GSM radio subsystem, but, for example, in the media gateway of the core network) should generate and send SID frames every 160 ms.
Формирование кадров SID в радиосети GSM определяется мобильной станцией GSM и радиоподсистемой GSM. Кадры SID поступают во время речевых пауз в восходящем направлении от мобильной станции примерно каждые 480 мс. В нисходящем направлении к мобильной станции, когда они формируются кодером радиоподсистемы GSM, кадры SID отправляются каждые 20 мс на базовую станцию GSM, которая затем выбирает только один кадр из каждых 480 мс для передачи по радиоканалу вниз. Для других применений, например транспортировки по IP, более уместно отправлять кадры SID реже, чем каждые 20 мс, но 480 мс может быть слишком редко. В качестве компромисса мы рекомендуем, чтобы кодек GSM-HR вне радиосети GSM (то есть не в мобильной станции GSM и не в радиоподсистеме GSM, а, например, в медиашлюзе базовой сети) формировал и отправлял кадры SID каждые 160 мс.
4. Payload Format Capabilities
4. Возможности формата полезной нагрузки
This RTP payload format carries one or more GSM-HR encoded frames -- either full voice or silence descriptor (SID) -- representing a mono speech signal. To maintain synchronization or to indicate unsent or lost frames, it has the capability to indicate No_Data frames.
Данный формат полезной нагрузки RTP переносит один или несколько кадров, закодированных GSM-HR, — либо полный речевой кадр, либо дескриптор тишины (SID), — представляющих монофонический речевой сигнал. Для поддержания синхронизации или указания непереданных либо потерянных кадров он позволяет помечать кадры No_Data.
4.1. Use of Forward Error Correction (FEC)
4.1. Использование прямой коррекции ошибок (FEC)
Generic forward error correction within RTP is defined, for example, in RFC 5109 [RFC5109]. Audio redundancy coding is defined in RFC 2198 [RFC2198]. Either scheme can be used to add redundant information to the RTP packet stream and make it more resilient to packet losses, at the expense of a higher bit rate. Please see either RFC for a discussion of the implications of the higher bit rate to network congestion.
Общая прямая коррекция ошибок в RTP определена, например, в RFC 5109 [RFC5109]. Кодирование аудиоизбыточности определено в RFC 2198 [RFC2198]. Любая из этих схем может использоваться для добавления избыточной информации в поток пакетов RTP и повышения его устойчивости к потерям пакетов ценой более высокой скорости передачи. Обсуждение последствий повышенной скорости передачи для перегрузки сети см. в любом из этих RFC.
In addition to these media-unaware mechanisms, this memo specifies an optional-to-use GSM-HR-specific form of audio redundancy coding, which may be beneficial in terms of packetization overhead. Conceptually, previously transmitted transport frames are aggregated together with new ones. A sliding window can be used to group the frames to be sent in each payload. Концептуально ранее переданные транспортные кадры объединяются с новыми. Скользящее окно может использоваться для группировки кадров, отправляемых в каждой полезной нагрузке. The mechanism described does not really require signaling at the session setup. However, signaling has been defined to allow the sender to voluntarily bound the buffering and delay requirements. If nothing is signaled, the use of this mechanism is allowed and unbounded. For a certain timestamp, the receiver may acquire multiple copies of a frame containing encoded audio data. The cost of this scheme is bandwidth, and the receiver delay is necessary to allow the redundant copy to arrive.
Описанный механизм на самом деле не требует сигнализации при установке сеанса. Однако сигнализация определена, чтобы позволить отправителю добровольно ограничивать требования к буферизации и задержке. Если ничего не сигнализируется, использование этого механизма разрешено и не ограничено. Для определённой отметки времени приёмник может получить несколько копий кадра с закодированными аудиоданными. Стоимость этой схемы — полоса пропускания, а задержка приёмника необходима, чтобы избыточная копия успела прийти.
This redundancy scheme provides a functionality similar to the one described in RFC 2198, but it works only if both original frames and redundant representations are GSM-HR frames. When the use of other media coding schemes is desirable, one has to resort to RFC 2198.
Эта схема избыточности обеспечивает функциональность, аналогичную описанной в RFC 2198, но работает только в том случае, если и исходные кадры, и избыточные представления являются кадрами GSM-HR. Когда желательно использовать другие схемы кодирования медиа, приходится прибегать к RFC 2198.
The sender is responsible for selecting an appropriate amount of redundancy, based on feedback regarding the channel conditions, e.g., in the RTP Control Protocol (RTCP) [RFC3550] receiver reports. The sender is also responsible for avoiding congestion, which may be exacerbated by redundancy (see Section 9 for more details).
Отправитель отвечает за выбор подходящего объёма избыточности на основе обратной связи о состоянии канала, например в отчётах приёмника протокола управления RTP (RTCP) [RFC3550]. Отправитель также отвечает за предотвращение перегрузки, которая может усиливаться избыточностью (подробнее см. раздел 9).
5. Payload Format
5. Формат полезной нагрузки
The format of the RTP header is specified in [RFC3550]. The payload format described in this document uses the header fields in a manner consistent with that specification.
Формат заголовка RTP определён в [RFC3550]. Формат полезной нагрузки, описанный в настоящем документе, использует поля заголовка в соответствии с этой спецификацией.
The duration of one speech frame is 20 ms. The sampling frequency is 8000 Hz, corresponding to 160 speech samples per frame. An RTP packet may contain multiple frames of encoded speech or SID parameters. Each packet covers a period of one or more contiguous 20-ms frame intervals. During silence periods, no speech packets are sent; however, SID packets are transmitted every now and then.
Длительность одного речевого кадра — 20 мс. Частота дискретизации — 8000 Гц, что соответствует 160 речевым отсчётам на кадр. Пакет RTP может содержать несколько кадров закодированной речи или параметров SID. Каждый пакет охватывает период в один или несколько последовательных 20-мс интервалов кадров. В периоды тишины речевые пакеты не отправляются; однако пакеты SID передаются время от времени.
To allow for error resiliency through redundant transmission, the periods covered by multiple packets MAY overlap in time. A receiver MUST be prepared to receive any speech frame multiple times. A given frame MUST NOT be encoded as a speech frame in one packet and as a SID frame or as a No_Data frame in another packet. Furthermore, a given frame MUST NOT be encoded with different voicing modes in different packets.
Чтобы обеспечить устойчивость к ошибкам за счёт избыточной передачи, периоды, охватываемые несколькими пакетами, МОГУТ перекрываться во времени. Приёмник ДОЛЖЕН быть готов принять любой речевой кадр несколько раз. Данный кадр НЕ ДОЛЖЕН кодироваться как речевой кадр в одном пакете и как кадр SID или кадр No_Data в другом пакете. Кроме того, данный кадр НЕ ДОЛЖЕН кодироваться с разными режимами вокализации в разных пакетах.
The rules regarding maximum payload size given in Section 3.2 of [RFC5405] SHOULD be followed.
Следует соблюдать правила максимального размера полезной нагрузки, приведённые в разделе 3.2 [RFC5405].
5.1. RTP Header Usage
5.1. Использование заголовка RTP
The RTP timestamp corresponds to the sampling instant of the first sample encoded for the first frame in the packet. The timestamp clock frequency SHALL be 8000 Hz. The timestamp is also used to recover the correct decoding order of the frames.
Отметка времени RTP соответствует моменту дискретизации первого отсчёта, закодированного для первого кадра в пакете. Тактовая частота отметок времени ДОЛЖНА быть 8000 Гц. Отметка времени также используется для восстановления правильного порядка декодирования кадров.
The RTP header marker bit (M) SHALL be set to 1 whenever the first frame carried in the packet is the first frame in a talkspurt (see definition of the talkspurt in Section 4.1 of [RFC3551]). For all other packets, the marker bit SHALL be set to zero (M=0).
Бит-маркер (M) заголовка RTP ДОЛЖЕН устанавливаться в 1 всякий раз, когда первый кадр, переносимый в пакете, является первым кадром всплеска речи (определение всплеска речи см. в разделе 4.1 [RFC3551]). Для всех остальных пакетов бит-маркер ДОЛЖЕН устанавливаться в ноль (M=0).
The assignment of an RTP payload type for the format defined in this memo is outside the scope of this document. The RTP profiles in use currently mandate binding the payload type dynamically for this payload format.
Назначение типа полезной нагрузки RTP для формата, определённого в настоящем меморандуме, выходит за рамки настоящего документа. Используемые в настоящее время профили RTP предписывают динамическое связывание типа полезной нагрузки для этого формата полезной нагрузки.
The remaining RTP header fields are used as specified in RFC 3550 [RFC3550].
Остальные поля заголовка RTP используются так, как указано в RFC 3550 [RFC3550].

Они помечаются как «No_Data frame», если встречаются внутри пакета RTP, переносящего более одного речевого кадра, кадра SID или кадра No_Data.
5.2.1. Encoding of Speech Frames
5.2.1. Кодирование речевых кадров
The 112 bits of GSM-HR-coded speech (b1...b112) are defined in TS 46.020, Annex B [TS46.020], in their order of occurrence. The first bit (b1) of the first parameter is placed in the most significant bit (MSB) (bit 0) of the first octet (octet 1) of the payload field; the second bit is placed in bit 1 of the first octet; and so on. The last bit (b112) is placed in the least significant bit (LSB) (bit 7) of octet 14.
112 бит речи, закодированной GSM-HR (b1...b112), определены в TS 46.020, приложение B [TS46.020], в порядке их следования. Первый бит (b1) первого параметра помещается в старший бит (MSB) (бит 0) первого октета (октет 1) поля полезной нагрузки; второй бит помещается в бит 1 первого октета; и так далее. Последний бит (b112) помещается в младший бит (LSB) (бит 7) октета 14.
5.2.2. Encoding of Silence Description Frames
5.2.2. Кодирование кадров описания тишины
The GSM-HR codec applies a specific coding for silence periods in so- called SID frames. The coding of SID frames is based on the coding of speech frames by using only the first 33 bits for SID parameters and by setting all of the remaining 79 bits to "1".
Кодек GSM-HR применяет особое кодирование для периодов тишины в так называемых кадрах SID. Кодирование кадров SID основано на кодировании речевых кадров: используются только первые 33 бита для параметров SID, а все остальные 79 бит устанавливаются в «1».
5.3. Implementation Considerations
5.3. Вопросы реализации
An application implementing this payload format MUST understand all the payload parameters that are defined in this specification. Any mapping of the parameters to a signaling protocol MUST support all parameters. So an implementation of this payload format in an application using SDP is required to understand all the payload parameters in their SDP-mapped form. This requirement ensures that an implementation always can decide whether it is capable of communicating when the communicating entities support this version of the specification.
Приложение, реализующее этот формат полезной нагрузки, ДОЛЖНО понимать все параметры полезной нагрузки, определённые в настоящей спецификации. Любое отображение параметров в протокол сигнализации ДОЛЖНО поддерживать все параметры. Поэтому реализация этого формата полезной нагрузки в приложении, использующем SDP, обязана понимать все параметры полезной нагрузки в их отображённой на SDP форме. Это требование гарантирует, что реализация всегда может решить, способна ли она взаимодействовать, когда взаимодействующие стороны поддерживают эту версию спецификации.
5.3.1. Transmission of SID Frames
5.3.1. Передача кадров SID
When using this RTP payload format, the sender SHOULD generate and send SID frames every 160 ms, i.e., every 8th frame, during silent periods. Other SID transmission intervals may occur due to gateways to other systems that use other transmission intervals.
При использовании этого формата полезной нагрузки RTP отправитель ДОЛЖЕН формировать и отправлять кадры SID каждые 160 мс, то есть каждый 8-й кадр, в периоды тишины. Другие интервалы передачи SID могут возникать из-за шлюзов в другие системы, использующие иные интервалы передачи.
5.3.2. Receiving Redundant Frames
5.3.2. Приём избыточных кадров
The reception of redundant audio frames, i.e., more than one audio frame from the same source for the same time slot, MUST be supported by the implementation.
Приём избыточных аудиокадров, то есть более одного аудиокадра от одного и того же источника для одного и того же временного слота, ДОЛЖЕН поддерживаться реализацией.
5.3.3. Decoding Validation
5.3.3. Проверка декодирования
If the receiver finds a mismatch between the size of a received payload and the size indicated by the ToC of the payload, the receiver SHOULD discard the packet. This is recommended, because decoding a frame parsed from a payload based on erroneous ToC data could severely degrade the audio quality.
Если приёмник обнаруживает несоответствие между размером полученной полезной нагрузки и размером, указанным в ToC полезной нагрузки, приёмник ДОЛЖЕН отбросить пакет. Это рекомендуется, поскольку декодирование кадра, разобранного из полезной нагрузки на основе ошибочных данных ToC, может серьёзно ухудшить качество звука.

7.2.2. Declarative SDP Considerations
7.2.2. Вопросы декларативного SDP
In declarative usage, like SDP in the Real Time Streaming Protocol (RTSP) [RFC2326] or the Session Announcement Protocol (SAP) [RFC2974], the parameters SHALL be interpreted as follows: o The stream property parameter ("max-red") is declarative, and a participant MUST follow what is declared for the session. In this case, it means that the receiver MUST be prepared to allocate buffer memory for the given redundancy. Any transmissions MUST NOT use more redundancy than what has been declared. More than one configuration may be provided if necessary by declaring multiple RTP payload types; however, the number of types should be kept small.
При декларативном использовании, как, например, SDP в протоколе потоковой передачи в реальном времени (RTSP) [RFC2326] или в протоколе объявления сеансов (SAP) [RFC2974], параметры ДОЛЖНЫ интерпретироваться следующим образом: o Параметр свойства потока («max-red») является декларативным, и участник ДОЛЖЕН следовать тому, что объявлено для сеанса. В этом случае это означает, что приёмник ДОЛЖЕН быть готов выделить буферную память для заданной избыточности. Любые передачи НЕ ДОЛЖНЫ использовать больше избыточности, чем было объявлено. При необходимости может быть предоставлено более одной конфигурации путём объявления нескольких типов полезной нагрузки RTP; однако число типов следует держать небольшим.
o Any "maxptime" and "ptime" values should be selected with care to ensure that the session's participants can achieve reasonable performance.
o Значения «maxptime» и «ptime» следует выбирать осторожно, чтобы участники сеанса могли достичь разумной производительности.

9. Congestion Control
9. Управление перегрузкой
The general congestion control considerations for transporting RTP data apply; see RTP [RFC3550] and any applicable RTP profiles, e.g., "RTP/AVP" [RFC3551].
Применяются общие соображения по управлению перегрузкой при передаче данных RTP; см. RTP [RFC3550] и любые применимые профили RTP, например «RTP/AVP» [RFC3551].
The number of frames encapsulated in each RTP payload highly influences the overall bandwidth of the RTP stream due to header overhead constraints. Packetizing more frames in each RTP payload can reduce the number of packets sent and hence the header overhead, at the expense of increased delay and reduced error robustness. If forward error correction (FEC) is used, the amount of FEC-induced redundancy needs to be regulated such that the use of FEC itself does not cause a congestion problem.
Количество кадров, инкапсулированных в каждой полезной нагрузке RTP, сильно влияет на общую полосу пропускания потока RTP из-за накладных расходов заголовков. Пакетирование большего числа кадров в каждой полезной нагрузке RTP может уменьшить число отправляемых пакетов и, следовательно, накладные расходы заголовков, ценой увеличения задержки и снижения устойчивости к ошибкам. Если используется прямая коррекция ошибок (FEC), объём вносимой FEC избыточности необходимо регулировать так, чтобы использование самой FEC не вызывало проблем с перегрузкой.
10. Security Considerations
10. Вопросы безопасности
RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [RFC3550], and in any applicable RTP profile. The main security considerations for the RTP packet carrying the RTP payload format defined within this memo are confidentiality, integrity, and source authenticity. Confidentiality is achieved by encryption of the RTP payload, and integrity of the RTP packets through a suitable cryptographic integrity protection mechanism. A cryptographic system may also allow the authentication of the source of the payload. A suitable security mechanism for this RTP payload format should provide confidentiality, integrity protection, and at least source authentication capable of determining whether or not an RTP packet is from a member of the RTP session. Note that the appropriate mechanism to provide security to RTP and payloads following this may vary. It is dependent on the application, the transport, and the signaling protocol employed. Therefore, a single mechanism is not sufficient, although if suitable, the usage of the Secure Real-time Transport Protocol (SRTP) [RFC3711] is recommended. Other mechanisms that may be used are IPsec [RFC4301] and Transport Layer Security (TLS) [RFC5246] (e.g., for RTP over TCP), but other alternatives may also exist.
Пакеты RTP, использующие формат полезной нагрузки, определённый в настоящей спецификации, подпадают под действие соображений безопасности, обсуждаемых в спецификации RTP [RFC3550] и в любом применимом профиле RTP. Основными соображениями безопасности для пакета RTP, переносящего определённый в настоящем меморандуме формат полезной нагрузки, являются конфиденциальность, целостность и подлинность источника. Конфиденциальность достигается шифрованием полезной нагрузки RTP, а целостность пакетов RTP — подходящим механизмом криптографической защиты целостности. Криптографическая система может также обеспечивать аутентификацию источника полезной нагрузки. Подходящий механизм безопасности для этого формата полезной нагрузки должен обеспечивать конфиденциальность, защиту целостности и по крайней мере аутентификацию источника, позволяющую определить, является ли пакет RTP пакетом от участника сеанса RTP. Отметим, что подходящий механизм обеспечения безопасности RTP и следующей за ним полезной нагрузки может различаться. Он зависит от приложения, транспорта и используемого протокола сигнализации. Поэтому одного механизма недостаточно, хотя, если это уместно, рекомендуется использовать протокол Secure Real-time Transport Protocol (SRTP) [RFC3711]. Другими механизмами, которые могут использоваться, являются IPsec [RFC4301] и Transport Layer Security (TLS) [RFC5246] (например, для RTP поверх TCP), но возможны и иные альтернативы.
This RTP payload format and its media decoder do not exhibit any significant non-uniformity in the receiver-side computational complexity for packet processing, and thus are unlikely to pose a denial-of-service threat due to the receipt of pathological data; nor does the RTP payload format contain any active content.
Этот формат полезной нагрузки RTP и его медиадекодер не проявляют сколько-нибудь значительной неоднородности вычислительной сложности на стороне приёмника при обработке пакетов и поэтому вряд ли представляют угрозу отказа в обслуживании из-за получения патологических данных; формат полезной нагрузки RTP также не содержит активного содержимого.
