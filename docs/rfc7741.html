Abstract
Аннотация
This memo describes an RTP payload format for the VP8 video codec. The payload format has wide applicability, as it supports applications from low-bitrate peer-to-peer usage to high-bitrate video conferences.
В настоящем документе описан формат полезной нагрузки RTP для видеокодека VP8. Формат применим широко: он поддерживает приложения от низкобитрейтного обмена между равноправными узлами до видеоконференций с высоким битрейтом.

1. Introduction
1. Введение
This memo describes an RTP payload specification applicable to the transmission of video streams encoded using the VP8 video codec [RFC6386]. The format described in this document can be used both in peer-to-peer and video-conferencing applications.
В настоящем документе описана спецификация полезной нагрузки RTP, применимая для передачи видеопотоков, закодированных с помощью видеокодека VP8 [RFC6386]. Формат, описанный в настоящем документе, может использоваться как в приложениях «равный с равным», так и в видеоконференциях.
VP8 is based on the decomposition of frames into square sub-blocks of pixels known as "macroblocks" (see Section 2 of [RFC6386]). Prediction of such sub-blocks using previously constructed blocks, and adjustment of such predictions (as well as synthesis of unpredicted blocks) is done using a discrete cosine transform (hereafter abbreviated as DCT). In one special case, however, VP8 uses a "Walsh-Hadamard" transform (hereafter abbreviated as WHT) instead of a DCT. An encoded VP8 frame is divided into two or more partitions, as described in [RFC6386]. The first partition (prediction or mode) contains prediction mode parameters and motion vectors for all macroblocks. The remaining partitions all contain the quantized DCT/WHT coefficients for the residuals. There can be 1, 2, 4, or 8 DCT/WHT partitions per frame, depending on encoder settings.
VP8 основан на разложении кадров на квадратные субблоки пикселей, называемые «макроблоками» (см. раздел 2 [RFC6386]). Предсказание таких субблоков с использованием ранее построенных блоков и корректировка таких предсказаний (а также синтез непредсказанных блоков) выполняются с помощью дискретного косинусного преобразования (далее — DCT). В одном особом случае, однако, VP8 использует вместо DCT преобразование «Уолша — Адамара» (далее — WHT). Закодированный кадр VP8 делится на два или более раздела, как описано в [RFC6386]. Первый раздел (предсказания или режима) содержит параметры режима предсказания и векторы движения для всех макроблоков. Остальные разделы содержат квантованные коэффициенты DCT/WHT для остатков. В зависимости от настроек кодера на кадр может приходиться 1, 2, 4 или 8 разделов DCT/WHT.

3. Media Format Description
3. Описание формата медиаданных
The VP8 codec uses three different reference frames for interframe prediction: the previous frame, the golden frame, and the altref frame. Blocks in an interframe may be predicted using blocks in the immediately previous frame as well as the most recent golden frame or altref frame. Every key frame is automatically golden and altref, and any interframe may optionally replace the most recent golden or altref frame. Golden frames and altref frames may also be used to increase the tolerance to dropped frames. The payload specification in this memo has elements that enable advanced use of the reference frames, e.g., for improved loss robustness.
Кодек VP8 использует три различных опорных кадра для предсказания интеркадров: предыдущий кадр, golden-кадр и altref-кадр. Блоки в интеркадре могут предсказываться с использованием блоков в непосредственно предыдущем кадре, а также в самом последнем golden- или altref-кадре. Каждый ключевой кадр автоматически является golden- и altref-кадром, и любой интеркадр может необязательно заменять самый последний golden- или altref-кадр. Golden- и altref-кадры могут также использоваться для повышения устойчивости к отбрасыванию кадров. Спецификация полезной нагрузки в настоящем документе содержит элементы, обеспечивающие расширенное использование опорных кадров, например для повышения устойчивости к потерям.
One specific use case of the three reference frame types is temporal scalability. By setting up the reference hierarchy in the appropriate way, up to five temporal layers can be encoded. (How to set up the reference hierarchy for temporal scalability is not within the scope of this memo.) Support for temporal scalability is provided by the optional TL0PICIDX and TID/Y/KEYIDX fields described in Section 4.2. For a general description of temporal scalability for video coding, see [Sch07].
Одним из конкретных случаев использования трёх типов опорных кадров является временная масштабируемость. При надлежащей организации иерархии опорных кадров можно кодировать до пяти временных слоёв. (То, как организовать иерархию опорных кадров для временной масштабируемости, выходит за рамки настоящего документа.) Поддержка временной масштабируемости обеспечивается необязательными полями TL0PICIDX и TID/Y/KEYIDX, описанными в разделе 4.2. Общее описание временной масштабируемости для кодирования видео см. в [Sch07].
Another property of the VP8 codec is that it applies data partitioning to the encoded data. Thus, an encoded VP8 frame can be divided into two or more partitions, as described in "VP8 Data Format and Decoding Guide" [RFC6386]. The first partition (prediction or mode) contains prediction mode parameters and motion vectors for all macroblocks. The remaining partitions all contain the transform coefficients for the residuals. The first partition is decodable without the remaining residual partitions. The subsequent partitions may be useful even if some part of the frame is lost. Accordingly, this document RECOMMENDS that the frame be packetized by the sender with each data partition in a separate packet or packets. This may be beneficial for decoder-side error concealment, and the payload format described in Section 4 provides fields that allow the partitions to be identified even if the first partition is not available. The sender can, alternatively, aggregate the data partitions into a single data stream and, optionally, split it into several packets without consideration of the partition boundaries. The receiver can use the length information in the first partition to identify the partitions during decoding.
Другое свойство кодека VP8 состоит в том, что он применяет разделение данных к закодированным данным. Таким образом, закодированный кадр VP8 может быть разделён на два или более разделов, как описано в «VP8 Data Format and Decoding Guide» [RFC6386]. Первый раздел (предсказания или режима) содержит параметры режима предсказания и векторы движения для всех макроблоков. Остальные разделы содержат коэффициенты преобразования для остатков. Первый раздел декодируется без остальных разделов остатков. Последующие разделы могут быть полезны, даже если часть кадра потеряна. Соответственно, настоящий документ РЕКОМЕНДУЕТ, чтобы отправитель пакетизировал кадр так, чтобы каждый раздел данных находился в отдельном пакете или пакетах. Это может быть полезно для маскирования ошибок на стороне декодера, а формат полезной нагрузки, описанный в разделе 4, предоставляет поля, позволяющие идентифицировать разделы даже при отсутствии первого раздела. Отправитель может в качестве альтернативы объединить разделы данных в один поток данных и при необходимости разбить его на несколько пакетов без учёта границ разделов. Получатель может использовать информацию о длине в первом разделе для идентификации разделов при декодировании.
The format specification is described in Section 4. In Section 5, a method to acknowledge receipt of reference frames using RTCP techniques is described.
Спецификация формата описана в разделе 4. В разделе 5 описан метод подтверждения получения опорных кадров с использованием методов RTCP.
The payload partitioning and the acknowledging method both serve as motivation for three of the fields included in the payload format: the "PID", "1st partition size", and "PictureID" fields. The ability to encode a temporally scalable stream motivates the "TL0PICIDX" and "TID" fields.
Разделение полезной нагрузки и метод подтверждения служат мотивацией для трёх полей, включённых в формат полезной нагрузки: полей «PID», «1st partition size» и «PictureID». Возможность кодирования временно масштабируемого потока мотивирует поля «TL0PICIDX» и «TID».

4. Формат полезной нагрузки
This section describes how the encoded VP8 bitstream is encapsulated in RTP. To handle network losses, usage of RTP/AVPF [RFC4585] is RECOMMENDED. All integer fields in the specifications are encoded as unsigned integers in network octet order.
В настоящем разделе описано, как закодированный битовый поток VP8 инкапсулируется в RTP. Для обработки сетевых потерь РЕКОМЕНДУЕТСЯ использовать RTP/AVPF [RFC4585]. Все целочисленные поля в спецификациях кодируются как беззнаковые целые числа в сетевом порядке октетов.

The PictureID extension: If the I bit is set to 1, the PictureID extension field MUST be present, and it MUST NOT be present otherwise. The field consists of two parts:

Отправив 7-битный PictureID со всеми битами, установленными в 1, отправитель может либо перевести PictureID в 0, либо расширить до 15 бит и продолжать увеличивать.
The TL0PICIDX extension: If the L bit is set to 1, the TL0PICIDX extension field MUST be present, and it MUST NOT be present otherwise. The field consists of one part:
Расширение TL0PICIDX: если бит L установлен в 1, поле расширения TL0PICIDX ДОЛЖНО присутствовать, а в противном случае оно НЕ ДОЛЖНО присутствовать. Поле состоит из одной части:
TL0PICIDX: 8 bits temporal level zero index. TL0PICIDX is a running index for the temporal base layer frames, i.e., the frames with TID set to 0. If TID is larger than 0, TL0PICIDX indicates on which base-layer frame the current image depends. TL0PICIDX MUST be incremented when TID is 0. The index MAY start at a random value, and it MUST wrap to 0 after reaching the maximum number 255. Use of TL0PICIDX depends on the presence of TID. Therefore, it is RECOMMENDED that the TID be used whenever TL0PICIDX is.
TL0PICIDX: 8-битный индекс нулевого временного уровня. TL0PICIDX — это изменяющийся индекс для кадров базового временного слоя, то есть кадров с TID, установленным в 0. Если TID больше 0, TL0PICIDX указывает, от какого кадра базового слоя зависит текущее изображение. TL0PICIDX ДОЛЖЕН увеличиваться, когда TID равен 0. Индекс МОЖЕТ начинаться со случайного значения и ДОЛЖЕН переходить в 0 после достижения максимального числа 255. Использование TL0PICIDX зависит от наличия TID. Поэтому РЕКОМЕНДУЕТСЯ использовать TID всякий раз, когда используется TL0PICIDX.
The TID/Y/KEYIDX extension: If either of the T or K bits are set to 1, the TID/Y/KEYIDX extension field MUST be present. It MUST NOT be present if both T and K are zero. The field consists of three parts:
Расширение TID/Y/KEYIDX: если любой из битов T или K установлен в 1, поле расширения TID/Y/KEYIDX ДОЛЖНО присутствовать. Оно НЕ ДОЛЖНО присутствовать, если и T, и K равны нулю. Поле состоит из трёх частей:
TID: 2 bits temporal-layer index. The TID field MUST be ignored by the receiver when the T bit is set equal to 0. The TID field indicates which temporal layer the packet represents. The lowest layer, i.e., the base layer, MUST have the TID set to 0. Higher layers SHOULD increment the TID according to their position in the layer hierarchy.
TID: 2-битный индекс временного слоя. Поле TID ДОЛЖНО игнорироваться получателем, когда бит T установлен равным 0. Поле TID указывает, какой временной слой представляет пакет. Самый нижний слой, то есть базовый слой, ДОЛЖЕН иметь TID, установленный в 0. Более высокие слои СЛЕДУЕТ увеличивать TID в соответствии с их положением в иерархии слоёв.
Y: 1 layer sync bit. The Y bit SHOULD be set to 1 if the current frame depends only on the base layer (TID = 0) frame with TL0PICIDX equal to that of the current frame. The Y bit MUST be set to 0 if the current frame depends on any other frame than the base layer (TID = 0) frame with TL0PICIDX equal to that of the current frame. Additionally, the Y bit MUST be set to 0 if any frame following the current frame depends on a non- base-layer frame older than the base-layer frame with TL0PICIDX equal to that of the current frame. If the Y bit is set when the T bit is equal to 0, the current frame MUST only depend on a past base-layer (TID=0) key frame as signaled by a change in the KEYIDX field. Additionally, this frame MUST NOT depend on any of the three codec buffers (as defined by [RFC6386]) that have been updated since the last time the KEYIDX field was changed.
Y: 1 бит синхронизации слоя. Бит Y СЛЕДУЕТ устанавливать в 1, если текущий кадр зависит только от кадра базового слоя (TID = 0) с TL0PICIDX, равным TL0PICIDX текущего кадра. Бит Y ДОЛЖЕН быть установлен в 0, если текущий кадр зависит от любого другого кадра, кроме кадра базового слоя (TID = 0) с TL0PICIDX, равным TL0PICIDX текущего кадра. Кроме того, бит Y ДОЛЖЕН быть установлен в 0, если любой кадр, следующий за текущим кадром, зависит от кадра не базового слоя, более старого, чем кадр базового слоя с TL0PICIDX, равным TL0PICIDX текущего кадра. Если бит Y установлен, когда бит T равен 0, текущий кадр ДОЛЖЕН зависеть только от прошлого ключевого кадра базового слоя (TID=0), как сигнализируется изменением поля KEYIDX. Кроме того, этот кадр НЕ ДОЛЖЕН зависеть ни от одного из трёх буферов кодека (как определено в [RFC6386]), которые были обновлены с момента последнего изменения поля KEYIDX.
Informative note: This document does not describe how to determine the dependency status for a frame; this information is preferably provided from the encoder implementation. In the case of unknown status, the Y bit can safely be set to 0.
Информационное примечание: в настоящем документе не описано, как определить статус зависимости кадра; эта информация предпочтительно предоставляется реализацией кодера. В случае неизвестного статуса бит Y можно безопасно установить в 0.
KEYIDX: 5 bits temporal key frame index. The KEYIDX field MUST be ignored by the receiver when the K bit is set equal to 0. The KEYIDX field is a running index for key frames. KEYIDX MAY start at a random value, and it MUST wrap to 0 after reaching the maximum number 31. When in use, the KEYIDX SHOULD be present for both key frames and interframes. The sender MUST increment KEYIDX for key frames that convey parameter updates critical to the interpretation of subsequent frames, and it SHOULD leave the KEYIDX unchanged for key frames that do not contain these critical updates. If the KEYIDX is present, a receiver SHOULD NOT decode an interframe if it has not received and decoded a key frame with the same KEYIDX after the last KEYIDX wraparound.
KEYIDX: 5-битный индекс временного ключевого кадра. Поле KEYIDX ДОЛЖНО игнорироваться получателем, когда бит K установлен равным 0. Поле KEYIDX — это изменяющийся индекс для ключевых кадров. KEYIDX МОЖЕТ начинаться со случайного значения и ДОЛЖЕН переходить в 0 после достижения максимального числа 31. При использовании KEYIDX СЛЕДУЕТ присутствовать как для ключевых кадров, так и для интеркадров. Отправитель ДОЛЖЕН увеличивать KEYIDX для ключевых кадров, которые передают обновления параметров, критичные для интерпретации последующих кадров, и ему СЛЕДУЕТ оставлять KEYIDX неизменным для ключевых кадров, не содержащих этих критичных обновлений. Если KEYIDX присутствует, получателю НЕ СЛЕДУЕТ декодировать интеркадр, если он не получил и не декодировал ключевой кадр с тем же KEYIDX после последнего перехода KEYIDX через максимум.
Informative note: This document does not describe how to determine if a key frame updates critical parameters; this information is preferably provided from the encoder implementation. A sender that does not have this information may either omit the KEYIDX field (set K equal to 0) or increment the KEYIDX on every key frame. The benefit with the latter is that any key-frame loss will be detected by the receiver, which can signal for re-transmission or request a new key frame.
Информационное примечание: в настоящем документе не описано, как определить, обновляет ли ключевой кадр критичные параметры; эта информация предпочтительно предоставляется реализацией кодера. Отправитель, не располагающий этой информацией, может либо опустить поле KEYIDX (установить K равным 0), либо увеличивать KEYIDX на каждом ключевом кадре. Преимущество последнего состоит в том, что любая потеря ключевого кадра будет обнаружена получателем, который может сигнализировать о необходимости повторной передачи или запросить новый ключевой кадр.

If packetization of a frame is done without considering the partition boundaries, the PID field MAY be set to 0 for all packets and the S bit MUST NOT be set to 1 for any other packet than the first.

5. Using VP8 with RPSI and SLI Feedback
5. Использование VP8 с обратной связью RPSI и SLI
The VP8 payload descriptor defined in Section 4.2 contains an optional PictureID parameter. This parameter is included mainly to enable use of reference picture selection indication (RPSI) and slice loss indication (SLI), both defined in [RFC4585].
Дескриптор полезной нагрузки VP8, определённый в разделе 4.2, содержит необязательный параметр PictureID. Этот параметр включён главным образом для обеспечения использования индикации выбора опорного изображения (RPSI) и индикации потери слайса (SLI), обе определены в [RFC4585].
5.1. RPSI
5.1. RPSI
The RPSI is a payload-specific feedback message defined within the RTCP-based feedback format. The RPSI message is generated by a receiver and can be used in two ways. Either it can signal a preferred reference picture when a loss has been detected by the decoder -- preferably then a reference that the decoder knows is perfect -- or it can be used as positive feedback information to acknowledge correct decoding of certain reference pictures. The positive-feedback method is useful for VP8 used for point-to-point (unicast) communication. The use of RPSI for VP8 is preferably combined with a special update pattern of the codec's two special reference frames -- the golden frame and the altref frame -- in which they are updated in an alternating leapfrog fashion. When a receiver has received and correctly decoded a golden or altref frame, and that frame has a PictureID in the payload descriptor, the receiver can acknowledge this simply by sending an RPSI message back to the sender. The message body (i.e., the "native RPSI bit string" in [RFC4585]) is simply the PictureID of the received frame.
RPSI — это сообщение обратной связи, специфичное для полезной нагрузки, определённое в формате обратной связи на основе RTCP. Сообщение RPSI генерируется получателем и может использоваться двумя способами. Оно может либо сигнализировать о предпочтительном опорном изображении, когда декодером обнаружена потеря, — предпочтительно о таком опорном изображении, которое декодер считает идеальным, — либо использоваться как положительная информация обратной связи для подтверждения правильного декодирования определённых опорных изображений. Метод положительной обратной связи полезен для VP8 при связи «точка-точка» (одноадресной). Использование RPSI для VP8 предпочтительно сочетать со специальной схемой обновления двух особых опорных кадров кодека — golden-кадра и altref-кадра, — при которой они обновляются поочерёдно, «чехардой». Когда получатель получил и правильно декодировал golden- или altref-кадр и этот кадр имеет PictureID в дескрипторе полезной нагрузки, получатель может подтвердить это, просто отправив отправителю сообщение RPSI обратно. Тело сообщения (то есть «native RPSI bit string» в [RFC4585]) — это просто PictureID полученного кадра.

7. Security Considerations
7. Соображения безопасности
RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [RFC3550], and in any applicable RTP profile such as RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711], or RTP/ SAVPF [RFC5124]. However, as "Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution" [RFC7202] discusses, it is not an RTP payload format's responsibility to discuss or mandate what solutions are used to meet the basic security goals like confidentiality, integrity, and source authenticity for RTP in general. This responsibility lays on anyone using RTP in an application. They can find guidance on available security mechanisms and important considerations in "Options for Securing RTP Sessions" [RFC7201]. Applications SHOULD use one or more appropriate strong security mechanisms. The rest of this security consideration section discusses the security impacting properties of the payload format itself.
Пакеты RTP, использующие формат полезной нагрузки, определённый в настоящей спецификации, подпадают под действие соображений безопасности, рассмотренных в спецификации RTP [RFC3550], и в любом применимом профиле RTP, таком как RTP/AVP [RFC3551], RTP/AVPF [RFC4585], RTP/SAVP [RFC3711] или RTP/SAVPF [RFC5124]. Однако, как обсуждается в «Securing the RTP Protocol Framework: Why RTP Does Not Mandate a Single Media Security Solution» [RFC7202], формат полезной нагрузки RTP не обязан обсуждать или предписывать, какие решения используются для достижения базовых целей безопасности, таких как конфиденциальность, целостность и подлинность источника для RTP в целом. Эта ответственность лежит на любом, кто использует RTP в приложении. Они могут найти руководство по доступным механизмам безопасности и важным соображениям в «Options for Securing RTP Sessions» [RFC7201]. Приложениям СЛЕДУЕТ использовать один или несколько подходящих стойких механизмов безопасности. Остальная часть этого раздела о соображениях безопасности обсуждает влияющие на безопасность свойства самого формата полезной нагрузки.
This RTP payload format and its media decoder do not exhibit any significant difference in the receiver-side computational complexity for packet processing and, thus, are unlikely to pose a denial-of- service threat due to the receipt of pathological data. Nor does the RTP payload format contain any active content.
Этот формат полезной нагрузки RTP и его медиадекодер не демонстрируют значительных различий в вычислительной сложности обработки пакетов на стороне получателя и, таким образом, вряд ли создают угрозу отказа в обслуживании из-за получения патологических данных. Формат полезной нагрузки RTP также не содержит активного содержимого.
8. Congestion Control
8. Управление перегрузкой
Congestion control for RTP SHALL be used in accordance with RFC 3550 [RFC3550] and with any applicable RTP profile; e.g., RFC 3551 [RFC3551]. The congestion control mechanism can, in a real-time encoding scenario, adapt the transmission rate by instructing the encoder to encode at a certain target rate. Media-aware network elements MAY use the information in the VP8 payload descriptor in Section 4.2 to identify non-reference frames and discard them in order to reduce network congestion. Note that discarding of non- reference frames cannot be done if the stream is encrypted (because the non-reference marker is encrypted).
Управление перегрузкой для RTP ДОЛЖНО использоваться в соответствии с RFC 3550 [RFC3550] и любым применимым профилем RTP, например RFC 3551 [RFC3551]. В сценарии кодирования в реальном времени механизм управления перегрузкой может адаптировать скорость передачи, предписывая кодеру кодировать с определённой целевой скоростью. Сетевые элементы, учитывающие медиаданные, МОГУТ использовать информацию из дескриптора полезной нагрузки VP8 в разделе 4.2 для идентификации неопорных кадров и их отбрасывания с целью снижения перегрузки сети. Отметим, что отбрасывание неопорных кадров невозможно, если поток зашифрован (поскольку маркер неопорности зашифрован).
