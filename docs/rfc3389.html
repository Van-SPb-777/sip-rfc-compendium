Abstract
Аннотация
This document describes a Real-time Transport Protocol (RTP) payload format for transporting comfort noise (CN). The CN payload type is primarily for use with audio codecs that do not support comfort noise as part of the codec itself such as ITU-T Recommendations G.711, G.726, G.727, G.728, and G.722.
Настоящий документ описывает формат полезной нагрузки протокола передачи в реальном времени (RTP) для передачи комфортного шума (CN). Тип полезной нагрузки CN предназначен прежде всего для использования со звуковыми кодеками, которые не поддерживают комфортный шум как часть самого кодека, например с рекомендациями ITU-T G.711, G.726, G.727, G.728 и G.722.

2. Introduction
2. Введение
This document describes a RTP [1] payload format for transporting comfort noise. The payload format is based on Appendix II of ITU-T Recommendation G.711 [8] which defines a comfort noise payload format (or bit-stream) for ITU-T G.711 [2] use in packet-based multimedia communication systems. The payload format is generic and may also be used with other audio codecs without built-in Discontinuous Transmission (DTX) capability such as ITU-T Recommendations G.726 [3], G.727 [4], G.728 [5], and G.722 [6]. The payload format provides a minimum interoperability specification for communication of comfort noise parameters. The comfort noise analysis and synthesis as well as the Voice Activity Detection (VAD) and DTX algorithms are unspecified and left implementation-specific.
Настоящий документ описывает формат полезной нагрузки RTP [1] для передачи комфортного шума. Формат полезной нагрузки основан на Приложении II к рекомендации ITU-T G.711 [8], которое определяет формат полезной нагрузки (или битового потока) комфортного шума для использования с ITU-T G.711 [2] в системах мультимедийной связи на основе пакетов. Формат полезной нагрузки является универсальным и может также использоваться с другими звуковыми кодеками, не имеющими встроенной возможности прерывистой передачи (DTX), например с рекомендациями ITU-T G.726 [3], G.727 [4], G.728 [5] и G.722 [6]. Формат полезной нагрузки обеспечивает минимальную спецификацию совместимости для передачи параметров комфортного шума. Анализ и синтез комфортного шума, а также алгоритмы детектирования активности голоса (VAD) и DTX не определены и оставлены зависимыми от реализации.
However, an example solution for G.711 has been tested and is described in the Appendix [8]. It uses the VAD and DTX of G.729 Annex B [9] and a comfort noise generation algorithm (CNG) which is provided in the Appendix for information.
Однако пример решения для G.711 был проверен и описан в Приложении [8]. В нём используются VAD и DTX из Приложения B к G.729 [9] и алгоритм генерации комфортного шума (CNG), который приведён в Приложении для сведения.
The comfort noise payload, which is also known as a Silence Insertion Descriptor (SID) frame, consists of a single octet description of the noise level and MAY contain spectral information in subsequent octets. An earlier version of the CN payload format consisting only of the noise level byte was defined in draft revisions of the RFC 1890. The extended payload format defined in this document should be backward compatible with implementations of the earlier version assuming that only the first byte is interpreted and any additional spectral information bytes are ignored.
Полезная нагрузка комфортного шума, известная также как кадр дескриптора вставки тишины (SID), состоит из описания уровня шума в одном октете и МОЖЕТ содержать спектральную информацию в последующих октетах. Более ранняя версия формата полезной нагрузки CN, состоявшая только из байта уровня шума, была определена в черновых редакциях RFC 1890. Расширенный формат полезной нагрузки, определённый в настоящем документе, должен быть обратно совместим с реализациями более ранней версии при условии, что интерпретируется только первый байт, а любые дополнительные байты спектральной информации игнорируются.
3. CN Payload Definition
3. Определение полезной нагрузки CN
The comfort noise payload consists of a description of the noise level and spectral information in the form of reflection coefficients for an all-pole model of the noise. The inclusion of spectral information is OPTIONAL and the model order (number of coefficients) is left unspecified. The encoder may choose an appropriate model order based on such considerations as quality, complexity, expected environmental noise, and signal bandwidth. The model order is not explicitly transmitted since the number of coefficients can be derived from the length of the payload at the receiver. The decoder may reduce the model order by setting higher order reflection coefficients to zero if desired to reduce complexity or for other reasons.
Полезная нагрузка комфортного шума состоит из описания уровня шума и спектральной информации в виде коэффициентов отражения для всеполюсной модели шума. Включение спектральной информации НЕОБЯЗАТЕЛЬНО, а порядок модели (число коэффициентов) не определён. Кодер может выбрать подходящий порядок модели исходя из таких соображений, как качество, сложность, ожидаемый шум окружающей среды и полоса сигнала. Порядок модели явно не передаётся, поскольку число коэффициентов может быть выведено из длины полезной нагрузки на приёмнике. Декодер может уменьшить порядок модели, установив коэффициенты отражения старших порядков в ноль, если это желательно для снижения сложности или по иным причинам.
3.1. Noise Level
3.1. Уровень шума
The magnitude of the noise level is packed into the least significant bits of the noise-level byte with the most significant bit unused and always set to 0 as shown below in Figure 1. The least significant bit of the noise level magnitude is packed into the least significant bit of the byte.
Величина уровня шума упакована в младшие значащие биты байта уровня шума, а самый старший бит не используется и всегда устанавливается в 0, как показано ниже на рисунке 1. Самый младший бит величины уровня шума упакован в самый младший бит байта.
The noise level is expressed in -dBov, with values from 0 to 127 representing 0 to -127 dBov. dBov is the level relative to the overload of the system. (Note: Representation relative to the overload point of a system is particularly useful for digital implementations, since one does not need to know the relative calibration of the analog circuitry.) For example, in the case of a u-law system, the reference would be a square wave with values +/- 8031, and this square wave represents 0dBov. This translates into 6.18dBm0.
Уровень шума выражается в -dBov, причём значения от 0 до 127 представляют уровень от 0 до -127 dBov. dBov — это уровень относительно перегрузки системы. (Примечание: представление относительно точки перегрузки системы особенно удобно для цифровых реализаций, поскольку не требуется знать относительную калибровку аналоговой схемы.) Например, в случае системы с u-law опорным сигналом будет прямоугольная волна со значениями +/- 8031, и эта прямоугольная волна представляет 0 dBov. Это соответствует 6,18 dBm0.

3.2. Spectral Information
3.2. Спектральная информация
The spectral information is transmitted using reflection coefficients [8]. Each reflection coefficient can have values between -1 and 1 and is quantized uniformly using 8 bits. The quantized value is represented by the 8 bit index N, where N=0..,254, and index N=255 is reserved for future use. Each index N is packed into a separate byte with the MSB first. The quantized value of each reflection coefficient, k_i, can be obtained from its corresponding index using:
Спектральная информация передаётся с использованием коэффициентов отражения [8]. Каждый коэффициент отражения может принимать значения от -1 до 1 и квантуется равномерно с использованием 8 битов. Квантованное значение представляется 8-битным индексом N, где N=0..,254, а индекс N=255 зарезервирован для будущего использования. Каждый индекс N упаковывается в отдельный байт, начиная с самого старшего бита. Квантованное значение каждого коэффициента отражения k_i может быть получено из соответствующего индекса с помощью формулы:

4. Usage of RTP
4. Использование RTP
The RTP header for the comfort noise packet SHOULD be constructed as if the comfort noise were an independent codec. Thus, the RTP timestamp designates the beginning of the comfort noise period. When this payload format is used under the RTP profile specified in RFC 1890 [10], a static payload type of 13 is assigned for RTP timestamp clock rate of 8,000 Hz; if other rates are needed, they MUST be defined through dynamic payload types. The RTP packet SHOULD NOT have the marker bit set.
Заголовок RTP для пакета комфортного шума СЛЕДУЕТ формировать так, как если бы комфортный шум был независимым кодеком. Таким образом, временная метка RTP обозначает начало периода комфортного шума. Когда этот формат полезной нагрузки используется в рамках профиля RTP, определённого в RFC 1890 [10], для тактовой частоты временной метки RTP 8 000 Гц назначается статический тип полезной нагрузки 13; если требуются другие частоты, они ДОЛЖНЫ определяться через динамические типы полезной нагрузки. В пакете RTP НЕ СЛЕДУЕТ устанавливать бит маркера.
Each RTP packet containing comfort noise MUST contain exactly one CN payload per channel. This is required since the CN payload has a variable length. If multiple audio channels are used, each channel MUST use the same spectral model order 'M'.
Каждый пакет RTP, содержащий комфортный шум, ДОЛЖЕН содержать ровно одну полезную нагрузку CN на канал. Это необходимо, поскольку полезная нагрузка CN имеет переменную длину. При использовании нескольких звуковых каналов каждый канал ДОЛЖЕН использовать один и тот же спектральный порядок модели «M».
5. Guidelines for Use
5. Рекомендации по использованию
An audio codec with DTX capabilities generally includes VAD, DTX, and CNG algorithms. The job of the VAD is to discriminate between active and inactive voice segments in the input signal. During inactive voice segments, the role of the CNG is to sufficiently describe the ambient noise while minimizing the transmission rate. A CN payload (or SID frame) containing a description of the noise is sent to the receiver to drive the CNG. The DTX algorithm determines when a CN payload is transmitted. During active voice segments, packets of the voice codec are transmitted and indicated in the RTP header by the static or dynamic payload type for that codec. At the beginning of an inactive voice segment (silence period), a CN packet is transmitted in the same RTP stream and indicated by the CN payload type. The CN packet update rate is left implementation specific. For example, the CN packet may be sent periodically or only when there is a significant change in the background noise characteristics. The CNG algorithm at the receiver uses the information in the CN payload to update its noise generation model and then produce an appropriate amount of comfort noise.
Звуковой кодек с возможностями DTX обычно включает алгоритмы VAD, DTX и CNG. Задача VAD состоит в том, чтобы различать активные и неактивные речевые сегменты во входном сигнале. В течение неактивных речевых сегментов роль CNG заключается в достаточном описании окружающего шума при минимизации скорости передачи. Полезная нагрузка CN (или кадр SID), содержащая описание шума, отправляется приёмнику для управления CNG. Алгоритм DTX определяет, когда передаётся полезная нагрузка CN. В течение активных речевых сегментов передаются пакеты речевого кодека, обозначаемые в заголовке RTP статическим или динамическим типом полезной нагрузки для этого кодека. В начале неактивного речевого сегмента (периода тишины) пакет CN передаётся в том же потоке RTP и обозначается типом полезной нагрузки CN. Частота обновления пакетов CN оставлена зависящей от реализации. Например, пакет CN может отправляться периодически или только при существенном изменении характеристик фонового шума. Алгоритм CNG на приёмнике использует информацию в полезной нагрузке CN для обновления своей модели генерации шума, а затем формирует соответствующее количество комфортного шума.
The CN payload format provides a minimum interoperability specification for communication of comfort noise parameters. The comfort noise analysis and synthesis as well as the VAD and DTX algorithms are unspecified and left implementation-specific. However, an example solution for G.711 has been tested and is described in Appendix II of ITU-T Recommendation G.711 [8]. It uses the VAD and DTX of G.729 Annex B [9] and a comfort noise generation algorithm (CNG), which is provided in the Appendix for information. Additional guidelines for use such as the factors affecting system performance in the design of the VAD/DTX/CNG algorithms are described in the Appendix.
Формат полезной нагрузки CN обеспечивает минимальную спецификацию совместимости для передачи параметров комфортного шума. Анализ и синтез комфортного шума, а также алгоритмы VAD и DTX не определены и оставлены зависящими от реализации. Однако пример решения для G.711 был проверен и описан в Приложении II к рекомендации ITU-T G.711 [8]. В нём используются VAD и DTX из Приложения B к G.729 [9] и алгоритм генерации комфортного шума (CNG), который приведён в Приложении для сведения. Дополнительные рекомендации по использованию, такие как факторы, влияющие на производительность системы при проектировании алгоритмов VAD/DTX/CNG, описаны в Приложении.
5.1. Usage of SDP
5.1. Использование SDP
When using the Session Description Protocol (SDP) [11] to specify RTP payload information, the use of comfort noise is indicated by the inclusion of a payload type for CN on the media description line. When using CN with the RTP/AVP profile [10] and a codec whose RTP timestamp clock rate is 8000 Hz, such as G.711 (PCMU, static payload type 0), the static payload type 13 for CN can be used:
При использовании протокола описания сеансов (SDP) [11] для указания информации о полезной нагрузке RTP использование комфортного шума обозначается включением типа полезной нагрузки для CN в строку описания медиа. При использовании CN с профилем RTP/AVP [10] и кодеком, тактовая частота временной метки RTP которого равна 8000 Гц, например G.711 (PCMU, статический тип полезной нагрузки 0), может использоваться статический тип полезной нагрузки 13 для CN:
m=audio 49230 RTP/AVP 0 13
m=audio 49230 RTP/AVP 0 13
When using CN with a codec that has a different RTP timestamp clock rate, a dynamic payload type mapping (rtpmap attribute) is required.
При использовании CN с кодеком, имеющим другую тактовую частоту временной метки RTP, требуется динамическое отображение типа полезной нагрузки (атрибут rtpmap).
This example shows CN used with the G.722.1 codec (see RFC 3047 [12]):
В этом примере показано использование CN с кодеком G.722.1 (см. RFC 3047 [12]):
m=audio 49230 RTP/AVP 101 102 a=rtpmap:101 G7221/16000 a=fmtp:121 bitrate=24000 a=rtpmap:102 CN/16000
m=audio 49230 RTP/AVP 101 102 a=rtpmap:101 G7221/16000 a=fmtp:121 bitrate=24000 a=rtpmap:102 CN/16000
Omission of a payload type for CN on the media description line implies that this comfort noise payload format will not be used, but it does not imply that silence will not be suppressed. RTP allows discontinuous transmission (silence suppression) on any audio payload format. The receiver can detect silence suppression on the first packet received after the silence by observing that the RTP timestamp is not contiguous with the end of the interval covered by the previous packet even though the RTP sequence number has incremented only by one. The RTP marker bit is also normally set on such a packet.
Отсутствие типа полезной нагрузки для CN в строке описания медиа означает, что этот формат полезной нагрузки комфортного шума не будет использоваться, но не означает, что тишина не будет подавляться. RTP допускает прерывистую передачу (подавление тишины) для любого формата полезной нагрузки. Приёмник может обнаружить подавление тишины по первому пакету, полученному после тишины, заметив, что временная метка RTP не является непрерывной по отношению к концу интервала, охваченного предыдущим пакетом, хотя порядковый номер RTP увеличился только на единицу. На таком пакете обычно также устанавливается бит маркера RTP.

7. Security Considerations
7. Вопросы безопасности
RTP packets using the payload format defined in this specification are subject to the security considerations discussed in the RTP specification [1]. This implies that confidentiality of the media streams is achieved by encryption. Because the payload format is arranged end-to-end, encryption MAY be performed after encapsulation so there is no conflict between the two operations.
Пакеты RTP, использующие формат полезной нагрузки, определённый в настоящей спецификации, подпадают под соображения безопасности, рассмотренные в спецификации RTP [1]. Это означает, что конфиденциальность медиапотоков достигается шифрованием. Поскольку формат полезной нагрузки организован по принципу «из конца в конец», шифрование МОЖЕТ выполняться после инкапсуляции, так что конфликта между этими двумя операциями нет.
As this format transports background noise, there are no significant security, confidentiality, or authentication concerns.
Поскольку этот формат передаёт фоновый шум, существенных проблем безопасности, конфиденциальности или аутентификации не возникает.
