Abstract
Аннотация
This document defines a dialog event package for the SIP Events architecture, along with a data format used in notifications for this package. The dialog package allows users to subscribe to another user and to receive notification of the changes in state of INVITE- initiated dialog usages in which the subscribed-to user is involved.
В настоящем документе определяется пакет событий диалога для архитектуры событий SIP вместе с форматом данных, используемым в уведомлениях этого пакета. Пакет диалога позволяет пользователям подписываться на другого пользователя и получать уведомления об изменениях состояния используемых диалогов, инициированных INVITE, в которых участвует пользователь, на которого оформлена подписка.

1. Introduction
1. Общее введение
The SIP Events framework [1] defines general mechanisms for subscription to, and notification of, events within SIP networks. It introduces the notion of a package, which is a specific "instantiation" of the events mechanism for a well-defined set of events. Packages have been defined for user presence [16], watcher information [17], and message waiting indicators [18], amongst others. This document defines an event package for INVITE-initiated dialog usages. Dialogs refer to the SIP relationship established between two SIP peers [2]. Dialogs can be created by many methods, although RFC 3261 defines only one: the INVITE method. RFC 3265 [1] defines the SUBSCRIBE and NOTIFY methods, which also create new dialog usages. However, using this package to model state for non- session dialog usages is out of the scope of this specification.
Архитектура событий SIP [1] определяет общие механизмы подписки на события в сетях SIP и уведомления о них. В ней вводится понятие пакета — конкретного «экземпляра» механизма событий для чётко определённого набора событий. Пакеты были определены, среди прочего, для присутствия пользователя [16], информации наблюдателя [17] и индикаторов ожидания сообщений [18]. Настоящий документ определяет пакет событий для используемых диалогов, инициированных INVITE. Диалоги относятся к отношениям SIP, устанавливаемым между двумя участниками SIP [2]. Диалоги могут создаваться многими методами, хотя RFC 3261 определяет только один: метод INVITE. RFC 3265 [1] определяет методы SUBSCRIBE и NOTIFY, которые также создают новые использования диалога. Однако использование этого пакета для моделирования состояния использований диалога, не связанных с сессией, выходит за рамки настоящей спецификации.
A variety of applications are enabled through knowledge of INVITE dialog usage state. Some examples include:
Различные приложения становятся возможными благодаря знанию состояния использования диалога INVITE. Некоторые примеры:
Automatic Callback: In this basic Public Switched Telephone Network (PSTN) application, user A calls user B but User B is busy. User A would like to get a callback when user B hangs up. When B hangs up, user A's phone rings. When A picks up, they hear ringing, while they are being connected to B. To implement this with SIP, a mechanism is required for A to receive a notification when the dialogs at B are complete.
Автоматический обратный вызов: в этом базовом приложении коммутируемой телефонной сети общего пользования (PSTN) пользователь A звонит пользователю B, но пользователь B занят. Пользователь A хотел бы получить обратный вызов, когда пользователь B положит трубку. Когда B положит трубку, телефон A звонит. Когда A отвечает, он слышит звонок, пока его соединяют с B. Чтобы реализовать это в SIP, нужен механизм, позволяющий A получать уведомление о завершении диалогов у B.
Presence-Enabled Conferencing: In this application, user A wishes to set up a conference call with users B and C. Rather than being scheduled, the call is created automatically when A, B and C are all available. To do this, the server providing the application would like to know whether A, B, and C are "online", not idle, and not in a phone call. Determining whether or not A, B, and C are in calls can be done in two ways. In the first, the server acts as a call-stateful proxy for users A, B, and C, and therefore knows their call state. This won't always be possible, however, and it introduces scalability, reliability, and operational complexities. In the second way, the server subscribes to the dialog state of those users and receives notifications as this state changes.
Конференция с учётом присутствия: в этом приложении пользователь A хочет организовать конференц-вызов с пользователями B и C. Вместо планирования вызов создаётся автоматически, когда A, B и C доступны. Для этого серверу, предоставляющему приложение, хотелось бы знать, находятся ли A, B и C «в сети», не простаивают и не участвуют в телефонном вызове. Определить, участвуют ли A, B и C в вызовах, можно двумя способами. В первом сервер действует как прокси с учётом состояния вызовов для пользователей A, B и C и поэтому знает состояние их вызовов. Однако это не всегда возможно и вносит сложность в масштабирование, надёжность и эксплуатацию. Во втором способе сервер подписывается на состояние диалогов этих пользователей и получает уведомления при изменении этого состояния.
This enables the application to be provided in a distributed way; the server need not reside in the same domain as the users.
Это позволяет предоставлять приложение распределённым образом; серверу не нужно находиться в том же домене, что и пользователи.
IM Conference Alerts: In this application, a user can receive an Instant Message (IM) on their phone whenever someone joins a conference that the phone is involved in. The IM alerts are generated by an application separate from the conference server.
Оповещения конференции через IM: в этом приложении пользователь может получать мгновенное сообщение (IM) на свой телефон всякий раз, когда кто-либо присоединяется к конференции, в которой участвует телефон. Оповещения IM формируются приложением, отдельным от сервера конференции.
In general, the dialog package allows for construction of distributed applications, where the application requires information on dialog state but is not co-resident with the end user on which that state resides.
В целом пакет диалога позволяет строить распределённые приложения, когда приложению требуется информация о состоянии диалога, но оно не находится вместе с конечным пользователем, у которого это состояние имеется.

3. Пакет событий диалога

3.1. Event Package Name
3.1. Имя пакета событий
The name of this event package is "dialog". This package name is carried in the Event and Allow-Events header fields, as defined in [1].
Имя этого пакета событий — «dialog». Это имя пакета передаётся в полях заголовков Event и Allow-Events, как определено в [1].
3.2. Event Package Parameters
3.2. Параметры пакета событий
This package defines four Event Package parameters: call-id, to-tag, from-tag, and include-session-description. If a subscription to a specific dialog is requested, the first three of these parameters MUST be present, to identify the dialog that is being subscribed to. The to-tag is matched against the local tag, the from-tag is matched against the remote tag, and the call-id is matched against the Call-ID. The include-session-description parameter indicates whether the subscriber would like to receive the session descriptions associated with the subscribed dialog usage or usages. It is also possible to subscribe to the set of dialogs created as a result of a single INVITE sent by a UAC (user agent client). In that case, the call-id and to-tag MUST be present. The to-tag is matched against the local tag and the call-id is matched against the Call-ID.
Этот пакет определяет четыре параметра пакета событий: call-id, to-tag, from-tag и include-session-description. Если запрашивается подписка на конкретный диалог, первые три из этих параметров ДОЛЖНЫ присутствовать, чтобы идентифицировать диалог, на который оформляется подписка. Параметр to-tag сопоставляется с локальным тегом, from-tag — с удалённым тегом, а call-id — с Call-ID. Параметр include-session-description указывает, хотел бы подписчик получать описания сеансов, связанные с подписанным использованием или использованиями диалога. Также можно подписаться на набор диалогов, созданных в результате одного INVITE, отправленного UAC (клиентом пользовательского агента). В этом случае параметры call-id и to-tag ДОЛЖНЫ присутствовать. Параметр to-tag сопоставляется с локальным тегом, а call-id — с Call-ID.
The ABNF for these parameters is shown below. It refers to many constructions from the ABNF of RFC3261, such as EQUAL, DQUOTE, and token.
ABNF этих параметров показан ниже. Он ссылается на многие конструкции из ABNF RFC 3261, такие как EQUAL, DQUOTE и token.
call-id = "call-id" EQUAL ( token / DQUOTE callid DQUOTE ) ;; NOTE: any DQUOTEs inside callid MUST be escaped! from-tag = "from-tag" EQUAL token to-tag = "to-tag" EQUAL token with-sessd = "include-session-description"
call-id = "call-id" EQUAL ( token / DQUOTE callid DQUOTE ) ;; NOTE: any DQUOTEs inside callid MUST be escaped! from-tag = "from-tag" EQUAL token to-tag = "to-tag" EQUAL token with-sessd = "include-session-description"
If any call-ids contain embedded double-quotes, those double-quotes MUST be escaped using the backslash-quoting mechanism. Note that the call-id parameter may need to be expressed as a quoted string. This is because the ABNF for the callid production and the word production, which is used by callid (both from RFC 3261 [1]), allow some characters (such as "@", "[", and ":") that are not allowed within a token.
Если какие-либо call-id содержат встроенные двойные кавычки, эти двойные кавычки ДОЛЖНЫ быть экранированы с помощью механизма обратной косой черты. Обратите внимание, что параметр call-id может потребоваться выразить в виде строки в кавычках. Это связано с тем, что ABNF для продукции callid и продукции word, которая используется callid (обе из RFC 3261 [1]), допускают некоторые символы (например, «@», «[» и «:»), не разрешённые внутри token.

3.4. Subscription Duration
3.4. Длительность подписки
Dialog state changes fairly quickly. Once established, a typical phone call lasts a few minutes (this is different for other session types, of course). However, the interval between new calls is typically long. Clients SHOULD specify an explicit duration.
Состояние диалога меняется довольно быстро. После установления типичный телефонный вызов длится несколько минут (для других типов сеансов это, конечно, иначе). Однако интервал между новыми вызовами обычно велик. Клиенты ДОЛЖНЫ указывать явную длительность.
There are two distinct use cases for dialog state. The first is when a subscriber is interested in the state of a specific dialog or dialogs (and they are authorized to find out just the state of those dialogs). In that case, when the dialogs terminate, so too does the subscription. In these cases, the value of the subscription duration is largely irrelevant; it SHOULD be longer than the typical duration of a dialog. We recommend a default duration of two hours, which is likely to cover most dialogs.
Существуют два различных варианта использования состояния диалога. Первый — когда подписчик заинтересован в состоянии конкретного диалога или диалогов (и уполномочен узнать только состояние этих диалогов). В этом случае при завершении диалогов завершается и подписка. В таких случаях значение длительности подписки в значительной степени не имеет значения; оно ДОЛЖНО быть больше типичной длительности диалога. Мы рекомендуем длительность по умолчанию два часа, что, вероятно, покроет большинство диалогов.
In another case, a subscriber is interested in the state of all dialogs for a specific user. In these cases, a shorter interval makes more sense. The default is one hour for these subscriptions.
В другом случае подписчик заинтересован в состоянии всех диалогов конкретного пользователя. В этих случаях более разумным является меньший интервал. По умолчанию для таких подписок используется один час.
3.5. NOTIFY Bodies
3.5. Тела NOTIFY
As described in RFC 3265 [1], the NOTIFY message will contain bodies that describe the state of the subscribed resource. This body is in a format listed in the Accept header field of the SUBSCRIBE, or in a package-specific default format if the Accept header field was omitted from the SUBSCRIBE.
Как описано в RFC 3265 [1], сообщение NOTIFY будет содержать тела, описывающие состояние ресурса, на который оформлена подписка. Это тело имеет формат, перечисленный в поле заголовка Accept запроса SUBSCRIBE, или формат по умолчанию, специфичный для пакета, если поле заголовка Accept в SUBSCRIBE отсутствовало.
In this event package, the body of the notification contains a dialog information document. This document describes the state of one or more dialogs associated with the subscribed resource. All subscribers and notifiers MUST support the "application/ dialog-info+xml" data format described in Section 4. The subscribe request MAY contain an Accept header field. If no such header field is present, it has a default value of "application/dialog-info+xml". If the header field is present, it MUST include "application/ dialog-info+xml", and it MAY include any other types capable of representing dialog state.
В этом пакете событий тело уведомления содержит документ информации о диалогах. Этот документ описывает состояние одного или нескольких диалогов, связанных с ресурсом, на который оформлена подписка. Все подписчики и уведомители ДОЛЖНЫ поддерживать формат данных «application/dialog-info+xml», описанный в разделе 4. Запрос SUBSCRIBE МОЖЕТ содержать поле заголовка Accept. Если такое поле заголовка отсутствует, оно имеет значение по умолчанию «application/dialog-info+xml». Если поле заголовка присутствует, оно ДОЛЖНО включать «application/dialog-info+xml» и МОЖЕТ включать любые другие типы, способные представлять состояние диалога.
Of course, the notifications generated by the server MUST be in one of the formats specified in the Accept header field in the SUBSCRIBE request.
Разумеется, уведомления, формируемые сервером, ДОЛЖНЫ быть в одном из форматов, указанных в поле заголовка Accept запроса SUBSCRIBE.
3.6. Notifier Processing of SUBSCRIBE Requests
3.6. Обработка запросов SUBSCRIBE уведомителем
The dialog information for a user contains sensitive information. Therefore, all subscriptions SHOULD be authenticated and then authorized before approval. All implementors of this package MUST support the digest authentication mechanism as a baseline. The authorization policy is at the discretion of the administrator, as always. However, a few recommendations can be made.
Информация о диалогах пользователя содержит конфиденциальные сведения. Поэтому все подписки ДОЛЖНЫ быть аутентифицированы, а затем авторизованы до одобрения. Все реализующие этот пакет ДОЛЖНЫ поддерживать механизм дайджест-аутентификации в качестве базового. Политика авторизации, как всегда, остаётся на усмотрение администратора. Тем не менее можно дать несколько рекомендаций.
It is RECOMMENDED that, if the policy of user B is that user A is allowed to call them, dialog subscriptions from user A be allowed. However, the information provided in the notifications does not contain any dialog identification information, merely an indication of whether the user is in at least one call. Specifically, they should not be able to find out any more information than if they sent an INVITE. (This concept of a "virtual" dialog is discussed more in Section 3.7.2, and an example of such a notification body is shown below).
РЕКОМЕНДУЕТСЯ, чтобы, если политика пользователя B разрешает пользователю A звонить ему, подписки пользователя A на диалоги были разрешены. Однако информация, предоставляемая в уведомлениях, не содержит идентификационной информации о диалоге, а лишь указание, участвует ли пользователь хотя бы в одном вызове. В частности, они не должны иметь возможности узнать больше, чем если бы отправили INVITE. (Эта концепция «виртуального» диалога более подробно обсуждается в разделе 3.7.2, а пример такого тела уведомления показан ниже).
<?xml version="1.0"?> <dialog-info xmlns="urn:ietf:params:xml:ns:dialog-info" version="0" state="full" entity="sip:alice@example.com"> <dialog id="as7d900as8"> <state>confirmed</state> </dialog> </dialog-info>

A user agent that registers with the address-of-record X SHOULD authorize subscriptions that come from any entity that can authenticate itself as X. Complete information on the dialog state SHOULD be sent in this case. This authorization behavior allows a group of devices representing a single user to become aware of each other's state. This is useful for applications such as single-line-extension, also known as shared lines. Note that many implementations of "shared-lines" have a feature that allows details of calls on a shared address-of-record to be made private. This is a completely reasonable authorization policy that could result in notifications that contain only the id attribute of the dialog element and the state element when shared-line privacy is requested, and notifications with more complete information when shared-line privacy is not requested.
Пользовательский агент, регистрирующийся с address-of-record X, ДОЛЖЕН авторизовывать подписки, поступающие от любой сущности, способной аутентифицироваться как X. В этом случае ДОЛЖНА отправляться полная информация о состоянии диалога. Такое поведение авторизации позволяет группе устройств, представляющих одного пользователя, узнавать состояние друг друга. Это полезно для таких приложений, как расширение одной линии, также известное как общие линии. Обратите внимание, что многие реализации «общих линий» имеют функцию, позволяющую делать сведения о вызовах на общем address-of-record закрытыми. Это совершенно разумная политика авторизации, которая может приводить к уведомлениям, содержащим только атрибут id элемента dialog и элемент state, когда запрошена конфиденциальность общей линии, и к уведомлениям с более полной информацией, когда конфиденциальность общей линии не запрошена.
3.7. Notifier Generation of NOTIFY Requests
3.7. Генерация запросов NOTIFY уведомителем
Notifications are generated for the dialog package when an INVITE request is sent, when a new dialog comes into existence at a UA, or when the state or characteristics of an existing dialog changes. Therefore, a model of dialog state is needed in order to determine precisely when to send notifications, and what their content should be. The SIP specification has a reasonably well defined lifecycle for dialogs. However, it is not explicitly modelled. This specification provides an explicit model of dialog state through a finite state machine.
Уведомления для пакета диалога формируются при отправке запроса INVITE, при возникновении нового диалога в UA или при изменении состояния или характеристик существующего диалога. Поэтому для точного определения момента отправки уведомлений и их содержания необходима модель состояния диалога. Спецификация SIP имеет достаточно хорошо определённый жизненный цикл для диалогов. Однако он явно не смоделирован в ней. Эта спецификация обеспечивает явную модель состояния диалога посредством конечного автомата.
It is RECOMMENDED that NOTIFY requests only contain information on the dialogs whose state or participation information has changed. However, if a notifier receives a SUBSCRIBE request, the triggered NOTIFY SHOULD contain the state of all dialogs that the subscriber is authorized to see.
РЕКОМЕНДУЕТСЯ, чтобы запросы NOTIFY содержали информацию только о тех диалогах, состояние или информация об участии которых изменились. Однако если уведомитель получает запрос SUBSCRIBE, NOTIFY, вызванный этим запросом, ДОЛЖЕН содержать состояние всех диалогов, которые подписчик уполномочен видеть.
3.7.1. The Dialog State Machine
3.7.1. Автомат состояний диалога
Modelling of dialog state is complicated by two factors. The first is forking, which can cause a single INVITE to generate many dialogs at a UAC. The second is the differing views of state at the UAC (user agent client) and UAS (usage agent server). We have chosen to handle the first issue by extending the dialog finite state machine (FSM) to include the states between transmission of the INVITE and the creation of actual dialogs through receipt of 1xx and 2xx responses. As a result, this specification supports the notion of dialog state for dialogs before they are fully instantiated.
Моделирование состояния диалога осложняется двумя факторами. Первый — разветвление (forking), которое может заставить один INVITE породить множество диалогов у UAC. Второй — различающиеся представления состояния у UAC (клиента пользовательского агента) и UAS (сервера пользовательского агента). Мы решили первую проблему, расширив конечный автомат (FSM) диалога, включив в него состояния между отправкой INVITE и созданием фактических диалогов при получении ответов 1xx и 2xx. В результате настоящая спецификация поддерживает понятие состояния диалога для диалогов до их полного создания.
We have also chosen to use a single FSM for both UAC and UAS.
Мы также решили использовать единый FSM как для UAC, так и для UAS.

The FSM for dialog state is shown in Figure 3. The FSM is best understood by considering the UAC and UAS cases separately. The FSM is created in the Trying state when the UAC sends an INVITE request. Upon receipt of a 1xx without a tag, the FSM transitions to the Proceeding state. Note that there is no actual dialog yet, as defined by the SIP specification. However, there is a "half-dialog", in the sense that two of the three components of the dialog ID (the call identifier and local tag) are known. If a 1xx with a tag is received, the FSM transitions to the Early state. The full dialog identifier is now defined. Had a 2xx been received, the FSM would have transitioned to the Confirmed state.
FSM состояния диалога показан на рисунке 3. FSM лучше всего понять, рассматривая случаи UAC и UAS по отдельности. FSM создаётся в состоянии Trying, когда UAC отправляет запрос INVITE. При получении 1xx без тега FSM переходит в состояние Proceeding. Обратите внимание, что фактического диалога, как он определён в спецификации SIP, ещё нет. Однако существует «полудиалог» в том смысле, что известны два из трёх компонентов идентификатора диалога (идентификатор вызова и локальный тег). Если получен 1xx с тегом, FSM переходит в состояние Early. Теперь определён полный идентификатор диалога. Если бы был получен 2xx, FSM перешёл бы в состояние Confirmed.
If, after transitioning to the Early or Confirmed states, the UAC receives another 1xx or 2xx respectively with a different tag, another instance of the FSM is created, initialized into the Early or Confirmed state, respectively. The benefit of this approach is that there will be a single FSM representing the entire state of the invitation and resulting dialog when dealing in the common case of no forking.
Если после перехода в состояния Early или Confirmed UAC получает ещё один 1xx или 2xx соответственно с другим тегом, создаётся другой экземпляр FSM, инициализируемый в состоянии Early или Confirmed соответственно. Преимущество этого подхода в том, что в обычном случае без разветвления будет существовать единый FSM, представляющий всё состояние приглашения и результирующего диалога.
If the UAC sends a CANCEL and then subsequently receives a 487 to its INVITE transaction, all FSMs spawned from that INVITE transition to the Terminated state with the event "cancelled". If the UAC receives a new invitation (with a Replaces [13] header) that replaces the current Early or Confirmed dialog, all INVITE transactions spawned from the replaced invitation transition to the Terminated state with the event "replaced". If the INVITE transaction terminates with a non-2xx response for any other reason, all FSMs spawned from that INVITE transition to the Terminated state with the event "rejected".
Если UAC отправляет CANCEL и затем получает 487 в своей транзакции INVITE, все FSM, порождённые этим INVITE, переходят в состояние Terminated с событием «cancelled». Если UAC получает новое приглашение (с полем заголовка Replaces [13]), заменяющее текущий диалог Early или Confirmed, все транзакции INVITE, порождённые заменённым приглашением, переходят в состояние Terminated с событием «replaced». Если транзакция INVITE завершается ответом, отличным от 2xx, по любой другой причине, все FSM, порождённые этим INVITE, переходят в состояние Terminated с событием «rejected».
Once in the Confirmed state, the call is active. It can transition to the Terminated state if the UAC sends a BYE or receives a BYE (corresponding to the "local-bye" and "remote-bye" events as appropriate), if a mid-dialog request generates a 481 or 408 response (corresponding to the "error" event), or a mid-dialog request generates no response (corresponding to the "timeout" event).
После перехода в состояние Confirmed вызов активен. Он может перейти в состояние Terminated, если UAC отправляет BYE или получает BYE (соответствуя событиям «local-bye» и «remote-bye»), если запрос внутри диалога порождает ответ 481 или 408 (соответствуя событию «error»), или если запрос внутри диалога не порождает ответа (соответствуя событию «timeout»).
From the perspective of the UAS, when an INVITE is received, the FSM is created in the Trying state. If it sends a 1xx without a tag, the FSM transitions to the Proceeding state. If a 1xx is sent with a tag, the FSM transitions to the Early state, and if a 2xx is sent, it transitions to the Confirmed state. If the UAS receives a CANCEL request and then generates a 487 response to the INVITE (which can occur in the Proceeding and Early states), the FSM transitions to the Terminated state with the event "cancelled". If the UAS generates any other non-2xx final response to the INVITE request, the FSM transitions to the Terminated state with the event "rejected". If the UAS receives a new invitation (with a Replaces [13] header field) that replaces the current Confirmed dialog, the replaced invitation transitions to the Terminated state with the event "replaced". Once in the Confirmed state, the other transitions to the Terminated state occur for the same reasons they do in the case of UAC.
С точки зрения UAS, при получении INVITE FSM создаётся в состоянии Trying. Если он отправляет 1xx без тега, FSM переходит в состояние Proceeding. Если отправляется 1xx с тегом, FSM переходит в состояние Early, а если отправляется 2xx — в состояние Confirmed. Если UAS получает запрос CANCEL и затем формирует ответ 487 на INVITE (что может произойти в состояниях Proceeding и Early), FSM переходит в состояние Terminated с событием «cancelled». Если UAS формирует любой другой окончательный ответ, отличный от 2xx, на запрос INVITE, FSM переходит в состояние Terminated с событием «rejected». Если UAS получает новое приглашение (с полем заголовка Replaces [13]), заменяющее текущий диалог Confirmed, заменённое приглашение переходит в состояние Terminated с событием «replaced». После перехода в состояние Confirmed другие переходы в состояние Terminated происходят по тем же причинам, что и в случае UAC.
There should never be a transition from the Trying state to the Terminated state with the event "cancelled", since the SIP specification prohibits transmission of CANCEL until a provisional response is received. However, this transition is defined in the FSM just to unify the transitions from Trying, Proceeding, and Early states to the Terminated state.
Никогда не должно происходить перехода из состояния Trying в состояние Terminated с событием «cancelled», поскольку спецификация SIP запрещает передачу CANCEL до получения предварительного ответа. Однако этот переход определён в FSM лишь для унификации переходов из состояний Trying, Proceeding и Early в состояние Terminated.
3.7.2. Applying the State Machine
3.7.2. Применение конечного автомата
The notifier MAY generate a NOTIFY request on any event transition of the FSM. Whether it does or not is policy dependent. However, some general guidelines are provided.
Уведомитель МОЖЕТ формировать запрос NOTIFY при любом переходе события FSM. Будет он это делать или нет, зависит от политики. Однако некоторые общие рекомендации приведены.
When the subscriber is unauthenticated, or it is authenticated but represents a third party with no specific authorization policies, it is RECOMMENDED that subscriptions to an individual dialog or to a specific set of dialogs be forbidden. Only subscriptions to all dialogs (i.e., there are no dialog identifiers in the Event header field) are permitted. In that case, actual dialog states across all dialogs will not be reported. Rather, a single "virtual" dialog FSM will be used, and event transitions on that FSM will be reported.
Когда подписчик не аутентифицирован или аутентифицирован, но представляет третью сторону без конкретных политик авторизации, РЕКОМЕНДУЕТСЯ запрещать подписки на отдельный диалог или на конкретный набор диалогов. Разрешаются только подписки на все диалоги (т. е. в поле заголовка Event нет идентификаторов диалогов). В этом случае фактические состояния отдельных диалогов по всем диалогам сообщаться не будут. Вместо этого будет использоваться единый FSM «виртуального» диалога, и будут сообщаться переходы событий этого FSM.
If there is any dialog at the UA whose state is Confirmed, the virtual FSM is in the Confirmed state. If there are no dialogs at the UA in the Confirmed state but there is at least one in the Early state, the virtual FSM is in the Early or Confirmed state. If there are no dialogs in the Confirmed or Early states but there is at least one in the Proceeding state, the virtual FSM is in the Proceeding, Early, or Confirmed state. If there are no dialogs in the Confirmed, Early, or Proceeding states but there is at least one in the Trying state, the virtual FSM is in the Trying, Proceeding, Early or Confirmed state. The choice of state to use depends on whether the UA wishes to let unknown users know that their phone is ringing, as opposed to being in an active call.
Если в UA есть какой-либо диалог в состоянии Confirmed, виртуальный FSM находится в состоянии Confirmed. Если в UA нет диалогов в состоянии Confirmed, но есть хотя бы один в состоянии Early, виртуальный FSM находится в состоянии Early или Confirmed. Если нет диалогов в состояниях Confirmed или Early, но есть хотя бы один в состоянии Proceeding, виртуальный FSM находится в состоянии Proceeding, Early или Confirmed. Если нет диалогов в состояниях Confirmed, Early или Proceeding, но есть хотя бы один в состоянии Trying, виртуальный FSM находится в состоянии Trying, Proceeding, Early или Confirmed. Выбор используемого состояния зависит от того, хочет ли UA сообщать неизвестным пользователям, что их телефон звонит, а не что идёт активный вызов.
It is RECOMMENDED that, in the absence of any preference, Confirmed is used in all cases as shown in the example in Section 3.6. Furthermore, it is RECOMMENDED that the notifications of changes in the virtual FSM machine not convey any information except the state of the FSM and its event transitions - no dialog identifiers (which are ill-defined in this model in any case). The use of this virtual FSM allows minimal information to be conveyed. A subscriber cannot know how many calls are in progress, or with whom, just that there exists a call. This is the same information they would receive if they simply sent an INVITE to the user instead; a 486 (Busy Here) response would indicate that they are on a call.
РЕКОМЕНДУЕТСЯ, чтобы при отсутствии каких-либо предпочтений во всех случаях использовалось состояние Confirmed, как показано в примере в разделе 3.6. Кроме того, РЕКОМЕНДУЕТСЯ, чтобы уведомления об изменениях в виртуальном FSM не передавали никакой информации, кроме состояния FSM и его переходов событий, — никаких идентификаторов диалогов (которые в этой модели в любом случае определены нечётко). Использование этого виртуального FSM позволяет передавать минимальную информацию. Подписчик не может узнать, сколько вызовов выполняется или с кем, а лишь то, что вызов существует. Это та же информация, которую он получил бы, просто отправив пользователю INVITE; ответ 486 (Busy Here) указывал бы, что пользователь разговаривает.
When the subscriber is authenticated and has authenticated itself with the same address-of-record that the UA itself uses, if no explicit authorization policy is defined, it is RECOMMENDED that all state transitions on dialogs that have been subscribed to be reported, along with complete dialog IDs. This means either all of the dialogs, if no dialog identifiers were present in the Event header field, or the specific set of dialogs identified by the Event header field parameters.
Когда подписчик аутентифицирован и аутентифицировал себя с тем же address-of-record, который использует сам UA, если явная политика авторизации не определена, РЕКОМЕНДУЕТСЯ сообщать все переходы состояний по диалогам, на которые была оформлена подписка, вместе с полными идентификаторами диалогов. Это означает либо все диалоги, если в поле заголовка Event не было идентификаторов диалогов, либо конкретный набор диалогов, идентифицированный параметрами поля заголовка Event.
The notifier SHOULD generate a NOTIFY request on any change in the characteristics associated with the dialog. Since these include Contact URIs, Contact parameters, and session descriptions, receipt of re-INVITEs and UPDATE requests [3] that modify this information MAY trigger notifications.
Уведомитель ДОЛЖЕН формировать запрос NOTIFY при любом изменении характеристик, связанных с диалогом. Поскольку они включают целевые URI Contact, параметры Contact и описания сеансов, получение повторных INVITE и запросов UPDATE [3], изменяющих эту информацию, МОЖЕТ инициировать уведомления.
3.8. Subscriber Processing of NOTIFY Requests
3.8. Обработка запросов NOTIFY подписчиком
The SIP Events framework expects packages to specify how a subscriber processes NOTIFY requests in package-specific ways. In particular, a package should specify how it uses the NOTIFY requests to construct a coherent view of the state of the subscribed resource.
Архитектура событий SIP ожидает, что пакеты определят, как подписчик обрабатывает запросы NOTIFY способами, специфичными для пакета. В частности, пакет должен определить, как он использует запросы NOTIFY для построения согласованного представления состояния ресурса, на который оформлена подписка.
Typically, the NOTIFY for the dialog package will contain information about only those dialogs whose state has changed. To construct a coherent view of the total state of all dialogs, a subscriber to the dialog package will need to combine NOTIFYs received over time.
Обычно NOTIFY для пакета диалога содержит информацию только о тех диалогах, состояние которых изменилось. Чтобы построить согласованное представление общего состояния всех диалогов, подписчику пакета диалога потребуется объединять NOTIFY, полученные с течением времени.
Notifications within this package can convey partial information; that is, they can indicate information about a subset of the state associated with the subscription. This means that an explicit algorithm needs to be defined in order to construct coherent and consistent state. The details of this mechanism are specific to the particular document type. See Section 4.3 for information on constructing coherent information from an application/dialog-info+xml document.
Уведомления в этом пакете могут передавать частичную информацию; то есть они могут указывать информацию о подмножестве состояния, связанного с подпиской. 3.9. Handling of Forked Requests
3.9. Обработка разветвлённых запросов
Since dialog state is distributed across the UA for a particular user, it is reasonable and useful for a SUBSCRIBE request for dialog state to fork and to reach multiple UAs.
Поскольку состояние диалога распределено по UA конкретного пользователя, разумно и полезно, чтобы запрос SUBSCRIBE на состояние диалога разветвлялся и достигал нескольких UA.
As a result, a forked SUBSCRIBE request for dialog state can install multiple subscriptions. Subscribers to this package MUST be prepared to install subscription state for each NOTIFY generated as a result of a single SUBSCRIBE.
В результате разветвлённый запрос SUBSCRIBE на состояние диалога может установить несколько подписок. Подписчики этого пакета ДОЛЖНЫ быть готовы установить состояние подписки для каждого NOTIFY, сформированного в результате одного SUBSCRIBE.
3.10. Rate of Notifications
3.10. Частота уведомлений
For reasons of congestion control, it is important that the rate of notifications not be excessive. It is RECOMMENDED that the server not generate notifications for a single subscriber faster than once every 1 second.
По причинам управления перегрузкой важно, чтобы частота уведомлений не была чрезмерной. РЕКОМЕНДУЕТСЯ, чтобы сервер формировал уведомления для одного подписчика не чаще одного раза в 1 секунду.
3.11. State Agents
3.11. Агенты состояния
Dialog state is ideally maintained in the user agents in which the dialog resides. Therefore, the elements that maintain the dialog are the ones best suited to handle subscriptions to it. However, in some cases, a network agent may also know the state of the dialogs held by a user. Such state agents MAY be used with this package.
Состояние диалога в идеале поддерживается в пользовательских агентах, в которых находится диалог. Поэтому элементы, поддерживающие диалог, лучше всего подходят для обработки подписок на него. Однако в некоторых случаях сетевой агент также может знать состояние диалогов пользователя. Такие агенты состояния МОГУТ использоваться с этим пакетом.

4.3. Constructing Coherent State
4.3. Построение согласованного состояния
The dialog information subscriber maintains a table listing the dialogs, with a row for each dialog. Each row is indexed by an ID that is present in the "id" attribute of the "dialog" element. Each row contains the state of that dialog, as conveyed in the document.
Подписчик информации о диалогах ведёт таблицу, перечисляющую диалоги, с одной строкой на каждый диалог. Каждая строка индексируется идентификатором, который присутствует в атрибуте «id» элемента «dialog». Каждая строка содержит состояние этого диалога, переданное в документе.
The table is also associated with a version number. The version number MUST be initialized with the value of the "version" attribute from the "dialog-info" element in the first document received. Each time a new document is received, the value of the local version number is compared to the "version" attribute in the new document. If the value in the new document is one higher than the local version number, the local version number is increased by one and the document is processed. If the value in the document is more than one higher than the local version number, the local version number is set to the value in the new document and the document is processed. If the document did not contain full state, the subscriber SHOULD generate a refresh request (SUBSCRIBE) to trigger a full state notification. If the value in the document is less than the local version, the document is discarded without processing.
Таблица также связана с номером версии. Номер версии ДОЛЖЕН инициализироваться значением атрибута «version» из элемента «dialog-info» в первом полученном документе. При каждом получении нового документа значение локального номера версии сравнивается с атрибутом «version» в новом документе. Если значение в новом документе на единицу больше локального номера версии, локальный номер версии увеличивается на единицу, и документ обрабатывается. Если значение в документе более чем на единицу больше локального номера версии, локальному номеру версии присваивается значение из нового документа, и документ обрабатывается. Если документ не содержал полного состояния, подписчику СЛЕДУЕТ сформировать запрос обновления (SUBSCRIBE), чтобы вызвать уведомление с полным состоянием. Если значение в документе меньше локальной версии, документ отбрасывается без обработки.
The processing of the dialog information document depends on whether it contains full or partial state. If it contains full state, indicated by the value of the "state" attribute in the "dialog-info" element, the contents of the table are flushed and then repopulated from the document. A new row in the table is created for each "dialog" element. If the document contains partial state, as indicated by the value of the "state" attribute in the "dialog-info" element, the document is used to update the table. For each "dialog" element in the document, the subscriber checks to see whether a row exists for that dialog. This check compares the ID in the "id" attribute of the "dialog" element with the ID associated with the row. If the dialog does not exist in the table, a row is added and its state is set to the information from that "dialog" element. If the dialog does exist, its state is updated to be the information from that "dialog" element. If a row is updated or created, such that its state is now terminated, that entry MAY be removed from the table at any time.
Обработка документа информации о диалогах зависит от того, содержит ли он полное или частичное состояние. Если он содержит полное состояние, указанное значением атрибута «state» в элементе «dialog-info», содержимое таблицы очищается, а затем заполняется заново из документа. Для каждого элемента «dialog» создаётся новая строка таблицы. Если документ содержит частичное состояние, указанное значением атрибута «state» в элементе «dialog-info», документ используется для обновления таблицы. Для каждого элемента «dialog» в документе подписчик проверяет, существует ли строка для этого диалога. Эта проверка сравнивает ID в атрибуте «id» элемента «dialog» с ID, связанным со строкой. Если диалога нет в таблице, добавляется строка, и её состояние устанавливается по информации из этого элемента «dialog». Если диалог существует, его состояние обновляется информацией из этого элемента «dialog». Если строка обновлена или создана так, что её состояние теперь terminated, эта запись МОЖЕТ быть удалена из таблицы в любое время.

5. Definition of New Media Feature Parameters
5. Определение новых параметров возможностей медиа
This section defines two new media feature parameters that are useful as input to user presence, in conferencing applications, and in applications like the shared-line example described in Section 6.2. These feature parameters are especially useful in combination with the dialog package, as they allow an authorized third party to become aware of these characteristics.
В этом разделе определяются два новых параметра возможностей медиа, полезных как входные данные для присутствия пользователя, в приложениях конференций и в таких приложениях, как пример общей линии, описанный в разделе 6.2. Эти параметры возможностей особенно полезны в сочетании с пакетом диалога, поскольку они позволяют авторизованной третьей стороне узнавать об этих характеристиках.
5.1. The "sip.byeless" Parameter
5.1. Параметр возможностей «sip.byeless»
The "sip.byeless" media feature parameter is a new boolean parameter, defined in this document, that provides a positive indication that the user agent setting the parameter is unable to terminate sessions on its own (for example, by sending a BYE request). For example, continuous announcement services and certain recording services are unable to determine when it would be desirable to terminate a session, and therefore they do not have the ability to terminate sessions at all. Also, many human call centers are configured so that they never terminate sessions. (This is to prevent call center agents from accidentally disconnecting the caller). (Note that per [10], this parameter name must be preceded by a "+" character when used in a SIP Contact header field.)
Параметр возможности медиа «sip.byeless» — новый булев параметр, определённый в настоящем документе, который даёт положительное указание, что пользовательский агент, устанавливающий этот параметр, не способен самостоятельно завершать сеансы (например, отправляя запрос BYE). Например, службы непрерывных объявлений и некоторые службы записи не могут определить, когда было бы желательно завершить сеанс, и поэтому вообще не имеют возможности завершать сеансы. Кроме того, многие человеческие колл-центры настроены так, что они никогда не завершают сеансы. (Это делается, чтобы агенты колл-центра случайно не отключили вызывающего.) (Обратите внимание, что согласно [10] имя этого параметра должно предваряться символом «+» при использовании в поле заголовка Contact SIP.)
Contact: <sip:recording-service@host.example.net> ;automaton;+sip.byeless
Contact: <sip:recording-service@host.example.net> ;automaton;+sip.byeless
5.2. The "sip.rendering" Parameter
5.2. Параметр «sip.rendering»
The "sip.rendering" media feature parameter is a new string parameter, defined in this document, that can provide a positive indication whether the user agent setting the parameter is currently rendering any of the media it is receiving in the context of a specific session. It MUST only be used in a Contact header field in a dialog created using the INVITE request.
Параметр возможности медиа «sip.rendering» — новый строковый параметр, определённый в настоящем документе, который может давать положительное указание, воспроизводит ли пользовательский агент, устанавливающий параметр, какие-либо из получаемых им медиа в контексте конкретного сеанса. Он ДОЛЖЕН использоваться только в поле заголовка Contact в диалоге, созданном с помощью запроса INVITE.
This parameter has three legal values: "yes", "no", and "unknown". The value "yes" indicates positive knowledge that the user agent is rendering at least one of the streams of media that it is receiving. The value "no" indicates positive knowledge that the user agent is rendering none of the media that it is receiving. The value "unknown" indicates that the user agent does not know whether the media associated with the session is being rendered (which may be the case if the user agent is acting as a 3pcc (Third Party Call Control) [19] controller).
Этот параметр имеет три допустимых значения: «yes», «no» и «unknown». Значение «yes» указывает на положительное знание, что пользовательский агент воспроизводит хотя бы один из получаемых им медиапотоков. Значение «no» указывает на положительное знание, что пользовательский агент не воспроизводит ни одного из получаемых им медиа. Значение «unknown» указывает, что пользовательский агент не знает, воспроизводится ли медиа, связанное с сеансом (что может быть в случае, если пользовательский агент действует как контроллер 3pcc (Third Party Call Control) [19]).
The "sip.rendering" parameter is useful in applications such as shared appearances, conference status monitoring, or as an input to user presence.
Параметр «sip.rendering» полезен в таких приложениях, как общие линии, мониторинг состояния конференции или в качестве входных данных для присутствия пользователя.
Contact: <sip:musak-onhold@host.example.net> ;automaton;+sip.rendering="no"
