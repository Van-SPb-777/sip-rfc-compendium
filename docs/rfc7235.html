Abstract
Аннотация
The Hypertext Transfer Protocol (HTTP) is a stateless application- level protocol for distributed, collaborative, hypermedia information systems. This document defines the HTTP Authentication framework.
Протокол передачи гипертекста (HTTP) — это протокол уровня приложений, не хранящий состояния, для распределённых, совместных гипермедийных информационных систем. Настоящий документ определяет основы аутентификации в HTTP.

1. Introduction
1. Введение
HTTP provides a general framework for access control and authentication, via an extensible set of challenge-response authentication schemes, which can be used by a server to challenge a client request and by a client to provide authentication information. This document defines HTTP/1.1 authentication in terms of the architecture defined in "Hypertext Transfer Protocol (HTTP/1.1): Message Syntax and Routing" [RFC7230], including the general framework previously described in "HTTP Authentication: Basic and Digest Access Authentication" [RFC2617] and the related fields and status codes previously defined in "Hypertext Transfer Protocol -- HTTP/1.1" [RFC2616].
HTTP предоставляет общие рамки для управления доступом и аутентификации с помощью расширяемого набора схем аутентификации «запрос-ответ», которые могут использоваться сервером для запроса аутентификации у клиента, а клиентом — для предоставления аутентификационной информации. Настоящий документ определяет аутентификацию HTTP/1.1 в терминах архитектуры, определённой в документе «Hypertext Transfer Protocol (HTTP/1.1): Message Syntax and Routing» [RFC7230], включая общие рамки, ранее описанные в документе «HTTP Authentication: Basic and Digest Access Authentication» [RFC2617], и связанные поля и коды состояния, ранее определённые в документе «Hypertext Transfer Protocol -- HTTP/1.1» [RFC2616].
The IANA Authentication Scheme Registry (Section 5.1) lists registered authentication schemes and their corresponding specifications, including the "basic" and "digest" authentication schemes previously defined by RFC 2617.
Реестр схем аутентификации IANA (раздел 5.1) перечисляет зарегистрированные схемы аутентификации и соответствующие им спецификации, включая схемы аутентификации «basic» и «digest», ранее определённые в RFC 2617.

1.2. Нотация синтаксиса
This specification uses the Augmented Backus-Naur Form (ABNF) notation of [RFC5234] with a list extension, defined in Section 7 of [RFC7230], that allows for compact definition of comma-separated lists using a '#' operator (similar to how the '*' operator indicates repetition). Appendix B describes rules imported from other documents. Appendix C shows the collected grammar with all list operators expanded to standard ABNF notation.

В приложении B описаны правила, импортированные из других документов. В приложении C показана сводная грамматика со всеми операторами списков, развёрнутыми в стандартную нотацию ABNF.
2. Access Authentication Framework
2. Основы аутентификации доступа
2.1. Challenge and Response
2.1. Запрос и ответ
HTTP provides a simple challenge-response authentication framework that can be used by a server to challenge a client request and by a client to provide authentication information. It uses a case- insensitive token as a means to identify the authentication scheme, followed by additional information necessary for achieving authentication via that scheme. The latter can be either a comma- separated list of parameters or a single sequence of characters capable of holding base64-encoded information.
HTTP предоставляет простые рамки аутентификации «запрос-ответ», которые могут использоваться сервером для запроса аутентификации у клиента, а клиентом — для предоставления аутентификационной информации. В них используется нечувствительный к регистру токен как средство идентификации схемы аутентификации, за которым следует дополнительная информация, необходимая для выполнения аутентификации по этой схеме. Последняя может быть либо списком параметров, разделённых запятыми, либо единственной последовательностью символов, способной содержать информацию в кодировке base64.
Authentication parameters are name=value pairs, where the name token is matched case-insensitively, and each parameter name MUST only occur once per challenge.
Параметры аутентификации представляют собой пары name=value, где имя-токен сопоставляется без учёта регистра, и каждое имя параметра должно встречаться в одном запросе только один раз.
auth-scheme = token auth-param = token BWS "=" BWS ( token / quoted-string ) token68 = 1*( ALPHA / DIGIT / "-" / "." / "_" / "~" / "+" / "/" ) *"="
auth-scheme = token auth-param = token BWS "=" BWS ( token / quoted-string ) token68 = 1*( ALPHA / DIGIT / "-" / "." / "_" / "~" / "+" / "/" ) *"="
The token68 syntax allows the 66 unreserved URI characters ([RFC3986]), plus a few others, so that it can hold a base64, base64url (URL and filename safe alphabet), base32, or base16 (hex) encoding, with or without padding, but excluding whitespace ([RFC4648]).
Синтаксис token68 допускает 66 нерезервированных символов URI ([RFC3986]) и несколько других, поэтому он может содержать кодировку base64, base64url (безопасный для URL и имён файлов алфавит), base32 или base16 (hex) — с заполнением или без него, но без пробельных символов ([RFC4648]).
A 401 (Unauthorized) response message is used by an origin server to challenge the authorization of a user agent, including a WWW-Authenticate header field containing at least one challenge applicable to the requested resource.
Ответное сообщение 401 (Unauthorized) используется исходным сервером для запроса авторизации у пользовательского агента и включает поле заголовка WWW-Authenticate, содержащее как минимум один запрос, применимый к запрошенному ресурсу.
A 407 (Proxy Authentication Required) response message is used by a proxy to challenge the authorization of a client, including a Proxy-Authenticate header field containing at least one challenge applicable to the proxy for the requested resource.
Ответное сообщение 407 (Proxy Authentication Required) используется прокси для запроса авторизации у клиента и включает поле заголовка Proxy-Authenticate, содержащее как минимум один запрос, применимый к прокси для запрошенного ресурса.
challenge = auth-scheme [ 1*SP ( token68 / #auth-param ) ]
challenge = auth-scheme [ 1*SP ( token68 / #auth-param ) ]
Note: Many clients fail to parse a challenge that contains an unknown scheme. A workaround for this problem is to list well- supported schemes (such as "basic") first.
Примечание. Многие клиенты не в состоянии разобрать запрос, содержащий неизвестную схему. Обходной путь для этой проблемы — перечислять первыми хорошо поддерживаемые схемы (такие как «basic»).
A user agent that wishes to authenticate itself with an origin server -- usually, but not necessarily, after receiving a 401 (Unauthorized) -- can do so by including an Authorization header field with the request.
Пользовательский агент, желающий аутентифицироваться на исходном сервере — обычно, но не обязательно, после получения ответа 401 (Unauthorized), — может сделать это, включив в запрос поле заголовка Authorization.
A client that wishes to authenticate itself with a proxy -- usually, but not necessarily, after receiving a 407 (Proxy Authentication Required) -- can do so by including a Proxy-Authorization header field with the request. Both the Authorization field value and the Proxy-Authorization field value contain the client's credentials for the realm of the resource being requested, based upon a challenge received in a response (possibly at some point in the past). When creating their values, the user agent ought to do so by selecting the challenge with what it considers to be the most secure auth-scheme that it understands, obtaining credentials from the user as appropriate. Transmission of credentials within header field values implies significant security considerations regarding the confidentiality of the underlying connection, as described in Section 6.1.
Клиент, желающий аутентифицироваться на прокси — обычно, но не обязательно, после получения ответа 407 (Proxy Authentication Required), — может сделать это, включив в запрос поле заголовка Proxy-Authorization. И значение поля Authorization, и значение поля Proxy-Authorization содержат учётные данные клиента для realm ресурса, к которому выполняется запрос, на основе запроса, полученного в ответе (возможно, в некоторый момент в прошлом). При создании своих значений пользовательскому агенту следует выбирать запрос с той схемой аутентификации, которую он считает наиболее защищённой из числа понятных ему, и получать учётные данные у пользователя по мере необходимости. Передача учётных данных внутри значений полей заголовков влечёт существенные соображения безопасности относительно конфиденциальности нижележащего соединения, как описано в разделе 6.1.
credentials = auth-scheme [ 1*SP ( token68 / #auth-param ) ]
credentials = auth-scheme [ 1*SP ( token68 / #auth-param ) ]
Upon receipt of a request for a protected resource that omits credentials, contains invalid credentials (e.g., a bad password) or partial credentials (e.g., when the authentication scheme requires more than one round trip), an origin server SHOULD send a 401 (Unauthorized) response that contains a WWW-Authenticate header field with at least one (possibly new) challenge applicable to the requested resource.
При получении запроса на защищённый ресурс, в котором отсутствуют учётные данные, содержатся недопустимые учётные данные (например, неверный пароль) или частичные учётные данные (например, когда схема аутентификации требует более одного обмена), исходному серверу следует отправить ответ 401 (Unauthorized), содержащий поле заголовка WWW-Authenticate как минимум с одним (возможно, новым) запросом, применимым к запрошенному ресурсу.
Likewise, upon receipt of a request that omits proxy credentials or contains invalid or partial proxy credentials, a proxy that requires authentication SHOULD generate a 407 (Proxy Authentication Required) response that contains a Proxy-Authenticate header field with at least one (possibly new) challenge applicable to the proxy.
Аналогично, при получении запроса, в котором отсутствуют учётные данные прокси или содержатся недопустимые либо частичные учётные данные прокси, прокси, требующий аутентификации, должен сформировать ответ 407 (Proxy Authentication Required), содержащий поле заголовка Proxy-Authenticate как минимум с одним (возможно, новым) запросом, применимым к прокси.
A server that receives valid credentials that are not adequate to gain access ought to respond with the 403 (Forbidden) status code (Section 6.5.3 of [RFC7231]).
Сервер, получивший допустимые учётные данные, которых недостаточно для получения доступа, должен ответить кодом состояния 403 (Forbidden) (раздел 6.5.3 документа [RFC7231]).
HTTP does not restrict applications to this simple challenge-response framework for access authentication. Additional mechanisms can be used, such as authentication at the transport level or via message encapsulation, and with additional header fields specifying authentication information. However, such additional mechanisms are not defined by this specification.
HTTP не ограничивает приложения этими простыми рамками аутентификации доступа «запрос-ответ». Могут использоваться дополнительные механизмы, такие как аутентификация на транспортном уровне или посредством инкапсуляции сообщений, а также с дополнительными полями заголовков, задающими аутентификационную информацию. Однако такие дополнительные механизмы настоящей спецификацией не определяются.
2.2. Protection Space (Realm)
2.2. Пространство защиты (realm)
The "realm" authentication parameter is reserved for use by authentication schemes that wish to indicate a scope of protection.
Параметр аутентификации realm зарезервирован для использования схемами аутентификации, которые желают указать область защиты.
A protection space is defined by the canonical root URI (the scheme and authority components of the effective request URI; see Section 5.5 of [RFC7230]) of the server being accessed, in combination with the realm value if present. These realms allow the protected resources on a server to be partitioned into a set of protection spaces, each with its own authentication scheme and/or authorization database. The realm value is a string, generally assigned by the origin server, that can have additional semantics specific to the authentication scheme. Note that a response can have multiple challenges with the same auth-scheme but with different realms.
Пространство защиты определяется каноническим корневым URI (компонентами схемы и authority действующего URI запроса; см. раздел 5.5 документа [RFC7230]) сервера, к которому выполняется доступ, в сочетании со значением realm, если оно присутствует. Эти realm позволяют разделить защищённые ресурсы на сервере на набор пространств защиты, каждое со своей схемой аутентификации и/или базой данных авторизации. Значение realm — это строка, обычно назначаемая исходным сервером, которая может иметь дополнительную семантику, специфичную для схемы аутентификации. Обратите внимание, что ответ может содержать несколько запросов с одной и той же схемой аутентификации, но с разными realm.
The protection space determines the domain over which credentials can be automatically applied. If a prior request has been authorized, the user agent MAY reuse the same credentials for all other requests within that protection space for a period of time determined by the authentication scheme, parameters, and/or user preferences (such as a configurable inactivity timeout). Unless specifically allowed by the authentication scheme, a single protection space cannot extend outside the scope of its server.
Пространство защиты определяет область, в пределах которой учётные данные могут применяться автоматически. Если предыдущий запрос был авторизован, пользовательский агент может повторно использовать одни и те же учётные данные для всех остальных запросов в пределах этого пространства защиты в течение периода времени, определяемого схемой аутентификации, параметрами и/или предпочтениями пользователя (например, настраиваемым тайм-аутом неактивности). Если это специально не разрешено схемой аутентификации, одно пространство защиты не может выходить за пределы своего сервера.
For historical reasons, a sender MUST only generate the quoted-string syntax. Recipients might have to support both token and quoted-string syntax for maximum interoperability with existing clients that have been accepting both notations for a long time.
По историческим причинам отправитель должен формировать только синтаксис quoted-string. Получателям, возможно, придётся поддерживать и синтаксис token, и синтаксис quoted-string для максимальной совместимости с существующими клиентами, которые долгое время принимали обе нотации.
3. Status Code Definitions
3. Определения кодов состояния
3.1. 401 Unauthorized
3.1. 401 Unauthorized
The 401 (Unauthorized) status code indicates that the request has not been applied because it lacks valid authentication credentials for the target resource. The server generating a 401 response MUST send a WWW-Authenticate header field (Section 4.1) containing at least one challenge applicable to the target resource.
Код состояния 401 (Unauthorized) указывает, что запрос не был применён, поскольку для целевого ресурса отсутствуют допустимые учётные данные аутентификации. Сервер, формирующий ответ 401, должен отправить поле заголовка WWW-Authenticate (раздел 4.1), содержащее как минимум один запрос, применимый к целевому ресурсу.
If the request included authentication credentials, then the 401 response indicates that authorization has been refused for those credentials. The user agent MAY repeat the request with a new or replaced Authorization header field (Section 4.2). If the 401 response contains the same challenge as the prior response, and the user agent has already attempted authentication at least once, then the user agent SHOULD present the enclosed representation to the user, since it usually contains relevant diagnostic information.
Если запрос содержал учётные данные аутентификации, то ответ 401 указывает, что в авторизации для этих учётных данных отказано. Пользовательский агент может повторить запрос с новым или заменённым полем заголовка Authorization (раздел 4.2). Если ответ 401 содержит тот же запрос, что и предыдущий ответ, и пользовательский агент уже предпринял хотя бы одну попытку аутентификации, то пользовательскому агенту следует показать пользователю вложенное представление, поскольку оно обычно содержит актуальную диагностическую информацию.
3.2. 407 Proxy Authentication Required
3.2. 407 Proxy Authentication Required
The 407 (Proxy Authentication Required) status code is similar to 401 (Unauthorized), but it indicates that the client needs to authenticate itself in order to use a proxy. The proxy MUST send a Proxy-Authenticate header field (Section 4.3) containing a challenge applicable to that proxy for the target resource. The client MAY repeat the request with a new or replaced Proxy-Authorization header field (Section 4.4).
Код состояния 407 (Proxy Authentication Required) аналогичен коду 401 (Unauthorized), но указывает, что клиенту необходимо аутентифицироваться, чтобы использовать прокси. Прокси должен отправить поле заголовка Proxy-Authenticate (раздел 4.3), содержащее запрос, применимый к этому прокси для целевого ресурса. Клиент может повторить запрос с новым или заменённым полем заголовка Proxy-Authorization (раздел 4.4).
4. Header Field Definitions
4. Определения полей заголовков
This section defines the syntax and semantics of header fields related to the HTTP authentication framework.
В этом разделе определены синтаксис и семантика полей заголовков, относящихся к основам аутентификации HTTP.
4.1. WWW-Authenticate
4.1. WWW-Authenticate
The "WWW-Authenticate" header field indicates the authentication scheme(s) and parameters applicable to the target resource.
Поле заголовка WWW-Authenticate указывает схему (схемы) аутентификации и параметры, применимые к целевому ресурсу.
WWW-Authenticate = 1#challenge
WWW-Authenticate = 1#challenge
A server generating a 401 (Unauthorized) response MUST send a WWW-Authenticate header field containing at least one challenge. A server MAY generate a WWW-Authenticate header field in other response messages to indicate that supplying credentials (or different credentials) might affect the response.
Сервер, формирующий ответ 401 (Unauthorized), должен отправить поле заголовка WWW-Authenticate, содержащее как минимум один запрос. Сервер может формировать поле заголовка WWW-Authenticate и в других ответных сообщениях, чтобы указать, что предоставление учётных данных (или других учётных данных) может повлиять на ответ.
A proxy forwarding a response MUST NOT modify any WWW-Authenticate fields in that response.
Прокси, пересылающий ответ, не должен изменять какие-либо поля WWW-Authenticate в этом ответе.
User agents are advised to take special care in parsing the field value, as it might contain more than one challenge, and each challenge can contain a comma-separated list of authentication parameters. Furthermore, the header field itself can occur multiple times.
Пользовательским агентам рекомендуется проявлять особую осторожность при разборе значения поля, поскольку оно может содержать более одного запроса, и каждый запрос может содержать список параметров аутентификации, разделённых запятыми. Кроме того, само поле заголовка может встречаться несколько раз.
For instance:
Например:
WWW-Authenticate: Newauth realm="apps", type=1, title="Login to \"apps\"", Basic realm="simple"
WWW-Authenticate: Newauth realm="apps", type=1, title="Login to \"apps\"", Basic realm="simple"
This header field contains two challenges; one for the "Newauth" scheme with a realm value of "apps", and two additional parameters "type" and "title", and another one for the "Basic" scheme with a realm value of "simple".
Это поле заголовка содержит два запроса: один для схемы «Newauth» со значением realm «apps» и двумя дополнительными параметрами «type» и «title», а другой — для схемы «Basic» со значением realm «simple».
Note: The challenge grammar production uses the list syntax as well. Therefore, a sequence of comma, whitespace, and comma can be considered either as applying to the preceding challenge, or to be an empty entry in the list of challenges. In practice, this ambiguity does not affect the semantics of the header field value and thus is harmless.
Примечание. Продукция грамматики challenge также использует синтаксис списка. Поэтому последовательность «запятая, пробел, запятая» можно рассматривать и как относящуюся к предшествующему запросу, и как пустую запись в списке запросов. На практике эта неоднозначность не влияет на семантику значения поля заголовка и потому безвредна.
4.2. Authorization
4.2. Authorization
The "Authorization" header field allows a user agent to authenticate itself with an origin server -- usually, but not necessarily, after receiving a 401 (Unauthorized) response. Its value consists of credentials containing the authentication information of the user agent for the realm of the resource being requested.
Поле заголовка Authorization позволяет пользовательскому агенту аутентифицироваться на исходном сервере — обычно, но не обязательно, после получения ответа 401 (Unauthorized). Его значение состоит из учётных данных, содержащих аутентификационную информацию пользовательского агента для realm ресурса, к которому выполняется запрос.
Authorization = credentials
Authorization = credentials
If a request is authenticated and a realm specified, the same credentials are presumed to be valid for all other requests within this realm (assuming that the authentication scheme itself does not require otherwise, such as credentials that vary according to a challenge value or using synchronized clocks).
Если запрос аутентифицирован и указан realm, предполагается, что одни и те же учётные данные действительны для всех остальных запросов в пределах этого realm (при условии, что сама схема аутентификации не требует иного, например учётных данных, изменяющихся в зависимости от значения запроса или при использовании синхронизированных часов).
A proxy forwarding a request MUST NOT modify any Authorization fields in that request. See Section 3.2 of [RFC7234] for details of and requirements pertaining to handling of the Authorization field by HTTP caches.
Прокси, пересылающий запрос, не должен изменять какие-либо поля Authorization в этом запросе. Подробности и требования, касающиеся обработки поля Authorization кэшами HTTP, см. в разделе 3.2 документа [RFC7234].
4.3. Proxy-Authenticate
4.3. Proxy-Authenticate
The "Proxy-Authenticate" header field consists of at least one challenge that indicates the authentication scheme(s) and parameters applicable to the proxy for this effective request URI (Section 5.5 of [RFC7230]). A proxy MUST send at least one Proxy-Authenticate header field in each 407 (Proxy Authentication Required) response that it generates.
Поле заголовка Proxy-Authenticate состоит как минимум из одного запроса, который указывает схему (схемы) аутентификации и параметры, применимые к прокси для данного действующего URI запроса (раздел 5.5 документа [RFC7230]). Прокси должен отправлять как минимум одно поле заголовка Proxy-Authenticate в каждом формируемом им ответе 407 (Proxy Authentication Required).
Proxy-Authenticate = 1#challenge
Proxy-Authenticate = 1#challenge
Unlike WWW-Authenticate, the Proxy-Authenticate header field applies only to the next outbound client on the response chain. This is because only the client that chose a given proxy is likely to have the credentials necessary for authentication. However, when multiple proxies are used within the same administrative domain, such as office and regional caching proxies within a large corporate network, it is common for credentials to be generated by the user agent and passed through the hierarchy until consumed. Hence, in such a configuration, it will appear as if Proxy-Authenticate is being forwarded because each proxy will send the same challenge set.
В отличие от WWW-Authenticate, поле заголовка Proxy-Authenticate применяется только к следующему исходящему клиенту в цепочке ответов. Это объясняется тем, что только клиент, выбравший данный прокси, вероятно, располагает учётными данными, необходимыми для аутентификации. Однако когда в одном административном домене используется несколько прокси, например офисные и региональные кэширующие прокси в крупной корпоративной сети, обычной практикой является формирование учётных данных пользовательским агентом и их передача по иерархии до момента использования. Следовательно, в такой конфигурации будет выглядеть так, будто Proxy-Authenticate пересылается, поскольку каждый прокси будет отправлять один и тот же набор запросов.
Note that the parsing considerations for WWW-Authenticate apply to this header field as well; see Section 4.1 for details.
Обратите внимание, что соображения по разбору, приведённые для WWW-Authenticate, применимы и к этому полю заголовка; подробности см. в разделе 4.1.
4.4. Proxy-Authorization
4.4. Proxy-Authorization
The "Proxy-Authorization" header field allows the client to identify itself (or its user) to a proxy that requires authentication. Its value consists of credentials containing the authentication information of the client for the proxy and/or realm of the resource being requested.
Поле заголовка Proxy-Authorization позволяет клиенту идентифицировать себя (или своего пользователя) перед прокси, требующим аутентификации. Его значение состоит из учётных данных, содержащих аутентификационную информацию клиента для прокси и/или realm ресурса, к которому выполняется запрос.
Proxy-Authorization = credentials
Proxy-Authorization = credentials
Unlike Authorization, the Proxy-Authorization header field applies only to the next inbound proxy that demanded authentication using the Proxy-Authenticate field. When multiple proxies are used in a chain, the Proxy-Authorization header field is consumed by the first inbound proxy that was expecting to receive credentials. A proxy MAY relay the credentials from the client request to the next proxy if that is the mechanism by which the proxies cooperatively authenticate a given request.
В отличие от Authorization, поле заголовка Proxy-Authorization применяется только к следующему входящему прокси, который потребовал аутентификации с помощью поля Proxy-Authenticate. Когда в цепочке используется несколько прокси, поле заголовка Proxy-Authorization используется первым входящим прокси, который ожидал получения учётных данных. Прокси может передать учётные данные из запроса клиента следующему прокси, если именно таким механизмом прокси совместно аутентифицируют данный запрос.

5.1.1. Процедура

5.1.2. Considerations for New Authentication Schemes
5.1.2. Соображения для новых схем аутентификации
There are certain aspects of the HTTP Authentication Framework that put constraints on how new authentication schemes can work:
Есть определённые аспекты основ аутентификации HTTP, которые накладывают ограничения на то, как могут работать новые схемы аутентификации:
o HTTP authentication is presumed to be stateless: all of the information necessary to authenticate a request MUST be provided in the request, rather than be dependent on the server remembering prior requests. Authentication based on, or bound to, the underlying connection is outside the scope of this specification and inherently flawed unless steps are taken to ensure that the connection cannot be used by any party other than the authenticated user (see Section 2.3 of [RFC7230]).
o Предполагается, что аутентификация HTTP не хранит состояния: вся информация, необходимая для аутентификации запроса, должна предоставляться в самом запросе, а не зависеть от того, помнит ли сервер предыдущие запросы. Аутентификация, основанная на нижележащем соединении или привязанная к нему, выходит за рамки настоящей спецификации и по своей сути порочна, если не предприняты меры, гарантирующие, что соединение не может быть использовано какой-либо стороной, кроме аутентифицированного пользователя (см. раздел 2.3 документа [RFC7230]).
o The authentication parameter "realm" is reserved for defining protection spaces as described in Section 2.2. New schemes MUST NOT use it in a way incompatible with that definition.
o Параметр аутентификации «realm» зарезервирован для определения пространств защиты, как описано в разделе 2.2. Новые схемы не должны использовать его способом, несовместимым с этим определением.
o The "token68" notation was introduced for compatibility with existing authentication schemes and can only be used once per challenge or credential. Thus, new schemes ought to use the auth-param syntax instead, because otherwise future extensions will be impossible.
o Нотация «token68» была введена для совместимости с существующими схемами аутентификации и может использоваться только один раз на запрос или учётные данные. Поэтому новым схемам следует вместо неё использовать синтаксис auth-param, поскольку иначе будущие расширения станут невозможны.
o The parsing of challenges and credentials is defined by this specification and cannot be modified by new authentication schemes. When the auth-param syntax is used, all parameters ought to support both token and quoted-string syntax, and syntactical constraints ought to be defined on the field value after parsing (i.e., quoted-string processing). This is necessary so that recipients can use a generic parser that applies to all authentication schemes.
o Разбор запросов и учётных данных определяется настоящей спецификацией и не может изменяться новыми схемами аутентификации. Когда используется синтаксис auth-param, все параметры должны поддерживать и синтаксис token, и синтаксис quoted-string, а синтаксические ограничения следует определять для значения поля после разбора (т. е. после обработки quoted-string). Это необходимо, чтобы получатели могли использовать общий анализатор, применимый ко всем схемам аутентификации.
Note: The fact that the value syntax for the "realm" parameter is restricted to quoted-string was a bad design choice not to be repeated for new parameters.
Примечание. Тот факт, что синтаксис значения параметра «realm» ограничен quoted-string, был неудачным проектным решением, которое не следует повторять для новых параметров.
o Definitions of new schemes ought to define the treatment of unknown extension parameters. In general, a "must-ignore" rule is preferable to a "must-understand" rule, because otherwise it will be hard to introduce new parameters in the presence of legacy recipients. Furthermore, it's good to describe the policy for defining new parameters (such as "update the specification" or "use this registry").
o Определения новых схем должны описывать обработку неизвестных параметров расширения. В общем случае правило «must-ignore» предпочтительнее правила «must-understand», поскольку иначе будет трудно вводить новые параметры при наличии устаревших получателей. Кроме того, полезно описать политику определения новых параметров (например, «обновить спецификацию» или «использовать этот реестр»).
o Authentication schemes need to document whether they are usable in origin-server authentication (i.e., using WWW-Authenticate), and/or proxy authentication (i.e., using Proxy-Authenticate).
o Схемы аутентификации должны документировать, применимы ли они при аутентификации на исходном сервере (т. е. с использованием WWW-Authenticate) и/или при аутентификации на прокси (т. е. с использованием Proxy-Authenticate).
o The credentials carried in an Authorization header field are specific to the user agent and, therefore, have the same effect on HTTP caches as the "private" Cache-Control response directive (Section 5.2.2.6 of [RFC7234]), within the scope of the request in which they appear.
o Учётные данные, переносимые в поле заголовка Authorization, специфичны для пользовательского агента и, следовательно, оказывают на кэши HTTP такое же влияние, как директива ответа Cache-Control «private» (раздел 5.2.2.6 документа [RFC7234]), в пределах области действия запроса, в котором они присутствуют.
Therefore, new authentication schemes that choose not to carry credentials in the Authorization header field (e.g., using a newly defined header field) will need to explicitly disallow caching, by mandating the use of either Cache-Control request directives (e.g., "no-store", Section 5.2.1.5 of [RFC7234]) or response directives (e.g., "private").
Поэтому новым схемам аутентификации, которые решают не переносить учётные данные в поле заголовка Authorization (например, используя новое определённое поле заголовка), потребуется явно запретить кэширование, предписав использование либо директив запроса Cache-Control (например, «no-store», раздел 5.2.1.5 документа [RFC7234]), либо директив ответа (например, «private»).

6. Security Considerations
6. Вопросы безопасности
This section is meant to inform developers, information providers, and users of known security concerns specific to HTTP authentication. More general security considerations are addressed in HTTP messaging [RFC7230] and semantics [RFC7231].
Настоящий раздел предназначен для информирования разработчиков, поставщиков информации и пользователей об известных проблемах безопасности, специфичных для аутентификации HTTP. Более общие соображения безопасности рассматриваются в документах о сообщениях HTTP [RFC7230] и его семантике [RFC7231].
Everything about the topic of HTTP authentication is a security consideration, so the list of considerations below is not exhaustive. Furthermore, it is limited to security considerations regarding the authentication framework, in general, rather than discussing all of the potential considerations for specific authentication schemes (which ought to be documented in the specifications that define those schemes). Various organizations maintain topical information and links to current research on Web application security (e.g., [OWASP]), including common pitfalls for implementing and using the authentication schemes found in practice.
Всё, что связано с темой аутентификации HTTP, является соображением безопасности, поэтому перечень соображений ниже не является исчерпывающим. Кроме того, он ограничен соображениями безопасности, касающимися основ аутентификации в целом, а не обсуждением всех потенциальных соображений для конкретных схем аутентификации (которые должны быть задокументированы в спецификациях, определяющих эти схемы). Различные организации поддерживают тематическую информацию и ссылки на текущие исследования по безопасности веб-приложений (например, [OWASP]), включая типичные подводные камни при реализации и использовании схем аутентификации, встречающихся на практике.
6.1. Confidentiality of Credentials
6.1. Конфиденциальность учётных данных
The HTTP authentication framework does not define a single mechanism for maintaining the confidentiality of credentials; instead, each authentication scheme defines how the credentials are encoded prior to transmission. While this provides flexibility for the development of future authentication schemes, it is inadequate for the protection of existing schemes that provide no confidentiality on their own, or that do not sufficiently protect against replay attacks. Furthermore, if the server expects credentials that are specific to each individual user, the exchange of those credentials will have the effect of identifying that user even if the content within credentials remains confidential.
Основы аутентификации HTTP не определяют единого механизма обеспечения конфиденциальности учётных данных; вместо этого каждая схема аутентификации определяет, как учётные данные кодируются перед передачей. Хотя это обеспечивает гибкость для разработки будущих схем аутентификации, этого недостаточно для защиты существующих схем, которые сами по себе не обеспечивают конфиденциальности или недостаточно защищают от атак повторного воспроизведения. Кроме того, если сервер ожидает учётные данные, специфичные для каждого отдельного пользователя, обмен этими учётными данными будет иметь эффект идентификации этого пользователя, даже если содержимое учётных данных остаётся конфиденциальным.
HTTP depends on the security properties of the underlying transport- or session-level connection to provide confidential transmission of header fields. In other words, if a server limits access to authenticated users using this framework, the server needs to ensure that the connection is properly secured in accordance with the nature of the authentication scheme used. For example, services that depend on individual user authentication often require a connection to be secured with TLS ("Transport Layer Security", [RFC5246]) prior to exchanging any credentials.
HTTP зависит от свойств безопасности нижележащего соединения транспортного или сеансового уровня для обеспечения конфиденциальной передачи полей заголовков. Иными словами, если сервер ограничивает доступ аутентифицированным пользователям с помощью этих основ, сервер должен обеспечить надлежащую защиту соединения в соответствии с характером используемой схемы аутентификации. Например, службы, зависящие от индивидуальной аутентификации пользователей, часто требуют, чтобы соединение было защищено с помощью TLS («Transport Layer Security», [RFC5246]) до обмена любыми учётными данными.
6.2. Authentication Credentials and Idle Clients
6.2. Учётные данные аутентификации и простаивающие клиенты
Existing HTTP clients and user agents typically retain authentication information indefinitely. HTTP does not provide a mechanism for the origin server to direct clients to discard these cached credentials, since the protocol has no awareness of how credentials are obtained or managed by the user agent. The mechanisms for expiring or revoking credentials can be specified as part of an authentication scheme definition.
Существующие клиенты HTTP и пользовательские агенты, как правило, хранят аутентификационную информацию бессрочно. HTTP не предоставляет механизма, позволяющего исходному серверу указать клиентам на необходимость отбросить эти кэшированные учётные данные, поскольку протокол не знает, как учётные данные получаются и управляются пользовательским агентом. Механизмы истечения срока действия или отзыва учётных данных могут быть определены как часть определения схемы аутентификации.
Circumstances under which credential caching can interfere with the application's security model include but are not limited to:
Обстоятельства, при которых кэширование учётных данных может мешать модели безопасности приложения, включают, помимо прочего:
o Clients that have been idle for an extended period, following which the server might wish to cause the client to re-prompt the user for credentials.
o Клиенты, которые простаивали в течение длительного периода, после чего серверу может потребоваться заставить клиента повторно запросить у пользователя учётные данные.
o Applications that include a session termination indication (such as a "logout" or "commit" button on a page) after which the server side of the application "knows" that there is no further reason for the client to retain the credentials.
o Приложения, которые включают указание на завершение сеанса (например, кнопку «logout» или «commit» на странице), после которого серверная часть приложения «знает», что у клиента больше нет причин хранить учётные данные.
User agents that cache credentials are encouraged to provide a readily accessible mechanism for discarding cached credentials under user control.
Пользовательским агентам, которые кэшируют учётные данные, рекомендуется предоставлять легкодоступный механизм удаления кэшированных учётных данных под управлением пользователя.
6.3. Protection Spaces
6.3. Пространства защиты
Authentication schemes that solely rely on the "realm" mechanism for establishing a protection space will expose credentials to all resources on an origin server. Clients that have successfully made authenticated requests with a resource can use the same authentication credentials for other resources on the same origin server. This makes it possible for a different resource to harvest authentication credentials for other resources.
Схемы аутентификации, которые полагаются исключительно на механизм «realm» для установления пространства защиты, предоставят учётные данные всем ресурсам на исходном сервере. Клиенты, успешно выполнившие аутентифицированные запросы к одному ресурсу, могут использовать те же учётные данные аутентификации для других ресурсов на том же исходном сервере. Это позволяет другому ресурсу собрать учётные данные аутентификации, предназначенные для других ресурсов.
This is of particular concern when an origin server hosts resources for multiple parties under the same canonical root URI (Section 2.2). Possible mitigation strategies include restricting direct access to authentication credentials (i.e., not making the content of the Authorization request header field available), and separating protection spaces by using a different host name (or port number) for each party.
Это особенно важно, когда исходный сервер размещает ресурсы нескольких сторон под одним и тем же каноническим корневым URI (раздел 2.2). Возможные стратегии смягчения включают ограничение прямого доступа к учётным данным аутентификации (т. е. отказ в доступе к содержимому поля заголовка запроса Authorization) и разделение пространств защиты путём использования другого имени хоста (или номера порта) для каждой стороны.
