Abstract
Аннотация
This document describes how to manage early media in the Session Initiation Protocol (SIP) using two models: the gateway model and the application server model. It also describes the inputs one needs to consider in defining local policies for ringing tone generation.
В настоящем документе описывается, как управлять ранними медиа в протоколе инициирования сессий (SIP) с помощью двух моделей: модели шлюза и модели сервера приложений. Также описаны исходные данные, которые необходимо учитывать при определении локальных правил генерации сигнала вызова.
1. Introduction
1. Введение
Early media refers to media (e.g., audio and video) that is exchanged before a particular session is accepted by the called user. Within a dialog, early media occurs from the moment the initial INVITE is sent until the User Agent Server (UAS) generates a final response. It may be unidirectional or bidirectional, and can be generated by the caller, the callee, or both. Typical examples of early media generated by the callee are ringing tone and announcements (e.g., queuing status). Early media generated by the caller typically consists of voice commands or dual tone multi-frequency (DTMF) tones to drive interactive voice response (IVR) systems.
Ранние медиа — это медиа (например, аудио и видео), которыми обмениваются до того, как вызываемый пользователь примет конкретную сессию. В пределах диалога ранние медиа имеют место с момента отправки начального INVITE и до тех пор, пока пользовательский агент-сервер (UAS) не сгенерирует окончательный ответ. Они могут быть однонаправленными или двунаправленными и генерироваться вызывающим, вызываемым или обеими сторонами. Типичные примеры ранних медиа, генерируемых вызываемым, — сигнал вызова и объявления (например, состояние очереди). Ранние медиа, генерируемые вызывающим, обычно состоят из голосовых команд или тональных сигналов DTMF (dual tone multi-frequency) для управления системами интерактивного голосового ответа (IVR).
The basic SIP specification (RFC 3261 [1]) only supports very simple early media mechanisms. These simple mechanisms have a number of problems which relate to forking and security, and do not satisfy the requirements of most applications. This document goes beyond the mechanisms defined in RFC 3261 [1] and describes two models of early media implementations using SIP: the gateway model and the application server model.
Базовая спецификация SIP (RFC 3261 [1]) поддерживает лишь очень простые механизмы ранних медиа. Эти простые механизмы имеют ряд проблем, связанных с разветвлением и безопасностью, и не удовлетворяют требованиям большинства приложений. Настоящий документ выходит за рамки механизмов, определённых в RFC 3261 [1], и описывает две модели реализации ранних медиа средствами SIP: модель шлюза и модель сервера приложений.
Although both early media models described in this document are superior to the one specified in RFC 3261 [1], the gateway model still presents a set of issues. In particular, the gateway model does not work well with forking. Nevertheless, the gateway model is needed because some SIP entities (in particular, some gateways) cannot implement the application server model.
Хотя обе модели ранних медиа, описанные в настоящем документе, превосходят модель, заданную в RFC 3261 [1], модель шлюза всё ещё создаёт ряд проблем. В частности, модель шлюза плохо работает при разветвлении. Тем не менее модель шлюза необходима, поскольку некоторые объекты SIP (в частности, некоторые шлюзы) не могут реализовать модель сервера приложений.
The application server model addresses some of the issues present in the gateway model. This model uses the early-session disposition type, which is specified in [2].
Модель сервера приложений решает некоторые проблемы, присущие модели шлюза. В этой модели используется тип диспозиции early-session, определённый в [2].
The remainder of this document is organized as follows: Section 2 describes the offer/answer model in the absence of early media, and Section 3 introduces the gateway model. In this model, the early media session is established using the early dialog established by the original INVITE. Sections 3.1, 3.2, and 3.4 describe the limitations of the gateway model and the scenarios where it is appropriate to use this model. Section 4 introduces the application server model, which, as stated previously, resolves some of the issues present in the gateway model. Section 5 discusses the interactions between the Alert-Info header field in both early media models.
Остальная часть документа организована следующим образом: в разделе 2 описана модель «предложение/ответ» при отсутствии ранних медиа, а раздел 3 вводит модель шлюза. В этой модели сессия ранних медиа устанавливается с использованием раннего диалога, созданного исходным INVITE. Разделы 3.1, 3.2 и 3.4 описывают ограничения модели шлюза и сценарии, в которых уместно её применять. Раздел 4 вводит модель сервера приложений, которая, как уже говорилось, решает некоторые проблемы модели шлюза. В разделе 5 обсуждается взаимодействие поля заголовка Alert-Info в обеих моделях ранних медиа.
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", " NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [9].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует интерпретировать так, как описано в [9].
2. Session Establishment in SIP
2. Установление сессии в SIP
Before presenting both early media models, we will briefly summarize how session establishment works in SIP. This will let us keep separate features that are intrinsic to SIP (e.g., media being played before the 200 (OK) to avoid media clipping) from early media operations.
Прежде чем представлять обе модели ранних медиа, кратко опишем, как в SIP происходит установление сессии. Это позволит нам отделить свойства, присущие самому SIP (например, воспроизведение медиа до ответа 200 (OK) для предотвращения обрезки медиа), от операций с ранними медиа.
SIP [1] uses the offer/answer model [3] to negotiate session parameters. One of the user agents - the offerer - prepares a session description that is called the offer. The other user agent - the answerer - responds with another session description called the answer. This two-way handshake allows both user agents to agree upon the session parameters to be used to exchange media.
SIP [1] использует модель «предложение/ответ» [3] для согласования параметров сессии. Один из пользовательских агентов — инициатор предложения — готовит описание сессии, называемое предложением. Другой пользовательский агент — отвечающий — отвечает другим описанием сессии, называемым ответом. Этот двусторонний обмен позволяет обоим пользовательским агентам договориться о параметрах сессии, которые будут использоваться для обмена медиа.
The offer/answer model decouples the offer/answer exchange from the messages used to transport the session descriptions. For example, the offer can be sent in an INVITE request and the answer can arrive in the 200 (OK) response for that INVITE, or, alternatively, the offer can be sent in the 200 (OK) for an empty INVITE and the answer can be sent in the ACK. When reliable provisional responses [4] and UPDATE requests [5] are used, there are many more possible ways to exchange offers and answers.
Модель «предложение/ответ» отделяет обмен предложением/ответом от сообщений, используемых для переноса описаний сессии. Например, предложение может быть отправлено в запросе INVITE, а ответ может прийти в ответе 200 (OK) на этот INVITE; альтернативно предложение может быть отправлено в ответе 200 (OK) на пустой INVITE, а ответ — в ACK. При использовании надёжных предварительных ответов [4] и запросов UPDATE [5] существует гораздо больше возможных способов обмена предложениями и ответами.
Media clipping occurs when the user (or the machine generating media) believes that the media session is already established, but the establishment process has not finished yet. The user starts speaking (i.e., generating media) and the first few syllables or even the first few words are lost.
Обрезка медиа возникает, когда пользователь (или машина, генерирующая медиа) считает, что медиасессия уже установлена, но процесс установления ещё не завершён. Пользователь начинает говорить (то есть генерировать медиа), и первые несколько слогов или даже первых несколько слов теряются.
When the offer/answer exchange takes place in the 200 (OK) response and in the ACK, media clipping is unavoidable. The called user starts speaking at the same time the 200 (OK) is sent, but the UAS cannot send any media until the answer from the User Agent Client (UAC) arrives in the ACK.
Когда обмен предложением/ответом происходит в ответе 200 (OK) и в ACK, обрезки медиа избежать нельзя. Вызываемый пользователь начинает говорить одновременно с отправкой 200 (OK), но UAS не может отправлять медиа, пока в ACK не придёт ответ от пользовательского агента-клиента (UAC).
On the other hand, media clipping does not appear in the most common offer/answer exchange (an INVITE with an offer and a 200 (OK) with an answer). UACs are ready to play incoming media packets as soon as they send an offer, because they cannot count on the reception of the 200 (OK) to start playing out media for the caller; SIP signalling and media packets typically traverse different paths, and so, media packets may arrive before the 200 (OK) response.
С другой стороны, обрезка медиа не возникает при наиболее распространённом обмене предложением/ответом (INVITE с предложением и 200 (OK) с ответом). UAC готовы воспроизводить входящие пакеты медиа сразу после отправки предложения, поскольку они не могут рассчитывать на получение 200 (OK) для начала воспроизведения медиа вызывающему; сигнализация SIP и пакеты медиа обычно проходят разными путями, поэтому пакеты медиа могут прибыть раньше ответа 200 (OK).
Another form of media clipping (not related to early media either) occurs in the caller-to-callee direction. When the callee picks up and starts speaking, the UAS sends a 200 (OK) response with an answer, in parallel with the first media packets. If the first media packets arrive at the UAC before the answer and the caller starts speaking, the UAC cannot send media until the 200 (OK) response from the UAS arrives.
Другая форма обрезки медиа (также не связанная с ранними медиа) возникает в направлении от вызывающего к вызываемому. Когда вызываемый берёт трубку и начинает говорить, UAS отправляет ответ 200 (OK), содержащий ответ, параллельно с первыми пакетами медиа. Если первые пакеты медиа приходят к UAC раньше ответа и вызывающий начинает говорить, UAC не может отправлять медиа, пока не придёт ответ 200 (OK) от UAS.
3. The Gateway Model
3. Модель шлюза
SIP uses the offer/answer model to negotiate session parameters (as described in Section 2). An offer/answer exchange that takes place before a final response for the INVITE is sent establishes an "early" media session. Early media sessions terminate when a final response for the INVITE is sent. If the final response is a 200 (OK), the early media session transitions to a regular media session. If the final response is a non-200 class final response, the early media session is simply terminated.
SIP использует модель «предложение/ответ» для согласования параметров сессии (как описано в разделе 2). Обмен предложением/ответом, происходящий до отправки окончательного ответа на INVITE, устанавливает «раннюю» медиасессию. Сессии ранних медиа завершаются при отправке окончательного ответа на INVITE. Если окончательный ответ — 200 (OK), сессия ранних медиа переходит в обычную медиасессию. Если окончательный ответ относится к классу, отличному от 200, сессия ранних медиа просто завершается.
Not surprisingly, media exchanged within an early media session is referred to as early media. The gateway model consists of managing early media sessions using offer/answer exchanges in reliable provisional responses, PRACKs, and UPDATEs.
Неудивительно, что медиа, передаваемые в рамках сессии ранних медиа, называются ранними медиа. Модель шлюза состоит в управлении сессиями ранних медиа с помощью обменов предложением/ответом в надёжных предварительных ответах, PRACK и UPDATE.
The gateway model is seriously limited in the presence of forking, as described in Section 3.1. Therefore, its use is only acceptable when the User Agent (UA) cannot distinguish between early and regular media, as described in Section 3.4. In any other situation (the majority of UAs), use of the application server model described in Section 4 is strongly recommended instead.
Модель шлюза серьёзно ограничена при наличии разветвления, как описано в разделе 3.1. Поэтому её применение допустимо только тогда, когда пользовательский агент (UA) не может отличить ранние медиа от обычных, как описано в разделе 3.4. Во всех остальных случаях (а это большинство UA) вместо неё настоятельно рекомендуется использовать модель сервера приложений, описанную в разделе 4.
3.1. Forking
3.1. Разветвление
In the absence of forking, assuming that the initial INVITE contains an offer, the gateway model does not introduce media clipping. Following normal SIP procedures, the UAC is ready to play any incoming media as soon as it sends the initial offer in the INVITE. The UAS sends the answer in a reliable provisional response and can send media as soon as there is media to send. Even if the first media packets arrive at the UAC before the 1xx response, the UAC will play them.
При отсутствии разветвления, если начальный INVITE содержит предложение, модель шлюза не вносит обрезки медиа. Следуя обычным процедурам SIP, UAC готов воспроизводить любые входящие медиа сразу после отправки начального предложения в INVITE. UAS отправляет ответ в надёжном предварительном ответе и может отправлять медиа, как только появляются медиа для отправки. Даже если первые пакеты медиа приходят к UAC раньше ответа 1xx, UAC будет их воспроизводить.
Note that, in some situations, the UAC needs to receive the answer before being able to play any media. UAs in such a situation (e.g., QoS, media authorization, or media encryption is required) use preconditions to avoid media clipping.
Отметим, что в некоторых ситуациях UAC должен получить ответ, прежде чем сможет воспроизводить какие-либо медиа. UA в такой ситуации (например, когда требуются QoS, авторизация медиа или шифрование медиа) используют предусловия, чтобы избежать обрезки медиа.
On the other hand, if the INVITE forks, the gateway model may introduce media clipping. This happens when the UAC receives different answers to its offer in several provisional responses from different UASs. The UAC has to deal with bandwidth limitations and early media session selection. If the UAC receives early media from different UASs, it needs to present it to the user. If the early media consists of audio, playing several audio streams to the user at the same time may be confusing. On the other hand, other media types (e.g., video) can be presented to the user at the same time. For example, the UAC can build a mosaic with the different inputs.
С другой стороны, если INVITE разветвляется, модель шлюза может вносить обрезку медиа. Это происходит, когда UAC получает разные ответы на своё предложение в нескольких предварительных ответах от разных UAS. UAC приходится учитывать ограничения полосы пропускания и выбирать сессию ранних медиа. Если UAC получает ранние медиа от разных UAS, он должен представить их пользователю. Если ранние медиа состоят из аудио, одновременное воспроизведение пользователю нескольких аудиопотоков может сбивать с толку. С другой стороны, другие типы медиа (например, видео) могут быть представлены пользователю одновременно. Например, UAC может построить мозаику из разных входных потоков.
However, even with media types that can be played at the same time to the user, if the UAC has limited bandwidth, it will not be able to receive early media from all the different UASs at the same time. Therefore, many times, the UAC needs to choose a single early media session and "mute" those sending UPDATE requests.
Однако даже для типов медиа, которые можно воспроизводить пользователю одновременно, при ограниченной полосе пропускания UAC не сможет одновременно принимать ранние медиа от всех разных UAS. Поэтому во многих случаях UAC должен выбрать одну сессию ранних медиа, а остальные «заглушить», отправляя запросы UPDATE.
It is difficult to decide which early media sessions carry more important information from the caller's perspective. In fact, in some scenarios, the UA cannot even correlate media packets with their particular SIP early dialog. Therefore, UACs typically pick one early dialog randomly and mute the rest.
Трудно решить, какие сессии ранних медиа несут более важную информацию с точки зрения вызывающего. Более того, в некоторых сценариях UA даже не может сопоставить пакеты медиа с конкретным ранним диалогом SIP. Поэтому UAC обычно выбирают один ранний диалог случайным образом и заглушают остальные.
If one of the early media sessions that was muted transitions to a regular media session (i.e., the UAS sends a 2xx response), media clipping is likely. The UAC typically sends an UPDATE with a new offer (upon reception of the 200 (OK) for the INVITE) to unmute the media session. The UAS cannot send any media until it receives the offer from the UAC. Therefore, if the caller starts speaking before the offer from the UAC is received, his words will get lost.
Если одна из заглушённых сессий ранних медиа переходит в обычную медиасессию (то есть UAS отправляет ответ 2xx), вероятна обрезка медиа. Обычно UAC отправляет UPDATE с новым предложением (при получении 200 (OK) на INVITE), чтобы снять заглушение с медиасессии. UAS не может отправлять медиа, пока не получит предложение от UAC. Поэтому если вызывающий начнёт говорить до получения предложения от UAC, его слова будут потеряны.
Having the UAS send the UPDATE to unmute the media session (instead of the UAC) does not avoid media clipping in the backward direction and it causes possible race conditions.
Отправка UPDATE для снятия заглушения со стороны UAS (а не UAC) не устраняет обрезку медиа в обратном направлении и может вызвать состояния гонки.
3.2. Ringing Tone Generation
3.2. Генерация сигнала вызова
In the PSTN, telephone switches typically play ringing tones for the caller, indicating that the callee is being alerted. When, where, and how these ringing tones are generated has been standardized (i.e., the local exchange of the callee generates a standardized ringing tone while the callee is being alerted). It makes sense for a standardized approach to provide this type of feedback for the user in a homogeneous environment such as the PSTN, where all the terminals have a similar user interface.
В ТфОП телефонные коммутаторы обычно воспроизводят вызывающему сигнал вызова, указывая, что вызываемому подаётся вызывной сигнал. То, когда, где и как генерируются эти сигналы вызова, стандартизировано (то есть местная АТС вызываемого генерирует стандартизированный сигнал вызова, пока вызываемому подаётся вызывной сигнал). Стандартизированный подход имеет смысл для предоставления пользователю такой обратной связи в однородной среде, такой как ТфОП, где все терминалы имеют сходный пользовательский интерфейс.
This homogeneity is not found among SIP user agents. SIP user agents have different capabilities, different user interfaces, and may be used to establish sessions that do not involve audio at all. Because of this, the way a SIP UA provides the user with information about the progress of session establishment is a matter of local policy. For example, a UA with a Graphical User Interface (GUI) may choose to display a message on the screen when the callee is being alerted, while another UA may choose to show a picture of a phone ringing instead. Many SIP UAs choose to imitate the user interface of the PSTN phones. They provide a ringing tone to the caller when the callee is being alerted. Such a UAC is supposed to generate ringing tones locally for its user as long as no early media is received from the UAS. If the UAS generates early media (e.g., an announcement or a special ringing tone), the UAC is supposed to play it rather than generate the ringing tone locally.
Такой однородности среди пользовательских агентов SIP нет. Пользовательские агенты SIP обладают разными возможностями, разными пользовательскими интерфейсами и могут использоваться для установления сессий, вообще не связанных с аудио. Поэтому то, как SIP UA предоставляет пользователю информацию о ходе установления сессии, относится к области локальных правил. Например, UA с графическим пользовательским интерфейсом (GUI) может при подаче вызывного сигнала вызываемому выводить сообщение на экран, а другой UA может вместо этого показывать изображение звонящего телефона. Многие SIP UA стремятся имитировать пользовательский интерфейс телефонов ТфОП. Они предоставляют вызывающему сигнал вызова, когда вызываемому подаётся вызывной сигнал. Такой UAC должен локально генерировать сигнал вызова для своего пользователя до тех пор, пока от UAS не получены ранние медиа. Если UAS генерирует ранние медиа (например, объявление или специальный сигнал вызова), UAC должен воспроизводить их, а не генерировать сигнал вызова локально.
The problem is that, sometimes, it is not an easy task for a UAC to know whether it will be receiving early media or it should generate local ringing. A UAS can send early media without using reliable provisional responses (very simple UASs do that) or it can send an answer in a reliable provisional response without any intention of sending early media (this is the case when preconditions are used). Therefore, by only looking at the SIP signalling, a UAC cannot be sure whether or not there will be early media for a particular session. The UAC needs to check if media packets are arriving at a given moment.
Проблема в том, что иногда UAC непросто определить, будет ли он получать ранние медиа или ему следует генерировать локальный сигнал вызова. UAS может отправлять ранние медиа без использования надёжных предварительных ответов (так поступают очень простые UAS) или может отправить ответ в надёжном предварительном ответе, вовсе не намереваясь отправлять ранние медиа (так бывает при использовании предусловий). Поэтому, глядя только на сигнализацию SIP, UAC не может быть уверен, будут ли для конкретной сессии ранние медиа. UAC должен проверять, приходят ли пакеты медиа в данный момент.
An implementation could even choose to look at the contents of the media packets, since they could carry only silence or comfort noise.
Реализация могла бы даже выбрать просмотр содержимого пакетов медиа, поскольку они могут нести только тишину или комфортный шум.
With this in mind, a UAC should develop its local policy regarding local ringing generation. For example, a POTS ("Plain Old Telephone Service")-like SIP User Agent (UA) could implement the following local policy:
С учётом сказанного UAC следует выработать свои локальные правила генерации локального сигнала вызова. Например, SIP-пользовательский агент (UA), подобный телефону ТфОП («Plain Old Telephone Service»), мог бы реализовать следующие локальные правила:
1. Unless a 180 (Ringing) response is received, never generate local ringing.
1. Если не получен ответ 180 (Ringing), никогда не генерировать локальный сигнал вызова.
2. If a 180 (Ringing) has been received but there are no incoming media packets, generate local ringing.
2. Если ответ 180 (Ringing) получен, но входящих пакетов медиа нет, генерировать локальный сигнал вызова.
3. If a 180 (Ringing) has been received and there are incoming media packets, play them and do not generate local ringing.
3. Если ответ 180 (Ringing) получен и входящие пакеты медиа есть, воспроизводить их и не генерировать локальный сигнал вызова.
Note that a 180 (Ringing) response means that the callee is being alerted, and a UAS should send such a response if the callee is being alerted, regardless of the status of the early media session.
Отметим, что ответ 180 (Ringing) означает, что вызываемому подаётся вызывной сигнал, и UAS должен отправлять такой ответ, если вызываемому подаётся вызывной сигнал, независимо от состояния сессии ранних медиа.
At first sight, such a policy may look difficult to implement in decomposed UAs (i.e., media gateway controller and media gateway), but this policy is the same as the one described in Section 2, which must be implemented by any UA. That is, any UA should play incoming media packets (and stop local ringing tone generation if it was being performed) in order to avoid media clipping, even if the 200 (OK) response has not arrived. So, the tools to implement this early media policy are already available to any UA that uses SIP.
На первый взгляд такая политика может показаться трудной для реализации в декомпозированных UA (то есть в контроллере медиашлюза и медиашлюзе), но эта политика совпадает с описанной в разделе 2, которую должен реализовать любой UA. А именно: любой UA должен воспроизводить входящие пакеты медиа (и прекращать генерацию локального сигнала вызова, если она выполнялась), чтобы избежать обрезки медиа, даже если ответ 200 (OK) ещё не пришёл. Таким образом, средства для реализации этой политики ранних медиа уже доступны любому UA, использующему SIP.
Note that, while it is not desirable to standardize a common local policy to be followed by every SIP UA, a particular subset of more or less homogeneous SIP UAs could use the same local policy by convention. Examples of such subsets of SIP UAs may be "all the PSTN/SIP gateways" or "every 3GPP IMS (Third Generation Partnership Project Internet Multimedia System) terminal". However, defining the particular common policy that such groups of SIP devices may use is outside the scope of this document.
Отметим, что хотя стандартизировать общее локальное правило, которому должен следовать каждый SIP UA, нежелательно, некоторое подмножество более или менее однородных SIP UA могло бы по соглашению использовать одни и те же локальные правила. Примерами таких подмножеств SIP UA могут быть «все шлюзы ТфОП/SIP» или «каждый терминал 3GPP IMS (Third Generation Partnership Project Internet Multimedia System)». Однако определение конкретных общих правил, которые могли бы использовать такие группы устройств SIP, выходит за рамки настоящего документа.
3.3. Absence of an Early Media Indicator
3.3. Отсутствие индикатора ранних медиа
SIP, as opposed to other signalling protocols, does not provide an early media indicator. That is, there is no information about the presence or absence of early media in SIP. Such an indicator could be potentially used to avoid the generation of local ringing tone by the UAC when UAS intends to provide an in-band ringing tone or some type of announcement. However, in the majority of the cases, such an indicator would be of little use due to the way SIP works.
SIP, в отличие от других протоколов сигнализации, не предоставляет индикатор ранних медиа. То есть в SIP нет информации о наличии или отсутствии ранних медиа. Такой индикатор потенциально мог бы использоваться, чтобы UAC не генерировал локальный сигнал вызова, когда UAS намеревается предоставить сигнал вызова в полосе или какое-либо объявление. Однако в большинстве случаев такой индикатор был бы малополезен из-за того, как работает SIP.
One important reason limiting the benefit of a potential early media indicator is the loose coupling between SIP signalling and the media path. SIP signalling traverses a different path than the media. The media path is typically optimized to reduce the end-to-end delay (e.g., minimum number of intermediaries), while the SIP signalling path typically traverses a number of proxies providing different services for the session. Hence, it is very likely that the media packets with early media reach the UAC before any SIP message that could contain an early media indicator.
Одна важная причина, ограничивающая пользу потенциального индикатора ранних медиа, — слабая связанность между сигнализацией SIP и путём медиа. Сигнализация SIP проходит иной путь, нежели медиа. При этом путь медиа обычно оптимизируется для уменьшения сквозной задержки (например, минимизируется число посредников), тогда как путь сигнализации SIP обычно проходит через ряд прокси-серверов, предоставляющих для сессии различные услуги. Следовательно, весьма вероятно, что пакеты медиа с ранними медиа достигнут UAC раньше любого сообщения SIP, которое могло бы содержать индикатор ранних медиа.
Nevertheless, sometimes SIP responses arrive at the UAC before any media packet. There are situations in which the UAS intends to send early media but cannot do it straight away. For example, UAs using Interactive Connectivity Establishment (ICE) [6] may need to exchange several Simple Traversals of the UDP Protocol through NAT (STUN) messages before being able to exchange media. In this situation, an early media indicator would keep the UAC from generating a local ringing tone during this time. However, while the early media is not arriving at the UAC, the user would not be aware that the remote user is being alerted, even though a 180 (Ringing) had been received. Therefore, a better solution would be to apply a local ringing tone until the early media packets could be sent from the UAS to the UAC. This solution does not require any early media indicator. Note that migrations from local ringing tone to early media at the UAC happen in the presence of forking as well; one UAS sends a 180 (Ringing) response, and later, another UAS starts sending early media.
Тем не менее иногда ответы SIP приходят к UAC раньше любого пакета медиа. Бывают ситуации, когда UAS намеревается отправить ранние медиа, но не может сделать это сразу. Например, UA, использующим Interactive Connectivity Establishment (ICE) [6], может потребоваться обменять несколько сообщений STUN (Simple Traversals of the UDP Protocol through NAT), прежде чем они смогут обмениваться медиа. В этой ситуации индикатор ранних медиа не позволял бы UAC генерировать локальный сигнал вызова в течение этого времени. Однако, пока ранние медиа не поступают к UAC, пользователь не знал бы, что удалённому пользователю подаётся вызывной сигнал, даже если ответ 180 (Ringing) был получен. Поэтому лучшим решением было бы применять локальный сигнал вызова до тех пор, пока пакеты ранних медиа не смогут быть отправлены от UAS к UAC. Это решение не требует индикатора ранних медиа. Отметим, что переход от локального сигнала вызова к ранним медиа на UAC происходит и при разветвлении; один UAS отправляет ответ 180 (Ringing), а позже другой UAS начинает отправлять ранние медиа.
3.4. Applicability of the Gateway Model
3.4. Применимость модели шлюза
Section 3 described some of the limitations of the gateway model. It produces media clipping in forking scenarios and requires media detection to generate local ringing properly. These issues are addressed by the application server model, described in Section 4, which is the recommended way of generating early media that is not continuous with the regular media generated during the session.
В разделе 3 описаны некоторые ограничения модели шлюза. Она порождает обрезку медиа в сценариях разветвления и требует обнаружения медиа для правильной генерации локального сигнала вызова. Эти проблемы решает модель сервера приложений, описанная в разделе 4, которая является рекомендуемым способом генерации ранних медиа, не являющихся непрерывными с обычными медиа, генерируемыми в ходе сессии.
The gateway model is, therefore, acceptable in situations where the UA cannot distinguish between early media and regular media. A PSTN gateway is an example of this type of situation. The PSTN gateway receives media from the PSTN over a circuit, and sends it to the IP network. The gateway is not aware of the contents of the media, and it does not exactly know when the transition from early to regular media takes place. From the PSTN perspective, the circuit is a continuous source of media.
Поэтому модель шлюза приемлема в тех ситуациях, когда UA не может отличить ранние медиа от обычных медиа. Шлюз ТфОП служит примером такой ситуации. Шлюз ТфОП получает медиа из сети ТфОП по выделенному каналу и передаёт их в сеть IP. Шлюз не осведомлён о содержимом медиа и точно не знает, в какой момент происходит переход от ранних медиа к обычным медиа. С точки зрения ТфОП этот выделенный канал является непрерывным источником медиа.
4. The Application Server Model
4. Модель сервера приложений
The application server model consists of having the UAS behave as an application server to establish early media sessions with the UAC. The UAC indicates support for the early-session disposition type (defined in [2]) using the early-session option tag. This way, UASs know that they can keep offer/answer exchanges for early media (early-session disposition type) separate from regular media (session disposition type).
Модель сервера приложений состоит в том, что UAS выступает в роли сервера приложений для установления сессий ранних медиа с UAC. UAC указывает поддержку типа диспозиции early-session (определённого в [2]) с помощью тега опции early-session. Так UAS узнают, что могут отделять обмены предложением/ответом для ранних медиа (тип диспозиции early-session) от обычных медиа (тип диспозиции session).
Sending early media using a different offer/answer exchange than the one used for sending regular media helps avoid media clipping in cases of forking. The UAC can reject or mute new offers for early media without muting the sessions that will carry media when the original INVITE is accepted. The UAC can give priority to media received over the latter sessions. This way, the application server model transitions from early to regular media at the right moment.
Отправка ранних медиа с помощью обмена предложением/ответом, отличного от используемого для обычных медиа, помогает избежать обрезки медиа в случаях разветвления. UAC может отклонять новые предложения для ранних медиа или заглушать их, не заглушая сессии, которые будут нести медиа после принятия исходного INVITE. UAC может отдавать приоритет медиа, полученным в этих последних сессиях. Так модель сервера приложений переходит от ранних медиа к обычным в нужный момент.
Having a separate offer/answer exchange for early media also helps UACs decide whether or not local ringing should be generated. If a new early session is established and that early session contains at least an audio stream, the UAC can assume that there will be incoming early media and it can then avoid generating local ringing. An alternative model would include the addition of a new stream, with an "early media" label, to the original session between the UAC and the UAS using an UPDATE instead of establishing a new early session. We have chosen to establish a new early session to be coherent with the mechanism used by application servers that are NOT co-located with the UAS. This way, the UAS uses the same mechanism as any application server in the network to interact with the UAC.
Наличие отдельного обмена предложением/ответом для ранних медиа также помогает UAC решать, следует ли генерировать локальный сигнал вызова. Если установлена новая ранняя сессия и эта ранняя сессия содержит хотя бы один аудиопоток, UAC может предположить, что будут входящие ранние медиа, и тогда может не генерировать локальный сигнал вызова. Альтернативная модель предусматривала бы добавление нового потока с меткой «ранние медиа» к исходной сессии между UAC и UAS с помощью UPDATE вместо установления новой ранней сессии. Мы решили устанавливать новую раннюю сессию, чтобы быть согласованными с механизмом, используемым серверами приложений, которые НЕ размещены совместно с UAS. Так UAS использует тот же механизм, что и любой сервер приложений в сети, для взаимодействия с UAC.
4.1. In-Band Versus Out-of-Band Session Progress Information
4.1. Информация о ходе сессии в полосе и вне полосы
Note that, even when the application server model is used, a UA will have to choose which early media sessions are muted and which ones are rendered to the user. In order to make this choice easier for UAs, it is strongly recommended that information that is not essential for the session not be transmitted using early media. For instance, UAs should not use early media to send special ringing tones. The status code and the reason phrase in SIP can already inform the remote user about the progress of session establishment, without incurring the problems associated with early media.
Отметим, что даже при использовании модели сервера приложений UA придётся выбирать, какие сессии ранних медиа заглушить, а какие воспроизводить пользователю. Чтобы облегчить UA этот выбор, настоятельно рекомендуется не передавать с помощью ранних медиа информацию, не являющуюся существенной для сессии. Например, UA не следует использовать ранние медиа для передачи специальных сигналов вызова. Код состояния и фраза причины в SIP уже могут информировать удалённого пользователя о ходе установления сессии, не вызывая проблем, связанных с ранними медиа.
5. Alert-Info Header Field
5. Поле заголовка Alert-Info
The Alert-Info header field allows specifying an alternative ringing content, such as ringing tone, to the UAC. This header field tells the UAC which tone should be played in case local ringing is generated, but it does not tell the UAC when to generate local ringing. A UAC should follow the rules described above for ringing tone generation in both models. If, after following those rules, the UAC decides to play local ringing, it can then use the Alert-Info header field to generate it.
Поле заголовка Alert-Info позволяет указать UAC альтернативное содержимое вызова, например сигнал вызова. Это поле заголовка сообщает UAC, какой сигнал следует воспроизводить в случае генерации локального сигнала вызова, но не сообщает UAC, когда генерировать локальный сигнал вызова. UAC должен следовать описанным выше правилам генерации сигнала вызова в обеих моделях. Если после следования этим правилам UAC решает воспроизводить локальный сигнал вызова, он может затем использовать поле заголовка Alert-Info для его генерации.
6. Security Considerations
6. Вопросы безопасности
SIP uses the offer/answer model [3] to establish early sessions in both the gateway and the application server models. User Agents (UAs) generate a session description, which contains the transport address (i.e., IP address plus port) where they want to receive media, and send it to their peer in a SIP message. When media packets arrive at this transport address, the UA assumes that they come from the receiver of the SIP message carrying the session description. Nevertheless, attackers may attempt to gain access to the contents of the SIP message and send packets to the transport address contained in the session description. To prevent this situation, UAs SHOULD encrypt their session descriptions (e.g., using S/MIME). Still, even if a UA encrypts its session descriptions, an attacker may try to guess the transport address used by the UA and send media packets to that address. Guessing such a transport address is sometimes easier than it may seem because many UAs always pick up the same initial media port. To prevent this situation, UAs SHOULD use media-level authentication mechanisms such as the Secure Realtime Transport Protocol (SRTP)[7]. In addition, UAs that wish to keep their communications confidential SHOULD use media-level encryption mechanisms (e.g, SRTP [7]).
SIP использует модель «предложение/ответ» [3] для установления ранних сессий как в модели шлюза, так и в модели сервера приложений. Пользовательские агенты (UA) генерируют описание сессии, которое содержит транспортный адрес (то есть IP-адрес и порт), по которому они хотят принимать медиа, и отправляют его своему партнёру в сообщении SIP. Когда пакеты медиа прибывают на этот транспортный адрес, UA предполагает, что они пришли от получателя сообщения SIP, содержащего описание сессии. Тем не менее злоумышленники могут попытаться получить доступ к содержимому сообщения SIP и отправлять пакеты на транспортный адрес, указанный в описании сессии. Чтобы предотвратить эту ситуацию, UA СЛЕДУЕТ шифровать свои описания сессии (например, с помощью S/MIME). Однако даже если UA шифрует свои описания сессии, злоумышленник может попытаться угадать транспортный адрес, используемый UA, и отправлять пакеты медиа на этот адрес. Угадать такой транспортный адрес иногда проще, чем кажется, поскольку многие UA всегда выбирают один и тот же начальный порт медиа. Чтобы предотвратить эту ситуацию, UA СЛЕДУЕТ применять механизмы аутентификации на уровне медиа, такие как Secure Realtime Transport Protocol (SRTP) [7]. Кроме того, UA, желающим сохранить конфиденциальность своих коммуникаций, СЛЕДУЕТ использовать механизмы шифрования на уровне медиа (например, SRTP [7]).
Attackers may attempt to make a UA send media to a victim as part of a DoS attack. This can be done by sending a session description with the victim's transport address to the UA. To prevent this attack, the UA SHOULD engage in a handshake with the owner of the transport address received in a session description (just verifying willingness to receive media) before sending a large amount of data to the transport address. This check can be performed by using a connection oriented transport protocol, by using STUN [8] in an end-to-end fashion, or by the key exchange in SRTP [7].
Злоумышленники могут попытаться заставить UA отправлять медиа жертве в рамках атаки типа DoS. Это можно сделать, отправив UA описание сессии с транспортным адресом жертвы. Чтобы предотвратить такую атаку, UA СЛЕДУЕТ выполнить рукопожатие с владельцем транспортного адреса, полученного в описании сессии (просто проверяя готовность принимать медиа), прежде чем отправлять на этот транспортный адрес большой объём данных. Такую проверку можно выполнить с помощью транспортного протокола с установлением соединения, с помощью STUN [8] в сквозном режиме или с помощью обмена ключами в SRTP [7].
In any event, note that the previous security considerations are not early media specific, but apply to the usage of the offer/answer model in SIP to establish sessions in general.
В любом случае отметим, что предыдущие соображения безопасности не специфичны для ранних медиа, а относятся к использованию модели «предложение/ответ» в SIP для установления сессий вообще.
Additionally, an early media-specific risk (roughly speaking, equivalent to forms of "toll fraud" in the PSTN) attempts to exploit the different charging policies some operators apply to early and regular media. When UAs are allowed to exchange early media for free, but are required to pay for regular media sessions, rogue UAs may try to establish a bidirectional early media session and never send a 200 (OK) response for the INVITE.
Кроме того, риск, специфичный для ранних медиа (грубо говоря, эквивалентный формам «мошенничества с оплатой» в ТфОП), пытается использовать различия в политиках тарификации, которые некоторые операторы применяют к ранним и обычным медиа. Когда UA разрешено бесплатно обмениваться ранними медиа, но требуется платить за обычные медиасессии, недобросовестные UA могут попытаться установить двунаправленную сессию ранних медиа и никогда не отправить ответ 200 (OK) на INVITE.
On the other hand, some application servers (e.g., Interactive Voice Response systems) use bidirectional early media to obtain information from the callers (e.g., the PIN code of a calling card). So, we do not recommend that operators disallow bidirectional early media. Instead, operators should consider a remedy of charging early media exchanges that last too long, or stopping them at the media level (according to the operator's policy).
С другой стороны, некоторые серверы приложений (например, системы интерактивного голосового ответа) используют двунаправленные ранние медиа для получения информации от вызывающих (например, PIN-кода телефонной карты). Поэтому мы не рекомендуем операторам запрещать двунаправленные ранние медиа. Вместо этого операторам следует рассмотреть меру в виде тарификации обменов ранними медиа, которые длятся слишком долго, или их остановки на уровне медиа (в соответствии с политикой оператора).
