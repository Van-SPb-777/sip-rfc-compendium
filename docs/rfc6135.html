An Alternative Connection Model for the Message Session Relay Protocol (MSRP)
Альтернативная модель соединения для протокола ретрансляции сеансов сообщений (MSRP)
Abstract
Аннотация
This document defines an alternative connection model for Message Session Relay Protocol (MSRP) User Agents (UAs); this model uses the connection-oriented media (COMEDIA) mechanism in order to create the MSRP transport connection. The model allows MSRP UAs behind Network Address Translators (NATs) to negotiate which endpoint initiates the establishment of the Transmission Control Protocol (TCP) connection, in order for MSRP messages to traverse the NAT.
Настоящий документ определяет альтернативную модель соединения для пользовательских агентов (UA) протокола ретрансляции сеансов сообщений (MSRP); эта модель использует механизм медиаданных, ориентированных на соединения (COMEDIA), для создания транспортного соединения MSRP. Модель позволяет пользовательским агентам MSRP, находящимся за трансляторами сетевых адресов (NAT), согласовывать, какая конечная точка инициирует установление соединения по протоколу управления передачей (TCP), чтобы сообщения MSRP проходили через NAT.

1. Introduction
1. Введение
The Message Session Relay Protocol (MSRP) core specification [RFC4975] states that the MSRP User Agent (UA) that sends the Session Description Protocol (SDP) offer is "active", and it is responsible for creating the MSRP transport connection towards the remote UA if a new connection is required. The core specification also allows, but does not define, alternate mechanisms for MSRP UAs to create MSRP transport connections.
Базовая спецификация протокола ретрансляции сеансов сообщений (MSRP) [RFC4975] указывает, что пользовательский агент (UA) MSRP, отправляющий предложение по протоколу описания сеансов (SDP), является «активным» и отвечает за создание транспортного соединения MSRP с удалённым UA, если требуется новое соединение. Базовая спецификация также допускает, но не определяет альтернативные механизмы создания транспортных соединений MSRP пользовательскими агентами MSRP.
[RFC4145] defines a connection-oriented media (COMEDIA) mechanism, which endpoints can use to negotiate the endpoint that initiates the creation of media transport connection.
В [RFC4145] определён механизм медиаданных с установлением соединения (COMEDIA), позволяющий конечным точкам согласовать, какая из них инициирует создание транспортного соединения медиаданных.
COMEDIA is especially useful when one of the endpoints is located behind a Network Address Translator (NAT). The endpoint can use the mechanism to indicate that it will create the media transport connection, in order for the media to traverse the NAT without the usage of relays and without being required to support more complex mechanisms (e.g., "TCP Candidates with Interactive Connectivity Establishment (ICE)" [ICE-TCP]). In addition, COMEDIA allows the usage of identical procedures in establishing Transmission Control Protocol (TCP) [RFC0793] connections for different types of media.
COMEDIA особенно полезна, когда одна из конечных точек находится за транслятором сетевых адресов (NAT). Конечная точка может использовать этот механизм, чтобы указать, что она создаст транспортное соединение медиаданных, — это позволяет медиаданным проходить через NAT без использования ретрансляторов и без необходимости поддерживать более сложные механизмы (например, «кандидаты TCP с интерактивным установлением соединения (ICE)» [ICE-TCP]). Кроме того, COMEDIA позволяет применять одинаковые процедуры при установлении соединений по протоколу управления передачей (TCP) [RFC0793] для различных типов медиаданных.
An example is the Open Mobile Alliance (OMA)-defined "Instant Message using SIMPLE" [OMA-SIMPLE], where one MSRP UA of every MSRP transport connection represents a media server, which is always located in the carrier network. The media server has a globally reachable IP address and handles application-specific policy control as well as NAT traversal. The OMA IM (Instant Messenger) uses COMEDIA for NAT traversal, and all OMA IM MSRP clients support COMEDIA.
Примером служит определённая Open Mobile Alliance (OMA) спецификация «Instant Message using SIMPLE» [OMA-SIMPLE], где один пользовательский агент MSRP каждого транспортного соединения MSRP представляет сервер медиаданных, который всегда расположен в сети оператора. Сервер медиаданных имеет глобально доступный IP-адрес и выполняет управление политиками на уровне приложения, а также обход NAT. OMA IM (Instant Messenger) использует COMEDIA для обхода NAT, и все клиенты MSRP OMA IM поддерживают COMEDIA.
This document defines how an MSRP UA uses COMEDIA in order to negotiate which UA will create the MSRP transport TCP connection towards the other UA. The document also defines how an MSRP UA that uses COMEDIA can establish an MSRP transport connection with a remote UA that does not support COMEDIA.
Настоящий документ определяет, как пользовательский агент MSRP использует COMEDIA для согласования того, какой UA создаст транспортное TCP-соединение MSRP с другим UA. Документ также определяет, как UA MSRP, использующий COMEDIA, может установить транспортное соединение MSRP с удалённым UA, который не поддерживает COMEDIA.

3. Applicability Statement
3. Заявление о применимости
Support of this specification is OPTIONAL for MSRP UAs in general. UAs that are likely to be deployed in networks with NATs SHOULD support this specification. It will improve the odds of being able to make TCP connections successfully traverse NATs, since UAs behind NATs can be requested to initiate the establishment of the TCP connections.
Поддержка настоящей спецификации в целом ЯВЛЯЕТСЯ НЕОБЯЗАТЕЛЬНОЙ для пользовательских агентов MSRP. UA, которые, вероятно, будут развёрнуты в сетях с NAT, СЛЕДУЕТ поддерживать настоящую спецификацию. Это повысит шансы на успешное прохождение TCP-соединений через NAT, поскольку UA, находящиеся за NAT, можно попросить инициировать установление TCP-соединений.
4. COMEDIA for MSRP
4. COMEDIA для MSRP
4.1. General
4.1. Общие положения
This section defines how an MSRP UA that supports this specification uses the COMEDIA SDP attributes defined in [RFC4145].
В этом разделе описано, как пользовательский агент MSRP, поддерживающий настоящую спецификацию, применяет атрибуты COMEDIA протокола SDP из [RFC4145].
4.2. a=setup
4.2. a=setup
4.2.1. General
4.2.1. Общие положения
An MSRP UA uses the SDP a=setup attribute [RFC4145] in order to negotiate which endpoint will create the MSRP transport connection towards the other UA.
Пользовательский агент MSRP использует атрибут a=setup протокола SDP [RFC4145], чтобы согласовать, какая конечная точка создаст транспортное соединение MSRP с другой конечной точкой.
An MSRP UA MUST always include an explicit a=setup attribute in its SDP offers and answers, since it might be useful for the other endpoint, or for entities in the network, to know whether the UA supports COMEDIA or not. An MSRP UA MUST support the a=setup "active", "actpass", and "passive" attribute values. An MSRP UA MUST NOT send the "holdconn" attribute value. If an MSRP UA receives the "holdconn" attribute value, it MUST ignore it and process the message as if it did not contain an a=setup attribute.
Пользовательский агент MSRP ДОЛЖЕН всегда включать явный атрибут a=setup в свои предложения и ответы SDP, поскольку другой конечной точке или объектам в сети может быть полезно знать, поддерживает ли UA COMEDIA. Пользовательский агент MSRP ДОЛЖЕН поддерживать значения атрибута a=setup «active», «actpass» и «passive». Пользовательский агент MSRP НЕ ДОЛЖЕН отправлять значение атрибута «holdconn». Если пользовательский агент MSRP получает значение атрибута «holdconn», он ДОЛЖЕН игнорировать его и обрабатывать сообщение так, как если бы оно не содержало атрибута a=setup.
4.2.2. Attribute Usage
4.2.2. Применение атрибута
When the a=setup attribute value is "actpass" or "passive", the IP address and port values in the MSRP URI of the SDP a=path attribute MUST contain the actual address and port values on which the UA can receive a TCP connection for the MSRP transport connection.
Когда значение атрибута a=setup — «actpass» или «passive», значения IP-адреса и порта в URI MSRP атрибута a=path протокола SDP ДОЛЖНЫ содержать фактические значения адреса и порта, на которых UA может принимать TCP-соединение для транспортного соединения MSRP.
In accordance with [RFC4145], if the a=setup attribute value is "active", the port number value should be 9.
В соответствии с [RFC4145], если значение атрибута a=setup — «active», значением номера порта следует считать 9.
If an MSRP UA can provide a globally reachable IP address that the other endpoint can use as a destination for a TCP connection, the UA MUST use the a=setup "actpass" attribute value in SDP offers. This is in order to allow the remote UA to send an SDP answer with an a=setup "active" attribute value if the UA is located behind a NAT, and in order to be compatible with UAs that do not support COMEDIA and thus always will act as passive endpoints. If an MSRP UA cannot provide the actual transport address, the UA MUST use the a=setup "active" attribute value.
Если пользовательский агент MSRP может предоставить глобально доступный IP-адрес, который другая конечная точка может использовать как пункт назначения для TCP-соединения, UA ДОЛЖЕН использовать в предложениях SDP значение атрибута a=setup «actpass». Это делается для того, чтобы удалённый UA мог отправить ответ SDP со значением атрибута a=setup «active», если UA находится за NAT, и чтобы обеспечить совместимость с UA, которые не поддерживают COMEDIA и потому всегда будут действовать как пассивные конечные точки. Если пользовательский агент MSRP не может предоставить фактический транспортный адрес, UA ДОЛЖЕН использовать значение атрибута a=setup «active».
The UA MUST NOT use the a=setup "passive" attribute value in an SDP offer.
UA НЕ ДОЛЖЕН использовать значение атрибута a=setup «passive» в предложении SDP.
The MSRP UA can determine that it provides a globally reachable IP address in the following scenarios:
Пользовательский агент MSRP может определить, что он предоставляет глобально доступный IP-адрес, в следующих сценариях:
o the UA can determine that it is not located behind a NAT;
o UA может определить, что он не расположен за NAT;
o the UA relays its MSRP transport connections via a relay (e.g., an MSRP relay or Traversal Using Relay NAT (TURN) server); or
o UA ретранслирует свои транспортные соединения MSRP через ретранслятор (например, ретранслятор MSRP или сервер TURN (Traversal Using Relay NAT)); или
o the UA has used Session Traversal Utilities for NAT (STUN) [RFC5389] signaling to retrieve the NAT address and port through the local port to be used for the eventual transport connection, while also having determined that the NAT has endpoint-independent mapping and filtering behavior [RFC5382], e.g., using the mechanism defined in [RFC5780].
o UA использовал сигнализацию Session Traversal Utilities for NAT (STUN) [RFC5389], чтобы получить адрес и порт NAT через локальный порт, который будет использоваться для итогового транспортного соединения, и при этом определил, что NAT обладает независимым от конечной точки поведением отображения и фильтрации [RFC5382], например с помощью механизма, определённого в [RFC5780].
Some UAs can determine whether the SIP [RFC3261] signaling has traversed a NAT by inspecting the SIP Via header field in the 200 (OK) response to the initial SIP REGISTER request, and comparing the IP addresses in the Via sent-by and the received header field parameters. If the IP addresses are not the same, then the UA can determine that there is a NAT in the path. Even though the media transport might not traverse the NAT, it is safe to assume that it will. This comparing mechanism does not work in all scenarios, though. For example, if SIP a request crosses a SIP proxy before crossing a NAT, the UA will not be able to detect the NAT by comparing the IP addresses.
Некоторые UA могут определить, прошла ли сигнализация SIP [RFC3261] через NAT, проверив поле заголовка SIP Via в ответе 200 (OK) на начальный запрос SIP REGISTER и сравнив IP-адреса в параметрах sent-by заголовка Via и received. Если IP-адреса не совпадают, UA может определить, что на пути есть NAT. Даже если транспорт медиаданных может не проходить через NAT, можно с уверенностью предположить, что он будет через него проходить. Однако этот механизм сравнения работает не во всех сценариях. Например, если запрос SIP проходит через прокси-сервер SIP до пересечения NAT, UA не сможет обнаружить NAT путём сравнения IP-адресов.
If an SDP offer includes an a=setup "actpass" attribute value, the SDP answerer MAY include an a=setup "active" attribute value in the SDP answer, but SHOULD include an a=setup "passive" attribute value if it knows that it is not located behind a NAT.
Если предложение SDP содержит значение атрибута a=setup «actpass», сторона, отвечающая на SDP, МОЖЕТ включить в ответ SDP значение атрибута a=setup «active», но СЛЕДУЕТ включить значение атрибута a=setup «passive», если она знает, что не находится за NAT.
Once the active UA has established the MSRP transport connection, the UA must immediately send an MSRP SEND request, as defined in [RFC4975].
Как только активный UA установил транспортное соединение MSRP, UA должен немедленно отправить запрос MSRP SEND, как определено в [RFC4975].
NOTE: According to [RFC4975], the initiating UA is always active, but when COMEDIA is used, the a=setup attribute is used to negotiate which UA becomes active.
ПРИМЕЧАНИЕ: согласно [RFC4975], инициирующий UA всегда активен, но при использовании COMEDIA атрибут a=setup служит для согласования того, какой UA станет активным.
4.3. TLS
4.3. TLS
If an MSRP UA conformant to this document uses Transport Layer Security (TLS), it MUST use the TLS mechanisms defined in [RFC4975] and [RFC4976].
Если UA MSRP, соответствующий настоящему документу, использует безопасность транспортного уровня (TLS), он ДОЛЖЕН применять механизмы TLS, определённые в [RFC4975] и [RFC4976].
According to [RFC4975], the connection can be established with or without TLS mutual authentication. In case mutual authentication is not used, the listening device waits until it receives a request on the connection, at which time it infers the identity of the connecting device from the associated session description. From the TLS authentication point of view, it is thus irrelevant whether an endpoint takes the active or passive role.
Согласно [RFC4975], соединение может быть установлено с взаимной аутентификацией TLS или без неё. Если взаимная аутентификация не используется, прослушивающее устройство ждёт, пока не получит запрос по соединению, и в этот момент выводит идентичность подключающегося устройства из связанного описания сеанса. С точки зрения аутентификации TLS, таким образом, не имеет значения, какую роль — активную или пассивную — принимает конечная точка.
If an MSRP UA uses a self-signed TLS certificate to authenticate itself to MSRP peers, it also includes its certificate fingerprint in the SDP.
Если пользовательский агент MSRP использует самоподписанный сертификат TLS для аутентификации перед одноранговыми узлами MSRP, он также включает отпечаток своего сертификата в SDP.
Note that fingerprints can only be exchanged in peer-to-peer communication, as MSRP relays [RFC4976] will not receive the SDP payloads containing the fingerprint attributes.
Отметим, что отпечатки можно обменивать только при одноранговой связи, поскольку ретрансляторы MSRP [RFC4976] не получают полезные нагрузки SDP, содержащие атрибуты отпечатков.
4.4. a=connection
4.4. a=connection
MSRP UAs MUST NOT use the SDP a=connection attribute. [RFC4975] defines connection reuse procedures for MSRP, and this document does not modify those procedures. If an MSRP UA receives an a=connection attribute, the UA MUST ignore it.
Пользовательские агенты MSRP НЕ ДОЛЖНЫ использовать атрибут a=connection в SDP. [RFC4975] определяет процедуры повторного использования соединений для MSRP, и настоящий документ их не изменяет. Если UA MSRP получает атрибут a=connection, он ДОЛЖЕН игнорировать его.
4.5. MSRP Relay Connection
4.5. Соединение с ретранслятором MSRP
If an MSRP UA is located behind an MSRP relay [RFC4976], the UA MUST always initiate a transport connection towards the relay, no matter what value the client has provided in the a=setup attribute.
Если пользовательский агент MSRP находится за ретранслятором MSRP [RFC4976], UA ДОЛЖЕН всегда инициировать транспортное соединение с ретранслятором, независимо от того, какое значение клиент указал в атрибуте a=setup.
NOTE: Even if an MSRP UA initiates the TCP connection towards its relay, the UA will only send a SEND request if the UA is active, based on the COMEDIA negotiation.
ПРИМЕЧАНИЕ: даже если пользовательский агент MSRP инициирует TCP-соединение со своим ретранслятором, UA отправит запрос SEND только в том случае, если он активен по результатам согласования COMEDIA.
5. Interoperability with the Connection Model Defined in RFC 4975
5. Взаимодействие с моделью соединения, определённой в RFC 4975
An MSRP UA conformant to this document can interoperate with a UA that follows the connection model defined in [RFC4975]. However, if an MSRP UA conformant to this document is located behind a NAT, does not proxy its MSRP communication via an MSRP relay, and receives an SDP offer from a remote UA that follows the connection model defined in [RFC4975], then NAT traversal can only be achieved if the MSRP UA supports ICE [ICE-TCP] or if the network supports Session Border Controller (SBC)-assisted NAT traversal for TCP.
Пользовательский агент MSRP, соответствующий настоящему документу, может взаимодействовать с UA, который следует модели соединения, определённой в [RFC4975]. Однако если UA MSRP, соответствующий настоящему документу, находится за NAT, не проксирует свой обмен сообщениями MSRP через ретранслятор MSRP и получает предложение SDP от удалённого UA, следующего модели соединения из [RFC4975], то обход NAT может быть достигнут только в том случае, если UA MSRP поддерживает ICE [ICE-TCP] или если сеть поддерживает обход NAT для TCP с помощью пограничного контроллера сеансов (SBC).
6. Security Considerations
6. Вопросы безопасности
According to the connection model defined in [RFC4975], the MSRP UA that sends the SDP offer becomes the active party, and it is responsible for creating the MSRP transport connection towards the remote UA if a new connection is required.
Согласно модели соединения, определённой в [RFC4975], пользовательский агент MSRP, отправляющий предложение SDP, становится активной стороной и отвечает за создание транспортного соединения MSRP с удалённым UA, если требуется новое соединение.
When COMEDIA is used, either the sender or the receiver of the SDP offer can become the active party. [RFC4975] requires that the active party immediately issue an MSRP SEND request once the connection has been established. This allows the passive party to bind the inbound TCP connection to the message session identified by the session id part of its MSRP URI. The use of COMEDIA does not change this requirement, but the sender of the SDP offer is no longer assumed to always become the active party.
При использовании COMEDIA активной стороной может стать как отправитель, так и получатель предложения SDP. [RFC4975] требует, чтобы активная сторона немедленно выдала запрос MSRP SEND после установления соединения. Это позволяет пассивной стороне привязать входящее TCP-соединение к сеансу обмена сообщениями, идентифицированному частью session id его URI MSRP. Использование COMEDIA не меняет это требование, но отправитель предложения SDP больше не считается всегда становящимся активной стороной.
The active party also takes the role of the TLS client, if TLS is used to protect the MSRP messages. However, there are no procedures in [RFC4975] that would break in case the receiver of the SDP offer takes the role of the TLS client, and the level of security provided by TLS is not affected.
Активная сторона также принимает роль клиента TLS, если TLS используется для защиты сообщений MSRP. Однако в [RFC4975] нет процедур, которые нарушились бы в случае, если роль клиента TLS принимает получатель предложения SDP, а уровень безопасности, обеспечиваемый TLS, при этом не затрагивается.
