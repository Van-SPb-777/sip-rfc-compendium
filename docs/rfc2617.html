Abstract
Аннотация
"HTTP/1.0", includes the specification for a Basic Access Authentication scheme. This scheme is not considered to be a secure method of user authentication (unless used in conjunction with some external secure system such as SSL [5]), as the user name and password are passed over the network as cleartext.
«HTTP/1.0» включает спецификацию схемы базовой аутентификации доступа. Эта схема не считается безопасным методом аутентификации пользователя, поскольку пароль и имя пользователя передаются в открытом виде и могут быть перехвачены. Все браузеры и большинство серверов поддерживают эту схему.
This document also provides the specification for HTTP's authentication framework, the original Basic authentication scheme and a scheme based on cryptographic hashes, referred to as "Digest Access Authentication". It is therefore also intended to serve as a replacement for RFC 2069 [6]. Some optional elements specified by RFC 2069 have been removed from this specification due to problems found since its publication; other new elements have been added for compatibility, those new elements have been made optional, but are strongly recommended. Like Basic, Digest access authentication verifies that both parties to a communication know a shared secret (a password); unlike Basic, this verification can be done without sending the password in the clear, which is Basic's biggest weakness. As with most other authentication protocols, the greatest sources of risks are usually found not in the core protocol itself but in policies and procedures surrounding its use.
Настоящий документ также предоставляет спецификацию структуры аутентификации HTTP, исходной схемы базовой аутентификации и схемы, основанной на криптографических хешах, называемой «дайджест-аутентификацией доступа». Поэтому он также предназначен служить заменой RFC 2069 [6]. Некоторые необязательные элементы, указанные в RFC 2069, были удалены из настоящей спецификации из-за проблем, обнаруженных после её публикации; другие новые элементы были добавлены для совместимости, эти новые элементы сделаны необязательными, но настоятельно рекомендуются. Как и Basic, дайджест-аутентификация доступа проверяет, что обе стороны связи знают общий секрет (пароль); в отличие от Basic, эта проверка может быть выполнена без передачи пароля в открытом виде, что является самым большим слабым местом Basic. Как и в большинстве других протоколов аутентификации, наибольшие источники рисков обычно находятся не в самом основном протоколе, а в политиках и процедурах, окружающих его использование.

1. Аутентификация доступа
1.1. Reliance on the HTTP/1.1 Specification
1.1. Опора на спецификацию HTTP/1.1
This specification is a companion to the HTTP/1.1 specification [2]. It uses the augmented BNF section 2.1 of that document, and relies on both the non-terminals defined in that document and other aspects of the HTTP/1.1 specification.
Настоящая спецификация является дополнением к спецификации HTTP/1.1 [2]. Она использует раздел 2.1 расширенной BNF того документа и опирается как на нетерминалы, определённые в нём, так и на другие аспекты спецификации HTTP/1.1.
1.2. Access Authentication Framework
1.2. Рамки аутентификации доступа
HTTP provides a simple challenge-response authentication mechanism that MAY be used by a server to challenge a client request and by a client to provide authentication information. It uses an extensible, case-insensitive token to identify the authentication scheme, followed by a comma-separated list of attribute-value pairs which carry the parameters necessary for achieving authentication via that scheme.
HTTP предоставляет простой механизм аутентификации «запрос-ответ», который МОЖЕТ использоваться сервером для запроса аутентификации у клиента, а клиентом — для предоставления аутентификационной информации. Он использует расширяемую, нечувствительную к регистру лексему для идентификации схемы аутентификации, за которой следует список пар «атрибут-значение», несущих параметры, необходимые для аутентификации по этой схеме.
auth-scheme = token auth-param = token "=" ( token | quoted-string )
auth-scheme = token auth-param = token "=" ( token | quoted-string )
The 401 (Unauthorized) response message is used by an origin server to challenge the authorization of a user agent. This response MUST include a WWW-Authenticate header field containing at least one challenge applicable to the requested resource. The 407 (Proxy Authentication Required) response message is used by a proxy to challenge the authorization of a client and MUST include a Proxy- Authenticate header field containing at least one challenge applicable to the proxy for the requested resource.
Ответное сообщение 401 (Unauthorized) используется исходным сервером для запроса авторизации у пользовательского агента. Этот ответ ДОЛЖЕН включать поле заголовка WWW-Authenticate, содержащее по меньшей мере один запрос, применимый к запрошенному ресурсу. Ответное сообщение 407 (Proxy Authentication Required) используется прокси для запроса авторизации у клиента и ДОЛЖНО включать поле заголовка Proxy-Authenticate, содержащее по меньшей мере один запрос, применимый к прокси для запрошенного ресурса.
challenge = auth-scheme 1*SP 1#auth-param
challenge = auth-scheme 1*SP 1#auth-param
Note: User agents will need to take special care in parsing the WWW- Authenticate or Proxy-Authenticate header field value if it contains more than one challenge, or if more than one WWW-Authenticate header field is provided, since the contents of a challenge may itself contain a comma-separated list of authentication parameters.
Примечание. Пользовательским агентам потребуется проявлять особую осторожность при разборе значения поля заголовка WWW-Authenticate или Proxy-Authenticate, если оно содержит более одного запроса либо если предоставлено более одного поля заголовка WWW-Authenticate, поскольку содержимое запроса само может содержать список параметров аутентификации.
The authentication parameter realm is defined for all authentication schemes:
Параметр аутентификации realm определён для всех схем аутентификации:
realm = "realm" "=" realm-value realm-value = quoted-string
realm = "realm" "=" realm-value realm-value = quoted-string
The realm directive (case-insensitive) is required for all authentication schemes that issue a challenge. The realm value (case-sensitive), in combination with the canonical root URL (the absoluteURI for the server whose abs_path is empty; see section 5.1.2 of [2]) of the server being accessed, defines the protection space. These realms allow the protected resources on a server to be partitioned into a set of protection spaces, each with its own authentication scheme and/or authorization database. The realm value is a string, generally assigned by the origin server, which may have additional semantics specific to the authentication scheme. Note that there may be multiple challenges with the same auth-scheme but different realms.
Директива realm (нечувствительна к регистру) требуется для всех схем аутентификации, выдающих запрос. Значение realm (чувствительно к регистру) в сочетании с каноническим корневым URL (absoluteURI для сервера, чей abs_path пуст; см. раздел 5.1.2 [2]) сервера, к которому осуществляется доступ, определяет пространство защиты. Эти realm позволяют разделить защищённые ресурсы на сервере на набор пространств защиты, каждое со своей схемой аутентификации и/или базой данных авторизации. Значение realm — строка, обычно назначаемая исходным сервером, которая может иметь дополнительную семантику, специфичную для схемы аутентификации. Обратите внимание, что может быть несколько запросов с одной и той же схемой аутентификации, но разными realm.
A user agent that wishes to authenticate itself with an origin server--usually, but not necessarily, after receiving a 401 (Unauthorized)--MAY do so by including an Authorization header field with the request. A client that wishes to authenticate itself with a proxy--usually, but not necessarily, after receiving a 407 (Proxy Authentication Required)--MAY do so by including a Proxy- Authorization header field with the request. Both the Authorization field value and the Proxy-Authorization field value consist of credentials containing the authentication information of the client for the realm of the resource being requested. The user agent MUST choose to use one of the challenges with the strongest auth-scheme it understands and request credentials from the user based upon that challenge.
Пользовательский агент, желающий аутентифицироваться на исходном сервере — обычно, но не обязательно, после получения ответа 401 (Unauthorized), — МОЖЕТ сделать это, включив в запрос поле заголовка Authorization. Клиент, желающий аутентифицироваться на прокси — обычно, но не обязательно, после получения ответа 407 (Proxy Authentication Required), — МОЖЕТ сделать это, включив в запрос поле заголовка Proxy-Authorization. Как значение поля Authorization, так и значение поля Proxy-Authorization состоят из учётных данных, содержащих аутентификационную информацию клиента для realm запрашиваемого ресурса. Пользовательский агент ДОЛЖЕН выбрать для использования один из запросов с самой сильной схемой аутентификации, которую он понимает, и запросить у пользователя учётные данные на основе этого запроса.
credentials = auth-scheme #auth-param
credentials = auth-scheme #auth-param
Note that many browsers will only recognize Basic and will require that it be the first auth-scheme presented. Servers should only include Basic if it is minimally acceptable.
Обратите внимание, что многие браузеры распознают только Basic и требуют, чтобы она была первой представленной схемой аутентификации. Серверы должны включать Basic только в том случае, если она минимально приемлема.
The protection space determines the domain over which credentials can be automatically applied. If a prior request has been authorized, the same credentials MAY be reused for all other requests within that protection space for a period of time determined by the authentication scheme, parameters, and/or user preference. Unless otherwise defined by the authentication scheme, a single protection space cannot extend outside the scope of its server.
Пространство защиты определяет область, в пределах которой учётные данные могут применяться автоматически. Если предыдущий запрос был авторизован, те же учётные данные МОГУТ повторно использоваться для всех остальных запросов в пределах этого пространства защиты в течение периода, определяемого схемой аутентификации, параметрами и мнением пользователя (которое может определять период, в течение которого учётные данные сохраняются).
If the origin server does not wish to accept the credentials sent with a request, it SHOULD return a 401 (Unauthorized) response. The response MUST include a WWW-Authenticate header field containing at least one (possibly new) challenge applicable to the requested resource. If a proxy does not accept the credentials sent with a request, it SHOULD return a 407 (Proxy Authentication Required). The response MUST include a Proxy-Authenticate header field containing a (possibly new) challenge applicable to the proxy for the requested resource.
Если исходный сервер не желает принимать учётные данные, отправленные с запросом, ему СЛЕДУЕТ вернуть ответ 401 (Unauthorized). Ответ ДОЛЖЕН включать поле заголовка WWW-Authenticate, содержащее по меньшей мере один (возможно, новый) запрос, применимый к запрошенному ресурсу. Если прокси не принимает учётные данные, он ДОЛЖЕН вернуть ответ 407 (Proxy Authentication Required), содержащий поле заголовка Proxy-Authenticate, которое содержит по меньшей мере один (возможно, новый) запрос, применимый к прокси для запрошенного ресурса.
The HTTP protocol does not restrict applications to this simple challenge-response mechanism for access authentication. Additional mechanisms MAY be used, such as encryption at the transport level or via message encapsulation, and with additional header fields specifying authentication information. However, these additional mechanisms are not defined by this specification.
Протокол HTTP не ограничивает приложения этим простым механизмом аутентификации «запрос-ответ» для аутентификации доступа. МОГУТ использоваться дополнительные механизмы, такие как шифрование на транспортном уровне или посредством инкапсуляции сообщений, а также дополнительные поля заголовка, задающие аутентификационную информацию.
Proxies MUST be completely transparent regarding user agent authentication by origin servers. That is, they must forward the WWW-Authenticate and Authorization headers untouched, and follow the rules found in section 14.8 of [2]. Both the Proxy-Authenticate and the Proxy-Authorization header fields are hop-by-hop headers (see section 13.5.1 of [2]).
Прокси ДОЛЖНЫ быть полностью прозрачны в отношении аутентификации пользовательских агентов исходными серверами. То есть они должны пересылать заголовки WWW-Authenticate и Authorization без изменений и соблюдать правила раздела 14.8 [2]. Как поле заголовка Proxy-Authenticate, Proxy-Authorization являются заголовками «хоп за хопом» (см. раздел 13.5.1 [2]).
2. Basic Authentication Scheme
2. Схема базовой аутентификации
The "basic" authentication scheme is based on the model that the client must authenticate itself with a user-ID and a password for each realm. The realm value should be considered an opaque string which can only be compared for equality with other realms on that server. The server will service the request only if it can validate the user-ID and password for the protection space of the Request-URI. There are no optional authentication parameters.
Схема аутентификации «basic» основана на модели, в которой клиент должен аутентифицироваться с помощью идентификатора пользователя и пароля для каждого realm. Значение realm следует рассматривать как непрозрачную строку, которую можно сравнивать только на равенство с другими realm на этом сервере. Сервер будет обслуживать запрос, только если он может проверить представленный идентификатор пользователя и связанный с ним пароль.
For Basic, the framework above is utilized as follows:
Для Basic описанные выше рамки используются следующим образом:
challenge = "Basic" realm credentials = "Basic" basic-credentials
challenge = "Basic" realm credentials = "Basic" basic-credentials
Upon receipt of an unauthorized request for a URI within the protection space, the origin server MAY respond with a challenge like the following:
При получении неавторизованного запроса для URI в пределах пространства защиты исходный сервер МОЖЕТ ответить запросом следующего вида:
WWW-Authenticate: Basic realm="WallyWorld"
WWW-Authenticate: Basic realm="WallyWorld"
where "WallyWorld" is the string assigned by the server to identify the protection space of the Request-URI. A proxy may respond with the same challenge using the Proxy-Authenticate header field.
где «WallyWorld» — строка, назначенная сервером для идентификации пространства защиты Request-URI. Прокси может ответить тем же запросом, используя поле заголовка Proxy-Authenticate.
To receive authorization, the client sends the userid and password, separated by a single colon (":") character, within a base64 [7] encoded string in the credentials.
Чтобы получить авторизацию, клиент отправляет идентификатор пользователя и пароль, разделённые одним символом двоеточия («:»), в виде строки, закодированной в base64 [7], в учётных данных.
basic-credentials = base64-user-pass base64-user-pass = <base64 [4] encoding of user-pass, except not limited to 76 char/line> user-pass = userid ":" password userid = *<TEXT excluding ":"> password = *TEXT
basic-credentials = base64-user-pass base64-user-pass = <base64 [4] encoding of user-pass, except not limited to 76 char/line> user-pass = userid ":" password userid = *<TEXT excluding ":"> password = *TEXT
Userids might be case sensitive.
Идентификаторы пользователей могут быть чувствительны к регистру.
If the user agent wishes to send the userid "Aladdin" and password "open sesame", it would use the following header field:
Если пользовательский агент желает отправить идентификатор пользователя «Aladdin» и пароль «open sesame», он использовал бы следующее поле заголовка:
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
A client SHOULD assume that all paths at or deeper than the depth of the last symbolic element in the path field of the Request-URI also are within the protection space specified by the Basic realm value of the current challenge. A client MAY preemptively send the corresponding Authorization header with requests for resources in that space without receipt of another challenge from the server. Similarly, when a client sends a request to a proxy, it may reuse a userid and password in the Proxy-Authorization header field without receiving another challenge from the proxy server. See section 4 for security considerations associated with Basic authentication.
Клиенту СЛЕДУЕТ предполагать, что все пути на уровне или глубже глубины последнего символического элемента в поле пути Request-URI также находятся в пределах пространства защиты, заданного значением realm Basic текущего запроса. Клиент МОЖЕТ упреждающе отправлять соответствующее поле заголовка Authorization с запросами ресурсов в этом пространстве без получения другого запроса от сервера. Аналогично, когда клиент отправляет запрос прокси, он может повторно использовать идентификатор пользователя и пароль в поле заголовка Proxy-Authorization без получения другого запроса от прокси-сервера. О вопросах безопасности, связанных с базовой аутентификацией, см. раздел 4.
3. Digest Access Authentication Scheme
3. Схема дайджест-аутентификации доступа
3.1. Introduction
3.1. Введение
3.1.1. Purpose
3.1.1. Назначение
The protocol referred to as "HTTP/1.0" includes the specification for a Basic Access Authentication scheme[1]. That scheme is not considered to be a secure method of user authentication, as the user name and password are passed over the network in an unencrypted form. This section provides the specification for a scheme that does not send the password in cleartext, referred to as "Digest Access Authentication".
Протокол, именуемый «HTTP/1.0», включает спецификацию схемы базовой аутентификации доступа [1]. Эта схема не считается безопасным методом аутентификации пользователя, поскольку имя пользователя и пароль передаются по сети в незашифрованном виде. В этом разделе приводится спецификация механизма аутентификации доступа, позволяющего избежать наиболее серьёзных недостатков базовой аутентификации.
The Digest Access Authentication scheme is not intended to be a complete answer to the need for security in the World Wide Web. This scheme provides no encryption of message content. The intent is simply to create an access authentication method that avoids the most serious flaws of Basic authentication.
Схема дайджест-аутентификации доступа не предназначена быть полным ответом на потребность в безопасности во Всемирной паутине. Эта схема не обеспечивает шифрования содержимого сообщений. Намерение состоит просто в создании метода аутентификации доступа, который позволяет избежать наиболее серьёзных изъянов базовой аутентификации.
3.1.2. Overall Operation
3.1.2. Общий принцип работы
Like Basic Access Authentication, the Digest scheme is based on a simple challenge-response paradigm. The Digest scheme challenges using a nonce value. A valid response contains a checksum (by default, the MD5 checksum) of the username, the password, the given nonce value, the HTTP method, and the requested URI. In this way, the password is never sent in the clear. Just as with the Basic scheme, the username and password must be prearranged in some fashion not addressed by this document.
Подобно базовой аутентификации доступа, схема Digest основана на простой парадигме «запрос-ответ». Схема Digest выдаёт запрос с использованием значения nonce. Допустимый ответ содержит контрольную сумму (по умолчанию контрольную сумму MD5) имени пользователя, пароля, заданного значения nonce, метода HTTP и запрошенного URI. Таким образом, пароль никогда не передаётся в открытом виде. Как и в случае схемы Basic, имя пользователя и пароль должны быть предварительно согласованы способом, не рассматриваемым настоящим документом.
3.1.3. Representation of digest values
3.1.3. Представление дайджест-значений
An optional header allows the server to specify the algorithm used to create the checksum or digest. By default the MD5 algorithm is used and that is the only algorithm described in this document.
Необязательный заголовок позволяет серверу указать алгоритм, используемый для создания контрольной суммы или дайджеста. По умолчанию используется алгоритм MD5, и это единственный алгоритм, описанный в настоящем документе.
For the purposes of this document, an MD5 digest of 128 bits is represented as 32 ASCII printable characters. The bits in the 128 bit digest are converted from most significant to least significant bit, four bits at a time to their ASCII presentation as follows. Each four bits is represented by its familiar hexadecimal notation from the characters 0123456789abcdef. That is, binary 0000 gets represented by the character '0', 0001, by '1', and so on up to the representation of 1111 as 'f'.
Для целей настоящего документа 128-битный дайджест MD5 представляется как 32 печатаемых символа ASCII. Биты в 128-битном дайджесте преобразуются от старшего к младшему биту по четыре бита за раз в их представление ASCII следующим образом. Каждые четыре бита представляются их шестнадцатеричным эквивалентом: значения от 0 до 9 представляются цифрами «0»–«9», а значения от 10 до 15 — буквами «a»–«f».
3.1.4. Limitations
3.1.4. Ограничения
The Digest authentication scheme described in this document suffers from many known limitations. It is intended as a replacement for Basic authentication and nothing more. It is a password-based system and (on the server side) suffers from all the same problems of any password system. In particular, no provision is made in this protocol for the initial secure arrangement between user and server to establish the user's password.
Описанная в настоящем документе схема дайджест-аутентификации страдает от множества известных ограничений. Она задумана как замена базовой аутентификации и не более того. Это система на основе паролей, и (на стороне сервера) она страдает от всех тех же проблем, что и любая парольная система. В частности, она не защищает от атак по словарю, не обеспечивает конфиденциальности содержимого и требует хранения сервером данных, производных от пароля.
Users and implementors should be aware that this protocol is not as secure as Kerberos, and not as secure as any client-side private-key scheme. Nevertheless it is better than nothing, better than what is commonly used with telnet and ftp, and better than Basic authentication.
Пользователям и разработчикам следует знать, что этот протокол не столь безопасен, как Kerberos, и не столь безопасен, как любая схема с закрытым ключом на стороне клиента. Тем не менее он лучше, чем ничего, лучше того, что обычно используется с telnet и ftp, и лучше базовой аутентификации.

Implementers should be aware of how authenticated transactions interact with shared caches. The HTTP/1.1 protocol specifies that when a shared cache (see section 13.7 of [2]) has received a request containing an Authorization header and a response from relaying that request, it MUST NOT return that response as a reply to any other request, unless one of two Cache-Control (see section 14.9 of [2]) directives was present in the response. В качестве альтернативы, если исходный ответ включал директиву Cache-Control «public», объект ответа МОЖЕТ возвращаться в ответ на любой последующий запрос.

3.3. Digest Operation
3.3. Работа Digest
Upon receiving the Authorization header, the server may check its validity by looking up the password that corresponds to the submitted username. Then, the server must perform the same digest operation (e.g., MD5) performed by the client, and compare the result to the given request-digest value.
По получении заголовка Authorization сервер может проверить его действительность, найдя пароль, соответствующий представленному имени пользователя. Затем сервер должен выполнить ту же операцию дайджеста (например, MD5), что и клиент, и сравнить результат с заданным значением request-digest.
Note that the HTTP server does not actually need to know the user's cleartext password. As long as H(A1) is available to the server, the validity of an Authorization header may be verified.
Обратите внимание, что HTTP-серверу фактически не нужно знать пароль пользователя в открытом виде. Пока H(A1) доступен серверу, действительность заголовка Authorization может быть проверена.
The client response to a WWW-Authenticate challenge for a protection space starts an authentication session with that protection space. The authentication session lasts until the client receives another WWW-Authenticate challenge from any server in the protection space. A client should remember the username, password, nonce, nonce count and opaque values associated with an authentication session to use to construct the Authorization header in future requests within that protection space. The Authorization header may be included preemptively; doing so improves server efficiency and avoids extra round trips for authentication challenges. The server may choose to accept the old Authorization header information, even though the nonce value included might not be fresh. Alternatively, the server may return a 401 response with a new nonce value, causing the client to retry the request; by specifying stale=TRUE with this response, the server tells the client to retry with the new nonce, but without prompting for a new username and password.
Ответ клиента на запрос WWW-Authenticate для пространства защиты начинает сессию аутентификации с этим пространством защиты. Сессия аутентификации длится до тех пор, пока клиент не получит другой запрос WWW-Authenticate от любого сервера в пространстве защиты. Клиент должен запоминать значения имени пользователя, пароля, nonce, счётчика nonce и opaque, связанные с сессией аутентификации, чтобы использовать их для построения заголовка Authorization в последующих запросах в пределах этого пространства защиты. Заголовок Authorization может включаться упреждающе; это повышает эффективность сервера и позволяет избежать дополнительных круговых обменов для запросов аутентификации. Сервер может по своему выбору принимать информацию старого заголовка Authorization, даже если включённое значение nonce может быть не свежим. Либо сервер может вернуть ответ 401 с новым значением nonce, заставляя клиента повторить запрос; указывая stale=TRUE в этом ответе, сервер сообщает клиенту о необходимости повтора с новым nonce, но без запроса новых имени пользователя и пароля.
Because the client is required to return the value of the opaque directive given to it by the server for the duration of a session, the opaque data may be used to transport authentication session state information. (Note that any such use can also be accomplished more easily and safely by including the state in the nonce.) For example, a server could be responsible for authenticating content that actually sits on another server. It would achieve this by having the first 401 response include a domain directive whose value includes a URI on the second server, and an opaque directive whose value contains the state information. The client will retry the request, at which time the server might respond with a 301/302 redirection, pointing to the URI on the second server. The client will follow the redirection, and pass an Authorization header , including the <opaque> data.
Поскольку клиент обязан возвращать значение директивы opaque, данное ему сервером, в течение всей сессии, данные opaque могут использоваться для передачи информации о состоянии сессии аутентификации. (Обратите внимание, что любое такое использование может быть выполнено также проще и безопаснее путём включения информации о состоянии в сам запрос, например в виде cookie или параметра URL, однако данные opaque позволяют транспортировать состояние без изменения формата запроса.) содержит информацию о состоянии. Клиент повторит запрос, и в этот момент сервер может ответить перенаправлением 301/302, указывающим на URI на втором сервере. Клиент проследует перенаправлению и передаст заголовок Authorization, включая данные <opaque>.
As with the basic scheme, proxies must be completely transparent in the Digest access authentication scheme. That is, they must forward the WWW-Authenticate, Authentication-Info and Authorization headers untouched. If a proxy wants to authenticate a client before a request is forwarded to the server, it can be done using the Proxy- Authenticate and Proxy-Authorization headers described in section 3.6 below.
Как и в случае схемы basic, прокси должны быть полностью прозрачны в схеме дайджест-аутентификации доступа. То есть они должны пересылать заголовки WWW-Authenticate, Authentication-Info и Authorization без изменений. Если прокси желает аутентифицировать клиента до того, как запрос будет передан серверу, он должен использовать заголовки Proxy-Authenticate и Proxy-Authorization, как описано в разделе 3.6.
3.4. Security Protocol Negotiation
3.4. Согласование протокола безопасности
It is useful for a server to be able to know which security schemes a client is capable of handling.
Для сервера полезно знать, какие схемы безопасности клиент способен обрабатывать.
It is possible that a server may want to require Digest as its authentication method, even if the server does not know that the client supports it. A client is encouraged to fail gracefully if the server specifies only authentication schemes it cannot handle.
Возможно, что сервер пожелает требовать Digest в качестве своего метода аутентификации, даже если серверу неизвестно, что клиент его поддерживает. Клиенту рекомендуется завершаться корректно, если сервер указывает только те схемы аутентификации, которые он не может обработать.

Both client and server know that the username for this document is "Mufasa", and the password is "Circle Of Life" (with one space between each of the three words).
Следующий пример предполагает, что защищённый от доступа документ запрашивается у сервера посредством запроса GET. URI документа — «http://www.nowhere.org/dir/index.html». И клиент, и сервер знают, что имя пользователя для этого документа — «Mufasa», а пароль — «Circle Of Life»
The first time the client requests the document, no Authorization header is sent, so the server responds with:
При первом запросе документа клиент не отправляет заголовок Authorization, поэтому сервер отвечает:
HTTP/1.1 401 Unauthorized WWW-Authenticate: Digest realm="testrealm@host.com", qop="auth,auth-int", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093", opaque="5ccc069c403ebaf9f0171e9517f40e41"
HTTP/1.1 401 Unauthorized WWW-Authenticate: Digest realm="testrealm@host.com", qop="auth,auth-int", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093", opaque="5ccc069c403ebaf9f0171e9517f40e41"
The client may prompt the user for the username and password, after which it will respond with a new request, including the following Authorization header:
Клиент может запросить у пользователя имя пользователя и пароль, после чего ответит новым запросом, включающим следующий заголовок Authorization:
Authorization: Digest username="Mufasa", realm="testrealm@host.com", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093", uri="/dir/index.html", qop=auth, nc=00000001, cnonce="0a4f113b", response="6629fae49393a05397450978507c4ef1", opaque="5ccc069c403ebaf9f0171e9517f40e41"
Authorization: Digest username="Mufasa", realm="testrealm@host.com", nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093", uri="/dir/index.html", qop=auth, nc=00000001, cnonce="0a4f113b", response="6629fae49393a05397450978507c4ef1", opaque="5ccc069c403ebaf9f0171e9517f40e41"
3.6. Proxy-Authentication and Proxy-Authorization
3.6. Прокси-аутентификация и прокси-авторизация
The digest authentication scheme may also be used for authenticating users to proxies, proxies to proxies, or proxies to origin servers by use of the Proxy-Authenticate and Proxy-Authorization headers. These headers are instances of the Proxy-Authenticate and Proxy- Authorization headers specified in sections 10.33 and 10.34 of the HTTP/1.1 specification [2] and their behavior is subject to restrictions described there. The transactions for proxy authentication are very similar to those already described. Upon receiving a request which requires authentication, the proxy/server must issue the "407 Proxy Authentication Required" response with a "Proxy-Authenticate" header. The digest-challenge used in the Proxy-Authenticate header is the same as that for the WWW- Authenticate header as defined above in section 3.2.1.
Схема дайджест-аутентификации может также использоваться для аутентификации пользователей на прокси, прокси на прокси или прокси на исходных серверах с помощью заголовков Proxy-Authenticate и Proxy-Authorization. Эти заголовки являются экземплярами заголовков Proxy-Authenticate и Proxy-Authorization, указанных в разделах 10.33 и 10.34 спецификации HTTP/1.1 [2], и их поведение подчинено ограничениям, описанным там. Транзакции для прокси-аутентификации очень похожи на уже описанные. По получении запроса, требующего аутентификации, прокси или сервер должен выдать ответ «407 Proxy Authentication Required» с заголовком «Proxy-Authenticate». Дайджест-запрос, используемый в заголовке Proxy-Authenticate, тот же, что и для заголовка WWW-Authenticate, как определено выше в разделе 3.2.1.
The client/proxy must then re-issue the request with a Proxy- Authorization header, with directives as specified for the Authorization header in section 3.2.2 above.
Затем клиент или прокси должен повторно выдать запрос с заголовком Proxy-Authorization и директивами, указанными для заголовка Authorization в разделе 3.2.2 выше.
On subsequent responses, the server sends Proxy-Authentication-Info with directives the same as those for the Authentication-Info header field.
В последующих ответах сервер отправляет Proxy-Authentication-Info с директивами такими же, как для поля заголовка Authentication-Info.
Note that in principle a client could be asked to authenticate itself to both a proxy and an end-server, but never in the same response.
Обратите внимание, что в принципе клиента могут попросить аутентифицироваться как на прокси, так и на конечном сервере, но никогда в одном и том же ответе.
4. Security Considerations
4. Вопросы безопасности
4.1. Authentication of Clients using Basic Authentication
4.1. Аутентификация клиентов с использованием Basic
The Basic authentication scheme is not a secure method of user authentication, nor does it in any way protect the entity, which is transmitted in cleartext across the physical network used as the carrier. HTTP does not prevent additional authentication schemes and encryption mechanisms from being employed to increase security or the addition of enhancements (such as schemes to use one-time passwords) to Basic authentication. The most serious flaw in Basic authentication is that it results in the essentially cleartext transmission of the user's password over the physical network. It is this problem which Digest Authentication attempts to address.
Схема базовой аутентификации не является безопасным методом аутентификации пользователя и никоим образом не защищает объект, который передаётся открытым текстом по физической сети, используемой в качестве носителя. HTTP не препятствует применению дополнительных схем аутентификации и механизмов шифрования для повышения безопасности, но для этого требуются дополнительные соглашения между клиентом и сервером. Наиболее серьёзный изъян базовой аутентификации состоит в том, что она приводит к передаче пароля пользователя по существу в открытом виде по физической сети. Именно эту проблему пытается решить дайджест-аутентификация.
Because Basic authentication involves the cleartext transmission of passwords it SHOULD NOT be used (without enhancements) to protect sensitive or valuable information.
Поскольку базовая аутентификация предполагает передачу паролей открытым текстом, её НЕ СЛЕДУЕТ использовать (без усовершенствований) для защиты конфиденциальной или ценной информации.
A common use of Basic authentication is for identification purposes -- requiring the user to provide a user name and password as a means of identification, for example, for purposes of gathering accurate usage statistics on a server. When used in this way it is tempting to think that there is no danger in its use if illicit access to the protected documents is not a major concern. This is only correct if the server issues both user name and password to the users and in particular does not allow the user to choose his or her own password. The danger arises because naive users frequently reuse a single password to avoid the task of maintaining multiple passwords.
Обычное использование базовой аутентификации — для целей идентификации, то есть требование от пользователя предоставить имя пользователя и пароль как средство идентификации, например для сбора точной статистики использования на сервере. При таком использовании возникает соблазн думать, что опасности нет, поскольку пользователь всего лишь идентифицирует себя. Однако это опасное заблуждение: перехваченный пароль даёт злоумышленнику доступ к большему, чем предполагалось, поскольку пользователи склонны использовать один и тот же пароль в разных местах.
If a server permits users to select their own passwords, then the threat is not only unauthorized access to documents on the server but also unauthorized access to any other resources on other systems that the user protects with the same password. Furthermore, in the server's password database, many of the passwords may also be users' passwords for other sites. The owner or administrator of such a system could therefore expose all users of the system to the risk of unauthorized access to all those sites if this information is not maintained in a secure fashion.
Если сервер позволяет пользователям выбирать собственные пароли, то угроза состоит не только в несанкционированном доступе к документам на сервере, но и в несанкционированном доступе к любым другим ресурсам на других системах, которые пользователь защищает тем же паролем. Кроме того, в базе паролей сервера многие пользователи могут использовать один и тот же пароль, и компрометация одного пароля компрометирует множество учётных записей.
Basic Authentication is also vulnerable to spoofing by counterfeit servers. If a user can be led to believe that he is connecting to a host containing information protected by Basic authentication when, in fact, he is connecting to a hostile server or gateway, then the attacker can request a password, store it for later use, and feign an error. This type of attack is not possible with Digest Authentication. Server implementers SHOULD guard against the possibility of this sort of counterfeiting by gateways or CGI scripts. In particular it is very dangerous for a server to simply turn over a connection to a gateway. That gateway can then use the persistent connection mechanism to engage in multiple transactions with the client while impersonating the original server in a way that is not detectable by the client.
Базовая аутентификация также уязвима к подмене поддельными серверами. Если пользователя можно убедить, что он подключается к хосту, содержащему информацию, защищённую базовой аутентификацией, тогда как на самом деле он подключается к враждебному серверу или шлюзу, то злоумышленник может запросить пароль, сохранить его для последующего использования и изобразить ошибку. Этот тип атаки невозможен при дайджест-аутентификации. Разработчикам серверов СЛЕДУЕТ защищаться от возможности такой подделки шлюзами или CGI-скриптами. В частности, для сервера очень опасно просто передать соединение шлюзу. Этот шлюз затем может использовать механизм постоянного соединения для проведения множества транзакций с клиентом, выдавая себя за исходный сервер способом, не обнаружимым клиентом.
4.2. Authentication of Clients using Digest Authentication
4.2. Аутентификация клиентов с помощью дайджест-аутентификации
Digest Authentication does not provide a strong authentication mechanism, when compared to public key based mechanisms, for example. However, it is significantly stronger than (e.g.) CRAM-MD5, which has been proposed for use with LDAP [10], POP and IMAP (see RFC 2195 [9]). It is intended to replace the much weaker and even more dangerous Basic mechanism.
Дайджест-аутентификация не обеспечивает сильного механизма аутентификации, например, по сравнению с механизмами на основе открытых ключей. Однако она значительно сильнее, чем (например) CRAM-MD5, который был предложен для использования с LDAP [10], POP и IMAP (см. RFC 2195 [9]). Она предназначена для замены гораздо более слабого и даже более опасного механизма Basic.
Digest Authentication offers no confidentiality protection beyond protecting the actual password. All of the rest of the request and response are available to an eavesdropper.
Дайджест-аутентификация не обеспечивает защиты конфиденциальности сверх защиты самого пароля. Весь остальной запрос и ответ доступны подслушивающему.
Digest Authentication offers only limited integrity protection for the messages in either direction. If qop=auth-int mechanism is used, those parts of the message used in the calculation of the WWW- Authenticate and Authorization header field response directive values (see section 3.2 above) are protected. Most header fields and their values could be modified as a part of a man-in-the-middle attack.
Дайджест-аутентификация обеспечивает лишь ограниченную защиту целостности сообщений в обоих направлениях. Если используется механизм qop=auth-int, те части сообщения, которые участвуют в вычислении значений директивы response полей заголовков WWW-Authenticate и Authorization (см. раздел 3.2 выше), защищены. Большинство полей заголовков и их значений могут быть изменены в ходе атаки «человек посередине».
Many needs for secure HTTP transactions cannot be met by Digest Authentication. For those needs TLS or SHTTP are more appropriate protocols. In particular Digest authentication cannot be used for any transaction requiring confidentiality protection. Nevertheless many functions remain for which Digest authentication is both useful and appropriate. Any service in present use that uses Basic should be switched to Digest as soon as practical.
Многие потребности в защищённых HTTP-транзакциях не могут быть удовлетворены дайджест-аутентификацией. Для этих потребностей более подходящими протоколами являются TLS или SHTTP. В частности, дайджест-аутентификация не может использоваться для любой транзакции, требующей защиты конфиденциальности. Тем не менее остаётся множество функций, для которых дайджест-аутентификация полезна и уместна. Любую используемую в настоящее время службу, которая применяет Basic, следует перевести на Digest при первой возможности.
4.3. Limited Use Nonce Values
4.3. Nonce с ограниченным использованием
The Digest scheme uses a server-specified nonce to seed the generation of the request-digest value (as specified in section 3.2.2.1 above). As shown in the example nonce in section 3.2.1, the server is free to construct the nonce such that it may only be used from a particular client, for a particular resource, for a limited period of time or number of uses, or any other restrictions. Doing so strengthens the protection provided against, for example, replay attacks (see 4.5). However, it should be noted that the method chosen for generating and checking the nonce also has performance and resource implications. For example, a server may choose to allow each nonce value to be used only once by maintaining a record of whether or not each recently issued nonce has been returned and sending a next-nonce directive in the Authentication-Info header field of every response. This protects against even an immediate replay attack, but has a high cost checking nonce values, and perhaps more important will cause authentication failures for any pipelined requests (presumably returning a stale nonce indication). Similarly, incorporating a request-specific element such as the Etag value for a resource limits the use of the nonce to that version of the resource and also defeats pipelining.
Схема Digest использует заданный сервером nonce для инициализации генерации значения request-digest (как указано в разделе 3.2.2.1 выше). Как показано в примере nonce в разделе 3.2.1, сервер может свободно строить nonce так, чтобы он мог использоваться только от конкретного клиента, для конкретного ресурса, в течение ограниченного периода времени или числа использований, либо с любыми иными ограничениями. Это усиливает защиту от, например, атак повторного воспроизведения (см. раздел 4.5). Однако следует отметить, что выбранный метод генерации и проверки nonce также имеет последствия для производительности и ресурсов. Например, сервер может пожелать разрешить использование каждого значения nonce только один раз, поддерживая запись о том, был ли возвращён каждый недавно выданный nonce, и отправляя директиву next-nonce в поле заголовка Authentication-Info каждого ответа. Это защищает даже от немедленной атаки повторного воспроизведения, но имеет высокую стоимость проверки значений nonce и, что возможно более важно, вызовет сбои аутентификации для любых конвейерных запросов (предположительно возвращая указание stale nonce). Аналогично включение элемента, специфичного для запроса, такого как значение Etag для ресурса, ограничивает использование nonce этого версией ресурса и также препятствует конвейеризации.
Thus it may be useful to do so for methods with side effects but have unacceptable performance for those that do not.
Поэтому это может быть полезно для методов с побочными эффектами, но даёт неприемлемую производительность для тех, у которых их нет.
4.4. Comparison of Digest with Basic Authentication
4.4. Сравнение Digest с базовой аутентификацией
Both Digest and Basic Authentication are very much on the weak end of the security strength spectrum. But a comparison between the two points out the utility, even necessity, of replacing Basic by Digest.
И Digest, и базовая аутентификация находятся в значительной степени на слабом конце спектра стойкости безопасности. Но сравнение между ними указывает на полезность, даже необходимость замены Basic на Digest.
The greatest threat to the type of transactions for which these protocols are used is network snooping. This kind of transaction might involve, for example, online access to a database whose use is restricted to paying subscribers. With Basic authentication an eavesdropper can obtain the password of the user. This not only permits him to access anything in the database, but, often worse, will permit access to anything else the user protects with the same password.
Наибольшая угроза для того типа транзакций, для которых используются эти протоколы, — это сетевой шпионаж. Такой тип транзакции может включать, например, онлайн-доступ к базе данных, использование которой ограничено платными подписчиками. При базовой аутентификации подслушивающий может получить пароль пользователя. Это позволяет ему не только получить доступ к чему угодно в базе данных, но, что часто хуже, позволит получить доступ ко всему остальному, что пользователь защищает тем же паролем.
By contrast, with Digest Authentication the eavesdropper only gets access to the transaction in question and not to the user's password. The information gained by the eavesdropper would permit a replay attack, but only with a request for the same document, and even that may be limited by the server's choice of nonce.
Напротив, при дайджест-аутентификации подслушивающий получает доступ только к рассматриваемой транзакции, но не к паролю пользователя. Информация, полученная подслушивающим, позволила бы атаку повторного воспроизведения, но только с запросом того же документа, и даже это может быть ограничено сервером.
4.5. Replay Attacks
4.5. Атаки повторного воспроизведения
A replay attack against Digest authentication would usually be pointless for a simple GET request since an eavesdropper would already have seen the only document he could obtain with a replay. This is because the URI of the requested document is digested in the client request and the server will only deliver that document. By contrast under Basic Authentication once the eavesdropper has the user's password, any document protected by that password is open to him.
Атака повторного воспроизведения против дайджест-аутентификации обычно была бы бессмысленной для простого запроса GET, поскольку подслушивающий уже увидел бы единственный документ, который он мог бы получить при воспроизведении. Это потому, что URI запрашиваемого документа хешируется в клиентском запросе, и сервер выдаст только этот документ. Напротив, при базовой аутентификации, как только подслушивающий получил пароль пользователя, любой документ, защищённый этим паролем, открыт для него.
Thus, for some purposes, it is necessary to protect against replay attacks. A good Digest implementation can do this in various ways. The server created "nonce" value is implementation dependent, but if it contains a digest of the client IP, a time-stamp, the resource ETag, and a private server key (as recommended above) then a replay attack is not simple. An attacker must convince the server that the request is coming from a false IP address and must cause the server to deliver the document to an IP address different from the address to which it believes it is sending the document. An attack can only succeed in the period before the time-stamp expires. Digesting the client IP and time-stamp in the nonce permits an implementation which does not maintain state between transactions.
Таким образом, для некоторых целей необходимо защищаться от атак повторного воспроизведения. Хорошая реализация Digest может делать это различными способами. Созданное сервером значение «nonce» зависит от реализации, но если оно содержит дайджест IP клиента, отметку времени, ETag ресурса и закрытый ключ сервера (как рекомендовано выше), то атака повторного воспроизведения не является простой. Злоумышленник должен убедить сервер, что запрос приходит с ложного IP-адреса, и должен заставить сервер выдать документ на IP-адрес, отличный от того, на который, как он считает, он отправляет документ. Атака может увенчаться успехом только в период до истечения срока отметки времени. Хеширование IP клиента и отметки времени в nonce допускает реализацию, не поддерживающую состояние между транзакциями.
For applications where no possibility of replay attack can be tolerated the server can use one-time nonce values which will not be honored for a second use. This requires the overhead of the server remembering which nonce values have been used until the nonce time- stamp (and hence the digest built with it) has expired, but it effectively protects against replay attacks.
Для приложений, где возможность атаки повторного воспроизведения недопустима, сервер может использовать одноразовые значения nonce, которые не будут приняты при повторном использовании. Это требует накладных расходов на то, чтобы сервер запоминал, какие значения nonce были использованы, пока не истечёт отметка времени nonce (и, следовательно, построенный на её основе дайджест), но это эффективно защищает от атак повторного воспроизведения.
An implementation must give special attention to the possibility of replay attacks with POST and PUT requests. Unless the server employs one-time or otherwise limited-use nonces and/or insists on the use of the integrity protection of qop=auth-int, an attacker could replay valid credentials from a successful request with counterfeit form data or other message body. Even with the use of integrity protection most metadata in header fields is not protected. Proper nonce generation and checking provides some protection against replay of previously used valid credentials, but see 4.8.
Реализация должна уделять особое внимание возможности атак повторного воспроизведения с запросами POST и PUT. Если сервер не применяет одноразовые или иным образом ограниченно используемые nonce и/или не настаивает на использовании защиты целостности qop=auth-int, злоумышленник мог бы воспроизвести действительные учётные данные из успешного запроса с поддельными данными формы или иным телом сообщения. Даже при использовании защиты целостности большая часть метаданных в полях заголовка не защищена. Правильная генерация и проверка nonce обеспечивает некоторую защиту от воспроизведения ранее использованных действительных учётных данных, но см. раздел 4.8.
4.6. Weakness Created by Multiple Authentication Schemes
4.6. Слабость, порождаемая множественными схемами аутентификации
An HTTP/1.1 server may return multiple challenges with a 401 (Authenticate) response, and each challenge may use a different auth-scheme. A user agent MUST choose to use the strongest auth- scheme it understands and request credentials from the user based upon that challenge.
Сервер HTTP/1.1 может вернуть несколько запросов с ответом 401 (Authenticate), и каждый запрос может использовать иную схему аутентификации. Пользовательский агент ДОЛЖЕН выбрать использование самой сильной схемы аутентификации, которую он понимает, и запросить у пользователя учётные данные на основе этого запроса.
Note that many browsers will only recognize Basic and will require that it be the first auth-scheme presented. Servers should only include Basic if it is minimally acceptable.
Обратите внимание, что многие браузеры распознают только Basic и требуют, чтобы она была первой представленной схемой аутентификации. Серверы должны включать Basic только в том случае, если она минимально приемлема.
When the server offers choices of authentication schemes using the WWW-Authenticate header, the strength of the resulting authentication is only as good as that of the of the weakest of the authentication schemes. See section 4.8 below for discussion of particular attack scenarios that exploit multiple authentication schemes.
Когда сервер предлагает выбор схем аутентификации с помощью заголовка WWW-Authenticate, стойкость результирующей аутентификации не выше, чем у самой слабой из схем аутентификации. О конкретных сценариях атак, использующих множественные схемы аутентификации, см. раздел 4.8 ниже.
4.7. Online dictionary attacks
4.7. Онлайн-атаки по словарю
If the attacker can eavesdrop, then it can test any overheard nonce/response pairs against a list of common words. Such a list is usually much smaller than the total number of possible passwords. The cost of computing the response for each password on the list is paid once for each challenge.
Если злоумышленник может подслушивать, он может проверить любые подслушанные пары nonce/response по списку распространённых слов. Такой список обычно гораздо меньше общего числа возможных паролей. Затраты на вычисление ответа для каждого пароля из списка окупаются один раз на каждый запрос.
The server can mitigate this attack by not allowing users to select passwords that are in a dictionary.
Сервер может смягчить эту атаку, не позволяя пользователям выбирать пароли, которые есть в словаре.
4.8. Man in the Middle
4.8. Атака «человек посередине»
Both Basic and Digest authentication are vulnerable to "man in the middle" (MITM) attacks, for example, from a hostile or compromised proxy. Clearly, this would present all the problems of eavesdropping. But it also offers some additional opportunities to the attacker.
И базовая, и дайджест-аутентификация уязвимы к атакам «человек посередине» (man in the middle, MITM), например со стороны враждебного или скомпрометированного прокси. Очевидно, это создало бы все проблемы подслушивания. Но это также даёт злоумышленнику некоторые дополнительные возможности.
A possible man-in-the-middle attack would be to add a weak authentication scheme to the set of choices, hoping that the client will use one that exposes the user's credentials (e.g. password). For this reason, the client should always use the strongest scheme that it understands from the choices offered.
Возможная атака «человек посередине» состояла бы в добавлении слабой схемы аутентификации к набору вариантов в надежде, что клиент использует ту, которая раскрывает учётные данные пользователя (например, пароль). По этой причине клиент должен всегда использовать самую сильную схему, которую он понимает, из предлагаемых вариантов.
An even better MITM attack would be to remove all offered choices, replacing them with a challenge that requests only Basic authentication, then uses the cleartext credentials from the Basic authentication to authenticate to the origin server using the stronger scheme it requested. A particularly insidious way to mount such a MITM attack would be to offer a "free" proxy caching service to gullible users.
Ещё лучшая атака MITM состояла бы в удалении всех предложенных вариантов с заменой их на запрос, требующий только базовой аутентификации, а затем в использовании учётных данных открытого текста из базовой аутентификации для аутентификации на исходном сервере с помощью более сильной схемы, которую он запросил.
User agents should consider measures such as presenting a visual indication at the time of the credentials request of what authentication scheme is to be used, or remembering the strongest authentication scheme ever requested by a server and produce a warning message before using a weaker one. It might also be a good idea for the user agent to be configured to demand Digest authentication in general, or from specific sites.
Пользовательским агентам следует рассмотреть такие меры, как отображение визуального указания во время запроса учётных данных о том, какая схема аутентификации будет использоваться, либо запоминание самой сильной схемы аутентификации, когда-либо запрошенной сервером, и выдачу предупреждающего сообщения перед использованием более слабой.
Or, a hostile proxy might spoof the client into making a request the attacker wanted rather than one the client wanted. Of course, this is still much harder than a comparable attack against Basic Authentication.
Или враждебный прокси мог бы обмануть клиента, заставив его выполнить запрос, который был нужен злоумышленнику, а не тот, который нужен клиенту. Конечно, это всё же гораздо сложнее, чем сопоставимая атака против базовой аутентификации.
4.9. Chosen plaintext attacks
4.9. Атаки с выбранным открытым текстом
With Digest authentication, a MITM or a malicious server can arbitrarily choose the nonce that the client will use to compute the response. This is called a "chosen plaintext" attack. The ability to choose the nonce is known to make cryptanalysis much easier [8].
При дайджест-аутентификации MITM или вредоносный сервер может произвольно выбрать nonce, который клиент будет использовать для вычисления ответа. Это называется атакой с «выбранным открытым текстом». Известно, что возможность выбора nonce делает криптоанализ значительно проще [8].
However, no way to analyze the MD5 one-way function used by Digest using chosen plaintext is currently known.
Однако в настоящее время неизвестен способ анализа односторонней функции MD5, используемой в Digest, с помощью выбранного открытого текста.
The countermeasure against this attack is for clients to be configured to require the use of the optional "cnonce" directive; this allows the client to vary the input to the hash in a way not chosen by the attacker.
Мерой противодействия этой атаке является настройка клиентов на требование использования необязательной директивы «cnonce»; это позволяет клиенту варьировать входные данные хеша способом, не выбранным злоумышленником.
4.10. Precomputed dictionary attacks
4.10. Атаки по предвычисленному словарю
With Digest authentication, if the attacker can execute a chosen plaintext attack, the attacker can precompute the response for many common words to a nonce of its choice, and store a dictionary of (response, password) pairs. Such precomputation can often be done in parallel on many machines. It can then use the chosen plaintext attack to acquire a response corresponding to that challenge, and just look up the password in the dictionary. Even if most passwords are not in the dictionary, some might be. Since the attacker gets to pick the challenge, the cost of computing the response for each password on the list can be amortized over finding many passwords. A dictionary with 100 million password/response pairs would take about 3.2 gigabytes of disk storage.
При дайджест-аутентификации, если злоумышленник может выполнить атаку с выбранным открытым текстом, он может предвычислить ответ для многих распространённых слов на выбранный им nonce и сохранить словарь пар (response, password). Такое предвычисление часто может выполняться параллельно на многих машинах. Затем он может использовать атаку с выбранным открытым текстом, чтобы получить ответ, соответствующий этому запросу, и просто найти пароль в словаре. Даже если большинства паролей нет в словаре, некоторые могут там быть. Поскольку злоумышленник может сам выбирать запрос, затраты на вычисление ответа для каждого пароля из списка могут быть амортизированы за счёт нахождения многих паролей. Словарь со 100 миллионами пар пароль/ответ занял бы около 3,2 гигабайта дискового пространства.
The countermeasure against this attack is to for clients to be configured to require the use of the optional "cnonce" directive.
Мерой противодействия этой атаке является настройка клиентов на требование использования необязательной директивы «cnonce».
4.11. Batch brute force attacks
4.11. Пакетные атаки полного перебора
With Digest authentication, a MITM can execute a chosen plaintext attack, and can gather responses from many users to the same nonce. It can then find all the passwords within any subset of password space that would generate one of the nonce/response pairs in a single pass over that space. It also reduces the time to find the first password by a factor equal to the number of nonce/response pairs gathered. This search of the password space can often be done in parallel on many machines, and even a single machine can search large subsets of the password space very quickly -- reports exist of searching all passwords with six or fewer letters in a few hours.
При дайджест-аутентификации MITM может выполнить атаку с выбранным открытым текстом и собрать ответы от многих пользователей на один и тот же nonce. Затем он может найти все пароли в любом подмножестве пространства паролей, которые породили бы одну из пар nonce/response, за один проход по этому пространству. Это также сокращает время нахождения первого пароля в число раз, равное количеству собранных пар nonce/response. Такой поиск по пространству паролей часто может выполняться параллельно на многих машинах, и даже одна машина может очень быстро просмотреть большие подмножества пространства паролей — есть сообщения о переборе всех паролей длиной шесть букв и менее за несколько часов.
The countermeasure against this attack is to for clients to be configured to require the use of the optional "cnonce" directive.
Мерой противодействия этой атаке является настройка клиентов на требование использования необязательной директивы «cnonce».
4.12. Spoofing by Counterfeit Servers
4.12. Подмена поддельными серверами
Basic Authentication is vulnerable to spoofing by counterfeit servers. If a user can be led to believe that she is connecting to a host containing information protected by a password she knows, when in fact she is connecting to a hostile server, then the hostile server can request a password, store it away for later use, and feign an error. This type of attack is more difficult with Digest Authentication -- but the client must know to demand that Digest authentication be used, perhaps using some of the techniques described above to counter "man-in-the-middle" attacks. Again, the user can be helped in detecting this attack by a visual indication of the authentication mechanism in use with appropriate guidance in interpreting the implications of each scheme.
Базовая аутентификация уязвима к подмене поддельными серверами. Если пользователя можно убедить, что он подключается к хосту, содержащему информацию, защищённую известным ему паролем, тогда как на самом деле он подключается к враждебному серверу, то враждебный сервер может запросить пароль, сохранить его для последующего использования и изобразить ошибку. Этот тип атаки сложнее при дайджест-аутентификации, но клиент должен знать, как потребовать использования дайджест-аутентификации, возможно применяя некоторые из описанных выше методов противодействия атакам «человек посередине». Опять же, пользователю можно помочь обнаружить эту атаку визуальным указанием используемого механизма аутентификации с соответствующими пояснениями о значении каждой схемы.
4.13. Storing passwords
4.13. Хранение паролей
Digest authentication requires that the authenticating agent (usually the server) store some data derived from the user's name and password in a "password file" associated with a given realm. Normally this might contain pairs consisting of username and H(A1), where H(A1) is the digested value of the username, realm, and password as described above.
Дайджест-аутентификация требует, чтобы аутентифицирующий агент (обычно сервер) хранил некоторые данные, производные от имени пользователя и пароля, в «файле паролей», связанном с данным realm. Обычно он может содержать пары, состоящие из имени пользователя и H(A1), где H(A1) — дайджест-значение имени пользователя, realm и пароля, как описано выше.
The security implications of this are that if this password file is compromised, then an attacker gains immediate access to documents on the server using this realm. Unlike, say a standard UNIX password file, this information need not be decrypted in order to access documents in the server realm associated with this file. On the other hand, decryption, or more likely a brute force attack, would be necessary to obtain the user's password. This is the reason that the realm is part of the digested data stored in the password file. It means that if one Digest authentication password file is compromised, it does not automatically compromise others with the same username and password (though it does expose them to brute force attack).
Последствия этого для безопасности таковы, что при компрометации этого файла паролей злоумышленник немедленно получает доступ к документам на сервере с использованием этого realm. В отличие, скажем, от стандартного файла паролей UNIX, эта информация не нуждается в расшифровке для доступа к документам в realm сервера, связанном с этим файлом. С другой стороны, расшифровка или, что более вероятно, атака полным перебором потребовалась бы для получения пароля пользователя. Именно поэтому realm является частью хешируемых данных, хранимых в файле паролей. Это означает, что если один файл паролей дайджест-аутентификации скомпрометирован, он не компрометирует автоматически другие с тем же именем пользователя и паролем (хотя и подвергает их атаке полным перебором).
There are two important security consequences of this. First the password file must be protected as if it contained unencrypted passwords, because for the purpose of accessing documents in its realm, it effectively does.
Из этого следуют два важных последствия для безопасности. Во-первых, файл паролей должен быть защищён так, как если бы он содержал незашифрованные пароли, поскольку для целей доступа к документам в своём realm он фактически их содержит.
A second consequence of this is that the realm string should be unique among all realms which any single user is likely to use. In particular a realm string should include the name of the host doing the authentication. The inability of the client to authenticate the server is a weakness of Digest Authentication.
Второе следствие состоит в том, что строка realm должна быть уникальной среди всех realm, которые может использовать любой отдельный пользователь. В частности, строка realm должна содержать имя хоста, выполняющего аутентификацию. Неспособность клиента аутентифицировать сервер является слабостью дайджест-аутентификации.
4.14. Summary
4.14. Итоги
By modern cryptographic standards Digest Authentication is weak. But for a large range of purposes it is valuable as a replacement for Basic Authentication. It remedies some, but not all, weaknesses of Basic Authentication. Its strength may vary depending on the implementation. In particular the structure of the nonce (which is dependent on the server implementation) may affect the ease of mounting a replay attack. A range of server options is appropriate since, for example, some implementations may be willing to accept the server overhead of one-time nonces or digests to eliminate the possibility of replay. Others may satisfied with a nonce like the one recommended above restricted to a single IP address and a single ETag or with a limited lifetime. The bottom line is that *any* compliant implementation will be relatively weak by cryptographic standards, but *any* compliant implementation will be far superior to Basic Authentication.
По современным криптографическим стандартам дайджест-аутентификация слаба. Но для широкого круга целей она ценна как замена базовой аутентификации. Она устраняет некоторые, но не все слабости базовой аутентификации. Её стойкость может различаться в зависимости от реализации. В частности, структура nonce (которая зависит от реализации сервера) может влиять на легкость проведения атаки повторного воспроизведения. Диапазон серверных опций уместен, поскольку, например, некоторые реализации могут быть готовы нести накладные расходы на одноразовые nonce или дайджесты, чтобы исключить возможность повторного воспроизведения. Другие могут удовлетвориться nonce, подобным рекомендованному выше, ограниченным одним IP-адресом и одним ETag либо ограниченным сроком жизни.
