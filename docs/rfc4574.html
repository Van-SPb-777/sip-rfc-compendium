Abstract
Аннотация
This document defines a new Session Description Protocol (SDP) media-level attribute: "label". The "label" attribute carries a pointer to a media stream in the context of an arbitrary network application that uses SDP. The sender of the SDP document can attach the "label" attribute to a particular media stream or streams. The application can then use the provided pointer to refer to each particular media stream in its context.
Настоящий документ определяет новый атрибут уровня медиа протокола описания сессий (SDP) — «label». Атрибут «label» несёт указатель на медиапоток в контексте произвольного сетевого приложения, использующего SDP. Отправитель документа SDP может прикрепить атрибут «label» к конкретному медиапотоку или потокам. Затем приложение может использовать предоставленный указатель для ссылки на каждый конкретный медиапоток в своём контексте.
1. Introduction
1. Введение
SDP is being used by a variety of distributed-over-the-network applications. These applications deal with multiple sessions being described by SDP [4] and serving multiple users or services in the context of a single application instance. Applications of this kind need a means to identify a particular media stream across multiple SDP descriptions exchanged with different users.
SDP используется самыми разными приложениями, распределёнными по сети. Эти приложения работают с несколькими сессиями, описываемыми SDP [4], и обслуживают множество пользователей или служб в контексте одного экземпляра приложения. Приложения такого рода нуждаются в средстве идентификации конкретного медиапотока в нескольких описаниях сессий SDP, которыми они обмениваются с разными пользователями.
The XCON framework is an example of a centralized conference architecture that uses SDP according to the offer/answer mechanism defined in [3] to establish media streams with each of the conference participants. Additionally, XCON identifies the need to uniquely identify a media stream in terms of its role in a conference regardless of its media type, transport protocol, and media format. This can be accomplished by using an external document that points to the appropriate media stream and provides information (e.g., the media stream's role in the conference) about it. The SIP Event Package for Conference State [7] defines and uses a concrete format for such external documents.
Архитектура XCON — пример централизованной конференц-архитектуры, которая использует SDP в соответствии с механизмом «предложение/ответ», определённым в [3], для установления медиапотоков с каждым из участников конференции. Кроме того, XCON определяет необходимость однозначной идентификации медиапотока с точки зрения его роли в конференции независимо от типа медиа, транспортного протокола и формата медиа. Это может быть достигнуто с помощью внешнего документа, который указывает на соответствующий медиапоток и предоставляет сведения о нём (например, роль медиапотока в конференции). Пакет событий SIP для состояния конференции [7] определяет и использует конкретный формат для таких внешних документов.
This specification defines the SDP [4] "label" media-level attribute, which provides a pointer to a media stream that is described by an 'm' line in an SDP session description.
Настоящая спецификация определяет атрибут уровня медиа «label» протокола SDP [4], который предоставляет указатель на медиапоток, описываемый строкой 'm' в описании сессии SDP.

3. Motivation for the New label Attribute
3. Мотивация для нового атрибута label
Even though SDP and its extensions already provide a few ways to refer to a media stream, none of them is appropriate to be used in the context of external documents that may be created before the session description itself and need to be handled by automata.
Хотя SDP и его расширения уже предоставляют несколько способов ссылаться на медиапоток, ни один из них не пригоден для использования в контексте внешних документов, которые могут быть созданы раньше самого описания сессии и должны обрабатываться автоматами.
The 'i' SDP attribute, defined in RFC 2327 [4], can be used to label media streams. Nevertheless, values of the 'i' attribute are intended for human users and not for automata. The 'mid' SDP attribute, defined in RFC 3388 [6], can be used to identify media streams as well. Nevertheless, the scope of 'mid' is too limited to be used by applications dealing with multiple SDP sessions. This is because values of the 'mid' attribute are meaningful in the context of a single SDP session, not in the context of a broader application (e.g., a multiparty application).
Атрибут SDP 'i', определённый в RFC 2327 [4], может использоваться для маркировки медиапотоков. Тем не менее значения атрибута 'i' предназначены для людей, а не для автоматов. Атрибут SDP 'mid', определённый в RFC 3388 [6], также может использоваться для идентификации медиапотоков. Тем не менее область применения 'mid' слишком ограничена для использования приложениями, работающими с несколькими сессиями SDP. Это объясняется тем, что значения атрибута 'mid' имеют смысл в контексте одной сессии SDP, а не в контексте более широкого приложения (например, многостороннего приложения).
Another way of referring to a media stream is by using the order of the 'm' line in the SDP session document (e.g., the 5th media stream in the session description). This is the mechanism used in the offer/answer model [3].
Ещё один способ ссылки на медиапоток — использование порядка строки 'm' в документе сессии SDP (например, пятый медиапоток в описании сессии). Именно этот механизм используется в модели «предложение/ответ» [3].
The problem with this mechanism is that it can only be used to refer to media streams in session descriptions that exist already. There are scenarios where a static document needs to refer, using a pointer, to a media stream that will be negotiated by SDP means and created in the future. When the media stream is eventually created, the application needs to label the media stream so that the pointer in the static document points to the proper media stream in the session description.
Проблема этого механизма состоит в том, что его можно использовать для ссылки на медиапотоки только в уже существующих описаниях сессий. Бывают сценарии, когда статический документ должен с помощью указателя ссылаться на медиапоток, который будет согласован средствами SDP и создан в будущем. Когда медиапоток в конечном счёте создан, приложению нужно пометить медиапоток, чтобы указатель в статическом документе указывал на надлежащий медиапоток в описании сессии.
4. The Label Attribute
4. Атрибут label
This specification defines a new media-level value attribute: 'label'. Its formatting in SDP is described by the following ABNF [2]:
Настоящая спецификация определяет новый атрибут-значение уровня медиа: 'label'. Его форматирование в SDP описано следующей ABNF [2]:
label-attribute = "a=label:" pointer pointer = token token = 1*(token-char) token-char = %x21 / %x23-27 / %x2A-2B / %x2D-2E / %x30-39 / %x41-5A / %x5E-7E
label-attribute = "a=label:" pointer pointer = token token = 1*(token-char) token-char = %x21 / %x23-27 / %x2A-2B / %x2D-2E / %x30-39 / %x41-5A / %x5E-7E
The token-char and token elements are defined in [4] but included here to provide support for the implementor of this SDP feature.
Элементы token-char и token определены в [4], но приведены здесь, чтобы поддержать разработчика этой возможности SDP.
The 'label' attribute contains a token that is defined by an application and is used in its context. The new attribute can be attached to 'm' lines in multiple SDP documents allowing the application to logically group the media streams across SDP sessions when necessary.
Атрибут 'label' содержит токен, который определяется приложением и используется в его контексте. Новый атрибут можно прикреплять к строкам 'm' в нескольких документах SDP, что позволяет приложению при необходимости логически группировать медиапотоки между сессиями SDP.
5. The Label Attribute in the Offer/Answer Model
5. Атрибут label в модели «предложение/ответ»
This specification does not define a means to discover whether or not the peer endpoint understands the 'label' attribute because 'label' values are informative only at the offer/answer model level.
Настоящая спецификация не определяет средство обнаружения того, понимает ли партнёрский узел атрибут 'label', поскольку значения 'label' носят информативный характер только на уровне модели «предложение/ответ».
At the offer/answer level, it means that the fact that an offer does not contain label attributes does not imply that the answer should not have them. It also means that the fact that an offer contains label attributes does not imply that the answer should have them too.
На уровне «предложение/ответ» это означает, что отсутствие атрибутов label в предложении не подразумевает, что их не должно быть в ответе. Это также означает, что наличие атрибутов label в предложении не подразумевает, что они должны быть и в ответе.
In addition to the basic offer/answer rule above, applications that use 'label' as a pointer to media streams MUST specify its usage constraints. For example, such applications MAY mandate support for 'label'. In this case, the application will define means for negotiation of the 'label' attribute support as a part of its specification.
В дополнение к основному правилу «предложение/ответ», приведённому выше, приложения, использующие 'label' в качестве указателя на медиапотоки, ДОЛЖНЫ указывать ограничения его использования. Например, такие приложения МОГУТ предписывать поддержку 'label'. В этом случае приложение определит средства согласования поддержки атрибута 'label' в составе своей спецификации.
6. Example
6. Пример
The following is an example of an SDP session description that uses the 'label' attribute:
Ниже приведён пример описания сессии SDP, в котором используется атрибут 'label':
v=0 o=bob 280744730 28977631 IN IP4 host.example.com s= i=A Seminar on the session description protocol c=IN IP4 192.0.2.2 t=0 0 m=audio 6886 RTP/AVP 0 a=label:1 m=audio 22334 RTP/AVP 0 a=label:2
v=0 o=bob 280744730 28977631 IN IP4 host.example.com s= i=A Seminar on the session description protocol c=IN IP4 192.0.2.2 t=0 0 m=audio 6886 RTP/AVP 0 a=label:1 m=audio 22334 RTP/AVP 0 a=label:2
7. Security Considerations
7. Вопросы безопасности
An attacker may attempt to add, modify, or remove 'label' attributes from a session description. This could result in an application behaving in a non-desirable way. So, it is strongly RECOMMENDED that integrity protection be applied to the SDP session descriptions. For session descriptions carried in SIP [5], S/MIME is the natural choice to provide such end-to-end integrity protection, as described in RFC 3261 [5]. Other applications MAY use a different form of integrity protection.
Злоумышленник может попытаться добавить, изменить или удалить атрибуты 'label' из описания сессии. Это может привести к нежелательному поведению приложения. Поэтому НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ применять защиту целостности к описаниям сессий SDP. Для описаний сессий, переносимых в SIP [5], естественным выбором для обеспечения такой сквозной защиты целостности является S/MIME, как описано в RFC 3261 [5]. Другие приложения МОГУТ использовать иную форму защиты целостности.
