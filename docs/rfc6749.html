The OAuth 2.0 Authorization Framework

Abstract
Аннотация
The OAuth 2.0 authorization framework enables a third-party application to obtain limited access to an HTTP service, either on behalf of a resource owner by orchestrating an approval interaction between the resource owner and the HTTP service, or by allowing the third-party application to obtain access on its own behalf. This specification replaces and obsoletes the OAuth 1.0 protocol described in RFC 5849.
Основы авторизации OAuth 2.0 позволяют стороннему приложению получить ограниченный доступ к службе HTTP — либо от имени владельца ресурса путём организации взаимодействия по утверждению между владельцем ресурса и службой HTTP, либо за счёт того, что стороннему приложению разрешается получить доступ от своего имени. Настоящая спецификация заменяет и делает устаревшим протокол OAuth 1.0, описанный в RFC 5849.

1. Introduction
1. Введение
In the traditional client-server authentication model, the client requests an access-restricted resource (protected resource) on the server by authenticating with the server using the resource owner's credentials. In order to provide third-party applications access to restricted resources, the resource owner shares its credentials with the third party. This creates several problems and limitations:
В традиционной модели аутентификации «клиент-сервер» клиент запрашивает у сервера ресурс с ограниченным доступом (защищённый ресурс), аутентифицируясь на сервере с помощью учётных данных владельца ресурса. Чтобы предоставить сторонним приложениям доступ к защищённым ресурсам, владелец ресурса делится с третьей стороной своими учётными данными. Это порождает несколько проблем и ограничений:
o Third-party applications are required to store the resource owner's credentials for future use, typically a password in clear-text.
o Сторонние приложения вынуждены хранить учётные данные владельца ресурса для последующего использования — как правило, пароль в открытом виде.
o Servers are required to support password authentication, despite the security weaknesses inherent in passwords.
o Серверы вынуждены поддерживать аутентификацию по паролю, несмотря на присущие паролям слабости защиты.
o Third-party applications gain overly broad access to the resource owner's protected resources, leaving resource owners without any ability to restrict duration or access to a limited subset of resources.
o Сторонние приложения получают чрезмерно широкий доступ к защищённым ресурсам владельца ресурса, лишая владельцев ресурсов всякой возможности ограничить срок действия или доступ к ограниченному подмножеству ресурсов.
o Resource owners cannot revoke access to an individual third party without revoking access to all third parties, and must do so by changing the third party's password.
o Владельцы ресурсов не могут отозвать доступ у отдельной третьей стороны, не отозвав доступ у всех третьих сторон, и вынуждены делать это, меняя пароль третьей стороны.
o Compromise of any third-party application results in compromise of the end-user's password and all of the data protected by that password.
o Компрометация любого стороннего приложения ведёт к компрометации пароля конечного пользователя и всех данных, защищённых этим паролем.
OAuth addresses these issues by introducing an authorization layer and separating the role of the client from that of the resource owner. In OAuth, the client requests access to resources controlled by the resource owner and hosted by the resource server, and is issued a different set of credentials than those of the resource owner.
OAuth решает эти проблемы, вводя слой авторизации и отделяя роль клиента от роли владельца ресурса. В OAuth клиент запрашивает доступ к ресурсам, контролируемым владельцем ресурса и размещённым на сервере ресурсов, и получает иной набор учётных данных, нежели учётные данные владельца ресурса.
Instead of using the resource owner's credentials to access protected resources, the client obtains an access token -- a string denoting a specific scope, lifetime, and other access attributes. Access tokens are issued to third-party clients by an authorization server with the approval of the resource owner. The client uses the access token to access the protected resources hosted by the resource server.
Вместо использования учётных данных владельца ресурса для доступа к защищённым ресурсам клиент получает токен доступа — строку, обозначающую конкретную область действия, срок жизни и другие атрибуты доступа. Токены доступа выдаются сторонним клиентам сервером авторизации с одобрения владельца ресурса. Клиент использует токен доступа для доступа к защищённым ресурсам, размещённым на сервере ресурсов.
For example, an end-user (resource owner) can grant a printing service (client) access to her protected photos stored at a photo- sharing service (resource server), without sharing her username and password with the printing service. Instead, she authenticates directly with a server trusted by the photo-sharing service (authorization server), which issues the printing service delegation- specific credentials (access token).
Например, конечный пользователь (владелец ресурса) может предоставить службе печати (клиенту) доступ к своим защищённым фотографиям, хранящимся в службе обмена фотографиями (сервере ресурсов), не сообщая службе печати своё имя пользователя и пароль. Вместо этого она аутентифицируется напрямую на сервере, которому доверяет служба обмена фотографиями (сервере авторизации), а тот выдаёт службе печати учётные данные делегирования (токен доступа), специфичные для неё.
This specification is designed for use with HTTP ([RFC2616]). The use of OAuth over any protocol other than HTTP is out of scope.
Настоящая спецификация предназначена для использования с HTTP ([RFC2616]). Использование OAuth поверх прочих протоколов выходит за рамки настоящей спецификации.
The OAuth 1.0 protocol ([RFC5849]), published as an informational document, was the result of a small ad hoc community effort. This Standards Track specification builds on the OAuth 1.0 deployment experience, as well as additional use cases and extensibility requirements gathered from the wider IETF community. The OAuth 2.0 protocol is not backward compatible with OAuth 1.0. The two versions may co-exist on the network, and implementations may choose to support both. However, it is the intention of this specification that new implementations support OAuth 2.0 as specified in this document and that OAuth 1.0 is used only to support existing deployments. The OAuth 2.0 protocol shares very few implementation details with the OAuth 1.0 protocol. Implementers familiar with OAuth 1.0 should approach this document without any assumptions as to its structure and details.
Протокол OAuth 1.0 ([RFC5849]), опубликованный как информационный документ, стал результатом небольшой неформальной работы сообщества. Настоящая спецификация уровня Standards Track опирается на опыт развёртывания OAuth 1.0, а также на дополнительные варианты использования и требования к расширяемости, собранные у более широкого сообщества IETF. Протокол OAuth 2.0 несовместим с OAuth 1.0 в обратном направлении. Обе версии могут сосуществовать в сети, и реализации могут поддерживать обе. Однако замысел настоящей спецификации состоит в том, чтобы новые реализации поддерживали OAuth 2.0 в соответствии с настоящим документом, а OAuth 1.0 использовался только для поддержки существующих развёртываний. Протокол OAuth 2.0 имеет очень мало общих деталей реализации с протоколом OAuth 1.0. Разработчикам, знакомым с OAuth 1.0, следует подходить к настоящему документу, не делая никаких предположений о его структуре и деталях.
1.1. Roles
1.1. Роли
OAuth defines four roles:
OAuth определяет четыре роли:
resource owner An entity capable of granting access to a protected resource. When the resource owner is a person, it is referred to as an end-user.
владелец ресурса. Сущность, способная предоставить доступ к защищённому ресурсу. Когда владелец ресурса — человек, его называют конечным пользователем.
resource server The server hosting the protected resources, capable of accepting and responding to protected resource requests using access tokens.
сервер ресурсов. Сервер, на котором размещены защищённые ресурсы и который способен принимать запросы к защищённым ресурсам и отвечать на них с использованием токенов доступа.
client An application making protected resource requests on behalf of the resource owner and with its authorization. The term "client" does not imply any particular implementation characteristics (e.g., whether the application executes on a server, a desktop, or other devices).
клиент. Приложение, запрашивающее защищённые ресурсы от имени владельца ресурса и с его разрешения. Термин «клиент» не подразумевает каких-либо конкретных особенностей реализации (например, выполняется ли приложение на сервере, настольном компьютере или иных устройствах).
authorization server The server issuing access tokens to the client after successfully authenticating the resource owner and obtaining authorization.
сервер авторизации. Сервер, выдающий клиенту токены доступа после успешной аутентификации владельца ресурса и получения авторизации.
The interaction between the authorization server and resource server is beyond the scope of this specification. The authorization server may be the same server as the resource server or a separate entity. A single authorization server may issue access tokens accepted by multiple resource servers.
Взаимодействие между сервером авторизации и сервером ресурсов выходит за рамки настоящей спецификации. Сервер авторизации может быть тем же сервером, что и сервер ресурсов, или отдельной сущностью. Один сервер авторизации может выдавать токены доступа, принимаемые несколькими серверами ресурсов.

1.3. Authorization Grant
1.3. Грант авторизации
An authorization grant is a credential representing the resource owner's authorization (to access its protected resources) used by the client to obtain an access token. This specification defines four grant types -- authorization code, implicit, resource owner password credentials, and client credentials -- as well as an extensibility mechanism for defining additional types.
Грант авторизации — это учётные данные, представляющие авторизацию владельца ресурса (на доступ к его защищённым ресурсам), используемые клиентом для получения токена доступа. Настоящая спецификация определяет четыре типа грантов — код авторизации, неявный, учётные данные пароля владельца ресурса и учётные данные клиента, — а также механизм расширения для определения дополнительных типов.
1.3.1. Authorization Code
1.3.1. Код авторизации
The authorization code is obtained by using an authorization server as an intermediary between the client and resource owner. Instead of requesting authorization directly from the resource owner, the client directs the resource owner to an authorization server (via its user-agent as defined in [RFC2616]), which in turn directs the resource owner back to the client with the authorization code.
Код авторизации получают, используя сервер авторизации как посредника между клиентом и владельцем ресурса. Вместо того чтобы запрашивать авторизацию напрямую у владельца ресурса, клиент направляет владельца ресурса на сервер авторизации (через его пользовательский агент, как определено в [RFC2616]), который, в свою очередь, направляет владельца ресурса обратно клиенту с кодом авторизации.
Before directing the resource owner back to the client with the authorization code, the authorization server authenticates the resource owner and obtains authorization. Because the resource owner only authenticates with the authorization server, the resource owner's credentials are never shared with the client.
Прежде чем направить владельца ресурса обратно клиенту с кодом авторизации, сервер авторизации аутентифицирует владельца ресурса и получает авторизацию. Поскольку владелец ресурса аутентифицируется только на сервере авторизации, его учётные данные никогда не передаются клиенту.
The authorization code provides a few important security benefits, such as the ability to authenticate the client, as well as the transmission of the access token directly to the client without passing it through the resource owner's user-agent and potentially exposing it to others, including the resource owner.
Код авторизации даёт несколько важных преимуществ в плане безопасности, например возможность аутентификации клиента, а также передачу токена доступа непосредственно клиенту без прохождения через пользовательский агент владельца ресурса и потенциального раскрытия его другим лицам, включая самого владельца ресурса.
1.3.2. Implicit
1.3.2. Неявный
The implicit grant is a simplified authorization code flow optimized for clients implemented in a browser using a scripting language such as JavaScript. In the implicit flow, instead of issuing the client an authorization code, the client is issued an access token directly (as the result of the resource owner authorization). The grant type is implicit, as no intermediate credentials (such as an authorization code) are issued (and later used to obtain an access token).
Неявный грант — это упрощённый поток кода авторизации, оптимизированный для клиентов, реализованных в браузере с использованием языка сценариев, такого как JavaScript. В неявном потоке вместо выдачи клиенту кода авторизации клиенту напрямую выдаётся токен доступа (как результат авторизации владельца ресурса). Тип гранта является неявным, поскольку промежуточные учётные данные (такие как код авторизации) не выдаются (и позже не используются для получения токена доступа).
When issuing an access token during the implicit grant flow, the authorization server does not authenticate the client. In some cases, the client identity can be verified via the redirection URI used to deliver the access token to the client. The access token may be exposed to the resource owner or other applications with access to the resource owner's user-agent.
При выдаче токена доступа в ходе неявного гранта сервер авторизации не аутентифицирует клиента. В некоторых случаях идентичность клиента можно проверить по URI перенаправления, используемому для доставки токена доступа клиенту. Токен доступа может быть раскрыт владельцу ресурса или другим приложениям, имеющим доступ к пользовательскому агенту владельца ресурса.
Implicit grants improve the responsiveness and efficiency of some clients (such as a client implemented as an in-browser application), since it reduces the number of round trips required to obtain an access token. However, this convenience should be weighed against the security implications of using implicit grants, such as those described in Sections 10.3 and 10.16, especially when the authorization code grant type is available.
Неявные гранты повышают отзывчивость и эффективность некоторых клиентов (например, клиента, реализованного как приложение в браузере), поскольку сокращают число обменов, необходимых для получения токена доступа. Однако эту удобность следует сопоставлять с последствиями для безопасности при использовании неявных грантов, такими как описанные в разделах 10.3 и 10.16, особенно когда доступен тип гранта «код авторизации».
1.3.3. Resource Owner Password Credentials
1.3.3. Учётные данные пароля владельца ресурса
The resource owner password credentials (i.e., username and password) can be used directly as an authorization grant to obtain an access token. The credentials should only be used when there is a high degree of trust between the resource owner and the client (e.g., the client is part of the device operating system or a highly privileged application), and when other authorization grant types are not available (such as an authorization code).
Учётные данные пароля владельца ресурса (то есть имя пользователя и пароль) можно использовать непосредственно как грант авторизации для получения токена доступа. Эти учётные данные следует использовать только тогда, когда между владельцем ресурса и клиентом существует высокая степень доверия (например, клиент входит в состав операционной системы устройства или является приложением с высокими привилегиями), и когда другие типы грантов авторизации недоступны (например, код авторизации).
Even though this grant type requires direct client access to the resource owner credentials, the resource owner credentials are used for a single request and are exchanged for an access token. This grant type can eliminate the need for the client to store the resource owner credentials for future use, by exchanging the credentials with a long-lived access token or refresh token.
Хотя этот тип гранта требует прямого доступа клиента к учётным данным владельца ресурса, учётные данные владельца ресурса используются для одного запроса и обмениваются на токен доступа. Этот тип гранта позволяет устранить необходимость хранения клиентом учётных данных владельца ресурса для последующего использования, обменивая эти учётные данные на долгоживущий токен доступа или токен обновления.
1.3.4. Client Credentials
1.3.4. Учётные данные клиента
The client credentials (or other forms of client authentication) can be used as an authorization grant when the authorization scope is limited to the protected resources under the control of the client, or to protected resources previously arranged with the authorization server. Client credentials are used as an authorization grant typically when the client is acting on its own behalf (the client is also the resource owner) or is requesting access to protected resources based on an authorization previously arranged with the authorization server.
Учётные данные клиента (или иные формы аутентификации клиента) можно использовать как грант авторизации, когда область действия авторизации ограничена защищёнными ресурсами, контролируемыми клиентом, или защищёнными ресурсами, о которых заранее договорились с сервером авторизации. Учётные данные клиента используются как грант авторизации обычно тогда, когда клиент действует от своего имени (клиент является также владельцем ресурса) или запрашивает доступ к защищённым ресурсам на основании авторизации, заранее согласованной с сервером авторизации.

1.5. Токен обновления
Refresh tokens are credentials used to obtain access tokens. Issuing a refresh token is optional at the discretion of the authorization server. If the authorization server issues a refresh token, it is included when issuing an access token (i.e., step (D) in Figure 1).

Выдача токена обновления необязательна и зависит от решения сервера авторизации. This specification makes extensive use of HTTP redirections, in which the client or the authorization server directs the resource owner's user-agent to another destination. Хотя примеры в настоящей спецификации показывают использование кода состояния HTTP 302, допускается любой другой способ, доступный через пользовательский агент для выполнения этого перенаправления, и он считается деталью реализации.
1.8. Interoperability
1.8. Совместимость
OAuth 2.0 provides a rich authorization framework with well-defined security properties. However, as a rich and highly extensible framework with many optional components, on its own, this specification is likely to produce a wide range of non-interoperable implementations.
OAuth 2.0 предоставляет богатые основы авторизации с хорошо определёнными свойствами безопасности. Однако, будучи богатыми и легко расширяемыми основами со множеством необязательных компонентов, настоящая спецификация сама по себе, вероятно, породит широкий спектр несовместимых реализаций.
In addition, this specification leaves a few required components partially or fully undefined (e.g., client registration, authorization server capabilities, endpoint discovery). Without these components, clients must be manually and specifically configured against a specific authorization server and resource server in order to interoperate.
Кроме того, настоящая спецификация оставляет некоторые обязательные компоненты частично или полностью неопределёнными (например, регистрацию клиента, возможности сервера авторизации, обнаружение конечных точек). Без этих компонентов клиенты должны быть настроены вручную и конкретно под определённый сервер авторизации и сервер ресурсов, чтобы обеспечивать совместимость.
This framework was designed with the clear expectation that future work will define prescriptive profiles and extensions necessary to achieve full web-scale interoperability.
Эти основы были разработаны с ясным расчётом на то, что будущая работа определит предписывающие профили и расширения, необходимые для достижения полной совместимости в масштабах веба.

Приложение на основе пользовательского агента — это публичный клиент, в котором код клиента загружается с веб-сервера и выполняется в пользовательском агенте (например, в веб-браузере) на устройстве, используемом владельцем ресурса. Данные протокола и учётные данные легко доступны (и часто видны) владельцу ресурса. Поскольку такие приложения находятся внутри пользовательского агента, они могут беспрепятственно использовать возможности пользовательского агента при запросе авторизации.
native application A native application is a public client installed and executed on the device used by the resource owner. Protocol data and credentials are accessible to the resource owner. It is assumed that any client authentication credentials included in the application can be extracted. On the other hand, dynamically issued credentials such as access tokens or refresh tokens can receive an acceptable level of protection. At a minimum, these credentials are protected from hostile servers with which the application may interact. On some platforms, these credentials might be protected from other applications residing on the same device.
нативное приложение. Нативное приложение — это публичный клиент, установленный и выполняемый на устройстве, используемом владельцем ресурса. Данные протокола и учётные данные доступны владельцу ресурса. Предполагается, что любые учётные данные аутентификации клиента, включённые в приложение, могут быть извлечены. С другой стороны, динамически выдаваемые учётные данные, такие как токены доступа или токены обновления, могут получить приемлемый уровень защиты. Как минимум, эти учётные данные защищены от враждебных серверов, с которыми приложение может взаимодействовать. На некоторых платформах эти учётные данные могут быть защищены от других приложений, находящихся на том же устройстве.
2.2. Client Identifier
2.2. Идентификатор клиента
The authorization server issues the registered client a client identifier -- a unique string representing the registration information provided by the client. The client identifier is not a secret; it is exposed to the resource owner and MUST NOT be used alone for client authentication. The client identifier is unique to the authorization server.
Сервер авторизации выдаёт зарегистрированному клиенту идентификатор клиента — уникальную строку, представляющую сведения регистрации, предоставленные клиентом. Идентификатор клиента не является секретом; он раскрывается владельцу ресурса и НЕ ДОЛЖЕН использоваться отдельно для аутентификации клиента. Идентификатор клиента уникален для сервера авторизации.
The client identifier string size is left undefined by this specification. The client should avoid making assumptions about the identifier size. The authorization server SHOULD document the size of any identifier it issues.
Размер строки идентификатора клиента настоящей спецификацией не определён. Клиенту следует избегать предположений о размере идентификатора. Серверу авторизации СЛЕДУЕТ документировать размер любого выдаваемого им идентификатора.
2.3. Client Authentication
2.3. Аутентификация клиента
If the client type is confidential, the client and authorization server establish a client authentication method suitable for the security requirements of the authorization server. The authorization server MAY accept any form of client authentication meeting its security requirements.
Если тип клиента конфиденциальный, клиент и сервер авторизации устанавливают метод аутентификации клиента, подходящий для требований безопасности сервера авторизации. Сервер авторизации МОЖЕТ принимать любую форму аутентификации клиента, отвечающую его требованиям безопасности.
Confidential clients are typically issued (or establish) a set of client credentials used for authenticating with the authorization server (e.g., password, public/private key pair).
Конфиденциальным клиентам обычно выдаётся (или они устанавливают) набор учётных данных клиента, используемых для аутентификации на сервере авторизации (например, пароль, пара открытого и закрытого ключей).
The authorization server MAY establish a client authentication method with public clients. However, the authorization server MUST NOT rely on public client authentication for the purpose of identifying the client.
Сервер авторизации МОЖЕТ установить метод аутентификации клиента и для публичных клиентов. Однако сервер авторизации НЕ ДОЛЖЕН полагаться на аутентификацию публичного клиента для целей идентификации клиента.
The client MUST NOT use more than one authentication method in each request.
Клиент НЕ ДОЛЖЕН использовать более одного метода аутентификации в каждом запросе.
2.3.1. Client Password
2.3.1. Пароль клиента
Clients in possession of a client password MAY use the HTTP Basic authentication scheme as defined in [RFC2617] to authenticate with the authorization server. The client identifier is encoded using the "application/x-www-form-urlencoded" encoding algorithm per Appendix B, and the encoded value is used as the username; the client password is encoded using the same algorithm and used as the password. The authorization server MUST support the HTTP Basic authentication scheme for authenticating clients that were issued a client password.
Клиенты, располагающие паролем клиента, МОГУТ использовать схему аутентификации HTTP Basic, определённую в [RFC2617], для аутентификации на сервере авторизации. Идентификатор клиента кодируется с использованием алгоритма кодирования «application/x-www-form-urlencoded» согласно приложению B, и закодированное значение используется как имя пользователя; пароль клиента кодируется тем же алгоритмом и используется как пароль. Сервер авторизации ДОЛЖЕН поддерживать схему аутентификации HTTP Basic для аутентификации клиентов, которым был выдан пароль клиента.
For example (with extra line breaks for display purposes only):
Например (дополнительные разрывы строк сделаны только для наглядности):

Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3

В качестве альтернативы сервер авторизации МОЖЕТ поддерживать включение учётных данных клиента в тело запроса с использованием следующих параметров:
client_id REQUIRED. The client identifier issued to the client during the registration process described by Section 2.2.
client_id ОБЯЗАТЕЛЕН. Идентификатор клиента, выданный клиенту в ходе процесса регистрации, описанного в разделе 2.2.
client_secret REQUIRED. The client secret. The client MAY omit the parameter if the client secret is an empty string.
client_secret ОБЯЗАТЕЛЕН. Секрет клиента. Клиент МОЖЕТ опустить параметр, если секрет клиента является пустой строкой.
Including the client credentials in the request-body using the two parameters is NOT RECOMMENDED and SHOULD be limited to clients unable to directly utilize the HTTP Basic authentication scheme (or other password-based HTTP authentication schemes). The parameters can only be transmitted in the request-body and MUST NOT be included in the request URI.
Включение учётных данных клиента в тело запроса с использованием двух параметров НЕ РЕКОМЕНДУЕТСЯ и СЛЕДУЕТ ограничивать клиентами, не имеющими возможности напрямую использовать схему аутентификации HTTP Basic (или другие схемы аутентификации HTTP на основе пароля). Параметры можно передавать только в теле запроса, и они НЕ ДОЛЖНЫ включаться в URI запроса.

The authorization server MUST require the use of TLS as described in Section 1.6 when sending requests using password authentication.
Сервер авторизации ДОЛЖЕН требовать использования TLS, как описано в разделе 1.6, при отправке запросов с использованием аутентификации по паролю.
Since this client authentication method involves a password, the authorization server MUST protect any endpoint utilizing it against brute force attacks.
Поскольку этот метод аутентификации клиента включает пароль, сервер авторизации ДОЛЖЕН защищать любую конечную точку, использующую его, от атак методом перебора.
2.3.2. Other Authentication Methods
2.3.2. Другие методы аутентификации
The authorization server MAY support any suitable HTTP authentication scheme matching its security requirements. When using other authentication methods, the authorization server MUST define a mapping between the client identifier (registration record) and authentication scheme.
Сервер авторизации МОЖЕТ поддерживать любую подходящую схему аутентификации HTTP, соответствующую его требованиям безопасности. При использовании других методов аутентификации сервер авторизации ДОЛЖЕН определить соответствие между идентификатором клиента (записью регистрации) и схемой аутентификации.
2.4. Unregistered Clients
2.4. Незарегистрированные клиенты
This specification does not exclude the use of unregistered clients. However, the use of such clients is beyond the scope of this specification and requires additional security analysis and review of its interoperability impact.
Настоящая спецификация не исключает использования незарегистрированных клиентов. Однако использование таких клиентов выходит за рамки настоящей спецификации и требует дополнительного анализа безопасности и рассмотрения его влияния на совместимость.
3. Protocol Endpoints
3. Конечные точки протокола
The authorization process utilizes two authorization server endpoints (HTTP resources):
В процессе авторизации используются две конечные точки сервера авторизации (ресурсы HTTP):
o Authorization endpoint - used by the client to obtain authorization from the resource owner via user-agent redirection.
o Конечная точка авторизации — используется клиентом для получения авторизации у владельца ресурса посредством перенаправления пользовательского агента.
o Token endpoint - used by the client to exchange an authorization grant for an access token, typically with client authentication.
o Конечная точка токена — используется клиентом для обмена гранта авторизации на токен доступа, как правило, с аутентификацией клиента.
As well as one client endpoint:
А также одна конечная точка клиента:
o Redirection endpoint - used by the authorization server to return responses containing authorization credentials to the client via the resource owner user-agent.
o Конечная точка перенаправления — используется сервером авторизации для возврата клиенту ответов, содержащих учётные данные авторизации, через пользовательский агент владельца ресурса.
Not every authorization grant type utilizes both endpoints. Extension grant types MAY define additional endpoints as needed.
Не каждый тип гранта авторизации использует обе конечные точки. Типы грантов-расширений МОГУТ определять дополнительные конечные точки по мере необходимости.
3.1. Authorization Endpoint
3.1. Конечная точка авторизации
The authorization endpoint is used to interact with the resource owner and obtain an authorization grant. The authorization server MUST first verify the identity of the resource owner. The way in which the authorization server authenticates the resource owner (e.g., username and password login, session cookies) is beyond the scope of this specification.
Конечная точка авторизации используется для взаимодействия с владельцем ресурса и получения гранта авторизации. Сервер авторизации ДОЛЖЕН сначала проверить идентичность владельца ресурса. Способ, которым сервер авторизации аутентифицирует владельца ресурса (например, вход по имени пользователя и паролю, сеансовые cookie-файлы), выходит за рамки настоящей спецификации.
The means through which the client obtains the location of the authorization endpoint are beyond the scope of this specification, but the location is typically provided in the service documentation.
Способы, которыми клиент получает местоположение конечной точки авторизации, выходят за рамки настоящей спецификации, но обычно это местоположение указывается в документации службы.
The endpoint URI MAY include an "application/x-www-form-urlencoded" formatted (per Appendix B) query component ([RFC3986] Section 3.4), which MUST be retained when adding additional query parameters. The endpoint URI MUST NOT include a fragment component.
URI конечной точки МОЖЕТ включать компонент запроса в формате «application/x-www-form-urlencoded» (согласно приложению B) ([RFC3986], раздел 3.4), который ДОЛЖЕН сохраняться при добавлении дополнительных параметров запроса. URI конечной точки НЕ ДОЛЖЕН включать компонент фрагмента.
Since requests to the authorization endpoint result in user authentication and the transmission of clear-text credentials (in the HTTP response), the authorization server MUST require the use of TLS as described in Section 1.6 when sending requests to the authorization endpoint.
Поскольку запросы к конечной точке авторизации приводят к аутентификации пользователя и передаче учётных данных в открытом виде (в ответе HTTP), сервер авторизации ДОЛЖЕН требовать использования TLS, как описано в разделе 1.6, при отправке запросов к конечной точке авторизации.
The authorization server MUST support the use of the HTTP "GET" method [RFC2616] for the authorization endpoint and MAY support the use of the "POST" method as well. Parameters sent without a value MUST be treated as if they were omitted from the request. The authorization server MUST ignore unrecognized request parameters. Request and response parameters MUST NOT be included more than once.
Сервер авторизации ДОЛЖЕН поддерживать использование метода HTTP «GET» [RFC2616] для конечной точки авторизации и МОЖЕТ также поддерживать метод «POST». Параметры, переданные без значения, ДОЛЖНЫ рассматриваться так, как если бы они были опущены в запросе. Сервер авторизации ДОЛЖЕН игнорировать нераспознанные параметры запроса. Параметры запроса и ответа НЕ ДОЛЖНЫ включаться более одного раза.
3.1.1. Response Type
3.1.1. Тип ответа
The authorization endpoint is used by the authorization code grant type and implicit grant type flows. The client informs the authorization server of the desired grant type using the following parameter:
Конечная точка авторизации используется в потоках типа гранта «код авторизации» и неявного типа гранта. Клиент сообщает серверу авторизации желаемый тип гранта с помощью следующего параметра:
response_type REQUIRED. The value MUST be one of "code" for requesting an authorization code as described by Section 4.1.1, "token" for requesting an access token (implicit grant) as described by Section 4.2.1, or a registered extension value as described by Section 8.4.
response_type ОБЯЗАТЕЛЕН. Значение ДОЛЖНО быть одним из: «code» для запроса кода авторизации, как описано в разделе 4.1.1; «token» для запроса токена доступа (неявный грант), как описано в разделе 4.2.1; либо зарегистрированного значения расширения, как описано в разделе 8.4.
Extension response types MAY contain a space-delimited (%x20) list of values, where the order of values does not matter (e.g., response type "a b" is the same as "b a"). The meaning of such composite response types is defined by their respective specifications.
Типы ответа-расширения МОГУТ содержать разделённый пробелами (%x20) список значений, в котором порядок значений не имеет значения (например, тип ответа «a b» совпадает с «b a»). Смысл таких составных типов ответа определяется соответствующими спецификациями.
If an authorization request is missing the "response_type" parameter, or if the response type is not understood, the authorization server MUST return an error response as described in Section 4.1.2.1.
Если в запросе авторизации отсутствует параметр «response_type» или тип ответа не понят, сервер авторизации ДОЛЖЕН вернуть ответ с ошибкой, как описано в разделе 4.1.2.1.
3.1.2. Redirection Endpoint
3.1.2. Конечная точка перенаправления
After completing its interaction with the resource owner, the authorization server directs the resource owner's user-agent back to the client. The authorization server redirects the user-agent to the client's redirection endpoint previously established with the authorization server during the client registration process or when making the authorization request.
После завершения взаимодействия с владельцем ресурса сервер авторизации направляет пользовательский агент владельца ресурса обратно клиенту. Сервер авторизации перенаправляет пользовательский агент на конечную точку перенаправления клиента, ранее установленную с сервером авторизации в ходе процесса регистрации клиента или при формировании запроса авторизации.
The redirection endpoint URI MUST be an absolute URI as defined by [RFC3986] Section 4.3. The endpoint URI MAY include an "application/x-www-form-urlencoded" formatted (per Appendix B) query component ([RFC3986] Section 3.4), which MUST be retained when adding additional query parameters. The endpoint URI MUST NOT include a fragment component.
URI конечной точки перенаправления ДОЛЖЕН быть абсолютным URI, как определено в [RFC3986], раздел 4.3. URI конечной точки МОЖЕТ включать компонент запроса в формате «application/x-www-form-urlencoded» (согласно приложению B) ([RFC3986], раздел 3.4), который ДОЛЖЕН сохраняться при добавлении дополнительных параметров запроса. URI конечной точки НЕ ДОЛЖЕН включать компонент фрагмента.
3.1.2.1. Endpoint Request Confidentiality
3.1.2.1. Конфиденциальность запросов к конечной точке
The redirection endpoint SHOULD require the use of TLS as described in Section 1.6 when the requested response type is "code" or "token", or when the redirection request will result in the transmission of sensitive credentials over an open network. This specification does not mandate the use of TLS because at the time of this writing, requiring clients to deploy TLS is a significant hurdle for many client developers. If TLS is not available, the authorization server SHOULD warn the resource owner about the insecure endpoint prior to redirection (e.g., display a message during the authorization request).
Конечная точка перенаправления ДОЛЖНА требовать использования TLS, как описано в разделе 1.6, когда запрашиваемый тип ответа — «code» или «token», либо когда запрос перенаправления приведёт к передаче конфиденциальных учётных данных по открытой сети. Настоящая спецификация не предписывает обязательное использование TLS, поскольку на момент написания этого документа требование развернуть TLS является существенным препятствием для многих разработчиков клиентов. Если TLS недоступен, серверу авторизации СЛЕДУЕТ предупредить владельца ресурса о небезопасной конечной точке до перенаправления (например, показать сообщение в ходе запроса авторизации).
Lack of transport-layer security can have a severe impact on the security of the client and the protected resources it is authorized to access. The use of transport-layer security is particularly critical when the authorization process is used as a form of delegated end-user authentication by the client (e.g., third-party sign-in service).
Отсутствие безопасности транспортного уровня может серьёзно повлиять на безопасность клиента и защищённых ресурсов, к которым он авторизован получать доступ. Использование безопасности транспортного уровня особенно критично, когда процесс авторизации используется клиентом как форма делегированной аутентификации конечного пользователя (например, служба входа третьей стороны).
3.1.2.2. Registration Requirements
3.1.2.2. Требования к регистрации
The authorization server MUST require the following clients to register their redirection endpoint:
Сервер авторизации ДОЛЖЕН требовать от следующих клиентов регистрации их конечной точки перенаправления:
o Public clients.
o Публичные клиенты.
o Confidential clients utilizing the implicit grant type.
o Конфиденциальные клиенты, использующие неявный тип гранта.
The authorization server SHOULD require all clients to register their redirection endpoint prior to utilizing the authorization endpoint.
Серверу авторизации СЛЕДУЕТ требовать от всех клиентов регистрации их конечной точки перенаправления до использования конечной точки авторизации.
The authorization server SHOULD require the client to provide the complete redirection URI (the client MAY use the "state" request parameter to achieve per-request customization). If requiring the registration of the complete redirection URI is not possible, the authorization server SHOULD require the registration of the URI scheme, authority, and path (allowing the client to dynamically vary only the query component of the redirection URI when requesting authorization).
Серверу авторизации СЛЕДУЕТ требовать от клиента предоставления полного URI перенаправления (клиент МОЖЕТ использовать параметр запроса «state» для настройки под каждый запрос). Если требование регистрации полного URI перенаправления невозможно, серверу авторизации СЛЕДУЕТ требовать регистрации схемы URI, полномочия и пути (позволяя клиенту динамически изменять только компонент запроса URI перенаправления при запросе авторизации).
The authorization server MAY allow the client to register multiple redirection endpoints.
Сервер авторизации МОЖЕТ разрешать клиенту регистрировать несколько конечных точек перенаправления.
Lack of a redirection URI registration requirement can enable an attacker to use the authorization endpoint as an open redirector as described in Section 10.15.
Отсутствие требования регистрации URI перенаправления может позволить злоумышленнику использовать конечную точку авторизации как открытый перенаправляющий узел, как описано в разделе 10.15.
3.1.2.3. Dynamic Configuration
3.1.2.3. Динамическая конфигурация
If multiple redirection URIs have been registered, if only part of the redirection URI has been registered, or if no redirection URI has been registered, the client MUST include a redirection URI with the authorization request using the "redirect_uri" request parameter.
Если зарегистрировано несколько URI перенаправления, если зарегистрирована только часть URI перенаправления или если не зарегистрировано ни одного URI перенаправления, клиент ДОЛЖЕН включать URI перенаправления в запрос авторизации с использованием параметра запроса «redirect_uri».
When a redirection URI is included in an authorization request, the authorization server MUST compare and match the value received against at least one of the registered redirection URIs (or URI components) as defined in [RFC3986] Section 6, if any redirection URIs were registered. If the client registration included the full redirection URI, the authorization server MUST compare the two URIs using simple string comparison as defined in [RFC3986] Section 6.2.1.
Когда URI перенаправления включён в запрос авторизации, сервер авторизации ДОЛЖЕН сравнить и сопоставить полученное значение хотя бы с одним из зарегистрированных URI перенаправления (или компонентов URI), как определено в [RFC3986], раздел 6, если какие-либо URI перенаправления были зарегистрированы. Если регистрация клиента включала полный URI перенаправления, сервер авторизации ДОЛЖЕН сравнивать два URI с использованием простого строкового сравнения, как определено в [RFC3986], раздел 6.2.1.
3.1.2.4. Invalid Endpoint
3.1.2.4. Недействительная конечная точка
If an authorization request fails validation due to a missing, invalid, or mismatching redirection URI, the authorization server SHOULD inform the resource owner of the error and MUST NOT automatically redirect the user-agent to the invalid redirection URI.
Если запрос авторизации не проходит проверку из-за отсутствующего, недействительного или несовпадающего URI перенаправления, серверу авторизации СЛЕДУЕТ сообщить владельцу ресурса об ошибке, и он НЕ ДОЛЖЕН автоматически перенаправлять пользовательский агент на недействительный URI перенаправления.
3.1.2.5. Endpoint Content
3.1.2.5. Содержимое конечной точки
The redirection request to the client's endpoint typically results in an HTML document response, processed by the user-agent. If the HTML response is served directly as the result of the redirection request, any script included in the HTML document will execute with full access to the redirection URI and the credentials it contains.
Запрос перенаправления на конечную точку клиента обычно приводит к ответу в виде HTML-документа, обрабатываемого пользовательским агентом. Если HTML-ответ отдаётся непосредственно в результате запроса перенаправления, любой сценарий, включённый в HTML-документ, будет выполняться с полным доступом к URI перенаправления и содержащимся в нём учётным данным.
The client SHOULD NOT include any third-party scripts (e.g., third- party analytics, social plug-ins, ad networks) in the redirection endpoint response. Instead, it SHOULD extract the credentials from the URI and redirect the user-agent again to another endpoint without exposing the credentials (in the URI or elsewhere). If third-party scripts are included, the client MUST ensure that its own scripts (used to extract and remove the credentials from the URI) will execute first.
Клиенту НЕ СЛЕДУЕТ включать какие-либо сторонние сценарии (например, стороннюю аналитику, социальные плагины, рекламные сети) в ответ конечной точки перенаправления. Вместо этого ему СЛЕДУЕТ извлечь учётные данные из URI и снова перенаправить пользовательский агент на другую конечную точку, не раскрывая учётные данные (в URI или иным образом). Если сторонние сценарии включены, клиент ДОЛЖЕН обеспечить, чтобы его собственные сценарии (используемые для извлечения и удаления учётных данных из URI) выполнялись первыми.
3.2. Token Endpoint
3.2. Конечная точка токена
The token endpoint is used by the client to obtain an access token by presenting its authorization grant or refresh token. The token endpoint is used with every authorization grant except for the implicit grant type (since an access token is issued directly). The means through which the client obtains the location of the token endpoint are beyond the scope of this specification, but the location is typically provided in the service documentation.
Конечная точка токена используется клиентом для получения токена доступа путём предъявления своего гранта авторизации или токена обновления. Конечная точка токена используется при каждом гранте авторизации, кроме неявного типа гранта (поскольку токен доступа выдаётся напрямую). Способы, которыми клиент получает местоположение конечной точки токена, выходят за рамки настоящей спецификации, но обычно это местоположение указывается в документации службы.
The endpoint URI MAY include an "application/x-www-form-urlencoded" formatted (per Appendix B) query component ([RFC3986] Section 3.4), which MUST be retained when adding additional query parameters. The endpoint URI MUST NOT include a fragment component.
URI конечной точки МОЖЕТ включать компонент запроса в формате «application/x-www-form-urlencoded» (согласно приложению B) ([RFC3986], раздел 3.4), который ДОЛЖЕН сохраняться при добавлении дополнительных параметров запроса. URI конечной точки НЕ ДОЛЖЕН включать компонент фрагмента.
Since requests to the token endpoint result in the transmission of clear-text credentials (in the HTTP request and response), the authorization server MUST require the use of TLS as described in Section 1.6 when sending requests to the token endpoint.
Поскольку запросы к конечной точке токена приводят к передаче учётных данных в открытом виде (в запросе и ответе HTTP), сервер авторизации ДОЛЖЕН требовать использования TLS, как описано в разделе 1.6, при отправке запросов к конечной точке токена.
The client MUST use the HTTP "POST" method when making access token requests.
Клиент ДОЛЖЕН использовать метод HTTP «POST» при выполнении запросов токена доступа.
Parameters sent without a value MUST be treated as if they were omitted from the request. The authorization server MUST ignore unrecognized request parameters. Request and response parameters MUST NOT be included more than once.
Параметры, переданные без значения, ДОЛЖНЫ рассматриваться так, как если бы они были опущены в запросе. Сервер авторизации ДОЛЖЕН игнорировать нераспознанные параметры запроса. Параметры запроса и ответа НЕ ДОЛЖНЫ включаться более одного раза.
3.2.1. Client Authentication
3.2.1. Аутентификация клиента
Confidential clients or other clients issued client credentials MUST authenticate with the authorization server as described in Section 2.3 when making requests to the token endpoint. Client authentication is used for:
Конфиденциальные клиенты или иные клиенты, которым выданы учётные данные клиента, ДОЛЖНЫ аутентифицироваться на сервере авторизации, как описано в разделе 2.3, при выполнении запросов к конечной точке токена. Аутентификация клиента используется для:
o Enforcing the binding of refresh tokens and authorization codes to the client they were issued to. Client authentication is critical when an authorization code is transmitted to the redirection endpoint over an insecure channel or when the redirection URI has not been registered in full.
o Обеспечения привязки токенов обновления и кодов авторизации к клиенту, которому они были выданы. Аутентификация клиента критична, когда код авторизации передаётся на конечную точку перенаправления по незащищённому каналу или когда URI перенаправления не был зарегистрирован полностью.
o Recovering from a compromised client by disabling the client or changing its credentials, thus preventing an attacker from abusing stolen refresh tokens. Changing a single set of client credentials is significantly faster than revoking an entire set of refresh tokens.
o Восстановления после компрометации клиента путём отключения клиента или изменения его учётных данных, что предотвращает злоупотребление украденными токенами обновления злоумышленником. Изменение одного набора учётных данных клиента значительно быстрее, чем отзыв целого набора токенов обновления.
o Implementing authentication management best practices, which require periodic credential rotation. Rotation of an entire set of refresh tokens can be challenging, while rotation of a single set of client credentials is significantly easier.
o Реализации передовых методов управления аутентификацией, которые требуют периодической смены учётных данных. Смена целого набора токенов обновления может быть сложной задачей, тогда как смена одного набора учётных данных клиента значительно проще.
A client MAY use the "client_id" request parameter to identify itself when sending requests to the token endpoint. In the "authorization_code" "grant_type" request to the token endpoint, an unauthenticated client MUST send its "client_id" to prevent itself from inadvertently accepting a code intended for a client with a different "client_id". This protects the client from substitution of the authentication code. (It provides no additional security for the protected resource.)
Клиент МОЖЕТ использовать параметр запроса «client_id» для идентификации себя при отправке запросов к конечной точке токена. В запросе «grant_type» со значением «authorization_code» к конечной точке токена неаутентифицированный клиент ДОЛЖЕН отправить свой «client_id», чтобы случайно не принять код, предназначенный для клиента с другим «client_id». Это защищает клиента от подмены кода аутентификации. (Для защищённого ресурса это не даёт дополнительной безопасности.)
3.3. Access Token Scope
3.3. Область действия токена доступа
The authorization and token endpoints allow the client to specify the scope of the access request using the "scope" request parameter. In turn, the authorization server uses the "scope" response parameter to inform the client of the scope of the access token issued.
Конечные точки авторизации и токена позволяют клиенту указать область действия запроса доступа с помощью параметра запроса «scope». В свою очередь, сервер авторизации использует параметр ответа «scope», чтобы сообщить клиенту область действия выданного токена доступа.
The value of the scope parameter is expressed as a list of space- delimited, case-sensitive strings. The strings are defined by the authorization server. If the value contains multiple space-delimited strings, their order does not matter, and each string adds an additional access range to the requested scope.
Значение параметра scope выражается как список разделённых пробелами строк, чувствительных к регистру. Строки определяются сервером авторизации. Если значение содержит несколько разделённых пробелами строк, их порядок не имеет значения, и каждая строка добавляет дополнительный диапазон доступа к запрашиваемой области действия.
scope = scope-token *( SP scope-token ) scope-token = 1*( %x21 / %x23-5B / %x5D-7E )
scope = scope-token *( SP scope-token ) scope-token = 1*( %x21 / %x23-5B / %x5D-7E )
The authorization server MAY fully or partially ignore the scope requested by the client, based on the authorization server policy or the resource owner's instructions. If the issued access token scope is different from the one requested by the client, the authorization server MUST include the "scope" response parameter to inform the client of the actual scope granted.
Сервер авторизации МОЖЕТ полностью или частично игнорировать область действия, запрошенную клиентом, исходя из политики сервера авторизации или указаний владельца ресурса. Если выданная область действия токена доступа отличается от запрошенной клиентом, сервер авторизации ДОЛЖЕН включить параметр ответа «scope», чтобы сообщить клиенту фактически предоставленную область действия.
If the client omits the scope parameter when requesting authorization, the authorization server MUST either process the request using a pre-defined default value or fail the request indicating an invalid scope. The authorization server SHOULD document its scope requirements and default value (if defined).
Если клиент опускает параметр scope при запросе авторизации, сервер авторизации ДОЛЖЕН либо обработать запрос с использованием предопределённого значения по умолчанию, либо отклонить запрос, указав недействительную область действия. Серверу авторизации СЛЕДУЕТ документировать свои требования к области действия и значение по умолчанию (если оно определено).
4. Obtaining Authorization
4. Получение авторизации
To request an access token, the client obtains authorization from the resource owner. The authorization is expressed in the form of an authorization grant, which the client uses to request the access token. OAuth defines four grant types: authorization code, implicit, resource owner password credentials, and client credentials. It also provides an extension mechanism for defining additional grant types.
Чтобы запросить токен доступа, клиент получает авторизацию у владельца ресурса. Авторизация выражается в форме гранта авторизации, который клиент использует для запроса токена доступа. OAuth определяет четыре типа грантов: код авторизации, неявный, учётные данные пароля владельца ресурса и учётные данные клиента. Он также предоставляет механизм расширения для определения дополнительных типов грантов.
4.1. Authorization Code Grant
4.1. Грант кода авторизации

Since this is a redirection-based flow, the client must be capable of interacting with the resource owner's user-agent (typically a web browser) and capable of receiving incoming requests (via redirection) from the authorization server.
Тип гранта «код авторизации» используется для получения как токенов доступа, так и токенов обновления и оптимизирован для конфиденциальных клиентов. 4.2. Implicit Grant
4.2. Неявный грант
The implicit grant type is used to obtain access tokens (it does not support the issuance of refresh tokens) and is optimized for public clients known to operate a particular redirection URI. These clients are typically implemented in a browser using a scripting language such as JavaScript.
Неявный тип гранта используется для получения токенов доступа (он не поддерживает выдачу токенов обновления) и оптимизирован для публичных клиентов, о которых известно, что они используют определённый URI перенаправления. Такие клиенты обычно реализуются в браузере с использованием языка сценариев, такого как JavaScript.
Since this is a redirection-based flow, the client must be capable of interacting with the resource owner's user-agent (typically a web browser) and capable of receiving incoming requests (via redirection) from the authorization server.
Поскольку это поток на основе перенаправления, клиент должен быть способен взаимодействовать с пользовательским агентом владельца ресурса (обычно веб-браузером) и принимать входящие запросы (через перенаправление) от сервера авторизации.
Unlike the authorization code grant type, in which the client makes separate requests for authorization and for an access token, the client receives the access token as the result of the authorization request.
В отличие от типа гранта «код авторизации», в котором клиент выполняет отдельные запросы для авторизации и для токена доступа, клиент получает токен доступа как результат запроса авторизации.
The implicit grant type does not include client authentication, and relies on the presence of the resource owner and the registration of the redirection URI. Because the access token is encoded into the redirection URI, it may be exposed to the resource owner and other applications residing on the same device.
Неявный тип гранта не включает аутентификацию клиента и полагается на присутствие владельца ресурса и регистрацию URI перенаправления. Поскольку токен доступа кодируется в URI перенаправления, он может быть раскрыт владельцу ресурса и другим приложениям, находящимся на том же устройстве.

7. Accessing Protected Resources
7. Доступ к защищённым ресурсам
The client accesses protected resources by presenting the access token to the resource server. The resource server MUST validate the access token and ensure that it has not expired and that its scope covers the requested resource. The methods used by the resource server to validate the access token (as well as any error responses) are beyond the scope of this specification but generally involve an interaction or coordination between the resource server and the authorization server.
Клиент получает доступ к защищённым ресурсам, предъявляя токен доступа серверу ресурсов. Методы, используемые сервером ресурсов для проверки токена доступа (а также любые ответы с ошибкой), выходят за рамки настоящей спецификации, но обычно предполагают взаимодействие или согласование между сервером ресурсов и сервером авторизации.
The method in which the client utilizes the access token to authenticate with the resource server depends on the type of access token issued by the authorization server. Typically, it involves using the HTTP "Authorization" request header field [RFC2617] with an authentication scheme defined by the specification of the access token type used, such as [RFC6750].
Метод, которым клиент использует токен доступа для аутентификации на сервере ресурсов, зависит от типа токена доступа, выданного сервером авторизации. Обычно он предполагает использование поля заголовка запроса HTTP «Authorization» [RFC2617] со схемой аутентификации, определённой спецификацией используемого типа токена доступа, например [RFC6750].
7.1. Access Token Types
7.1. Типы токенов доступа
The access token type provides the client with the information required to successfully utilize the access token to make a protected resource request (along with type-specific attributes). The client MUST NOT use an access token if it does not understand the token type.
Тип токена доступа предоставляет клиенту сведения, необходимые для успешного использования токена доступа при выполнении запроса защищённого ресурса (вместе с атрибутами, специфичными для типа). Клиент НЕ ДОЛЖЕН использовать токен доступа, если он не понимает тип токена.
For example, the "bearer" token type defined in [RFC6750] is utilized by simply including the access token string in the request:
Например, тип токена «bearer», определённый в [RFC6750], используется путём простого включения строки токена доступа в запрос:
GET /resource/1 HTTP/1.1 Host: example.com Authorization: Bearer mF_9.B5f-4.1JqM
GET /resource/1 HTTP/1.1 Host: example.com Authorization: Bearer mF_9.B5f-4.1JqM
while the "mac" token type defined in [OAuth-HTTP-MAC] is utilized by issuing a Message Authentication Code (MAC) key together with the access token that is used to sign certain components of the HTTP requests:
тогда как тип токена «mac», определённый в [OAuth-HTTP-MAC], используется путём выдачи ключа Message Authentication Code (MAC) вместе с токеном доступа, который применяется для подписи определённых компонентов запросов HTTP:
GET /resource/1 HTTP/1.1 Host: example.com Authorization: MAC id="h480djs93hd8",
GET /resource/1 HTTP/1.1 Host: example.com Authorization: MAC id="h480djs93hd8",
nonce="274312:dj83hs9s", mac="kDZvddkndxvhGRXZhvuDjEWhGeE="
nonce="274312:dj83hs9s", mac="kDZvddkndxvhGRXZhvuDjEWhGeE="
The above examples are provided for illustration purposes only. Developers are advised to consult the [RFC6750] and [OAuth-HTTP-MAC] specifications before use.
Приведённые выше примеры даны исключительно для иллюстрации. Разработчикам рекомендуется ознакомиться со спецификациями [RFC6750] и [OAuth-HTTP-MAC] перед использованием.
Each access token type definition specifies the additional attributes (if any) sent to the client together with the "access_token" response parameter. It also defines the HTTP authentication method used to include the access token when making a protected resource request.
Каждое определение типа токена доступа задаёт дополнительные атрибуты (если они есть), отправляемые клиенту вместе с параметром ответа «access_token». Оно также определяет метод аутентификации HTTP, используемый для включения токена доступа при выполнении запроса защищённого ресурса.
7.2. Error Response
7.2. Ответ с ошибкой
If a resource access request fails, the resource server SHOULD inform the client of the error. While the specifics of such error responses are beyond the scope of this specification, this document establishes a common registry in Section 11.4 for error values to be shared among OAuth token authentication schemes.
Если запрос доступа к ресурсу не удаётся, серверу ресурсов СЛЕДУЕТ сообщить клиенту об ошибке. Хотя особенности таких ответов с ошибкой выходят за рамки настоящей спецификации, настоящий документ учреждает в разделе 11.4 общий реестр значений ошибок, которые должны использоваться совместно схемами аутентификации токенов OAuth.
New authentication schemes designed primarily for OAuth token authentication SHOULD define a mechanism for providing an error status code to the client, in which the error values allowed are registered in the error registry established by this specification. Such schemes MAY limit the set of valid error codes to a subset of the registered values. If the error code is returned using a named parameter, the parameter name SHOULD be "error".
Новые схемы аутентификации, разработанные прежде всего для аутентификации токенов OAuth, СЛЕДУЕТ определять механизм предоставления клиенту кода состояния ошибки, при котором допустимые значения ошибок регистрируются в реестре ошибок, учреждённом настоящей спецификацией. Такие схемы МОГУТ ограничивать набор допустимых кодов ошибок подмножеством зарегистрированных значений. Если код ошибки возвращается с использованием именованного параметра, именем параметра СЛЕДУЕТ выбирать «error».
Other schemes capable of being used for OAuth token authentication, but not primarily designed for that purpose, MAY bind their error values to the registry in the same manner.
Другие схемы, которые могут использоваться для аутентификации токенов OAuth, но не разработаны для этой цели в первую очередь, МОГУТ привязывать свои значения ошибок к реестру таким же образом.
New authentication schemes MAY choose to also specify the use of the "error_description" and "error_uri" parameters to return error information in a manner parallel to their usage in this specification.
Новые схемы аутентификации МОГУТ также предусматривать использование параметров «error_description» и «error_uri» для возврата сведений об ошибке аналогично их использованию в настоящей спецификации.
8. Extensibility
8. Расширяемость
8.1. Defining Access Token Types
8.1. Определение типов токенов доступа
Access token types can be defined in one of two ways: registered in the Access Token Types registry (following the procedures in Section 11.1), or by using a unique absolute URI as its name.
Типы токенов доступа можно определять одним из двух способов: регистрацией в реестре Access Token Types (следуя процедурам раздела 11.1) или использованием уникального абсолютного URI в качестве его имени.
Types utilizing a URI name SHOULD be limited to vendor-specific implementations that are not commonly applicable, and are specific to the implementation details of the resource server where they are used.
Типы, использующие имя в виде URI, СЛЕДУЕТ ограничивать реализациями, специфичными для поставщика, которые обычно неприменимы и зависят от деталей реализации сервера ресурсов, где они используются.
All other types MUST be registered. Type names MUST conform to the type-name ABNF. If the type definition includes a new HTTP authentication scheme, the type name SHOULD be identical to the HTTP authentication scheme name (as defined by [RFC2617]). The token type "example" is reserved for use in examples.
Все остальные типы ДОЛЖНЫ быть зарегистрированы. Имена типов ДОЛЖНЫ соответствовать ABNF type-name. Если определение типа включает новую схему аутентификации HTTP, имя типа СЛЕДУЕТ делать идентичным имени схемы аутентификации HTTP (как определено в [RFC2617]). Тип токена «example» зарезервирован для использования в примерах.
type-name = 1*name-char name-char = "-" / "." / "_" / DIGIT / ALPHA
type-name = 1*name-char name-char = "-" / "." / "_" / DIGIT / ALPHA
8.2. Defining New Endpoint Parameters
8.2. Определение новых параметров конечных точек
New request or response parameters for use with the authorization endpoint or the token endpoint are defined and registered in the OAuth Parameters registry following the procedure in Section 11.2.
Новые параметры запроса или ответа для использования с конечной точкой авторизации или конечной точкой токена определяются и регистрируются в реестре OAuth Parameters согласно процедуре раздела 11.2.
Parameter names MUST conform to the param-name ABNF, and parameter values syntax MUST be well-defined (e.g., using ABNF, or a reference to the syntax of an existing parameter).
Имена параметров ДОЛЖНЫ соответствовать ABNF param-name, а синтаксис значений параметров ДОЛЖЕН быть чётко определён (например, с использованием ABNF или ссылки на синтаксис существующего параметра).
param-name = 1*name-char name-char = "-" / "." / "_" / DIGIT / ALPHA
param-name = 1*name-char name-char = "-" / "." / "_" / DIGIT / ALPHA
Unregistered vendor-specific parameter extensions that are not commonly applicable and that are specific to the implementation details of the authorization server where they are used SHOULD utilize a vendor-specific prefix that is not likely to conflict with other registered values (e.g., begin with 'companyname_').
Незарегистрированные расширения параметров, специфичные для поставщика, которые обычно неприменимы и зависят от деталей реализации сервера авторизации, где они используются, СЛЕДУЕТ снабжать префиксом, специфичным для поставщика, который вряд ли будет конфликтовать с другими зарегистрированными значениями (например, начинающимся с «companyname_»).
8.3. Defining New Authorization Grant Types
8.3. Определение новых типов грантов авторизации
New authorization grant types can be defined by assigning them a unique absolute URI for use with the "grant_type" parameter. If the extension grant type requires additional token endpoint parameters, they MUST be registered in the OAuth Parameters registry as described by Section 11.2.
Новые типы грантов авторизации можно определять, присваивая им уникальный абсолютный URI для использования с параметром «grant_type». Если тип гранта-расширения требует дополнительных параметров конечной точки токена, они ДОЛЖНЫ быть зарегистрированы в реестре OAuth Parameters, как описано в разделе 11.2.
8.4. Defining New Authorization Endpoint Response Types
8.4. Определение новых типов ответа конечной точки авторизации
New response types for use with the authorization endpoint are defined and registered in the Authorization Endpoint Response Types registry following the procedure in Section 11.3. Response type names MUST conform to the response-type ABNF.
Новые типы ответа для использования с конечной точкой авторизации определяются и регистрируются в реестре Authorization Endpoint Response Types согласно процедуре раздела 11.3. Имена типов ответа ДОЛЖНЫ соответствовать ABNF response-type.
response-type = response-name *( SP response-name ) response-name = 1*response-char response-char = "_" / DIGIT / ALPHA
response-type = response-name *( SP response-name ) response-name = 1*response-char response-char = "_" / DIGIT / ALPHA
If a response type contains one or more space characters (%x20), it is compared as a space-delimited list of values in which the order of values does not matter. Only one order of values can be registered, which covers all other arrangements of the same set of values.
Если тип ответа содержит один или несколько символов пробела (%x20), он сравнивается как разделённый пробелами список значений, в котором порядок значений не имеет значения. Может быть зарегистрирован только один порядок значений, который охватывает все остальные расположения того же набора значений.
For example, the response type "token code" is left undefined by this specification. However, an extension can define and register the "token code" response type. Once registered, the same combination cannot be registered as "code token", but both values can be used to denote the same response type.
Например, тип ответа «token code» настоящей спецификацией не определён. Однако расширение может определить и зарегистрировать тип ответа «token code». После регистрации та же комбинация не может быть зарегистрирована как «code token», но оба значения могут использоваться для обозначения одного и того же типа ответа.
8.5. Defining Additional Error Codes
8.5. Определение дополнительных кодов ошибок
In cases where protocol extensions (i.e., access token types, extension parameters, or extension grant types) require additional error codes to be used with the authorization code grant error response (Section 4.1.2.1), the implicit grant error response (Section 4.2.2.1), the token error response (Section 5.2), or the resource access error response (Section 7.2), such error codes MAY be defined. Extension error codes MUST be registered (following the procedures in Section 11.4) if the extension they are used in conjunction with is a registered access token type, a registered endpoint parameter, or an extension grant type. Error codes used with unregistered extensions MAY be registered.
В случаях когда расширения протокола (то есть типы токенов доступа, параметры-расширения или типы грантов-расширений) требуют дополнительных кодов ошибок для использования с ответом с ошибкой гранта кода авторизации (раздел 4.1.2.1), ответом с ошибкой неявного гранта (раздел 4.2.2.1), ответом с ошибкой токена (раздел 5.2) или ответом с ошибкой доступа к ресурсу (раздел 7.2), такие коды ошибок МОГУТ быть определены. Коды ошибок-расширений ДОЛЖНЫ быть зарегистрированы (следуя процедурам раздела 11.4), если расширение, вместе с которым они используются, является зарегистрированным типом токена доступа, зарегистрированным параметром конечной точки или типом гранта-расширения. Коды ошибок, используемые с незарегистрированными расширениями, МОГУТ быть зарегистрированы.
Error codes MUST conform to the error ABNF and SHOULD be prefixed by an identifying name when possible. For example, an error identifying an invalid value set to the extension parameter "example" SHOULD be named "example_invalid".
Коды ошибок ДОЛЖНЫ соответствовать ABNF error и, когда это возможно, СЛЕДУЕТ снабжать их идентифицирующим префиксом. Например, ошибку, идентифицирующую недействительное значение, установленное для параметра-расширения «example», СЛЕДУЕТ именовать «example_invalid».
error = 1*error-char error-char = %x20-21 / %x23-5B / %x5D-7E
error = 1*error-char error-char = %x20-21 / %x23-5B / %x5D-7E
9. Native Applications
9. Нативные приложения
Native applications are clients installed and executed on the device used by the resource owner (i.e., desktop application, native mobile application). Native applications require special consideration related to security, platform capabilities, and overall end-user experience.
Нативные приложения — это клиенты, установленные и выполняемые на устройстве, используемом владельцем ресурса (то есть настольное приложение, нативное мобильное приложение). Нативные приложения требуют особого рассмотрения в отношении безопасности, возможностей платформы и общего удобства для конечного пользователя.
The authorization endpoint requires interaction between the client and the resource owner's user-agent. Native applications can invoke an external user-agent or embed a user-agent within the application. For example:
Конечная точка авторизации требует взаимодействия между клиентом и пользовательским агентом владельца ресурса. Нативные приложения могут вызывать внешний пользовательский агент или встраивать пользовательский агент в приложение. Например:
o External user-agent - the native application can capture the response from the authorization server using a redirection URI with a scheme registered with the operating system to invoke the client as the handler, manual copy-and-paste of the credentials, running a local web server, installing a user-agent extension, or by providing a redirection URI identifying a server-hosted resource under the client's control, which in turn makes the response available to the native application.
o Внешний пользовательский агент — нативное приложение может получать ответ от сервера авторизации с использованием URI перенаправления со схемой, зарегистрированной в операционной системе для вызова клиента в качестве обработчика, ручного копирования и вставки учётных данных, запуска локального веб-сервера, установки расширения пользовательского агента либо предоставления URI перенаправления, идентифицирующего размещённый на сервере ресурс под контролем клиента, который, в свою очередь, делает ответ доступным нативному приложению.
o Embedded user-agent - the native application obtains the response by directly communicating with the embedded user-agent by monitoring state changes emitted during the resource load, or accessing the user-agent's cookies storage.
o Встроенный пользовательский агент — нативное приложение получает ответ путём прямого взаимодействия со встроенным пользовательским агентом, отслеживая изменения состояния, выдаваемые при загрузке ресурса, или получая доступ к хранилищу cookie-файлов пользовательского агента.
When choosing between an external or embedded user-agent, developers should consider the following:
При выборе между внешним и встроенным пользовательским агентом разработчикам следует учитывать следующее:
o An external user-agent may improve completion rate, as the resource owner may already have an active session with the authorization server, removing the need to re-authenticate. It provides a familiar end-user experience and functionality. The resource owner may also rely on user-agent features or extensions to assist with authentication (e.g., password manager, 2-factor device reader).
o Внешний пользовательский агент может повысить долю завершения, поскольку у владельца ресурса может уже быть активный сеанс с сервером авторизации, что устраняет необходимость повторной аутентификации. Он обеспечивает привычное для конечного пользователя поведение и функциональность. Владелец ресурса также может полагаться на возможности или расширения пользовательского агента для содействия аутентификации (например, менеджер паролей, считыватель двухфакторных устройств).
o An embedded user-agent may offer improved usability, as it removes the need to switch context and open new windows.
o Встроенный пользовательский агент может обеспечить лучшую удобность, поскольку устраняет необходимость переключать контекст и открывать новые окна.
o An embedded user-agent poses a security challenge because resource owners are authenticating in an unidentified window without access to the visual protections found in most external user-agents. An embedded user-agent educates end-users to trust unidentified requests for authentication (making phishing attacks easier to execute).
o Встроенный пользовательский агент создаёт проблему безопасности, поскольку владельцы ресурсов аутентифицируются в неопознанном окне без доступа к визуальным средствам защиты, имеющимся в большинстве внешних пользовательских агентов. Встроенный пользовательский агент приучает конечных пользователей доверять неопознанным запросам аутентификации (что облегчает проведение фишинговых атак).
When choosing between the implicit grant type and the authorization code grant type, the following should be considered:
При выборе между неявным типом гранта и типом гранта «код авторизации» следует принимать во внимание следующее:
o Native applications that use the authorization code grant type SHOULD do so without using client credentials, due to the native application's inability to keep client credentials confidential.
o Нативным приложениям, использующим тип гранта «код авторизации», СЛЕДУЕТ делать это без использования учётных данных клиента, поскольку нативное приложение не способно сохранять конфиденциальность учётных данных клиента.
o When using the implicit grant type flow, a refresh token is not returned, which requires repeating the authorization process once the access token expires.
o При использовании потока неявного типа гранта токен обновления не возвращается, что требует повторения процесса авторизации после истечения токена доступа.
10. Security Considerations
10. Соображения безопасности
As a flexible and extensible framework, OAuth's security considerations depend on many factors. The following sections provide implementers with security guidelines focused on the three client profiles described in Section 2.1: web application, user-agent-based application, and native application.
Будучи гибкой и расширяемой основой, безопасность OAuth зависит от многих факторов. В следующих разделах предоставляются рекомендации по безопасности для разработчиков, ориентированные на три профиля клиентов, описанных в разделе 2.1: веб-приложение, приложение на основе пользовательского агента и нативное приложение.
A comprehensive OAuth security model and analysis, as well as background for the protocol design, is provided by [OAuth-THREATMODEL].
Всеобъемлющая модель безопасности и анализ OAuth, а также обоснование проекта протокола предоставлены в [OAuth-THREATMODEL].
10.1. Client Authentication
10.1. Аутентификация клиента
The authorization server establishes client credentials with web application clients for the purpose of client authentication. The authorization server is encouraged to consider stronger client authentication means than a client password. Web application clients MUST ensure confidentiality of client passwords and other client credentials. The authorization server MUST NOT issue client passwords or other client credentials to native application or user-agent-based application clients for the purpose of client authentication. The authorization server MAY issue a client password or other credentials for a specific installation of a native application client on a specific device.
Сервер авторизации устанавливает учётные данные клиента с клиентами-веб-приложениями для целей аутентификации клиента. Серверу авторизации рекомендуется рассмотреть более сильные средства аутентификации клиента, нежели пароль клиента. Клиенты-веб-приложения ДОЛЖНЫ обеспечивать конфиденциальность паролей клиента и других учётных данных клиента. Сервер авторизации НЕ ДОЛЖЕН выдавать пароли клиента или другие учётные данные клиента клиентам-нативным приложениям или клиентам-приложениям на основе пользовательского агента для целей аутентификации клиента. Сервер авторизации МОЖЕТ выдать пароль клиента или другие учётные данные для конкретной установки клиента-нативного приложения на конкретном устройстве.
When client authentication is not possible, the authorization server SHOULD employ other means to validate the client's identity -- for example, by requiring the registration of the client redirection URI or enlisting the resource owner to confirm identity. A valid redirection URI is not sufficient to verify the client's identity when asking for resource owner authorization but can be used to prevent delivering credentials to a counterfeit client after obtaining resource owner authorization.
Когда аутентификация клиента невозможна, серверу авторизации СЛЕДУЕТ применять иные средства проверки идентичности клиента — например, требуя регистрации URI перенаправления клиента или привлекая владельца ресурса для подтверждения идентичности. Действительный URI перенаправления недостаточен для проверки идентичности клиента при запросе авторизации владельца ресурса, но может использоваться для предотвращения доставки учётных данных поддельным клиентом после получения авторизации владельца ресурса.
The authorization server must consider the security implications of interacting with unauthenticated clients and take measures to limit the potential exposure of other credentials (e.g., refresh tokens) issued to such clients.
Сервер авторизации должен учитывать последствия для безопасности взаимодействия с неаутентифицированными клиентами и принимать меры для ограничения потенциального раскрытия других учётных данных (например, токенов обновления), выдаваемых таким клиентам.
10.2. Client Impersonation
10.2. Подмена клиента
A malicious client can impersonate another client and obtain access to protected resources if the impersonated client fails to, or is unable to, keep its client credentials confidential.
Вредоносный клиент может выдать себя за другой клиент и получить доступ к защищённым ресурсам, если клиент, за которого он себя выдаёт, не обеспечивает или не способен обеспечить конфиденциальность своих учётных данных клиента.
The authorization server MUST authenticate the client whenever possible. If the authorization server cannot authenticate the client due to the client's nature, the authorization server MUST require the registration of any redirection URI used for receiving authorization responses and SHOULD utilize other means to protect resource owners from such potentially malicious clients. For example, the authorization server can engage the resource owner to assist in identifying the client and its origin.
Сервер авторизации ДОЛЖЕН аутентифицировать клиента, когда это возможно. Если сервер авторизации не может аутентифицировать клиента в силу природы клиента, он ДОЛЖЕН требовать регистрации любого URI перенаправления, используемого для получения ответов авторизации, и СЛЕДУЕТ применять иные средства защиты владельцев ресурсов от таких потенциально вредоносных клиентов. Например, сервер авторизации может привлечь владельца ресурса для содействия в идентификации клиента и его источника.
The authorization server SHOULD enforce explicit resource owner authentication and provide the resource owner with information about the client and the requested authorization scope and lifetime. It is up to the resource owner to review the information in the context of the current client and to authorize or deny the request.
Серверу авторизации СЛЕДУЕТ обеспечивать явную аутентификацию владельца ресурса и предоставлять владельцу ресурса сведения о клиенте, запрошенной области действия авторизации и сроке её действия. Владелец ресурса должен сам рассмотреть эти сведения в контексте текущего клиента и авторизовать или отклонить запрос.
The authorization server SHOULD NOT process repeated authorization requests automatically (without active resource owner interaction) without authenticating the client or relying on other measures to ensure that the repeated request comes from the original client and not an impersonator.
Серверу авторизации НЕ СЛЕДУЕТ обрабатывать повторные запросы авторизации автоматически (без активного взаимодействия с владельцем ресурса), если он не аутентифицирует клиента и не полагается на иные меры, обеспечивающие, что повторный запрос исходит от первоначального клиента, а не от подменяющего его лица.
10.3. Access Tokens
10.3. Токены доступа
Access token credentials (as well as any confidential access token attributes) MUST be kept confidential in transit and storage, and only shared among the authorization server, the resource servers the access token is valid for, and the client to whom the access token is issued. Access token credentials MUST only be transmitted using TLS as described in Section 1.6 with server authentication as defined by [RFC2818].
Учётные данные токена доступа (а также любые конфиденциальные атрибуты токена доступа) ДОЛЖНЫ сохраняться конфиденциальными при передаче и хранении и разделяться только между сервером авторизации, серверами ресурсов, для которых токен доступа действителен, и клиентом, которому токен доступа выдан. Учётные данные токена доступа ДОЛЖНЫ передаваться только с использованием TLS, как описано в разделе 1.6, с аутентификацией сервера, как определено в [RFC2818].
When using the implicit grant type, the access token is transmitted in the URI fragment, which can expose it to unauthorized parties.
При использовании неявного типа гранта токен доступа передаётся в компоненте фрагмента URI, что может раскрыть его неавторизованным сторонам.
The authorization server MUST ensure that access tokens cannot be generated, modified, or guessed to produce valid access tokens by unauthorized parties.
Сервер авторизации ДОЛЖЕН обеспечивать, чтобы неавторизованные стороны не могли сгенерировать, изменить или угадать токены доступа так, чтобы получить действительные токены доступа.
The client SHOULD request access tokens with the minimal scope necessary. The authorization server SHOULD take the client identity into account when choosing how to honor the requested scope and MAY issue an access token with less rights than requested.
Клиенту СЛЕДУЕТ запрашивать токены доступа с минимально необходимой областью действия. Серверу авторизации СЛЕДУЕТ учитывать идентичность клиента при выборе того, как выполнять запрошенную область действия, и он МОЖЕТ выдать токен доступа с меньшими правами, чем запрошено.
This specification does not provide any methods for the resource server to ensure that an access token presented to it by a given client was issued to that client by the authorization server.
Настоящая спецификация не предоставляет никаких методов, позволяющих серверу ресурсов убедиться, что токен доступа, предъявленный ему данным клиентом, был выдан этому клиенту сервером авторизации.
10.4. Refresh Tokens
10.4. Токены обновления
Authorization servers MAY issue refresh tokens to web application clients and native application clients.
Серверы авторизации МОГУТ выдавать токены обновления клиентам-веб-приложениям и клиентам-нативным приложениям.
Refresh tokens MUST be kept confidential in transit and storage, and shared only among the authorization server and the client to whom the refresh tokens were issued. The authorization server MUST maintain the binding between a refresh token and the client to whom it was issued. Refresh tokens MUST only be transmitted using TLS as described in Section 1.6 with server authentication as defined by [RFC2818].
Токены обновления ДОЛЖНЫ сохраняться конфиденциальными при передаче и хранении и разделяться только между сервером авторизации и клиентом, которому токены обновления были выданы. Сервер авторизации ДОЛЖЕН поддерживать привязку между токеном обновления и клиентом, которому он был выдан. Токены обновления ДОЛЖНЫ передаваться только с использованием TLS, как описано в разделе 1.6, с аутентификацией сервера, как определено в [RFC2818].
The authorization server MUST verify the binding between the refresh token and client identity whenever the client identity can be authenticated. When client authentication is not possible, the authorization server SHOULD deploy other means to detect refresh token abuse.
Сервер авторизации ДОЛЖЕН проверять привязку между токеном обновления и идентичностью клиента всякий раз, когда идентичность клиента можно аутентифицировать. Когда аутентификация клиента невозможна, серверу авторизации СЛЕДУЕТ применять иные средства обнаружения злоупотребления токеном обновления.
For example, the authorization server could employ refresh token rotation in which a new refresh token is issued with every access token refresh response. The previous refresh token is invalidated but retained by the authorization server. If a refresh token is compromised and subsequently used by both the attacker and the legitimate client, one of them will present an invalidated refresh token, which will inform the authorization server of the breach.
Например, сервер авторизации мог бы применять смену токенов обновления, при которой новый токен обновления выдаётся с каждым ответом на обновление токена доступа. Предыдущий токен обновления аннулируется, но сохраняется сервером авторизации. Если токен обновления скомпрометирован и впоследствии используется как злоумышленником, так и законным клиентом, один из них предъявит аннулированный токен обновления, что сообщит серверу авторизации о нарушении.
The authorization server MUST ensure that refresh tokens cannot be generated, modified, or guessed to produce valid refresh tokens by unauthorized parties.
Сервер авторизации ДОЛЖЕН обеспечивать, чтобы неавторизованные стороны не могли сгенерировать, изменить или угадать токены обновления так, чтобы получить действительные токены обновления.
10.5. Authorization Codes
10.5. Коды авторизации
The transmission of authorization codes SHOULD be made over a secure channel, and the client SHOULD require the use of TLS with its redirection URI if the URI identifies a network resource. Since authorization codes are transmitted via user-agent redirections, they could potentially be disclosed through user-agent history and HTTP referrer headers.
Передачу кодов авторизации СЛЕДУЕТ выполнять по защищённому каналу, и клиенту СЛЕДУЕТ требовать использования TLS со своим URI перенаправления, если этот URI идентифицирует сетевой ресурс. Поскольку коды авторизации передаются посредством перенаправлений пользовательского агента, они потенциально могут быть раскрыты через историю пользовательского агента и заголовки referrer HTTP.
Authorization codes operate as plaintext bearer credentials, used to verify that the resource owner who granted authorization at the authorization server is the same resource owner returning to the client to complete the process. Therefore, if the client relies on the authorization code for its own resource owner authentication, the client redirection endpoint MUST require the use of TLS.
Коды авторизации действуют как учётные данные носителя в открытом виде, используемые для проверки того, что владелец ресурса, предоставивший авторизацию на сервере авторизации, — тот же владелец ресурса, который возвращается к клиенту для завершения процесса. Поэтому, если клиент полагается на код авторизации для собственной аутентификации владельца ресурса, конечная точка перенаправления клиента ДОЛЖНА требовать использования TLS.
Authorization codes MUST be short lived and single-use. If the authorization server observes multiple attempts to exchange an authorization code for an access token, the authorization server SHOULD attempt to revoke all access tokens already granted based on the compromised authorization code.
Коды авторизации ДОЛЖНЫ быть короткоживущими и одноразовыми. Если сервер авторизации наблюдает несколько попыток обменять код авторизации на токен доступа, серверу авторизации СЛЕДУЕТ попытаться отозвать все токены доступа, уже выданные на основании скомпрометированного кода авторизации.
If the client can be authenticated, the authorization servers MUST authenticate the client and ensure that the authorization code was issued to the same client.
Если клиента можно аутентифицировать, серверы авторизации ДОЛЖНЫ аутентифицировать клиента и убедиться, что код авторизации был выдан тому же клиенту.
10.6. Authorization Code Redirection URI Manipulation
10.6. Манипулирование URI перенаправления кода авторизации
When requesting authorization using the authorization code grant type, the client can specify a redirection URI via the "redirect_uri" parameter. If an attacker can manipulate the value of the redirection URI, it can cause the authorization server to redirect the resource owner user-agent to a URI under the control of the attacker with the authorization code.
При запросе авторизации с использованием типа гранта «код авторизации» клиент может указать URI перенаправления с помощью параметра «redirect_uri». Если злоумышленник может манипулировать значением URI перенаправления, он может заставить сервер авторизации перенаправить пользовательский агент владельца ресурса на URI под контролем злоумышленника вместе с кодом авторизации.
An attacker can create an account at a legitimate client and initiate the authorization flow. When the attacker's user-agent is sent to the authorization server to grant access, the attacker grabs the authorization URI provided by the legitimate client and replaces the client's redirection URI with a URI under the control of the attacker. The attacker then tricks the victim into following the manipulated link to authorize access to the legitimate client.
Злоумышленник может создать учётную запись у законного клиента и инициировать процесс авторизации. Когда пользовательский агент злоумышленника отправляется на сервер авторизации для предоставления доступа, злоумышленник перехватывает URI авторизации, предоставленный законным клиентом, и заменяет URI перенаправления клиента на URI под контролем злоумышленника. Затем злоумышленник обманом заставляет жертву перейти по изменённой ссылке, чтобы авторизовать доступ к законному клиенту.
Once at the authorization server, the victim is prompted with a normal, valid request on behalf of a legitimate and trusted client, and authorizes the request. The victim is then redirected to an endpoint under the control of the attacker with the authorization code. The attacker completes the authorization flow by sending the authorization code to the client using the original redirection URI provided by the client. The client exchanges the authorization code with an access token and links it to the attacker's client account, which can now gain access to the protected resources authorized by the victim (via the client).
Попав на сервер авторизации, жертва видит обычный действительный запрос от имени законного и доверенного клиента и авторизует этот запрос. Затем жертва перенаправляется на конечную точку под контролем злоумышленника вместе с кодом авторизации. Злоумышленник завершает процесс авторизации, отправляя код авторизации клиенту с использованием первоначального URI перенаправления, предоставленного клиентом. Клиент обменивает код авторизации на токен доступа и связывает его с учётной записью клиента, принадлежащей злоумышленнику, которая теперь может получить доступ к защищённым ресурсам, авторизованным жертвой (через клиента).
In order to prevent such an attack, the authorization server MUST ensure that the redirection URI used to obtain the authorization code is identical to the redirection URI provided when exchanging the authorization code for an access token. The authorization server MUST require public clients and SHOULD require confidential clients to register their redirection URIs. If a redirection URI is provided in the request, the authorization server MUST validate it against the registered value.
Чтобы предотвратить такую атаку, сервер авторизации ДОЛЖЕН обеспечить, чтобы URI перенаправления, использованный для получения кода авторизации, был идентичен URI перенаправления, предоставленному при обмене кода авторизации на токен доступа. Сервер авторизации ДОЛЖЕН требовать от публичных клиентов и СЛЕДУЕТ требовать от конфиденциальных клиентов регистрации их URI перенаправления. Если в запросе предоставлен URI перенаправления, сервер авторизации ДОЛЖЕН проверить его соответствие зарегистрированному значению.
10.7. Resource Owner Password Credentials
10.7. Учётные данные пароля владельца ресурса
The resource owner password credentials grant type is often used for legacy or migration reasons. It reduces the overall risk of storing usernames and passwords by the client but does not eliminate the need to expose highly privileged credentials to the client.
Тип гранта «учётные данные пароля владельца ресурса» часто используется по причинам, связанным с унаследованными системами или миграцией. Он снижает общий риск хранения имён пользователей и паролей клиентом, но не устраняет необходимости раскрытия клиенту учётных данных с высокими привилегиями.
This grant type carries a higher risk than other grant types because it maintains the password anti-pattern this protocol seeks to avoid. The client could abuse the password, or the password could unintentionally be disclosed to an attacker (e.g., via log files or other records kept by the client).
Этот тип гранта несёт более высокий риск, чем другие типы грантов, поскольку он сохраняет антипаттерн пароля, которого этот протокол стремится избежать. Клиент мог бы злоупотребить паролем, либо пароль мог бы непреднамеренно раскрыться злоумышленнику (например, через файлы журналов или иные записи, хранимые клиентом).
Additionally, because the resource owner does not have control over the authorization process (the resource owner's involvement ends when it hands over its credentials to the client), the client can obtain access tokens with a broader scope than desired by the resource owner. The authorization server should consider the scope and lifetime of access tokens issued via this grant type.
Кроме того, поскольку владелец ресурса не контролирует процесс авторизации (участие владельца ресурса заканчивается, когда он передаёт клиенту свои учётные данные), клиент может получить токены доступа с более широкой областью действия, чем желает владелец ресурса. Серверу авторизации следует учитывать область действия и срок жизни токенов доступа, выдаваемых посредством этого типа гранта.
The authorization server and client SHOULD minimize use of this grant type and utilize other grant types whenever possible.
Серверу авторизации и клиенту СЛЕДУЕТ минимизировать использование этого типа гранта и применять другие типы грантов, когда это возможно.
10.8. Request Confidentiality
10.8. Конфиденциальность запросов
Access tokens, refresh tokens, resource owner passwords, and client credentials MUST NOT be transmitted in the clear. Authorization codes SHOULD NOT be transmitted in the clear.
Токены доступа, токены обновления, пароли владельца ресурса и учётные данные клиента НЕ ДОЛЖНЫ передаваться в открытом виде. Коды авторизации НЕ СЛЕДУЕТ передавать в открытом виде.
The "state" and "scope" parameters SHOULD NOT include sensitive client or resource owner information in plain text, as they can be transmitted over insecure channels or stored insecurely.
Параметры «state» и «scope» НЕ СЛЕДУЕТ включать конфиденциальные сведения клиента или владельца ресурса в открытом тексте, поскольку они могут передаваться по незащищённым каналам или храниться небезопасно.
10.9. Ensuring Endpoint Authenticity
10.9. Обеспечение подлинности конечной точки
In order to prevent man-in-the-middle attacks, the authorization server MUST require the use of TLS with server authentication as defined by [RFC2818] for any request sent to the authorization and token endpoints. The client MUST validate the authorization server's TLS certificate as defined by [RFC6125] and in accordance with its requirements for server identity authentication.
Чтобы предотвратить атаки «человек посередине», сервер авторизации ДОЛЖЕН требовать использования TLS с аутентификацией сервера, как определено в [RFC2818], для любого запроса, отправляемого на конечные точки авторизации и токена. Клиент ДОЛЖЕН проверять сертификат TLS сервера авторизации, как определено в [RFC6125], и в соответствии со своими требованиями к аутентификации идентичности сервера.
10.10. Credentials-Guessing Attacks
10.10. Атаки методом угадывания учётных данных
The authorization server MUST prevent attackers from guessing access tokens, authorization codes, refresh tokens, resource owner passwords, and client credentials.
Сервер авторизации ДОЛЖЕН предотвращать угадывание злоумышленниками токенов доступа, кодов авторизации, токенов обновления, паролей владельца ресурса и учётных данных клиента.
The probability of an attacker guessing generated tokens (and other credentials not intended for handling by end-users) MUST be less than or equal to 2^(-128) and SHOULD be less than or equal to 2^(-160).
Вероятность того, что злоумышленник угадает сгенерированные токены (и другие учётные данные, не предназначенные для обработки конечными пользователями), ДОЛЖНА быть меньше или равна 2^(-128) и СЛЕДУЕТ быть меньше или равна 2^(-160).
The authorization server MUST utilize other means to protect credentials intended for end-user usage.
Сервер авторизации ДОЛЖЕН применять иные средства защиты учётных данных, предназначенных для конечных пользователей.
10.11. Phishing Attacks
10.11. Фишинговые атаки
Wide deployment of this and similar protocols may cause end-users to become inured to the practice of being redirected to websites where they are asked to enter their passwords. If end-users are not careful to verify the authenticity of these websites before entering their credentials, it will be possible for attackers to exploit this practice to steal resource owners' passwords.
Широкое развёртывание этого и подобных протоколов может привести к тому, что конечные пользователи привыкнут к практике перенаправления на веб-сайты, где их просят ввести пароли. Если конечные пользователи не будут тщательно проверять подлинность этих веб-сайтов перед вводом своих учётных данных, злоумышленники смогут использовать эту практику для кражи паролей владельцев ресурсов.
Service providers should attempt to educate end-users about the risks phishing attacks pose and should provide mechanisms that make it easy for end-users to confirm the authenticity of their sites. Client developers should consider the security implications of how they interact with the user-agent (e.g., external, embedded), and the ability of the end-user to verify the authenticity of the authorization server. To reduce the risk of phishing attacks, the authorization servers MUST require the use of TLS on every endpoint used for end-user interaction.
Поставщикам служб следует пытаться просвещать конечных пользователей о рисках, которые представляют фишинговые атаки, и предоставлять механизмы, позволяющие конечным пользователям легко подтверждать подлинность своих сайтов. Разработчикам клиентов следует учитывать последствия для безопасности того, как они взаимодействуют с пользовательским агентом (например, внешним или встроенным), и способность конечного пользователя проверять подлинность сервера авторизации. Чтобы снизить риск фишинговых атак, серверы авторизации ДОЛЖНЫ требовать использования TLS на каждой конечной точке, используемой для взаимодействия с конечным пользователем.
10.12. Cross-Site Request Forgery
10.12. Подделка межсайтовых запросов
Cross-site request forgery (CSRF) is an exploit in which an attacker causes the user-agent of a victim end-user to follow a malicious URI (e.g., provided to the user-agent as a misleading link, image, or redirection) to a trusting server (usually established via the presence of a valid session cookie).
Подделка межсайтовых запросов (CSRF) — это атака, при которой злоумышленник заставляет пользовательский агент жертвы перейти по вредоносному URI (например, предоставленному пользовательскому агенту в виде вводящей в заблуждение ссылки, изображения или перенаправления) к доверяющему серверу (обычно установленному благодаря наличию действительного сеансового cookie-файла).
A CSRF attack against the client's redirection URI allows an attacker to inject its own authorization code or access token, which can result in the client using an access token associated with the attacker's protected resources rather than the victim's (e.g., save the victim's bank account information to a protected resource controlled by the attacker).
CSRF-атака на URI перенаправления клиента позволяет злоумышленнику внедрить свой собственный код авторизации или токен доступа, что может привести к тому, что клиент будет использовать токен доступа, связанный с защищёнными ресурсами злоумышленника, а не жертвы (например, сохранить сведения о банковском счёте жертвы в защищённом ресурсе, контролируемом злоумышленником).
The client MUST implement CSRF protection for its redirection URI. This is typically accomplished by requiring any request sent to the redirection URI endpoint to include a value that binds the request to the user-agent's authenticated state (e.g., a hash of the session cookie used to authenticate the user-agent). The client SHOULD utilize the "state" request parameter to deliver this value to the authorization server when making an authorization request.
Клиент ДОЛЖЕН реализовать защиту от CSRF для своего URI перенаправления. Обычно это достигается требованием, чтобы любой запрос, отправляемый на конечную точку URI перенаправления, включал значение, привязывающее запрос к аутентифицированному состоянию пользовательского агента (например, хеш сеансового cookie-файла, используемого для аутентификации пользовательского агента). Клиенту СЛЕДУЕТ использовать параметр запроса «state» для доставки этого значения серверу авторизации при выполнении запроса авторизации.
Once authorization has been obtained from the end-user, the authorization server redirects the end-user's user-agent back to the client with the required binding value contained in the "state" parameter. The binding value enables the client to verify the validity of the request by matching the binding value to the user-agent's authenticated state. The binding value used for CSRF protection MUST contain a non-guessable value (as described in Section 10.10), and the user-agent's authenticated state (e.g., session cookie, HTML5 local storage) MUST be kept in a location accessible only to the client and the user-agent (i.e., protected by same-origin policy).
После получения авторизации от конечного пользователя сервер авторизации перенаправляет пользовательский агент конечного пользователя обратно клиенту с требуемым значением привязки, содержащимся в параметре «state». Значение привязки позволяет клиенту проверить действительность запроса путём сопоставления значения привязки с аутентифицированным состоянием пользовательского агента. Значение привязки, используемое для защиты от CSRF, ДОЛЖНО содержать непредсказуемое значение (как описано в разделе 10.10), а аутентифицированное состояние пользовательского агента (например, сеансовый cookie-файл, локальное хранилище HTML5) ДОЛЖНО храниться в месте, доступном только клиенту и пользовательскому агенту (то есть защищённом политикой одного источника).
A CSRF attack against the authorization server's authorization endpoint can result in an attacker obtaining end-user authorization for a malicious client without involving or alerting the end-user.
CSRF-атака на конечную точку авторизации сервера авторизации может привести к тому, что злоумышленник получит авторизацию конечного пользователя для вредоносного клиента, не вовлекая конечного пользователя и не уведомляя его.
The authorization server MUST implement CSRF protection for its authorization endpoint and ensure that a malicious client cannot obtain authorization without the awareness and explicit consent of the resource owner.
Сервер авторизации ДОЛЖЕН реализовать защиту от CSRF для своей конечной точки авторизации и обеспечить, чтобы вредоносный клиент не мог получить авторизацию без осведомлённости и явного согласия владельца ресурса.
10.13. Clickjacking
10.13. Кликджекинг
In a clickjacking attack, an attacker registers a legitimate client and then constructs a malicious site in which it loads the authorization server's authorization endpoint web page in a transparent iframe overlaid on top of a set of dummy buttons, which are carefully constructed to be placed directly under important buttons on the authorization page. When an end-user clicks a misleading visible button, the end-user is actually clicking an invisible button on the authorization page (such as an "Authorize" button). This allows an attacker to trick a resource owner into granting its client access without the end-user's knowledge.
При атаке кликджекинга злоумышленник регистрирует законного клиента, а затем создаёт вредоносный сайт, на котором загружает веб-страницу конечной точки авторизации сервера авторизации в прозрачный iframe, наложенный поверх набора фиктивных кнопок, тщательно сконструированных так, чтобы располагаться прямо под важными кнопками на странице авторизации. Когда конечный пользователь нажимает вводящую в заблуждение видимую кнопку, он фактически нажимает невидимую кнопку на странице авторизации (например, кнопку «Authorize»). Это позволяет злоумышленнику обманом заставить владельца ресурса предоставить своему клиенту доступ без ведома конечного пользователя.
To prevent this form of attack, native applications SHOULD use external browsers instead of embedding browsers within the application when requesting end-user authorization. For most newer browsers, avoidance of iframes can be enforced by the authorization server using the (non-standard) "x-frame-options" header. This header can have two values, "deny" and "sameorigin", which will block any framing, or framing by sites with a different origin, respectively. For older browsers, JavaScript frame-busting techniques can be used but may not be effective in all browsers.
Чтобы предотвратить эту форму атаки, нативным приложениям СЛЕДУЕТ использовать внешние браузеры вместо встраивания браузеров в приложение при запросе авторизации конечного пользователя. В большинстве новых браузеров избежать iframe можно средствами сервера авторизации с использованием (нестандартного) заголовка «x-frame-options». Этот заголовок может иметь два значения: «deny» и «sameorigin», которые блокируют любое кадрирование или кадрирование сайтами с другим источником соответственно. Для старых браузеров можно использовать методы защиты от кадрирования на JavaScript, но они могут быть неэффективны во всех браузерах.
10.14. Code Injection and Input Validation
10.14. Внедрение кода и проверка входных данных
A code injection attack occurs when an input or otherwise external variable is used by an application unsanitized and causes modification to the application logic. This may allow an attacker to gain access to the application device or its data, cause denial of service, or introduce a wide range of malicious side-effects.
Атака внедрения кода происходит, когда входная или иная внешняя переменная используется приложением без очистки и вызывает изменение логики приложения. Это может позволить злоумышленнику получить доступ к устройству приложения или его данным, вызвать отказ в обслуживании или внести широкий спектр вредоносных побочных эффектов.
The authorization server and client MUST sanitize (and validate when possible) any value received -- in particular, the value of the "state" and "redirect_uri" parameters.
Сервер авторизации и клиент ДОЛЖНЫ очищать (и, когда возможно, проверять) любое полученное значение — в частности, значения параметров «state» и «redirect_uri».
10.15. Open Redirectors
10.15. Открытые перенаправляющие узлы
The authorization server, authorization endpoint, and client redirection endpoint can be improperly configured and operate as open redirectors. An open redirector is an endpoint using a parameter to automatically redirect a user-agent to the location specified by the parameter value without any validation.
Сервер авторизации, конечная точка авторизации и конечная точка перенаправления клиента могут быть неправильно настроены и работать как открытые перенаправляющие узлы. Открытый перенаправляющий узел — это конечная точка, использующая параметр для автоматического перенаправления пользовательского агента на местоположение, указанное значением параметра, без какой-либо проверки.
Open redirectors can be used in phishing attacks, or by an attacker to get end-users to visit malicious sites by using the URI authority component of a familiar and trusted destination. In addition, if the authorization server allows the client to register only part of the redirection URI, an attacker can use an open redirector operated by the client to construct a redirection URI that will pass the authorization server validation but will send the authorization code or access token to an endpoint under the control of the attacker.
Открытые перенаправляющие узлы могут использоваться в фишинговых атаках или злоумышленником, чтобы заставить конечных пользователей посещать вредоносные сайты, используя компонент полномочия URI знакомого и доверенного назначения. Кроме того, если сервер авторизации позволяет клиенту зарегистрировать только часть URI перенаправления, злоумышленник может использовать открытый перенаправляющий узел, управляемый клиентом, чтобы сформировать URI перенаправления, который пройдёт проверку сервера авторизации, но отправит код авторизации или токен доступа на конечную точку под контролем злоумышленника.
10.16. Misuse of Access Token to Impersonate Resource Owner in Implicit Flow
10.16. Злоупотребление токеном доступа для выдачи себя за владельца ресурса в неявном потоке
For public clients using implicit flows, this specification does not provide any method for the client to determine what client an access token was issued to.
Для публичных клиентов, использующих неявные потоки, настоящая спецификация не предоставляет никакого метода, позволяющего клиенту определить, какому клиенту был выдан токен доступа.
A resource owner may willingly delegate access to a resource by granting an access token to an attacker's malicious client. This may be due to phishing or some other pretext. An attacker may also steal a token via some other mechanism. An attacker may then attempt to impersonate the resource owner by providing the access token to a legitimate public client.
Владелец ресурса может добровольно делегировать доступ к ресурсу, предоставив токен доступа вредоносному клиенту злоумышленника. Это может быть следствием фишинга или иного предлога. Злоумышленник также может украсть токен каким-либо иным механизмом. Затем злоумышленник может попытаться выдать себя за владельца ресурса, предоставив токен доступа законному публичному клиенту.
In the implicit flow (response_type=token), the attacker can easily switch the token in the response from the authorization server, replacing the real access token with the one previously issued to the attacker.
В неявном потоке (response_type=token) злоумышленник может легко заменить токен в ответе сервера авторизации, подменив настоящий токен доступа тем, который ранее был выдан злоумышленнику.
Servers communicating with native applications that rely on being passed an access token in the back channel to identify the user of the client may be similarly compromised by an attacker creating a compromised application that can inject arbitrary stolen access tokens.
Серверы, взаимодействующие с нативными приложениями, которые полагаются на передачу токена доступа по обратному каналу для идентификации пользователя клиента, могут быть аналогично скомпрометированы злоумышленником, создающим скомпрометированное приложение, способное внедрять произвольные украденные токены доступа.
Any public client that makes the assumption that only the resource owner can present it with a valid access token for the resource is vulnerable to this type of attack.
Любой публичный клиент, который делает предположение, что только владелец ресурса может предъявить ему действительный токен доступа к ресурсу, уязвим к такому типу атаки.
This type of attack may expose information about the resource owner at the legitimate client to the attacker (malicious client). This will also allow the attacker to perform operations at the legitimate client with the same permissions as the resource owner who originally granted the access token or authorization code.
Этот тип атаки может раскрыть злоумышленнику (вредоносному клиенту) сведения о владельце ресурса у законного клиента. Это также позволит злоумышленнику выполнять операции у законного клиента с теми же правами, что и владелец ресурса, который изначально предоставил токен доступа или код авторизации.
Authenticating resource owners to clients is out of scope for this specification. Any specification that uses the authorization process as a form of delegated end-user authentication to the client (e.g., third-party sign-in service) MUST NOT use the implicit flow without additional security mechanisms that would enable the client to determine if the access token was issued for its use (e.g., audience- restricting the access token).
Аутентификация владельцев ресурсов для клиентов выходит за рамки настоящей спецификации. Любая спецификация, использующая процесс авторизации как форму делегированной аутентификации конечного пользователя для клиента (например, служба входа третьей стороны), НЕ ДОЛЖНА использовать неявный поток без дополнительных механизмов безопасности, которые позволили бы клиенту определить, был ли токен доступа выдан для его использования (например, ограничение токена доступа аудиторией).

Appendix B. Use of application/x-www-form-urlencoded Media Type
Приложение B. Использование типа носителя application/x-www-form-urlencoded
At the time of publication of this specification, the "application/x-www-form-urlencoded" media type was defined in Section 17.13.4 of [W3C.REC-html401-19991224] but not registered in the IANA MIME Media Types registry (<http://www.iana.org/assignments/media-types>). Furthermore, that definition is incomplete, as it does not consider non-US-ASCII characters.
На момент публикации настоящей спецификации тип носителя «application/x-www-form-urlencoded» был определён в разделе 17.13.4 [W3C.REC-html401-19991224], но не зарегистрирован в реестре типов носителей MIME IANA (<http://www.iana.org/assignments/media-types>). Кроме того, это определение неполно, поскольку не учитывает символы, отличные от US-ASCII.
To address this shortcoming when generating payloads using this media type, names and values MUST be encoded using the UTF-8 character encoding scheme [RFC3629] first; the resulting octet sequence then needs to be further encoded using the escaping rules defined in [W3C.REC-html401-19991224].
Чтобы устранить этот недостаток при формировании полезных нагрузок с использованием этого типа носителя, имена и значения ДОЛЖНЫ сначала кодироваться с использованием схемы кодирования символов UTF-8 [RFC3629]; полученную последовательность октетов затем нужно дополнительно закодировать с использованием правил экранирования, определённых в [W3C.REC-html401-19991224].
When parsing data from a payload using this media type, the names and values resulting from reversing the name/value encoding consequently need to be treated as octet sequences, to be decoded using the UTF-8 character encoding scheme.
При разборе данных из полезной нагрузки с использованием этого типа носителя имена и значения, полученные в результате обращения кодирования имён и значений, должны, следовательно, рассматриваться как последовательности октетов, подлежащие декодированию с использованием схемы кодирования символов UTF-8.
For example, the value consisting of the six Unicode code points (1) U+0020 (SPACE), (2) U+0025 (PERCENT SIGN), (3) U+0026 (AMPERSAND), (4) U+002B (PLUS SIGN), (5) U+00A3 (POUND SIGN), and (6) U+20AC (EURO SIGN) would be encoded into the octet sequence below (using hexadecimal notation):
