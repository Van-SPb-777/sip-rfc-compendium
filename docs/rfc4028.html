Abstract
Аннотация
This document defines an extension to the Session Initiation Protocol (SIP). This extension allows for a periodic refresh of SIP sessions through a re-INVITE or UPDATE request. The refresh allows both user agents and proxies to determine whether the SIP session is still active. The extension defines two new header fields: Session-Expires, which conveys the lifetime of the session, and Min-SE, which conveys the minimum allowed value for the session timer.
Настоящий документ определяет расширение протокола инициирования сессий (SIP). Это расширение допускает периодическое обновление сессий SIP с помощью запроса re-INVITE или UPDATE. Обновление позволяет как пользовательским агентам, так и прокси определять, активна ли ещё сессия SIP. Расширение определяет два новых поля заголовка: Session-Expires, которое передаёт время жизни сессии, и Min-SE, которое передаёт минимально допустимое значение таймера сессии.
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [2] does not define a keepalive mechanism for the sessions it establishes. Although the user agents may be able to determine whether the session has timed out by using session specific mechanisms, proxies will not be able to do so. The result is that call stateful proxies will not always be able to determine whether a session is still active. For instance, when a user agent fails to send a BYE message at the end of a session, or when the BYE message gets lost due to network problems, a call stateful proxy will not know when the session has ended. In this situation, the call stateful proxy will retain state for the call and has no method to determine when the call state information no longer applies.
Протокол инициирования сессий (SIP) [2] не определяет механизм поддержания соединения (keepalive) для устанавливаемых им сессий. Хотя пользовательские агенты, возможно, и способны определять, истекло ли время сессии, с помощью механизмов, специфичных для сессии, прокси сделать это не смогут. В результате прокси с сохранением состояния вызова не всегда способны определить, активна ли сессия. Например, если пользовательский агент не отправил сообщение BYE в конце сессии или если сообщение BYE потерялось из-за проблем в сети, прокси с сохранением состояния вызова не узнает, когда сессия завершилась. В такой ситуации прокси с сохранением состояния вызова будет хранить состояние вызова и не имеет способа определить, когда информация о состоянии вызова перестаёт быть актуальной.
To resolve this problem, this extension defines a keepalive mechanism for SIP sessions. UAs send periodic re-INVITE or UPDATE [3] requests (referred to as session refresh requests) to keep the session alive. The interval for the session refresh requests is determined through a negotiation mechanism defined here. If a session refresh request is not received before the interval passes, the session is considered terminated. Both UAs are supposed to send a BYE, and call stateful proxies can remove any state for the call.
Для решения этой проблемы расширение определяет механизм поддержания соединения для сессий SIP. Пользовательские агенты отправляют периодические запросы re-INVITE или UPDATE [3] (называемые запросами обновления сессии), чтобы поддерживать сессию активной. Интервал между запросами обновления сессии определяется механизмом согласования, определённым здесь. Если запрос обновления сессии не получен до истечения интервала, сессия считается завершённой. Оба пользовательских агента должны отправить BYE, а прокси с сохранением состояния вызова могут удалить любое состояние вызова.
This refresh mechanism has additional applications. A user agent would like to determine whether the session is still active for the same reasons a call stateful proxy server would. This determination can be made at a user agent without the use of SIP level mechanisms; for audio sessions, periodic RTCP packets serve as an indication of liveness [5]. However, it is desirable to separate indications of SIP session liveness from the details of the particular session.
Этот механизм обновления имеет дополнительное применение. Пользовательский агент хотел бы определять, активна ли ещё сессия, по тем же причинам, что и сервер прокси с сохранением состояния вызова. Такое определение может быть выполнено на пользовательском агенте без использования механизмов уровня SIP; для аудиосессий периодические пакеты RTCP служат признаком работоспособности [5]. Однако желательно отделять признаки работоспособности сессии SIP от подробностей конкретной сессии.
Another application of the session timer is in the construction of a SIP Network Address Translator (NAT) Application Level Gateway (ALG) [6]. The ALG embedded in a NAT will need to maintain state for the duration of a call. This state must eventually be removed. Relying on a BYE to trigger the removal of state, besides being unreliable, introduces a potential denial of service attack.
Другое применение таймера сессии — при построении шлюза прикладного уровня (ALG) преобразователя сетевых адресов (NAT) для SIP [6]. ALG, встроенному в NAT, потребуется поддерживать состояние в течение всей длительности вызова. Это состояние в конечном счёте должно быть удалено. Полагаться на BYE как на триггер удаления состояния, помимо своей ненадёжности, создаёт потенциальную угрозу отказа в обслуживании.
This document provides an extension to SIP that defines a session expiration mechanism. Periodic refreshes, through re-INVITEs or UPDATEs, are used to keep the session active. The extension is sufficiently backward compatible with SIP that it works as long as either one of the two participants in a dialog understands the extension. Two new header fields (Session-Expires and Min-SE) and a new response code (422) are defined. Session-Expires conveys the duration of the session, and Min-SE conveys the minimum allowed value for the session expiration. The 422 response code indicates that the session timer duration was too small.
Настоящий документ предоставляет расширение SIP, определяющее механизм истечения сессии. Периодические обновления посредством re-INVITE или UPDATE используются для поддержания активности сессии. Расширение достаточно обратно совместимо с SIP, чтобы работать, пока хотя бы один из двух участников диалога понимает расширение. Определяются два новых поля заголовка (Session-Expires и Min-SE) и новый код ответа (422). Session-Expires передаёт длительность сессии, а Min-SE — минимально допустимое значение истечения сессии. Код ответа 422 указывает, что длительность таймера сессии была слишком мала.
2. Terminology
2. Терминология
In this document, the key words 'MUST', 'MUST NOT', 'REQUIRED', 'SHALL', 'SHALL NOT', 'SHOULD', 'SHOULD NOT', 'RECOMMENDED', 'MAY', and 'OPTIONAL' are to be interpreted as described in RFC 2119 [1] and indicate requirement levels for compliant SIP implementations. Additionally, we define the following terms:
В настоящем документе ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» должны интерпретироваться так, как описано в RFC 2119 [1], и обозначают уровни требований для совместимых реализаций SIP. Кроме того, мы определяем следующие термины:
Session Interval: The maximum amount of time that can occur between session refresh requests in a dialog before the session will be considered timed out. The session interval is conveyed in the Session-Expires header field, which is defined here. The UAS obtains this value from the Session-Expires header field in a 2xx response to a session refresh request that it sends. Proxies and UACs determine this value from the Session-Expires header field in a 2xx response to a session refresh request that they receive.
Интервал сессии (Session Interval): максимальный промежуток времени, который может пройти между запросами обновления сессии в диалоге, прежде чем сессия будет считаться просроченной. Интервал сессии передаётся в поле заголовка Session-Expires, которое определено здесь. UAS получает это значение из поля заголовка Session-Expires в ответе 2xx на запрос обновления сессии, который он отправляет. Прокси и UAC определяют это значение из поля заголовка Session-Expires в ответе 2xx на запрос обновления сессии, который они получают.
Minimum Timer: Because of the processing load of mid-dialog requests, all elements (proxy, UAC, UAS) can have a configured minimum value for the session interval that they are willing to accept. This value is called the minimum timer.
Минимальный таймер (Minimum Timer): из-за нагрузки при обработке запросов внутри диалога все элементы (прокси, UAC, UAS) могут иметь настроенное минимальное значение интервала сессии, которое они готовы принять. Это значение называется минимальным таймером.
Session Expiration: The time at which an element will consider the session timed out, if no successful session refresh transaction occurs beforehand.
Момент истечения сессии (Session Expiration): время, в которое элемент сочтёт сессию просроченной, если до этого не произойдёт успешной транзакции обновления сессии.
Session Refresh Request: An INVITE or UPDATE request processed according to the rules of this specification. If the request generates a 2xx response, the session expiration is increased to the current time plus the session interval obtained from the response. A session refresh request is not to be confused with a target refresh request, defined in Section 6 of [2], which is a request that can update the remote target of a dialog.
Запрос обновления сессии (Session Refresh Request): запрос INVITE или UPDATE, обрабатываемый по правилам настоящей спецификации. Если запрос порождает ответ 2xx, момент истечения сессии увеличивается до текущего времени плюс интервал сессии, полученный из ответа. Запрос обновления сессии не следует путать с запросом обновления целевого адреса (target refresh request), определённым в разделе 6 документа [2], который представляет собой запрос, способный обновить удалённую цель диалога.
Initial Session Refresh Request: The first session refresh request sent with a particular Call-ID value.
Первоначальный запрос обновления сессии (Initial Session Refresh Request): первый такой запрос с конкретным значением Call-ID.
Subsequent Session Refresh Request: Any session refresh request sent with a particular Call-ID after the initial session refresh request.
Последующий запрос обновления сессии (Subsequent Session Refresh Request): любой такой запрос, отправленный с конкретным Call-ID после первоначального.
Refresh: Same as a session refresh request.
Обновление: то же, что запрос обновления сессии.
3. Overview of Operation
3. Обзор работы
This section provides a brief overview of the operation of the extension. It is tutorial in nature and should not be considered normative.
В этом разделе даётся краткий обзор работы расширения. Он носит обучающий характер и не должен рассматриваться как нормативный.
This extension has the property that it works even when only one UA in a dialog supports it. The processing steps differ for handling each of the four cases (the UAC does or doesn't support it, and the UAS does or doesn't support it). For simplicity's sake, this section will describe basic operation in the case where both sides support the extension.
Это расширение обладает тем свойством, что работает, даже когда его поддерживает только один UA в диалоге. Шаги обработки различаются для каждого из четырёх случаев (UAC поддерживает его или нет, и UAS поддерживает его или нет). Для простоты в этом разделе будет описана базовая работа в случае, когда обе стороны поддерживают расширение.
A UAC starts by sending an INVITE. This includes a Supported header field with the option tag 'timer', indicating support for this extension.
UAC начинает с отправки INVITE. В него включается поле заголовка Supported с тегом опции «timer», указывающим на поддержку этого расширения.
This request passes through proxies, any one of which may have an interest in establishing a session timer. Each proxy can insert a Session-Expires header field and a Min-SE header field into the request (if none is already there) or alter the value of existing Session-Expires and Min-SE header fields as described below.
Этот запрос проходит через прокси, любой из которых может быть заинтересован в установлении таймера сессии. Каждый прокси может вставить в запрос поле заголовка Session-Expires и поле заголовка Min-SE (если их там ещё нет) или изменить значения существующих полей заголовка Session-Expires и Min-SE, как описано ниже.
The Min-SE header field establishes the lower bound for the session refresh interval; i.e., the fastest rate any proxy servicing this request will be allowed to require. The purpose of this header field is to prevent hostile proxies from setting arbitrarily short refresh intervals so that their neighbors are overloaded. Each proxy processing the request can raise this lower bound (increase the period between refreshes) but is not allowed to lower it.
Поле заголовка Min-SE устанавливает нижнюю границу интервала обновления сессии, т. е. самую высокую частоту, которую будет разрешено требовать любому прокси, обслуживающему этот запрос. Назначение этого поля заголовка — не позволить недружественным прокси задавать произвольно короткие интервалы обновления, чтобы их соседи не были перегружены. Каждый прокси, обрабатывающий запрос, может поднять эту нижнюю границу (увеличить период между обновлениями), но не вправе её понижать.
The Session-Expires header field establishes the upper bound for the session refresh interval; i.e., the time period after processing a request for which any session-stateful proxy must retain its state for this session. Any proxy servicing this request can lower this value, but it is not allowed to decrease it below the value specified in the Min-SE header field.
Поле заголовка Session-Expires устанавливает верхнюю границу интервала обновления сессии, т. е. период времени после обработки запроса, в течение которого любой прокси, хранящий состояние сессии, обязан сохранять своё состояние для этой сессии. Любой прокси, обслуживающий этот запрос, может понизить это значение, но не вправе уменьшать его ниже значения, указанного в поле заголовка Min-SE.
If the Session-Expires interval is too low for a proxy (i.e., lower than the value of Min-SE that the proxy would wish to assert), the proxy rejects the request with a 422 response. That response contains a Min-SE header field identifying the minimum session interval it is willing to support. The UAC will try again, this time including the Min-SE header field in the request. The header field contains the largest Min-SE header field it observed in all 422 responses previously received. This way, the minimum timer meets the constraints of all proxies along the path.
Если интервал Session-Expires слишком мал для прокси (т. е. ниже значения Min-SE, которое прокси хотел бы отстаивать), прокси отклоняет запрос ответом 422. Этот ответ содержит поле заголовка Min-SE, определяющее минимальный интервал сессии, который он готов поддерживать. UAC повторит попытку, на этот раз включив поле заголовка Min-SE в запрос. Поле заголовка содержит наибольшее значение Min-SE, которое он наблюдал во всех ранее полученных ответах 422. Таким образом, минимальный таймер удовлетворяет ограничениям всех прокси на пути.
After several INVITE/422 iterations, the request eventually arrives at the UAS. The UAS can adjust the value of the session interval as if it were a proxy; when done, it places the final session interval into the Session-Expires header field in a 2xx response. The Session-Expires header field also contains a 'refresher' parameter, which indicates who is doing the refreshing -- the UA that is currently the UAC, or the UA that is currently the UAS. As the 2xx response travels back through the proxy chain, each proxy can observe the final session interval but can't change it. From the Session-Expires header field in the response, both UAs know that a session timer is active, when it will expire, and who is refreshing. At some point before the expiration, the currently active refresher generates a session refresh request, which is a re-INVITE or UPDATE [3] request. If the refresher never gets a response to that session refresh request, it sends a BYE to terminate the session. Similarly, if the other side never gets the session refresh request before the session expires, it sends a BYE.
После нескольких итераций INVITE/422 запрос в конце концов достигает UAS. UAS может скорректировать значение интервала сессии так, как если бы он был прокси; когда это сделано, он помещает окончательный интервал сессии в поле заголовка Session-Expires в ответе 2xx. Поле заголовка Session-Expires также содержит параметр «refresher», который указывает, кто выполняет обновление, — UA, являющийся в данный момент UAC, или UA, являющийся в данный момент UAS. Пока ответ 2xx идёт обратно по цепочке прокси, каждый прокси может наблюдать окончательный интервал сессии, но не может его изменить. Из поля заголовка Session-Expires в ответе оба UA узнают, что таймер сессии активен, когда он истечёт и кто выполняет обновление. В некоторый момент до истечения текущий активный refresher порождает запрос обновления сессии, то есть запрос re-INVITE или UPDATE [3]. Если refresher так и не получит ответа на этот запрос обновления сессии, он отправляет BYE для завершения сессии. Аналогично, если другая сторона так и не получит запрос обновления сессии до истечения сессии, она отправляет BYE.
The refresh requests sent once the session is established are processed identically to the initial requests, as described above. This means that a successful session refresh request will extend the session, as desired.
Запросы обновления, отправляемые после установления сессии, обрабатываются точно так же, как первоначальные запросы, описанные выше. Это означает, что успешный запрос обновления сессии продлит сессию, как и требуется.
The extension introduces additional complications beyond this basic flow to support cases where only one of the UAs supports it. One such complication is that a proxy may need to insert the Session-Expires header field into the response, in the event that the UAS doesn't support the extension. The negotiation of the role of refresher is also affected by this capability; it takes into consideration which participants support the extension.
Расширение вносит дополнительные усложнения сверх этого базового потока, чтобы поддерживать случаи, когда его поддерживает только один из UA. Одно из таких усложнений состоит в том, что прокси может потребоваться вставить поле заголовка Session-Expires в ответ, если UAS не поддерживает расширение. На согласование роли refresher также влияет эта возможность: оно учитывает, какие участники поддерживают расширение.
Note that the session timer refreshes the session, not the dialog used to establish the session. Of course, the two are related. If the session expires, a BYE is sent, which terminates the session and, generally, the dialog.
Отметим, что таймер сессии обновляет сессию, а не диалог использованный для установления сессии. Конечно, эти два понятия связаны. Если сессия истекает, отправляется BYE, который завершает сессию и, как правило, диалог.
4. Session-Expires Header Field Definition
4. Определение поля заголовка Session-Expires
The Session-Expires header field conveys the session interval for a SIP session. It is placed only in INVITE or UPDATE requests, as well as in any 2xx response to an INVITE or UPDATE. Like the SIP Expires header field, it contains a delta-time.
Поле заголовка Session-Expires передаёт интервал сессии для сессии SIP. Оно помещается только в запросы INVITE или UPDATE, а также в любой ответ 2xx на INVITE или UPDATE. Как и поле заголовка SIP Expires, оно содержит значение delta-time (приращение времени).
The absolute minimum for the Session-Expires header field is 90 seconds. This value represents a bit more than twice the duration that a SIP transaction can take in the event of a timeout. This allows sufficient time for a UA to attempt a refresh at the halfpoint of the session interval, and for that transaction to complete normally before the session expires. However, 1800 seconds (30 minutes) is RECOMMENDED as the value for the Session-Expires header field. In other words, SIP entities MUST be prepared to handle Session-Expires header field values of any duration greater than 90 seconds, but entities that insert the Session-Expires header field SHOULD NOT choose values of less than 30 minutes. Small session intervals can be destructive to the network. They cause excessive messaging traffic that affects both user agents and proxy servers. They increase the possibility of 'glare' that can occur when both user agents send a re-INVITE or UPDATE at the same time. Since the primary purpose of the session timer is to provide a means to time out state in SIP elements, very small values won't generally be needed. 30 minutes was chosen because 95% of phone calls are shorter than this duration.
Абсолютный минимум для поля заголовка Session-Expires составляет 90 секунд. Это значение представляет собой чуть больше удвоенной длительности, которую транзакция SIP может занять в случае тайм-аута. Это оставляет достаточно времени для того, чтобы UA попытался выполнить обновление на половине интервала сессии и чтобы эта транзакция нормально завершилась до истечения сессии. Однако в качестве значения поля заголовка Session-Expires РЕКОМЕНДУЕТСЯ 1800 секунд (30 минут). Иными словами, элементы SIP ДОЛЖНЫ быть готовы обрабатывать значения поля заголовка Session-Expires любой длительности больше 90 секунд, но элементы, вставляющие поле заголовка Session-Expires, НЕ ДОЛЖНЫ выбирать значения меньше 30 минут. Малые интервалы сессии могут быть разрушительны для сети. Они вызывают избыточный обмен сообщениями, который затрагивает и пользовательские агенты, и прокси-серверы. Они повышают вероятность «конфликта» (glare), который может возникнуть, когда оба пользовательских агента одновременно отправляют re-INVITE или UPDATE. Поскольку основное назначение таймера сессии — дать средство для истечения состояния в элементах SIP, очень малые значения, как правило, не понадобятся. 30 минут были выбраны потому, что 95 % телефонных звонков короче этой длительности.
However, the 30 minute minimum is listed as a SHOULD, and not as a MUST, since the exact value for this number is dependent on many network factors, including network bandwidths and latencies, computing power, memory availability, network topology, and, of course, the application scenario. After all, SIP can set up any kind of session, not just a phone call. At the time of publication of this document, 30 minutes seems appropriate. Advances in technologies may result in the number being excessively large five years in the future.
Однако минимум в 30 минут указан как SHOULD, а не как MUST, поскольку точное значение этого числа зависит от многих сетевых факторов, включая пропускную способность и задержки сети, вычислительную мощность, доступность памяти, топологию сети и, разумеется, сценарий применения. В конце концов, SIP может устанавливать любые сессии, а не только телефонные звонки. На момент публикации настоящего документа 30 минут представляются подходящими. Прогресс технологий может привести к тому, что через пять лет это число окажется чрезмерно большим.
The default value of the Session-Expires header field is undefined. This means that the absence of the Session-Expires header field implies no expiration of the session, using the mechanism defined in this specification. Note that other mechanisms not defined in this specification, such as locally configured timers, may apply.
Значение по умолчанию для поля заголовка Session-Expires не определено. Это означает, что отсутствие поля заголовка Session-Expires подразумевает отсутствие истечения сессии при использовании механизма, определённого в настоящей спецификации. Отметим, что могут применяться другие механизмы, не определённые в настоящей спецификации, например локально настроенные таймеры.

Отметим, что для Session-Expires зарезервирована сокращённая форма — буква x. BNF для delta-seconds и generic-param определён в разделе 25 RFC 3261 [2].

5. Min-SE Header Field Definition
5. Определение поля заголовка Min-SE
The Min-SE header field indicates the minimum value for the session interval, in units of delta-seconds. When used in an INVITE or UPDATE request, it indicates the smallest value of the session interval that can be used for that session. When present in a request or response, its value MUST NOT be less than 90 seconds.
Поле заголовка Min-SE указывает минимальное значение интервала сессии в единицах delta-seconds. При использовании в запросе INVITE или UPDATE оно указывает наименьшее значение интервала сессии, которое может быть использовано для этой сессии. При наличии в запросе или ответе его значение НЕ ДОЛЖНО быть меньше 90 секунд.
When the header field is not present, its default value for is 90 seconds.
Когда поле заголовка отсутствует, его значением по умолчанию являются 90 секунд.
The Min-SE header field MUST NOT be used in responses except for those with a 422 response code. It indicates the minimum value of the session interval that the server is willing to accept.
Поле заголовка Min-SE НЕ ДОЛЖНО использоваться в ответах, кроме ответов с кодом 422. Оно указывает минимальное значение интервала сессии, которое сервер готов принять.
The syntax of the Min-SE header field is as follows:
Синтаксис поля заголовка Min-SE выглядит следующим образом:
Min-SE = "Min-SE" HCOLON delta-seconds *(SEMI generic-param)
Min-SE = "Min-SE" HCOLON delta-seconds *(SEMI generic-param)
6. 422 Response Code Definition
6. Определение кода ответа 422
This extension introduces the 422 (Session Interval Too Small) response code. It is generated by a UAS or proxy when a request contains a Session-Expires header field with a duration below the minimum timer for the server. The 422 response MUST contain a Min-SE header field with the minimum timer for that server.
Это расширение вводит код ответа 422 (Session Interval Too Small). Он формируется UAS или прокси, когда запрос содержит поле заголовка Session-Expires с длительностью ниже минимального таймера для сервера. Ответ 422 ДОЛЖЕН содержать поле заголовка Min-SE с минимальным таймером для этого сервера.
7. UAC Behavior
7. Поведение UAC
7.1. Generating an Initial Session Refresh Request
7.1. Формирование первоначального запроса обновления сессии
A UAC that supports the session timer extension defined here MUST include a Supported header field in each request (except ACK), listing the option tag 'timer' [2]. It MUST do so even if the UAC is not requesting usage of the session timer for this session.
UAC, поддерживающий определённое здесь расширение таймера сессии, ДОЛЖЕН включать поле заголовка Supported в каждый запрос (кроме ACK), перечисляя тег опции «timer» [2]. Он ДОЛЖЕН делать это, даже если UAC не запрашивает использование таймера сессии для этой сессии.
The UAC MAY include a Require header field in the request with the value 'timer' to indicate that the UAS must support the session timer to participate in the session. This does not mean that the UAC is requiring the UAS to perform the refreshes, only that it is requiring the UAS to support the extension. In addition, the UAC MAY include a Proxy-Require header field in the request with the value 'timer' to indicate that proxies must support the session timer in order to correctly process the request. However, usage of either Require or Proxy-Require by the UAC is NOT RECOMMENDED. They are not needed, since the extension works even when only the UAC supports the extension. The Supported header field containing 'timer' MUST still be included, even if the Require or Proxy-Require header fields are present containing 'timer'.
UAC МОЖЕТ включить в запрос поле заголовка Require со значением «timer», чтобы указать, что UAS должен поддерживать таймер сессии для участия в сессии. Это не означает, что UAC требует от UAS выполнения обновлений, — только то, что он требует от UAS поддержки расширения. Кроме того, UAC МОЖЕТ включить в запрос поле заголовка Proxy-Require со значением «timer», чтобы указать, что прокси должны поддерживать таймер сессии для правильной обработки запроса. Однако использование UAC как Require, так и Proxy-Require НЕ РЕКОМЕНДУЕТСЯ. Они не нужны, поскольку расширение работает, даже когда его поддерживает только UAC. Поле заголовка Supported, содержащее «timer», ДОЛЖНО всё равно включаться, даже если присутствуют поля заголовка Require или Proxy-Require, содержащие «timer».
A UAC MAY include the Min-SE header field in the initial INVITE request.
UAC МОЖЕТ включить поле заголовка Min-SE в первоначальный запрос INVITE.
A UAC MAY include a Session-Expires header field in an initial session refresh request if it wants a session timer applied to the session. The value of this header field indicates the session interval desired by the UAC. If a Min-SE header is included in the initial session refresh request, the value of the Session-Expires MUST be greater than or equal to the value in Min-SE.
UAC МОЖЕТ включить поле заголовка Session-Expires в первоначальный запрос обновления сессии, если он хочет, чтобы к сессии применялся таймер сессии. Значение этого поля заголовка указывает интервал сессии, желаемый UAC. Если в первоначальный запрос обновления сессии включено поле заголовка Min-SE, значение Session-Expires ДОЛЖНО быть больше или равно значению в Min-SE.
The UAC MAY include the refresher parameter with value 'uac' if it wants to perform the refreshes. However, it is RECOMMENDED that the parameter be omitted so that it can be selected by the negotiation mechanisms described below.
UAC МОЖЕТ включить параметр refresher со значением «uac», если он хочет выполнять обновления. Однако РЕКОМЕНДУЕТСЯ опустить этот параметр, чтобы он мог быть выбран механизмами согласования, описанными ниже.
7.2. Processing a 2xx Response
7.2. Обработка ответа 2xx
The session timer requires a UA to create and maintain state. This state includes the session interval, the session expiration, and the identity of the refresher. This state is associated with the dialog on which the session has been negotiated. When a 2xx response to a session refresh request arrives, it may or may not contain a Require header field with the value 'timer'. If it does, the UAC MUST look for the Session-Expires header field to process the response.
Таймер сессии требует, чтобы UA создавал и поддерживал состояние. Это состояние включает интервал сессии, момент истечения сессии и идентичность refresher. Это состояние связано с диалогом, в котором была согласована сессия. Когда приходит ответ 2xx на запрос обновления сессии, он может содержать или не содержать поле заголовка Require со значением «timer». Если содержит, UAC ДОЛЖЕН искать поле заголовка Session-Expires, чтобы обработать ответ.
If there was a Require header field in the response with the value 'timer', the Session-Expires header field will always be present. UACs MUST be prepared to receive a Session-Expires header field in a response, even if none were present in the request. The 'refresher' parameter will be present in the Session-Expires header field, indicating who will perform the refreshes. The UAC MUST set the identity of the refresher to the value of this parameter. If the parameter contains the value 'uac', the UAC will perform them. It is possible that the UAC requested the session timer (and thus included a Session-Expires header field in the request) and that there was no Require or Session-Expires header field in the 2xx response. This will happen when the UAS doesn't support the session timer extension and only the UAC has asked for a session timer (no proxies have requested it). In this case, if the UAC still wishes to use the session timer (which is purely for its benefit alone), it has to perform them. To do this, the UAC follows the procedures defined in this specification as if the Session-Expires header field were in the 2xx response, and its value was the same as that in the request, but with a refresher parameter of 'uac'.
Если в ответе было поле заголовка Require со значением «timer», поле заголовка Session-Expires будет присутствовать всегда. UAC ДОЛЖНЫ быть готовы получить поле заголовка Session-Expires в ответе, даже если в запросе его не было. В поле заголовка Session-Expires будет присутствовать параметр «refresher», указывающий, кто будет выполнять обновления. UAC ДОЛЖЕН установить идентичность refresher в значение этого параметра. Если параметр содержит значение «uac», обновления будет выполнять UAC. Возможна ситуация, когда UAC запросил таймер сессии (и, следовательно, включил поле заголовка Session-Expires в запрос), а в ответе 2xx не было ни поля заголовка Require, ни поля заголовка Session-Expires. Это произойдёт, когда UAS не поддерживает расширение таймера сессии и таймер сессии запросил только UAC (ни один прокси его не запрашивал). В этом случае, если UAC всё же хочет использовать таймер сессии (что приносит пользу исключительно ему), он должен выполнять обновления. Для этого UAC следует процедурам, определённым в настоящей спецификации, как если бы поле заголовка Session-Expires присутствовало в ответе 2xx и его значение совпадало со значением в запросе, но с параметром refresher со значением «uac».
If the 2xx response did not contain a Session-Expires header field, there is no session expiration. In this case, no refreshes need to be sent. A 2xx without a Session-Expires can come for both initial and subsequent session refresh requests. This means that the session timer can be 'turned-off' in mid dialog by receiving a response without a Session-Expires header field.
Если ответ 2xx не содержал поля заголовка Session-Expires, истечения сессии нет. В этом случае обновления отправлять не нужно. Ответ 2xx без Session-Expires может прийти как на первоначальный, так и на последующий запрос обновления сессии. Это означает, что таймер сессии можно «выключить» в середине диалога, получив ответ без поля заголовка Session-Expires.
The UAC remembers the session interval for a session as the value of the delta-time from the Session-Expires header field in the most recent 2xx response to a session refresh request on a dialog. It is explicitly allowed for there to be differing session intervals (or none at all) on differing dialogs established as a result of a single INVITE. The UAC also remembers whether it or its peer is the refresher on for the session.
UAC запоминает интервал сессии для сессии как значение delta-time из поля заголовка Session-Expires в самом последнем ответе 2xx на запрос обновления сессии в диалоге. Явно допускается, чтобы в разных диалогах, установленных в результате одного INVITE, были различные интервалы сессии (или их не было вовсе). UAC также запоминает, является ли refresher он сам или его партнёр для этой сессии.
If the UAC must perform the refreshes, it computes the session expiration for that session. The session expiration is the time of reception of the last 2xx response to a session refresh request on that dialog plus the session interval for that session. If the UA seeks to continue with the session beyond the session expiration, it MUST generate a refresh before the session expiration. It is RECOMMENDED that this refresh be sent once half the session interval has elapsed. Additional procedures for this refresh are described in Section 10.
Если обновления должен выполнять UAC, он вычисляет момент истечения сессии для этой сессии. Момент истечения сессии — это время получения последнего ответа 2xx на запрос обновления сессии в этом диалоге плюс интервал сессии для этой сессии. Если UA намерен продолжить сессию после момента её истечения, он ДОЛЖЕН сформировать обновление до наступления этого момента. РЕКОМЕНДУЕТСЯ отправлять это обновление, когда прошла половина интервала сессии. Дополнительные процедуры для этого обновления описаны в разделе 10.
Similarly, a re-INVITE or UPDATE request sent within a dialog for purposes other than session refreshes will also have the effect of refreshing the session, and its processing will follow the procedures defined in this specification.
Аналогично, запрос re-INVITE или UPDATE, отправленный в диалоге для целей, отличных от обновления сессии, также будет иметь эффект обновления сессии, и его обработка будет следовать процедурам, определённым в настоящей спецификации.
7.3. Processing a 422 Response
7.3. Обработка ответа 422
If the response to a session refresh request is a 422 (Session Interval Too Small) response message, then the UAC MAY retry the request. The procedures for retrying are described in Section 7.4. This new request constitutes a new transaction and SHOULD have the same value as the Call-ID, To, and From of the previous request, but the CSeq should contain a new sequence number that is one higher than the previous.
Если ответом на запрос обновления сессии является ответное сообщение 422 (Session Interval Too Small), UAC МОЖЕТ повторить запрос. Процедуры повторной попытки описаны в разделе 7.4. Этот новый запрос представляет собой новую транзакцию и ДОЛЖЕН иметь те же значения Call-ID, To и From, что и предыдущий запрос, но CSeq должен содержать новый порядковый номер, на единицу больший предыдущего.
7.4. Generating Subsequent Session Refresh Requests
7.4. Формирование последующих запросов обновления сессии
The values of Supported, Require, and Proxy-Require used in the initial Session refresh request MUST be used.
Значения Supported, Require и Proxy-Require, использованные в первоначальном запросе обновления сессии, ДОЛЖНЫ использоваться и далее.
The UAC MUST insert the Min-SE header field into a session refresh request for a particular dialog if it has ever received a 422 response to a previous session refresh request on the same dialog, or if it has received a session refresh request on that dialog that contained a Min-SE header field. Similarly, if no dialog has been established yet, a UAC MUST insert the Min-SE header field into an INVITE request if it has ever received a 422 response to a previous INVITE request with the same Call-ID.
UAC ДОЛЖЕН вставлять поле заголовка Min-SE в запрос обновления сессии для конкретного диалога, если он когда-либо получал ответ 422 на предыдущий запрос обновления сессии в том же диалоге или если он получал в этом диалоге запрос обновления сессии, содержащий поле заголовка Min-SE. Аналогично, если диалог ещё не установлен, UAC ДОЛЖЕН вставлять поле заголовка Min-SE в запрос INVITE, если он когда-либо получал ответ 422 на предыдущий запрос INVITE с тем же Call-ID.
The value of the Min-SE header field present in a session refresh request MUST be the largest value among all Min-SE header field values returned in all 422 responses or received in session refresh requests, on the same dialog, if a dialog has been established. If no dialog has been established, the Min-SE header field value is set to the largest value among all Min-SE header field values returned in all 422 responses for an INVITE request with the same Call-ID. A result of this rule is that the maximum value of the Min-SE is effectively 'cleared' once the dialog is established, and from that point on, only the values from proxies known to be on the proxy path will end up being used.
Значение поля заголовка Min-SE, присутствующего в запросе обновления сессии, ДОЛЖНО быть наибольшим среди всех значений поля заголовка Min-SE, возвращённых во всех ответах 422 или полученных в запросах обновления сессии в том же диалоге, если диалог установлен. Если диалог не установлен, значение поля заголовка Min-SE устанавливается в наибольшее среди всех значений поля заголовка Min-SE, возвращённых во всех ответах 422 на запрос INVITE с тем же Call-ID. Следствием этого правила является то, что максимальное значение Min-SE фактически «сбрасывается» после установления диалога, и с этого момента будут использоваться только значения от прокси, о которых известно, что они находятся на пути прокси.
The UAC may have its own opinions about the minimum session interval. In that case, if the value above is too small, the UAC MAY increase it. In a session refresh request sent within a dialog with an active session timer, the Session-Expires header field SHOULD be present. When present, it SHOULD be equal to the maximum of the Min-SE header field (recall that its default value when not present is 90 seconds) and the current session interval. Inclusion of the Session-Expires header field with this value avoids certain denial-of-service attacks, as documented in Section 11. As such, a UA should only ignore the SHOULD in unusual and singular cases where it is desirable to change the session interval mid-dialog.
У UAC могут быть собственные представления о минимальном интервале сессии. В этом случае, если приведённое выше значение слишком мало, UAC МОЖЕТ его увеличить. В запросе обновления сессии, отправленном в диалоге с активным таймером сессии, поле заголовка Session-Expires СЛЕДУЕТ включать. При наличии оно СЛЕДУЕТ устанавливать равным максимуму из значения поля заголовка Min-SE (напомним, что его значение по умолчанию при отсутствии равно 90 секундам) и текущего интервала сессии. Включение поля заголовка Session-Expires с этим значением предотвращает некоторые атаки типа «отказ в обслуживании», как описано в разделе 11. Поэтому UA должен отступать от данного СЛЕДУЕТ только в необычных и единичных случаях, когда желательно изменить интервал сессии внутри диалога.
If the session refresh request is not the initial one, it is RECOMMENDED that the refresher parameter be set to 'uac' if the element sending the request is currently performing refreshes, and to 'uas' if its peer is performing the refreshes. This way, the role of refresher does not change on each refresh. However, if it wishes to explicitly change the roles, it MAY use a value of 'uas' if it knows that the other side supports the session timer. It could know this by having received a request from its peer with a Supported header field containing the value 'timer'. If it seeks to reselect the roles, it MAY omit the parameter.
Если запрос обновления сессии не является первоначальным, РЕКОМЕНДУЕТСЯ устанавливать параметр refresher в значение «uac», если элемент, отправляющий запрос, в настоящее время выполняет обновления, и в значение «uas», если обновления выполняет его партнёр. Таким образом роль refresher не меняется при каждом обновлении. Однако если он желает явно изменить роли, он МОЖЕТ использовать значение «uas», если знает, что другая сторона поддерживает таймер сессии. Он может узнать это, получив от партнёра запрос с полем заголовка Supported, содержащим значение «timer». Если он стремится заново выбрать роли, он МОЖЕТ опустить этот параметр.
A re-INVITE generated to refresh the session is a normal re-INVITE, and an UPDATE generated to refresh a session is a normal UPDATE. If a UAC knows that its peer supports the UPDATE method, it is RECOMMENDED that UPDATE be used instead of a re-INVITE. A UA can make this determination if it has seen an Allow header field from its peer with the value 'UPDATE', or through a mid-dialog OPTIONS request. It is RECOMMENDED that the UPDATE request not contain an offer [4], but a re-INVITE SHOULD contain one, even if the details of the session have not changed. In that case, the offer MUST indicate that it has not changed. In the case of SDP, this is accomplished by including the same value for the origin field as did previous SDP messages to its peer. The same is true for an answer exchanged as a result of a session refresh request; if it has not changed, that MUST be indicated.
re-INVITE, сформированный для обновления сессии, является обычным re-INVITE, а UPDATE, сформированный для обновления сессии, — обычным UPDATE. Если UAC знает, что его партнёр поддерживает метод UPDATE, РЕКОМЕНДУЕТСЯ использовать UPDATE вместо re-INVITE. UA может установить это, если он видел от партнёра поле заголовка Allow со значением «UPDATE» или получил запрос OPTIONS внутри диалога. РЕКОМЕНДУЕТСЯ, чтобы запрос UPDATE не содержал предложения (offer) [4], но re-INVITE СЛЕДУЕТ содержать его, даже если параметры сессии не изменились. В этом случае предложение ДОЛЖНО указывать, что оно не изменилось. В случае SDP это достигается включением того же значения поля origin, что и в предыдущих сообщениях SDP партнёру. То же верно и для ответа, обмен которым происходит в результате запроса обновления сессии; если он не изменился, это ДОЛЖНО быть указано.
8. Proxy Behavior
8. Поведение прокси
Session timers are mostly of interest to call stateful proxy servers (that is, to servers that maintain the state of calls and dialogs established through them). However, a stateful proxy server (that is, a server which is aware of transaction state but does not retain call or dialog state) MAY also follow the rules described here. Stateless proxies MUST NOT attempt to request session timers. Proxies that ask for session timers SHOULD record-route, as they won't receive refreshes if they don't. The proxy processing rules require the proxy to remember information between the request and response, ruling out stateless proxies.
Таймеры сессии в основном интересны прокси-серверам с сохранением состояния вызова (то есть серверам, которые хранят состояние вызовов и диалогов, установленных через них). Однако прокси-сервер с сохранением состояния (то есть сервер, который осведомлён о состоянии транзакций, но не сохраняет состояние вызова или диалога) МОЖЕТ также следовать описанным здесь правилам. Прокси без сохранения состояния НЕ ДОЛЖНЫ пытаться запрашивать таймеры сессии. Прокси, запрашивающие таймеры сессии, СЛЕДУЕТ выполнять record-route, поскольку иначе они не будут получать обновления. Правила обработки прокси требуют, чтобы прокси запоминал информацию между запросом и ответом, что исключает прокси без сохранения состояния.
8.1. Processing of Requests
8.1. Обработка запросов
Processing of requests is identical for all session refresh requests.
Обработка запросов одинакова для всех запросов обновления сессии.
To request a session timer for a session, a proxy makes sure that a Session-Expires header field is present in a session refresh request for that session. A proxy MAY insert a Session-Expires header field in the request before forwarding it if none was present in the request. This Session-Expires header field may contain any desired expiration time the proxy would like, but not with a duration lower than the value in the Min-SE header field in the request, if it is present. The proxy MUST NOT include a refresher parameter in the header field value.
Чтобы запросить таймер сессии для сессии, прокси убеждается, что в запросе обновления сессии для этой сессии присутствует поле заголовка Session-Expires. Прокси МОЖЕТ вставить поле заголовка Session-Expires в запрос перед его пересылкой, если в запросе его не было. Это поле заголовка Session-Expires может содержать любое желаемое время истечения, которое хотел бы прокси, но не с длительностью ниже значения в поле заголовка Min-SE в запросе, если оно присутствует. Прокси НЕ ДОЛЖЕН включать параметр refresher в значение поля заголовка.
If the request already had a Session-Expires header field, the proxy MAY reduce its value but MUST NOT set it to a duration lower than the value in the Min-SE header field in the request, if it is present. If the value of the Session-Expires header field is greater than or equal to the value in the Min-SE header field (recall that the default is 90 seconds when the Min-SE header field is not present), the proxy MUST NOT increase the value of the Session-Expires header field. If the value of the Session-Expires header field is lower than the value of the Min-SE header field (possibly because the proxy increased the value of the Min-SE header field, as described below), the proxy MUST increase the value of the Session-Expires header field to make it equal to Min-SE header field value. The proxy MUST NOT insert or modify the value of the 'refresher' parameter in the Session-Expires header field.
Если в запросе уже было поле заголовка Session-Expires, прокси МОЖЕТ уменьшить его значение, но НЕ ДОЛЖЕН устанавливать его в длительность ниже значения в поле заголовка Min-SE в запросе, если оно присутствует. Если значение поля заголовка Session-Expires больше или равно значению в поле заголовка Min-SE (напомним, что по умолчанию оно равно 90 секундам, когда поле заголовка Min-SE отсутствует), прокси НЕ ДОЛЖЕН увеличивать значение поля заголовка Session-Expires. Если значение поля заголовка Session-Expires меньше значения поля заголовка Min-SE (возможно, потому что прокси увеличил значение поля заголовка Min-SE, как описано ниже), прокси ДОЛЖЕН увеличить значение поля заголовка Session-Expires, чтобы сделать его равным значению поля заголовка Min-SE. Прокси НЕ ДОЛЖЕН вставлять или изменять значение параметра «refresher» в поле заголовка Session-Expires.
If the request contains a Supported header field with a value 'timer', the proxy MAY reject the INVITE request with a 422 (Session Interval Too Small) response if the session interval in the Session-Expires header field is smaller than the minimum interval defined by the proxy's local policy. When sending the 422 response, the proxy MUST include a Min-SE header field with the value of its minimum interval. That minimum MUST NOT be lower than 90 seconds.
Если запрос содержит поле заголовка Supported со значением «timer», прокси МОЖЕТ отклонить запрос INVITE ответом 422 (Session Interval Too Small), если интервал сессии в поле заголовка Session-Expires меньше минимального интервала, определённого локальной политикой прокси. При отправке ответа 422 прокси ДОЛЖЕН включить поле заголовка Min-SE со значением своего минимального интервала. Этот минимум НЕ ДОЛЖЕН быть меньше 90 секунд.
If the request doesn't indicate support for the session timer but contains a session interval that is too small, the proxy cannot usefully reject the request, as this would result in a call failure. Rather, the proxy SHOULD insert a Min-SE header field containing its minimum interval. If a Min-SE header field is already present, the proxy SHOULD increase (but MUST NOT decrease) the value to its minimum interval. The proxy MUST then increase the Session-Expires header field value to be equal to the value in the Min-SE header field, as described above. A proxy MUST NOT insert a Min-SE header field or modify the value of an existing header field in a proxied request if that request contains a Supported header field with the value 'timer'. This is needed to protect against certain denial of service attacks, described in Section 11.
Если запрос не указывает на поддержку таймера сессии, но содержит слишком малый интервал сессии, прокси не может с пользой отклонить запрос, поскольку это привело бы к сбою вызова. Вместо этого прокси СЛЕДУЕТ вставить поле заголовка Min-SE, содержащее его минимальный интервал. Если поле заголовка Min-SE уже присутствует, прокси СЛЕДУЕТ увеличить (но НЕ ДОЛЖЕН уменьшать) значение до своего минимального интервала. Затем прокси ДОЛЖЕН увеличить значение поля заголовка Session-Expires, чтобы оно было равно значению в поле заголовка Min-SE, как описано выше. Прокси НЕ ДОЛЖЕН вставлять поле заголовка Min-SE или изменять значение существующего поля заголовка в проксируемом запросе, если этот запрос содержит поле заголовка Supported со значением «timer». Это необходимо для защиты от некоторых атак типа «отказ в обслуживании», описанных в разделе 11.
Assuming that the proxy has requested a session timer (and thus has possibly inserted the Session-Expires header field or reduced it), the proxy MUST remember that it is using a session timer, and also remember the value of the Session-Expires header field from the proxied request. This MUST be remembered for the duration of the transaction.
Предполагая, что прокси запросил таймер сессии (и, следовательно, возможно, вставил поле заголовка Session-Expires или уменьшил его), прокси ДОЛЖЕН запомнить, что он использует таймер сессии, а также запомнить значение поля заголовка Session-Expires из проксируемого запроса. Это ДОЛЖНО запоминаться на время транзакции.
The proxy MUST remember, for the duration of the transaction, whether the request contained the Supported header field with the value 'timer'. If the request did not contain a Supported header field with the value 'timer', the proxy MAY insert a Require header field with the value 'timer' into the request. However, this is NOT RECOMMENDED. This allows the proxy to insist on a session timer for the session. This header field is not needed if a Supported header field was in the request; in this case, the proxy would already be sure the session timer can be used for the session.
Прокси ДОЛЖЕН на время транзакции запомнить, содержал ли запрос поле заголовка Supported со значением «timer». Если запрос не содержал поля заголовка Supported со значением «timer», прокси МОЖЕТ вставить в запрос поле заголовка Require со значением «timer». Однако это НЕ РЕКОМЕНДУЕТСЯ. Это позволяет прокси настоять на таймере сессии для сессии. Это поле заголовка не нужно, если в запросе было поле заголовка Supported; в этом случае прокси уже был бы уверен, что таймер сессии можно использовать для сессии.
8.2. Processing of Responses
8.2. Обработка ответов
When the final response to the request arrives, it is examined by the proxy.
Когда приходит окончательный ответ на запрос, прокси его анализирует.
If the response does not contain a Session-Expires header field but the proxy remembers that it requested a session timer in the request (by inserting, modifying, or examining and accepting the Session-Expires header field in the proxied request), this means that the UAS did not support the session timer. If the proxy remembers that the UAC did not support the session timer either, the proxy forwards the response upstream normally. There is no session expiration for this session. If, however, the proxy remembers that the UAC did support the session timer, additional processing is needed.
Если ответ не содержит поля заголовка Session-Expires, но прокси помнит, что запросил таймер сессии в запросе (вставив, изменив или проверив и приняв поле заголовка Session-Expires в проксируемом запросе), это означает, что UAS не поддерживает таймер сессии. Если прокси помнит, что UAC тоже не поддерживает таймер сессии, прокси обычным образом пересылает ответ вверх по цепочке. Для этой сессии истечения сессии нет. Если же прокси помнит, что UAC поддерживал таймер сессии, требуется дополнительная обработка.
Because there is no Session-Expires or Require header field in the response, the proxy knows that it is the first session-timer-aware proxy to receive the response. This proxy MUST insert a Session-Expires header field into the response with the value it remembered from the forwarded request. It MUST set the value of the 'refresher' parameter to 'uac'. The proxy MUST add the 'timer' option tag to any Require header field in the response, and if none was present, add the Require header field with that value before forwarding it upstream.
Поскольку в ответе нет поля заголовка Session-Expires или Require, прокси знает, что он первый прокси, поддерживающий таймер сессии, получивший этот ответ. Этот прокси ДОЛЖЕН вставить в ответ поле заголовка Session-Expires со значением, которое он запомнил из пересланного запроса. Он ДОЛЖЕН установить значение параметра «refresher» в «uac». Прокси ДОЛЖЕН добавить тег опции «timer» в любое поле заголовка Require в ответе, а если такого не было, добавить поле заголовка Require с этим значением перед пересылкой ответа вверх по цепочке.
If the received response contains a Session-Expires header field, no modification of the response is needed.
Если полученный ответ содержит поле заголовка Session-Expires, никаких изменений ответа не требуется.
In all cases, if the 2xx response forwarded upstream by the proxy contains a Session-Expires header field, its value represents the session interval for the session associated with that response. The proxy computes the session expiration as the time when the 2xx response is forwarded upstream, plus the session interval. This session expiration MUST update any existing session expiration for the session. The refresher parameter in the Session-Expires header field in the 2xx response forwarded upstream will be present, and it indicates which UA is performing the refreshes. There can be multiple 2xx responses to a single INVITE, each representing a different dialog, resulting in multiple session expirations, one for each session associated with each dialog.
Во всех случаях, если ответ 2xx, пересылаемый прокси вверх по цепочке, содержит поле заголовка Session-Expires, его значение представляет интервал сессии для сессии, связанной с этим ответом. Прокси вычисляет момент истечения сессии как время, когда ответ 2xx пересылается вверх по цепочке, плюс интервал сессии. Этот момент истечения сессии ДОЛЖЕН обновить любой существующий момент истечения сессии для сессии. Параметр refresher в поле заголовка Session-Expires в ответе 2xx, пересылаемом вверх по цепочке, будет присутствовать, и он указывает, какой UA выполняет обновления. На один INVITE может приходиться несколько ответов 2xx, каждый из которых представляет отдельный диалог, что приводит к нескольким моментам истечения сессии — по одному для каждой сессии, связанной с каждым диалогом.
The proxy MUST NOT modify the value of the Session-Expires header field received in the response (assuming one was present) before forwarding it upstream.
Прокси НЕ ДОЛЖЕН изменять значение поля заголовка Session-Expires, полученного в ответе (при условии, что оно присутствовало), перед пересылкой ответа вверх по цепочке.
8.3. Session Expiration
8.3. Истечение сессии
When the current time equals or passes the session expiration for a session, the proxy MAY remove associated call state, and MAY free any resources associated with the call. Unlike the UA, it MUST NOT send a BYE.
Когда текущее время равно моменту истечения сессии или превышает его, прокси МОЖЕТ удалить связанное состояние вызова и МОЖЕТ освободить любые ресурсы, связанные с вызовом. В отличие от UA, он НЕ ДОЛЖЕН отправлять BYE.
9. UAS Behavior
9. Поведение UAS
The UAS must respond to a request for a session timer by the UAC or a proxy in the path of the request, or it may request that a session timer be used itself.
UAS должен отвечать на запрос таймера сессии, поступивший от UAC или от прокси на пути запроса, либо может сам запросить использование таймера сессии.
If an incoming request contains a Supported header field with a value 'timer' and a Session Expires header field, the UAS MAY reject the INVITE request with a 422 (Session Interval Too Small) response if the session interval in the Session-Expires header field is smaller than the minimum interval defined by the UAS' local policy. When sending the 422 response, the UAS MUST include a Min-SE header field with the value of its minimum interval. This minimum interval MUST NOT be lower than 90 seconds.
Если входящий запрос содержит поле заголовка Supported со значением «timer» и поле заголовка Session-Expires, UAS МОЖЕТ отклонить запрос INVITE ответом 422 (Session Interval Too Small), если интервал сессии в поле заголовка Session-Expires меньше минимального интервала, определённого локальной политикой UAS. При отправке ответа 422 UAS ДОЛЖЕН включить поле заголовка Min-SE со значением своего минимального интервала. Этот минимальный интервал НЕ ДОЛЖЕН быть меньше 90 секунд.
If the UAS wishes to accept the request, it copies the value of the Session-Expires header field from the request into the 2xx response. The UAS response MAY reduce its value but MUST NOT set it to a duration lower than the value in the Min-SE header field in the request, if it is present; otherwise the UAS MAY reduce its value but MUST NOT set it to a duration lower than 90 seconds. The UAS MUST NOT increase the value of the Session-Expires header field.
Если UAS желает принять запрос, он копирует значение поля заголовка Session-Expires из запроса в ответ 2xx. Ответ UAS МОЖЕТ уменьшать это значение, но НЕ ДОЛЖЕН устанавливать его в длительность ниже значения в поле заголовка Min-SE в запросе, если оно присутствует; в противном случае UAS МОЖЕТ уменьшать его значение, но НЕ ДОЛЖЕН устанавливать его в длительность ниже 90 секунд. UAS НЕ ДОЛЖЕН увеличивать значение поля заголовка Session-Expires.
If the incoming request contains a Supported header field with a value 'timer' but does not contain a Session-Expires header, it means that the UAS is indicating support for timers but is not requesting one. The UAS may request a session timer in the 2XX response by including a Session-Expires header field. The value MUST NOT be set to a duration lower than the value in the Min-SE header field in the request, if it is present.
Если входящий запрос содержит поле заголовка Supported со значением «timer», но не содержит поля заголовка Session-Expires, это означает, что UAS указывает на поддержку таймеров, но не запрашивает его. UAS может запросить таймер сессии в ответе 2XX, включив поле заголовка Session-Expires. Значение НЕ ДОЛЖНО устанавливаться в длительность ниже значения в поле заголовка Min-SE в запросе, если оно присутствует.
The UAS MUST set the value of the refresher parameter in the Session-Expires header field in the 2xx response. This value specifies who will perform refreshes for the dialog. The value is based on the value of this parameter in the request, and on whether the UAC supports the session timer extension. A value of 'NA' in the third column means that this particular combination shouldn't happen, as it is disallowed by the protocol.
UAS ДОЛЖЕН установить значение параметра refresher в поле заголовка Session-Expires в ответе 2xx. Это значение определяет, кто будет выполнять обновления для диалога. Значение основывается на значении этого параметра в запросе и на том, поддерживает ли UAC расширение таймера сессии. If the refresher parameter in the Session-Expires header field in the 2xx response has a value of 'uac', the UAS MUST place a Require header field into the response with the value 'timer'. This is because the uac is performing refreshes and the response has to be processed for the UAC to know this. If the refresher parameter in the 2xx response has a value of 'uas' and the Supported header field in the request contained the value 'timer', the UAS SHOULD place a Require header field into the response with the value 'timer'. In this case, the UAC is not refreshing, but it is supposed to send a BYE if it never receives a refresh. Since the call will still succeed without the UAC sending a BYE, insertion of the Require is a SHOULD here, and not a MUST.
Если параметр refresher в поле заголовка Session-Expires в ответе 2xx имеет значение «uac», UAS ДОЛЖЕН поместить в ответ поле заголовка Require со значением «timer». Это объясняется тем, что обновления выполняет uac и ответ должен быть обработан, чтобы UAC узнал об этом. Если параметр refresher в ответе 2xx имеет значение «uas», а поле заголовка Supported в запросе содержало значение «timer», UAS СЛЕДУЕТ поместить в ответ поле заголовка Require со значением «timer». В этом случае обновления выполняет не UAC, но он должен отправить BYE, если так и не получит обновления. Поскольку вызов всё равно завершится успешно и без отправки BYE со стороны UAC, вставка Require здесь является SHOULD, а не MUST.
Just like the UAC, the UAS stores state for the session timer. This state includes the session interval, the session expiration, and the identity of the refresher. This state is bound to the dialog used to set up the session. The session interval is set to the value of the delta-time from the Session-Expires header field in the most recent 2xx response to a session refresh request on that dialog. It also remembers whether it or its peer is the refresher on the dialog, based on the value of the refresher parameter from the most recent 2xx response to a session refresh request on that dialog. If the most recent 2xx response had no Session-Expires header field, there is no session expiration, and no refreshes have to be performed.
Подобно UAC, UAS хранит состояние для таймера сессии. Это состояние включает интервал сессии, момент истечения сессии и идентичность refresher. Это состояние привязано к диалогу, использованному для установления сессии. Интервал сессии устанавливается в значение delta-time из поля заголовка Session-Expires в самом последнем ответе 2xx на запрос обновления сессии в этом диалоге. Он также запоминает, является ли refresher он сам или его партнёр в диалоге, исходя из значения параметра refresher из самого последнего ответа 2xx на запрос обновления сессии в этом диалоге. Если в самом последнем ответе 2xx не было поля заголовка Session-Expires, истечения сессии нет и обновления выполнять не нужно.
If the UAS must refresh the session, it computes the session expiration. The session expiration is the time of transmission of the last 2xx response to a session refresh request on that dialog plus the session interval. If UA wishes to continue with the session beyond the session expiration, it MUST generate a refresh before the session expiration. It is RECOMMENDED that this refresh be sent once half the session interval has elapsed. Additional procedures for this refresh are described in Section 10.
Если UAS должен обновлять сессию, он вычисляет момент истечения сессии. Момент истечения сессии — это время отправки последнего ответа 2xx на запрос обновления сессии в этом диалоге плюс интервал сессии. Если UA желает продолжить сессию после момента её истечения, он ДОЛЖЕН сформировать обновление до наступления этого момента. РЕКОМЕНДУЕТСЯ отправлять это обновление, когда прошла половина интервала сессии. Дополнительные процедуры для этого обновления описаны в разделе 10.
10. Performing Refreshes
10. Выполнение обновлений
The side generating a refresh does so according to the UAC procedures defined in Section 7. Note that only a 2xx response to a session refresh request extends the session expiration. This means that a UA could attempt a refresh and receive a 422 response with a Min-SE header field that contains a value much larger than the current session interval. The UA will still have to send a session refresh request before the session expiration (which has not changed), even though this request will contain a value of the Session-Expires that is much larger than the current session interval.
Сторона, формирующая обновление, делает это согласно процедурам UAC, определённым в разделе 7. Отметим, что только ответ 2xx на запрос обновления сессии продлевает момент истечения сессии. Это означает, что UA может попытаться выполнить обновление и получить ответ 422 с полем заголовка Min-SE, содержащим значение, намного большее текущего интервала сессии. UA всё равно должен будет отправить запрос обновления сессии до момента истечения сессии (который не изменился), даже если этот запрос будет содержать значение Session-Expires, намного большее текущего интервала сессии.
If the session refresh request transaction times out or generates a 408 or 481 response, then the UAC sends a BYE request as per Section 12.2.1.2 of RFC 3261 [2]. If the session refresh request does not generate a 2xx response (and, as a result, the session is not refreshed), and a response other than 408 or 481 is received, the UAC SHOULD follow the rules specific to that response code and retry if possible. For example, if the response is a 401, the UAC would retry the request with new credentials. However, the UAC SHOULD NOT continuously retry the request if the server indicates the same error response.
Если транзакция запроса обновления сессии завершается тайм-аутом или порождает ответ 408 или 481, UAC отправляет запрос BYE в соответствии с разделом 12.2.1.2 RFC 3261 [2]. Если запрос обновления сессии не порождает ответ 2xx (и, как следствие, сессия не обновляется), а получен ответ, отличный от 408 или 481, UAC СЛЕДУЕТ соблюдать правила, специфичные для этого кода ответа, и повторить попытку, если это возможно. Например, если ответ — 401, UAC повторит запрос с новыми учётными данными. Однако UAC НЕ СЛЕДУЕТ непрерывно повторять запрос, если сервер указывает тот же ответ об ошибке.
Similarly, if the side not performing refreshes does not receive a session refresh request before the session expiration, it SHOULD send a BYE to terminate the session, slightly before the session expiration. The minimum of 32 seconds and one third of the session interval is RECOMMENDED.
Аналогично, если сторона, не выполняющая обновления, не получила запрос обновления сессии до момента истечения сессии, ей СЛЕДУЕТ отправить BYE для завершения сессии немного раньше этого момента. РЕКОМЕНДУЕТСЯ минимум из 32 секунд и одной трети интервала сессии.
Firewalls and NAT ALGs may be very unforgiving about allowing SIP traffic to pass after the expiration time of the session. This is why the BYE should be sent before the expiration.
Межсетевые экраны и ALG для NAT могут быть очень нетерпимы к пропуску трафика SIP после момента истечения сессии. Именно поэтому BYE следует отправлять до истечения.
11. Security Considerations
11. Вопросы безопасности
The session timer introduces the capability of a proxy or UA element to force compliant UAs to send refreshes at a rate of the element's choosing. This introduces the possibility of denial-of-service attacks with significant amplification properties. These attacks can be launched from 'outsiders' (elements that attempt to modify messages in transit) or by 'insiders' (elements that are legitimately in the request path but are intent on doing harm). Fortunately, both cases are adequately handled by this specification.
Таймер сессии вводит возможность для прокси или элемента UA принуждать совместимые UA отправлять обновления с частотой, выбираемой этим элементом. Это создаёт возможность атак типа «отказ в обслуживании» со значительными усилительными свойствами. Такие атаки могут запускаться «извне» (элементами, которые пытаются изменять сообщения в пути) или «изнутри» (элементами, которые законно находятся на пути запроса, но намерены причинить вред). К счастью, оба случая должным образом обрабатываются настоящей спецификацией.
11.1. Inside Attacks
11.1. Атаки изнутри
This introduces the possibility of rogue proxies or UAs introducing denial-of-service attacks. However, the mechanisms in this specification prevent that from happening.
Это создаёт возможность того, что недобросовестные прокси или UA будут инициировать атаки типа «отказ в обслуживании». Однако механизмы настоящей спецификации препятствуют этому.
First, consider the case of a rogue UAC that wishes to force a UAS to generate refreshes at a rapid rate. To do so, it inserts a Session-Expires header field into an INVITE with a low duration and a refresher parameter equal to uas. Assume it places a Supported header field into the request. The UAS or any proxy that objects to this low timer will reject the request with a 422, thereby preventing the attack. If no Supported header field was present, the proxies will insert a Min-SE header field into the request before forwarding it. As a result, the UAS will not choose a session timer lower than the minimum allowed by all elements on the path. This too prevents the attack.
Сначала рассмотрим случай недобросовестного UAC, который желает заставить UAS формировать обновления с высокой частотой. Для этого он вставляет в INVITE поле заголовка Session-Expires с малой длительностью и параметром refresher, равным uas. Предположим, он поместил в запрос поле заголовка Supported. UAS или любой прокси, возражающий против такого малого таймера, отклонит запрос ответом 422, тем самым предотвратив атаку. Если поля заголовка Supported не было, прокси вставят в запрос поле заголовка Min-SE перед его пересылкой. В результате UAS не выберет таймер сессии меньше минимума, допустимого всеми элементами на пути. Это также предотвращает атаку.
Next, consider the case of a rogue UAS that wishes to force a UAC to generate refreshes at a rapid rate. In that case, the UAC has to support session timer. The initial INVITE arrives at the rogue UAS, which returns a 2xx with a very small session interval. The UAC uses this timer and quickly sends a refresh. Section 7.4 requires that the UAC copy the current session interval into the Session-Expires header field in the request. This enables the proxies to see the current value. The proxies will reject this request and provide a Min-SE with a higher minimum, which the UAC will then use. Note, that if the proxies did not reject the request, but rather proxied the request with a Min-SE header field, an attack would still be possible. The UAS could discard this header field in a 2xx response and force the UAC to continue to generate rapid requests.
Затем рассмотрим случай недобросовестного UAS, который желает заставить UAC формировать обновления с высокой частотой. В этом случае UAC должен поддерживать таймер сессии. Первоначальный INVITE приходит к недобросовестному UAS, который возвращает 2xx с очень малым интервалом сессии. UAC использует этот таймер и быстро отправляет обновление. Раздел 7.4 требует, чтобы UAC скопировал текущий интервал сессии в поле заголовка Session-Expires в запросе. Это позволяет прокси увидеть текущее значение. Прокси отклонят этот запрос и предоставят Min-SE с более высоким минимумом, который UAC затем использует. Отметим, что если бы прокси не отклонили запрос, а проксировали его с полем заголовка Min-SE, атака всё ещё была бы возможна. UAS мог бы отбросить это поле заголовка в ответе 2xx и заставить UAC продолжать формировать частые запросы.
In a similar fashion, a rogue proxy cannot force either the UAC or UAS to generate refreshes unless the proxy remains on the signaling path and sees every request and response.
Подобным образом недобросовестный прокси не может заставить ни UAC, ни UAS формировать обновления, если только прокси не остаётся на пути сигнализации и не видит каждый запрос и ответ.
11.2. Outside Attacks
11.2. Атаки извне
An element that can observe and modify a request or response in transit can force rapid session refreshes. To prevent this, requests and responses have to be protected by message integrity. Since the session timer header fields are not end-to-end and are manipulated by proxies, the SIP S/MIME capabilities are not suitable for this task. Rather, integrity has to be protected by using hop-by-hop mechanisms. As a result, it is RECOMMENDED that an element send a request with a Session-Expires header field or a Supported header field with the value 'timer' by using TLS. As adequate protection is obtained only if security is applied on each hop, it is RECOMMENDED that the SIPS URI scheme be used in conjunction with this extension. This means that proxies that record-route and request session timer SHOULD record-route with a SIPS URI. A UA that inserts a Session-Expires header into a request or response SHOULD include a Contact URI that is a SIPS URI.
Элемент, способный наблюдать и изменять запрос или ответ в пути, может принудительно вызвать частые обновления сессии. Чтобы предотвратить это, запросы и ответы должны быть защищены целостностью сообщений. Поскольку поля заголовка таймера сессии не являются сквозными и обрабатываются прокси, возможности S/MIME в SIP для этой задачи не подходят. Скорее, целостность должна защищаться с помощью механизмов «переход-за-переходом» (hop-by-hop). В результате РЕКОМЕНДУЕТСЯ, чтобы элемент отправлял запрос с полем заголовка Session-Expires или полем заголовка Supported со значением «timer», используя TLS. Поскольку достаточная защита достигается, только если безопасность применяется на каждом переходе, РЕКОМЕНДУЕТСЯ использовать схему URI SIPS вместе с этим расширением. Это означает, что прокси, выполняющие record-route и запрашивающие таймер сессии, СЛЕДУЕТ выполнять record-route с URI SIPS. UA, вставляющий поле заголовка Session-Expires в запрос или ответ, СЛЕДУЕТ включать URI Contact, являющийся URI SIPS.
