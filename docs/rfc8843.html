Negotiating Media Multiplexing Using the Session Description Protocol (SDP)
Согласование мультиплексирования медиа с помощью протокола описания сессий (SDP)
Abstract
Аннотация
This specification defines a new Session Description Protocol (SDP) Grouping Framework extension called 'BUNDLE'. The extension can be used with the SDP offer/answer mechanism to negotiate the usage of a single transport (5-tuple) for sending and receiving media described by multiple SDP media descriptions ("m=" sections). Such transport is referred to as a BUNDLE transport, and the media is referred to as bundled media. The "m=" sections that use the BUNDLE transport form a BUNDLE group.
Настоящая спецификация определяет новое расширение механизма группировки SDP (Session Description Protocol) под названием 'BUNDLE'. Расширение может использоваться с механизмом «предложение/ответ» SDP для согласования использования одного транспорта (5-кортежа) для отправки и приёма медиа, описываемых несколькими описаниями медиа SDP (секциями «m=»). Такой транспорт называется BUNDLE-транспортом, а медиа — связанными (bundled) медиа. Секции «m=», использующие BUNDLE-транспорт, образуют BUNDLE-группу.
This specification defines a new RTP Control Protocol (RTCP) Source Description (SDES) item and a new RTP header extension.
Настоящая спецификация определяет новый элемент SDES (Source Description) протокола RTCP и новое расширение заголовка RTP.
This specification updates RFCs 3264, 5888, and 7941.
Настоящая спецификация обновляет RFC 3264, 5888 и 7941.

1. Introduction
1. Введение
1.1. Background
1.1. Предыстория
When the SDP offer/answer mechanism [RFC3264] is used to negotiate the establishment of multimedia communication sessions, if separate transports (5-tuples) are negotiated for each individual media stream, each transport consumes additional resources (especially when Interactive Connectivity Establishment (ICE) [RFC8445] is used). For this reason, it is attractive to use a single transport for multiple media streams.
Когда механизм «предложение/ответ» SDP [RFC3264] используется для согласования установления сеансов мультимедийной связи, если для каждого отдельного медиапотока согласуются отдельные транспорты (5-кортежи), каждый транспорт потребляет дополнительные ресурсы (особенно при использовании механизма Interactive Connectivity Establishment (ICE) [RFC8445]). По этой причине привлекательно использовать один транспорт для нескольких медиапотоков.
1.2. BUNDLE Mechanism
1.2. Механизм BUNDLE
This specification defines a way to use a single transport (BUNDLE transport) for sending and receiving media (bundled media) described by multiple SDP media descriptions ("m=" sections). The address:port combination used by an endpoint for sending and receiving bundled media is referred to as the BUNDLE address:port. The set of SDP attributes that are applied to each "m=" section within a BUNDLE group is referred to as BUNDLE attributes. The same BUNDLE transport is used for sending and receiving bundled media, which means that the symmetric Real-time Transport Protocol (RTP) mechanism [RFC4961] is always used for RTP-based bundled media.
Настоящая спецификация определяет способ использования одного транспорта (BUNDLE-транспорта) для отправки и приёма медиа (связанных медиа), описываемых несколькими описаниями медиа SDP (секциями «m=»). Комбинация адрес:порт, используемая конечной точкой для отправки и приёма связанных медиа, называется BUNDLE-адресом:портом. Набор атрибутов SDP, применяемых к каждой секции «m=» в BUNDLE-группе, называется BUNDLE-атрибутами. Один и тот же BUNDLE-транспорт используется для отправки и приёма связанных медиа, что означает, что для связанных медиа на основе RTP всегда используется механизм симметричного Real-time Transport Protocol (RTP) [RFC4961].
This specification defines a new SDP Grouping Framework [RFC5888] extension called 'BUNDLE'. The extension can be used with the Session Description Protocol (SDP) Offer/Answer mechanism [RFC3264] to negotiate which "m=" sections will become part of a BUNDLE group. In addition, the offerer and answerer [RFC3264] use the BUNDLE extension to negotiate the BUNDLE addresses:ports (offerer BUNDLE address:port and answerer BUNDLE address:port) and the set of BUNDLE attributes (offerer BUNDLE attributes and answerer BUNDLE attributes) that will be applied to each "m=" section within the BUNDLE group.
Настоящая спецификация определяет новое расширение механизма группировки SDP [RFC5888] под названием 'BUNDLE'. Расширение может использоваться с механизмом «предложение/ответ» SDP [RFC3264] для согласования того, какие секции «m=» станут частью BUNDLE-группы. Кроме того, инициатор предложения и отвечающая сторона [RFC3264] используют расширение BUNDLE для согласования BUNDLE-адресов:портов (BUNDLE-адрес:порт инициатора и BUNDLE-адрес:порт отвечающей стороны) и набора BUNDLE-атрибутов (BUNDLE-атрибуты инициатора и BUNDLE-атрибуты отвечающей стороны), которые будут применяться к каждой секции «m=» в BUNDLE-группе.
The use of a BUNDLE transport allows the usage of a single set of ICE [RFC8445] candidates for the whole BUNDLE group.
Использование BUNDLE-транспорта позволяет задействовать один набор кандидатов ICE [RFC8445] для всей BUNDLE-группы.
A given BUNDLE address:port MUST only be associated with a single BUNDLE group. If an SDP offer or SDP answer (hereafter referred to as "offer" and "answer") contains multiple BUNDLE groups, the procedures in this specification apply to each group independently. All RTP-based bundled media associated with a given BUNDLE group belong to a single RTP session [RFC3550].
Данный BUNDLE-адрес:порт ДОЛЖЕН быть связан только с одной BUNDLE-группой. Если предложение или ответ SDP (далее — «предложение» и «ответ») содержит несколько BUNDLE-групп, процедуры настоящей спецификации применяются к каждой группе независимо. Все связанные медиа на основе RTP, относящиеся к данной BUNDLE-группе, принадлежат одному сеансу RTP [RFC3550].
The BUNDLE extension is backward compatible. Endpoints that do not support the extension are expected to generate offers and answers without an SDP 'group:BUNDLE' attribute and assign a unique address:port to each "m=" section within an offer and answer, according to the procedures in [RFC3264] and [RFC4566].
Расширение BUNDLE обратно совместимо. Ожидается, что конечные точки, не поддерживающие расширение, будут формировать предложения и ответы без атрибута SDP 'group:BUNDLE' и назначать уникальный адрес:порт каждой секции «m=» в предложении и ответе согласно процедурам [RFC3264] и [RFC4566].
1.3. Protocol Extensions
1.3. Расширения протокола
In addition to defining the new SDP Grouping Framework extension, this specification defines the following protocol extensions and RFC updates. This specification:
Помимо определения нового расширения механизма группировки SDP, настоящая спецификация определяет следующие расширения протокола и обновления RFC. Настоящая спецификация:
* defines a new SDP attribute, 'bundle-only', which can be used to request that a specific "m=" section (and the associated media) be used only if kept within a BUNDLE group.
* определяет новый атрибут SDP 'bundle-only', который может использоваться для запроса, чтобы конкретная секция «m=» (и связанные медиа) использовалась только при сохранении в BUNDLE-группе.
* updates RFC 3264 [RFC3264], to also allow assigning a zero port value to an "m=" section in cases where the media described by the "m=" section is not disabled or rejected.
* обновляет RFC 3264 [RFC3264], чтобы также разрешить назначение нулевого значения порта секции «m=» в случаях, когда медиа, описываемые секцией «m=», не отключены и не отклонены.
* defines a new RTCP [RFC3550] SDES item, 'MID', and a new RTP SDES header extension that can be used to associate RTP streams with "m=" sections.
* определяет новый элемент SDES 'MID' протокола RTCP [RFC3550] и новое расширение заголовка RTP SDES, которое может использоваться для сопоставления потоков RTP с секциями «m=».
* updates [RFC7941] by adding an exception, for the MID RTP header extension, to the requirement regarding protection of an SDES RTP header extension carrying an SDES item for the MID RTP header extension.
* обновляет [RFC7941], добавляя исключение для расширения заголовка RTP MID в требование о защите расширения заголовка RTP SDES, несущего элемент SDES для расширения заголовка RTP MID.
1.4. Contradiction regarding bundle-only "m=" sections
1.4. Противоречие относительно секций «m=» bundle-only
Since the approval of the WebRTC specification documents, the IETF has become aware of an inconsistency between the document specifying JSEP and the document specifying BUNDLE (RFC 8829 and this RFC, respectively). Rather than delaying publication further to come to a resolution, the documents are being published as they were originally approved. The IETF intends to restart work on these technologies, and revised versions of these documents will be published as soon as a resolution becomes available.
После утверждения документов спецификации WebRTC IETF стало известно о несоответствии между документом, определяющим JSEP, и документом, определяющим BUNDLE (RFC 8829 и настоящий RFC соответственно). Вместо дальнейшей задержки публикации для достижения решения документы публикуются в том виде, в каком они были изначально утверждены. IETF намерена возобновить работу над этими технологиями, и пересмотренные версии этих документов будут опубликованы, как только будет найдено решение.
The specific issue involves the handling of "m=" sections that are designated as bundle-only, as discussed in [RFC8829], Section 4.1.1. Currently, there is divergence between JSEP and BUNDLE, as well as between these specifications and existing browser implementations:
Конкретная проблема касается обработки секций «m=», обозначенных как bundle-only, как обсуждается в [RFC8829], раздел 4.1.1. В настоящее время существует расхождение между JSEP и BUNDLE, а также между этими спецификациями и существующими реализациями браузеров:
* JSEP prescribes that said "m=" sections should use port zero and add an "a=bundle-only" attribute in initial offers, but not in answers or subsequent offers.
* JSEP предписывает, чтобы указанные секции «m=» использовали нулевой порт и добавляли атрибут «a=bundle-only» в начальных предложениях, но не в ответах или последующих предложениях.
* BUNDLE prescribes that these "m=" sections should be marked as described in the previous point, but in all offers and answers.
* BUNDLE предписывает, чтобы эти секции «m=» были помечены, как описано в предыдущем пункте, но во всех предложениях и ответах.
* Most current browsers do not mark any "m=" sections with port zero and instead use the same port for all bundled "m=" sections; some others follow the JSEP behavior.
* Большинство современных браузеров не помечают секции «m=» нулевым портом, а используют один и тот же порт для всех связанных секций «m=»; некоторые другие следуют поведению JSEP.
2. Terminology
2. Терминология
"m=" section: SDP bodies contain one or more media descriptions, referred to as "m=" sections. Each "m=" section is represented by an SDP "m=" line and zero or more SDP attributes associated with the "m=" line. A local address:port combination is assigned to each "m=" section.
секция «m=»: Тела SDP содержат одно или несколько описаний медиа, называемых секциями «m=». Каждая секция «m=» представлена строкой SDP «m=», а также нулём или более атрибутами SDP, связанными с этой строкой «m=». Каждой секции «m=» назначается локальная комбинация адрес:порт.
5-tuple: A collection of the following values: source address, source port, destination address, destination port, and transport-layer protocol.
5-кортеж: Совокупность следующих значений: адрес источника, порт источника, адрес назначения, порт назначения и используемый протокол транспортного уровня.
Unique address:port: An address:port combination that is assigned to only one "m=" section in an offer or answer.
Уникальный адрес:порт: Комбинация адрес:порт, которая назначается только одной секции «m=» в предложении или ответе.
Offerer BUNDLE-tag: The first identification-tag in a given SDP 'group:BUNDLE' attribute identification-tag list in an offer.
BUNDLE-тег инициатора: Первый identification-tag в заданном списке identification-tag атрибута SDP 'group:BUNDLE' в предложении.
Answerer BUNDLE-tag: The first identification-tag in a given SDP 'group:BUNDLE' attribute identification-tag list in an answer.
BUNDLE-тег отвечающей стороны: Первый identification-tag в списке identification-tag атрибута SDP 'group:BUNDLE' в ответе.
Suggested offerer-tagged "m=" section: The bundled "m=" section identified by the offerer BUNDLE-tag in an initial BUNDLE offer, before a BUNDLE group has been negotiated.
Предлагаемая секция «m=» с тегом инициатора: Связанная секция «m=», идентифицируемая BUNDLE-тегом инициатора в начальном BUNDLE-предложении, до согласования BUNDLE-группы.
Offerer-tagged "m=" section: The bundled "m=" section identified by the offerer BUNDLE-tag in a subsequent offer. The "m=" section contains characteristics (offerer BUNDLE address:port and offerer BUNDLE attributes) that are applied to each "m=" section within the BUNDLE group.
Секция «m=» с тегом инициатора: Связанная секция «m=», идентифицируемая BUNDLE-тегом инициатора в последующем предложении. Секция «m=» содержит характеристики (BUNDLE-адрес:порт инициатора и BUNDLE-атрибуты инициатора), которые применяются к каждой секции «m=» в BUNDLE-группе.
Answerer-tagged "m=" section: The bundled "m=" section identified by the answerer BUNDLE-tag in an answer (initial BUNDLE answer or subsequent). The "m=" section contains characteristics (answerer BUNDLE address:port and answerer BUNDLE attributes) that are applied to each "m=" section within the BUNDLE group.
Секция «m=» с тегом отвечающей стороны: Связанная секция «m=», идентифицируемая BUNDLE-тегом отвечающей стороны в ответе (начальном BUNDLE-ответе или последующем). Секция «m=» содержит характеристики (BUNDLE-адрес:порт отвечающей стороны и BUNDLE-атрибуты отвечающей стороны), которые применяются к каждой секции «m=» в BUNDLE-группе.
BUNDLE address:port: An address:port combination that an endpoint uses for sending and receiving bundled media.
BUNDLE-адрес:порт: Комбинация адрес:порт, которую конечная точка использует для отправки и приёма связанных медиа.
Offerer BUNDLE address:port: The address:port combination used by the offerer for sending and receiving media.
BUNDLE-адрес:порт инициатора: Комбинация адрес:порт, которая используется инициатором для отправки и приёма медиа.
Answerer BUNDLE address:port: The address:port combination used by the answerer for sending and receiving media.
BUNDLE-адрес:порт отвечающей стороны: Комбинация адрес:порт, используемая отвечающей стороной для отправки и приёма медиа.
BUNDLE attributes: IDENTICAL and TRANSPORT multiplexing category SDP attributes. Once a BUNDLE group has been created, the attribute values apply to each bundled "m=" section within the BUNDLE group.
BUNDLE-атрибуты: Атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT. После того как BUNDLE-группа создана, значения атрибутов применяются к каждой связанной секции «m=» в BUNDLE-группе.
Offerer BUNDLE attributes: IDENTICAL and TRANSPORT multiplexing category SDP attributes included in the offerer-tagged "m=" section.
BUNDLE-атрибуты инициатора: Атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT, включённые в секцию «m=» с тегом инициатора.
Answerer BUNDLE attributes: IDENTICAL and TRANSPORT multiplexing category SDP attributes included in the answerer-tagged "m=" section.
BUNDLE-атрибуты отвечающей стороны: Атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT, включённые в секцию «m=» с тегом отвечающей стороны.
BUNDLE transport: The transport (5-tuple) used by all media described by the "m=" sections within a BUNDLE group.
BUNDLE-транспорт: Транспорт (5-кортеж), который используется всеми медиа, описываемыми секциями «m=» в BUNDLE-группе.
BUNDLE group: A set of bundled "m=" sections, created using an SDP offer/answer exchange, that uses a single BUNDLE transport, and a single set of BUNDLE attributes, for sending and receiving all media (bundled media) described by the set of "m=" sections. The same BUNDLE transport is used for sending and receiving bundled media.
BUNDLE-группа: Набор связанных секций «m=», созданный с помощью обмена «предложение/ответ» SDP, который использует один BUNDLE-транспорт и один набор BUNDLE-атрибутов для отправки и приёма всех медиа (связанных медиа), описываемых набором секций «m=». Один и тот же BUNDLE-транспорт используется для отправки и приёма связанных медиа.
Bundled "m=" section: An "m=" section, whose identification-tag is placed in an SDP 'group:BUNDLE' attribute identification-tag list in an offer or answer.

5. SDP Grouping Framework BUNDLE Extension
5. Расширение BUNDLE механизма группировки SDP
This section defines a new SDP Grouping Framework [RFC5888] extension, 'BUNDLE'. The BUNDLE extension can be used with the SDP offer/answer mechanism to negotiate a set of "m=" sections that will become part of a BUNDLE group. Within a BUNDLE group, each "m=" section uses a BUNDLE transport for sending and receiving bundled media. Each endpoint uses a single address:port combination for sending and receiving the bundled media.
Настоящий раздел определяет новое расширение механизма группировки SDP [RFC5888] — 'BUNDLE'. Расширение BUNDLE может использоваться с механизмом «предложение/ответ» SDP для согласования набора секций «m=», которые станут частью BUNDLE-группы. В BUNDLE-группе каждая секция «m=» использует BUNDLE-транспорт для отправки и приёма связанных медиа. Каждая конечная точка использует одну комбинацию адрес:порт для отправки и приёма связанных медиа.
The BUNDLE extension is indicated using an SDP 'group' attribute with a semantics value [RFC5888] of "BUNDLE". An identification-tag is assigned to each bundled "m=" section, and each identification-tag is listed in the SDP 'group:BUNDLE' attribute identification-tag list. Each "m=" section whose identification-tag is listed in the identification-tag list is associated with a given BUNDLE group.
Расширение BUNDLE указывается с помощью атрибута SDP 'group' со значением семантики [RFC5888] «BUNDLE». Каждой связанной секции «m=» назначается identification-tag, и каждый identification-tag перечисляется в списке identification-tag атрибута SDP 'group:BUNDLE'. Каждая секция «m=», identification-tag которой указан в списке identification-tag, связывается с данной BUNDLE-группой.
SDP bodies can contain multiple BUNDLE groups. Any given bundled "m=" section MUST NOT be associated with more than one BUNDLE group at any given time.
Тела SDP могут содержать несколько BUNDLE-групп. Любая данная связанная секция «m=» НЕ ДОЛЖНА быть связана более чем с одной BUNDLE-группой в любой момент времени.
NOTE: The order of the "m=" sections listed in the SDP 'group:BUNDLE' attribute identification-tag list does not have to be the same as the order in which the "m=" sections occur in the SDP.
ПРИМЕЧАНИЕ. Порядок секций «m=», перечисленных в списке identification-tag атрибута SDP 'group:BUNDLE', не обязан совпадать с порядком, в котором секции «m=» встречаются в SDP.
The multiplexing category [RFC8859] for the 'group:BUNDLE' attribute is 'NORMAL'.
Категория мультиплексирования [RFC8859] для атрибута 'group:BUNDLE' — 'NORMAL'.

Раздел 7 определяет подробные процедуры «предложение/ответ» SDP для расширения BUNDLE.
6. SDP 'bundle-only' Attribute
6. Атрибут SDP 'bundle-only'
This section defines a new SDP media-level attribute [RFC4566], 'bundle-only'. 'bundle-only' is a property attribute [RFC4566] and hence has no value.
Настоящий раздел определяет новый атрибут SDP уровня медиа [RFC4566] 'bundle-only'. 'bundle-only' — атрибут-свойство [RFC4566], поэтому он не имеет значения.
In order to ensure that an answerer that does not support the BUNDLE extension always rejects a bundled "m=" section in an offer, the offerer can assign a zero port value to the "m=" section. According to [RFC3264], an answerer will reject such an "m=" section. By including an SDP 'bundle-only' attribute in a bundled "m=" section, the offerer can request that the answerer accepts the "m=" section only if the answerer supports the BUNDLE extension and if the answerer keeps the "m=" section within the associated BUNDLE group.
Чтобы гарантировать, что отвечающая сторона, не поддерживающая расширение BUNDLE, всегда отклоняет связанную секцию «m=» в предложении, инициатор может назначить этой секции «m=» нулевое значение порта. Согласно [RFC3264], отвечающая сторона отклонит такую секцию «m=». Включив атрибут SDP 'bundle-only' в связанную секцию «m=», инициатор может запросить, чтобы отвечающая сторона приняла секцию «m=» только если она поддерживает расширение BUNDLE и сохраняет секцию «m=» в связанной BUNDLE-группе.
Name: bundle-only
Имя: bundle-only
Value: N/A
Значение: Н/Д
Usage Level: media
Уровень использования: медиа
Charset Dependent: no
Зависимость от набора символов: нет
Example: a=bundle-only
Пример: a=bundle-only
Once the offerer-tagged "m=" section and the answerer-tagged "m=" section have been selected, an offerer and answerer will include an SDP 'bundle-only' attribute in, and assign a zero port value to, every other bundled "m=" section.
После того как выбраны секция «m=» с тегом инициатора и секция «m=» с тегом отвечающей стороны, инициатор и отвечающая сторона включают атрибут SDP 'bundle-only' во все остальные связанные секции «m=» и назначают им нулевое значение порта.
The usage of the 'bundle-only' attribute is only defined for a bundled "m=" section with a zero port value. Other usage is unspecified.
Использование атрибута 'bundle-only' определено только для связанной секции «m=» с нулевым значением порта. Иное использование не определено.

Раздел 7 определяет подробные процедуры «предложение/ответ» SDP для атрибута 'bundle-only'.

7.1. Generic SDP Considerations
7.1. Общие соображения по SDP
This section describes generic restrictions associated with the usage of SDP parameters within a BUNDLE group. It also describes how to calculate a value for the whole BUNDLE group, when parameter and attribute values have been assigned to each bundled "m=" section.
Настоящий раздел описывает общие ограничения, связанные с использованием параметров SDP в BUNDLE-группе. Он также описывает, как вычислить значение для всей BUNDLE-группы, когда значения параметров и атрибутов назначены каждой связанной секции «m=».
7.1.1. Connection Data ("c=")
7.1.1. Данные соединения («c=»)
The "c=" line nettype value [RFC4566] associated with a bundled "m=" section MUST be 'IN'.
Значение nettype строки «c=» [RFC4566], связанное со связанной секцией «m=», ДОЛЖНО быть 'IN'.
The "c=" line addrtype value [RFC4566] associated with a bundled "m=" section MUST be 'IP4' or 'IP6'. The same value MUST be associated with each "m=" section.
Значение addrtype строки «c=» [RFC4566], связанное со связанной секцией «m=», ДОЛЖНО быть 'IP4' или 'IP6'. Одно и то же значение ДОЛЖНО быть связано с каждой секцией «m=».
NOTE: Extensions to this specification can specify usage of the BUNDLE mechanism for other nettype and addrtype values than the ones listed above.
ПРИМЕЧАНИЕ. Расширения настоящей спецификации могут определять использование механизма BUNDLE для других значений nettype и addrtype, помимо перечисленных выше.
7.1.2. Bandwidth ("b=")
7.1.2. Полоса пропускания («b=»)
An offerer and answerer MUST use the rules and restrictions defined in [RFC8859] for associating the SDP bandwidth ("b=") line with bundled "m=" sections.
Инициатор и отвечающая сторона ДОЛЖНЫ использовать правила и ограничения, определённые в [RFC8859], для связывания строки полосы пропускания SDP («b=») со связанными секциями «m=».
7.1.3. Attributes ("a=")
7.1.3. Атрибуты («a=»)
An offerer and answerer MUST include SDP attributes in every bundled "m=" section where applicable, following the normal offer/answer procedures for each attribute, with the following exceptions:
Инициатор и отвечающая сторона ДОЛЖНЫ включать атрибуты SDP в каждую связанную секцию «m=», где это применимо, следуя обычным процедурам «предложение/ответ» для каждого атрибута, за следующими исключениями:
* In the initial BUNDLE offer, the offerer MUST NOT include IDENTICAL and TRANSPORT multiplexing category SDP attributes (BUNDLE attributes) in bundle-only "m=" sections. The offerer MUST include such attributes in all other bundled "m=" sections. In the initial BUNDLE offer, each bundled "m=" line can contain a different set of BUNDLE attributes and attribute values. Once the offerer-tagged "m=" section has been selected, the BUNDLE attributes contained in the offerer-tagged "m=" section will apply to each bundled "m=" section within the BUNDLE group.
* В начальном BUNDLE-предложении инициатор НЕ ДОЛЖЕН включать атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT (BUNDLE-атрибуты) в секции «m=» типа bundle-only. Инициатор ДОЛЖЕН включать такие атрибуты во все остальные связанные секции «m=». В начальном BUNDLE-предложении каждая связанная строка «m=» может содержать разный набор BUNDLE-атрибутов и значений атрибутов. После выбора секции «m=» с тегом инициатора BUNDLE-атрибуты, содержащиеся в этой секции, будут применяться к каждой связанной секции «m=» в BUNDLE-группе.
* In a subsequent offer, or in an answer (initial of subsequent), the offerer and answerer MUST include IDENTICAL and TRANSPORT multiplexing category SDP attributes (BUNDLE attributes) only in the tagged "m=" section (offerer-tagged "m=" section or answerer- tagged "m=" section). The offerer and answerer MUST NOT include such attributes in any other bundled "m=" section. The BUNDLE attributes contained in the tagged "m=" section will apply to each bundled "m=" section within the BUNDLE group.
* В последующем предложении или в ответе (начальном или последующем) инициатор и отвечающая сторона ДОЛЖНЫ включать атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT (BUNDLE-атрибуты) только в секцию «m=» с тегом (секцию с тегом инициатора или секцию с тегом отвечающей стороны). Инициатор и отвечающая сторона НЕ ДОЛЖНЫ включать такие атрибуты в любую другую связанную секцию «m=». BUNDLE-атрибуты, содержащиеся в секции «m=» с тегом, будут применяться к каждой связанной секции «m=» в BUNDLE-группе.
* In an offer (initial BUNDLE offer or subsequent), or in an answer (initial BUNDLE answer or subsequent), the offerer and answerer MUST include SDP attributes from categories other than IDENTICAL and TRANSPORT in each bundled "m=" section that a given attribute applies to. Each bundled "m=" line can contain a different set of such attributes, and attribute values, as such attributes only apply to the given bundled "m=" section in which they are included.
* В предложении (начальном BUNDLE-предложении или последующем) или в ответе (начальном BUNDLE-ответе или последующем) инициатор и отвечающая сторона ДОЛЖНЫ включать атрибуты SDP категорий, отличных от IDENTICAL и TRANSPORT, в каждую связанную секцию «m=», к которой применяется данный атрибут. Каждая связанная строка «m=» может содержать разный набор таких атрибутов и значений атрибутов, поскольку такие атрибуты применяются только к той связанной секции «m=», в которую они включены.
NOTE: A consequence of the rules above is that media-specific IDENTICAL and TRANSPORT multiplexing category SDP attributes that are applicable only to some of the bundled "m=" sections within the BUNDLE group might appear in the tagged "m=" section for which they are not applicable. For instance, the tagged "m=" section might contain an SDP 'rtcp-mux' attribute even if the tagged "m=" section does not describe RTP-based media (but another bundled "m=" section within the BUNDLE group does describe RTP-based media).
ПРИМЕЧАНИЕ. Следствием приведённых выше правил является то, что специфичные для медиа атрибуты SDP категории мультиплексирования IDENTICAL и TRANSPORT, применимые лишь к некоторым связанным секциям «m=» в BUNDLE-группе, могут оказаться в секции «m=» с тегом, к которой они не применимы. Например, секция «m=» с тегом может содержать атрибут SDP 'rtcp-mux', даже если эта секция не описывает медиа на основе RTP (но другая связанная секция «m=» в BUNDLE-группе описывает медиа на основе RTP).

7.2. Формирование начального предложения SDP

* Include SDP attributes in the bundled "m=" sections following the rules in Section 7.1.3;
* включить атрибуты SDP в связанные секции «m=» согласно правилам раздела 7.1.3;
* Include an SDP 'group:BUNDLE' attribute in the offer; and
* включить атрибут SDP 'group:BUNDLE' в предложение; и

* The answerer is only allowed to include a bundled "m=" section in the same BUNDLE group as the bundled "m=" line in the corresponding offer.
* отвечающая сторона может включить связанную секцию «m=» только в ту же BUNDLE-группу, что и связанная строка «m=» в соответствующем предложении.

Кроме того, когда отвечающая сторона формирует ответ (начальный BUNDLE-ответ или последующий), содержащий BUNDLE-группу, она ДОЛЖНА:
* In case of an initial BUNDLE answer, select the offerer-tagged "m=" section using the procedures in Section 7.3.1. In case of a subsequent answer, the offerer-tagged "m=" section is indicated in the corresponding subsequent offer and MUST NOT be changed by the answerer;

При выборе секции «m=» с тегом инициатора отвечающая сторона ДОЛЖНА сначала проверить, соответствует ли эта секция следующим критериям раздела 7.2.1:
* The answerer will not move the "m=" section out of the BUNDLE group (Section 7.3.2);
* отвечающая сторона не будет перемещать секцию «m=» из BUNDLE-группы (раздел 7.3.2);
* The answerer will not reject the "m=" section (Section 7.3.3); and
* отвечающая сторона не будет отклонять секцию «m=» (раздел 7.3.3); и
* The "m=" section does not contain a zero port value.
* секция «m=» не содержит нулевого значения порта.
If all of the criteria above are fulfilled, the answerer MUST select the "m=" section as the offerer-tagged "m=" section and MUST also mark the corresponding "m=" section in the answer as the answerer- tagged "m=" section. In the answer, the answerer BUNDLE-tag indicates the answerer-tagged "m=" section.
Если все перечисленные выше критерии выполнены, отвечающая сторона ДОЛЖНА выбрать эту секцию «m=» в качестве секции «m=» с тегом инициатора, а также ДОЛЖНА пометить соответствующую секцию «m=» в ответе как секцию «m=» с тегом отвечающей стороны. В ответе BUNDLE-тег отвечающей стороны указывает секцию «m=» с тегом отвечающей стороны.
If one or more of the criteria are not fulfilled, the answerer MUST pick the next identification-tag in the identification-tag list in the offer and perform the same criteria check for the "m=" section indicated by that identification-tag. If there are no more identification-tags in the identification-tag list, the answerer MUST NOT create the BUNDLE group. Unless the answerer rejects the whole offer, the answerer MUST apply the answerer procedures for moving an "m=" section out of a BUNDLE group (Section 7.3.2) or rejecting an "m=" section within a BUNDLE group (Section 7.3.3) to every bundled "m=" section in the offer when creating the answer.

Если в списке identification-tag больше нет идентификаторов, отвечающая сторона НЕ ДОЛЖНА создавать BUNDLE-группу. Если только отвечающая сторона не отклоняет всё предложение, при формировании ответа она ДОЛЖНА применить процедуры отвечающей стороны для перемещения секции «m=» из BUNDLE-группы (раздел 7.3.2) или отклонения секции «m=» в BUNDLE-группе (раздел 7.3.3) к каждой связанной секции «m=» в предложении.

7.3.2. Moving a Media Description Out of a BUNDLE Group
7.3.2. Перемещение описания медиа из BUNDLE-группы
When an answerer generates the answer, if the answerer wants to move a bundled "m=" section out of the negotiated BUNDLE group, the answerer MUST first check the following criteria:
Когда отвечающая сторона формирует ответ и хочет переместить связанную секцию «m=» из согласованной BUNDLE-группы, она ДОЛЖНА сначала проверить следующие критерии:
* In the corresponding offer, the "m=" section is within a previously negotiated BUNDLE group, and
* в соответствующем предложении секция «m=» находится в ранее согласованной BUNDLE-группе, и
* In the corresponding offer, the "m=" section contains an SDP 'bundle-only' attribute.
* в соответствующем предложении секция «m=» содержит атрибут SDP 'bundle-only'.
If either criterion above is fulfilled, the answerer cannot move the "m=" section out of the BUNDLE group in the answer. The answerer can reject the whole offer, reject each bundled "m=" section within the BUNDLE group (Section 7.3.3), or keep the "m=" section within the BUNDLE group in the answer and later create an offer where the "m=" section is moved out of the BUNDLE group (Section 7.5.2).
Если выполнен хотя бы один из перечисленных выше критериев, отвечающая сторона не может переместить секцию «m=» из BUNDLE-группы в ответе. Отвечающая сторона может отклонить всё предложение, отклонить каждую связанную секцию «m=» в BUNDLE-группе (раздел 7.3.3) или сохранить секцию «m=» в BUNDLE-группе в ответе и позже сформировать предложение, в котором секция «m=» перемещается из BUNDLE-группы (раздел 7.5.2).
NOTE: One consequence of the rules above is that, once a BUNDLE group has been negotiated, a bundled "m=" section cannot be moved out of the BUNDLE group in an answer. Instead, an offer is needed.
ПРИМЕЧАНИЕ. Одно из следствий приведённых правил состоит в том, что после согласования BUNDLE-группы связанная секция «m=» не может быть перемещена из BUNDLE-группы в ответе. Вместо этого требуется предложение.
When the answerer generates an answer, in which it moves a bundled "m=" section out of a BUNDLE group, the answerer:
Когда отвечающая сторона формирует ответ, в котором перемещает связанную секцию «m=» из BUNDLE-группы, она:
* MUST assign a unique address:port to the "m=" section;
* ДОЛЖНА назначить секции «m=» уникальный адрес:порт;
* MUST include any applicable SDP attribute in the "m=" section, using the normal offer/answer procedures for each attribute;
* ДОЛЖНА включить в секцию «m=» любой применимый атрибут SDP, используя обычные процедуры «предложение/ответ» для каждого атрибута;
* MUST NOT place the identification-tag associated with the "m=" section in the SDP 'group:BUNDLE' attribute identification-tag list associated with the BUNDLE group; and
* НЕ ДОЛЖНА помещать identification-tag, связанный с этой секцией «m=», в список identification-tag атрибута SDP 'group:BUNDLE', связанный с BUNDLE-группой; и
* MUST NOT include an SDP 'bundle-only' attribute to the "m=" section.
* НЕ ДОЛЖНА включать атрибут SDP 'bundle-only' в секцию «m=».
Because an answerer is not allowed to move an "m=" section from one BUNDLE group to another within an answer (Section 7.3), if the answerer wants to move an "m=" section from one BUNDLE group to another, it MUST first move the "m=" section out of the current BUNDLE group and then generate an offer where the "m=" section is added to another BUNDLE group (Section 7.5.1).
Поскольку отвечающей стороне не разрешается перемещать секцию «m=» из одной BUNDLE-группы в другую в ответе (раздел 7.3), если она хочет переместить секцию «m=» из одной BUNDLE-группы в другую, она ДОЛЖНА сначала переместить секцию «m=» из текущей BUNDLE-группы, а затем сформировать предложение, в котором секция «m=» добавляется в другую BUNDLE-группу (раздел 7.5.1).
7.3.3. Rejecting a Media Description in a BUNDLE Group
7.3.3. Отклонение описания медиа в BUNDLE-группе
When an answerer wants to reject a bundled "m=" section in an answer, it MUST first check the following criterion:
Когда отвечающая сторона хочет отклонить связанную секцию «m=» в ответе, она ДОЛЖНА сначала проверить следующий критерий:
* In the corresponding offer, the "m=" section is the offerer-tagged "m=" section.
* в соответствующем предложении секция «m=» является секцией «m=» с тегом инициатора.
If the criterion above is fulfilled, the answerer cannot reject the "m=" section in the answer. The answerer can reject the whole offer, reject each bundled "m=" section within the BUNDLE group, or keep the "m=" section within the BUNDLE group in the answer and later create an offer where the "m=" section is disabled within the BUNDLE group (Section 7.5.3).
Если приведённый выше критерий выполнен, отвечающая сторона не может отклонить секцию «m=» в ответе. Она может отклонить всё предложение, отклонить каждую связанную секцию «m=» в BUNDLE-группе или сохранить секцию «m=» в BUNDLE-группе в ответе и позже сформировать предложение, в котором секция «m=» отключена в BUNDLE-группе (раздел 7.5.3).
When an answerer generates an answer, in which it rejects a bundled "m=" section, the answerer:

8. Protocol Identification
8. Идентификация протокола
Each "m=" section within a BUNDLE group MUST use the same transport- layer protocol. If bundled "m=" sections use different upper-layer protocols on top of the transport-layer protocol, there MUST exist a publicly available specification that describes how a mechanism associates received data with the correct protocol for this particular protocol combination.
Каждая секция «m=» в BUNDLE-группе ДОЛЖНА использовать один и тот же протокол транспортного уровня. Если связанные секции «m=» используют разные протоколы верхнего уровня поверх протокола транспортного уровня, ДОЛЖНА существовать общедоступная спецификация, описывающая, как механизм сопоставляет полученные данные с правильным протоколом для данной конкретной комбинации протоколов.
In addition, if received data can be associated with more than one bundled "m=" section, there MUST exist a publicly available specification that describes a mechanism for associating the received data with the correct "m=" section.
Кроме того, если полученные данные могут быть сопоставлены более чем с одной связанной секцией «m=», ДОЛЖНА существовать общедоступная спецификация, описывающая механизм сопоставления полученных данных с правильной секцией «m=».
This document describes a mechanism to identify the protocol of received data among the Session Traversal Utilities for NAT (STUN), DTLS, and the Secure Real-time Transport Protocol (SRTP) (in any combination) when UDP is used as a transport-layer protocol, but it does not describe how to identify different protocols transported on DTLS. While the mechanism is generally applicable to other protocols and transport-layer protocols, any such use requires further specification that encompasses how to multiplex multiple protocols on a given transport-layer protocol and how to associate received data with the correct protocols.
Настоящий документ описывает механизм идентификации протокола полученных данных среди Session Traversal Utilities for NAT (STUN), DTLS и Secure Real-time Transport Protocol (SRTP) (в любой комбинации), когда UDP используется в качестве протокола транспортного уровня, но не описывает, как идентифицировать различные протоколы, передаваемые поверх DTLS. Хотя механизм в целом применим к другим протоколам и протоколам транспортного уровня, любое такое использование требует дальнейшей спецификации, охватывающей, как мультиплексировать несколько протоколов на данном протоколе транспортного уровня и как сопоставлять полученные данные с правильными протоколами.
8.1. STUN, DTLS, and SRTP
8.1. STUN, DTLS и SRTP
Section 5.1.2 of [RFC5764] describes a mechanism to identify the protocol of a received packet among the STUN, DTLS, and SRTP protocols (in any combination). If an offer or answer includes a bundled "m=" section that represents these protocols, the offerer or answerer MUST support the mechanism described in [RFC5764], and no explicit negotiation is required in order to indicate support and usage of the mechanism.
Раздел 5.1.2 [RFC5764] описывает механизм идентификации протокола полученного пакета среди протоколов STUN, DTLS и SRTP (в любой комбинации). Кроме того, если полученный пакет DTLS может быть сопоставлен более чем с одной секцией «m=», ДОЛЖНА существовать спецификация, описывающая механизм сопоставления полученных пакетов DTLS с правильной секцией «m=».

9. RTP Considerations
9. Соображения по RTP
9.1. Single RTP Session
9.1. Единый сеанс RTP
All RTP-based media within a single BUNDLE group belong to a single RTP session [RFC3550].
Все медиа на основе RTP в одной BUNDLE-группе принадлежат одному сеансу RTP [RFC3550].
Since a single BUNDLE transport is used for sending and receiving bundled media, the symmetric RTP mechanism [RFC4961] MUST be used for RTP-based bundled media.
Поскольку для отправки и приёма связанных медиа используется один BUNDLE-транспорт, для связанных медиа на основе RTP ДОЛЖЕН использоваться механизм симметричного RTP [RFC4961].
Since a single RTP session is used for each BUNDLE group, all "m=" sections representing RTP-based media within a BUNDLE group will share a single Synchronization Source (SSRC) numbering space [RFC3550].
Поскольку для каждой BUNDLE-группы используется один сеанс RTP, все секции «m=», представляющие медиа на основе RTP в BUNDLE-группе, будут совместно использовать единое пространство нумерации Synchronization Source (SSRC) [RFC3550].
The following rules and restrictions apply for a single RTP session:
Для единого сеанса RTP применяются следующие правила и ограничения:
* A specific payload type value can be used in multiple bundled "m=" sections only if each codec associated with the payload type number shares an identical codec configuration (Section 9.1.1).
* Конкретное значение типа полезной нагрузки может использоваться в нескольких связанных секциях «m=», только если каждый кодек, связанный с номером типа полезной нагрузки, имеет идентичную конфигурацию кодека (раздел 9.1.1).
* The proto value in each bundled RTP-based "m=" section MUST be identical (e.g., RTP/AVPF).
* Значение proto в каждой связанной секции «m=» на основе RTP ДОЛЖНО быть идентичным (например, RTP/AVPF).
* The RTP MID header extension MUST be enabled, by including an SDP 'extmap' attribute [RFC8285], with a 'urn:ietf:params:rtp- hdrext:sdes:mid' URI value, in each bundled RTP-based "m=" section in every offer and answer.
* Расширение заголовка RTP MID ДОЛЖНО быть включено путём добавления атрибута SDP 'extmap' [RFC8285] со значением URI 'urn:ietf:params:rtp-hdrext:sdes:mid' в каждую связанную секцию «m=» на основе RTP в каждом предложении и ответе.
* A given SSRC MUST NOT transmit RTP packets using payload types that originate from different bundled "m=" sections.
* Данный SSRC НЕ ДОЛЖЕН передавать пакеты RTP с типами полезной нагрузки, происходящими из разных связанных секций «m=».
NOTE: The last bullet above is to avoid sending multiple media types from the same SSRC. If transmission of multiple media types are done with time overlap, RTP and RTCP fail to function. Even if done in proper sequence, this causes RTP timestamp rate switching issues [RFC7160]. However, once an SSRC has left the RTP session (by sending an RTCP BYE packet), that SSRC can be reused by another source (possibly associated with a different bundled "m=" section) after a delay of 5 RTCP reporting intervals (the delay is to ensure the SSRC has timed out, in case the RTCP BYE packet was lost [RFC3550]).
ПРИМЕЧАНИЕ. Последний пункт выше предназначен для предотвращения отправки нескольких типов медиа от одного SSRC. Если передача нескольких типов медиа выполняется с перекрытием по времени, RTP и RTCP перестают работать. Даже при правильной последовательности это вызывает проблемы переключения частоты временных меток RTP [RFC7160]. Однако после того как SSRC покинул сеанс RTP (отправив пакет RTCP BYE), этот SSRC может быть повторно использован другим источником (возможно, связанным с другой связанной секцией «m=») после задержки в 5 интервалов отчётов RTCP (задержка нужна, чтобы гарантировать, что SSRC истёк по тайм-ауту, если пакет RTCP BYE был потерян [RFC3550]).
[RFC7657] defines Differentiated Services (Diffserv) considerations for RTP-based bundled media sent using a mixture of Diffserv Codepoints.
[RFC7657] определяет соображения Differentiated Services (Diffserv) для связанных медиа на основе RTP, передаваемых со смесью кодовых точек Diffserv.
9.1.1. Payload Type (PT) Value Reuse
9.1.1. Повторное использование значения типа полезной нагрузки (PT)
Multiple bundled "m=" sections might describe RTP-based media. As all RTP-based media associated with a BUNDLE group belong to the same RTP session, in order for a given payload type value to be used inside more than one bundled "m=" section, all codecs associated with the payload type number MUST share an identical codec configuration. This means that the codecs MUST share the same media type, encoding name, clock rate, and any parameter that can affect the codec configuration and packetization. [RFC8859] lists SDP attributes, whose attribute values are required to be identical for all codecs that use the same payload type value.
Несколько связанных секций «m=» могут описывать медиа на основе RTP. Поскольку все медиа на основе RTP, относящиеся к BUNDLE-группе, принадлежат одному сеансу RTP, для использования данного значения типа полезной нагрузки более чем в одной связанной секции «m=» все кодеки, связанные с номером типа полезной нагрузки, ДОЛЖНЫ иметь идентичную конфигурацию кодека. Это означает, что кодеки ДОЛЖНЫ иметь одинаковый тип медиа, имя кодирования, тактовую частоту и любой параметр, который может влиять на конфигурацию кодека и пакетизацию. [RFC8859] перечисляет атрибуты SDP, значения которых должны быть идентичными для всех кодеков, использующих одно и то же значение типа полезной нагрузки.
9.2. Associating RTP/RTCP Streams with the Correct SDP Media Description
9.2. Сопоставление потоков RTP/RTCP с правильным описанием медиа SDP
As described in [RFC3550], RTP packets are associated with RTP streams [RFC7656]. Each RTP stream is identified by an SSRC value, and each RTP packet includes an SSRC field that is used to associate the packet with the correct RTP stream. RTCP packets also use SSRCs to identify which RTP streams the packet relates to. However, an RTCP packet can contain multiple SSRC fields, in the course of providing feedback or reports on different RTP streams, and therefore can be associated with multiple such streams.
Как описано в [RFC3550], пакеты RTP связываются с потоками RTP [RFC7656]. Каждый поток RTP идентифицируется значением SSRC, и каждый пакет RTP содержит поле SSRC, используемое для связывания пакета с правильным потоком RTP. Пакеты RTCP также используют SSRC для определения того, к каким потокам RTP относится пакет. Однако пакет RTCP может содержать несколько полей SSRC в ходе предоставления обратной связи или отчётов о различных потоках RTP и поэтому может быть связан с несколькими такими потоками.
In order to be able to process received RTP/RTCP packets correctly, it MUST be possible to associate an RTP stream with the correct "m=" section, as the "m=" section and SDP attributes associated with the "m=" section contains information needed to process the packets.
Чтобы иметь возможность корректно обрабатывать полученные пакеты RTP/RTCP, ДОЛЖНА существовать возможность сопоставить поток RTP с правильной секцией «m=», поскольку секция «m=» и связанные с ней атрибуты SDP содержат информацию, необходимую для обработки пакетов.
As all RTP streams associated with a BUNDLE group use the same transport for sending and receiving RTP/RTCP packets, the local address:port combination part of the transport cannot be used to associate an RTP stream with the correct "m=" section. In addition, multiple RTP streams might be associated with the same "m=" section.
Поскольку все потоки RTP, относящиеся к BUNDLE-группе, используют один транспорт для отправки и приёма пакетов RTP/RTCP, часть комбинации локальный адрес:порт транспорта не может использоваться для сопоставления потока RTP с правильной секцией «m=». Кроме того, с одной секцией «m=» может быть связано несколько потоков RTP.
An offerer and answerer can inform each other which SSRC values they will use for an RTP stream by using the SDP 'ssrc' attribute [RFC5576]. However, an offerer will not know which SSRC values the answerer will use until the offerer has received the answer providing that information. Due to this, before the offerer has received the answer, the offerer will not be able to associate an RTP stream with the correct "m=" section using the SSRC value associated with the RTP stream. In addition, the offerer and answerer may start using new SSRC values mid-session, without informing each other about using the SDP 'ssrc' attribute.
Инициатор и отвечающая сторона могут сообщить друг другу, какие значения SSRC они будут использовать для потока RTP, с помощью атрибута SDP 'ssrc' [RFC5576]. Однако инициатор не узнает, какие значения SSRC будет использовать отвечающая сторона, пока не получит ответ с этой информацией. Из-за этого до получения ответа инициатор не сможет сопоставить поток RTP с правильной секцией «m=», используя значение SSRC, связанное с потоком RTP. Кроме того, инициатор и отвечающая сторона могут начать использовать новые значения SSRC в середине сеанса, не сообщая друг другу об этом с помощью атрибута SDP 'ssrc'.
In order for an offerer and answerer to always be able to associate an RTP stream with the correct "m=" section, the offerer and answerer using the BUNDLE extension MUST support the mechanism defined in Section 15, where the offerer and answerer insert the identification- tag associated with an "m=" section (provided by the remote peer) into RTP and RTCP packets associated with a BUNDLE group.
Чтобы инициатор и отвечающая сторона всегда могли сопоставить поток RTP с правильной секцией «m=», они, используя расширение BUNDLE, ДОЛЖНЫ поддерживать механизм, определённый в разделе 15, согласно которому инициатор и отвечающая сторона вставляют identification-tag, связанный с секцией «m=» (предоставленный удалённым партнёром), в пакеты RTP и RTCP, относящиеся к BUNDLE-группе.
When using this mechanism, the mapping from an SSRC to an identification-tag is carried in RTP header extensions or RTCP SDES packets, as specified in Section 15. Since a compound RTCP packet can contain multiple RTCP SDES packets, and each RTCP SDES packet can contain multiple chunks, a single RTCP packet can contain several mappings of SSRC to identification-tag. The offerer and answerer maintain tables used for routing that are updated each time an RTP/ RTCP packet contains new information that affects how packets are to be routed.
При использовании этого механизма сопоставление SSRC с identification-tag передаётся в расширениях заголовка RTP или пакетах RTCP SDES, как указано в разделе 15. Поскольку составной пакет RTCP может содержать несколько пакетов RTCP SDES, а каждый пакет RTCP SDES может содержать несколько блоков, один пакет RTCP может содержать несколько сопоставлений SSRC с identification-tag. Инициатор и отвечающая сторона ведут таблицы маршрутизации, которые обновляются каждый раз, когда пакет RTP/RTCP содержит новую информацию, влияющую на маршрутизацию пакетов.
However, some legacy implementations may not include this identification-tag in their RTP and RTCP traffic when using the BUNDLE mechanism and instead use a mechanism based on the payload type to associate RTP streams with SDP "m=" sections. In this situation, each "m=" section needs to use unique payload type values, in order for the payload type to be a reliable indicator of the relevant "m=" section for the RTP stream. If an implementation fails to ensure unique payload type values, it will be impossible to associate the RTP stream using that payload type value to a particular "m=" section. Note that when using the payload type to associate RTP streams with "m=" sections, an RTP stream, identified by its SSRC, will be mapped to an "m=" section when the first packet of that RTP stream is received, and the mapping will not be changed even if the payload type used by that RTP stream changes. In other words, the SSRC cannot "move" to a different "m=" section simply by changing the payload type.
Однако некоторые устаревшие реализации могут не включать этот identification-tag в свой трафик RTP и RTCP при использовании механизма BUNDLE, а вместо этого использовать механизм на основе типа полезной нагрузки для сопоставления потоков RTP с секциями «m=» SDP. В этой ситуации каждой секции «m=» необходимо использовать уникальные значения типа полезной нагрузки, чтобы тип полезной нагрузки был надёжным индикатором соответствующей секции «m=» для потока RTP. Если реализация не обеспечивает уникальные значения типа полезной нагрузки, сопоставить поток RTP, использующий это значение типа полезной нагрузки, с конкретной секцией «m=» будет невозможно. Обратите внимание: при использовании типа полезной нагрузки для сопоставления потоков RTP с секциями «m=» поток RTP, идентифицируемый своим SSRC, сопоставляется с секцией «m=» при получении первого пакета этого потока RTP, и сопоставление не изменяется, даже если тип полезной нагрузки, используемый этим потоком RTP, изменится. Иными словами, SSRC не может «переместиться» в другую секцию «m=» просто путём изменения типа полезной нагрузки.
Applications can implement RTP stacks in many different ways. The algorithm below details one way that RTP streams can be associated with "m=" sections, but it is not meant to be prescriptive about exactly how an RTP stack needs to be implemented. Applications MAY use any algorithm that achieves equivalent results to those described in the algorithm below.
Приложения могут реализовывать стеки RTP многими разными способами. Приведённый ниже алгоритм подробно описывает один из способов сопоставления потоков RTP с секциями «m=», но он не предписывает, как именно должен быть реализован стек RTP. Приложения МОГУТ использовать любой алгоритм, дающий результаты, эквивалентные описанным в приведённом ниже алгоритме.
To prepare to associate RTP streams with the correct "m=" section, the following steps MUST be followed for each BUNDLE group:
Чтобы подготовиться к сопоставлению потоков RTP с правильной секцией «m=», для каждой BUNDLE-группы необходимо выполнить следующие шаги:
* Construct a table mapping a MID to an "m=" section for each "m=" section in this BUNDLE group. Note that an "m=" section may only have one MID.
* построить таблицу сопоставления MID с секцией «m=» для каждой секции «m=» в данной BUNDLE-группе. Обратите внимание, что секция «m=» может иметь только один MID.
* Construct a table mapping SSRCs of incoming RTP streams to an "m=" section for each "m=" section in this BUNDLE group and for each SSRC configured for receiving in that "m=" section.
* построить таблицу сопоставления SSRC входящих потоков RTP с секцией «m=» для каждой секции «m=» в данной BUNDLE-группе и для каждого SSRC, настроенного для приёма в этой секции «m=».
* Construct a table mapping the SSRC of each outgoing RTP stream to an "m=" section for each "m=" section in this BUNDLE group and for each SSRC configured for sending in that "m=" section.
* построить таблицу сопоставления SSRC каждого исходящего потока RTP с секцией «m=» для каждой секции «m=» в данной BUNDLE-группе и для каждого SSRC, настроенного для отправки в этой секции «m=».
* Construct a table mapping a payload type to an "m=" section for each "m=" section in the BUNDLE group and for each payload type configured for receiving in that "m=" section. If any payload type is configured for receiving in more than one "m=" section in the BUNDLE group, do not include it in the table, as it cannot be used to uniquely identify an "m=" section.
* построить таблицу сопоставления типа полезной нагрузки с секцией «m=» для каждой секции «m=» в BUNDLE-группе и для каждого типа полезной нагрузки, настроенного для приёма в этой секции «m=». Если какой-либо тип полезной нагрузки настроен для приёма более чем в одной секции «m=» в BUNDLE-группе, не включайте его в таблицу, поскольку он не может использоваться для однозначной идентификации секции «m=».
* Note that for each of these tables, there can only be one mapping for any given key (MID, SSRC, or PT). In other words, the tables are not multimaps.
* Обратите внимание, что в каждой из этих таблиц для любого данного ключа (MID, SSRC или PT) может быть только одно сопоставление. Иными словами, таблицы не являются мультиотображениями.
As "m=" sections are added or removed from the BUNDLE groups, or their configurations are changed, the tables above MUST also be updated.
По мере добавления или удаления секций «m=» из BUNDLE-групп или изменения их конфигураций указанные выше таблицы также ДОЛЖНЫ обновляться.
When an RTP packet is received, it MUST be delivered to the RTP stream corresponding to its SSRC. That RTP stream MUST then be associated with the correct "m=" section within a BUNDLE group, for additional processing, according to the following steps:
При получении пакета RTP он ДОЛЖЕН быть доставлен потоку RTP, соответствующему его SSRC. Затем этот поток RTP ДОЛЖЕН быть сопоставлен с правильной секцией «m=» в BUNDLE-группе для дальнейшей обработки согласно следующим шагам:
* If the MID associated with the RTP stream is not in the table mapping a MID to an "m=" section, then the RTP stream is not decoded and the payload data is discarded.
* Если MID, связанный с потоком RTP, отсутствует в таблице сопоставления MID с секцией «m=», поток RTP не декодируется, а данные полезной нагрузки отбрасываются.
* If the packet has a MID, and the packet's extended sequence number is greater than that of the last MID update, as discussed in [RFC7941], Section 4.2.2, update the MID associated with the RTP stream to match the MID carried in the RTP packet, and then update the mapping tables to include an entry that maps the SSRC of that RTP stream to the "m=" section for that MID.
* Если пакет содержит MID и расширенный порядковый номер пакета больше, чем у последнего обновления MID, как обсуждается в [RFC7941], раздел 4.2.2, обновите MID, связанный с потоком RTP, чтобы он соответствовал MID, переносимому в пакете RTP, а затем обновите таблицы сопоставления, включив запись, сопоставляющую SSRC этого потока RTP с секцией «m=» для этого MID.
* If the SSRC of the RTP stream is in the incoming SSRC mapping table, check that the payload type used by the RTP stream matches a payload type included on the matching "m=" section. If so, associate the RTP stream with that "m=" section. Otherwise, the RTP stream is not decoded and the payload data is discarded.
* Если SSRC потока RTP присутствует в таблице сопоставления входящих SSRC, проверьте, что тип полезной нагрузки, используемый потоком RTP, соответствует типу полезной нагрузки, включённому в совпадающую секцию «m=». Если да, сопоставьте поток RTP с этой секцией «m=». В противном случае поток RTP не декодируется, а данные полезной нагрузки отбрасываются.
* If the payload type used by the RTP stream is in the payload type table, update the incoming SSRC mapping table to include an entry that maps the RTP stream's SSRC to the "m=" section for that payload type. Associate the RTP stream with the corresponding "m=" section.
* Если тип полезной нагрузки, используемый потоком RTP, присутствует в таблице типов полезной нагрузки, обновите таблицу сопоставления входящих SSRC, включив запись, сопоставляющую SSRC потока RTP с секцией «m=» для этого типа полезной нагрузки. Сопоставьте поток RTP с соответствующей секцией «m=».
* Otherwise, mark the RTP stream as "not for decoding" and discard the payload.
* В противном случае пометьте поток RTP как «не для декодирования» и отбросьте полезную нагрузку.
If the RTP packet contains one or more Contributing Source (CSRC) identifiers, then each CSRC is looked up in the incoming SSRC table, and a copy of the RTP packet is associated with the corresponding "m=" section for additional processing.
Если пакет RTP содержит один или несколько идентификаторов Contributing Source (CSRC), каждый CSRC ищется в таблице входящих SSRC, и копия пакета RTP сопоставляется с соответствующей секцией «m=» для дальнейшей обработки.
For each RTCP packet received (including each RTCP packet that is part of a compound RTCP packet), the packet is processed as usual by the RTP layer, then associated with the appropriate "m=" sections, and processed for the RTP streams represented by those "m=" sections. This routing is type dependent, as each kind of RTCP packet has its own mechanism for associating it with the relevant RTP streams.
Для каждого полученного пакета RTCP (включая каждый пакет RTCP, входящий в составной пакет RTCP) пакет обрабатывается как обычно уровнем RTP, затем сопоставляется с соответствующими секциями «m=» и обрабатывается для потоков RTP, представленных этими секциями «m=». Эта маршрутизация зависит от типа, поскольку каждый вид пакета RTCP имеет собственный механизм сопоставления с соответствующими потоками RTP.
RTCP packets that cannot be associated with an appropriate "m=" section MUST still be processed as usual by the RTP layer, which updates the metadata associated with the corresponding RTP streams. This situation can occur with certain multiparty RTP topologies or when RTCP packets are sent containing a subset of the SDES information.
Пакеты RTCP, которые не могут быть сопоставлены с подходящей секцией «m=», тем не менее ДОЛЖНЫ обрабатываться как обычно уровнем RTP, который обновляет метаданные, связанные с соответствующими потоками RTP. Такая ситуация может возникать в некоторых многосторонних топологиях RTP или когда отправляются пакеты RTCP, содержащие подмножество информации SDES.
Additional rules for processing various types of RTCP packets are explained below.
Дополнительные правила обработки различных типов пакетов RTCP описаны ниже.
* If the RTCP packet is of type SDES, for each chunk in the packet whose SSRC is found in the incoming SSRC table, deliver a copy of the SDES packet to the "m=" section associated with that SSRC. In addition, for any SDES MID items contained in these chunks, if the MID is found in the table mapping a MID to an "m=" section, update the incoming SSRC table to include an entry that maps the RTP stream associated with the chunk's SSRC to the "m=" section associated with that MID, unless the packet is older than the packet that most recently updated the mapping for this SSRC, as discussed in [RFC7941], Section 4.2.6.
* Если пакет RTCP имеет тип SDES, для каждого блока пакета, SSRC которого найден в таблице входящих SSRC, доставьте копию пакета SDES в секцию «m=», связанную с этим SSRC. Кроме того, для любых элементов SDES MID, содержащихся в этих блоках, если MID найден в таблице сопоставления MID с секцией «m=», обновите таблицу входящих SSRC, включив запись, сопоставляющую поток RTP, связанный с SSRC блока, с секцией «m=», связанной с этим MID, если только пакет не старше пакета, который последним обновил сопоставление для этого SSRC, как обсуждается в [RFC7941], раздел 4.2.6.
* Note that if an SDES packet is received as part of a compound RTCP packet, the SSRC to "m=" section mapping might not exist until the SDES packet is handled (e.g., in the case where RTCP for a source is received before any RTP packets). Therefore, it can be beneficial for an implementation to delay RTCP packet routing, such that it either prioritizes processing of the SDES item to generate or update the mapping or buffers the RTCP information that needs to be routed until the SDES item(s) has been processed. If the implementation is unable to follow this recommendation, the consequence could be that some RTCP information from this particular RTCP compound packet is not provided to higher layers. The impact from this is likely minor, when this information relates to a future incoming RTP stream.
* Обратите внимание, что если пакет SDES получен в составе составного пакета RTCP, сопоставление SSRC с секцией «m=» может не существовать до обработки пакета SDES (например, когда RTCP для источника получен раньше любых пакетов RTP). Поэтому реализации может быть полезно задержать маршрутизацию пакета RTCP, чтобы либо отдать приоритет обработке элемента SDES для создания или обновления сопоставления, либо буферизовать информацию RTCP, которую нужно маршрутизировать, до обработки элемента(ов) SDES. Если реализация не может следовать этой рекомендации, следствием может стать то, что часть информации RTCP из этого конкретного составного пакета RTCP не будет предоставлена верхним уровням. Влияние этого, вероятно, невелико, когда эта информация относится к будущему входящему потоку RTP.
* If the RTCP packet is of type BYE, it indicates that the RTP streams referenced in the packet are ending. Therefore, for each SSRC indicated in the packet that is found in the incoming SSRC table, first deliver a copy of the BYE packet to the "m=" section associated with that SSRC, and then remove the entry for that SSRC from the incoming SSRC table after an appropriate delay to account for "straggler packets", as specified in [RFC3550], Section 6.2.1.
* Если пакет RTCP имеет тип BYE, это указывает на завершение потоков RTP, упомянутых в пакете. Поэтому для каждого SSRC, указанного в пакете и найденного в таблице входящих SSRC, сначала доставьте копию пакета BYE в секцию «m=», связанную с этим SSRC, а затем удалите запись для этого SSRC из таблицы входящих SSRC после соответствующей задержки для учёта «запаздывающих пакетов», как указано в [RFC3550], раздел 6.2.1.
* If the RTCP packet is of type Sender Report (SR) or Receiver Report (RR), for each report block in the report whose "SSRC of source" is found in the outgoing SSRC table, deliver a copy of the SR or RR packet to the "m=" section associated with that SSRC. In addition, if the packet is of type SR, and the sender SSRC for the packet is found in the incoming SSRC table, deliver a copy of the SR packet to the "m=" section associated with that SSRC.
* Если пакет RTCP имеет тип Sender Report (SR) или Receiver Report (RR), для каждого блока отчёта, у которого «SSRC of source» найден в таблице исходящих SSRC, доставьте копию пакета SR или RR в секцию «m=», связанную с этим SSRC. Кроме того, если пакет имеет тип SR и SSRC отправителя пакета найден в таблице входящих SSRC, доставьте копию пакета SR в секцию «m=», связанную с этим SSRC.
* If the implementation supports the RTCP Extended Report (XR) and the packet is of type XR, as defined in [RFC3611], for each report block in the report whose "SSRC of source" is found in the outgoing SSRC table, deliver a copy of the XR packet to the "m=" section associated with that SSRC. In addition, if the sender SSRC for the packet is found in the incoming SSRC table, deliver a copy of the XR packet to the "m=" section associated with that SSRC.
* Если реализация поддерживает RTCP Extended Report (XR) и пакет имеет тип XR, как определено в [RFC3611], для каждого блока отчёта, у которого «SSRC of source» найден в таблице исходящих SSRC, доставьте копию пакета XR в секцию «m=», связанную с этим SSRC. Кроме того, если SSRC отправителя пакета найден в таблице входящих SSRC, доставьте копию пакета XR в секцию «m=», связанную с этим SSRC.
* If the RTCP packet is a feedback message of type RTPFB (transport- layer FB message) or PSFB (payload-specific FB message), as defined in [RFC4585], it will contain a media source SSRC, and this SSRC is used for routing certain subtypes of feedback messages. However, several subtypes of PSFB and RTPFB messages include a target SSRC(s) in a section called Feedback Control Information (FCI). For these messages, the target SSRC(s) is used for routing.
* Если пакет RTCP является сообщением обратной связи типа RTPFB (сообщение FB транспортного уровня) или PSFB (сообщение FB, специфичное для полезной нагрузки), как определено в [RFC4585], он будет содержать SSRC источника медиа, и этот SSRC используется для маршрутизации определённых подтипов сообщений обратной связи. Однако несколько подтипов сообщений PSFB и RTPFB содержат целевой SSRC (целевые SSRC) в разделе Feedback Control Information (FCI). Для этих сообщений для маршрутизации используется целевой SSRC (целевые SSRC).
* If the RTCP packet is a feedback packet that does not include target SSRCs in its FCI section, and the media source SSRC is found in the outgoing SSRC table, deliver the feedback packet to the "m=" section associated with that SSRC. RTPFB and PSFB types that are handled in this way include:
* Если пакет RTCP является пакетом обратной связи, который не содержит целевых SSRC в своём разделе FCI, а SSRC источника медиа найден в таблице исходящих SSRC, доставьте пакет обратной связи в секцию «m=», связанную с этим SSRC. Типы RTPFB и PSFB, обрабатываемые таким образом, включают:
Generic NACK: (PT=RTPFB, FMT=1) [RFC4585].
Generic NACK: (PT=RTPFB, FMT=1) [RFC4585].
Picture Loss Indication (PLI): (PT=PSFB, FMT=1) [RFC4585].
Picture Loss Indication (PLI): (PT=PSFB, FMT=1) [RFC4585].
Slice Loss Indication (SLI): (PT=PSFB, FMT=2) [RFC4585].
Slice Loss Indication (SLI): (PT=PSFB, FMT=2) [RFC4585].
Reference Picture Selection Indication (RPSI): (PT=PSFB, FMT=3) [RFC4585].
Reference Picture Selection Indication (RPSI): (PT=PSFB, FMT=3) [RFC4585].
* If the RTCP packet is a feedback message that does include a target SSRC(s) in its FCI section, it can either be a request or a notification. Requests reference an RTP stream that is being sent by the message recipient, whereas notifications are responses to an earlier request and therefore reference an RTP stream that is being received by the message recipient.
* Если пакет RTCP является сообщением обратной связи, которое содержит целевой SSRC (целевые SSRC) в своём разделе FCI, оно может быть либо запросом, либо уведомлением. Запросы ссылаются на поток RTP, отправляемый получателем сообщения, а уведомления являются ответами на более ранний запрос и поэтому ссылаются на поток RTP, принимаемый получателем сообщения.
* If the RTCP packet is a feedback request that includes a target SSRC(s), for each target SSRC that is found in the outgoing SSRC table, deliver a copy of the RTCP packet to the "m=" section associated with that SSRC. PSFB and RTPFB types that are handled in this way include:
* Если пакет RTCP является запросом обратной связи, содержащим целевой SSRC (целевые SSRC), для каждого целевого SSRC, найденного в таблице исходящих SSRC, доставьте копию пакета RTCP в секцию «m=», связанную с этим SSRC. Типы PSFB и RTPFB, обрабатываемые таким образом, включают:
Full Intra Request (FIR): (PT=PSFB, FMT=4) [RFC5104].
Full Intra Request (FIR): (PT=PSFB, FMT=4) [RFC5104].
Temporal-Spatial Trade-off Request (TSTR): (PT=PSFB, FMT=5) [RFC5104].
Temporal-Spatial Trade-off Request (TSTR): (PT=PSFB, FMT=5) [RFC5104].
H.271 Video Back Channel Message (VBCM): (PT=PSFB, FMT=7) [RFC5104].
H.271 Video Back Channel Message (VBCM): (PT=PSFB, FMT=7) [RFC5104].
Temporary Maximum Media Stream Bit Rate Request (TMMBR): (PT=R TPFB, FMT=3) [RFC5104].
Temporary Maximum Media Stream Bit Rate Request (TMMBR): (PT=R TPFB, FMT=3) [RFC5104].
Layer Refresh Request (LRR): (PT=PSFB, FMT=10) [LLR-RTCP].
Layer Refresh Request (LRR): (PT=PSFB, FMT=10) [LLR-RTCP].
* If the RTCP packet is a feedback notification that includes a target SSRC(s), for each target SSRC that is found in the incoming SSRC table, deliver a copy of the RTCP packet to the "m=" section associated with the RTP stream with a matching SSRC. PSFB and RTPFB types that are handled in this way include:
* Если пакет RTCP является уведомлением обратной связи, содержащим целевой SSRC (целевые SSRC), для каждого целевого SSRC, найденного в таблице входящих SSRC, доставьте копию пакета RTCP в секцию «m=», связанную с потоком RTP с совпадающим SSRC. Типы PSFB и RTPFB, обрабатываемые таким образом, включают:
Temporal-Spatial Trade-off Notification (TSTN): (PT=PSFB, FMT=6) [RFC5104]. This message is a notification in response to a prior TSTR.
Temporal-Spatial Trade-off Notification (TSTN): (PT=PSFB, FMT=6) [RFC5104]. Это сообщение является уведомлением в ответ на предыдущий TSTR.
Temporary Maximum Media Stream Bit Rate Notification (TMMBN): (PT=RTPFB, FMT=4) [RFC5104]. This message is a notification in response to a prior TMMBR, but it can also be sent unsolicited.
Temporary Maximum Media Stream Bit Rate Notification (TMMBN): (PT=RTPFB, FMT=4) [RFC5104]. Это сообщение является уведомлением в ответ на предыдущий TMMBR, но также может отправляться без запроса.
If the RTCP packet is of type APP, then it is handled in an application-specific manner. If the application does not recognize the APP packet, then it MUST be discarded.
Если пакет RTCP имеет тип APP, он обрабатывается зависящим от приложения образом. Если приложение не распознаёт пакет APP, он ДОЛЖЕН быть отброшен.
9.3. RTP/RTCP Multiplexing
9.3. Мультиплексирование RTP/RTCP
Within a BUNDLE group, the offerer and answerer MUST enable RTP/RTCP multiplexing [RFC5761] for the RTP-based bundled media (i.e., the same transport will be used for both RTP packets and RTCP packets). In addition, the offerer and answerer MUST support the SDP 'rtcp-mux- only' attribute [RFC8858].
В BUNDLE-группе инициатор и отвечающая сторона ДОЛЖНЫ включить мультиплексирование RTP/RTCP [RFC5761] для связанных медиа на основе RTP (т. е. один транспорт будет использоваться как для пакетов RTP, так и для пакетов RTCP). Кроме того, инициатор и отвечающая сторона ДОЛЖНЫ поддерживать атрибут SDP 'rtcp-mux-only' [RFC8858].
9.3.1. SDP Offer/Answer Procedures
9.3.1. Процедуры «предложение/ответ» SDP
This section describes how an offerer and answerer use the SDP 'rtcp- mux' [RFC5761] and SDP 'rtcp-mux-only' attributes [RFC8858] to negotiate usage of RTP/RTCP multiplexing for RTP-based bundled media.
Настоящий раздел описывает, как инициатор и отвечающая сторона используют атрибуты SDP 'rtcp-mux' [RFC5761] и SDP 'rtcp-mux-only' [RFC8858] для согласования использования мультиплексирования RTP/RTCP для связанных медиа на основе RTP.
RTP/RTCP multiplexing only applies to RTP-based media. However, as described in Section 7.1.3, within an offer or answer the SDP 'rtcp- mux' and SDP 'rtcp-mux-only' attributes might be included in a bundled "m=" section for non-RTP-based media (if such "m=" section is the offerer-tagged "m=" section or answerer-tagged "m=" section).
Мультиплексирование RTP/RTCP применяется только к медиа на основе RTP. Однако, как описано в разделе 7.1.3, в предложении или ответе атрибуты SDP 'rtcp-mux' и SDP 'rtcp-mux-only' могут быть включены в связанную секцию «m=» для медиа, не основанных на RTP (если такая секция «m=» является секцией «m=» с тегом инициатора или секцией «m=» с тегом отвечающей стороны).
9.3.1.1. Generating the Initial SDP BUNDLE Offer
9.3.1.1. Формирование начального BUNDLE-предложения SDP
When an offerer generates an initial BUNDLE offer, if the offer contains one or more bundled "m=" sections for RTP-based media (or, if there is a chance that "m=" sections for RTP-based media will later be added to the BUNDLE group), the offerer MUST include an SDP 'rtcp-mux' attribute [RFC5761] in each bundled "m=" section (excluding any bundle-only "m=" sections). In addition, the offerer MAY include an SDP 'rtcp-mux-only' attribute [RFC8858] in one or more bundled "m=" sections for RTP-based media.
Когда инициатор формирует начальное BUNDLE-предложение, если предложение содержит одну или несколько связанных секций «m=» для медиа на основе RTP (или если существует вероятность, что секции «m=» для медиа на основе RTP будут позже добавлены в BUNDLE-группу), инициатор ДОЛЖЕН включить атрибут SDP 'rtcp-mux' [RFC5761] в каждую связанную секцию «m=» (за исключением секций «m=» типа bundle-only). Кроме того, инициатор МОЖЕТ включить атрибут SDP 'rtcp-mux-only' [RFC8858] в одну или несколько связанных секций «m=» для медиа на основе RTP.
NOTE: Whether the offerer includes the SDP 'rtcp-mux-only' attribute depends on whether the offerer supports fallback to usage of a separate port for RTCP in case the answerer moves one or more "m=" sections for RTP-based media out of the BUNDLE group in the answer.
ПРИМЕЧАНИЕ. Включение инициатором атрибута SDP 'rtcp-mux-only' зависит от того, поддерживает ли инициатор переход к использованию отдельного порта для RTCP в случае, если отвечающая сторона переместит одну или несколько секций «m=» для медиа на основе RTP из BUNDLE-группы в ответе.
NOTE: If the offerer includes an SDP 'rtcp-mux' attribute in the bundled "m=" sections, but does not include an SDP 'rtcp-mux-only' attribute, the offerer can also include an SDP 'rtcp' attribute [RFC3605] in one or more RTP-based bundled "m=" sections in order to provide a fallback port for RTCP, as described in [RFC5761]. However, the fallback port will only be applied to "m=" sections for RTP-based media that are moved out of the BUNDLE group by the answerer.
ПРИМЕЧАНИЕ. Если инициатор включает атрибут SDP 'rtcp-mux' в связанные секции «m=», но не включает атрибут SDP 'rtcp-mux-only', он может также включить атрибут SDP 'rtcp' [RFC3605] в одну или несколько связанных секций «m=» на основе RTP, чтобы предоставить резервный порт для RTCP, как описано в [RFC5761]. Однако резервный порт будет применён только к секциям «m=» для медиа на основе RTP, которые отвечающая сторона переместит из BUNDLE-группы.
In the initial BUNDLE offer, the address:port combination for RTCP MUST be unique in each bundled "m=" section for RTP-based media (excluding a bundle-only "m=" section), similar to RTP.
В начальном BUNDLE-предложении комбинация адрес:порт для RTCP ДОЛЖНА быть уникальной в каждой связанной секции «m=» для медиа на основе RTP (за исключением секции «m=» типа bundle-only), аналогично RTP.
9.3.1.2. Generating the SDP Answer
9.3.1.2. Формирование ответа SDP
When an answerer generates an answer, if the answerer supports RTP- based media, and if a bundled "m=" section in the corresponding offer contained an SDP 'rtcp-mux' attribute, the answerer MUST enable usage of RTP/RTCP multiplexing, even if there currently are no bundled "m=" sections for RTP-based media within the BUNDLE group. The answerer MUST include an SDP 'rtcp-mux' attribute in the answerer-tagged "m=" section, following the procedures for BUNDLE attributes (Section 7.1.3). In addition, if the "m=" section that is selected as the offerer-tagged "m=" section contained an SDP 'rtcp-mux-only' attribute, the answerer MUST include an SDP 'rtcp-mux-only' attribute in the answerer-tagged "m=" section.
Когда отвечающая сторона формирует ответ, если она поддерживает медиа на основе RTP и если связанная секция «m=» в соответствующем предложении содержала атрибут SDP 'rtcp-mux', отвечающая сторона ДОЛЖНА включить использование мультиплексирования RTP/RTCP, даже если в настоящее время в BUNDLE-группе нет связанных секций «m=» для медиа на основе RTP. Отвечающая сторона ДОЛЖНА включить атрибут SDP 'rtcp-mux' в секцию «m=» с тегом отвечающей стороны, следуя процедурам для BUNDLE-атрибутов (раздел 7.1.3). Кроме того, если секция «m=», выбранная в качестве секции «m=» с тегом инициатора, содержала атрибут SDP 'rtcp-mux-only', отвечающая сторона ДОЛЖНА включить атрибут SDP 'rtcp-mux-only' в секцию «m=» с тегом отвечающей стороны.
In an initial BUNDLE offer, if the suggested offerer-tagged "m=" section contained an SDP 'rtcp-mux-only' attribute, the "m=" section was for RTP-based media; thus, the answerer does not accept the "m=" section in the created BUNDLE group, and the answerer MUST move the "m=" section out of the BUNDLE group (Section 7.3.2); include the attribute in the moved "m=" section and enable RTP/RTCP multiplexing for the media associated with the "m=" section; or reject the "m=" section (Section 7.3.3).
В начальном BUNDLE-предложении, если предлагаемая секция «m=» с тегом инициатора содержала атрибут SDP 'rtcp-mux-only', эта секция «m=» была предназначена для медиа на основе RTP; таким образом, отвечающая сторона не принимает эту секцию «m=» в созданной BUNDLE-группе, и она ДОЛЖНА переместить секцию «m=» из BUNDLE-группы (раздел 7.3.2); включить атрибут в перемещённую секцию «m=» и включить мультиплексирование RTP/RTCP для медиа, связанных с этой секцией «m=»; или отклонить секцию «m=» (раздел 7.3.3).
The answerer MUST NOT include an SDP 'rtcp' attribute in any bundled "m=" section in the answer. The answerer will use the port value of the offerer-tagged "m=" section sending RTP and RTCP packets associated with RTP-based bundled media towards the offerer.
Отвечающая сторона НЕ ДОЛЖНА включать атрибут SDP 'rtcp' ни в одну связанную секцию «m=» в ответе. Отвечающая сторона будет использовать значение порта секции «m=» с тегом инициатора для отправки пакетов RTP и RTCP, связанных со связанными медиа на основе RTP, в сторону инициатора.
If the usage of RTP/RTCP multiplexing within a BUNDLE group has been negotiated in a previous offer/answer exchange, the answerer MUST include an SDP 'rtcp-mux' attribute in the answerer-tagged "m=" section. It is not possible to disable RTP/RTCP multiplexing within a BUNDLE group.
Если использование мультиплексирования RTP/RTCP в BUNDLE-группе было согласовано в ходе предыдущего обмена «предложение/ответ», отвечающая сторона ДОЛЖНА включить атрибут SDP 'rtcp-mux' в секцию «m=» с тегом отвечающей стороны. Отключить мультиплексирование RTP/RTCP в BUNDLE-группе невозможно.
9.3.1.3. Offerer Processing of the SDP Answer
9.3.1.3. Обработка ответа SDP инициатором
When an offerer receives an answer, if the answerer has accepted the usage of RTP/RTCP multiplexing (Section 9.3.1.2), the answerer follows the procedures for RTP/RTCP multiplexing defined in [RFC5761]. The offerer will use the port value of the answerer- tagged "m=" section for sending RTP and RTCP packets associated with RTP-based bundled media towards the answerer.
Когда инициатор получает ответ, если отвечающая сторона приняла использование мультиплексирования RTP/RTCP (раздел 9.3.1.2), отвечающая сторона следует процедурам мультиплексирования RTP/RTCP, определённым в [RFC5761]. Инициатор будет использовать значение порта секции «m=» с тегом отвечающей стороны для отправки пакетов RTP и RTCP, связанных со связанными медиа на основе RTP, в сторону отвечающей стороны.
NOTE: It is considered a protocol error if the answerer has not accepted the usage of RTP/RTCP multiplexing for RTP-based "m=" sections that the answerer included in the BUNDLE group.
ПРИМЕЧАНИЕ. Считается ошибкой протокола, если отвечающая сторона не приняла использование мультиплексирования RTP/RTCP для секций «m=» на основе RTP, которые она включила в BUNDLE-группу.
9.3.1.4. Modifying the Session
9.3.1.4. Изменение сеанса
When an offerer generates a subsequent offer, the offerer MUST include an SDP 'rtcp-mux' attribute in the offerer-tagged "m=" section, following the procedures for IDENTICAL multiplexing category attributes in Section 7.1.3.
Когда инициатор формирует последующее предложение, он ДОЛЖЕН включить атрибут SDP 'rtcp-mux' в секцию «m=» с тегом инициатора, следуя процедурам для атрибутов категории мультиплексирования IDENTICAL в разделе 7.1.3.
10. ICE Considerations
10. Соображения по ICE
This section describes how to use the BUNDLE grouping extension together with the ICE mechanism [RFC8445].
Настоящий раздел описывает, как использовать расширение группировки BUNDLE вместе с механизмом ICE [RFC8445].
The generic procedures for negotiating the usage of ICE using SDP, defined in [RFC8839], also apply to the usage of ICE with BUNDLE, with the following exceptions:
Общие процедуры согласования использования ICE с помощью SDP, определённые в [RFC8839], также применяются к использованию ICE с BUNDLE, за следующими исключениями:
* When the BUNDLE transport has been established, ICE connectivity checks and keepalives only need to be performed for the BUNDLE transport, instead of per individual bundled "m=" section within the BUNDLE group.
* После установления BUNDLE-транспорта проверки связности ICE и поддержание активности нужно выполнять только для BUNDLE-транспорта, а не для каждой отдельной связанной секции «m=» в BUNDLE-группе.
* The generic SDP attribute offer/answer considerations (Section 7.1.3) also apply to ICE-related attributes. Therefore, when an offerer sends an initial BUNDLE offer (in order to negotiate a BUNDLE group), the offerer includes ICE-related media- level attributes in each bundled "m=" section (excluding any bundle-only "m=" sections), and each "m=" section MUST contain unique ICE properties. When an answerer generates an answer (initial BUNDLE answer or subsequent) that contains a BUNDLE group, and when an offerer sends a subsequent offer that contains a BUNDLE group, ICE-related media-level attributes are only included in the tagged "m=" section (suggested offerer-tagged "m=" section or answerer-tagged "m=" section), and the ICE properties are applied to each bundled "m=" section within the BUNDLE group.
* Общие соображения «предложение/ответ» для атрибутов SDP (раздел 7.1.3) также применяются к атрибутам, связанным с ICE. Поэтому, когда инициатор отправляет начальное BUNDLE-предложение (для согласования BUNDLE-группы), он включает связанные с ICE атрибуты уровня медиа в каждую связанную секцию «m=» (за исключением секций «m=» типа bundle-only), и каждая секция «m=» ДОЛЖНА содержать уникальные свойства ICE. Изначально, до того как ICE сформирует выбранные пары кандидатов, которые будут использоваться для медиа, может быть установлено несколько транспортов (если проверяется несколько пар кандидатов). После того как ICE выберет пары кандидатов, они образуют BUNDLE-транспорт.
Support and usage of the ICE mechanism together with the BUNDLE extension is OPTIONAL, and the procedures in this section only apply when the ICE mechanism is used. Note that applications might mandate usage of the ICE mechanism even if the BUNDLE extension is not used.

NOTE: If the Trickle ICE mechanism [RFC8840] is used, an offerer and answerer might assign a port value of '9' and an IPv4 address of '0.0.0.0' (or, the IPv6 equivalent '::') to multiple bundled "m=" sections in the initial BUNDLE offer. ПРИМЕЧАНИЕ. 11. DTLS Considerations
11. Соображения по DTLS
One or more media streams within a BUNDLE group might use the Datagram Transport Layer Security (DTLS) protocol [RFC6347] in order to encrypt the data or negotiate encryption keys if another encryption mechanism is used to encrypt media.
Один или несколько медиапотоков в BUNDLE-группе могут использовать протокол Datagram Transport Layer Security (DTLS) [RFC6347] для шифрования данных или согласования ключей шифрования, если для шифрования медиа используется другой механизм шифрования.
When DTLS is used within a BUNDLE group, the following rules apply:
При использовании DTLS в BUNDLE-группе применяются следующие правила:
* There can only be one DTLS association [RFC6347] associated with the BUNDLE group;
* с BUNDLE-группой может быть связано только одно DTLS-соединение [RFC6347];
* Each usage of the DTLS association within the BUNDLE group MUST use the same mechanism for determining which endpoints (the offerer or answerer) become DTLS client and DTLS server;
* каждое использование DTLS-соединения в BUNDLE-группе ДОЛЖНО использовать один и тот же механизм для определения того, какие конечные точки (инициатор или отвечающая сторона) становятся DTLS-клиентом и DTLS-сервером;
* Each usage of the DTLS association within the BUNDLE group MUST use the same mechanism for determining whether an offer or answer will trigger the establishment of a new DTLS association or an existing DTLS association will be used; and
* каждое использование DTLS-соединения в BUNDLE-группе ДОЛЖНО использовать один и тот же механизм для определения того, вызовет ли предложение или ответ установление нового DTLS-соединения или будет использовано существующее DTLS-соединение; и
* If the DTLS client supports DTLS-SRTP, it MUST include the 'use_srtp' extension in the DTLS ClientHello message [RFC5764]. The client MUST include the extension even if the usage of DTLS- SRTP is not negotiated as part of the multimedia session (e.g., the SIP session [RFC3261]).
* Если DTLS-клиент поддерживает DTLS-SRTP, он ДОЛЖЕН включить расширение 'use_srtp' в сообщение DTLS ClientHello [RFC5764]. Клиент ДОЛЖЕН включить это расширение, даже если использование DTLS-SRTP не согласовано в рамках мультимедийного сеанса (например, сеанса SIP [RFC3261]).
NOTE: The inclusion of the 'use_srtp' extension during the initial DTLS handshake ensures that a DTLS renegotiation will not be required in order to include the extension, in case DTLS-SRTP encrypted media is added to the BUNDLE group later during the multimedia session.
ПРИМЕЧАНИЕ. Включение расширения 'use_srtp' во время начального рукопожатия DTLS гарантирует, что не потребуется повторное согласование DTLS для включения расширения в случае, если медиа, зашифрованные с помощью DTLS-SRTP, будут добавлены в BUNDLE-группу позже в ходе мультимедийного сеанса.

Рекомендуется, чтобы identification-tag был коротким. 17. Security Considerations
17. Вопросы безопасности
The security considerations defined in [RFC3264] and [RFC5888] apply to the BUNDLE extension. BUNDLE does not change which information, e.g., RTP streams, flows over the network, with the exception of the usage of the MID SDES item as discussed below. Primarily, it changes which addresses and ports, and thus in which (RTP) sessions, the information flows to. This affects the security contexts being used and can cause previously separated information flows to share the same security context. This has very little impact on the performance of the security mechanism of the RTP sessions. In cases where one would have applied different security policies on the different RTP streams being bundled, or where the parties having access to the security contexts would have differed between the RTP streams, additional analysis of the implications are needed before selecting to apply BUNDLE.
Соображения безопасности, определённые в [RFC3264] и [RFC5888], применяются к расширению BUNDLE. BUNDLE не изменяет, какая информация, например потоки RTP, передаётся по сети, за исключением использования элемента MID SDES, как обсуждается ниже. Главным образом он изменяет, на какие адреса и порты и, следовательно, в какие (RTP) сеансы направляется информация. Это влияет на используемые контексты безопасности и может привести к тому, что ранее разделённые информационные потоки будут совместно использовать один и тот же контекст безопасности. Это очень мало влияет на производительность механизма безопасности сеансов RTP. В случаях, когда к разным связываемым потокам RTP применялись бы разные политики безопасности или когда стороны, имеющие доступ к контекстам безопасности, различались бы между потоками RTP, перед выбором применения BUNDLE необходим дополнительный анализ последствий.
The identification-tag, independent of transport, RTCP SDES packet, or RTP header extension, can expose the value to parties beyond the signaling chain. Therefore, the identification-tag values MUST be generated in a fashion that does not leak user information, e.g., randomly or using a per-bundle group counter, and SHOULD be 3 bytes or less to allow them to efficiently fit into the MID RTP header extension. Note that if implementations use different methods for generating identification-tags, this could enable fingerprinting of the implementation making it vulnerable to targeted attacks. The identification-tag is exposed on the RTP stream level when included in the RTP header extensions; however, what it reveals of the RTP media stream structure of the endpoint and application was already possible to deduce from the RTP streams without the MID SDES header extensions. As the identification-tag is also used to route the media stream to the right application functionality, it is important that the value received is the one intended by the sender; thus, integrity and the authenticity of the source are important to prevent denial of service on the application. Existing SRTP configurations and other security mechanisms protecting the whole RTP/RTCP packets will provide the necessary protection.
identification-tag независимо от транспорта, пакета RTCP SDES или расширения заголовка RTP может раскрыть значение сторонам за пределами цепочки сигнализации. Поэтому значения identification-tag ДОЛЖНЫ формироваться так, чтобы не раскрывать пользовательскую информацию, например случайным образом или с использованием счётчика на уровне BUNDLE-группы, и СЛЕДУЕТ, чтобы они были не длиннее 3 байт, чтобы эффективно помещаться в расширение заголовка RTP MID. Обратите внимание, что если реализации используют разные методы формирования identification-tag, это может позволить выполнить фингерпринтинг реализации и сделать её уязвимой для целевых атак. identification-tag раскрывается на уровне потока RTP, когда он включается в расширения заголовка RTP; однако то, что он раскрывает о структуре медиапотоков RTP конечной точки и приложения, уже можно было вывести из потоков RTP и без расширений заголовка MID SDES. Поскольку identification-tag также используется для маршрутизации медиапотока к правильной функциональности приложения, важно, чтобы полученное значение было тем, которое задумал отправитель; таким образом, целостность и подлинность источника важны для предотвращения отказа в обслуживании приложения. Существующие конфигурации SRTP и другие механизмы безопасности, защищающие пакеты RTP/RTCP целиком, обеспечат необходимую защиту.
When the BUNDLE extension is used, the set of configurations of the security mechanism used in all the bundled media descriptions will need to be compatible so that they can be used simultaneously, at least per direction or endpoint. When using SRTP, this will be the case, at least for the IETF-defined key-management solutions due to their SDP attributes ("a=crypto", "a=fingerprint", "a=mikey") and their classification in [RFC8859].
Когда используется расширение BUNDLE, наборы конфигураций механизма безопасности, используемых во всех связанных описаниях медиа, должны быть совместимы, чтобы их можно было использовать одновременно, по крайней мере для каждого направления или конечной точки. При использовании SRTP это будет так, по крайней мере для определённых IETF решений управления ключами, благодаря их атрибутам SDP («a=crypto», «a=fingerprint», «a=mikey») и их классификации в [RFC8859].
The security considerations of "RTP Header Extension for the RTP Control Protocol (RTCP) Source Description Items" [RFC7941] require that when RTCP is confidentiality protected, any SDES RTP header extension carrying an SDES item, such as the MID RTP header extension, is also protected using commensurate strength algorithms. However, assuming the above requirements and recommendations are followed, there are no known significant security risks with leaving the MID RTP header extension without confidentiality protection. Therefore, this specification updates RFC 7941 by adding the exception that this requirement MAY be ignored for the MID RTP header extension. Security mechanisms for RTP/RTCP are discussed in "Options for Securing RTP Sessions" [RFC7201], for example, SRTP [RFC3711] can provide the necessary security functions of ensuring the integrity and source authenticity.
Соображения безопасности документа «RTP Header Extension for the RTP Control Protocol (RTCP) Source Description Items» [RFC7941] требуют, чтобы при защите конфиденциальности RTCP любое расширение заголовка RTP SDES, несущее элемент SDES, такое как расширение заголовка RTP MID, также защищалось с помощью соразмерных по стойкости алгоритмов. Однако при условии соблюдения приведённых выше требований и рекомендаций нет известных значительных рисков безопасности в том, чтобы оставить расширение заголовка RTP MID без защиты конфиденциальности. Поэтому настоящая спецификация обновляет RFC 7941, добавляя исключение, согласно которому это требование МОЖЕТ игнорироваться для расширения заголовка RTP MID. Механизмы безопасности для RTP/RTCP обсуждаются в «Options for Securing RTP Sessions» [RFC7201]; например, SRTP [RFC3711] может обеспечить необходимые функции безопасности для обеспечения целостности и подлинности источника.

Appendix A. Design Considerations
Приложение A. Соображения по проектированию
One of the main issues regarding the BUNDLE grouping extensions has been whether, in offers and answers, the same port value can be inserted in "m=" lines associated with a BUNDLE group, as the purpose of the extension is to negotiate the usage of a single transport for media specified by the "m=" sections. Issues with both approaches, discussed in the Appendix, have been raised. The outcome was to specify a mechanism that uses offers with both different and identical port values.
Одним из главных вопросов, касающихся расширений группировки BUNDLE, был вопрос о том, можно ли в предложениях и ответах вставлять одно и то же значение порта в строки «m=», связанные с BUNDLE-группой, поскольку назначение расширения — согласовать использование одного транспорта для медиа, заданных секциями «m=». Были подняты проблемы, связанные с обоими подходами (обсуждаются в приложении). Результатом стала спецификация механизма, использующего предложения как с разными, так и с одинаковыми значениями портов.
Below are the primary issues that have been considered when defining the "BUNDLE" grouping extension:
Ниже перечислены основные вопросы, которые рассматривались при определении расширения группировки «BUNDLE»:
1) Interoperability with existing User Agents (UAs).
1) Совместимость с существующими пользовательскими агентами (UA).
2) Interoperability with intermediary Back-to-Back User Agent (B2BUA) and proxy entities.
2) Совместимость с промежуточными объектами Back-to-Back User Agent (B2BUA) и прокси.
3) Time to gather, and the number of, ICE candidates.
3) Время сбора и количество кандидатов ICE.
4) Different error scenarios and when they occur.
4) Различные сценарии ошибок и то, когда они возникают.
5) SDP offer/answer impacts, including usage of port number value zero.
5) Влияние на «предложение/ответ» SDP, включая использование нулевого значения номера порта.

A.2. Usage of Port Number Value Zero
A.2. Использование нулевого значения номера порта
In an offer or answer, the media specified by an "m=" section can be disabled/rejected by setting the port number value to zero. This is different from, e.g., using the SDP direction attributes, where RTCP traffic will continue even if the SDP 'inactive' attribute is indicated for the associated "m=" section.
В предложении или ответе медиа, заданные секцией «m=», могут быть отключены или отклонены путём установки значения номера порта в ноль. Это отличается, например, от использования атрибутов направления SDP, когда трафик RTCP продолжается, даже если для соответствующей секции «m=» указан атрибут SDP 'inactive'.
If each "m=" section associated with a BUNDLE group would contain different port values, and one of those port values would be used for a BUNDLE address:port associated with the BUNDLE group, problems would occur if an endpoint wants to disable/reject the "m=" section associated with that port, by setting the port value to zero. After that, no "m=" section would contain the port value that is used for the BUNDLE address:port. In addition, it is unclear what would happen to the ICE candidates associated with the "m=" section, as they are also used for the BUNDLE address:port.
Если каждая секция «m=», связанная с BUNDLE-группой, содержала бы разные значения портов и одно из этих значений порта использовалось бы для BUNDLE-адреса:порта, связанного с BUNDLE-группой, возникли бы проблемы, если конечная точка захочет отключить или отклонить секцию «m=», связанную с этим портом, установив значение порта в ноль. После этого ни одна секция «m=» не содержала бы значения порта, используемого для BUNDLE-адреса:порта. Кроме того, неясно, что произойдёт с кандидатами ICE, связанными с этой секцией «m=», поскольку они также используются для BUNDLE-адреса:порта.
A.3. B2BUA and Proxy Interoperability
A.3. Совместимость B2BUA и прокси
Some back-to-back user agents may be configured in a mode where if the incoming call leg contains an SDP attribute the B2BUA does not understand, the B2BUA still generates that SDP attribute in the Offer for the outgoing call leg. Consider a B2BUA that did not understand the SDP 'rtcp' attribute, defined in RFC 3605, yet acted this way. Further assume that the B2BUA was configured to tear down any call where it did not see any RTCP for 5 minutes. In this case, if the B2BUA received an Offer like:
Некоторые back-to-back пользовательские агенты могут быть настроены в режиме, когда, если входящее плечо вызова содержит атрибут SDP, который B2BUA не понимает, B2BUA всё равно формирует этот атрибут SDP в предложении для исходящего плеча вызова. Рассмотрим B2BUA, который не понимал атрибут SDP 'rtcp', определённый в RFC 3605, но действовал таким образом. Предположим далее, что B2BUA был настроен разрывать любой вызов, в котором он не видит RTCP в течение 5 минут. В этом случае, если B2BUA получил предложение вида:
SDP Offer
Предложение SDP
v=0 o=alice 2890844526 2890844526 IN IP4 atlanta.example.com s= c=IN IP4 atlanta.example.com t=0 0 m=audio 49170 RTP/AVP 0 a=rtcp:53020
v=0 o=alice 2890844526 2890844526 IN IP4 atlanta.example.com s= c=IN IP4 atlanta.example.com t=0 0 m=audio 49170 RTP/AVP 0 a=rtcp:53020
It would be looking for RTCP on port 49171 but would not see any because the RTCP would be on port 53020, and after five minutes, it would tear down the call. Similarly, a B2BUA that did not understand BUNDLE yet put it in its offer may be looking for media on the wrong port and tear down the call. It is worth noting that a B2BUA that generated an Offer with capabilities it does not understand is not compliant with the specifications.
Он искал бы RTCP на порту 49171, но не увидел бы его, поскольку RTCP был бы на порту 53020, и через пять минут разорвал бы вызов. Аналогично B2BUA, который не понимал BUNDLE, но всё же поместил его в своё предложение, может искать медиа на неправильном порту и разорвать вызов. Стоит отметить, что B2BUA, сформировавший предложение с возможностями, которые он не понимает, не соответствует спецификациям.
A.3.1. Traffic Policing
A.3.1. Политика трафика
Sometimes intermediaries do not act as B2BUAs, in the sense that they don't modify SDP bodies nor do they terminate SIP dialogs. However, they may still use SDP information (e.g., IP address and port) in order to control traffic gating functions and to set traffic policing rules. There might be rules that will trigger a session to be terminated in case media is not sent or received on the ports retrieved from the SDP. This typically occurs once the session is already established and ongoing.
Иногда промежуточные объекты не действуют как B2BUA в том смысле, что они не изменяют тела SDP и не завершают диалоги SIP. Однако они всё ещё могут использовать информацию SDP (например, IP-адрес и порт) для управления функциями пропускания трафика и установки правил его полиции. Могут существовать правила, которые приведут к завершению сеанса, если медиа не отправляются или не принимаются на портах, полученных из SDP. Обычно это происходит, когда сеанс уже установлен и идёт.
A.3.2. Bandwidth Allocation
A.3.2. Распределение полосы пропускания
Sometimes, intermediaries do not act as B2BUAs, in the sense that they don't modify SDP bodies nor do they terminate SIP dialogs. However, they may still use SDP information (e.g., codecs and media types) in order to control bandwidth allocation functions. The bandwidth allocation is done per "m=" section, which means that it might not be enough if media specified by all "m=" sections try to use that bandwidth. That may simply lead to either bad user experience or termination of the call.
Иногда промежуточные объекты не действуют как B2BUA в том смысле, что они не изменяют тела SDP и не завершают диалоги SIP. Однако они всё ещё могут использовать информацию SDP (например, кодеки и типы медиа) для управления функциями распределения полосы пропускания. Распределение полосы пропускания выполняется для каждой секции «m=», что означает, что её может не хватить, если медиа, заданные всеми секциями «m=», попытаются использовать эту полосу. Это может просто привести к плохому опыту пользователя или к завершению вызова.
A.4. Candidate Gathering
A.4. Сбор кандидатов
When using ICE, a candidate needs to be gathered for each port. This takes approximately 20 ms extra for each extra "m=" section due to the NAT pacing requirements. All of this gathering can be overlapped with other things while, e.g., a web page is loading to minimize the impact. If the client only wants to generate Traversal Using Relays around NAT (TURN) or STUN ICE candidates for one of the "m=" lines and then use Trickle ICE [RFC8838] to get the non-host ICE candidates for the rest of the "m=" sections, it MAY do that and will not need any additional gathering time.
При использовании ICE кандидата нужно собрать для каждого порта. Это занимает примерно на 20 мс больше для каждой дополнительной секции «m=» из-за требований к темпу NAT. Весь этот сбор может перекрываться с другими процессами, пока, например, загружается веб-страница, чтобы минимизировать влияние. Если клиент хочет сформировать кандидатов ICE только типа Traversal Using Relays around NAT (TURN) или STUN для одной из строк «m=», а затем использовать Trickle ICE [RFC8838] для получения кандидатов ICE, не являющихся локальными (host), для остальных секций «m=», он МОЖЕТ это сделать, и дополнительное время на сбор не потребуется.
Some people have suggested a TURN extension to get a bunch of TURN allocations at once. This would only provide a single STUN result, so in cases where the other end did not support BUNDLE, it may cause more use of the TURN server, but it would be quick in the cases where both sides supported BUNDLE and would fall back to a successful call in the other cases.
Некоторые предлагали расширение TURN для получения сразу нескольких выделений TURN. Это дало бы только один результат STUN, поэтому в случаях, когда другая сторона не поддерживала BUNDLE, это могло бы привести к большему использованию сервера TURN, но было бы быстрым в случаях, когда обе стороны поддерживали BUNDLE, и в остальных случаях приводило бы к успешному вызову.
