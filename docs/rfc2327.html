Abstract
Аннотация
This document defines the Session Description Protocol, SDP. SDP is intended for describing multimedia sessions for the purposes of session announcement, session invitation, and other forms of multimedia session initiation.
Настоящий документ определяет протокол описания сессий SDP. SDP предназначен для описания мультимедийных сессий с целью анонсирования сессий, приглашения на сессию и других форм инициирования мультимедийных сессий.
This document is a product of the Multiparty Multimedia Session Control (MMUSIC) working group of the Internet Engineering Task Force. Comments are solicited and should be addressed to the working group's mailing list at confctrl@isi.edu and/or the authors.
Настоящий документ является продуктом рабочей группы Multiparty Multimedia Session Control (MMUSIC) Инженерной группы Интернета. Комментарии приветствуются и должны направляться в список рассылки рабочей группы по адресу confctrl@isi.edu и/или автору.
1. Introduction
1. Введение
On the Internet multicast backbone (Mbone), a session directory tool is used to advertise multimedia conferences and communicate the conference addresses and conference tool-specific information necessary for participation. This document defines a session description protocol for this purpose, and for general real-time multimedia session description purposes. This memo does not describe multicast address allocation or the distribution of SDP messages in detail. These are described in accompanying memos. SDP is not intended for negotiation of media encodings.
В многоадресной магистрали Интернета (Mbone) инструмент каталога сессий используется для анонсирования мультимедийных конференций и передачи адресов конференций и специфичной для инструментов конференции информации, необходимой для участия. Настоящий документ определяет протокол описания сессий для этой цели, а также для общего описания сессий мультимедиа в реальном времени. В настоящем документе не описываются подробно распределение многоадресных адресов и распространение сообщений SDP. Они описаны в сопровождающих документах. SDP не предназначен для согласования кодировок медиа.
2. Background
2. Предыстория
The Mbone is the part of the internet that supports IP multicast, and thus permits efficient many-to-many communication. It is used extensively for multimedia conferencing. Such conferences usually have the property that tight coordination of conference membership is not necessary; to receive a conference, a user at an Mbone site only has to know the conference's multicast group address and the UDP ports for the conference data streams.
Mbone — это часть Интернета, поддерживающая IP-многоадресную рассылку и тем самым допускающая эффективную связь «многие ко многим». Она широко используется для мультимедийных конференций. Такие конференции обычно обладают тем свойством, что тесная координация состава участников не требуется; чтобы принять конференцию, пользователю на узле Mbone достаточно знать адрес многоадресной группы конференции и UDP-порты для потоков данных конференции.
Session directories assist the advertisement of conference sessions and communicate the relevant conference setup information to prospective participants. SDP is designed to convey such information to recipients. SDP is purely a format for session description - it does not incorporate a transport protocol, and is intended to use different transport protocols as appropriate including the Session Announcement Protocol [4], Session Initiation Protocol [11], Real- Time Streaming Protocol [12], electronic mail using the MIME extensions, and the Hypertext Transport Protocol.
Каталоги сессий способствуют анонсированию сессий конференций и передают потенциальным участникам соответствующую информацию о настройке конференции. SDP разработан для передачи такой информации получателям. SDP — это исключительно формат описания сессии: он не включает транспортный протокол и предназначен для использования различных транспортных протоколов по обстоятельствам, включая протокол анонсирования сессий (Session Announcement Protocol) [4], протокол инициирования сессий (Session Initiation Protocol) [11], протокол потоковой передачи в реальном времени (Real-Time Streaming Protocol) [12], электронную почту с расширениями MIME и протокол передачи гипертекста.
SDP is intended to be general purpose so that it can be used for a wider range of network environments and applications than just multicast session directories. However, it is not intended to support negotiation of session content or media encodings - this is viewed as outside the scope of session description.
SDP задуман как универсальный, чтобы его можно было применять в более широком диапазоне сетевых сред и приложений, нежели только каталоги многоадресных сессий. Однако он не предназначен для поддержки согласования содержимого сессии или кодировок медиа — это рассматривается как выходящее за рамки описания сессии.

4. SDP Usage
4. Использование SDP
4.1. Multicast Announcements
4.1. Многоадресные анонсы
SDP is a session description protocol for multimedia sessions. A common mode of usage is for a client to announce a conference session by periodically multicasting an announcement packet to a well known multicast address and port using the Session Announcement Protocol (SAP).
SDP — это протокол описания сессий для мультимедийных сессий. Распространённый способ использования состоит в том, что клиент анонсирует сессию конференции, периодически рассылая многоадресно пакет-анонс на широко известный многоадресный адрес и порт с использованием протокола анонсирования сессий (SAP).
SAP packets are UDP packets with the following format:
Пакеты SAP — это UDP-пакеты следующего формата:
|--------------------| | SAP header | |--------------------| | text payload | |//////////
|--------------------| | SAP header | |--------------------| | text payload | |//////////
The header is the Session Announcement Protocol header. SAP is described in more detail in a companion memo [4]
Заголовок — это заголовок протокола анонсирования сессий. SAP более подробно описан в сопровождающем документе [4].
The text payload is an SDP session description, as described in this memo. The text payload should be no greater than 1 Kbyte in length. If announced by SAP, only one session announcement is permitted in a single packet.
Текстовая полезная нагрузка — это описание сессии SDP, как описано в настоящем документе. Длина текстовой полезной нагрузки не должна превышать 1 Кбайт. Если анонс выполняется через SAP, в одном пакете допускается только один анонс сессии.
4.2. Email and WWW Announcements
4.2. Анонсы по электронной почте и в WWW
Alternative means of conveying session descriptions include electronic mail and the World Wide Web. For both email and WWW distribution, the use of the MIME content type "application/sdp" should be used. This enables the automatic launching of applications for participation in the session from the WWW client or mail reader in a standard manner. Note that announcements of multicast sessions made only via email or the World Wide Web (WWW) do not have the property that the receiver of a session announcement can necessarily receive the session because the multicast sessions may be restricted in scope, and access to the WWW server or reception of email is possible outside this scope. SAP announcements do not suffer from this mismatch.
Альтернативные средства передачи описаний сессий включают электронную почту и Всемирную паутину. Для распространения как по электронной почте, так и через WWW следует использовать тип содержимого MIME «application/sdp». Это позволяет стандартным образом автоматически запускать приложения для участия в сессии из WWW-клиента или программы чтения почты. Обратите внимание, что анонсы многоадресных сессий, сделанные только по электронной почте или через Всемирную паутину (WWW), не обладают тем свойством, что получатель анонса сессии обязательно сможет принять эту сессию, поскольку многоадресные сессии могут быть ограничены по области действия, а доступ к WWW-серверу или получение почты возможны вне этой области. Анонсы SAP не страдают от такого несоответствия.
5. Requirements and Recommendations
5. Требования и рекомендации
The purpose of SDP is to convey information about media streams in multimedia sessions to allow the recipients of a session description to participate in the session. SDP is primarily intended for use in an internetwork, although it is sufficiently general that it can describe conferences in other network environments.
Назначение SDP — передавать информацию о медиапотоках в мультимедийных сессиях, чтобы получатели описания сессии могли участвовать в сессии. SDP предназначен в первую очередь для использования в объединённой сети, хотя он достаточно универсален, чтобы описывать конференции и в иных сетевых средах.
A multimedia session, for these purposes, is defined as a set of media streams that exist for some duration of time. Media streams can be many-to-many. The times during which the session is active need not be continuous.
Для этих целей мультимедийная сессия определяется как набор медиапотоков, существующих в течение некоторого промежутка времени. Медиапотоки могут быть «многие ко многим». Периоды, в течение которых сессия активна, не обязаны быть непрерывными.
Thus far, multicast based sessions on the Internet have differed from many other forms of conferencing in that anyone receiving the traffic can join the session (unless the session traffic is encrypted). In such an environment, SDP serves two primary purposes. It is a means to communicate the existence of a session, and is a means to convey sufficient information to enable joining and participating in the session. In a unicast environment, only the latter purpose is likely to be relevant.
До сих пор многоадресные сессии в Интернете отличались от многих иных форм конференций тем, что любой, кто принимает трафик, может присоединиться к сессии (если только трафик сессии не зашифрован). В такой среде SDP служит двум основным целям. Он является средством сообщения о существовании сессии и средством передачи достаточной информации, позволяющей присоединиться к сессии и участвовать в ней. В одноадресной среде, вероятно, имеет значение только последняя цель.
Thus SDP includes:
Таким образом, SDP включает:
o Session name and purpose
o Имя и назначение сессии
o Time(s) the session is active
o Время (времена), когда сессия активна
o The media comprising the session
o Медиа, составляющие сессию
o Information to receive those media (addresses, ports, formats and so on)
o Информацию для приёма этих медиа (адреса, порты, форматы и т. д.)
As resources necessary to participate in a session may be limited, some additional information may also be desirable:
Поскольку ресурсы, необходимые для участия в сессии, могут быть ограничены, может также оказаться желательной некоторая дополнительная информация:
o Information about the bandwidth to be used by the conference
o Информация о полосе пропускания, которая будет использоваться конференцией
o Contact information for the person responsible for the session In general, SDP must convey sufficient information to be able to join a session (with the possible exception of encryption keys) and to announce the resources to be used to non-participants that may need to know.
o Контактная информация лица, ответственного за сессию В общем случае SDP должен передавать достаточную информацию, чтобы можно было присоединиться к сессии (за возможным исключением ключей шифрования), и объявлять ресурсы, которые будут использоваться, неучастникам, которым это может понадобиться знать.
5.1. Media Information
5.1. Информация о медиа
SDP includes:
SDP включает:
o The type of media (video, audio, etc)
o Тип медиа (видео, аудио и т. д.)
o The transport protocol (RTP/UDP/IP, H.320, etc)
o Транспортный протокол (RTP/UDP/IP, H.320 и т. д.)
o The format of the media (H.261 video, MPEG video, etc)
o Формат медиа (видео H.261, видео MPEG и т. д.)
For an IP multicast session, the following are also conveyed:
Для сессии IP-многоадресной рассылки также передаётся:
o Multicast address for media o Transport Port for media
o Многоадресный адрес для медиа o Транспортный порт для медиа
This address and port are the destination address and destination port of the multicast stream, whether being sent, received, or both.
Этот адрес и порт являются адресом назначения и портом назначения многоадресного потока — независимо от того, отправляется он, принимается или и то и другое.
For an IP unicast session, the following are conveyed:
Для сессии IP-одноадресной передачи передаётся:
o Remote address for media o Transport port for contact address
o Удалённый адрес для медиа o Транспортный порт для адреса контакта
The semantics of this address and port depend on the media and transport protocol defined. By default, this is the remote address and remote port to which data is sent, and the remote address and local port on which to receive data. However, some media may define to use these to establish a control channel for the actual media flow.
Семантика этого адреса и порта зависит от определённых медиа и транспортного протокола. По умолчанию это удалённый адрес и удалённый порт, на которые отправляются данные, а также удалённый адрес и локальный порт, на которых принимаются данные. Однако некоторые медиа могут определять использование этих адреса и порта для установления канала управления фактическим медиапотоком.
5.2. Timing Information
5.2. Информация о времени
Sessions may either be bounded or unbounded in time. Whether or not they are bounded, they may be only active at specific times.
Сессии могут быть ограничены или не ограничены во времени. Независимо от того, ограничены они или нет, они могут быть активны только в определённые моменты времени.
SDP can convey:
SDP может передавать:
o An arbitrary list of start and stop times bounding the session
o Произвольный список времён начала и остановки, ограничивающих сессию
o For each bound, repeat times such as "every Wednesday at 10am for one hour" This timing information is globally consistent, irrespective of local time zone or daylight saving time.
o Для каждой границы — повторяющиеся времена, например «каждую среду в 10 утра в течение одного часа» Эта информация о времени является глобально согласованной, независимо от местного часового пояса или перехода на летнее время.
5.3. Private Sessions
5.3. Закрытые сессии
It is possible to create both public sessions and private sessions. Private sessions will typically be conveyed by encrypting the session description to distribute it. The details of how encryption is performed are dependent on the mechanism used to convey SDP - see [4] for how this is done for session announcements.
Можно создавать как открытые, так и закрытые сессии. Закрытые сессии обычно передаются путём шифрования описания сессии для его распространения. Детали того, как выполняется шифрование, зависят от механизма, используемого для передачи SDP; см. [4] относительно того, как это делается для анонсов сессий.
If a session announcement is private it is possible to use that private announcement to convey encryption keys necessary to decode each of the media in a conference, including enough information to know which encryption scheme is used for each media.
Если анонс сессии является закрытым, можно использовать этот закрытый анонс для передачи ключей шифрования, необходимых для декодирования каждого из медиа в конференции, включая достаточно информации, чтобы знать, какая схема шифрования используется для каждого медиа.
5.4. Obtaining Further Information about a Session
5.4. Получение дополнительной информации о сессии
A session description should convey enough information to decide whether or not to participate in a session. SDP may include additional pointers in the form of Universal Resources Identifiers (URIs) for more information about the session.
Описание сессии должно передавать достаточно информации, чтобы решить, участвовать ли в сессии. SDP может включать дополнительные указатели в виде универсальных идентификаторов ресурсов (URI) для получения дополнительной информации о сессии.
5.5. Categorisation
5.5. Категоризация
When many session descriptions are being distributed by SAP or any other advertisement mechanism, it may be desirable to filter announcements that are of interest from those that are not. SDP supports a categorisation mechanism for sessions that is capable of being automated.
Когда распространяется множество описаний сессий через SAP или любой другой механизм анонсирования, может оказаться желательным отфильтровать представляющие интерес анонсы от прочих. SDP поддерживает механизм категоризации сессий, допускающий автоматизацию.
5.6. Internationalization
5.6. Интернационализация
The SDP specification recommends the use of the ISO 10646 character sets in the UTF-8 encoding (RFC 2044) to allow many different languages to be represented. However, to assist in compact representations, SDP also allows other character sets such as ISO 8859-1 to be used when desired. Internationalization only applies to free-text fields (session name and background information), and not to SDP as a whole.
Спецификация SDP рекомендует использовать наборы символов ISO 10646 в кодировке UTF-8 (RFC 2044), чтобы допустить представление множества различных языков. Однако для содействия компактным представлениям SDP также допускает использование других наборов символов, таких как ISO 8859-1, когда это желательно. Интернационализация применяется только к полям свободного текста (имя сессии и фоновая информация), а не к SDP в целом.
6. SDP Specification
6. Спецификация SDP
SDP session descriptions are entirely textual using the ISO 10646 character set in UTF-8 encoding. SDP field names and attributes names use only the US-ASCII subset of UTF-8, but textual fields and attribute values may use the full ISO 10646 character set. The textual form, as opposed to a binary encoding such as ASN/1 or XDR, was chosen to enhance portability, to enable a variety of transports to be used (e.g, session description in a MIME email message) and to allow flexible, text-based toolkits (e.g., Tcl/Tk ) to be used to generate and to process session descriptions. However, since the total bandwidth allocated to all SAP announcements is strictly limited, the encoding is deliberately compact. Also, since announcements may be transported via very unreliable means (e.g., email) or damaged by an intermediate caching server, the encoding was designed with strict order and formatting rules so that most errors would result in malformed announcements which could be detected easily and discarded. This also allows rapid discarding of encrypted announcements for which a receiver does not have the correct key.
Описания сессий SDP являются полностью текстовыми и используют набор символов ISO 10646 в кодировке UTF-8. Имена полей и атрибутов SDP используют только подмножество US-ASCII набора UTF-8, но текстовые поля и значения атрибутов могут использовать полный набор символов ISO 10646. Текстовая форма, в отличие от двоичного кодирования, такого как ASN/1 или XDR, была выбрана для повышения переносимости, чтобы можно было использовать разнообразные транспорты (например, описание сессии в письме MIME) и чтобы можно было применять гибкие инструментальные средства на основе текста (например, Tcl/Tk) для генерации и обработки описаний сессий. Однако поскольку общая полоса пропускания, выделяемая на все анонсы SAP, строго ограничена, кодировка намеренно сделана компактной. Кроме того, поскольку анонсы могут передаваться крайне ненадёжными средствами (например, по электронной почте) или быть повреждены промежуточным кэширующим сервером, кодировка была спроектирована со строгими правилами порядка и форматирования, чтобы большинство ошибок приводило к некорректным анонсам, которые можно легко обнаружить и отбросить. Это также позволяет быстро отбрасывать зашифрованные анонсы, для которых у получателя нет правильного ключа.
An SDP session description consists of a number of lines of text of the form <type>=<value> <type> is always exactly one character and is case-significant. <value> is a structured text string whose format depends on <type>. It also will be case-significant unless a specific field defines otherwise. Whitespace is not permitted either side of the `=' sign. In general <value> is either a number of fields delimited by a single space character or a free format string.
Описание сессии SDP состоит из некоторого числа строк текста вида <type>=<value>. <type> всегда представляет ровно один символ и чувствителен к регистру. <value> — это структурированная текстовая строка, формат которой зависит от <type>. A session description consists of a session-level description (details that apply to the whole session and all media streams) and optionally several media-level descriptions (details that apply onto to a single media stream).
Описание сессии состоит из описания уровня сессии (подробности, применимые ко всей сессии и всем медиапотокам) и, необязательно, нескольких описаний уровня медиа (подробности, применимые к отдельному медиапотоку).
An announcement consists of a session-level section followed by zero or more media-level sections. The session-level part starts with a `v=' line and continues to the first media-level section. The media description starts with an `m=' line and continues to the next media description or end of the whole session description. In general, session-level values are the default for all media unless overridden by an equivalent media-level value.
Анонс состоит из секции уровня сессии, за которой следуют ноль или более секций уровня медиа. Часть уровня сессии начинается со строки «v=» и продолжается до первой секции уровня медиа. Описание медиа начинается со строки «m=» и продолжается до следующего описания медиа или до конца всего описания сессии. В общем случае значения уровня сессии являются значениями по умолчанию для всех медиа, если не переопределены эквивалентным значением уровня медиа.
When SDP is conveyed by SAP, only one session description is allowed per packet. When SDP is conveyed by other means, many SDP session descriptions may be concatenated together (the `v=' line indicating the start of a session description terminates the previous description). Text records such as the session name and information are bytes strings which may contain any byte with the exceptions of 0x00 (Nul), 0x0a (ASCII newline) and 0x0d (ASCII carriage return). Initially "IP4" and "IP6" are defined. <address> is the globally unique address of the machine from which the session was created. For an address type of IP6, this is either the fully-qualified domain name of the machine, or the compressed textual representation of the IP version 6 address of the machine. For both IP4 and IP6, the fully-qualified domain name is the form that SHOULD be given unless this is unavailable, in which case the globally unique address may be substituted. o "t=" fields specify the start and stop times for a conference session. Multiple "t=" fields may be used if a session is active at multiple irregularly spaced times; each additional "t=" field specifies an additional period of time for which the session will be active. If the session is active at regular times, an "r=" field (see below) should be used in addition to and following a "t=" field - in which case the "t=" field specifies the start and stop times of the repeat sequence.
o Поля «t=» задают время начала и остановки сессии конференции. o The first and second sub-fields give the start and stop times for the conference respectively. These values are the decimal representation of Network Time Protocol (NTP) time values in seconds [1]. To convert these values to UNIX time, subtract decimal 2208988800.

User interfaces should strongly discourage the creation of unbounded and permanent sessions as they give no information about when the session is actually going to terminate, and so make scheduling difficult.
Пользовательским интерфейсам следует настоятельно отговаривать от создания неограниченных и постоянных сессий, поскольку они не дают информации о том, когда сессия фактически завершится, и поэтому затрудняют планирование.
The general assumption may be made, when displaying unbounded sessions that have not timed out to the user, that an unbounded session will only be active until half an hour from the current time or the session start time, whichever is the later. If behaviour other than this is required, an end-time should be given and modified as appropriate when new information becomes available about when the session should really end.
При отображении пользователю неограниченных сессий, срок которых не истёк, можно принять общее допущение, что неограниченная сессия будет активна только до получаса от текущего времени или от времени начала сессии — в зависимости от того, что позже. Если требуется иное поведение, следует задать время окончания и изменять его по мере поступления новой информации о том, когда сессия должна в действительности завершиться.
Permanent sessions may be shown to the user as never being active unless there are associated repeat times which state precisely when the session will be active. In general, permanent sessions should not be created for any session expected to have a duration of less than 2 months, and should be discouraged for sessions expected to have a duration of less than 6 months.
Постоянные сессии могут отображаться пользователю как никогда не активные, если только нет связанных времён повторения, точно указывающих, когда сессия будет активна. В общем случае постоянные сессии не следует создавать для любой сессии, предположительно имеющей длительность менее 2 месяцев, и их следует избегать для сессий с ожидаемой длительностью менее 6 месяцев.

A media description may have any number of attributes ("a=" fields) which are media specific. These are referred to as "media-level" attributes and add information about the media stream. Attribute fields can also be added before the first media field; these "session-level" attributes convey additional information that applies to the conference as a whole rather than to individual media; an example might be the conference's floor control policy.
Описание медиа может иметь любое количество атрибутов (полей «a=»), специфичных для этого медиа. Они называются атрибутами «уровня медиа» и добавляют информацию о медиапотоке. Поля атрибутов могут быть добавлены также перед первым полем медиа; такие атрибуты называются атрибутами «уровня сессии» и применяются ко всем медиа сессии, если не переопределены атрибутом того же имени на уровне медиа.
Attribute fields may be of two forms:
Поля атрибутов могут быть двух форм:
o property attributes. A property attribute is simply of the form "a=<flag>". These are binary attributes, and the presence of the attribute conveys that the attribute is a property of the session. An example might be "a=recvonly".
o атрибуты-свойства. Атрибут-свойство имеет просто вид «a=<flag>». Это бинарные атрибуты, и наличие атрибута означает, что этот атрибут является свойством сессии. Примером может служить «a=recvonly».
o value attributes. A value attribute is of the form "a=<attribute>:<value>". An example might be that a whiteboard could have the value attribute "a=orient:landscape"
o атрибуты-значения. Атрибут-значение имеет вид «a=<attribute>:<value>». Примером может служить атрибут-значение «a=orient:landscape» у доски.
Attribute interpretation depends on the media tool being invoked. Thus receivers of session descriptions should be configurable in their interpretation of announcements in general and of attributes in particular.
Интерпретация атрибутов зависит от вызываемого медиаинструмента. Поэтому получатели описаний сессий должны быть настраиваемыми в отношении интерпретации анонсов в целом и атрибутов в частности.
Attribute names must be in the US-ASCII subset of ISO-10646/UTF-8. Attribute values are byte strings, and MAY use any byte value except 0x00 (Nul), 0x0A (LF), and 0x0D (CR). By default, attribute values are to be interpreted as in ISO-10646 character set with UTF-8 encoding. Unlike other text fields, attribute values are NOT normally affected by the `charset' attribute as this would make comparisons against known values problematic. However, when an attribute is defined, it can be defined to be charset-dependent, in which case it's value should be interpreted in the session charset rather than in ISO-10646.
Имена атрибутов должны находиться в подмножестве US-ASCII набора ISO-10646/UTF-8. Значения атрибутов — это строки байтов, и они МОГУТ использовать любое значение байта, кроме 0x00 (Nul), 0x0A (LF) и 0x0D (CR). По умолчанию значения атрибутов должны интерпретироваться так же, как в наборе символов ISO-10646 с кодировкой UTF-8. В отличие от других текстовых полей, значения атрибутов НЕ зависят от атрибута charset. Значения атрибутов могут содержать любые символы, включая пробелы, и потому границы атрибутов определяются только символом конца строки.
Attributes that will be commonly used can be registered with IANA (see Appendix B). Unregistered attributes should begin with "X-" to prevent inadvertent collision with registered attributes. In either case, if an attribute is received that is not understood, it should simply be ignored by the receiver.
Атрибуты, которые будут широко использоваться, могут быть зарегистрированы в IANA (см. Приложение B). Незарегистрированные атрибуты должны начинаться с «X-», чтобы предотвратить случайное совпадение с зарегистрированными атрибутами. В любом случае, если получен атрибут, который не понят,
Media Announcements m=<media> <port> <transport> <fmt list>
Анонсы медиа m=<media> <port> <transport> <fmt list>
A session description may contain a number of media descriptions. Each media description starts with an "m=" field, and is terminated by either the next "m=" field or by the end of the session description. A media field also has several sub-fields:
Описание сессии может содержать ряд описаний медиа. Каждое описание медиа начинается с поля «m=» и завершается либо следующим полем «m=», либо концом описания сессии. Поле медиа также имеет несколько подполей:
o The first sub-field is the media type. Currently defined media are "audio", "video", "application", "data" and "control", though this list may be extended as new communication modalities emerge (e.g., telepresense). The difference between "application" and "data" is that the former is a media flow such as whiteboard information, and the latter is bulk-data transfer such as multicasting of program executables which will not typically be displayed to the user. "control" is used to specify an additional conference control channel for the session.
o Первое подполе — тип медиа. В настоящее время определены медиа «audio», «video», «application», «data» и «control», хотя этот список может быть расширен по мере появления новых способов связи (например, телеприсутствия). Разница между «application» и «data» состоит в том, что первое — это медиапоток, такой как информация доски, а второе — это передача больших объёмов данных, например многоадресная рассылка исполняемых программ, которая обычно не отображается пользователю. «control» используется для указания дополнительного канала управления конференцией для этой сессии.
o The second sub-field is the transport port to which the media stream will be sent. The meaning of the transport port depends on the network being used as specified in the relevant "c" field and on the transport protocol defined in the third sub-field. Other ports used by the media application (such as the RTCP port, see [2]) should be derived algorithmically from the base media port.
o Второе подполе — транспортный порт, на который будет отправляться медиапоток. Смысл транспортного порта зависит от используемой сети, как указано в соответствующем поле «c», и от транспортного протокола, определённого в третьем подполе. Другие подполя порта могут быть определены для конкретных транспортных протоколов по мере необходимости.
Note: For transports based on UDP, the value should be in the range 1024 to 65535 inclusive. For RTP compliance it should be an even number. For applications where hierarchically encoded streams are being sent to a unicast address, it may be necessary to specify multiple transport ports. This is done using a similar notation to that used for IP multicast addresses in the "c=" field:
Примечание. Для транспортов на основе UDP значение должно находиться в диапазоне от 1024 до 65535 включительно. Для соответствия RTP оно должно быть чётным числом. Для приложений, в которых иерархически закодированные потоки отправляются на одноадресный адрес, может потребоваться указать несколько транспортных портов. Это делается с использованием нотации, аналогичной той, что применяется для многоадресных адресов IP в поле «c=»:
m=<media> <port>/<number of ports> <transport> <fmt list>
m=<media> <port>/<number of ports> <transport> <fmt list>
In such a case, the ports used depend on the transport protocol. For RTP, only the even ports are used for data and the corresponding one-higher odd port is used for RTCP. For example:
В таком случае используемые порты зависят от транспортного протокола. Для RTP для данных используются только чётные порты, а соответствующий нечётный порт с бо́льшим номером используется для RTCP. Например:
m=video 49170/2 RTP/AVP 31
m=video 49170/2 RTP/AVP 31
would specify that ports 49170 and 49171 form one RTP/RTCP pair and 49172 and 49173 form the second RTP/RTCP pair. RTP/AVP is the transport protocol and 31 is the format (see below).
задавало бы, что порты 49170 и 49171 образуют одну пару RTP/RTCP, а 49172 и 49173 образуют вторую пару RTP/RTCP. RTP/AVP — это транспортный протокол, а 31 — формат (см. ниже).
It is illegal for both multiple addresses to be specified in the "c=" field and for multiple ports to be specified in the "m=" field in the same session description.
Недопустимо одновременно указывать несколько адресов в поле «c=» и несколько портов в поле «m=» в одном и том же описании сессии; такие комбинации должны задаваться только через упомянутые выше механизмы указания нескольких адресов.
o The third sub-field is the transport protocol. The transport protocol values are dependent on the address-type field in the "c=" fields. Thus a "c=" field of IP4 defines that the transport protocol runs over IP4. For IP4, it is normally expected that most media traffic will be carried as RTP over UDP. The following transport protocols are preliminarily defined, but may be extended through registration of new protocols with IANA:
o Третье подполе — транспортный протокол. Значения транспортного протокола зависят от поля типа адреса в полях «c=». Так, поле «c=» со значением IP4 определяет, что транспортный протокол работает поверх IP4. Для IP4 обычно предполагается, что большинство медиа будет передаваться по протоколу RTP/AVP, но могут использоваться и другие транспорты. Следующие транспортные протоколы определены:
- RTP/AVP - the IETF's Realtime Transport Protocol using the Audio/Video profile carried over UDP.
- RTP/AVP — протокол передачи в реальном времени IETF, использующий профиль Audio/Video поверх UDP;
- udp - User Datagram Protocol
- udp — протокол дейтаграмм пользователя (User Datagram Protocol).
If an application uses a single combined proprietary media format and transport protocol over UDP, then simply specifying the transport protocol as udp and using the format field to distinguish the combined protocol is recommended. If a transport protocol is used over UDP to carry several distinct media types that need to be distinguished by a session directory, then specifying the transport protocol and media format separately is necessary. RTP is an example of a transport-protocol that carries multiple payload formats that must be distinguished by the session directory for it to know how to start appropriate tools, relays, mixers or recorders. The main reason to specify the transport-protocol in addition to the media format is that the same standard media formats may be carried over different transport protocols even when the network protocol is the same - a historical example is vat PCM audio and RTP PCM audio. In addition, relays and monitoring tools that are transport-protocol-specific but format-independent are possible.
Если приложение использует единый объединённый проприетарный формат медиа и транспортный протокол поверх UDP, то рекомендуется просто указать транспортный протокол как udp и использовать поле формата для различения объединённого протокола. Если транспортный протокол используется поверх UDP для передачи нескольких различных типов медиа, которые должны различаться каталогом сессий, то необходимо указывать транспортный протокол и формат медиа отдельно. RTP является примером транспортного протокола, который несёт множество форматов полезной нагрузки, которые должны различаться каталогом сессий, чтобы он знал, как запускать подходящие инструменты, ретрансляторы, микшеры или средства записи. Основная причина указывать транспортный протокол в дополнение к формату медиа состоит в том, что одни и те же стандартные форматы медиа могут передаваться по разным транспортным протоколам даже при одном и том же сетевом протоколе — историческим примером служат аудио PCM в vat и аудио PCM в RTP, которые используют разные транспортные протоколы при одном и том же формате кодирования.
For RTP media streams operating under the RTP Audio/Video Profile [3], the protocol field is "RTP/AVP". Should other RTP profiles be defined in the future, their profiles will be specified in the same way. For example, the protocol field "RTP/XYZ" would specify RTP operating under a profile whose short name is "XYZ".
Для медиапотоков RTP, работающих в соответствии с профилем RTP Audio/Video [3], поле протокола — «RTP/AVP». Если в будущем будут определены другие профили RTP, их профили будут задаваться таким же образом. Например, поле протокола «RTP/XYZ» означало бы RTP, работающий по профилю с кратким именем «XYZ».
o The fourth and subsequent sub-fields are media formats. For audio and video, these will normally be a media payload type as defined in the RTP Audio/Video Profile.
o Четвёртое и последующие подполя — это форматы медиа. Для аудио и видео они обычно представляют собой тип полезной нагрузки медиа, определённый в профиле RTP Audio/Video.
When a list of payload formats is given, this implies that all of these formats may be used in the session, but the first of these formats is the default format for the session.
Когда задан список форматов полезной нагрузки, это подразумевает, что все эти форматы могут использоваться в сессии, но первый из них является форматом по умолчанию для сессии.
For media whose transport protocol is not RTP or UDP the format field is protocol specific. Such formats should be defined in an additional specification document.
Для медиа, транспортный протокол которых не является RTP или UDP, поле формата специфично для протокола. Такие форматы должны быть определены в дополнительном документе-спецификации.
For media whose transport protocol is RTP, SDP can be used to provide a dynamic binding of media encoding to RTP payload type. The encoding names in the RTP AV Profile do not specify unique audio encodings (in terms of clock rate and number of audio channels), and so they are not used directly in SDP format fields. Instead, the payload type number should be used to specify the format for static payload types and the payload type number along with additional encoding information should be used for dynamically allocated payload types.
Для медиа, транспортный протокол которых — RTP, SDP может использоваться для обеспечения динамической привязки кодировки медиа к типу полезной нагрузки RTP. Имена кодировок в профиле RTP AV не задают уникальных аудиокодировок (в смысле частоты дискретизации и числа аудиоканалов). Для динамических типов полезной нагрузки эта привязка должна задаваться атрибутом rtpmap, описанным ниже в настоящем разделе.
An example of a static payload type is u-law PCM coded single channel audio sampled at 8KHz. This is completely defined in the RTP Audio/Video profile as payload type 0, so the media field for such a stream sent to UDP port 49232 is:
Примером статического типа полезной нагрузки является одноканальный звук, закодированный в PCM µ-law с частотой дискретизации 8 кГц. Он полностью определён в профиле RTP Audio/Video как тип полезной нагрузки 0, поэтому поле медиа для такого потока, отправляемого на UDP-порт 49232, будет:
m=video 49232 RTP/AVP 0
m=video 49232 RTP/AVP 0
An example of a dynamic payload type is 16 bit linear encoded stereo audio sampled at 16KHz. If we wish to use dynamic RTP/AVP payload type 98 for such a stream, additional information is required to decode it:
Примером динамического типа полезной нагрузки является 16-битный линейно закодированный стереозвук с частотой дискретизации 16 кГц. Если мы желаем использовать динамический тип полезной нагрузки RTP/AVP 98 для такого потока, для его декодирования потребуется дополнительная информация:
m=video 49232 RTP/AVP 98 a=rtpmap:98 L16/16000/2
m=video 49232 RTP/AVP 98 a=rtpmap:98 L16/16000/2
The general form of an rtpmap attribute is:
Общая форма атрибута rtpmap:
a=rtpmap:<payload type> <encoding name>/<clock rate>[/<encoding parameters>]
a=rtpmap:<payload type> <encoding name>/<clock rate>[/<encoding parameters>]
For audio streams, <encoding parameters> may specify the number of audio channels. This parameter may be omitted if the number of channels is one provided no additional parameters are needed. For video streams, no encoding parameters are currently specified.
Для аудиопотоков <encoding parameters> может задавать число аудиоканалов. Этот параметр может быть опущен, если число каналов равно единице и при условии, что дополнительные параметры не нужны. Для видеопотоков в настоящее время параметры кодирования не задаются.
Additional parameters may be defined in the future, but codecspecific parameters should not be added. Parameters added to an rtpmap attribute should only be those required for a session directory to make the choice of appropriate media too to participate in a session. Codec-specific parameters should be added in other attributes.
Дополнительные параметры могут быть определены в будущем, но параметры, специфичные для кодека, добавляться не должны. Параметры, добавленные к атрибуту rtpmap, должны быть только теми, что требуются каталогу сессий для выбора подходящего медиаинструмента для участия в сессии. Параметры, специфичные для кодека, следует добавлять в других атрибутах.
Up to one rtpmap attribute can be defined for each media format specified. Thus we might have:
Для каждого указанного формата медиа может быть определён самое большее один атрибут rtpmap. Таким образом, мы могли бы иметь:
m=audio 49230 RTP/AVP 96 97 98 a=rtpmap:96 L8/8000 a=rtpmap:97 L16/8000 a=rtpmap:98 L16/11025/2
m=audio 49230 RTP/AVP 96 97 98 a=rtpmap:96 L8/8000 a=rtpmap:97 L16/8000 a=rtpmap:98 L16/11025/2
RTP profiles that specify the use of dynamic payload types must define the set of valid encoding names and/or a means to register encoding names if that profile is to be used with SDP.
Профили RTP, задающие использование динамических типов полезной нагрузки, должны определять набор допустимых имён кодировок и/или средство регистрации имён кодировок, если этот профиль должен использоваться с SDP.
Experimental encoding formats can also be specified using rtpmap. RTP formats that are not registered as standard format names must be preceded by "X-". Thus a new experimental redundant audio stream called GSMLPC using dynamic payload type 99 could be specified as:
Экспериментальные форматы кодирования также могут задаваться с помощью rtpmap. Форматы RTP, не зарегистрированные как стандартные имена форматов, должны иметь префикс «X-». Таким образом, новый экспериментальный избыточный аудиопоток под названием GSMLPC с использованием динамического типа полезной нагрузки 99 мог бы быть задан следующим образом:
m=video 49232 RTP/AVP 99 a=rtpmap:99 X-GSMLPC/8000
m=video 49232 RTP/AVP 99 a=rtpmap:99 X-GSMLPC/8000
Such an experimental encoding requires that any site wishing to receive the media stream has relevant configured state in its session directory to know which tools are appropriate.
Такой экспериментальный формат кодирования требует, чтобы любой узел, желающий принимать этот медиапоток, имел соответствующим образом настроенное состояние в своём каталоге сессий, чтобы знать, какие инструменты подходят.
Note that RTP audio formats typically do not include information about the number of samples per packet. If a non-default (as defined in the RTP Audio/Video Profile) packetisation is required, the "ptime" attribute is used as given below. For more details on RTP audio and video formats, see [3].
Обратите внимание, что аудиоформаты RTP, как правило, не содержат информации о числе сэмплов на пакет. Если требуется упаковка в пакет, отличная от значения по умолчанию (как определено в профиле RTP Audio/Video), используется атрибут «ptime», как указано ниже.
o Formats for non-RTP media should be registered as MIME content types as described in Appendix B. For example, the LBL whiteboard application might be registered as MIME content-type application/wb with encoding considerations specifying that it operates over UDP, with no appropriate file format. In SDP this would then be expressed using a combination of the "media" field and the "fmt" field, as follows:
o Форматы для медиа, не относящихся к RTP, должны быть зарегистрированы как типы содержимого MIME, как описано в Приложении B. Например, приложение доски LBL могло бы быть зарегистрировано как тип содержимого MIME application/wb с указанием особенностей кодирования, определяющих, что оно работает поверх UDP. В SDP это выражалось бы с помощью комбинации поля «media» и поля «fmt» следующим образом:
m=application 32416 udp wb
m=application 32416 udp wb
Suggested Attributes
Предлагаемые атрибуты
The following attributes are suggested. Since application writers may add new attributes as they are required, this list is not exhaustive.
Предлагаются следующие атрибуты. Поскольку авторы приложений могут добавлять новые атрибуты по мере необходимости, этот список не является исчерпывающим.
a=cat:<category> This attribute gives the dot-separated hierarchical category of the session. This is to enable a receiver to filter unwanted sessions by category. It would probably have been a compulsory separate field, except for its experimental nature at this time. It is a session-level attribute, and is not dependent on charset.
a=cat:<category>. Этот атрибут задаёт иерархическую категорию сессии, разделённую точками. Это служит для того, чтобы получатель мог фильтровать нежелательные сессии по категории. Вероятно, он был бы обязательным отдельным полем, если бы не его экспериментальный характер.
a=keywds:<keywords> Like the cat attribute, this is to assist identifying wanted sessions at the receiver. This allows a receiver to select interesting session based on keywords describing the purpose of the session. It is a session-level attribute. It is a charset dependent attribute, meaning that its value should be interpreted in the charset specified for the session description if one is specified, or by default in ISO 10646/UTF-8.
a=keywds:<keywords>. Подобно атрибуту cat, этот атрибут служит для облегчения выявления нужных сессий на приёмной стороне. Он позволяет получателю выбрать интересующие сессии по ключевым словам, описывающим назначение сессии. Это атрибут уровня сессии. Он зависит от charset, поскольку ключевые слова являются текстом, и к ним применимы те же правила кодирования, что и к другим текстовым полям.
a=tool:<name and version of tool> This gives the name and version number of the tool used to create the session description. It is a session-level attribute, and is not dependent on charset.
a=tool:<name and version of tool>. Задаёт имя и номер версии инструмента, использованного для создания описания сессии. Это атрибут уровня сессии, и он не зависит от charset.
a=ptime:<packet time> This gives the length of time in milliseconds represented by the media in a packet. This is probably only meaningful for audio data. It should not be necessary to know ptime to decode RTP or vat audio, and it is intended as a recommendation for the encoding/packetisation of audio. It is a media attribute, and is not dependent on charset.

7. Security Considerations
7. Вопросы безопасности
SDP is a session description format that describes multimedia sessions. A session description should not be trusted unless it has been obtained by an authenticated transport protocol from a trusted source. Many different transport protocols may be used to distribute session description, and the nature of the authentication will differ from transport to transport.
SDP — это формат описания сессий, описывающий мультимедийные сессии. Описанию сессии не следует доверять, если оно не получено по аутентифицированному транспортному протоколу от доверенного источника. Может использоваться множество различных транспортных протоколов для распространения описаний сессий, и каждый из них может обеспечивать различные уровни гарантий безопасности.
One transport that will frequently be used to distribute session descriptions is the Session Announcement Protocol (SAP). SAP provides both encryption and authentication mechanisms but due to the nature of session announcements it is likely that there are many occasions where the originator of a session announcement cannot be authenticated because they are previously unknown to the receiver of the announcement and because no common public key infrastructure is available.
Одним из транспортов, который будет часто использоваться для распространения описаний сессий, является протокол анонсирования сессий (Session Announcement Protocol, SAP). SAP предоставляет как механизмы шифрования, так и механизмы аутентификации, но в силу характера анонсов сессий вероятно, что многие анонсы будут неаутентифицированными, а многие получатели не смогут проверить их подлинность.
On receiving a session description over an unauthenticated transport mechanism or from an untrusted party, software parsing the session should take a few precautions. Session description contain information required to start software on the receivers system. Software that parses a session description MUST not be able to start other software except that which is specifically configured as appropriate software to participate in multimedia sessions. It is normally considered INAPPROPRIATE for software parsing a session description to start, on a user's system, software that is appropriate to participate in multimedia sessions, without the user first being informed that such software will be started and giving their consent. Thus a session description arriving by session announcement, email, session invitation, or WWW page SHOULD not deliver the user into an {it interactive} multimedia session without the user being aware that this will happen. As it is not always simple to tell whether a session is interactive or not, applications that are unsure should assume sessions are interactive.
При получении описания сессии по неаутентифицированному транспортному механизму или от недоверенной стороны программное обеспечение, разбирающее сессию, должно принять некоторые меры предосторожности. Описания сессий содержат информацию, необходимую для запуска программного обеспечения в системе получателя. Программное обеспечение, разбирающее описание сессии, НЕ ДОЛЖНО иметь возможности запускать иное программное обеспечение, кроме того, которое специально настроено как подходящее для участия в мультимедийных сессиях. Обычно считается НЕПОДХОДЯЩИМ, чтобы программное обеспечение, разбирающее описание сессии, запускало в системе пользователя программное обеспечение, подходящее для участия в мультимедийных сессиях, без предварительного уведомления пользователя о том, что такое программное обеспечение будет запущено, и без его согласия. Таким образом, описание сессии, поступающее через анонс сессии, электронную почту, приглашение на сессию или страницу WWW, НЕ ДОЛЖНО вводить пользователя в интерактивную мультимедийную сессию без осведомлённости пользователя о том, что это произойдёт. Поскольку не всегда просто определить, является ли сессия интерактивной, приложения, которые в этом не уверены, должны предполагать, что сессии интерактивны.
In this specification, there are no attributes which would allow the recipient of a session description to be informed to start multimedia tools in a mode where they default to transmitting. Under some circumstances it might be appropriate to define such attributes. If this is done an application parsing a session description containing such attributes SHOULD either ignore them, or inform the user that joining this session will result in the automatic transmission of multimedia data. The default behaviour for an unknown attribute is to ignore it. Session descriptions may be parsed at intermediate systems such as firewalls for the purposes of opening a hole in the firewall to allow the participation in multimedia sessions. It is considered INAPPROPRIATE for a firewall to open such holes for unicast data streams unless the session description comes in a request from inside the firewall.
В настоящей спецификации нет атрибутов, которые позволяли бы сообщить получателю описания сессии о необходимости запуска мультимедийных инструментов в режиме, где они по умолчанию передают. При некоторых обстоятельствах могло бы быть уместно определить такие атрибуты. Если это будет сделано, приложение, разбирающее описание сессии, содержащее такие атрибуты, ДОЛЖНО либо игнорировать их, либо уведомить пользователя о том, что присоединение к этой сессии приведёт к автоматической передаче мультимедийных данных. Поведением по умолчанию для неизвестного атрибута является его игнорирование. Описания сессий могут разбираться на промежуточных системах, таких как межсетевые экраны, с целью открытия отверстия в межсетевом экране для обеспечения участия в мультимедийных сессиях. Считается НЕПОДХОДЯЩИМ, чтобы межсетевой экран открывал такие отверстия для одноадресных потоков данных, если только описание сессии не приходит в запросе изнутри межсетевого экрана.
For multicast sessions, it is likely that local administrators will apply their own policies, but the exclusive use of "local" or "site- local" administrative scope within the firewall and the refusal of the firewall to open a hole for such scopes will provide separation of global multicast sessions from local ones. Appendix B: Guidelines for registering SDP names with IANA
Приложение B. Рекомендации по регистрации имён SDP в IANA
There are seven field names that may be registered with IANA. Using the terminology in the SDP specification BNF, they are "media", "proto", "fmt", "att-field", "bwtype", "nettype" and "addrtype".
Существует семь имён полей, которые могут быть зарегистрированы в IANA. Используя терминологию из BNF спецификации SDP, это «media», «proto», «fmt», «att-field», «bwtype», «nettype» и «addrtype».
"media" (eg, audio, video, application, data).
«media» (например, audio, video, application, data).
Packetized media types, such as those used by RTP, share the namespace used by media types registry [RFC 2048] (i.e. "MIME types"). The list of valid media names is the set of top-level MIME content types. The set of media is intended to be small and not to be extended except under rare circumstances. (The MIME subtype corresponds to the "fmt" parameter below).
Пакетированные типы медиа, такие как используемые RTP, разделяют пространство имён, используемое реестром типов медиа [RFC 2048] (то есть «типы MIME»). Список допустимых имён медиа — это набор типов содержимого MIME верхнего уровня. Новые имена медиа могут быть зарегистрированы, если они представляют новый класс медиа, а не просто новый формат медиа.
"proto"
«proto».
In general this should be an IETF standards-track transport protocol identifier such as RTP/AVP (rfc 1889 under the rfc 1890 profile).
В общем случае это должен быть идентификатор транспортного протокола уровня Standards Track IETF, такой как RTP/AVP (RFC 1889 под профилем RFC 1890).
However, people will want to invent their own proprietary transport protocols. Some of these should be registered as a "fmt" using "udp" as the protocol and some of which probably can't be.
Однако люди будут желать изобретать собственные проприетарные транспортные протоколы. Некоторые из них следует регистрировать как «fmt», используя «udp» в качестве протокола, а некоторые, вероятно, так зарегистрировать нельзя.
Where the protocol and the application are intimately linked, such as with the LBL whiteboard wb which used a proprietary and special purpose protocol over UDP, the protocol name should be "udp" and the format name that should be registered is "wb". The rules for formats (see below) apply to such registrations.
Там, где протокол и приложение тесно связаны, как в случае доски LBL wb, которая использовала проприетарный протокол специального назначения поверх UDP, имя протокола должно быть «udp», а имя формата, которое следует зарегистрировать, — «wb». К таким регистрациям применяются правила для форматов (см. ниже).
Where the proprietary transport protocol really carries many different data formats, it is possible to register a new protocol name with IANA. In such a case, an RFC MUST be produced describing the protocol and referenced in the registration. Such an RFC MAY be informational, although it is preferable if it is standards-track.
Там, где проприетарный транспортный протокол действительно несёт множество различных форматов данных, можно зарегистрировать новое имя протокола в IANA. В таком случае ДОЛЖЕН быть выпущен RFC, описывающий протокол и упоминаемый в регистрации. Такой RFC МОЖЕТ быть информационным, хотя предпочтительно, чтобы он относился к уровню Standards Track.
"fmt"
«fmt».
The format namespace is dependent on the context of the "proto" field, so a format cannot be registered without specifying one or more transport protocols that it applies to.
Пространство имён форматов зависит от контекста поля «proto», поэтому формат не может быть зарегистрирован без указания одного или нескольких транспортных протоколов, к которым он применяется.
Formats cover all the possible encodings that might want to be transported in a multimedia session. For RTP formats that have been assigned static payload types, the payload type number is used. For RTP formats using a dynamic payload type number, the dynamic payload type number is given as the format and an additional "rtpmap" attribute specifies the format and parameters.
Форматы охватывают все возможные кодировки, которые могут потребоваться передавать в мультимедийной сессии. Для форматов RTP, которым назначены статические типы полезной нагрузки, используется номер типа полезной нагрузки. Для форматов RTP, использующих номер динамического типа полезной нагрузки, этот номер задаётся как формат, а дополнительный атрибут «rtpmap» задаёт формат и параметры.
For non-RTP formats, any unregistered format name may be registered through the MIME-type registration process [RFC 2048]. The type given here is the MIME subtype only (the top-level MIME content type is specified by the media parameter). The MIME type registration SHOULD reference a standards-track RFC which describes the transport protocol for this media type. If there is an existing MIME type for this format, the MIME registration should be augmented to reference the transport specification for this media type. If there is not an existing MIME type for this format, and there exists no appropriate file format, this should be noted in the encoding considerations as "no appropriate file format".
Для форматов, не относящихся к RTP, любое незарегистрированное имя формата может быть зарегистрировано через процесс регистрации типов MIME [RFC 2048]. Тип, указанный здесь, — это только подтип MIME (тип содержимого MIME верхнего уровня задаётся параметром media). Регистрация типа MIME СЛЕДУЕТ ссылаться на RFC уровня Standards Track, описывающий транспортный протокол для этого типа медиа. Если для этого формата уже существует тип MIME, регистрацию MIME следует дополнить ссылкой на спецификацию транспорта для этого типа медиа. Если для этого формата не существует типа MIME и нет подходящего формата файла, это следует отметить в особенностях кодирования как «подходящий формат файла отсутствует».

«att-field» (имена атрибутов).

o contact name, email address and telephone number

o attribute-name (as it will appear in SDP)

IANA не будет проверять такие регистрации атрибутов на разумность, кроме проверки того, что они не конфликтуют с существующими регистрациями. Размножение спецификаторов полосы пропускания решительно не поощряется.

Новые спецификаторы полосы пропускания могут быть зарегистрированы в IANA. «nettype» (тип сети).

The number of network types should be small and should be rarely extended. A new network type cannot be registered without registering at least one address type to be used with that network type. A new network type registration MUST reference an RFC which gives details of the network type and address type and specifies how and when they would be used. Such an RFC MAY be Informational.
Новые типы сетей могут быть зарегистрированы в IANA, если SDP потребуется использовать в контексте неинтернет-сред. Хотя это обычно не является прерогативой IANA, могут возникнуть обстоятельства, когда интернет-приложению необходимо взаимодействовать с неинтернет-приложением, например при шлюзовании телефонного вызова через Интернет в ТфОП. Регистрация нового типа сети ДОЛЖНА ссылаться на RFC, который содержит сведения о типе сети и типе адреса и определяет, как и когда они будут использоваться. Такой RFC МОЖЕТ быть уровня Informational.

Тип адреса имеет смысл только в контексте типа сети, и любая регистрация типа адреса ДОЛЖНА указывать зарегистрированный тип сети либо представляться вместе с регистрацией нового типа сети, для которого она имеет смысл.
