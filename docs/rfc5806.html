Abstract
Аннотация
This RFC, which contains the text of an Internet Draft that was submitted originally to the SIP Working Group, is being published now for the historical record and to provide a reference for later Informational RFCs. The original Abstract follows.
Настоящий RFC, содержащий текст Internet Draft, который был изначально представлен рабочей группе SIP, публикуется теперь для исторической записи и как справочный материал для последующих информационных RFC. Ниже приводится исходная аннотация.
This document proposes an extension to the Session Initiation Protocol (SIP). This extension provides the ability for the called SIP user agent to identify from whom the call was diverted and why the call was diverted. The extension defines a general header, Diversion, which conveys the diversion information from other SIP user agents and proxies to the called user agent.
Настоящий документ предлагает расширение протокола инициирования сессий (SIP). Это расширение даёт вызываемому пользовательскому агенту SIP возможность определять, кем вызов был переадресован и почему он был переадресован. Расширение определяет общий заголовок Diversion, который передаёт информацию о переадресации от других пользовательских агентов SIP и прокси вызываемому пользовательскому агенту.
This extension allows enhanced support for various features, including Unified Messaging, Third-Party Voicemail, and Automatic Call Distribution (ACD). SIP user agents and SIP proxies that receive diversion information may use this as supplemental information for feature invocation decisions.
Это расширение позволяет расширить поддержку различных функций, включая унифицированный обмен сообщениями, голосовую почту третьей стороны и автоматическое распределение вызовов (ACD). Пользовательские агенты SIP и прокси SIP, получающие информацию о переадресации, могут использовать её как дополнительную информацию при принятии решений о вызове функций.

3. Overview
3. Обзор
In order to implement certain third-party features such as Third- Party Voicemail and Automatic Call Distribution (ACD) applications, diversion information needs to be given to the called third party so that he may respond to the caller intelligently. In these situations, the party receiving a diverted call needs answers for two
Чтобы реализовать некоторые функции третьих сторон, такие как голосовая почта третьей стороны и приложения автоматического распределения вызовов (ACD), вызываемой третьей стороне необходимо передать информацию о переадресации, чтобы она могла осмысленно ответить вызывающему. В этих ситуациях сторона, принимающая переадресованный вызов, нуждается в ответах на два
questions:
вопроса:
Question 1: From whom was the request diverted?
Вопрос 1: Кем был переадресован запрос?
Question 2: Why was the request diverted?
Вопрос 2: Почему запрос был переадресован?
This document proposes usage of the Diversion header to answer these questions for the party receiving the diverted call.
Настоящий документ предлагает использовать заголовок Diversion для ответа на эти вопросы стороне, принимающей переадресованный вызов.
Insertion of the previous Request-URI (before the diversion occurred) into the Diversion header answers question 1.
Внесение предыдущего Request-URI (до того, как произошла переадресация) в заголовок Diversion отвечает на вопрос 1.
Insertion of the "reason" tag into the Diversion header (by the divertor) answers question 2.
Внесение тега «reason» в заголовок Diversion (переадресующим) отвечает на вопрос 2.
3.1. When Is the Diversion Header Used?
3.1. Когда используется заголовок Diversion?
The Diversion header SHOULD be added when a SIP proxy server, SIP redirect server, or SIP user agent changes the ultimate endpoint that will receive the call.
Заголовок Diversion СЛЕДУЕТ добавлять, когда прокси-сервер SIP, сервер перенаправления SIP или пользовательский агент SIP изменяет конечную точку, которая получит вызов.
Diversion information SHOULD NOT be added for normal call routing changes to the Request-URI. Thus, the Diversion header is not added when features such as speed dial change the Request-URI.
Информацию о переадресации НЕ СЛЕДУЕТ добавлять при обычных изменениях маршрутизации вызова, затрагивающих Request-URI. Так, заголовок Diversion не добавляется, когда такие функции, как быстрый набор, изменяют Request-URI.
When a diversion occurs, a Diversion header SHOULD be added to the forwarded request or forwarded 3xx response. The Diversion header MUST contain the Request-URI of the request prior to the diversion. The Diversion header SHOULD contain a reason that the diversion occurred.
Когда происходит переадресация, в пересылаемый запрос или пересылаемый ответ 3xx СЛЕДУЕТ добавить заголовок Diversion. Заголовок Diversion ДОЛЖЕН содержать Request-URI запроса до переадресации. Заголовок Diversion СЛЕДУЕТ содержать причину, по которой произошла переадресация.
Existing Diversion headers received in an incoming request MUST NOT be removed or changed in forwarded requests.
Существующие заголовки Diversion, полученные во входящем запросе, НЕ ДОЛЖНЫ удаляться или изменяться в пересылаемых запросах.
Existing Diversion headers received in an incoming response MUST NOT be removed or changed in the forwarded response.
Существующие заголовки Diversion, полученные во входящем ответе, НЕ ДОЛЖНЫ удаляться или изменяться в пересылаемом ответе.
A Diversion header is added when features such as call forwarding or call deflection change the Request-URI.
Заголовок Diversion добавляется, когда такие функции, как переадресация вызова или отклонение вызова, изменяют Request-URI.

5. Detailed Semantics
5. Подробная семантика
5.1. UAS Behavior
5.1. Поведение UAS
A SIP User Agent Service (UAS) that receives a request and returns a 3xx SHOULD add a Diversion header containing the previous Request-URI and the reason for the diversion.
UAS (SIP User Agent Service), который получает запрос и возвращает 3xx, СЛЕДУЕТ добавить заголовок Diversion, содержащий предыдущий Request-URI и причину переадресации.
5.2. UAC Behavior
5.2. Поведение UAC
A SIP UAC that receives a 3xx containing a Diversion header SHOULD copy the Diversion header into each downstream forked request that resulted from the 3xx.
UAC SIP, который получает ответ 3xx с заголовком Diversion, СЛЕДУЕТ копировать заголовок Diversion в каждый нижестоящий ответвлённый запрос, порождённый этим ответом 3xx.
5.3. Redirect Server Behavior
5.3. Поведение сервера перенаправления
A SIP redirect server that receives a request and returns a 3xx containing a Contact that diverts the request to a different endpoint SHOULD add a Diversion header containing the Request-URI from the incoming request and the reason for the diversion.
Сервер перенаправления SIP, который получает запрос и возвращает ответ 3xx, содержащий Contact, переадресующий запрос на другую конечную точку, СЛЕДУЕТ добавить заголовок Diversion, содержащий Request-URI входящего запроса и причину переадресации.
5.4. Proxy Server Behavior
5.4. Поведение прокси-сервера
A non-recursing SIP proxy that receives a 3xx containing a Diversion header SHOULD forward the 3xx containing the Diversion header upstream unchanged.
Нерекурсивный прокси SIP, который получает ответ 3xx, содержащий заголовок Diversion, СЛЕДУЕТ переслать этот ответ 3xx с заголовком Diversion вверх по потоку без изменений.
A SIP proxy that receives a request and invokes a feature that changes the Request-URI of the forwarded request in order to divert the request to a different endpoint SHOULD add a Diversion header containing the Request-URI from the incoming request and the reason for the diversion.
Прокси SIP, который получает запрос и вызывает функцию, изменяющую Request-URI пересылаемого запроса, чтобы переадресовать запрос на другую конечную точку, СЛЕДУЕТ добавить заголовок Diversion, содержащий Request-URI входящего запроса и причину переадресации.
A SIP proxy that receives a request and returns a 3xx containing a Contact that diverts the request to a different endpoint SHOULD add a Diversion header containing the Request-URI from the incoming request and the reason for the diversion.
Прокси SIP, который получает запрос и возвращает ответ 3xx, содержащий Contact, переадресующий запрос на другую конечную точку, СЛЕДУЕТ добавить заголовок Diversion, содержащий Request-URI входящего запроса и причину переадресации.

6. Examples Using Diversion Header
6. Примеры использования заголовка Diversion
There are several implementations of call forwarding features that can be implemented by either recursing or non-recursing SIP proxies or SIP user agents.
Существует несколько реализаций функций переадресации вызова, которые могут быть реализованы как рекурсивными, так и нерекурсивными прокси SIP или пользовательскими агентами SIP.
A SIP proxy or user agent that generates or forwards 3xxs upstream is non-recursing. A SIP proxy or user agent that handles received (or internally generated) 3xxs itself is recursing.
Прокси или пользовательский агент SIP, порождающий или пересылающий 3xx вверх по потоку, является нерекурсивным. Прокси или пользовательский агент SIP, обрабатывающий полученные (или внутренне порождённые) 3xx сам, является рекурсивным.
The following examples illustrate usage of the Diversion header for some of the variants of recursing and non-recursing proxies and user agents.
Следующие примеры иллюстрируют использование заголовка Diversion для некоторых вариантов рекурсивных и нерекурсивных прокси и пользовательских агентов.

7. Security Considerations
7. Вопросы безопасности
There are some privacy considerations when using the Diversion header. Usage of the Diversion header implies that the diverting UAS trusts the diverted-to UAS. Usage of the Diversion header by SIP proxies or SIP user agents can cause information leakage of route information and called information to untrusted SIP proxies and untrusted callers in upstream 3xxs. Leakage of this information can be mitigated by having a recursing trusted upstream proxy server. For a SIP network architecture where all proxies are required to be non-recursive, Diversion header hiding may be considered necessary in order to prevent leakage of route information to the caller. To accomplish Diversion header hiding, a trusted upstream proxy would add a Record-Route header and use a secret key to encrypt the contents of the Diversion header in 3xxs that are forwarded upstream. On receipt of re-INVITEs, the proxy would decrypt the contents of the Diversion header (using its secret key) and forward the INVITE. There is no currently defined interaction of the Diversion and Hide headers. Question: Should there be?
При использовании заголовка Diversion есть ряд аспектов конфиденциальности. Использование заголовка Diversion подразумевает, что переадресующий UAS доверяет UAS, на который выполняется переадресация. Использование заголовка Diversion прокси SIP или пользовательскими агентами SIP может привести к утечке информации о маршрутизации и информации о вызываемом абоненте недоверенным прокси SIP и недоверенным вызывающим в восходящих ответах 3xx. Утечку этой информации можно уменьшить, имея доверенный восходящий прокси-сервер, работающий рекурсивно. Для сетевой архитектуры SIP, в которой все прокси обязаны быть нерекурсивными, сокрытие заголовка Diversion может считаться необходимым, чтобы предотвратить утечку информации о маршрутизации вызывающему. Чтобы обеспечить сокрытие заголовка Diversion, доверенный восходящий прокси добавил бы заголовок Record-Route и использовал секретный ключ для шифрования содержимого заголовка Diversion в ответах 3xx, пересылаемых вверх по потоку. При получении re-INVITE прокси расшифровывал бы содержимое заголовка Diversion (используя свой секретный ключ) и пересылал INVITE. В настоящее время взаимодействие заголовков Diversion и Hide не определено. Вопрос: следует ли его определить?

8.3. Questions and Answers on Alternative Approaches
8.3. Вопросы и ответы об альтернативных подходах
Question 1:
Вопрос 1:
Why do we need the Diversion header when we can see the To: header?
Зачем нам нужен заголовок Diversion, если мы видим заголовок To:?
Answer:
Ответ:
a) The To: header is not guaranteed to have significance to the called party.
a) Заголовок To: не обязательно имеет значение для вызываемой стороны.
For example, the To: header may contain a locally significant URL (to the caller) such as a private numbering plan, speed dial digits, telephony escape digits, or telephony prefix digits.
Например, заголовок To: может содержать локально значимый URL (для вызывающего), такой как частный план нумерации, цифры быстрого набора, цифры выхода из телефонной сети или префиксные цифры телефонной сети.
Without a Diversion header, enumerating all possible locally significant To: headers that anyone might use to contact Bob@uas1.isp.com becomes a configuration problem at Voicemail@isp.com and is prone to namespace collision.
Без заголовка Diversion перечисление всех возможных локально значимых заголовков To:, которые кто-либо мог бы использовать для связи с Bob@uas1.isp.com, становится проблемой конфигурации в Voicemail@isp.com и подвержено коллизиям пространства имён.
Support for Diversion headers enables Bob to contract a third- party service (Voicemail@isp.com) with a single globally significant URL for his voice mailbox (Bob@uas1.isp.com).
Поддержка заголовков Diversion позволяет Bob заключить договор со сторонней службой (Voicemail@isp.com), используя один глобально значимый URL для своего голосового ящика (Bob@uas1.isp.com).
b) Given a set of multiple diversions, there is a policy decision of which Diversion header takes precedence for service logic.
b) При наличии множества переадресаций требуется политическое решение о том, какой заголовок Diversion имеет приоритет для логики услуги.
Different services (or even different users for the same service) may want to configure this policy differently (first, last, second to last, etc.).
Различные службы (или даже разные пользователи одной и той же службы) могут захотеть настроить эту политику по-разному (первый, последний, предпоследний и т. д.).
Question 2:
Вопрос 2:
Why do we need the Diversion header when we can see the Via: header?
Зачем нам нужен заголовок Diversion, если мы видим заголовок Via:?
Answer:
Ответ:
The Via header does not contain information about servers whom have deflected the call (using a 3xx).
Заголовок Via не содержит информации о серверах, которые отклонили вызов (используя 3xx).
9. Mapping ISUP/ISDN Redirection Information to SIP Diversion Header
9. Отображение информации перенаправления ISUP/ISDN на заголовок Diversion в SIP
The discussions below regarding ISUP/ISDN reflect generic elements in ISUP/ISDN. In some variations of ISUP/ISDN, the information elements are represented differently. Regardless of the ISUP/ISDN variant, translation should be performed for the "first redirecting number" and the "last redirecting number".
Приведённые ниже рассуждения об ISUP/ISDN отражают обобщённые элементы ISUP/ISDN. В некоторых вариантах ISUP/ISDN информационные элементы представлены иначе. Независимо от варианта ISUP/ISDN, трансляция должна выполняться для «first redirecting number» и «last redirecting number».
In order to prevent ambiguity, it is important to highlight a terminology mismatch between ISUP/ISDN and SIP. In SIP, a "redirect" indicates the act of returning a 3xx response. In ISUP/ISDN, a "redirection" is diversion of a call by a network entity. In ISUP/ISDN, a call may also be deflected (by an endpoint). Diversion is the more generic term that refers to either the act of an network redirection or endpoint deflection.
Чтобы избежать неоднозначности, важно подчеркнуть терминологическое расхождение между ISUP/ISDN и SIP. В SIP «redirect» обозначает действие по возврату ответа 3xx. В ISUP/ISDN «redirection» — это переадресация вызова сетевым субъектом. В ISUP/ISDN вызов также может быть отклонён (конечной точкой). Diversion — более общий термин, обозначающий либо акт сетевого перенаправления, либо отклонение конечной точкой.
In SIP, Diversion can be implemented as either an upstream 3xx (non- recursive) or an additionally forked downstream request (recursive). In the following text, a lowercase "redirect" indicates the SIP usage, while an uppercase "Redirect" indicates ISUP usage.
В SIP переадресация Diversion может быть реализована либо как восходящий ответ 3xx (нерекурсивно), либо как дополнительно ответвлённый нижестоящий запрос (рекурсивно). В дальнейшем тексте «redirect» со строчной буквы обозначает использование в SIP, а «Redirect» с заглавной — использование в ISUP.

9.3. Mapping ISDN Redirection Information to SIP Diversion Header
9.3. Отображение информации перенаправления ISDN на заголовок Diversion в SIP
An ISDN message can contain up to two instances of a Redirecting Number information element. When a diversion occurs, an additional Redirection number information element is added. When a third (or greater) diversion occurs, the new Redirecting Number information element replaces the bottom-most Redirection number information element.
Сообщение ISDN может содержать до двух экземпляров информационного элемента Redirecting Number. Когда происходит переадресация, добавляется дополнительный информационный элемент Redirection number. Когда происходит третья (или последующая) переадресация, новый информационный элемент Redirecting Number заменяет самый нижний информационный элемент Redirection number.
9.3.1. ISDN Definitions
9.3.1. Определения ISDN
Called Party Number The number of the party to which the call is currently being routed.
Номер вызываемой стороны — номер стороны, на которую в данный момент маршрутизируется вызов.
Redirecting Number information element Aggregate information element that contains Redirecting number and Reason for diversion.
Информационный элемент Redirecting Number — агрегированный информационный элемент, содержащий Redirecting number и Reason for diversion.
Redirecting Number The number to which the call was being routed when the last diversion occurred.
Перенаправляющий номер — номер, на который маршрутизировался вызов при последней переадресации.
Reason for Diversion The reason that the last diversion occurred.
Причина переадресации — причина, по которой произошла последняя переадресация.
Origin of Number Indicates whether the number is user provided and screened or network provided.
Источник номера — указывает, предоставлен ли номер пользователем и прошёл проверку или предоставлен сетью.
Presentation Status Indicates if presentation is allowed or prohibited.
Статус представления — указывает, разрешено или запрещено представление.

9.3.2. Параметры ISDN

An ISDN message contains information on the first and last diversions that occurred. The top-most Redirection number information element contains information (including the Redirecting Number, Origin of Number, Presentation Status, and Reason for diversion) about the last diversion that occurred. The bottom-most Redirection number information element contains information (including the Redirecting Number, Origin of Number, Presentation Status, and Reason for diversion) about the first diversion that occurred.
Сообщение ISDN содержит информацию о первой и последней произошедших переадресациях. Самый верхний информационный элемент Redirection number содержит информацию (включая Redirecting Number, Origin of Number, Presentation Status и Reason for diversion) о последней произошедшей переадресации. Самый нижний информационный элемент Redirection number содержит информацию (включая Redirecting Number, Origin of Number, Presentation Status и Reason for diversion) о первой произошедшей переадресации.
If only one Diversion has occurred, only one Redirection number information element is present.
Если произошла только одна переадресация, присутствует только один информационный элемент Redirection number.
The Redirecting Number information element has the same Type of Number/Numbering Plan, and Digits as the Calling Party Number information element.
Информационный элемент Redirecting Number имеет те же Type of Number/Numbering Plan и Digits, что и информационный элемент Calling Party Number.
There is no Redirection Counter associated with this ISDN information element.
С этим информационным элементом ISDN не связан Redirection Counter.
Notice that the order of the Redirection number information elements in an ISDN message (top=first, bottom=last) is reversed from the order of Diversion headers in a SIP message (top=last, bottom=first).
Обратите внимание, что порядок информационных элементов Redirection number в сообщении ISDN (верхний = первый, нижний = последний) противоположен порядку заголовков Diversion в сообщении SIP (верхний = последний, нижний = первый).

9.4. Information Loss in SIP to ISUP/ISDN Translation
9.4. Потеря информации при трансляции SIP в ISUP/ISDN
Because ISUP and ISDN only support a subset of the information in a SIP Diversion header, information loss occurs during translation at a SIP/ISUP or SIP/ISDN boundary.
Поскольку ISUP и ISDN поддерживают только подмножество информации из заголовка Diversion в SIP, при трансляции на границе SIP/ISUP или SIP/ISDN происходит потеря информации.
9.4.1. Loss of Diversion URI Information
9.4.1. Потеря информации URI переадресации
Because ISUP and ISDN only support a subset of URI types (specifically tel: URIs and sip:x@y;user=phone URIs), diversion information occurring for other URI types may be lost when crossing from SIP to ISDN or ISUP.
Поскольку ISUP и ISDN поддерживают только подмножество типов URI (в частности URI tel: и URI sip:x@y;user=phone), информация о переадресации для других типов URI может быть потеряна при переходе из SIP в ISDN или ISUP.
9.4.2. Loss of Diversion Reason Information
9.4.2. Потеря информации о причине переадресации
Because ISUP and ISDN only support a subset of the reason codes supported by the Diversion header, specific reason code information may be lost when crossing from SIP to ISDN or ISUP.
Поскольку ISUP и ISDN поддерживают только подмножество кодов причины, поддерживаемых заголовком Diversion, конкретная информация о коде причины может быть потеряна при переходе из SIP в ISDN или ISUP.
9.4.3. Loss of Diversion Counter Information
9.4.3. Потеря информации счётчика переадресаций
Because ISDN does not support a counter field (indicating the number of diversions that have occurred), counter information may be lost when crossing from SIP to ISDN.
Поскольку ISDN не поддерживает поле счётчика (указывающее количество произошедших переадресаций), информация счётчика может быть потеряна при переходе из SIP в ISDN.
