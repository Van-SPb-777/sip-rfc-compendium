Abstract
Аннотация
This document describes a DNS RR which specifies the location of the server(s) for a specific protocol and domain.
Настоящий документ описывает ресурсную запись DNS (DNS RR), которая указывает местоположение сервера (серверов) для конкретного протокола и домена.
Overview and rationale
Обзор и обоснование
Currently, one must either know the exact address of a server to contact it, or broadcast a question.
В настоящее время нужно либо знать точный адрес сервера, чтобы связаться с ним, либо передавать широковещательный запрос.
The SRV RR allows administrators to use several servers for a single domain, to move services from host to host with little fuss, and to designate some hosts as primary servers for a service and others as backups.
Запись SRV позволяет администраторам использовать несколько серверов для одного домена, перемещать службы с хоста на хост без лишних хлопот, а также назначать одни хосты как основные серверы для службы, а другие — как резервные.
Clients ask for a specific service/protocol for a specific domain (the word domain is used here in the strict RFC 1034 sense), and get back the names of any available servers.
Клиенты запрашивают конкретную службу/протокол для конкретного домена (слово «домен» здесь используется в строгом смысле RFC 1034) и получают обратно имена любых доступных серверов.
Note that where this document refers to "address records", it means A RR's, AAAA RR's, or their most modern equivalent. Definitions
Обратите внимание, что там, где настоящий документ упоминает «адресные записи», имеются в виду записи A, записи AAAA или их наиболее современный эквивалент.
The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT" and "MAY" used in this document are to be interpreted as specified in [BCP 14]. Other terms used in this document are defined in the DNS specification, RFC 1034.
Ключевые слова «MUST», «MUST NOT», «SHOULD», «SHOULD NOT» и «MAY», используемые в настоящем документе, должны толковаться так, как указано в [BCP 14]. Другие термины, используемые в настоящем документе, определены в спецификации DNS, RFC 1034.
Applicability Statement
Заявление о применимости
In general, it is expected that SRV records will be used by clients for applications where the relevant protocol specification indicates that clients should use the SRV record. Such specification MUST define the symbolic name to be used in the Service field of the SRV record as described below. It also MUST include security considerations. Service SRV records SHOULD NOT be used in the absence of such specification.
В общем случае ожидается, что записи SRV будут использоваться клиентами для приложений, где соответствующая спецификация протокола указывает, что клиентам следует использовать запись SRV. Такая спецификация ДОЛЖНА определить символическое имя, которое будет использоваться в поле Service записи SRV, как описано ниже. Она также ДОЛЖНА включать рассмотрение вопросов безопасности. Записи SRV служб НЕ СЛЕДУЕТ использовать при отсутствии такой спецификации.

The format of the SRV RR
Формат записи SRV
Here is the format of the SRV RR, whose DNS type code is 33:
Вот формат записи SRV, код типа DNS которой — 33:
_Service._Proto.Name TTL Class SRV Priority Weight Port Target
_Service._Proto.Name TTL Class SRV Priority Weight Port Target
(There is an example near the end of this document.)
(Пример есть в конце настоящего документа.)
Service The symbolic name of the desired service, as defined in Assigned Numbers [STD 2] or locally. An underscore (_) is prepended to the service identifier to avoid collisions with DNS labels that occur in nature. Some widely used services, notably POP, don't have a single universal name. If Assigned Numbers names the service indicated, that name is the only name which is legal for SRV lookups. The Service is case insensitive.
Service. Символическое имя желаемой службы, как определено в Assigned Numbers [STD 2] или локально. К идентификатору службы добавляется символ подчёркивания (_), чтобы избежать конфликтов с ярлыками DNS, встречающимися в природе. Некоторые широко используемые службы, в частности POP, не имеют единого универсального имени. Если Assigned Numbers именует службу, это имя является единственным допустимым для поиска SRV. Имя службы нечувствительно к регистру.
Proto The symbolic name of the desired protocol, with an underscore (_) prepended to prevent collisions with DNS labels that occur in nature. _TCP and _UDP are at present the most useful values for this field, though any name defined by Assigned Numbers or locally may be used (as for Service). The Proto is case insensitive.
Proto. Символическое имя желаемого протокола с предшествующим символом подчёркивания (_) для предотвращения конфликтов с ярлыками DNS, встречающимися в природе. _TCP и _UDP в настоящее время являются наиболее полезными значениями для этого поля, хотя может использоваться любое имя, определённое в Assigned Numbers или локально (как и для Service). Поле Proto нечувствительно к регистру.
Name The domain this RR refers to. The SRV RR is unique in that the name one searches for is not this name; the example near the end shows this clearly.
Name. Домен, к которому относится эта RR. Запись SRV уникальна тем, что имя, которое ищут, не является этим именем; пример в конце показывает это наглядно.
TTL Standard DNS meaning [RFC 1035].
TTL. Стандартное значение DNS [RFC 1035].
Class Standard DNS meaning [RFC 1035]. SRV records occur in the IN Class.
Class. Стандартное значение DNS [RFC 1035]. Записи SRV встречаются в классе IN.
Priority The priority of this target host. A client MUST attempt to contact the target host with the lowest-numbered priority it can reach; target hosts with the same priority SHOULD be tried in an order defined by the weight field. The range is 0-65535. This is a 16 bit unsigned integer in network byte order.
Priority. Приоритет этого целевого хоста. Клиент ДОЛЖЕН пытаться связаться с целевым хостом с наименьшим номером приоритета, до которого он может добраться; целевые хосты с одинаковым приоритетом СЛЕДУЕТ пробовать в порядке, определяемом полем weight. Диапазон — 0–65535. Это 16-битное беззнаковое целое в сетевом порядке байтов.
Weight A server selection mechanism. The weight field specifies a relative weight for entries with the same priority. Larger weights SHOULD be given a proportionately higher probability of being selected. The range of this number is 0-65535. This is a 16 bit unsigned integer in network byte order. Domain administrators SHOULD use Weight 0 when there isn't any server selection to do, to make the RR easier to read for humans (less noisy). In the presence of records containing weights greater than 0, records with weight 0 should have a very small chance of being selected.
Weight. Механизм выбора сервера. Поле weight задаёт относительный вес для записей с одинаковым приоритетом. Большим весам СЛЕДУЕТ давать пропорционально более высокую вероятность быть выбранными. Диапазон этого числа — 0–65535. Это 16-битное беззнаковое целое в сетевом порядке байтов. Администраторам доменов СЛЕДУЕТ использовать Weight 0, когда выбор сервера не требуется, чтобы сделать RR более удобочитаемой для людей (менее шумной). При наличии записей с весами больше 0 записи с весом 0 должны иметь очень малую вероятность быть выбранными.
In the absence of a protocol whose specification calls for the use of other weighting information, a client arranges the SRV RRs of the same Priority in the order in which target hosts, specified by the SRV RRs, will be contacted. The following algorithm SHOULD be used to order the SRV RRs of the same priority:
При отсутствии протокола, спецификация которого требует использования иной весовой информации, клиент упорядочивает RR SRV одинакового Priority в том порядке, в котором будут опрашиваться целевые хосты, указанные в этих RR SRV. Для упорядочения RR SRV одинакового приоритета СЛЕДУЕТ использовать следующий алгоритм.
To select a target to be contacted next, arrange all SRV RRs (that have not been ordered yet) in any order, except that all those with weight 0 are placed at the beginning of the list.
Чтобы выбрать цель, с которой связываться следующей, расположите все ещё не упорядоченные RR SRV в произвольном порядке, за исключением того, что все записи с весом 0 помещаются в начало списка.
Compute the sum of the weights of those RRs, and with each RR associate the running sum in the selected order.
Вычислите сумму весов этих RR и свяжите с каждой RR накопленную сумму в выбранном порядке.
Then choose a uniform random number between 0 and the sum computed (inclusive), and select the RR whose running sum value is the first in the selected order which is greater than or equal to the random number selected. The target host specified in the selected SRV RR is the next one to be contacted by the client. Remove this SRV RR from the set of the unordered SRV RRs and apply the described algorithm to the unordered SRV RRs to select the next target host. Continue the ordering process until there are no unordered SRV RRs. This process is repeated for each Priority.
Затем выбирается равномерно распределённое случайное число от 0 до вычисленной суммы включительно, и выбирается та RR, накопленная сумма которой в выбранном порядке первой больше или равна выбранному случайному числу. Целевой хост, указанный в выбранной SRV RR, — следующий, с которым клиент будет связываться. Эта SRV RR удаляется из набора неупорядоченных SRV RR, и описанный алгоритм применяется к неупорядоченным SRV RR, чтобы выбрать следующий целевой хост. Процесс упорядочивания продолжается, пока не останется неупорядоченных SRV RR. Этот процесс повторяется для каждого приоритета.
Port The port on this target host of this service. The range is 0- 65535. This is a 16 bit unsigned integer in network byte order. This is often as specified in Assigned Numbers but need not be.
Port. Порт на этом целевом хосте для данной службы. Диапазон — 0–65535. Это 16-битное беззнаковое целое в сетевом порядке байтов. Часто это значение, указанное в Assigned Numbers, но это не обязательно.
Target The domain name of the target host. There MUST be one or more address records for this name, the name MUST NOT be an alias (in the sense of RFC 1034 or RFC 2181). Implementors are urged, but not required, to return the address record(s) in the Additional Data section. Unless and until permitted by future standards action, name compression is not to be used for this field.
Target. Доменное имя целевого хоста. Для этого имени ДОЛЖНА быть одна или несколько адресных записей, и имя НЕ ДОЛЖНО быть псевдонимом (в смысле RFC 1034 или RFC 2181). Разработчикам настоятельно рекомендуется, но не вменяется в обязанность, возвращать адресные записи в разделе Additional Data.
A Target of "." means that the service is decidedly not available at this domain.
Если и пока это не разрешено будущими действиями по стандартизации,
Domain administrator advice
Рекомендации администраторам доменов
Expecting everyone to update their client applications when the first server publishes a SRV RR is futile (even if desirable). Therefore SRV would have to coexist with address record lookups for existing protocols, and DNS administrators should try to provide address records to support old clients:
Ожидать, что все обновят свои клиентские приложения, когда первый сервер опубликует запись SRV, тщетно (даже если это желательно). Поэтому SRV придётся сосуществовать с поиском адресных записей для существующих протоколов, и администраторам DNS следует стараться предоставлять адресные записи для поддержки старых клиентов:
- Where the services for a single domain are spread over several hosts, it seems advisable to have a list of address records at the same DNS node as the SRV RR, listing reasonable (if perhaps suboptimal) fallback hosts for Telnet, NNTP and other protocols likely to be used with this name. Note that some programs only try the first address they get back from e.g. gethostbyname(), and we don't know how widespread this behavior is.
- Там, где службы для одного домена распределены по нескольким хостам, представляется целесообразным иметь список адресных записей в том же узле DNS, что и RR SRV, перечисляющий разумные (хотя, возможно, не оптимальные) резервные хосты для Telnet, NNTP и других протоколов, которые, вероятно, будут использоваться с этим именем. Обратите внимание, что некоторые программы пробуют только первый адрес, который они получают, например от gethostbyname(), и мы не знаем, насколько это поведение распространено.
- Where one service is provided by several hosts, one can either provide address records for all the hosts (in which case the round-robin mechanism, where available, will share the load equally) or just for one (presumably the fastest).
- Там, где одна служба предоставляется несколькими хостами, можно либо предоставить адресные записи для всех хостов (и в этом случае механизм кругового перебора, где он доступен, будет распределять нагрузку поровну), либо только для одного (предположительно самого быстрого).
- If a host is intended to provide a service only when the main server(s) is/are down, it probably shouldn't be listed in address records.
- Если хост предназначен для предоставления службы только тогда, когда основной сервер (основные серверы) недоступен, его, вероятно, не следует включать в адресные записи.
- Hosts that are referenced by backup address records must use the port number specified in Assigned Numbers for the service.
- Хосты, на которые ссылаются резервные адресные записи, должны использовать номер порта, указанный в Assigned Numbers для этой службы.
- Designers of future protocols for which "secondary servers" is not useful (or meaningful) may choose to not use SRV's support for secondary servers.
- Разработчики будущих протоколов, для которых «вторичные серверы» бесполезны (или бессмысленны), могут выбрать не использовать поддержку вторичных серверов в SRV.
Clients for such protocols may use or ignore SRV RRs with Priority higher than the RR with the lowest Priority for a domain.
Клиенты таких протоколов могут использовать или игнорировать SRV RR с приоритетом выше, чем у RR с наименьшим приоритетом для домена.
Currently there's a practical limit of 512 bytes for DNS replies. Until all resolvers can handle larger responses, domain administrators are strongly advised to keep their SRV replies below 512 bytes.
В настоящее время существует практическое ограничение в 512 байт для ответов DNS. Пока не все резолверы смогут обрабатывать ответы большего размера, администраторам доменов настоятельно рекомендуется держать ответы SRV в пределах 512 байт.
All round numbers, wrote Dr. Johnson, are false, and these numbers are very round: A reply packet has a 30-byte overhead plus the name of the service ("_ldap._tcp.example.com" for instance); each SRV RR adds 20 bytes plus the name of the target host; each NS RR in the NS section is 15 bytes plus the name of the name server host; and finally each A RR in the additional data section is 20 bytes or so, and there are A's for each SRV and NS RR mentioned in the answer. This size estimate is extremely crude, but shouldn't underestimate the actual answer size by much. If an answer may be close to the limit, using a DNS query tool (e.g. "dig") to look at the actual answer is a good idea.
Все круглые числа ложны, писал доктор Джонсон, и эти числа очень круглые: пакет ответа имеет накладные расходы в 30 байт плюс имя службы (например, «_ldap._tcp.example.com»); каждая RR SRV добавляет 20 байт плюс имя целевого хоста; каждая RR NS в разделе NS составляет 15 байт плюс имя хоста сервера имён; и наконец каждая RR A в разделе дополнительных данных составляет около 20 байт, а записи A есть для каждой RR SRV и RR NS, упомянутой в ответе. Эта оценка размера крайне груба, но не должна сильно занижать фактический размер ответа. Если ответ может быть близок к пределу, хорошей идеей будет воспользоваться инструментом запросов DNS (например, «dig»), чтобы посмотреть на фактический ответ.
The "Weight" field
Поле «Weight»
Weight, the server selection field, is not quite satisfactory, but the actual load on typical servers changes much too quickly to be kept around in DNS caches. It seems to the authors that offering administrators a way to say "this machine is three times as fast as that one" is the best that can practically be done. The only way the authors can see of getting a "better" load figure is asking a separate server when the client selects a server and contacts it. For short-lived services an extra step in the connection establishment seems too expensive, and for long-lived services, the load figure may well be thrown off a minute after the connection is established when someone else starts or finishes a heavy job.
Weight, поле выбора сервера, не вполне удовлетворительно, но фактическая нагрузка на типичные серверы меняется слишком быстро, чтобы её можно было хранить в кэшах DNS. Авторам представляется, что предложить администраторам способ сказать «эта машина в три раза быстрее той» — лучшее, что практически можно сделать. Единственный известный авторам способ получить «лучшую» цифру нагрузки — опрашивать отдельный сервер, когда клиент выбирает сервер и связывается с ним. Для недолго живущих служб лишний шаг при установлении соединения представляется слишком дорогим, а для долгоживущих служб цифра нагрузки вполне может устареть через минуту после соединения.
Note: There are currently various experiments at providing relative network proximity estimation, available bandwidth estimation, and similar services. Use of the SRV record with such facilities, and in particular the interpretation of the Weight field when these facilities are used, is for further study. Weight is only intended for static, not dynamic, server selection. Using SRV weight for dynamic server selection would require assigning unreasonably short TTLs to the SRV RRs, which would limit the usefulness of the DNS caching mechanism, thus increasing overall network load and decreasing overall reliability. Server selection via SRV is only intended to express static information such as "this server has a faster CPU than that one" or "this server has a much better network connection than that one".
Примечание. В настоящее время существуют различные эксперименты по оценке относительной сетевой близости, оценке доступной полосы пропускания и подобным службам. Использование записи SRV с такими средствами и, в частности, интерпретация поля Weight при использовании этих средств, требует дальнейшего изучения. Weight предназначен только для статического, а не динамического выбора сервера. Использование веса SRV для динамического выбора сервера потребовало бы назначения неразумно коротких TTL для RR SRV, что ограничило бы полезность механизма кэширования DNS, увеличив тем самым общую сетевую нагрузку и снизив общую надёжность. Выбор сервера посредством SRV предназначен только для выражения статической информации, такой как «у этого сервера процессор быстрее, чем у того» или «у этого сервера гораздо лучше сетевое соединение, чем у того».
The Port number
Номер порта
Currently, the translation from service name to port number happens at the client, often using a file such as /etc/services.
В настоящее время преобразование имени службы в номер порта происходит на клиенте, часто с использованием такого файла, как /etc/services.
Moving this information to the DNS makes it less necessary to update these files on every single computer of the net every time a new service is added, and makes it possible to move standard services out of the "root-only" port range on unix.
Перемещение этой информации в DNS делает менее необходимым обновление этих файлов на каждом отдельном компьютере сети всякий раз, когда добавляется новая служба, и делает возможным вывести стандартные службы из диапазона портов «только для root» в Unix.
Usage rules
Правила использования
A SRV-cognizant client SHOULD use this procedure to locate a list of servers and connect to the preferred one:
Клиент, понимающий SRV, СЛЕДУЕТ этой процедуре для определения списка серверов и подключения к предпочтительному:
Do a lookup for QNAME=_service._protocol.target, QCLASS=IN, QTYPE=SRV.
Выполнить поиск для QNAME=_service._protocol.target, QCLASS=IN, QTYPE=SRV.
If the reply is NOERROR, ANCOUNT>0 and there is at least one SRV RR which specifies the requested Service and Protocol in the reply:
Если ответ NOERROR, ANCOUNT>0 и в ответе есть хотя бы одна RR SRV, задающая запрошенные Service и Protocol:
If there is precisely one SRV RR, and its Target is "." (the root domain), abort. Else, for all such RR's, build a list of (Priority, Weight, Target) tuples
Если имеется ровно одна RR SRV и её Target равен «.» (корневой домен), прервать. Иначе для всех таких RR построить список кортежей (Priority, Weight, Target).
Sort the list by priority (lowest number first)
Отсортировать список по приоритету (наименьший номер первым).
Create a new empty list
Создать новый пустой список.
For each distinct priority level While there are still elements left at this priority level
Для каждого отдельного уровня приоритета: пока на этом уровне приоритета остаются элементы.
Select an element as specified above, in the description of Weight in "The format of the SRV RR" Section, and move it to the tail of the new list
Выбрать элемент, как указано выше в описании Weight в разделе «Формат записи SRV», и переместить его в конец нового списка.
For each element in the new list
Для каждого элемента в новом списке
query the DNS for address records for the Target or use any such records found in the Additional Data section of the earlier SRV response.
Запросить в DNS адресные записи для Target либо использовать любые такие записи, найденные в разделе Additional Data предыдущего ответа SRV.
for each address record found, try to connect to the (protocol, address, service).
Для каждой найденной адресной записи попытаться подключиться к (протоколу, адресу, службе).
else
Иначе:
Do a lookup for QNAME=target, QCLASS=IN, QTYPE=A
Выполнить поиск для QNAME=target, QCLASS=IN, QTYPE=A;
for each address record found, try to connect to the (protocol, address, service)
Для каждой найденной адресной записи попытаться подключиться к (протоколу, адресу, службе).
Notes:
Примечания:
- Port numbers SHOULD NOT be used in place of the symbolic service or protocol names (for the same reason why variant names cannot be allowed: Applications would have to do two or more lookups).
- Номера портов НЕ СЛЕДУЕТ использовать вместо символических имён службы или протокола (по той же причине, по которой нельзя допускать варианты имён: приложениям пришлось бы делать два или более поисков).
- If a truncated response comes back from an SRV query, the rules described in [RFC 2181] shall apply.
- Если при запросе SRV возвращается усечённый ответ, применяются правила, описанные в [RFC 2181].
- A client MUST parse all of the RR's in the reply.
- Клиент ДОЛЖЕН разобрать все RR в ответе.
- If the Additional Data section doesn't contain address records for all the SRV RR's and the client may want to connect to the target host(s) involved, the client MUST look up the address record(s). (This happens quite often when the address record has shorter TTL than the SRV or NS RR's.) - Future protocols could be designed to use SRV RR lookups as the means by which clients locate their servers.
- Если раздел Additional Data не содержит адресных записей для всех RR SRV и клиент может пожелать подключиться к задействованным целевым хостам, клиент ДОЛЖЕН выполнить поиск адресной записи (адресных записей). (Это происходит довольно часто, когда адресная запись имеет меньший TTL, чем RR SRV или NS.)

Changes from RFC 2052
Изменения относительно RFC 2052
This document obsoletes RFC 2052. The major change from that previous, experimental, version of this specification is that now the protocol and service labels are prepended with an underscore, to lower the probability of an accidental clash with a similar name used for unrelated purposes. Aside from that, changes are only intended to increase the clarity and completeness of the document. This document especially clarifies the use of the Weight field of the SRV records.
Настоящий документ отменяет RFC 2052. Основное изменение относительно предыдущей экспериментальной версии этой спецификации состоит в том, что теперь ярлыки протокола и службы предваряются символом подчёркивания, чтобы снизить вероятность случайного совпадения с похожим именем, используемым для несвязанных целей. Помимо этого, изменения носят исключительно редакционный характер.
Security Considerations
Вопросы безопасности
The authors believe this RR to not cause any new security problems. Some problems become more visible, though.
Авторы полагают, что эта RR не создаёт новых проблем безопасности. Однако некоторые проблемы становятся более заметными.
- The ability to specify ports on a fine-grained basis obviously changes how a router can filter packets. It becomes impossible to block internal clients from accessing specific external services, slightly harder to block internal users from running unauthorized services, and more important for the router operations and DNS operations personnel to cooperate.
- Возможность указывать порты на мелкозернистой основе, очевидно, меняет то, как маршрутизатор может фильтровать пакеты. Становится невозможно заблокировать внутренним клиентам доступ к конкретным внешним службам, несколько сложнее блокировать внутренних пользователей от запуска несанкционированных служб, и более важными становятся операции маршрутизатора и управление DNS.
- There is no way a site can keep its hosts from being referenced as servers. This could lead to denial of service. - With SRV, DNS spoofers can supply false port numbers, as well as host names and addresses. Because this vulnerability exists already, with names and addresses, this is not a new vulnerability, merely a slightly extended one, with little practical effect.
- Нет способа, которым сайт может воспрепятствовать тому, чтобы его хосты упоминались как серверы. Это может привести к отказу в обслуживании. - С SRV подделыватели DNS могут предоставлять ложные номера портов, а также имена хостов и адреса. Поскольку эта уязвимость уже существует для имён и адресов, это не новая уязвимость, а лишь слегка расширенная, с малым практическим эффектом.
