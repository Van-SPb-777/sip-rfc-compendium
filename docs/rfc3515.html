Abstract
Аннотация
This document defines the REFER method. This Session Initiation Protocol (SIP) extension requests that the recipient REFER to a resource provided in the request. It provides a mechanism allowing the party sending the REFER to be notified of the outcome of the referenced request. This can be used to enable many applications, including call transfer.
Настоящий документ определяет метод REFER. Это расширение протокола инициирования сессий (SIP) запрашивает, чтобы получатель обратился (REFER) к ресурсу, предоставленному в запросе. Оно предоставляет механизм, позволяющий стороне, отправившей REFER, быть уведомлённой о результате указанного запроса. Это может использоваться для обеспечения многих приложений, включая перевод вызова.
In addition to the REFER method, this document defines the the refer event package and the Refer-To request header.
Помимо метода REFER, настоящий документ определяет пакет событий refer и заголовок запроса Refer-To.
1. Overview
1. Обзор
This document defines the REFER method. This SIP [1] extension requests that the recipient REFER to a resource provided in the request.
Настоящий документ определяет метод REFER. Это расширение SIP [1] запрашивает, чтобы получатель обратился к ресурсу, предоставленному в запросе.
This can be used to enable many applications, including Call Transfer. For instance, if Alice is in a call with Bob, and decides Bob needs to talk to Carol, Alice can instruct her SIP user agent (UA) to send a SIP REFER request to Bob's UA providing Carol's SIP Contact information. Assuming Bob has given it permission, Bob's UA will attempt to call Carol using that contact. Bob's UA will then report whether it succeeded in reaching the contact to Alice's UA.
Это может использоваться для обеспечения многих приложений, включая перевод вызова. Например, если Alice находится в разговоре с Bob и решает, что Bob нужно поговорить с Carol, Alice может дать указание своему пользовательскому агенту SIP (UA) отправить запрос SIP REFER UA Bob, предоставив контактную информацию SIP Carol. При условии что Bob дал на это разрешение, UA Bob попытается позвонить Carol, используя этот контакт. Затем UA Bob сообщит UA Alice, удалось ли ему связаться с контактом.
2. The REFER Method
2. Метод REFER
REFER is a SIP method as defined by RFC 3261 [1]. The REFER method indicates that the recipient (identified by the Request-URI) should contact a third party using the contact information provided in the request.
REFER — это метод SIP, как определено RFC 3261 [1]. Метод REFER указывает, что получатель (идентифицированный Request-URI) должен связаться с третьей стороной, используя контактную информацию, предоставленную в запросе.
Unless stated otherwise, the protocol for emitting and responding to a REFER request are identical to those for a BYE request in [1]. The behavior of SIP entities not implementing the REFER (or any other unknown) method is explicitly defined in [1].
Если не указано иное, протокол отправки и ответа на запрос REFER идентичен таковому для запроса BYE в [1]. Поведение SIP-объектов, не реализующих метод REFER (или любой другой неизвестный метод), явно определено в [1].
A REFER request implicitly establishes a subscription to the refer event. Event subscriptions are defined in [2].
Запрос REFER неявно устанавливает подписку на событие refer. Подписки на события определены в [2].
A REFER request MAY be placed outside the scope of a dialog created with an INVITE. REFER creates a dialog, and MAY be Record-Routed, hence MUST contain a single Contact header field value. REFERs occurring inside an existing dialog MUST follow the Route/Record- Route logic of that dialog.
Запрос REFER МОЖЕТ быть размещён вне области диалога, созданного с помощью INVITE. REFER создаёт диалог и МОЖЕТ быть Record-Routed, следовательно, ДОЛЖЕН содержать единственное значение поля заголовка Contact. Запросы REFER, occurring внутри существующего диалога, ДОЛЖНЫ следовать логике Route/Record-Route этого диалога.

2.3. Message Body Inclusion
2.3. Включение тела сообщения
A REFER method MAY contain a body. This specification assigns no meaning to such a body. A receiving agent may choose to process the body according to its Content-Type.
Метод REFER МОЖЕТ содержать тело. Настоящая спецификация не придаёт никакого значения такому телу. Принимающий агент может по своему выбору обработать тело согласно его Content-Type.
2.4. Behavior of SIP User Agents
2.4. Поведение пользовательских агентов SIP
2.4.1. Forming a REFER request
2.4.1. Формирование запроса REFER
REFER is a SIP request and is constructed as defined in [1]. A REFER request MUST contain exactly one Refer-To header field value.
REFER — это запрос SIP, и он строится так, как определено в [1]. Запрос REFER ДОЛЖЕН содержать ровно одно значение поля заголовка Refer-To.
2.4.2. Processing a REFER request
2.4.2. Обработка запроса REFER
A UA accepting a well-formed REFER request SHOULD request approval from the user to proceed (this request could be satisfied with an interactive query or through accessing configured policy). If approval is granted, the UA MUST contact the resource identified by the URI in the Refer-To header field value as discussed in Section 2.4.3.
UA, принимающий правильно сформированный запрос REFER, СЛЕДУЕТ запросить у пользователя одобрение на продолжение (этот запрос может быть удовлетворён интерактивным опросом либо обращением к сконфигурированной политике). Если одобрение получено, UA ДОЛЖЕН связаться с ресурсом, идентифицированным URI в значении поля заголовка Refer-To, как обсуждается в разделе 2.4.3.
If the approval sought above for a well-formed REFER request is immediately denied, the UA MAY decline the request.
Если испрошенное выше одобрение для правильно сформированного запроса REFER немедленно отклонено, UA МОЖЕТ отклонить запрос.
An agent responding to a REFER method MUST return a 400 (Bad Request) if the request contained zero or more than one Refer-To header field values.
Агент, отвечающий на метод REFER, ДОЛЖЕН вернуть 400 (Bad Request), если запрос содержал ноль или более одного значения поля заголовка Refer-To.
An agent (including proxies generating local responses) MAY return a 100 (Trying) or any appropriate 4xx-6xx class response as prescribed by [1].
Агент (включая прокси, генерирующие локальные ответы) МОЖЕТ вернуть 100 (Trying) или любой подходящий ответ класса 4xx–6xx, как предписано в [1].
Care should be taken when implementing the logic that determines whether or not to accept the REFER request. A UA not capable of accessing non-SIP URIs SHOULD NOT accept REFER requests to them.
Следует соблюдать осторожность при реализации логики, определяющей, принимать ли запрос REFER. UA, не способный обращаться к не-SIP URI, НЕ СЛЕДУЕТ принимать запросы REFER к ним.
If no final response has been generated according to the rules above, the UA MUST return a 202 Accepted response before the REFER transaction expires.
Если по правилам выше не сгенерировано окончательного ответа, UA ДОЛЖЕН вернуть ответ 202 Accepted до истечения транзакции REFER.
If a REFER request is accepted (that is, a 2xx class response is returned), the recipient MUST create a subscription and send notifications of the status of the refer as described in Section 2.4.4.
Если запрос REFER принят (то есть возвращён ответ класса 2xx), получатель ДОЛЖЕН создать подписку и отправлять уведомления о состоянии ссылки, как описано в разделе 2.4.4.
2.4.3. Accessing the Referred-to Resource
2.4.3. Доступ к ресурсу, на который указывает ссылка
The resource identified by the Refer-To URI is contacted using the normal mechanisms for that URI type. For example, if the URI is a SIP URI indicating INVITE (using a method=INVITE URI parameter for example), the UA would issue a new INVITE using all of the normal rules for sending an INVITE defined in [1]. 2.4.4 Using SIP Events to Report the Results of the Reference
Связь с ресурсом, идентифицированным URI Refer-To, устанавливается с использованием обычных механизмов для этого типа URI. Например, если URI — это URI SIP, указывающий INVITE (например, с параметром URI method=INVITE), UA выдал бы новый INVITE, используя все обычные правила отправки INVITE, определённые в [1].
The NOTIFY mechanism defined in [2] MUST be used to inform the agent sending the REFER of the status of the reference. The dialog identifiers (To, From, and Call-ID) of each NOTIFY must match those of the REFER as they would if the REFER had been a SUBSCRIBE request.
Механизм NOTIFY, определённый в [2], ДОЛЖЕН использоваться, чтобы информировать агента, отправившего REFER, о состоянии ссылки. Идентификаторы диалога (To, From и Call-ID) каждого NOTIFY должны совпадать с таковыми у REFER так, как если бы REFER был запросом SUBSCRIBE.
Each NOTIFY MUST contain an Event header field with a value of refer and possibly an id parameter (see Section 2.4.6).
Каждый NOTIFY ДОЛЖЕН содержать поле заголовка Event со значением refer и, возможно, параметр id (см. раздел 2.4.6).
Each NOTIFY MUST contain a body of type "message/sipfrag" [3].
Каждый NOTIFY ДОЛЖЕН содержать тело типа «message/sipfrag» [3].
The creation of a subscription as defined by [2] always results in an immediate NOTIFY. Analogous to the case for SUBSCRIBE described in that document, the agent that issued the REFER MUST be prepared to receive a NOTIFY before the REFER transaction completes.
Создание подписки, как определено в [2], всегда приводит к немедленному NOTIFY. Аналогично случаю с SUBSCRIBE, описанному в том документе, агент, выдавший REFER, ДОЛЖЕН быть готов получить NOTIFY до завершения транзакции REFER.
The implicit subscription created by a REFER is the same as a subscription created with a SUBSCRIBE request. The agent issuing the REFER can terminate this subscription prematurely by unsubscribing using the mechanisms described in [2]. Terminating a subscription, either by explicitly unsubscribing or rejecting NOTIFY, is not an indication that the referenced request should be withdrawn or abandoned. In particular, an agent acting on a REFER request SHOULD NOT issue a CANCEL to any referenced SIP requests because the agent sending the REFER terminated its subscription to the refer event before the referenced request completes.
Неявная подписка, созданная REFER, такая же, как подписка, созданная с помощью запроса SUBSCRIBE. Агент, выдающий REFER, может преждевременно завершить эту подписку, отменив её с использованием механизмов, описанных в [2]. Завершение подписки — явной отменой подписки или отклонением NOTIFY — не является указанием на то, что указанный запрос следует отозвать или прекратить. В частности, агенту, действующему по запросу REFER, НЕ СЛЕДУЕТ выдавать CANCEL для каких-либо указанных запросов SIP из-за того, что агент, отправивший REFER, завершил свою подписку на событие refer до завершения указанного запроса.
The agent issuing the REFER may extend its subscription using the subscription refresh mechanisms described in [2].
Агент, выдающий REFER, может продлить свою подписку с использованием механизмов возобновления подписки, описанных в [2].
REFER is the only mechanism that can create a subscription to event refer. If a SUBSCRIBE request for event refer is received for a subscription that does not already exist, it MUST be rejected with a 403.
REFER — единственный механизм, способный создать подписку на событие refer. Если запрос SUBSCRIBE для события refer получен для подписки, которая ещё не существует, он ДОЛЖЕН быть отклонён ответом 403.
Notice that unlike SUBSCRIBE, the REFER transaction does not contain a duration for the subscription in either the request or the response. The lifetime of the state being subscribed to is determined by the progress of the referenced request. The duration of the subscription is chosen by the agent accepting the REFER and is communicated to the agent sending the REFER in the subscription's initial NOTIFY (using the Subscription-State expires header parameter). Note that agents accepting REFER and not wishing to hold subscription state can terminate the subscription with this initial NOTIFY.
Обратите внимание, что в отличие от SUBSCRIBE транзакция REFER не содержит длительности подписки ни в запросе, ни в ответе. Время жизни состояния, на которое подписываются, определяется ходом указанного запроса. Длительность подписки выбирается агентом, принимающим REFER, и сообщается агенту, отправляющему REFER, в начальном NOTIFY подписки (с использованием параметра заголовка Subscription-State expires). Обратите внимание, что агенты, принимающие REFER и не желающие поддерживать состояние подписки, могут завершить подписку этим начальным NOTIFY.
2.4.5. The Body of the NOTIFY
2.4.5. Тело NOTIFY
Each NOTIFY MUST contain a body of type "message/sipfrag" [3]. The body of a NOTIFY MUST begin with a SIP Response Status-Line as defined in [1]. The response class in this status line indicates the status of the referred action. The body MAY contain other SIP header fields to provide information about the outcome of the referenced action. This body provides a complete statement of the status of the referred action. The refer event package does not support state deltas.
Каждый NOTIFY ДОЛЖЕН содержать тело типа «message/sipfrag» [3]. Тело NOTIFY ДОЛЖНО начинаться со строки состояния SIP Response Status-Line, как определено в [1]. Класс ответа в этой строке состояния указывает состояние указанного действия. Тело МОЖЕТ содержать другие поля заголовков SIP для предоставления информации о результате указанного действия. Это тело предоставляет полное утверждение о состоянии указанного действия. Пакет событий refer не поддерживает разностные изменения состояния.
If a NOTIFY is generated when the subscription state is pending, its body should consist only of a status line containing a response code of 100.
Если NOTIFY генерируется, когда состояние подписки — pending, его тело должно состоять только из строки состояния, содержащей код ответа 100.
A minimal, but complete, implementation can respond with a single NOTIFY containing either the body:
Минимальная, но полная реализация может ответить единственным NOTIFY, содержащим либо тело:
SIP/2.0 100 Trying
SIP/2.0 100 Trying
if the subscription is pending, the body:
если подписка находится в ожидании, тело:
SIP/2.0 200 OK
SIP/2.0 200 OK
if the reference was successful, the body:
если ссылка была успешной, тело:
SIP/2.0 503 Service Unavailable
SIP/2.0 503 Service Unavailable
if the reference failed, or the body:
если ссылка не удалась, либо тело:
SIP/2.0 603 Declined
SIP/2.0 603 Declined
if the REFER request was accepted before approval to follow the reference could be obtained and that approval was subsequently denied (see Section 2.4.7).
если запрос REFER был принят до получения одобрения на следование ссылке и это одобрение впоследствии было отклонено (см. раздел 2.4.7).
An implementation MAY include more of a SIP message in that body to convey more information. Warning header field values received in responses to the referred action are good candidates. In fact, if the reference was to a SIP URI, the entire response to the referenced action could be returned (perhaps to assist with debugging). However, doing so could have grave security repercussions (see Section 5). Implementers must carefully consider what they choose to include.
Реализация МОЖЕТ включать больше сообщения SIP в это тело для передачи большего объёма информации. Значения полей заголовка Warning, полученные в ответах на указанное действие, — хорошие кандидаты. Фактически если ссылка была на URI SIP, можно было бы вернуть весь ответ на указанное действие (возможно, в помощь отладке). Однако это могло бы иметь серьёзные последствия для безопасности (см. раздел 5). Разработчики должны тщательно обдумать, что они решат включить.
Note that if the reference was to a non-SIP URI, status in any NOTIFYs to the referrer must still be in the form of SIP Response Status-Lines. The minimal implementation discussed above is sufficient to provide a basic indication of success or failure. For example, if a client receives a REFER to a HTTP URL, and is successful in accessing the resource, its NOTIFY to the referrer can contain the message/sipfrag body of "SIP/2.0 200 OK". If the notifier wishes to return additional non-SIP protocol specific information about the status of the request, it may place it in the body of the sipfrag message.
Обратите внимание, что если ссылка была на не-SIP URI, состояние во всех NOTIFY отправителю ссылки всё равно должно быть в форме строк состояния SIP Response Status-Lines. Минимальная реализация, обсуждённая выше, достаточна для предоставления базового указания на успех или неудачу. Например, если клиент получает REFER на HTTP URL и успешно обращается к ресурсу, его NOTIFY отправителю ссылки может содержать тело message/sipfrag «SIP/2.0 200 OK». Если уведомитель желает вернуть дополнительную информацию о состоянии запроса, специфичную для не-SIP протокола, он может поместить её в тело сообщения sipfrag.
2.4.6. Multiple REFER Requests in a Dialog
2.4.6. Несколько запросов REFER в диалоге
A REFER creates an implicit subscription sharing the dialog identifiers in the REFER request. If more than one REFER is issued in the same dialog (a second attempt at transferring a call for example), the dialog identifiers do not provide enough information to associate the resulting NOTIFYs with the proper REFER.
REFER создаёт неявную подписку, разделяющую идентификаторы диалога в запросе REFER. Если в одном диалоге выдано более одного REFER (например, вторая попытка перевода вызова), идентификаторы диалога не дают достаточно информации, чтобы связать результирующие NOTIFY с нужным REFER.
Thus, for the second and subsequent REFER requests a UA receives in a given dialog, it MUST include an id parameter[2] in the Event header field of each NOTIFY containing the sequence number (the number from the CSeq header field value) of the REFER this NOTIFY is associated with. This id parameter MAY be included in NOTIFYs to the first REFER a UA receives in a given dialog. A SUBSCRIBE sent to refresh or terminate this subscription MUST contain this id parameter.
Поэтому для второго и последующих запросов REFER, которые UA получает в данном диалоге, он ДОЛЖЕН включать параметр id [2] в поле заголовка Event каждого NOTIFY, содержащий порядковый номер (номер из значения поля заголовка CSeq) REFER, с которым связан этот NOTIFY. Этот параметр id МОЖЕТ включаться в NOTIFY для первого REFER, который UA получает в данном диалоге. SUBSCRIBE, отправленный для возобновления или завершения этой подписки, ДОЛЖЕН содержать этот параметр id.
2.4.7. Using the Subscription-State Header Field with Event Refer
2.4.7. Использование поля заголовка Subscription-State с событием refer
Each NOTIFY must contain a Subscription-State header field as defined in [2]. The final NOTIFY sent in response to a REFER MUST indicate the subscription has been "terminated" with a reason of "noresource". (The resource being subscribed to is the state of the referenced request).
Каждый NOTIFY должен содержать поле заголовка Subscription-State, как определено в [2]. Финальный NOTIFY, отправленный в ответ на REFER, ДОЛЖЕН указывать, что подписка «terminated» (прекращена) с причиной «noresource». (Ресурс, на который подписываются, — это состояние указанного запроса.)
If a NOTIFY indicates a reason that indicates a re-subscribe is appropriate according to [2], the agent sending the REFER is NOT obligated to re-subscribe.
Если NOTIFY указывает причину, которая согласно [2] указывает на уместность повторной подписки, агент, отправляющий REFER, НЕ обязан повторно подписываться.
In the case where a REFER was accepted with a 202, but approval to follow the reference was subsequently denied, the reason and retry- after elements of the Subscription-State header field can be used to indicate if and when the REFER can be re-attempted (as described for SUBSCRIBE in [2]).
В случае если REFER был принят с 202, но одобрение на следование ссылке впоследствии отклонено, элементы reason и retry-after поля заголовка Subscription-State могут использоваться, чтобы указать, можно ли и когда повторить REFER (как описано для SUBSCRIBE в [2]).
2.5. Behavior of SIP Registrars/Redirect Servers
2.5. Поведение регистраторов и серверов перенаправления SIP
A registrar that is unaware of the definition of the REFER method will return a 501 response as defined in [1]. A registrar aware of the definition of REFER SHOULD return a 405 response. This specification places no requirements on redirect server behavior beyond those specified in [1]. Thus, it is possible for REFER requests to be redirected.
Регистратор, не знающий определения метода REFER, вернёт ответ 501, как определено в [1]. Регистратору, знающему определение REFER, СЛЕДУЕТ вернуть ответ 405. Настоящая спецификация не предъявляет к поведению сервера перенаправления никаких требований сверх указанных в [1]. Таким образом, запросы REFER могут быть перенаправлены.
2.6. Behavior of SIP Proxies
2.6. Поведение прокси-серверов SIP
SIP proxies do not require modification to support the REFER method. Specifically, as required by [1], a proxy should process a REFER request the same way it processes an OPTIONS request.
Прокси-серверы SIP не требуют модификации для поддержки метода REFER. В частности, как требуется в [1], прокси должен обрабатывать запрос REFER так же, как он обрабатывает запрос OPTIONS.

3.4. Subscription Duration
3.4. Длительность подписки
The duration of an implicit subscription created by a REFER request is initially determined by the agent accepting the REFER and communicated to the subscribing agent in the Subscription-State header field's expire parameter in the first NOTIFY sent in the subscription. Reasonable choices for this initial duration depend on the type of request indicated in the Refer-To URI. The duration SHOULD be chosen to be longer than the time the referenced request will be given to complete. For example, if the Refer-To URI is a SIP INVITE URI, the subscription interval should be longer than the Expire value in the INVITE. Additional time MAY be included to account for time needed to authorize the subscription. The subscribing agent MAY extend the subscription by refreshing it, or terminate it by unsubscribing. As described in Section 2.4.7, the agent accepting the REFER will terminate the subscription when it reports the final result of the reference, indicating that termination in the Subscription-State header field.
Длительность неявной подписки, созданной запросом REFER, изначально определяется агентом, принимающим REFER, и сообщается подписывающемуся агенту в параметре expire поля заголовка Subscription-State в первом NOTIFY, отправленном в подписке. Разумные варианты этой начальной длительности зависят от типа запроса, указанного в URI Refer-To. Длительность СЛЕДУЕТ выбирать большей, чем время, отведённое указанному запросу на завершение. Например, если URI Refer-To — это URI SIP INVITE, интервал подписки должен быть больше значения Expire в INVITE. МОЖЕТ быть включено дополнительное время для учёта времени, необходимого на авторизацию подписки. Подписывающийся агент МОЖЕТ продлить подписку, возобновив её, либо завершить её, отменив подписку. Как описано в разделе 2.4.7, агент, принимающий REFER, завершит подписку, когда сообщит окончательный результат ссылки, указав это завершение в поле заголовка Subscription-State.

3.9. Handling of Forked Requests
3.9. Обработка разветвлённых запросов
A REFER sent within the scope of an existing dialog will not fork. A REFER sent outside the context of a dialog MAY fork, and if it is accepted by multiple agents, MAY create multiple subscriptions. These subscriptions are created and managed as per "Handling of Forked Requests" in [2] as if the REFER had been a SUBSCRIBE. The agent sending the REFER manages the state associated with each subscription separately. It does NOT merge the state from the separate subscriptions. The state is the status of the referenced request at each of the accepting agents.
REFER, отправленный в пределах существующего диалога, не будет разветвлён. REFER, отправленный вне контекста диалога, МОЖЕТ быть разветвлён и, если он принят несколькими агентами, МОЖЕТ создать несколько подписок. Эти подписки создаются и управляются согласно «Обработке разветвлённых запросов» в [2], как если бы REFER был SUBSCRIBE. Агент, отправляющий REFER, управляет состоянием, связанным с каждой подпиской, отдельно. Он НЕ объединяет состояние отдельных подписок. Состояние — это состояние указанного запроса у каждого из принимающих агентов.
3.10. Rate of Notifications
3.10. Частота уведомлений
An event refer NOTIFY might be generated each time new knowledge of the status of a referenced requests becomes available. For instance, if the REFER was to a SIP INVITE, NOTIFYs might be generated with each provisional response and the final response to the INVITE. Alternatively, the subscription might only result in two NOTIFY requests, the immediate NOTIFY and the NOTIFY carrying the final result of the reference. NOTIFYs to event refer SHOULD NOT be sent more frequently than once per second.
NOTIFY события refer может генерироваться каждый раз, когда становятся доступны новые сведения о состоянии указанного запроса. Например, если REFER был на SIP INVITE, NOTIFY могли бы генерироваться при каждом предварительном ответе и окончательном ответе на INVITE. Либо подписка могла бы привести только к двум запросам NOTIFY: немедленному NOTIFY и NOTIFY, несущему окончательный результат ссылки. NOTIFY для события refer НЕ СЛЕДУЕТ отправлять чаще одного раза в секунду.

5. Security Considerations
5. Вопросы безопасности
The security considerations described in Section 26 of [1] apply to the REFER transaction. In particular, the implementation requirements and considerations in Section 26.3 address securing a generic SIP transaction. Special consideration is warranted for the authorization polices applied to REFER requests and for the use of message/sipfrag to convey the results of the referenced request.
Соображения безопасности, описанные в разделе 26 [1], применяются к транзакции REFER. В частности, требования к реализации и соображения в разделе 26.3 касаются защиты общей транзакции SIP. Особого рассмотрения заслуживают политики авторизации, применяемые к запросам REFER, и использование message/sipfrag для передачи результатов указанного запроса.
5.1. Constructing a Refer-To URI
5.1. Построение URI Refer-To
This mechanism relies on providing contact information for the referred-to resource to the party being referred. Care should be taken to provide a suitably restricted URI if the referred-to resource should be protected.
Этот механизм опирается на предоставление контактной информации ресурса, на который указывает ссылка, стороне, которой адресована ссылка. Следует соблюдать осторожность, чтобы предоставить надлежащим образом ограниченный URI, если ресурс, на который указывает ссылка, должен быть защищён.
5.2. Authorization Considerations for REFER
5.2. Соображения авторизации для REFER
As described in Section 2.4.2, an implementation can receive a REFER requests with a Refer-To URI containing an arbitrary scheme. For instance, a user could be referred to an online service such as a MUD using a telnet URI. Customer service could refer a customer to an order tracking web page using an HTTP URI. Section 2.4.2 allows a user agent to reject a REFER request when it can not process the referenced scheme. It also requires the user agent to obtain authorization from its user before attempting to use the URI. Generally, this could be achieved by prompting the user with the full URI and a question such as "Do you wish to access this resource (Y/N)". Of course, URIs can be arbitrarily long and are occasionally constructed with malicious intent, so care should be taken to avoid surprise even in the display of the URI itself (such as partial display or crashing). Further, care should be taken to expose as much information about the reference as possible to the user to mitigate the risk of being misled into a dangerous decision. For instance, the Refer-To header may contain a display name along with the URI. Nothing ensures that any property implied by that display name is shared by the URI. For instance, the display name may contain "secure" or "president" and when the URI indicates sip:agent59@telemarketing.example.com.
Как описано в разделе 2.4.2, реализация может получать запросы REFER с URI Refer-To, содержащими произвольную схему. Например, пользователь мог быть направлен к онлайн-службе, такой как MUD, с использованием URI telnet. Служба поддержки могла бы направить клиента на веб-страницу отслеживания заказов с использованием URI HTTP. Раздел 2.4.2 позволяет пользовательскому агенту отклонить запрос REFER, когда он не может обработать указанную схему. Он также требует, чтобы пользовательский агент получил авторизацию у своего пользователя, прежде чем пытаться использовать URI. Обычно этого можно достичь, запросив у пользователя полный URI и вопрос вида «Желаете ли вы обратиться к этому ресурсу (Y/N)». Разумеется, URI могут быть произвольно длинными и иногда строятся со злым умыслом, поэтому следует соблюдать осторожность, чтобы избежать сюрпризов даже при отображении самого URI (например, частичное отображение или сбой). Более того, следует позаботиться о том, чтобы предоставить пользователю как можно больше информации о ссылке, чтобы смягчить риск быть введённым в заблуждение и принять опасное решение. Например, заголовок Refer-To может содержать отображаемое имя вместе с URI. Ничто не гарантирует, что какое-либо свойство, подразумеваемое этим отображаемым именем, присуще URI. Например, отображаемое имя может содержать «secure» или «president», в то время как URI указывает sip:agent59@telemarketing.example.com.
Thus, prompting the user with the display name alone is insufficient.
Таким образом, запрашивать у пользователя только отображаемое имя недостаточно.
In some cases, the user can provide authorization for some REFER requests ahead of time by providing policy to the user agent. This is appropriate, for instance, for call transfer as discussed in [4]. Here, a properly authenticated REFER request within an existing SIP dialog to a sip:, sips:, or tel: URI may be accepted through policy without interactively obtaining the user's authorization. Similarly, it may be appropriate to accept a properly authenticated REFER to an HTTP URI if the referror is on an explicit list of approved referrors. In the absence of such pre-provided authorization, the user must interactively provide authorization to reference the indicated resource.
В некоторых случаях пользователь может заранее предоставить авторизацию для некоторых запросов REFER, задав политику в пользовательском агенте. Это уместно, например, для перевода вызова, как обсуждается в [4]. Здесь правильно аутентифицированный запрос REFER в существующем диалоге SIP на URI sip:, sips: или tel: может быть принят по политике без интерактивного получения авторизации пользователя. Аналогично может быть уместно принять правильно аутентифицированный REFER на URI HTTP, если отправитель ссылки находится в явном списке одобренных отправителей. При отсутствии такой заранее предоставленной авторизации пользователь должен интерактивно предоставить авторизацию на обращение к указанному ресурсу.
To see the danger of a policy that blindly accepts and acts on an HTTP URI, for example, consider a web server configured to accept requests only from clients behind a small organization's firewall. As it sits in this soft-creamy-middle environment where the small organization trusts all its members and has little internal security, the web server is frequently behind on maintenance, leaving it vulnerable to attack through maliciously constructed URIs (resulting perhaps in running arbitrary code provided in the URI). If a SIP UA inside this firewall blindly accepted a reference to an arbitrary HTTP URI, an attacker outside the firewall could compromise the web server. On the other hand, if the UA's user has to take positive action (such as responding to a prompt) before acting on this URI, the risk is reduced to the same level as the user clicking on the URI in a web-browser or email message.
Чтобы увидеть опасность политики, которая слепо принимает и действует по URI HTTP, например, рассмотрим веб-сервер, сконфигурированный принимать запросы только от клиентов за межсетевым экраном небольшой организации. Находясь в этой «мягкой» среде, где небольшая организация доверяет всем своим членам и имеет слабую внутреннюю безопасность, веб-сервер часто отстаёт в обслуживании, становясь уязвимым для атаки через злонамеренно построенные URI (что может привести, например, к выполнению произвольного кода, предоставленного в URI). Если SIP UA внутри этого межсетевого экрана слепо примет ссылку на произвольный URI HTTP, злоумышленник вне межсетевого экрана мог бы скомпрометировать веб-сервер. С другой стороны, если пользователь UA должен предпринять действие, риск снижается до того же уровня, что и при щелчке пользователя по URI в веб-браузере или сообщении электронной почты.
The conclusion in the above paragraph generalizes to URIs with an arbitrary scheme. An agent that takes automated action to access a URI with a given scheme risks being used to indirectly attack another host that is vulnerable to some security flaw related to that scheme. This risk and the potential for harm to that other host is heightened when the host and agent reside behind a common policy-enforcement point such as a firewall. Furthermore, this agent increases its exposure to denial of service attacks through resource exhaustion, especially if each automated action involves opening a new connection.
Вывод в приведённом выше абзаце обобщается на URI с произвольной схемой. Агент, предпринимающий автоматические действия для обращения к URI с заданной схемой, рискует быть использованным для косвенной атаки на другой хост, уязвимый к некоторой ошибке безопасности, связанной с этой схемой. Этот риск и вероятность вреда тому другому хосту повышаются, когда хост и агент находятся за общим пунктом применения политики, например за межсетевым экраном. Более того, этот агент увеличивает свою подверженность атакам отказа в обслуживании через исчерпание ресурсов, особенно если каждое автоматическое действие включает открытие нового соединения.
User agents should take care when handing an arbitrary URI to a third-party service such as that provided by some modern operating systems, particularly if the user agent is not aware of the scheme and the possible ramifications using the protocols it indicates. The opportunity for violating the principal of least surprise is very high.
Пользовательским агентам следует соблюдать осторожность при передаче произвольного URI сторонней службе, такой как предоставляемая некоторыми современными операционными системами, особенно если пользовательский агент не знает схему и возможные последствия использования указываемых ею протоколов. Возможность нарушения принципа наименьшего удивления очень высока.
5.3. Considerations for the use of message/sipfrag
5.3. Соображения по использованию message/sipfrag
Using message/sipfrag bodies to return the progress and results of a REFER request is extremely powerful. Careless use of that capability can compromise confidentiality and privacy. Here are a couple of simple, somewhat contrived, examples to demonstrate the potential for harm.
Использование тел message/sipfrag для возврата хода и результатов запроса REFER чрезвычайно мощно. Небрежное использование этой возможности может подорвать конфиденциальность и приватность. Вот пара простых, несколько надуманных примеров, демонстрирующих потенциал вреда.
5.3.1. Circumventing Privacy
5.3.1. Обход приватности
Suppose Alice has a user agent that accepts REFER requests to SIP INVITE URIs, and NOTIFYs the referrer of the progress of the INVITE by copying each response to the INVITE into the body of a NOTIFY.
Предположим, у Alice есть пользовательский агент, принимающий запросы REFER на URI SIP INVITE и уведомляющий отправителя ссылки о ходе INVITE путём копирования каждого ответа на INVITE в тело NOTIFY.
Suppose further that Carol has a reason to avoid Mallory and has configured her system at her proxy to only accept calls from a certain set of people she trusts (including Alice), so that Mallory doesn't learn when she's around, or what user agent she's actually using.
Предположим далее, что у Carol есть причина избегать Mallory, и она настроила свою систему у своего прокси так, чтобы принимать вызовы только от определённого набора доверенных лиц (включая Alice), чтобы Mallory не узнал, когда она рядом, или какой пользовательский агент она на самом деле использует.
Mallory can send a REFER to Alice, with a Refer-To URI indicating Carol. If Alice can reach Carol, the 200 OK Carol sends gets returned to Mallory in a NOTIFY, letting him know not only that Carol is around, but also the IP address of the agent she's using.
Mallory может отправить REFER для Alice с URI Refer-To, указывающим на Carol. Если Alice может достичь Carol, ответ 200 OK, который отправляет Carol, возвращается Mallory в NOTIFY, сообщая ему не только о том, что Carol рядом, но и IP-адрес используемого ею агента.
5.3.2. Circumventing Confidentiality
5.3.2. Обход конфиденциальности
Suppose Alice, with the same user agent as above, is working at a company that is working on the greatest SIP device ever invented - the SIP FOO. The company has been working for months building the device and the marketing materials, carefully keeping the idea, even the name of the idea secret (since a FOO is one of those things that anybody could do if they'd just had the idea first). FOO is up and running, and anyone at the company can use it, but it's not available outside the company firewall.
Предположим, Alice с тем же пользовательским агентом, что и выше, работает в компании, разрабатывающей величайшее SIP-устройство из когда-либо изобретённых — SIP FOO. Компания месяцами работала над устройством и маркетинговыми материалами, тщательно храня в тайне идею и даже название идеи (поскольку FOO — одна из тех вещей, которые мог бы сделать любой, если бы только придумал идею первым). FOO работает, и любой в компании может им пользоваться, но он недоступен за пределами межсетевого экрана компании.
Mallory has heard rumor that Alice's company is onto something big, and has even managed to get his hands on a URI that he suspects might have something to do with it. He sends a REFER to ALICE with the mysterious URI and as Alice connects to the FOO, Mallory gets NOTIFYs with bodies containing

5.3.3. Limiting the Breach
5.3.3. Ограничение утечки
For each of these cases, and in general, returning a carefully selected subset of the information available about the progress of the reference through the NOTIFYs mitigates risk. The minimal implementation described in Section 2.4.5 exposes the least information about what the agent operating on the REFER request has done, and is least likely to be a useful tool for malicious users.
Для каждого из этих случаев и в целом возврат тщательно выбранного подмножества доступной информации о ходе ссылки посредством NOTIFY смягчает риск. Минимальная реализация, описанная в разделе 2.4.5, раскрывает меньше всего информации о том, что сделал агент, действующий по запросу REFER, и наименее вероятно станет полезным инструментом для злоумышленников.
5.3.4. Cut, Paste and Replay Considerations
5.3.4. Соображения по копированию и повторному воспроизведению
The mechanism defined in this specification is not directly susceptible to abuse through copying the message/sipfrag bodies from NOTIFY requests and inserting them, in whole or in part, in future NOTIFY requests associated with the same or a different REFER. Under this specification the agent replying to the REFER request is in complete control of the content of the bodies of the NOTIFY it sends. There is no mechanism defined here requiring this agent to faithfully forward any information from the referenced party. Thus, saving a body for later replay gives the agent no more ability to affect the mechanism defined in this document at its peer than it has without that body. Similarly, capture of a message/sipfrag body by eavesdroppers will give them no more ability to affect this mechanism than they would have without it.
Механизм, определённый в настоящей спецификации, не подвержен напрямую злоупотреблению через копирование тел message/sipfrag из запросов NOTIFY и вставку их целиком или частично в будущие запросы NOTIFY, связанные с тем же или другим REFER. По настоящей спецификации агент, отвечающий на запрос REFER, полностью контролирует содержимое тел отправляемых им NOTIFY. Здесь не определён никакой механизм, требующий от этого агента добросовестно пересылать любую информацию от указанной стороны. Таким образом, сохранение тела для последующего воспроизведения не даёт агенту большей возможности влиять на определённый в настоящем документе механизм у своего партнёра, чем без этого тела. Аналогично перехват тела message/sipfrag подслушивающими не даст им большей возможности влиять на этот механизм, чем без него.
Future extensions may place additional constraints on the agent responding to REFER to allow using the message/sipfrag body part in a NOTIFY to make statements like "I contacted the party you referred me to, and here's cryptographic proof". These statements might be used to affect the behavior of the receiving UA. This kind of extension will need to define additional mechanism to protect itself from copy based attacks.
Будущие расширения могут наложить дополнительные ограничения на агента, отвечающего на REFER, чтобы позволить использовать часть тела message/sipfrag в NOTIFY для утверждений вида «Я связался со стороной, к которой вы меня направили, и вот криптографическое доказательство». Эти утверждения могли бы использоваться для воздействия на поведение принимающего UA. Такого рода расширение должно будет определить дополнительный механизм для защиты от атак, основанных на копировании.
6. Historic Material
6. Исторический материал
This method was initially motivated by the call-transfer application. Starting as TRANSFER, and later generalizing to REFER, this method improved on the BYE/Also concept of the expired draft-ietf-sip-cc-01 by disassociating transfers from the processing of BYE. These changes facilitate recovery of failed transfers and clarify state management in the participating entities.
Этот метод изначально был мотивирован приложением перевода вызова. Начавшись как TRANSFER и позже обобщившись до REFER, этот метод улучшил концепцию BYE/Also истёкшего черновика draft-ietf-sip-cc-01, разъединив переводы с обработкой BYE. Эти изменения облегчают восстановление после неудачных переводов и проясняют управление состоянием у участвующих объектов.
Early versions of this work required the agent responding to REFER to wait until the referred action completed before sending a final response to the REFER. That final response reflected the success or failure of the referred action. This was infeasible due to the transaction timeout rules defined for non-INVITE requests in [1]. A REFER must always receive an immediate (within the lifetime of a non-INVITE transaction) final response.
Ранние версии этой работы требовали, чтобы агент, отвечающий на REFER, ждал завершения указанного действия перед отправкой окончательного ответа на REFER. Этот окончательный ответ отражал успех или неудачу указанного действия. Это было неосуществимо из-за правил тайм-аута транзакций, определённых для запросов, не являющихся INVITE, в [1]. REFER всегда должен получать немедленный (в пределах времени жизни транзакции, не являющейся INVITE) окончательный ответ.
