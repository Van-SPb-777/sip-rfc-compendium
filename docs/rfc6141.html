Abstract
Аннотация
The procedures for handling SIP re-INVITEs are described in RFC 3261. Implementation and deployment experience has uncovered a number of issues with the original documentation, and this document provides additional procedures that update the original specification to address those issues. In particular, this document defines in which situations a UAS (User Agent Server) should generate a success response and in which situations a UAS should generate an error response to a re-INVITE. Additionally, this document defines further details of procedures related to target-refresh requests.
Процедуры обработки SIP re-INVITE описаны в RFC 3261. Опыт реализации и развёртывания выявил ряд проблем в исходной документации, и настоящий документ содержит дополнительные процедуры, обновляющие исходную спецификацию и устраняющие эти проблемы. В частности, документ определяет, в каких ситуациях UAS (пользовательский агент-сервер) должен генерировать успешный ответ, а в каких ситуациях UAS должен генерировать ответ с ошибкой на re-INVITE. Кроме того, документ уточняет детали процедур, связанных с запросами целевого обновления.

1. Introduction
1. Введение
As discussed in Section 14 of RFC 3261 [RFC3261], an INVITE request sent within an existing dialog is known as a re-INVITE. A re-INVITE is used to modify session parameters, dialog parameters, or both. That is, a single re-INVITE can change both the parameters of its associated session (e.g., changing the IP address where a media stream is received) and the parameters of its associated dialog (e.g., changing the remote target of the dialog). A re-INVITE can change the remote target of a dialog because it is a target refresh request, as defined in Section 6 of RFC 3261 [RFC3261]. A re-INVITE transaction has an offer/answer [RFC3264] exchange associated with it. The UAC (User Agent Client) generating a given re-INVITE can act as the offerer or as the answerer. A UAC willing to act as the offerer includes an offer in the re-INVITE. The UAS (User Agent Server) then provides an answer in a response to the re-INVITE. A UAC willing to act as answerer does not include an offer in the re-INVITE. The UAS then provides an offer in a response to the re-INVITE becoming, thus, the offerer.
Как обсуждается в разделе 14 RFC 3261 [RFC3261], запрос INVITE, отправленный в рамках существующего диалога, называется re-INVITE. re-INVITE используется для изменения параметров сессии, параметров диалога или и того, и другого. То есть один re-INVITE может изменить как параметры связанной с ним сессии (например, изменить IP-адрес, на который принимается медиапоток), так и параметры связанного с ним диалога (например, изменить удалённую цель диалога). re-INVITE может изменять удалённую цель диалога, поскольку он является запросом целевого обновления, как определено в разделе 6 RFC 3261 [RFC3261]. С транзакцией re-INVITE связан обмен предложением/ответом [RFC3264]. UAC (пользовательский агент-клиент), генерирующий конкретный re-INVITE, может выступать в роли инициатора предложения или автора ответа. UAC, готовый выступить инициатором предложения, включает предложение в re-INVITE. UAS (пользовательский агент-сервер) затем предоставляет ответ в ответе на re-INVITE. UAC, готовый выступить автором ответа, не включает предложение в re-INVITE. UAS затем предоставляет предложение в ответе на re-INVITE, становясь, таким образом, инициатором предложения.
Certain transactions within a re-INVITE (e.g., UPDATE [RFC3311] transactions) can also have offer/answer exchanges associated to them. A UA (User Agent) can act as the offerer or the answerer in any of these transactions regardless of whether the UA was the offerer or the answerer in the umbrella re-INVITE transaction.
Некоторые транзакции в рамках re-INVITE (например, транзакции UPDATE [RFC3311]) также могут иметь связанные с ними обмены предложением/ответом. UA (пользовательский агент) может выступать инициатором предложения или автором ответа в любой из этих транзакций независимо от того, был ли UA инициатором предложения или автором ответа в объемлющей транзакции re-INVITE.
There has been some confusion among implementors regarding how a UAS should handle re-INVITEs. In particular, implementors requested clarification on which type of response a UAS should generate in different situations. In this document, we clarify these issues.
Среди разработчиков существовала некоторая путаница относительно того, как UAS должен обрабатывать re-INVITE. В частности, разработчики просили уточнить, какой тип ответа UAS должен генерировать в различных ситуациях. В настоящем документе мы уточняем эти вопросы.
Additionally, there has also been some confusion among implementors regarding target refresh requests, which include but are not limited to re-INVITEs. In this document, we also clarify the process by which remote targets are refreshed.
Кроме того, среди разработчиков также существовала некоторая путаница относительно запросов целевого обновления, которые включают, но не ограничиваются re-INVITE. В настоящем документе мы также уточняем процесс, посредством которого обновляются удалённые цели.

3. Changing the Session State during a Re-INVITE
3. Изменение состояния сессии при выполнении re-INVITE
The following sub-sections discuss how to change the state of the session during a re-INVITE transaction.
В следующих подразделах обсуждается, как изменять состояние сессии в ходе транзакции re-INVITE.
3.1. Background on Re-INVITE Handling by UASs
3.1. Предыстория обработки re-INVITE в UAS
Eventually, a UAS receiving a re-INVITE will need to generate a response to it. Some re-INVITEs can be responded to immediately because their handling does not require user interaction (e.g., changing the IP address where a media stream is received). The handling of other re-INVITEs requires user interaction (e.g., adding a video stream to an audio-only session). Therefore, these re-INVITEs cannot be responded to immediately.
В конечном счёте UAS, получивший re-INVITE, должен сгенерировать на него ответ. На некоторые re-INVITE можно ответить немедленно, поскольку их обработка не требует взаимодействия с пользователем (например, изменение IP-адреса, на который принимается медиапоток). Обработка других re-INVITE требует взаимодействия с пользователем (например, добавление видеопотока в сессию, содержащую только аудио). Поэтому на такие re-INVITE нельзя ответить немедленно.
An error response to a re-INVITE has the following semantics. As specified in Section 12.2.2 of RFC 3261 [RFC3261], if a re-INVITE is rejected, no state changes are performed. These state changes include state changes associated to the re-INVITE transaction and all other transactions within the re-INVITE (this section deals with changes to the session state; target refreshes are discussed in Section 4.2). That is, the session state is the same as before the re-INVITE was received. The example in Figure 1 illustrates this point.
Ответ с ошибкой на re-INVITE имеет следующую семантику. Как указано в разделе 12.2.2 RFC 3261 [RFC3261], если re-INVITE отклонён, никакие изменения состояния не выполняются. Эти изменения состояния включают изменения, связанные с транзакцией re-INVITE и всеми другими транзакциями в рамках re-INVITE (в этом разделе рассматриваются изменения состояния сессии; целевые обновления обсуждаются в разделе 4.2). То есть состояние сессии остаётся таким же, как до получения re-INVITE. Пример на рисунке 1 иллюстрирует это положение.

SDP1: m=audio 30000 RTP/AVP 0 SDP2: m=audio 31000 RTP/AVP 0

At a later point, the UAC sends a re-INVITE (4) in order to add a video stream to the session.
Спустя некоторое время UAC отправляет re-INVITE (4), чтобы добавить в сессию видеопоток.
SDP3: m=audio 30000 RTP/AVP 0 m=video 30002 RTP/AVP 31
SDP3: m=audio 30000 RTP/AVP 0 m=video 30002 RTP/AVP 31
The UAS is configured to automatically reject video streams. Consequently, the UAS returns an error response (5). At that point, the session parameters in use are still those resulting from the initial offer/answer exchange, which are described by SDP1 and SDP2. That is, the session state is the same as before the re-INVITE was received.
UAS настроен на автоматическое отклонение видеопотоков. Следовательно, UAS возвращает ответ с ошибкой (5). В этот момент используемые параметры сессии всё ещё те, что получены в результате начального обмена предложением/ответом, описанного в SDP1 и SDP2. То есть состояние сессии такое же, как до получения re-INVITE.

However, there are situations where a UAS wants to accept some but not all the changes requested in a re-INVITE. In these cases, the UAS generates a 200 (OK) response with a Session Description Protocol (SDP) indicating which changes were accepted and which were not. The example in Figure 2 illustrates this point.
В предыдущем примере UAS отклонил все изменения, запрошенные в re-INVITE, вернув ответ с ошибкой. Однако существуют ситуации, когда UAS хочет принять некоторые, но не все изменения, запрошенные в re-INVITE. В этих случаях UAS генерирует ответ 200 (OK) с описанием сессии (SDP), указывающим, какие изменения приняты, а какие нет. Пример на рисунке 2 иллюстрирует это положение.

3.2. Problems with Error Responses and Already Executed Changes
3.2. Проблемы ответов с ошибкой и уже выполненных изменений
Section 3.1 contains examples on how a UAS rejects all the changes requested in a re-INVITE without executing any of them by returning an error response (Figure 1), and how a UAS executes some of the changes requested in a re-INVITE and rejects some of them by returning a 2xx response (Figures 2 and 3). A UAS can accept and reject different sets of changes simultaneously (Figure 2) or at different times (Figure 3).
Раздел 3.1 содержит примеры того, как UAS отклоняет все изменения, запрошенные в re-INVITE, не выполняя ни одного из них, возвращая ответ с ошибкой (рисунок 1), и того, как UAS выполняет некоторые запрошенные в re-INVITE изменения и отклоняет некоторые из них, возвращая ответ 2xx (рисунки 2 и 3). UAS может принимать и отклонять различные наборы изменений одновременно (рисунок 2) или в разное время (рисунок 3).
The scenario that created confusion among implementors consists of a UAS that receives a re-INVITE, executes some of the changes requested in it, and then wants to reject all those already executed changes and revert to the pre-re-INVITE state. Such a UAS may consider returning an error response to the re-INVITE (the message flow would be similar to the one in Figure 1), or using an UPDATE request to revert to the pre-re-INVITE state and then returning a 2xx response to the re-INVITE (the message flow would be similar to the one in Figure 3). This section explains the problems associated with returning an error response in these circumstances. In order to avoid these problems, the UAS should use the latter option (UPDATE request plus a 2xx response). Sections 3.3 and 3.4 contain the normative statements needed to avoid these problems. The reason for not using an error response to undo already executed changes is that an error response to a re-INVITE for which changes have already been executed (e.g., as a result of UPDATE transactions or reliable provisional responses) is effectively requesting a change in the session state. However, the UAC has no means to reject that change if it is unable to execute them. That is, if the UAC is unable to revert to the pre-re-INVITE state, it will not be able to communicate this fact to the UAS.
Сценарий, вызвавший путаницу среди разработчиков, состоит в том, что UAS получает re-INVITE, выполняет некоторые запрошенные в нём изменения, а затем хочет отклонить все эти уже выполненные изменения и вернуться к состоянию до re-INVITE. Такой UAS может рассмотреть возврат ответа с ошибкой на re-INVITE (поток сообщений был бы аналогичен рисунку 1) либо использование запроса UPDATE для возврата к состоянию до re-INVITE с последующим возвратом ответа 2xx на re-INVITE (поток сообщений был бы аналогичен рисунку 3). В этом разделе объясняются проблемы, связанные с возвратом ответа с ошибкой в таких обстоятельствах. Чтобы избежать этих проблем, UAS следует использовать последний вариант (запрос UPDATE плюс ответ 2xx). Разделы 3.3 и 3.4 содержат нормативные утверждения, необходимые для предотвращения этих проблем. Причина, по которой для отмены уже выполненных изменений не используется ответ с ошибкой, состоит в том, что ответ с ошибкой на re-INVITE, изменения которого уже выполнены (например, в результате транзакций UPDATE или надёжных предварительных ответов), фактически запрашивает изменение состояния сессии. Однако UAC не имеет средств отклонить это изменение, если он не в состоянии их выполнить. То есть если UAC не может вернуться к состоянию до re-INVITE, он не сможет сообщить об этом UAS.
3.3. UAS Behavior
3.3. Поведение UAS
UASs should only return an error response to a re-INVITE if no changes to the session state have been executed since the re-INVITE was received. Such an error response indicates that no changes have been executed as a result of the re-INVITE or any other transaction within it.
UAS следует возвращать ответ с ошибкой на re-INVITE только в том случае, если с момента получения re-INVITE не было выполнено ни одного изменения состояния сессии. Такой ответ с ошибкой указывает, что в результате re-INVITE или любой другой транзакции в его рамках не было выполнено ни одного изменения.
If any of the changes requested in a re-INVITE or in any transaction within it have already been executed, the UAS SHOULD return a 2xx response.
Если какие-либо из изменений, запрошенных в re-INVITE или в любой транзакции в его рамках, уже выполнены, UAS СЛЕДУЕТ возвращать ответ 2xx.
A change to the session state is considered to have been executed if an offer/answer without preconditions [RFC4032] for the stream has completed successfully or the UA has sent or received media using the new parameters. Connection establishment messages (e.g., TCP SYN), connectivity checks (e.g., when using Interactive Connectivity Establishment (ICE) [RFC5245]), and any other messages used in the process of meeting the preconditions for a stream are not considered media.
Изменение состояния сессии считается выполненным, если успешно завершился обмен предложением/ответом без предусловий [RFC4032] для данного потока либо если UA отправил или получил медиа с использованием новых параметров. Сообщения установления соединения (например, TCP SYN), проверки связности (например, при использовании Interactive Connectivity Establishment (ICE) [RFC5245]) и любые другие сообщения, используемые в процессе выполнения предусловий для потока, не считаются медиа.
Normally, a UA receiving media can easily detect when the new parameters for the media stream are used (e.g., media is received on a new port). However, in some scenarios, the UA will have to process incoming media packets in order to detect whether they use the old or new parameters.
Обычно UA, принимающий медиа, может легко определить, когда используются новые параметры медиапотока (например, медиа принимается на новом порту). Однако в некоторых сценариях UA придётся обрабатывать входящие пакеты медиа, чтобы определить, используют ли они старые или новые параметры.
The successful completion of an offer/answer exchange without preconditions indicates that the new parameters for the media stream are already considered to be in use. The successful completion of an offer/answer exchange with preconditions means something different. The fact that all mandatory preconditions for the stream are met indicates that the new parameters for the media stream are ready to be used. However, they will not actually be used until the UAS decides to use them. During a session establishment, the UAS can wait before using the media parameters until the callee starts being alerted or until the callee accepts the session. During a session modification, the UAS can wait until its user accepts the changes to the session. When dealing with streams where the UAS sends media more or less continuously, the UAC notices that the new parameters are in use because the UAC receives media that uses the new parameters. However, this mechanism does not work with other types of streams. Therefore, it is RECOMMENDED that when a UAS decides to start using the new parameters for a stream for which all mandatory preconditions have been met, the UAS either sends media using the new parameters or sends a new offer where the precondition-related attributes for the stream have been removed. As indicated above, the successful completion of an offer/answer exchange without preconditions indicates that the new parameters for the media stream are already considered to be in use.
Успешное завершение обмена предложением/ответом без предусловий указывает на то, что новые параметры медиапотока уже считаются используемыми. Успешное завершение обмена предложением/ответом с предусловиями означает нечто иное. Тот факт, что все обязательные предусловия для потока выполнены, указывает на то, что новые параметры медиапотока готовы к использованию. Однако фактически они не будут использоваться, пока UAS не решит их использовать. Во время установления сессии UAS может подождать, прежде чем использовать параметры медиа, до тех пор, пока вызываемый абонент не начнёт получать сигнал вызова или не примет сессию. Во время изменения сессии UAS может подождать, пока его пользователь примет изменения сессии. При работе с потоками, в которых UAS отправляет медиа более или менее непрерывно, UAC замечает, что новые параметры используются, поскольку получает медиа с новыми параметрами. Однако этот механизм не работает с другими типами потоков. Поэтому РЕКОМЕНДУЕТСЯ, чтобы при решении начать использовать новые параметры для потока, все обязательные предусловия которого выполнены, UAS либо отправлял медиа с использованием новых параметров, либо отправлял новое предложение, в котором атрибуты, связанные с предусловиями для потока, удалены. Как указано выше, успешное завершение обмена предложением/ответом без предусловий указывает на то, что новые параметры медиапотока уже считаются используемыми.
3.4. UAC Behavior
3.4. Поведение UAC
A UAC that receives an error response to a re-INVITE that undoes already executed changes within the re-INVITE may be facing a legacy UAS that does not support this specification (i.e., a UAS that does not follow the guidelines in Section 3.3). There are also certain race condition situations that get both user agents out of synchronization. In order to cope with these race condition situations, a UAC that receives an error response to a re-INVITE for which changes have been already executed SHOULD generate a new re-INVITE or UPDATE request in order to make sure that both UAs have a common view of the state of the session (the UAC uses the criteria in Section 3.3 in order to decide whether or not changes have been executed for a particular stream). The purpose of this new offer/ answer exchange is to synchronize both UAs, not to request changes that the UAS may choose to reject. Therefore, session parameters in the offer/answer exchange SHOULD be as close to those in the pre-re-INVITE state as possible.
UAC, получивший ответ с ошибкой на re-INVITE, который отменяет уже выполненные изменения в рамках re-INVITE, может иметь дело с устаревшим UAS, не поддерживающим настоящую спецификацию (то есть с UAS, не следующим рекомендациям раздела 3.3). Существуют также некоторые ситуации гонки, из-за которых оба пользовательских агента выходят из синхронизации. Чтобы справиться с такими ситуациями гонки, UAC, получивший ответ с ошибкой на re-INVITE, изменения которого уже выполнены, СЛЕДУЕТ генерировать новый re-INVITE или запрос UPDATE, чтобы убедиться, что оба UA имеют общее представление о состоянии сессии (UAC использует критерии раздела 3.3, чтобы решить, выполнены ли изменения для конкретного потока). Цель этого нового обмена предложением/ответом — синхронизировать оба UA, а не запросить изменения, которые UAS может отклонить. Поэтому параметры сессии в обмене предложением/ответом СЛЕДУЕТ делать как можно более близкими к параметрам состояния до re-INVITE.
3.5. Glare Situations
3.5. Ситуации глэр
Section 4 of RFC 3264 [RFC3264] defines glare conditions as a user agent receiving an offer after having sent one but before having received an answer to it. That section specifies rules to avoid glare situations in most cases. When, despite following those rules, a glare condition occurs (as a result of a race condition), it is handled as specified in Sections 14.1 and 14.2 of RFC 3261 [RFC3261]. The UAS returns a 491 (Request Pending) response and the UAC retries the offer after a randomly selected time, which depends on which user agent is the owner of the Call-ID of the dialog. The rules in RFC 3261 [RFC3261] not only cover collisions between re-INVITEs that contain offers, they cover collisions between two re-INVITEs in general, even if they do not contain offers. Sections 5.2 and 5.3 of RFC 3311 [RFC3311] extend those rules to also cover collisions between an UPDATE request carrying an offer and another message (UPDATE, PRACK, or INVITE) also carrying an offer. The rules in RFC 3261 [RFC3261] do not cover collisions between an UPDATE request and a non-2xx final response to a re-INVITE. Since both the UPDATE request and the reliable response could be requesting changes to the session state, it would not be clear which changes would need to be executed first. However, the procedures discussed in Section 3.4 already cover this type of situation. Therefore, there is no need to specify further rules here.
Раздел 4 RFC 3264 [RFC3264] определяет условия глэр как получение пользовательским агентом предложения после того, как он отправил своё предложение, но до получения на него ответа. Этот раздел задаёт правила, позволяющие избежать ситуаций глэр в большинстве случаев. Когда, несмотря на соблюдение этих правил, возникает условие глэр (в результате гонки), оно обрабатывается, как указано в разделах 14.1 и 14.2 RFC 3261 [RFC3261]. UAS возвращает ответ 491 (Request Pending), а UAC повторяет предложение через случайно выбранное время, которое зависит от того, какой пользовательский агент является владельцем Call-ID диалога. Правила RFC 3261 [RFC3261] охватывают не только коллизии между re-INVITE, содержащими предложения, но и коллизии между двумя re-INVITE в целом, даже если они не содержат предложений. Разделы 5.2 и 5.3 RFC 3311 [RFC3311] расширяют эти правила, охватывая также коллизии между запросом UPDATE, несущим предложение, и другим сообщением (UPDATE, PRACK или INVITE), также несущим предложение. Правила RFC 3261 [RFC3261] не охватывают коллизии между запросом UPDATE и окончательным ответом, отличным от 2xx, на re-INVITE. Поскольку и запрос UPDATE, и надёжный ответ могут запрашивать изменения состояния сессии, было бы неясно, какие изменения нужно выполнить первыми. Однако процедуры, рассмотренные в разделе 3.4, уже охватывают такой тип ситуации. Поэтому нет необходимости задавать здесь дополнительные правила.

4. Refreshing a Dialog's Targets
4. Обновление целей диалога

4.1. Background and Terminology on a Dialog's Targets
4.1. Предыстория и терминология целей диалога
As described in Section 12 of RFC 3261 [RFC3261], a UA involved in a dialog keeps a record of the SIP or Session Initiation Protocol Secure (SIPS) URI at which it can communicate with a specific instance of its peer (this is called the "dialog's remote target URI" and is equal to the URI contained in the Contact header of requests and responses it receives from the peer). This document introduces the complementary concept of the "dialog's local target URI", defined as a UA's record of the SIP or SIPS URI at which the peer can communicate with it (equal to the URI contained in the Contact header of requests and responses it sends to the peer). These terms are complementary because the "dialog's remote target URI" according to one UA is the "dialog's local target URI" according to the other UA, and vice versa.
Как описано в разделе 12 RFC 3261 [RFC3261], UA, участвующий в диалоге, хранит запись об URI SIP или SIPS (Session Initiation Protocol Secure), по которому он может взаимодействовать с конкретным экземпляром своего партнёра (это называется «URI удалённой цели диалога» и равно URI, содержащемуся в заголовке Contact запросов и ответов, которые он получает от партнёра). Настоящий документ вводит дополнительное понятие «URI локальной цели диалога», определяемое как запись UA об URI SIP или SIPS, по которому партнёр может взаимодействовать с ним (равно URI, содержащемуся в заголовке Contact запросов и ответов, которые он отправляет партнёру). Эти термины дополняют друг друга, поскольку «URI удалённой цели диалога» с точки зрения одного UA является «URI локальной цели диалога» с точки зрения другого UA, и наоборот.

4.2. Предыстория запросов целевого обновления

Запрос целевого обновления, отправленный в рамках диалога, определяется как запрос, который может изменить удалённую цель диалога.
Additionally, 2xx responses to target-refresh requests can also update the remote target of the dialog. As discussed in Section 12.2 of RFC 3261 [RFC3261], re-INVITEs are target-refresh requests.
Кроме того, ответы 2xx на запросы целевого обновления также могут обновлять удалённую цель диалога. Как обсуждается в разделе 12.2 RFC 3261 [RFC3261], re-INVITE являются запросами целевого обновления.
RFC 3261 [RFC3261] specifies the behavior of UASs receiving target- refresh requests and of UACs receiving a 2xx response for a target- refresh request.
RFC 3261 [RFC3261] определяет поведение UAS, получающих запросы целевого обновления, и UAC, получающих ответ 2xx на запрос целевого обновления.

Тот факт, что re-INVITE могут быть долгоживущими транзакциями и содержать другие транзакции, делает необходимым пересмотр этих правил. 4.3. Clarification on the Atomicity of Target-Refresh Requests
4.3. Уточнение об атомарности запросов целевого обновления
The local and remote targets of a dialog are special types of state information because of their essential role in the exchange of SIP messages between UAs in a dialog. A UA involved in a dialog receives the remote target of the dialog from the remote UA. The UA uses the received remote target to send SIP requests to the remote UA.
Локальная и удалённая цели диалога — это особые виды информации о состоянии из-за их существенной роли в обмене сообщениями SIP между UA в диалоге. UA, участвующий в диалоге, получает удалённую цель диалога от удалённого UA. UA использует полученную удалённую цель для отправки запросов SIP удалённому UA.
The dialog's local target is a piece of state information that is not meant to be negotiated. When a UA changes its local target (i.e., the UA changes its IP address), the UA simply communicates its new local target to the remote UA (e.g., the UA communicates its new IP address to the remote UA in order to remain reachable by the remote UA). UAs need to follow the behavior specified in Sections 4.4, 4.5, 4.6, and 4.7 of this specification instead of that specified in RFC 3261 [RFC3261], which was discussed in Section 4.2. The new behavior regarding target-refresh requests implies that a target-refresh request can, in some cases, update the remote target even if the request is responded to with a final error response. This means that target-refresh requests are not atomic.
Локальная цель диалога — это элемент информации о состоянии, который не предназначен для согласования. Когда UA изменяет свою локальную цель (то есть UA изменяет свой IP-адрес), UA просто сообщает свою новую локальную цель удалённому UA (например, UA сообщает свой новый IP-адрес удалённому UA, чтобы оставаться доступным для удалённого UA). UA должны следовать поведению, указанному в разделах 4.4, 4.5, 4.6 и 4.7 настоящей спецификации, вместо поведения, указанного в RFC 3261 [RFC3261], которое обсуждалось в разделе 4.2. Новое поведение в отношении запросов целевого обновления означает, что запрос целевого обновления может в некоторых случаях обновлять удалённую цель, даже если на запрос отвечают окончательным ответом с ошибкой. Это означает, что запросы целевого обновления не являются атомарными.
4.4. UA Updating the Dialog's Local Target in a Request
4.4. Обновление UA локальной цели диалога в запросе
In order to update its local target, a UA can send a target-refresh request. If the UA receives an error response to the target-refresh request, the remote UA has not updated its remote target.
Чтобы обновить свою локальную цель, UA может отправить запрос целевого обновления. Если UA получает ответ с ошибкой на запрос целевого обновления, удалённый UA не обновил свою удалённую цель.
This allows UASs to authenticate target-refresh requests (see Section 26.2 of RFC 3261 [RFC3261]).
Это позволяет UAS аутентифицировать запросы целевого обновления (см. раздел 26.2 RFC 3261 [RFC3261]).
If the UA receives a reliable provisional response or a 2xx response to the target-refresh request, or the UA receives an in-dialog request on the new local target, the remote UA has updated its remote target. The UA can consider the target refresh operation completed.
Если UA получает надёжный предварительный ответ или ответ 2xx на запрос целевого обновления либо получает запрос в рамках диалога на новую локальную цель, удалённый UA обновил свою удалённую цель. UA может считать операцию целевого обновления завершённой.
Even if the target request was a re-INVITE and the final response to the re-INVITE was an error response, the UAS would not revert to the pre-re-INVITE remote target.
Даже если запрос целевого обновления был re-INVITE и окончательный ответ на re-INVITE был ответом с ошибкой, UAS не вернулся бы к удалённой цели до re-INVITE.
A UA SHOULD NOT use the same target refresh request to refresh the target and to make session changes unless the session changes can be trivially accepted by the remote UA (e.g., an IP address change). Piggybacking a target refresh with more complicated session changes would make it unnecessarily complicated for the remote UA to accept the target refresh while rejecting the session changes. Only in case the target refresh request is a re-INVITE and the UAS supports reliable provisional response or UPDATE requests, the UAC MAY piggyback session changes and a target refresh in the same re-INVITE.
UA НЕ СЛЕДУЕТ использовать один и тот же запрос целевого обновления для обновления цели и для изменения сессии, если только изменения сессии не могут быть тривиально приняты удалённым UA (например, изменение IP-адреса). Совмещение целевого обновления с более сложными изменениями сессии сделало бы для удалённого UA излишне сложным принятие целевого обновления при отклонении изменений сессии. Только в случае, если запрос целевого обновления является re-INVITE и UAS поддерживает надёжный предварительный ответ или запросы UPDATE, UAC МОЖЕТ совмещать изменения сессии и целевое обновление в одном re-INVITE.
4.5. UA Updating the Dialog's Local Target in a Response
4.5. Обновление UA локальной цели диалога в ответе
A UA processing an incoming target refresh request can update its local target by returning a reliable provisional response or a 2xx response to the target-refresh request. The response needs to contain the updated local target URI in its Contact header field. On sending the response, the UA can consider the target refresh operation completed.
UA, обрабатывающий входящий запрос целевого обновления, может обновить свою локальную цель, вернув надёжный предварительный ответ или ответ 2xx на запрос целевого обновления. Ответ должен содержать обновлённый URI локальной цели в своём поле заголовка Contact. Отправив ответ, UA может считать операцию целевого обновления завершённой.

4.6. Запрос, обновляющий удалённую цель диалога

4.8. Race Conditions and Target Refreshes
4.8. Гонки и целевые обновления
SIP provides request ordering by using the Cseq header field. That is, a UA that receives two requests at roughly the same time can know which one is newer. However, SIP does not provide ordering between responses and requests. For example, if a UA receives a 200 (OK) response to an UPDATE request and an UPDATE request at roughly the same time, the UA cannot know which one was sent last. Since both messages can refresh the remote target, the UA needs to know which message was sent last in order to know which remote target needs to be used. This document specifies the following rule to avoid the situation just described. If the protocol allows a UA to use a target-refresh request at the point in time that the UA wishes to refresh its local target, the UA MUST use a target-refresh request instead of a response to refresh its local target. This rule implies that a UA only uses a response (i.e., a reliable provisional response or a 2xx response to a target-refresh request) to refresh its local target if the UA is unable to use a target-refresh request at that point in time (e.g., the UAS of an ongoing re-INVITE without support for UPDATE).
SIP обеспечивает упорядочивание запросов с помощью поля заголовка CSeq. То есть UA, получивший два запроса примерно в одно и то же время, может узнать, какой из них новее. Однако SIP не обеспечивает упорядочивания между ответами и запросами. Например, если UA получает ответ 200 (OK) на запрос UPDATE и запрос UPDATE примерно в одно и то же время, UA не может узнать, какое из сообщений отправлено последним. Поскольку оба сообщения могут обновлять удалённую цель, UA нужно знать, какое сообщение отправлено последним, чтобы знать, какую удалённую цель нужно использовать. Настоящий документ задаёт следующее правило, чтобы избежать только что описанной ситуации. Если протокол позволяет UA использовать запрос целевого обновления в тот момент, когда UA желает обновить свою локальную цель, UA ДОЛЖЕН использовать запрос целевого обновления, а не ответ, для обновления своей локальной цели. Это правило означает, что UA использует ответ (то есть надёжный предварительный ответ или ответ 2xx на запрос целевого обновления) для обновления своей локальной цели только в том случае, если UA не может использовать запрос целевого обновления в этот момент (например, UAS в ходе продолжающегося re-INVITE без поддержки UPDATE).
4.9. Early Dialogs
4.9. Ранние диалоги
The rules given in this section about which messages can refresh the target of a dialog also apply to early dialogs created by an initial INVITE transaction. Additionally, as specified in Section 13.2.2.4 of RFC 3261 [RFC3261], on receiving a 2xx response to the initial INVITE, the UAC recomputes the whole route set of the dialog, which transitions from the "early" state to the "confirmed" state.
Правила, приведённые в этом разделе относительно того, какие сообщения могут обновлять цель диалога, также применяются к ранним диалогам, созданным начальной транзакцией INVITE. Кроме того, как указано в разделе 13.2.2.4 RFC 3261 [RFC3261], при получении ответа 2xx на начальный INVITE UAC пересчитывает весь набор маршрутов диалога, который переходит из состояния «early» в состояние «confirmed».
Section 12.1 of RFC 3261 allows unreliable provisional responses to create early dialogs. However, per the rules given in this section, unreliable provisional responses cannot refresh the target of a dialog. Therefore, the UAC of an initial INVITE transaction will not perform any target refresh as a result of the reception of an unreliable provisional response with an updated Contact value on an (already established) early dialog. Note also that a given UAS can establish additional early dialogs, which can have different targets, by returning additional unreliable provisional responses with different To tags.
Раздел 12.1 RFC 3261 допускает создание ранних диалогов ненадёжными предварительными ответами. Однако, согласно правилам, приведённым в этом разделе, ненадёжные предварительные ответы не могут обновлять цель диалога. Поэтому UAC начальной транзакции INVITE не будет выполнять никакого целевого обновления в результате получения ненадёжного предварительного ответа с обновлённым значением Contact в (уже установленном) раннем диалоге. Отметим также, что данный UAS может устанавливать дополнительные ранние диалоги, которые могут иметь другие цели, возвращая дополнительные ненадёжные предварительные ответы с различными тегами To.
5. A UA Losing Its Contact
5. UA, теряющий свой Contact
The following sections discuss the case where a UA loses its transport address during an ongoing re-INVITE transaction. Such a UA will refresh the dialog's local target so that it reflects its new transport address. Note that target refreshes that do not involve changes in the UA's transport address are outside of the scope of this section. Also, UAs losing their transport address during a non-re-INVITE transaction (e.g., a UA losing its transport address right after having sent an UPDATE request before having received a response to it) are out of scope as well.
В следующих разделах рассматривается случай, когда UA теряет свой транспортный адрес в ходе продолжающейся транзакции re-INVITE. Такой UA обновит локальную цель диалога так, чтобы она отражала его новый транспортный адрес. Отметим, что целевые обновления, не связанные с изменениями транспортного адреса UA, находятся вне рамок этого раздела. Также вне рамок находятся UA, теряющие свой транспортный адрес в ходе транзакции, не являющейся re-INVITE (например, UA, теряющий свой транспортный адрес сразу после отправки запроса UPDATE и до получения на него ответа).
The rules given in this section are also applicable to initial INVITE requests that have established early dialogs.
Правила, приведённые в этом разделе, также применимы к начальным запросам INVITE, установившим ранние диалоги.
5.1. Background on Re-INVITE Transaction Routing
5.1. Предыстория маршрутизации транзакции re-INVITE
Re-INVITEs are routed using the dialog's route set, which contains all the proxy servers that need to be traversed by requests sent within the dialog. Responses to the re-INVITE are routed using the Via entries in the re-INVITE.
re-INVITE маршрутизируются с использованием набора маршрутов диалога, который содержит все прокси-серверы, через которые должны проходить запросы, отправляемые в рамках диалога. Ответы на re-INVITE маршрутизируются с использованием записей Via в re-INVITE.
ACK requests for 2xx responses and for non-2xx final responses are generated in different ways. As specified in Sections 14.1 and 13.2.1 of RFC 3261 [RFC3261], ACK requests for 2xx responses are generated by the UAC core and are routed using the dialog's route set. As specified in Section 17.1.1.2 of RFC 3261 [RFC3261], ACK requests for non-2xx final responses are generated by the INVITE client transaction (i.e., they are generated in a hop-by-hop fashion by the proxy servers in the path) and are sent to the same transport address as the re-INVITE.
Запросы ACK для ответов 2xx и для окончательных ответов, отличных от 2xx, генерируются по-разному. Как указано в разделах 14.1 и 13.2.1 RFC 3261 [RFC3261], запросы ACK для ответов 2xx генерируются ядром UAC и маршрутизируются с использованием набора маршрутов диалога. Как указано в разделе 17.1.1.2 RFC 3261 [RFC3261], запросы ACK для окончательных ответов, отличных от 2xx, генерируются клиентской транзакцией INVITE (то есть генерируются по принципу «от узла к узлу» прокси-серверами на пути) и отправляются на тот же транспортный адрес, что и re-INVITE.
5.2. Problems with UAs Losing Their Contact
5.2. Проблемы UA, теряющих свой Contact
Refreshing the dialog's remote target during a re-INVITE transaction (see Section 4.3) presents some issues because of the fact that re-INVITE transactions can be long lived. As described in Section 5.1, the way responses to the re-INVITE and ACKs for non-2xx final responses are routed is fixed once the re-INVITE is sent. The routing of this messages does not depend on the dialog's route set and, thus, target refreshes within an ongoing re-INVITE do not affect their routing. A UA that changes its location (i.e., performs a target refresh) but is still reachable at its old location will be able to receive those messages (which will be sent to the old location). However, a UA that cannot be reachable at its old location any longer will not be able to receive them.
Обновление удалённой цели диалога в ходе транзакции re-INVITE (см. раздел 4.3) создаёт некоторые проблемы из-за того, что транзакции re-INVITE могут быть долгоживущими. Как описано в разделе 5.1, способ маршрутизации ответов на re-INVITE и ACK для окончательных ответов, отличных от 2xx, фиксируется после отправки re-INVITE. Маршрутизация этих сообщений не зависит от набора маршрутов диалога, и, таким образом, целевые обновления в ходе продолжающегося re-INVITE не влияют на их маршрутизацию. UA, который изменяет своё местоположение (то есть выполняет целевое обновление), но всё ещё доступен по старому местоположению, сможет получать эти сообщения (которые будут отправлены на старое местоположение). Однако UA, который больше не может быть доступен по старому местоположению, не сможет их получать.
The following sections describe the errors UAs face when they lose their transport address during a re-INVITE. On detecting some of these errors, UAs following the rules specified in RFC 3261 [RFC3261] will terminate the dialog. When the dialog is terminated, the only option for the UAs is to establish a new dialog. The following sections change the requirements RFC 3261 [RFC3261] places on UAs when certain errors occur so that the UAs can recover from those errors. In short, the UAs generate a new re-INVITE transaction to synchronize both UAs. Note that there are existing UA implementations deployed that already implement this behavior.
В следующих разделах описаны ошибки, с которыми сталкиваются UA, теряющие свой транспортный адрес во время re-INVITE. При обнаружении некоторых из этих ошибок UA, следующие правилам RFC 3261 [RFC3261], завершают диалог. Когда диалог завершён, единственный вариант для UA — установить новый диалог. В следующих разделах изменяются требования, которые RFC 3261 [RFC3261] предъявляет к UA при возникновении некоторых ошибок, чтобы UA могли восстанавливаться после этих ошибок. Короче говоря, UA генерируют новую транзакцию re-INVITE для синхронизации обоих UA. Отметим, что существуют уже развёрнутые реализации UA, которые уже реализуют такое поведение.
5.3. UAS Losing Its Contact: UAC Behavior
5.3. UAS теряет свой Contact: поведение UAC
When a UAS that moves to a new contact and loses its old contact generates a non-2xx final response to the re-INVITE, it will not be able to receive the ACK request. The entity receiving the response and, thus, generating the ACK request will either get a transport error or a timeout error, which, as described in Section 8.1.3.1 of RFC 3261 [RFC3261], will be treated as a 503 (Service Unavailable) response and as a 408 (Request Timeout) response, respectively. If the sender of the ACK request is a proxy server, it will typically ignore this error. If the sender of the ACK request is the UAC, according to Section 12.2.1.2 of RFC 3261 [RFC3261], it is supposed to (at the SHOULD level) terminate the dialog by sending a BYE request. However, because of the special properties of ACK requests for non-2xx final responses, most existing UACs do not terminate the dialog when ACK request fails, which is fortunate.
Когда UAS, который переходит на новый Contact и теряет старый, генерирует окончательный ответ, отличный от 2xx, на re-INVITE, он не сможет получить запрос ACK. Объект, получающий ответ и, таким образом, генерирующий запрос ACK, получит либо ошибку транспорта, либо ошибку тайм-аута, которые, как описано в разделе 8.1.3.1 RFC 3261 [RFC3261], будут рассматриваться как ответ 503 (Service Unavailable) и ответ 408 (Request Timeout) соответственно. Если отправителем запроса ACK является прокси-сервер, он, как правило, проигнорирует эту ошибку. Если отправителем запроса ACK является UAC, то согласно разделу 12.2.1.2 RFC 3261 [RFC3261] он должен (на уровне SHOULD) завершить диалог, отправив запрос BYE. Однако из-за особых свойств запросов ACK для окончательных ответов, отличных от 2xx, большинство существующих UAC не завершают диалог при неудаче запроса ACK, что является удачным обстоятельством.
A UAC that accepts a target refresh within a re-INVITE MUST ignore transport and timeout errors when generating an ACK request for a non-2xx final response. Additionally, UAC SHOULD generate a new re-INVITE in order to make sure that both UAs have a common view of the state of the session.
UAC, принимающий целевое обновление в рамках re-INVITE, ДОЛЖЕН игнорировать ошибки транспорта и тайм-аута при генерации запроса ACK для окончательного ответа, отличного от 2xx. Кроме того, UAC СЛЕДУЕТ генерировать новый re-INVITE, чтобы убедиться, что оба UA имеют общее представление о состоянии сессии.
It is possible that the errors ignored by the UAC were not related to the target refresh operation. If that was the case, the second re-INVITE would fail and the UAC would terminate the dialog because, per the rules above, UACs only ignore errors when they accept a target refresh within the re-INVITE.
Возможно, что ошибки, проигнорированные UAC, не были связаны с операцией целевого обновления. В этом случае второй re-INVITE завершился бы неудачей, и UAC завершил бы диалог, поскольку, согласно приведённым выше правилам, UAC игнорируют ошибки только тогда, когда они принимают целевое обновление в рамках re-INVITE.
5.4. UAC Losing Its Contact: UAS Behavior
5.4. UAC теряет свой Contact: поведение UAS
When a UAC moves to a new contact and loses its old contact, it will not be able to receive responses to the re-INVITE. Consequently, it will never generate an ACK request.
Когда UAC переходит на новый Contact и теряет старый, он не сможет получать ответы на re-INVITE. Следовательно, он никогда не сгенерирует запрос ACK.
As described in Section 16.9 of RFC 3261 [RFC3261], a proxy server that gets an error when forwarding a response does not take any measures. Consequently, proxy servers relaying responses will effectively ignore the error.
Как описано в разделе 16.9 RFC 3261 [RFC3261], прокси-сервер, получающий ошибку при пересылке ответа, не принимает никаких мер. Следовательно, прокси-серверы, ретранслирующие ответы, фактически игнорируют ошибку.
If there are no proxy servers in the dialog's route set, the UAS will get an error when sending a non-2xx final response. The UAS core will be notified of the transaction failure, as described in Section 17.2.1 of RFC 3261 [RFC3261]. Most existing UASs do not terminate the dialog on encountering this failure, which is fortunate.
Если в наборе маршрутов диалога нет прокси-серверов, UAS получит ошибку при отправке окончательного ответа, отличного от 2xx. Ядро UAS узнает о сбое транзакции, как описано в разделе 17.2.1 RFC 3261 [RFC3261]. Большинство существующих UAS не завершают диалог при возникновении этого сбоя, что является удачным обстоятельством.
Regardless of the presence or absence of proxy servers in the dialog's route set, a UAS generating a 2xx response to the re-INVITE will never receive an ACK request for it. According to Section 14.2 of RFC 3261 [RFC3261], such a UAS is supposed to (at the "should" level) terminate the dialog by sending a BYE request. A UAS that accepts a target refresh within a re-INVITE and never receives an ACK request after having sent a final response to the re-INVITE SHOULD NOT terminate the dialog if the UA has received a new re-INVITE with a higher CSeq sequence number than the original one.
Независимо от наличия или отсутствия прокси-серверов в наборе маршрутов диалога, UAS, генерирующий ответ 2xx на re-INVITE, никогда не получит на него запрос ACK. Согласно разделу 14.2 RFC 3261 [RFC3261], такой UAS должен (на уровне «should») завершить диалог, отправив запрос BYE. UAS, принимающий целевое обновление в рамках re-INVITE и никогда не получающий запрос ACK после отправки окончательного ответа на re-INVITE, НЕ СЛЕДУЕТ завершать диалог, если UA получил новый re-INVITE с большим номером последовательности CSeq, чем исходный.
5.5. UAC Losing Its Contact: UAC Behavior
5.5. UAC теряет свой Contact: поведение UAC
When a UAC moves to a new contact and loses its old contact, it will not be able to receive responses to the re-INVITE. Consequently, it will never generate an ACK request.
Когда UAC переходит на новый Contact и теряет старый, он не сможет получать ответы на re-INVITE. Следовательно, он никогда не сгенерирует запрос ACK.
Such a UAC SHOULD generate a CANCEL request to cancel the re-INVITE and cause the INVITE client transaction corresponding to the re-INVITE to enter the "Terminated" state. The UAC SHOULD also send a new re-INVITE in order to make sure that both UAs have a common view of the state of the session.
Такому UAC СЛЕДУЕТ генерировать запрос CANCEL, чтобы отменить re-INVITE и заставить клиентскую транзакцию INVITE, соответствующую re-INVITE, перейти в состояние «Terminated». UAC также СЛЕДУЕТ отправить новый re-INVITE, чтобы убедиться, что оба UA имеют общее представление о состоянии сессии.
Per Section 14.2 of RFC 3261 [RFC3261], the UAS will accept new incoming re-INVITEs as soon as it has generated a final response to the previous INVITE request, which had a lower CSeq sequence number.
Согласно разделу 14.2 RFC 3261 [RFC3261], UAS примет новые входящие re-INVITE, как только сгенерирует окончательный ответ на предыдущий запрос INVITE, который имел меньший номер последовательности CSeq.
6. Security Considerations
6. Соображения безопасности
This document does not introduce any new security issue. It just clarifies how certain transactions should be handled in SIP. Security issues related to re-INVITEs and UPDATE requests are discussed in RFC 3261 [RFC3261] and RFC 3311 [RFC3311].
Настоящий документ не вводит никаких новых проблем безопасности. Он лишь уточняет, как следует обрабатывать некоторые транзакции в SIP. Вопросы безопасности, связанные с re-INVITE и запросами UPDATE, рассматриваются в RFC 3261 [RFC3261] и RFC 3311 [RFC3311].
In particular, in order not to reduce the security level for a given session, re-INVITEs and UPDATE requests SHOULD be secured using a mechanism equivalent to or stronger than the initial INVITE request that created the session. For example, if the initial INVITE request was end-to-end integrity protected or encrypted, subsequent re-INVITEs and UPDATE requests should also be so.
В частности, чтобы не снижать уровень безопасности данной сессии, re-INVITE и запросы UPDATE СЛЕДУЕТ защищать с помощью механизма, эквивалентного или более стойкого, чем механизм защиты начального запроса INVITE, создавшего сессию. Например, если начальный запрос INVITE был защищён сквозной проверкой целостности или зашифрован, последующие re-INVITE и запросы UPDATE также должны быть такими.
