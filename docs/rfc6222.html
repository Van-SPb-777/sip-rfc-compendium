Guidelines for Choosing RTP Control Protocol (RTCP) Canonical Names (CNAMEs)
Рекомендации по выбору канонических имён (CNAME) протокола управления RTP
Abstract
Аннотация
The RTP Control Protocol (RTCP) Canonical Name (CNAME) is a persistent transport-level identifier for an RTP endpoint. While the Synchronization Source (SSRC) identifier of an RTP endpoint may change if a collision is detected or when the RTP application is restarted, its RTCP CNAME is meant to stay unchanged, so that RTP endpoints can be uniquely identified and associated with their RTP media streams. For proper functionality, RTCP CNAMEs should be unique within the participants of an RTP session. However, the existing guidelines for choosing the RTCP CNAME provided in the RTP standard are insufficient to achieve this uniqueness. This memo updates those guidelines to allow endpoints to choose unique RTCP CNAMEs.
Каноническое имя (CNAME) протокола управления RTP (RTCP) — это постоянный идентификатор транспортного уровня для конечной точки RTP. Хотя идентификатор источника синхронизации (SSRC) конечной точки RTP может меняться при обнаружении коллизии или при перезапуске приложения RTP, её CNAME RTCP должен оставаться неизменным, чтобы конечные точки RTP можно было однозначно идентифицировать и связывать с их медиапотоками RTP. Для правильного функционирования имена CNAME RTCP должны быть уникальны среди участников сеанса RTP. Однако существующие рекомендации по выбору CNAME RTCP, приведённые в стандарте RTP, недостаточны для достижения такой уникальности. Настоящий меморандум обновляет эти рекомендации, чтобы конечные точки могли выбирать уникальные имена CNAME RTCP.

1. Introduction
1. Введение
In Section 6.5.1 of the RTP specification, [RFC3550], there are a number of recommendations for choosing a unique RTCP CNAME for an RTP endpoint. However, in practice, some of these methods are not guaranteed to produce a unique RTCP CNAME. This memo updates guidelines for choosing RTCP CNAMEs, superseding those presented in Section 6.5.1 of [RFC3550].
В разделе 6.5.1 спецификации RTP [RFC3550] приведён ряд рекомендаций по выбору уникального CNAME RTCP для конечной точки RTP. Однако на практике некоторые из этих методов не гарантируют получения уникального CNAME RTCP. Настоящий меморандум обновляет рекомендации по выбору имён CNAME RTCP, заменяя приведённые в разделе 6.5.1 документа [RFC3550].

2. Нотация требований

3. Deficiencies with Earlier Guidelines for Choosing an RTCP CNAME
3. Недостатки прежних рекомендаций по выбору RTCP CNAME
The recommendation in [RFC3550] is to generate an RTCP CNAME of the form "user@host" for multiuser systems, or "host" if the username is not available. The "host" part is specified to be the fully qualified domain name (FQDN) of the host from which the real-time data originates. While this guidance was appropriate at the time [RFC3550] was written, FQDNs are no longer necessarily unique and can sometimes be common across several endpoints in large service provider networks. This document replaces the use of FQDN as an RTCP CNAME by alternative mechanisms.
В [RFC3550] рекомендуется генерировать CNAME RTCP вида «user@host» для многопользовательских систем или «host», если имя пользователя недоступно. Часть «host» должна представлять собой полное доменное имя (FQDN) узла, на котором создаются данные реального времени. Хотя такая рекомендация была уместна во время написания [RFC3550], полные доменные имена уже не обязательно уникальны и иногда могут совпадать у нескольких конечных точек в крупных сетях операторов связи. Настоящий документ заменяет использование FQDN в качестве CNAME RTCP альтернативными механизмами.
IPv4 addresses are also suggested for use in RTCP CNAMEs in [RFC3550], where the "host" part of the RTCP CNAME is the numeric representation of the IPv4 address of the interface from which the RTP data originates. As noted in [RFC3550], the use of private network address space [RFC1918] can result in hosts having network addresses that are not globally unique. Additionally, this shared use of the same IPv4 address can also occur with public IPv4 addresses if multiple hosts are assigned the same public IPv4 address and connected to a Network Address Translation (NAT) device [RFC3022]. When multiple hosts share the same IPv4 address, whether private or public, using the IPv4 address as the RTCP CNAME leads to RTCP CNAMEs that are not necessarily unique.
В [RFC3550] для использования в именах CNAME RTCP также предлагаются адреса IPv4, где часть «host» имени CNAME RTCP представляет собой числовое представление адреса IPv4 того интерфейса, с которого исходят данные RTP. Как отмечено в [RFC3550], использование пространства частных сетевых адресов [RFC1918] может привести к тому, что узлы будут иметь сетевые адреса, не являющиеся глобально уникальными. Кроме того, такое совместное использование одного и того же адреса IPv4 может происходить и с публичными адресами IPv4, если нескольким узлам назначен один и тот же публичный адрес IPv4 и они подключены к устройству преобразования сетевых адресов (NAT) [RFC3022]. Когда несколько узлов совместно используют один и тот же адрес IPv4, частный или публичный, использование адреса IPv4 в качестве CNAME RTCP приводит к именам CNAME RTCP, которые не обязательно уникальны.
It is also noted in [RFC3550] that if hosts with private addresses and no direct IP connectivity to the public Internet have their RTP packets forwarded to the public Internet through an RTP-level translator, they could end up having non-unique RTCP CNAMEs. The suggestion in [RFC3550] is that such applications provide a configuration option to allow the user to choose a unique RTCP CNAME; this technique puts the burden on the translator to translate RTCP CNAMEs from private addresses to public addresses if necessary to keep private addresses from being exposed. Experience has shown that this does not work well in practice.
В [RFC3550] также отмечено, что если узлы с частными адресами и без прямого IP-подключения к публичному Интернету передают свои пакеты RTP в публичный Интернет через транслятор уровня RTP, они могут получить неуникальные имена CNAME RTCP. В [RFC3550] предлагается, чтобы такие приложения предоставляли параметр конфигурации, позволяющий пользователю выбрать уникальное CNAME RTCP; этот способ перекладывает на транслятор задачу преобразования имён CNAME RTCP из частных адресов в публичные, если это необходимо, чтобы не раскрывать частные адреса. Опыт показал, что на практике это работает плохо.
4. Choosing an RTCP CNAME
4. Выбор имени CNAME RTCP
It is difficult, and in some cases impossible, for a host to determine if there is a NAT between itself and its RTP peer. Furthermore, even some public IPv4 addresses can be shared by multiple hosts in the Internet. Using the numeric representation of the IPv4 address as the "host" part of the RTCP CNAME is NOT RECOMMENDED.
Узлу трудно, а в некоторых случаях невозможно определить, есть ли между ним и его партнёром по RTP устройство NAT. Кроме того, даже некоторые публичные адреса IPv4 могут совместно использоваться несколькими узлами в Интернете. Использование числового представления адреса IPv4 в качестве части «host» имени CNAME RTCP НЕ РЕКОМЕНДУЕТСЯ.
4.1. Persistent RTCP CNAMEs versus Per-Session RTCP CNAMEs
4.1. Постоянные имена CNAME RTCP в сравнении с посеансными
The RTCP CNAME can be either persistent across different RTP sessions for an RTP endpoint or unique per session, meaning that an RTP endpoint chooses a different RTCP CNAME for each RTP session.
CNAME RTCP может либо сохраняться при переходе между разными сеансами RTP для одной конечной точки RTP, либо быть уникальным для каждого сеанса, то есть конечная точка RTP выбирает другое CNAME RTCP для каждого сеанса RTP.
An RTP endpoint that is emitting multiple related RTP streams that require synchronization at the other endpoint(s) MUST use the same RTCP CNAME for all streams that are to be synchronized. This requires a short-term persistent RTCP CNAME that is common across several RTP streams, and potentially across several related RTP sessions. A common example of such use occurs when lip-syncing audio and video streams in a multimedia session, where a single participant has to use the same RTCP CNAME for its audio RTP session and for its video RTP session. Another example might be to synchronize the layers of a layered audio codec, where the same RTCP CNAME has to be used for each layer.
Конечная точка RTP, передающая несколько связанных потоков RTP, которые должны синхронизироваться на другой конечной точке (других конечных точках), ДОЛЖНА использовать одно и то же CNAME RTCP для всех потоков, подлежащих синхронизации. Для этого требуется кратковременно постоянное CNAME RTCP, общее для нескольких потоков RTP и, возможно, для нескольких связанных сеансов RTP. Типичный пример такого использования — синхронизация аудио и видео в мультимедийном сеансе, когда одному участнику нужно использовать одно и то же CNAME RTCP для своего аудиосеанса RTP и для своего видеосеанса RTP. Другим примером может быть синхронизация слоёв многослойного аудиокодека, когда для каждого слоя нужно использовать одно и то же CNAME RTCP.
A longer-term persistent RTCP CNAME is sometimes useful to facilitate third-party monitoring, consistent with [RFC3550]. One such use might be to allow network management tools to correlate the ongoing quality of service for a participant across multiple RTP sessions for fault diagnosis, and to understand long-term network performance statistics. An implementation that wishes to discourage this type of third-party monitoring can generate a unique RTCP CNAME for each RTP session, or group of related RTP sessions, that it joins. Such a per-session RTCP CNAME cannot be used for traffic analysis, and so provides some limited form of privacy (note that there are non-RTP means that can be used by a third party to correlate RTP sessions, so the use of per-session RTCP CNAMEs will not prevent a determined traffic analyst from monitoring such sessions).
Более долговременно постоянное CNAME RTCP иногда полезно для облегчения мониторинга третьей стороной, что согласуется с [RFC3550]. Один из вариантов такого использования — позволить средствам управления сетью сопоставлять текущее качество обслуживания участника в нескольких сеансах RTP для диагностики неисправностей и понимать долгосрочную статистику производительности сети. Реализация, которая хочет воспрепятствовать такому мониторингу третьей стороной, может генерировать уникальное CNAME RTCP для каждого сеанса RTP или группы связанных сеансов RTP, к которым она присоединяется. Такое посеансное CNAME RTCP не может использоваться для анализа трафика и потому обеспечивает некоторую ограниченную форму приватности (отметим, что существуют не связанные с RTP средства, с помощью которых третья сторона может сопоставлять сеансы RTP, поэтому использование посеансных имён CNAME RTCP не помешает целеустремлённому аналитику трафика вести мониторинг таких сеансов).
This memo defines several different ways by which an implementation can choose an RTCP CNAME. It is possible, and legitimate, for independent implementations to make different choices of RTCP CNAME when running on the same host. This can hinder third-party monitoring, unless some external means is provided to configure a persistent choice of RTCP CNAME for those implementations.
Настоящий меморандум определяет несколько различных способов, которыми реализация может выбрать CNAME RTCP. Независимые реализации могут, и это законно, делать разный выбор CNAME RTCP при работе на одном и том же узле. Это может затруднить мониторинг третьей стороной, если не предусмотрено какое-либо внешнее средство для настройки постоянного выбора CNAME RTCP для таких реализаций.
Note that there is no backwards compatibility issue (with [RFC3550]- compatible implementations) introduced in this memo, since the RTCP CNAMEs are opaque strings to remote peers.
Отметим, что настоящий меморандум не создаёт проблемы обратной совместимости (с реализациями, совместимыми с [RFC3550]), поскольку имена CNAME RTCP являются для удалённых партнёров непрозрачными строками.
4.2. Requirements
4.2. Требования
RTP endpoints will choose to generate RTCP CNAMEs that are persistent or per-session. An RTP endpoint that wishes to generate a persistent RTCP CNAME MUST use one of the following two methods:
Конечные точки RTP будут выбирать генерацию постоянных или посеансных имён CNAME RTCP. Конечная точка RTP, желающая генерировать постоянное CNAME RTCP, ДОЛЖНА использовать один из следующих двух методов:
o To produce a long-term persistent RTCP CNAME, an RTP endpoint MUST generate and store a Universally Unique IDentifier (UUID) [RFC4122] for use as the "host" part of its RTCP CNAME. The UUID MUST be version 1, 2, or 4, as described in [RFC4122], with the "urn:uuid:" stripped, resulting in a 36-octet printable string representation.
o Чтобы получить долговременно постоянное CNAME RTCP, конечная точка RTP ДОЛЖНА сгенерировать и сохранить универсально уникальный идентификатор (UUID) [RFC4122] для использования в качестве части «host» своего CNAME RTCP. UUID ДОЛЖЕН быть версии 1, 2 или 4, как описано в [RFC4122], с удалённым префиксом «urn:uuid:», что даёт 36-октетное печатное строковое представление.
o To produce a short-term persistent RTCP CNAME, an RTP endpoint MUST either (a) use the numeric representation of the layer-2 (Media Access Control (MAC)) address of the interface that is used to initiate the RTP session as the "host" part of its RTCP CNAME or (b) generate and use an identifier by following the procedure described in Section 5. In either case, the procedure is performed once per initialization of the software. After obtaining an identifier by doing (a) or (b), the least significant 48 bits are converted to the standard colon-separated hexadecimal format [RFC5342], e.g., "00:23:32:af:9b:aa", resulting in a 17-octet printable string representation.
o Чтобы получить кратковременно постоянное CNAME RTCP, конечная точка RTP ДОЛЖНА либо (a) использовать числовое представление адреса уровня 2 (MAC-адреса, Media Access Control) интерфейса, используемого для инициирования сеанса RTP, в качестве части «host» своего CNAME RTCP, либо (b) сгенерировать и использовать идентификатор, следуя процедуре, описанной в разделе 5. В любом случае процедура выполняется один раз при каждой инициализации программного обеспечения. После получения идентификатора способом (a) или (b) младшие 48 бит преобразуются в стандартный шестнадцатеричный формат с двоеточиями [RFC5342], например «00:23:32:af:9b:aa», что даёт 17-октетное печатное строковое представление.
In the two cases above, the "user@" part of the RTCP CNAME MAY be omitted on single-user systems and MAY be replaced by an opaque token on multi-user systems, to preserve privacy.
В двух случаях выше часть «user@» имени CNAME RTCP МОЖЕТ быть опущена в системах с одним пользователем и МОЖЕТ быть заменена непрозрачным токеном в системах с несколькими пользователями в целях сохранения приватности.
An RTP endpoint that wishes to generate a per-session RTCP CNAME MUST use the following method:
Конечная точка RTP, желающая генерировать посеансное CNAME RTCP, ДОЛЖНА использовать следующий метод:
o For every new RTP session, a new CNAME is generated following the procedure described in Section 5. After performing that procedure, the least significant 96 bits are used to generate an identifier (to compromise between packet size and security), which is converted to ASCII using Base64 encoding [RFC4648]. This results in a 16-octet string representation. The RTCP CNAME cannot change over the life of an RTP session [RFC3550]; hence, only the initial SSRC value chosen by the endpoint is used. The "user@" part of the RTCP CNAME is omitted when generating per-session RTCP CNAMEs.
o Для каждого нового сеанса RTP новое CNAME генерируется согласно процедуре, описанной в разделе 5. После выполнения этой процедуры младшие 96 бит используются для формирования идентификатора (в качестве компромисса между размером пакета и безопасностью), который преобразуется в ASCII с помощью кодирования Base64 [RFC4648]. В результате получается 16-октетное строковое представление. CNAME RTCP не может изменяться в течение жизни сеанса RTP [RFC3550]; поэтому используется только начальное значение SSRC, выбранное конечной точкой. Часть «user@» имени CNAME RTCP опускается при генерации посеансных имён CNAME RTCP.
It is believed that obtaining uniqueness (with a high probability) is an important property that requires careful evaluation of the method. This document provides a number of methods, at least one of which would be suitable for all deployment scenarios. This document therefore does not provide for the implementor to define and select an alternative method.
Считается, что получение уникальности (с высокой вероятностью) является важным свойством, требующим тщательной оценки метода. Настоящий документ предоставляет несколько методов, по крайней мере один из которых подойдёт для всех сценариев развёртывания. Поэтому настоящий документ не предусматривает, чтобы разработчик определял и выбирал альтернативный метод.
A future specification might define an alternative method for generating RTCP CNAMEs, as long as the proposed method has appropriate uniqueness and there is consistency between the methods used for multiple RTP sessions that are to be correlated. However, such a specification needs to be reviewed and approved before deployment.
Будущая спецификация может определить альтернативный метод генерации имён CNAME RTCP при условии, что предлагаемый метод обладает надлежащей уникальностью и существует согласованность между методами, используемыми для нескольких сеансов RTP, которые должны быть сопоставлены. Однако такая спецификация должна быть рассмотрена и одобрена до развёртывания.
The mechanisms described in this document are to be used to generate RTCP CNAMEs, and they are not to be used for generating general- purpose unique identifiers.
Описанные в настоящем документе механизмы должны использоваться для генерации имён CNAME RTCP и не должны использоваться для генерации универсальных уникальных идентификаторов.
5. Procedure to Generate a Unique Identifier
5. Процедура генерации уникального идентификатора
The algorithm described below is intended to be used for locally generated unique identifiers.
Описанный ниже алгоритм предназначен для локальной генерации уникальных идентификаторов.
1. Obtain the current time of day in 64-bit NTP format [RFC5905].
1. Получить текущее время суток в 64-битном формате NTP [RFC5905].
2. Obtain a modified EUI-64 identifier from the system running this algorithm [RFC4291]. If such a system does not exist, an identifier can be created from a 48-bit MAC address, as specified in [RFC4291]. If one cannot be obtained or created, a suitably unique identifier, local to the node, should be used (e.g., system serial number).
2. Получить модифицированный идентификатор EUI-64 от системы, выполняющей этот алгоритм [RFC4291]. Если такой системы нет, идентификатор можно создать из 48-битного MAC-адреса, как указано в [RFC4291]. Если получить или создать его невозможно, следует использовать подходящий уникальный идентификатор, локальный для узла (например, серийный номер системы).
3. Concatenate the time of day with the system-specific identifier in order to create a key.
3. Выполнить конкатенацию времени суток с системным идентификатором, чтобы создать ключ.
4. If generating a per-session CNAME, also concatenate the RTP endpoint's initial SSRC, the source and destination IP addresses, and ports to the key.
4. Если генерируется посеансное CNAME, к ключу также добавляются начальное значение SSRC конечной точки RTP, исходный и целевой IP-адреса и порты.
5. Compute the 256-bit output of the SHA-256 digest of the key, as specified in [RFC4634].
5. Вычислить 256-битный результат дайджеста SHA-256 от ключа, как указано в [RFC4634].
6. Security Considerations
6. Вопросы безопасности
The security considerations of [RFC3550] apply to this memo.
Вопросы безопасности [RFC3550] применимы к настоящему меморандуму.
6.1. Considerations on Uniqueness of RTCP CNAMEs
6.1. Соображения об уникальности имён CNAME RTCP
The recommendations given in this document for RTCP CNAME generation ensure that a set of cooperating participants in an RTP session will, with very high probability, have unique RTCP CNAMEs. However, neither [RFC3550] nor this document provides any way to ensure that participants will choose RTCP CNAMEs appropriately, and thus implementations MUST NOT rely on the uniqueness of CNAMEs for any essential security services. This is consistent with [RFC3550], which does not require that RTCP CNAMEs are unique within a session but instead says that condition SHOULD hold. As described in the Security Considerations section of [RFC3550], because each participant in a session is free to choose its own RTCP CNAME, they can do so in such a way as to impersonate another participant. That is, participants are trusted to not impersonate each other. No recommendation for generating RTCP CNAMEs can prevent this impersonation, because an attacker can neglect the stipulation. Secure RTP (SRTP) [RFC3711] keeps unauthorized entities out of an RTP session, but it does not aim to prevent impersonation attacks from unauthorized entities.
Рекомендации по генерации имён CNAME RTCP, приведённые в настоящем документе, гарантируют, что набор взаимодействующих участников сеанса RTP будет с очень высокой вероятностью иметь уникальные имена CNAME RTCP. Однако ни [RFC3550], ни настоящий документ не предоставляют способа гарантировать, что участники выберут имена CNAME RTCP надлежащим образом, поэтому реализации НЕ ДОЛЖНЫ полагаться на уникальность имён CNAME для каких-либо существенных служб безопасности. Это согласуется с [RFC3550], который не требует, чтобы имена CNAME RTCP были уникальны в пределах сеанса, а вместо этого говорит, что это условие ДОЛЖНО выполняться. Как описано в разделе вопросов безопасности [RFC3550], поскольку каждый участник сеанса свободен выбирать своё собственное CNAME RTCP, он может сделать это так, чтобы выдать себя за другого участника. То есть предполагается, что участники доверяют друг другу и не выдают себя друг за друга. Никакая рекомендация по генерации имён CNAME RTCP не может предотвратить такую подмену, поскольку злоумышленник может пренебречь этим условием. Защищённый RTP (SRTP) [RFC3711] не допускает неавторизованных субъектов в сеанс RTP, но не ставит целью предотвращение атак подмены со стороны неавторизованных субъектов.
This document uses a hash function to ensure the uniqueness of RTCP CNAMEs. A cryptographic hash function is used because such functions provide the randomness properties that are needed. However, no security assumptions are made on the hash function. The hash function is not assumed to be collision resistant, preimage resistant, or second preimage resistant in an adversarial setting; as described above, an attacker attempting an impersonation attack could merely set the RTCP CNAME directly rather than attacking the hash function. Similarly, the hash function is not assumed to be a one- way function or pseudorandom in a cryptographic sense.
В настоящем документе для обеспечения уникальности имён CNAME RTCP используется хеш-функция. Применяется криптографическая хеш-функция, поскольку такие функции обеспечивают необходимые свойства случайности. Однако никаких предположений о безопасности хеш-функции не делается. Не предполагается, что хеш-функция устойчива к коллизиям, устойчива к прообразу или устойчива ко второму прообразу в условиях противодействия; как описано выше, злоумышленник, пытающийся осуществить атаку подмены, мог бы просто напрямую задать CNAME RTCP, а не атаковать хеш-функцию. Аналогично не предполагается, что хеш-функция является односторонней функцией или псевдослучайной в криптографическом смысле.
No confidentiality is provided on the data used as input to the RTCP CNAME generation algorithm. It might be possible for an attacker who observes an RTCP CNAME to determine the inputs that were used to generate that value.
Конфиденциальность данных, используемых в качестве входа для алгоритма генерации CNAME RTCP, не обеспечивается. Вполне возможно, что злоумышленник, наблюдающий CNAME RTCP, сможет определить входные данные, использованные для генерации этого значения.
6.2. Session Correlation Based on RTCP CNAMEs
6.2. Корреляция сеансов на основе имён CNAME RTCP
In some environments, notably telephony, a fixed RTCP CNAME value allows separate RTP sessions to be correlated and eliminates the obfuscation provided by IPv6 privacy addresses [RFC4941] or IPv4 Network Address Port Translation (NAPT) [RFC3022]. SRTP [RFC3711] can help prevent such correlation by encrypting Secure RTCP (SRTCP), but it should be noted that SRTP only mandates SRTCP integrity protection (not encryption). Thus, RTP applications used in such environments should consider encrypting their SRTCP or generate a per-session RTCP CNAME as discussed in Section 4.1.
В некоторых средах, в частности в телефонии, фиксированное значение CNAME RTCP позволяет сопоставлять отдельные сеансы RTP и устраняет сокрытие, обеспечиваемое адресами конфиденциальности IPv6 [RFC4941] или преобразованием сетевых адресов и портов IPv4 (NAPT) [RFC3022]. SRTP [RFC3711] может помочь предотвратить такую корреляцию, шифруя защищённый RTCP (SRTCP), но следует отметить, что SRTP требует только защиты целостности SRTCP (а не шифрования). Таким образом, приложения RTP, используемые в таких средах, должны рассмотреть возможность шифрования своего SRTCP или генерации посеансного CNAME RTCP, как обсуждалось в разделе 4.1.
