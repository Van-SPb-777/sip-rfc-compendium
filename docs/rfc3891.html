Abstract
Аннотация
This document defines a new header for use with Session Initiation Protocol (SIP) multi-party applications and call control. The Replaces header is used to logically replace an existing SIP dialog with a new SIP dialog. This primitive can be used to enable a variety of features, for example: "Attended Transfer" and "Call Pickup". Note that the definition of these example features is non- normative.
Настоящий документ определяет новый заголовок для использования в многопользовательских приложениях протокола инициирования сессий (SIP) и управлении вызовами. Заголовок Replaces используется для логической замены существующего диалога SIP новым диалогом SIP. Этот примитив может использоваться для поддержки различных функций, например: «Attended Transfer» (перевод с консультацией) и «Call Pickup» (перехват вызова). Обратите внимание, что определения этих примерных функций не являются нормативными.
1. Overview
1. Обзор
This document describes a SIP [1] extension header field as part of the SIP multiparty applications architecture framework [10]. The Replaces header is used to logically replace an existing SIP dialog with a new SIP dialog. This is especially useful in peer-to-peer call control environments.
Настоящий документ описывает расширение поля заголовка SIP [1] в рамках архитектурной концепции многопартийных приложений SIP [10]. Заголовок Replaces используется для логической замены существующего диалога SIP новым диалогом SIP. Это особенно полезно в средах управления вызовами «равный с равным».
One use of the "Replaces" header is to replace one participant with another in a multimedia conversation. While this functionality is already available using 3rd party call control [11] style call control, the 3pcc model requires a central point of control which may not be desirable in many environments. As such, a method of performing these same call control primitives in a distributed, peer-to-peer fashion is very desirable.
Одно из применений заголовка «Replaces» — замена одного участника другим в мультимедийном разговоре. Хотя эта функциональность уже доступна при управлении вызовами по модели стороннего управления вызовами [11], модель 3pcc требует центральной точки управления, что может быть нежелательно во многих средах. Поэтому очень желателен способ выполнения тех же примитивов управления вызовами распределённым образом, по принципу «равный с равным».
Use of a new INVITE with a new header for dialog matching was chosen over making implicit associations in an incoming INVITE based on call-id or other fields for the following reasons:
Использование нового INVITE с новым заголовком для сопоставления диалогов было выбрано вместо неявных ассоциаций во входящем INVITE на основе call-id или других полей по следующим причинам:
o An INVITE already has the correct semantics for a new call
o INVITE уже имеет правильную семантику для нового вызова
o Using an explicit Replaces header in a new request makes the intent of the request obvious.
o Использование явного заголовка Replaces в новом запросе делает намерение запроса очевидным.
o A unique call-id may be given to the replacement call. This avoids dialog matching problems in any of the related User Agents.
o Заменяющему вызову можно дать уникальный call-id. Это позволяет избежать проблем сопоставления диалогов во всех связанных агентах.
o There are no adverse effects if the header is unsupported.
o Если заголовок не поддерживается, отрицательных последствий нет.
The Replaces header enables services such as attended call transfer, retrieve from park, and transition from locally mixed conferences to two party calls in a distributed peer-to-peer way. This list of services is not exhaustive. Although the Replaces header is frequently used in combination with the REFER [8] method as used in a Transfer [12], they may be used independently.
Заголовок Replaces обеспечивает такие услуги, как перевод вызова с консультацией, извлечение вызова из парковки и переход от локально смешанных конференций к двухсторонним вызовам распределённым способом «равный с равным». Этот список услуг не является исчерпывающим. Хотя заголовок Replaces часто используется вместе с методом REFER [8], как в случае перевода [12], они могут использоваться независимо.
For example, Alice is talking to Bob from phone1. She transfers Bob to a Parking Place while she goes to the lab. When she gets there she retrieves the "parked" call from phone2 by sending an INVITE with a Replaces header field to Bob with the dialog information Bob shared with the Parking Place. Alice got this information using some out of band mechanism. Perhaps she subscribed to this information from the Parking Place (using the session dialog package [13]), or went to a website and clicked on a URI. A short call flow for this example follows. (Via and Max-Forwards headers are omitted for clarity.)
Например, Alice разговаривает с Bob с телефона phone1. Она переводит Bob на парковочное место, пока идёт в лабораторию. Придя туда, она извлекает «припаркованный» вызов с телефона phone2, отправляя Bob INVITE с полем заголовка Replaces и информацией о диалоге, которую Bob разделил с парковочным местом. Alice получила эту информацию с помощью некоторого внешнего механизма. Возможно, она подписалась на эту информацию у парковочного места (используя пакет состояния диалога [13]) или зашла на веб-сайт и щёлкнула по URI. 3. User Agent Server Behavior: Receiving a Replaces Header
3. Поведение сервера пользовательского агента: получение заголовка Replaces
The Replaces header contains information used to match an existing SIP dialog (call-id, to-tag, and from-tag). Upon receiving an INVITE with a Replaces header, the User Agent (UA) attempts to match this information with a confirmed or early dialog. The User Agent Server (UAS) matches the to-tag and from-tag parameters as if they were tags present in an incoming request. In other words, the to-tag parameter is compared to the local tag, and the from-tag parameter is compared to the remote tag.
Заголовок Replaces содержит информацию, используемую для сопоставления с существующим диалогом SIP (call-id, to-tag и from-tag). Получив INVITE с заголовком Replaces, пользовательский агент (UA) пытается сопоставить эту информацию с подтверждённым или ранним диалогом. Сервер пользовательского агента (UAS) сопоставляет параметры to-tag и from-tag так, как если бы они были тегами, присутствующими во входящем запросе. Иначе говоря, параметр to-tag сравнивается с локальным тегом, а параметр from-tag — с удалённым тегом.
If more than one Replaces header field is present in an INVITE, or if a Replaces header field is present in a request other than INVITE, the UAS MUST reject the request with a 400 Bad Request response.
Если в INVITE присутствует более одного поля заголовка Replaces или если поле заголовка Replaces присутствует в запросе, отличном от INVITE, UAS ДОЛЖЕН отклонить запрос с ответом 400 Bad Request.
The Replaces header has specific call control semantics. If both a Replaces header field and another header field with contradictory semantics are present in a request, the request MUST be rejected with a 400 "Bad Request" response.
Заголовок Replaces имеет специфическую семантику управления вызовами. Если в запросе одновременно присутствуют поле заголовка Replaces и другое поле заголовка с противоречащей семантикой, запрос ДОЛЖЕН быть отклонён с ответом 400 «Bad Request».
If the Replaces header field matches more than one dialog, the UA MUST act as if no match is found.
Если поле заголовка Replaces соответствует нескольким диалогам, UA ДОЛЖЕН действовать так, будто соответствие не найдено.
If no match is found, the UAS rejects the INVITE and returns a 481 Call/Transaction Does Not Exist response. Likewise, if the Replaces header field matches a dialog which was not created with an INVITE, the UAS MUST reject the request with a 481 response.
Если соответствие не найдено, UAS отклоняет INVITE и возвращает ответ 481 Call/Transaction Does Not Exist. Аналогично, если поле заголовка Replaces соответствует диалогу, который не был создан с помощью INVITE, UAS ДОЛЖЕН отклонить запрос с ответом 481.
If the Replaces header field matches a dialog which has already terminated, the UA SHOULD decline the request with a 603 Declined response. (If the matched invitation was just terminated, the replacement request should fail as well. Declining the request with a 600-class response prevents an irritating race-condition where the UA rings or alerts for a replacement call which is not wanted.)
Если поле заголовка Replaces соответствует диалогу, который уже завершён, UA СЛЕДУЕТ отклонить запрос с ответом 603 Declined. (Если сопоставленное приглашение только что было завершено, запрос замены также должен завершиться неудачей. Отклонение запроса ответом класса 600 предотвращает раздражающее состояние гонки, когда UA звонит или оповещает о заменяющем вызове, который не нужен.)
If the Replaces header field matches an active dialog, the UA MUST verify that the initiator of the new INVITE is authorized to replace the matched dialog. If the initiator of the new INVITE has been successfully authenticated as equivalent to the user who is being replaced, then the replacement is authorized. For example, if the user being replaced and the initiator of the replacement dialog share the same credentials for Digest authentication [6], or they sign the replacement request with S/MIME [7] with the same private key and present the (same) corresponding certificate used in the original dialog, then the replacement is authorized.
Если поле заголовка Replaces соответствует активному диалогу, UA ДОЛЖЕН проверить, что инициатор нового INVITE уполномочен заменить сопоставленный диалог. Если инициатор нового INVITE успешно аутентифицирован как эквивалентный пользователю, которого заменяют, замена разрешена. Например, если заменяемый пользователь и инициатор заменяющего диалога имеют одинаковые учётные данные для Digest-аутентификации [6] или подписывают запрос замены с помощью S/MIME [7] одним и тем же закрытым ключом и предъявляют (тот же) соответствующий сертификат, использованный в исходном диалоге, замена разрешена.
Alternatively, the Referred-By mechanism [4] defines a mechanism that the UAS can use to verify that a replacement request was sent on behalf of the other participant in the matched dialog (in this case, triggered by a REFER request). If the replacement request contains a Referred-By header that corresponds to the user being replaced, the UA SHOULD treat the replacement as if the replacement was authorized by the replaced party. The Referred-By header SHOULD reference a corresponding, valid Refererred-By Authenticated Identity Body [5]. The UA MAY apply other local policy to authorize the remainder of the request. In other words, the UAS may apply a different policy to the replacement dialog than was applied to the replaced dialog.
В качестве альтернативы механизм Referred-By [4] определяет механизм, с помощью которого UAS может проверить, что запрос замены был отправлен от имени другого участника сопоставленного диалога (в данном случае инициирован запросом REFER). Если запрос замены содержит заголовок Referred-By, соответствующий заменяемому пользователю, UA СЛЕДУЕТ рассматривать замену так, как если бы она была разрешена заменяемой стороной. Заголовок Referred-By СЛЕДУЕТ содержать ссылку на соответствующий действительный Refererred-By Authenticated Identity Body [5]. UA МОЖЕТ применить другую локальную политику для авторизации остальной части запроса. Иначе говоря, UAS может применить к заменяющему диалогу иную политику, чем к заменяемому диалогу.
In addition, the UA MAY use other authorization mechanisms defined for this purpose in standards track extensions. Extensions could define other mechanisms for transitively asserting authorization of a replacement.
Кроме того, UA МОЖЕТ использовать другие механизмы авторизации, определённые для этой цели в расширениях уровня стандартов. Расширения могут определять иные механизмы транзитивного подтверждения авторизации замены.
If authorization is successful, the UA attempts to accept the new INVITE, reassign the user interface and other resources of the matched dialog to the new INVITE, and shut down the replaced dialog. If the UA cannot accept the new INVITE (for example: it cannot establish required QoS or keying, or it has incompatible media), the UA MUST return an appropriate error response and MUST leave the matched dialog unchanged.
При успешной авторизации UA пытается принять новый INVITE, переназначить пользовательский интерфейс и другие ресурсы сопоставленного диалога новому INVITE и завершить заменяемый диалог. Если UA не может принять новый INVITE (например, не может обеспечить требуемое QoS или ключи либо имеет несовместимые медиа), UA ДОЛЖЕН вернуть соответствующий ответ об ошибке и ДОЛЖЕН оставить сопоставленный диалог без изменений.
If the Replaces header field matches a confirmed dialog, it checks for the presence of the "early-only" flag in the Replaces header field. (This flag allows the UAC to prevent a potentially undesirable race condition described in Section 7.1.) If the flag is present, the UA rejects the request with a 486 Busy response. Otherwise, it accepts the new INVITE by sending a 200-class response, and shuts down the replaced dialog by sending a BYE. If the Replaces header field matches an early dialog that was initiated by the UA, it accepts the new INVITE by sending a 200-class response, and shuts down the replaced dialog by sending a CANCEL.
Если поле заголовка Replaces соответствует подтверждённому диалогу, оно проверяет наличие флага «early-only» в поле заголовка Replaces. (Этот флаг позволяет UAC предотвратить потенциально нежелательное состояние гонки, описанное в разделе 7.1.) Если флаг присутствует, UA отклоняет запрос ответом 486 Busy. В противном случае он принимает новый INVITE, отправляя ответ класса 200, и завершает заменяемый диалог, отправляя BYE. Если поле заголовка Replaces соответствует раннему диалогу, инициированному UA, оно принимает новый INVITE, отправляя ответ класса 200, и завершает заменяемый диалог, отправляя CANCEL.
If the Replaces header field matches an early dialog that was not initiated by this UA, it returns a 481 (Call/Transaction Does Not Exist) response to the new INVITE, and leaves the matched dialog unchanged. Note that since Replaces matches only a single dialog, the replacement dialog will not be retargeted according to the same forking logic as the original request which created the early dialog.
Если поле заголовка Replaces соответствует раннему диалогу, который не был инициирован этим UA, оно возвращает ответ 481 (Call/Transaction Does Not Exist) на новый INVITE и оставляет сопоставленный диалог без изменений. Обратите внимание: поскольку Replaces сопоставляется только с одним диалогом, заменяющий диалог не будет перенаправлен по той же логике разветвления, что и исходный запрос, создавший ранний диалог.
(Currently, no use cases have been identified for replacing just a single dialog in this circumstance.)
(В настоящее время не выявлено вариантов использования для замены только одного диалога в этих обстоятельствах.)
4. User Agent Client Behavior: Sending a Replaces Header
4. Поведение клиента пользовательского агента: отправка заголовка Replaces
A User Agent that wishes to replace a single existing early or confirmed dialog with a new dialog of its own, MAY send the target User Agent an INVITE request containing a Replaces header field. The User Agent Client (UAC) places the Call-ID, to-tag, and from-tag information for the target dialog in a single Replaces header field and sends the new INVITE to the target. If the user agent only wishes to replace an early dialog (as in the Call Pickup example in Section 7.1), the UAC MAY also include the "early-only" parameter in the Replaces header field. A UAC MUST NOT send an INVITE with a Replaces header field that attempts to replace an early dialog which was not originated by the target of the INVITE with a Replaces header field.
Пользовательский агент, желающий заменить один существующий ранний или подтверждённый диалог своим новым диалогом, МОЖЕТ отправить целевому пользовательскому агенту запрос INVITE, содержащий поле заголовка Replaces. Клиент пользовательского агента (UAC) помещает информацию Call-ID, to-tag и from-tag целевого диалога в одно поле заголовка Replaces и отправляет новый INVITE цели. Если пользовательский агент желает заменить только ранний диалог (как в примере с перехватом вызова в разделе 7.1), UAC МОЖЕТ также включить параметр «early-only» в поле заголовка Replaces. UAC НЕ ДОЛЖЕН отправлять INVITE с полем заголовка Replaces, которое пытается заменить ранний диалог, инициированный не целью INVITE с полем заголовка Replaces.
Note that use of this mechanism does not provide a way to match multiple dialogs, nor does it provide a way to match an entire call, an entire transaction, or to follow a chain of proxy forking logic. For example, if Alice replaces Cathy in an early dialog with Bob, but Bob does not answer, Alice's replacement request will not match other dialogs to which Bob's UA redirects, nor other branches to which his proxy forwards. Although this specification takes reasonable precautions to prevent unexpected behavior in the face of forking, implementations SHOULD only address replacement requests (i.e., set the Request-URI of the replacement request) to the SIP Contact URI of the target.
Обратите внимание, что использование этого механизма не даёт способа сопоставить несколько диалогов, а также не позволяет сопоставить весь вызов, всю транзакцию или проследовать по цепочке логики разветвления прокси. Например, если Alice заменяет Cathy в раннем диалоге с Bob, но Bob не отвечает, запрос замены Alice не будет соответствовать другим диалогам, на которые перенаправляет UA Bob, или другим ветвям, на которые пересылает его прокси. Хотя настоящая спецификация принимает разумные меры предосторожности против неожиданного поведения при разветвлении, реализации СЛЕДУЕТ адресовать запросы замены (то есть задавать Request-URI запроса замены) только SIP Contact URI цели.
5. Proxy behavior
5. Поведение прокси
Proxy Servers do not require any new behavior to support this extension. They simply pass the Replaces header field transparently as described in the SIP specification.
Прокси-серверы не требуют нового поведения для поддержки этого расширения. Они просто передают поле заголовка Replaces прозрачно, как описано в спецификации SIP.
Note that it is possible for a proxy (especially when forking based on some application layer logic, such as caller screening or time- of-day routing) to forward an INVITE request containing a Replaces header field to a completely orthogonal set of Contacts other than the original request it was intended to replace. In this case, the INVITE request with the Replaces header field will fail.
Обратите внимание, что прокси (особенно при разветвлении на основе некоторой логики прикладного уровня, такой как отбор вызывающих или маршрутизация по времени суток) может переслать запрос INVITE, содержащий поле заголовка Replaces, совершенно другому набору Contact, отличному от исходного запроса, который предполагалось заменить. В этом случае запрос INVITE с полем заголовка Replaces потерпит неудачу.
6. Syntax
6. Синтаксис
6.1. The Replaces Header
6.1. Заголовок Replaces
The Replaces header field indicates that a single dialog identified by the header field is to be shut down and logically replaced by the incoming INVITE in which it is contained. It is a request header only, and defined only for INVITE requests. The Replaces header field MAY be encrypted as part of end-to-end encryption. Only a single Replaces header field value may be present in a SIP request.
Поле заголовка Replaces указывает, что отдельный диалог, идентифицированный этим полем заголовка, должен быть завершён и логически заменён входящим INVITE, в котором оно содержится. Это поле заголовка только запроса, определённое только для запросов INVITE. Поле заголовка Replaces МОЖЕТ быть зашифровано в рамках сквозного шифрования. В запросе SIP может присутствовать только одно значение поля заголовка Replaces.

8. Security Considerations
8. Вопросы безопасности
The extension specified in this document significantly changes the relative security of SIP devices. Currently in SIP, even if an eavesdropper learns the Call-ID, To, and From headers of a dialog, they cannot easily modify or destroy that dialog if Digest authentication or end-to-end message integrity are used.
Расширение, определённое в настоящем документе, существенно меняет относительную безопасность устройств SIP. В настоящее время в SIP, даже если подслушивающий узнает заголовки Call-ID, To и From диалога, он не может легко изменить или уничтожить этот диалог, если используются Digest-аутентификация или сквозная целостность сообщений.
This extension can be used to disconnect participants or replace participants in a multimedia conversation. As such, invitations with the Replaces header MUST only be accepted if the peer requesting replacement has been properly authenticated using a standard SIP mechanism (Digest or S/MIME), and authorized to request a replacement of the target dialog. All SIP implementations are already required to support Digest Authentication. In addition, implementations which support the Replaces header SHOULD also implement the Referred-By mechanism.
Это расширение можно использовать для отключения участников или замены участников в мультимедийном разговоре. Поэтому приглашения с заголовком Replaces ДОЛЖНЫ приниматься только в том случае, если сторона, запрашивающая замену, была должным образом аутентифицирована с использованием стандартного механизма SIP (Digest или S/MIME) и уполномочена запрашивать замену целевого диалога. Все реализации SIP уже обязаны поддерживать Digest-аутентификацию. Кроме того, реализации, поддерживающие заголовок Replaces, СЛЕДУЕТ также реализовывать механизм Referred-By.
How a User Agent determines which requests are legitimately authorized to make dialog replacements is non-trivial and depends on a considerable amount of local policy configuration. In general, there are four cases when an authorization for a replacement is reasonable or warranted.
То, как пользовательский агент определяет, какие запросы законно уполномочены выполнять замену диалогов, нетривиально и зависит от значительного объёма конфигурации локальной политики. В общем случае существует четыре ситуации, когда авторизация замены разумна или оправдана.
1. Replacement made by a party considered equivalent to the replaced party
1. Замена, выполненная стороной, считающейся эквивалентной заменяемой стороне
2. Replacement made on behalf of the replaced party (perhaps transitively)
2. Замена, выполненная от имени заменяемой стороны (возможно, транзитивно)
3. Replacement made by a former participant
3. Замена, выполненная бывшим участником
4. Replacement made by a specifically authorized party
4. Замена, выполненная специально уполномоченной стороной
Starting with #1 for example, if an executive and an assistant both receive requests for a shared address-of-record, if so configured, either should be able to replace dialogs of the other for the shared identity. Both could even share the same keying material (Digest or S/MIME), or one could hold an authorization document signed by the other expressing this relationship. Likewise, in a call center environment, each call center agent could possess credentials to which supervisors also have access.
Начиная со случая № 1: например, если руководитель и помощник оба получают запросы на общий адрес записи, то при соответствующей настройке любой из них должен иметь возможность заменять диалоги другого для общей идентичности. Оба могут даже совместно использовать один и тот же ключевой материал (Digest или S/MIME), или один может хранить подписанный другим документ авторизации, выражающий эти отношения. Аналогично, в среде центра обработки вызовов каждый агент центра обработки вызовов может обладать учётными данными, к которым также имеют доступ супервизоры.
The most common use case of a replacement is on the request of the replaced participant (who no longer wants to be involved). This is the case in many features, such as completing an Attended Transfer and converting a 3-way call to a point-to-point call. Such replacements are typically triggered by a REFER [8] request from the replaced participant. The Referred-By [4] mechanism defines one way to identify the apparent original requester and can point to a SIP Authenticated Identity Body [5] (an S/MIME-based signed assertion) to secure this information.
Наиболее распространённый вариант использования замены — по запросу заменяемого участника (который больше не хочет участвовать). Это имеет место во многих функциях, таких как завершение перевода с консультацией и преобразование трёхстороннего вызова в двухточечный вызов. Такие замены обычно инициируются запросом REFER [8] от заменяемого участника. Механизм Referred-By [4] определяет один из способов идентификации предполагаемого исходного запросителя и может указывать на SIP Authenticated Identity Body [5] (подписанное утверждение на основе S/MIME) для защиты этой информации.
In the example in section 1, Alice sends an INVITE with Replaces to Bob. Alice was a former participant in the conversation and had a previous dialog relationship with Bob. Alice can use the same Digest or S/MIME credentials she used to authenticate with Bob during the original call to prove that she was a former participant. Note that this justification for replacing calls is more dangerous than the others, and in most cases is another way to authorize that the replacing participant is available. Implementations SHOULD NOT rely on this method as an authorization mechanism.
В примере из раздела 1 Alice отправляет Bob INVITE с Replaces. Alice была бывшим участником разговора и имела предыдущие диалоговые отношения с Bob. Alice может использовать те же учётные данные Digest или S/MIME, которые она использовала для аутентификации у Bob во время исходного вызова, чтобы доказать, что она была бывшим участником. Обратите внимание, что это обоснование замены вызовов опаснее остальных и в большинстве случаев является ещё одним способом авторизации доступности заменяющего участника. Реализациям НЕ СЛЕДУЕТ полагаться на этот метод как на механизм авторизации.
The last scenario is the easiest to secure but the least likely to be useful in practice. It is unlikely that an arbitrary host in the Internet is aware of any special authorization relationship between the replaced and the replacing parties. However, this use case may be useful in some environments. Since this usage does not effectively degrade the security of the solution, it is still allowed.
Последний сценарий проще всего защитить, но он наименее вероятен для практического использования. Маловероятно, что произвольный хост в Интернете знает о каких-либо особых отношениях авторизации между заменяемой и заменяющей сторонами. Однако этот вариант использования может быть полезен в некоторых средах. Поскольку такое использование не снижает эффективно безопасность решения, оно всё же разрешено.
Some mechanisms for obtaining the dialog information needed by the Replaces header (Call-ID, to-tag, and from-tag) include URIs on a web page, subscriptions to an appropriate event package, and notifications after a REFER request. Since manipulating this dialog information could cause User Agents to replace the wrong dialog, use of message integrity protection for this information is STRONGLY RECOMMENDED. Use of end-to-end security mechanisms to encrypt this information is also RECOMMENDED.
Некоторые механизмы получения информации о диалоге, необходимой заголовку Replaces (Call-ID, to-tag и from-tag), включают URI на веб-странице, подписки на соответствующий пакет событий и уведомления после запроса REFER. Поскольку манипулирование этой информацией о диалоге может привести к замене пользовательскими агентами не того диалога, НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ использовать защиту целостности сообщений для этой информации. Также РЕКОМЕНДУЕТСЯ использовать механизмы сквозной безопасности для шифрования этой информации.
This extension was designed to take advantage of future signature or authorization schemes defined in standards track extensions. In general, call control features benefit considerably from such work.
Это расширение было разработано, чтобы воспользоваться будущими схемами подписи или авторизации, определёнными в расширениях уровня стандартов. В целом функции управления вызовами значительно выигрывают от такой работы.
