Abstract
Аннотация
The Session Initiation Protocol (SIP) utilizes the offer/answer model to establish and update multimedia sessions using the Session Description Protocol (SDP). The description of the offer/answer model in SIP is dispersed across multiple RFCs. This document summarizes all the current usages of the offer/answer model in SIP communication.
Протокол инициирования сессий (SIP) использует модель «предложение/ответ» для установления и обновления мультимедийных сессий с помощью протокола описания сессий (SDP). Описание модели «предложение/ответ» в SIP разбросано по множеству RFC. Настоящий документ обобщает все текущие варианты использования модели «предложение/ответ» при взаимодействии по SIP.

1. Introduction
1. Введение
SIP utilizes the offer/answer model to establish and update sessions. The rules that govern the offer/answer behaviors in SIP are described in several RFCs: [RFC3261], [RFC3262], [RFC3264], [RFC3311], and [RFC6141].
SIP использует модель «предложение/ответ» для установления и обновления сессий. Правила, определяющие поведение при обмене «предложение/ответ» в SIP, описаны в нескольких RFC: [RFC3261], [RFC3262], [RFC3264], [RFC3311] и [RFC6141].
The primary purpose of this document is to describe all forms of SIP usage of the offer/answer model in one document to help the readers to fully understand it. Also, this document tries to incorporate the results of the discussions on the controversial issues to avoid repeating the same discussions later.
Основная цель настоящего документа — описать все формы использования модели «предложение/ответ» в SIP в одном документе, чтобы помочь читателям полностью понять её. Кроме того, настоящий документ пытается учесть результаты обсуждений спорных вопросов, чтобы избежать повторения тех же обсуждений в дальнейшем.
This document describes ambiguities in the current specifications and the authors' understanding of the correct interpretation of these specifications. This document is not intended to make any changes to those specifications, but rather is intended to provide a reference for future standards development work on the SIP offer/answer model and to developers looking for advice on how to implement in compliance with the standards.
Настоящий документ описывает неоднозначности в текущих спецификациях и понимание авторами правильной трактовки этих спецификаций. 2. Summary of SIP Usage of the Offer/Answer Model
2. Сводка использования модели «предложение/ответ» в SIP
The offer/answer model itself is independent from the higher layer application protocols that utilize it. SIP is one of the applications using the offer/answer model. [RFC3264] defines the offer/answer model, but does not specify which SIP messages should convey an offer or an answer. This should be defined in the SIP core and extension RFCs.
Сама модель «предложение/ответ» не зависит от протоколов приложений более высокого уровня, которые её используют. SIP — одно из приложений, использующих модель «предложение/ответ». [RFC3264] определяет модель «предложение/ответ», но не указывает, какие сообщения SIP должны нести предложение или ответ. Это должно определяться в базовых и расширяющих RFC по SIP.
In theory, any SIP message can include a session description in its body. But a session description in a SIP message is not necessarily an offer or an answer. Only certain session description usages that conform to the rules described in Standards-Track RFCs can be interpreted as an offer or an answer. The rules for how to handle the offer/answer model are defined in several RFCs.
Теоретически любое сообщение SIP может содержать описание сессии в своём теле. Но описание сессии в сообщении SIP не обязательно является предложением или ответом. Только определённые способы использования описания сессии, соответствующие правилам, описанным в RFC уровня Standards Track, могут трактоваться как предложение или ответ. Правила обращения с моделью «предложение/ответ» определены в нескольких RFC.
The offer/answer model defines a mechanism for update of sessions. In SIP, a dialog is used to associate an offer/answer exchange with the session that it is to update. In other words, only the offer/ answer exchange in the SIP dialog can update the session that is managed by that dialog.
Модель «предложение/ответ» определяет механизм обновления сессий. В SIP диалог используется для связывания обмена «предложение/ответ» с сессией, которую требуется обновить. Иными словами, только обмен «предложение/ответ» в диалоге SIP может обновлять сессию, управляемую этим диалогом.

2.2. Offer/Answer Exchange Pairs in SIP Messages
2.2. Пары обмена «предложение/ответ» в сообщениях SIP
Currently, the rules on the offer/answer model are defined in [RFC3261], [RFC3262], [RFC3264], [RFC3311], and [RFC6141]. In these RFCs, only the six patterns shown in Table 1 are defined for exchanging an offer and an answer with SIP messages.
В настоящее время правила модели «предложение/ответ» определены в [RFC3261], [RFC3262], [RFC3264], [RFC3311] и [RFC6141]. В этих RFC для обмена предложением и ответом с помощью сообщений SIP определены только шесть шаблонов, показанных в таблице 1.
Note that an offer/answer exchange initiated by an INVITE request must follow exactly one of the Patterns 1, 2, 3, 4. When an initial INVITE causes multiple dialogs due to forking, an offer/answer exchange is carried out independently in each distinct dialog. When an INVITE request contains no offer, only Pattern 2 or Pattern 4 apply. According to Section 13.2.1 of [RFC3261], 'The first reliable non-failure message' must have an offer if there is no offer in the INVITE request. This means that the User Agent (UA) that receives the INVITE request without an offer must include an offer in the first reliable response with 100rel extension. If no reliable provisional response has been sent, the User Agent Server (UAS) must include an offer when sending 2xx response.
Отметим, что обмен «предложение/ответ», инициированный запросом INVITE, должен следовать ровно одному из шаблонов 1, 2, 3, 4. Когда начальный INVITE порождает несколько диалогов из-за разветвления, обмен «предложение/ответ» выполняется независимо в каждом отдельном диалоге. Когда запрос INVITE не содержит предложения, применим только шаблон 2 или шаблон 4. Согласно разделу 13.2.1 [RFC3261], «первое надёжное сообщение, не являющееся отказом» должно содержать предложение, если в запросе INVITE предложения нет. Это означает, что агент пользователя (UA), получивший запрос INVITE без предложения, должен включить предложение в первый надёжный ответ с расширением 100rel. Если ни одного надёжного предварительного ответа не отправлено, сервер агента пользователя (UAS) должен включить предложение при отправке ответа 2xx.
In Pattern 3, the first reliable provisional response may or may not have an answer. When a reliable provisional response contains a session description, and is the first to do so, then that session description is the answer to the offer in the INVITE request. The answer cannot be updated, and a new offer cannot be sent in a subsequent reliable response for the same INVITE transaction.
В шаблоне 3 первый надёжный предварительный ответ может содержать ответ, а может и не содержать. Когда надёжный предварительный ответ содержит описание сессии и является первым таким, это описание сессии является ответом на предложение в запросе INVITE. Ответ не может быть обновлён, и новое предложение не может быть отправлено в последующем надёжном ответе для той же транзакции INVITE.
In Pattern 5, a Provisional Response ACKnowledgement (PRACK) request can contain an offer only if the reliable response that it acknowledges contains an answer to the previous offer/answer exchange.
В шаблоне 5 запрос Provisional Response ACKnowledgement (PRACK) может содержать предложение только в том случае, если подтверждаемый им надёжный ответ содержит ответ на предыдущий обмен «предложение/ответ».
NOTE: It is legal to have UPDATE/2xx exchanges without offer/ answer exchanges (Pattern 6). However, when re-INVITEs are sent for non-offer/answer purposes, an offer/answer exchange is required. In that case, the prior SDP will typically be repeated.
ПРИМЕЧАНИЕ: допустимо иметь обмены UPDATE/2xx без обмена «предложение/ответ» (шаблон 6). Однако когда re-INVITE отправляются не для целей «предложение/ответ», обмен «предложение/ответ» требуется. В этом случае обычно повторяется предыдущий SDP.
There may be ONLY ONE offer/answer negotiation in progress for a single dialog at any point in time. Section 4 explains how to ensure this. When an INVITE results in multiple dialogs, each has a separate offer/answer negotiation.
В любой момент времени для одного диалога может быть ТОЛЬКО ОДНО согласование «предложение/ответ». В разделе 4 объясняется, как это обеспечить. Когда INVITE приводит к нескольким диалогам, каждый имеет отдельное согласование «предложение/ответ».
NOTE: This is when using a Content-Disposition of "session". There may be a second offer/answer negotiation in progress using a Content-Disposition of "early-session" [RFC3959]. That is not addressed by this document.
ПРИМЕЧАНИЕ: это относится к случаю использования Content-Disposition со значением "session". Может существовать второе согласование «предложение/ответ» с Content-Disposition со значением "early-session" [RFC3959]. Это в настоящем документе не рассматривается.

2.3. Rejection of an Offer
2.3. Отклонение предложения
It is not always clear how to reject an offer when it is unacceptable, and some methods do not allow explicit rejection of an offer. For each of the patterns in Table 1, Table 2 shows how to reject an offer.
Не всегда ясно, как отклонить предложение, если оно неприемлемо, а некоторые методы не допускают явного отклонения предложения. Для каждого из шаблонов в таблице 1 таблица 2 показывает, как отклонить предложение.
When a UA receives an INVITE request with an unacceptable offer, it should respond with a 488 response, preferably with Warning header field indicating the reason of the rejection, unless another response code is more appropriate to reject it (Pattern 1 and Pattern 3). If this is a re-INVITE, extra care must be taken, as detailed in [RFC6141]. Specifically, if the offer contains any changes or additions to media stream properties, and those have already been used to transmit/receive media before the final response is sent, then a 2xx response should be sent, with a syntactically correct session description. This may optionally be followed by an UPDATE request to rearrange the session parameters if both ends support the UPDATE method. Alternatively, the UA may send an error response to the (re-)INVITE request to terminate the dialog or to roll back the offer/answer status before sending re-INVITE request. In this case, the UAS should not continue to retransmit the unacknowledged reliable provisional response; the User Agent Client (UAC) should not continue to retransmit a PRACK request.
Когда UA получает запрос INVITE с неприемлемым предложением, он должен ответить ответом 488, предпочтительно с полем заголовка Warning, указывающим причину отклонения, если только другой код ответа не является более подходящим для его отклонения (шаблоны 1 и 3). Если это re-INVITE, необходимо соблюдать особую осторожность, как подробно описано в [RFC6141]. В частности, если предложение содержит какие-либо изменения или дополнения свойств медиапотока, и они уже использовались для передачи/приёма медиа до отправки финального ответа, то следует отправить ответ 2xx с синтаксически корректным описанием сессии. За ним может необязательно следовать запрос UPDATE для переупорядочения параметров сессии, если оба конца поддерживают метод UPDATE. В качестве альтернативы UA может отправить ответ об ошибке на запрос (re-)INVITE, чтобы завершить диалог или откатить состояние «предложение/ответ» перед отправкой запроса re-INVITE. В этом случае UAS не должен продолжать ретрансляцию неподтверждённого надёжного предварительного ответа; клиент агента пользователя (UAC) не должен продолжать ретрансляцию запроса PRACK.
When a UA receives an UPDATE request with an offer that it cannot accept, it should respond with a 488 response, preferably with Warning header field indicating the reason of the rejection, unless another response code is more appropriate to reject it (Pattern 6).
Когда UA получает запрос UPDATE с предложением, которое он не может принять, он должен ответить ответом 488, предпочтительно с полем заголовка Warning, указывающим причину отклонения, если только другой код ответа не является более подходящим для его отклонения (шаблон 6).
When a UA receives a PRACK request with an offer that it cannot accept, it may respond with a 200 response with a syntactically correct session description. Optionally, this may be followed by an UPDATE request to rearrange the session parameters if both ends support the UPDATE method. Alternatively, the UA may terminate the dialog and send an error response to the INVITE request (Pattern 5).
Когда UA получает запрос PRACK с предложением, которое он не может принять, он может ответить ответом 200 с синтаксически корректным описанием сессии. Необязательно за ним может следовать запрос UPDATE для переупорядочения параметров сессии, если оба конца поддерживают метод UPDATE. В качестве альтернативы UA может завершить диалог и отправить ответ об ошибке на запрос INVITE (шаблон 5).
In addition, there is a possibility for UAC to receive a 488 response for an PRACK request. In that case, UAC may send again a PRACK request without an offer or send a CANCEL request to terminate the INVITE transaction.
Кроме того, существует возможность, что UAC получит ответ 488 на запрос PRACK. В этом случае UAC может повторно отправить запрос PRACK без предложения или отправить запрос CANCEL для завершения транзакции INVITE.
NOTE: In [RFC3262], the following restriction is defined with regard to responding to a PRACK request.
ПРИМЕЧАНИЕ: в [RFC3262] определено следующее ограничение в отношении ответа на запрос PRACK.
"If the PRACK does match an unacknowledged reliable provisional response, it MUST be responded to with a 2xx response."
«Если PRACK действительно соответствует неподтверждённому надёжному предварительному ответу, на него ДОЛЖЕН быть дан ответ 2xx».
This restriction is not clear. There are cases where it is unacceptable to send a 2xx response. For example, the UAS may need to send an authentication challenge in a 401 response. This is an open issue and out of scope for this document.
Это ограничение неясно. Существуют случаи, когда отправка ответа 2xx неприемлема. Например, UAS может потребоваться отправить запрос аутентификации в ответе 401. Это открытый вопрос, выходящий за рамки настоящего документа.
When a UA receives a response with an offer that it cannot accept, the UA does not have a way to reject it explicitly. Therefore, a UA should respond to the offer with the correct session description and rearrange the session parameters by initiating a new offer/answer exchange, or alternatively terminate the session (Pattern 2 and Pattern 4). When initiating a new offer/answer, a UA should take care not to cause an infinite offer/answer loop.
Когда UA получает ответ с предложением, которое он не может принять, у него нет способа явно отклонить его. Поэтому UA следует ответить на предложение правильным описанием сессии и переупорядочить параметры сессии, инициировав новый обмен «предложение/ответ», или, в качестве альтернативы, завершить сессию (шаблоны 2 и 4). При инициировании нового обмена «предложение/ответ» UA следует позаботиться о том, чтобы не вызвать бесконечный цикл «предложение/ответ».

3.1.1. INVITE Request with SDP
3.1.1. Запрос INVITE с SDP
When a UAC includes an SDP body in the INVITE request as an offer, only the first SDP in a reliable non-failure response to the INVITE request is the real answer. No other offer/answer exchanges can occur within the messages (other responses and ACK) of the INVITE transaction.
Когда UAC включает тело SDP в запрос INVITE в качестве предложения, только первый SDP в надёжном ответе, не являющемся отказом, на запрос INVITE является настоящим ответом. Никакие другие обмены «предложение/ответ» не могут происходить в сообщениях (других ответах и ACK) транзакции INVITE.
In [RFC3261] there are some descriptions about an offer/answer exchange, but those cause a little confusion. We interpret those descriptions as follows,
В [RFC3261] есть некоторые описания обмена «предложение/ответ», но они вызывают некоторую путаницу. Мы трактуем эти описания следующим образом,
UAC behavior:
Поведение UAC:
1. If the first SDP that the UAC received is included in an unreliable provisional response to the INVITE request, [RFC3261] (Section 13.2.1, second bullet) requires that this be treated as an answer. However, because that same section states that the answer has to be in a reliable non-failure message, this SDP is not the true answer and therefore the offer/answer exchange is not yet completed.
1. Если первый SDP, полученный UAC, включён в ненадёжный предварительный ответ на запрос INVITE, [RFC3261] (раздел 13.2.1, второй пункт) требует трактовать его как ответ. Однако, поскольку в том же разделе указано, что ответ должен быть в надёжном сообщении, не являющемся отказом, этот SDP не является настоящим ответом и, следовательно, обмен «предложение/ответ» ещё не завершён.
2. After the UAC has received the answer in a reliable provisional response to the INVITE, [RFC3261] requires that any SDP in subsequent responses be ignored.
2. После того как UAC получил ответ в надёжном предварительном ответе на INVITE, [RFC3261] требует игнорировать любой SDP в последующих ответах.
3. If the second and subsequent SDP (including a real answer) is different from the first SDP, the UAC should consider that the SDP is equal to the first SDP. Therefore, the UAC should not switch to the new SDP.
3. Если второй и последующие SDP (включая настоящий ответ) отличаются от первого SDP, UAC следует считать, что SDP равен первому SDP. Поэтому UAC не должен переключаться на новый SDP.
UAS behavior:
Поведение UAS:
1. [RFC3261] requires all SDP in the responses to the INVITE request to be identical.
1. [RFC3261] требует, чтобы все SDP в ответах на запрос INVITE были идентичны.
2. After the UAS has sent the answer in a reliable provisional response to the INVITE, the UAS should not include any SDPs in subsequent responses to the INVITE.
2. После того как UAS отправил ответ в надёжном предварительном ответе на INVITE, UAS не должен включать какие-либо SDP в последующие ответы на INVITE.
3. [RFC3261] permits the UAS to send any provisional response without SDP regardless of the transmission of the answer.
3. [RFC3261] разрешает UAS отправлять любой предварительный ответ без SDP независимо от передачи ответа.
A session description in an unreliable response that precedes a reliable response can be considered a "preview" of the answer that will be coming.

NOTE: This "preview" session description rule applies to a single offer/answer exchange. In parallel offer/answer exchanges (caused by forking), a UA may obviously receive a different "preview" of an answer in each dialog. UAs are expected to deal with this.

Предполагается, что UA будут с этим справляться.

When both UAs support the 100rel extension, they can update the session in the early dialog once the first offer/answer exchange has been completed.
Когда оба UA поддерживают расширение 100rel, они могут обновлять сессию в раннем диалоге после завершения первого обмена «предложение/ответ».
From a UA sending an INVITE request:
Со стороны UA, отправляющего запрос INVITE:
A UA can send an UPDATE request with a new offer if both ends support the UPDATE method. Note that if the UAS needs to prompt the user to accept or reject the offer, the delay can result in retransmission of the UPDATE request.
UA может отправить запрос UPDATE с новым предложением, если оба конца поддерживают метод UPDATE. Отметим, что если UAS должен запросить у пользователя принятие или отклонение предложения, задержка может привести к ретрансляции запроса UPDATE.
A UA can send a PRACK request with a new offer only when acknowledging the reliable provisional response carrying the answer to an offer in the INVITE request. Compared to using the UPDATE method, using PRACK can reduce the number of messages exchanged between the UAs. However, to avoid problems or delays caused by PRACK offer rejection, the UA is recommended to send a PRACK request only when it has strong reasons to expect the receiver will accept it. For example, the procedure used in precondition extension [RFC3312] is a case where a PRACK request should be used for updating the session status in an early dialog. UA может отправить запрос PRACK с новым предложением только при подтверждении надёжного предварительного ответа, несущего ответ на предложение в запросе INVITE. По сравнению с использованием метода UPDATE, использование PRACK позволяет сократить число сообщений, обмениваемых между UA. Однако чтобы избежать проблем или задержек, вызванных отклонением предложения в PRACK, UA рекомендуется отправлять запрос PRACK только тогда, когда у него есть веские основания ожидать, что получатель его примет. 3.3. Offer/Answer Exchange in an Established Dialog
3.3. Обмен «предложение/ответ» в установленном диалоге
Both the re-INVITE and UPDATE methods can be used in an established dialog to update the session.
Как метод re-INVITE, так и метод UPDATE могут использоваться в установленном диалоге для обновления сессии.
The UPDATE method is simpler and can save at least one message compared with the INVITE method. But both ends must support the UPDATE method for it to be used.
Метод UPDATE проще и позволяет сэкономить как минимум одно сообщение по сравнению с методом INVITE. Но для его использования оба конца должны поддерживать метод UPDATE.
The INVITE method needs at least three messages to complete but no extensions are needed. Additionally, the INVITE method allows the peer to take time to decide whether or not it will accept a session update by sending provisional responses. That is, re-INVITE allows the UAS to interact with the user at the peer, while UPDATE needs to be answered automatically by the UAS. It is noted that re-INVITE should be answered immediately unless such a user interaction is needed. Otherwise, some Third Party Call Control (3PCC) [RFC3725] flows will break.
Метод INVITE требует как минимум трёх сообщений для завершения, но не требует расширений. Кроме того, метод INVITE позволяет партнёру потратить время на решение о том, примет ли он обновление сессии, отправляя предварительные ответы. То есть re-INVITE позволяет UAS взаимодействовать с пользователем на стороне партнёра, тогда как на UPDATE UAS должен отвечать автоматически. Отмечается, что на re-INVITE следует отвечать немедленно, если только такое взаимодействие с пользователем не требуется. В противном случае некоторые сценарии управления вызовом третьей стороной (3PCC) [RFC3725] нарушатся.
3.4. Recovering from a Failed Re-INVITE
3.4. Восстановление после неудачного re-INVITE
Section 14.1 of [RFC3261] requires that the session parameters in effect prior to a re-INVITE remain unchanged if the re-INVITE fails, as if no re-INVITE had been issued. This remains the case even if multiple offer/answer exchanges have occurred between the sending of the re-INVITE and its failure, and even if media has been exchanged using the proposed changes in the session. Because this can be difficult to achieve in practice, a newer specification [RFC6141] recommends the UAS to send a 2xx response to a re-INVITE in cases where rolling back changes would be problematic.
Раздел 14.1 [RFC3261] требует, чтобы параметры сессии, действовавшие до re-INVITE, оставались неизменными, если re-INVITE завершается неудачей, как если бы re-INVITE не отправлялся. Это остаётся в силе, даже если между отправкой re-INVITE и его неудачей произошло несколько обменов «предложение/ответ», и даже если медиа уже передавались с использованием предложенных изменений в сессии. Поскольку на практике этого может быть трудно достичь, более новая спецификация [RFC6141] рекомендует UAS отправлять ответ 2xx на re-INVITE в случаях, когда откат изменений был бы проблематичным.
Nevertheless, a UAC may receive a failure response to a re-INVITE after proposed changes that must be rolled back have already been used. In such a case, the UAC should send an UPDATE offering the SDP that has been reinstated. (See [RFC6141] for details.)
Тем не менее UAC может получить отказный ответ на re-INVITE после того, как предложенные изменения, которые должны быть откатаны, уже использовались. В таком случае UAC следует отправить UPDATE с предложением SDP, который был восстановлен. (Подробности см. в [RFC6141].)
4. Exceptional Case Handling
4. Обработка исключительных случаев
In [RFC3264], the following restrictions are defined with regard to sending a new offer.
В [RFC3264] определены следующие ограничения в отношении отправки нового предложения.
At any time, either agent MAY generate a new offer that updates the session. However, it MUST NOT generate a new offer if it has received an offer which it has not yet answered or rejected. Furthermore, it MUST NOT generate a new offer if it has generated a prior offer for which it has not yet received an answer or a rejection.
В любой момент любой агент МОЖЕТ сформировать новое предложение, обновляющее сессию. Однако он НЕ ДОЛЖЕН формировать новое предложение, если он получил предложение, на которое ещё не ответил или не отклонил его. Кроме того, он НЕ ДОЛЖЕН формировать новое предложение, если он сформировал предыдущее предложение, на которое ещё не получил ответ или отказ.
Assuming that the above rules are guaranteed, there seem to be two possible 'exceptional' cases to be considered in SIP offer/answer usage: the 'message crossing' case and the 'glare' case. One of the reasons why the usage of SIP methods to exchange offer/answer needs to be carefully restricted in the RFCs is to ensure that the UA can detect and handle appropriately the 'exceptional' cases to avoid incompatible behavior.
При условии соблюдения вышеуказанных правил в использовании «предложение/ответ» в SIP можно выделить два возможных «исключительных» случая: случай «пересечения сообщений» и случай «конфликта» (glare). Одна из причин, по которой использование методов SIP для обмена «предложение/ответ» должно тщательно ограничиваться в RFC, состоит в том, чтобы гарантировать, что UA сможет обнаруживать «исключительные» случаи и надлежащим образом их обрабатывать, избегая несовместимого поведения.

5.1. General Principle for Constructing Offers and Answers
5.1. Общий принцип построения предложений и ответов
A UA should send an offer that indicates what it, and its user, are interested in using/doing at that time, without regard for what the other party in the call may have indicated previously. This is the case even when the offer is sent in response to an INVITE or re- INVITE that contains no offer. (However, in the case of re-INVITE, the constraints of [RFC3261] and [RFC3264] must be observed.)
UA следует отправлять предложение, которое указывает, что он и его пользователь заинтересованы использовать или делать в этот момент, без учёта того, что другая сторона вызова могла указать ранее. Это относится и к случаю, когда предложение отправляется в ответ на INVITE или re-INVITE, не содержащий предложения. (Однако в случае re-INVITE необходимо соблюдать ограничения [RFC3261] и [RFC3264].)
A UA should send an answer that includes as close an approximation to what the UA and its user are interested in doing at that time, while remaining consistent with the offer/answer rules of [RFC3264] and other RFCs.
UA следует отправлять ответ, который содержит как можно более близкое приближение к тому, что UA и его пользователь заинтересованы делать в этот момент, оставаясь при этом в соответствии с правилами «предложение/ответ» из [RFC3264] и других RFC.
NOTE: "at that time" is important. The device may permit the user to configure which supported media are to be used by default.
ПРИМЕЧАНИЕ: «в этот момент» важно. Устройство может позволять пользователю настраивать, какие поддерживаемые типы медиа используются по умолчанию.
In some cases, a UA may not have direct knowledge of what it is interested in doing at a particular time. If it is an intermediary, it may be able to delegate the decision. In the worst case, it may apply a default, such as assuming it wants to use all of its capabilities.
В некоторых случаях UA может не иметь прямого знания о том, что его интересует в конкретный момент. Если он является промежуточным узлом, он может делегировать решение. В худшем случае он может применить значение по умолчанию, например предположить, что хочет использовать все свои возможности.
5.2. Choice of Media Types and Formats to Include and Exclude
5.2. Выбор типов медиа и форматов для включения и исключения
5.2.1. Sending an Initial INVITE with Offer
5.2.1. Отправка начального INVITE с предложением
When a UAC sends an initial INVITE with an offer, it has complete freedom to choose which media type(s) and media format(s) (payload types in the case of RTP) it should include in the offer.
Когда UAC отправляет начальный INVITE с предложением, он имеет полную свободу выбора типа (типов) медиа и формата (форматов) медиа (типов полезной нагрузки в случае RTP), которые следует включить в предложение.
The media types may be all or a subset of the media the UAC is capable of supporting, with the particular subset being determined by the design and configuration (e.g., via [RFC6080]) of the UAC combined with input from the user interface of the UAC.
Типы медиа могут быть всеми или подмножеством типов медиа, которые UAC способен поддерживать, причём конкретное подмножество определяется дизайном и конфигурацией UAC (например, через [RFC6080]) в сочетании с вводом от пользовательского интерфейса UAC.
The media formats may be all or a subset of the media formats the UAC is capable of supporting for the corresponding media type, with the particular subset being determined by the design and configuration of the UAC combined with input from the user interface of the UAC.
Форматы медиа могут быть всеми или подмножеством форматов медиа, которые UAC способен поддерживать для соответствующего типа медиа, причём конкретное подмножество определяется дизайном и конфигурацией UAC в сочетании с вводом от пользовательского интерфейса UAC.
Including all supported media formats will maximize the possibility that the other party will have a supported format in common. But including many can result in an unacceptably large SDP body.
Включение всех поддерживаемых форматов медиа максимизирует вероятность того, что у другой стороны будет общий поддерживаемый формат. Но включение многих из них может привести к недопустимо большому телу SDP.
5.2.2. Responding with an Offer When the Initial INVITE Has No Offer
5.2.2. Ответ с предложением, когда начальный INVITE не содержит предложения
When a UAS has received an initial INVITE without an offer, it must include an offer in the first reliable response to the INVITE. It has largely the same options as when sending an initial INVITE with an offer, but there are some differences. The choice may be governed by both static (default) selections of media types as well as dynamic selections made by a user via interaction with the device while it is alerting.
Когда UAS получил начальный INVITE без предложения, он должен включить предложение в первый надёжный ответ на INVITE. У него в значительной степени те же возможности, что и при отправке начального INVITE с предложением, но есть некоторые различия. Выбор может определяться как статическими (по умолчанию) настройками типов медиа, так и динамическим выбором, сделанным пользователем при взаимодействии с устройством, пока оно подаёт сигнал вызова.
NOTE: The offer may be sent in a reliable provisional response, before the user of the device has been alerted and had an opportunity to select media options for the call. In this case, the UAS cannot include any call-specific options from the user of the device. If there is a possibility that the user of the device will wish to change what is offered before answering the call, then special care should be taken. If PRACK and UPDATE are supported by caller and callee then an initial offer can be sent reliably, and changed with an UPDATE if the user desires a change. If PRACK and UPDATE are not supported, then the initial offer cannot be changed until the call is fully established. In that case, the offer in a 200 response for the initial INVITE should include only the media types and formats believed to be acceptable to the user.
ПРИМЕЧАНИЕ: предложение может быть отправлено в надёжном предварительном ответе до того, как пользователь устройства был оповещён и получил возможность выбрать параметры медиа для вызова. В этом случае UAS не может включить какие-либо параметры, специфичные для вызова, от пользователя устройства. Если существует вероятность того, что пользователь устройства захочет изменить предлагаемое до ответа на вызов, следует проявлять особую осторожность. Если PRACK и UPDATE поддерживаются вызывающей и вызываемой сторонами, начальное предложение может быть отправлено надёжно и изменено с помощью UPDATE, если пользователь желает изменения. Если PRACK и UPDATE не поддерживаются, начальное предложение нельзя изменить до полного установления вызова. В этом случае предложение в ответе 200 на начальный INVITE должно включать только те типы и форматы медиа, которые, по мнению UAS, будут приемлемы для пользователя.
5.2.3. Answering an Initial INVITE with Offer
5.2.3. Ответ на начальный INVITE с предложением
When a UAS receives an initial INVITE with an offer, what media lines the answer may contain is constrained by [RFC3264]. The answer must contain the same number of "m=" lines as the offer, and they must contain the same media types. Each media line may be accepted, by including a non-zero port number, or rejected by including a zero port number in the answer. The media lines that are accepted should typically be those with types and formats the UAS would have included if it were the offerer.
Когда UAS получает начальный INVITE с предложением, то, какие медиалинии может содержать ответ, ограничено [RFC3264]. Ответ должен содержать то же число строк «m=», что и предложение, и они должны содержать те же типы медиа. Каждая медиалиния может быть принята путём включения ненулевого номера порта или отклонена путём включения нулевого номера порта в ответе. Принятые медиалинии обычно должны быть теми, которые UAS включил бы, если бы он был отправителем предложения.
The media formats the answer may contain are constrained by [RFC3264]. For each accepted "m=" line in the answer, there must be at least one media format in common with the corresponding "m=" line of the offer. The UAS may also include other media formats it is able to support at this time. Doing so establishes an asymmetric media format situation, where these "other" media formats may only be sent from the offerer to the answerer. This asymmetric media situation is also limited because it cannot be sustained if there is a subsequent offer/answer exchange in the opposite direction. Also, there is limited value in including these other media formats because there is no assurance that the offerer will be able to use them. If the UAS does not wish to indicate support for any of the media types in a particular media line of the offer it must reject the corresponding media line, by setting the port number to zero.
Форматы медиа, которые может содержать ответ, ограничены [RFC3264]. Для каждой принятой строки «m=» в ответе должен быть хотя бы один формат медиа, общий с соответствующей строкой «m=» предложения. UAS может также включить другие форматы медиа, которые он способен поддерживать в это время. Это создаёт асимметричную ситуацию с форматами медиа, когда эти «другие» форматы медиа могут передаваться только от отправителя предложения к отвечающему. Эта асимметричная ситуация с медиа также ограничена, поскольку она не может сохраняться при последующем обмене «предложение/ответ» в обратном направлении. Кроме того, включение этих других форматов медиа имеет ограниченную ценность, поскольку нет гарантии, что отправитель предложения сможет их использовать. Если UAS не желает указывать поддержку ни одного из типов медиа в конкретной медиалинии предложения, он должен отклонить соответствующую медиалинию, установив номер порта равным нулю.
When the UAS wishes to reject all of the media lines in the offer, it may send a 488 failure response. Alternatively, it may send a reliable non-failure response including all media lines with port numbers set to zero.
Когда UAS желает отклонить все медиалинии в предложении, он может отправить отказный ответ 488. В качестве альтернативы он может отправить надёжный ответ, не являющийся отказом, включающий все медиалинии с номерами портов, установленными в ноль.
5.2.4. Answering When the Initial INVITE Had No Offer
5.2.4. Ответ, когда начальный INVITE не содержал предложения
When a UAC has sent an initial INVITE without an offer, and then receives a response with the first offer, it should answer in the same way as a UAS receiving an initial INVITE with an offer.
Когда UAC отправил начальный INVITE без предложения, а затем получает ответ с первым предложением, он должен отвечать так же, как UAS, получающий начальный INVITE с предложением.
Because the offer arrives in a response to the INVITE, the UAC cannot reject the message containing the offer. If the UAC wishes to reject the entire offer, it must send a PRACK or ACK request including all the media lines with ports set to zero. Then, if it does not wish to continue the session, it may send a CANCEL or BYE request to terminate the dialog.
Поскольку предложение приходит в ответе на INVITE, UAC не может отклонить сообщение, содержащее предложение. Если UAC желает отклонить всё предложение, он должен отправить запрос PRACK или ACK, включающий все медиалинии с портами, установленными в ноль. Затем, если он не желает продолжать сессию, он может отправить запрос CANCEL или BYE для завершения диалога.
5.2.5. Subsequent Offers and Answers
5.2.5. Последующие предложения и ответы
The guidelines above (Sections 5.1 and 5.2.1 through Section 5.2.4) apply, but constraints in [RFC3264] must also be followed. The following are of particular note because they have proven troublesome:
Приведённые выше рекомендации (разделы 5.1 и с 5.2.1 по 5.2.4) применимы, но также необходимо соблюдать ограничения [RFC3264]. Следующие моменты особенно важны, поскольку они оказались проблемными:
o The number of "m=" lines may not be reduced in a subsequent offer. Previously rejected media streams must remain, or be reused to offer the same or a different stream. (Section 6 of [RFC3264].)
o Число строк «m=» не может быть уменьшено в последующем предложении. Ранее отклонённые медиапотоки должны остаться или быть повторно использованы для предложения того же или другого потока. (Раздел 6 [RFC3264].)
o In the "o=" line, only the version number may change, and if it changes, it must increment by one from the one previously sent as an offer or answer. (Section 8 of [RFC3264].) If it doesn't change, then the entire SDP body must be identical to what was previously sent as an offer or answer. Changing the "o=" line, except version number value, during the session is an error case. The behavior when receiving such a non-compliant offer/answer SDP body is implementation dependent. If a UA needs to negotiate a 'new' SDP session, it should use the INVITE/Replaces method.
o В строке «o=» может изменяться только номер версии, и если он изменяется, он должен увеличиваться на единицу относительно того, который был ранее отправлен в качестве предложения или ответа. (Раздел 8 [RFC3264].) Если он не изменяется, то всё тело SDP должно быть идентично тому, что было ранее отправлено в качестве предложения или ответа. Изменение строки «o=», кроме значения номера версии, во время сессии является ошибочным случаем. Поведение при получении такого несоответствующего правилам тела SDP «предложение/ответ» зависит от реализации. Если UA необходимо согласовать «новую» сессию SDP, он должен использовать метод INVITE/Replaces.
o In the case of RTP, the mapping from a particular dynamic payload type number to a particular codec within that media stream ("m=" line) must not change for the duration of the session. (Section 8.3.2 of [RFC3264].) NOTE: This may be impossible for a back-to-back user agent (B2BUA) to follow in some cases (e.g., 3PCC transfer) if it does not terminate media.
o В случае RTP соответствие между конкретным номером динамического типа полезной нагрузки и конкретным кодеком внутри этого медиапотока (строки «m=») не должно изменяться в течение сессии. (Раздел 8.3.2 [RFC3264].) ПРИМЕЧАНИЕ: это может быть невозможно для агента пользователя типа back-to-back (B2BUA) в некоторых случаях (например, при переадресации 3PCC), если он не завершает медиа.
When the new offer is sent in response to an offerless (re-)INVITE, it should be constructed according to the General Principle for Constructing Offers and Answers (Section 5.1 ): all codecs the UA is currently willing and able to use should be included, not just the ones that were negotiated by previous offer/answer exchanges. The same is true for media types -- so if UA A initially offered audio and video to UA B, and they end up with only audio, and UA B sends an offerless (re-)INVITE to UA A, A's resulting offer should most likely re-attempt video, by reusing the zeroed "m=" line used previously.
Когда новое предложение отправляется в ответ на (re-)INVITE без предложения, оно должно строиться в соответствии с Общим принципом построения предложений и ответов (раздел 5.1): следует включать все кодеки, которые UA в настоящее время желает и способен использовать, а не только те, которые были согласованы предыдущими обменами «предложение/ответ». То же относится и к типам медиа — так что если UA A изначально предложил UA B аудио и видео, а они в итоге получили только аудио, и UA B отправляет UA A (re-)INVITE без предложения, то результирующее предложение A, скорее всего, должно снова попытаться предложить видео, повторно используя ранее обнулённую строку «m=».

Or, the offerer may simply not have enough resources to offer "everything" at that point. Even if the UAS is not able to offer any other SDP that the one currently being used, it should not reject the re- INVITE. Instead, it should generate an offer with the currently used SDP with "o=" line unchanged.

5.3. Hold and Resume of Media
5.3. Удержание и возобновление медиа
[RFC3264] specifies (using non-normative language) that "hold" should be indicated in an established session by sending a new offer containing "a=sendonly" attribute for each media stream to be held. An answerer is then to respond with "a=recvonly" attribute to acknowledge that the hold request has been understood.
[RFC3264] указывает (используя ненормативную формулировку), что «удержание» следует обозначать в установленной сессии отправкой нового предложения, содержащего атрибут «a=sendonly» для каждого удерживаемого медиапотока. После этого отвечающий должен ответить атрибутом «a=recvonly», чтобы подтвердить, что запрос удержания понят.
Note that the use of sendonly/recvonly is not limited to hold. These may be used for other reasons, such as devices that are only capable of sending or receiving. So receiving an offer with "a=sendonly" attribute must not be treated as a certain indication that the offerer has placed the media stream on hold.
Отметим, что использование sendonly/recvonly не ограничивается удержанием. Они могут использоваться по другим причинам, например для устройств, способных только отправлять или только принимать. Поэтому получение предложения с атрибутом «a=sendonly» не должно трактоваться как достоверное указание на то, что отправитель предложения перевёл медиапоток в режим удержания.
This model is based on an assumption that the UA initiating the hold will want to play Music on Hold, which is not always the case. A UA may, if desired, initiate hold by offering "a=inactive" attribute if it does not intend to transmit any media while in hold status.
Эта модель основана на предположении, что UA, инициирующий удержание, захочет воспроизводить музыку для ожидающего (Music on Hold), что не всегда так. При желании UA может инициировать удержание, предложив атрибут «a=inactive», если он не намерен передавать какие-либо медиа, находясь в состоянии удержания.
The rules of [RFC3264] constrain what may be in an answer when the offer contains "sendonly", "recvonly", or "inactive" in an "a=" line. But they do not constrain what must be in a subsequent offer. The "General Principle for Constructing Offers and Answers" (Section 5.1)

is important here. The initiation of "hold" is a local action. It

The receipt of an offer containing "a=sendonly" attribute or "a=inactive" attribute and the sending of a compatible answer should not change the desired state of the recipient. However, a UA that has been "placed on hold" may itself desire to initiate its own hold status, based on local input.

Получение предложения, содержащего атрибут «a=sendonly» или «a=inactive», и отправка совместимого ответа не должны изменять желаемое состояние получателя. Однако UA, который был «поставлен на удержание», сам может пожелать инициировать собственное состояние удержания на основе локальных данных.
If UA2 has previously been "placed on hold" by UA1, via receipt of "a=sendonly" attribute, then it may initiate its own hold by sending a new offer containing "a=sendonly" attribute to UA1. Upon receipt of that, UA1 will answer with "a=inactive" attribute because that is the only valid answer that reflects its desire not to receive media.
Если UA2 ранее был «поставлен на удержание» UA1 путём получения атрибута «a=sendonly», то он может инициировать собственное удержание, отправив UA1 новое предложение с атрибутом «a=sendonly». Получив его, UA1 ответит атрибутом «a=inactive», поскольку это единственный допустимый ответ, отражающий его желание не принимать медиа.
NOTE: Section 8.4 of [RFC3264] contains a conflicting recommendation that the offer contain "a=inactive" attribute in this case. We interpret that recommendation to be non-normative. The use of "a=sendonly" attribute in this case will never produce a worse outcome, and can produce a better outcome in useful cases.
ПРИМЕЧАНИЕ: раздел 8.4 [RFC3264] содержит противоречащую рекомендацию о том, что в этом случае предложение должно содержать атрибут «a=inactive». Мы считаем эту рекомендацию ненормативной. Использование атрибута «a=sendonly» в этом случае никогда не даст худшего результата и может дать лучший результат в полезных случаях.
Once in this state, to resume a two-way exchange of media, each side must reset its local hold status. If UA1 is first to go off hold, it will then send an offer with "a=sendrecv" attribute. The UA2 will respond with its desired state of "a=sendonly" attribute because that is a permitted response. When UA2 desires to also resume, it will send an offer with "a=sendrecv" attribute. In this case, because UA1 has the same desire it will respond with "a=sendrecv" attribute. In the same case, when UA2 receives the offer with "a=sendrecv" attribute, if it has decided it wants to reset its local hold but has not yet signaled the intent, it may send "a=sendrecv" attribute in the answer.
Оказавшись в этом состоянии, для возобновления двустороннего обмена медиа каждая сторона должна сбросить свой локальный статус удержания. Если UA1 снимает удержание первым, он отправит предложение с атрибутом «a=sendrecv». UA2 ответит своим желаемым состоянием — атрибутом «a=sendonly», поскольку это допустимый ответ. Когда UA2 также пожелает возобновить, он отправит предложение с атрибутом «a=sendrecv». В этом случае, поскольку UA1 имеет то же желание, он ответит атрибутом «a=sendrecv». В том же случае, когда UA2 получает предложение с атрибутом «a=sendrecv», если он решил, что хочет сбросить свой локальный статус удержания, но ещё не сообщил об этом, он может отправить атрибут «a=sendrecv» в ответе.
If UA2 has been "placed on hold" by UA1 via receipt of "a=inactive" attribute, and subsequently wants to initiate its own hold, also using "a=inactive" attribute, it need not send a new offer, since the only valid response is "a=inactive" attribute and that is already in effect. However, its local desired state will now be either "inactive" or "a=sendonly" attribute. This affects what it will send in future offers and answers.
Если UA2 был «поставлен на удержание» UA1 путём получения атрибута «a=inactive» и впоследствии хочет инициировать собственное удержание, также используя атрибут «a=inactive», ему не нужно отправлять новое предложение, поскольку единственный допустимый ответ — атрибут «a=inactive», и он уже действует. Однако его локальное желаемое состояние теперь будет либо «inactive», либо атрибут «a=sendonly». Это влияет на то, что он будет отправлять в будущих предложениях и ответах.
If a UA has occasion to send another offer in the session, without any desire to change the hold status (e.g., in response to a re- INVITE without an offer, or when sending a re-INVITE to refresh the session timer), it should follow the "General Principle for Constructing Offers and Answers" (Section 5.1). If it previously initiated a "hold" by sending "a=sendonly" attribute or "a=inactive" attribute, then it should offer that again. If it had not previously initiated "hold", then it should offer "a=sendrecv" attribute, even if it had previously been forced to answer something else. Without this behavior it is possible to get "stuck on hold" in some cases, especially when a 3pcc is involved.
Если у UA возникает повод отправить в сессии другое предложение без желания изменить статус удержания (например, в ответ на re-INVITE без предложения или при отправке re-INVITE для обновления таймера сессии), он должен следовать «Общему принципу построения предложений и ответов» (раздел 5.1). Если он ранее инициировал «удержание», отправив атрибут «a=sendonly» или «a=inactive», то он должен предложить его снова. Если он ранее не инициировал «удержание», то он должен предложить атрибут «a=sendrecv», даже если ранее был вынужден ответить что-то другое. Без такого поведения в некоторых случаях можно «застрять на удержании», особенно когда задействован 3pcc.
5.4. Behavior on Receiving SDP with c=0.0.0.0
5.4. Поведение при получении SDP с c=0.0.0.0
[RFC3264] requires that an agent be capable of receiving SDP with a connection address of 0.0.0.0, in which case it means that neither RTP nor RTCP should be sent to the peer.
[RFC3264] требует, чтобы агент был способен принимать SDP с адресом соединения 0.0.0.0, что в этом случае означает, что ни RTP, ни RTCP не должны отправляться партнёру.
If a UA generates an answer to the offer received with "c=IN IP4 0.0.0.0", the direction attribute of the accepted media stream in the answer must still be based on direction attribute of the offered stream and rules specified in [RFC3264] to form the direction "a=" line in the answer. There is no clear rule about the use of "c=IN IP4 0.0.0.0" in the answer; it may be used or "c=" line with a valid IP address may be used. RTP/RTCP will not be sent toward an address of 0.0.0.0 because it is an invalid address.
Если UA формирует ответ на предложение, полученное с «c=IN IP4 0.0.0.0», атрибут направления принятого медиапотока в ответе всё равно должен основываться на атрибуте направления предложенного потока и правилах, определённых в [RFC3264], для формирования строки направления «a=» в ответе. Нет чёткого правила об использовании «c=IN IP4 0.0.0.0» в ответе; он может использоваться, или может использоваться строка «c=» с допустимым IP-адресом. RTP/RTCP не будут отправляться на адрес 0.0.0.0, поскольку это недопустимый адрес.
6. Security Considerations
6. Вопросы безопасности
This document clarifies ambiguities in the intended behavior of the two SIP User Agents engaged in a dialog. The primary specification of offer/answer behavior that is being clarified resides in [RFC3261] and [RFC3264], with extensions in [RFC3311], [RFC3312], and [RFC6141]. The focus of this document is on cases where ambiguities can result failed or degraded calls when there is no attacker. The clarifications exclude call flows that lead to difficulties, without legitimizing any formerly invalid call flows. Thus, the security considerations of the above mentioned documents continue to apply and need not be extended to handle any additional cases.
Настоящий документ разъясняет неоднозначности в предполагаемом поведении двух агентов пользователя SIP, участвующих в диалоге. Основная спецификация поведения «предложение/ответ», которая разъясняется, находится в [RFC3261] и [RFC3264], с расширениями в [RFC3311], [RFC3312] и [RFC6141]. Настоящий документ сосредоточен на случаях, когда неоднозначности могут приводить к неудачным или ухудшенным вызовам при отсутствии злоумышленника. Эти разъяснения исключают потоки вызовов, приводящие к трудностям, не узаконивая при этом никакие ранее недопустимые потоки вызовов. Таким образом, соображения безопасности вышеупомянутых документов продолжают применяться и не требуют расширения для обработки каких-либо дополнительных случаев.
The offer/answer process can be disrupted in numerous ways by an attacker. SIP provides mechanisms to protect the offer/answer exchange from tampering by third parties. Of note is "Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)" [RFC4474], as well as Section 26.3.2, "Security Solutions", of [RFC3261].
Процесс «предложение/ответ» может быть нарушен злоумышленником множеством способов. SIP предоставляет механизмы защиты обмена «предложение/ответ» от вмешательства третьих сторон. Среди них следует отметить «Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)» [RFC4474], а также раздел 26.3.2 «Security Solutions» в [RFC3261].
