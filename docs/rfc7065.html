Универсальный идентификатор ресурса (URI) для TURN
Abstract
Аннотация
This document specifies the syntax of Uniform Resource Identifier (URI) schemes for the Traversal Using Relays around NAT (TURN) protocol. It defines two URI schemes to provision the TURN Resolution Mechanism (RFC 5928).
Настоящий документ определяет синтаксис схем универсального идентификатора ресурса (URI) для протокола прохождения через NAT с помощью ретрансляторов (TURN). В нём определяются две схемы URI для обеспечения механизма определения TURN (RFC 5928).

1. Introduction
1. Введение
This document specifies the syntax and semantics of the Uniform Resource Identifier (URI) scheme for the Traversal Using Relays around NAT (TURN) protocol.
Настоящий документ определяет синтаксис и семантику схемы универсального идентификатора ресурса (URI) для протокола прохождения через NAT с помощью ретрансляторов (TURN).
The TURN protocol is a specification allowing hosts behind NAT to control the operation of a relay server. The relay server allows hosts to exchange packets with its peers. The peers themselves may also be behind NATs. RFC 5766 [RFC5766] defines the specifics of the TURN protocol.
Протокол TURN — это спецификация, позволяющая узлам за NAT управлять работой сервера-ретранслятора. Сервер-ретранслятор позволяет узлам обмениваться пакетами со своими одноранговыми узлами. Сами одноранговые узлы также могут находиться за NAT. В RFC 5766 [RFC5766] определены особенности протокола TURN.
The "turn" and "turns" URI schemes are used to designate a TURN server (also known as a relay) on Internet hosts accessible using the TURN protocol. With the advent of standards such as WebRTC [WEBRTC], we anticipate a plethora of endpoints and web applications to be able to identify and communicate with such a TURN server to carry out the TURN protocol. This implies that endpoints and/or applications must be provisioned with the appropriate configuration to identify the TURN server. Having an inconsistent syntax adds ambiguity and can result in non-interoperable solutions and implementation limitations. The "turn" and "turns" URI schemes help alleviate most of these issues by providing a consistent way to describe, configure, and exchange the information identifying a TURN server.
Схемы URI «turn» и «turns» используются для обозначения сервера TURN (также известного как ретранслятор) на интернет-узлах, доступных с использованием протокола TURN. С появлением таких стандартов, как WebRTC [WEBRTC], мы ожидаем, что множество оконечных устройств и веб-приложений смогут идентифицировать такой сервер TURN и обмениваться с ним данными для выполнения протокола TURN. Это означает, что оконечные устройства и/или приложения должны быть обеспечены соответствующей конфигурацией для идентификации сервера TURN. Несогласованный синтаксис вносит неоднозначность и может привести к несовместимым решениям и ограничениям реализации. Схемы URI «turn» и «turns» помогают смягчить большинство этих проблем, обеспечивая согласованный способ описания, настройки и обмена информацией, идентифицирующей сервер TURN.
[RFC5928] defines a resolution mechanism to convert a secure flag, a host name or IP address, a potentially empty port, and a potentially empty transport to a list of IP address, port, and TURN transport tuples.
В [RFC5928] определён механизм определения, преобразующий флаг защищённости, имя узла или IP-адрес, потенциально пустой порт и потенциально пустой транспорт в список кортежей из IP-адреса, порта и транспорта TURN.
To simplify the provisioning of TURN clients, this document defines the "turn" and "turns" URI schemes that can carry the four components needed for the resolution mechanism.
Чтобы упростить обеспечение клиентов TURN, настоящий документ определяет схемы URI «turn» и «turns», которые могут переносить четыре компонента, необходимые для механизма определения.

3. Definitions of the "turn" and "turns" URI
3. Определения URI «turn» и «turns»
3.1. URI Scheme Syntax
3.1. Синтаксис схемы URI
The "turn" and "turns" URIs have the following formal ABNF syntax [RFC5234]:
URI «turn» и «turns» имеют следующий формальный синтаксис ABNF [RFC5234]:
turnURI = scheme ":" host [ ":" port ] [ "?transport=" transport ] scheme = "turn" / "turns" transport = "udp" / "tcp" / transport-ext transport-ext = 1*unreserved
turnURI = scheme ":" host [ ":" port ] [ "?transport=" transport ] scheme = "turn" / "turns" transport = "udp" / "tcp" / transport-ext transport-ext = 1*unreserved
<host> and <port> are specified in [RFC3986]. While these two ABNF productions are defined in [RFC3986] as components of the generic hierarchical URI, this does not imply that the "turn" and "turns" schemes are hierarchical URIs. Developers MUST NOT use a generic hierarchical URI parser to parse a "turn" or "turns" URI.
<host> и <port> определены в [RFC3986]. Хотя эти две продукции ABNF определены в [RFC3986] как компоненты общего иерархического URI, это не означает, что схемы «turn» и «turns» являются иерархическими URI. Разработчики НЕ ДОЛЖНЫ использовать общий синтаксический анализатор иерархических URI для разбора URI «turn» или «turns».
The <host>, <port>, and <transport> components are passed without modification to the [RFC5928] algorithm. <secure> is set to false if <scheme> is equal to "turn", and set to true if <scheme> is equal to "turns" and passed to the [RFC5928] algorithm with the other components.
Компоненты <host>, <port> и <transport> передаются в алгоритм [RFC5928] без изменений. <secure> устанавливается в false, если <scheme> равен «turn», и в true, если <scheme> равен «turns», и передаётся в алгоритм [RFC5928] вместе с другими компонентами.
3.2. URI Scheme Semantics
3.2. Семантика схемы URI
The "turn" and "turns" URI schemes are used to designate a TURN server (also known as a relay) on Internet hosts accessible using the TURN protocol. The TURN protocol supports sending messages over UDP, TCP, or TLS-over-TCP. The "turns" URI scheme MUST be used when TURN is run over TLS-over-TCP (or, in the future, DTLS-over-UDP), and the "turn" scheme MUST be used otherwise.
Схемы URI «turn» и «turns» используются для обозначения сервера TURN (также известного как ретранслятор) на интернет-узлах, доступных с использованием протокола TURN. Протокол TURN поддерживает отправку сообщений по UDP, TCP или TLS-over-TCP. Схема URI «turns» ДОЛЖНА использоваться, когда TURN работает по TLS-over-TCP (или в будущем по DTLS-over-UDP), а схема «turn» ДОЛЖНА использоваться в остальных случаях.
The required <host> part of the "turn" URI denotes the TURN server host.
Обязательная часть <host> URI «turn» обозначает узел сервера TURN.
As specified in [RFC5766] and [RFC5928], the <port> part, if present, denotes the port on which the TURN server is awaiting connection requests. If it is absent, the default port is 3478 for both UDP and TCP. The default port for TURN over TLS is 5349.
Как указано в [RFC5766] и [RFC5928], часть <port>, если она присутствует, обозначает порт, на котором сервер TURN ожидает запросы на соединение. Если она отсутствует, порт по умолчанию равен 3478 как для UDP, так и для TCP. Порт по умолчанию для TURN поверх TLS — 5349.
4. Security Considerations
4. Вопросы безопасности
Security considerations for the resolution mechanism are discussed in Section 5 of [RFC5928]. Note that this section contains normative text defining authentication procedures to be followed by turn clients when TLS is used.
Вопросы безопасности механизма определения рассматриваются в разделе 5 [RFC5928]. Обратите внимание, что этот раздел содержит нормативный текст, определяющий процедуры аутентификации, которым должны следовать клиенты TURN при использовании TLS.
The "turn" and "turns" URI schemes do not introduce any specific security issues beyond the security considerations discussed in [RFC3986].
Схемы URI «turn» и «turns» не вносят никаких специфических проблем безопасности сверх вопросов безопасности, рассмотренных в [RFC3986].
Although a "turn" or "turns" URI does not itself include the username or password that will be used to authenticate the TURN client, in certain environments, such as WebRTC, the username and password will almost certainly be provisioned remotely by an external agent at the same time as a "turns" URI is sent to that client. Thus, in such situations, if the username and password were received in the clear, there would be little or no benefit to using a "turns" URI. For this reason, a TURN client MUST ensure that the username, password, "turns" URI, and any other security-relevant parameters are received with equivalent security before using the "turns" URI. Receiving those parameters over another TLS session can provide the appropriate level of security, if both TLS sessions are similarly parameterised, e.g., with commensurate strength ciphersuites.
Хотя URI «turn» или «turns» сам по себе не содержит имени пользователя или пароля, которые будут использоваться для аутентификации клиента TURN, в некоторых средах, таких как WebRTC, имя пользователя и пароль почти наверняка будут предоставлены удалённо внешним агентом одновременно с отправкой этому клиенту URI «turns». Таким образом, в таких ситуациях, если имя пользователя и пароль были получены в открытом виде, использование URI «turns» даст мало пользы или не даст её вовсе. По этой причине клиент TURN ДОЛЖЕН гарантировать, что имя пользователя, пароль, URI «turns» и любые другие параметры, важные для безопасности, получены с эквивалентным уровнем безопасности до использования URI «turns». Получение этих параметров через другую сессию TLS может обеспечить надлежащий уровень безопасности, если обе сессии TLS параметризованы аналогичным образом, например с использованием наборов шифров сопоставимой стойкости.

Appendix B. Design Notes
Приложение B. Заметки о проектировании
o One recurring comment was to stop using the suffix "s" on the URI scheme, and to move the secure option to a parameter (e.g. ";proto=tls"). We decided against this idea because the STUN URI does not have a ";proto=" parameter and we would have lost the symmetry between the TURN and STUN URIs.
o Одним из повторяющихся комментариев было предложение перестать использовать суффикс «s» в схеме URI и перенести опцию защищённости в параметр (например, «;proto=tls»). Мы отказались от этой идеи, поскольку URI STUN не имеет параметра «;proto=» и мы потеряли бы симметрию между URI TURN и STUN.
o Following the advice of Section 2.2 of RFC 4395, and because the TURN URI does not describe a hierarchical structure, the TURN URIs are opaque URIs.
o Следуя рекомендации раздела 2.2 RFC 4395, а также поскольку URI TURN не описывает иерархическую структуру, URI TURN являются непрозрачными URI.
o <password> is not used in the URIs because it is deprecated [RFC3986]. <username> and <auth> are not used in the URIs because they do not guide the resolution mechanism.
o <password> не используется в URI, поскольку он устарел [RFC3986]. <username> и <auth> не используются в URI, поскольку они не направляют механизм определения.
o As discussed at IETF 72 in Dublin, there are no generic parameters in the URI to prevent compatibility issues.
o Как обсуждалось на IETF 72 в Дублине, в URI нет общих параметров, чтобы предотвратить проблемы совместимости.
