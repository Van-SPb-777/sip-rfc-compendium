Abstract
Аннотация
This document defines a mechanism by which two entities can make use of the Session Description Protocol (SDP) to arrive at a common view of a multimedia session between them. In the model, one participant offers the other a description of the desired session from their perspective, and the other participant answers with the desired session from their perspective. This offer/answer model is most useful in unicast sessions where information from both participants is needed for the complete view of the session. The offer/answer model is used by protocols like the Session Initiation Protocol (SIP).
Настоящий документ определяет механизм, с помощью которого два объекта могут использовать протокол описания сессий (SDP) для достижения общего представления о мультимедийной сессии. Механизм работает через обмен предложением и ответом. Один участник предлагает набор параметров медиа, а другой участник принимает, отклоняет или изменяет эти параметры, отправляя ответ. Настоящая спецификация определяет обязательный базовый механизм, используемый протоколом инициирования сессий (SIP).
1. Introduction
1. Введение
The Session Description Protocol (SDP) [1] was originally conceived as a way to describe multicast sessions carried on the Mbone. The Session Announcement Protocol (SAP) [6] was devised as a multicast mechanism to carry SDP messages. Although the SDP specification allows for unicast operation, it is not complete. Unlike multicast, where there is a global view of the session that is used by all participants, unicast sessions involve two participants, and a complete view of the session requires information from both participants, and agreement on parameters between them.
Протокол описания сессий (SDP) [1] изначально задумывался как способ описания многоадресных сессий, передаваемых в Mbone. Протокол анонсирования сессий (SAP) [6] был разработан как механизм многоадресной рассылки для передачи сообщений SDP. Хотя спецификация SDP и допускает одноадресную работу, она неполна. В отличие от многоадресной передачи, где существует глобальное представление сессии, используемое всеми участниками, одноадресные сессии включают двух участников, и полное представление сессии требует информации от обоих участников и согласия по параметрам между ними.
As an example, a multicast session requires conveying a single multicast address for a particular media stream. However, for a unicast session, two addresses are needed - one for each participant. As another example, a multicast session requires an indication of which codecs will be used in the session. However, for unicast, the set of codecs needs to be determined by finding an overlap in the set supported by each participant.
Например, многоадресная сессия требует передачи одного многоадресного адреса для конкретного медиапотока. Однако для одноадресной сессии нужны два адреса — по одному на каждого участника. В качестве другого примера многоадресная сессия требует указания, какие кодеки будут использоваться в сессии. Однако для одноадресной передачи набор кодеков нужно определить путём нахождения пересечения множеств, поддерживаемых каждым участником.
As a result, even though SDP has the expressiveness to describe unicast sessions, it is missing the semantics and operational details of how it is actually done. In this document, we remedy that by defining a simple offer/answer model based on SDP. In this model, one participant in the session generates an SDP message that constitutes the offer - the set of media streams and codecs the offerer wishes to use, along with the IP addresses and ports the offerer would like to use to receive the media. The offer is conveyed to the other participant, called the answerer. The answerer generates an answer, which is an SDP message that responds to the offer provided by the offerer. The answer has a matching media stream for each stream in the offer, indicating whether the stream is accepted or not, along with the codecs that will be used and the IP addresses and ports that the answerer wants to use to receive media.
В результате, хотя SDP обладает выразительными возможностями для описания одноадресных сессий, в нём отсутствуют семантика и операционные детали того, как это фактически делается. В настоящем документе мы исправляем это, определяя простую модель «предложение/ответ» на основе SDP. В этой модели один участник сессии формирует сообщение SDP, которое представляет собой предложение — набор медиапотоков и кодеков, которые предлагающий желает использовать, вместе с IP-адресами и портами, которые предлагающий хотел бы использовать для приёма медиа. Предложение передаётся другому участнику, называемому отвечающим. Отвечающий формирует ответ — сообщение SDP, которое отвечает на предложение, предоставленное предлагающим. Ответ содержит соответствующий медиапоток для каждого потока в предложении, указывая, принят ли поток, вместе с кодеками, которые будут использоваться, и IP-адресами и портами, которые отвечающий хочет использовать для приёма медиа.
It is also possible for a multicast session to work similar to a unicast one; its parameters are negotiated between a pair of users as in the unicast case, but both sides send packets to the same multicast address, rather than unicast ones. This document also discusses the application of the offer/answer model to multicast streams.
Также возможно, чтобы многоадресная сессия работала подобно одноадресной: её параметры согласуются между парой пользователей, как в одноадресном случае, но обе стороны отправляют пакеты на один и тот же многоадресный адрес, а не на одноадресные. В настоящем документе также рассматривается применение модели offer/answer к многоадресным потокам.
We also define guidelines for how the offer/answer model is used to update a session after an initial offer/answer exchange.
Мы также определяем руководящие принципы того, как модель «предложение/ответ» используется для обновления сессии после начального обмена предложением и ответом.
The means by which the offers and answers are conveyed are outside the scope of this document. The offer/answer model defined here is the mandatory baseline mechanism used by the Session Initiation Protocol (SIP) [7].
Средства, которыми передаются предложения и ответы, выходят за рамки настоящего документа. Определённая здесь модель «предложение/ответ» является обязательным базовым механизмом, используемым протоколом инициирования сессий (SIP) [7].

3. Definitions
3. Определения
The following terms are used throughout this document:
В настоящем документе используются следующие термины:
Agent: An agent is the protocol implementation involved in the offer/answer exchange. There are two agents involved in an offer/answer exchange.
Агент — протокольная реализация, участвующая в обмене предложением и ответом. В обмене предложением и ответом участвуют два агента.
Answer: An SDP message sent by an answerer in response to an offer received from an offerer.
Ответ — сообщение SDP, отправленное отвечающим в ответ на полученное от предлагающего предложение.
Answerer: An agent which receives a session description from another agent describing aspects of desired media communication, and then responds to that with its own session description.
Отвечающий — агент, который получает описание сессии от другого агента, описывающее аспекты желаемой медиакоммуникации, и затем отвечает на него своим собственным описанием сессии.
Media Stream: From RTSP [8], a media stream is a single media instance, e.g., an audio stream or a video stream as well as a single whiteboard or shared application group. In SDP, a media stream is described by an "m=" line and its associated attributes.
Медиапоток — из RTSP [8], медиапоток является единичным медиаэкземпляром, например аудиопотоком или видеопотоком, а также единичной доской объявлений или группой совместно используемых приложений. В SDP медиапоток описывается строкой «m=» и связанными с ней атрибутами.
Offer: An SDP message sent by an offerer.
Предложение — сообщение SDP, отправленное предлагающим.
Offerer: An agent which generates a session description in order to create or modify a session.
Предлагающий — агент, который формирует описание сессии для создания или изменения сессии.
4. Protocol Operation
4. Работа протокола
The offer/answer exchange assumes the existence of a higher layer protocol (such as SIP) which is capable of exchanging SDP for the purposes of session establishment between agents.
Обмен «предложение/ответ» предполагает существование протокола более высокого уровня (например, SIP), способного обмениваться SDP для целей установления сессии между агентами.
Protocol operation begins when one agent sends an initial offer to another agent. An offer is initial if it is outside of any context that may have already been established through the higher layer protocol. It is assumed that the higher layer protocol provides maintenance of some kind of context which allows the various SDP exchanges to be associated together.
Работа протокола начинается, когда один агент отправляет начальное предложение другому агенту. Предложение является начальным, если оно находится вне любого контекста, который уже мог быть установлен протоколом более высокого уровня. Предполагается, что протокол более высокого уровня обеспечивает поддержание некоторого контекста, позволяющего связать различные обмены SDP друг с другом.
The agent receiving the offer MAY generate an answer, or it MAY reject the offer. The means for rejecting an offer are dependent on the higher layer protocol. The offer/answer exchange is atomic; if the answer is rejected, the session reverts to the state prior to the offer (which may be absence of a session).
Агент, получивший предложение, МОЖЕТ сформировать ответ либо МОЖЕТ отклонить предложение. Средства отклонения предложения зависят от протокола более высокого уровня. Обмен «предложение/ответ» является атомарным: если ответ отклонён, сессия возвращается в состояние, предшествовавшее обмену.
At any time, either agent MAY generate a new offer that updates the session. However, it MUST NOT generate a new offer if it has received an offer which it has not yet answered or rejected. Furthermore, it MUST NOT generate a new offer if it has generated a prior offer for which it has not yet received an answer or a rejection. If an agent receives an offer after having sent one, but before receiving an answer to it, this is considered a "glare" condition.
В любой момент любой агент МОЖЕТ сформировать новое предложение, обновляющее сессию. Однако он НЕ ДОЛЖЕН формировать новое предложение, если он получил предложение, на которое ещё не ответил и не отклонил его. Более того, он НЕ ДОЛЖЕН формировать новое предложение, если он сформировал предыдущее предложение, на которое ещё не получил ответ или отказ. Если агент получает предложение после того, как отправил своё, но до получения ответа на него, это считается состоянием «конфликта» (glare).
The term glare was originally used in circuit switched telecommunications networks to describe the condition where two switches both attempt to seize the same available circuit on the same trunk at the same time. Here, it means both agents have attempted to send an updated offer at the same time.
Термин glare первоначально использовался в сетях связи с коммутацией каналов для описания ситуации, когда две станции одновременно пытаются занять одну и ту же доступную цепь на одном и том же канале. Здесь это означает, что оба агента попытались отправить обновлённое предложение одновременно.
The higher layer protocol needs to provide a means for resolving such conditions. The higher layer protocol will need to provide a means for ordering of messages in each direction. SIP meets these requirements [7].
Протокол более высокого уровня должен предоставлять средства для разрешения таких ситуаций. Протоколу более высокого уровня потребуется обеспечить средства упорядочения сообщений в каждом направлении. SIP удовлетворяет этим требованиям [7].
5. Generating the Initial Offer
5. Формирование начального предложения
The offer (and answer) MUST be a valid SDP message, as defined by RFC 2327 [1], with one exception. RFC 2327 mandates that either an e or a p line is present in the SDP message. This specification relaxes that constraint; an SDP formulated for an offer/answer application MAY omit both the e and p lines. The numeric value of the session id and version in the o line MUST be representable with a 64 bit signed integer. The initial value of the version MUST be less than (2**62)-1, to avoid rollovers. Although the SDP specification allows for multiple session descriptions to be concatenated together into a large SDP message, an SDP message used in the offer/answer model MUST contain exactly one session description.
Предложение (и ответ) ДОЛЖНЫ быть допустимым сообщением SDP, как определено RFC 2327 [1], с одним исключением. RFC 2327 требует, чтобы в сообщении SDP присутствовала строка e или p. Настоящая спецификация ослабляет это ограничение: SDP, сформированный для приложения «предложение/ответ», МОЖЕТ опускать обе строки — e и p. Числовое значение идентификатора сессии и версии в строке o ДОЛЖНО быть представимо 64-битным знаковым целым. Начальное значение версии ДОЛЖНО быть меньше (2**62)-1 во избежание переполнения. Хотя спецификация SDP допускает объединение нескольких описаний сессий в одно большое сообщение SDP, сообщение SDP, используемое в модели «предложение/ответ», ДОЛЖНО содержать ровно одно описание сессии.
The SDP "s=" line conveys the subject of the session, which is reasonably defined for multicast, but ill defined for unicast. For unicast sessions, it is RECOMMENDED that it consist of a single space character (0x20) or a dash (-).
Строка SDP «s=» передаёт тему сессии, которая разумно определена для многоадресной рассылки, но плохо определена для одноадресной. Для одноадресных сессий РЕКОМЕНДУЕТСЯ, чтобы она состояла из одного символа пробела (0x20) или дефиса (-).
Unfortunately, SDP does not allow the "s=" line to be empty.
К сожалению, SDP не допускает, чтобы строка «s=» была пустой.
The SDP "t=" line conveys the time of the session. Generally, streams for unicast sessions are created and destroyed through external signaling means, such as SIP. In that case, the "t=" line SHOULD have a value of "0 0".
Строка SDP «t=» передаёт время сессии. Обычно потоки для одноадресных сессий создаются и уничтожаются посредством внешней сигнализации, такой как SIP. В этом случае строка «t=» СЛЕДУЕТ иметь значение «0 0».
The offer will contain zero or more media streams (each media stream is described by an "m=" line and its associated attributes). Zero media streams implies that the offerer wishes to communicate, but that the streams for the session will be added at a later time through a modified offer. The streams MAY be for a mix of unicast and multicast; the latter obviously implies a multicast address in the relevant "c=" line(s).
Предложение будет содержать ноль или более медиапотоков (каждый медиапоток описывается строкой «m=» и связанными с ней атрибутами). Ноль медиапотоков означает, что предлагающий желает общаться, но потоки сессии будут добавлены позже посредством изменённого предложения. Потоки МОГУТ быть смесью одноадресных и многоадресных; последнее, очевидно, подразумевает многоадресный адрес в соответствующих строках «c=».
Construction of each offered stream depends on whether the stream is multicast or unicast.
Построение каждого предлагаемого потока зависит от того, является ли поток многоадресным или одноадресным.
5.1. Unicast Streams
5.1. Одноадресные потоки
If the offerer wishes to only send media on a stream to its peer, it MUST mark the stream as sendonly with the "a=sendonly" attribute. We refer to a stream as being marked with a certain direction if a direction attribute was present as either a media stream attribute or a session attribute. If the offerer wishes to only receive media from its peer, it MUST mark the stream as recvonly. If the offerer wishes to communicate, but wishes to neither send nor receive media at this time, it MUST mark the stream with an "a=inactive" attribute. The inactive direction attribute is specified in RFC 3108 [3]. Note that in the case of the Real Time Transport Protocol (RTP) [4], RTCP is still sent and received for sendonly, recvonly, and inactive streams. That is, the directionality of the media stream has no impact on the RTCP usage. If the offerer wishes to both send and receive media with its peer, it MAY include an "a=sendrecv" attribute, or it MAY omit it, since sendrecv is the default.
Если предлагающий желает только отправлять медиа по потоку своему партнёру, он ДОЛЖЕН пометить поток как sendonly с помощью атрибута «a=sendonly». Мы говорим, что поток помечен определённым направлением, если атрибут направления присутствовал как атрибут медиапотока либо атрибут сессии. Если предлагающий желает только принимать медиа от своего партнёра, он ДОЛЖЕН пометить поток как recvonly. Если предлагающий желает общаться, но в настоящее время не хочет ни отправлять, ни принимать медиа, он ДОЛЖЕН пометить поток атрибутом «a=inactive». Атрибут направления inactive определён в RFC 3108 [3]. Обратите внимание, что в случае протокола передачи в реальном времени (RTP) [4] RTCP всё равно отправляется и принимается для потоков sendonly, recvonly и inactive. То есть направленность медиапотока не влияет на использование RTCP. Если предлагающий желает как отправлять, так и принимать медиа со своим партнёром, он МОЖЕТ включить атрибут «a=sendrecv», а МОЖЕТ его опустить, поскольку sendrecv является направлением по умолчанию.
For recvonly and sendrecv streams, the port number and address in the offer indicate where the offerer would like to receive the media stream. For sendonly RTP streams, the address and port number indirectly indicate where the offerer wants to receive RTCP reports. Unless there is an explicit indication otherwise, reports are sent to the port number one higher than the number indicated. The IP address and port present in the offer indicate nothing about the source IP address and source port of RTP and RTCP packets that will be sent by the offerer. A port number of zero in the offer indicates that the stream is offered but MUST NOT be used. This has no useful semantics in an initial offer, but is allowed for reasons of completeness, since the answer can contain a zero port indicating a rejected stream (Section 6). Furthermore, existing streams can be terminated by setting the port to zero (Section 8). In general, a port number of zero indicates that the media stream is not wanted.
Для потоков recvonly и sendrecv номер порта и адрес в предложении указывают, где предлагающий хотел бы принимать медиапоток. Для потоков RTP sendonly адрес и номер порта косвенно указывают, где предлагающий хочет принимать отчёты RTCP. Если нет явного указания об ином, отчёты отправляются на номер порта на единицу больше указанного. IP-адрес и порт, присутствующие в предложении, ничего не говорят об исходном IP-адресе и исходном порте пакетов RTP и RTCP, которые будут отправляться предлагающим. Номер порта ноль в предложении указывает, что поток предлагается, но НЕ ДОЛЖЕН использоваться. Это не имеет полезной семантики в начальном предложении, но допускается ради полноты, поскольку ответ может содержать нулевой порт, указывающий на отклонённый поток (раздел 6). Более того, существующие потоки могут быть завершены установкой порта в ноль (раздел 8). В общем случае номер порта ноль указывает, что медиапоток не нужен.
The list of media formats for each media stream conveys two pieces of information, namely the set of formats (codecs and any parameters associated with the codec, in the case of RTP) that the offerer is capable of sending and/or receiving (depending on the direction attributes), and, in the case of RTP, the RTP payload type numbers used to identify those formats. If multiple formats are listed, it means that the offerer is capable of making use of any of those formats during the session. In other words, the answerer MAY change formats in the middle of the session, making use of any of the formats listed, without sending a new offer. For a sendonly stream, the offer SHOULD indicate those formats the offerer is willing to send for this stream. For a recvonly stream, the offer SHOULD indicate those formats the offerer is willing to receive for this stream. For a sendrecv stream, the offer SHOULD indicate those codecs that the offerer is willing to send and receive with.
Список форматов медиа для каждого медиапотока передаёт две части информации: набор форматов (кодеков и любых параметров, связанных с кодеком, в случае RTP), которые предлагающий способен отправлять и/или принимать (в зависимости от атрибутов направления), и, в случае RTP, номера типов полезной нагрузки RTP, используемые для идентификации этих форматов. Если перечислено несколько форматов, это означает, что предлагающий способен использовать любой из этих форматов в течение сессии. Иными словами, отвечающий МОЖЕТ менять форматы в середине сессии, используя любой из перечисленных форматов, не отправляя нового предложения. Для потока sendonly предложение СЛЕДУЕТ указывать те форматы, которые предлагающий готов отправлять для этого потока. Для потока recvonly предложение СЛЕДУЕТ указывать те форматы, которые предлагающий готов принимать для этого потока. Для потока sendrecv предложение СЛЕДУЕТ указывать те кодеки, с которыми предлагающий готов отправлять и принимать.
For recvonly RTP streams, the payload type numbers indicate the value of the payload type field in RTP packets the offerer is expecting to receive for that codec. For sendonly RTP streams, the payload type numbers indicate the value of the payload type field in RTP packets the offerer is planning to send for that codec. For sendrecv RTP streams, the payload type numbers indicate the value of the payload type field the offerer expects to receive, and would prefer to send. However, for sendonly and sendrecv streams, the answer might indicate different payload type numbers for the same codecs, in which case, the offerer MUST send with the payload type numbers from the answer.
Для потоков RTP recvonly номера типов полезной нагрузки указывают значение поля типа полезной нагрузки в пакетах RTP, которые предлагающий ожидает получить для этого кодека. Для потоков RTP sendonly номера типов полезной нагрузки указывают значение поля типа полезной нагрузки в пакетах RTP, предлагающий планирует отправлять для этого кодека. Для потоков RTP sendrecv номера типов полезной нагрузки указывают значение поля типа полезной нагрузки, которое предлагающий ожидает получать и которое предпочёл бы отправлять. Однако для потоков sendonly и sendrecv ответ может указывать другие номера типов полезной нагрузки для тех же кодеков, и в этом случае предлагающий ДОЛЖЕН отправлять с номерами типов полезной нагрузки из ответа.
Different payload type numbers may be needed in each direction because of interoperability concerns with H.323.
Разные номера типов полезной нагрузки могут потребоваться в каждом направлении из соображений совместимости с H.323.
As per RFC 2327, fmtp parameters MAY be present to provide additional parameters of the media format.
Согласно RFC 2327 параметры fmtp МОГУТ присутствовать для предоставления дополнительных параметров формата медиа.
In the case of RTP streams, all media descriptions SHOULD contain "a=rtpmap" mappings from RTP payload types to encodings. If there is no "a=rtpmap", the default payload type mapping, as defined by the current profile in use (for example, RFC 1890 [5]) is to be used.
В случае потоков RTP все описания медиа СЛЕДУЕТ содержать отображения «a=rtpmap» типов полезной нагрузки RTP в кодировки. Если «a=rtpmap» отсутствует, должно использоваться отображение типов полезной нагрузки по умолчанию, как определено используемым в настоящее время профилем (например, RFC 1890 [5]).
This allows easier migration away from static payload types.
Это позволяет упростить переход от статических типов полезной нагрузки.
In all cases, the formats in the "m=" line MUST be listed in order of preference, with the first format listed being preferred. In this case, preferred means that the recipient of the offer SHOULD use the format with the highest preference that is acceptable to it.
Во всех случаях форматы в строке «m=» ДОЛЖНЫ быть перечислены в порядке предпочтения, причём первым указывается предпочтительный формат. В этом случае «предпочтительный» означает, что получателю предложения СЛЕДУЕТ использовать формат с наивысшим предпочтением, который для него приемлем.
If the ptime attribute is present for a stream, it indicates the desired packetization interval that the offerer would like to receive. The ptime attribute MUST be greater than zero.
Если для потока присутствует атрибут ptime, он указывает желаемый интервал пакетирования, который предлагающий хотел бы получать. Атрибут ptime ДОЛЖЕН быть больше нуля.
If the bandwidth attribute is present for a stream, it indicates the desired bandwidth that the offerer would like to receive. A value of zero is allowed, but discouraged. It indicates that no media should be sent. In the case of RTP, it would also disable all RTCP.
Если для потока присутствует атрибут полосы пропускания, он указывает желаемую полосу пропускания, которую предлагающий хотел бы получать. Значение ноль допускается, но не поощряется. Оно указывает, что медиа не должны отправляться. В случае RTP это также отключило бы весь RTCP.
If multiple media streams of different types are present, it means that the offerer wishes to use those streams at the same time. A typical case is an audio and a video stream as part of a videoconference.
Если присутствуют несколько медиапотоков различных типов, это означает, что предлагающий желает использовать эти потоки одновременно. Типичный случай — аудиопоток и видеопоток в рамках видеоконференции.
If multiple media streams of the same type are present in an offer, it means that the offerer wishes to send (and/or receive) multiple streams of that type at the same time. When sending multiple streams of the same type, it is a matter of local policy as to how each media source of that type (for example, a video camera and VCR in the case of video) is mapped to each stream. When a user has a single source for a particular media type, only one policy makes sense: the source is sent to each stream of the same type. Each stream MAY use different encodings. When receiving multiple streams of the same type, it is a matter of local policy as to how each stream is mapped to the various media sinks for that particular type (for example, speakers or a recording device in the case of audio). There are a few constraints on the policies, however. First, when receiving multiple streams of the same type, each stream MUST be mapped to at least one sink for the purpose of presentation to the user. In other words, the intent of receiving multiple streams of the same type is that they should all be presented in parallel, rather than choosing just one. Another constraint is that when multiple streams are received and sent to the same sink, they MUST be combined in some media specific way. For example, in the case of two audio streams, the received media from each might be mapped to the speakers.
Если в предложении присутствуют несколько медиапотоков одного типа, это означает, что предлагающий желает отправлять (и/или принимать) несколько потоков этого типа одновременно. При отправке нескольких потоков одного типа вопросом локальной политики является то, как каждый источник медиа этого типа (например, видеокамера и видеомагнитофон в случае видео) отображается на каждый поток. Когда у пользователя есть единственный источник конкретного типа медиа, разумна только одна политика: источник отправляется в каждый поток того же типа. Каждый поток МОЖЕТ использовать различные кодировки. При приёме нескольких потоков одного типа вопросом локальной политики является то, как каждый поток отображается на различные приёмники медиа для этого конкретного типа (например, динамики или устройство записи в случае аудио). Однако к политикам предъявляется несколько ограничений. Во-первых, при приёме нескольких потоков одного типа каждый поток ДОЛЖЕН отображаться как минимум на один приёмник с целью представления пользователю. Иными словами, смысл приёма нескольких потоков одного типа состоит в том, что все они должны представляться параллельно, а не выбираться лишь один. Другое ограничение состоит в том, что когда несколько потоков принимаются и подаются на один приёмник, они ДОЛЖНЫ объединяться некоторым специфичным для медиа способом. Например, в случае двух аудиопотоков принятые медиа из каждого могут подаваться на динамики.
In that case, the combining operation would be to mix them. In the case of multiple instant messaging streams, where the sink is the screen, the combining operation would be to present all of them to the user interface. The third constraint is that if multiple sources are mapped to the same stream, those sources MUST be combined in some media specific way before they are sent on the stream. Although policies beyond these constraints are flexible, an agent won't generally want a policy that will copy media from its sinks to its sources unless it is a conference server (i.e., don't copy received media on one stream to another stream).
В этом случае объединяющей операцией было бы их смешивание. В случае нескольких потоков мгновенных сообщений, где приёмником является экран, объединяющей операцией было бы представление их всех пользовательскому интерфейсу. Третье ограничение состоит в том, что если несколько источников отображены в один поток, эти источники ДОЛЖНЫ быть объединены некоторым специфичным для медиа способом, прежде чем они будут отправлены в поток. Хотя политики за пределами этих ограничений гибки, агент обычно не захочет политики, которая будет копировать медиа из своих приёмников в свои источники, если это не сервер конференций (то есть не копировать принятые медиа одного потока в другой поток).
A typical usage example for multiple media streams of the same type is a pre-paid calling card application, where the user can press and hold the pound ("#") key at any time during a call to hangup and make a new call on the same card. This requires media from the user to two destinations - the remote gateway, and the DTMF processing application which looks for the pound. This could be accomplished with two media streams, one sendrecv to the gateway, and the other sendonly (from the perspective of the user) to the DTMF application.
Типичный пример использования нескольких медиапотоков одного типа — приложение предоплаченной телефонной карты, где пользователь может нажать и удерживать клавишу решётки («#») в любой момент вызова, чтобы завершить его и выполнить новый вызов по той же карте. Это требует медиа от пользователя к двум адресатам — удалённому шлюзу и приложению обработки DTMF, которое ищет решётку. Это могло бы быть выполнено двумя медиапотоками: один sendrecv к шлюзу, а другой sendonly (с точки зрения пользователя) к приложению DTMF.
Once the offerer has sent the offer, it MUST be prepared to receive media for any recvonly streams described by that offer. It MUST be prepared to send and receive media for any sendrecv streams in the offer, and send media for any sendonly streams in the offer (of course, it cannot actually send until the peer provides an answer with the needed address and port information). In the case of RTP, even though it may receive media before the answer arrives, it will not be able to send RTCP receiver reports until the answer arrives.
После отправки предложения предлагающий ДОЛЖЕН быть готов принимать медиа для любых потоков recvonly, описанных в этом предложении. Он ДОЛЖЕН быть готов отправлять и принимать медиа для любых потоков sendrecv в предложении и отправлять медиа для любых потоков sendonly в предложении (разумеется, он не может фактически отправлять до тех пор, пока партнёр не предоставит ответ с необходимыми адресом и портом). В случае RTP, хотя он может получать медиа до прибытия ответа, он не сможет отправлять отчёты получателя RTCP до прибытия ответа.
5.2. Multicast Streams
5.2. Многоадресные потоки
If a session description contains a multicast media stream which is listed as receive (send) only, it means that the participants, including the offerer and answerer, can only receive (send) on that stream. This differs from the unicast view, where the directionality refers to the flow of media between offerer and answerer. Beyond that clarification, the semantics of an offered multicast stream are exactly as described in RFC 2327 [1].
Если описание сессии содержит многоадресный медиапоток, указанный как только для приёма (отправки), это означает, что участники, включая предлагающего и отвечающего, могут только принимать (отправлять) по этому потоку. Это отличается от одноадресного представления, где направленность относится Помимо этого уточнения, семантика предлагаемого многоадресного потока в точности соответствует описанной в RFC 2327 [1].
6. Generating the Answer
6. Формирование ответа
The answer to an offered session description is based on the offered session description. If the answer is different from the offer in any way (different IP addresses, ports, etc.), the origin line MUST be different in the answer, since the answer is generated by a different entity. In that case, the version number in the "o=" line of the answer is unrelated to the version number in the o line of the offer.
Ответ на предложенное описание сессии основан на предложенном описании сессии. Если ответ отличается от предложения каким-либо образом (другие IP-адреса, порты и т. д.), строка origin в ответе ДОЛЖНА быть иной, поскольку ответ формируется другим объектом. В этом случае номер версии в строке «o=» ответа не связан с номером версии в строке o предложения.
For each "m=" line in the offer, there MUST be a corresponding "m=" line in the answer. The answer MUST contain exactly the same number of "m=" lines as the offer. This allows for streams to be matched up based on their order. This implies that if the offer contained zero "m=" lines, the answer MUST contain zero "m=" lines.
Для каждой строки «m=» в предложении ДОЛЖНА быть соответствующая строка «m=» в ответе. Ответ ДОЛЖЕН содержать ровно столько же строк «m=», сколько в предложении. Это позволяет сопоставлять потоки по их порядку. Это подразумевает, что если предложение содержало ноль строк «m=», ответ ДОЛЖЕН содержать ноль строк «m=».
The "t=" line in the answer MUST equal that of the offer. The time of the session cannot be negotiated.
Строка «t=» в ответе ДОЛЖНА равняться строке «t=» предложения. Время сессии не может быть согласовано.
An offered stream MAY be rejected in the answer, for any reason. If a stream is rejected, the offerer and answerer MUST NOT generate media (or RTCP packets) for that stream. To reject an offered stream, the port number in the corresponding stream in the answer MUST be set to zero. Any media formats listed are ignored. At least one MUST be present, as specified by SDP.
Предложенный поток МОЖЕТ быть отклонён в ответе по любой причине. Если поток отклонён, предлагающий и отвечающий НЕ ДОЛЖНЫ генерировать медиа (или пакеты RTCP) для этого потока. Чтобы отклонить предложенный поток, номер порта в соответствующем потоке ответа ДОЛЖЕН быть установлен в ноль. Любые перечисленные форматы медиа игнорируются. Должен присутствовать хотя бы один, как указано в SDP.
Constructing an answer for each offered stream differs for unicast and multicast.
Построение ответа для каждого предложенного потока различается для одноадресных и многоадресных потоков.
6.1. Unicast Streams
6.1. Одноадресные потоки
If a stream is offered with a unicast address, the answer for that stream MUST contain a unicast address. The media type of the stream in the answer MUST match that of the offer.
Если поток предложен с одноадресным адресом, ответ для этого потока ДОЛЖЕН содержать одноадресный адрес. Тип медиа потока в ответе ДОЛЖЕН совпадать с типом в предложении.
If a stream is offered as sendonly, the corresponding stream MUST be marked as recvonly or inactive in the answer. If a media stream is listed as recvonly in the offer, the answer MUST be marked as sendonly or inactive in the answer. If an offered media stream is listed as sendrecv (or if there is no direction attribute at the media or session level, in which case the stream is sendrecv by default), the corresponding stream in the answer MAY be marked as sendonly, recvonly, sendrecv, or inactive. If an offered media stream is listed as inactive, it MUST be marked as inactive in the answer. For streams marked as recvonly in the answer, the "m=" line MUST contain at least one media format the answerer is willing to receive with from amongst those listed in the offer. The stream MAY indicate additional media formats, not listed in the corresponding stream in the offer, that the answerer is willing to receive. For streams marked as sendonly in the answer, the "m=" line MUST contain at least one media format the answerer is willing to send from amongst those listed in the offer. For streams marked as sendrecv in the answer, the "m=" line MUST contain at least one codec the answerer is willing to both send and receive, from amongst those listed in the offer.
Если поток предложен как sendonly, соответствующий поток ДОЛЖЕН быть помечен в ответе как recvonly или inactive. Если медиапоток указан в предложении как recvonly, ответ ДОЛЖЕН быть помечен как sendonly или inactive. Если предлагаемый медиапоток указан как sendrecv (либо если нет атрибута направления на уровне медиа или сессии, и в этом случае поток по умолчанию является sendrecv), соответствующий поток в ответе МОЖЕТ быть помечен как sendonly, recvonly, sendrecv или inactive. Если предлагаемый медиапоток указан как inactive, он ДОЛЖЕН быть помечен как inactive в ответе. Для потоков, помеченных в ответе как recvonly, строка «m=» ДОЛЖНА содержать как минимум один формат медиа, который отвечающий готов принимать, из числа указанных в предложении. Поток МОЖЕТ указывать дополнительные форматы медиа, не указанные в соответствующем потоке предложения, которые отвечающий готов принимать. Для потоков, помеченных в ответе как sendonly, строка «m=» ДОЛЖНА содержать как минимум один формат медиа, который отвечающий готов отправлять, из числа указанных в предложении. Для потоков, помеченных в ответе как sendrecv, строка «m=» ДОЛЖНА содержать как минимум один кодек, который отвечающий готов и отправлять, и принимать, из числа указанных в предложении.
The stream MAY indicate additional media formats, not listed in the corresponding stream in the offer, that the answerer is willing to send or receive (of course, it will not be able to send them at this time, since it was not listed in the offer). For streams marked as inactive in the answer, the list of media formats is constructed based on the offer. If the offer was sendonly, the list is constructed as if the answer were recvonly. Similarly, if the offer was recvonly, the list is constructed as if the answer were sendonly, and if the offer was sendrecv, the list is constructed as if the answer were sendrecv. If the offer was inactive, the list is constructed as if the offer were actually sendrecv and the answer were sendrecv.
Поток МОЖЕТ указывать дополнительные форматы медиа, не перечисленные в соответствующем потоке предложения, которые отвечающая сторона готова отправлять или принимать (разумеется, отправить их сейчас она не сможет, поскольку в предложении их не было). Для потоков, помеченных в ответе как inactive, список форматов медиа строится на основе предложения. Если предложение было sendonly, список строится так, как если бы ответ был recvonly. Аналогично, если предложение было recvonly, список строится так, как если бы ответ был sendonly, а если предложение было sendrecv — так, как если бы ответ был sendrecv. Если предложение было inactive, список строится так, как если бы предложение было на самом деле sendrecv и ответ был sendrecv.
The connection address and port in the answer indicate the address where the answerer wishes to receive media (in the case of RTP, RTCP will be received on the port which is one higher unless there is an explicit indication otherwise). This address and port MUST be present even for sendonly streams; in the case of RTP, the port one higher is still used to receive RTCP.
Адрес и порт соединения в ответе указывают адрес, по которому отвечающий желает принимать медиа (в случае RTP отчёты RTCP будут приниматься на порту на единицу больше, если нет явного указания об ином). Этот адрес и порт ДОЛЖНЫ быть указаны даже для потоков sendonly; в случае RTP порт на единицу больше всё равно используется для приёма RTCP.
In the case of RTP, if a particular codec was referenced with a specific payload type number in the offer, that same payload type number SHOULD be used for that codec in the answer. Even if the same payload type number is used, the answer MUST contain rtpmap attributes to define the payload type mappings for dynamic payload types, and SHOULD contain mappings for static payload types. The media formats in the "m=" line MUST be listed in order of preference, with the first format listed being preferred. In this case, preferred means that the offerer SHOULD use the format with the highest preference from the answer.
В случае RTP, если конкретный кодек был указан в предложении с определённым номером типа полезной нагрузки, этот же номер типа полезной нагрузки СЛЕДУЕТ использовать для этого кодека в ответе. Даже если используется тот же номер типа полезной нагрузки, ответ ДОЛЖЕН содержать атрибуты rtpmap для определения отображений типов полезной нагрузки для динамических типов полезной нагрузки и СЛЕДУЕТ содержать отображения для статических типов полезной нагрузки. Форматы медиа в строке «m=» ДОЛЖНЫ быть перечислены в порядке предпочтения, причём первым указывается предпочтительный формат. В этом случае «предпочтительный» означает, что предлагающему СЛЕДУЕТ использовать формат с наивысшим предпочтением из ответа.
Although the answerer MAY list the formats in their desired order of preference, it is RECOMMENDED that unless there is a specific reason, the answerer list formats in the same relative order they were present in the offer. In other words, if a stream in the offer lists audio codecs 8, 22 and 48, in that order, and the answerer only supports codecs 8 and 48, it is RECOMMENDED that, if the answerer has no reason to change it, the ordering of codecs in the answer be 8, 48, and not 48, 8. This helps assure that the same codec is used in both directions.
Хотя отвечающий МОЖЕТ перечислять форматы в желаемом для него порядке предпочтения, РЕКОМЕНДУЕТСЯ, если нет особой причины, чтобы отвечающий перечислял форматы в том же относительном порядке, в каком они присутствовали в предложении. Иными словами, если поток в предложении перечисляет аудиокодеки 8, 22 и 48 в этом порядке, а отвечающий поддерживает только кодеки 8 и 48, РЕКОМЕНДУЕТСЯ, чтобы, если у отвечающего нет причин его менять, порядок кодеков в ответе должен быть 8, 48, а не 48, 8. Это помогает обеспечить использование одного и того же кодека в обоих направлениях.
The interpretation of fmtp parameters in an offer depends on the parameters. In many cases, those parameters describe specific configurations of the media format, and should therefore be processed as the media format value itself would be. This means that the same fmtp parameters with the same values MUST be present in the answer if the media format they describe is present in the answer. Other fmtp parameters are more like parameters, for which it is perfectly acceptable for each agent to use different values. In that case, the answer MAY contain fmtp parameters, and those MAY have the same values as those in the offer, or they MAY be different. SDP extensions that define new parameters SHOULD specify the proper interpretation in offer/answer.
Интерпретация параметров fmtp в предложении зависит от параметров. Во многих случаях эти параметры описывают конкретные конфигурации формата медиа и потому должны обрабатываться так же, как обрабатывалось бы само значение формата медиа. Это означает, что те же параметры fmtp с теми же значениями ДОЛЖНЫ присутствовать в ответе, если описанный ими формат медиа присутствует в ответе. Другие параметры fmtp в большей степени являются параметрами, для которых вполне допустимо, чтобы каждый агент использовал разные значения. В этом случае ответ МОЖЕТ содержать параметры fmtp, и они МОГУТ иметь те же значения, что и в предложении, либо МОГУТ отличаться. Расширения SDP, определяющие новые параметры, СЛЕДУЕТ указывать правильную интерпретацию в модели «предложение/ответ».
The answerer MAY include a non-zero ptime attribute for any media stream; this indicates the packetization interval that the answerer would like to receive. There is no requirement that the packetization interval be the same in each direction for a particular stream.
Отвечающий МОЖЕТ включить ненулевой атрибут ptime для любого медиапотока; это указывает интервал пакетирования, который отвечающий хотел бы получать. Нет требования, чтобы интервал пакетирования был одинаковым в каждом направлении для конкретного потока.
The answerer MAY include a bandwidth attribute for any media stream; this indicates the bandwidth that the answerer would like the offerer to use when sending media. The value of zero is allowed, interpreted as described in Section 5.
Отвечающий МОЖЕТ включить атрибут полосы пропускания для любого медиапотока; это указывает полосу пропускания, которую отвечающий хотел бы, чтобы предлагающий использовал при отправке медиа. Значение ноль допускается и интерпретируется, как описано в разделе 5.
If the answerer has no media formats in common for a particular offered stream, the answerer MUST reject that media stream by setting the port to zero.
Если у отвечающего нет общих форматов медиа для конкретного предложенного потока, отвечающий ДОЛЖЕН отклонить этот медиапоток, установив порт в ноль.
If there are no media formats in common for all streams, the entire offered session is rejected.
Если нет общих форматов медиа для всех потоков, вся предложенная сессия отклоняется.
Once the answerer has sent the answer, it MUST be prepared to receive media for any recvonly streams described by that answer. It MUST be prepared to send and receive media for any sendrecv streams in the answer, and it MAY send media immediately. The answerer MUST be prepared to receive media for recvonly or sendrecv streams using any media formats listed for those streams in the answer, and it MAY send media immediately. When sending media, it SHOULD use a packetization interval equal to the value of the ptime attribute in the offer, if any was present. It SHOULD send media using a bandwidth no higher than the value of the bandwidth attribute in the offer, if any was present. The answerer MUST send using a media format in the offer that is also listed in the answer, and SHOULD send using the most preferred media format in the offer that is also listed in the answer. In the case of RTP, it MUST use the payload type numbers from the offer, even if they differ from those in the answer.
После того как отвечающий отправил ответ, он ДОЛЖЕН быть готов принимать медиа для любых потоков recvonly, описанных в этом ответе. Он ДОЛЖЕН быть готов отправлять и принимать медиа для любых потоков sendrecv в ответе и МОЖЕТ отправлять медиа немедленно. Отвечающий ДОЛЖЕН быть готов принимать медиа для потоков recvonly или sendrecv с использованием любых форматов медиа, указанных для этих потоков в ответе, и МОЖЕТ отправлять медиа немедленно. При отправке медиа ему СЛЕДУЕТ использовать интервал пакетирования, равный значению атрибута ptime в предложении, если он присутствовал. Ему СЛЕДУЕТ отправлять медиа с полосой пропускания не выше значения атрибута полосы пропускания в предложении, если он присутствовал. Отвечающий ДОЛЖЕН отправлять с использованием формата медиа из предложения, который также указан в ответе, и СЛЕДУЕТ отправлять с использованием наиболее предпочтительного формата медиа в предложении, который также указан который также указан в предложении, даже если они отличаются от указанных в ответе.
6.2. Multicast Streams
6.2. Многоадресные потоки
Unlike unicast, where there is a two-sided view of the stream, there is only a single view of the stream for multicast. As such, generating an answer to a multicast offer generally involves modifying a limited set of aspects of the stream.
В отличие от одноадресной передачи, где существует двустороннее представление потока, для многоадресной существует только одно представление потока. Как таковое, формирование ответа на многоадресное предложение обычно включает изменение ограниченного набора аспектов потока.
If a multicast stream is accepted, the address and port information in the answer MUST match that of the offer. Similarly, the directionality information in the answer (sendonly, recvonly, or sendrecv) MUST equal that of the offer. This is because all participants in a multicast session need to have equivalent views of the parameters of the session, an underlying assumption of the multicast bias of RFC 2327.
Если многоадресный поток принят, информация об адресе и порте в ответе ДОЛЖНА совпадать с таковой в предложении. Аналогично информация о направленности в ответе (sendonly, recvonly или sendrecv) ДОЛЖНА равняться таковой в предложении. Это потому, что все участники многоадресной сессии должны иметь эквивалентные представления о параметрах сессии — основополагающее допущение многоадресной направленности RFC 2327.
The set of media formats in the answer MUST be equal to or be a subset of those in the offer. Removing a format is a way for the answerer to indicate that the format is not supported.
Набор форматов медиа в ответе ДОЛЖЕН быть равен набору в предложении или являться его подмножеством. Удаление формата — это способ, которым отвечающий указывает, что формат не поддерживается.
The ptime and bandwidth attributes in the answer MUST equal the ones in the offer, if present. If not present, a non-zero ptime MAY be added to the answer.
Атрибуты ptime и полосы пропускания в ответе ДОЛЖНЫ равняться таковым в предложении, если они присутствуют. Если они отсутствуют, в ответ МОЖЕТ быть добавлен ненулевой ptime.
7. Offerer Processing of the Answer
7. Обработка ответа предлагающим
When the offerer receives the answer, it MAY send media on the accepted stream(s) (assuming it is listed as sendrecv or recvonly in the answer). It MUST send using a media format listed in the answer, and it SHOULD use the first media format listed in the answer when it does send.
Когда предлагающий получает ответ, он МОЖЕТ отправлять медиа по принятому потоку (потокам), предполагая, что в ответе он указан как sendrecv или recvonly. Он ДОЛЖЕН отправлять с использованием формата медиа, указанного в ответе, и СЛЕДУЕТ использовать первый формат медиа, указанный в ответе, когда он отправляет.
The reason this is a SHOULD, and not a MUST (its also a SHOULD, and not a MUST, for the answerer), is because there will oftentimes be a need to change codecs on the fly. For example, during silence periods, an agent might like to switch to a comfort noise codec. Or, if the user presses a number on the keypad, the agent might like to send that using RFC 2833 [9]. Congestion control might necessitate changing to a lower rate codec based on feedback.
Причина, по которой это СЛЕДУЕТ, а не ДОЛЖЕН (для отвечающего это тоже СЛЕДУЕТ, а не ДОЛЖЕН), состоит в том, что часто будет потребность менять кодеки на лету. Например, в периоды тишины агент может пожелать переключиться на кодек комфортного шума. Либо, если пользователь нажимает цифру на клавиатуре, агент может пожелать отправить её с использованием RFC 2833 [9]. Управление перегрузкой может потребовать переключения на кодек с более низкой скоростью на основе обратной связи.
The offerer SHOULD send media according to the value of any ptime and bandwidth attribute in the answer.
Предлагающему СЛЕДУЕТ отправлять медиа в соответствии со значением любых атрибутов ptime и полосы пропускания в ответе.
The offerer MAY immediately cease listening for media formats that were listed in the initial offer, but not present in the answer.
Предлагающий МОЖЕТ немедленно прекратить прослушивание форматов медиа, которые были указаны в начальном предложении, но отсутствуют в ответе.
8. Modifying the Session
8. Изменение сессии
At any point during the session, either participant MAY issue a new offer to modify characteristics of the session. It is fundamental to the operation of the offer/answer model that the exact same offer/answer procedure defined above is used for modifying parameters of an existing session.
В любой момент в течение сессии любой участник МОЖЕТ выдать новое предложение для изменения характеристик сессии. Для работы модели «предложение/ответ» принципиально важно, что для изменения параметров существующей сессии используется в точности та же процедура «предложение/ответ», определённая выше.
The offer MAY be identical to the last SDP provided to the other party (which may have been provided in an offer or an answer), or it MAY be different. We refer to the last SDP provided as the "previous SDP". If the offer is the same, the answer MAY be the same as the previous SDP from the answerer, or it MAY be different. If the offered SDP is different from the previous SDP, some constraints are placed on its construction, discussed below.
Предложение МОЖЕТ быть идентичным последнему SDP, предоставленному другой стороне (которое могло быть предоставлено в предложении или в ответе), либо МОЖЕТ отличаться. Последнее предоставленное SDP мы называем «предыдущим SDP». Если предложение то же, ответ МОЖЕТ быть тем же, что и предыдущее SDP от отвечающего, либо МОЖЕТ отличаться. Если предлагаемый SDP отличается от предыдущего SDP, на его построение накладываются некоторые ограничения, обсуждаемые ниже.
Nearly all aspects of the session can be modified. New streams can be added, existing streams can be deleted, and parameters of existing streams can change. When issuing an offer that modifies the session, the "o=" line of the new SDP MUST be identical to that in the previous SDP, except that the version in the origin field MUST increment by one from the previous SDP. If the version in the origin line does not increment, the SDP MUST be identical to the SDP with that version number. The answerer MUST be prepared to receive an offer that contains SDP with a version that has not changed; this is effectively a no-op. However, the answerer MUST generate a valid answer (which MAY be the same as the previous SDP from the answerer, or MAY be different), according to the procedures defined in Section 6.
Почти все аспекты сессии могут быть изменены. Могут быть добавлены новые потоки, существующие потоки могут быть удалены, а параметры существующих потоков могут меняться. При выдаче предложения, изменяющего сессию, строка «o=» нового SDP ДОЛЖНА быть идентична таковой в предыдущем SDP, за исключением того, что версия в поле origin ДОЛЖНА увеличиться на единицу относительно предыдущего SDP. Если версия в строке origin не увеличивается, SDP ДОЛЖЕН быть идентичен SDP с этим номером версии. Отвечающий ДОЛЖЕН быть готов получить предложение, содержащее SDP с неизменённой версией; это фактически ничего не меняет. Однако отвечающий ДОЛЖЕН сформировать действительный ответ (который МОЖЕТ быть тем же, что и предыдущее SDP от отвечающего, либо МОЖЕТ отличаться) согласно процедурам, определённым в разделе 6.
If an SDP is offered, which is different from the previous SDP, the new SDP MUST have a matching media stream for each media stream in the previous SDP. In other words, if the previous SDP had N "m=" lines, the new SDP MUST have at least N "m=" lines. The i-th media stream in the previous SDP, counting from the top, matches the i-th media stream in the new SDP, counting from the top. This matching is necessary in order for the answerer to determine which stream in the new SDP corresponds to a stream in the previous SDP. Because of these requirements, the number of "m=" lines in a stream never decreases, but either stays the same or increases. Deleted media streams from a previous SDP MUST NOT be removed in a new SDP; however, attributes for these streams need not be present.
Если предлагается SDP, отличный от предыдущего SDP, новый SDP ДОЛЖЕН иметь соответствующий медиапоток для каждого медиапотока в предыдущем SDP. Иными словами, если предыдущий SDP имел N строк «m=», новый SDP ДОЛЖЕН иметь не менее N строк «m=». i-й медиапоток в предыдущем SDP, считая сверху, соответствует i-му медиапотоку в новом SDP, считая сверху. Это соответствие необходимо, чтобы отвечающий мог определить, какой поток в новом SDP соответствует потоку в предыдущем SDP. Из-за этих требований число строк «m=» в потоке никогда не уменьшается, а либо остаётся тем же, либо увеличивается. Удалённые медиапотоки из предыдущего SDP НЕ ДОЛЖНЫ удаляться в новом SDP; однако атрибуты для этих потоков не обязаны присутствовать.
8.1. Adding a Media Stream
8.1. Добавление медиапотока
New media streams are created by new additional media descriptions below the existing ones, or by reusing the "slot" used by an old media stream which had been disabled by setting its port to zero. Reusing its slot means that the new media description replaces the old one, but retains its positioning relative to other media descriptions in the SDP. New media descriptions MUST appear below any existing media sections. The rules for formatting these media descriptions are identical to those described in Section 5.
Новые медиапотоки создаются новыми дополнительными описаниями медиа ниже существующих либо путём повторного использования «слота», который использовался старым медиапотоком, отключённым установкой его порта в ноль. Повторное использование его слота означает, что новое описание медиа заменяет старое, но сохраняет своё положение относительно других описаний медиа в SDP. Новые описания медиа ДОЛЖНЫ появляться ниже любых существующих секций медиа. Правила форматирования этих описаний медиа идентичны правилам, описанным в разделе 5.
When the answerer receives an SDP with more media descriptions than the previous SDP from the offerer, or it receives an SDP with a media stream in a slot where the port was previously zero, the answerer knows that new media streams are being added. These can be rejected or accepted by placing an appropriately structured media description in the answer. The procedures for constructing the new media description in the answer are described in Section 6.
Когда отвечающий получает SDP с большим числом описаний медиа, чем в предыдущем SDP от предлагающего, либо получает SDP с медиапотоком в слоте, где порт ранее был равен нулю, отвечающий знает, что добавляются новые медиапотоки. Они могут быть отклонены или приняты путём размещения в ответе соответствующим образом структурированного описания медиа. Процедуры построения нового описания медиа в ответе описаны в разделе 6.
8.2. Removing a Media Stream
8.2. Удаление медиапотока
Existing media streams are removed by creating a new SDP with the port number for that stream set to zero. The stream description MAY omit all attributes present previously, and MAY list just a single media format.
Существующие медиапотоки удаляются созданием нового SDP с номером порта для этого потока, установленным в ноль. Описание потока МОЖЕТ опускать все атрибуты, присутствовавшие ранее, и МОЖЕТ указывать только один формат медиа.
A stream that is offered with a port of zero MUST be marked with port zero in the answer. Like the offer, the answer MAY omit all attributes present previously, and MAY list just a single media format from amongst those in the offer.
Поток, предложенный с портом ноль, ДОЛЖЕН быть помечен портом ноль в ответе. Как и предложение, ответ МОЖЕТ опускать все атрибуты, присутствовавшие ранее, и МОЖЕТ указывать только один формат медиа из числа тех, что в предложении.
Removal of a media stream implies that media is no longer sent for that stream, and any media that is received is discarded. In the case of RTP, RTCP transmission also ceases, as does processing of any received RTCP packets. Any resources associated with it can be released. The user interface might indicate that the stream has terminated, by closing the associated window on a PC, for example.
Удаление медиапотока подразумевает, что медиа больше не отправляются для этого потока, а любые принимаемые медиа отбрасываются. В случае RTP передача RTCP также прекращается, как и обработка любых принятых пакетов RTCP. Любые связанные с ним ресурсы могут быть освобождены. Пользовательский интерфейс может указать, что поток завершён, например закрыв соответствующее окно на ПК.
8.3. Modifying a Media Stream
8.3. Изменение медиапотока
Nearly all characteristics of a media stream can be modified.
Почти все характеристики медиапотока могут быть изменены.
8.3.1. Modifying Address, Port or Transport
8.3.1. Изменение адреса, порта или транспорта
The port number for a stream MAY be changed. To do this, the offerer creates a new media description, with the port number in the m line different from the corresponding stream in the previous SDP. If only the port number is to be changed, the rest of the media stream description SHOULD remain unchanged. The offerer MUST be prepared to receive media on both the old and new ports as soon as the offer is sent. The offerer SHOULD NOT cease listening for media on the old port until the answer is received and media arrives on the new port. Doing so could result in loss of media during the transition. Received, in this case, means that the media is passed to a media sink. This means that if there is a playout buffer, the agent would continue to listen on the old port until the media on the new port reached the top of the playout buffer. At that time, it MAY cease listening for media on the old port.
Номер порта для потока МОЖЕТ быть изменён. Для этого предлагающий создаёт новое описание медиа, в котором номер порта в строке m отличается от соответствующего потока в предыдущем SDP. Если нужно изменить только номер порта, остальная часть описания медиапотока СЛЕДУЕТ оставить неизменной. Предлагающий ДОЛЖЕН быть готов принимать медиа на обоих портах — старом и новом — как только предложение отправлено. Предлагающему НЕ СЛЕДУЕТ прекращать прослушивание медиа на старом порту до тех пор, пока не получен ответ и медиа не пришли на новый порт. Это могло бы привести к потере медиа во время перехода. «Получены» в этом случае означает, что медиа переданы в приёмник медиа. Это означает, что при наличии буфера воспроизведения агент продолжал бы прослушивать старый порт до тех пор, пока медиа на новом порту не достигли бы вершины буфера воспроизведения. В этот момент он МОЖЕТ прекратить прослушивание медиа на старом порту.
The corresponding media stream in the answer MAY be the same as the stream in the previous SDP from the answerer, or it MAY be different. If the updated stream is accepted by the answerer, the answerer SHOULD begin sending traffic for that stream to the new port immediately. If the answerer changes the port from the previous SDP, it MUST be prepared to receive media on both the old and new ports as soon as the answer is sent. The answerer MUST NOT cease listening for media on the old port until media arrives on the new port. At that time, it MAY cease listening for media on the old port. The same is true for an offerer that sends an updated offer with a new port; it MUST NOT cease listening for media on the old port until media arrives on the new port.
Соответствующий медиапоток в ответе МОЖЕТ быть тем же, что и поток в предыдущем SDP от отвечающего, либо МОЖЕТ отличаться. Если обновлённый поток принят отвечающим, отвечающему СЛЕДУЕТ немедленно начать отправлять трафик для этого потока на новый порт. Если отвечающий изменяет порт относительно предыдущего SDP, он ДОЛЖЕН быть готов принимать медиа на обоих портах — старом и новом — как только ответ отправлен. Отвечающий НЕ ДОЛЖЕН прекращать прослушивание медиа на старом порту до тех пор, пока медиа не придут на новый порт. В этот момент он МОЖЕТ прекратить прослушивание медиа на старом порту. То же верно и для предлагающего, который отправляет обновлённое предложение с новым портом; он НЕ ДОЛЖЕН прекращать прослушивание медиа на старом порту до тех пор, пока медиа не придут на новый порт.
Of course, if the offered stream is rejected, the offerer can cease being prepared to receive using the new port as soon as the rejection is received.
Разумеется, если предложенный поток отклонён, предлагающий может прекратить готовность принимать через новый порт сразу после получения отказа.
To change the IP address where media is sent to, the same procedure is followed for changing the port number. The only difference is that the connection line is updated, not the port number.
Чтобы изменить IP-адрес, на который отправляются медиа, применяется та же процедура, что и для изменения номера порта. Единственное различие состоит в том, что обновляется строка соединения, а не номер порта.
The transport for a stream MAY be changed. The process for doing this is identical to changing the port, except the transport is updated, not the port.
Транспорт для потока МОЖЕТ быть изменён. Процесс для этого идентичен изменению порта, за исключением того, что обновляется транспорт, а не порт.
8.3.2. Changing the Set of Media Formats
8.3.2. Изменение набора форматов медиа
The list of media formats used in the session MAY be changed. To do this, the offerer creates a new media description, with the list of media formats in the "m=" line different from the corresponding media stream in the previous SDP. This list MAY include new formats, and MAY remove formats present from the previous SDP. However, in the case of RTP, the mapping from a particular dynamic payload type number to a particular codec within that media stream MUST NOT change for the duration of a session. For example, if A generates an offer with G.711 assigned to dynamic payload type number 46, payload type number 46 MUST refer to G.711 from that point forward in any offers or answers for that media stream within the session. However, it is acceptable for multiple payload type numbers to be mapped to the same codec, so that an updated offer could also use payload type number 72 for G.711. The mappings need to remain fixed for the duration of the session because of the loose synchronization between signaling exchanges of SDP and the media stream.
Список форматов медиа, используемых в сессии, МОЖЕТ быть изменён. Для этого предлагающий создаёт новое описание медиа, в котором список форматов медиа в строке «m=» отличается от соответствующего медиапотока в предыдущем SDP. Этот список МОЖЕТ включать новые форматы и МОЖЕТ удалять форматы, присутствовавшие в предыдущем SDP. Однако в случае RTP отображение конкретного номера динамического типа полезной нагрузки в конкретный кодек в пределах этого медиапотока НЕ ДОЛЖНО меняться в течение сессии. Например, если A формирует предложение с назначением G.711 номеру динамического типа полезной нагрузки 46, номер типа полезной нагрузки 46 ДОЛЖЕН ссылаться на G.711 с этого момента далее во всех предложениях или ответах для этого медиапотока в пределах сессии. Однако допустимо, чтобы несколько номеров типов полезной нагрузки отображались в один и тот же кодек, так что обновлённое предложение могло бы также использовать номер типа полезной нагрузки 72 для G.711. Отображения должны оставаться фиксированными в течение сессии из-за слабой синхронизации между обменами сигнализации SDP и медиапотоком.
The corresponding media stream in the answer is formulated as described in Section 6, and may result in a change in media formats as well. Similarly, as described in Section 6, as soon as it sends its answer, the answerer MUST begin sending media using any formats in the offer that were also present in the answer, and SHOULD use the most preferred format in the offer that was also listed in the answer (assuming the stream allows for sending), and MUST NOT send using any formats that are not in the offer, even if they were present in a previous SDP from the peer. Similarly, when the offerer receives the answer, it MUST begin sending media using any formats in the answer, and SHOULD use the most preferred one (assuming the stream allows for sending), and MUST NOT send using any formats that are not in the answer, even if they were present in a previous SDP from the peer.
Соответствующий медиапоток в ответе формируется, как описано в разделе 6, и также может привести к изменению форматов медиа. Аналогично, как описано в разделе 6, как только отвечающий отправит свой ответ, он ДОЛЖЕН начать отправлять медиа с использованием любых форматов из предложения, которые также присутствовали в ответе, и СЛЕДУЕТ использовать наиболее предпочтительный формат в предложении, который также был указан в ответе (предполагая, что поток позволяет отправку), и НЕ ДОЛЖЕН отправлять с использованием любых форматов, которых нет в предложении, даже если они присутствовали в предыдущем SDP от партнёра. Аналогично, когда предлагающий получает ответ, он ДОЛЖЕН начать отправлять медиа с использованием любых форматов в ответе и СЛЕДУЕТ использовать наиболее предпочтительный из них (предполагая, что поток позволяет отправку), и НЕ ДОЛЖЕН отправлять с использованием любых форматов, которых нет в ответе, даже если они присутствовали в предыдущем SDP от партнёра.
When an agent ceases using a media format (by not listing that format in an offer or answer, even though it was in a previous SDP) the agent will still need to be prepared to receive media with that format for a brief time. How does it know when it can be prepared to stop receiving with that format? If it needs to know, there are three techniques that can be applied. First, the agent can change ports in addition to changing formats. When media arrives on the new port, it knows that the peer has ceased sending with the old format, and it can cease being prepared to receive with it. This approach has the benefit of being media format independent. However, changes in ports may require changes in resource reservation or rekeying of security protocols. The second approach is to use a totally new set of dynamic payload types for all codecs when one is discarded. When media is received with one of the new payload types, the agent knows that the peer has ceased sending with the old format. This approach doesn't affect reservations or security contexts, but it is RTP specific and wasteful of a very small payload type space. A third approach is to use a timer. When the SDP from the peer is received, the timer is set. When it fires, the agent can cease being prepared to receive with the old format. A value of one minute would typically be more than sufficient.
Когда агент прекращает использовать формат медиа (не указывая этот формат в предложении или ответе, хотя он был в предыдущем SDP), агенту всё равно потребуется быть готовым принимать медиа с этим форматом в течение короткого времени. Как он узнаёт, когда можно прекратить приём с этим форматом? Если ему нужно это знать, можно применить три способа. Во-первых, агент может изменить порты в дополнение к изменению форматов. Когда медиа приходят на новый порт, он знает, что партнёр прекратил отправлять со старым форматом, и он может перестать быть готовым принимать с ним. Этот подход имеет преимущество независимости от формата медиа. Однако изменения портов могут потребовать изменений в резервировании ресурсов или перегенерации ключей протоколов безопасности. Второй подход состоит в использовании полностью нового набора динамических типов полезной нагрузки для всех кодеков при отбрасывании одного из них. Когда медиа принимаются с одним из новых типов полезной нагрузки, агент знает, что партнёр прекратил отправлять со старым форматом. Этот подход не влияет на резервирования или контексты безопасности, но он специфичен для RTP и расточителен в отношении очень небольшого пространства типов полезной нагрузки. Третий подход — использование таймера. Когда SDP от партнёра получен, таймер устанавливается. Когда он срабатывает, агент может перестать быть готовым принимать со старым форматом. Значения в одну минуту обычно более чем достаточно.
In some cases, an agent may not care, and thus continually be prepared to receive with the old formats. Nothing need be done in this case.
В некоторых случаях агенту может быть безразлично, и он будет постоянно готов принимать со старыми форматами. В этом случае ничего делать не нужно.
Of course, if the offered stream is rejected, the offer can cease being prepared to receive using any new formats as soon as the rejection is received.
Разумеется, если предложенный поток отклонён, предлагающий может прекратить готовность принимать с использованием любых новых форматов сразу после получения отказа.
8.3.3. Changing Media Types
8.3.3. Изменение типов медиа
The media type (audio, video, etc.) for a stream MAY be changed. It is RECOMMENDED that the media type be changed (as opposed to adding a new stream), when the same logical data is being conveyed, but just in a different media format. This is particularly useful for changing between voiceband fax and fax in a single stream, which are both separate media types. To do this, the offerer creates a new media description, with a new media type, in place of the description in the previous SDP which is to be changed.
Тип медиа (аудио, видео и т. д.) для потока МОЖЕТ быть изменён. РЕКОМЕНДУЕТСЯ изменять тип медиа (в отличие от добавления нового потока), когда передаются те же логические данные, но лишь в другом формате медиа. Это особенно полезно при переключении между факсом в голосовой полосе и факсом в одном потоке, которые являются разными типами медиа. Для этого предлагающий создаёт новое описание медиа с новым типом медиа вместо описания в предыдущем SDP, которое нужно изменить.
The corresponding media stream in the answer is formulated as described in Section 6. Assuming the stream is acceptable, the answerer SHOULD begin sending with the new media type and formats as soon as it receives the offer. The offerer MUST be prepared to receive media with both the old and new types until the answer is received, and media with the new type is received and reaches the top of the playout buffer.
Соответствующий медиапоток в ответе формируется, как описано в разделе 6. При условии, что поток приемлем, отвечающему СЛЕДУЕТ начать отправку с новым типом медиа и форматами, как только он получит предложение. Предлагающий ДОЛЖЕН быть готов принимать медиа как со старым, так и с новым типами до получения ответа и до того, как медиа с новым типом придут и достигнут вершины буфера воспроизведения.
8.3.4. Changing Attributes
8.3.4. Изменение атрибутов
Any other attributes in a media description MAY be updated in an offer or answer. Generally, an agent MUST send media (if the directionality of the stream allows) using the new parameters once the SDP with the change is received.
Любые другие атрибуты в описании медиа МОГУТ быть обновлены в предложении или ответе. В общем случае агент ДОЛЖЕН отправлять медиа (если направленность потока это позволяет) с использованием новых параметров после получения SDP с изменением.
8.4. Putting a Unicast Media Stream on Hold
8.4. Постановка одноадресного медиапотока на удержание
If a party in a call wants to put the other party "on hold", i.e., request that it temporarily stops sending one or more unicast media streams, a party offers the other an updated SDP.
Если сторона в вызове хочет поставить другую сторону «на удержание», то есть попросить её временно прекратить отправку одного или нескольких одноадресных медиапотоков, сторона предлагает другой обновлённый SDP.
If the stream to be placed on hold was previously a sendrecv media stream, it is placed on hold by marking it as sendonly. If the stream to be placed on hold was previously a recvonly media stream, it is placed on hold by marking it inactive.
Если поток, который нужно поставить на удержание, ранее был медиапотоком sendrecv, он ставится на удержание путём пометки его как sendonly. Если поток, который нужно поставить на удержание, ранее был медиапотоком recvonly, он ставится на удержание путём пометки его как inactive.
This means that a stream is placed "on hold" separately in each direction. Each stream is placed "on hold" independently. The recipient of an offer for a stream on-hold SHOULD NOT automatically return an answer with the corresponding stream on hold. An SDP with all streams "on hold" is referred to as held SDP.
Это означает, что поток ставится «на удержание» отдельно в каждом направлении. Каждый поток ставится «на удержание» независимо. Получатель предложения о потоке на удержании НЕ ДОЛЖЕН автоматически возвращать ответ с соответствующим потоком на удержании. SDP со всеми потоками «на удержании» называется удерживающим SDP.
Certain third party call control scenarios do not work when an answerer responds to held SDP with held SDP.
Некоторые сценарии управления вызовом третьей стороной не работают, когда отвечающий отвечает на удерживающий SDP удерживающим SDP.
Typically, when a user "presses" hold, the agent will generate an offer with all streams in the SDP indicating a direction of sendonly, and it will also locally mute, so that no media is sent to the far end, and no media is played out.
Обычно, когда пользователь «нажимает» удержание, агент формирует предложение со всеми потоками в SDP, указывающими направление sendonly, а также локально отключает звук, так что медиа не отправляются на дальний конец и не воспроизводятся.
RFC 2543 [10] specified that placing a user on hold was accomplished by setting the connection address to 0.0.0.0. Its usage for putting a call on hold is no longer recommended, since it doesn't allow for RTCP to be used with held streams, doesn't work with IPv6, and breaks with connection oriented media. However, it can be useful in an initial offer when the offerer knows it wants to use a particular set of media streams and formats, but doesn't know the addresses and ports at the time of the offer. Of course, when used, the port number MUST NOT be zero, which would specify that the stream has been disabled. An agent MUST be capable of receiving SDP with a connection address of 0.0.0.0, in which case it means that neither RTP nor RTCP should be sent to the peer.
RFC 2543 [10] определял, что постановка пользователя на удержание выполняется установкой адреса соединения в 0.0.0.0. Его использование для постановки вызова на удержание больше не рекомендуется, поскольку оно не позволяет использовать RTCP с удерживаемыми потоками, не работает с IPv6 и нарушается при медиа, ориентированных на соединение. Однако он может быть полезен в начальном предложении, когда предлагающий знает, что хочет использовать конкретный набор медиапотоков и форматов, но не знает адресов и портов на момент предложения. Разумеется, при использовании номер порта НЕ ДОЛЖЕН быть нулём, что указывало бы на отключённый поток. Агент ДОЛЖЕН быть способен принимать SDP с адресом соединения 0.0.0.0, и в этом случае он означает, что ни RTP, ни RTCP не должны отправляться партнёру.
9. Indicating Capabilities
9. Указание возможностей
Before an agent sends an offer, it is helpful to know if the media formats in that offer would be acceptable to the answerer. Certain protocols, like SIP, provide a means to query for such capabilities. SDP can be used in responses to such queries to indicate capabilities. This section describes how such an SDP message is formatted. Since SDP has no way to indicate that the message is for the purpose of capability indication, this is determined from the context of the higher layer protocol. The ability of baseline SDP to indicate capabilities is very limited. It cannot express allowed parameter ranges or values, and can not be done in parallel with an offer/answer itself. Extensions might address such limitations in the future.
Прежде чем агент отправит предложение, полезно знать, будут ли форматы медиа в этом предложении приемлемы для отвечающего. Некоторые протоколы, такие как SIP, предоставляют средство запроса таких возможностей. SDP может использоваться в ответах на такие запросы для указания возможностей. В этом разделе описывается, как форматируется такое сообщение SDP. Поскольку SDP не имеет способа указать, что сообщение предназначено для указания возможностей, это определяется из контекста протокола более высокого уровня. Возможность базового SDP указывать возможности очень ограничена. Он не может выражать допустимые диапазоны или значения параметров и не может выполняться параллельно с самим обменом «предложение/ответ». Расширения могли бы устранить такие ограничения в будущем.
An SDP constructed to indicate media capabilities is structured as follows. It MUST be a valid SDP, except that it MAY omit both "e=" and "p=" lines. The "t=" line MUST be equal to "0 0". For each media type supported by the agent, there MUST be a corresponding media description of that type. The session ID in the origin field MUST be unique for each SDP constructed to indicate media capabilities. The port MUST be set to zero, but the connection address is arbitrary. The usage of port zero makes sure that an SDP formatted for capabilities does not cause media streams to be established if it is interpreted as an offer or answer.
SDP, сформированный для указания возможностей медиа, структурирован следующим образом. Он ДОЛЖЕН быть допустимым SDP, за исключением того, что он МОЖЕТ опускать обе строки «e=» и «p=». Строка «t=» ДОЛЖНА быть равна «0 0». Для каждого типа медиа, поддерживаемого агентом, ДОЛЖНО быть соответствующее описание медиа этого типа. Идентификатор сессии в поле origin ДОЛЖЕН быть уникальным для каждого SDP, сформированного для указания возможностей медиа. Порт ДОЛЖЕН быть установлен в ноль, но адрес соединения произволен. Использование нулевого порта гарантирует, что SDP, сформированный для указания возможностей, не приведёт к установлению медиапотоков, если он будет интерпретирован как предложение или ответ.
The transport component of the "m=" line indicates the transport for that media type. For each media format of that type supported by the agent, there SHOULD be a media format listed in the "m=" line. In the case of RTP, if dynamic payload types are used, an rtpmap attribute MUST be present to bind the type to a specific format. There is no way to indicate constraints, such as how many simultaneous streams can be supported for a particular codec, and so on.
Компонент транспорта строки «m=» указывает транспорт для этого типа медиа. Для каждого формата медиа этого типа, поддерживаемого агентом, в строке «m=» СЛЕДУЕТ указывать формат медиа. В случае RTP, если используются динамические типы полезной нагрузки, атрибут rtpmap ДОЛЖЕН присутствовать для привязки типа к конкретному формату. Нет способа указать ограничения, например сколько одновременных потоков может поддерживаться для конкретного кодека, и т. д.
v=0 o=carol 28908764872 28908764872 IN IP4 100.3.6.6 s=- t=0 0 c=IN IP4 192.0.2.4 m=audio 0 RTP/AVP 0 1 3 a=rtpmap:0 PCMU/8000 a=rtpmap:1 1016/8000 a=rtpmap:3 GSM/8000 m=video 0 RTP/AVP 31 34 a=rtpmap:31 H261/90000 a=rtpmap:34 H263/90000

The SDP of Figure 1 indicates that the agent can support three audio codecs (PCMU, 1016, and GSM) and two video codecs (H.261 and H.263).

10. Примеры обменов «предложение/ответ»
This section provides example offer/answer exchanges.
В этом разделе приведены примеры обменов «предложение/ответ».

10.1. Базовый обмен

10.2. One of N Codec Selection
10.2. Выбор одного из N кодеков
A common occurrence in embedded phones is that the Digital Signal Processor (DSP) used for compression can support multiple codecs at a time, but once that codec is selected, it cannot be readily changed on the fly. This example shows how a session can be set up using an initial offer/answer exchange, followed immediately by a second one to lock down the set of codecs.
Обычная ситуация во встроенных телефонах состоит в том, что цифровой сигнальный процессор (DSP), используемый для сжатия, может поддерживать несколько кодеков одновременно, но после выбора кодека его нельзя легко изменить на лету. Этот пример показывает, как можно установить сессию с использованием начального обмена предложение/ответ, за которым сразу следует второй, фиксирующий набор кодеков.
The initial offer from Alice to Bob indicates a single audio stream with the three audio codecs that are available in the DSP. The stream is marked as inactive, since media cannot be received until a codec is locked down:
Начальное предложение от Алисы к Бобу указывает один аудиопоток с тремя аудиокодеками, доступными в DSP. Поток помечен как inactive, поскольку медиа не могут приниматься до тех пор, пока кодек не будет зафиксирован:
v=0 o=alice 2890844526 2890844526 IN IP4 host.anywhere.com s= c=IN IP4 host.anywhere.com t=0 0 m=audio 62986 RTP/AVP 0 4 18 a=rtpmap:0 PCMU/8000 a=rtpmap:4 G723/8000 a=rtpmap:18 G729/8000 a=inactive Bob can support dynamic switching between PCMU and G.723. So, he sends the following answer:

v=0 o=bob 2890844730 2890844731 IN IP4 host.example.com s= c=IN IP4 host.example.com t=0 0 m=audio 54344 RTP/AVP 0 4 a=rtpmap:0 PCMU/8000 a=rtpmap:4 G723/8000 a=inactive
Alice can then select any one of these two codecs. So, she sends an updated offer with a sendrecv stream:
Затем Алиса может выбрать любой из этих двух кодеков. Поэтому она отправляет обновлённое предложение с потоком sendrecv:
v=0 o=alice 2890844526 2890844527 IN IP4 host.anywhere.com s= c=IN IP4 host.anywhere.com t=0 0 m=audio 62986 RTP/AVP 4 a=rtpmap:4 G723/8000 a=sendrecv

Bob accepts the single codec:
Боб принимает единственный кодек:

v=0 o=bob 2890844730 2890844732 IN IP4 host.example.com s= c=IN IP4 host.example.com t=0 0 m=audio 54344 RTP/AVP 4 a=rtpmap:4 G723/8000 a=sendrecv
If the answerer (Bob), was only capable of supporting one-of-N codecs, Bob would select one of the codecs from the offer, and place that in his answer. In this case, Alice would do a re-INVITE to activate that stream with that codec.
Если бы отвечающий (Боб) был способен поддерживать только один из N кодеков, Боб выбрал бы один из кодеков предложения и поместил бы его в свой ответ. В этом случае Алиса выполнила бы re-INVITE, чтобы активировать этот поток с этим кодеком.
As an alternative to using "a=inactive" in the first exchange, Alice can list all codecs, and as soon as she receives media from Bob, generate an updated offer locking down the codec to the one just received. Of course, if Bob only supports one-of-N codecs, there would only be one codec in his answer, and in this case, there is no need for a re-INVITE to lock down to a single codec.
В качестве альтернативы использованию «a=inactive» в первом обмене Алиса может перечислить все кодеки и, как только получит медиа от Боба, сформировать обновлённое предложение, фиксирующее кодек на том, который только что был получен. Разумеется, если Боб поддерживает только один из N кодеков, в предложении Алисы был бы только один.
11. Security Considerations
11. Вопросы безопасности
There are numerous attacks possible if an attacker can modify offers or answers in transit. Generally, these include diversion of media streams (enabling eavesdropping), disabling of calls, and injection of unwanted media streams. If a passive listener can construct fake offers, and inject those into an exchange, similar attacks are possible. Even if an attacker can simply observe offers and answers, they can inject media streams into an existing conversation.
Возможно множество атак, если злоумышленник может изменять предложения или ответы при передаче. Как правило, они включают отвод медиапотоков (что позволяет подслушивание), отключение вызовов и внедрение нежелательных медиапотоков. Если пассивный слушатель может сформировать поддельные предложения и внедрить их в обмен, возможны аналогичные атаки. Даже если злоумышленник может просто наблюдать предложения и ответы, он может внедрить медиапотоки в существующий разговор.
Offer/answer relies on transport within an application signaling protocol, such as SIP. It also relies on that protocol for security capabilities. Because of the attacks described above, that protocol MUST provide a means for end-to-end authentication and integrity protection of offers and answers. It SHOULD offer encryption of bodies to prevent eavesdropping. However, media injection attacks can alternatively be resolved through authenticated media exchange, and therefore the encryption requirement is a SHOULD instead of a MUST.
Модель «предложение/ответ» полагается на транспорт в рамках протокола сигнализации приложения, такого как SIP. Она также полагается на этот протокол в части возможностей безопасности. Из-за описанных выше атак этот протокол ДОЛЖЕН обеспечивать средство сквозной аутентификации и защиты целостности предложений и ответов. Ему СЛЕДУЕТ предлагать шифрование тел для предотвращения подслушивания. Однако атаки внедрения медиа могут быть в качестве альтернативы решены посредством аутентифицированного обмена медиа, и потому требование шифрования — это СЛЕДУЕТ, а не ДОЛЖЕН.
Replay attacks are also problematic. An attacker can replay an old offer, perhaps one that had put media on hold, and thus disable media streams in a conversation. Therefore, the application protocol MUST provide a secure way to sequence offers and answers, and to detect and reject old offers or answers.
Атаки повторного воспроизведения также проблематичны. Злоумышленник может воспроизвести старое предложение, возможно то, которое поставило медиа на удержание, и тем самым отключить медиапотоки в разговоре. Поэтому протокол приложения ДОЛЖЕН обеспечивать защищённый способ упорядочения предложений и ответов, а также обнаружения и отклонения старых предложений или ответов.
SIP [7] meets all of these requirements.
SIP [7] удовлетворяет всем этим требованиям.
