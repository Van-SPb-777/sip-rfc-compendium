3. Digest Access Authentication Scheme
3. Схема дайджест-аутентификации доступа
3.1. Overall Operation
3.1. Общий порядок работы
The Digest scheme is based on a simple challenge-response paradigm. The Digest scheme challenges using a nonce value and might indicate that username hashing is supported. A valid response contains an unkeyed digest of the username, the password, the given nonce value, the HTTP method, and the requested URI. In this way, the password is never sent in the clear, and the username can be hashed, depending on the indication received from the server. The username and password must be prearranged in some fashion not addressed by this document.
Схема Digest основана на простой парадигме «запрос-ответ». Схема Digest выдаёт запрос с использованием значения нонса и может указывать, что поддерживается хеширование имени пользователя. Корректный ответ содержит дайджест без ключа от имени пользователя, пароля, заданного значения нонса, метода HTTP и запрошенного URI. Таким образом, пароль никогда не передаётся в открытом виде, а имя пользователя может быть хешировано в зависимости от указания, полученного от сервера. Имя пользователя и пароль должны быть согласованы заранее некоторым способом, не рассматриваемым в настоящем документе.
3.2. Representation of Digest Values
3.2. Представление значений дайджеста
An optional header field allows the server to specify the algorithm used to create the unkeyed digest or digest. This document adds SHA-256 and SHA-512/256 algorithms. To maintain backwards compatibility with [RFC2617], the MD5 algorithm is still supported but NOT RECOMMENDED.
Необязательное поле заголовка позволяет серверу указать алгоритм, используемый для создания дайджеста без ключа или дайджеста. Настоящий документ добавляет алгоритмы SHA-256 и SHA-512/256. Для сохранения обратной совместимости с [RFC2617] алгоритм MD5 по-прежнему поддерживается, но НЕ РЕКОМЕНДУЕТСЯ.
The size of the digest depends on the algorithm used. The bits in the digest are converted from the most significant to the least significant bit, four bits at a time, to the ASCII representation as follows. Each sequence of four bits is represented by its familiar hexadecimal notation from the characters 0123456789abcdef; that is, binary 0000 is represented by the character '0', 0001 by '1' and so on up to the representation of 1111 as 'f'. If the MD5 algorithm is used to calculate the digest, then the MD5 digest will be represented as 32 hexadecimal characters, while SHA-256 and SHA-512/256 are represented as 64 hexadecimal characters.
Размер дайджеста зависит от используемого алгоритма. Биты дайджеста преобразуются от старшего к младшему по четыре бита за раз в представление ASCII следующим образом. Каждая последовательность из четырёх битов представляется своей привычной шестнадцатеричной записью из символов 0123456789abcdef; то есть двоичное 0000 представляется символом '0', 0001 — символом '1' и так далее вплоть до представления 1111 как 'f'. Если для вычисления дайджеста применяется алгоритм MD5, то дайджест MD5 будет представлен 32 шестнадцатеричными символами, тогда как SHA-256 и SHA-512/256 представляются 64 шестнадцатеричными символами.

Содержимое нонса зависит от реализации. Качество реализации зависит от удачного выбора. Нонс мог бы, например, быть построен как кодировка Base64 от

where timestamp is a server-generated time, which preferably includes micro- or nanoseconds, or other non-repeating values; ETag is the value of the HTTP ETag header field associated with the requested entity; and secret-data is data known only to the server. With a nonce of this form, a server would recalculate the hash portion after receiving the client authentication header field and reject the request if it did not match the nonce from that header field or if the timestamp value is not recent enough. In this way, the server can limit the time of the nonce's validity. The inclusion of the ETag prevents a replay request for an updated version of the resource. Including the IP address of the client in the nonce would appear to offer the server the ability to limit the reuse of the nonce to the same client that originally got it. However, that would break because requests from a single user often go through different proxies. Also, IP address spoofing is not that hard.
где timestamp — сгенерированное сервером время, которое предпочтительно включает микро- или наносекунды или иные неповторяющиеся значения; ETag — значение поля заголовка HTTP ETag, связанного с запрошенным объектом; а secret-data — данные, известные только серверу. Однако это не будет работать, потому что запросы от одного пользователя часто проходят через разные прокси. Кроме того, подмена IP-адреса не так уж сложна.
An implementation might choose not to accept a previously used nonce or a previously used digest, in order to protect against a replay attack. stale
stale
A case-insensitive flag indicating that the previous request from the client was rejected because the nonce value was stale. If stale is true, the client may wish to simply retry the request with a new encrypted response, without re-prompting the user for a new username and password. The server SHOULD only set stale to true if it receives a request for which the nonce is invalid. If stale is false, or anything other than true, or the stale parameter is not present, the username and/or password are invalid, and new values MUST be obtained.
Флаг, нечувствительный к регистру, указывающий, что предыдущий запрос клиента был отклонён, поскольку значение нонса устарело. Если stale имеет значение true, клиент может пожелать просто повторить запрос с новым зашифрованным ответом, не запрашивая у пользователя новые имя пользователя и пароль. Серверу СЛЕДУЕТ устанавливать stale в true, только если он получает запрос, для которого нонс недействителен. Если stale равно false, или чему-либо иному, кроме true, или параметр stale отсутствует, имя пользователя и (или) пароль недействительны, и ДОЛЖНЫ быть получены новые значения.

algorithm

Строка, указывающая алгоритм, используемый для создания дайджеста и дайджеста без ключа. Если она отсутствует, предполагается «MD5». Если алгоритм не понят, запрос СЛЕДУЕТ игнорировать (и использовать другой, если их более одного).
When used with the Digest mechanism, each one of the algorithms has two variants: Session variant and non-Session variant. The non-Session variant is denoted by "<algorithm>", e.g., "SHA-256", and the Session variant is denoted by "<algorithm>-sess", e.g., "SHA-256-sess".
При использовании с механизмом Digest каждый из алгоритмов имеет два варианта: сеансовый вариант и несеансовый вариант. Несеансовый вариант обозначается как «<algorithm>», например «SHA-256», а сеансовый вариант обозначается как «<algorithm>-sess», например «SHA-256-sess».
In this document, the string obtained by applying the digest algorithm to the data "data" with secret "secret" will be denoted by KD(secret, data), and the string obtained by applying the unkeyed digest algorithm to the data "data" will be denoted H(data). KD stands for Keyed Digest, and the notation unq(X) means the value of the quoted-string X without the surrounding quotes and with quoting slashes removed.
В настоящем документе строка, получаемая применением алгоритма дайджеста к данным «data» с секретом «secret», будет обозначаться KD(secret, data), а строка, получаемая применением алгоритма дайджеста без ключа к данным «data», будет обозначаться H(data). 3.6. Digest Operation
3.6. Работа схемы Digest
Upon receiving the Authorization header field, the server MAY check its validity by looking up the password that corresponds to the submitted username. Then, the server MUST perform the same digest operation (e.g., MD5, SHA-256) performed by the client and compare the result to the given response value.
Получив поле заголовка Authorization, сервер МОЖЕТ проверить его действительность, найдя пароль, соответствующий предоставленному имени пользователя. Затем сервер ДОЛЖЕН выполнить ту же операцию дайджеста (например, MD5, SHA-256), которую выполнил клиент, и сравнить результат с заданным значением response.
Note that the HTTP server does not actually need to know the user's cleartext password. As long as H(A1) is available to the server, the validity of an Authorization header field can be verified. The client response to a WWW-Authenticate challenge for a protection space starts an authentication session with that protection space. The authentication session lasts until the client receives another WWW-Authenticate challenge from any server in the protection space. A client SHOULD remember the username, password, nonce, nonce count, and opaque values associated with an authentication session to use to construct the Authorization header field in future requests within that protection space. The Authorization header field MAY be included preemptively; doing so improves server efficiency and avoids extra round trips for authentication challenges. The server MAY choose to accept the old Authorization header field information, even though the nonce value included might not be fresh. Alternatively, the server MAY return a 401 response with a new nonce value in the WWW-Authenticate header field, causing the client to retry the request; by specifying "stale=true" with this response, the server tells the client to retry with the new nonce, but without prompting for a new username and password.
Обратите внимание, что HTTP-серверу фактически не нужно знать пароль пользователя в открытом виде. Пока H(A1) доступен серверу, действительность поля заголовка Authorization может быть проверена. Ответ клиента на запрос WWW-Authenticate для пространства защиты начинает сеанс аутентификации с этим пространством защиты. Сеанс аутентификации длится до тех пор, пока клиент не получит другой запрос WWW-Authenticate от любого сервера в пространстве защиты. Клиенту СЛЕДУЕТ запоминать значения username, password, nonce, nonce count и opaque, связанные с сеансом аутентификации, чтобы использовать их для построения поля заголовка Authorization в будущих запросах в пределах этого пространства защиты. Поле заголовка Authorization МОЖЕТ включаться упреждающе; это повышает эффективность сервера и позволяет избежать дополнительных круговых обменов для запросов аутентификации. Сервер МОЖЕТ по своему выбору принимать информацию из старого поля заголовка Authorization, даже если включённое в него значение нонса может быть не новым. Либо сервер МОЖЕТ вернуть ответ 401 с новым значением нонса в поле заголовка WWW-Authenticate, заставляя клиента повторить запрос; указывая «stale=true» с этим ответом, сервер сообщает клиенту о необходимости повторить запрос с новым нонсом, но без запроса новых имени пользователя и пароля.
Because the client is required to return the value of the opaque parameter given to it by the server for the duration of a session, the opaque data can be used to transport authentication session state information. (Note that any such use can also be accomplished more easily and safely by including the state in the nonce.) For example, a server could be responsible for authenticating content that actually sits on another server. It would achieve this by having the first 401 response include a domain parameter whose value includes a URI on the second server, and an opaque parameter whose value contains the state information. The client will retry the request, at which time the server might respond with "HTTP Redirection" (Section 6.4 of [RFC7231]), pointing to the URI on the second server. The client will follow the redirection and pass an Authorization header field, including the <opaque> data.
Поскольку клиент обязан возвращать значение параметра opaque, данное ему сервером, на протяжении всего сеанса, данные opaque могут использоваться для передачи информации о состоянии сеанса аутентификации. (Обратите внимание, что любое такое использование можно также осуществить проще и безопаснее, включив состояние в нонс.) Например, сервер мог бы отвечать за аутентификацию содержимого, которое фактически находится на другом сервере. Он достиг бы этого, включив в первый ответ 401 параметр domain, значение которого включает URI на втором сервере, и параметр opaque, значение которого содержит информацию о состоянии. Клиент повторит запрос, и в этот момент сервер может ответить «HTTP Redirection» (раздел 6.4 документа [RFC7231]), указывая на URI на втором сервере. Клиент проследует перенаправлению и передаст поле заголовка Authorization, включая данные <opaque>.
Proxies MUST be completely transparent in the Digest access authentication scheme. That is, they MUST forward the WWW- Authenticate, Authentication-Info, and Authorization header fields untouched. If a proxy wants to authenticate a client before a request is forwarded to the server, it can be done using the Proxy- Authenticate and Proxy-Authorization header fields described in Section 3.8 below.
Прокси ДОЛЖНЫ быть полностью прозрачны в схеме дайджест-аутентификации доступа. То есть они ДОЛЖНЫ пересылать поля заголовков WWW-Authenticate, Authentication-Info и Authorization без изменений. Если прокси хочет аутентифицировать клиента до пересылки запроса на сервер, это можно сделать с помощью полей заголовков Proxy-Authenticate и Proxy-Authorization, описанных в разделе 3.8 ниже.
3.7. Security Protocol Negotiation
3.7. Согласование протокола безопасности
It is useful for a server to be able to know which security schemes a client is capable of handling.
Серверу полезно уметь определять, какие схемы безопасности клиент способен обрабатывать.
It is possible that a server wants to require Digest as its authentication method, even if the server does not know that the client supports it. A client is encouraged to fail gracefully if the server specifies only authentication schemes it cannot handle.
Возможно, что сервер хочет требовать Digest в качестве своего метода аутентификации, даже если сервер не знает, что клиент его поддерживает. Клиенту рекомендуется корректно завершать работу, если сервер указывает только схемы аутентификации, которые он не может обработать.
When a server receives a request to access a resource, the server might challenge the client by responding with "401 Unauthorized" response and include one or more WWW-Authenticate header fields. If the server responds with multiple challenges, then each one of these challenges MUST use a different digest algorithm. The server MUST add these challenges to the response in order of preference, starting with the most preferred algorithm, followed by the less preferred algorithm.
Когда сервер получает запрос на доступ к ресурсу, сервер может запросить у клиента аутентификацию, ответив ответом «401 Unauthorized» и включив одно или несколько полей заголовка WWW-Authenticate. Если сервер отвечает несколькими запросами, то каждый из этих запросов ДОЛЖЕН использовать другой алгоритм дайджеста. Сервер ДОЛЖЕН добавлять эти запросы в ответ в порядке предпочтения, начиная с наиболее предпочтительного алгоритма, за которым следует менее предпочтительный алгоритм.
This specification defines the following algorithms:
Настоящая спецификация определяет следующие алгоритмы:
o SHA2-256 (mandatory to implement)
o SHA2-256 (обязателен к реализации)
o SHA2-512/256 (as a backup algorithm)
o SHA2-512/256 (как резервный алгоритм)
o MD5 (for backward compatibility).
o MD5 (для обратной совместимости).
When the client receives the first challenge, it SHOULD use the first challenge it supports, unless a local policy dictates otherwise.
Когда клиент получает первый запрос, ему СЛЕДУЕТ использовать первый запрос, который он поддерживает, если только локальная политика не диктует иное.
3.8. Proxy-Authenticate and Proxy-Authorization
3.8. Proxy-Authenticate и Proxy-Authorization
The Digest Authentication scheme can also be used for authenticating users to proxies, proxies to proxies, or proxies to origin servers by use of the Proxy-Authenticate and Proxy-Authorization header fields. These header fields are instances of the Proxy-Authenticate and Proxy-Authorization header fields specified in Sections 4.3 and 4.4 of the HTTP/1.1 specification [RFC7235], and their behavior is subject to restrictions described there. The transactions for proxy authentication are very similar to those already described. Upon receiving a request that requires authentication, the proxy/server MUST issue the "407 Proxy Authentication Required" response with a "Proxy-Authenticate" header field. The digest-challenge used in the Proxy-Authenticate header field is the same as that for the WWW- Authenticate header field as defined above in Section 3.3.
Схема дайджест-аутентификации также может использоваться для аутентификации пользователей на прокси, прокси на прокси или прокси на исходных серверах с помощью полей заголовков Proxy-Authenticate и Proxy-Authorization. Эти поля заголовков являются экземплярами полей заголовков Proxy-Authenticate и Proxy-Authorization, определённых в разделах 4.3 и 4.4 спецификации HTTP/1.1 [RFC7235], и их поведение подпадает под ограничения, описанные там. Транзакции для аутентификации прокси очень похожи на уже описанные. Получив запрос, требующий аутентификации, прокси (сервер) ДОЛЖЕН выдать ответ «407 Proxy Authentication Required» с полем заголовка «Proxy-Authenticate». Дайджест-запрос, используемый в поле заголовка Proxy-Authenticate, совпадает с таковым для поля заголовка WWW-Authenticate, как определено выше в разделе 3.3.
The client/proxy MUST then reissue the request with a Proxy- Authorization header field, with parameters as specified for the Authorization header field in Section 3.4 above.
Затем клиент (прокси) ДОЛЖЕН повторно выдать запрос с полем заголовка Proxy-Authorization с параметрами, указанными для поля заголовка Authorization в разделе 3.4 выше.
On subsequent responses, the server sends Proxy-Authentication-Info with parameters the same as those for the Authentication-Info header field.
При последующих ответах сервер отправляет Proxy-Authentication-Info с параметрами, такими же, как для поля заголовка Authentication-Info.
Note that, in principle, a client could be asked to authenticate itself to both a proxy and an end-server, but never in the same response.
Обратите внимание, что в принципе у клиента может быть запрошена аутентификация как на прокси, так и на конечном сервере, но никогда в одном и том же ответе.

5. Security Considerations
5. Соображения безопасности
5.1. Limitations
5.1. Ограничения
HTTP Digest Authentication, when used with human-memorable passwords, is vulnerable to dictionary attacks. Such attacks are much easier than cryptographic attacks on any widely used algorithm, including those that are no longer considered secure. In other words, algorithm agility does not make this usage any more secure.
Дайджест-аутентификация HTTP при использовании с запоминаемыми человеком паролями уязвима к атакам по словарю. Такие атаки намного проще, чем криптографические атаки на любой широко используемый алгоритм, включая те, которые больше не считаются безопасными. Иными словами, гибкость выбора алгоритма не делает такое использование сколько-нибудь безопаснее.
As a result, Digest Authentication SHOULD be used only with passwords that have a reasonable amount of entropy, e.g., 128-bit or more. Such passwords typically cannot be memorized by humans but can be used for automated web services.
В результате дайджест-аутентификацию СЛЕДУЕТ использовать только с паролями, имеющими разумное количество энтропии, например 128 бит или более. Такие пароли обычно не могут быть запомнены человеком, но могут использоваться для автоматизированных веб-служб.
If Digest Authentication is being used, it SHOULD be over a secure channel like HTTPS [RFC2818].
Если дайджест-аутентификация используется, ей СЛЕДУЕТ применяться поверх защищённого канала, такого как HTTPS [RFC2818].
5.2. Storing Passwords
5.2. Хранение паролей
Digest Authentication requires that the authenticating agent (usually the server) store some data derived from the user's name and password in a "password file" associated with a given realm. Normally, this might contain pairs consisting of username and H(A1), where H(A1) is the digested value of the username, realm, and password as described above.
Дайджест-аутентификация требует, чтобы агент, выполняющий аутентификацию (обычно сервер), хранил некоторые данные, производные от имени и пароля пользователя, в «файле паролей», связанном с данной областью защиты. Обычно он может содержать пары, состоящие из имени пользователя и H(A1), где H(A1) — хешированное значение имени пользователя, области защиты и пароля, как описано выше.
The security implications of this are that if this password file is compromised, then an attacker gains immediate access to documents on the server using this realm. Unlike, say, a standard UNIX password file, this information needs not be decrypted in order to access documents in the server realm associated with this file. On the other hand, decryption, or more likely a brute-force attack, would be necessary to obtain the user's password. This is the reason that the realm is part of the digested data stored in the password file. It means that if one Digest Authentication password file is compromised, it does not automatically compromise others with the same username and password (though it does expose them to brute-force attack).
Связанные с этим последствия для безопасности таковы: если этот файл паролей скомпрометирован, злоумышленник получает немедленный доступ к документам на сервере, использующим эту область защиты. В отличие, скажем, от стандартного файла паролей UNIX, эта информация не требует расшифровки для доступа к документам в области защиты сервера, связанной с этим файлом. С другой стороны, для получения пароля пользователя потребовалась бы расшифровка или, что более вероятно, атака методом перебора. Именно поэтому область защиты является частью хешированных данных, хранимых в файле паролей. Это означает, что если один файл паролей дайджест-аутентификации скомпрометирован, это не автоматически компрометирует другие с тем же именем пользователя и паролем (хотя и подвергает их атаке методом перебора).
There are two important security consequences of this. First, the password file must be protected as if it contained unencrypted passwords, because, for the purpose of accessing documents in its realm, it effectively does.
Отсюда следуют два важных последствия для безопасности. Во-первых, файл паролей должен быть защищён так, как если бы он содержал незашифрованные пароли, потому что для целей доступа к документам в его области защиты он фактически их содержит.
A second consequence of this is that the realm string SHOULD be unique among all realms that any single user is likely to use. In particular, a realm string SHOULD include the name of the host doing the authentication. The inability of the client to authenticate the server is a weakness of Digest Authentication.
Второе следствие состоит в том, что строка realm ДОЛЖНА быть уникальной среди всех областей защиты, которые может использовать какой-либо отдельный пользователь. В частности, строка realm ДОЛЖНА включать имя хоста, выполняющего аутентификацию. Невозможность для клиента аутентифицировать сервер является слабостью дайджест-аутентификации.
5.3. Authentication of Clients Using Digest Authentication
5.3. Аутентификация клиентов с использованием дайджест-аутентификации
Digest Authentication does not provide a strong authentication mechanism, when compared to public-key-based mechanisms, for example.
Дайджест-аутентификация не обеспечивает сильный механизм аутентификации по сравнению, например, с механизмами на основе открытых ключей.
However, it is significantly stronger than, e.g., CRAM-MD5, which has been proposed for use with Lightweight Directory Access Protocol (LDAP) [RFC4513] and IMAP/POP (see [RFC2195]). It was intended to replace the much weaker and even more dangerous Basic mechanism.
Однако она значительно сильнее, чем, например, CRAM-MD5, который был предложен для использования с протоколом Lightweight Directory Access Protocol (LDAP) [RFC4513] и IMAP/POP (см. [RFC2195]). Она была предназначена для замены значительно более слабого и ещё более опасного механизма Basic.
Digest Authentication offers no confidentiality protection beyond protecting the actual username and password. All of the rest of the request and response are available to an eavesdropper.
Дайджест-аутентификация не обеспечивает защиты конфиденциальности сверх защиты собственно имени пользователя и пароля. Всё остальное содержимое запроса и ответа доступно подслушивающему.
Digest Authentication offers only limited integrity protection for the messages in either direction. If the "qop=auth-int" mechanism is used, those parts of the message used in the calculation of the WWW- Authenticate and Authorization header field response parameter values (see Section 3.2 above) are protected. Most header fields and their values could be modified as a part of a man-in-the-middle attack.
Дайджест-аутентификация обеспечивает лишь ограниченную защиту целостности сообщений в обоих направлениях. Если используется механизм «qop=auth-int», защищаются те части сообщения, которые используются при вычислении значений параметра response полей заголовков WWW-Authenticate и Authorization (см. раздел 3.2 выше). Большинство полей заголовков и их значений могут быть изменены в рамках атаки «человек посередине».
Many needs for secure HTTP transactions cannot be met by Digest Authentication. For those needs, TLS is a more appropriate protocol. In particular, Digest Authentication cannot be used for any transaction requiring confidentiality protection. Nevertheless, many functions remain for which Digest Authentication is both useful and appropriate.
Многие потребности в защищённых HTTP-транзакциях не могут быть удовлетворены дайджест-аутентификацией. Для таких потребностей более подходящим протоколом является TLS. В частности, дайджест-аутентификация не может использоваться для любой транзакции, требующей защиты конфиденциальности. Тем не менее остаётся много функций, для которых дайджест-аутентификация полезна и уместна.
5.4. Limited-Use Nonce Values
5.4. Нонсы с ограниченным использованием
The Digest scheme uses a server-specified nonce to seed the generation of the response value (as specified in Section 3.4.1 above). As shown in the example nonce in Section 3.3, the server is free to construct the nonce such that it MAY only be used from a particular client, for a particular resource, for a limited period of time or number of uses, or any other restrictions. Doing so strengthens the protection provided against, for example, replay attacks (see Section 5.5). However, it should be noted that the method chosen for generating and checking the nonce also has performance and resource implications. For example, a server MAY choose to allow each nonce value to be used only once by maintaining a record of whether or not each recently issued nonce has been returned and sending a next-nonce parameter in the Authentication- Info header field of every response. This protects against even an immediate replay attack, but it has a high cost due to checking nonce values; perhaps more important, it will cause authentication failures for any pipelined requests (presumably returning a stale nonce indication). Similarly, incorporating a request-specific element such as the ETag value for a resource limits the use of the nonce to that version of the resource and also defeats pipelining. Thus, it MAY be useful to do so for methods with side effects but have unacceptable performance for those that do not.
Схема Digest использует задаваемый сервером нонс для инициализации генерации значения response (как указано в разделе 3.4.1 выше). Как показано в примере нонса в разделе 3.3, сервер свободен строить нонс так, чтобы он МОГ использоваться только от конкретного клиента, для конкретного ресурса, в течение ограниченного периода времени или числа использований либо с любыми другими ограничениями. Это усиливает защиту, например, от атак повторного воспроизведения (см. раздел 5.5). Однако следует отметить, что выбранный способ генерации и проверки нонса также имеет последствия для производительности и ресурсов. Например, сервер МОЖЕТ выбрать разрешение использовать каждое значение нонса только один раз, поддерживая запись о том, возвращён ли каждый недавно выданный нонс, и отправляя параметр next-nonce в поле заголовка Authentication-Info каждого ответа. Это защищает даже от немедленной атаки повторного воспроизведения, но имеет высокую цену из-за проверки значений нонса; возможно, что более важно, это вызовет отказы аутентификации для любых конвейерных запросов (предположительно, возвращая указание устаревшего нонса). Аналогично, включение элемента, специфичного для запроса, такого как значение ETag для ресурса, ограничивает использование нонса этой версией ресурса и также исключает конвейеризацию. Таким образом, это МОЖЕТ быть полезно для методов с побочными эффектами, но иметь неприемлемую производительность для методов без них.
5.5. Replay Attacks
5.5. Атаки повторного воспроизведения
A replay attack against Digest Authentication would usually be pointless for a simple GET request since an eavesdropper would already have seen the only document he could obtain with a replay. This is because the URI of the requested document is digested in the client request, and the server will only deliver that document. By contrast, under Basic Authentication, once the eavesdropper has the user's password, any document protected by that password is open to him.
Атака повторного воспроизведения против дайджест-аутентификации обычно была бы бессмысленной для простого GET-запроса, поскольку подслушивающий уже увидел бы единственный документ, который он мог бы получить с помощью повтора. Это объясняется тем, что URI запрошенного документа хешируется в клиентском запросе, и сервер доставит только этот документ. Напротив, при базовой аутентификации, как только подслушивающий получает пароль пользователя, ему открывается любой документ, защищённый этим паролем.
Thus, for some purposes, it is necessary to protect against replay attacks. A good Digest implementation can do this in various ways. The server-created "nonce" value is implementation dependent, but if it contains a digest of the client IP, a timestamp, the resource ETag, and a private server key (as recommended above), then a replay attack is not simple. An attacker must convince the server that the request is coming from a false IP address and must cause the server to deliver the document to an IP address different from the address to which it believes it is sending the document. An attack can only succeed in the period before the timestamp expires. Digesting the client IP and timestamp in the nonce permits an implementation that does not maintain state between transactions. For applications where no possibility of replay attack can be tolerated, the server can use one-time nonce values that will not be honored for a second use. This requires the overhead of the server remembering which nonce values have been used until the nonce timestamp (and hence the digest built with it) has expired, but it effectively protects against replay attacks.
Таким образом, для некоторых целей необходимо защищаться от атак повторного воспроизведения. Хорошая реализация Digest может делать это разными способами. Создаваемое сервером значение «нонс» зависит от реализации, но если оно содержит дайджест IP-адреса клиента, отметку времени, ETag ресурса и закрытый ключ сервера (как рекомендовано выше), то атака повторного воспроизведения не будет простой. Злоумышленник должен убедить сервер в том, что запрос приходит с ложного IP-адреса, и заставить сервер доставить документ на IP-адрес, отличный от того, на который, как он считает, он отправляет документ. Атака может удаться только в период до истечения срока действия отметки времени. Хеширование IP-адреса клиента и отметки времени в нонсе позволяет реализовать вариант, не поддерживающий состояние между транзакциями. Для приложений, где нельзя допустить никакой возможности атаки повторного воспроизведения, сервер может использовать одноразовые значения нонса, которые не будут приняты при повторном использовании. Это требует накладных расходов на запоминание сервером того, какие значения нонса использовались, до истечения срока действия отметки времени нонса (и, следовательно, построенного с её помощью дайджеста), но это эффективно защищает от атак повторного воспроизведения.
An implementation must give special attention to the possibility of replay attacks with POST and PUT requests. Unless the server employs one-time or otherwise limited-use nonces and/or insists on the use of the integrity protection of "qop=auth-int", an attacker could replay valid credentials from a successful request with counterfeit data or other message body. Even with the use of integrity protection, most metadata in header fields is not protected. Proper nonce generation and checking provides some protection against replay of previously used valid credentials, but see Section 5.8.
Реализация должна уделять особое внимание возможности атак повторного воспроизведения с запросами POST и PUT. Если сервер не применяет одноразовые или иным образом ограниченно используемые нонсы и (или) не настаивает на использовании защиты целостности «qop=auth-int», злоумышленник мог бы повторно использовать допустимые учётные данные из успешного запроса с поддельными данными или иным телом сообщения. Даже при использовании защиты целостности большинство метаданных в полях заголовков не защищены. Надлежащая генерация и проверка нонса обеспечивает некоторую защиту от повтора ранее использованных допустимых учётных данных, но см. раздел 5.8.
5.6. Weakness Created by Multiple Authentication Schemes
5.6. Слабость, создаваемая множественными схемами аутентификации
An HTTP/1.1 server MAY return multiple challenges with a 401 (Authenticate) response, and each challenge MAY use a different auth- scheme. A user agent MUST choose to use the strongest auth-scheme it understands and request credentials from the user based upon that challenge.
Сервер HTTP/1.1 МОЖЕТ возвращать несколько запросов в ответе 401 (Authenticate), и каждый запрос МОЖЕТ использовать другую схему аутентификации. Пользовательский агент ДОЛЖЕН выбрать использование самой сильной схемы аутентификации, которую он понимает, и запросить учётные данные у пользователя на основе этого запроса.
When the server offers choices of authentication schemes using the WWW-Authenticate header field, the strength of the resulting authentication is only as good as that of the of the weakest of the authentication schemes. See Section 5.7 below for discussion of particular attack scenarios that exploit multiple authentication schemes.
Когда сервер предлагает выбор схем аутентификации с помощью поля заголовка WWW-Authenticate, сила результирующей аутентификации не выше, чем у самой слабой из схем аутентификации. Обсуждение конкретных сценариев атак, использующих множественные схемы аутентификации, см. в разделе 5.7 ниже.
5.7. Online Dictionary Attacks
5.7. Онлайновые атаки по словарю
If the attacker can eavesdrop, then it can test any overheard nonce/ response pairs against a list of common words. Such a list is usually much smaller than the total number of possible passwords. The cost of computing the response for each password on the list is paid once for each challenge.
Если злоумышленник может подслушивать, он может проверить любые перехваченные пары «нонс/ответ» по списку распространённых слов. Такой список обычно намного меньше общего числа возможных паролей. Стоимость вычисления ответа для каждого пароля из списка оплачивается один раз для каждого запроса.
The server can mitigate this attack by not allowing users to select passwords that are in a dictionary.
Сервер может смягчить эту атаку, не позволяя пользователям выбирать пароли, которые есть в словаре.
5.8. Man-in-the-Middle Attacks
5.8. Атаки «человек посередине»
Digest Authentication is vulnerable to man-in-the-middle (MITM) attacks, for example, from a hostile or compromised proxy. Clearly, this would present all the problems of eavesdropping. But, it also offers some additional opportunities to the attacker.
Дайджест-аутентификация уязвима к атакам «человек посередине» (MITM), например, со стороны враждебного или скомпрометированного прокси. Очевидно, это создало бы все проблемы подслушивания. Но это также даёт злоумышленнику некоторые дополнительные возможности.
A possible man-in-the-middle attack would be to add a weak authentication scheme to the set of choices, hoping that the client will use one that exposes the user's credentials (e.g., password). For this reason, the client SHOULD always use the strongest scheme that it understands from the choices offered.
Возможной атакой «человек посередине» было бы добавление слабой схемы аутентификации в набор вариантов в надежде, что клиент использует ту, которая раскрывает учётные данные пользователя (например, пароль). По этой причине клиенту СЛЕДУЕТ всегда использовать самую сильную схему, которую он понимает, из предложенных вариантов.
An even better MITM attack would be to remove all offered choices, replacing them with a challenge that requests only Basic authentication, then uses the cleartext credentials from the Basic authentication to authenticate to the origin server using the stronger scheme it requested. A particularly insidious way to mount such a MITM attack would be to offer a "free" proxy caching service to gullible users.
Ещё лучшей атакой MITM было бы удаление всех предложенных вариантов с заменой их запросом, который требует только базовой аутентификации, а затем использование учётных данных в открытом виде из базовой аутентификации для аутентификации на исходном сервере с использованием более сильной схемы, которую он запросил. Особенно коварным способом организации такой атаки MITM было бы предложение доверчивым пользователям «бесплатной» службы кеширования через прокси.
User agents should consider measures such as presenting a visual indication at the time of the credentials request of what authentication scheme is to be used, or remembering the strongest authentication scheme ever requested by a server and producing a warning message before using a weaker one. It might also be a good idea for the user agent to be configured to demand Digest authentication in general or from specific sites.
Пользовательским агентам следует рассматривать такие меры, как показ визуального указания в момент запроса учётных данных о том, какая схема аутентификации будет использоваться, или запоминание самой сильной схемы аутентификации, когда-либо запрошенной сервером, и выдача предупреждающего сообщения перед использованием более слабой. Возможно, также было бы хорошей идеей настроить пользовательский агент на требование дайджест-аутентификации в целом или от конкретных сайтов.
Or, a hostile proxy might spoof the client into making a request the attacker wanted rather than one the client wanted. Of course, this is still much harder than a comparable attack against Basic Authentication.
Либо враждебный прокси мог бы обмануть клиента, заставив его сделать запрос, который хотел злоумышленник, а не тот, который хотел клиент. Конечно, это всё же намного сложнее, чем сопоставимая атака на базовую аутентификацию.

5.10. Precomputed Dictionary Attacks
5.10. Атаки по предвычисленному словарю
With Digest Authentication, if the attacker can execute a chosen plaintext attack, the attacker can precompute the response for many common words to a nonce of its choice and store a dictionary of response/password pairs. Such precomputation can often be done in parallel on many machines. It can then use the chosen plaintext attack to acquire a response corresponding to that challenge and just look up the password in the dictionary. Even if most passwords are not in the dictionary, some might be. Since the attacker gets to pick the challenge, the cost of computing the response for each password on the list can be amortized over finding many passwords. A dictionary with 100 million password/response pairs would take about 3.2 gigabytes of disk storage.
При дайджест-аутентификации, если злоумышленник может выполнить атаку с выбранным открытым текстом, он может предвычислить ответ для многих распространённых слов на выбранный им нонс и сохранить словарь пар «ответ/пароль». Такое предвычисление часто можно выполнить параллельно на многих машинах. Затем он может использовать атаку с выбранным открытым текстом, чтобы получить ответ, соответствующий этому запросу, и просто найти пароль в словаре. Даже если большинства паролей нет в словаре, некоторые могут там быть. Поскольку злоумышленник сам выбирает запрос, стоимость вычисления ответа для каждого пароля из списка можно амортизировать за счёт нахождения многих паролей. Словарь со 100 миллионами пар «пароль/ответ» занял бы около 3,2 гигабайта дискового пространства.
The countermeasure against this attack is for clients to use the cnonce parameter.
Мерой противодействия этой атаке является использование клиентами параметра cnonce.
5.11. Batch Brute-Force Attacks
5.11. Пакетные атаки методом перебора
With Digest Authentication, a MITM can execute a chosen plaintext attack and can gather responses from many users to the same nonce. It can then find all the passwords within any subset of password space that would generate one of the nonce/response pairs in a single pass over that space. It also reduces the time to find the first password by a factor equal to the number of nonce/response pairs gathered. This search of the password space can often be done in parallel on many machines, and even a single machine can search large subsets of the password space very quickly -- reports exist of searching all passwords with six or fewer letters in a few hours.
При дайджест-аутентификации MITM может выполнить атаку с выбранным открытым текстом и собрать ответы от многих пользователей на один и тот же нонс. Затем он может найти все пароли в любом подмножестве пространства паролей, которые дали бы одну из пар «нонс/ответ», за один проход по этому пространству. Это также сокращает время нахождения первого пароля в число раз, равное числу собранных пар «нонс/ответ». Этот поиск по пространству паролей часто можно выполнить параллельно на многих машинах, и даже одна машина может очень быстро искать большие подмножества пространства паролей — есть сообщения о поиске всех паролей длиной шесть букв или меньше за несколько часов.
The countermeasure against this attack is for clients to use the cnonce parameter.
Мерой противодействия этой атаке является использование клиентами параметра cnonce.
5.12. Parameter Randomness
5.12. Случайность параметров
The security of this protocol is critically dependent on the randomness of the randomly chosen parameters, such as client and server nonces. These should be generated by a strong random or properly seeded pseudorandom source (see [RFC4086]).
Безопасность этого протокола критически зависит от случайности случайно выбираемых параметров, таких как нонсы клиента и сервера. Они должны генерироваться сильным случайным или надлежащим образом инициализированным псевдослучайным источником (см. [RFC4086]).
5.13. Summary
5.13. Итог
By modern cryptographic standards, Digest Authentication is weak. But, for a large range of purposes, it is valuable as a replacement for Basic Authentication. It remedies some, but not all, weaknesses of Basic Authentication. Its strength may vary depending on the implementation. In particular, the structure of the nonce (which is dependent on the server implementation) may affect the ease of mounting a replay attack. A range of server options is appropriate since, for example, some implementations may be willing to accept the server overhead of one-time nonces or digests to eliminate the possibility of replay. Others may be satisfied with a nonce like the one recommended above, i.e., restricted to a single IP address and a single ETag or with a limited lifetime.
По современным криптографическим стандартам дайджест-аутентификация слаба. Но для широкого круга целей она ценна как замена базовой аутентификации. Она устраняет некоторые, но не все слабости базовой аутентификации. Её сила может различаться в зависимости от реализации. В частности, структура нонса (которая зависит от реализации сервера) может влиять на лёгкость организации атаки повторного воспроизведения. Подходит ряд вариантов сервера, поскольку, например, некоторые реализации могут быть готовы принять накладные расходы сервера на одноразовые нонсы или дайджесты, чтобы исключить возможность повтора. Другие могут удовлетвориться нонсом, подобным рекомендованному выше, то есть ограниченным одним IP-адресом и одним ETag или с ограниченным временем жизни.
The bottom line is that *any* compliant implementation will be relatively weak by cryptographic standards, but *any* compliant implementation will be far superior to Basic Authentication.
Суть в том, что *любая* соответствующая требованиям реализация будет относительно слабой по криптографическим стандартам, но *любая* соответствующая требованиям реализация будет намного превосходить базовую аутентификацию.

Appendix A. Changes from RFC 2617
Приложение A. Изменения относительно RFC 2617
This document introduces the following changes:
Настоящий документ вводит следующие изменения:
o Adds support for two new algorithms, SHA2-256 as mandatory and SHA2-512/256 as a backup, and defines the proper algorithm negotiation. The document keeps the MD5 algorithm support but only for backward compatibility.
o Добавляет поддержку двух новых алгоритмов, SHA2-256 как обязательного и SHA2-512/256 как резервного, и определяет надлежащее согласование алгоритмов. Документ сохраняет поддержку алгоритма MD5, но только для обратной совместимости.
o Introduces the username hashing capability and the parameter associated with that, mainly for privacy reasons.
o Вводит возможность хеширования имени пользователя и связанный с этим параметр, главным образом по соображениям конфиденциальности.
o Adds various internationalization considerations that impact the A1 calculation and username and password encoding.
o Добавляет различные соображения интернационализации, влияющие на вычисление A1 и кодирование имени пользователя и пароля.
o Introduces a new IANA registry, "Hash Algorithms for HTTP Digest Authentication", that lists the hash algorithms that can be used in HTTP Digest Authentication.
o Вводит новый реестр IANA «Hash Algorithms for HTTP Digest Authentication», который перечисляет хеш-алгоритмы, которые могут использоваться в дайджест-аутентификации HTTP.
o Deprecates backward compatibility with RFC 2069.
o Объявляет устаревшей обратную совместимость с RFC 2069.
