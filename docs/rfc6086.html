1. Introduction
1. Введение
This document defines a method, INFO, for the Session Initiation Protocol (SIP) [RFC3261].
В этом документе определяется метод INFO для протокола инициирования сессий (SIP) [RFC3261].
The purpose of the INFO message is to carry application level information between endpoints, using the SIP dialog signaling path. Note that the INFO method is not used to update characteristics of a SIP dialog or session, but to allow the applications that use the SIP session to exchange information (which might update the state of those applications).
Назначение сообщения INFO — переносить информацию уровня приложения между оконечными точками по пути сигнализации диалога SIP. Отметим, что метод INFO не используется для обновления характеристик диалога или сессии SIP; он позволяет приложениям, использующим сессию SIP, обмениваться информацией (что может обновлять состояние этих приложений).
Use of the INFO method does not constitute a separate dialog usage. INFO messages are always part of, and share the fate of, an invite dialog usage [RFC5057]. INFO messages cannot be sent as part of other dialog usages, or outside an existing dialog.
Использование метода INFO не образует отдельного использования диалога. Сообщения INFO всегда являются частью использования диалога INVITE и разделяют его судьбу [RFC5057]. Сообщения INFO нельзя отправлять в составе других использований диалога или вне существующего диалога.
This document also defines an Info Package mechanism. An Info Package specification defines the content and semantics of the information carried in an INFO message associated with the Info Package. The Info Package mechanism also provides a way for user agents (UAs) to indicate for which Info Packages they are willing to receive INFO requests, and which Info Package a specific INFO request is associated with.
В этом документе также определяется механизм пакетов Info. Спецификация пакета Info определяет содержание и семантику информации, переносимой в сообщении INFO, связанном с этим пакетом Info. Механизм пакетов Info также даёт пользовательским агентам (UA) способ указывать, для каких пакетов Info они готовы принимать запросы INFO и с каким пакетом Info связан конкретный запрос INFO.
A UA uses the Recv-Info header field, on a per-dialog basis, to indicate for which Info Packages it is willing to receive INFO requests. A UA can indicate an initial set of Info Packages during dialog establishment and can indicate a new set during the lifetime of the invite dialog usage.
UA использует поле заголовка Recv-Info — для каждого диалога отдельно — чтобы указать, для каких пакетов Info он готов принимать запросы INFO. UA может указать начальный набор пакетов Info при установлении диалога и новый набор — в течение времени существования использования диалога INVITE.
NOTE: A UA can use an empty Recv-Info header field (a header field without a value) to indicate that it is not willing to receive INFO requests for any Info Package, while still informing other UAs that it supports the Info Package mechanism.
NOTE: A UA can use an empty Recv-Info header field (a header field without a value) to indicate that it is not willing to receive INFO requests for any Info Package, while still informing other UAs that it supports the Info Package mechanism.
When a UA sends an INFO request, it uses the Info-Package header field to indicate which Info Package is associated with the request. One particular INFO request can only be associated with a single Info Package.
Отправляя запрос INFO, UA использует поле заголовка Info-Package, чтобы указать, с каким пакетом Info связан запрос. Один конкретный запрос INFO может быть связан только с одним пакетом Info.

Some legacy INFO usages are also recognized as being shortcuts to more appropriate and flexible mechanisms.
Некоторые устаревшие использования INFO также признаны сокращёнными путями к более подходящим и гибким механизмам.
Furthermore, RFC 2976 did not define mechanisms that would enable a SIP UA to indicate (1) the types of applications and contexts in which the UA supports the INFO method or (2) the types of applications and contexts with which a specific INFO message is associated.
Кроме того, RFC 2976 не определил механизмы, которые позволили бы UA SIP указывать (1) типы приложений и контексты, в которых UA поддерживает метод INFO, или (2) типы приложений и контексты, с которыми связано конкретное сообщение INFO.
Because legacy INFO usages do not have associated Info Packages, it is not possible to use the Recv-Info and Info-Package header fields with legacy INFO usages. That is, a UA cannot use the Recv-Info header field to indicate for which legacy INFO usages it is willing to receive INFO requests, and a UA cannot use the Info-Package header field to indicate with which legacy INFO usage an INFO request is associated.
Поскольку устаревшие использования INFO не имеют связанных пакетов Info, использовать поля заголовков Recv-Info и Info-Package вместе с ними невозможно. То есть UA не может с помощью поля заголовка Recv-Info указать, для каких устаревших использований INFO он готов принимать запросы INFO, и не может с помощью поля заголовка Info-Package указать, с каким устаревшим использованием INFO связан запрос INFO.
Due to the problems described above, legacy INFO usages often require static configuration to indicate the types of applications and contexts for which the UAs support the INFO method, and the way they handle application information transported in INFO messages. This has caused interoperability problems in the industry.
Из-за описанных выше проблем устаревшие использования INFO часто требуют статической конфигурации, указывающей типы приложений и контексты, в которых UA поддерживает метод INFO, и способ обработки информации приложений, переносимой в сообщениях INFO. Это вызвало проблемы совместимости в отрасли.
To overcome these problems, the SIP Working Group has spent significant discussion time over many years coming to agreement on whether it was more appropriate to fix INFO (by defining a registration mechanism for the ways in which it was used) or to deprecate it altogether (with the usage described in RFC 3398 [RFC3398] being grandfathered as the sole legitimate usage). Although it required substantial consensus building and concessions by those more inclined to completely deprecate INFO, the eventual direction of the working group was to publish a framework for registration of Info Packages as defined in this specification.
Чтобы преодолеть эти проблемы, рабочая группа SIP потратила много времени на обсуждения, добиваясь согласия в вопросе о том, что целесообразнее: исправить INFO (определив механизм регистрации способов его использования) или полностью его упразднить (при этом использование, описанное в RFC 3398 [RFC3398], сохранялось бы как единственное законное). Хотя это потребовало значительной работы по достижению консенсуса и уступок со стороны тех, кто склонялся к полному упразднению INFO, рабочая группа в итоге пришла к публикации механизма регистрации пакетов Info, определённого в настоящей спецификации.

4.1. General
4.1. Общие положения
The INFO method provides a mechanism for transporting application level information that can further enhance a SIP application. Section 8 gives more details on the types of applications for which the use of INFO is appropriate.
Метод INFO предоставляет механизм переноса информации уровня приложения, который может дополнительно расширить возможности приложения SIP. Раздел 8 подробнее описывает типы приложений, для которых использование INFO уместно.

В этом разделе описано, как UA обрабатывает запросы и ответы INFO, а также тела сообщений, включаемые в сообщения INFO.
4.2. INFO Request
4.2. Запрос INFO
4.2.1. INFO Request Sender
4.2.1. Отправитель запроса INFO
An INFO request can be associated with an Info Package (see Section 5), or associated with a legacy INFO usage (see Section 2).
Запрос INFO может быть связан с пакетом Info (см. раздел 5) или с устаревшим использованием INFO (см. раздел 2).
The construction of the INFO request is the same as any other non-target refresh request within an existing invite dialog usage as described in Section 12.2 of RFC 3261. When a UA sends an INFO request associated with an Info Package, it MUST include an Info-Package header field that indicates which Info Package is associated with the request. A specific INFO request can be used only for a single Info Package.
Запрос INFO строится так же, как любой другой запрос, не обновляющий целевой адрес, в рамках существующего использования диалога INVITE, как описано в разделе 12.2 RFC 3261. Отправляя запрос INFO, связанный с пакетом Info, UA ДОЛЖЕН включить поле заголовка Info-Package, указывающее, с каким пакетом Info связан запрос. Конкретный запрос INFO может использоваться только для одного пакета Info.
When a UA sends an INFO request associated with a legacy INFO usage, there is no Info Package associated with the request, and the UA MUST NOT include an Info-Package header field in the request.
Когда UA отправляет запрос INFO, связанный с устаревшим использованием INFO, с запросом не связан никакой пакет Info, и UA НЕ ДОЛЖЕН включать поле заголовка Info-Package в запрос.
The INFO request MUST NOT contain a Recv-Info header field. A UA can only indicate a set of Info Packages for which it is willing to receive INFO requests by using the SIP methods (and their responses) listed in Section 5.
Запрос INFO НЕ ДОЛЖЕН содержать поле заголовка Recv-Info. UA может указать набор пакетов Info, для которых он готов принимать запросы INFO, только с помощью методов SIP (и их ответов), перечисленных в разделе 5.
A UA MUST NOT send an INFO request outside an invite dialog usage and MUST NOT send an INFO request for an Info Package inside an invite dialog usage if the remote UA has not indicated willingness to receive that Info Package within that dialog.
UA НЕ ДОЛЖЕН отправлять запрос INFO вне использования диалога INVITE и НЕ ДОЛЖЕН отправлять запрос INFO для пакета Info внутри использования диалога INVITE, если удалённый UA не выразил готовности принимать этот пакет Info в этом диалоге.
If a UA receives a 469 (Bad Info Package) response to an INFO request, based on RFC 5057 [RFC5057], the response represents a Transaction Only failure, and the UA MUST NOT terminate the invite dialog usage.
Если UA получает ответ 469 (Bad Info Package) на запрос INFO, то, согласно RFC 5057 [RFC5057], этот ответ представляет собой отказ уровня только транзакции (Transaction Only), и UA НЕ ДОЛЖЕН завершать использование диалога INVITE.
Due to the possibility of forking, the UA that sends the initial INVITE request MUST be prepared to receive INFO requests from multiple remote UAs during the early dialog phase. In addition, the UA MUST be prepared to receive different Recv-Info header field values from different remote UAs.
Из-за возможности разветвления UA, отправляющий начальный запрос INVITE, ДОЛЖЕН быть готов принимать запросы INFO от нескольких удалённых UA на этапе раннего диалога. Кроме того, UA ДОЛЖЕН быть готов получать разные значения поля заголовка Recv-Info от разных удалённых UA.
NOTE: If the User Agent Server (UAS) (receiver of the initial INVITE request) sends an INFO request just after it has sent the response that creates the dialog, the UAS needs to be prepared for the possibility that the INFO request will reach the User Agent Client (UAC) before the dialog-creating response, and might therefore be rejected by the UAC. In addition, an INFO request might be rejected due to a race condition, if a UA sends the INFO request at the same time that the remote UA sends a new set of Info Packages for which it is willing to receive INFO requests.
NOTE: If the User Agent Server (UAS) (receiver of the initial INVITE request) sends an INFO request just after it has sent the response that creates the dialog, the UAS needs to be prepared for the possibility that the INFO request will reach the User Agent Client (UAC) before the dialog-creating response, and might therefore be rejected by the UAC. 4.2.2. INFO Request Receiver
4.2.2. Получатель запроса INFO
If a UA receives an INFO request associated with an Info Package that the UA has not indicated willingness to receive, the UA MUST send a 469 (Bad Info Package) response (see Section 11.6), which contains a Recv-Info header field with Info Packages for which the UA is willing to receive INFO requests. The UA MUST NOT use the response to update the set of Info Packages, but simply to indicate the current set. In the terminology of multiple dialog usages [RFC5057], this represents a Transaction Only failure, and does not terminate the invite dialog usage.
Если UA получает запрос INFO, связанный с пакетом Info, готовность принимать который UA не выражал, UA ДОЛЖЕН отправить ответ 469 (Bad Info Package) (см. раздел 11.6), содержащий поле заголовка Recv-Info с пакетами Info, для которых UA готов принимать запросы INFO. UA НЕ ДОЛЖЕН использовать этот ответ для обновления набора пакетов Info — только для указания текущего набора. В терминологии множественных использований диалога [RFC5057] это отказ уровня только транзакции, и он не завершает использование диалога INVITE.
If a UA receives an INFO request associated with an Info Package, and the message body part with Content-Disposition "Info-Package" (see Section 4.3.1) has a Multipurpose Internet Mail Extensions (MIME) type that the UA supports but not in the context of that Info Package, it is RECOMMENDED that the UA send a 415 (Unsupported Media Type) response.
Если UA получает запрос INFO, связанный с пакетом Info, и часть тела сообщения со значением Content-Disposition «Info-Package» (см. раздел 4.3.1) имеет тип многоцелевых расширений почты Интернета (MIME), который UA поддерживает, но не в контексте этого пакета Info, РЕКОМЕНДУЕТСЯ, чтобы UA отправил ответ 415 (Unsupported Media Type).
The UA MAY send other error responses, such as Request Failure (4xx), Server Failure (5xx), and Global Failure (6xx), in accordance with the error-handling procedures defined in RFC 3261.
UA МОЖЕТ отправлять другие ответы об ошибках, такие как отказ запроса (4xx), отказ сервера (5xx) и глобальный отказ (6xx), в соответствии с процедурами обработки ошибок, определёнными в RFC 3261.
Otherwise, if the INFO request is syntactically correct and well structured, the UA MUST send a 200 (OK) response.
В противном случае, если запрос INFO синтаксически корректен и правильно структурирован, UA ДОЛЖЕН отправить ответ 200 (OK).
NOTE: If the application needs to reject the information that it received in an INFO request, that needs to be done on the application level. That is, the application needs to trigger a new INFO request, which contains information that the previously received application data was not accepted. Individual Info Package specifications need to describe the details for such procedures.
ПРИМЕЧАНИЕ: если приложению нужно отклонить информацию, полученную в запросе INFO, это делается на уровне приложения. То есть приложение должно инициировать новый запрос INFO, содержащий сведения о том, что ранее полученные данные приложения не были приняты. Детали таких процедур должны описывать отдельные спецификации пакетов Info.
4.2.3. SIP Proxies
4.2.3. Прокси-серверы SIP
Proxies need no additional behavior beyond that described in RFC 3261 to support INFO.
Для поддержки INFO прокси-серверам не требуется никакого поведения сверх описанного в RFC 3261.
4.3. INFO Message Body
4.3. Тело сообщения INFO
4.3.1. INFO Request Message Body
4.3.1. Тело сообщения запроса INFO
The purpose of the INFO request is to carry application level information between SIP UAs. The application information data is carried in the payload of the message body of the INFO request.
Назначение запроса INFO — переносить информацию уровня приложения между UA SIP. Данные информации приложения переносятся в полезной нагрузке тела сообщения запроса INFO.
NOTE: An INFO request associated with an Info Package can also include information associated with the Info Package using Info-Package header field parameters.
ПРИМЕЧАНИЕ: запрос INFO, связанный с пакетом Info, может также включать информацию, связанную с пакетом Info, с помощью параметров поля заголовка Info-Package.
If an INFO request associated with an Info Package contains a message body part, the body part is identified by a Content-Disposition header field "Info-Package" value. The body part can contain a single MIME type, or it can be a multipart [RFC5621] that contains other body parts associated with the Info Package.
Если запрос INFO, связанный с пакетом Info, содержит часть тела сообщения, эта часть тела идентифицируется значением «Info-Package» поля заголовка Content-Disposition. Часть тела может содержать один тип MIME или быть составной (multipart) [RFC5621], содержащей другие части тела, связанные с пакетом Info.
UAs MUST support multipart body parts in accordance with RFC 5621.
UA ДОЛЖНЫ поддерживать составные части тела в соответствии с RFC 5621.
NOTE: An INFO request can also contain other body parts that are meaningful within the context of an invite dialog usage but are not specifically associated with the INFO method and the application concerned.
ПРИМЕЧАНИЕ: запрос INFO может также содержать другие части тела, значимые в контексте использования диалога INVITE, но не связанные специально с методом INFO и рассматриваемым приложением.
When a UA supports a specific Info Package, the UA MUST also support message body MIME types in accordance with that Info Package. However, in accordance with RFC 3261, the UA still indicates the supported MIME types using the Accept header.
Когда UA поддерживает конкретный пакет Info, он ДОЛЖЕН также поддерживать типы MIME тела сообщения в соответствии с этим пакетом Info. Однако, согласно RFC 3261, UA по-прежнему указывает поддерживаемые типы MIME с помощью заголовка Accept.
4.3.2. INFO Response Message Body
4.3.2. Тело сообщения ответа INFO
A UA MUST NOT include a message body associated with an Info Package in an INFO response. Message bodies associated with Info Packages MUST only be sent in INFO requests.
UA НЕ ДОЛЖЕН включать тело сообщения, связанное с пакетом Info, в ответ INFO. Тела сообщений, связанные с пакетами Info, ДОЛЖНЫ отправляться только в запросах INFO.
A UA MAY include a message body that is not associated with an Info Package in an INFO response.
UA МОЖЕТ включать тело сообщения, которое не связано с пакетом Info, в ответ INFO.
4.4. Order of Delivery
4.4. Порядок доставки
The Info Package mechanism does not define a delivery order mechanism. Info Packages can rely on the CSeq header field [RFC3261] to detect if an INFO request is received out of order.
Механизм пакетов Info не определяет механизм порядка доставки. Пакеты Info могут полагаться на поле заголовка CSeq [RFC3261], чтобы обнаружить, что запрос INFO получен не по порядку.
If specific applications need additional mechanisms for order of delivery, those mechanisms, and related procedures, are specified as part of the associated Info Package (e.g., the use of sequence numbers within the application data).
Если конкретным приложениям нужны дополнительные механизмы порядка доставки, эти механизмы и связанные с ними процедуры определяются как часть соответствующего пакета Info (например, использование порядковых номеров внутри данных приложения).
5. Info Packages
5. Пакеты Info
5.1. General
5.1. Общие положения
An Info Package specification defines the content and semantics of the information carried in an INFO message associated with an Info Package. The Info Package mechanism provides a way for UAs to indicate for which Info Packages they are willing to receive INFO requests, and with which Info Package a specific INFO request is associated.
Спецификация пакета Info определяет содержание и семантику той информации, которая переносится в сообщении INFO, связанном с этим пакетом Info. Механизм пакетов Info даёт UA способ указывать, для каких пакетов Info они готовы принимать запросы INFO и с каким пакетом Info связан конкретный запрос INFO.
5.2. User Agent Behavior
5.2. Поведение пользовательского агента
5.2.1. General
5.2.1. Общие положения
This section describes how a UA handles Info Packages, how a UA uses the Recv-Info header field, and how the UA acts in re-INVITE rollback situations.
В этом разделе описано, как UA обрабатывает пакеты Info, как UA использует поле заголовка Recv-Info и как UA действует в ситуациях отката при повторном INVITE (re-INVITE).
5.2.2. UA Procedures
5.2.2. Процедуры UA
A UA that supports the Info Package mechanism MUST indicate, using the Recv-Info header field, the set of Info Packages for which it is willing to receive INFO requests for a specific session. A UA can list multiple Info Packages in a single Recv-Info header field, and the UA can use multiple Recv-Info header fields. A UA can use an empty Recv-Info header field, i.e., a header field without any header field values.
UA, поддерживающий механизм пакетов Info, ДОЛЖЕН указывать с помощью поля заголовка Recv-Info набор пакетов Info, для которых он готов принимать запросы INFO в конкретной сессии. UA может перечислить несколько пакетов Info в одном поле заголовка Recv-Info, и UA может использовать несколько полей заголовка Recv-Info. UA может использовать пустое поле заголовка Recv-Info, то есть поле заголовка без каких-либо значений.
A UA provides its set of Info Packages for which it is willing to receive INFO requests during the dialog establishment. A UA can update the set of Info Packages during the invite dialog usage.
UA предоставляет набор пакетов Info, для которых он готов принимать запросы INFO, при установлении диалога. UA может обновлять набор пакетов Info в течение времени существования использования диалога INVITE.
If a UA is not willing to receive INFO requests for any Info Packages, during dialog establishment or later during the invite dialog usage, the UA MUST indicate this by including an empty Recv-Info header field. This informs other UAs that the UA still supports the Info Package mechanism.
Если UA не готов принимать запросы INFO ни для каких пакетов Info — при установлении диалога или позже, в течение времени существования использования диалога INVITE, — UA ДОЛЖЕН указать это, включив пустое поле заголовка Recv-Info. Это сообщает другим UA, что UA по-прежнему поддерживает механизм пакетов Info.
Example: If a UA has previously indicated Info Packages "foo" and "bar" in a Recv-Info header field, and the UA during the lifetime of the invite dialog usage wants to indicate that it does not want to receive INFO requests for any Info Packages anymore, the UA sends a message with an empty Recv-Info header field.
Пример: если UA ранее указал пакеты Info «foo» и «bar» в поле заголовка Recv-Info, и в течение времени существования использования диалога INVITE UA хочет указать, что больше не желает принимать запросы INFO ни для каких пакетов Info, UA отправляет сообщение с пустым полем заголовка Recv-Info.
Once a UA has sent a message with a Recv-Info header field containing a set of Info Packages, the set is valid until the UA sends a new Recv-Info header field containing a new, or empty, set of Info Packages.
После того как UA отправил сообщение с полем заголовка Recv-Info, содержащим набор пакетов Info, этот набор действителен до тех пор, пока UA не отправит новое поле заголовка Recv-Info, содержащее новый или пустой набор пакетов Info.
Once a UA has indicated that it is willing to receive INFO requests for a specific Info Package, and a dialog has been established, the UA MUST be prepared to receive INFO requests associated with that Info Package until the UA indicates that it is no longer willing to receive INFO requests associated with that Info Package.
После того как UA указал, что готов принимать запросы INFO для конкретного пакета Info, и диалог был установлен, UA ДОЛЖЕН быть готов принимать запросы INFO, связанные с этим пакетом Info, пока UA не укажет, что больше не готов принимать запросы INFO, связанные с этим пакетом Info.
For a specific dialog usage, a UA MUST NOT send an INFO request associated with an Info Package until it has received an indication that the remote UA is willing to receive INFO requests for that Info Package, or after the UA has received an indication that the remote UA is no longer willing to receive INFO requests associated with that Info Package.
В конкретном использовании диалога UA НЕ ДОЛЖЕН отправлять запрос INFO, связанный с пакетом Info, пока не получит указание на то, что удалённый UA готов принимать запросы INFO для этого пакета Info, или после того, как UA получил указание, что удалённый UA больше не готов принимать запросы INFO, связанные с этим пакетом Info.
NOTE: When a UA sends a message that contains a Recv-Info header field with a new set of Info Packages for which the UA is willing to receive INFO requests, the remote UA might, before it receives the message, send an INFO request based on the old set of Info Packages. In this case, the receiver of the INFO requests rejects, and sends a 469 (Bad Info Package) response to, the INFO request.
ПРИМЕЧАНИЕ: когда UA отправляет сообщение, содержащее поле заголовка Recv-Info с новым набором пакетов Info, для которых UA готов принимать запросы INFO, удалённый UA может до получения этого сообщения отправить запрос INFO на основе старого набора пакетов Info. В этом случае получатель запросов INFO отклоняет запрос INFO и отправляет на него ответ 469 (Bad Info Package).
If a UA indicates multiple Info Packages that provide similar functionality, it is not possible to indicate a priority order of the Info Packages, or to indicate that the UA wishes to only receive INFO requests for one of the Info Packages. It is up to the application logic associated with the Info Packages, and particular Info Package specifications, to describe application behavior in such cases.
Если UA указывает несколько пакетов Info со сходными функциями, указать порядок приоритета пакетов Info или указать, что UA желает принимать запросы INFO только для одного из пакетов Info, невозможно. Описание поведения приложения в таких случаях оставляется на усмотрение логики приложения, связанной с пакетами Info, и конкретных спецификаций пакетов Info.
For backward compatibility purposes, even if a UA indicates support of the Info Package mechanism, it is still allowed to enable legacy INFO usages. In addition, if a UA indicates support of the INFO method using the Allow header field [RFC3261], it does not implicitly indicate support of the Info Package mechanism. A UA MUST use the Recv-Info header field in order to indicate that it supports the Info Package mechanism. Likewise, even if a UA uses the Recv-Info header field to indicate that it supports the Info Package mechanism, in addition the UA still indicates support of the INFO method using the Allow header.
В целях обратной совместимости, даже если UA указывает поддержку механизма пакетов Info, ему по-прежнему разрешено включать устаревшие использования INFO. Кроме того, если UA указывает поддержку метода INFO с помощью поля заголовка Allow [RFC3261], это не означает неявно поддержку механизма пакетов Info. UA ДОЛЖЕН использовать поле заголовка Recv-Info, чтобы указать, что он поддерживает механизм пакетов Info. Равным образом, даже если UA использует поле заголовка Recv-Info, чтобы указать, что он поддерживает механизм пакетов Info, UA дополнительно по-прежнему указывает поддержку метода INFO с помощью заголовка Allow.
This document does not define a SIP option-tag [RFC3261] for the Info Package mechanism. However, an Info Package specification can define an option-tag associated with the specific Info Package, as described in Section 10.6.
Настоящий документ не определяет тег опции SIP [RFC3261] для механизма пакетов Info. Однако спецификация пакета Info может определить тег опции, связанный с конкретным пакетом Info, как описано в разделе 10.6.
5.2.3. Recv-Info Header Field Rules
5.2.3. Правила поля заголовка Recv-Info
The text below defines rules on when a UA is required to include a Recv-Info header field in SIP messages. Section 7.1 lists the SIP methods for which a UA can insert a Recv-Info header field in requests and responses.
Приведённый ниже текст определяет правила того, когда UA обязан включать поле заголовка Recv-Info в сообщения SIP. В разделе 7.1 перечислены методы SIP, в запросы и ответы которых UA может вставлять поле заголовка Recv-Info.
o The sender of an initial INVITE request MUST include a Recv-Info header field in the initial INVITE request, even if the sender is not willing to receive INFO requests associated with any Info Package.
о Отправитель начального запроса INVITE ДОЛЖЕН включить поле заголовка Recv-Info в начальный запрос INVITE, даже если отправитель не готов принимать запросы INFO, связанные с каким-либо пакетом Info.
o The receiver of a request that contains a Recv-Info header field MUST include a Recv-Info header field in a reliable 18x/2xx response to the request, even if the request contains an empty Recv-Info header field, and even if the header field value of the receiver has not changed since the previous time it sent a Recv-Info header field.
о Получатель запроса, содержащего поле заголовка Recv-Info, ДОЛЖЕН включить поле заголовка Recv-Info в надёжный ответ 18x/2xx на этот запрос, даже если запрос содержит пустое поле заголовка Recv-Info и даже если значение поля заголовка у получателя не изменилось с того времени, когда он в последний раз отправлял поле заголовка Recv-Info.
o A UA MUST NOT include a Recv-Info header field in a response if the associated request did not contain a Recv-Info header field.
о UA НЕ ДОЛЖЕН включать поле заголовка Recv-Info в ответ, если связанный запрос не содержал поля заголовка Recv-Info.
NOTE: In contrast to the rules for generating Session Description Protocol (SDP) answers [RFC3264], the receiver of a request is not restricted to generating its own set of Info Packages as a subset of the Info Package set received in the Info-Package header field of the request.
ПРИМЕЧАНИЕ: в отличие от правил формирования ответов протокола описания сессий (SDP) [RFC3264], получатель запроса не ограничен формированием своего набора пакетов Info как подмножества набора пакетов Info, полученного в поле заголовка Info-Package запроса.
As with SDP answers, the receiver can include the same Recv-Info header field value in multiple responses (18x/2xx) for the same INVITE/re-INVITE transaction, but the receiver MUST use the same Recv-Info header field value (if included) in all responses for the same transaction.
Как и в случае с ответами SDP, получатель может включать одно и то же значение поля заголовка Recv-Info в несколько ответов (18x/2xx) для одной и той же транзакции INVITE/re-INVITE, но получатель ДОЛЖЕН использовать одно и то же значение поля заголовка Recv-Info (если оно включается) во всех ответах для одной и той же транзакции.
5.2.4. Info Package Fallback Rules
5.2.4. Правила возврата к прежнему набору пакетов Info
If the receiver of a request that contains a Recv-Info header field rejects the request, both the sender and receiver of the request MUST roll back to the set of Info Packages that was used before the request was sent. This also applies to the case where the receiver of an INVITE/re-INVITE request has included a Recv-Info header field in a provisional response, but later rejects the request.
Если получатель запроса, содержащего поле заголовка Recv-Info, отклоняет запрос, и отправитель, и получатель запроса ДОЛЖНЫ вернуться к набору пакетов Info, который использовался до отправки запроса. Это относится и к случаю, когда получатель запроса INVITE/re-INVITE включил поле заголовка Recv-Info в предварительный ответ, но позже отклонил запрос.
NOTE: The dialog state rollback rules for Info Packages might differ from the rules for other types of dialog state information (SDP, target, etc.).
ПРИМЕЧАНИЕ: правила отката состояния диалога для пакетов Info могут отличаться от правил для других видов информации о состоянии диалога (SDP, целевой адрес и т. д.).
5.3. REGISTER Processing
5.3. Обработка REGISTER
This document allows a UA to insert a Recv-Info header field in a REGISTER request. However, a UA SHALL NOT include a header value for a specific Info Package unless the particular Info Package specification describes how the header field value shall be interpreted and used by the registrar, e.g., in order to determine request targets. Rather than using the Recv-Info header field in order to determine request targets, it is recommended to use more appropriate mechanisms, e.g., based on RFC 3840 [RFC3840]. However, this document does not define a feature tag for the Info Package mechanism, or a mechanism to define feature tags for specific Info Packages.
Настоящий документ разрешает UA вставлять поле заголовка Recv-Info в запрос REGISTER. Однако UA НЕ ДОЛЖЕН включать значение заголовка для конкретного пакета Info, если спецификация этого пакета Info не описывает, как значение поля заголовка должно интерпретироваться и использоваться регистратором, например для определения целевых адресов запроса. Вместо использования поля заголовка Recv-Info для определения целевых адресов запроса рекомендуется применять более подходящие механизмы, например основанные на RFC 3840 [RFC3840]. Однако настоящий документ не определяет тег возможности для механизма пакетов Info или механизм определения тегов возможностей для конкретных пакетов Info.

8. Info Package Considerations
8. Вопросы, связанные с пакетами Info
8.1. General
8.1. Общие положения
This section covers considerations to take into account when deciding whether the usage of an Info Package is appropriate for transporting application information for a specific use-case.
В этом разделе рассмотрены соображения, которые следует учитывать, решая, уместно ли использование пакета Info для переноса информации приложений в конкретном случае использования.
8.2. Appropriateness of Info Package Usage
8.2. Уместность использования пакета Info
When designing an Info Package, for application level information exchange, it is important to consider: is signaling, using INFO requests, within a SIP dialog, an appropriate mechanism for the use- case? Is it because it is the most reasonable and appropriate choice, or merely because "it's easy"? Choosing an inappropriate mechanism for a specific use-case can cause negative effects in SIP networks where the mechanism is used.
При разработке пакета Info для обмена информацией на уровне приложения важно учитывать: является ли сигнализация с помощью запросов INFO в рамках диалога SIP подходящим механизмом для данного случая использования? Выбран ли он потому, что это наиболее разумный и подходящий вариант, или лишь потому, что «так проще»? Выбор неподходящего механизма для конкретного случая использования может вызвать негативные последствия в сетях SIP, где этот механизм применяется.
8.3. INFO Request Rate and Volume
8.3. Частота и объём запросов INFO
INFO messages differ from many other sorts of SIP messages in that they carry application information, and the size and rate of INFO messages are directly determined by the application. This can cause application information traffic to interfere with other traffic on that infrastructure, or to self-interfere when data rates become too high.
Сообщения INFO отличаются от многих других видов сообщений SIP тем, что они переносят информацию приложения, а размер и частота сообщений INFO напрямую определяются приложением. Это может приводить к тому, что трафик информации приложений мешает другому трафику в этой инфраструктуре или мешает сам себе, когда скорость передачи данных становится слишком высокой.
There is no default throttling mechanism for INFO requests. Apart from the SIP session establishment, the number of SIP messages exchanged during the lifetime of a normal SIP session is rather small. Some applications, like those sending Dual-Tone Multi-Frequency (DTMF) tones, can generate a burst of up to 20 messages per second. Other applications, like constant GPS location updates, could generate a high rate of INFO requests during the lifetime of the invite dialog usage.
Для запросов INFO нет механизма ограничения частоты по умолчанию. Помимо установления сессии SIP, число сообщений SIP, которыми обмениваются за время существования обычной сессии SIP, довольно мало. Некоторые приложения, например передающие тоны двухтонального многочастотного набора (DTMF), могут генерировать всплеск до 20 сообщений в секунду. Другие приложения, например постоянно обновляющие данные о местоположении GPS, могут генерировать высокую частоту запросов INFO за время существования использования диалога INVITE.
A designer of an Info Package, and the application that uses it, need to consider the impact that the size and the rate of the INFO messages have on the network and on other traffic, since it normally cannot be ensured that INFO messages will be carried over a congestion-controlled transport protocol end-to-end. Even if an INFO message is sent over such a transport protocol, a downstream SIP entity might forward the message over a transport protocol that does not provide congestion control.
Разработчику пакета Info и приложения, которое его использует, необходимо учитывать влияние размера и частоты сообщений INFO на сеть и на другой трафик, поскольку обычно нельзя гарантировать, что сообщения INFO будут передаваться через транспортный протокол с управлением перегрузкой от конца до конца. Даже если сообщение INFO отправлено через такой транспортный протокол, нижестоящий объект SIP может переслать сообщение через транспортный протокол, не обеспечивающий управление перегрузкой.
Furthermore, SIP messages tend to be relatively small, on the order of 500 Bytes to 32K Bytes. SIP is a poor mechanism for direct exchange of bulk data beyond these limits, especially if the headers plus body exceed the User Datagram Protocol (UDP) MTU [RFC0768]. Appropriate mechanisms for such traffic include the Hypertext Transfer Protocol (HTTP) [RFC2616], the Message Session Relay Protocol (MSRP) [RFC4975], or other media plane data transport mechanisms.
Кроме того, сообщения SIP обычно относительно малы — порядка от 500 байт до 32 Кбайт. SIP — плохой механизм для прямого обмена большими объёмами данных за этими пределами, особенно если заголовки вместе с телом превышают MTU протокола дейтаграмм пользователя (UDP) [RFC0768]. Подходящие механизмы для такого трафика — протокол передачи гипертекста (HTTP) [RFC2616], протокол ретрансляции сеансовых сообщений (MSRP) [RFC4975] или другие механизмы переноса данных в плоскости медиаданных.
RFC 5405 [RFC5405] provides additional guidelines for applications using UDP that may be useful background reading.
RFC 5405 [RFC5405] содержит дополнительные рекомендации для приложений, использующих UDP, которые могут оказаться полезными для ознакомления.
8.4. Alternative Mechanisms
8.4. Альтернативные механизмы
8.4.1. Alternative SIP Signaling Plane Mechanisms
8.4.1. Альтернативные механизмы плоскости сигнализации SIP
8.4.1.1. General
8.4.1.1. Общие положения
This subsection describes some alternative mechanisms for transporting application information on the SIP signaling plane, using SIP messages.
В этом подразделе описаны некоторые альтернативные механизмы переноса информации приложений в плоскости сигнализации SIP с помощью сообщений SIP.
8.4.1.2. SUBSCRIBE/NOTIFY
8.4.1.2. SUBSCRIBE/NOTIFY
An alternative for application level interaction is to use subscription-based events [RFC3265] that use the SIP SUBSCRIBE and NOTIFY methods. Using that mechanism, a UA requests state information, such as keypad presses from a device to an application server, or key-map images from an application server to a device. Event Packages [RFC3265] perform the role of disambiguating the context of a message for subscription-based events. The Info Package mechanism provides similar functionality for application information exchange using invite dialog usages [RFC5057].
Альтернативой взаимодействию уровня приложения является использование событий на основе подписки [RFC3265], в которых применяются методы SIP SUBSCRIBE и NOTIFY. Используя этот механизм, UA запрашивает информацию о состоянии, например нажатия клавиш от устройства к серверу приложений или изображения клавиатуры от сервера приложений к устройству. Пакеты событий [RFC3265] выполняют роль устранения неоднозначности контекста сообщения для событий на основе подписки. Механизм пакетов Info обеспечивает аналогичную функциональность при обмене информацией приложений в рамках использований диалога INVITE [RFC5057].
While an INFO request is always part of, and shares the fate of, an existing invite dialog usage, a SUBSCRIBE request creates a separate dialog usage [RFC5057], and is normally sent outside an existing dialog usage.
В то время как запрос INFO всегда является частью существующего использования диалога INVITE и разделяет его судьбу, запрос SUBSCRIBE создаёт отдельное использование диалога [RFC5057] и обычно отправляется вне существующего использования диалога.
The subscription-based mechanism can be used by SIP entities to receive state information about SIP dialogs and sessions, without requiring the entities to be part of the route set of those dialogs and sessions.
Механизм на основе подписки может использоваться объектами SIP для получения информации о состоянии диалогов и сессий SIP без необходимости входить в набор маршрутов этих диалогов и сессий.
As SUBSCRIBE/NOTIFY messages traverse through stateful SIP proxies and back-to-back user agents (B2BUAs), the resource impact caused by the subscription dialogs needs to be considered. The number of subscription dialogs per user also needs to be considered.
Поскольку сообщения SUBSCRIBE/NOTIFY проходят через прокси-серверы SIP с сохранением состояния и пользовательские агенты типа B2BUA (back-to-back user agents), необходимо учитывать нагрузку на ресурсы, создаваемую диалогами подписки. Необходимо также учитывать число диалогов подписки на одного пользователя.
As for any other SIP-signaling-plane-based mechanism for transporting application information, the SUBSCRIBE/NOTIFY messages can put a significant burden on intermediate SIP entities that are part of the dialog route set, but do not have any interest in the application information transported between the end users.
Как и для любого другого механизма переноса информации приложений в плоскости сигнализации SIP, сообщения SUBSCRIBE/NOTIFY могут создавать значительную нагрузку на промежуточные объекты SIP, которые входят в набор маршрутов диалога, но не заинтересованы в информации приложений, переносимой между оконечными пользователями.
8.4.1.3. MESSAGE
8.4.1.3. MESSAGE
The MESSAGE method [RFC3428] defines one-time instant message exchange, typically for sending MIME contents for rendering to the user.
Метод MESSAGE [RFC3428] определяет одноразовый обмен мгновенными сообщениями, обычно для отправки содержимого MIME для отображения пользователю.
8.4.2. Media Plane Mechanisms
8.4.2. Механизмы плоскости медиаданных
8.4.2.1. General
8.4.2.1. Общие положения
In SIP, media plane channels associated with SIP dialogs are established using SIP signaling, but the data exchanged on the media plane channel does not traverse SIP signaling intermediates, so if there will be a lot of information exchanged, and there is no need for the SIP signaling intermediaries to examine the information, it is recommended to use a media plane mechanism, rather than a SIP- signaling-based mechanism.
В SIP каналы плоскости медиаданных, связанные с диалогами SIP, устанавливаются с помощью сигнализации SIP, но данные, передаваемые по каналу плоскости медиаданных, не проходят через промежуточные узлы сигнализации SIP, поэтому если объём обмениваемой информации велик и промежуточным узлам сигнализации SIP не нужно её просматривать, рекомендуется использовать механизм плоскости медиаданных, а не механизм на основе сигнализации SIP.
A low-latency requirement for the exchange of information is one strong indicator for using a media channel. Exchanging information through the SIP routing network can introduce hundreds of milliseconds of latency.
Требование малой задержки при обмене информацией — один из весомых признаков того, что следует использовать канал медиаданных. Обмен информацией через сеть маршрутизации SIP может вносить задержку в сотни миллисекунд.
8.4.2.2. MRCP
8.4.2.2. MRCP
One mechanism for media plane exchange of application data is the Media Resource Control Protocol (MRCP) [SPEECHSC-MRCPv2], where a media plane connection-oriented channel, such as a Transmission Control Protocol (TCP) [RFC0793] or Stream Control Transmission Protocol (SCTP) [RFC4960] stream is established.
Один из механизмов обмена данными приложений в плоскости медиаданных — протокол управления медиаресурсами (MRCP) [SPEECHSC-MRCPv2], при использовании которого устанавливается ориентированный на соединение канал плоскости медиаданных, например поток протокола управления передачей (TCP) [RFC0793] или протокола передачи с управлением потоками (SCTP) [RFC4960].
8.4.2.3. MSRP
8.4.2.3. MSRP
MSRP [RFC4975] defines session-based instant messaging as well as bulk file transfer and other such large-volume uses.
MSRP [RFC4975] определяет обмен мгновенными сообщениями в рамках сессии, массовую передачу файлов и другие подобные применения большого объёма.
8.4.3. Non-SIP-Related Mechanisms
8.4.3. Механизмы, не связанные с SIP
Another alternative is to use a SIP-independent mechanism, such as HTTP [RFC2616]. In this model, the UA knows about a rendezvous point to which it can direct HTTP requests for the transfer of information. Examples include encoding of a prompt to retrieve in the SIP Request URI [RFC4240] or the encoding of a SUBMIT target in a VoiceXML [W3C.REC-voicexml21-20070619] script.
Другая альтернатива — использовать механизм, не зависящий от SIP, например HTTP [RFC2616]. В этой модели UA знает точку рандеву, на которую он может направлять запросы HTTP для передачи информации. Примеры включают кодирование подсказки, которую нужно получить, в Request URI SIP [RFC4240] или кодирование цели SUBMIT в сценарии VoiceXML [W3C.REC-voicexml21-20070619].

10.2. Общее описание
The Info Package specification MUST contain an overall description of the Info Package: what type of information is carried in INFO requests associated with the Info Package, and for what types of applications and functionalities UAs can use the Info Package.
Спецификация пакета Info ДОЛЖНА содержать общее описание пакета Info: какого рода информация переносится в запросах INFO, связанных с этим пакетом Info, и для каких типов приложений и функциональных возможностей UA может использовать этот пакет Info.

10.3. Applicability
10.3. Применимость
The Info Package specification MUST describe why the Info Package mechanism, rather than some other mechanism, has been chosen for the specific use-case to transfer application information between SIP endpoints. Common reasons can be a requirement for SIP proxies or back-to-back user agents (B2BUAs) to see the transported application information (which would not be the case if the information was transported on a media path), or that it is not seen as feasible to establish separate dialogs (subscription) in order to transport the information.
Спецификация пакета Info ДОЛЖНА описывать, почему для конкретного случая использования выбран механизм пакетов Info, а не какой-либо иной механизм переноса информации приложений между оконечными точками SIP. Обычные причины — необходимость того, чтобы прокси-серверы SIP или пользовательские агенты типа B2BUA видели переносимую информацию приложений (чего не было бы, если бы информация передавалась по пути медиаданных), или невозможность установления отдельных диалогов (подписки) для переноса информации.
Section 8 provides more information and describes alternative mechanisms that one should consider for solving a specific use-case.
Раздел 8 содержит дополнительную информацию и описывает альтернативные механизмы, которые следует рассматривать при решении конкретного случая использования.
10.4. Info Package Name
10.4. Имя пакета Info
The Info Package specification MUST define an Info Package name, which UAs use as a header field value (e.g., "infoX") to identify the Info Package in the Recv-Info and Info-Package header fields. The header field value MUST conform to the ABNF defined in Section 9.2.
Спецификация пакета Info ДОЛЖНА определить имя пакета Info, которое UA использует как значение поля заголовка (например, «infoX»), чтобы идентифицировать пакет Info в полях заголовков Recv-Info и Info-Package. Значение поля заголовка ДОЛЖНО соответствовать ABNF, определённому в разделе 9.2.
The Info Package mechanism does not support package versioning. Specific Info Package message body payloads can contain version information, which is handled by the applications associated with the Info Package. However, such a feature is outside the scope of the generic Info Package mechanism.
Механизм пакетов Info не поддерживает версионирование пакетов. Полезная нагрузка тела сообщения конкретных пакетов Info может содержать информацию о версии, которой занимаются приложения, связанные с пакетом Info. Однако такая возможность выходит за рамки общего механизма пакетов Info.
NOTE: Even if an Info Package name contains version numbering (e.g., foo_v2), the Info Package mechanism does not distinguish a version number from the rest of the Info Package name.
ПРИМЕЧАНИЕ: даже если имя пакета Info содержит номер версии (например, foo_v2), механизм пакетов Info не отличает номер версии от остальной части имени пакета Info.
10.5. Info Package Parameters
10.5. Параметры пакета Info
The Info Package specification MAY define Info Package parameters, which can be used in the Recv-Info or Info-Package header fields, together with the header field value that indicates the Info Package name (see Section 10.4).
Спецификация пакета Info МОЖЕТ определять параметры пакета Info, которые можно использовать в полях заголовков Recv-Info или Info-Package вместе со значением поля заголовка, указывающим имя пакета Info (см. раздел 10.4).
The Info Package specification MUST define the syntax and semantics of the defined parameters. In addition, the specification MUST define whether a specific parameter is applicable to only the Recv-Info header field, only the Info-Package header field, or to both.
Спецификация пакета Info ДОЛЖНА определить синтаксис и семантику определяемых параметров. Кроме того, спецификация ДОЛЖНА определить, применим ли конкретный параметр только к полю заголовка Recv-Info, только к полю заголовка Info-Package или к обоим.
By default, an Info Package parameter is only applicable to the Info Package for which the parameter has been explicitly defined. Info Package parameters defined for specific Info Packages can share the name with parameters defined for other Info Packages, but the parameter semantics are specific to the Info Package for which they are defined. However, when choosing the name of a parameter, it is RECOMMENDED to not use the same name as an existing parameter for another Info Package, if the semantics of the parameters are different.
По умолчанию параметр пакета Info применим только к тому пакету Info, для которого он явно определён. Параметры пакетов Info, определённые для конкретных пакетов Info, могут совпадать по имени с параметрами, определёнными для других пакетов Info, но семантика параметра относится именно к тому пакету Info, для которого он определён. Однако при выборе имени параметра РЕКОМЕНДУЕТСЯ не использовать то же имя, что и у существующего параметра другого пакета Info, если семантика параметров различается.

10.7. Части тела сообщения INFO

Спецификация пакета Info ДОЛЖНА определить, какие типы MIME частей тела сообщения связаны с пакетом Info. Спецификация ДОЛЖНА либо определить эти части тела, включая синтаксис, семантику и тип MIME каждой части тела, либо сослаться на другие документы, определяющие эти части тела.

10.8. Info Package Usage Restrictions
10.8. Ограничения на использование пакета Info
If there are restrictions on how UAs can use an Info Package, the Info Package specification MUST document such restrictions.
Если существуют ограничения на то, как UA может использовать пакет Info, спецификация пакета Info ДОЛЖНА документировать такие ограничения.
There can be restrictions related to whether UAs are allowed to send overlapping (outstanding) INFO requests associated with the Info Package, or whether the UA has to wait for the response for a previous INFO request associated with the same Info Package.
Ограничения могут касаться того, разрешено ли UA отправлять перекрывающиеся (ещё не завершённые) запросы INFO, связанные с пакетом Info, или того, должен ли UA ждать ответа на предыдущий запрос INFO, связанный с тем же пакетом Info.
There can also be restrictions related to whether UAs need to support and use other SIP extensions and capabilities when they use the Info Package, and if there are restrictions related to how UAs can use the Info Package together with other Info Packages. As the SIP stack might not be aware of Info Package specific restrictions, it cannot be assumed that overlapping requests would be rejected. As defined in Section 4.2.2, UAs will normally send a 200 (OK) response to an INFO request. The application logic associated with the Info Package needs to handle situations where UAs do not follow restrictions associated with the Info Package.
Ограничения могут также касаться того, нужно ли UA поддерживать и использовать другие расширения и возможности SIP при использовании пакета Info, и того, как UA может использовать пакет Info вместе с другими пакетами Info. Поскольку стек SIP может не знать об ограничениях, специфичных для пакета Info, нельзя предполагать, что перекрывающиеся запросы будут отклонены. Как определено в разделе 4.2.2, UA обычно отправляет ответ 200 (OK) на запрос INFO. Логика приложения, связанная с пакетом Info, должна обрабатывать ситуации, когда UA не соблюдают ограничения, связанные с пакетом Info.

10.9. Частота запросов INFO

Если существует максимальная или минимальная частота, с которой UA могут отправлять запросы INFO, связанные с пакетом Info, в рамках диалога, спецификация пакета Info ДОЛЖНА документировать значения этой частоты.
If the rates can vary, the Info Package specification MAY define Info Package parameters that UAs can use to indicate or negotiate the rates. Alternatively, the rate information can be part of the application data information associated with the Info Package.
Если частота может изменяться, спецификация пакета Info МОЖЕТ определять параметры пакета Info, которые UA могут использовать для указания или согласования частоты. Либо информация о частоте может быть частью данных приложения, связанных с пакетом Info.
10.10. Info Package Security Considerations
10.10. Вопросы безопасности пакета Info
If the application information carried in INFO requests associated with the Info Package requires a certain level of security, the Info Package specification MUST describe the mechanisms that UAs need to use in order to provide the required security.
Если информация приложений, переносимая в запросах INFO, связанных с пакетом Info, требует определённого уровня безопасности, спецификация пакета Info ДОЛЖНА описать механизмы, которые UA должны использовать для обеспечения требуемой безопасности.
If the Info Package specification does not require any additional security, other than what the underlying SIP protocol provides, this MUST be stated in the Info Package specification.
Если спецификация пакета Info не требует какой-либо дополнительной безопасности помимо той, которую обеспечивает базовый протокол SIP, это ДОЛЖНО быть указано в спецификации пакета Info.
NOTE: In some cases, it may not be sufficient to mandate Transport Layer Security (TLS) [RFC5246] in order to secure the Info Package payload, since intermediaries will have access to the payload, and because beyond the first hop, there is no way to assure subsequent hops will not forward the payload in clear text. The best way to ensure secure transport at the application level is to have the security at the application level. One way of achieving this is to use end-to-end security techniques such as Secure/Multipurpose Internet Mail Extensions (S/MIME) [RFC5751].
ПРИМЕЧАНИЕ: в некоторых случаях требования использовать безопасность транспортного уровня (TLS) [RFC5246] может оказаться недостаточно для защиты полезной нагрузки пакета Info, поскольку промежуточные узлы имеют доступ к полезной нагрузке и, помимо первого перехода, нет способа гарантировать, что последующие переходы не перешлют полезную нагрузку в открытом виде. Лучший способ обеспечить безопасную передачу на уровне приложения — иметь безопасность на уровне приложения. Один из способов достичь этого — использовать сквозные методы защиты, такие как Secure/Multipurpose Internet Mail Extensions (S/MIME) [RFC5751].

13. Security Considerations
13. Вопросы безопасности
By eliminating multiple usages of INFO messages without adequate community review, and by eliminating the possibility of rogue SIP UAs confusing another UA by purposely sending unrelated INFO requests, we expect this document's clarification of the use of INFO to improve the security of the Internet. While rogue UAs can still send unrelated INFO requests, this mechanism enables the UAS and other security devices to associate INFO requests with Info Packages that have been negotiated for a session. If the content of the Info Package payload is private, UAs will need to use end-to-end encryption, such as S/MIME, to prevent access to the content. This is particularly important, as transport of INFO is likely not to be end-to-end, but through SIP proxies and back-to-back user agents (B2BUAs), which the user may not trust.
Устраняя множественные применения сообщений INFO без надлежащего рассмотрения сообществом и устраняя возможность того, что недобросовестные UA SIP будут вводить в заблуждение другой UA, намеренно отправляя не относящиеся к делу запросы INFO, мы рассчитываем, что разъяснение использования INFO в настоящем документе повысит безопасность Интернета. Хотя недобросовестные UA по-прежнему могут отправлять не относящиеся к делу запросы INFO, этот механизм позволяет UAS и другим средствам безопасности связывать запросы INFO с пакетами Info, согласованными для сессии. Если содержание полезной нагрузки пакета Info является конфиденциальным, UA потребуется использовать сквозное шифрование, например S/MIME, чтобы предотвратить доступ к содержанию. Это особенно важно, поскольку передача INFO, вероятно, осуществляется не от конца до конца, а через прокси-серверы SIP и пользовательские агенты типа B2BUA, которым пользователь может не доверять.
The INFO request transports application level information. One implication of this is that INFO messages may require a higher level of protection than the underlying SIP dialog signaling. In particular, if one does not protect the SIP signaling from eavesdropping or authentication and repudiation attacks, for example by using TLS transport, then the INFO request and its contents will be vulnerable as well. Even with SIP/TLS, any SIP hop along the path from UAC to UAS can view, modify, or intercept INFO requests, as they can with any SIP request. This means some applications may require end-to-end encryption of the INFO payload, beyond, for example, hop- by-hop protection of the SIP signaling itself. Since the application dictates the level of security required, individual Info Packages have to enumerate these requirements. In any event, the Info Package mechanism described by this document provides the tools for such secure, end-to-end transport of application data.
Запрос INFO переносит информацию уровня приложения. Одно из следствий этого — сообщения INFO могут требовать более высокого уровня защиты, чем сигнализация диалога SIP, лежащая в основе. В частности, если сигнализация SIP не защищена от прослушивания или атак на аутентификацию и отказ от авторства, например с помощью транспорта TLS, то запрос INFO и его содержание также окажутся уязвимыми. Даже при использовании SIP/TLS любой переход SIP на пути от UAC к UAS может просматривать, изменять или перехватывать запросы INFO, как и любые запросы SIP. Это означает, что некоторым приложениям может потребоваться сквозное шифрование полезной нагрузки INFO — сверх, например, пошаговой защиты самой сигнализации SIP. Поскольку уровень требуемой безопасности диктует приложение, отдельные пакеты Info должны перечислять эти требования. В любом случае механизм пакетов Info, описанный в настоящем документе, предоставляет средства для такой безопасной сквозной передачи данных приложений.
One interesting property of Info Package usage is that one can re-use the same digest-challenge mechanism used for INVITE-based authentication for the INFO request. For example, one could use a quality-of-protection (qop) value of authentication with integrity (auth-int), to challenge the request and its body, and prevent intermediate devices from modifying the body. However, this assumes the device that knows the credentials in order to perform the INVITE challenge is still in the path for the INFO request, or that the far- end UAS knows such credentials.
Одно интересное свойство использования пакетов Info состоит в том, что для запроса INFO можно повторно использовать тот же механизм дайджест-запроса, который применяется для аутентификации на основе INVITE. Например, можно использовать значение качества защиты (qop) authentication with integrity (auth-int), чтобы выполнить запрос с проверкой запроса и его тела и воспрепятствовать изменению тела промежуточными устройствами. Однако это предполагает, что устройство, обладающее учётными данными для выполнения запроса при INVITE, по-прежнему находится на пути запроса INFO, или что дальний UAS знает такие учётные данные.
