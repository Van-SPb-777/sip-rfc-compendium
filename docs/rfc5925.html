The TCP Authentication Option
Опция аутентификации TCP (TCP-AO)
Abstract
Аннотация
This document specifies the TCP Authentication Option (TCP-AO), which obsoletes the TCP MD5 Signature option of RFC 2385 (TCP MD5). TCP-AO specifies the use of stronger Message Authentication Codes (MACs), protects against replays even for long-lived TCP connections, and provides more details on the association of security with TCP connections than TCP MD5. TCP-AO is compatible with either a static Master Key Tuple (MKT) configuration or an external, out-of-band MKT management mechanism; in either case, TCP-AO also protects connections when using the same MKT across repeated instances of a connection, using traffic keys derived from the MKT, and coordinates MKT changes between endpoints. The result is intended to support current infrastructure uses of TCP MD5, such as to protect long-lived connections (as used, e.g., in BGP and LDP), and to support a larger set of MACs with minimal other system and operational changes. TCP- AO uses a different option identifier than TCP MD5, even though TCP- AO and TCP MD5 are never permitted to be used simultaneously. TCP-AO supports IPv6, and is fully compatible with the proposed requirements for the replacement of TCP MD5.
В настоящем документе определяется опция аутентификации TCP (TCP-AO), которая заменяет опцию сигнатуры TCP MD5 из RFC 2385 (TCP MD5). TCP-AO предусматривает использование более стойких кодов аутентификации сообщений (MAC), защищает от повторов даже для долгоживущих соединений TCP и содержит больше сведений о связи безопасности с соединениями TCP, чем TCP MD5. TCP-AO совместима как со статической конфигурацией кортежей главных ключей (MKT), так и с внешним механизмом управления MKT вне полосы; в обоих случаях TCP-AO также защищает соединения при использовании одного и того же MKT для повторных экземпляров соединения, применяя транспортные ключи, производные от MKT, и координирует изменения MKT между конечными точками. Результат призван поддержать текущее использование TCP MD5 в инфраструктуре, например для защиты долгоживущих соединений (как применяется, например, в BGP и LDP), и поддержать более широкий набор MAC при минимальных прочих системных и эксплуатационных изменениях. TCP-AO использует иной идентификатор опции, чем TCP MD5, хотя TCP-AO и TCP MD5 никогда не разрешается использовать одновременно. TCP-AO поддерживает IPv6 и полностью совместима с предложенными требованиями к замене TCP MD5.

1. Introduction
1. Введение
The TCP MD5 Signature (TCP MD5) is a TCP option that authenticates TCP segments, including the TCP IPv4 pseudoheader, TCP header, and TCP data. It was developed to protect BGP sessions from spoofed TCP segments, which could affect BGP data or the robustness of the TCP connection itself [RFC2385][RFC4953].
Сигнатура TCP MD5 (TCP MD5) — это опция TCP, которая аутентифицирует сегменты TCP, включая псевдозаголовок IPv4, заголовок TCP и данные TCP. Она была разработана для защиты сеансов BGP от поддельных сегментов TCP, которые могли бы повлиять на данные BGP или на устойчивость самого соединения TCP [RFC2385][RFC4953].
There have been many recent concerns about TCP MD5. Its use of a simple keyed hash for authentication is problematic because there have been escalating attacks on the algorithm itself [Wa05]. TCP MD5 also lacks both key-management and algorithm agility. This document adds the latter, and provides a simple key coordination mechanism giving the ability to move from one key to another within the same connection. It does not however provide for complete cryptographic key management to be handled in band of TCP, because TCP SYN segments lack sufficient remaining space to handle such a negotiation (see Section 7.6). This document obsoletes the TCP MD5 option with a more general TCP Authentication Option (TCP-AO). This new option supports the use of other, stronger hash functions, provides replay protection for long-lived connections and across repeated instances of a single connection, coordinates key changes between endpoints, and provides a more explicit recommendation for external key management. The result is compatible with IPv6, and is fully compatible with proposed requirements for a replacement for TCP MD5 [Ed07].
В последнее время возникло много опасений по поводу TCP MD5. Использование простого хэша с ключом для аутентификации проблематично, поскольку атаки на сам алгоритм усиливаются [Wa05]. TCP MD5 также не обладает ни управлением ключами, ни гибкостью алгоритмов. Настоящий документ добавляет последнюю и предоставляет простой механизм координации ключей, дающий возможность переходить от одного ключа к другому в рамках одного соединения. Однако он не предусматривает полного управления криптографическими ключами в полосе TCP, поскольку в сегментах SYN протокола TCP не хватает оставшегося места для такой координации (см. раздел 7.6). Настоящий документ заменяет опцию TCP MD5 более общей опцией аутентификации TCP (TCP-AO). Эта новая опция поддерживает использование других, более стойких хэш-функций, обеспечивает защиту от повторов для долгоживущих соединений и для повторных экземпляров одного соединения, координирует изменения ключей между конечными точками и даёт более явную рекомендацию по внешнему управлению ключами. Результат совместим с IPv6 и полностью совместим с предложенными требованиями к замене TCP MD5 [Ed07].
TCP-AO obsoletes TCP MD5, although a particular implementation may support both mechanisms for backward compatibility. For a given connection, only one can be in use. TCP MD5-protected connections cannot be migrated to TCP-AO because TCP MD5 does not support any changes to a connection's security algorithm once established.
TCP-AO заменяет TCP MD5, хотя конкретная реализация может поддерживать оба механизма для обратной совместимости. Для данного соединения можно использовать только один из них. Соединения, защищённые TCP MD5, нельзя перевести на TCP-AO, поскольку TCP MD5 не поддерживает никаких изменений алгоритма безопасности соединения после его установления.

1.2. Applicability Statement
1.2. Заявление о применимости
TCP-AO is intended to support current uses of TCP MD5, such as to protect long-lived connections for routing protocols, such as BGP and LDP. It is also intended to provide similar protection to any long- lived TCP connection, as might be used between proxy caches, for example, and is not designed solely or primarily for routing protocol uses.
TCP-AO предназначена для поддержки текущего использования TCP MD5, например для защиты долгоживущих соединений протоколов маршрутизации, таких как BGP и LDP. Она также предназначена для обеспечения аналогичной защиты любого долгоживущего соединения TCP, которое может использоваться, например, между кэширующими прокси, и не разработана исключительно или прежде всего для нужд протоколов маршрутизации.
TCP-AO is intended to replace (and thus obsolete) the use of TCP MD5. TCP-AO enhances the capabilities of TCP MD5 as summarized in Section 1.3. This document recommends overall that:
TCP-AO предназначена заменить (и тем самым сделать устаревшим) использование TCP MD5. TCP-AO расширяет возможности TCP MD5, как кратко описано в разделе 1.3. Настоящий документ в целом рекомендует следующее:
>> TCP implementations that support TCP MD5 MUST support TCP-AO.
>> Реализации TCP, поддерживающие TCP MD5, ДОЛЖНЫ поддерживать TCP-AO.
>> TCP-AO SHOULD be implemented where the protection afforded by TCP authentication is needed, because either IPsec is not supported or TCP-AO's particular properties are needed (e.g., per-connection keys).
>> TCP-AO СЛЕДУЕТ реализовывать там, где необходима защита, обеспечиваемая аутентификацией TCP, поскольку либо IPsec не поддерживается, либо нужны особые свойства TCP-AO (например, ключи для каждого соединения).
>> TCP-AO MAY be implemented elsewhere.
>> TCP-AO МОЖЕТ быть реализована в других местах.
TCP-AO is not intended to replace the use of the IPsec suite (IPsec and Internet Key Exchange Protocol (IKE)) to protect TCP connections [RFC4301][RFC4306]. Specific differences are noted in Section 1.3. In fact, we recommend the use of IPsec and IKE, especially where IKE's level of existing support for parameter negotiation, session key negotiation, or rekeying are desired. TCP-AO is intended for use only where the IPsec suite would not be feasible, e.g., as has been suggested is the case to support some routing protocols [RFC4953], or in cases where keys need to be tightly coordinated with individual transport sessions [Ed07].
TCP-AO не предназначена заменять использование набора IPsec (IPsec и протокол обмена ключами Интернета (IKE)) для защиты соединений TCP [RFC4301][RFC4306]. Конкретные различия отмечены в разделе 1.3. Фактически мы рекомендуем использовать IPsec и IKE, особенно там, где желателен существующий уровень поддержки IKE для согласования параметров, согласования сеансовых ключей или смены ключей. TCP-AO предназначена для использования только там, где набор IPsec был бы неосуществим, например, как было предложено для поддержки некоторых протоколов маршрутизации [RFC4953], или в случаях, когда ключи должны быть тесно согласованы с отдельными транспортными сеансами [Ed07].
TCP-AO is not intended to replace the use of Transport Layer Security (TLS) [RFC5246], Secure BGP (sBGP) or Secure Origin BGP (soBGP) [Le09], or any other mechanisms that protect only the TCP data stream. TCP-AO protects the transport layer, preventing attacks from disabling the TCP connection itself [RFC4953]. Data stream mechanisms protect only the contents of the TCP segments, and can be disrupted when the connection is affected. Some of these data protection protocols -- notably TLS -- offer a richer set of key management and authentication mechanisms than TCP-AO, and thus protect the data stream in a different way. TCP-AO may be used together with these data stream protections to complement each other's strengths.
TCP-AO не предназначена заменять использование безопасности транспортного уровня (TLS) [RFC5246], защищённого BGP (sBGP) или защищённого BGP с проверкой источника (soBGP) [Le09] либо любых других механизмов, защищающих только поток данных TCP. TCP-AO защищает транспортный уровень, не позволяя атакам отключать само соединение TCP [RFC4953]. Механизмы потока данных защищают только содержимое сегментов TCP и могут быть нарушены при воздействии на соединение. Некоторые из этих протоколов защиты данных — в частности TLS — предлагают более богатый набор механизмов управления ключами и аутентификации, чем TCP-AO, и поэтому защищают поток данных иным способом. TCP-AO может использоваться вместе с этими средствами защиты потока данных, чтобы дополнять сильные стороны друг друга.
1.3. Executive Summary
1.3. Краткое изложение
This document replaces TCP MD5 as follows [RFC2385]:
Настоящий документ заменяет TCP MD5 следующим образом [RFC2385]:
o TCP-AO uses a separate option Kind (29).
o TCP-AO использует отдельное значение Kind опции (29).
o TCP-AO allows TCP MD5 to continue to be used concurrently for legacy connections.
o TCP-AO позволяет продолжать одновременно использовать TCP MD5 для устаревших соединений.
o TCP-AO replaces TCP MD5's single MAC algorithm with MACs specified in a separate document and can be extended to include other MACs.
o TCP-AO заменяет единственный алгоритм MAC в TCP MD5 алгоритмами MAC, указанными в отдельном документе, и может быть расширена для включения других MAC.
o TCP-AO allows rekeying during a TCP connection, assuming that an out-of-band protocol or manual mechanism provides the new keys. The option includes a 'key ID', which allows the efficient concurrent use of multiple keys, and a key coordination mechanism using a 'receive next key ID' manages the key change within a connection. Note that TCP MD5 does not preclude rekeying during a connection, but does not require its support either. Further, TCP-AO supports key changes with zero segment loss, whereas key changes in TCP MD5 can lose segments in transit during the changeover or require trying multiple keys on each received segment during key use overlap because it lacks an explicit key ID. Although TCP recovers lost segments through retransmission, loss can have a substantial impact on performance.
o TCP-AO допускает смену ключей во время соединения TCP при условии, что внеполосный протокол или ручной механизм предоставляет новые ключи. Опция включает "key ID", что позволяет эффективно одновременно использовать несколько ключей, а механизм координации ключей с использованием "receive next key ID" управляет сменой ключа в пределах соединения. Отметим, что TCP MD5 не исключает смены ключей во время соединения, но и не требует её поддержки. Кроме того, TCP-AO поддерживает смену ключей без потери сегментов, тогда как смена ключей в TCP MD5 может приводить к потере сегментов в пути во время перехода или требовать проверки нескольких ключей для каждого принятого сегмента во время перекрытия использования ключей из-за отсутствия явного key ID. Хотя TCP восстанавливает потерянные сегменты путём повторной передачи, потери могут существенно повлиять на производительность.
o TCP-AO provides automatic replay protection for long-lived connections using sequence number extensions.
o TCP-AO обеспечивает автоматическую защиту от повторов для долгоживущих соединений с помощью расширений номера последовательности.
o TCP-AO ensures per-connection traffic keys as unique as the TCP connection itself, using TCP's Initial Sequence Numbers (ISNs) for differentiation, even when static master key tuples are used across repeated instances of connections on a single socket pair.
o TCP-AO обеспечивает транспортные ключи для каждого соединения настолько же уникальными, как само соединение TCP, используя начальные номера последовательности (ISN) TCP для различения, даже когда статические кортежи главных ключей используются для повторных экземпляров соединений на одной паре сокетов.
o TCP-AO specifies the details of how this option interacts with TCP's states, event processing, and user interface.
o TCP-AO определяет подробности того, как эта опция взаимодействует с состояниями TCP, обработкой событий и пользовательским интерфейсом.
o TCP-AO is 2 bytes shorter than TCP MD5 (16 bytes overall, rather than 18) in the initially specified default case (using a 96-bit MAC).
o TCP-AO на 2 байта короче TCP MD5 (16 байт в целом вместо 18) в первоначально заданном случае по умолчанию (при использовании MAC длиной 96 бит).

TCP-AO отличается от решения на основе IPsec/IKE следующим образом [RFC4301][RFC4306]:
o TCP-AO does not support dynamic parameter negotiation. o TCP-AO includes TCP's socket pair (source address, destination address, source port, destination port) as a security parameter index (together with the KeyID), rather than using a separate field as an index (IPsec's Security Parameter Index (SPI)).
o TCP-AO не поддерживает динамическое согласование параметров. o TCP-AO включает пару сокетов TCP (адрес источника, адрес назначения, порт источника, порт назначения) в качестве индекса параметров безопасности (вместе с KeyID), а не использует отдельное поле в качестве индекса (индекс параметров безопасности (SPI) в IPsec).
o TCP-AO forces a change of computed MACs when a connection restarts, even when reusing a TCP socket pair (IP addresses and port numbers) [Ed07].
o TCP-AO вынуждает изменять вычисляемые MAC при перезапуске соединения, даже если повторно используется пара сокетов TCP (IP-адреса и номера портов) [Ed07].

2.2. The TCP Authentication Option Format

3. TCP-AO Keys and Their Properties
3. Ключи TCP-AO и их свойства
TCP-AO relies on two sets of keys to authenticate incoming and outgoing segments: Master Key Tuples (MKTs) and traffic keys. MKTs are used to derive unique traffic keys, and include the keying material used to generate those traffic keys, as well as indicating the associated parameters under which traffic keys are used. Such parameters include whether TCP options are authenticated, and indicators of the algorithms used for traffic key derivation and MAC calculation. Traffic keys are the keying material used to compute the MAC of individual TCP segments.
TCP-AO опирается на два набора ключей для аутентификации входящих и исходящих сегментов: кортежи главных ключей (MKT) и транспортные ключи. MKT используются для вывода уникальных транспортных ключей и включают ключевой материал, применяемый для генерации этих транспортных ключей, а также указывают связанные параметры, при которых используются транспортные ключи. Такие параметры включают признак аутентификации опций TCP и указатели алгоритмов, используемых для вывода транспортных ключей и вычисления MAC. Транспортные ключи — это ключевой материал, используемый для вычисления MAC отдельных сегментов TCP.

5. Cryptographic Algorithms
5. Криптографические алгоритмы
TCP-AO uses cryptographic algorithms to compute the MAC (Message Authentication Code) that is used to authenticate a segment and its headers; these are called MAC algorithms and are specified in a separate document to facilitate updating the algorithm requirements independently from the protocol [RFC5926]. TCP-AO also uses cryptographic algorithms to convert MKTs, which can be shared across connections, into unique traffic keys for each connection. These are called Key Derivation Functions (KDFs) and are specified [RFC5926]. This section describes how these algorithms are used by TCP-AO.
TCP-AO использует криптографические алгоритмы для вычисления MAC (кода аутентификации сообщений), который служит для аутентификации сегмента и его заголовков; они называются алгоритмами MAC и определены в отдельном документе, чтобы можно было обновлять требования к алгоритмам независимо от протокола [RFC5926]. TCP-AO также использует криптографические алгоритмы для преобразования MKT, которые могут разделяться между соединениями, в уникальные транспортные ключи для каждого соединения. Они называются функциями вывода ключей (KDF) и определены в [RFC5926]. В настоящем разделе описывается, как эти алгоритмы используются в TCP-AO.

5.3. Traffic Key Establishment and Duration Issues
5.3. Вопросы установления и длительности транспортных ключей
TCP-AO does not provide a mechanism for traffic key negotiation or parameter negotiation (MAC algorithm, length, or use of TCP-AO on a connection), or for coordinating rekeying during a connection. We assume out-of-band mechanisms for MKT establishment, parameter negotiation, and rekeying. This separation of MKT use from MKT management is similar to that in the IPsec suite [RFC4301][RFC4306].
TCP-AO не предоставляет механизма согласования транспортных ключей или параметров (алгоритма MAC, длины или использования TCP-AO в соединении), а также координации смены ключей во время соединения. Мы предполагаем использование внеполосных механизмов для установления MKT, согласования параметров и смены ключей. Такое разделение использования MKT и управления MKT аналогично подходу в наборе IPsec [RFC4301][RFC4306].
We encourage users of TCP-AO to apply known techniques for generating appropriate MKTs, including the use of reasonable master key lengths, limited traffic key sharing, and limiting the duration of MKT use [RFC3562]. This also includes the use of per-connection nonces, as suggested in Section 5.2.
Мы призываем пользователей TCP-AO применять известные методы генерации подходящих MKT, включая использование разумных длин главных ключей, ограниченного совместного использования транспортных ключей и ограничения срока использования MKT [RFC3562]. Это также включает использование nonce для каждого соединения, как предложено в разделе 5.2.
TCP-AO supports rekeying in which new MKTs are negotiated and coordinated out of band, either via a protocol or a manual procedure [RFC4808]. New MKT use is coordinated using the out-of-band mechanism to update both TCP endpoints. When only a single MKT is used at a time, the temporary use of invalid MKTs could result in segments being dropped; although TCP is already robust to such drops, TCP-AO uses the KeyID field to avoid such drops. A given connection can have multiple matching MKTs, where the KeyID field is used to identify the MKT that corresponds to the traffic key used for a segment, to avoid the need for expensive trial-and-error testing of MKTs in sequence.
TCP-AO поддерживает смену ключей, при которой новые MKT согласуются и координируются вне полосы, с помощью протокола или ручной процедуры [RFC4808]. Использование нового MKT координируется с помощью внеполосного механизма обновления обеих конечных точек TCP. Когда одновременно используется только один MKT, временное использование недопустимых MKT могло бы привести к отбрасыванию сегментов; хотя TCP уже устойчив к таким потерям, TCP-AO использует поле KeyID, чтобы избежать таких потерь. Данное соединение может иметь несколько подходящих MKT, при этом поле KeyID используется для определения MKT, соответствующего транспортному ключу, применённому к сегменту, чтобы избежать необходимости дорогостоящей проверки MKT методом проб и ошибок по очереди.
TCP-AO provides an explicit MKT coordination mechanism, described in Section 6.1. Such a mechanism is useful when new MKTs are installed, or when MKTs are changed, to determine when to commence using installed MKTs.
TCP-AO предоставляет явный механизм координации MKT, описанный в разделе 6.1. Такой механизм полезен при установке новых MKT или при изменении MKT, чтобы определить, когда начинать использовать установленные MKT.
Users are advised to manage MKTs following the spirit of the advice for key management when using TCP MD5 [RFC3562], notably to use appropriate key lengths (12-24 bytes) and to avoid sharing MKTs among multiple BGP peering arrangements.
Пользователям рекомендуется управлять MKT в духе рекомендаций по управлению ключами при использовании TCP MD5 [RFC3562], в частности использовать подходящие длины ключей (12–24 байта) и избегать совместного использования MKT между несколькими схемами пиринга BGP.
5.3.1. MKT Reuse Across Socket Pairs
5.3.1. Повторное использование MKT в разных парах сокетов
MKTs can be reused across different socket pairs within a host, or across different instances of a socket pair within a host. In either case, replay protection is maintained.
MKT можно повторно использовать для разных пар сокетов в пределах узла или для разных экземпляров пары сокетов в пределах узла. В обоих случаях защита от повторов сохраняется.
MKTs reused across different socket pairs cannot enable replay attacks because the TCP socket pair is included in the MAC, as well as in the generation of the traffic key. MKTs reused across repeated instances of a given socket pair cannot enable replay attacks because the connection ISNs are included in the traffic key generation algorithm, and ISN pairs are unlikely to repeat over useful periods.
MKT, повторно используемые для разных пар сокетов, не могут позволить атаки повторного воспроизведения, поскольку пара сокетов TCP включается в MAC, а также в генерацию транспортного ключа. MKT, повторно используемые для повторных экземпляров данной пары сокетов, не могут позволить атаки повторного воспроизведения, поскольку ISN соединения включаются в алгоритм генерации транспортного ключа, а пары ISN вряд ли повторятся за полезные периоды времени.
5.3.2. MKTs Use within a Long-Lived Connection
5.3.2. Использование MKT в долгоживущем соединении
TCP-AO uses Sequence Number Extensions (SNEs) to prevent replay attacks within long-lived connections. Explicit MKT rollover, accomplished by external means and indexed using the KeyID field, can be used to change keying material for various reasons (e.g., personnel turnover), but is not required to support long-lived connections.
TCP-AO использует расширения номера последовательности (SNE) для предотвращения атак повторного воспроизведения в долгоживущих соединениях. Явная смена MKT, выполняемая внешними средствами и индексируемая с помощью поля KeyID, может использоваться для смены ключевого материала по разным причинам (например, из-за смены персонала), но не требуется для поддержки долгоживущих соединений.
6. Additional Security Mechanisms
6. Дополнительные механизмы безопасности
TCP-AO adds mechanisms to support efficient use, especially in environments where only manual keying is available. These include the previously described mechanisms for supporting multiple concurrent MKTs (via the KeyID field) and for generating unique per- connection traffic keys (via the KDF). This section describes additional mechanisms to coordinate MKT changes and to prevent replay attacks when a traffic key is not changed for long periods of time.
TCP-AO добавляет механизмы для поддержки эффективного использования, особенно в средах, где доступно только ручное управление ключами. К ним относятся описанные ранее механизмы поддержки нескольких одновременных MKT (через поле KeyID) и генерации уникальных транспортных ключей для каждого соединения (через KDF). В настоящем разделе описаны дополнительные механизмы координации изменений MKT и предотвращения атак повторного воспроизведения, когда транспортный ключ не меняется в течение длительного времени.
6.1. Coordinating Use of New MKTs
6.1. Координация использования новых MKT
At any given time, a single TCP connection may have multiple MKTs specified for each segment direction (incoming, outgoing). TCP-AO provides a mechanism to indicate when a new MKT is ready, which allows the sender to commence use of that new MKT. This mechanism allows new MKT use to be coordinated, to avoid unnecessary loss due to sender authentication using an MKT not yet ready at the receiver.
В любой момент времени для одного соединения TCP может быть указано несколько MKT для каждого направления сегментов (входящего, исходящего). TCP-AO предоставляет механизм указания готовности нового MKT, что позволяет отправителю начать использовать этот новый MKT. Этот механизм позволяет координировать использование нового MKT, чтобы избежать ненужных потерь из-за аутентификации отправителем с помощью MKT, ещё не готового у получателя.
Note that this is intended as an optimization. Deciding when to start using a key is a performance issue. Deciding when to remove an MKT is a security issue. Invalid MKTs are expected to be removed. TCP-AO provides no mechanism to coordinate their removal, as we consider this a key management operation.
Отметим, что это задумано как оптимизация. Решение о том, когда начать использовать ключ, — вопрос производительности. Решение о том, когда удалить MKT, — вопрос безопасности. Ожидается, что недопустимые MKT будут удалены. TCP-AO не предоставляет механизма координации их удаления, поскольку мы считаем это операцией управления ключами.

6.2. Preventing Replay Attacks within Long-Lived Connections
6.2. Предотвращение атак повторного воспроизведения в долгоживущих соединениях
TCP uses a 32-bit sequence number, which may, for long-lived connections, roll over and repeat. This could result in TCP segments being intentionally and legitimately replayed within a connection. TCP-AO prevents replay attacks, and thus requires a way to differentiate these legitimate replays from each other, and so it adds a 32-bit Sequence Number Extension (SNE) for transmitted and received segments.
TCP использует 32-битный номер последовательности, который для долгоживущих соединений может переполняться и повторяться. Это могло бы привести к тому, что сегменты TCP умышленно и правомерно воспроизводились бы в пределах соединения. TCP-AO предотвращает атаки повторного воспроизведения и поэтому нуждается в способе отличать такие правомерные повторы друг от друга, а потому добавляет 32-битное расширение номера последовательности (SNE) для переданных и принятых сегментов.
The SNE extends the TCP sequence number so that segments within a single connection are always unique. When the TCP's sequence number rolls over, there is a chance that a segment could be repeated in total; using an SNE differentiates even identical segments sent with identical sequence numbers at different times in a connection. TCP- AO emulates a 64-bit sequence number space by inferring when to increment the high-order 32-bit portion (the SNE) based on transitions in the low-order portion (the TCP sequence number).
SNE расширяет номер последовательности TCP так, что сегменты в пределах одного соединения всегда уникальны. Когда номер последовательности TCP переполняется, существует вероятность, что сегмент может повториться целиком; использование SNE различает даже идентичные сегменты, отправленные с одинаковыми номерами последовательности в разные моменты времени в соединении. TCP-AO эмулирует 64-битное пространство номеров последовательности, выводя момент увеличения старшей 32-битной части (SNE) на основе переходов в младшей части (номере последовательности TCP).
TCP-AO thus maintains SND.SNE for transmitted segments, and RCV.SNE for received segments, both initialized as zero when a connection begins. The intent of these SNEs is, together with TCP's 32-bit sequence numbers, to provide a 64-bit overall sequence number space.
Таким образом, TCP-AO поддерживает SND.SNE для переданных сегментов и RCV.SNE для принятых сегментов, причём оба инициализируются нулём при начале соединения. Назначение этих SNE вместе с 32-битными номерами последовательности TCP — обеспечить общее 64-битное пространство номеров последовательности.
For transmitted segments, SND.SNE can be implemented by extending TCP's sequence number to 64 bits; SND.SNE would be the top (high- order) 32 bits of that number. For received segments, TCP-AO needs to emulate the use of a 64-bit number space and correctly infer the appropriate high-order 32-bits of that number as RCV.SNE from the received 32-bit sequence number and the current connection context.
Для переданных сегментов SND.SNE можно реализовать, расширив номер последовательности TCP до 64 бит; SND.SNE был бы старшими 32 битами этого числа. Для принятых сегментов TCP-AO должен эмулировать использование 64-битного пространства номеров и правильно выводить соответствующие старшие 32 бита этого числа как RCV.SNE из принятого 32-битного номера последовательности и текущего контекста соединения.
The implementation of SNEs is not specified in this document, but one possible way is described here that can be used for either RCV.SNE, SND.SNE, or both.

Рассмотрим реализацию с двумя SNE, как требуется (SND.SNE, RCV.SNE), и дополнительными переменными, перечисленными ниже, все из которых инициализированы нулём, а также с полем текущего сегмента TCP (SEG.SEQ):
o SND.PREV_SEQ, needed to detect rollover of SND.SEQ
o SND.PREV_SEQ, необходимый для обнаружения переполнения SND.SEQ
o RCV.PREV_SEQ, needed to detect rollover of RCV.SEQ
o RCV.PREV_SEQ, необходимый для обнаружения переполнения RCV.SEQ
o SND.SNE_FLAG, which indicates when to increment the SND.SNE
o SND.SNE_FLAG, указывающий, когда увеличивать SND.SNE
o RCV.SNE_FLAG, which indicates when to increment the RCV.SNE
o RCV.SNE_FLAG, указывающий, когда увеличивать RCV.SNE
When a segment is received, the following algorithm (in C-like pseudocode) computes the SNE used in the MAC; this is the "RCV" side, and an equivalent algorithm can be applied to the "SND" side:
Когда сегмент принят, следующий алгоритм (на псевдокоде, подобном C) вычисляет SNE, используемый в MAC; это сторона "RCV", и эквивалентный алгоритм можно применить к стороне "SND":
/* set the flag when the SEG.SEQ first rolls over */ if ((RCV.SNE_FLAG == 0) && (RCV.PREV_SEQ > 0x7fff) && (SEG.SEQ < 0x7fff)) { RCV.SNE = RCV.SNE + 1; RCV.SNE_FLAG = 1; } /* decide which SNE to use after incremented */ if ((RCV.SNE_FLAG == 1) && (SEG.SEQ > 0x7fff)) { SNE = RCV.SNE - 1; # use the pre-increment value } else { SNE = RCV.SNE; # use the current value } /* reset the flag in the *middle* of the window */ if ((RCV.PREV_SEQ < 0x7fff) && (SEG.SEQ > 0x7fff)) { RCV.SNE_FLAG = 0; } /* save the current SEQ for the next time through the code */ RCV.PREV_SEQ = SEG.SEQ;
/* set the flag when the SEG.SEQ first rolls over */ if ((RCV.SNE_FLAG == 0) && (RCV.PREV_SEQ > 0x7fff) && (SEG.SEQ < 0x7fff)) { RCV.SNE = RCV.SNE + 1; RCV.SNE_FLAG = 1; } /* decide which SNE to use after incremented */ if ((RCV.SNE_FLAG == 1) && (SEG.SEQ > 0x7fff)) { SNE = RCV.SNE - 1; # use the pre-increment value } else { SNE = RCV.SNE; # use the current value } /* reset the flag in the *middle* of the window */ if ((RCV.PREV_SEQ < 0x7fff) && (SEG.SEQ > 0x7fff)) { RCV.SNE_FLAG = 0; } /* save the current SEQ for the next time through the code */ RCV.PREV_SEQ = SEG.SEQ;
In the above code, the first time the sequence number rolls over, i.e., when the new number is low (in the bottom half of the number space) and the old number is high (in the top half of the number space), the SNE is incremented and a flag is set.
В приведённом выше коде при первом переполнении номера последовательности, то есть когда новый номер мал (в нижней половине пространства номеров), а старый номер велик (в верхней половине пространства номеров), SNE увеличивается и устанавливается флаг.
If the flag is set and a high number is seen, it must be a reordered segment, so use the pre-increment SNE; otherwise, use the current SNE.
Если флаг установлен и виден большой номер, это должен быть переупорядоченный сегмент, поэтому используется SNE до увеличения; в противном случае используется текущий SNE.
The flag will be cleared by the time the number rolls all the way around.
Флаг будет сброшен к тому времени, когда номер совершит полный оборот.
The flag prevents the SNE from being incremented again until the flag is reset, which happens in the middle of the window (when the old number is in the bottom half and the new is in the top half). Because the receive window is never larger than half of the number space, it is impossible to both set and reset the flag at the same time -- outstanding segments, regardless of reordering, cannot straddle both regions simultaneously.
Флаг предотвращает повторное увеличение SNE до сброса флага, который происходит в середине окна (когда старый номер находится в нижней половине, а новый — в верхней). Поскольку окно приёма никогда не больше половины пространства номеров, невозможно одновременно установить и сбросить флаг — неподтверждённые сегменты, независимо от переупорядочения, не могут находиться в обеих областях сразу.
7. TCP-AO Interaction with TCP
7. Взаимодействие TCP-AO с TCP
The following is a description of how TCP-AO affects various TCP states, segments, events, and interfaces. This description is intended to augment the description of TCP as provided in RFC 793, and its presentation mirrors that of RFC 793 as a result [RFC793].
Ниже описано, как TCP-AO влияет на различные состояния, сегменты, события и интерфейсы TCP. Это описание предназначено дополнить описание TCP, приведённое в RFC 793, и поэтому его изложение повторяет изложение RFC 793 [RFC793].
7.1. TCP User Interface
7.1. Пользовательский интерфейс TCP
The TCP user interface supports active and passive OPEN, SEND, RECEIVE, CLOSE, STATUS, and ABORT commands. TCP-AO does not alter this interface as it applies to TCP, but some commands or command sequences of the interface need to be modified to support TCP-AO. TCP-AO does not specify the details of how this is achieved.
Пользовательский интерфейс TCP поддерживает команды активного и пассивного OPEN, SEND, RECEIVE, CLOSE, STATUS и ABORT. TCP-AO не изменяет этот интерфейс в той части, которая относится к TCP, но некоторые команды или последовательности команд интерфейса необходимо изменить для поддержки TCP-AO. TCP-AO не определяет подробности того, как это достигается.
TCP-AO requires that the TCP user interface be extended to allow the MKTs to be configured, as well as to allow an ongoing connection to manage which MKTs are active. The MKTs need to be configured prior to connection establishment, and the set of MKTs may change during a connection:
TCP-AO требует, чтобы пользовательский интерфейс TCP был расширен для настройки MKT, а также для того, чтобы текущее соединение могло управлять тем, какие MKT активны. MKT необходимо настроить до установления соединения, и набор MKT может изменяться во время соединения:
>> TCP OPEN, or the sequence of commands that configure a connection to be in the active or passive OPEN state, MUST be augmented so that an MKT can be configured.
>> TCP OPEN, или последовательность команд, которые настраивают соединение в активное или пассивное состояние OPEN, ДОЛЖНЫ быть расширены так, чтобы можно было настроить MKT.
>> A TCP-AO implementation MUST allow the set of MKTs for ongoing TCP connections (i.e., not in the CLOSED state) to be modified.
>> Реализация TCP-AO ДОЛЖНА позволять изменять набор MKT для текущих соединений TCP (то есть не находящихся в состоянии CLOSED).
The MKTs associated with a connection need to be available for confirmation; this includes the ability to read the MKTs:
MKT, связанные с соединением, должны быть доступны для подтверждения; это включает возможность чтения MKT:
>> TCP STATUS SHOULD be augmented to allow the MKTs of a current or pending connection to be read (for confirmation).
>> TCP STATUS СЛЕДУЕТ расширить, чтобы позволить читать MKT текущего или ожидающего соединения (для подтверждения).
Senders may need to be able to determine when the outgoing MKT changes (KeyID) or when a new preferred MKT (RNextKeyID) is indicated; these changes immediately affect all subsequent outgoing segments:
Отправителям может понадобиться определять, когда меняется исходящий MKT (KeyID) или когда указан новый предпочтительный MKT (RNextKeyID); эти изменения немедленно влияют на все последующие исходящие сегменты:
>> TCP SEND, or a sequence of commands resulting in a SEND, MUST be augmented so that the preferred outgoing MKT (current_key) and/or the preferred incoming MKT (rnext_key) of a connection can be indicated.
>> TCP SEND, или последовательность команд, приводящая к SEND, ДОЛЖНЫ быть расширены так, чтобы можно было указать предпочтительный исходящий MKT (current_key) и/или предпочтительный входящий MKT (rnext_key) соединения.
It may be useful to change the outgoing active MKT (current_key) even when no data is being sent, which can be achieved by sending a zero- length buffer or by using a non-send interface (e.g., socket options in Unix), depending on the implementation.
Может быть полезно изменить активный исходящий MKT (current_key), даже когда данные не отправляются; этого можно достичь, отправив буфер нулевой длины или используя не-SEND-интерфейс (например, параметры сокета в Unix), в зависимости от реализации.
It is also useful to indicate recent segment KeyID and RNextKeyID values received; although there could be a number of such values, they are not expected to change quickly, so any recent sample should be sufficient: >> TCP RECEIVE, or the sequence of commands resulting in a RECEIVE, MUST be augmented so that the KeyID and RNextKeyID of a recently received segment is available to the user out of band (e.g., as an additional parameter to RECEIVE or via a STATUS call).
Также полезно указывать значения KeyID и RNextKeyID недавно принятого сегмента; хотя таких значений может быть несколько, они не должны быстро меняться, поэтому любого недавнего образца должно быть достаточно: >> TCP RECEIVE, или последовательность команд, приводящая к RECEIVE, ДОЛЖНЫ быть расширены так, чтобы KeyID и RNextKeyID недавно принятого сегмента были доступны пользователю вне полосы (например, как дополнительный параметр RECEIVE или через вызов STATUS).
7.2. TCP States and Transitions
7.2. Состояния и переходы TCP
TCP includes the states LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT, and CLOSED.
TCP включает состояния LISTEN, SYN-SENT, SYN-RECEIVED, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT и CLOSED.
>> An MKT MAY be associated with any TCP state.
>> MKT МОЖЕТ быть связан с любым состоянием TCP.
7.3. TCP Segments
7.3. Сегменты TCP
TCP includes control (at least one of SYN, FIN, RST flags set) and data (none of SYN, FIN, or RST flags set) segments. Note that some control segments can include data (e.g., SYN).
TCP включает управляющие сегменты (установлен минимум один из флагов SYN, FIN, RST) и сегменты данных (ни один из флагов SYN, FIN и RST не установлен). Отметим, что некоторые управляющие сегменты могут нести данные (например, SYN).
>> All TCP segments MUST be checked against the set of MKTs for matching TCP connection identifiers.
>> Все сегменты TCP ДОЛЖНЫ проверяться на соответствие набору MKT по идентификаторам соединения TCP.
>> TCP segments whose TCP-AO does not validate MUST be silently discarded.
>> Сегменты TCP, для которых TCP-AO не проходит проверку, ДОЛЖНЫ молча отбрасываться.
>> A TCP-AO implementation MUST allow for configuration of the behavior of segments with TCP-AO but that do not match an MKT. The initial default of this configuration SHOULD be to silently accept such connections. If this is not the desired case, an MKT can be included to match such connections, or the connection can indicate that TCP-AO is required. Alternately, the configuration can be changed to discard segments with the AO option not matching an MKT.
>> Реализация TCP-AO ДОЛЖНА позволять настраивать поведение для сегментов с TCP-AO, которые не соответствуют ни одному MKT. Начальным значением по умолчанию этой настройки СЛЕДУЕТ считать молчаливый приём таких соединений. Если это нежелательно, можно включить MKT, соответствующий таким соединениям, или соединение может указать, что требуется TCP-AO. В качестве альтернативы настройку можно изменить так, чтобы отбрасывать сегменты с опцией AO, не соответствующей ни одному MKT.
>> Silent discard events SHOULD be signaled to the user as a warning, and silent accept events MAY be signaled to the user as a warning. Both warnings, if available, MUST be accessible via the STATUS interface. Either signal MAY be asynchronous, but if so, they MUST be rate-limited. Either signal MAY be logged; logging SHOULD allow rate-limiting as well.
>> События молчаливого отбрасывания СЛЕДУЕТ сигнализировать пользователю как предупреждение, а события молчаливого приёма МОГУТ сигнализироваться пользователю как предупреждение. Оба предупреждения, если они доступны, ДОЛЖНЫ быть доступны через интерфейс STATUS. Любой сигнал МОЖЕТ быть асинхронным, но в этом случае он ДОЛЖЕН быть ограничен по частоте. Любой сигнал МОЖЕТ регистрироваться в журнале; регистрация СЛЕДУЕТ также допускать ограничение частоты.
All TCP-AO processing occurs between the interface of TCP and IP; for incoming segments, this occurs after validation of the TCP checksum. For outgoing segments, this occurs before computation of the TCP checksum. Note that use of TCP-AO on a connection is not negotiated within TCP. It is the responsibility of the receiver to determine when TCP-AO is required via other means (e.g., out of band, manually or with a key management protocol) and to enforce that requirement.
Вся обработка TCP-AO происходит между интерфейсом TCP и IP; для входящих сегментов это происходит после проверки контрольной суммы TCP. Для исходящих сегментов это происходит до вычисления контрольной суммы TCP. Отметим, что использование TCP-AO в соединении не согласуется внутри TCP. Получатель обязан определять, когда требуется TCP-AO, другими средствами (например, вне полосы, вручную или с помощью протокола управления ключами) и обеспечивать выполнение этого требования.
7.4. Sending TCP Segments
7.4. Отправка сегментов TCP
The following procedure describes the modifications to TCP to support inserting TCP-AO when a segment departs.
Следующая процедура описывает изменения в TCP для поддержки вставки TCP-AO при отправке сегмента.
>> Note that TCP-AO MUST be the last TCP option processed on outgoing segments, because its MAC calculation may include the values of other TCP options.
>> Отметим, что TCP-AO ДОЛЖНА быть последней опцией TCP, обрабатываемой в исходящих сегментах, поскольку её вычисление MAC может включать значения других опций TCP.
1. Find the per-connection parameters for the segment:
1. Найти параметры для данного сегмента, действующие для соединения:
a. If the segment is a SYN, then this is the first segment of a new connection. Find the matching MKT for this segment based on the segment's socket pair.
a. Если сегмент является SYN, то это первый сегмент нового соединения. Найти соответствующий MKT для этого сегмента по паре сокетов сегмента.
i. If there is no matching MKT, omit TCP-AO. Proceed with transmitting the segment.
i. Если подходящего MKT нет, не включать TCP-AO. Продолжить передачу сегмента.
ii. If there is a matching MKT, then set the per-connection parameters as needed (see Section 4). Proceed with the step 2.
ii. Если подходящий MKT есть, задать параметры соединения, как требуется (см. раздел 4). Перейти к шагу 2.
b. If the segment is not a SYN, then determine whether TCP-AO is being used for the connection and use the MKT as indicated by the current_key value from the per-connection parameters (see Section 4) and proceed with the step 2.
b. Если сегмент не является SYN, определить, используется ли TCP-AO для соединения, и использовать MKT, указанный значением current_key из параметров соединения (см. раздел 4), затем перейти к шагу 2.
2. Using the per-connection parameters:
2. Используя параметры соединения:
a. Augment the TCP header with TCP-AO, inserting the appropriate Length and KeyID based on the MKT indicated by current_key (using the current_key MKT's SendID as the TCP-AO KeyID). Update the TCP header length accordingly.
a. Дополнить заголовок TCP опцией TCP-AO, вставив соответствующие Length и KeyID на основе MKT, указанного current_key (используя SendID MKT current_key как KeyID в TCP-AO). Соответственно обновить длину заголовка TCP.
b. Determine SND.SNE as described in Section 6.2.
b. Определить SND.SNE, как описано в разделе 6.2.
c. Determine the appropriate traffic key, i.e., as pointed to by the current_key (as noted in Section 6.1, and as probably cached in the TCB). That is, use the send_SYN_traffic_key for SYN segments and the send_other_traffic_key for other segments.
c. Определить соответствующий транспортный ключ, то есть тот, на который указывает current_key (как отмечено в разделе 6.1 и, вероятно, кэшированный в TCB). А именно использовать send_SYN_traffic_key для сегментов SYN и send_other_traffic_key для остальных сегментов.
d. Determine the RNextKeyID as indicated by the rnext_key pointer, and insert it in the TCP-AO RNextKeyID field (using the rnext_key MKT's RecvID as the TCP-AO KeyID) (as noted in Section 6.1).
d. Определить RNextKeyID, как указано указателем rnext_key, и вставить его в поле RNextKeyID опции TCP-AO (используя RecvID MKT rnext_key как KeyID в TCP-AO) (как отмечено в разделе 6.1).
e. Compute the MAC using the MKT (and cached traffic key) and data from the segment as specified in Section 5.1.
e. Вычислить MAC с использованием MKT (и кэшированного транспортного ключа) и данных сегмента, как указано в разделе 5.1.
f. Insert the MAC in the TCP-AO MAC field.
f. Вставить MAC в поле MAC опции TCP-AO.
g. Proceed with transmitting the segment.
g. Продолжить передачу сегмента.
7.5. Receiving TCP Segments
7.5. Получение сегментов TCP
The following procedure describes the modifications to TCP to support TCP-AO when a segment arrives.
Следующая процедура описывает изменения в TCP для поддержки TCP-AO при поступлении сегмента.
>> Note that TCP-AO MUST be the first TCP option processed on incoming segments, because its MAC calculation may include the values of other TCP options that could change during TCP option processing. This also protects the behavior of all other TCP options from the impact of spoofed segments or modified header information.
>> Отметим, что TCP-AO ДОЛЖНА быть первой опцией TCP, обрабатываемой во входящих сегментах, поскольку её вычисление MAC может включать значения других опций TCP, которые могут измениться во время обработки опций TCP. Это также защищает поведение всех остальных опций TCP от воздействия поддельных сегментов или изменённой информации заголовка.
>> Note that TCP-AO checks MUST be performed for all incoming SYNs to avoid accepting SYNs lacking TCP-AO where required. Other segments can cache whether TCP-AO is needed in the TCB.
>> Отметим, что проверки TCP-AO ДОЛЖНЫ выполняться для всех входящих SYN, чтобы избежать приёма SYN без TCP-AO там, где он требуется. Остальные сегменты могут кэшировать в TCB сведения о том, нужен ли TCP-AO.
1. Find the per-connection parameters for the segment:
1. Найти параметры для данного сегмента, действующие для соединения:
a. If the segment is a SYN, then this is the first segment of a new connection. Find the matching MKT for this segment, using the segment's socket pair and its TCP-AO KeyID, matched against the MKT's TCP connection identifier and the MKT's RecvID.
a. Если сегмент является SYN, то это первый сегмент нового соединения. Найти соответствующий MKT для этого сегмента, используя пару сокетов сегмента и его KeyID в TCP-AO, сопоставленные с идентификатором соединения TCP у MKT и RecvID у MKT.
i. If there is no matching MKT, remove TCP-AO from the segment. Proceed with further TCP handling of the segment.
i. Если подходящего MKT нет, удалить TCP-AO из сегмента. Продолжить дальнейшую обработку сегмента средствами TCP.
NOTE: this presumes that connections that do not match any MKT should be silently accepted, as noted in Section 7.3.
ПРИМЕЧАНИЕ: это предполагает, что соединения, не соответствующие ни одному MKT, должны молча приниматься, как отмечено в разделе 7.3.
ii. If there is a matching MKT, then set the per-connection parameters as needed (see Section 4). Proceed with step 2.
ii. Если подходящий MKT есть, задать параметры соединения, как требуется (см. раздел 4). Перейти к шагу 2.
2. Using the per-connection parameters:
2. Используя параметры соединения:
a. Check that the segment's TCP-AO Length matches the length indicated by the MKT.
a. Проверить, что Length в TCP-AO сегмента соответствует длине, указанной MKT.
i. If the lengths differ, silently discard the segment. Log and/or signal the event as indicated in Section 7.3.
i. Если длины различаются, молча отбросить сегмент. Зарегистрировать и/или сигнализировать событие, как указано в разделе 7.3.
b. Determine the segment's RCV.SNE as described in Section 6.2.
b. Определить RCV.SNE сегмента, как описано в разделе 6.2.
c. Determine the segment's traffic key from the MKT as described in Section 5.1 (and as likely cached in the TCB). That is, use the receive_SYN_traffic_key for SYN segments and the receive_other_traffic_key for other segments.
c. Определить транспортный ключ сегмента из MKT, как описано в разделе 5.1 (и, вероятно, кэшированного в TCB). А именно использовать receive_SYN_traffic_key для сегментов SYN и receive_other_traffic_key для остальных сегментов.
d. Compute the segment's MAC using the MKT (and its derived traffic key) and portions of the segment as indicated in Section 5.1.
d. Вычислить MAC сегмента с использованием MKT (и выведенного из него транспортного ключа) и частей сегмента, как указано в разделе 5.1.
i. If the computed MAC differs from the TCP-AO MAC field value, silently discard the segment. Log and/or signal the event as indicated in Section 7.3.
i. Если вычисленный MAC отличается от значения поля MAC в TCP-AO, молча отбросить сегмент. Зарегистрировать и/или сигнализировать событие, как указано в разделе 7.3.
e. Compare the received RNextKeyID value to the currently active outgoing KeyID value (current_key MKT's SendID).
e. Сравнить принятое значение RNextKeyID с текущим активным значением KeyID для исходящих сегментов (SendID MKT current_key).
i. If they match, no further action is required.
i. Если они совпадают, дальнейших действий не требуется.
ii. If they differ, determine whether the RNextKeyID MKT is ready.
ii. Если они различаются, определить, готов ли MKT с данным RNextKeyID.
1. If the MKT corresponding to the segment's socket pair and RNextKeyID is not available, no action is required (RNextKeyID of a received segment needs to match the MKT's SendID).
1. Если MKT, соответствующий паре сокетов сегмента и RNextKeyID, недоступен, никаких действий не требуется (RNextKeyID принятого сегмента должен совпадать с SendID MKT).
2. If the matching MKT corresponding to the segment's socket pair and RNextKeyID is available:
2. Если соответствующий MKT для пары сокетов сегмента и RNextKeyID доступен:
a. Set current_key to the RNextKeyID MKT.
a. Установить current_key равным MKT с данным RNextKeyID.
f. Proceed with TCP processing of the segment.
f. Продолжить обработку сегмента средствами TCP.
It is suggested that TCP-AO implementations validate a segment's Length field before computing a MAC to reduce the overhead incurred by spoofed segments with invalid TCP-AO fields. Additional reductions in MAC validation overhead can be supported in the MAC algorithms, e.g., by using a computation algorithm that prepends a fixed value to the computed portion and a corresponding validation algorithm that verifies the fixed value before investing in the computed portion. Such optimizations would be contained in the MAC algorithm specification, and thus are not specified in TCP-AO explicitly. Note that the KeyID cannot be used for connection validation per se, because it is not assumed random.
Предлагается, чтобы реализации TCP-AO проверяли поле Length сегмента до вычисления MAC, чтобы снизить накладные расходы, вызванные поддельными сегментами с недопустимыми полями TCP-AO. Дополнительное снижение накладных расходов на проверку MAC может поддерживаться в алгоритмах MAC, например путём использования алгоритма вычисления, который добавляет фиксированное значение к вычисляемой части, и соответствующего алгоритма проверки, который проверяет фиксированное значение до затрат на вычисляемую часть. Такие оптимизации содержались бы в спецификации алгоритма MAC и поэтому явно не определены в TCP-AO. Отметим, что KeyID нельзя использовать для проверки соединения как таковой, поскольку он не предполагается случайным.
7.6. Impact on TCP Header Size
7.6. Влияние на размер заголовка TCP
TCP-AO, using the initially required 96-bit MACs, uses a total of 16 bytes of TCP header space [RFC5926]. TCP-AO is thus 2 bytes smaller than the TCP MD5 option (18 bytes).
TCP-AO при использовании первоначально требуемых MAC длиной 96 бит занимает в общей сложности 16 байт пространства заголовка TCP [RFC5926]. Таким образом, TCP-AO на 2 байта меньше опции TCP MD5 (18 байт).
Note that the TCP option space is most critical in SYN segments, because flags in those segments could potentially increase the option space area in other segments. Because TCP ignores unknown segments, however, it is not possible to extend the option space of SYNs without breaking backward compatibility.
Отметим, что пространство опций TCP наиболее критично в сегментах SYN, поскольку флаги в этих сегментах потенциально могли бы увеличить область пространства опций в других сегментах. Однако, поскольку TCP игнорирует неизвестные сегменты, невозможно расширить пространство опций SYN, не нарушив обратную совместимость.
TCP's 4-bit data offset requires that the options end 60 bytes (15 32-bit words) after the header begins, including the 20-byte header. This leaves 40 bytes for options, of which 15 are expected in current implementations (listed below), leaving at most 25 for other uses. TCP-AO consumes 16 bytes, leaving 9 bytes for additional SYN options (depending on implementation dependant alignment padding, which could consume another 2 bytes at most).
4-битное смещение данных в TCP требует, чтобы опции заканчивались через 60 байт (15 32-битных слов) после начала заголовка, включая 20-байтовый заголовок. Это оставляет 40 байт для опций, из которых 15 ожидаются в текущих реализациях (перечислены ниже), оставляя не более 25 для других целей. TCP-AO занимает 16 байт, оставляя 9 байт для дополнительных опций SYN (в зависимости от выравнивающего заполнения, зависящего от реализации, которое может занять ещё до 2 байт).
o SACK permitted (2 bytes) [RFC2018][RFC3517]
o Разрешён SACK (2 байта) [RFC2018][RFC3517]
o Timestamps (10 bytes) [RFC1323]
o Временные метки (10 байт) [RFC1323]
o Window scale (3 bytes) [RFC1323]
o Масштабирование окна (3 байта) [RFC1323]
After a SYN, the following options are expected in current implementations of TCP:
После сегмента SYN в текущих реализациях TCP ожидаются следующие опции:
o SACK (10bytes) [RFC2018][RFC3517] (18 bytes if D-SACK [RFC2883])
o SACK (10 байт) [RFC2018][RFC3517] (18 байт, если D-SACK [RFC2883])
o Timestamps (10 bytes) [RFC1323]
o Временные метки (10 байт) [RFC1323]
TCP-AO continues to consume 16 bytes in non-SYN segments, leaving a total of 24 bytes for other options, of which the timestamp consumes 10. This leaves 14 bytes, of which 10 are used for a single SACK block. When two SACK blocks are used, such as to handle D-SACK, a smaller TCP-AO MAC would be required to make room for the additional SACK block (i.e., to leave 18 bytes for the D-SACK variant of the SACK option) [RFC2883]. Note that D-SACK is not supportable in TCP MD5 in the presence of timestamps, because TCP MD5's MAC length is fixed and too large to leave sufficient option space.
TCP-AO продолжает занимать 16 байт в сегментах, не являющихся SYN, оставляя в общей сложности 24 байта для других опций, из которых временная метка занимает 10. Это оставляет 14 байт, из которых 10 используются для одного блока SACK. Когда используются два блока SACK, например для обработки D-SACK, потребовался бы MAC меньшей длины в TCP-AO, чтобы освободить место для дополнительного блока SACK (то есть оставить 18 байт для варианта D-SACK опции SACK) [RFC2883]. Отметим, что D-SACK не поддерживается в TCP MD5 при наличии временных меток, поскольку длина MAC в TCP MD5 фиксирована и слишком велика, чтобы оставить достаточно места для опций.
Although TCP option space is limited, we believe TCP-AO is consistent with the desire to authenticate TCP at the connection level for similar uses as were intended by TCP MD5.
Хотя пространство опций TCP ограничено, мы считаем, что TCP-AO согласуется с желанием аутентифицировать TCP на уровне соединения для тех же целей, для которых предназначался TCP MD5.
7.7. Connectionless Resets
7.7. Сбросы без установления соединения
TCP-AO allows TCP resets (RSTs) to be exchanged provided both sides have established valid connection state. After such state is established, if one side reboots, TCP-AO prevents TCP's RST mechanism from clearing out old state on the side that did not reboot. This happens because the rebooting side has lost its connection state, and thus its traffic keys.
TCP-AO позволяет обмениваться сбросами TCP (RST) при условии, что обе стороны установили допустимое состояние соединения. После установления такого состояния, если одна сторона перезагружается, TCP-AO не позволяет механизму RST протокола TCP очистить старое состояние на стороне, которая не перезагружалась. Это происходит потому, что перезагрузившаяся сторона потеряла своё состояние соединения, а значит, и свои транспортные ключи.
It is important that implementations are capable of detecting excesses of TCP connections in such a configuration and can clear them out if needed to protect its memory usage [Ba10]. To protect against such state from accumulating and not being cleared out, a number of recommendations are made:
Важно, чтобы реализации были способны обнаруживать избыток соединений TCP в такой конфигурации и могли очищать их при необходимости для защиты использования памяти [Ba10]. Для защиты от накопления такого состояния без очистки даются следующие рекомендации:
>> Connections using TCP-AO SHOULD also use TCP keepalives [RFC1122].
>> Соединениям, использующим TCP-AO, СЛЕДУЕТ также использовать keepalive TCP [RFC1122].
The use of TCP keepalives ensures that connections whose keys are lost are terminated after a finite time; a similar effect can be achieved at the application layer, e.g., with BGP keepalives [RFC4271]. Either kind of keepalive helps ensure the TCP state is cleared out in such a case; the alternative, of allowing unauthenticated RSTs to be received, would allow one of the primary vulnerabilities that TCP-AO is intended to prevent.
Использование keepalive TCP гарантирует, что соединения, ключи которых потеряны, завершаются через конечное время; аналогичный эффект может быть достигнут на прикладном уровне, например с помощью keepalive BGP [RFC4271]. Любой из этих видов keepalive помогает обеспечить очистку состояния TCP в таком случае; альтернатива — приём неаутентифицированных RST — позволила бы одну из основных уязвимостей, которую TCP-AO призвана предотвращать.
Keepalives ensure that connections are dropped across reboots, but this can have a detrimental effect on some protocols. Specifically, BGP reacts poorly to such connection drops, even if caused by the use of BGP keepalives; "graceful restart" was introduced to address this effect [RFC4724], and extended to support BGP with MPLS [RFC4781]. As a result:
Keepalive гарантируют, что соединения разрываются при перезагрузках, но это может неблагоприятно влиять на некоторые протоколы. В частности, BGP плохо реагирует на такие разрывы соединений, даже если они вызваны использованием keepalive BGP; "грациозный перезапуск" (graceful restart) был введён для устранения этого эффекта [RFC4724] и расширен для поддержки BGP с MPLS [RFC4781]. В результате:
>> BGP connections SHOULD require support for graceful restart when using TCP-AO. We recognize that support for graceful restart is not always feasible. As a result:
>> Соединения BGP СЛЕДУЕТ требовать поддержки грациозного перезапуска при использовании TCP-AO. Мы признаём, что поддержка грациозного перезапуска не всегда осуществима. В результате:
>> When BGP without graceful restart is used with TCP-AO, both sides of the connection SHOULD save traffic keys in storage that persists across reboots and restore them after a reboot, and SHOULD limit any performance impacts that result from this storage/restoration.
>> Когда BGP без грациозного перезапуска используется с TCP-AO, обе стороны соединения СЛЕДУЕТ сохранять транспортные ключи в хранилище, устойчивом к перезагрузкам, и восстанавливать их после перезагрузки, а также СЛЕДУЕТ ограничивать любые влияния на производительность, возникающие из-за этого сохранения/восстановления.
7.8. ICMP Handling
7.8. Обработка ICMP
TCP can be attacked both in band, using TCP segments, or out of band using ICMP. ICMP packets cannot be protected using TCP-AO mechanisms; however, in this way, both TCP-AO and IPsec do not directly solve the need for protected ICMP signaling. TCP-AO does make specific recommendations on how to handle certain ICMPs, beyond what IPsec requires, and these are made possible because TCP-AO operates inside the context of a TCP connection.
TCP может подвергаться атакам как в полосе, с помощью сегментов TCP, так и вне полосы, с помощью ICMP. Пакеты ICMP нельзя защитить механизмами TCP-AO; однако, таким образом, ни TCP-AO, ни IPsec напрямую не решают задачу защищённой сигнализации ICMP. TCP-AO даёт конкретные рекомендации о том, как обрабатывать определённые сообщения ICMP, сверх того, что требует IPsec, и они возможны потому, что TCP-AO работает в контексте соединения TCP.
IPsec makes recommendations regarding dropping ICMPs in certain contexts or requiring that they are endpoint authenticated in others [RFC4301]. There are other mechanisms proposed to reduce the impact of ICMP attacks by further validating ICMP contents and changing the effect of some messages based on TCP state, but these do not provide the level of authentication for ICMP that TCP-AO provides for TCP [Go10]. As a result, we recommend a conservative approach to accepting ICMP messages as summarized in [Go10]:
IPsec даёт рекомендации относительно отбрасывания ICMP в определённых контекстах или требования их аутентификации конечной точкой в других [RFC4301]. Предлагаются и другие механизмы для снижения воздействия атак ICMP путём дополнительной проверки содержимого ICMP и изменения эффекта некоторых сообщений в зависимости от состояния TCP, но они не обеспечивают такого уровня аутентификации ICMP, какой TCP-AO обеспечивает для TCP [Go10]. В результате мы рекомендуем консервативный подход к приёму сообщений ICMP, кратко изложенный в [Go10]:
>> A TCP-AO implementation MUST default to ignore incoming ICMPv4 messages of Type 3 (destination unreachable), Codes 2-4 (protocol unreachable, port unreachable, and fragmentation needed -- 'hard errors'), and ICMPv6 Type 1 (destination unreachable), Code 1 (administratively prohibited) and Code 4 (port unreachable) intended for connections in synchronized states (ESTABLISHED, FIN-WAIT-1, FIN- WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT) that match MKTs.
>> Реализация TCP-AO ДОЛЖНА по умолчанию игнорировать входящие сообщения ICMPv4 типа 3 (назначение недостижимо) с кодами 2–4 (протокол недостижим, порт недостижим и требуется фрагментация — "жёсткие ошибки"), а также ICMPv6 типа 1 (назначение недостижимо) с кодом 1 (административно запрещено) и кодом 4 (порт недостижим), предназначенные для соединений в синхронизированных состояниях (ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK, TIME-WAIT), которые соответствуют MKT.
>> A TCP-AO implementation SHOULD allow whether such ICMPs are ignored to be configured on a per-connection basis.
>> Реализация TCP-AO СЛЕДУЕТ позволять настраивать, игнорируются ли такие сообщения ICMP, для каждого соединения отдельно.
>> A TCP-AO implementation SHOULD implement measures to protect ICMP "packet too big" messages, some examples of which are discussed in [Go10].
>> Реализация TCP-AO СЛЕДУЕТ реализовывать меры защиты сообщений ICMP "packet too big", некоторые примеры которых обсуждаются в [Go10].
>> An implementation SHOULD allow ignored ICMPs to be logged.
>> Реализации СЛЕДУЕТ позволять регистрировать игнорируемые ICMP в журнале.
This control affects only ICMPs that currently require 'hard errors', which would abort the TCP connection [RFC1122]. This recommendation is intended to be similar to how IPsec would handle those messages, with an additional default assumed [RFC4301].
Этот контроль затрагивает только сообщения ICMP, которые в настоящее время требуют "жёстких ошибок", то есть приводят к прерыванию соединения TCP [RFC1122]. Эта рекомендация задумана аналогичной тому, как IPsec обрабатывал бы такие сообщения, с дополнительным значением по умолчанию [RFC4301].
8. Obsoleting TCP MD5 and Legacy Interactions
8. Замена TCP MD5 и взаимодействие с устаревшими системами
TCP-AO obsoletes TCP MD5. As we have noted earlier:
TCP-AO заменяет TCP MD5. Как мы отмечали ранее:
>> TCP implementations that support TCP MD5 MUST support TCP-AO.
>> Реализации TCP, поддерживающие TCP MD5, ДОЛЖНЫ поддерживать TCP-AO.
Systems implementing TCP MD5 only are considered legacy, and ought to be upgraded when possible. In order to support interoperation with such legacy systems until upgrades are available:
Системы, реализующие только TCP MD5, считаются устаревшими, и их следует, по возможности, модернизировать. Чтобы поддержать взаимодействие с такими устаревшими системами до появления обновлений:
>> TCP MD5 SHOULD be supported where interactions with legacy systems are needed.
>> TCP MD5 СЛЕДУЕТ поддерживать там, где необходимо взаимодействие с устаревшими системами.
>> A system that supports both TCP-AO and TCP MD5 MUST use TCP-AO for connections unless not supported by its peer, at which point it MAY use TCP MD5 instead.
>> Система, поддерживающая и TCP-AO, и TCP MD5, ДОЛЖНА использовать TCP-AO для соединений, если только это не поддерживается её партнёром, и в этом случае она МОЖЕТ использовать вместо него TCP MD5.
>> A TCP implementation MUST NOT use both TCP-AO and TCP MD5 for a particular TCP connection, but MAY support TCP-AO and TCP MD5 simultaneously for different connections (notably to support legacy use of TCP MD5).
>> Реализация TCP НЕ ДОЛЖНА использовать одновременно TCP-AO и TCP MD5 для конкретного соединения TCP, но МОЖЕТ поддерживать TCP-AO и TCP MD5 одновременно для разных соединений (в частности, для поддержки устаревшего использования TCP MD5).
The Kind value explicitly indicates whether TCP-AO or TCP MD5 is used for a particular connection in TCP segments.
Значение Kind явно указывает, используется ли TCP-AO или TCP MD5 для конкретного соединения в сегментах TCP.
It is possible that MKTs could be augmented to support TCP MD5, although use of MKTs is not described in RFC 2385.
Возможно, MKT можно было бы расширить для поддержки TCP MD5, хотя использование MKT не описано в RFC 2385.
It is possible to require TCP-AO for a connection or TCP MD5, but it is not possible to require 'either'. When an endpoint is configured to require TCP MD5 for a connection, it must be added to all outgoing segments and validated on all incoming segments [RFC2385]. TCP MD5's requirements prohibit the speculative use of both options for a given connection, e.g., to be decided by the other end of the connection.
Можно потребовать TCP-AO для соединения или TCP MD5, но нельзя потребовать "любой из них". Когда конечная точка настроена требовать TCP MD5 для соединения, он должен добавляться ко всем исходящим сегментам и проверяться на всех входящих сегментах [RFC2385]. Требования TCP MD5 запрещают предположительное использование обеих опций для данного соединения, например с решением, принимаемым другим концом соединения.
9. Interactions with Middleboxes
9. Взаимодействие с промежуточными устройствами
TCP-AO may interact with middleboxes, depending on their behavior [RFC3234]. Some middleboxes either alter TCP options (such as TCP- AO) directly or alter the information TCP-AO includes in its MAC calculation. TCP-AO may interfere with these devices, exactly where the device modifies information TCP-AO is designed to protect.
TCP-AO может взаимодействовать с промежуточными устройствами в зависимости от их поведения [RFC3234]. Некоторые промежуточные устройства либо напрямую изменяют опции TCP (такие как TCP-AO), либо изменяют информацию, которую TCP-AO включает в вычисление своего MAC. TCP-AO может мешать этим устройствам именно там, где устройство изменяет информацию, которую TCP-AO призвана защищать.
9.1. Interactions with Non-NAT/NAPT Middleboxes
9.1. Взаимодействие с промежуточными устройствами без NAT/NAPT
TCP-AO supports middleboxes that do not change the IP addresses or ports of segments. Such middleboxes may modify some TCP options, in which case TCP-AO would need to be configured to ignore all options in the MAC calculation on connections traversing that element.
TCP-AO поддерживает промежуточные устройства, которые не изменяют IP-адреса или порты сегментов. Такие устройства могут изменять некоторые опции TCP; в этом случае TCP-AO потребовалось бы настроить так, чтобы игнорировать все опции при вычислении MAC для соединений, проходящих через этот элемент.
Note that ignoring TCP options may provide less protection, i.e., TCP options could be modified in transit, and such modifications could be used by an attacker. Depending on the modifications, TCP could have compromised efficiency (e.g., timestamp changes), or could cease correct operation (e.g., window scale changes). These vulnerabilities affect only the TCP connections for which TCP-AO is configured to ignore TCP options.
Отметим, что игнорирование опций TCP может обеспечить меньшую защиту, то есть опции TCP могут быть изменены при передаче, и такие изменения могут быть использованы атакующим. В зависимости от изменений TCP может потерять эффективность (например, при изменении временных меток) или прекратить корректную работу (например, при изменении масштабирования окна). Эти уязвимости затрагивают только те соединения TCP, для которых TCP-AO настроена игнорировать опции TCP.
9.2. Interactions with NAT/NAPT Devices
9.2. Взаимодействие с устройствами NAT/NAPT
TCP-AO cannot interoperate natively across NAT/NAPT (Network Address Port Translation) devices, which modify the IP addresses and/or port numbers. We anticipate that traversing such devices may require variants of existing NAT/NAPT traversal mechanisms, e.g., encapsulation of the TCP-AO-protected segment in another transport segment (e.g., UDP), as is done in IPsec [RFC2663][RFC3947]. Such variants can be adapted for use with TCP-AO, or IPsec with NAT traversal can be used instead of TCP-AO in such cases [RFC3947].
TCP-AO не может работать изначально через устройства NAT/NAPT (трансляции сетевых адресов и портов), которые изменяют IP-адреса и/или номера портов. Мы предполагаем, что для прохождения через такие устройства могут потребоваться варианты существующих механизмов прохождения NAT/NAPT, например инкапсуляция защищённого TCP-AO сегмента в другой транспортный сегмент (например, UDP), как это делается в IPsec [RFC2663][RFC3947]. Такие варианты можно адаптировать для использования с TCP-AO, или в таких случаях вместо TCP-AO можно использовать IPsec с прохождением NAT [RFC3947].
An alternate proposal for accommodating NATs extends TCP-AO independently of this specification [To10].
Альтернативное предложение по поддержке NAT расширяет TCP-AO независимо от настоящей спецификации [To10].

10. Оценка выполнения требований
TCP-AO satisfies all the current requirements for a revision to TCP MD5, as summarized below [Ed07].
TCP-AO удовлетворяет всем текущим требованиям к пересмотру TCP MD5, как кратко изложено ниже [Ed07].

This is supported -- see Section 5.1.

11. Security Considerations
11. Вопросы безопасности
Use of TCP-AO, like the use of TCP MD5 or IPsec, will impact host performance. Connections that are known to use TCP-AO can be attacked by transmitting segments with invalid MACs. Attackers would need to know only the TCP connection ID and TCP-AO Length value to substantially impact the host's processing capacity. This is similar to the susceptibility of IPsec to on-path attacks, where the IP addresses and SPI would be visible. For IPsec, the entire SPI space (32 bits) is arbitrary, whereas for routing protocols typically only the source port (16 bits) is arbitrary (typically with less than 16 bits of randomness [La10]). As a result, it would be easier for an off-path attacker to spoof a TCP-AO segment that could cause receiver validation effort. However, we note that between Internet routers, both ports could be arbitrary (i.e., determined a priori out of band), which would constitute roughly the same off-path antispoofing protection of an arbitrary SPI.
Использование TCP-AO, как и использование TCP MD5 или IPsec, влияет на производительность узла. Соединения, о которых известно, что они используют TCP-AO, могут подвергаться атакам путём передачи сегментов с недопустимыми MAC. Атакующим достаточно знать только идентификатор соединения TCP и значение Length в TCP-AO, чтобы существенно повлиять на вычислительную способность узла. Это аналогично подверженности IPsec атакам на пути, где IP-адреса и SPI были бы видны. В IPsec всё пространство SPI (32 бита) произвольно, тогда как для протоколов маршрутизации обычно произволен только порт источника (16 бит) (как правило, с менее чем 16 битами случайности [La10]). В результате атакующему вне пути было бы легче подделать сегмент TCP-AO, который мог бы вызвать у получателя затраты на проверку. Однако отметим, что между маршрутизаторами Интернета оба порта могли бы быть произвольными (то есть определёнными заранее вне полосы), что составило бы примерно такую же защиту от подделки вне пути, как при произвольном SPI.
TCP-AO, like TCP MD5, may inhibit connectionless resets. Such resets typically occur after peer crashes, either in response to new connection attempts or when data is sent on stale connections; in either case, the recovering endpoint may lack the connection key required (e.g., if lost during the crash). This may result in timeouts, rather than a more responsive recovery after such a crash. Recommendations for mitigating this effect are discussed in Section 7.7.
TCP-AO, как и TCP MD5, может препятствовать сбросам без установления соединения. Такие сбросы обычно происходят после сбоев партнёра — либо в ответ на новые попытки соединения, либо при отправке данных по устаревшим соединениям; в любом случае восстанавливающаяся конечная точка может не иметь требуемого ключа соединения (например, если он потерян во время сбоя). Это может приводить к тайм-аутам вместо более быстрого восстановления после такого сбоя. Рекомендации по смягчению этого эффекта обсуждаются в разделе 7.7.
TCP-AO does not include a fast decline capability, e.g., where a SYN- ACK is received without an expected TCP-AO and the connection is quickly reset or aborted. Normal TCP operation will retry and timeout, which is what should be expected when the intended receiver is not capable of the TCP variant required anyway. Backoff is not optimized because it would present an opportunity for attackers on the wire to abort authenticated connection attempts by sending spoofed SYN-ACKs without TCP-AO.
TCP-AO не включает возможности быстрого отказа, например когда получается SYN-ACK без ожидаемого TCP-AO и соединение быстро сбрасывается или прерывается. Обычная работа TCP приведёт к повторным попыткам и тайм-ауту, что и следует ожидать, когда предполагаемый получатель всё равно не способен поддерживать требуемый вариант TCP. Откат не оптимизируется, поскольку он дал бы атакующим в сети возможность прерывать попытки аутентифицированных соединений, отправляя поддельные SYN-ACK без TCP-AO.
TCP-AO is intended to provide similar protections to IPsec, but is not intended to replace the use of IPsec or IKE either for more robust security or more sophisticated security management. TCP-AO is intended to protect the TCP protocol itself from attacks that TLS, sBGP/soBGP, and other data stream protection mechanisms cannot. Like IPsec, TCP-AO does not address the overall issue of ICMP attacks on TCP, but does limit the impact of ICMPs, as noted in Section 7.8.
TCP-AO предназначена обеспечить защиту, аналогичную IPsec, но не предназначена заменять использование IPsec или IKE ни для более стойкой безопасности, ни для более сложного управления безопасностью. TCP-AO предназначена защищать сам протокол TCP от атак, которые не могут предотвратить TLS, sBGP/soBGP и другие механизмы защиты потока данных. Как и IPsec, TCP-AO не решает общую проблему атак ICMP на TCP, но ограничивает воздействие сообщений ICMP, как отмечено в разделе 7.8.
TCP-AO includes the TCP connection ID (the socket pair) in the MAC calculation. This prevents different concurrent connections using the same MKT (for whatever reason) from potentially enabling a traffic-crossing attack, in which segments to one socket pair are diverted to attack a different socket pair. When multiple connections use the same MKT, it would be useful to know that segments intended for one ID could not be (maliciously or otherwise) modified in transit and end up being authenticated for the other ID. That requirement would place an additional burden of uniqueness on MKTs within endsystems, and potentially across endsystems. Although the resulting attack is low probability, the protection afforded by including the received ID warrants its inclusion in the MAC, and does not unduly increase the MAC calculation or MKT management.
TCP-AO включает идентификатор соединения TCP (пару сокетов) в вычисление MAC. Это предотвращает потенциальную возможность для разных одновременных соединений, использующих один и тот же MKT (по любой причине), включить атаку пересечения трафика, при которой сегменты для одной пары сокетов перенаправляются для атаки на другую пару сокетов. Когда несколько соединений используют один и тот же MKT, было бы полезно знать, что сегменты, предназначенные для одного идентификатора, не могли бы быть (злонамеренно или иначе) изменены при передаче и в итоге аутентифицированы для другого идентификатора. Это требование наложило бы дополнительное бремя уникальности на MKT внутри конечных систем и потенциально между конечными системами. Хотя результирующая атака маловероятна, защита, обеспечиваемая включением принятого идентификатора, оправдывает его включение в MAC и не увеличивает чрезмерно вычисление MAC или управление MKT.
The use of any security algorithm can present an opportunity for a CPU Denial-of-Service (DoS) attack, where the attacker sends false, random segments that the receiver under attack expends substantial CPU effort to reject. In IPsec, such attacks are reduced by the use of a large Security Parameter Index (SPI) and Sequence Number fields to partly validate segments before CPU cycles are invested validated the Integrity Check Value (ICV). In TCP-AO, the socket pair performs most of the function of IPsec's SPI, and IPsec's Sequence Number, used to avoid replay attacks, isn't needed due to TCP's Sequence Number, which is used to reorder received segments (provided the sequence number doesn't wrap around, which is why TCP-AO adds the SNE in Section 6.2). TCP already protects itself from replays of authentic segment data as well as authentic explicit TCP control (e.g., SYN, FIN, ACK bits) but even authentic replays could affect TCP congestion control [Sa99]. TCP-AO does not protect TCP congestion control from this last form of attack due to the cumbersome nature of layering a windowed security sequence number within TCP in addition to TCP's own sequence number; when such protection is desired, users are encouraged to apply IPsec instead.
Использование любого алгоритма безопасности может дать возможность для атаки отказа в обслуживании (DoS) на процессор, когда атакующий отправляет ложные случайные сегменты, на отклонение которых атакуемый получатель расходует значительные усилия процессора. В IPsec такие атаки снижаются за счёт использования большого индекса параметров безопасности (SPI) и полей номера последовательности для частичной проверки сегментов до того, как циклы процессора будут вложены в проверку значения контроля целостности (ICV). В TCP-AO пара сокетов выполняет большую часть функции SPI в IPsec, а номер последовательности IPsec, используемый для предотвращения атак повторного воспроизведения, не нужен благодаря номеру последовательности TCP, который используется для переупорядочения принятых сегментов (при условии, что номер последовательности не переполняется, поэтому TCP-AO и добавляет SNE в разделе 6.2). TCP уже защищает себя от повторов аутентифицированных данных сегментов, а также аутентифицирующего явного управления TCP (например, битов SYN, FIN, ACK), но даже аутентичные повторы могли бы повлиять на управление перегрузкой TCP [Sa99]. TCP-AO не защищает управление перегрузкой TCP от этой последней формы атаки из-за громоздкости наложения оконного номера последовательности безопасности внутри TCP в дополнение к собственному номеру последовательности TCP; когда такая защита желательна, пользователям рекомендуется применять вместо неё IPsec.
Further, it is not useful to validate TCP's Sequence Number before performing a TCP-AO authentication calculation, because out-of-window segments can still cause valid TCP protocol actions (e.g., ACK retransmission) [RFC793]. It is similarly not useful to add a separate Sequence Number field to TCP-AO, because doing so could cause a change in TCP's behavior even when segments are valid.
Кроме того, бесполезно проверять номер последовательности TCP до выполнения вычисления аутентификации TCP-AO, поскольку сегменты вне окна всё равно могут вызвать допустимые действия протокола TCP (например, повторную передачу ACK) [RFC793]. Столь же бесполезно добавлять отдельное поле номера последовательности в TCP-AO, поскольку это могло бы вызвать изменение поведения TCP даже при допустимых сегментах.
