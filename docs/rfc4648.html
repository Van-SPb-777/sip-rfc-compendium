Abstract
Аннотация
This document describes the commonly used base 64, base 32, and base 16 encoding schemes. It also discusses the use of line-feeds in encoded data, use of padding in encoded data, use of non-alphabet characters in encoded data, use of different encoding alphabets, and canonical encodings.
В настоящем документе описаны широко используемые схемы кодирования base 64, base 32 и base 16. Также рассматриваются использование переводов строк в кодированных данных, использование заполнения (padding) в кодированных данных, использование символов вне алфавита в кодированных данных, использование различных алфавитов кодирования и канонические кодировки.

1. Introduction
1. Введение
Base encoding of data is used in many situations to store or transfer data in environments that, perhaps for legacy reasons, are restricted to US-ASCII [1] data. Base encoding can also be used in new applications that do not have legacy restrictions, simply because it makes it possible to manipulate objects with text editors.
Base-кодирование данных используется во многих ситуациях для хранения или передачи данных в средах, которые, возможно в силу исторических причин, ограничены данными US-ASCII [1]. Base-кодирование может также применяться в новых приложениях, не имеющих исторических ограничений, просто потому что оно позволяет манипулировать объектами с помощью текстовых редакторов.
In the past, different applications have had different requirements and thus sometimes implemented base encodings in slightly different ways. Today, protocol specifications sometimes use base encodings in general, and "base64" in particular, without a precise description or reference. Multipurpose Internet Mail Extensions (MIME) [4] is often used as a reference for base64 without considering the consequences for line-wrapping or non-alphabet characters. The purpose of this specification is to establish common alphabet and encoding considerations. This will hopefully reduce ambiguity in other documents, leading to better interoperability.
В прошлом разные приложения имели разные требования и потому иногда реализовывали base-кодирование слегка по-разному. Сегодня спецификации протоколов иногда используют base-кодирование вообще и «base64» в частности без точного описания или ссылки. Multipurpose Internet Mail Extensions (MIME) [4] часто используется как ссылка для base64 без учёта последствий для переноса строк или символов вне алфавита. Цель настоящей спецификации — установить общие соображения об алфавите и кодировании. Это, как мы надеемся, уменьшит неоднозначность в других документах и приведёт к лучшей совместимости.

3. Implementation Discrepancies
3. Расхождения в реализациях
Here we discuss the discrepancies between base encoding implementations in the past and, where appropriate, mandate a specific recommended behavior for the future.
Здесь мы обсуждаем расхождения между реализациями base-кодирования в прошлом и, где это уместно, предписываем конкретное рекомендуемое поведение на будущее.
3.1. Line Feeds in Encoded Data
3.1. Переводы строк в кодированных данных
MIME [4] is often used as a reference for base 64 encoding. However, MIME does not define "base 64" per se, but rather a "base 64 Content- Transfer-Encoding" for use within MIME. As such, MIME enforces a limit on line length of base 64-encoded data to 76 characters. MIME inherits the encoding from Privacy Enhanced Mail (PEM) [3], stating that it is "virtually identical"; however, PEM uses a line length of 64 characters. The MIME and PEM limits are both due to limits within SMTP.
MIME [4] часто используется как ссылка для кодирования base 64. Однако MIME определяет не «base 64» как таковое, а «base 64 Content-Transfer-Encoding» для использования внутри MIME. Таким образом, MIME накладывает ограничение на длину строки кодированных в base 64 данных — 76 символов. MIME наследует кодирование из Privacy Enhanced Mail (PEM) [3], утверждая, что оно «практически идентично»; однако PEM использует длину строки 64 символа. Ограничения MIME и PEM оба обусловлены ограничениями внутри SMTP.
Implementations MUST NOT add line feeds to base-encoded data unless the specification referring to this document explicitly directs base encoders to add line feeds after a specific number of characters.
Реализации не должны добавлять переводы строк в base-кодированные данные, если только спецификация, ссылающаяся на настоящий документ, явно не предписывает base-кодировщикам добавлять переводы строк после определённого числа символов.
3.2. Padding of Encoded Data
3.2. Заполнение (padding) кодированных данных
In some circumstances, the use of padding ("=") in base-encoded data is not required or used. In the general case, when assumptions about the size of transported data cannot be made, padding is required to yield correct decoded data.
В некоторых случаях заполнение («=») в base-кодированных данных не требуется и не используется. В общем случае, когда нельзя предположить размер передаваемых данных, заполнение необходимо для корректного декодирования.
Implementations MUST include appropriate pad characters at the end of encoded data unless the specification referring to this document explicitly states otherwise.
Реализации должны включать соответствующие символы заполнения в конец кодированных данных, если только спецификация, ссылающаяся на настоящий документ, явно не утверждает иное.
The base64 and base32 alphabets use padding, as described below in sections 4 and 6, but the base16 alphabet does not need it; see section 8.
Алфавиты base64 и base32 используют заполнение, как описано ниже в разделах 4 и 6, а алфавиту base16 оно не нужно; см. раздел 8.
3.3. Interpretation of Non-Alphabet Characters in Encoded Data
3.3. Интерпретация символов вне алфавита в кодированных данных
Base encodings use a specific, reduced alphabet to encode binary data. Non-alphabet characters could exist within base-encoded data, caused by data corruption or by design. Non-alphabet characters may be exploited as a "covert channel", where non-protocol data can be sent for nefarious purposes. Non-alphabet characters might also be sent in order to exploit implementation errors leading to, e.g., buffer overflow attacks.
Base-кодирование использует определённый сокращённый алфавит для кодирования двоичных данных. В base-кодированных данных могут присутствовать символы вне алфавита, вызванные повреждением данных или замыслом. Символы вне алфавита могут использоваться как «скрытый канал» (covert channel), по которому для неблаговидных целей можно передавать данные, не относящиеся к протоколу. Символы вне алфавита могут также передаваться для использования ошибок реализации, приводящих, например, к атакам переполнения буфера.
Implementations MUST reject the encoded data if it contains characters outside the base alphabet when interpreting base-encoded data, unless the specification referring to this document explicitly states otherwise. Such specifications may instead state, as MIME does, that characters outside the base encoding alphabet should simply be ignored when interpreting data ("be liberal in what you accept"). Note that this means that any adjacent carriage return/ line feed (CRLF) characters constitute "non-alphabet characters" and are ignored. Furthermore, such specifications MAY ignore the pad character, "=", treating it as non-alphabet data, if it is present before the end of the encoded data. If more than the allowed number of pad characters is found at the end of the string (e.g., a base 64 string terminated with "==="), the excess pad characters MAY also be ignored.
Реализации должны отвергать кодированные данные, если при интерпретации base-кодированных данных они содержат символы вне базового алфавита, если только спецификация, ссылающаяся на настоящий документ, явно не утверждает иное. Такие спецификации могут вместо этого утверждать, как это делает MIME, что символы вне алфавита base-кодирования следует просто игнорировать при интерпретации данных («будь либерален в том, что принимаешь»). Отметим, что это означает, что любые соседние символы возврата каретки/перевода строки (CRLF) составляют «символы вне алфавита» и игнорируются. Кроме того, такие спецификации МОГУТ игнорировать символ заполнения «=», трактуя его как данные вне алфавита, если он присутствует до конца кодированных данных. Если в конце строки обнаружено большее, чем разрешено, число символов заполнения (например, строка base 64, заканчивающаяся на «===»), избыточные символы заполнения МОГУТ также игнорироваться.

3.5. Canonical Encoding
3.5. Каноническое кодирование
The padding step in base 64 and base 32 encoding can, if improperly implemented, lead to non-significant alterations of the encoded data. For example, if the input is only one octet for a base 64 encoding, then all six bits of the first symbol are used, but only the first two bits of the next symbol are used. These pad bits MUST be set to zero by conforming encoders, which is described in the descriptions on padding below. If this property do not hold, there is no canonical representation of base-encoded data, and multiple base- encoded strings can be decoded to the same binary data. If this property (and others discussed in this document) holds, a canonical encoding is guaranteed.
Этап заполнения в кодировании base 64 и base 32 может при неправильной реализации приводить к незначащим изменениям кодированных данных. Например, если входные данные для кодирования base 64 состоят всего из одного октета, то используются все шесть битов первого символа, но только первые два бита следующего символа. Эти биты заполнения должны быть установлены в ноль соответствующими кодировщиками, что описано в приведённых ниже описаниях заполнения. Если это свойство не выполняется, канонического представления base-кодированных данных не существует, и несколько base-кодированных строк могут декодироваться в одни и те же двоичные данные. Если это свойство (и другие, обсуждаемые в настоящем документе) выполняется, каноническое кодирование гарантировано.
In some environments, the alteration is critical and therefore decoders MAY chose to reject an encoding if the pad bits have not been set to zero. The specification referring to this may mandate a specific behaviour.
В некоторых средах такое изменение критично, и поэтому декодеры МОГУТ предпочесть отвергнуть кодирование, если биты заполнения не установлены в ноль. Спецификация, ссылающаяся на это, может предписывать конкретное поведение.
4. Base 64 Encoding
4. Кодирование base 64
The following description of base 64 is derived from [3], [4], [5], and [6]. This encoding may be referred to as "base64".
Приведённое ниже описание base 64 выведено из [3], [4], [5] и [6]. Это кодирование может называться «base64».
The Base 64 encoding is designed to represent arbitrary sequences of octets in a form that allows the use of both upper- and lowercase letters but that need not be human readable. A 65-character subset of US-ASCII is used, enabling 6 bits to be represented per printable character. (The extra 65th character, "=", is used to signify a special processing function.)
Кодирование base 64 предназначено для представления произвольных последовательностей октетов в форме, допускающей использование как прописных, так и строчных букв, но не требующей удобочитаемости для человека. Используется 65-символьное подмножество US-ASCII, позволяющее представлять 6 битов на один печатаемый символ. (Дополнительный 65-й символ «=» используется для обозначения специальной функции обработки.)
The encoding process represents 24-bit groups of input bits as output strings of 4 encoded characters. Proceeding from left to right, a 24-bit input group is formed by concatenating 3 8-bit input groups. These 24 bits are then treated as 4 concatenated 6-bit groups, each of which is translated into a single character in the base 64 alphabet.
Процесс кодирования представляет 24-битовые группы входных битов как выходные строки из 4 кодированных символов. Двигаясь слева направо, 24-битовую входную группу образуют конкатенацией 3 входных 8-битовых групп. Затем эти 24 бита рассматриваются как 4 конкатенированные 6-битовые группы, каждая из которых переводится в один символ алфавита base 64.
Each 6-bit group is used as an index into an array of 64 printable characters. The character referenced by the index is placed in the output string.
Каждая 6-битовая группа используется как индекс в массиве из 64 печатаемых символов. Символ, на который указывает индекс, помещается в выходную строку.

(2) The final quantum of encoding input is exactly 8 bits; here, the final unit of encoded output will be two characters followed by two "=" padding characters.
(2) Последний квант входных данных кодирования равен ровно 8 битам; здесь последняя единица кодированного вывода будет состоять из двух символов, за которыми следуют два символа заполнения «=».
(3) The final quantum of encoding input is exactly 16 bits; here, the final unit of encoded output will be three characters followed by one "=" padding character.
(3) Последний квант входных данных кодирования равен ровно 16 битам; здесь последняя единица кодированного вывода будет состоять из трёх символов, за которыми следует один символ заполнения «=».
5. Base 64 Encoding with URL and Filename Safe Alphabet
5. Кодирование base 64 с безопасным для URL и имён файлов алфавитом
The Base 64 encoding with an URL and filename safe alphabet has been used in [12].
Кодирование base 64 с безопасным для URL и имён файлов алфавитом использовалось в [12].
An alternative alphabet has been suggested that would use "~" as the 63rd character. Since the "~" character has special meaning in some file system environments, the encoding described in this section is recommended instead. The remaining unreserved URI character is ".", but some file system environments do not permit multiple "." in a filename, thus making the "." character unattractive as well.
Был предложен альтернативный алфавит, использующий «~» в качестве 63-го символа. Поскольку символ «~» имеет особый смысл в некоторых файловых системах, вместо него рекомендуется кодирование, описанное в этом разделе. Оставшимся незарезервированным символом URI является «.», но некоторые файловые системы не допускают несколько «.» в имени файла, что делает символ «.» также непривлекательным.
The pad character "=" is typically percent-encoded when used in an URI [9], but if the data length is known implicitly, this can be avoided by skipping the padding; see section 3.2.
Символ заполнения «=» обычно кодируется процентным кодированием при использовании в URI [9], но если длина данных известна неявно, этого можно избежать, пропустив заполнение; см. раздел 3.2.
This encoding may be referred to as "base64url". This encoding should not be regarded as the same as the "base64" encoding and should not be referred to as only "base64". Unless clarified otherwise, "base64" refers to the base 64 in the previous section.

6. Base 32 Encoding
6. Кодирование base 32
The following description of base 32 is derived from [11] (with corrections). This encoding may be referred to as "base32".
Приведённое ниже описание base 32 выведено из [11] (с исправлениями). Данное кодирование может именоваться «base32».
The Base 32 encoding is designed to represent arbitrary sequences of octets in a form that needs to be case insensitive but that need not be human readable.
Кодирование base 32 предназначено для представления произвольных последовательностей октетов в форме, которая должна быть нечувствительной к регистру, но не обязательно удобочитаемой для человека.
A 33-character subset of US-ASCII is used, enabling 5 bits to be represented per printable character. (The extra 33rd character, "=", is used to signify a special processing function.)
Используется 33-символьное подмножество US-ASCII, позволяющее представлять 5 битов на один печатаемый символ. (Дополнительный 33-й символ «=» используется для обозначения специальной функции обработки.)
The encoding process represents 40-bit groups of input bits as output strings of 8 encoded characters. Proceeding from left to right, a 40-bit input group is formed by concatenating 5 8bit input groups. These 40 bits are then treated as 8 concatenated 5-bit groups, each of which is translated into a single character in the base 32 alphabet. When a bit stream is encoded via the base 32 encoding, the bit stream must be presumed to be ordered with the most-significant- bit first. That is, the first bit in the stream will be the high- order bit in the first 8bit byte, the eighth bit will be the low- order bit in the first 8bit byte, and so on. Each 5-bit group is used as an index into an array of 32 printable characters. The character referenced by the index is placed in the output string. These characters, identified in Table 3, below, are selected from US-ASCII digits and uppercase letters.
Процесс кодирования представляет 40-битовые группы входных битов как выходные строки из 8 кодированных символов. Двигаясь слева направо, 40-битовую входную группу образуют конкатенацией 5 входных 8-битовых групп. Затем эти 40 битов рассматриваются как 8 конкатенированных 5-битовых групп, каждая из которых переводится в один символ алфавита base 32. Когда поток битов кодируется с помощью кодирования base 32, следует считать, что поток битов упорядочен от старшего бита к младшему. То есть первый бит в потоке будет старшим битом в первом 8-битовом байте, восьмой бит будет младшим битом в первом 8-битовом байте, и так далее. Каждая 5-битовая группа используется как индекс в массиве из 32 печатаемых символов. Символ, на который указывает индекс, помещается в выходную строку. Эти символы, идентифицированные в таблице 3 ниже, выбраны из цифр и прописных букв US-ASCII.

Special processing is performed if fewer than 40 bits are available at the end of the data being encoded. A full encoding quantum is always completed at the end of a body. When fewer than 40 input bits are available in an input group, bits with value zero are added (on the right) to form an integral number of 5-bit groups. Padding at the end of the data is performed using the "=" character. Since all base 32 input is an integral number of octets, only the following cases can arise:
Специальная обработка выполняется, если в конце кодируемых данных доступно менее 40 битов. Полный квант кодирования всегда завершается в конце тела. Когда во входной группе доступно менее 40 входных битов, справа добавляются биты с нулевым значением, чтобы образовать целое число 5-битовых групп. Заполнение в конце данных выполняется символом «=». Поскольку все входные данные base 32 составляют целое число октетов, могут возникнуть только следующие случаи:
(1) The final quantum of encoding input is an integral multiple of 40 bits; here, the final unit of encoded output will be an integral multiple of 8 characters with no "=" padding.
(1) Последний квант входных данных кодирования кратен 40 битам; здесь последняя единица кодированного вывода будет кратной 8 символам без заполнения «=».
(2) The final quantum of encoding input is exactly 8 bits; here, the final unit of encoded output will be two characters followed by six "=" padding characters.
(2) Последний квант входных данных кодирования равен ровно 8 битам; здесь последняя единица кодированного вывода будет состоять из двух символов, за которыми следуют шесть символов заполнения «=».
(3) The final quantum of encoding input is exactly 16 bits; here, the final unit of encoded output will be four characters followed by four "=" padding characters.
(3) Последний квант входных данных кодирования равен ровно 16 битам; здесь последняя единица кодированного вывода будет состоять из четырёх символов, за которыми следуют четыре символа заполнения «=».
(4) The final quantum of encoding input is exactly 24 bits; here, the final unit of encoded output will be five characters followed by three "=" padding characters.
(4) Последний квант входных данных кодирования равен ровно 24 битам; здесь последняя единица кодированного вывода будет состоять из пяти символов, за которыми следуют три символа заполнения «=».
(5) The final quantum of encoding input is exactly 32 bits; here, the final unit of encoded output will be seven characters followed by one "=" padding character.
(5) Последний квант входных данных кодирования равен ровно 32 битам; здесь последняя единица кодированного вывода будет состоять из семи символов, за которыми следует один символ заполнения «=».

8. Base 16 Encoding
8. Кодирование base 16
The following description is original but analogous to previous descriptions. Essentially, Base 16 encoding is the standard case- insensitive hex encoding and may be referred to as "base16" or "hex".
Приведённое ниже описание является оригинальным, но аналогично предыдущим описаниям. По существу, кодирование base 16 — это стандартное шестнадцатеричное кодирование без учёта регистра, и оно может называться «base16» или «hex».
A 16-character subset of US-ASCII is used, enabling 4 bits to be represented per printable character.
Используется 16-символьное подмножество US-ASCII, позволяющее представлять 4 бита на один печатаемый символ.
The encoding process represents 8-bit groups (octets) of input bits as output strings of 2 encoded characters. Proceeding from left to right, an 8-bit input is taken from the input data. These 8 bits are then treated as 2 concatenated 4-bit groups, each of which is translated into a single character in the base 16 alphabet.
Процесс кодирования представляет 8-битовые группы (октеты) входных битов как выходные строки из 2 кодированных символов. Двигаясь слева направо, из входных данных берётся 8-битовый вход. Затем эти 8 битов рассматриваются как 2 конкатенированные 4-битовые группы, каждая из которых переводится в один символ алфавита base 16.
Each 4-bit group is used as an index into an array of 16 printable characters. The character referenced by the index is placed in the output string.
Каждая 4-битовая группа используется как индекс в массиве из 16 печатаемых символов. Символ, на который указывает индекс, помещается в выходную строку.

12. Security Considerations
12. Соображения безопасности
When base encoding and decoding is implemented, care should be taken not to introduce vulnerabilities to buffer overflow attacks, or other attacks on the implementation. A decoder should not break on invalid input including, e.g., embedded NUL characters (ASCII 0).
При реализации base-кодирования и декодирования следует проявлять осторожность, чтобы не внести уязвимости к атакам переполнения буфера или другим атакам на реализацию. Декодер не должен ломаться при недопустимом входе, включая, например, встроенные символы NUL (ASCII 0).
If non-alphabet characters are ignored, instead of causing rejection of the entire encoding (as recommended), a covert channel that can be used to "leak" information is made possible. The ignored characters could also be used for other nefarious purposes, such as to avoid a string equality comparison or to trigger implementation bugs. The implications of ignoring non-alphabet characters should be understood in applications that do not follow the recommended practice. Similarly, when the base 16 and base 32 alphabets are handled case insensitively, alteration of case can be used to leak information or make string equality comparisons fail.
Если символы вне алфавита игнорируются вместо отклонения всего кодирования (как рекомендуется), становится возможным скрытый канал, который можно использовать для «утечки» информации. Игнорируемые символы можно также использовать для других неблаговидных целей, например чтобы обойти сравнение строк на равенство или вызвать ошибки реализации. Последствия игнорирования символов вне алфавита должны быть поняты в приложениях, которые не следуют рекомендуемой практике. Аналогично, когда алфавиты base 16 и base 32 обрабатываются без учёта регистра, изменение регистра можно использовать для утечки информации или чтобы сравнения строк на равенство давали сбой.
When padding is used, there are some non-significant bits that warrant security concerns, as they may be abused to leak information or used to bypass string equality comparisons or to trigger implementation problems.
Когда используется заполнение, есть несколько незначащих битов, вызывающих опасения по безопасности, поскольку их можно использовать для утечки информации, для обхода сравнений строк на равенство или для провоцирования проблем реализации.
Base encoding visually hides otherwise easily recognized information, such as passwords, but does not provide any computational confidentiality. This has been known to cause security incidents when, e.g., a user reports details of a network protocol exchange (perhaps to illustrate some other problem) and accidentally reveals the password because she is unaware that the base encoding does not protect the password.
Base-кодирование визуально скрывает иначе легко распознаваемую информацию, такую как пароли, но не обеспечивает никакой вычислительной конфиденциальности. Известно, что это приводило к инцидентам безопасности, когда, например, пользователь сообщал сведения о сетевом обмене протокола (возможно, чтобы проиллюстрировать другую проблему) и случайно раскрывал пароль, поскольку не знал, что base-кодирование не защищает пароль.
Base encoding adds no entropy to the plaintext, but it does increase the amount of plaintext available and provide a signature for cryptanalysis in the form of a characteristic probability distribution.
Base-кодирование не добавляет энтропии к открытому тексту, но оно увеличивает объём доступного открытого текста и даёт сигнатуру для криптоанализа в виде характерного распределения вероятностей.
