Abstract
Аннотация
This document describes the Real-time Transport Protocol (RTP) payload format for the internet Low Bit Rate Codec (iLBC) Speech developed by Global IP Sound (GIPS). Also, within the document there are included necessary details for the use of iLBC with MIME and Session Description Protocol (SDP).
Настоящий документ описывает формат полезной нагрузки протокола передачи в реальном времени (RTP) для речи, создаваемой интернет-кодеком с низкой скоростью передачи (iLBC) компании Global IP Sound (GIPS). В документ также включены необходимые сведения об использовании iLBC совместно с MIME и протоколом описания сеансов (SDP).
1. Introduction
1. Введение
This document describes how compressed iLBC speech, as produced by the iLBC codec [1], may be formatted for use as an RTP payload type. Methods are provided to packetize the codec data frames into RTP packets. The sender may send one or more codec data frames per packet depending on the application scenario or based on the transport network condition, bandwidth restriction, delay requirements and packet-loss tolerance.
Настоящий документ описывает, каким образом сжатая речь iLBC, формируемая кодеком iLBC [1], может быть оформлена для использования в качестве типа полезной нагрузки RTP. Приведены методы пакетирования кадров данных кодека в пакеты RTP. Отправитель может передавать один или несколько кадров данных кодека в пакете в зависимости от сценария применения либо от состояния транспортной сети, ограничений полосы, требований к задержке и допустимости потерь пакетов.
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14, RFC 2119 [2].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует интерпретировать так, как описано в BCP 14, RFC 2119 [2].
2. Background
2. Предыстория
Global IP Sound (GIPS) has developed a speech compression algorithm for use in IP based communications [1]. The iLBC codec enables graceful speech quality degradation in the case of lost frames, which occurs in connection with lost or delayed IP packets.
Компания Global IP Sound (GIPS) разработала алгоритм сжатия речи для использования в IP-связи [1]. Кодек iLBC обеспечивает плавное снижение качества речи при потере кадров, что происходит при потере или задержке IP-пакетов.
This codec is suitable for real time communications such as, telephony and videoconferencing, streaming audio, archival and messaging.
Этот кодек подходит для связи в реальном времени, такой как телефония и видеоконференции, потоковое аудио, архивирование и обмен сообщениями.
The iLBC codec [1] is an algorithm that compresses each basic frame (20 ms or 30 ms) of 8000 Hz, 16-bit sampled input speech, into output frames with rate of 400 bits for 30 ms basic frame size and 304 bits for 20 ms basic frame size.
Кодек iLBC [1] — это алгоритм, который сжимает каждый базовый кадр (20 мс или 30 мс) входной речи, дискретизированной на частоте 8000 Гц с 16-битными отсчётами, в выходные кадры со скоростью 400 бит для базового кадра 30 мс и 304 бит для базового кадра 20 мс.
The codec supports two basic frame lengths: 30 ms at 13.33 kbit/s and 20 ms at 15.2 kbit/s, using a block independent linear-predictive coding (LPC) algorithm. When the codec operates at block lengths of 20 ms, it produces 304 bits per block which MUST be packetized in 38 bytes. Similarly, for block lengths of 30 ms it produces 400 bits per block which MUST be packetized in 50 bytes. This algorithm results in a speech coding system with a controlled response to packet losses similar to what is known from pulse code modulation (PCM) with a packet loss concealment (PLC), such as ITU-T G711 standard [7], which operates at a fixed bit rate of 64 kbit/s. At the same time, this algorithm enables fixed bit rate coding with a quality-versus-bit rate tradeoff close to what is known from code- excited linear prediction (CELP).
Кодек поддерживает две базовые длины кадра: 30 мс при 13,33 кбит/с и 20 мс при 15,2 кбит/с, используя алгоритм линейного предсказания с кодированием (LPC) независимо для каждого блока. При работе с длиной блока 20 мс кодек выдаёт 304 бита на блок, которые ДОЛЖНЫ быть упакованы в 38 байт. Аналогично, при длине блока 30 мс он выдаёт 400 бит на блок, которые ДОЛЖНЫ быть упакованы в 50 байт. Этот алгоритм даёт систему кодирования речи с контролируемой реакцией на потери пакетов, подобной той, что известна из импульсно-кодовой модуляции (PCM) с маскированием потерь пакетов (PLC), например из стандарта ITU-T G.711 [7], работающего с фиксированной скоростью 64 кбит/с. В то же время этот алгоритм обеспечивает кодирование с фиксированной скоростью при компромиссе между качеством и скоростью, близком к известному из линейного предсказания с кодовым возбуждением (CELP).

The assignment of an RTP payload type for this new packet format is outside the scope of this document, and will not be specified here. It is expected that the RTP profile for a particular class of applications will assign a payload type for this encoding, or if that is not done, then a payload type in the dynamic range shall be chosen by the sender.
Назначение типа полезной нагрузки RTP для этого нового формата пакетов выходит за рамки настоящего документа и здесь не определяется. Ожидается, что профиль RTP для конкретного класса приложений назначит тип полезной нагрузки для этого кодирования, либо, если это не сделано, отправитель выберет тип полезной нагрузки из динамического диапазона.
3.1. Bitstream definition
3.1. Определение битового потока
The total number of bits used to describe one frame of 20 ms speech is 304, which fits in 38 bytes and results in a bit rate of 15.20 kbit/s. For the case with a frame length of 30 ms speech the total number of bits used is 400, which fits in 50 bytes and results in a bit rate of 13.33 kbit/s. In the bitstream definition, the bits are distributed into three classes according to their bit error or loss sensitivity. The most sensitive bits (class 1) are placed first in the bitstream for each frame. The less sensitive bits (class 2) are placed after the class 1 bits. The least sensitive bits (class 3) are placed at the end of the bitstream for each frame.
Общее число битов, используемых для описания одного кадра речи 20 мс, равно 304, что укладывается в 38 байт и даёт скорость 15,20 кбит/с. Для случая с длиной кадра речи 30 мс общее число используемых битов равно 400, что укладывается в 50 байт и даёт скорость 13,33 кбит/с. В определении битового потока биты распределены на три класса в соответствии с их чувствительностью к битовым ошибкам или потерям. Наиболее чувствительные биты (класс 1) размещаются первыми в битовом потоке каждого кадра. Менее чувствительные биты (класс 2) размещаются после битов класса 1. Наименее чувствительные биты (класс 3) размещаются в конце битового потока каждого кадра.
Looking at the 20/30 ms frame length cases for each class: The class 1 bits occupy a total of 6/8 bytes (48/64 bits), the class 2 bits occupy 8/12 bytes (64/96 bits), and the class 3 bits occupy 24/30 bytes (191/239 bits). This distribution of the bits enables the use of uneven level protection (ULP). The detailed bit allocation is shown in the table below. When a quantization index is distributed between more classes the more significant bits belong to the lowest class.
Рассматривая случаи длины кадра 20/30 мс для каждого класса: биты класса 1 занимают в сумме 6/8 байт (48/64 бита), биты класса 2 занимают 8/12 байт (64/96 бит), а биты класса 3 занимают 24/30 байт (191/239 бит). 3.2. Multiple iLBC frames in a RTP packet
3.2. Несколько кадров iLBC в пакете RTP
More than one iLBC frame may be included in a single RTP packet by a sender.
Отправитель может включить в один пакет RTP более одного кадра iLBC.
It is important to observe that senders have the following additional restrictions:
Важно отметить, что на отправителей накладываются следующие дополнительные ограничения:
o SHOULD NOT include more iLBC frames in a single RTP packet than will fit in the MTU of the RTP transport protocol.
o НЕ СЛЕДУЕТ включать в один пакет RTP больше кадров iLBC, чем помещается в MTU транспортного протокола RTP.
o Frames MUST NOT be split between RTP packets.
o Кадры НЕ ДОЛЖНЫ разделяться между пакетами RTP.
o Frames of the different modes (20 ms and 30 ms) MUST NOT be included within the same packet.
o Кадры разных режимов (20 мс и 30 мс) НЕ ДОЛЖНЫ включаться в один и тот же пакет.
It is RECOMMENDED that the number of frames contained within an RTP packet are consistent with the application. For example, in telephony and other real time applications where delay is important, the delay is lower depending on the amount of frames per packet (i.e., fewer frames per packet, the lower the delay). Whereas for bandwidth constrained links or delay insensitive streaming messaging application, one or more frames per packet would be acceptable.
РЕКОМЕНДУЕТСЯ, чтобы число кадров в пакете RTP соответствовало приложению. Например, в телефонии и других приложениях реального времени, где важна задержка, задержка тем меньше, чем меньше кадров в пакете (т.е. чем меньше кадров в пакете, тем ниже задержка). В то же время для каналов с ограниченной полосой или для нечувствительных к задержке приложений потокового обмена сообщениями приемлемым будет один или несколько кадров на пакет.
Information describing the number of frames contained in an RTP packet is not transmitted as part of the RTP payload. The way to determine the number of iLBC frames is to count the total number of octets within the RTP packet, and divide the octet count by the number of expected octets per frame (32/50 per frame).
Информация о числе кадров, содержащихся в пакете RTP, не передаётся как часть полезной нагрузки RTP. Чтобы определить число кадров iLBC, нужно подсчитать общее число октетов в пакете RTP и разделить его на ожидаемое число октетов на кадр (32/50 на кадр).

5. Mapping To SDP Parameters
5. Отображение в параметры SDP
The information carried in the MIME media type specification has a specific mapping to fields in the Session Description Protocol (SDP) [5], which is commonly used to describe RTP sessions. When SDP is used to specify sessions employing the iLBC codec, the mapping is as follows:
Информация, содержащаяся в спецификации типа медиа MIME, имеет определённое отображение в поля протокола описания сеансов (SDP) [5], который обычно используется для описания сеансов RTP. Когда SDP используется для указания сеансов, применяющих кодек iLBC, отображение выглядит следующим образом:
o The MIME type ("audio") goes in SDP "m=" as the media name.
o Тип MIME («audio») записывается в SDP «m=» как имя медиа.
o The MIME subtype (payload format name) goes in SDP "a=rtpmap" as the encoding name.
o Подтип MIME (имя формата полезной нагрузки) записывается в SDP «a=rtpmap» как имя кодирования.
o The parameters "ptime" and "maxptime" go in the SDP "a=ptime" and "a=maxptime" attributes, respectively.
o Параметры «ptime» и «maxptime» записываются в атрибуты SDP «a=ptime» и «a=maxptime» соответственно.
o The parameter "mode" goes in the SDP "a=fmtp" attribute by copying it directly from the MIME media type string as "mode=value".
o Параметр «mode» записывается в атрибут SDP «a=fmtp» путём прямого копирования из строки типа медиа MIME как «mode=value».
When conveying information by SDP, the encoding name SHALL be "iLBC" (the same as the MIME subtype).
При передаче информации посредством SDP имя кодирования ДОЛЖНО быть «iLBC» (совпадать с подтипом MIME).
An example of the media representation in SDP for describing iLBC might be:
Пример представления медиа в SDP для описания iLBC может выглядеть так:
m=audio 49120 RTP/AVP 97 a=rtpmap:97 iLBC/8000
m=audio 49120 RTP/AVP 97 a=rtpmap:97 iLBC/8000
If 20 ms frame size mode is used, remote iLBC encoder SHALL receive "mode" parameter in the SDP "a=fmtp" attribute by copying them directly from the MIME media type string as a semicolon separated with parameter=value, where parameter is "mode", and values can be 0 and 20 (where 0 is reserved and 20 stands for preferred 20 ms frame size). An example of the media representation in SDP for describing iLBC when 20 ms frame size mode is used might be:
Если используется режим кадра 20 мс, удалённый кодер iLBC ДОЛЖЕН получить параметр «mode» в атрибуте SDP «a=fmtp» путём прямого копирования из строки типа медиа MIME в виде разделённых точкой с запятой пар parameter=value, где parameter — это «mode», а значения могут быть 0 и 20 (где 0 зарезервировано, а 20 означает предпочтительный размер кадра 20 мс). Пример представления медиа в SDP для описания iLBC при использовании режима кадра 20 мс может выглядеть так:
m=audio 49120 RTP/AVP 97 a=rtpmap:97 iLBC/8000 a=fmtp:97 mode=20
m=audio 49120 RTP/AVP 97 a=rtpmap:97 iLBC/8000 a=fmtp:97 mode=20
It is important to emphasize the bi-directional character of the "mode" parameter - both sides of a bi-directional session MUST use the same "mode" value.
Важно подчеркнуть двунаправленный характер параметра «mode» — обе стороны двунаправленного сеанса ДОЛЖНЫ использовать одно и то же значение «mode».
The offer contains the preferred mode of the offerer. The answerer may agree to that mode by including the same mode in the answer, or may include a different mode. The resulting mode used by both parties SHALL be the lower of the bandwidth modes in the offer and answer.
Предложение содержит предпочтительный режим предлагающей стороны. Отвечающая сторона может согласиться с этим режимом, включив тот же режим в ответ, или указать другой режим. Итоговый режим, используемый обеими сторонами, ДОЛЖЕН быть меньшим из режимов полосы в предложении и ответе.
That is, an offer of "mode=20" receiving an answer of "mode=30" will result in "mode=30" being used by both participants. Similarly, an offer of "mode=30" and an answer of "mode=20" will result in "mode=30" being used by both participants.
То есть предложение «mode=20» с ответом «mode=30» приведёт к тому, что оба участника будут использовать «mode=30». Аналогично предложение «mode=30» с ответом «mode=20» приведёт к использованию обоими участниками «mode=30».
This is important when one end point utilizes a bandwidth constrained link (e.g., 28.8k modem link or slower), where only the lower frame size will work.
Это важно, когда одна из конечных точек использует канал с ограниченной полосой (например, модемное соединение 28,8k или медленнее), где будет работать только меньший размер кадра.
Parameter ptime can not be used for the purpose of specifying iLBC operating mode, due to fact that for the certain values it will be impossible to distinguish which mode is about to be used (e.g., when ptime=60, it would be impossible to distinguish if packet is carrying 2 frames of 30 ms or 3 frames of 20 ms, etc.).
Параметр ptime нельзя использовать для указания рабочего режима iLBC, поскольку при некоторых значениях будет невозможно различить, какой режим будет использоваться (например, при ptime=60 невозможно определить, несёт ли пакет 2 кадра по 30 мс или 3 кадра по 20 мс, и т.д.).
Note that the payload format (encoding) names are commonly shown in upper case. MIME subtypes are commonly shown in lower case. These names are case-insensitive in both places. Similarly, parameter names are case-insensitive both in MIME types and in the default mapping to the SDP a=fmtp attribute
Отметим, что имена формата (кодирования) полезной нагрузки обычно пишутся в верхнем регистре. Подтипы MIME обычно пишутся в нижнем регистре. Эти имена нечувствительны к регистру в обоих местах. Аналогично имена параметров нечувствительны к регистру как в типах MIME, так и в отображении по умолчанию в атрибут SDP a=fmtp
6. Security Considerations
6. Вопросы безопасности
RTP packets using the payload format defined in this specification are subject to the general security considerations discussed in [3] and any appropriate profile (e.g., [4]).
Пакеты RTP, использующие формат полезной нагрузки, определённый в настоящей спецификации, подпадают под общие соображения безопасности, рассмотренные в [3] и любом применимом профиле (например, [4]).
As this format transports encoded speech, the main security issues include confidentiality and authentication of the speech itself. The payload format itself does not have any built-in security mechanisms. Confidentiality of the media streams is achieved by encryption, therefore external mechanisms, such as SRTP [6], MAY be used for that purpose. The data compression used with this payload format is applied end-to-end; hence encryption may be performed after compression with no conflict between the two operations.
Поскольку этот формат передаёт кодированную речь, основные проблемы безопасности включают конфиденциальность и аутентификацию самой речи. Сам формат полезной нагрузки не имеет встроенных механизмов безопасности. Конфиденциальность медиапотоков достигается шифрованием, поэтому для этой цели МОГУТ использоваться внешние механизмы, например SRTP [6]. Сжатие данных, используемое с этим форматом полезной нагрузки, применяется по принципу «из конца в конец»; следовательно, шифрование может выполняться после сжатия без конфликта между этими двумя операциями.
A potential denial-of-service threat exists for data encoding using compression techniques that have non-uniform receiver-end computational load. The attacker can inject pathological datagrams into the stream which are complex to decode and cause the receiver to become overloaded. However, the encodings covered in this document do not exhibit any significant non-uniformity.
Для кодирования данных с использованием методов сжатия, имеющих неравномерную вычислительную нагрузку на приёмнике, существует потенциальная угроза отказа в обслуживании. Злоумышленник может внедрять в поток патологические датаграммы, сложные для декодирования, и перегружать приёмник. Однако рассмотренные в настоящем документе кодирования не проявляют существенной неравномерности.
