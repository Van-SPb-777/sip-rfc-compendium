Abstract
Аннотация
The Open Mobile Alliance (OMA) is defining the Push-to-talk over Cellular (PoC) service where SIP is the protocol used to establish half-duplex media sessions across different participants, to send instant messages, etc. This document defines a SIP event package to support publication, subscription, and notification of additional capabilities required by the PoC service. This SIP event package is applicable to the PoC service and may not be applicable to the general Internet.
Open Mobile Alliance (OMA) определяет службу Push-to-talk over Cellular (PoC), где SIP — это протокол, используемый для установления полудуплексных сессий мультимедиа между различными участниками, для отправки мгновенных сообщений и т. д. Этот документ определяет пакет событий SIP для поддержки публикации, подписки и уведомления о дополнительных возможностях, требуемых службой PoC. Этот пакет событий SIP применим к услуге PoC и может быть неприменим к общему Интернету.

1. Introduction
1. Введение
The Open Mobile Alliance (OMA) (http://www.openmobilealliance.org) is currently specifying the Push-to-talk over Cellular (PoC) service. This service allows a SIP User Agent (PoC terminal) to establish a session to one or more SIP User Agents (UAs) simultaneously, usually initiated when the initiating user pushes a button.
Открытый мобильный альянс (OMA) (http://www.openmobilealliance.org) в настоящее время определяет услугу Push-to-talk через сотовую связь (PoC). Эта услуга позволяет агенту пользователя SIP (терминал PoC) одновременно устанавливать сессия с одним или несколькими агентами пользователя SIP (UA), обычно инициируемый, когда инициирующий пользователь нажимает кнопку.
OMA has defined a collection of very stringent requirements in support of the PoC service. In order to provide the user with a satisfactory experience, the initial session establishment (from the time the user presses the button to the time they get an indication to speak) must be minimized.
OMA определила набор очень строгих требований для поддержки услуги PoC. Чтобы обеспечить пользователю удовлетворительное взаимодействие, начальное установление сессии (с момента, когда пользователь нажимает кнопку до момента, когда он получает указание говорить) должно быть сведено к минимуму.
The PoC terminal may support hardware capabilities such as a speakerphone and/or headset and software that provide the capability for the user to configure the PoC terminal to accept session initiations immediately and play out the media as soon as it is received without requiring the intervention of the called user. This mode of operation is known as Auto-Answer mode or automatic mode. The user may alternatively configure the PoC terminal to first alert the user and require the user to accept the session invitation manually before media is accepted. This mode of operation is known as Manual-Answer mode. The PoC terminal may support both or only one of these modes of operation. The user may change the Answer Mode (AM) configuration of the PoC terminal frequently based on their current circumstances and preference (perhaps because the user is busy or in a public area where she cannot use a speaker phone, etc.).
Терминал PoC может поддерживать аппаратные возможности, такие как громкая связь и/или гарнитура, а также программное обеспечение, которые предоставляют пользователю возможность сконфигурировать терминал PoC для немедленного приема инициирования сессий и воспроизведения мультимедиа, как только он будет получен, без необходимости вмешательства вызываемого пользователя. Этот режим работы известен как режим Auto-Answer или автоматический режим. В качестве альтернативы пользователь может сконфигурировать терминал PoC так, чтобы он сначала предупреждал пользователя и требовал от пользователя принять приглашение на сессия вручную перед тем, как будет принят носитель. Этот режим работы известен как режим Manual-Answer. Терминал PoC может поддерживать оба или только один из этих режимов работы. Пользователь может часто менять конфигурацию режима ответа (AM) терминала PoC в зависимости от своих текущих обстоятельств и предпочтений (возможно, потому что пользователь занят или находится в общественном месте, где он не может использовать громкую связь и т. д.).
SIP PoC terminals can support various SIP-based communication services in addition to Push-to-talk (e.g., VoIP telephony, presence services, messaging services, etc.). The user may at times wish to disable the acceptance of Push-to-talk sessions whilst still remaining SIP registered for one or more other SIP-based services. When the PoC terminal is configured to not accept any incoming Push- to-talk sessions, this is known as Incoming Session Barring (ISB).
Терминалы SIP PoC могут поддерживать различные SIP-based коммуникационные услуги в дополнение к Push-to-talk (например, VoIP-телефонии, службам присутствия, службам обмена сообщениями и т. д.). Иногда пользователь может захотеть отключить прием Push-to-talk сессий, оставаясь при этом зарегистрированным SIP для одной или нескольких других SIP-based служб. Когда терминал PoC настроен так, чтобы не принимать входящие сессии «нажми и говори», это называется запретом входящего сессии (ISB).
A user may wish to contact another user who has a PoC terminal with Incoming Session Barring enabled. A user may send an Instant Personal Alert to another user to inform him that he wishes to engage him in a PoC Session. This Instant Personal Alert is received even when the destination PoC terminal has enabled Incoming Session Barring. If a user wishes to disable the acceptance of Instant Personal Alerts, he can configure his PoC terminal not accept any incoming Instant Personal Alerts. This is known as Instant Personal Alert Barring (IPAB). Some PoC terminals may provide support for handling multiple PoC sessions simultaneously whereas other terminals are only able to handle one PoC session at time. Or, even if the terminal is able to handle multiple PoC sessions simultaneously, the user may desire to have just one single PoC session at a time. This indication of support for multiple PoC sessions simultaneously is known as Simultaneous PoC Sessions Support (SSS).
Пользователь может пожелать связаться с другим пользователем, у которого есть терминал PoC с включенным запретом входящих сессий. Пользователь может отправить мгновенное личное оповещение другому пользователю, чтобы сообщить ему, что он желает вовлечь его в сессия PoC. Это мгновенное персональное оповещение принимается даже в том случае, если PoC-терминал назначения включил запрет входящего сессии. Если пользователь желает отключить прием мгновенных персональных оповещений, он может настроить свой PoC-терминал так, чтобы он не принимал входящие мгновенные персональные оповещения. Это известно как мгновенный запрет персональных оповещений (IPAB). Некоторые терминалы PoC могут обеспечивать поддержку одновременной обработки нескольких сессий PoC, тогда как другие терминалы могут обрабатывать только один сессия PoC одновременно. Или, даже если терминал способен обрабатывать несколько сессий PoC одновременно, пользователь может захотеть иметь только один сессия PoC за раз. Этот признак поддержки нескольких сессий PoC одновременно известен как поддержка одновременных сессий PoC (SSS).
The OMA PoC Architecture utilizes SIP servers within the network that may perform roles such as a conference focus [12], an RTP translator, or a policy server. A possible optimization to minimize the delay in providing the caller with an indication to speak consist of the SIP network server to perform buffering of media packets in order to provide an early or unconfirmed indication to the caller and allow the caller to start speaking before the called PoC terminal has answered. This optimization only is appropriate when the called PoC terminal is currently accepting PoC sessions and its Answer Mode is set to Auto-Answer. This optimization therefore requires the network SIP server to have knowledge of the current ISB and AM settings of the called PoC terminal.
Архитектура OMA PoC использует SIP-серверы внутри сети, которые могут выполнять такие роли, как фокус конференции [12], транслятор RTP или сервер политики. Возможная оптимизация для минимизации задержки в предоставлении вызывающему абоненту указания на разговор состоит в том, что сетевой сервер SIP выполняет буферизацию медиа-пакетов, чтобы предоставить вызывающему абоненту раннюю или неподтвержденную индикацию и позволить вызывающему абоненту начать говорить до того, как вызываемый терминал PoC ответит. Эта оптимизация подходит только тогда, когда вызываемый терминал PoC в настоящий момент принимает сессии PoC и его режим ответа установлен на Auto-Answer. Поэтому эта оптимизация требует, чтобы сетевой SIP-сервер знал текущие настройки ISB и AM вызываемого PoC-терминала.
Similarly, in order to avoid unnecessary transmission of Instant Personal Alerts across the radio interface, the network SIP server needs to have knowledge of the current IPAB setting at the terminal.
Аналогичным образом, чтобы избежать ненужной передачи мгновенных персональных оповещений через радиоинтерфейс, сетевой SIP-сервер должен знать текущую настройку IPAB на терминале.
When the UA supports multiple PoC sessions simultaneously the server needs to act as a B2BUA in order to multiplex media and floor control signaling between multiple sessions using a single bandwidth limited radio bearer. When handling of multiple PoC sessions simultaneously is not needed the server can act as a SIP proxy. It is therefore advantageous for the server to be informed whether the UA currently intends to support multiple PoC sessions simultaneously.
Когда UA поддерживает несколько сессий PoC одновременно, серверу необходимо действовать как B2BUA для мультиплексирования сигналов управления мультимедиа и напольного контроля между несколькими сессиями с использованием одного радиоканала с ограниченной полосой пропускания. Если обработка нескольких сессий PoC одновременно не требуется, сервер может действовать как SIP-прокси. Поэтому серверу выгодно быть проинформированным о том, намерен ли UA в настоящее время поддерживать несколько сессий PoC одновременно.
This document proposes additional SIP capabilities to enable the communication of the ISB, AM, IPAB, and SSS settings between the SIP PoC terminal and the SIP network server.
В этом документе предлагаются дополнительные возможности SIP, обеспечивающие передачу настроек ISB, AM, IPAB и SSS между терминалом SIP PoC и сетевым сервером SIP.
We define a SIP event package that allows a SIP Event Publication Agent (EPA) to publish the user's settings at that particular EPA which may impact some specific session attempts. This allows subscribers to subscribe to the Event State Compositor to this event package to gather this information, and anticipate to the user's needs when a session is attempted to that user. It is believed that the SIP event package defined here is not applicable to the general Internet: it has been designed to serve the architecture of the PoC service. In particular, and in the context defined by RFC 3903 [8], it is the intention of OMA to make PoC terminals behave as Event Publication Agents (EPA), and network servers behave as Event State Compositors (ESC). It is possible that PoC terminals and network servers may also subscribe to the user's PoC related settings, so that changes in this state made in one terminal are kept in synchronization across all different terminals or with the network server for a particular user.
Мы определяем пакет событий SIP, который позволяет агенту публикации событий SIP (EPA) публиковать настройки пользователя в этом конкретном EPA, что может повлиять на некоторые конкретные попытки сессии. Это позволяет подписчикам подписаться на составитель состояний событий для этого пакета событий, чтобы собирать эту информацию и предугадывать потребности пользователя при попытке установить сессия с этим пользователем. Считается, что определенный здесь пакет событий SIP неприменим к общему Интернету: он был разработан для обслуживания архитектуры службы PoC. В частности, и в контексте, определенном RFC 3903 [8], целью OMA является заставить терминалы PoC вести себя как агенты публикации событий (EPA), а сетевые серверы вести себя как составители состояний событий (ESC). Вполне возможно, что терминалы PoC и сетевые серверы могут также подписываться на настройки пользователя, связанные с PoC, так что изменения в этом состоянии, сделанные в одном терминале, синхронизируются между всеми различными терминалами или с сетевым сервером для конкретного пользователя.
This document defines a PoC-settings document that allows an EPA to convey its ISB, AM, IPAB, and SSS settings to an ESC. The EPA sends a PoC-settings document in PUBLISH requests [8]. The PoC-settings document contain represents the settings view at that particular EPA. The ESC can collect PoC-settings document for the same user at different EPAs, apply a composition policy, and provide notifications. Notifications can contain a composed view of the settings or a list of settings per EPA, depending on whether the ESC is able to resolve conflicts. A subscriber can receive notifications of changes in this document according to the procedures specified in RFC 3265 [5]. The aim of this memo is to follow the procedure indicated in RFC 3427 [6] and to register a new poc-settings event package with IANA.
Этот документ определяет документ PoC-settings, который позволяет EPA передавать настройки ISB, AM, IPAB и SSS на ESC. Агентство по охране окружающей среды отправляет документ PoC-settings в запросах PUBLISH [8]. Документ PoC-settings представляет представление настроек в этом конкретном EPA. ESC может собирать документы PoC-settings для одного и того же пользователя в разных EPA, применять политику составления и предоставлять уведомления. Уведомления могут содержать составное представление настроек или список настроек для каждого EPA, в зависимости от того, способен ли ESC разрешать конфликты. Абонент может получать уведомления об изменениях в настоящем документе в порядке, указанном в RFC 3265[5]. Целью этого документа является выполнение процедуры, указанной в RFC 3427 [6] и регистрация нового пакета событий poc-settings в IANA.

Пакет событий, определенный в этом документе, предназначен для использования с сетевыми серверами приложений, которые предоставляют услугу Push-to-Talk через сотовую связь.
4. Requirements
4. Требования
A comprehensive description of all the requirements that affect the Push-to-Talk over Cellular service developed by the Open Mobile Alliance can be found in the Open Mobile Alliance web page at http://www.openmobilealliance.org.
Подробное описание всех требований, влияющих на услугу Push-to-Talk over Cellular, разработанную Open Mobile Alliance, можно найти на веб-странице Open Mobile Alliance по адресу http://www.openmobilealliance.org.
For the sake of simplicity, we briefly discuss here those requirements that affect the solution described in this document. These requirements can be summarized as follows: 1. There must be a mechanism that reduces the session setup time as much as possible.
Для простоты мы кратко обсудим здесь те требования, которые влияют на решение, описанное в этом документе. Эти требования можно резюмировать следующим образом: 1. Должен быть механизм, максимально сокращающий время установки сессии.
2. In order to allow proper usage of scarce resources, there must be a mechanism that saves the air interface from being congested with unneeded or undesired traffic.
2. Чтобы обеспечить правильное использование ограниченных ресурсов, должен существовать механизм, который предохраняет радиоинтерфейс от перегрузки ненужным или нежелательным трафиком.
3. The mechanism should not involve the implementation of new protocols, unless strictly needed.
3. Механизм не должен предусматривать внедрение новых протоколов, за исключением случаев крайней необходимости.
These requirements lead to a solution whereby the user can indicate to a network node his ability to accept or reject sessions or certain types of messages. Pushing these settings to a network node allows the network node to produce a faster response to the originator, perhaps even declining or filtering some SIP requests towards the destination. This approaches the goal of reducing the session setup time.
Эти требования приводят к решению, посредством которого пользователь может указать сетевому узлу свою способность принимать или отклонять сессии или определенные типы сообщений. Передача этих настроек сетевому узлу позволяет сетевому узлу быстрее отвечать отправителю, возможно, даже отклоняя или фильтруя некоторые SIP-запросы к месту назначения. Это приближает к цели сокращения времени установки сессии.
5. The "poc-settings" Event Package
5. Пакет мероприятий «poc-settings»
RFC 3265 [5] defines a SIP extension for subscribing to remote nodes and receiving notifications of changes (events) in their states. It leaves the definition of many aspects of these events to concrete extensions, known as event packages. This document qualifies as an event package. This section fills in the information required for all event packages by RFC 3265 [5].
RFC 3265[5] определяет расширение SIP для подписки на удаленные узлы и получения уведомлений об изменениях (событиях) в их состояниях. Он оставляет определение многих аспектов этих событий конкретным расширениям, известным как пакеты событий. Этот документ квалифицируется как пакет мероприятий. В этом разделе представлена ​​информация, необходимая для всех пакетов мероприятий RFC 3265 [5].
Additionally, RFC 3903 [8] defines an extension that allows SIP User Agents to publish event state. According to RFC 3903 [8], any event package intended to be used in conjunction with the SIP PUBLISH method has to include a considerations section. This section also fills the information for all event packages to be used with PUBLISH requests.
Кроме того, RFC 3903 [8] определяет расширение, которое позволяет агентам пользователя SIP публиковать состояние событий. Согласно RFC 3903 [8], любой пакет событий, предназначенный для использования в сочетании с методом SIP PUBLISH, должен включать раздел с соображениями. В этом разделе также содержится информация обо всех пакетах событий, которые будут использоваться с запросами PUBLISH.
We define a new "poc-settings" event package. Event Publication Agents (EPA) use PUBLISH requests to inform an Event State Compositor (ESC) of changes in the poc-settings event package. Acting as a notifier, the ESC notifies subscribers to the user's poc-settings information when changes occur.
Мы определяем новый пакет событий «poc-settings». Агенты публикации событий (EPA) используют запросы PUBLISH для информирования композитора состояния событий (ESC) об изменениях в пакете событий poc-settings. Действуя как уведомитель, ESC уведомляет подписчиков о настройках poc пользователя при возникновении изменений.
5.1. Package Name
5.1. Имя пакета
The name of this package is "poc-settings". As specified in RFC 3265 [5], this value appears in the Event header field present in SUBSCRIBE and NOTIFY requests. As specified in RFC 3903 [8], this value also appears in the Event header field present in PUBLISH requests.
Имя этого пакета — «poc-settings». Как указано в RFC 3265 [5], это значение появляется в поле заголовка Event в запросах SUBSCRIBE и NOTIFY. Как указано в RFC 3903 [8], это значение также появляется в поле заголовка Event в запросах PUBLISH.
5.2. Event Package Parameters
5.2. Параметры пакета событий
RFC 3265 [5] allows event packages to define additional parameters carried in the Event header field. This event package, "poc-settings", does not define additional parameters.
RFC 3265 [5] позволяет пакетам событий определять дополнительные параметры, переносимые в поле заголовка Event. Этот пакет событий «poc-settings» не определяет дополнительных параметров.
5.3. SUBSCRIBE Bodies
5.3. ПОДПИСАТЬСЯ
According to RFC 3265 [5], a SUBSCRIBE request can contain a body. The purpose of the body depends on its type. Subscriptions to the poc-settings event package will normally not contain bodies.
Согласно RFC 3265[5], запрос SUBSCRIBE может содержать тело. Назначение тела зависит от его типа. Подписки на пакет событий poc-settings обычно не содержат тел.
The Request-URI of the SUBSCRIBE request identifies the user about whose poc-settings the subscriber wants to be informed.
Request-URI запроса SUBSCRIBE идентифицирует пользователя, о настройках poc которого подписчик хочет быть проинформирован.
5.4. Subscription Duration
5.4. Продолжительность подписки
The default expiration time for subscriptions within this package is 3600 seconds. As per RFC 3265 [5], the subscriber MAY specify an alternate expiration in the Expires header field.
Срок действия подписок в этом пакете по умолчанию составляет 3600 секунд. Согласно RFC 3265 [5], подписчик МОЖЕТ указать альтернативный срок действия в поле заголовка Expires.
5.5. NOTIFY Bodies
5.5. УВЕДОМЛЯЮЩИЕ органы
As described in RFC 3265 [5], the NOTIFY message will contain bodies describing the state of the subscribed resource. This body is in a format listed in the Accept header field of the SUBSCRIBE request, or a package-specific default format if the Accept header field was omitted from the SUBSCRIBE request.
Как описано в RFC 3265 [5], сообщение NOTIFY будет содержать тела, описывающие состояние подписанного ресурса. Это тело имеет формат, указанный в поле заголовка Accept запроса SUBSCRIBE, или формат по умолчанию, специфичный для пакета, если поле заголовка Accept было опущено в запросе SUBSCRIBE.
In this event package, the body of the notification contains a PoC- settings document (see Section 6). The ESC has gathered PoC- settings documents for the user at different EPAs. The ESC applies a composition policy and composes a PoC-settings document with a common view of all these settings across different EPAs. In case the ESC is not able to resolve a conflict, due to contradictory information provided by two different EPAs, the ESC provides a PoC-settings document containing the settings at each terminal so that the subscriber can resolve the conflict.
В этом пакете событий тело уведомления содержит документ настроек PoC (см. раздел 6). ESC собрал документы PoC-настроек для пользователя в различных EPA. ESC применяет политику композиции и составляет документ PoC-settings с общим представлением всех этих настроек в разных EPA. В случае, если ESC не может разрешить конфликт из-за противоречивой информации, предоставленной двумя разными EPA, ESC предоставляет документ PoC-settings, содержащий настройки на каждом терминале, чтобы абонент мог разрешить конфликт.
All subscribers and notifiers of the "poc-settings" event package MUST support the "application/poc-settings+xml" data format described in Section 6. The SUBSCRIBE request MAY contain an Accept header field. If no such header field is present, it has a default value of "application/poc-settings+xml" (assuming that the Event header field contains a value of "poc-settings"). If the Accept header field is present, it MUST include "application/poc-settings+xml" and MAY include any other types capable of representing user settings for PoC.
Все подписчики и уведомители пакета событий «poc-settings» ДОЛЖНЫ поддерживать формат данных «application/poc-settings+xml», описанный в разделе 6. Запрос SUBSCRIBE МОЖЕТ содержать поле заголовка Accept. Если такое поле заголовка отсутствует, оно имеет значение по умолчанию «application/poc-settings+xml» (при условии, что поле заголовка Event содержит значение «poc-settings»). Если поле заголовка Accept присутствует, оно ДОЛЖНО включать «application/poc-settings+xml» и МОЖЕТ включать любые другие типы, способные представлять пользовательские настройки для PoC.
5.6. Notifier Processing of SUBSCRIBE Requests
5.6. Обработка уведомлений запросами на ПОДПИСКУ
The contents of a PoC-settings document can contain sensitive information that can reveal some privacy information. Therefore, PoC-settings documents MUST only be sent to authorized subscribers. In order to determine if a subscription originates in an authorized user, the user MUST be authenticated as described in Section 5.6.1 and then he MUST be authorized to be a subscriber as described in Section 5.6.2.
Содержимое документа PoC-settings может содержать конфиденциальную информацию, которая может раскрыть некоторую информацию о конфиденциальности. Следовательно, PoC-settings документы ДОЛЖНЫ отправляться только авторизованным подписчикам. Чтобы определить, исходит ли подписка от авторизованного пользователя, пользователь ДОЛЖЕН пройти аутентификацию, как описано в разделе 5.6.1, а затем он ДОЛЖЕН быть авторизован как подписчик, как описано в разделе 5.6.2.
5.6.1. Authentication
5.6.1. Аутентификация
Notifiers MUST authenticate all subscription requests. This authentication can be done using any of the mechanisms defined in RFC 3261 [4] and other authentication extensions.
Уведомители ДОЛЖНЫ аутентифицировать все запросы на подписку. Эта аутентификация может быть выполнена с использованием любого из механизмов, определенных в RFC 3261 [4] и других расширениях аутентификации.
5.6.2. Authorization
5.6.2. Авторизация
Once authenticated, the notifier makes an authorization decision. A notifier MUST NOT accept a subscription unless authorization has been provided by the user. The means by which authorization are provided are outside the scope of this document. Authorization may have been provided ahead of time through access lists, perhaps specified in a web page. Authorization may have been provided by means of uploading some kind of standardized access control list document.
После аутентификации уведомитель принимает решение об авторизации. Уведомитель НЕ ДОЛЖЕН принимать подписку, если пользователь не предоставил авторизацию. Способы предоставления авторизации выходят за рамки данного документа. Авторизация могла быть предоставлена ​​заранее через списки доступа, возможно, указанные на веб-странице. Авторизация могла быть предоставлена ​​посредством загрузки какого-либо стандартизированного документа списка контроля доступа.
5.7. Notifier Generation of NOTIFY Requests
5.7. Генерация уведомлений уведомителем запросов NOTIFY
RFC 3265 [5] details the formatting and structure of NOTIFY messages. However, packages are mandated to provide detailed information on when to send a NOTIFY, how to compute the state of the resource, how to generate neutral or fake state information, and whether state information is complete or partial. This section describes those details for the poc-settings event package.
RFC 3265 [5] подробно описывает форматирование и структуру сообщений NOTIFY. Однако пакеты обязаны предоставлять подробную информацию о том, когда отправлять NOTIFY, как вычислять состояние ресурса, как генерировать нейтральную или поддельную информацию о состоянии и является ли информация о состоянии полной или частичной. В этом разделе описываются детали пакета событий poc-settings.
A notifier MAY send a NOTIFY at any time. Typically, it will send one when the poc-settings stage of a user changes. The NOTIFY request MAY contain a body containing a PoC-settings document. The times at which the NOTIFY is sent for a particular subscriber, and the contents of the body within that notification, are subject to any rules specified by the authorization policy that governs the subscription. However, typically the NOTIFY will contain an indication of those PoC-related services for which a change has occurred.
Уведомитель МОЖЕТ отправить УВЕДОМЛЕНИЕ в любое время. Обычно он отправляет его при изменении этапа настроек poc пользователя. Запрос NOTIFY МОЖЕТ содержать тело, содержащее документ PoC-settings. Время отправки NOTIFY для конкретного подписчика и содержимое тела этого уведомления регулируются любыми правилами, указанными в политике авторизации, которая управляет подпиской. Однако обычно NOTIFY будет содержать указание тех PoC-related сервисов, для которых произошло изменение.
In the case of a pending subscription, when final authorization is determined, a NOTIFY can be sent. If the result of the authorization decision was success, a NOTIFY SHOULD be sent and SHOULD contain a complete PoC-settings document with the current state of the user's PoC settings. If the subscription is rejected, a NOTIFY MAY be sent. As described in RFC 3265 [5], the Subscription-State header field indicates the state of the subscription.
В случае ожидающей подписки, когда определена окончательная авторизация, может быть отправлено УВЕДОМЛЕНИЕ. Если решение об авторизации было успешным, СЛЕДУЕТ отправить УВЕДОМЛЕНИЕ, которое ДОЛЖНО содержать полный PoC-settings документ с текущим состоянием настроек PoC пользователя. Если подписка отклонена, МОЖЕТ быть отправлено УВЕДОМЛЕНИЕ. Как описано в RFC 3265 [5], поле заголовка Subscription-State указывает состояние подписки.
The body of the NOTIFY MUST be sent using one of the types listed in the Accept header field in the most recent SUBSCRIBE request, or using the type "application/poc-settings+xml" if no Accept header field was present.
Тело NOTIFY ДОЛЖНО быть отправлено с использованием одного из типов, перечисленных в поле заголовка Accept в самом последнем запросе SUBSCRIBE, или с использованием типа «application/poc-settings+xml», если поле заголовка Accept не присутствовало.
Notifiers will typically act as Event State Compositors (ESC) and thus will learn the poc-settings event state via PUBLISH requests sent from the user's Event Publication Agent (EPA) when the user changes one of those settings. It is possible that the notifier generates a NOTIFY request for a user for which no publication has taken place. In that case, the PoC-settings document will not contain any <entity> element (see Section 6.1 for a detailed description of the <entity> element).
Уведомители обычно действуют как составители состояний событий (ESC) и, таким образом, изучают состояние событий poc-settings через запросы PUBLISH, отправляемые от агента публикации событий пользователя (EPA), когда пользователь меняет один из этих параметров. Возможно, что уведомитель генерирует запрос NOTIFY для пользователя, для которого не было публикации. В этом случае документ PoC-settings не будет содержать ни одного элемента <entity> (подробное описание элемента <entity> см. в разделе 6.1).
For reasons of privacy, it will frequently be necessary to encrypt the contents of the notifications. This can be accomplished using S/MIME [9]. The encryption can be performed using the key of the subscriber as identified in the From field of the SUBSCRIBE request. Similarly, integrity of the notifications is important to subscribers. As such, the contents of the notifications MAY provide authentication and message integrity using S/MIME [9]. Since the NOTIFY is generated by the notifier, which may not have access to the key of the user represented by the poc-settings user, often the NOTIFY will be signed by a third party. The NOTIFY request SHOULD be signed by an authority over the domain of the user. In other words, for a user whose SIP URI is sip:user@example.com, the signator of the NOTIFY SHOULD be the authority for example.com.
Из соображений конфиденциальности часто бывает необходимо зашифровать содержимое уведомлений. Это можно сделать с помощью S/MIME [9]. Шифрование может быть выполнено с использованием ключа подписчика, указанного в поле «От» запроса SUBSCRIBE. Точно так же для подписчиков важна целостность уведомлений. Таким образом, содержимое уведомлений МОЖЕТ обеспечивать аутентификацию и целостность сообщений с использованием S/MIME [9]. Поскольку NOTIFY генерируется уведомителем, который может не иметь доступа к ключу пользователя, представленному пользователем poc-settings, часто NOTIFY будет подписан третьей стороной. Запрос NOTIFY ДОЛЖЕН быть подписан уполномоченным лицом домена пользователя. Другими словами, для пользователя, чей SIP URI равен sip:user@example.com,, подписавший NOTIFY ДОЛЖЕН быть уполномоченным для example.com.
5.8. Subscriber Processing of NOTIFY Requests
5.8. Обработка подписчиком запросов NOTIFY
RFC 3265 [5] leaves it to event packages to describe the process followed by the subscriber upon receipt of a NOTIFY request, including any logic required to form a coherent resource state.
RFC 3265 [5] оставляет на усмотрение пакетов событий описание процесса, которому следует подписчик при получении запроса NOTIFY, включая любую логику, необходимую для формирования согласованного состояния ресурса.
In this specification, each NOTIFY request contains either no PoC- settings document, or a document representing one or more PoC related settings for a given user. Within a dialog, the PoC-settings document in the NOTIFY request with the highest CSeq header field value is the current one. When no document is present in that NOTIFY, the PoC-settings document present in the NOTIFY with the next highest CSeq value is used.
В этой спецификации каждый запрос NOTIFY либо не содержит документа настроек PoC, либо документ, представляющий одну или несколько настроек, связанных с PoC, для данного пользователя. В диалоговом окне текущим является документ PoC-settings в запросе NOTIFY с наибольшим значением поля заголовка CSeq. Если в этом NOTIFY нет документа, используется документ PoC-settings, присутствующий в NOTIFY, со следующим по величине значением CSeq.
5.9. Handling of Forked Requests
5.9. Обработка разветвленных запросов
RFC 3265 [5] requires each package to describe handling of forked SUBSCRIBE requests.
RFC 3265 [5] требует, чтобы каждый пакет описывал обработку разветвленных запросов SUBSCRIBE.
This specification only allows a single dialog to be constructed as a result of emitting an initial SUBSCRIBE request. This guarantees that only a single subscriber is generating notifications for a particular subscription to a particular user. The result of this is that a user can have multiple SIP User Agents active, but these should be homogeneous, so that each can generate the same set of notifications for the user's poc-settings.
Эта спецификация позволяет создать только один диалог в результате отправки первоначального запроса SUBSCRIBE. Это гарантирует, что только один подписчик генерирует уведомления для конкретной подписки для конкретного пользователя. В результате у пользователя может быть несколько активных пользовательских агентов SIP, но они должны быть однородными, чтобы каждый мог генерировать один и тот же набор уведомлений для настроек poc пользователя.
5.10. Rate of Notifications
5.10. Скорость уведомлений
RFC 3265 [5] requires each package to specify the maximum rate at which notifications can be sent.
RFC 3265 [5] требует, чтобы в каждом пакете была указана максимальная скорость отправки уведомлений.
Poc-settings notifiers SHOULD NOT generate notifications for a single user at a rate of more than once every five seconds.
Poc-settings уведомителям НЕ СЛЕДУЕТ генерировать уведомления для одного пользователя чаще, чем раз в пять секунд.
5.11. State Agents
5.11. Государственные агенты
RFC 3265 [5] requires each package to consider the role of state agents in the package and, if they are used, to specify how authentication and authorization are done.
RFC 3265 [5] требует, чтобы каждый пакет учитывал роль агентов состояния в пакете и, если они используются, определял, как выполняются аутентификация и авторизация.
This specification allows state agents to be located in the network. Publication of PoC-settings document is linked to a user. However, a user may be simultaneously logged in at different PoC terminals. If a user changes her PoC settings from a terminal, it will send a PUBLISH request containing a PoC-settings document. These settings are applicable to the user independently of the terminal at which she is logged in. In other words, PoC settings changes done in a terminal affect all the PoC terminals where the user is logged. It is RECOMMENDED that each of the terminals where the user is logged in subscribes to its own PoC-settings document in order to keep a coherent state view with the state agent.
Эта спецификация позволяет агентам состояния находиться в сети. Публикация документа PoC-settings связана с пользователем. Однако пользователь может одновременно войти в систему на разных терминалах PoC. Если пользователь изменит настройки PoC с терминала, он отправит запрос PUBLISH, содержащий документ PoC-settings. Эти настройки применимы к пользователю независимо от терминала, на котором он зарегистрирован. Другими словами, изменения настроек PoC, выполненные в терминале, влияют на все терминалы PoC, на которых зарегистрирован пользователь. РЕКОМЕНДУЕТСЯ, чтобы каждый из терминалов, на которых пользователь вошел в систему, подписался на свой собственный документ PoC-settings для поддержания согласованного представления состояния с агентом состояния.

5.13. Использование URI для получения состояния

RFC 3265 [5] позволяет пакетам использовать URI для получения больших документов состояния. PoC-settings документы довольно маленькие. Этот пакет событий не предоставляет механизм использования URI для получения больших документов состояния.
5.14. PUBLISH Bodies
5.14. ПУБЛИКОВАТЬ
RFC 3903 [8] requires event packages to define the content types expected in PUBLISH requests.
RFC 3903 [8] требует, чтобы пакеты событий определяли типы контента, ожидаемые в запросах PUBLISH.
In this event package, the body of a PUBLISH request contains a PoC- settings document (see Section 6). This PoC-settings document describes the PoC-related settings of a user at an EPA. EPAs SHOULD include their own information in a PoC-settings document; i.e., there SHOULD be a single <entity> element in the body of the PUBLISH request (See Section 6.1 for a detailed description of the <entity> element).
В этом пакете событий тело запроса PUBLISH содержит документ настроек PoC (см. раздел 6). В этом документе PoC-settings описаны PoC-related настройки пользователя в EPA. EPA ДОЛЖНЫ включать свою собственную информацию в документ PoC-settings; то есть, в теле запроса PUBLISH ДОЛЖЕН быть один элемент <entity> (подробное описание элемента <entity> см. в разделе 6.1).
All EPAs and ESCs MUST support the "application/poc-settings+xml" data format described in Section 6 and MAY support other formats.
Все EPA и ESC ДОЛЖНЫ поддерживать формат данных «application/poc-settings+xml», описанный в разделе 6, и МОГУТ поддерживать другие форматы.

Эта спецификация не связывает семантику с телом ответа PUBLISH.
5.16. Multiple Sources for Event State
5.16. Несколько источников состояния события
RFC 3903 [8] requires event packages to specify whether multiple sources can contribute to the event state view at the ESC.
RFC 3903 [8] требует, чтобы пакеты событий указывали, могут ли несколько источников вносить вклад в представление состояния события на ESC.
This event package allows different EPAs to publish the PoC settings for a particular user. Each EPA publishes its own settings grouped in an <entity> element. The EPA provides a globally unique identifier for a given address of record. This allows the ESC to differentiate EPAs and either compose a state resolving conflicts or provide the union of the states of all the EPAs that contributed to it. The composition policy at the ESC is outside the scope of this document.
Этот пакет событий позволяет различным агентствам по охране окружающей среды публиковать настройки PoC для конкретного пользователя. Каждое EPA публикует свои собственные настройки, сгруппированные в элементе <entity>. EPA предоставляет глобальный уникальный идентификатор для данного адреса записи. Это позволяет ESC дифференцировать EPA и либо составлять государство, разрешающее конфликты, либо обеспечивать объединение штатов всех EPA, которые внесли в него свой вклад. Политика состава ESC выходит за рамки данного документа.
5.17. Event State Segmentation
5.17. Сегментация состояний событий
RFC 3903 [8] defines segments within a state document. Each segment is defined as one of potentially many identifiable sections in the published event state.
RFC 3903 [8] определяет сегменты внутри документа состояния. Каждый сегмент определяется как один из потенциально многих идентифицируемых разделов в опубликованном состоянии события.
This event package defines, for a given EPA, four segments identified by the elements <isb-settings>, <am-settings>, <ipab-settings>, and <sss-settings>, respectively. Each of them refers to different states of the EPA.
Этот пакет событий определяет для данного EPA четыре сегмента, идентифицированные элементами <isb-settings>, <am-settings>, <ipab-settings> и <sss-settings> соответственно. Каждый из них относится к разным штатам EPA.
5.18. Rate of Publication
5.18. Скорость публикации
RFC 3903 [8] allows event packages to define their own rate of publication.
RFC 3903 [8] позволяет пакетам событий определять собственную скорость публикации.
There are no rate-limiting recommendations for poc-settings publication. Since changes in a PoC-settings document are typically triggered by interaction with a human user, there is not periodicity, nor a minimum or maximum rate of publication.
Никаких рекомендаций по ограничению скорости публикации poc-настроек не существует. Поскольку изменения в документе PoC-settings обычно инициируются взаимодействием с пользователем-человеком, здесь нет периодичности, а также минимальной или максимальной скорости публикации.
6. PoC-Settings Document
6. PoC-Settings Документ
PoC-settings is an XML document [10] that MUST be well-formed and SHOULD be valid. PoC-settings documents MUST be based on XML 1.0 and MUST be encoded using UTF-8 [7]. This specification makes use of XML namespaces for identifying PoC-settings documents. The namespace URI for elements defined by this specification is a URN [2], using the namespace identifier 'oma'. This URN is: urn:oma:params:xml:ns:poc:poc-settings
PoC-settings — это XML-документ [10], который ДОЛЖЕН быть корректным и ДОЛЖЕН быть действительным. Документы PoC-settings ДОЛЖНЫ быть основаны на XML 1.0 и ДОЛЖНЫ быть закодированы с использованием UTF-8 [7]. Эта спецификация использует пространства имен XML для идентификации документов PoC-settings. URI пространства имен для элементов, определенных в этой спецификации, представляет собой URN [2] с использованием идентификатора пространства имен «oma». Этот URN: urn:oma:params:xml:ns:poc:poc-settings
PoC-settings documents are identified with the MIME type "application/poc-settings+xml" and are instances of the XML schema defined in Section 6.1.
Документы PoC-settings идентифицируются с помощью MIME-типа «application/poc-settings+xml» и являются экземплярами схемы XML, определенной в разделе 6.1.
A PoC-settings document begins with the root element tag <poc-settings>. It consists of zero or more <entity> elements, each one including an 'id' attribute that contains a globally unique identifier for a given address of record that represents an EPA. An <entity> element represents an EPA, and it is uniquely identified by the 'id' attribute. EPAs SHOULD include a single <entity> element in a PoC-settings document. ESCs MAY include several <entity> elements in a PoC-settings document, typically when the ESC is unable to resolve conflicts due to incongruent publication from different sources. A valid PoC-settings document can include zero <entity> elements if the ESC provides a notification for which no publication has occurred.
Документ PoC-settings начинается с тега корневого элемента <poc-settings>. Он состоит из нуля или более элементов <entity>, каждый из которых включает атрибут «id», который содержит глобальный уникальный идентификатор для данного адреса записи, представляющей EPA. Элемент <entity> представляет EPA и однозначно идентифицируется атрибутом «id». EPA ДОЛЖНЫ включать один элемент <entity> в документ PoC-settings. ESC МОГУТ включать несколько элементов <entity> в документ PoC-settings, обычно когда ESC не может разрешить конфликты из-за несоответствующей публикации из разных источников. Действительный документ PoC-settings может содержать ноль элементов <entity>, если ESC предоставляет уведомление, для которого не было публикации.
The <entity> element MAY contain other elements and attributes from different namespaces for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <entity> МОЖЕТ содержать другие элементы и атрибуты из разных пространств имен в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.
The <entity> element consists of zero or one <isb-settings> elements, zero or one <am-settings> elements, zero or one <ipab-settings>, and zero or one <sss-settings> elements. Other elements and attributes from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <entity> состоит из нуля или одного элемента <isb-settings>, нуля или одного элемента <am-settings>, нуля или одного элемента <ipab-settings> и нуля или одного элемента <sss-settings>. Другие элементы и атрибуты из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.
An <isb-settings> element contains a single <incoming-session- barring> element that contains a boolean 'active' attribute. The 'active' attribute indicates whether incoming sessions are barred at the UA, depending on the user's preferences for this setting. Other elements and attributes from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <isb-settings> содержит один элемент <incoming-session- barring> с логическим атрибутом «active». Атрибут «active» указывает, запрещены ли входящие сессии на UA, в зависимости от предпочтений пользователя для этого параметра. Другие элементы и атрибуты из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.
An <am-settings> element contains an <answer-mode> element, whose value can be set to either "automatic" or "manual". Other elements and attributes from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <am-settings> содержит элемент <answer-mode>, значение которого может быть установлено как «automatic» или «manual». Другие элементы и атрибуты из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.
A server such as a URI-list server [11] receives a SIP request addressed to one or more recipients. If the intended recipient set the <answer-mode> to "manual", the URI-list server proceeds with the session attempt. If she set it to "automatic", the URI-list server generates a 200-class response prior to contacting the intended recipient.
Сервер, такой как URI-list сервер [11], получает запрос SIP, адресованный одному или нескольким получателям. Если предполагаемый получатель установил для <answer-mode> значение «manual», сервер URI-list продолжит попытку сессии. Если она установит для него значение «automatic», сервер URI-list сгенерирует ответ класса 200 перед тем, как связаться с предполагаемым получателем.
An <ipab-settings> element contains a single <incoming-personal- alert-barring> element that contains a boolean 'active' attribute. The 'active' attribute indicates whether incoming personal alert messages are barred at the UA, depending on the user's preferences for this setting. Other elements from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <ipab-settings> содержит один элемент <incoming-personal- alert-barring> с логическим атрибутом «active». Атрибут «active» указывает, запрещены ли входящие персональные предупреждающие сообщения на UA, в зависимости от предпочтений пользователя для этого параметра. Другие элементы из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.
An <sss-settings> element contains a single <simultaneous-sessions- support> element that contains a boolean 'active' attribute. The 'active' attribute indicates whether the SIP UA is willing to handle more than one PoC session simultaneously. If the 'active' attribute is set to "false" or "0", then when the SIP UA is engaged in a PoC session, and the SIP UA receives an second incoming request for a SIP PoC session, the UA will decline the invitation. If the 'active' attribute is set to "true" or "1", then when the SIP UA is engaged in a PoC session, and the SIP UA receives an second incoming request for a SIP PoC session, the UA will possibly accept the invitation. Other elements and attributes from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored.
Элемент <sss-settings> содержит один элемент <simultaneous-sessions- support> с логическим атрибутом «active». Атрибут «active» указывает, готов ли SIP UA обрабатывать более одного сессии PoC одновременно. Если атрибут «active» установлен в «false» или «0», то, когда SIP UA участвует в сессии PoC, и SIP UA получает второй входящий запрос на сессия SIP PoC, UA отклонит приглашение. Если атрибут «active» установлен в «true» или «1», то, когда SIP UA участвует в сессии PoC, и SIP UA получает второй входящий запрос на сессия SIP PoC, UA, возможно, примет приглашение. Другие элементы и атрибуты из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться.

7. Security Considerations
7. Вопросы безопасности
The "poc-settings" event package defined by this document is meant to be transported with SIP PUBLISH requests. Therefore, the Security Considerations (Section 14) in RFC 3903 [8] apply to this document. In particular, the settings contained in the "poc-settings" event package are applicable to the user that generated the SIP PUBLISH request. Therefore, servers that receive SIP PUBLISH requests containing a "poc-settings" event package SHOULD authenticate the user prior to authorizing the event publication (as required by RFC 3903 [8]).
Пакет событий «poc-settings», определенный в этом документе, предназначен для передачи с запросами SIP PUBLISH. Таким образом, к этому документу применимы соображения безопасности (раздел 14) в RFC 3903 [8]. В частности, настройки, содержащиеся в пакете событий «poc-settings» применимы к пользователю, сгенерировавшему запрос SIP PUBLISH. Таким образом, серверы, которые получают запросы SIP PUBLISH, содержащие пакет событий «poc-settings», ДОЛЖНЫ аутентифицировать пользователя перед авторизацией публикации события (как того требует RFC 3903 [8]).
Authentication and authorization of subscriptions have been discussed in Section 5.6. Lack of authentication or authorization may provide poc-settings information to unauthorized parties, who can use that information for creating attacks. For example, an unauthorized recipient of a PoC-settings document can learn that the publisher's terminal is set to answer PoC sessions in automatic answer mode and then create a malicious session containing inappropriate media that the UAS will play automatically. Or the attacker can learn that the terminal is willing to receive simultaneous PoC sessions and then try to exhaust resources in the SIP UA by creating bogus PoC sessions that leave hung states in the attacked SIP UA.
Аутентификация и авторизация подписок обсуждались в разделе 5.6. Отсутствие аутентификации или авторизации может предоставить информацию о настройках poc неавторизованным лицам, которые могут использовать эту информацию для создания атак. Например, неавторизованный получатель документа PoC-settings может узнать, что терминал издателя настроен на ответ на сессии PoC в режиме автоматического ответа, а затем создать вредоносный сессия, содержащий неподходящие медиафайлы, которые UAS будет воспроизводить автоматически. Или злоумышленник может узнать, что терминал готов получать одновременные сессии PoC, а затем попытаться исчерпать ресурсы SIP UA, создавая поддельные сессии PoC, которые оставляют зависшие состояния в атакованном SIP UA.
Integrity protection and confidentiality of notifications are also discussed in Section 5.7. If a notifier does not encrypt bodies of NOTIFY requests, an eavesdropper could learn the status of a SIP user agent and use it to create malicious PoC sessions. If the notifier does not integrity protect the bodies of NOTIFY requests, a man-in- the-middle attacker or malicious SIP proxy could modify the contents of the poc-settings event package notification. Although this does not cause harm, it can create annoyances (e.g., media clip due to lack of buffering) when PoC sessions are delivered to the user.
Защита целостности и конфиденциальность уведомлений также обсуждаются в разделе 5.7. Если уведомитель не шифрует тела запросов NOTIFY, перехватчик может узнать статус пользовательского агента SIP и использовать его для создания вредоносных сессий PoC. Если уведомитель не обеспечивает целостность тела запросов NOTIFY, злоумышленник «посредник» или вредоносный прокси SIP могут изменить содержимое уведомления пакета событий poc-settings. Хотя это и не причиняет вреда, но может создавать неудобства (например, медиаклип из-за отсутствия буферизации), когда сессии PoC доставляются пользователю.
