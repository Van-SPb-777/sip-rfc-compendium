Abstract
Аннотация
SIP supports communications for several services, including real-time audio, video, text, instant messaging, and presence. In its current form, it allows session invitations, instant messages, and other requests to be delivered from one party to another without requiring explicit consent of the recipient. Without such consent, it is possible for SIP to be used for malicious purposes, including amplification and DoS (Denial of Service) attacks. This document identifies a framework for consent-based communications in SIP.
SIP поддерживает связь для нескольких служб, включая аудио, видео, текстовые сообщения в реальном времени, обмен мгновенными сообщениями и присутствие. В своей текущей форме он позволяет доставлять приглашения на сессии, мгновенные сообщения и другие запросы от одной стороны к другой без необходимости явного согласия получателя. Без такого согласия возможно использование SIP в злонамеренных целях, включая усиление и DoS-атаки (отказ в обслуживании). Этот документ определяет структуру для связи на основе согласия в SIP.

1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [RFC3261] supports communications for several services, including real-time audio, video, text, instant messaging, and presence. This communication is established by the transmission of various SIP requests (such as INVITE and MESSAGE [RFC3428]) from an initiator to the recipient with whom communication is desired. Although a recipient of such a SIP request can reject the request, and therefore decline the session, a network of SIP proxy servers will deliver a SIP request to its recipients without their explicit consent.
Протокол инициирования сессий (SIP) [RFC3261] поддерживает связь для нескольких служб, включая аудио, видео, текстовые сообщения в реальном времени, обмен мгновенными сообщениями и присутствие. Эта связь устанавливается путем передачи различных SIP-запросов (таких как INVITE и MESSAGE [RFC3428]) от инициатора получателю, с которым требуется связь. Хотя получатель такого запроса SIP может отклонить запрос и, следовательно, отклонить сессия, сеть прокси SIP доставит запрос SIP своим получателям без их явного согласия.
Receipt of these requests without explicit consent can cause a number of problems. These include amplification and DoS (Denial of Service) attacks. These problems are described in more detail in a companion requirements document [RFC4453].
Получение этих запросов без явного согласия может вызвать ряд проблем. К ним относятся атаки усиления и DoS (отказ в обслуживании). Эти проблемы более подробно описаны в сопутствующем документе с требованиями [RFC4453].
This specification defines a basic framework for adding consent-based communication to SIP.
Эта спецификация определяет базовую структуру для добавления связи на основе согласия в SIP.
2. Definitions and Terminology
2. Определения и терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [RFC2119].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует интерпретировать так, как описано в RFC 2119 [RFC2119].
Recipient URI: The Request-URI of an outgoing request sent by an entity (e.g., a user agent or a proxy). The sending of such request can have been the result of a translation operation.
URI получателя: Request-URI исходящего запроса, отправленного объектом (например, пользовательским агентом или прокси). Отправка такого запроса могла быть результатом операции перевода.
Relay: Any SIP server, be it a proxy, B2BUA (Back-to-Back User Agent), or some hybrid, that receives a request, translates its Request-URI into one or more next-hop URIs (i.e., recipient URIs), and delivers the request to those URIs.
Ретрансляция: любой SIP-сервер, будь то прокси, B2BUA (Back-to-Back Пользовательский агент) или какой-либо гибрид, который получает запрос, преобразует свой Request-URI в один или несколько URI следующего перехода (то есть, URI получателя) и доставляет запрос по этим URI.
Target URI: The Request-URI of an incoming request that arrives to a relay that will perform a translation operation.
Целевой URI: Request-URI входящего запроса, поступающего на ретранслятор, который выполнит операцию трансляции.
Translation logic: The logic that defines a translation operation at a relay. This logic includes the translation's target and recipient URIs.
Логика трансляции: Логика, определяющая операцию трансляции на реле. Эта логика включает в себя URI цели и получателя перевода.
Translation operation: Operation by which a relay translates the Request-URI of an incoming request (i.e., the target URI) into one or more URIs (i.e., recipient URIs) that are used as the Request- URIs of one or more outgoing requests.
Операция трансляции: Операция, посредством которой ретранслятор преобразует Request-URI входящего запроса (то есть, целевой URI) в один или несколько URI (то есть, URI получателя), которые используются в качестве Request-URI одного или нескольких исходящих запросов.
3. Relays and Translations
3. Ретрансляции и трансляции
Relays play a key role in this framework. A relay is defined as any SIP server, be it a proxy, B2BUA (Back-to-Back User Agent), or some hybrid, that receives a request, translates its Request-URI into one or more next-hop URIs, and delivers the request to those URIs. The Request-URI of the incoming request is referred to as 'target URI' and the destination URIs of the outgoing requests are referred to as 'recipient URIs', as shown in Figure 1.
Реле играют ключевую роль в этой системе. Ретранслятор определяется как любой SIP-сервер, будь то прокси, B2BUA (Back-to-Back User Agent) или какой-либо гибрид, который получает запрос, преобразует свой Request-URI в один или несколько URI следующего перехода и доставляет запрос на эти URI. Request-URI входящего запроса называется «целевым URI», а URI назначения исходящих запросов называются «URI получателя», как показано на рисунке 1.

+---------------+ recipient URI | |----------------> | | target URI | Translation | [...] -------------->| Operation | | | recipient URI | |----------------> +---------------+ Figure 1: Translation Operation
Thus, an essential aspect of a relay is that of translation. When a relay receives a request, it translates the Request-URI (target URI) into one or more additional URIs (recipient URIs). Through this translation operation, the relay can create outgoing requests to one or more additional recipient URIs, thus creating the consent problem.
Таким образом, существенным аспектом ретрансляции является трансляция. Когда ретранслятор получает запрос, он преобразует Request-URI (целевой URI) в один или несколько дополнительных URI (URI получателя). Посредством этой операции трансляции ретранслятор может создавать исходящие запросы к одному или нескольким дополнительным URI получателя, создавая тем самым проблему согласия.
The consent problem is created by two types of translations: translations based on local data and translations that involve amplifications.
Проблему согласия создают два типа переводов: переводы, основанные на местных данных, и переводы, предполагающие расширения.
Translation operations based on local policy or local data (such as registrations) are the vehicle by which a request is delivered directly to an endpoint, when it would not otherwise be possible to. In other words, if a spammer has the address of a user, 'sip:user@example.com', it cannot deliver a MESSAGE request to the UA (user agent) of that user without having access to the registration data that maps 'sip:user@example.com' to the user agent on which that user is present. Thus, it is the usage of this registration data, and more generally, the translation logic, that is expected to be authorized in order to prevent undesired communications. Of course, if the spammer knows the address of the user agent, it will be able to deliver requests directly to it.
Операции перевода, основанные на локальной политике или локальных данных (например, регистрации), являются средством, с помощью которого запрос доставляется непосредственно в конечную точку, когда иначе это было бы невозможно. Другими словами, если у спамера есть адрес пользователя «sip:user@example.com», он не может доставить запрос MESSAGE UA (агенту пользователя) этого пользователя, не имея доступа к регистрационным данным, которые сопоставляют «sip:user@example.com» с агентом пользователя, в котором присутствует этот пользователь. Таким образом, ожидается, что использование этих регистрационных данных и, в более общем смысле, логики трансляции будет авторизовано для предотвращения нежелательной связи. Конечно, если спамер знает адрес пользовательского агента, он сможет доставлять запросы непосредственно к нему.
Translation operations that result in more than one recipient URI are a source of amplification. Servers that do not perform translations, such as outbound proxy servers, do not cause amplification. On the other hand, servers that perform translations (e.g., inbound proxies authoritatively responsible for a SIP domain) may cause amplification if the user can be reached at multiple endpoints (thereby resulting in multiple recipient URIs).
Операции перевода, в результате которых получается более одного URI получателя, являются источником амплификации. Серверы, которые не выполняют трансляции, например исходящие прокси, не вызывают амплификации. С другой стороны, серверы, выполняющие трансляции (например, входящие прокси, ответственные за домен SIP), могут вызвать усиление, если с пользователем можно связаться на нескольких конечных точках (что приводит к появлению нескольких URI получателей).

4.1. Permissions at a Relay
4.1. Разрешения на реле
Relays implementing this framework obtain and store permissions associated to their translation logic. These permissions indicate whether or not a particular recipient has agreed to receive traffic at any given time. Recipients that have not given the relay permission to send them traffic are simply ignored by the relay when performing a translation.
Ретрансляторы, реализующие эту структуру, получают и сохраняют разрешения, связанные с их логикой трансляции. Эти разрешения указывают, согласился ли конкретный получатель получать трафик в любой момент времени. Получатели, которые не предоставили ретранслятору разрешение на отправку им трафика, ретранслятор просто игнорирует при выполнении трансляции.
In principle, permissions are valid as long as the context where they were granted is valid or until they are revoked. For example, the permissions obtained by a URI-list SIP service that distributes MESSAGE requests to a set of recipients will be valid as long as the URI-list SIP service exists or until the permissions are revoked. Additionally, if a recipient is removed from a relay's translation logic, the relay SHOULD delete the permissions related to that recipient. For example, if the registration of a contact URI expires or is otherwise terminated, the registrar deletes the permissions related to that contact address.
В принципе, разрешения действительны до тех пор, пока действителен контекст, в котором они были предоставлены, или до тех пор, пока они не будут отозваны. Например, разрешения, полученные службой SIP URI-list, которая распределяет запросы MESSAGE набору получателей, будут действительны до тех пор, пока служба SIP URI-list существует или пока разрешения не будут отозваны. Кроме того, если получатель удален из логики трансляции ретранслятора, ретранслятору СЛЕДУЕТ удалить разрешения, относящиеся к этому получателю. Например, если срок регистрации контактного URI истекает или прекращается иным образом, регистратор удаляет разрешения, связанные с этим контактным адресом.
It is also RECOMMENDED that relays request recipients to refresh their permissions periodically. If a recipient fails to refresh its permissions for a given period of time, the relay SHOULD delete the permissions related to that recipient. This framework does not provide any guidance for the values of the refreshment intervals because different applications can have different requirements to set those values. For example, a relay dealing with recipients that do not implement this framework may choose to use longer intervals between refreshes. The refresh process in such recipients has to be performed manually by their users (since the recipients do not implement this framework), and having too short refresh intervals may become too heavy a burden for those users.
Также РЕКОМЕНДУЕТСЯ, чтобы ретрансляторы запрашивали получателей периодически обновлять свои разрешения. Если получателю не удается обновить свои разрешения в течение определенного периода времени, ретранслятор ДОЛЖЕН удалить разрешения, относящиеся к этому получателю. Эта платформа не предоставляет никаких указаний по значениям интервалов обновления, поскольку разные приложения могут предъявлять разные требования к установке этих значений. Например, ретранслятор, работающий с получателями, которые не реализуют эту структуру, может использовать более длинные интервалы между обновлениями. Процесс обновления в таких получателях должен выполняться их пользователями вручную (поскольку получатели не реализуют эту структуру), и слишком короткие интервалы обновления могут стать слишком тяжелым бременем для этих пользователей.
4.2. Consenting Manipulations on a Relay's Translation Logic
4.2. Согласованные манипуляции с логикой трансляции реле
This framework aims to ensure that any particular relay only performs translations towards destinations that have given the relay permission to perform such a translation. Consequently, when the translation logic of a relay is manipulated (e.g., a new recipient URI is added), the relay obtains permission from the new recipient in order to install the new translation logic. Relays ask recipients for permission using MESSAGE [RFC3428] requests.
Эта структура направлена ​​на то, чтобы любой конкретный ретранслятор выполнял переводы только в направлении пунктов назначения, которые предоставили ретранслятору разрешение на выполнение такого перевода. Следовательно, когда манипулируют логикой трансляции ретранслятора (например, добавляется новый URI получателя), ретранслятор получает разрешение от нового получателя для установки новой логики трансляции. Ретрансляторы запрашивают у получателей разрешение, используя запросы MESSAGE [RFC3428].
For example, the relay hosting the URI-list service at 'sip:friends@example.com' performs a translation from that target URI to a set of recipient URIs. When a client (e.g., the administrator of that URI-list service) adds 'bob@example.org' as a new recipient URI, the relay sends a MESSAGE request to 'sip:bob@example.org' asking whether or not it is OK to perform the translation from 'sip:friends@example.com' to 'sip:bob@example.org'. The MESSAGE request carries in its message body a permission document that describes the translation for which permissions are being requested and a human-readable part that also describes the translation. If the answer is positive, the new translation logic is installed at the relay. That is, the new recipient URI is added. The human-readable part is included so that user agents that do not understand permission documents can still process the request and display it in a sensible way to the user.
Например, ретранслятор, размещающий службу URI-list в «sip:friends@example.com», выполняет преобразование из этого целевого URI в набор URI получателей. Когда клиент (например, администратор этой службы URI-list) добавляет «bob@example.org» в качестве URI нового получателя, ретранслятор отправляет запрос MESSAGE на «sip:bob@example.org» с вопросом, можно ли выполнить преобразование из «sip:friends@example.com» в «sip:bob@example.org». Запрос MESSAGE содержит в своем теле сообщения документ разрешения, описывающий перевод, для которого запрашиваются разрешения, и удобочитаемую часть, которая также описывает перевод. Если ответ положительный, в реле устанавливается новая логика трансляции. То есть добавляется новый URI получателя. Удобочитаемая часть включена для того, чтобы пользовательские агенты, которые не понимают разрешительные документы, могли обрабатывать запрос и отображать его пользователю в разумной форме.
The mechanism to be used to manipulate the translation logic of a particular relay depends on the relay. Two existing mechanisms to manipulate translation logic are XML Configuration Access Protocol (XCAP) [RFC4825] and REGISTER transactions. Section 5 uses a URI-list service whose translation logic is manipulated with XCAP as an example of a translation, in order to specify this framework. Section 5.10 discusses how to apply this framework to registrations, which are a different type of translation.
Механизм, который будет использоваться для управления логикой трансляции конкретного реле, зависит от реле. Двумя существующими механизмами управления логикой трансляции являются протокол доступа к конфигурации XML (XCAP) [RFC4825] и транзакции REGISTER. В разделе 5 в качестве примера перевода используется сервис URI-list, логика перевода которого управляется с помощью XCAP, чтобы указать эту структуру. В разделе 5.10 обсуждается, как применять эту структуру к регистрациям, которые представляют собой другой тип перевода.
In any case, relays implementing this framework SHOULD have a means to indicate that a particular recipient URI is in the states specified in [RFC5362] (i.e., pending, waiting, error, denied, or granted).
В любом случае ретрансляторы, реализующие эту структуру, ДОЛЖНЫ иметь средства, указывающие, что конкретный URI получателя находится в состояниях, указанных в [RFC5362] (то есть, ожидание, ожидание, ошибка, отказ или разрешение).
4.3. Store-and-Forward Servers
4.3. Store-and-Forward Серверы
When a MESSAGE request with a permission document arrives to the recipient URI to which it was sent by the relay, the receiving user can grant or deny the permission needed to perform the translation. However, the receiving user may not be available when the MESSAGE request arrives, or it may have expressed preferences to block all incoming requests for a certain time period. In such cases, a store-and-forward server can act as a substitute for the user and buffer the incoming MESSAGE requests, which are subsequently delivered to the user when he or she is available again.
Когда запрос MESSAGE с документом разрешения поступает на URI получателя, которому он был отправлен ретранслятором, принимающий пользователь может предоставить или отклонить разрешение, необходимое для выполнения перевода. Однако принимающий пользователь может быть недоступен при поступлении запроса MESSAGE или может иметь выраженное предпочтение блокировать все входящие запросы на определенный период времени. В таких случаях сервер промежуточного хранения может действовать вместо пользователя и буферизовать входящие запросы MESSAGE, которые впоследствии доставляются пользователю, когда он или она снова доступны.
There are several mechanisms to implement store-and-forward message services (e.g., with an instant message to email gateway). Any of these mechanisms can be used between a user agent and its store-and- forward server as long as they agree on which mechanism to use. Therefore, this framework does not make any provision for the interface between user agents and their store-and-forward servers. Note that the same store-and-forward message service can handle all incoming MESSAGE requests for a user while they are offline, not only those MESSAGE requests with a permission document in their bodies.
Существует несколько механизмов реализации служб сообщений с промежуточным хранением (например, с мгновенным сообщением на шлюз электронной почты). Любой из этих механизмов может использоваться между пользовательским агентом и его сервером хранения и пересылки, если они договорились, какой механизм использовать. Таким образом, эта платформа не предусматривает никакого интерфейса между пользовательскими агентами и их серверами промежуточного хранения. Обратите внимание, что одна и та же служба сообщений с промежуточным хранением может обрабатывать все входящие запросы MESSAGE для пользователя, когда он находится в автономном режиме, а не только те запросы MESSAGE, в теле которых есть разрешительный документ.
Even though store-and-forward servers perform a useful function and they are expected to be deployed in most domains, some domains will not deploy them from the outset. However, user agents and relays in domains without store-and-forward servers can still use this consent framework. When a relay requests permissions from an offline user agent that does not have an associated store-and-forward server, the relay will obtain an error response indicating that its MESSAGE request could not be delivered. The client that attempted to add the offline user to the relay's translation logic will be notified about the error (e.g., using the Pending Additions event package [RFC5362]). This client MAY attempt to add the same user at a later point, hopefully when the user is online. Clients can discover whether or not a user is online by using a presence service, for instance.
Несмотря на то, что серверы с промежуточным хранением выполняют полезную функцию и ожидается, что они будут развернуты в большинстве доменов, некоторые домены не будут развертывать их с самого начала. Однако пользовательские агенты и ретрансляторы в доменах без серверов хранения и пересылки по-прежнему могут использовать эту структуру согласия. Когда ретранслятор запрашивает разрешения у автономного пользовательского агента, у которого нет связанного сервера промежуточного хранения, ретранслятор получит ответ об ошибке, указывающий, что его запрос MESSAGE не может быть доставлен. Клиент, который попытался добавить автономного пользователя в логику трансляции реле, будет уведомлен об ошибке (например, с использованием пакета событий «Ожидание дополнений» [RFC5362]). Этот клиент МОЖЕТ попытаться добавить того же пользователя позже, возможно, когда пользователь будет в сети. Клиенты могут узнать, находится ли пользователь в сети, например, с помощью службы присутствия.
4.4. Recipients Grant Permissions
4.4. Получатели предоставляют разрешения
Permission documents generated by a relay include URIs that can be used by the recipient of the document to grant or deny the relay the permission described in the document. Relays always include SIP URIs and can include HTTP [RFC2616] URIs for this purpose. Consequently, recipients provide relays with permissions using SIP PUBLISH requests or HTTP GET requests.
Документы разрешений, созданные ретранслятором, включают URI, которые может использоваться получателем документа для предоставления или отказа ретранслятору в разрешении, описанном в документе. Ретрансляторы всегда включают SIP URI и для этой цели могут включать HTTP [RFC2616] URI. Следовательно, получатели предоставляют ретрансляторам разрешения, используя запросы SIP PUBLISH или запросы HTTP GET.
4.5. Entities Implementing This Framework
4.5. Субъекты, реализующие эту структуру
The goal of this framework is to keep relays from executing translations towards unwilling recipients. Therefore, all relays MUST implement this framework in order to avoid being used to perform attacks (e.g., amplification attacks).
Цель этой структуры — не дать ретрансляторам выполнять переводы нежелательным получателям. Следовательно, все ретрансляторы ДОЛЖНЫ реализовать эту структуру, чтобы избежать использования для выполнения атак (например, атаки с усилением).
This framework has been designed with backwards compatibility in mind so that legacy user agents (i.e., user agents that do not implement this framework) can act both as clients and recipients with an acceptable level of functionality. However, it is RECOMMENDED that user agents implement this framework, which includes supporting the Pending Additions event package specified in [RFC5362], the format for permission documents specified in [RFC5361], and the header fields and response code specified in this document, in order to achieve full functionality.
Эта платформа была разработана с учетом обратной совместимости, чтобы устаревшие пользовательские агенты (то есть, пользовательские агенты, которые не реализуют эту структуру) могли действовать как клиенты и получатели с приемлемым уровнем функциональности. Однако РЕКОМЕНДУЕТСЯ, чтобы пользовательские агенты реализовали эту структуру, которая включает поддержку пакета событий «Ожидание дополнений», указанного в [RFC5362], формата разрешительных документов, указанного в [RFC5361], а также полей заголовка и кода ответа, указанных в этом документе, для достижения полной функциональности.
The only requirement that this framework places on store-and-forward servers is that they need to be able to deliver encrypted and integrity-protected messages to their user agents, as discussed in Section 7. However, this is not a requirement specific to this framework but a general requirement for store-and-forward servers.
Единственное требование, которое эта платформа предъявляет к серверам с промежуточным хранением, состоит в том, что они должны иметь возможность доставлять зашифрованные и защищенные целостность сообщения своим пользовательским агентам, как обсуждалось в разделе 7. Однако это не требование, специфичное для этой платформы, а общее требование для серверов с промежуточным хранением.

5.1. Amplification Avoidance
5.1. Избегание усиления
Once 'sip:B@example.com' is in the pending state, the relay needs to ask user B for permission by sending a MESSAGE request to 'sip:B@example.com'. However, the relay needs to ensure that it is not used as an amplifier to launch amplification attacks. In such an attack, the attacker would add a large number of recipient URIs to the translation logic of a relay. The relay would then send a MESSAGE request to each of those recipient URIs. The bandwidth generated by the relay would be much higher than the bandwidth used by the attacker to add those recipient URIs to the translation logic of the relay.
Как только 'sip:B@example.com' находится в состоянии ожидания, реле должно запросить разрешение у пользователя B, отправив запрос MESSAGE на 'sip:B@example.com'. Однако реле должно гарантировать, что оно не будет использоваться в качестве усилителя для запуска атак с усилением. При такой атаке злоумышленник добавляет большое количество URI получателей в логику трансляции ретранслятора. Затем ретранслятор отправит запрос MESSAGE каждому из этих URI получателей. Пропускная способность, генерируемая ретранслятором, будет намного выше, чем полоса пропускания, используемая злоумышленником для добавления URI получателей в логику трансляции ретранслятора.
This framework uses a credit-based authorization mechanism to avoid the attack just described. It requires users adding new recipient URIs to a translation to generate an amount of bandwidth that is comparable to the bandwidth the relay will generate when sending MESSAGE requests towards those recipient URIs. When XCAP is used, this requirement is met by not allowing clients to add more than one URI per HTTP transaction. When a REGISTER transaction is used, this requirement is met by not allowing clients to register more than one contact per REGISTER transaction.
Эта структура использует механизм авторизации на основе кредитов, чтобы избежать только что описанной атаки. Это требует от пользователей добавления новых URI получателей в преобразование для создания пропускной способности, сопоставимой с пропускной способностью, которую ретранслятор будет генерировать при отправке запросов MESSAGE к этим URI получателей. При использовании XCAP это требование удовлетворяется тем, что клиентам не разрешается добавлять более одного URI для каждой HTTP-транзакции. Когда используется транзакция REGISTER, это требование выполняется за счет того, что клиентам не разрешается регистрировать более одного контакта для каждой транзакции REGISTER.
5.1.1. Relay's Behavior
5.1.1. Поведение реле
Relays implementing this framework MUST NOT allow clients to add more than one recipient URI per transaction. If a client using XCAP attempts to add more than one recipient URI in a single HTTP transaction, the XCAP server SHOULD return an HTTP 409 (Conflict) response. The XCAP server SHOULD describe the reason for the refusal in an XML body using the <constraint-failure> element, as described in [RFC4825]. If a client attempts to register more than one contact in a single REGISTER transaction, the registrar SHOULD return a SIP 403 response and explain the reason for the refusal in its reason phrase (e.g., maximum one contact per registration).
Ретрансляторы, реализующие эту структуру, НЕ ДОЛЖНЫ позволять клиентам добавлять более одного URI получателя за транзакцию. Если клиент, использующий XCAP, пытается добавить более одного URI получателя в одной транзакции HTTP, сервер XCAP ДОЛЖЕН вернуть ответ HTTP 409 (конфликт). Сервер XCAP ДОЛЖЕН описать причину отказа в теле XML, используя элемент <constraint-failure>, как описано в [RFC4825]. Если клиент пытается зарегистрировать более одного контакта в одной транзакции REGISTER, регистратор ДОЛЖЕН вернуть ответ SIP 403 и объяснить причину отказа в своей фразе причины (например, максимум один контакт на регистрацию).
5.2. Subscription to the Permission Status
5.2. Подписка на статус разрешения
Clients need a way to be informed about the status of the operations they requested. Otherwise, users can be waiting for an operation to succeed when it has actually already failed. In particular, if the target of the request for consent was not reachable and did not have an associated store-and-forward server, the client needs to know to retry the request later. The Pending Additions SIP event package [RFC5362] is a way to provide clients with that information.
Клиентам нужен способ получать информацию о статусе запрошенных ими операций. В противном случае пользователи могут ожидать успешного завершения операции, хотя на самом деле она уже завершилась неудачно. В частности, если цель запроса на согласие недоступна и не имеет связанного с ней сервера промежуточного хранения, клиенту необходимо знать, чтобы повторить запрос позже. Пакет событий SIP «Ожидающие дополнения» [RFC5362] — это способ предоставить клиентам эту информацию.
Clients can use the Pending Additions SIP event package to be informed about the status of the operations they requested. That is, the client will be informed when an operation (e.g., the addition of a recipient URI to a relay's translation logic) is authorized (and thus executed) or rejected. Clients use the target URI of the SIP translation being manipulated to subscribe to the 'pending-additions' event package. In our example, after receiving the response from the relay (2), user A subscribes to the Pending Additions event package at the relay (5). This subscription keeps user A informed about the status of the permissions (e.g., granted or denied) the relay will obtain.
Клиенты могут использовать пакет событий SIP «Ожидающие дополнения», чтобы получать информацию о статусе запрошенных ими операций. То есть клиент будет проинформирован, когда операция (например, добавление URI получателя в логику трансляции ретранслятора) авторизована (и, следовательно, выполнена) или отклонена. Клиенты используют целевой URI преобразования SIP, которым манипулируют, для подписки на пакет событий «pending-additions». В нашем примере после получения ответа от ретранслятора (2) пользователь А подписывается на пакет событий Pending Additions на ретрансляторе (5). Эта подписка информирует пользователя А о статусе разрешений (e.g, предоставлено или отклонено), которые получит ретранслятор.
5.2.1. Relay's Behavior
5.2.1. Поведение реле
Relays SHOULD support the Pending Additions SIP event package specified in [RFC5362].
Реле СЛЕДУЕТ поддерживать пакет событий SIP «Ожидающие дополнения», указанный в [RFC5362].
5.3. Request for Permission
5.3. Запрос на разрешение
A relay requests permissions from potential recipients to add them to its translation logic using MESSAGE requests. In our example, on receiving the request to add user B to the translation logic of the relay (1), the relay generates a MESSAGE request (3) towards 'sip:B@example.com'. This MESSAGE request carries a permission document, which describes the translation that needs to be authorized and carries a set of URIs to be used by the recipient to grant or to deny the relay permission to perform that translation. Since user B is offline, the MESSAGE request will be buffered by user B's store- and-forward server. User B will later go online and authorize the translation by using one of those URIs, as described in Section 5.6. The MESSAGE request also carries a body part that contains the same information as the permission document but in a human-readable format.
Ретранслятор запрашивает разрешения у потенциальных получателей на добавление их в свою логику перевода с помощью запросов MESSAGE. В нашем примере, получив запрос на добавление пользователя B в логику трансляции реле (1), реле генерирует запрос MESSAGE (3) к 'sip:B@example.com'. Этот запрос MESSAGE содержит документ разрешения, который описывает перевод, который необходимо авторизовать, и содержит набор URI, которые получатель может использовать для предоставления или отказа в разрешении ретрансляции для выполнения этого перевода. Поскольку пользователь B находится в автономном режиме, запрос MESSAGE будет буферизован сервером промежуточного хранения пользователя B. Пользователь Б позже выйдет в Интернет и авторизует перевод, используя один из этих URI, как описано в разделе 5.6. Запрос MESSAGE также содержит часть тела, содержащую ту же информацию, что и документ разрешения, но в удобочитаемом формате.
When user B uses one of the URIs in the permission document to grant or deny permissions, the relay needs to make sure that it was actually user B using that URI, and not an attacker. The relay can use any of the methods described in Section 5.6 to authenticate the permission document.
Когда пользователь B использует один из URI в документе разрешений для предоставления или отказа в разрешениях, ретранслятору необходимо убедиться, что этот URI действительно использовал пользователь B, а не злоумышленник. Ретранслятор может использовать любой из методов, описанных в разделе 5.6, для аутентификации разрешительного документа.
5.3.1. Relay's Behavior
5.3.1. Поведение реле
Relays that implement this framework MUST obtain permissions from potential recipients before adding them to their translation logic. Relays request permissions from potential recipients using MESSAGE requests.
Ретрансляторы, реализующие эту структуру, ДОЛЖНЫ получать разрешения от потенциальных получателей, прежде чем добавлять их в свою логику трансляции. Ретрансляторы запрашивают разрешения у потенциальных получателей, используя запросы MESSAGE.
Section 5.6 describes the methods a relay can use to authenticate those recipients giving the relay permission to perform a particular translation. These methods are SIP identity [RFC4474], P-Asserted-Identity [RFC3325], a return routability test, or SIP digest. Relays that use the method consisting of a return routability test have to send their MESSAGE requests to a SIPS URI, as specified in Section 5.6. MESSAGE requests sent to request permissions MUST include a permission document and SHOULD include a human-readable part in their bodies. The human-readable part contains the same information as the permission document (but in a human-readable format), including the URIs to grant and deny permissions. User agents that do not understand permission documents can still process the request and display it in a sensible way to the user, as they would display any other instant message. This way, even if the user agent does not implement this framework, the (human) user will be able to manually click on the correct URI in order to grant or deny permissions. Этими методами являются идентификаторы SIP [RFC4474], P-Asserted-Identity [RFC3325], тест обратной маршрутизации или дайджест SIP. 5.4. Permission Document Structure
5.4. Структура разрешительного документа
A permission document is the representation (e.g., encoded in XML) of a permission. A permission document contains several pieces of data:
Документ разрешения — это представление (например, закодированное в XML) разрешения. Разрешительный документ содержит несколько фрагментов данных:
Identity of the Sender: A URI representing the identity of the sender for whom permissions are granted.
Идентификация отправителя: URI, представляющий личность отправителя, которому предоставлены разрешения.
Identity of the Original Recipient: A URI representing the identity of the original recipient, which is used as the input for the translation operation. This is also called the target URI.
Идентификация исходного получателя: URI, представляющий личность исходного получателя, который используется в качестве входных данных для операции перевода. Это также называется целевым URI.
Identity of the Final Recipient: A URI representing the result of the translation. The permission grants ability for the sender to send requests to the target URI and for a relay receiving those requests to forward them to this URI. This is also called the recipient URI.
Идентификация конечного получателя: URI, представляющий результат перевода. Разрешение предоставляет отправителю возможность отправлять запросы на целевой URI, а ретранслятору, получающему эти запросы, пересылать их на этот URI. Это также называется URI получателя.
URIs to Grant Permission: URIs that recipients can use to grant the relay permission to perform the translation described in the document. Relays MUST support the use of SIP and SIPS URIs in permission documents and MAY support the use of HTTP and HTTPS URIs.
URI для предоставления разрешения: URI, которые получатели могут использовать для предоставления разрешения ретрансляции для выполнения перевода, описанного в документе. Ретрансляторы ДОЛЖНЫ поддерживать использование URI SIP и SIPS в разрешительных документах и ​​МОГУТ поддерживать использование URI HTTP и HTTPS.
URIs to Deny Permission: URIs that recipients can use to deny the relay permission to perform the translation described in the document. Relays MUST support the use of SIP and SIPS URIs in permission documents and MAY support the use of HTTP and HTTPS URIs.
URI для отказа в разрешении: URI, которые получатели могут использовать для отказа в разрешении на ретрансляцию для выполнения перевода, описанного в документе. Ретрансляторы ДОЛЖНЫ поддерживать использование URI SIP и SIPS в разрешительных документах и ​​МОГУТ поддерживать использование URI HTTP и HTTPS.
Permission documents can contain wildcards. For example, a permission document can request permission for any relay to forward requests coming from a particular sender to a particular recipient. Such a permission document would apply to any target URI. That is, the field containing the identity of the original recipient would match any URI. However, the recipient URI MUST NOT be wildcarded.
Разрешительные документы могут содержать подстановочные знаки. Например, документ разрешения может запрашивать разрешение для любого ретранслятора на пересылку запросов, поступающих от конкретного отправителя к конкретному получателю. Такой разрешительный документ будет применяться к любому целевому URI. То есть поле, содержащее идентификационные данные исходного получателя, будет соответствовать любому URI. Однако URI получателя НЕ ДОЛЖЕН быть подстановочным.
Entities implementing this framework MUST support the format for permission documents defined in [RFC5361] and MAY support other formats.
Объекты, реализующие эту структуру, ДОЛЖНЫ поддерживать формат разрешительных документов, определенный в [RFC5361], и МОГУТ поддерживать другие форматы.

5.5. Уведомление о запросе разрешения

Получив запрос MESSAGE (3), сервер промежуточного хранения пользователя B сохраняет его, поскольку пользователь B в этот момент находится в автономном режиме. Когда пользователь B выходит в Интернет, пользователь B извлекает все запросы, сохраненные на его сервере промежуточного хранения (9).
5.6. Permission Grant
5.6. Предоставление разрешения
A recipient gives a relay permission to execute the translation described in a permission document by sending a SIP PUBLISH or an HTTP GET request to one of the URIs to grant permissions contained in the document. Similarly, a recipient denies a relay permission to execute the translation described in a permission document by sending a SIP PUBLISH or an HTTP GET request to one of the URIs to deny permissions contained in the document. Requests to grant or deny permissions contain an empty body.
Получатель предоставляет разрешение ретрансляции на выполнение перевода, описанного в документе разрешения, отправляя запрос SIP PUBLISH или HTTP GET на один из URI для предоставления разрешений, содержащихся в документе. Аналогично, получатель отказывает в разрешении ретрансляции на выполнение перевода, описанного в документе разрешения, отправляя запрос SIP PUBLISH или HTTP GET на один из URI, чтобы отклонить разрешения, содержащиеся в документе. Запросы на предоставление или отказ в разрешениях содержат пустое тело.
In our example, user B obtains the permission document (10) that was received earlier by its store-and-forward server in the MESSAGE request (3). User B authorizes the translation described in the permission document received by sending a PUBLISH request (11) to the SIP URI to grant permissions contained in the permission document.
В нашем примере пользователь B получает документ разрешения (10), который ранее был получен его сервером промежуточного хранения в запросе MESSAGE (3). Пользователь B авторизует перевод, описанный в полученном разрешительном документе, отправляя запрос PUBLISH (11) на SIP URI для предоставления разрешений, содержащихся в разрешительном документе.
5.6.1. Relay's Behavior
5.6.1. Поведение реле
Relays MUST ensure that the SIP PUBLISH or the HTTP GET request received was generated by the recipient of the translation and not by an attacker. Relays can use four methods to authenticate those requests: SIP identity, P-Asserted-Identity [RFC3325], a return routability test, or SIP digest. While return routability tests can be used to authenticate both SIP PUBLISH and HTTP GET requests, SIP identity, P-Asserted-Identity, and SIP digest can only be used to authenticate SIP PUBLISH requests. SIP digest can only be used to authenticate recipients that share a secret with the relay (e.g., recipients that are in the same domain as the relay).
Ретрансляторы ДОЛЖНЫ гарантировать, что полученный запрос SIP PUBLISH или HTTP GET был сгенерирован получателем перевода, а не злоумышленником. Ретрансляторы могут использовать четыре метода для аутентификации этих запросов: идентификатор SIP, P-Asserted-Identity [RFC3325], тест обратной маршрутизации или дайджест SIP. Хотя тесты обратной маршрутизации можно использовать для аутентификации запросов SIP PUBLISH и HTTP GET, идентификатор SIP, P-Asserted-Identity и дайджест SIP могут использоваться только для аутентификации запросов SIP PUBLISH. Дайджест SIP можно использовать только для аутентификации получателей, которые используют общий секрет с ретранслятором (например, получатели, находящиеся в том же домене, что и ретранслятор).
5.6.1.1. SIP Identity
5.6.1.1. SIP-идентификация
The SIP identity [RFC4474] mechanism can be used to authenticate the sender of a PUBLISH request. The relay MUST check that the originator of the PUBLISH request is the owner of the recipient URI in the permission document. Otherwise, the PUBLISH request SHOULD be responded with a 401 (Unauthorized) response and MUST NOT be processed further.
Механизм идентификации SIP [RFC4474] можно использовать для аутентификации отправителя запроса PUBLISH. Ретранслятор ДОЛЖЕН проверить, что отправитель запроса PUBLISH является владельцем URI получателя в разрешительном документе. В противном случае на запрос PUBLISH ДОЛЖЕН быть получен ответ 401 (Несанкционированный) и НЕ ДОЛЖНО обрабатываться дальше.
5.6.1.2. P-Asserted-Identity
5.6.1.2. P-Asserted-Identity
The P-Asserted-Identity [RFC3325] mechanism can also be used to authenticate the sender of a PUBLISH request. However, as discussed in [RFC3325], this mechanism is intended to be used only within networks of trusted SIP servers. That is, the use of this mechanism is only applicable inside an administrative domain with previously agreed-upon policies. The relay MUST check that the originator of the PUBLISH request is the owner of the recipient URI in the permission document. Otherwise, the PUBLISH request SHOULD be responded with a 401 (Unauthorized) response and MUST NOT be processed further.
Механизм P-Asserted-Identity [RFC3325] также можно использовать для аутентификации отправителя запроса PUBLISH. Однако, как обсуждалось в [RFC3325], этот механизм предназначен для использования только в сетях доверенных SIP-серверов. То есть использование этого механизма применимо только внутри административного домена с заранее согласованной политикой. Ретранслятор ДОЛЖЕН проверить, что отправитель запроса PUBLISH является владельцем URI получателя в разрешительном документе. В противном случае на запрос PUBLISH ДОЛЖЕН быть получен ответ 401 (Несанкционированный) и НЕ ДОЛЖНО обрабатываться дальше.
5.6.1.3. Return Routability
5.6.1.3. Обратная маршрутизация
SIP identity provides a good authentication mechanism for incoming PUBLISH requests. Nevertheless, SIP identity is not widely available on the public Internet yet. That is why an authentication mechanism that can already be used at this point is needed.
Идентификация SIP обеспечивает хороший механизм аутентификации для входящих запросов PUBLISH. Тем не менее, SIP-идентификация пока не получила широкого распространения в общедоступном Интернете. Вот почему необходим механизм аутентификации, который уже можно использовать на этом этапе.
Return routability tests do not provide the same level of security as SIP identity, but they provide a better-than-nothing security level in architectures where the SIP identity mechanism is not available (e.g., the current Internet). The relay generates an unguessable URI (i.e., with a cryptographically random user part) and places it in the permission document in the MESSAGE request (3). The recipient needs to send a SIP PUBLISH request or an HTTP GET request to that URI. Any incoming request sent to that URI SHOULD be considered authenticated by the relay. Note that the return routability method is the only one that allows the use of HTTP URIs in permission documents. The other methods require the use of SIP URIs.
Тесты обратной маршрутизации не обеспечивают такой же уровень безопасности, как идентификация SIP, но они обеспечивают уровень безопасности «лучше, чем ничего» в архитектурах, где механизм идентификации SIP недоступен (например, текущий Интернет). Ретранслятор генерирует неугадываемый URI (то есть, с криптографически случайной пользовательской частью) и помещает его в документ разрешения в запросе MESSAGE (3). Получателю необходимо отправить запрос SIP PUBLISH или запрос HTTP GET на этот URI. Любой входящий запрос, отправленный на этот URI, ДОЛЖЕН считаться аутентифицированным ретранслятором. Обратите внимание, что метод обратной маршрутизации — единственный, который позволяет использовать URI HTTP в разрешительных документах. Другие методы требуют использования SIP URI.
Relays using a return routability test to perform this authentication MUST send the MESSAGE request with the permission document to a SIPS URI. This ensures that attackers do not get access to the (unguessable) URI. Thus, the only user able to use the (unguessable) URI is the receiver of the MESSAGE request. Similarly, permission documents sent by relays using a return routability test MUST only contain secure URIs (i.e., SIPS and HTTPS) to grant and deny permissions. A part of these URIs (e.g., the user part of a SIPS URI) MUST be cryptographically random with at least 32 bits of randomness.
Реле, использующие тест обратной маршрутизации для выполнения этой аутентификации, ДОЛЖНЫ отправить запрос MESSAGE с документом разрешения на URI SIPS. Это гарантирует, что злоумышленники не получат доступ к (неугаданному) URI. Таким образом, единственным пользователем, который может использовать (неопределимый) URI, является получатель запроса MESSAGE. Аналогичным образом, документы разрешений, отправляемые ретрансляторами с использованием теста обратной маршрутизации, ДОЛЖНЫ содержать только безопасные URI (то есть, SIPS и HTTPS) для предоставления и отказа в разрешениях. Часть этих URI (например, пользовательская часть SIPS URI) ДОЛЖНА быть криптографически случайной и содержать не менее 32 бит случайности.
Relays can transition from return routability tests to SIP identity by simply requiring the use of SIP identity for incoming PUBLISH requests. That is, such a relay would reject PUBLISH requests that did not use SIP identity.
Ретрансляторы могут переходить от тестов обратной маршрутизации к идентификации SIP, просто требуя использования идентификации SIP для входящих запросов PUBLISH. То есть такой ретранслятор будет отклонять запросы PUBLISH, которые не используют идентификатор SIP.
5.6.1.4. SIP Digest
5.6.1.4. SIP-дайджест
The SIP digest mechanism can be used to authenticate the sender of a PUBLISH request as long as that sender shares a secret with the relay. The relay MUST check that the originator of the PUBLISH request is the owner of the recipient URI in the permission document. Otherwise, the PUBLISH request SHOULD be responded with a 401 (Unauthorized) response and MUST NOT be processed further.
Механизм дайджеста SIP можно использовать для аутентификации отправителя запроса PUBLISH, если этот отправитель разделяет секрет с ретранслятором. Ретранслятор ДОЛЖЕН проверить, что отправитель запроса PUBLISH является владельцем URI получателя в разрешительном документе. В противном случае на запрос PUBLISH ДОЛЖЕН быть получен ответ 401 (Несанкционированный) и НЕ ДОЛЖНО обрабатываться дальше.
5.7. Permission Granted Notification
5.7. Уведомление о предоставлении разрешения
On receiving the PUBLISH request (11), the relay sends a NOTIFY request (13) to inform user A that the permission for the translation has been received and that the translation logic at the relay has been updated. That is, 'sip:B@example.com' has been added as a recipient URI.
При получении запроса PUBLISH (11) ретранслятор отправляет запрос NOTIFY (13), чтобы сообщить пользователю A, что разрешение на трансляцию получено и что логика трансляции на ретрансляторе обновлена. То есть «sip:B@example.com» был добавлен в качестве URI получателя.
5.8. Permission Revocation
5.8. Отзыв разрешения
At any time, if a recipient wants to revoke any permission, it uses the URI it received in the permission document to deny the permissions it previously granted. If a recipient loses this URI for some reason, it needs to wait until it receives a new request produced by the translation. Such a request will contain a Trigger- Consent header field with a URI. That Trigger-Consent header field will have a target-uri header field parameter identifying the target URI of the translation. The recipient needs to send a PUBLISH request with an empty body to the URI in the Trigger-Consent header field in order to receive a MESSAGE request from the relay. Such a MESSAGE request will contain a permission document with a URI to revoke the permission that was previously granted.
В любой момент, если получатель хочет отозвать какое-либо разрешение, он использует URI, полученный в документе разрешения, для отказа в ранее предоставленных разрешениях. Если получатель по какой-то причине потеряет этот URI, ему придется подождать, пока он не получит новый запрос, созданный в результате перевода. Такой запрос будет содержать поле заголовка Trigger-Consent с URI. Это поле заголовка Trigger-Consent будет иметь параметр поля заголовка target-uri, идентифицирующий целевой URI перевода. Получателю необходимо отправить запрос PUBLISH с пустым телом на URI в поле заголовка Trigger-Consent, чтобы получить запрос MESSAGE от ретранслятора. Такой запрос MESSAGE будет содержать документ разрешения с URI для отзыва ранее предоставленного разрешения.

The user rejects an incoming INVITE (1) request, which contains a Trigger-Consent header field. Using the URI in that header field, the user sends a PUBLISH request (4) to the relay. On receiving the PUBLISH request (4), the relay generates a MESSAGE request (6) towards the user. Finally, the user revokes the permissions by sending a PUBLISH request (8) to the relay.

5.9. Request-Contained URI Lists
5.9. Request-Contained Списки URI
In the scenarios described so far, a user adds recipient URIs to the translation logic of a relay. However, the relay does not perform translations towards those recipient URIs until permissions are obtained.
В описанных выше сценариях пользователь добавляет URI получателя в логику трансляции ретранслятора. Однако ретранслятор не выполняет преобразование этих URI получателей до тех пор, пока не будут получены разрешения.
URI-list services using request-contained URI lists are a special case because the selection of recipient URIs is performed at the same time as the communication attempt. A user places a set of recipient URIs in a request and sends it to a relay so that the relay sends a similar request to all those recipient URIs.
Службы URI-list с использованием списков URI, содержащихся в запросе, являются особым случаем, поскольку выбор URI получателя выполняется одновременно с попыткой связи. Пользователь помещает набор URI получателей в запрос и отправляет его ретранслятору, чтобы ретранслятор отправлял аналогичный запрос всем этим URI получателя.
Relays implementing this consent framework and providing request- contained URI-list services behave in a slightly different way than the relays described so far. This type of relay also maintains a list of recipient URIs for which permissions have been received. Clients also manipulate this list using a manipulation mechanism (e.g., XCAP). Nevertheless, this list does not represent the recipient URIs of every translation performed by the relay. This list just represents all the recipient URIs for which permissions have been received -- that is, the set of URIs that will be accepted if a request containing a URI-list arrives to the relay. This set of URIs is a superset of the recipient URIs of any particular translation the relay performs.
Ретрансляторы, реализующие эту структуру согласия и предоставляющие содержащие запрос URI-list услуги, ведут себя немного иначе, чем ретрансляторы, описанные до сих пор. Этот тип ретранслятора также поддерживает список URI получателей, для которых были получены разрешения. Клиенты также манипулируют этим списком, используя механизм манипуляции (например, XCAP). Тем не менее, этот список не представляет URI получателя каждого перевода, выполненного ретранслятором. Этот список просто представляет все URI получателей, для которых были получены разрешения, то есть набор URI, которые будут приняты, если на ретранслятор поступит запрос, содержащий URI-list. Этот набор URI является расширенным набором URI получателя любого конкретного перевода, выполняемого ретранслятором.

5.10. Registrations
5.10. Регистрации
Even though the example used to specify this framework has been a URI-list service, this framework applies to any type of translation (i.e., not only to URI-list services). Registrations are a different type of translations that deserve discussion.
Несмотря на то, что примером, использованным для указания этой платформы, была служба URI-list, эта структура применима к любому типу перевода (то есть, а не только к службам URI-list). Регистрации — это другой вид переводов, заслуживающий обсуждения.
Registrations are a special type of translations. The user registering has a trust relationship with the registrar in its home domain. This is not the case when a user gives any type of permissions to a relay in a different domain.
Регистрации – это особый вид переводов. Регистрирующийся пользователь имеет доверительные отношения с регистратором своего домашнего домена. Это не тот случай, когда пользователь предоставляет какие-либо разрешения ретранслятору в другом домене.
Traditionally, REGISTER transactions have performed two operations at the same time: setting up a translation and authorizing the use of that translation. For example, a user registering its current contact URI is giving permission to the registrar to forward traffic sent to the user's AoR (Address of Record) to the registered contact URI. This works fine when the entity registering is the same as the one that will be receiving traffic at a later point (e.g., the entity receives traffic over the same connection used for the registration as described in [OUTBOUND]). However, this schema creates some potential attacks that relate to third-party registrations.
Традиционно транзакции REGISTER выполняют две операции одновременно: настройку перевода и авторизацию использования этого перевода. Например, пользователь, регистрирующий свой текущий URI контакта, дает разрешение регистратору пересылать трафик, отправленный в AoR (адрес записи) пользователя, на зарегистрированный URI контакта. Это работает нормально, если регистрируемый объект совпадает с тем, который будет получать трафик в более поздней точке (например, объект получает трафик через то же соединение, которое использовалось для регистрации, как описано в [OUTBOUND]). Однако эта схема создает некоторые потенциальные атаки, связанные с регистрацией третьих лиц.
An attacker binds, via a registration, his or her AoR with the contact URI of a victim. Now the victim will receive unsolicited traffic that was originally addressed to the attacker.
Злоумышленник посредством регистрации связывает свой AoR с контактным URI жертвы. Теперь жертва будет получать нежелательный трафик, который изначально был адресован злоумышленнику.

Разрешительные документы, создаваемые регистраторами, обычно носят очень общий характер. Пользователям, которые хотят определить, как обрабатываются входящие запросы, с более высокой степенью детализации (например, запросы от пользователя А принимаются только с 9:00 до 11:00), придется использовать другие механизмы, такие как язык обработки вызовов (CPL) [RFC3880]. 5.11. Relays Generating Traffic towards Recipients
5.11. Реле, генерирующие трафик для получателей
Relays generating traffic towards recipients need to make sure that those recipients can revoke the permissions they gave at any time. The Trigger-Consent helps achieve this.
Ретрансляторы, генерирующие трафик к получателям, должны гарантировать, что эти получатели могут в любое время отозвать предоставленные ими разрешения. Trigger-Consent помогает добиться этого.
5.11.1. Relay's Behavior
5.11.1. Поведение реле
A relay executing a translation that involves sending a request to a URI from which permissions were obtained previously SHOULD add a Trigger-Consent header field to the request. The URI in the Trigger-Consent header field MUST have a target-uri header field parameter identifying the target URI of the translation.
Ретранслятор, выполняющий трансляцию, которая включает отправку запроса на URI, от которого ранее были получены разрешения, ДОЛЖЕН добавить к запросу поле заголовка Trigger-Consent. URI в поле заголовка Trigger-Consent ДОЛЖЕН иметь параметр поля заголовка target-uri, идентифицирующий целевой URI перевода.
On receiving a PUBLISH request addressed to the URI that a relay previously placed in a Trigger-Consent header field, the relay SHOULD send a MESSAGE request to the corresponding recipient URI with a permission document. Therefore, the relay needs to be able to correlate the URI it places in the Trigger-Consent header field with the recipient URI of the translation.
При получении запроса PUBLISH, адресованного URI, который ретранслятор ранее поместил в поле заголовка Trigger-Consent, ретранслятор ДОЛЖЕН отправить запрос MESSAGE соответствующему URI получателя с документом разрешения. Следовательно, ретранслятору необходимо иметь возможность сопоставлять URI, который он помещает в поле заголовка Trigger-Consent, с URI получателя перевода.

7. Security Considerations
7. Вопросы безопасности
Security has been discussed throughout the whole document. However, there are some issues that deserve special attention.
Безопасность обсуждается на протяжении всего документа. Однако есть некоторые вопросы, заслуживающие особого внимания.
Relays generally implement several security mechanisms that relate to client authentication and authorization. Clients are typically authenticated before they can manipulate a relay's translation logic. Additionally, clients are typically also authenticated and sometimes need to perform SPAM prevention tasks [RFC5039] when they send traffic to a relay. It is important that relays implement these types of security mechanisms. However, they fall out of the scope of this framework. Even with these mechanisms in place, there is still a need for relays to implement this framework because the use of these mechanisms does not prevent authorized clients to add recipients to a translation without their consent. Consequently, relays performing translations MUST implement this framework. Note that, as indicated previously, user agents using the same connection to register and to receive traffic from the registrar, as described in [OUTBOUND], do not need to use this framework. Therefore, a registrar that did not accept third-party registrations would not need to implement this framework.
Ретрансляторы обычно реализуют несколько механизмов безопасности, связанных с аутентификацией и авторизацией клиента. Клиенты обычно аутентифицируются, прежде чем они смогут манипулировать логикой трансляции ретранслятора. Кроме того, клиенты обычно также проходят проверку подлинности, и иногда им необходимо выполнять задачи по предотвращению спама [RFC5039] при отправке трафика на ретранслятор. Важно, чтобы реле реализовывали эти типы механизмов безопасности. Однако они выходят за рамки этой рамки. Даже при наличии этих механизмов все еще существует потребность в ретрансляторах для реализации этой структуры, поскольку использование этих механизмов не мешает авторизованным клиентам добавлять получателей к переводу без их согласия. Следовательно, ретрансляторы, выполняющие трансляцию, ДОЛЖНЫ реализовать эту структуру. Обратите внимание, что, как указывалось ранее, пользовательским агентам, использующим одно и то же соединение для регистрации и получения трафика от регистратора, как описано в [OUTBOUND], не требуется использовать эту структуру. Таким образом, регистратору, который не принимает регистрации третьих лиц, не потребуется внедрять эту структуру.
As pointed out in Section 5.6.1.3, when return routability tests are used to authenticate recipients granting or denying permissions, the URIs used to grant or deny permissions need to be protected from attackers. SIPS URIs provide a good tool to meet this requirement, as described in [RFC5361]. When store-and-forward servers are used, the interface between a user agent and its store-and-forward server is frequently not based on SIP. In such a case, SIPS cannot be used to secure those URIs. Implementations of store-and-forward servers MUST provide a mechanism for delivering encrypted and integrity- protected messages to their user agents.
Как указано в разделе 5.6.1.3, когда тесты обратной маршрутизации используются для аутентификации получателей, предоставляющих или запрещающих разрешения, URI, используемые для предоставления или отказа в разрешениях, должны быть защищены от злоумышленников. SIPS URI предоставляют хороший инструмент для удовлетворения этого требования, как описано в [RFC5361]. При использовании серверов с промежуточным хранением интерфейс между пользовательским агентом и его сервером с промежуточным хранением часто не основан на SIP. В таком случае SIPS нельзя использовать для защиты этих URI. Реализации серверов с промежуточным хранением ДОЛЖНЫ обеспечивать механизм доставки зашифрованных и защищенных целостности сообщений своим пользовательским агентам.
The information provided by the Pending Additions event package can be sensitive. For this reason, as described in [RFC5362], relays need to use strong means for authentication and information confidentiality. SIPS URIs are a good mechanism to meet this requirement.
Информация, предоставляемая пакетом событий «Ожидающие дополнения», может быть конфиденциальной. По этой причине, как описано в [RFC5362], ретрансляторы должны использовать надежные средства аутентификации и конфиденциальности информации. SIPS URI — хороший механизм для удовлетворения этого требования.
Permission documents can reveal sensitive information. Attackers may attempt to modify them in order to have clients grant or deny permissions different from the ones they think they are granting or denying. For this reason, it is RECOMMENDED that relays use strong means for information integrity protection and confidentiality when sending permission documents to clients. The mechanism used for conveying information to clients SHOULD ensure the integrity and confidentially of the information. In order to achieve these, an end-to-end SIP encryption mechanism, such as S/MIME, as described in [RFC3261], SHOULD be used.
Разрешительные документы могут содержать конфиденциальную информацию. Злоумышленники могут попытаться изменить их, чтобы клиенты предоставляли или запрещали разрешения, отличные от тех, которые, по их мнению, они предоставляют или запрещают. По этой причине РЕКОМЕНДУЕТСЯ, чтобы ретрансляторы использовали надежные средства защиты целостности и конфиденциальности информации при отправке разрешительных документов клиентам. Механизм, используемый для передачи информации клиентам, ДОЛЖЕН обеспечивать целостность и конфиденциальность информации. Для достижения этих целей СЛЕДУЕТ использовать механизм сквозного шифрования SIP, такой как S/MIME, как описано в [RFC3261].
If strong end-to-end security means (such as above) are not available, it is RECOMMENDED that hop-by-hop security based on TLS and SIPS URIs, as described in [RFC3261], is used.
Если надежные средства сквозной безопасности (например, описанные выше) недоступны, РЕКОМЕНДУЕТСЯ использовать пошаговую безопасность на основе URI TLS и SIPS, как описано в [RFC3261].
