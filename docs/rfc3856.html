Abstract
Аннотация
This document describes the usage of the Session Initiation Protocol (SIP) for subscriptions and notifications of presence. Presence is defined as the willingness and ability of a user to communicate with other users on the network. Historically, presence has been limited to "on-line" and "off-line" indicators; the notion of presence here is broader. Subscriptions and notifications of presence are supported by defining an event package within the general SIP event notification framework. This protocol is also compliant with the Common Presence Profile (CPP) framework.
В настоящем документе описывается использование протокола инициирования сессий (SIP) для подписок на присутствие и уведомлений о присутствии. Присутствие определяется как готовность и способность пользователя общаться с другими пользователями в сети. Исторически присутствие ограничивалось индикаторами «в сети» и «не в сети»; понятие присутствия здесь шире. Подписки на присутствие и уведомления о нём поддерживаются за счёт определения пакета событий в рамках общего механизма уведомления о событиях SIP. Этот протокол также соответствует требованиям механизма Common Presence Profile (CPP).
1. Introduction
1. Введение
Presence, also known as presence information, conveys the ability and willingness of a user to communicate across a set of devices. RFC 2778 [10] defines a model and terminology for describing systems that provide presence information. In that model, a presence service is a system that accepts, stores, and distributes presence information to interested parties, called watchers. A presence protocol is a protocol for providing a presence service over the Internet or any IP network.
Присутствие, также называемое информацией о присутствии, передаёт способность и готовность пользователя общаться через набор устройств. RFC 2778 [10] определяет модель и терминологию для описания систем, предоставляющих информацию о присутствии. В этой модели служба присутствия — это система, которая принимает, хранит и распространяет информацию о присутствии среди заинтересованных сторон, называемых наблюдателями. Протокол присутствия — это протокол предоставления службы присутствия через Интернет или любую IP-сеть.
This document proposes the usage of the Session Initiation Protocol (SIP) [1] as a presence protocol. This is accomplished through a concrete instantiation of the general event notification framework defined for SIP [2], and as such, makes use of the SUBSCRIBE and NOTIFY methods defined there. Specifically, this document defines an event package, as described in RFC 3265 [2]. SIP is particularly well suited as a presence protocol. SIP location services already contain presence information, in the form of registrations. Furthermore, SIP networks are capable of routing requests from any user on the network to the server that holds the registration state for a user. As this state is a key component of user presence, those SIP networks can allow SUBSCRIBE requests to be routed to the same server. This means that SIP networks can be reused to establish global connectivity for presence subscriptions and notifications.
В настоящем документе предлагается использовать протокол инициирования сессий (SIP) [1] в качестве протокола присутствия. Это достигается за счёт конкретного воплощения общего механизма уведомления о событиях, определённого для SIP [2], и, соответственно, использует методы SUBSCRIBE и NOTIFY, определённые там. В частности, в настоящем документе определяется пакет событий, как описано в RFC 3265 [2]. SIP особенно хорошо подходит в качестве протокола присутствия. Службы определения местоположения SIP уже содержат информацию о присутствии в виде регистраций. Кроме того, сети SIP способны маршрутизировать запросы от любого пользователя сети к серверу, который хранит состояние регистрации пользователя. Поскольку это состояние является ключевым компонентом присутствия пользователя, такие сети SIP позволяют маршрутизировать запросы SUBSCRIBE к тому же серверу. Это означает, что сети SIP можно повторно использовать для установления глобальной связности для подписок на присутствие и уведомлений о нём.
This event package is based on the concept of a presence agent, which is a new logical entity that is capable of accepting subscriptions, storing subscription state, and generating notifications when there are changes in presence. The entity is defined as a logical one, since it is generally co-resident with another entity.
Этот пакет событий основан на концепции агента присутствия — новой логической сущности, способной принимать подписки, хранить состояние подписки и формировать уведомления при изменениях присутствия. Эта сущность определяется как логическая, поскольку обычно она сосуществует с другой сущностью.
This event package is also compliant with the Common Presence Profile (CPP) framework that has been defined in [3]. This allows SIP for presence to easily interwork with other presence systems compliant to CPP.
Этот пакет событий также соответствует требованиям механизма Common Presence Profile (CPP), определённого в [3]. Это позволяет легко обеспечить взаимодействие SIP для присутствия с другими системами присутствия, соответствующими CPP.

4. Overview of Operation
4. Обзор работы
In this section, we present an overview of the operation of this event package. The overview describes behavior that is documented in part here, in part within the SIP event framework [2], and in part in the SIP specification [1], in order to provide clarity on this package for readers only casually familiar with those specifications. However, the detailed semantics of this package require the reader to be familiar with SIP events and the SIP specification itself.
В этом разделе представлен обзор работы данного пакета событий. Обзор описывает поведение, документированное частично здесь, частично в механизме событий SIP [2], а частично в спецификации SIP [1], чтобы прояснить этот пакет для читателей, лишь поверхностно знакомых с указанными спецификациями. Однако подробная семантика этого пакета требует от читателя знания событий SIP и самой спецификации SIP.
When an entity, the subscriber, wishes to learn about presence information from some user, it creates a SUBSCRIBE request. This request identifies the desired presentity in the Request-URI, using a SIP URI, SIPS URI [1] or a presence (pres) URI [3]. The SUBSCRIBE request is carried along SIP proxies as any other SIP request would be. In most cases, it eventually arrives at a presence server, which can either generate a response to the request (in which case it acts as the presence agent for the presentity), or proxy it on to an edge presence server. If the edge presence server handles the subscription, it is acting as the presence agent for the presentity. The decision at a presence server about whether to proxy or terminate the SUBSCRIBE is a local matter; however, we describe one way to effect such a configuration, using REGISTER. The presence agent (whether in the presence server or edge presence server) first authenticates the subscription, then authorizes it. The means for authorization are outside the scope of this protocol, and we expect that many mechanisms will be used. If authorized, a 200 OK response is returned. If authorization could not be obtained at this time, the subscription is considered "pending", and a 202 response is returned. In both cases, the PA sends an immediate NOTIFY message containing the state of the presentity and of the subscription.
Когда некоторая сущность — подписчик — желает получить информацию о присутствии некоторого пользователя, она создаёт запрос SUBSCRIBE. Этот запрос идентифицирует нужного презентити в Request-URI с помощью SIP URI, SIPS URI [1] или URI присутствия (pres) [3]. Запрос SUBSCRIBE передаётся через прокси SIP так же, как любой другой запрос SIP. В большинстве случаев он в конечном счёте поступает на сервер присутствия, который может либо сформировать ответ на запрос (в этом случае он действует как агент присутствия для презентити), либо проксировать его на периферийный сервер присутствия. Если периферийный сервер присутствия обрабатывает подписку, он действует как агент присутствия для презентити. Решение на сервере присутствия о том, проксировать или завершать SUBSCRIBE, является локальным вопросом; однако мы описываем один способ реализации такой конфигурации с использованием REGISTER. Агент присутствия (находится ли он на сервере присутствия или на периферийном сервере присутствия) сначала аутентифицирует подписку, затем авторизует её. Средства авторизации выходят за рамки данного протокола, и мы ожидаем, что будет использоваться множество механизмов. Если авторизация получена, возвращается ответ 200 OK. Если авторизацию в этот момент получить не удалось, подписка считается «ожидающей» и возвращается ответ 202. В обоих случаях PA отправляет немедленное сообщение NOTIFY, содержащее состояние презентити и состояние подписки.
The presentity state may be bogus in the case of a pending subscription, indicating offline no matter what the actual state of the presentity, for example. This is to protect the privacy of the presentity, who may not want to reveal that they have not provided authorization for the subscriber. As the state of the presentity changes, the PA generates NOTIFYs containing those state changes to all subscribers with authorized subscriptions. Changes in the state of the subscription itself can also trigger NOTIFY requests; that state is carried in the Subscription-State header field of the NOTIFY, and would typically indicate whether the subscription is active or pending.
Состояние презентити может быть недостоверным в случае ожидающей подписки: например, оно может указывать на состояние «офлайн» независимо от того, каково на самом деле состояние презентити. Это делается для защиты конфиденциальности презентити, который может не желать раскрывать, что не дал разрешения подписчику. Когда состояние презентити меняется, агент присутствия (PA) формирует уведомления NOTIFY, содержащие эти изменения, всем подписчикам, чьи подписки авторизованы. Изменения самого состояния подписки также могут вызывать запросы NOTIFY; это состояние передаётся в поле заголовка Subscription-State уведомления NOTIFY и обычно указывает, активна подписка или ожидает подтверждения.
The SUBSCRIBE message establishes a "dialog" with the presence agent. A dialog is defined in RFC 3261 [1], and it represents the SIP state between a pair of entities to facilitate peer-to-peer message exchanges. This state includes the sequence numbers for messages in both directions (SUBSCRIBE from the subscriber, NOTIFY from the presence agent), in addition to a route set and remote target URI. The route set is a list of SIP (or SIPS) URIs which identify SIP proxy servers that are to be visited along the path of SUBSCRIBE refreshes or NOTIFY requests. The remote target URI is the SIP or SIPS URI that identifies the target of the message - the subscriber, in the case of NOTIFY, or the presence agent, in the case of a SUBSCRIBE refresh.
Сообщение SUBSCRIBE устанавливает «диалог» с агентом присутствия. Диалог определён в RFC 3261 [1] и представляет состояние SIP между парой сущностей, облегчающее обмен сообщениями между равноправными узлами. Это состояние включает порядковые номера сообщений в обоих направлениях (SUBSCRIBE от подписчика, NOTIFY от агента присутствия), а также набор маршрутов и URI удалённой цели. Набор маршрутов — это список URI SIP (или SIPS), которые идентифицируют прокси-серверы SIP, подлежащие посещению на пути обновлений SUBSCRIBE или запросов NOTIFY. URI удалённой цели — это URI SIP или SIPS, идентифицирующий цель сообщения: подписчика в случае NOTIFY или агента присутствия в случае обновления SUBSCRIBE.
SIP provides a procedure called record-routing that allows for proxy servers to request to be on the path of NOTIFY messages and SUBSCRIBE refreshes. This is accomplished by inserting a URI into the Record-Route header field in the initial SUBSCRIBE request.
SIP предоставляет процедуру, называемую маршрутизацией с записью маршрута (record-routing), которая позволяет прокси-серверам запросить включение в путь сообщений NOTIFY и обновлений SUBSCRIBE. Это достигается вставкой URI в поле заголовка Record-Route первоначального запроса SUBSCRIBE.
The subscription persists for a duration that is negotiated as part of the initial SUBSCRIBE. The subscriber will need to refresh the subscription before its expiration, if they wish to retain the subscription. This is accomplished by sending a SUBSCRIBE refresh within the same dialog established by the initial SUBSCRIBE. This SUBSCRIBE is nearly identical to the initial one, but contains a tag in the To header field, a higher CSeq header field value, and possibly a set of Route header field values that identify the path of proxies the request is to take. The subscriber can terminate the subscription by sending a SUBSCRIBE, within the dialog, with an Expires header field (which indicates duration of the subscription) value of zero. This causes an immediate termination of the subscription. A NOTIFY request is then generated by the presence agent with the most recent state. In fact, behavior of the presence agent for handling a SUBSCRIBE request with Expires of zero is no different than for any other expiration value; pending or authorized SUBSCRIBE requests result in a triggered NOTIFY with the current presentity and subscription state.
Подписка сохраняется в течение срока, согласованного при первоначальном SUBSCRIBE. Подписчику потребуется обновить подписку до её истечения, если он желает сохранить подписку. Это достигается отправкой обновления SUBSCRIBE в том же диалоге, установленном первоначальным SUBSCRIBE. Этот SUBSCRIBE почти идентичен первоначальному, но содержит тег в поле заголовка To, большее значение поля заголовка CSeq и, возможно, набор значений полей заголовка Route, идентифицирующих путь прокси, который должен пройти запрос. Подписчик может завершить подписку, отправив в рамках диалога SUBSCRIBE со значением поля заголовка Expires (указывающего продолжительность подписки), равным нулю. Это приводит к немедленному завершению подписки. После этого агент присутствия формирует запрос NOTIFY с самым последним состоянием. Фактически поведение агента присутствия при обработке запроса SUBSCRIBE с Expires, равным нулю, ничем не отличается от поведения при любом другом значении истечения: ожидающие или авторизованные запросы SUBSCRIBE приводят к сформированному NOTIFY с текущим состоянием презентити и подписки.
The presence agent can terminate the subscription at any time. To do so, it sends a NOTIFY request with a Subscription-State header field indicating that the subscription has been terminated. A reason parameter can be supplied which provides the reason.
Агент присутствия может завершить подписку в любой момент. Для этого он отправляет запрос NOTIFY с полем заголовка Subscription-State, указывающим, что подписка завершена. Может быть указан параметр reason, дающий причину.
It is also possible to fetch the current presence state, resulting in a one-time notification containing the current state. This is accomplished by sending a SUBSCRIBE request with an immediate expiration.
Также возможно получить текущее состояние присутствия, что приводит к однократному уведомлению, содержащему текущее состояние. Это достигается отправкой запроса SUBSCRIBE с немедленным истечением срока.
5. Usage of Presence URIs
5. Использование URI присутствия
A presentity is identified in the most general way through a presence URI [3], which is of the form pres:user@domain. These URIs are resolved to protocol specific URIs, such as the SIP or SIPS URI, through domain-specific mapping policies maintained on a server.
Презентити идентифицируется наиболее общим образом посредством URI присутствия [3], имеющего вид pres:user@domain. Эти URI разрешаются в URI, специфичные для протокола, например SIP или SIPS URI, с помощью специфичных для домена правил отображения, поддерживаемых на сервере.
It is very possible that a user will have both a SIP (and/or SIPS) URI and a pres URI to identify both themself and other users. This leads to questions about how these URI relate and which are to be used.
Вполне возможно, что пользователь будет иметь как SIP (и/или SIPS) URI, так и pres URI для идентификации и себя, и других пользователей. Отсюда возникают вопросы о том, как эти URI соотносятся и какие следует использовать.
In some instances, a user starts with one URI format, such as the pres URI, and learns a URI in a different format through some protocol means. As an example, a SUBSCRIBE request sent to a pres URI will result in learning a SIP or SIPS URI for the presentity from the Contact header field of the 200 OK to the SUBSCRIBE request. As another example, a DNS mechanism might be defined that would allow lookup of a pres URI to obtain a SIP or SIPS URI. In cases where one URI is learned from another through protocol means, those means will often provide some kind of scoping that limit the lifetime of the learned URI. DNS, for example, provides a TTL which would limit the scope of the URI. These scopes are very useful to avoid stale or conflicting URIs for identifying the same resource. To ensure that a user can always determine whether a learned URI is still valid, it is RECOMMENDED that systems which provide lookup services for presence URIs have some kind of scoping mechanism. If a subscriber is only aware of the protocol-independent pres URI for a presentity, it follows the procedures defined in [5]. These procedures will result in the placement of the pres URI in the Request-URI of the SIP request, followed by the usage of the DNS procedures defined in [5] to determine the host to send the SIP request to.
В некоторых случаях пользователь начинает с одного формата URI, например pres URI, и узнаёт URI в другом формате посредством некоторого протокольного механизма. Например, запрос SUBSCRIBE, отправленный на pres URI, приведёт к получению SIP или SIPS URI для презентити из поля заголовка Contact ответа 200 OK на запрос SUBSCRIBE. В качестве другого примера может быть определён механизм DNS, позволяющий выполнить поиск по pres URI для получения SIP или SIPS URI. В случаях, когда один URI узнаётся из другого посредством протокольных механизмов, эти механизмы часто обеспечивают некоторую область действия, ограничивающую время жизни полученного URI. Например, DNS предоставляет TTL, который ограничивает область действия URI. Такие области действия очень полезны для того, чтобы избежать устаревших или конфликтующих URI при идентификации одного и того же ресурса. Чтобы пользователь всегда мог определить, действителен ли полученный URI, РЕКОМЕНДУЕТСЯ, чтобы системы, предоставляющие службы поиска для URI присутствия, имели некоторый механизм ограничения области действия. Если подписчик знает только не зависящий от протокола pres URI для презентити, он следует процедурам, определённым в [5]. Эти процедуры приведут к помещению pres URI в Request-URI запроса SIP с последующим использованием процедур DNS, определённых в [5], для определения хоста, на который следует отправить запрос SIP.
Of course, a local outbound proxy may alternatively be used, as specified in RFC 3261 [1]. If the subscriber is aware of both the protocol-independent pres URI and the SIP or SIPS URI for the same presentity, and both are valid (as discussed above) it SHOULD use the pres URI format. Of course, if the subscriber only knows the SIP URI for the presentity, that URI is used, and standard RFC 3261 processing will occur. When the pres URI is used, any proxies along the path of the SUBSCRIBE request which do not understand the URI scheme will reject the request. As such, it is expected that many systems will be initially deployed that only provide users with a SIP URI.
Разумеется, вместо этого можно использовать локальный исходящий прокси, как указано в RFC 3261 [1]. Если подписчик знает и не зависящий от протокола URI pres, и URI SIP или SIPS для одного и того же презентити, и оба действительны (как обсуждалось выше), ему СЛЕДУЕТ использовать формат URI pres. Разумеется, если подписчику известен только SIP URI презентити, используется этот URI и выполняется стандартная обработка по RFC 3261. Когда используется URI pres, любые прокси на пути запроса SUBSCRIBE, не понимающие эту схему URI, отклонят запрос. Поэтому ожидается, что многие системы изначально будут развёрнуты так, что пользователям предоставляется только SIP URI.
SUBSCRIBE messages also contain logical identifiers that define the originator and recipient of the subscription (the To and From header fields). These headers can take either a pres or SIP URI. When the subscriber is aware of both a pres and SIP URI for its own identity, it SHOULD use the pres URI in the From header field. Similarly, when the subscriber is aware of both a pres and a SIP URI for the desired presentity, it SHOULD use the pres URI in the To header field.
Сообщения SUBSCRIBE также содержат логические идентификаторы, определяющие инициатора и получателя подписки (поля заголовков To и From header fields). Эти заголовки могут содержать либо pres URI, либо SIP URI. Когда подписчик знает как pres URI, так и SIP URI для своей собственной идентичности, ему СЛЕДУЕТ использовать pres URI в поле заголовка From. Аналогично, когда подписчик знает как pres URI, так и SIP URI для нужного презентити, ему СЛЕДУЕТ использовать pres URI в поле заголовка To.
The usage of the pres URI instead of the SIP URI within the SIP message supports interoperability through gateways to other CPP-compliant systems. It provides a protocol-independent form of identification which can be passed between systems. Without such an identity, gateways would be forced to map SIP URIs into the addressing format of other protocols. Generally, this is done by converting the SIP URI to the form <foreign-protocol-scheme>:<encoded SIP URI>@<gateway>. This is commonly done in email systems, and has many known problems. The usage of the pres URI is a SHOULD, and not a MUST, to allow for cases where it is known that there are no gateways present, or where the usage of the pres URI will cause interoperability problems with SIP components that do not support the pres URI.
Использование pres URI вместо SIP URI в сообщении SIP поддерживает взаимодействие через шлюзы с другими системами, совместимыми с CPP. Он обеспечивает независимую от протокола форму идентификации, которая может передаваться между системами. Без такой идентичности шлюзам пришлось бы отображать SIP URI в формат адресации других протоколов. Обычно это делается путём преобразования SIP URI в форму <foreign-protocol-scheme>:<encoded SIP URI>@<gateway>. Это часто делается в почтовых системах и имеет много известных проблем. Использование pres URI является рекомендацией (SHOULD), а не требованием (MUST), чтобы допустить случаи, когда известно, что шлюзы отсутствуют, или когда использование pres URI вызовет проблемы взаимодействия с компонентами SIP, не поддерживающими pres URI.
The Contact, Record-Route and Route fields do not identify logical entities, but rather concrete ones used for SIP messaging. SIP [1] specifies rules for their construction.
Поля Contact, Record-Route и Route не идентифицируют логические сущности, а идентифицируют конкретные сущности, используемые для обмена сообщениями SIP. SIP [1] задаёт правила их построения.

Имя этого пакета — «presence». Как указано в RFC 3265 [2], это значение присутствует в поле заголовка Event запросов SUBSCRIBE и NOTIFY.

Механизм событий SIP позволяет пакетам событий определять дополнительные параметры, передаваемые в поле заголовка Event. Данный пакет, presence, не определяет никаких дополнительных параметров.

Запрос SUBSCRIBE МОЖЕТ содержать тело. Назначение тела зависит от его типа. Подписки обычно не содержат тел.
The Request-URI, which identifies the presentity, combined with the event package name, is sufficient for presence.
Request-URI, который идентифицирует презентити, в сочетании с именем пакета событий достаточно для присутствия.
One type of body that can be included in a SUBSCRIBE request is a filter document. These filters request that only certain presence events generate notifications, or would ask for a restriction on the set of data returned in NOTIFY requests. For example, a presence filter might specify that the notifications should only be generated when the status of the user's instant inbox [10] changes. It might also say that the content of these notifications should only contain the status of the instant inbox. Filter documents are not specified in this document, and at the time of writing, are expected to be the subject of future standardization activity.
Один из типов тела, который может быть включён в запрос SUBSCRIBE, — это документ фильтра. Такие фильтры требуют, чтобы уведомления формировались только для определённых событий присутствия, либо задают ограничение на набор данных, возвращаемых в запросах NOTIFY. Например, фильтр присутствия может указывать, что уведомления должны формироваться только при изменении состояния мгновенного почтового ящика пользователя [10]. Он также может указывать, что содержимое этих уведомлений должно включать только состояние мгновенного почтового ящика. Документы фильтров в настоящем документе не определяются и, на момент написания, как ожидается, станут предметом будущей деятельности по стандартизации.
Honoring of these filters is at the policy discretion of the PA.
Соблюдение этих фильтров остаётся на усмотрение политики PA.
If the SUBSCRIBE request does not contain a filter, this tells the PA that no filter is to be applied. The PA SHOULD send NOTIFY requests at the discretion of its own policy.
Если запрос SUBSCRIBE не содержит фильтра, это сообщает PA, что фильтр не должен применяться. PA СЛЕДУЕТ отправлять запросы NOTIFY по усмотрению собственной политики.

User presence changes as a result of many events. Some examples are:
Пользовательское присутствие изменяется в результате многих событий. Некоторые примеры:

As per RFC 3265 [2], the subscriber MAY specify an alternate expiration in the Expires header field.
Эти события обычно инициируются вмешательством человека и происходят с частотой от секунд до часов. Поэтому подписки должны иметь срок истечения в середине этого диапазона, то есть примерно один час. Следовательно, срок истечения по умолчанию для подписок в этом пакете составляет 3600 секунд. Согласно RFC 3265 [2], подписчик МОЖЕТ указать другой срок истечения в поле заголовка Expires.

In this event package, the body of the notification contains a presence document. This document describes the presence of the presentity that was subscribed to. If no such header field is present, it has a default value of "application/pidf+xml". If the header field is present, it MUST include "application/pidf+xml", and MAY include any other types capable of representing user presence.
В этом пакете событий тело уведомления содержит документ присутствия. Этот документ описывает присутствие презентити, на который была оформлена подписка. Все подписчики и уведомители ДОЛЖНЫ поддерживать формат данных присутствия «application/pidf+xml», описанный в [6]. Запрос SUBSCRIBE МОЖЕТ содержать поле заголовка Accept. 6.6. Notifier Processing of SUBSCRIBE Requests
6.6. Обработка запросов SUBSCRIBE уведомителем
Based on the proxy routing procedures defined in the SIP specification, the SUBSCRIBE request will arrive at a presence agent (PA). This subsection defines package-specific processing at the PA of a SUBSCRIBE request. General processing rules for requests are covered in Section 8.2 of RFC 3261 [1], in addition to general SUBSCRIBE processing in RFC 3265 [2]. User presence is highly sensitive information. Because the implications of divulging presence information can be severe, strong requirements are imposed on the PA regarding subscription processing, especially related to authentication and authorization.
Согласно процедурам маршрутизации прокси, определённым в спецификации SIP, запрос SUBSCRIBE поступит на агент присутствия (PA). В этом подразделе определяется специфичная для пакета обработка запроса SUBSCRIBE на PA. Общие правила обработки запросов рассмотрены в разделе 8.2 RFC 3261 [1], а также общая обработка SUBSCRIBE — в RFC 3265 [2]. Присутствие пользователя является весьма конфиденциальной информацией. Поскольку последствия раскрытия информации о присутствии могут быть серьёзными, к PA предъявляются строгие требования в отношении обработки подписок, особенно связанные с аутентификацией и авторизацией.
6.6.1. Authentication
6.6.1. Аутентификация
A presence agent MUST authenticate all subscription requests. This authentication can be done using any of the mechanisms defined in RFC 3261 [1]. Note that digest is mandatory to implement, as specified in RFC 3261.
Агент присутствия ДОЛЖЕН аутентифицировать все запросы подписки. Эта аутентификация может выполняться с использованием любого из механизмов, определённых в RFC 3261 [1]. Отметим, что digest обязателен для реализации, как указано в RFC 3261.
In single-domain systems, where the subscribers all have shared secrets with the PA, the combination of digest authentication over Transport Layer Security (TLS) [7] provides a secure and workable solution for authentication. This use case is described in Section 26.3.2.1 of RFC 3261 [1].
В системах одного домена, где все подписчики имеют общий секрет с PA, сочетание дайджест-аутентификации поверх Transport Layer Security (TLS) [7] обеспечивает безопасное и работоспособное решение для аутентификации. Этот вариант использования описан в разделе 26.3.2.1 RFC 3261 [1].
In inter-domain scenarios, establishing an authenticated identity of the subscriber is harder. It is anticipated that authentication will often be established through transitive trust. SIP mechanisms for network asserted identity can be applied to establish the identity of the subscriber [11].
В сценариях между доменами установление аутентифицированной идентичности подписчика сложнее. Предполагается, что аутентификация часто будет устанавливаться через транзитивное доверие. Механизмы SIP для идентичности, утверждаемой сетью, могут применяться для установления идентичности подписчика [11].
A presentity MAY choose to represent itself with a SIPS URI. By "represent itself", it means that the user represented by the presentity hands out, on business cards, web pages, and so on, a SIPS URI for their presentity. The semantics associated with this URI, as described in RFC 3261 [1], require TLS usage on each hop between the subscriber and the server in the domain of the URI. This provides additional assurances (but no absolute guarantees) that identity has been verified at each hop.
Презентити МОЖЕТ выбрать представление себя посредством SIPS URI. Под «представлением себя» понимается, что пользователь, представленный презентити, раздаёт на визитных карточках, веб-страницах и т. п. SIPS URI для своего презентити. Семантика, связанная с этим URI, как описано в RFC 3261 [1], требует использования TLS на каждом участке между подписчиком и сервером в домене URI. Это даёт дополнительные гарантии (но не абсолютные) того, что идентичность была проверена на каждом участке.
Another mechanism for authentication is S/MIME. Its usage with SIP is described fully in RFC 3261 [1]. It provides an end-to-end authentication mechanism that can be used for a PA to establish the identity of the subscriber.
Ещё один механизм аутентификации — S/MIME. Его использование с SIP полностью описано в RFC 3261 [1]. Он обеспечивает сквозной механизм аутентификации, который PA может использовать для установления идентичности подписчика.
6.6.2. Authorization
6.6.2. Авторизация
Once authenticated, the PA makes an authorization decision. A PA MUST NOT accept a subscription unless authorization has been provided by the presentity. The means by which authorization are provided are outside the scope of this document. Authorization may have been provided ahead of time through access lists, perhaps specified in a web page. Authorization may have been provided by means of uploading of some kind of standardized access control list document. Back end authorization servers, such as a DIAMETER [12] server, can also be used. It is also useful to be able to query the user for authorization following the receipt of a subscription request for which no authorization information has been provided. The "watcherinfo" event template package for SIP [8] defines a means by which a presentity can become aware that a user has attempted to subscribe to it, so that it can then provide an authorization decision.
После аутентификации PA принимает решение об авторизации. PA НЕ ДОЛЖЕН принимать подписку, если авторизация не была предоставлена презентити. Средства предоставления авторизации выходят за рамки настоящего документа. Авторизация может быть предоставлена заранее через списки доступа, возможно, заданные на веб-странице. Авторизация может быть предоставлена путём загрузки некоторого стандартизированного документа списка управления доступом. Также могут использоваться внутренние серверы авторизации, например сервер DIAMETER [12]. Полезной является и возможность запросить у пользователя авторизацию после получения запроса подписки, для которого информация об авторизации не была предоставлена. Пакет шаблона событий «watcherinfo» для SIP [8] определяет средство, с помощью которого презентити может узнать, что пользователь попытался оформить на него подписку, чтобы затем предоставить решение об авторизации.
Authorization decisions can be very complex. Ultimately, all authorization decisions can be mapped into one of three states: rejected, successful, and pending. Any subscription for which the client is authorized to receive information about some subset of presence state at some points in time is a successful subscription. Any subscription for which the client will never receive any information about any subset of the presence state is a rejected subscription. Any subscription for which it is not yet known whether it is successful or rejected is pending. Generally, a pending subscription occurs when the server cannot obtain authorization at the time of the subscription, but may be able to do so at a later time, perhaps when the presentity becomes available.
Решения об авторизации могут быть очень сложными. В конечном счёте все решения об авторизации можно свести к одному из трёх состояний: отклонено, успешно и ожидание. Любая подписка, по которой клиент авторизован получать информацию о некотором подмножестве состояния присутствия в некоторые моменты времени, является успешной подпиской. Любая подписка, по которой клиент никогда не получит никакой информации о любом подмножестве состояния присутствия, является отклонённой подпиской. Любая подписка, по которой пока неизвестно, является она успешной или отклонённой, является ожидающей. Обычно ожидающая подписка возникает, когда сервер не может получить авторизацию в момент подписки, но может сделать это позже, возможно, когда презентити станет доступен.
The appropriate response codes for conveying a successful, rejected, or pending subscription (200, 403 or 603, and 202, respectively) are described in RFC 3265 [2].
Соответствующие коды ответов для передачи успешной, отклонённой или ожидающей подписки (200, 403 или 603 и 202 соответственно) описаны в RFC 3265 [2].
If the resource is not in a meaningful state, RFC 3265 [2] allows the body of the initial NOTIFY to be empty. In the case of presence, that NOTIFY MAY contain a presence document. This document would indicate whatever presence state the subscriber has been authorized to see; it is interpreted by the subscriber as the current presence state of the presentity. For pending subscriptions, the state of the presentity SHOULD include some kind of textual note that indicates a pending status.
Если ресурс не находится в осмысленном состоянии, RFC 3265 [2] допускает, чтобы тело первоначального NOTIFY было пустым. В случае присутствия этот NOTIFY МОЖЕТ содержать документ присутствия. Этот документ указывает то состояние присутствия, которое подписчику разрешено видеть; подписчик интерпретирует его как текущее состояние присутствия презентити. Для ожидающих подписок состояние презентити СЛЕДУЕТ включать некоторое текстовое примечание, указывающее на ожидающий статус.
Polite blocking, as described in [13], is possible by generating a 200 OK to the subscription even though it has been rejected (or marked pending). Of course, an immediate NOTIFY will still be sent. The contents of the presence document in such a NOTIFY are at the discretion of the implementor, but SHOULD be constructed in such a way as to not reveal to the subscriber that their request has actually been blocked. Typically, this is done by indicating "offline" or equivalent status for a single contact address.
Вежливая блокировка, как описано в [13], возможна путём формирования ответа 200 OK на подписку, даже если она отклонена (или помечена как ожидающая). Разумеется, немедленный NOTIFY всё равно будет отправлен. Содержимое документа присутствия в таком NOTIFY остаётся на усмотрение разработчика, но СЛЕДУЕТ строить его так, чтобы не раскрывать подписчику, что его запрос фактически заблокирован. Обычно это делается путём указания статуса «не в сети» или эквивалентного для одного адреса контакта.
6.7. Notifier Generation of NOTIFY Requests
6.7. Формирование запросов NOTIFY уведомителем
RFC 3265 details the formatting and structure of NOTIFY messages. However, packages are mandated to provide detailed information on when to send a NOTIFY, how to compute the state of the resource, how to generate neutral or fake state information, and whether state information is complete or partial. This section describes those details for the presence event package.
RFC 3265 подробно описывает форматирование и структуру сообщений NOTIFY. Однако пакеты обязаны предоставлять подробную информацию о том, когда отправлять NOTIFY, как вычислять состояние ресурса, как формировать нейтральную или фиктивную информацию о состоянии и является ли информация о состоянии полной или частичной. В этом разделе такие сведения описываются для пакета событий присутствия.
A PA MAY send a NOTIFY at any time. Typically, it will send one when the state of the presentity changes. The NOTIFY request MAY contain a body indicating the state of the presentity. The times at which the NOTIFY is sent for a particular subscriber, and the contents of the body within that notification, are subject to any rules specified by the authorization policy that governs the subscription. This protocol in no way limits the scope of such policies. As a baseline, a reasonable policy is to generate notifications when the state of any of the presence tuples changes. These notifications would contain the complete and current presence state of the presentity as known to the presence agent. Future extensions can be defined that allow a subscriber to request that the notifications contain changes in presence information only, rather than complete state.
PA МОЖЕТ отправлять NOTIFY в любой момент. Обычно он отправляет его при изменении состояния презентити. Запрос NOTIFY МОЖЕТ содержать тело, указывающее состояние презентити. Моменты, в которые NOTIFY отправляется конкретному подписчику, и содержимое тела в этом уведомлении подчиняются любым правилам, заданным политикой авторизации, которая управляет подпиской. Настоящий протокол никоим образом не ограничивает область действия таких политик. В качестве базового варианта разумной политикой является формирование уведомлений при изменении состояния любого из кортежей присутствия. Эти уведомления содержат полное и текущее состояние присутствия презентити, известное агенту присутствия. В будущем могут быть определены расширения, позволяющие подписчику запрашивать, чтобы уведомления содержали только изменения информации о присутствии, а не полное состояние.
In the case of a pending subscription, when final authorization is determined, a NOTIFY can be sent. If the result of the authorization decision was success, a NOTIFY SHOULD be sent and SHOULD contain a presence document with the current state of the presentity. If the subscription is rejected, a NOTIFY MAY be sent. As described in RFC 3265 [2], the Subscription-State header field indicates the state of the subscription.
В случае ожидающей подписки, когда окончательная авторизация определена, может быть отправлен NOTIFY. Если результатом решения об авторизации стал успех, СЛЕДУЕТ отправить NOTIFY, и он СЛЕДУЕТ включать документ присутствия с текущим состоянием презентити. Если подписка отклонена, NOTIFY МОЖЕТ быть отправлен. Как описано в RFC 3265 [2], поле заголовка Subscription-State указывает состояние подписки.
The body of the NOTIFY MUST be sent using one of the types listed in the Accept header field in the most recent SUBSCRIBE request, or using the type "application/pidf+xml" if no Accept header field was present.
Тело NOTIFY ДОЛЖНО отправляться с использованием одного из типов, перечисленных в поле заголовка Accept в самом последнем запросе SUBSCRIBE, или с использованием типа «application/pidf+xml», если поле заголовка Accept отсутствовало.
The means by which the PA learns the state of the presentity are also outside the scope of this recommendation. Registrations can provide a component of the presentity state. However, the means by which a PA uses registrations to construct a presence document are an implementation choice. If a PUA wishes to explicitly inform the presence agent of its presence state, it should explicitly publish the presence document (or its piece of it) rather than attempting to manipulate their registrations to achieve the desired result.
Средства, с помощью которых PA узнаёт состояние презентити, также выходят за рамки этой рекомендации. Регистрации могут предоставлять компонент состояния презентити. Однако средства, с помощью которых PA использует регистрации для построения документа присутствия, являются выбором реализации. Если PUA желает явно сообщить агенту присутствия своё состояние присутствия, ему следует явно публиковать документ присутствия (или свою его часть), а не пытаться манипулировать своими регистрациями для достижения желаемого результата.
For reasons of privacy, it will frequently be necessary to encrypt the contents of the notifications. This can be accomplished using S/MIME. The encryption can be performed using the key of the subscriber as identified in the From field of the SUBSCRIBE request. Similarly, integrity of the notifications is important to subscribers. As such, the contents of the notifications MAY provide authentication and message integrity using S/MIME. Since the NOTIFY is generated by the presence server, which may not have access to the key of the user represented by the presentity, it will frequently be the case that the NOTIFY is signed by a third party. It is RECOMMENDED that the signature be by an authority over the domain of the presentity. In other words, for a user pres:user@example.com, the signator of the NOTIFY SHOULD be the authority for example.com.
По соображениям конфиденциальности часто будет необходимо шифровать содержимое уведомлений. Это может быть выполнено с использованием S/MIME. Шифрование может выполняться с использованием ключа подписчика, определённого в поле From запроса SUBSCRIBE. Аналогично, целостность уведомлений важна для подписчиков. Поэтому содержимое уведомлений МОЖЕТ обеспечивать аутентификацию и целостность сообщения с использованием S/MIME. Поскольку NOTIFY формируется сервером присутствия, который может не иметь доступа к ключу пользователя, представляемого презентити, часто будет так, что NOTIFY подписывается третьей стороной. РЕКОМЕНДУЕТСЯ, чтобы подпись ставилась полномочным представителем домена презентити. Иными словами, для пользователя pres:user@example.com подписывающим NOTIFY СЛЕДУЕТ быть полномочному представителю example.com.
6.8. Subscriber Processing of NOTIFY Requests
6.8. Обработка запросов NOTIFY подписчиком
RFC 3265 [2] leaves it to event packages to describe the process followed by the subscriber upon receipt of a NOTIFY request, including any logic required to form a coherent resource state.
RFC 3265 [2] оставляет пакетам событий задание процесса, которому следует подписчик при получении запроса NOTIFY, включая любую логику, необходимую для формирования согласованного состояния ресурса.
In this specification, each NOTIFY contains either no presence document, or a document representing the complete and coherent state of the presentity. Within a dialog, the presence document in the NOTIFY request with the highest CSeq header field value is the current one. When no document is present in that NOTIFY, the presence document present in the NOTIFY with the next highest CSeq value is used. Extensions which specify the use of partial state for presentities will need to dictate how coherent state is achieved.
В этой спецификации каждый NOTIFY содержит либо документ присутствия, либо документ, представляющий полное и согласованное состояние презентити. В рамках диалога документ присутствия в запросе NOTIFY с наибольшим значением поля заголовка CSeq является текущим. Когда в этом NOTIFY документ отсутствует, используется документ присутствия из NOTIFY со следующим по величине значением CSeq. Расширения, задающие использование частичного состояния для презентити, должны будут определить, как достигается согласованное состояние.
6.9. Handling of Forked Requests
6.9. Обработка разветвлённых запросов
RFC 3265 [2] requires each package to describe handling of forked SUBSCRIBE requests.
RFC 3265 [2] требует, чтобы каждый пакет описывал обработку разветвлённых запросов SUBSCRIBE.
This specification only allows a single dialog to be constructed as a result of emitting an initial SUBSCRIBE request. This guarantees that only a single PA is generating notifications for a particular subscription to a particular presentity. The result of this is that a presentity can have multiple PAs active, but these should be homogeneous, so that each can generate the same set of notifications for the presentity. Supporting heterogeneous PAs, each of which generates notifications for a subset of the presence data, is complex and difficult to manage. Doing so would require the subscriber to act as the aggregator for presence data. This aggregation function can only reasonably be performed by agents representing the presentity. Therefore, if aggregation is needed, it MUST be done in a PA representing the presentity.
Эта спецификация допускает построение только одного диалога в результате отправки первоначального запроса SUBSCRIBE. Это гарантирует, что уведомления для конкретной подписки на конкретный презентити формирует только один PA. Следствием этого является то, что у презентити может быть несколько активных PA, но они должны быть однородными, чтобы каждый мог формировать одинаковый набор уведомлений для презентити. Поддержка неоднородных PA, каждый из которых формирует уведомления для подмножества данных присутствия, сложна и трудна в управлении. Это потребовало бы от подписчика выполнения функции агрегатора данных присутствия. Такая функция агрегации разумно может выполняться только агентами, представляющими презентити. Поэтому, если агрегация необходима, она ДОЛЖНА выполняться в PA, представляющем презентити.
Section 4.4.9 of RFC 3265 [2] describes the processing that is required to guarantee the creation of a single dialog in response to a SUBSCRIBE request.
В разделе 4.4.9 RFC 3265 [2] описана обработка, необходимая для гарантии создания одного диалога в ответ на запрос SUBSCRIBE.
6.10. Rate of Notifications
6.10. Частота уведомлений
RFC 3265 [2] requires each package to specify the maximum rate at which notifications can be sent.
RFC 3265 [2] требует, чтобы каждый пакет задавал максимальную частоту, с которой могут отправляться уведомления.
A PA SHOULD NOT generate notifications for a single presentity at a rate of more than once every five seconds.
PA НЕ СЛЕДУЕТ формировать уведомления для одного презентити чаще, чем один раз в пять секунд.
6.11. State Agents
6.11. Агенты состояния
RFC 3265 [2] requires each package to consider the role of state agents in the package, and if they are used, to specify how authentication and authorization are done.
RFC 3265 [2] требует, чтобы каждый пакет рассматривал роль агентов состояния в пакете и, если они используются, определял, как выполняются аутентификация и авторизация.
State agents are core to this package. Whenever the PA is not co-located with the PUA for the presentity, the PA is acting as a state agent. It collects presence state from the PUA, and aggregates it into a presence document. Because there can be multiple PUA, a centralized state agent is needed to perform this aggregation. That is why state agents are fundamental to presence. Indeed, they have a specific term that describes them - a presence server.
Агенты состояния являются основой этого пакета. Всякий раз, когда PA не сосуществует с PUA для презентити, PA действует как агент состояния. Он собирает состояние присутствия от PUA и агрегирует его в документ присутствия. Поскольку PUA может быть несколько, для выполнения этой агрегации необходим централизованный агент состояния. Именно поэтому агенты состояния принципиально важны для присутствия. Более того, для них есть специальный термин — сервер присутствия.
6.11.1. Aggregation, Authentication, and Authorization
6.11.1. Агрегация, аутентификация и авторизация
The means by which aggregation is done in the state agent is purely a matter of policy. The policy will typically combine the desires of the presentity along with the desires of the provider. This document in no way restricts the set of policies which may be applied.
Средства выполнения агрегации в агенте состояния определяются исключительно политикой. Политика обычно объединяет пожелания презентити с пожеланиями поставщика услуг. Настоящий документ никоим образом не ограничивает набор политик, которые могут применяться.
However, there is clearly a need for the state agent to have access to the state of the presentity. This state is manipulated by the PUA. One way in which the state agent can obtain this state is to subscribe to it. As a result, if there were 5 PUA manipulating presence state for a single presentity, the state agent would generate 5 subscriptions, one to each PUA. For this mechanism to be effective, all PUA SHOULD be capable of acting as a PA for the state that they manipulate, and that they authorize subscriptions that can be authenticated as coming from the domain of the presentity.
Однако агенту состояния явно необходим доступ к состоянию презентити. Это состояние изменяется PUA. Один из способов, которым агент состояния может получить это состояние, — оформить на него подписку. В результате, если бы 5 PUA изменяли состояние присутствия для одного презентити, агент состояния сформировал бы 5 подписок, по одной на каждый PUA. Чтобы этот механизм был эффективным, все PUA СЛЕДУЕТ делать способными действовать как PA для состояния, которое они изменяют, и авторизовывать подписки, аутентифицированные как исходящие из домена презентити.
The usage of state agents does not significantly alter the way in which authentication is done by the PA. Any of the SIP authentication mechanisms can be used by a state agent. However, digest authentication will require the state agent to be aware of the shared secret between the presentity and the subscriber. This will require some means to securely transfer the shared secrets from the presentity to the state agent. The usage of state agents does, however, have a significant impact on authorization. As stated in Section 6.6, a PA is required to authorize all subscriptions. If no explicit authorization policy has been defined, the PA will need to query the user for authorization. In a presence edge server (where the PUA is co-located with the PUA), this is trivially accomplished. However, when state agents are used (i.e., a presence server), a means is needed to alert the user that an authorization decision is required. This is the reason for the watcherinfo event template-package [8]. All state agents SHOULD support the watcherinfo template-package.
Использование агентов состояния существенно не изменяет способ выполнения аутентификации в PA. Агент состояния может использовать любой из механизмов аутентификации SIP. Однако дайджест-аутентификация потребует, чтобы агент состояния знал общий секрет между презентити и подписчиком. Для этого потребуется некоторое средство безопасной передачи общих секретов от презентити агенту состояния. Использование агентов состояния, однако, существенно влияет на авторизацию. Как указано в разделе 6.6, PA обязан авторизовывать все подписки. Если явная политика авторизации не определена, PA потребуется запросить у пользователя авторизацию. В периферийном сервере присутствия (где PUA сосуществует с PUA) это выполняется тривиально. Однако когда используются агенты состояния (то есть сервер присутствия), необходимо средство оповещения пользователя о необходимости решения об авторизации. Именно для этого существует пакет шаблона событий watcherinfo [8]. Все агенты состояния СЛЕДУЕТ поддерживать пакет шаблона watcherinfo.
6.11.2. Migration
6.11.2. Миграция
On occasion, it makes sense for the PA function to migrate from one server to another. For example, for reasons of scale, the PA function may reside in the presence server when the PUA is not running, but when the PUA connects to the network, the PA migrates subscriptions to it in order to reduce state in the network. The mechanism for accomplishing the migration is described in Section 3.3.5 of RFC 3265 [2]. However, packages need to define under what conditions such a migration would take place.
Иногда функция PA имеет смысл для миграции с одного сервера на другой. Например, по причинам масштабирования функция PA может размещаться на сервере присутствия, когда PUA не работает, но когда PUA подключается к сети, PA переносит подписки на него, чтобы сократить состояние в сети. Механизм выполнения миграции описан в разделе 3.3.5 RFC 3265 [2]. Однако пакеты должны определить, при каких условиях такая миграция происходит.
A PA MAY choose to migrate subscriptions at any time, through configuration, or through dynamic means. The REGISTER request provides one dynamic means for a presence server to discover that the function can migrate to a PUA. Specifically, if a PUA wishes to indicate support for the PA function, it SHOULD use the callee capabilities specification [9] to indicate that it supports the SUBSCRIBE request method and the presence event package. The combination of these two define a PA. Of course, a presence server can always attempt a migration without these explicit hints. If it fails with either a 405 or 489 response code, the server knows that the PUA does not support the PA function. In this case, the server itself will need to act as a PA for that subscription request. Once such a failure has occurred, the server SHOULD NOT attempt further migrations to that PUA for the duration of its registration. However, to avoid the extra traffic generated by these failed requests, a presence server SHOULD support the callee capabilities extension.
PA МОЖЕТ выбрать миграцию подписок в любой момент — посредством конфигурации или динамическими средствами. Запрос REGISTER предоставляет одно динамическое средство, позволяющее серверу присутствия обнаружить, что функция может мигрировать на PUA. В частности, если PUA желает указать поддержку функции PA, ему СЛЕДУЕТ использовать спецификацию возможностей вызываемого абонента [9], чтобы указать, что он поддерживает метод запроса SUBSCRIBE и пакет событий присутствия. Сочетание этих двух определяет PA. Разумеется, сервер присутствия всегда может попытаться выполнить миграцию без этих явных подсказок. Если она завершается неудачей с кодом ответа 405 или 489, сервер знает, что PUA не поддерживает функцию PA. В этом случае сам сервер должен будет действовать как PA для этого запроса подписки. После того как такая неудача произошла, серверу НЕ СЛЕДУЕТ пытаться выполнять дальнейшие миграции на этот PUA в течение срока его регистрации. Однако, чтобы избежать дополнительного трафика, порождаемого этими неудачными запросами, серверу присутствия СЛЕДУЕТ поддерживать расширение возможностей вызываемого абонента.
Furthermore, indication of support for the SUBSCRIBE request and the presence event package is not sufficient for migration of subscriptions. A PA SHOULD NOT migrate the subscription if it is composing aggregated presence documents received from multiple PUA.
Кроме того, указания поддержки метода запроса SUBSCRIBE и пакета событий присутствия недостаточно для миграции подписок. PA НЕ СЛЕДУЕТ переносить подписку, если он составляет агрегированные документы присутствия, полученные от нескольких PUA.
7. Learning Presence State
7. Изучение состояния присутствия
Presence information can be obtained by the PA in many ways. No specific mechanism is mandated by this specification. This section overviews some of the options, for informational purposes only.
Информация о присутствии может быть получена PA многими способами. Настоящая спецификация не предписывает какой-либо конкретный механизм. В этом разделе приводится обзор некоторых вариантов, исключительно в информационных целях.
7.1. Co-location
7.1. Совместное размещение
When the PA function is co-located with the PUA, presence is known directly by the PA.
Когда функция PA сосуществует с PUA, присутствие известно PA непосредственно.
7.2. REGISTER
7.2. REGISTER
A UA uses the SIP REGISTER method to inform the SIP network of its current communications addresses (i.e., Contact addresses). Multiple UA can independently register Contact addresses for the same address-of-record. This registration state represents an important piece of the overall presence information for a presentity. It is an indication of basic reachability for communications.
UA использует метод SIP REGISTER, чтобы сообщить сети SIP свои текущие адреса связи (то есть адреса Contact). Несколько UA могут независимо регистрировать адреса Contact для одного и того же адреса записи. Это состояние регистрации представляет важную часть общей информации о присутствии для презентити. Оно является указанием базовой достижимости для связи.
Usage of REGISTER information to construct presence is only possible if the PA has access to the registration database, and can be informed of changes to that database. One way to accomplish that is to co-locate the PA with the registrar.
Использование информации REGISTER для построения присутствия возможно только в том случае, если PA имеет доступ к базе данных регистрации и может быть информирован об изменениях в этой базе данных. Один из способов добиться этого — совместно разместить PA с регистратором.
The means by which registration state is converted into presence state is a matter of local policy, and beyond the scope of this specification. However, some general guidelines can be provided. The address-of-record in the registration (the To header field) identifies the presentity. Each registered Contact header field identifies a point of communications for that presentity, which can be modeled using a tuple. Note that the contact address in the tuple need not be the same as the registered contact address. Using an address-of-record instead allows subsequent communications from a watcher to pass through proxies. This is useful for policy processing on behalf of the presentity and the provider.
Средства, с помощью которых состояние регистрации преобразуется в состояние присутствия, определяются локальной политикой и выходят за рамки настоящей спецификации. Однако можно дать некоторые общие рекомендации. Адрес записи в регистрации (поле заголовка To) идентифицирует презентити. Каждое зарегистрированное поле заголовка Contact идентифицирует точку связи для этого презентити, которую можно смоделировать с помощью кортежа. Заметим, что адрес контакта в кортеже не обязательно должен совпадать с зарегистрированным адресом контакта. Использование вместо него адреса записи позволяет последующим сообщениям от наблюдателя проходить через прокси. Это полезно для обработки политик в интересах презентити и поставщика услуг.
A PUA that uses registrations to manipulate presence state SHOULD make use of the SIP callee capabilities extension [9]. This allows the PUA to provide the PA with richer information about itself. For example, the presence of the methods parameter listing the method "MESSAGE" indicates support for instant messaging.
PUA, который использует регистрации для изменения состояния присутствия, СЛЕДУЕТ использовать расширение возможностей вызываемого абонента SIP [9]. Это позволяет PUA предоставить PA более богатую информацию о себе. Например, наличие параметра methods со значением метода «MESSAGE» указывает на поддержку обмена мгновенными сообщениями.
The q values from the Contact header field [1] can be used to establish relative priorities amongst the various communications addresses in the Contact header fields. The usage of registrations to obtain presence information increases the requirements for authenticity and integrity of registrations. Therefore, REGISTER requests used by presence user agents MUST be authenticated.
Значения q из поля заголовка Contact [1] можно использовать для установления относительных приоритетов среди различных адресов связи в полях заголовка Contact. Использование регистраций для получения информации о присутствии повышает требования к подлинности и целостности регистраций. Поэтому запросы REGISTER, используемые пользовательскими агентами присутствия, ДОЛЖНЫ быть аутентифицированы.
7.3. Uploading Presence Documents
7.3. Загрузка документов присутствия
If a means exists to upload presence documents from PUA to the PA, the PA can act as an aggregator and redistributor of those documents. The PA, in this case, would take the presence documents received from each PUA for the same presentity, and merge the tuples across all of those PUA into a single presence document. Typically, this aggregation would be accomplished through administrator or user defined policies about how the aggregation should be done.
Если существует средство загрузки документов присутствия от PUA в PA, PA может действовать как агрегатор и распространитель этих документов. В этом случае PA брал бы документы присутствия, полученные от каждого PUA для одного и того же презентити, и объединял бы кортежи из всех этих PUA в единый документ присутствия. Обычно такая агрегация выполнялась бы согласно политикам, заданным администратором или пользователем, относительно того, как следует выполнять агрегацию.
The specific means by which a presence document is uploaded to a presence agent are outside the scope of this specification. When a PUA wishes to have direct manipulation of the presence that is distributed to subscribers, direct uploading of presence documents is RECOMMENDED.
Конкретные средства, с помощью которых документ присутствия загружается агенту присутствия, выходят за рамки настоящей спецификации. Когда PUA желает напрямую управлять присутствием, распространяемым подписчикам, РЕКОМЕНДУЕТСЯ прямая загрузка документов присутствия.

9. Security Considerations
9. Вопросы безопасности
There are numerous security considerations for presence. RFC 2779 [13] outlines many of them, and they are discussed above. This section considers them issue by issue.
Для присутствия существует множество соображений безопасности. RFC 2779 [13] описывает многие из них, и они обсуждались выше. В этом разделе они рассматриваются пункт за пунктом.
9.1. Confidentiality
9.1. Конфиденциальность
Confidentiality encompasses many aspects of a presence system:
Конфиденциальность охватывает многие аспекты системы присутствия:
o Subscribers may not want to reveal the fact that they have subscribed to certain users
o подписчики могут не желать раскрывать сам факт подписки на определённых пользователей;
o Users may not want to reveal that they have accepted subscriptions from certain users
o пользователи могут не желать раскрывать, что приняли подписки от определённых пользователей;
o Notifications (and fetch results) may contain sensitive data which should not be revealed to anyone but the subscriber
o уведомления (и результаты запросов) могут содержать чувствительные данные, которые не следует раскрывать никому, кроме подписчика
Confidentiality is provided through a combination of hop-by-hop encryption and end-to-end encryption. The hop-by-hop mechanisms provide scalable confidentiality services, disable attacks involving traffic analysis, and hide all aspects of presence messages. However, they operate based on transitivity of trust, and they cause message content to be revealed to proxies. The end-to-end mechanisms do not require transitivity of trust, and reveal information only to the desired recipient. However, end-to-end encryption cannot hide all information, and is susceptible to traffic analysis. Strong end-to-end authentication and encryption can be done using public keys, and end-to-end encryption can be done using private keys [14]. Both hop-by-hop and end-to-end mechanisms will likely be needed for complete privacy services.
Конфиденциальность обеспечивается сочетанием шифрования на каждом участке (hop-by-hop) и сквозного шифрования. Механизмы hop-by-hop обеспечивают масштабируемые услуги конфиденциальности, предотвращают атаки, связанные с анализом трафика, и скрывают все аспекты сообщений присутствия. Однако они работают на основе транзитивности доверия и приводят к раскрытию содержимого сообщений прокси. Сквозные механизмы не требуют транзитивности доверия и раскрывают информацию только нужному получателю. Однако сквозное шифрование не может скрыть всю информацию и подвержено анализу трафика. Стойкая сквозная аутентификация и шифрование могут выполняться с использованием открытых ключей, а сквозное шифрование — с использованием закрытых ключей [14]. Для полного набора услуг конфиденциальности, вероятно, потребуются как механизмы hop-by-hop, так и сквозные механизмы.
SIP allows any hop by hop encryption scheme, but TLS is mandatory to implement for servers. Therefore, it is RECOMMENDED that TLS [7] be used between elements to provide this function. The details for usage of TLS for server-to-server and client-to-server security are detailed in Section 26.3.2 of RFC 3261 [1].
SIP допускает любую схему шифрования на каждом участке, но TLS обязателен для реализации на серверах. Поэтому РЕКОМЕНДУЕТСЯ использовать TLS [7] между элементами для обеспечения этой функции. Подробности использования TLS для защиты «сервер-сервер» и «клиент-сервер» изложены в разделе 26.3.2 RFC 3261 [1].
SIP encryption, using S/MIME, MAY be used end-to-end for the transmission of both SUBSCRIBE and NOTIFY requests.
Шифрование SIP с использованием S/MIME МОЖЕТ применяться сквозным образом для передачи как запросов SUBSCRIBE, так и запросов NOTIFY.
9.2. Message Integrity and Authenticity
9.2. Целостность и подлинность сообщений
It is important for the message recipient to ensure that the message contents are actually what was sent by the originator, and that the recipient of the message be able to determine who the originator really is. This applies to both requests and responses of SUBSCRIBE and NOTIFY. NOTIFY requests are particularly important. Without authentication and integrity, presence documents could be forged or modified, fooling the watcher into believing incorrect presence information.
Для получателя сообщения важно убедиться, что содержимое сообщения действительно то, что было отправлено отправителем, и что получатель сообщения может определить, кем на самом деле является отправитель. Это относится как к запросам, так и к ответам SUBSCRIBE и NOTIFY. Запросы NOTIFY особенно важны. Без аутентификации и целостности документы присутствия могли бы быть подделаны или изменены, вводя наблюдателя в заблуждение относительно недостоверной информации о присутствии.
RFC 3261 provides many mechanisms to provide these features. In order for the PA to authenticate the watcher, it MAY use HTTP Digest (Section 22 of RFC 3261). As a result, all watchers MUST support HTTP Digest. This is a redundant requirement, however, since all SIP user agents are mandated to support it by RFC 3261. To provide authenticity and integrity services, a watcher MAY use the SIPS scheme when subscribing to the presentity. To support this, all PA MUST support TLS and SIPS as if they were a proxy (see Section 26.3.1 of RFC 3261).
RFC 3261 предоставляет множество механизмов для обеспечения этих свойств. Чтобы PA мог аутентифицировать наблюдателя, он МОЖЕТ использовать HTTP Digest (раздел 22 RFC 3261). В результате все наблюдатели ДОЛЖНЫ поддерживать HTTP Digest. Однако это избыточное требование, поскольку все пользовательские агенты SIP обязаны поддерживать его согласно RFC 3261. Для обеспечения услуг подлинности и целостности наблюдатель МОЖЕТ использовать схему SIPS при подписке на презентити. Чтобы поддерживать это, все PA ДОЛЖНЫ поддерживать TLS и SIPS так, как если бы они были прокси (см. раздел 26.3.1 RFC 3261).
Furthermore, SMIME MAY be used for integrity and authenticity of SUBSCRIBE and NOTIFY requests. This is described in Section 23 of RFC 3261.
Кроме того, SMIME МОЖЕТ использоваться для целостности и подлинности запросов SUBSCRIBE и NOTIFY. Это описано в разделе 23 RFC 3261.
9.3. Outbound Authentication
9.3. Исходящая аутентификация
When local proxies are used for transmission of outbound messages, proxy authentication is RECOMMENDED. This is useful to verify the identity of the originator, and prevent spoofing and spamming at the originating network.
Когда для передачи исходящих сообщений используются локальные прокси, РЕКОМЕНДУЕТСЯ аутентификация на прокси. Это полезно для проверки идентичности отправителя и предотвращения подмены и спама в сети отправителя.
9.4. Replay Prevention
9.4. Предотвращение повторного воспроизведения
Replay attacks can be used by an attacker to fool a watcher into believing an outdated presence state for a presentity. For example, a document describing a presentity as being "offline" can be replayed, fooling watchers into thinking that the user is never online. This may effectively block communications with the presentity.
Атаки повторного воспроизведения могут использоваться злоумышленником, чтобы ввести наблюдателя в заблуждение относительно устаревшего состояния присутствия презентити. Например, может быть воспроизведён документ, описывающий презентити как «не в сети», в результате чего наблюдатели будут считать, что пользователь никогда не бывает в сети. Это может фактически заблокировать связь с презентити.
SIP S/MIME can provide message integrity and authentication over SIP request bodies. Watchers and PAs MAY implement S/MIME signatures to prevent these replay attacks. When it is used for that purpose, the presence document carried in the NOTIFY request MUST contain a timestamp. In the case of PIDF, this is accomplished using the timestamp element, as described in Section 6 of [6]. Tuples whose timestamp is older than the timestamp of the most recently received presence document SHOULD be considered stale, and discarded.
SIP S/MIME может обеспечивать целостность и аутентификацию сообщений для тел запросов SIP. Наблюдатели и PA МОГУТ реализовывать подписи S/MIME для предотвращения таких атак повторного воспроизведения. Когда это используется для указанной цели, документ присутствия, передаваемый в запросе NOTIFY, ДОЛЖЕН содержать отметку времени. В случае PIDF это достигается с использованием элемента timestamp, как описано в разделе 6 [6]. Кортежи, отметка времени которых старше отметки времени самого последнего полученного документа присутствия, СЛЕДУЕТ считать устаревшими и отбрасывать.
Finally, HTTP digest authentication (which MUST be implemented by watchers and PAs) MAY be used to prevent replay attacks, when there is a shared secret between the PA and the watcher. In such a case, the watcher can challenge the NOTIFY requests with the auth-int quality of protection.
Наконец, аутентификация HTTP digest (которая ДОЛЖНА быть реализована наблюдателями и PA) МОЖЕТ использоваться для предотвращения атак повторного воспроизведения, когда между PA и наблюдателем есть общий секрет. В таком случае наблюдатель может запросить аутентификацию запросов NOTIFY с качеством защиты auth-int.
9.5. Denial of Service Attacks Against Third Parties
9.5. Атаки отказа в обслуживании против третьих сторон
Denial of Service (DOS) attacks are a critical problem for an open, inter-domain, presence protocol. Unfortunately, presence is a good candidate for Distributed DoS (DDOS) attacks because of its amplification properties. A single SUBSCRIBE message could generate a nearly unending stream of notifications, so long as a suitably dynamic source of presence data can be found. Thus, a simple way to launch an attack against a target is to send subscriptions to a large number of users, and in the Contact header field (which is where notifications are sent), place the address of the target. RFC 3265 provides some mechanisms to mitigate these attacks [2]. If a NOTIFY is not acknowledged or was not wanted, the subscription that generated it is removed. This eliminates the amplification properties of providing false Contact addresses. Authentication and authorization at the PA can also prevent these attacks. Typically, authorization policy will not allow subscriptions from unknown watchers. If the attacks are launched from watchers unknown to the presentity (a common case), the attacks are mitigated.
Атаки отказа в обслуживании (DOS) являются критической проблемой для открытого междоменного протокола присутствия. К сожалению, присутствие является хорошим кандидатом для распределённых атак DoS (DDOS) из-за свойств усиления. Одно сообщение SUBSCRIBE могло бы породить почти бесконечный поток уведомлений, если удастся найти достаточно динамичный источник данных присутствия. Таким образом, простой способ начать атаку на цель — отправить подписки большому числу пользователей и указать в поле заголовка Contact (куда отправляются уведомления) адрес цели. RFC 3265 предоставляет некоторые механизмы для смягчения таких атак [2]. Если NOTIFY не подтверждён или не был нужен, подписка, породившая его, удаляется. Это устраняет свойства усиления, связанные с указанием ложных адресов Contact. Аутентификация и авторизация в PA также могут предотвратить такие атаки. Обычно политика авторизации не допускает подписок от неизвестных наблюдателей. Если атаки инициируются наблюдателями, неизвестными презентити (обычный случай), атаки смягчаются.
9.6. Denial Of Service Attacks Against Servers
9.6. Атаки отказа в обслуживании против серверов
Denial of service attacks can also be launched against a presence agent itself, in order to disrupt service to a community of users. SIP itself, along with RFC 3265 [2], describes several mechanisms to mitigate these attacks.
Атаки отказа в обслуживании могут также инициироваться против самого агента присутствия, чтобы нарушить обслуживание сообщества пользователей. Сам SIP вместе с RFC 3265 [2] описывает несколько механизмов смягчения таких атак.
A server can prevent SYN-attack style attacks through a four-way handshake using digest authentication [1]. Even if the server does not have a shared secret with the client, it can verify the source IP address of the request using the "anonymous" user mechanism described in Section 22.1 of RFC 3261 [1]. SIP also allows a server to instruct a client to back-off from sending it requests, using the 503 response code (Section 21.5.4 of RFC 3261 [1]). This can be used to fend off floods of SUBSCRIBE requests launched as a result of a distributed denial of service attack.
Сервер может предотвращать атаки в стиле SYN-атак с помощью четырёхэтапного рукопожатия с использованием дайджест-аутентификации [1]. Даже если сервер не имеет общего секрета с клиентом, он может проверить IP-адрес источника запроса с использованием механизма пользователя «anonymous», описанного в разделе 22.1 RFC 3261 [1]. SIP также позволяет серверу указать клиенту снизить интенсивность отправки ему запросов с использованием кода ответа 503 (раздел 21.5.4 RFC 3261 [1]). Это можно использовать для отражения потоков запросов SUBSCRIBE, инициированных в результате распределённой атаки отказа в обслуживании.
