Abstract
Аннотация
The Session Initiation Protocol (SIP) operates over UDP and TCP, among others. When used with UDP, responses to requests are returned to the source address the request came from, and to the port written into the topmost Via header field value of the request. This behavior is not desirable in many cases, most notably, when the client is behind a Network Address Translator (NAT). This extension defines a new parameter for the Via header field, called "rport", that allows a client to request that the server send the response back to the source IP address and port from which the request originated.
Протокол инициирования сессий (SIP) работает поверх UDP, TCP и других протоколов. При использовании UDP ответы на запросы возвращаются на исходный адрес, с которого пришёл запрос, и на порт, записанный в значении самого верхнего поля заголовка Via запроса. Во многих случаях такое поведение нежелательно, прежде всего когда клиент находится за преобразователем сетевых адресов (NAT). Это расширение определяет новый параметр поля заголовка Via под названием «rport», позволяющий клиенту запросить, чтобы сервер отправлял ответ на исходный IP-адрес и порт, с которых пришёл запрос.
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [1] operates over UDP and TCP. When used with UDP, responses to requests are returned to the source address the request came from, and to the port written into the topmost Via header field value of the request. This results in a "hybrid" way of computing the destination of the response. Half of the information (specifically, the IP address) is taken from the IP packet headers, and the other half (specifically, the port) from the SIP message headers. SIP operates in this manner so that a server can listen for all messages, both requests and responses, on a single
Протокол инициирования сессий (SIP) [1] работает поверх UDP и TCP. При использовании UDP ответы на запросы возвращаются на исходный адрес, с которого пришёл запрос, и на порт, записанный в значении самого верхнего поля заголовка Via запроса. Это приводит к «гибридному» способу вычисления пункта назначения ответа. Половина информации (а именно IP-адрес) берётся из заголовков IP-пакетов, а другая половина (а именно порт) — из заголовков сообщений SIP. SIP работает так, чтобы сервер мог прослушивать все сообщения, как запросы, так и ответы, на одном
IP address and port. This helps improve scalability. However, this behavior is not desirable in many cases, most notably, when the client is behind a NAT. In that case, the response will not properly traverse the NAT, since it will not match the binding established with the request.
IP-адресе и порту. Это помогает повысить масштабируемость. Однако такое поведение нежелательно во многих случаях, прежде всего когда клиент находится за NAT. В этом случае ответ не сможет должным образом пройти через NAT, поскольку он не будет соответствовать привязке, установленной при запросе.
Furthermore, there is currently no way for a client to examine a response and determine the source port that the server saw in the corresponding request. Currently, SIP provides the client with the source IP address that the server saw in the request, but not the port. The source IP address is conveyed in the "received" parameter in the topmost Via header field value of the response. This information has proved useful for basic NAT traversal, debugging purposes, and support of multi-homed hosts. However, it is incomplete without the port information.
Кроме того, в настоящее время у клиента нет способа исследовать ответ и определить исходный порт, который сервер увидел в соответствующем запросе. Сейчас SIP предоставляет клиенту исходный IP-адрес, который сервер увидел в запросе, но не порт. Исходный IP-адрес передаётся в параметре «received» в значении самого верхнего поля заголовка Via ответа. Эта информация оказалась полезной для базового прохождения NAT, отладки и поддержки хостов с несколькими интерфейсами. Однако без информации о порте она неполна.
This extension defines a new parameter for the Via header field, called "rport", that allows a client to request that the server send the response back to the source IP address and port where the request came from. The "rport" parameter is analogous to the "received" parameter, except "rport" contains a port number, not the IP address.
Это расширение определяет новый параметр поля заголовка Via под названием «rport», позволяющий клиенту запросить, чтобы сервер отправлял ответ на исходный IP-адрес и порт, откуда пришёл запрос. Параметр «rport» аналогичен параметру «received», за исключением того, что «rport» содержит номер порта, а не IP-адрес.

3. Client Behavior
3. Поведение клиента
The client behavior specified here affects the transport processing defined in Section 18.1 of SIP (RFC 3261) [1].
Описанное здесь поведение клиента влияет на обработку транспорта, определённую в разделе 18.1 SIP (RFC 3261) [1].
A client, compliant to this specification (clients include UACs and proxies), MAY include an "rport" parameter in the top Via header field value of requests it generates. This parameter MUST have no value; it serves as a flag to indicate to the server that this extension is supported and requested for the transaction.
Клиент, совместимый с настоящей спецификацией (к клиентам относятся UAC и прокси), MAY включать параметр «rport» в значение самого верхнего поля заголовка Via в генерируемых им запросах. Этот параметр MUST не иметь значения; он служит флагом, указывающим серверу, что данное расширение поддерживается и запрошено для транзакции.
When the client sends the request, if the request is sent using UDP, the client MUST be prepared to receive the response on the same IP address and port it used to populate the source IP address and source port of the request. For backwards compatibility, the client MUST still be prepared to receive a response on the port indicated in the sent-by field of the topmost Via header field value, as specified in Section 18.1.1 of SIP [1].
Когда клиент отправляет запрос, если запрос отправляется по UDP, клиент MUST быть готов принять ответ на том же IP-адресе и порте, которые он использовал для заполнения исходного IP-адреса и исходного порта запроса. Для обратной совместимости клиент MUST по-прежнему быть готов принять ответ на порте, указанном в поле sent-by значения самого верхнего поля заголовка Via, как определено в разделе 18.1.1 SIP [1].
When there is a NAT between the client and server, the request will create (or refresh) a binding in the NAT. This binding must remain in existence for the duration of the transaction in order for the client to receive the response. Most UDP NAT bindings appear to have a timeout of about one minute. This exceeds the duration of non- INVITE transactions. Therefore, responses to a non-INVITE request will be received while the binding is still in existence. INVITE transactions can take an arbitrarily long amount of time to complete. As a result, the binding may expire before a final response is received. To keep the binding fresh, the client SHOULD retransmit its INVITE every 20 seconds or so. These retransmissions will need to take place even after receiving a provisional response. A UA MAY execute the binding lifetime discovery algorithm in Section 10.2 of RFC 3489 [4] to determine the actual binding lifetime in the NAT. If it is longer than 1 minute, the client SHOULD increase the interval for request retransmissions up to half of the discovered lifetime. If it is shorter than one minute, it SHOULD decrease the interval for request retransmissions to half of the discovered lifetime. Note that discovery of binding lifetimes can be unreliable. See Section 14.3 of RFC 3489 [4].
Когда между клиентом и сервером находится NAT, запрос создаёт (или обновляет) привязку в NAT. Эта привязка должна существовать в течение всей транзакции, чтобы клиент мог получить ответ. Большинство привязок UDP в NAT, по-видимому, имеют тайм-аут около одной минуты. Это превышает длительность транзакций, не связанных с INVITE. Поэтому ответы на запрос, не являющийся INVITE, будут получены, пока привязка ещё существует. Транзакции INVITE могут занимать произвольно долгое время. В результате привязка может истечь до получения окончательного ответа. Чтобы поддерживать привязку свежей, клиент SHOULD повторно передавать свой INVITE примерно каждые 20 секунд. Эти повторные передачи потребуются даже после получения предварительного ответа. UA MAY выполнить алгоритм определения времени жизни привязки из раздела 10.2 RFC 3489 [4], чтобы определить фактическое время жизни привязки в NAT. Если оно больше 1 минуты, клиент SHOULD увеличить интервал повторной передачи запросов до половины обнаруженного времени жизни. Если оно меньше одной минуты, он SHOULD уменьшить интервал повторной передачи запросов до половины обнаруженного времени жизни. Учтите, что определение времени жизни привязок может быть ненадёжным. См. раздел 14.3 RFC 3489 [4].
4. Server Behavior
4. Поведение сервера
The server behavior specified here affects the transport processing defined in Section 18.2 of SIP [1].
Описанное здесь поведение сервера влияет на обработку транспорта, определённую в разделе 18.2 SIP [1].
When a server compliant to this specification (which can be a proxy or UAS) receives a request, it examines the topmost Via header field value. If this Via header field value contains an "rport" parameter with no value, it MUST set the value of the parameter to the source port of the request. This is analogous to the way in which a server will insert the "received" parameter into the topmost Via header field value. In fact, the server MUST insert a "received" parameter containing the source IP address that the request came from, even if it is identical to the value of the "sent-by" component. Note that this processing takes place independent of the transport protocol.
Когда сервер, совместимый с настоящей спецификацией (это может быть прокси или UAS), получает запрос, он проверяет значение самого верхнего поля заголовка Via. Если это значение поля заголовка Via содержит параметр «rport» без значения, сервер MUST установить значение параметра равным исходному порту запроса. Это аналогично тому, как сервер вставляет параметр «received» в значение самого верхнего поля заголовка Via. Фактически сервер MUST вставить параметр «received», содержащий исходный IP-адрес, с которого пришёл запрос, даже если он совпадает со значением компонента «sent-by». Отметим, что эта обработка выполняется независимо от протокола транспорта.
When a server attempts to send a response, it examines the topmost Via header field value of that response. If the "sent-protocol" component indicates an unreliable unicast transport protocol, such as UDP, and there is no "maddr" parameter, but there is both a "received" parameter and an "rport" parameter, the response MUST be sent to the IP address listed in the "received" parameter, and the port in the "rport" parameter. The response MUST be sent from the same address and port that the corresponding request was received on. This effectively adds a new processing step between bullets two and three in Section 18.2.2 of SIP [1].
Когда сервер пытается отправить ответ, он проверяет значение самого верхнего поля заголовка Via этого ответа. Если компонент «sent-protocol» указывает на ненадёжный одноадресный протокол транспорта, такой как UDP, и параметр «maddr» отсутствует, но присутствуют как параметр «received», так и параметр «rport», ответ MUST быть отправлен на IP-адрес, указанный в параметре «received», и на порт, указанный в параметре «rport». Ответ MUST быть отправлен с того же адреса и порта, на которые был получен соответствующий запрос. Это фактически добавляет новый шаг обработки между пунктами два и три в разделе 18.2.2 SIP [1].
The response must be sent from the same address and port that the request was received on in order to traverse symmetric NATs. When a server is listening for requests on multiple ports or interfaces, it will need to remember the one on which the request was received. For a stateful proxy, storing this information for the duration of the transaction is not an issue. However, a stateless proxy does not store state between a request and its response, and therefore cannot remember the address and port on which a request was received. To properly implement this specification, a stateless proxy can encode the destination address and port of a request into the Via header field value that it inserts. When the response arrives, it can extract this information and use it to forward the response.
Ответ должен быть отправлен с того же адреса и порта, на которые был получен запрос, чтобы пройти через симметричные NAT. Когда сервер прослушивает запросы на нескольких портах или интерфейсах, ему нужно запомнить, на каком из них был получен запрос. Для прокси с сохранением состояния хранение этой информации в течение транзакции не составляет проблемы. Однако прокси без сохранения состояния не хранит состояние между запросом и его ответом и поэтому не может запомнить адрес и порт, на которые был получен запрос. Чтобы правильно реализовать настоящую спецификацию, прокси без сохранения состояния может закодировать адрес назначения и порт запроса в значение поля заголовка Via, которое он вставляет. Когда приходит ответ, он может извлечь эту информацию и использовать её для пересылки ответа.
5. Syntax
5. Синтаксис
The syntax for the "rport" parameter is:
Синтаксис параметра «rport» следующий:
response-port = "rport" [EQUAL 1*DIGIT]
response-port = "rport" [EQUAL 1*DIGIT]
This extends the existing definition of the Via header field parameters, so that its BNF now looks like:
Это расширяет существующее определение параметров поля заголовка Via, так что его BNF теперь выглядит так:

6. Example
6. Пример
A client sends an INVITE to a proxy server which looks like, in part:
Клиент отправляет INVITE прокси-серверу, который частично выглядит так:
INVITE sip:user@example.com SIP/2.0 Via: SIP/2.0/UDP 10.1.1.1:4540;rport;branch=z9hG4bKkjshdyff
INVITE sip:user@example.com SIP/2.0 Via: SIP/2.0/UDP 10.1.1.1:4540;rport;branch=z9hG4bKkjshdyff
This INVITE is sent with a source port of 4540 and a source IP address of 10.1.1.1. The proxy is at 192.0.2.2 (proxy.example.com), listening on both port 5060 and 5070. The client sends the request to port 5060. The request passes through a NAT on the way to the proxy, so that the source IP address appears as 192.0.2.1 and the source port as 9988. The proxy forwards the request, but not before appending a value to the "rport" parameter in the proxied request:
Этот INVITE отправляется с исходным портом 4540 и исходным IP-адресом 10.1.1.1. Прокси находится по адресу 192.0.2.2 (proxy.example.com) и прослушивает как порт 5060, так и порт 5070. Клиент отправляет запрос на порт 5060. По пути к прокси запрос проходит через NAT, так что исходный IP-адрес выглядит как 192.0.2.1, а исходный порт — как 9988. Прокси пересылает запрос, но перед этим добавляет значение к параметру «rport» в пересылаемом запросе:
INVITE sip:user@example.com SIP/2.0 Via: SIP/2.0/UDP proxy.example.com;branch=z9hG4bKkjsh77 Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
INVITE sip:user@example.com SIP/2.0 Via: SIP/2.0/UDP proxy.example.com;branch=z9hG4bKkjsh77 Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
;branch=z9hG4bKkjshdyff
;branch=z9hG4bKkjshdyff
This request generates a response which arrives at the proxy:
Этот запрос порождает ответ, который приходит на прокси:
SIP/2.0 200 OK Via: SIP/2.0/UDP proxy.example.com;branch=z9hG4bKkjsh77 Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
SIP/2.0 200 OK Via: SIP/2.0/UDP proxy.example.com;branch=z9hG4bKkjsh77 Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
;branch=z9hG4bKkjshdyff
;branch=z9hG4bKkjshdyff
The proxy strips its top Via header field value, and then examines the next one. It contains both a "received" parameter and an "rport" parameter. The server follows the rules specified in Section 4 and sends the response to IP address 192.0.2.1, port 9988, and sends it from port 5060 on 192.0.2.2:
Прокси удаляет значение своего самого верхнего поля заголовка Via, а затем проверяет следующее. Оно содержит как параметр «received», так и параметр «rport». Сервер следует правилам, указанным в разделе 4, и отправляет ответ на IP-адрес 192.0.2.1, порт 9988, и отправляет его с порта 5060 на 192.0.2.2:
SIP/2.0 200 OK Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
SIP/2.0 200 OK Via: SIP/2.0/UDP 10.1.1.1:4540;received=192.0.2.1;rport=9988
;branch=z9hG4bKkjshdyff
;branch=z9hG4bKkjshdyff
This packet matches the binding created by the initial request. Therefore, the NAT rewrites the destination address of this packet back to 10.1.1.1, and the destination port back to 4540. It forwards this response to the client, which is listening for the response on that address and port. The client properly receives the response.
Этот пакет соответствует привязке, созданной первоначальным запросом. Поэтому NAT переписывает адрес назначения этого пакета обратно на 10.1.1.1, а порт назначения обратно на 4540. Он пересылает этот ответ клиенту, который прослушивает ответ на этом адресе и порте. Клиент правильно получает ответ.
7. Security Considerations
7. Вопросы безопасности
When a server uses this specification, responses that it sends will now include the source port where the request came from. In some instances, the source address and port of a request are sensitive information. If they are sensitive, requests SHOULD be protected by using SIP over TLS [1]. In such a case, this specification does not provide any response routing functions (as these only work with TCP); it merely provides the client with information about the source port as seen by the server.
Когда сервер использует настоящую спецификацию, отправляемые им ответы теперь будут включать исходный порт, с которого пришёл запрос. В некоторых случаях исходный адрес и порт запроса являются конфиденциальной информацией. Если они конфиденциальны, запросы SHOULD защищаться с помощью SIP поверх TLS [1]. В таком случае настоящая спецификация не предоставляет никаких функций маршрутизации ответов (поскольку они работают только с TCP); она лишь предоставляет клиенту информацию об исходном порте, как его видит сервер.
It is possible that an attacker might try to disrupt service to a client by acting as a man-in-the-middle, modifying the "rport" parameter in a Via header in a request sent by a client. Removal of this parameter will prevent clients from behind NATs from receiving service. The addition of the parameter will generally have no impact. Of course, if an attacker is capable of launching a man-in- the-middle attack, there are many other ways of denying service, such as merely discarding the request. Therefore, this attack does not seem significant.
Возможно, что злоумышленник попытается нарушить обслуживание клиента, действуя как посредник (man-in-the-middle) и изменяя параметр «rport» в поле заголовка Via запроса, отправленного клиентом. Удаление этого параметра не позволит клиентам за NAT получать обслуживание. Добавление параметра, как правило, не окажет никакого влияния. Разумеется, если злоумышленник способен осуществить атаку «посредник посередине», существует множество других способов отказа в обслуживании, например просто отбрасывание запроса. Поэтому эта атака не представляется существенной.

9. IAB Considerations
9. Вопросы IAB
The IAB has studied a class of protocols referred to as Unilateral Self Address Fixing (UNSAF) protocols [5]. These protocols allow a client behind a NAT to learn the IP address and port that a NAT will allocate for a particular request, in order to use this information in application layer protocols. An example of an UNSAF protocol is the Simple Traversal of UDP Through NATs (STUN) [4]. Any protocol is an UNSAF protocol if it reveals, to a client, the source IP address and port of a packet sent through that NAT. Although not designed for that purpose, this specification can be used as an UNSAF protocol. Using the "rport" parameter (defined here) and the "received" parameter (defined in RFC 3261 [1]) in the topmost Via header field value of a response, a client sending a request can learn its address as it was seen by the server which sent the response.
IAB исследовал класс протоколов, называемых протоколами одностороннего самостоятельного исправления адреса (UNSAF) [5]. Эти протоколы позволяют клиенту за NAT узнать IP-адрес и порт, которые NAT выделит для конкретного запроса, чтобы использовать эту информацию в протоколах прикладного уровня. Примером протокола UNSAF является простое прохождение UDP через NAT (STUN) [4]. Любой протокол является протоколом UNSAF, если он раскрывает клиенту исходный IP-адрес и порт пакета, отправленного через этот NAT. Хотя настоящая спецификация не разрабатывалась для этой цели, её можно использовать как протокол UNSAF. Используя параметр «rport» (определённый здесь) и параметр «received» (определённый в RFC 3261 [1]) в значении самого верхнего поля заголовка Via ответа, клиент, отправляющий запрос, может узнать свой адрес в том виде, в каком его увидел сервер, отправивший ответ.
There are two uses of this information. The first is for registrations. Consider a client behind a NAT wishing to register with a proxy/registrar on the other side of the NAT. The client must provide, in its registration, the address at which it should receive incoming SIP requests from the proxy. However, since the client is located behind a NAT, none of the addresses on any of its interfaces will be reachable from the proxy. If the client can provide the proxy with an address that the proxy can reach, the client can receive incoming requests. Using this specification, a client behind a NAT can learn its address and port as seen by the proxy which receives a REGISTER request. The client can then perform an additional registration, using this address in a Contact header. This would allow a client to receive incoming requests, such as INVITE, on the IP address and port it used to populate the source IP address and port of the registration it sent. This approach will only work when servers send requests to a UA from the same address and port on which the REGISTER itself was received.
У этой информации есть два применения. Первое — для регистраций. Рассмотрим клиента за NAT, желающего зарегистрироваться у прокси/регистратора по другую сторону NAT. Клиент должен указать в своей регистрации адрес, на который он должен получать входящие запросы SIP от прокси. Однако, поскольку клиент находится за NAT, ни один из адресов на любом из его интерфейсов не будет достижим с прокси. Если клиент может предоставить прокси адрес, который прокси может достичь, клиент сможет получать входящие запросы. Используя настоящую спецификацию, клиент за NAT может узнать свой адрес и порт в том виде, в каком их видит прокси, получающий запрос REGISTER. Затем клиент может выполнить дополнительную регистрацию, используя этот адрес в поле заголовка Contact. Это позволило бы клиенту получать входящие запросы, такие как INVITE, на IP-адресе и порте, которые он использовал для заполнения исходного IP-адреса и порта отправленной им регистрации. Этот подход будет работать только тогда, когда серверы отправляют запросы UA с того же адреса и порта, на которые был получен сам REGISTER.
In many cases, the server to whom the registration is sent won't be the registrar itself, but rather a proxy which then sends the request to the registrar. In such a case, any incoming requests for the client must traverse the proxy to whom the registration was directly sent. The Path header extension to SIP [3] allows the proxy to indicate that it must be on the path of such requests.
Во многих случаях сервер, которому отправляется регистрация, будет не самим регистратором, а прокси, который затем отправляет запрос регистратору. В таком случае любые входящие запросы для клиента должны проходить через прокси, которому регистрация была отправлена напрямую. Расширение заголовка Path для SIP [3] позволяет прокси указать, что он должен находиться на пути таких запросов.
The second usage is for record routing, to address the same problem as above, but between two proxies. A proxy behind a NAT which forwards a request to a server can use OPTIONS, for example, to learn its address as seen by that server. This address can be placed into the Record-Route header field of requests sent to that server. This would allow the proxy to receive requests from that server on the same IP address and port it used to populate the source IP address and port of the OPTIONS request.
Второе применение — для записи маршрута (record routing), чтобы решить ту же проблему, что и выше, но между двумя прокси. Прокси за NAT, пересылающий запрос серверу, может использовать, например, OPTIONS, чтобы узнать свой адрес в том виде, в каком его видит этот сервер. Этот адрес можно поместить в поле заголовка Record-Route запросов, отправляемых этому серверу. Это позволило бы прокси получать запросы от этого сервера на том же IP-адресе и порте, которые он использовал для заполнения исходного IP-адреса и порта запроса OPTIONS.
Because of this potential usage, this document must consider the issues raised in [5].
Из-за этого потенциального применения настоящий документ должен рассмотреть вопросы, поднятые в [5].

9.1. Постановка задачи

Precise definition of a specific, limited-scope problem that is to be solved with the UNSAF proposal. A short term fix should not be generalized to solve other problems; this is why "short term fixes usually aren't".
Точное определение конкретной задачи ограниченного масштаба, которая должна быть решена с помощью предложения UNSAF. Краткосрочное решение не следует обобщать на решение других задач; именно поэтому «краткосрочные решения обычно таковыми и не являются».
This specification is primarily aimed at allowing SIP responses to be received when a request is sent through a NAT. In this primary application, this specification is not an UNSAF proposal. However, as a side effect of this capability, this specification can be used as an UNSAF protocol. In that usage, it would address two issues:
Настоящая спецификация в первую очередь направлена на то, чтобы позволить получать ответы SIP при отправке запроса через NAT. В этом основном применении настоящая спецификация не является предложением UNSAF. Однако как побочный эффект этой возможности настоящую спецификацию можно использовать как протокол UNSAF. В таком применении она решила бы два вопроса:
o Provide a client with an address that it could use in the Contact header of a REGISTER request when it is behind a NAT.

o Предоставить прокси адрес, который он мог бы использовать в поле заголовка Record-Route в запросе, когда он находится за NAT.
9.2. Exit Strategy
9.2. Стратегия выхода
From [5], any UNSAF proposal must provide:
Согласно [5], любое предложение UNSAF должно содержать:
Description of an exit strategy/transition plan. The better short term fixes are the ones that will naturally see less and less use as the appropriate technology is deployed.
Описание стратегии выхода/плана перехода. Лучшие краткосрочные решения — те, которые естественным образом будут использоваться всё меньше и меньше по мере развёртывания соответствующей технологии.
The SIP working group has recognized that the usage of this specification to support registrations and record-routing through NATs is not appropriate. It has a number of known problems which are documented below. The way to eliminate potential usage of this specification for address fixing is to provide a proper solution to the problems that might motivate the usage of this specification for address fixing. Specifically, appropriate solutions for registrations and record-routing in the presence of NATs need to be developed. These solutions would not rely on address fixing.
Рабочая группа SIP признала, что использование настоящей спецификации для поддержки регистраций и записи маршрута через NAT нецелесообразно. У неё есть ряд известных проблем, которые описаны ниже. Способ устранить потенциальное использование настоящей спецификации для исправления адреса — предоставить надлежащее решение проблем, которые могут мотивировать использование настоящей спецификации для исправления адреса. В частности, необходимо разработать надлежащие решения для регистраций и записи маршрута при наличии NAT. Эти решения не должны полагаться на исправление адреса.
Requirements for such solutions are already under development [6].
Требования к таким решениям уже разрабатываются [6].
Implementors of this specification are encouraged to follow this work for better solutions for registrations and record-routing through NAT.
Разработчикам настоящей спецификации рекомендуется следить за этой работой ради лучших решений для регистраций и записи маршрута через NAT.
9.3. Brittleness Introduced by this Specification
9.3. Хрупкость, вносимая настоящей спецификацией
From [5], any UNSAF proposal must provide:
Согласно [5], любое предложение UNSAF должно содержать:
Discussion of specific issues that may render systems more "brittle". For example, approaches that involve using data at multiple network layers create more dependencies, increase debugging challenges, and make it harder to transition.
Обсуждение конкретных вопросов, которые могут сделать системы более «хрупкими». Например, подходы, использующие данные на нескольких сетевых уровнях, создают больше зависимостей, усложняют отладку и затрудняют переход.
This specification, if used for address fixing, introduces several points of brittleness into a SIP system:
Настоящая спецификация, если её использовать для исправления адреса, вносит в систему SIP несколько элементов хрупкости:
o If used for UDP registrations, a client will need to frequently re-register in order to keep the NAT bindings fresh. In many cases, these registrations will need to take place nearly one hundred times more frequently than the typical refresh interval of a registration. This introduces load into the system and hampers scalability.
o При использовании для регистраций UDP клиенту потребуется часто повторно регистрироваться, чтобы поддерживать привязки NAT свежими. Во многих случаях такие регистрации потребуется выполнять почти в сто раз чаще, чем типичный интервал обновления регистрации. Это создаёт нагрузку на систему и снижает масштабируемость.
o A client cannot accurately determine the binding lifetime of a NAT it is registering (or record-routing) through. Therefore, there may be periods of unreachability that occur between the time a binding expires and the next registration or OPTIONS refresh is sent. This may result in missed calls, messages, or other information.
o Клиент не может точно определить время жизни привязки NAT, через который он регистрируется (или выполняет запись маршрута). Поэтому между моментом истечения привязки и отправкой следующей регистрации или обновления OPTIONS могут возникать периоды недоступности. Это может привести к пропущенным вызовам, сообщениям или другой информации.
o If the NAT is of the symmetric variety [4], a client will only be able to use its address to receive requests from the server it has sent the request to. If that server is one of many servers in a cluster, the client may not be able to receive requests from other servers in the cluster. This may result in missed calls, messages, or other information.
o Если NAT является симметричным [4], клиент сможет использовать свой адрес для получения запросов только от того сервера, которому он отправил запрос. Если этот сервер — один из многих серверов в кластере, клиент может не суметь получить запросы от других серверов кластера. Это может привести к пропущенным вызовам, сообщениям или другой информации.
o If the NAT is of the symmetric variety [4], a client will only be able to use its address to receive requests if the server sends requests to the client from the same address and port the server received the registrations on. This server behavior is not mandated by RFC 3261 [1], although it appears to be common in practice.
o В случае симметричного NAT [4] клиент сможет использовать свой адрес для получения запросов только в том случае, если сервер отправляет запросы клиенту с того же адреса и порта, на которые сервер получил регистрации. Такое поведение сервера не предписано RFC 3261 [1], хотя, по-видимому, распространено на практике.

Using Path when the address in the topmost Via header field is a private address will usually work, but may result in usage of Path when it is not actually needed.

9.4. Requirements for a Long Term Solution
9.4. Требования к долгосрочному решению
From [5], any UNSAF proposal must provide:
Согласно [5], любое предложение UNSAF должно содержать:
Identify requirements for longer term, sound technical solutions -- contribute to the process of finding the right longer term solution.
Определение требований к долгосрочным, обоснованным техническим решениям — вклад в процесс поиска правильного долгосрочного решения.
The brittleness described in Section 9.3 has led us to the following requirements for a long term solution:
Хрупкость, описанная в разделе 9.3, привела нас к следующим требованиям к долгосрочному решению:
The client should not need to specify its address. Registrations and record routing require the client to specify the address at which it should receive requests. A sound technical solution should allow a client to explicitly specify that it wants to receive incoming requests on the connection over which the outgoing request was sent. In this way, the client does not need to specify its address.
Клиенту не должно требоваться указывать свой адрес. Регистрации и запись маршрута требуют, чтобы клиент указал адрес, на который он должен получать запросы. Обоснованное техническое решение должно позволять клиенту явно указать, что он хочет получать входящие запросы по соединению, по которому был отправлен исходящий запрос. Таким образом, клиенту не нужно указывать свой адрес.
The solution must deal with clusters of servers. In many commercially deployed SIP systems, there will be multiple servers, each at different addresses and ports, handling incoming requests for a client. The solution must explicitly consider this case.
Решение должно учитывать кластеры серверов. Во многих коммерчески развёрнутых системах SIP будет несколько серверов, каждый с разными адресами и портами, обрабатывающих входящие запросы для клиента. Решение должно явно учитывать этот случай.
The solution must not require increases in network load. There cannot be a penalty for a sound technical solution.
Решение не должно требовать увеличения сетевой нагрузки. За обоснованное техническое решение не может быть штрафа.
