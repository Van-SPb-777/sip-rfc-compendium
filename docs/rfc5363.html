Abstract
Аннотация
This document describes the need for SIP URI-list services and provides requirements for their invocation. Additionally, it defines a framework for SIP URI-list services, which includes security considerations applicable to these services.
В документе описана потребность в службах списков URI протокола SIP и приведены требования к их вызову. Кроме того, в нём определены основы служб списков URI SIP, включающие соображения безопасности, применимые к этим службам.

1. Introduction
1. Введение
Some applications require that, at a given moment, a SIP [RFC3261] UA (User Agent) performs a similar transaction with a number of remote UAs. For example, an instant messaging application that needs to send a particular message (e.g., "Hello folks") to n receivers needs to send n MESSAGE requests; one to each receiver.
Некоторые приложения требуют, чтобы в определённый момент агент пользователя (UA) SIP [RFC3261] выполнял однотипную транзакцию с рядом удалённых агентов пользователя. Например, приложению обмена мгновенными сообщениями, которому нужно отправить определённое сообщение (например, «Привет, народ») n получателям, необходимо отправить n запросов MESSAGE — по одному каждому получателю.
When the transaction that needs to be repeated consists of a large request, or when the number of recipients is high, or both, the access network of the UA needs to carry a considerable amount of traffic. Completing all the transactions on a low-bandwidth access would require a long time. This is unacceptable for a number of applications.
Когда повторяемая транзакция состоит из крупного запроса, или когда число получателей велико, или и то и другое, сети доступа агента пользователя приходится передавать значительный объём трафика. Завершение всех транзакций по каналу с малой пропускной способностью потребовало бы много времени. Для ряда приложений это неприемлемо.
A solution to this problem consists of introducing URI-list services in the network. The task of a SIP URI-list service is to receive a request that contains or references a URI list (i.e., a list of one or more URIs) and send a number of similar requests to the destinations in this list. Once the requests are sent, the URI-list service typically informs the UA about their status. Effectively, the URI-list service behaves as a B2BUA (Back-to-Back-User-Agent).
Решение этой проблемы состоит в том, чтобы ввести службы списков URI в сети. Задача службы списков URI SIP — принять запрос, содержащий список URI или ссылающийся на него (то есть список из одного или нескольких URI), и отправить ряд однотипных запросов адресатам из этого списка. После отправки запросов служба списков URI обычно информирует агента пользователя об их состоянии. Фактически служба списков URI действует как B2BUA (Back-to-Back-User-Agent).
A given URI-list service can take as an input a URI list contained in the SIP request sent by the client or an external URI list (e.g., the Request-URI is a SIP URI that is associated with a URI list at the server). External URI lists are typically set up using out-of-band mechanisms (e.g., XML Configuration Access Protocol (XCAP) [RFC4825]). An example of a URI-list service for SUBSCRIBE requests that uses stored URI lists is described in [RFC4662].
Конкретная служба списков URI может принимать на вход список URI, содержащийся в запросе SIP, отправленном клиентом, либо внешний список URI (например, Request-URI — это SIP URI, связанный со списком URI на сервере). Внешние списки URI обычно задаются с помощью внешних по отношению к протоколу механизмов (например, протокола доступа к конфигурации XML (XCAP) [RFC4825]). Пример службы списков URI для запросов SUBSCRIBE, использующей хранимые списки URI, описан в [RFC4662].
The remainder of this document provides requirements and a framework for URI-list services using request-contained URI lists, external URI lists, or both.
Остальная часть документа содержит требования и основы для служб списков URI, использующих списки URI, содержащиеся в запросе, внешние списки URI или и те и другие.

2. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].

3. Requirements
3. Требования
Section 3.1 discusses requirements that only apply to URI-list services that use request-contained lists, and Section 3.2 discusses requirements that also apply to services using external lists.
В разделе 3.1 обсуждаются требования, применимые только к службам списков URI, использующим списки, содержащиеся в запросе, а в разделе 3.2 — требования, применимые также к службам, использующим внешние списки.
3.1. Requirements for URI-List Services Using Request-Contained Lists
3.1. Требования к службам списков URI, использующим списки, содержащиеся в запросе
REQ 1: The URI-list service invocation mechanism MUST allow the invoker to provide a list of destination URIs to the URI-list service.
REQ 1: Механизм вызова службы списков URI ДОЛЖЕН позволять инициатору передать службе списков URI список URI назначения.
REQ 2: The invocation mechanism SHOULD NOT require more than one transaction.
REQ 2: Механизм вызова НЕ ДОЛЖЕН требовать более одной транзакции.
3.2. General Requirements for URI-List Services
3.2. Общие требования к службам списков URI
GEN 1: A URI-list service MAY include services beyond sending requests to the URIs in the URI list. That is, URI-list services can be modeled as application servers. For example, a URI-list service handling INVITE requests may behave as a conference server and perform media mixing for all the participants.
GEN 1: Служба списков URI МОЖЕТ включать службы, помимо отправки запросов на URI из списка URI. То есть службы списков URI можно моделировать как серверы приложений. Например, служба списков URI, обрабатывающая запросы INVITE, может вести себя как сервер конференций и выполнять микширование медиапотоков для всех участников.
GEN 2: The interpretation of the meaning of the URI list sent by the invoker MUST be at the discretion of the application to which the list is sent.
GEN 2: Толкование смысла списка URI, отправленного инициатором, ДОЛЖНО оставаться на усмотрение приложения, которому этот список направлен.
GEN 3: It MUST be possible for the invoker to find out about the result of the operations performed by the URI-list service with the URI list. An invoker may, for instance, be interested in the status of the transactions initiated by the URI-list service.
GEN 3: Инициатор ДОЛЖЕН иметь возможность узнать о результате операций, выполненных службой списков URI со списком URI. Например, инициатора может интересовать состояние транзакций, инициированных службой списков URI.
GEN 4: URI-list services MUST NOT send requests to any destination without authenticating the invoker.
GEN 4: Службы списков URI НЕ ДОЛЖНЫ отправлять запросы ни на какой адрес без аутентификации инициатора.
4. Framework
4. Основы
This framework is not restricted to application servers that only provide request fan-out services. Per GEN 1, this framework also deals with application servers that provide a particular service that includes a request fan-out (e.g., a conference server that INVITEs several participants that are chosen by a user agent).
Настоящие основы не ограничиваются серверами приложений, которые предоставляют только службы разветвления запросов. Согласно GEN 1, они также охватывают серверы приложений, предоставляющие определённую службу, которая включает разветвление запросов (например, сервер конференций, который отправляет INVITE нескольким участникам, выбранным агентом пользователя).
4.1. Carrying URI Lists in SIP
4.1. Передача списков URI в SIP
The requirements related to URI-list services that use request- contained lists identify the need for a mechanism to provide a SIP URI-list service with a URI list in a single transaction. We define a new disposition type [RFC2183] for the Content-Disposition header field: recipient-list. Both requests and responses MAY carry recipient-list bodies. Bodies whose disposition type is recipient- list carry a list of URIs that contains the final recipients of the requests to be generated by a URI-list service.
Требования, относящиеся к службам списков URI, использующим списки, содержащиеся в запросе, указывают на необходимость механизма, позволяющего передать службе списков URI SIP список URI в рамках одной транзакции. Мы определяем новый тип диспозиции [RFC2183] для поля заголовка Content-Disposition: recipient-list. Как запросы, так и ответы МОГУТ нести тела recipient-list. Тела, тип диспозиции которых — recipient-list, несут список URI, содержащий конечных получателей запросов, которые должна сгенерировать служба списков URI.
The default format for recipient-list bodies is service specific. So, URI-list services specifications MUST specify a default format for recipient-list bodies used within a particular service. In any case, clients SHOULD NOT include any particular URI more than once in a given URI list.
Формат по умолчанию для тел recipient-list зависит от службы. Поэтому спецификации служб списков URI ДОЛЖНЫ определять формат по умолчанию для тел recipient-list, используемых в рамках конкретной службы. В любом случае клиенты НЕ ДОЛЖНЫ включать какой-либо URI более одного раза в данный список URI.
A UA server receiving a request with more than one recipient-list body parts (e.g., each body part using a different URI-list format) MUST behave as if it had received a single URI list that contains all the URIs present in the different body parts.
Сервер UA, получающий запрос с несколькими частями тела recipient-list (например, каждая часть тела использует свой формат списка URI), ДОЛЖЕН вести себя так, как если бы он получил единый список URI, содержащий все URI, присутствующие в разных частях тела.
A UA server receiving a recipient-list URI list that contains a URI more than once MUST behave as if that URI appeared in the URI list only once. The UA server uses the comparison rules specific to the URI scheme of each of the URIs in the URI list to determine if there is any URI that appears more than once. Additionally, Section 4 of "Extensible Markup Language (XML) Format Extension for Representing Copy Control Attributes in Resource Lists" [RFC5364] discusses cases where duplicated URI entries are tagged with different values of the 'copyControl' attribute. Naturally, URI-list services using the 'copyControl' attribute defined in [RFC5364] need to follow the recommendations in [RFC5364] with respect to avoiding sending duplicated requests.
Сервер UA, получающий список URI типа recipient-list, в котором URI встречается более одного раза, ДОЛЖЕН вести себя так, как если бы этот URI встречался в списке URI только один раз. Для определения того, встречается ли какой-либо URI более одного раза, сервер UA использует правила сравнения, специфичные для схемы каждого URI в списке. Кроме того, в разделе 4 документа «Extensible Markup Language (XML) Format Extension for Representing Copy Control Attributes in Resource Lists» [RFC5364] рассматриваются случаи, когда повторяющиеся записи URI помечены разными значениями атрибута 'copyControl'. Естественно, службы списков URI, использующие атрибут 'copyControl', определённый в [RFC5364], должны следовать рекомендациям [RFC5364] в отношении избежания отправки дублирующихся запросов.
The way a UA server interprets a URI list that it has received is service specific, as described in Section 4.2.
Способ, которым сервер UA толкует полученный список URI, зависит от службы, как описано в разделе 4.2.
4.2. Processing of URI Lists
4.2. Обработка списков URI
According to GEN 1 and GEN 2, URI-list services can behave as application servers. That is, taking a URI list as an input, they can provide arbitrary services. So, the interpretation of the URI list by the server depends on the service to be provided. For example, for a conference server, the URIs in the list may identify the initial set of participants. On the other hand, for a server dealing with MESSAGEs, the URIs in the list may identify the recipients of an instant message.
Согласно GEN 1 и GEN 2, службы списков URI могут вести себя как серверы приложений. То есть, принимая список URI на вход, они могут предоставлять произвольные службы. Таким образом, толкование списка URI сервером зависит от предоставляемой службы. Например, для сервера конференций URI в списке могут определять исходный набор участников. С другой стороны, для сервера, работающего с MESSAGE, URI в списке могут определять получателей мгновенного сообщения.
At the SIP level, this implies that the behavior of application servers receiving requests with URI lists SHOULD be specified on a per-service basis. Examples of such specifications are [RFC5366] for INVITE, [RFC5365] for MESSAGE, and [RFC5367] for SUBSCRIBE.
На уровне SIP это означает, что поведение серверов приложений, получающих запросы со списками URI, СЛЕДУЕТ определять отдельно для каждой службы. Примерами таких спецификаций являются [RFC5366] для INVITE, [RFC5365] для MESSAGE и [RFC5367] для SUBSCRIBE.
4.3. Results
4.3. Результаты
According to GEN 3, user agents should have a way to obtain information about the operations performed by the application server. Since these operations are service specific, the way user agents are kept informed is also service specific. For example, a user agent establishing an ad hoc conference with an INVITE with a URI list may discover which participants were successfully brought into the conference by using the conference package [RFC4575].
Согласно GEN 3, у агентов пользователя должен быть способ получать информацию об операциях, выполняемых сервером приложений. Поскольку эти операции зависят от службы, способ информирования агентов пользователя также зависит от службы. Например, агент пользователя, устанавливающий конференцию ad hoc с помощью INVITE со списком URI, может узнать, какие участники были успешно привлечены в конференцию, используя пакет конференции [RFC4575].
5. Security Considerations
5. Вопросы безопасности
Security plays an important role in the implementation of any URI- list service. In fact, it is the most important common area across all types of URI-list services.
Безопасность играет важную роль при реализации любой службы списков URI. Фактически это наиболее важная общая область для всех типов служб списков URI.
By definition, a URI-list service takes one request in and sends a potentially large number of them out. Attackers may attempt to use URI-list services as traffic amplifiers to launch DoS (denial-of- service) attacks. This section provides guidelines to avoid these attacks.
По определению служба списков URI принимает один запрос и отправляет потенциально большое число запросов наружу. Злоумышленники могут попытаться использовать службы списков URI как усилители трафика для запуска атак DoS (отказ в обслуживании). В этом разделе приведены рекомендации по предотвращению таких атак.
5.1. List Integrity and Confidentiality
5.1. Целостность и конфиденциальность списков
Attackers may attempt to modify URI lists sent from clients to servers. This would cause a different behavior at the server than expected by the client (e.g., requests being sent to different recipients than the ones specified by the client). To prevent this attack, clients SHOULD integrity protect URI lists using end-to-end mechanisms such as S/MIME or, if not available, hop-by-hop mechanisms such as TLS. Both S/MIME and TLS can also provide URI-list confidentiality if needed.
Злоумышленники могут попытаться изменить списки URI, отправляемые клиентами на серверы. Это привело бы к поведению сервера, отличному от ожидаемого клиентом (например, запросы отправлялись бы не тем получателям, которых указал клиент). Чтобы предотвратить эту атаку, клиенты СЛЕДУЕТ защищать целостность списков URI с помощью сквозных механизмов, таких как S/MIME, или, если они недоступны, механизмов защиты «переход за переходом» (hop-by-hop), таких как TLS. S/MIME и TLS также могут обеспечивать конфиденциальность списка URI, если это необходимо.
5.2. Amplification Attacks
5.2. Атаки с усилением
URI-list services take a request in and send a potentially large number of them out. Given that URI-list services are typically implemented on top of powerful servers with high-bandwidth access links, we should be careful to keep attackers from using them as amplification tools to launch DoS attacks.
Службы списков URI принимают один запрос и отправляют потенциально большое число запросов наружу. Поскольку службы списков URI обычно реализуются на мощных серверах с высокоскоростными каналами доступа, следует следить за тем, чтобы злоумышленники не использовали их как инструменты усиления для запуска атак DoS.
Attackers may attempt to send a URI list containing URIs whose host parts route to the victims of the DoS attack. These victims do not need to be SIP nodes; they can be non-SIP endpoints or even routers. If this attack is successful, the result is that an attacker can flood a set of nodes, or a single node, with traffic without needing to generate a high volume of traffic itself. In any case, note that this problem is not specific to SIP URI- list services; it also appears in scenarios that relate to multihoming where a server needs to contact a set of IP addresses provided by a client.
Злоумышленники могут попытаться отправить список URI, содержащий URI, части хоста которых маршрутизируются к жертвам атаки DoS. Этими жертвами не обязательно должны быть узлы SIP; это могут быть оконечные точки, не поддерживающие SIP, или даже маршрутизаторы. Если эта атака удастся, злоумышленник сможет залить потоком трафика набор узлов или один узел, не создавая при этом большого объёма трафика сам. В любом случае отметим, что эта проблема не специфична для служб списков URI SIP; она также возникает в сценариях, связанных с многодомным подключением (multihoming), где серверу нужно связаться с набором IP-адресов, предоставленных клиентом.
There are several measures that need to be taken to prevent this type of attack. The first one is keeping unauthorized users from using URI-list services. So, URI-list services MUST NOT perform any request explosion for an unauthorized user. URI-list services MUST authenticate users and check whether they are authorized to request the service before performing any request fan-out.
Для предотвращения этого типа атак необходимо принять несколько мер. Первая — не допускать использования служб списков URI неавторизованными пользователями. Поэтому службы списков URI НЕ ДОЛЖНЫ выполнять никакого размножения запросов для неавторизованного пользователя. Прежде чем выполнять какое-либо разветвление запросов, службы списков URI ДОЛЖНЫ аутентифицировать пользователей и проверить, авторизованы ли они для запроса этой службы.
Note that the risk of this attack also exists when a client uses stored URI lists. Application servers MUST use authentication and authorization mechanisms with equivalent security properties when dealing with stored and request-contained URI lists.
Отметим, что риск такой атаки существует и тогда, когда клиент использует хранимые списки URI. При работе с хранимыми списками URI и списками, содержащимися в запросе, серверы приложений ДОЛЖНЫ использовать механизмы аутентификации и авторизации с эквивалентными свойствами безопасности.
Even though the previous rule keeps unauthorized users from using URI-list services, authorized users may still launch attacks using these services. To prevent these attacks, we introduce the concept of opt-in lists. That is, URI-list services should not allow a client to place a user (identified by his or her URI) in a URI list unless the user has previously agreed to be placed in such a URI list. So, URI-list services MUST NOT send a request to a destination that has not agreed to receive requests from the URI-list service beforehand. Users can agree to receive requests from a URI-list service in several ways, such as filling a web page, sending an email, signing a contract, or using "A Framework for Consent-Based Communications in the Session Initiation Protocol (SIP)" [RFC5360], whose requirements are discussed in [RFC4453]. Additionally, users MUST be able to further describe the requests they are willing to receive. For example, a user may only want to receive requests from a particular URI-list service on behalf of a particular user. Effectively, these rules make URI lists that used by URI-list services into opt-in lists.
Даже несмотря на то, что предыдущее правило не позволяет неавторизованным пользователям использовать службы списков URI, авторизованные пользователи всё ещё могут запускать атаки с помощью этих служб. Чтобы предотвратить такие атаки, мы вводим понятие списков с предварительным согласием (opt-in). То есть службы списков URI не должны позволять клиенту помещать пользователя (идентифицируемого его или её URI) в список URI, если этот пользователь ранее не согласился на включение в такой список. Поэтому службы списков URI НЕ ДОЛЖНЫ отправлять запрос адресату, который не согласился заранее получать запросы от этой службы списков URI. Пользователи могут согласиться получать запросы от службы списков URI несколькими способами, например заполнив веб-страницу, отправив сообщение электронной почты, подписав договор или используя документ «A Framework for Consent-Based Communications in the Session Initiation Protocol (SIP)» [RFC5360], требования которого обсуждаются в [RFC4453]. Кроме того, пользователи ДОЛЖНЫ иметь возможность дополнительно описать запросы, которые они готовы получать. Например, пользователь может хотеть получать запросы от конкретной службы списков URI только от имени конкретного пользователя. Фактически эти правила превращают списки URI, используемые службами списков URI, в списки с предварительным согласием.
When a URI-list service receives a request with a URI list from a client, the URI-list service checks whether all the destinations have agreed beforehand to receive requests from the service on behalf of this client. If the URI list has permission to send requests to all of the targets in the request, it does so. If not, it does not send any request at all.
Когда служба списков URI получает от клиента запрос со списком URI, она проверяет, согласились ли все адресаты заранее получать запросы от этой службы от имени данного клиента. Если у списка URI есть разрешение отправлять запросы всем целям в запросе, служба так и делает. Если нет, она не отправляет ни одного запроса.
The Framework for Consent-Based Communications in SIP [RFC5360] specifies a means for the URI-list service to inform the client that some permissions were missing and how to request them. Note that the mechanism used to obtain permissions should not create opportunities to launch DoS amplification attacks. These attacks would be possible if, for instance, the URI-list service automatically contacted the full set of targets for which it did not have permissions in order to request permissions. The URI- list service would be receiving one SIP request and sending out a number of authorization request messages. The Framework for Consent-Based Communications in SIP [RFC5360] avoids this type of attack by having the client generate roughly the same amount of traffic towards the URI-list service as the service generates towards the destinations.
Документ «A Framework for Consent-Based Communications in SIP» [RFC5360] определяет средство, с помощью которого служба списков URI сообщает клиенту об отсутствующих разрешениях и о том, как их запросить. Отметим, что механизм получения разрешений не должен создавать возможностей для запуска атак DoS с усилением. Такие атаки были бы возможны, если бы, например, служба списков URI автоматически связывалась со всем набором целей, на которые у неё нет разрешений, чтобы запросить разрешения. Тогда служба списков URI получала бы один запрос SIP и отправляла бы ряд сообщений запроса авторизации. Документ «A Framework for Consent-Based Communications in SIP» [RFC5360] избегает такого типа атак, заставляя клиента генерировать примерно такой же объём трафика в направлении службы списков URI, какой служба генерирует в направлении адресатов.
In order to have an interoperable way to meet the requirements related to opt-in lists described in this section, URI-list services MUST implement and SHOULD use "A Framework for Consent-Based Communications in SIP" [RFC5360].
Чтобы иметь совместимый способ выполнения требований, относящихся к спискам с предварительным согласием, описанным в этом разделе, службы списков URI ДОЛЖНЫ реализовывать и СЛЕДУЕТ использовать документ «A Framework for Consent-Based Communications in SIP» [RFC5360].
5.3. General Issues
5.3. Общие вопросы
URI-list services MAY have policies that limit the number of URIs in the lists they accept, as a very long list could be used in a denial-of-service attack to place a large burden on the URI-list service to send a large number of SIP requests.
Службы списков URI МОГУТ иметь политики, ограничивающие число URI в принимаемых списках, поскольку очень длинный список мог бы использоваться в атаке на отказ в обслуживании, чтобы создать большую нагрузку на службу списков URI по отправке большого числа запросов SIP.
A URI-list service generates a set of requests from a URI list. Section 19.1.5 of [RFC3261] provides recommendations that need to be taken into consideration when forming a request from a URI. Naturally, those recommendations apply to all SIP URI-list services.
Служба списков URI формирует набор запросов из списка URI. Раздел 19.1.5 документа [RFC3261] содержит рекомендации, которые необходимо учитывать при формировании запроса из URI. Естественно, эти рекомендации применимы ко всем службам списков URI SIP.
The general requirement GEN 4, which states that URI-list services need to authenticate their clients, and the previous rules apply to URI-list services in general. In addition, specifications dealing with individual methods MUST describe the security issues that relate to each particular method.
Общее требование GEN 4, согласно которому службы списков URI должны аутентифицировать своих клиентов, и предыдущие правила применимы к службам списков URI в целом. Кроме того, спецификации, касающиеся отдельных методов, ДОЛЖНЫ описывать проблемы безопасности, относящиеся к каждому конкретному методу.
