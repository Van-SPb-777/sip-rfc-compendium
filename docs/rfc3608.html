Abstract
Аннотация
This document defines a Session Initiation Protocol (SIP) extension header field used in conjunction with responses to REGISTER requests to provide a mechanism by which a registrar may inform a registering user agent (UA) of a service route that the UA may use to request outbound services from the registrar's domain.
В этом документе определяется поле заголовка расширения протокола инициирования сессий (SIP), используемое в сочетании с ответами на запросы REGISTER для обеспечения механизма, с помощью которого регистратор может информировать регистрирующего пользовательского агента (UA) о маршруте обслуживания, который UA может использовать для запроса исходящих услуг из домена регистратора.

2. Background
2. Предыстория
The Third Generation Partnership Project (3GPP) established a requirement for discovering home proxies during SIP registration and published this requirement in [6]. The 3GPP network dynamically assigns a home service proxy to each address-of-record (AOR). This assignment may occur in conjunction with a REGISTER operation, or out-of-band as needed to support call services when the address-of- record has no registrations. This home service proxy may provide both inbound (UA terminated) and outbound (UA originated) services.
Проект партнерства третьего поколения (3GPP) установил требование обнаружения домашних прокси во время регистрации SIP и опубликовал это требование в [6]. Сеть 3GPP динамически назначает прокси домашнего сервиса каждому адресу записи (AOR). Это назначение может происходить в сочетании с операцией REGISTER или внеполосно, если это необходимо для поддержки услуг вызова, когда адрес записи не имеет регистрации. Этот прокси домашней службы может предоставлять как входящие (завершенные UA), так и исходящие (инициируемые UA) услуги.
In the inbound case, the Request-Uniform Resource Identifier (URI) of incoming SIP requests matches the address-of-record of a user associated with the home service proxy. The home service proxy then (in most cases) forwards the request to the registered contact address for that AOR. A mechanism for traversing required proxies between the home service proxy and the registered UA is presented in [4].
Во входящем случае идентификатор ресурса (URI) Request-Uniform входящих SIP-запросов соответствует адресу записи пользователя, связанного с прокси домашней службы. Затем прокси домашней службы (в большинстве случаев) пересылает запрос на зарегистрированный контактный адрес для этого AOR. Механизм перемещения необходимых прокси между прокси домашнего сервиса и зарегистрированным UA представлен в [4].
Outbound (UA originated) session cases raise another issue. Specifically, "How does the UA know which service proxy to use and how to get there?"
Случаи исходящих сессий (инициированных UA) вызывают еще одну проблему. В частности, «Как UA узнает, какой сервисный прокси использовать и как туда добраться?»
Several mechanisms were proposed in list discussions, including:
В ходе обсуждений списка было предложено несколько механизмов, в том числе:
1. Configuration data in the UA. This raises questions of UA configuration management and updating, especially if proxy assignment is very dynamic, such as in load-balancing scenarios.
1. Данные конфигурации в UA. Это поднимает вопросы по управлению и обновлению конфигурации UA, особенно если назначение прокси очень динамично, например, в сценариях балансировки нагрузки.
2. Use of some other protocol, such as HTTP, to get configuration data from a configuration server in the home network. While functional, this solution requires additional protocol engines, firewall complexity, operations overhead, and significant additional "over the air" traffic.
2. Использование другого протокола, например HTTP, для получения данных конфигурации с сервера конфигурации в домашней сети. Несмотря на свою функциональность, это решение требует дополнительных механизмов протоколов, сложности брандмауэра, накладных расходов на операции и значительного дополнительного «беспроводного» трафика.
3. Use of lookup tables in the home network, as may be done for inbound requests in some 3G networks. This has a relatively high overhead in terms of database operations.
3. Использование справочных таблиц в домашней сети, как это может быть сделано для входящих запросов в некоторых сетях 3G. Это имеет относительно высокие накладные расходы с точки зрения операций с базой данных.
4. Returning a 302 response indicating the service proxy as a new contact, causing the upstream node processing the 302 (ostensibly the UA) to retransmit the request toward the service proxy. While this shares the database operation of the previous alternative, it does explicitly allow for caching the 302 response thereby potentially reducing the frequency and number of database operations.
4. Возврат ответа 302, указывающий прокси службы как новый контакт, в результате чего вышестоящий узел, обрабатывающий 302 (якобы UA), повторно передает запрос к прокси-службе. Хотя этот вариант аналогичен операции с базой данных, как и предыдущий вариант, он явно позволяет кэшировать ответ 302, тем самым потенциально уменьшая частоту и количество операций с базой данных.
5. Performing an operation equivalent to record-routing in a REGISTER transaction between the UA and the associated registrar, then storing that route in the UA and reusing it as a service route on future requests originating from the UA. While efficient, this constrains the service route for proxy operations to be congruent with the route taken by the REGISTER message.
5. Выполнение операции, эквивалентной маршрутизации записи в транзакции REGISTER между UA и соответствующим регистратором, затем сохранение этого маршрута в UA и повторное использование его в качестве маршрута обслуживания для будущих запросов, исходящих от UA. Несмотря на свою эффективность, это ограничивает маршрут службы для операций прокси, чтобы он совпадал с маршрутом, пройденным сообщением REGISTER.
6. Returning service route information as the value of a header field in the REGISTER response. While similar to the previous alternative, this approach grants the ability for the registrar to selectively apply knowledge about the topology of the home network in constructing the service route.
6. Возврат информации о маршруте службы в виде значения поля заголовка в ответе REGISTER. Хотя этот подход аналогичен предыдущему варианту, он предоставляет регистратору возможность выборочно применять знания о топологии домашней сети при построении маршрута обслуживания.
This document defines this final alternative: returning the service route information as a header field in the REGISTER response. This new header field indicates a "preloaded route" that the UA may wish to use if requesting services from the proxy network associated with the registrar generating the response.
Этот документ определяет эту последнюю альтернативу: возврат информации о маршруте службы в виде поля заголовка в ответе REGISTER. Это новое поле заголовка указывает «предварительно загруженный маршрут», который UA может захотеть использовать при запросе услуг из прокси-сети, связанной с регистратором, генерирующим ответ.

Сценарий

In this scenario, we have a "home network" containing routing proxy P2, registrar R, home service proxy HSP, and database DBMS used by both R and HSP. P2 represents the "edge" of the home network from a SIP perspective, and might be called an "edge proxy". UA1 is an external UA behind proxy P1. UA1 discovers P1 via Dynamic Host Configuration Protocol (DHCP) (this is just an example, and other mechanisms besides DHCP are possible). UA2 is another UA on the Internet, and does not use a default outbound proxy. We do not show Domain Name System (DNS) elements in this diagram, but will assume their reasonable availability in the discussion. The mission is for UA1 to discover HSP so that outbound requests from UA1 may be routed (at the discretion of UA1) through HSP, thereby receiving outbound services from HSP.
В этом сценарии у нас есть «домашняя сеть», содержащая прокси маршрутизации P2, регистратор R, домашний прокси HSP и СУБД базы данных, используемую как R, так и HSP. P2 представляет собой «edge» домашней сети с точки зрения SIP и может называться «граничным прокси». UA1 — это внешний UA за прокси P1. UA1 обнаруживает P1 через протокол динамической конфигурации хоста (DHCP) (это всего лишь пример, возможны и другие механизмы, помимо DHCP). UA2 — это еще один UA в Интернете, который не использует исходящий прокси по умолчанию. Мы не показываем элементы системы доменных имен (DNS) на этой схеме, но при обсуждении будем предполагать их разумную доступность. Задача UA1 состоит в том, чтобы обнаружить HSP, чтобы исходящие запросы от UA1 могли маршрутизироваться (по усмотрению UA1) через HSP, тем самым получая исходящие услуги от HSP.
3. Discussion of Mechanism
3. Обсуждение механизма
UAs may include a Route header field in an initial request to force that request to visit and potentially be serviced by one or more proxies. Using such a route (called a "service route" or "preloaded route") allows a UA to request services from a specific home proxy or network of proxies. The open question is, "How may a UA discover what service route to use?"
UA могут включать поле заголовка Route в первоначальный запрос, чтобы заставить этот запрос посетить и потенциально обслуживаться одним или несколькими прокси. Использование такого маршрута (называемого «сервисным маршрутом» или «предварительно загруженным маршрутом») позволяет UA запрашивать услуги у определенного домашнего прокси или сети прокси. Открытым остается вопрос: «Как UA может определить, какой маршрут обслуживания использовать?»
This document defines a header field called "Service-Route" which can contain a route vector that, if used as discussed above, will direct requests through a specific sequence of proxies. A registrar may use a Service-Route header field to inform a UA of a service route that, if used by the UA, will provide services from a proxy or set of proxies associated with that registrar. The Service-Route header field may be included by a registrar in the response to a REGISTER request. Consequently, a registering UA learns of a service route that may be used to request services from the system it just registered with.
Этот документ определяет поле заголовка под названием «Service-Route», которое может содержать вектор маршрута, который, если его использовать, как описано выше, будет направлять запросы через определенную последовательность прокси. Регистратор может использовать поле заголовка Service-Route для информирования UA о маршруте обслуживания, который, если он используется UA, будет предоставлять услуги от прокси или набора прокси, связанных с этим регистратором. Поле заголовка Service-Route может быть включено регистратором в ответ на запрос REGISTER. Следовательно, регистрирующийся UA узнает о маршруте обслуживания, который может использоваться для запроса услуг из системы, в которой он только что зарегистрировался.
The routing established by the Service-Route mechanism applies only to requests originating in the user agent. That is, it applies only to UA originated requests, and not to requests terminated by that UA.
Маршрутизация, установленная механизмом Service-Route применяется только к запросам, исходящим от пользовательского агента. То есть это применимо только к запросам, исходящим от UA, а не к запросам, завершенным этим UA.
Simply put, the registrar generates a service route for the registering UA and returns it in the response to each successful REGISTER request. This service route has the form of a Route header field that the registering UA may use to send requests through the service proxy selected by the registrar. The UA would use this route by inserting it as a preloaded Route header field in requests originated by the UA intended for routing through the service proxy.
Проще говоря, регистратор генерирует маршрут обслуживания для регистрирующего UA и возвращает его в ответ на каждый успешный запрос REGISTER. Этот маршрут службы имеет форму поля заголовка Route, которое регистрирующий UA может использовать для отправки запросов через прокси службы, выбранный регистратором. UA будет использовать этот маршрут, вставляя его в качестве предварительно загруженного поля заголовка Route в запросы, исходящие от UA, предназначенные для маршрутизации через прокси службы.
The mechanism by which the registrar constructs the header field value is specific to the local implementation and outside the scope of this document.
Механизм, с помощью которого регистратор создает значение поля заголовка, зависит от локальной реализации и выходит за рамки данного документа.
4. Applicability Statement
4. Заявление о применимости
The Service-Route mechanism is applicable when:
Механизм Service-Route применим, когда:
1. The UA registers with a registrar.
1. UA регистрируется у регистратора.
2. The registrar has knowledge of a service proxy that should be used by the UA when requesting services from the domain of the registrar. This knowledge may be a result of dynamic assignment or some other mechanism outside the scope of this document.
2. Регистратору известен сервисный прокси, который должен использоваться UA при запросе услуг из домена регистратора. Эти знания могут быть результатом динамического присвоения или какого-либо другого механизма, выходящего за рамки этого документа.
3. The registrar(s) has/have sufficient knowledge of the network topology, policy, and situation such that a reasonable service route can be constructed.
3. Регистратор(ы) обладает достаточными знаниями о топологии сети, политике и ситуации, чтобы можно было построить разумный маршрут обслуживания.
4. The service route constructed by the registrar is the same for all contacts associated with a single address-of-record. This mechanism does not provide for contact-specific service routes.
4. Маршрут обслуживания, построенный регистратором, одинаков для всех контактов, связанных с одним адресом записи. Этот механизм не предусматривает маршрутов обслуживания для конкретных контактов.
5. Other mechanisms for proposing a service route to the UA are not available or are inappropriate for use within the specific environment.
5. Другие механизмы предложения маршрута обслуживания UA недоступны или не подходят для использования в конкретной среде.
Other methods may also be available by which a UA may be informed of a service route. Such alternative methods are outside the scope of this document. Discussion of why one might wish to assign a service route during registration or when it might be appropriate to do so is outside the scope of this document.
Также могут быть доступны другие методы, с помощью которых UA может быть проинформирован о маршруте обслуживания. Такие альтернативные методы выходят за рамки данного документа. Обсуждение того, почему может потребоваться назначить маршрут обслуживания во время регистрации или когда это может быть целесообразно, выходит за рамки этого документа.

6. Usage
6. Использование
6.1. Procedures at the UA
6.1. Процедуры в UA
The UA performs a registration as usual. The REGISTER response may contain a Service-Route header field. If so, the UA MAY store the value of the Service-Route header field in an association with the address-of-record for which the REGISTER transaction had registered a contact. If the UA supports multiple addresses-of-record, it may be able to store multiple service routes, one per address-of-record. If the UA refreshes the registration, the stored value of the Service- Route is updated according to the Service-Route header field of the latest 200 class response. If there is no Service-Route header field in the response, the UA clears any service route for that address- of-record previously stored by the UA. If the re-registration request is refused or if an existing registration expires and the UA chooses not to re-register, the UA SHOULD discard any stored service route for that address-of-record.
UA выполняет регистрацию как обычно. Ответ REGISTER может содержать поле заголовка Service-Route. Если да, то UA МОЖЕТ сохранить значение поля заголовка Service-Route в ассоциации с адресом записи, для которого транзакция REGISTER зарегистрировала контакт. Если UA поддерживает несколько адресов записи, он может иметь возможность хранить несколько маршрутов обслуживания, по одному на каждый адрес записи. Если UA обновляет регистрацию, сохраненное значение Service-Route обновляется в соответствии с полем заголовка Service-Route последнего ответа класса 200. Если в ответе нет поля заголовка Service-Route, UA очищает любой маршрут обслуживания для этого адреса записи, ранее сохраненного UA. Если запрос на перерегистрацию отклонен или если срок действия существующей регистрации истек, и UA решает не перерегистрироваться, UA СЛЕДУЕТ отменить любой сохраненный маршрут обслуживания для этого адреса записи.
The UA MAY choose to exercise a service route for future requests associated with a given address-of-record for which a service route is known. If so, it uses the content of the Service-Route header field as a preloaded Route header field in outgoing initial requests [3]. The UA MUST preserve the order, in case there is more than one Service-Route header field or header field value.
UA МОЖЕТ выбрать использование маршрута обслуживания для будущих запросов, связанных с данным адресом записи, для которого известен маршрут обслуживания. Если да, то он использует содержимое поля заголовка Service-Route в качестве предварительно загруженного поля заголовка Route в исходящих первоначальных запросах [3]. UA ДОЛЖЕН сохранять порядок в случае, если имеется более одного поля заголовка Service-Route или значения поля заголовка.
Loose routes may interact with routing policy in interesting ways. The specifics of how the service route set integrates with any locally required default route and local policy are implementation dependent. For example, some devices will use locally-configured explicit loose routing to reach a next-hop proxy, and others will use a default outbound-proxy routing rule. However, for the result to function, the combination MUST provide valid routing in the local environment. In general, the service route set is appended to any locally configured route needed to egress the access proxy chain. Systems designers must match the service routing policy of their nodes with the basic SIP routing policy in order to get a workable system.
Свободные маршруты могут интересным образом взаимодействовать с политикой маршрутизации. Особенности интеграции набора маршрутов службы с любым локальным маршрутом по умолчанию и локальной политикой зависят от реализации. Например, некоторые устройства будут использовать локально настроенную явную свободную маршрутизацию для достижения прокси следующего перехода, а другие будут использовать правило маршрутизации исходящего прокси по умолчанию. Однако для того, чтобы результат работал, комбинация ДОЛЖНА обеспечивать действительную маршрутизацию в локальной среде. Как правило, набор маршрутов службы добавляется к любому локально настроенному маршруту, необходимому для выхода из цепочки прокси доступа. Проектировщики систем должны согласовать политику маршрутизации услуг своих узлов с базовой политикой маршрутизации SIP, чтобы получить работоспособную систему.
6.2. Procedures at the Proxy
6.2. Процедуры у прокси
The Service-Route header field is generally treated like any other unknown header field by intermediate proxies. They simply forward it on towards the destination. Note that, as usual, intermediate proxies that need to be traversed by future requests within a dialog may record-route. Proxies should not assume that they will be traversed by future requests in a dialog simply because they appear in the Service-Route header field. There is a question of whether proxies processing a REGISTER response may add themselves to the route set in the Service-Route header field. While this would enable dynamic construction of service routes, it has two significant problems. The first is one of transparency, as seen by the registrar: Intermediate proxies could add themselves without the knowledge or consent of the registrar. The second problem is interaction with end-to-end security. If the registrar uses S/MIME techniques to protect the REGISTER response, such additions would be visible to the UA as "man in the middle" alterations in the response. Consequently, intermediate proxies SHOULD NOT alter the value of Service-Route in REGISTER responses, and if they do, the UA MUST NOT be required to accept the alteration.
Поле заголовка Service-Route обычно обрабатывается промежуточными прокси как любое другое неизвестное поле заголовка. Они просто пересылают его по направлению к месту назначения. Обратите внимание, что, как обычно, промежуточные прокси, через которые будут проходить будущие запросы в диалоге, могут записывать маршрут. Прокси не должны предполагать, что они будут пройдены будущими запросами в диалоге просто потому, что они появляются в поле заголовка Service-Route. Возникает вопрос, могут ли прокси, обрабатывающие ответ REGISTER, добавлять себя к маршруту, установленному в поле заголовка Service-Route. Хотя это позволит динамично строить маршруты обслуживания, у этого есть две существенные проблемы. Первый — это прозрачность с точки зрения регистратора: промежуточные прокси могут добавляться без ведома или согласия регистратора. Вторая проблема — взаимодействие со сквозной безопасностью. Если регистратор использует методы S/MIME для защиты ответа REGISTER, такие дополнения будут видны UA как изменения «человек посередине» в ответе. Следовательно, промежуточные прокси НЕ ДОЛЖНЫ изменять значение Service-Route в ответах REGISTER, и если они это делают, UA НЕ ДОЛЖЕН быть обязан принимать это изменение.
Additional considerations apply if a proxy is "dual homed", meaning connected to two (or more) different networks such that requests are received on one interface and proxied out through another network interface. Proxies implementing multi-homing precisely as documented in [3] record-route a request with the sending interface. When processing the reply, they replace the Record-Route header field value that represents the interface onto which they proxied the request with a new value that represents the interface onto which they will proxy the response. Consequently, the route vector seen at the User Agent Server (UAS) is not the exact inverse of the route vector seen at the User Agent Client (UAC). While in itself harmless, this complicates matters for nodes that use the recorded route vector (or recorded Path vector as per [4]) in the determination of a service route for future use.
Дополнительные соображения применимы, если прокси является «двойным», то есть подключенным к двум (или более) различным сетям, так что запросы принимаются на одном интерфейсе и передаются через другой сетевой интерфейс. Прокси, реализующие множественную адресацию точно так, как описано в [3], записывают запрос с отправляющим интерфейсом. При обработке ответа они заменяют значение поля заголовка Record-Route, представляющее интерфейс, на который они перенаправили запрос, на новое значение, представляющее интерфейс, на который они передадут ответ. Следовательно, вектор маршрута, видимый на сервере пользовательского агента (UAS), не является точной инверсией вектора маршрута, видимого на клиенте пользовательского агента (UAC). Хотя само по себе это безвредно, это усложняет ситуацию для узлов, которые используют записанный вектор маршрута (или записанный вектор пути согласно [4]) при определении маршрута обслуживания для будущего использования.
Instead of following the procedure in [3], proxies used with Service-Route that are inserting Record-Route or Path header field values SHOULD record not one but two route values when processing the request. The first value recorded indicates the receiving interface, and the second indicates the sending interface. When processing the response, no modification of the recorded route is required. This optimization provides for fully invertible routes that can be effectively used in construction of service routes.
Вместо следования процедуре, описанной в [3], прокси, используемые с Service-Route и вставляющие значения полей заголовка Record-Route или Path, ДОЛЖНЫ записывать не одно, а два значения маршрута при обработке запроса. Первое записанное значение указывает интерфейс приема, а второе — интерфейс отправки. При обработке ответа модификация записанного маршрута не требуется. Такая оптимизация обеспечивает полностью обратимые маршруты, которые можно эффективно использовать при построении сервисных маршрутов.
6.3. Procedures at the Registrar
6.3. Процедуры в Регистраторе
When a registrar receives a successful REGISTER request, it MAY choose to return one or more Service-Route header field(s) in the 200 class response. The determination(s) of whether to include these header fields(s) into the 200 class response and what value(s) to insert are a matter of local policy and outside the scope of this document. Having inserted a Service-Route header field or fields, the registrar returns the 200 class response to the UA in accordance with standard procedures.
Когда регистратор получает успешный запрос REGISTER, он МОЖЕТ вернуть одно или несколько полей заголовка Service-Route в ответе класса 200. Определение(я) того, включать ли эти поля заголовка в ответ класса 200 и какое значение(я) вставлять, является вопросом местной политики и выходит за рамки этого документа. Вставив поле или поля заголовка Service-Route, регистратор возвращает UA ответ класса 200 в соответствии со стандартными процедурами.
A REGISTER operation performing a Fetching Bindings (i.e., no Contact header field is present in the request) SHOULD return the same value of Service-Route as returned in the corresponding previous REGISTER response for the address-of-record in question. In some cases, the Service-Route may be dynamically calculated by the registrar rather than stored, and the decision as to whether this route should be recalculated in the event of a Fetching Bindings operation is left to the implementation.
Операция REGISTER, выполняющая выборку привязок (то есть, в запросе нет поля заголовка Contact) ДОЛЖНА возвращать то же значение Service-Route, которое было возвращено в соответствующем предыдущем ответе REGISTER для рассматриваемого адреса записи. В некоторых случаях Service-Route может динамически рассчитываться регистратором, а не сохраняться, и решение о том, следует ли пересчитывать этот маршрут в случае операции извлечения привязок, остается на усмотрение реализации.
Note: A Fetching Bindings operation could be used by the UA to recover a lost value of Service-Route. Alternatively, a UA in this situation could just re-REGISTER.
Примечание. Операция выборки привязок может использоваться UA для восстановления потерянного значения Service-Route. В качестве альтернативы UA в этой ситуации может просто ПЕРЕРЕГИСТРИРОВАТЬСЯ.
Certain network topologies MAY require a specific proxy (e.g., firewall proxy) to be traversed before the home service proxy. Thus, a registrar with specific knowledge of the network topology MAY return more than one Service-Route header field or element in the 200 class response; the order is specified as top-down, meaning the topmost Service-Route entry will be visited first. Such constructions are implementation specific and outside the scope of this document.
Определенные сетевые топологии МОГУТ требовать прохождения определенного прокси (например, прокси межсетевого экрана) перед прокси домашней службы. Таким образом, регистратор, обладающий конкретными знаниями топологии сети, МОЖЕТ вернуть более одного поля или элемента заголовка Service-Route в ответе класса 200; порядок указан сверху вниз, что означает, что самая верхняя запись Service-Route будет посещена первой. Такие конструкции зависят от реализации и выходят за рамки этого документа.
In general, the Service-Route header field contains references to elements strictly within the administrative domain of the registrar and home service proxy. For example, consider a case where a user leaves the "home" network and roams into a "visited" network. The registrar cannot be assumed to have knowledge of the topology of the visited network, so the Service-Route it returns contains elements only within the home network.
Как правило, поле заголовка Service-Route содержит ссылки на элементы строго внутри административного домена регистратора и прокси домашней службы. Например, рассмотрим случай, когда пользователь покидает сеть «home» и переходит в сеть «visited». Нельзя предполагать, что регистратор знает топологию посещаемой сети, поэтому возвращаемый им Service-Route содержит элементы только внутри домашней сети.
Note that the inserted Service-Route element(s) MUST conform to the syntax of a Route element as defined in [3]. As suggested therein, such route elements MUST include the loose-routing indicator parameter ";lr" for full compliance with [3].
Обратите внимание, что вставленные элементы Service-Route ДОЛЖНЫ соответствовать синтаксису элемента маршрута, как определено в [3]. Как предложено там, такие элементы маршрута ДОЛЖНЫ включать параметр индикатора свободной маршрутизации «;lr» для полного соответствия [3].

7. Security Considerations
7. Вопросы безопасности
It is possible for proxies between the UA and the registrar during the REGISTER transaction to modify the value of Service-Route returned by the registrar, or to insert a Service-Route even when one was not returned by the registrar. The consequence of such an attack is that future requests made by the UA using the service route might be diverted to or through a node other than would normally be visited. It is also possible for proxies on the INVITE path to execute many different attacks. It is therefore desirable to apply transitive mutual authentication using sips: or other available mechanisms in order to prevent such attacks.
Прокси между UA и регистратором во время транзакции REGISTER могут изменять значение Service-Route, возвращенное регистратором, или вставлять Service-Route, даже если оно не было возвращено регистратором. Последствием такой атаки является то, что будущие запросы, сделанные UA, использующим сервисный маршрут, могут быть перенаправлены на узел или через него, отличный от узла, который обычно посещается. Прокси на пути INVITE также могут выполнять множество различных атак. Поэтому желательно применять транзитивную взаимную аутентификацию с использованием sips: или других доступных механизмов, чтобы предотвратить такие атаки.
The "sips:" URI as defined in [3] defines a mechanism by which a UA may request transport-level message integrity and mutual authentication. Since there is no requirement for proxies to modify messages, S/MIME signed bodies may be used to provide end-to-end protection for the returned value.
URI «sips:», как определено в [3], определяет механизм, с помощью которого UA может запрашивать целостность сообщения на транспортном уровне и взаимную аутентификацию. Поскольку прокси не требуется изменять сообщения, подписанные тела S/MIME могут использоваться для обеспечения сквозной защиты возвращаемого значения.
Systems using Service-Route SHOULD provide hop-by-hop message integrity and mutual authentication. UAs SHOULD request this support by using a "sips:" URI. Registrars returning a Service-Route MUST implement end-to-end protection using S/MIME and SHOULD use S/MIME to protect all such responses. UAs receiving Service-Route SHOULD authenticate attached S/MIME bodies if present.
Системы, использующие Service-Route ДОЛЖНЫ обеспечивать поэтапную целостность сообщений и взаимную аутентификацию. UA ДОЛЖНЫ запрашивать эту поддержку, используя URI «sips:». Регистраторы, возвращающие Service-Route ДОЛЖНЫ реализовать сквозную защиту с использованием S/MIME, и ДОЛЖНЫ использовать S/MIME для защиты всех таких ответов. UA, получающие Service-Route ДОЛЖНЫ аутентифицировать прикрепленные тела S/MIME, если они присутствуют.
