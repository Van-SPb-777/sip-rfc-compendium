Abstract
Аннотация
The WebSocket protocol enables two-way real-time communication between clients and servers in web-based applications. This document specifies a WebSocket subprotocol as a reliable transport mechanism between Session Initiation Protocol (SIP) entities to enable use of SIP in web-oriented deployments.
Протокол WebSocket обеспечивает двустороннюю связь в реальном времени между клиентами и серверами в веб-приложениях. Настоящий документ определяет подпротокол WebSocket как надёжный транспортный механизм между объектами протокола инициирования сессий (SIP), позволяющий использовать SIP в веб-ориентированных развёртываниях.

1. Introduction
1. Введение
The WebSocket protocol [RFC6455] enables message exchange between clients and servers on top of a persistent TCP connection (optionally secured with Transport Layer Security (TLS) [RFC5246]). The initial protocol handshake makes use of HTTP [RFC2616] semantics, allowing the WebSocket protocol to reuse existing HTTP infrastructure.
Протокол WebSocket [RFC6455] обеспечивает обмен сообщениями между клиентами и серверами поверх постоянного TCP-соединения (необязательно защищённого с помощью Transport Layer Security (TLS) [RFC5246]). Начальное рукопожатие протокола использует семантику HTTP [RFC2616], что позволяет протоколу WebSocket повторно использовать существующую инфраструктуру HTTP.
Modern web browsers include a WebSocket client stack complying with the WebSocket API [WS-API] as specified by the W3C. It is expected that other client applications (those running in personal computers and devices such as smartphones) will also make a WebSocket client stack available. The specification in this document enables use of SIP in these scenarios.
Современные веб-браузеры включают стек клиента WebSocket, совместимый с WebSocket API [WS-API] в соответствии со спецификацией W3C. Ожидается, что другие клиентские приложения (работающие на персональных компьютерах и устройствах, таких как смартфоны) также предоставят стек клиента WebSocket. Спецификация в настоящем документе позволяет использовать SIP в этих сценариях.
This specification defines a WebSocket subprotocol (as defined in Section 1.9 of [RFC6455]) for transporting SIP messages between a WebSocket client and server, a reliable and message-boundary- preserving transport for SIP, and DNS Naming Authority Pointer (NAPTR) [RFC3403] service values and procedures for SIP entities implementing the WebSocket transport. Media transport is out of the scope of this document.
Настоящая спецификация определяет подпротокол WebSocket (как определено в разделе 1.9 [RFC6455]) для транспортировки сообщений SIP между клиентом и сервером WebSocket, надёжный транспорт для SIP с сохранением границ сообщений, а также значения служб DNS Naming Authority Pointer (NAPTR) [RFC3403] и процедуры для объектов SIP, реализующих транспорт WebSocket. Транспорт медиа выходит за рамки настоящего документа.
Section 3 in this specification relaxes the requirement in [RFC3261] by which the SIP server transport MUST add a "received" parameter in the top Via header in certain circumstances.
Раздел 3 настоящей спецификации ослабляет требование [RFC3261], согласно которому транспорт SIP-сервера ДОЛЖЕН добавлять параметр «received» в верхнее поле заголовка Via в определённых обстоятельствах.

2.1. Definitions
2.1. Определения
SIP WebSocket Client: A SIP entity capable of opening outbound connections to WebSocket servers and communicating using the WebSocket SIP subprotocol as defined by this document.
Клиент SIP WebSocket: объект SIP, способный открывать исходящие соединения с серверами WebSocket и взаимодействовать с использованием подпротокола WebSocket SIP, определённого в настоящем документе.
SIP WebSocket Server: A SIP entity capable of listening for inbound connections from WebSocket clients and communicating using the WebSocket SIP subprotocol as defined by this document.
Сервер SIP WebSocket: объект SIP, способный прослушивать входящие соединения от клиентов WebSocket и взаимодействовать с использованием подпротокола WebSocket SIP, определённого в настоящем документе.
3. The WebSocket Protocol
3. Протокол WebSocket
The WebSocket protocol [RFC6455] is a transport layer on top of TCP (optionally secured with TLS [RFC5246]) in which both client and server exchange message units in both directions. The protocol defines a connection handshake, WebSocket subprotocol and extensions negotiation, a frame format for sending application and control data, a masking mechanism, and status codes for indicating disconnection causes.
Протокол WebSocket [RFC6455] — это транспортный уровень поверх TCP (необязательно защищённый с помощью TLS [RFC5246]), в котором и клиент, и сервер обмениваются единицами сообщений в обоих направлениях. Протокол определяет рукопожатие соединения, согласование подпротокола WebSocket и расширений, формат кадра для отправки прикладных и управляющих данных, механизм маскирования и коды состояния для указания причин разрыва соединения.
The WebSocket connection handshake is based on HTTP [RFC2616] and utilizes the HTTP GET method with an "Upgrade" request. This is sent by the client and then answered by the server (if the negotiation succeeded) with an HTTP 101 status code. Once the handshake is completed, the connection upgrades from HTTP to the WebSocket protocol. This handshake procedure is designed to reuse the existing HTTP infrastructure. During the connection handshake, the client and server agree on the application protocol to use on top of the WebSocket transport. Such an application protocol (also known as a "WebSocket subprotocol") defines the format and semantics of the messages exchanged by the endpoints. This could be a custom protocol or a standardized one (as defined by the WebSocket SIP subprotocol in this document). Once the HTTP 101 response is processed, both the client and server reuse the underlying TCP connection for sending WebSocket messages and control frames to each other. Unlike plain HTTP, this connection is persistent and can be used for multiple message exchanges.
Рукопожатие соединения WebSocket основано на HTTP [RFC2616] и использует метод HTTP GET с запросом «Upgrade». Он отправляется клиентом, а затем подтверждается сервером (если согласование прошло успешно) кодом состояния HTTP 101. После завершения рукопожатия соединение переходит от HTTP к протоколу WebSocket. Эта процедура рукопожатия предназначена для повторного использования существующей инфраструктуры HTTP. Во время рукопожатия соединения клиент и сервер договариваются о прикладном протоколе, который будет использоваться поверх транспорта WebSocket. Такой прикладной протокол (также называемый «подпротоколом WebSocket») определяет формат и семантику сообщений, которыми обмениваются конечные точки. Это может быть пользовательский протокол или стандартизованный (как определено подпротоколом WebSocket SIP в настоящем документе). После обработки ответа HTTP 101 и клиент, и сервер повторно используют нижележащее TCP-соединение для отправки друг другу сообщений WebSocket и управляющих кадров. В отличие от обычного HTTP это соединение является постоянным и может использоваться для обмена несколькими сообщениями.
WebSocket defines message units to be used by applications for the exchange of data, so it provides a message-boundary-preserving transport layer. These message units can contain either UTF-8 text or binary data and can be split into multiple WebSocket text/binary transport frames as needed by the WebSocket stack.
WebSocket определяет единицы сообщений, используемые приложениями для обмена данными, поэтому он обеспечивает транспортный уровень с сохранением границ сообщений. Эти единицы сообщений могут содержать текст UTF-8 или двоичные данные и могут разбиваться на несколько кадров транспорта WebSocket (текстовых или двоичных) по мере необходимости для стека WebSocket.
The WebSocket API [WS-API] for web browsers only defines callbacks to be invoked upon receipt of an entire message unit, regardless of whether it was received in a single WebSocket frame or split across multiple frames.
WebSocket API [WS-API] для веб-браузеров определяет только обратные вызовы, которые должны вызываться при получении всей единицы сообщения, независимо от того, получена ли она в одном кадре WebSocket или разбита на несколько кадров.
4. The WebSocket SIP Subprotocol
4. Подпротокол WebSocket SIP
The term WebSocket subprotocol refers to an application-level protocol layered on top of a WebSocket connection. This document specifies the WebSocket SIP subprotocol for carrying SIP requests and responses through a WebSocket connection.
Термин «подпротокол WebSocket» обозначает протокол прикладного уровня, расположенный поверх соединения WebSocket. Настоящий документ определяет подпротокол WebSocket SIP для передачи запросов и ответов SIP через соединение WebSocket.
4.1. Handshake
4.1. Рукопожатие
The SIP WebSocket Client and SIP WebSocket Server negotiate usage of the WebSocket SIP subprotocol during the WebSocket handshake procedure as defined in Section 1.3 of [RFC6455]. The client MUST include the value "sip" in the Sec-WebSocket-Protocol header in its handshake request. The 101 reply from the server MUST contain "sip" in its corresponding Sec-WebSocket-Protocol header.
Клиент SIP WebSocket и сервер SIP WebSocket согласуют использование подпротокола WebSocket SIP во время процедуры рукопожатия WebSocket, как определено в разделе 1.3 [RFC6455]. Клиент ДОЛЖЕН включать значение «sip» в заголовок Sec-WebSocket-Protocol своего запроса рукопожатия. Ответ 101 от сервера ДОЛЖЕН содержать «sip» в соответствующем заголовке Sec-WebSocket-Protocol.
The WebSocket client initiates a WebSocket connection when attempting to send a SIP request (unless there is an already established WebSocket connection for sending the SIP request). In case there is no HTTP 101 response during the WebSocket handshake, it is considered a transaction error as per [RFC3261], Section 8.1.3.1., "Transaction Layer Errors".
Клиент WebSocket инициирует соединение WebSocket при попытке отправить запрос SIP (если только нет уже установленного соединения WebSocket для отправки запроса SIP). Если во время рукопожатия WebSocket нет ответа HTTP 101, это считается ошибкой транзакции согласно [RFC3261], раздел 8.1.3.1., «Transaction Layer Errors».
Below is an example of a WebSocket handshake in which the client requests the WebSocket SIP subprotocol support from the server:
Ниже приведён пример рукопожатия WebSocket, в котором клиент запрашивает у сервера поддержку подпротокола WebSocket SIP:
GET / HTTP/1.1 Host: sip-ws.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Origin: http://www.example.com Sec-WebSocket-Protocol: sip Sec-WebSocket-Version: 13
GET / HTTP/1.1 Host: sip-ws.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Origin: http://www.example.com Sec-WebSocket-Protocol: sip Sec-WebSocket-Version: 13
The handshake response from the server accepting the WebSocket SIP subprotocol would look as follows:
Ответ рукопожатия от сервера, принимающего подпротокол WebSocket SIP, будет выглядеть следующим образом:
HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= Sec-WebSocket-Protocol: sip
HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= Sec-WebSocket-Protocol: sip
Once the negotiation has been completed, the WebSocket connection is established and can be used for the transport of SIP requests and responses. Messages other than SIP requests and responses MUST NOT be transmitted over this connection.
После завершения согласования соединение WebSocket установлено и может использоваться для транспортировки запросов и ответов SIP. Сообщения, отличные от запросов и ответов SIP, НЕ ДОЛЖНЫ передаваться по этому соединению.
4.2. SIP Encoding
4.2. Кодирование SIP
WebSocket messages can be transported in either UTF-8 text frames or binary frames. SIP [RFC3261] allows both text and binary bodies in SIP requests and responses. Therefore, SIP WebSocket Clients and SIP WebSocket Servers MUST accept both text and binary frames.
Сообщения WebSocket могут передаваться в текстовых кадрах UTF-8 или в двоичных кадрах. SIP [RFC3261] допускает как текстовые, так и двоичные тела в запросах и ответах SIP. Поэтому клиенты SIP WebSocket и серверы SIP WebSocket ДОЛЖНЫ принимать как текстовые, так и двоичные кадры.
If there is at least one non-UTF-8 symbol in the whole SIP message (including headers and the body), then the whole message MUST be sent within a WebSocket binary message. Given the nature of JavaScript and the WebSocket API, it is RECOMMENDED to use UTF-8 encoding (or ASCII, which is a subset of UTF-8) for SIP messages carried over a WebSocket connection.
Если в целом сообщении SIP (включая заголовки и тело) есть хотя бы один символ, отличный от UTF-8, то всё сообщение ДОЛЖНО быть отправлено в двоичном сообщении WebSocket. Учитывая природу JavaScript и WebSocket API, РЕКОМЕНДУЕТСЯ использовать кодировку UTF-8 (или ASCII, являющуюся подмножеством UTF-8) для сообщений SIP, передаваемых по соединению WebSocket.
5. SIP WebSocket Transport
5. Транспорт SIP WebSocket
WebSocket [RFC6455] is a reliable protocol; therefore, the SIP WebSocket subprotocol defined by this document is a reliable SIP transport. Thus, client and server transactions using WebSocket for transport MUST follow the procedures and timer values for reliable transports as defined in [RFC3261].
WebSocket [RFC6455] — надёжный протокол; поэтому подпротокол WebSocket SIP, определённый в настоящем документе, является надёжным транспортом SIP. Таким образом, клиентские и серверные транзакции, использующие WebSocket в качестве транспорта, ДОЛЖНЫ следовать процедурам и значениям таймеров для надёжных транспортов, как определено в [RFC3261].
Each SIP message MUST be carried within a single WebSocket message, and a WebSocket message MUST NOT contain more than one SIP message. Because the WebSocket transport preserves message boundaries, the use of the Content-Length header in SIP messages is not necessary when they are transported using the WebSocket subprotocol.
Каждое сообщение SIP ДОЛЖНО передаваться в пределах одного сообщения WebSocket, а сообщение WebSocket НЕ ДОЛЖНО содержать более одного сообщения SIP. Поскольку транспорт WebSocket сохраняет границы сообщений, использование заголовка Content-Length в сообщениях SIP не требуется, когда они передаются с использованием подпротокола WebSocket.
This simplifies the parsing of SIP messages for both clients and servers. There is no need to establish message boundaries using Content-Length headers between messages. Other SIP transports, such as UDP and the Stream Control Transmission Protocol (SCTP) [RFC4168], also provide this benefit.
Это упрощает разбор сообщений SIP как для клиентов, так и для серверов. Нет необходимости устанавливать границы сообщений с помощью заголовков Content-Length между сообщениями. Другие транспорты SIP, такие как UDP и Stream Control Transmission Protocol (SCTP) [RFC4168], также дают это преимущество.
5.1. Via Transport Parameter
5.1. Транспортный параметр Via
Via header fields in SIP messages carry a transport protocol identifier. This document defines the value "WS" to be used for requests over plain WebSocket connections and "WSS" for requests over secure WebSocket connections (in which the WebSocket connection is established using TLS [RFC5246] with TCP transport).
Поля заголовка Via в сообщениях SIP несут идентификатор транспортного протокола. Настоящий документ определяет значение «WS» для запросов по обычным соединениям WebSocket и «WSS» для запросов по защищённым соединениям WebSocket (в которых соединение WebSocket устанавливается с использованием TLS [RFC5246] поверх транспорта TCP).
The updated augmented BNF (Backus-Naur Form) [RFC5234] for this parameter is the following (the original BNF for this parameter can be found in [RFC3261], which was then updated by [RFC4168]):
Обновлённая расширенная форма Бэкуса — Наура (BNF) [RFC5234] для этого параметра приведена ниже (исходную BNF для этого параметра можно найти в [RFC3261], которая затем была обновлена в [RFC4168]):
transport =/ "WS" / "WSS"
transport =/ "WS" / "WSS"

5.2. Транспортный параметр SIP URI

Настоящий документ определяет значение «ws» как значение транспортного параметра SIP URI [RFC3986], с которым следует связываться, используя подпротокол WebSocket SIP в качестве транспорта.
The updated augmented BNF for this parameter is the following (the original BNF for this parameter can be found in [RFC3261]):
Обновлённая расширенная BNF для этого параметра приведена ниже (исходную BNF для этого параметра можно найти в [RFC3261]):
transport-param =/ "transport=" "ws"
transport-param =/ "transport=" "ws"
5.3. Via "received" Parameter
5.3. Параметр «received» в Via
The following is stated in [RFC3261], Section 18.2.1, "Receiving Requests":
В [RFC3261], раздел 18.2.1, «Receiving Requests», сказано:
When the server transport receives a request over any transport, it MUST examine the value of the "sent-by" parameter in the top Via header field value. If the host portion of the "sent-by" field contains a domain name, or if it contains an IP address that differs from the packet source address, the server MUST add a "received" parameter to that Via header field value. This parameter MUST contain the source address from which the packet was received.
когда транспорт сервера получает запрос по любому транспорту, он ДОЛЖЕН проверить значение параметра «sent-by» в значении верхнего поля заголовка Via. Если часть «sent-by», обозначающая хост, содержит доменное имя или если она содержит IP-адрес, отличающийся от адреса источника пакета, сервер ДОЛЖЕН добавить параметр «received» к значению этого поля заголовка Via. Этот параметр ДОЛЖЕН содержать адрес источника, с которого был получен пакет.
The requirement of adding the "received" parameter does not fit well into the WebSocket protocol design. The WebSocket connection handshake reuses the existing HTTP infrastructure in which there could be an unknown number of HTTP proxies and/or TCP load balancers between the SIP WebSocket Client and Server, so the source address the server would write into the Via "received" parameter would be the address of the HTTP/TCP intermediary in front of it. This could reveal sensitive information about the internal topology of the server's network to the client.
Требование добавления параметра «received» плохо вписывается в устройство протокола WebSocket. Рукопожатие соединения WebSocket повторно использует существующую инфраструктуру HTTP, в которой между клиентом и сервером SIP WebSocket может быть неизвестное число прокси HTTP и (или) балансировщиков нагрузки TCP, поэтому адрес источника, который сервер записал бы в параметр «received» поля Via, был бы адресом промежуточного узла HTTP/TCP перед ним. Это могло бы раскрыть клиенту конфиденциальную информацию о внутренней топологии сети сервера.
Given the fact that SIP responses can only be sent over the existing WebSocket connection, the Via "received" parameter is of little use. Therefore, in order to allow hiding possible sensitive information about the SIP WebSocket Server's network, this document updates [RFC3261], Section 18.2.1 by stating:
Учитывая тот факт, что ответы SIP могут отправляться только по существующему соединению WebSocket, параметр «received» поля Via малополезен. Поэтому, чтобы позволить скрыть возможную конфиденциальную информацию о сети сервера SIP WebSocket, настоящий документ обновляет [RFC3261], раздел 18.2.1, указывая:
When a SIP WebSocket Server receives a request, it MAY decide not to add a "received" parameter to the top Via header. Therefore, SIP WebSocket Clients MUST accept responses without such a parameter in the top Via header regardless of whether the Via "sent-by" field contains a domain name.
когда сервер SIP WebSocket получает запрос, он МОЖЕТ решить не добавлять параметр «received» в верхнее поле Via. Поэтому клиенты SIP WebSocket ДОЛЖНЫ принимать ответы без такого параметра в верхнем поле Via независимо от того, содержит ли поле «sent-by» поля Via доменное имя.
5.4. SIP Transport Implementation Requirements
5.4. Требования к реализации транспорта SIP
The following is stated in [RFC3261], Section 18, "Transport":
В [RFC3261], раздел 18, «Transport», сказано:
All SIP elements MUST implement UDP and TCP. SIP elements MAY implement other protocols.
Все элементы SIP ДОЛЖНЫ реализовывать UDP и TCP. Элементы SIP МОГУТ реализовывать другие протоколы.
The specification of this transport enables SIP to be used as a session establishment protocol in scenarios where none of the other transport protocols defined for SIP can be used. Since some environments do not enable SIP elements to use UDP and TCP as SIP transport protocols, a SIP element acting as a SIP WebSocket Client is not mandated to implement support of UDP and TCP.
Спецификация этого транспорта позволяет использовать SIP как протокол установления сессий в сценариях, где не может использоваться ни один из других транспортных протоколов, определённых для SIP. Поскольку в некоторых средах элементы SIP не имеют возможности использовать UDP и TCP в качестве транспортных протоколов SIP, элемент SIP, действующий как клиент SIP WebSocket, не обязан реализовывать поддержку UDP и TCP.
5.5. Locating a SIP Server
5.5. Поиск SIP-сервера
[RFC3263] specifies the procedures that should be followed by SIP entities for locating SIP servers. This specification defines the NAPTR service value "SIP+D2W" for SIP WebSocket Servers that support plain WebSocket connections and "SIPS+D2W" for SIP WebSocket Servers that support secure WebSocket connections.
[RFC3263] определяет процедуры, которых должны придерживаться объекты SIP при поиске SIP-серверов. Настоящая спецификация определяет значение службы NAPTR «SIP+D2W» для серверов SIP WebSocket, поддерживающих обычные соединения WebSocket, и «SIPS+D2W» для серверов SIP WebSocket, поддерживающих защищённые соединения WebSocket.
At the time this document was written, DNS NAPTR/Service Record (SRV) queries could not be performed by commonly available WebSocket client stacks (in JavaScript engines and web browsers).
На момент написания настоящего документа широко доступные стеки клиента WebSocket (в движках JavaScript и веб-браузерах) не могли выполнять запросы DNS NAPTR/Service Record (SRV).
In the absence of DNS SRV resource records or an explicit port, the default port for a SIP URI using the "sip" scheme and the "ws" transport parameter is 80, and the default port for a SIP URI using the "sips" scheme and the "ws" transport parameter is 443.
При отсутствии записей ресурсов DNS SRV или явно указанного порта порт по умолчанию для SIP URI со схемой «sip» и транспортным параметром «ws» равен 80, а порт по умолчанию для SIP URI со схемой «sips» и транспортным параметром «ws» равен 443.
6. Connection Keep-Alive
6. Поддержание соединения
SIP WebSocket Clients and Servers may keep their WebSocket connections open by sending periodic WebSocket "Ping" frames as described in [RFC6455], Section 5.5.2.
Клиенты и серверы SIP WebSocket могут поддерживать свои соединения WebSocket открытыми, отправляя периодические кадры WebSocket «Ping», как описано в [RFC6455], раздел 5.5.2.
The WebSocket API [WS-API] does not provide a mechanism for applications running in a web browser to control whether or not periodic WebSocket "Ping" frames are sent to the server. The implementation of such a keep-alive feature is the decision of each web browser manufacturer and may also depend on the configuration of the web browser.
WebSocket API [WS-API] не предоставляет приложениям, работающим в веб-браузере, механизма управления тем, отправляются ли периодические кадры WebSocket «Ping» на сервер. Реализация такого механизма поддержания соединения — решение каждого производителя веб-браузера и может также зависеть от конфигурации веб-браузера.
The indication and use of the CRLF NAT keep-alive mechanism defined for SIP connection-oriented transports in [RFC5626], Section 3.5.1 or [RFC6223] are, of course, usable over the transport defined in this specification.
Указание и использование механизма поддержания соединения CRLF NAT, определённого для ориентированных на соединение транспортов SIP в [RFC5626], раздел 3.5.1, или в [RFC6223], конечно, применимы поверх транспорта, определённого в настоящей спецификации.
7. Authentication
7. Аутентификация
This section describes how authentication is achieved through the requirements in [RFC6455], [RFC6265], [RFC2617], and [RFC3261].
В этом разделе описывается, как достигается аутентификация с помощью требований [RFC6455], [RFC6265], [RFC2617] и [RFC3261].
The WebSocket protocol [RFC6455] does not define an authentication mechanism; instead, it exposes the following text in Section 10.5, "WebSocket Client Authentication": This protocol doesn't prescribe any particular way that servers can authenticate clients during the WebSocket handshake. The WebSocket server can use any client authentication mechanism available to a generic HTTP server, such as cookies, HTTP authentication, or TLS authentication.
Протокол WebSocket [RFC6455] не определяет механизм аутентификации; вместо этого в разделе 10.5, «WebSocket Client Authentication», он приводит следующий текст: этот протокол не предписывает какого-либо конкретного способа, которым серверы могут аутентифицировать клиентов во время рукопожатия WebSocket. Сервер WebSocket может использовать любой механизм аутентификации клиента, доступный обычному серверу HTTP, например cookie, аутентификацию HTTP или аутентификацию TLS.
The following list exposes mandatory-to-implement and optional mechanisms for SIP WebSocket Clients and Servers in order to get interoperability at the WebSocket authentication level:
Следующий список описывает обязательные и необязательные для реализации механизмы для клиентов и серверов SIP WebSocket, обеспечивающие совместимость на уровне аутентификации WebSocket:
o A SIP WebSocket Client MUST be ready to add a session cookie when it runs in a web browser (or behaves like a browser navigating a website) and has previously retrieved a session cookie from the web server whose URL domain matches the domain in the WebSocket URI. This mechanism is defined by [RFC6265].
o Клиент SIP WebSocket ДОЛЖЕН быть готов добавить сеансовый cookie, когда он работает в веб-браузере (или ведёт себя как браузер, просматривающий веб-сайт) и ранее получил сеансовый cookie от веб-сервера, домен URL которого совпадает с доменом в URI WebSocket. Этот механизм определён в [RFC6265].
o A SIP WebSocket Client MUST be ready to be challenged with an HTTP 401 status code [RFC2617] by the SIP WebSocket Server when performing the WebSocket handshake.
o Клиент SIP WebSocket ДОЛЖЕН быть готов к тому, что сервер SIP WebSocket запросит у него аутентификацию кодом состояния HTTP 401 [RFC2617] при выполнении рукопожатия WebSocket.
o A SIP WebSocket Client MAY use TLS client authentication (when in a secure WebSocket connection) as an optional authentication mechanism.
o Клиент SIP WebSocket МОЖЕТ использовать аутентификацию клиента TLS (при защищённом соединении WebSocket) в качестве необязательного механизма аутентификации.
Note, however, that TLS client authentication in the WebSocket protocol is governed by the rules of the HTTP protocol rather than the rules of SIP.
Однако учтите, что аутентификация клиента TLS в протоколе WebSocket регулируется правилами протокола HTTP, а не правилами SIP.
o A SIP WebSocket Server MUST be ready to read session cookies when present in the WebSocket handshake request and use such a cookie value for determining whether the WebSocket connection has been initiated by an HTTP client navigating a website in the same domain (or subdomain) as the SIP WebSocket Server.
o Сервер SIP WebSocket ДОЛЖЕН быть готов прочитать сеансовые cookie, если они присутствуют в запросе рукопожатия WebSocket, и использовать такое значение cookie для определения того, было ли соединение WebSocket инициировано клиентом HTTP, просматривающим веб-сайт в том же домене (или поддомене), что и сервер SIP WebSocket.
o A SIP WebSocket Server SHOULD be able to reject a WebSocket handshake request with an HTTP 401 status code by providing a Basic/Digest challenge as defined for the HTTP protocol.
o Сервер SIP WebSocket СЛЕДУЕТ уметь отклонять запрос рукопожатия WebSocket кодом состояния HTTP 401, предоставляя запрос аутентификации Basic/Digest, как определено для протокола HTTP.
Regardless of whether or not the SIP WebSocket Server requires authentication during the WebSocket handshake, authentication MAY be requested at the SIP level.
Независимо от того, требует ли сервер SIP WebSocket аутентификацию во время рукопожатия WebSocket, аутентификация МОЖЕТ быть запрошена на уровне SIP.
Some authentication use cases are exposed in Appendix A.
Некоторые варианты использования аутентификации описаны в приложении A.

9. Security Considerations
9. Вопросы безопасности
9.1. Secure WebSocket Connection
9.1. Защищённое соединение WebSocket
It is RECOMMENDED that the SIP traffic transported over a WebSocket communication be protected by using a secure WebSocket connection (using TLS [RFC5246] over TCP).
РЕКОМЕНДУЕТСЯ, чтобы трафик SIP, передаваемый по соединению WebSocket, защищался с использованием защищённого соединения WebSocket (с использованием TLS [RFC5246] поверх TCP).
When establishing a connection using SIP over secure WebSocket transport, the client MUST authenticate the server using the server's certificate according to the WebSocket validation procedure in [RFC6455].
При установке соединения с использованием SIP по защищённому транспорту WebSocket клиент ДОЛЖЕН аутентифицировать сервер с использованием сертификата сервера согласно процедуре проверки WebSocket в [RFC6455].
Server operators should note that this authentication procedure is different from the procedure for SIP domain certificates defined in [RFC5922]. Certificates that are appropriate for SIP over TLS over TCP will probably not be appropriate for SIP over secure WebSocket connections.
Операторам серверов следует учесть, что эта процедура аутентификации отличается от процедуры для сертификатов домена SIP, определённой в [RFC5922]. Сертификаты, пригодные для SIP по TLS поверх TCP, вероятно, не будут пригодны для SIP по защищённым соединениям WebSocket.
9.2. Usage of "sips" Scheme
9.2. Использование схемы «sips»
The "sips" scheme in a SIP URI dictates that the entire request path to the target be secure. If such a path includes a WebSocket connection, it MUST be a secure WebSocket connection.
Схема «sips» в SIP URI предписывает, что весь путь запроса к цели должен быть защищённым. Если такой путь включает соединение WebSocket, оно ДОЛЖНО быть защищённым соединением WebSocket.

Appendix A. Authentication Use Cases
Приложение A. Варианты использования аутентификации
The sections below briefly describe some SIP over WebSocket scenarios in which authentication takes place in different ways.
В разделах ниже кратко описаны некоторые сценарии SIP поверх WebSocket, в которых аутентификация выполняется разными способами.
A.1. Just SIP Authentication
A.1. Только аутентификация SIP
SIP Private Branch Exchange (PBX) model A implements the SIP WebSocket transport defined by this specification. Its implementation is 100% website agnostic as it does not share information with the web server providing the HTML code to browsers, meaning that the SIP WebSocket Server (here, PBX model A) has no knowledge about web login activity within the website.
SIP Private Branch Exchange (PBX) модель A реализует транспорт SIP WebSocket, определённый в настоящей спецификации. Её реализация на 100 % не зависит от веб-сайта, поскольку она не обменивается информацией с веб-сервером, предоставляющим браузерам код HTML; это означает, что сервер SIP WebSocket (здесь — PBX модель A) ничего не знает об активности входа на веб-сайте.
In this simple scenario, the SIP WebSocket Server does not inspect fields in the WebSocket handshake HTTP GET request such as the request URL, the Origin header value, the Host header value, or the Cookie header value (if present). However, some of those fields could be inspected for a minimal validation (i.e., PBX model A could require that the Origin header value contains a specific URL so just users navigating such a website would be able to establish a WebSocket connection with PBX model A).
В этом простом сценарии сервер SIP WebSocket не проверяет поля запроса HTTP GET рукопожатия WebSocket, такие как URL запроса, значение заголовка Origin, значение заголовка Host или значение заголовка Cookie (если он присутствует). Однако некоторые из этих полей можно проверить для минимальной валидации (т. е. PBX модель A могла бы требовать, чтобы значение заголовка Origin содержало конкретный URL, чтобы только пользователи, просматривающие такой веб-сайт, могли установить соединение WebSocket с PBX моделью A).
Once the WebSocket connection has been established, SIP authentication is requested by PBX model A for each SIP request coming over that connection. Therefore, SIP WebSocket Clients must be provisioned with their corresponding SIP password.
После установления соединения WebSocket PBX модель A запрашивает аутентификацию SIP для каждого запроса SIP, поступающего по этому соединению. Поэтому клиенты SIP WebSocket должны быть обеспечены соответствующим паролем SIP.
A.2. Just Web Authentication
A.2. Только веб-аутентификация
A SIP-to-PSTN (Public Switched Telephone Network) provider offers telephony service for clients logged into its website. The provider does not want to expose SIP passwords into the web for security/ privacy reasons.
Поставщик услуг SIP-to-PSTN (Public Switched Telephone Network) предлагает телефонную услугу клиентам, вошедшим на его веб-сайт. Поставщик не хочет раскрывать пароли SIP в веб-сети по соображениям безопасности и конфиденциальности.
Once the user is logged into the web, the web server provides him with a SIP identity (SIP URI) and a session temporary token string (along with the SIP WebSocket Client JavaScript application and SIP settings). The web server stores the SIP identity and session token into a database.
После входа пользователя в веб-сеть веб-сервер предоставляет ему идентификацию SIP (SIP URI) и строку временного сеансового токена (вместе с приложением JavaScript клиента SIP WebSocket и настройками SIP). Веб-сервер сохраняет идентификацию SIP и сеансовый токен в базе данных.
The web application adds the SIP identity and session token as URL query parameters in the WebSocket handshake request and attempts the connection. The SIP WebSocket Server inspects the handshake request and validates that the session token matches the value stored in the database for the given SIP identity. In case the value matches, the WebSocket connection gets "authenticated" for that SIP identity. The SIP WebSocket Client can then register and make calls. The SIP WebSocket Server would, however, verify that the identity in those SIP requests (i.e., the From URI value) matches the SIP identity the WebSocket connection is associated to (otherwise, the SIP request is rejected).
Веб-приложение добавляет идентификацию SIP и сеансовый токен как параметры запроса URL в запрос рукопожатия WebSocket и пытается установить соединение. Сервер SIP WebSocket проверяет запрос рукопожатия и убеждается, что сеансовый токен совпадает со значением, сохранённым в базе данных для данной идентификации SIP. Если значение совпадает, соединение WebSocket становится «аутентифицированным» для этой идентификации SIP. Затем клиент SIP WebSocket может зарегистрироваться и совершать вызовы. Однако сервер SIP WebSocket проверял бы, что идентификация в этих запросах SIP (т. е. значение URI From) совпадает с идентификацией SIP, с которой связано соединение WebSocket (в противном случае запрос SIP отклоняется).
When the user performs a logout action in the web, the web server removes the SIP identity and session token tuple from the database and notifies the SIP WebSocket Server, which revokes and closes the WebSocket connection.
Когда пользователь выполняет действие выхода в веб-сети, веб-сервер удаляет кортеж из идентификации SIP и сеансового токена из базы данных и уведомляет сервер SIP WebSocket, который отзывает и закрывает соединение WebSocket.
No SIP authentication takes place in this scenario.
В этом сценарии аутентификация SIP не выполняется.
A.3. Cookie-Based Authentication
A.3. Аутентификация на основе cookie
The Apache web server comes with a new module: mod_sip_websocket. In port 80, the web server is configured to listen for both HTTP common requests and WebSocket handshake requests. Therefore, both the web server and the SIP WebSocket Server are co-located within the same host and same domain.
Веб-сервер Apache поставляется с новым модулем: mod_sip_websocket. На порту 80 веб-сервер настроен на прослушивание как обычных запросов HTTP, так и запросов рукопожатия WebSocket. Поэтому и веб-сервер, и сервер SIP WebSocket размещены на одном и том же хосте и в одном домене.
Once the user is logged into the web, he is provided with the SIP WebSocket Client JavaScript application and SIP settings. The HTTP 200 response after the login procedure also contains a session cookie [RFC6265]. The web application then attempts a WebSocket connection against the same URL/domain of the website, and thus the session cookie is automatically added by the browser into the WebSocket handshake request (as the WebSocket protocol [RFC6455] states).
После входа пользователя в веб-сеть ему предоставляются приложение JavaScript клиента SIP WebSocket и настройки SIP. Ответ HTTP 200 после процедуры входа также содержит сеансовый cookie [RFC6265]. Затем веб-приложение пытается установить соединение WebSocket по тому же URL и домену веб-сайта, и поэтому браузер автоматически добавляет сеансовый cookie в запрос рукопожатия WebSocket (как указано в протоколе WebSocket [RFC6455]).
The web server inspects the cookie value (as it would do for a common HTTP request containing a session cookie so that the login procedure is not required again). If the cookie is valid, the WebSocket connection is authorized. And, as in the previous use case, the connection is also associated with a specific SIP identity that must be satisfied by every SIP request coming over that connection.
Веб-сервер проверяет значение cookie (как он делал бы для обычного запроса HTTP, содержащего сеансовый cookie, чтобы процедура входа не требовалась снова). Если cookie действителен, соединение WebSocket авторизуется. И, как в предыдущем варианте использования, соединение также связывается с определённой идентификацией SIP, которой должен удовлетворять каждый запрос SIP, поступающий по этому соединению.
No SIP authentication takes place in this scenario but just common cookie usage as widely deployed in the World Wide Web.
В этом сценарии аутентификация SIP не выполняется, используется только обычное применение cookie, широко распространённое во Всемирной паутине.
Appendix B. Implementation Guidelines
Приложение B. Рекомендации по реализации
Let us assume a scenario in which the users access with their web browsers (probably behind NAT) an application provided by a server on an intranet, login by entering their user identifier and credentials, and retrieve a JavaScript application (along with the HTML) implementing a SIP WebSocket Client. Such a SIP stack connects to a given SIP WebSocket Server (an outbound SIP proxy that also implements classic SIP transports such as UDP and TCP). The HTTP GET method request sent by the web browser for the WebSocket handshake includes a Cookie [RFC6265] header with the value previously provided by the server after the successful login procedure. The cookie value is then inspected by the WebSocket server to authorize the connection. Once the WebSocket connection is established, the SIP WebSocket Client performs a SIP registration to a SIP registrar server that is reachable through the proxy. After registration, the SIP WebSocket Client and Server exchange SIP messages as would normally be expected.
Предположим сценарий, в котором пользователи обращаются со своих веб-браузеров (вероятно, находящихся за NAT) к приложению, предоставляемому сервером в интрасети, входят, вводя свой идентификатор пользователя и учётные данные, и получают приложение JavaScript (вместе с HTML), реализующее клиент SIP WebSocket. Такой стек SIP подключается к заданному серверу SIP WebSocket (исходящему прокси SIP, который также реализует классические транспорты SIP, такие как UDP и TCP). Запрос метода HTTP GET, отправляемый веб-браузером для рукопожатия WebSocket, содержит заголовок Cookie [RFC6265] со значением, ранее предоставленным сервером после успешной процедуры входа. Затем значение cookie проверяется сервером WebSocket для авторизации соединения. После установления соединения WebSocket клиент SIP WebSocket выполняет регистрацию SIP на сервере регистратора SIP, доступном через прокси. После регистрации клиент и сервер SIP WebSocket обмениваются сообщениями SIP, как обычно и ожидается.
This scenario is quite similar to ones in which SIP user agents (UAs) behind NATs connect to a proxy and must reuse the same TCP connection for incoming requests (because they are not directly reachable by the proxy otherwise). In both cases, the SIP UAs are only reachable through the proxy to which they are connected.
Этот сценарий довольно похож на сценарии, в которых пользовательские агенты SIP (UA) за NAT подключаются к прокси и должны повторно использовать одно и то же TCP-соединение для входящих запросов (поскольку иначе они недоступны прокси напрямую). В обоих случаях UA SIP доступны только через прокси, к которому они подключены.
The SIP Outbound extension [RFC5626] seems an appropriate solution for this scenario. Therefore, these SIP WebSocket Clients and the SIP registrar implement both the Outbound and Path [RFC3327] extensions, and the SIP proxy acts as an Outbound Edge Proxy (as defined in [RFC5626], Section 3.4).
Расширение SIP Outbound [RFC5626] кажется подходящим решением для этого сценария. Поэтому эти клиенты SIP WebSocket и регистратор SIP реализуют как расширение Outbound, так и расширение Path [RFC3327], а прокси SIP действует как краевой прокси Outbound (как определено в [RFC5626], раздел 3.4).
SIP WebSocket Clients in this scenario receive incoming SIP requests via the SIP WebSocket Server to which they are connected. Therefore, in some call transfer cases, the use of GRUU [RFC5627] (which should be implemented in both the SIP WebSocket Clients and SIP registrar) is valuable.
Клиенты SIP WebSocket в этом сценарии получают входящие запросы SIP через сервер SIP WebSocket, к которому они подключены. Поэтому в некоторых случаях переадресации вызова ценно использование GRUU [RFC5627] (которое следует реализовать как в клиентах SIP WebSocket, так и в регистраторе SIP).
If a REFER request is sent to a third SIP user agent including the Contact URI of a SIP WebSocket Client as the target in its Refer-To header field, such a URI will be reachable by the third SIP UA only if it is a globally routable URI. GRUU (Globally Routable User Agent URI) is a solution for those scenarios and would cause the incoming request from the third SIP user agent to be sent to the SIP registrar, which would route the request to the SIP WebSocket Client via the Outbound Edge Proxy.
Если запрос REFER отправлен третьему пользовательскому агенту SIP с включением Contact URI клиента SIP WebSocket как цели в его поле заголовка Refer-To, такой URI будет доступен третьему UA SIP только в том случае, если он является глобально маршрутизируемым URI. GRUU (Globally Routable User Agent URI) — решение для таких сценариев; оно привело бы к тому, что входящий запрос от третьего пользовательского агента SIP отправлялся бы регистратору SIP, который маршрутизировал бы запрос клиенту SIP WebSocket через краевой прокси Outbound.
B.1. SIP WebSocket Client Considerations
B.1. Соображения о клиенте SIP WebSocket
The JavaScript stack in web browsers does not have the ability to discover the local transport address used for originating WebSocket connections. A SIP WebSocket Client running in such an environment can construct a domain name consisting of a random token followed by the ".invalid" top-level domain name, as stated in [RFC2606], and uses it within its Via and Contact headers. The Contact URI provided by SIP UAs requesting (and receiving) Outbound support is not used for routing requests to those UAs, thus it is safe to set a random domain in the Contact URI hostport.
Стек JavaScript в веб-браузерах не имеет возможности обнаружить локальный транспортный адрес, используемый для исходящих соединений WebSocket. Клиент SIP WebSocket, работающий в такой среде, может построить доменное имя, состоящее из случайного токена, за которым следует доменное имя верхнего уровня «.invalid», как указано в [RFC2606], и использовать его в своих заголовках Via и Contact. Contact URI, предоставляемый UA SIP, запрашивающими (и получающими) поддержку Outbound, не используется для маршрутизации запросов к этим UA, поэтому безопасно задать случайный домен в hostport Contact URI.
Both the Outbound and GRUU specifications require a SIP UA to include a Uniform Resource Name (URN) in a "+sip.instance" parameter of the Contact header in which they include their SIP REGISTER requests. The client device is responsible for generating or collecting a suitable value for this purpose.
Как спецификация Outbound, так и спецификация GRUU требуют, чтобы UA SIP включал Uniform Resource Name (URN) в параметр «+sip.instance» заголовка Contact, в который они включают свои запросы SIP REGISTER. Клиентское устройство отвечает за генерацию или сбор подходящего значения для этой цели.
In web browsers, it is difficult to generate or collect a suitable value to be used as an URN value from the browser itself. This scenario suggests that value is generated according to [RFC5626], Section 4.1 by the web application running in the browser the first time it loads the JavaScript SIP stack code, and then it is stored as a cookie within the browser.
В веб-браузерах трудно сгенерировать или собрать подходящее значение для использования в качестве значения URN из самого браузера. Этот сценарий предполагает, что значение генерируется согласно [RFC5626], раздел 4.1, веб-приложением, работающим в браузере, при первой загрузке кода стека SIP JavaScript, а затем сохраняется как cookie в браузере.
B.2. SIP WebSocket Server Considerations
B.2. Соображения о сервере SIP WebSocket
The SIP WebSocket Server in this scenario behaves as a SIP Outbound Edge Proxy, which involves support for Outbound [RFC5626] and Path [RFC3327].
Сервер SIP WebSocket в этом сценарии ведёт себя как краевой прокси SIP Outbound, что подразумевает поддержку Outbound [RFC5626] и Path [RFC3327].
The proxy performs loose routing and remains in the path of dialogs as specified in [RFC3261]. If it did not do this, in-dialog requests would fail since SIP WebSocket Clients make use of their SIP WebSocket Server in order to send and receive SIP messages.
Прокси выполняет свободную маршрутизацию и остаётся на пути диалогов, как указано в [RFC3261]. Если бы он этого не делал, запросы внутри диалога завершались бы неудачно, поскольку клиенты SIP WebSocket используют свой сервер SIP WebSocket для отправки и получения сообщений SIP.
