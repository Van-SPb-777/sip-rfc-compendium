Basic Telephony SIP End-to-End Performance Metrics
Базовые метрики сквозной производительности SIP-телефонии
Abstract
Аннотация
This document defines a set of metrics and their usage to evaluate the performance of end-to-end Session Initiation Protocol (SIP) for telephony services in both production and testing environments. The purpose of this document is to combine a standard set of common metrics, allowing interoperable performance measurements, easing the comparison of industry implementations.
В настоящем документе определяется набор метрик и порядок их применения для оценки производительности сквозного протокола инициирования сессий (SIP) в телефонных услугах как в производственной, так и в тестовой среде. Цель документа — объединить стандартный набор общих метрик, что позволяет проводить совместимые измерения производительности и упрощает сравнение реализаций разных производителей.

1. Introduction and Scope
1. Введение и область применения
SIP has become a widely used standard among many service providers, vendors, and end users in the telecommunications industry. Although there are many different standards for measuring the performance of telephony signaling protocols, such as Signaling System 7 (SS7), none of the metrics specifically address SIP.
SIP стал широко используемым стандартом среди многих поставщиков услуг, производителей и конечных пользователей в телекоммуникационной отрасли. Хотя существует множество различных стандартов измерения производительности протоколов телефонной сигнализации, таких как система сигнализации № 7 (SS7), ни одна из метрик не относится конкретно к SIP.
The scope of this document is limited to the definitions of a standard set of metrics for measuring and reporting SIP performance from an end-to-end perspective in a telephony environment. The metrics introduce a common foundation for understanding and quantifying performance expectations between service providers, vendors, and the users of services based on SIP. The intended audience for this document can be found among network operators, who often collect information on the responsiveness of the network to customer requests for services.
Область применения настоящего документа ограничена определениями стандартного набора метрик для измерения и отчётности о производительности SIP со сквозной точки зрения в телефонной среде. Метрики закладывают общую основу для понимания и количественной оценки ожиданий по производительности между поставщиками услуг, производителями и пользователями услуг на основе SIP. Целевая аудитория настоящего документа — сетевые операторы, которые часто собирают сведения об отзывчивости сети на запросы клиентов на услуги.
Measurements of the metrics described in this document are affected by variables external to SIP. The following is a non-exhaustive list of examples:
На измерения метрик, описанных в настоящем документе, влияют переменные, внешние по отношению к SIP. Ниже приведён неисчерпывающий перечень примеров:
o Network connectivity
o Сетевое подключение
o Switch and router performance
o Работа коммутаторов и маршрутизаторов
o Server processes and hardware performance
o Производительность серверных процессов и оборудования
This document defines a list of pertinent metrics for varying aspects of a telephony environment. They may be used individually or as a set based on the usage of SIP within the context of a given telecommunications service.
В настоящем документе определён перечень уместных метрик для различных аспектов телефонной среды. Их можно использовать по отдельности или как набор в зависимости от применения SIP в контексте конкретной телекоммуникационной услуги.
The metrics defined in this document DO NOT take into consideration the impairment or failure of actual application processing of a request or response. The metrics do not distinguish application processing time from other sources of delay, such as packet transfer delay.
Метрики, определённые в настоящем документе, НЕ учитывают нарушения или отказы фактической прикладной обработки запроса или ответа. Метрики не отличают время прикладной обработки от других источников задержки, таких как задержка передачи пакетов.
Metrics designed to quantify single device application processing performance are beyond the scope of this document.
Метрики, предназначенные для количественной оценки производительности прикладной обработки одного устройства, выходят за рамки настоящего документа.
This document does not provide any numerical objectives or acceptance threshold values for the SIP performance metrics defined below, as these items are beyond the scope of IETF activities, in general.
Настоящий документ не задаёт никаких числовых целей или пороговых значений приемлемости для метрик производительности SIP, определённых ниже, поскольку эти вопросы в целом выходят за рамки деятельности IETF.
The metrics defined in this document are applicable in scenarios where the SIP messages launched (into a network under test) are dedicated messages for testing purposes, or where the messages are user-initiated and a portion of the live is traffic present. These two scenarios are sometimes referred to as active and passive measurement, respectively.
Метрики, определённые в настоящем документе, применимы в сценариях, где запускаемые (в тестируемую сеть) сообщения SIP являются выделенными сообщениями для целей тестирования, или где сообщения инициируются пользователями и составляют часть действующего трафика. Эти два сценария иногда называют соответственно активным и пассивным измерением.
2. Terminology
2. Терминология
The following terms and conventions will be used throughout this document:
В настоящем документе используются следующие термины и соглашения:
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [RFC2119]. End-to-End - This is described as two or more elements utilized for initiating a request, receiving the request, and responding to the request. It encompasses elements as necessary to be involved in a session dialog between the originating user agent client (UAC), destination user agent server (UAS), and any interim proxies (may also include back-to-back user agents (B2BUAs)). This may be relative to a single operator's set of elements or may extend to encompass all elements (if beyond a single operator's network) associated with a session.
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует интерпретировать так, как описано в RFC 2119 [RFC2119]. Сквозной (End-to-End) — так описываются два или более элемента, используемых для инициирования запроса, получения запроса и ответа на запрос. Это охватывает элементы, которые необходимо задействовать в сеансовом диалоге между исходным клиентом пользовательского агента (UAC), целевым сервером пользовательского агента (UAS) и любыми промежуточными прокси (может также включать связанные друг с другом пользовательские агенты (B2BUA)). Это может относиться к набору элементов одного оператора или распространяться на все элементы (если они находятся за пределами сети одного оператора), связанные с сеансом.
Session - As described in RFC 3261 [RFC3261], SIP is used primarily to request, create, and conclude sessions. "These sessions include Internet telephone calls, multimedia distribution, and multimedia conferences". The metrics within this document measure the performance associated with the SIP dialogs necessary to establish these sessions; therefore, they are titled as Session Request Delay, Session Disconnect Delay, etc. Although the titles of many of the metrics include this term, they are specifically measuring the signaling aspects only. Each session is identified by a unique "Call-ID", "To", and "From" header field tag.
Сеанс (Session) — как описано в RFC 3261 [RFC3261], SIP используется в первую очередь для запроса, создания и завершения сеансов. «Эти сеансы включают интернет-телефонные вызовы, распространение мультимедиа и мультимедийные конференции». Метрики в настоящем документе измеряют производительность, связанную с диалогами SIP, необходимыми для установления этих сеансов; поэтому они названы «Задержка запроса сеанса», «Задержка отключения сеанса» и т. д. Хотя названия многих метрик включают этот термин, они измеряют именно аспекты сигнализации. Каждый сеанс идентифицируется уникальной комбинацией тегов заголовочных полей «Call-ID», «To» и «From».
Session Establishment - Session establishment occurs when a 200 OK response from the target UA has been received, in response to the originating UA's INVITE setup request, indicating the session setup request was successful.
Установление сеанса (Session Establishment) — установление сеанса происходит при получении ответа 200 OK от целевого UA в ответ на запрос установки INVITE исходного UA, что указывает на успешность запроса установки сеанса.
Session Setup - As referenced within the sub-sections of Section 4.2 in this document, session setup is the set of messages and included parameters directly related to the process of a UA requesting to establish a session with a corresponding UA. This is also described as a set of steps in order to establish "ringing" [RFC3261].
Настройка сеанса (Session Setup) — как указано в подразделах раздела 4.2 настоящего документа, настройка сеанса представляет собой набор сообщений и включённых параметров, непосредственно связанных с процессом запроса UA на установление сеанса с соответствующим UA. Это также описывается как набор шагов для установления «посылки вызова» (ringing) [RFC3261].
3. Time Interval Measurement and Reporting
3. Измерение и отчётность по временным интервалам
Many of the metrics defined in this memo utilize a clock to assess the time interval between two events. This section defines time- related terms and reporting requirements.
Многие метрики, определённые в настоящем меморандуме, используют часы для оценки временного интервала между двумя событиями. В этом разделе определяются термины, связанные со временем, и требования к отчётности.
t1 - start time
t1 — время начала
This is the time instant (when a request is sent) that begins a continuous time interval. t1 occurs when the designated request has been processed by the SIP application and the first bit of the request packet has been sent from the UA or proxy (and is externally observable at some logical or physical interface). t1 represents the time at which each request-response test begins, and SHALL be used to designate the time of day when a particular measurement was conducted (e.g., the Session Request Delay at "t1" (at some specific UA interface) was measured to be X ms).
Это момент времени (когда отправляется запрос), с которого начинается непрерывный временной интервал. t1 наступает, когда назначенный запрос обработан приложением SIP и первый бит пакета запроса отправлен из UA или прокси (и внешне наблюдаем на некотором логическом или физическом интерфейсе). t1 представляет время начала каждого испытания «запрос-ответ» и ДОЛЖЕН использоваться для указания времени суток, когда проводилось конкретное измерение (например, задержка запроса сеанса при «t1» (на некотором конкретном интерфейсе UA) измерена равной X мс).
t4 - end time
t4 — окончание
This is the time instant that concludes the continuous time interval begun when the related request is sent. t4 occurs when the last bit of the designated response is received by the SIP application at the requesting device (and is externally observable at some logical or physical interface).
Это момент времени, которым завершается непрерывный временной интервал, начатый при отправке соответствующего запроса. t4 наступает, когда последний бит назначенного ответа получен приложением SIP на устройстве-инициаторе запроса (и внешне наблюдаем на некотором логическом или физическом интерфейсе).
Note: The designations t2 and t3 are reserved for future use at another interface involved in satisfying a request.
Примечание: обозначения t2 и t3 зарезервированы для будущего использования на другом интерфейсе, участвующем в удовлетворении запроса.
Section 10.1 of [RFC2330] describes time-related issues in measurements, and defines the errors that can be attributed to the clocks themselves. These definitions are used in the material below.
В разделе 10.1 [RFC2330] описаны вопросы, связанные со временем, при измерениях и определены ошибки, которые можно отнести к самим часам. Эти определения используются в приведённом ниже материале.
Time-of-Day Accuracy
Точность времени суток
As defined above, t1 is associated with the start of a request and also serves as the time-of-day stamp associated with a single specific measurement. The clock offset [RFC2330] is the difference between t1 and a recognized primary source of time, such as UTC (offset = t1 - UTC).
Как определено выше, t1 связан с началом запроса и также служит отметкой времени суток, связанной с одним конкретным измерением. Смещение часов [RFC2330] — это разность между t1 и признанным первичным источником времени, таким как UTC (смещение = t1 - UTC).
When measurement results will be correlated with other results or information using time-of-day stamps, then the time clock that supplies t1 SHOULD be synchronized to a primary time source, to minimize the clock's offset. The clocks used at the different measurement points SHOULD be synchronized to each other, to minimize the relative offset (as defined in RFC2330). The clock's offset and the relative offset MUST be reported with each measurement.
Когда результаты измерений будут соотноситься с другими результатами или информацией с помощью отметок времени суток, часы, дающие t1, ДОЛЖНЫ быть синхронизированы с первичным источником времени, чтобы минимизировать смещение часов. Часы, используемые в разных точках измерения, ДОЛЖНЫ быть синхронизированы друг с другом, чтобы минимизировать относительное смещение (как определено в RFC 2330). Смещение часов и относительное смещение ДОЛЖНЫ сообщаться при каждом измерении.
Time Interval Accuracy
Точность интервала времени
The accuracy of the t4-t1 interval is also critical to maintain and report. The difference between a clock's offsets at t1 and t4 is one source of error for the measurement and is associated with the clock's skew [RFC2330]. A stable and reasonably accurate clock is needed to make the time interval measurements required by this memo. This source of error SHOULD be constrained to less than +/- 1 ms, implying 1-part-per-1000 frequency accuracy for a 1-second interval. This implies that greater stability is required as the length of the t4-t1 increases, in order to constrain the error to be less than +/- 1 ms.
Точность интервала t4-t1 также критична для поддержания и отчётности. Разность смещений часов в моменты t1 и t4 является одним из источников ошибки измерения и связана с уходом частоты часов (skew) [RFC2330]. Для выполнения измерений временных интервалов, требуемых настоящим меморандумом, нужны стабильные и достаточно точные часы. Этот источник ошибки СЛЕДУЕТ ограничивать значением менее +/- 1 мс, что подразумевает точность частоты 1 часть на 1000 для интервала в 1 секунду. Это означает, что с увеличением длительности t4-t1 требуется большая стабильность, чтобы ограничить ошибку значением менее +/- 1 мс.
There are other important aspects of clock operation:
Существуют и другие важные аспекты работы часов:
1. Synchronization protocols require some ability to make adjustments to the local clock. However, these adjustments (clock steps or slewing) can cause large errors if they occur during the t1 to t4 measurement interval. Clock correction SHOULD be suspended during a t1 to t4 measurement interval, unless the time interval accuracy requirement above will be met. Alternatively, a measurement SHOULD NOT be performed during clock correction, unless the time interval accuracy requirement above will be met.
1. Протоколы синхронизации требуют некоторой возможности вносить поправки в локальные часы. Однако такие поправки (скачки или плавная подстройка часов) могут вызвать большие ошибки, если они происходят в течение интервала измерения t1–t4. Коррекцию часов СЛЕДУЕТ приостанавливать на время интервала измерения t1–t4, если только не будет выполнено требование к точности временного интервала, указанное выше. В качестве альтернативы измерение НЕ СЛЕДУЕТ выполнять во время коррекции часов, если только не будет выполнено требование к точности временного интервала, указанное выше.
2. If a free-running clock is used to make the time interval measurement, then the time of day reported with the measurement (which is normally timestamp t1) SHOULD be derived from a different clock that meets the time-of-day accuracy requirements described above.
2. Если для измерения временного интервала используются свободно идущие часы, то время суток, сообщаемое с измерением (обычно это отметка времени t1), СЛЕДУЕТ получать от других часов, отвечающих требованиям к точности времени суток, описанным выше.
The physical operation of reading time from a clock may be constrained by the delay to service the interrupt. Therefore, if the accuracy of the time stamp read at t1 or t4 includes the interrupt delay, this source of error SHOULD be known and included in the error assessment.
Физическая операция чтения времени с часов может быть ограничена задержкой обслуживания прерывания. Поэтому, если точность отметки времени, считанной в момент t1 или t4, включает задержку прерывания, этот источник ошибки ДОЛЖЕН быть известен и учтён при оценке ошибки.
4. SIP Performance Metrics
4. Метрики производительности SIP
In regard to all of the following metrics, t1 begins with the first associated SIP message sent by either UA, and is not reset if the UA must retransmit the same message, within the same transaction, multiple times. The first associated SIP message indicates the t1 associated with the user or application expectation relative to the request.
Применительно ко всем перечисленным ниже метрикам t1 начинается с первого соответствующего сообщения SIP, отправленного любым UA, и не сбрасывается, если UA должен повторно передавать одно и то же сообщение в рамках одной транзакции несколько раз. Первое соответствующее сообщение SIP указывает на t1, связанное с ожиданием пользователя или приложения относительно запроса.
Some metrics are calculated using messages from different transactions in order to measure across actions such as redirection and failure recovery. The end time is typically based on a successful end-to-end provisional response, a successful final response, or a failure final response for which there is no recovery. The individual metrics detail which message to base the end time on. The authentication method used to establish the SIP dialog will change the message exchanges. The example message exchanges used do not attempt to describe all of the various authentication types. Since authentication is frequently used, SIP Digest authentication was used for example purposes.
Некоторые метрики рассчитываются с использованием сообщений из разных транзакций, чтобы измерять сквозные действия, такие как переадресация и восстановление после отказа. Время окончания обычно основано на успешном предварительном сквозном ответе, успешном окончательном ответе или окончательном ответе об отказе, для которого не предусмотрено восстановление. В описании отдельных метрик указано, на каком сообщении основывать время окончания. Метод аутентификации, используемый для установления диалога SIP, изменит обмен сообщениями. Применительно ко всем метрикам точность и гранулярность выходных значений связаны с точностью и гранулярностью входных значений. Некоторые из приведённых ниже метрик определяются через отношение. Когда знаменатель этого отношения равен 0, метрика не определена.

Например, некоторые поставщики услуг SIP (SSP) [RFC5486] могут собирать входные данные за часовой, суточный, недельный или месячный период, а другой SSP может выполнять расчёт метрик по изменяющемуся набору диалогов SIP.

4.3.1. Successful Session Setup SRD
4.3.1. SRD при успешной настройке сеанса
In a successful request attempt, SRD is defined as the time interval from when the first bit of the initial INVITE message containing the necessary information is sent by the originating user agent to the intended mediation or destination agent, until the last bit of the first provisional response is received indicating an audible or visual status of the initial session setup request. (Note: In some cases, the initial INVITE may be forked. Section 5.4 provides information for consideration on forking.) In SIP, the message indicating status would be a non-100 Trying provisional message received in response to an INVITE request. In some cases, a non-100 Trying provisional message is not received, but rather a 200 message is received as the first status message instead. In these situations, the 200 message would be used to calculate the interval. In most circumstances, this metric relies on receiving a non-100 Trying message. The use of the Provisional Response ACKnowledgement (PRACK) method [RFC3262] MAY improve the quality and consistency of the results.
При успешной попытке запроса SRD определяется как временной интервал от момента, когда первый бит начального сообщения INVITE, содержащего необходимую информацию, отправлен исходным пользовательским агентом предполагаемому посредничающему или целевому агенту, до момента получения последнего бита первого предварительного ответа, указывающего на слышимое или видимое состояние начального запроса установления сеанса. (Примечание: в некоторых случаях начальный INVITE может разветвляться. В разделе 5.4 приведены сведения, которые следует учитывать при разветвлении.) В SIP сообщением, указывающим состояние, будет предварительное сообщение, отличное от 100 Trying, полученное в ответ на запрос INVITE. В некоторых случаях предварительное сообщение, отличное от 100 Trying, не получено, а вместо него первым сообщением о состоянии получено сообщение 200. В таких ситуациях для расчёта интервала будет использоваться сообщение 200. В большинстве обстоятельств эта метрика зависит от получения сообщения, отличного от 100 Trying. Использование метода подтверждения предварительного ответа (PRACK) [RFC3262] МОЖЕТ улучшить качество и согласованность результатов.

4.7. Session Establishment Effectiveness Ratio (SEER)
4.7. Отношение эффективности установления сеансов (SEER)
This metric is complimentary to SER, but is intended to exclude the potential effects of an individual user of the target UA from the metric. SEER is defined as the ratio of the number of INVITE requests resulting in a 200 OK response and INVITE requests resulting in a 480, 486, 600, or 603; to the total number of attempted INVITE requests less INVITE requests resulting in a 3XX response. The response codes 480, 486, 600, and 603 were chosen because they clearly indicate the effect of an individual user of the UA. It is possible an individual user could cause a negative effect on the UA. For example, they may have misconfigured the UA, causing a response code not directly related to an SSP, but this cannot be easily determined from an intermediary B2BUA somewhere between the originating and terminating UAs. With this in consideration, response codes such as 401, 407, and 420 (not an exhaustive list) were not included in the numerator of the metric. This metric is similar to the Network Effectiveness Ratio (NER) defined in [E.411]. It is measured at the originating UA only. The output value of this metric is numerical and SHOULD be adjusted to indicate a percentage of successfully established sessions less common UAS failures.
Эта метрика дополняет SER, но предназначена для исключения из метрики возможного влияния отдельного пользователя целевого UA. SEER определяется как отношение числа запросов INVITE, приводящих к ответу 200 OK, и запросов INVITE, приводящих к ответу 480, 486, 600 или 603, к общему числу попыток запросов INVITE за вычетом запросов INVITE, приводящих к ответу 3XX. Например, он мог неправильно настроить UA, вызвав код ответа, не связанный напрямую с SSP, но это нелегко определить из промежуточного B2BUA где-то между исходным и завершающим UA. С учётом этого такие коды ответов, как 401, 407 и 420 (список неисчерпывающий), не были включены в числитель метрики. Эта метрика аналогична отношению сетевой эффективности (Network Effectiveness Ratio, NER), определённому в [E.411]. Она измеряется только на исходном UA. 5.2. Back-to-Back User Agent (B2BUA)
5.2. Пользовательский агент B2BUA
A B2BUA may impact the ability to collect these metrics with an end- to-end perspective. It is necessary to realize that a B2BUA may act as an originating UAC and terminating UAS, or it may act as a proxy. In some cases, it may be necessary to consider information collected from both sides of the B2BUA in order to determine the end-to-end perspective. In other cases, the B2BUA may act simply as a proxy allowing data to be derived as necessary for the input into any of the listed calculations.
B2BUA может влиять на возможность сбора этих метрик со сквозной точки зрения. Необходимо понимать, что B2BUA может действовать как исходный UAC и завершающий UAS либо как прокси. В некоторых случаях может потребоваться рассмотреть информацию, собранную с обеих сторон B2BUA, чтобы определить сквозную картину. В других случаях B2BUA может действовать просто как прокси, позволяя получать данные, необходимые в качестве входных для любого из перечисленных расчётов.
5.3. Authorization and Authentication
5.3. Авторизация и аутентификация
During the process of setting up a SIP dialog, various authentication methods may be utilized. These authentication methods will add to the duration as measured by the metrics, and the length of time will vary based on those methods. The failures of these authentication methods will also be captured by these metrics, since SIP is ultimately used to indicate the success or failure of the authorization and/or authentication attempt. The metrics in Section 3 are inclusive of the duration associated with this process, even if the method is external to SIP. This was included purposefully, due to its inherent impact on the protocol and the subsequent SIP dialogs.
В процессе установления диалога SIP могут использоваться различные методы аутентификации. Эти методы аутентификации увеличивают длительность, измеряемую метриками, причём продолжительность будет зависеть от этих методов. Отказы этих методов аутентификации также будут фиксироваться этими метриками, поскольку SIP в конечном итоге используется для указания успеха или неудачи попытки авторизации и/или аутентификации. Метрики в разделе 3 включают длительность, связанную с этим процессом, даже если метод является внешним по отношению к SIP. Это включено намеренно, из-за присущего ему влияния на протокол и последующие диалоги SIP.
5.4. Forking
5.4. Разветвление
Forking SHOULD be considered when determining the messages associated with the input values for the described metrics. If all of the forked dialogs were used in the metric calculations, the numbers would skew dramatically. There are two different points of forking, and each MUST be considered. First, forking may occur at a proxy downstream from the UA that is being used for metric input values. The downstream proxy is responsible for forking a message. Then, this proxy will send provisional (e.g., 180) messages received from the requests and send the accepted (e.g., 200) response to the UA.
Разветвление СЛЕДУЕТ учитывать при определении сообщений, связанных с входными значениями для описанных метрик. Если бы в расчётах метрик использовались все разветвлённые диалоги, числа исказились бы кардинально. Существуют две разные точки разветвления, и каждую из них НЕОБХОДИМО учитывать. Во-первых, разветвление может произойти на прокси ниже по потоку от UA, используемого для входных значений метрик. Нижележащий прокси отвечает за разветвление сообщения. Затем этот прокси будет отправлять предварительные (например, 180) сообщения, полученные по запросам, и отправлять принятый (например, 200) ответ UA.
Second, in the cases where the originating UA or proxy is forking the messages, then it MUST parse the message exchanges necessary for input into the metrics. For example, it MAY utilize the first INVITE or set of INVITE messages sent and the first accepted 200 OK. Tags will identify this dialog as distinct from the other 200 OK responses, which are acknowledged, and an immediate BYE is sent. The application responsible for capturing and/or understanding the input values MUST utilize these tags to distinguish between dialog requests.
Во-вторых, в случаях, когда исходный UA или прокси выполняет разветвление сообщений, он ДОЛЖЕН разбирать обмен сообщениями, необходимый для входных данных метрик. Например, он МОЖЕТ использовать первый INVITE или набор отправленных сообщений INVITE и первый принятый 200 OK. Теги идентифицируют этот диалог как отличный от других ответов 200 OK, которые подтверждаются и на которые сразу отправляется BYE. Приложение, отвечающее за фиксацию и/или понимание входных значений, ДОЛЖНО использовать эти теги для различения запросов диалога.
Note that if an INVITE is forked before reaching its destination, multiple early dialogs are likely, and multiple confirmed dialogs are possible (though unlikely). When this occurs, an SRD measurement should be taken for each dialog that is created (early or confirmed).
Отметим, что если INVITE разветвляется до достижения пункта назначения, вероятны несколько ранних диалогов и возможно несколько подтверждённых диалогов (хотя и маловероятно). Когда это происходит, измерение SRD следует выполнять для каждого созданного диалога (раннего или подтверждённого).
5.5. Data Collection
5.5. Сбор информации
The input necessary for these calculations may be collected in a number of different manners. It may be collected or retrieved from call detail records (CDRs) or raw signaling information generated by a proxy or UA. When using records, time synchronization MUST be considered between applicable elements.
Входные данные, необходимые для этих расчётов, могут собираться несколькими разными способами. Их можно собирать или извлекать из подробных записей о вызовах (CDR) или необработанной информации о сигнализации, формируемой прокси или UA. При использовании записей НЕОБХОДИМО учитывать синхронизацию времени между применимыми элементами.
If these metrics are calculated at individual elements (such as proxies or endpoints) instead of by a centralized management system, and the individual elements use different measurement sample sizes, then the metrics reported for the same event at those elements may differ significantly.
Если эти метрики рассчитываются на отдельных элементах (таких как прокси или конечные точки), а не централизованной системой управления, и отдельные элементы используют разные размеры выборки измерений, то метрики, сообщаемые для одного и того же события на этих элементах, могут существенно различаться.
The information may also be transmitted through the use of network management protocols like the Simple Network Management Protocol (SNMP) and via future extensions to the SIP Management Information Base (MIB) modules [RFC4780], or through a potential undefined new performance metric event package [RFC3265] retrieved via SUBSCRIBE requests. Data may be collected for a sample of calls or all calls, and may also be derived from test call scenarios. These metrics are flexible based on the needs of the application.
Информация также может передаваться с использованием протоколов управления сетью, таких как Simple Network Management Protocol (SNMP), и через будущие расширения модулей базы управляющей информации SIP (MIB) [RFC4780], либо через потенциальный новый, пока не определённый пакет событий метрик производительности [RFC3265], получаемый с помощью запросов SUBSCRIBE. Данные могут собираться для выборки вызовов или для всех вызовов, а также могут быть получены из сценариев тестовых вызовов. Эти метрики гибко настраиваются в зависимости от потребностей приложения.
For consistency in calculation of the metrics, elements should expect to reveal event inputs for use by a centralized management system, which would calculate the metrics based on a varying set sample size of inputs received from elements compliant with this specification.
Для согласованности расчёта метрик элементы должны предоставлять входные события для использования централизованной системой управления, которая рассчитывала бы метрики на основе изменяющегося размера выборки входных данных, получаемых от элементов, совместимых с настоящей спецификацией.
5.6. Testing Documentation
5.6. Документация тестирования
In some cases, these metrics will be used to provide output values to signify the performance level of a specific SIP-based element. When using these metrics in a test environment, the environment MUST be accurately documented for the purposes of replicating any output values in future testing and/or validation.
В некоторых случаях эти метрики будут использоваться для выдачи выходных значений, обозначающих уровень производительности конкретного элемента на основе SIP. При использовании этих метрик в тестовой среде среда ДОЛЖНА быть точно задокументирована для целей воспроизведения любых выходных значений в будущем тестировании и/или валидации.
6. Conclusions
6. Заключение
This document provides a description of common performance metrics and their defined use with SIP. The use of these metrics will provide a common viewpoint across all vendors, service providers, and users. These metrics will likely be utilized in production telephony SIP environments for providing input regarding Key Performance Indicators (KPI) and Service Level Agreement (SLA) indications; however, they may also be used for testing end-to-end SIP-based service environments.
В настоящем документе приведено описание общих метрик производительности и их определённого использования с SIP. Использование этих метрик обеспечит общую точку зрения для всех производителей, поставщиков услуг и пользователей. Эти метрики, вероятно, будут использоваться в производственных телефонных средах SIP для предоставления входных данных о ключевых показателях эффективности (KPI) и индикаторах соглашения об уровне обслуживания (SLA); однако они также могут использоваться для тестирования сквозных сервисных сред на основе SIP.
7. Security Considerations
7. Вопросы безопасности
Security should be considered in the aspect of securing the relative data utilized in providing input to the above calculations. All other aspects of security should be considered as described in RFC 3261 [RFC3261].
Безопасность следует рассматривать в аспекте защиты соответствующих данных, используемых для предоставления входных данных для вышеуказанных расчётов. Все остальные аспекты безопасности следует рассматривать так, как описано в RFC 3261 [RFC3261].
Implementers of these metrics MUST realize that these metrics could be used to describe characteristics of customer and user usage patterns, and privacy should be considered when collecting, transporting, and storing them.
Реализаторы этих метрик ДОЛЖНЫ понимать, что эти метрики могут использоваться для описания характеристик моделей использования клиентов и пользователей, и при их сборе, передаче и хранении следует учитывать конфиденциальность.
