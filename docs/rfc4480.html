Abstract
Аннотация
The Presence Information Data Format (PIDF) defines a basic format for representing presence information for a presentity. This format defines a textual note, an indication of availability (open or closed) and a Uniform Resource Identifier (URI) for communication. The Rich Presence Information Data format (RPID) described here is an extension that adds optional elements to the Presence Information Data Format (PIDF). These extensions provide additional information about the presentity and its contacts. The information is designed so that much of it can be derived automatically, e.g., from calendar files or user activity.
Формат информации о присутствии (PIDF) определяет базовый формат представления информации о присутствии для презентити. Этот формат определяет текстовую заметку, признак доступности (открыт или закрыт) и унифицированный идентификатор ресурса (URI) для связи. Описываемый здесь формат расширенной информации о присутствии (RPID) является расширением, добавляющим необязательные элементы к формату информации о присутствии (PIDF). Эти расширения предоставляют дополнительную информацию о презентити и его контактах. Информация устроена так, что значительная её часть может выводиться автоматически, например, из файлов календаря или активности пользователя.
This extension includes information about what the person is doing, a grouping identifier for a tuple, when a service or device was last used, the type of place a person is in, what media communications might remain private, the relationship of a service tuple to another presentity, the person's mood, the time zone it is located in, the type of service it offers, an icon reflecting the presentity's status, and the overall role of the presentity.
Это расширение включает сведения о том, чем занимается человек, идентификатор группировки для кортежа, когда в последний раз использовалась услуга или устройство, тип места, в котором находится человек, какие медиаданные, возможно, остаются конфиденциальными, отношение кортежа услуги к другому презентити, настроение человека, часовой пояс, в котором он находится, тип предлагаемой услуги, значок, отражающий статус презентити, и общую роль презентити.
These extensions include presence information for persons, services (tuples), and devices.
Эти расширения включают информацию о присутствии для людей, услуг (кортежей) и устройств.
1. Introduction
1. Введение
The Presence Information Data Format (PIDF) definition [8] describes a basic presence information data format, encoded as an Extensible Markup Language (XML) [9] (SCHEMA-1 [10]) (SCHEMA-2 [11]), for exchanging presence information in systems compliant with the common model for presence and instant messaging [5]. It consists of a <presence> root element, zero or more <tuple> elements carrying presence information including a Uniform Resource Identifier (URI) for communication, zero or more <note> elements, and zero or more extension elements from other name spaces. Each tuple defines a basic status of either "open" or "closed". However, it is frequently useful to convey additional information about a user that needs to be interpreted by an automata, and is therefore not appropriate to be placed in the <note> element of the PIDF document, which is typically intended for the human observer. Therefore, this specification defines extensions to the PIDF document format for conveying richer presence information. Generally, the extensions have been chosen to provide features common in existing presence systems at the time of writing, in addition to elements that could readily be derived automatically from existing sources of presence, such as calendaring systems or communication devices, or sources describing the user's current physical environment.
Определение формата информации о присутствии (PIDF) [8] описывает базовый формат данных о присутствии, кодируемый на расширяемом языке разметки (XML) [9] (SCHEMA-1 [10]) (SCHEMA-2 [11]), для обмена информацией о присутствии в системах, соответствующих общей модели присутствия и обмена мгновенными сообщениями [5]. Он состоит из корневого элемента <presence>, нуля или более элементов <tuple>, несущих информацию о присутствии, включая унифицированный идентификатор ресурса (URI) для связи, нуля или более элементов <note> и нуля или более элементов расширения из других пространств имён. Каждый кортеж определяет базовый статус «open» или «closed». Однако часто полезно передавать дополнительную информацию о пользователе, которая должна интерпретироваться автоматом и поэтому не подходит для размещения в элементе <note> документа PIDF, обычно предназначенном для наблюдателя-человека. Поэтому настоящая спецификация определяет расширения формата документа PIDF для передачи более богатой информации о присутствии. В целом расширения выбраны так, чтобы обеспечить возможности, распространённые в существующих системах присутствия на момент написания, в дополнение к элементам, которые можно легко выводить автоматически из существующих источников присутствия, таких как календарные системы или устройства связи, либо из источников, описывающих текущее физическое окружение пользователя.
The presence data model [16] defines the concepts of service, device, and person as the data elements that are used to model the state of a presentity. (The term "presentity" is defined in RFC 2778 [5] and abbreviates presence entity. A presentity provides presence information to a presence service.) Services are encoded using the <tuple> element, defined in PIDF; devices and persons are represented by the <device> and <person> XML elements, respectively, defined in the data model [16]. However, neither PIDF nor the data model defines presence attributes beyond the <basic> status element.
Модель данных о присутствии [16] определяет понятия услуги, устройства и человека как элементы данных, используемые для моделирования состояния презентити. (Термин «презентити» определён в RFC 2778 [5] и сокращает «объект присутствия». Презентити предоставляет информацию о присутствии службе присутствия.) Услуги кодируются с помощью элемента <tuple>, определённого в PIDF; устройства и люди представляются XML-элементами <device> и <person> соответственно, определёнными в модели данных [16]. Однако ни PIDF, ни модель данных не определяют атрибуты присутствия сверх элемента статуса <basic>.
This specification defines additional presence attributes to describe person, service, and device data elements, summarized as "Rich Presence Information Data format for presence" (RPID). These attributes are specified by XML elements that extend the PIDF <tuple> element and the <device> and <person> elements defined in the data model.
Настоящая спецификация определяет дополнительные атрибуты присутствия для описания элементов данных человека, услуги и устройства, обобщённо называемые «форматом расширенной информации о присутствии» (RPID). Эти атрибуты задаются XML-элементами, которые расширяют элемент <tuple> PIDF и элементы <device> и <person>, определённые в модели данных.
This extension has two main goals:
Это расширение имеет две основные цели:
1. Provide rich presence information that is at least as powerful as common commercial presence systems. Such feature-parity simplifies transition to systems complying with the Common Profile for Instant Messaging (CPIM) [14], both in terms of user acceptance and protocol conversion.
1. Обеспечить богатую информацию о присутствии, по крайней мере не уступающую по возможностям распространённым коммерческим системам присутствия. Такое равенство функций упрощает переход к системам, соответствующим общему профилю обмена мгновенными сообщениями (CPIM) [14], как с точки зрения принятия пользователями, так и с точки зрения преобразования протоколов.
2. Maintain backward-compatibility with PIDF, so that PIDF-only watchers and gateways can continue to function properly, naturally without access to the functionality described here.
2. Сохранить обратную совместимость с PIDF, чтобы наблюдатели и шлюзы, поддерживающие только PIDF, могли продолжать нормально работать — естественно, без доступа к описанным здесь возможностям.
We make no assumptions as to how the information in the RPID elements is generated. Experience has shown that users are not always diligent about updating their presence status. Thus, we want to make it as easy as possible to derive RPID information from other information sources, such as personal calendars, the status of communication devices such as telephones, typing activity, and physical presence detectors as commonly found in energy-management systems.
Мы не делаем предположений о том, как генерируется информация в элементах RPID. Опыт показывает, что пользователи не всегда тщательно обновляют свой статус присутствия. Поэтому мы хотим максимально упростить получение информации RPID из других источников, таких как личные календари, состояние устройств связи (например, телефонов), активность набора текста и датчики физического присутствия, обычно встречающиеся в системах управления энергопотреблением.
Many of the elements correspond to data commonly found in personal calendars. Thus, we attempted to align some of the extensions with the usage found in calendar formats such as iCal [13].
Многие элементы соответствуют данным, обычно встречающимся в личных календарях. Поэтому мы постарались согласовать некоторые расширения с практикой, принятой в календарных форматах, таких как iCal [13].
The information in a presence document can be generated by a single entity or can be composed from information published by multiple entities.
Информация в документе присутствия может генерироваться одной сущностью или компоноваться из информации, публикуемой несколькими сущностями.
Note that PIDF documents and this extension can be used in two different contexts, namely, by the presentity to publish its presence status and by the presence server to notify some set of watchers. The presence server MAY compose, translate, or filter the published presence state before delivering customized presence information to the watcher. For example, it may merge presence information from multiple presence user agents, remove whole elements, translate values in elements, or remove information from elements. Mechanisms that filter calls and other communications to the presentity can subscribe to this presence information just like a regular watcher and in turn generate automated rules, such as scripts [15], that govern the actual communications behavior of the presentity. Details are described in the data model document.
Обратите внимание, что документы PIDF и это расширение могут использоваться в двух разных контекстах: презентити публикует свой статус присутствия, а сервер присутствия уведомляет некоторый набор наблюдателей. Сервер присутствия МОЖЕТ компоновать, преобразовывать или фильтровать опубликованное состояние присутствия перед доставкой настроенной информации о присутствии наблюдателю. Например, он может объединять информацию о присутствии от нескольких пользовательских агентов присутствия, удалять целые элементы, преобразовывать значения в элементах или удалять информацию из элементов. Механизмы, фильтрующие вызовы и другие коммуникации к презентити, могут подписываться на эту информацию о присутствии как обычный наблюдатель и, в свою очередь, порождать автоматические правила, например сценарии [15], которые управляют фактическим поведением презентити при связи. Подробности описаны в документе модели данных.
Since RPID is a PIDF XML document, it also uses the content type application/pidf+xml.
Поскольку RPID является XML-документом PIDF, он также использует тип содержимого application/pidf+xml.

3.2. Activities Element
3.2. Элемент activities
The <activities> element describes what the person is currently doing, expressed as an enumeration of activity-describing elements. A person can be engaged in multiple activities at the same time, e.g., traveling and having a meal. The <activities> element can be quite helpful to the watcher in judging how appropriate a communication attempt is and which means of communications is most likely to succeed and not annoy the person. The activity indications correspond roughly to the category field in calendar entries, such as Section 4.8.1.2 of RFC 2445 [13].
Элемент <activities> описывает, чем человек занимается в настоящее время, в виде перечисления элементов, описывающих деятельность. Человек может заниматься несколькими делами одновременно, например путешествовать и принимать пищу. Элемент <activities> может быть весьма полезен наблюдателю при оценке того, насколько уместна попытка связи и какое средство связи скорее всего увенчается успехом и не побеспокоит человека. Обозначения деятельности примерно соответствуют полю category в записях календаря, например в разделе 4.8.1.2 RFC 2445 [13].

3.3. Class Element
3.3. Элемент class
The <class> element describes the class of the service, device, or person. Multiple elements can have the same class name within a presence document, but each person, service, or device can only have one class label. The naming of classes is left to the presentity. The presentity can use this information to group similar services, devices, or person elements or to convey information that the presence agent can use for filtering or authorization. This information is not generally presented to the watcher user interface.
Элемент <class> описывает класс услуги, устройства или человека. Несколько элементов могут иметь одно и то же имя класса в пределах документа присутствия, но каждый человек, услуга или устройство может иметь только одну метку класса. Именование классов оставлено на усмотрение презентити. Презентити может использовать эту информацию для группировки похожих элементов услуг, устройств или людей либо для передачи сведений, которые агент присутствия может использовать для фильтрации или авторизации. Обычно эта информация не показывается в пользовательском интерфейсе наблюдателя.

Элемент <class> НЕ ДОЛЖЕН быть дополнен атрибутами 'from' и 'until', как описано в разделе 3.1.

3.13. Time Offset
3.13. Смещение времени
The <time-offset> element describes the number of minutes of offset from UTC at the person's current location. A positive number indicates that the local time-of-day is ahead (i.e., east of) Universal Time, while a negative number indicates that the local time-of-day is behind (i.e., west of) Universal Time. Transitions into and out of daylight savings time may temporarily cause a difference between the true offset from UTC and the time offset element.
Элемент <time-offset> описывает величину смещения от UTC в минутах в текущем местоположении человека. Положительное число означает, что местное время суток опережает всемирное время (то есть находится восточнее его), а отрицательное число означает, что местное время суток отстаёт от всемирного времени (то есть находится западнее его). Переходы на летнее время и обратно могут временно вызывать расхождение между истинным смещением от UTC и элементом смещения времени.
An optional attribute, description, can be used to describe the offset, e.g., by labeling the time zone. This description is meant for human consumption.
Необязательный атрибут description может использоваться для описания смещения, например для обозначения часового пояса. Это описание предназначено для восприятия человеком.
Publishers on mobile devices SHOULD NOT publish this information unless they know the time offset information to reflect the current location. (For example, many laptop users do not update their time zone when traveling.) Publishers SHOULD update the information whenever they discover that their UTC offset has changed.
Издатели на мобильных устройствах НЕ ДОЛЖНЫ публиковать эту информацию, если они не знают, что сведения о смещении времени отражают текущее местоположение. (Например, многие пользователи ноутбуков не обновляют свой часовой пояс при поездках.) Издателям СЛЕДУЕТ обновлять информацию всякий раз, когда они обнаруживают, что их смещение от UTC изменилось.
Example:
Пример:
<time-offset description="America/New_York">-300 </time-offset>
<time-offset description="America/New_York">-300 </time-offset>
3.14. User-Input Element
3.14. Элемент user-input
The <user-input> element records the user-input or usage state of the service or device, based on human user input, e.g., keyboard, pointing device, or voice. If contained in a <person> element, it summarizes any user input activity across all services and devices operated by the presentity. The mechanism for such aggregation is beyond the scope of this document, but generally reflects the most recent user input across all devices and services. The element can assume one of two values, namely, 'active' or 'idle', with an optional 'last-input' attribute that records when the last user input was received. An optional 'idle-threshold' element records how long the presentity will wait before reporting the service or device to be idle, measured in seconds.
Элемент <user-input> фиксирует состояние пользовательского ввода или использования услуги либо устройства на основе ввода человека, например с клавиатуры, указывающего устройства или голосом. Если он содержится в элементе <person>, он обобщает любую активность пользовательского ввода по всем услугам и устройствам, которыми управляет презентити. Механизм такого обобщения выходит за рамки настоящего документа, но обычно отражает самый последний пользовательский ввод по всем устройствам и услугам. Элемент может принимать одно из двух значений: «active» или «idle», с необязательным атрибутом «last-input», фиксирующим, когда был получен последний пользовательский ввод. Необязательный элемент «idle-threshold» фиксирует, как долго презентити будет ждать, прежде чем сообщить, что услуга или устройство бездействует, измеряется в секундах.
(A two-state model was chosen since it would otherwise be necessary to send repeated last-input updates during continuous activity.)
(Двухсостоянийная модель выбрана потому, что иначе при непрерывной активности пришлось бы отправлять повторяющиеся обновления last-input.)
A service that wants to indicate user input activity sends a <user- input> 'active' indication when the user has provided user input within a configurable interval of time, the idle-threshold. If the user ceases to provide input and the idle-threshold has elapsed, the tuple is marked with a <user-input> 'idle' indication instead, optionally including the time of last activity in the 'last-input' attribute. An example is below:
Услуга, желающая указать активность пользовательского ввода, отправляет признак <user-input> «active», когда пользователь обеспечил ввод в течение настраиваемого интервала времени — порога бездействия. Если пользователь перестаёт вводить данные и порог бездействия истёк, кортеж вместо этого помечается признаком <user-input> «idle», необязательно включая время последней активности в атрибуте «last-input». Пример приведён ниже:
<user-input idle-threshold="600"
<user-input idle-threshold="600"
last-input="2004-10-21T13:20:00.000-05:00">idle</user-input>
last-input="2004-10-21T13:20:00.000-05:00">idle</user-input>
Depending on device or service capabilities, user input may be detected only for a particular application, i.e., when the application has user focus or when a user has sent a message or placed a call, or can be based on user input across all applications running on one end system.
В зависимости от возможностей устройства или услуги пользовательский ввод может обнаруживаться только для конкретного приложения, то есть когда приложение имеет фокус пользователя либо когда пользователь отправил сообщение или позвонил, или же может основываться на вводе во всех приложениях, работающих на одной конечной системе.
The <user-input> element may be used by a watcher, typically in combination with other data, to estimate how likely a user is to answer when contacting the service. A tuple that has not been used in a while may still be OPEN, but a watcher may choose to first contact a URI in a tuple that is both OPEN and has been used more recently.
Элемент <user-input> может использоваться наблюдателем, обычно в сочетании с другими данными, для оценки того, насколько вероятно, что пользователь ответит при обращении к услуге. Кортеж, который давно не использовался, может по-прежнему быть OPEN, но наблюдатель может сначала обратиться к URI в кортеже, который одновременно OPEN и использовался недавно.

In particular, the schema allows each element to appear anyhere in PIDF or data-model elements; Table 1 restricts where these elements can appear for semantically valid RPID documents. Elements that do not have from/until parameters MUST NOT appear more than once in each <person>, <tuple>, or <device>.

6. Расширение RPID
Any developer can introduce their own element names, avoiding conflict by choosing an appropriate namespace URI. To add new standardized elements to the enumerations <activities>, <mood>, <privacy>, <relationship> and <service-class>, the extension process described in PIDF [9] is followed, i.e., such extensions would use namespace designators such as urn:ietf:params:xml:ns:pidf:ext, where 'ext' is the name of the extension. Any new values for the <place- type> element are assigned according to [12] and are given a namespace designator at their time of registration. To avoid the unnecessary proliferation of XML namespaces containing a single element, groups of element registrations for each of these enumerations, such as <privacy>, SHOULD be bundled into a single namespace rather than assigning a new namespace to each new element.
Любой разработчик может вводить собственные имена элементов, избегая конфликтов путём выбора подходящего URI пространства имён. Чтобы добавить новые стандартизованные элементы в перечисления <activities>, <mood>, <privacy>, <relationship> и <service-class>, применяется процесс расширения, описанный в PIDF [9], то есть такие расширения должны использовать обозначения пространств имён вроде urn:ietf:params:xml:ns:pidf:ext, где «ext» — имя расширения. Любые новые значения для элемента <place-type> назначаются согласно [12] и получают обозначение пространства имён в момент их регистрации. Чтобы избежать ненужного размножения XML-пространств имён, содержащих один элемент, группы регистраций элементов для каждого из этих перечислений, например <privacy>, СЛЕДУЕТ объединять в одно пространство имён, а не назначать новое пространство имён каждому новому элементу.

8. Internationalization Considerations
8. Вопросы интернационализации
RPID contains mostly tokens that are meant for consumption by programs, not directly by humans. Programs are expected to translate those tokens into language-appropriate text strings according to the preferences of the watcher.
RPID содержит в основном токены, предназначенные для обработки программами, а не непосредственно людьми. Ожидается, что программы переводят эти токены в текстовые строки, соответствующие языку, в соответствии с предпочтениями наблюдателя.
Some elements may contain <note> and <other> elements that can contain free text. These elements SHOULD be labeled with the 'xml: lang' attribute to indicate their language and script. The specification allows multiple occurrences of these elements so that the presentity can convey <note> and <other> elements in multiple scripts and languages. If no 'xml:lang' attribute is provided, the default value is "i-default" [3].
Некоторые элементы могут содержать элементы <note> и <other>, в которых может быть свободный текст. Эти элементы СЛЕДУЕТ помечать атрибутом 'xml:lang', чтобы указать их язык и письменность. Спецификация допускает многократное появление этих элементов, чтобы презентити мог передавать элементы <note> и <other> на нескольких языках и в нескольких системах письма. Если атрибут 'xml:lang' не указан, значением по умолчанию является «i-default» [3].
Since RPID is represented in XML, it provides native support for encoding information using the Unicode character set and its more compact representations including UTF-8. Conformant XML processors recognize both UTF-8 and UTF-16. Though XML includes provisions to identify and use other character encodings through use of an "encoding" attribute in an <?xml?> declaration, use of UTF-8 is RECOMMENDED in environments where parser encoding support incompatibility exists.
Поскольку RPID представлен в XML, он обеспечивает встроенную поддержку кодирования информации с использованием набора символов Unicode и его более компактных представлений, включая UTF-8. Соответствующие XML-процессоры распознают как UTF-8, так и UTF-16. Хотя XML предусматривает идентификацию и использование других кодировок символов через атрибут «encoding» в объявлении <?xml?>, в средах, где существует несовместимость поддержки кодировок анализаторами, РЕКОМЕНДУЕТСЯ использовать UTF-8.

9. Security Considerations
9. Вопросы безопасности
The security considerations in [8] apply, as well as [7]. Compared to PIDF, this presence document format reveals additional information about presentities that can be highly sensitive. Beyond traditional security measures to protect confidentiality and integrity, systems should offer a means to selectively reveal information to particular watchers and to inspect the information that is being published, particularly if it is generated automatically from other sources, such as calendars or sensors. Like any reference to an external object, the <status-icon> may allow the presentity to induce the watcher to retrieve data from a third party (content indirection attack), thus either retrieving harmful content or adding to the server load of the referenced resource.
К вопросам безопасности, изложенным в [8], применяются также [7]. По сравнению с PIDF этот формат документа присутствия раскрывает дополнительную информацию о презентити, которая может быть весьма конфиденциальной. Помимо традиционных мер безопасности для защиты конфиденциальности и целостности, системы должны предоставлять средства для выборочного раскрытия информации определённым наблюдателям и для проверки публикуемой информации, особенно если она автоматически генерируется из других источников, таких как календари или датчики. Как и любая ссылка на внешний объект, <status-icon> может позволить презентити побудить наблюдателя получить данные от третьей стороны (атака косвенного обращения к содержимому), что может привести либо к получению вредоносного содержимого, либо к дополнительной нагрузке на сервер, на который ссылается ресурс.
