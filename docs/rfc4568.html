Abstract
Аннотация
This document defines a Session Description Protocol (SDP) cryptographic attribute for unicast media streams. The attribute describes a cryptographic key and other parameters that serve to configure security for a unicast media stream in either a single message or a roundtrip exchange. The attribute can be used with a variety of SDP media transports, and this document defines how to use it for the Secure Real-time Transport Protocol (SRTP) unicast media streams. The SDP crypto attribute requires the services of a data security protocol to secure the SDP message.
Настоящий документ определяет криптографический атрибут протокола описания сессий (SDP) для одноадресных медиапотоков. Атрибут описывает криптографический ключ и другие параметры, служащие для настройки безопасности одноадресного медиапотока в одном сообщении или при обмене с полным циклом передачи. Атрибут может использоваться с разнообразными медиатранспортами SDP, и настоящий документ определяет, как применять его для одноадресных медиапотоков протокола Secure Real-time Transport Protocol (SRTP). Атрибут SDP crypto требует услуг протокола защиты данных для защиты сообщения SDP.
1. Introduction
1. Введение
The Session Description Protocol (SDP) [RFC4566] describes multimedia sessions, which can be audio, video, whiteboard, fax, modem, and other media streams. Security services such as data origin authentication, integrity, and confidentiality are often needed for those streams. The Secure Real-time Transport Protocol (SRTP) [RFC3711] provides security services for RTP media and is signaled by use of secure RTP transport (e.g., "RTP/SAVP" or "RTP/SAVPF") in an SDP media (m=) line. However, there are no means within SDP itself to configure SRTP beyond using default values. This document specifies a new SDP attribute called "crypto", which is used to signal and negotiate cryptographic parameters for media streams in general, and for SRTP in particular. The definition of the crypto attribute in this document is limited to two-party unicast media streams where each source has a unique cryptographic key; support for multicast media streams or multipoint unicast streams is for further study.
Протокол описания сессий (SDP) [RFC4566] описывает мультимедийные сессии, которые могут быть аудиопотоками, видеопотоками, потоками доски, факса, модема и другими медиапотоками. Для таких потоков часто требуются услуги безопасности, например аутентификация источника данных, целостность и конфиденциальность. Протокол Secure Real-time Transport Protocol (SRTP) [RFC3711] предоставляет услуги безопасности для медиа RTP и сигнализируется путём использования защищённого транспорта RTP (например, «RTP/SAVP» или «RTP/SAVPF») в строке медиа (m=) SDP. Однако в самом SDP нет средств настройки SRTP сверх использования значений по умолчанию. Настоящий документ определяет новый атрибут SDP с именем «crypto», который используется для сигнализации и согласования криптографических параметров для медиапотоков вообще и для SRTP в частности. Определение атрибута crypto в настоящем документе ограничено одноадресными медиапотоками двух сторон, где каждый источник имеет уникальный криптографический ключ; поддержка многоадресных медиапотоков или многоточечных одноадресных потоков оставлена для дальнейшего изучения.
The crypto attribute is defined in a generic way to enable its use with SRTP and any other secure transports that can establish cryptographic parameters with only a single message or in a single round-trip exchange using the offer/answer model [RFC3264]. Extensions to transports other than SRTP, however, is beyond the scope of this document. Each type of secure media transport needs its own specification for the crypto-attribute parameter. These definitions are frequently unique to the particular type of transport and must be specified in a Standards-Track RFC and registered with IANA according to the procedures defined in Section 10. This document defines the security parameters and keying material for SRTP only. It would be self-defeating not to secure cryptographic keys and other parameters at least as well as the data are secured. Data security protocols such as SRTP rely upon a separate key management system to securely establish encryption and/or authentication keys. Key management protocols provide authenticated key establishment (AKE) procedures to authenticate the identity of each endpoint and protect against man-in-the-middle, reflection/replay, connection hijacking, and some denial-of-service attacks [skeme].
Атрибут crypto определён общим образом, чтобы его можно было использовать с SRTP и любыми другими защищёнными транспортами, способными установить криптографические параметры с помощью одного сообщения или за один обмен с полным циклом передачи по модели предложения/ответа [RFC3264]. Расширение на транспорты, отличные от SRTP, однако, выходит за рамки настоящего документа. Каждый тип защищённого медиатранспорта нуждается в собственной спецификации параметра атрибута crypto. Эти определения часто уникальны для конкретного типа транспорта и должны быть заданы в RFC уровня Standards Track и зарегистрированы в IANA согласно процедурам, определённым в разделе 10. Настоящий документ определяет параметры безопасности и ключевой материал только для SRTP. Было бы саморазрушительно не защищать криптографические ключи и другие параметры хотя бы так же хорошо, как защищены данные. Протоколы защиты данных, такие как SRTP, полагаются на отдельную систему управления ключами для безопасного установления ключей шифрования и (или) аутентификации. Протоколы управления ключами предоставляют процедуры аутентифицированного установления ключей (AKE) для аутентификации идентичности каждой конечной точки и защиты от атак «человек посередине», отражения и повторного воспроизведения, перехвата соединения и некоторых атак отказа в обслуживании [skeme].
Along with the key, an AKE protocol such as MIKEY [mikey], GDOI [GDOI], KINK [kink], IKE [ike], Secure Multiparts [s/mime, pgp/mime], or TLS [TLS] securely disseminates information describing both the key and the data- security session. AKE is needed because it is pointless to provide a key over a medium where an attacker can snoop the key, alter the definition of the key to render it useless, or change the parameters of the security session to gain unauthorized access to session- related information.
Вместе с ключом протокол AKE, такой как MIKEY [mikey], GDOI [GDOI], KINK [kink], IKE [ike], Secure Multiparts [s/mime, pgp/mime] или TLS [TLS], надёжно распространяет информацию, описывающую и ключ, и сеанс защиты данных. AKE нужен потому, что бессмысленно передавать ключ по среде, где атакующий может перехватить ключ, изменить определение ключа так, чтобы сделать его бесполезным, или изменить параметры сеанса защиты, чтобы получить несанкционированный доступ к сведениям о сеансе.
SDP, however, was not designed to provide AKE services, and the media security descriptions defined in this document do not add AKE services to SDP. This specification is no replacement for a key management protocol or for the conveyance of key management messages in SDP [keymgt]. The SDP security descriptions defined here are suitable for restricted cases only where IPsec, TLS, or some other encapsulating data-security protocol (e.g., SIP S/MIME) protects the SDP message. This document adds security descriptions to those encrypted and/or authenticated SDP messages through the new SDP "crypto" attribute, which provides the cryptographic parameters of a media stream.
Однако SDP не был предназначен для предоставления услуг AKE, и описания безопасности медиа, определённые в настоящем документе, не добавляют услуги AKE в SDP. Настоящая спецификация не заменяет протокол управления ключами или передачу сообщений управления ключами в SDP [keymgt]. Описания безопасности SDP, определённые здесь, подходят только для ограниченных случаев, когда IPsec, TLS или какой-либо другой инкапсулирующий протокол защиты данных (например, SIP S/MIME) защищает сообщение SDP. Настоящий документ добавляет описания безопасности к этим зашифрованным и (или) аутентифицированным сообщениям SDP через новый атрибут SDP «crypto», который предоставляет криптографические параметры медиапотока.
The "crypto" attribute can be adapted to any media transport, but its precise definition is unique to a particular transport.
Атрибут «crypto» может быть адаптирован к любому медиатранспорту, но его точное определение уникально для конкретного транспорта.

В разделе 6 мы определяем детали атрибута crypto, необходимые для SRTP, а в разделе 7 определяем специфичное для SRTP использование атрибута с моделью предложения/ответа и без неё. Соображения по IANA приведены в разделе 10.

3. Applicability
3. Применимость
RFC 4567 provides similar cryptographic key distribution capabilities and is intended for use when the signaling is to be confidential and/or integrity-protected separately from the keying material.
RFC 4567 предоставляет аналогичные возможности распространения криптографических ключей и предназначен для использования, когда сигнализация должна быть конфиденциальной и (или) защищённой от нарушения целостности отдельно от ключевого материала.
In contrast, this specification carries the keying material within the SDP message, and it is intended for use when the keying material is protected along with the signaling. Implementations MUST employ security mechanisms that provide confidentiality and integrity for the keying material. When this specification is used in the context of SIP [RFC3261], the application SHOULD employ either the SIPS URI or S/MIME to provide protection for the SDP message and the keying material that it contains. The use of transport layer or IP layer security in lieu of the SIPS URI or S/MIME protection is NOT RECOMMENDED since the protection of the SDP message and the keying material that it contains cannot be ensured through all intermediate entities such as SIP proxies.
Напротив, настоящая спецификация переносит ключевой материал внутри сообщения SDP и предназначена для использования, когда ключевой материал защищён вместе с сигнализацией. Реализации ДОЛЖНЫ применять механизмы безопасности, обеспечивающие конфиденциальность и целостность ключевого материала. Когда настоящая спецификация используется в контексте SIP [RFC3261], приложение СЛЕДУЕТ применять либо URI SIPS, либо S/MIME для защиты сообщения SDP и содержащегося в нём ключевого материала. Использование защиты транспортного или IP-уровня вместо защиты через URI SIPS или S/MIME НЕ РЕКОМЕНДУЕТСЯ, поскольку защиту сообщения SDP и содержащегося в нём ключевого материала нельзя гарантировать через все промежуточные объекты, такие как прокси SIP.
4. SDP "Crypto" Attribute and Parameters
4. Атрибут SDP «Crypto» и параметры
A new media-level SDP attribute called "crypto" describes the cryptographic suite, key parameters, and session parameters for the preceding unicast media line. The "crypto" attribute MUST only appear at the SDP media level (not at the session level). The "crypto" attribute follows the format (see Section 9.1 for the formal ABNF grammar):
Новый атрибут SDP уровня медиа с именем «crypto» описывает криптонабор, параметры ключа и параметры сеанса для предшествующей одноадресной строки медиа. Атрибут «crypto» ДОЛЖЕН появляться только на уровне медиа SDP (не на уровне сеанса). Атрибут «crypto» имеет следующий формат (формальная грамматика ABNF приведена в разделе 9.1):
a=crypto:<tag> <crypto-suite> <key-params> [<session-params>]
a=crypto:<tag> <crypto-suite> <key-params> [<session-params>]
The fields tag, crypto-suite, key-params, and session-params are described in the following sub-sections. The values of each of these fields is case-insensitive, unless otherwise noted. However, implementers are encouraged to use the actual case shown in this document and any extensions to it. Note that per normal SDP rules, the "crypto" attribute name itself is case-sensitive. Below, we show an example of the crypto attribute for the "RTP/SAVP" transport, i.e., the secure RTP extension to the Audio/Video Profile [RFC3711]. Поля tag, crypto-suite, key-params и session-params описаны в следующих подразделах. Значения каждого из этих полей нечувствительны к регистру, если не указано иное. Однако разработчикам рекомендуется использовать тот регистр, который показан в настоящем документе и в любых его расширениях. Отметим, что согласно обычным правилам SDP само имя атрибута «crypto» чувствительно к регистру. Ниже приведён пример атрибута crypto для транспорта «RTP/SAVP», то есть расширения безопасного RTP для профиля Audio/Video Profile [RFC3711]. a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:PS1uQCVeeCFCanVmcjkpPywjNWhcYD0mXXtxaVBR|2^20|1:32
a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:PS1uQCVeeCFCanVmcjkpPywjNWhcYD0mXXtxaVBR|2^20|1:32
The crypto-suite is AES_CM_128_HMAC_SHA1_80, key-params is defined by the text starting with "inline:", and session-params is omitted.

4.1. Tag
4.1. Tag
The tag is a decimal number used as an identifier for a particular crypto attribute (see Section 9.1 for details); leading zeroes MUST NOT be used. The tag MUST be unique among all crypto attributes for a given media line. It is used with the offer/answer model to determine which of several offered crypto attributes were chosen by the answerer (see Section 5.1).
tag — десятичное число, используемое как идентификатор конкретного атрибута crypto (подробности см. в разделе 9.1); ведущие нули использоваться НЕ ДОЛЖНЫ. Значение tag ДОЛЖНО быть уникальным среди всех атрибутов crypto для данной строки медиа. Оно используется с моделью предложения/ответа, чтобы определить, какой из нескольких предложенных атрибутов crypto выбрал ответчик (см. раздел 5.1).
In the offer/answer model, the tag is a negotiated parameter.
В модели предложения/ответа tag — согласуемый параметр.
4.2. Crypto-Suite
4.2. Криптонабор
The crypto-suite field is an identifier that describes the encryption and authentication algorithms (e.g., AES_CM_128_HMAC_SHA1_80) for the transport in question (see Section 9.1 for details). The possible values for the crypto-suite parameter are defined within the context of the transport, i.e., each transport defines a separate namespace for the set of crypto-suites. For example, the crypto-suite "AES_CM_128_HMAC_SHA1_80" defined within the context "RTP/SAVP" transport applies to Secure RTP only; the string may be reused for another transport (e.g., "RTP/SAVPF" [srtpf]), but a separate definition would be needed.
Поле crypto-suite — идентификатор, описывающий алгоритмы шифрования и аутентификации (например, AES_CM_128_HMAC_SHA1_80) для рассматриваемого транспорта (подробности см. в разделе 9.1). Возможные значения параметра crypto-suite определяются в контексте транспорта, то есть каждый транспорт определяет отдельное пространство имён для множества криптонаборов. Например, криптонабор «AES_CM_128_HMAC_SHA1_80», определённый в контексте транспорта «RTP/SAVP», применим только к Secure RTP; эта строка может быть повторно использована для другого транспорта (например, «RTP/SAVPF» [srtpf]), но для этого потребовалось бы отдельное определение.
In the offer/answer model, the crypto-suite is a negotiated parameter.
В модели предложения/ответа crypto-suite — согласуемый параметр.
4.3. Key Parameters
4.3. Параметры ключа
The key-params field provides one or more sets of keying material for the crypto-suite in question. The field consists of a method indicator followed by a colon, and the actual keying information as shown below (the formal grammar is provided in Section 9.1):
Поле key-params предоставляет один или несколько наборов ключевого материала для рассматриваемого криптонабора. Поле состоит из индикатора метода, за которым следует двоеточие, и собственно ключевой информации, как показано ниже (формальная грамматика приведена в разделе 9.1):
key-params = <key-method> ":" <key-info>
key-params = <key-method> ":" <key-info>
Keying material might be provided by different means from that for key-params; however, this is out of scope. Only one method is defined in this document, namely, "inline", which indicates that the actual keying material is provided in the key-info field itself. There is a single name space for the key-method, i.e., the key-method is transport independent. New key-methods (e.g., use of a URL) may be defined in a Standards-Track RFC in the future. Although the key-method itself may be generic, the accompanying key-info definition is specific not only to the key-method, but also to the transport in question. Key-info encodes keying material for a crypto suite, which defines that keying material. New key methods MUST be registered with the IANA according to the procedures defined in Section 10.2.1.
Ключевой материал может предоставляться иными средствами, чем key-params; однако это выходит за рамки. В настоящем документе определён только один метод, а именно «inline», который указывает, что собственно ключевой материал предоставляется в самом поле key-info. Для key-method существует единое пространство имён, то есть key-method не зависит от транспорта. Новые методы ключа (например, использование URL) могут быть определены в RFC уровня Standards Track в будущем. Хотя сам key-method может быть общим, сопровождающее его определение key-info зависит не только от метода ключа, но и от рассматриваемого транспорта. Key-info кодирует ключевой материал для криптонабора, который определяет этот ключевой материал. Новые методы ключа ДОЛЖНЫ быть зарегистрированы в IANA согласно процедурам, определённым в разделе 10.2.1.
Key-info is defined as a general octet string (see Section 9.1 for details); further transport and key-method specific syntax and semantics MUST be provided in a Standards-Track RFC for each combination of transport and key-method that uses it; definitions for SRTP are provided in Section 6. Note that such definitions are provided within the context of both a particular transport (e.g., "RTP/SAVP") and a specific key-method (e.g., "inline"). IANA will register the list of supported key methods for each transport.
Key-info определён как общая строка октетов (подробности см. в разделе 9.1); дальнейший синтаксис и семантика, зависящие от транспорта и метода ключа, ДОЛЖНЫ быть приведены в RFC уровня Standards Track для каждой комбинации транспорта и метода ключа, которая их использует; определения для SRTP приведены в разделе 6. Отметим, что такие определения приводятся в контексте как конкретного транспорта (например, «RTP/SAVP»), так и конкретного метода ключа (например, «inline»). IANA будет регистрировать список поддерживаемых методов ключа для каждого транспорта.
When multiple keys are included in the key parameters, it MUST be possible to determine which of the keys is being used in a given media packet by a simple inspection of the media packet received; a trial-and-error approach between the possible keys MUST NOT be performed.
Когда в параметрах ключа содержится несколько ключей, ДОЛЖНА быть возможность определить, какой из ключей используется в данном медиапакете, простым просмотром полученного медиапакета; подход перебора между возможными ключами применяться НЕ ДОЛЖЕН.
For SRTP, this could be achieved by use of Master Key Identifiers (MKI) [RFC3711]. Use of <"From, "To"> values are not supported in SRTP security descriptions for reasons explained in Section 6.1, below.
Для SRTP этого можно достичь использованием идентификаторов главного ключа (MKI) [RFC3711]. Значения <«From», «To»> в описаниях безопасности SRTP не поддерживаются по причинам, объяснённым ниже в разделе 6.1.
In the offer/answer model, the key parameter is a declarative parameter.
В модели предложения/ответа параметр ключа — декларативный параметр.
4.4. Session Parameters
4.4. Параметры сеанса
Session parameters are specific to a given transport and use of them is OPTIONAL in the security descriptions framework, where they are just defined as general character strings. If session parameters are to be used for a given transport, then transport-specific syntax and semantics MUST be provided in a Standards-Track RFC; definitions for SRTP are provided in Section 6.
Параметры сеанса специфичны для данного транспорта, и их использование в структуре описаний безопасности НЕОБЯЗАТЕЛЬНО, где они определяются просто как общие символьные строки. Если для данного транспорта предполагается использовать параметры сеанса, то зависящие от транспорта синтаксис и семантика ДОЛЖНЫ быть приведены в RFC уровня Standards Track; определения для SRTP приведены в разделе 6.
In the offer/answer model, session parameters may be either negotiated or declarative; the definition of specific session parameters MUST indicate whether they are negotiated or declarative. Negotiated parameters apply to data sent in both directions, whereas declarative parameters apply only to media sent by the entity that generated the SDP. Thus, a declarative parameter in an offer applies to media sent by the offerer, whereas a declarative parameter in an answer applies to media sent by the answerer.
В модели предложения/ответа параметры сеанса могут быть согласуемыми или декларативными; определение конкретных параметров сеанса ДОЛЖНО указывать, являются они согласуемыми или декларативными. Согласуемые параметры применяются к данным, передаваемым в обоих направлениях, тогда как декларативные параметры применяются только к медиа, передаваемым объектом, сформировавшим SDP. Так, декларативный параметр в предложении применяется к медиа, передаваемым автором предложения, а декларативный параметр в ответе применяется к медиа, передаваемым ответчиком.

5. General Use of the crypto Attribute
5. Общее использование атрибута crypto
In this section, we describe the general use of the crypto attribute outside of any transport or key-method specific rules.
В этом разделе мы описываем общее использование атрибута crypto вне каких-либо правил, специфичных для транспорта или метода ключа.
5.1. Use with Offer/Answer
5.1. Использование с предложением/ответом
The general offer/answer rules for the crypto attribute are in addition to the rules specified in RFC 3264, which MUST be followed, unless otherwise noted. RFC 3264 defines operation for both unicast and multicast streams; the sections below describe operation for two-party unicast streams only, since support for multicast streams (and multipoint unicast streams) is for further study.
Общие правила предложения/ответа для атрибута crypto дополняют правила, заданные в RFC 3264, которым ДОЛЖНО следовать, если не указано иное. RFC 3264 определяет работу как для одноадресных, так и для многоадресных потоков; разделы ниже описывают работу только для одноадресных потоков двух сторон, поскольку поддержка многоадресных потоков (и многоточечных одноадресных потоков) оставлена для дальнейшего изучения.
5.1.1. Generating the Initial Offer - Unicast Streams
5.1.1. Формирование начального предложения — одноадресные потоки
When generating an initial offer for a unicast stream, there MUST be one or more crypto attributes present for each media stream for which security is desired. Each crypto attribute for a given media stream MUST contain a unique tag.
При формировании начального предложения для одноадресного потока для каждого медиапотока, для которого желательна безопасность, ДОЛЖЕН присутствовать один или несколько атрибутов crypto. Каждый атрибут crypto для данного медиапотока ДОЛЖЕН содержать уникальный tag.
The ordering of multiple "a=crypto" lines is significant: the most preferred crypto line is listed first. Each crypto attribute describes the crypto-suite, key(s), and possibly session parameters offered for the media stream. In general, a "more preferred" crypto-suite SHOULD be cryptographically stronger than a "less preferred" crypto-suite.
Порядок нескольких строк «a=crypto» значим: наиболее предпочтительная строка crypto указана первой. Каждый атрибут crypto описывает криптонабор, ключ (ключи) и, возможно, параметры сеанса, предложенные для медиапотока. В общем случае «более предпочтительный» криптонабор СЛЕДУЕТ выбирать криптографически более стойким, чем «менее предпочтительный».
The crypto-suite always applies to media in the directions supported by the media stream (e.g., send and receive). The key(s), however, apply to data packets (e.g., SRTP and SRTCP packets) that will be sent by the same party that generated the SDP. That is, each endpoint determines its own transmission keys and sends those keys, in SDP, to the other endpoint.
Криптонабор всегда применяется к медиа в направлениях, поддерживаемых медиапотоком (например, отправка и приём). Ключ (ключи), однако, применяются к пакетам данных (например, пакетам SRTP и SRTCP), которые будет отправлять та же сторона, что сформировала SDP. То есть каждая конечная точка определяет свои собственные ключи передачи и отправляет эти ключи в SDP другой конечной точке.
This is done for consistency. Also, in the case of SRTP, for example, secure RTCP will still be flowing in both the send and receive direction for a unidirectional stream.
Это делается для согласованности. Кроме того, например, в случае SRTP защищённый RTCP всё равно будет идти в направлениях отправки и приёма для однонаправленного потока.
The inline parameter conveys the keying material used by an endpoint to encrypt the media streams transmitted by that endpoint. The same keying material is used by the recipient to decrypt those streams.
Параметр inline передаёт ключевой материал, используемый конечной точкой для шифрования медиапотоков, передаваемых этой конечной точкой. Тот же ключевой материал используется получателем для расшифровки этих потоков.
The offer may include session parameters. There are no general offer rules for the session parameters; instead, specific rules may be provided as part of the transport-specific definitions of any session parameters. When issuing an offer, the offerer MUST be prepared to support media security in accordance with any of the crypto attributes included in the offer. There are, however, two problems associated with this. First of all, the offerer does not know which key the answerer will be using for media sent to the offerer. Second, the offerer may not be able to deduce which of the offered crypto attributes were accepted. Since media may arrive prior to the answer, delay or clipping can occur. If this is unacceptable to the offerer, the offerer SHOULD use a mechanism outside the scope of this document to prevent the above problem.
Предложение может включать параметры сеанса. Общих правил предложения для параметров сеанса нет; вместо этого конкретные правила могут быть приведены как часть зависящих от транспорта определений любых параметров сеанса. Выдавая предложение, автор предложения ДОЛЖЕН быть готов поддержать безопасность медиа в соответствии с любым из атрибутов crypto, включённых в предложение. Однако с этим связаны две проблемы. Во-первых, автор предложения не знает, какой ключ ответчик будет использовать для медиа, отправляемых автору предложения. Во-вторых, автор предложения может быть не в состоянии определить, какие из предложенных атрибутов crypto были приняты. Поскольку медиа может прийти до ответа, возможны задержка или обрезка. Если это неприемлемо для автора предложения, автор предложения СЛЕДУЕТ использовать механизм вне рамок настоящего документа, чтобы предотвратить указанную проблему.
For example, in SIP [RFC3261], a "security" precondition as defined in [sprecon] could solve the above problem.
Например, в SIP [RFC3261] предусловие «security», как определено в [sprecon], могло бы решить указанную проблему.
5.1.2. Generating the Initial Answer - Unicast Streams
5.1.2. Формирование начального ответа — одноадресные потоки
When the answerer receives the initial offer with one or more crypto attributes for a given unicast media stream, the answerer MUST either accept exactly one of the offered crypto attributes, or the offered stream MUST be rejected.
Когда ответчик получает начальное предложение с одним или несколькими атрибутами crypto для данного одноадресного медиапотока, ответчик ДОЛЖЕН либо принять ровно один из предложенных атрибутов crypto, либо предложенный поток ДОЛЖЕН быть отклонён.
If the answerer wishes to indicate support for other crypto attributes, those can be listed by use of the SDP Simple Capability Declaration [RFC3407] extensions.
Если ответчик желает указать поддержку других атрибутов crypto, их можно перечислить с помощью расширений SDP Simple Capability Declaration [RFC3407].
Only crypto attributes that are valid can be accepted; valid attributes do not violate any of the general rules defined for security descriptions, nor any specific rules defined for the transport and key-method in question. When selecting one of the valid crypto attributes, the answerer SHOULD select the most preferred crypto attribute it can support, i.e., the first valid supported crypto attribute in the list, according to the answerer's capabilities and security policies.
Принимать можно только действительные атрибуты crypto; действительные атрибуты не нарушают ни одного из общих правил, определённых для описаний безопасности, ни каких-либо конкретных правил, определённых для рассматриваемого транспорта и метода ключа. Выбирая один из действительных атрибутов crypto, ответчик СЛЕДУЕТ выбирать наиболее предпочтительный атрибут crypto, который он может поддержать, то есть первый действительный поддерживаемый атрибут crypto в списке, в соответствии с возможностями и политиками безопасности ответчика.
If there are one or more crypto attributes in the offer, but none of them are valid or none of the valid ones are supported, the offered media stream MUST be rejected.
Если в предложении есть один или несколько атрибутов crypto, но ни один из них не действителен или ни один из действительных не поддерживается, предложенный медиапоток ДОЛЖЕН быть отклонён.
When an offered crypto attribute is accepted, the crypto attribute in the answer MUST contain the following:
Когда предложенный атрибут crypto принят, атрибут crypto в ответе ДОЛЖЕН содержать следующее:
* The tag and crypto-suite from the accepted crypto attribute in the offer (the same crypto-suite MUST be used in the send and receive direction).
* tag и crypto-suite из принятого атрибута crypto в предложении (один и тот же crypto-suite ДОЛЖЕН использоваться в направлениях отправки и приёма).
* The key(s) the answerer will be using for media sent to the offerer. Note that a key MUST be provided, irrespective of any direction attributes in the offer or answer.
* Ключ (ключи), которые ответчик будет использовать для медиа, отправляемых автору предложения. Отметим, что ключ ДОЛЖЕН быть предоставлен независимо от каких-либо атрибутов направления в предложении или ответе.
Furthermore, any session parameters that are negotiated MUST be included in the answer. Declarative session parameters provided by the offerer are not included in the answer; however, the answerer may provide its own set of declarative session parameters.
Кроме того, любые согласованные параметры сеанса ДОЛЖНЫ быть включены в ответ. Декларативные параметры сеанса, предоставленные автором предложения, в ответ не включаются; однако ответчик может предоставить свой собственный набор декларативных параметров сеанса.
Once the answerer has accepted one of the offered crypto attributes, the answerer MAY begin sending media to the offerer in accordance with the selected crypto attribute. Note, however, that the offerer may not be able to process such media packets correctly until the answer has been received.
Как только ответчик принял один из предложенных атрибутов crypto, ответчик МОЖЕТ начать отправку медиа автору предложения в соответствии с выбранным атрибутом crypto. Отметим, однако, что автор предложения может быть не в состоянии корректно обработать такие медиапакеты до получения ответа.
5.1.3. Processing of the Initial Answer - Unicast Streams
5.1.3. Обработка начального ответа — одноадресные потоки
When the offerer receives the answer, the offerer MUST verify that one of the initially offered crypto suites and its accompanying tag were accepted and echoed in the answer. Also, the answer MUST include one or more keys, which will be used for media sent from the answerer to the offerer.
Когда автор предложения получает ответ, автор предложения ДОЛЖЕН проверить, что один из первоначально предложенных криптонаборов и сопровождающий его tag были приняты и повторены в ответе. Кроме того, ответ ДОЛЖЕН включать один или несколько ключей, которые будут использоваться для медиа, отправляемых от ответчика автору предложения.
If the offer contained any mandatory negotiated session parameters (see Section 6.3.7), the offerer MUST verify that said parameters are included in the answer and support them. If the answer contains any mandatory declarative session parameters, the offerer MUST be able to support those.
Если предложение содержало какие-либо обязательные согласуемые параметры сеанса (см. раздел 6.3.7), автор предложения ДОЛЖЕН проверить, что указанные параметры включены в ответ, и поддержать их. Если ответ содержит какие-либо обязательные декларативные параметры сеанса, автор предложения ДОЛЖЕН быть в состоянии их поддержать.
If any of the above fails, the negotiation MUST fail.
Если что-либо из вышеперечисленного не выполняется, согласование ДОЛЖНО завершиться неудачей.
5.1.4. Modifying the Session
5.1.4. Изменение сеанса
Once a media stream has been established, it MAY be modified at any time, as described in RFC 3264, Section 8. Such a modification MAY be triggered by the security service, e.g., in order to perform a re-keying or change the crypto-suite. If media stream security using the general security descriptions defined here is still desired, the crypto attribute MUST be included in these new offer/answer exchanges. The procedures are similar to those defined in Section 5.1.1, 5.1.2, and 5.1.3 of this document, subject to the considerations provided in RFC 3264, Section 8.
После установления медиапотока он МОЖЕТ быть изменён в любое время, как описано в RFC 3264, раздел 8. Такое изменение МОЖЕТ быть инициировано службой безопасности, например для выполнения перевыработки ключей или изменения криптонабора. Если безопасность медиапотока с использованием общих описаний безопасности, определённых здесь, всё ещё желательна, атрибут crypto ДОЛЖЕН быть включён в эти новые обмены предложения/ответа. Процедуры аналогичны определённым в разделах 5.1.1, 5.1.2 и 5.1.3 настоящего документа, с учётом соображений, приведённых в RFC 3264, раздел 8.
5.2. Use Outside Offer/Answer
5.2. Использование вне предложения/ответа
The crypto attribute can also be used outside the context of offer/answer where there is no negotiation of the crypto suite, cryptographic key, or session parameters. In this case, the sender determines security parameters for the stream. Since there is no negotiation mechanism, the sender MUST include exactly one crypto attribute, and the receiver MUST either accept it or SHOULD NOT receive the associated stream. The sender SHOULD select the security description that it deems most secure for its purposes.
Атрибут crypto может также использоваться вне контекста предложения/ответа, где нет согласования криптонабора, криптографического ключа или параметров сеанса. В этом случае отправитель определяет параметры безопасности для потока. Поскольку механизма согласования нет, отправитель ДОЛЖЕН включить ровно один атрибут crypto, а получатель ДОЛЖЕН либо принять его, либо НЕ ДОЛЖЕН принимать связанный поток. Отправителю СЛЕДУЕТ выбирать описание безопасности, которое он считает наиболее безопасным для своих целей.
5.3. General Backwards Compatibility Considerations
5.3. Общие соображения обратной совместимости
In the offer/answer model, it is possible that the answerer supports a given secure transport (e.g., "RTP/SAVP") and accepts the offered media stream, but that the answerer does not support the crypto attribute defined in this document and hence ignores it. The offerer can recognize this situation by seeing an accepted media stream in the answer that does not include a crypto line. In that case, the security negotiation defined here MUST fail.
В модели предложения/ответа возможно, что ответчик поддерживает данный защищённый транспорт (например, «RTP/SAVP») и принимает предложенный медиапоток, но не поддерживает атрибут crypto, определённый в настоящем документе, и поэтому игнорирует его. Автор предложения может распознать эту ситуацию, увидев в ответе принятый медиапоток, который не содержит строки crypto. В этом случае согласование безопасности, определённое здесь, ДОЛЖНО завершиться неудачей.
Similar issues exist when security descriptions are used outside the offer/answer model. But the source of a non-negotiated security description has no indication that the receiver has ignored the crypto attribute.
Аналогичные проблемы существуют, когда описания безопасности используются вне модели предложения/ответа. Но источник несогласованного описания безопасности не имеет указания на то, что получатель проигнорировал атрибут crypto.
6. SRTP Security Descriptions
6. Описания безопасности SRTP
In this section, we provide definitions for security descriptions for SRTP media streams. In the next section, we define how to use SRTP security descriptions with and without the offer/answer model.
В этом разделе мы приводим определения описаний безопасности для медиапотоков SRTP. В следующем разделе мы определяем, как использовать описания безопасности SRTP с моделью предложения/ответа и без неё.
SRTP security descriptions MUST only be used with the SRTP transport (e.g., "RTP/SAVP" or "RTP/SAVPF"). The following specifies security descriptions for the "RTP/SAVP" profile, defined in [RFC3711]. However, it is expected that other secure RTP profiles (e.g., "RTP/SAVPF") can use the same descriptions, which are in accordance with the SRTP protocol specification [RFC3711].
Описания безопасности SRTP ДОЛЖНЫ использоваться только с транспортом SRTP (например, «RTP/SAVP» или «RTP/SAVPF»). Далее определяются описания безопасности для профиля «RTP/SAVP», определённого в [RFC3711]. Однако ожидается, что другие профили защищённого RTP (например, «RTP/SAVPF») могут использовать те же описания, которые соответствуют спецификации протокола SRTP [RFC3711].
There is no assurance that an endpoint is capable of configuring its SRTP service with a particular crypto attribute parameter, but SRTP guarantees minimal interoperability among SRTP endpoints through the default SRTP parameters [RFC3711]. More capable SRTP endpoints support a variety of parameter values beyond the SRTP defaults, and these values can be configured by the SRTP security descriptions defined here. An endpoint that does not support the crypto attribute will ignore it according to the SDP. Such an endpoint will not correctly process the particular media stream. By using the Offer/Answer model, the offerer and answerer can negotiate the crypto parameters to be used before commencement of the multimedia session (see Section 7.1).
Нет гарантии, что конечная точка способна настроить свою службу SRTP с конкретным параметром атрибута crypto, но SRTP гарантирует минимальную совместимость между конечными точками SRTP благодаря параметрам SRTP по умолчанию [RFC3711]. Более развитые конечные точки SRTP поддерживают разнообразные значения параметров сверх значений SRTP по умолчанию, и эти значения можно настроить с помощью описаний безопасности SRTP, определённых здесь. Конечная точка, не поддерживающая атрибут crypto, проигнорирует его согласно SDP. Такая конечная точка не будет корректно обрабатывать данный медиапоток. Используя модель предложения/ответа, автор предложения и ответчик могут согласовать криптографические параметры, которые будут использоваться до начала мультимедийной сессии (см. раздел 7.1).

6.1. SRTP Key Parameter
6.1. Параметр ключа SRTP
SRTP security descriptions define the use of the "inline" key method as described in the following. Use of any other keying method (e.g., URL) for SRTP security descriptions is for further study.
Описания безопасности SRTP определяют использование метода ключа «inline», как описано ниже. Использование любого другого метода ключа (например, URL) для описаний безопасности SRTP оставлено для дальнейшего изучения.
The "inline" type of key contains the keying material (master key and salt) and all policy related to that master key, including how long it can be used (lifetime) and whether it uses a master key identifier (MKI) to associate an incoming SRTP packet with a particular master key. Compliant implementations obey the policies associated with a master key and MUST NOT accept incoming packets that violate the policy (e.g., after the master key lifetime has expired).
Тип ключа «inline» содержит ключевой материал (главный ключ и соль) и всю политику, связанную с этим главным ключом, включая то, как долго его можно использовать (время жизни), и использует ли он идентификатор главного ключа (MKI) для связи входящего пакета SRTP с конкретным главным ключом. Соответствующие реализации подчиняются политике, связанной с главным ключом, и НЕ ДОЛЖНЫ принимать входящие пакеты, нарушающие политику (например, после истечения времени жизни главного ключа).
The key parameter contains one or more cryptographic master keys, each of which MUST be a unique cryptographically random [RFC1750] value with respect to other master keys in the entire SDP message (i.e., including master keys for other streams). Each key follows the format (the formal definition is provided in Section 9.2):
Параметр ключа содержит один или несколько криптографических главных ключей, каждый из которых ДОЛЖЕН быть уникальным криптографически случайным [RFC1750] значением относительно других главных ключей во всём сообщении SDP (то есть включая главные ключи для других потоков). Каждый ключ имеет следующий формат (формальное определение приведено в разделе 9.2):
"inline:" <key||salt> ["|" lifetime] ["|" MKI ":" length]
«inline:» <key||salt> [«|» lifetime] [«|» MKI «:» length] key||salt
key||salt concatenated master key and salt, base64 encoded (see [RFC3548], Section 3) lifetime master key lifetime (max number of SRTP or SRTCP packets using this master key) MKI:length MKI and length of the MKI field in SRTP packets
— конкатенация главного ключа и соли, закодированная в base64 (см. [RFC3548], раздел 3); lifetime — время жизни главного ключа (максимальное число пакетов SRTP или SRTCP с использованием этого главного ключа); MKI:length — MKI и длина поля MKI в пакетах SRTP.

inline:d0RmdmcmVCspeEc3QGZiNWpVLFJhQX1cfHAwJSoj|2^20|1:4
inline:d0RmdmcmVCspeEc3QGZiNWpVLFJhQX1cfHAwJSoj|2^20|1:4
The first field ("d0RmdmcmVCspeEc3QGZiNWpVLFJhQX1cfHAwJSoj") of the parameter is the cryptographic master key appended with the master salt; the two are first concatenated and then base64 encoded. The length of the concatenated key and salt is determined by the crypto- suite for which the key applies. If the length (after being decoded from base64) does not match that specified for the crypto-suite, the crypto attribute in question MUST be considered invalid. Each master key and salt MUST be a cryptographically random number and MUST be unique to the entire SDP message. When base64 decoding the key and salt, padding characters (i.e., one or two "=" at the end of the base64-encoded data) are discarded (see [RFC3548] for details). Base64 encoding assumes that the base64 encoding input is an integral number of octets. If a given crypto-suite requires the use of a concatenated key and salt with a length that is not an integral number of octets, said crypto-suite MUST define a padding scheme that results in the base64 input being an integral number of octets. For example, if the length defined were 250 bits, then 6 padding bits would be needed, which could be defined to be the last 6 bits in a 256 bit input.
Первое поле («d0RmdmcmVCspeEc3QGZiNWpVLFJhQX1cfHAwJSoj») параметра — криптографический главный ключ, к которому добавлена главная соль; сначала эти две величины конкатенируются, а затем кодируются в base64. Длина конкатенированных ключа и соли определяется криптонабором, к которому относится ключ. Если длина (после декодирования из base64) не соответствует указанной для криптонабора, рассматриваемый атрибут crypto ДОЛЖЕН считаться недействительным. Каждый главный ключ и соль ДОЛЖНЫ быть криптографически случайным числом и ДОЛЖНЫ быть уникальными для всего сообщения SDP. При декодировании ключа и соли из base64 символы заполнения (то есть один или два «=» в конце данных, закодированных в base64) отбрасываются (подробности см. в [RFC3548]). Кодирование base64 предполагает, что входные данные кодирования base64 составляют целое число октетов. Если данный криптонабор требует использования конкатенированных ключа и соли с длиной, не являющейся целым числом октетов, указанный криптонабор ДОЛЖЕН определять схему заполнения, при которой входные данные base64 составляют целое число октетов. Например, если была бы определена длина 250 бит, потребовалось бы 6 бит заполнения, которые можно определить как последние 6 бит 256-битного входа.
The second field is the OPTIONAL lifetime of the master key as measured in maximum number of SRTP or SRTCP packets using that master key (i.e., the number of SRTP packets and the number of SRTCP packets each have to be less than the lifetime). The lifetime value MAY be written as a non-zero, positive decimal integer or as a power of 2 (see the grammar in Section 9.2 for details); leading zeroes MUST NOT be used. The "lifetime" value MUST NOT exceed the maximum packet lifetime for the crypto-suite. If the lifetime is too large or otherwise invalid, then the entire crypto attribute MUST be considered invalid. The default MAY be implicitly signaled by omitting the lifetime (note that the lifetime field never includes a colon, whereas the third field always does). This is convenient when the SRTP cryptographic key lifetime is the default value. As a shortcut to avoid long decimal values, the syntax of the lifetime allows using the literal "2^", which indicates "two to the power of". The example above shows a case where the lifetime is specified as 2^20. The following example, which is for the AES_CM_128_HMAC_SHA1_80 crypto-suite, has a default for the lifetime field, which means that SRTP's and SRTCP's default values will be used (see [RFC3711]):
Второе поле — НЕОБЯЗАТЕЛЬНОЕ время жизни главного ключа, измеряемое максимальным числом пакетов SRTP или SRTCP с использованием этого главного ключа (то есть число пакетов SRTP и число пакетов SRTCP должно быть меньше времени жизни). Значение lifetime МОЖЕТ быть записано как ненулевое положительное десятичное целое число или как степень 2 (подробности см. в грамматике раздела 9.2); ведущие нули использоваться НЕ ДОЛЖНЫ. Значение «lifetime» НЕ ДОЛЖНО превышать максимальное время жизни пакета для криптонабора. Если время жизни слишком велико или иным образом недействительно, то весь атрибут crypto ДОЛЖЕН считаться недействительным. Значение по умолчанию МОЖЕТ быть неявно просигнализировано путём опускания lifetime (отметим, что поле lifetime никогда не содержит двоеточия, тогда как третье поле всегда его содержит). Это удобно, когда время жизни криптографического ключа SRTP равно значению по умолчанию. Как сокращение, позволяющее избежать длинных десятичных значений, синтаксис lifetime допускает использование литерала «2^», который означает «два в степени». Пример выше показывает случай, когда время жизни задано как 2^20. Следующий пример, относящийся к криптонабору AES_CM_128_HMAC_SHA1_80, имеет значение по умолчанию для поля lifetime, что означает использование значений SRTP и SRTCP по умолчанию (см. [RFC3711]):
inline:YUJDZGVmZ2hpSktMbW9QUXJzVHVWd3l6MTIzNDU2|1066:4
inline:YUJDZGVmZ2hpSktMbW9QUXJzVHVWd3l6MTIzNDU2|1066:4

Пример показывает 30-октетный ключ и конкатенированную соль, закодированные в base64: 30-октетная конкатенация ключа и соли расширяется до 40 символов (октетов) благодаря кодированию base64 по схеме «три в четырёх».
The third field, which is also OPTIONAL, is the Master Key Identifier (MKI) and its byte length.
Третье поле, которое также НЕОБЯЗАТЕЛЬНО, — идентификатор главного ключа (MKI) и его длина в байтах.
"MKI" is the master key identifier associated with the SRTP master key. The MKI is here defined as a positive decimal integer that is encoded as a big-endian integer in the actual SRTP packets; leading zeroes MUST NOT be used in the integer representation. If the MKI is given, then the length of the MKI MUST also be given and separated from the MKI by a colon (":"). The MKI length is the size of the MKI field in the SRTP packet, specified in bytes as a decimal integer; leading zeroes MUST NOT be used. If the MKI length is not given or its value exceeds 128 (bytes), then the entire crypto attribute MUST be considered invalid. The substring "1:4" in the first example assigns to the key a master key identifier of 1 that is 4 bytes long, and the second example assigns a 4-byte master key identifier of 1066 to the key. One or more master keys with their associated MKI can be initially defined, and then later updated, or deleted and new ones defined.
«MKI» — идентификатор главного ключа, связанный с главным ключом SRTP. Здесь MKI определён как положительное десятичное целое число, которое кодируется как целое число с обратным порядком байтов (big-endian) в собственно пакетах SRTP; ведущие нули в представлении целого числа использоваться НЕ ДОЛЖНЫ. Если MKI задан, то длина MKI также ДОЛЖНА быть задана и отделена от MKI двоеточием («:»). Длина MKI — это размер поля MKI в пакете SRTP, заданный в байтах как десятичное целое число; ведущие нули использоваться НЕ ДОЛЖНЫ. Если длина MKI не задана или её значение превышает 128 (байт), то весь атрибут crypto ДОЛЖЕН считаться недействительным. Подстрока «1:4» в первом примере назначает ключу идентификатор главного ключа 1 длиной 4 байта, а второй пример назначает ключу 4-байтовый идентификатор главного ключа 1066. Один или несколько главных ключей вместе со связанными с ними MKI можно сначала определить, а затем позже обновить, либо удалить и определить новые.
SRTP offers a second feature for specifying the lifetime of a master key in terms of two values, called "From" and "To," which are defined on the SRTP sequence number space [RFC3711]. This SRTP Security Descriptions specification, however, does not support the <"From", "To"> feature since the lifetime of an AES master key is 2^48 SRTP packets, which means that there is no cryptographic reason to replace a master key for practical point-to-point applications. For this reason, there is no need to support two means for signaling key update. The MKI is chosen over <"From", "To"> by this specification for the very few applications that need it since the MKI feature is simpler (though the MKI adds additional bytes to each packet, whereas <"From", "To"> does not). As mentioned above, the key parameter can contain one or more master keys. When the key parameter contains more than one master key, all the master keys in that key parameter MUST include an MKI value.
SRTP предлагает вторую возможность задавать время жизни главного ключа через две величины, называемые «From» и «To», которые определены в пространстве порядковых номеров SRTP [RFC3711]. Однако настоящая спецификация описаний безопасности SRTP не поддерживает возможность <«From», «To»>, поскольку время жизни главного ключа AES составляет 2^48 пакетов SRTP, а значит, нет криптографической причины заменять главный ключ в практических приложениях «точка — точка». По этой причине нет необходимости поддерживать два средства сигнализации обновления ключа. Для тех очень немногих приложений, которым это нужно, настоящая спецификация выбирает MKI вместо <«From», «To»>, поскольку возможность MKI проще (хотя MKI добавляет дополнительные байты к каждому пакету, а <«From», «To»> — нет). Как упомянуто выше, параметр ключа может содержать один или несколько главных ключей. Когда параметр ключа содержит более одного главного ключа, все главные ключи в этом параметре ключа ДОЛЖНЫ включать значение MKI.
When using the MKI, the MKI length MUST be the same for all keys in a given crypto attribute.
При использовании MKI длина MKI ДОЛЖНА быть одинаковой для всех ключей в данном атрибуте crypto.

Длина главного ключа — 128 бит, время жизни по умолчанию — не более 2^48 пакетов SRTP или 2^31 пакетов SRTCP, в зависимости от того, что наступит раньше [страница 39, srtp].

SRTP допускает 2^48 пакетов SRTP или 2^31 пакетов SRTCP, в зависимости от того, что наступит раньше. Однако РЕКОМЕНДУЕТСЯ, чтобы автоматическое управление ключами допускало простую и эффективную перевыработку ключей через интервалы, намного меньшие 2^31 пакетов, учитывая сегодняшние скорости медиа или даже скорости медиа HDTV.
The SRTP and SRTCP encryption key lengths are 128 bits. The SRTP and SRTCP authentication key lengths are 160 bits (see Security Considerations in Section 8). The master salt value is 112 bits in length and the session salt value is 112 bits in length. The pseudo-random function (PRF) is the default SRTP pseudo-random function that uses AES Counter Mode with a 128-bit key length.

Значение главной соли имеет длину 112 бит, и значение сеансовой соли имеет длину 112 бит. Псевдослучайная функция (PRF) — это псевдослучайная функция SRTP по умолчанию, использующая AES Counter Mode с длиной ключа 128 бит.
The length of the base64-decoded key and salt value for this crypto- suite MUST be 30 characters (i.e., 240 bits); otherwise, the crypto attribute is considered invalid.
Длина декодированного из base64 значения ключа и соли для этого криптонабора ДОЛЖНА быть 30 символов (то есть 240 бит); в противном случае атрибут crypto считается недействительным.

Описания безопасности SRTP определяют набор параметров «сеанса», которые НЕОБЯЗАТЕЛЬНО могут использоваться для переопределения значений по умолчанию сеанса SRTP для потоков SRTP и SRTCP. 6.3.1. KDR=n

6.4. SRTP Crypto Context Initialization
6.4. Инициализация криптографического контекста SRTP
In addition to the various SRTP parameters defined above, there are three pieces of information that are critical to the operation of the default SRTP ciphers:
В дополнение к различным параметрам SRTP, определённым выше, есть три элемента информации, критичных для работы шифров SRTP по умолчанию:
* SSRC: Synchronization source * ROC: Roll-over counter for a given SSRC * SEQ: Sequence number for a given SSRC
* SSRC: синхронизирующий источник * ROC: счётчик переполнения для данного SSRC * SEQ: порядковый номер для данного SSRC
In a unicast session, as defined here, there are three constraints on these values.
В одноадресной сессии, как определено здесь, на эти значения накладываются три ограничения.
The first constraint is on the SSRC, which makes an SRTP keystream unique from other participants. As explained in SRTP, the keystream MUST NOT be reused on two or more different pieces of plaintext. Keystream reuse makes the ciphertext vulnerable to cryptanalysis. One vulnerability is that known-plaintext fields in one stream can expose portions of the reused keystream, and this could further expose more plaintext in other streams. Since all current SRTP encryption transforms use keystreams, key sharing is a general problem [RFC3711]. SRTP mitigates this problem by including the SSRC of the sender in the keystream. But SRTP does not solve this problem in its entirety because the Real-time Transport Protocol has SSRC collisions, which although very rare [RFC3550] are quite possible. During a collision, two or more SSRCs that share a master key will have identical keystreams for overlapping portions of the RTP sequence number space. SRTP Security Descriptions avoid keystream reuse by making unique master keys REQUIRED for the sender and receiver of the security description. Thus, the first constraint is satisfied.
Первое ограничение относится к SSRC, который делает поток ключей SRTP уникальным относительно других участников. Как объяснено в SRTP, поток ключей НЕ ДОЛЖЕН повторно использоваться на двух или более различных фрагментах открытого текста. Повторное использование потока ключей делает зашифрованный текст уязвимым для криптоанализа. Одна из уязвимостей состоит в том, что поля известного открытого текста в одном потоке могут раскрыть части повторно использованного потока ключей, а это может дополнительно раскрыть больше открытого текста в других потоках. Поскольку все современные преобразования шифрования SRTP используют потоки ключей, совместное использование ключей является общей проблемой [RFC3711]. SRTP смягчает эту проблему, включая SSRC отправителя в поток ключей. Но SRTP не решает эту проблему полностью, поскольку в протоколе реального времени RTP возможны коллизии SSRC, которые, хотя и очень редки [RFC3550], вполне возможны. При коллизии два или более SSRC, использующих общий главный ключ, будут иметь идентичные потоки ключей для перекрывающихся частей пространства порядковых номеров RTP. Описания безопасности SRTP избегают повторного использования потока ключей, требуя уникальных главных ключей для отправителя и получателя описания безопасности. Таким образом, первое ограничение выполняется.
Also note that there is a second problem with SSRC collisions: the SSRC is used to identify the crypto context and thereby the cipher, key, ROC, etc. to process incoming packets.
Отметим также, что с коллизиями SSRC связана вторая проблема: SSRC используется для идентификации криптографического контекста и тем самым шифра, ключа, ROC и т. д. для обработки входящих пакетов.
In case of SSRC collisions, crypto context identification becomes ambiguous and correct packet processing may not occur. Furthermore, if an RTCP BYE packet is to be sent for a colliding SSRC, that packet may also have to be secured. In a (unicast) point-to-multipoint scenario, this can be problematic for the same reasons, i.e., it is not known which of the possible crypto contexts to use. Note that these problems are not unique to the SDP security descriptions; any use of SRTP needs to consider them.
В случае коллизий SSRC идентификация криптографического контекста становится неоднозначной, и корректная обработка пакетов может не выполняться. Кроме того, если для конфликтующего SSRC нужно отправить пакет RTCP BYE, этот пакет также может потребоваться защитить. В одноадресном сценарии «точка — много точек» это может быть проблематично по тем же причинам, то есть неизвестно, какой из возможных криптографических контекстов использовать. Отметим, что эти проблемы не уникальны для описаний безопасности SDP: их нужно учитывать при любом использовании SRTP.
The second constraint is that the ROC MUST be zero at the time that each SSRC commences sending packets. Thus, there is no concept of a "late joiner" in SRTP security descriptions, which are constrained to be unicast and pairwise. The ROC and SEQ form a "packet index" in the default SRTP transforms and the ROC is consistently set to zero at session commencement, according to this document.
Второе ограничение состоит в том, что ROC ДОЛЖЕН быть нулевым в момент, когда каждый SSRC начинает отправку пакетов. Таким образом, в описаниях безопасности SRTP нет понятия «позднего присоединившегося», поскольку они ограничены одноадресными и парными. ROC и SEQ образуют «индекс пакета» в преобразованиях SRTP по умолчанию, и согласно настоящему документу ROC неизменно устанавливается в нуль при начале сеанса.
The third constraint is that the initial value of SEQ SHOULD be chosen to be within the range of 0..2^15-1; this avoids an ambiguity when packets are lost at the start of the session. If it is at the start of a session, an SSRC source might randomly select a high sequence-number value and put the receiver in an ambiguous situation: if initial packets are lost in transit up to the point that the sequence number wraps (i.e., exceeds 2^16-1), then the receiver might not recognize that its ROC needs to be incremented. By restricting the initial SEQ to the range of 0..2^15-1, SRTP packet-index determination will find the correct ROC value, unless all the first 2^15 packets are lost (which seems, if not impossible, rather unlikely). See Section 3.3.1 of the SRTP specification regarding packet-index determination [RFC3711].
Третье ограничение состоит в том, что начальное значение SEQ СЛЕДУЕТ выбирать в диапазоне 0..2^15-1; это позволяет избежать неоднозначности при потере пакетов в начале сеанса. Если это начало сеанса, источник SSRC может случайно выбрать большое значение порядкового номера и поставить получателя в неоднозначную ситуацию: если начальные пакеты потеряны в пути до момента, когда порядковый номер переполнится (то есть превысит 2^16-1), получатель может не распознать, что его ROC нужно увеличить. Ограничив начальный SEQ диапазоном 0..2^15-1, определение индекса пакета SRTP найдёт правильное значение ROC, если только все первые 2^15 пакетов не потеряны (что кажется, если не невозможным, то довольно маловероятным). Относительно определения индекса пакета см. раздел 3.3.1 спецификации SRTP [RFC3711].

6.5. Removal of Crypto Contexts
6.5. Удаление криптографических контекстов
The mechanism defined above addresses the issue of creating crypto contexts. However, in practice, session participants may want to remove crypto contexts prior to session termination. Since a crypto context contains information that cannot automatically be recovered (e.g., ROC), it is important that the sender and receiver agree on when a crypto context can be removed, and perhaps more importantly when it cannot.
Описанный выше механизм решает задачу создания криптографических контекстов. Однако на практике участники сеанса могут захотеть удалить криптографические контексты до завершения сеанса. Поскольку криптографический контекст содержит информацию, которая не может быть автоматически восстановлена (например, ROC), важно, чтобы отправитель и получатель договорились о том, когда криптографический контекст можно удалить, и, возможно, что ещё важнее, когда его нельзя удалять.
Even when late binding is used for a unicast stream, the ROC is lost and cannot be recovered automatically (unless it is zero) once the crypto context is removed.
Даже когда для одноадресного потока используется позднее связывание, ROC теряется и не может быть восстановлен автоматически (если только он не равен нулю), как только криптографический контекст удалён.
We resolve this problem as follows. When SRTP security descriptions are being used, crypto-context removal MUST follow the same rules as SSRC removal from the member table [RFC3550]; note that this can happen as the result of an SRTCP BYE packet or a simple time-out due to inactivity. Inactive session participants that wish to ensure their crypto contexts are not timed out MUST thus send SRTCP packets at regular intervals.
Мы решаем эту проблему следующим образом. Когда используются описания безопасности SRTP, удаление криптографического контекста ДОЛЖНО следовать тем же правилам, что и удаление SSRC из таблицы участников [RFC3550]; отметим, что это может произойти в результате пакета SRTCP BYE или простого тайм-аута из-за неактивности. Таким образом, неактивные участники сеанса, желающие гарантировать, что их криптографические контексты не будут удалены по тайм-ауту, ДОЛЖНЫ отправлять пакеты SRTCP через регулярные интервалы.

7.1. Use with Offer/Answer
7.1. Использование с предложением/ответом
In this section, we describe how the SRTP security descriptions are used with the offer/answer model to negotiate cryptographic capabilities and communicate SRTP master keys. The rules defined below complement the general offer/answer rules defined in Section 5.1, which MUST be followed, unless otherwise specified. Note that the rules below define unicast operation only; support for multicast and multipoint unicast streams is for further study.
В этом разделе мы описываем, как описания безопасности SRTP используются с моделью предложения/ответа для согласования криптографических возможностей и передачи главных ключей SRTP. Определённые ниже правила дополняют общие правила предложения/ответа, определённые в разделе 5.1, которым ДОЛЖНО следовать, если не указано иное. Отметим, что правила ниже определяют только одноадресную работу; поддержка многоадресных и многоточечных одноадресных потоков оставлена для дальнейшего изучения.
7.1.1. Generating the Initial Offer - Unicast Streams
7.1.1. Формирование начального предложения — одноадресные потоки
When the initial offer is generated, the offerer MUST follow the steps in Section 5.1.1, as well as the following steps.
При формировании начального предложения автор предложения ДОЛЖЕН выполнить шаги из раздела 5.1.1, а также следующие шаги.
For each unicast media line (m=) using the secure RTP transport where the offerer wants to specify cryptographic parameters, the offerer MUST provide at least one valid SRTP security description ("a=crypto" line), as defined in Section 6. If the media stream includes Forward Error Correction with a different IP-address and/or port from that of the media stream itself, an FEC_KEY parameter MUST be included, as described in Section 6.3.5.
Для каждой одноадресной строки медиа (m=), использующей транспорт защищённого RTP, где автор предложения хочет задать криптографические параметры, автор предложения ДОЛЖЕН предоставить хотя бы одно действительное описание безопасности SRTP (строку «a=crypto»), как определено в разделе 6. Если медиапоток включает прямую коррекцию ошибок с другим IP-адресом и (или) портом, чем у самого медиапотока, ДОЛЖЕН быть включён параметр FEC_KEY, как описано в разделе 6.3.5.
The inline parameter conveys the SRTP master key used by an endpoint to encrypt the SRTP and SRTCP streams transmitted by that endpoint. The same key is used by the recipient to decrypt those streams. However, the receiver MUST NOT use that same key for the SRTP or SRTCP packets that it sends to the session because the default SRTP cipher and mode is insecure when the master key is reused across distinct SRTP streams.
Параметр inline передаёт главный ключ SRTP, используемый конечной точкой для шифрования потоков SRTP и SRTCP, передаваемых этой конечной точкой. Получатель использует тот же ключ для расшифровки этих потоков. Однако получатель НЕ ДОЛЖЕН использовать тот же ключ для пакетов SRTP или SRTCP, которые он отправляет в сеанс, поскольку шифр и режим SRTP по умолчанию небезопасны при повторном использовании главного ключа в различных потоках SRTP.
The offerer MAY include one or more other SRTP session parameters, as defined in Section 6.3. Note, however, that if any SRTP session parameters are included that are not known to the answerer, but that are nonetheless mandatory (see Section 6.3.6), the negotiation will fail if the answerer does not support them.
Автор предложения МОЖЕТ включить один или несколько других параметров сеанса SRTP, как определено в разделе 6.3. Отметим, однако, что если включены любые параметры сеанса SRTP, неизвестные ответчику, но при этом обязательные (см. раздел 6.3.6), согласование завершится неудачей, если ответчик их не поддерживает.
7.1.2. Generating the Initial Answer - Unicast Streams
7.1.2. Формирование начального ответа — одноадресные потоки
When the initial answer is generated, the answerer MUST follow the steps in Section 5.1.2, as well as the following steps.
При формировании начального ответа ответчик ДОЛЖЕН выполнить шаги из раздела 5.1.2, а также следующие шаги.
For each unicast media line that uses the secure RTP transport and contains one or more "a=crypto" lines in the offer, the answerer MUST either accept one (and only one) of the crypto lines for that media stream, or it MUST reject the media stream. Only "a=crypto" lines that are considered valid SRTP security descriptions, as defined in Section 6, can be accepted. Furthermore, all parameters (crypto- suite, key parameter, and mandatory session parameters) MUST be acceptable to the answerer in order for the offered media stream to be accepted. Note that if the media stream includes Forward Error Correction with a different IP-address and/or port from that of the media stream itself, an FEC_KEY parameter MUST be included, as described in Section 6.3.5.
Для каждой одноадресной строки медиа, использующей транспорт защищённого RTP и содержащей одну или несколько строк «a=crypto» в предложении, ответчик ДОЛЖЕН либо принять одну (и только одну) из строк crypto для этого медиапотока, либо отклонить медиапоток. Принимать можно только строки «a=crypto», считающиеся действительными описаниями безопасности SRTP, как определено в разделе 6. Кроме того, все параметры (криптонабор, параметр ключа и обязательные параметры сеанса) ДОЛЖНЫ быть приемлемы для ответчика, чтобы предложенный медиапоток был принят. Отметим, что если медиапоток включает прямую коррекцию ошибок с другим IP-адресом и (или) портом, чем у самого медиапотока, ДОЛЖЕН быть включён параметр FEC_KEY, как описано в разделе 6.3.5.
When the answerer accepts an SRTP unicast media stream with a crypto line, the answerer MUST include one or more master keys appropriate for the selected crypto algorithm; the master key(s) included in the answer MUST be different from those in the offer.
Когда ответчик принимает одноадресный медиапоток SRTP со строкой crypto, ответчик ДОЛЖЕН включить один или несколько главных ключей, подходящих для выбранного криптографического алгоритма; главные ключи, включённые в ответ, ДОЛЖНЫ отличаться от ключей в предложении.
When the master key(s) are not shared between the offerer and answerer, SSRC collisions between the offerer and answerer will not lead to keystream reuse, and hence SSRC collisions do not necessarily have to be prevented.
Когда главные ключи не разделяются между автором предложения и ответчиком, коллизии SSRC между автором предложения и ответчиком не приведут к повторному использованию потока ключей, и поэтому коллизии SSRC не обязательно должны предотвращаться.
If Forward Error Correction to a separate IP-address and/or port is included, the answer MUST include an FEC_KEY parameter, as described in Section 6.3.5.
Если включена прямая коррекция ошибок на отдельный IP-адрес и (или) порт, ответ ДОЛЖЕН включать параметр FEC_KEY, как описано в разделе 6.3.5.
Declarative session parameters may be added to the answer as usual; however, the answerer SHOULD NOT add any mandatory session parameter (see Section 6.3.6) that might be unknown to the offerer.
Декларативные параметры сеанса могут быть добавлены в ответ как обычно; однако ответчику НЕ СЛЕДУЕТ добавлять какие-либо обязательные параметры сеанса (см. раздел 6.3.6), которые могут быть неизвестны автору предложения.
If the answerer cannot find any valid crypto line that it supports, or if its configured policy prohibits any cryptographic key parameter (e.g., key length) or cryptographic session parameter (e.g., KDR, FEC_ORDER), it MUST reject the media stream, unless it is able to successfully negotiate use of SRTP by other means outside the scope of this document (e.g., by use of MIKEY [mikey]).
Если ответчик не может найти ни одной действительной строки crypto, которую он поддерживает, или если его настроенная политика запрещает какой-либо параметр криптографического ключа (например, длину ключа) или параметр криптографического сеанса (например, KDR, FEC_ORDER), он ДОЛЖЕН отклонить медиапоток, если только он не способен успешно согласовать использование SRTP иными средствами вне рамок настоящего документа (например, с помощью MIKEY [mikey]).

7.1.4. Modifying the Session
7.1.4. Изменение сеанса
When a media stream using the SRTP security descriptions has been established and a new offer/answer exchange is performed, the offerer and answerer MUST follow the steps in Section 5.1.4, as well as the following steps.
Когда медиапоток с использованием описаний безопасности SRTP установлен и выполняется новый обмен предложения/ответа, автор предложения и ответчик ДОЛЖНЫ выполнить шаги из раздела 5.1.4, а также следующие шаги.
When modifying the session, all negotiated aspects of the SRTP media stream can be modified. For example, a new crypto suite can be used or a new master key can be established. As described in RFC 3264, when a new offer/answer exchange is made, there will be a window of time where the offerer and the answerer must be prepared to receive media according to both the old and new offer/answer exchange. This requirement applies here as well; however, the following should be noted:
При изменении сеанса можно изменить все согласованные аспекты медиапотока SRTP. Например, можно использовать новый криптонабор или установить новый главный ключ. Как описано в RFC 3264, при новом обмене предложения/ответа будет окно времени, в течение которого автор предложения и ответчик должны быть готовы принимать медиа в соответствии как со старым, так и с новым обменом предложения/ответа. Это требование применимо и здесь; однако следует отметить следующее:
* When authentication is not being used, it may not be possible for either the offerer or answerer to determine if a given packet is encrypted according to the old or new offer/answer exchange. RFC 3264 defines a couple of techniques to address this problem, e.g., changing the payload types used and/or the transport addresses. Note, however, that a change in transport addresses may have an impact on quality of service as well as on firewall and NAT traversal. The SRTP security descriptions use the MKI to deal with this (which adds a few bytes to each SRTP packet), as described in Section 6.1. For further details on the MKI, please refer to [RFC3711].
* Когда аутентификация не используется, ни автор предложения, ни ответчик, возможно, не смогут определить, зашифрован ли данный пакет согласно старому или новому обмену предложения/ответа. RFC 3264 определяет несколько методов решения этой проблемы, например изменение используемых типов полезной нагрузки и (или) транспортных адресов. Отметим, однако, что изменение транспортных адресов может повлиять на качество обслуживания, а также на прохождение через межсетевые экраны и NAT. Описания безопасности SRTP используют для этого MKI (что добавляет несколько байт к каждому пакету SRTP), как описано в разделе 6.1. Дополнительные сведения о MKI см. в [RFC3711].
* If the answerer changes its master key, the offerer will not be able to process packets secured via this master key until the answer is received. This could be addressed by using a security "precondition" [sprecon].
* Если ответчик изменяет свой главный ключ, автор предложения не сможет обрабатывать пакеты, защищённые этим главным ключом, до получения ответа. Это можно решить с помощью предусловия безопасности «security» [sprecon].
If the offerer includes an IP address and/or port that differs from that used previously for a media stream (or FEC stream), the offerer MUST include a new master key with the offer (and in so doing, it will be creating a new crypto context where the ROC is set to zero). Similarly, if the answerer includes an IP address and/or port that differs from that used previously for a media stream (or FEC stream), the answerer MUST include a new master key with the answer (and hence create a new crypto context with the ROC set to zero). The reason for this is that when the answerer receives an offer or the offerer receives an answer with an updated IP address and/or port, it is not possible to determine if the other side has access to the old crypto context parameters (and in particular the ROC). For example, if one side is a decomposed media gateway, or if a SIP back-to-back user agent is involved, it is possible that the media endpoint changed and no longer has access to the old crypto context. By always requiring a new master key in this case, the answerer/offerer will know that the ROC is zero for this offer/answer, and any key lifetime constraints will trivially be satisfied too.
Если автор предложения указывает IP-адрес и (или) порт, отличающиеся от использованных ранее для медиапотока (или потока FEC), автор предложения ДОЛЖЕН включить новый главный ключ в предложение (и тем самым создаст новый криптографический контекст, в котором ROC установлен в нуль). Аналогично, если ответчик указывает IP-адрес и (или) порт, отличающиеся от использованных ранее для медиапотока (или потока FEC), ответчик ДОЛЖЕН включить новый главный ключ в ответ (и тем самым создать новый криптографический контекст с ROC, установленным в нуль). Причина в том, что когда ответчик получает предложение или автор предложения получает ответ с обновлённым IP-адресом и (или) портом, невозможно определить, имеет ли другая сторона доступ к старым параметрам криптографического контекста (и в частности к ROC). Например, если одна сторона является декомпозированным медиашлюзом или если задействован SIP-агент B2BUA, возможно, что медиаоконечная точка изменилась и больше не имеет доступа к старому криптографическому контексту. Всегда требуя в этом случае новый главный ключ, ответчик/автор предложения будет знать, что ROC для этого предложения/ответа равен нулю, и любые ограничения времени жизни ключа также будут тривиально выполнены.
Another consideration here applies to media relays; if the relay changes the media endpoint on one side transparently to the other side, the relay cannot operate as a simple packet reflector but will have to actively engage in SRTP packet processing and transformation (i.e., decryption and re- encryption, etc.).
Здесь есть ещё одно соображение, касающееся медиаретрансляторов: если ретранслятор прозрачно для одной стороны меняет медиаконенную точку на другой стороне, он не может работать простым отражателем пакетов и должен активно участвовать в обработке и преобразовании пакетов SRTP (то есть в расшифровании и повторном шифровании).
Finally, note that if the new offer is rejected, the old crypto parameters remain in place.
Наконец, отметим, что если новое предложение отклонено, старые криптографические параметры остаются в силе.

7.3. Support for SIP Forking
7.3. Поддержка разветвления SIP
As mentioned earlier, the security descriptions defined here do not support multicast media streams or multipoint unicast streams. However, in the SIP protocol, it is possible to receive several answers to a single offer due to the use of forking (see [SIP]). Receiving multiple answers leads to a couple of problems for the SRTP security descriptions:
Как упомянуто ранее, определённые здесь описания безопасности не поддерживают многоадресные медиапотоки или многоточечные одноадресные потоки. Однако в протоколе SIP из-за использования разветвления можно получить несколько ответов на одно предложение (см. [SIP]). Получение нескольких ответов создаёт пару проблем для описаний безопасности SRTP:
* Different answerers may choose different ciphers, keys, etc.; however, there is no way for the offerer to associate a particular incoming media packet with a particular answer.
* Разные ответчики могут выбрать разные шифры, ключи и т. д.; однако у автора предложения нет способа связать конкретный входящий медиапакет с конкретным ответом.
* Two or more answerers may pick the same SSRC, and hence the SSRC collision problems mentioned earlier may arise.
* Два или более ответчиков могут выбрать один и тот же SSRC, и поэтому могут возникнуть упомянутые ранее проблемы коллизий SSRC.
As stated earlier, the above point-to-multipoint cases are outside the scope of the SDP security descriptions. However, there are still ways of supporting SIP forking, e.g., by changing the multipoint scenario resulting from SIP forking into multiple two-party unicast cases. This can be done as follows:
Как указано ранее, приведённые выше случаи «точка — много точек» выходят за рамки описаний безопасности SDP. Однако всё ещё существуют способы поддержки разветвления SIP, например путём превращения многоточечного сценария, возникающего из-за разветвления SIP, в несколько случаев одноадресной связи двух сторон. 8. Security Considerations
8. Соображения безопасности
Like all SDP messages, SDP messages containing security descriptions are conveyed in an encapsulating application protocol (e.g., SIP, MGCP). It is the responsibility of the encapsulating protocol to ensure the protection of the SDP security descriptions. Therefore, IT IS REQUIRED that the application invoke its own security mechanisms (e.g., secure multiparts such as S/MIME [smime]) or, alternatively, utilize a lower-layer security service (e.g., TLS or IPsec). IT IS REQUIRED that this security service provide strong message authentication and packet-payload encryption, as well as effective replay protection.
Как и все сообщения SDP, сообщения SDP, содержащие описания безопасности, передаются в инкапсулирующем прикладном протоколе (например, SIP, MGCP). Ответственность за защиту описаний безопасности SDP несёт инкапсулирующий протокол. Поэтому ТРЕБУЕТСЯ, чтобы приложение вызывало свои собственные механизмы безопасности (например, защищённые составные части, такие как S/MIME [smime]) или, в качестве альтернативы, использовало службу безопасности нижнего уровня (например, TLS или IPsec). ТРЕБУЕТСЯ, чтобы эта служба безопасности обеспечивала стойкую аутентификацию сообщений и шифрование полезной нагрузки пакетов, а также эффективную защиту от повторного воспроизведения.
"Replay protection" is needed against an attacker that has enough access to the communications channel to intercept messages and to deliver copies to the destination. A successful replay attack will cause the recipient to perform duplicate processing on a message; the attack is worse when the duped recipient sends a duplicate reply to the initiator. Replay protections are not found in S/MIME or in the other secure-multiparts standard, PGP/MIME. S/MIME and PGP/MIME, therefore, need to be augmented with some replay-protection mechanism that is appropriate to the encapsulating application protocol (e.g., SIP, MGCP). Three common ways to provide replay protection are to place a sequence number in the message, to use a timestamp, or for the receiver to keep a hash of the message to be compared with incoming messages. There typically needs to be a replay "window" and some policy for keeping state information from previous messages in a "replay table" or list.
«Защита от повторного воспроизведения» нужна против злоумышленника, имеющего достаточный доступ к каналу связи, чтобы перехватывать сообщения и доставлять копии к месту назначения. Успешная атака повторного воспроизведения заставит получателя выполнить дублирующую обработку сообщения; атака хуже, когда обманутый получатель отправляет инициатору дублирующий ответ. Защита от повторного воспроизведения отсутствует в S/MIME и в другом стандарте защищённых составных частей — PGP/MIME. Поэтому S/MIME и PGP/MIME необходимо дополнить неким механизмом защиты от повторного воспроизведения, подходящим для инкапсулирующего прикладного протокола (например, SIP, MGCP). Три распространённых способа обеспечить защиту от повторного воспроизведения — поместить в сообщение порядковый номер, использовать отметку времени или заставить получателя хранить хэш сообщения для сравнения с входящими сообщениями. Обычно требуется «окно» повторного воспроизведения и некоторая политика хранения информации о состоянии предыдущих сообщений в «таблице повторного воспроизведения» или списке.
The discussion that follows uses "message authentication" and "message confidentiality" in a manner consistent with SRTP [RFC3711]. "Message confidentiality" means that only the holder of the secret decryption key can access the plain-text content of the message. The decryption key is the same key as the encryption key, using SRTP counter mode and f8 encryption transforms, which are vulnerable to message tampering and need SRTP message authentication to detect such tampering. "Message authentication" and "message integrity validation" generally mean the same thing in IETF security standards: an SRTP message is authenticated following a successful HMAC integrity check [RFC3711], which proves that the message originated from the holder of an SRTP master key and was not altered en route. Such an "authentic" message, however, can be captured by an attacker and "replayed" when the attacker re-inserts the packet into the channel. A replayed packet can have a variety of bad effects on the session, and SRTP uses the extended sequence number to detect replayed SRTP packets [RFC3711].
В последующем обсуждении термины «аутентификация сообщений» и «конфиденциальность сообщений» используются в значении, согласующемся с SRTP [RFC3711]. «Конфиденциальность сообщений» означает, что только владелец секретного ключа расшифровки может получить доступ к открытому тексту сообщения. Ключ расшифровки — тот же ключ, что и ключ шифрования, с использованием режима счётчика SRTP и преобразований шифрования f8, которые уязвимы к подмене сообщений и нуждаются в аутентификации сообщений SRTP для обнаружения такой подмены. «Аутентификация сообщений» и «проверка целостности сообщений» в стандартах безопасности IETF обычно означают одно и то же: сообщение SRTP аутентифицируется после успешной проверки целостности HMAC [RFC3711], что доказывает, что сообщение пришло от владельца главного ключа SRTP и не было изменено в пути. Однако такое «подлинное» сообщение может быть перехвачено злоумышленником и «воспроизведено», когда злоумышленник повторно вставит пакет в канал. Воспроизведённый пакет может оказать разнообразное вредное влияние на сеанс, и SRTP использует расширенный порядковый номер для обнаружения воспроизведённых пакетов SRTP [RFC3711].
The SRTP specification identifies which services and features are default values that are normative-to-implement (such as AES_CM_128_80) versus normative-to-use (such as AES_CM_128_32).
Спецификация SRTP определяет, какие услуги и возможности являются значениями по умолчанию, нормативными для реализации (например, AES_CM_128_80), а какие — нормативными для использования (например, AES_CM_128_32).
8.1. Authentication of Packets
8.1. Аутентификация пакетов
Security descriptions as defined herein signal security services for RTP packets. RTP messages are vulnerable to a variety of attacks, such as replay and forging. To limit these attacks, SRTP message integrity mechanisms SHOULD be used (SRTP replay protection is always enabled).
Описания безопасности, определённые в настоящем документе, сигнализируют услуги безопасности для пакетов RTP. Сообщения RTP уязвимы к разнообразным атакам, таким как повторное воспроизведение и подделка. Чтобы ограничить эти атаки, СЛЕДУЕТ использовать механизмы целостности сообщений SRTP (защита SRTP от повторного воспроизведения всегда включена).
8.2. Keystream Reuse
8.2. Повторное использование потока ключей
SRTP security descriptions signal configuration parameters for SRTP sessions. Misconfigured SRTP sessions are vulnerable to attacks on their encryption services when running the crypto suites defined in Sections 6.2.1, 6.2.2, and 6.2.3. An SRTP encryption service is "misconfigured" when two or more media streams are encrypted using the same keystream of AES blocks. When senders and receivers share derived session keys, SRTP requires that the SSRCs of session participants serve to make their corresponding keystreams unique, which is violated in the case of SSRC collision: SRTP SSRC collision drastically weakens SRTP or SRTCP payload encryption during the time that identical keystreams are used [RFC3711]. An attacker, for example, might collect SRTP and SRTCP messages and await a collision. This attack on the AES-CM and AES-f8 encryption is avoided entirely when each media stream has its own unique master key in both the send and receive direction. This specification restricts use of SDP security description to unicast point-to-point streams so that keys are not shared between SRTP hosts, and the master keys used in the send and receive direction for a given media stream are unique.
Описания безопасности SRTP сигнализируют параметры конфигурации для сеансов SRTP. Неверно настроенные сеансы SRTP уязвимы к атакам на их службы шифрования при работе с криптонаборами, определёнными в разделах 6.2.1, 6.2.2 и 6.2.3. Служба шифрования SRTP «настроена неверно», когда два или более медиапотока шифруются с использованием одного и того же потока ключей блоков AES. Когда отправители и получатели совместно используют производные сеансовые ключи, SRTP требует, чтобы SSRC участников сеанса служили для обеспечения уникальности соответствующих потоков ключей, что нарушается в случае коллизии SSRC: коллизия SRTP SSRC резко ослабляет шифрование полезной нагрузки SRTP или SRTCP в течение времени использования идентичных потоков ключей [RFC3711]. Злоумышленник, например, может собирать сообщения SRTP и SRTCP и ждать коллизии. Эта атака на шифрование AES-CM и AES-f8 полностью избегается, когда каждый медиапоток имеет свой собственный уникальный главный ключ в обоих направлениях — отправки и приёма. Настоящая спецификация ограничивает использование описания безопасности SDP одноадресными потоками «точка — точка», чтобы ключи не разделялись между хостами SRTP, а главные ключи, используемые в направлениях отправки и приёма для данного медиапотока, были уникальными.
8.3. Signaling Authentication and Signaling Encryption
8.3. Аутентификация сигнализации и шифрование сигнализации
There is no reason to incur the complexity and computational expense of SRTP, however, when its key establishment is exposed to unauthorized parties. In most cases, the SRTP crypto attribute and its parameters are vulnerable to denial-of-service attacks when they are carried in an unauthenticated SDP message. In some cases, the integrity or confidentiality of the RTP stream can be compromised. For example, if an attacker sets UNENCRYPTED for the SRTP stream in an offer, this could result in the answerer's not decrypting the encrypted SRTP messages. In the worst case, the answerer might itself send unencrypted SRTP and leave its data exposed to snooping.
Однако нет причин нести сложность и вычислительные затраты SRTP, когда его установление ключей подвергается воздействию неавторизованных сторон. В большинстве случаев атрибут SRTP crypto и его параметры уязвимы к атакам отказа в обслуживании, когда они передаются в неаутентифицированном сообщении SDP. В некоторых случаях целостность или конфиденциальность потока RTP может быть скомпрометирована. Например, если злоумышленник задаст UNENCRYPTED для потока SRTP в предложении, это может привести к тому, что ответчик не расшифрует зашифрованные сообщения SRTP. В худшем случае ответчик сам может отправлять незашифрованный SRTP и оставить свои данные открытыми для подглядывания.
Thus, IT IS REQUIRED that MIME secure multiparts, IPsec, TLS, or some other data security service be used to provide message authentication for the encapsulating protocol that carries the SDP messages having a crypto attribute (a=crypto). Furthermore, IT IS REQUIRED that encryption of the encapsulating payload be used whenever a master key parameter (inline) appears in the message. Failure to encrypt the SDP message containing an inline SRTP master key renders the SRTP authentication or encryption service useless in practically all circumstances. Failure to authenticate an SDP message that carries SRTP parameters renders the SRTP authentication or encryption service useless in most practical applications.
Таким образом, ТРЕБУЕТСЯ, чтобы безопасные составные части MIME, IPsec, TLS или какая-либо другая служба защиты данных использовались для обеспечения аутентификации сообщений для инкапсулирующего протокола, который переносит сообщения SDP с атрибутом crypto (a=crypto). Кроме того, ТРЕБУЕТСЯ использовать шифрование инкапсулирующей полезной нагрузки всякий раз, когда в сообщении присутствует параметр главного ключа (inline). Неспособность зашифровать сообщение SDP, содержащее встроенный главный ключ SRTP (inline), делает службу аутентификации или шифрования SRTP бесполезной практически во всех обстоятельствах. Неспособность аутентифицировать сообщение SDP, несущее параметры SRTP, делает службу аутентификации или шифрования SRTP бесполезной в большинстве практических приложений.
When the communication path of the SDP message is routed through intermediate systems that inspect parts of the SDP message, security protocols such as [IPsec] or TLS SHOULD NOT be used for encrypting and/or authenticating the security description. In the case of intermediate-system processing of a message containing SDP security descriptions, the "a=crypto" attributes SHOULD be protected end-to- end so that the intermediate system can neither modify the security description nor access the keying material. Network or transport security protocols that terminate at each intermediate system, therefore, SHOULD NOT be used for protecting SDP security descriptions. A security protocol SHOULD allow the security descriptions to be encrypted and authenticated end-to-end independently of the portions of the SDP message that any intermediate system modifies or inspects: MIME secure multiparts are RECOMMENDED for the protection of SDP messages that are processed by intermediate systems.
Когда путь передачи сообщения SDP проходит через промежуточные системы, которые просматривают части сообщения SDP, протоколы безопасности, такие как [IPsec] или TLS, НЕ СЛЕДУЕТ использовать для шифрования и (или) аутентификации описания безопасности. В случае обработки сообщения, содержащего описания безопасности SDP, промежуточной системой атрибуты «a=crypto» СЛЕДУЕТ защищать сквозным образом, чтобы промежуточная система не могла ни изменить описание безопасности, ни получить доступ к ключевому материалу. Поэтому сетевые или транспортные протоколы безопасности, завершающиеся на каждой промежуточной системе, НЕ СЛЕДУЕТ использовать для защиты описаний безопасности SDP. Протокол безопасности СЛЕДУЕТ позволять шифровать и аутентифицировать описания безопасности сквозным образом независимо от тех частей сообщения SDP, которые изменяет или просматривает любая промежуточная система: для защиты сообщений SDP, обрабатываемых промежуточными системами, РЕКОМЕНДУЮТСЯ безопасные составные части MIME.

Appendix A - Rationale for Keying Material Directionality
Приложение A. Обоснование направленности ключевого материала
SDP security descriptions define the keying material for the sending direction, which is included in the SDP. Thus, the key that is carried in an SDP message is a decryption key for the receiver of that SDP message. This is in contrast to the majority of information included in SDP, which describes information for the receiving (or receiving and sending) direction. This reversed information directionality generates some challenges with using the mechanism in the offer/answer model and in particular with SIP, where early media and forking require special consideration (as described in Section 7.3). There are however good reasons for why this was done, which can be summarized as follows:
Описания безопасности SDP определяют ключевой материал для направления отправки, который включается в SDP. Таким образом, ключ, переносимый в сообщении SDP, является ключом расшифровки для получателя этого сообщения SDP. Это противоположно большей части информации, включаемой в SDP, которая описывает информацию для направления приёма (или приёма и отправки). Такая обратная направленность информации создаёт некоторые проблемы при использовании механизма в модели предложения/ответа и, в частности, в SIP, где ранние медиа и разветвление требуют особого рассмотрения (как описано в разделе 7.3). Однако есть веские причины, по которым это было сделано, и их можно резюмировать следующим образом:
First of all, there is the general security philosophy of letting the entity that sends traffic decide what key to use for protecting it. SRTP uses counter mode, which is secure when counters do not overlap among senders who share a master key; the surest way to avoid counter overlap is for each endpoint to generate its own master key. Secondly, if SDP security descriptions had been designed to keep the normal SDP information directionality, it would have resulted in problems with supporting early media and SIP forking: If an offer generates multiple answers and the keying material was for the receive direction, some of the parameter values (e.g. lifetime) would have to be shared between all the answerers (senders of media), which would lead to considerable complexity, possibly requiring changes or extensions to SRTP. Other problems were discovered as well, which we describe further below.
Прежде всего, существует общая философия безопасности, позволяющая объекту, отправляющему трафик, решать, какой ключ использовать для его защиты. SRTP использует режим счётчика, который безопасен, когда счётчики не перекрываются среди отправителей, совместно использующих главный ключ; самый надёжный способ избежать перекрытия счётчиков — чтобы каждая конечная точка вырабатывала собственный главный ключ. Во-вторых, если бы описания безопасности SDP были разработаны с сохранением обычной направленности информации SDP, это привело бы к проблемам с поддержкой ранних медиа и разветвления SIP: если предложение порождает несколько ответов, а ключевой материал предназначался бы для направления приёма, некоторые значения параметров (например, время жизни) пришлось бы разделять между всеми ответчиками (отправителями медиа), что привело бы к значительной сложности и, возможно, потребовало бы изменений или расширений SRTP. Были обнаружены и другие проблемы, которые мы описываем далее ниже.
In the following scenarios, we analyze what would occur if SDP security descriptions had been designed so that the keying material was the receive keying material (rather than its actual design, where the keying material is the sending keying material): Scenario A: Non-Forking Case
В следующих сценариях мы анализируем, что произошло бы, если бы описания безопасности SDP были разработаны так, чтобы ключевой материал был ключевым материалом приёма (а не его фактический дизайн, где ключевой материал — это ключевой материал отправки): Сценарий A: случай без разветвления
In this scenario, the offer includes the receiving keying material, the answerer receives it and starts sending data packets towards the offerer. If there was a single crypto attribute in the offer, there would be no ambiguity about which crypto suite was being used and, hence, the incoming packet could be processed. However, in the case where the offer included multiple alternative crypto-attributes, the offerer would not know which one was chosen, and hence, if the offerer received packets before the answer came back, the offerer would be unable to process those packets (problem 1). (Use of the MKI has been suggested as one possible solution to that, however it incurs a per-packet overhead.)
В этом сценарии предложение включает ключевой материал приёма, ответчик получает его и начинает отправлять пакеты данных автору предложения. Если в предложении был единственный атрибут crypto, не было бы неоднозначности относительно используемого криптонабора, и, следовательно, входящий пакет можно было бы обработать. Однако в случае, когда предложение включало несколько альтернативных атрибутов crypto, автор предложения не знал бы, какой из них выбран, и, следовательно, если бы автор предложения получал пакеты до прихода ответа, он не смог бы обработать эти пакеты (проблема 1). (Использование MKI предлагалось как одно из возможных решений, однако оно влечёт накладные расходы на каждый пакет.)
Scenario B: Serial Forking Case
Сценарий B: случай последовательного разветвления
In this scenario, Alice generates an offer to Bob, who starts sending (early) media towards Alice (no answer returned yet). In this scenario, we assume we aren't also encountering Scenario A (e.g., the offer includes only a single crypto-attribute) and that Bob is using a Synchronization Source (SSRC) value of 1 for his SRTP and SRTCP packets. Alice thus has a crypto-context for SSRC 1, including the associated ROC (Roll Over Counter) and SEQ (RTP Sequence Number). Bob now forwards the call to Carol (Bob still has not generated an answer). At this point, Bob has Alice's key, which sometimes might be a security weakness. As the exchange proceeds, Carol gets the original offer, including the offered crypto-attribute and starts sending media packets towards Alice. It just so happens that Carol chooses an SSRC value of 1, as did Bob. When Carol starts generating packets, there is a potential for what RFC 3711 calls a "two-time pad" issue (problem 2), as well as the potential for the ROC to be out of sync between Alice and Carol (problem 3). Note that since Bob and Carol are (presumably) using different source transport addresses, the SSRC reuse does not constitute an SSRC collision (although it may still be interpreted as such by Alice).
В этом сценарии Алиса формирует предложение Бобу, который начинает отправлять (ранние) медиа Алисе (ответ ещё не возвращён). В этом сценарии мы предполагаем, что мы не сталкиваемся также со сценарием A (например, предложение включает только единственный атрибут crypto) и что Боб использует значение Synchronization Source (SSRC), равное 1, для своих пакетов SRTP и SRTCP. Таким образом, у Алисы есть криптографический контекст для SSRC 1, включая связанные ROC (Roll Over Counter) и SEQ (RTP Sequence Number). Теперь Боб переадресует вызов Кэрол (Боб всё ещё не сформировал ответ). В этот момент у Боба есть ключ Алисы, что иногда может быть слабостью безопасности. По мере развития обмена Кэрол получает исходное предложение, включая предложенный атрибут crypto, и начинает отправлять медиапакеты Алисе. Так уж случается, что Кэрол выбирает значение SSRC, равное 1, как и Боб. Когда Кэрол начинает формировать пакеты, появляется потенциальная возможность того, что RFC 3711 называет проблемой «двукратной маски» (проблема 2), а также потенциальная возможность рассинхронизации ROC между Алисой и Кэрол (проблема 3). Отметим, что поскольку Боб и Кэрол (предположительно) используют разные исходные транспортные адреса, повторное использование SSRC не является коллизией SSRC (хотя всё ещё может быть истолковано Алисой как таковая).
Per RFC 3711, since the master key would be shared between Bob and Carol in this case, it is RECOMMENDED that Alice leave the session at that point in order to avoid the two-time pad issue. It should also be noted that RFC 3711 recommends against sharing SRTP master keys, which forking may accidentally introduce when the keying material is for the receiving direction.
Согласно RFC 3711, поскольку в этом случае главный ключ был бы общим для Bob и Carol, РЕКОМЕНДУЕТСЯ, чтобы Alice на этом моменте покинула сессию во избежание проблемы двухкратной подкладки. Следует также отметить, что RFC 3711 не рекомендует совместно использовать главные ключи SRTP, а разветвление может случайно привести к этому, когда ключевой материал предназначен для принимающего направления.
If we consider the above scenario again, but this time with keying material in the offer (and answer) being the sending keying material (as specified by SDP security descriptions), the scenario instead looks as follows: Bob again chooses SSRC 1, and Bob will need to send back an answer to Alice, since Alice needs to learn Bob's sending key. Bob also starts sending media towards Alice (clipping may occur until Alice receives Bob's answer). Bob again forwards the call to Carol who also starts sending early media using SSRC 1. However, Carol needs to generate a new answer (for the dialog between Alice and Carol) in order for Alice to process Carol's packets . Upon receiving this answer, Alice can initiate a new offer/answer exchange (to move the session to another transport address as described in Section 7.3). In this case, there is one master key per session and a unique keystream regardless of whether or not SSRCs collide.
Если рассмотреть описанный выше сценарий снова, но на этот раз с ключевым материалом в предложении (и ответе), являющимся отправляющим ключевым материалом (как определено в описаниях безопасности SDP), сценарий выглядит иначе: Bob снова выбирает SSRC 1 и должен отправить ответ Alice, поскольку Alice нужно узнать отправляющий ключ Bob. Bob также начинает отправлять медиа в сторону Alice (до получения ответа Bob у Alice возможна обрезка). Bob снова переадресует вызов Carol, которая тоже начинает отправлять ранние медиа с SSRC 1. Однако Carol должна сформировать новый ответ (для диалога между Alice и Carol), чтобы Alice могла обрабатывать пакеты Carol. Получив этот ответ, Alice может инициировать новый обмен предложение/ответ (чтобы перевести сеанс на другой транспортный адрес, как описано в разделе 7.3). В этом случае на каждый сеанс приходится один главный ключ и уникальный поток ключей независимо от того, сталкиваются ли SSRC.
Scenario C: Parallel Forking Case
Сценарий C: случай параллельного разветвления
In this scenario, Alice generates an offer (with receive keying material) that gets forked to Bob and Carol in parallel. Bob and Carol both start sending packets (early media) to Alice. If Bob and Carol choose different SSRCs, everything is fine initially. However, one of the crypto context parameters is the master key lifetime, and since Bob and Carol are sharing the same master key (unbeknownst to either), they do not know when they need to rekey (problem 4). If they choose the same SSRC, we have the two-time pad problem again (problem 2).
В этом сценарии Алиса формирует предложение (с ключевым материалом приёма), которое разветвляется к Бобу и Кэрол параллельно. Боб и Кэрол оба начинают отправлять пакеты (ранние медиа) Алисе. Если Боб и Кэрол выбирают разные SSRC, изначально всё в порядке. Однако одним из параметров криптографического контекста является время жизни главного ключа, и, поскольку Боб и Кэрол используют один и тот же главный ключ (не зная об этом), они не знают, когда им нужно перевыработать ключ (проблема 4). Если они выбирают один и тот же SSRC, снова возникает проблема двукратной маски (проблема 2).
In summary, if keying material were for the receive direction, we would have the following problems:
В итоге, если бы ключевой материал предназначался для направления приёма, мы имели бы следующие проблемы:
- Problem 1: Offerer does not know which of multiple crypto offers was chosen by answerer.
- Проблема 1: автор предложения не знает, какой из нескольких предложенных вариантов crypto выбрал ответчик.
- Problem 2: SSRC reuse (or SSRC collisions) between multiple answerers (serial or parallel forking) may lead to the two-time pad issue.
- Проблема 2: повторное использование SSRC (или коллизии SSRC) между несколькими ответчиками (последовательное или параллельное разветвление) может привести к проблеме двукратной маски.
- Problem 3: Part of the crypto context parameters (specifically the ROC) is not communicated but derived, and if we allow multiple entities to use the same SSRC (sequentially), the ROC can be wrong.
- Проблема 3: часть параметров криптографического контекста (в частности ROC) не передаётся, а выводится, и если мы позволяем нескольким объектам использовать один и тот же SSRC (последовательно), ROC может оказаться неверным.
- Problem 4: All crypto contexts that share a master key need to maintain a shared set of counters (master key lifetime), and if we allow for multiple entities on different platforms to share a master key, we would need a mechanism to synchronize these counters.
- Проблема 4: все криптографические контексты, совместно использующие главный ключ, должны поддерживать общий набор счётчиков (время жизни главного ключа), и если мы позволяем нескольким объектам на разных платформах совместно использовать главный ключ, нам понадобился бы механизм синхронизации этих счётчиков.
Problem 1 could be addressed by using the MKI as proposed separately; however, it would result in using extra bandwidth for each SRTP media packet. Solving problem 2 implies a need for being able to synchronize SSRC values with the answerer (or abandon the session when SSRC reuse or SSRC collisions occur). Problem 3 implies a need for being able to synchronize ROC values on a per SSRC basis (or abandon the session when SSRC reuse occurs).
Проблему 1 можно было бы решить использованием MKI, как предлагалось отдельно; однако это привело бы к дополнительному расходу полосы пропускания на каждый медиапакет SRTP. Решение проблемы 2 подразумевает необходимость синхронизировать значения SSRC с ответчиком (или отказаться от сеанса при повторном использовании SSRC или коллизиях SSRC). Проблема 3 подразумевает необходимость синхронизировать значения ROC для каждого SSRC (или отказаться от сеанса при повторном использовании SSRC).
Problem 4 could be solved by having the offerer (Alice, i.e., the entity receiving media) determine how many packets have actually been generated by the total set of senders to Alice and, hence, be the one to initiate the rekeying. In the case of packet losses, etc. this is not foolproof, but in practice it could probably be addressed by use of a reasonable safety margin.
Проблему 4 можно решить, если предлагающая сторона (Alice, то есть объект, принимающий медиа) определит, сколько пакетов фактически сгенерировано всем набором отправителей в адрес Alice, и, следовательно, сама инициирует смену ключа. При потерях пакетов и т. п. это не гарантирует полной надёжности, но на практике, вероятно, решается разумным запасом.
In conclusion, it would be expected from an offer/answer and SIP point of view to have the offer (and answer) keying material be the receive keying material; however, doing so would trade security for SIP friendliness, e.g., two-time pad and master key lifetime issues, and violate the RFC 3711 rule for sharing an SRTP master key across SRTP sessions.
В заключение, с точки зрения модели предложение/ответ и SIP, ожидалось бы, что ключевой материал предложения (и ответа) будет принимающим ключевым материалом; однако это обменяло бы безопасность на дружелюбность к SIP, например, создав проблемы двукратной подкладки и времени жизни главного ключа, и нарушило бы правило RFC 3711 о совместном использовании главного ключа SRTP между сеансами SRTP.
