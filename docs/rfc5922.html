Domain Certificates in the Session Initiation Protocol (SIP)
Доменные сертификаты в протоколе инициирования сессий (SIP)
Abstract
Аннотация
This document describes how to construct and interpret certain information in a PKIX-compliant (Public Key Infrastructure using X.509) certificate for use in a Session Initiation Protocol (SIP) over Transport Layer Security (TLS) connection. More specifically, this document describes how to encode and extract the identity of a SIP domain in a certificate and how to use that identity for SIP domain authentication. As such, this document is relevant both to implementors of SIP and to issuers of certificates.
В настоящем документе описано, как формировать и интерпретировать определённую информацию в сертификате, соответствующем PKIX (инфраструктура открытых ключей с использованием X.509), для применения в соединении протокола инициирования сессий (SIP) через протокол защиты транспортного уровня (TLS). Более конкретно, в документе описано, как кодировать и извлекать идентичность SIP-домена в сертификате и как использовать эту идентичность для аутентификации SIP-домена. Таким образом, документ актуален как для разработчиков SIP, так и для организаций, выпускающих сертификаты.

1. Introduction
1. Введение
RFC 5246 [5] Transport Layer Security (TLS) is available in an increasing number of Session Initiation Protocol (SIP) RFC 3261 [2] implementations. In order to use the authentication capabilities of TLS, certificates as defined by the Internet X.509 Public Key Infrastructure, see RFC 5280 [6], are required.
RFC 5246 [5] Transport Layer Security (TLS) доступен во всё большем числе реализаций RFC 3261 [2] протокола инициирования сессий (SIP). Чтобы использовать возможности аутентификации, которые предоставляет TLS, требуются сертификаты, определённые в рамках инфраструктуры открытых ключей Интернета X.509, см. RFC 5280 [6].
Existing SIP specifications do not sufficiently specify how to use certificates for domain (as opposed to host) authentication. This document provides guidance to ensure interoperability and uniform conventions for the construction and interpretation of certificates used to identify their holders as being authoritative for the domain.
Существующие спецификации SIP недостаточно точно определяют, как использовать сертификаты для аутентификации домена (в отличие от хоста). В настоящем документе приведены рекомендации, обеспечивающие совместимость и единообразные соглашения при формировании и интерпретации сертификатов, используемых для удостоверения того, что их владельцы являются авторитетными для домена.
The discussion in this document is pertinent to an X.509 PKIX- compliant certificate used for a TLS connection; this document does not define use of such certificates for any other purpose (such as Secure/Multipurpose Internet Mail Extensions (S/MIME)).
Обсуждение в настоящем документе относится к сертификату, соответствующему X.509 PKIX и используемому для соединения TLS; настоящий документ не определяет использование таких сертификатов для каких-либо иных целей (например, для Secure/Multipurpose Internet Mail Extensions (S/MIME)).

3. Problem Statement
3. Постановка задачи
TLS uses RFC 5280 [6] X.509 Public Key Infrastructure to bind an identity or a set of identities, to the subject of an X.509 certificate. While RFC 3261 provides adequate guidance on the use of X.509 certificates for S/MIME, it is relatively silent on the use of such certificates for TLS. With respect to certificates for TLS, RFC 3261 (Section 26.3.1) says:
TLS использует инфраструктуру открытых ключей X.509 (RFC 5280 [6]), чтобы привязать идентичность или набор идентичностей к субъекту сертификата X.509. Хотя RFC 3261 даёт достаточные рекомендации по использованию сертификатов X.509 для S/MIME, он относительно мало говорит об использовании таких сертификатов для TLS. Относительно сертификатов для TLS в RFC 3261 (раздел 26.3.1) сказано:
Proxy servers, redirect servers, and registrars SHOULD possess a site certificate whose subject corresponds to their canonical hostname.
Прокси-серверы, серверы переадресации и регистраторы СЛЕДУЕТ обладать сертификатом сайта, субъект которого соответствует их каноническому имени хоста.
The security properties of TLS and S/MIME as used in SIP are different: X.509 certificates for S/MIME are generally used for end- to-end authentication and encryption; thus, they serve to bind the identity of a user to the certificate and RFC 3261 is sufficiently clear that in certificates used for S/MIME, the subjectAltName field will contain the appropriate identity. On the other hand, X.509 certificates used for TLS serve to bind the identities of the per-hop domain sending or receiving the SIP messages. However, the lack of guidelines in RFC 3261 on exactly where to put identities -- in the subjectAltName field or carried as a Common Name (CN) in the Subject field -- of an X.509 certificate created ambiguities. Following the accepted practice of the time, legacy X.509 certificates were allowed to store the identity in the CN field of the certificate instead of the currently specified subjectAltName extension. Lack of further guidelines on how to interpret the identities, which identity to choose if more than one identity is present in the certificate, the behavior when multiple identities with different schemes were present in the certificate, etc., lead to ambiguities when attempting to interpret the certificate in a uniform manner for TLS use.
Свойства безопасности TLS и S/MIME при их использовании в SIP различаются: сертификаты X.509 для S/MIME обычно применяются для аутентификации и шифрования «из конца в конец»; таким образом, они служат для привязки идентичности пользователя к сертификату, и RFC 3261 достаточно ясно указывает, что в сертификатах, используемых для S/MIME, поле subjectAltName будет содержать соответствующую идентичность. С другой стороны, сертификаты X.509, используемые для TLS, служат для привязки идентичностей домена, отправляющего или принимающего сообщения SIP, на каждом участке. Однако отсутствие в RFC 3261 указаний о том, где именно размещать идентичности — в поле subjectAltName или в виде Common Name (CN) в поле Subject — порождало неоднозначности. Следуя принятой в то время практике, устаревшим сертификатам X.509 разрешалось хранить идентичность в поле CN сертификата вместо ныне указанного расширения subjectAltName. Отсутствие дальнейших указаний о том, как интерпретировать идентичности, какую идентичность выбирать при наличии в сертификате нескольких идентичностей, как вести себя при наличии в сертификате нескольких идентичностей с разными схемами и т. п., порождало неоднозначности при попытке единообразной интерпретации сертификата для использования в TLS.
This document shows how the certificates are to be used for mutual authentication when both the client and server possess appropriate certificates, and normative behavior for matching the DNS query string with an identity stored in the X.509 certificate. Furthermore, a certificate can contain multiple identities for the subject in the subjectAltName extension (the "subject" of a certificate identifies the entity associated with the public key stored in the public key field). As such, this document specifies appropriate matching rules to encompass various subject identity representation options. And finally, this document also provides guidelines to service providers for assigning certificates to SIP servers.
В настоящем документе показано, как следует использовать сертификаты для взаимной аутентификации, когда и клиент, и сервер обладают подходящими сертификатами, а также нормативное поведение при сопоставлении строки DNS-запроса с идентичностью, сохранённой в сертификате X.509. Кроме того, сертификат может содержать в расширении subjectAltName несколько идентичностей субъекта (термин "субъект" сертификата обозначает объект, связанный с открытым ключом, который хранится в поле открытого ключа). Поэтому в настоящем документе определены надлежащие правила сопоставления, охватывающие различные варианты представления идентичности субъекта. И наконец, документ содержит рекомендации для поставщиков услуг по назначению сертификатов SIP-серверам.
The rest of this document is organized as follows: the next section provides an overview of the most primitive case of a client using DNS to access a SIP server and the resulting authentication steps. Section 5 looks at the reason why mutual inter-domain authentication is desired in SIP, and the lack of normative text and behavior in RFC 3261 for doing so. Section 6 outlines normative guidelines for a service provider assigning certificates to SIP servers. Section 7 provides normative behavior on the SIP entities (user agent clients, user agent servers, registrars, redirect servers, and proxies) that need perform authentication based on X.509 certificates. Section 8 includes the security considerations.
Остальная часть документа организована следующим образом: в следующем разделе дан обзор простейшего случая, когда клиент использует DNS для доступа к SIP-серверу, и последующих шагов аутентификации. В разделе 5 рассматривается причина, по которой в SIP желательна взаимная междоменная аутентификация, и отсутствие нормативного текста и поведения для этого в RFC 3261. В разделе 6 изложены нормативные рекомендации поставщику услуг по назначению сертификатов SIP-серверам. В разделе 7 приведено нормативное поведение SIP-объектов (клиентов пользовательских агентов, серверов пользовательских агентов, регистраторов, серверов переадресации и прокси-серверов), которым требуется выполнять аутентификацию на основе сертификатов X.509. Раздел 8 содержит соображения безопасности.
4. SIP Domain to Host Resolution
4. Сопоставление SIP-домена с хостом
Routing in SIP is performed by having the client execute RFC 3263 [8] procedures on a URI, called the "Application Unique String (AUS)" (c.f. Section 8 of RFC 3263 [8]). These procedures take as input a SIP AUS (the SIP URI), extract the domain portion of that URI for use as a lookup key, and query the Domain Name Service (DNS) to obtain an ordered set of one or more IP addresses with a port number and transport corresponding to each IP address in the set (the "Expected Output"). If the transport indicates the use of TLS, then a TLS connection is opened to the server on a specific IP address and port. The server presents an X.509 certificate to the client for verification as part of the initial TLS handshake.
Маршрутизация в SIP выполняется так: клиент выполняет процедуры RFC 3263 [8] над URI, называемым "уникальной строкой приложения (Application Unique String, AUS)" (см. раздел 8 RFC 3263 [8]). Эти процедуры принимают на вход AUS SIP (SIP URI), извлекают доменную часть этого URI для использования в качестве ключа поиска и запрашивают службу доменных имён (DNS), чтобы получить упорядоченный набор из одного или нескольких IP-адресов с номером порта и транспортом, соответствующими каждому IP-адресу из набора ("ожидаемый результат"). Если транспорт указывает на использование TLS, то к серверу по конкретным IP-адресу и порту открывается соединение TLS. В ходе первоначального рукопожатия TLS сервер предъявляет клиенту сертификат X.509 для проверки.
The client extracts identifiers from the Subject and any subjectAltName extension in the certificate (see Section 7.1) and compares these values to the domain part extracted from the original SIP URI (the AUS). If any identifier match is found, the server is considered to be authenticated and subsequent signaling can now proceed over the TLS connection. Matching rules for X.509 certificates and the normative behavior for clients is specified in Section 7.3.
Клиент извлекает идентификаторы из поля Subject и из любого расширения subjectAltName в сертификате (см. раздел 7.1) и сравнивает эти значения с доменной частью, извлечённой из исходного SIP URI (AUS). Если найдено совпадение хотя бы одного идентификатора, сервер считается аутентифицированным, и последующая сигнализация может идти по соединению TLS. Правила сопоставления для сертификатов X.509 и нормативное поведение клиентов определены в разделе 7.3.
As an example, consider a request that is to be routed to the SIP address "sips:alice@example.com". This address requires a secure connection to the SIP domain "example.com" (the 'sips' scheme mandates a secure connection). Through a series of DNS manipulations, the domain name is mapped to a set of host addresses and transports. The entity attempting to create the connection selects an address appropriate for use with TLS from this set. When the connection is established to that server, the server presents a certificate asserting the identity "sip:example.com". Since the domain part of the SIP AUS matches the subject of the certificate, the server is authenticated (see Section 7.2 for the normative rules that govern this comparison).
В качестве примера рассмотрим запрос, который должен быть маршрутизирован на SIP-адрес "sips:alice@example.com". Этот адрес требует защищённого соединения с SIP-доменом "example.com" (схема 'sips' предписывает защищённое соединение). В результате ряда манипуляций с DNS доменное имя отображается на набор адресов хостов и транспортов. Объект, пытающийся создать соединение, выбирает из этого набора адрес, подходящий для использования с TLS. Когда соединение с этим сервером установлено, сервер предъявляет сертификат, утверждающий идентичность "sip:example.com". Поскольку доменная часть AUS SIP совпадает с субъектом сертификата, сервер считается аутентифицированным (нормативные правила такого сравнения см. в разделе 7.2).
Session Initiation Protocol Secure (SIPS) borrows this pattern of server certificate matching from HTTPS. However, RFC 2818 [7] prefers that the identity be conveyed as a subjectAltName extension of type dNSName rather than the common practice of conveying the identity in the CN field of the Subject field. Similarly, this document recommends that the SIP domain identity be conveyed as a subjectAltName extension of type uniformResourceIdentifier (c.f. Sections 6 and 7.1).
Session Initiation Protocol Secure (SIPS) заимствует этот образец сопоставления сертификата сервера из HTTPS. Однако RFC 2818 [7] предпочитает, чтобы идентичность передавалась в расширении subjectAltName типа dNSName, а не обычной практикой передачи идентичности в поле CN поля Subject. Аналогично, настоящий документ рекомендует передавать идентичность SIP-домена в расширении subjectAltName типа uniformResourceIdentifier (см. разделы 6 и 7.1).
A domain name in an X.509 certificates is properly interpreted only as a sequence of octets to be compared to the URI used to reach the host. No inference can be made based on the DNS name hierarchy. For example, a valid certificate for "example.com" does not imply that the owner of that certificate has any relationship at all to "subname.example.com".
Доменное имя в сертификатах X.509 правильно интерпретируется только как последовательность октетов, которую следует сравнить с URI, использованным для достижения хоста. Никаких выводов на основании иерархии DNS-имён делать нельзя. Например, действительный сертификат для "example.com" вовсе не означает, что владелец этого сертификата имеет какое-либо отношение к "subname.example.com".
5. The Need for Mutual Interdomain Authentication
5. Необходимость взаимной междоменной аутентификации
Consider the SIP trapezoid shown in Figure 1.
Рассмотрим трапецию SIP, показанную на рисунке 1.
Proxy-A.example.com Proxy-B.example.net +-------+ +-------+ | Proxy |--------------------| Proxy | +----+--+ +---+---+ | | | | | | | +---+ 0---0 | | /-\ |___| +---+ / / +----+ alice@example.com bob@example.net Figure 1: SIP Trapezoid
Proxy-A.example.com Proxy-B.example.net +-------+ +-------+ | Proxy |--------------------| Proxy | +----+--+ +---+---+ | | | | | | | +---+ 0---0 | | /-\ |___| +---+ / / +----+ alice@example.com bob@example.net Figure 1: SIP Trapezoid
A user, alice@example.com, invites bob@example.net for a multimedia communication session. Alice's outbound proxy, Proxy-A.example.com, uses normal RFC 3263 [8] resolution rules to find a proxy -- Proxy- B.example.net -- in the example.net domain that uses TLS. Proxy-A actively establishes an interdomain TLS connection with Proxy-B and each presents a certificate to authenticate that connection.
Пользователь alice@example.com приглашает bob@example.net на сеанс мультимедийной связи. Исходящий прокси-сервер Алисы, Proxy-A.example.com, использует обычные правила разрешения RFC 3263 [8], чтобы найти в домене example.net прокси-сервер — Proxy-B.example.net, использующий TLS. Proxy-A активно устанавливает междоменное соединение TLS с Proxy-B, и каждая сторона предъявляет сертификат для аутентификации этого соединения.
RFC 3261 [2], Section 26.3.2.2, "Interdomain Requests" states that when a TLS connection is created between two proxies:
В RFC 3261 [2], раздел 26.3.2.2, "Interdomain Requests", сказано, что при создании соединения TLS между двумя прокси-серверами:
Each side of the connection SHOULD verify and inspect the certificate of the other, noting the domain name that appears in the certificate for comparison with the header fields of SIP messages.
Каждая сторона соединения СЛЕДУЕТ проверять и изучать сертификат другой стороны, обращая внимание на доменное имя, указанное в сертификате, для сравнения с полями заголовков сообщений SIP.
However, RFC 3261 is silent on whether to use the subjectAltName or CN of the certificate to obtain the domain name, and which takes precedence when there are multiple names identifying the holder of the certificate. The authentication problem for Proxy-A is straightforward: in the certificate Proxy-A receives from Proxy-B, Proxy-A looks for an identity that is a SIP URI ("sip:example.net") or a DNS name ("example.net") that asserts Proxy-B's authority over the example.net domain. Normative behavior for a TLS client like Proxy-A is specified in Section 7.3.
Однако RFC 3261 умалчивает о том, использовать ли для получения доменного имени subjectAltName или CN сертификата и что имеет приоритет при наличии нескольких имён, идентифицирующих владельца сертификата. Задача аутентификации для Proxy-A проста: в сертификате, полученном Proxy-A от Proxy-B, Proxy-A ищет идентичность — SIP URI ("sip:example.net") или DNS-имя ("example.net"), — которая подтверждает полномочия Proxy-B в отношении домена example.net. Нормативное поведение клиента TLS, такого как Proxy-A, определено в разделе 7.3.
The problem for Proxy-B is slightly more complex since it accepts the TLS request passively. Thus, Proxy-B does not possess an equivalent AUS that it can use as an anchor in matching identities from Proxy-A's certificate.
Задача Proxy-B несколько сложнее, поскольку он принимает запрос TLS пассивно. Таким образом, Proxy-B не располагает эквивалентным AUS, который он мог бы использовать в качестве опоры при сопоставлении идентичностей из сертификата Proxy-A.
RFC 3261 [2], Section 26.3.2.2, only tells Proxy-B to "compare the domain asserted by the certificate with the 'domainname' portion of the From header field in the INVITE request". The difficulty with that instruction is that the domainname in the From header field is not always that of the domain from which the request is received.
В RFC 3261 [2], раздел 26.3.2.2, Proxy-B лишь предписывается "сравнить домен, утверждённый сертификатом, с частью 'domainname' поля заголовка From в запросе INVITE". Сложность этого указания в том, что domainname в поле заголовка From не всегда совпадает с доменом, из которого получен запрос.
The normative behavior for a TLS server like Proxy-B that passively accepts a TLS connection and requires authentication of the sending peer domain is provided in Section 7.4.
Нормативное поведение сервера TLS, такого как Proxy-B, который пассивно принимает соединение TLS и требует аутентификации домена отправляющей стороны, приведено в разделе 7.4.
6. Certificate Usage by a SIP Service Provider
6. Использование сертификатов поставщиком услуг SIP
It is possible for service providers to continue the practice of using existing certificates for SIP usage with the identity conveyed only in the Subject field, but they should carefully consider the following advantages of conveying identity in the subjectAltName extension field:
Поставщики услуг могут продолжать практику использования существующих сертификатов для SIP, когда идентичность передаётся только в поле Subject, но им следует внимательно рассмотреть следующие преимущества передачи идентичности в расширении subjectAltName:
o The subjectAltName extension can hold multiple values, so the same certificate can identify multiple servers or sip domains.
o Расширение subjectAltName может содержать несколько значений, поэтому один и тот же сертификат может идентифицировать несколько серверов или SIP-доменов.
o There is no fixed syntax specified for the Subject field, so issuers vary in how the field content is set. This forces a recipient to use heuristics to extract the identity, again increasing opportunities for misinterpretation.
o Для поля Subject не определён фиксированный синтаксис, поэтому у разных центров сертификации содержимое поля задаётся по-разному. Это вынуждает получателя применять эвристики для извлечения идентичности, что снова увеличивает возможности неверной интерпретации.
Because of these advantages, service providers are strongly encouraged to obtain certificates that contain the identity or identities in the subjectAltName extension field.
В силу этих преимуществ поставщикам услуг настоятельно рекомендуется получать сертификаты, содержащие идентичность или идентичности в расширении subjectAltName.
When assigning certificates to authoritative servers, a SIP service provider MUST ensure that the SIP domain used to reach the server appears as an identity in the subjectAltName field, or for compatibility with existing certificates, the Subject field of the certificate. In practice, this means that a service provider distributes to its users SIP URIs whose domain portion corresponds to an identity for which the service provider has been issued a certificate.
При назначении сертификатов авторитетным серверам поставщик услуг SIP ОБЯЗАН обеспечить, чтобы SIP-домен, используемый для доступа к серверу, присутствовал как идентичность в поле subjectAltName или, для совместимости с существующими сертификатами, в поле Subject сертификата. На практике это означает, что поставщик услуг распространяет среди своих пользователей SIP URI, доменная часть которых соответствует идентичности, на которую поставщику услуг выдан сертификат.
7. Behavior of SIP Entities
7. Поведение SIP-объектов
This section normatively specifies the behavior of SIP entities when using X.509 certificates to determine an authenticated SIP domain identity.
В настоящем разделе нормативно определено поведение SIP-объектов при использовании сертификатов X.509 для определения аутентифицированной идентичности SIP-домена.
The first two subsections apply to all SIP implementations that use TLS to authenticate the peer: Section 7.1 describes how to extract a set of SIP identities from the certificate obtained from a TLS peer, and Section 7.2 specifies how to compare SIP identities. The remaining subsections provide context for how and when these rules are to be applied by entities in different SIP roles.
Первые два подраздела относятся ко всем реализациям SIP, использующим TLS для аутентификации стороны: в разделе 7.1 описано, как извлечь набор идентичностей SIP из сертификата, полученного от стороны TLS, а в разделе 7.2 определено, как сравнивать идентичности SIP. Остальные подразделы поясняют, как и когда эти правила должны применяться объектами в различных ролях SIP.
7.1. Finding SIP Identities in a Certificate
7.1. Поиск идентичностей SIP в сертификате
Implementations (both clients and server) MUST determine the validity of a certificate by following the procedures described in RFC 5280 [6].
Реализации (как клиенты, так и серверы) ОБЯЗАНЫ определять действительность сертификата, следуя процедурам, описанным в RFC 5280 [6].
As specified by RFC 5280 [6], Section 4.2.1.12, implementations MUST check for restrictions on certificate usage declared by any extendedKeyUsage extensions in the certificate. The SIP Extended Key Usage (EKU) document [12] defines an extendedKeyUsage for SIP.
В соответствии с RFC 5280 [6], раздел 4.2.1.12, реализации ОБЯЗАНЫ проверять ограничения на использование сертификата, объявленные любыми расширениями extendedKeyUsage в сертификате. Документ о расширенном использовании ключа (EKU) для SIP [12] определяет extendedKeyUsage для SIP.
Given an X.509 certificate that the above checks have found to be acceptable, the following describes how to determine what SIP domain identity or identities the certificate contains. A single certificate can serve more than one purpose -- that is, the certificate might contain identities not acceptable as SIP, domain identities and/or might contain one or more identities that are acceptable for use as SIP domain identities.
Если по результатам указанных выше проверок сертификат X.509 признан приемлемым, далее описывается, как определить, какие идентичности SIP-домена он содержит. Один сертификат может служить более чем одной цели, то есть сертификат может содержать идентичности, не приемлемые в качестве SIP-доменных, и (или) одну или несколько идентичностей, приемлемых для использования в качестве идентичностей SIP-домена.
1. Examine each value in the subjectAltName field. The subjectAltName field and the constraints on its values are defined in Section 4.2.1.6 of RFC 5280 [6]. The subjectAltName field can be absent or can contain one or more values. Each value in the subjectAltName has a type; the only types acceptable for encoding a SIP domain identity SHALL be:
1. Просмотреть каждое значение в поле subjectAltName. Поле subjectAltName и ограничения на его значения определены в разделе 4.2.1.6 RFC 5280 [6]. Поле subjectAltName может отсутствовать или содержать одно или несколько значений. Каждое значение в subjectAltName имеет тип; единственными типами, приемлемыми для кодирования идентичности SIP-домена, ДОЛЖНЫ быть:
URI If the scheme of the URI is not "sip", then the implementation MUST NOT accept the value as a SIP domain identity.
URI Если схема URI не "sip", то реализация НЕ ДОЛЖНА принимать это значение в качестве идентичности SIP-домена.
If the scheme of the URI value is "sip", and the URI value that contains a userpart (there is an '@'), the implementation MUST NOT accept the value as a SIP domain identity (a value with a userpart identifies an individual user, not a domain).
Если схема значения URI — "sip", а само значение URI содержит userpart (есть символ '@'), то реализация НЕ ДОЛЖНА принимать это значение в качестве идентичности SIP-домена (значение с userpart идентифицирует отдельного пользователя, а не домен).
If the scheme of the URI value is "sip", and there is no userinfo component in the URI (there is no '@'), then the implementation MUST accept the hostpart as a SIP domain identity.
Если схема значения URI — "sip" и в URI нет компонента userinfo (нет символа '@'), то реализация ОБЯЗАНА принять hostpart в качестве идентичности SIP-домена.
Note: URI scheme tokens are always case insensitive.
Примечание: токены схем URI всегда нечувствительны к регистру.
DNS An implementation MUST accept a domain name system identifier as a SIP domain identity if and only if no other identity is found that matches the "sip" URI type described above.
DNS Реализация ОБЯЗАНА принять идентификатор системы доменных имён в качестве идентичности SIP-домена тогда и только тогда, когда не найдено иной идентичности, соответствующей типу URI "sip", описанному выше.
2. If and only if the subjectAltName does not appear in the certificate, the implementation MAY examine the CN field of the certificate. If a valid DNS name is found there, the implementation MAY accept this value as a SIP domain identity. Accepting a DNS name in the CN value is allowed for backward compatibility, but when constructing new certificates, consider the advantages of using the subjectAltName extension field (see Section 6).
2. Тогда и только тогда, когда в сертификате отсутствует subjectAltName, реализация МОЖЕТ исследовать поле CN сертификата. Если там обнаруживается допустимое DNS-имя, реализация МОЖЕТ принять это значение в качестве идентичности SIP-домена. Принятие DNS-имени в значении CN допускается для обратной совместимости, но при создании новых сертификатов следует учитывать преимущества расширения subjectAltName (см. раздел 6).
The above procedure yields a set containing zero or more identities from the certificate. A client uses these identities to authenticate a server (see Section 7.3) and a server uses them to authenticate a client (see Section 7.4).
Описанная процедура даёт набор, содержащий ноль или более идентичностей из сертификата. Клиент использует эти идентичности для аутентификации сервера (см. раздел 7.3), а сервер — для аутентификации клиента (см. раздел 7.4).
7.2. Comparing SIP Identities
7.2. Сравнение идентичностей SIP
When an implementation (either client or server) compares two values as SIP domain identities:
Когда реализация (клиент или сервер) сравнивает два значения как идентичности SIP-домена:
Implementations MUST compare only the DNS name component of each SIP domain identifier; an implementation MUST NOT use any scheme or parameters in the comparison.
Реализации ОБЯЗАНЫ сравнивать только компонент DNS-имени каждого идентификатора SIP-домена; реализация НЕ ДОЛЖНА использовать при сравнении какие-либо схемы или параметры.
Implementations MUST compare the values as DNS names, which means that the comparison is case insensitive as specified by RFC 4343 [3]. Implementations MUST handle Internationalized Domain Names (IDNs) in accordance with Section 7.2 of RFC 5280 [6].
Реализации ОБЯЗАНЫ сравнивать значения как DNS-имена, то есть сравнение нечувствительно к регистру, как указано в RFC 4343 [3]. Реализации ОБЯЗАНЫ обрабатывать интернационализированные доменные имена (IDN) в соответствии с разделом 7.2 RFC 5280 [6].
Implementations MUST match the values in their entirety:
Реализации ОБЯЗАНЫ сопоставлять значения целиком:
Implementations MUST NOT match suffixes. For example, "foo.example.com" does not match "example.com".
Реализации НЕ ДОЛЖНЫ сопоставлять суффиксы. Например, "foo.example.com" не соответствует "example.com".
Implementations MUST NOT match any form of wildcard, such as a leading "." or "*." with any other DNS label or sequence of labels. For example, "*.example.com" matches only "*.example.com" but not "foo.example.com". Similarly, ".example.com" matches only ".example.com", and does not match "foo.example.com".
Реализации НЕ ДОЛЖНЫ сопоставлять никакую форму шаблона, например ведущую "." или "*." с любой другой меткой DNS или последовательностью меток. Например, "*.example.com" соответствует только "*.example.com", но не "foo.example.com". Аналогично, ".example.com" соответствует только ".example.com" и не соответствует "foo.example.com".
RFC 2818 [7] (HTTP over TLS) allows the dNSName component to contain a wildcard; e.g., "DNS:*.example.com". RFC 5280 [6], while not disallowing this explicitly, leaves the interpretation of wildcards to the individual specification. RFC 3261 [2] does not provide any guidelines on the presence of wildcards in certificates. Through the rule above, this document prohibits such wildcards in certificates for SIP domains.
RFC 2818 [7] (HTTP over TLS) допускает наличие шаблона в компоненте dNSName, например "DNS:*.example.com". RFC 5280 [6], явно не запрещая этого, оставляет интерпретацию шаблонов на усмотрение отдельных спецификаций. RFC 3261 [2] не даёт никаких указаний о наличии шаблонов в сертификатах. В силу приведённого выше правила настоящий документ запрещает такие шаблоны в сертификатах для SIP-доменов.
7.3. Client Behavior
7.3. Поведение клиента
A client uses the domain portion of the SIP AUS to query a (possibly untrusted) DNS to obtain a result set, which is one or more SRV and A records identifying the server for the domain (see Section 4 for an overview).
Клиент использует доменную часть AUS SIP, чтобы запросить (возможно, недоверенную) DNS и получить результирующий набор — одну или несколько записей SRV и A, идентифицирующих сервер для домена (обзор см. в разделе 4).
The SIP server, when establishing a TLS connection, presents its certificate to the client for authentication. The client MUST determine the SIP domain identities in the server certificate using the procedure in Section 7.1. Then, the client MUST compare the original domain portion of the SIP AUS used as input to the RFC 3263 [8] server location procedures to the SIP domain identities obtained from the certificate.
SIP-сервер при установлении соединения TLS предъявляет клиенту свой сертификат для аутентификации. Клиент ОБЯЗАН определить идентичности SIP-домена в сертификате сервера с помощью процедуры из раздела 7.1. Затем клиент ОБЯЗАН сравнить исходную доменную часть AUS SIP, использованную на входе процедур определения местоположения сервера RFC 3263 [8], с идентичностями SIP-домена, полученными из сертификата.
o If there were no identities found in the server certificate, the server is not authenticated.
o Если в сертификате сервера не найдено ни одной идентичности, сервер не аутентифицирован.
o If the domain extracted from the AUS matches any SIP domain identity obtained from the certificate when compared as described in Section 7.2, the server is authenticated for the domain.
o Если домен, извлечённый из AUS, совпадает с любой идентичностью SIP-домена, полученной из сертификата, при сравнении, описанном в разделе 7.2, сервер считается аутентифицированным для этого домена.
If the server is not authenticated, the client MUST close the connection immediately.
Если сервер не аутентифицирован, клиент ОБЯЗАН немедленно закрыть соединение.
7.4. Server Behavior
7.4. Поведение сервера
When a server accepts a TLS connection, the server presents its own X.509 certificate to the client. Servers that wish to authenticate the client will ask the client for a certificate. If the client possesses a certificate, that certificate is presented to the server. If the client does not present a certificate, the client MUST NOT be considered authenticated.
Когда сервер принимает соединение TLS, он предъявляет клиенту свой сертификат X.509. Серверы, желающие аутентифицировать клиента, запрашивают у клиента сертификат. Если клиент располагает сертификатом, этот сертификат предъявляется серверу. Если клиент не предъявляет сертификат, он НЕ ДОЛЖЕН считаться аутентифицированным.
Whether or not to close a connection if the client does not present a certificate is a matter of local policy, and depends on the authentication needs of the server for the connection. Some currently deployed servers use Digest authentication to authenticate individual requests on the connection, and choose to treat the connection as authenticated by those requests for some purposes (but see Section 8.1).
Закрывать ли соединение, если клиент не предъявил сертификат, — вопрос локальной политики, зависящий от потребностей сервера в аутентификации для данного соединения. Некоторые развёрнутые в настоящее время серверы используют аутентификацию Digest для аутентификации отдельных запросов в соединении и для некоторых целей рассматривают соединение как аутентифицированное этими запросами (но см. раздел 8.1).
If the local server policy requires client authentication for some local purpose, then one element of such a local policy might be to allow the connection only if the client is authenticated. For example, if the server is an inbound proxy that has peering relationships with the outbound proxies of other specific domains, the server might allow only connections authenticated as coming from those domains.
Если локальная политика сервера требует аутентификации клиента для некоторой локальной цели, то одним из элементов такой локальной политики может быть разрешение соединения только при условии аутентификации клиента. Например, если сервер является входящим прокси-сервером, имеющим отношения пиринга с исходящими прокси-серверами других конкретных доменов, сервер может разрешать только соединения, аутентифицированные как исходящие из этих доменов.
When authenticating the client, the server MUST obtain the set of SIP domain identities from the client certificate as described in Section 7.1. Because the server accepted the TLS connection passively, unlike a client, the server does not possess an AUS for comparison. Nonetheless, server policies can use the set of SIP domain identities gathered from the certificate in Section 7.1 to make authorization decisions.
При аутентификации клиента сервер ОБЯЗАН получить набор идентичностей SIP-домена из сертификата клиента так, как описано в разделе 7.1. Поскольку сервер принял соединение TLS пассивно, в отличие от клиента он не располагает AUS для сравнения. Тем не менее политики сервера могут использовать набор идентичностей SIP-домена, собранный из сертификата в разделе 7.1, для принятия решений об авторизации.
For example, a very open policy could be to accept an X.509 certificate and validate the certificate using the procedures in RFC 5280 [6]. If the certificate is valid, the identity set is logged.
Например, весьма открытая политика может состоять в приёме сертификата X.509 и проверке сертификата с помощью процедур RFC 5280 [6]. Если сертификат действителен, набор идентичностей заносится в журнал.
Alternatively, the server could have a list of all SIP domains the server is allowed to accept connections from; when a client presents its certificate, for each identity in the client certificate, the server searches for the identity in the list of acceptable domains to decide whether or not to accept the connection. Other policies that make finer distinctions are possible. The decision of whether or not the authenticated connection to the client is appropriate for use to route new requests to the client domain is independent of whether or not the connection is authenticated; the connect-reuse [10] document discusses this aspect in more detail.
В качестве альтернативы сервер может иметь список всех SIP-доменов, соединения из которых ему разрешено принимать; когда клиент предъявляет сертификат, сервер для каждой идентичности в сертификате клиента ищет эту идентичность в списке допустимых доменов, чтобы решить, принимать ли соединение. Возможны и другие политики, проводящие более тонкие различия. Решение о том, пригодно ли аутентифицированное соединение с клиентом для маршрутизации новых запросов к домену клиента, не зависит от того, аутентифицировано ли соединение; документ о повторном использовании соединений [10] рассматривает этот аспект подробнее.
7.5. Proxy Behavior
7.5. Поведение прокси-сервера
A proxy MUST use the procedures defined for a User Agent Server (UAS) in Section 7.4 when authenticating a connection from a client.
Прокси-сервер ОБЯЗАН использовать процедуры, определённые для сервера пользовательского агента (UAS) в разделе 7.4, при аутентификации соединения от клиента.
A proxy MUST use the procedures defined for a User Agent Client (UAC) in Section 7.3 when requesting an authenticated connection to a UAS.
Прокси-сервер ОБЯЗАН использовать процедуры, определённые для клиента пользовательского агента (UAC) в разделе 7.3, при запросе аутентифицированного соединения с UAS.
If a proxy adds a Record-Route when forwarding a request with the expectation that the route is to use secure connections, the proxy MUST insert into the Record-Route header a URI that corresponds to an identity for which the proxy has a certificate; if the proxy does not insert such a URI, then creation of a secure connection using the value from the Record-Route as the AUS will be impossible.
Если прокси-сервер добавляет Record-Route при пересылке запроса в расчёте на то, что маршрут будет использовать защищённые соединения, прокси-сервер ОБЯЗАН вставить в заголовок Record-Route URI, соответствующий идентичности, на которую у прокси-сервера есть сертификат; если прокси-сервер не вставит такой URI, создание защищённого соединения с использованием значения из Record-Route в качестве AUS будет невозможно.
7.6. Registrar Behavior
7.6. Поведение регистратора
A SIP registrar, acting as a server, follows the normative behavior of Section 7.4. When the SIP registrar accepts a TLS connection from the client, the SIP registrar presents its certificate. Depending on the registrar policies, the SIP registrar can challenge the client with HTTP Digest.
SIP-регистратор, действуя как сервер, следует нормативному поведению раздела 7.4. Когда SIP-регистратор принимает соединение TLS от клиента, он предъявляет свой сертификат. В зависимости от политик регистратора SIP-регистратор может запросить у клиента прохождение аутентификации HTTP Digest.
7.7. Redirect Server Behavior
7.7. Поведение сервера переадресации
A SIP redirect server follows the normative behavior of a UAS as specified in Section 7.4.
SIP-сервер переадресации следует нормативному поведению UAS, указанному в разделе 7.4.
7.8. Virtual SIP Servers and Certificate Content
7.8. Виртуальные SIP-серверы и содержимое сертификата
In the "virtual hosting" cases where multiple domains are managed by a single application, a certificate can contain multiple subjects by having distinct identities in the subjectAltName field as specified in RFC 4474 [9]. Clients seeking to authenticate a server on such a virtual host can still follow the directions in Section 7.3 to find the identity matching the SIP AUS used to query DNS.
В случаях "виртуального хостинга", когда несколько доменов управляются одним приложением, сертификат может содержать несколько субъектов, имея различные идентичности в поле subjectAltName, как указано в RFC 4474 [9]. Клиенты, стремящиеся аутентифицировать сервер на таком виртуальном хосте, могут по-прежнему следовать указаниям раздела 7.3, чтобы найти идентичность, совпадающую с AUS SIP, использованным для запроса DNS.
Alternatively, if the TLS client hello "server_name" extension as defined in RFC 4366 [4] is supported, the client SHOULD use that extension to request a certificate corresponding to the specific domain (from the SIP AUS) with which the client is seeking to establish a connection.
В качестве альтернативы, если поддерживается расширение "server_name" сообщения TLS client hello, определённое в RFC 4366 [4], клиенту СЛЕДУЕТ использовать это расширение, чтобы запросить сертификат, соответствующий конкретному домену (из AUS SIP), с которым клиент стремится установить соединение.
8. Security Considerations
8. Соображения безопасности
The goals of TLS (when used with X.509 certificates) include the following security guarantees at the transport layer:
Цели TLS (при использовании с сертификатами X.509) включают следующие гарантии безопасности на транспортном уровне:
Confidentiality: packets tunneled through TLS can be read only by the sender and receiver.
Конфиденциальность: пакеты, передаваемые через TLS, могут читать только отправитель и получатель.
Integrity: packets tunneled through TLS cannot be undetectably modified on the connection between the sender and receiver.
Целостность: пакеты, передаваемые через TLS, не могут быть незаметно изменены в соединении между отправителем и получателем.
Authentication: each principal is authenticated to the other as possessing a private key for which a certificate has been issued. Moreover, this certificate has not been revoked, and is verifiable by a certificate chain leading to a (locally configured) trust anchor.
Аутентификация: каждая сторона аутентифицируется для другой как обладающая закрытым ключом, на который выдан сертификат. Более того, этот сертификат не отозван и проверяем с помощью цепочки сертификатов, ведущей к (локально настроенной) точке доверия.
We expect appropriate processing of domain certificates to provide the following security guarantees at the application level:
Мы ожидаем, что надлежащая обработка доменных сертификатов обеспечит следующие гарантии безопасности на уровне приложения:
Confidentiality: SIPS messages from alice@example.com to bob@example.net can be read only by alice@example.com, bob@example.net, and SIP proxies issued with domain certificates for example.com or example.net.
Конфиденциальность: сообщения SIPS от alice@example.com к bob@example.net могут читать только alice@example.com, bob@example.net и SIP-прокси, которым выданы доменные сертификаты для example.com или example.net.
Integrity: SIPS messages from alice@example.com to bob@example.net cannot be undetectably modified on the links between alice@example.com, bob@example.net, and SIP proxies issued with domain certificates for example.com or example.net.
Целостность: сообщения SIPS от alice@example.com к bob@example.net не могут быть незаметно изменены на участках между alice@example.com, bob@example.net и SIP-прокси, которым выданы доменные сертификаты для example.com или example.net.
Authentication: alice@example.com and proxy.example.com are mutually authenticated; moreover, proxy.example.com is authenticated to alice@example.com as an authoritative proxy for domain example.com. Similar mutual authentication guarantees are given between proxy.example.com and proxy.example.net and between proxy.example.net and bob@example.net. As a result, alice@example.com is transitively mutually authenticated to bob@example.net (assuming trust in the authoritative proxies for example.com and example.net).
Аутентификация: alice@example.com и proxy.example.com взаимно аутентифицированы; более того, proxy.example.com аутентифицирован для alice@example.com как авторитетный прокси-сервер для домена example.com. Аналогичные гарантии взаимной аутентификации обеспечиваются между proxy.example.com и proxy.example.net, а также между proxy.example.net и bob@example.net. В результате alice@example.com транзитивно взаимно аутентифицирован с bob@example.net (при условии доверия к авторитетным прокси-серверам для example.com и example.net).
8.1. Connection Authentication Using Digest
8.1. Аутентификация соединения с использованием Digest
Digest authentication in SIP provides for authentication of the message sender to the challenging UAS. As commonly deployed, digest authentication provides only very limited integrity protection of the authenticated message, and has no provision for binding the authentication to any attribute of the transport. Many existing SIP deployments have chosen to use the Digest authentication of one or more messages on a particular transport connection as a way to authenticate the connection itself -- by implication, authenticating other (unauthenticated) messages on that connection. Some even choose to similarly authenticate a UDP source address and port based on the digest authentication of another message received from that address and port. This use of digest goes beyond the assurances that the Digest Authentication mechanism was designed to provide. A SIP implementation SHOULD NOT use the Digest Authentication of one message on a TCP connection or from a UDP peer to infer any authentication of any other messages on that connection or from that peer. Authentication of the domain at the other end of a connection SHOULD be accomplished using TLS and the certificate validation rules described by this specification instead.
Аутентификация Digest в SIP обеспечивает аутентификацию отправителя сообщения для UAS, выдающего запрос. В распространённом применении аутентификация digest обеспечивает лишь весьма ограниченную защиту целостности аутентифицированного сообщения и не предусматривает привязки аутентификации к какому-либо атрибуту транспорта. Многие существующие развёртывания SIP выбрали использование аутентификации Digest одного или нескольких сообщений в конкретном транспортном соединении как способ аутентификации самого соединения — по сути, аутентифицируя другие (неаутентифицированные) сообщения в этом соединении. Некоторые даже аналогично аутентифицируют адрес и порт источника UDP на основании аутентификации digest другого сообщения, полученного с этого адреса и порта. Такое использование digest выходит за пределы гарантий, для предоставления которых был разработан механизм аутентификации Digest. Реализации SIP НЕ СЛЕДУЕТ использовать аутентификацию Digest одного сообщения в соединении TCP или от стороны UDP для вывода об аутентификации любых других сообщений в этом соединении или от этой стороны. Вместо этого аутентификацию домена на другом конце соединения СЛЕДУЕТ выполнять с использованием TLS и правил проверки сертификатов, описанных в настоящей спецификации.
