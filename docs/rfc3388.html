Abstract
Аннотация
This document defines two Session Description Protocol (SDP) attributes: "group" and "mid". They allow to group together several "m" lines for two different purposes: for lip synchronization and for receiving media from a single flow (several media streams) that are encoded in different formats during a particular session, on different ports and host interfaces.
Настоящий документ определяет два атрибута протокола описания сессий (SDP): «group» и «mid». Они позволяют группировать несколько строк «m» для двух различных целей: для синхронизации губ и для приёма медиа из одного потока (нескольких медиапотоков), которые в течение конкретной сессии кодируются в разных форматах, на разных портах и интерфейсах хоста.
1. Introduction
1. Введение
An SDP session description typically contains one or more media lines - they are commonly known as "m" lines. When a session description contains more than one "m" line, SDP does not provide any means to express a particular relationship between two or more of them. When an application receives an SDP session description with more than one "m" line, it is up to the application what to do with them. SDP does not carry any information about grouping media streams.
Описание сессии SDP обычно содержит одну или несколько строк медиа — их обычно называют строками «m». Когда описание сессии содержит более одной строки «m», SDP не предоставляет никаких средств для выражения конкретного отношения между двумя или более из них. Когда приложение получает описание сессии SDP с более чем одной строкой «m», что с ними делать — решает само приложение. SDP не несёт никакой информации о группировке медиапотоков.
While in some environments this information can be carried out of band, it would be desirable to have extensions to SDP that allow the expression of how different media streams within a session description relate to each other. This document defines such extensions.
Хотя в некоторых средах эта информация может передаваться внеполосно, было бы желательно иметь расширения SDP, позволяющие выразить, как различные медиапотоки в описании сессии соотносятся друг с другом. Настоящий документ определяет такие расширения.

3. Media Stream Identification Attribute
3. Атрибут идентификации медиапотока
A new "media stream identification" media attribute is defined. It is used for identifying media streams within a session description. Its formatting in SDP [2] is described by the following BNF:
Определён новый атрибут медиа «media stream identification» (идентификация медиапотока). Он используется для идентификации медиапотоков в описании сессии. Его форматирование в SDP [2] описывается следующей BNF:
mid-attribute = "a=mid:" identification-tag identification-tag = token
mid-attribute = "a=mid:" identification-tag identification-tag = token
The identification tag MUST be unique within an SDP session description.
Тег идентификации ДОЛЖЕН быть уникальным в пределах описания сессии SDP.
4. Group Attribute
4. Атрибут group
A new "group" session-level attribute is defined. It is used for grouping together different media streams. Its formatting in SDP is described by the following BNF:
Определён новый атрибут уровня сессии «group». Он используется для группировки различных медиапотоков. Его форматирование в SDP описывается следующей BNF:
group-attribute = "a=group:" semantics *(space identification-tag) semantics = "LS" | "FID"
group-attribute = "a=group:" semantics *(space identification-tag) semantics = "LS" | "FID"
This document defines two standard semantics: LS (Lip Synchronization) and FID (Flow Identification). Further semantics need to be defined in a standards-track document. However, defining new semantics apart from LS and FID is discouraged. Instead, it is RECOMMENDED to use other session description mechanisms such as SDPng.
Настоящий документ определяет две стандартные семантики: LS (Lip Synchronization — синхронизация губ) и FID (Flow Identification — идентификация потока). Дальнейшие семантики должны быть определены в документе уровня Standards Track. Однако определять новые семантики помимо LS и FID не поощряется. Вместо этого РЕКОМЕНДУЕТСЯ использовать другие механизмы описания сессий, такие как SDPng.
5. Use of "group" and "mid"
5. Использование «group» и «mid»
All the "m" lines of a session description that uses "group" MUST be identified with a "mid" attribute whether they appear in the group line(s) or not. If a session description contains at least one "m" line that has no "mid" identification the application MUST NOT perform any grouping of media lines.
Все строки «m» описания сессии, использующего «group», ДОЛЖНЫ быть идентифицированы атрибутом «mid», независимо от того, появляются ли они в строке (строках) group. Если описание сессии содержит хотя бы одну строку «m» без идентификации «mid», приложение НЕ ДОЛЖНО выполнять никакой группировки строк медиа.
"a=group" lines are used to group together several "m" lines that are identified by their "mid" attribute. "a=group" lines that contain identification-tags that do not correspond to any "m" line within the session description MUST be ignored. The application acts as if the "a=group" line did not exist. The behavior of an application receiving an SDP with grouped "m" lines is defined by the semantics field in the "a=group" line. There MAY be several "a=group" lines in a session description. All the "a=group" lines of a session description MAY or MAY NOT use the same semantics. An "m" line identified by its "mid" attribute MAY appear in more than one "a=group" line as long as the "a=group" lines use different semantics. An "m" line identified by its "mid" attribute MUST NOT appear in more than one "a=group" line using the same semantics.
Строки «a=group» используются для группировки нескольких строк «m», идентифицированных их атрибутом «mid». Строки «a=group», содержащие идентификационные теги, не соответствующие ни одной строке «m» в описании сессии, ДОЛЖНЫ игнорироваться. Приложение ведёт себя так, как если бы строки «a=group» не было. Поведение приложения, получающего SDP со сгруппированными строками «m», определяется полем семантики в строке «a=group». В описании сессии МОЖЕТ быть несколько строк «a=group». Все строки «a=group» описания сессии МОГУТ или МОГУТ НЕ использовать одну и ту же семантику. Строка «m», идентифицированная её атрибутом «mid», МОЖЕТ появляться более чем в одной строке «a=group», при условии что строки «a=group» используют разные семантики. Строка «m», идентифицированная её атрибутом «mid», НЕ ДОЛЖНА появляться более чем в одной строке «a=group», использующей одну и ту же семантику.
6. Lip Synchronization (LS)
6. Синхронизация губ (LS)
An application that receives a session description that contains "m" lines that are grouped together using LS semantics MUST synchronize the playout of the corresponding media streams. Note that LS semantics not only apply to a video stream that has to be synchronized with an audio stream. The playout of two streams of the same type can be synchronized as well.
Приложение, получающее описание сессии, содержащее строки «m», сгруппированные вместе с использованием семантики LS, ДОЛЖНО синхронизировать воспроизведение соответствующих медиапотоков. Обратите внимание, что семантика LS применяется не только к видеопотоку, который должен быть синхронизирован с аудиопотоком. Воспроизведение двух потоков одного типа также может быть синхронизировано.
For RTP streams synchronization is typically performed using RTCP, which provides enough information to map time stamps from the different streams into a wall clock. However, the concept of media stream synchronization MAY also apply to media streams that do not make use of RTP. If this is the case, the application MUST recover the original timing relationship between the streams using whatever available mechanism.
Для потоков RTP синхронизация обычно выполняется с использованием RTCP, который предоставляет достаточно информации для отображения отметок времени из разных потоков в единое время. Однако понятие синхронизации медиапотоков МОЖЕТ также применяться к медиапотокам, не использующим RTP. Если это так, приложение ДОЛЖНО восстановить исходное временное соотношение между потоками с использованием любого доступного механизма.
6.1. Example of LS
6.1. Пример LS
The following example shows a session description of a conference that is being multicast. The first media stream (mid:1) contains the voice of the speaker who speaks in English. The second media stream (mid:2) contains the video component and the third (mid:3) media stream carries the translation to Spanish of what he is saying. The first and the second media streams MUST be synchronized.
Следующий пример показывает описание сессии конференции, передаваемой многоадресно. Первый медиапоток (mid:1) содержит голос оратора, говорящего по-английски. Второй медиапоток (mid:2) содержит видеокомпонент, а третий (mid:3) медиапоток несёт перевод на испанский того, что он говорит. Первый и второй медиапотоки ДОЛЖНЫ быть синхронизированы.
v=0 o=Laura 289083124 289083124 IN IP4 one.example.com t=0 0 c=IN IP4 224.2.17.12/127 a=group:LS 1 2 m=audio 30000 RTP/AVP 0 a=mid:1 m=video 30002 RTP/AVP 31 a=mid:2 m=audio 30004 RTP/AVP 0 i=This media stream contains the Spanish translation a=mid:3
v=0 o=Laura 289083124 289083124 IN IP4 one.example.com t=0 0 c=IN IP4 224.2.17.12/127 a=group:LS 1 2 m=audio 30000 RTP/AVP 0 a=mid:1 m=video 30002 RTP/AVP 31 a=mid:2 m=audio 30004 RTP/AVP 0 i=This media stream contains the Spanish translation a=mid:3
Note that although the third media stream is not present in the group line, it still MUST contain a mid attribute (mid:3), as stated before.
Обратите внимание, что хотя третьего медиапотока нет в строке group, он всё равно ДОЛЖЕН содержать атрибут mid (mid:3), как указано ранее.
7. Flow Identification (FID)
7. Идентификация потока (FID)
An "m" line in an SDP session description defines a media stream. However, SDP does not define what a media stream is. This definition can be found in the RTSP specification. The RTSP RFC [5] defines a media stream as "a single media instance, e.g., an audio stream or a video stream as well as a single whiteboard or shared application group. When using RTP, a stream consists of all RTP and RTCP packets created by a source within an RTP session".
Строка «m» в описании сессии SDP определяет медиапоток. Однако SDP не определяет, что такое медиапоток. Это определение можно найти в спецификации RTSP. RFC RTSP [5] определяет медиапоток как «единичный медиаэкземпляр, например аудиопоток или видеопоток, а также единичную доску объявлений или группу совместно используемых приложений. При использовании RTP поток состоит из всех пакетов RTP и RTCP, созданных источником в рамках сессии RTP».
This definition assumes that a single audio (or video) stream maps into an RTP session. The RTP RFC [6] defines an RTP session as follows: "For each participant, the session is defined by a particular pair of destination transport addresses (one network address plus a port pair for RTP and RTCP)".
Это определение предполагает, что единичный аудио- (или видео-) поток отображается в сессию RTP. RFC RTP [6] определяет сессию RTP следующим образом: «Для каждого участника сессия определяется конкретной парой транспортных адресов назначения (один сетевой адрес плюс пара портов для RTP и RTCP)».
While the previous definitions cover the most common cases, there are situations where a single media instance, (e.g., an audio stream or a video stream) is sent using more than one RTP session. Two examples (among many others) of this kind of situation are cellular systems using SIP [3] and systems receiving DTMF tones on a different host than the voice.
Хотя предыдущие определения охватывают наиболее общие случаи, есть ситуации, когда единичный медиаэкземпляр (например, аудиопоток или видеопоток) передаётся с использованием более чем одной сессии RTP. Два примера (среди многих других) такого рода ситуаций — сотовые системы, использующие SIP [3], и системы, принимающие DTMF-тоны на другом хосте, отличном от голоса.
7.1. SIP and Cellular Access
7.1. SIP и сотовый доступ
Systems using a cellular access and SIP as a signalling protocol need to receive media over the air. During a session the media can be encoded using different codecs. The encoded media has to traverse the radio interface. The radio interface is generally characterized by being bit error prone and associated with relatively high packet transfer delays. In addition, radio interface resources in a cellular environment are scarce and thus expensive, which calls for special measures in providing a highly efficient transport. In order to get an appropriate speech quality in combination with an efficient transport, precise knowledge of codec properties are required so that a proper radio bearer for the RTP session can be configured before transferring the media. These radio bearers are dedicated bearers per media type, i.e., codec.
Системы, использующие сотовый доступ и SIP в качестве протокола сигнализации, нуждаются в приёме медиа по радиоинтерфейсу. Во время сессии медиа может кодироваться разными кодеками. Кодированные медиа должны проходить через радиоинтерфейс. Радиоинтерфейс, как правило, характеризуется подверженностью битовым ошибкам и относительно высокими задержками передачи пакетов. Кроме того, ресурсы радиоинтерфейса в сотовой среде ограничены и потому дороги, что требует особых мер для обеспечения высокоэффективного транспорта. Чтобы получить надлежащее качество речи в сочетании с эффективным транспортом, требуется точное знание свойств кодека, чтобы можно было сконфигурировать надлежащий радионесущий канал для сессии RTP до передачи медиа. Эти радионесущие каналы являются выделенными несущими на тип медиа, то есть на кодек.
Cellular systems typically configure different radio bearers on different port numbers. Therefore, incoming media has to have different destination port numbers for the different possible codecs in order to be routed properly to the correct radio bearer. Thus, this is an example in which several RTP sessions are used to carry a single media instance (the encoded speech from the sender).
Сотовые системы обычно конфигурируют разные радионесущие каналы на разных номерах портов. Поэтому входящие медиа должны иметь разные номера портов назначения для разных возможных кодеков, чтобы маршрутизироваться надлежащим образом к правильному радионесущему каналу. Таким образом, это пример, в котором для передачи единичного медиаэкземпляра (кодированной речи от отправителя) используется несколько сессий RTP.
7.2. DTMF Tones
7.2. DTMF-тоны
Some voice sessions include DTMF tones. Sometimes the voice handling is performed by a different host than the DTMF handling. It is common to have an application server in the network gathering DTMF tones for the user while the user receives the encoded speech on his user agent. In this situations it is necessary to establish two RTP sessions: one for the voice and the other for the DTMF tones. Both RTP sessions are logically part of the same media instance.
Некоторые голосовые сессии включают DTMF-тоны. Иногда обработка голоса выполняется на другом хосте, отличном от обработки DTMF. Обычно прикладной сервер в сети собирает DTMF-тоны для пользователя, пока пользователь получает кодированную речь на своём пользовательском агенте. В этих ситуациях необходимо установить две сессии RTP: одну для голоса, другую для DTMF-тонов. Обе сессии RTP логически являются частью одного и того же медиаэкземпляра.
7.3. Media Flow Definition
7.3. Определение медиапотока
The previous examples show that the definition of a media stream in [5] do not cover some scenarios. It cannot be assumed that a single media instance maps into a single RTP session. Therefore, we introduce the definition of a media flow:
Предыдущие примеры показывают, что определение медиапотока в [5] не охватывает некоторые сценарии. Нельзя предполагать, что единичный медиаэкземпляр отображается в единственную сессию RTP. Поэтому мы вводим определение медиапотока (media flow):
Media flow consists of a single media instance, e.g., an audio stream or a video stream as well as a single whiteboard or shared application group. When using RTP, a media flow comprises one or more RTP sessions.
Медиапоток состоит из единичного медиаэкземпляра, например аудиопотока или видеопотока, а также единичной доски объявлений или группы совместно используемых приложений. При использовании RTP медиапоток включает одну или несколько сессий RTP.
7.4. FID Semantics
7.4. Семантика FID
Several "m" lines grouped together using FID semantics form a media flow. A media agent handling a media flow that comprises several "m" lines MUST send a copy of the media to every "m" line part of the flow as long as the codecs and the direction attribute present in a particular "m" line allow it.
Несколько строк «m», сгруппированных вместе с использованием семантики FID, образуют медиапоток. Медиаагент, обрабатывающий медиапоток, включающий несколько строк «m», ДОЛЖЕН отправлять копию медиа в каждую строку «m», входящую в поток, если только кодеки и атрибут направления, присутствующие в конкретной строке «m», это позволяют.
It is assumed that the application uses only one codec at a time to encode the media produced. This codec MAY change dynamically during the session, but at any particular moment only one codec is in use.
Предполагается, что приложение использует только один кодек за раз для кодирования производимых медиа. Этот кодек МОЖЕТ динамически меняться в течение сессии, но в любой конкретный момент используется только один кодек.
The application encodes the media using the current codec and checks one by one all the "m" lines that are part of the flow. If a particular "m" line contains the codec being used and the direction attribute is "sendonly" or "sendrecv", a copy of the encoded media is sent to the address/port specified in that particular media stream. If either the "m" line does not contain the codec being used or the direction attribute is neither "sendonly" nor "sendrecv", nothing is sent over this media stream.
Приложение кодирует медиа текущим кодеком и проверяет одну за другой все строки «m», входящие в поток. Если конкретная строка «m» содержит используемый кодек и атрибут направления — «sendonly» или «sendrecv», копия кодированных медиа отправляется на адрес/порт, указанный в этом конкретном медиапотоке. Если строка «m» не содержит используемый кодек либо атрибут направления не «sendonly» и не «sendrecv», по этому медиапотоку ничего не отправляется.
The application typically ends up sending media to different destinations (IP address/port number) depending on the codec used at any moment.
Приложение обычно в итоге отправляет медиа на разные пункты назначения (IP-адрес/номер порта) в зависимости от используемого в данный момент кодека.
7.4.1. Examples of FID
7.4.1. Примеры FID
The session description below might be sent by a SIP user agent using a cellular access. The user agent supports GSM on port 30000 and AMR on port 30002. When the remote party sends GSM, it will send RTP packets to port number 30000. When AMR is the codec chosen, packets will be sent to port 30002. Note that the remote party can switch between both codecs dynamically in the middle of the session. However, in this example, only one media stream at a time carries voice. The other remains "muted" while its corresponding codec is not in use.

7.5. Scenarios that FID does not Cover
7.5. Сценарии, которые FID не покрывает
It is worthwhile mentioning some scenarios where the "group" attribute using existing semantics (particularly FID) might seem to be applicable but is not.
Стоит упомянуть некоторые сценарии, в которых атрибут «group» с существующей семантикой (особенно FID) может показаться применимым, но не является таковым.
7.5.1. Parallel Encoding Using Different Codecs
7.5.1. Параллельное кодирование с использованием разных кодеков
FID semantics are useful when the application only uses one codec at a time. An application that encodes the same media using different codecs simultaneously MUST NOT use FID to group those media lines. Some systems that handle DTMF tones are a typical example of parallel encoding using different codecs.
Семантика FID полезна, когда приложение использует только один кодек за раз. Приложение, которое одновременно кодирует одни и те же медиа разными кодеками, НЕ ДОЛЖНО использовать FID для группировки этих строк медиа. Некоторые системы, обрабатывающие DTMF-тоны, являются типичным примером параллельного кодирования с использованием разных кодеков.
Some systems implement the RTP payload defined in RFC 2833, but when they send DTMF tones they do not mute the voice channel. Therefore, in effect they are sending two copies of the same DTMF tone: encoded as voice and encoded as a telephony event. When the receiver gets both copies, it typically uses the telephony event rather than the tone encoded as voice. FID semantics MUST NOT be used in this context to group both media streams since such a system is not using alternative codecs but rather different parallel encodings for the same information.
Некоторые системы реализуют полезную нагрузку RTP, определённую в RFC 2833, но при отправке DTMF-тонов они не приглушают голосовой канал. Поэтому фактически они отправляют две копии одного и того же DTMF-тона: кодированную как голос и кодированную как телефонное событие. Когда приёмник получает обе копии, он обычно использует телефонное событие вместо тона, кодированного как голос. В этом контексте семантика FID НЕ ДОЛЖНА использоваться для группировки обоих медиапотоков, поскольку такая система альтернативные кодеки, а разные параллельные кодировки одной и той же информации.

7.5.3. Один и тот же IP-адрес и номер порта

8. Usage of the "group" Attribute in SIP
8. Использование атрибута «group» в SIP
SDP descriptions are used by several different protocols, SIP among them. We include a section about SIP because the "group" attribute will most likely be used mainly by SIP systems.
Описания SDP используются несколькими разными протоколами, в том числе SIP. Мы включаем раздел о SIP, поскольку атрибут «group», скорее всего, будет использоваться в основном системами SIP.
SIP [3] is an application layer protocol for establishing, terminating and modifying multimedia sessions. SIP carries session descriptions in the bodies of the SIP messages but is independent from the protocol used for describing sessions. SDP [2] is one of the protocols that can be used for this purpose.
SIP [3] — это протокол прикладного уровня для установления, завершения и изменения мультимедийных сессий. SIP передаёт описания сессий в телах сообщений SIP, но не зависит от протокола, используемого для описания сессий. SDP [2] — один из протоколов, которые могут использоваться для этой цели.
At session establishment SIP provides a three-way handshake (INVITE- 200 OK-ACK) between end systems. However, just two of these three messages carry SDP, as described in [4].
При установлении сессии SIP обеспечивает трёхстороннее рукопожатие (INVITE — 200 OK — ACK) между конечными системами. Однако только два из этих трёх сообщений несут SDP, как описано в [4].
8.1. Mid Value in Answers
8.1. Значение mid в ответах
The "mid" attribute is an identifier for a particular media stream. Therefore, the "mid" value in the offer MUST be the same as the "mid" value in the answer. Besides, subsequent offers (e.g., in a re- INVITE) SHOULD use the same "mid" value for the already existing media streams.
Атрибут «mid» — это идентификатор конкретного медиапотока. Поэтому значение «mid» в предложении ДОЛЖНО быть тем же, что и значение «mid» в ответе. Кроме того, последующие предложения (например, в re-INVITE) СЛЕДУЕТ использовать то же значение «mid» для уже существующих медиапотоков.
RFC 3264 [4] describes the usage of SDP in relation to SIP. The offerer and the answerer align their media description so that the nth media stream ("m=" line) in the offerer's session description corresponds to the nth media stream in the answerer's description.
RFC 3264 [4] описывает использование SDP в связи с SIP. Предлагающий и отвечающий выравнивают свои описания медиа так, что n-й медиапоток (строка «m=») в описании сессии предлагающего соответствует n-му медиапотоку в описании отвечающего.
The presence of the "group" attribute in an SDP session description does not modify this behavior.
Присутствие атрибута «group» в описании сессии SDP не изменяет это поведение.
Since the "mid" attribute provides a means to label "m" lines, it would be possible to perform media alignment using "mid" labels rather than matching nth "m" lines. However this would not bring any gain and would add complexity to implementations. Therefore SIP systems MUST perform media alignment matching nth lines regardless of the presence of the "group" or "mid" attributes.
Поскольку атрибут «mid» предоставляет средство для маркировки строк «m», можно было бы выполнять выравнивание медиа с использованием меток «mid», а не сопоставления n-х строк «m». Однако это не дало бы никакого выигрыша и добавило бы сложности реализациям. Поэтому системы SIP ДОЛЖНЫ выполнять выравнивание медиа сопоставлением n-х строк независимо от присутствия атрибутов «group» или «mid».
If a media stream that contained a particular "mid" identifier in the offer contains a different identifier in the answer the application ignores all the "mid" and "group" lines that might appear in the session description. The following example illustrates this scenario.

8.2. Group Value in Answers
8.2. Значение group в ответах
A SIP entity that receives an offer that contains an "a=group" line with semantics that it does not understand MUST return an answer without the "group" line. Note that, as it was described in the previous section, the "mid" lines MUST still be present in the answer.
Объект SIP, получающий предложение, содержащее строку «a=group» с семантикой, которую он не понимает, ДОЛЖЕН вернуть ответ без строки «group». Обратите внимание, что, как описано в предыдущем разделе, строки «mid» всё равно ДОЛЖНЫ присутствовать в ответе.
A SIP entity that receives an offer that contains an "a=group" line with semantics that are understood MUST return an answer that contains an "a=group" line with the same semantics. The identification-tags contained in this "a=group" lines MUST be the same that were received in the offer or a subset of them (zero identification-tags is a valid subset). When the identification-tags in the answer are a subset, the "group" value to be used in the session MUST be the one present in the answer.
Объект SIP, получающий предложение, содержащее строку «a=group» с понимаемой семантикой, ДОЛЖЕН вернуть ответ, содержащий строку «a=group» с той же семантикой. Идентификационные теги, содержащиеся в этих строках «a=group», ДОЛЖНЫ быть теми же, что были получены в предложении, или их подмножеством (ноль идентификационных тегов — допустимое подмножество). Когда идентификационные теги в ответе являются подмножеством, значение «group», которое должно использоваться в сессии, — то, что присутствует в ответе.
SIP entities refuse media streams by setting the port to zero in the corresponding "m" line. "a=group" lines MUST NOT contain identification-tags that correspond to "m" lines with port zero.
Объекты SIP отказываются от медиапотоков, устанавливая порт в ноль в соответствующей строке «m». Строки «a=group» НЕ ДОЛЖНЫ содержать идентификационные теги, соответствующие строкам «m» с портом ноль.
Note that grouping of m lines MUST always be requested by the offerer, never by the answerer. Since SIP provides a two-way SDP exchange, an answerer that requested grouping would not know whether the "group" attribute was accepted by the offerer or not. An answerer that wants to group media lines SHOULD issue another offer after having responded to the first one (in a re-INVITE for instance).
Обратите внимание, что группировка строк m ДОЛЖНА всегда запрашиваться предлагающим, никогда отвечающим. Поскольку SIP обеспечивает двусторонний обмен SDP, отвечающий, который запросил группировку, не знал бы, был ли атрибут «group» принят предлагающим или нет. Отвечающему, желающему сгруппировать строки медиа, СЛЕДУЕТ выдать другое предложение после ответа на первое (например, в re-INVITE).

8.3. Capability Negotiation
8.3. Согласование возможностей
A client that understands "group" and "mid" but does not want to make use of them in a particular session MAY want to indicate that it supports them. If a client decides to do that, it SHOULD add an "a=group" line with no identification-tags for every semantics it understands.
Клиент, который понимает «group» и «mid», но не хочет использовать их в конкретной сессии, МОЖЕТ пожелать указать, что он их поддерживает. Если клиент решает это сделать, ему СЛЕДУЕТ добавить строку «a=group» без идентификационных тегов для каждой семантики, которую он понимает.
If a server receives an offer that contains empty "a=group" lines, it SHOULD add its capabilities also in the form of empty "a=group" lines to its answer.
Если сервер получает предложение, содержащее пустые строки «a=group», ему СЛЕДУЕТ также добавить свои возможности в форме пустых строк «a=group» в свой ответ.

8.4. Backward Compatibility
8.4. Обратная совместимость
This document does not define any SIP "Require" header. Therefore, if one of the SIP user agents does not understand the "group" attribute the standard SDP fall back mechanism MUST be used (attributes that are not understood are simply ignored).
Настоящий документ не определяет никакого заголовка SIP «Require». Поэтому, если один из пользовательских агентов SIP не понимает атрибут «group», ДОЛЖЕН использоваться стандартный механизм отката SDP (атрибуты, которые не поняты, просто игнорируются).
8.4.1. Offerer does not Support "group"
8.4.1. Предлагающий не поддерживает «group»
This situation does not represent a problem because grouping requests are always performed by offerers, not by answerers. If the offerer does not support "group" this attribute will just not be used.
Эта ситуация не представляет проблемы, поскольку запросы группировки всегда выполняются предлагающими, а не отвечающими. Если предлагающий не поддерживает «group», этот атрибут просто не будет использоваться.
8.4.2. Answerer does not Support "group"
8.4.2. Отвечающий не поддерживает «group»
The answerer will ignore the "group" attribute, since it does not understand it (it will also ignore the "mid" attribute). For LS semantics, the answerer might decide to perform or to not perform synchronization between media streams.
Отвечающий проигнорирует атрибут «group», поскольку не понимает его (он также проигнорирует атрибут «mid»). Для семантики LS отвечающий может решить выполнять или не выполнять синхронизацию между медиапотоками.
For FID semantics, the answerer will consider that the session comprises several media streams.
Для семантики FID отвечающий будет считать, что сессия включает несколько медиапотоков.
Different implementations would behave in different ways. In the case of audio and different "m" lines for different codecs an implementation might decide to act as a mixer with the different incoming RTP sessions, which is the correct behavior.
Разные реализации будут вести себя по-разному. В случае аудио и разных строк «m» для разных кодеков реализация может решить действовать как микшер с разными входящими сессиями RTP, что является правильным поведением.
An implementation might also decide to refuse the request (e.g., 488 Not acceptable here or 606 Not Acceptable) because it contains several "m" lines. In this case, the server does not support the type of session that the caller wanted to establish. In case the client is willing to establish a simpler session anyway, he SHOULD re-try the request without "group" attribute and only one "m" line per flow.
Реализация может также решить отклонить запрос (например, 488 Not acceptable here или 606 Not Acceptable), поскольку он содержит несколько строк «m». В этом случае сервер не поддерживает тип сессии, который хотел установить вызывающий. В случае если клиент всё же желает установить более простую сессию, ему СЛЕДУЕТ повторить запрос без атрибута «group» и только с одной строкой «m» на поток.
9. Security Considerations
9. Вопросы безопасности
Using the "group" parameter with FID semantics, an entity that managed to modify the session descriptions exchanged between the participants to establish a multimedia session could force the participants to send a copy of the media to any particular destination.
Используя параметр «group» с семантикой FID, объект, которому удалось изменить описания сессий, обмениваемые участниками для установления мультимедийной сессии, мог бы заставить участников отправлять копию медиа любому конкретному адресату.
Integrity mechanism provided by protocols used to exchange session descriptions and media encryption can be used to prevent this attack.
Для предотвращения этой атаки может использоваться механизм целостности, обеспечиваемый протоколами, используемыми для обмена описаниями сессий, и шифрование медиа.
