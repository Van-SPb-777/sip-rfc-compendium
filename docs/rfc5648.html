Multiple Care-of Addresses Registration
Регистрация нескольких care-of адресов
Abstract
Аннотация
According to the current Mobile IPv6 specification, a mobile node may have several care-of addresses but only one, called the primary care-of address, can be registered with its home agent and the correspondent nodes. However, for matters of cost, bandwidth, delay, etc, it is useful for the mobile node to get Internet access through multiple accesses simultaneously, in which case the mobile node would be configured with multiple active IPv6 care-of addresses. This document proposes extensions to the Mobile IPv6 protocol to register and use multiple care-of addresses. The extensions proposed in this document can be used by mobile routers using the NEMO (Network Mobility) Basic Support protocol as well.
Согласно текущей спецификации Mobile IPv6 мобильный узел может иметь несколько care-of адресов, но только один из них, называемый первичным care-of адресом, может быть зарегистрирован у своего домашнего агента и корреспондентских узлов. Однако с точки зрения стоимости, полосы пропускания, задержки и т. п. мобильному узлу полезно одновременно получать доступ в Интернет через несколько подключений; в этом случае мобильный узел будет настроен с несколькими активными care-of адресами IPv6. В настоящем документе предлагаются расширения протокола Mobile IPv6 для регистрации и использования нескольких care-of адресов. Предлагаемые расширения могут также использоваться мобильными маршрутизаторами, применяющими протокол базовой поддержки NEMO (Network Mobility).

1. Introduction
1. Введение
A mobile node may use various types of network interfaces to obtain durable and wide area network connectivity. This has increasingly become true with mobile nodes having multiple interfaces, such as 802.2, 802.11, 802.16, cellular radios, etc. The motivations for and benefits of using multiple points of attachment are discussed in [MOTIVATION]. When a mobile node with multiple interfaces uses Mobile IPv6 [RFC3775] for mobility management, it cannot use its multiple interfaces to send and receive packets while taking advantage of session continuity provided by Mobile IPv6. This is because Mobile IPv6 allows the mobile node to bind only one care-of address at a time with its home address. See [MIP6ANALYSIS] for a further analysis of using multiple interfaces and addresses with Mobile IPv6.
Мобильный узел может использовать сетевые интерфейсы различных типов для получения долговременного и широкополосного сетевого подключения. Это всё чаще оказывается возможным для мобильных узлов, имеющих несколько интерфейсов, таких как 802.2, 802.11, 802.16, сотовые радиомодули и т. п. Мотивы и преимущества использования нескольких точек подключения обсуждаются в [MOTIVATION]. Когда мобильный узел с несколькими интерфейсами использует Mobile IPv6 [RFC3775] для управления мобильностью, он не может задействовать свои несколько интерфейсов для отправки и приёма пакетов, пользуясь при этом непрерывностью сеанса, обеспечиваемой Mobile IPv6. Это объясняется тем, что Mobile IPv6 позволяет мобильному узлу привязать к своему домашнему адресу только один care-of адрес одновременно. Дополнительный анализ использования нескольких интерфейсов и адресов с Mobile IPv6 см. в [MIP6ANALYSIS].
This document proposes extensions to Mobile IPv6 to allow a mobile node to register multiple care-of addresses for a home address and create multiple binding cache entries. A new Binding Identification (BID) number is created for each binding the mobile node wants to create and is sent in the Binding Update. The home agent that receives this Binding Update creates a separate binding for each BID. The BID information is stored in the corresponding binding cache entry. The BID information can now be used to identify individual bindings. The same extensions can also be used in Binding Updates sent to the correspondent nodes.
Настоящий документ предлагает расширения Mobile IPv6, позволяющие мобильному узлу регистрировать несколько care-of адресов для одного домашнего адреса и создавать несколько записей кэша привязок. Для каждой привязки, которую мобильный узел хочет создать, формируется новый номер Binding Identification (BID), который отправляется в сообщении Binding Update. Домашний агент, получивший это сообщение Binding Update, создаёт отдельную привязку для каждого BID. Информация BID сохраняется в соответствующей записи кэша привязок. Теперь информация BID может использоваться для идентификации отдельных привязок. Те же расширения могут применяться и в сообщениях Binding Update, отправляемых корреспондентским узлам.

Binding Identification Number (BID)
Binding Identification Number (BID).
The BID is an identification number used to distinguish multiple bindings registered by the mobile node. Assignment of distinct BIDs allows a mobile node to register multiple binding cache entries for a given home address. BIDs assigned to the same home address must not be duplicated at the same time. The value zero is reserved for future extensions. Each BID is generated and managed by a mobile node. The BID is stored in the Binding Update List and is sent by the mobile node in the Binding Update. A mobile node may change the value of a BID at any time according to its administrative policy -- for instance, to protect its privacy. An implementation must carefully assign the BID so as to keep using the same BID for the same binding even when the status of the binding is changed. More details can be found in Section 5.1.
BID — это идентификационный номер, используемый для различения нескольких привязок, зарегистрированных мобильным узлом. Назначение различных BID позволяет мобильному узлу зарегистрировать несколько записей кэша привязок для заданного домашнего адреса. BID, назначенные одному и тому же домашнему адресу, не должны дублироваться одновременно. Значение ноль зарезервировано для будущих расширений. Каждый BID генерируется и управляется мобильным узлом. BID сохраняется в списке Binding Update List и отправляется мобильным узлом в сообщении Binding Update. Мобильный узел может в любое время изменить значение BID в соответствии со своей административной политикой — например, для защиты конфиденциальности. Реализация должна аккуратно назначать BID, чтобы продолжать использовать один и тот же BID для одной и той же привязки даже при изменении состояния привязки. Более подробные сведения приведены в разделе 5.1.
Binding Identifier Mobility Option The Binding Identifier mobility option is used to carry the BID information.
Binding Identifier Mobility Option. Опция мобильности Binding Identifier используется для переноса информации BID.
Bulk Registration
Bulk Registration.
A mobile node can register multiple bindings at once by sending a single Binding Update. A mobile node can also replace some or all of the bindings available at the home agent with the new bindings by using the bulk registration. Bulk registration is supported only for home registration (i.e., with the home agent) as explained in Section 5.3. A mobile node must not perform the bulk registration mechanism described in this specification with a correspondent node.
Мобильный узел может зарегистрировать несколько привязок одновременно, отправив одно сообщение Binding Update. Мобильный узел может также заменить некоторые или все привязки, имеющиеся у домашнего агента, новыми привязками с помощью массовой регистрации. Массовая регистрация поддерживается только для домашней регистрации (то есть у домашнего агента), как объясняется в разделе 5.3. Мобильный узел не должен выполнять описанный в настоящей спецификации механизм массовой регистрации с корреспондентским узлом.
3. Protocol Overview
3. Обзор протокола
A new extension called the Binding Identification number (BID) is introduced to distinguish between multiple bindings pertaining to the same home address. If a mobile node configures several IPv6 global addresses on one or more of its interfaces, it can register these addresses with its home agent as care-of addresses. If the mobile node wants to register multiple bindings, it MUST generate a BID for each care-of address and store the BID in the Binding Update List. A mobile node can manipulate each binding independently by using the BIDs. The mobile node then registers its care-of addresses by sending a Binding Update with a Binding Identifier mobility option. The BID is included in the Binding Identifier mobility option. After receiving the Binding Update with a Binding Identifier mobility option, the home agent MUST copy the BID from the Binding Identifier mobility option to the corresponding field in the binding cache entry. If there is an existing binding cache entry for the mobile node, and if the BID in the Binding Update does not match the one with the existing entry, the home agent MUST create a new binding cache entry for the new care-of address and BID. The mobile node can either register multiple care-of addresses at once in a single Binding Update or independently in individual Binding Updates.
Вводится новое расширение под названием Binding Identification number (BID), предназначенное для различения нескольких привязок, относящихся к одному и тому же домашнему адресу. Если мобильный узел настраивает несколько глобальных адресов IPv6 на одном или нескольких своих интерфейсах, он может зарегистрировать эти адреса у своего домашнего агента в качестве care-of адресов. Если мобильный узел хочет зарегистрировать несколько привязок, он ДОЛЖЕН сгенерировать BID для каждого care-of адреса и сохранить BID в списке Binding Update List. Мобильный узел может независимо управлять каждой привязкой с помощью BID. Затем мобильный узел регистрирует свои care-of адреса, отправляя сообщение Binding Update с опцией мобильности Binding Identifier. BID включается в опцию мобильности Binding Identifier. После получения сообщения Binding Update с опцией мобильности Binding Identifier домашний агент ДОЛЖЕН скопировать BID из опции мобильности Binding Identifier в соответствующее поле записи кэша привязок. Если для мобильного узла уже существует запись кэша привязок и если BID в сообщении Binding Update не совпадает с BID существующей записи, домашний агент ДОЛЖЕН создать новую запись кэша привязок для нового care-of адреса и BID. Мобильный узел может либо зарегистрировать несколько care-of адресов сразу в одном сообщении Binding Update, либо независимо в отдельных сообщениях Binding Update.
If the mobile host wishes to register its binding with a correspondent node, it must perform return routability operations as described in [RFC3775]. This includes managing a Care-of Keygen token per care-of address and exchanging Care-of Test Init and Care- of Test messages with the correspondent node for each care-of address. The mobile node MAY use the same BID that it used with the home agent for a particular care-of address. For protocol simplicity, bulk registration to correspondent nodes is not supported in this document. This is because the return routability mechanism introduced in [RFC3775] cannot be easily extended to verify multiple care-of addresses stored in a single Binding Update.
Если мобильный узел хочет зарегистрировать свою привязку у корреспондентского узла, он должен выполнить операции проверки обратной маршрутизации (return routability), как описано в [RFC3775]. Это включает управление токеном Care-of Keygen для каждого care-of адреса и обмен сообщениями Care-of Test Init и Care-of Test с корреспондентским узлом для каждого care-of адреса. Мобильный узел МОЖЕТ использовать тот же BID, который он использовал с домашним агентом для данного care-of адреса. Для простоты протокола массовая регистрация у корреспондентских узлов в настоящем документе не поддерживается. Это объясняется тем, что механизм проверки обратной маршрутизации, введённый в [RFC3775], нельзя легко расширить для проверки нескольких care-of адресов, содержащихся в одном сообщении Binding Update.

If the mobile node decides to act as a regular mobile node compliant with [RFC3775], it sends a Binding Update without any Binding Identifier mobility options. The receiver of the Binding Update deletes all the bindings registered with a BID and registers only a single binding for the mobile node. Note that the mobile node can continue using the BID even if it has only a single binding that is active.
Если мобильный узел решает действовать как обычный мобильный узел, соответствующий [RFC3775], он отправляет сообщение Binding Update без каких-либо опций мобильности Binding Identifier. Получатель сообщения Binding Update удаляет все привязки, зарегистрированные с BID, и регистрирует только одну привязку для мобильного узла. Отметим, что мобильный узел может продолжать использовать BID, даже если у него имеется только одна активная привязка.
Binding cache lookup is done based on the home address and BID information if a BID is available. This is different from RFC 3775, where only the home address is used for binding cache lookup. Binding cache lookup is operated for either protocol signaling or data packets. For protocol signaling such as a Binding Update, BID should be always carried by a BID sub-option in a protocol signaling. Therefore, a correspondent binding cache that matches the specified BID MUST be found from the binding cache database. On the other hand, for the data packets, no BID information is carried in a packet. The binding cache lookup may involve policy or flow filters to retrieve a correspondent BID per packet in cases where some policy or flow filters are used to direct a certain packet or flow to a particular care-of address. However, the binding cache lookup using policy or flow filters is out of scope for this document. If no such mechanism is available and no BID is found for a packet, a node SHOULD use the binding that was last verified by receiving data packets or signaling from the mobile node. In case the binding cache lookup for data packets, using the combination of home address and BID, does not return a valid binding cache entry, the home agent SHOULD perform the lookup based on only the home address as described in [RFC3775].
Поиск в кэше привязок выполняется на основе домашнего адреса и информации BID, если BID доступен. Это отличается от RFC 3775, где для поиска в кэше привязок используется только домашний адрес. Поиск в кэше привязок выполняется как для сигнализации протокола, так и для пакетов данных. Для сигнализации протокола, такой как Binding Update, BID должен всегда переноситься подопцией BID в сигнализации протокола. Поэтому соответствующая запись кэша привязок, совпадающая с указанным BID, ДОЛЖНА быть найдена в базе данных кэша привязок. С другой стороны, в пакетах данных информация BID не переносится. Поиск в кэше привязок может включать политики или фильтры потоков для извлечения соответствующего BID для каждого пакета в случаях, когда некоторые политики или фильтры потоков используются для направления определённого пакета или потока на конкретный care-of адрес. Однако поиск в кэше привязок с использованием политик или фильтров потоков выходит за рамки настоящего документа. Если такой механизм недоступен и для пакета не найден BID, узел ДОЛЖЕН использовать привязку, которая последней была проверена путём получения пакетов данных или сигнализации от мобильного узла. В случае если поиск в кэше привязок для пакетов данных с использованием комбинации домашнего адреса и BID не возвращает допустимую запись кэша привязок, домашний агент ДОЛЖЕН выполнить поиск только по домашнему адресу, как описано в [RFC3775].
In any case, to avoid problems with upper-layer protocols and TCP in particular, a single packet flow as identified by the 5-tuple SHOULD only be sent to a single care-of address at a time.
В любом случае, чтобы избежать проблем с протоколами верхних уровней и в особенности с TCP, один поток пакетов, идентифицируемый 5-кортежем, ДОЛЖЕН отправляться только на один care-of адрес за раз.
The mobile node may return to the home link through one of its interfaces. There are two options possible for the mobile node when it returns home. Sections 5.5.1 and 5.6 describe the returning-home procedures in more detail.
Мобильный узел может вернуться на домашний канал через один из своих интерфейсов. При возвращении домой для мобильного узла возможны два варианта. Разделы 5.5.1 и 5.6 описывают процедуры возвращения домой более подробно.
1. The mobile node uses only the interface with which it attaches to the home link and takes back full ownership of its HoA (home address) on the home link. This is illustrated in Figure 2. It de-registers all bindings with the home agent related to all care-of addresses. The interfaces still attached to the visited link(s) are no longer going to be receiving any encapsulated traffic from the home agent. On the other hand, the mobile node can continue communicating with the correspondent nodes from the other interfaces attached to foreign links by using route optimization. Even if the mobile node is attached to the home link, it can still send Binding Updates for other active care-of addresses (CoA1 and CoA2) to correspondent nodes. Since the correspondent node has bindings, packets are routed from and to each care-of address directly.

5. Mobile Node Operation
5. Работа мобильного узла
5.1. Management of Care-of Address(es) and Binding Identifier(s)
5.1. Управление care-of адресами и Binding Identifier
There are two cases when a mobile node might acquire several care-of addresses. A mixture of the two cases is also possible. Note that a mobile node can use BID regardless of the number of interfaces and care-of addresses. Whether or not a mobile node uses BID is determined by a local configuration.
Существуют два случая, когда мобильный узел может получить несколько care-of адресов. Возможно и сочетание этих двух случаев. Отметим, что мобильный узел может использовать BID независимо от числа интерфейсов и care-of адресов. Использует ли мобильный узел BID, определяется локальной конфигурацией.
1. A mobile node is using several physical network interfaces and acquires a care-of address on each of its interfaces.
1. Мобильный узел использует несколько физических сетевых интерфейсов и получает care-of адрес на каждом из своих интерфейсов.
2. A mobile node uses a single physical network interface but receives advertisements for multiple prefixes on the link to which the interface is attached. This will result in the mobile node configuring several global addresses on the interface from each of the announced prefixes.
2. Мобильный узел использует один физический сетевой интерфейс, но получает объявления для нескольких префиксов в канале, к которому подключён интерфейс. Это приведёт к тому, что мобильный узел настроит на интерфейсе несколько глобальных адресов из каждого объявленного префикса.
The difference between the above two cases is only in the number of physical network interfaces and is therefore irrelevant in this document. What is of significance is the fact that the mobile node has several addresses it can use as care-of addresses.
Различие между двумя вышеуказанными случаями состоит только в числе физических сетевых интерфейсов и поэтому в настоящем документе несущественно. Существенно то, что мобильный узел имеет несколько адресов, которые он может использовать в качестве care-of адресов.
A mobile node assigns a BID to each care-of address when it wants to register them simultaneously with its home address. The BID MUST be unique for a given home address. The value is an integer between 1 and 65535. A zero value SHOULD NOT be used as a BID. If a mobile node has only one care-of address, the assignment of a BID is not needed until it has multiple care-of addresses with which to register, at which time all of the care-of addresses MUST be mapped to BIDs.
Мобильный узел назначает BID каждому care-of адресу, когда хочет зарегистрировать их одновременно со своим домашним адресом. BID ДОЛЖЕН быть уникальным для заданного домашнего адреса. Значение представляет собой целое число от 1 до 65535. Значение ноль НЕ ДОЛЖНО использоваться в качестве BID. Если мобильный узел имеет только один care-of адрес, назначение BID не требуется до тех пор, пока у него не появится несколько care-of адресов для регистрации; в этот момент все care-of адреса ДОЛЖНЫ быть сопоставлены BID.
When a mobile node registers a given BID for the first time, it MUST include the Care-of Address field in the Binding Identifier mobility option. For any subsequent registrations that either re-register or de-register the same BID, the MN need not include the Care-of Address field in the Binding Identifier mobility option.
Когда мобильный узел регистрирует заданный BID впервые, он ДОЛЖЕН включить поле Care-of Address в опцию мобильности Binding Identifier. При любых последующих регистрациях, которые либо повторно регистрируют, либо дерегистрируют тот же BID, MN может не включать поле Care-of Address в опцию мобильности Binding Identifier.

5.3. Массовая регистрация

This is very useful if the mobile node, for instance, does not want to send a lot of signaling messages through an interface where the bandwidth is scarce. Массовая регистрация — это оптимизация для привязки нескольких care-of адресов к домашнему адресу с помощью одного сообщения Binding Update. 5.4. Binding De-Registration
5.4. Дерегистрация привязки
When a mobile node decides to delete all the bindings for its home address, it sends a regular de-registration Binding Update with lifetime set to zero as defined in [RFC3775]. The Binding Identifier mobility option is not required.
Когда мобильный узел решает удалить все привязки для своего домашнего адреса, он отправляет обычное сообщение Binding Update для дерегистрации с временем жизни, установленным в ноль, как определено в [RFC3775]. Опция мобильности Binding Identifier не требуется.
If a mobile node wants to delete a particular binding(s) from its home agent and correspondent nodes, the mobile node sends a Binding Update with lifetime set to zero and includes a Binding Identifier mobility option(s) with the BID(s) it wants to de-register. The receiver will remove only the care-of address(es) that match(es) the specified BID(s). Since de-registration attempts to remove a BID that already exists, the Care-of Address field in each Binding Identifier option can be omitted by the sender as defined in Section 5.1.
Если мобильный узел хочет удалить определённую привязку (привязки) у своего домашнего агента и корреспондентских узлов, он отправляет сообщение Binding Update с временем жизни, установленным в ноль, и включает одну или несколько опций мобильности Binding Identifier с BID, которые он хочет дерегистрировать. Получатель удалит только те care-of адреса, которые соответствуют указанным BID. Поскольку дерегистрация пытается удалить уже существующий BID, поле Care-of Address в каждой опции Binding Identifier может быть опущено отправителем, как определено в разделе 5.1.
5.5. Returning Home with Complete Binding De-Registration: Using a Single Interface
5.5. Возвращение домой с полной дерегистрацией привязки: использование одного интерфейса
The mobile node may return to the home link by attaching to the home link through one of its interfaces. When the mobile node wants to return home, it should be configured with information on what interface it needs to use.
Мобильный узел может вернуться в домашний канал, подключившись к домашнему каналу через один из своих интерфейсов. Когда мобильный узел хочет вернуться домой, он должен быть настроен со сведениями о том, какой интерфейс ему нужно использовать.
5.5.1. Using Only the Interface Attached to the Home Link
5.5.1. Использование только интерфейса, подключённого к домашнему каналу
The mobile node returns home and de-registers all the bindings it has with the home agent, as shown in Figure 2 and as defined in [RFC3775]. After the de-registration step, all the packets routed by the home agent are only forwarded to the interface attached to the home link, even if there are other active interfaces attached to the visited link(s). While the mobile node de-registers all the bindings from the home agent, it may continue registering, to the correspondent node, bindings for interfaces attached to visited links as shown in Figure 2.
Мобильный узел возвращается домой и дерегистрирует все привязки, которые у него есть у домашнего агента, как показано на рисунке 2 и как определено в [RFC3775]. После этапа дерегистрации все пакеты, маршрутизируемые домашним агентом, пересылаются только на интерфейс, подключённый к домашнему каналу, даже если имеются другие активные интерфейсы, подключённые к посещаемому каналу (каналам). Хотя мобильный узел дерегистрирует все привязки у домашнего агента, он может продолжать регистрировать у корреспондентского узла привязки для интерфейсов, подключённых к посещаемым каналам, как показано на рисунке 2.
5.5.2. Using Only the Interface Attached to the Visited Link
5.5.2. Использование только интерфейса, подключённого к посещаемому каналу
The mobile node returns home physically but shuts down the interface attached to the home link. As a result, a mobile node does not return home even though it attaches to the home link by one of the interfaces. Before shutting down the interface, any binding for the care-of address previously associated with the interface should be deleted as defined in Section 5.4.
Мобильный узел физически возвращается домой, но отключает интерфейс, подключённый к домашнему каналу. В результате мобильный узел не считается вернувшимся домой, хотя он и подключается к домашнему каналу через один из интерфейсов. Перед отключением интерфейса любую привязку для care-of адреса, ранее связанного с этим интерфейсом, следует удалить, как определено в разделе 5.4.
In this scenario, despite the fact that the mobile node is connected to its home link, all of its traffic is sent and received via the home agent and its foreign links.
В этом сценарии, несмотря на то что мобильный узел подключён к своему домашнему каналу, весь его трафик отправляется и принимается через домашний агент и его зарубежные каналы.
5.6. Returning Home: Simultaneous Home and Visited Link Operation
5.6. Возвращение домой: одновременная работа с домашним и посещаемым каналами
5.6.1. Problems of Simultaneous Home and Foreign Attachments
5.6.1. Проблемы одновременного подключения к домашнему и зарубежному каналам
The mobile node returns home and continues using all the interfaces attached to both foreign and home links as shown in Figure 3.
Мобильный узел возвращается домой и продолжает использовать все интерфейсы, подключённые как к зарубежному, так и к домашнему каналам, как показано на рисунке 3.
In [RFC3775], the home agent intercepts packets meant for the mobile node using proxy Neighbor Discovery [RFC4861] while the mobile node is away from the home link. When the mobile node returns home, the home agent deletes the binding cache and stops proxying for the home address so that a mobile node can configure its home address on the interface attached to the home link. In this specification, a mobile node may return home and configure the home address on the interface attached to the home link, but still use the interfaces attached to the foreign links. In this case, a possible conflict arises when both the home agent and the mobile node try to defend the home address. If the home agent stops proxying for the home address, the packets are always routed to the interface attached to the home link and are never routed to the interfaces attached to the visited links. Deployments making use of multiple care-of addresses are required to avoid configuration conflict between the home agent and the mobile node, while still allowing the simultaneous use of home and foreign links. The following describes the mechanism for achieving this.
В [RFC3775] домашний агент перехватывает пакеты, предназначенные мобильному узлу, с помощью прокси-версии протокола Neighbor Discovery [RFC4861], пока мобильный узел находится вне домашнего канала. Когда мобильный узел возвращается домой, домашний агент удаляет кэш привязок и прекращает проксирование домашнего адреса, чтобы мобильный узел мог настроить свой домашний адрес на интерфейсе, подключённом к домашнему каналу. В настоящей спецификации мобильный узел может вернуться домой и настроить домашний адрес на интерфейсе, подключённом к домашнему каналу, но по-прежнему использовать интерфейсы, подключённые к зарубежным каналам. В этом случае возможен конфликт, когда и домашний агент, и мобильный узел пытаются защищать домашний адрес. Если домашний агент прекращает проксирование домашнего адреса, пакеты всегда направляются на интерфейс, подключённый к домашнему каналу, и никогда не направляются на интерфейсы, подключённые к посещаемым каналам. Развёртывания, использующие несколько care-of адресов, обязаны избегать конфликта конфигурации между домашним агентом и мобильным узлом, продолжая при этом допускать одновременное использование домашнего и зарубежных каналов. Далее описывается механизм достижения этого.
5.6.2. Overview and Approach
5.6.2. Обзор и подход
The home agent MUST intercept all the packets meant for the mobile node, whether or not the mobile node is attached to the home link, and decide whether to send the traffic directly to the home address on the link or tunnel to the care-of address.
Домашний агент ДОЛЖЕН перехватывать все пакеты, предназначенные мобильному узлу, независимо от того, подключён ли мобильный узел к домашнему каналу, и решать, отправлять ли трафик напрямую на домашний адрес в канале или туннелировать его на care-of адрес.
Two scenarios are illustrated in Figure 3, depending on whether or not the home agent is the only router at the home link. The difference is on who defends the home address by (Proxy) Neighbor Discovery on the home link.
На рисунке 3 показаны два сценария в зависимости от того, является ли домашний агент единственным маршрутизатором в домашнем канале. Различие состоит в том, кто защищает домашний адрес с помощью (прокси-)протокола Neighbor Discovery в домашнем канале.
1. Mobile node defends the home address by the regular Neighbor Discovery protocol (illustrated as topology-a in Figure 3). The home agent is the only router on the home link. Therefore, the home agent is capable of intercepting packets without relying on the proxy Neighbor Discovery protocol, and the mobile node can manage the neighbor cache entry of the home address on the home link as a regular IPv6 node. However, there is one limitation of this scenario. If a correspondent node is located at the home link, the home agent may not intercept the packets destined to the mobile node. These packets are routed only via the home link, but this is the most optimal path for the mobile node to communicate with nodes on the home link.
1. Мобильный узел защищает домашний адрес с помощью обычного протокола Neighbor Discovery (показано как топология-a на рисунке 3). Домашний агент является единственным маршрутизатором в домашнем канале. Поэтому домашний агент способен перехватывать пакеты, не полагаясь на прокси-протокол Neighbor Discovery, а мобильный узел может управлять записью кэша соседей для домашнего адреса в домашнем канале как обычный узел IPv6. Однако у этого сценария есть одно ограничение. Если корреспондентский узел находится в домашнем канале, домашний агент может не перехватывать пакеты, предназначенные мобильному узлу. Эти пакеты маршрутизируются только через домашний канал, но это наиболее оптимальный путь для обмена мобильного узла с узлами домашнего канала.
2. If there are routers other than the home agent on the home link, then it cannot be guaranteed that all packets meant for the mobile node are routed to the home agent. In this case, the mobile node MUST NOT operate the Neighbor Discovery protocol for the home address on the home link. This allows the home agent to keep using proxy Neighbor Discovery, and thus it keeps receiving all the packets sent to the mobile node's home address. If the home agent, according to its local policy, needs to deliver packets to the mobile node over the home link, an issue arises with respect to how the home agent discovers the mobile node's link local address. This specification uses the Mobility Header Link-Layer Address option defined in [RFC5568] in order to carry the mobile node's link-layer address in the Binding Update. Likewise, the mobile node would also know the link-layer address of the default router address to send packets from the home link without Neighbor Discovery. The link-layer address is used to transmit packets from and to the mobile node on the home link. The packets are transmitted without the Neighbor Discovery protocol by constructing the link-layer header manually. This operation is similar to Mobile IPv6 [RFC3775] when a mobile node sends a de-registration Binding Update to the home agent's link- layer address in the operation for returning home.
2. Если в домашнем канале имеются маршрутизаторы, отличные от домашнего агента, то нельзя гарантировать, что все пакеты, предназначенные мобильному узлу, будут направлены домашнему агенту. В этом случае мобильный узел НЕ ДОЛЖЕН работать по протоколу Neighbor Discovery для домашнего адреса в домашнем канале. Это позволяет домашнему агенту продолжать использовать прокси-протокол Neighbor Discovery и, следовательно, продолжать получать все пакеты, отправленные на домашний адрес мобильного узла. Если домашнему агенту согласно его локальной политике нужно доставлять пакеты мобильному узлу через домашний канал, возникает вопрос о том, как домашний агент обнаруживает локальный адрес канального уровня мобильного узла. В настоящей спецификации используется опция Mobility Header Link-Layer Address, определённая в [RFC5568], чтобы переносить адрес канального уровня мобильного узла в сообщении Binding Update. Аналогично мобильный узел также узнаёт адрес канального уровня адреса маршрутизатора по умолчанию, чтобы отправлять пакеты из домашнего канала без протокола Neighbor Discovery. Адрес канального уровня используется для передачи пакетов от мобильного узла и к нему в домашнем канале. Пакеты передаются без протокола Neighbor Discovery путём ручного формирования заголовка канального уровня. Эта операция аналогична операции Mobile IPv6 [RFC3775], когда мобильный узел отправляет сообщение Binding Update для дерегистрации на адрес канального уровня домашнего агента в рамках процедуры возвращения домой.
5.6.3. Home Binding Support
5.6.3. Поддержка домашней привязки
When the home binding is used, the mobile node MUST send a registering Binding Update with a Binding Identifier mobility option with the 'H' flag set. The lifetime MUST be set to a non-zero lifetime of the home binding, and the Care-of Address field MUST be set to the home address. The mobile node registers only one home binding at a time, even if it attaches to the home link by multiple interfaces.
Когда используется домашняя привязка, мобильный узел ДОЛЖЕН отправить регистрирующее сообщение Binding Update с опцией мобильности Binding Identifier и установленным флагом 'H'. Время жизни ДОЛЖНО быть установлено ненулевым временем жизни домашней привязки, а поле Care-of Address ДОЛЖНО быть установлено равным домашнему адресу. Мобильный узел регистрирует только одну домашнюю привязку одновременно, даже если он подключается к домашнему каналу через несколько интерфейсов.
The mobile node SHOULD include the Mobility Header Link-Layer Address option [RFC5568] to notify the mobile node's link-layer address to the home agent, too. The option code of the Mobility Header Link- Layer Address option MUST be set to '2' (link-layer address of the mobile node). This link-layer address is required for the home agent to send the Binding Acknowledgement and to forward the mobile node's packet.
Мобильный узел ДОЛЖЕН также включить опцию Mobility Header Link-Layer Address [RFC5568], чтобы сообщить домашнему агенту адрес канального уровня мобильного узла. Код опции Mobility Header Link-Layer Address ДОЛЖЕН быть установлен в '2' (адрес канального уровня мобильного узла). Этот адрес канального уровня необходим домашнему агенту для отправки сообщения Binding Acknowledgement и пересылки пакетов мобильного узла.
According to [RFC3775], the mobile node MUST start responding to Neighbor Solicitation for its home address right after it sends the de-registration Binding Update to the home agent. However, in this specification, the mobile node MUST NOT respond to Neighbor Solicitation before receiving a Binding Acknowledgement, since the home agent may continue proxying for the home address. If the mobile node receives [MCOA RETURNHOME WO/NDP (5)] status value in the received Binding Acknowledgment, it MUST NOT respond to Neighbor Solicitation even after the Binding Acknowledgement.
Согласно [RFC3775] мобильный узел ДОЛЖЕН начать отвечать на сообщения Neighbor Solicitation для своего домашнего адреса сразу после отправки домашнему агенту сообщения Binding Update для дерегистрации. Однако в настоящей спецификации мобильный узел НЕ ДОЛЖЕН отвечать на сообщения Neighbor Solicitation до получения сообщения Binding Acknowledgement, поскольку домашний агент может продолжать проксирование домашнего адреса. Если мобильный узел получает в полученном сообщении Binding Acknowledgement значение статуса [MCOA RETURNHOME WO/NDP (5)], он НЕ ДОЛЖЕН отвечать на сообщения Neighbor Solicitation даже после получения сообщения Binding Acknowledgement.
The management of the home binding is the same as the binding management described in this specification. The home binding can be included in a bulk binding registration (Section 5.3). The MN SHOULD refresh the lifetime of the home binding by sending appropriate Binding Updates as with any other binding.
Управление домашней привязкой такое же, как управление привязками, описанное в настоящей спецификации. Домашняя привязка может быть включена в массовую регистрацию привязок (раздел 5.3). MN ДОЛЖЕН обновлять время жизни домашней привязки, отправляя соответствующие сообщения Binding Update, как и для любой другой привязки.
5.6.4. Sending Packets from the Home Link
5.6.4. Отправка пакетов из домашнего канала
o When the mobile node receives the Binding Acknowledgement with the status value 'Binding Update Accepted' and the BID option, it can configure its home address to the interface attached to the home link and start operating Neighbor Discovery for the home address on the home link. Packets can be transmitted from and to the mobile node as if the mobile node were a regular IPv6 node.
o Когда мобильный узел получает сообщение Binding Acknowledgement со значением статуса 'Binding Update Accepted' и опцией BID, он может настроить свой домашний адрес на интерфейсе, подключённом к домашнему каналу, и начать работу протокола Neighbor Discovery для домашнего адреса в домашнем канале. Пакеты могут передаваться от мобильного узла и к нему так, как если бы мобильный узел был обычным узлом IPv6.
o If the mobile node receives the status [MCOA RETURNHOME WO/NDP] in the Binding Acknowledgement, it MUST NOT operate Neighbor Discovery for the home address. When the mobile node sends packets from the interface attached to the home link, it MUST learn the link-layer address of the next hop (i.e., default router of the mobile node). A mobile node learns the default router's link-layer address from a Source Link-Layer Address option in Router Advertisements. The mobile node sends packets directly to the default router's link-layer address. This is done by constructing the packet to include a link-layer header with the learned link-layer address of the default router. The home agent also forwards the packet to the mobile node on the home link by using the mobile node's link-layer address. The link-layer address SHOULD be cached when the home agent receives the de-registration Binding Update message. Note that the default router MUST NOT cache the mobile node's link-layer address in the neighbor cache when it forwards the packet from the mobile node to the home agent.
o Если мобильный узел получает в сообщении Binding Acknowledgement статус [MCOA RETURNHOME WO/NDP], он НЕ ДОЛЖЕН работать по протоколу Neighbor Discovery для домашнего адреса. Когда мобильный узел отправляет пакеты с интерфейса, подключённого к домашнему каналу, он ДОЛЖЕН узнать адрес канального уровня следующего перехода (то есть маршрутизатора по умолчанию для мобильного узла). Мобильный узел узнаёт адрес канального уровня маршрутизатора по умолчанию из опции Source Link-Layer Address в сообщениях Router Advertisement. Мобильный узел отправляет пакеты непосредственно на адрес канального уровня маршрутизатора по умолчанию. Это делается путём формирования пакета с заголовком канального уровня, содержащим изученный адрес канального уровня маршрутизатора по умолчанию. Домашний агент также пересылает пакет мобильному узлу в домашнем канале, используя адрес канального уровня мобильного узла. Адрес канального уровня ДОЛЖЕН кэшироваться, когда домашний агент получает сообщение Binding Update для дерегистрации. Отметим, что маршрутизатор по умолчанию НЕ ДОЛЖЕН кэшировать адрес канального уровня мобильного узла в кэше соседей, когда он пересылает пакет от мобильного узла домашнему агенту.
5.6.5. Leaving from the Home Link
5.6.5. Уход из домашнего канала
When the mobile node detaches from the home link, it SHOULD immediately send a Binding Update for one of the active care-of addresses with the 'H' flag unset. When the 'H' flag of the BID option is unset in any Binding Update, the home agent stops forwarding the mobile node's packets to the home link.
Когда мобильный узел отсоединяется от домашнего канала, он ДОЛЖЕН немедленно отправить сообщение Binding Update для одного из активных care-of адресов с снятым флагом 'H'. Когда флаг 'H' опции BID снят в любом сообщении Binding Update, домашний агент прекращает пересылку пакетов мобильного узла в домашний канал.
5.7. Receiving Binding Acknowledgement
5.7. Получение Binding Acknowledgement
The verification of a Binding Acknowledgement is the same as Mobile IPv6 (Section 11.7.3 of [RFC3775]). The operation for sending a Binding Acknowledgement is described in Section 6.2.
Проверка сообщения Binding Acknowledgement выполняется так же, как в Mobile IPv6 (раздел 11.7.3 в [RFC3775]). Операция отправки сообщения Binding Acknowledgement описана в разделе 6.2.
If a mobile node includes a Binding Identifier mobility option in a Binding Update with the 'A' flag set, a Binding Acknowledgement SHOULD carry a Binding Identifier mobility option. According to [RFC3775], the receiver of the Binding Update ignores unknown mobility options and processes the Binding Update without the unknown mobility option. Therefore, if no such mobility option is included in the Binding Acknowledgement in response to a Binding Update for a multiple care-of addresses registration, this indicates that the originating node of the Binding Acknowledgement does not support processing the Binding Identifier mobility option regardless of status value. In such case, the receiver of the Binding Update may create a regular binding. The mobile node then SHOULD no longer attempt a multiple care-of addresses registration with that node. If this occurs with home registration, the mobile node MAY attempt to discover another home agent that supports the Binding Identifier mobility option for the home registration.
Если мобильный узел включает опцию мобильности Binding Identifier в сообщение Binding Update с установленным флагом 'A', сообщение Binding Acknowledgement ДОЛЖНО содержать опцию мобильности Binding Identifier. Согласно [RFC3775] получатель сообщения Binding Update игнорирует неизвестные опции мобильности и обрабатывает сообщение Binding Update без неизвестной опции мобильности. Поэтому если в ответ на сообщение Binding Update для регистрации нескольких care-of адресов в сообщении Binding Acknowledgement не включена такая опция мобильности, это означает, что узел-отправитель сообщения Binding Acknowledgement не поддерживает обработку опции мобильности Binding Identifier независимо от значения статуса. В таком случае получатель сообщения Binding Update может создать обычную привязку. После этого мобильному узлу НЕ СЛЕДУЕТ больше пытаться выполнить регистрацию нескольких care-of адресов с этим узлом. Если это происходит при домашней регистрации, мобильный узел МОЖЕТ попытаться обнаружить другого домашнего агента, поддерживающего опцию мобильности Binding Identifier для домашней регистрации.
If a Binding Identifier mobility option is present in the received Binding Acknowledgement, the mobile node checks the Status field in the option. If the status value in the Binding Identifier mobility option is zero, the mobile node uses the value in the Status field of the Binding Acknowledgement. Otherwise, it uses the value in the Status field of the Binding Identifier mobility option.
Если в полученном сообщении Binding Acknowledgement присутствует опция мобильности Binding Identifier, мобильный узел проверяет поле Status в этой опции. Если значение статуса в опции мобильности Binding Identifier равно нулю, мобильный узел использует значение поля Status сообщения Binding Acknowledgement. В противном случае он использует значение поля Status опции мобильности Binding Identifier.
If the status code is greater than or equal to 128, the mobile node starts relevant operations according to the error code. Otherwise, the mobile node assumes that the originator (home agent or correspondent node) successfully registered the binding information and BID for the mobile node.
Если код статуса больше или равен 128, мобильный узел запускает соответствующие операции в соответствии с кодом ошибки. В противном случае мобильный узел предполагает, что отправитель (домашний агент или корреспондентский узел) успешно зарегистрировал информацию привязки и BID для мобильного узла.
o If the status value is [MCOA PROHIBITED], the mobile node MUST stop registering multiple bindings with the node that sent the Binding Acknowledgement.
o Если значением статуса является [MCOA PROHIBITED], мобильный узел ДОЛЖЕН прекратить регистрацию нескольких привязок у узла, отправившего сообщение Binding Acknowledgement.
o If the status value is [MCOA BULK REGISTRATION PROHIBITED], the mobile node needs to stop using bulk registrations with the node that sent the Binding Acknowledgement. It should assume that none of the attempted registrations were successful.
o Если значением статуса является [MCOA BULK REGISTRATION PROHIBITED], мобильному узлу необходимо прекратить использование массовых регистраций у узла, отправившего сообщение Binding Acknowledgement. Ему следует предполагать, что ни одна из предпринятых регистраций не была успешной.
o If [MCOA MALFORMED] is specified, it indicates that the Binding Identifier mobility option is formatted wrong, presumably due to a programming error or major packet corruption.
o Если указано [MCOA MALFORMED], это означает, что опция мобильности Binding Identifier имеет неверный формат, вероятно, из-за ошибки программирования или серьёзного повреждения пакета.
o If [MCOA NON-MCOA BINDING EXISTS] is specified, it means that there is a non-MCoA binding entry in the receiver. The mobile node MUST set 'O' flag so that all the registered bindings are replaced by an MCoA registration as described in Section 5.9.
o Если указано [MCOA NON-MCOA BINDING EXISTS], это означает, что у получателя имеется запись привязки, не относящаяся к MCoA. Мобильный узел ДОЛЖЕН установить флаг 'O', чтобы все зарегистрированные привязки были заменены регистрацией MCoA, как описано в разделе 5.9.
o If [MCOA UNKNOWN COA] is specified, it means that the mobile node sent a Binding Identifier mobility option without a Care-of Address field, but the receiver could not find an entry for the BID indicated. If the mobile node is trying to de-register a BID, it need not do anything further. If the mobile node is trying to refresh a binding, it SHOULD send a Binding Identifier mobility option including the Care-of Address field.
o Если указано [MCOA UNKNOWN COA], это означает, что мобильный узел отправил опцию мобильности Binding Identifier без поля Care-of Address, но получатель не смог найти запись для указанного BID. Если мобильный узел пытается дерегистрировать BID, ему не нужно предпринимать дальнейших действий. Если мобильный узел пытается обновить привязку, ему СЛЕДУЕТ отправить опцию мобильности Binding Identifier, включающую поле Care-of Address.
5.8. Receiving Binding Refresh Request
5.8. Получение Binding Refresh Request
The verification of a Binding Refresh Request is the same as in Mobile IPv6 (Section 11.7.4 of [RFC3775]). The operation of sending a Binding Refresh Request is described in Section 6.4.
Проверка сообщения Binding Refresh Request выполняется так же, как в Mobile IPv6 (раздел 11.7.4 в [RFC3775]). Операция отправки сообщения Binding Refresh Request описана в разделе 6.4.
If a mobile node receives a Binding Refresh Request with a Binding Identifier mobility option, it indicates that the node sending the Binding Refresh Request message is requesting that the mobile node send a new Binding Update for the BID. The mobile node SHOULD then send a Binding Update at least for the respective binding, as described in Sections 5.2 and 5.3.
Если мобильный узел получает сообщение Binding Refresh Request с опцией мобильности Binding Identifier, это означает, что узел, отправляющий сообщение Binding Refresh Request, требует, чтобы мобильный узел отправил новое сообщение Binding Update для этого BID. Мобильный узел ДОЛЖЕН затем отправить сообщение Binding Update как минимум для соответствующей привязки, как описано в разделах 5.2 и 5.3.
5.9. Bootstrapping
5.9. Начальная загрузка
When a mobile node bootstraps and registers multiple bindings for the first time, it MUST set the 'O' flag in the Binding Update message. If old bindings still exist at the home agent, the mobile node has no knowledge of which bindings still exist at the home agent. This scenario happens when a mobile node reboots and loses state regarding the registrations. If the 'O' flag is set, all the bindings are replaced by the new binding(s).
Когда мобильный узел выполняет начальную загрузку и впервые регистрирует несколько привязок, он ДОЛЖЕН установить флаг 'O' в сообщении Binding Update. Если у домашнего агента всё ещё существуют старые привязки, мобильный узел не знает, какие привязки ещё существуют у домашнего агента. Этот сценарий возникает, когда мобильный узел перезагружается и теряет состояние регистраций. Если флаг 'O' установлен, все привязки заменяются новой привязкой (новыми привязками).
6. Home Agent and Correspondent Node Operation
6. Работа домашнего агента и корреспондентского узла
6.1. Searching Binding Cache with Binding Identifier
6.1. Поиск в кэше привязок по Binding Identifier
A node that is either a correspondent node or a home agent SHOULD use both the home address and the BID as the search key of the binding cache if it knows the corresponding BID (for example, when processing signaling messages). In the example below, if a node searches the binding with the home address and BID2, it gets binding2 for this mobile node.
Узел, являющийся корреспондентским узлом или домашним агентом, ДОЛЖЕН использовать как домашний адрес, так и BID в качестве ключа поиска в кэше привязок, если он знает соответствующий BID (например, при обработке сообщений сигнализации). В приведённом ниже примере, если узел ищет привязку по домашнему адресу и BID2, он получает binding2 для этого мобильного узла.

The node learns the BID when it receives a Binding Identifier mobility option. At that time, the node MUST look up its binding cache database with the home address and the BID retrieved from the Binding Update. If the node does not know the BID, it searches for a binding with only the home address. In such a case, the first matched binding is found. If the node does not desire to use multiple bindings for a mobile node, it can simply ignore the BID.
Узел узнаёт BID, когда получает опцию мобильности Binding Identifier. В этот момент узел ДОЛЖЕН выполнить поиск в своей базе данных кэша привязок по домашнему адресу и BID, извлечённым из сообщения Binding Update. Если узел не знает BID, он ищет привязку только по домашнему адресу. В таком случае находится первая совпавшая привязка. Если узел не желает использовать несколько привязок для мобильного узла, он может просто игнорировать BID.
6.2. Processing Binding Update
6.2. Обработка Binding Update
If a Binding Update does not contain a Binding Identifier mobility option, its processing is the same as in [RFC3775]. If the receiver already has multiple bindings for the home address, it MUST replace all the existing bindings with the received binding. If the [RFC3775] Binding Update is for de-registration, the receiver MUST delete all existing bindings from its binding cache.
Если сообщение Binding Update не содержит опции мобильности Binding Identifier, его обработка выполняется так же, как в [RFC3775]. Если у получателя уже есть несколько привязок для домашнего адреса, он ДОЛЖЕН заменить все существующие привязки полученной привязкой. Если сообщение Binding Update [RFC3775] предназначено для дерегистрации, получатель ДОЛЖЕН удалить все существующие привязки из своего кэша привязок.
If the Binding Update contains Binding Identifier mobility option(s), it is first validated according to Section 9.5.1 of [RFC3775]. Then the receiver processes the Binding Identifier mobility option(s) as described in the following steps.
Если сообщение Binding Update содержит одну или несколько опций мобильности Binding Identifier, оно сначала проверяется согласно разделу 9.5.1 в [RFC3775]. Затем получатель обрабатывает опции мобильности Binding Identifier, как описано в следующих шагах.
o The length value is examined. The length value MUST be either 4, 8, or 20 depending on the Care-of Address field. If the length is incorrect, the receiver MUST reject the Binding Update and return the status value set to [MCOA MALFORMED].
o Проверяется значение длины. Значение длины ДОЛЖНО быть равно 4, 8 или 20 в зависимости от поля Care-of Address. Если длина неверна, получатель ДОЛЖЕН отклонить сообщение Binding Update и вернуть значение статуса, установленное в [MCOA MALFORMED].
o When the length value is either 8 or 20, the care-of address MUST be present in the Binding Identifier mobility option. If the unicast routable address [RFC3775] is not present in the Care-of Address field, the receiver MUST reject the Binding Identifier mobility option and return the status value set to [MCOA MALFORMED].
o Когда значение длины равно 8 или 20, care-of адрес ДОЛЖЕН присутствовать в опции мобильности Binding Identifier. Если одноадресный маршрутизируемый адрес [RFC3775] не присутствует в поле Care-of Address, получатель ДОЛЖЕН отклонить опцию мобильности Binding Identifier и вернуть значение статуса, установленное в [MCOA MALFORMED].
o When multiple Binding Identifier mobility options are present in the Binding Update, it is treated as bulk registration. If the receiving node is a correspondent node, it MUST reject the Binding Update and return the status value set to [MCOA BULK REGISTRATION PROHIBITED] in the binding Acknowledgement.
o Когда в сообщении Binding Update присутствуют несколько опций мобильности Binding Identifier, это рассматривается как массовая регистрация. Если принимающий узел является корреспондентским узлом, он ДОЛЖЕН отклонить сообщение Binding Update и вернуть в сообщении Binding Acknowledgement значение статуса, установленное в [MCOA BULK REGISTRATION PROHIBITED].
o If the Lifetime field in the Binding Update is set to zero, the receiving node deletes the binding entry that corresponds to the BID in the Binding Identifier mobility option. If the receiving node does not have an appropriate binding for the BID, it MUST reject the Binding Update and send a Binding Acknowledgement with status set to 133 [not home agent for this mobile node].
o Если поле Lifetime в сообщении Binding Update установлено в ноль, принимающий узел удаляет запись привязки, соответствующую BID в опции мобильности Binding Identifier. Если у принимающего узла нет подходящей привязки для BID, он ДОЛЖЕН отклонить сообщение Binding Update и отправить сообщение Binding Acknowledgement со статусом 133 [not home agent for this mobile node].
o If the 'O' flag is set in the de-registering Binding Update, it is ignored. If the 'H' flag is set, the home agent stores a home address in the Care-of Address field of the binding cache entry. The home agent MUST follow the descriptions described in Section 5.6.
o Если флаг 'O' установлен в дерегистрирующем сообщении Binding Update, он игнорируется. Если установлен флаг 'H', домашний агент сохраняет домашний адрес в поле Care-of Address записи кэша привязок. Домашний агент ДОЛЖЕН следовать описаниям, приведённым в разделе 5.6.
o If the Lifetime field is not set to zero, the receiving node registers a binding with the specified BID as a mobile node's binding. The care-of address is obtained from the Binding Update packet as follows:
o Если поле Lifetime не установлено в ноль, принимающий узел регистрирует привязку с указанным BID в качестве привязки мобильного узла. Care-of адрес получается из пакета Binding Update следующим образом:
* If the length value of the Binding Identifier mobility option is 20, the care-of address is the IPv6 address copied from the Care-of Address field in the Binding Identifier mobility option.
* Если значение длины опции мобильности Binding Identifier равно 20, care-of адресом является адрес IPv6, скопированный из поля Care-of Address опции мобильности Binding Identifier.
* When the length value is 8, the address MUST be the IPv4 valid address. How to obtain an IPv4 care-of address is described in Section 8.
* Когда значение длины равно 8, адрес ДОЛЖЕН быть допустимым адресом IPv4. То, как получить care-of адрес IPv4, описано в разделе 8.
* When the length value is 4 and the Binding Identifier is present in the binding cache, the receiving node MUST update the associated binding entry. Otherwise, the receiving node MUST reject that Binding Identifier mobility option and send a Binding Acknowledgement with the status for that Binding Identifier mobility option set to [MCOA UNKNOWN].
* Когда значение длины равно 4 и Binding Identifier присутствует в кэше привязок, принимающий узел ДОЛЖЕН обновить соответствующую запись привязки. В противном случае принимающий узел ДОЛЖЕН отклонить эту опцию мобильности Binding Identifier и отправить сообщение Binding Acknowledgement со статусом для этой опции мобильности Binding Identifier, установленным в [MCOA UNKNOWN].
o Once the care-of address(es) have been retrieved from the Binding Update, the receiving nodes create new binding(s).
o После того как care-of адрес (адреса) извлечён из сообщения Binding Update, принимающие узлы создают новую привязку (новые привязки).
* If the 'O' flag is set in the Binding Update, the receiving node removes all the existing bindings and registers the received binding(s).
* Если флаг 'O' установлен в сообщении Binding Update, принимающий узел удаляет все существующие привязки и регистрирует полученную привязку (полученные привязки).
* If the 'O' flag is unset in the Binding Update and the receiver has a regular binding that does not have a BID for the mobile node, it must not process the Binding Update. The receiver should send a Binding Acknowledgement with status set to [MCOA NON-MCOA BINDING EXISTS].
* Если флаг 'O' не установлен в сообщении Binding Update и у получателя есть обычная привязка без BID для мобильного узла, он не должен обрабатывать сообщение Binding Update. Получателю следует отправить сообщение Binding Acknowledgement со статусом, установленным в [MCOA NON-MCOA BINDING EXISTS].
* If the receiver already has a binding with the same BID but different care-of address, it MUST update the binding and respond with a Binding Acknowledgement with status set to 0 [Binding Update accepted].
* Если у получателя уже есть привязка с тем же BID, но другим care-of адресом, он ДОЛЖЕН обновить привязку и ответить сообщением Binding Acknowledgement со статусом, установленным в 0 [Binding Update accepted].
* If the receiver does not have a binding entry for the BID, it registers a new binding for the BID and responds with a Binding Acknowledgement with status set to 0 [Binding Update accepted].
* Если у получателя нет записи привязки для BID, он регистрирует новую привязку для BID и отвечает сообщением Binding Acknowledgement со статусом, установленным в 0 [Binding Update accepted].
If all the above operations are successfully completed and the 'A' flag is set in the Binding Update, a Binding Acknowledgement containing the Binding Identifier mobility options MUST be sent to the mobile node. Whenever a Binding Acknowledgement is sent, all the Binding Identifier mobility options stored in the Binding Update MUST be copied to the Binding Acknowledgement except the Status field. The Care-of Address field in each Binding Identifier mobility option, however, MAY be omitted, because the mobile node can match a corresponding Binding Update List entry using the BID.
Если все вышеуказанные операции успешно завершены и в сообщении Binding Update установлен флаг 'A', мобильному узлу ДОЛЖНО быть отправлено сообщение Binding Acknowledgement, содержащее опции мобильности Binding Identifier. Всякий раз при отправке сообщения Binding Acknowledgement все опции мобильности Binding Identifier, сохранённые в сообщении Binding Update, ДОЛЖНЫ быть скопированы в сообщение Binding Acknowledgement, за исключением поля Status. Однако поле Care-of Address в каждой опции мобильности Binding Identifier МОЖЕТ быть опущено, поскольку мобильный узел может сопоставить соответствующую запись Binding Update List с помощью BID.
When a correspondent node sends a Binding Acknowledgement, the status value MUST always be stored in the Status field of the Binding Acknowledgement and the Status field of the Binding Identifier mobility option MUST always be set to zero.
Когда корреспондентский узел отправляет сообщение Binding Acknowledgement, значение статуса ДОЛЖНО всегда сохраняться в поле Status сообщения Binding Acknowledgement, а поле Status опции мобильности Binding Identifier ДОЛЖНО всегда устанавливаться в ноль.
When the home agent sends a Binding Acknowledgement, the status value can be stored in the Status field of either a Binding Acknowledgement or a Binding Identifier mobility option. If the status value is specific to one of the bindings in the bulk registration, the status value MUST be stored in the Status field in the corresponding Binding Identifier mobility option. In this case, the Status field of the Binding Acknowledgement MUST be set to [MCOA NOTCOMPLETE], so that the receiver can examine the Status field of each Binding Identifier mobility option for further operations. Otherwise, the Status field of the Binding Identifier mobility option MUST be set to zero and the home agent Status field of the Binding Acknowledgement is used.
Когда домашний агент отправляет сообщение Binding Acknowledgement, значение статуса может сохраняться в поле Status либо сообщения Binding Acknowledgement, либо опции мобильности Binding Identifier. Если значение статуса относится к одной из привязок в массовой регистрации, значение статуса ДОЛЖНО сохраняться в поле Status соответствующей опции мобильности Binding Identifier. В этом случае поле Status сообщения Binding Acknowledgement ДОЛЖНО быть установлено в [MCOA NOTCOMPLETE], чтобы получатель мог проверить поле Status каждой опции мобильности Binding Identifier для дальнейших операций. В противном случае поле Status опции мобильности Binding Identifier ДОЛЖНО быть установлено в ноль и используется поле Status домашнего агента в сообщении Binding Acknowledgement.
6.3. Sending a Binding Acknowledgement for Home Link Registration
6.3. Отправка Binding Acknowledgement для регистрации в домашнем канале
The operations described in this section are related to returning home with simultaneous use of home and foreign links.
Описанные в этом разделе операции относятся к возвращению домой при одновременном использовании домашнего и зарубежных каналов.
o When the home agent sends the Binding Acknowledgement after successfully processing the home binding registration, it MUST set the status value to either 0 [Binding Update Accepted] or [MCOA RETURNHOME WO/NDP (5)] in the Status field of the Binding Acknowledgment, depending on home agent configuration at the home link. The new values are:
o Когда домашний агент отправляет сообщение Binding Acknowledgement после успешной обработки регистрации домашней привязки, он ДОЛЖЕН установить в поле Status сообщения Binding Acknowledgement значение 0 [Binding Update Accepted] или [MCOA RETURNHOME WO/NDP (5)] в зависимости от конфигурации домашнего агента в домашнем канале. Новые значения:
* Binding Update Accepted (0): The Neighbor Discovery protocol is permitted for the home address at the home link. This is the regular returning home operation of [RFC3775].
* Binding Update Accepted (0): протокол Neighbor Discovery разрешён для домашнего адреса в домашнем канале. Это обычная операция возвращения домой из [RFC3775].
* MCOA RETURNHOME WO/NDP (5): The Neighbor Discovery protocol is prohibited for the home address at the home link.
* MCOA RETURNHOME WO/NDP (5): протокол Neighbor Discovery запрещён для домашнего адреса в домашнем канале.
The respective Binding Identifier mobility options need to be included in the Binding Acknowledgement.
Соответствующие опции мобильности Binding Identifier необходимо включить в сообщение Binding Acknowledgement.
o If the Binding Update is rejected, the appropriate error value MUST be set in the Status field. In this case, the home agent operation is the same as in [RFC3775].
o Если сообщение Binding Update отклонено, в поле Status ДОЛЖНО быть установлено соответствующее значение ошибки. В этом случае работа домашнего агента такая же, как в [RFC3775].
o Only if the home agent is the only router in the home link MAY it turn off Neighbor Discovery for the requested home address and respond with the [Binding Update Accepted] status value to the mobile node. Since the mobile node will not reply to Neighbor Solicitation for the home address before receiving the Binding Acknowledgement, the home agent SHOULD use the link-layer address carried by the Mobility Header Link-Layer Address option [RFC5568] in the received Binding Update. After the completion of the home binding registration, the mobile node starts regular Neighbor Discovery operations for the home address on the home link. The neighbor cache entry for the home address is created by the regular exchange of Neighbor Solicitation and Neighbor Advertisement.
o Только если домашний агент является единственным маршрутизатором в домашнем канале, он МОЖЕТ отключить протокол Neighbor Discovery для запрошенного домашнего адреса и ответить мобильному узлу значением статуса [Binding Update Accepted]. Поскольку мобильный узел не будет отвечать на сообщения Neighbor Solicitation для домашнего адреса до получения сообщения Binding Acknowledgement, домашний агент ДОЛЖЕН использовать адрес канального уровня, переносимый опцией Mobility Header Link-Layer Address [RFC5568], в полученном сообщении Binding Update. После завершения регистрации домашней привязки мобильный узел начинает обычные операции протокола Neighbor Discovery для домашнего адреса в домашнем канале. Запись кэша соседей для домашнего адреса создаётся путём обычного обмена сообщениями Neighbor Solicitation и Neighbor Advertisement.
o If the home agent is not the only router in the home link, the home agent returns [MCOA RETURNHOME WO/NDP] value in the Status field of the Binding Identifier mobility option. The home agent learns the mobile node's link-layer address by receiving the Mobility Header Link-Layer Address option carried by the Binding Update. It stores the link-layer address as a neighbor cache entry for the mobile node so that it can send the packets to the mobile node's link-layer address.
o Если домашний агент не является единственным маршрутизатором в домашнем канале, он возвращает значение [MCOA RETURNHOME WO/NDP] в поле Status опции мобильности Binding Identifier. Домашний агент узнаёт адрес канального уровня мобильного узла, получая опцию Mobility Header Link-Layer Address, переносимую в сообщении Binding Update. Он сохраняет адрес канального уровня как запись кэша соседей для мобильного узла, чтобы иметь возможность отправлять пакеты на адрес канального уровня мобильного узла.
o Note that the use of proxy Neighbor Discovery is an easier way to intercept the mobile nodes' packets instead of IP routing in some deployment scenarios. Therefore, even if a home agent is the only router, it is an implementation and operational choice whether the home agent returns [Binding Update Accepted] or [MCOA RETURNHOME WO/NDP].
o Отметим, что использование прокси-протокола Neighbor Discovery в некоторых сценариях развёртывания является более простым способом перехвата пакетов мобильных узлов, чем IP-маршрутизация. Поэтому, даже если домашний агент является единственным маршрутизатором, выбор того, возвращает ли домашний агент [Binding Update Accepted] или [MCOA RETURNHOME WO/NDP], остаётся вопросом реализации и эксплуатации.
o If the BID option is not included in the Binding Acknowledgement, the home agent might not recognize the home registration. The home agent might have processed the home registration Binding Update as a regular de-registration, as described in [RFC3775], and deleted all the registered binding cache entries for the mobile node. Thus, the mobile node SHOULD stop using the interface attached to the foreign link and use only the interface attached to the home link.
o Если опция BID не включена в сообщение Binding Acknowledgement, домашний агент может не распознать домашнюю регистрацию. Домашний агент мог обработать сообщение Binding Update для домашней регистрации как обычную дерегистрацию, как описано в [RFC3775], и удалить все зарегистрированные записи кэша привязок для мобильного узла. Поэтому мобильному узлу СЛЕДУЕТ прекратить использование интерфейса, подключённого к зарубежному каналу, и использовать только интерфейс, подключённый к домашнему каналу.
6.4. Sending Binding Refresh Request
6.4. Отправка Binding Refresh Request
When a node (home agent or correspondent node) sends a Binding Refresh Request for a particular binding created with the BID, the node SHOULD include the Binding Identifier mobility option in the Binding Refresh Request. The node MAY include multiple Binding Identifier mobility options if there are multiple bindings that need to be refreshed.
Когда узел (домашний агент или корреспондентский узел) отправляет сообщение Binding Refresh Request для конкретной привязки, созданной с помощью BID, узел ДОЛЖЕН включить опцию мобильности Binding Identifier в сообщение Binding Refresh Request. Узел МОЖЕТ включить несколько опций мобильности Binding Identifier, если имеется несколько привязок, которые нужно обновить.
6.5. Receiving Packets from Mobile Node
6.5. Получение пакетов от мобильного узла
When a node receives packets with a Home Address destination option from a mobile node, it MUST check that the care-of address that appears in the Source Address field of the IPv6 header is equal to one of the care-of addresses in the binding cache entry. If no binding is found, the packets MUST be discarded. The node MUST also send a Binding Error message as specified in [RFC3775]. This verification MUST NOT be done for a Binding Update.
Когда узел получает от мобильного узла пакеты с опцией назначения Home Address, он ДОЛЖЕН проверить, что care-of адрес, указанный в поле Source Address заголовка IPv6, равен одному из care-of адресов в записи кэша привязок. Если привязка не найдена, пакеты ДОЛЖНЫ быть отброшены. Узел ДОЛЖЕН также отправить сообщение Binding Error, как указано в [RFC3775]. Эта проверка НЕ ДОЛЖНА выполняться для сообщения Binding Update.
7. Network Mobility Applicability
7. Применимость к Network Mobility
The binding management mechanisms are the same for a mobile host that uses Mobile IPv6 and for a mobile router that is using the NEMO Basic Support protocol [RFC3963]. Therefore, the extensions described in this document can also be used to support a mobile router with multiple care-of addresses. [RFC4980] contains an analysis of NEMO multihoming.
Механизмы управления привязками одинаковы для мобильного узла, использующего Mobile IPv6, и для мобильного маршрутизатора, использующего протокол базовой поддержки NEMO [RFC3963]. Поэтому описанные в настоящем документе расширения также могут использоваться для поддержки мобильного маршрутизатора с несколькими care-of адресами. В [RFC4980] содержится анализ мультихоуминга NEMO.
8. DSMIPv6 Applicability
8. Применимость к DSMIPv6
Dual Stack Mobile IPv6 (DSMIPv6) [RFC5555] extends Mobile IPv6 to register an IPv4 care-of address instead of the IPv6 care-of address when the mobile node is attached to an IPv4-only access network. It also allows the mobile node to acquire an IPv4 home address in addition to an IPv6 home address for use with IPv4-only correspondent nodes. This section describes how the multiple care-of addresses registration works with IPv4 care-of and home addresses.
Dual Stack Mobile IPv6 (DSMIPv6) [RFC5555] расширяет Mobile IPv6, позволяя регистрировать care-of адрес IPv4 вместо care-of адреса IPv6, когда мобильный узел подключён к сети доступа, поддерживающей только IPv4. Он также позволяет мобильному узлу получить домашний адрес IPv4 в дополнение к домашнему адресу IPv6 для использования с корреспондентскими узлами, поддерживающими только IPv4. В этом разделе описывается, как регистрация нескольких care-of адресов работает с care-of адресами и домашними адресами IPv4.
8.1. IPv4 Care-of Address Registration
8.1. Регистрация care-of адреса IPv4
The mobile node can use the extensions described in the document to register multiple care-of addresses, even if some of the care-of addresses are IPv4 addresses.
Мобильный узел может использовать описанные в документе расширения для регистрации нескольких care-of адресов, даже если некоторые из care-of адресов являются адресами IPv4.
Bulk registration MUST NOT be used for the initial binding registration from an IPv4 care-of address. This is because the Binding Update and Binding Acknowledgement exchange is used to detect NAT on the path between the mobile node and the home agent. So the mobile node needs to check for a NAT between each IPv4 care-of address and the home agent.
Массовая регистрация НЕ ДОЛЖНА использоваться для начальной регистрации привязки с care-of адреса IPv4. Это объясняется тем, что обмен сообщениями Binding Update и Binding Acknowledgement используется для обнаружения NAT на пути между мобильным узлом и домашним агентом. Поэтому мобильному узлу необходимо проверять наличие NAT между каждым care-of адресом IPv4 и домашним агентом.

8.2. IPv4 Home Address Management
8.2. Управление домашним адресом IPv4
When the mobile node wants to configure an IPv4 home address in addition to the IPv6 home address, it can request one using the IPv4 Home Address option in the Binding Update. If the home agent accepts the Binding Update, the mobile node can now register multiple care-of addresses for the IPv4 home address in addition to the IPv6 home address. The mobile node MUST always use the IPv4 Home Address mobility option for any purposes of the IPv4 home address management. The same set of care-of addresses will be registered for both IPv6 and IPv4 home addresses. The mobile node cannot bind a different set of care-of addresses to each home address. According to [RFC5555], the home agent includes the IPv4 Address Acknowledgement option in the Binding Acknowledgement only if the mobile node had requested an IPv4 home address in the corresponding Binding Update. The IPv4 Address Acknowledgement option MUST be present before any Binding Identifier mobility option. The Status field of the IPv4 Address Acknowledgement option contains only the error code defined in Section 3.2.1 of [RFC5555]. The home agent MUST always include the IPv4 Address Acknowledgement mobility option in the Binding Acknowledgement for the IPv4 home address registration.
Когда мобильный узел хочет настроить домашний адрес IPv4 в дополнение к домашнему адресу IPv6, он может запросить его с помощью опции IPv4 Home Address в сообщении Binding Update. Если домашний агент принимает сообщение Binding Update, мобильный узел теперь может регистрировать несколько care-of адресов для домашнего адреса IPv4 в дополнение к домашнему адресу IPv6. Мобильный узел ДОЛЖЕН всегда использовать опцию мобильности IPv4 Home Address для любых целей управления домашним адресом IPv4. Один и тот же набор care-of адресов будет зарегистрирован как для домашнего адреса IPv6, так и для домашнего адреса IPv4. Мобильный узел не может привязать разный набор care-of адресов к каждому домашнему адресу. Согласно [RFC5555] домашний агент включает опцию IPv4 Address Acknowledgement в сообщение Binding Acknowledgement только в том случае, если мобильный узел запросил домашний адрес IPv4 в соответствующем сообщении Binding Update. Опция IPv4 Address Acknowledgement ДОЛЖНА присутствовать перед любой опцией мобильности Binding Identifier. Поле Status опции IPv4 Address Acknowledgement содержит только код ошибки, определённый в разделе 3.2.1 в [RFC5555]. Домашний агент ДОЛЖЕН всегда включать опцию мобильности IPv4 Address Acknowledgement в сообщение Binding Acknowledgement для регистрации домашнего адреса IPv4.
9. IPsec and IKEv2 Interaction
9. Взаимодействие с IPsec и IKEv2
Mobile IPv6 [RFC3775] and the NEMO protocol [RFC3963] require the use of IPsec to protect signaling messages, including Binding Updates, Binding Acknowledgements, and return routability messages. IPsec may also be used to protect all tunneled data traffic. The Mobile IPv6- IKEv2 specification [RFC4877] specifies how IKEv2 can be used to set up the required IPsec security associations. The following assumptions were made in [RFC3775], [RFC3963], and [RFC4877] with respect to the use of IKEv2 and IPsec.
Mobile IPv6 [RFC3775] и протокол NEMO [RFC3963] требуют использования IPsec для защиты сообщений сигнализации, включая Binding Update, Binding Acknowledgement и сообщения проверки обратной маршрутизации. IPsec также может использоваться для защиты всего туннелируемого трафика данных. Спецификация Mobile IPv6-IKEv2 [RFC4877] определяет, как IKEv2 может использоваться для установления необходимых безопасных ассоциаций IPsec. В [RFC3775], [RFC3963] и [RFC4877] были сделаны следующие допущения относительно использования IKEv2 и IPsec.
o There is only one primary care-of address per mobile node.
o На каждый мобильный узел приходится только один первичный care-of адрес.
o The primary care-of address is stored in the IPsec database for tunnel encapsulation and decapsulation.
o Первичный care-of адрес хранится в базе данных IPsec для инкапсуляции и декапсуляции туннеля.
o When the home agent receives a packet from the mobile node, the source address is verified against the care-of address in the corresponding binding cache entry. If the packet is a reverse- tunneled packet from the mobile node, the care-of address check is done against the source address on the outer IPv6 header. The reverse-tunneled packet could either be a tunneled Home Test Init message or tunneled data traffic to the correspondent node.
o Когда домашний агент получает пакет от мобильного узла, адрес источника проверяется по care-of адресу в соответствующей записи кэша привязок. Если пакет является обратно туннелированным пакетом от мобильного узла, проверка care-of адреса выполняется по адресу источника во внешнем заголовке IPv6. Обратно туннелированный пакет может быть либо туннелированным сообщением Home Test Init, либо туннелируемым трафиком данных к корреспондентскому узлу.
o The mobile node runs IKEv2 (or IKEv1) with the home agent using the care-of address. The IKE SA is based on the care-of address of the mobile node.
o Мобильный узел запускает IKEv2 (или IKEv1) с домашним агентом, используя care-of адрес. SA IKE основана на care-of адресе мобильного узла.
The above assumptions may not be valid when multiple care-of addresses are used by the mobile node. In the following sections, the main issues with the use of multiple care-of addresses with IPsec are addressed.
Вышеуказанные допущения могут оказаться неверными, когда мобильный узел использует несколько care-of адресов. В следующих разделах рассматриваются основные проблемы использования нескольких care-of адресов с IPsec.
9.1. Use of Care-of Address in the IKEv2 Exchange
9.1. Использование care-of адреса в обмене IKEv2
For each home address for which the mobile node sets up security associations with the home agent, the mobile node must pick one care-of address and use that as the source address for all IKEv2 messages exchanged to create and maintain the IPsec security associations associated with the home address. The resultant IKEv2 security association is created based on this care-of address.
Для каждого домашнего адреса, для которого мобильный узел устанавливает безопасные ассоциации с домашним агентом, мобильный узел должен выбрать один care-of адрес и использовать его в качестве адреса источника для всех сообщений IKEv2, которыми создаются и поддерживаются безопасные ассоциации IPsec, связанные с домашним адресом. Результирующая безопасная ассоциация IKEv2 создаётся на основе этого care-of адреса.
If the mobile node needs to change the care-of address, it just sends a Binding Update with the care-of address it wants to use, with the corresponding Binding Identifier mobility option, and with the 'K' bit set. This will force the home agent to update the IKEv2 security association to use the new care-of address. If the 'K' bit is not supported on the mobile node or the home agent, the mobile node MUST re-establish the IKEv2 security association with the new care-of address. This will also result in new IPsec security associations being set up for the home address.
Если мобильному узлу нужно изменить care-of адрес, он просто отправляет сообщение Binding Update с care-of адресом, который хочет использовать, с соответствующей опцией мобильности Binding Identifier и с установленным битом 'K'. Это заставит домашний агент обновить безопасную ассоциацию IKEv2, чтобы использовать новый care-of адрес. Если бит 'K' не поддерживается на мобильном узле или на домашнем агенте, мобильный узел ДОЛЖЕН повторно установить безопасную ассоциацию IKEv2 с новым care-of адресом. Это также приведёт к установлению новых безопасных ассоциаций IPsec для домашнего адреса.
9.2. Transport Mode IPsec-Protected Messages
9.2. Сообщения, защищённые IPsec в транспортном режиме
For Mobile IPv6 signaling message protected using IPsec in transport mode, the use of a particular care-of address among multiple care-of addresses does not matter for IPsec processing.
Для сообщений сигнализации Mobile IPv6, защищаемых с помощью IPsec в транспортном режиме, использование конкретного care-of адреса из нескольких care-of адресов не имеет значения для обработки IPsec.
The home agent processes Mobile Prefix Discovery messages with the same rules of data packets described in Section 6.5.
Домашний агент обрабатывает сообщения Mobile Prefix Discovery по тем же правилам, что и пакеты данных, описанным в разделе 6.5.
9.3. Tunnel Mode IPsec-Protected Messages
9.3. Сообщения, защищённые IPsec в туннельном режиме
The use of IPsec in tunnel mode with multiple care-of addresses introduces a few issues that require changes to how the mobile node and the home agent send and receive tunneled traffic. The route optimization mechanism described in [RFC3775] mandates the use of IPsec protection in tunnel mode for the Home Test Init and Home Test messages. The mobile node and the home agent may also choose to protect all reverse-tunneled payload traffic with IPsec in tunnel mode. The following sections address multiple care-of address support for these two types of messages.
Использование IPsec в туннельном режиме с несколькими care-of адресами порождает ряд проблем, требующих изменений в том, как мобильный узел и домашний агент отправляют и принимают туннелируемый трафик. Механизм оптимизации маршрутизации, описанный в [RFC3775], предписывает использование защиты IPsec в туннельном режиме для сообщений Home Test Init и Home Test. Мобильный узел и домашний агент могут также выбрать защиту всего обратно туннелируемого трафика данных с помощью IPsec в туннельном режиме. В следующих разделах рассматривается поддержка нескольких care-of адресов для этих двух типов сообщений.
9.3.1. Tunneled Home Test Init and Home Test Messages
9.3.1. Туннелированные сообщения Home Test Init и Home Test
The mobile node MAY use the same care-of address for all Home Test Init messages sent reverse tunneled through the home agent. The mobile node may use the same care-of address irrespective of which correspondent node the Home Test Init message is being to. RFC 3775 requires the home agent to verify that the mobile node is using the care-of address that is in the binding cache entry when it receives a reverse-tunneled Home Test Init message. If a different address is used as the source address, the message is silently dropped by the home agent. This document requires the home agent implementation to decapsulate and forward the Home Test Init message as long as the source address is one of the care-of addresses in the binding cache entry for the mobile node.
Мобильный узел МОЖЕТ использовать один и тот же care-of адрес для всех сообщений Home Test Init, отправляемых обратно туннелированными через домашний агент. Мобильный узел может использовать один и тот же care-of адрес независимо от того, какому корреспондентскому узлу предназначено сообщение Home Test Init. RFC 3775 требует, чтобы домашний агент проверял, что мобильный узел использует care-of адрес, содержащийся в записи кэша привязок, при получении обратно туннелированного сообщения Home Test Init. Если в качестве адреса источника используется другой адрес, сообщение молча отбрасывается домашним агентом. Настоящий документ требует, чтобы реализация домашнего агента декапсулировала и пересылала сообщение Home Test Init, пока адрес источника является одним из care-of адресов в записи кэша привязок для мобильного узла.
When the home agent tunnels a Home Test message to the mobile node, the care-of address used in the outer IPv6 header is not relevant to the Home Test message. So regular IPsec tunnel encapsulation with the care-of address known to the IPsec implementation on the home agent is sufficient.
Когда домашний агент туннелирует сообщение Home Test мобильному узлу, care-of адрес, используемый во внешнем заголовке IPv6, не имеет значения для сообщения Home Test. Поэтому достаточно обычной инкапсуляции туннеля IPsec с care-of адресом, известным реализации IPsec на домашнем агенте.
9.3.2. Tunneled Payload Traffic
9.3.2. Туннелируемый трафик данных
When the mobile node sends and receives multiple traffic flows protected by IPsec to different care-of addresses, the use of the correct care-of address for each flow becomes important. Support for this requires the following two considerations on the home agent.
Когда мобильный узел отправляет и принимает несколько защищённых IPsec потоков трафика к разным care-of адресам, использование правильного care-of адреса для каждого потока становится важным. Для поддержки этого на домашнем агенте требуются два следующих условия.
o When the home agent receives a reverse-tunneled payload message protected by IPsec in tunnel mode, the source address used in the outer IPv6 header is irrelevant to IPsec, since the tunnel mode security association is based on the addresses in the inner IPv6 header. Therefore, the same IPsec security association can be used for payload traffic tunneled from any of the care-of addresses. Note that the care-of address used in the reverse- tunneled traffic can be different from the care-of address used as the source address in the IKEv2 exchange. However, this does not cause an issue due to the above-mentioned reason.
o Когда домашний агент получает обратно туннелированное сообщение данных, защищённое IPsec в туннельном режиме, адрес источника, используемый во внешнем заголовке IPv6, не имеет значения для IPsec, поскольку безопасная ассоциация туннельного режима основана на адресах во внутреннем заголовке IPv6. Поэтому одна и та же безопасная ассоциация IPsec может использоваться для трафика данных, туннелированного с любого из care-of адресов. Отметим, что care-of адрес, используемый в обратно туннелированном трафике, может отличаться от care-of адреса, используемого в качестве адреса источника в обмене IKEv2. Однако по вышеуказанной причине это не создаёт проблемы.
o For tunneled IPsec traffic from the home agent to the mobile node, the IPsec implementation on the home agent will not be aware of which care-of address to use when performing IPsec tunnel encapsulation. The Mobile IP stack on the home agent, based on the binding cache entries created by the mobile node, knows to which care-of address the packet belonging to a particular flow needs to be tunneled. The destination address for the outer IP header must either be conveyed dynamically per packet to the IPsec stack when it performs the encapsulation or the Mobile IPv6 stack must get access to the packet after IPsec processing is done and modify the destination address. The first option requires changes to the IPsec implementation. In the second option, there is a need for special processing in the forwarding function to replace the destination address on the outer header with the correct care-of address. The exact technique to achieve the above is implementation specific.
o Для туннелируемого трафика IPsec от домашнего агента мобильному узлу реализация IPsec на домашнем агенте не будет знать, какой care-of адрес использовать при выполнении инкапсуляции туннеля IPsec. Стек Mobile IP на домашнем агенте на основе записей кэша привязок, созданных мобильным узлом, знает, на какой care-of адрес нужно туннелировать пакет, принадлежащий конкретному потоку. Адрес назначения для внешнего заголовка IP должен либо динамически передаваться стеку IPsec для каждого пакета при выполнении инкапсуляции, либо стек Mobile IPv6 должен получить доступ к пакету после завершения обработки IPsec и изменить адрес назначения. Первый вариант требует изменений в реализации IPsec. Во втором варианте требуется специальная обработка в функции пересылки для замены адреса назначения во внешнем заголовке правильным care-of адресом. Точный способ достижения вышеуказанного зависит от реализации.
10. Security Considerations
10. Вопросы безопасности
The security considerations for securing the Binding Update and Binding Acknowledgement messages with multiple care-of addresses are very similar to the security considerations for securing the Binding Update and Binding Acknowledgement. Please see [RFC3775] for more information. The Binding Update and Binding Acknowledgement messages with multiple care-of addresses are securely exchanged as described in [RFC3775], [RFC4877], and Section 9 of this document. Additional security considerations are described below.
Вопросы безопасности для защиты сообщений Binding Update и Binding Acknowledgement с несколькими care-of адресами очень похожи на вопросы безопасности для защиты сообщений Binding Update и Binding Acknowledgement. Дополнительные сведения см. в [RFC3775]. Сообщения Binding Update и Binding Acknowledgement с несколькими care-of адресами безопасно обмениваются, как описано в [RFC3775], [RFC4877] и разделе 9 настоящего документа. Дополнительные вопросы безопасности описаны ниже.
With simultaneous binding support, it is possible for a malicious mobile node to successfully bind a number of victims' addresses as valid care-of addresses for the mobile node with its home agent. Once these addresses have been bound, the malicious mobile node can perform a re-direction attack by instructing the home agent (e.g., setting filtering rules to direct a large file transfer) to tunnel packets to the victims' addresses. Such risk is highlighted in [MIP6ANALYSIS]. These attacks are possible because the care-of addresses sent by the mobile node in the Binding Update messages are not verified by the home agent, i.e., the home agent does not check if the mobile node is at the care-of address at which it claims to be. The security model for Mobile IPv6 assumes that there is a trust relationship between the mobile node and its home agent. Any malicious attack by the mobile node is traceable by the home agent. This acts as a deterrent for the mobile node to launch such attacks.
При поддержке одновременных привязок злонамеренный мобильный узел может успешно привязать ряд адресов жертв в качестве допустимых care-of адресов мобильного узла у своего домашнего агента. После того как эти адреса привязаны, злонамеренный мобильный узел может выполнить атаку перенаправления, предписав домашнему агенту (например, установив правила фильтрации для направления передачи большого файла) туннелировать пакеты на адреса жертв. Такая угроза отмечена в [MIP6ANALYSIS]. Эти атаки возможны потому, что care-of адреса, отправляемые мобильным узлом в сообщениях Binding Update, не проверяются домашним агентом, то есть домашний агент не проверяет, находится ли мобильный узел по тому care-of адресу, который он заявляет. Модель безопасности Mobile IPv6 предполагает наличие доверительных отношений между мобильным узлом и его домашним агентом. Любая злонамеренная атака мобильного узла может быть отслежена домашним агентом. Это удерживает мобильный узел от запуска таких атак.
Although such a risk exists in Mobile IPv6, the risk level is increased when simultaneous multiple care-of address bindings are performed. In Mobile IPv6, a mobile node can only have a single care-of address binding per home address at a given time. However, for simultaneous multiple care-of address bindings, a mobile node can have more than one care-of address binding per home address at a given time. This implies that a mobile node using simultaneous binding support can effectively bind more than a single victim's address. Another difference is the degree of risk involved. In the single care-of address binding case, once the re-direction attack is initiated, a malicious mobile node would be unable to use its home address for communications (such as to receive control packets pertaining to the file transfer). However, in the simultaneous binding support case, a malicious mobile node could bind a valid care-of address in addition to multiple victims addresses. This valid care-of address could then be used by the malicious mobile node to set up flow filtering rules at its home agent, thereby controlling and/or launching new re-direction attacks. Thus, in view of such risks, it is advisable for a home agent to employ some form of care-of address verification mechanism before using the care-of addresses as a valid routing path to a mobile node.
Хотя такая угроза существует в Mobile IPv6, уровень риска возрастает при выполнении одновременных привязок нескольких care-of адресов. В Mobile IPv6 мобильный узел может иметь только одну привязку care-of адреса на домашний адрес в данный момент времени. Однако при одновременных привязках нескольких care-of адресов мобильный узел может иметь более одной привязки care-of адреса на домашний адрес в данный момент времени. Это означает, что мобильный узел, использующий поддержку одновременных привязок, может фактически привязать более одного адреса жертвы. Ещё одно различие состоит в степени риска. В случае привязки одного care-of адреса после начала атаки перенаправления злонамеренный мобильный узел не смог бы использовать свой домашний адрес для связи (например, для получения управляющих пакетов, относящихся к передаче файла). Однако в случае поддержки одновременных привязок злонамеренный мобильный узел мог бы привязать допустимый care-of адрес в дополнение к нескольким адресам жертв. Этот допустимый care-of адрес затем мог бы использоваться злонамеренным мобильным узлом для настройки правил фильтрации потоков у своего домашнего агента, тем самым управляя новыми атаками перенаправления и (или) запуская их. Таким образом, учитывая такие риски, домашнему агенту целесообразно применять некоторую форму механизма проверки care-of адресов, прежде чем использовать care-of адреса в качестве допустимого пути маршрутизации к мобильному узлу.
These mechanisms are out of scope for this document.
Эти механизмы выходят за рамки настоящего документа.
In the binding registration of Mobile IPv6, a care-of address is always verified by its reachability by a home agent. This reachability test may decrease the above risks. However, when bulk registration is used, a home agent cannot verify reachability of care-of addresses carried in a Binding Identifier mobility option. Therefore, the home agent can choose to reject bulk registration by using [MCOA BULK REGISTRATION PROHIBITED] in a Binding Acknowledgement. Alternatively, when a mobile node first registers a care-of address, it uses the individual Binding Updates for the first appeared care-of address. During the initial binding registration, a home agent can verify the address reachability for that given care-of address. After that, the mobile node uses bulk registration to refresh the care-of address.
При регистрации привязки в Mobile IPv6 care-of адрес всегда проверяется на достижимость домашним агентом. Эта проверка достижимости может снизить вышеуказанные риски. Однако при использовании массовой регистрации домашний агент не может проверить достижимость care-of адресов, переносимых в опции мобильности Binding Identifier. Поэтому домашний агент может выбрать отклонение массовой регистрации с помощью [MCOA BULK REGISTRATION PROHIBITED] в сообщении Binding Acknowledgement. В качестве альтернативы, когда мобильный узел впервые регистрирует care-of адрес, он использует индивидуальные сообщения Binding Update для впервые появившегося care-of адреса. При начальной регистрации привязки домашний агент может проверить достижимость адреса для данного care-of адреса. После этого мобильный узел использует массовую регистрацию для обновления care-of адреса.
