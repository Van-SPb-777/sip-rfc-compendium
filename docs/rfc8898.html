Third-Party Token-Based Authentication and Authorization for Session Initiation Protocol (SIP)
Аутентификация и авторизация в SIP по сторонним токенам
Abstract
Аннотация
This document defines the "Bearer" authentication scheme for the Session Initiation Protocol (SIP) and a mechanism by which user authentication and SIP registration authorization is delegated to a third party, using the OAuth 2.0 framework and OpenID Connect Core 1.0. This document updates RFC 3261 to provide guidance on how a SIP User Agent Client (UAC) responds to a SIP 401/407 response that contains multiple WWW-Authenticate/Proxy-Authenticate header fields.
Настоящий документ определяет схему аутентификации «Bearer» для протокола инициирования сессий (SIP) и механизм, посредством которого аутентификация пользователя и авторизация регистрации в SIP делегируются третьей стороне с использованием основ OAuth 2.0 и OpenID Connect Core 1.0. Настоящий документ обновляет RFC 3261, давая указания о том, как клиент пользовательского агента SIP (UAC) отвечает на ответ SIP 401/407, содержащий несколько полей заголовка WWW-Authenticate/Proxy-Authenticate.

1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [RFC3261] uses the same framework as HTTP [RFC7230] to authenticate users: a simple challenge-response authentication mechanism that allows a SIP User Agent Server (UAS), proxy, or registrar to challenge a SIP User Agent Client (UAC) request and allows the UAC to provide authentication information in response to that challenge.
Протокол инициирования сессий (SIP) [RFC3261] использует ту же основу, что и HTTP [RFC7230], для аутентификации пользователей: простой механизм аутентификации «запрос-ответ», который позволяет серверу пользовательского агента SIP (UAS), прокси или регистратору запросить аутентификацию у клиента пользовательского агента SIP (UAC) и позволяет UAC предоставить аутентификационную информацию в ответ на этот запрос.
OAuth 2.0 [RFC6749] defines a token-based authorization framework to allow an OAuth client to access resources on behalf of its user.
OAuth 2.0 [RFC6749] определяет основу авторизации на основе токенов, позволяющую OAuth-клиенту получать доступ к ресурсам от имени своего пользователя.
The OpenID Connect Core 1.0 specification [OPENID] defines a simple identity layer on top of the OAuth 2.0 protocol, which enables OAuth/ OpenID clients to verify the identity of the user based on the authentication performed by a dedicated authorization server (AS), referred to as OpenID Provider (OP), as well as to obtain basic profile information about the user.
Спецификация OpenID Connect Core 1.0 [OPENID] определяет простой уровень идентификации поверх протокола OAuth 2.0, который позволяет клиентам OAuth/OpenID проверять личность пользователя на основе аутентификации, выполненной выделенным сервером авторизации (AS), называемым провайдером OpenID (OP), а также получать базовую информацию профиля о пользователе.
This document defines the "Bearer" authentication scheme for SIP and a mechanism by which user authentication and SIP registration authorization is delegated to a third party, using the OAuth 2.0 framework and OpenID Connect Core 1.0. This kind of user authentication enables single sign-on, which allows the user to authenticate once and gain access to both SIP and non-SIP services.
Настоящий документ определяет схему аутентификации «Bearer» для SIP и механизм, посредством которого аутентификация пользователя и авторизация регистрации в SIP делегируются третьей стороне с использованием основ OAuth 2.0 и OpenID Connect Core 1.0. Такой вид аутентификации пользователя обеспечивает единый вход, позволяющий пользователю аутентифицироваться один раз и получать доступ как к SIP-, так и к не-SIP-службам.
This document also updates [RFC3261] by defining the UAC procedures when a UAC receives a 401/407 response with multiple WWW- Authenticate/Proxy-Authenticate header fields, providing challenges using different authentication schemes for the same realm.
Настоящий документ также обновляет [RFC3261], определяя процедуры UAC для случая, когда UAC получает ответ 401/407 с несколькими полями заголовка WWW-Authenticate/Proxy-Authenticate, предоставляющими запросы аутентификации с использованием разных схем аутентификации для одной и той же области (realm).

1.2. Applicability
1.2. Применимость
This document covers cases where grants that allow the UAC to obtain an access token from the AS are used. Cases where the UAC is not able to obtain an access token (e.g., in the case of an authorization code grant) are not covered.
Настоящий документ охватывает случаи, когда используются гранты, позволяющие UAC получить токен доступа от AS. Случаи, когда UAC не может получить токен доступа (например, в случае гранта кода авторизации), не рассматриваются.
1.3. Token Types and Formats
1.3. Типы и форматы токенов
The tokens used in third-party authorization depend on the type of AS.
Токены, используемые при сторонней авторизации, зависят от типа AS.
An OAuth AS provides the following tokens to a successfully authorized UAC:
OAuth AS предоставляет успешно авторизованному UAC следующие токены:
Access Token: The UAC will use this token to gain access to services by providing the token to a SIP server.
Токен доступа: UAC будет использовать этот токен для доступа к службам, предоставляя токен SIP-серверу.
Refresh Token: The UAC will present this token to the AS to refresh a stale access token.
Токен обновления: UAC будет предъявлять этот токен AS для обновления устаревшего токена доступа.
An OP returns an additional token:
OP возвращает дополнительный токен:
ID Token: This token contains a SIP URI associated with the user and other user-specific details that will be consumed by the UAC.
ID-токен: этот токен содержит SIP URI, связанный с пользователем, и другие сведения о пользователе, которые будут использоваться UAC.
Tokens can be represented in two different formats:
Токены могут быть представлены в двух разных форматах:
Structured Token: A token that consists of a structured object that contains the claims associated with the token, e.g., JSON Web Token (JWT), as defined in [RFC7519].
Структурированный токен: токен, состоящий из структурированного объекта, содержащего утверждения, связанные с токеном, например веб-токен JSON (JWT), как определено в [RFC7519].
Reference Token: A token that consists of an opaque string that is used to obtain the details of the token and its associated claims, as defined in [RFC6749].
Ссылочный токен: токен, состоящий из непрозрачной строки, используемой для получения сведений о токене и связанных с ним утверждениях, как определено в [RFC6749].
Access tokens are represented in one of the above two formats. Refresh tokens usually are represented in a reference format, as this token is consumed only by the AS that issued the token. The ID token is defined as a structured token in the form of a JWT.
Токены доступа представляются в одном из двух вышеуказанных форматов. Токены обновления обычно представляются в ссылочном формате, поскольку этот токен используется только AS, выдавшим токен. ID-токен определён как структурированный токен в форме JWT.

Рисунок 1: Пример потока регистрации
In step [1], the UAC starts the registration process by sending a SIP REGISTER request to the registrar without any credentials.
На шаге [1] UAC начинает процесс регистрации, отправляя регистратору запрос SIP REGISTER без каких-либо учётных данных.
In step [2], the registrar challenges the UA by sending a SIP 401 (Unauthorized) response to the REGISTER request. In the response, the registrar includes information about the AS to contact in order to obtain a token.
На шаге [2] регистратор запрашивает аутентификацию у UA, отправляя в ответ на запрос REGISTER ответ SIP 401 (Unauthorized). В ответе регистратор включает информацию об AS, к которому следует обратиться для получения токена.
In step [3], the UAC interacts with the AS via an out-of-scope mechanism, potentially using the OAuth Native App mechanism defined in [RFC8252]. The AS authenticates the user and provides the UAC with the tokens needed to access the SIP service.
На шаге [3] UAC взаимодействует с AS через механизм, выходящий за рамки настоящего документа, возможно, используя механизм OAuth для нативных приложений, определённый в [RFC8252]. AS аутентифицирует пользователя и предоставляет UAC токены, необходимые для доступа к SIP-службе.
In step [4], the UAC retries the registration process by sending a new REGISTER request that includes the access token that the UAC obtained in the step above.
На шаге [4] UAC повторяет процесс регистрации, отправляя новый запрос REGISTER, который включает токен доступа, полученный UAC на предыдущем шаге.
The registrar validates the access token. If the access token is a reference token, the registrar MAY perform an introspection [RFC7662], as in steps [5] and [6], in order to obtain more information about the access token and its scope, per [RFC7662]. Otherwise, after the registrar validates the token, it inspects its claims and acts upon it.
Регистратор проверяет токен доступа. Если токен доступа является ссылочным токеном, регистратор МОЖЕТ выполнить интроспекцию [RFC7662], как на шагах [5] и [6], чтобы получить больше информации о токене доступа и его области действия, согласно [RFC7662]. В противном случае, после проверки токена регистратор изучает его утверждения и действует на их основе.
In step [7], once the registrar has successfully verified and accepted the access token, it sends a 200 (OK) response to the REGISTER request.
На шаге [7], после того как регистратор успешно проверил и принял токен доступа, он отправляет в ответ на запрос REGISTER ответ 200 (OK).

2. SIP Procedures
2. Процедуры SIP
Section 22 of [RFC3261] defines the SIP procedures for the Digest authentication mechanism. The same procedures apply to the "Bearer" authentication mechanism, with the changes described in this section.
Раздел 22 [RFC3261] определяет процедуры SIP для механизма аутентификации Digest. Те же процедуры применяются к механизму аутентификации «Bearer» с изменениями, описанными в настоящем разделе.
2.1. UAC Behavior
2.1. Поведение UAC
2.1.1. Obtaining Tokens and Responding to Challenges
2.1.1. Получение токенов и ответ на запросы аутентификации
When a UAC sends a request without credentials (or with invalid credentials), it could receive either a 401 (Unauthorized) response with a WWW-Authenticate header field or a 407 (Proxy Authentication Required) response with a Proxy-Authenticate header field. If the WWW-Authenticate or Proxy-Authenticate header field indicates "Bearer" scheme authentication and contains an address to an AS, the UAC contacts the AS in order to obtain tokens and includes the requested scopes, based on a local configuration (Figure 1). The UAC MUST check the AS URL received in the 401/407 response against a list of trusted ASs configured on the UAC in order to prevent several classes of possible vulnerabilities when a client blindly attempts to use any provided AS.
Когда UAC отправляет запрос без учётных данных (или с недействительными учётными данными), он может получить либо ответ 401 (Unauthorized) с полем заголовка WWW-Authenticate, либо ответ 407 (Proxy Authentication Required) с полем заголовка Proxy-Authenticate. Если поле заголовка WWW-Authenticate или Proxy-Authenticate указывает на аутентификацию по схеме «Bearer» и содержит адрес AS, UAC связывается с AS для получения токенов и включает запрошенные области действия (scope) на основе локальной конфигурации (рисунок 1). UAC ОБЯЗАН проверить URL AS, полученный в ответе 401/407, по списку доверенных AS, настроенному на UAC, чтобы предотвратить несколько классов возможных уязвимостей, когда клиент слепо пытается использовать любой предоставленный AS.
The detailed OAuth2 procedure to authenticate the user and obtain these tokens is out of scope of this document. The address of the AS might already be known to the UAC via configuration. In such cases, the UAC can contact the AS for tokens before it sends a SIP request (Figure 2). Procedures for native applications are defined in [RFC8252]. When using the mechanism defined in [RFC8252], the user of the UAC will be directed to interact with the AS using a web browser, which allows the AS to prompt the user for multi-factor authentication, to redirect the user to third-party identity providers, and to enable the use of single sign-on sessions.
Подробная процедура OAuth2 аутентификации пользователя и получения этих токенов выходит за рамки настоящего документа. Адрес AS может быть уже известен UAC посредством конфигурации. В таких случаях UAC может связаться с AS для получения токенов до отправки SIP-запроса (рисунок 2). Процедуры для нативных приложений определены в [RFC8252]. При использовании механизма, определённого в [RFC8252], пользователь UAC будет направлен на взаимодействие с AS через веб-браузер, что позволяет AS запросить у пользователя многофакторную аутентификацию, перенаправить пользователя к сторонним поставщикам идентификации и включить использование сеансов единого входа.
The tokens returned to the UAC depend on the type of AS; an OAuth AS provides an access token and, optionally, a refresh token [RFC6749]. The refresh token is only used between the UAC and the AS. If the AS provides a refresh token to the UAC, the UAC uses it to request a new access token from the AS before the currently used access token expires ([RFC6749], Section 1.5). If the AS does not provide a refresh token, the UAC needs to reauthenticate the user in order to get a new access token before the currently used access token expires. An OP returns an additional ID token that contains claims about the authentication of the user by an authorization server. The ID token can potentially include other optional claims about the user, e.g., the SIP URI, that will be consumed by the UAC and later used to register with the registrar.
Токены, возвращаемые UAC, зависят от типа AS; OAuth AS предоставляет токен доступа и, возможно, токен обновления [RFC6749]. Токен обновления используется только между UAC и AS. Если AS предоставляет UAC токен обновления, UAC использует его для запроса нового токена доступа от AS до истечения срока действия текущего используемого токена доступа ([RFC6749], раздел 1.5). Если AS не предоставляет токен обновления, UAC должен повторно аутентифицировать пользователя, чтобы получить новый токен доступа до истечения срока действия текущего используемого токена доступа. OP возвращает дополнительный ID-токен, содержащий утверждения об аутентификации пользователя сервером авторизации. ID-токен может потенциально включать другие необязательные утверждения о пользователе, например SIP URI, которые будут использоваться UAC и позже применены для регистрации у регистратора.
If the UAC receives a 401/407 response with multiple WWW- Authenticate/Proxy-Authenticate header fields, providing challenges using different authentication schemes for the same realm, the UAC provides credentials for one of the schemes that it supports, based on local policy.
Если UAC получает ответ 401/407 с несколькими полями заголовка WWW-Authenticate/Proxy-Authenticate, предоставляющими запросы аутентификации с использованием разных схем аутентификации для одной и той же области (realm), UAC предоставляет учётные данные для одной из поддерживаемых им схем на основе локальной политики.

2.1.2. Protecting the Access Token
2.1.2. Защита токена доступа
[RFC6749] mandates that access tokens are protected with TLS when in transit. However, SIP makes use of intermediary SIP proxies, and TLS only guarantees hop-to-hop protection when used to protect SIP signaling. Therefore, the access token MUST be protected in a way so that only authorized SIP servers will have access to it. SIP endpoints that support this document MUST use encrypted JWTs [RFC7519] for encoding and protecting access tokens when they are included in SIP requests, unless some other mechanism is used to guarantee that only authorized SIP endpoints have access to the access token. TLS can still be used for protecting traffic between SIP endpoints and the AS, as defined in [RFC6749].
[RFC6749] требует, чтобы токены доступа защищались с помощью TLS при передаче. Однако SIP использует промежуточные SIP-прокси, а TLS гарантирует защиту только между соседними узлами, когда применяется для защиты сигнализации SIP. Поэтому токен доступа ДОЛЖЕН быть защищён так, чтобы только авторизованные SIP-серверы имели к нему доступ. SIP-конечные точки, поддерживающие настоящий документ, ОБЯЗАНЫ использовать зашифрованные JWT [RFC7519] для кодирования и защиты токенов доступа, когда они включаются в SIP-запросы, если только не используется какой-либо другой механизм, гарантирующий, что только авторизованные SIP-конечные точки имеют доступ к токену доступа. TLS по-прежнему может использоваться для защиты трафика между SIP-конечными точками и AS, как определено в [RFC6749].
2.1.3. REGISTER Request
2.1.3. Запрос REGISTER
The procedures in this section apply when the UAC has received a challenge that contains a "Bearer" scheme and the UAC has obtained a token, as specified in Section 2.1.1.
Процедуры в настоящем разделе применяются, когда UAC получил запрос аутентификации, содержащий схему «Bearer», и UAC получил токен, как указано в разделе 2.1.1.
The UAC sends a REGISTER request with an Authorization header field containing the response to the challenge, including the "Bearer" scheme carrying a valid access token in the request, as specified in [RFC6750].
UAC отправляет запрос REGISTER с полем заголовка Authorization, содержащим ответ на запрос аутентификации, включая схему «Bearer», несущую действительный токен доступа в запросе, как указано в [RFC6750].
Note that if there were multiple challenges with different schemes, then the UAC may be able to successfully retry the request using non-"Bearer" credentials.
Обратите внимание: если было несколько запросов аутентификации с разными схемами, то UAC может успешно повторить запрос с использованием учётных данных не «Bearer».
Typically, a UAC will obtain a new access token for each new binding. However, based on local policy, a UAC MAY include an access token that has been used for another binding associated with the same Address Of Record (AOR) in the request.
Обычно UAC получает новый токен доступа для каждой новой привязки. Однако на основе локальной политики UAC МОЖЕТ включить в запрос токен доступа, который использовался для другой привязки, связанной с тем же адресом записи (AOR).
If the access token included in a REGISTER request is not accepted and the UAC receives a 401 response or a 407 response, the UAC follows the procedures in Section 2.1.1.
Если токен доступа, включённый в запрос REGISTER, не принимается и UAC получает ответ 401 или ответ 407, то UAC следует процедурам, изложенным в разделе 2.1.1.
2.1.4. Non-REGISTER Request
2.1.4. Запрос, отличный от REGISTER
The procedures in this section apply when the UAC has received a challenge that contains a "Bearer" scheme and the UAC has obtained a token, as specified in Section 2.1.1.
Процедуры в настоящем разделе применяются, когда UAC получил запрос аутентификации, содержащий схему «Bearer», и UAC получил токен, как указано в разделе 2.1.1.
When the UAC sends a request, it MUST include an Authorization header field with a "Bearer" scheme carrying a valid access token obtained from the AS indicated in the challenge in the request, as specified in [RFC6750]. Based on local policy, the UAC MAY include an access token that has been used for another dialog, or for another stand- alone request, if the target of the new request is the same.
Когда UAC отправляет запрос, он ОБЯЗАН включить поле заголовка Authorization со схемой «Bearer», несущее действительный токен доступа, полученный от AS, указанного в запросе аутентификации в запросе, как указано в [RFC6750]. На основе локальной политики UAC МОЖЕТ включить токен доступа, который использовался для другого диалога или для другого отдельного запроса, если цель нового запроса та же.
If the access token included in a request is not accepted and the UAC receives a 401 response or a 407 response, the UAC follows the procedures in Section 2.1.1.
Если токен доступа, включённый в запрос, не принимается и UAC получает ответ 401 или ответ 407, то UAC следует процедурам, изложенным в разделе 2.1.1.
2.2. User Agent Server (UAS) and Registrar Behavior
2.2. Поведение сервера пользовательского агента (UAS) и регистратора
When a UAS or registrar receives a request that fails to contain authorization credentials acceptable to it, the UAS/registrar SHOULD challenge the request by sending a 401 (Unauthorized) response. If the UAS/registrar chooses to challenge the request and is willing to accept an access token as a credential, it MUST include a WWW- Authenticate header field in the response that indicates a "Bearer" scheme and includes an AS address, encoded as an https URI [RFC7230], from which the UAC can obtain an access token.
Когда UAS или регистратор получает запрос, который не содержит приемлемых для него учётных данных авторизации, UAS/регистратор ДОЛЖЕН запросить аутентификацию, отправив ответ 401 (Unauthorized). Если UAS/регистратор решает запросить аутентификацию и готов принять токен доступа в качестве учётных данных, он ОБЯЗАН включить в ответ поле заголовка WWW-Authenticate, указывающее на схему «Bearer» и содержащее адрес AS, закодированный как https URI [RFC7230], от которого UAC может получить токен доступа.
When a UAS or registrar receives a SIP request that contains an Authorization header field with an access token, the UAS/registrar MUST validate the access token using the procedures associated with the type of access token (structured or reference) used, e.g., [RFC7519]. If the token provided is an expired access token, then the UAS/registrar MUST reply with a 401 (Unauthorized) response, as defined in Section 3 of [RFC6750]. If the validation is successful, the UAS/registrar can continue to process the request using normal SIP procedures. If the validation fails, the UAS/registrar MUST reply with a 401 (Unauthorized) response.
Когда UAS или регистратор получает SIP-запрос, содержащий поле заголовка Authorization с токеном доступа, UAS/регистратор ОБЯЗАН проверить токен доступа с использованием процедур, связанных с типом используемого токена доступа (структурированный или ссылочный), например [RFC7519]. Если предоставленный токен является просроченным токеном доступа, UAS/регистратор ОБЯЗАН ответить ответом 401 (Unauthorized), как определено в разделе 3 [RFC6750]. Если проверка успешна, UAS/регистратор может продолжить обработку запроса с использованием обычных процедур SIP. Если проверка не удалась, UAS/регистратор ОБЯЗАН ответить ответом 401 (Unauthorized).
2.3. Proxy Behavior
2.3. Поведение прокси
When a proxy receives a request that fails to contain authorization credentials acceptable to it, it SHOULD challenge the request by sending a 407 (Proxy Authentication Required) response. If the proxy chooses to challenge the request and is willing to accept an access token as a credential, it MUST include a Proxy-Authenticate header field in the response that indicates a "Bearer" scheme and includes an AS address, encoded as an https URI [RFC7230], from which the UAC can obtain an access token.
Когда прокси получает запрос, который не содержит приемлемых для него учётных данных авторизации, он ДОЛЖЕН запросить аутентификацию, отправив ответ 407 (Proxy Authentication Required). Если прокси решает запросить аутентификацию и готов принять токен доступа в качестве учётных данных, он ОБЯЗАН включить в ответ поле заголовка Proxy-Authenticate, указывающее на схему «Bearer» и содержащее адрес AS, закодированный как https URI [RFC7230], от которого UAC может получить токен доступа.
When a proxy wishes to authenticate a received request, it MUST search the request for Proxy-Authorization header fields with 'realm' parameters that match its realm. It then MUST successfully validate the credentials from at least one Proxy-Authorization header field for its realm. When the scheme is "Bearer", the proxy MUST validate the access token using the procedures associated with the type of access token (structured or reference) used, e.g., [RFC7519].
Когда прокси желает аутентифицировать полученный запрос, он ОБЯЗАН найти в запросе поля заголовка Proxy-Authorization с параметрами 'realm', соответствующими его realm. Затем он ОБЯЗАН успешно проверить учётные данные хотя бы из одного поля заголовка Proxy-Authorization для своего realm. Когда схема — «Bearer», прокси ОБЯЗАН проверить токен доступа с использованием процедур, связанных с типом используемого токена доступа (структурированный или ссылочный), например [RFC7519].
3. Access Token Claims
3. Утверждения токена доступа
The type of services to which an access token grants access can be determined using different methods. The methods used and the access provided by the token are based on local policy agreed between the AS and the registrar.
Тип служб, к которым предоставляет доступ токен доступа, можно определить разными методами. Используемые методы и предоставляемый токеном доступ основаны на локальной политике, согласованной между AS и регистратором.
If an access token is encoded as a JWT, it will contain a list of claims [RFC7519], including both registered and application-specific claims. The registrar can grant access to services based on such claims, some other mechanism, or a combination of claims and some other mechanism. If an access token is a reference token, the registrar will grant access based on some other mechanism. Examples of such other mechanisms are introspection [RFC7662] and user profile lookups.
Если токен доступа закодирован как JWT, он будет содержать список утверждений [RFC7519], включая как зарегистрированные, так и зависящие от приложения утверждения. Регистратор может предоставлять доступ к службам на основе таких утверждений, какого-либо другого механизма или сочетания утверждений и какого-либо другого механизма. Если токен доступа является ссылочным токеном, регистратор будет предоставлять доступ на основе какого-либо другого механизма. Примерами таких других механизмов являются интроспекция [RFC7662] и поиск профилей пользователей.

As defined in [RFC6749], the value of the scope parameter is expressed as a list of space-delimited, case-sensitive strings. The strings are defined by the AS. The values of the scope parameter are out of scope of this document. The UAC will use the scope provided by the registrar to contact the AS and obtain a proper token with the requested scope.

UAC будет использовать область действия, предоставленную регистратором, для связи с AS и получения надлежащего токена с запрошенной областью действия.
The error parameter could be used by the registrar/proxy to indicate to the UAC the reason for the error, with possible values of "invalid_token" or "invalid_scope".
Параметр error может использоваться регистратором/прокси, чтобы указать UAC причину ошибки, с возможными значениями «invalid_token» или «invalid_scope».
5. Security Considerations
5. Вопросы безопасности
The security considerations for OAuth are defined in [RFC6749]. The security considerations for "Bearer" tokens are defined in [RFC6750]. The security considerations for JWTs are defined in [RFC7519]. These security considerations also apply to SIP usage of access tokens, as defined in this document.
Вопросы безопасности для OAuth определены в [RFC6749]. Вопросы безопасности для токенов «Bearer» определены в [RFC6750]. Вопросы безопасности для JWT определены в [RFC7519]. Эти вопросы безопасности также применяются к использованию токенов доступа в SIP, как определено в настоящем документе.
[RFC6749] mandates that access tokens are protected with TLS when in transit. However, SIP makes use of intermediary SIP proxies, and TLS only guarantees hop-to-hop protection when used to protect SIP signaling. Therefore, the access token MUST be protected in a way so that only authorized SIP servers will have access to it. SIP endpoints that support this document MUST use encrypted JWTs [RFC7519] for encoding and protecting access tokens when they are included in SIP requests, unless some other mechanism is used to guarantee that only authorized SIP endpoints have access to the access token. TLS can still be used for protecting traffic between SIP endpoints and the AS, as defined in [RFC6749].
[RFC6749] требует, чтобы токены доступа защищались с помощью TLS при передаче. Однако SIP использует промежуточные SIP-прокси, а TLS гарантирует защиту только между соседними узлами, когда применяется для защиты сигнализации SIP. Поэтому токен доступа ДОЛЖЕН быть защищён так, чтобы только авторизованные SIP-серверы имели к нему доступ. SIP-конечные точки, поддерживающие настоящий документ, ОБЯЗАНЫ использовать зашифрованные JWT [RFC7519] для кодирования и защиты токенов доступа, когда они включаются в SIP-запросы, если только не используется какой-либо другой механизм, гарантирующий, что только авторизованные SIP-конечные точки имеют доступ к токену доступа. TLS по-прежнему может использоваться для защиты трафика между SIP-конечными точками и AS, как определено в [RFC6749].
Single Sign-On (SSO) enables the user to use one set of credentials to authenticate once and gain access to multiple SIP and non-SIP services using access token(s). If the SSO login is compromised, that single point of compromise has a much broader effect than is the case without SSO. Further, an attacker can often use a compromised account to set up Single Sign-On for other services that the victim has not established an account with and sometimes can even switch a dedicated account into SSO mode, creating a still broader attack.
Единый вход (SSO) позволяет пользователю использовать один набор учётных данных, чтобы аутентифицироваться один раз и получить доступ к нескольким SIP- и не-SIP-службам с использованием токена(ов) доступа. Если вход SSO скомпрометирован, эта единая точка компрометации имеет гораздо более широкий эффект, чем в случае без SSO. Кроме того, злоумышленник часто может использовать скомпрометированную учётную запись для настройки единого входа для других служб, с которыми жертва не устанавливала учётную запись, а иногда даже может перевести выделенную учётную запись в режим SSO, создавая ещё более широкую атаку.
Because of that, it is critical to make sure that extra security measures be taken to safeguard credentials used for Single Sign-On. Examples of such measures include a long passphrase instead of a password, enabling multi-factor authentication, and the use of the native platform browser when possible, as defined in [RFC8252].
Из-за этого критически важно убедиться, что принимаются дополнительные меры безопасности для защиты учётных данных, используемых для единого входа. Примеры таких мер включают длинную парольную фразу вместо пароля, включение многофакторной аутентификации и использование встроенного браузера платформы, когда это возможно, как определено в [RFC8252].
Although this is out of scope for this document, it is important to carefully consider the claims provided in the tokens used to access these services to make sure of the privacy of the user accessing these services. As mentioned above, this document calls for encrypting JWTs representing the access token.
Хотя это выходит за рамки настоящего документа, важно тщательно рассмотреть утверждения, предоставляемые в токенах, используемых для доступа к этим службам, чтобы обеспечить конфиденциальность пользователя, получающего доступ к этим службам. Как упомянуто выше, настоящий документ требует шифрования JWT, представляющих токен доступа.
It is important that both parties participating in SSO provide mechanisms for users to sever the SSO relationship so that it is possible without undue difficulty to mitigate a compromise that has already happened.
Важно, чтобы обе стороны, участвующие в SSO, предоставляли пользователям механизмы для разрыва отношений SSO, чтобы можно было без чрезмерных трудностей смягчить уже произошедшую компрометацию.
The operator of an SSO authentication system has access to private information about sites and services that their users log into and even, to some extent, their usage patterns. It's important to call these out in privacy disclosures and policies and to make sure that users can be aware of the trade-offs between convenience and privacy when they choose to use SSO.
Оператор системы аутентификации SSO имеет доступ к частной информации о сайтах и службах, в которые входят его пользователи, и даже, в некоторой степени, к их моделям использования. Важно указывать это в раскрытиях о конфиденциальности и политиках, а также следить за тем, чтобы пользователи могли осознавать компромиссы между удобством и конфиденциальностью, когда они выбирают использование SSO.
When a registrar chooses to challenge a REGISTER request, if the registrar can provide access to different levels of services, it is RECOMMENDED that the registrar include a scope in the response in order to indicate the minimum scope needed to register and access basic services. The access token might include an extended scope that gives the user access to more advanced features beyond basic services. In SIP, the AS administrator will typically decide what level of access is provided for a given user.
Когда регистратор решает запросить аутентификацию для запроса REGISTER, если регистратор может предоставить доступ к разным уровням служб, РЕКОМЕНДУЕТСЯ, чтобы регистратор включал область действия в ответ, чтобы указать минимальную область действия, необходимую для регистрации и доступа к базовым службам. Токен доступа может включать расширенную область действия, дающую пользователю доступ к более продвинутым функциям помимо базовых служб. В SIP администратор AS обычно решает, какой уровень доступа предоставляется данному пользователю.
The UAC MUST check the AS URL received in the 401/407 response against a list of trusted ASs configured on the UAC in order to prevent several classes of possible vulnerabilities when a client blindly attempts to use any provided AS.
UAC ОБЯЗАН проверить URL AS, полученный в ответе 401/407, по списку доверенных AS, настроенному на UAC, чтобы предотвратить несколько классов возможных уязвимостей, когда клиент слепо пытается использовать любой предоставленный AS.
