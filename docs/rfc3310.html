Abstract
Аннотация
This memo specifies an Authentication and Key Agreement (AKA) based one-time password generation mechanism for Hypertext Transfer Protocol (HTTP) Digest access authentication. The HTTP Authentication Framework includes two authentication schemes: Basic and Digest. Both schemes employ a shared secret based mechanism for access authentication. The AKA mechanism performs user authentication and session key distribution in Universal Mobile Telecommunications System (UMTS) networks. AKA is a challenge- response based mechanism that uses symmetric cryptography.
В этом документе описывается механизм генерации одноразового пароля на основе аутентификации и соглашения о ключах (AKA) для аутентификации дайджест-доступа протокола передачи гипертекста (HTTP). Платформа HTTP-аутентификации включает две схемы аутентификации: базовую и дайджест. Обе схемы используют механизм аутентификации доступа на основе общего секрета. Механизм AKA выполняет аутентификацию пользователей и распределение ключей сессии в сетях универсальной системы мобильной связи (UMTS). AKA — это механизм, основанный на запросе-ответе и использующий симметричную криптографию.
1. Introduction and Motivation
1. Введение и мотивация
The Hypertext Transfer Protocol (HTTP) Authentication Framework, described in RFC 2617 [2], includes two authentication schemes: Basic and Digest. Both schemes employ a shared secret based mechanism for access authentication. The Basic scheme is inherently insecure in that it transmits user credentials in plain text. The Digest scheme improves security by hiding user credentials with cryptographic hashes, and additionally by providing limited message integrity.
Структура аутентификации протокола передачи гипертекста (HTTP), описанная в RFC 2617 [2], включает две схемы аутентификации: базовую и дайджест. Обе схемы используют механизм аутентификации доступа на основе общего секрета. Базовая схема по своей сути небезопасна, поскольку она передает учетные данные пользователя в виде обычного текста. Схема дайджеста повышает безопасность, скрывая учетные данные пользователя с помощью криптографических хешей, а также обеспечивая ограниченную целостность сообщений.
The Authentication and Key Agreement (AKA) [6] mechanism performs authentication and session key distribution in Universal Mobile Telecommunications System (UMTS) networks. AKA is a challenge- response based mechanism that uses symmetric cryptography. AKA is typically run in a UMTS IM Services Identity Module (ISIM), which resides on a smart card like device that also provides tamper resistant storage of shared secrets. This document specifies a mapping of AKA parameters onto HTTP Digest authentication. In essence, this mapping enables the usage of AKA as a one-time password generation mechanism for Digest authentication.
Механизм аутентификации и соглашения о ключах (AKA) [6] выполняет аутентификацию и распределение сеансовых ключей в сетях универсальной системы мобильной связи (UMTS). AKA — это механизм, основанный на запросе-ответе и использующий симметричную криптографию. AKA обычно запускается в модуле идентификации служб IM UMTS (ISIM), который находится на устройстве, подобном смарт-карте, которое также обеспечивает защищенное от несанкционированного доступа хранение общих секретов. Этот документ определяет сопоставление параметров AKA с аутентификацией HTTP Digest. По сути, это сопоставление позволяет использовать AKA в качестве механизма генерации одноразового пароля для дайджест-аутентификации.
As the Session Initiation Protocol (SIP) [3] Authentication Framework closely follows the HTTP Authentication Framework, Digest AKA is directly applicable to SIP as well as any other embodiment of HTTP Digest.
Поскольку структура аутентификации протокола инициирования сессий (SIP) [3] тесно связана со структурой аутентификации HTTP, Digest AKA напрямую применим к SIP, а также к любому другому варианту HTTP Digest.

2. AKA Mechanism Overview
2. Обзор механизма АКА
This chapter describes the AKA operation in detail:
В этой главе подробно описывается работа AKA:
1. A shared secret K is established beforehand between the ISIM and the Authentication Center (AuC). The secret is stored in the ISIM, which resides on a smart card like, tamper resistant device.
1. Общий секрет K заранее устанавливается между ISIM и Центром аутентификации (AuC). Секрет хранится в ISIM, который находится на защищенном от несанкционированного доступа устройстве, напоминающем смарт-карту.
2. The AuC of the home network produces an authentication vector AV, based on the shared secret K and a sequence number SQN. The authentication vector contains a random challenge RAND, network authentication token AUTN, expected authentication result XRES, a session key for integrity check IK, and a session key for encryption CK.
2. AuC домашней сети создает вектор аутентификации AV на основе общего секрета K и порядкового номера SQN. Вектор аутентификации содержит случайный запрос RAND, сетевой токен аутентификации AUTN, ожидаемый результат аутентификации XRES, сеансовый ключ для проверки целостности IK и сеансовый ключ для шифрования CK.
3. The authentication vector is downloaded to a server. Optionally, the server can also download a batch of AVs, containing more than one authentication vector.
3. Вектор аутентификации загружается на сервер. При желании сервер также может загрузить пакет AV, содержащий более одного вектора аутентификации.
4. The server creates an authentication request, which contains the random challenge RAND, and the network authenticator token AUTN.
4. Сервер создает запрос аутентификации, который содержит случайный запрос RAND и токен сетевого аутентификатора AUTN.
5. The authentication request is delivered to the client.
5. Запрос аутентификации доставляется клиенту.
6. Using the shared secret K and the sequence number SQN, the client verifies the AUTN with the ISIM. If the verification is successful, the network has been authenticated. The client then produces an authentication response RES, using the shared secret K and the random challenge RAND.
6. Используя общий секрет K и порядковый номер SQN, клиент проверяет AUTN с помощью ISIM. Если проверка прошла успешно, сеть аутентифицирована. Затем клиент выдает ответ аутентификации RES, используя общий секрет K и случайный запрос RAND.
7. The authentication response, RES, is delivered to the server.
7. Ответ аутентификации RES доставляется на сервер.
8. The server compares the authentication response RES with the expected response, XRES. If the two match, the user has been successfully authenticated, and the session keys, IK and CK, can be used for protecting further communications between the client and the server.
8. Сервер сравнивает ответ аутентификации RES с ожидаемым ответом XRES. Если они совпадают, пользователь успешно аутентифицирован, а сеансовые ключи IK и CK можно использовать для защиты дальнейшего обмена данными между клиентом и сервером.
When verifying the AUTN, the client may detect that the sequence numbers between the client and the server have fallen out of sync. In this case, the client produces a synchronization parameter AUTS, using the shared secret K and the client sequence number SQN. The AUTS parameter is delivered to the network in the authentication response, and the authentication can be tried again based on authentication vectors generated with the synchronized sequence number.
При проверке AUTN клиент может обнаружить, что порядковые номера между клиентом и сервером не синхронизированы. В этом случае клиент создает параметр синхронизации AUTS, используя общий секрет K и порядковый номер клиента SQN. Параметр AUTS доставляется в сеть в ответе на аутентификацию, и аутентификацию можно повторить на основе векторов аутентификации, сгенерированных с помощью синхронизированного порядкового номера.
For a specification of the AKA mechanism and the generation of the cryptographic parameters AUTN, RES, IK, CK, and AUTS, see reference 3GPP TS 33.102 [6].
Подробную информацию о механизме AKA и генерации криптографических параметров AUTN, RES, IK, CK и AUTS см. в документе 3GPP TS 33.102 [6].
3. Specification of Digest AKA
3. Спецификация дайджеста АКА
In general, the Digest AKA operation is identical to the Digest operation in RFC 2617 [2]. This chapter specifies the parts in which Digest AKA extends the Digest operation. The notation used in the Augmented BNF definitions for the new and modified syntax elements in this section is as used in SIP [3], and any elements not defined in this section are as defined in SIP and the documents to which it refers.
В целом операция Digest AKA идентична операции Digest в RFC 2617 [2]. В этой главе указаны части, в которых Digest AKA расширяет операцию Digest. Обозначения, используемые в определениях расширенного BNF для новых и измененных элементов синтаксиса в этом разделе, аналогичны используемым в SIP [3], а любые элементы, не определенные в этом разделе, соответствуют определению в SIP и документах, к которым он относится.
3.1. Algorithm Directive
3.1. Директива алгоритма
In order to direct the client into using AKA for authentication instead of the standard password system, the RFC 2617 defined algorithm directive is overloaded in Digest AKA:
Чтобы направить клиента на использование AKA для аутентификации вместо стандартной системы паролей, определенная директива алгоритма RFC 2617 перегружается в Digest AKA:
algorithm = "algorithm" EQUAL ( aka-namespace / algorithm-value ) aka-namespace = aka-version "-" algorithm-value aka-version = "AKAv" 1*DIGIT algorithm-value = ( "MD5" / "MD5-sess" / token )
algorithm = "algorithm" EQUAL ( aka-namespace / algorithm-value ) aka-namespace = aka-version "-" algorithm-value aka-version = "AKAv" 1*DIGIT algorithm-value = ( "MD5" / "MD5-sess" / token )
algorithm
алгоритм
A string indicating the algorithm used in producing the digest and the checksum. If the directive is not understood, the nonce SHOULD be ignored, and another challenge (if one is present) should be used instead. The default aka-version is "AKAv1". Further AKA versions can be specified, with version numbers assigned by IANA [7]. When the algorithm directive is not present, it is assumed to be "MD5". This indicates, that AKA is not used to produce the Digest password. Example: algorithm=AKAv1-MD5 If the entropy of the used RES value is limited (e.g., only 32 bits), reuse of the same RES value in authenticating subsequent requests and responses is NOT RECOMMENDED. Such a RES value SHOULD only be used as a one-time password, and algorithms such as "MD5-sess", which limit the amount of material hashed with a single key, by producing a session key for authentication, SHOULD NOT be used.

3.2. Creating a Challenge
3.2. Создание вызова

Чтобы доставить запрос аутентификации AKA клиенту в Digest AKA, директива nonce, определенная в RFC 2617, расширяется:
nonce = "nonce" EQUAL ( aka-nonce / nonce-value ) aka-nonce = LDQUOT aka-nonce-value RDQUOT aka-nonce-value = <base64 encoding of RAND, AUTN, and server specific data>
nonce = "nonce" EQUAL ( aka-nonce / nonce-value ) aka-nonce = LDQUOT aka-nonce-value RDQUOT aka-nonce-value = <base64 encoding of RAND, AUTN, and server specific data>

If the server receives a client authentication containing the "auts" parameter defined in Section 3.4, that includes a valid AKA AUTS parameter, the server MUST use it to generate a new challenge to the client. Note that when the AUTS is present, the included "response" parameter is calculated using an empty password (password of ""), instead of a RES.
Если сервер получает аутентификацию клиента, содержащую параметр «auts», определенный в разделе 3.4, который включает действительный параметр AKA AUTS, сервер ДОЛЖЕН использовать его для генерации нового запроса клиенту. Обратите внимание, что при наличии AUTS включенный параметр «response» рассчитывается с использованием пустого пароля (пароля «») вместо RES.
3.3. Client Authentication
3.3. Аутентификация клиента
When a client receives a Digest AKA authentication challenge, it extracts the RAND and AUTN from the "nonce" parameter, and assesses the AUTN token provided by the server. If the client successfully authenticates the server with the AUTN, and determines that the SQN used in generating the challenge is within expected range, the AKA algorithms are run with the RAND challenge and shared secret K.
Когда клиент получает запрос аутентификации Digest AKA, он извлекает RAND и AUTN из параметра «nonce» и оценивает токен AUTN, предоставленный сервером. Если клиент успешно аутентифицирует сервер с помощью AUTN и определяет, что SQN, используемый при генерации запроса, находится в пределах ожидаемого диапазона, алгоритмы AKA запускаются с запросом RAND и общим секретом K.
The resulting AKA RES parameter is treated as a "password" when calculating the response directive of RFC 2617.
Результирующий параметр AKA RES обрабатывается как «password» при вычислении директивы ответа RFC 2617.
3.4. Synchronization Failure
3.4. Ошибка синхронизации
For indicating an AKA sequence number synchronization failure, and to re-synchronize the SQN in the AuC using the AUTS token, a new directive is defined for the "digest-response" of the "Authorization" request header defined in RFC 2617:
Для индикации сбоя синхронизации порядкового номера AKA и повторной синхронизации SQN в AuC с использованием токена AUTS определяется новая директива для «digest-response» заголовка запроса «Authorization», определенного в RFC 2617:
auts = "auts" EQUAL auts-param auts-param = LDQUOT auts-value RDQUOT auts-value = <base64 encoding of AUTS>
auts = "auts" EQUAL auts-param auts-param = LDQUOT auts-value RDQUOT auts-value = <base64 encoding of AUTS>
auts
ауты
A string carrying a base64 encoded AKA AUTS parameter. This directive is used to re-synchronize the server side SQN. If the directive is present, the client doesn't use any password when calculating its credentials. Instead, the client MUST calculate its credentials using an empty password (password of ""). Example: auts="CjkyMzRfOiwg5CfkJ2UK="
A string carrying a base64 encoded AKA AUTS parameter. This directive is used to re-synchronize the server side SQN. If the directive is present, the client doesn't use any password when calculating its credentials. Instead, the client MUST calculate its credentials using an empty password (password of ""). Example: auts="CjkyMzRfOiwg5CfkJ2UK="
Upon receiving the "auts" parameter, the server will check the validity of the parameter value using the shared secret K. A valid AUTS parameter is used to re-synchronize the SQN in the AuC. The synchronized SQN is then used to generate a fresh authentication vector AV, with which the client is then re-challenged.
После получения параметра «auts» сервер проверит достоверность значения параметра, используя общий секрет K. Действительный параметр AUTS используется для повторной синхронизации SQN в AuC. Синхронизированный SQN затем используется для генерации нового вектора аутентификации AV, с помощью которого клиент затем повторно запрашивается.
3.5. Server Authentication
3.5. Аутентификация сервера
Even though AKA provides inherent mutual authentication with the AKA AUTN token, mutual authentication mechanisms provided by Digest may still be useful in order to provide message integrity.
Несмотря на то, что AKA обеспечивает внутреннюю взаимную аутентификацию с помощью токена AKA AUTN, механизмы взаимной аутентификации, предоставляемые Digest, по-прежнему могут быть полезны для обеспечения целостности сообщений.
In Digest AKA, the server uses the AKA XRES parameter as "password" when calculating the "response-auth" of the "Authentication-Info" header defined in RFC 2617.
В Digest AKA сервер использует параметр AKA XRES как «password» при вычислении «response-auth» заголовка «Authentication-Info», определенного в RFC 2617.

5. Security Considerations
5. Вопросы безопасности
In general, Digest AKA is vulnerable to the same security threats as HTTP authentication [2]. This chapter discusses the relevant exceptions.
В целом Digest AKA уязвим для тех же угроз безопасности, что и аутентификация HTTP [2]. В этой главе обсуждаются соответствующие исключения.
5.1. Authentication of Clients using Digest AKA
5.1. Аутентификация клиентов с помощью Digest AKA
AKA is typically -- though this isn't a theoretical limitation -- run on an ISIM application that usually resides in a tamper resistant smart card. Interfaces to the ISIM exist, which enable the host device to request authentication to be performed on the card. However, these interfaces do not allow access to the long-term secret outside the ISIM, and the authentication can only be performed if the device accessing the ISIM has knowledge of a PIN code, shared between the user and the ISIM. Such PIN codes are typically obtained from user input, and are usually required when the device is powered on.
AKA обычно (хотя это не теоретическое ограничение) запускается в приложении ISIM, которое обычно находится на защищенной от несанкционированного доступа смарт-карте. Существуют интерфейсы ISIM, которые позволяют главному устройству запрашивать аутентификацию на карте. Однако эти интерфейсы не обеспечивают доступ к долгосрочному секрету за пределами ISIM, и аутентификация может быть выполнена только в том случае, если устройство, обращающееся к ISIM, знает PIN-код, общий для пользователя и ISIM. Такие PIN-коды обычно получаются в результате ввода пользователя и обычно требуются при включении устройства.
The use of tamper resistant cards with secure interfaces implies that Digest AKA is typically more secure than regular Digest implementations, as neither possession of the host device nor Trojan Horses in the software give access to the long term secret. Where a PIN scheme is used, the user is also authenticated when the device is powered on. However, there may be a difference in the resulting security of Digest AKA, compared to traditional Digest implementations, depending of course on whether those implementations cache/store passwords that are received from the user.
Использование защищенных от несанкционированного доступа карт с защищенными интерфейсами означает, что Digest AKA обычно более безопасен, чем обычные реализации Digest, поскольку ни владение хост-устройством, ни троянские кони в программном обеспечении не дают доступа к долгосрочному секрету. Если используется схема PIN-кода, пользователь также проходит аутентификацию при включении устройства. Однако может быть разница в итоговой безопасности Digest AKA по сравнению с традиционными реализациями Digest, в зависимости, конечно, от того, кэшируют ли эти реализации/хранят ли пароли, полученные от пользователя.
5.2. Limited Use of Nonce Values
5.2. Ограниченное использование значений Nonce
The Digest scheme uses server-specified nonce values to seed the generation of the request-digest value. The server is free to construct the nonce in such a way, that it may only be used from a particular client, for a particular resource, for a limited period of time or number of uses, or any other restrictions. Doing so strengthens the protection provided against, for example, replay attacks.
Схема дайджеста использует значения nonce, указанные сервером, для создания начального значения дайджеста запроса. Сервер может сконструировать одноразовый номер таким образом, чтобы его можно было использовать только от конкретного клиента, для определенного ресурса, в течение ограниченного периода времени или количества использований или любых других ограничений. Это усиливает защиту, обеспечиваемую, например, от атак повторного воспроизведения.
Digest AKA limits the applicability of a nonce value to a particular ISIM. Typically, the ISIM is accessible only to one client device at a time. However, the nonce values are strong and secure even though limited to a particular ISIM. Additionally, this requires that the server is provided with the client identity before an authentication challenge can be generated. If a client identity is not available, an additional round trip is needed to acquire it. Such a case is analogous to an AKA synchronization failure.
Digest AKA ограничивает применимость значения nonce к конкретному ISIM. Обычно ISIM доступен только одному клиентскому устройству одновременно. Однако значения nonce являются надежными и безопасными, даже если они ограничены конкретным ISIM. Кроме того, для этого необходимо, чтобы серверу были предоставлены идентификационные данные клиента, прежде чем можно будет сгенерировать запрос аутентификации. Если удостоверение клиента недоступно, для его получения потребуется дополнительная поездка туда и обратно. Такой случай аналогичен сбою синхронизации AKA.
A server may allow each nonce value to be used only once by sending a next-nonce directive in the Authentication-Info header field of every response. However, this may cause a synchronization failure, and consequently some additional round trips in AKA, if the same SQN space is also used for other access schemes at the same time.
Сервер может разрешить использование каждого значения nonce только один раз, отправив директиву next-nonce в поле заголовка Authentication-Info каждого ответа. Однако это может привести к сбою синхронизации и, следовательно, к некоторым дополнительным двусторонним проходам в AKA, если одно и то же пространство SQN одновременно используется для других схем доступа.
5.3. Multiple Authentication Schemes and Algorithms
5.3. Множественные схемы и алгоритмы аутентификации
In HTTP authentication, a user agent MUST choose the strongest authentication scheme it understands and request credentials from the user, based upon that challenge.
При аутентификации HTTP пользовательский агент ДОЛЖЕН выбрать самую надежную схему аутентификации, которую он понимает, и запросить учетные данные у пользователя на основе этого запроса.
In general, using passwords generated by Digest AKA with other HTTP authentication schemes is not recommended even though the realm values or protection domains would coincide. In these cases, a password should be requested from the end-user instead. Digest AKA passwords MUST NOT be re-used with such HTTP authentication schemes, which send the password in clear. In particular, AKA passwords MUST NOT be re-used with HTTP Basic.
В общем, использование паролей, сгенерированных Digest AKA, с другими схемами аутентификации HTTP не рекомендуется, даже если значения области или домены защиты совпадают. В этих случаях вместо этого пароль следует запросить у конечного пользователя. Пароли Digest AKA НЕ ДОЛЖНЫ повторно использоваться с такими схемами аутентификации HTTP, которые отправляют пароль в открытом виде. В частности, пароли AKA НЕ ДОЛЖНЫ повторно использоваться с HTTP Basic.
The same principle must be applied within a scheme if several algorithms are supported. A client receiving an HTTP Digest challenge with several available algorithms MUST choose the strongest algorithm it understands. For example, Digest with "AKAv1-MD5" would be stronger than Digest with "MD5".
Тот же принцип должен применяться в схеме, если поддерживается несколько алгоритмов. Клиент, получающий запрос HTTP-дайджеста с несколькими доступными алгоритмами, ДОЛЖЕН выбрать самый сильный алгоритм, который он понимает. Например, дайджест с «AKAv1-MD5» будет более надежным, чем дайджест с «MD5».
5.4. Online Dictionary Attacks
5.4. Атаки онлайн-словарей
Since user-selected passwords are typically quite simple, it has been proposed that servers should not accept passwords for HTTP Digest, which are in the dictionary [2]. This potential threat does not exist in HTTP Digest AKA because the algorithm will use ISIM originated passwords. However, the end-user must still be careful with PIN codes. Even though HTTP Digest AKA password requests are never displayed to the end-user, she will be authenticated to the ISIM via a PIN code. Commonly known initial PIN codes are typically installed to the ISIM during manufacturing and if the end-users do not change them, there is a danger that an unauthorized user may be able to use the device. Naturally this requires that the unauthorized user has access to the physical device, and that the end-user has not changed the initial PIN code. For this reason, end-users are strongly encouraged to change their PIN codes when they receive an ISIM.
Поскольку пароли, выбираемые пользователем, обычно довольно просты, было предложено, чтобы серверы не принимали пароли для HTTP Digest, которые находятся в словаре [2]. Эта потенциальная угроза не существует в HTTP Digest AKA, поскольку алгоритм будет использовать пароли, созданные ISIM. Однако конечный пользователь все равно должен быть осторожен с PIN-кодами. Несмотря на то, что запросы пароля HTTP Digest AKA никогда не отображаются конечному пользователю, он будет аутентифицирован в ISIM с помощью PIN-кода. Общеизвестные начальные PIN-коды обычно устанавливаются в ISIM во время производства, и если конечные пользователи не изменят их, существует опасность того, что неавторизованный пользователь сможет использовать устройство. Естественно, для этого необходимо, чтобы неавторизованный пользователь имел доступ к физическому устройству и чтобы конечный пользователь не менял первоначальный PIN-код. По этой причине конечным пользователям настоятельно рекомендуется менять свои PIN-коды при получении ISIM.
5.5. Session Protection
5.5. Защита сессии
Digest AKA is able to generate additional session keys for integrity (IK) and confidentiality (CK) protection. Even though this document does not specify the use of these additional keys, they may be used for creating additional security within HTTP authentication or some other security mechanism.
Digest AKA может генерировать дополнительные сеансовые ключи для защиты целостности (IK) и конфиденциальности (CK). Несмотря на то, что в этом документе не указано использование этих дополнительных ключей, они могут использоваться для создания дополнительной безопасности в рамках аутентификации HTTP или какого-либо другого механизма безопасности.
5.6. Replay Protection
5.6. Защита от повтора
AKA allows sequence numbers to be tracked for each authentication, with the SQN parameter. This allows authentications to be replay protected even if the RAND parameter happened to be the same for two authentication requests. More importantly, this offers additional protection for the case where an attacker replays an old authentication request sent by the network. The client will be able to detect that the request is old, and refuse authentication. This proves liveliness of the authentication request even in the case where a MitM attacker tries to trick the client into providing an authentication response, and then replaces parts of the message with something else. In other words, a client challenged by Digest AKA is not vulnerable for chosen plain text attacks. Finally, frequent sequence number errors would reveal an attack where the tamper resistant card has been cloned and is being used in multiple devices.
AKA позволяет отслеживать порядковые номера для каждой аутентификации с помощью параметра SQN. Это позволяет защитить аутентификацию от повтора, даже если параметр RAND оказался одинаковым для двух запросов аутентификации. Что еще более важно, это обеспечивает дополнительную защиту в случае, если злоумышленник воспроизводит старый запрос аутентификации, отправленный сетью. Клиент сможет обнаружить, что запрос устарел, и отказаться от аутентификации. Это доказывает живость запроса аутентификации даже в том случае, когда злоумышленник MitM пытается обманом заставить клиента предоставить ответ аутентификации, а затем заменяет части сообщения чем-то другим. Другими словами, клиент, подвергшийся атаке с помощью Digest AKA, не уязвим для выбранных атак с использованием простого текста. Наконец, частые ошибки в порядковых номерах могут указывать на атаку, при которой защищенная от несанкционированного доступа карта была клонирована и используется в нескольких устройствах.
The downside of sequence number tracking is that servers must hold more information for each user than just their long-term secret, namely the current SQN value. However, this information is typically not stored in the SIP nodes, but in dedicated authentication servers instead.
Недостатком отслеживания порядковых номеров является то, что серверы должны хранить больше информации о каждом пользователе, чем просто его долгосрочный секрет, а именно текущее значение SQN. Однако эта информация обычно хранится не на узлах SIP, а на выделенных серверах аутентификации.
5.7. Improvements to AKA Security
5.7. Улучшения в системе безопасности AKA
Even though AKA is perceived as a secure mechanism, Digest AKA is able to improve it. More specifically, the AKA parameters carried between the client and the server during authentication may be protected along with other parts of the message by using Digest AKA. This is not possible with plain AKA.
Несмотря на то, что AKA считается безопасным механизмом, Digest AKA способен его улучшить. Более конкретно, параметры AKA, передаваемые между клиентом и сервером во время аутентификации, могут быть защищены вместе с другими частями сообщения с помощью Digest AKA. Это невозможно с простым AKA.
6. IANA Considerations
6. Вопросы IANA
This document specifies an aka-version namespace in Section 3.1 which requires a central coordinating body. The body responsible for this coordination is the Internet Assigned Numbers Authority (IANA).
В разделе 3.1 этого документа указано пространство имен aka-version, для которого требуется центральный координирующий орган. Органом, ответственным за эту координацию, является Управление по присвоению номеров Интернета (IANA).
The default aka-version defined in this document is "AKAv1". Following the policies outlined in [5], versions above 1 are allocated as Expert Review.
Версия по умолчанию, определенная в этом документе, — «AKAv1». В соответствии с политикой, изложенной в [5], версии выше 1 выделяются как экспертная оценка.
Registrations with the IANA MUST include the version number being registered, including the "AKAv" prefix. For example, a registration for "AKAv2" would potentially be a valid one, whereas a registration for "FOOv2" or "2" would not be valid. Further, the registration MUST include contact information for the party responsible for the registration. As this document defines the default aka-version, the initial IANA registration for aka-version values will contain an entry for "AKAv1".
Регистрации в IANA ДОЛЖНЫ включать номер регистрируемой версии, включая префикс «AKAv». Например, регистрация для «AKAv2» потенциально может быть действительной, тогда как регистрация для «FOOv2» или «2» недействительна. Кроме того, регистрация ДОЛЖНА включать контактную информацию лица, ответственного за регистрацию. Поскольку в этом документе определяется версия aka по умолчанию, первоначальная регистрация IANA для значений aka-версии будет содержать запись для «AKAv1».
