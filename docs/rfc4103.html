Abstract
Аннотация
This memo obsoletes RFC 2793; it describes how to carry real-time text conversation session contents in RTP packets. Text conversation session contents are specified in ITU-T Recommendation T.140.
Настоящий меморандум отменяет RFC 2793; он описывает, как передавать содержимое сеанса текстового разговора в пакетах RTP. Содержимое сеанса текстового разговора определено в Рекомендации ITU-T T.140.
One payload format is described for transmitting text on a separate RTP session dedicated for the transmission of text.
Описывается один формат полезной нагрузки для передачи текста в отдельном сеансе RTP, выделенном для передачи текста.
This RTP payload description recommends a method to include redundant text from already transmitted packets in order to reduce the risk of text loss caused by packet loss.
Настоящее описание полезной нагрузки RTP рекомендует метод включения избыточного текста из уже переданных пакетов для снижения риска потери текста из-за потери пакетов.
1. Introduction
1. Введение
This document defines a payload type for carrying text conversation session contents in RTP [2] packets. Text conversation session contents are specified in ITU-T Recommendation T.140 [1]. Text conversation is used alone or in connection with other conversational facilities, such as video and voice, to form multimedia conversation services. Text in multimedia conversation sessions is sent character-by-character as soon as it is available, or with a small delay for buffering.
Настоящий документ определяет тип полезной нагрузки для передачи содержимого сеанса текстового разговора в пакетах RTP [2]. Содержимое сеанса текстового разговора определено в Рекомендации ITU-T T.140 [1]. Текстовый разговор используется самостоятельно или вместе с другими средствами разговора, такими как видео и голос, образуя службы мультимедийного разговора. Текст в сеансах мультимедийного разговора отправляется посимвольно, как только он становится доступен, либо с небольшой задержкой на буферизацию.
The text is intended to be entered by human users from a keyboard, handwriting recognition, voice recognition or any other input method. The rate of character entry is usually at a level of a few characters per second or less. In general, only one or a few new characters are expected to be transmitted with each packet. Small blocks of text may be prepared by the user and pasted into the user interface for transmission during the conversation, occasionally causing packets to carry more payload.
Текст предназначен для ввода человеческими пользователями с клавиатуры, средства распознавания рукописного ввода, распознавания речи или любого иного способа ввода. Скорость ввода символов обычно составляет несколько символов в секунду или меньше. Как правило, с каждым пакетом предполагается передавать только один или несколько новых символов. Пользователь может подготовить небольшие блоки текста и вставить их в пользовательский интерфейс для передачи во время разговора, что иногда приводит к тому, что пакеты несут больше полезной нагрузки.
T.140 specifies that text and other T.140 elements must be transmitted in ISO 10646-1 [5] code with UTF-8 [6] transformation. This makes it easy to implement internationally useful applications and to handle the text in modern information technology environments. The payload of an RTP packet that follows this specification consists of text encoded according to T.140, without any additional framing. A common case will be a single ISO 10646 character, UTF-8 encoded.
T.140 требует, чтобы текст и другие элементы T.140 передавались в коде ISO 10646-1 [5] с преобразованием UTF-8 [6]. Это упрощает реализацию международно пригодных приложений и обработку текста в современных средах информационных технологий. Полезная нагрузка пакета RTP, следующего настоящей спецификации, состоит из текста, закодированного согласно T.140, без какого-либо дополнительного кадрирования. Обычным случаем будет одиночный символ ISO 10646, закодированный в UTF-8.
T.140 requires the transport channel to provide characters without duplication and in original order. Text conversation users expect that text will be delivered with no, or a low level, of lost information.
T.140 требует, чтобы транспортный канал обеспечивал передачу символов без дублирования и в исходном порядке. Пользователи текстового разговора ожидают, что текст будет доставляться без потери информации или с низким уровнем потерь.
Therefore, a mechanism based on RTP is specified here. It gives text arrival in correct order, without duplication, and with detection and indication of loss. It also includes an optional possibility to repeat data for redundancy in order to lower the risk of loss. Because packet overhead is usually much larger than the T.140 contents, the increase in bandwidth, with the use of redundancy, is minimal.
Поэтому здесь определяется механизм, основанный на RTP. Он обеспечивает поступление текста в правильном порядке, без дублирования и с обнаружением и индикацией потерь. Он также включает необязательную возможность повторения данных для избыточности, чтобы снизить риск потери. Поскольку накладные расходы пакета обычно намного больше, чем содержимое T.140, увеличение полосы пропускания при использовании избыточности минимально.
By using RTP for text transmission in a multimedia conversation application, uniform handling of text and other media can be achieved in, for example, conferencing systems, firewalls, and network translation devices. This, in turn, eases the design and increases the possibility for prompt and proper media delivery. This document obsoletes RFC 2793 [16]. The text clarifies ambiguities in RFC 2793, improves on the specific implementation requirements learned through development experience and gives explicit usage examples.
Используя RTP для передачи текста в приложении мультимедийного разговора, можно достичь единообразной обработки текста и других медиа, например, в системах конференций, межсетевых экранах и устройствах трансляции сетевых адресов. Это, в свою очередь, упрощает проектирование и повышает возможность быстрой и правильной доставки медиа. Настоящий документ отменяет RFC 2793 [16]. Текст устраняет неоднозначности RFC 2793, улучшает конкретные требования к реализации, полученные из опыта разработки, и приводит явные примеры использования.

3. Usage of RTP
3. Использование RTP
The payload format for real-time text transmission with RTP [2] described in this memo is intended for general text conversation use and is called text/t140 after its MIME registration.
Формат полезной нагрузки для передачи текста в реальном времени с помощью RTP [2], описанный в настоящем меморандуме, предназначен для общего использования в текстовом разговоре и называется text/t140 по его регистрации MIME.
3.1. Motivations and Rationale
3.1. Мотивации и обоснование
The text/t140 format is intended to be used for text transmitted on a separate RTP session, dedicated for the transmission of text, and not shared with other media.
Формат text/t140 предназначен для использования при передаче текста в отдельном сеансе RTP, выделенном для передачи текста и не разделяемом с другими медиа.
The text/t140 format MAY be used for any non-gateway application, as well as in gateways. It MAY be used simultaneously with other media streams, transmitted as a separate RTP session, as required in real time multimedia applications.
Формат text/t140 МОЖЕТ использоваться для любого приложения, не являющегося шлюзом, а также в шлюзах. Он МОЖЕТ использоваться одновременно с другими медиапотоками, передаваемыми как отдельный сеанс RTP, как требуется в мультимедийных приложениях реального времени.
The text/t140 format specified in this memo is compatible with its earlier definition in RFC 2793. It has been refined, with the main intention to minimize interoperability problems and encourage good reliability and functionality.
Формат text/t140, определённый в настоящем меморандуме, совместим с его более ранним определением в RFC 2793. Он был усовершенствован главным образом с целью минимизировать проблемы совместимости и повысить надёжность и функциональность.
By specifying text transmission as a text medium, many good effects are gained. Routing, device selection, invocation of transcoding, selection of quality of service parameters, and other high and low level functions depend on each medium being explicitly specified.
Определяя передачу текста как текстовую среду, мы получаем много полезных эффектов. Маршрутизация, выбор устройства, запуск перекодирования, выбор параметров качества обслуживания и другие функции высокого и низкого уровней зависят от того, что каждая среда явно определена.
3.2. Payload Format for Transmission of text/t140 Data
3.2. Формат полезной нагрузки для передачи данных text/t140
A text/t140 conversation RTP payload format consists of one, and only one, block of T.140 data, referred to as a "T140block" (see Section 3.3). There are no additional headers specific to this payload format. The fields in the RTP header are set as defined in Section 3.5, carried in network byte order (see RFC 791 [12]).
Формат полезной нагрузки RTP для разговора text/t140 состоит из одного и только одного блока данных T.140, называемого «T140block» (см. раздел 3.3). Дополнительных заголовков, специфичных для этого формата полезной нагрузки, нет. Поля в заголовке RTP устанавливаются, как определено в разделе 3.5, и передаются в сетевом порядке байтов (см. RFC 791 [12]).
3.3. The "T140block"
3.3. «T140block»
T.140 text is UTF-8 coded, as specified in T.140, with no extra framing. The T140block contains one or more T.140 code elements as specified in [1]. Most T.140 code elements are single ISO 10646 [5] characters, but some are multiple character sequences. Each character is UTF-8 encoded [6] into one or more octets. Each block MUST contain an integral number of UTF-8 encoded characters regardless of the number of octets per character. Any composite character sequence (CCS) SHOULD be placed within one block.
Текст T.140 кодируется в UTF-8, как указано в T.140, без дополнительного кадрирования. T140block содержит один или несколько элементов кода T.140, как указано в [1]. Большинство элементов кода T.140 — отдельные символы ISO 10646 [5], но некоторые представляют собой последовательности из нескольких символов. Каждый символ кодируется в UTF-8 [6] в один или несколько октетов. Каждый блок ДОЛЖЕН содержать целое число символов, закодированных в UTF-8, независимо от числа октетов на символ. Любую последовательность составного символа (composite character sequence, CCS) СЛЕДУЕТ размещать в пределах одного блока.
3.4. Synchronization of Text with Other Media
3.4. Синхронизация текста с другими медиа
Usually, each medium in a session utilizes a separate RTP stream. As such, if synchronization of the text and other media packets is important, the streams MUST be associated when the sessions are established and the streams MUST share the same reference clock (refer to the description of the timestamp field as it relates to synchronization in Section 5.1 of RFC 3550 [2]). Association of RTP streams can be done through the CNAME field of RTCP SDES function. It is dependent on the particular application and is outside the scope of this document.
Обычно каждая среда в сеансе использует отдельный поток RTP. Поэтому, если синхронизация текста и других медиапакетов важна, потоки ДОЛЖНЫ быть связаны при установлении сеансов и ДОЛЖНЫ использовать одни и те же опорные часы (см. описание поля отметки времени в связи с синхронизацией в разделе 5.1 RFC 3550 [2]). Связывание потоков RTP может выполняться через поле CNAME функции RTCP SDES. Это зависит от конкретного приложения и выходит за рамки настоящего документа.
3.5. RTP Packet Header
3.5. Заголовок пакета RTP
Each RTP packet starts with a fixed RTP header. The following fields of the RTP fixed header are specified for T.140 text streams:
Каждый пакет RTP начинается с фиксированного заголовка RTP. Для текстовых потоков T.140 определены следующие поля фиксированного заголовка RTP:
Payload Type (PT): The assignment of an RTP payload type is specific to the RTP profile under which the payload format is used. For profiles that use dynamic payload type number assignment, this payload format can be identified by the MIME type "text/t140" (see Section 10). If redundancy is used per RFC 2198, another payload type number needs to be provided for the redundancy format. The MIME type for identifying RFC 2198 is available in RFC 4102 [9].
Тип полезной нагрузки (PT): назначение типа полезной нагрузки RTP зависит от профиля RTP, в рамках которого используется формат полезной нагрузки. Для профилей, использующих динамическое назначение номеров типов полезной нагрузки, этот формат полезной нагрузки может быть идентифицирован по MIME-типу «text/t140» (см. раздел 10). Если избыточность используется согласно RFC 2198, для формата избыточности необходимо предоставить другой номер типа полезной нагрузки. MIME-тип для идентификации RFC 2198 доступен в RFC 4102 [9].
Sequence number: The definition of sequence numbers is available in RFC 3550 [2]. When transmitting text using the payload format for text/t140, it is used for detection of packet loss and out-of-order packets, and can be used in the process of retrieval of redundant text, reordering of text and marking missing text.
Порядковый номер: определение порядковых номеров доступно в RFC 3550 [2]. При передаче текста с использованием формата полезной нагрузки text/t140 он используется для обнаружения потери пакетов и пакетов, пришедших не по порядку, а также может использоваться в процессе восстановления избыточного текста, переупорядочивания текста и маркировки отсутствующего текста.
Timestamp: The RTP Timestamp encodes the approximate instance of entry of the primary text in the packet. A clock frequency of 1000 Hz MUST be used. Sequential packets MUST NOT use the same timestamp. Because packets do not represent any constant duration, the timestamp cannot be used to directly infer packet loss.
Отметка времени: отметка времени RTP кодирует приблизительный момент ввода основного текста в пакет. ДОЛЖНА использоваться тактовая частота 1000 Гц. Последовательные пакеты НЕ ДОЛЖНЫ использовать одну и ту же отметку времени. Поскольку пакеты не представляют никакой постоянной длительности, отметка времени не может использоваться для непосредственного вывода о потере пакетов.
M-bit: The M-bit MUST be included. The first packet in a session, and the first packet after an idle period, SHOULD be distinguished by setting the marker bit in the RTP data header to one. The marker bit in all other packets MUST be set to zero. The reception of the marker bit MAY be used for refined methods for detection of loss.
M-бит: M-бит ДОЛЖЕН быть включён в каждый пакет. Первый пакет в сеансе, а также первый пакет после периода простоя СЛЕДУЕТ отличать путём установки маркерного бита в заголовке данных RTP равным единице. Во всех остальных пакетах маркерный бит ДОЛЖЕН быть установлен равным нулю. Приём маркерного бита МОЖЕТ также использоваться для реализации уточнённых методов обнаружения возможной потери текста в принимаемом потоке.
4. Protection against Loss of Data
4. Защита от потери данных
Consideration must be devoted to keeping loss of text due to packet loss within acceptable limits. (See ITU-T F.703 [17])
Необходимо уделять внимание тому, чтобы потери текста из-за потери пакетов оставались в приемлемых пределах. (См. ITU-T F.703 [17])
The default method that MUST be used, when no other method is explicitly selected, is redundancy in accordance with RFC 2198 [3]. When this method is used, the original text and two redundant generations SHOULD be transmitted if the application or end-to-end conditions do not call for other levels of redundancy to be used.
Методом по умолчанию, который ДОЛЖЕН использоваться, когда явно не выбран другой метод, является избыточность в соответствии с RFC 2198 [3]. При использовании этого метода СЛЕДУЕТ передавать исходный текст и два избыточных поколения, если условия приложения или сквозные условия не требуют использования других уровней избыточности.
Forward Error Correction mechanisms, as per RFC 2733 [8], or any other mechanism with the purpose of increasing the reliability of text transmission, MAY be used as an alternative or complement to redundancy. Text data MAY be sent without additional protection if end-to-end network conditions allow the text quality requirements, specified in ITU-T F.703 [17], to be met in all anticipated load conditions.
Механизмы упреждающей коррекции ошибок (Forward Error Correction) согласно RFC 2733 [8] или любой другой механизм, целью которого является повышение надёжности передачи текста, МОГУТ использоваться как альтернатива избыточности или дополнение к ней. Текстовые данные МОГУТ передаваться без дополнительной защиты, если сквозные сетевые условия позволяют выполнить требования к качеству текста, указанные в ITU-T F.703 [17], при всех предполагаемых условиях нагрузки.
4.1. Payload Format When Using Redundancy
4.1. Формат полезной нагрузки при использовании избыточности
When using the payload format with redundant data, the transmitter may select a number of T140block generations to retransmit in each packet. A higher number introduces better protection against loss of text but marginally increases the data rate.
При использовании формата полезной нагрузки с избыточными данными передатчик может выбрать число поколений T140block для повторной передачи в каждом пакете. Более высокое число обеспечивает лучшую защиту от потери текста, но незначительно увеличивает скорость передачи данных.
The RTP header is followed by one or more redundant data block headers: one for each redundant data block to be included. Each of these headers provides the timestamp offset and length of the corresponding data block, in addition to a payload type number (indicating the payload format text/t140). The redundant data block headers are followed by the redundant data fields carrying T140blocks from previous packets. Finally, the new (primary) T140block for this packet follows.
За заголовком RTP следует один или несколько заголовков блоков избыточных данных: по одному для каждого включаемого блока избыточных данных. Каждый из этих заголовков содержит смещение отметки времени и длину соответствующего блока данных, а также номер типа полезной нагрузки (указывающий формат полезной нагрузки text/t140). За заголовками блоков избыточных данных следуют поля избыточных данных, несущие T140block из предыдущих пакетов. Наконец, следует новый (основной) T140block для этого пакета.
Redundant data that would need a timestamp offset higher than 16383 (due to its age at transmission) MUST NOT be included in transmitted packets.
Избыточные данные, для которых требуется смещение отметки времени больше 16383 (из-за их возраста при передаче), НЕ ДОЛЖНЫ включаться в передаваемые пакеты.
4.2. Using Redundancy with the text/t140 Format
4.2. Использование избыточности с форматом text/t140
Because text is transmitted only when there is text to transmit, the timestamp is not used to identify a lost packet. Rather, missing sequence numbers are used to detect lost text packets at reception. Also, because sequence numbers are not provided in the redundant header, some additional rules must be followed to allow redundant data that corresponds to missing primary data to be properly merged into the stream of primary data T140blocks. They are:
Поскольку текст передаётся только тогда, когда есть текст для передачи, отметка времени не используется для идентификации потерянного пакета. Вместо этого для обнаружения потерянных текстовых пакетов при приёме используются пропуски в порядковых номерах. Кроме того, поскольку порядковые номера не предоставляются в заголовке избыточности, необходимо соблюдать некоторые дополнительные правила, чтобы избыточные данные, соответствующие отсутствующим основным данным, могли быть должным образом объединены в поток T140block основных данных. Они таковы:
- Each redundant data block MUST contain the same data as a T140block previously transmitted as primary data.
- Каждый блок избыточных данных ДОЛЖЕН содержать те же данные, что и T140block, ранее переданный в качестве основных данных.
- The redundant data MUST be placed in age order, with the most recent redundant T140block last in the redundancy area.
- Избыточные данные ДОЛЖНЫ размещаться в порядке возраста, причём самый последний избыточный T140block должен быть последним в области избыточности.
- All T140blocks, from the oldest desired generation up through the generation immediately preceding the new (primary) T140block, MUST be included.
- Все T140block, от самого старого требуемого поколения до поколения, непосредственно предшествующего новому (основному) T140block, ДОЛЖНЫ быть включены.
These rules allow the sequence numbers for the redundant T140blocks to be inferred by counting backwards from the sequence number in the RTP header. The result will be that all the text in the payload will be contiguous and in order.
Эти правила позволяют вывести порядковые номера для избыточных T140block обратным отсчётом от порядкового номера в заголовке RTP. В результате весь текст в полезной нагрузке будет непрерывным и упорядоченным.
If there is a gap in the received RTP sequence numbers, and redundant T140blocks are available in a subsequent packet, the sequence numbers for the redundant T140blocks should be inferred by counting backwards from the sequence number in the RTP header for that packet. If there are redundant T140blocks with sequence numbers matching those that are missing, the redundant T140blocks may be substituted for the missing T140blocks.
Если в принятых порядковых номерах RTP имеется пропуск и избыточные T140block доступны в последующем пакете, порядковые номера для избыточных T140block следует выводить обратным отсчётом от порядкового номера в заголовке RTP этого пакета. Если имеются избыточные T140block с порядковыми номерами, совпадающими с отсутствующими, избыточные T140block могут быть подставлены вместо отсутствующих T140block.
5. Recommended Procedure
5. Рекомендуемая процедура
This section contains RECOMMENDED procedures for usage of the payload format. Based on the information in the received packets, the receiver can:
Настоящий раздел содержит РЕКОМЕНДУЕМЫЕ процедуры использования формата полезной нагрузки. На основе информации в принятых пакетах приёмник может:
- reorder text received out of order.
- переупорядочивать текст, принятый не по порядку;
- mark where text is missing because of packet loss.
- помечать места, где текст отсутствует из-за потери пакетов;
- compensate for lost packets by using redundant data.
- компенсировать потерянные пакеты с помощью избыточных данных.
5.1. Recommended Basic Procedure
5.1. Рекомендуемая базовая процедура
Packets are transmitted when there is valid T.140 data to transmit.
Пакеты передаются, когда есть допустимые данные T.140 для передачи.
T.140 specifies that T.140 data MAY be buffered for transmission with a maximum buffering time of 500 ms. A buffering time of 300 ms is RECOMMENDED when the application or end-to-end network conditions are not known to require another value.
T.140 предусматривает, что данные T.140 МОГУТ буферизоваться для передачи с максимальным временем буферизации 500 мс. РЕКОМЕНДУЕТСЯ время буферизации 300 мс, когда не известно, что условия приложения или сквозной сети требуют другого значения.
If no new data is available for a longer period than the buffering time, the transmission process is in an idle period.
Если новые данные недоступны в течение периода, превышающего время буферизации, процесс передачи находится в периоде простоя.
When new text is available for transmission after an idle period, it is RECOMMENDED to send it as soon as possible. After this transmission, it is RECOMMENDED to buffer T.140 data in buffering time intervals, until the next idle period. This is done in order to keep the maximum bit rate usage for text at a reasonable level. The buffering time MUST be selected so that text users will perceive a real-time text flow.
Когда после периода простоя появляется новый текст для передачи, РЕКОМЕНДУЕТСЯ отправить его как можно скорее. После этой передачи РЕКОМЕНДУЕТСЯ буферизовать данные T.140 через интервалы времени буферизации до следующего периода простоя. Это делается для того, чтобы максимальное использование битовой скорости для текста оставалось на разумном уровне. Время буферизации ДОЛЖНО выбираться так, чтобы пользователи текста воспринимали поток текста как реальный.
5.2. Transmission before and after "Idle Periods"
5.2. Передача до и после «периодов простоя»
When valid T.140 data has been sent and no new T.140 data is available for transmission after the selected buffering time, an empty T140block SHOULD be transmitted. This situation is regarded as the beginning of an idle period. The procedure is recommended in order to more rapidly detect potentially missing text before an idle period.
Когда допустимые данные T.140 были отправлены и после выбранного времени буферизации новые данные T.140 для передачи отсутствуют, СЛЕДУЕТ передать пустой T140block. Эта ситуация рассматривается как начало периода простоя. Процедура рекомендуется для более быстрого обнаружения потенциально отсутствующего текста перед периодом простоя.
An empty T140block contains no data.
Пустой T140block не содержит данных.
When redundancy is used, transmission continues with a packet at every transmission timer expiration and insertion of an empty T.140block as primary, until the last non-empty T140block has been transmitted, as primary and as redundant data, with all intended generations of redundancy. The last packet before an idle period will contain only one non-empty T140block as redundant data, while the remainder of the redundancy packet will contain empty T140blocks. Any empty T140block sent as primary data MUST be included as redundant T140blocks in subsequent packets, just as normal text T140blocks would be, unless the empty T140block is too old to be transmitted. This is done so that sequence number inference for the redundant T140blocks will be correct, as explained in Section 4.2.
При использовании избыточности передача продолжается путём отправки пакета при каждом срабатывании таймера передачи и вставки пустого T.140block в качестве основного до тех пор, пока последний непустой T140block не будет передан как основные и как избыточные данные со всеми предусмотренными поколениями избыточности. Последний пакет перед периодом простоя будет содержать только один непустой T140block в качестве избыточных данных, тогда как остальная часть пакета избыточности будет содержать пустые T140block. Любой пустой T140block, отправленный в качестве основных данных, ДОЛЖЕН включаться как избыточный T140block в последующие пакеты так же, как это делалось бы с обычными текстовыми T140block, если только пустой T140block не является слишком старым для передачи. Это делается для того, чтобы вывод порядковых номеров для избыточных T140block был правильным, как объяснено в разделе 4.2.
After an idle period, the transmitter SHOULD set the M-bit to one in the first packet with new text.
После периода простоя передатчику СЛЕДУЕТ установить M-бит в единицу в первом пакете с новым текстом.
5.3. Detection of Lost Text Packets
5.3. Обнаружение потерянных текстовых пакетов
Packet loss for text/t140 packets MAY be detected by observing gaps in the sequence numbers of RTP packets received by the receiver.
Потеря пакетов text/t140 МОЖЕТ обнаруживаться путём наблюдения пропусков в порядковых номерах пакетов RTP, принимаемых получателем.
With text/t140, the loss of packets is usually detected by comparison of the sequence of RTP packets as they arrive. Any discrepancy MAY be used to indicate loss. The highest RTP sequence number received may also be compared with that in RTCP reports, as an additional check for loss of the last packet before an idle period.
В случае text/t140 потеря пакетов обычно обнаруживается путём сравнения последовательности пакетов RTP по мере их прибытия. Любое расхождение МОЖЕТ использоваться для указания на потерю. Наибольший принятый порядковый номер RTP также может сравниваться с номером в отчётах RTCP как дополнительная проверка потери последнего пакета перед периодом простоя.
Missing data SHOULD be marked by insertion of a missing text marker in the received stream for each missing T140block, as specified in ITU-T T.140 Addendum 1 [1].
Отсутствующие данные СЛЕДУЕТ помечать вставкой маркера отсутствующего текста в принимаемый поток для каждого отсутствующего T140block, как указано в ITU-T T.140 Addendum 1 [1].
Because empty T140blocks are transmitted in the beginning of an idle period, there is a slight risk of falsely marking loss of text, when only an empty T140block was lost. Procedures based on detection of the packet with the M-bit set to one MAY be used to reduce the risk of introducing false markers of loss.
Поскольку пустые T140block передаются в начале периода простоя, существует небольшой риск ложной маркировки потери текста, когда был потерян только пустой T140block. Процедуры, основанные на обнаружении пакета с установленным в единицу M-битом, МОГУТ использоваться для снижения риска внесения ложных маркеров потери.
If redundancy is used with the text/t140 format, and a packet is received with fewer redundancy levels than normally in the session, it SHOULD be treated as if one empty T140block has been received for each excluded level in the received packet. This is because the only occasion when a T140block is excluded from transmission is when it is an empty T140block that has become too old to be transmitted.
Если избыточность используется с форматом text/t140 и принят пакет с меньшим числом уровней избыточности, чем обычно в сеансе, его СЛЕДУЕТ обрабатывать так, как если бы для каждого исключённого уровня в принятом пакете был принят один пустой T140block. Это связано с тем, что единственный случай, когда T140block исключается из передачи, — это когда он является пустым T140block, ставшим слишком старым для передачи.
If two successive packets have the same number of redundant generations, it SHOULD be treated as the general redundancy level for the session. Change of the general redundancy level SHOULD only be done after an idle period.
Если два последовательных пакета имеют одинаковое число избыточных поколений, это СЛЕДУЕТ рассматривать как общий уровень избыточности для сеанса. Изменение общего уровня избыточности СЛЕДУЕТ производить только после периода простоя.
The text/t140 format relies on use of the sequence number in the RTP packet header for detection of loss and, therefore, is not suitable for applications where it needs to be alternating with other payloads in the same RTP stream. It would be complicated and unreliable to try to detect loss of data at the edges of the shifts between t140 text and other stream contents. Therefore, text/t140 is RECOMMENDED to be the only payload type in the RTP stream.
Формат text/t140 полагается на использование порядкового номера в заголовке пакета RTP для обнаружения потерь и поэтому не подходит для приложений, где он должен чередоваться с другими полезными нагрузками в одном и том же потоке RTP. Было бы сложно и ненадёжно пытаться обнаружить потерю данных на границах переходов между текстом t140 и содержимым другого потока. Поэтому РЕКОМЕНДУЕТСЯ, чтобы text/t140 был единственным типом полезной нагрузки в потоке RTP.
5.4. Compensation for Packets Out of Order
5.4. Компенсация пакетов, пришедших не по порядку
For protection against packets arriving out of order, the following procedure MAY be implemented in the receiver. If analysis of a received packet reveals a gap in the sequence and no redundant data is available to fill that gap, the received packet SHOULD be kept in a buffer to allow time for the missing packet(s) to arrive. It is RECOMMENDED that the waiting time be limited to 1 second.
Для защиты от пакетов, прибывающих не по порядку, в приёмнике МОЖЕТ быть реализована следующая процедура. Если анализ принятого пакета выявляет пропуск в последовательности и избыточные данные для заполнения этого пропуска отсутствуют, принятый пакет СЛЕДУЕТ сохранять в буфере, чтобы дать время прибыть отсутствующим пакетам. РЕКОМЕНДУЕТСЯ ограничивать время ожидания 1 секундой.
If a packet with a T140block belonging to the gap arrives before the waiting time expires, this T140block is inserted into the gap and then consecutive T140blocks from the leading edge of the gap may be consumed. Any T140block that does not arrive before the time limit expires should be treated as lost and a missing text marker should be inserted (see Section 5.3).
Если пакет с T140block, принадлежащим пропуску, прибывает до истечения времени ожидания, этот T140block вставляется в пропуск, после чего могут быть использованы последовательные T140block с переднего края пропуска. Любой T140block, который не прибудет до истечения предельного времени, следует рассматривать как потерянный, и должен быть вставлен маркер отсутствующего текста (см. раздел 5.3).
6. Parameter for Character Transmission Rate
6. Параметр скорости передачи символов
In some cases, it is necessary to limit the rate at which characters are transmitted. For example, when a Public Switched Telephone Network (PSTN) gateway is interworking between an IP device and a PSTN textphone, it may be necessary to limit the character rate from the IP device in order to avoid throwing away characters (in case of buffer overflow at the PSTN gateway).
В некоторых случаях необходимо ограничивать скорость передачи символов. Например, когда шлюз телефонной сети общего пользования (PSTN) обеспечивает взаимодействие между IP-устройством и текстовым телефоном PSTN, может потребоваться ограничить скорость символов от IP-устройства, чтобы избежать отбрасывания символов (в случае переполнения буфера на шлюзе PSTN).
To control the character transmission rate, the MIME parameter "cps" in the "fmtp" attribute [7] is defined (see Section 10 ). It is used in SDP with the following syntax:
Для управления скоростью передачи символов определён параметр MIME «cps» в атрибуте «fmtp» [7] (см. раздел 10). Он используется в SDP со следующим синтаксисом:
a=fmtp:<format> cps=<integer>
a=fmtp:<format> cps=<integer>
The <format> field is populated with the payload type that is used for text. The <integer> field contains an integer representing the maximum number of characters that may be received per second. The value shall be used as a mean value over any 10-second interval. The default value is 30.
Поле <format> заполняется типом полезной нагрузки, который используется для текста. Поле <integer> содержит целое число, представляющее максимальное количество символов, которое может быть принято за секунду. Значение должно использоваться как среднее значение за любой 10-секундный интервал. Значение по умолчанию — 30.
Examples of use in SDP are found in Section 7.2.
Примеры использования в SDP приведены в разделе 7.2.
In receipt of this parameter, devices MUST adhere to the request by transmitting characters at a rate at or below the specified <integer> value. Note that this parameter was not defined in RFC 2793 [16]. Therefore implementations of the text/t140 format may be in use that do not recognize and act according to this parameter. Therefore, receivers of text/t140 MUST be designed so they can handle temporary reception of characters at a higher rate than this parameter specifies. As a result malfunction due to buffer overflow is avoided for text conversation with human input.
При получении этого параметра устройства ДОЛЖНЫ соблюдать требование, передавая символы со скоростью не выше указанного значения <integer>. Обратите внимание, что этот параметр не был определён в RFC 2793 [16]. Поэтому могут использоваться реализации формата text/t140, которые не распознают этот параметр и не действуют в соответствии с ним. Поэтому приёмники text/t140 ДОЛЖНЫ быть спроектированы так, чтобы они могли справляться с временным приёмом символов со скоростью выше, чем указывает этот параметр. В результате для текстового разговора с человеческим вводом избегается сбой из-за переполнения буфера.

8. Security Considerations
8. Вопросы безопасности
All of the security considerations from Section 14 of RFC 3550 [2] apply.
Применяются все соображения безопасности из раздела 14 RFC 3550 [2].
8.1. Confidentiality
8.1. Конфиденциальность
Because the intention of the described payload format is to carry text in a text conversation, security measures in the form of encryption are of importance. The amount of data in a text conversation session is low. Therefore, any encryption method MAY be selected and applied to T.140 session contents or to whole RTP packets. Secure Real-time Transport Protocol (SRTP) [14] provides a suitable method for ensuring confidentiality.
Поскольку назначение описанного формата полезной нагрузки — передавать текст в текстовом разговоре, важное значение имеют меры безопасности в форме шифрования. Объём данных в сеансе текстового разговора невелик. Поэтому любой метод шифрования МОЖЕТ быть выбран и применён к содержимому сеанса T.140 или к целым пакетам RTP. Безопасный протокол передачи в реальном времени (SRTP) [14] предоставляет подходящий метод обеспечения конфиденциальности.
8.2. Integrity
8.2. Целостность
It may be desirable to protect the text contents of an RTP stream against manipulation. SRTP [14] provides methods for providing integrity that MAY be applied.
Может быть желательно защитить текстовое содержимое потока RTP от манипуляций. SRTP [14] предоставляет методы обеспечения целостности, которые МОГУТ применяться.
8.3. Source Authentication
8.3. Аутентификация источника
There are several methods of making sure the source of the text is the intended one.
Существует несколько методов удостовериться в том, что источник текста является предполагаемым.
Text streams are usually used in a multimedia control environment. Security measures for authentication are available and SHOULD be applied in the registration and session establishment procedures, so that the identity of the sender of the text stream is reliably associated with the person or device setting up the session. Once established, SRTP [14] mechanisms MAY be applied to ascertain that the source is maintained the same during the session.
Текстовые потоки обычно используются в среде управления мультимедиа. Меры безопасности для аутентификации доступны, и их СЛЕДУЕТ применять в процедурах регистрации и установления сеанса, чтобы личность отправителя текстового потока надёжно связывалась с человеком или устройством, устанавливающим сеанс. После установления сеанса механизмы SRTP [14] МОГУТ применяться для того, чтобы удостовериться, что источник остаётся тем же на протяжении сеанса.
9. Congestion Considerations
9. Вопросы перегрузки
The congestion considerations from Section 10 of RFC 3550 [2], Section 6 of RFC 2198 [3], and any used profile (e.g., the section about congestion in chapter 2 of RFC 3551 [11]) apply with the following application-specific considerations.
Применяются соображения по перегрузке из раздела 10 RFC 3550 [2], раздела 6 RFC 2198 [3] и любого используемого профиля (например, раздела о перегрузке в главе 2 RFC 3551 [11]) со следующими соображениями, специфичными для приложения.
Automated systems MUST NOT use this format to send large amounts of text at rates significantly above those a human user could enter.
Автоматизированные системы НЕ ДОЛЖНЫ применять этот формат для отправки больших объёмов текста со скоростью, значительно превышающей скорость ввода человека.
Even if the network load from users of text conversation is usually very low, for best-effort networks an application MUST monitor the packet loss rate and take appropriate actions to reduce its sending rate (if this application sends at higher rate than what TCP would achieve over the same path). The reason for this is that this application, due to its recommended usage of two or more redundancy levels, is very robust against packet loss. At the same time, due to the low bit-rate of text conversations, if one considers the discussion in RFC 3714 [13], this application will experience very high packet loss rates before it needs to perform any reduction in the sending rate.
Даже если сетевая нагрузка от пользователей текстового разговора обычно очень низка, для сетей с доставкой по мере возможности приложение ДОЛЖНО отслеживать долю потерь пакетов и предпринимать соответствующие действия для снижения своей скорости отправки (если это приложение отправляет с более высокой скоростью, чем достиг бы TCP на том же пути). Причина этого в том, что данное приложение благодаря рекомендуемому использованию двух или более уровней избыточности очень устойчиво к потере пакетов. В то же время из-за низкой битовой скорости текстовых разговоров, если учесть обсуждение в RFC 3714 [13], это приложение будет испытывать очень высокие доли потерь пакетов, прежде чем ему потребуется выполнять какое-либо снижение скорости отправки.
If the application needs to reduce its sending rate, it SHOULD NOT reduce the number of redundancy levels below the default amount specified in Section 4. Instead, the following actions are RECOMMENDED in order of priority:
Если приложению необходимо снизить скорость отправки, ему НЕ СЛЕДУЕТ уменьшать число уровней избыточности ниже количества по умолчанию, указанного в разделе 4. Вместо этого РЕКОМЕНДУЮТСЯ следующие действия в порядке приоритета:
- Increase the shortest time between transmissions (described in Section 5.1) from the recommended 300 ms to 500 ms, which is the highest value allowed according to T.140.
- Увеличить кратчайшее время между передачами (описанное в разделе 5.1) с рекомендуемых 300 мс до 500 мс, что является наибольшим значением, допустимым согласно T.140.
- Limit the maximum rate of characters transmitted.
- Ограничить максимальную скорость передаваемых символов.
- Increase the shortest time between transmissions to a higher value, not higher than 5 seconds. This will cause unpleasant delays in transmission, beyond what is allowed according to T.140, but text will still be conveyed in the session with some usability.
- Увеличить кратчайшее время между передачами до более высокого значения, не превышающего 5 секунд. Это вызовет неприятные задержки в передаче, выходящие за пределы, допустимые согласно T.140, но текст всё же будет передаваться в сеансе с некоторой пригодностью к использованию.
- Exclude participants from the session.
- Исключить участников из состава сеанса.
Please note that if the reduction in bit-rate achieved through the above measures is not sufficient, the only remaining action is to terminate the session.
Обратите внимание, что если снижение битовой скорости, достигнутое вышеуказанными мерами, недостаточно, единственным оставшимся действием является завершение сеанса.
As guidance, some load figures are provided here as examples based on use of IPv4, including the load from IP, UDP, and RTP headers without compression .
В качестве руководства здесь приведены некоторые цифры нагрузки в качестве примеров, основанных на использовании IPv4, включая нагрузку от заголовков IP, UDP и RTP без сжатия.
- Experience tells that a common mean character transmission rate, during a complete PSTN text telephony session, is around two characters per second.
- Опыт показывает, что обычная средняя скорость передачи символов за полный сеанс текстовой телефонии PSTN составляет около двух символов в секунду.
- A maximum performance of 20 characters per second is enough even for voice-to-text applications.
- Максимальной производительности 20 символов в секунду достаточно даже для приложений преобразования речи в текст.
- With the (unusually high) load of 20 characters per second, in a language that makes use of three octets per UTF-8 character, two redundant levels, and 300 ms between transmissions, the maximum load of this application is 3300 bits/s. - When the restrictions mentioned above are applied, limiting transmission to 10 characters per second, using 5 s between transmissions, the maximum load of this application, in a language that uses one octet per UTF-8 character, is 300 bits/s.
- При (необычно высокой) нагрузке 20 символов в секунду, в языке, использующем три октета на символ UTF-8, двух уровнях избыточности и 300 мс между передачами, максимальная нагрузка этого приложения составляет 3300 бит/с. - При применении ограничений, упомянутых выше, ограничивающих передачу 10 символами в секунду, с использованием 5 с между передачами, максимальная нагрузка этого приложения в языке, использующем один октет на символ UTF-8, составляет 300 бит/с.
Note that this payload can be used in a congested situation as a last resort to maintain some contact when audio and video media need to be stopped. The availability of one low bit-rate stream for text in such adverse situations may be crucial for maintaining some communication in a critical situation.
Обратите внимание, что эта полезная нагрузка может использоваться в условиях перегрузки как последнее средство для поддержания некоторого контакта, когда аудио- и видеоматериалы необходимо остановить. Доступность одного потока с низкой битовой скоростью для текста в таких неблагоприятных условиях может иметь решающее значение для поддержания некоторой связи в критической ситуации.

10.2. SDP Mapping of MIME Parameters
10.2. Отображение параметров MIME на SDP
The information carried in the MIME media type specification has a specific mapping to fields in the Session Description Protocol (SDP) [7], which is commonly used to describe RTP sessions. When SDP is used to specify sessions employing the text/t140 format, the mapping is as follows:

- Параметр «cps» помещается в атрибут SDP «a=fmtp».

- Когда тип полезной нагрузки используется с избыточностью согласно RFC 2198, уровень избыточности показывается числом элементов в разделённом косыми чертами списке типов полезной нагрузки в параметре «fmtp» объявления избыточности, как определено в RFC 4102 [9] и RFC 2198 [3].
