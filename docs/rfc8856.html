1. Introduction
1. Введение
As discussed in the BFCP (Binary Floor Control Protocol) specification [RFC8855], a given BFCP client needs a set of data in order to establish a BFCP connection to a floor control server. This data includes the transport address of the server, the conference identifier, and the user identifier.
Как обсуждается в спецификации BFCP (двоичного протокола управления полом) [RFC8855], конкретному клиенту BFCP нужен набор данных, чтобы установить соединение BFCP с сервером управления полом. Эти данные включают транспортный адрес сервера, идентификатор конференции и идентификатор пользователя.
One way for clients to obtain this information is to use a Session Description Protocol (SDP) offer/answer exchange [RFC3264]. This document specifies how to encode this information in the SDP session descriptions that are part of such an offer/answer exchange.
Один из способов получения клиентами этих сведений — использовать обмен предложением/ответом протокола описания сессий (SDP) [RFC3264]. Настоящий документ определяет, как кодировать эти сведения в описаниях сессии SDP, входящих в такой обмен предложением/ответом.
User agents typically use the offer/answer model to establish a number of media streams of different types. Following this model, a BFCP connection is described as any other media stream by using an SDP "m=" line, possibly followed by a number of SDP lines that also apply to the BFCP connection.
Пользовательские агенты обычно применяют модель предложения/ответа для установления ряда медиапотоков различных типов. Следуя этой модели, соединение BFCP описывается как любой другой медиапоток с помощью строки «m=» SDP, за которой, возможно, следует ряд строк SDP, также относящихся к соединению BFCP.

3. Floor Control Roles
3. Роли управления полом
When two endpoints establish a BFCP stream, they need to determine which of them acts as a floor control client and which acts as a floor control server.
Когда две оконечные точки устанавливают поток BFCP, им нужно определить, какая из них действует как клиент управления полом, а какая — как сервер управления полом.
Once the roles have been determined, the roles will apply to all BFCP-controlled streams associated with the BFCP stream.
После определения ролей они будут применяться ко всем медиапотокам, управляемым BFCP, связанным с потоком BFCP.
4. Fields in the "m=" Line
4. Поля строки «m=»
According to the SDP specification [RFC8866], the "m=" line format is as follows:
Согласно спецификации SDP [RFC8866], формат строки «m=» имеет следующий вид:
m=<media> <port> <proto> <fmt> ...
m=<media> <port> <proto> <fmt> ...
This section describes how to generate an "m=" line of an SDP Media Description ("m=" section) describing a BFCP stream.
В этом разделе описывается, как сформировать строку «m=» описания медиа SDP (раздел «m=»), описывающую поток BFCP.
The media field MUST have a value of "application".
Поле media ДОЛЖНО иметь значение «application».
Depending on the value of the proto field, the port field is set as explained below. A port field value of zero has the standard SDP meaning (i.e., rejection of the media stream), regardless of the proto field.
В зависимости от значения поля proto поле port задаётся так, как описано ниже. Значение поля port, равное нулю, имеет стандартный смысл SDP (то есть отказ от медиапотока), независимо от поля proto.
* When TCP is used as the transport, the port field is set following the rules in [RFC4145]. Depending on the value of the 'setup' attribute (defined in [RFC4145] and discussed in Section 7.1), the port field contains the port to which the remote endpoint will direct BFCP messages, or in the case where the endpoint will initiate the connection towards the remote endpoint, should be set to a value of 9.
* Когда в качестве транспорта используется TCP, поле port задаётся по правилам [RFC4145]. В зависимости от значения атрибута 'setup' (определённого в [RFC4145] и обсуждаемого в разделе 7.1) поле port содержит порт, на который удалённая оконечная точка будет направлять сообщения BFCP, или, в случае когда оконечная точка будет инициировать соединение с удалённой оконечной точкой, должно быть установлено в значение 9.
* When UDP is used as the transport, the port field contains the port to which the remote endpoint will direct BFCP messages, regardless of the value of the 'setup' attribute.
* Когда в качестве транспорта используется UDP, поле port содержит порт, на который удалённая оконечная точка будет направлять сообщения BFCP, независимо от значения атрибута 'setup'.
This document defines five values for the proto field: 'TCP/BFCP', 'TCP/DTLS/BFCP', 'TCP/TLS/BFCP', 'UDP/BFCP', and 'UDP/TLS/BFCP'.
Настоящий документ определяет пять значений поля proto: 'TCP/BFCP', 'TCP/DTLS/BFCP', 'TCP/TLS/BFCP', 'UDP/BFCP' и 'UDP/TLS/BFCP'.
The proto values are used as described below:
Значения proto используются так, как описано ниже:
* 'TCP/BFCP' is used for TCP transport of BFCP without TLS encryption and is backward compatible with endpoints that are compliant with RFC 4583.
* 'TCP/BFCP' используется для транспортировки BFCP по TCP без шифрования TLS и обратно совместим с оконечными точками, соответствующими RFC 4583.
* 'TCP/TLS/BFCP' is used for TCP transport of BFCP with TLS encryption and is backward compatible with endpoints that are compliant with RFC 4583 and support TLS.
* 'TCP/TLS/BFCP' используется для транспортировки BFCP по TCP с шифрованием TLS и обратно совместим с оконечными точками, соответствующими RFC 4583 и поддерживающими TLS.
* 'UDP/BFCP' is used for UDP transport of BFCP without DTLS encryption [RFC6347].
* 'UDP/BFCP' используется для транспортировки BFCP по UDP без шифрования DTLS [RFC6347].
* 'UDP/TLS/BFCP' is used for UDP transport of BFCP with DTLS encryption. This is one of the options when ICE is used (Section 9). It can also be used without ICE when backward compatibility with endpoints compliant with RFC 4583 is not required.
* 'UDP/TLS/BFCP' используется для транспортировки BFCP по UDP с шифрованием DTLS. Это один из вариантов, когда используется ICE (раздел 9). Его также можно использовать без ICE, когда обратная совместимость с оконечными точками, соответствующими RFC 4583, не требуется.
* 'TCP/DTLS/BFCP' is used for TCP transport of BFCP with DTLS encryption, running on top of TCP using the framing method defined in [RFC4571], with DTLS packets being sent and received instead of RTP / RTP Control Protocol (RTCP) packets, such that the LENGTH field defined in RFC 4571 precedes each DTLS message. This is one of the options when ICE is used (Section 9). It can also be used without ICE when backward compatibility with endpoints compliant with RFC 4583 is not required.
* 'TCP/DTLS/BFCP' используется для транспортировки BFCP по TCP с шифрованием DTLS поверх TCP с применением метода кадрирования, определённого в [RFC4571], при котором вместо пакетов RTP / протокола управления RTP (RTCP) отправляются и принимаются пакеты DTLS, так что поле LENGTH, определённое в RFC 4571, предшествует каждому сообщению DTLS. Это один из вариантов, когда используется ICE (раздел 9). Его также можно использовать без ICE, когда обратная совместимость с оконечными точками, соответствующими RFC 4583, не требуется.
The fmt (format) list is not applicable to BFCP. The fmt list of "m=" lines in the case of any proto field value related to BFCP MUST contain a single "*" character. If the fmt list contains any other value, it MUST be ignored.
Список fmt (форматов) к BFCP не применим. Список fmt строк «m=» в случае любого значения поля proto, относящегося к BFCP, ДОЛЖЕН содержать единственный символ «*». Если список fmt содержит любое другое значение, оно ДОЛЖНО быть проигнорировано.
The following is an example of an "m=" line for a BFCP connection:
Ниже приведён пример строки «m=», описывающей соединение BFCP:
m=application 50000 TCP/TLS/BFCP *
m=application 50000 TCP/TLS/BFCP *

5. Атрибуты SDP
5.1. SDP 'floorctrl' Attribute
5.1. Атрибут SDP 'floorctrl'
This section defines the SDP 'floorctrl' media-level attribute. The attribute is used to determine the floor control roles (client and server) for the endpoints associated with the BFCP stream.
В этом разделе определяется атрибут уровня медиа SDP 'floorctrl'. Атрибут используется для определения ролей управления полом (клиент и сервер) для оконечных точек, связанных с потоком BFCP.
Attribute Name: floorctrl
Имя атрибута: floorctrl.
Attribute Value: floor-control
Значение атрибута: floor-control.
Usage Level: media
Уровень использования: media.
Charset Dependent: No
Зависимость от кодировки: No.
Mux Category: TBD
Категория мультиплексирования: TBD.
The Augmented BNF syntax [RFC5234] for the attribute is:
Расширенная форма Бэкуса — Наура (ABNF) [RFC5234] для атрибута:
floor-control = role *(SP role) role = "c-only" / "s-only" / "c-s"
floor-control = role *(SP role) role = "c-only" / "s-only" / "c-s"
An endpoint includes the attribute to indicate the role(s) it would be willing to perform for the BFCP-controlled media streams:
Оконечная точка включает атрибут, чтобы указать роль (роли), которую она готова выполнять для медиапотоков, управляемых BFCP:
c-only: The endpoint is willing to act as a floor control client.
c-only: оконечная точка готова действовать как клиент управления полом.
s-only: The endpoint is willing to act as a floor control server only.
s-only: оконечная точка готова действовать только как сервер управления полом.
When inserted in an offer, the offerer MAY indicate multiple attribute values ("c-only" and "s-only"). When inserted in an answer, the answerer MUST indicate only one attribute value: "c-only" or "s-only". The answerer indicates the role taken by the answerer. The offerer will then take the opposite role.
При вставке в предложение предлагающий МОЖЕТ указать несколько значений атрибута («c-only» и «s-only»). При вставке в ответ отвечающий ДОЛЖЕН указать только одно значение атрибута: «c-only» или «s-only». Отвечающий указывает роль, которую он принимает. Предлагающий затем примет противоположную роль.
In [RFC4583], there was a third attribute specified, "c-s", which meant that an endpoint was willing to act as both a floor control client and a floor control server at the same time for the BFCP stream, taking different roles for different BFCP-controlled media streams. The feature was underspecified and implemented in different ways; in particular, many implementations interpreted "c-s" to mean that the endpoint is willing to act as either a client or a server (equivalent to "c-only s-only"). An implementation compliant with this specification MUST NOT include the "c-s" 'floorctrl' attribute value in an offer or in an answer but MUST accept the attribute value in an offer and process it as equivalent to "c-only s-only" (or "s-only c-only"). Also, as an implementation compliant with this specification is only allowed to include one role -- either "c-only" or "s-only" -- in an answer, each endpoint will only take one role, and as a result the endpoint will take the same role for each BFCP- controlled media stream associated with the BFCP stream.
В [RFC4583] был определён третий атрибут, «c-s», который означал, что оконечная точка готова действовать одновременно и как клиент управления полом, и как сервер управления полом для потока BFCP, принимая разные роли для разных медиапотоков, управляемых BFCP. Эта возможность была недоопределена и реализовывалась по-разному; в частности, многие реализации толковали «c-s» как готовность оконечной точки действовать либо клиентом, либо сервером (что эквивалентно «c-only s-only»). Реализация, соответствующая настоящей спецификации, НЕ ДОЛЖНА включать значение атрибута 'floorctrl' «c-s» в предложение или в ответ, но ДОЛЖНА принимать это значение атрибута в предложении и обрабатывать его как эквивалент «c-only s-only» (или «s-only c-only»). Кроме того, поскольку реализация, соответствующая настоящей спецификации, вправе включать в ответ только одну роль — либо «c-only», либо «s-only», — каждая оконечная точка будет принимать только одну роль, и, как следствие, оконечная точка будет принимать одну и ту же роль для каждого медиапотока, управляемого BFCP, связанного с потоком BFCP.
Table 1 shows the roles that the answerer is allowed to take, based on what roles the offerer has indicated that it is willing to take.
В таблице 1 показаны роли, которые отвечающему разрешено принимать, исходя из того, какие роли предлагающий указал как готовность принять.

Endpoints compliant with [RFC4583] might not include the 'floorctrl' attribute in offers and answers. If the 'floorctrl' attribute is not present, in order to be interoperable with such endpoints, the offerer will act as a floor control client and the answerer will act as a floor control server.
Оконечные точки, соответствующие [RFC4583], могут не включать атрибут 'floorctrl' в предложения и ответы. Если атрибут 'floorctrl' отсутствует, то для совместимости с такими оконечными точками предлагающий будет действовать как клиент управления полом, а отвечающий — как сервер управления полом.
The SDP Offer/Answer procedures for the 'floorctrl' attribute are defined in Section 10.
Процедуры предложения/ответа SDP для атрибута 'floorctrl' определены в разделе 10.

5.2. SDP 'confid' Attribute

7.1. TCP Connection Management
7.1. Управление TCP-соединением
The management of the TCP connection used to transport BFCP messages is performed using the SDP 'setup' and 'connection' attributes [RFC4145]. The 'setup' attribute indicates which of the endpoints initiates the TCP connection. The 'connection' attribute handles TCP connection re-establishment.
Управление TCP-соединением, используемым для транспортировки сообщений BFCP, выполняется с помощью атрибутов SDP 'setup' и 'connection' [RFC4145]. Атрибут 'setup' указывает, какая из оконечных точек инициирует TCP-соединение. Атрибут 'connection' обеспечивает повторное установление TCP-соединения.
The BFCP specification [RFC8855] describes a number of situations when the TCP connection between a floor control client and the floor control server needs to be re-established. However, [RFC8855] does not describe the re-establishment process, because this process depends on how the connection was established in the first place. Endpoints using the offer/answer mechanism follow the following rules.
Спецификация BFCP [RFC8855] описывает ряд ситуаций, когда TCP-соединение между клиентом управления полом и сервером управления полом должно быть установлено повторно. Однако [RFC8855] не описывает процесс повторного установления, поскольку этот процесс зависит от того, как соединение было установлено изначально. Оконечные точки, использующие механизм предложения/ответа, следуют приведённым ниже правилам.
When the existing TCP connection is closed and re-established following the rules in [RFC8855], the floor control client MUST send an offer towards the floor control server in order to re-establish the connection. If a TCP connection cannot deliver a BFCP message and times out, the endpoint that attempted to send the message (i.e., the one that detected the TCP timeout) MUST send an offer in order to re-establish the TCP connection.
Когда существующее TCP-соединение закрыто и повторно устанавливается по правилам [RFC8855], клиент управления полом ДОЛЖЕН отправить предложение серверу управления полом, чтобы повторно установить соединение. Если TCP-соединение не может доставить сообщение BFCP и происходит тайм-аут, оконечная точка, пытавшаяся отправить сообщение (то есть та, которая обнаружила тайм-аут TCP), ДОЛЖНА отправить предложение, чтобы повторно установить TCP-соединение.
Endpoints that use the offer/answer mechanism to negotiate TCP connections MUST support the 'setup' and 'connection' attributes.
Оконечные точки, использующие механизм предложения/ответа для согласования TCP-соединений, ДОЛЖНЫ поддерживать атрибуты 'setup' и 'connection'.

Основываясь на процедурах, определённых в [RFC8842], оконечные точки рассматривают все пары кандидатов ICE, связанные с потоком BFCP поверх ассоциации DTLS, как часть одной и той же ассоциации DTLS. Если добавляются новые кандидаты, они также будут частью той же ассоциации DTLS.
In order to maximize the likelihood of interoperability between the endpoints, all ICE-enabled BFCP-over-DTLS endpoints SHOULD implement support for UDP/TLS/BFCP.
Чтобы максимально повысить вероятность совместимости между оконечными точками, все оконечные точки BFCP-по-DTLS с поддержкой ICE ДОЛЖНЫ реализовывать поддержку UDP/TLS/BFCP.

Если для кандидата по умолчанию используется транспорт UDP, значение proto в строке «m=» ДОЛЖНО быть 'UDP/TLS/BFCP'. Если для кандидата по умолчанию используется транспорт TCP, значение proto в строке «m=» ДОЛЖНО быть 'TCP/DTLS/BFCP'.

12. Security Considerations
12. Вопросы безопасности
The BFCP specification [RFC8855], SDP specification [RFC8866], and offer/answer specification [RFC3264] discuss security issues related to BFCP, SDP, and offer/answer, respectively. In addition, [RFC4145] and [RFC8122] discuss security issues related to the establishment of TCP and TLS connections using an offer/answer model. Furthermore, when using DTLS over UDP, the generic offer/answer considerations defined in [RFC8842] MUST be followed.
В спецификации BFCP [RFC8855], спецификации SDP [RFC8866] и спецификации предложения/ответа [RFC3264] рассматриваются вопросы безопасности, относящиеся соответственно к BFCP, SDP и предложению/ответу. Кроме того, [RFC4145] и [RFC8122] рассматривают вопросы безопасности, связанные с установлением соединений TCP и TLS по модели предложения/ответа. Более того, при использовании DTLS поверх UDP ДОЛЖНЫ соблюдаться общие соображения по предложению/ответу, определённые в [RFC8842].
The usage of certain proto values in the SDP offer/answer negotiation will result in a BFCP stream that is not protected by TLS or DTLS. Operators will need to provide integrity protection and confidentiality protection of the BFCP stream using other means.
Использование некоторых значений proto при согласовании предложения/ответа SDP приведёт к тому, что поток BFCP не будет защищён средствами TLS или DTLS. Операторам потребуется обеспечить защиту целостности и конфиденциальности потока BFCP другими средствами.
The generic security considerations associated with SDP attributes are defined in [RFC3264]. While the attributes defined in this specification do not reveal information about the content of individual BFCP-controlled media streams, they do reveal which media streams will be BFCP controlled.
Общие вопросы безопасности, связанные с атрибутами SDP, определены в [RFC3264]. Хотя атрибуты, определённые в настоящей спецификации, не раскрывают сведений о содержимом отдельных медиапотоков, управляемых BFCP, они раскрывают, какие медиапотоки будут управляться BFCP.
