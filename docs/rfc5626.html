Managing Client-Initiated Connections in the Session Initiation Protocol (SIP)
Управление соединениями, инициируемыми клиентом, в протоколе инициирования сессий (SIP)
Abstract
Аннотация
The Session Initiation Protocol (SIP) allows proxy servers to initiate TCP connections or to send asynchronous UDP datagrams to User Agents in order to deliver requests. However, in a large number of real deployments, many practical considerations, such as the existence of firewalls and Network Address Translators (NATs) or the use of TLS with server-provided certificates, prevent servers from connecting to User Agents in this way. This specification defines behaviors for User Agents, registrars, and proxy servers that allow requests to be delivered on existing connections established by the User Agent. It also defines keep-alive behaviors needed to keep NAT bindings open and specifies the usage of multiple connections from the User Agent to its registrar.
Протокол инициирования сессий (SIP) позволяет прокси-серверам устанавливать TCP-соединения или отправлять асинхронные UDP-дейтаграммы пользовательским агентам для доставки запросов. Однако во многих реальных развёртываниях ряд практических соображений, таких как наличие межсетевых экранов и преобразователей сетевых адресов (NAT) или использование TLS с серверными сертификатами, не позволяет серверам подключаться к пользовательским агентам таким образом. В настоящей спецификации определяются правила поведения пользовательских агентов, регистраторов и прокси-серверов, позволяющие доставлять запросы по существующим соединениям, установленным пользовательским агентом. В ней также определяются механизмы keep-alive, необходимые для поддержания привязок NAT, и задаётся порядок использования нескольких соединений от пользовательского агента к его регистратору.

1. Introduction
1. Введение
There are many environments for SIP [RFC3261] deployments in which the User Agent (UA) can form a connection to a registrar or proxy but in which connections in the reverse direction to the UA are not possible. This can happen for several reasons, but the most likely is a NAT or a firewall in between the SIP UA and the proxy. Many such devices will only allow outgoing connections. This specification allows a SIP User Agent behind such a firewall or NAT to receive inbound traffic associated with registrations or dialogs that it initiates.
Существует множество сред развёртывания SIP [RFC3261], в которых пользовательский агент (UA) может установить соединение с регистратором или прокси, но в которых соединения в обратном направлении, к UA, невозможны. Это может происходить по нескольким причинам, но наиболее вероятной является NAT или межсетевой экран между SIP-UA и прокси. Многие такие устройства разрешают только исходящие соединения. Настоящая спецификация позволяет SIP-пользовательскому агенту, находящемуся за таким межсетевым экраном или NAT, получать входящий трафик, связанный с регистрациями или диалогами, которые он инициирует.
Most IP phones and personal computers get their network configurations dynamically via a protocol such as the Dynamic Host Configuration Protocol (DHCP) [RFC2131]. These systems typically do not have a useful name in the Domain Name System (DNS) [RFC1035], and they almost never have a long-term, stable DNS name that is appropriate for use in the subjectAltName of a certificate, as required by [RFC3261]. However, these systems can still act as a Transport Layer Security (TLS) [RFC5246] client and form outbound connections to a proxy or registrar that authenticates with a server certificate. The server can authenticate the UA using a shared secret in a digest challenge (as defined in Section 22 of RFC 3261) over that TLS connection. This specification allows a SIP User Agent who has to initiate the TLS connection to receive inbound traffic associated with registrations or dialogs that it initiates.
Большинство IP-телефонов и персональных компьютеров получают сетевую конфигурацию динамически по протоколу, подобному протоколу динамической конфигурации узла (DHCP) [RFC2131]. Такие системы, как правило, не имеют полезного имени в системе доменных имён (DNS) [RFC1035] и почти никогда не имеют долговременного стабильного DNS-имени, пригодного для использования в subjectAltName сертификата, как того требует [RFC3261]. Тем не менее эти системы по-прежнему могут выступать клиентом транспортного уровня безопасности (TLS) [RFC5246] и устанавливать исходящие соединения с прокси или регистратором, который аутентифицируется серверным сертификатом. Сервер может аутентифицировать пользовательский агент с помощью общего секрета в дайджест-запросе (как определено в разделе 22 RFC 3261) по этому TLS-соединению. Настоящая спецификация позволяет SIP-пользовательскому агенту, которому приходится инициировать TLS-соединение, получать входящий трафик, связанный с регистрациями или диалогами, которые он инициирует.
The key idea of this specification is that when a UA sends a REGISTER request or a dialog-forming request, the proxy can later use this same network "flow" -- whether this is a bidirectional stream of UDP datagrams, a TCP connection, or an analogous concept in another transport protocol -- to forward any incoming requests that need to go to this UA in the context of the registration or dialog.
Ключевая идея настоящей спецификации состоит в том, что когда пользовательский агент отправляет запрос REGISTER или запрос, формирующий диалог, прокси может впоследствии использовать тот же самый сетевой «поток» — будь то двунаправленный поток UDP-дейтаграмм, TCP-соединение или аналогичное понятие в другом транспортном протоколе — для пересылки любых входящих запросов, которые должны быть доставлены этому пользовательскому агенту в контексте данной регистрации или диалога.
For a UA to receive incoming requests, the UA has to connect to a server. Since the server can't connect to the UA, the UA has to make sure that a flow is always active. This requires the UA to detect when a flow fails. Since such detection takes time and leaves a window of opportunity for missed incoming requests, this mechanism allows the UA to register over multiple flows at the same time. This specification also defines two keep-alive schemes. The keep-alive mechanism is used to keep NAT bindings fresh, and to allow the UA to detect when a flow has failed.
Чтобы пользовательский агент мог получать входящие запросы, он должен подключиться к серверу. Поскольку сервер не может подключиться к пользовательскому агенту, тот должен следить за тем, чтобы поток всегда был активен. Для этого пользовательский агент должен обнаруживать отказ потока. Поскольку такое обнаружение занимает время и оставляет окно для пропуска входящих запросов, данный механизм позволяет пользовательскому агенту регистрироваться одновременно через несколько потоков. В настоящей спецификации также определены две схемы keep-alive. Механизм keep-alive используется для поддержания актуальности привязок NAT и для того, чтобы пользовательский агент мог обнаруживать отказ потока.

2.1. Definitions
2.1. Определения
Authoritative Proxy: A proxy that handles non-REGISTER requests for a specific Address-of-Record (AOR), performs the logical Location Server lookup described in [RFC3261], and forwards those requests to specific Contact URIs. (In [RFC3261], the role that is authoritative for REGISTER requests for a specific AOR is a Registration Server.)
Авторитетный прокси: прокси, который обрабатывает запросы, отличные от REGISTER, для конкретного адреса записи (AOR), выполняет логический поиск в сервере местоположения, описанный в [RFC3261], и пересылает эти запросы конкретным Contact URI. (В [RFC3261] роль, авторитетная для запросов REGISTER по конкретному AOR, — это регистрационный сервер.)
Edge Proxy: An edge proxy is any proxy that is located topologically between the registering User Agent and the Authoritative Proxy. The "first" edge proxy refers to the first edge proxy encountered when a UA sends a request.
Граничный прокси: граничным называется любой прокси, расположенный топологически между регистрирующимся пользовательским агентом и авторитетным прокси. «Первым» граничным прокси считается первый граничный прокси, встреченный при отправке запроса пользовательским агентом.
Flow: A Flow is a transport-layer association between two hosts that is represented by the network address and port number of both ends and by the transport protocol. For TCP, a flow is equivalent to a TCP connection. For UDP a flow is a bidirectional stream of datagrams between a single pair of IP addresses and ports of both peers. With TCP, a flow often has a one-to-one correspondence with a single file descriptor in the operating system.
Поток: поток — это ассоциация транспортного уровня между двумя узлами, представленная сетевыми адресами и номерами портов обоих концов, а также транспортным протоколом. Для TCP поток эквивалентен TCP-соединению. Для UDP поток — это двунаправленный поток дейтаграмм между одной парой IP-адресов и портов обоих узлов. При использовании TCP поток часто имеет взаимно однозначное соответствие с отдельным файловым дескриптором в операционной системе.
Flow Token: An identifier that uniquely identifies a flow which can be included in a SIP URI (Uniform Resource Identifier [RFC3986]).
Токен потока: идентификатор, однозначно определяющий поток, который может быть включён в SIP URI (универсальный идентификатор ресурса [RFC3986]).
reg-id: This refers to the value of a new header field parameter value for the Contact header field. When a UA registers multiple times, each for a different flow, each concurrent registration gets a unique reg-id value.
reg-id: здесь имеется в виду значение нового параметра поля заголовка для поля заголовка Contact. Когда пользовательский агент регистрируется несколько раз, каждый раз для другого потока, каждая одновременная регистрация получает уникальное значение reg-id.
instance-id: This specification uses the word instance-id to refer to the value of the "sip.instance" media feature tag which appears as a "+sip.instance" Contact header field parameter. This is a Uniform Resource Name (URN) that uniquely identifies this specific UA instance.
instance-id: в настоящей спецификации слово instance-id обозначает значение тега характеристики среды «sip.instance», который фигурирует как параметр поля заголовка Contact «+sip.instance». Это универсальное имя ресурса (URN), однозначно идентифицирующее данный экземпляр пользовательского агента.
"ob" Parameter: The "ob" parameter is a SIP URI parameter that has a different meaning depending on context. In a Path header field value, it is used by the first edge proxy to indicate that a flow token was added to the URI. In a Contact or Route header field value, it indicates that the UA would like other requests in the same dialog to be routed over the same flow.
Параметр «ob»: параметр «ob» — это параметр SIP URI, имеющий разное значение в зависимости от контекста. В значении поля заголовка Path он используется первым граничным прокси, чтобы указать, что в URI был добавлен токен потока. В значении поля заголовка Contact или Route он указывает, что пользовательский агент хотел бы, чтобы остальные запросы того же диалога маршрутизировались по тому же потоку.
outbound-proxy-set: A set of SIP URIs (Uniform Resource Identifiers) that represents each of the outbound proxies (often edge proxies) with which the UA will attempt to maintain a direct flow. The first URI in the set is often referred to as the primary outbound proxy and the second as the secondary outbound proxy. There is no difference between any of the URIs in this set, nor does the primary/secondary terminology imply that one is preferred over the other.
outbound-proxy-set: набор SIP URI (универсальных идентификаторов ресурсов), представляющий каждый из исходящих прокси (часто граничных), с которыми пользовательский агент будет пытаться поддерживать прямое соединение. Первый URI в наборе часто называют основным исходящим прокси, а второй — вторичным исходящим прокси. Между URI этого набора нет никакой разницы, и терминология «основной/вторичный» также не подразумевает предпочтения одного другому.
3. Overview
3. Обзор
The mechanisms defined in this document are useful in several scenarios discussed below, including the simple co-located registrar and proxy, a User Agent desiring multiple connections to a resource (for redundancy, for example), and a system that uses edge proxies.
Описанные в настоящем документе механизмы полезны в нескольких сценариях, рассмотренных ниже, включая простой совместно размещённый регистратор и прокси, пользовательский агент, желающий иметь несколько соединений с ресурсом (например, для резервирования), и систему, использующую граничные прокси.

3.1. Summary of Mechanism
3.1. Краткое описание механизма
Each UA has a unique instance-id that stays the same for this UA even if the UA reboots or is power cycled. Each UA can register multiple times over different flows for the same SIP Address of Record (AOR) to achieve high reliability. Each registration includes the instance-id for the UA and a reg-id label that is different for each flow. The registrar can use the instance-id to recognize that two different registrations both correspond to the same UA. The registrar can use the reg-id label to recognize whether a UA is creating a new flow or refreshing or replacing an old one, possibly after a reboot or a network failure.
У каждого пользовательского агента есть уникальный instance-id, который сохраняется для этого агента даже после перезагрузки или цикла отключения питания. Каждый пользовательский агент может регистрироваться несколько раз через разные потоки для одного и того же адреса записи SIP (AOR) для достижения высокой надёжности. Каждая регистрация включает instance-id пользовательского агента и метку reg-id, различающуюся для каждого потока. Регистратор может использовать instance-id, чтобы распознать, что две разные регистрации соответствуют одному и тому же пользовательскому агенту. Регистратор может использовать метку reg-id, чтобы распознать, создаёт ли пользовательский агент новый поток, обновляет или заменяет старый, возможно, после перезагрузки или отказа сети.
When a proxy goes to route a message to a UA for which it has a binding, it can use any one of the flows on which a successful registration has been completed. A failure to deliver a request on a particular flow can be tried again on an alternate flow. Proxies can determine which flows go to the same UA by comparing the instance-id. Proxies can tell that a flow replaces a previously abandoned flow by looking at the reg-id.
Когда прокси маршрутизирует сообщение пользовательскому агенту, для которого у него есть привязка, он может использовать любой из потоков, по которым успешно завершена регистрация. Неудачную доставку запроса по конкретному потоку можно повторить по альтернативному потоку. Прокси могут определить, какие потоки ведут к одному и тому же пользовательскому агенту, сравнив instance-id. Прокси может определить, что поток заменяет ранее заброшенный поток, посмотрев на reg-id.
When sending a dialog-forming request, a UA can also ask its first edge proxy to route subsequent requests in that dialog over the same flow. This is necessary whether the UA has registered or not.
При отправке запроса, формирующего диалог, пользовательский агент может также попросить свой первый граничный прокси проводить последующие запросы этого диалога по тому же потоку. Это нужно независимо от того, регистрировался ли агент.
UAs use a simple periodic message as a keep-alive mechanism to keep their flow to the proxy or registrar alive. For connection-oriented transports such as TCP this is based on carriage-return and line-feed sequences (CRLF), while for transports that are not connection oriented, this is accomplished by using a SIP-specific usage profile of STUN (Session Traversal Utilities for NAT) [RFC5389].
Пользовательские агенты используют простое периодическое сообщение в качестве механизма keep-alive, чтобы поддерживать свой поток к прокси или регистратору активным. Для транспортов с установлением соединения, таких как TCP, это основано на последовательностях возврата каретки и перевода строки (CRLF), а для транспортов без установления соединения это достигается с помощью специфичного для SIP профиля использования STUN (утилиты обхода сеансов для NAT) [RFC5389].
3.2. Single Registrar and UA
3.2. Единый регистратор и пользовательский агент
In the topology shown below, a single server is acting as both a registrar and proxy.
В топологии, показанной ниже, один сервер выступает одновременно и регистратором, и прокси.
+-----------+ | Registrar | | Proxy | +-----+-----+ | | +----+--+ | User | | Agent | +-------+
+-----------+ | Registrar | | Proxy | +-----+-----+ | | +----+--+ | User | | Agent | +-------+
User Agents that form only a single flow continue to register normally but include the instance-id as described in Section 4.1. The UA also includes a "reg-id" Contact header field parameter that is used to allow the registrar to detect and avoid keeping invalid contacts when a UA reboots or reconnects after its old connection has failed for some reason.
Пользовательские агенты, формирующие только один поток, продолжают регистрироваться обычным образом, но включают instance-id, как описано в разделе 4.1. Пользовательский агент также включает параметр поля заголовка Contact «reg-id», который позволяет регистратору обнаруживать и не сохранять недействительные контакты, когда пользовательский агент перезагружается или переподключается после отказа старого соединения по какой-либо причине.
For clarity, here is an example. Bob's UA creates a new TCP flow to the registrar and sends the following REGISTER request.
Для ясности приведём пример. Пользовательский агент Боба создаёт новый TCP-поток к регистратору и отправляет следующий запрос REGISTER.

The registrar challenges this registration to authenticate Bob. When the registrar adds an entry for this contact under the AOR for Bob, the registrar also keeps track of the connection over which it received this registration. The registrar saves the instance-id ("urn:uuid:00000000-0000-1000-8000-000A95A0E128") and reg-id ("1") along with the rest of the Contact header field. If the instance-id and reg-id are the same as a previous registration for the same AOR, the registrar replaces the old Contact URI and flow information. This allows a UA that has rebooted to replace its previous registration for each flow with minimal impact on overall system load.
Регистратор запрашивает аутентификацию при этой регистрации, чтобы аутентифицировать Боба. Когда регистратор добавляет запись для этого контакта под AOR Боба, он также отслеживает соединение, по которому получил эту регистрацию. Регистратор сохраняет instance-id («urn:uuid:00000000-0000-1000-8000-000A95A0E128») и reg-id («1») вместе с остальной частью поля заголовка Contact. Если instance-id и reg-id совпадают с предыдущей регистрацией для того же AOR, регистратор заменяет старый Contact URI и информацию о потоке. Это позволяет перезагрузившемуся пользовательскому агенту заменить свою предыдущую регистрацию для каждого потока с минимальным влиянием на общую нагрузку системы.
When Alice sends a request to Bob, his authoritative proxy selects the target set. The proxy forwards the request to elements in the target set based on the proxy's policy. The proxy looks at the target set and uses the instance-id to understand if two targets both end up routing to the same UA. When the proxy goes to forward a request to a given target, it looks and finds the flows over which it received the registration. The proxy then forwards the request over an existing flow, instead of resolving the Contact URI using the procedures in [RFC3263] and trying to form a new flow to that contact.
Когда Алиса отправляет запрос Бобу, его авторитетный прокси выбирает целевой набор. Прокси пересылает запрос элементам целевого набора в соответствии со своей политикой. Прокси просматривает целевой набор и использует instance-id, чтобы понять, ведут ли две цели к одному и тому же пользовательскому агенту. Собираясь переслать запрос данной цели, прокси находит потоки, по которым он получил регистрацию. Затем прокси пересылает запрос по существующему потоку вместо того, чтобы разрешать Contact URI по процедурам [RFC3263] и пытаться сформировать новый поток к этому контакту.
As described in the next section, if the proxy has multiple flows that all go to this UA, the proxy can choose any one of the registration bindings for this AOR that has the same instance-id as the selected UA.
Как описано в следующем разделе, если у прокси есть несколько потоков, ведущих к этому пользовательскому агенту, он может выбрать любую из привязок регистрации для этого AOR с тем же instance-id, что и у выбранного пользовательского агента.
3.3. Multiple Connections from a User Agent
3.3. Несколько соединений от пользовательского агента
There are various ways to deploy SIP to build a reliable and scalable system. This section discusses one such design that is possible with the mechanisms in this specification. Other designs are also possible.
Существуют различные способы развёртывания SIP для построения надёжной и масштабируемой системы. В этом разделе рассматривается один из вариантов такой архитектуры, возможный с механизмами настоящей спецификации. Возможны и другие архитектуры.
In the example system below, the logical outbound proxy/registrar for the domain is running on two hosts that share the appropriate state and can both provide registrar and outbound proxy functionality for the domain. The UA will form connections to two of the physical hosts that can perform the authoritative proxy/registrar function for the domain. Reliability is achieved by having the UA form two TCP connections to the domain.
В примере системы ниже логический исходящий прокси/регистратор для домена работает на двух узлах, которые совместно используют надлежащее состояние и оба могут обеспечивать функции регистратора и исходящего прокси для домена. Пользовательский агент установит соединения с двумя физическими узлами, способными выполнять функцию авторитетного прокси/регистратора для домена. Надёжность достигается тем, что пользовательский агент устанавливает два TCP-соединения к домену.
+-------------------+ | Domain | | Logical Proxy/Reg | | | |+-----+ +-----+| ||Host1| |Host2|| |+-----+ +-----+| +---\------------/--+ \ / \ / \ / \ / +------+ | User | | Agent| +------+
+-------------------+ | Domain | | Logical Proxy/Reg | | | |+-----+ +-----+| ||Host1| |Host2|| |+-----+ +-----+| +---\------------/--+ \ / \ / \ / \ / +------+ | User | | Agent| +------+
The UA is configured with multiple outbound proxy registration URIs. These URIs are configured into the UA through whatever the normal mechanism is to configure the proxy address and AOR in the UA. If the AOR is alice@example.com, the outbound-proxy-set might look something like "sip:primary.example.com" and "sip: secondary.example.com". Note that each URI in the outbound-proxy-set could resolve to several different physical hosts. The administrative domain that created these URIs should ensure that the two URIs resolve to separate hosts. These URIs are handled according to normal SIP processing rules, so mechanisms like DNS SRV [RFC2782] can be used to do load-balancing across a proxy farm. The approach in this document does not prevent future extensions, such as the SIP UA configuration framework [CONFIG-FMWK], from adding other ways for a User Agent to discover its outbound-proxy-set.
Пользовательский агент конфигурируется несколькими URI регистрации исходящих прокси. Эти URI задаются в пользовательском агенте тем обычным механизмом, который используется для настройки адреса прокси и AOR в агенте. Если AOR — alice@example.com, то outbound-proxy-set может выглядеть примерно как «sip:primary.example.com» и «sip:secondary.example.com». Заметим, что каждый URI в outbound-proxy-set может разрешаться в несколько различных физических узлов. Административный домен, создавший эти URI, должен обеспечить, чтобы два URI разрешались в разные узлы. Эти URI обрабатываются по обычным правилам обработки SIP, поэтому такие механизмы, как DNS SRV [RFC2782], могут использоваться для балансировки нагрузки между фермой прокси. Подход настоящего документа не препятствует будущим расширениям, таким как framework конфигурации SIP UA [CONFIG-FMWK], добавляющим иные способы обнаружения пользовательским агентом своего outbound-proxy-set.
The domain also needs to ensure that a request for the UA sent to Host1 or Host2 is then sent across the appropriate flow to the UA. The domain might choose to use the Path header approach (as described in the next section) to store this internal routing information on Host1 or Host2.
Домен также должен обеспечить, чтобы запрос к пользовательскому агенту, отправленный на Host1 или Host2, затем передавался по соответствующему потоку к пользовательскому агенту. Домен может выбрать подход с полем заголовка Path (описанный в следующем разделе), чтобы хранить эту внутреннюю информацию маршрутизации на Host1 или Host2.
When a single server fails, all the UAs that have a flow through it will detect a flow failure and try to reconnect. This can cause large loads on the server. When large numbers of hosts reconnect nearly simultaneously, this is referred to as the avalanche restart problem, and is further discussed in Section 4.5. The multiple flows to many servers help reduce the load caused by the avalanche restart. If a UA has multiple flows, and one of the servers fails, the UA delays a recommended amount of time before trying to form a new connection to replace the flow to the server that failed. By spreading out the time used for all the UAs to reconnect to a server, the load on the server farm is reduced.
При отказе одного сервера все пользовательские агенты, имеющие через него поток, обнаружат отказ потока и попытаются переподключиться. Это может вызвать большие нагрузки на сервер. Когда большое число узлов переподключается почти одновременно, это называется проблемой лавинной перезагрузки и дополнительно рассматривается в разделе 4.5. Несколько потоков ко многим серверам помогают снизить нагрузку, вызванную лавинной перезагрузкой. Если у пользовательского агента несколько потоков и один из серверов отказывает, агент выдерживает рекомендованное время перед попыткой сформировать новое соединение для замены потока к отказавшему серверу. Распределяя по времени переподключение всех пользовательских агентов к серверу, нагрузка на ферму серверов снижается.
Scalability is achieved by using DNS SRV [RFC2782] to load-balance the primary connection across a set of machines that can service the primary connection, and also using DNS SRV to load-balance across a separate set of machines that can service the secondary connection. The deployment here requires that DNS is configured with one entry that resolves to all the primary hosts and another entry that resolves to all the secondary hosts. While this introduces additional DNS configuration, the approach works and requires no additional SIP extensions to [RFC3263].
Масштабируемость достигается использованием DNS SRV [RFC2782] для балансировки нагрузки основного соединения между набором машин, способных обслуживать основное соединение, а также DNS SRV для балансировки нагрузки между отдельным набором машин, способных обслуживать вторичное соединение. Такое развёртывание требует, чтобы в DNS была одна запись, разрешающаяся во все основные узлы, и другая запись, разрешающаяся во все вторичные узлы. Хотя это вводит дополнительную конфигурацию DNS, подход работает и не требует дополнительных расширений SIP к [RFC3263].
Another motivation for maintaining multiple flows between the UA and its registrar is related to multihomed UAs. Such UAs can benefit from multiple connections from different interfaces to protect against the failure of an individual access link.
Ещё одна причина поддерживать несколько потоков между пользовательским агентом и его регистратором связана с многоинтерфейсными пользовательскими агентами. Такие агенты могут извлечь выгоду из нескольких соединений с разных интерфейсов для защиты от отказа отдельного канала доступа.
3.4. Edge Proxies
3.4. Граничные прокси
Some SIP deployments use edge proxies such that the UA sends the REGISTER to an edge proxy that then forwards the REGISTER to the registrar. There could be a NAT or firewall between the UA and the edge proxy.
В некоторых развёртываниях SIP используются граничные прокси, так что пользовательский агент отправляет REGISTER граничному прокси, который затем пересылает его регистратору. Между агентом и граничным прокси может быть NAT или межсетевой экран.
+---------+ |Registrar| |Proxy | +---------+ / \ / \ / \ +-----+ +-----+ |Edge1| |Edge2| +-----+ +-----+ \ / \ / ----------------------------NAT/FW \ / \ / +------+ |User | |Agent | +------+
+---------+ |Registrar| |Proxy | +---------+ / \ / \ / \ +-----+ +-----+ |Edge1| |Edge2| +-----+ +-----+ \ / \ / ----------------------------NAT/FW \ / \ / +------+ |User | |Agent | +------+
The edge proxy includes a Path header [RFC3327] so that when the proxy/registrar later forwards a request to this UA, the request is routed through the edge proxy.
Граничный прокси вставляет поле заголовка Path [RFC3327], чтобы, когда прокси/регистратор впоследствии пересылает запрос этому пользовательскому агенту, запрос направлялся через граничный прокси.
These systems can use effectively the same mechanism as described in the previous sections but need to use the Path header. When the edge proxy receives a registration, it needs to create an identifier value that is unique to this flow (and not a subsequent flow with the same addresses) and put this identifier in the Path header URI. This identifier has two purposes. First, it allows the edge proxy to map future requests back to the correct flow. Second, because the identifier will only be returned if the user authenticates with the registrar successfully, it allows the edge proxy to indirectly check the user's authentication information via the registrar. The identifier is placed in the user portion of a loose route in the Path header. If the registration succeeds, the edge proxy needs to map future requests (that are routed to the identifier value from the Path header) to the associated flow.
Такие системы могут фактически использовать тот же механизм, что описан в предыдущих разделах, но должны использовать поле заголовка Path. Получив регистрацию, граничный прокси должен создать значение идентификатора, уникальное для этого потока (а не для последующего потока с теми же адресами), и поместить этот идентификатор в URI поля заголовка Path. У этого идентификатора две цели. Во-первых, он позволяет граничному прокси сопоставлять будущие запросы с нужным потоком. Во-вторых, поскольку идентификатор будет возвращён только в том случае, если пользователь успешно аутентифицировался у регистратора, он позволяет граничному прокси косвенно проверить аутентификационные сведения пользователя через регистратора. Идентификатор помещается в часть пользователя свободного маршрута в поле заголовка Path. Если регистрация успешна, граничный прокси должен сопоставить будущие запросы (которые маршрутизируются к значению идентификатора из поля заголовка Path) с соответствующим потоком.
The term edge proxy is often used to refer to deployments where the edge proxy is in the same administrative domain as the registrar. However, in this specification we use the term to refer to any proxy between the UA and the registrar. For example, the edge proxy may be inside an enterprise that requires its use, and the registrar could be from a service provider with no relationship to the enterprise. Regardless of whether they are in the same administrative domain, this specification requires that registrars and edge proxies support the Path header mechanism in [RFC3327].
Термин «граничный прокси» часто используется для обозначения развёртываний, где граничный прокси находится в том же административном домене, что и регистратор. Однако в настоящей спецификации мы используем этот термин для любого прокси между пользовательским агентом и регистратором. Например, граничный прокси может находиться внутри предприятия, требующего его использования, а регистратор может принадлежать поставщику услуг, не связанному с предприятием. Независимо от того, находятся ли они в одном административном домене, настоящая спецификация требует, чтобы регистраторы и граничные прокси поддерживали механизм поля заголовка Path из [RFC3327].

This document describes two keep-alive mechanisms: a CRLF keep-alive and a STUN keep-alive. Each of these mechanisms uses a client-to- server "ping" keep-alive and a corresponding server-to-client "pong" message. This document also suggests timer values for these client keep-alive mechanisms. These timer values were chosen to keep most NAT and firewall bindings open, to detect unresponsive servers within 2 minutes, and to mitigate against the avalanche restart problem. However, the client may choose different timer values to suit its needs, for example to optimize battery life. Эти значения выбраны так, чтобы сохранять открытыми большинство привязок NAT и межсетевых экранов, обнаруживать неотвечающие серверы в течение 2 минут и смягчать проблему лавинной перезагрузки. Однако клиент может выбрать другие значения таймеров, исходя из своих потребностей, например для оптимизации времени работы от батареи. В некоторых средах сервер также может отслеживать время с момента получения ping по потоку, чтобы оценить вероятность того, что поток по-прежнему пригоден для доставки сообщений SIP.
When the UA detects that a flow has failed or that the flow definition has changed, the UA needs to re-register and will use the back-off mechanism described in Section 4.5 to provide congestion relief when a large number of agents simultaneously reboot.
Когда пользовательский агент обнаруживает, что поток отказал или что определение потока изменилось, он должен повторно зарегистрироваться и использует механизм отсрочки, описанный в разделе 4.5, чтобы снизить перегрузку, когда большое число агентов перезагружается одновременно.
A keep-alive mechanism needs to keep NAT bindings refreshed; for connections, it also needs to detect failure of a connection; and for connectionless transports, it needs to detect flow failures including changes to the NAT public mapping. For connection-oriented transports such as TCP [RFC0793] and SCTP [RFC4960], this specification describes a keep-alive approach based on sending CRLFs. For connectionless transport, such as UDP [RFC0768], this specification describes using STUN [RFC5389] over the same flow as the SIP traffic to perform the keep-alive.
Механизм keep-alive должен поддерживать свежесть привязок NAT; для соединений он также должен обнаруживать отказ соединения; а для транспортов без установления соединения он должен обнаруживать отказы потоков, включая изменения публичного отображения NAT. Для транспортов с установлением соединения, таких как TCP [RFC0793] и SCTP [RFC4960], настоящая спецификация описывает подход к keep-alive, основанный на отправке CRLF. Для транспорта без установления соединения, такого как UDP [RFC0768], настоящая спецификация описывает использование STUN [RFC5389] по тому же потоку, что и трафик SIP, для выполнения keep-alive.
UAs and Proxies are also free to use native transport keep-alives; however, the application may not be able to set these timers on a per-connection basis, and the server certainly cannot make any assumption about what values are used. Use of native transport keep-alives is outside the scope of this document.
Пользовательские агенты и прокси также вправе использовать собственные keep-alive транспорта; однако приложение может не иметь возможности задавать эти таймеры для каждого соединения, а сервер, безусловно, не может делать никаких предположений о том, какие значения используются. Использование собственных keep-alive транспорта выходит за рамки настоящего документа.
3.5.1. CRLF Keep-Alive Technique
3.5.1. Метод keep-alive на основе CRLF
This approach can only be used with connection-oriented transports such as TCP or SCTP. The client periodically sends a double-CRLF (the "ping") then waits to receive a single CRLF (the "pong"). If the client does not receive a "pong" within an appropriate amount of time, it considers the flow failed.
Этот подход может использоваться только с транспортами с установлением соединения, такими как TCP или SCTP. Клиент периодически отправляет двойной CRLF («ping»), а затем ждёт получения одиночного CRLF («pong»). Если клиент не получает «pong» за надлежащее время, он считает поток отказавшим.
Note: Sending a CRLF over a connection-oriented transport is backwards compatible (because of requirements in Section 7.5 of [RFC3261]), but only implementations which support this specification will respond to a "ping" with a "pong".
Примечание: отправка CRLF по транспорту с установлением соединения обратно совместима (благодаря требованиям раздела 7.5 [RFC3261]), но отвечать на «ping» сообщением «pong» будут только реализации, поддерживающие настоящую спецификацию.
3.5.2. STUN Keep-Alive Technique
3.5.2. Метод keep-alive на основе STUN
This approach can only be used for connection-less transports, such as UDP.
Этот подход применим только к транспортам без установления соединения, например UDP.
For connection-less transports, a flow definition could change because a NAT device in the network path reboots and the resulting public IP address or port mapping for the UA changes. To detect this, STUN requests are sent over the same flow that is being used for the SIP traffic. The proxy or registrar acts as a limited Session Traversal Utilities for NAT (STUN) [RFC5389] server on the SIP signaling port.
Для транспортов без установления соединения определение потока может измениться из-за перезагрузки устройства NAT на пути следования, в результате чего публичный IP-адрес или отображение порта пользовательского агента меняются. Чтобы обнаружить это, запросы STUN отправляются по тому же потоку, который используется для трафика SIP. Прокси или регистратор выступает в роли ограниченного сервера STUN (утилит обхода сеансов для NAT) [RFC5389] на порту сигнализации SIP.
Note: The STUN mechanism is very robust and allows the detection of a changed IP address and port. Many other options were considered, but the SIP Working Group selected the STUN-based approach. Approaches using SIP requests were abandoned because many believed that good performance and full backwards compatibility using this method were mutually exclusive.
Примечание: механизм STUN весьма устойчив и позволяет обнаруживать изменение IP-адреса и порта. Рассматривались многие другие варианты, но рабочая группа SIP выбрала подход на основе STUN. Подходы с использованием запросов SIP были отброшены, поскольку многие считали, что хорошая производительность и полная обратная совместимость при таком методе взаимно исключают друг друга.
4. User Agent Procedures
4. Процедуры пользовательского агента
4.1. Instance ID Creation
4.1. Создание идентификатора экземпляра
Each UA MUST have an Instance Identifier Uniform Resource Name (URN) [RFC2141] that uniquely identifies the device. Usage of a URN provides a persistent and unique name for the UA instance. It also provides an easy way to guarantee uniqueness within the AOR. This URN MUST be persistent across power cycles of the device. The instance ID MUST NOT change as the device moves from one network to another.
Каждый пользовательский агент ДОЛЖЕН иметь универсальное имя ресурса (URN) идентификатора экземпляра [RFC2141], которое однозначно идентифицирует устройство. Использование URN обеспечивает постоянное и уникальное имя для экземпляра пользовательского агента. Оно также даёт простой способ гарантировать уникальность в пределах AOR. Это URN ДОЛЖНО сохраняться при циклах отключения питания устройства. Идентификатор экземпляра НЕ ДОЛЖЕН меняться при перемещении устройства из одной сети в другую.
A UA SHOULD create a Universally Unique Identifier (UUID) URN [RFC4122] as its instance-id. The UUID URN allows for non- centralized computation of a URN based on time, unique names (such as a MAC address), or a random number generator.
Пользовательский агент СЛЕДУЕТ создавать в качестве своего instance-id универсальное уникальное имя (UUID) URN [RFC4122]. UUID URN допускает децентрализованное вычисление URN на основе времени, уникальных имён (например, MAC-адреса) или генератора случайных чисел.
Note: A device like a "soft phone", when first installed, can generate a UUID [RFC4122] and then save this in persistent storage for all future use. For a device such as a "hard phone", which will only ever have a single SIP UA present, the UUID can include the MAC address and be generated at any time because it is guaranteed that no other UUID is being generated at the same time on that physical device. This means the value of the time component of the UUID can be arbitrarily selected to be any time less than the time when the device was manufactured. A time of 0 (as shown in the example in Section 3.2) is perfectly legal as long as the device knows no other UUIDs were generated at this time on this device.
Примечание: устройство типа «софтфона» при первой установке может сгенерировать UUID [RFC4122] и затем сохранить его в энергонезависимой памяти для дальнейшего использования. Для устройства типа «аппаратного телефона», в котором всегда будет присутствовать только один SIP-пользовательский агент, UUID может включать MAC-адрес и генерироваться в любой момент, поскольку гарантировано, что никакой другой UUID в это же время на этом физическом устройстве не генерируется. Это означает, что значение временной составляющей UUID может быть произвольно выбрано равным любому моменту ранее времени изготовления устройства. Время 0 (как показано в примере в разделе 3.2) вполне допустимо, если устройство знает, что никакие другие UUID в это время на этом устройстве не генерировались.
If a URN scheme other than UUID is used, the UA MUST only use URNs for which an RFC (from the IETF stream) defines how the specific URN needs to be constructed and used in the "+sip.instance" Contact header field parameter for outbound behavior. To convey its instance-id in both requests and responses, the UA includes a "sip.instance" media feature tag as a UA characteristic [RFC3840]. This media feature tag is encoded in the Contact header field as the "+sip.instance" Contact header field parameter. One case where a UA could prefer to omit the "sip.instance" media feature tag is when it is making an anonymous request or some other privacy concern requires that the UA not reveal its identity.
Если используется схема URN, отличная от UUID, пользовательский агент ДОЛЖЕН использовать только те URN, для которых RFC (из потока IETF) определяет, как конкретный URN должен быть построен и использован в параметре поля заголовка Contact «+sip.instance» для поведения outbound. Чтобы передавать свой instance-id как в запросах, так и в ответах, пользовательский агент включает тег характеристики среды «sip.instance» в качестве характеристики UA [RFC3840]. Этот тег характеристики среды кодируется в поле заголовка Contact как параметр поля заголовка Contact «+sip.instance». Один случай, когда пользовательский агент мог бы предпочесть опустить тег характеристики среды «sip.instance», — это когда он выполняет анонимный запрос или какая-либо иная причина, связанная с конфиденциальностью, требует, чтобы агент не раскрывал свою личность.
Note: [RFC3840] defines equality rules for callee capabilities parameters, and according to that specification, the "sip.instance" media feature tag will be compared by case- sensitive string comparison. This means that the URN will be encapsulated by angle brackets ("<" and ">") when it is placed within the quoted string value of the "+sip.instance" Contact header field parameter. The case-sensitive matching rules apply only to the generic usages defined in the callee capabilities [RFC3840] and the caller preferences [RFC3841] specifications. When the instance ID is used in this specification, it is "extracted" from the value in the "sip.instance" media feature tag.
Примечание: [RFC3840] определяет правила равенства для параметров возможностей вызываемого; согласно этой спецификации тег характеристики среды «sip.instance» сравнивается с помощью чувствительного к регистру сравнения строк. Это означает, что URN будет заключён в угловые скобки («<» и «>»), когда он помещается внутрь значения в кавычках параметра поля заголовка Contact «+sip.instance». Правила сопоставления с учётом регистра применяются только к общим способам использования, определённым в спецификациях возможностей вызываемого [RFC3840] и предпочтений вызывающего [RFC3841]. Когда идентификатор экземпляра используется в настоящей спецификации, он «извлекается» из значения тега характеристики среды «sip.instance».
Thus, equality comparisons are performed using the rules for URN equality that are specific to the scheme in the URN. If the element performing the comparisons does not understand the URN scheme, it performs the comparisons using the lexical equality rules defined in [RFC2141]. Lexical equality could result in two URNs being considered unequal when they are actually equal. In this specific usage of URNs, the only element that provides the URN is the SIP UA instance identified by that URN. As a result, the UA instance has to provide lexically equivalent URNs in each registration it generates. This is likely to be normal behavior in any case; clients are not likely to modify the value of the instance ID so that it remains functionally equivalent to (yet lexicographically different from) previous registrations.
Таким образом, сравнения на равенство выполняются по правилам равенства URN, специфичным для схемы данного URN. Если элемент, выполняющий сравнения, не понимает схему URN, он выполняет сравнения по правилам лексического равенства, определённым в [RFC2141]. Лексическое равенство может привести к тому, что два URN будут признаны неравными, хотя на самом деле они равны. В этом конкретном способе использования URN единственный элемент, предоставляющий URN, — это экземпляр SIP-пользовательского агента, идентифицируемый этим URN. В результате экземпляр пользовательского агента должен предоставлять лексически эквивалентные URN в каждой регистрации, которую он формирует. Это, скорее всего, будет обычным поведением в любом случае; клиенты вряд ли станут изменять значение идентификатора экземпляра так, чтобы оно оставалось функционально эквивалентным (но лексикографически отличным от) предыдущих регистраций.
4.2. Registrations
4.2. Регистрации
4.2.1. Initial Registrations
4.2.1. Начальные регистрации
At configuration time, UAs obtain one or more SIP URIs representing the default outbound-proxy-set. This specification assumes the set is determined via any of a number of configuration mechanisms, and future specifications can define additional mechanisms such as using DNS to discover this set. How the UA is configured is outside the scope of this specification. However, a UA MUST support sets with at least two outbound proxy URIs and SHOULD support sets with up to four URIs. For each outbound proxy URI in the set, the User Agent Client (UAC) SHOULD send a REGISTER request using this URI as the default outbound proxy. (Alternatively, the UA could limit the number of flows formed to conserve battery power, for example). If the set has more than one URI, the UAC MUST send a REGISTER request to at least two of the default outbound proxies from the set. UAs that support this specification MUST include the outbound option tag in a Supported header field in a REGISTER request. Each of these REGISTER requests will use a unique Call-ID. Forming the route set for the request is outside the scope of this document, but typically results in sending the REGISTER such that the topmost Route header field contains a loose route to the outbound proxy URI.
Во время конфигурирования пользовательские агенты получают один или несколько SIP URI, представляющих outbound-proxy-set по умолчанию. Настоящая спецификация предполагает, что набор определяется любым из ряда механизмов конфигурирования, а будущие спецификации могут определять дополнительные механизмы, такие как использование DNS для обнаружения этого набора. Способ конфигурирования пользовательского агента выходит за рамки настоящей спецификации. Однако пользовательский агент ДОЛЖЕН поддерживать наборы как минимум с двумя URI исходящих прокси и СЛЕДУЕТ поддерживать наборы до четырёх URI. Для каждого URI исходящего прокси в наборе клиент пользовательского агента (UAC) СЛЕДУЕТ отправлять запрос REGISTER, используя этот URI в качестве исходящего прокси по умолчанию. (В качестве альтернативы пользовательский агент мог бы, например, ограничить число формируемых потоков для экономии заряда батареи.) Если набор содержит более одного URI, UAC ДОЛЖЕН отправить запрос REGISTER как минимум двум исходящим прокси по умолчанию из набора. Пользовательские агенты, поддерживающие настоящую спецификацию, ДОЛЖНЫ включать option tag outbound в поле заголовка Supported в запросе REGISTER. Каждый из этих запросов REGISTER будет использовать уникальный Call-ID. Формирование набора маршрутов для запроса выходит за рамки настоящего документа, но обычно приводит к отправке REGISTER так, что самое верхнее поле заголовка Route содержит свободный маршрут к URI исходящего прокси.
REGISTER requests, other than those described in Section 4.2.3, MUST include an instance-id media feature tag as specified in Section 4.1.
Запросы REGISTER, кроме описанных в разделе 4.2.3, ДОЛЖНЫ включать тег характеристики среды instance-id, как указано в разделе 4.1.
A UAC conforming to this specification MUST include in the Contact header field, a "reg-id" parameter that is distinct from other "reg-id" parameters used in other registrations that use the same "+sip.instance" Contact header field parameter and AOR. Each one of these registrations will form a new flow from the UA to the proxy. The sequence of reg-id values does not have to be sequential but MUST be exactly the same sequence of reg-id values each time the UA instance power cycles or reboots, so that the reg-id values will collide with the previously used reg-id values. This is so the registrar can replace the older registrations.
UAC, соответствующий настоящей спецификации, ДОЛЖЕН включать в поле заголовка Contact параметр «reg-id», отличный от других параметров «reg-id», используемых в других регистрациях с тем же параметром поля заголовка Contact «+sip.instance» и AOR. Каждая из этих регистраций формирует новый поток от пользовательского агента к прокси. Последовательность значений reg-id не обязана быть последовательной, но ДОЛЖНА быть в точности одной и той же последовательностью значений reg-id каждый раз при перезагрузке или цикле питания экземпляра пользовательского агента, чтобы значения reg-id совпадали с ранее использованными значениями reg-id. Это нужно, чтобы регистратор мог заменить более старые регистрации.
Note: The UAC can situationally decide whether to request outbound behavior by including or omitting the "reg-id" Contact header field parameter. For example, imagine the outbound-proxy-set contains two proxies in different domains, EP1 and EP2. If an outbound-style registration succeeded for a flow through EP1, the UA might decide to include 'outbound' in its Require header field when registering with EP2, in order to ensure consistency. Similarly, if the registration through EP1 did not support outbound, the UA might not register with EP2 at all.
Примечание: UAC может ситуативно решать, запрашивать ли поведение outbound, включая или опуская параметр поля заголовка Contact «reg-id». Например, представьте, что outbound-proxy-set содержит два прокси в разных доменах, EP1 и EP2. Если регистрация в стиле outbound через EP1 прошла успешно, пользовательский агент может решить включить 'outbound' в своё поле заголовка Require при регистрации у EP2, чтобы обеспечить согласованность. Аналогично, если регистрация через EP1 не поддерживала outbound, пользовательский агент может вообще не регистрироваться у EP2.
The UAC MUST support the Path header [RFC3327] mechanism, and indicate its support by including the 'path' option-tag in a Supported header field value in its REGISTER requests. Other than optionally examining the Path vector in the response, this is all that is required of the UAC to support Path.
UAC ДОЛЖЕН поддерживать механизм поля заголовка Path [RFC3327] и указывать свою поддержку, включая option-tag 'path' в значение поля заголовка Supported в своих запросах REGISTER. Помимо необязательного изучения вектора Path в ответе, это всё, что требуется от UAC для поддержки Path.
The UAC examines successful registration responses for the presence of an outbound option-tag in a Require header field value. Presence of this option-tag indicates that the registrar is compliant with this specification, and that any edge proxies which needed to participate are also compliant. If the registrar did not support outbound, the UA has potentially registered an un-routable contact. It is the responsibility of the UA to remove any inappropriate Contacts.
UAC проверяет успешные ответы на регистрацию на наличие option-tag outbound в значении поля заголовка Require. Наличие этого option-tag указывает, что регистратор соответствует настоящей спецификации и что любые граничные прокси, которым нужно было участвовать, также соответствуют ей. Если регистратор не поддерживал outbound, пользовательский агент, возможно, зарегистрировал контакт, не поддающийся маршрутизации. Ответственность за удаление любых неподходящих Contact'ов лежит на пользовательском агенте.
If outbound registration succeeded, as indicated by the presence of the outbound option-tag in the Require header field of a successful registration response, the UA begins sending keep-alives as described in Section 4.4.
Если регистрация outbound прошла успешно, на что указывает наличие option-tag outbound в поле заголовка Require успешного ответа на регистрацию, пользовательский агент начинает отправлять keep-alive, как описано в разделе 4.4.
Note: The UA needs to honor 503 (Service Unavailable) responses to registrations as described in [RFC3261] and [RFC3263]. In particular, implementors should note that when receiving a 503 (Service Unavailable) response with a Retry-After header field, the UA is expected to wait the indicated amount of time and retry the registration. A Retry-After header field value of 0 is valid and indicates the UA is expected to retry the REGISTER request immediately. Implementations need to ensure that when retrying the REGISTER request, they revisit the DNS resolution results such that the UA can select an alternate host from the one chosen the previous time the URI was resolved.
Примечание: пользовательский агент должен соблюдать ответы 503 (Service Unavailable) на регистрации, как описано в [RFC3261] и [RFC3263]. В частности, разработчикам следует учесть, что при получении ответа 503 (Service Unavailable) с полем заголовка Retry-After пользовательский агент должен подождать указанное время и повторить регистрацию. Значение поля заголовка Retry-After, равное 0, допустимо и указывает, что пользовательский агент должен немедленно повторить запрос REGISTER. Реализации должны обеспечить, чтобы при повторной попытке запроса REGISTER они заново обращались к результатам разрешения DNS, чтобы пользовательский агент мог выбрать другой узел, отличный от выбранного в прошлый раз при разрешении URI.
If the registering UA receives a 439 (First Hop Lacks Outbound Support) response to a REGISTER request, it MAY re-attempt registration without using the outbound mechanism (subject to local policy at the client). If the client has one or more alternate outbound proxies available, it MAY re-attempt registration through such outbound proxies. See Section 11.6 for more information on the 439 response code.
Если регистрирующийся пользовательский агент получает на запрос REGISTER ответ 439 (First Hop Lacks Outbound Support), он МОЖЕТ повторить попытку регистрации без использования механизма outbound (с учётом локальной политики клиента). Если у клиента есть один или несколько альтернативных исходящих прокси, он МОЖЕТ повторить регистрацию через такие исходящие прокси. См. раздел 11.6 для получения дополнительной информации о коде ответа 439.
4.2.2. Subsequent REGISTER Requests
4.2.2. Последующие запросы REGISTER
Registrations for refreshing a binding and for removing a binding use the same instance-id and reg-id values as the corresponding initial registration where the binding was added. Registrations that merely refresh an existing binding are sent over the same flow as the original registration where the binding was added.
Регистрации для обновления привязки и для удаления привязки используют те же значения instance-id и reg-id, что и соответствующая начальная регистрация, в которой была добавлена привязка. Регистрации, которые лишь обновляют существующую привязку, отправляются по тому же потоку, что и исходная регистрация, в которой была добавлена привязка.
If a re-registration is rejected with a recoverable error response, for example by a 503 (Service Unavailable) containing a Retry-After header, the UAC SHOULD NOT tear down the corresponding flow if the flow uses a connection-oriented transport such as TCP. As long as "pongs" are received in response to "pings", the flow SHOULD be kept active until a non-recoverable error response is received. This prevents unnecessary closing and opening of connections.
Если повторная регистрация отклонена восстановимым ответом об ошибке, например ответом 503 (Service Unavailable), содержащим заголовок Retry-After, UAC НЕ СЛЕДУЕТ разрывать соответствующий поток, если поток использует транспорт с установлением соединения, такой как TCP. Пока в ответ на «ping» приходят «pong», поток СЛЕДУЕТ поддерживать активным до получения невосстановимого ответа об ошибке. Это предотвращает ненужное закрытие и открытие соединений.
4.2.3. Third-Party Registrations
4.2.3. Регистрации третьих сторон
In an initial registration or re-registration, a UA MUST NOT include a "reg-id" header field parameter in the Contact header field if the registering UA is not the same instance as the UA referred to by the target Contact header field. (This practice is occasionally used to install forwarding policy into registrars.)
При начальной регистрации или повторной регистрации пользовательский агент НЕ ДОЛЖЕН включать параметр поля заголовка «reg-id» в поле заголовка Contact, если регистрирующийся пользовательский агент не является тем же экземпляром, что и пользовательский агент, на который ссылается целевое поле заголовка Contact. (Эта практика иногда используется для установки политики переадресации в регистраторах.)
A UAC also MUST NOT include an instance-id feature tag or "reg-id" Contact header field parameter in a request to un-register all Contacts (a single Contact header field value with the value of "*").
UAC также НЕ ДОЛЖЕН включать тег характеристики instance-id или параметр поля заголовка Contact «reg-id» в запрос на отмену регистрации всех Contact'ов (единственное значение поля заголовка Contact со значением «*»).
4.3. Sending Non-REGISTER Requests
4.3. Отправка запросов, отличных от REGISTER
When a UAC is about to send a request, it first performs normal processing to select the next hop URI. The UA can use a variety of techniques to compute the route set and accordingly the next hop URI. Discussion of these techniques is outside the scope of this document. UAs that support this specification SHOULD include the outbound option tag in a Supported header field in a request that is not a REGISTER request.
Когда UAC собирается отправить запрос, он сначала выполняет обычную обработку для выбора URI следующего перехода. Пользовательский агент может использовать различные методы для вычисления набора маршрутов и, соответственно, URI следующего перехода. Обсуждение этих методов выходит за рамки настоящего документа. Пользовательские агенты, поддерживающие настоящую спецификацию, СЛЕДУЕТ включать option tag outbound в поле заголовка Supported в запросе, не являющемся запросом REGISTER.
The UAC performs normal DNS resolution on the next hop URI (as described in [RFC3263]) to find a protocol, IP address, and port. For protocols that don't use TLS, if the UAC has an existing flow to this IP address, and port with the correct protocol, then the UAC MUST use the existing connection. For TLS protocols, there MUST also be a match between the host production in the next hop and one of the URIs contained in the subjectAltName in the peer certificate. If the UAC cannot use one of the existing flows, then it SHOULD form a new flow by sending a datagram or opening a new connection to the next hop, as appropriate for the transport protocol.
UAC выполняет обычное разрешение DNS для URI следующего перехода (как описано в [RFC3263]), чтобы найти протокол, IP-адрес и порт. Для протоколов, не использующих TLS, если у UAC есть существующий поток к этому IP-адресу и порту с правильным протоколом, то UAC ДОЛЖЕН использовать существующее соединение. Для протоколов TLS также ДОЛЖНО быть соответствие между именем хоста в следующем переходе и одним из URI, содержащихся в subjectAltName в сертификате партнёра. Если UAC не может использовать один из существующих потоков, ему СЛЕДУЕТ сформировать новый поток, отправив дейтаграмму или открыв новое соединение к следующему переходу, в зависимости от транспортного протокола.
Typically, a UAC using the procedures of this document and sending a dialog-forming request will want all subsequent requests in the dialog to arrive over the same flow. If the UAC is using a Globally Routable UA URI (GRUU) [RFC5627] that was instantiated using a Contact header field value that included an "ob" parameter, the UAC sends the request over the flow used for registration, and subsequent requests will arrive over that same flow. If the UAC is not using such a GRUU, then the UAC adds an "ob" parameter to its Contact header field value. This will cause all subsequent requests in the dialog to arrive over the flow instantiated by the dialog-forming request. This case is typical when the request is sent prior to registration, such as in the initial subscription dialog for the configuration framework [CONFIG-FMWK]. Note: If the UAC wants a UDP flow to work through NATs or firewalls, it still needs to put the 'rport' parameter [RFC3581] in its Via header field value, and send from the port it is prepared to receive on. More general information about NAT traversal in SIP is described in [NAT-SCEN].
Как правило, UAC, использующий процедуры настоящего документа и отправляющий запрос, формирующий диалог, хочет, чтобы все последующие запросы диалога приходили по тому же потоку. Если UAC использует глобально маршрутизируемый URI пользовательского агента (GRUU) [RFC5627], созданный с использованием значения поля заголовка Contact, которое включало параметр «ob», UAC отправляет запрос по потоку, использованному для регистрации, и последующие запросы будут приходить по тому же потоку. Если UAC не использует такой GRUU, то UAC добавляет параметр «ob» в значение своего поля заголовка Contact. Это приведёт к тому, что все последующие запросы диалога будут приходить по потоку, созданному запросом, формирующим диалог. Этот случай типичен, когда запрос отправляется до регистрации, например в начальном диалоге подписки для framework конфигурации [CONFIG-FMWK]. Примечание: если UAC хочет, чтобы поток UDP работал через NAT или межсетевые экраны, ему по-прежнему нужно поместить параметр 'rport' [RFC3581] в значение поля заголовка Via и отправлять с того порта, на котором он готов принимать. Более общая информация о прохождении через NAT в SIP описана в [NAT-SCEN].
4.4. Keep-Alives and Detecting Flow Failure
4.4. Keep-alive и обнаружение отказа потока
Keep-alives are used for refreshing NAT/firewall bindings and detecting flow failure. Flows can fail for many reasons including the rebooting of NATs and the crashing of edge proxies.
Keep-alive используются для обновления привязок NAT/межсетевых экранов и обнаружения отказа потока. Потоки могут отказывать по многим причинам, включая перезагрузку NAT и аварийное завершение граничных прокси.
As described in Section 4.2, a UA that registers will begin sending keep-alives after an appropriate registration response. A UA that does not register (for example, a PSTN gateway behind a firewall) can also send keep-alives under certain circumstances.
Как описано в разделе 4.2, пользовательский агент, который регистрируется, начинает отправлять keep-alive после надлежащего ответа на регистрацию. Пользовательский агент, который не регистрируется (например, шлюз PSTN за межсетевым экраном), также может при определённых обстоятельствах отправлять keep-alive.
Under specific circumstances, a UAC might be allowed to send STUN keep-alives even if the procedures in Section 4.2 were not completed, provided that there is an explicit indication that the target first- hop SIP node supports STUN keep-alives. For example, this applies to a non-registering UA or to a case where the UA registration succeeded, but the response did not include the outbound option-tag in the Require header field.
При определённых обстоятельствах UAC может быть разрешено отправлять keep-alive STUN, даже если процедуры раздела 4.2 не были завершены, при условии наличия явного указания на то, что целевой SIP-узел первого перехода поддерживает keep-alive STUN. Например, это относится к нерегистрирующемуся пользовательскому агенту или к случаю, когда регистрация пользовательского агента прошла успешно, но ответ не содержал option-tag outbound в поле заголовка Require.
Note: A UA can "always" send a double CRLF (a "ping") over connection-oriented transports as this is already allowed by Section 7.5 of [RFC3261]. However a UA that did not register using outbound registration cannot expect a CRLF in response (a "pong") unless the UA has an explicit indication that CRLF keep- alives are supported as described in this section. Likewise, a UA that did not successfully register with outbound procedures needs explicit indication that the target first-hop SIP node supports STUN keep-alives before it can send any STUN messages.
Примечание: пользовательский агент может «всегда» отправлять двойной CRLF («ping») по транспортам с установлением соединения, поскольку это уже разрешено разделом 7.5 [RFC3261]. Однако пользовательский агент, который не регистрировался с использованием регистрации outbound, не может ожидать CRLF в ответ («pong»), если у него нет явного указания на поддержку keep-alive CRLF, как описано в этом разделе. Аналогично, пользовательский агент, который не зарегистрировался успешно с помощью процедур outbound, нуждается в явном указании того, что целевой SIP-узел первого перехода поддерживает keep-alive STUN, прежде чем он сможет отправлять какие-либо сообщения STUN.
A configuration option indicating keep-alive support for a specific target is considered an explicit indication. If these conditions are satisfied, the UA sends its keep-alives according to the same guidelines as those used when UAs register; these guidelines are described below.
Параметр конфигурации, указывающий поддержку keep-alive для конкретной цели, считается явным указанием. Если эти условия выполнены, пользовательский агент отправляет свои keep-alive в соответствии с теми же рекомендациями, которые используются при регистрации пользовательских агентов; эти рекомендации описаны ниже.
The UA needs to detect when a specific flow fails. The UA actively tries to detect failure by periodically sending keep-alive messages using one of the techniques described in Sections 4.4.1 or 4.4.2. If a flow with a registration has failed, the UA follows the procedures in Section 4.2 to form a new flow to replace the failed one. When a successful registration response contains the Flow-Timer header field, the value of this header field is the number of seconds the server is prepared to wait without seeing keep-alives before it could consider the corresponding flow dead. Note that the server would wait for an amount of time larger than the Flow-Timer in order to have a grace period to account for transport delay. The UA MUST send keep-alives at least as often as this number of seconds. If the UA uses the server-recommended keep-alive frequency it SHOULD send its keep-alives so that the interval between each keep-alive is randomly distributed between 80% and 100% of the server-provided time. For example, if the server suggests 120 seconds, the UA would send each keep-alive with a different frequency between 95 and 120 seconds.
Пользовательский агент должен обнаруживать отказ конкретного потока. Пользовательский агент активно пытается обнаружить отказ, периодически отправляя сообщения keep-alive с использованием одного из методов, описанных в разделах 4.4.1 или 4.4.2. Если поток с регистрацией отказал, пользовательский агент следует процедурам раздела 4.2, чтобы сформировать новый поток вместо отказавшего. Когда успешный ответ на регистрацию содержит поле заголовка Flow-Timer, значение этого поля заголовка — число секунд, в течение которых сервер готов ждать, не видя keep-alive, прежде чем он сможет считать соответствующий поток неисправным. Заметим, что сервер будет ждать время, большее Flow-Timer, чтобы иметь льготный период на компенсацию транспортной задержки. Пользовательский агент ДОЛЖЕН отправлять keep-alive не реже, чем раз в это число секунд. Если пользовательский агент использует рекомендованную сервером частоту keep-alive, ему СЛЕДУЕТ отправлять keep-alive так, чтобы интервал между каждым keep-alive был случайно распределён между 80 % и 100 % времени, предоставленного сервером. Например, если сервер предлагает 120 секунд, пользовательский агент будет отправлять каждый keep-alive с разной частотой в интервале от 95 до 120 секунд.
If no Flow-Timer header field was present in a register response for this flow, the UA can send keep-alives at its discretion. The sections below provide RECOMMENDED default values for these keep- alives.
Если в ответе на регистрацию для этого потока не было поля заголовка Flow-Timer, пользовательский агент может отправлять keep-alive по своему усмотрению. Разделы ниже содержат РЕКОМЕНДУЕМЫЕ значения по умолчанию для этих keep-alive.
The client needs to perform normal [RFC3263] SIP DNS resolution on the URI from the outbound-proxy-set to pick a transport. Once a transport is selected, the UA selects the keep-alive approach that is recommended for that transport.
Клиент должен выполнить обычное разрешение SIP DNS по [RFC3263] для URI из outbound-proxy-set, чтобы выбрать транспорт. После выбора транспорта пользовательский агент выбирает подход к keep-alive, рекомендованный для этого транспорта.
Section 4.4.1 describes a keep-alive mechanism for connection- oriented transports such as TCP or SCTP. Section 4.4.2 describes a keep-alive mechanism for connection-less transports such as UDP. Support for other transports such as DCCP [RFC4340] is for further study.
Раздел 4.4.1 описывает механизм keep-alive для транспортов с установлением соединения, таких как TCP или SCTP. Раздел 4.4.2 описывает механизм keep-alive для транспортов без установления соединения, таких как UDP. Поддержка других транспортов, таких как DCCP [RFC4340], требует дальнейшего изучения.
4.4.1. Keep-Alive with CRLF
4.4.1. Keep-alive с CRLF
This approach MUST only be used with connection oriented transports such as TCP or SCTP; it MUST NOT be used with connection-less transports such as UDP.
Этот подход ДОЛЖЕН использоваться только с транспортами с установлением соединения, такими как TCP или SCTP; он НЕ ДОЛЖЕН использоваться с транспортами без установления соединения, такими как UDP.
A User Agent that forms flows checks if the configured URI to which the UA is connecting resolves to a connection-oriented transport (e.g., TCP and TLS over TCP).
Пользовательский агент, формирующий потоки, проверяет, разрешается ли сконфигурированный URI, к которому подключается агент, в транспорт с установлением соединения (например, TCP и TLS поверх TCP).
For this mechanism, the client "ping" is a double-CRLF sequence, and the server "pong" is a single CRLF, as defined in the ABNF below:
Для этого механизма «ping» клиента — это последовательность двойного CRLF, а «pong» сервера — одиночный CRLF, как определено в ABNF ниже:
CRLF = CR LF double-CRLF = CR LF CR LF CR = %x0D LF = %x0A
CRLF = CR LF double-CRLF = CR LF CR LF CR = %x0D LF = %x0A
The "ping" and "pong" need to be sent between SIP messages and cannot be sent in the middle of a SIP message. If sending over TLS, the CRLFs are sent inside the TLS protected channel. If sending over a SigComp [RFC3320] compressed data stream, the CRLF keep-alives are sent inside the compressed stream. The double CRLF is considered a single SigComp message. The specific mechanism for representing these characters is an implementation-specific matter to be handled by the SigComp compressor at the sending end.
«ping» и «pong» нужно отправлять между сообщениями SIP, их нельзя отправлять в середине сообщения SIP. При отправке по TLS последовательности CRLF отправляются внутри защищённого канала TLS. При отправке по сжатому потоку данных SigComp [RFC3320] keep-alive CRLF отправляются внутри сжатого потока. Двойной CRLF считается одним сообщением SigComp. Конкретный механизм представления этих символов является вопросом реализации и должен обрабатываться компрессором SigComp на отправляющей стороне.
If a pong is not received within 10 seconds after sending a ping (or immediately after processing any incoming message being received when that 10 seconds expires), then the client MUST treat the flow as failed. Clients MUST support this CRLF keep-alive.
Если pong не получен в течение 10 секунд после отправки ping (или сразу после обработки любого входящего сообщения, полученного при истечении этих 10 секунд), то клиент ДОЛЖЕН считать поток отказавшим. Клиенты ДОЛЖНЫ поддерживать этот keep-alive CRLF.
Note: This value of 10-second timeout was selected to be long enough that it allows plenty of time for a server to send a response even if the server is temporarily busy with an administrative activity. At the same time, it was selected to be small enough that a UA registered to two redundant servers with unremarkable hardware uptime could still easily provide very high levels of overall reliability. Although some Internet protocols are designed for round-trip times over 10 seconds, SIP for real- time communications is not really usable in these type of environments as users often abandon calls before waiting much more than a few seconds.
Примечание: это значение тайм-аута в 10 секунд выбрано достаточно большим, чтобы дать серверу достаточно времени отправить ответ даже при временной занятости административными действиями. В то же время оно выбрано достаточно малым, чтобы пользовательский агент, зарегистрированный у двух резервирующих друг друга серверов с невыдающейся аппаратной надёжностью, всё равно мог легко обеспечить очень высокий общий уровень надёжности. Хотя некоторые интернет-протоколы рассчитаны на времена кругового обхода более 10 секунд, SIP для связи в реальном времени действительно непригоден в таких средах, поскольку пользователи часто прекращают вызов, не дождавшись и нескольких секунд.
When a Flow-Timer header field is not provided in the most recent success registration response, the proper selection of keep-alive frequency is primarily a trade-off between battery usage and availability. The UA MUST select a random number between a fixed or configurable upper bound and a lower bound, where the lower bound is 20% less then the upper bound. The fixed upper bound or the default configurable upper bound SHOULD be 120 seconds (95 seconds for the lower bound) where battery power is not a concern and 840 seconds (672 seconds for the lower bound) where battery power is a concern. The random number will be different for each keep-alive "ping".
Когда поле заголовка Flow-Timer не предоставлено в последнем успешном ответе на регистрацию, правильный выбор частоты keep-alive является в первую очередь компромиссом между расходом батареи и доступностью. Пользовательский агент ДОЛЖЕН выбирать случайное число между фиксированной или настраиваемой верхней границей и нижней границей, где нижняя граница на 20 % меньше верхней. Фиксированная верхняя граница или настраиваемая верхняя граница по умолчанию СЛЕДУЕТ устанавливать равной 120 секундам (95 секунд для нижней границы), когда расход батареи не важен, и 840 секундам (672 секунды для нижней границы), когда расход батареи важен. Случайное число будет разным для каждого keep-alive «ping».
Note on selection of time values: the 120-second upper bound was chosen based on the idea that for a good user experience, failures normally will be detected in this amount of time and a new connection will be set up. The 14-minute upper bound for battery- powered devices was selected based on NATs with TCP timeouts as low as 15 minutes. Operators that wish to change the relationship between load on servers and the expected time that a user might not receive inbound communications will probably adjust this time. The 95-second lower bound was chosen so that the jitter introduced will result in a relatively even load on the servers after 30 minutes.
Примечание о выборе значений времени: верхняя граница 120 секунд выбрана исходя из идеи, что при хорошем пользовательском опыте отказы обычно обнаруживаются за это время и устанавливается новое соединение. Верхняя граница 14 минут для устройств с батарейным питанием выбрана на основе NAT с тайм-аутами TCP до 15 минут. Операторы, желающие изменить соотношение между нагрузкой на серверы и ожидаемым временем, в течение которого пользователь может не получать входящую связь, вероятно, будут корректировать это время. Нижняя граница 95 секунд выбрана так, чтобы вносимое дрожание приводило к относительно равномерной нагрузке на серверы через 30 минут.
4.4.2. Keep-Alive with STUN
4.4.2. Keep-alive с STUN
This approach MUST only be used with connection-less transports, such as UDP; it MUST NOT be used for connection-oriented transports such as TCP and SCTP.
Этот подход ДОЛЖЕН использоваться только с транспортами без установления соединения, такими как UDP; он НЕ ДОЛЖЕН использоваться для транспортов с установлением соединения, таких как TCP и SCTP.
A User Agent that forms flows checks if the configured URI to which the UA is connecting resolves to use the UDP transport. The UA can periodically perform keep-alive checks by sending STUN [RFC5389] Binding Requests over the flow as described in Section 8. Clients MUST support STUN-based keep-alives.
Пользовательский агент, формирующий потоки, проверяет, разрешается ли сконфигурированный URI, к которому подключается агент, в использование транспорта UDP. Пользовательский агент может периодически выполнять проверки keep-alive, отправляя Binding Requests STUN [RFC5389] по потоку, как описано в разделе 8. Клиенты ДОЛЖНЫ поддерживать keep-alive на основе STUN.
When a Flow-Timer header field is not included in a successful registration response, the time between each keep-alive request SHOULD be a random number between 24 and 29 seconds.
Когда поле заголовка Flow-Timer не включено в успешный ответ на регистрацию, время между каждым запросом keep-alive СЛЕДУЕТ выбирать случайным числом от 24 до 29 секунд.
Note on selection of time values: the upper bound of 29 seconds was selected, as many NATs have UDP timeouts as low as 30 seconds. The 24-second lower bound was selected so that after 10 minutes the jitter introduced by different timers will make the keep-alive requests unsynchronized to evenly spread the load on the servers. Note that the short NAT timeouts with UDP have a negative impact on battery life.
Примечание о выборе значений времени: верхняя граница 29 секунд выбрана, поскольку многие NAT имеют тайм-ауты UDP всего 30 секунд. Нижняя граница 24 секунды выбрана так, чтобы через 10 минут дрожание, вносимое разными таймерами, делало запросы keep-alive несинхронизированными и равномерно распределяло нагрузку на серверы. Заметим, что короткие тайм-ауты NAT при UDP отрицательно влияют на время работы от батареи.
If a STUN Binding Error Response is received, or if no Binding Response is received after 7 retransmissions (16 times the STUN "RTO" timer -- where RTO is an estimate of round-trip time), the UA considers the flow failed. If the XOR-MAPPED-ADDRESS in the STUN Binding Response changes, the UA MUST treat this event as a failure on the flow.
Если получен Binding Error Response STUN или если после 7 повторных передач (16-кратный таймер «RTO» STUN — где RTO является оценкой времени кругового обхода) не получен Binding Response, пользовательский агент считает поток отказавшим. Если XOR-MAPPED-ADDRESS в Binding Response STUN изменяется, пользовательский агент ДОЛЖЕН рассматривать это событие как отказ потока.
4.5. Flow Recovery
4.5. Восстановление потока
When a flow used for registration (through a particular URI in the outbound-proxy-set) fails, the UA needs to form a new flow to replace the old flow and replace any registrations that were previously sent over this flow. Each new registration MUST have the same reg-id value as the registration it replaces. This is done in much the same way as forming a brand new flow as described in Section 4.2; however, if there is a failure in forming this flow, the UA needs to wait a certain amount of time before retrying to form a flow to this particular next hop.
Когда поток, использованный для регистрации (через конкретный URI в outbound-proxy-set), отказывает, пользовательский агент должен сформировать новый поток для замены старого и заменить все регистрации, ранее отправленные по этому потоку. Каждая новая регистрация ДОЛЖНА иметь то же значение reg-id, что и заменяемая регистрация. Это делается почти так же, как формирование совершенно нового потока, описанного в разделе 4.2; однако при отказе в формировании этого потока пользовательский агент должен подождать определённое время, прежде чем повторять попытку сформировать поток к этому конкретному следующему переходу.
The amount of time to wait depends if the previous attempt at establishing a flow was successful. For the purposes of this section, a flow is considered successful if outbound registration succeeded, and if keep-alives are in use on this flow, at least one subsequent keep-alive response was received. The number of seconds to wait is computed in the following way. If all of the flows to every URI in the outbound proxy set have failed, the base-time is set to a lower value (with a default of 30 seconds); otherwise, in the case where at least one of the flows has not failed, the base-time is set to a higher value (with a default of 90 seconds). The upper-bound wait time (W) is computed by taking two raised to the power of the number of consecutive registration failures for that URI, and multiplying this by the base-time, up to a configurable maximum time (with a default of 1800 seconds).
Величина времени ожидания зависит от того, была ли успешной предыдущая попытка установить поток. Для целей этого раздела поток считается успешным, если регистрация outbound прошла успешно и, если keep-alive используются в этом потоке, был получен хотя бы один последующий ответ keep-alive. Число секунд ожидания вычисляется следующим образом. Если все потоки ко всем URI в наборе исходящих прокси отказали, base-time устанавливается в меньшее значение (по умолчанию 30 секунд); в противном случае, когда по крайней мере один из потоков не отказал, base-time устанавливается в большее значение (по умолчанию 90 секунд). Верхняя граница времени ожидания (W) вычисляется возведением двойки в степень числа последовательных отказов регистрации для этого URI и умножением результата на base-time, вплоть до настраиваемого максимального времени (по умолчанию 1800 секунд).
W = min (max-time, (base-time * (2 ^ consecutive-failures)))
W = min (max-time, (base-time * (2 ^ consecutive-failures)))
These times MAY be configurable in the UA. The three times are:
Эти значения времени МОГУТ настраиваться в агенте. Есть три значения:
o max-time with a default of 1800 seconds
o max-time по умолчанию 1800 секунд
o base-time (if all failed) with a default of 30 seconds
o base-time (если все отказали) по умолчанию 30 секунд
o base-time (if all have not failed) with a default of 90 seconds
o base-time (если все не отказали) по умолчанию 90 секунд
For example, if the base-time is 30 seconds, and there were three failures, then the upper-bound wait time is min(1800, 30*(2^3)) or 240 seconds. The actual amount of time the UA waits before retrying registration (the retry delay time) is computed by selecting a uniform random time between 50 and 100% of the upper-bound wait time. The UA MUST wait for at least the value of the retry delay time before trying another registration to form a new flow for that URI (a 503 response to an earlier failed registration attempt with a Retry- After header field value may cause the UA to wait longer).
Например, если base-time равно 30 секундам, а отказов было три, то верхняя граница времени ожидания равна min(1800, 30*(2^3)), или 240 секундам. Фактическое время, которое пользовательский агент ждёт перед повторной попыткой регистрации (время задержки повтора), вычисляется выбором равномерно распределённого случайного времени между 50 и 100 % верхней границы времени ожидания. Пользовательский агент ДОЛЖЕН подождать как минимум значение времени задержки повтора, прежде чем предпринять очередную попытку регистрации для формирования нового потока для этого URI (ответ 503 на предыдущую неудачную попытку регистрации со значением поля заголовка Retry-After может заставить агент ждать дольше).
To be explicitly clear on the boundary conditions: when the UA boots, it immediately tries to register. If this fails and no registration on other flows succeed, the first retry happens somewhere between 30 and 60 seconds after the failure of the first registration request. If the number of consecutive-failures is large enough that the maximum of 1800 seconds is reached, the UA will keep trying indefinitely with a random time of 15 to 30 minutes between each attempt.
Чтобы явно обозначить граничные условия: при загрузке пользовательский агент сразу пытается зарегистрироваться. Если это не удаётся и никакие регистрации по другим потокам не увенчались успехом, первый повтор происходит где-то через 30–60 секунд после отказа первого запроса REGISTER. Если число последовательных отказов достаточно велико, чтобы достигался максимум 1800 секунд, агент будет пытаться бесконечно со случайным интервалом от 15 до 30 минут между попытками.
5. Edge Proxy Procedures
5. Процедуры граничного прокси
5.1. Processing Register Requests
5.1. Обработка запросов регистрации
When an edge proxy receives a registration request with a "reg-id" header field parameter in the Contact header field, it needs to determine if it (the edge proxy) will have to be visited for any subsequent requests sent to the User Agent identified in the Contact header field, or not. If the edge proxy is the first hop, as indicated by the Via header field, it MUST insert its URI in a Path header field value as described in [RFC3327]. If it is not the first hop, it might still decide to add itself to the Path header based on local policy. In addition, if the edge proxy is the first SIP node after the UAC, the edge proxy either MUST store a "flow token" (containing information about the flow from the previous hop) in its Path URI or reject the request. The flow token MUST be an identifier that is unique to this network flow. The flow token MAY be placed in the userpart of the URI. In addition, the first node MUST include an "ob" URI parameter in its Path header field value. If the edge proxy is not the first SIP node after the UAC it MUST NOT place an "ob" URI parameter in a Path header field value. The edge proxy can determine if it is the first hop by examining the Via header field.
Когда граничный прокси получает запрос регистрации с параметром поля заголовка «reg-id» в поле заголовка Contact, он должен определить, придётся ли к нему (граничному прокси) обращаться при любых последующих запросах, отправляемых пользовательскому агенту, указанному в поле заголовка Contact, или нет. Если граничный прокси является первым переходом, как указывает поле заголовка Via, он ДОЛЖЕН вставить свой URI в значение поля заголовка Path, как описано в [RFC3327]. Если он не является первым переходом, он всё равно может решить добавить себя в поле заголовка Path на основе локальной политики. Кроме того, если граничный прокси является первым SIP-узлом после UAC, он должен либо сохранить «токен потока» (содержащий информацию о потоке от предыдущего перехода) в своём Path URI, либо отклонить запрос. Токен потока ДОЛЖЕН быть идентификатором, уникальным для этого сетевого потока. Токен потока МОЖЕТ быть помещён в часть пользователя URI. Кроме того, первый узел ДОЛЖЕН включить параметр URI «ob» в значение поля заголовка Path. Если граничный прокси не является первым SIP-узлом после UAC, он НЕ ДОЛЖЕН помещать параметр URI «ob» в значение поля заголовка Path. Граничный прокси может определить, является ли он первым переходом, проверив поле заголовка Via.
5.2. Generating Flow Tokens
5.2. Формирование токенов потока
A trivial but impractical way to satisfy the flow token requirement in Section 5.1 involves storing a mapping between an incrementing counter and the connection information; however, this would require the edge proxy to keep an infeasible amount of state. It is unclear when this state could be removed, and the approach would have problems if the proxy crashed and lost the value of the counter. A stateless example is provided below. A proxy can use any algorithm it wants as long as the flow token is unique to a flow, the flow can be recovered from the token, and the token cannot be modified by attackers.
Тривиальный, но непрактичный способ удовлетворить требование к токену потока из раздела 5.1 состоит в хранении отображения между увеличивающимся счётчиком и информацией о соединении; однако это потребовало бы от граничного прокси хранить недопустимо большой объём состояния. Неясно, когда это состояние можно было бы удалить, и подход имел бы проблемы, если бы прокси аварийно завершился и потерял значение счётчика. Пример без сохранения состояния приведён ниже. Прокси может использовать любой алгоритм, если токен потока уникален для потока, поток можно восстановить из токена, и токен не может быть изменён злоумышленниками.
Example Algorithm: When the proxy boots, it selects a 20-octet crypto random key called K that only the edge proxy knows. A byte array, called S, is formed that contains the following information about the flow the request was received on: an enumeration indicating the protocol, the local IP address and port, the remote IP address and port. The HMAC of S is computed using the key K and the HMAC-SHA1-80 algorithm, as defined in [RFC2104]. The concatenation of the HMAC and S are base64 encoded, as defined in [RFC4648], and used as the flow identifier. When using IPv4 addresses, this will result in a 32-octet identifier.
Пример алгоритма: при загрузке прокси выбирает 20-октетный криптографический случайный ключ K, известный только граничному прокси. Формируется байтовый массив S, содержащий следующую информацию о потоке, по которому был получен запрос: перечисление, указывающее протокол, локальный IP-адрес и порт, удалённый IP-адрес и порт. HMAC от S вычисляется с использованием ключа K и алгоритма HMAC-SHA1-80, как определено в [RFC2104]. Конкатенация HMAC и S кодируется в base64, как определено в [RFC4648], и используется в качестве идентификатора потока. При использовании IPv4-адресов это даёт 32-октетный идентификатор.
5.3. Forwarding Non-REGISTER Requests
5.3. Пересылка запросов, отличных от REGISTER
When an edge proxy receives a request, it applies normal routing procedures with the following additions. If the edge proxy receives a request where the edge proxy is the host in the topmost Route header field value, and the Route header field value contains a flow token, the proxy follows the procedures of this section. Otherwise the edge proxy skips the procedures in this section, removes itself from the Route header field, and continues processing the request. The proxy decodes the flow token and compares the flow in the flow token with the source of the request to determine if this is an "incoming" or "outgoing" request.
Когда граничный прокси получает запрос, он применяет обычные процедуры маршрутизации со следующими дополнениями. Если граничный прокси получает запрос, в котором он является хостом в значении самого верхнего поля заголовка Route, и значение поля заголовка Route содержит токен потока, прокси следует процедурам этого раздела. В противном случае граничный прокси пропускает процедуры этого раздела, удаляет себя из поля заголовка Route и продолжает обработку запроса. Прокси декодирует токен потока и сравнивает поток в токене потока с источником запроса, чтобы определить, является ли этот запрос «входящим» или «исходящим».
If the flow in the flow token identified by the topmost Route header field value matches the source IP address and port of the request, the request is an "outgoing" request; otherwise, it is an "incoming" request.
Если поток в токене потока, указанном самым верхним значением поля заголовка Route, совпадает с исходным IP-адресом и портом запроса, запрос является «исходящим»; в противном случае он является «входящим».
5.3.1. Processing Incoming Requests
5.3.1. Обработка входящих запросов
If the Route header value contains an "ob" URI parameter, the Route header was probably copied from the Path header in a registration. If the Route header value contains an "ob" URI parameter, and the request is a new dialog-forming request, the proxy needs to adjust the route set to ensure that subsequent requests in the dialog can be delivered over a valid flow to the UA instance identified by the flow token.
Если значение заголовка Route содержит параметр URI «ob», поле заголовка Route, вероятно, было скопировано из поля заголовка Path при регистрации. Если значение заголовка Route содержит параметр URI «ob» и запрос является новым запросом, формирующим диалог, прокси должен скорректировать набор маршрутов, чтобы последующие запросы диалога могли доставляться по действительному потоку экземпляру пользовательского агента, идентифицированному токеном потока.
Note: A simple approach to satisfy this requirement is for the proxy to add a Record-Route header field value that contains the flow-token, by copying the URI in the Route header minus the "ob" parameter.
Примечание: простой способ выполнить это требование — прокси добавляет значение поля заголовка Record-Route, содержащее токен потока, скопировав URI из заголовка Route без параметра «ob».
Next, whether the Route header field contained an "ob" URI parameter or not, the proxy removes the Route header field value and forwards the request over the 'logical flow' identified by the flow token, that is known to deliver data to the specific target UA instance. If the flow token has been tampered with, the proxy SHOULD send a 403 (Forbidden) response. If the flow no longer exists, the proxy SHOULD send a 430 (Flow Failed) response to the request.
Далее, независимо от того, содержало ли поле заголовка Route параметр URI «ob», прокси удаляет значение поля заголовка Route и пересылает запрос по «логическому потоку», идентифицированному токеном потока, который, как известно, доставляет данные конкретному целевому экземпляру пользовательского агента. Если токен потока был подменён, прокси СЛЕДУЕТ отправить ответ 403 (Forbidden). Если поток больше не существует, прокси СЛЕДУЕТ отправить на запрос ответ 430 (Flow Failed).
Proxies that used the example algorithm described in Section 5.2 to form a flow token follow the procedures below to determine the correct flow. To decode the flow token, take the flow identifier in the user portion of the URI and base64 decode it, then verify the HMAC is correct by recomputing the HMAC and checking that it matches. If the HMAC is not correct, the request has been tampered with.
Прокси, использовавшие пример алгоритма из раздела 5.2 для формирования токена потока, следуют приведённым ниже процедурам для определения правильного потока. Чтобы декодировать токен потока, нужно взять идентификатор потока в части пользователя URI, декодировать его из base64, затем проверить правильность HMAC, пересчитав HMAC и убедившись, что он совпадает. Если HMAC неверен, запрос был подменён.
5.3.2. Processing Outgoing Requests
5.3.2. Обработка исходящих запросов
For mid-dialog requests to work with outbound UAs, the requests need to be forwarded over some valid flow to the appropriate UA instance. If the edge proxy receives an outgoing dialog-forming request, the edge proxy can use the presence of the "ob" URI parameter in the UAC's Contact URI (or topmost Route header field) to determine if the edge proxy needs to assist in mid-dialog request routing. Implementation note: Specific procedures at the edge proxy to ensure that mid-dialog requests are routed over an existing flow are not part of this specification. However, an approach such as having the edge proxy add a Record-Route header with a flow token is one way to ensure that mid-dialog requests are routed over the correct flow.
Чтобы запросы в середине диалога работали с outbound-пользовательскими агентами, их нужно пересылать по некоторому действительному потоку соответствующему экземпляру пользовательского агента. Если граничный прокси получает исходящий запрос, формирующий диалог, он может использовать наличие параметра URI «ob» в Contact URI пользовательского агента (или в самом верхнем поле заголовка Route), чтобы определить, нужно ли ему помогать в маршрутизации запросов в середине диалога. Примечание по реализации: конкретные процедуры на граничном прокси, гарантирующие маршрутизацию запросов в середине диалога по существующему потоку, не входят в настоящую спецификацию. Однако такой подход, как добавление граничным прокси заголовка Record-Route с токеном потока, является одним из способов обеспечить маршрутизацию запросов в середине диалога по правильному потоку.
5.4. Edge Proxy Keep-Alive Handling
5.4. Обработка keep-alive на граничном прокси
All edge proxies compliant with this specification MUST implement support for STUN NAT keep-alives on their SIP UDP ports as described in Section 8.
Все граничные прокси, соответствующие настоящей спецификации, ДОЛЖНЫ реализовывать поддержку keep-alive STUN для NAT на своих UDP-портах SIP, как описано в разделе 8.
When a server receives a double CRLF sequence between SIP messages on a connection-oriented transport such as TCP or SCTP, it MUST immediately respond with a single CRLF over the same connection.
Когда сервер получает последовательность двойного CRLF между сообщениями SIP на транспорте с установлением соединения, таком как TCP или SCTP, он ДОЛЖЕН немедленно ответить одиночным CRLF по тому же соединению.
The last proxy to forward a successful registration response to a UA MAY include a Flow-Timer header field if the response contains the outbound option-tag in a Require header field value in the response. The reason a proxy would send a Flow-Timer is if it wishes to detect flow failures proactively and take appropriate action (e.g., log alarms, provide alternative treatment if incoming requests for the UA are received, etc.). The server MUST wait for an amount of time larger than the Flow-Timer in order to have a grace period to account for transport delay.
Последний прокси, пересылающий успешный ответ на регистрацию пользовательскому агенту, МОЖЕТ включать поле заголовка Flow-Timer, если ответ содержит option-tag outbound в значении поля заголовка Require. Причина, по которой прокси может отправлять Flow-Timer, состоит в желании проактивно обнаруживать отказы потоков и предпринимать соответствующие действия (например, регистрировать аварийные сигналы, обеспечивать альтернативную обработку при получении входящих запросов для пользовательского агента и т. п.). Сервер ДОЛЖЕН ждать время, большее Flow-Timer, чтобы иметь льготный период на компенсацию транспортной задержки.
6. Registrar Procedures
6. Процедуры регистратора
This specification updates the definition of a binding in [RFC3261], Section 10 and [RFC3327], Section 5.3.
Настоящая спецификация обновляет определение привязки в разделе 10 [RFC3261] и разделе 5.3 [RFC3327].
Registrars that implement this specification MUST support the Path header mechanism [RFC3327].
Регистраторы, реализующие настоящую спецификацию, ДОЛЖНЫ поддерживать механизм поля заголовка Path [RFC3327].
When receiving a REGISTER request, the registrar MUST check from its Via header field if the registrar is the first hop or not. If the registrar is not the first hop, it MUST examine the Path header of the request. If the Path header field is missing or it exists but the first URI does not have an "ob" URI parameter, then outbound processing MUST NOT be applied to the registration. In this case, the following processing applies: if the REGISTER request contains the reg-id and the outbound option tag in a Supported header field, then the registrar MUST respond to the REGISTER request with a 439 (First Hop Lacks Outbound Support) response; otherwise, the registrar MUST ignore the "reg-id" parameter of the Contact header. See Section 11.6 for more information on the 439 response code. A Contact header field value with an instance-id media feature tag but no "reg-id" header field parameter is valid (this combination will result in the creation of a GRUU, as described in the GRUU specification [RFC5627]), but one with a reg-id but no instance-id is not valid. If the registrar processes a Contact header field value with a reg-id but no instance-id, it simply ignores the reg-id parameter.
При получении запроса REGISTER регистратор ДОЛЖЕН проверить по полю заголовка Via, является ли он первым переходом или нет. Если регистратор не является первым переходом, он ДОЛЖЕН проверить поле заголовка Path запроса. Если поле заголовка Path отсутствует или существует, но первый URI не имеет параметра URI «ob», то обработка outbound НЕ ДОЛЖНА применяться к регистрации. В этом случае применяется следующая обработка: если запрос REGISTER содержит reg-id и option tag outbound в поле заголовка Supported, регистратор ДОЛЖЕН ответить на запрос REGISTER ответом 439 (First Hop Lacks Outbound Support); в противном случае регистратор ДОЛЖЕН игнорировать параметр «reg-id» поля заголовка Contact. См. раздел 11.6 для получения дополнительной информации о коде ответа 439. Значение поля заголовка Contact с тегом характеристики среды instance-id, но без параметра поля заголовка «reg-id», допустимо (эта комбинация приведёт к созданию GRUU, как описано в спецификации GRUU [RFC5627]), а значение с reg-id, но без instance-id недопустимо. Если регистратор обрабатывает значение поля заголовка Contact с reg-id, но без instance-id, он просто игнорирует параметр reg-id.
A registration containing a "reg-id" header field parameter and a non-zero expiration is used to register a single UA instance over a single flow, and can also de-register any Contact header fields with zero expiration. Therefore, if the Contact header field contains more than one header field value with a non-zero expiration and any of these header field values contain a "reg-id" Contact header field parameter, the entire registration SHOULD be rejected with a 400 (Bad Request) response. The justification for recommending rejection versus making it mandatory is that the receiver is allowed by [RFC3261] to squelch (not respond to) excessively malformed or malicious messages.
Регистрация, содержащая параметр поля заголовка «reg-id» и ненулевое время истечения, используется для регистрации одного экземпляра пользовательского агента по одному потоку, а также может отменять регистрацию любых полей заголовка Contact с нулевым временем истечения. Поэтому, если поле заголовка Contact содержит более одного значения поля заголовка с ненулевым временем истечения и любое из этих значений содержит параметр поля заголовка Contact «reg-id», всю регистрацию СЛЕДУЕТ отклонить с ответом 400 (Bad Request). Обоснование рекомендации отклонять, а не делать это обязательным, состоит в том, что [RFC3261] позволяет получателю подавлять (не отвечать на) чрезмерно искажённые или вредоносные сообщения.
If the Contact header did not contain a "reg-id" Contact header field parameter or if that parameter was ignored (as described above), the registrar MUST NOT include the outbound option-tag in the Require header field of its response.
Если поле заголовка Contact не содержало параметр поля заголовка Contact «reg-id» или если этот параметр был проигнорирован (как описано выше), регистратор НЕ ДОЛЖЕН включать option-tag outbound в поле заголовка Require своего ответа.
The registrar MUST be prepared to receive, simultaneously for the same AOR, some registrations that use instance-id and reg-id and some registrations that do not. The registrar MAY be configured with local policy to reject any registrations that do not include the instance-id and reg-id, or with Path header field values that do not contain the "ob" URI parameter. If the Contact header field does not contain a "+sip.instance" Contact header field parameter, the registrar processes the request using the Contact binding rules in [RFC3261].
Регистратор ДОЛЖЕН быть готов принимать одновременно для одного и того же AOR одни регистрации, использующие instance-id и reg-id, и другие регистрации, которые их не используют. Регистратор МОЖЕТ быть настроен с локальной политикой отклонять любые регистрации, не включающие instance-id и reg-id, или со значениями поля заголовка Path, не содержащими параметр URI «ob». Если поле заголовка Contact не содержит параметр поля заголовка Contact «+sip.instance», регистратор обрабатывает запрос по правилам привязки Contact из [RFC3261].
When a "+sip.instance" Contact header field parameter and a "reg-id" Contact header field parameter are present in a Contact header field of a REGISTER request (after the Contact header validation as described above), the corresponding binding is between an AOR and the combination of the instance-id (from the "+sip.instance" Contact header parameter) and the value of "reg-id" Contact header field parameter parameter. The registrar MUST store in the binding the Contact URI, all the Contact header field parameters, and any Path header field values. (Even though the Contact URI is not used for binding comparisons, it is still needed by the authoritative proxy to form the target set.) Provided that the UAC had included an outbound option-tag (defined in Section 11.4) in a Supported header field value in the REGISTER request, the registrar MUST include the outbound option-tag in a Require header field value in its response to that REGISTER request.
Когда в поле заголовка Contact запроса REGISTER присутствуют параметр поля заголовка Contact «+sip.instance» и параметр поля заголовка Contact «reg-id» (после проверки поля заголовка Contact, описанной выше), соответствующая привязка устанавливается между AOR и комбинацией instance-id (из параметра заголовка Contact «+sip.instance») и значения параметра поля заголовка Contact «reg-id». Регистратор ДОЛЖЕН сохранить в привязке Contact URI, все параметры поля заголовка Contact и любые значения поля заголовка Path. (Хотя Contact URI не используется для сравнений привязок, он по-прежнему нужен авторитетному прокси для формирования целевого набора.) При условии, что UAC включил option-tag outbound (определённый в разделе 11.4) в значение поля заголовка Supported в запросе REGISTER, регистратор ДОЛЖЕН включить option-tag outbound в значение поля заголовка Require в своём ответе на этот запрос REGISTER.
If the UAC has a direct flow with the registrar, the registrar MUST store enough information to uniquely identify the network flow over which the request arrived. For common operating systems with TCP, this would typically be just the handle to the file descriptor where the handle would become invalid if the TCP session was closed. For common operating systems with UDP this would typically be the file descriptor for the local socket that received the request, the local interface, and the IP address and port number of the remote side that sent the request. The registrar MAY store this information by adding itself to the Path header field with an appropriate flow token.
Если у UAC есть прямой поток с регистратором, регистратор ДОЛЖЕН сохранить достаточно информации, чтобы однозначно идентифицировать сетевой поток, по которому пришёл запрос. Для распространённых операционных систем с TCP это, как правило, просто дескриптор файла, который станет недействительным при закрытии TCP-сеанса. Для распространённых операционных систем с UDP это, как правило, дескриптор локального сокета, принявшего запрос, локальный интерфейс, а также IP-адрес и номер порта удалённой стороны, отправившей запрос. Регистратор МОЖЕТ сохранить эту информацию, добавив себя в поле заголовка Path с соответствующим токеном потока.
If the registrar receives a re-registration for a specific combination of AOR, and instance-id and reg-id values, the registrar MUST update any information that uniquely identifies the network flow over which the request arrived if that information has changed, and SHOULD update the time the binding was last updated.
Если регистратор получает повторную регистрацию для конкретной комбинации AOR, значений instance-id и reg-id, он ДОЛЖЕН обновить любую информацию, однозначно идентифицирующую сетевой поток, по которому пришёл запрос, если эта информация изменилась, и СЛЕДУЕТ обновить время последнего обновления привязки.
To be compliant with this specification, registrars that can receive SIP requests directly from a UAC without intervening edge proxies MUST implement the same keep-alive mechanisms as edge proxies (Section 5.4). Registrars with a direct flow with a UA MAY include a Flow-Timer header in a 2xx class registration response that includes the outbound option-tag in the Require header.
Чтобы соответствовать настоящей спецификации, регистраторы, которые могут получать запросы SIP непосредственно от UAC без промежуточных граничных прокси, ДОЛЖНЫ реализовывать те же механизмы keep-alive, что и граничные прокси (раздел 5.4). Регистраторы, имеющие прямой поток с пользовательским агентом, МОГУТ включать заголовок Flow-Timer в ответ на регистрацию класса 2xx, содержащий option-tag outbound в заголовке Require.
7. Authoritative Proxy Procedures: Forwarding Requests
7. Процедуры авторитетного прокси: пересылка запросов
When a proxy uses the location service to look up a registration binding and then proxies a request to a particular contact, it selects a contact to use normally, with a few additional rules:
Когда прокси использует службу местоположения для поиска привязки регистрации и затем проксирует запрос конкретному контакту, он выбирает контакт обычным образом, с несколькими дополнительными правилами:
o The proxy MUST NOT populate the target set with more than one contact with the same AOR and instance-id at a time.
o Прокси НЕ ДОЛЖЕН включать в целевой набор более одного контакта с одинаковыми AOR и instance-id одновременно.
o If a request for a particular AOR and instance-id fails with a 430 (Flow Failed) response, the proxy SHOULD replace the failed branch with another target (if one is available) with the same AOR and instance-id, but a different reg-id.
o Если запрос для конкретных AOR и instance-id завершается ответом 430 (Flow Failed), прокси СЛЕДУЕТ заменить отказавшую ветвь другой целью (если она доступна) с теми же AOR и instance-id, но другим reg-id.
o If the proxy receives a final response from a branch other than a 408 (Request Timeout) or a 430 (Flow Failed) response, the proxy MUST NOT forward the same request to another target representing the same AOR and instance-id. The targeted instance has already provided its response.
o Если прокси получает окончательный ответ от ветви, отличный от ответа 408 (Request Timeout) или 430 (Flow Failed), прокси НЕ ДОЛЖЕН пересылать тот же запрос другой цели, представляющей те же AOR и instance-id. Целевой экземпляр уже предоставил свой ответ.
The proxy uses the next-hop target of the message and the value of any stored Path header field vector in the registration binding to decide how to forward and populate the Route header in the request. If the proxy is co-located with the registrar and stored information about the flow to the UA that created the binding, then the proxy MUST send the request over the same 'logical flow' saved with the binding, since that flow is known to deliver data to the specific target UA instance's network flow that was saved with the binding.
Прокси использует цель следующего перехода сообщения и значение любого сохранённого вектора поля заголовка Path в привязке регистрации, чтобы решить, как пересылать запрос и заполнять заголовок Route в нём. Если прокси размещён совместно с регистратором и сохранил информацию о потоке к пользовательскому агенту, создавшему привязку, то прокси ДОЛЖЕН отправлять запрос по тому же «логическому потоку», сохранённому с привязкой, поскольку этот поток, как известно, доставляет данные в сетевой поток конкретного целевого экземпляра пользовательского агента, сохранённый с привязкой.
Implementation note: Typically this means that for TCP, the request is sent on the same TCP socket that received the REGISTER request. For UDP, the request is sent from the same local IP address and port over which the registration was received, to the same IP address and port from which the REGISTER was received.
Примечание по реализации: обычно это означает, что для TCP запрос отправляется через тот же TCP-сокет, который принял запрос REGISTER. Для UDP запрос отправляется с того же локального IP-адреса и порта, по которому была получена регистрация, на тот же IP-адрес и порт, с которого был получен REGISTER.
If a proxy or registrar receives information from the network that indicates that no future messages will be delivered on a specific flow, then the proxy MUST invalidate all the bindings in the target set that use that flow (regardless of AOR). Examples of this are a TCP socket closing or receiving a destination unreachable ICMP error on a UDP flow. Similarly, if a proxy closes a file descriptor, it MUST invalidate all the bindings in the target set with flows that use that file descriptor.
Если прокси или регистратор получает из сети информацию, указывающую, что никакие будущие сообщения не будут доставлены по конкретному потоку, то прокси ДОЛЖЕН сделать недействительными все привязки в целевом наборе, использующие этот поток (независимо от AOR). Примерами этого являются закрытие TCP-сокета или получение ICMP-ошибки «destination unreachable» по потоку UDP. Аналогично, если прокси закрывает дескриптор файла, он ДОЛЖЕН сделать недействительными все привязки в целевом наборе с потоками, использующими этот дескриптор.
8. STUN Keep-Alive Processing
8. Обработка keep-alive STUN
This section describes changes to the SIP transport layer that allow SIP and STUN [RFC5389] Binding Requests to be mixed over the same
В этом разделе описываются изменения транспортного уровня SIP, которые позволяют смешивать запросы SIP и запросы Binding протокола STUN [RFC5389] в одном и том же
flow. This constitutes a new STUN usage. The STUN messages are used
потоке. Это составляет новый вариант использования STUN. Сообщения STUN используются
to verify that connectivity is still available over a UDP flow, and to provide periodic keep-alives. These STUN keep-alives are always sent to the next SIP hop. STUN messages are not delivered end-to- end.
чтобы убедиться, что связность по-прежнему доступна через поток UDP, и обеспечивать периодические keep-alive. Эти keep-alive STUN всегда отправляются следующему переходу SIP. Сообщения STUN не доставляются от конца до конца.
The only STUN messages required by this usage are Binding Requests, Binding Responses, and Binding Error Responses. The UAC sends Binding Requests over the same UDP flow that is used for sending SIP messages. These Binding Requests do not require any STUN attributes. The corresponding Binding Responses do not require any STUN attributes except the XOR-MAPPED-ADDRESS. The UAS, proxy, or registrar responds to a valid Binding Request with a Binding Response that MUST include the XOR-MAPPED-ADDRESS attribute.
Единственные сообщения STUN, требуемые этим вариантом использования, — это Binding Requests, Binding Responses и Binding Error Responses. UAC отправляет Binding Requests по тому же потоку UDP, который используется для отправки сообщений SIP. Эти Binding Requests не требуют никаких атрибутов STUN. Соответствующие Binding Responses не требуют никаких атрибутов STUN, кроме XOR-MAPPED-ADDRESS. UAS, прокси или регистратор отвечает на действительный Binding Request ответом Binding Response, который ДОЛЖЕН включать атрибут XOR-MAPPED-ADDRESS.
If a server compliant to this section receives SIP requests on a given interface and UDP port, it MUST also provide a limited version of a STUN server on the same interface and UDP port. Note: It is easy to distinguish STUN and SIP packets sent over UDP, because the first octet of a STUN Binding method has a value of 0 or 1, while the first octet of a SIP message is never a 0 or 1.
Если сервер, соответствующий этому разделу, получает запросы SIP на заданном интерфейсе и UDP-порту, он ДОЛЖЕН также предоставить ограниченную версию сервера STUN на том же интерфейсе и UDP-порту. Примечание: пакеты STUN и SIP, отправляемые по UDP, легко различить, поскольку первый октет метода STUN Binding имеет значение 0 или 1, тогда как первый октет сообщения SIP никогда не равен 0 или 1.
Because sending and receiving binary STUN data on the same ports used for SIP is a significant and non-backwards compatible change to RFC 3261, this section requires a number of checks before sending STUN messages to a SIP node. If a SIP node sends STUN requests (for example, due to incorrect configuration) despite these warnings, the node could be blacklisted for UDP traffic.
Поскольку отправка и приём двоичных данных STUN на тех же портах, что используются для SIP, являются существенным и обратно несовместимым изменением RFC 3261, этот раздел требует ряда проверок перед отправкой сообщений STUN SIP-узлу. Если SIP-узел отправляет запросы STUN (например, из-за неверной конфигурации) несмотря на эти предупреждения, узел может быть занесён в чёрный список для трафика UDP.
A SIP node MUST NOT send STUN requests over a flow unless it has an explicit indication that the target next-hop SIP server claims to support this specification. UACs MUST NOT use an ambiguous configuration option such as "Work through NATs?" or "Do keep- alives?" to imply next-hop STUN support. A UAC MAY use the presence of an "ob" URI parameter in the Path header in a registration response as an indication that its first edge proxy supports the keep-alives defined in this document.
SIP-узел НЕ ДОЛЖЕН отправлять запросы STUN по потоку, если у него нет явного указания на то, что целевой SIP-сервер следующего перехода заявляет о поддержке настоящей спецификации. UAC НЕ ДОЛЖНЫ использовать неоднозначный параметр конфигурации, такой как «Work through NATs?» или «Do keep-alives?», чтобы подразумевать поддержку STUN на следующем переходе. UAC МОЖЕТ использовать наличие параметра URI «ob» в заголовке Path в ответе на регистрацию как указание на то, что его первый граничный прокси поддерживает keep-alive, определённые в настоящем документе.
Note: Typically, a SIP node first sends a SIP request and waits to receive a 2xx class response over a flow to a new target destination, before sending any STUN messages. When scheduled for the next NAT refresh, the SIP node sends a STUN request to the target.
Примечание: обычно SIP-узел сначала отправляет запрос SIP и ждёт получения ответа класса 2xx по потоку к новой цели, прежде чем отправлять какие-либо сообщения STUN. При наступлении времени следующего обновления NAT SIP-узел отправляет запрос STUN цели.
Once a flow is established, failure of a STUN request (including its retransmissions) is considered a failure of the underlying flow. For SIP over UDP flows, if the XOR-MAPPED-ADDRESS returned over the flow changes, this indicates that the underlying connectivity has changed, and is considered a flow failure.
После установления потока отказ запроса STUN (включая его повторные передачи) считается отказом нижележащего потока. Для потоков SIP поверх UDP, если XOR-MAPPED-ADDRESS, возвращённый по потоку, изменяется, это указывает на изменение нижележащей связности и считается отказом потока.
The SIP keep-alive STUN usage requires no backwards compatibility with [RFC3489].
Вариант использования STUN для keep-alive в SIP не требует обратной совместимости с [RFC3489].
8.1. Use with SigComp
8.1. Использование с SigComp
When STUN is used together with SigComp [RFC3320] compressed SIP messages over the same flow, the STUN messages are simply sent uncompressed, "outside" of SigComp. This is supported by multiplexing STUN messages with SigComp messages by checking the two topmost bits of the message. These bits are always one for SigComp, or zero for STUN.
Когда STUN используется вместе со сжатыми сообщениями SIP SigComp [RFC3320] по одному и тому же потоку, сообщения STUN просто отправляются несжатыми, «вне» SigComp. Это поддерживается мультиплексированием сообщений STUN с сообщениями SigComp путём проверки двух старших битов сообщения. Эти биты всегда равны единице для SigComp и нулю для STUN.
Note: All SigComp messages contain a prefix (the five most significant bits of the first byte are set to one) that does not occur in UTF-8 [RFC3629] encoded text messages, so for applications that use this encoding (or ASCII encoding) it is possible to multiplex uncompressed application messages and SigComp messages on the same UDP port. The most significant two bits of every STUN Binding method are both zeroes. This, combined with the magic cookie, aids in differentiating STUN packets from other protocols when STUN is multiplexed with other protocols on the same port.
Примечание: все сообщения SigComp содержат префикс (пять старших битов первого байта установлены в единицу), который не встречается в текстовых сообщениях в кодировке UTF-8 [RFC3629], поэтому для приложений, использующих эту кодировку (или кодировку ASCII), можно мультиплексировать несжатые сообщения приложений и сообщения SigComp на одном UDP-порту. Два старших бита каждого метода STUN Binding равны нулю. Это в сочетании с magic cookie помогает отличать пакеты STUN от пакетов других протоколов, когда STUN мультиплексируется с другими протоколами на том же порту.

12. Security Considerations
12. Вопросы безопасности
One of the key security concerns in this work is making sure that an attacker cannot hijack the sessions of a valid user and cause all calls destined to that user to be sent to the attacker. Note that the intent is not to prevent existing active attacks on SIP UDP and TCP traffic, but to ensure that no new attacks are added by introducing the outbound mechanism.
Одна из ключевых проблем безопасности в этой работе — гарантировать, что злоумышленник не сможет перехватить сеансы законного пользователя и направить все вызовы, предназначенные этому пользователю, злоумышленнику. Отметим, что цель состоит не в предотвращении существующих активных атак на трафик SIP UDP и TCP, а в том, чтобы гарантировать, что введение механизма outbound не добавляет новых атак.
The simple case is when there are no edge proxies. In this case, the only time an entry can be added to the routing for a given AOR is when the registration succeeds. SIP already protects against attackers being able to successfully register, and this scheme relies on that security. Some implementers have considered the idea of just saving the instance-id without relating it to the AOR with which it registered. This idea will not work because an attacker's UA can impersonate a valid user's instance-id and hijack that user's calls.
Простой случай — отсутствие граничных прокси. В этом случае единственный момент, когда запись может быть добавлена в маршрутизацию для данного AOR, — это успешная регистрация. SIP уже защищает от того, чтобы злоумышленники могли успешно зарегистрироваться, и эта схема опирается на такую защиту. Некоторые разработчики рассматривали идею просто сохранять instance-id, не связывая его с AOR, с которым он был зарегистрирован. Эта идея не работает, поскольку пользовательский агент злоумышленника может выдать себя за instance-id законного пользователя и перехватить его вызовы.
The more complex case involves one or more edge proxies. When a UA sends a REGISTER request through an edge proxy on to the registrar, the edge proxy inserts a Path header field value. If the registration is successfully authenticated, the registrar stores the value of the Path header field. Later, when the registrar forwards a request destined for the UA, it copies the stored value of the Path header field into the Route header field of the request and forwards the request to the edge proxy.
Более сложный случай связан с одним или несколькими граничными прокси. Когда пользовательский агент отправляет запрос REGISTER через граничный прокси регистратору, граничный прокси вставляет значение поля заголовка Path. Если регистрация успешно аутентифицирована, регистратор сохраняет значение поля заголовка Path. Позже, когда регистратор пересылает запрос, предназначенный пользовательскому агенту, он копирует сохранённое значение поля заголовка Path в поле заголовка Route запроса и пересылает запрос граничному прокси.
The only time an edge proxy will route over a particular flow is when it has received a Route header that has the flow identifier information that it has created. An incoming request would have gotten this information from the registrar. The registrar will only save this information for a given AOR if the registration for the AOR has been successful; and the registration will only be successful if the UA can correctly authenticate. Even if an attacker has spoofed some bad information in the Path header sent to the registrar, the attacker will not be able to get the registrar to accept this information for an AOR that does not belong to the attacker. The registrar will not hand out this bad information to others, and others will not be misled into contacting the attacker.
Граничный прокси маршрутизирует по конкретному потоку только тогда, когда он получил заголовок Route с информацией идентификатора потока, которую он создал. Входящий запрос получил бы эту информацию от регистратора. Регистратор сохранит эту информацию для данного AOR только в том случае, если регистрация для этого AOR прошла успешно; а регистрация будет успешной только тогда, когда пользовательский агент сможет правильно аутентифицироваться. Даже если злоумышленник подделал неверную информацию в заголовке Path, отправленном регистратору, он не сможет добиться, чтобы регистратор принял эту информацию для AOR, не принадлежащего злоумышленнику. Регистратор не будет передавать эту неверную информацию другим, и другие не будут введены в заблуждение и не станут связываться со злоумышленником.
The Security Considerations discussed in [RFC3261] and [RFC3327] are also relevant to this document. For the security considerations of generating flow tokens, please also see Section 5.2. A discussion of preventing the avalanche restart problem is in Section 4.5.
Вопросы безопасности, рассмотренные в [RFC3261] и [RFC3327], также относятся к настоящему документу. О вопросах безопасности формирования токенов потока см. также раздел 5.2. Обсуждение предотвращения проблемы лавинной перезагрузки приведено в разделе 4.5.
This document does not change the mandatory-to-implement security mechanisms in SIP. User Agents are already required to implement Digest authentication while support of TLS is recommended; proxy servers are already required to implement Digest and TLS.
Настоящий документ не изменяет обязательные для реализации механизмы безопасности SIP. Пользовательские агенты уже обязаны реализовывать аутентификацию Digest, а поддержка TLS рекомендуется; прокси-серверы уже обязаны реализовывать Digest и TLS.
13. Operational Notes on Transports
13. Эксплуатационные заметки о транспортах
This entire section is non-normative.
Весь этот раздел не является нормативным.
[RFC3261] requires proxies, registrars, and User Agents to implement both TCP and UDP but deployments can chose which transport protocols they want to use. Deployments need to be careful in choosing what transports to use. Many SIP features and extensions, such as large presence notification bodies, result in SIP requests that can be too large to be reasonably transported over UDP. [RFC3261] states that when a request is too large for UDP, the device sending the request attempts to switch over to TCP. It is important to note that when using outbound, this will only work if the UA has formed both UDP and TCP outbound flows. This specification allows the UA to do so, but in most cases it will probably make more sense for the UA to form a TCP outbound connection only, rather than forming both UDP and TCP flows. One of the key reasons that many deployments choose not to use TCP has to do with the difficulty of building proxies that can maintain a very large number of active TCP connections. Many deployments today use SIP in such a way that the messages are small enough that they work over UDP but they can not take advantage of all the functionality SIP offers. Deployments that use only UDP outbound connections are going to fail with sufficiently large SIP messages.
[RFC3261] требует, чтобы прокси, регистраторы и пользовательские агенты реализовывали как TCP, так и UDP, но развёртывания могут выбирать, какие транспортные протоколы использовать. При выборе транспортов нужно быть осторожными. Многие функции и расширения SIP, такие как большие тела уведомлений о присутствии, приводят к запросам SIP, которые могут оказаться слишком большими для разумной передачи по UDP. [RFC3261] указывает, что когда запрос слишком велик для UDP, устройство, отправляющее запрос, пытается переключиться на TCP. Важно отметить, что при использовании outbound это сработает только в том случае, если пользовательский агент сформировал исходящие потоки и UDP, и TCP. Настоящая спецификация позволяет пользовательскому агенту это делать, но в большинстве случаев, вероятно, разумнее сформировать только исходящее TCP-соединение, а не оба потока — UDP и TCP. Одна из ключевых причин, по которой многие развёртывания отказываются от TCP, связана с трудностью построения прокси, способных поддерживать очень большое число активных TCP-соединений. Многие развёртывания сегодня используют SIP так, что сообщения достаточно малы и работают по UDP, но они не могут воспользоваться всей функциональностью, которую предлагает SIP. Развёртывания, использующие только исходящие соединения UDP, будут отказывать при достаточно больших сообщениях SIP.
