1. Introduction
1. Вводная часть
The work on media security started when the Session Initiation Protocol (SIP) was still in its infancy. With the increased SIP deployment and the availability of new SIP extensions and related protocols, the need for end-to-end security was re-evaluated. The procedure of re-evaluating prior protocol work and design decisions is not an uncommon strategy and, to some extent, considered necessary to ensure that the developed protocols indeed meet the previously envisioned needs for the users on the Internet.
Работы над медиабезопасностью начались, когда Протокол инициирования сессий (SIP) ещё только зарождался. С ростом развёртывания SIP и появлением новых расширений SIP и связанных протоколов потребность в сквозной защите была пересмотрена. Процедура пересмотра прежних работ над протоколами и проектных решений не является редкой стратегией и в известной мере считается необходимой, чтобы разрабатываемые протоколы действительно отвечали ранее задуманным потребностям пользователей Интернета.
This document summarizes media security requirements, i.e., requirements for mechanisms that negotiate security context such as cryptographic keys and parameters for SRTP.
В настоящем документе обобщены требования к медиабезопасности, то есть требования к механизмам, которые согласуют контекст безопасности, например криптографические ключи и параметры для SRTP.
The organization of this document is as follows: Section 2 introduces terminology, Section 3 describes various attack scenarios against the signaling path and media path, Section 4 provides an overview about possible call scenarios, and Section 5 lists requirements for media security. The main part of the document concludes with the security considerations Section 6, and acknowledgements in Section 7. Appendix A lists and compares available solution proposals. The following Appendix A.4 compares the different approaches regarding their suitability for the SIP signaling scenarios described in Appendix A, while Appendix A.5 provides a comparison regarding security aspects. Appendix B lists non-goals for this document.
Структура документа следующая: в разделе 2 вводится терминология, в разделе 3 описаны различные сценарии атак на сигнальный и медийный пути, в разделе 4 дан обзор возможных сценариев вызова, а в разделе 5 перечислены требования к медиабезопасности. Основная часть документа завершается разделом 6 о соображениях безопасности и разделом 7 с благодарностями. В приложении A перечислены и сопоставлены доступные предложения по решениям. 2. Terminology
2. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119], with the important qualification that, unless otherwise stated, these terms apply to the design of the media security key management protocol, not its implementation or application.
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует понимать так, как описано в [RFC2119], с важной оговоркой: если не указано иное, эти термины относятся к проектированию протокола управления ключами медиабезопасности, а не к его реализации или применению.
Furthermore, the terminology described in SIP [RFC3261] regarding functions and components are used throughout the document. Additionally, the following items are used in this document:
Кроме того, в документе повсеместно используется терминология, описанная в SIP [RFC3261] применительно к функциям и компонентам. Дополнительно в настоящем документе используются следующие термины:
AOR (Address-of-Record): A SIP or SIPS URI that points to a domain with a location service that can map the URI to another URI where the user might be available. Typically, the location service is populated through registrations. An AOR is frequently thought of as the "public address" of the user.
AOR (Address-of-Record): SIP- или SIPS-URI, указывающий на домен со службой местоположения, которая может сопоставить URI с другим URI, где пользователь может быть доступен. Обычно служба местоположения наполняется посредством регистраций. AOR часто рассматривают как «публичный адрес» пользователя.
SSRC: The 32-bit value that defines the synchronization source, used in RTP. These are generally unique, but collisions can occur.
SSRC: 32-битное значение, определяющее источник синхронизации, используется в RTP. Обычно эти значения уникальны, но возможны коллизии.
two-time pad: The use of the same key and the same keystream to encrypt different data. For SRTP, a two-time pad occurs if two senders are using the same key and the same RTP SSRC value.
two-time pad: Использование одного ключа и одного гаммирующего потока для шифрования разных данных. В SRTP двукратное наложение гаммы возникает, если два отправителя используют один ключ и одно значение RTP SSRC.
Perfect Forward Secrecy (PFS): The property that disclosure of the long-term secret keying material that is used to derive an agreed ephemeral key does not compromise the secrecy of agreed keys from earlier runs.
Perfect Forward Secrecy (PFS): Свойство, состоящее в том, что раскрытие долговременного секретного ключевого материала, используемого для вывода согласованного эфемерного ключа, не компрометирует секретность согласованных ключей предыдущих сеансов.
active adversary: An active adversary is able to alter data communication to affect its operation (see also [RFC4949]).
active adversary: Активный противник способен изменять передачу данных, влияя на её работу (см. также [RFC4949]).
passive adversary: A passive adversary is able to learn information from data communication, but not alter that data communication (see also [RFC4949]).
passive adversary: Пассивный противник способен извлекать информацию из передачи данных, но не изменять саму эту передачу (см. также [RFC4949]).
signaling path: The signaling path is the route taken by SIP signaling messages transmitted between the calling and called user agents. This can be either direct signaling between the calling and called user agents or, more commonly, involves the SIP proxy servers that were involved in the call setup.
signaling path: Сигнальный путь — это маршрут, по которому передаются сигнальные сообщения SIP между вызывающим и вызываемым пользовательскими агентами. Это может быть либо прямая сигнализация между вызывающим и вызываемым пользовательскими агентами, либо, что более типично, путь, включающий прокси-серверы SIP, участвовавшие в установлении вызова.
media path: The media path is the route taken by media packets exchanged by the endpoints. In the simplest case, the endpoints exchange media directly, and the "media path" is defined by a quartet of IP addresses and TCP/UDP ports, along with an IP route. In other cases, this path may include RTP relays, mixers, transcoders, session border controllers, NATs, or media gateways.
media path: Медийный путь — это маршрут, по которому передаются медиапакеты, которыми обмениваются конечные точки. В простейшем случае конечные точки обмениваются медиаданными напрямую, и «медийный путь» определяется четвёркой IP-адресов и портов TCP/UDP вместе с IP-маршрутом. В других случаях этот путь может включать RTP-ретрансляторы, микшеры, транскодеры, пограничные контроллеры сессий, NAT или медиашлюзы.
Moreover, as this document discusses requirements for media security, the nomenclature R-XXX is used to mark requirements, where XXX is the requirement, which needs to be met.
Кроме того, поскольку в настоящем документе рассматриваются требования к медиабезопасности, для обозначения требований используется номенклатура R-XXX, где XXX — идентификатор требования, которое должно быть выполнено.
3. Attack Scenarios
3. Сценарии нападения
The discussion in this section relates to requirements R-ASSOC (specified in Section 5.1) R-PASS-MEDIA, R-PASS-SIG, R-SIG-MEDIA, R-ACT-ACT, and R-ID-BINDING (specified in Section 5.2).
Обсуждение в этом разделе относится к требованиям R-ASSOC (указано в разделе 5.1), R-PASS-MEDIA, R-PASS-SIG, R-SIG-MEDIA, R-ACT-ACT и R-ID-BINDING (указано в разделе 5.2).
This document classifies adversaries according to their access and their capabilities. An adversary might have access:
В настоящем документе противники классифицируются по их доступу и возможностям. Противник может иметь доступ:
1. only to the media path,
1. только к медийному пути,
2. only to the signaling path,
2. только к сигнальному пути,
3. to the media path and to the signaling path.
3. к медийному пути и к сигнальному пути.
An attacker that can solely be located along the signaling path, and does not have access to media (item 2), is not considered in this document.
Атакующий, который может находиться исключительно на сигнальном пути и не имеет доступа к медиаданным (пункт 2), в настоящем документе не рассматривается.
There are two different types of adversaries: active and passive. An active adversary may need to be active with regard to the key exchange relevant information traveling along the media path or traveling along the signaling path.
Существуют два разных типа противников: активный и пассивный. Активному противнику может потребоваться активность в отношении информации, относящейся к обмену ключами и передаваемой по медийному или сигнальному пути.
Based on their robustness against the adversary capabilities described above, we can group security mechanisms using the following labels. This list is generally ordered from easiest to compromise (at the top) to more difficult to compromise:
Исходя из их устойчивости к описанным выше возможностям противника, мы можем сгруппировать механизмы безопасности с помощью следующих обозначений. Этот список в целом упорядочен от наиболее простых для компрометации (вверху) до более сложных:

no-signaling-passive-media: Access only to the media path is sufficient to reveal the content of the media traffic.
no-signaling-passive-media: Доступ только к медийному пути достаточен для раскрытия содержания медиатрафика.
passive-signaling-passive-media: Passive attack on the signaling and passive attack on the media path is necessary to reveal the content of the media traffic.
passive-signaling-passive-media: Для раскрытия содержания медиатрафика необходимы пассивная атака на сигнализацию и пассивная атака на медийный путь.
passive-signaling-active-media: Passive attack on the signaling and active attack on the media path is necessary to reveal the content of the media traffic.
passive-signaling-active-media: Для раскрытия содержания медиатрафика необходимы пассивная атака на сигнализацию и активная атака на медийный путь.
active-signaling-passive-media: Active attack on the signaling path and passive attack on the media path is necessary to reveal the content of the media traffic.
active-signaling-passive-media: Для раскрытия содержания медиатрафика необходимы активная атака на сигнальный путь и пассивная атака на медийный путь.
no-signaling-active-media: Active attack on the media path is sufficient to reveal the content of the media traffic.
no-signaling-active-media: Активная атака на медийный путь достаточна для раскрытия содержания медиатрафика.
active-signaling-active-media: Active attack on both the signaling path and the media path is necessary to reveal the content of the media traffic.
active-signaling-active-media: Для раскрытия содержания медиатрафика необходима активная атака как на сигнальный, так и на медийный путь.
active-signaling-active-media-detect: Active attack on both signaling and media path is necessary to reveal the content of the media traffic (as with active-signaling- active-media), and the attack is detectable by protocol messages exchanged between the endpoints.
active-signaling-active-media-detect: Для раскрытия содержания медиатрафика необходима активная атака как на сигнальный, так и на медийный путь (как в случае active-signaling-active-media), и эта атака обнаруживается по протокольным сообщениям, которыми обмениваются конечные точки.
For example, unencrypted RTP is vulnerable to no-signaling-passive- media.
Например, незашифрованный RTP уязвим к атаке no-signaling-passive-media.
As another example, SDP Security Descriptions [RFC4568], when protected by TLS (as it is commonly implemented and deployed), belong in the passive-signaling-passive-media category since the adversary needs to learn the SDP Security Descriptions key by seeing the SIP signaling message at a SIP proxy (assuming that the adversary is in control of the SIP proxy). The media traffic can be decrypted using that learned key.
Ещё один пример: SDP Security Descriptions [RFC4568] при защите с помощью TLS (как это обычно реализуется и развёртывается) относятся к категории passive-signaling-passive-media, поскольку противнику нужно узнать ключ SDP Security Descriptions, увидев сигнальное сообщение SIP на прокси-сервере SIP (при условии, что противник контролирует этот прокси-сервер). Зная этот ключ, можно расшифровать медиатрафик.
As another example, DTLS-SRTP (Datagram Transport Layer Security Extension for SRTP) falls into active-signaling-active-media category when DTLS-SRTP is used with a public-key-based ciphersuite with self- signed certificates and without SIP Identity [RFC4474]. An adversary would have to modify the fingerprint that is sent along the signaling path and subsequently to modify the certificates carried in the DTLS handshake that travel along the media path. If DTLS-SRTP is used with both SIP Identity [RFC4474] and SIP Connected Identity [RFC4916], the RFC-4474 signature protects both the offer and the answer, and such a system would then belong to the active-signaling- active-media-detect category (provided, of course, the signaling path to the RFC-4474 authenticator and verifier is secured as per RFC 4474, and the RFC-4474 authenticator and verifier are behaving as per RFC 4474). The above discussion of DTLS-SRTP demonstrates how a single security protocol can be in different classes depending on the mode in which it is operated. Other protocols can achieve a similar effect by adding functions outside of the on-the-wire key management protocol itself.
Ещё один пример: DTLS-SRTP (расширение Datagram Transport Layer Security для SRTP) попадает в категорию active-signaling-active-media, когда DTLS-SRTP используется с набором шифров на основе открытого ключа с самоподписанными сертификатами и без SIP Identity [RFC4474]. Противнику пришлось бы изменить отпечаток, передаваемый по сигнальному пути, а затем изменить сертификаты, передаваемые в рукопожатии DTLS, которое проходит по медийному пути. Если DTLS-SRTP используется вместе с SIP Identity [RFC4474] и SIP Connected Identity [RFC4916], подпись RFC-4474 защищает и предложение, и ответ, и такая система будет относиться к категории active-signaling-active-media-detect (при условии, конечно, что сигнальный путь к аутентификатору и верификатору RFC-4474 защищён согласно RFC 4474, а аутентификатор и верификатор RFC-4474 ведут себя согласно RFC 4474). Приведённое выше обсуждение DTLS-SRTP показывает, как один протокол безопасности может относиться к разным классам в зависимости от режима его работы. Другие протоколы могут достичь аналогичного эффекта, добавив функции вне самого протокола управления ключами, передаваемого по сети.
Although it may be appropriate to deploy lower-classed mechanisms in some cases, the ultimate security requirement for a media security negotiation protocol is that it have a mode of operation available in which is detect-attack, which provides protection against the passive and active attacks and provides detection of such attacks. That is, there must be a way to use the protocol so that an active attack is required against both the signaling and media paths, and so that such attacks are detectable by the endpoints.
Хотя в некоторых случаях может быть уместно развёртывать механизмы более низкого класса, окончательное требование безопасности к протоколу согласования медиабезопасности состоит в том, чтобы у него был доступный режим работы с обнаружением атаки, который обеспечивает защиту от пассивных и активных атак и обнаружение таких атак. То есть должен существовать способ использования протокола, при котором требуется активная атака как на сигнальный, так и на медийный путь, и при котором такие атаки обнаруживаются конечными точками.

4.1. Clipping Media before Signaling Answer
4.1. Обрезка медиаданных до сигнального ответа
The discussion in this section relates to requirements R-AVOID- CLIPPING and R-ALLOW-RTP.
Обсуждение в этом разделе относится к требованиям R-AVOID-CLIPPING и R-ALLOW-RTP.
Per the Session Description Protocol (SDP) Offer/Answer Model [RFC3264]:
Согласно модели предложения/ответа протокола описания сеанса (SDP) [RFC3264]:
Once the offerer has sent the offer, it MUST be prepared to receive media for any recvonly streams described by that offer. It MUST be prepared to send and receive media for any sendrecv streams in the offer, and send media for any sendonly streams in the offer (of course, it cannot actually send until the peer provides an answer with the needed address and port information).
После того как инициатор отправил предложение, он ДОЛЖЕН быть готов принимать медиаданные для любых потоков recvonly, описанных в этом предложении. Он ДОЛЖЕН быть готов отправлять и принимать медиаданные для любых потоков sendrecv в предложении и отправлять медиаданные для любых потоков sendonly в предложении (разумеется, фактически он не может отправлять, пока партнёр не предоставит ответ с необходимыми сведениями об адресе и порте).
To meet this requirement with SRTP, the offerer needs to know the SRTP key for arriving media. If either endpoint receives encrypted media before it has access to the associated SRTP key, it cannot play the media -- causing clipping. For key exchange mechanisms that send the answerer's key in SDP, a SIP provisional response [RFC3261], such as 183 (session progress), is useful. However, the 183 messages are not reliable unless both the calling and called endpoint support Provisional Response ACKnowledgement (PRACK) [RFC3262], use TCP across all SIP proxies, implement Security Preconditions [RFC5027], or both ends implement Interactive Connectivity Establishment [ICE] and the answerer implements the reliable provisional response mechanism described in ICE. Unfortunately, there is not wide deployment of any of these techniques and there is industry reluctance to require these techniques to avoid the problems described in this section.
Чтобы выполнить это требование с SRTP, инициатору нужно знать ключ SRTP для прибывающих медиаданных. Если любая из конечных точек получает зашифрованные медиаданные до того, как у неё появится доступ к соответствующему ключу SRTP, она не может воспроизвести эти медиаданные, что вызывает обрезку. Для механизмов обмена ключами, которые передают ключ отвечающей стороны в SDP, полезен предварительный ответ SIP [RFC3261], например 183 (session progress). Однако сообщения 183 ненадёжны, если только и вызывающая, и вызываемая конечные точки не поддерживают подтверждение предварительного ответа (PRACK) [RFC3262], не используют TCP через все прокси-серверы SIP, не реализуют предварительные условия безопасности (Security Preconditions) [RFC5027], либо обе стороны не реализуют установление интерактивной связности (ICE), а отвечающая сторона не реализует механизм надёжного предварительного ответа, описанный в ICE. К сожалению, ни одна из этих методик широко не развёрнута, и отрасль не желает требовать их для устранения проблем, описанных в этом разделе.
Note that the receipt of an SDP answer is not always sufficient to allow media to be played to the offerer. Sometimes, the offerer must send media in order to open up firewall holes or NAT bindings before media can be received (for details, see [MIDDLEBOX]). In this case, even a solution that makes the key available before the SDP answer arrives will not help.
Отметим, что получения ответа SDP не всегда достаточно, чтобы инициатор мог воспроизвести медиаданные. Иногда инициатор должен отправить медиаданные, чтобы открыть отверстия в межсетевом экране или привязки NAT, прежде чем сможет принимать медиаданные (подробности см. в [MIDDLEBOX]). В этом случае не поможет даже решение, которое делает ключ доступным до прибытия ответа SDP.
Preventing the arrival of early media (i.e., media that arrives at the SDP offerer before the SDP answer arrives) might obsolete the R-AVOID-CLIPPING requirement, but at the time of writing such early media exists in many normal call scenarios.
Предотвращение прибытия ранних медиаданных (то есть медиаданных, которые прибывают к инициатору SDP до прибытия ответа SDP) может сделать требование R-AVOID-CLIPPING неактуальным, но на момент написания такие ранние медиаданные существуют во многих обычных сценариях вызова.
4.2. Retargeting and Forking
4.2. Ретаргетинг и разветвление
The discussion in this section relates to requirements R-FORK- RETARGET, R-DISTINCT, R-HERFP, and R-BEST-SECURE.
Обсуждение в этом разделе относится к требованиям R-FORK-RETARGET, R-DISTINCT, R-HERFP и R-BEST-SECURE.
In SIP, a request sent to a specific AOR but delivered to a different AOR is called a "retarget". A typical scenario is a "call forwarding" feature. In Figure 1, Alice sends an INVITE in step 1 that is sent to Bob in step 2. Bob responds with a redirect (SIP response code 3xx) pointing to Carol in step 3. This redirect typically does not propagate back to Alice but only goes to a proxy (i.e., the retargeting proxy) that sends the original INVITE to Carol in step 4.
В SIP запрос, отправленный на конкретный AOR, но доставленный другому AOR, называется «ретаргетингом». Типичный сценарий — функция «переадресация вызова». На рисунке 1 Алиса отправляет INVITE на шаге 1, который отправляется Бобу на шаге 2. Боб отвечает перенаправлением (код ответа SIP 3xx), указывающим на Кэрол, на шаге 3. Это перенаправление обычно не возвращается к Алисе, а идёт только к прокси-серверу (то есть прокси-серверу ретаргетинга), который отправляет исходный INVITE Кэрол на шаге 4.
+-----+ |Alice| +--+--+ | | INVITE (1) V +----+----+ | proxy | ++-+-----++ | ^ | INVITE (2) | | | INVITE (4) & redirect (3) | | | V | V ++-++ ++----+ |Bob| |Carol| +---+ +-----+ Figure 1: Retargeting
+-----+ |Alice| +--+--+ | | INVITE (1) V +----+----+ | proxy | ++-+-----++ | ^ | INVITE (2) | | | INVITE (4) & redirect (3) | | | V | V ++-++ ++----+ |Bob| |Carol| +---+ +-----+ Figure 1: Retargeting
Using retargeting might lead to situations where the User Agent Client (UAC) does not know where its request will be going. This might not immediately seem like a serious problem; after all, when one places a telephone call on the Public Switched Telephone Network (PSTN), one never really knows if it will be forwarded to a different number, who will pick up the line when it rings, and so on. However, when considering SIP mechanisms for authenticating the called party, this function can also make it difficult to differentiate an intermediary that is behaving legitimately from an attacker. From this perspective, the main problems with retargeting are:
Использование ретаргетинга может приводить к ситуациям, когда клиентский пользовательский агент (UAC) не знает, куда будет направлен его запрос. Это может не показаться сразу серьёзной проблемой; в конце концов, когда человек звонит по телефонной сети общего пользования (PSTN), он никогда точно не знает, будет ли вызов переадресован на другой номер, кто снимет трубку, когда она зазвонит, и так далее. Однако при рассмотрении механизмов SIP для аутентификации вызываемой стороны эта функция также может затруднить отличие посредника, действующего законно, от атакующего. С этой точки зрения основные проблемы ретаргетинга таковы:
Not detectable by the caller: The originating user agent has no means of anticipating that the condition will arise, nor any means of determining that it has occurred until the call has already been set up.
Не обнаруживается вызывающей стороной: у исходного пользовательского агента нет средств предвидеть возникновение этого условия и нет средств определить, что оно наступило, пока вызов уже не будет установлен.
Not preventable by the caller: There is no existing mechanism that might be employed by the originating user agent in order to guarantee that the call will not be retargeted.
Не предотвращается вызывающей стороной: не существует механизма, который исходный пользовательский агент мог бы применить, чтобы гарантировать, что вызов не будет ретаргетирован.
The mechanism used by SIP for identifying the calling party is SIP Identity [RFC4474]. However, due to the nature of retargeting, SIP Identity can only identify the calling party (that is, the party that initiated the SIP request). Some key exchange mechanisms predate SIP Identity and include their own identity mechanism (e.g., Multimedia Internet KEYing (MIKEY)). However, those built-in identity mechanism also suffer from the SIP retargeting problem. While Connected Identity [RFC4916] allows positive identification of the called party, the primary difficulty still remains that the calling party does not know if a mismatched called party is legitimate (i.e., due to authorized retargeting) or illegitimate (i.e., due to unauthorized retargeting by an attacker above to modify SIP signaling).
Механизм, используемый SIP для идентификации вызывающей стороны, — это SIP Identity [RFC4474]. Однако из-за природы ретаргетинга SIP Identity может идентифицировать только вызывающую сторону (то есть сторону, инициировавшую запрос SIP). Некоторые механизмы обмена ключами появились раньше SIP Identity и включают собственный механизм идентификации (например, Multimedia Internet KEYing (MIKEY)). Однако эти встроенные механизмы идентификации также страдают от проблемы ретаргетинга в SIP. Хотя Connected Identity [RFC4916] позволяет положительно идентифицировать вызываемую сторону, основная трудность всё же остаётся: вызывающая сторона не знает, является ли несовпадающая вызываемая сторона законной (то есть следствием санкционированного ретаргетинга) или незаконной (то есть следствием несанкционированного ретаргетинга атакующим, способным изменять сигнализацию SIP).
In SIP, 'forking' is the delivery of a request to multiple locations. This happens when a single AOR is registered more than once. An example of forking is when a user has a desk phone, PC client, and mobile handset all registered with the same AOR.
В SIP «разветвление» — это доставка запроса в несколько мест. Это происходит, когда один AOR регистрируется более одного раза. Пример разветвления — когда у пользователя есть настольный телефон, клиент ПК и мобильный аппарат, все зарегистрированные с одним AOR.
+-----+ |Alice| +--+--+ | | INVITE V +-----+-----+ | proxy | ++---------++ | | INVITE | | INVITE V V +--+--+ +--+--+ |Bob-1| |Bob-2| +-----+ +-----+ Figure 2: Forking
+-----+ |Alice| +--+--+ | | INVITE V +-----+-----+ | proxy | ++---------++ | | INVITE | | INVITE V V +--+--+ +--+--+ |Bob-1| |Bob-2| +-----+ +-----+ Figure 2: Forking
With forking, both Bob-1 and Bob-2 might send back SDP answers in SIP responses. Alice will see those intermediate (18x) and final (200) responses. It is useful for Alice to be able to associate the SIP response with the incoming media stream. Although this association can be done with ICE [ICE], and ICE is useful to make this association with RTP, it is not desirable to require ICE to accomplish this association.
При разветвлении и Боб-1, и Боб-2 могут отправлять ответы SDP в ответах SIP. Алиса увидит эти промежуточные (18x) и окончательные (200) ответы. Алисе полезно иметь возможность связать ответ SIP с входящим медиапотоком. Хотя эту связь можно установить с помощью ICE [ICE], и ICE полезен для установления такой связи с RTP, нежелательно требовать ICE для выполнения этой связи.
Forking and retargeting are often used together. For example, a boss and secretary might have both phones ring (forking) and rollover to voice mail if neither phone is answered (retargeting).
Разветвление и ретаргетинг часто используются вместе. Например, у начальника и секретаря могут звонить оба телефона (разветвление) и переключаться на голосовую почту, если ни один телефон не отвечает (ретаргетинг).
To maintain the security of the media traffic, only the endpoint that answers the call should know the SRTP keys for the session. Forked and retargeted calls only reveal sensitive information to non- responders when the signaling messages contain sensitive information (e.g., SRTP keys) that is accessible by parties that receive the offer, but may not respond (i.e., the original recipients in a retargeted call, or non-answering endpoints in a forked call). For key exchange mechanisms that do not provide secure forking or secure retargeting, one workaround is to rekey immediately after forking or retargeting. However, because the originator may not be aware that the call forked this mechanism requires rekeying immediately after every session is established. This doubles the number of messages processed by the network.
Для поддержания безопасности медиатрафика только конечная точка, отвечающая на вызов, должна знать ключи SRTP для сеанса. Разветвлённые и ретаргетированные вызовы раскрывают конфиденциальную информацию не отвечающим сторонам только тогда, когда сигнальные сообщения содержат конфиденциальную информацию (например, ключи SRTP), доступную сторонам, которые получают предложение, но могут не ответить (то есть исходным получателям при ретаргетированном вызове или не отвечающим конечным точкам при разветвлённом вызове). Для механизмов обмена ключами, которые не обеспечивают безопасное разветвление или безопасный ретаргетинг, один из обходных путей — немедленно сменить ключи после разветвления или ретаргетинга. Однако, поскольку инициатор может не знать, что вызов был разветвлён, этот механизм требует смены ключей сразу после установления каждого сеанса. Это удваивает число сообщений, обрабатываемых сетью.
Further compounding this problem is a unique feature of SIP that, when forking is used, there is always only one final error response delivered to the sender of the request: the forking proxy is responsible for choosing which final response to choose in the event where forking results in multiple final error responses being received by the forking proxy. This means that if a request is rejected, say with information that the keying information was rejected and providing the far end's credentials, it is very possible that the rejection will never reach the sender. This problem, called the Heterogeneous Error Response Forking Problem (HERFP) [RFC3326], is difficult to solve in SIP. Because we expect the HERFP to continue to be a problem in SIP for the foreseeable future, a media security system should function even in the presence of HERFP behavior.
Дополнительно усложняет эту проблему уникальная особенность SIP: при использовании разветвления отправителю запроса всегда доставляется только один окончательный ответ об ошибке — прокси-сервер разветвления отвечает за выбор того, какой окончательный ответ выбрать, если разветвление привело к получению прокси-сервером разветвления нескольких окончательных ответов об ошибке. Это означает, что если запрос отклонён, скажем, с информацией о том, что ключевая информация была отклонена, и с учётными данными дальнего конца, вполне возможно, что это отклонение никогда не дойдёт до отправителя. Эта проблема, называемая проблемой разветвления неоднородных ответов об ошибках (HERFP) [RFC3326], трудно решаема в SIP. Поскольку мы ожидаем, что HERFP останется проблемой SIP в обозримом будущем, система медиабезопасности должна функционировать даже при наличии поведения HERFP.
4.3. Recording
4.3. Запись бесед
The discussion in this section relates to requirement R-RECORDING.
Обсуждение в этом разделе относится к требованию R-RECORDING.
Some business environments, such as stock brokerages, banks, and catalog call centers, require recording calls with customers. This is the familiar "this call is being recorded for quality purposes" heard during calls to these sorts of businesses. In these environments, media recording is typically performed by an intermediate device (with RTP, this is typically implemented in a 'sniffer').
Некоторые деловые среды, такие как брокерские фирмы, банки и центры обработки заказов, требуют записи разговоров с клиентами. Это знакомое «этот разговор записывается в целях контроля качества», которое слышно при звонках в подобные организации. В таких средах запись медиаданных обычно выполняется промежуточным устройством (при использовании RTP это обычно реализуется в «сниффере»).
When performing such call recording with SRTP, the end-to-end security is compromised. This is unavoidable, but necessary because the operation of the business requires such recording. It is desirable that the media security is not unduly compromised by the media recording. The endpoint within the organization needs to be informed that there is an intermediate device and needs to cooperate with that intermediate device.
При выполнении такой записи разговоров с помощью SRTP сквозная безопасность нарушается. Это неизбежно, но необходимо, поскольку деятельность организации требует такой записи. Желательно, чтобы медиабезопасность не была чрезмерно подорвана записью медиаданных. Конечная точка внутри организации должна быть проинформирована о наличии промежуточного устройства и должна взаимодействовать с этим промежуточным устройством.
This scenario does not place a requirement directly on the key management protocol. The requirement could be met directly by the key management protocol (e.g., MIKEY-NULL or [RFC4568]) or through an external out-of-band mechanism (e.g., [SRTP-KEY]).
Этот сценарий не возлагает требование непосредственно на протокол управления ключами. Требование может быть выполнено непосредственно протоколом управления ключами (например, MIKEY-NULL или [RFC4568]) либо через внешний механизм вне полосы (например, [SRTP-KEY]).
4.4. PSTN Gateway
4.4. Шлюз сети PSTN
The discussion in this section relates to requirement R-PSTN.
Обсуждение в этом разделе относится к требованию R-PSTN.
It is desirable, even when one leg of a call is on the PSTN, that the IP leg of the call be protected with SRTP.
Желательно, даже когда одно плечо вызова находится в PSTN, чтобы IP-плечо вызова было защищено с помощью SRTP.
A typical case of using media security where two entities are having a Voice over IP (VoIP) conversation over IP-capable networks. However, there are cases where the other end of the communication is not connected to an IP-capable network. In this kind of setting, there needs to be some kind of gateway at the edge of the IP network that converts the VoIP conversation to a format understood by the other network. An example of such a gateway is a PSTN gateway sitting at the edge of IP and PSTN networks (such as the architecture described in [RFC3372]).
Типичный случай использования медиабезопасности — это когда две стороны ведут разговор Voice over IP (VoIP) по сетям, поддерживающим протокол IP. Однако бывают случаи, когда другой конец связи не подключён к сети, поддерживающей IP. В такой обстановке на границе IP-сети требуется какой-то шлюз, который преобразует VoIP-разговор в формат, понятный другой сети. Пример такого шлюза — шлюз PSTN, расположенный на границе сетей IP и PSTN (например, архитектура, описанная в [RFC3372]).
If media security (e.g., SRTP protection) is employed in this kind of gateway-setting, then media security and the related key management is terminated at the PSTN gateway. The other network (e.g., PSTN) may have its own measures to protect the communication, but this means that from media security point of view the media security is not employed truly end-to-end between the communicating entities.
Если в такой конфигурации со шлюзом применяется медиабезопасность (например, защита SRTP), то медиабезопасность и связанное с ней управление ключами завершаются на шлюзе PSTN. Другая сеть (например, PSTN) может иметь собственные меры защиты связи, но это означает, что с точки зрения медиабезопасности защита не применяется действительно сквозным образом между общающимися сторонами.
4.5. Call Setup Performance
4.5. Скорость установки вызова
The discussion in this section relates to requirement R-REUSE.
Обсуждение в этом разделе относится к требованию R-REUSE.
Some devices lack sufficient processing power to perform public key operations or Diffie-Hellman operations for each call, or prefer to avoid performing those operations on every call. The ability to reuse previous public key or Diffie-Hellman operations can vastly decrease the call setup delay and processing requirements for such devices.
Некоторые устройства не обладают достаточной вычислительной мощностью, чтобы выполнять операции с открытым ключом или операции Диффи-Хеллмана для каждого вызова, либо предпочитают избегать этих операций при каждом вызове. Возможность повторно использовать ранее выполненные операции с открытым ключом или операции Диффи-Хеллмана может значительно сократить задержку установления вызова и требования к обработке для таких устройств.
In certain devices, it can take a second or two to perform a Diffie- Hellman operation. Examples of these devices include handsets, IP Multimedia Services Identity Modules (ISIMs), and PSTN gateways. PSTN gateways typically utilize a Digital Signal Processor (DSP) that is not yet involved with typical DSP operations at the beginning of a call; thus, the DSP could be used to perform the calculation, so as to avoid having the central host processor perform the calculation. However, not all PSTN gateways use DSPs (some have only central processors or their DSPs are incapable of performing the necessary public key or Diffie-Hellman operation), and handsets lack a separate, unused processor to perform these operations. Two scenarios where R-REUSE is useful are calls between an endpoint and its voicemail server or its PSTN gateway. In those scenarios, calls are made relatively often and it can be useful for the voicemail server or PSTN gateway to avoid public key operations for subsequent calls.
В некоторых устройствах выполнение операции Диффи-Хеллмана может занимать одну-две секунды. Примеры таких устройств — телефонные аппараты, модули идентификации мультимедийных услуг IP (ISIM) и шлюзы PSTN. Шлюзы PSTN обычно используют цифровой сигнальный процессор (DSP), который в начале вызова ещё не занят типичными операциями DSP; таким образом, DSP можно задействовать для выполнения вычислений, чтобы не загружать центральный процессор. Однако не все шлюзы PSTN используют DSP (у некоторых есть только центральные процессоры, а их DSP неспособны выполнять необходимые операции с открытым ключом или операции Диффи-Хеллмана), а телефонные аппараты не имеют отдельного незанятого процессора для выполнения этих операций. Два сценария, в которых полезен R-REUSE, — это вызовы между конечной точкой и её сервером голосовой почты или её шлюзом PSTN. В этих сценариях вызовы совершаются относительно часто, и серверу голосовой почты или шлюзу PSTN может быть полезно избегать операций с открытым ключом для последующих вызовов.
Storing keys across sessions often interferes with perfect forward secrecy (R-PFS).
Хранение ключей между сеансами часто мешает совершенной прямой секретности (R-PFS).
4.6. Transcoding
4.6. Транскодинг
The discussion in this section relates to requirement R-TRANSCODER.
Обсуждение в этом разделе относится к требованию R-TRANSCODER.
In some environments, it is necessary for network equipment to transcode from one codec (e.g., a highly compressed codec that makes efficient use of wireless bandwidth) to another codec (e.g., a standardized codec to a SIP peering interface). With RTP, a transcoding function can be performed with the combination of a SIP back-to-back user agent (B2BUA) to modify the SDP and a processor to perform the transcoding between the codecs. However, with end-to-end secured SRTP, a transcoding function implemented the same way is a man-in-the-middle attack, and the key management system prevents its use.
В некоторых средах сетевому оборудованию необходимо транскодировать из одного кодека (например, сильно сжатого кодека, эффективно использующего беспроводную полосу пропускания) в другой кодек (например, в стандартизованный кодек для интерфейса пиринга SIP). В RTP функцию транскодирования можно выполнить сочетанием SIP-агента с обратным соединением (B2BUA) для изменения SDP и процессора для транскодирования между кодеками. Однако при сквозной защите SRTP функция транскодирования, реализованная таким же образом, является атакой «человек посередине», и система управления ключами препятствует её использованию.
However, such a network-based transcoder can still be realized with the cooperation and approval of the endpoint, and can provide end-to- transcoder and transcoder-to-end security.
Однако такой сетевой транскодер всё же может быть реализован при сотрудничестве и одобрении конечной точки и может обеспечивать защиту «конечная точка — транскодер» и «транскодер — конечная точка».
4.7. Upgrading to SRTP
4.7. Переход на SRTP
The discussion in this section relates to the requirement R-ALLOW- RTP.
Обсуждение в этом разделе относится к требованию R-ALLOW-RTP.
Legitimate RTP media can be sent to an endpoint for announcements, colorful ringback tones (e.g., music), advertising, or normal call progress tones. The RTP may be received before an associated SDP answer. For details on various scenarios, see [EARLY-MEDIA].
Законные медиаданные RTP могут отправляться конечной точке для объявлений, красочных мелодий обратного вызова (например, музыки), рекламы или обычных тонов хода вызова. RTP может быть получен до соответствующего ответа SDP. Подробности о различных сценариях см. в [EARLY-MEDIA].
While receiving such RTP exposes the calling party to a risk of receiving malicious RTP from an attacker, SRTP endpoints will need to receive and play out RTP media in order to be compatible with deployed systems that send RTP to calling parties.
Хотя получение такого RTP подвергает вызывающую сторону риску получить вредоносный RTP от атакующего, конечные точки SRTP должны принимать и воспроизводить медиаданные RTP, чтобы быть совместимыми с развёрнутыми системами, которые отправляют RTP вызывающим сторонам.
4.8. Interworking with Other Signaling Protocols
4.8. Взаимодействие с другими протоколами сигнализации
The discussion in this section relates to the requirement R-OTHER- SIGNALING.
Обсуждение в этом разделе относится к требованию R-OTHER-SIGNALING.
In many environments, some devices are signaled with protocols other than SIP that do not share SIP's offer/answer model (e.g., [H.248.1] or do not utilize SDP (e.g., H.323). In other environments, both endpoints may be SIP, but may use different key management systems (e.g., one uses MIKEY-RSA, the other MIKEY-RSA-R).
Во многих средах некоторые устройства сигнализируются протоколами, отличными от SIP, которые не используют модель предложения/ответа SIP (например, [H.248.1]) или не используют SDP (например, H.323). В других средах обе конечные точки могут использовать SIP, но применять разные системы управления ключами (например, одна использует MIKEY-RSA, другая — MIKEY-RSA-R).
In these environments, it is desirable to have SRTP -- rather than RTP -- between the two endpoints. It is always possible, although undesirable, to interwork those disparate signaling systems or disparate key management systems by decrypting and re-encrypting each SRTP packet in a device in the middle of the network (often the same device performing the signaling interworking). This is undesirable due to the cost and increased attack area, as such an SRTP/SRTP interworking device is a valuable attack target.
В этих средах желательно иметь SRTP, а не RTP, между двумя конечными точками. Всегда возможно, хотя и нежелательно, обеспечить взаимодействие этих разнородных систем сигнализации или разнородных систем управления ключами путём расшифрования и повторного шифрования каждого пакета SRTP в устройстве в середине сети (часто в том же устройстве, которое выполняет взаимодействие сигнализации). Это нежелательно из-за стоимости и увеличения площади атаки, поскольку такое устройство взаимодействия SRTP/SRTP является ценной целью для атаки.
At the time of this writing, interworking is considered important. Interworking without decryption/encryption of the SRTP, while useful, is not yet deemed critical because the scale of such SRTP deployments is, to date, relatively small.
На момент написания взаимодействие считается важным. Взаимодействие без расшифрования/шифрования SRTP, хотя и полезное, пока не признано критически важным, поскольку масштаб таких развёртываний SRTP на сегодняшний день относительно невелик.
4.9. Certificates
4.9. Сертификаты
The discussion in this section relates to R-CERTS.
Обсуждение в этом разделе относится к R-CERTS.
On the Internet and on some private networks, validating another peer's certificate is often done through a trust anchor -- a list of Certificate Authorities that are trusted. It can be difficult or expensive for a peer to obtain these certificates. In all cases, both parties to the call would need to trust the same trust anchor (i.e., "certificate authority"). For these reasons, it is important that the media plane key management protocol offer a mechanism that allows end-users who have no prior association to authenticate to each other without acquiring credentials from a third-party trust point. Note that this does not rule out mechanisms in which servers have certificates and attest to the identities of end-users.
В Интернете и в некоторых частных сетях проверка сертификата другого партнёра часто выполняется через доверенный якорь — список центров сертификации, которым доверяют. Партнёру может быть трудно или дорого получить эти сертификаты. Во всех случаях обе стороны вызова должны доверять одному и тому же доверенному якорю (то есть «центру сертификации»). По этим причинам важно, чтобы протокол управления ключами медиаплоскости предлагал механизм, позволяющий конечным пользователям, не имеющим предварительных связей, аутентифицировать друг друга без получения учётных данных из сторонней точки доверия. Отметим, что это не исключает механизмы, в которых серверы имеют сертификаты и удостоверяют идентичности конечных пользователей.
5. Requirements
5. Требования
This section is divided into several parts: requirements specific to the key management protocol (Section 5.1), attack scenarios (Section 5.2), and requirements that can be met inside the key management protocol or outside of the key management protocol (Section 5.3).
Этот раздел разделён на несколько частей: требования, специфичные для протокола управления ключами (раздел 5.1), сценарии атак (раздел 5.2) и требования, которые могут быть выполнены внутри или вне протокола управления ключами (раздел 5.3).
5.1. Key Management Protocol Requirements
5.1. Требования к протоколу управления ключами
SIP Forking and Retargeting, from Section 4.2:
Разветвление и ретаргетинг в SIP, из раздела 4.2:
R-FORK-RETARGET: The media security key management protocol MUST securely support forking and retargeting when all endpoints are willing to use SRTP without causing the call setup to fail. This requirement means the endpoints that did not answer the call MUST NOT learn the SRTP keys (in either direction) used by the answering endpoint.
R-FORK-RETARGET: Протокол управления ключами медиабезопасности ДОЛЖЕН безопасно поддерживать разветвление и ретаргетинг, когда все конечные точки готовы использовать SRTP, не вызывая сбоя установления вызова. Это требование означает, что конечные точки, не ответившие на вызов, НЕ ДОЛЖНЫ узнавать ключи SRTP (в любом направлении), используемые отвечающей конечной точкой.
R-DISTINCT: The media security key management protocol MUST be capable of creating distinct, independent cryptographic contexts for each endpoint in a forked session.
R-DISTINCT: Протокол управления ключами медиабезопасности ДОЛЖЕН быть способен создавать различные независимые криптографические контексты для каждой конечной точки в разветвлённом сеансе.
R-HERFP: The media security key management protocol MUST function securely even in the presence of HERFP behavior, i.e., the rejection of key information does not reach the sender.
R-HERFP: Протокол управления ключами медиабезопасности ДОЛЖЕН функционировать безопасно даже при наличии поведения HERFP, то есть когда отклонение ключевой информации не доходит до отправителя.
Performance considerations:
Соображения производительности:
R-REUSE: The media security key management protocol MAY support the reuse of a previously established security context.
R-REUSE: Протокол управления ключами медиабезопасности МОЖЕТ поддерживать повторное использование ранее установленного контекста безопасности.
Note: reuse of the security context does not imply reuse of RTP parameters (e.g., payload type or SSRC).
Прим.: повторное использование контекста не подразумевает повторного использования параметров RTP (например, типа полезной нагрузки или SSRC).
Media considerations:
Соображения о медиаданных:
R-AVOID-CLIPPING: The media security key management protocol SHOULD avoid clipping media before SDP answer without requiring Security Preconditions [RFC5027]. This requirement comes from Section 4.1.
R-AVOID-CLIPPING: Протокол управления ключами медиабезопасности ДОЛЖЕН избегать обрезки медиаданных до ответа SDP, не требуя предварительных условий безопасности (Security Preconditions) [RFC5027]. Это требование происходит из раздела 4.1.
R-RTP-CHECK: If SRTP key negotiation is performed over the media path (i.e., using the same UDP/TCP ports as media packets), the key negotiation packets MUST NOT pass the RTP validity check defined in Appendix A.1 of [RFC3550], so that SRTP negotiation packets can be differentiated from RTP packets.
R-RTP-CHECK: Если согласование ключей SRTP выполняется по медийному пути (то есть с использованием тех же портов UDP/TCP, что и медиапакеты), пакеты согласования ключей НЕ ДОЛЖНЫ проходить проверку достоверности RTP, определённую в приложении A.1 к [RFC3550], чтобы пакеты согласования SRTP можно было отличить от пакетов RTP.
R-ASSOC: The media security key management protocol SHOULD include a mechanism for associating key management messages with both the signaling traffic that initiated the session and with protected media traffic. It is useful to associate key management messages with call signaling messages, as this allows the SDP offerer to avoid performing CPU-consuming operations (e.g., Diffie-Hellman or public key operations) with attackers that have not seen the signaling messages.
R-ASSOC: Протокол управления ключами медиабезопасности ДОЛЖЕН включать механизм связывания сообщений управления ключами как с сигнальным трафиком, инициировавшим сеанс, так и с защищаемым медиатрафиком. Полезно связывать сообщения управления ключами с сообщениями сигнализации вызова, поскольку это позволяет инициатору SDP избегать ресурсоёмких операций (например, операций Диффи-Хеллмана или операций с открытым ключом) с атакующими, которые не видели сигнальные сообщения.
For example, if using a Diffie-Hellman keying technique with security preconditions that forks to 20 endpoints, the call initiator would get 20 provisional responses containing 20 signed Diffie-Hellman key pairs. Calculating 20 Diffie-Hellman secrets and validating signatures can be a difficult task for some devices. Hence, in the case of forking, it is not desirable to perform a Diffie-Hellman operation with every party, but rather only with the party that answers the call (and incur some media clipping). To do this, the signaling and media need to be associated so the calling party knows which key management exchange needs to be completed. This might be done by using the transport address indicated in the SDP, although NATs can complicate this association.
Например, при использовании метода формирования ключей Диффи-Хеллмана с предварительными условиями безопасности, разветвляющегося на 20 конечных точек, инициатор вызова получил бы 20 предварительных ответов, содержащих 20 подписанных пар ключей Диффи-Хеллмана. Вычисление 20 секретов Диффи-Хеллмана и проверка подписей может быть трудной задачей для некоторых устройств. Следовательно, при разветвлении нежелательно выполнять операцию Диффи-Хеллмана с каждой стороной, а только со стороной, отвечающей на вызов (при этом возникает некоторая обрезка медиаданных). Для этого сигнализацию и медиаданные нужно связать, чтобы вызывающая сторона знала, какой обмен ключами нужно завершить. Это можно сделать с помощью транспортного адреса, указанного в SDP, хотя NAT могут усложнить такую связь.
Note: due to RTP's design requirements, it is expected that SRTP receivers will have to perform authentication of any received SRTP packets.
Примечание: из-за требований к проектированию RTP ожидается, что получатели SRTP должны будут выполнять аутентификацию любых полученных пакетов SRTP.
R-NEGOTIATE: The media security key management protocol MUST allow a SIP User Agent to negotiate media security parameters for each individual session. Such negotiation MUST NOT cause a two-time pad (Section 9.1 of [RFC3711]).
R-NEGOTIATE: Протокол управления ключами медиабезопасности ДОЛЖЕН позволять пользовательскому агенту SIP согласовывать параметры медиабезопасности для каждого отдельного сеанса. Такое согласование НЕ ДОЛЖНО приводить к двукратному наложению гаммы (раздел 9.1 в [RFC3711]).
R-PSTN: The media security key management protocol MUST support termination of media security in a PSTN gateway. This requirement is from Section 4.4.
R-PSTN: Протокол управления ключами медиабезопасности ДОЛЖЕН поддерживать завершение медиабезопасности на шлюзе PSTN. Это требование из раздела 4.4.
5.2. Security Requirements
5.2. Требования безопасности
This section describes overall security requirements and specific requirements from the attack scenarios (Section 3). Overall security requirements:
В этом разделе описаны общие требования безопасности и конкретные требования из сценариев атак (раздел 3). Общие требования безопасности:
R-PFS: The media security key management protocol MUST be able to support perfect forward secrecy.
R-PFS: Протокол управления ключами медиабезопасности ДОЛЖЕН быть способен поддерживать совершенную прямую секретность.
R-COMPUTE: The media security key management protocol MUST support offering additional SRTP cipher suites without incurring significant computational expense.
R-COMPUTE: Протокол управления ключами медиабезопасности ДОЛЖЕН поддерживать предложение дополнительных наборов шифров SRTP без значительных вычислительных затрат.
R-CERTS: The key management protocol MUST NOT require that end-users obtain credentials (certificates or private keys) from a third- party trust anchor.
R-CERTS: Протокол управления ключами НЕ ДОЛЖЕН требовать, чтобы конечные пользователи получали учётные данные (сертификаты или закрытые ключи) из стороннего доверенного якоря.
R-FIPS: The media security key management protocol SHOULD use algorithms that allow FIPS 140-2 [FIPS-140-2] certification or similar country-specific certification (e.g., [AISITSEC]).
R-FIPS: Протокол управления ключами медиабезопасности ДОЛЖЕН использовать алгоритмы, допускающие сертификацию по FIPS 140-2 [FIPS-140-2] или аналогичную сертификацию, специфичную для страны (например, [AISITSEC]).
The United States Government can only purchase and use crypto implementations that have been validated by the FIPS-140 [FIPS-140-2] process:
Правительство Соединённых Штатов может приобретать и использовать только те криптографические реализации, которые прошли проверку в рамках процесса FIPS-140 [FIPS-140-2]:
The FIPS-140 standard is applicable to all Federal agencies that use cryptographic-based security systems to protect sensitive information in computer and telecommunication systems, including voice systems. The adoption and use of this standard is available to private and commercial organizations.
Стандарт FIPS-140 применим ко всем федеральным агентствам, использующим криптографические системы безопасности для защиты конфиденциальной информации в компьютерных и телекоммуникационных системах, включая голосовые системы. Принятие и использование этого стандарта доступно частным и коммерческим организациям.
Some commercial organizations, such as banks and defense contractors, require or prefer equipment that has received the same validation.
Некоторые коммерческие организации, такие как банки и оборонные подрядчики, требуют или предпочитают оборудование, получившее такую же проверку.
R-DOS: The media security key management protocol MUST NOT introduce any new significant denial-of-service vulnerabilities (e.g., the protocol should not request the endpoint to perform CPU- intensive operations without the client being able to validate or authorize the request).
R-DOS: Протокол управления ключами медиабезопасности НЕ ДОЛЖЕН вносить новые значительные уязвимости к отказу в обслуживании (например, протокол не должен требовать от конечной точки выполнения ресурсоёмких операций без возможности клиента проверить или авторизовать запрос).
R-EXISTING: The media security key management protocol SHOULD allow endpoints to authenticate using pre-existing cryptographic credentials, e.g., certificates or pre-shared keys.
R-EXISTING: Протокол управления ключами медиабезопасности ДОЛЖЕН позволять конечным точкам аутентифицироваться с помощью существующих криптографических учётных данных, например сертификатов или предварительно разделённых ключей.
R-AGILITY: The media security key management protocol MUST provide crypto- agility, i.e., the ability to adapt to evolving cryptography and security requirements (update of cryptographic algorithms without substantial disruption to deployed implementations).
R-AGILITY: Протокол управления ключами медиабезопасности ДОЛЖЕН обеспечивать криптографическую гибкость, то есть способность адаптироваться к развивающейся криптографии и требованиям безопасности (обновление криптографических алгоритмов без существенных нарушений для развёрнутых реализаций).
R-DOWNGRADE: The media security key management protocol MUST protect cipher suite negotiation against downgrading attacks.
R-DOWNGRADE: Протокол управления ключами медиабезопасности ДОЛЖЕН защищать согласование наборов шифров от атак понижения уровня.
R-PASS-MEDIA: The media security key management protocol MUST have a mode that prevents a passive adversary with access to the media path from gaining access to keying material used to protect SRTP media packets.
R-PASS-MEDIA: Протокол управления ключами медиабезопасности ДОЛЖЕН иметь режим, предотвращающий получение пассивным противником с доступом к медийному пути ключевого материала, используемого для защиты медиапакетов SRTP.
R-PASS-SIG: The media security key management protocol MUST have a mode in which it prevents a passive adversary with access to the signaling path from gaining access to keying material used to protect SRTP media packets.
R-PASS-SIG: Протокол управления ключами медиабезопасности ДОЛЖЕН иметь режим, в котором он предотвращает получение пассивным противником с доступом к сигнальному пути ключевого материала, используемого для защиты медиапакетов SRTP.
R-SIG-MEDIA: The media security key management protocol MUST have a mode in which it defends itself from an attacker that is solely on the media path and from an attacker that is solely on the signaling path. A successful attack refers to the ability for the adversary to obtain keying material to decrypt the SRTP encrypted media traffic.
R-SIG-MEDIA: Протокол управления ключами медиабезопасности ДОЛЖЕН иметь режим, в котором он защищается от атакующего, находящегося исключительно на медийном пути, и от атакующего, находящегося исключительно на сигнальном пути. Успешная атака означает способность противника получить ключевой материал для расшифрования зашифрованного медиатрафика SRTP.
R-ID-BINDING: The media security key management protocol MUST enable the media security keys to be cryptographically bound to an identity of the endpoint.
R-ID-BINDING: Протокол управления ключами медиабезопасности ДОЛЖЕН позволять криптографически привязывать ключи медиабезопасности к идентичности конечной точки.
Note: This allows domains to deploy SIP Identity [RFC4474].
Примечание: это позволяет доменам развёртывать SIP Identity [RFC4474].
R-ACT-ACT: The media security key management protocol MUST support a mode of operation that provides active-signaling-active-media-detect robustness, and MAY support modes of operation that provide lower levels of robustness (as described in Section 3).
R-ACT-ACT: Протокол управления ключами медиабезопасности ДОЛЖЕН поддерживать режим работы, обеспечивающий устойчивость active-signaling-active-media-detect, и МОЖЕТ поддерживать режимы работы с более низкими уровнями устойчивости (как описано в разделе 3).
Note: Failing to meet R-ACT-ACT indicates the protocol cannot provide secure end-to-end media.

Appendix A. Overview and Evaluation of Existing Keying Mechanisms
Приложение A. Обзор и оценка существующих механизмов формирования ключей
Based on how the SRTP keys are exchanged, each SRTP key exchange mechanism belongs to one general category:
В зависимости от того, как обмениваются ключи SRTP, каждый механизм обмена ключами SRTP относится к одной общей категории:
signaling path: All the keying is carried in the call signaling (SIP or SDP) path.
signaling path: Весь ключевой материал передаётся по сигнальному пути вызова (SIP или SDP).
media path: All the keying is carried in the SRTP/SRTCP media path, and no signaling whatsoever is carried in the call signaling path.
media path: Весь ключевой материал передаётся по медийному пути SRTP/SRTCP, и никакая сигнализация не передаётся по сигнальному пути вызова.
signaling and media path: Parts of the keying are carried in the SRTP/SRTCP media path, and parts are carried in the call signaling (SIP or SDP) path.
signaling and media path: Части ключевого материала передаются по медийному пути SRTP/SRTCP, а части — по сигнальному пути вызова (SIP или SDP).
One of the significant benefits of SRTP over other end-to-end encryption mechanisms, such as for example IPsec, is that SRTP is bandwidth efficient and SRTP retains the header of RTP packets. Bandwidth efficiency is vital for VoIP in many scenarios where access bandwidth is limited or expensive, and retaining the RTP header is important for troubleshooting packet loss, delay, and jitter.
Одно из значительных преимуществ SRTP перед другими механизмами сквозного шифрования, например IPsec, состоит в том, что SRTP эффективно использует полосу пропускания и сохраняет заголовок пакетов RTP. Эффективность использования полосы пропускания жизненно важна для VoIP во многих сценариях, где доступная полоса пропускания ограничена или дорога, а сохранение заголовка RTP важно для диагностики потерь пакетов, задержки и джиттера.
Related to SRTP's characteristics is a goal that any SRTP keying mechanism to also be efficient and not cause additional call setup delay. Contributors to additional call setup delay include network or database operations: retrieval of certificates and additional SIP or media path messages, and computational overhead of establishing keys or validating certificates.
С характеристиками SRTP связана цель: любой механизм формирования ключей SRTP также должен быть эффективным и не вызывать дополнительной задержки установления вызова. К дополнительной задержке установления вызова приводят сетевые операции или операции с базами данных: получение сертификатов и дополнительные сообщения SIP или медийного пути, а также вычислительные затраты на установление ключей или проверку сертификатов.
When examining the choice between keying in the signaling path, keying in the media path, or keying in both paths, it is important to realize the media path is generally "faster" than the SIP signaling path. The SIP signaling path has computational elements involved that parse and route SIP messages. The media path, on the other hand, does not normally have computational elements involved, and even when computational elements such as firewalls are involved, they cause very little additional delay. Thus, the media path can be useful for exchanging several messages to establish SRTP keys. A disadvantage of keying over the media path is that interworking different key exchange requires the interworking function be in the media path, rather than just in the signaling path; in practice, this involvement is probably unavoidable anyway.
При рассмотрении выбора между формированием ключей на сигнальном пути, на медийном пути или на обоих путях важно понимать, что медийный путь обычно «быстрее» сигнального пути SIP. На сигнальном пути SIP есть вычислительные элементы, которые разбирают и маршрутизируют сообщения SIP. Медийный путь, напротив, обычно не содержит вычислительных элементов, и даже когда в нём участвуют такие вычислительные элементы, как межсетевые экраны, они вносят очень небольшую дополнительную задержку. Таким образом, медийный путь может быть полезен для обмена несколькими сообщениями при установлении ключей SRTP. Недостаток формирования ключей по медийному пути состоит в том, что для взаимодействия разных обменов ключами функция взаимодействия должна находиться на медийном пути, а не только на сигнальном; на практике такое участие, вероятно, всё равно неизбежно.
A.1. Signaling Path Keying Techniques
A.1. Методы ключей на сигнальном пути
A.1.1. MIKEY-NULL
A.1.1. MIKEY-NULL
MIKEY-NULL [RFC3830] has the offerer indicate the SRTP keys for both directions. The key is sent unencrypted in SDP, which means the SDP must be encrypted hop-by-hop (e.g., by using TLS (SIPS)) or end-to- end (e.g., by using Secure/Multipurpose Internet Mail Extensions (S/MIME)).
В MIKEY-NULL [RFC3830] инициатор указывает ключи SRTP для обоих направлений. Ключ передаётся в SDP незашифрованным, что означает, что SDP должен быть зашифрован по звеньям (например, с помощью TLS (SIPS)) или сквозным образом (например, с помощью Secure/Multipurpose Internet Mail Extensions (S/MIME)).
MIKEY-NULL requires one message from offerer to answerer (half a round trip), and does not add additional media path messages.
MIKEY-NULL требует одного сообщения от инициатора к отвечающей стороне (половина кругового обмена) и не добавляет дополнительных сообщений медийного пути.
A.1.2. MIKEY-PSK
A.1.2. MIKEY-PSK
MIKEY-PSK (pre-shared key) [RFC3830] requires that all endpoints share one common key. MIKEY-PSK has the offerer encrypt the SRTP keys for both directions using this pre-shared key.
MIKEY-PSK (предварительно разделённый ключ) [RFC3830] требует, чтобы все конечные точки разделяли один общий ключ. В MIKEY-PSK инициатор шифрует ключи SRTP для обоих направлений этим предварительно разделённым ключом.
MIKEY-PSK requires one message from offerer to answerer (half a round trip), and does not add additional media path messages.
MIKEY-PSK требует одного сообщения от инициатора к отвечающей стороне (половина кругового обмена) и не добавляет дополнительных сообщений медийного пути.
A.1.3. MIKEY-RSA
A.1.3. MIKEY-RSA
MIKEY-RSA [RFC3830] has the offerer encrypt the keys for both directions using the intended answerer's public key, which is obtained from a mechanism outside of MIKEY.
В MIKEY-RSA [RFC3830] инициатор шифрует ключи для обоих направлений открытым ключом предполагаемой отвечающей стороны, который получается с помощью механизма вне MIKEY.
MIKEY-RSA requires one message from offerer to answerer (half a round trip), and does not add additional media path messages. MIKEY-RSA requires the offerer to obtain the intended answerer's certificate.
MIKEY-RSA требует одного сообщения от инициатора к отвечающей стороне (половина кругового обмена) и не добавляет дополнительных сообщений медийного пути. MIKEY-RSA требует, чтобы инициатор получил сертификат предполагаемой отвечающей стороны.
A.1.4. MIKEY-RSA-R
A.1.4. MIKEY-RSA-R
MIKEY-RSA-R [RFC4738] is essentially the same as MIKEY-RSA but reverses the role of the offerer and the answerer with regards to providing the keys. That is, the answerer encrypts the keys for both directions using the offerer's public key. Both the offerer and answerer validate each other's public keys using a standard X.509 validation techniques. MIKEY-RSA-R also enables sending certificates in the MIKEY message.
MIKEY-RSA-R [RFC4738] по существу совпадает с MIKEY-RSA, но меняет роли инициатора и отвечающей стороны в отношении предоставления ключей. То есть отвечающая сторона шифрует ключи для обоих направлений открытым ключом инициатора. И инициатор, и отвечающая сторона проверяют открытые ключи друг друга с помощью стандартных методов проверки X.509. MIKEY-RSA-R также позволяет отправлять сертификаты в сообщении MIKEY.
MIKEY-RSA-R requires one message from offerer to answer, and one message from answerer to offerer (full round trip), and does not add additional media path messages. MIKEY-RSA-R requires the offerer validate the answerer's certificate.
MIKEY-RSA-R требует одного сообщения от инициатора к отвечающей стороне и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен) и не добавляет дополнительных сообщений медийного пути. MIKEY-RSA-R требует, чтобы инициатор проверил сертификат отвечающей стороны.
A.1.5. MIKEY-DHSIGN
A.1.5. MIKEY-DHSIGN
In MIKEY-DHSIGN [RFC3830], the offerer and answerer derive the key from a Diffie-Hellman (DH) exchange. In order to prevent an active man-in-the-middle, the DH exchange itself is signed using each endpoint's private key and the associated public keys are validated using standard X.509 validation techniques.
В MIKEY-DHSIGN [RFC3830] инициатор и отвечающая сторона выводят ключ из обмена Диффи-Хеллмана (DH). Чтобы предотвратить активную атаку «человек посередине», сам обмен DH подписывается закрытым ключом каждой конечной точки, а связанные открытые ключи проверяются с помощью стандартных методов проверки X.509.
MIKEY-DHSIGN requires one message from offerer to answerer, and one message from answerer to offerer (full round trip), and does not add additional media path messages. MIKEY-DHSIGN requires the offerer and answerer to validate each other's certificates. MIKEY-DHSIGN also enables sending the answerer's certificate in the MIKEY message.
MIKEY-DHSIGN требует одного сообщения от инициатора к отвечающей стороне и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен) и не добавляет дополнительных сообщений медийного пути. MIKEY-DHSIGN требует, чтобы инициатор и отвечающая сторона проверили сертификаты друг друга. MIKEY-DHSIGN также позволяет отправлять сертификат отвечающей стороны в сообщении MIKEY.
A.1.6. MIKEY-DHHMAC
A.1.6. MIKEY-DHHMAC
MIKEY-DHHMAC [RFC4650] uses a pre-shared secret to HMAC the Diffie- Hellman exchange, essentially combining aspects of MIKEY-PSK with MIKEY-DHSIGN, but without MIKEY-DHSIGN's need for certificate authentication.
MIKEY-DHHMAC [RFC4650] использует предварительно разделённый секрет для HMAC обмена Диффи-Хеллмана, по существу объединяя аспекты MIKEY-PSK с MIKEY-DHSIGN, но без необходимости аутентификации по сертификатам, характерной для MIKEY-DHSIGN.
MIKEY-DHHMAC requires one message from offerer to answerer, and one message from answerer to offerer (full round trip), and does not add additional media path messages.
MIKEY-DHHMAC требует одного сообщения от инициатора к отвечающей стороне и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен) и не добавляет дополнительных сообщений медийного пути.
A.1.7. MIKEY-ECIES and MIKEY-ECMQV (MIKEY-ECC)
A.1.7. MIKEY-ECIES и MIKEY-ECMQV (MIKEY-ECC)
ECC Algorithms For MIKEY [MIKEY-ECC] describes how ECC can be used with MIKEY-RSA (using Elliptic Curve Digital Signature Algorithm (ECDSA) signature) and with MIKEY-DHSIGN (using a new DH-Group code), and also defines two new ECC-based algorithms, Elliptic Curve Integrated Encryption Scheme (ECIES) and Elliptic Curve Menezes-Qu- Vanstone (ECMQV) .
ECC Algorithms For MIKEY [MIKEY-ECC] описывает, как ECC можно использовать с MIKEY-RSA (с подписью Elliptic Curve Digital Signature Algorithm (ECDSA)) и с MIKEY-DHSIGN (с новым кодом DH-Group), а также определяет два новых алгоритма на основе ECC: Elliptic Curve Integrated Encryption Scheme (ECIES) и Elliptic Curve Menezes-Qu-Vanstone (ECMQV).
With this proposal, the ECDSA signature, MIKEY-ECIES, and MIKEY-ECMQV function exactly like MIKEY-RSA, and the new DH-Group code function exactly like MIKEY-DHSIGN. Therefore, these ECC mechanisms are not discussed separately in this document.
В этом предложении подпись ECDSA, MIKEY-ECIES и MIKEY-ECMQV функционируют точно так же, как MIKEY-RSA, а новый код DH-Group функционирует точно так же, как MIKEY-DHSIGN. Поэтому эти механизмы ECC в настоящем документе отдельно не рассматриваются.
A.1.8. SDP Security Descriptions with SIPS
A.1.8. SDP Security Descriptions с SIPS
SDP Security Descriptions [RFC4568] have each side indicate the key they will use for transmitting SRTP media, and the keys are sent in the clear in SDP. SDP Security Descriptions rely on hop-by-hop (TLS via "SIPS:") encryption to protect the keys exchanged in signaling. SDP Security Descriptions requires one message from offerer to answerer, and one message from answerer to offerer (full round trip), and does not add additional media path messages.
В SDP Security Descriptions [RFC4568] каждая сторона указывает ключ, который будет использовать для передачи медиаданных SRTP, и ключи передаются в SDP в открытом виде. SDP Security Descriptions полагаются на пошаговое (TLS через «SIPS:») шифрование для защиты ключей, обмениваемых при сигнализации. SDP Security Descriptions требует одного сообщения от инициатора к отвечающей стороне и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен) и не добавляет дополнительных сообщений медийного пути.
A.1.9. SDP Security Descriptions with S/MIME
A.1.9. SDP Security Descriptions с S/MIME
This keying mechanism is identical to Appendix A.1.8 except that, rather than protecting the signaling with TLS, the entire SDP is encrypted with S/MIME.
Этот механизм формирования ключей идентичен приложению A.1.8, за исключением того, что вместо защиты сигнализации с помощью TLS весь SDP шифруется с помощью S/MIME.
A.1.10. SDP-DH (Expired)
A.1.10. SDP-DH (устаревший)
SDP Diffie-Hellman [SDP-DH] exchanges Diffie-Hellman messages in the signaling path to establish session keys. To protect against active man-in-the-middle attacks, the Diffie-Hellman exchange needs to be protected with S/MIME, SIPS, or SIP Identity [RFC4474] and SIP Connected Identity [RFC4916].
SDP Diffie-Hellman [SDP-DH] обменивается сообщениями Диффи-Хеллмана на сигнальном пути для установления ключей сеанса. Для защиты от активных атак «человек посередине» обмен Диффи-Хеллмана нужно защищать с помощью S/MIME, SIPS или SIP Identity [RFC4474] и SIP Connected Identity [RFC4916].
SDP-DH requires one message from offerer to answerer, and one message from answerer to offerer (full round trip), and does not add additional media path messages.
SDP-DH требует одного сообщения от инициатора к отвечающей стороне и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен) и не добавляет дополнительных сообщений медийного пути.
A.1.11. MIKEYv2 in SDP (Expired)
A.1.11. MIKEYv2 в SDP (устаревший)
MIKEYv2 [MIKEYv2] adds mode negotiation to MIKEYv1 and removes the time synchronization requirement. It therefore now takes 2 round trips to complete. In the first round trip, the communicating parties learn each other's identities, agree on a MIKEY mode, crypto algorithm, SRTP policy, and exchanges nonces for replay protection. In the second round trip, they negotiate unicast and/or group SRTP context for SRTP and/or SRTCP.
MIKEYv2 [MIKEYv2] добавляет согласование режима к MIKEYv1 и устраняет требование синхронизации времени. Поэтому теперь для завершения требуется 2 круговых обмена. В первом круговом обмене общающиеся стороны узнают идентичности друг друга, договариваются о режиме MIKEY, криптографическом алгоритме, политике SRTP и обмениваются nonce для защиты от воспроизведения. Во втором круговом обмене они согласуют одноадресный и/или групповой контекст SRTP для SRTP и/или SRTCP.
Furthermore, MIKEYv2 also defines an in-band negotiation mode as an alternative to SDP (see Appendix A.3.3).
Кроме того, MIKEYv2 также определяет режим согласования в полосе как альтернативу SDP (см. приложение A.3.3).
A.2. Media Path Keying Technique
A.2. Методы ключей на медийном пути
A.2.1. ZRTP
A.2.1. ZRTP
ZRTP [ZRTP] does not exchange information in the signaling path (although it's possible for endpoints to exchange a hash of the ZRTP Hello message with "a=zrtp-hash" in the initial offer if sent over an integrity-protected signaling channel. This provides some useful correlation between the signaling and media layers). In ZRTP, the keys are exchanged entirely in the media path using a Diffie-Hellman exchange. The advantage to this mechanism is that the signaling channel is used only for call setup and the media channel is used to establish an encrypted channel -- much like encryption devices on the PSTN. ZRTP uses voice authentication of its Diffie-Hellman exchange by having each person read digits or words to the other person. Subsequent sessions with the same ZRTP endpoint can be authenticated using the stored hash of the previously negotiated key rather than voice authentication. ZRTP uses four media path messages (Hello, Commit, DHPart1, and DHPart2) to establish the SRTP key, and three media path confirmation messages. These initial messages are all sent as non-RTP packets.
ZRTP [ZRTP] не обменивается информацией на сигнальном пути (хотя конечные точки могут обменяться хешем сообщения ZRTP Hello с помощью «a=zrtp-hash» в начальном предложении, если оно отправлено по сигнальному каналу, защищённому целостностью; это обеспечивает полезную корреляцию между уровнями сигнализации и медиаданных). В ZRTP ключи обмениваются полностью на медийном пути с помощью обмена Диффи-Хеллмана. Преимущество этого механизма в том, что сигнальный канал используется только для установления вызова, а медийный канал — для установления зашифрованного канала, во многом как устройства шифрования в PSTN. ZRTP использует голосовую аутентификацию своего обмена Диффи-Хеллмана, заставляя каждого человека читать цифры или слова другому человеку. Последующие сеансы с той же конечной точкой ZRTP можно аутентифицировать с помощью сохранённого хеша ранее согласованного ключа вместо голосовой аутентификации. ZRTP использует четыре сообщения медийного пути (Hello, Commit, DHPart1 и DHPart2) для установления ключа SRTP и три сообщения подтверждения медийного пути. Все эти начальные сообщения отправляются как пакеты, не являющиеся RTP.
Note: that when ZRTP probing is used, unencrypted RTP can be exchanged until the SRTP keys are established.
Примечание: при использовании зондирования ZRTP незашифрованный RTP может обмениваться до установления ключей SRTP.
A.3. Signaling and Media Path Keying Techniques
A.3. Методы ключей на сигнальном и медийном путях
A.3.1. EKT
A.3.1. EKT
EKT [EKT] relies on another SRTP key exchange protocol, such as SDP Security Descriptions or MIKEY, for bootstrapping. In the initial phase, each member of a conference uses an SRTP key exchange protocol to establish a common key encryption key (KEK). Each member may use the KEK to securely transport its SRTP master key and current SRTP rollover counter (ROC), via RTCP, to the other participants in the session.
EKT [EKT] полагается на другой протокол обмена ключами SRTP, например SDP Security Descriptions или MIKEY, для начальной загрузки. На начальном этапе каждый участник конференции использует протокол обмена ключами SRTP для установления общего ключа шифрования ключей (KEK). Каждый участник может использовать KEK для безопасной передачи своего главного ключа SRTP и текущего счётчика переполнения SRTP (ROC) через RTCP другим участникам сеанса.
EKT requires the offerer to send some parameters (EKT_Cipher, KEK, and security parameter index (SPI)) via the bootstrapping protocol such as SDP Security Descriptions or MIKEY. Each answerer sends an SRTCP message that contains the answerer's SRTP Master Key, rollover counter, and the SRTP sequence number. Rekeying is done by sending a new SRTCP message. For reliable transport, multiple RTCP messages need to be sent.
EKT требует, чтобы инициатор отправил некоторые параметры (EKT_Cipher, KEK и индекс параметров безопасности (SPI)) через протокол начальной загрузки, такой как SDP Security Descriptions или MIKEY. Каждая отвечающая сторона отправляет сообщение SRTCP, содержащее главный ключ SRTP отвечающей стороны, счётчик переполнения и порядковый номер SRTP. Смена ключей выполняется отправкой нового сообщения SRTCP. Для надёжной передачи необходимо отправить несколько сообщений RTCP.
A.3.2. DTLS-SRTP
A.3.2. DTLS-SRTP
DTLS-SRTP [DTLS-SRTP] exchanges public key fingerprints in SDP [SIP-DTLS] and then establishes a DTLS session over the media channel. The endpoints use the DTLS handshake to agree on crypto suites and establish SRTP session keys. SRTP packets are then exchanged between the endpoints.
DTLS-SRTP [DTLS-SRTP] обменивается отпечатками открытых ключей в SDP [SIP-DTLS], а затем устанавливает сеанс DTLS по медийному каналу. Конечные точки используют рукопожатие DTLS, чтобы договориться о криптографических наборах и установить ключи сеанса SRTP. Затем между конечными точками обмениваются пакеты SRTP.
DTLS-SRTP requires one message from offerer to answerer (half round trip), and one message from the answerer to offerer (full round trip) so the offerer can correlate the SDP answer with the answering endpoint. DTLS-SRTP uses four media path messages to establish the SRTP key. This document assumes DTLS will use TLS_RSA_WITH_AES_128_CBC_SHA as its cipher suite, which is the mandatory-to-implement cipher suite in TLS [RFC5246].
DTLS-SRTP требует одного сообщения от инициатора к отвечающей стороне (половина кругового обмена) и одного сообщения от отвечающей стороны к инициатору (полный круговой обмен), чтобы инициатор мог сопоставить ответ SDP с отвечающей конечной точкой. DTLS-SRTP использует четыре сообщения медийного пути для установления ключа SRTP. В настоящем документе предполагается, что DTLS будет использовать TLS_RSA_WITH_AES_128_CBC_SHA в качестве набора шифров, который является обязательным для реализации набором шифров в TLS [RFC5246].
A.3.3. MIKEYv2 Inband (Expired)
A.3.3. MIKEYv2 в полосе (устаревший)
As defined in Appendix A.1.11, MIKEYv2 also defines an in-band negotiation mode as an alternative to SDP (see Appendix A.3.3). The details are not sorted out in the document yet on what in-band actually means (i.e., UDP, RTP, RTCP, etc.).
Как определено в приложении A.1.11, MIKEYv2 также определяет режим согласования в полосе как альтернативу SDP (см. приложение A.3.3). В документе ещё не уточнено, что именно означает «в полосе» (то есть UDP, RTP, RTCP и т. д.).

A.4.3. SSRC and ROC
A.4.3. SSRC и ROC
In SRTP, a cryptographic context is defined as the SSRC, destination network address, and destination transport port number. Whereas RTP, a flow is defined as the destination network address and destination transport port number. This results in a problem -- how to communicate the SSRC so that the SSRC can be used for the cryptographic context.
В SRTP криптографический контекст определяется как SSRC, сетевой адрес назначения и номер транспортного порта назначения. В RTP поток определяется как сетевой адрес назначения и номер транспортного порта назначения. Отсюда возникает проблема: как передать SSRC, чтобы SSRC можно было использовать для криптографического контекста.
Two approaches have emerged for this communication. One, used by all MIKEY modes, is to communicate the SSRCs to the peer in the MIKEY exchange. Another, used by SDP Security Descriptions, is to apply "late binding" -- that is, any new packet containing a previously unseen SSRC (which arrives at the same destination network address and destination transport port number) will create a new cryptographic context. Another approach, common amongst techniques with media-path SRTP key establishment, is to require a handshake over that media path before SRTP packets are sent. MIKEY's approach changes RTP's SSRC collision detection behavior by requiring RTP to pre-establish the SSRC values for each session.
Для такой передачи появились два подхода. Один, используемый всеми режимами MIKEY, состоит в передаче SSRC партнёру в обмене MIKEY. Другой, используемый SDP Security Descriptions, состоит в применении «позднего связывания» — то есть любой новый пакет, содержащий ранее не встречавшийся SSRC (который прибывает на тот же сетевой адрес назначения и тот же номер транспортного порта назначения), создаёт новый криптографический контекст. Ещё один подход, распространённый среди методов установления ключей SRTP по медийному пути, требует рукопожатия по этому медийному пути до отправки пакетов SRTP. Подход MIKEY изменяет поведение RTP при обнаружении коллизий SSRC, требуя, чтобы RTP заранее устанавливал значения SSRC для каждого сеанса.
Another related issue is that SRTP introduces a rollover counter (ROC), which records how many times the SRTP sequence number has rolled over. As the sequence number is used for SRTP's default ciphers, it is important that all endpoints know the value of the ROC. The ROC starts at 0 at the beginning of a session. Some keying mechanisms cause a two-time pad to occur if two endpoints of a forked call have an SSRC collision.
Ещё одна связанная проблема состоит в том, что SRTP вводит счётчик переполнения (ROC), который фиксирует, сколько раз порядковый номер SRTP переполнялся. Поскольку порядковый номер используется в стандартных шифрах SRTP, важно, чтобы все конечные точки знали значение ROC. ROC начинается с 0 в начале сеанса. Некоторые механизмы формирования ключей приводят к двукратному наложению гаммы, если у двух конечных точек разветвлённого вызова возникает коллизия SSRC.
Note: A proposal has been made to send the ROC value on every Nth SRTP packet[RFC4771]. This proposal has not yet been incorporated into this document.

A.5.1. Distribution and Validation of Persistent Public Keys and Certificates
A.5.1. Распространение и проверка постоянных открытых ключей и сертификатов
Using persistent public keys for confidentiality and authentication can introduce requirements for two types of systems, often implemented using certificates: (1) a system to distribute those persistent public keys certificates, and (2) a system for validating those persistent public keys. We refer to the former as a key distribution system and the latter as an authentication infrastructure. In many cases, a monolithic public key infrastructure (PKI) is used to fulfill both of these roles. However, these functions can be provided by many other systems. For instance, key distribution may be accomplished by any public repository of keys. Any system in which the two endpoints have access to trust anchors and intermediate CA certificates that can be used to validate other endpoints' certificates (including a system of self-signed certificates) can be used to support certificate validation in the below schemes.
Использование постоянных открытых ключей для конфиденциальности и аутентификации может порождать требования к системам двух типов, часто реализуемым с помощью сертификатов: (1) системе распространения сертификатов этих постоянных открытых ключей и (2) системе проверки этих постоянных открытых ключей. Первую мы называем системой распространения ключей, а вторую — инфраструктурой аутентификации. Во многих случаях для выполнения обеих ролей используется монолитная инфраструктура открытых ключей (PKI). Однако эти функции могут обеспечиваться многими другими системами. Например, распространение ключей может выполняться любым публичным хранилищем ключей. Любая система, в которой обе конечные точки имеют доступ к доверенным якорям и промежуточным сертификатам CA, которые можно использовать для проверки сертификатов других конечных точек (включая систему самоподписанных сертификатов), может использоваться для поддержки проверки сертификатов в приведённых ниже схемах.
With real-time communications, it is desirable to avoid fetching or validating certificates that delay call setup. Rather, it is preferable to fetch or validate certificates in such a way that call setup is not delayed. For example, a certificate can be validated while the phone is ringing or can be validated while ring-back tones are being played or even while the called party is answering the phone and saying "hello". Even better is to avoid fetching or validating persistent public keys at all.
В связи с обменом данными в реальном времени желательно избегать получения или проверки сертификатов, которые задерживают установление вызова. Напротив, предпочтительно получать или проверять сертификаты так, чтобы установление вызова не задерживалось. Например, сертификат можно проверить, пока звонит телефон, или пока воспроизводятся тоны обратного вызова, или даже пока вызываемая сторона отвечает на телефон и говорит «алло». Ещё лучше — вообще избегать получения или проверки постоянных открытых ключей.
SRTP key exchange mechanisms that require a particular authentication infrastructure to operate (whether for distribution or validation) are gated on the deployment of a such an infrastructure available to both endpoints. This means that no media security is achievable until such an infrastructure exists. For SIP, something like sip- certs [SIP-CERTS] might be used to obtain the certificate of a peer.

A.5.2. Perfect Forward Secrecy
A.5.2. Совершенная прямая секретность
In the context of SRTP, Perfect Forward Secrecy is the property that SRTP session keys that protected a previous session are not compromised if the static keys belonging to the endpoints are compromised. That is, if someone were to record your encrypted session content and later acquires either party's private key, that encrypted session content would be safe from decryption if your key exchange mechanism had perfect forward secrecy.
В контексте SRTP совершенная прямая секретность — это свойство, состоящее в том, что ключи сеанса SRTP, защищавшие предыдущий сеанс, не компрометируются, если статические ключи, принадлежащие конечным точкам, скомпрометированы. То есть если кто-то запишет содержимое вашего зашифрованного сеанса, а затем получит закрытый ключ любой из сторон, это зашифрованное содержимое сеанса останется защищённым от расшифрования, если ваш механизм обмена ключами обладал совершенной прямой секретностью.

A.5.3. Best Effort Encryption
A.5.3. Шифрование при возможности
With best effort encryption, SRTP is used with endpoints that support SRTP, otherwise RTP is used.
При шифровании по мере возможностей SRTP используется с конечными точками, поддерживающими SRTP, иначе используется RTP.
SIP needs a backwards-compatible best effort encryption in order for SRTP to work successfully with SIP retargeting and forking when there is a mix of forked or retargeted devices that support SRTP and don't support SRTP.
SIP нуждается в обратно совместимом шифровании по мере возможностей, чтобы SRTP успешно работал с ретаргетингом и разветвлением SIP, когда среди разветвлённых или ретаргетированных устройств есть поддерживающие SRTP и не поддерживающие SRTP.
Consider the case of Bob, with a phone that only does RTP and a voice mail system that supports SRTP and RTP. If Alice calls Bob with an SRTP offer, Bob's RTP-only phone will reject the media stream (with an empty "m=" line) because Bob's phone doesn't understand SRTP (RTP/SAVP). Alice's phone will see this rejected media stream and may terminate the entire call (BYE) and re-initiate the call as RTP-only, or Alice's phone may decide to continue with call setup with the SRTP-capable leg (the voice mail system). If Alice's phone decided to re-initiate the call as RTP- only, and Bob doesn't answer his phone, Alice will then leave voice mail using only RTP, rather than SRTP as expected.
Рассмотрим случай с Бобом, у которого есть телефон, работающий только с RTP, и система голосовой почты, поддерживающая SRTP и RTP. Если Алиса звонит Бобу с предложением SRTP, телефон Боба, поддерживающий только RTP, отклонит медиапоток (пустой строкой «m=»), потому что телефон Боба не понимает SRTP (RTP/SAVP). Телефон Алисы увидит этот отклонённый медиапоток и может завершить весь вызов (BYE) и повторно инициировать вызов только с RTP, либо телефон Алисы может решить продолжить установление вызова с плечом, поддерживающим SRTP (системой голосовой почты). Если телефон Алисы решит повторно инициировать вызов только с RTP, а Боб не ответит на свой телефон, Алиса оставит сообщение голосовой почты, используя только RTP, а не SRTP, как ожидалось.
Currently, several techniques are commonly considered as candidates to provide opportunistic encryption:

multipart/alternative [MULTIPART] describes how to form a multipart/alternative body part in SIP. The significant issues with this technique are (1) that multipart MIME is incompatible with existing SIP proxies, firewalls, Session Border Controllers, and endpoints and (2) when forking, the Heterogeneous Error Response Forking Problem (HERFP) [RFC3326] causes problems if such non-multipart-capable endpoints were involved in the forking.
multipart/alternative [MULTIPART] описывает, как сформировать тело multipart/alternative в SIP. Существенные проблемы этого метода: (1) multipart MIME несовместим с существующими прокси-серверами SIP, межсетевыми экранами, пограничными контроллерами сеансов и конечными точками, и (2) при разветвлении проблема разветвления неоднородных ответов об ошибках (HERFP) [RFC3326] создаёт проблемы, если такие конечные точки, не поддерживающие multipart, участвовали в разветвлении.
session attribute With this technique, the endpoints signal their desire to do SRTP by signaling RTP (RTP/AVP), and using an attribute ("a=") in the SDP. This technique is entirely backwards compatible with non-SRT-aware endpoints, but doesn't use the RTP/SAVP protocol registered by SRTP [RFC3711].
атрибут сеанса При этом методе конечные точки сигнализируют о желании использовать SRTP, сигнализируя RTP (RTP/AVP) и используя атрибут («a=») в SDP. Этот метод полностью обратно совместим с конечными точками, не знающими об SRTP, но не использует протокол RTP/SAVP, зарегистрированный для SRTP [RFC3711].
SDP Capability Negotiation SDP Capability Negotiation [SDP-CAP] provides a backwards- compatible mechanism to allow offering both SRTP and RTP in a single offer. This is the preferred technique.

Probing With this technique, the endpoints first establish an RTP session using RTP (RTP/AVP). The endpoints send probe messages, over the media path, to determine if the remote endpoint supports their keying technique. A disadvantage of probing is an active attacker can interfere with probes, and until probing completes (and SRTP is established) the media is in the clear.
Зондирование При этом методе конечные точки сначала устанавливают сеанс RTP с использованием RTP (RTP/AVP). Конечные точки отправляют зондирующие сообщения по медийному пути, чтобы определить, поддерживает ли удалённая конечная точка их метод формирования ключей. Недостаток зондирования в том, что активный атакующий может вмешиваться в зондирование, а до завершения зондирования (и установления SRTP) медиаданные передаются в открытом виде.
The preferred technique, SDP Capability Negotiation [SDP-CAP], can be used with all key exchange mechanisms. What remains unique is ZRTP, which can also accomplish its best effort encryption by probing (sending ZRTP messages over the media path) or by session attribute (see "a=zrtp-hash" in [ZRTP]). Current implementations of ZRTP use probing.
Предпочтительный метод, согласование возможностей SDP [SDP-CAP], можно использовать со всеми механизмами обмена ключами. Уникальным остаётся ZRTP, который также может обеспечить шифрование по мере возможностей с помощью зондирования (отправки сообщений ZRTP по медийному пути) или с помощью атрибута сеанса (см. «a=zrtp-hash» в [ZRTP]). Текущие реализации ZRTP используют зондирование.
A.5.4. Upgrading Algorithms
A.5.4. Обновление алгоритмов
It is necessary to allow upgrading SRTP encryption and hash algorithms, as well as upgrading the cryptographic functions used for the key exchange mechanism. With SIP's offer/answer model, this can be computationally expensive because the offer needs to contain all combinations of the key exchange mechanisms (all MIKEY modes, SDP Security Descriptions), all SRTP cryptographic suites (AES-128, AES-256) and all SRTP cryptographic hash functions (SHA-1, SHA-256) that the offerer supports. In order to do this, the offerer has to expend CPU resources to build an offer containing all of this information that becomes computationally prohibitive.
Необходимо допускать обновление алгоритмов шифрования и хеширования SRTP, а также обновление криптографических функций, используемых механизмом обмена ключами. При модели предложения/ответа SIP это может быть вычислительно дорого, поскольку предложение должно содержать все комбинации механизмов обмена ключами (все режимы MIKEY, SDP Security Descriptions), всех криптографических наборов SRTP (AES-128, AES-256) и всех криптографических хеш-функций SRTP (SHA-1, SHA-256), которые поддерживает инициатор. Чтобы сделать это, инициатор должен расходовать ресурсы ЦП на построение предложения, содержащего всю эту информацию, что становится вычислительно недопустимым.

B.1. Shared Key Conferencing
B.1. Конференции с общим ключом
The consensus on the RTPSEC mailing list was to concentrate on unicast, point-to-point sessions. Thus, there are no requirements related to shared key conferencing. This section is retained for informational purposes.
Консенсус в списке рассылки RTPSEC состоял в том, чтобы сосредоточиться на одноадресных сеансах «точка-точка». Таким образом, требований, связанных с конференциями с общим ключом, нет. Этот раздел сохранён для информационных целей.
For efficient scaling, large audio and video conference bridges operate most efficiently by encrypting the current speaker once and distributing that stream to the conference attendees. Typically, inactive participants receive the same streams -- they hear (or see) the active speaker(s), and the active speakers receive distinct streams that don't include themselves. In order to maintain the confidentiality of such conferences where listeners share a common key, all listeners must rekeyed when a listener joins or leaves a conference. Использование нескольких входящих сеансов (сценарий a) не расточает вычислительные ресурсы, хотя и потребляет дополнительный криптографический контекст на микшере для каждого участника, и имеет преимущество аутентификации источника данных.
To support a single outbound session (scenario d), the mixer has to dictate its encryption key to the participants. Some keying mechanisms allow the transmitter to determine its own key, and others allow the offerer to determine the key for the offerer and answerer. Depending on how the call is established, the offerer might be a participant (such as a participant dialing into a conference bridge) or the offerer might be the mixer (such as a conference bridge calling a participant). The use of offerless INVITEs may help some keying mechanisms reverse the role of offerer/answerer. A difficulty, however, is knowing a priori if the role should be reversed for a particular call. The significant advantage of a single outbound session is the number of SRTP encryption operations remains constant even as the number of participants increases. However, a disadvantage is that data origin authentication is lost, allowing any participant to spoof the sender (because all participants know the sender's SRTP key). Authors' Addresses
Чтобы поддерживать единый исходящий сеанс (сценарий d), микшер должен продиктовать свой ключ шифрования участникам. Некоторые механизмы формирования ключей позволяют передатчику определять собственный ключ, а другие позволяют инициатору определять ключ для инициатора и отвечающей стороны. В зависимости от того, как устанавливается вызов, инициатором может быть участник (например, участник, звонящий в конференцмост), либо инициатором может быть микшер (например, конференцмост, звонящий участнику). Использование INVITE без предложения может помочь некоторым механизмам формирования ключей поменять роли инициатора и отвечающей стороны. Однако трудность состоит в том, чтобы заранее знать, следует ли менять роли для конкретного вызова. Значительное преимущество единого исходящего сеанса в том, что число операций шифрования SRTP остаётся постоянным даже при увеличении числа участников. Однако недостаток в том, что теряется аутентификация источника данных, позволяя любому участнику подделать отправителя (поскольку все участники знают ключ SRTP отправителя). Адреса авторов RFC
