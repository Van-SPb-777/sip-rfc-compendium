Abstract
Аннотация
This document describes MIME types for application/ISUP and application/QSIG objects for use in SIP applications, according to the rules defined in RFC 2048. These types can be used to identify ISUP and QSIG objects within a SIP message such as INVITE or INFO, as might be implemented when using SIP in an environment where part of the call involves interworking to the PSTN.
Настоящий документ описывает типы MIME для объектов application/ISUP и application/QSIG для использования в приложениях SIP согласно правилам, определённым в RFC 2048. Эти типы могут использоваться для идентификации объектов ISUP и QSIG в сообщении SIP, таком как INVITE или INFO, как это могло бы быть реализовано при использовании SIP в среде, где часть вызова включает взаимодействие с ТфОП.
1. Introduction
1. Введение
ISUP (ISDN User part) defined in the ITU-T recommendations Q.761-4 is a signaling protocol used between telephony switches. There are configurations in which ISUP-encoded signaling information needs to be transported between SIP entities as part of the payload of SIP messages, where the preservation of ISUP data is necessary for the proper operation of PSTN features. QSIG is the analogous signaling protocol used between private branch exchanges to support calls within private telephony networks. There is a similar need to transport QSIG-encoded signaling information between SIP entities in some environments.
Протокол ISUP (ISDN User Part), определённый в рекомендациях ITU-T Q.761–4, — это протокол сигнализации, используемый между телефонными станциями. Существуют конфигурации, в которых сигнальная информация, закодированная в ISUP, должна передаваться между объектами SIP как часть полезной нагрузки сообщений SIP, где сохранение данных ISUP необходимо. QSIG — это аналогичный протокол сигнализации, используемый между учрежденческими АТС для поддержки вызовов внутри частных телефонных сетей. Существует аналогичная потребность в передаче сигнальной информации, закодированной в QSIG, между объектами SIP в некоторых средах.
This document is specific to this usage and would not apply to the transportation of ISUP or QSIG messages in other applications. These media types are intended for ISUP or QSIG application information that is used within the context of a SIP session, and not as general purpose transport of SCN signaling.
Настоящий документ специфичен для этого использования и не применяется к передаче сообщений ISUP или QSIG в других приложениях. Эти типы носителя предназначены для информации приложений ISUP или QSIG, используемой в контексте сессии SIP, а не для передачи сигнализации SCN общего назначения.
The definition of media types for ISUP and QSIG application information does not address fully how the non-SIP and SIP entities exchanging messages determine or negotiate compatibility. It is assumed that this is addressed by alternative means such as the configuration of the interworking functions.
Определение типов носителя для информации приложений ISUP и QSIG не рассматривает полностью, как обменивающиеся сообщениями объекты SIP и не-SIP определяют или согласуют совместимость. Предполагается, что это решается иными средствами, например конфигурацией функций взаимодействия.
This is intended to be an IETF approved MIME type, and to be defined through an RFC. NOTE: usage of Q.SIG within SIP is neither endorsed nor recommended as a result of this MIME registration.
Предполагается, что это тип MIME, одобренный IETF, и что он определяется посредством RFC. ПРИМЕЧАНИЕ. Использование Q.SIG внутри SIP не одобряется и не рекомендуется в результате этой регистрации MIME.
3. Proposed new media types
3. Предлагаемые новые типы носителя
ISUP and QSIG messages are composed of arbitrary binary data that is transparent to SIP processing. The best way to encode these is to use binary encoding. This is in conformance with the restrictions imposed on the use of binary data for MIME (RFC 2045 [3]). It should be noted that the rules mentioned in the RFC 2045 apply to Internet mail messages and not to SIP messages. Binary has been preferred over Base64 encoding because the latter would only result in adding bulk to the encoded messages and possibly be more costly in terms of processing power.
Сообщения ISUP и QSIG состоят из произвольных двоичных данных, прозрачных для обработки SIP. Наилучшим способом их кодирования является двоичное кодирование. Это соответствует ограничениям, накладываемым на использование двоичных данных в MIME (RFC 2045 [3]). Следует отметить, что правила, упомянутые в RFC 2045, применяются к сообщениям интернет-почты, а не к сообщениям SIP. Двоичное кодирование предпочтено кодированию Base64, поскольку последнее лишь увеличило бы объём закодированных сообщений и, возможно, было бы более затратным с точки зрения вычислительных ресурсов.
3.1. ISUP Media Type
3.1. Тип носителя ISUP
This media type is defined by the following information:
Этот тип носителя определяется следующей информацией:
Media type name: application Media subtype name: ISUP Required parameters: version Optional parameters: base Encoding scheme: binary Security considerations: See section 5.
Имя типа носителя: application. Имя подтипа носителя: ISUP. Обязательные параметры: version. Необязательные параметры: base. Схема кодирования: binary. Вопросы безопасности: см. раздел 5.
The ISUP message is encapsulated beginning with the Message Type Code (i.e., omitting Routing Label and Circuit ID Code). The use of the 'version' parameter allows network administrators to identify specific versions of ISUP that will be exchanged on a bilateral basis. This enables a particular client such as a SoftSwitch/Media Gateway Controller to recognize and parse the message correctly, or (possibly) to reject the message if the specified ISUP version is not supported. This specification places no constraints on the values that may be used in 'version'; these are left to the discretion of the network administrator.
Сообщение ISUP инкапсулируется, начиная с кода типа сообщения (то есть без метки маршрутизации и кода идентификатора канала). Использование параметра «version» позволяет сетевым администраторам идентифицировать конкретные версии ISUP, которыми будут обмениваться на двусторонней основе. Это позволяет конкретному клиенту, например SoftSwitch или контроллеру медиашлюза, правильно распознать и разобрать сообщение либо (возможно) отклонить сообщение, если указанная версия ISUP не поддерживается. Настоящая спецификация не накладывает ограничений на значения, которые могут использоваться в «version»; они оставлены на усмотрение сетевого администратора.
This 'version' could, for example, be used to identify a network- specific implementation of ISUP, e.g., X-NetxProprietaryISUPv3, or to identify a well-known standard version of ISUP, e.g., itu-t or ansi.
Эта «version» могла бы, например, использоваться для идентификации специфичной для сети реализации ISUP, например X-NetxProprietaryISUPv3, либо для идентификации широко известной стандартной версии ISUP, например itu-t или ansi.
A 'base' parameter can optionally be included in some cases (e.g., if the receiver may not recognize the 'version' string) to specify that the encapsulated ISUP can also be processed using the identified 'base' specification. Table 1 provides a list of 'base' values supported by the 'application/ISUP' media type, including whether or not the forward compatibility mechanism defined in ITU-T 1992 ISUP is supported.
В некоторых случаях может быть необязательно включён параметр «base» (например, если получатель может не распознать строку «version»), чтобы указать, что инкапсулированный ISUP может также обрабатываться согласно указанной спецификации «base». The Content-Disposition header [5] may be included to describe how the encapsulated ISUP is to be processed, and in particular what the handling should be if the received Content-Type is not recognized. The default disposition-type for an ISUP message body is "signal". This type indicates that the body part contains signaling information associated with the session, but does not describe the session.
Заголовок Content-Disposition [5] может быть включён, чтобы описать, как следует обрабатывать инкапсулированный ISUP, и в частности каким должно быть поведение, если полученный Content-Type не распознан. Тип диспозиции по умолчанию для тела сообщения ISUP — «signal». Этот тип указывает, что часть тела содержит сигнальную информацию, связанную с сессией, но не описывает саму сессию.

5. Security considerations
5. Вопросы безопасности
Information contained in ISUP and QSIG bodies may include sensitive customer information, potentially requiring use of encryption.
Информация, содержащаяся в телах ISUP и QSIG, может включать конфиденциальную информацию о клиентах, что потенциально требует использования шифрования.
Security mechanisms are provided in RFC 2543 (SIP - Session Initiation Protocol) and should be used as appropriate for both the SIP message and the encapsulated ISUP or QSIG body.
Механизмы безопасности предусмотрены в RFC 2543 (SIP — протокол инициирования сессий) и должны использоваться надлежащим образом как для сообщения SIP, так и для инкапсулированного тела ISUP или QSIG.
6. IANA considerations
6. Вопросы IANA
This document registers the "application/ISUP" and "application/QSIG" MIME media types.
Настоящий документ регистрирует типы носителя MIME «application/ISUP» и «application/QSIG».
Registrations for the 'version' symbols used within the ISUP and QSIG MIME types must specify a definitive specification reference, identifying a particular issue of the specification, to which the new symbol shall refer. Identifying a definite specification reference requires a review process; the authors recommend that a subject matter expert be designated as described in RFC 2434 [6] under Expert Review.
Регистрации символов «version», используемых в типах MIME ISUP и QSIG, должны указывать определённую ссылку на спецификацию, идентифицирующую конкретный выпуск спецификации, к которому будет относиться новый символ. Идентификация определённой ссылки на спецификацию требует процесса рассмотрения; авторы рекомендуют назначить эксперта по предметной области, как описано в RFC 2434 [6] в категории Expert Review.
Note that where a specification is fully peer-to-peer backwards compatible with a previous issue (i.e., the compatibility mechanism is supported by both), then there is no need for separate symbols to be registered. The symbol for the original specification should be used to identify backwards-compatible upgrades of that specification as well.
Обратите внимание, что если спецификация полностью обратно совместима по схеме «равный с равным» с предыдущим выпуском (то есть механизм совместимости поддерживается обеими сторонами), то нет необходимости регистрировать отдельные символы. Символ исходной спецификации следует использовать для идентификации обратно совместимых обновлений этой спецификации.
Symbols beginning with the characters 'X-' are reserved for non- standard usage (e.g., cases in which a token other than a string representing an issue of an ISUP specification is appropriate for characterizing ISUP within an administrative domain). Such non- standard version can only be transmitted between administrative domains in accordance with a bilateral agreement. These symbols should be administered under the Private Use policy described in RFC 2434. This document registers a new disposition-type for the Content- Disposition header, 'signal', to be used when a MIME body contains supplemental signaling information (ISUP and QSIG as MIME bodies being examples of this).
Символы, начинающиеся с символов «X-», зарезервированы для нестандартного использования (например, случаев, когда лексема, отличная от строки, представляющей выпуск спецификации ISUP, уместна для характеристики ISUP в пределах административного домена). Такая нестандартная версия может передаваться между административными доменами только в соответствии с двусторонним соглашением. Эти символы должны администрироваться в соответствии с политикой Private Use, описанной в RFC 2434. Настоящий документ регистрирует новый тип диспозиции для заголовка Content-Disposition — «signal», который должен использоваться, когда тело MIME содержит дополнительную сигнальную информацию (тела MIME ISUP и QSIG — примеры этого).
This document also defines a Content Disposition parameter, "handling". The handling parameter, handling-parm, describes how the UAS should react if it receives a message body whose content type or disposition type it does not understand. If the parameter has the value "optional", the UAS MUST ignore the message body; if it has the value "required", the UAS MUST return 415 (Unsupported Media Type). If the handling parameter is missing, the value "required" is to be assumed.
Настоящий документ также определяет параметр Content Disposition «handling». Параметр handling (handling-parm) описывает, как сервер UAS должен реагировать, если он получает тело сообщения, тип содержимого или тип диспозиции которого он не понимает. Если параметр имеет значение «optional», сервер UAS ДОЛЖЕН игнорировать тело сообщения; если он имеет значение «required», сервер UAS ДОЛЖЕН вернуть 415 (Unsupported Media Type). Если параметр handling отсутствует, следует предполагать значение «required».
