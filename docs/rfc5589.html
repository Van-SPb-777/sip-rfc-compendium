Abstract
Аннотация
This document describes providing Call Transfer capabilities in the Session Initiation Protocol (SIP). SIP extensions such as REFER and Replaces are used to provide a number of transfer services including blind transfer, consultative transfer, and attended transfer. This work is part of the SIP multiparty call control framework.
В настоящем документе описано предоставление возможностей перевода вызова в протоколе инициирования сессий (SIP). Расширения SIP, такие как REFER и Replaces, используются для предоставления ряда служб перевода, включая слепой перевод, консультативный перевод и перевод с консультацией. Эта работа является частью инфраструктуры управления многосторонними вызовами SIP.

5. Using REFER to Achieve Call Transfer
5. Использование REFER для выполнения перевода вызова
A REFER [RFC3515] can be issued by the Transferor to cause the Transferee to issue an INVITE to the Transfer Target. Note that a successful REFER transaction does not terminate the session between the Transferor and the Transferee. If those parties wish to terminate their session, they must do so with a subsequent BYE request. The media negotiated between the transferee and the Transfer Target is not affected by the media that had been negotiated between the Transferor and the Transferee. In particular, the INVITE issued by the Transferee will have the same Session Description Protocol (SDP) body it would have if the Transferee had initiated that INVITE on its own. Further, the disposition of the media streams between the Transferor and the Transferee is not altered by the REFER method.
Инициатор передачи может выдать REFER [RFC3515], чтобы побудить передаваемого участника выдать INVITE целевому участнику. Обратите внимание: успешная транзакция REFER не завершает сессию между инициатором передачи и передаваемым участником. Если эти стороны желают завершить свою сессию, они должны сделать это последующим запросом BYE. Медиапотоки, согласованные между передаваемым участником и целевым участником, не зависят от медиапотоков, согласованных между инициатором передачи и передаваемым участником. В частности, INVITE, выданный передаваемым участником, будет иметь то же тело протокола описания сессий (SDP), какое он имел бы, если бы передаваемый участник инициировал этот INVITE самостоятельно. Кроме того, распределение медиапотоков между инициатором передачи и передаваемым участником не изменяется методом REFER.
Agents may alter a session's media through additional signaling. For example, they may make use of the SIP hold re-INVITE [RFC3261] or conferencing extensions described in the conferencing framework [RFC4353].
Агенты могут изменять медиапотоки сессии с помощью дополнительной сигнализации. Например, они могут использовать re-INVITE для удержания в SIP [RFC3261] или расширения конференцсвязи, описанные в инфраструктуре конференцсвязи [RFC4353].
To perform the transfer, the Transferor and Transferee could reuse an existing dialog established by an INVITE to send the REFER. This would result in a single dialog shared by two uses -- an invite usage and a subscription usage. The call flows for this are shown in detail in Section 6.2. However, the approach described in this document is to avoid dialog reuse. The issues and difficulties associated with dialog reuse are described in [RFC5057].
Для выполнения перевода инициатор передачи и передаваемый участник могли бы повторно использовать существующий диалог, установленный посредством INVITE, для отправки REFER. Это привело бы к тому, что один диалог использовался бы двумя применениями — применением invite и применением подписки. Потоки вызовов для этого подробно показаны в разделе 6.2. Однако подход, описанный в настоящем документе, состоит в том, чтобы избегать повторного использования диалога. Вопросы и трудности, связанные с повторным использованием диалога, описаны в [RFC5057].

6. Basic Transfer
6. Базовый перевод вызова
Basic Transfer consists of the Transferor providing the Transfer Target's contact to the Transferee. The Transferee attempts to establish a session using that contact and reports the results of that attempt to the Transferor. The signaling relationship between the Transferor and Transferee is not terminated, so the call is recoverable if the Transfer Target cannot be reached. Note that the Transfer Target's contact information has been exposed to the Transferee. The provided contact can be used to make new calls in the future. The participants in a basic transfer SHOULD indicate support for the REFER and NOTIFY methods in Allow header fields in INVITE, 200 OK to INVITE, and OPTIONS messages. Participants SHOULD also indicate support for Target-Dialog in the Supported header field.
Базовый перевод вызова состоит в том, что инициатор передачи предоставляет передаваемому участнику контакт целевого участника. Передаваемый участник пытается установить сессию с использованием этого контакта и сообщает инициатору передачи результаты этой попытки. Сигнальное отношение между инициатором передачи и передаваемым участником не прекращается, поэтому вызов можно восстановить, если целевой участник недоступен. Обратите внимание: контактные данные целевого участника стали известны передаваемому участнику. Предоставленный контакт можно использовать для новых вызовов в дальнейшем. Участникам базового перевода СЛЕДУЕТ указывать поддержку методов REFER и NOTIFY в полях заголовка Allow в сообщениях INVITE, 200 OK на INVITE и OPTIONS. Участникам также СЛЕДУЕТ указывать поддержку Target-Dialog в поле заголовка Supported.

Если агент инициатора передачи не желает участвовать в оставшейся части процесса REFER и не намерен помогать восстановлению после неудачного перевода, он может выдать BYE передаваемому участнику сразу после завершения транзакции REFER. Такой поток иногда называют «перевод без участия» (unattended transfer) или «слепой перевод».

As a result, the Transferor sends the REFER outside the INVITE dialog. The Transferee is able to match this REFER to the existing dialog using the Target-Dialog header field in the refer which references the existing dialog.

Transfer with consultation hold involves a session between the Transferor and the Transfer Target before the transfer actually takes place. This is implemented with SIP Hold and Transfer as described above.
Перевод с консультационным удержанием включает сессию между инициатором передачи и целевым участником до того, как перевод фактически состоится. Это реализуется с помощью удержания и перевода в SIP, как описано выше.
A nice feature is for the Transferor to let the target know that the session relates to an intended transfer. 7.2. Protecting Transfer Target
7.2. Защита целевого участника
The Transferor places the Transferee on hold, establishes a call with the Transfer Target and then reverses their roles, transferring the original Transfer Target to the original Transferee. This has the advantage of hiding information about the original Transfer Target from the original Transferee. On the other hand, the Transferee's experience is different than in current systems. The Transferee is effectively "called back" by the Transfer Target.
Инициатор передачи ставит передаваемого участника на удержание, устанавливает вызов с целевым участником, а затем меняет их роли, переводя исходного целевого участника к исходному передаваемому участнику. Преимущество этого подхода в том, что сведения об исходном целевом участнике скрываются от исходного передаваемого участника. С другой стороны, восприятие передаваемого участника отличается от привычного в современных системах. Передаваемому участнику фактически поступает вызов от целевого участника.
One of the problems with this simplest implementation of a target protecting transfer is that the Transferee is receiving a new call from the Transfer Target. Unless the Transferee's agent has a reliable way to associate this new call with the call it already has with the Transferor, it will have to alert the new call on another appearance. If this, or some other call-waiting-like UI were not available, the Transferee might be stuck returning a Busy-Here to the Transfer Target, effectively preventing the transfer. There are many ways that correlation could be provided. The dialog parameters could be provided directly as header parameters in the Refer-To URI, for example. The Replaces mechanism [RFC3891] uses this approach and solves this problem nicely.
Одна из проблем этой простейшей реализации перевода с защитой целевого участника состоит в том, что передаваемый участник получает новый вызов от целевого участника. Если у агента передаваемого участника нет надёжного способа связать этот новый вызов с вызовом, уже существующим у него с инициатором передачи, ему придётся оповещать о новом вызове на другом появлении. Если бы этого или какого-либо другого интерфейса, подобного ожиданию вызова, не было, передаваемый участник мог бы оказаться вынужден вернуть целевому участнику ответ Busy-Here, фактически предотвратив перевод. Существует много способов обеспечить такую взаимосвязь. Например, параметры диалога можно передать непосредственно как параметры заголовка в URI Refer-To. Механизм Replaces [RFC3891] использует этот подход и удачно решает эту проблему.
For the flow below, dialog1 means dialog identifier 1, and consists of the parameters of the Replaces header for dialog 1. In [RFC3891], this is the Call-ID, To-tag, and From-tag.
В приведённом ниже потоке dialog1 означает идентификатор диалога 1 и состоит из параметров поля заголовка Replaces для диалога 1. В [RFC3891] это Call-ID, To-tag и From-tag.
Note that the Transferee's agent emits a BYE to the Transferor's agent as an immediate consequence of processing the Replaces header.
Обратите внимание: агент передаваемого участника выдаёт BYE агенту инициатора передачи непосредственно как следствие обработки поля заголовка Replaces.
The Transferor knows that both the Transferee and the Transfer Target support the Replaces header from the Supported: replaces header contained in the 200 OK responses from both.
Инициатор передачи знает, что и передаваемый участник, и целевой участник поддерживают поле заголовка Replaces, по полю заголовка Supported: replaces, содержащемуся в ответах 200 OK от обоих.
In this scenario, the Transferee utilizes a GRUU as a Contact URI for reasons discussed in Section 6.3.
В этом сценарии передаваемый участник использует GRUU в качестве Contact URI по причинам, обсуждаемым в разделе 6.3.
Note that the conventions used in the SIP Torture Test Messages [RFC4475] document are reused, specifically the <allOneLine> tag.
Обратите внимание: используются те же соглашения, что и в документе «SIP Torture Test Messages» [RFC4475], в частности тег <allOneLine>.

7.3. Attended Transfer
7.3. Перевод с консультацией
The Transferor places the Transferee on hold, establishes a call with the Transfer Target to alert them to the impending transfer, places the target on hold, then proceeds with transfer using an escaped Replaces header field in the Refer-To header. This is another common service expected by current PBX and Centrex users.
Инициатор передачи ставит передаваемого участника на удержание, устанавливает вызов с целевым участником, чтобы предупредить его о предстоящем переводе, ставит целевого участника на удержание, а затем выполняет перевод, используя экранированное поле заголовка Replaces в заголовке Refer-To. Это ещё одна распространённая служба, ожидаемая современными пользователями PBX и Centrex.
The Contact URI of the Transfer Target SHOULD be used by the Transferor as the Refer-To URI, unless the URI is suspected or known to not be routable outside the dialog. Otherwise, the Address of Record (AOR) of the Transfer Target SHOULD be used. That is, the same URI that the Transferor used to establish the session with the Transfer Target should be used. In case the triggered INVITE is routed to a different User Agent than the Transfer Target, the Require: replaces header field SHOULD be used in the triggered INVITE. (This is to prevent an incorrect User Agent that does not support Replaces from ignoring the Replaces and answering the INVITE without a dialog match.)
Инициатору передачи СЛЕДУЕТ использовать Contact URI целевого участника в качестве URI Refer-To, если только URI не подозревается или не известно, что он не маршрутизируется вне диалога. В противном случае СЛЕДУЕТ использовать адрес записи (AOR) целевого участника. То есть следует использовать тот же URI, который инициатор передачи использовал для установления сессии с целевым участником. 7.6. Semi-Attended Transfer
7.6. Полуконсультативный перевод
In any of the consultation hold flows above, the Transferor may decide to terminate its attempt to contact the Transfer Target before that session is established. Most frequently, that will be the end of the scenario, but in some circumstances, the Transferor may wish to proceed with the transfer action. For example, the Transferor may wish to complete the transfer knowing that the Transferee will end up eventually talking to the Transfer Target's voicemail service. Some PBX systems support this feature, sometimes called "semi-attended transfer", that is effectively a hybrid between a fully attended transfer and an unattended transfer. A call flow is shown in Figure 11. In this flow, the Transferor's User Agent continues the transfer as an attended transfer even after the Transferor hangs up. Note that media must be played to the Transfer Target upon answer -- otherwise, the Target may hang up and the resulting transfer operation will fail.
В любом из описанных выше потоков с консультационным удержанием инициатор передачи может решить прекратить попытку связаться с целевым участником до установления этой сессии. Чаще всего на этом сценарий заканчивается, но в некоторых обстоятельствах инициатор передачи может пожелать продолжить операцию перевода. Например, инициатор передачи может пожелать завершить перевод, зная, что передаваемый участник в итоге будет разговаривать со службой голосовой почты целевого участника. Некоторые системы PBX поддерживают эту возможность, иногда называемую «полуконсультативным переводом» (semi-attended transfer), которая фактически является гибридом полностью консультативного перевода и перевода без участия. Поток вызовов показан на рисунке 11. В этом потоке пользовательский агент инициатора передачи продолжает перевод как перевод с консультацией даже после того, как инициатор передачи кладёт трубку. Обратите внимание: после ответа целевому участнику должны воспроизводиться медиаданные — иначе целевой участник может положить трубку, и операция перевода завершится неудачей.

Two other possible semi-attended transfer call flows are shown in Figures 12 and 13. However, these call flows are NOT RECOMMENDED due to race conditions. In both of these flows, when the Transferor hangs up, the Transferor attempts to revert to unattended transfer by sending a CANCEL to the target. This can result in two race conditions. One is that the target answers despite the CANCEL and the resulting unattended transfer fails. This race condition can be eliminated by the Transferor waiting to send the REFER until the 487 response from the target is returned. Instead of a 487, a 200 OK may be returned indicating that the target has answered the consultation call. In this case, the call flow in Figure 13 must be followed. In this flow, the Transferor must play some kind of media to the Target to prevent the Target from hanging up, or the transfer will fail. That is, the human at the Transfer Target will hear silence from when they answer (message F1) until the transfer completes (F3 and they are talking to the Transferee unless some media is played (F2)).
На рисунках 12 и 13 показаны два других возможных потока вызовов полуконсультативного перевода. Однако эти потоки НЕ РЕКОМЕНДУЮТСЯ из-за состояний гонки. В обоих потоках, когда инициатор передачи кладёт трубку, он пытается вернуться к переводу без участия, отправляя целевому участнику CANCEL. Это может привести к двум состояниям гонки. Первое состоит в том, что целевой участник отвечает, несмотря на CANCEL, и перевод без участия завершается неудачей. Это состояние гонки можно устранить, если инициатор передачи подождёт с отправкой REFER до получения ответа 487 от целевого участника. Вместо 487 может быть возвращён ответ 200 OK, указывающий, что целевой участник ответил на консультационный вызов. В этом случае необходимо следовать потоку вызовов на рисунке 13. В этом потоке инициатор передачи должен воспроизводить целевой стороне какие-либо медиаданные, чтобы целевой участник не положил трубку, иначе перевод завершится неудачей. То есть человек у целевого участника будет слышать тишину с момента ответа (сообщение F1) до завершения перевода (F3, после чего он разговаривает с передаваемым участником, если не воспроизведены медиаданные (F2)).
The second race condition occurs in Figure 12 if the Transfer Target goes "off hook" after the CANCEL is received and the 487 returned. This may result in a 486 Busy Here response to the unattended transfer.
Второе состояние гонки возникает на рисунке 12, если целевой участник снимает трубку после получения CANCEL и возврата 487. Это может привести к ответу 486 Busy Here на перевод без участия.
The recommended call flow of Figure 11 does not utilize a CANCEL and does not suffer from these race conditions.
Рекомендуемый поток вызовов на рисунке 11 не использует CANCEL и не подвержен этим состояниям гонки.

8. Transfer with Referred-By
8. Перевод вызова с Referred-By
In the previous examples, the Transfer Target does not have definitive information about what party initiated the transfer, or, in some cases, even that transfer is taking place. The Referred-By mechanism [RFC3892] provides a way for the Transferor to provide the Transferee with a way to let the Transfer Target know what party initiated the transfer.
В предыдущих примерах целевой участник не имеет достоверных сведений о том, какая сторона инициировала перевод, а в некоторых случаях — даже о том, что перевод выполняется. Механизм Referred-By [RFC3892] позволяет инициатору передачи дать передаваемому участнику способ сообщить целевому участнику, какая сторона инициировала перевод.
The simplest and least secure approach just involves the inclusion of the Referred-By header field in the REFER, which is then copied into the triggered INVITE. However, a more secure mechanism involving the Referred-By security token, which is generated and signed by the Transferor and passed in a message body to the Transferee then to the Transfer Target.
Простейший и наименее безопасный подход заключается просто во включении поля заголовка Referred-By в REFER, которое затем копируется в инициированный INVITE. Однако существует более безопасный механизм с использованием токена безопасности Referred-By, который формируется и подписывается инициатором передачи и передаётся в теле сообщения передаваемому участнику, а затем целевому участнику.

9. Transfer as an Ad Hoc Conference
9. Перевод вызова как конференция ad hoc
In this flow, shown in Figure 17, Bob does an attended transfer of Alice to Carol. In order to keep both Alice and Carol fully informed of the nature and state of the transfer operation, Bob acts as a focus [RFC4579] and hosts an ad hoc conference involving Alice, Bob, and Carol. Alice and Carol subscribe to the conference package [RFC4575] of Bob's focus, which allows them to know the exact status of the operation. After the transfer operation is complete, Bob deletes the conference. This call flow meets requirement 6 of Section 4. NOTIFY messages related to the refer package are indicated as NOTIFY (refer), while NOTIFYs related to the Conference Info package are indicated as NOTIFY (Conf-Info).
В этом потоке, показанном на рисунке 17, Bob выполняет перевод с консультацией: переводит Alice к Carol. Чтобы Alice и Carol были полностью осведомлены о характере и состоянии операции перевода, Bob выступает в роли фокуса [RFC4579] и организует конференцию ad hoc с участием Alice, Bob и Carol. Alice и Carol подписываются на пакет конференции [RFC4575] фокуса Bob, что позволяет им знать точное состояние операции. После завершения операции перевода Bob удаляет конференцию. Этот поток вызовов удовлетворяет требованию 6 из раздела 4. 11. Gateway Transfer Issues
11. Проблемы перевода через шлюзы
A gateway in SIP acts as a User Agent. As a result, the entire preceding discussion and call flows apply equally well to gateways as native SIP endpoints. However, there are some gateway-specific issues that are documented in this section. While this discussion focuses on the common cases involving Public Switched Telephone Network (PSTN) gateways, similar situations exist for other gateways, such as H.323/SIP gateways.
Шлюз в SIP действует как пользовательский агент. Поэтому всё предшествующее обсуждение и потоки вызовов в равной мере применимы к шлюзам, как и к собственным конечным точкам SIP. Однако существуют некоторые специфичные для шлюзов вопросы, которые описаны в этом разделе. Хотя обсуждение сосредоточено на распространённых случаях с шлюзами телефонной сети общего пользования (PSTN), аналогичные ситуации возможны и для других шлюзов, например шлюзов H.323/SIP.
11.1. Coerce Gateway Hairpins to the Same Gateway
11.1. Принудительное направление hairpin-вызовов через один шлюз
To illustrate how a hairpin situation can occur in transfer, consider this example. The original call dialog is setup with the Transferee residing on the PSTN side of a SIP gateway. The Transferor is a SIP phone purely in the IP space. The Transfer Target is on the PSTN side of a SIP gateway as well. After completing the transfer, (regardless of consultative or blind) the Transferee is in a call with the Transfer Target (both on the PSTN side of a gateway). It is often desirable to remove the gateway(s) out of the loop. This is likely to only be possible if both legs of the target call are on the same gateway. With both legs on the same gateway, it may be able to invoke the analogous transfer on the PSTN side. Then the target call would not involve the gateway.
Чтобы проиллюстрировать, как при переводе может возникнуть ситуация hairpin, рассмотрим этот пример. Исходный диалог вызова устанавливается, когда передаваемый участник находится на стороне PSTN шлюза SIP. Инициатор передачи — это SIP-телефон, находящийся целиком в IP-пространстве. Целевой участник также находится на стороне PSTN шлюза SIP. После завершения перевода (независимо от того, консультативный он или слепой) передаваемый участник разговаривает с целевым участником (оба на стороне PSTN шлюза). Часто желательно вывести шлюзы из цепочки. Это, вероятно, возможно только в том случае, если оба плеча целевого вызова проходят через один шлюз. Если оба плеча проходят через один шлюз, можно попытаться выполнить аналогичный перевод на стороне PSTN. Тогда целевой вызов не будет задействовать шлюз.
So the problem is how to give the proxy enough information so that it knows to route the call to the same gateway. With a simple single call that hairpins, the incoming and outgoing leg have the same dialog. The proxy should have enough information to optimize the routing.
Итак, проблема в том, как предоставить прокси достаточно информации, чтобы он знал, что вызов нужно маршрутизировать через тот же шлюз. В простом одиночном вызове с hairpin входящее и исходящее плечи имеют один и тот же диалог. Прокси должен располагать достаточной информацией для оптимизации маршрутизации.
In the consultative transfer scenario, it is desirable to coerce the consultative INVITE out the same gateway as the original call to be transferred. However, there is no way to relate the consultation with the original call. In the consultative case, the target call INVITE includes the Replaces header, which contains dialog information that can be used to relate it to the consultation. However, there is no information that relates the target call to the original.
В сценарии консультативного перевода желательно направить консультационный INVITE через тот же шлюз, что и исходный вызов, подлежащий переводу. Однако нет способа связать консультацию с исходным вызовом. В консультативном случае INVITE целевого вызова включает поле заголовка Replaces, которое содержит информацию о диалоге, позволяющую связать его с консультацией. Однако нет информации, связывающей целевой вызов с исходным.
In the blind transfer scenario, it is desirable to coerce the target call onto the same gateway as the original call. However, the same problem exists in that the target-dialog cannot be related to the original dialog.
В сценарии слепого перевода желательно направить целевой вызов через тот же шлюз, что и исходный вызов. Однако существует та же проблема: target-dialog нельзя связать с исходным диалогом.
In either transfer scenario, it may be desirable to push the transfer operation onto the non-SIP side of the gateway. Presumably, this is not possible unless all of the legs go out the same gateway. If the gateway supports more than one trunk group, it might also be necessary to get all of the legs on the same trunk group in order to perform the transfer on the non-SIP side of the gateway.
В любом из сценариев перевода может оказаться желательным перенести операцию перевода на не-SIP сторону шлюза. Предположительно, это невозможно, если только все плечи не выходят через один шлюз. Если шлюз поддерживает более одной транковой группы, может также потребоваться, чтобы все плечи находились в одной транковой группе, — чтобы выполнить перевод на не-SIP стороне шлюза.
Solutions to these gateway specific issues may involve new extensions to SIP in the future.
Решения этих специфичных для шлюзов вопросов могут в будущем потребовать новых расширений SIP.

12. Security Considerations
12. Вопросы безопасности
The call transfer flows shown in this document are implemented using the REFER and Replaces call control primitives in SIP. As such, the security considerations detailed in the REFER [RFC3515] and Replaces [RFC3891] documents MUST be followed, which are briefly summarized in the following paragraphs. This document addresses the issue of protecting the Address of Record URI of a Transfer Target in Sections 7.1 and 7.2. Any REFER request MUST be appropriately authenticated and authorized using standard SIP mechanisms or else calls may be hijacked. A User Agent may use local policy or human intervention in deciding whether or not to accept a REFER. In generating NOTIFY responses based on the outcome of the triggered request, care should be taken in constructing the message/sipfrag body to ensure that no private information is leaked.
Потоки перевода вызова, показанные в настоящем документе, реализуются с использованием примитивов управления вызовами REFER и Replaces в SIP. Поэтому ДОЛЖНЫ соблюдаться требования безопасности, подробно изложенные в документах REFER [RFC3515] и Replaces [RFC3891], кратко суммированные в следующих абзацах. Настоящий документ рассматривает вопрос защиты URI адреса записи целевого участника в разделах 7.1 и 7.2. Любой запрос REFER ДОЛЖЕН быть надлежащим образом аутентифицирован и авторизован с использованием стандартных механизмов SIP, иначе вызовы могут быть перехвачены. Пользовательский агент может использовать локальную политику или вмешательство человека при решении вопроса о том, принимать ли REFER. При формировании ответов NOTIFY на основе результата инициированного запроса следует проявлять осторожность при построении тела message/sipfrag, чтобы не допустить утечки конфиденциальной информации.
An INVITE containing a Replaces header field SHOULD only be accepted if it has been properly authenticated and authorized using standard SIP mechanisms, and the requestor is authorized to perform dialog replacement. Special care is needed if the replaced dialog utilizes additional media streams compared to the original dialog. In this case, the user MUST authorize the addition of new media streams in a dialog replacement. For example, the same mechanism used to authorize the addition of a media stream in a re-INVITE could be used.
INVITE, содержащий поле заголовка Replaces, СЛЕДУЕТ принимать только в том случае, если он был надлежащим образом аутентифицирован и авторизован с использованием стандартных механизмов SIP и запрашивающая сторона уполномочена выполнять замену диалога. Особую осторожность следует проявлять, если заменяемый диалог использует дополнительные медиапотоки по сравнению с исходным диалогом. В этом случае пользователь ДОЛЖЕН разрешить добавление новых медиапотоков при замене диалога. Например, можно использовать тот же механизм, который применяется для разрешения добавления медиапотока в re-INVITE.
