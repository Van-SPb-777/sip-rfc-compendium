3. Предпосылки
3.1. Models for Using TLS in SIP
3.1. Модели использования TLS в SIP
This section describes briefly the usage of TLS in SIP.
В настоящем разделе кратко описано использование TLS в SIP.
3.1.1. Server-Provided Certificate
3.1.1. Сертификат, предоставляемый сервером
In this model, only the TLS server provides a certificate during the TLS handshake. This is applicable only between a user agent (UA) and a proxy, where the UA is the TLS client and the proxy is the TLS server, and hence the UA uses TLS to authenticate the proxy but the proxy does not use TLS to authenticate the UA. If the proxy needs to authenticate the UA, this can be achieved by SIP HTTP digest authentication. This directionality implies that the TLS connection always needs to be set up by the UA (e.g., during the registration phase). Since SIP allows for requests in both directions (e.g., an incoming call), the UA is expected to keep the TLS connection alive, and that connection is expected to be reused for both incoming and outgoing requests.
В этой модели сертификат при установлении TLS-соединения предоставляет только TLS-сервер. Она применима лишь во взаимодействии пользовательского агента (UA) с прокси, где UA выступает TLS-клиентом, а прокси — TLS-сервером, поэтому UA использует TLS для аутентификации прокси, а прокси не использует TLS для аутентификации UA. Если прокси необходимо аутентифицировать UA, это можно сделать с помощью дайджест-аутентификации SIP HTTP. Такая направленность означает, что TLS-соединение всегда должно устанавливаться со стороны UA (например, на этапе регистрации). Поскольку SIP допускает запросы в обоих направлениях (например, входящий вызов), предполагается, что UA будет поддерживать TLS-соединение открытым и это соединение будет повторно использоваться как для входящих, так и для исходящих запросов.
This solution of having the UA always initiate and keep alive the connection also solves the Network Address Translation (NAT) and firewall problem as it ensures that responses and further requests will always be deliverable on the existing connection.
Такое решение, при котором UA всегда инициирует соединение и поддерживает его, решает также проблему трансляции сетевых адресов (NAT) и межсетевых экранов, поскольку гарантирует, что ответы и последующие запросы всегда будут доставлены по существующему соединению.
[RFC5626] provides the mechanism for initiating and maintaining outbound connections in a standard interoperable way.
[RFC5626] предоставляет механизм инициирования и поддержания исходящих соединений стандартным совместимым способом.
3.1.2. Mutual Authentication
3.1.2. Взаимная аутентификация
In this model, both the TLS client and the TLS server provide a certificate in the TLS handshake phase. When used between a UA and a proxy (or between two UAs), this implies that a UA is in possession of a certificate. When sending a SIP request when there is not already a suitable TLS connection in place, a user agent client (UAC) takes on the role of TLS client in establishing a new TLS connection. When establishing a TLS connection for receipt of a SIP request, a user agent server (UAS) takes on the role of TLS server. Because in SIP a UA or a proxy acts both as UAC and UAS depending on if it is sending or receiving requests, the symmetrical nature of mutual TLS is very convenient. This allows for TLS connections to be set up or torn down at will and does not rely on keeping the TLS connection alive for further requests.
В этой модели сертификат на этапе установления TLS-соединения предоставляют как TLS-клиент, так и TLS-сервер. При использовании между UA и прокси (или между двумя UA) это означает, что UA располагает сертификатом. При отправке SIP-запроса, когда подходящее TLS-соединение ещё не установлено, клиент пользовательского агента (UAC) берёт на себя роль TLS-клиента при установлении нового TLS-соединения. При установлении TLS-соединения для приёма SIP-запроса сервер пользовательского агента (UAS) берёт на себя роль TLS-сервера. Поскольку в SIP UA или прокси выступает и как UAC, и как UAS в зависимости от того, отправляет он запросы или принимает их, симметричный характер взаимного TLS очень удобен. Это позволяет устанавливать или разрывать TLS-соединения по желанию и не требует поддержания TLS-соединения открытым для последующих запросов.
However, there are some significant limitations.
Однако существует ряд существенных ограничений.
The first obvious limitation is not with mutual authentication per se, but with the model where the underlying TCP connection can be established by either side, interchangeably, which is not possible in many environments. For examples, NATs and firewalls will often allow TCP connections to be established in one direction only. This includes most residential SIP deployments, for example. Mutual authentication can be used in those environments, but only if the connection is always started by the same side, for example, by using [RFC5626] as described in Section 3.1.1. Having to rely on [RFC5626] in this case negates many of the advantages of mutual authentication.
Первое очевидное ограничение связано не с самой взаимной аутентификацией, а с моделью, в которой базовое TCP-соединение может устанавливаться любой из сторон поочерёдно, что невозможно во многих средах. Например, NAT и межсетевые экраны часто допускают установление TCP-соединений только в одном направлении. Это касается, в частности, большинства домашних SIP-развёртываний. В таких средах взаимную аутентификацию использовать можно, но только если соединение всегда инициируется одной и той же стороной, например с помощью [RFC5626], как описано в разделе 3.1.1. Необходимость полагаться в этом случае на [RFC5626] сводит на нет многие преимущества взаимной аутентификации.
The second significant limitation is that mutual authentication requires both sides to exchange a certificate. This has proven to be impractical in many environments, in particular for SIP UAs, because of the difficulties of setting up a certificate infrastructure for a wide population of users.
Второе существенное ограничение состоит в том, что взаимная аутентификация требует обмена сертификатами между обеими сторонами. Это оказалось непрактичным во многих средах, в частности для SIP UA, из-за трудностей создания инфраструктуры сертификатов для широкой аудитории пользователей.
For these reasons, mutual authentication is mostly used in server-to- server communications (e.g., between SIP proxies, or between proxies and gateways or media servers), and in environments where using certificates on both sides is possible (e.g., high-security devices used within an enterprise).
По этим причинам взаимная аутентификация используется в основном при взаимодействии серверов (например, между SIP-прокси или между прокси и шлюзами либо медиасерверами), а также в средах, где применение сертификатов на обеих сторонах возможно (например, устройства повышенной защищённости в пределах предприятия).
3.1.3. Using TLS with SIP Instead of SIPS
3.1.3. Использование TLS с SIP вместо SIPS
Because a SIPS URI implies that requests sent to the resource identified by it be sent over each SIP hop over TLS, SIPS URIs are not suitable for "best-effort TLS": they are only suitable for "TLS- only" requests. This is recognized in Section 26.2.2 of [RFC3261]. Users that distribute a SIPS URI as an address-of-record may elect to operate devices that refuse requests over insecure transports.
Поскольку схема URI SIPS подразумевает, что запросы, отправляемые ресурсу, который она идентифицирует, передаются на каждом участке SIP через TLS, такие URI непригодны для «TLS по возможности»: они подходят только для запросов, требующих исключительно TLS. Это признано в разделе 26.2.2 документа [RFC3261]. Пользователи, распространяющие схему URI SIPS в качестве адреса записи, могут использовать устройства, отклоняющие запросы по незащищённым транспортам.
If one wants to use "best-effort TLS" for SIP, one just needs to use a SIP URI, and send the request over TLS.
Если требуется использовать «TLS по возможности» для SIP, достаточно применить схему URI SIP и отправить запрос через TLS.
Using SIP over TLS is very simple. A UA opens a TLS connection and uses SIP URIs instead of SIPS URIs for all the header fields in a SIP message (From, To, Request-URI, Contact header field, Route, etc.). When TLS is used, the Via header field indicates TLS.
Использование SIP через TLS очень просто. UA открывает TLS-соединение и использует схемы URI SIP вместо URI SIPS во всех полях заголовков SIP-сообщения (From, To, Request-URI, Contact, Route и т. д.). При использовании TLS поле заголовка Via указывает TLS.
[RFC3261], Section 26.3.2.1, states:
В разделе 26.3.2.1 документа [RFC3261] сказано:
When a UA comes online and registers with its local administrative domain, it SHOULD establish a TLS connection with its registrar (...). Once the registration has been accepted by the registrar, the UA SHOULD leave this TLS connection open provided that the registrar also acts as the proxy server to which requests are sent for users in this administrative domain. The existing TLS connection will be reused to deliver incoming requests to the UA that had just completed registration.
когда UA выходит в сеть и регистрируется в своём локальном административном домене, ему СЛЕДУЕТ установить TLS-соединение со своим регистратором (...). После того как регистратор принял регистрацию, UA СЛЕДУЕТ оставить это TLS-соединение открытым при условии, что регистратор также выполняет роль прокси-сервера, которому направляются запросы для пользователей этого административного домена. Существующее TLS-соединение будет повторно использоваться для доставки входящих запросов только что завершившему регистрацию UA.
[RFC5626] describes how to establish and maintain a TLS connection in environments where it can only be initiated by the UA.
В [RFC5626] описано, как устанавливать и поддерживать TLS-соединение в средах, где его может инициировать только UA.
Similarly, proxies can forward requests using TLS if they can open a TLS connection, even if the route set used SIP URIs instead of SIPS URIs. The proxies can insert Record-Route header fields using SIP URIs even if it uses TLS transport. [RFC3261], Section 26.3.2.2, explains how interdomain requests can use TLS.
Аналогично прокси могут пересылать запросы через TLS, если они могут открыть TLS-соединение, даже если набор маршрутов использует URI SIP, а не URI SIPS. Прокси могут вставлять поля заголовка Record-Route с URI SIP, даже если применяется транспорт TLS. В разделе 26.3.2.2 документа [RFC3261] объясняется, как междоменные запросы могут использовать TLS.
Some user agents, redirect servers, and proxies might have local policies that enforce TLS on all connections, independently of whether or not SIPS is used.
Некоторые пользовательские агенты, серверы перенаправления и прокси могут иметь локальные политики, требующие TLS для всех соединений независимо от того, используется ли SIPS.
3.1.4. Usage of the transport=tls URI Parameter and the TLS Via Parameter
3.1.4. Использование параметра URI transport=tls и параметра TLS в заголовке Via
[RFC3261], Section 26.2.2 deprecated the "transport=tls" URI transport parameter in SIPS or SIP URIs:
В разделе 26.2.2 документа [RFC3261] объявлен устаревшим параметр транспорта URI «transport=tls» в URI SIPS или SIP:
Note that in the SIPS URI scheme, transport is independent of TLS, and thus "sips:alice@atlanta.com;transport=TCP" and "sips:alice@atlanta.com;transport=sctp" are both valid (although note that UDP is not a valid transport for SIPS). The use of "transport=tls" has consequently been deprecated, partly because it was specific to a single hop of the request. This is a change since RFC 2543.
Обратите внимание, что в схеме URI SIPS транспорт не зависит от TLS, поэтому «sips:alice@atlanta.com;transport=TCP» и «sips:alice@atlanta.com;transport=sctp» одинаково допустимы (хотя UDP не является допустимым транспортом для SIPS). Использование «transport=tls» вследствие этого объявлено устаревшим, отчасти потому, что этот параметр относился к отдельному участку запроса. Это изменение по сравнению с RFC 2543.
The "tls" parameter has not been eliminated from the ABNF in [RFC3261], Section 25, since the parameter needs to remain in the ABNF for backward compatibility in order for parsers to be able to process the parameter correctly. The transport=tls parameter has never been defined in an RFC, but only in some of the Internet drafts between [RFC2543] and [RFC3261].
Параметр «tls» не был удалён из ABNF в разделе 25 документа [RFC3261], поскольку он должен оставаться в ABNF для обратной совместимости, чтобы синтаксические анализаторы могли корректно обрабатывать этот параметр. Параметр transport=tls никогда не определялся в RFC, а только в некоторых черновиках Интернета в период между [RFC2543] и [RFC3261].
This specification does not make use of the transport=tls parameter.
В настоящей спецификации параметр transport=tls не используется.
The reinstatement of the transport=tls parameter, or an alternative mechanism for indicating the use of the TLS on a single hop in a URI, is outside the scope of this specification.
Восстановление параметра transport=tls или любого иного механизма указания использования TLS на отдельном участке в URI выходит за рамки настоящей спецификации.
For Via header fields, the following transport protocols are defined in [RFC3261]: "UDP", "TCP", "TLS", "SCTP", and in [RFC4168]: "TLS- SCTP".
Для полей заголовка Via в [RFC3261] определены следующие транспортные протоколы: «UDP», «TCP», «TLS», «SCTP», а в [RFC4168] — «TLS-SCTP».
3.2. Detection of Hop-by-Hop Security
3.2. Обнаружение защиты на каждом участке
The presence of a SIPS Request-URI does not necessarily indicate that the request was sent securely on each hop. So how does a UAS know if SIPS was used for the entire request path to secure the request end- to-end? Effectively, the UAS cannot know for sure. However,
Наличие SIPS Request-URI не обязательно означает, что запрос был безопасно передан на каждом участке. Как же тогда UAS узнаёт, использовался ли SIPS на всём пути запроса для обеспечения сквозной защиты от начала до конца? Фактически UAS не может знать этого наверняка. Однако
[RFC3261], Section 26.4.4, recommends how a UAS can make some checks to validate the security. Additionally, the History-Info header field [RFC4244] could be inspected for detecting retargeting from SIP and SIPS. Retargeting from SIP to SIPS by a proxy is an issue because it can leave the receiver of the request with the impression that the request was delivered securely on each hop, while in fact, it was not.
В разделе 26.4.4 документа [RFC3261] рекомендуется, какие проверки может выполнить UAS для подтверждения безопасности. Кроме того, для обнаружения перенацеливания с SIP и SIPS можно анализировать поле заголовка History-Info [RFC4244]. Перенацеливание прокси с SIP на SIPS является проблемой, поскольку оно может создать у получателя запроса впечатление, что запрос был безопасно доставлен на каждом участке, тогда как в действительности это не так.
To emphasize, all the checking can be circumvented by any proxies or back-to-back user agents (B2BUAs) on the path that do not follow the rules and recommendations of this specification and of [RFC3261].
Подчеркнём: все проверки могут быть обойдены любыми прокси или посредниками пользовательских агентов (B2BUA) на пути, которые не соблюдают правила и рекомендации настоящей спецификации и [RFC3261].
Proxies can have their own policies regarding routing of requests to SIP or SIPS URIs. For example, some proxies in some environments can be configured to only route SIPS URIs. Some proxies can be configured to detect non-compliances and reject unsecure requests. For example, proxies could inspect Request-URIs, Path, Record-Route, To, From, Contact header fields, and Via header fields to enforce SIPS.
Прокси могут иметь собственные политики маршрутизации запросов к URI SIP или SIPS. Например, некоторые прокси в определённых средах можно настроить так, чтобы они маршрутизировали только URI SIPS. Некоторые прокси можно настроить на обнаружение нарушений и отклонение незащищённых запросов. Например, прокси могут проверять Request-URI, поля заголовков Path, Record-Route, To, From, Contact и Via, чтобы обеспечить соблюдение SIPS.
[RFC3261], Section 26.4.4, explains that S/MIME can also be used by the originating UAC to ensure that the original form of the To header field is carried end-to-end. While not specifically mentioned in [RFC3261], Section 26.4.4, this is meant to imply that [RFC3893] would be used to "tunnel" important header fields (such as To and From) in an encrypted and signed S/MIME body, replicating the information in the SIP message, and allowing the UAS to validate the content of those important header fields. While this approach is certainly legal, a preferable approach is to use the SIP Identity mechanism defined in [RFC4474]. SIP Identity creates a signed identity digest, which includes, among other things, the Address of Record (AOR) of the sender (from the From header field) and the AOR of the original target (from the To header field).
В разделе 26.4.4 документа [RFC3261] поясняется, что инициирующий UAC может также использовать S/MIME, чтобы исходная форма поля заголовка To передавалась от конца до конца. Хотя в разделе 26.4.4 документа [RFC3261] это прямо не указано, подразумевается, что [RFC3893] будет использоваться для «туннелирования» важных полей заголовков (таких как To и From) в зашифрованном и подписанном теле S/MIME с дублированием информации из SIP-сообщения, что позволяет UAS проверить содержимое этих важных полей заголовков. Хотя такой подход, безусловно, допустим, предпочтительнее использовать механизм идентификации SIP Identity, определённый в [RFC4474]. SIP Identity создаёт подписанный дайджест идентичности, который среди прочего включает адрес записи (AOR) отправителя (из поля заголовка From) и AOR первоначального получателя (из поля заголовка To).
3.3. The Problems with the Meaning of SIPS in RFC 3261

URI SIPS указывает, что к ресурсу следует обращаться безопасным образом. Это означает, в частности, что между UAC и доменом, которому принадлежит URI, должен использоваться TLS. Далее для связи с пользователем применяются защищённые каналы, причём конкретный механизм защиты зависит от политики домена.

One can then wonder why TLS is mandatory between UA a@A and Proxy A but not between Proxy B and UA b@B. The main reason is that [RFC3261] was written before [RFC5626]. At that time, it was recognized that in many practical deployments, Proxy B might not be able to establish a TLS connection with UA b because only Proxy B would have a certificate to provide and UA b would not. Since UA b would be the TLS server, it would then not be able to accept the incoming TLS connection. The consequence is that an [RFC3261]- compliant UAS b, while it might not need to support TLS for incoming requests, will nevertheless have to support TLS for outgoing requests as it takes the UAC role. Contrary to what many believed erroneously, the last-hop exception was not created to allow for using a SIPS URI to address a UAS that does not support TLS: the last-hop exception was an attempt to allow for incoming requests to not be transported over TLS when a SIPS URI is used, and it does not apply to outgoing requests. The rationale for this was somewhat flawed, and since then, [RFC5626] has provided a more satisfactory solution to this problem. [RFC5626] also solves the problem that if UA b is behind a NAT or firewall, Proxy B would not even be able to establish a TCP session in the first place.
Возникает вопрос: почему TLS обязателен между UA a@A и прокси A, но не между прокси B и UA b@B? Основная причина в том, что [RFC3261] был написан до [RFC5626]. В то время было признано, что во многих практических развёртываниях прокси B может быть не в состоянии установить TLS-соединение с UA b, поскольку сертификат для предоставления был бы только у прокси B, а у UA b его нет. Поскольку TLS-сервером был бы UA b, он не смог бы принять входящее TLS-соединение. Следствие таково: UAS b, совместимый с [RFC3261], может не нуждаться в поддержке TLS для входящих запросов, но тем не менее должен поддерживать TLS для исходящих запросов, поскольку выступает в роли UAC. Вопреки ошибочному мнению многих, исключение для последнего участка было создано не для того, чтобы можно было использовать URI SIPS для адресации UAS, не поддерживающего TLS: это исключение было попыткой разрешить передачу входящих запросов без TLS при использовании URI SIPS, и оно не распространяется на исходящие запросы. Обоснование этого было несколько ошибочным, и с тех пор [RFC5626] предложил более удовлетворительное решение этой проблемы. [RFC5626] решает также проблему, состоящую в том, что если UA b находится за NAT или межсетевым экраном, прокси B вообще не смог бы установить даже TCP-сеанс.
Furthermore, consider the problem of using SIPS inside a dialog. If a@A sends a request to b@B using a SIPS Request-URI, then, according to [RFC3261], Section 8.1.1.8, "the Contact header field MUST contain a SIPS URI as well". This means that b@B, upon sending a new Request within the dialog (e.g., a BYE or re-INVITE), will have to use a SIPS URI. If there is no Record-Route entry, or if the last Record-Route entry consists of a SIPS URI, this implies that b@B is expected to understand SIPS in the first place, and is required to also support TLS. If the last Record-Route entry however is a sip URI, then b would be able to send requests without using TLS (but b would still have to be able to handle SIPS schemes when parsing the message). In either case, the Request-URI in the request from b@B to B would be a SIPS URI.
Кроме того, рассмотрим проблему использования SIPS внутри диалога. Если a@A отправляет запрос b@B с SIPS Request-URI, то, согласно разделу 8.1.1.8 документа [RFC3261], «поле заголовка Contact также ДОЛЖНО содержать URI SIPS». Это означает, что b@B при отправке нового запроса в диалоге (например, BYE или re-INVITE) должен будет использовать URI SIPS. Если записи Record-Route нет или последняя запись Record-Route состоит из URI SIPS, это подразумевает, что b@B изначально должен понимать SIPS и обязан также поддерживать TLS. Если же последняя запись Record-Route представляет собой URI sip, то b сможет отправлять запросы без использования TLS (но b всё равно должен уметь обрабатывать схемы SIPS при разборе сообщения). В любом случае Request-URI в запросе от b@B к B будет URI SIPS.

4. Обзор вариантов работы
Because of all the problems described in Section 3.3, this specification deprecates the last-hop exception when forwarding a request to the last hop (see Section 5.3). This will ensure that TLS is used on all hops all the way up to the remote target.
Из-за всех проблем, описанных в разделе 3.3, настоящая спецификация отменяет исключение для последнего участка при пересылке запроса на последний участок (см. раздел 5.3). Это обеспечит использование TLS на всех участках вплоть до удалённой цели.

The SIPS scheme implies transitive trust. Obviously, there is nothing that prevents proxies from cheating (see [RFC3261], Section 26.4.4). While SIPS is useful to request that a resource be contacted securely, it is not useful as an indication that a resource was in fact contacted securely. Therefore, it is not appropriate to infer that because an incoming request had a Request-URI (or even a To header field) containing a SIPS URI, that it necessarily guarantees that the request was in fact transmitted securely on each hop. Some have been tempted to believe that the SIPS scheme was equivalent to an HTTPS scheme in the sense that one could provide a visual indication to a user (e.g., a padlock icon) to the effect that the session is secured. This is obviously not the case, and therefore the meaning of a SIPS URI is not to be oversold. There is currently no mechanism to provide an indication of end-to-end security for SIP. Other mechanisms can provide a more concrete indication of some level of security. For example, SIP Identity [RFC4474] provides an authenticated identity mechanism and a domain- to-domain integrity protection mechanism.
Схема SIPS подразумевает транзитивное доверие. Очевидно, ничто не мешает прокси обманывать (см. раздел 26.4.4 документа [RFC3261]). Хотя SIPS полезен для требования безопасного обращения к ресурсу, он не служит указанием на то, что к ресурсу действительно обратились безопасным образом. Поэтому не следует делать вывод, что наличие входящего запроса с Request-URI (или даже с полем заголовка To), содержащим URI SIPS, непременно гарантирует, что запрос был действительно безопасно передан на каждом участке. Некоторые были склонны считать, что схема SIPS эквивалентна схеме HTTPS в том смысле, что можно предоставить пользователю визуальный индикатор (например, значок замка), указывающий на защищённость сеанса. Очевидно, это не так, и поэтому значение URI SIPS не следует преувеличивать. В настоящее время не существует механизма, позволяющего указать на сквозную защиту для SIP. Другие механизмы могут дать более конкретное указание на определённый уровень защиты. Например, SIP Identity [RFC4474] предоставляет механизм аутентифицированной идентичности и механизм защиты целостности между доменами.
Some have asked why is SIPS useful in a global open environment such as the Internet, if (when used in a Request-URI) it is not an absolute guarantee that the request will in fact be delivered over TLS on each hop? Why is SIPS any different from just using TLS transport with SIP? The difference is that using a SIPS URI in a Request-URI means that if you are instructing the network to use TLS over each hop and if it is not possible to reject the request, you would rather have the request fail than have the request delivered without TLS. Just using TLS with a SIP Request-URI instead of a SIPS Request-URI implies a "best-effort" service: the request can but need not be delivered over TLS on each hop.
Некоторые спрашивают, чем полезен SIPS в глобальной открытой среде, такой как Интернет, если (при использовании в Request-URI) он не является абсолютной гарантией того, что запрос действительно будет доставлен через TLS на каждом участке? Чем SIPS отличается от простого использования транспорта TLS с SIP? Разница в том, что использование URI SIPS в Request-URI означает: если вы предписываете сети применять TLS на каждом участке и при этом невозможно отклонить запрос, вы предпочтёте, чтобы запрос не удался, а не был доставлен без TLS. Простое использование TLS с SIP Request-URI вместо SIPS Request-URI подразумевает обслуживание «по возможности»: запрос может, но не обязан доставляться через TLS на каждом участке.
Another common question is why not have a Proxy-Require and Require option tag forcing the use of TLS instead? The answer is that it would only be functionally equivalent to using SIPS in a Request-URI. SIPS URIs however can be used in many other header fields: in Contact for registration, Contact in dialog-creating requests, Route, Record- Route, Path, From, To, Refer-To, Referred-By, etc. SIPS URIs can also be used in human-usable format (e.g., business cards, user interface). SIPS URIs can even be used in other protocols or document formats that allow for including SIPS URIs (e.g., HTML).
Другой распространённый вопрос: почему бы вместо этого не ввести теги опций Proxy-Require и Require, принудительно включающие TLS? Ответ: это было бы функционально эквивалентно использованию SIPS в Request-URI. Однако URI SIPS могут применяться во многих других полях заголовков: в Contact при регистрации, в Contact в запросах, создающих диалог, в Route, Record-Route, Path, From, To, Refer-To, Referred-By и т. д. URI SIPS могут также использоваться в удобочитаемом для человека формате (например, визитные карточки, пользовательский интерфейс). URI SIPS могут даже применяться в других протоколах или форматах документов, допускающих включение URI SIPS (например, HTML).
This document specifies that SIPS means that the SIP resource designated by the target SIPS URI is to be contacted securely, using TLS on each hop between the UAC and the remote UAS (as opposed to only to the proxy responsible for the target domain of the Request- URI). It is outside of the scope of this document to specify what happens when a SIPS URI identifies a UAS resource that "maps" outside the SIP network, for example, to other networks such as the Public Switched Telephone Network (PSTN).
Настоящий документ устанавливает, что SIPS означает безопасное обращение к ресурсу SIP, обозначенному целевым URI SIPS, с использованием TLS на каждом участке между UAC и удалённым UAS (а не только до прокси, отвечающего за целевой домен Request-URI). Определение того, что происходит, когда URI SIPS идентифицирует ресурс UAS, «отображаемый» за пределы сети SIP, например в другие сети, такие как телефонная сеть общего пользования (PSTN), выходит за рамки настоящего документа.
4.1. Routing
4.1. Маршруты
SIP and SIPS URIs that are identical except for the scheme itself (e.g., sip:alice@example.com and sips:alice@example.com) refer to the same resource. This requirement is implicit in [RFC3261], Section 19.1, which states that "any resource described by a SIP URI can be 'upgraded' to a SIPS URI by just changing the scheme, if it is desired to communicate with that resource securely". This does not mean that the SIPS URI will necessarily be reachable, in particular, if the proxy cannot establish a secure connection to a client or another proxy. This does not suggest either that proxies would arbitrarily "upgrade" SIP URIs to SIPS URIs when forwarding a request (see Section 5.3). Rather, it means that when a resource is addressable with SIP, it will also be addressable with SIPS.
URI SIP и SIPS, совпадающие во всём, кроме самой схемы (например, sip:alice@example.com и sips:alice@example.com), указывают на один и тот же ресурс. Это требование неявно следует из раздела 19.1 документа [RFC3261], где сказано, что «любой ресурс, описываемый URI SIP, можно „повысить“ до URI SIPS, просто изменив схему, если требуется взаимодействовать с этим ресурсом безопасным образом». Это не означает, что URI SIPS обязательно будет достижим, в частности если прокси не может установить защищённое соединение с клиентом или другим прокси. Это также не означает, что прокси будут произвольно «повышать» URI SIP до URI SIPS при пересылке запроса (см. раздел 5.3). Скорее, это означает, что если ресурс адресуем с помощью SIP, он будет адресуем и с помощью SIPS.
For example, consider the case of a UA that has registered with a SIPS Contact header field. If a UAC later addresses a request using a SIP Request-URI, the proxy will forward the request addressed to a SIP Request-URI to the UAS, as illustrated by message F13 in Sections 6.3 and in 6.4. The proxy forwards the request to the UA using a SIP Request-URI and not the SIPS Request-URI used in registration. The proxy does this by replacing the SIPS scheme that was used in the registered Contact header field binding with a SIP scheme while leaving the rest of the URI as is, and then by using this new URI as the Request-URI. If the proxy did not do this, and instead used a SIPS Request-URI, then the response (e.g., a 200 to an INVITE) would have to include a SIPS Contact header field. That SIPS Contact header field would then force the other UA to use a SIPS Contact header field in any mid-dialog request, including the ACK (which would not be possible if that UA did not support SIPS).
Например, рассмотрим случай, когда UA зарегистрировался с полем заголовка Contact, содержащим URI SIPS. Если затем UAC адресует запрос с SIP Request-URI, прокси перешлёт запрос, адресованный с SIP Request-URI, на UAS, как показано сообщением F13 в разделах 6.3 и 6.4. Прокси пересылает запрос UA с SIP Request-URI, а не с SIPS Request-URI, использованным при регистрации. Для этого прокси заменяет схему SIPS, применённую в зарегистрированной привязке поля заголовка Contact, на схему SIP, оставляя остальную часть URI без изменений, и затем использует этот новый URI в качестве Request-URI. Если бы прокси этого не сделал и вместо этого использовал SIPS Request-URI, то ответ (например, 200 на INVITE) должен был бы содержать поле заголовка Contact с URI SIPS. Такое поле заголовка Contact с URI SIPS вынудило бы другой UA использовать поле заголовка Contact с URI SIPS во всех запросах внутри диалога, включая ACK (что было бы невозможно, если этот UA не поддерживает SIPS).
This specification mandates that when a proxy is forwarding a request, a resource described by a SIPS Request-URI cannot be "downgraded" to a SIP URI by changing the scheme, or by sending the associated request over a nonsecure link. If a request needs to be rejected because otherwise it would be a "downgrade", the request would be rejected with a 480 (Temporarily Unavailable) response (potentially with a Warning header with warn-code 380 "SIPS Not Allowed"). Similarly, this specification mandates that when a proxy is forwarding a request, a resource described by a SIP Request-URI cannot be "upgraded" to a SIPS URI by changing the scheme (otherwise it would be an "upgrade" only for that hop onwards rather than on all hops, and would therefore mislead the UAS). If a request needs to be rejected because otherwise it would be a misleading "upgrade", the request would be rejected with a 480 (Temporarily Unavailable) response (potentially with a Warning header field with warn-code 381 "SIPS Required"). See Section 5.3 for more details.
Настоящая спецификация требует, чтобы при пересылке запроса прокси ресурс, описываемый SIPS Request-URI, не мог быть «понижен» до URI SIP путём изменения схемы или отправки соответствующего запроса по незащищённому каналу. Если запрос необходимо отклонить, поскольку в противном случае произошло бы «понижение», запрос отклоняется ответом 480 (Temporarily Unavailable) (возможно, с полем заголовка Warning и кодом предупреждения 380 «SIPS Not Allowed»). Аналогично настоящая спецификация требует, чтобы при пересылке запроса прокси ресурс, описываемый SIP Request-URI, не мог быть «повышен» до URI SIPS путём изменения схемы (иначе это было бы «повышением» только для данного участка и далее, а не на всех участках, и ввело бы UAS в заблуждение). Если запрос необходимо отклонить, поскольку в противном случае произошло бы вводящее в заблуждение «повышение», запрос отклоняется ответом 480 (Temporarily Unavailable) (возможно, с полем заголовка Warning и кодом предупреждения 381 «SIPS Required»). Подробнее см. раздел 5.3.
For example, the sip:bob@example.com and sips:bob@example.com AORs refer to the same user "Bob" in the domain "example.com": the first URI is the SIP version, and the second one is the SIPS version. From the point of view of routing, requests to either sip:bob@example.com or sips:bob@example.com are treated the same way. When Bob registers, it therefore does not really matter if he is using a SIP or a SIPS AOR, since they both refer to the same user. At first glance, Section 19.1.4 of [RFC3261] seems to contradict this idea by stating that a SIP and a SIPS URI are never equivalent. Specifically, it says that they are never equivalent for the purpose of comparing bindings in Contact header field URIs in REGISTER requests. The key point is that this statement applies to the Contact header field bindings in a registration: it is the association of the Contact header field with the AOR that will determine whether or not the user is reachable with a SIPS URI.
Например, AOR sip:bob@example.com и sips:bob@example.com указывают на одного и того же пользователя «Bob» в домене «example.com»: первый URI — это версия SIP, второй — версия SIPS. С точки зрения маршрутизации запросы как к sip:bob@example.com, так и к sips:bob@example.com обрабатываются одинаково. Поэтому при регистрации Боба не имеет особого значения, использует ли он AOR SIP или AOR SIPS, поскольку оба указывают на одного и того же пользователя. На первый взгляд раздел 19.1.4 документа [RFC3261] противоречит этой идее, утверждая, что URI SIP и URI SIPS никогда не эквивалентны. В частности, там сказано, что они никогда не эквивалентны для целей сравнения привязок в URI поля заголовка Contact в запросах REGISTER. Ключевой момент состоит в том, что это утверждение относится к привязкам поля заголовка Contact при регистрации: именно связь поля заголовка Contact с AOR определяет, достижим ли пользователь по URI SIPS.
Consider this example: if Bob (AOR bob@example.com) registers with a SIPS Contact header field (e.g., sips:bob@bobphone.example.com), the registrar and the location service then know that Bob is reachable at sips:bob@bobphone.example.com and at sip:bob@bobphone.example.com. If a request is sent to AOR sips:bob@example.com, Bob's proxy will route it to Bob at Request-URI sips:bob@bobphone.example.com. If a request is sent to AOR sip:bob@example.com, Bob's proxy will route it to Bob at Request-URI sip:bob@bobphone.example.com.
Рассмотрим пример: если Боб (AOR bob@example.com) регистрируется с полем заголовка Contact, содержащим URI SIPS (например, sips:bob@bobphone.example.com), регистратор и служба определения местоположения узнают, что Боб достижим по sips:bob@bobphone.example.com и по sip:bob@bobphone.example.com. Если запрос отправлен на AOR sips:bob@example.com, прокси Боба направит его Бобу с Request-URI sips:bob@bobphone.example.com. Если запрос отправлен на AOR sip:bob@example.com, прокси Боба направит его Бобу с Request-URI sip:bob@bobphone.example.com.
If Bob wants to ensure that every request delivered to him always be transported over TLS, Bob can use [RFC5626] when registering.
Если Боб хочет гарантировать, что каждый доставляемый ему запрос всегда передаётся через TLS, он может использовать [RFC5626] при регистрации.
However, if Bob had registered with a SIP Contact header field instead of a SIPS Contact header field (e.g., sip:bob@bobphone.example.com), then a request to AOR sips:bob@example.com would not be routed to Bob, since there is no SIPS Contact header field for Bob, and "downgrades" from SIPS to SIP are not allowed.
Однако если бы Боб зарегистрировался с полем заголовка Contact, содержащим URI SIP, а не URI SIPS (например, sip:bob@bobphone.example.com), то запрос на AOR sips:bob@example.com не был бы направлен Бобу, поскольку для Боба нет поля заголовка Contact с URI SIPS, а «понижения» с SIPS до SIP не допускаются.
See Section 6 for illustrative call flows.
Иллюстративные потоки вызовов см. в разделе 6.
5. Normative Requirements
5. Нормативные требования
This section describes all the normative requirements defined by this specification.
В настоящем разделе описаны все нормативные требования, определённые настоящей спецификацией.
5.1. General User Agent Behavior
5.1. Поведение пользовательского агента
5.1.1. UAC Behavior
5.1.1. Поведение UAC
When presented with a SIPS URI, a UAC MUST NOT change it to a SIP URI. For example, if a directory entry includes a SIPS AOR, the UAC is not expected to send requests to that AOR using a SIP Request-URI. Similarly, if a user reads a business card with a SIPS URI, it is not possible to infer a SIP URI. If a 3XX response includes a SIPS Contact header field, the UAC does not replace it with a SIP Request- URI (e.g., by replacing the SIPS scheme with a SIP scheme) when sending a request as a result of the redirection.
Получив URI SIPS, UAC НЕ ДОЛЖЕН заменять его на URI SIP. Например, если запись каталога содержит AOR SIPS, UAC не должен отправлять запросы на этот AOR с SIP Request-URI. Аналогично, если пользователь видит визитную карточку с URI SIPS, вывести из неё URI SIP невозможно. Если ответ 3XX содержит поле заголовка Contact с URI SIPS, UAC не заменяет его на SIP Request-URI (например, путём замены схемы SIPS на схему SIP) при отправке запроса в результате перенаправления.
As mandated by [RFC3261], Section 8.1.1.8, in a request, "if the Request-URI or top Route header field value contains a SIPS URI, the Contact header field MUST contain a SIPS URI as well".
Как предписано разделом 8.1.1.8 документа [RFC3261], в запросе «если Request-URI или значение верхнего поля заголовка Route содержит URI SIPS, поле заголовка Contact также ДОЛЖНО содержать URI SIPS».
Upon receiving a 416 response or a 480 (Temporarily Unavailable) response with a Warning header with warn-code 380 "SIPS Not Allowed", a UAC MUST NOT re-attempt the request by automatically replacing the SIPS scheme with a SIP scheme as described in [RFC3261], Section 8.1.3.5, as it would be a security vulnerability. If the UAC does re-attempt the call with a SIP URI, the UAC SHOULD get a confirmation from the user to authorize re-initiating the session with a SIP Request-URI instead of a SIPS Request-URI. When the route set is not empty (e.g., when a service route [RFC3608] is returned by the registrar), it is the responsibility of the UAC to use a Route header field consisting of all SIPS URIs when using a SIPS Request-URI. Specifically, if the route set included any SIP URI, the UAC MUST change the SIP URIs to SIPS URIs simply by changing the scheme from "sip" to "sips" before sending the request. This allows for configuring or discovering one service route with all SIP URIs and allowing sending requests to both SIP and SIPS URIs.
При получении ответа 416 или ответа 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 380 «SIPS Not Allowed» UAC НЕ ДОЛЖЕН повторять запрос, автоматически заменяя схему SIPS на схему SIP, как описано в разделе 8.1.3.5 документа [RFC3261], поскольку это было бы уязвимостью безопасности. Если UAC всё же повторяет вызов с URI SIP, ему СЛЕДУЕТ получить от пользователя подтверждение, разрешающее повторно инициировать сеанс с SIP Request-URI вместо SIPS Request-URI. Когда набор маршрутов не пуст (например, когда регистратор возвращает служебный маршрут [RFC3608]), UAC отвечает за использование поля заголовка Route, состоящего только из URI SIPS, при использовании SIPS Request-URI. В частности, если набор маршрутов содержал какие-либо URI SIP, UAC ДОЛЖЕН заменить URI SIP на URI SIPS, просто изменив схему с «sip» на «sips» перед отправкой запроса. Это позволяет настроить или обнаружить один служебный маршрут со всеми URI SIP и разрешает отправлять запросы как на URI SIP, так и на URI SIPS.
When the UAC is using a SIP Request-URI, if the route set is not empty and the topmost Route header field entry is a SIPS URI with the lr parameter, the UAC MUST send the request over TLS (using a SIP Request-URI). If the route is not empty and the Route header field entry is a SIPS URI without the lr parameter, the UAC MUST send the request over TLS using a SIPS Request-URI corresponding to the topmost entry in the route set.
Когда UAC использует SIP Request-URI, если набор маршрутов не пуст и самая верхняя запись поля заголовка Route представляет собой URI SIPS с параметром lr, UAC ДОЛЖЕН отправить запрос через TLS (используя SIP Request-URI). Если маршрут не пуст и запись поля заголовка Route представляет собой URI SIPS без параметра lr, UAC ДОЛЖЕН отправить запрос через TLS, используя SIPS Request-URI, соответствующий самой верхней записи в наборе маршрутов.
To emphasize what is already defined in [RFC3261], UAs MUST NOT use the "transport=tls" parameter.
Подчеркнём уже определённое в [RFC3261]: UA НЕ ДОЛЖНЫ использовать параметр «transport=tls».
5.1.1.1. Registration
5.1.1.1. Регистрация
The UAC registers Contacts header fields to either a SIPS or a SIP AOR.
UAC регистрирует поля заголовка Contact на AOR SIPS или на AOR SIP.
If a UA wishes to be reachable with a SIPS URI, the UA MUST register with a SIPS Contact header field. Requests addressed to that UA's AOR using either a SIP or SIPS Request-URI will be routed to that UA. This includes UAs that support both SIP and SIPS. This specification does not provide any SIP-based mechanism for a UA to provision its proxy to only forward requests using a SIPS Request-URI. A non-SIP mechanism such as a web interface could be used to provision such a preference. A SIP mechanism for provisioning such a preference is outside the scope of this specification.
Если UA желает быть достижимым по URI SIPS, он ДОЛЖЕН зарегистрироваться с полем заголовка Contact, содержащим URI SIPS. Запросы, адресованные AOR этого UA с SIP или SIPS Request-URI, будут направлены этому UA. Это относится и к UA, поддерживающим как SIP, так и SIPS. Настоящая спецификация не предоставляет никакого механизма на основе SIP, позволяющего UA настроить свой прокси так, чтобы тот пересылал запросы только с SIPS Request-URI. Для настройки такого предпочтения можно использовать механизм, не относящийся к SIP, например веб-интерфейс. Механизм настройки такого предпочтения средствами SIP выходит за рамки настоящей спецификации.
If a UA does not wish to be reached with a SIPS URI, it MUST register with a SIP Contact header field.
Если UA не желает быть достижимым по URI SIPS, он ДОЛЖЕН зарегистрироваться с полем заголовка Contact, содержащим URI SIP.
Because registering with a SIPS Contact header field implies a binding of both a SIPS Contact and a corresponding SIP Contact to the AOR, a UA MUST NOT include both the SIPS and the SIP versions of the same Contact header field in a REGISTER request; the UA MUST only use the SIPS version in this case. Similarly, a UA SHOULD NOT register both a SIP Contact header field and a SIPS Contact header field in separate registrations as the SIP Contact header field would be superfluous. If it does, the second registration replaces the first one (e.g., a UA could register first with a SIP Contact header field, meaning it does not support SIPS, and later register with a SIPS Contact header field, meaning it now supports SIPS). Similarly, if a UA registers first with a SIPS Contact header field and later registers with a SIP Contact header field, that SIP Contact header field replaces the SIPS Contact header field.
Поскольку регистрация с полем заголовка Contact, содержащим URI SIPS, подразумевает привязку к AOR как URI SIPS, так и соответствующего URI SIP в поле заголовка Contact, UA НЕ ДОЛЖЕН включать в запрос REGISTER обе версии — SIPS и SIP — одного и того же поля заголовка Contact; в этом случае UA ДОЛЖЕН использовать только версию SIPS. Аналогично UA НЕ СЛЕДУЕТ регистрировать поле заголовка Contact с URI SIP и поле заголовка Contact с URI SIPS в отдельных регистрациях, поскольку поле заголовка Contact с URI SIP было бы излишним. Если он это делает, вторая регистрация заменяет первую (например, UA может сначала зарегистрироваться с полем заголовка Contact с URI SIP, что означает отсутствие поддержки SIPS, а позже зарегистрироваться с полем заголовка Contact с URI SIPS, что означает, что теперь он поддерживает SIPS). Аналогично, если UA сначала регистрируется с полем заголовка Contact с URI SIPS, а позже — с полем заголовка Contact с URI SIP, это поле заголовка Contact с URI SIP заменяет поле заголовка Contact с URI SIPS.
[RFC5626] can be used by a UA if it wants to ensure that no requests are delivered to it without using the TLS connection it used when registering.
UA может использовать [RFC5626], если хочет гарантировать, что ни один запрос не будет доставлен ему без использования TLS-соединения, применённого при регистрации.
If all the Contact header fields in a REGISTER request are SIPS, the UAC MUST use SIPS AORs in the From and To header fields in the REGISTER request. If at least one of the Contact header fields is not SIPS (e.g., sip, mailto, tel, http, https), the UAC MUST use SIP AORs in the From and To header fields in the REGISTER request.
Если все поля заголовка Contact в запросе REGISTER имеют схему SIPS, UAC ДОЛЖЕН использовать AOR SIPS в полях заголовка From и To запроса REGISTER. Если хотя бы одно из полей заголовка Contact не является SIPS (например, sip, mailto, tel, http, https), UAC ДОЛЖЕН использовать AOR SIP в полях заголовка From и To запроса REGISTER.
To emphasize what is already defined in [RFC3261], UACs MUST NOT use the "transport=tls" parameter.
Подчеркнём уже определённое в [RFC3261]: UAC НЕ ДОЛЖНЫ использовать параметр «transport=tls».
5.1.1.2. SIPS in a Dialog
5.1.1.2. SIPS в диалоге
If the Request-URI in a request that initiates a dialog is a SIP URI, then the UAC needs to be careful about what to use in the Contact header field (in case Record-Route is not used for this hop). If the Contact header field was a SIPS URI, it would mean that the UAS would only accept mid-dialog requests that are sent over secure transport on each hop. Since the Request-URI in this case is a SIP URI, it is quite possible that the UA sending a request to that URI might not be able to send requests to SIPS URIs. If the top Route header field does not contain a SIPS URI, the UAC MUST use a SIP URI in the Contact header field, even if the request is sent over a secure transport (e.g., the first hop could be re-using a TLS connection to the proxy as would be the case with [RFC5626]).
Если Request-URI в запросе, инициирующем диалог, является URI SIP, то UAC должен внимательно выбирать, что использовать в поле заголовка Contact (на случай, если Record-Route для этого участка не применяется). Если бы поле заголовка Contact содержало URI SIPS, это означало бы, что UAS принимает только запросы внутри диалога, передаваемые по защищённому транспорту на каждом участке. Поскольку в этом случае Request-URI является URI SIP, вполне возможно, что UA, отправляющий запрос на этот URI, не сможет отправлять запросы на URI SIPS. Если верхнее поле заголовка Route не содержит URI SIPS, UAC ДОЛЖЕН использовать URI SIP в поле заголовка Contact, даже если запрос передаётся по защищённому транспорту (например, первый участок может повторно использовать TLS-соединение с прокси, как в случае [RFC5626]).
When a target refresh occurs within a dialog (e.g., re-INVITE request, UPDATE request), the UAC MUST include a Contact header field with a SIPS URI if the original request used a SIPS Request-URI.
Когда в диалоге происходит обновление цели (например, запрос re-INVITE или UPDATE), UAC ДОЛЖЕН включить поле заголовка Contact с URI SIPS, если исходный запрос использовал SIPS Request-URI.
5.1.1.3. Derived Dialogs and Transactions
5.1.1.3. Производные диалоги и транзакции
Sessions, dialogs, and transactions can be "derived" from existing ones. A good example of a derived dialog is one that was established as a result of using the REFER method [RFC3515].
Сеансы, диалоги и транзакции могут «производиться» от существующих. Хороший пример производного диалога — диалог, установленный в результате использования метода REFER [RFC3515].
As a general principle, derived dialogs and transactions cannot result in an effective downgrading of SIPS to SIP, without the explicit authorization of the entities involved. For example, when a REFER request is used to perform a call transfer, it results in an existing dialog being terminated and another one being created based on the Refer-To URI. If that initial dialog was established using SIPS, then the UAC MUST NOT establish a new one using SIP, unless there is an explicit authorization given by the recipient of the REFER request. This could be a warning provided to the user. Having such a warning could be useful, for example, for a secure directory service application, to warn a user that a request may be routed to a UA that does not support SIPS.
Общий принцип таков: производные диалоги и транзакции не могут приводить к фактическому понижению SIPS до SIP без явного разрешения участвующих сторон. Например, когда запрос REFER используется для перевода вызова, это приводит к завершению существующего диалога и созданию другого на основе URI Refer-To. Если этот исходный диалог был установлен с использованием SIPS, то UAC НЕ ДОЛЖЕН устанавливать новый диалог с использованием SIP, если только получатель запроса REFER не дал явного разрешения. Таким разрешением может быть предупреждение, показанное пользователю. Наличие такого предупреждения может быть полезно, например, для приложения безопасной службы каталогов, чтобы предупредить пользователя о том, что запрос может быть направлен UA, не поддерживающему SIPS.
A REFER request can also be used for referring to resources that do not result in dialogs being created. In fact, a REFER request can be used to point to resources that are of a different type than the original one (i.e., not SIP or SIPS). Please see [RFC3515], Section 5.2, for security considerations related to this.
Запрос REFER можно также использовать для ссылки на ресурсы, не приводящие к созданию диалогов. Фактически запрос REFER может указывать на ресурсы иного типа, чем исходный (то есть не SIP или SIPS). Вопросы безопасности, связанные с этим, см. в разделе 5.2 документа [RFC3515].
Other examples of derived dialogs and transactions include the use of Third-Party Call Control [RFC3725], the Replaces header field [RFC3891], and the Join header field [RFC3911]. Again, the general principle is that these mechanisms SHOULD NOT result in an effective downgrading of SIPS to SIP, without the proper authorization.
Другие примеры производных диалогов и транзакций — использование управления вызовами третьей стороны [RFC3725], поля заголовка Replaces [RFC3891] и поля заголовка Join [RFC3911]. Опять же, общий принцип состоит в том, что эти механизмы НЕ ДОЛЖНЫ приводить к фактическому понижению SIPS до SIP без надлежащего разрешения.
5.1.1.4. GRUU
5.1.1.4. GRUU
When a Globally Routable User Agent URI (GRUU) [RFC5627] is assigned to an instance ID/AOR pair, both SIP and SIPS GRUUs will be assigned. When a GRUU is obtained through registration, if the Contact header field in the REGISTER request contains a SIP URI, the SIP version of the GRUU is returned. If the Contact header field in the REGISTER request contains a SIPS URI, the SIPS version of the GRUU is returned.
Когда паре «идентификатор экземпляра/AOR» назначается глобально маршрутизируемый URI пользовательского агента (GRUU) [RFC5627], назначаются GRUU как для SIP, так и для SIPS. При получении GRUU посредством регистрации, если поле заголовка Contact в запросе REGISTER содержит URI SIP, возвращается версия GRUU для SIP. Если поле заголовка Contact в запросе REGISTER содержит URI SIPS, возвращается версия GRUU для SIPS.
If the wrong scheme is received in the GRUU (which would be an error in the registrar), the UAC SHOULD treat it as if the proper scheme was used (i.e., it SHOULD replace the scheme with the proper scheme before using the GRUU).
Если в GRUU получена неправильная схема (что было бы ошибкой регистратора), UAC СЛЕДУЕТ обращаться с ней так, как если бы использовалась надлежащая схема (то есть СЛЕДУЕТ заменить схему на надлежащую перед использованием GRUU).
5.1.2. UAS Behavior
5.1.2. Поведение UAS
When presented with a SIPS URI, a UAS MUST NOT change it to a SIP URI.
Получив URI SIPS, UAS ни при каких обстоятельствах НЕ ДОЛЖЕН заменять его на URI SIP.
As mandated by [RFC3261], Section 12.1.1:
Как предписано разделом 12.1.1 документа [RFC3261]:
If the request that initiated the dialog contained a SIPS URI in the Request-URI or in the top Record-Route header field value, if there was any, or the Contact header field if there was no Record- Route header field, the Contact header field in the response MUST be a SIPS URI.
Если запрос, инициировавший диалог, содержал URI SIPS в Request-URI или в значении верхнего поля заголовка Record-Route (если оно было), либо в поле заголовка Contact (если поля заголовка Record-Route не было), поле заголовка Contact в ответе ДОЛЖНО содержать URI SIPS.
If a UAS does not wish to be reached with a SIPS URI but only with a SIP URI, the UAS MUST respond with a 480 (Temporarily Unavailable) response. The UAS SHOULD include a Warning header with warn-code 380 "SIPS Not Allowed". [RFC3261], Section 8.2.2.1, states that UASs that do not support the SIPS URI scheme at all "SHOULD reject the request with a 416 (Unsupported URI scheme) response".
Если UAS не желает быть достижимым по URI SIPS, а только по URI SIP, он ДОЛЖЕН ответить ответом 480 (Temporarily Unavailable). UAS СЛЕДУЕТ включить поле заголовка Warning с кодом предупреждения 380 «SIPS Not Allowed». В разделе 8.2.2.1 документа [RFC3261] сказано, что UAS, вообще не поддерживающие схему URI SIPS, «СЛЕДУЕТ отклонять запрос ответом 416 (Unsupported URI scheme)».
If a UAS does not wish to be contacted with a SIP URI but instead by a SIPS URI, it MUST reject a request to a SIP Request-URI with a 480 (Temporarily Unavailable) response. The UAS SHOULD include a Warning header with warn-code 381 "SIPS Required".
Если UAS не желает, чтобы к нему обращались по URI SIP, а только по URI SIPS, он ДОЛЖЕН отклонять запрос с SIP Request-URI ответом 480 (Temporarily Unavailable). UAS СЛЕДУЕТ включить поле заголовка Warning с кодом предупреждения 381 «SIPS Required».
It is a matter of local policy for a UAS to accept incoming requests addressed to a URI scheme that does not correspond to what it used for registration. For example, a UA with a policy of "always SIPS" would address the registrar using a SIPS Request-URI over TLS, would register with a SIPS Contact header field, and the UAS would reject requests using the SIP scheme with a 480 (Temporarily Unavailable) response with a Warning header with warn-code 381 "SIPS Required". A UA with a policy of "best-effort SIPS" would address the registrar using a SIPS Request-URI over TLS, would register with a SIPS Contact header field, and the UAS would accept requests addressed to either SIP or SIPS Request-URIs. A UA with a policy of "No SIPS" would address the registrar using a SIP Request-URI, could use TLS or not, would register with a SIP AOR and a SIP Contact header field, and the UAS would accept requests addressed to a SIP Request-URI.
Приём входящих запросов, адресованных со схемой URI, не соответствующей той, что использовалась при регистрации, является вопросом локальной политики UAS. Например, UA с политикой «всегда SIPS» обращался бы к регистратору с SIPS Request-URI через TLS, регистрировался бы с полем заголовка Contact, содержащим URI SIPS, а UAS отклонял бы запросы со схемой SIP ответом 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 381 «SIPS Required». UA с политикой «SIPS по возможности» обращался бы к регистратору с SIPS Request-URI через TLS, регистрировался бы с полем заголовка Contact с URI SIPS, а UAS принимал бы запросы, адресованные с SIP или SIPS Request-URI. UA с политикой «без SIPS» обращался бы к регистратору с SIP Request-URI, мог бы использовать TLS или не использовать его, регистрировался бы с AOR SIP и полем заголовка Contact с URI SIP, а UAS принимал бы запросы, адресованные с SIP Request-URI.
If a UAS needs to reject a request because the URIs are used inconsistently (e.g., the Request-URI is a SIPS URI, but the Contact header field is a SIP URI), the UAS MUST reject the request with a 400 (Bad Request) response.
Если UAS необходимо отклонить запрос из-за несогласованного использования URI (например, Request-URI является URI SIPS, а поле заголовка Contact — URI SIP), UAS ДОЛЖЕН отклонить запрос ответом 400 (Bad Request).
When a target refresh occurs within a dialog (e.g., re-INVITE request, UPDATE request), the UAS MUST include a Contact header field with a SIPS URI if the original request used a SIPS Request-URI. To emphasize what is already defined in [RFC3261], UASs MUST NOT use the "transport=tls" parameter.
Когда в диалоге происходит обновление цели (например, запрос re-INVITE или UPDATE), UAS ДОЛЖЕН включить поле заголовка Contact с URI SIPS, если исходный запрос использовал SIPS Request-URI. Подчеркнём уже определённое в [RFC3261]: UAS НЕ ДОЛЖНЫ использовать параметр «transport=tls».
5.2. Registrar Behavior
5.2. Поведение регистратора
The UAC registers Contacts header fields to either a SIPS or a SIP AOR. From a routing perspective, it does not matter which one is used for registration as they identify the same resource. The registrar MUST consider AORs that are identical except for one having the SIP scheme and the other having the SIPS scheme to be equivalent.
UAC регистрирует поля заголовка Contact на AOR SIPS или на AOR SIP. С точки зрения маршрутизации неважно, какой из них используется для регистрации, поскольку они идентифицируют один и тот же ресурс. Регистратор ДОЛЖЕН считать эквивалентными AOR, совпадающие во всём, кроме схемы: у одного — SIP, у другого — SIPS.
A registrar MUST accept a binding to a SIPS Contact header field only if all the appropriate URIs are of the SIPS scheme; otherwise, there could be an inadvertent binding of a secure resource (SIPS) to an unsecured one (SIP). This includes the Request-URI and the Contacts and all the Path header fields, but does not include the From and To header fields. If the URIs are not of the proper SIPS scheme, the registrar MUST reject the REGISTER with a 400 (Bad Request).
Регистратор ДОЛЖЕН принимать привязку к полю заголовка Contact с URI SIPS, только если все соответствующие URI имеют схему SIPS; в противном случае могла бы возникнуть непреднамеренная привязка защищённого ресурса (SIPS) к незащищённому (SIP). Это относится к Request-URI, полям заголовка Contact и всем полям заголовка Path, но не к полям заголовка From и To. Если URI не имеют надлежащей схемы SIPS, регистратор ДОЛЖЕН отклонить REGISTER ответом 400 (Bad Request).
A registrar can return a service route [RFC3608] and impose some constraints on whether or not TLS will be mandatory on specific hops. For example, if the topmost entry in the Path header field returned by the registrar is a SIPS URI, the registrar is telling the UAC that TLS is to be used for the first hop, even if the Request-URI is SIP.
Регистратор может возвращать служебный маршрут [RFC3608] и накладывать некоторые ограничения на то, будет ли TLS обязателен на конкретных участках. Например, если самая верхняя запись в поле заголовка Path, возвращаемом регистратором, является URI SIPS, регистратор сообщает UAC, что на первом участке должен использоваться TLS, даже если Request-URI имеет схему SIP.
If a UA registered with a SIPS Contact header field, the registrar returning a service route [RFC3608] MUST return a service route consisting of SIP URIs if the intent of the registrar is to allow both SIP and SIPS to be used in requests sent by that client. If a UA registers with a SIPS Contact header field, the registrar returning a service route MUST return a service route consisting of SIPS URIs if the intent of the registrar is to allow only SIPS URIs to be used in requests sent by that UA.
Если UA зарегистрировался с полем заголовка Contact, содержащим URI SIPS, регистратор, возвращающий служебный маршрут [RFC3608], ДОЛЖЕН вернуть служебный маршрут, состоящий из URI SIP, если намерение регистратора — разрешить использование как SIP, так и SIPS в запросах, отправляемых этим клиентом. Если UA регистрируется с полем заголовка Contact, содержащим URI SIPS, регистратор, возвращающий служебный маршрут, ДОЛЖЕН вернуть служебный маршрут, состоящий из URI SIPS, если намерение регистратора — разрешить использование только URI SIPS в запросах, отправляемых этим UA.
5.2.1. GRUU
5.2.1. GRUU
When a GRUU [RFC5627] is assigned to an instance ID/AOR pair through registration, the registrar MUST assign both a SIP GRUU and a SIPS GRUU. If the Contact header field in the REGISTER request contains a SIP URI, the registrar MUST return the SIP version of the GRUU. If the Contact header field in the REGISTER request contains a SIPS URI, the registrar MUST return the SIPS version of the GRUU.
Когда GRUU [RFC5627] назначается паре «идентификатор экземпляра/AOR» посредством регистрации, регистратор ДОЛЖЕН назначить как GRUU для SIP, так и GRUU для SIPS. Если поле заголовка Contact в запросе REGISTER содержит URI SIP, регистратор ДОЛЖЕН вернуть версию GRUU для SIP. Если поле заголовка Contact в запросе REGISTER содержит URI SIPS, регистратор ДОЛЖЕН вернуть версию GRUU для SIPS.
5.3. Proxy Behavior
5.3. Поведение прокси
Proxies MUST NOT use the last-hop exception of [RFC3261] when forwarding or retargeting a request to the last hop. Specifically, when a proxy receives a request with a SIPS Request-URI, the proxy MUST only forward or retarget the request to a SIPS Request-URI. If the target UAS had registered previously using a SIP Contact header field instead of a SIPS Contact header field, the proxy MUST NOT forward the request to the URI indicated in the Contact header field. If the proxy needs to reject the request for that reason, the proxy MUST reject it with a 480 (Temporarily Unavailable) response. In this case, the proxy SHOULD include a Warning header with warn-code 380 "SIPS Not Allowed".
Прокси НЕ ДОЛЖНЫ использовать исключение для последнего участка из [RFC3261] при пересылке запроса на последний участок или перенацеливании на него. В частности, когда прокси получает запрос с SIPS Request-URI, он ДОЛЖЕН пересылать или перенацеливать запрос только на SIPS Request-URI. Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIP, а не URI SIPS, прокси НЕ ДОЛЖЕН пересылать запрос на URI, указанный в поле заголовка Contact. Если прокси необходимо отклонить запрос по этой причине, он ДОЛЖЕН отклонить его ответом 480 (Temporarily Unavailable). В этом случае прокси СЛЕДУЕТ включить поле заголовка Warning с кодом предупреждения 380 «SIPS Not Allowed».
Proxies SHOULD transport requests using a SIP URI over TLS when it is possible to set up a TLS connection, or reuse an existing one. [RFC5626], for example, allows for re-using an existing TLS connection. Some proxies could have policies that prohibit sending any request over anything but TLS.
Прокси СЛЕДУЕТ передавать запросы с URI SIP через TLS, когда можно установить TLS-соединение или повторно использовать существующее. [RFC5626], например, допускает повторное использование существующего TLS-соединения. Некоторые прокси могут иметь политики, запрещающие отправлять любые запросы иначе как через TLS.
When a proxy receives a request with a SIP Request-URI, the proxy MUST NOT forward the request to a SIPS Request-URI. If the target UAS had registered previously using a SIPS Contact header field, and the proxy decides to forward the request, the proxy MUST replace that SIPS scheme with a SIP scheme while leaving the rest of the URI as is, and use the resulting URI as the Request-URI of the forwarded request. The proxy MUST use TLS to forward the request to the UAS. Some proxies could have a policy of not forwarding at all requests using a non-SIPS Request-URI if the UAS had registered using a SIPS Contact header field. If the proxy elects to reject the request because it has such a policy or because it is not capable of establishing a TLS connection, the proxy MAY reject it with a 480 (Temporarily Unavailable) response with a Warning header with warn- code 381 "SIPS Required".
Когда прокси получает запрос с SIP Request-URI, он НЕ ДОЛЖЕН пересылать запрос на SIPS Request-URI. Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIPS, и прокси решает переслать запрос, он ДОЛЖЕН заменить схему SIPS на схему SIP, оставив остальную часть URI без изменений, и использовать полученный URI в качестве Request-URI пересылаемого запроса. Прокси ДОЛЖЕН использовать TLS для пересылки запроса на UAS. Некоторые прокси могут иметь политику вообще не пересылать запросы с Request-URI, не являющимся SIPS, если UAS зарегистрировался с полем заголовка Contact с URI SIPS. Если прокси решает отклонить запрос из-за такой политики или из-за невозможности установить TLS-соединение, он МОЖЕТ отклонить его ответом 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 381 «SIPS Required».
If a proxy needs to reject a request because the URIs are used inconsistently (e.g., the Request-URI is a SIPS URI, but the Contact header field is a SIP URI), the proxy SHOULD use response code 400 (Bad Request).
Если прокси необходимо отклонить запрос из-за несогласованного использования URI (например, Request-URI является URI SIPS, а поле заголовка Contact — URI SIP), прокси СЛЕДУЕТ использовать код ответа 400 (Bad Request).
It is RECOMMENDED that the proxy use the outbound proxy procedures defined in [RFC5626] for supporting UACs that cannot provide a certificate for establishing a TLS connection (i.e., when server-side authentication is used).
РЕКОМЕНДУЕТСЯ, чтобы прокси использовал процедуры исходящего прокси, определённые в [RFC5626], для поддержки UAC, которые не могут предоставить сертификат для установления TLS-соединения (то есть когда используется аутентификация на стороне сервера).
When a proxy sends a request using a SIPS Request-URI and receives a 3XX response with a SIP Contact header field, or a 416 response, or a 480 (Temporarily Unavailable) response with a Warning header with warn-code 380 "SIPS Not Allowed" response, the proxy MUST NOT recurse on the response. In this case, the proxy SHOULD forward the best response instead of recursing, in order to allow for the UAC to take the appropriate action. When a proxy sends a request using a SIP Request-URI and receives a 3XX response with a SIPS Contact header field, or a 480 (Temporarily Unavailable) response with a Warning header with warn-code 381 "SIPS Required", the proxy MUST NOT recurse on the response. In this case, the proxy SHOULD forward the best response instead of recursing, in order to allow for the UAC to take the appropriate action.
Когда прокси отправляет запрос с SIPS Request-URI и получает ответ 3XX с полем заголовка Contact, содержащим URI SIP, либо ответ 416, либо ответ 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 380 «SIPS Not Allowed», прокси НЕ ДОЛЖЕН выполнять рекурсию по этому ответу. В этом случае прокси СЛЕДУЕТ переслать наилучший ответ вместо рекурсии, чтобы дать UAC возможность предпринять надлежащие действия. Когда прокси отправляет запрос с SIP Request-URI и получает ответ 3XX с полем заголовка Contact, содержащим URI SIPS, либо ответ 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 381 «SIPS Required», прокси НЕ ДОЛЖЕН выполнять рекурсию по этому ответу. В этом случае прокси СЛЕДУЕТ переслать наилучший ответ вместо рекурсии, чтобы дать UAC возможность предпринять надлежащие действия.
To emphasize what is already defined in [RFC3261], proxies MUST NOT use the "transport=tls" parameter.
Подчеркнём уже определённое в [RFC3261]: прокси НЕ ДОЛЖНЫ использовать параметр «transport=tls».
5.4. Redirect Server Behavior
5.4. Работа сервера перенаправления
Using a redirect server with TLS instead of using a proxy has some limitations that have to be taken into account. Since there is no pre-established connection between the proxy and the UAS (such as with [RFC5626]), it is only appropriate for scenarios where inbound connections are allowed. For example, it could be used in a server- to-server environment (redirect server or proxy server) where TLS mutual authentication is used, and where there are no NAT traversal issues. A redirect server would not be able to redirect to an entity that does not have a certificate. A redirect server might not be usable if there is a NAT between the server and the UAS.
Использование сервера перенаправления с TLS вместо прокси имеет некоторые ограничения, которые необходимо учитывать. Поскольку между прокси и UAS нет заранее установленного соединения (как в случае [RFC5626]), это подходит только для сценариев, где допускаются входящие соединения. Например, это можно применять в среде «сервер-сервер» (сервер перенаправления или прокси-сервер), где используется взаимная аутентификация TLS и отсутствуют проблемы прохождения NAT. Сервер перенаправления не смог бы перенаправить запрос объекту, у которого нет сертификата. Сервер перенаправления может оказаться непригодным, если между сервером и UAS есть NAT.
When a redirect server receives a request with a SIP Request-URI, the redirect server MAY redirect with a 3XX response to either a SIP or a SIPS Contact header field. If the target UAS had registered previously using a SIPS Contact header field, the redirect server SHOULD return a SIPS Contact header field if it is in an environment where TLS is usable (as described in the previous paragraph). If the target UAS had registered previously using a SIP Contact header field, the redirect server MUST return a SIP Contact header field in a 3XX response if it redirects the request.
Когда сервер перенаправления получает запрос с SIP Request-URI, он МОЖЕТ перенаправить его ответом 3XX на поле заголовка Contact с URI SIP или URI SIPS. Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIPS, сервер перенаправления СЛЕДУЕТ вернуть поле заголовка Contact с URI SIPS, если он находится в среде, где TLS применим (как описано в предыдущем абзаце). Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIP, сервер перенаправления ДОЛЖЕН вернуть поле заголовка Contact с URI SIP в ответе 3XX, если он перенаправляет запрос.
When a redirect server receives a request with a SIPS Request-URI, the redirect server MAY redirect with a 3XX response to a SIP or a SIPS Contact header field. If the target UAS had registered previously using a SIPS Contact header field, the redirect server SHOULD return a SIPS Contact header field if it is in an environment where TLS is usable. If the target UAS had registered previously using a SIP Contact header field, the redirect server MUST return a SIP Contact header field in a 3XX response if it chooses to redirect; otherwise, the UAS MAY reject the request with a 480 (Temporarily Unavailable) response with a Warning header with warn-code 380 "SIPS Not Allowed". If a redirect server redirects to a UAS that it has no knowledge of (e.g., an AOR in a different domain), the Contact header field could be of any scheme. If a redirect server needs to reject a request because the URIs are used inconsistently (e.g., the Request-URI is a SIPS URI, but the Contact header field is a SIP URI), the redirect server SHOULD use response code 400 (Bad Request).
Когда сервер перенаправления получает запрос с SIPS Request-URI, он МОЖЕТ перенаправить его ответом 3XX на поле заголовка Contact с URI SIP или URI SIPS. Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIPS, сервер перенаправления СЛЕДУЕТ вернуть поле заголовка Contact с URI SIPS, если он находится в среде, где TLS применим. Если целевой UAS ранее зарегистрировался с полем заголовка Contact, содержащим URI SIP, сервер перенаправления ДОЛЖЕН вернуть поле заголовка Contact с URI SIP в ответе 3XX, если он решает перенаправить запрос; в противном случае UAS МОЖЕТ отклонить запрос ответом 480 (Temporarily Unavailable) с полем заголовка Warning и кодом предупреждения 380 «SIPS Not Allowed». Если сервер перенаправления перенаправляет запрос UAS, о котором он ничего не знает (например, AOR в другом домене), поле заголовка Contact может иметь любую схему. Если серверу перенаправления необходимо отклонить запрос из-за несогласованного использования URI (например, Request-URI является URI SIPS, а поле заголовка Contact — URI SIP), ему СЛЕДУЕТ использовать код ответа 400 (Bad Request).
To emphasize what is already defined in [RFC3261], redirect servers MUST NOT use the "transport=tls" parameter.
Подчеркнём уже определённое в [RFC3261]: серверы перенаправления НЕ ДОЛЖНЫ использовать параметр «transport=tls».

Both Registrar/Authoritative Proxy B and Edge Proxy B insert themselves in the Record-Route. Bob's phone's policy is to accept calls to SIP and SIPS (i.e., "best effort"), so both his PC client and his SIP phone ring simultaneously. Bob answers on his SIP phone, and the forked call leg to the PC client is canceled.

Алиса адресовала запрос Бобу с SIP Request-URI (sip:bob@example.com), поэтому регистратор/авторитетный прокси B определяет, что вызов нужно направить как на bobpc (который зарегистрировался с полем заголовка Contact, содержащим URI SIP), так и на bobphone (который зарегистрировался с полем заголовка Contact, содержащим URI SIPS), и, следовательно, запрос разветвляется на sip:bob@bobpc.example.com и sip:bob@bobphone.example.com через пограничный прокси B. 7. Further Considerations
7. Дополнительные соображения
SIP [RFC3261] itself introduces some complications with using SIPS, for example, when Record-Route is not used. When a SIPS URI is used in a Contact header field in a dialog-initiating request and Record- Route is not used, that SIPS URI might not be usable by the other end. If the other end does not support SIPS and/or TLS, it will not be able to use it. The last-hop exception is an example of when this can occur. In this case, using Record-Route so that the requests are sent through proxies can help in making it work. Another example is that even in a case where the Contact header field is a SIPS URI, no Record-Route is used, and the far end supports SIPS and TLS, it might still not be possible for the far end to establish a TLS connection with the SIP originating end if the certificate cannot be validated by the far end. This could typically be the case if the originating end was using server-side authentication as described below, or if the originating end is not using a certificate that can be validated.
Сам SIP [RFC3261] вносит некоторые сложности в использование SIPS, например когда Record-Route не применяется. Когда URI SIPS используется в поле заголовка Contact в запросе, инициирующем диалог, и Record-Route не применяется, этот URI SIPS может оказаться непригодным для другой стороны. Если другая сторона не поддерживает SIPS и/или TLS, она не сможет его использовать. Исключение для последнего участка — пример ситуации, когда это может произойти. В этом случае использование Record-Route, чтобы запросы проходили через прокси, может помочь обеспечить работоспособность. Другой пример: даже если поле заголовка Contact содержит URI SIPS, Record-Route не используется, а удалённая сторона поддерживает SIPS и TLS, удалённой стороне всё равно может быть невозможно установить TLS-соединение с инициирующей стороной SIP, если сертификат не может быть проверен удалённой стороной. Обычно это возможно, если инициирующая сторона использовала аутентификацию на стороне сервера, как описано ниже, или если инициирующая сторона использует сертификат, который невозможно проверить.
TLS itself has a significant impact on how SIPS can be used. Server- side authentication (where the server side provides its certificate but the client side does not) is typically used between a SIP end- user device acting as the TLS client side (e.g., a phone or a personal computer) and its SIP server (proxy or registrar) acting as the TLS server side. TLS mutual authentication (where both the client side and the server side provide their respective certificates) is typically used between SIP servers (proxies, registrars), or statically configured devices such as PSTN gateways or media servers. In the mutual authentication model, for two entities to be able to establish a TLS connection, it is required that both sides be able to validate each other's certificates, either by static configuration or by being able to recurse to a valid root certificate. With server-side authentication, only the client side is capable of validating the server side's certificate, as the client side does not provide a certificate. The consequences of all this are that whenever a SIPS URI is used to establish a TLS connection, it is expected to be possible for the entity establishing the connection (the client) to validate the certificate from the server side. For server-side authentication, [RFC5626] is the recommended approach.
Сам TLS существенно влияет на то, как можно использовать SIPS. Аутентификация на стороне сервера (когда сервер предоставляет свой сертификат, а клиент — нет) обычно применяется между устройством конечного пользователя SIP, выступающим в роли TLS-клиента (например, телефоном или персональным компьютером), и его SIP-сервером (прокси или регистратором), выступающим в роли TLS-сервера. Взаимная аутентификация TLS (когда и клиент, и сервер предоставляют свои сертификаты) обычно применяется между SIP-серверами (прокси, регистраторами) или статически настроенными устройствами, такими как шлюзы PSTN или медиасерверы. В модели взаимной аутентификации для установления TLS-соединения двумя объектами требуется, чтобы обе стороны могли проверить сертификаты друг друга — либо путём статической настройки, либо путём рекурсивного перехода к действительному корневому сертификату. При аутентификации на стороне сервера только клиент может проверить сертификат сервера, поскольку клиент сертификат не предоставляет. Следствие всего этого таково: всякий раз, когда URI SIPS используется для установления TLS-соединения, ожидается, что объект, устанавливающий соединение (клиент), сможет проверить сертификат сервера. При аутентификации на стороне сервера рекомендуемым подходом является [RFC5626].
For mutual authentication, one needs to ensure that the architecture of the network is such that connections are made between entities that have access to each other's certificates. Record-Route [RFC3261] and Path [RFC3327] are very useful in ensuring that previously established TLS connections can be reused. Other mechanisms might also be used in certain circumstances: for example, using root certificates that are widely recognized allows for more easily created TLS connections.
При взаимной аутентификации необходимо обеспечить такую архитектуру сети, при которой соединения устанавливаются между объектами, имеющими доступ к сертификатам друг друга. Record-Route [RFC3261] и Path [RFC3327] очень полезны для обеспечения возможности повторного использования ранее установленных TLS-соединений. В определённых обстоятельствах могут применяться и другие механизмы: например, использование широко признанных корневых сертификатов позволяет проще создавать TLS-соединения.
