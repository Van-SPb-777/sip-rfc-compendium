Abstract
Аннотация
This document defines a new header for use with SIP multi-party applications and call control. The Join header is used to logically join an existing SIP dialog with a new SIP dialog. This primitive can be used to enable a variety of features, for example: "Barge-In", answering-machine-style "Message Screening" and "Call Center Monitoring". Note that definition of these example features is non- normative.
Настоящий документ определяет новый заголовок для использования в многопользовательских приложениях SIP и управлении вызовами. Заголовок Join используется для логического присоединения существующего диалога SIP к новому диалогу SIP. Этот примитив позволяет реализовать различные функции, например «Barge-In» (вклинивание в разговор), «Message Screening» в стиле автоответчика и «Call Center Monitoring» (мониторинг центра обработки вызовов). Обратите внимание, что определения этих примерных функций не являются нормативными.
1. Introduction
1. Введение
This document describes a SIP [1] extension header field as part of the SIP multiparty applications architecture framework [12]. The Join header is used to logically join an existing SIP dialog with a new SIP dialog. This is especially useful in peer-to-peer call control environments.
Настоящий документ описывает расширение поля заголовка SIP [1] в рамках архитектурной концепции многопартийных приложений SIP [12]. Заголовок Join используется для логического присоединения существующего диалога SIP к новому диалогу SIP. Это особенно полезно в средах управления вызовами «равный с равным».
One use of the "Join" header is to insert a new participant into a multimedia conversation (which may be a two-party call or a SIP conference [15]). While this functionality is already available using 3rd party call control [17], style call control, the 3pcc model requires a central point of control which may not be desirable in many environments. As such, a method of performing these same call control primitives in a distributed, peer-to-peer fashion is very desirable.
Одно из применений заголовка «Join» — вставка нового участника в мультимедийный разговор (который может быть двухсторонним вызовом или конференцией SIP [15]). Хотя эта функциональность уже доступна при управлении вызовами по модели стороннего управления вызовами [17], модель 3pcc требует центральной точки управления, что может быть нежелательно во многих средах. Поэтому очень желателен способ выполнения тех же примитивов управления вызовами распределённым образом, по принципу «равный с равным».
Use of an explicit Join header is needed in some cases instead of addressing an INVITE to a conference URI for the following reasons:
В некоторых случаях необходимо использовать явный заголовок Join вместо адресации INVITE на URI конференции по следующим причинам:
o A conference may not yet exist--the new invitation may be trying to join an ordinary two-party call.
o Конференции может ещё не существовать — новое приглашение может пытаться присоединиться к обычному двухстороннему вызову.
o The party joining may not know if the dialog it wants to join is part of a conference.
o Присоединяющаяся сторона может не знать, входит ли нужный ей диалог в конференцию.
o The party joining may not know the conference URI.
o Присоединяющаяся сторона может не знать URI конференции.
The Join header enables services such as barge-in, real-time message screening, and call center monitoring in a distributed peer-to-peer way. This list of services is not exhaustive.
Заголовок Join позволяет оказывать такие услуги, как вклинивание в разговор, просмотр сообщений в реальном времени и мониторинг центра обработки вызовов распределённо, по принципу «равный с равным». Список этих услуг не исчерпывающий.
For example, the Boss has an established 2-party conversation with a Customer, and using some out-of-band mechanism (e.g., voice, gestures, or email) asks an Assistant to join the conversation. The Assistant sends an INVITE with a Join header to the Boss with the dialog information for the established dialog. The Assistant obtained this information from some other mechanism, for example a web-page, an instant message, or from the SIP session dialog package [13].
Например, у Начальника установлен двухсторонний разговор с Клиентом, и он, используя некоторый внешний механизм (например, голос, жесты или электронную почту), просит Помощника присоединиться к разговору. Помощник отправляет Начальнику INVITE с заголовком Join и информацией о диалоге для установленного диалога. Помощник получил эту информацию с помощью другого механизма, например веб-страницы, мгновенного сообщения или пакета состояния диалога сеанса SIP [13].
Assistant Boss Customer | callid: 4@A | callid: 7@c | | | | | |<============>| | | | |INVITE------>| | |Join: 7@c | | | |reINVITE----->| |<----200-----|<----200------| |-----ACK---->|<----ACK------| | | | | .. begins mixing .. | | | | |<===========>|<============>| |<::::::::::::::::::::::::::>|
Assistant Boss Customer | callid: 4@A | callid: 7@c | | | | | |<============>| | | | |INVITE------>| | |Join: 7@c | | | |reINVITE----->| |<----200-----|<----200------| |-----ACK---->|<----ACK------| | | | | .. begins mixing .. | | | | |<===========>|<============>| |<::::::::::::::::::::::::::>|
Note that this operation effectively creates a new conference. The Boss needs to cause a new conference to start (and consequently create or obtain a new conference URI). In our example, the Boss mixes all media locally, so it needs to generate a new conference URI, return the conference URI as the Contact to the Join INVITE (with the "isfocus" Contact header field parameter as defined in [6], and reINVITE or UPDATE [22] the Customer with the conference URI as the new Contact. This scenario is also discussed in more detail in [16].
Обратите внимание, что эта операция фактически создаёт новую конференцию. Начальник должен инициировать запуск новой конференции (и, следовательно, создать или получить новый URI конференции). В нашем примере Начальник смешивает все медиа локально, поэтому ему нужно сгенерировать новый URI конференции, вернуть этот URI конференции как Contact в ответе на INVITE с заголовком Join (с параметром поля заголовка Contact «isfocus», как определено в [6]), а затем отправить Клиенту reINVITE или UPDATE [22] с URI конференции в качестве нового Contact. Этот сценарий также более подробно рассматривается в [16].
2. Conventions
2. Соглашения
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [2].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует интерпретировать так, как описано в RFC 2119 [2].
This document refers frequently to the terms "confirmed dialog" and "early dialog". These are defined in Section 12 of SIP [1].
Настоящий документ часто ссылается на термины «подтверждённый диалог» и «ранний диалог». Они определены в разделе 12 SIP [1].
3. Applicability of RFC 2804 ("Raven")
3. Применимость RFC 2804 («Raven»)
This primitive can be used to create services which are used for monitoring purposes, however these services do not meet the definition of a wiretap according to RFC 2804 [14]. The definition from RFC 2804 is included here:
Этот примитив может использоваться для создания услуг, применяемых для целей мониторинга, однако такие услуги не соответствуют определению прослушивания согласно RFC 2804 [14]. Определение из RFC 2804 приводится ниже:
Wiretapping is what occurs when information passed across the Internet from one party to one or more other parties is delivered to a third party:
Перехват — это когда информация, передаваемая по Интернету от одной стороны одной или нескольким другим сторонам, доставляется третьей стороне:
1. Without the sending party knowing about the third party
1. Без ведома отправляющей стороны о третьей стороне
2. Without any of the recipient parties knowing about the delivery to the third party
2. Без ведома кого-либо из получающих сторон о доставке данных третьей стороне
3. When the normal expectation of the sender is that the transmitted information will only be seen by the recipient parties or parties obliged to keep the information in confidence
3. Когда обычное ожидание отправителя состоит в том, что передаваемая информация будет видна только получающим сторонам или сторонам, обязанным сохранять информацию в тайне
4. When the third party acts deliberately to target the transmission of the first party, either because he is of interest, or because the second party's reception is of interest.
4. Когда третья сторона действует намеренно, нацеливаясь на передачу первой стороны, либо потому, что он представляет интерес, либо потому, что интерес представляет приём второй стороны.
Specifically, item 2 of this definition does not apply to this extension, as one party is always aware of a Join request and can even decline such requests. In addition, in many applications of this primitive, some or all of the other items may not apply. For example, in many call centers which handle financial transactions, all conversations are recorded with the full knowledge and expectation of all parties involved.
В частности, пункт 2 этого определения не применим к данному расширению, поскольку одна из сторон всегда знает о запросе Join и может даже отклонить такие запросы. Кроме того, во многих применениях этого примитива некоторые или все остальные пункты могут не применяться. Например, во многих центрах обработки вызовов, обрабатывающих финансовые транзакции, все разговоры записываются при полном знании и согласии всех участвующих сторон.
4. User Agent Server Behavior: Receiving a Join Header
4. Поведение сервера пользовательского агента: получение заголовка Join
The Join header contains information used to match an existing SIP dialog (call-id, to-tag, and from-tag). Upon receiving an INVITE with a Join header, the UA attempts to match this information with a confirmed or early dialog. The to-tag and from-tag parameters are matched as if they were tags present in an incoming request. In other words the to-tag parameter is compared to the local tag, and the from-tag parameter is compared to the remote tag.
Заголовок Join содержит информацию, используемую для сопоставления с существующим диалогом SIP (call-id, to-tag и from-tag). Получив INVITE с заголовком Join, UA пытается сопоставить эту информацию с подтверждённым или ранним диалогом. Параметры to-tag и from-tag сопоставляются так, как если бы они были тегами, присутствующими во входящем запросе. Иначе говоря, параметр to-tag сравнивается с локальным тегом, а параметр from-tag — с удалённым тегом.
If more than one Join header field is present in an INVITE, or if a Join header field is present in a request other than INVITE, the UAS MUST reject the request with a 400 Bad Request response.
Если в INVITE присутствует более одного поля заголовка Join или если поле заголовка Join присутствует в запросе, отличном от INVITE, UAS ДОЛЖЕН отклонить запрос с ответом 400 Bad Request.
The Join header has specific call control semantics. If both a Join header field and another header field with contradictory semantics (for example a Replaces [8] header field) are present in a request, the request MUST be rejected with a 400 "Bad Request" response.
Заголовок Join имеет специфическую семантику управления вызовами. Если в запросе одновременно присутствуют поле заголовка Join и другое поле заголовка с противоречащей семантикой (например, поле заголовка Replaces [8]), запрос ДОЛЖЕН быть отклонён с ответом 400 «Bad Request».
If the Join header field matches more than one dialog, the UA MUST act as if no match is found.
Если поле заголовка Join соответствует нескольким диалогам, UA ДОЛЖЕН действовать так, будто соответствие не найдено.
If no match is found, but the Request-URI in the INVITE corresponds to a conference URI, the UAS MUST ignore the Join header and continue processing the INVITE as if the Join header did not exist. This allows User Agents which receive an INVITE with Join to redirect the request directly to a conference URI. Otherwise if no match is found, the UAS rejects the INVITE and returns a 481 Call/Transaction Does Not Exist response. Likewise, if the Join header field matches a dialog which was not created with an INVITE, the UAS MUST reject the request with a 481 response.
Если соответствие не найдено, но Request-URI в INVITE соответствует URI конференции, UAS ДОЛЖЕН игнорировать заголовок Join и продолжить обработку INVITE так, как если бы заголовка Join не существовало. Это позволяет пользовательским агентам, получающим INVITE с Join, перенаправлять запрос непосредственно на URI конференции. В противном случае, если соответствие не найдено, UAS отклоняет INVITE и возвращает ответ 481 Call/Transaction Does Not Exist. Аналогично, если поле заголовка Join соответствует диалогу, который не был создан с помощью INVITE, UAS ДОЛЖЕН отклонить запрос с ответом 481.
If the Join header field matches a dialog which has already terminated, the UA SHOULD decline the request with a 603 Declined response.
Если поле заголовка Join соответствует диалогу, который уже завершён, UA СЛЕДУЕТ отклонить запрос с ответом 603 Declined.
If the Join header field matches an active dialog (n.b. unlike the Replaces header, the Join header has no limitation on its use with early dialogs), the UA MUST verify that the initiator of the new INVITE is authorized to join the matched dialog. If the initiator of the new INVITE has authenticated successfully as equivalent to the user who is being joined, then the join is authorized. For example, if the user being joined and the initiator of the joining dialog share the same credentials for Digest authentication [4], or they sign the join request with S/MIME [5] with the same private key and present the (same) corresponding certificate used in the original dialog, then the join is authorized.
Если поле заголовка Join соответствует активному диалогу (прим.: в отличие от заголовка Replaces, заголовок Join не имеет ограничений на использование с ранними диалогами), UA ДОЛЖЕН проверить, что инициатор нового INVITE уполномочен присоединиться к сопоставленному диалогу. Если инициатор нового INVITE успешно аутентифицирован как эквивалентный пользователю, к которому присоединяются, присоединение разрешено. Например, если пользователь, к которому присоединяются, и инициатор присоединяющего диалога имеют одинаковые учётные данные для Digest-аутентификации [4] или подписывают запрос присоединения с помощью S/MIME [5] одним и тем же закрытым ключом и предъявляют (тот же) соответствующий сертификат, использованный в исходном диалоге, присоединение разрешено.
Alternatively, the Referred-By mechanism [9] defines a mechanism that the UAS can use to verify that a join request was sent on behalf of the other participant in the matched dialog (in this case, triggered by a REFER request). If the join request contains a Referred-By header which corresponds to the user being joined, the UA SHOULD treat the join as if it was authorized by the joined party. The Referred-By header MUST reference a corresponding, valid Refererred- By Authenticated Identity Body [10]. The UA MAY apply other local policy to authorize the remainder of the request. In other words, the UAS may apply different policy to the joined dialog than was applied to the target dialog.
В качестве альтернативы механизм Referred-By [9] определяет механизм, с помощью которого UAS может проверить, что запрос присоединения был отправлен от имени другого участника сопоставленного диалога (в данном случае инициирован запросом REFER). Если запрос присоединения содержит заголовок Referred-By, соответствующий пользователю, к которому присоединяются, UA СЛЕДУЕТ рассматривать присоединение так, как если бы оно было разрешено присоединяемой стороной. Заголовок Referred-By ДОЛЖЕН содержать ссылку на соответствующий действительный Refererred-By Authenticated Identity Body [10]. UA МОЖЕТ применить другую локальную политику для авторизации остальной части запроса. Иначе говоря, UAS может применить к присоединяемому диалогу иную политику, чем к целевому диалогу.
The UA MAY also maintain a list of authorized entities who are allowed to join any dialog with certain characteristics (for example, all dialogs placed in the call center context of the UA). In addition, the UA MAY use other authorization mechanisms defined for this purpose in standards track extensions. For example, an extension could define a mechanism for transitively asserting authorization of a join.
UA МОЖЕТ также вести список уполномоченных субъектов, которым разрешено присоединяться к любому диалогу с определёнными характеристиками (например, ко всем диалогам, находящимся в контексте центра обработки вызовов данного UA). Кроме того, UA МОЖЕТ использовать другие механизмы авторизации, определённые для этой цели в расширениях уровня стандартов. Например, расширение могло бы определить механизм транзитивного подтверждения авторизации присоединения.
If authorization is successful, the UA attempts to accept the new INVITE, and assign any mixing or conferencing resources necessary to complete the join. If the UA cannot accept the new INVITE (for example: it cannot establish required QoS or keying, or it has incompatible media), the UA MUST return an appropriate error response and MUST leave the matched dialog unchanged. A User Agent that accepts a Join header needs to setup dialogs or conferences such that the requesting UAC is logically added to the conversation space associated with the matched dialog. Any dialogs which are already logically associated with the matched dialog in the same conversation space are included as well. For a detailed description of various conferencing mechanisms that could be used to handle a Join, please consult the SIP conferencing framework [15].
При успешной авторизации UA пытается принять новый INVITE и выделить любые ресурсы смешивания или конференции, необходимые для завершения присоединения. Если UA не может принять новый INVITE (например, не может обеспечить требуемое QoS или ключи либо имеет несовместимые медиа), UA ДОЛЖЕН вернуть соответствующий ответ об ошибке и ДОЛЖЕН оставить сопоставленный диалог без изменений. Пользовательский агент, принимающий заголовок Join, должен настроить диалоги или конференции так, чтобы запрашивающий UAC был логически добавлен в пространство разговора, связанное с сопоставленным диалогом. Все диалоги, уже логически связанные с сопоставленным диалогом в том же пространстве разговора, также включаются. Подробное описание различных механизмов конференц-связи, которые можно использовать для обработки Join, см. в архитектуре конференций SIP [15].
If the UAS has sufficient resources to locally handle the Join request, the UAS SHOULD accept the Join request and perform the appropriate media mixing or combining. The UAS MAY rearrange appropriate dialogs instead as described below, based on some local policy.
Если UAS располагает достаточными ресурсами для локальной обработки запроса Join, UAS СЛЕДУЕТ принять запрос Join и выполнить соответствующее смешивание или объединение медиа. Вместо этого UAS МОЖЕТ, исходя из некоторой локальной политики, перестроить соответствующие диалоги, как описано ниже.
If the UAS does not have sufficient resources locally to handle the request, or does not wish to use these local resources, but is aware of other resources which could be used to satisfy the request (e.g., a centralized conference server), the UA SHOULD create a conference using this resource (e.g., INVITE the conference server to obtain a conference URI), redirect the requestor to this resource, and request other participants in the same conversation space to use this resource. The UA MAY use any appropriate mechanism to transition participants to the new resource (e.g., 3xx response, 3rd-party call control reinvitiations, REFER requests, or reinvitations to a multicast group). The UA SHOULD only use mechanisms which are expected to be acceptable to the other participants. For example, the UA SHOULD NOT attempt to transition the participants to a multicast group unless the UA can reasonably expect that all the participants can support multicast.
Если UAS не располагает достаточными локальными ресурсами для обработки запроса или не желает использовать эти локальные ресурсы, но знает о других ресурсах, которые можно использовать для удовлетворения запроса (например, централизованный сервер конференций), UA СЛЕДУЕТ создать конференцию с использованием этого ресурса (например, отправить INVITE серверу конференций для получения URI конференции), перенаправить запросителя на этот ресурс и попросить других участников в том же пространстве разговора использовать этот ресурс. UA МОЖЕТ использовать любой подходящий механизм для перевода участников на новый ресурс (например, ответ 3xx, повторные приглашения при стороннем управлении вызовами, запросы REFER или повторные приглашения в группу многоадресной рассылки). UA СЛЕДУЕТ использовать только механизмы, которые, как ожидается, будут приемлемы для других участников. Например, UA НЕ СЛЕДУЕТ пытаться перевести участников в группу многоадресной рассылки, если UA не может разумно ожидать, что все участники смогут поддерживать многоадресную рассылку.
If the UAS is incapable of satisfying the Join request, it MUST return a 488 "Not Acceptable Here" response.
Если UAS не способен удовлетворить запрос Join, он ДОЛЖЕН вернуть ответ 488 «Not Acceptable Here».
5. User Agent Client Behavior: Sending a Join header
5. Поведение клиента пользовательского агента: отправка заголовка Join
A User Agent that wishes to add a new dialog of its own to a single existing early or confirmed dialog and any associated dialogs or conferences, MAY send the target User Agent an INVITE request containing a Join header field. The UAC places the Call-ID, to-tag, and from-tag information for the target dialog in a single Join header field and sends the new INVITE to the target.
Пользовательский агент, желающий добавить свой новый диалог к одному существующему раннему или подтверждённому диалогу и любым связанным с ним диалогам или конференциям, МОЖЕТ отправить целевому пользовательскому агенту запрос INVITE, содержащий поле заголовка Join. UAC помещает информацию Call-ID, to-tag и from-tag целевого диалога в одно поле заголовка Join и отправляет новый INVITE цели.
If the User Agent receives a 300-class response, and acts on this response by sending an INVITE to a Contact in the response, this redirected INVITE MUST contain the same Join header which was present in the original request. Although this is unusual, this allows INVITE requests with a Join header to be redirected before reaching the target UAS. Note that use of the Join mechanism does not provide a way to match multiple dialogs, nor does it provide a way to match an entire call, an entire transaction, or to follow a chain of proxy forking logic.
Если пользовательский агент получает ответ класса 300 и реагирует на него, отправляя INVITE на один из Contact из ответа, этот перенаправленный INVITE ДОЛЖЕН содержать тот же заголовок Join, который присутствовал в исходном запросе. Хотя это необычно, это позволяет перенаправлять запросы INVITE с заголовком Join до достижения целевого UAS. Обратите внимание, что использование механизма Join не даёт способа сопоставить несколько диалогов, а также не позволяет сопоставить весь вызов, всю транзакцию или проследовать по цепочке логики разветвления прокси.
6. Proxy behavior
6. Поведение прокси
Proxy Servers do not require any new behavior to support this extension. They simply pass the Join header field transparently as described in the SIP specification.
Прокси-серверы не требуют нового поведения для поддержки этого расширения. Они просто передают поле заголовка Join прозрачно, как описано в спецификации SIP.
Note that it is possible for a proxy (especially when forking based on some application layer logic, such as caller screening or time- of-day routing) to forward an INVITE request containing a Join header field to a completely orthogonal set of Contacts than the original request it was intended to replace. In this case, the INVITE request with the Join header field will fail.
Обратите внимание, что прокси (особенно при разветвлении на основе некоторой логики прикладного уровня, такой как отбор вызывающих или маршрутизация по времени суток) может переслать запрос INVITE, содержащий поле заголовка Join, совершенно другому набору Contact, отличному от исходного запроса, который предполагалось заменить. В этом случае запрос INVITE с полем заголовка Join потерпит неудачу.
7. Syntax
7. Синтаксис
7.1. The Join Header
7.1. Заголовок Join
The Join header field indicates that a new dialog (created by the INVITE in which the Join header field in contained) should be joined with a dialog identified by the header field, and any associated dialogs or conferences. It is a request header only, and defined only for INVITE requests. The Join header field MAY be encrypted as part of end-to-end encryption. Only a single Join header field value may be present in a SIP request
Поле заголовка Join указывает, что новый диалог (создаваемый INVITE, в котором содержится это поле заголовка) следует присоединить к диалогу, идентифицированному этим полем заголовка, и к любым связанным с ним диалогам или конференциям. Это поле заголовка только запроса, определённое только для запросов INVITE. Поле заголовка Join МОЖЕТ быть зашифровано в рамках сквозного шифрования. В запросе SIP может присутствовать только одно значение поля заголовка Join.

9. Security Considerations
9. Вопросы безопасности
The extension specified in this document significantly changes the relative security of SIP devices. Currently in SIP, even if an eavesdropper learns the Call-ID, To, and From headers of a dialog, they cannot easily modify or destroy that dialog if Digest authentication or end-to-end message integrity are used.
Расширение, определённое в настоящем документе, существенно меняет относительную безопасность устройств SIP. В настоящее время в SIP, даже если подслушивающий узнает заголовки Call-ID, To и From диалога, он не может легко изменить или уничтожить этот диалог, если используются Digest-аутентификация или сквозная целостность сообщений.
This extension can be used to insert or monitor potentially sensitive content in a multimedia conversation. As such, invitations with the Join header MUST only be accepted if the peer requesting replacement has been properly authenticated using a standard SIP mechanism (Digest or S/MIME), and authorized to be joined with the target dialog. (All SIP implementations are already required to support Digest Authentication.) Generally authorization for joins are configured as a matter of local policy as long-duration persistent relationships.
Это расширение можно использовать для вставки или мониторинга потенциально конфиденциального содержимого в мультимедийном разговоре. Поэтому приглашения с заголовком Join ДОЛЖНЫ приниматься только в том случае, если сторона, запрашивающая присоединение, была должным образом аутентифицирована с использованием стандартного механизма SIP (Digest или S/MIME) и уполномочена присоединиться к целевому диалогу. (Все реализации SIP уже обязаны поддерживать Digest-аутентификацию.) Как правило, авторизация присоединений настраивается в рамках локальной политики как долговременные постоянные отношения.
For example, the UAs used by call center agents might be configured with a list of identities who could join their calls (supervisors and any call center monitoring User Agents). Alternatively the call center agents might rely on transitive authorization assertions from a (shorter) list of authorized hosts (e.g., a certificate authority). For answering-machine-style message screening this is even easier. Presumably the user screening their messages already has some credentials with their messaging server.
Например, UA, используемые агентами центра обработки вызовов, могут быть настроены со списком идентичностей, которые могут присоединяться к их вызовам (супервизоры и любые пользовательские агенты мониторинга центра обработки вызовов). В качестве альтернативы агенты центра обработки вызовов могут полагаться на транзитивные утверждения об авторизации из (более короткого) списка уполномоченных хостов (например, центра сертификации). Для просмотра сообщений в стиле автоответчика это ещё проще. Предположительно, пользователь, просматривающий свои сообщения, уже имеет некоторые учётные данные на своём сервере обмена сообщениями.
Some mechanisms for obtaining the dialog information needed by the Join header (Call-ID, to-tag, and from-tag) include URIs on a web page, subscriptions to an appropriate event package, and notifications after a REFER request. Use of end-to-end security mechanisms to integrity protect and encrypt this information is also RECOMMENDED.
Некоторые механизмы получения информации о диалоге, необходимой заголовку Join (Call-ID, to-tag и from-tag), включают URI на веб-странице, подписки на соответствующий пакет событий и уведомления после запроса REFER. Также РЕКОМЕНДУЕТСЯ использовать механизмы сквозной безопасности для защиты целостности и шифрования этой информации.
This extension was designed to take advantage of future signature or authorization schemes defined by standards track extensions. In general, call control features would benefit considerably from such work. Section 4 describes specific mechanisms for authorization using Digest Authentication and S/MIME (RFC 3261) and Referred-by [9], the currently available capabilities in SIP.
Это расширение было разработано, чтобы воспользоваться будущими схемами подписи или авторизации, определёнными расширениями уровня стандартов. В целом функции управления вызовами значительно выиграли бы от такой работы. В разделе 4 описаны конкретные механизмы авторизации с использованием Digest-аутентификации и S/MIME (RFC 3261) и Referred-by [9] — возможностей, доступных в SIP в настоящее время.
