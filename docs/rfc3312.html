Abstract
Аннотация
This document defines a generic framework for preconditions, which are extensible through IANA registration. This document also discusses how network quality of service can be made a precondition for establishment of sessions initiated by the Session Initiation Protocol (SIP). These preconditions require that the participant reserve network resources before continuing with the session. We do not define new quality of service reservation mechanisms; these preconditions simply require a participant to use existing resource reservation mechanisms before beginning the session.
Настоящий документ определяет общую структуру для предусловий, которая может быть расширена посредством регистрации IANA. Настоящий документ также рассматривает, как сетевое качество обслуживания может быть сделано предусловием для установления сессий, инициированных протоколом инициирования сессий (SIP). Эти предусловия требуют, чтобы участник зарезервировал сетевые ресурсы до продолжения сессии. Мы не определяем новых механизмов резервирования качества обслуживания; эти предусловия просто требуют, чтобы участник использовал существующие механизмы резервирования ресурсов до начала сессии.
1. Introduction
1. Введение
Some architectures require that at session establishment time, once the callee has been alerted, the chances of a session establishment failure are minimum. One source of failure is the inability to reserve network resources for a session. In order to minimize "ghost rings", it is necessary to reserve network resources for the session before the callee is alerted. However, the reservation of network resources frequently requires learning the IP address, port, and session parameters from the callee. This information is obtained as a result of the initial offer/answer exchange carried in SIP. This exchange normally causes the "phone to ring", thus introducing a chicken-and-egg problem: resources cannot be reserved without performing an initial offer/answer exchange, and the initial offer/answer exchange can't be done without performing resource reservation. The solution is to introduce the concept of a precondition. A precondition is a set of constraints about the session which are introduced in the offer. The recipient of the offer generates an answer, but does not alert the user or otherwise proceed with session establishment. That only occurs when the preconditions are met. This can be known through a local event (such as a confirmation of a resource reservation), or through a new offer sent by the caller.
Некоторые архитектуры требуют, чтобы при установлении сессии, как только вызываемый был оповещён, вероятность сбоя установления сессии была минимальной. Одним из источников сбоя является невозможность зарезервировать сетевые ресурсы для сессии. Чтобы свести к минимуму «фантомные звонки», необходимо зарезервировать сетевые ресурсы для сессии до того, как вызываемый будет оповещён. Однако резервирование сетевых ресурсов часто требует узнать IP-адрес, порт и параметры сессии от вызываемого. Эта информация получается в результате начального обмена «предложение/ответ», передаваемого в SIP. Этот обмен обычно заставляет «телефон зазвонить», что порождает проблему курицы и яйца: ресурсы нельзя зарезервировать без выполнения начального обмена «предложение/ответ», а начальный обмен «предложение/ответ» нельзя выполнить без выполнения резервирования ресурсов. Решение состоит во введении понятия предусловия (precondition). Предусловие — это набор ограничений на сессию, которые вводятся в предложении. Получатель предложения формирует ответ, но не оповещает пользователя и иным образом не продолжает установление сессии. Это происходит только тогда, когда предусловия выполнены. Это может быть установлено посредством локального события (например, подтверждения резервирования ресурсов) либо посредством нового предложения, отправленного вызывающим.
This document deals with sessions that use SIP [1] as a signalling protocol and SDP [2] to describe the parameters of the session.
Настоящий документ имеет дело с сессиями, которые используют SIP [1] в качестве протокола сигнализации и SDP [2] для описания параметров сессии.
We have chosen to include the quality of service preconditions in the SDP description rather than in the SIP header because preconditions are stream specific.
Мы выбрали включение предусловий качества обслуживания в описание SDP, а не в заголовок SIP, потому что предусловия специфичны для потока.

3. Overview
3. Обзор
In order to ensure that session establishment does not take place until certain preconditions are met, we distinguish between two different state variables that affect a particular media stream: current status and desired status. This document defines the quality of service status.
Чтобы гарантировать, что установление сессии не произойдёт до выполнения определённых предусловий, мы различаем две различные переменные состояния, влияющие на конкретный медиапоток: текущее состояние и желаемое состояние. Настоящий документ определяет состояние качества обслуживания.
The desired status consists of a threshold for the current status. Session establishment stops until the current status reaches or surpasses this threshold. Once this threshold is reached or surpassed, session establishment resumes.
Желаемое состояние состоит из порога для текущего состояния. Установление сессии приостанавливается, пока текущее состояние не достигнет этого порога или не превысит его. Как только этот порог достигнут или превышен, установление сессии возобновляется.

Например, следующие значения текущего и желаемого состояния не позволили бы установлению сессии возобновиться:
current status = resources reserved in the send direction desired status = resources reserved in both (sendrecv) directions

On the other hand, the values of the example below would make session establishment resume:
С другой стороны, значения из примера ниже заставили бы установление сессии возобновиться:
current status = resources reserved in both (sendrecv) directions desired status = resources reserved in the send direction

These two state variables define a certain piece of state of a media stream the same way the direction attribute or the codecs in use define other pieces of state. Consequently, we treat these two new variables in the same way as other SDP media attributes are treated in the offer/answer model used by SIP [4]: they are exchanged between two user agents using an offer and an answer in order to have a shared view of the status of the session.
Эти две переменные состояния определяют определённый элемент состояния медиапотока так же, как атрибут направления или используемые кодеки определяют другие элементы состояния. Следовательно, мы обращаемся с этими двумя новыми переменными так же, как с другими атрибутами медиа SDP в модели «предложение/ответ», используемой SIP [4]: они обмениваются между двумя пользовательскими агентами посредством предложения и ответа, чтобы иметь общее представление о состоянии сессии.
Figure 1 shows a typical message exchange between two SIP user agents using preconditions. A includes quality of service preconditions in the SDP of the initial INVITE. A does not want B to be alerted until there are network resources reserved in both directions (sendrecv) end-to-end. B agrees to reserve network resources for this session before alerting the callee. B will handle resource reservation in the B->A direction, but needs A to handle the A->B direction. To indicate so, B returns a 183 (Session Progress) response to A asking A to start resource reservation and to confirm to B as soon as the A->B direction is ready for the session. A and B both start resource reservation. B finishes reserving resources in the B->A direction, but does not alert the user yet, because network resources in both directions are needed. When A finishes reserving resources in the A->B direction, it sends an UPDATE [5] to B. B returns a 200 (OK) response for the UPDATE, indicating that all the preconditions for the session have been met. At this point in time, B starts alerting the user, and session establishment completes normally.
Рисунок 1 показывает типичный обмен сообщениями между двумя пользовательскими агентами SIP, использующими предусловия. A включает предусловия качества обслуживания в SDP начального INVITE. A не хочет, чтобы B был оповещён до тех пор, пока в обоих направлениях (sendrecv) сквозным образом не будут зарезервированы сетевые ресурсы. B соглашается зарезервировать сетевые ресурсы для этой сессии до оповещения вызываемого. B будет обрабатывать резервирование ресурсов в направлении B->A, но ему нужно, чтобы A обработал направление A->B. Чтобы указать это, B возвращает A ответ 183 (Session Progress), прося A начать резервирование ресурсов и подтвердить это B, как только направление A->B будет готово для сессии. A и B оба начинают резервирование ресурсов. B заканчивает резервирование ресурсов в направлении B->A, но ещё не оповещает пользователя, поскольку нужны сетевые ресурсы в обоих направлениях. Когда A заканчивает резервирование ресурсов в направлении A->B, он отправляет UPDATE [5] к B. B возвращает ответ 200 (OK) на UPDATE, указывая, что все предусловия для сессии выполнены. В этот момент B начинает оповещать пользователя, и установление сессии завершается нормально.

5. Usage of preconditions with offer/answer
5. Использование предусловий с «предложением/ответом»
Parameter negotiation in SIP is carried out using the offer/answer model described in [4]. The idea behind this model is to provide a shared view of the session parameters for both user agents once the answer has been received by the offerer. This section describes which values our new SDP attributes can take in an answer, depending on their value in the offer.
Согласование параметров в SIP выполняется с использованием модели «предложение/ответ», описанной в [4]. Идея этой модели состоит в том, чтобы обеспечить общее представление о параметрах сессии для обоих пользовательских агентов, как только ответ получен предлагающим. В этом разделе описывается, какие значения могут принимать наши новые атрибуты SDP в ответе в зависимости от их значения в предложении.
To achieve a shared view of the status of a media stream, we define a model that consists of three tables: both user agents implement a local status table, and each offer/answer exchange has a transaction status table associated to it. The offerer generates a transaction status table, identical to its local status table, and sends it to the answerer in the offer. The answerer uses the information of this transaction status table to update its local status table. The answerer also updates the transaction status table fields that were out of date and returns this table to the offerer in the answer. The offerer can then update its local status table with the information received in the answer. After this offer/answer exchange, the local status tables of both user agents are synchronised. They now have a common view of the status of the media stream. Sessions that involve several media streams implement these tables per media stream. Note, however, that this is a model of user agent behavior, not of software. An implementation is free to take any approach that replicates the external behavior this model defines.
Для достижения общего представления о состоянии медиапотока мы определяем модель, состоящую из трёх таблиц: оба пользовательских агента реализуют локальную таблицу состояния, и с каждым обменом «предложение/ответ» связана таблица состояния транзакции. Предлагающий формирует таблицу состояния транзакции, идентичную своей локальной таблице состояния, и отправляет её отвечающему в предложении. Отвечающий использует информацию этой таблицы состояния транзакции для обновления своей локальной таблицы состояния. Отвечающий также обновляет поля таблицы состояния транзакции, которые устарели, и возвращает эту таблицу предлагающему в ответе. Затем предлагающий может обновить свою локальную таблицу состояния информацией, полученной в ответе. После этого обмена «предложение/ответ» локальные таблицы состояния обоих пользовательских агентов синхронизированы. Теперь у них общее представление о состоянии медиапотока. Сессии, включающие несколько медиапотоков, реализуют эти таблицы для каждого медиапотока. Обратите внимание, однако, что это модель поведения пользовательского агента, а не программного обеспечения. Реализация свободна выбирать любой подход, который воспроизводит внешнее поведение, определённое этой моделью.
5.1. Generating an offer
5.1. Формирование предложения
Both user agents MUST maintain a local precondition status, which is referred to as a "local status table". Tables 1 and 2 show the format of these tables for both the end-to-end and the segmented status types. For the end-to-end status type, the table contains two rows; one for each direction (i.e., send and recv). A value of "yes" in the "Current" field indicates the successful reservation of that resource in the corresponding direction. "No" indicates that resources have not been reserved yet. The "Desired Strength" field indicates the strength of the preconditions in the corresponding direction. The table for the segmented status type contains four rows: both directions in the local access network and in the peer's access network. The meaning of the fields is the same as in the end-to-end case.

6. Suspending and Resuming Session Establishment
6. Приостановка и возобновление установления сессии
A user agent server that receives an offer with preconditions SHOULD NOT alert the user until all the mandatory preconditions are met; session establishment is suspended until that moment (e.g., a PSTN gateway reserves resources without sending signalling to the PSTN.) A user agent server may receive an INVITE request with no offer in it. In this case, following normal procedures defined in [1] and [5], the user agent server will provide an offer in a reliable 1xx response. The user agent client will send the answer in another SIP request (i.e., the PRACK for the 1xx). If the offer and the answer contain preconditions, the user agent server SHOULD NOT alert the user until all the mandatory preconditions in the answer are met.
Серверу пользовательского агента, получающему предложение с предусловиями, НЕ СЛЕДУЕТ оповещать пользователя до тех пор, пока не выполнены все обязательные предусловия; установление сессии приостанавливается до этого момента (например, шлюз ТфОП резервирует ресурсы, не отправляя сигнализацию в ТфОП). Сервер пользовательского агента может получить запрос INVITE без предложения в нём. В этом случае, согласно обычным процедурам, определённым в [1] и [5], сервер пользовательского агента предоставит предложение в надёжном ответе 1xx. Клиент пользовательского агента отправит ответ в другом запросе SIP (то есть в PRACK для 1xx). Если предложение и ответ содержат предусловия, серверу пользовательского агента НЕ СЛЕДУЕТ оповещать пользователя до тех пор, пока не выполнены все обязательные предусловия в ответе.
Note that in this case, a user agent server providing an initial offer with preconditions, a 180 (Ringing) response with preconditions will never be sent, since the user agent server cannot alert the user until all the preconditions are met.

A UAS that is not capable of unilaterally meeting all of the mandatory preconditions MUST include a confirm-status attribute in the SDP (offer or answer) that it sends (see Section 7). Further, the SDP (offer or answer) that contains this confirm-status attribute MUST be sent as soon as allowed by the SIP offer/answer rules.

While session establishment is suspended, user agents SHOULD not send any data over any media stream. In the case of RTP [6], neither RTP nor RTCP packets are sent.

7. Status Confirmation
7. Подтверждение состояния
The confirm-status attribute MAY be used in both offers and answers. This attribute represents a threshold for the resource reservation. When this threshold is reached or surpassed, the user agent MUST send an offer to the peer user agent, reflecting the new current status of the media line as soon as allowed by the SIP offer/answer rules. If this threshold is crossed again (e.g., the network stops providing resources for the media stream), the user agent MUST send a new offer as well, as soon as allowed by the SIP offer/answer rules. If a peer has requested confirmation on a particular stream, an agent MUST mark that stream with a flag in its local status table. When all the rows with this flag have a "Current" value of "yes", the user agent MUST send a new offer to the peer. This offer will contain the current status of resource reservation in the current-status attributes. Later, if any of the rows with this flag transition to "No", a new offer MUST be sent as well.
Атрибут confirm-status МОЖЕТ использоваться как в предложениях, так и в ответах. Этот атрибут представляет собой порог для резервирования ресурсов. Когда этот порог достигнут или превышен, пользовательский агент ДОЛЖЕН отправить предложение партнёрскому пользовательскому агенту, отражающее новое текущее состояние строки медиа, так скоро, как это допускают правила «предложение/ответ» SIP. Если этот порог снова пересечён (например, сеть перестаёт предоставлять ресурсы для медиапотока), пользовательский агент ДОЛЖЕН также отправить новое предложение, так скоро, как это допускают правила «предложение/ответ» SIP. Если партнёр запросил подтверждение для конкретного потока, агент ДОЛЖЕН пометить этот поток флагом в своей локальной таблице состояния. Когда все строки с этим флагом имеют значение «Current», равное «yes», пользовательский агент ДОЛЖЕН отправить новое предложение партнёру. Это предложение будет содержать текущее состояние резервирования ресурсов в атрибутах current-status. Позднее, если любая из строк с этим флагом переходит в «No», новое предложение также ДОЛЖНО быть отправлено.

When a UAS, acting as an answerer, cannot or is not willing to meet the preconditions in the offer, it SHOULD reject the offer by returning a 580 (Precondition-Failure) response.
Когда UAS, действующий как отвечающий, не может или не желает выполнить предусловия в предложении, ему СЛЕДУЕТ отклонить предложение, вернув ответ 580 (Precondition-Failure).
Using the 580 (Precondition Failure) status code to refuse an offer is useful when the offer comes in an INVITE or in an UPDATE request. However, SIP does not provide a means to refuse offers that arrive in a response (1xx or 2xx) to an INVITE. If a UAC generates an initial INVITE without an offer and receives an offer in a 1xx or 2xx response which is not acceptable, it SHOULD respond to this offer with a correctly formed answer and immediately send a CANCEL or a BYE. If the offer comes in a 1xx or 2xx response to a re-INVITE, A would not have a way to reject it without terminating the session at the same time. The same recommendation given in Section 15.2 of [1] applies here:
Использование кода состояния 580 (Precondition Failure) для отказа от предложения полезно, когда предложение приходит в запросе INVITE или UPDATE. Однако SIP не предоставляет средства для отказа от предложений, которые приходят в ответе (1xx или 2xx) на INVITE. Если UAC формирует начальный INVITE без предложения и получает предложение в ответе 1xx или 2xx, которое неприемлемо, ему СЛЕДУЕТ ответить на это предложение правильно сформированным ответом и немедленно отправить CANCEL или BYE. Если предложение приходит в ответе 1xx или 2xx на re-INVITE, A не имел бы способа отклонить его без одновременного завершения сессии. Здесь применима та же рекомендация, что дана в разделе 15.2 [1]:
"The UAS MUST ensure that the session description overlaps with its previous session description in media formats, transports, other parameters that require support from the peer. This is to avoid the need for the peer to reject the session description. If, however, it is unacceptable to A, A SHOULD generate an answer with a valid session description, and then send a BYE to terminate the session."
«UAS ДОЛЖЕН обеспечить, чтобы описание сессии перекрывалось с его предыдущим описанием сессии по форматам медиа, транспортам и другим параметрам, требующим поддержки со стороны партнёра. Это делается для того, чтобы избежать необходимости для партнёра отклонять описание сессии. Если, однако, оно неприемлемо для A, A СЛЕДУЕТ сформировать ответ с действительным описанием сессии, а затем отправить BYE для завершения сессии».
580 (Precondition Failure) responses and BYE and CANCEL requests, indicating failure to meet certain preconditions, SHOULD contain an SDP description, indicating which desired status triggered the failure. Note that this SDP description is not an offer or an answer, since it does not lead to the establishment of a session. The format of such a description is based on the last SDP (an offer or an answer) received from the remote UA.
Ответы 580 (Precondition Failure), а также запросы BYE и CANCEL, указывающие на неудачу в выполнении определённых предусловий, СЛЕДУЕТ содержать описание SDP, указывающее, какое желаемое состояние вызвало неудачу. Обратите внимание, что это описание SDP не является предложением или ответом, поскольку оно не ведёт к установлению сессии. Формат такого описания основан на последнем SDP (предложении или ответе), полученном от удалённого UA.
For each "m=" line in the last SDP description received, there MUST be a corresponding "m=" line in the SDP description indicating failure. This SDP description MUST contain exactly the same number of "m=" lines as the last SDP description received. The port number of every "m=" line MUST be set to zero, but the connection address is arbitrary.
Для каждой строки «m=» в последнем полученном описании SDP ДОЛЖНА быть соответствующая строка «m=» в описании SDP, указывающем неудачу. Это описание SDP ДОЛЖНО содержать ровно столько же строк «m=», сколько последнее полученное описание SDP. Номер порта каждой строки «m=» ДОЛЖЕН быть установлен в ноль, но адрес соединения произволен.
The desired status line corresponding to the precondition that triggered the failure MUST use the "failure" strength-tag, as shown in the example below:
Строка desired status, соответствующая предусловию, вызвавшему неудачу, ДОЛЖНА использовать strength-тег «failure», как показано в примере ниже:
m=audio 20000 RTP/AVP 0 a=des:qos failure e2e send
m=audio 20000 RTP/AVP 0 a=des:qos failure e2e send
8.1. Rejecting a Media Stream
8.1. Отклонение медиапотока
In the offer/answer model, when an answerer wishes to reject a media stream, it sets its port to zero. The presence of preconditions does not change this behaviour; streams are still rejected by setting their port to zero.
В модели «предложение/ответ», когда отвечающий желает отклонить медиапоток, он устанавливает его порт в ноль. Наличие предусловий не меняет это поведение; потоки по-прежнему отклоняются установкой их порта в ноль.
Both the offerer and the answerer MUST ignore all the preconditions that affect a stream with its port set to zero. They are not taken into consideration to decide whether or not session establishment can resume.
Как предлагающий, так и отвечающий ДОЛЖНЫ игнорировать все предусловия, влияющие на поток с портом, установленным в ноль. Они не учитываются при решении о том, может ли установление сессии возобновиться.
9. Unknown Precondition Type
9. Неизвестный тип предусловия
This document defines the "qos" tag for quality of service preconditions. New precondition-types defined in the future will have new associated tags. A UA that receives an unknown precondition-type, with a "mandatory" strength-tag in an offer, MUST refuse the offer unless the only unknown mandatory preconditions have the "local" tag. In this case, the UA does not need to be involved in order to meet the preconditions. The UA will ask for confirmation of the preconditions and, when the confirmation arrives, it will resume session establishment.
Настоящий документ определяет тег «qos» для предусловий качества обслуживания. Новые типы предусловий, определённые в будущем, будут иметь новые связанные теги. UA, получающий неизвестный тип предусловия со strength-тегом «mandatory» в предложении, ДОЛЖЕН отклонить предложение, если только единственными неизвестными обязательными предусловиями не являются предусловия с тегом «local». В этом случае UA не нужно быть вовлечённым для выполнения предусловий. UA запросит подтверждение предусловий и, когда подтверждение придёт, возобновит установление сессии.
A UA refusing an offer follows the rules described in section 8, but instead of the tag "failure", it uses the tag "unknown", as shown in the example below:
UA, отклоняющий предложение, следует правилам, описанным в разделе 8, но вместо тега «failure» использует тег «unknown», как показано в примере ниже:
m=audio 20000 RTP/AVP 0 a=des:foo unknown e2e send
m=audio 20000 RTP/AVP 0 a=des:foo unknown e2e send
10. Multiple Preconditions per Media Stream
10. Несколько предусловий на медиапоток
A media stream MAY contain multiple preconditions. Different preconditions MAY have the same precondition-type and different status-types (e.g., end to end and segmented quality of service preconditions) or different precondition-types (this document only defines the "qos" precondition type, but extensions may define more precondition-types in the future).
Медиапоток МОЖЕТ содержать несколько предусловий. Различные предусловия МОГУТ иметь одинаковый тип предусловия и разные типы состояния (например, сквозные и сегментированные предусловия качества обслуживания) либо разные типы предусловий (настоящий документ определяет только тип предусловия «qos», но расширения могут определить больше типов предусловий в будущем).
All the preconditions for a media stream MUST be met in order to resume session establishment. The following example shows a session description that uses both end-to-end and segmented status-types for a media stream.

m=audio 20000 RTP/AVP 0 a=curr:qos local none a=curr:qos remote none a=des:qos mandatory local sendrecv a=des:qos mandatory remote sendrecv a=curr:qos e2e none a=des:qos optional e2e sendrecv

11. Option Tag for Preconditions
11. Тег опции для предусловий
We define the option tag "precondition" for use in the Require and Supported header fields. An offerer MUST include this tag in the Require header field if the offer contains one or more "mandatory" strength-tags. If all the strength-tags in the description are "optional" or "none", the offerer MUST include this tag in either a Supported header field or in a Require header field. It is, however, RECOMMENDED that the Supported header field be used in this case. The lack of preconditions in the answer would indicate that the answerer did not support this extension.
Мы определяем тег опции «precondition» для использования в полях заголовков Require и Supported. Предлагающий ДОЛЖЕН включать этот тег в поле заголовка Require, если предложение содержит один или несколько strength-тегов «mandatory». Если все strength-теги в описании — «optional» или «none», предлагающий ДОЛЖЕН включать этот тег либо в поле заголовка Supported, либо в поле заголовка Require. Однако РЕКОМЕНДУЕТСЯ в этом случае использовать поле заголовка Supported. Отсутствие предусловий в ответе указывало бы на то, что отвечающий не поддерживает это расширение.
The mapping of offers and answers to SIP requests and responses is performed following the rules given in [5]. Therefore, a user agent including preconditions in the SDP MUST support the PRACK and UPDATE methods. Consequently, it MUST include the "100rel" [7] tag in the Supported header field and SHOULD include an Allow header field with the "UPDATE" tag [5].
Отображение предложений и ответов на запросы и ответы SIP выполняется согласно правилам, приведённым в [5]. Поэтому пользовательский агент, включающий предусловия в SDP, ДОЛЖЕН поддерживать методы PRACK и UPDATE. Следовательно, он ДОЛЖЕН включать тег «100rel» [7] в поле заголовка Supported и СЛЕДУЕТ включать поле заголовка Allow с тегом «UPDATE» [5].

14. Security Considerations
14. Вопросы безопасности
An entity in the middle of two user agents establishing a session may add desired-status attributes making session establishment impossible. It could also modify the content of the current-status parameters so that the session is established without meeting the preconditions. Integrity protection can be used to avoid these attacks.
Объект в середине между двумя пользовательскими агентами, устанавливающими сессию, может добавить атрибуты desired-status, делая установление сессии невозможным. Он также может изменить содержимое параметров current-status так, что сессия будет установлена без выполнения предусловий. Для предотвращения таких атак может использоваться защита целостности.
An entity performing resource reservations upon reception of unauthenticated requests carrying preconditions can be an easy target for a denial of service attack. Requests with preconditions SHOULD be authenticated.
Объект, выполняющий резервирование ресурсов по получении неаутентифицированных запросов, несущих предусловия, может быть лёгкой целью для атаки отказа в обслуживании. Запросы с предусловиями СЛЕДУЕТ аутентифицировать.
