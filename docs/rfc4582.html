Abstract
Аннотация
Floor control is a means to manage joint or exclusive access to shared resources in a (multiparty) conferencing environment. Thereby, floor control complements other functions -- such as conference and media session setup, conference policy manipulation, and media control -- that are realized by other protocols.
Управление полом — это средство организации совместного или исключительного доступа к общим ресурсам в среде конференции (с несколькими участниками). Тем самым управление полом дополняет другие функции — такие как установление конференции и медиасессий, изменение политики конференции и управление медиа, — которые реализуются другими протоколами.
This document specifies the Binary Floor Control Protocol (BFCP). BFCP is used between floor participants and floor control servers, and between floor chairs (i.e., moderators) and floor control servers.
Настоящий документ определяет двоичный протокол управления полом (BFCP). BFCP используется между участниками пола и серверами управления полом, а также между председателями пола (то есть модераторами) и серверами управления полом.

1. Introduction
1. Введение
Within a conference, some applications need to manage the access to a set of shared resources, such as the right to send media to a particular media session. Floor control enables such applications to provide users with coordinated (shared or exclusive) access to these resources.
В конференции некоторым приложениям требуется управлять доступом к набору общих ресурсов, например правом отправлять медиа в конкретную медиасессию. Управление полом позволяет таким приложениям предоставлять пользователям согласованный (совместный или исключительный) доступ к этим ресурсам.
The Requirements for Floor Control Protocol [9] list a set of requirements that need to be met by floor control protocols. The Binary Floor Control Protocol (BFCP), which is specified in this document, meets these requirements.
В "Requirements for Floor Control Protocol" [9] перечислен набор требований, которым должны удовлетворять протоколы управления полом. Двоичный протокол управления полом (BFCP), определяемый в настоящем документе, этим требованиям удовлетворяет.
In addition, BFCP has been designed so that it can be used in low-bandwidth environments. The binary encoding used by BFCP achieves a small message size (when message signatures are not used) that keeps the time it takes to transmit delay-sensitive BFCP messages to a minimum. Delay-sensitive BFCP messages include FloorRequest, FloorRelease, FloorRequestStatus, and ChairAction. It is expected that future extensions to these messages will not increase the size of these messages in a significant way.
Кроме того, BFCP спроектирован так, чтобы его можно было использовать в средах с малой пропускной способностью. Двоичное кодирование, применяемое в BFCP, обеспечивает малый размер сообщений (когда подписи сообщений не используются), что сводит к минимуму время передачи сообщений BFCP, чувствительных к задержке. К чувствительным к задержке сообщениям BFCP относятся FloorRequest, FloorRelease, FloorRequestStatus и ChairAction. Ожидается, что будущие расширения этих сообщений не увеличат их размер сколько-нибудь существенно.
The remainder of this document is organized as follows: Section 2 defines the terminology used throughout this document, Section 3 discusses the scope of BFCP (i.e., which tasks fall within the scope of BFCP and which ones are performed using different mechanisms), Section 4 provides a non-normative overview of BFCP operation, and subsequent sections provide the normative specification of BFCP.
Остальная часть документа организована следующим образом: раздел 2 определяет терминологию, используемую в настоящем документе, раздел 3 обсуждает область применения BFCP (то есть какие задачи входят в область применения BFCP, а какие выполняются иными механизмами), раздел 4 даёт необязательный к исполнению обзор работы BFCP, а последующие разделы содержат нормативную спецификацию BFCP.

2. Терминология

В настоящем документе ключевые слова "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" и "OPTIONAL" должны интерпретироваться так, как описано в BCP 14, RFC 2119 [1], и указывают уровни требований для соответствующих реализаций.
Media Participant: An entity that has access to the media resources of a conference (e.g., it can receive a media stream). In floor- controlled conferences, a given media participant is typically colocated with a floor participant, but it does not need to be. The protocol between a floor participant and a media participant (that are not colocated) is outside the scope of this document.

Запрос пола за третье лицо состоит в том, что участник пола запрашивает пол для медиаучастника, когда они не размещены совместно. Протокол между участником пола и медиаучастником (не размещёнными совместно) находится вне области применения настоящего документа.
Client: A floor participant or a floor chair that communicates with a floor control server using BFCP. Floor: A temporary permission to access or manipulate a specific shared resource or set of resources.
Клиент: участник пола или председатель пола, взаимодействующий с сервером управления полом по протоколу BFCP. Пол: временное разрешение на доступ к конкретному общему ресурсу или набору ресурсов либо на манипулирование ими.

The roles of floor chair and floor participant are defined on a transaction-by- transaction basis. BFCP transactions are defined in Section 8.
Председатель пола: логическая сущность, управляющая одним полом (предоставляет, отклоняет или отзывает пол). Сущность, принимающая на себя логическую роль председателя пола для данной транзакции, может принимать другую роль (например, участника пола) для другой транзакции. Роли председателя пола и участника пола определяются для каждой транзакции отдельно. Транзакции BFCP определены в разделе 8.
Floor Control: A mechanism that enables applications or users to gain safe and mutually exclusive or non-exclusive input access to the shared object or resource.
Управление полом: механизм, позволяющий приложениям или пользователям получать безопасный и взаимно исключительный или неисключительный доступ ввода к общему объекту или ресурсу.
Floor Control Server: A logical entity that maintains the state of the floor(s), including which floors exists, who the floor chairs are, who holds a floor, etc. Requests to manipulate a floor are directed at the floor control server. The floor control server of a conference may perform other logical roles (e.g., floor participant) in another conference.
Сервер управления полом: логическая сущность, поддерживающая состояние пола (полов), включая сведения о том, какие полы существуют, кто является председателем пола, кто владеет полом, и т. д. Запросы на манипулирование полом направляются серверу управления полом. Сервер управления полом одной конференции может выполнять другие логические роли (например, участника пола) в другой конференции.
Floor Participant: A logical entity that requests floors, and possibly information about them, from a floor control server. An entity that assumes the logical role of a floor participant for a given transaction may assume a different role (e.g., a floor chair) for a different transaction. The roles of floor participant and floor chair are defined on a transaction-by-transaction basis. BFCP transactions are defined in Section 8. In floor-controlled conferences, a given floor participant is typically colocated with a media participant, but it does not need to be. Third-party floor requests consist of having a floor participant request a floor for a media participant when they are not colocated.
Участник пола: логическая сущность, запрашивающая у сервера управления полом полы и, возможно, сведения о них. Сущность, принимающая на себя логическую роль участника пола для данной транзакции, может принимать другую роль (например, председателя пола) для другой транзакции. Роли участника пола и председателя пола определяются для каждой транзакции отдельно. Транзакции BFCP определены в разделе 8. В конференциях с управлением полом данный участник пола обычно размещён совместно с медиаучастником, но это не обязательно. Запрос пола за третье лицо состоит в том, что участник пола запрашивает пол для медиаучастника, когда они не размещены совместно.
Participant: An entity that acts as a floor participant, as a media participant, or as both.
Участник: сущность, выступающая как участник пола, как медиаучастник или как то и другое.
3. Scope
3. Область применения
As stated earlier, BFCP is a protocol to coordinate access to shared resources in a conference following the requirements defined in [9]. Floor control complements other functions defined in the XCON conferencing framework [10]. The floor control protocol BFCP defined in this document only specifies a means to arbitrate access to floors. The rules and constraints for floor arbitration and the results of floor assignments are outside the scope of this document and are defined by other protocols [10]. Как указано ранее, BFCP — это протокол согласования доступа к общим ресурсам в конференции в соответствии с требованиями, определёнными в [9]. Управление полом дополняет другие функции, определённые в инфраструктуре конференций XCON [10]. Протокол управления полом BFCP, определяемый в настоящем документе, задаёт лишь средство арбитража доступа к полам. Хотя задачи, не входящие в предыдущий перечень, находятся вне области применения BFCP, некоторые из этих задач связаны с управлением полом и существенны для создания полов и установления соединений BFCP между различными сущностями. В следующих подразделах рассматриваются некоторые из таких задач и механизмы их выполнения.
3.1. Floor Creation
3.1. Создание пола
The association of a given floor with a resource or a set of resources (e.g., media streams) is out of the scope of BFCP as described in [10]. Floor creation and termination are also outside the scope of BFCP; these aspects are handled using the conference control protocol for manipulating the conference object. Consequently, the floor control server needs to stay up to date on changes to the conference object (e.g., when a new floor is created).
Связывание данного пола с ресурсом или набором ресурсов (например, медиапотоками) находится вне области применения BFCP, как описано в [10]. Создание и завершение пола также выходят за рамки BFCP; эти аспекты обрабатываются протоколом управления конференцией при манипулировании объектом конференции. Следовательно, сервер управления полом должен быть в курсе изменений объекта конференции (например, когда создаётся новый пол).
3.2. Obtaining Information to Contact a Floor Control Server
3.2. Получение сведений для связи с сервером управления полом
A client needs a set of data in order to establish a BFCP connection to a floor control server. These data include the transport address of the server, the conference identifier, and a user identifier.
Клиенту нужен набор данных, чтобы установить соединение BFCP с сервером управления полом. Эти данные включают транспортный адрес сервера, идентификатор конференции и идентификатор пользователя.
Clients can obtain this information in different ways. One is to use an SDP offer/answer [8] exchange, which is described in [7]. Other mechanisms are described in the XCON framework [10] (and other related documents).
Клиенты могут получать эти сведения разными способами. Один из них — обмен SDP offer/answer [8], описанный в [7]. Другие механизмы описаны в инфраструктуре XCON [10] (и других связанных документах).
3.3. Obtaining Floor-Resource Associations
3.3. Получение связей между полами и ресурсами
Floors are associated with resources. For example, a floor that controls who talks at a given time has a particular audio session as its associated resource. Associations between floors and resources are part of the conference object.
Полы связаны с ресурсами. Например, пол, управляющий тем, кто говорит в данный момент, имеет в качестве связанного ресурса конкретную аудиосессию. Связи между полами и ресурсами являются частью объекта конференции.
Floor participants and floor chairs need to know which resources are associated with which floors. They can obtain this information by using different mechanisms, such as an SDP offer/answer [8] exchange. How to use an SDP offer/answer exchange to obtain these associations is described in [7].
Участникам пола и председателям пола нужно знать, какие именно ресурсы связаны с какими именно полами. Они могут получать эти сведения с помощью различных механизмов, например обмена SDP offer/answer [8]. Как использовать обмен SDP offer/answer для получения этих связей, описано в [7].
Note that floor participants perform SDP offer/answer exchanges with the conference focus of the conference. So, the conference focus needs to obtain information about associations between floors and resources in order to be able to provide this information to a floor participant in an SDP offer/answer exchange.
Заметим, что участники пола выполняют обмен SDP offer/answer именно с фокусом конференции. Поэтому фокусу конференции нужно получить сведения о связях между полами и ресурсами, чтобы предоставить их участнику пола в обмене SDP offer/answer.
Other mechanisms for obtaining this information, including discussion of how the information is made available to a (SIP) Focus, are described in the XCON framework [10] (and other related documents).
Другие механизмы получения этих сведений, включая обсуждение того, как сведения становятся доступны фокусу (SIP), описаны в инфраструктуре XCON [10] (и других связанных документах).
3.4. Privileges of Floor Control
3.4. Привилегии управления полом
A participant whose floor request is granted has the right to use (in a certain way) the resource or resources associated with the floor that was requested. For example, the participant may have the right to send media over a particular audio stream.
Участник, чей запрос пола удовлетворён, имеет право определённым образом использовать ресурс или ресурсы, связанные с запрошенным полом. Например, участник может иметь право отправлять медиа по конкретному аудиопотоку.
Nevertheless, holding a floor does not imply that others will not be able to use its associated resources at the same time, even if they do not have the right to do so. Determination of which media participants can actually use the resources in the conference is discussed in the XCON Framework [10].
Тем не менее владение полом не означает, что другие не смогут одновременно использовать связанные с ним ресурсы, даже если они не имеют на это права. Определение того, какие медиаучастники действительно могут использовать ресурсы конференции, рассматривается в инфраструктуре XCON [10].
4. Overview of Operation
4. Обзор работы
This section provides a non-normative description of BFCP operations. Section 4.1 describes the interface between floor participants and floor control servers, and Section 4.2 describes the interface between floor chairs and floor control servers.
В этом разделе даётся необязательный к исполнению обзор работы BFCP. Раздел 4.1 описывает интерфейс между участниками пола и серверами управления полом, а раздел 4.2 — интерфейс между председателями пола и серверами управления полом.
BFCP messages, which use a TLV (Type-Length-Value) binary encoding, consist of a common header followed by a set of attributes. The common header contains, among other information, a 32-bit conference identifier. Floor participants, media participants, and floor chairs are identified by 16-bit user identifiers.
Сообщения BFCP, использующие двоичное кодирование TLV (Type-Length-Value), состоят из общего заголовка, за которым следует набор атрибутов. Общий заголовок содержит, помимо прочего, 32-битный идентификатор конференции. Участники пола, медиаучастники и председатели пола идентифицируются 16-битными идентификаторами пользователей.
BFCP supports nested attributes (i.e., attributes that contain attributes). These are referred to as grouped attributes.
BFCP поддерживает вложенные атрибуты (то есть атрибуты, содержащие атрибуты). Они называются сгруппированными атрибутами.
There are two types of transactions in BFCP: client-initiated transactions and server-initiated transactions. Client-initiated transactions consist of a message from a client to the floor control server and a response from the floor control server to the client. Both messages can be related because they carry the same Transaction ID value in their common headers. Server-initiated transactions consist of a single message, whose Transaction ID is 0, from the floor control server to a client.
В BFCP существует два типа транзакций: транзакции, инициируемые клиентом, и транзакции, инициируемые сервером. Транзакции, инициируемые клиентом, состоят из сообщения клиента серверу управления полом и ответа сервера управления полом клиенту. Оба сообщения могут быть связаны, поскольку несут одно и то же значение Transaction ID в своих общих заголовках. Транзакции, инициируемые сервером, состоят из одного сообщения сервера управления полом клиенту, Transaction ID которого равен 0.
4.1. Floor Participant to Floor Control Server Interface
4.1. Интерфейс между участником пола и сервером управления полом
Floor participants request a floor by sending a FloorRequest message to the floor control server. BFCP supports third-party floor requests. That is, the floor participant sending the floor request need not be colocated with the media participant that will get the floor once the floor request is granted. FloorRequest messages carry the identity of the requester in the User ID field of the common header, and the identity of the beneficiary of the floor (in third- party floor requests) in a BENEFICIARY-ID attribute. Third-party floor requests can be sent, for example, by floor participants that have a BFCP connection to the floor control server but that are not media participants (i.e., they do not handle any media).
Участники пола запрашивают пол, отправляя серверу управления полом сообщение FloorRequest. BFCP поддерживает запросы пола за третье лицо. То есть участник пола, отправляющий запрос пола, не обязательно должен быть размещён совместно с медиаучастником, который получит пол после удовлетворения запроса пола. Сообщения FloorRequest несут идентичность запрашивающей стороны в поле User ID общего заголовка, а идентичность получателя пола (в запросах пола за третье лицо) — в атрибуте BENEFICIARY-ID. Запросы пола за третье лицо могут отправляться, например, участниками пола, которые имеют соединение BFCP с сервером управления полом, но не являются медиаучастниками (то есть не работают ни с какими медиа).
FloorRequest messages identify the floor or floors being requested by carrying their 16-bit floor identifiers in FLOOR-ID attributes. If a FloorRequest message carries more than one floor identifier, the floor control server treats all the floor requests as an atomic package. That is, the floor control server either grants or denies all the floors in the FloorRequest message.
Сообщения FloorRequest идентифицируют запрашиваемый пол или полы, неся их 16-битные идентификаторы полов в атрибутах FLOOR-ID. Если сообщение FloorRequest несёт более одного идентификатора пола, сервер управления полом трактует все запросы пола как атомарный пакет. То есть сервер управления полом либо предоставляет, либо отклоняет все полы в сообщении FloorRequest.
Floor control servers respond to FloorRequest messages with FloorRequestStatus messages, which provide information about the status of the floor request. The first FloorRequestStatus message is the response to the FloorRequest message from the client, and therefore has the same Transaction ID as the FloorRequest.
Серверы управления полом отвечают на сообщения FloorRequest сообщениями FloorRequestStatus, которые предоставляют сведения о состоянии запроса пола. Первое сообщение FloorRequestStatus является ответом на сообщение FloorRequest от клиента и поэтому имеет тот же Transaction ID, что и FloorRequest.
Additionally, the first FloorRequestStatus message carries the Floor Request ID in a FLOOR-REQUEST-INFORMATION attribute. Subsequent FloorRequestStatus messages related to the same floor request will carry the same Floor Request ID. This way, the floor participant can associate them with the appropriate floor request.
Кроме того, первое сообщение FloorRequestStatus несёт Floor Request ID в атрибуте FLOOR-REQUEST-INFORMATION. Последующие сообщения FloorRequestStatus, относящиеся к тому же запросу пола, будут нести тот же Floor Request ID. Так участник пола может сопоставить их с соответствующим запросом пола.
Messages from the floor participant related to a particular floor request also use the same Floor Request ID as the first FloorRequestStatus Message from the floor control server.
Сообщения от участника пола, относящиеся к конкретному запросу пола, также используют тот же Floor Request ID, что и первое сообщение FloorRequestStatus от сервера управления полом.

A multi-floor floor request applies to more than one floor (e.g., a participant wants to be able to speak and write on the whiteboard at the same time). The floor control server treats a multi-floor floor request as an atomic package. That is, the floor control server either grants the request for all floors or denies the request for all floors.
Запрос пола на несколько полов относится к более чем одному полу (например, участник хочет иметь возможность одновременно говорить и писать на доске). Сервер управления полом трактует запрос пола на несколько полов как атомарный пакет. То есть сервер управления полом либо удовлетворяет запрос для всех полов, либо отклоняет его для всех полов.
4.2. Floor Chair to Floor Control Server Interface
4.2. Интерфейс между председателем пола и сервером управления полом
Figure 4 shows a floor chair instructing a floor control server to grant a floor.

Note, however, that although the floor control server needs to take into consideration the instructions received in ChairAction messages (e.g., granting a floor), it does not necessarily need to perform them exactly as requested by the floor chair. The operation that the floor control server performs depends on the ChairAction message and on the internal state of the floor control server.
Заметим, однако, что хотя сервер управления полом должен принимать во внимание инструкции, полученные в сообщениях ChairAction (например, о предоставлении пола), он не обязательно должен выполнять их в точности так, как запросил председатель пола. Операция, выполняемая сервером управления полом, зависит от сообщения ChairAction и от внутреннего состояния сервера управления полом.
For example, a floor chair may send a ChairAction message granting a floor that was requested as part of an atomic floor request operation that involved several floors. Even if the chair responsible for one of the floors instructs the floor control server to grant the floor, the floor control server will not grant it until the chairs responsible for the other floors agree to grant them as well. In another example, a floor chair may instruct the floor control server to grant a floor to a participant. The floor control server needs to revoke the floor from its current holder before granting it to the new participant.
Например, председатель пола может отправить сообщение ChairAction, предоставляющее пол, который был запрошен в рамках атомарной операции запроса пола, затрагивающей несколько полов. Даже если председатель, отвечающий за один из полов, даёт серверу управления полом указание предоставить пол, сервер управления полом не предоставит его, пока председатели, отвечающие за остальные полы, не согласятся их предоставить. В другом примере председатель пола может дать серверу управления полом указание предоставить пол участнику. Серверу управления полом нужно отозвать пол у текущего владельца, прежде чем предоставить его новому участнику.
So, the floor control server is ultimately responsible for keeping a coherent floor state using instructions from floor chairs as input to this state.
Таким образом, сервер управления полом в конечном счёте отвечает за поддержание согласованного состояния полов, используя инструкции председателей пола как входные данные для этого состояния.

6. Transport
6. Транспорт
BFCP entities exchange BFCP messages using TCP connections. TCP provides an in-order reliable delivery of a stream of bytes. Consequently, message framing is implemented in the application layer. BFCP implements application-layer framing using TLV-encoded attributes.
Сущности BFCP обмениваются сообщениями BFCP по TCP-соединениям. TCP обеспечивает надёжную доставку потока байтов с сохранением порядка. Следовательно, кадрирование сообщений реализуется на уровне приложения. BFCP реализует кадрирование на уровне приложения с помощью атрибутов, кодируемых в TLV.
A client MUST NOT use more than one TCP connection to communicate with a given floor control server within a conference. Nevertheless, if the same physical box handles different clients (e.g., a floor chair and a floor participant), which are identified by different User IDs, a separate connection per client is allowed.
Клиент НЕ ДОЛЖЕН использовать более одного TCP-соединения для связи с данным сервером управления полом в рамках конференции. Тем не менее, если один и тот же физический хост обслуживает разных клиентов (например, председателя пола и участника пола), которые идентифицируются разными User ID, допускается отдельное соединение для каждого клиента.
If a BFCP entity (a client or a floor control server) receives data from TCP that cannot be parsed, the entity MUST close the TCP connection, and the connection SHOULD be reestablished. Similarly, if a TCP connection cannot deliver a BFCP message and times out, the TCP connection SHOULD be reestablished. The way connection reestablishment is handled depends on how the client obtains information to contact the floor control server (e.g., using an SDP offer/answer exchange [7]). Once the TCP connection is reestablished, the client MAY resend those messages for which it did not get a response from the floor control server.
Если сущность BFCP (клиент или сервер управления полом) получает из TCP данные, которые невозможно разобрать, сущность ДОЛЖНА закрыть TCP-соединение, а соединение СЛЕДУЕТ установить заново. Аналогично, если TCP-соединение не может доставить сообщение BFCP и происходит тайм-аут, TCP-соединение СЛЕДУЕТ установить заново. То, как выполняется повторное установление соединения, зависит от того, как клиент получает сведения для связи с сервером управления полом (например, с помощью обмена SDP offer/answer [7]). После повторного установления TCP-соединения клиент МОЖЕТ повторно отправить те сообщения, на которые он не получил ответа от сервера управления полом.
If a floor control server detects that the TCP connection towards one of the floor participants is lost, it is up to the local policy of the floor control server what to do with the pending floor requests of the floor participant. In any case, it is RECOMMENDED that the floor control server keep the floor requests (i.e., that it does not cancel them) while the TCP connection is reestablished.
Если сервер управления полом обнаруживает, что TCP-соединение с одним из участников пола потеряно, то, что делать с ожидающими запросами пола этого участника, определяется локальной политикой сервера управления полом. В любом случае РЕКОМЕНДУЕТСЯ, чтобы сервер управления полом сохранял запросы пола (то есть не отменял их до тех пор), пока TCP-соединение не будет установлено заново.
If a client wishes to end its BFCP connection with a floor control server, the client closes (i.e., a graceful close) the TCP connection towards the floor control server. If a floor control server wishes to end its BFCP connection with a client (e.g., the Focus of the conference informs the floor control server that the client has been kicked out from the conference), the floor control server closes (i.e., a graceful close) the TCP connection towards the client.
Если клиент хочет завершить своё соединение BFCP с сервером управления полом, клиент закрывает (то есть выполняет корректное закрытие) TCP-соединение с сервером управления полом. Если сервер управления полом хочет завершить своё соединение BFCP с клиентом (например, фокус конференции сообщает серверу управления полом, что клиент исключён из конференции), сервер управления полом закрывает (то есть выполняет корректное закрытие) TCP-соединение с клиентом.
7. Lower-Layer Security
7. Безопасность нижних уровней
BFCP relies on lower-layer security mechanisms to provide replay and integrity protection and confidentiality. BFCP floor control servers and clients (which include both floor participants and floor chairs) MUST support TLS [3]. Any BFCP entity MAY support other security mechanisms.
BFCP полагается на механизмы безопасности нижних уровней для защиты от повторного воспроизведения, обеспечения целостности и конфиденциальности. Серверы управления полом и клиенты BFCP (к которым относятся как участники пола, так и председатели пола) ДОЛЖНЫ поддерживать TLS [3]. Любая сущность BFCP МОЖЕТ поддерживать другие механизмы безопасности.
BFCP entities MUST support, at a minimum, the TLS TLS_RSA_WITH_AES_128_CBC_SHA ciphersuite [5].
Сущности BFCP ДОЛЖНЫ поддерживать как минимум набор шифров TLS TLS_RSA_WITH_AES_128_CBC_SHA [5].
Which party, the client or the floor control server, acts as the TLS server depends on how the underlying TCP connection is established. For example, when the TCP connection is established using an SDP offer/answer exchange [7], the answerer (which may be the client or the floor control server) always acts as the TLS server.
То, какая сторона — клиент или сервер управления полом — выступает в роли TLS-сервера, зависит от способа установления нижележащего TCP-соединения. Например, когда TCP-соединение устанавливается с помощью обмена SDP offer/answer [7], отвечающая сторона (которой может быть клиент или сервер управления полом) всегда выступает в роли TLS-сервера.
8. Protocol Transactions
8. Транзакции протокола
In BFCP, there are two types of transactions: client-initiated transactions and server-initiated transactions (notifications). Client-initiated transactions consist of a request from a client to a floor control server and a response from the floor control server to the client. The request carries a Transaction ID in its common header, which the floor control server copies into the response. Clients use Transaction ID values to match responses with previously issued requests. Server-initiated transactions consist of a single message from a floor control server to a client. Since they do not trigger any response, their Transaction ID is set to 0.
В BFCP есть два типа транзакций: транзакции, инициируемые клиентом, и транзакции, инициируемые сервером (уведомления). Транзакции, инициируемые клиентом, состоят из запроса клиента к серверу управления полом и ответа сервера управления полом клиенту. Запрос несёт Transaction ID в своём общем заголовке, который сервер управления полом копирует в ответ. Клиенты используют значения Transaction ID, чтобы сопоставлять ответы с ранее выданными запросами. Транзакции, инициируемые сервером, состоят из одного сообщения от сервера управления полом клиенту. Поскольку они не вызывают никакого ответа, их Transaction ID устанавливается в 0.
8.1. Client Behavior
8.1. Поведение клиента
A client starting a client-initiated transaction MUST set the Conference ID in the common header of the message to the Conference ID for the conference that the client obtained previously.
Клиент, начинающий транзакцию, инициируемую клиентом, ДОЛЖЕН установить Conference ID в общем заголовке сообщения в значение Conference ID той конференции, которое клиент получил ранее.
The client MUST set the Transaction ID value in the common header to a number that is different from 0 and that MUST NOT be reused in another message from the client until a response from the server is received for the transaction. The client uses the Transaction ID value to match this message with the response from the floor control server.
Клиент ДОЛЖЕН установить значение Transaction ID в общем заголовке в число, отличное от 0, которое НЕ ДОЛЖНО повторно использоваться в другом сообщении клиента до получения ответа сервера на данную транзакцию. Клиент использует значение Transaction ID для сопоставления этого сообщения с ответом сервера управления полом.
8.2. Server Behavior
8.2. Поведение сервера
A floor control server sending a response within a client-initiated transaction MUST copy the Conference ID, the Transaction ID, and the User ID from the request received from the client into the response. Server-initiated transactions MUST contain a Transaction ID equal to 0.
Сервер управления полом, отправляющий ответ в рамках инициируемой клиентом транзакции, ДОЛЖЕН скопировать Conference ID, Transaction ID и User ID из полученного от клиента запроса в ответ. Транзакции, инициируемые сервером, ДОЛЖНЫ содержать Transaction ID, равный 0.
9. Authentication and Authorization
9. Аутентификация и авторизация
BFCP clients SHOULD authenticate the floor control server before sending any BFCP message to it or accepting any BFCP message from it. Similarly, floor control servers SHOULD authenticate a client before accepting any BFCP message from it or sending any BFCP message to it.
Клиентам BFCP СЛЕДУЕТ аутентифицировать сервер управления полом, прежде чем отправлять ему какие-либо сообщения BFCP или принимать от него какие-либо сообщения BFCP. Аналогично, серверам управления полом СЛЕДУЕТ аутентифицировать клиента, прежде чем принимать от него какие-либо сообщения BFCP или отправлять ему какие-либо сообщения BFCP.
BFCP supports TLS-based mutual authentication between clients and floor control servers, as specified in Section 9.1. This is the RECOMMENDED authentication mechanism in BFCP.
BFCP поддерживает взаимную аутентификацию на основе TLS между клиентами и серверами управления полом, как указано в разделе 9.1. Это РЕКОМЕНДУЕМЫЙ механизм аутентификации в BFCP.
Note that future extensions may define additional authentication mechanisms.
Заметим, что будущие расширения могут определить дополнительные механизмы аутентификации.
In addition to authenticating BFCP messages, floor control servers need to authorize them. On receiving an authenticated BFCP message, the floor control server checks whether the client sending the message is authorized. If the client is not authorized to perform the operation being requested, the floor control server generates an Error message, as described in Section 13.8, with an Error code with a value of 5 (Unauthorized Operation). Messages from a client that cannot be authorized MUST NOT be processed further.
Помимо аутентификации сообщений BFCP, серверам управления полом нужно авторизовывать их. При получении аутентифицированного сообщения BFCP сервер управления полом проверяет, авторизован ли отправивший его клиент. Если клиент не авторизован для выполнения запрашиваемой операции, сервер управления полом генерирует сообщение Error, как описано в разделе 13.8, с кодом ошибки 5 (Unauthorized Operation). Сообщения от клиента, который не может быть авторизован, НЕ ДОЛЖНЫ обрабатываться дальше.
9.1. TLS-Based Mutual Authentication
9.1. Взаимная аутентификация на основе TLS
BFCP supports TLS-based mutual authentication between clients and floor control servers. BFCP assumes that there is an integrity- protected channel between the client and the floor control server that can be used to exchange their self-signed certificates or, more commonly, the fingerprints of these certificates. These certificates are used at TLS establishment time.
BFCP поддерживает взаимную аутентификацию на основе TLS между клиентами и серверами управления полом. BFCP предполагает наличие канала с защитой целостности между клиентом и сервером управления полом, который можно использовать для обмена самоподписанными сертификатами или, что встречается чаще, отпечатками этих сертификатов. Эти сертификаты используются при установлении TLS.
The implementation of such an integrity-protected channel using SIP and the SDP offer/answer model is described in [7].
Реализация такого канала с защитой целостности с помощью SIP и модели SDP offer/answer описана в [7].
BFCP messages received over an authenticated TLS connection are considered authenticated. A floor control server that receives a BFCP message over TCP (no TLS) can request the use of TLS by generating an Error message, as described in Section 13.8, with an Error code with a value of 9 (Use TLS). Clients SHOULD simply ignore unauthenticated messages.
Сообщения BFCP, полученные по аутентифицированному TLS-соединению, считаются аутентифицированными. Сервер управления полом, получающий сообщение BFCP по TCP (без TLS), может запросить использование TLS, сгенерировав сообщение Error, как описано в разделе 13.8, с кодом ошибки 9 (Use TLS). Клиентам СЛЕДУЕТ просто игнорировать неаутентифицированные сообщения.
Note that future extensions may define additional authentication mechanisms that may not require an initial integrity-protected channel (e.g., authentication based on certificates signed by a certificate authority).
Заметим, что будущие расширения могут определить дополнительные механизмы аутентификации, которые могут не требовать первоначального канала с защитой целостности (например, аутентификацию на основе сертификатов, подписанных удостоверяющим центром).
As described in Section 9, floor control servers need to perform authorization before processing any message. In particular, the floor control server SHOULD check that messages arriving over a given authenticated TLS connection use an authorized User ID (i.e., a User ID that the user that established the authenticated TLS connection is allowed to use).
Как описано в разделе 9, серверам управления полом нужно выполнять авторизацию перед обработкой любого сообщения. В частности, серверу управления полом СЛЕДУЕТ проверять, что сообщения, приходящие по данному аутентифицированному TLS-соединению, используют авторизованный User ID (то есть User ID, который пользователю, установившему аутентифицированное TLS-соединение, разрешено использовать).

10. Операции участника пола
This section specifies how floor participants can perform different operations, such as requesting a floor, using the protocol elements described in earlier sections. Section 11 specifies operations that are specific to floor chairs, such as instructing the floor control server to grant or revoke a floor, and Section 12 specifies operations that can be performed by any client (i.e., both floor participants and floor chairs).
В этом разделе указано, как участники пола могут выполнять различные операции, например запрашивать пол, используя элементы протокола, описанные в предыдущих разделах. Раздел 11 описывает операции, специфичные для председателей пола, например указание серверу управления полом предоставить или отозвать пол, а раздел 12 описывает операции, которые может выполнять любой клиент (то есть как участники пола, так и председатели пола).
10.1. Requesting a Floor
10.1. Запрос пола
A floor participant that wishes to request one or more floors does so by sending a FloorRequest message to the floor control server.
Участник пола, желающий запросить один или несколько полов, делает это, отправляя серверу управления полом сообщение FloorRequest.
10.1.1. Sending a FloorRequest Message
10.1.1. Отправка сообщения FloorRequest
The ABNF in Section 5.3.1 describes the attributes that a FloorRequest message can contain. In addition, the ABNF specifies normatively which of these attributes are mandatory, and which ones are optional.
ABNF в разделе 5.3.1 описывает атрибуты, которые может содержать сообщение FloorRequest. Кроме того, ABNF нормативно определяет, какие из этих атрибутов обязательны, а какие необязательны.
The floor participant sets the Conference ID and the Transaction ID in the common header following the rules given in Section 8.1.
Участник пола устанавливает поля Conference ID и Transaction ID в общем заголовке согласно правилам, приведённым в разделе 8.1.
The floor participant sets the User ID in the common header to the floor participant's identifier. This User ID will be used by the floor control server to authenticate and authorize the request. If the sender of the FloorRequest message (identified by the User ID) is not the participant that would eventually get the floor (i.e., a third-party floor request), the sender SHOULD add a BENEFICIARY-ID attribute to the message identifying the beneficiary of the floor.
Участник пола устанавливает User ID в общем заголовке в значение идентификатора участника пола. Этот User ID будет использоваться сервером управления полом для аутентификации и авторизации запроса. Если отправитель сообщения FloorRequest (идентифицируемый по User ID) не является участником, который в итоге получит пол (то есть при запросе пола за третье лицо), отправителю СЛЕДУЕТ добавить в сообщение атрибут BENEFICIARY-ID, идентифицирующий получателя пола.
Note that the name space for both the User ID and the Beneficiary ID is the same. That is, a given participant is identified by a single 16-bit value that can be used in the User ID in the common header and in several attributes: BENEFICIARY-ID, BENEFICIARY- INFORMATION, and REQUESTED-BY-INFORMATION.
Заметим, что пространство имён для User ID и Beneficiary ID одно и то же. То есть данный участник идентифицируется одним 16-битным значением, которое может использоваться в User ID общего заголовка и в нескольких атрибутах: BENEFICIARY-ID, BENEFICIARY-INFORMATION и REQUESTED-BY-INFORMATION.
The floor participant must insert at least one FLOOR-ID attribute in the FloorRequest message. If the client inserts more than one FLOOR-ID attribute, the floor control server will treat all the floor requests as an atomic package. That is, the floor control server will either grant or deny all the floors in the FloorRequest message.
Участник пола должен вставить в сообщение FloorRequest как минимум один атрибут FLOOR-ID. Если клиент вставляет более одного атрибута FLOOR-ID, сервер управления полом трактует все запросы пола как атомарный пакет. То есть сервер управления полом либо предоставит, либо отклонит все полы в сообщении FloorRequest.
The floor participant may use a PARTICIPANT-PROVIDED-INFO attribute to state the reason why the floor or floors are being requested. The Text field in the PARTICIPANT-PROVIDED-INFO attribute is intended for human consumption.
Участник пола может использовать атрибут PARTICIPANT-PROVIDED-INFO, чтобы указать причину запроса пола или полов. Поле Text атрибута PARTICIPANT-PROVIDED-INFO предназначено для восприятия человеком.
The floor participant may request that the server handle the floor request with a certain priority using a PRIORITY attribute.
Участник пола может потребовать, чтобы сервер обработал запрос пола с определённым приоритетом, используя атрибут PRIORITY.
10.1.2. Receiving a Response
10.1.2. Получение ответа
A message from the floor control server is considered a response to the FloorRequest message if the message from the floor control server has the same Conference ID, Transaction ID, and User ID as the FloorRequest message, as described in Section 8.1. On receiving such a response, the floor participant follows the rules in Section 9 that relate to floor control server authentication. The successful processing of a FloorRequest message at the floor control server involves generating one or several FloorRequestStatus messages. The floor participant obtains a Floor Request ID in the Floor Request ID field of a FLOOR-REQUEST-INFORMATION attribute in the first FloorRequestStatus message from the floor control server. Subsequent FloorRequestStatus messages from the floor control server regarding the same floor request will carry the same Floor Request ID in a FLOOR-REQUEST-INFORMATION attribute as the initial FloorRequestStatus message. This way, the floor participant can associate subsequent incoming FloorRequestStatus messages with the ongoing floor request.
Сообщение от сервера управления полом считается ответом на сообщение FloorRequest, если сообщение от сервера управления полом имеет тот же Conference ID, Transaction ID и User ID, что и сообщение FloorRequest, как описано в разделе 8.1. При получении такого ответа участник пола следует правилам раздела 9, относящимся к аутентификации сервера управления полом. Успешная обработка сообщения FloorRequest на сервере управления полом включает генерацию одного или нескольких сообщений FloorRequestStatus. Участник пола получает Floor Request ID в поле Floor Request ID атрибута FLOOR-REQUEST-INFORMATION в первом сообщении FloorRequestStatus от сервера управления полом. Последующие сообщения FloorRequestStatus от сервера управления полом, касающиеся того же запроса пола, будут нести тот же Floor Request ID в атрибуте FLOOR-REQUEST-INFORMATION, что и первоначальное сообщение FloorRequestStatus. Так участник пола может сопоставить последующие поступающие сообщения FloorRequestStatus с текущим запросом пола.
The floor participant obtains information about the status of the floor request in the FLOOR-REQUEST-INFORMATION attribute of each of the FloorRequestStatus messages received from the floor control server. This attribute is a grouped attribute, and as such it includes a number of attributes that provide information about the floor request.
Участник пола получает сведения о состоянии запроса пола в атрибуте FLOOR-REQUEST-INFORMATION каждого из сообщений FloorRequestStatus, полученных от сервера управления полом. Этот атрибут является сгруппированным атрибутом и потому включает в себя ряд атрибутов, предоставляющих подробные сведения о конкретном запросе пола.
The OVERALL-REQUEST-STATUS attribute provides information about the overall status of the floor request. If the Request Status value is Granted, all the floors that were requested in the FloorRequest message have been granted. If the Request Status value is Denied, all the floors that were requested in the FloorRequest message have been denied. A floor request is considered to be ongoing while it is in the Pending, Accepted, or Granted states. If the floor request value is unknown, then the response is still processed. However, no meaningful value can be reported to the user.
Атрибут OVERALL-REQUEST-STATUS предоставляет сведения об общем состоянии запроса пола. Если значение Request Status равно Granted, все полы, запрошенные в сообщении FloorRequest, были предоставлены. Если значение Request Status равно Denied, все полы, запрошенные в сообщении FloorRequest, были отклонены. Запрос пола считается продолжающимся, пока он находится в состояниях Pending, Accepted или Granted. Если значение запроса пола неизвестно, ответ всё равно обрабатывается. Однако пользователю не может быть сообщено никакого осмысленного значения.
The STATUS-INFO attribute, if present, provides extra information that the floor participant MAY display to the user.
Атрибут STATUS-INFO, если присутствует, предоставляет дополнительную информацию, которую участник пола МОЖЕТ показать пользователю.
The FLOOR-REQUEST-STATUS attributes provide information about the status of the floor request as it relates to a particular floor. The STATUS-INFO attribute, if present, provides extra information that the floor participant MAY display to the user.
Атрибуты FLOOR-REQUEST-STATUS предоставляют сведения о состоянии запроса пола применительно к конкретному полу. Атрибут STATUS-INFO, если присутствует, предоставляет дополнительную информацию, которую участник пола МОЖЕТ показать пользователю.
The BENEFICIARY-INFORMATION attribute identifies the beneficiary of the floor request in third-party floor requests. The REQUESTED-BY-INFORMATION attribute need not be present in FloorRequestStatus messages received by the floor participant that requested the floor, as this floor participant is already identified by the User ID in the common header.
Атрибут BENEFICIARY-INFORMATION идентифицирует получателя запроса пола в запросах пола за третье лицо. Атрибут REQUESTED-BY-INFORMATION может отсутствовать в сообщениях FloorRequestStatus, получаемых участником пола, запросившим пол, поскольку этот участник пола уже идентифицирован User ID в общем заголовке.
The PRIORITY attribute, when present, contains the priority that was requested by the generator of the FloorRequest message. If the response is an Error message, the floor control server could not process the FloorRequest message for some reason, which is described in the Error message.
Атрибут PRIORITY, когда присутствует, содержит приоритет, запрошенный генератором сообщения FloorRequest. Если ответом является сообщение Error, сервер управления полом не смог обработать сообщение FloorRequest по некоторой причине, которая описана в сообщении Error.
10.2. Cancelling a Floor Request and Releasing a Floor
10.2. Отмена запроса пола и освобождение пола
A floor participant that wishes to cancel an ongoing floor request does so by sending a FloorRelease message to the floor control server. The FloorRelease message is also used by floor participants that hold a floor and would like to release it.
Участник пола, желающий отменить продолжающийся запрос пола, делает это, отправляя серверу управления полом сообщение FloorRelease. Сообщение FloorRelease также используется участниками пола, которые владеют полом и хотели бы его освободить.
10.2.1. Sending a FloorRelease Message
10.2.1. Отправка сообщения FloorRelease
The ABNF in Section 5.3.2 describes the attributes that a FloorRelease message can contain. In addition, the ABNF specifies normatively which of these attributes are mandatory, and which ones are optional.
ABNF в разделе 5.3.2 описывает атрибуты, которые может содержать сообщение FloorRelease. Кроме того, ABNF нормативно определяет, какие из этих атрибутов обязательны, а какие необязательны.
The floor participant sets the Conference ID and the Transaction ID in the common header following the rules given in Section 8.1.
Участник пола устанавливает Conference ID и Transaction ID в общем заголовке согласно правилам раздела 8.1.
The floor participant sets the User ID in the common header to the floor participant's identifier. This User ID will be used by the floor control server to authenticate and authorize the request.
Участник пола устанавливает User ID в общем заголовке в значение идентификатора участника пола. Этот User ID будет использоваться сервером управления полом для аутентификации и авторизации запроса.
Note that the FloorRelease message is used to release a floor or floors that were granted and to cancel ongoing floor requests (from the protocol perspective, both are ongoing floor requests). Using the same message in both situations helps resolve the race condition that occurs when the FloorRelease message and the FloorGrant message cross each other on the wire.
Заметим, что сообщение FloorRelease используется для освобождения предоставленного пола или полов и для отмены продолжающихся запросов пола (с точки зрения протокола и то и другое — продолжающиеся запросы пола). Использование одного и того же сообщения в обеих ситуациях помогает разрешить гонку, возникающую, когда сообщение FloorRelease и сообщение FloorGrant пересекаются в сети.
The floor participant uses the FLOOR-REQUEST-ID that was received in the response to the FloorRequest message that the FloorRelease message is cancelling.
Участник пола использует FLOOR-REQUEST-ID, полученный в ответе на сообщение FloorRequest, которое отменяет сообщение FloorRelease.
Note that if the floor participant requested several floors as an atomic operation (i.e., in a single FloorRequest message), all the floors are released as an atomic operation as well (i.e., all are released at the same time).
Заметим, что если участник пола запросил несколько полов как атомарную операцию (то есть в одном сообщении FloorRequest), все полы освобождаются также как атомарная операция (то есть все освобождаются одновременно).
10.2.2. Receiving a Response
10.2.2. Получение ответа
A message from the floor control server is considered a response to the FloorRelease message if the message from the floor control server has the same Conference ID, Transaction ID, and User ID as the FloorRequest message, as described in Section 8.1. On receiving such a response, the floor participant follows the rules in Section 9 that relate to floor control server authentication. If the response is a FloorRequestStatus message, the Request Status value in the OVERALL-REQUEST-STATUS attribute (within the FLOOR- REQUEST-INFORMATION grouped attribute) will be Cancelled or Released.
Сообщение от сервера управления полом считается ответом на сообщение FloorRelease, если сообщение от сервера управления полом имеет тот же Conference ID, Transaction ID и User ID, что и сообщение FloorRequest, как описано в разделе 8.1. При получении такого ответа участник пола следует правилам раздела 9, относящимся к аутентификации сервера управления полом. Если ответом является сообщение FloorRequestStatus, значение Request Status в атрибуте OVERALL-REQUEST-STATUS (внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION) будет Cancelled или Released.
If the response is an Error message, the floor control server could not process the FloorRequest message for some reason, which is described in the Error message.
Если ответом является сообщение Error, сервер управления полом не смог обработать сообщение FloorRequest по некоторой причине, которая описана в сообщении Error.
It is possible that the FloorRelease message crosses on the wire with a FloorRequestStatus message from the server with a Request Status different from Cancelled or Released. In any case, such a FloorRequestStatus message will not be a response to the FloorRelease message, as its Transaction ID will not match that of the FloorRelease.
Возможно, что сообщение FloorRelease пересекается в сети с сообщением FloorRequestStatus от сервера со значением Request Status, отличным от Cancelled или Released. В любом случае такое сообщение FloorRequestStatus не будет ответом на сообщение FloorRelease, поскольку его Transaction ID не совпадёт с Transaction ID сообщения FloorRelease.
11. Chair Operations
11. Операции председателя
This section specifies how floor chairs can instruct the floor control server to grant or revoke a floor using the protocol elements described in earlier sections.
В этом разделе указано, как председатели пола могут давать серверу управления полом указания предоставить или отозвать пол, используя элементы протокола, описанные в предыдущих разделах.
Floor chairs that wish to send instructions to a floor control server do so by sending a ChairAction message.
Председатели пола, желающие отправить серверу управления полом инструкции, делают это, отправляя сообщение ChairAction.
11.1. Sending a ChairAction Message
11.1. Отправка сообщения ChairAction
The ABNF in Section 5.3.9 describes the attributes that a ChairAction message can contain. In addition, the ABNF specifies normatively which of these attributes are mandatory, and which ones are optional.
ABNF в разделе 5.3.9 описывает атрибуты, которые может содержать сообщение ChairAction. Кроме того, ABNF нормативно определяет, какие из этих атрибутов обязательны, а какие необязательны.
The floor chair sets the Conference ID and the Transaction ID in the common header following the rules given in Section 8.1. The floor chair sets the User ID in the common header to the floor participant's identifier. This User ID will be used by the floor control server to authenticate and authorize the request.
Председатель пола устанавливает Conference ID и Transaction ID в общем заголовке согласно правилам раздела 8.1. Председатель пола устанавливает User ID в общем заголовке в значение идентификатора участника пола. Этот User ID будет использоваться сервером управления полом для аутентификации и авторизации запроса.
The ChairAction message contains instructions that apply to one or more floors within a particular floor request. The floor or floors are identified by the FLOOR-REQUEST-STATUS attributes and the floor request is identified by the FLOOR-REQUEST-INFORMATION-HEADER, which are carried in the ChairAction message.
Сообщение ChairAction содержит инструкции, которые применяются к одному или нескольким полам в рамках конкретного запроса пола. Пол или полы идентифицируются атрибутами FLOOR-REQUEST-STATUS, а запрос пола идентифицируется заголовком FLOOR-REQUEST-INFORMATION-HEADER, которые переносятся в сообщении ChairAction.
For example, if a floor request consists of two floors that depend on different floor chairs, each floor chair will grant its floor within the floor request. Once both chairs have granted their floor, the floor control server will grant the floor request as a whole. On the other hand, if one of the floor chairs denies its floor, the floor control server will deny the floor request as a whole, regardless of the other floor chair's decision.
Например, если запрос пола состоит из двух полов, зависящих от разных председателей пола, каждый председатель пола предоставит свой пол в рамках запроса пола. Как только оба председателя предоставят свои полы, сервер управления полом предоставит запрос пола целиком. С другой стороны, если один из председателей пола отклонит свой пол, сервер управления полом отклонит запрос пола целиком, независимо от решения другого председателя пола.
The floor chair provides the new status of the floor request as it relates to a particular floor using a FLOOR-REQUEST-STATUS attribute. If the new status of the floor request is Accepted, the floor chair MAY use the Queue Position field to provide a queue position for the floor request. If the floor chair does not wish to provide a queue position, all the bits of the Queue Position field SHOULD be set to zero. The floor chair SHOULD use the Status Revoked to revoke a floor that was granted (i.e., Granted status) and SHOULD use the Status Denied to reject floor requests in any other status (e.g., Pending and Accepted).
Председатель пола указывает новое состояние запроса пола применительно к конкретному полу с помощью атрибута FLOOR-REQUEST-STATUS. Если новое состояние запроса пола — Accepted, председатель пола МОЖЕТ использовать поле Queue Position, чтобы указать позицию запроса пола в очереди. Если председатель пола не хочет указывать позицию в очереди, все биты поля Queue Position СЛЕДУЕТ установить в ноль. Председателю пола СЛЕДУЕТ использовать статус Revoked для отзыва ранее предоставленного пола (то есть статуса Granted) и СЛЕДУЕТ использовать статус Denied для отклонения запросов пола в любом другом статусе (например, Pending и Accepted).
The floor chair MAY add an OVERALL-REQUEST-STATUS attribute to the ChairAction message to provide a new overall status for the floor request. If the new overall status of the floor request is Accepted, the floor chair MAY use the Queue Position field to provide a queue position for the floor request.
Председатель пола МОЖЕТ добавить атрибут OVERALL-REQUEST-STATUS в сообщение ChairAction, чтобы указать новое общее состояние запроса пола. Если новое общее состояние запроса пола — Accepted, председатель пола МОЖЕТ использовать поле Queue Position, чтобы указать позицию запроса пола в очереди.
Note that a particular floor control server may implement a different queue for each floor containing all the floor requests that relate to that particular floor, a general queue for all floor requests, or both. Also note that a floor request may involve several floors and that a ChairAction message may only deal with a subset of these floors (e.g., if a single floor chair is not authorized to manage all the floors). In this case, the floor control server will combine the instructions received from the different floor chairs in FLOOR-REQUEST-STATUS attributes to come up with the overall status of the floor request.
Заметим, что конкретный сервер управления полом может реализовывать отдельную очередь для каждого пола, содержащую все запросы пола, относящиеся к этому полу, общую очередь для всех запросов пола или и то и другое. Заметим также, что запрос пола может затрагивать несколько полов, а сообщение ChairAction может касаться только части этих полов (например, если один председатель пола не уполномочен управлять всеми полами). В этом случае сервер управления полом объединит инструкции, полученные от разных председателей пола в атрибутах FLOOR-REQUEST-STATUS, чтобы получить общее состояние запроса пола.
Note that, while the action of a floor chair may communicate information in the OVERALL-REQUEST-STATUS attribute, the floor control server may override, modify, or ignore this field's content.
Заметим, что, хотя действие председателя пола может передавать информацию в атрибуте OVERALL-REQUEST-STATUS, сервер управления полом может переопределить, изменить или проигнорировать содержимое этого поля.
The floor chair may use STATUS-INFO attributes to state the reason why the floor or floors are being accepted, granted, or revoked. The Text in the STATUS-INFO attribute is intended for human consumption.
Председатель пола может использовать атрибуты STATUS-INFO, чтобы указать причину, по которой пол или полы принимаются, предоставляются или отзываются. Текст в атрибуте STATUS-INFO предназначен для восприятия человеком.
11.2. Receiving a Response
11.2. Получение ответа
A message from the floor control server is considered a response to the ChairAction message if the message from the server has the same Conference ID, Transaction ID, and User ID as the ChairAction message, as described in Section 8.1. On receiving such a response, the floor chair follows the rules in Section 9 that relate to floor control server authentication. A ChairActionAck message from the floor control server confirms that the floor control server has accepted the ChairAction message. An Error message indicates that the floor control server could not process the ChairAction message for some reason, which is described in the Error message.
Сообщение от сервера управления полом считается ответом на сообщение ChairAction, если это сообщение имеет тот же Conference ID, Transaction ID и User ID, что и сообщение ChairAction, как описано в разделе 8.1. При получении такого ответа председатель пола следует правилам раздела 9, относящимся к аутентификации сервера управления полом. Сообщение ChairActionAck от сервера управления полом подтверждает, что сервер управления полом принял сообщение ChairAction. Сообщение Error означает, что сервер управления полом не смог обработать сообщение ChairAction по некоторой причине, описанной в сообщении Error.
12. General Client Operations
12. Общие операции клиента
This section specifies operations that can be performed by any client. That is, they are not specific to floor participants or floor chairs. They can be performed by both.
В этом разделе описаны операции, которые может выполнять любой клиент. То есть они не специфичны для участников пола или председателей пола. Их могут выполнять и те, и другие.
12.1. Requesting Information about Floors
12.1. Запрос сведений о полах
A client can obtain information about the status of a floor or floors in different ways, which include using BFCP and using out-of-band mechanisms. Clients using BFCP to obtain such information use the procedures described in this section.
Клиент может получать сведения о состоянии пола или полов разными способами, в том числе с помощью BFCP и с помощью внешних механизмов. Клиенты, использующие для этого BFCP, применяют процедуры, описанные в этом разделе.
Clients request information about the status of one or several floors by sending a FloorQuery message to the floor control server.
Клиенты запрашивают сведения о состоянии одного или нескольких полов, отправляя серверу управления полом сообщение FloorQuery.
12.1.1. Sending a FloorQuery Message
12.1.1. Отправка сообщения FloorQuery
The ABNF in Section 5.3.7 describes the attributes that a FloorQuery message can contain. In addition, the ABNF specifies normatively which of these attributes are mandatory, and which ones are optional.
ABNF в разделе 5.3.7 описывает атрибуты, которые может содержать сообщение FloorQuery. Кроме того, ABNF нормативно определяет, какие из этих атрибутов обязательны, а какие необязательны.
The client sets the Conference ID and the Transaction ID in the common header following the rules given in Section 8.1. The client sets the User ID in the common header to the client's identifier. This User ID will be used by the floor control server to authenticate and authorize the request.
Клиент устанавливает Conference ID и Transaction ID в общем заголовке согласно правилам раздела 8.1. Клиент устанавливает User ID в общем заголовке в значение идентификатора клиента. Этот User ID будет использоваться сервером управления полом для аутентификации и авторизации запроса.
The client inserts in the message all the Floor IDs it wants to receive information about. The floor control server will send periodic information about all of these floors. If the client does not want to receive information about a particular floor any longer, it sends a new FloorQuery message removing the FLOOR-ID of this floor. If the client does not want to receive information about any floor any longer, it sends a FloorQuery message with no FLOOR-ID attribute.
Клиент вставляет в сообщение все Floor ID, сведения о которых он хочет получать. Сервер управления полом будет периодически отправлять сведения обо всех этих полах. Если клиент больше не хочет получать сведения о конкретном поле, он отправляет новое сообщение FloorQuery, удалив FLOOR-ID этого пола. Если клиент больше не хочет получать сведения ни об одном поле, он отправляет сообщение FloorQuery без атрибута FLOOR-ID.
12.1.2. Receiving a Response
12.1.2. Получение ответа
A message from the floor control server is considered a response to the FloorQuery message if the message from the floor control server has the same Conference ID, Transaction ID, and User ID as the FloorRequest message, as described in Section 8.1. On receiving such a response, the client follows the rules in Section 9 that relate to floor control server authentication.
Сообщение от сервера управления полом считается ответом на сообщение FloorQuery, если это сообщение имеет тот же Conference ID, Transaction ID и User ID, что и сообщение FloorRequest, как описано в разделе 8.1. При получении такого ответа клиент следует правилам раздела 9, относящимся к аутентификации сервера управления полом.
On reception of the FloorQuery message, the floor control server will respond with a FloorStatus message or with an Error message. If the response is a FloorStatus message, it will contain information about one of the floors the client requested information about. If the client did not include any FLOOR-ID attribute in its FloorQuery message (i.e., the client does not want to receive information about any floor any longer), the FloorStatus message from the floor control server will not include any FLOOR-ID attribute either.
При получении сообщения FloorQuery сервер управления полом отвечает сообщением FloorStatus или сообщением Error. Если ответом является сообщение FloorStatus, оно будет содержать сведения об одном из полов, о которых клиент запросил информацию. Если клиент не включил в своё сообщение FloorQuery ни одного атрибута FLOOR-ID (то есть больше не хочет получать сведения ни об одном поле), сообщение FloorStatus от сервера управления полом также не будет содержать ни одного атрибута FLOOR-ID.
FloorStatus messages that carry information about a floor contain a FLOOR-ID attribute that identifies the floor. After this attribute, FloorStatus messages contain information about existing (one or more) floor requests that relate to that floor. The information about each particular floor request is encoded in a FLOOR-REQUEST-INFORMATION attribute. This grouped attribute carries a Floor Request ID that identifies the floor request, followed by a set of attributes that provide information about the floor request.
Сообщения FloorStatus, несущие сведения о поле, содержат атрибут FLOOR-ID, идентифицирующий пол. После этого атрибута сообщения FloorStatus содержат сведения о существующих (одном или нескольких) запросах пола, относящихся к этому полу. Сведения о каждом конкретном запросе пола кодируются в атрибуте FLOOR-REQUEST-INFORMATION. Этот сгруппированный атрибут несёт Floor Request ID, идентифицирующий запрос пола, за которым следует набор атрибутов, предоставляющих сведения о запросе пола.
After the first FloorStatus, the floor control server will continue sending FloorStatus messages, periodically informing the client about changes on the floors the client requested information about.
После первого сообщения FloorStatus сервер управления полом продолжает отправлять сообщения FloorStatus, периодически информируя клиента об изменениях полов, о которых клиент запросил сведения.
12.2. Requesting Information about Floor Requests
12.2. Запрос сведений о запросах пола
A client can obtain information about the status of one or several floor requests in different ways, which include using BFCP and using out-of-band mechanisms. Clients using BFCP to obtain such information use the procedures described in this section.
Клиент может получать сведения о состоянии одного или нескольких запросов пола разными способами, в том числе с помощью BFCP и с помощью внешних механизмов. Клиенты, использующие для этого BFCP, применяют процедуры, описанные в этом разделе.
Clients request information about the current status of a floor request by sending a FloorRequestQuery message to the floor control server.
Клиенты запрашивают сведения о текущем состоянии запроса пола, отправляя серверу управления полом сообщение FloorRequestQuery.
Requesting information about a particular floor request is useful in a number of situations. For example, on reception of a FloorRequest message, a floor control server may choose to return FloorRequestStatus messages only when the floor request changes its state (e.g., from Accepted to Granted), but not when the floor request advances in its queue. In this situation, if the user requests it, the floor participant can use a FloorRequestQuery message to poll the floor control server for the status of the floor request.
Запрос сведений о конкретном запросе пола полезен в ряде ситуаций. Например, при получении сообщения FloorRequest сервер управления полом может решить возвращать сообщения FloorRequestStatus только при изменении состояния запроса пола (например, с Accepted на Granted), но не при продвижении запроса пола в очереди. В этой ситуации участник пола, если пользователь того потребует, может использовать сообщение FloorRequestQuery для опроса сервера управления полом о состоянии запроса пола.
12.2.1. Sending a FloorRequestQuery Message
12.2.1. Отправка сообщения FloorRequestQuery
The ABNF in Section 5.3.3 describes the attributes that a FloorRequestQuery message can contain. In addition, the ABNF specifies normatively which of these attributes are mandatory, and which ones are optional.
ABNF в разделе 5.3.3 описывает атрибуты, которые может содержать сообщение FloorRequestQuery. Кроме того, ABNF нормативно определяет, какие из этих атрибутов обязательны, а какие необязательны.

Клиент должен вставить атрибут FLOOR-REQUEST-ID, идентифицирующий запрос пола на сервере управления полом.

12.2.2. Получение ответа

13. Floor Control Server Operations
13. Операции сервера управления полом
This section specifies how floor control servers can perform different operations, such as granting a floor, using the protocol elements described in earlier sections.
В этом разделе описано, как серверы управления полом выполняют различные операции, например предоставление пола, с использованием элементов протокола, описанных в предыдущих разделах.
On reception of a message from a client, the floor control server MUST check whether the value of the Primitive is supported. If it does not, the floor control server SHOULD send an Error message, as described in Section 13.8, with Error code 3 (Unknown Primitive).
При получении сообщения от клиента сервер управления полом ДОЛЖЕН проверить, поддерживается ли значение Primitive. Если нет, серверу управления полом СЛЕДУЕТ отправить сообщение Error, как описано в разделе 13.8, с кодом ошибки 3 (Unknown Primitive).

При получении сообщения от клиента сервер управления полом ДОЛЖЕН проверить, соответствует ли значение Conference ID существующей конференции. При получении сообщения от клиента сервер управления полом ДОЛЖЕН проверить, понимает ли он все обязательные атрибуты (с установленным битом 'M') в сообщении. Если сервер управления полом понимает не все из них, ему СЛЕДУЕТ отправить сообщение Error, как описано в разделе 13.8, с кодом ошибки 2 (Authentication Failed). В сообщении Error СЛЕДУЕТ перечислить атрибуты, которые не были поняты.
13.1. Reception of a FloorRequest Message
13.1. Приём сообщения FloorRequest
On reception of a FloorRequest message, the floor control server follows the rules in Section 9 that relate to client authentication and authorization. If while processing the FloorRequest message, the floor control server encounters an error, it SHOULD generate an Error response following the procedures described in Section 13.8.
При получении сообщения FloorRequest сервер управления полом следует правилам раздела 9, относящимся к аутентификации и авторизации клиента. Если при обработке сообщения FloorRequest сервер управления полом сталкивается с ошибкой, ему СЛЕДУЕТ сгенерировать ответ Error согласно процедурам, описанным в разделе 13.8.
BFCP allows floor participants to have several ongoing floor requests for the same floor (e.g., the same floor participant can occupy more than one position in a queue at the same time). A floor control server that only supports a certain number of ongoing floor requests per floor participant (e.g., one) can use Error Code 8 (You have Already Reached the Maximum Number of Ongoing Floor Requests for this Floor) to inform the floor participant.
BFCP позволяет участникам пола иметь несколько продолжающихся запросов пола для одного и того же пола (например, один и тот же участник пола может одновременно занимать более одной позиции в очереди). Сервер управления полом, поддерживающий лишь определённое число продолжающихся запросов пола на участника пола (например, один), может использовать код ошибки 8 (You have Already Reached the Maximum Number of Ongoing Floor Requests for this Floor), чтобы сообщить об этом участнику пола.
13.1.1. Generating the First FloorRequestStatus Message
13.1.1. Генерация первого сообщения FloorRequestStatus
The successful processing of a FloorRequest message by a floor control server involves generating one or several FloorRequestStatus messages, the first of which SHOULD be generated as soon as possible. If the floor control server cannot accept, grant, or deny the floor request right away (e.g., a decision from a chair is needed), it SHOULD use a Request Status value of Pending in the OVERALL-REQUEST- STATUS attribute (within the FLOOR-REQUEST-INFORMATION grouped attribute) of the first FloorRequestStatus message it generates.
Успешная обработка сообщения FloorRequest сервером управления полом включает генерацию одного или нескольких сообщений FloorRequestStatus, первое из которых СЛЕДУЕТ сгенерировать как можно скорее. Если сервер управления полом не может немедленно принять, предоставить или отклонить запрос пола (например, требуется решение председателя), ему СЛЕДУЕТ использовать значение Request Status, равное Pending, в атрибуте OVERALL-REQUEST-STATUS (внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION) первого генерируемого сообщения FloorRequestStatus.
The policy that a floor control server follows to grant or deny floors is outside the scope of this document. A given floor control server may perform these decisions automatically while another may contact a human acting as a chair every time a decision needs to be made.
Политика, которой следует сервер управления полом при предоставлении или отклонении полов, находится вне области применения настоящего документа. Данный сервер управления полом может принимать такие решения автоматически, тогда как другой может обращаться к человеку, исполняющему роль председателя, каждый раз, когда нужно принять решение.
The floor control server MUST copy the Conference ID, the Transaction ID, and the User ID from the FloorRequest into the FloorRequestStatus, as described in Section 8.2. Additionally, the floor control server MUST add a FLOOR-REQUEST-INFORMATION grouped attribute to the FloorRequestStatus. The attributes contained in this grouped attribute carry information about the floor request.
Сервер управления полом ДОЛЖЕН скопировать Conference ID, Transaction ID и User ID из сообщения FloorRequest в сообщение FloorRequestStatus, как описано в разделе 8.2. Кроме того, сервер управления полом ДОЛЖЕН добавить сгруппированный атрибут FLOOR-REQUEST-INFORMATION в сообщение FloorRequestStatus. Атрибуты, содержащиеся в этом сгруппированном атрибуте, несут сведения о запросе пола.
The floor control server MUST assign an identifier that is unique within the conference to this floor request, and MUST insert it in the Floor Request ID field of the FLOOR-REQUEST-INFORMATION attribute. This identifier will be used by the floor participant (or by a chair or chairs) to refer to this specific floor request in the future.
Сервер управления полом ДОЛЖЕН назначить этому запросу пола идентификатор, уникальный в рамках конференции, и ДОЛЖЕН вставить его в поле Floor Request ID атрибута FLOOR-REQUEST-INFORMATION. Этот идентификатор будет использоваться участником пола (или председателем либо председателями) для ссылки на этот конкретный запрос пола в дальнейшем.
The floor control server MUST copy the Floor IDs in the FLOOR-ID attributes of the FloorRequest into the FLOOR-REQUEST-STATUS attributes in the FLOOR-REQUEST-INFORMATION grouped attribute. These Floor IDs identify the floors being requested (i.e., the floors associated with this particular floor request).
Сервер управления полом ДОЛЖЕН скопировать Floor ID из атрибутов FLOOR-ID сообщения FloorRequest в атрибуты FLOOR-REQUEST-STATUS внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION. Эти Floor ID идентифицируют запрашиваемые полы (то есть полы, связанные с этим конкретным запросом пола).
The floor control server SHOULD copy (if present) the contents of the BENEFICIARY-ID attribute from the FloorRequest into a BENEFICIARY-INFORMATION attribute inside the FLOOR-REQUEST-INFORMATION grouped attribute. Additionally, the floor control server MAY provide the display name and the URI of the beneficiary in this BENEFICIARY-INFORMATION attribute.
Серверу управления полом СЛЕДУЕТ скопировать (если присутствует) содержимое атрибута BENEFICIARY-ID из сообщения FloorRequest в атрибут BENEFICIARY-INFORMATION внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION. Кроме того, сервер управления полом МОЖЕТ предоставить отображаемое имя и URI получателя в этом атрибуте BENEFICIARY-INFORMATION.
The floor control server MAY provide information about the requester of the floor in a REQUESTED-BY-INFORMATION attribute inside the FLOOR-REQUEST-INFORMATION grouped attribute.
Сервер управления полом МОЖЕТ предоставить сведения о запрашивающей стороне в атрибуте REQUESTED-BY-INFORMATION внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION.
The floor control server MAY copy (if present) the PARTICIPANT- PROVIDED-INFO attribute from the FloorRequest into the FLOOR- REQUEST-INFORMATION grouped attribute.
Сервер управления полом МОЖЕТ скопировать (если присутствует) атрибут PARTICIPANT-PROVIDED-INFO из сообщения FloorRequest в сгруппированный атрибут FLOOR-REQUEST-INFORMATION.
Note that this attribute carries the priority requested by the participant. The priority that the floor control server assigns to the floor request depends on the priority requested by the participant and the rights the participant has according to the policy of the conference. For example, a participant that is only allowed to use the Normal priority may request Highest priority for a floor request. In that case, the floor control server would ignore the priority requested by the participant.
Заметим, что этот атрибут несёт приоритет, запрошенный участником. Приоритет, который сервер управления полом назначает запросу пола, зависит от приоритета, запрошенного участником, и от прав, которыми участник обладает согласно политике конференции. Например, участник, которому разрешено использовать только приоритет Normal, может запросить для запроса пола приоритет Highest. В этом случае сервер управления полом проигнорирует приоритет, запрошенный участником.
The floor control server MAY copy (if present) the PARTICIPANT-PROVIDED-INFO attribute from the FloorRequest into the FLOOR-REQUEST-INFORMATION grouped attribute.
Сервер управления полом МОЖЕТ скопировать атрибут PARTICIPANT-PROVIDED-INFO из сообщения FloorRequest в сгруппированный атрибут FLOOR-REQUEST-INFORMATION, если он присутствует.
13.1.2. Generation of Subsequent FloorRequestStatus Messages
13.1.2. Генерация последующих сообщений FloorRequestStatus
A floor request is considered to be ongoing as long as it is not in the Cancelled, Released, or Revoked states. If the OVERALL-REQUEST- STATUS attribute (inside the FLOOR-REQUEST-INFORMATION grouped attribute) of the first FloorRequestStatus message generated by the floor control server did not indicate any of these states, the floor control server will need to send subsequent FloorRequestStatus messages.
Запрос пола считается продолжающимся, пока он не находится в состояниях Cancelled, Released или Revoked. Если атрибут OVERALL-REQUEST-STATUS (внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION) первого сообщения FloorRequestStatus, сгенерированного сервером управления полом, не указывал ни одного из этих состояний, серверу управления полом нужно будет отправлять последующие сообщения FloorRequestStatus.
When the status of the floor request changes, the floor control server SHOULD send new FloorRequestStatus messages with the appropriate Request Status. The floor control server MUST add a FLOOR-REQUEST-INFORMATION attribute with a Floor Request ID equal to the one sent in the first FloorRequestStatus message to any new FloorRequestStatus related to the same floor request. (The Floor Request ID identifies the floor request to which the FloorRequestStatus applies.)

The floor control server SHOULD add a BENEFICIARY-ID attribute to the FLOOR-REQUEST-INFORMATION grouped attribute identifying the beneficiary of the floor request. Additionally, the floor control server MAY provide the display name and the URI of the beneficiary in this BENEFICIARY-INFORMATION attribute.
Сервер управления полом СЛЕДУЕТ добавить атрибут BENEFICIARY-ID в сгруппированный атрибут FLOOR-REQUEST-INFORMATION, идентифицирующий получателя запроса пола. Кроме того, сервер управления полом МОЖЕТ предоставить отображаемое имя и URI получателя в этом атрибуте BENEFICIARY-INFORMATION.
The floor control server MAY provide information about the requester of the floor in a REQUESTED-BY-INFORMATION attribute inside the FLOOR-REQUEST-INFORMATION grouped attribute.
Сервер управления полом МОЖЕТ предоставить сведения о запрашивающей стороне в атрибуте REQUESTED-BY-INFORMATION внутри сгруппированного атрибута FLOOR-REQUEST-INFORMATION.
The floor control server MAY provide the reason why the floor participant requested the floor in a PARTICIPANT-PROVIDED-INFO.
Сервер управления полом МОЖЕТ предоставить причину, по которой участник пола запросил пол, в атрибуте PARTICIPANT-PROVIDED-INFO.
The floor control server MAY also add to the FLOOR-REQUEST- INFORMATION grouped attribute a PRIORITY attribute with the Priority value requested for the floor request.
Сервер управления полом МОЖЕТ также добавить в сгруппированный атрибут FLOOR-REQUEST-INFORMATION атрибут PRIORITY со значением приоритета, запрошенным для запроса пола.
The floor control server MUST add an OVERALL-REQUEST-STATUS attribute to the FLOOR-REQUEST-INFORMATION grouped attribute with the current status of the floor request. The floor control server MAY add a STATUS-INFO attribute with extra information about the floor request.
Сервер управления полом ДОЛЖЕН добавить атрибут OVERALL-REQUEST-STATUS в сгруппированный атрибут FLOOR-REQUEST-INFORMATION с текущим состоянием запроса пола. Сервер управления полом МОЖЕТ добавить атрибут STATUS-INFO с дополнительными сведениями о запросе пола.
The floor control server MAY provide information about the status of the floor request as it relates to each of the floors being requested in the FLOOR-REQUEST-STATUS attributes.
Сервер управления полом МОЖЕТ предоставлять сведения о состоянии запроса пола применительно к каждому из запрашиваемых полов в атрибутах FLOOR-REQUEST-STATUS.
13.5.2. Generation of Subsequent FloorStatus Messages
13.5.2. Генерация последующих сообщений FloorStatus
If the FloorQuery message carried more than one FLOOR-ID attribute, the floor control server SHOULD generate a FloorStatus message for each of them (except for the FLOOR-ID attribute chosen for the first FloorStatus message) as soon as possible. These FloorStatus messages are generated following the same rules as those for the first FloorStatus message (see Section 13.5.1), but their Transaction ID is 0.
Если сообщение FloorQuery несло более одного атрибута FLOOR-ID, сервер управления полом СЛЕДУЕТ сгенерировать сообщение FloorStatus для каждого из них (кроме атрибута FLOOR-ID, выбранного для первого сообщения FloorStatus) как можно скорее. Эти сообщения FloorStatus генерируются по тем же правилам, что и первое сообщение FloorStatus (см. раздел 13.5.1), но их Transaction ID равен 0.
After generating these messages, the floor control server sends FloorStatus messages, periodically keeping the client informed about all the floors for which the client requested information. The Transaction ID of these messages MUST be 0.
После генерации этих сообщений сервер управления полом отправляет сообщения FloorStatus, периодически держа клиента в курсе всех полов, о которых клиент запросил сведения. Transaction ID этих сообщений ДОЛЖЕН быть равен 0.
The rate at which the floor control server sends FloorStatus messages is a matter of local policy. A floor control server may choose to send a new FloorStatus message every time a new floor request arrives, while another may choose to only send a new FloorStatus message when a new floor request is Granted.
Частота, с которой сервер управления полом отправляет сообщения FloorStatus, определяется локальной политикой. Один сервер управления полом может отправлять новое сообщение FloorStatus при каждом поступлении нового запроса пола, а другой — только когда новый запрос пола получает статус Granted.
13.6. Reception of a ChairAction Message
13.6. Приём сообщения ChairAction
On reception of a ChairAction message, the floor control server follows the rules in Section 9 that relate to client authentication and authorization. If while processing the ChairAction message, the floor control server encounters an error, it SHOULD generate an Error response following the procedures described in Section 13.8.
При получении сообщения ChairAction сервер управления полом следует правилам раздела 9, относящимся к аутентификации и авторизации клиента. Если при обработке сообщения ChairAction сервер управления полом сталкивается с ошибкой, ему СЛЕДУЕТ сгенерировать ответ Error согласно процедурам, описанным в разделе 13.8.
The successful processing of a ChairAction message by a floor control server involves generating a ChairActionAck message, which SHOULD be generated as soon as possible. The floor control server MUST copy the Conference ID, the Transaction ID, and the User ID from the ChairAction message into the ChairActionAck message, as described in Section 8.2.
Успешная обработка сообщения ChairAction сервером управления полом включает генерацию сообщения ChairActionAck, которое СЛЕДУЕТ сгенерировать как можно скорее. Сервер управления полом ДОЛЖЕН скопировать Conference ID, Transaction ID и User ID из сообщения ChairAction в сообщение ChairActionAck, как описано в разделе 8.2.
The floor control server needs to take into consideration the operation requested in the ChairAction message (e.g., granting a floor) but does not necessarily need to perform it as requested by the floor chair. The operation that the floor control server performs depends on the ChairAction message and on the internal state of the floor control server.
Серверу управления полом нужно принимать во внимание операцию, запрошенную в сообщении ChairAction (например, предоставление пола), но не обязательно выполнять её так, как запросил председатель пола. Выполняемая сервером управления полом операция зависит от сообщения ChairAction и от внутреннего состояния сервера управления полом.
For example, a floor chair may send a ChairAction message granting a floor that was requested as part of an atomic floor request operation that involved several floors. Even if the chair responsible for one of the floors instructs the floor control server to grant the floor, the floor control server will not grant it until the chairs responsible for the other floors agree to grant them as well.
Например, председатель пола может отправить сообщение ChairAction, предоставляющее пол, который был запрошен в рамках атомарной операции запроса пола, затрагивающей несколько полов. Даже если председатель, отвечающий за один из полов, даёт серверу управления полом указание предоставить пол, сервер управления полом не предоставит его, пока председатели, отвечающие за остальные полы, не согласятся их предоставить.
So, the floor control server is ultimately responsible for keeping a coherent floor state using instructions from floor chairs as input to this state.
Таким образом, сервер управления полом в конечном счёте отвечает за поддержание согласованного состояния полов, используя инструкции председателей пола как входные данные для этого состояния.
If the new Status in the ChairAction message is Accepted and all the bits of the Queue Position field are zero, the floor chair is requesting that the floor control server assign a queue position (e.g., the last in the queue) to the floor request based on the local policy of the floor control server. (Of course, such a request only applies if the floor control server implements a queue.)
Если новое значение Status в сообщении ChairAction равно Accepted и все биты поля Queue Position нулевые, председатель пола просит сервер управления полом назначить запросу пола позицию в очереди (например, последнюю в очереди) на основе локальной политики сервера управления полом. (Разумеется, такой запрос применим, только если сервер управления полом реализует очередь.)

The floor control server MUST add a SUPPORTED-PRIMITIVES attribute to the HelloAck message listing all the primitives (i.e., BFCP messages) supported by the floor control server. The floor control server MUST add a SUPPORTED-ATTRIBUTES attribute to the HelloAck message listing all the attributes supported by the floor control server.

Сервер управления полом ДОЛЖЕН добавить в сообщение HelloAck атрибут SUPPORTED-ATTRIBUTES, перечисляющий все атрибуты, поддерживаемые сервером управления полом.

14. Security Considerations
14. Вопросы безопасности
BFCP uses TLS to provide mutual authentication between clients and servers. TLS also provides replay and integrity protection and confidentiality. It is RECOMMENDED that TLS with non-null encryption always be used. BFCP entities MAY use other security mechanisms as long as they provide similar security properties.
BFCP использует TLS для обеспечения взаимной аутентификации клиентов и серверов. TLS также обеспечивает защиту от повторного воспроизведения, целостность и конфиденциальность. РЕКОМЕНДУЕТСЯ всегда использовать TLS с ненулевым шифрованием. Сущности BFCP МОГУТ использовать другие механизмы безопасности, если они обеспечивают аналогичные свойства безопасности.
The remainder of this section analyzes some of the threats against BFCP and how they are addressed.
Остальная часть этого раздела анализирует некоторые угрозы для BFCP и то, как им противодействуют.
An attacker may attempt to impersonate a client (a floor participant or a floor chair) in order to generate forged floor requests or to grant or deny existing floor requests. Client impersonation is avoided by having servers only accept BFCP messages over authenticated TLS connections. The floor control server assumes that attackers cannot highjack the TLS connection and, therefore, that messages over the TLS connection come from the client that was initially authenticated.
Злоумышленник может попытаться выдать себя за клиента (участника пола или председателя пола), чтобы сгенерировать поддельные запросы пола или предоставить либо отклонить существующие запросы пола. Выдаче себя за клиента противодействует то, что серверы принимают сообщения BFCP только по аутентифицированным TLS-соединениям. Сервер управления полом исходит из того, что злоумышленники не могут перехватить TLS-соединение и, следовательно, сообщения по TLS-соединению приходят от клиента, прошедшего первоначальную аутентификацию.
An attacker may attempt to impersonate a floor control server. A successful attacker would be able to make clients think that they hold a particular floor so that they would try to access a resource (e.g., sending media) without having legitimate rights to access it. Floor control server impersonation is avoided by having servers only accept BFCP messages over authenticated TLS connections. Attackers may attempt to modify messages exchanged by a client and a floor control server. The integrity protection provided by TLS connections prevents this attack.
Злоумышленник может попытаться выдать себя за сервер управления полом. Успешный злоумышленник смог бы заставить клиентов думать, что они владеют определённым полом, чтобы они попытались получить доступ к ресурсу (например, отправлять медиа), не имея законных прав на такой доступ. Выдаче себя за сервер управления полом противодействует то, что серверы принимают сообщения BFCP только по аутентифицированным TLS-соединениям. Злоумышленники могут пытаться изменить сообщения, которыми обмениваются клиент и сервер управления полом. Защита целостности, обеспечиваемая TLS-соединениями, предотвращает эту атаку.
An attacker may attempt to fetch a valid message sent by a client to a floor control server and replay it over a connection between the attacker and the floor control server. This attack is prevented by having floor control servers check that messages arriving over a given authenticated TLS connection use an authorized user ID (i.e., a user ID that the user that established the authenticated TLS connection is allowed to use).
Злоумышленник может попытаться перехватить допустимое сообщение, отправленное клиентом серверу управления полом, и воспроизвести его по соединению между злоумышленником и сервером управления полом. Этой атаке противодействует то, что серверы управления полом проверяют, используют ли сообщения, приходящие по данному аутентифицированному TLS-соединению, авторизованный User ID (то есть User ID, который пользователю, установившему аутентифицированное TLS-соединение, разрешено использовать).
Attackers may attempt to pick messages from the network to get access to confidential information between the floor control server and a client (e.g., why a floor request was denied). TLS confidentiality prevents this attack. Therefore, it is RECOMMENDED that TLS be used with a non-null encryption algorithm.
Злоумышленники могут пытаться перехватывать сообщения из сети, чтобы получить доступ к конфиденциальной информации, которой обмениваются сервер управления полом и клиент (например, к причине отказа в запросе пола). Конфиденциальность TLS предотвращает эту атаку. Поэтому РЕКОМЕНДУЕТСЯ использовать TLS с ненулевым алгоритмом шифрования.
