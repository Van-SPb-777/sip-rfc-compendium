1. Introduction
1. Введение
Session recording is a critical requirement in many communications environments, such as call centers and financial trading organizations. In some of these environments, all calls must be recorded for regulatory, compliance, and consumer protection reasons. The recording of a session is typically performed by sending a copy of a media stream to a recording device. This document focuses on the recording metadata, which describes the Communication Session (CS). The document describes a metadata model as viewed by the Session Recording Server (SRS) and the recording metadata format, the requirements for which are described in [RFC6341] and the architecture for which is described in [RFC7245].
Запись сеансов является критически важным требованием во многих средах связи, таких как контакт-центры и организации финансовой торговли. В некоторых из этих сред все вызовы должны записываться по причинам соответствия нормативным требованиям, законодательству и защиты потребителей. Запись сеанса обычно выполняется путём отправки копии медиапотока на устройство записи. Настоящий документ посвящён метаданным записи, которые описывают сеанс связи (CS). В документе описываются модель метаданных с точки зрения сервера записи сеансов (SRS) и формат метаданных записи, требования к которым изложены в [RFC6341], а архитектура — в [RFC7245].

The model allows metadata describing CSs to be communicated to the SRS as a series of snapshots, each representing the state as seen by a single SRC at a particular instant in time. Metadata changes from one snapshot to another reflect changes in what is being recorded. For example, if a participant joins a conference, then the SRC sends the SRS a snapshot of metadata having that participant information (with attributes like (Name, AoR) tuple and associate-time). (Note: "AoR" means "Address-of-Record".)
Модель позволяет передавать метаданные, описывающие сеансы связи (CS), на SRS в виде последовательности снимков, каждый из которых представляет состояние, видимое одним SRC в определённый момент времени. Изменения метаданных от одного снимка к другому отражают изменения в записываемом содержимом. Например, если участник присоединяется к конференции, SRC отправляет SRS снимок метаданных с информацией об этом участнике (с такими атрибутами, как кортеж (Name, AoR), и associate-time). (Примечание: «AoR» означает «Address-of-Record».)
Some of the metadata is not required to be conveyed explicitly from the SRC to the SRS, if it can be obtained contextually by the SRS (e.g., from SIP or Session Description Protocol (SDP) signaling). For example, the 'label' attribute within the 'stream' XML element references an SDP "a=label" attribute that identifies an m-line within the Recording Session (RS) SDP. The SRS would learn the media properties from the media line.
Некоторые метаданные не требуется передавать от SRC к SRS в явном виде, если SRS может получить их контекстно (например, из сигнализации SIP или протокола описания сеансов (SDP)). Например, атрибут 'label' внутри XML-элемента 'stream' ссылается на атрибут «a=label» SDP, который идентифицирует m-строку в SDP сеанса записи (RS). SRS узнаёт свойства медиа из строки медиа.
5. Recording Metadata Format from SRC to SRS
5. Формат метаданных записи от SRC к SRS
This section gives an overview of the recording metadata format. Some data from the metadata model is assumed to be made available to the SRS through SDP [RFC4566], and therefore this data is not represented in the XML document format specified in this document. SDP attributes describe different media formats like audio and video. The other metadata attributes, such as participant details, are represented in a new recording-specific XML document of type 'application/rs-metadata+xml'. The SDP "label" attribute [RFC4574] provides an identifier by which a metadata XML document can refer to a specific media description in the SDP sent from the SRC to the SRS.
В этом разделе приведён обзор формата метаданных записи. Предполагается, что некоторые данные из модели метаданных становятся доступны SRS через SDP [RFC4566], и поэтому эти данные не представлены в формате XML-документа, определённом в настоящем документе. Атрибуты SDP описывают различные форматы медиа, такие как аудио и видео. Другие атрибуты метаданных, например сведения об участниках, представлены в новом XML-документе, специфичном для записи, типа 'application/rs-metadata+xml'. Атрибут «label» SDP [RFC4574] предоставляет идентификатор, с помощью которого XML-документ метаданных может ссылаться на конкретное описание медиа в SDP, отправленном от SRC к SRS.
The XML document format can be used to represent either the complete metadata or a partial update to the metadata. The latter includes only elements that have changed compared to the previously reported metadata.
Формат XML-документа может использоваться для представления либо полных метаданных, либо частичного обновления метаданных. Последнее включает только элементы, которые изменились по сравнению с ранее переданными метаданными.
5.1. XML Data Format
5.1. Формат XML-данных
Every recording metadata XML document sent from the SRC to the SRS contains a 'recording' element. The 'recording' element acts as a container for all other elements in this XML document. A 'recording' object is an XML document. It has the XML declaration and contains an encoding declaration in the XML declaration, e.g., "<?xml version="1.0" encoding="UTF-8"?>". If the charset parameter of the MIME content type declaration is present and it is different from the encoding declaration, the charset parameter takes precedence.
Каждый XML-документ метаданных записи, отправляемый от SRC к SRS, содержит элемент 'recording'. Элемент 'recording' служит контейнером для всех остальных элементов этого XML-документа. Объект 'recording' является XML-документом. Он имеет XML-объявление и содержит объявление кодировки в XML-объявлении, например «<?xml version="1.0" encoding="UTF-8"?>». Если параметр charset объявления типа содержимого MIME присутствует и отличается от объявления кодировки, параметр charset имеет приоритет.
Every application conforming to this specification MUST accept the UTF-8 character encoding to ensure minimal interoperability.

Syntax and semantic errors in an XML document should be reported to the originator, using application-specific mechanisms.
Синтаксические и семантические ошибки в XML-документе следует сообщать отправителю с использованием механизмов, специфичных для приложения.

The RS object is represented in the XML schema using the 'recording' element, which in turn relies on the SIP/SDP session with which the XML document is associated to provide the attributes of the RS element.
Объект RS представлен в XML-схеме с помощью элемента 'recording', который, в свою очередь, полагается на сеанс SIP/SDP, с которым связан XML-документ, для предоставления атрибутов элемента RS.
6.1.1. Attributes
6.1.1. Атрибуты
An RS class has the following attributes:
Класс RS обладает следующими атрибутами:
o start-time - Represents the start time of an RS object.
o start-time — представляет время начала объекта RS.
o end-time - Represents the end time of an RS object.
o end-time — представляет время окончания объекта RS.
'start-time' and 'end-time' attribute values are derivable from the Date header (if present in the SIP message) in the RS. In cases where the Date header is not present, 'start-time' is derivable from the time at which the SRS receives the notification of the SIP message to set up the RS, and 'end-time' is derivable from the time at which the SRS receives a disconnect on the RS SIP dialog.
Значения атрибутов 'start-time' и 'end-time' могут быть выведены из заголовка Date (если он присутствует в сообщении SIP) в RS. В случаях, когда заголовок Date отсутствует, 'start-time' выводится из времени, в которое SRS получает уведомление о сообщении SIP для установления RS, а 'end-time' — из времени, в которое SRS получает разъединение в диалоге SIP сеанса RS.
6.1.2. Linkages
6.1.2. Связи
Each instance of an RS has:
Каждый экземпляр RS имеет:
o Zero or more instances of CS-Groups.
o Ноль или более экземпляров CS-Group.
o Zero or more instances of CS objects.
o Ноль или более экземпляров объектов CS.
o Zero or more instances of MediaStream objects.
o Ноль или более экземпляров объектов MediaStream.
Zero instances of CSs and CS-Groups in a 'recording' element are allowed to accommodate persistent recording scenarios. A persistent RS is a SIP dialog that is set up between the SRC and the SRS, even before any CS is set up. The metadata sent from the SRC to the SRS when the persistent RS SIP dialog is set up may not have any CS (and the related CS-Group) elements in the XML, as there may not be a session that is associated to the RS yet. For example, a phone acting as an SRC can set up an RS with the SRS, possibly even before the phone is part of a CS. Once the phone joins a CS, the same RS would be used to convey the CS metadata.
Ноль экземпляров CS и CS-Group в элементе 'recording' допускается для поддержки сценариев постоянной записи. Постоянный RS — это диалог SIP, устанавливаемый между SRC и SRS ещё до установления какого-либо CS. Метаданные, отправляемые от SRC к SRS при установлении диалога SIP постоянного RS, могут не содержать в XML элементов CS (и связанных CS-Group), поскольку сеанс, связанный с RS, может ещё отсутствовать. Например, телефон, действующий как SRC, может установить RS с SRS, возможно, ещё до того, как телефон станет частью CS. После присоединения телефона к CS тот же RS будет использоваться для передачи метаданных CS.

Значение этих элементов ДОЛЖНО соответствовать формату даты и времени Instant Messaging and Presence Protocol (IMPP) [RFC3339]. Метки времени, содержащие «T» или «Z», ДОЛЖНЫ использовать формы с заглавными буквами.
As a security measure, the 'timestamp' element MUST be included in all tuples, unless the exact time of the status change cannot be determined.
В качестве меры безопасности элемент 'timestamp' ДОЛЖЕН включаться во все кортежи, если только точное время изменения состояния не может быть определено.
6.10. Format of Unique ID
6.10. Формат уникального идентификатора
A unique_id is generated in two steps:
unique_id генерируется в два этапа:
o The Universally Unique Identifier (UUID) is created using any of the procedures mentioned in Sections 4.3, 4.4, and 4.5 of [RFC4122]. The algorithm MUST ensure that it does not use any potentially personally identifying information to generate the UUIDs. If implementations are using a Name-Based UUID as defined in Section 4.3 of [RFC4122], a namespace ID generated using the guidance in Section 4.2 or 4.5 of [RFC4122] might be a good choice.
o Universally Unique Identifier (UUID) создаётся с использованием любой из процедур, упомянутых в разделах 4.3, 4.4 и 4.5 [RFC4122]. Алгоритм ДОЛЖЕН гарантировать, что для генерации UUID не используется какая-либо потенциально лично идентифицирующая информация. Если реализации используют Name-Based UUID, как определено в разделе 4.3 [RFC4122], хорошим выбором может быть идентификатор пространства имён, сгенерированный с использованием рекомендаций разделов 4.2 или 4.5 [RFC4122].
o The UUID is encoded using base64 as defined in [RFC4648].
o UUID кодируется с использованием base64, как определено в [RFC4648].
The above-mentioned unique_id mechanism SHOULD be used for each metadata element. Multiple SRCs can refer to the same element/UUID (how each SRC learns the UUID here is beyond the scope of this document). If two SRCs use the same UUID, they MUST retain the UUID/element mapping. If the SRS detects that a UUID is mapped to more than one element at any point in time, it MUST treat this as an error. For example, the SRS may choose to reject or ignore the portions of metadata where it detects that the same UUID is mapped to an element that is different than the expected element (the SRS learns the mapped UUID when it sees an element for the first time in a metadata instance).
Описанный выше механизм unique_id СЛЕДУЕТ использовать для каждого элемента метаданных. Несколько SRC могут ссылаться на один и тот же элемент/UUID (то, как каждый SRC узнаёт UUID, выходит за рамки настоящего документа). Если два SRC используют один и тот же UUID, они ДОЛЖНЫ сохранять сопоставление UUID/элемента. Если SRS обнаруживает, что UUID сопоставлен более чем одному элементу в любой момент времени, он ДОЛЖЕН рассматривать это как ошибку. Например, SRS может выбрать отклонение или игнорирование тех частей метаданных, где он обнаруживает, что один и тот же UUID сопоставлен элементу, отличному от ожидаемого (SRS узнаёт сопоставленный UUID, когда впервые видит элемент в экземпляре метаданных).
6.11. Metadata Version Indicator
6.11. Индикатор версии метаданных
The Metadata version is defined to help the SRC and SRS know the version of metadata XML schema used. SRCs and SRSs that support this specification MUST use version 1 in the namespace (urn:ietf:params:xml:ns:recording:1) in all the XML documents. Implementations may not interoperate if the version implemented by the sender is not known by the receiver. No negotiation of versions is provided. The version number has no significance, although documents that update or obsolete this document (possibly including drafts of such documents) should include a higher version number if the metadata XML schema changes.
Версия метаданных определена, чтобы помочь SRC и SRS узнать версию используемой XML-схемы метаданных. SRC и SRS, поддерживающие настоящую спецификацию, ДОЛЖНЫ использовать версию 1 в пространстве имён (urn:ietf:params:xml:ns:recording:1) во всех XML-документах. Реализации могут не взаимодействовать, если версия, реализованная отправителем, неизвестна получателю. Согласование версий не предусмотрено. Номер версии не имеет значения, хотя документы, обновляющие или делающие устаревшим настоящий документ (возможно, включая черновики таких документов), должны включать более высокий номер версии, если XML-схема метаданных изменяется.

10. Security Considerations
10. Вопросы безопасности
This document describes an extensive set of metadata that may be recorded by the SRS. Most of the metadata could be considered private data. The procedures mentioned in the Security Considerations section of [RFC7866] MUST be followed by the SRC and the SRS for mutual authentication and to protect the content of the metadata in the RS.
Настоящий документ описывает обширный набор метаданных, которые могут записываться SRS. Большинство метаданных можно считать частными данными. Процедуры, упомянутые в разделе «Вопросы безопасности» [RFC7866], ДОЛЖНЫ выполняться SRC и SRS для взаимной аутентификации и защиты содержимого метаданных в RS.
An SRC MAY, by policy, choose to limit the parts of the metadata sent to the SRS for recording. Also, the policy of the SRS might not require recording all the metadata it receives. For the sake of data minimization, the SRS MUST NOT record additional metadata that is not explicitly required by local policy. Metadata in storage needs to be provided with a level of security that is comparable to that of the recording session.
SRC МОЖЕТ в соответствии с политикой ограничивать части метаданных, отправляемых на SRS для записи. Кроме того, политика SRS может не требовать записи всех получаемых метаданных. В целях минимизации данных SRS НЕ ДОЛЖЕН записывать дополнительные метаданные, которые явно не требуются локальной политикой. Метаданные в хранилище должны обеспечиваться уровнем безопасности, сопоставимым с уровнем безопасности сеанса записи.
