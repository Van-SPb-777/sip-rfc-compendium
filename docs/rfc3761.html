1. Introduction
1. Введение
This document discusses the use of the Domain Name System (DNS) for storage of E.164 numbers. More specifically, how DNS can be used for identifying available services connected to one E.164 number. It specifically obsoletes RFC 2916 to bring it in line with the Dynamic Delegation Discovery System (DDDS) Application specification found in the document series specified in RFC 3401 [6]. It is very important to note that it is impossible to read and understand this document without reading the documents discussed in RFC 3401 [6].
Настоящий документ рассматривает использование Domain Name System (DNS) для хранения номеров E.164. Точнее говоря, вопросы о том, как DNS может применяться для выявления доступных служб, связанных с конкретным номером E.164. Документ явно делает устаревшим RFC 2916, приводя его в соответствие со спецификацией приложения Dynamic Delegation Discovery System (DDDS), приведённой в серии документов, указанных в RFC 3401 [6]. Весьма важно отметить, что прочитать и понять настоящий документ невозможно без прочтения документов, рассмотренных в RFC 3401 [6].
Through transformation of International Public Telecommunication Numbers in the international format [5], called within this document E.164 numbers, into DNS names and the use of existing DNS services like delegation through NS records and NAPTR records, one can look up what services are available for a specific E.164 in a decentralized way with distributed management of the different levels in the lookup process.
Путём преобразования International Public Telecommunication Numbers в международном формате [5], называемых в настоящем документе номерами E.164, в имена DNS и использования существующих служб DNS, таких как делегирование через записи NS и записи NAPTR, можно децентрализованно, при распределённом управлении различными уровнями процесса поиска, выяснять, какие службы доступны для конкретного номера E.164.
The domain "e164.arpa" is being populated in order to provide the infrastructure in DNS for storage of E.164 numbers. In order to facilitate distributed operations, this domain is divided into subdomains. Holders of E.164 numbers which want to be listed in DNS should contact the appropriate zone administrator according to the policy which is attached to the zone. One should start looking for this information by examining the SOA resource record associated with the zone, just like in normal DNS operations.
Домен «e164.arpa» наполняется для того, чтобы обеспечить в DNS инфраструктуру хранения номеров E.164. Чтобы облегчить распределённую работу, этот домен разделён на поддомены. Держателям номеров E.164, которые хотят быть представлены в DNS, следует обращаться к соответствующему администратору зоны в соответствии с политикой, принятой для этой зоны. Поиск такой информации следует начинать с изучения ресурсной записи SOA, связанной с зоной, — так же, как при обычных операциях DNS.
Of course, as with other domains, policies for such listings will be controlled on a subdomain basis and may differ in different parts of the world.
Разумеется, как и в случае других доменов, политика в отношении таких записей будет определяться на уровне поддоменов и может различаться в разных частях мира.

1.2. Use for these mechanisms for private dialing plans
1.2. Использование этих механизмов для частных планов нумерации
This document describes the operation of these mechanisms in the context of numbers allocated according to the ITU-T recommendation E.164. The same mechanisms might be used for private dialing plans. Кроме того, используемая уникальная строка приложения ДОЛЖНА быть полным номером, как указано, но без ведущего символа «+», и такое частное использование НЕ ДОЛЖНО называться «ENUM».
1.3. Application of local policy
1.3. Применение локальной политики
The Order field in the NAPTR record specifies in what order the DNS records are to be interpreted. This is because DNS does not guarantee the order of records returned in the answer section of a DNS packet. In most ENUM cases this isn't an issue because the typical regular expression will be '!^.*$!' since the first query often results in a terminal Rule.
Поле Order в записи NAPTR задаёт порядок, в котором должны интерпретироваться записи DNS. Это связано с тем, что DNS не гарантирует порядок записей, возвращаемых в разделе ответа пакета DNS. В большинстве случаев ENUM это не проблема, поскольку типичное регулярное выражение имеет вид '!^.*$!', так как первый запрос часто даёт терминальное правило.
But there are other cases (non-terminal Rules) where two different Rules both match the given Application Unique String. As each Rule is evaluated within the algorithm, one may match a more significant piece of the AUS than the other. For example, by using a non- terminal NAPTR a given set of numbers is sent to some private- dialing-plan-specific zone. Within that zone there are two Rules that state that if a match is for the entire exchange and the service is SIP related then the first, SIP-specific rule is used. But the other Rule matches a longer piece of the AUS, specifying that for some other service (instant messaging) that the Rule denotes a departmental level service. If the shorter matching Rule comes before the longer match, it can 'mask' the other rules. Thus, the order in which each Rule is tested against the AUS is an important corner case that many DDDS applications take advantage of.
Но есть и другие случаи (нетерминальные правила), когда два разных правила соответствуют заданной уникальной строке приложения. Поскольку каждое правило оценивается в рамках алгоритма, одно из них может соответствовать более значимой части AUS, чем другое. Например, с помощью нетерминальной записи NAPTR заданный набор номеров направляется в некоторую зону, специфичную для частного плана нумерации. Внутри этой зоны есть два правила, которые гласят, что если совпадение относится ко всей АТС и служба связана с SIP, то используется первое, специфичное для SIP правило. Но другое правило соответствует более длинной части AUS, указывая, что для некоторой другой службы (обмен мгновенными сообщениями) это правило обозначает службу уровня отдела. Если более короткое совпадающее правило стоит перед более длинным, оно может «маскировать» другие правила. Таким образом, порядок, в котором каждое правило проверяется на соответствие AUS, — важный особый случай, которым пользуются многие приложения DDDS.
In the case where the zone authority wishes to state that two Rules have the same effect or are identical in usage, then the Order for those records is set to the same value. In that case, the Preference is used to specify a locally over-ridable suggestion by the zone authority that one Rule might simply be better than another for some reason.
В случае когда администрация зоны желает указать, что два правила имеют одинаковый эффект или идентичны по использованию, поле Order для этих записей устанавливается в одно и то же значение. В этом случае поле Preference используется для указания предложения администрации зоны, которое можно локально переопределить: одно правило может просто быть лучше другого по какой-то причине.
For ENUM this specifies where a client is allowed to apply local policy and where it is not. The Order field in the NAPTR is a request from the holder of the E.164 number that the records be handled in a specific way. The Preference field is merely a suggestion from that E.164 holder that one record might be better than another. A client implementing ENUM MUST adhere to the Order field but can simply take the Preference value "on advisement" as part of a client context specific selection method.
Для ENUM это определяет, где клиенту разрешено применять локальную политику, а где — нет. Поле Order в записи NAPTR — это требование держателя номера E.164 обрабатывать записи определённым образом. Поле Preference — лишь предложение этого держателя E.164 о том, что одна запись может быть лучше другой. Клиент, реализующий ENUM, ДОЛЖЕН соблюдать поле Order, но может просто принимать значение Preference «к сведению» как часть метода выбора, специфичного для контекста клиента.
2. The ENUM Application Specifications
2. Спецификации приложения ENUM
This template defines the ENUM DDDS Application according to the rules and requirements found in [7]. The DDDS database used by this Application is found in [2] which is the document that defines the NAPTR DNS Resource Record type.
Этот шаблон определяет приложение ENUM DDDS в соответствии с правилами и требованиями, изложенными в [7]. База данных DDDS, используемая этим приложением, описана в [2] — документе, который определяет тип ресурсной записи NAPTR DNS.
ENUM is only applicable for E.164 numbers. ENUM compliant applications MUST only query DNS for what it believes is an E.164 number. Since there are numerous dialing plans which can change over time, it is probably impossible for a client application to have perfect knowledge about every valid and dialable E.164 number. Therefore a client application, doing everything within its power, can end up with what it thinks is a syntactically correct E.164 number which in reality is not actually valid or dialable. This implies that applications MAY send DNS queries when, for example, a user mistypes a number in a user interface. Because of this, there is the risk that collisions between E.164 numbers and non-E.164 numbers can occur. To mitigate this risk, the E2U portion of the service field MUST NOT be used for non-E.164 numbers.
ENUM применим только к номерам E.164. Приложения, совместимые с ENUM, ДОЛЖНЫ запрашивать в DNS только то, что, по их мнению, является номером E.164. Поскольку существует множество планов нумерации, которые могут меняться со временем, клиентское приложение, вероятно, не способно обладать точным знанием о каждом допустимом и набираемом номере E.164. Поэтому клиентское приложение, делающее всё, что в его силах, может получить то, что считает синтаксически правильным номером E.164, который в действительности не является допустимым или набираемым. Отсюда следует, что приложения МОГУТ отправлять запросы DNS, например, когда пользователь ошибается при вводе номера в пользовательском интерфейсе. Из-за этого существует риск возникновения коллизий между номерами E.164 и номерами, не являющимися E.164. Для снижения этого риска часть E2U поля сервиса НЕ ДОЛЖНА использоваться для номеров, не являющихся E.164.
2.1. Application Unique String
2.1. Уникальная строка приложения
The Application Unique String is a fully qualified E.164 number minus any non-digit characters except for the '+' character which appears at the beginning of the number. The "+" is kept to provide a well understood anchor for the AUS in order to distinguish it from other telephone numbers that are not part of the E.164 namespace.
Уникальная строка приложения — это полный номер E.164 без любых нецифровых символов, кроме символа «+», который стоит в начале номера. Символ «+» сохраняется, чтобы обеспечить общепонятную привязку для AUS и тем самым отличить её от других телефонных номеров, не входящих в пространство имён E.164.
For example, the E.164 number could start out as "+44-116-496-0348". To ensure that no syntactic sugar is allowed into the AUS, all non- digits except for "+" are removed, yielding "+441164960348".
Например, номер E.164 мог изначально иметь вид «+44-116-496-0348». Чтобы в AUS не попадало никаких синтаксических украшений, все нецифровые символы, кроме «+», удаляются, что даёт «+441164960348».
2.2. First Well Known Rule
2.2. Первое общеизвестное правило
The First Well Known Rule for this Application is the identity rule. The output of this rule is the same as the input. This is because the E.164 namespace and this Applications databases are organized in such a way that it is possible to go directly from the name to the smallest granularity of the namespace directly from the name itself.
Первое общеизвестное правило для этого приложения — тождественное правило. Выход этого правила совпадает со входом. Это объясняется тем, что пространство имён E.164 и базы данных этого приложения организованы так, что от имени можно перейти непосредственно к наименьшей гранулярности пространства имён, исходя прямо из самого имени.
Take the previous example, the AUS is "+441164960348". Applying the First Well Known Rule produces the exact same string, "+441164960348".
Возьмём предыдущий пример: AUS равна «+441164960348». Применение первого общеизвестного правила даёт в точности ту же строку — «+441164960348».
2.3. Expected Output
2.3. Ожидаемый результат
The output of the last DDDS loop is a Uniform Resource Identifier in its absolute form according to the 'absoluteURI' production in the Collected ABNF found in RFC2396 [4].
Результат последнего цикла DDDS — это Uniform Resource Identifier в его абсолютной форме, согласно правилу 'absoluteURI' в Collected ABNF из RFC2396 [4].

2.4.1. Flags
2.4.1. Флаги
This Database contains a field that contains flags that signal when the DDDS algorithm has finished. At this time only one flag, "U", is defined. This means that this Rule is the last one and that the output of the Rule is a URI [4]. See RFC 3404 [3].
Эта база данных содержит поле с флагами, которые сигнализируют о завершении алгоритма DDDS. В настоящее время определён только один флаг — «U». Он означает, что это правило является последним и что выходом правила является URI [4]. См. RFC 3404 [3].
If a client encounters a record with an unknown flag, it MUST ignore it and move to the next Rule. This test takes precedence over any ordering since flags can control the interpretation placed on fields. A novel flag might change the interpretation of the regexp and/or replacement fields such that it is impossible to determine if a record matched a given target.
Если клиент встречает запись с неизвестным флагом, он ДОЛЖЕН игнорировать её и перейти к следующему правилу. Эта проверка имеет приоритет над любым упорядочением, поскольку флаги могут управлять интерпретацией полей. Новый флаг может изменить интерпретацию полей regexp и/или replacement так, что становится невозможно определить, соответствовала ли запись заданной цели.
If this flag is not present then this rule is non-terminal. If a Rule is non-terminal then clients MUST use the Key produced by this Rewrite Rule as the new Key in the DDDS loop (i.e., causing the client to query for new NAPTR records at the domain-name that is the result of this Rule).
Если этот флаг отсутствует, то это правило является нетерминальным. Если правило нетерминально, клиенты ДОЛЖНЫ использовать ключ, порождённый этим правилом перезаписи, как новый ключ в цикле DDDS (то есть заставить клиента запросить новые записи NAPTR по имени домена, являющемуся результатом этого правила).
2.4.2. Services Parameters
2.4.2. Параметры службы
Service Parameters for this Application take the following form and are found in the Service field of the NAPTR record.
Параметры службы для этого приложения имеют следующую форму и находятся в поле Service записи NAPTR.
service-field = "E2U" 1*(servicespec) servicespec = "+" enumservice enumservice = type 0*(subtypespec) subtypespec = ":" subtype type = 1*32(ALPHA / DIGIT) subtype = 1*32(ALPHA / DIGIT)
service-field = "E2U" 1*(servicespec) servicespec = "+" enumservice enumservice = type 0*(subtypespec) subtypespec = ":" subtype type = 1*32(ALPHA / DIGIT) subtype = 1*32(ALPHA / DIGIT)
In other words, a non-optional "E2U" (used to denote ENUM only Rewrite Rules in order to mitigate record collisions) followed by 1 or more or more Enumservices which indicate what class of functionality a given end point offers. Each Enumservice is indicated by an initial '+' character.
Иными словами, обязательный элемент «E2U» (используемый для обозначения правил перезаписи, относящихся только к ENUM, чтобы снизить вероятность коллизий записей), за которым следуют одна или более Enumservices, указывающих, какой класс функциональности предлагает данная конечная точка. Каждая Enumservice обозначается начальным символом «+».
2.4.2.1. ENUM Services
2.4.2.1. Службы ENUM
Enumservice specifications contain the functional specification (i.e., what it can be used for), the valid protocols, and the URI schemes that may be returned. Note that there is no implicit mapping between the textual string "type" or "subtype" in the grammar for the Enumservice and URI schemes or protocols. The mapping, if any, must be made explicit in the specification for the Enumservice itself. A registration of a specific Type also has to specify the Subtypes allowed.
Спецификации Enumservice содержат функциональную спецификацию (то есть для чего эта служба может использоваться), допустимые протоколы и схемы URI, которые могут быть возвращены. Отметим, что между текстовой строкой «type» или «subtype» в грамматике Enumservice и схемами URI или протоколами нет неявного отображения. Отображение, если оно есть, должно быть явно задано в спецификации самой Enumservice. Регистрация конкретного типа также должна указывать разрешённые подтипы.
The only exception to the registration rule is for Types and Subtypes used for experimental purposes, and those are to start with the facet "X-". These elements are unregistered, experimental, and should be used only with the active agreement of the parties exchanging them.
Единственное исключение из правила регистрации составляют типы и подтипы, используемые в экспериментальных целях: они должны начинаться с фасета «X-». Эти элементы не регистрируются, являются экспериментальными и должны использоваться только при активном согласии обменивающихся ими сторон.
The registration mechanism is specified in Section 3.
Механизм регистрации определён в разделе 3.
2.5. What constitutes an 'Enum Resolver'?
2.5. Что представляет собой «Enum Resolver»?
There has been some confusion over what exactly an ENUM Resolver returns and what relation that has to the 'Note 1' section in RFC 3402. On first reading it seems as though it might be possible for an ENUM Resolver to return two Rules.
Возникала некоторая путаница в отношении того, что именно возвращает ENUM Resolver и как это связано с разделом «Note 1» в RFC 3402. При первом чтении кажется, будто ENUM Resolver может вернуть два правила.
The ENUM algorithm always returns a single rule. Specific applications may have application-specific knowledge or facilities that allow them to present multiple results or speed selection, but these should never change the operation of the algorithm.
Алгоритм ENUM всегда возвращает единственное правило. Конкретные приложения могут располагать специфичными для приложения знаниями или средствами, позволяющими представлять несколько результатов или ускорять выбор, но они никогда не должны изменять работу алгоритма.
3. Registration mechanism for Enumservices
3. Механизм регистрации Enumservices
As specified in the ABNF found in Section 2.4.2, an 'enumservice' is made up of 'types' and 'subtypes'. For any given 'type', the allowable 'subtypes' must be specified in the registration. There is currently no concept of a registered 'subtype' outside the scope of a given 'type'. Thus the registration process uses the 'type' as its main key within the IANA Registry. While the combination of each type and all of its subtypes constitutes the allowed values for the 'enumservice' field, it is not sufficient to simply document those values. A complete registration will also include the allowed URI schemes, a functional specification, security considerations, intended usage, and any other information needed to allow for interoperability within ENUM. In order to be a registered ENUM Service, the entire specification, including the template, requires approval by the IESG and publication of the Enumservice registration specification as an RFC.
Как указано в ABNF из раздела 2.4.2, «enumservice» состоит из «types» и «subtypes». Для любого заданного «type» допустимые «subtypes» должны быть указаны в регистрации. В настоящее время не существует понятия зарегистрированного «subtype» вне области действия заданного «type». Поэтому процесс регистрации использует «type» в качестве основного ключа в реестре IANA. Хотя сочетание каждого типа и всех его подтипов составляет допустимые значения поля «enumservice», недостаточно просто задокументировать эти значения. Полная регистрация также включает допустимые схемы URI, функциональную спецификацию, вопросы безопасности, предполагаемое использование и любую другую информацию, необходимую для обеспечения интероперабельности в рамках ENUM. Чтобы стать зарегистрированной службой ENUM, вся спецификация, включая шаблон, требует одобрения IESG и публикации спецификации регистрации Enumservice в виде RFC.
3.1. Registration Requirements
3.1. Требования к регистрации
Service registration proposals are all expected to conform to various requirements laid out in the following sections.
Предполагается, что все предложения о регистрации службы будут соответствовать различным требованиям, изложенным в следующих разделах.
3.1.1. Functionality Requirement
3.1.1. Требование функциональности
A registered Enumservice must be able to function as a selection mechanism when choosing one NAPTR resource record from another. That means that the registration MUST specify what is expected when using that very NAPTR record, and the URI which is the outcome of the use of it.
Зарегистрированная Enumservice должна быть способна работать как механизм выбора при выборе одной ресурсной записи NAPTR из другой. Это означает, что регистрация ДОЛЖНА указывать, что ожидается при использовании именно этой записи NAPTR, и URI, который является результатом её использования.
Specifically, a registered Enumservice MUST specify the URI scheme(s) that may be used for the Enumservice, and, when needed, other information which will have to be transferred into the URI resolution process itself (LDAP Distinguished Names, transferring of the AUS into the resulting URI, etc).
В частности, зарегистрированная Enumservice ДОЛЖНА указывать схемы URI, которые могут использоваться для этой Enumservice, и при необходимости другую информацию, которая должна быть передана в сам процесс разрешения URI (отличительные имена LDAP, передача AUS в результирующий URI и т. д.).
3.1.2. Naming requirement
3.1.2. Требование к именованию
An Enumservice MUST be unique in order to be useful as a selection criteria. Since an Enumservice is made up of a type and a type- dependent subtype, it is sufficient to require that the 'type' itself be unique. The 'type' MUST be unique, conform to the ABNF specified in Section 2.4.2, and MUST NOT start with the facet "X-" which is reserved for experimental, private use.
Enumservice ДОЛЖНА быть уникальной, чтобы быть полезной в качестве критерия выбора. Поскольку Enumservice состоит из типа и зависящего от типа подтипа, достаточно потребовать, чтобы уникальным был сам «type». «type» ДОЛЖЕН быть уникальным, соответствовать ABNF, указанному в разделе 2.4.2, и НЕ ДОЛЖЕН начинаться с фасета «X-», который зарезервирован для экспериментального частного использования.
The subtype, being dependent on the type, MUST be unique within a given 'type'. It must conform to the ABNF specified in Section 2.4.2, and MUST NOT start with the facet "X-" which is reserved for experimental, private use. The subtype for one type MAY be the same as a subtype for a different registered type but it is not sufficient to simply reference another type's subtype. The function of each subtype must be specified in the context of the type being registered.
Подтип, будучи зависимым от типа, ДОЛЖЕН быть уникальным в пределах заданного «type». Он должен соответствовать ABNF, указанному в разделе 2.4.2, и НЕ ДОЛЖЕН начинаться с фасета «X-», который зарезервирован для экспериментального частного использования. Подтип одного типа МОЖЕТ совпадать с подтипом другого зарегистрированного типа, но недостаточно просто сослаться на подтип другого типа. Функция каждого подтипа должна быть указана в контексте регистрируемого типа.
3.1.3. Security requirement
3.1.3. Требование безопасности
An analysis of security issues is required for all registered Enumservices. (This is in accordance with the basic requirements for all IETF protocols.)
Для всех зарегистрированных Enumservices требуется анализ вопросов безопасности. (Это соответствует базовым требованиям ко всем протоколам IETF.)
All descriptions of security issues must be as accurate as possible regardless of registration tree. In particular, a statement that there are "no security issues associated with this Enumservice" must not be confused with "the security issues associated with this Enumservice have not been assessed".
Все описания вопросов безопасности должны быть как можно более точными независимо от дерева регистрации. В частности, утверждение о том, что «с этой Enumservice не связано никаких вопросов безопасности», не должно смешиваться с утверждением «вопросы безопасности, связанные с этой Enumservice, не оценивались».
There is no requirement that an Enumservice must be secure or completely free from risks. Nevertheless, all known security risks must be identified in the registration of an Enumservice.
Нет требования, чтобы Enumservice была безопасной или полностью свободной от рисков. Тем не менее все известные риски безопасности должны быть выявлены при регистрации Enumservice.
The security considerations section of all registrations is subject to continuing evaluation and modification.
Раздел вопросов безопасности всех регистраций подлежит постоянной оценке и изменению.
Some of the issues that should be looked at in a security analysis of an Enumservice are:
Некоторые из вопросов, которые следует рассматривать при анализе безопасности Enumservice:
1. Complex Enumservices may include provisions for directives that institute actions on a user's resources. In many cases provision can be made to specify arbitrary actions in an unrestricted fashion which may then have devastating results. Especially if there is a risk for a new ENUM lookup, and because of that an infinite loop in the overall resolution process of the E.164.
1. Сложные Enumservices могут включать положения о директивах, которые инициируют действия с ресурсами пользователя. Во многих случаях можно предусмотреть задание произвольных действий без каких-либо ограничений, что затем может иметь разрушительные последствия. Особенно если существует риск нового поиска в ENUM и, как следствие, бесконечного цикла в общем процессе разрешения E.164.
2. Complex Enumservices may include provisions for directives that institute actions which, while not directly harmful, may result in disclosure of information that either facilitates a subsequent attack or else violates the users privacy in some way.
2. Сложные Enumservices могут включать положения о директивах, которые инициируют действия, хотя и не прямо вредные, но способные привести к раскрытию информации, что либо облегчает последующую атаку, либо тем или иным образом нарушает неприкосновенность частной жизни пользователей.
3. An Enumservice might be targeted for applications that require some sort of security assurance but do not provide the necessary security mechanisms themselves. For example, an Enumservice could be defined for storage of confidential security services information such as alarm systems or message service passcodes, which in turn require an external confidentiality service.
3. Enumservice может быть предназначена для приложений, которые требуют определённых гарантий безопасности, но сами не обеспечивают необходимых механизмов безопасности. Например, Enumservice может быть определена для хранения конфиденциальной информации служб безопасности, такой как системы сигнализации или коды доступа к службе сообщений, что в свою очередь требует внешней службы обеспечения конфиденциальности.
3.1.4. Publication Requirements
3.1.4. Требования к публикации
Proposals for Enumservices registrations MUST be published as one of the following documents; RFC on the Standards Track, Experimental RFC, or as a BCP.
Предложения о регистрации Enumservices ДОЛЖНЫ публиковаться в виде одного из следующих документов: RFC уровня Standards Track, экспериментального RFC либо BCP.

IANA будет хранить копии всех предложений о регистрации Enumservice и «публиковать» их как часть самого дерева регистрации Enumservice.

4. Examples
4. Примеры
The examples below use theoretical services that contain Enumservices which might not make sense, but that are still used for educational purposes. For example, the protocol used is in some cases exactly the same string as the URI scheme. That was the specification in RFC 2916, but this 'default' specification of an Enumservice is no longer allowed. All Enumservices need to be registered explicitly by the procedure specified in section Section 3.
Приведённые ниже примеры используют теоретические службы, содержащие Enumservices, которые могут не иметь смысла, но всё же используются в учебных целях. Например, используемый протокол в некоторых случаях представляет собой в точности ту же строку, что и схема URI. Так было в спецификации RFC 2916, но такая «умалчиваемая» спецификация Enumservice больше не допускается. Все Enumservices должны быть явно зарегистрированы процедурой, указанной в разделе 3.
4.1. Example
4.1. Пример
$ORIGIN 3.8.0.0.6.9.2.3.6.1.4.4.e164.arpa. NAPTR 10 100 "u" "E2U+sip" "!^.*$!sip:info@example.com!" . NAPTR 10 101 "u" "E2U+h323" "!^.*$!h323:info@example.com!" . NAPTR 10 102 "u" "E2U+msg" "!^.*$!mailto:info@example.com!" .
Запись зоны DNS для примера (данные записи приведены дословно и не переводятся): $ORIGIN 3.8.0.0.6.9.2.3.6.1.4.4.e164.arpa. NAPTR 10 100 "u" "E2U+sip" "!^.*$!sip:info@example.com!" . NAPTR 10 101 "u" "E2U+h323" "!^.*$!h323:info@example.com!" . NAPTR 10 102 "u" "E2U+msg" "!^.*$!mailto:info@example.com!" .
This describes that the domain 3.8.0.0.6.9.2.3.6.1.4.4.e164.arpa. is preferably contacted by SIP, secondly via H.323 for voice, and thirdly by SMTP for messaging. Note that the tokens "sip", "h323", and "msg" are Types registered with IANA, and they have no implicit connection with the protocols or URI schemes with the same names. In all cases, the next step in the resolution process is to use the resolution mechanism for each of the protocols, (specified by the URI schemes sip, h323 and mailto) to know what node to contact for each.
Это означает, что к домену 3.8.0.0.6.9.2.3.6.1.4.4.e164.arpa. предпочтительно обращаться по SIP, во вторую очередь — по H.323 для передачи голоса и в третью очередь — по SMTP для передачи сообщений. Отметим, что токены «sip», «h323» и «msg» — это типы, зарегистрированные в IANA, и они не имеют неявной связи с протоколами или схемами URI с теми же именами. Во всех случаях следующий шаг процесса разрешения — использовать механизм разрешения для каждого из протоколов (заданный схемами URI sip, h323 и mailto), чтобы узнать, с каким узлом связываться в каждом случае.
5. IANA Considerations
5. Вопросы IANA
RFC 2916 (which this document replaces) requested IANA to delegate the E164.ARPA domain following instructions to be provided by the IAB. The domain was delegated according to those instructions. Names within this zone are to be delegated to parties according to the ITU-T Recommendation E.164. The names allocated should be hierarchic in accordance with ITU-T Recommendation E.164, and the codes should be assigned in accordance with that Recommendation.
В RFC 2916 (который заменяет настоящий документ) IANA было предложено делегировать домен E164.ARPA в соответствии с инструкциями, которые должен предоставить IAB. Домен был делегирован согласно этим инструкциям. Имена в этой зоне должны делегироваться сторонам в соответствии с рекомендацией ITU-T E.164. Выделяемые имена должны быть иерархическими в соответствии с рекомендацией ITU-T E.164, а коды должны назначаться в соответствии с этой рекомендацией.
IAB is to coordinate with ITU-T TSB if the technical contact for the domain e164.arpa is to change, as ITU-T TSB has an operational working relationship with this technical contact which needs to be reestablished.
Если технический контакт для домена e164.arpa должен измениться, IAB следует согласовать это с ITU-T TSB, поскольку ITU-T TSB имеет с этим техническим контактом рабочие отношения, которые необходимо восстановить.
Delegations in the zone e164.arpa (not delegations in delegated domains of e164.arpa) should be done after Expert Review, and the IESG will appoint a designated expert.

6. Security Considerations
6. Вопросы безопасности
6.1. DNS Security
6.1. Безопасность DNS
As ENUM uses DNS, which in its current form is an insecure protocol, there is no mechanism for ensuring that the data one gets back is authentic. As ENUM is deployed on the global Internet, it is expected to be a popular target for various kind of attacks, and attacking the underlying DNS infrastructure is one way of attacking the ENUM service itself.
Поскольку ENUM использует DNS, который в его нынешнем виде является незащищённым протоколом, не существует механизма, гарантирующего подлинность получаемых данных. Поскольку ENUM развёртывается в глобальном Интернете, следует ожидать, что он станет популярной целью для разного рода атак, а атака на нижележащую инфраструктуру DNS — один из способов атаковать саму службу ENUM.
There are multiple types of attacks that can happen against DNS that ENUM implementations should be aware of. The following threats are taken from Threat Analysis Of The Domain Name System [10]:
Существует несколько типов атак на DNS, о которых реализации ENUM должны знать. Следующие угрозы взяты из «Threat Analysis Of The Domain Name System» [10]:
Packet Interception Some of the simplest threats against DNS are various forms of packet interception: monkey-in-the-middle attacks, eavesdropping on requests combined with spoofed responses that beat the real response back to the resolver, and so forth. In any of these scenarios, the attacker can simply tell either party (usually the resolver) whatever it wants that party to believe. While packet interception attacks are far from unique to DNS, DNS's usual behavior of sending an entire query or response in a single unsigned, unencrypted UDP packet makes these attacks particularly easy for any bad guy with the ability to intercept packets on a shared or transit network.
Перехват пакетов. Одни из простейших угроз для DNS — это различные формы перехвата пакетов: атаки «человек посередине», прослушивание запросов в сочетании с поддельными ответами, которые опережают настоящий ответ, приходящий резолверу, и т. п. В любом из этих сценариев атакующий может просто сообщить любой из сторон (обычно резолверу) то, что он хочет, чтобы эта сторона считала истиной. Хотя атаки с перехватом пакетов отнюдь не уникальны для DNS, обычное поведение DNS, при котором весь запрос или ответ отправляется в одном неподписанном, незашифрованном пакете UDP, делает эти атаки особенно лёгкими для любого злоумышленника, способного перехватывать пакеты в разделяемой сети или сети передачи.
ID Guessing and Query Prediction Since the ID field in the DNS header is only a 16-bit field and the server UDP port associated with DNS is a well-known value, there are only 2**32 possible combinations of ID and client UDP port for a given client and server. Thus it is possible for a reasonable brute force attack to allow an attacker to masquerade as a trusted server. In most respects, this attack is similar to a packet interception attack except that it does not require the attacker to be on a transit or shared network.
Угадывание ID и предсказание запросов. Поскольку поле ID в заголовке DNS занимает всего 16 бит, а UDP-порт сервера, связанный с DNS, является широко известным значением, для заданных клиента и сервера существует всего 2**32 возможных сочетаний ID и UDP-порта клиента. Таким образом, разумная атака методом перебора позволяет атакующему выдавать себя за доверенный сервер. По большинству аспектов эта атака похожа на атаку с перехватом пакетов, за исключением того, что она не требует присутствия атакующего в транзитной или разделяемой сети.
Name-based Attacks Name-based attacks use the actual DNS caching behavior as a tool to insert bad data into a victim's cache, thus potentially subverting subsequent decisions based on DNS names. Most examples occur with CNAME, NS and DNAME Resource Records as they redirect a victim's query to another location. The common thread in all of these attacks is that response messages allow the attacker to introduce arbitrary DNS names of the attacker's choosing and provide further information that the attacker claims is associated with those names; unless the victim has better knowledge of the data associated with those names, the victim is going to have a hard time defending against this class of attacks.
Атаки на основе имён. Атаки на основе имён используют фактическое поведение кэширования DNS как инструмент для внедрения неверных данных в кэш жертвы, что потенциально позволяет подменить последующие решения, основанные на именах DNS. Большинство примеров встречается с ресурсными записями CNAME, NS и DNAME, поскольку они перенаправляют запрос жертвы в другое место. Общая черта всех этих атак состоит в том, что ответные сообщения позволяют атакующему ввести произвольные имена DNS по своему выбору и предоставить дополнительную информацию, которую атакующий утверждает как связанную с этими именами; если только жертва не располагает лучшими знаниями о данных, связанных с этими именами, ей будет трудно защититься от этого класса атак.
Betrayal By A Trusted Server Another variation on the packet interception attack is the trusted server that turns out not to be so trustworthy, whether by accident or by intent. Many client machines are only configured with stub resolvers, and use trusted servers to perform all of their DNS queries on their behalf. In many cases the trusted server is furnished by the user's ISP and advertised to the client via DHCP or PPP options. Besides accidental betrayal of this trust relationship (via server bugs, successful server break-ins, etc), the server itself may be configured to give back answers that are not what the user would expect (whether in an honest attempt to help the user or to further some other goal such as furthering a business partnership between the ISP and some third party).
Измена доверенного сервера. Ещё одна разновидность атаки с перехватом пакетов — доверенный сервер, который оказывается не столь надёжным, случайно или намеренно. Многие клиентские машины настроены только с так называемыми stub resolvers и используют доверенные серверы для выполнения всех своих запросов DNS от своего имени. Во многих случаях доверенный сервер предоставляется провайдером пользователя и объявляется клиенту через параметры DHCP или PPP. Помимо случайной измены этим доверительным отношениям (из-за ошибок сервера, успешного взлома сервера и т. п.), сам сервер может быть настроен так, чтобы возвращать ответы, не соответствующие ожиданиям пользователя (будь то честная попытка помочь пользователю или продвижение какой-то иной цели, например развитие делового партнёрства между провайдером и некоей третьей стороной).
Denial of Service As with any network service (or, indeed, almost any service of any kind in any domain of discourse), DNS is vulnerable to denial of service attacks. DNS servers are also at risk of being used as denial of service amplifiers, since DNS response packets tend to be significantly longer than DNS query packets.
Отказ в обслуживании. Как и любая сетевая служба (и вообще почти любая служба любого рода в любой предметной области), DNS уязвима для атак типа «отказ в обслуживании». Серверы DNS также подвержены риску быть использованными в качестве усилителей отказа в обслуживании, поскольку пакеты ответов DNS, как правило, значительно длиннее пакетов запросов DNS.
Authenticated Denial of Domain Names The existence of RR types whose absence causes an action other than immediate failure (such as missing MX and SRV RRs, which fail over to A RRs) constitutes a real threat. In the specific case of ENUM, even the immediate failure of a missing RR can be considered a problem as a method for changing call routing policy.
Аутентифицированный отказ в отношении доменных имён. Существование типов RR, отсутствие которых вызывает действие, отличное от немедленного отказа (например, отсутствующие RR MX и SRV, при которых происходит переход к RR A), представляет собой реальную угрозу. В конкретном случае ENUM даже немедленный отказ из-за отсутствующей RR можно рассматривать как проблему — как метод изменения политики маршрутизации вызовов.
Because of these threats, a deployed ENUM service SHOULD include mechanisms which ameliorate these threats. Most of these threats can be solved by verifying the authenticity of the data via mechanisms such as DNSSEC [8] once it is deployed. Others, such and Denial Of Service attacks, cannot be solved by data authentication. It is important to remember that these threats include not only the NAPTR lookups themselves, but also the various records needed for the services to be useful (for example NS, MX, SRV and A records).
Из-за этих угроз развёрнутая служба ENUM ДОЛЖНА включать механизмы, смягчающие эти угрозы. Большинство этих угроз можно устранить путём проверки подлинности данных с помощью таких механизмов, как DNSSEC [8], после его развёртывания. Другие, например атаки типа «отказ в обслуживании», нельзя устранить путём аутентификации данных. Важно помнить, что эти угрозы включают не только сами поиски NAPTR, но и различные записи, необходимые для того, чтобы службы были полезны (например, записи NS, MX, SRV и A).
Even if DNSSEC is deployed, a service that uses ENUM for address translation should not blindly trust that the peer is the intended party as all kind of attacks against DNS can not be protected against with DNSSEC. A service should always authenticate the peers as part of the setup process for the service itself and never blindly trust any kind of addressing mechanism.
Даже если DNSSEC развёрнут, служба, использующая ENUM для трансляции адресов, не должна слепо доверять тому, что партнёр является предполагаемой стороной, поскольку от всех видов атак на DNS с помощью DNSSEC защититься невозможно. Служба должна всегда аутентифицировать партнёров в рамках процесса установки для самой службы и никогда не доверять слепо никакому механизму адресации.
Finally, as an ENUM service will be implementing some type of security mechanism, software which implements ENUM MUST be prepared to receive DNSSEC and other standardized DNS security responses, including large responses, EDNS0 signaling, unknown RRs, etc.
Наконец, поскольку служба ENUM будет реализовывать некоторый тип механизма безопасности, программное обеспечение, реализующее ENUM, ДОЛЖНО быть готово принимать ответы DNSSEC и другие стандартизованные ответы безопасности DNS, включая большие ответы, сигнализацию EDNS0, неизвестные RR и т. д.
6.2. Caching Security
6.2. Безопасность кэширования
The caching in DNS can make the propagation time for a change take the same amount of time as the time to live for the NAPTR records in the zone that is changed. The use of this in an environment where IP-addresses are for hire (for example, when using DHCP [9]) must therefore be done very carefully.
Кэширование в DNS может привести к тому, что время распространения изменения окажется равным времени жизни записей NAPTR в изменяемой зоне. Поэтому использование этого в среде, где IP-адреса сдаются внаём (например, при использовании DHCP [9]), должно выполняться очень осмотрительно.
6.3. Call Routing Security
6.3. Безопасность маршрутизации вызовов
There are a number of countries (and other numbering environments) in which there are multiple providers of call routing and number/name- translation services. In these areas, any system that permits users, or putative agents for users, to change routing or supplier information may provide incentives for changes that are actually unauthorized (and, in some cases, for denial of legitimate change requests). Such environments should be designed with adequate mechanisms for identification and authentication of those requesting changes and for authorization of those changes.
Есть ряд стран (и иных сред нумерации), где имеется несколько поставщиков услуг маршрутизации вызовов и трансляции номеров/имён. В таких областях любая система, позволяющая пользователям или предполагаемым агентам пользователей изменять информацию о маршрутизации или поставщике, может создавать стимулы для изменений, которые в действительности не разрешены (а в некоторых случаях — и для отказа в законных запросах на изменение). Такие среды должны проектироваться с адекватными механизмами идентификации и аутентификации тех, кто запрашивает изменения, и авторизации этих изменений.
6.4. URI Resolution Security
6.4. Безопасность разрешения URI
A large amount of Security Issues have to do with the resolution process itself, and use of the URIs produced by the DDDS mechanism. Those have to be specified in the registration of the Enumservice used, as specified in Section 3.1.3.
Большое количество вопросов безопасности связано с самим процессом разрешения и использованием URI, порождаемых механизмом DDDS. Они должны быть указаны в регистрации используемой Enumservice, как указано в разделе 3.1.3.

8. Changes since RFC 2916
8. Изменения по сравнению с RFC 2916
Part from clarifications in the text in this document, the major changes are two:
Помимо уточнений в тексте настоящего документа, основных изменений два:
The document uses an explicit DDDS algorithm, and not only NAPTR resource records in an "ad-hoc" mode. In reality this doesn't imply any changes in deployed base of applications, as the algorithm used for ENUM resolution is exactly the same.
Документ использует явный алгоритм DDDS, а не только ресурсные записи NAPTR в «специальном» режиме. В действительности это не влечёт никаких изменений в развёрнутой базе приложений, поскольку алгоритм, используемый для разрешения ENUM, в точности тот же.
The format of the service field has changed. The old format was of the form "example+E2U", while the new format is "E2U+example". Reason for this change have to with the added subtypes in the enumservice, the ability to support more than one enumservice per NAPTR RR, and a general agreement in the IETF that the main selector between different NAPTR with the same owner (E2U in this case) should be first.
Формат поля сервиса изменился. Старый формат имел вид «example+E2U», а новый формат — «E2U+example». Причина этого изменения связана с добавленными подтипами в enumservice, возможностью поддерживать более одной enumservice на одну RR NAPTR и общим согласием в IETF о том, что основной селектор между разными NAPTR с одним и тем же владельцем (в данном случае E2U) должен стоять первым.
