Abstract
Аннотация
In certain types of multimedia communications, a Session Initiation Protocol (SIP) request is distributed to a group of SIP User Agents (UAs). The sender sends a single SIP request to a server which further distributes the request to the group. This SIP request contains a list of Uniform Resource Identifiers (URIs), which identify the recipients of the SIP request. This URI list is expressed as a resource list XML document. This specification defines an XML extension to the XML resource list format that allows the sender of the request to qualify a recipient with a copy control level similar to the copy control level of existing email systems.
В некоторых видах мультимедийной связи запрос протокола инициирования сессий (SIP) распределяется группе агентов пользователя (UA) SIP. Отправитель посылает одиночный запрос SIP серверу, который затем распределяет запрос по группе. Этот запрос SIP содержит список универсальных идентификаторов ресурсов (URI), идентифицирующих получателей запроса SIP. Этот список URI выражен в виде XML-документа списка ресурсов. Настоящая спецификация определяет расширение XML для формата списка ресурсов XML, позволяющее отправителю запроса снабдить получателя уровнем управления копированием, аналогичным уровню управления копированием в существующих системах электронной почты.
1. Introduction
1. Введение
RFC 5363 [RFC5363] describes a generic framework for carrying Uniform Resource Identifier (URI) lists in SIP [RFC3261] messages. Specifically, the document provides a common framework for specific implementations of URI-list services, such as conferences initiated with INVITE requests [RFC5366] or Multiple-recipient MESSAGE requests [RFC5365].
RFC 5363 [RFC5363] описывает общие основы передачи списков универсальных идентификаторов ресурсов (URI) в сообщениях SIP [RFC3261]. В частности, документ предоставляет общую основу для конкретных реализаций служб списков URI, таких как конференции, инициируемые запросами INVITE [RFC5366], или запросы MESSAGE нескольким получателям [RFC5365].
Common to all URI-list services is the presence of a SIP request that contains a collection of resources, typically expressed as an XML resource list [RFC4826]. SIP requests carrying resource lists can appear either in requests received by the URI-list server, indicating the list of intended recipients, or in each of the requests that the URI-list server sends to recipients, indicating the list of recipients of the same SIP request.
Общим для всех служб списков URI является наличие запроса SIP, содержащего набор ресурсов, обычно выражаемый в виде списка ресурсов XML [RFC4826]. Запросы SIP, несущие списки ресурсов, могут появляться либо в запросах, получаемых сервером списков URI и указывающих список предполагаемых получателей, либо в каждом из запросов, которые сервер списков URI отправляет получателям и которые указывают список получателей того же запроса SIP.
Although the XML resource list [RFC4826] provides a powerful mechanism for describing a list of resources, there is a need for a copy control attribute to determine whether a resource is receiving a SIP request as a primary recipient, a carbon copy, or a blind carbon copy. This is similar to common email systems, where the sender can categorize each recipient as a "to", "cc", or "bcc" recipient.
Хотя список ресурсов XML [RFC4826] предоставляет мощный механизм описания списка ресурсов, существует потребность в атрибуте управления копированием, определяющем, получает ли ресурс запрос SIP как основной получатель, обычную копию или скрытую копию. Это аналогично распространённым системам электронной почты, где отправитель может отнести каждого получателя к категории «to», «cc» или «bcc».
This document addresses this problem by providing an extension to the XML resource list [RFC4826] that enables the sender to supply a copy control attribute that labels each recipient as a "to", "cc", or "bcc" recipient. This attribute indicates whether the recipient is receiving a primary copy of the SIP request, a carbon copy, or a blind carbon copy. Additionally, we provide the sender with the capability of indicating in the URI list that one or more resources should be anonymized, so that some recipients' URIs are not disclosed to the other recipients. Instead, these URIs are replaced with anonymous URIs.
Настоящий документ решает эту проблему, предоставляя расширение списка ресурсов XML [RFC4826], которое позволяет отправителю задать атрибут управления копированием, помечающий каждого получателя как получателя «to», «cc» или «bcc». Этот атрибут указывает, получает ли получатель основную копию запроса SIP, обычную копию или скрытую копию. Кроме того, мы предоставляем отправителю возможность указать в списке URI, что один или несколько ресурсов следует анонимизировать, чтобы URI некоторых получателей не раскрывались другим получателям. Вместо этого такие URI заменяются анонимными URI.

Section 7 discusses the implications of carrying URI lists in SIP messages.

2. Terminology
2. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14, RFC 2119 [RFC2119] and indicate requirement levels for compliant implementations.
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует толковать так, как описано в BCP 14, RFC 2119 [RFC2119], и они указывают уровни требований для совместимых реализаций.
URI-list service: SIP application service that receives a SIP request containing a URI list and sends a similar SIP request to each URI in the list.
Служба списков URI: служба приложений SIP, которая принимает запрос SIP, содержащий список URI, и отправляет аналогичный запрос SIP каждому URI в списке.
Intended recipient: The intended final recipient of the request to be generated by URI-list service.
Предполагаемый получатель: предполагаемый конечный получатель запроса, который должна сформировать служба списков URI.
Copy control: An attribute assigned by the sender to a URI in an XML resource list. Its purpose is to indicate to the recipient whether he is getting a primary, carbon, or blind carbon copy of the SIP request.
Управление копированием: атрибут, назначаемый отправителем URI в списке ресурсов XML. Его назначение — указать получателю, получает ли он основную, обычную или скрытую копию запроса SIP.
Recipient list or recipient XML resource list: An XML resource list containing the list of intended recipients. The sender sets this list in the SIP request he sends to the URI-list server.
Список получателей или список ресурсов XML получателей: список ресурсов XML, содержащий список предполагаемых получателей. Отправитель задаёт этот список в запросе SIP, который он отправляет серверу списков URI.
Recipient-history list or recipient-history XML resource list: An XML resource list containing the visible list of recipients (i.e., those non-anonymous non-bcc). The URI-list server creates this list, based on the recipient list, and includes it in each of the SIP requests it sends to each recipient.
Список истории получателей или список ресурсов XML истории получателей: список ресурсов XML, содержащий видимый список получателей (то есть неанонимных и не-bcc). Сервер списков URI создаёт этот список на основе списка получателей и включает его в каждый из запросов SIP, отправляемых каждому получателю.

In addition to the 'copyControl' attribute for a URI in an XML resource list, we define a second boolean attribute called 'anonymize'. The sender of a SIP request can mark a URI in a recipient XML resource list with the 'anonymize' attribute to indicate the URI-list server that the URI marked with that attribute is to be replaced with an anonymous URI in the recipient-history XML resource list. This provides knowledge to the recipients of a SIP request of the number of additional visible recipients whose URIs have not been disclosed.
Помимо атрибута 'copyControl' для URI в списке ресурсов XML, мы определяем второй булев атрибут 'anonymize'. Отправитель запроса SIP может пометить URI в списке ресурсов XML получателей атрибутом 'anonymize', чтобы указать серверу списков URI, что URI, помеченный этим атрибутом, должен быть заменён анонимным URI в списке ресурсов XML истории получателей. Это даёт получателям запроса SIP знание о числе дополнительных видимых получателей, чьи URI не раскрыты.
There are cases when the sender marks several URIs with the 'anonymize' attribute. The URI-list server can group the anonymized URIs in a single anonymized URI within its copy control level, and provide a count of the number of anonymized URIs. To support this scenario, we define a new 'count' attribute to a URI in the recipient-history XML resource list. It is expected that the 'count' attribute is only used with anonymous URIs, although syntactically it is possible to add a 'count' attribute to any URI in any XML resource list.
Бывают случаи, когда отправитель помечает атрибутом 'anonymize' несколько URI. Сервер списков URI может сгруппировать анонимизированные URI в один анонимизированный URI в рамках своего уровня управления копированием и указать количество анонимизированных URI. Для поддержки этого сценария мы определяем новый атрибут 'count' для URI в списке ресурсов XML истории получателей. Предполагается, что атрибут 'count' используется только с анонимными URI, хотя синтаксически можно добавить атрибут 'count' к любому URI в любом списке ресурсов XML.
Initially, it may be thought that the 'anonymize' attribute overlaps with the "bcc" value of the 'copyControl' attribute. However, there are differences between them. If the sender qualifies a URI with a 'copyControl' attribute of "bcc" in the recipient XML resource list, the URI-list server will typically remove that URI from the recipient-history XML resource list (unless the URI-list server decides to preserve a "bcc" marked URI when that URI is itself the recipient of the SIP request). Recipients of the SIP request will not notice that one or more extra "bcc" URIs also received the request. However, if the sender qualifies a URI with the 'anonymize' attribute in the recipient XML resource list, the URI-list server will replace the URI with an anonymous one in the recipient-history list. Recipients of the SIP request will notice that there have been one or more additional recipients of the same request, but their URIs are not disclosed.
Поначалу может показаться, что атрибут 'anonymize' пересекается со значением «bcc» атрибута 'copyControl'. Однако между ними есть различия. Если отправитель снабжает URI атрибутом 'copyControl' со значением «bcc» в списке ресурсов XML получателей, сервер списков URI обычно удаляет этот URI из списка ресурсов XML истории получателей (если только сервер списков URI не решит сохранить URI с пометкой «bcc», когда этот URI сам является получателем запроса SIP). Получатели запроса SIP не заметят, что один или несколько дополнительных URI «bcc» также получили запрос. Однако если отправитель снабжает URI атрибутом 'anonymize' в списке ресурсов XML получателей, сервер списков URI заменит URI на анонимный в списке истории получателей. Получатели запроса SIP заметят, что у того же запроса были один или несколько дополнительных получателей, но их URI не раскрыты.
4. Extension to the Resource List Data Format
4. Расширение формата данных списка ресурсов
This document defines an extension to the XML resource list data format [RFC4826] that allows the sender to indicate a copy control attribute that qualifies a recipient with a copy control level. We define a new 'copyControl' attribute to the <entry> element of the resource list document format [RFC4826]. The 'copyControl' attribute has similar semantics to the type of destination address in email systems. It can take the values "to", "cc", and "bcc". A "to" value of the 'copyControl' attribute indicates that the resource is considered a primary recipient of the SIP request. A "cc" value indicates that the resource receives a carbon copy of the SIP request. A "bcc" value indicates that the resource receives a blind carbon copy of the SIP request (i.e., this URI is not disclosed to other recipients of the SIP request). The default 'copyControl' value is "bcc". That is, the absence of a 'copyControl' attribute MUST be treated as if the 'copyControl' was set to "bcc".
Настоящий документ определяет расширение формата данных списка ресурсов XML [RFC4826], которое позволяет отправителю указать атрибут управления копированием, снабжающий получателя уровнем управления копированием. Мы определяем новый атрибут 'copyControl' для элемента <entry> формата документа списка ресурсов [RFC4826]. Атрибут 'copyControl' имеет семантику, аналогичную типу адреса назначения в электронной почте. Он может принимать значения «to», «cc» и «bcc». Значение «to» атрибута 'copyControl' указывает, что ресурс считается основным получателем запроса SIP. Значение «cc» указывает, что ресурс получает обычную копию запроса SIP. Значение «bcc» указывает, что ресурс получает скрытую копию запроса SIP (то есть этот URI не раскрывается другим получателям запроса SIP). Значение 'copyControl' по умолчанию — «bcc». То есть отсутствие атрибута 'copyControl' ДОЛЖНО трактоваться так, как если бы для 'copyControl' было задано «bcc».
When creating a recipient-history list, URI-list servers use "bcc" 'copyControl' attributes to route SIP requests. In addition, URI- list servers behave similarly to email systems [RFC2822] with respect to the treatment of these URIs marked with a "bcc" copy control, because they have two ways of treating "bcc" marked URIs. При создании списка истории получателей серверы списков URI используют атрибуты 'copyControl' со значением «bcc» для маршрутизации запросов SIP. Кроме того, серверы списков URI ведут себя аналогично системам электронной почты [RFC2822] в отношении обработки этих URI с пометкой управления копированием «bcc», поскольку у них есть два способа обработки URI с пометкой «bcc». However, recipients who are tagged with "bcc" values are not explicitly informed about it.
o Серверы списков URI ДОЛЖНЫ удалять из списков истории получателей все URI с пометкой управления копированием «bcc». Этот механизм позволяет серверам списков URI отправлять одинаковый список истории получателей каждому получателю запроса SIP. Однако получатели, помеченные значениями «bcc», не получают об этом явного уведомления.
o URI-list servers MUST preserve with a "bcc" copy control in the recipient-history list the URI that identifies the recipient (if any) and MUST remove the remaining URIs marked with a "bcc" copy control. Consequently, each recipient receives a different recipient-history list. However, recipients who have been marked with a "bcc" copy control are explicitly informed about it.
o Серверы списков URI ДОЛЖНЫ сохранять в списке истории получателей с управлением копированием «bcc» URI, идентифицирующий получателя (если таковой есть), и ДОЛЖНЫ удалить остальные URI с пометкой управления копированием «bcc». Следовательно, каждый получатель получает свой список истории получателей. Однако получатели, помеченные управлением копированием «bcc», получают об этом явное уведомление.
Implementations that are able to receive recipient-history lists must pay attention to the contents of the list. If the recipient's URI is not included in the recipient-history list or if it is included but tagged with a "bcc" copy control, then implementations SHOULD prevent the user from replying to all the recipients of the SIP request. This would allow the non-blind recipients to notice the existence of blind recipients of the SIP request. A new 'anonymize' attribute can be included in a <entry> element of the resource list document format [RFC4826]. If set to a "true" value, it provides an indication to the URI-list server for not disclosing the URI itself in a URI list sent to the recipient, but instead to anonymize the URI (i.e., making it bogus in the recipient- history XML resource list). URI-list servers can use URIs tagged with the 'anonymize' attribute for routing SIP requests, but MUST convert them to the SIP URI "sip:anonymous@anonymous.invalid" in recipient-history lists. The default value of the 'anonymize' attribute is "false".
Реализации, способные принимать списки истории получателей, должны обращать внимание на содержимое списка. Если URI получателя не включён в список истории получателей или включён, но помечен управлением копированием «bcc», то реализации СЛЕДУЕТ не позволять пользователю отвечать всем получателям запроса SIP. Это позволило бы не-слепым получателям заметить существование слепых получателей запроса SIP. В элемент <entry> формата документа списка ресурсов [RFC4826] можно включить новый атрибут 'anonymize'. Если ему задано значение «true», это указывает серверу списков URI не раскрывать сам URI в списке, отправляемом получателю, а вместо этого анонимизировать URI (то есть сделать его фиктивным в списке ресурсов XML истории получателей). Серверы списков URI могут использовать URI с пометкой атрибута 'anonymize' для маршрутизации запросов SIP, но ДОЛЖНЫ преобразовывать их в URI SIP «sip:anonymous@anonymous.invalid» в списках истории получателей. Значение атрибута 'anonymize' по умолчанию — «false».
There are occasions where the URI-list server encounters the same URI entry duplicated in a resource list, where duplicated URI entries are tagged with the same or different values of the 'copyControl' attribute. There are no reasonable usages that justify duplicated URIs in resource lists; thus, this is considered an error. URI-list servers should not send duplicated copies of the same SIP request to the same intended recipient. In case the URI-list server encounters the same URI entry duplicated in a resource list, it should send at most a single copy of the request to that intended recipient. For each set of duplicated URI entries, the URI-list server MUST select the highest precedence value of the 'copyControl' attribute for the same intended recipient. The order of precedence of the values of the 'copyControl' attribute is: "to", "cc", and "bcc". Once the URI- list server has selected a value for the 'copyControl' attribute of an intended recipient, the URI-list server can continue processing the request.
Бывают случаи, когда сервер списков URI встречает в списке ресурсов повторяющуюся запись URI, причём дублирующиеся записи URI помечены одинаковыми или разными значениями атрибута 'copyControl'. Не существует разумных вариантов использования, оправдывающих дублирование URI в списках ресурсов; поэтому это считается ошибкой. Серверы списков URI не должны отправлять дублирующиеся копии одного и того же запроса SIP одному и тому же предполагаемому получателю. Если сервер списков URI встречает в списке ресурсов повторяющуюся запись URI, он должен отправить этому предполагаемому получателю не более одной копии запроса. Для каждого набора дублирующихся записей URI сервер списков URI ДОЛЖЕН выбрать значение атрибута 'copyControl' с наивысшим приоритетом для одного и того же предполагаемого получателя. Порядок приоритета значений атрибута 'copyControl': «to», «cc» и «bcc». После того как сервер списков URI выбрал значение атрибута 'copyControl' для предполагаемого получателя, сервер списков URI может продолжить обработку запроса.
Processing of URIs tagged with a 'copyControl' attribute set to a "bcc" value has higher precedence over the 'anonymize' attribute. Thus, if the 'copyControl' of a URI is set to "bcc", the URI-list server MUST remove that URI from the recipient-history list, and the 'anonymize' attribute will be ignored. Therefore, the 'anonymize' attribute is only useful for those URIs tagged with a 'copyControl' of "to" or "cc".
Обработка URI с атрибутом 'copyControl', установленным в значение «bcc», имеет более высокий приоритет, чем атрибут 'anonymize'. Поэтому если для 'copyControl' URI задано «bcc», сервер списков URI ДОЛЖЕН удалить этот URI из списка истории получателей, а атрибут 'anonymize' будет проигнорирован. Следовательно, атрибут 'anonymize' полезен только для тех URI, которые помечены 'copyControl' со значением «to» или «cc».
A new 'count' attribute can be also included in an <entry> element of the resource list document format [RFC4826]. It provides the number of equal URIs. Typically, recipient lists created by UACs will not have equal (or duplicate) URI entries; thus, it is not expected to contain URIs tagged with 'count' attributes. However, recipient- history lists can contain duplicated anonymized URIs; therefore, it is expected that recipient-history lists will contain 'count' attributes. The default value of the 'count' attribute is "1". The 'copyControl', 'anonymize', and 'count' attributes SHOULD be included as modifiers of any of the child elements included in the <list> element of a resource list (e.g., attribute of the <entry> or <external> elements).
Новый атрибут 'count' также можно включить в элемент <entry> формата документа списка ресурсов [RFC4826]. Он задаёт число одинаковых URI. Обычно списки получателей, создаваемые клиентами UAC, не содержат одинаковых (или дублирующихся) записей URI; поэтому не ожидается, что они будут содержать URI с атрибутом 'count'. Однако списки истории получателей могут содержать дублирующиеся анонимизированные URI; поэтому ожидается, что списки истории получателей будут содержать атрибуты 'count'. Значение атрибута 'count' по умолчанию — «1». Атрибуты 'copyControl', 'anonymize' и 'count' СЛЕДУЕТ включать как модификаторы любого из дочерних элементов, входящих в элемент <list> списка ресурсов (например, как атрибут элементов <entry> или <external>).

В разделе 5 описан формат атрибутов 'copyControl', 'anonymize' и 'count'. Реализации, соответствующие настоящей спецификации, ДОЛЖНЫ поддерживать эту схему XML.

If the recipient's URI is not included in recipient-history list or if it is included but tagged with a "bcc" copy control, then they SHOULD prevent the user from replying to all the recipients of the SIP request. This would allow the non-blind recipients to notice the existence of blind recipients in the original SIP request.
Реализации, получающие списки истории получателей, должны обращать внимание на содержимое списка. Если URI получателя не включён в список истории получателей или включён, но помечен управлением копированием «bcc», то им СЛЕДУЕТ не позволять пользователю отвечать всем получателям запроса SIP. 7. Carrying URI Lists in SIP
7. Передача списков URI в SIP
A SIP UAC (User Agent Client) that composes a SIP request can include a URI list with the extensions specified in this document to indicate the list of intended recipients. On doing so, as specified in RFC 5363 [RFC5363], the UAC adds a Content-Disposition [RFC2183] header field set to the value 'recipient-list'. Typically UACs send these 'recipient-list' bodies to URI-list services (this corresponds to flow F1 in Figure 1). A body whose Content-Disposition type is 'recipient-list' contains a URI list that includes the intended recipients of the SIP request, something known throughout this document as a recipient list. The <entry> element in the URI list MAY also include a 'copyControl' and 'anonymize' attributes, as specified in Section 4.
Клиент агента пользователя (UAC) SIP, составляющий запрос SIP, может включить список URI с расширениями, указанными в настоящем документе, чтобы указать список предполагаемых получателей. При этом, как указано в RFC 5363 [RFC5363], UAC добавляет поле заголовка Content-Disposition [RFC2183], установленное в значение 'recipient-list'. Обычно UAC отправляют эти тела 'recipient-list' службам списков URI (это соответствует потоку F1 на рисунке 1). Тело, тип Content-Disposition которого — 'recipient-list', содержит список URI, включающий предполагаемых получателей запроса SIP, что в настоящем документе называется списком получателей. Элемент <entry> в списке URI МОЖЕТ также включать атрибуты 'copyControl' и 'anonymize', как указано в разделе 4.
To be able to inform intended recipients of who else is receiving a copy of the SIP request, we define a new mail disposition type to be included in a Content-Disposition [RFC2183] header field of a SIP request. The value of this new disposition type is 'recipient-list- history' and its purpose is to indicate a list of recipients that a SIP request was sent to, something known throughout this document as a recipient-history list. A body whose Content-Disposition type is 'recipient-list-history' contains a URI list with the visible (including anonymized) recipients of the SIP request. The <entry> element in the URI list MAY also include a 'copyControl' and 'count' attributes, as specified in Section 4.
Чтобы иметь возможность сообщать предполагаемым получателям, кто ещё получает копию запроса SIP, мы определяем новый тип диспозиции почты, включаемый в поле заголовка Content-Disposition [RFC2183] запроса SIP. Значение этого нового типа диспозиции — 'recipient-list-history', и его назначение — указывать список получателей, которым был отправлен запрос SIP, что в настоящем документе называется списком истории получателей. Тело, тип Content-Disposition которого — 'recipient-list-history', содержит список URI с видимыми (включая анонимизированные) получателями запроса SIP. Элемент <entry> в списке URI МОЖЕТ также включать атрибуты 'copyControl' и 'count', как указано в разделе 4.
On sending a SIP request that contains a recipient-history list, if the intended recipient does not support this specification, the SIP request should not fail. In order to ensure successful receipt of the SIP requests that include 'recipient-list-history' bodies, User Agents (such as URI-list servers) that build SIP requests with the Content-Disposition header field set to 'recipient-list-history' SHOULD add a "handling" parameter [RFC3204] set to "optional". Otherwise, the SIP request could fail and never be received by the intended recipient.
При отправке запроса SIP, содержащего список истории получателей, если предполагаемый получатель не поддерживает настоящую спецификацию, запрос SIP не должен завершаться неудачей. Чтобы обеспечить успешное получение запросов SIP, включающих тела 'recipient-list-history', агенты пользователя (например, серверы списков URI), которые строят запросы SIP с полем заголовка Content-Disposition, установленным в 'recipient-list-history', СЛЕДУЕТ добавлять параметр "handling" [RFC3204], установленный в "optional". В противном случае запрос SIP мог бы завершиться неудачей и так и не быть получен предполагаемым получателем.
Even though "Message Body Handling in SIP" [SIP_BODY] mandates support for multipart bodies, legacy recipients may not support them. In such a case, if the request sent by the relay to the recipient needs to contain another body (e.g., a MESSAGE request carrying a message in its body), the relay will not be able to use this extension because the recipient would not be able to process a multipart body with the original body plus the 'recipient-list- history' body.
Даже несмотря на то, что документ «Message Body Handling in SIP» [SIP_BODY] требует поддержки составных тел, устаревшие получатели могут их не поддерживать. В таком случае, если запрос, отправленный ретранслятором получателю, должен содержать другое тело (например, запрос MESSAGE, несущий сообщение в своём теле), ретранслятор не сможет использовать это расширение, потому что получатель не смог бы обработать составное тело с исходным телом плюс телом 'recipient-list-history'.
8. Security Considerations
8. Вопросы безопасности
RFC 5363 [RFC5363] discusses issues related to SIP URI-list services. Implementations of this specification MUST follow the security- related rules in RFC 5363 [RFC5363]. These rules include opt-in lists and mandatory authentication and authorization of clients.
RFC 5363 [RFC5363] обсуждает вопросы, связанные со службами списков URI SIP. Реализации настоящей спецификации ДОЛЖНЫ следовать правилам, касающимся безопасности, из RFC 5363 [RFC5363]. Эти правила включают списки с предварительным согласием и обязательную аутентификацию и авторизацию клиентов.
User Agent Clients SHOULD NOT hand SIP requests containing URI-list services to unauthenticated and untrusted parties. This is to avoid man-in-the-middle attacks or acquiring URI lists for performing spam attacks. URI lists may contain private information, such as SIP URIs. It is therefore not desirable that these URI lists are known by third parties. Eavesdroppers are able to watch URI lists contained in SIP requests unless the SIP message is sent over a secured channel, by using any of the available SIP mechanisms, such as Transport Layer Security (TLS) [RFC4346], or unless the URI-list body itself is encrypted with, e.g., S/MIME [RFC3851]. Therefore, it is RECOMMENDED that URI-list bodies are encrypted with S/MIME [RFC3851] or that the SIP request is encrypted with TLS [RFC4346] or any other suitable encryption mechanism.
Клиентам агентов пользователя НЕ СЛЕДУЕТ передавать запросы SIP, содержащие службы списков URI, неаутентифицированным и недоверенным сторонам. Это делается во избежание атак «человек посередине» или получения списков URI для проведения спам-атак. Списки URI могут содержать конфиденциальную информацию, например URI SIP. Поэтому нежелательно, чтобы эти списки URI были известны третьим сторонам. Подслушивающие стороны могут просматривать списки URI, содержащиеся в запросах SIP, если сообщение SIP не передаётся по защищённому каналу с использованием любого из доступных механизмов SIP, таких как протокол безопасности транспортного уровня (TLS) [RFC4346], или если само тело списка URI не зашифровано, например, с помощью S/MIME [RFC3851]. Поэтому РЕКОМЕНДУЕТСЯ шифровать тела списков URI с помощью S/MIME [RFC3851] или шифровать запрос SIP с помощью TLS [RFC4346] либо любого другого подходящего механизма шифрования.
Note that this URI list does not indicate the actual participants in the session. It indicates only the URIs invited and that might accept the request. It does not assert that these parties actually exist, that they are reachable at the given URI, or that they have accepted the invitation. No inferences about billing should be made from this information. It is subject to spoofing by loading the list with falsified content.
Отметим, что этот список URI не указывает фактических участников сессии. Он указывает только URI, которые приглашены и могут принять запрос. Он не утверждает, что эти стороны действительно существуют, достижимы по данному URI или приняли приглашение. Из этой информации не следует делать никаких выводов о выставлении счетов. Она подвержена подмене путём загрузки списка со сфальсифицированным содержимым.
Issuers of SIP request use the "bcc" copy control attribute described in Section 4 to facilitate sending SIP requests to recipients without revealing the URIs of one or more of the other recipients. Mishandling this use of "bcc" copy control has implications for confidential information that might be revealed, which could eventually lead to security problems through knowledge of even the existence of a particular URI. For example, if using the first method described in Section 4, where the "bcc" tagged URIs are removed from the recipient-history list, blind recipients have no explicit indication that they have been sent a blind copy of the SIP request, except insofar as their URI does not appear in the recipient-history list. Because of this, one of the blind URIs could potentially send a reply to all of the shown recipients and accidentally reveal that the message went to the blind recipient. When the second method from Section 4 is used, the blind recipient's address appears in the recipient-history list of a separate copy of the list. If the "bcc" tagged URI sent contains all of the "bcc" tagged URIs, all of the "bcc" recipients will be seen by each "bcc" recipient.
Инициаторы запросов SIP используют атрибут управления копированием «bcc», описанный в разделе 4, чтобы облегчить отправку запросов SIP получателям, не раскрывая URI одного или нескольких других получателей. Неправильная обработка этого использования управления копированием «bcc» имеет последствия для конфиденциальной информации, которая может быть раскрыта, что в конечном итоге может привести к проблемам безопасности из-за знания даже о существовании конкретного URI. Например, при использовании первого метода, описанного в разделе 4, когда URI с пометкой «bcc» удаляются из списка истории получателей, слепые получатели не имеют явного указания на то, что им была отправлена скрытая копия запроса SIP, кроме того, что их URI не появляется в списке истории получателей. Из-за этого один из слепых URI потенциально может отправить ответ всем показанным получателям и случайно раскрыть, что сообщение ушло слепому получателю. Когда используется второй метод из раздела 4, адрес слепого получателя появляется в списке истории получателей отдельной копии списка. Если отправленный URI с пометкой «bcc» содержит все URI с пометкой «bcc», все получатели «bcc» будут видны каждому получателю «bcc».
Even if a separate message is sent to each "bcc" recipient with only the individual's URI, implementations still need to be careful to process replies to the message as per Section 4 so as not to accidentally reveal the blind recipient to other recipients.
Даже если каждому получателю «bcc» отправляется отдельное сообщение только с его собственным URI, реализации всё равно должны аккуратно обрабатывать ответы на сообщение согласно разделу 4, чтобы случайно не раскрыть скрытого получателя другим получателям.
