Abstract
Аннотация
This document describes the Message Session Relay Protocol, a protocol for transmitting a series of related instant messages in the context of a session. Message sessions are treated like any other media stream when set up via a rendezvous or session creation protocol such as the Session Initiation Protocol.
Настоящий документ описывает протокол ретрансляции сеансов сообщений — протокол передачи последовательности связанных мгновенных сообщений в контексте сеанса. Сеансы обмена сообщениями рассматриваются как любой другой поток медиаданных при установлении через протокол рандеву или создания сеанса, такой как протокол инициирования сеансов (SIP).
1. Introduction
1. Введение
A series of related instant messages between two or more parties can be viewed as part of a "message session", that is, a conversational exchange of messages with a definite beginning and end. This is in contrast to individual messages each sent independently. Messaging schemes that track only individual messages can be described as "page-mode" messaging, whereas messaging that is part of a "session" with a definite start and end is called "session-mode" messaging.
Последовательность связанных мгновенных сообщений между двумя или более сторонами можно рассматривать как часть "сеанса обмена сообщениями", то есть разговорного обмена сообщениями с определённым началом и концом. Это отличается от отдельных сообщений, каждое из которых отправляется независимо. Схемы обмена сообщениями, которые отслеживают только отдельные сообщения, можно назвать обменом в "постраничном режиме", тогда как обмен сообщениями в рамках "сеанса" с определённым началом и концом называется обменом в "сеансовом режиме".
Page-mode messaging is enabled in SIP via the SIP [4] MESSAGE method [22]. Session-mode messaging has a number of benefits over page-mode messaging, however, such as explicit rendezvous, tighter integration with other media-types, direct client-to-client operation, and brokered privacy and security.
Обмен сообщениями в постраничном режиме реализуется в SIP через метод MESSAGE [22] протокола SIP [4]. Однако обмен сообщениями в сеансовом режиме имеет ряд преимуществ перед постраничным режимом, таких как явное рандеву, более тесная интеграция с другими типами медиаданных, прямая работа клиент-клиент и посредническое обеспечение конфиденциальности и безопасности.
This document defines a session-oriented instant message transport protocol called the Message Session Relay Protocol (MSRP), whose sessions can be negotiated with an offer or answer [3] using the Session Description Protocol (SDP) [2]. The exchange is carried by some signaling protocol, such as SIP [4]. This allows a communication user agent to offer a messaging session as one of the possible media-types in a session. For instance, Alice may want to communicate with Bob. Alice doesn't know at the moment whether Bob has his phone or his IM client handy, but she's willing to use either. She sends an invitation to a session to the address of record she has for Bob, sip:bob@example.com. Her invitation offers both voice and an IM session. The SIP services at example.com forward the invitation to Bob at his currently registered clients. Bob accepts the invitation at his IM client, and they begin a threaded chat conversation.
Настоящий документ определяет ориентированный на сеансы протокол транспортировки мгновенных сообщений под названием "протокол ретрансляции сеансов сообщений" (MSRP), сеансы которого могут быть согласованы с помощью предложения или ответа [3] с использованием протокола описания сеансов (SDP) [2]. Обмен переносится некоторым сигнальным протоколом, например SIP [4]. Это позволяет коммуникационному пользовательскому агенту предложить сеанс обмена сообщениями в качестве одного из возможных типов медиаданных в сеансе. Например, Алиса может захотеть связаться с Бобом. В данный момент Алиса не знает, под рукой ли у Боба телефон или его клиент мгновенных сообщений, но она готова использовать любой из них. Она отправляет приглашение к сеансу на адрес записи, который у неё есть для Боба, sip:bob@example.com. Её приглашение предлагает и голос, и сеанс обмена мгновенными сообщениями. Службы SIP в example.com пересылают приглашение Бобу на его зарегистрированные в данный момент клиенты. Боб принимает приглашение на своём клиенте мгновенных сообщений, и они начинают связанную беседу в чате.
When a user uses an Instant Messaging (IM) URL, RFC 3861 [32] defines how DNS can be used to map this to a particular protocol to establish the session such as SIP. SIP can use an offer/answer model to transport the MSRP URIs for the media in SDP. This document defines how the offer/answer exchange works to establish MSRP connections and how messages are sent across the MSRP, but it does not deal with the issues of mapping an IM URL to a session establishment protocol.
Когда пользователь использует URL мгновенных сообщений (IM), RFC 3861 [32] определяет, как DNS может применяться для его отображения на конкретный протокол установления сеанса, такой как SIP. SIP может использовать модель предложения/ответа для транспортировки URI MSRP медиаданных в SDP. Настоящий документ определяет, как обмен предложения/ответа работает для установления соединений MSRP и как сообщения передаются по MSRP, но он не рассматривает вопросы отображения IM URL на протокол установления сеанса.
This session model allows message sessions to be integrated into advanced communications applications with little to no additional protocol development. For example, during the above chat session, Bob decides Alice really needs to be talking to Carol. Bob can transfer [21] Alice to Carol, introducing them into their own messaging session. Messaging sessions can then be easily integrated into call-center and dispatch environments using third-party call control [20] and conferencing [19] applications. This document specifies MSRP behavior only for peer-to-peer sessions, that is, sessions crossing only a single hop. MSRP relay devices [23] (referred to herein as "relays") are specified in a separate document. An endpoint that implements this specification, but not the relay specification, will be unable to introduce relays into the message path, but will still be able to interoperate with peers that do use relays.
Эта модель сеанса позволяет интегрировать сеансы обмена сообщениями в перспективные коммуникационные приложения почти без дополнительной разработки протоколов. Например, во время указанного сеанса чата Боб решает, что Алисе действительно нужно поговорить с Кэрол. Боб может перевести [21] Алису к Кэрол, введя их в их собственный сеанс обмена сообщениями. Затем сеансы обмена сообщениями можно легко интегрировать в среды колл-центров и диспетчерских, используя приложения управления вызовами третьей стороной [20] и конференц-связи [19]. Настоящий документ определяет поведение MSRP только для одноранговых сеансов, то есть сеансов, пересекающих лишь один переход. Устройства ретрансляции MSRP [23] (далее — "ретрансляторы") определены в отдельном документе. Конечная точка, реализующая эту спецификацию, но не спецификацию ретранслятора, не сможет вводить ретрансляторы в путь сообщений, но всё же сможет взаимодействовать с узлами, которые используют ретрансляторы.

This document consistently refers to a "message" as a complete unit of MIME or text content. In some cases, a message is split and delivered in more than one MSRP request. Each of these portions of the complete message is called a "chunk".
В настоящем документе "сообщение" последовательно обозначает законченную единицу содержимого MIME или текста. В некоторых случаях сообщение разделяется и доставляется более чем в одном запросе MSRP. Каждая из этих частей полного сообщения называется "фрагментом".
3. Applicability of MSRP
3. Область применения MSRP
MSRP is not designed for use as a standalone protocol. MSRP MUST be used only in the context of a rendezvous mechanism meeting the following requirements:
MSRP не предназначен для использования в качестве самостоятельного протокола. MSRP ДОЛЖЕН использоваться только в контексте механизма рандеву, удовлетворяющего следующим требованиям:
o The rendezvous mechanism MUST provide both MSRP URIs associated with an MSRP session to each of the participating endpoints. The rendezvous mechanism MUST implement mechanisms to protect the confidentiality of these URIs -- they MUST NOT be made available to an untrusted third party or be easily discoverable.
o Механизм рандеву ДОЛЖЕН предоставлять оба URI MSRP, связанные с сеансом MSRP, каждой из участвующих конечных точек. Механизм рандеву ДОЛЖЕН реализовывать механизмы защиты конфиденциальности этих URI — они НЕ ДОЛЖНЫ становиться доступными недоверенной третьей стороне или легко обнаруживаться.
o The rendezvous mechanism MUST provide mechanisms for the negotiation of any supported MSRP extensions that are not backwards compatible.
o Механизм рандеву ДОЛЖЕН предоставлять механизмы согласования любых поддерживаемых расширений MSRP, не являющихся обратно совместимыми.
o The rendezvous mechanism MUST be able to natively transport im: URIs or automatically translate im: URIs [27] into the addressing identifiers of the rendezvous protocol.
o Механизм рандеву ДОЛЖЕН быть способен изначально транспортировать URI im: или автоматически преобразовывать URI im: [27] в идентификаторы адресации протокола рандеву.
To use a rendezvous mechanism with MSRP, an RFC MUST be prepared that describes how it exchanges MSRP URIs and meets these requirements listed here. This document provides such a description for the use of MSRP in the context of SIP and SDP.
Чтобы использовать механизм рандеву с MSRP, ДОЛЖЕН быть подготовлен RFC, описывающий, как он обменивается URI MSRP и удовлетворяет перечисленным здесь требованиям. Настоящий документ содержит такое описание использования MSRP в контексте SIP и SDP.
SIP meets these requirements for a rendezvous mechanism. The MSRP URIs are exchanged using SDP in an offer/answer exchange via SIP. The exchanged SDP can also be used to negotiate MSRP extensions. This SDP can be secured using any of the mechanisms available in SIP, including using the sips mechanism to ensure transport security across intermediaries and Secure/Multipurpose Internet Mail Extensions (S/MIME) for end-to-end protection of the SDP body. SIP can carry arbitrary URIs (including im: URIs) in the Request-URI, and procedures are available to map im: URIs to sip: or sips: URIs. It is expected that initial deployments of MSRP will use SIP as its rendezvous mechanism.
SIP удовлетворяет этим требованиям к механизму рандеву. URI MSRP обмениваются с помощью SDP в ходе обмена предложения/ответа через SIP. Обмениваемый SDP также может использоваться для согласования расширений MSRP. Этот SDP может быть защищён любым из механизмов, доступных в SIP, включая использование механизма sips для обеспечения безопасности транспорта через посредников и Secure/Multipurpose Internet Mail Extensions (S/MIME) для сквозной защиты тела SDP. SIP может переносить произвольные URI (включая URI im:) в Request-URI, и имеются процедуры для отображения URI im: на URI sip: или sips:. Ожидается, что начальные развёртывания MSRP будут использовать SIP в качестве механизма рандеву.
4. Protocol Overview
4. Обзор протокола
MSRP is a text-based, connection-oriented protocol for exchanging arbitrary (binary) MIME [8] content, especially instant messages. This section is a non-normative overview of how MSRP works and how it is used with SIP.
MSRP — это текстовый протокол, ориентированный на соединения, для обмена произвольным (двоичным) содержимым MIME [8], особенно мгновенными сообщениями. Этот раздел представляет собой ненормативный обзор того, как работает MSRP и как он используется с SIP.
MSRP sessions are typically arranged using SIP the same way a session of audio or video media is set up. One SIP user agent (Alice) sends the other (Bob) a SIP invitation containing an offered session- description that includes a session of MSRP. The receiving SIP user agent can accept the invitation and include an answer session- description that acknowledges the choice of media. Alice's session description contains an MSRP URI that describes where she is willing to receive MSRP requests from Bob, and vice versa. (Note: Some lines in the examples are removed for clarity and brevity.)
Сеансы MSRP обычно организуются с помощью SIP так же, как устанавливается сеанс аудио- или видеомедиаданных. Один пользовательский агент SIP (Алиса) отправляет другому (Бобу) приглашение SIP, содержащее предложенное описание сеанса, которое включает сеанс MSRP. Принимающий пользовательский агент SIP может принять приглашение и включить ответное описание сеанса, подтверждающее выбор медиаданных. Описание сеанса Алисы содержит URI MSRP, описывающий, где она готова принимать запросы MSRP от Боба, и наоборот. (Примечание: некоторые строки в примерах удалены для ясности и краткости.)

MSRP defines two request types, or methods. SEND requests are used to deliver a complete message or a chunk (a portion of a complete message), while REPORT requests report on the status of a previously sent message, or a range of bytes inside a message. When Alice receives Bob's answer, she checks to see if she has an existing connection to Bob. If not, she opens a new connection to Bob using the URI he provided in the SDP. Alice then delivers a SEND request to Bob with her initial message, and Bob replies indicating that Alice's request was received successfully. MSRP a786hjs2 SEND To-Path: msrp://biloxi.example.com:12763/kjhd37s2s20w2a;tcp From-Path: msrp://atlanta.example.com:7654/jshA7weztas;tcp Message-ID: 87652491 Byte-Range: 1-25/25 Content-Type: text/plain
MSRP определяет два типа запросов, или метода. Запросы SEND используются для доставки полного сообщения или фрагмента (части полного сообщения), тогда как запросы REPORT сообщают о состоянии ранее отправленного сообщения или диапазона байтов внутри сообщения. Получив ответ Боба, Алиса проверяет, есть ли у неё существующее соединение с Бобом. Если нет, она открывает новое соединение с Бобом, используя URI, который он предоставил в SDP. Затем Алиса доставляет Бобу запрос SEND со своим первоначальным сообщением, и Боб отвечает, указывая, что запрос Алисы был успешно получен. Alice's request begins with the MSRP start line, which contains a transaction identifier that is also used for request framing. Next she includes the path of URIs to the destination in the To-Path header field, and her own URI in the From-Path header field. In this typical case, there is just one "hop", so there is only one URI in each path header field. She also includes a message ID, which she can use to correlate status reports with the original message. Next she puts the actual content. Finally, she closes the request with an end-line of seven hyphens, the transaction identifier, and a "$" to indicate that this request contains the end of a complete message.
Запрос Алисы начинается со стартовой строки MSRP, которая содержит идентификатор транзакции, также используемый для кадрирования запроса. Затем она включает путь из URI к получателю в поле заголовка To-Path, а свой собственный URI — в поле заголовка From-Path. В этом типичном случае имеется всего один "переход", поэтому в каждом поле заголовка пути только один URI. Она также включает идентификатор сообщения, который может использовать для соотнесения отчётов о состоянии с исходным сообщением. Далее она помещает фактическое содержимое. Наконец, она завершает запрос конечной строкой из семи дефисов, идентификатора транзакции и "$", указывающего, что этот запрос содержит конец полного сообщения.
If Alice wants to deliver a very large message, she can split the message into chunks and deliver each chunk in a separate SEND request. The message ID corresponds to the whole message, so the receiver can also use it to reassemble the message and tell which chunks belong with which message. Chunking is described in more detail in Section 5.1. The Byte-Range header field identifies the portion of the message carried in this chunk and the total size of the message.
Если Алиса хочет доставить очень большое сообщение, она может разбить его на фрагменты и доставлять каждый фрагмент в отдельном запросе SEND. Идентификатор сообщения соответствует всему сообщению, поэтому получатель также может использовать его для повторной сборки сообщения и определения, какие фрагменты принадлежат какому сообщению. Разбиение на фрагменты более подробно описано в разделе 5.1. Поле заголовка Byte-Range идентифицирует часть сообщения, переносимую в этом фрагменте, и общий размер сообщения.
Alice can also specify what type of reporting she would like in response to her request. If Alice requests positive acknowledgments, Bob sends a REPORT request to Alice confirming the delivery of her complete message. This is especially useful if Alice sent a series of SEND requests containing chunks of a single message. More on requesting types of reports and errors is described in Section 5.3.
Алиса также может указать, какой тип отчётности она хотела бы получить в ответ на свой запрос. Если Алиса запрашивает положительные подтверждения, Боб отправляет Алисе запрос REPORT, подтверждающий доставку её полного сообщения. Это особенно полезно, если Алиса отправила последовательность запросов SEND, содержащих фрагменты одного сообщения. Подробнее о запросе типов отчётов и об ошибках рассказывается в разделе 5.3.
Alice and Bob choose their MSRP URIs in such a way that it is difficult to guess the exact URI. Alice and Bob can reject requests to URIs they are not expecting to service and can correlate the specific URI with the probable sender. Alice and Bob can also use TLS [1] to provide channel security over this hop. To receive MSRP requests over a TLS protected connection, Alice or Bob could advertise URIs with the "msrps" scheme instead of "msrp".
Алиса и Боб выбирают свои URI MSRP таким образом, чтобы было трудно угадать точный URI. Алиса и Боб могут отклонять запросы к URI, которые они не ожидают обслуживать, и могут соотносить конкретный URI с вероятным отправителем. Алиса и Боб также могут использовать TLS [1] для обеспечения безопасности канала на этом переходе. Чтобы принимать запросы MSRP по соединению, защищённому TLS, Алиса или Боб могут анонсировать URI со схемой "msrps" вместо "msrp".
MSRP is designed with the expectation that MSRP can carry URIs for nodes on the far side of relays. For this reason, a URI with the "msrps" scheme makes no assertion about the security properties of other hops, just the next hop. The user agent knows the URI for each hop, so it can verify that each URI has the desired security properties.
MSRP разработан с расчётом на то, что он может переносить URI для узлов по другую сторону ретрансляторов. По этой причине URI со схемой "msrps" не делает никаких утверждений о свойствах безопасности других переходов, а только следующего перехода. Пользовательский агент знает URI каждого перехода, поэтому может проверить, что каждый URI обладает нужными свойствами безопасности.

5. Ключевые понятия
5.1. MSRP Framing and Message Chunking
5.1. Кадрирование MSRP и разбиение сообщений на фрагменты
Messages sent using MSRP can be very large and can be delivered in several SEND requests, where each SEND request contains one chunk of the overall message. Long chunks may be interrupted in mid- transmission to ensure fairness across shared transport connections. To support this, MSRP uses a boundary-based framing mechanism. The start line of an MSRP request contains a unique identifier that is also used to indicate the end of the request. Included at the end of the end-line, there is a flag that indicates whether this is the last chunk of data for this message or whether the message will be continued in a subsequent chunk. There is also a Byte-Range header field in the request that indicates the overall position of this chunk inside the complete message.
Сообщения, отправляемые с помощью MSRP, могут быть очень большими и могут доставляться в нескольких запросах SEND, где каждый запрос SEND содержит один фрагмент общего сообщения. Длинные фрагменты могут быть прерваны в середине передачи, чтобы обеспечить справедливость при совместном использовании транспортных соединений. Для поддержки этого MSRP использует механизм кадрирования на основе границ. Стартовая строка запроса MSRP содержит уникальный идентификатор, который также используется для указания конца запроса. В конце конечной строки включён флаг, указывающий, является ли это последним фрагментом данных для данного сообщения или сообщение будет продолжено в последующем фрагменте. В запросе также имеется поле заголовка Byte-Range, указывающее общее положение этого фрагмента внутри полного сообщения.

This chunking mechanism allows a sender to interrupt a chunk part of the way through sending it. The ability to interrupt messages allows multiple sessions to share a TCP connection, and for large messages to be sent efficiently while not blocking other messages that share the same connection, or even the same MSRP session. Any chunk that is larger than 2048 octets MUST be interruptible. While MSRP would be simpler to implement if each MSRP session used its own TCP connection, there are compelling reasons to conserve connections. For example, the TCP peer may be a relay device that connects to many other peers. Such a device will scale better if each peer does not create a large number of connections. (Note that in the above example, the initial chunk was interruptible for the sake of example, even though its size is well below the limit for which interruptibility would be required.)
Этот механизм разбиения на фрагменты позволяет отправителю прервать фрагмент на полпути его отправки. Возможность прерывать сообщения позволяет нескольким сеансам совместно использовать одно TCP-соединение, а большие сообщения отправлять эффективно, не блокируя другие сообщения, использующие то же соединение или даже тот же сеанс MSRP. Любой фрагмент размером более 2048 октетов ДОЛЖЕН допускать прерывание. Например, TCP-пир может быть устройством ретрансляции, которое соединяется со многими другими пирами. Такое устройство будет масштабироваться лучше, если каждый пир не создаёт большое количество соединений. The chunking mechanism only applies to the SEND method, as it is the only method used to transfer message content.
Механизм разбиения на фрагменты применяется только к методу SEND, поскольку это единственный метод, используемый для передачи содержимого сообщения.

5.3. MSRP Transaction and Report Model
5.3. Модель транзакций и отчётов MSRP
A sender sends MSRP requests to a receiver. The receiver MUST quickly accept or reject the request. If the receiver initially accepted the request, it still may then do things that take significant time to succeed or fail. For example, if the receiver is an MSRP to Extensible Messaging and Presence Protocol (XMPP) [30] gateway, it may forward the message over XMPP. The XMPP side may later indicate that the request did not work. At this point, the MSRP receiver may need to indicate that the request did not succeed. There are two important concepts here: first, the hop-by-hop delivery of the request may succeed or fail; second, the end result of the request may or may not be successfully processed. The first type of status is referred to as "transaction status" and may be returned in response to a request. The second type of status is referred to as "delivery status" and may be returned in a REPORT transaction.
Отправитель посылает запросы MSRP получателю. Получатель ДОЛЖЕН быстро принять или отклонить запрос. Если получатель первоначально принял запрос, он всё же может затем выполнять действия, для успеха или неудачи которых требуется значительное время. Например, если получатель является шлюзом между MSRP и протоколом обмена сообщениями и присутствия (XMPP) [30], он может переслать сообщение по XMPP. Сторона XMPP может позже указать, что запрос не удался. В этот момент получатель MSRP может нуждаться в указании того, что запрос не завершился успешно. Здесь важны два понятия: во-первых, доставка запроса от перехода к переходу может успешно завершиться или не завершиться; во-вторых, конечный результат запроса может быть успешно обработан или нет. Первый тип состояния называется "состоянием транзакции" и может возвращаться в ответ на запрос. Второй тип состояния называется "состоянием доставки" и может возвращаться в транзакции REPORT.
The original sender of a request can indicate if they wish to receive reports for requests that fail, and can independently indicate if they wish to receive reports for requests that succeed. A receiver only sends a success REPORT if it knows that the request was successfully delivered, and the sender requested a success report. A receiver only sends a failure REPORT if the request failed to be delivered and the sender requested failure reports.
Исходный отправитель запроса может указать, желает ли он получать отчёты о запросах, завершившихся неудачей, и независимо указать, желает ли он получать отчёты о запросах, завершившихся успешно. Получатель отправляет отчёт об успехе, только если он знает, что запрос был успешно доставлен, и отправитель запросил отчёт об успехе. Получатель отправляет отчёт о неудаче, только если запрос не был доставлен и отправитель запросил отчёты о неудачах.
This document describes the behavior of MSRP endpoints. MSRP relays will introduce additional conditions that indicate a failure REPORT should be sent, such as the failure to receive a positive response from the next hop.
Настоящий документ описывает поведение конечных точек MSRP. Ретрансляторы MSRP вводят дополнительные условия, указывающие, что следует отправить отчёт о неудаче, например невозможность получить положительный ответ от следующего перехода.
Two header fields control the sender's desire to receive reports. The Success-Report header field can have a value of "yes" or "no" and the Failure-Report header field can have a value of "yes", "no", or "partial".
Два поля заголовка управляют желанием отправителя получать отчёты. Поле заголовка Success-Report может иметь значение "yes" или "no", а поле заголовка Failure-Report — значение "yes", "no" или "partial".
The combinations of reporting are needed to meet the various scenarios of currently deployed IM systems. Success-Report might be "no" in many public systems to reduce load, but might be "yes" in certain enterprise systems, such as systems used for securities trading. A Failure-Report value of "no" is useful for sending system messages such as "the system is going down in 5 minutes" without causing a response explosion to the sender. A Failure-Report of "yes" is used by many systems that wish to notify the user if the message failed. A Failure-Report of "partial" is a way to report errors other than timeouts. Timeout error reporting requires the sending hop to run a timer and the receiving hop to send an acknowledgment to stop the timer. Some systems don't want the overhead of doing this. "Partial" allows them to choose not to do so, but still allows error responses to be sent in many cases.
Комбинации отчётности необходимы для охвата различных сценариев развёрнутых в настоящее время систем обмена мгновенными сообщениями. Success-Report может иметь значение "no" во многих публичных системах для снижения нагрузки, но может быть "yes" в некоторых корпоративных системах, например в системах биржевой торговли. Значение Failure-Report "no" полезно для отправки системных сообщений, таких как "система будет отключена через 5 минут", не вызывая взрыва ответов у отправителя. Failure-Report "yes" используется многими системами, которые хотят уведомить пользователя о неудаче сообщения. Failure-Report "partial" — это способ сообщать об ошибках, отличных от тайм-аутов. Отчётность об ошибках тайм-аута требует, чтобы отправляющий переход запускал таймер, а принимающий переход отправлял подтверждение для остановки таймера. Некоторые системы не хотят нести накладные расходы на это. "Partial" позволяет им выбрать отказ от этого, но по-прежнему позволяет во многих случаях отправлять ответы об ошибках.
The term "partial" denotes that the hop-by-hop acknowledgment mechanism that would be required with a Failure-Report value of "yes" is not invoked. Thus, each device uses only "part" of the set of error detection tools available to them. This allows a compromise between no reporting of failures at all, and reporting every possible failure. For example, with "partial", a sending device does not have to keep transaction state around waiting for a positive acknowledgment.
Термин "partial" означает, что механизм подтверждения от перехода к переходу, который потребовался бы при значении Failure-Report "yes", не задействуется. Таким образом, каждое устройство использует лишь "часть" набора доступных ему средств обнаружения ошибок. Это позволяет достичь компромисса между полным отсутствием отчётности о сбоях и сообщением о каждой возможной неудаче. Например, при "partial" отправляющее устройство не обязано хранить состояние транзакции в ожидании положительного подтверждения.
But it still allows devices to report other types of errors. The receiving device could still report a policy violation such as an unacceptable content-type, or an ICMP error trying to connect to a downstream device.
Но это по-прежнему позволяет устройствам сообщать о других типах ошибок. Принимающее устройство всё ещё может сообщить о нарушении политики, например о неприемлемом типе содержимого, или об ошибке ICMP при попытке соединиться с нижестоящим устройством.

However, this requirement MAY be weakened if standardized mechanisms for negotiating the connection direction become available and are implemented by both parties to the connection.

Однако это требование МОЖЕТ быть ослаблено, если станут доступны стандартизованные механизмы согласования направления соединения и они будут реализованы обеими сторонами соединения.
Likewise, the active endpoint MUST immediately issue a SEND request. This initial SEND request MAY have a body if the sender has content to send, or it MAY have no body at all.
Аналогично, активная конечная точка ДОЛЖНА немедленно выдать запрос SEND. Этот первоначальный запрос SEND МОЖЕТ иметь тело, если отправителю есть что отправить, или МОЖЕТ вообще не иметь тела.

Если бы допускалось несколько соединений, связанных с одним и тем же сеансом, возникла бы проблема безопасности. Если первоначальный запрос SEND не защищён, подслушивающий может узнать URI и использовать его для вставки сообщений в сеанс через другое соединение.
If a connection fails for any reason, then an MSRP endpoint MUST consider any sessions associated with the connection as also having failed. When either endpoint notices such a failure, it MAY attempt to re-create any such sessions. If it chooses to do so, it MUST use a new SDP exchange, for example, in a SIP re-INVITE. If a replacement session is successfully created, endpoints MAY attempt to resend any content for which delivery on the original session could not be confirmed. If it does this, the Message-ID values for the resent messages MUST match those used in the initial attempts. If the receiving endpoint receives more than one message with the same Message-ID, it SHOULD assume that the messages are duplicates. The specific action that an endpoint takes when it receives a duplicate message is a matter of local policy, except that it SHOULD NOT present the duplicate messages to the user without warning of the duplication. Note that acknowledgments as needed based on the Failure-Report and Success-Report settings are still necessary even for requests containing duplicate content.
Если соединение прерывается по какой-либо причине, конечная точка MSRP ДОЛЖНА считать любые сеансы, связанные с этим соединением, также завершившимися неудачно. Когда любая из конечных точек замечает такой сбой, она МОЖЕТ попытаться восстановить такие сеансы. Если она решает это сделать, она ДОЛЖНА использовать новый обмен SDP, например в повторном INVITE (re-INVITE) SIP. Если замещающий сеанс успешно создан, конечные точки МОГУТ попытаться повторно отправить любое содержимое, доставку которого в исходном сеансе подтвердить не удалось. Если они это делают, значения Message-ID повторно отправляемых сообщений ДОЛЖНЫ совпадать с использованными в первоначальных попытках. Если принимающая конечная точка получает более одного сообщения с одинаковым Message-ID, она ДОЛЖНА считать эти сообщения дубликатами. Конкретное действие, которое конечная точка предпринимает при получении дублирующего сообщения, определяется локальной политикой, за исключением того, что она НЕ ДОЛЖНА показывать пользователю дублирующие сообщения без предупреждения о дублировании. Обратите внимание, что подтверждения, требуемые согласно настройкам Failure-Report и Success-Report, всё равно необходимы даже для запросов, содержащих дублирующееся содержимое.
When endpoints create a new session in this fashion, the chunks for a given logical message MAY be split across the sessions. However, endpoints SHOULD NOT split chunks between sessions under non-failure circumstances.
Когда конечные точки создают новый сеанс таким образом, фрагменты данного логического сообщения МОГУТ быть распределены между сеансами. Однако конечные точки НЕ ДОЛЖНЫ разделять фрагменты между сеансами в условиях отсутствия сбоя.
If an endpoint attempts to re-create a failed session in this manner, it MUST NOT assume that the MSRP URIs in the SDP will be the same as the old ones.
Если конечная точка пытается восстановить неудачный сеанс таким образом, она НЕ ДОЛЖНА предполагать, что URI MSRP в SDP будут такими же, как старые.
A connection SHOULD NOT be closed while there are sessions associated with it.
Соединение НЕ ДОЛЖНО закрываться до тех пор, пока с ним связаны какие-либо сеансы.
6. MSRP URIs
6. URI MSRP
URIs using the "msrp" and "msrps" schemes are used to identify a session of instant messages at a particular MSRP device, as well as to identify an MSRP relay in general. This document describes the former usage; the latter usage is described in the MSRP relay specification [23]. MSRP URIs that identify sessions are ephemeral; an MSRP device will use a different MSRP URI for each distinct session. An MSRP URI that identifies a session has no meaning outside the scope of that session.
URI, использующие схемы "msrp" и "msrps", применяются для идентификации сеанса мгновенных сообщений на конкретном устройстве MSRP, а также для идентификации ретранслятора MSRP в целом. Настоящий документ описывает первое использование; второе описано в спецификации ретранслятора MSRP [23]. URI MSRP, идентифицирующие сеансы, являются эфемерными; устройство MSRP будет использовать другой URI MSRP для каждого отдельного сеанса. URI MSRP, идентифицирующий сеанс, не имеет смысла вне области этого сеанса.
An MSRP URI follows a subset of the URI syntax in Appendix A of RFC 3986 [10], with a scheme of "msrp" or "msrps". The syntax is described in Section 9.
URI MSRP следует подмножеству синтаксиса URI из приложения A RFC 3986 [10] со схемой "msrp" или "msrps". Синтаксис описан в разделе 9.
MSRP URIs are primarily expected to be generated and exchanged between systems, and are not intended for "human consumption". Therefore, they are encoded entirely in US-ASCII.
URI MSRP в первую очередь предполагаются для генерации и обмена между системами и не предназначены для "человеческого потребления". Поэтому они целиком кодируются в US-ASCII.
The constructions for "authority", "userinfo", and "unreserved" are detailed in RFC 3986 [10]. URIs designating MSRP over TCP MUST include the "tcp" transport parameter. Since this document only specifies MSRP over TCP, all MSRP URIs herein use the "tcp" transport parameter. Documents that provide bindings on other transports should define respective parameters for those transports.
Конструкции "authority", "userinfo" и "unreserved" подробно описаны в RFC 3986 [10]. URI, обозначающие MSRP поверх TCP, ДОЛЖНЫ включать транспортный параметр "tcp". Поскольку настоящий документ определяет MSRP только поверх TCP, все URI MSRP в нём используют транспортный параметр "tcp". Документы, обеспечивающие привязки к другим транспортам, должны определять соответствующие параметры для этих транспортов.
The MSRP URI authority field identifies a participant in a particular MSRP session. If the authority field contains a numeric IP address, it MUST also contain a port. The session-id part identifies a particular session of the participant. The absence of the session-id part indicates a reference to an MSRP host device, but does not refer to a particular session at that device. A particular value of session-id is only meaningful in the context of the associated authority; thus, the authority component can be thought of as identifying the "authority" governing a namespace for the session-id.
Поле authority URI MSRP идентифицирует участника конкретного сеанса MSRP. Если поле authority содержит числовой IP-адрес, оно ДОЛЖНО также содержать порт. Часть session-id идентифицирует конкретный сеанс участника. Отсутствие части session-id указывает на ссылку на хост-устройство MSRP, но не относится к конкретному сеансу на этом устройстве. Конкретное значение session-id имеет смысл только в контексте связанного authority; таким образом, компонент authority можно рассматривать как идентифицирующий "полномочие", управляющее пространством имён для session-id.
A scheme of "msrps" indicates that the underlying connection MUST be protected with TLS.
Схема "msrps" указывает, что нижележащее соединение ДОЛЖНО быть защищено с помощью TLS.
MSRP has an IANA-registered recommended port defined in Section 15.4. This value is not a default, as the URI negotiation process described herein will always include explicit port numbers. However, the URIs SHOULD be configured so that the recommended port is used whenever appropriate. This makes life easier for network administrators who need to manage firewall policy for MSRP.
MSRP имеет рекомендованный порт, зарегистрированный в IANA, определённый в разделе 15.4. Это значение не является значением по умолчанию, поскольку описанный в настоящем документе процесс согласования URI всегда будет включать явные номера портов. Однако URI ДОЛЖНЫ быть настроены так, чтобы рекомендованный порт использовался, когда это уместно. Это облегчает жизнь сетевым администраторам, которым нужно управлять политикой межсетевого экрана для MSRP.
The authority component will typically not contain a userinfo component, but MAY do so to indicate a user account for which the session is valid. Note that this is not the same thing as identifying the session itself. A userinfo part MUST NOT contain password information.
Компонент authority обычно не будет содержать компонент userinfo, но МОЖЕТ содержать его для указания учётной записи пользователя, для которой действителен сеанс. Обратите внимание, что это не то же самое, что идентификация самого сеанса. Часть userinfo НЕ ДОЛЖНА содержать информацию о пароле.
The following is an example of a typical MSRP URI: msrp://host.example.com:8493/asfd34;tcp
Следующее является примером типичного URI MSRP: msrp://host.example.com:8493/asfd34;tcp

6.2. Resolving MSRP Host Device
6.2. Разрешение хост-устройства MSRP
An MSRP host device is identified by the authority component of an MSRP URI.
Хост-устройство MSRP идентифицируется компонентом authority URI MSRP.
If the authority component contains a numeric IP address and port, they MUST be used as listed.
Если компонент authority содержит числовой IP-адрес и порт, они ДОЛЖНЫ использоваться так, как указано.
If the authority component contains a host name and a port, the connecting device MUST determine a host address by doing an A or AAAA DNS query and use the port as listed.
Если компонент authority содержит имя хоста и порт, подключающееся устройство ДОЛЖНО определить адрес хоста, выполнив DNS-запрос A или AAAA, и использовать порт так, как указано.
If a connection attempt fails, the device SHOULD attempt to connect to the addresses returned in any additional A or AAAA records, in the order the records were presented.
Если попытка соединения завершается неудачей, устройство ДОЛЖНО попытаться подключиться к адресам, возвращённым в любых дополнительных записях A или AAAA, в порядке представления записей.
This process assumes that the connection port is always known prior to resolution. This is always true for the MSRP URI uses described in this document, that is, URIs exchanged in the SDP offer and answer. The introduction of relays creates situations where this is not the case. For example, when a user configures her client to use a relay, it is desirable that the relay's MSRP URI is easy to remember and communicate to humans. Often this type of MSRP will omit the port number. Therefore, the relay specification [23] describes additional steps to resolve the port number.
Этот процесс предполагает, что порт соединения всегда известен до разрешения. Например, когда пользователь настраивает свой клиент на использование ретранслятора, желательно, чтобы URI MSRP ретранслятора было легко запомнить и сообщить людям. Часто в таком URI MSRP номер порта опускается. Поэтому спецификация ретранслятора [23] описывает дополнительные шаги для разрешения номера порта.
MSRP devices MAY use other methods for discovering other such devices, when appropriate. For example, MSRP endpoints may use other mechanisms to discover relays, which are beyond the scope of this document.
Устройства MSRP МОГУТ использовать другие методы для обнаружения других таких устройств, когда это уместно. Например, конечные точки MSRP могут использовать другие механизмы для обнаружения ретрансляторов, что выходит за рамки настоящего документа.
7. Method-Specific Behavior
7. Поведение, зависящее от метода
7.1. Constructing Requests
7.1. Построение запросов
To form a new request, the sender creates a transaction identifier and uses this and the method name to create an MSRP request start line. The transaction identifier MUST NOT collide with that of other transactions that exist at the same time. Therefore, it MUST contain at least 64 bits of randomness.
Чтобы сформировать новый запрос, отправитель создаёт идентификатор транзакции и использует его и имя метода для создания стартовой строки запроса MSRP. Идентификатор транзакции НЕ ДОЛЖЕН совпадать с идентификатором других транзакций, существующих одновременно. Поэтому он ДОЛЖЕН содержать не менее 64 бит случайности.
Next, the sender places the target path in a To-Path header field, and the sender's URI in a From-Path header field. If multiple URIs are present in the To-Path, the leftmost is the first URI visited; the rightmost URI is the last URI visited. The processing then becomes method specific. Additional method-specific header fields are added as described in the following sections.
Затем отправитель помещает целевой путь в поле заголовка To-Path, а свой URI — в поле заголовка From-Path. Если в To-Path присутствует несколько URI, самый левый — это первый посещаемый URI; самый правый URI — последний посещаемый URI. Затем обработка становится зависящей от метода. Дополнительные поля заголовков, зависящие от метода, добавляются, как описано в следующих разделах.
After any method-specific header fields are added, processing continues to handle a body, if present. If the request has a body, it MUST contain a Content-Type header field. It may contain other MIME-specific header fields. The Content-Type header field MUST be the last field in the message header section. The body MUST be separated from the header fields with an extra CRLF.
После добавления зависящих от метода полей заголовков обработка продолжается обработкой тела, если оно присутствует. Если запрос имеет тело, он ДОЛЖЕН содержать поле заголовка Content-Type. Он может содержать другие поля заголовков, специфичные для MIME. Поле заголовка Content-Type ДОЛЖНО быть последним полем в разделе заголовков сообщения. Тело ДОЛЖНО быть отделено от полей заголовков дополнительным CRLF.
Non-SEND requests are not intended to carry message content, and are therefore not interruptible. Non-SEND request bodies MUST NOT be larger than 10240 octets.
Запросы, отличные от SEND, не предназначены для переноса содержимого сообщений и поэтому не допускают прерывания. Тела запросов, отличных от SEND, НЕ ДОЛЖНЫ быть больше 10240 октетов.
Although this document does not discuss any particular usage of bodies in non-SEND requests, they may be useful in the future for carrying security or identity information, information about a message in progress, etc. The 10K size limit was chosen to be large enough for most of such applications, but small enough to avoid the fairness issues caused by sending arbitrarily large content in non-interruptible method bodies.
Хотя настоящий документ не обсуждает какое-либо конкретное использование тел в запросах, отличных от SEND, они могут быть полезны в будущем для переноса информации о безопасности или идентичности, информации о сообщении в процессе передачи и т. п. Предел в 10 КБ выбран достаточно большим для большинства таких приложений, но достаточно малым, чтобы избежать проблем справедливости, вызванных отправкой произвольно большого содержимого в телах методов, не допускающих прерывания.
A request with no body MUST NOT include a Content-Type or any other MIME-specific header fields. A request without a body MUST contain an end-line after the final header field. No extra CRLF will be present between the header section and the end-line.
Запрос без тела НЕ ДОЛЖЕН включать Content-Type или любые другие поля заголовков, специфичные для MIME. Запрос без тела ДОЛЖЕН содержать конечную строку после последнего поля заголовка. Между разделом заголовков и конечной строкой не будет дополнительного CRLF.
Requests with no bodies are useful when a client wishes to send "traffic", but does not wish to send content to be rendered to the peer user. For example, the active endpoint sends a SEND request immediately upon establishing a connection. If it has nothing to say at the moment, it can send a request with no body. Bodiless requests may also be used in certain applications to keep Network Address Translation (NAT) bindings alive, etc. Bodiless requests are distinct from requests with empty bodies. A request with an empty body will have a Content-Type header field value and will generally be rendered to the recipient according to the rules for that type.
Запросы без тела полезны, когда клиент желает отправить "трафик", но не желает отправлять содержимое для отображения пользователю-пиру. Например, активная конечная точка отправляет запрос SEND сразу после установления соединения. Если ей нечего сказать в данный момент, она может отправить запрос без тела. Запросы без тела также могут использоваться в некоторых приложениях для поддержания привязок преобразования сетевых адресов (NAT) и т. п. Запросы без тела отличаются от запросов с пустым телом. Запрос с пустым телом будет иметь значение поля заголовка Content-Type и обычно будет отображаться получателю согласно правилам для этого типа.
The end-line that terminates the request MUST be composed of seven "-" (minus sign) characters, the transaction ID as used in the start line, and a flag character. If a body is present, the end-line MUST be preceded by a CRLF that is not part of the body. If the chunk represents the data that forms the end of the complete message, the flag value MUST be a "$". If the sender is aborting an incomplete message, and intends to send no further chunks in that message, the flag MUST be a "#". Otherwise, the flag MUST be a "+".
Конечная строка, завершающая запрос, ДОЛЖНА состоять из семи символов "-" (знак минус), идентификатора транзакции, как в стартовой строке, и символа-флага. Если тело присутствует, конечной строке ДОЛЖЕН предшествовать CRLF, не являющийся частью тела. Если фрагмент представляет данные, образующие конец полного сообщения, значение флага ДОЛЖНО быть "$". Если отправитель прерывает неполное сообщение и намеревается не отправлять дальнейшие фрагменты в этом сообщении, флаг ДОЛЖЕН быть "#". В противном случае флаг ДОЛЖЕН быть "+".
If the request contains a body, the sender MUST ensure that the end- line (seven hyphens, the transaction identifier, and a continuation flag) is not present in the body. If the end-line is present in the body, the sender MUST choose a new transaction identifier that is not present in the body, and add a CRLF if needed, and the end-line, including the "$", "#", or "+" character.
Если запрос содержит тело, отправитель ДОЛЖЕН убедиться, что конечная строка (семь дефисов, идентификатор транзакции и флаг продолжения) отсутствует в теле. Если конечная строка присутствует в теле, отправитель ДОЛЖЕН выбрать новый идентификатор транзакции, отсутствующий в теле, и при необходимости добавить CRLF, а также конечную строку, включая символ "$", "#" или "+".
Some implementations may choose to scan for the closing sequence as they send the body, and if it is encountered, simply interrupt the chunk at that point and start a new transaction with a different transaction identifier to carry the rest of the body. Other implementations may choose to scan the data and ensure that the body does not contain the transaction identifier before they start sending the transaction.
Некоторые реализации могут сканировать закрывающую последовательность по мере отправки тела и, если она встречается, просто прервать фрагмент в этот момент и начать новую транзакцию с другим идентификатором транзакции для переноса остальной части тела. Другие реализации могут сканировать данные и гарантировать, что тело не содержит идентификатор транзакции, до начала отправки транзакции.
Once a request is ready for delivery, the sender follows the connection management (Section 5.4) rules to forward the request over an existing open connection or create a new connection.
Когда запрос готов к доставке, отправитель следует правилам управления соединениями (раздел 5.4), чтобы переслать запрос по существующему открытому соединению или создать новое соединение.
7.1.1. Sending SEND Requests
7.1.1. Отправка запросов SEND
When an endpoint has a message to deliver, it first generates a new Message-ID. The value MUST be highly unlikely to be repeated by another endpoint instance, or by the same instance in the future. If necessary, the endpoint breaks the message into chunks. It then generates a SEND request for each chunk, following the procedures for constructing requests (Section 7.1).
Когда конечной точке нужно доставить сообщение, она сначала генерирует новый Message-ID. Значение ДОЛЖНО быть крайне маловероятным для повторения другим экземпляром конечной точки или тем же экземпляром в будущем. При необходимости конечная точка разбивает сообщение на фрагменты. Затем она генерирует запрос SEND для каждого фрагмента, следуя процедурам построения запросов (раздел 7.1).
The Message-ID header field provides a unique message identifier that refers to a particular version of a particular message. The term "Message" in this context refers to a unit of content that the sender wishes to convey to the recipient. While such a message may be broken into chunks, the Message-ID refers to the entire message, not a chunk of the message. The uniqueness of the message identifier is ensured by the host that generates it. This message identifier is intended to be machine readable and not necessarily meaningful to humans. A message identifier pertains to exactly one version of a particular message; subsequent revisions to the message each receive new message identifiers. Endpoints can ensure sufficient uniqueness in any number of ways, the selection of which is an implementation choice.
Поле заголовка Message-ID предоставляет уникальный идентификатор сообщения, который относится к конкретной версии конкретного сообщения. Термин "сообщение" в этом контексте относится к единице содержимого, которую отправитель желает передать получателю. Хотя такое сообщение может быть разбито на фрагменты, Message-ID относится ко всему сообщению, а не к фрагменту сообщения. Уникальность идентификатора сообщения обеспечивается хостом, который его генерирует. Этот идентификатор сообщения предназначен для машинного чтения и не обязательно должен быть осмысленным для людей. Идентификатор сообщения относится ровно к одной версии конкретного сообщения; последующие редакции сообщения каждая получает новые идентификаторы сообщений. Конечные точки могут обеспечить достаточную уникальность любым числом способов, выбор которых является решением реализации.
For example, an endpoint could concatenate an instance identifier such as a MAC address, its idea of the number of seconds since the epoch, a process ID, and a monotonically increasing 16-bit integer, all base-64 encoded. Alternately, an endpoint without an on-board clock could simply use a 64-bit random number.
Например, конечная точка может объединить идентификатор экземпляра, такой как MAC-адрес, своё представление о числе секунд с начала эпохи, идентификатор процесса и монотонно возрастающее 16-битное целое, закодировав всё это в base64. В качестве альтернативы конечная точка без встроенных часов может просто использовать 64-битное случайное число.
Each chunk of a message MUST contain a Message-ID header field containing the Message-ID. If the sender wishes non-default status reporting, it MUST insert a Failure-Report and/or Success-Report header field with an appropriate value. All chunks of the same message MUST use the same Failure-Report and Success-Report values in their SEND requests.
Каждый фрагмент сообщения ДОЛЖЕН содержать поле заголовка Message-ID, содержащее Message-ID. Если отправитель желает отчётность о состоянии, отличную от стандартной, он ДОЛЖЕН вставить поле заголовка Failure-Report и/или Success-Report с соответствующим значением. Все фрагменты одного и того же сообщения ДОЛЖНЫ использовать одинаковые значения Failure-Report и Success-Report в своих запросах SEND.
If success reports are requested, i.e., the value of the Success- Report header field is "yes", the sending device MAY wish to run a timer of some value that makes sense for its application and take action if a success report is not received in this time. There is no universal value for this timer. For many IM applications, it may be 2 minutes while for some trading systems it may be under a second. Regardless of whether such a timer is used, if the success report has not been received by the time the session is ended, the device SHOULD inform the user.
Если запрошены отчёты об успехе, то есть значение поля заголовка Success-Report равно "yes", отправляющему устройству МОЖЕТ потребоваться запустить таймер с некоторым значением, имеющим смысл для его приложения, и предпринять действия, если отчёт об успехе не получен за это время. Универсального значения для этого таймера нет. Для многих приложений IM это может быть 2 минуты, а для некоторых торговых систем — менее секунды. Независимо от того, используется ли такой таймер, если отчёт об успехе не получен к моменту завершения сеанса, устройство ДОЛЖНО проинформировать пользователя.
If the value of "Failure-Report" is set to "yes", then the sender of the request runs a timer. If a 200 response to the transaction is not received within 30 seconds from the time the last byte of the transaction is sent, or submitted to the operating system for sending, the element MUST inform the user that the request probably failed. If the value is set to "partial", then the element sending the transaction does not have to run a timer, but MUST inform the user if it receives a non-recoverable error response to the transaction. Regardless of the Failure-Report value, there is no requirement to wait for a response prior to sending the next request.
Если значение "Failure-Report" установлено в "yes", то отправитель запроса запускает таймер. Если ответ 200 на транзакцию не получен в течение 30 секунд с момента отправки последнего байта транзакции или передачи его операционной системе для отправки, элемент ДОЛЖЕН проинформировать пользователя о том, что запрос, вероятно, не удался. Если значение установлено в "partial", то элемент, отправляющий транзакцию, не обязан запускать таймер, но ДОЛЖЕН проинформировать пользователя, если получит невосстановимый ответ об ошибке на транзакцию. Независимо от значения Failure-Report, нет требования ждать ответа перед отправкой следующего запроса.
The treatment of timers for success reports and failure reports is intentionally inconsistent. An explicit timeout value makes sense for failure reports since such reports will usually refer to a message "chunk" that is acknowledged on a hop-by-hop basis. This is not the case for success reports, which are end-to-end and may refer to the entire message content, which can be arbitrarily large.
Обращение с таймерами для отчётов об успехе и отчётов о неудаче намеренно непоследовательно. Явное значение тайм-аута имеет смысл для отчётов о неудаче, поскольку такие отчёты обычно относятся к "фрагменту" сообщения, подтверждаемому на основе перехода к переходу. Это не так для отчётов об успехе, которые являются сквозными и могут относиться ко всему содержимому сообщения, которое может быть произвольно большим.
If no Success-Report header field is present in a SEND request, it MUST be treated the same as a Success-Report header field with a value of "no". If no Failure-Report header field is present, it MUST be treated the same as a Failure-Report header field with a value of "yes". If an MSRP endpoint receives a REPORT for a Message-ID it does not recognize, it SHOULD silently ignore the REPORT.
Если в запросе SEND отсутствует поле заголовка Success-Report, оно ДОЛЖНО обрабатываться так же, как поле заголовка Success-Report со значением "no". Если отсутствует поле заголовка Failure-Report, оно ДОЛЖНО обрабатываться так же, как поле заголовка Failure-Report со значением "yes". Если конечная точка MSRP получает REPORT для Message-ID, который она не распознаёт, она ДОЛЖНА молча игнорировать этот REPORT.
The Byte-Range header field value contains a starting value (range- start) followed by a "-", an ending value (range-end) followed by a "/", and finally the total length. The first octet in the message has a position of one, rather than a zero.
Значение поля заголовка Byte-Range содержит начальное значение (range-start), за которым следует "-", конечное значение (range-end), за которым следует "/", и, наконец, общую длину. Первый октет в сообщении имеет позицию один, а не ноль.
The first chunk of the message SHOULD, and all subsequent chunks MUST, include a Byte-Range header field. The range-start field MUST indicate the position of the first byte in the body in the overall message (for the first chunk this field will have a value of one). The range-end field SHOULD indicate the position of the last byte in the body, if known. It MUST take the value of "*" if the position is unknown, or if the request needs to be interruptible. The total field SHOULD contain the total size of the message, if known. The total field MAY contain a "*" if the total size of the message is not known in advance. The sender MUST send all chunks in Byte-Range order. (However, the receiver cannot assume that the requests will be delivered in order, as intervening relays may have changed the order.)
Первый фрагмент сообщения ДОЛЖЕН, а все последующие фрагменты ОБЯЗАНЫ включать поле заголовка Byte-Range. Поле range-start ДОЛЖНО указывать позицию первого байта в теле в общем сообщении (для первого фрагмента это поле будет иметь значение один). Поле range-end ДОЛЖНО указывать позицию последнего байта в теле, если она известна. Оно ДОЛЖНО принимать значение "*", если позиция неизвестна или если запрос должен допускать прерывание. Поле total ДОЛЖНО содержать общий размер сообщения, если он известен. Поле total МОЖЕТ содержать "*", если общий размер сообщения заранее неизвестен. Отправитель ДОЛЖЕН отправлять все фрагменты в порядке Byte-Range. (Однако получатель не может предполагать, что запросы будут доставлены по порядку, поскольку промежуточные ретрансляторы могли изменить порядок.)
There are some circumstances where an endpoint may choose to send an empty SEND request. For the sake of consistency, a Byte-Range header field referring to nonexistent or zero-length content MUST still have a range-start value of 1. For example, "1-0/0".
Есть некоторые обстоятельства, когда конечная точка может выбрать отправку пустого запроса SEND. Ради согласованности поле заголовка Byte-Range, относящееся к несуществующему содержимому или содержимому нулевой длины, ДОЛЖНО всё же иметь значение range-start, равное 1. Например, "1-0/0".
To ensure fairness over a connection, senders MUST NOT send chunks with a body larger than 2048 octets unless they are prepared to interrupt them (meaning that any chunk with a body of greater than 2048 octets will have a "*" character in the range-end field). A sender can use one of the following two strategies to satisfy this requirement. The sender is STRONGLY RECOMMENDED to send messages larger than 2048 octets using as few chunks as possible, interrupting chunks (at least 2048 octets long) only when other traffic is waiting to use the same connection. Alternatively, the sender MAY simply send chunks in 2048-octet increments until the final chunk. Note that the former strategy results in markedly more efficient use of the connection. All MSRP nodes MUST be able to receive chunks of any size from zero octets to the maximum number of octets they can receive for a complete message. Senders SHOULD NOT break messages into chunks smaller than 2048 octets, except for the final chunk of a complete message.
Чтобы обеспечить справедливость при использовании соединения, отправители НЕ ДОЛЖНЫ отправлять фрагменты с телом более 2048 октетов, если они не готовы их прервать (это означает, что любой фрагмент с телом более 2048 октетов будет иметь символ "*" в поле range-end). Отправитель может использовать одну из следующих двух стратегий для выполнения этого требования. Отправителю НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ отправлять сообщения размером более 2048 октетов, используя как можно меньше фрагментов, прерывая фрагменты (длиной не менее 2048 октетов) только тогда, когда другой трафик ожидает использования того же соединения. В качестве альтернативы отправитель МОЖЕТ просто отправлять фрагменты шагами по 2048 октетов до последнего фрагмента. Обратите внимание, что первая стратегия даёт заметно более эффективное использование соединения. Все узлы MSRP ДОЛЖНЫ быть способны принимать фрагменты любого размера от нуля октетов до максимального числа октетов, которое они могут принять для полного сообщения. Отправителям НЕ СЛЕДУЕТ разбивать сообщения на фрагменты меньше 2048 октетов, кроме последнего фрагмента полного сообщения.
A SEND request is interrupted while a body is in the process of being written to the connection by simply noting how much of the message has already been written to the connection, then writing out the end- line to end the chunk. It can then be resumed in a another chunk with the same Message-ID and a Byte-Range header field range start field containing the position of the first byte after the interruption occurred.
Запрос SEND прерывается в процессе записи тела в соединение путём простой фиксации того, сколько сообщения уже было записано в соединение, а затем записи конечной строки для завершения фрагмента. Затем его можно возобновить в другом фрагменте с тем же Message-ID и полем range-start заголовка Byte-Range, содержащим позицию первого байта после места прерывания.
SEND requests larger than 2048 octets MUST be interrupted if the sender needs to send pending responses or REPORT requests. If multiple SEND requests from different sessions are concurrently being sent over the same connection, the device SHOULD implement some scheme to alternate between them such that each concurrent request gets a chance to send some fair portion of data at regular intervals suitable to the application.
Запросы SEND размером более 2048 октетов ДОЛЖНЫ прерываться, если отправителю нужно отправить ожидающие ответы или запросы REPORT. Если несколько запросов SEND из разных сеансов одновременно отправляются по одному соединению, устройство ДОЛЖНО реализовать некоторую схему чередования между ними, чтобы каждый одновременный запрос получал возможность отправить справедливую порцию данных через регулярные интервалы, подходящие для приложения.
The sender MUST NOT assume that a message is received by the peer with the same chunk allocation with which it was sent. An intervening relay could possibly break SEND requests into smaller chunks, or aggregate multiple chunks into larger ones.
Отправитель НЕ ДОЛЖЕН предполагать, что сообщение получено пиром с тем же распределением фрагментов, с которым оно было отправлено. Промежуточный ретранслятор может разбить запросы SEND на меньшие фрагменты или объединить несколько фрагментов в более крупные.
The default disposition of messages is to be rendered to the user. If the sender wants a different disposition, it MAY insert a Content- Disposition [9] header field. Values MAY include any from RFC 2183 [9] or the IANA registry it defines. Since MSRP can carry unencoded binary payloads, transfer encoding is always "binary", and transfer- encoding parameters MUST NOT be present.
Стандартное размещение сообщений — отображение пользователю. Если отправитель хочет иного размещения, он МОЖЕТ вставить поле заголовка Content-Disposition [9]. Значения МОГУТ включать любые из RFC 2183 [9] или реестра IANA, который он определяет. Поскольку MSRP может переносить незакодированные двоичные полезные нагрузки, транспортное кодирование всегда "binary", и параметры транспортного кодирования НЕ ДОЛЖНЫ присутствовать.
7.1.2. Sending REPORT Requests
7.1.2. Отправка запросов REPORT
REPORT requests are similar to SEND requests, except that report requests MUST NOT include Success-Report or Failure-Report header fields, and MUST contain a Status header field. REPORT requests MUST contain the Message-ID header field from the original SEND request.
Запросы REPORT похожи на запросы SEND, за исключением того, что запросы REPORT НЕ ДОЛЖНЫ включать поля заголовков Success-Report или Failure-Report и ДОЛЖНЫ содержать поле заголовка Status. Запросы REPORT ДОЛЖНЫ содержать поле заголовка Message-ID из исходного запроса SEND.
If an MSRP element receives a REPORT for a Message-ID it does not recognize, it SHOULD silently ignore the REPORT.
Если элемент MSRP получает REPORT для Message-ID, который он не распознаёт, он ДОЛЖЕН молча игнорировать этот REPORT.
An MSRP endpoint MUST be able to generate success REPORT requests.
Конечная точка MSRP ДОЛЖНА быть способна генерировать запросы REPORT об успехе.
REPORT requests will normally not include a body, as the REPORT request header fields can carry sufficient information in most cases. However, REPORT requests MAY include a body containing additional information about the status of the associated SEND request. Such a body is informational only, and the sender of the REPORT request SHOULD NOT assume that the recipient pays any attention to the body. REPORT requests are not interruptible.
Запросы REPORT обычно не включают тело, поскольку поля заголовков запроса REPORT в большинстве случаев могут нести достаточно информации. Однако запросы REPORT МОГУТ включать тело, содержащее дополнительную информацию о состоянии связанного запроса SEND. Такое тело носит только информационный характер, и отправитель запроса REPORT НЕ ДОЛЖЕН предполагать, что получатель обращает на тело какое-либо внимание. Запросы REPORT не допускают прерывания.
Success-Report and Failure-Report header fields MUST NOT be present in REPORT requests. MSRP nodes MUST NOT send REPORT requests in response to REPORT requests. MSRP nodes MUST NOT send MSRP responses to REPORT requests.
Поля заголовков Success-Report и Failure-Report НЕ ДОЛЖНЫ присутствовать в запросах REPORT. Узлы MSRP НЕ ДОЛЖНЫ отправлять запросы REPORT в ответ на запросы REPORT. Узлы MSRP НЕ ДОЛЖНЫ отправлять ответы MSRP на запросы REPORT.
Endpoints SHOULD NOT send REPORT requests if they have reason to believe the request will not be delivered. For example, they SHOULD NOT send a REPORT request for a session that is no longer valid.
Конечным точкам НЕ СЛЕДУЕТ отправлять запросы REPORT, если у них есть основания полагать, что запрос не будет доставлен. Например, им НЕ СЛЕДУЕТ отправлять запрос REPORT для сеанса, который больше не действителен.
7.1.3. Generating Success Reports
7.1.3. Генерация отчётов об успехе
When an endpoint receives a message in one or more chunks that contain a Success-Report value of "yes", it MUST send a success report or reports covering all bytes that are received successfully. The success reports are sent in the form of REPORT requests, following the normal procedures (Section 7.1), with a few additional requirements.
Когда конечная точка получает сообщение в одном или нескольких фрагментах со значением Success-Report "yes", она ДОЛЖНА отправить отчёт или отчёты об успехе, охватывающие все байты, полученные успешно. Отчёты об успехе отправляются в форме запросов REPORT, следуя обычным процедурам (раздел 7.1), с несколькими дополнительными требованиями.
The receiver MAY wait until it receives the last chunk of a message, and send a success report that covers the complete message. Alternately, it MAY generate incremental success REPORTs as the chunks are received. These can be sent periodically and cover all the bytes that have been received so far, or they can be sent after a chunk arrives and cover just the part from that chunk.
Получатель МОЖЕТ ждать, пока не получит последний фрагмент сообщения, и отправить отчёт об успехе, охватывающий всё сообщение. В качестве альтернативы он МОЖЕТ генерировать инкрементные REPORT об успехе по мере получения фрагментов. Они могут отправляться периодически и охватывать все байты, полученные к этому моменту, или могут отправляться после прихода фрагмента и охватывать только часть из этого фрагмента.
It is helpful to think of a success REPORT as reporting on a particular range of bytes, rather than on a particular chunk sent by a client. The sending client cannot depend on the Byte-Range header field in a given success report matching that of a particular SEND request. For example, an intervening MSRP relay may break chunks into smaller chunks, or aggregate multiple chunks into larger ones. A side effect of this is, even if no relay is used, the receiving client may report on byte ranges that do not exactly match those in the original chunks sent by the sender. It can wait until all bytes in a message are received and report on the whole, it can report as it receives each chunk, or it can report on any other received range. Reporting on ranges smaller than the entire message contents allows certain improved user experiences for the sender. For example, a sending client could display incremental status information showing which ranges of bytes have been acknowledged by the receiver.
Полезно рассматривать REPORT об успехе как отчёт о конкретном диапазоне байтов, а не о конкретном фрагменте, отправленном клиентом. Отправляющий клиент не может рассчитывать на то, что поле заголовка Byte-Range в данном отчёте об успехе будет совпадать с таковым в конкретном запросе SEND. Например, промежуточный ретранслятор MSRP может разбить фрагменты на меньшие фрагменты или объединить несколько фрагментов в более крупные. Побочным эффектом этого является то, что даже если ретранслятор не используется, принимающий клиент может сообщать о диапазонах байтов, которые не точно соответствуют диапазонам в исходных фрагментах, отправленных отправителем. Он может ждать, пока все байты в сообщении будут получены, и сообщить обо всём целиком, может сообщать по мере получения каждого фрагмента или может сообщать о любом другом полученном диапазоне. Отчётность о диапазонах меньших, чем всё содержимое сообщения, позволяет обеспечить определённые улучшенные возможности взаимодействия с пользователем для отправителя. Например, отправляющий клиент мог бы отображать инкрементную информацию о состоянии, показывающую, какие диапазоны байтов были подтверждены получателем.
However, the choice on whether to report incrementally is entirely up to the receiving client. There is no mechanism for the sender to assert its desire to receive incremental reports or not. Since the presence of a relay can cause the receiver to see a very different chunk allocation than the sender, such a mechanism would be of questionable value.
Однако решение о том, сообщать ли инкрементально, целиком остаётся за принимающим клиентом. Механизма, позволяющего отправителю заявить о своём желании получать инкрементальные отчёты (или не получать их), нет. Поскольку наличие ретранслятора может привести к тому, что получатель увидит совсем иное распределение фрагментов, чем отправитель, такой механизм был бы сомнительной ценности.
When generating a REPORT request, the endpoint inserts a To-Path header field containing the From-Path value from the original request, and a From-Path header field containing the URI identifying itself in the session. The endpoint then inserts a Status header field with a namespace of "000", a status-code of "200", and an implementation-defined comment phrase. It also inserts a Message-ID header field containing the value from the original request.
Генерируя запрос REPORT, конечная точка вставляет поле заголовка To-Path, содержащее значение From-Path из исходного запроса, и поле заголовка From-Path, содержащее URI, идентифицирующий её в сеансе. Затем конечная точка вставляет поле заголовка Status с пространством имён "000", кодом состояния "200" и определяемой реализацией фразой-комментарием. Она также вставляет поле заголовка Message-ID, содержащее значение из исходного запроса.
The namespace field denotes the context of the status-code field. The namespace value of "000" means the status-code should be interpreted in the same way as the matching MSRP transaction response code. If a future specification uses the status-code field for some other purpose, it MUST define a new namespace field value.
Поле пространства имён обозначает контекст поля status-code. Значение пространства имён "000" означает, что поле status-code следует интерпретировать так же, как соответствующий код ответа транзакции MSRP. Если будущая спецификация использует поле status-code для какой-либо другой цели, она ДОЛЖНА определить новое значение поля пространства имён.
The endpoint MUST NOT send a success report for a SEND request that either contained no Success-Report header field or contained such a field with a value of "no". That is, if no Success-Report header field is present, it is treated identically to one with a value of "no".
Конечная точка НЕ ДОЛЖНА отправлять отчёт об успехе для запроса SEND, который либо не содержал поля заголовка Success-Report, либо содержал такое поле со значением "no". То есть, если поле заголовка Success-Report отсутствует, оно трактуется идентично полю со значением "no".
7.1.4. Generating Failure Reports
7.1.4. Генерация отчётов о неудаче
If an MSRP endpoint receives a SEND request that it cannot process for some reason, and the Failure-Report header field either was not present in the original request or had a value of "yes", it SHOULD simply include the appropriate error code in the transaction response. However, there may be situations where the error cannot be determined quickly, such as when the endpoint is a gateway that waits for a downstream network to indicate an error. In this situation, it MAY send a 200 OK response to the request, and then send a failure REPORT request when the error is detected.
Если конечная точка MSRP получает запрос SEND, который она не может обработать по какой-либо причине, и поле заголовка Failure-Report либо отсутствовало в исходном запросе, либо имело значение "yes", она ДОЛЖНА просто включить соответствующий код ошибки в ответ транзакции. Однако могут быть ситуации, когда ошибку нельзя определить быстро, например когда конечная точка является шлюзом, ожидающим, пока нижестоящая сеть укажет на ошибку. В этой ситуации она МОЖЕТ отправить ответ 200 OK на запрос, а затем, когда ошибка обнаружена, отправить запрос REPORT о неудаче.
If the endpoint receives a SEND request with a Failure-Report header field value of "no", then it MUST NOT send a failure REPORT request, and MUST NOT send a transaction response. If the value is "partial", it MUST NOT send a 200 transaction response to the request, but SHOULD send an appropriate non-200 class response if a failure occurs.
Если конечная точка получает запрос SEND со значением поля заголовка Failure-Report "no", то она НЕ ДОЛЖНА отправлять запрос REPORT о неудаче и НЕ ДОЛЖНА отправлять ответ транзакции. Если значение "partial", она НЕ ДОЛЖНА отправлять ответ транзакции 200 на запрос, но ДОЛЖНА отправить соответствующий ответ класса, отличного от 200, если происходит сбой.
As stated above, if no Failure-Report header field is present, it MUST be treated the same as a Failure-Report header field with a value of "yes". Construction of failure REPORT requests is identical to that for success REPORT requests, except the Status header field code field MUST contain the appropriate error code. Any error response code defined in this specification MAY also be used in failure reports.
Как указано выше, если поле заголовка Failure-Report отсутствует, оно ДОЛЖНО трактоваться так же, как поле заголовка Failure-Report со значением "yes". Построение запросов REPORT о неудаче идентично построению запросов REPORT об успехе, за исключением того, что поле кода в поле заголовка Status ДОЛЖНО содержать соответствующий код ошибки. Любой код ответа об ошибке, определённый в настоящей спецификации, также МОЖЕТ использоваться в отчётах о неудаче.
If a failure REPORT request is sent in response to a SEND request that contained a chunk, it MUST include a Byte-Range header field indicating the actual range being reported on. It can take the range-start and total values from the original SEND request, but MUST calculate the range-end field from the actual body data.
Если запрос REPORT о неудаче отправляется в ответ на запрос SEND, содержавший фрагмент, он ДОЛЖЕН включать поле заголовка Byte-Range, указывающее фактический диапазон, о котором сообщается. Он может взять значения range-start и total из исходного запроса SEND, но ДОЛЖЕН вычислить поле range-end на основе фактических данных тела.
This section only describes failure report generation behavior for MSRP endpoints. Relay behavior is beyond the scope of this document, and will be considered in a separate document [23]. We expect failure reports to be more commonly generated by relays than by endpoints.
Этот раздел описывает только поведение генерации отчётов о неудаче для конечных точек MSRP. Поведение ретранслятора выходит за рамки настоящего документа и будет рассмотрено в отдельном документе [23]. Мы ожидаем, что отчёты о неудаче будут чаще генерироваться ретрансляторами, чем конечными точками.
7.2. Constructing Responses
7.2. Построение ответов
If an MSRP endpoint receives a request that either contains a Failure-Report header field value of "yes" or does not contain a Failure-Report header field at all, it MUST immediately generate a response. Likewise, if an MSRP endpoint receives a request that contains a Failure-Report header field value of "partial", and the receiver is unable to process the request, it SHOULD immediately generate a response.
Если конечная точка MSRP получает запрос, который либо содержит значение поля заголовка Failure-Report "yes", либо вообще не содержит поля заголовка Failure-Report, она ДОЛЖНА немедленно сгенерировать ответ. Аналогично, если конечная точка MSRP получает запрос, содержащий значение поля заголовка Failure-Report "partial", и получатель не в состоянии обработать запрос, он ДОЛЖЕН немедленно сгенерировать ответ.
To construct the response, the endpoint first creates the response start line, inserting the appropriate response code and optionally a comment. The transaction identifier in the response start line MUST match the transaction identifier from the original request.
Чтобы построить ответ, конечная точка сначала создаёт стартовую строку ответа, вставляя соответствующий код ответа и, необязательно, комментарий. Идентификатор транзакции в стартовой строке ответа ДОЛЖЕН совпадать с идентификатором транзакции из исходного запроса.
The endpoint then inserts an appropriate To-Path header field. If the request triggering the response was a SEND request, the To-Path header field is formed by copying the first (leftmost) URI in the From-Path header field of the request. (Responses to SEND requests are returned only to the previous hop.) For responses to all other request methods, the To-Path header field contains the full path back to the original sender. This full path is generated by copying the list of URIs from the From-Path of the original request into the To- Path of the response. (Legal REPORT requests do not request responses, so this specification doesn't exercise the behavior described above; however, we expect that extensions for gateways and relays will need such behavior.)
Затем конечная точка вставляет соответствующее поле заголовка To-Path. Если запрос, вызвавший ответ, был запросом SEND, поле заголовка To-Path формируется путём копирования первого (самого левого) URI в поле заголовка From-Path запроса. (Ответы на запросы SEND возвращаются только предыдущему переходу.) Для ответов на все другие методы запроса поле заголовка To-Path содержит полный путь обратно к исходному отправителю. Этот полный путь генерируется путём копирования списка URI из From-Path исходного запроса в To-Path ответа. (Правомерные запросы REPORT не запрашивают ответов, поэтому настоящая спецификация не реализует описанное выше поведение; однако мы ожидаем, что расширения для шлюзов и ретрансляторов будут нуждаться в таком поведении.)
Finally, the endpoint inserts a From-Path header field containing the URI that identifies it in the context of the session, followed by the end-line after the last header field. Since a response is never chunked, the continuation flag in the end-line will always contain a dollar sign ("$"). The response MUST be transmitted back on the same connection on which the original request arrived.
Наконец, конечная точка вставляет поле заголовка From-Path, содержащее URI, идентифицирующий её в контексте сеанса, а после последнего поля заголовка — конечную строку. Поскольку ответ никогда не разбивается на фрагменты, флаг продолжения в конечной строке всегда будет содержать знак доллара ("$"). Ответ ДОЛЖЕН передаваться обратно по тому же соединению, по которому пришёл исходный запрос.
7.3. Receiving Requests
7.3. Получение запросов
The receiving endpoint MUST first check the URI in the To-Path to make sure the request belongs to an existing session. When the request is received, the To-Path will have exactly one URI, which MUST map to an existing session that is associated with the connection on which the request arrived. If this is not true, then the receiver MUST generate a 481 error and ignore the request. Note that if the Failure-Report header field had a value of "no", then no error report would be sent.
Принимающая конечная точка ДОЛЖНА сначала проверить URI в To-Path, чтобы убедиться, что запрос принадлежит существующему сеансу. При получении запроса To-Path будет содержать ровно один URI, который ДОЛЖЕН отображаться на существующий сеанс, связанный с соединением, по которому пришёл запрос. Если это не так, получатель ДОЛЖЕН сгенерировать ошибку 481 и игнорировать запрос. Обратите внимание: если поле заголовка Failure-Report имело значение "no", то никакой отчёт об ошибке не будет отправлен.
Further request processing by the receiver is method specific.
Дальнейшая обработка запроса получателем зависит от метода.
7.3.1. Receiving SEND Requests
7.3.1. Получение запросов SEND
When the receiving endpoint receives a SEND request, it first determines if it contains a complete message or a chunk from a larger message. If the request contains no Byte-Range header field, or contains one with a range-start value of "1", and the closing line continuation flag has a value of "$", then the request contained the entire message. Otherwise, the receiver looks at the Message-ID value to associate chunks together into the original message. The receiver forms a virtual buffer to receive the message, keeping track of which bytes have been received and which are missing. The receiver takes the data from the request and places it in the appropriate place in the buffer. The receiver SHOULD determine the actual length of each chunk by inspecting the payload itself; it is possible the body is shorter than the range-end field indicates. This can occur if the sender interrupted a SEND request unexpectedly. It is worth noting that the chunk that has a termination character of "$" defines the total length of the message.
Когда принимающая конечная точка получает запрос SEND, она сначала определяет, содержит ли он полное сообщение или фрагмент более крупного сообщения. Если запрос не содержит поля заголовка Byte-Range или содержит его со значением range-start "1", а флаг продолжения в закрывающей строке имеет значение "$", то запрос содержал всё сообщение. В противном случае получатель смотрит на значение Message-ID, чтобы объединить фрагменты в исходное сообщение. Получатель формирует виртуальный буфер для приёма сообщения, отслеживая, какие байты получены, а какие отсутствуют. Получатель берёт данные из запроса и помещает их в соответствующее место буфера. Получатель ДОЛЖЕН определять фактическую длину каждого фрагмента путём проверки самой полезной нагрузки; возможно, что тело короче, чем указывает поле range-end. Это может произойти, если отправитель неожиданно прервал запрос SEND. Стоит отметить, что фрагмент с символом завершения "$" определяет общую длину сообщения.
It is technically illegal for the sender to prematurely interrupt a request that had anything other than "*" in the last-byte position of the Byte-Range header field. But having the receiver calculate a chunk length based on actual content adds resilience in the face of sender errors.
Технически отправителю не разрешается преждевременно прерывать запрос, если в позиции последнего байта поля заголовка Byte-Range не было ничего, кроме "*". Но вычисление получателем длины фрагмента на основе фактического содержимого повышает устойчивость при ошибках отправителя.
Since this should never happen with compliant senders, this only has a "SHOULD" strength.
Поскольку при корректных отправителях этого происходить не должно, данное требование имеет лишь силу «СЛЕДУЕТ».
Receivers MUST not assume that the chunks will be delivered in order or that they will receive all the chunks with "+" flags before they receive the chunk with the "$" flag. In certain cases of connection failure, it is possible for information to be duplicated. If chunk data is received that overlaps already received data for the same message, the last chunk received SHOULD take precedence (even though this may not have been the last chunk transmitted). For example, if bytes 1 to 100 were received and a chunk arrives that contains bytes 50 to 150, this second chunk will overwrite bytes 50 to 100 of the data that had already been received. Although other schemes work, this is the easiest for the receiver and results in consistent behavior between clients.
Получатели НЕ ДОЛЖНЫ предполагать, что фрагменты будут доставлены по порядку или что они получат все фрагменты с флагами "+" до получения фрагмента с флагом "$". В некоторых случаях отказа соединения возможно дублирование информации. Если получены данные фрагмента, перекрывающиеся с уже полученными данными того же сообщения, последний полученный фрагмент ДОЛЖЕН иметь приоритет (даже если он мог быть не последним переданным фрагментом). Например, если получены байты с 1 по 100 и приходит фрагмент, содержащий байты с 50 по 150, этот второй фрагмент перезапишет байты с 50 по 100 уже полученных данных. Хотя работают и другие схемы, эта наиболее проста для получателя и обеспечивает согласованное поведение между клиентами.
There are situations in which the receiver may not be able to give precedence to the last chunk received when chunks overlap. For example, the recipient might incrementally render chunks as they arrive. If a new chunk arrives that overlaps with a previously rendered chunk, it would be too late to "take back" any conflicting data from the first chunk. Therefore, the requirement to give precedence to the most recent chunk is specified at a "SHOULD" strength. This requirement is not intended to disallow applications where this behavior does not make sense.
Есть ситуации, когда получатель может быть не в состоянии отдать приоритет последнему полученному фрагменту при перекрытии фрагментов. Например, получатель может отображать фрагменты по мере их поступления. Если приходит новый фрагмент, перекрывающийся с ранее отображённым, было бы слишком поздно "забирать обратно" конфликтующие данные из первого фрагмента. Поэтому требование отдавать приоритет самому последнему фрагменту задано с силой "SHOULD". Это требование не предназначено для запрета приложений, в которых такое поведение не имеет смысла.
The seven "-" in the end-line are used so that the receiver can search for the value "----", 32 bits at a time to find the probable location of the end-line. This allows most processors to locate the boundaries and copy the memory at the same rate that a normal memory copy could be done. This approach results in a system that is as fast as framing based on specifying the body length in the header fields of the request, but also allows for the interruption of messages.
Семь "-" в конечной строке используются для того, чтобы получатель мог искать значение "----" по 32 бита за раз, чтобы найти вероятное расположение конечной строки. Это позволяет большинству процессоров находить границы и копировать память с той же скоростью, с какой выполнялось бы обычное копирование памяти. Такой подход даёт систему, столь же быструю, как кадрирование на основе указания длины тела в полях заголовка запроса, но при этом допускает прерывание сообщений.
What is done with the body is outside the scope of MSRP and largely determined by the MIME Content-Type and Content-Disposition. The body MAY be rendered after the whole message is received or partially rendered as it is being received.
То, что делается с телом, выходит за рамки MSRP и в значительной степени определяется MIME Content-Type и Content-Disposition. Тело МОЖЕТ отображаться после получения всего сообщения или частично отображаться по мере его получения.
If the SEND request contained a Content-Type header field indicating an unsupported media-type, and the Failure-Report value is not "no", the receiver MUST generate a response with a status code of 415. All MSRP endpoints MUST be able to receive the multipart/mixed [15] and multipart/alternative [15] media-types.
Если запрос SEND содержал поле заголовка Content-Type, указывающее неподдерживаемый тип медиаданных, и значение Failure-Report не равно "no", получатель ДОЛЖЕН сгенерировать ответ с кодом состояния 415. Все конечные точки MSRP ДОЛЖНЫ быть способны принимать типы медиаданных multipart/mixed [15] и multipart/alternative [15].
If the Success-Report header field was set to "yes", the receiver must construct and send one or more success reports, as described in Section 7.1.3.
Если поле заголовка Success-Report было установлено в "yes", получатель должен сформировать и отправить один или несколько отчётов об успехе, как описано в разделе 7.1.3.
7.3.2. Receiving REPORT Requests
7.3.2. Получение запросов REPORT
When an endpoint receives a REPORT request, it correlates the report to the original SEND request using the Message-ID and the Byte-Range, if present. If it requested success reports, then it SHOULD keep enough state about each outstanding sent message so that it can correlate REPORT requests to the original messages.
Когда конечная точка получает запрос REPORT, она соотносит отчёт с исходным запросом SEND, используя Message-ID и Byte-Range, если он присутствует. Если она запрашивала отчёты об успехе, то ДОЛЖНА хранить достаточно состояния о каждом отправленном сообщении, ожидающем подтверждения, чтобы соотносить запросы REPORT с исходными сообщениями.
An endpoint that receives a REPORT request containing a Status header field with a namespace field of "000" MUST interpret the report in exactly the same way it would interpret an MSRP transaction response with a response code matching the status-code field.
Конечная точка, получающая запрос REPORT, содержащий поле заголовка Status с полем пространства имён "000", ДОЛЖНА интерпретировать отчёт точно так же, как она интерпретировала бы ответ транзакции MSRP с кодом ответа, совпадающим с полем status-code.
It is possible to receive a failure report or a failure transaction response for a chunk that is currently being delivered. In this case, the entire message corresponding to that chunk SHOULD be aborted, by including the "#" character in the continuation field of the end-line.
Возможно получение отчёта о неудаче или ответа транзакции о неудаче для фрагмента, который в данный момент доставляется. В этом случае всё сообщение, соответствующее этому фрагменту, ДОЛЖНО быть прервано путём включения символа "#" в поле продолжения конечной строки.
It is possible that an endpoint will receive a REPORT request on a session that is no longer valid. The endpoint's behavior if this happens is a matter of local policy. The endpoint is not required to take any steps to facilitate such late delivery; i.e., it is not expected to keep a connection active in case late REPORTs might arrive.
Возможно, что конечная точка получит запрос REPORT по сеансу, который больше не действителен. Поведение конечной точки в этом случае определяется локальной политикой. Конечная точка не обязана предпринимать какие-либо шаги для облегчения такой поздней доставки, то есть не обязана поддерживать соединение активным на случай прихода поздних REPORT.
When an endpoint that sent a SEND request receives a failure REPORT indicating that a particular byte range was not received, it MUST treat the session as failed. If it wishes to recover, it MUST first re-negotiate the URIs at the signaling level then resend that range of bytes of the message on the resulting new session.
Когда конечная точка, отправившая запрос SEND, получает отчёт о неудаче, указывающий, что определённый диапазон байтов не был получен, она ДОЛЖНА рассматривать сеанс как неудачный. Если она желает восстановиться, она ДОЛЖНА сначала повторно согласовать URI на сигнальном уровне, а затем повторно отправить этот диапазон байтов сообщения в новом созданном сеансе.
MSRP nodes MUST NOT send MSRP REPORT requests in response to other REPORT requests.
Узлы MSRP НЕ ДОЛЖНЫ отправлять запросы MSRP REPORT в ответ на другие запросы REPORT.
8. Using MSRP with SIP and SDP
8. Использование MSRP с SIP и SDP
MSRP sessions will typically be initiated using the Session Description Protocol (SDP) [2] via the SIP offer/answer mechanism [3].
Сеансы MSRP обычно инициируются с использованием протокола описания сеансов (SDP) [2] через механизм предложения/ответа SIP [3].
This document defines a handful of new SDP parameters to set up MSRP sessions. These are detailed below and in the IANA Considerations section.
Настоящий документ определяет несколько новых параметров SDP для установления сеансов MSRP. Они подробно описаны ниже и в разделе "Соображения IANA".
An MSRP media-line (that is, a media-line proposing MSRP) in the session description is accompanied by a mandatory "path" attribute. This attribute contains a space-separated list of URIs to be visited to contact the user agent advertising this session description. If more than one URI is present, the leftmost URI is the first URI to be visited to reach the target resource. (The path list can contain multiple URIs to allow for the deployment of gateways or relays in the future.) MSRP implementations that can accept incoming connections without the need for relays will typically only provide a single URI here.
Строка медиаданных MSRP (то есть строка медиаданных, предлагающая MSRP) в описании сеанса сопровождается обязательным атрибутом "path". Этот атрибут содержит разделённый пробелами список URI, которые нужно посетить для связи с пользовательским агентом, анонсирующим это описание сеанса. Если присутствует более одного URI, самый левый URI — это первый URI, посещаемый для достижения целевого ресурса. (Список пути может содержать несколько URI, чтобы допустить развёртывание шлюзов или ретрансляторов в будущем.) Реализации MSRP, которые могут принимать входящие соединения без необходимости в ретрансляторах, обычно предоставляют здесь только один URI.
An MSRP media line is also accompanied by an "accept-types" attribute, and optionally an "accept-wrapped-types" attribute. These attributes are used to specify the media-types that are acceptable to the endpoint.
Строка медиаданных MSRP также сопровождается атрибутом "accept-types" и, необязательно, атрибутом "accept-wrapped-types". Эти атрибуты используются для указания типов медиаданных, приемлемых для конечной точки.

8.1. Соединение SDP и строки медиаданных
An SDP connection-line takes the following format:
Строка соединения SDP имеет следующий формат:
c=<network type> <address type> <connection address>

The network type and address type fields are used as normal for SDP. The connection address field MUST be set to the IP address or fully qualified domain name from the MSRP URI identifying the endpoint in its path attribute.
Поля типа сети и типа адреса используются как обычно для SDP. Поле адреса соединения ДОЛЖНО быть установлено в IP-адрес или полное доменное имя из URI MSRP, идентифицирующего конечную точку в её атрибуте path.
The general format of an SDP media-line is:
Общий формат строки медиаданных SDP:
m=<media> <port> <protocol> <format list>
m=<media> <port> <protocol> <format list>
Figure 5: Standard SDP Media Line
Рисунок 5: Стандартная строка медиаданных SDP
An offered or accepted media-line for MSRP over TCP MUST include a protocol field value of "TCP/MSRP", or "TCP/TLS/MSRP" for TLS. The media field value MUST be "message". The format list field MUST be set to "*".
Предложенная или принятая строка медиаданных для MSRP поверх TCP ДОЛЖНА включать значение поля протокола "TCP/MSRP" или "TCP/TLS/MSRP" для TLS. Значение поля медиаданных ДОЛЖНО быть "message". Поле списка форматов ДОЛЖНО быть установлено в "*".
The port field value MUST match the port value used in the endpoint's MSRP URI in the path attribute, except that, as described in [3], a user agent that wishes to accept an offer, but not a specific media- line, MUST set the port number of that media-line to zero (0) in the response. Since MSRP allows multiple sessions to share the same TCP connection, multiple m-lines in a single SDP document may share the same port field value; MSRP devices MUST NOT assume any particular relationship between m-lines on the sole basis that they have matching port field values. MSRP devices do not use the c-line address field, or the m-line port and format list fields to determine where to connect. Rather, they use the attributes defined in this specification. The connection information is copied to the c-line and m-line for purposes of backwards compatibility with conventional SDP usages. While MSRP could theoretically carry any media-type, "message" is appropriate.
Значение поля порта ДОЛЖНО совпадать со значением порта, используемым в URI MSRP конечной точки в атрибуте path, за исключением того, что, как описано в [3], пользовательский агент, желающий принять предложение, но не конкретную строку медиаданных, ДОЛЖЕН установить номер порта этой строки медиаданных в ноль (0) в ответе. Поскольку MSRP позволяет нескольким сеансам совместно использовать одно TCP-соединение, несколько строк m-line в одном документе SDP могут иметь одинаковое значение поля порта; устройства MSRP НЕ ДОЛЖНЫ предполагать какой-либо конкретной связи между строками m-line только на основании совпадения значений поля порта. Устройства MSRP не используют поле адреса строки c-line или поля порта и списка форматов строки m-line для определения места подключения. Вместо этого они используют атрибуты, определённые в настоящей спецификации. Информация о соединении копируется в c-line и m-line для обратной совместимости с обычным использованием SDP. Хотя MSRP теоретически мог бы переносить любой тип медиаданных, "message" является подходящим.
8.2. URI Negotiations
8.2. Согласование URI
Each endpoint in an MSRP session is identified by a URI. These URIs are negotiated in the SDP exchange. Each SDP offer or answer that proposes MSRP MUST contain a "path" attribute containing one or more MSRP URIs. The path attribute is used in an SDP a-line, and has the following syntax:
Каждая конечная точка в сеансе MSRP идентифицируется URI. Эти URI согласуются в ходе обмена SDP. Каждое предложение или ответ SDP, предлагающее MSRP, ДОЛЖНО содержать атрибут "path", содержащий один или несколько URI MSRP. Атрибут path используется в строке a-line SDP и имеет следующий синтаксис:
path = path-label ":" path-list path-label = "path" path-list= MSRP-URI *(SP MSRP-URI) Figure 6: Path Attribute
path = path-label ":" path-list path-label = "path" path-list= MSRP-URI *(SP MSRP-URI) Figure 6: Path Attribute
where MSRP-URI is an "msrp" or "msrps" URI as defined in Section 6. MSRP URIs included in an SDP offer or answer MUST include explicit port numbers.
где MSRP-URI — это URI "msrp" или "msrps", определённый в разделе 6. URI MSRP, включённые в предложение или ответ SDP, ДОЛЖНЫ включать явные номера портов.
An MSRP device uses the URI to determine a host address, port, transport, and protection level when connecting, and to identify the target when sending requests and responses.
Устройство MSRP использует URI для определения адреса хоста, порта, транспорта и уровня защиты при подключении, а также для идентификации цели при отправке запросов и ответов.
The offerer and answerer each selects a URI to represent itself and sends that URI to its peer in the SDP document. Each peer stores the path value received from the other peer and uses that value as the target for requests inside the resulting session. If the path attribute received from the peer contains more than one URI, then the target URI is the rightmost, while the leftmost entry represents the adjacent hop. If only one entry is present, then it is both the peer and adjacent hop URI. The target path is the entire path attribute value received from the peer.
Предлагающая и отвечающая стороны каждая выбирает URI для представления себя и отправляет этот URI своему пиру в документе SDP. Каждый пир сохраняет значение path, полученное от другого пира, и использует это значение как цель для запросов в результирующем сеансе. Если атрибут path, полученный от пира, содержит более одного URI, то целевым URI является самый правый, а самая левая запись представляет соседний переход. Если присутствует только одна запись, то она является URI как пира, так и соседнего перехода. Целевой путь — это всё значение атрибута path, полученное от пира.

Следующий пример показывает предложение SDP с URI сеанса "msrp://alice.example.com:7394/2s93i9ek2a;tcp".
v=0 o=alice 2890844526 2890844527 IN IP4 alice.example.com s= - c=IN IP4 alice.example.com t=0 0 m=message 7394 TCP/MSRP * a=accept-types:text/plain a=path:msrp://alice.example.com:7394/2s93i9ek2a;tcp
v=0 o=alice 2890844526 2890844527 IN IP4 alice.example.com s= - c=IN IP4 alice.example.com t=0 0 m=message 7394 TCP/MSRP * a=accept-types:text/plain a=path:msrp://alice.example.com:7394/2s93i9ek2a;tcp

The rightmost URI in the path attribute MUST identify the endpoint that generated the SDP document, or some other location where that endpoint wishes to receive requests associated with the session. It MUST be assigned for this particular session, and MUST NOT duplicate any URI in use for any other session in which the endpoint is currently participating. It SHOULD be hard to guess, and protected from eavesdroppers. This is discussed in more detail in Section 14.
Самый правый URI в атрибуте path ДОЛЖЕН идентифицировать конечную точку, сгенерировавшую документ SDP, или другое место, где эта конечная точка желает принимать запросы, связанные с сеансом. Он ДОЛЖЕН быть назначен для этого конкретного сеанса и НЕ ДОЛЖЕН дублировать какой-либо URI, используемый для любого другого сеанса, в котором конечная точка в настоящее время участвует. Он ДОЛЖЕН быть трудно угадываемым и защищённым от подслушивания. Это более подробно обсуждается в разделе 14.
8.3. Path Attributes with Multiple URIs
8.3. Атрибуты path с несколькими URI
As mentioned previously, this document describes MSRP for peer-to- peer scenarios, that is, when no relays are used. The use of relays is described in a separate document [23]. In order to allow an MSRP device that only implements the core specification to interoperate with devices that use relays, this document must include a few assumptions about how relays work.
Как упоминалось ранее, настоящий документ описывает MSRP для одноранговых сценариев, то есть когда ретрансляторы не используются. Использование ретрансляторов описано в отдельном документе [23]. Чтобы устройство MSRP, реализующее только базовую спецификацию, могло взаимодействовать с устройствами, использующими ретрансляторы, настоящий документ должен включать несколько допущений о работе ретрансляторов.
An endpoint that uses one or more relays will indicate that by putting a URI for each device in the relay chain into the SDP path attribute. The final entry will point to the endpoint itself. The other entries will indicate each proposed relay, in order. The first entry will point to the first relay in the chain from the perspective of the peer, that is, the relay to which the peer device, or a relay operating on its behalf, should connect.
Конечная точка, использующая один или несколько ретрансляторов, укажет это, поместив URI для каждого устройства в цепочке ретрансляторов в атрибут path SDP. Последняя запись в этом списке будет указывать на саму конечную точку. Остальные записи будут указывать каждый предлагаемый ретранслятор по порядку. Первая запись будет указывать на первый ретранслятор в цепочке с точки зрения пира, то есть ретранслятор, к которому должно подключаться устройство-пир или действующий от его имени ретранслятор.
Endpoints that do not wish to insert a relay, including those that do not support relays at all, will put exactly one URI into the path attribute. This URI represents both the endpoint for the session and the connection point.
Конечные точки, которые не желают вставлять ретранслятор, в том числе те, которые вообще не поддерживают ретрансляторы, поместят в атрибут path ровно один URI. Этот URI представляет как конечную точку для сеанса, так и точку подключения.
Even though endpoints that implement only this specification will never introduce a relay, they need to be able to interoperate with other endpoints that do use relays. Therefore, they MUST be prepared to receive more than one URI in the SDP path attribute. When an endpoint receives more than one URI in a path attribute, only the first entry is relevant for purposes of resolving the address and port, and establishing the network connection, as it describes the first adjacent hop.
Хотя конечные точки, реализующие только эту спецификацию, никогда не будут вводить ретранслятор, они должны иметь возможность взаимодействовать с другими конечными точками, которые действительно используют ретрансляторы. Поэтому они ДОЛЖНЫ быть готовы получить более одного URI в атрибуте path SDP. Когда конечная точка получает более одного URI в атрибуте path, только первая запись имеет значение для разрешения адреса и порта и установления сетевого соединения, поскольку она описывает первый соседний переход.
If an endpoint puts more than one URI in a path attribute, the final URI in the path attribute (the peer URI) identifies the session, and MUST not duplicate the URI of any other session in which the endpoint is currently participating. Uniqueness requirements for other entries in the path attribute are out of scope for this document.
Если конечная точка помещает более одного URI в атрибут path, последний URI в атрибуте path (URI пира) идентифицирует сеанс и НЕ ДОЛЖЕН дублировать URI любого другого сеанса, в котором конечная точка в настоящее время участвует. Требования уникальности для других записей в атрибуте path выходят за рамки настоящего документа.
8.4. Updated SDP Offers
8.4. Обновлённые предложения SDP
MSRP endpoints may sometimes need to send additional SDP exchanges for an existing session. They may need to send periodic exchanges with no change to refresh state in the network, for example, SIP session timers or the SIP UPDATE [24] request. They may need to change some other stream in a session without affecting the MSRP stream, or they may need to change an MSRP stream without affecting some other stream.
Конечным точкам MSRP иногда может потребоваться отправить дополнительные обмены SDP для существующего сеанса. Им может потребоваться отправлять периодические обмены без изменений для обновления состояния в сети, например таймеры сеанса SIP или запрос SIP UPDATE [24]. Им может потребоваться изменить какой-либо другой поток в сеансе, не затрагивая поток MSRP, или изменить поток MSRP, не затрагивая какой-либо другой поток.
Either peer may initiate an updated exchange at any time. The endpoint that sends the new offer assumes the role of offerer for all purposes. The answerer MUST respond with a path attribute that represents a valid path to itself at the time of the updated exchange. This new path may be the same as its previous path, but may be different. The new offerer MUST NOT assume that the peer will answer with the same path it used previously.
Любой из пиров может инициировать обновлённый обмен в любое время. Конечная точка, отправляющая новое предложение, принимает роль предлагающей стороны во всех смыслах. Отвечающая сторона ДОЛЖНА ответить атрибутом path, представляющим действительный путь к себе на момент обновлённого обмена. Этот новый путь может совпадать с её предыдущим путём, но может и отличаться. Новый предлагающий НЕ ДОЛЖЕН предполагать, что пир ответит тем же путём, который использовал ранее.
If either party wishes to send an SDP document that changes nothing at all, then it MUST use the same o-line as in the previous exchange.
Если какая-либо из сторон желает отправить документ SDP, который ничего не меняет, она ДОЛЖНА использовать ту же строку o-line, что и в предыдущем обмене.
8.5. Connection Negotiation
8.5. Согласование соединения
Previous versions of this document included a mechanism to negotiate the direction for any required TCP connection. The mechanism was loosely based on the Connection-Oriented Media (COMEDIA) [26] work done by the MMUSIC working group. The primary motivation was to allow MSRP sessions to succeed in situations where the offerer could not accept connections but the answerer could. For example, the offerer might be behind a NAT, while the answerer might have a globally routable address.
Предыдущие версии настоящего документа включали механизм согласования направления любого требуемого TCP-соединения. Механизм был в общих чертах основан на работе по медиаданным, ориентированным на соединения (COMEDIA) [26], выполненной рабочей группой MMUSIC. Основной мотивацией было позволить сеансам MSRP устанавливаться в ситуациях, когда предлагающая сторона не могла принимать соединения, а отвечающая могла. Например, предлагающая сторона могла находиться за NAT, а отвечающая сторона могла иметь глобально маршрутизируемый адрес.
The SIMPLE working group chose to remove that mechanism from MSRP, as it added a great deal of complexity to connection management. Instead, MSRP now specifies a default connection direction. The party that sent the original offer is responsible for connecting to its peer.
Рабочая группа SIMPLE решила удалить этот механизм из MSRP, поскольку он добавлял большую сложность в управление соединениями. Вместо этого MSRP теперь задаёт направление соединения по умолчанию. Сторона, отправившая исходное предложение, отвечает за подключение к своему пиру.
8.6. Content Type Negotiation
8.6. Согласование типа содержимого
An SDP media-line proposing MSRP MUST be accompanied by an accept- types attribute.
Строка медиаданных SDP, предлагающая MSRP, ДОЛЖНА сопровождаться атрибутом accept-types.
An entry of "*" in the accept-types attribute indicates that the sender may attempt to send content with media-types that have not been explicitly listed. Likewise, an entry with an explicit type and a "*" character as the subtype indicates that the sender may attempt to send content with any subtype of that type. If the receiver receives an MSRP request and is able to process the media-type, it does so. If not, it will respond with a 415 response. Note that all explicit entries SHOULD be considered preferred over any non-listed types. This feature is needed as, otherwise, the list of formats for rich IM devices may be prohibitively large.
Запись "*" в атрибуте accept-types указывает, что отправитель может попытаться отправить содержимое с типами медиаданных, которые не были явно перечислены. Аналогично, запись с явным типом и символом "*" в качестве подтипа указывает, что отправитель может попытаться отправить содержимое с любым подтипом этого типа. Если получатель получает запрос MSRP и способен обработать тип медиаданных, он это делает. Если нет, он ответит ответом 415. Обратите внимание, что все явные записи ДОЛЖНЫ считаться предпочтительнее любых неперечисленных типов. Эта возможность нужна, поскольку иначе список форматов для устройств с богатыми возможностями обмена мгновенными сообщениями мог бы стать непомерно большим.
This specification requires the support of certain data formats. Mandatory formats MUST be signaled like any other, either explicitly or by the use of a "*".
Настоящая спецификация требует поддержки определённых форматов данных. Обязательные форматы ДОЛЖНЫ сигнализироваться как любые другие, либо явно, либо с использованием "*".
The accept-types attribute may include container types, that is, MIME formats that contain other types internally. If compound types are used, the types listed in the accept-types attribute may be used as the root payload or may be wrapped in a listed container type. Any container types MUST also be listed in the accept-types attribute.
Атрибут accept-types может включать контейнерные типы, то есть форматы MIME, которые внутренне содержат другие типы. Если используются составные типы, типы, перечисленные в атрибуте accept-types, могут использоваться как корневая полезная нагрузка или могут быть вложены в перечисленный контейнерный тип. Любые контейнерные типы также ДОЛЖНЫ быть перечислены в атрибуте accept-types.
Occasionally, an endpoint will need to specify a MIME media-type that can only be used if wrapped inside a listed container type.
Иногда конечной точке потребуется указать тип медиаданных MIME, который может использоваться только при вложении в перечисленный контейнерный тип.
Endpoints MAY specify media-types that are only allowed when wrapped inside compound types using the "accept-wrapped-types" attribute in an SDP a-line.
Конечные точки МОГУТ указывать типы медиаданных, которые разрешены только при вложении в составные типы, используя атрибут "accept-wrapped-types" в строке a-line SDP.
The semantics for accept-wrapped-types are identical to those of the accept-types attribute, with the exception that the specified types may only be used when wrapped inside container types listed in the accept-types attribute. Only types listed in the accept-types attribute may be used as the "root" type for the entire body. Since any type listed in accept-types may be both used as a root body and wrapped in other bodies, format entries from accept-types SHOULD NOT be repeated in this attribute.
Семантика accept-wrapped-types идентична семантике атрибута accept-types, за исключением того, что указанные типы могут использоваться только при вложении в контейнерные типы, перечисленные в атрибуте accept-types. Только типы, перечисленные в атрибуте accept-types, могут использоваться как "корневой" тип для всего тела. Поскольку любой тип, перечисленный в accept-types, может использоваться и как корневое тело, и как вложенный в другие тела, записи формата из accept-types НЕ ДОЛЖНЫ повторяться в этом атрибуте.
This approach does not allow for specifying distinct lists of acceptable wrapped types for different types of containers. If an endpoint understands a media-type in the context of one wrapper, it is assumed to understand it in the context of any other acceptable wrappers, subject to any constraints defined by the wrapper types themselves. The approach of specifying types that are only allowed inside of containers separately from the primary payload types allows an endpoint to force the use of certain wrappers. For example, a Common Presence and Instant Messaging (CPIM) [12] gateway device may require all messages to be wrapped inside message/cpim bodies, but may allow several content types inside the wrapper. If the gateway were to specify the wrapped types in the accept-types attribute, its peer might attempt to use those types without the wrapper.
Этот подход не позволяет задавать отдельные списки приемлемых вложенных типов для разных типов контейнеров. Если конечная точка понимает тип медиаданных в контексте одного контейнера, предполагается, что она понимает его и в контексте любых других приемлемых контейнеров, с учётом любых ограничений, определённых самими контейнерными типами. Подход, при котором типы, разрешённые только внутри контейнеров, указываются отдельно от основных типов полезной нагрузки, позволяет конечной точке принудительно использовать определённые контейнеры. Например, устройство шлюза Common Presence and Instant Messaging (CPIM) [12] может требовать, чтобы все сообщения были вложены в тела message/cpim, но может разрешать несколько типов содержимого внутри контейнера. Если бы шлюз указал вложенные типы в атрибуте accept-types, его пир мог бы попытаться использовать эти типы без контейнера.
If the recipient of an offer does not understand any of the payload types indicated in the offered SDP, it SHOULD indicate that using the appropriate mechanism of the rendezvous protocol. For example, in SIP, it SHOULD return a SIP 488 response.
Если получатель предложения не понимает ни один из типов полезной нагрузки, указанных в предложенном SDP, он ДОЛЖЕН указать это с помощью соответствующего механизма протокола рандеву. Например, в SIP он ДОЛЖЕН вернуть ответ SIP 488.
An MSRP endpoint MUST NOT send content of a type not signaled by the peer in either an accept-types or an accept-wrapped-types attribute. Furthermore, it MUST NOT send a top-level (i.e., not wrapped) MIME document of a type not signaled in the accept-types attribute. In either case, the signaling could be explicit, or implicit through the use of the "*" character.
Конечная точка MSRP НЕ ДОЛЖНА отправлять содержимое типа, не сигнализированного пиром ни в атрибуте accept-types, ни в атрибуте accept-wrapped-types. Более того, она НЕ ДОЛЖНА отправлять документ MIME верхнего уровня (то есть не вложенный) типа, не сигнализированного в атрибуте accept-types. В любом случае сигнализация может быть явной или неявной благодаря использованию символа "*".
An endpoint MAY indicate the maximum size message it wishes to receive using the max-size a-line attribute. Max-size refers to the complete message in octets, not the size of any one chunk. Senders SHOULD NOT exceed the max-size limit for any message sent in the resulting session. However, the receiver should consider max-size value as a hint.

Max-size относится к полному сообщению в октетах, а не к размеру какого-либо одного фрагмента. 8.8. MSRP User Experience with SIP
8.8. Опыт пользователя MSRP при использовании SIP
In typical SIP applications, when an endpoint receives an INVITE request, it alerts the user, and waits for user input before responding. This is analogous to the typical telephone user experience, where the callee "answers" the call.
В типичных приложениях SIP, когда конечная точка получает запрос INVITE, она оповещает пользователя и ждёт ввода пользователя, прежде чем ответить. Это аналогично типичному опыту пользователя телефонии, когда вызываемый "отвечает" на вызов.
In contrast, the typical user experience for instant messaging applications is that the initial received message is immediately displayed to the user, without waiting for the user to "join" the conversation. Therefore, the principle of least surprise would suggest that MSRP endpoints using SIP signaling SHOULD allow a mode where the endpoint quietly accepts the session and begins displaying messages.
Напротив, типичный опыт пользователя приложений обмена мгновенными сообщениями состоит в том, что первоначально полученное сообщение немедленно отображается пользователю, без ожидания, пока пользователь "присоединится" к беседе. Поэтому принцип наименьшего удивления предполагал бы, что конечные точки MSRP, использующие сигнализацию SIP, ДОЛЖНЫ допускать режим, в котором конечная точка тихо принимает сеанс и начинает отображать сообщения.
This guideline may not make sense for all situations, such as for mixed-media applications, where both MSRP and audio sessions are offered in the same INVITE. In general, good application design should take precedence.
Это руководство может не иметь смысла во всех ситуациях, например для приложений со смешанными медиаданными, где в одном INVITE предлагаются и сеанс MSRP, и аудиосеанс. В целом, хороший дизайн приложения должен преобладать.
SIP INVITE requests may be forked by a SIP proxy, resulting in more than one endpoint receiving the same INVITE. SIP early media [29] techniques can be used to establish a preliminary session with each endpoint so the initial message(s) are displayed on each endpoint, and canceling the INVITE transaction for any endpoints that do not send MSRP traffic after some period of time, so that they cease receiving MSRP traffic from the inviter.
Запросы SIP INVITE могут разветвляться прокси-сервером SIP, в результате чего один и тот же INVITE получают несколько конечных точек. Методы ранних медиаданных SIP [29] можно использовать для установления предварительного сеанса с каждой конечной точкой, чтобы первоначальные сообщения отображались на каждой конечной точке, и для отмены транзакции INVITE для тех конечных точек, которые не отправляют трафик MSRP по истечении некоторого времени, чтобы они прекратили получать трафик MSRP от инициатора приглашения.
8.9. SDP Direction Attribute and MSRP
8.9. Атрибут направления SDP и MSRP
SDP defines a number of attributes that modify the direction of media flows. These are the "sendonly", "recvonly", "inactive", and "sendrecv" attributes. If a "sendonly" or "recvonly" attribute modifies an MSRP media description line, the attribute indicates the direction of MSRP SEND requests that contain regular message payloads. Unless otherwise specified, these attributes do not affect the direction of other types of requests, such as REPORT. SEND requests that contain some kind of control or reporting protocol rather than regular message payload (e.g., Instant Message Delivery Notification (IMDN) reports) should be generated according to the protocol rules as if no direction attribute were present.
SDP определяет ряд атрибутов, изменяющих направление потоков медиаданных. Это атрибуты "sendonly", "recvonly", "inactive" и "sendrecv". Если атрибут "sendonly" или "recvonly" изменяет строку описания медиаданных MSRP, атрибут указывает направление запросов MSRP SEND, содержащих обычные полезные нагрузки сообщений. Если не указано иное, эти атрибуты не влияют на направление других типов запросов, таких как REPORT. Запросы SEND, содержащие какой-либо протокол управления или отчётности вместо обычной полезной нагрузки сообщения (например, отчёты Instant Message Delivery Notification (IMDN)), должны генерироваться согласно правилам протокола так, как если бы атрибут направления отсутствовал.

11.7. Forked IM
11.7. Разветвлённое мгновенное сообщение
Traditional IM systems generally do a poor job of handling multiple simultaneous IM clients online for the same person. While some do a better job than many existing systems, handling of multiple clients is fairly crude. This becomes a much more significant issue when always-on mobile devices are available, but it is desirable to use them only if another IM client is not available.
Традиционные системы обмена мгновенными сообщениями, как правило, плохо справляются с несколькими одновременными клиентами IM, находящимися онлайн у одного человека. Хотя некоторые справляются лучше, чем многие существующие системы, обработка нескольких клиентов довольно примитивна. Это становится гораздо более существенной проблемой, когда доступны постоянно включённые мобильные устройства, но желательно использовать их только в том случае, если другой клиент IM недоступен.
Using SIP makes rendezvous decisions explicit, deterministic, and very flexible. In contrast, "page-mode" IM systems use implicit implementation-specific decisions that IM clients cannot influence. With SIP session-mode messaging, rendezvous decisions can be under control of the client in a predictable, interoperable way for any host that implements callee capabilities [31]. As a result, rendezvous policy is managed consistently for each address of record.
Использование SIP делает решения о рандеву явными, детерминированными и очень гибкими. Напротив, системы IM "постраничного режима" используют неявные решения, зависящие от реализации, на которые клиенты IM не могут влиять. При обмене сообщениями в сеансовом режиме SIP решения о рандеву могут контролироваться клиентом предсказуемым, совместимым способом для любого хоста, реализующего возможности вызываемого [31]. В результате политика рандеву управляется согласованно для каждого адреса записи.

12. Extensibility
12. Расширяемость
MSRP was designed to be only minimally extensible. New MSRP methods, header fields, and status codes can be defined in standards-track RFCs. MSRP does not contain a version number or any negotiation mechanism to require or discover new features. If an extension is specified in the future that requires negotiation, the specification will need to describe how the extension is to be negotiated in the encapsulating signaling protocol. If a non-interoperable update or extension occurs in the future, it will be treated as a new protocol, and MUST describe how its use will be signaled.
MSRP был разработан с расчётом лишь на минимальную расширяемость. Новые методы, поля заголовков и коды состояния MSRP могут быть определены в RFC уровня стандартов. MSRP не содержит номера версии или какого-либо механизма согласования для требования или обнаружения новых возможностей. Если в будущем будет определена расширение, требующее согласования, спецификация должна будет описать, как это расширение согласуется в инкапсулирующем сигнальном протоколе. Если в будущем появится несовместимое обновление или расширение, оно будет рассматриваться как новый протокол и ДОЛЖНО описывать, как будет сигнализироваться его использование.
In order to allow extension header fields without breaking interoperability, if an MSRP device receives a request or response containing a header field that it does not understand, it MUST ignore the header field and process the request or response as if the header field was not present. If an MSRP device receives a request with an unknown method, it MUST return a 501 response.
Чтобы допустить поля заголовков расширений без нарушения совместимости, если устройство MSRP получает запрос или ответ, содержащий непонятое им поле заголовка, оно ДОЛЖНО игнорировать это поле заголовка и обрабатывать запрос или ответ так, как если бы этого поля не было. Если устройство MSRP получает запрос с неизвестным методом, оно ДОЛЖНО вернуть ответ 501.
MSRP was designed to use lists of URIs instead of a single URI in the To-Path and From-Path header fields in anticipation of relay or gateway functionality being added. In addition, "msrp" and "msrps" URIs can contain parameters that are extensible.
MSRP был разработан так, чтобы использовать списки URI вместо одного URI в полях заголовков To-Path и From-Path, в предвидении добавления функциональности ретранслятора или шлюза. Кроме того, URI "msrp" и "msrps" могут содержать расширяемые параметры.
13. CPIM Compatibility
13. Совместимость с CPIM
MSRP sessions may go to a gateway to other Common Profile for Instant Messaging (CPIM) [27] compatible protocols. If this occurs, the gateway MUST maintain session state, and MUST translate between the MSRP session semantics and CPIM semantics, which do not include a concept of sessions. Furthermore, when one endpoint of the session is a CPIM gateway, instant messages SHOULD be wrapped in "message/cpim" [12] bodies. Such a gateway MUST include "message/cpim" as the first entry in its SDP accept-types attribute. MSRP endpoints sending instant messages to a peer that has included "message/cpim" as the first entry in the accept-types attribute SHOULD encapsulate all instant message bodies in "message/ cpim" wrappers. All MSRP endpoints MUST support the message/cpim type, and SHOULD support the S/MIME[7] features of that format.
Сеансы MSRP могут вести к шлюзу других протоколов, совместимых с Common Profile for Instant Messaging (CPIM) [27]. Если это происходит, шлюз ДОЛЖЕН поддерживать состояние сеанса и ДОЛЖЕН выполнять преобразование между семантикой сеанса MSRP и семантикой CPIM, которая не включает понятия сеансов. Кроме того, когда одна из конечных точек сеанса является шлюзом CPIM, мгновенные сообщения ДОЛЖНЫ быть вложены в тела "message/cpim" [12]. Такой шлюз ДОЛЖЕН включать "message/cpim" в качестве первой записи в своём атрибуте accept-types SDP. Конечные точки MSRP, отправляющие мгновенные сообщения пиру, включившему "message/cpim" в качестве первой записи в атрибуте accept-types, ДОЛЖНЫ инкапсулировать все тела мгновенных сообщений в обёртки "message/cpim". Все конечные точки MSRP ДОЛЖНЫ поддерживать тип message/cpim и ДОЛЖНЫ поддерживать возможности S/MIME [7] этого формата.
If a message is to be wrapped in a message/cpim envelope, the wrapping MUST be done prior to breaking the message into chunks, if needed. All MSRP endpoints MUST recognize the From, To, DateTime, and Require header fields as defined in RFC 3862. Such applications SHOULD recognize the CC header field, and MAY recognize the Subject header field. Any MSRP application that recognizes any message/cpim header field MUST understand the NS (name space) header field.
Если сообщение должно быть вложено в конверт message/cpim, обёртывание ДОЛЖНО быть выполнено до разбиения сообщения на фрагменты, если это необходимо. Все конечные точки MSRP ДОЛЖНЫ распознавать поля заголовков From, To, DateTime и Require, как определено в RFC 3862. Такие приложения ДОЛЖНЫ распознавать поле заголовка CC и МОГУТ распознавать поле заголовка Subject. Любое приложение MSRP, распознающее любое поле заголовка message/cpim, ДОЛЖНО понимать поле заголовка NS (пространство имён).
All message/cpim body parts sent by an MSRP endpoint MUST include the From and To header fields. If the message/cpim body part is protected using S/MIME, then it MUST also include the DateTime header field.
Все части тела message/cpim, отправляемые конечной точкой MSRP, ДОЛЖНЫ включать поля заголовков From и To. Если часть тела message/cpim защищена с помощью S/MIME, то она ДОЛЖНА также включать поле заголовка DateTime.
The NS, To, and CC header fields may occur multiple times. Other header fields defined in RFC 3862 MUST NOT occur more than once in a given message/cpim body part in an MSRP message. The Require header field MAY include multiple values. The NS header field MAY occur zero or more times, depending on how many name spaces are being referenced.
Поля заголовков NS, To и CC могут встречаться несколько раз. Другие поля заголовков, определённые в RFC 3862, НЕ ДОЛЖНЫ встречаться более одного раза в данной части тела message/cpim в сообщении MSRP. Поле заголовка Require МОЖЕТ включать несколько значений. Поле заголовка NS МОЖЕТ встречаться ноль или более раз, в зависимости от того, сколько пространств имён упоминается.
Extension header fields MAY occur more than once, depending on the definition of such header fields.
Поля заголовков расширений МОГУТ встречаться более одного раза, в зависимости от определения таких полей.
Using message/cpim envelopes is also useful if an MSRP device wishes to send a message on behalf of some other identity. The device may add a message/cpim envelope with the appropriate From header field value.
Использование конвертов message/cpim также полезно, если устройство MSRP желает отправить сообщение от имени некоторой другой идентичности. Устройство может добавить конверт message/cpim с соответствующим значением поля заголовка From.
14. Security Considerations
14. Соображения безопасности
Instant messaging systems are used to exchange a variety of sensitive information ranging from personal conversations, to corporate confidential information, to account numbers and other financial trading information. IM is used by individuals, corporations, and governments for communicating important information. IM systems need to provide the properties of integrity and confidentiality for the exchanged information, and the knowledge that you are communicating with the correct party, and they need to allow the possibility of anonymous communication. MSRP pushes many of the hard problems to SIP when SIP sets up the session, but some of the problems remain. Spam and Denial of Service (DoS) attacks are also very relevant to IM systems.
Системы обмена мгновенными сообщениями используются для обмена разнообразной конфиденциальной информацией — от личных бесед до корпоративной конфиденциальной информации, номеров счетов и других данных финансовой торговли. IM используется отдельными людьми, корпорациями и правительствами для обмена важной информацией. Системы IM должны обеспечивать целостность и конфиденциальность обмениваемой информации, а также знание того, что вы общаетесь с правильной стороной, и должны допускать возможность анонимного общения. MSRP перекладывает многие трудные задачи на SIP, когда SIP устанавливает сеанс, но некоторые проблемы остаются. Спам и атаки типа "отказ в обслуживании" (DoS) также очень актуальны для систем IM.
MSRP needs to provide confidentiality and integrity for the messages it transfers. It also needs to provide assurances that the connected host is the host that it meant to connect to and that the connection has not been hijacked.
MSRP должен обеспечивать конфиденциальность и целостность передаваемых сообщений. Он также должен обеспечивать гарантии того, что подключённый хост — это тот хост, к которому предполагалось подключиться, и что соединение не было перехвачено.
14.1. Secrecy of the MSRP URI
14.1. Секретность URI MSRP
When an endpoint sends an MSRP URI to its peer in a rendezvous protocol, that URI is effectively a secret shared between the peers. If an attacker learns or guesses the URI prior to the completion of session setup, it may be able to impersonate one of the peers.
Когда конечная точка отправляет URI MSRP своему пиру в протоколе рандеву, этот URI фактически является секретом, разделяемым между пирами. Если злоумышленник узнает или угадает URI до завершения установления сеанса, он может выдать себя за одного из пиров.
Assuming the URI exchange in the rendezvous protocol is sufficiently protected, it is critical that the URI remain difficult to "guess" via brute force methods. Most components of the URI, such as the scheme and the authority components, are common knowledge. The secrecy is entirely provided by the session-id component.
Если предположить, что обмен URI в протоколе рандеву достаточно защищён, критически важно, чтобы URI оставался трудным для "угадывания" методами перебора. Большинство компонентов URI, таких как схема и компоненты authority, являются общеизвестными. Секретность обеспечивается полностью компонентом session-id.
Therefore, when an MSRP device generates an MSRP URI to be used in the initiation of an MSRP session, the session-id component MUST contain at least 80 bits of randomness.
Поэтому, когда устройство MSRP генерирует URI MSRP для использования при инициировании сеанса MSRP, компонент session-id ДОЛЖЕН содержать не менее 80 бит случайности.
14.2. Transport Level Protection
14.2. Защита на транспортном уровне
When using only TCP connections, MSRP security is fairly weak. If host A is contacting host B, B passes its hostname and a secret to A using a rendezvous protocol. Although MSRP requires the use of a rendezvous protocol with the ability to protect this exchange, there is no guarantee that the protection will be used all the time. If such protection is not used, anyone can see this secret. Host A then connects to the provided hostname and passes the secret in the clear across the connection to B. Host A assumes that it is talking to B based on where it sent the SYN packet and then delivers the secret in plain text across the connections. Host B assumes it is talking to A because the host on the other end of the connection delivered the secret. An attacker that could ACK the SYN packet could insert itself as a man-in-the-middle in the connection.
При использовании только TCP-соединений безопасность MSRP довольно слаба. Если хост A связывается с хостом B, B передаёт A своё имя хоста и секрет через протокол рандеву. Хотя MSRP требует использования протокола рандеву с возможностью защиты этого обмена, нет гарантии, что защита будет использоваться всегда. Если такая защита не используется, секрет может увидеть любой. Затем хост A подключается к предоставленному имени хоста и передаёт секрет в открытом виде по соединению к B. Хост A предполагает, что общается с B, исходя из того, куда он отправил пакет SYN, и затем передаёт секрет открытым текстом по соединениям. Хост B предполагает, что общается с A, потому что хост на другом конце соединения передал секрет. Злоумышленник, способный подтвердить пакет SYN, мог бы встроиться в соединение как посредник.
When using TLS connections, the security is significantly improved. We assume that the host accepting the connection has a certificate from a well-known certification authority. Furthermore, we assume that the signaling to set up the session is protected by the rendezvous protocol. In this case, when host A contacts host B, the secret is passed through a confidential channel to A. A connects with TLS to B. B presents a valid certificate, so A knows it really is connected to B. A then delivers the secret provided by B, so that B can verify it is connected to A. In this case, a rogue SIP Proxy can see the secret in the SIP signaling traffic and could potentially insert itself as a man-in-the-middle.
При использовании TLS-соединений безопасность значительно повышается. Мы предполагаем, что хост, принимающий соединение, имеет сертификат от известного удостоверяющего центра. Кроме того, мы предполагаем, что сигнализация для установления сеанса защищена протоколом рандеву. В этом случае, когда хост A связывается с хостом B, секрет передаётся A по конфиденциальному каналу. A подключается к B по TLS; B предъявляет действительный сертификат, поэтому A знает, что действительно подключён к B. Затем A передаёт секрет, предоставленный B, чтобы B мог убедиться, что он подключён к A. В этом случае недобросовестный прокси-сервер SIP может видеть секрет в сигнальном трафике SIP и потенциально может встроиться как посредник.
Realistically, using TLS with certificates from well-known certification authorities is difficult for peer-to-peer connections, as the types of hosts that end clients use for sending instant messages are unlikely to have long-term stable IP addresses or DNS names that the certificates can bind to. In addition, the cost of server certificates from well-known certification authorities is currently expensive enough to discourage their use for each client. Using TLS in a peer-to-peer mode without well-known certificates is discussed in Section 14.4.
Реалистично говоря, использование TLS с сертификатами от известных удостоверяющих центров затруднительно для одноранговых соединений, поскольку типы хостов, которые конечные клиенты используют для отправки мгновенных сообщений, вряд ли имеют долговременные стабильные IP-адреса или DNS-имена, к которым сертификаты могли бы быть привязаны. Кроме того, стоимость серверных сертификатов от известных удостоверяющих центров в настоящее время достаточно высока, чтобы препятствовать их использованию для каждого клиента. Использование TLS в одноранговом режиме без известных сертификатов обсуждается в разделе 14.4.
TLS becomes much more practical when some form of relay is introduced. Clients can then form TLS connections to relays, which are much more likely to have TLS certificates. While this specification does not address such relays, they are described by a companion document [23]. That document makes extensive use of TLS to protect traffic between clients and relays, and between one relay and another.
TLS становится гораздо практичнее, когда вводится некоторая форма ретрансляции. Клиенты могут тогда устанавливать TLS-соединения с ретрансляторами, которые гораздо чаще имеют TLS-сертификаты. Хотя настоящая спецификация не рассматривает такие ретрансляторы, они описаны в сопровождающем документе [23]. Этот документ широко использует TLS для защиты трафика между клиентами и ретрансляторами, а также между одним ретранслятором и другим.
TLS is used to authenticate devices and to provide integrity and confidentiality for the header fields being transported. MSRP elements MUST implement TLS and MUST also implement the TLS ClientExtendedHello extended hello information for server name indication as described in [11]. A TLS cipher-suite of TLS_RSA_WITH_AES_128_CBC_SHA [13] MUST be supported (other cipher- suites MAY also be supported).
TLS используется для аутентификации устройств и обеспечения целостности и конфиденциальности переносимых полей заголовков. Элементы MSRP ДОЛЖНЫ реализовывать TLS и ДОЛЖНЫ также реализовывать расширенную информацию приветствия TLS ClientExtendedHello для указания имени сервера, как описано в [11]. ДОЛЖЕН поддерживаться набор шифров TLS TLS_RSA_WITH_AES_128_CBC_SHA [13] (другие наборы шифров также МОГУТ поддерживаться).
14.3. S/MIME
14.3. S/MIME
The only strong security for non-TLS connections is achieved using S/MIME.
Единственная надёжная защита для соединений без TLS достигается с помощью S/MIME.
Since MSRP carries arbitrary MIME content, it can trivially carry S/MIME protected messages as well. All MSRP implementations MUST support the multipart/signed media-type even if they do not support S/MIME. Since SIP can carry a session key, S/MIME messages in the context of a session could also be protected using a key-wrapped shared secret [28] provided in the session setup. MSRP can carry unencoded binary payloads. Therefore, MIME bodies MUST be transferred with a transfer encoding of binary. If a message is both signed and encrypted, it SHOULD be signed first, then encrypted. If S/MIME is supported, SHA-1, SHA-256, RSA, and AES-128 MUST be supported. For RSA, implementations MUST support key sizes of at least 1024 bits and SHOULD support key sizes of 2048 bits or more.
Поскольку MSRP переносит произвольное содержимое MIME, он может тривиально переносить и защищённые S/MIME сообщения. Все реализации MSRP ДОЛЖНЫ поддерживать тип медиаданных multipart/signed, даже если они не поддерживают S/MIME. Поскольку SIP может переносить сеансовый ключ, сообщения S/MIME в контексте сеанса также могут быть защищены с помощью ключа-обёртки общего секрета [28], предоставленного при установлении сеанса. MSRP может переносить незакодированные двоичные полезные нагрузки. Поэтому тела MIME ДОЛЖНЫ передаваться с транспортным кодированием binary. Если сообщение и подписано, и зашифровано, оно ДОЛЖНО быть сначала подписано, а затем зашифровано. Если поддерживается S/MIME, ДОЛЖНЫ поддерживаться SHA-1, SHA-256, RSA и AES-128. Для RSA реализации ДОЛЖНЫ поддерживать размеры ключей не менее 1024 бит и ДОЛЖНЫ поддерживать размеры ключей 2048 бит или более.
This does not actually require the endpoint to have certificates from a well-known certification authority. When MSRP is used with SIP, the Identity [17] and Certificates [25] mechanisms provide S/MIME- based delivery of a secret between A and B. No SIP intermediary except the explicitly trusted authentication service (one per user) can see the secret. The S/MIME encryption of the SDP can also be used by SIP to exchange keying material that can be used in MSRP. The MSRP session can then use S/MIME with this keying material to sign and encrypt messages sent over MSRP. The connection can still be hijacked since the secret is sent in clear text to the other end of the TCP connection, but the consequences are mitigated if all the MSRP content is signed and encrypted with S/MIME. Although out of scope for this document, the SIP negotiation of an MSRP session can negotiate symmetric keying material to be used with S/MIME for integrity and privacy.
На самом деле это не требует, чтобы конечная точка имела сертификаты от известного удостоверяющего центра. Когда MSRP используется с SIP, механизмы Identity [17] и Certificates [25] обеспечивают доставку секрета между A и B на основе S/MIME. Ни один посредник SIP, кроме явно доверенной службы аутентификации (одна на пользователя), не может увидеть секрет. Шифрование SDP с помощью S/MIME также может использоваться SIP для обмена ключевым материалом, который может применяться в MSRP. Затем сеанс MSRP может использовать S/MIME с этим ключевым материалом для подписи и шифрования сообщений, отправляемых по MSRP. Соединение всё ещё может быть перехвачено, поскольку секрет передаётся открытым текстом на другой конец TCP-соединения, но последствия смягчаются, если всё содержимое MSRP подписано и зашифровано с помощью S/MIME. Хотя это выходит за рамки настоящего документа, согласование SIP для сеанса MSRP может согласовывать симметричный ключевой материал для использования с S/MIME для целостности и конфиденциальности.
14.4. Using TLS in Peer-to-Peer Mode
14.4. Использование TLS в одноранговом режиме
TLS can be used with a self-signed certificate as long as there is a mechanism for both sides to ascertain that the other side used the correct certificate. When used with SDP and SIP, the correct certificate can be verified by passing a fingerprint of the certificate in the SDP and ensuring that the SDP has suitable integrity protection. When SIP is used to transport the SDP, the integrity can be provided by the SIP Identity mechanism [17]. The rest of this section describes the details of this approach.
TLS может использоваться с самоподписанным сертификатом, если есть механизм, позволяющий обеим сторонам убедиться, что другая сторона использовала правильный сертификат. При использовании с SDP и SIP правильный сертификат можно проверить, передав отпечаток сертификата в SDP и обеспечив надлежащую защиту целостности SDP. Когда SIP используется для транспортировки SDP, целостность может быть обеспечена механизмом SIP Identity [17]. Остальная часть этого раздела описывает детали этого подхода.
If self-signed certificates are used, the content of the subjectAltName attribute inside the certificate MAY use the URI of the user. In SIP, this URI of the user is the User's Address of Record (AOR). This is useful for debugging purposes only and is not required to bind the certificate to one of the communication endpoints. Unlike normal TLS operations in this protocol, when doing peer-to-peer TLS, the subjectAltName is not an important component of the certificate verification. If the endpoint is also able to make anonymous sessions, a distinct, unique certificate MUST be used for this purpose. For a client that works with multiple users, each user SHOULD have its own certificate. Because the generation of public/private key pairs is relatively expensive, endpoints are not required to generate certificates for each session.
Если используются самоподписанные сертификаты, содержимое атрибута subjectAltName внутри сертификата МОЖЕТ использовать URI пользователя. В SIP этот URI пользователя — это адрес записи (AOR) пользователя. Это полезно только для целей отладки и не требуется для привязки сертификата к одной из конечных точек связи. В отличие от обычных операций TLS в этом протоколе, при одноранговом TLS subjectAltName не является важным компонентом проверки сертификата. Если конечная точка также способна устанавливать анонимные сеансы, для этой цели ДОЛЖЕН использоваться отдельный, уникальный сертификат. Для клиента, работающего с несколькими пользователями, каждый пользователь ДОЛЖЕН иметь собственный сертификат. Поскольку генерация пар открытых/закрытых ключей относительно дорога, конечные точки не обязаны генерировать сертификаты для каждого сеанса.
A certificate fingerprint is the output of a one-way hash function computed over the Distinguished Encoding Rules (DER) form of the certificate. The endpoint MUST use the certificate fingerprint attribute as specified in [18] and MUST include this in the SDP. The certificate presented during the TLS handshake needs to match the fingerprint exchanged via the SDP, and if the fingerprint does not match the hashed certificate then the endpoint MUST tear down the media session immediately.
Отпечаток сертификата — это результат односторонней хеш-функции, вычисленной по форме Distinguished Encoding Rules (DER) сертификата. Конечная точка ДОЛЖНА использовать атрибут отпечатка сертификата, как указано в [18], и ДОЛЖНА включать его в SDP. Сертификат, предъявленный во время рукопожатия TLS, должен совпадать с отпечатком, переданным через SDP, и если отпечаток не соответствует хешированному сертификату, конечная точка ДОЛЖНА немедленно разорвать сеанс медиаданных.
When using SIP, the integrity of the fingerprint can be ensured through the SIP Identity mechanism [17]. When a client wishes to use SIP to set up a secure MSRP session with another endpoint, it sends an SDP offer in a SIP message to the other endpoint. This offer includes, as part of the SDP payload, the fingerprint of the certificate that the endpoint wants to use. The SIP message containing the offer is sent to the offerer's SIP proxy, which will add an Identity header according to the procedures outlined in [17]. When the far endpoint receives the SIP message, it can verify the identity of the sender using the Identity header. Since the Identity header is a digital signature across several SIP headers, in addition to the body or bodies of the SIP message, the receiver can also be certain that the message has not been tampered with after the digital signature was added to the SIP message.
При использовании SIP целостность отпечатка может быть обеспечена с помощью механизма SIP Identity [17]. Когда клиент желает использовать SIP для установления защищённого сеанса MSRP с другой конечной точкой, он отправляет предложение SDP в сообщении SIP другой конечной точке. Это предложение включает в составе полезной нагрузки SDP отпечаток сертификата, который конечная точка хочет использовать. Сообщение SIP, содержащее предложение, отправляется прокси-серверу SIP предлагающей стороны, который добавит заголовок Identity согласно процедурам, изложенным в [17]. Когда дальняя конечная точка получает сообщение SIP, она может проверить подлинность отправителя с помощью заголовка Identity. Поскольку заголовок Identity представляет собой цифровую подпись по нескольким заголовкам SIP, а также по телу или телам сообщения SIP, получатель может также убедиться, что сообщение не было изменено после добавления цифровой подписи к сообщению SIP.

14.5. Other Security Concerns
14.5. Другие проблемы безопасности
MSRP cannot be used as an amplifier for DoS attacks, but it can be used to form a distributed attack to consume TCP connection resources on servers. The attacker, Mallory, sends a SIP INVITE with no offer to Alice. Alice returns a 200 with an offer and Mallory returns an answer with SDP indicating that his MSRP address is the address of Tom. Since Alice sent the offer, Alice will initiate a connection to Tom using up resources on Tom's server. Given the huge number of IM clients, and the relatively few TCP connections that most servers support, this is a fairly straightforward attack.
MSRP не может использоваться как усилитель для атак DoS, но может использоваться для формирования распределённой атаки с целью исчерпания ресурсов TCP-соединений на серверах. Злоумышленник Мэллори отправляет Алисе SIP INVITE без предложения. Алиса возвращает 200 с предложением, а Мэллори возвращает ответ с SDP, указывающим, что его адрес MSRP — это адрес Тома. Поскольку Алиса отправила предложение, Алиса инициирует соединение с Томом, расходуя ресурсы сервера Тома. Учитывая огромное количество клиентов IM и относительно небольшое число TCP-соединений, которые поддерживает большинство серверов, это довольно простая атака.
SIP is attempting to address issues in dealing with spam. The spam issue is probably best dealt with at the SIP level when an MSRP session is initiated and not at the MSRP level.
SIP пытается решать проблемы борьбы со спамом. Проблему спама, вероятно, лучше решать на уровне SIP при инициировании сеанса MSRP, а не на уровне самого MSRP.
If a sender chooses to employ S/MIME to protect a message, all S/MIME operations apply to the complete message, prior to any breaking of the message into chunks.
Если отправитель решает применить S/MIME для защиты сообщения, все операции S/MIME применяются к полному сообщению до любого разбиения сообщения на фрагменты.
The signaling will have set up the session to or from some specific URIs that will often have "im:" or "sip:" URI schemes. When the signaling has been set up to a specific end user, and S/MIME is implemented, then the client needs to verify that the name in the SubjectAltName of the certificate contains an entry that matches the URI that was used for the other end in the signaling. There are some cases, such as IM conferencing, where the S/MIME certificate name and the signaled identity will not match. In these cases, the client should ensure that the user is informed that the message came from the user identified in the certificate and does not assume that the message came from the party they signaled.
Сигнализация настроит сеанс к некоторым конкретным URI или от них, которые часто имеют схемы URI "im:" или "sip:". Когда сигнализация настроена на конкретного конечного пользователя и S/MIME реализован, клиент должен проверить, что имя в SubjectAltName сертификата содержит запись, соответствующую URI, который использовался для другого конца в сигнализации. Есть некоторые случаи, например конференц-связь IM, когда имя в сертификате S/MIME и сигнализированная идентичность не совпадут. В этих случаях клиент должен убедиться, что пользователь проинформирован о том, что сообщение пришло от пользователя, указанного в сертификате, и не должен предполагать, что сообщение пришло от той стороны, с которой он сигнализировал.
In some cases, a sending device may need to attribute a message to some other identity, and may use different identities for different messages in the same session. For example, a conference server may send messages on behalf of multiple users on the same session. Rather than add additional header fields to MSRP for this purpose, MSRP relies on the message/cpim format for this purpose. The sender may envelop such a message in a message/cpim body, and place the actual sender identity in the From field. The trustworthiness of such an attribution is affected by the security properties of the session in the same way that the trustworthiness of the identity of the actual peer is affected, with the additional issue of determining whether the recipient trusts the sender to assert the identity.
В некоторых случаях отправляющему устройству может потребоваться приписать сообщение некоторой другой идентичности, и оно может использовать разные идентичности для разных сообщений в одном сеансе. Например, сервер конференции может отправлять сообщения от имени нескольких пользователей в одном сеансе. Вместо добавления дополнительных полей заголовков в MSRP для этой цели MSRP полагается на формат message/cpim. Отправитель может обернуть такое сообщение в тело message/cpim и поместить фактическую идентичность отправителя в поле From. Надёжность такой атрибуции затрагивается свойствами безопасности сеанса так же, как затрагивается надёжность идентичности фактического пира, с дополнительным вопросом определения того, доверяет ли получатель отправителю в утверждении идентичности.
This approach can result in nesting of message/cpim envelopes. For example, a message originates from a CPIM gateway, and is then forwarded by a conference server onto a new session. Both the gateway and the conference server introduce envelopes. In this case, the recipient client SHOULD indicate the chain of identity assertions to the user, rather than allow the user to assume that either the gateway or the conference server originated the message.
Этот подход может привести к вложению конвертов message/cpim. Например, сообщение создаётся шлюзом CPIM, а затем пересылается сервером конференции в новый сеанс. И шлюз, и сервер конференции вводят конверты. В этом случае клиент-получатель ДОЛЖЕН указать пользователю цепочку утверждений идентичности, вместо того чтобы позволить пользователю предполагать, что сообщение создано шлюзом или сервером конференции.
It is possible that a recipient might receive messages that are attributed to the same sender via different MSRP sessions. For example, Alice might be in a conversation with Bob via an MSRP session over a TLS protected channel. Alice might then receive a different message from Bob over a different session, perhaps with a conference server that asserts Bob's identity in a message/cpim envelope signed by the server.
Возможно, что получатель получит сообщения, приписываемые одному и тому же отправителю, через разные сеансы MSRP. Например, Алиса может вести беседу с Бобом через сеанс MSRP по каналу, защищённому TLS. Затем Алиса может получить другое сообщение от Боба в другом сеансе, возможно, с сервером конференции, который утверждает идентичность Боба в конверте message/cpim, подписанном сервером.
MSRP does not prohibit multiple simultaneous sessions between the same pair of identities. Nor does it prohibit an endpoint sending a message on behalf of another identity, such as may be the case for a conference server. The recipient's endpoint should determine its level of trust of the authenticity of the sender independently for each session. The fact that an endpoint trusts the authenticity of the sender on any given session should not affect the level of trust it assigns for apparently the same sender on a different session. When MSRP clients form or acquire a certificate, they SHOULD ensure that the subjectAltName has a GeneralName entry of type uniformResourceIdentifier for each URI corresponding to this client and should always include an "im:" URI. It is fine if the certificate contains other URIs such as "sip:" or "xmpp:" URIs.
MSRP не запрещает несколько одновременных сеансов между одной и той же парой идентичностей. Он также не запрещает конечной точке отправлять сообщение от имени другой идентичности, как это может быть в случае сервера конференции. Конечная точка получателя должна определять свой уровень доверия к подлинности отправителя независимо для каждого сеанса. Тот факт, что конечная точка доверяет подлинности отправителя в каком-либо сеансе, не должен влиять на уровень доверия, назначаемый по-видимому тому же отправителю в другом сеансе. Когда клиенты MSRP формируют или приобретают сертификат, они ДОЛЖНЫ обеспечить, чтобы subjectAltName имел запись GeneralName типа uniformResourceIdentifier для каждого URI, соответствующего этому клиенту, и всегда должны включать URI "im:". Ничего страшного, если сертификат содержит другие URI, такие как URI "sip:" или "xmpp:".
MSRP implementors should be aware of a potential attack on MSRP devices that involves placing very large values in the byte-range header field, potentially causing the device to allocate very large memory buffers to hold the message. Implementations SHOULD apply some degree of sanity checking on byte-range values before allocating such buffers.
Реализаторам MSRP следует знать о потенциальной атаке на устройства MSRP, которая заключается в помещении очень больших значений в поле заголовка byte-range, что может заставить устройство выделить очень большие буферы памяти для хранения сообщения. Реализации ДОЛЖНЫ применять некоторую степень проверки разумности значений byte-range перед выделением таких буферов.
