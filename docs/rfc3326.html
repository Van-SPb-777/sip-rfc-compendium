Abstract
Аннотация
For creating services, it is often useful to know why a Session Initiation Protocol (SIP) request was issued. This document defines a header field, Reason, that provides this information. The Reason header field is also intended to be used to encapsulate a final status code in a provisional response. This functionality is needed to resolve the "Heterogeneous Error Response Forking Problem", or HERFP.
Для создания служб часто полезно знать, почему был выдан запрос протокола инициирования сессий (SIP). Настоящий документ определяет поле заголовка Reason, которое предоставляет эту информацию. Поле заголовка Reason также предназначено для инкапсуляции окончательного кода состояния в предварительном ответе. Эта функциональность необходима для решения «Проблемы ветвления неоднородных ответов об ошибках» (Heterogeneous Error Response Forking Problem, HERFP).
1. Introduction
1. Введение
The same SIP [1] request can be issued for a variety of reasons. For example, a SIP CANCEL request can be issued if the call has completed on another branch or was abandoned before answer. While the protocol and system behavior is the same in both cases, namely, alerting will cease, the user interface may well differ. In the second case, the call may be logged as a missed call, while this would not be appropriate if the call was picked up elsewhere.
Один и тот же запрос SIP [1] может быть выдан по различным причинам. Например, запрос CANCEL SIP может быть выдан, если вызов был завершён на другой ветви или был оставлен до ответа. Хотя поведение протокола и системы в обоих случаях одинаково, а именно: оповещение прекращается, — пользовательский интерфейс может существенно различаться. Во втором случае вызов может быть зарегистрирован как пропущенный, тогда как это было бы неуместно, если вызов был принят в другом месте.
Third party call controllers sometimes generate a SIP request upon reception of a SIP response from another dialog. Gateways generate SIP requests after receiving messages from a different protocol than SIP. In both cases the client may be interested in knowing what triggered the SIP request.
Контроллеры вызовов третьей стороны иногда формируют запрос SIP по получении ответа SIP из другого диалога. Шлюзы формируют запросы SIP после получения сообщений из протокола, отличного от SIP. В обоих случаях клиент может быть заинтересован в том, чтобы знать, что инициировало запрос SIP.
SIP responses already offer a means of informing the user of why a request failed. The simple mechanism in this document accomplishes something roughly similar for requests.
Ответы SIP уже предоставляют средство информирования пользователя о том, почему запрос потерпел неудачу. Простой механизм в настоящем документе выполняет примерно то же для запросов.
An INVITE can sometimes be rejected not because the session initiation was declined, but because some aspect of the request was not acceptable. If the INVITE forked and resulted in a rejection, the error response may never be forwarded to the client unless all the other branches also reject the request. This problem is known as the "Heterogeneous Error Response Forking Problem", or HERFP. It is foreseen that a solution to this problem may involve encapsulating the final error response in a provisional response. The Reason header field is a candidate to be used for such encapsulation. Initially, the Reason header field defined here appears to be most useful for BYE and CANCEL requests, but it can appear in any request within a dialog, in any CANCEL request and in any response whose status code explicitly allows the presence of this header field.
INVITE иногда может быть отклонён не потому, что инициирование сессии было отклонено, а потому что некоторый аспект запроса был неприемлем. Если INVITE был разветвлён и привёл к отклонению, ответ об ошибке может так и не быть переслан клиенту, если только все остальные ветви также не отклонят запрос. Эта проблема известна как «Проблема ветвления неоднородных ответов об ошибках» (HERFP). Предполагается, что решение этой проблемы может включать инкапсуляцию окончательного ответа об ошибке в предварительный ответ. Поле заголовка Reason является кандидатом для использования при такой инкапсуляции. Изначально определённое здесь поле заголовка Reason кажется наиболее полезным для запросов BYE и CANCEL, но оно может появляться в любом запросе внутри диалога, в любом запросе CANCEL и в любом ответе, код состояния которого явно допускает присутствие этого поля заголовка.
Note that the Reason header field is usually not needed in responses because the status code and the reason phrase already provide sufficient information.
Обратите внимание, что поле заголовка Reason обычно не нужно в ответах, поскольку код состояния и фраза причины уже предоставляют достаточную информацию.
Clients and servers are free to ignore this header field. It has no impact on protocol processing.
Клиенты и серверы свободны игнорировать это поле заголовка. Оно не влияет на обработку протокола.

2. The Reason Header Field
2. Поле заголовка Reason
The Reason header field MAY appear in any request within a dialog, in any CANCEL request and in any response whose status code explicitly allows the presence of this header field. The syntax of the header field follows the standard SIP parameter syntax.
Поле заголовка Reason МОЖЕТ появляться в любом запросе внутри диалога, в любом запросе CANCEL и в любом ответе, код состояния которого явно допускает присутствие этого поля заголовка. Синтаксис поля заголовка следует стандартному синтаксису параметров SIP.
Reason = "Reason" HCOLON reason-value *(COMMA reason-value) reason-value = protocol *(SEMI reason-params) protocol = "SIP" / "Q.850" / token reason-params = protocol-cause / reason-text
Reason = "Reason" HCOLON reason-value *(COMMA reason-value) reason-value = protocol *(SEMI reason-params) protocol = "SIP" / "Q.850" / token reason-params = protocol-cause / reason-text
/ reason-extension
/ reason-extension
protocol-cause = "cause" EQUAL cause cause = 1*DIGIT reason-text = "text" EQUAL quoted-string reason-extension = generic-param
protocol-cause = "cause" EQUAL cause cause = 1*DIGIT reason-text = "text" EQUAL quoted-string reason-extension = generic-param
The following values for the protocol field have been defined:
Определены следующие значения для поля protocol:
SIP: The cause parameter contains a SIP status code.
SIP — параметр cause содержит код состояния SIP.
Q.850: The cause parameter contains an ITU-T Q.850 cause value in decimal representation.
Q.850 — параметр cause содержит значение причины ITU-T Q.850 в десятичном представлении.
Examples are:
Примеры:
Reason: SIP ;cause=200 ;text="Call completed elsewhere" Reason: Q.850 ;cause=16 ;text="Terminated" Reason: SIP ;cause=600 ;text="Busy Everywhere" Reason: SIP ;cause=580 ;text="Precondition Failure"
Reason: SIP ;cause=200 ;text="Call completed elsewhere" Reason: Q.850 ;cause=16 ;text="Terminated" Reason: SIP ;cause=600 ;text="Busy Everywhere" Reason: SIP ;cause=580 ;text="Precondition Failure"
Proxies generating a CANCEL request upon reception of a CANCEL from the previous hop that contains a Reason header field SHOULD copy it into the new CANCEL request.
Прокси, формирующие запрос CANCEL по получении CANCEL от предыдущего перехода, содержащего поле заголовка Reason, СЛЕДУЕТ копировать его в новый запрос CANCEL.
In normal SIP operation, a SIP status code in a response provides the client with information about the request that triggered the response, the session parameters, or the user. For example, a 405 (Method not allowed) response indicates that the request contained an unsupported method. A 488 (Not Acceptable Here) indicates that the session parameters are unacceptable and a 486 (Busy Here) provides information about the status of the user.
При нормальной работе SIP код состояния SIP в ответе предоставляет клиенту информацию о запросе, который вызвал ответ, о параметрах сессии или о пользователе. Например, ответ 405 (Method not allowed) указывает, что запрос содержал неподдерживаемый метод. Ответ 488 (Not Acceptable Here) указывает, что параметры сессии неприемлемы, а ответ 486 (Busy Here) предоставляет информацию о состоянии пользователя.
Any SIP status code MAY appear in the Reason header field of a request. However, status codes that provide information about the user and about session parameters are typically useful for implementing services whereas status codes intended to report errors about a request are typically useful for debugging purposes.
Любой код состояния SIP МОЖЕТ появляться в поле заголовка Reason запроса. Однако коды состояния, предоставляющие информацию о пользователе и о параметрах сессии, обычно полезны для реализации служб, тогда как коды состояния, предназначенные для сообщения об ошибках запроса, обычно полезны для целей отладки.
A SIP message MAY contain more than one Reason value (i.e., multiple Reason lines), but all of them MUST have different protocol values (e.g., one SIP and another Q.850). An implementation is free to ignore Reason values that it does not understand.
Сообщение SIP МОЖЕТ содержать более одного значения Reason (то есть несколько строк Reason), но все они ДОЛЖНЫ иметь разные значения protocol (например, одно SIP и другое Q.850). Реализация свободна игнорировать значения Reason, которые она не понимает.
3. Examples
3. Примеры
This section contains a number of examples that illustrate the use of the Reason header field.
Этот раздел содержит несколько примеров, иллюстрирующих использование поля заголовка Reason.
3.1. Call Completed Elsewhere
3.1. Вызов завершён в другом месте
A proxy forks an INVITE request and one of the branches returns a 200 (OK). The forking proxy includes this status code in a Reason header field in the CANCEL request that it sends to the rest of the branches.
Прокси разветвляет запрос INVITE, и одна из ветвей возвращает 200 (OK). Разветвляющий прокси включает этот код состояния в поле заголовка Reason в запросе CANCEL, который он отправляет остальным ветвям.
3.2. Refusing an Offer that Comes in a Response
3.2. Отказ от предложения, пришедшего в ответе
A client sends an empty INVITE and receives an unacceptable offer in a 200 (OK) response. The client sends an ACK with a correctly formatted answer and immediately sends a BYE to terminate the session. The client includes a 488 (Not Acceptable Here) status code in a Reason header field.
Клиент отправляет пустой INVITE и получает неприемлемое предложение в ответе 200 (OK). Клиент отправляет ACK с правильно сформированным ответом и немедленно отправляет BYE для завершения сессии. Клиент включает код состояния 488 (Not Acceptable Here) в поле заголовка Reason.

3.3. Управление вызовом третьей стороной

4. IANA Considerations
4. Вопросы IANA
This document defines a new SIP header field, "Reason", according to Section 27 of RFC 3261.
Настоящий документ определяет новое поле заголовка SIP «Reason» согласно разделу 27 RFC 3261.
Protocol values (and their associated protocol cause) to be used with this header field are registered by the IANA into a new sub-registry under http://www.iana.org/assignments/sip-parameters, labeled "Reason Protocols". Reason protocols MUST refer to either an ITU-T Recommendation number, an IETF protocol name or the recognized protocol identifier from another standardization organization. Protocol cause describes the source of the 'cause' field in the Reason header field.
Значения протокола (и связанная с ними причина протокола) для использования с этим полем заголовка регистрируются IANA в новом подреестре по адресу http://www.iana.org/assignments/sip-parameters под названием «Reason Protocols». Протоколы причин ДОЛЖНЫ ссылаться либо на номер рекомендации ITU-T, либо на имя протокола IETF, либо на признанный идентификатор протокола другой организации по стандартизации. Причина протокола описывает источник поля «cause» в поле заголовка Reason.

5. Security Considerations
5. Вопросы безопасности
Spoofing or removing the Reason header field from a response in a HERFP scenario can make it impossible for a client to update properly its previous request, making therefore session establishment impossible. Thus, it is RECOMMENDED that this header field is protected by a suitable integrity mechanism.
Подделка или удаление поля заголовка Reason из ответа в сценарии HERFP может сделать невозможным для клиента правильное обновление своего предыдущего запроса, делая тем самым установление сессии невозможным. Поэтому РЕКОМЕНДУЕТСЯ, чтобы это поле заголовка было защищено подходящим механизмом целостности.
