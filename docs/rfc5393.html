Abstract
Аннотация
This document normatively updates RFC 3261, the Session Initiation Protocol (SIP), to address a security vulnerability identified in SIP proxy behavior. This vulnerability enables an attack against SIP networks where a small number of legitimate, even authorized, SIP requests can stimulate massive amounts of proxy-to-proxy traffic.
Настоящий документ нормативно обновляет RFC 3261 (протокол инициирования сессий, SIP) в части устранения уязвимости безопасности, выявленной в поведении прокси SIP. Эта уязвимость позволяет проводить атаку на сети SIP, при которой небольшое число легитимных и даже авторизованных запросов SIP порождает огромные объёмы трафика между прокси.
This document strengthens loop-detection requirements on SIP proxies when they fork requests (that is, forward a request to more than one destination). It also corrects and clarifies the description of the loop-detection algorithm such proxies are required to implement. Additionally, this document defines a Max-Breadth mechanism for limiting the number of concurrent branches pursued for any given request.
Настоящий документ усиливает требования к обнаружению петель у прокси SIP при разветвлении запросов (то есть при пересылке запроса более чем в один пункт назначения). Он также исправляет и уточняет описание алгоритма обнаружения петель, который такие прокси обязаны реализовывать. Кроме того, документ определяет механизм Max-Breadth, ограничивающий число одновременных ветвей, обслуживаемых для любого заданного запроса.
1. Introduction
1. Введение
Interoperability testing uncovered a vulnerability in the behavior of forking SIP proxies as defined in [RFC3261]. This vulnerability can be leveraged to cause a small number of valid SIP requests to generate an extremely large number of proxy-to-proxy messages. A version of this attack demonstrates fewer than ten messages stimulating potentially 2^71 messages.
Испытания на совместимость выявили уязвимость в поведении разветвляющих прокси SIP, определённых в [RFC3261]. Эту уязвимость можно использовать, чтобы небольшое число допустимых запросов SIP порождало чрезвычайно большое число сообщений между прокси. Один из вариантов этой атаки демонстрирует, что менее десяти сообщений порождают потенциально 2^71 сообщений.
This document specifies normative changes to the SIP protocol to address this vulnerability. According to this update, when a SIP proxy forks a request to more than one destination, it is required to ensure it is not participating in a request loop.
Настоящий документ задаёт нормативные изменения протокола SIP для устранения этой уязвимости. Согласно настоящему обновлению, когда прокси SIP разветвляет запрос более чем в один пункт назначения, он обязан убедиться, что не участвует в петле запроса.
This normative update alone is insufficient to protect against crafted variations of the attack described here involving multiple Addresses of Record (AORs). To further address the vulnerability, this document defines the Max-Breadth mechanism to limit the total number of concurrent branches caused by a forked SIP request. The mechanism only limits concurrency. It does not limit the total number of branches a request can traverse over its lifetime.
Одно лишь это нормативное обновление недостаточно для защиты от целенаправленных вариантов описанной здесь атаки с участием множества адресов записи (AOR). Чтобы дополнительно устранить уязвимость, настоящий документ определяет механизм Max-Breadth, ограничивающий общее число одновременных ветвей, порождаемых разветвлённым запросом SIP. Механизм ограничивает только одновременность. Он не ограничивает общее число ветвей, которые запрос может пройти за всё время своего существования.
The mechanisms in this update will protect against variations of the attack described here that use a small number of resources, including most unintentional self-inflicted variations that occur through accidental misconfiguration. However, an attacker with access to a sufficient number of distinct resources will still be able to stimulate a very large number of messages. The number of concurrent messages will be limited by the Max-Breadth mechanism, so the entire set will be spread out over a long period of time, giving operators better opportunity to detect the attack and take corrective measures outside the protocol. Future protocol work is needed to prevent this form of the attack.
Механизмы настоящего обновления защищают от вариантов описанной здесь атаки, которые используют небольшое число ресурсов, включая большинство непреднамеренных вариантов, возникающих из-за случайной ошибки конфигурации. Однако злоумышленник, имеющий доступ к достаточному числу различных ресурсов, всё ещё сможет породить очень большое число сообщений. Число одновременных сообщений будет ограничено механизмом Max-Breadth, поэтому весь набор окажется растянут на долгий период времени, давая операторам лучшую возможность обнаружить атаку и принять корректирующие меры вне протокола. Для предотвращения этой формы атаки требуется дальнейшая работа над протоколом.

3. Vulnerability: Leveraging Forking to Flood a Network
3. Уязвимость: использование разветвления для затопления сети
This section describes setting up an attack with a simplifying assumption: that two accounts on each of two different RFC 3261 compliant proxy/registrar servers that do not perform loop detection are available to an attacker. This assumption is not necessary for the attack but makes representing the scenario simpler. The same attack can be realized with a single account on a single server. Consider two proxy/registrar services, P1 and P2, and four Addresses of Record, a@P1, b@P1, a@P2, and b@P2. Using normal REGISTER requests, establish bindings to these AORs as follows (non-essential details elided):
В этом разделе описывается подготовка атаки при упрощающем допущении: в распоряжении злоумышленника есть по две учётные записи на каждом из двух различных серверов прокси/регистратора, совместимых с RFC 3261 и не выполняющих обнаружение петель. Для атаки это допущение не обязательно, но оно упрощает изложение сценария. Та же атака может быть реализована с одной учётной записью на одном сервере. Рассмотрим две службы прокси/регистратора, P1 и P2, и четыре адреса записи: a@P1, b@P1, a@P2 и b@P2. Обычными запросами REGISTER создадим привязки для этих AOR следующим образом (несущественные подробности опущены):
REGISTER sip:P1 SIP/2.0 To: <sip:a@P1> Contact: <sip:a@P2>, <sip:b@P2> REGISTER sip:P1 SIP/2.0 To: <sip:b@P1> Contact: <sip:a@P2>, <sip:b@P2> REGISTER sip:P2 SIP/2.0 To: <sip:a@P2> Contact: <sip:a@P1>, <sip:b@P1> REGISTER sip:P2 SIP/2.0 To: <sip:b@P2> Contact: <sip:a@P1>, <sip:b@P1>
REGISTER sip:P1 SIP/2.0 To: <sip:a@P1> Contact: <sip:a@P2>, <sip:b@P2> REGISTER sip:P1 SIP/2.0 To: <sip:b@P1> Contact: <sip:a@P2>, <sip:b@P2> REGISTER sip:P2 SIP/2.0 To: <sip:a@P2> Contact: <sip:a@P1>, <sip:b@P1> REGISTER sip:P2 SIP/2.0 To: <sip:b@P2> Contact: <sip:a@P1>, <sip:b@P1>
With these bindings in place, introduce an INVITE request to any of the four AORs, say a@P1. This request will fork to two requests handled by P2, which will fork to four requests handled by P1, which will fork to eight messages handled by P2, and so on. This message flow is represented in Figure 1.
При наличии этих привязок отправим запрос INVITE на любой из четырёх AOR, скажем a@P1. Этот запрос разветвится на два запроса, обрабатываемых P2, которые разветвятся на четыре запроса, обрабатываемых P1, которые разветвятся на восемь сообщений, обрабатываемых P2, и так далее. Этот поток сообщений представлен на рисунке 1.

Requests will continue to propagate down this tree until Max-Forwards reaches zero. If the endpoint and two proxies involved follow RFC 3261 recommendations, the tree will be 70 rows deep, representing 2^71-1 requests. The actual number of messages may be much larger if the time to process the entire tree's worth of requests is longer than Timer C at either proxy. In this case, a storm of 408 responses and/or a storm of CANCEL requests will also be propagating through the tree along with the INVITE requests. Remember that there are only two proxies involved in this scenario - each having to hold the state for all the transactions it sees (at least 2^70 simultaneously active transactions near the end of the scenario).
Запросы будут продолжать распространяться по этому дереву, пока Max-Forwards не достигнет нуля. Если оконечная точка и два участвующих прокси следуют рекомендациям RFC 3261, дерево будет иметь глубину 70 ярусов, что соответствует 2^71-1 запросам. Фактическое число сообщений может быть гораздо больше, если время обработки всего дерева запросов превышает Timer C на любом из прокси. В этом случае по дереву вместе с запросами INVITE будет распространяться также шторм ответов 408 и/или шторм запросов CANCEL. Напомним, что в этом сценарии участвуют всего два прокси, и каждому приходится хранить состояние всех транзакций, которые он видит (по крайней мере 2^70 одновременно активных транзакций ближе к концу сценария).
The attack can be simplified to one account at one server if the service can be convinced that contacts with varying attributes (parameters, schemes, embedded headers) are sufficiently distinct, and these parameters are not used as part of AOR comparisons when forwarding a new request. Since RFC 3261 mandates that all URI parameters must be removed from a URI before looking it up in a location service and that the URIs from the Contact header field are compared using URI equality, the following registration should be sufficient to set up this attack using a single REGISTER request to a single account:
Атаку можно свести к одной учётной записи на одном сервере, если службу удаётся убедить, что контакты с различающимися атрибутами (параметрами, схемами, встроенными заголовками) достаточно различны, а эти параметры не используются при сравнении AOR при пересылке нового запроса. Поскольку RFC 3261 предписывает удалять все параметры URI из URI перед его поиском в службе определения местоположения и сравнивать URI из поля заголовка Contact по равенству URI, для подготовки этой атаки достаточно следующей регистрации одним запросом REGISTER для одной учётной записи:
REGISTER sip:P1 SIP/2.0 To: <sip:a@P1> Contact: <sip:a@P1;unknown-param=whack>,<sip:a@P1;unknown-param=thud>
REGISTER sip:P1 SIP/2.0 To: <sip:a@P1> Contact: <sip:a@P1;unknown-param=whack>,<sip:a@P1;unknown-param=thud>
This attack was realized in practice during one of the SIP Interoperability Test (SIPit) sessions. The scenario was extended to include more than two proxies, and the participating proxies all limited Max-Forwards to be no larger than 20. After a handful of messages to construct the attack, the participating proxies began bombarding each other. Extrapolating from the several hours the experiment was allowed to run, the scenario would have completed in just under 10 days. Had the proxies used the RFC 3261 recommended Max-Forwards value of 70, and assuming they performed linearly as the state they held increased, it would have taken 3 trillion years to complete the processing of the single INVITE request that initiated the attack. It is interesting to note that a few proxies rebooted during the scenario and rejoined in the attack when they restarted (as long as they maintained registration state across reboots). This points out that if this attack were launched on the Internet at large, it might require coordination among all the affected elements to stop it.
Эта атака была реализована на практике в ходе одной из сессий испытаний на совместимость SIP (SIPit). Сценарий был расширен до более чем двух прокси, и все участвовавшие прокси ограничивали Max-Forwards значением не больше 20. После нескольких сообщений, потребовавшихся для построения атаки, участвовавшие прокси начали бомбардировать друг друга. Если экстраполировать несколько часов, в течение которых разрешалось проводить эксперимент, сценарий завершился бы чуть менее чем за 10 дней. Если бы прокси использовали рекомендуемое RFC 3261 значение Max-Forwards, равное 70, и при допущении, что они работают линейно по мере роста хранимого состояния, на обработку единственного запроса INVITE, инициировавшего атаку, ушло бы 3 триллиона лет. Интересно отметить, что несколько прокси перезагрузились во время сценария и после перезапуска вновь включились в атаку (поскольку сохраняли состояние регистрации между перезагрузками). Это показывает, что если бы такая атака была запущена в масштабе Интернета, для её остановки могла бы потребоваться координация всех затронутых элементов.
Loop detection, as specified in this document, at any of the proxies in the scenarios described so far would have stopped the attack immediately. (If all the proxies involved implemented this loop detection, the total number of stimulated messages in the first scenario described would be reduced to 14; in the variation involving one server, the number of stimulated messages would be reduced to 10.) However, there is a variant of the attack that uses multiple AORs where loop detection alone is insufficient protection. In this variation, each participating AOR forks to all the other participating AORs. For small numbers of participating AORs (10, for example), paths through the resulting tree will not loop until very large numbers of messages have been generated. Acquiring a sufficient number of AORs to launch such an attack on networks currently available is quite feasible.
Обнаружение петель, как оно определено в настоящем документе, на любом из прокси в описанных до сих пор сценариях немедленно остановило бы атаку. (Если бы все участвующие прокси реализовали это обнаружение петель, общее число порождённых сообщений в первом описанном сценарии сократилось бы до 14; в варианте с одним сервером число порождённых сообщений сократилось бы до 10.) Однако существует вариант атаки, использующий несколько AOR, при котором одного обнаружения петель недостаточно для защиты. В этом варианте каждый участвующий AOR разветвляется на все остальные участвующие AOR. При небольшом числе участвующих AOR (например, 10) пути по получающемуся дереву не образуют петлю, пока не будет порождено очень большое число сообщений. Получить достаточное число AOR для запуска такой атаки в нынешних сетях вполне осуществимо.
In this scenario, requests will often take many hops to complete a loop, and there are a very large number of different loops that will occur during the attack. In fact, if N is the number of participating AORs, and provided N is less than or equal to Max- Forwards, the amount of traffic generated by the attack is greater than N!, even if all proxies involved are performing loop detection.
В этом сценарии запросам часто требуется много переходов, чтобы замкнуть петлю, и во время атаки возникает очень большое число различных петель. Фактически, если N — число участвующих AOR и при условии, что N не превышает Max-Forwards, объём трафика, порождённого атакой, больше N!, даже если все участвующие прокси выполняют обнаружение петель.
Suppose we have a set of N AORs, all of which are set up to fork to the entire set. For clarity, assume AOR 1 is where the attack begins. Every permutation of the remaining N-1 AORs will play out, defining (N-1)! distinct paths, without repeating any AOR. Then, each of these paths will fork N ways one last time, and a loop will be detected on each of these branches. These final branches alone total N! requests ((N-1)! paths, with N forks at the end of each path).
Предположим, имеется множество из N AOR, каждый из которых настроен на разветвление на всё множество. Для наглядности будем считать, что атака начинается с AOR 1. Реализуются все перестановки остальных N-1 AOR, задавая (N-1)! различных путей без повторения какого-либо AOR. Затем каждый из этих путей в последний раз разветвляется на N направлений, и на каждой из этих ветвей обнаруживается петля. Только эти последние ветви в сумме дают N! запросов ((N-1)! путей с N разветвлениями в конце каждого пути).

In a network where all proxies are performing loop detection, an attacker is still afforded rapidly increasing returns on the number of AORs they are able to leverage. The Max-Breadth mechanism defined in this document is designed to limit the effectiveness of this variation of the attack. In all of the scenarios, it is important to notice that at each forking proxy, an additional branch could be added pointing to a single victim (that might not even be a SIP-aware element), resulting in a massive amount of traffic being directed towards the victim from potentially as many sources as there are AORs participating in the attack.
В сети, где все прокси выполняют обнаружение петель, злоумышленник всё равно получает быстро растущую отдачу от числа AOR, которые ему удаётся задействовать. Механизм Max-Breadth, определённый в настоящем документе, призван ограничить эффективность этого варианта атаки. Во всех сценариях важно отметить, что на каждом разветвляющем прокси можно добавить дополнительную ветвь, указывающую на одну жертву (которая может даже не быть элементом, поддерживающим SIP), в результате чего на жертву направляется огромный объём трафика потенциально из стольких источников, сколько AOR участвует в атаке.
4. Updates to RFC 3261
4. Обновления RFC 3261
4.1. Strengthening the Requirement to Perform Loop Detection
4.1. Усиление требования выполнять обнаружение петель
The following requirements mitigate the risk of a proxy falling victim to the attack described in this document.
Следующие требования снижают риск того, что прокси станет жертвой описанной в настоящем документе атаки.
When a SIP proxy forks a particular request to more than one location, it MUST ensure that request is not looping through this proxy. It is RECOMMENDED that proxies meet this requirement by performing the loop-detection steps defined in this document.
Когда прокси SIP разветвляет конкретный запрос более чем в одно место, он ОБЯЗАН убедиться, что этот запрос не образует петлю через данный прокси. РЕКОМЕНДУЕТСЯ, чтобы прокси выполняли это требование путём выполнения шагов обнаружения петель, определённых в настоящем документе.
The requirement to use this document's refinement of the loop- detection algorithm from RFC 3261 is set at should-strength to allow for future Standards-Track mechanisms that will allow a proxy to determine it is not looping. For example, a proxy forking to destinations established using the sip-outbound mechanism [OUTBOUND] would know those branches will not loop.
Требование использовать уточнённый в настоящем документе алгоритм обнаружения петель из RFC 3261 задано на уровне «следует», чтобы допустить будущие механизмы уровня стандартов, позволяющие прокси установить, что петли нет. Например, прокси, разветвляющий запрос на пункты назначения, установленные с помощью механизма sip-outbound [OUTBOUND], знал бы, что эти ветви не образуют петлю.
A SIP proxy forwarding a request to only one location MAY perform loop detection but is not required to. When forwarding to only one location, the amplification risk being exploited is not present, and the Max-Forwards mechanism will protect the network to the extent it was designed (always keep in mind the constant multiplier due to exhausting Max-Forwards while not forking). A proxy is not required to perform loop detection when forwarding a request to a single location even if it happened to have previously forked that request (and performed loop detection) in its progression through the network.
Прокси SIP, пересылающий запрос только в одно место, МОЖЕТ выполнять обнаружение петель, но не обязан. При пересылке только в одно место риск усиления, которым пользуются злоумышленники, отсутствует, а механизм Max-Forwards защитит сеть в той мере, в какой он для этого предназначен (всегда помните о постоянном множителе, возникающем из-за исчерпания Max-Forwards без разветвления). Прокси не обязан выполнять обнаружение петель при пересылке запроса в единственное место, даже если он ранее разветвлял этот запрос (и выполнял обнаружение петель) по мере его продвижения по сети.

4.2.1. Update to Section 16.6

The proxy MUST insert a Via header field value into the copy before the existing Via header field values. The construction of this value follows the same guidelines of Section 8.1.1.7. This implies that the proxy will compute its own branch parameter, which will be globally unique for that branch, and will contain the requisite magic cookie. Note that following only the guidelines in Section 8.1.1.7 will result in a branch parameter that will be different for different instances of a spiraled or looped request through a proxy.

Это означает, что прокси вычислит собственный параметр branch, который будет глобально уникальным для этой ветви и будет содержать требуемый magic cookie. Отметим, что следование только указаниям раздела 8.1.1.7 даст параметр branch, который будет различаться для разных экземпляров запроса, закрученного спиралью или образующего петлю через прокси.
Proxies required to perform loop detection by RFC 5393 have an additional constraint on the value they place in the Via header field. Such proxies SHOULD create a branch value separable into two parts in any implementation-dependent way.
Прокси, обязанные выполнять обнаружение петель согласно RFC 5393, имеют дополнительное ограничение на значение, которое они помещают в поле заголовка Via. Таким прокси СЛЕДУЕТ создавать значение branch, разделимое на две части любым зависящим от реализации способом.
The remainder of this section's description assumes the existence of these two parts. If a proxy chooses to employ some other mechanism, it is the implementer's responsibility to verify that the detection properties defined by the requirements placed on these two parts are achieved.
Остальная часть описания настоящего раздела предполагает существование этих двух частей. Если прокси решает применить какой-либо иной механизм, ответственность за проверку того, что свойства обнаружения, заданные требованиями к этим двум частям, достигнуты, лежит на реализаторе.
The first part of the branch value MUST satisfy the constraints of Section 8.1.1.7. The second part is used to perform loop detection and distinguish loops from spirals.
Первая часть значения branch ОБЯЗАНА удовлетворять ограничениям раздела 8.1.1.7. Вторая часть используется для обнаружения петель и для отличия петель от спиралей.
This second part MUST vary with any field used by the location service logic in determining where to retarget or forward this request. This is necessary to distinguish looped requests from spirals by allowing the proxy to recognize if none of the values affecting the processing of the request have changed. Hence, the second part MUST depend at least on the received Request-URI and any Route header field values used when processing the received request. Implementers need to take care to include all fields used by the location service logic in that particular implementation.
Эта вторая часть ОБЯЗАНА различаться при любом поле, используемом логикой службы определения местоположения при определении того, куда перенацелить или переслать этот запрос. Это необходимо, чтобы отличать зацикленные запросы от спиралей, позволяя прокси распознать, что ни одно из значений, влияющих на обработку запроса, не изменилось. Следовательно, вторая часть ОБЯЗАНА зависеть как минимум от полученного Request-URI и любых значений поля заголовка Route, использованных при обработке полученного запроса. Реализаторам нужно позаботиться о включении всех полей, которые используются логикой службы определения местоположения в данной конкретной реализации.
This second part MUST NOT vary with the request method. CANCEL and non-200 ACK requests MUST have the same branch parameter value as the corresponding request they cancel or acknowledge. This branch parameter value is used in correlating those requests at the server handling them (see Sections 17.2.3 and 9.2).
Эта вторая часть НЕ ДОЛЖНА зависеть от метода запроса. Запросы CANCEL и запросы ACK, не относящиеся к ответу 200, ОБЯЗАНЫ иметь то же значение параметра branch, что и соответствующий запрос, который они отменяют или подтверждают. Это значение параметра branch используется для соотнесения таких запросов на сервере, который их обрабатывает (см. разделы 17.2.3 и 9.2).
4.2.2. Update to Section 16.3
4.2.2. Обновление раздела 16.3
This section replaces all of item 4 in Section 16.3 of RFC 3261 (item 4 appears on page 95 of RFC 3261). 4. Loop-Detection Check
Настоящий раздел заменяет весь пункт 4 раздела 16.3 RFC 3261 (пункт 4 находится на странице 95 RFC 3261). 4. Проверка обнаружения петель
Proxies required to perform loop detection by RFC 5393 MUST perform the following loop-detection test before forwarding a request. Each Via header field value in the request whose sent-by value matches a value placed into previous requests by this proxy MUST be inspected for the "second part" defined in Section 4.2.1 of RFC 5393. This second part will not be present if the message was not forked when that Via header field value was added. If the second field is present, the proxy MUST perform the second-part calculation described in Section 4.2.1 of RFC 5393 on this request and compare the result to the value from the Via header field. If these values are equal, the request has looped and the proxy MUST reject the request with a 482 (Loop Detected) response. If the values differ, the request is spiraling and processing continues to the next step.
Прокси, обязанные выполнять обнаружение петель согласно RFC 5393, ОБЯЗАНЫ перед пересылкой запроса выполнить следующую проверку обнаружения петель. Каждое значение поля заголовка Via в запросе, у которого значение sent-by совпадает со значением, помещённым этим прокси в предыдущие запросы, ОБЯЗАНО быть проверено на наличие «второй части», определённой в разделе 4.2.1 RFC 5393. Эта вторая часть будет отсутствовать, если сообщение не разветвлялось в момент добавления этого значения поля заголовка Via. Если второе поле присутствует, прокси ОБЯЗАН выполнить для этого запроса вычисление второй части, описанное в разделе 4.2.1 RFC 5393, и сравнить результат со значением из поля заголовка Via. Если эти значения равны, запрос образовал петлю, и прокси ОБЯЗАН отклонить запрос ответом 482 (Loop Detected). Если значения различаются, запрос закручивается спиралью, и обработка переходит к следующему шагу.
4.2.3. Impact of Loop Detection on Overall Network Performance
4.2.3. Влияние обнаружения петель на общую производительность сети
These requirements and the recommendation to use the loop-detection mechanisms in this document make the favorable trade of exponential message growth for work that is, at worst, order n^2 as a message crosses n proxies. Specifically, this work is order m*n where m is the number of proxies in the path that fork the request to more than one location. In practice, m is expected to be small.
Эти требования и рекомендация использовать механизмы обнаружения петель из настоящего документа обеспечивают выгодный обмен экспоненциального роста числа сообщений на работу, которая в худшем случае имеет порядок n^2 при прохождении сообщением n прокси. В частности, эта работа имеет порядок m*n, где m — число прокси в пути, разветвляющих запрос более чем в одно место. На практике ожидается, что m невелико.
The loop-detection algorithm expressed in this document requires a proxy to inspect each Via element in a received request. In the worst case, where a message crosses N proxies, each of which loop detect, proxy k does k inspections, and the overall number of inspections spread across the proxies handling this request is the sum of k from k=1 to k=N which is N(N+1)/2.
Выраженный в настоящем документе алгоритм обнаружения петель требует, чтобы прокси проверял каждый элемент Via в полученном запросе. В худшем случае, когда сообщение проходит N прокси, каждый из которых выполняет обнаружение петель, прокси k выполняет k проверок, а общее число проверок, распределённых по прокси, обрабатывающим этот запрос, равно сумме k от k=1 до k=N, то есть N(N+1)/2.
4.2.4. Note to Implementers
4.2.4. Примечание для реализаторов
A common way to create the second part of the branch parameter value when forking a request is to compute a hash over the concatenation of the Request-URI, any Route header field values used during processing the request, and any other values used by the location service logic while processing this request. The hash should be chosen so that there is a low probability that two distinct sets of these parameters will collide. Because the maximum number of inputs that need to be compared is 70, the chance of a collision is low even with a relatively small hash value, such as 32 bits. CRC-32c as specified in [RFC4960] is a specific acceptable function, as is MD5 [RFC1321]. Note that MD5 is being chosen purely for non-cryptographic properties. An attacker who can control the inputs in order to produce a hash collision can attack the connection in a variety of other ways. When forming the second part using a hash, implementations SHOULD include at least one field in the input to the hash that varies between different transactions attempting to reach the same destination to avoid repeated failure should the hash collide. The Call-ID and CSeq fields would be good inputs for this purpose.
Распространённый способ создания второй части значения параметра branch при разветвлении запроса состоит в вычислении хеша по конкатенации Request-URI, любых значений поля заголовка Route, использованных при обработке запроса, и любых других значений, используемых логикой службы определения местоположения при обработке этого запроса. Хеш следует выбирать так, чтобы вероятность совпадения двух различных наборов этих параметров была мала. Поскольку максимальное число входных наборов, которые нужно сравнить, равно 70, вероятность совпадения мала даже при сравнительно небольшом значении хеша, например 32 битах. CRC-32c, определённый в [RFC4960], является конкретной приемлемой функцией, как и MD5 [RFC1321]. Отметим, что MD5 выбирается исключительно из-за некриптографических свойств. Злоумышленник, который может управлять входными данными, чтобы получить совпадение хеша, способен атаковать соединение множеством других способов. При формировании второй части с помощью хеша реализациям СЛЕДУЕТ включать во входные данные хеша хотя бы одно поле, различающееся между разными транзакциями, пытающимися достичь одного и того же пункта назначения, чтобы избежать повторяющихся отказов при совпадении хеша. Для этой цели хорошими входными данными были бы поля Call-ID и CSeq.
A common point of failure to interoperate at SIPit events has been due to parsers objecting to the contents of another element's Via header field values when inspecting the Via stack for loops. Implementers need to take care to avoid making assumptions about the format of another element's Via header field value beyond the basic constraints placed on that format by RFC 3261. In particular, parsing a header field value with unknown parameter names, parameters with no values, or parameter values with or without quoted strings must not cause an implementation to fail.
Частой причиной несовместимости на мероприятиях SIPit было то, что синтаксические анализаторы возражали против содержимого значений полей заголовка Via другого элемента при проверке стека Via на наличие петель. Реализаторам нужно позаботиться о том, чтобы не делать предположений о формате значения поля заголовка Via другого элемента сверх базовых ограничений, накладываемых на этот формат RFC 3261. В частности, разбор значения поля заголовка с неизвестными именами параметров, параметрами без значений или значениями параметров с кавычками и без них не должен приводить к отказу реализации.
Removing, obfuscating, or in any other way modifying the branch parameter values in Via header fields in a received request before forwarding it removes the ability for the node that placed that branch parameter into the message to perform loop detection. If two elements in a loop modify branch parameters this way, a loop can never be detected.
Удаление, запутывание или любое иное изменение значений параметра branch в полях заголовка Via полученного запроса перед его пересылкой лишает узел, поместивший этот параметр branch в сообщение, возможности выполнять обнаружение петель. Если два элемента в петле изменяют параметры branch таким образом, петля никогда не будет обнаружена.
5. Max-Breadth
5. Max-Breadth
5.1. Overview
5.1. Обзор
The Max-Breadth mechanism defined here limits the total number of concurrent branches caused by a forked SIP request. With this mechanism, all proxyable requests are assigned a positive integral Max-Breadth value, which denotes the maximum number of concurrent branches this request may spawn through parallel forking as it is forwarded from its current point. When a proxy forwards a request, its Max-Breadth value is divided among the outgoing requests. In turn, each of the forwarded requests has a limit on how many concurrent branches it may spawn. As branches complete, their portion of the Max-Breadth value becomes available for subsequent branches, if needed. If there is insufficient Max-Breadth to carry out a desired parallel fork, a proxy can return the 440 (Max-Breadth Exceeded) response defined in this document.
Определённый здесь механизм Max-Breadth ограничивает общее число одновременных ветвей, порождённых разветвлённым запросом SIP. Согласно этому механизму всем проксируемым запросам назначается положительное целое значение Max-Breadth, обозначающее максимальное число одновременных ветвей, которые этот запрос может породить путём параллельного разветвления при пересылке из текущей точки. Когда прокси пересылает запрос, его значение Max-Breadth делится между исходящими запросами. В свою очередь каждый из пересланных запросов имеет ограничение на число одновременных ветвей, которые он может породить. По мере завершения ветвей их доля значения Max-Breadth становится доступной для последующих ветвей, если это необходимо. Если Max-Breadth недостаточно для выполнения желаемого параллельного разветвления, прокси может вернуть определённый в настоящем документе ответ 440 (Max-Breadth Exceeded).
This mechanism operates independently from Max-Forwards. Max- Forwards limits the depth of the tree a request may traverse as it is forwarded from its origination point to each destination it is forked to. As Section 3 shows, the number of branches in a tree of even limited depth can be made large (exponential with depth) by leveraging forking. Each such branch has a pair of SIP transaction state machines associated with it. The Max-Breadth mechanism limits the number of branches that are active (those that have running transaction state machines) at any given point in time.
Этот механизм работает независимо от Max-Forwards. Max-Forwards ограничивает глубину дерева, которое запрос может пройти при пересылке от точки своего возникновения к каждому пункту назначения, на который он разветвляется. Как показано в разделе 3, число ветвей в дереве даже ограниченной глубины можно сделать большим (экспоненциальным по глубине), используя разветвление. С каждой такой ветвью связана пара конечных автоматов состояния транзакций SIP. Механизм Max-Breadth ограничивает число ветвей, которые активны (то есть имеют работающие конечные автоматы состояния транзакций) в любой заданный момент времени.
Max-Breadth does not prevent forking. It only limits the number of concurrent parallel forked branches. In particular, a Max-Breadth of 1 restricts a request to pure serial forking rather than restricting it from being forked at all.
Max-Breadth не препятствует разветвлению. Он ограничивает только число одновременных параллельно разветвлённых ветвей. В частности, Max-Breadth, равный 1, ограничивает запрос чисто последовательным разветвлением, а не запрещает разветвлять его вообще.
A client receiving a 440 (Max-Breadth Exceeded) response can infer that its request did not reach all possible destinations. Recovery options are similar to those when receiving a 483 (Too Many Hops) response, and include affecting the routing decisions through whatever mechanisms are appropriate to result in a less broad search, or refining the request itself before submission to make the search space smaller.
Клиент, получивший ответ 440 (Max-Breadth Exceeded), может заключить, что его запрос не достиг всех возможных пунктов назначения. Варианты восстановления аналогичны вариантам при получении ответа 483 (Too Many Hops) и включают влияние на решения о маршрутизации с помощью любых подходящих механизмов, чтобы поиск стал менее широким, либо уточнение самого запроса перед отправкой, чтобы уменьшить пространство поиска.

. . . Max-Breadth and Max-Forwards Working Together
. . . Max-Breadth and Max-Forwards Working Together
5.3. Formal Mechanism
5.3. Формальный механизм
5.3.1. Max-Breadth Header Field
5.3.1. Поле заголовка Max-Breadth
The Max-Breadth header field takes a single positive integer as its value. The Max-Breadth header field value takes no parameters.
Поле заголовка Max-Breadth принимает в качестве значения одно положительное целое число. Значение поля заголовка Max-Breadth не имеет параметров.
5.3.2. Terminology
5.3.2. Терминология
For each "response context" (see Section 16 of [RFC3261]) in a proxy, this mechanism defines two positive integral values: Incoming Max- Breadth and Outgoing Max-Breadth. Incoming Max-Breadth is the value in the Max-Breadth header field in the request that formed the response context. Outgoing Max-Breadth is the sum of the Max-Breadth header field values in all forwarded requests in the response context that have not received a final response.
Для каждого «контекста ответа» (см. раздел 16 [RFC3261]) в прокси этот механизм определяет два положительных целых значения: входящий Max-Breadth и исходящий Max-Breadth. Входящий Max-Breadth — это значение в поле заголовка Max-Breadth запроса, который сформировал контекст ответа. Исходящий Max-Breadth — это сумма значений поля заголовка Max-Breadth во всех пересланных запросах контекста ответа, не получивших окончательного ответа.
5.3.3. Proxy Behavior
5.3.3. Поведение прокси
If a SIP proxy receives a request with no Max-Breadth header field value, it MUST add one, with a value that is RECOMMENDED to be 60. Proxies MUST have a maximum allowable Incoming Max-Breadth value, which is RECOMMENDED to be 60. If this maximum is exceeded in a received request, the proxy MUST overwrite it with a value that SHOULD be no greater than its allowable maximum.
Если прокси SIP получает запрос без значения поля заголовка Max-Breadth, он ОБЯЗАН добавить его со значением, которое РЕКОМЕНДУЕТСЯ брать равным 60. Прокси ОБЯЗАНЫ иметь максимально допустимое значение входящего Max-Breadth, которое РЕКОМЕНДУЕТСЯ брать равным 60. Если этот максимум превышен в полученном запросе, прокси ОБЯЗАН перезаписать его значением, которое НЕ ДОЛЖНО превышать его допустимый максимум.
All proxied requests MUST contain a single Max-Breadth header field value.
Все проксируемые запросы ОБЯЗАНЫ содержать единственное значение поля заголовка Max-Breadth.
SIP proxies MUST NOT allow the Outgoing Max-Breadth to exceed the Incoming Max-Breadth in a given response context.
Прокси SIP НЕ ДОЛЖНЫ допускать, чтобы исходящий Max-Breadth превышал входящий Max-Breadth в данном контексте ответа.
If a SIP proxy determines a response context has insufficient Incoming Max-Breadth to carry out a desired parallel fork, and the proxy is unwilling/unable to compensate by forking serially or sending a redirect, that proxy MUST return a 440 (Max-Breadth Exceeded) response.
Если прокси SIP устанавливает, что входящего Max-Breadth в контексте ответа недостаточно для выполнения желаемого параллельного разветвления, и при этом прокси не желает или не может компенсировать это последовательным разветвлением либо отправкой перенаправления, такой прокси ОБЯЗАН вернуть ответ 440 (Max-Breadth Exceeded).
Notice that these requirements mean a proxy receiving a request with a Max-Breadth of 1 can only fork serially, but it is not required to fork at all -- it can return a 440 instead. Thus, this mechanism is not a tool a user agent can use to force all proxies in the path of a request to fork serially.
Заметим, что из этих требований следует: прокси, получивший запрос со значением Max-Breadth, равным 1, может разветвлять его только последовательно, но вовсе не обязан разветвлять его — вместо этого он может вернуть 440. Таким образом, этот механизм не является инструментом, которым пользовательский агент мог бы заставить все прокси на пути запроса разветвлять его последовательно.
A SIP proxy MAY distribute Max-Breadth in an arbitrary fashion between active branches. A proxy SHOULD NOT use a smaller amount of Max-Breadth than was present in the original request unless the Incoming Max-Breadth exceeded the proxy's maximum acceptable value. A proxy MUST NOT decrement Max-Breadth for each hop or otherwise use it to restrict the "depth" of a request's propagation.
Прокси SIP МОЖЕТ распределять Max-Breadth произвольным образом между активными ветвями. Прокси НЕ СЛЕДУЕТ использовать меньшее значение Max-Breadth, чем было в исходном запросе, если только входящий Max-Breadth не превысил максимально допустимое значение прокси. Прокси НЕ ДОЛЖЕН уменьшать Max-Breadth на каждом переходе или иным образом использовать его для ограничения «глубины» распространения запроса.
5.3.3.1. Reusing Max-Breadth
5.3.3.1. Повторное использование Max-Breadth
Because forwarded requests that have received a final response do not count towards the Outgoing Max-Breadth, whenever a final response arrives, the Max-Breadth that was used on that branch becomes available for reuse. Proxies SHOULD be prepared to reuse this Max- Breadth in cases where there may be elements left in the target-set.
Поскольку пересланные запросы, получившие окончательный ответ, не учитываются в исходящем Max-Breadth, при получении окончательного ответа использованный на этой ветви Max-Breadth становится доступным для повторного использования. Прокси СЛЕДУЕТ быть готовыми повторно использовать этот Max-Breadth в случаях, когда в целевом множестве могут оставаться элементы.
5.3.4. UAC Behavior
5.3.4. Поведение UAC
A User Agent Client (UAC) MAY place a Max-Breadth header field value in outgoing requests. If so, this value is RECOMMENDED to be 60.
Пользовательский агент клиента (UAC) МОЖЕТ помещать значение поля заголовка Max-Breadth в исходящие запросы. В этом случае это значение РЕКОМЕНДУЕТСЯ брать равным 60.
5.3.5. UAS Behavior
5.3.5. Поведение UAS
This mechanism does not affect User Agent Server (UAS) behavior. A UAS receiving a request with a Max-Breadth header field will ignore that field while processing the request.
Этот механизм не влияет на поведение пользовательского агента сервера (UAS). UAS, получивший запрос с полем заголовка Max-Breadth, будет игнорировать это поле при обработке запроса.
5.4. Implementer Notes
5.4. Примечания для реализаторов
5.4.1. Treatment of CANCEL
5.4.1. Обработка CANCEL
Since CANCEL requests are never proxied, a Max-Breadth header field value is meaningless in a CANCEL request. Sending a CANCEL in no way affects the Outgoing Max-Breadth in the associated INVITE response context. Receiving a CANCEL in no way affects the Incoming Max- Breadth of the associated INVITE response context.
Поскольку запросы CANCEL никогда не проксируются, значение поля заголовка Max-Breadth в запросе CANCEL не имеет смысла. Отправка CANCEL никак не влияет на исходящий Max-Breadth в связанном контексте ответа на INVITE. Получение CANCEL никак не влияет на входящий Max-Breadth связанного контекста ответа на INVITE.
5.4.2. Reclamation of Max-Breadth on 2xx Responses
5.4.2. Освобождение Max-Breadth при ответах 2xx
Whether 2xx responses free up Max-Breadth is mostly a moot issue, since proxies are forbidden to start new branches in this case. But, there is one caveat. A proxy may receive multiple 2xx responses for a single forwarded INVITE request. Also, [RFC2543] implementations may send back a 6xx followed by a 2xx on the same branch. Implementations that subtract from the Outgoing Max-Breadth when they receive a 2xx response to an INVITE request must be careful to avoid bugs caused by subtracting multiple times for a single branch.
Вопрос о том, освобождают ли ответы 2xx Max-Breadth, в основном не имеет значения, поскольку прокси запрещено начинать в этом случае новые ветви. Но есть одна оговорка. Прокси может получить несколько ответов 2xx на один пересланный запрос INVITE. Кроме того, реализации [RFC2543] могут отправлять в одной ветви ответ 6xx, за которым следует 2xx. Реализации, которые вычитают из исходящего Max-Breadth при получении ответа 2xx на запрос INVITE, должны быть внимательны, чтобы избежать ошибок, вызванных многократным вычитанием для одной ветви.
5.4.3. Max-Breadth and Automaton UAs
5.4.3. Max-Breadth и автоматические UA
Designers of automaton user agents (UAs) (including B2BUAs, gateways, exploders, and any other element that programmatically sends requests as a result of incoming SIP traffic) should consider whether Max- Breadth limitations should be placed on outgoing requests. For example, it is reasonable to design B2BUAs to carry the Max-Breadth value from incoming requests into requests that are sent as a result. Also, it is reasonable to place Max-Breadth constraints on sets of requests sent by exploders when they may be leveraged in an amplification attack.
Разработчикам автоматических пользовательских агентов (UA), включая B2BUA, шлюзы, «размножители» и любой другой элемент, который программно отправляет запросы в результате входящего трафика SIP, следует рассмотреть, нужно ли накладывать ограничения Max-Breadth на исходящие запросы. Например, разумно проектировать B2BUA так, чтобы они переносили значение Max-Breadth из входящих запросов в запросы, отправляемые в результате. Также разумно накладывать ограничения Max-Breadth на наборы запросов, отправляемых «размножителями», когда их можно задействовать в атаке усиления.
5.5. Parallel and Sequential Forking
5.5. Параллельное и последовательное разветвление
Inherent in the definition of this mechanism is the ability of a proxy to reclaim apportioned Max-Breadth while forking sequentially. The limitation on outgoing Max-Breadth is applied to concurrent branches only.
Неотъемлемой частью определения этого механизма является способность прокси возвращать распределённый Max-Breadth при последовательном разветвлении. Ограничение на исходящий Max-Breadth применяется только к одновременным ветвям.
For example, if a proxy receives a request with a Max-Breadth of 4 and has 8 targets to forward it to, that proxy may parallel fork to 4 of these targets initially (each with a Max-Breadth of 1, totaling an Outgoing Max-Breadth of 4). If one of these transactions completes with a failure response, the outgoing Max-Breadth drops to 3, allowing the proxy to forward to one of the 4 remaining targets (again, with a Max-Breadth of 1).
Например, если прокси получает запрос со значением Max-Breadth, равным 4, и имеет 8 целей для его пересылки, этот прокси может сначала параллельно разветвить запрос на 4 из этих целей (каждая со значением Max-Breadth, равным 1, что в сумме даёт исходящий Max-Breadth, равный 4). Если одна из этих транзакций завершается ответом об ошибке, исходящий Max-Breadth падает до 3, что позволяет прокси переслать запрос одной из 4 оставшихся целей (опять же со значением Max-Breadth, равным 1).
5.6. Max-Breadth Split Weight Selection
5.6. Выбор веса разделения Max-Breadth
There are a variety of mechanisms for controlling the weight of each fork branch. Fork branches that are given more Max-Breadth are more likely to complete quickly (because it is less likely that a proxy down the line will be forced to fork sequentially). By the same token, if it is known that a given branch will not fork later on, a Max-Breadth of 1 may be assigned with no ill effect. This would be appropriate, for example, if a proxy knows the branch is using the SIP outbound extension [OUTBOUND].
Имеется множество механизмов управления весом каждой ветви разветвления. Ветви, которым выделено больше Max-Breadth, с большей вероятностью завершатся быстро (поскольку меньше вероятность того, что нижестоящий прокси будет вынужден разветвлять последовательно). Точно так же, если известно, что данная ветвь в дальнейшем не будет разветвляться, можно назначить Max-Breadth, равный 1, без каких-либо вредных последствий. Это было бы уместно, например, если прокси знает, что ветвь использует расширение SIP outbound [OUTBOUND].
5.7. Max-Breadth's Effect on Forking-Based Amplification Attacks
5.7. Влияние Max-Breadth на атаки усиления, основанные на разветвлении
Max-Breadth limits the total number of active branches spawned by a given request at any one time, while placing no constraint on the distance (measured in hops) that the request can propagate. (i.e., receiving a request with a Max-Breadth of 1 means that any forking must be sequential, not that forking is forbidden)
Max-Breadth ограничивает общее число активных ветвей, порождённых данным запросом в любой момент времени, не накладывая ограничений на расстояние (измеряемое в переходах), на которое запрос может распространиться. (То есть получение запроса со значением Max-Breadth, равным 1, означает, что любое разветвление должно быть последовательным, а не то, что разветвление запрещено.)
This limits the effectiveness of any amplification attack that leverages forking because the amount of state/bandwidth needed to process the traffic at any given point in time is capped.
Это ограничивает эффективность любой атаки усиления, использующей разветвление, поскольку объём состояния и полосы пропускания, необходимых для обработки трафика в любой заданный момент времени, оказывается ограничен сверху.

7. Security Considerations
7. Вопросы безопасности
This document is entirely about documenting and addressing a vulnerability in SIP proxies as defined by RFC 3261 that can lead to an exponentially growing message exchange attack.
Настоящий документ целиком посвящён описанию и устранению уязвимости в прокси SIP, определённых в RFC 3261, которая может привести к атаке с экспоненциально растущим обменом сообщениями.
The Max-Breadth mechanism defined here does not decrease the aggregate traffic caused by the forking-loop attack. It only serves to spread the traffic caused by the attack over a longer period by limiting the number of concurrent branches that are being processed at the same time. An attacker could pump multiple requests into a network that uses the Max-Breadth mechanism and gradually build traffic to unreasonable levels. Deployments should monitor carefully and react to gradual increases in the number of concurrent outstanding transactions related to a given resource to protect against this possibility. Operators should anticipate being able to temporarily disable any resources identified as being used in such an attack. A rapid increase in outstanding concurrent transactions system-wide may be an indication of the presence of this kind of attack across many resources. Deployments in which it is feasible for an attacker to obtain a very large number of resources are particularly at risk. If detecting and intervening in each instance of the attack is insufficient to reduce the load, overload may occur.
Определённый здесь механизм Max-Breadth не уменьшает совокупный трафик, вызванный атакой с разветвлением и петлями. Он лишь распределяет трафик, вызванный атакой, на более длительный период, ограничивая число одновременно обрабатываемых ветвей. Злоумышленник может вкачивать в сеть, использующую механизм Max-Breadth, множество запросов и постепенно наращивать трафик до неразумных уровней. Развёртываниям следует внимательно наблюдать за постепенным ростом числа одновременных незавершённых транзакций, связанных с данным ресурсом, и реагировать на него, чтобы защититься от этой возможности. Операторам следует рассчитывать на возможность временно отключать любые ресурсы, которые будут признаны используемыми в такой атаке. Быстрый рост числа незавершённых одновременных транзакций в масштабе системы может указывать на наличие такой атаки по многим ресурсам. Особенно подвержены риску развёртывания, в которых злоумышленник может получить очень большое число ресурсов. Если обнаружения и вмешательства в каждый случай атаки недостаточно для снижения нагрузки, может возникнуть перегрузка.
Implementers and operators are encouraged to follow the recommendations being developed for handling overload conditions (see [REQS] and [DESIGN]).
Реализаторам и операторам рекомендуется следовать рекомендациям, разрабатываемым для обработки условий перегрузки (см. [REQS] и [DESIGN]).
Designers of protocol gateways should consider the implications of this kind of attack carefully. As an example, if a message transits from a SIP network into the Public Switched Telephone Network (PSTN) and subsequently back into a SIP network, and information about the history of the request on either side of the protocol translation is lost, it becomes possible to construct loops that neither Max- Forwards nor loop detection can protect against. This, combined with forking amplification on the SIP side of the loop, will result in an attack as described in this document that the mechanisms here will not abate, not even to the point of limiting the number of concurrent messages in the attack. These considerations are particularly important for designers of gateways from SIP to SIP (as found in B2BUAs, for example). Many existing B2BUA implementations are under some pressure to hide as much information about the two sides communicating with them as possible. Implementers of such implementations may be tempted to remove the data that might be used by the loop-detection, Max-Forwards, or Max-Breadth mechanisms at other points in the network, taking on the responsibility for detecting loops (or forms of this attack). However, if two such implementations are involved in the attack, neither will be able to detect it.
Разработчикам шлюзов протоколов следует внимательно рассмотреть последствия такого рода атаки. Например, если сообщение переходит из сети SIP в коммутируемую телефонную сеть общего пользования (PSTN), а затем обратно в сеть SIP, и информация об истории запроса по обе стороны преобразования протокола теряется, становится возможным построить петли, от которых не могут защитить ни Max-Forwards, ни обнаружение петель. В сочетании с усилением при разветвлении на стороне SIP петли это приведёт к описанной в настоящем документе атаке, которую здешние механизмы не ослабят даже до уровня ограничения числа одновременных сообщений в атаке. Эти соображения особенно важны для разработчиков шлюзов из SIP в SIP (каковые встречаются, например, в B2BUA). Многие существующие реализации B2BUA испытывают определённое давление, требуя скрывать как можно больше информации о двух взаимодействующих с ними сторонах. Реализаторов таких реализаций может подтолкнуть удалить данные, которые могли бы использоваться механизмами обнаружения петель, Max-Forwards или Max-Breadth в других точках сети, взяв на себя ответственность за обнаружение петель (или форм этой атаки). Однако если в атаке участвуют две такие реализации, ни одна из них не сможет её обнаружить.
7.1. Alternate Solutions That Were Considered and Rejected
7.1. Альтернативные решения, которые рассматривались и были отвергнуты
Alternative solutions that were discussed include:
Рассматривавшиеся альтернативные решения включают:
Doing nothing - rely on suing the offender: While systems that have accounts have logs that can be mined to locate abusers, it isn't clear that this provides a credible deterrent or defense against the attack described in this document. Systems that don't recognize the situation and take corrective/preventative action are likely to experience failure of a magnitude that precludes retrieval of the records documenting the setup of the attack. (In one scenario, the registrations can occur in a radically different time period than the INVITE transaction. The INVITE request itself may have come from an innocent). It's even possible that the scenario may be set up unintentionally. Furthermore, for some existing deployments, the cost and audit ability of an account is simply an email address. Finding someone to punish may be impossible. Finally, there are individuals who will not respond to any threat of legal action, and the effect of even a single successful instance of this kind of attack would be devastating to a service provider.
Ничего не делать — полагаться на судебное преследование нарушителя: хотя системы, имеющие учётные записи, ведут журналы, по которым можно найти нарушителей, неясно, обеспечивает ли это надёжное сдерживание или защиту от описанной в настоящем документе атаки. Системы, которые не распознают ситуацию и не принимают корректирующих или предупредительных мер, вероятно, потерпят отказ такого масштаба, который исключит извлечение записей, документирующих подготовку атаки. (В одном из сценариев регистрации могут произойти в совершенно иной период времени, чем транзакция INVITE. Сам запрос INVITE может прийти от невиновного.) Вполне возможно даже, что сценарий будет подготовлен непреднамеренно. Более того, в некоторых существующих развёртываниях стоимость и проверяемость учётной записи — это просто адрес электронной почты. Найти кого-то, кого можно наказать, может оказаться невозможно. Наконец, есть лица, которых не остановит никакая угроза судебного преследования, а последствия даже одного успешного случая такого рода атаки были бы опустошительными для поставщика услуг.
Putting a smaller cap on Max-Forwards: The effect of the attack is exponential with respect to the initial Max-Forwards value. Turning this value down limits the effect of the attack. This comes at the expense of severely limiting the reach of requests in the network, possibly to the point that existing architectures will begin to fail.
Установка меньшего предела для Max-Forwards: эффект атаки экспоненциален относительно исходного значения Max-Forwards. Снижение этого значения ограничивает эффект атаки. Это достигается ценой серьёзного ограничения дальности распространения запросов в сети, возможно, до такой степени, что существующие архитектуры начнут отказывать.
Disallowing registration bindings to arbitrary contacts: The way registration binding is currently defined is a key part of the success of the kind of attack documented here. The alternative of limiting registration bindings to allow only binding to the network element performing the registration, perhaps to the extreme of ignoring bits provided in the Contact in favor of transport artifacts observed in the registration request, has been discussed (particularly in the context of the mechanisms being defined in [OUTBOUND]). Mechanisms like this may be considered again in the future, but are currently insufficiently developed to address the present threat.
Запрет привязок регистрации к произвольным контактам: то, как сейчас определена привязка регистрации, является ключевой частью успеха описанного здесь вида атаки. Обсуждалась альтернатива ограничения привязок регистрации так, чтобы разрешалось привязываться только к сетевому элементу, выполняющему регистрацию, возможно, вплоть до крайности игнорировать сведения, предоставленные в Contact, в пользу транспортных артефактов, наблюдаемых в запросе регистрации (особенно в контексте механизмов, определяемых в [OUTBOUND]). Подобные механизмы могут быть рассмотрены вновь в будущем, но сейчас они разработаны недостаточно, чтобы противостоять нынешней угрозе.
Deprecate forking: This attack does not exist in a system that relies entirely on redirection and initiation of new requests by the original endpoint. Removing such a large architectural component from the system at this time was deemed too extreme a solution.
Признание разветвления устаревшим: эта атака не существует в системе, которая полностью полагается на перенаправление и инициирование новых запросов исходной оконечной точкой. Удаление столь крупного архитектурного компонента из системы в настоящее время было признано слишком радикальным решением.
Don't reclaim breadth: An alternative design of the Max-Breadth mechanism that was considered and rejected was to not allow the breadth from completed branches to be reused (see Section 5.3.3.1). Under this alternative, an introduced request would cause, at most, the initial value of Max-Breadth transactions to be generated in the network. While that approach limits any variant of the amplification vulnerability described here to a constant multiplier, it would dramatically change the potential reach of requests, and there is belief that it would break existing deployments.
Отказ от повторного использования ширины: альтернативный проект механизма Max-Breadth, который рассматривался и был отвергнут, состоял в том, чтобы не разрешать повторно использовать ширину завершённых ветвей (см. раздел 5.3.3.1). При этой альтернативе введённый запрос порождал бы в сети не более начального значения транзакций Max-Breadth. Хотя такой подход ограничивает любой вариант описанной здесь уязвимости усиления постоянным множителем, он кардинально изменил бы потенциальную дальность распространения запросов, и есть основания полагать, что он сломает существующие развёртывания.
