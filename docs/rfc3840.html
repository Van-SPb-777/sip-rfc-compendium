Abstract
Аннотация
This specification defines mechanisms by which a Session Initiation Protocol (SIP) user agent can convey its capabilities and characteristics to other user agents and to the registrar for its domain. This information is conveyed as parameters of the Contact header field.
Эта спецификация определяет механизмы, с помощью которых агент пользователя протокола инициирования сессий (SIP) может сообщать свои возможности и характеристики другим агентам пользователя и регистратору своего домена. Эта информация передаётся в качестве параметров заголовочного поля Contact.
1. Introduction
1. Введение
Session Initiation Protocol (SIP) [1] user agents vary widely in their capabilities and in the types of devices they represent. Frequently, it is important for another SIP element to learn the capabilities and characteristics of a SIP UA. Some of the applications of this information include:
Агенты пользователя протокола инициирования сессий (SIP) [1] сильно различаются по своим возможностям и по типам устройств, которые они представляют. Часто другому элементу SIP важно узнать возможности и характеристики агента пользователя SIP. Некоторые из приложений этой информации включают:
o One user agent, a PC-based application, is communicating with another that is embedded in a limited-function device. The PC would like to be able to "grey out" those components of the user interface that represent features or capabilities not supported by its peer. To do that, there needs to be a way to exchange capability information within a dialog.
o Один агент пользователя — приложение на базе ПК — обменивается данными с другим, встроенным в устройство с ограниченными функциями. ПК хотел бы иметь возможность «затенять» те компоненты пользовательского интерфейса, которые представляют функции или возможности, не поддерживаемые его партнёром. Для этого нужен способ обмена информацией о возможностях в рамках диалога.
o A user has two devices at their disposal. One is a videophone, and the other, a voice-only wireless phone. A caller wants to interact with the user using video. As such, they would like their call preferentially routed to the device which supports video. To do this, the INVITE request can contain parameters that express a preference for routing to a device with the specified capabilities [11].
o В распоряжении пользователя есть два устройства. Одно — видеотелефон, а другое — беспроводной телефон только с голосом. Вызывающий хочет взаимодействовать с пользователем с помощью видео. Поэтому он хотел бы, чтобы его вызов маршрутизировался преимущественно на устройство, поддерживающее видео. Для этого запрос INVITE может содержать параметры, выражающие предпочтение маршрутизации на устройство с указанными возможностями [11].
o A network application would like to asynchronously send information to a user agent in a MESSAGE [16] request. However, before sending it, they would like to know if the UA has the capabilities necessary to receive the message. To do that, they would ideally query a user database managed by the domain which holds such information. Population of such a database would require that a UA convey its capabilities as part of its registration. Thus, there is a need for conveying capabilities in REGISTER requests.
o Сетевое приложение хотело бы асинхронно отправить информацию агенту пользователя в запросе MESSAGE [16]. Однако перед отправкой оно хотело бы знать, обладает ли UA возможностями, необходимыми для приёма сообщения. Для этого идеальным решением было бы запросить базу данных пользователей, управляемую доменом и хранящую такую информацию. Наполнение такой базы данных потребовало бы, чтобы UA сообщал свои возможности в рамках регистрации. Таким образом, существует потребность в передаче возможностей в запросах REGISTER.
SIP has some support for expression of capabilities. The Allow, Accept, Accept-Language, and Supported header fields convey some information about the capabilities of a user agent. However, these header fields convey only a small part of the information that is needed. They do not provide a general framework for expression of capabilities. Furthermore, they only specify capabilities indirectly; the header fields really indicate the capabilities of the UA as they apply to this request. SIP also has no ability to convey characteristics, that is, information that describes a UA.
SIP располагает некоторыми средствами выражения возможностей. Заголовочные поля Allow, Accept, Accept-Language и Supported передают часть информации о возможностях агента пользователя. Однако эти поля передают лишь малую часть необходимой информации. Они не обеспечивают общей основы для выражения возможностей. Более того, они указывают возможности лишь косвенно: в действительности эти поля сообщают о возможностях UA применительно к данному запросу. SIP также не имеет средств передачи характеристик, то есть информации, описывающей UA.
As a result, this specification provides a more general framework for an indication of capabilities and characteristics in SIP. Capability and characteristic information about a UA is carried as parameters of the Contact header field. These parameters can be used within REGISTER requests and responses, OPTIONS responses, and requests and responses that create dialogs (such as INVITE).
В результате эта спецификация предоставляет более общую основу для указания возможностей и характеристик в SIP. Информация о возможностях и характеристиках UA передаётся в качестве параметров заголовочного поля Contact. Эти параметры могут использоваться в запросах и ответах REGISTER, в ответах OPTIONS, а также в запросах и ответах, создающих диалоги (например, INVITE).

3. Definitions
3. Определения
Feature: As defined in RFC 2703 [17], a piece of information about the media handling properties of a message passing system component or of a data resource. For example, the SIP methods supported by a UA represent a feature.
Признак: как определено в RFC 2703 [17], это элемент информации о свойствах обработки медиаданных компонентом системы передачи сообщений или информационным ресурсом. Например, методы SIP, поддерживаемые UA, представляют собой признак.
Feature Tag: As defined in RFC 2703 [17], a feature tag is a name that identifies a feature. An example is "sip.methods".
Тег признака: как определено в RFC 2703 [17], тег признака — это имя, идентифицирующее признак. Пример — «sip.methods».
Media Feature: As defined in RFC 2703, [17], a media feature is information that indicates facilities assumed to be available for the message content to be properly rendered or otherwise presented. Media features are not intended to include information that affects message transmission.
Медиа-признак: как определено в RFC 2703 [17], медиа-признак — это информация, указывающая средства, которые предполагаются доступными для надлежащего отображения или иного представления содержимого сообщения. Медиа-признаки не предназначены для включения информации, влияющей на передачу сообщений.
In the context of this specification, a media feature is information that indicates facilities for handling SIP requests, rather than specifically for content. In that sense, it is used synonymously with feature.
В контексте этой спецификации медиа-признак — это информация, указывающая средства обработки запросов SIP, а не содержимого как такового. В этом смысле он используется как синоним признака.
Feature Collection: As defined in RFC 2533 [4], a feature collection is a collection of different media features and associated values. This might be viewed as describing a specific rendering of a specific instance of a document or resource by a specific recipient.
Коллекция признаков: как определено в RFC 2533 [4], коллекция признаков — это набор различных медиа-признаков и связанных с ними значений. Это можно рассматривать как описание конкретного представления конкретного экземпляра документа или ресурса конкретным получателем.
Feature Set: As defined in RFC 2703 [17], a feature set is information about a sender, recipient, or other participant in a message transfer which describes the set of features that it can handle. Where a 'feature' describes a single identified attribute of a resource, a 'feature set' describes a full set of possible attributes.
Набор признаков: как определено в RFC 2703 [17], набор признаков — это информация об отправителе, получателе или другом участнике передачи сообщения, описывающая набор признаков, которые он может обрабатывать. Если «признак» описывает отдельный идентифицированный атрибут ресурса, то «набор признаков» описывает полный набор возможных атрибутов.
Feature Parameters: A set of SIP header field parameters that can appear in the Contact header field. The feature parameters represent an encoding of a feature set. Each set of feature parameters maps to a feature set predicate.
Параметры признаков: набор параметров заголовочных полей SIP, которые могут присутствовать в заголовочном поле Contact. Параметры признаков представляют собой кодирование набора признаков. Каждый набор параметров признаков отображается в предикат набора признаков.
Capability: As defined in RFC 2703 [17], a capability is an attribute of a sender or receiver (often the receiver) which indicates an ability to generate or process a particular type of message content. A capability is distinct from a characteristic in that a capability may or may not be utilized in any particular call, whereas a characteristic is a non-negotiable property of a UA. SIP itself will often negotiate whether or not capabilities are used in a call.
Возможность: как определено в RFC 2703 [17], возможность — это атрибут отправителя или получателя (часто получателя), указывающий способность генерировать или обрабатывать определённый тип содержимого сообщения. Возможность отличается от характеристики тем, что возможность может использоваться или не использоваться в конкретном вызове, тогда как характеристика — это необсуждаемое свойство UA. Сам SIP часто согласует, используются ли возможности в вызове.
Characteristic: A characteristic is like a capability, but describes an aspect of a UA which is not negotiable. As an example, whether or not a UA is a mobile phone is a characteristic, not a capability. The semantics of this specification do not differentiate between capability and characteristic, but the distinction is useful for illustrative purposes. Indeed, in the text below, when we say "capability", it refers to both capabilities and characteristics, unless the text explicitly says otherwise.
Характеристика: характеристика похожа на возможность, но описывает аспект UA, который не является предметом согласования. Например, является ли UA мобильным телефоном — это характеристика, а не возможность. Семантика этой спецификации не различает возможность и характеристику, но это различие полезно для иллюстрации. Действительно, ниже в тексте, когда мы говорим «возможность», это относится и к возможностям, и к характеристикам, если в тексте явно не сказано иное.
Filter: A single expression in a feature set predicate.
Фильтр: отдельное выражение в предикате набора признаков.
Simple Filter: An expression in a feature set predicate which is a comparison (equality or inequality) of a feature tag against a feature value.
Простой фильтр: выражение в предикате набора признаков, представляющее собой сравнение (равенство или неравенство) тега признака со значением признака.
Disjunction: A boolean OR operation across some number of terms.
Дизъюнкция: логическая операция OR над некоторым числом термов.
Conjunction: A boolean AND operation across some number of terms.
Конъюнкция: логическая операция AND над некоторым числом термов.
Predicate: A boolean expression.
Предикат: логическое выражение.
Feature Set Predicate: From RFC 2533 [4], a feature set predicate is a function of an arbitrary feature collection value which returns a Boolean result. A TRUE result is taken to mean that the corresponding feature collection belongs to some set of media feature handling capabilities defined by this predicate.
Предикат набора признаков: согласно RFC 2533 [4], предикат набора признаков — это функция от произвольного значения коллекции признаков, возвращающая логический результат. Результат TRUE означает, что соответствующая коллекция признаков принадлежит некоторому набору возможностей обработки медиа-признаков, определённому этим предикатом.
Contact Predicate: The feature set predicate associated with a URI registered in the Contact header field of a REGISTER request. The contact predicate is derived from the feature parameters in the Contact header field.
Предикат контакта: предикат набора признаков, связанный с URI, зарегистрированным в заголовочном поле Contact запроса REGISTER. Предикат контакта выводится из параметров признаков в заголовочном поле Contact.
4. Usage of the Content Negotiation Framework
4. Использование framework согласования содержимого
This specification makes heavy use of the terminology and concepts in the content negotiation work carried out within the IETF, and documented in several RFCs. The ones relevant to this specification are RFC 2506 [3], which provides a template for registering media feature tags, RFC 2533 [4], which presents a syntax and matching algorithm for media feature sets, RFC 2738 [5], which provides a minor update to RFC 2533, and RFC 2703 [17], which provides a general framework for content negotiation.
Эта спецификация активно использует терминологию и концепции работ по согласованию содержимого, выполненных в IETF и документированных в нескольких RFC. К относящимся к этой спецификации относятся RFC 2506 [3], который предоставляет шаблон для регистрации тегов медиа-признаков, RFC 2533 [4], который представляет синтаксис и алгоритм сопоставления наборов медиа-признаков, RFC 2738 [5], который вносит небольшое обновление в RFC 2533, и RFC 2703 [17], который предоставляет общую основу для согласования содержимого.
In case the reader does not have the time to read those specifications, Appendix A provides a brief overview of the concepts and terminology in those documents that is critical for understanding this specification.
Если у читателя нет времени читать эти спецификации, приложение A содержит краткий обзор концепций и терминологии из этих документов, критически важных для понимания данной спецификации.
Since the content negotiation work was primarily meant to apply to documents or other resources with a set of possible renderings, it is not immediately apparent how it is used to model SIP user agents. A feature set is composed of a set of feature collections, each of which represents a specific rendering supported by the entity described by the feature set. In the context of a SIP user agent, a feature collection represents an instantaneous modality. That is, if you look at the run time processing of a SIP UA and take a snapshot in time, the feature collection describes what it is doing at that very instant.
Поскольку работы по согласованию содержимого были в первую очередь предназначены для документов или других ресурсов с набором возможных представлений, не сразу очевидно, как они используются для моделирования агентов пользователя SIP. Набор признаков состоит из набора коллекций признаков, каждая из которых представляет конкретное представление, поддерживаемое объектом, описываемым набором признаков. В контексте агента пользователя SIP коллекция признаков представляет собой мгновенную модальность. То есть, если посмотреть на обработку во время выполнения агента пользователя SIP и сделать снимок во времени, коллекция признаков опишет, что он делает в этот самый момент.
This model is important, since it provides guidance on how to determine whether something is a value for a particular feature tag, or a feature tag by itself. If two properties can be exhibited by a UA simultaneously so that both are present in an instantaneous modality, they need to be represented by separate media feature tags. For example, a UA may be able to support some number of media types - audio, video, and control. Should each of these be different values for a single "media-types" feature tag, or should each of them be a separate boolean feature tag? The model provides the answer. Since, at any instance in time, a UA could be handling both audio and video, they need to be separate media feature tags. However, the SIP methods supported by a UA can each be represented as different values for the same media feature tag (the "sip.methods" tag), because fundamentally, a UA processes a single request at a time. It may be multi-threading, so that it appears that this is not so, but at a purely functional level, it is true.
Эта модель важна, поскольку она даёт руководство для определения того, является ли нечто значением конкретного тега признака или самим тегом признака. Если два свойства могут проявляться UA одновременно так, что оба присутствуют в мгновенной модальности, их нужно представлять отдельными тегами медиа-признаков. Например, UA может поддерживать некоторое число типов медиаданных — audio, video и control. Должен ли каждый из них быть отдельным значением одного тега признака «media-types» или каждый из них должен быть отдельным логическим тегом признака? Модель даёт ответ. Поскольку в любой момент времени UA может обрабатывать одновременно audio и video, они должны быть отдельными тегами медиа-признаков. Однако методы SIP, поддерживаемые UA, можно представить как различные значения одного и того же тега медиа-признака (тега «sip.methods»), поскольку по существу UA обрабатывает один запрос за раз. Он может быть многопоточным, так что это выглядит иначе, но на чисто функциональном уровне это верно.
Clearly, there are weaknesses in this model, but it serves as a useful guideline for applying the concepts of RFC 2533 to the problem at hand.
Очевидно, в этой модели есть слабые места, но она служит полезным руководством для применения концепций RFC 2533 к рассматриваемой задаче.
5. Computing Capabilities
5. Вычисление возможностей
To construct a set of Contact header field parameters that indicate capabilities, a UA constructs a feature predicate for that contact. This process is described in terms of RFC 2533 [4] (and its minor update, RFC 2738 [5]) syntax and constructs, followed by a conversion to the syntax used in this specification. However, this represents a logical flow of processing. There is no requirement that an implementation actually use RFC 2533 syntax as an intermediate step.
Чтобы построить набор параметров заголовочного поля Contact, указывающих возможности, UA строит предикат признаков для этого контакта. Этот процесс описывается в терминах синтаксиса и конструкций RFC 2533 [4] (и его небольшого обновления RFC 2738 [5]) с последующим преобразованием в синтаксис, используемый в этой спецификации. Однако это представляет собой логический порядок обработки. Нет требования, чтобы реализация действительно использовала синтаксис RFC 2533 в качестве промежуточного шага.
A UA MAY use any feature tags that are registered through IANA in the SIP tree (Established in Section 12.1), IETF, or global trees [3]; this document registers several into the SIP tree. The feature tags discussed in this specification are referred to as base tags. While other tags can be used, in order to identify them as feature parameters (as opposed to parameters for another SIP extension), they are encoded with a leading "+" sign in the Contact header field. It is also permissible to use the URI tree [3] for expressing vendor- specific feature tags. Feature tags in any other trees created through IANA MAY also be used.
UA MAY использовать любые теги признаков, зарегистрированные через IANA в дереве SIP (созданном в разделе 12.1), деревьях IETF или global [3]; этот документ регистрирует несколько тегов в дереве SIP. Теги признаков, обсуждаемые в этой спецификации, называются базовыми тегами. Хотя можно использовать и другие теги, чтобы идентифицировать их как параметры признаков (в отличие от параметров другого расширения SIP), они кодируются с ведущим знаком «+» в заголовочном поле Contact. Также допустимо использовать дерево URI [3] для выражения тегов признаков, зависящих от поставщика. Теги признаков в любых других деревьях, созданных через IANA, также MAY использоваться.
When using the "sip.methods" feature tag, a UA MUST NOT include values that correspond to methods not standardized in IETF standards track RFCs. When using the "sip.events" feature tag, a UA MUST NOT include values that correspond to event packages not standardized in IETF standards track RFCs. When using the "sip.schemes" feature tag, a UA MUST NOT include values that correspond to schemes not standardized in IETF standards track RFCs. When using the "sip.extensions" feature tag, a UA MUST NOT include values that correspond to option tags not standardized in IETF standards track RFCs.
При использовании тега признака «sip.methods» UA MUST NOT включать значения, соответствующие методам, не стандартизованным в RFC уровня стандартов IETF. При использовании тега признака «sip.events» UA MUST NOT включать значения, соответствующие пакетам событий, не стандартизованным в RFC уровня стандартов IETF. При использовании тега признака «sip.schemes» UA MUST NOT включать значения, соответствующие схемам, не стандартизованным в RFC уровня стандартов IETF. При использовании тега признака «sip.extensions» UA MUST NOT включать значения, соответствующие тегам опций, не стандартизованным в RFC уровня стандартов IETF.
Note that the "sip.schemes" feature tag does not indicate the scheme of the registered URI. Rather, it indicates schemes that a UA is capable of sending requests to, should such a URI be received in a web page or Contact header field of a redirect response.
Обратите внимание, что тег признака «sip.schemes» не указывает схему зарегистрированного URI. Вместо этого он указывает схемы, на которые UA способен отправлять запросы, если такой URI будет получен в веб-странице или заголовочном поле Contact ответа переадресации.
It is RECOMMENDED that a UA provide complete information in its contact predicate. That is, it SHOULD provide information on as many feature tags as possible. The mechanisms in this specification work best when user agents register complete feature sets. Furthermore, when a UA registers values for a particular feature tag, it MUST list all values that it supports. For example, when including the "sip.methods" feature tag, a UA MUST list all methods it supports.
РЕКОМЕНДУЕТСЯ, чтобы UA предоставлял полную информацию в своём предикате контакта. То есть он SHOULD предоставлять информацию о как можно большем числе тегов признаков. Механизмы этой спецификации работают лучше всего, когда агенты пользователя регистрируют полные наборы признаков. Более того, когда UA регистрирует значения для конкретного тега признака, он MUST перечислить все поддерживаемые значения. Например, включая тег признака «sip.methods», UA MUST перечислить все поддерживаемые им методы.
The contact predicate constructed by a UA MUST be an AND of terms (called a conjunction). Each term is either an OR (called a disjunction) of simple filters or negations of simple filters, or a single simple filter or negation of a single filter. In the case of a disjunction, each filter in the disjunction MUST indicate feature values for the same feature tag (i.e., the disjunction represents a set of values for a particular feature tag), while each element of the conjunction MUST be for a different feature tag. Each simple filter can be an equality, or in the case of numeric feature tags, an inequality or range. If a string (as defined in RFC 2533 [4]) is used as the value of a simple filter, that value MUST NOT include the "<" or ">" characters, the simple filter MUST NOT be negated, and it MUST be the only simple filter for that particular feature tag. This contact predicate is then converted to a list of feature parameters, following the procedure outlined below.
Предикат контакта, построенный UA, MUST быть операцией AND над термами (называемой конъюнкцией). Каждый терм является либо операцией OR (называемой дизъюнкцией) простых фильтров или отрицаний простых фильтров, либо одним простым фильтром или отрицанием одного фильтра. В случае дизъюнкции каждый фильтр в дизъюнкции MUST указывать значения признака для одного и того же тега признака (то есть дизъюнкция представляет набор значений для конкретного тега признака), тогда как каждый элемент конъюнкции MUST относиться к разному тегу признака. Каждый простой фильтр может быть равенством или, в случае числовых тегов признаков, неравенством или диапазоном. Если в качестве значения простого фильтра используется строка (как определено в RFC 2533 [4]), это значение MUST NOT содержать символы «<» или «>», простой фильтр MUST NOT быть отрицанием, и он MUST быть единственным простым фильтром для данного конкретного тега признака. Затем этот предикат контакта преобразуется в список параметров признаков в соответствии с описанной ниже процедурой.
The contact predicate is a conjunction of terms. Each term indicates constraints on a single feature tag, and each term is represented by a separate feature parameter that will be present in the Contact header field. The syntax of this parameter depends on the feature tag. Each forward slash in the feature tag is converted to a single quote, and each colon are converted to an exclamation point. For the base tags - that is, those feature tags documented in this specification (sip.audio, sip.automata, sip.class, sip.duplex, sip.data, sip.control, sip.mobility, sip.description, sip.events, sip.priority, sip.methods, sip.extensions, sip.schemes, sip.application, sip.video, language, type, sip.isfocus, sip.actor and sip.text), the leading "sip.", if present, is stripped. For feature tags not in this list, the leading "sip." MUST NOT be stripped if present, and indeed, a plus sign ("+") MUST be added as the first character of the Contact header field parameter. The result is the feature parameter name. As a result of these rules, the base tags appear "naked" in the Contact header field - they have neither a "+" nor a "sip." prefix. All other tags will always have a leading "+" when present in the Contact header field, and will additionally have a "sip." if the tag is in the SIP tree.
Предикат контакта представляет собой конъюнкцию термов. Каждый терм указывает ограничения на один тег признака, и каждый терм представляется отдельным параметром признака, который будет присутствовать в заголовочном поле Contact. Синтаксис этого параметра зависит от тега признака. Каждая косая черта в теге признака преобразуется в одинарную кавычку, а каждое двоеточие — в восклицательный знак. Для базовых тегов, то есть тех тегов признаков, которые документированы в этой спецификации (sip.audio, sip.automata, sip.class, sip.duplex, sip.data, sip.control, sip.mobility, sip.description, sip.events, sip.priority, sip.methods, sip.extensions, sip.schemes, sip.application, sip.video, language, type, sip.isfocus, sip.actor и sip.text), ведущий «sip.», если он присутствует, отбрасывается. Для тегов признаков, не входящих в этот список, ведущий «sip.» MUST NOT отбрасываться, если он присутствует, и, более того, первым символом параметра заголовочного поля Contact MUST быть добавлен знак «+». Результат — имя параметра признака. Вследствие этих правил базовые теги выглядят в заголовочном поле Contact «нагими» — у них нет ни префикса «+», ни префикса «sip.». Все остальные теги всегда будут иметь ведущий «+», когда присутствуют в заголовочном поле Contact, и дополнительно будут иметь «sip.», если тег находится в дереве SIP.
The value of the feature parameter depends on the term of the conjunction. If the term is a boolean expression with a value of true, i.e., (sip.audio=TRUE), the contact parameter has no value. If the term of the conjunction is a disjunction, the value of the contact parameter is a quoted string. The quoted string is a comma separated list of strings, each one derived from one of the terms in the disjunction. If the term of the conjunction is a negation, the value of the contact parameter is a quoted string. The quoted string begins with an exclamation point (!), and the remainder is constructed from the expression being negated.
Значение параметра признака зависит от терма конъюнкции. Если терм является логическим выражением со значением true, то есть (sip.audio=TRUE), параметр контакта не имеет значения. Если терм конъюнкции является дизъюнкцией, значением параметра контакта является строка в кавычках. Строка в кавычках — это разделённый запятыми список строк, каждая из которых получена из одного из термов дизъюнкции. Если терм конъюнкции является отрицанием, значением параметра контакта является строка в кавычках. Строка в кавычках начинается с восклицательного знака (!), а остальная часть строится из отрицаемого выражения.
The remaining operation is to compute a string from a primitive filter. If the filter is a simple filter that is performing a numeric comparison, the string starts with an octothorpe (#), followed by the comparator in the filter (=, >=, or <=), followed by the value from the filter. If the value from the filter is expressed in rational form (X / Y), then X and Y are divided, yielding a decimal number, and this decimal number is output to the string.
Оставшаяся операция — вычислить строку из примитивного фильтра. Если фильтр является простым фильтром, выполняющим числовое сравнение, строка начинается со знака решётки (#), за которым следует компаратор в фильтре (=, >= или <=), а затем значение из фильтра. Если значение из фильтра выражено в рациональной форме (X / Y), то X и Y делятся, давая десятичное число, и это десятичное число выводится в строку.
RFC 2533 uses a fractional notation to describe rational numbers. This specification uses a decimal form. The above text merely converts between the two representations. Practically speaking, this conversion is not needed since the numbers are the same in either case. However, it is described in case implementations wish to directly plug the predicates generated by the rules in this section into an RFC 2533 implementation.
RFC 2533 использует дробную нотацию для описания рациональных чисел. Эта спецификация использует десятичную форму. Приведённый выше текст лишь преобразует одно представление в другое. Практически говоря, это преобразование не нужно, поскольку числа в обоих случаях одинаковы. Однако оно описано на случай, если реализации захотят напрямую подставить предикаты, порождённые правилами этого раздела, в реализацию RFC 2533.
If the filter is a range (foo=X..Y), the string is equal to X:Y, where X and Y have been converted from fractional numbers (A / B) to their decimal equivalent.
Если фильтр является диапазоном (foo=X..Y), строка равна X:Y, где X и Y преобразованы из дробных чисел (A / B) в их десятичный эквивалент.
If the filter is an equality over a token or boolean, then that token or boolean value ("TRUE" or "FALSE") is output to the string.
Если фильтр является равенством над токеном или логическим значением, то этот токен или логическое значение («TRUE» или «FALSE») выводится в строку.
If the filter is an equality over a quoted string, the output is a less than (<), followed by the quoted string, followed by a greater than (>).
Если фильтр является равенством над строкой в кавычках, выводом является знак «меньше» (<), за которым следует строка в кавычках, а затем знак «больше» (>).
As an example, this feature predicate:
В качестве примера этот предикат признаков:

(& (sip.mobility=fixed) (| (! (sip.events=presence)) (sip.events=message-summary)) (| (language=en) (language=de)) (sip.description="PC") (sip.newparam=TRUE) (rangeparam=-4..5125/1000))
would be converted into the following feature parameters:
будет преобразован в следующие параметры признаков:
mobility="fixed";events="!presence,message-summary";language="en,de" ;description="<PC>";+sip.newparam;+rangeparam="#-4:+5.125"
mobility="fixed";events="!presence,message-summary";language="en,de" ;description="<PC>";+sip.newparam;+rangeparam="#-4:+5.125"
These feature tags would then appear as part of the Contact header field:
Затем эти теги признаков появятся в составе заголовочного поля Contact:

Contact: <sip:user@pc.example.com>
;mobility="fixed";events="!presence,message-summary" ;language="en,de";description="<PC>" ;+sip.newparam;+rangeparam="#-4:+5.125"

Notice how the leading "sip." was stripped from the sip.mobility, sip.events and sip.description feature tags before encoding them in the Contact header field. This is because these feature tags are amongst the base tags listed above. It is for this reason that these feature tags were not encoded with a leading "+" either. However, the sip.newparam feature tag was encoded with both the "+" and its leading "sip.", and the rangeparam was also encoded with a leading "+". This is because neither of these feature tags are defined in this specification. As such, the leading "sip." is not stripped off, and a "+" is added.
Обратите внимание, как ведущий «sip.» был отброшен у тегов признаков sip.mobility, sip.events и sip.description перед их кодированием в заголовочном поле Contact. Это объясняется тем, что эти теги признаков входят в число перечисленных выше базовых тегов. По этой же причине эти теги признаков не были закодированы и с ведущим «+». Однако тег признака sip.newparam был закодирован и с «+», и со своим ведущим «sip.», а rangeparam также был закодирован с ведущим «+». Это объясняется тем, что ни один из этих тегов признаков не определён в данной спецификации. Поэтому ведущий «sip.» не отбрасывается и добавляется «+».
6. Expressing Capabilities in a Registration
6. Выражение возможностей при регистрации
When a UA registers, it can choose to indicate a feature set associated with a registered contact. Whether or not a UA does so depends on what the registered URI represents. If the registered URI represents a UA instance (the common case in registrations), a UA compliant to this specification SHOULD indicate a feature set using the mechanisms described here. If, however, the registered URI represents an address-of-record, or some other resource that is not representable by a single feature set, it SHOULD NOT include a feature set. As an example, if a user wishes to forward calls from sip:user1@example.com to sip:user2@example.org, it could generate a registration that looks like, in part:
Когда UA регистрируется, он может указать набор признаков, связанный с зарегистрированным контактом. Делает ли UA это, зависит от того, что представляет зарегистрированный URI. Если зарегистрированный URI представляет экземпляр UA (обычный случай при регистрациях), UA, совместимый с этой спецификацией, SHOULD указывать набор признаков с помощью описанных здесь механизмов. Если же зарегистрированный URI представляет адрес записи или другой ресурс, который нельзя представить одним набором признаков, он SHOULD NOT включать набор признаков. Например, если пользователь хочет переадресовать вызовы с sip:user1@example.com на sip:user2@example.org, он может сгенерировать регистрацию, выглядящую, в частности, так:
REGISTER sip:example.com SIP/2.0 To: sip:user1@example.com Contact: sip:user2@example.org
REGISTER sip:example.com SIP/2.0 To: sip:user1@example.com Contact: sip:user2@example.org
In this case, the registered contact is not identifying a UA, but rather, another address-of-record. In such a case, the registered contact would not indicate a feature set.
В этом случае зарегистрированный контакт идентифицирует не UA, а другой адрес записи. В таком случае зарегистрированный контакт не будет указывать набор признаков.
However, in some cases, a UA may wish to express feature parameters for an address-of-record. One example is an AOR which represents a multiplicity of devices in a home network, and routes to a proxy server in the user's home. Since all devices in the home are for personal use, the AOR itself can be described with the ;class="personal" feature parameter. A registration that forwards calls to this home AOR could make use of that feature parameter. Generally speaking, a feature parameter can only be associated with an address-of-record if all devices bound to that address-of-record share the exact same set of values for that feature parameter.
Однако в некоторых случаях UA может пожелать выразить параметры признаков для адреса записи. Один из примеров — AOR, представляющий множество устройств в домашней сети и маршрутизирующий на прокси-сервер в доме пользователя. Поскольку все устройства в доме предназначены для личного использования, сам AOR можно описать параметром признака ;class="personal". Регистрация, переадресующая вызовы на этот домашний AOR, могла бы использовать этот параметр признака. Вообще говоря, параметр признака можно связать с адресом записи только в том случае, если все устройства, привязанные к этому адресу записи, имеют совершенно одинаковый набор значений для этого параметра признака.
Similarly, in some cases, a UA can exhibit one characteristic or another, but the characteristic is not known in advance. For example, a UA could represent a device that is a phone with an embedded answering machine. The ideal way to treat such devices is to model them as if they were actually a proxy fronting two devices - a phone (which is never an answering machine), and an answering machine (which is never a phone). The registration from this device would be constructed as if it were an AOR, as per the procedures above. Generally, this means that, unless the characteristic is identical between the logical devices, that characteristic will not be present in any registration generated by the actual device.
Аналогично, в некоторых случаях UA может демонстрировать одну или другую характеристику, но эта характеристика неизвестна заранее. Например, UA может представлять устройство, являющееся телефоном со встроенным автоответчиком. Идеальный способ обращения с такими устройствами — моделировать их так, как если бы они фактически были прокси, обслуживающим два устройства: телефон (который никогда не является автоответчиком) и автоответчик (который никогда не является телефоном). Регистрация от этого устройства строилась бы так, как если бы оно было AOR, в соответствии с процедурами выше. Обычно это означает, что, если характеристика не идентична между логическими устройствами, эта характеристика не будет присутствовать ни в одной регистрации, сгенерированной фактическим устройством.
The remainder of this section assumes that a UA would like to associate a feature set with a contact that it is registering. This feature set is constructed and converted to a series of Contact header field parameters, as described in Section 5, and those feature parameters are added to the Contact header field value containing the URI to which the parameters apply. The Allow, Accept, Accept- Language and Allow-Events [9] header fields are allowed in REGISTER requests, and also indicate capabilities. However, their semantic in REGISTER is different, indicating capabilities, used by the registrar, for generation of the response. As such, they are not a substitute or an alternate for the Contact feature parameters, which indicate the capabilities of the UA generally speaking.
Остальная часть этого раздела предполагает, что UA хочет связать набор признаков с контактом, который он регистрирует. Этот набор признаков строится и преобразуется в серию параметров заголовочного поля Contact, как описано в разделе 5, и эти параметры признаков добавляются к значению заголовочного поля Contact, содержащему URI, к которому относятся параметры. Заголовочные поля Allow, Accept, Accept-Language и Allow-Events [9] разрешены в запросах REGISTER и также указывают возможности. Однако их семантика в REGISTER иная: они указывают возможности, используемые регистратором для формирования ответа. Поэтому они не заменяют и не подменяют параметры признаков Contact, которые в общем случае указывают возможности UA.
The REGISTER request MAY contain a Require header field with the value "pref" if the client wants to be sure that the registrar understands the extensions defined in this specification. This means that the registrar will store the feature parameters, and make them available to elements accessing the location service within the domain. In the absence of the Require header field, a registrar that does not understand this extension will simply ignore the Contact header field parameters.
Запрос REGISTER MAY содержать заголовочное поле Require со значением «pref», если клиент хочет быть уверен, что регистратор понимает расширения, определённые в этой спецификации. Это означает, что регистратор сохранит параметры признаков и сделает их доступными элементам, обращающимся к службе определения местоположения в домене. При отсутствии заголовочного поля Require регистратор, не понимающий это расширение, просто проигнорирует параметры заголовочного поля Contact.
If a UA registers against multiple separate addresses-of-record, and the contacts registered for each have different capabilities, a UA MUST use different URIs in each registration. This allows the UA to uniquely determine the feature set that is associated with the request URI of an incoming request.
Если UA регистрируется для нескольких отдельных адресов записи и контакты, зарегистрированные для каждого из них, имеют разные возможности, UA MUST использовать разные URI в каждой регистрации. Это позволяет UA однозначно определить набор признаков, связанный с URI запроса входящего запроса.

7. Indicating Feature Sets in Remote Target URIs
7. Указание наборов признаков в URI удалённой цели
Target refresh requests and responses are used to establish and modify the remote target URI in a dialog. The remote target URI is conveyed in the Contact header field. A UAC or UAS MAY add feature parameters to the Contact header field value in target refresh requests and responses for the purpose of indicating the capabilities of the UA. To do that, it constructs a set of feature parameters according to Section 5. These are then added as Contact header field parameters in the request or response.
Запросы и ответы обновления целевого объекта используются для установления и изменения URI удалённой цели в диалоге. URI удалённой цели передаётся в заголовочном поле Contact. UAC или UAS MAY добавлять параметры признаков к значению заголовочного поля Contact в запросах и ответах обновления целевого объекта для указания возможностей UA. Для этого он строит набор параметров признаков в соответствии с разделом 5. Затем они добавляются в качестве параметров заголовочного поля Contact в запрос или ответ.
The feature parameters can be included in both initial requests and mid-dialog requests, and MAY change mid-dialog to signal a change in UA capabilities.
Параметры признаков можно включать как в начальные запросы, так и в запросы внутри диалога, и они MAY изменяться в середине диалога, сигнализируя об изменении возможностей UA.
There is overlap in the callee capabilities mechanism with the Allow, Accept, Accept-Language, and Allow-Events [9] header fields, which can also be used in target refresh requests. Specifically, the Allow header field and "sip.methods" feature tag indicate the same information. The Accept header field and the "type" feature tag indicate the same information. The Accept-Language header field and the "language" feature tag indicate the same information. The Allow-Events header field and the "sip.events" feature tag indicate the same information. It is possible that other header fields and feature tags defined in the future may also overlap. When there exists a feature tag that describes a capability that can also be represented with a SIP header field, a UA MUST use the header field to describe the capability. A UA receiving a message that contains both the header field and the feature tag MUST use the header field, and not the feature tag.
В механизме возможностей вызываемого абонента есть пересечение с заголовочными полями Allow, Accept, Accept-Language и Allow-Events [9], которые также можно использовать в запросах обновления целевого объекта. В частности, заголовочное поле Allow и тег признака «sip.methods» указывают одну и ту же информацию. Заголовочное поле Accept и тег признака «type» указывают одну и ту же информацию. Заголовочное поле Accept-Language и тег признака «language» указывают одну и ту же информацию. Заголовочное поле Allow-Events и тег признака «sip.events» указывают одну и ту же информацию. Возможно, другие заголовочные поля и теги признаков, определённые в будущем, также будут пересекаться. Когда существует тег признака, описывающий возможность, которая также может быть представлена заголовочным полем SIP, UA MUST использовать заголовочное поле для описания этой возможности. UA, получивший сообщение, содержащее и заголовочное поле, и тег признака, MUST использовать заголовочное поле, а не тег признака.
8. OPTIONS Processing
8. Обработка OPTIONS
When a UAS compliant to this specification receives an OPTIONS request, it MAY add feature parameters to the Contact header field in the OPTIONS response for the purpose of indicating the capabilities of the UA. To do that, it constructs a set of feature parameters according to Section 5. These are then added as Contact header field parameters in OPTIONS response. Indeed, if feature parameters were included in the registration generated by that UA, those same parameters SHOULD be used in the OPTIONS response.
Когда UAS, совместимый с этой спецификацией, получает запрос OPTIONS, он MAY добавлять параметры признаков к заголовочному полю Contact в ответе OPTIONS для указания возможностей UA. Для этого он строит набор параметров признаков в соответствии с разделом 5. Затем они добавляются в качестве параметров заголовочного поля Contact в ответ OPTIONS. Более того, если параметры признаков были включены в регистрацию, сгенерированную этим UA, те же самые параметры SHOULD использоваться и в ответе OPTIONS.
The guidelines in Section 7 regarding the overlap of the various callee capabilities feature tags with SIP header fields applies to the generation of OPTIONS responses as well. In particular, they apply when a Contact header field is describing the UA which generated the OPTIONS response. When a Contact header field in the OPTIONS response is identifying a different UA, there is no overlap.
Руководящие указания раздела 7 о пересечении различных тегов признаков возможностей вызываемого абонента с заголовочными полями SIP применимы и к формированию ответов OPTIONS. В частности, они применимы, когда заголовочное поле Contact описывает UA, сгенерировавший ответ OPTIONS. Когда заголовочное поле Contact в ответе OPTIONS идентифицирует другой UA, пересечения нет.

10. Media Feature Tag Definitions
10. Определения тегов медиа-признаков
This specification defines an initial set of media feature tags for use with this specification. This section serves as the IANA registration for these feature tags, which are made into the SIP media feature tag tree. New media feature tags are registered in the IETF or global trees based on the process defined for feature tag registrations [3], or in the SIP tree based on the process defined in Section 12.1.
Эта спецификация определяет начальный набор тегов медиа-признаков для использования с этой спецификацией. Этот раздел служит регистрацией IANA для этих тегов признаков, которые помещаются в дерево тегов медиа-признаков SIP. Новые теги медиа-признаков регистрируются в деревьях IETF или global на основе процесса, определённого для регистрации тегов признаков [3], либо в дереве SIP на основе процесса, определённого в разделе 12.1.
Any registered feature tags MAY be used with this specification. However, several existing ones appear to be particularly applicable. These include the language feature tag [6], which can be used to specify the language of the human or automata represented by the UA, and the type feature tag [7], which can be used to specify the MIME types that a SIP UA can receive in a SIP message. The audio, video, application, data, and control feature tags in the SIP tree (each of which indicate a media type, as defined in RFC 2327 [8]) are different. They do not indicate top level MIME types which can be received in SIP requests. Rather, they indicate media types that can be used in media streams, and as a result, match up with the types defined in RFC 2327 [8].
С этой спецификацией MAY использоваться любые зарегистрированные теги признаков. Однако некоторые существующие теги представляются особенно применимыми. К ним относятся тег признака language [6], который можно использовать для указания языка человека или automata, представляемого UA, и тег признака type [7], который можно использовать для указания типов MIME, которые агент пользователя SIP может принимать в сообщении SIP. Теги признаков audio, video, application, data и control в дереве SIP (каждый из которых указывает тип медиаданных, как определено в RFC 2327 [8]) отличаются. Они не указывают типы MIME верхнего уровня, которые можно принимать в запросах SIP. Вместо этого они указывают типы медиаданных, которые можно использовать в медиапотоках, и, следовательно, соответствуют типам, определённым в RFC 2327 [8].
If a new SDP media type were to be defined, such as "message", a new feature tag registration SHOULD be created for it in the SIP tree. The name of the feature tag MUST equal "sip." concatenated with the name of the media type, unless there is an unlikely naming collision between the new media type and an existing feature tag registration. As a result, implementations can safely construct caller preferences and callee capabilities for the new media type before it is registered, as long as there is no naming conflict.
Если бы требовалось определить новый тип медиаданных SDP, например «message», для него SHOULD быть создана новая регистрация тега признака в дереве SIP. Имя тега признака MUST быть равно «sip.» в конкатенации с именем типа медиаданных, если только не возникнет маловероятный конфликт имён между новым типом медиаданных и существующей регистрацией тега признака. В результате реализации могут безопасно строить предпочтения вызывающего абонента и возможности вызываемого абонента для нового типа медиаданных до его регистрации, при условии отсутствия конфликта имён.
If a new media feature tag is registered with the intent of using that tag with this specification, the registration is done for the unencoded form of the tag (see Section 5). In other words, if a new feature tag "foo" is registered in the IETF tree, the IANA registration would be for the tag "foo" and not "+foo". Similarly, if a new feature tag "sip.gruu" is registered in the SIP tree, the IANA registration would be for the tag "sip.gruu" and not "+sip.gruu" or "gruu". As such, all registrations into the SIP tree will have the "sip." prefix.
Если новый тег медиа-признака регистрируется с намерением использовать этот тег с данной спецификацией, регистрация выполняется для некодированной формы тега (см. раздел 5). Иными словами, если новый тег признака «foo» регистрируется в дереве IETF, регистрация IANA была бы для тега «foo», а не «+foo». Аналогично, если новый тег признака «sip.gruu» регистрируется в дереве SIP, регистрация IANA была бы для тега «sip.gruu», а не «+sip.gruu» или «gruu». Таким образом, все регистрации в дереве SIP будут иметь префикс «sip.».
The feature tags in this section are all registered in the SIP media feature tag tree created by Section 12.1.
Все теги признаков в этом разделе зарегистрированы в дереве тегов медиа-признаков SIP, созданном разделом 12.1.

11. Security Considerations
11. Вопросы безопасности
11.1. Considerations for Media Feature Tags
11.1. Вопросы безопасности тегов медиа-признаков
This section discusses security considerations for the media feature tags, including, but not limited to, this specification. The media feature tags defined in Section 10 reveal sensitive information about a user or the user agent they are describing. Some of the feature tags convey capability information about the agent - for example, the media types it can support, the SIP methods it can support, and the SIP extensions it can support. This capability information might be used for industrial espionage, for example, and so its protection may be important. Other attributes, such as the mobility, priority, and isfocus attributes, reveal characteristics of the user agent. These attributes are more sensitive than the capability information. They describe the way in which a user agent is utilized by a user, and thus reveal information about user preferences and the ways in which they want calls handled. Some feature tags, such as languages, reveal information about the user themself. As a result, applications which utilize these media feature tags SHOULD provide a means for ensuring their confidentiality.
В этом разделе рассматриваются вопросы безопасности тегов медиа-признаков, в том числе (но не только) определённых в этой спецификации. Теги медиа-признаков, определённые в разделе 10, раскрывают конфиденциальную информацию о пользователе или описываемом агенте пользователя. Некоторые теги признаков передают информацию о возможностях агента — например, поддерживаемые им типы медиаданных, методы SIP и расширения SIP. Эта информация о возможностях может использоваться, например, для промышленного шпионажа, поэтому её защита может быть важна. Другие атрибуты, такие как mobility, priority и isfocus, раскрывают характеристики агента пользователя. Эти атрибуты более чувствительны, чем информация о возможностях. Они описывают то, как пользователь использует агента пользователя, и тем самым раскрывают информацию о предпочтениях пользователя и о том, как он хочет обрабатывать вызовы. Некоторые теги признаков, например языки, раскрывают информацию о самом пользователе. В результате приложения, использующие эти теги медиа-признаков, SHOULD обеспечивать средство защиты их конфиденциальности.
The media feature tags can be used in ways which affect application behaviors. For example, the SIP caller preferences extension [11] allows for call routing decisions to be based on the values of these parameters. Therefore, if an attacker can modify the values of these feature tags, they may be able to affect the behavior of applications. As a result of this, applications which utilize these media feature tags SHOULD provide a means for ensuring their integrity. Similarly, media feature tags should only be trusted as valid when they come from the user or user agent described by those feature tags. As a result, mechanisms for conveying feature tags SHOULD provide a mechanism for guaranteeing authenticity.
Теги медиа-признаков можно использовать способами, влияющими на поведение приложений. Например, расширение предпочтений вызывающего абонента SIP [11] позволяет принимать решения о маршрутизации вызовов на основе значений этих параметров. Поэтому, если злоумышленник может изменить значения этих тегов признаков, он может повлиять на поведение приложений. Вследствие этого приложения, использующие эти теги медиа-признаков, SHOULD обеспечивать средство защиты их целостности. Аналогично тегам медиа-признаков следует доверять как действительным только тогда, когда они исходят от пользователя или агента пользователя, описываемого этими тегами. В результате механизмы передачи тегов признаков SHOULD обеспечивать механизм гарантии подлинности.
11.2. Considerations for Registrations
11.2. Вопросы безопасности регистраций
As per the general requirements in Section 11.1, when media feature tags are carried in a registration, authenticity, confidentiality, and integrity need to be provided. To accomplish this, registrations containing capability information SHOULD be made by addressing the registration to a SIPS URI (in other words, the Request URI of the request would be sips:example.com when creating a registration in the example.com domain). Furthermore, the registrar SHOULD challenge the UA using digest over TLS, to verify its authenticity. The combination of TLS and digest provide integrity, confidentiality, and authenticity, as required.
Согласно общим требованиям раздела 11.1, когда теги медиа-признаков передаются в регистрации, необходимо обеспечить подлинность, конфиденциальность и целостность. Для этого регистрации, содержащие информацию о возможностях, SHOULD выполняться путём адресации регистрации на URI SIPS (иными словами, Request URI запроса был бы sips:example.com при создании регистрации в домене example.com). Более того, регистратор SHOULD запрашивать у UA аутентификацию с использованием digest поверх TLS для проверки его подлинности. Сочетание TLS и digest обеспечивает требуемые целостность, конфиденциальность и подлинность.
It is not necessary for the Contact in the registration to itself contain a sips URI, since the feature tags are not carried in incoming requests sent to the UA.
Не обязательно, чтобы Contact в регистрации сам содержал URI sips, поскольку теги признаков не передаются во входящих запросах, отправляемых UA.
11.3. Considerations for OPTIONS Responses
11.3. Вопросы безопасности ответов OPTIONS
When including information on capabilities in a response to an OPTIONS request, a UA SHOULD verify with the user (either through a user interface or though prior configuration) whether or not capability information should be divulged to the requester. If the identity of the requester cannot be cryptographically verified (using digest or the SIP identity enhancements [15]), the user SHOULD also be alerted to this fact, and be allowed to choose whether such information should be divulged.
Когда UA включает информацию о возможностях в ответ на запрос OPTIONS, он SHOULD выяснить у пользователя (через пользовательский интерфейс или посредством предварительной настройки), следует ли раскрывать информацию о возможностях запрашивающей стороне. Если личность запрашивающей стороны не может быть криптографически проверена (с помощью digest или расширений идентичности SIP [15]), пользователь SHOULD также быть предупреждён об этом и иметь возможность выбрать, следует ли раскрывать такую информацию.
If the user does wish to reveal capability information to the requester, and wishes to guarantee its confidentiality, but the request did not arrive using SIPS, the UAS SHOULD redirect the request to a sips URI. This will cause the UAC to send the OPTIONS request using SIPS instead, and therefore provide confidentiality of any responses sent over the secure connections.
Если пользователь действительно желает раскрыть информацию о возможностях запрашивающей стороне и хочет гарантировать её конфиденциальность, но запрос поступил не через SIPS, UAS SHOULD перенаправить запрос на URI sips. Это заставит UAC отправить запрос OPTIONS с использованием SIPS и тем самым обеспечит конфиденциальность любых ответов, передаваемых по защищённым соединениям.
Furthermore, S/MIME MAY be used in the OPTIONS response. In that case, the capability information would be contained only in the secured S/MIME body, and not in the header fields of the OPTIONS response.
Кроме того, в ответе OPTIONS MAY использоваться S/MIME. В этом случае информация о возможностях содержалась бы только в защищённом теле S/MIME, а не в заголовочных полях ответа OPTIONS.
11.4. Considerations for Dialog Initiating Messages
11.4. Вопросы безопасности сообщений, инициирующих диалог
When a UAS generates a response that will initiate a dialog, and they wish to include capability information in the Contact header field, the same considerations as described in Section 11.3 apply.
Когда UAS формирует ответ, который инициирует диалог, и желает включить информацию о возможностях в заголовочное поле Contact, применяются те же соображения, что описаны в разделе 11.3.
When a UAC generates a request that will initiate a dialog, it SHOULD obtain permission from the user (either through a user interface or apriori configuration) before including capability information in the Contact header field of the request. Confidentiality and integrity of the information SHOULD be provided using SIPS. S/MIME MAY be used.
Когда UAC формирует запрос, который инициирует диалог, он SHOULD получить разрешение пользователя (через пользовательский интерфейс или предварительную конфигурацию) перед включением информации о возможностях в заголовочное поле Contact запроса. Конфиденциальность и целостность информации SHOULD обеспечиваться с использованием SIPS. MAY использоваться S/MIME.

12.1. SIP Media Feature Tag Registration Tree

This specification serves to create a new media feature tag registration tree, per the guidelines of Section 3.1.4 of RFC 2506 [3]. The name of this tree is the "SIP Media Feature Tag Registration Tree", and its prefix is "sip.". It is used for the registration of media feature tags that are applicable to the Session Initiation Protocol, and whose meaning is only defined within that usage.
Эта спецификация создаёт новое дерево регистрации тегов медиа-признаков в соответствии с руководящими указаниями раздела 3.1.4 RFC 2506 [3]. Имя этого дерева — «SIP Media Feature Tag Registration Tree», а его префикс — «sip.». Оно используется для регистрации тегов медиа-признаков, применимых к протоколу инициирования сессий и значение которых определено только в рамках такого использования.
The addition of entries into this registry occurs through IETF consensus, as defined in RFC 2434 [18]. This requires the publication of an RFC that contains the registration. The information required in the registration is identical to the IETF tree. As such, specifications adding entries to the registry should use the template provided in Section 3.4 of RFC 2506. Note that all media feature tags registered in the SIP tree will have names with a prefix of "sip.". No leading "+" is used in the registrations in any of the media feature tag trees.

Информация, требуемая при регистрации, идентична информации дерева IETF. Поэтому спецификации, добавляющие записи в реестр, должны использовать шаблон, предоставленный в разделе 3.4 RFC 2506. Обратите внимание, что все теги медиа-признаков, зарегистрированные в дереве SIP, будут иметь имена с префиксом «sip.». Ведущий «+» не используется в регистрациях ни в одном из деревьев тегов медиа-признаков.

Appendix A. Overview of RFC 2533
Приложение A. Обзор RFC 2533
This section provides a brief overview of RFC 2533 and related specifications that form the content negotiation framework. This section does not represent normative behavior. In the event of any conflict between the tutorial material here and the normative text in RFC 2533, RFC 2533 takes precedence.
В этом разделе приводится краткий обзор RFC 2533 и связанных спецификаций, образующих framework согласования содержимого. Этот раздел не представляет нормативного поведения. В случае любого конфликта между учебным материалом здесь и нормативным текстом RFC 2533 преимущество имеет RFC 2533.
A critical concept in the framework is that of a feature set. A feature set is information about an entity (in our case, a UA), which describes a set of features it can handle. A feature set can be thought of as a region in N-dimensional space. Each dimension in this space is a different media feature, identified by a media feature tag. For example, one dimension (or axis) might represent languages, another might represent methods, and another, MIME types. A feature collection represents a single point in this space. It represents a particular rendering or instance of an entity (in our case, a UA). For example, a "rendering" of a UA would define an instantaneous mode of operation that it can support. One such rendering would be processing the INVITE method, which carried the application/sdp MIME type, sent to a UA for a user that is speaking English.
Критически важным понятием в framework является набор признаков. Набор признаков — это информация об объекте (в нашем случае о UA), описывающая набор признаков, которые он может обрабатывать. Набор признаков можно рассматривать как область в N-мерном пространстве. Каждое измерение этого пространства — это отдельный медиа-признак, идентифицируемый тегом медиа-признака. Например, одно измерение (или ось) может представлять языки, другое — методы, а ещё одно — типы MIME. Коллекция признаков представляет одну точку в этом пространстве. Она представляет конкретное представление или экземпляр объекта (в нашем случае UA). Например, «представление» UA определяло бы мгновенный режим работы, который он может поддерживать. Одним из таких представлений была бы обработка метода INVITE, несшего тип MIME application/sdp, отправленного UA для пользователя, говорящего по-английски.
A feature set can therefore be defined as a set of feature collections. In other words, a feature set is a region of N- dimensional feature-space, that region being defined by the set of points - feature collections - that make up the space. If a particular feature collection is in the space, it means that the rendering described by that feature collection is supported by the device with that feature set.
Таким образом, набор признаков можно определить как набор коллекций признаков. Иными словами, набор признаков — это область N-мерного пространства признаков, определяемая набором точек — коллекций признаков, — составляющих это пространство. Если конкретная коллекция признаков находится в этом пространстве, это означает, что представление, описываемое этой коллекцией признаков, поддерживается устройством с таким набором признаков.
How does one represent a feature set? There are many ways to describe an N-dimensional space. One way is to identify mathematical functions which identify its contours. Clearly, that is too complex to be useful. The solution taken in RFC 2533 is to define the space with a feature set predicate. A feature predicate defines a relation over an N-dimensional space; its input is any point in that space (i.e., a feature collection), and is true for all points that are in the region thus defined.
Как представить набор признаков? Существует много способов описать N-мерное пространство. Один из способов — определить математические функции, задающие его контуры. Очевидно, это слишком сложно, чтобы быть полезным. Решение, принятое в RFC 2533, состоит в определении пространства с помощью предиката набора признаков. Предикат признаков определяет отношение над N-мерным пространством; его входом является любая точка этого пространства (то есть коллекция признаков), и он истинен для всех точек, входящих в определённую таким образом область.
RFC 2533 describes a syntax for writing down these N-dimensional boolean functions, borrowed from LDAP [14]. It uses a prolog-style syntax which is fairly self-explanatory. This representation is called a feature set predicate. The base unit of the predicate is a filter, which is a boolean expression encased in round brackets. A filter can be complex, where it contains conjunctions and disjunctions of other filters, or it can be simple. A simple filter is one that expresses a comparison operation on a single media feature tag.
RFC 2533 описывает синтаксис для записи этих N-мерных логических функций, заимствованный из LDAP [14]. Он использует синтаксис в стиле Prolog, который довольно самоочевиден. Это представление называется предикатом набора признаков. Базовой единицей предиката является фильтр — логическое выражение, заключённое в круглые скобки. Фильтр может быть сложным, содержащим конъюнкции и дизъюнкции других фильтров, или простым. Простой фильтр — это фильтр, выражающий операцию сравнения для одного тега медиа-признака.
For example, consider the feature set predicate:
Например, рассмотрим предикат набора признаков:
(& (foo=A) (bar=B) (| (baz=C) (& (baz=D) (bif=E))))
(& (foo=A) (bar=B) (| (baz=C) (& (baz=D) (bif=E))))
This defines a function over four media features - foo, bar, baz, and bif. Any point in feature space with foo equal to A, bar equal to B, and baz equal to either C or D, and bif equal to E, is in the feature set defined by this feature set predicate.
Он определяет функцию над четырьмя медиа-признаками — foo, bar, baz и bif. Любая точка пространства признаков, в которой foo равно A, bar равно B, baz равно C или D, а bif равно E, входит в набор признаков, определяемый этим предикатом набора признаков.
Note that the predicate doesn't say anything about the number of dimensions in feature space. The predicate operates on a feature space of any number of dimensions, but only those dimensions labeled foo, bar, baz, and bif matter. The result is that values of other media features don't matter. The feature collection {foo=A,bar=B,baz=C,bop=F} is in the feature set described by the predicate, even though the media feature tag "bop" isn't mentioned. Feature set predicates are therefore inclusive by default. A feature collection is present unless the boolean predicate rules it out. This was a conscious design choice in RFC 2533.
Обратите внимание, что предикат ничего не говорит о числе измерений пространства признаков. Предикат действует в пространстве признаков с любым числом измерений, но имеют значение только измерения, помеченные foo, bar, baz и bif. В результате значения других медиа-признаков не важны. Коллекция признаков {foo=A,bar=B,baz=C,bop=F} входит в набор признаков, описываемый предикатом, хотя тег медиа-признака «bop» не упомянут. Поэтому предикаты наборов признаков по умолчанию включающие. Коллекция признаков присутствует, если логический предикат не исключает её. Это было сознательным проектным решением в RFC 2533.
RFC 2533 also talks about matching a preference with a capability set. This is accomplished by representing both with a feature set. A preference is a feature set - its a specification of a number of feature collections, any one of which would satisfy the requirements of the sender. A capability is also a feature set - its a specification of the feature collections that the recipient supports. There is a match when the spaces defined by both feature sets overlap. When there is overlap, there exists at least one feature collection that exists in both feature sets, and therefore a modality or rendering desired by the sender which is supported by the recipient.
RFC 2533 также говорит о сопоставлении предпочтения с набором возможностей. Это достигается представлением обоих в виде набора признаков. Предпочтение — это набор признаков, то есть спецификация ряда коллекций признаков, любая из которых удовлетворила бы требованиям отправителя. Возможность — это также набор признаков, то есть спецификация коллекций признаков, поддерживаемых получателем. Совпадение есть тогда, когда области, определяемые обоими наборами признаков, пересекаются. При наличии пересечения существует по крайней мере одна коллекция признаков, присутствующая в обоих наборах признаков, и, следовательно, модальность или представление, желаемые отправителем и поддерживаемые получателем.
This leads directly to the definition of a match. Two feature sets match if there exists at least one feature collection present in both feature sets.
Это непосредственно приводит к определению совпадения. Два набора признаков совпадают, если существует по крайней мере одна коллекция признаков, присутствующая в обоих наборах.
Computing a match for two general feature set predicates is not easy. Section 5 of RFC 2533 presents an algorithm for doing it by expanding an arbitrary expression into disjunctive normal form. However, the feature set predicates used by this specification are constrained. They are always in conjunctive normal form, with each term in the conjunction describing values for different media features. This makes computation of a match easy. It is computed independently for each media feature, and then the feature sets overlap if media features specified in both sets overlap. Computing the overlap of a single media feature is very straightforward, and is a simple matter of computing whether two finite sets overlap.
Вычисление совпадения для двух общих предикатов наборов признаков — непростая задача. Раздел 5 RFC 2533 представляет алгоритм, делающий это путём разложения произвольного выражения в дизъюнктивную нормальную форму. Однако предикаты наборов признаков, используемые в этой спецификации, ограничены. Они всегда находятся в конъюнктивной нормальной форме, причём каждый терм конъюнкции описывает значения для разных медиа-признаков. Это делает вычисление совпадения простым. Оно вычисляется независимо для каждого медиа-признака, и затем наборы признаков пересекаются, если пересекаются медиа-признаки, указанные в обоих наборах. Вычисление пересечения одного медиа-признака очень просто и сводится к вычислению того, пересекаются ли два конечных набора.
