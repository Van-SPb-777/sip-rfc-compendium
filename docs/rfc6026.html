Correct Transaction Handling for 2xx Responses to Session Initiation Protocol (SIP) INVITE Requests
Корректная обработка транзакций для ответов 2xx на INVITE
Abstract
Аннотация
This document normatively updates RFC 3261, the Session Initiation Protocol (SIP), to address an error in the specified handling of success (2xx class) responses to INVITE requests. Elements following RFC 3261 exactly will misidentify retransmissions of the request as a new, unassociated request. The correction involves modifying the INVITE transaction state machines. The correction also changes the way responses that cannot be matched to an existing transaction are handled to address a security risk.
Настоящий документ нормативно обновляет RFC 3261 (протокол инициирования сессий, SIP), устраняя ошибку в заданной обработке успешных ответов (класса 2xx) на запросы INVITE. Элементы, точно следующие RFC 3261, будут ошибочно принимать повторные передачи запроса за новый, не связанный с ним запрос. Исправление состоит в изменении автоматов состояний транзакций INVITE. Исправление также меняет способ обработки ответов, которые не удаётся сопоставить существующей транзакции, чтобы устранить угрозу безопасности.

1. Introduction
1. Введение
This document describes an essential correction to the Session Initiation Protocol (SIP), defined in [RFC3261]. The change addresses an error in the handling of 2xx class responses to INVITE requests that leads to retransmissions of the INVITE being treated as new requests and forbids forwarding stray INVITE responses.
Настоящий документ описывает существенное исправление протокола инициирования сессий (SIP), определённого в [RFC3261]. Изменение устраняет ошибку в обработке ответов класса 2xx на запросы INVITE, из-за которой повторные передачи INVITE рассматриваются как новые запросы, и запрещает пересылку посторонних ответов на INVITE.
2. Conventions and Definitions
2. Соглашения и определения
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [RFC2119].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует понимать так, как описано в RFC 2119 [RFC2119].
3. Reason for Change
3. Причина изменения
One use of the INVITE method in SIP is to establish new sessions. These "initial" INVITEs may fork at intermediaries, and more than one receiving endpoint may choose to accept the request. SIP is designed such that the requester receives all of these success responses.
Одно из применений метода INVITE в SIP — установление новых сессий. Такие «начальные» INVITE могут разветвляться на промежуточных элементах, и более одной оконечной точки может принять запрос. SIP устроен так, что запрашивающая сторона получает все эти успешные ответы.
Two sets of requirements in [RFC3261] work together to allow multiple 2xx responses to be processed correctly by the requester. First, all elements are required to immediately destroy any INVITE client transaction state upon forwarding a matching 2xx class response. This requirement applies to both UAs (user agents) and proxies (proxies forward the response upstream, the transaction layer at user agents forwards the response to its "UA core"). Second, all proxies are required to statelessly forward upstream any 2xx class responses that do not match an existing transaction, also called stray responses. The transaction layer at user agents is required to forward these responses to its UA core. Logic in the UA core deals with acknowledging each of these responses.
Два набора требований в [RFC3261] совместно обеспечивают корректную обработку нескольких ответов 2xx запрашивающей стороной. Во-первых, все элементы обязаны немедленно уничтожать состояние клиентской транзакции INVITE при пересылке соответствующего ответа класса 2xx. Это требование относится и к UA (пользовательским агентам), и к прокси (прокси пересылают ответ вверх по потоку, транзакционный уровень пользовательских агентов передаёт ответ своему «ядру UA»). Во-вторых, все прокси обязаны без установления состояния пересылать вверх по потоку любые ответы класса 2xx, не соответствующие существующей транзакции, — так называемые посторонние ответы. Транзакционный уровень пользовательских агентов обязан передавать эти ответы своему ядру UA. Логика ядра UA обеспечивает подтверждение каждого из этих ответов.
This technique for specifying the behavior was chosen over adjusting INVITE client transaction state machines as a simpler way to specify the correct behavior.
Этот способ задания поведения был выбран вместо изменения автоматов состояний клиентской транзакции INVITE как более простой путь задать правильное поведение.
Over time, implementation experience demonstrated the existing text is in error. Once any element with a server transaction (say, a proxy in the path of the INVITE) deletes that transaction state, any retransmission of the INVITE will be treated as a new request, potentially forwarded to different locations than the original. Many implementations in the field have made proprietary adjustments to their transaction logic to avoid this error. The requirement to statelessly forward stray responses has also been identified as a security risk. Through it, elements compliant to [RFC3261] are compelled to do work (forward packets) that is not protected by the admission policies applied to requests. This can be leveraged to, for instance, use a SIP proxy as an anonymizing forwarder of packets in a distributed denial-of-service attack. General Internet endpoints can also collude to tunnel non-SIP content through such proxies by wrapping them in an SIP response envelope.
Со временем опыт реализации показал, что существующий текст содержит ошибку. Как только любой элемент с серверной транзакцией (скажем, прокси на пути INVITE) удаляет это состояние транзакции, любая повторная передача INVITE будет рассматриваться как новый запрос и, возможно, будет переслана в другие места, нежели исходный. Многие реализации на практике внесли собственные изменения в свою транзакционную логику, чтобы избежать этой ошибки. Требование без установления состояния пересылать посторонние ответы также было признано угрозой безопасности. Благодаря ему элементы, совместимые с [RFC3261], вынуждены выполнять работу (пересылать пакеты), не защищённую политиками допуска, применяемыми к запросам. Это можно использовать, например, чтобы задействовать SIP-прокси как анонимизирующий пересыльщик пакетов при распределённой атаке типа «отказ в обслуживании». Обычные оконечные точки Интернета также могут сговориться и туннелировать содержимое, не относящееся к SIP, через такие прокси, заворачивая его в конверт SIP-ответа.
Additionally, [RFC3261] requires that if an unrecoverable transport error is encountered while sending a response in a client transaction, that the transaction moves immediately into the "Terminated" state. This will result in any retransmitted INVITE requests received after such an error was encountered to be processed as a new request instead of being absorbed as a retransmission.
Кроме того, [RFC3261] требует, чтобы при обнаружении неустранимой ошибки транспорта при отправке ответа в клиентской транзакции эта транзакция немедленно переходила в состояние «Terminated». В результате любые повторно переданные запросы INVITE, полученные после такой ошибки, будут обрабатываться как новый запрос, а не поглощаться как повторная передача.
4. Summary of Change
4. Сводка изменения
This correction document updates [RFC3261], adding a state and changing the transitions in the INVITE client state machine such that the INVITE client transaction remains in place to receive multiple 2xx responses. It adds a state to the INVITE server state machine to absorb retransmissions of the INVITE after a 2xx response has been sent. It modifies state transitions in the INVITE server state machine to absorb retransmissions of the INVITE request after encountering an unrecoverable transport error when sending a response. It also forbids forwarding stray responses to INVITE requests (not just 2xx responses), which RFC 3261 requires.
Настоящий документ-исправление обновляет [RFC3261], добавляя состояние и изменяя переходы в автомате состояний клиентской транзакции INVITE так, чтобы клиентская транзакция INVITE оставалась на месте для приёма нескольких ответов 2xx. Он добавляет состояние в автомат состояний серверной транзакции INVITE, чтобы поглощать повторные передачи INVITE после отправки ответа 2xx. Он изменяет переходы состояний в автомате состояний серверной транзакции INVITE, чтобы поглощать повторные передачи запроса INVITE после неустранимой ошибки транспорта при отправке ответа. Он также запрещает пересылку посторонних ответов на запросы INVITE (не только ответов 2xx), чего требует RFC 3261.
5. Consequences if Not Implemented
5. Последствия при отказе от реализации
Implementations strictly conformant to [RFC3261] will process retransmitted initial INVITE requests as new requests. Proxies may forward them to different locations than the original. Proxies may also be used as anonymizing forwarders of bulk traffic. Implementations will process any retransmitted INVITE request as a new request after an attempt to send a response results in an unrecoverable error.
Реализации, строго соответствующие [RFC3261], будут обрабатывать повторно переданные начальные запросы INVITE как новые запросы. Прокси могут пересылать их в другие места, нежели исходный. Прокси также могут использоваться как анонимизирующие пересыльщики массового трафика. Реализации будут обрабатывать любой повторно переданный запрос INVITE как новый запрос после того, как попытка отправить ответ приведёт к неустранимой ошибке.
6. The Change
6. Изменение
An element sending or receiving a 2xx to an INVITE transaction MUST NOT destroy any matching INVITE transaction state. This state is necessary to ensure correct processing of retransmissions of the request and the retransmission of the 2xx and ACK that follow. An element encountering an unrecoverable transport error when trying to send a response to an INVITE request MUST NOT immediately destroy the associated INVITE server transaction state. This state is necessary to ensure correct processing of retransmissions of the request.
Элемент, отправляющий или получающий ответ 2xx на транзакцию INVITE, НЕ ДОЛЖЕН уничтожать какое-либо соответствующее состояние транзакции INVITE. Это состояние необходимо для корректной обработки повторных передач запроса и повторной передачи ответа 2xx и ACK, следующих за ним. Элемент, столкнувшийся с неустранимой ошибкой транспорта при попытке отправить ответ на запрос INVITE, НЕ ДОЛЖЕН немедленно уничтожать связанное состояние серверной транзакции INVITE. Это состояние необходимо для корректной обработки повторных передач запроса.
When receiving any SIP response, a transaction-stateful proxy MUST compare the transaction identifier in that response against its existing transaction state machines. The proxy MUST NOT forward the response if there is no matching transaction state machine.
При получении любого SIP-ответа прокси с установлением состояния транзакции ДОЛЖЕН сравнить идентификатор транзакции в этом ответе со своими существующими автоматами состояний транзакций. Прокси НЕ ДОЛЖЕН пересылать ответ, если нет соответствующего автомата состояний транзакции.
When receiving an ACK that matches an existing INVITE server transaction and that does not contain a branch parameter containing the magic cookie defined in RFC 3261, the matching transaction MUST be checked to see if it is in the "Accepted" state. If it is, then the ACK must be passed directly to the transaction user instead of being absorbed by the transaction state machine. This is necessary as requests from RFC 2543 clients will not include a unique branch parameter, and the mechanisms for calculating the transaction ID from such a request will be the same for both INVITE and ACKs.
При получении ACK, соответствующего существующей серверной транзакции INVITE и не содержащего параметр branch с «магическим cookie», определённым в RFC 3261, соответствующая транзакция ДОЛЖНА быть проверена: не находится ли она в состоянии «Accepted». Если находится, ACK должен передаваться непосредственно пользователю транзакции, а не поглощаться автоматом состояний транзакции. Это необходимо, поскольку запросы от клиентов RFC 2543 не будут содержать уникальный параметр branch, и механизмы вычисления идентификатора транзакции по такому запросу будут одинаковыми и для INVITE, и для ACK.
7. Change Details
7. Детали изменения
These changes impact requirements in several sections of RFC 3261. The exact effect on that text is detailed in Section 8. This section describes the details of the change, particularly the impact on the INVITE state machines, more succinctly to facilitate review and simplify implementation.
Эти изменения затрагивают требования в нескольких разделах RFC 3261. Точное влияние на этот текст подробно описано в разделе 8. В настоящем разделе подробности изменения, в частности влияние на автоматы состояний INVITE, изложены более сжато, чтобы облегчить рассмотрение и упростить реализацию.
7.1. Server Transaction Impacts
7.1. Влияние на серверную транзакцию
To allow a SIP element to recognize retransmissions of an INVITE as retransmissions instead of new requests, a new state, "Accepted", is added to the INVITE server transaction state machine. A new timer, Timer L, is also added to ultimately allow the state machine to terminate. A server transaction in the "Proceeding" state will transition to the "Accepted" state when it issues a 2xx response and will remain in that state just long enough to absorb any retransmissions of the INVITE.
Чтобы SIP-элемент мог распознавать повторные передачи INVITE как повторные передачи, а не как новые запросы, в автомат состояний серверной транзакции INVITE добавляется новое состояние «Accepted». Также добавляется новый таймер — таймер L, позволяющий автомату в конечном счёте завершиться. Серверная транзакция в состоянии «Proceeding» перейдёт в состояние «Accepted», когда выдаст ответ 2xx, и останется в этом состоянии ровно настолько, чтобы поглотить любые повторные передачи INVITE.
If the SIP element's TU (Transaction User) issues a 2xx response for this transaction while the state machine is in the "Proceeding" state, the state machine MUST transition to the "Accepted" state and set Timer L to 64*T1, where T1 is the round-trip time estimate defined in Section 17.1.1.1 of [RFC3261]. While in the "Accepted" state, any retransmissions of the INVITE received will match this transaction state machine and will be absorbed by the machine without changing its state. These retransmissions are not passed onto the TU. RFC 3261 requires the TU to periodically retransmit the 2xx response until it receives an ACK. The server transaction MUST NOT generate 2xx retransmissions on its own. Any retransmission of the 2xx response passed from the TU to the transaction while in the "Accepted" state MUST be passed to the transport layer for transmission. Any ACKs received from the network while in the "Accepted" state MUST be passed directly to the TU and not absorbed.
Если TU (пользователь транзакции) SIP-элемента выдаёт ответ 2xx для этой транзакции, пока автомат состояний находится в состоянии «Proceeding», автомат ДОЛЖЕН перейти в состояние «Accepted» и установить таймер L в 64*T1, где T1 — оценка времени кругового обхода, определённая в разделе 17.1.1.1 [RFC3261]. Пока он находится в состоянии «Accepted», любые полученные повторные передачи INVITE будут соответствовать этому автомату состояний транзакции и будут поглощаться автоматом без изменения его состояния. Эти повторные передачи не передаются в TU. RFC 3261 требует, чтобы TU периодически повторно передавал ответ 2xx, пока не получит ACK. Серверная транзакция НЕ ДОЛЖНА порождать повторные передачи 2xx самостоятельно. Любая повторная передача ответа 2xx, переданного от TU транзакции, пока она находится в состоянии «Accepted», ДОЛЖНА передаваться транспортному уровню для отправки. Любые ACK, полученные из сети, пока транзакция находится в состоянии «Accepted», ДОЛЖНЫ передаваться непосредственно в TU и не поглощаться.
When Timer L fires and the state machine is in the "Accepted" state, the machine MUST transition to the "Terminated" state. Once the transaction is in the "Terminated" state, it MUST be destroyed immediately. Timer L reflects the amount of time the server transaction could receive 2xx responses for retransmission from the TU while it is waiting to receive an ACK.
Когда таймер L срабатывает, а автомат состояний находится в состоянии «Accepted», автомат ДОЛЖЕН перейти в состояние «Terminated». Как только транзакция оказывается в состоянии «Terminated», она ДОЛЖНА быть немедленно уничтожена. Таймер L отражает время, в течение которого серверная транзакция могла получать ответы 2xx для повторной передачи от TU, ожидая получения ACK.
A server transaction MUST NOT discard transaction state based only on encountering a non-recoverable transport error when sending a response. Instead, the associated INVITE server transaction state machine MUST remain in its current state. (Timers will eventually cause it to transition to the "Terminated" state). This allows retransmissions of the INVITE to be absorbed instead of being processed as a new request.
Серверная транзакция НЕ ДОЛЖНА отбрасывать состояние транзакции только на том основании, что при отправке ответа возникла неустранимая ошибка транспорта. Вместо этого связанный автомат состояний серверной транзакции INVITE ДОЛЖЕН оставаться в текущем состоянии. (Таймеры в конечном счёте вызовут его переход в состояние «Terminated».) Это позволяет поглощать повторные передачи INVITE, а не обрабатывать их как новый запрос.

7.2. Client Transaction Impacts
7.2. Влияние на клиентскую транзакцию
In order to correctly distinguish retransmissions of 2xx responses from stray 2xx responses, the INVITE client state machine is modified to not transition immediately to "Terminated" on receipt of a 2xx response. Instead, the machine will transition to a new "Accepted" state, and remain there just long enough, determined by a new timer M, to receive and pass to the TU any retransmissions of the 2xx response or any additional 2xx responses from other branches of a downstream fork of the matching request. If a 2xx response is received while the client INVITE state machine is in the "Calling" or "Proceeding" states, it MUST transition to the "Accepted" state, pass the 2xx response to the TU, and set Timer M to 64*T1. A 2xx response received while in the "Accepted" state MUST be passed to the TU and the machine remains in the "Accepted" state. The client transaction MUST NOT generate an ACK to any 2xx response on its own. The TU responsible for the transaction will generate the ACK.
Чтобы правильно отличать повторные передачи ответов 2xx от посторонних ответов 2xx, автомат состояний клиентской транзакции INVITE изменяется так, чтобы не переходить немедленно в состояние «Terminated» при получении ответа 2xx. Вместо этого автомат перейдёт в новое состояние «Accepted» и останется там ровно настолько, сколько определяется новым таймером M, чтобы принимать и передавать в TU любые повторные передачи ответа 2xx или любые дополнительные ответы 2xx от других ветвей нижестоящего ответвления соответствующего запроса. Если ответ 2xx получен, пока автомат состояний клиентской транзакции INVITE находится в состоянии «Calling» или «Proceeding», он ДОЛЖЕН перейти в состояние «Accepted», передать ответ 2xx в TU и установить таймер M в 64*T1. Ответ 2xx, полученный в состоянии «Accepted», ДОЛЖЕН быть передан в TU, и автомат остаётся в состоянии «Accepted». Клиентская транзакция НЕ ДОЛЖНА порождать ACK для какого-либо ответа 2xx самостоятельно. ACK будет порождать TU, отвечающий за транзакцию.
When Timer M fires and the state machine is in the "Accepted" state, the machine MUST transition to the "Terminated" state. Once the transaction is in the "Terminated" state, it MUST be destroyed immediately.
Когда таймер M срабатывает, а автомат состояний находится в состоянии «Accepted», автомат ДОЛЖЕН перейти в состояние «Terminated». Как только транзакция оказывается в состоянии «Terminated», она ДОЛЖНА быть немедленно уничтожена.
Any response received that does not match an existing client transaction state machine is simply dropped. (Implementations are, of course, free to log or do other implementation-specific things with such responses, but the implementer should be sure to consider the impact of large numbers of malicious stray responses.)
Любой полученный ответ, не соответствующий существующему автомату состояний клиентской транзакции, просто отбрасывается. (Реализации, разумеется, вольны журналировать такие ответы или делать с ними другие действия, зависящие от реализации, но разработчику следует обязательно учитывать последствия большого числа вредоносных посторонних ответов.)
Note that it is not necessary to preserve client transaction state upon the detection of unrecoverable transport errors. Existing requirements ensure the TU has been notified, and the new requirements in this document ensure that any received retransmitted response will be dropped since there will no longer be any matching transaction state.
Отметим, что сохранять состояние клиентской транзакции при обнаружении неустранимых ошибок транспорта не требуется. Существующие требования гарантируют, что TU уведомлён, а новые требования настоящего документа гарантируют, что любой полученный повторно переданный ответ будет отброшен, поскольку соответствующего состояния транзакции больше не будет.

7.3. Proxy Considerations
7.3. Соображения о прокси
This document changes the behavior of transaction-stateful proxies to not forward stray INVITE responses. When receiving any SIP response, a transaction-stateful proxy MUST compare the transaction identifier in that response against its existing transaction state machines. The proxy MUST NOT forward the response if there is no matching transaction state machine.
Настоящий документ изменяет поведение прокси с установлением состояния транзакции так, чтобы они не пересылали посторонние ответы на INVITE. При получении любого SIP-ответа прокси с установлением состояния транзакции ДОЛЖЕН сравнить идентификатор транзакции в этом ответе со своими существующими автоматами состояний транзакций. Прокси НЕ ДОЛЖЕН пересылать ответ, если нет соответствующего автомата состояний транзакции.

10. Security Considerations
10. Соображения безопасности
This document makes two changes to the Session Initiation Protocol to address the error discussed in Section 3. It changes the behavior of both the client and server INVITE transaction state machines, and it changes the way "stray" responses (those that don't match any existing transaction) are handled at transaction-stateful elements.
Настоящий документ вносит два изменения в протокол инициирования сессий, чтобы устранить ошибку, рассмотренную в разделе 3. Он изменяет поведение автоматов состояний клиентской и серверной транзакций INVITE, а также способ обработки «посторонних» ответов (тех, что не соответствуют никакой существующей транзакции) на элементах с установлением состояния транзакции.
The changes to the state machines cause elements to hold onto each accepted INVITE transaction state 32 seconds longer than what was specified in RFC 3261. This will have a direct impact on the amount of work an attacker that is leveraging state exhaustion will have to exert against the system. However, this additional state is necessary to achieve correct operation. There is some discussion of avoiding state exhaustion and other denial-of-service attacks in RFC 3261, Section 26.3.2.4.
Изменения в автоматах состояний заставляют элементы удерживать состояние каждой принятой транзакции INVITE на 32 секунды дольше, чем было указано в RFC 3261. Это напрямую повлияет на объём работы, которую злоумышленнику, использующему исчерпание состояния, придётся выполнить против системы. Однако это дополнительное состояние необходимо для корректной работы. В разделе 26.3.2.4 RFC 3261 есть некоторые рассуждения об избежании исчерпания состояния и других атак типа «отказ в обслуживании».
RFC 3261 required SIP proxies to forward any stray 2xx class responses to an INVITE request upstream statelessly. As a result, conformant proxies can be forced to forward packets (that look sufficiently like SIP responses) to destinations of the sender's choosing. Section 3 discusses some of the malicious behavior this enables. This document reverses the stateless forwarding requirement, making it a violation of the specification to forward stray responses.
RFC 3261 требовал от SIP-прокси без установления состояния пересылать вверх по потоку любые посторонние ответы класса 2xx на запрос INVITE. В результате соответствующие требованиям прокси можно принудить пересылать пакеты (достаточно похожие на SIP-ответы) в пункты назначения по выбору отправителя. В разделе 3 рассматривается часть вредоносного поведения, которое это позволяет. Настоящий документ отменяет требование о пересылке без установления состояния, делая пересылку посторонних ответов нарушением спецификации.
RFC 3261 defines a "stateless proxy", which forwards requests and responses without creating or maintaining any transaction state. The requirements introduced in this document do not change the behavior of these elements in any way. Stateless proxies are inherently vulnerable to the abuses discussed in Section 3. One way operators might mitigate this vulnerability is to carefully control which peer elements can present traffic to a given stateless proxy.
RFC 3261 определяет «прокси без установления состояния», который пересылает запросы и ответы, не создавая и не поддерживая никакого состояния транзакции. Требования, вводимые настоящим документом, никак не изменяют поведение этих элементов. Прокси без установления состояния по своей природе уязвимы для злоупотреблений, рассмотренных в разделе 3. Один из способов, которым операторы могут смягчить эту уязвимость, — тщательно контролировать, какие равноправные элементы могут передавать трафик данному прокси без установления состояния.
The changes introduced by this document are backward-compatible. Transaction behavior will be no less correct, and possibly more correct, when only one peer in a transaction implements these changes. Except for the considerations mentioned earlier in this section, introducing elements implementing these changes into deployments with RFC 3261 implementations adds no additional security concerns.
Изменения, вводимые настоящим документом, обратно совместимы. Поведение транзакций будет не менее корректным, а возможно, и более корректным, когда эти изменения реализует только один участник транзакции. За исключением соображений, упомянутых ранее в этом разделе, внедрение элементов, реализующих эти изменения, в развёртывания с реализациями RFC 3261 не добавляет никаких дополнительных проблем безопасности.
