Abstract
Аннотация
This document defines a Session Initiation Protocol (SIP) event package for registrations. Through its REGISTER method, SIP allows a user agent to create, modify, and delete registrations. Registrations can also be altered by administrators in order to enforce policy. As a result, these registrations represent a piece of state in the network that can change dynamically. There are many cases where a user agent would like to be notified of changes in this state. This event package defines a mechanism by which those user agents can request and obtain such notifications.
Этот документ определяет пакет событий протокола инициирования сессий (SIP) для регистраций. С помощью метода REGISTER SIP позволяет пользовательскому агенту создавать, изменять и удалять регистрации. Регистрации также могут быть изменены администраторами для обеспечения соблюдения политики. В результате эти регистрации представляют собой часть состояния сети, которая может динамически меняться. Во многих случаях пользовательский агент хотел бы получать уведомления об изменениях в этом состоянии. Этот пакет событий определяет механизм, с помощью которого эти пользовательские агенты могут запрашивать и получать такие уведомления.

1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [1] provides all of the functions needed for the establishment and maintenance of communications sessions between users. One of the functions it provides is a registration operation. A registration is a binding between a SIP URI, called an address-of-record, and one or more contact URIs. These contact URIs represent additional resources that can be contacted in order to reach the user identified by the address-of-record. When a proxy receives a request within its domain of administration, it uses the Request-URI as an address-of-record, and uses the contacts bound to the address-of-record to forward (or redirect) the request.
Протокол инициирования сессий (SIP) [1] предоставляет все функции, необходимые для установления и поддержания сессий связи между пользователями. Одной из предоставляемых функций является операция регистрации. Регистрация — это привязка между URI SIP, называемым адресом записи, и одним или несколькими URI контакта. Эти контактные URI представляют собой дополнительные ресурсы, с которыми можно связаться, чтобы связаться с пользователем, идентифицированным по адресу записи. Когда прокси получает запрос в пределах своего домена администрирования, он использует Request-URI в качестве адреса записи и использует контакты, привязанные к адресу записи, для пересылки (или перенаправления) запроса.
The SIP REGISTER method provides a way for a user agent to manipulate registrations. Contacts can be added or removed, and the current set of contacts can be queried. Registrations can also change as a result of administrator policy. For example, if a user is suspected of fraud, their registration can be deleted so that they cannot receive any requests. Registrations also expire after some time if not refreshed. Registrations represent a dynamic piece of state maintained by the network. There are many cases in which user agents would like to know about changes to the state of registrations. The SIP Events Framework [2] defines a generic framework for subscription to, and notification of, events related to SIP systems. The framework defines the methods SUBSCRIBE and NOTIFY, and introduces the notion of a package. A package is a concrete application of the event framework to a particular class of events. Packages have been defined for user presence [9], for example. This specification defines a package for registration state.
Метод SIP REGISTER предоставляет агенту пользователя возможность манипулировать регистрациями. Контакты можно добавлять или удалять, а также можно запросить текущий набор контактов. Регистрации также могут меняться в зависимости от политики администратора. Например, если пользователя подозревают в мошенничестве, его регистрацию можно удалить, чтобы он не мог получать никаких запросов. Регистрация также истекает через некоторое время, если ее не обновить. Регистрации представляют собой динамическую часть состояния, поддерживаемую сетью. Во многих случаях пользовательские агенты хотели бы знать об изменениях в состоянии регистрации. Структура событий SIP [2] определяет общую структуру для подписки и уведомления о событиях, связанных с системами SIP. Платформа определяет методы SUBSCRIBE и NOTIFY и вводит понятие пакета. Пакет — это конкретное применение структуры событий к определенному классу событий. Например, пакеты были определены для присутствия пользователя [9]. Эта спецификация определяет пакет для состояния регистрации.

3.2. Composing Presence
3.2. Составление присутствия
An important concept to understand is the relationship between this event package and the event package for user presence [9]. User presence represents the willingness and ability of a user to communicate with other users on the network. It is composed of a set of contact addresses that represent the various means for contacting the user. Those contact addresses might represent the contact address for voice, for example. Typically, the contact address listed for voice will be an address-of-record. The status of that contact (whether its open or closed) may depend on any number of factors, including the state of any registrations against that address-of-record. As a result, registration state can be viewed as an input to the process which determines the presence state of a user. Effectively, registration state is "raw" data, which is combined with other information about a user to generate a document that describes the user's presence.
Важно понимать взаимосвязь между этим пакетом событий и пакетом событий присутствия пользователя [9]. Присутствие пользователя представляет собой желание и способность пользователя общаться с другими пользователями в сети. Он состоит из набора контактных адресов, которые представляют собой различные способы связи с пользователем. Эти контактные адреса могут представлять собой, например, контактный адрес для голосовой связи. Обычно контактный адрес, указанный для голосовой связи, является адресом записи. Статус этого контакта (открытый или закрытый) может зависеть от любого количества факторов, включая состояние любых регистраций по этому адресу записи. В результате состояние регистрации можно рассматривать как входные данные для процесса, который определяет состояние присутствия пользователя. По сути, состояние регистрации — это данные «raw», которые объединяются с другой информацией о пользователе для создания документа, описывающего присутствие пользователя.
In fact, this event package allows for a presence server to be separated from a SIP registration server, yet still use registration information to construct a presence document. When a presence server receives a presence subscription for some user, the presence server itself would generate a subscription to the registration server for the registration event package. As a result, the presence server would learn about the registration state for that user, and it could use that information to generate presence documents.
Фактически, этот пакет событий позволяет отделить сервер присутствия от сервера регистрации SIP, но при этом использовать регистрационную информацию для создания документа присутствия. Когда сервер присутствия получает подписку о присутствии для некоторого пользователя, сервер присутствия сам генерирует подписку на сервер регистрации для пакета событий регистрации. В результате сервер присутствия узнает о состоянии регистрации этого пользователя и может использовать эту информацию для создания документов присутствия.
3.3. Welcome Notices
3.3. Приветственные уведомления
A common service in current mobile networks are "welcome notices". When the user turns on their phone in a foreign country, they receive a message that welcomes them to the country, and provides information on transportation services, for example.
Распространенной услугой в современных сетях мобильной связи являются «приветственные уведомления». Когда пользователь включает свой телефон в чужой стране, он получает сообщение, приветствующее его в стране и содержащее, например, информацию о транспортных услугах.
In order to implement this service in a SIP system, an application server can subscribe to the registration state of the user. When the user turns on their phone, the phone will generate a registration. This will result in a notification being sent to the application that the user has registered. The application can then send a SIP MESSAGE request [10] to the device, welcoming the user and providing any necessary information.
Чтобы реализовать эту услугу в системе SIP, сервер приложений может подписаться на состояние регистрации пользователя. Когда пользователь включит свой телефон, телефон сгенерирует регистрацию. В результате в приложение, которое зарегистрировал пользователь, будет отправлено уведомление. Затем приложение может отправить на устройство запрос SIP-СООБЩЕНИЯ [10], приветствуя пользователя и предоставляя всю необходимую информацию.

Of course, the server can apply any policy it likes to the subscription.

4.4. Subscription Duration
4.4. Продолжительность подписки
The SIP Events specification requires package definitions to define a default value for subscription durations, and to discuss reasonable choices for durations when they are explicitly specified.
Спецификация событий SIP требует, чтобы определения пакетов определяли значение по умолчанию для длительности подписки и обсуждали разумный выбор длительности, если она указана явно.
Registration state changes as contacts are created through REGISTER requests, and then time out due to lack of refresh. Their rate of change is therefore related to the typical registration expiration. Since the default expiration for registrations is 3600 seconds, the default duration of subscriptions to registration state is slightly longer, 3761 seconds. This helps avoid any potential problems with coupling of subscription and registration refreshes. Of course, clients MAY include an Expires header in the SUBSCRIBE request asking for a different duration.
Состояние регистрации меняется, когда контакты создаются с помощью запросов REGISTER, а затем истекает время ожидания из-за отсутствия обновления. Таким образом, скорость их изменения связана с типичным сроком действия регистрации. Поскольку срок действия регистрации по умолчанию составляет 3600 секунд, продолжительность подписки на состояние регистрации по умолчанию немного больше — 3761 секунда. Это помогает избежать потенциальных проблем с объединением обновлений подписки и регистрации. Конечно, клиенты МОГУТ включать заголовок Expires в запрос SUBSCRIBE, запрашивая другую продолжительность.
4.5. NOTIFY Bodies
4.5. УВЕДОМЛЯЮЩИЕ органы
The SIP Events specification requires package definitions to describe the allowed set of body types in NOTIFY requests, and to specify the default value to be used when there is no Accept header in the SUBSCRIBE request.
Спецификация событий SIP требует, чтобы определения пакетов описывали разрешенный набор типов тела в запросах NOTIFY и указывали значение по умолчанию, которое будет использоваться, когда в запросе SUBSCRIBE нет заголовка Accept.
The body of a notification of a change in registration state contains a registration information document. This document describes some or all of the contacts associated with a particular address-of-record. All subscribers and notifiers MUST support the "application/reginfo+xml" format described in Section 5. The subscribe request MAY contain an Accept header field. If no such header field is present, it has a default value of "application/reginfo+xml". If the header field is present, it MUST include "application/reginfo+xml", and MAY include any other types capable of representing registration information.
Тело уведомления об изменении состояния регистрации содержит документ с регистрационной информацией. В этом документе описываются некоторые или все контакты, связанные с конкретным адресом записи. Все подписчики и уведомители ДОЛЖНЫ поддерживать формат «application/reginfo+xml», описанный в разделе 5. Запрос на подписку МОЖЕТ содержать поле заголовка Accept. Если такое поле заголовка отсутствует, оно имеет значение по умолчанию «application/reginfo+xml». Если поле заголовка присутствует, оно ДОЛЖНО включать «application/reginfo+xml» и МОЖЕТ включать любые другие типы, способные представлять регистрационную информацию.
Of course, the notifications generated by the server MUST be in one of the formats specified in the Accept header field in the SUBSCRIBE request.
Разумеется, уведомления, формируемые сервером, ДОЛЖНЫ быть в одном из форматов, указанных в поле заголовка Accept запроса SUBSCRIBE.
4.6. Notifier Processing of SUBSCRIBE Requests
4.6. Обработка уведомлений запросами на ПОДПИСКУ
The SIP Events framework specifies that packages should define any package-specific processing of SUBSCRIBE requests at a notifier, specifically with regards to authentication and authorization.
Структура SIP Events определяет, что пакеты должны определять любую специфичную для пакета обработку запросов SUBSCRIBE у уведомителя, особенно в отношении аутентификации и авторизации.
Registration state can be sensitive information. Therefore, all subscriptions to it SHOULD be authenticated and authorized before approval. Authentication MAY be performed using any of the techniques available through SIP, including digest, S/MIME, TLS or other transport specific mechanisms [1]. Authorization policy is at the discretion of the administrator, as always. However, a few recommendations can be made.
Состояние регистрации может быть конфиденциальной информацией. Поэтому все подписки на него ДОЛЖНЫ быть аутентифицированы и авторизованы перед утверждением. Аутентификация МОЖЕТ выполняться с использованием любого из методов, доступных через SIP, включая дайджест, S/MIME, TLS или другие механизмы, специфичные для транспорта [1]. Политика авторизации, как всегда, на усмотрение администратора. Однако можно дать несколько рекомендаций.
It is RECOMMENDED that a user be allowed to subscribe to their own registration state. Such subscriptions are useful when there are many devices that represent a user, each of which needs to learn the registration state of the other devices. We also anticipate that applications and automata will frequently be subscribers to the registration state. In those cases, authorization policy will typically be provided ahead of time.
РЕКОМЕНДУЕТСЯ разрешить пользователю подписаться на свой собственный статус регистрации. Такие подписки полезны, когда имеется множество устройств, представляющих пользователя, каждому из которых необходимо узнать состояние регистрации других устройств. Мы также ожидаем, что приложения и автоматы часто будут подписчиками состояния регистрации. В таких случаях политика авторизации обычно предоставляется заранее.
4.7. Notifier Generation of NOTIFY Requests
4.7. Генерация уведомлений уведомителем запросов NOTIFY
The SIP Event framework requests that packages specify the conditions under which notifications are sent for that package, and how such notifications are constructed.
Платформа событий SIP требует, чтобы пакеты указывали условия, при которых отправляются уведомления для этого пакета, и способ создания таких уведомлений.
To determine when a notifier should send notifications of changes in registration state, we define a finite state machine (FSM) that represents the state of a contact for a particular address-of-record. Transitions in this state machine MAY result in the generation of notifications. These notifications will carry information on the new state and the event which triggered the state change. It is important to note that this FSM is just a model of the registration state machinery maintained by a server. An implementation would map its own state machines to this one in an implementation-specific manner.
Чтобы определить, когда уведомитель должен отправлять уведомления об изменениях состояния регистрации, мы определяем конечный автомат (FSM), который представляет состояние контакта для определенного адреса записи. Переходы в этом автомате МОГУТ привести к генерации уведомлений. Эти уведомления будут содержать информацию о новом состоянии и событии, которое вызвало изменение состояния. Важно отметить, что этот автомат представляет собой всего лишь модель механизма регистрации, поддерживаемого сервером. Реализация будет отображать свои собственные конечные автоматы в этом автомате в зависимости от реализации.

Когда срок действия последнего контакта истечет или будет удален, регистрация перейдет в состояние прекращено. После этого он немедленно возвращается в исходное состояние. Этот переход невидим, поскольку о нем НЕ ДОЛЖНО сообщаться подписчику в запросе NOTIFY. Это позволяет оптимизировать реализацию, благодаря чему регистратор может уничтожить объекты, связанные с конечным автоматом регистрации, как только он перейдет в состояние завершения и будет отправлено уведомление NOTIFY. Вместо этого регистратор может предположить, что, если объекты для этого конечного автомата больше не существуют, конечный автомат находится в состоянии инициализации.

The FSM remains in the active state so long as the contact is bound to the address-of-record. When a contact is refreshed through a REGISTER request, the FSM stays in the same state, but a refreshed event is generated. Likewise, when an administrator modifies the expiration time of a binding (without deleting the binding) to trigger the contact to re-register and possibly re-authenticate, the FSM stays in the active state, but a shortened event is generated.
FSM остается в активном состоянии до тех пор, пока контакт привязан к адресу записи. Когда контакт обновляется с помощью запроса REGISTER, FSM остается в том же состоянии, но генерируется событие обновления. Аналогичным образом, когда администратор изменяет срок действия привязки (не удаляя привязку), чтобы вызвать повторную регистрацию контакта и, возможно, повторную аутентификацию, FSM остается в активном состоянии, но генерируется сокращенное событие.
When the contact is no longer bound to the address-of-record, the FSM moves to the terminated state, and once a NOTIFY is sent, the state machine is destroyed. As a result, the terminated state is effectively transient. There are several reasons this can happen. The first is an expiration, which occurs when the contact was not refreshed by a REGISTER request. The second reason is deactivated. This occurs when the administrator has removed the contact as a valid binding, but still wishes the client to attempt to re-register the contact. In contrast, the rejected event occurs when an active contact is removed by the administrator, but re-registrations will not help to re-establish it. This might occur if a user does not pay their bills, for example. The probation event occurs when an active contact is removed by the administrator, and the administrator wants the client to re-register, but to do so at a later time. The unregistered event occurs when a REGISTER request sets the expiration time of that contact to zero.
Когда контакт больше не привязан к адресу записи, FSM переходит в состояние завершения, и как только отправляется NOTIFY, конечный автомат уничтожается. В результате прекращенное состояние фактически является временным. Это может произойти по нескольким причинам. Первый — это истечение срока действия, которое происходит, когда контакт не был обновлен запросом REGISTER. Вторая причина деактивирована. Это происходит, когда администратор удалил контакт как действительную привязку, но по-прежнему хочет, чтобы клиент попытался перерегистрировать контакт. Напротив, событие отклонения происходит, когда активный контакт удаляется администратором, но повторная регистрация не поможет восстановить его. Это может произойти, например, если пользователь не оплачивает свои счета. Событие испытательного срока происходит, когда активный контакт удаляется администратором, и администратор хочет, чтобы клиент перерегистрировался, но сделал это позже. Незарегистрированное событие происходит, когда запрос REGISTER устанавливает время истечения срока действия этого контакта равным нулю.
4.7.2. Applying the state machine
4.7.2. Применение государственной машины
The server MAY generate a notification to subscribers when any event occurs in either the address-of-record or per-contact state machines, except for the transition from terminated to init in the address-of- record state machine. As noted above, a notification MUST NOT be sent in this case. For other transitions, whether the server sends a notification or not is policy dependent. However, several guidelines are defined.
Сервер МОЖЕТ генерировать уведомление подписчикам, когда происходит какое-либо событие либо в автомате состояния адреса записи, либо в автомате состояния каждого контакта, за исключением перехода от завершения к инициализации в автомате состояния адреса записи. Как отмечалось выше, в этом случае НЕ ДОЛЖНО отправляться уведомление. Для других переходов то, отправляет ли сервер уведомление или нет, зависит от политики. Тем не менее, определены несколько руководящих принципов.
As a general rule, when a subscriber is authorized to receive notifications about a set of registrations, it is RECOMMENDED that notifications contain information about those contacts which have changed state (and thus triggered a notification), instead of delivering the current state of every contact in all registrations. However, notifications triggered as a result of a fetch operation (a SUBSCRIBE with Expires of 0) SHOULD result in the full state of all contacts for all registrations to be present in the NOTIFY.
Как правило, когда подписчику разрешено получать уведомления о наборе регистраций, РЕКОМЕНДУЕТСЯ, чтобы уведомления содержали информацию о тех контактах, которые изменили состояние (и, таким образом, вызвали уведомление), вместо доставки текущего состояния каждого контакта во всех регистрациях. Однако уведомления, вызванные в результате операции выборки (SUBSCRIBE со сроком действия 0), ДОЛЖНЫ привести к тому, что полное состояние всех контактов для всех регистраций будет присутствовать в NOTIFY.
4.8. Subscriber Processing of NOTIFY Requests
4.8. Обработка подписчиком запросов NOTIFY
The SIP Events framework expects packages to specify how a subscriber processes NOTIFY requests in any package specific ways, and in particular, how it uses the NOTIFY requests to construct a coherent view of the state of the subscribed resource. Typically, the NOTIFY will only contain information for contacts whose state has changed. To construct a coherent view of the total state of all registrations, the subscriber will need to combine NOTIFYs received over time. The details of this process depend on the document format used to convey registration state. Section 5 outlines the process for the application/reginfo+xml format.
Платформа SIP Events ожидает, что пакеты будут указывать, как подписчик обрабатывает запросы NOTIFY любыми способами, специфичными для пакета, и, в частности, как он использует запросы NOTIFY для создания согласованного представления о состоянии подписанного ресурса. Обычно NOTIFY содержит информацию только о контактах, состояние которых изменилось. Чтобы создать целостное представление общего состояния всех регистраций, подписчику необходимо будет объединить уведомления NOTIFY, полученные с течением времени. Детали этого процесса зависят от формата документа, используемого для передачи состояния регистрации. В разделе 5 описывается процесс для формата application/reginfo+xml.
4.9. Handling of Forked Requests
4.9. Обработка разветвленных запросов
The SIP Events framework mandates that packages indicate whether or not forked SUBSCRIBE requests can install multiple subscriptions.
Платформа событий SIP требует, чтобы пакеты указывали, могут ли разветвленные запросы SUBSCRIBE устанавливать несколько подписок.
Registration state is normally stored in some repository (whether it be co-located with a proxy/registrar or in a separate database). As such, there is usually a single place where the contact information for a particular address-of-record is resident. This implies that a subscription for this information is readily handled by a single element with access to this repository. There is, therefore, no compelling need for a subscription to registration information to fork. As a result, a subscriber MUST NOT create multiple dialogs as a result of a single subscription request. The required processing to guarantee that only a single dialog is established is described in Section 4.4.9 of the SIP Events framework [2].
Состояние регистрации обычно хранится в каком-либо репозитории (независимо от того, находится ли он рядом с прокси/регистратором или в отдельной базе данных). Таким образом, обычно существует одно место, где находится контактная информация для определенного адреса записи. Это означает, что подписка на эту информацию легко обрабатывается одним элементом, имеющим доступ к этому репозиторию. Таким образом, нет острой необходимости в подписке на регистрационную информацию для форка. В результате подписчик НЕ ДОЛЖЕН создавать несколько диалогов в результате одного запроса на подписку. Необходимая обработка, гарантирующая установление только одного диалога, описана в разделе 4.4.9 структуры SIP Events [2].
4.10. Rate of Notifications
4.10. Скорость уведомлений
The SIP Events framework mandates that packages define a maximum rate of notifications for their package.
Структура событий SIP требует, чтобы пакеты определяли максимальную частоту уведомлений для своего пакета.
For reasons of congestion control, it is important that the rate of notifications not become excessive. As a result, it is RECOMMENDED that the server not generate notifications for a single subscriber at a rate faster than once every 5 seconds.
Из соображений контроля перегрузки важно, чтобы частота уведомлений не становилась чрезмерной. В результате РЕКОМЕНДУЕТСЯ, чтобы сервер не генерировал уведомления для одного подписчика со скоростью, превышающей один раз в 5 секунд.

Note that the document format explicitly allows for conveying information on multiple addresses-of-record. This enables subscriptions to groups of registrations, where such a group is identified by some kind of URI. For example, a domain might define sip:allusers@example.com as a subscribable resource that generates notifications when the state of any address-of-record in the domain changes.
Обратите внимание, что формат документа явно позволяет передавать информацию по нескольким адресам записи. Это позволяет подписаться на группы регистраций, если такая группа идентифицируется каким-либо URI. Например, домен может определить sip:allusers@example.com как подписываемый ресурс, который генерирует уведомления при изменении состояния любого адреса записи в домене.
The "registration" element has a list of any number of "contact" sub-elements, each of which contains information on a single contact. Other elements from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored. In particular, if two URI identifying an address-of-record differ after their canonicalization according to the procedures in step 5 of Section 10.3 of RFC 3261 [1], the id attributes in the "registration" elements for those addresses-of-record MUST differ. The valid values are "init", "active" and "terminated".

С элементом «registration» связаны три атрибута, каждый из которых ДОЛЖЕН присутствовать: aor: Атрибут aor содержит URI, который является адресом записи, на который ссылается эта регистрация. id: Атрибут id идентифицирует эту регистрацию. Он ДОЛЖЕН быть уникальным среди всех других атрибутов id, присутствующих в других элементах регистрации, передаваемых подписчику в рамках его подписки. В частности, если два URI, идентифицирующие адрес записи, различаются после их канонизации в соответствии с процедурами шага 5 раздела 10.3 RFC 3261 [1], атрибуты id в элементах «registration» для этих адресов записи ДОЛЖНЫ различаться. Более того, атрибут id для элемента «registration» для конкретного адреса записи ДОЛЖЕН быть одинаковым для всех уведомлений, отправленных в рамках подписки. состояние: атрибут состояния указывает состояние регистрации. Допустимые значения: «init», «active» и «terminated».
The "contact" element contains a "uri" element, an optional "display-name" element, and an optional "unknown-param" element. Other elements from different namespaces MAY be present for the purposes of extensibility; elements or attributes from unknown namespaces MUST be ignored. There are several attributes associated with the "contact" element which MUST be present: id: The id attribute identifies this contact. It MUST be unique amongst all other id attributes present in other contact elements conveyed to the subscriber within the scope of their subscription. In particular, if the URI for two contacts differ (based on the URI comparison rules in RFC 3261 [1]), the id attributes for those contacts MUST differ. However, unlike the id attribute for an address- of-record, if the URI for two contacts are the same, their id attributes SHOULD be the same across notifications. This requirement is at SHOULD strength, and not MUST strength, since it is difficult to compute such an id as a function of the URI without retaining additional state. No hash function applied to the URI can, in fact, meet a MUST requirement. This is because equality of the SIP URI is not transitive. However, a hash function which includes unknown URI parameters (that is, any not defined in RFC 3261), will always result in a value that is the different if two URI are different, and usually the same if the URI are equal. state: The state attribute indicates the state of the contact. The valid values are "active" and "terminated". event: The event attribute indicates the event which caused the contact state machine to go into its current state. Valid values are registered, created, refreshed, shortened, expired, deactivated, probation, unregistered and rejected.
Элемент «contact» содержит элемент «uri», необязательный элемент «display-name» и необязательный элемент «unknown-param». Другие элементы из разных пространств имен МОГУТ присутствовать в целях расширяемости; элементы или атрибуты из неизвестных пространств имен ДОЛЖНЫ игнорироваться. Существует несколько атрибутов, связанных с элементом «contact», которые ДОЛЖНЫ присутствовать: id: Атрибут id идентифицирует этот контакт. Он ДОЛЖЕН быть уникальным среди всех других атрибутов id, присутствующих в других контактных элементах, передаваемых подписчику в рамках его подписки. В частности, если URI для двух контактов различаются (на основе правил сравнения URI в RFC 3261 [1]), атрибуты id для этих контактов ДОЛЖНЫ различаться. Однако, в отличие от атрибута id для адреса записи, если URI для двух контактов одинаковы, их атрибуты id ДОЛЖНЫ быть одинаковыми во всех уведомлениях. Это требование соответствует уровню СЛЕДУЕТ, а не ДОЛЖНО, поскольку трудно вычислить такой идентификатор как функцию URI без сохранения дополнительного состояния. Никакая хэш-функция, примененная к URI, фактически не может соответствовать требованию MUST. Это связано с тем, что равенство URI SIP не является транзитивным. Однако хеш-функция, включающая неизвестные параметры URI (то есть те, которые не определены в RFC 3261), всегда будет давать разное значение, если два URI различны, и обычно одинаковое, если URI равны. состояние: атрибут состояния указывает состояние контакта. Допустимые значения: «active» и «terminated». событие: атрибут события указывает на событие, которое привело к переходу конечного автомата контакта в его текущее состояние. Действительные значения регистрируются, создаются, обновляются, сокращаются, истекают, деактивируются, проходят испытательный срок, не регистрируются и отклоняются.
If the event attribute has a value of shortened, the "expires" attribute MUST be present. It contains an unsigned long integer which indicates the number of seconds remaining until the binding is due to expire. This attribute MAY be included with any event attribute value for which the state of the contact is active.
Если атрибут события имеет значение сокращенного, ДОЛЖЕН присутствовать атрибут «expires». Он содержит длинное целое число без знака, которое указывает количество секунд, оставшихся до истечения срока действия привязки. Этот атрибут МОЖЕТ быть включен в любое значение атрибута события, для которого состояние контакта является активным.
If the event attribute has a value of probation, the "retry-after" attribute MUST be present. It contains an unsigned long integer which indicates the amount of seconds after which the owner of the contact is expected to retry its registration.
Если атрибут события имеет значение испытательного срока, ДОЛЖЕН присутствовать атрибут «retry-after». Он содержит длинное целое число без знака, которое указывает количество секунд, по истечении которых владелец контакта, как ожидается, повторит попытку регистрации.
The optional "duration-registered" attribute conveys the amount of time that the contact has been bound to the address-of-record, in seconds. The optional "q" attribute conveys the relative priority of this contact compared to other registered contacts. The optional "callid" attribute contains the current Call-ID carried in the REGISTER that was last used to update this contact, and the optional "cseq" attribute contains the last CSeq value present in a REGISTER request that updated this contact value. The "uri" element contains the URI associated with that contact. The "display-name" element contains the display name for the contact. The "display-name" element MAY contain the xml:lang attribute to indicate the language of the display name.
Необязательный атрибут «duration-registered» передает количество времени, в течение которого контакт был привязан к адресу записи, в секундах. Необязательный атрибут «q» передает относительный приоритет этого контакта по сравнению с другими зарегистрированными контактами. Необязательный атрибут «callid» содержит текущее значение Call-ID, содержащееся в REGISTER, который в последний раз использовался для обновления этого контакта, а необязательный атрибут «cseq» содержит последнее значение CSeq, присутствующее в запросе REGISTER, который обновил это значение контакта. Элемент «uri» содержит URI, связанный с этим контактом. Элемент «display-name» содержит отображаемое имя контакта. Элемент «display-name» МОЖЕТ содержать атрибут xml:lang, указывающий язык отображаемого имени.
The "unknown-param" element is used to convey contact header field parameters that are not specified in RFC 3261. One example are the user agent capability parameters specified in [11]. Each "unknown- param" element describes a single contact header field parameter. The name of the parameter is contained in the mandatory name attribute of the "unknown-param" element, and the value of the parameter is the content of the "unknown-param" element. For contact header field parameters that have no value, the content of the "unknown-param" element is empty.
Элемент «unknown-param» используется для передачи параметров поля заголовка контакта, которые не указаны в RFC 3261. Одним из примеров являются параметры возможностей пользовательского агента, указанные в [11]. Каждый элемент «unknown-param» описывает один параметр поля заголовка контакта. Имя параметра содержится в обязательном атрибуте имени элемента «unknown-param», а значение параметра — это содержимое элемента «unknown-param». Для параметров поля заголовка контакта, которые не имеют значения, содержимое элемента «unknown-param» пусто.
5.2. Computing Registrations from the Document
5.2. Вычисление регистраций из документа
Typically, the NOTIFY for registration information will only contain information about those contacts whose state has changed. To construct a coherent view of the total state of all registrations, a subscriber will need to combine NOTIFYs received over time. The subscriber maintains a table for each registration it receives information for. Each registration is uniquely identified by the "id" attribute in the "registration" element. Each table contains a row for each contact in that registration. Each row is indexed by the unique ID for that contact. It is conveyed in the "id" attribute of the "contact" element. The contents of each row contain the state of that contact as conveyed in the "contact" element. The tables are also associated with a version number. The version number MUST be initialized with the value of the "version" attribute from the "reginfo" element in the first document received. Each time a new document is received, the value of the local version number, and the "version" attribute in the new document, are compared. If the value in the new document is one higher than the local version number, the local version number is increased by one, and the document is processed. If the value in the document is more than one higher than the local version number, the local version number is set to the value in the new document, the document is processed, and the subscriber SHOULD generate a refresh request to trigger a full state notification. If the value in the document is less than the local version, the document is discarded without processing.
Обычно NOTIFY для регистрационной информации будет содержать информацию только о тех контактах, состояние которых изменилось. Чтобы создать целостное представление общего состояния всех регистраций, подписчику необходимо будет объединить уведомления NOTIFY, полученные с течением времени. Абонент ведет таблицу для каждой регистрации, для которой он получает информацию. Каждая регистрация уникально идентифицируется атрибутом «id» в элементе «registration». Каждая таблица содержит строку для каждого контакта в этой регистрации. Каждая строка индексируется уникальным идентификатором этого контакта. Это передается в атрибуте «id» элемента «contact». Содержимое каждой строки содержит состояние этого контакта, переданное в элементе «contact». Таблицы также связаны с номером версии. Номер версии ДОЛЖЕН быть инициализирован значением атрибута «version» из элемента «reginfo» в первом полученном документе. Каждый раз при получении нового документа сравнивается значение локального номера версии и атрибута «version» в новом документе. Если значение в новом документе на единицу превышает номер локальной версии, номер локальной версии увеличивается на единицу и документ обрабатывается. Если значение в документе более чем на единицу превышает номер локальной версии, номер локальной версии устанавливается равным значению в новом документе, документ обрабатывается, и подписчик ДОЛЖЕН сгенерировать запрос на обновление, чтобы вызвать уведомление о полном состоянии. Если значение в документе меньше локальной версии, документ отбрасывается без обработки.
The processing of the document depends on whether it contains full or partial state. If it contains full state, indicated by the value of the "state" attribute in the "reginfo" element, the contents of all tables associated with this subscription are flushed. They are re-populated from the document. A new table is created for each "registration" element, and a new row in each table is created for each "contact" element. If the reginfo contains partial state, as indicated by the value of the "state" attribute in the "reginfo" element, the document is used to update the existing tables. For each "registration" element, the subscriber checks to see if a table exists for that registration. This check is done by comparing the value in the "id" attribute of the "registration" element with the ID associated with the table. If a table doesn't exist for that registration, one is created. For each "contact" element in the registration, the subscriber checks to see whether a row exists for that contact. This check is done by comparing the ID in the "id" attribute of the "contact" element with the ID associated with the row. If the contact doesn't exist in the table, a row is added, and its state is set to the information from that "contact" element. If the contact does exist, its state is updated to be the information from that "contact" element. If a row is updated or created, such that its state is now terminated, that entry MAY be removed from the table at any time.
Обработка документа зависит от того, содержит ли он полное или частичное состояние. Если оно содержит полное состояние, указанное значением атрибута «state» в элементе «reginfo», содержимое всех таблиц, связанных с этой подпиской, сбрасывается. Они повторно заполняются из документа. Для каждого элемента «registration» создается новая таблица, а для каждого элемента «contact» создается новая строка в каждой таблице. Если reginfo содержит частичное состояние, на что указывает значение атрибута «state» в элементе «reginfo», документ используется для обновления существующих таблиц. Для каждого элемента «registration» подписчик проверяет, существует ли таблица для этой регистрации. Эта проверка выполняется путем сравнения значения атрибута «id» элемента «registration» с идентификатором, связанным с таблицей. Если таблица для этой регистрации не существует, она создается. Для каждого элемента «contact» в регистрации подписчик проверяет, существует ли строка для этого контакта. Эта проверка выполняется путем сравнения идентификатора в атрибуте «id» элемента «contact» с идентификатором, связанным со строкой. Если контакт не существует в таблице, добавляется строка, и ее состояние устанавливается на информацию из этого элемента «contact». Если контакт существует, его состояние обновляется в соответствии с информацией из этого элемента «contact». Если строка обновлена ​​или создана так, что ее состояние теперь завершено, эта запись МОЖЕТ быть удалена из таблицы в любое время.

7. Security Considerations
7. Вопросы безопасности
Security considerations for SIP event packages are discussed in RFC 3265 [2], and those considerations apply here.
Вопросы безопасности для пакетов событий SIP обсуждаются в RFC 3265 [2], и эти соображения применимы здесь.
Registration information is sensitive, potentially private, information. Subscriptions to this event package SHOULD be authenticated and authorized according to local policy. Some policy guidelines are suggested in Section 4.6. In addition, notifications SHOULD be sent in such a way to ensure confidentiality, message integrity and verification of subscriber identity, such as sending subscriptions and notifications using a SIPS URL or protecting the notification bodies with S/MIME.
Регистрационная информация является конфиденциальной и потенциально частной информацией. Подписки на этот пакет событий СЛЕДУЕТ аутентифицировать и авторизовать в соответствии с местной политикой. Некоторые руководящие принципы политики предлагаются в разделе 4.6. Кроме того, уведомления СЛЕДУЕТ отправлять таким образом, чтобы обеспечить конфиденциальность, целостность сообщений и проверку личности подписчика, например, отправка подписок и уведомлений с использованием URL-адреса SIPS или защита органов уведомлений с помощью S/MIME.
