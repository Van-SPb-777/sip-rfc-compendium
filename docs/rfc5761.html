Multiplexing RTP Data and Control Packets on a Single Port
Мультиплексирование пакетов данных и управления RTP на одном порту
Abstract
Аннотация
This memo discusses issues that arise when multiplexing RTP data packets and RTP Control Protocol (RTCP) packets on a single UDP port. It updates RFC 3550 and RFC 3551 to describe when such multiplexing is and is not appropriate, and it explains how the Session Description Protocol (SDP) can be used to signal multiplexed sessions.
В настоящем документе рассматриваются вопросы, возникающие при мультиплексировании пакетов данных RTP и пакетов протокола управления RTP (RTCP) на одном порту UDP. Он обновляет RFC 3550 и RFC 3551, описывая, когда такое мультиплексирование уместно, а когда нет, и объясняет, как протокол описания сеансов (SDP) может использоваться для сигнализации о мультиплексированных сеансах.

1. Introduction
1. Введение
The Real-time Transport Protocol (RTP) [1] comprises two components: a data transfer protocol and an associated control protocol (RTCP). Historically, RTP and RTCP have been run on separate UDP ports. With increased use of Network Address Port Translation (NAPT) [14], this has become problematic, since maintaining multiple NAT bindings can be costly. It also complicates firewall administration, since multiple ports must be opened to allow RTP traffic. This memo discusses how the RTP and RTCP flows for a single media type can be run on a single port, to ease NAT traversal and simplify firewall administration, and considers when such multiplexing is appropriate. The multiplexing of several types of media (e.g., audio and video) onto a single port is not considered here (but see Section 5.2 of [1]).
Транспортный протокол реального времени (RTP) [1] состоит из двух компонентов: протокола передачи данных и связанного с ним протокола управления (RTCP). Исторически RTP и RTCP работали на разных портах UDP. С ростом использования трансляции сетевых адресов и портов (NAPT) [14] это стало проблемой, поскольку поддержание нескольких привязок NAT может быть дорогостоящим. Это также усложняет администрирование межсетевых экранов, так как для пропуска трафика RTP необходимо открывать несколько портов. В настоящем меморандуме обсуждается, как потоки RTP и RTCP для одного типа медиаданных могут работать на одном порту, чтобы облегчить прохождение через NAT и упростить администрирование межсетевого экрана, а также рассматривается, когда такое мультиплексирование уместно. Мультиплексирование нескольких типов медиаданных (например, аудио и видео) на один порт здесь не рассматривается (но см. раздел 5.2 в [1]).
This memo is structured as follows: in Section 2 we discuss the design choices that led to the use of separate ports and comment on the applicability of those choices to current network environments. We discuss terminology in Section 3 and how to distinguish multiplexed packets in Section 4; we then specify when and how RTP and RTCP should be multiplexed, and how to signal multiplexed sessions, in Section 5. Quality of service and bandwidth issues are discussed in Section 6. We conclude with security considerations in Section 7 and IANA considerations in Section 8.
Настоящий меморандум построен следующим образом: в разделе 2 мы обсуждаем проектные решения, которые привели к использованию раздельных портов, и комментируем применимость этих решений к современным сетевым средам. В разделе 3 мы обсуждаем терминологию, а в разделе 4 — способы различения мультиплексированных пакетов; затем в разделе 5 мы определяем, когда и как следует мультиплексировать RTP и RTCP и как сигнализировать о мультиплексированных сеансах. Вопросы качества обслуживания и полосы пропускания обсуждаются в разделе 6. Мы завершаем рассмотрением вопросов безопасности в разделе 7 и вопросов IANA в разделе 8.

2. Background
2. Предыстория
An RTP session comprises data packets and periodic control (RTCP) packets. RTCP packets are assumed to use "the same distribution mechanism as the data packets", and the "underlying protocol MUST provide multiplexing of the data and control packets, for example using separate port numbers with UDP" [1]. Multiplexing was deferred to the underlying transport protocol, rather than being provided within RTP, for the following reasons:
Сеанс RTP включает пакеты данных и периодические пакеты управления (RTCP). Предполагается, что пакеты RTCP используют «тот же механизм распространения, что и пакеты данных», а «нижележащий протокол ДОЛЖЕН обеспечивать мультиплексирование пакетов данных и управления, например используя отдельные номера портов в UDP» [1]. Мультиплексирование было отнесено к нижележащему транспортному протоколу, а не реализовано внутри RTP, по следующим причинам:
1. Simplicity: an RTP implementation is simplified by moving the RTP and RTCP demultiplexing to the transport layer, since it need not concern itself with the separation of data and control packets. This allows the implementation to be structured in a very natural fashion, with a clean separation of data and control planes.
1. Простота: реализация RTP упрощается за счёт переноса демультиплексирования RTP и RTCP на транспортный уровень, поскольку ей не нужно заботиться о разделении пакетов данных и управления. Это позволяет структурировать реализацию весьма естественным образом, с чистым разделением плоскостей данных и управления.
2. Efficiency: following the principle of integrated layer processing [15], an implementation will be more efficient when demultiplexing happens in a single place (e.g., according to UDP port) than when split across multiple layers of the stack (e.g., according to UDP port and then according to packet type).
2. Эффективность: следуя принципу интегрированной обработки уровней [15], реализация будет более эффективной, когда демультиплексирование происходит в одном месте (например, по порту UDP), чем когда оно распределено по нескольким уровням стека (например, сначала по порту UDP, а затем по типу пакета).
3. To enable third-party monitors: while unicast voice-over-IP has always been considered, RTP was also designed to support loosely coupled multicast conferences [16] and very large-scale multicast streaming media applications (such as the so-called triple-play IP television (IPTV) service). Accordingly, the design of RTP allows the RTCP packets to be multicast using a separate IP multicast group and UDP port to the data packets. This not only allows participants in a session to get reception-quality feedback but also enables deployment of third-party monitors, which listen to reception quality without access to the data packets. This was intended to provide manageability of multicast sessions, without compromising privacy.
3. Для обеспечения сторонних мониторов: хотя одноадресная передача голоса по IP всегда рассматривалась, RTP также проектировался для поддержки слабо связанных многоадресных конференций [16] и очень крупномасштабных многоадресных приложений потокового мультимедиа (таких как так называемая услуга тройной игры — IP-телевидение (IPTV)). Соответственно, проект RTP допускает многоадресную передачу пакетов RTCP с использованием отдельной группы IP-многоадресации и порта UDP, отличных от пакетов данных. Это не только позволяет участникам сеанса получать обратную связь о качестве приёма, но и даёт возможность развёртывать сторонние мониторы, которые прослушивают качество приёма, не имея доступа к пакетам данных. Это было задумано для обеспечения управляемости многоадресных сеансов без ущерба для конфиденциальности.
While these design choices are appropriate for many uses of RTP, they are problematic in some cases. There are many RTP deployments that don't use IP multicast, and with the increased use of Network Address Translation (NAT) the simplicity of multiplexing at the transport layer has become a liability, since it requires complex signalling to open multiple NAT pinholes. In environments such as these, it is desirable to provide an alternative to demultiplexing RTP and RTCP using separate UDP ports, instead using only a single UDP port and demultiplexing within the application.
Хотя эти проектные решения подходят для многих применений RTP, в некоторых случаях они проблематичны. Существует множество развёртываний RTP, которые не используют IP-многоадресацию, а с ростом использования трансляции сетевых адресов (NAT) простота мультиплексирования на транспортном уровне стала обузой, поскольку она требует сложной сигнализации для открытия нескольких отверстий в NAT. В таких средах желательно предусмотреть альтернативу демультиплексированию RTP и RTCP с использованием отдельных портов UDP — а именно использовать только один порт UDP и выполнять демультиплексирование внутри приложения.
This memo provides such an alternative by multiplexing RTP and RTCP packets on a single UDP port, distinguished by the RTP payload type and RTCP packet type values. This pushes some additional work onto the RTP implementation, in exchange for simplified NAT traversal.
Настоящий меморандум предоставляет такую альтернативу, мультиплексируя пакеты RTP и RTCP на одном порту UDP и различая их по значениям типа полезной нагрузки RTP и типа пакета RTCP. Это переносит часть дополнительной работы на реализацию RTP в обмен на упрощённое прохождение через NAT.

4. Distinguishable RTP and RTCP Packets
4. Различимые пакеты RTP и RTCP
When RTP and RTCP packets are multiplexed onto a single port, the RTCP packet type field occupies the same position in the packet as the combination of the RTP marker (M) bit and the RTP payload type (PT). This field can be used to distinguish RTP and RTCP packets when two restrictions are observed: 1) the RTP payload type values used are distinct from the RTCP packet types used; and 2) for each RTP payload type (PT), PT+128 is distinct from the RTCP packet types used. The first constraint precludes a direct conflict between RTP payload type and RTCP packet type; the second constraint precludes a conflict between an RTP data packet with the marker bit set and an RTCP packet.
Когда пакеты RTP и RTCP мультиплексируются на один порт, поле типа пакета RTCP занимает в пакете ту же позицию, что и сочетание бита маркера (M) RTP и типа полезной нагрузки (PT) RTP. Это поле может использоваться для различения пакетов RTP и RTCP при соблюдении двух ограничений: 1) используемые значения типа полезной нагрузки RTP отличаются от используемых типов пакетов RTCP; и 2) для каждого типа полезной нагрузки RTP (PT) значение PT+128 отличается от используемых типов пакетов RTCP. Первое ограничение исключает прямое противоречие между типом полезной нагрузки RTP и типом пакета RTCP; второе ограничение исключает конфликт между пакетом данных RTP с установленным битом маркера и пакетом RTCP.
The following conflicts between RTP and RTCP packet types are known:
Известны следующие конфликты между типами пакетов RTP и RTCP:

o RTP payload types 72-76 conflict with the RTCP SR, RR, SDES, BYE, and APP packets defined in the RTP specification [1].
o типы полезной нагрузки RTP 72-76 конфликтуют с пакетами RTCP SR, RR, SDES, BYE и APP, определёнными в спецификации RTP [1].
o RTP payload types 77-78 conflict with the RTCP RTPFB and PSFB packets defined in the RTP/AVPF profile [4].
o типы полезной нагрузки RTP 77-78 конфликтуют с пакетами RTCP RTPFB и PSFB, определёнными в профиле RTP/AVPF [4].

New RTCP packet types may be registered in the future and will further reduce the RTP payload types that are available when multiplexing RTP and RTCP onto a single port. To allow this multiplexing, future RTCP packet type assignments SHOULD be made after the current assignments in the range 209-223, then in the range 194-199, so that only the RTP payload types in the range 64-95 are blocked. RTCP packet types in the ranges 1-191 and 224-254 SHOULD only be used when other values have been exhausted.
В будущем могут быть зарегистрированы новые типы пакетов RTCP, что ещё больше сократит набор типов полезной нагрузки RTP, доступных при мультиплексировании RTP и RTCP на один порт. Чтобы сохранить возможность такого мультиплексирования, будущие назначения типов пакетов RTCP СЛЕДУЕТ производить после текущих назначений в диапазоне 209-223, затем в диапазоне 194-199, чтобы блокировались только типы полезной нагрузки RTP в диапазоне 64-95. Типы пакетов RTCP в диапазонах 1-191 и 224-254 СЛЕДУЕТ использовать только тогда, когда другие значения исчерпаны.
Given these constraints, it is RECOMMENDED to follow the guidelines in the RTP/AVP profile [7] for the choice of RTP payload type values, with the additional restriction that payload type values in the range 64-95 MUST NOT be used. Specifically, dynamic RTP payload types SHOULD be chosen in the range 96-127 where possible. Values below 64 MAY be used if that is insufficient, in which case it is RECOMMENDED that payload type numbers that are not statically assigned by [7] be used first.
С учётом этих ограничений РЕКОМЕНДУЕТСЯ следовать руководящим указаниям профиля RTP/AVP [7] при выборе значений типа полезной нагрузки RTP с дополнительным ограничением: значения типа полезной нагрузки в диапазоне 64-95 НЕ ДОЛЖНЫ использоваться. В частности, динамические типы полезной нагрузки RTP СЛЕДУЕТ по возможности выбирать в диапазоне 96-127. Значения ниже 64 МОГУТ использоваться, если этого недостаточно, и в этом случае РЕКОМЕНДУЕТСЯ сначала использовать номера типов полезной нагрузки, не назначенные статически в [7].
Note: Since Section 6.1 of [1] specifies that all RTCP packets MUST be sent as compound packets beginning with a Sender Report (SR) or a Receiver Report (RR) packet, one might wonder why RTP payload types other than 72 and 73 are prohibited when multiplexing RTP and RTCP. This is done to support [18], which allows the use of non-compound RTCP packets in some circumstances.
Примечание: поскольку раздел 6.1 в [1] устанавливает, что все пакеты RTCP ДОЛЖНЫ отправляться как составные пакеты, начинающиеся с пакета отчёта отправителя (SR) или отчёта получателя (RR), может возникнуть вопрос, почему при мультиплексировании RTP и RTCP запрещены типы полезной нагрузки RTP, отличные от 72 и 73. Это сделано для поддержки [18], который в некоторых обстоятельствах допускает использование несоставных пакетов RTCP.
5. Multiplexing RTP and RTCP on a Single Port
5. Мультиплексирование RTP и RTCP на одном порту
The procedures for multiplexing RTP and RTCP on a single port depend on whether the session is a unicast session or a multicast session. For multicast sessions, the procedures also depend on whether Any Source Multicast (ASM) or Source-Specific Multicast (SSM) is to be used.
Процедуры мультиплексирования RTP и RTCP на одном порту зависят от того, является ли сеанс одноадресным или многоадресным. Для многоадресных сеансов процедуры также зависят от того, будет ли использоваться многоадресная рассылка от любого источника (ASM) или многоадресная рассылка от конкретного источника (SSM).
5.1. Unicast Sessions
5.1. Одноадресные сеансы
It is acceptable to multiplex RTP and RTCP packets on a single UDP port to ease NAT traversal for unicast sessions, provided the RTP payload types used in the session are chosen according to the rules in Section 4, and provided that multiplexing is signalled in advance. The following sections describe how such multiplexed sessions can be signalled using the Session Initiation Protocol (SIP) with the offer/ answer model.
Допускается мультиплексировать пакеты RTP и RTCP на одном порту UDP, чтобы облегчить прохождение через NAT для одноадресных сеансов, при условии что используемые в сеансе типы полезной нагрузки RTP выбраны согласно правилам раздела 4 и что о мультиплексировании сигнализируется заранее. Следующие разделы описывают, как такие мультиплексированные сеансы могут сигнализироваться с использованием протокола инициирования сеансов (SIP) по модели «предложение/ответ».
5.1.1. SDP Signalling
5.1.1. Сигнализация SDP
When the Session Description Protocol (SDP) [8] is used to negotiate RTP sessions following the offer/answer model [9], the "a=rtcp-mux" attribute (see Section 8) indicates the desire to multiplex RTP and RTCP onto a single port. The initial SDP offer MUST include this attribute at the media level to request multiplexing of RTP and RTCP on a single port. For example:
Когда протокол описания сеансов (SDP) [8] используется для согласования сеансов RTP по модели «предложение/ответ» [9], атрибут «a=rtcp-mux» (см. раздел 8) указывает на желание мультиплексировать RTP и RTCP на один порт. Начальное предложение SDP ДОЛЖНО включать этот атрибут на уровне медиаданных, чтобы запросить мультиплексирование RTP и RTCP на одном порту. Например:
v=0 o=csp 1153134164 1153134164 IN IP6 2001:DB8::211:24ff:fea3:7a2e s=- c=IN IP6 2001:DB8::211:24ff:fea3:7a2e t=1153134164 1153137764 m=audio 49170 RTP/AVP 97 a=rtpmap:97 iLBC/8000 a=rtcp-mux
v=0 o=csp 1153134164 1153134164 IN IP6 2001:DB8::211:24ff:fea3:7a2e s=- c=IN IP6 2001:DB8::211:24ff:fea3:7a2e t=1153134164 1153137764 m=audio 49170 RTP/AVP 97 a=rtpmap:97 iLBC/8000 a=rtcp-mux
This offer denotes a unicast voice-over-IP session using the RTP/AVP profile with iLBC coding. The answerer is requested to send both RTP and RTCP to port 49170 on IPv6 address 2001:DB8::211:24ff:fea3:7a2e.
Это предложение обозначает одноадресный сеанс передачи голоса по IP, использующий профиль RTP/AVP с кодированием iLBC. Отвечающему предлагается отправлять и RTP, и RTCP на порт 49170 по адресу IPv6 2001:DB8::211:24ff:fea3:7a2e.
If the answerer wishes to multiplex RTP and RTCP onto a single port, it MUST include a media-level "a=rtcp-mux" attribute in the answer. The RTP payload types used in the answer MUST conform to the rules in Section 4. If the answer does not contain an "a=rtcp-mux" attribute, the offerer MUST NOT multiplex RTP and RTCP packets on a single port. Instead, it should send and receive RTCP on a port allocated according to the usual port-selection rules (either the port pair, or a signalled port if the "a=rtcp:" attribute [10] is also included). This will occur when talking to a peer that does not understand the "a=rtcp-mux" attribute.
Если отвечающий желает мультиплексировать RTP и RTCP на один порт, он ДОЛЖЕН включить в ответ атрибут «a=rtcp-mux» на уровне медиаданных. Типы полезной нагрузки RTP, используемые в ответе, ДОЛЖНЫ соответствовать правилам раздела 4. Если ответ не содержит атрибута «a=rtcp-mux», предлагающий НЕ ДОЛЖЕН мультиплексировать пакеты RTP и RTCP на одном порту. Вместо этого ему следует отправлять и принимать RTCP на порту, выделенном согласно обычным правилам выбора порта (либо пара портов, либо сигнализированный порт, если также включён атрибут «a=rtcp:» [10]). Это произойдёт при взаимодействии с узлом, который не понимает атрибут «a=rtcp-mux».
When SDP is used in a declarative manner, the presence of an "a=rtcp- mux" attribute signals that the sender will multiplex RTP and RTCP on the same port. The receiver MUST be prepared to receive RTCP packets on the RTP port, and any resource reservation needs to be made including the RTCP bandwidth.
Когда SDP используется декларативным образом, наличие атрибута «a=rtcp-mux» сигнализирует, что отправитель будет мультиплексировать RTP и RTCP на одном и том же порту. Получатель ДОЛЖЕН быть готов принимать пакеты RTCP на порту RTP, а любое резервирование ресурсов должно выполняться с учётом полосы пропускания RTCP.
5.1.2. Interactions with SIP Forking
5.1.2. Взаимодействие с разветвлением SIP
When using SIP with a forking proxy, it is possible that an INVITE request may result in multiple 200 (OK) responses. If RTP and RTCP multiplexing is offered in that INVITE, it is important to be aware that some answerers may support multiplexed RTP and RTCP, some not. This will require the offerer to listen for RTCP on both the RTP port and the usual RTCP port, and to send RTCP on both ports, unless branches of the call that support multiplexing are re-negotiated to use separate RTP and RTCP ports.
При использовании SIP с разветвляющим прокси возможна ситуация, когда запрос INVITE приводит к нескольким ответам 200 (OK). Если в этом INVITE предлагается мультиплексирование RTP и RTCP, важно учитывать, что некоторые отвечающие могут поддерживать мультиплексирование RTP и RTCP, а некоторые — нет. Это потребует от предлагающего прослушивать RTCP как на порту RTP, так и на обычном порту RTCP и отправлять RTCP на оба порта, если только ветви вызова, поддерживающие мультиплексирование, не будут пересогласованы на использование раздельных портов RTP и RTCP.
5.1.3. Interactions with ICE
5.1.3. Взаимодействие с ICE
It is common to use the Interactive Connectivity Establishment (ICE) [19] methodology to establish RTP sessions in the presence of Network Address Translation (NAT) devices or other middleboxes. If RTP and RTCP are sent on separate ports, the RTP media stream comprises two components in ICE (one for RTP and one for RTCP), with connectivity checks being performed for each component. If RTP and RTCP are to be multiplexed on the same port some of these connectivity checks can be avoided, reducing the overhead of ICE.
Обычно для установления сеансов RTP при наличии устройств трансляции сетевых адресов (NAT) или других промежуточных устройств используется методология интерактивного установления соединений (ICE) [19]. Если RTP и RTCP отправляются на разных портах, медиапоток RTP состоит в ICE из двух компонентов (один для RTP и один для RTCP), и для каждого компонента выполняются проверки связности. Если RTP и RTCP должны мультиплексироваться на одном порту, некоторых из этих проверок связности можно избежать, что снижает накладные расходы ICE.
If it is desired to use both ICE and multiplexed RTP and RTCP, the initial offer MUST contain an "a=rtcp-mux" attribute to indicate that RTP and RTCP multiplexing is desired and MUST contain "a=candidate:" lines for both RTP and RTCP along with an "a=rtcp:" line indicating a fallback port for RTCP in the case that the answerer does not support RTP and RTCP multiplexing. This MUST be done for each media where RTP and RTCP multiplexing is desired.
Если требуется использовать одновременно ICE и мультиплексирование RTP и RTCP, начальное предложение ДОЛЖНО содержать атрибут «a=rtcp-mux», указывающий, что мультиплексирование RTP и RTCP желательно, и ДОЛЖНО содержать строки «a=candidate:» как для RTP, так и для RTCP, а также строку «a=rtcp:», указывающую резервный порт для RTCP на случай, если отвечающий не поддерживает мультиплексирование RTP и RTCP. Это ДОЛЖНО быть сделано для каждого вида медиаданных, где желательно мультиплексирование RTP и RTCP.
If the answerer wishes to multiplex RTP and RTCP on a single port, it MUST generate an answer containing an "a=rtcp-mux" attribute and a single "a=candidate:" line corresponding to the RTP port (i.e., there is no candidate for RTCP) for each media where it is desired to use RTP and RTCP multiplexing. The answerer then performs connectivity checks for that media as if the offer had contained only a single candidate for RTP. If the answerer does not want to multiplex RTP and RTCP on a single port, it MUST NOT include the "a=rtcp-mux" attribute in its answer and MUST perform connectivity checks for all offered candidates in the usual manner.
Если отвечающий желает мультиплексировать RTP и RTCP на одном порту, он ДОЛЖЕН сформировать ответ, содержащий атрибут «a=rtcp-mux» и одну строку «a=candidate:», соответствующую порту RTP (то есть кандидат для RTCP отсутствует), для каждого вида медиаданных, где предполагается использовать мультиплексирование RTP и RTCP. Затем отвечающий выполняет проверки связности для этих медиаданных так, как если бы предложение содержало только один кандидат для RTP. Если отвечающий не желает мультиплексировать RTP и RTCP на одном порту, он НЕ ДОЛЖЕН включать атрибут «a=rtcp-mux» в свой ответ и ДОЛЖЕН выполнить проверки связности для всех предложенных кандидатов обычным образом.
On receipt of the answer, the offerer looks for the presence of the "a=rtcp-mux" line for each media where multiplexing was offered. If this is present, then connectivity checks proceed as if only a single candidate (for RTP) were offered, and multiplexing is used once the session is established. If the "a=rtcp-mux" line is not present, the session proceeds with connectivity checks using both RTP and RTCP candidates, eventually leading to a session being established with RTP and RTCP on separate ports (as signalled by the "a=rtcp:" attribute).
По получении ответа предлагающий проверяет наличие строки «a=rtcp-mux» для каждого вида медиаданных, для которых предлагалось мультиплексирование. Если она присутствует, проверки связности выполняются так, как если бы был предложен только один кандидат (для RTP), и после установления сеанса используется мультиплексирование. Если строка «a=rtcp-mux» отсутствует, сеанс продолжается с проверками связности с использованием кандидатов как для RTP, так и для RTCP, что в конечном итоге приводит к установлению сеанса с RTP и RTCP на раздельных портах (как сигнализировано атрибутом «a=rtcp:»).
5.1.4. Interactions with Header Compression
5.1.4. Взаимодействие со сжатием заголовков
Multiplexing RTP and RTCP packets onto a single port may negatively impact header compression schemes, for example, Compressed RTP (CRTP) [20] and RObust Header Compression (ROHC) [21] [22]. Header compression exploits patterns of change in the RTP headers of consecutive packets to send an indication that the packet changed in the expected way, rather than sending the complete header each time. This can lead to significant bandwidth savings if flows have uniform behaviour.
Мультиплексирование пакетов RTP и RTCP на одном порту может негативно повлиять на схемы сжатия заголовков, например на сжатие RTP (CRTP) [20] и робастное сжатие заголовков (ROHC) [21] [22]. Сжатие заголовков использует закономерности изменения заголовков RTP в последовательных пакетах, чтобы передавать указание на то, что пакет изменился ожидаемым образом, вместо отправки полного заголовка каждый раз. Это может дать значительную экономию полосы пропускания, если потоки ведут себя однородно.
The presence of RTCP packets multiplexed with RTP data packets can disrupt the patterns of change between headers and has the potential to significantly reduce header compression efficiency. The extent of this disruption depends on the header compression algorithm used and on the way flows are classified. A well-designed classifier should be able to separate RTP and RTCP multiplexed on the same port into different compression contexts, using the payload type field, such that the effect on the compression ratio is small. A classifier that assigns compression contexts based only on the IP addresses and UDP ports will not perform well. It is expected that implementations of header compression will need to be updated to efficiently support RTP and RTCP multiplexed on the same port.
Наличие пакетов RTCP, мультиплексированных с пакетами данных RTP, может нарушать закономерности изменений между заголовками и способно значительно снизить эффективность сжатия заголовков. Степень такого нарушения зависит от используемого алгоритма сжатия заголовков и от способа классификации потоков. Хорошо спроектированный классификатор должен уметь разделять RTP и RTCP, мультиплексированные на одном порту, в разные контексты сжатия с использованием поля типа полезной нагрузки, так что влияние на степень сжатия будет небольшим. Классификатор, который назначает контексты сжатия только на основе IP-адресов и портов UDP, будет работать плохо. Ожидается, что реализации сжатия заголовков потребуют обновления для эффективной поддержки RTP и RTCP, мультиплексированных на одном порту.
This effect of multiplexing RTP and RTCP on header compression may be especially significant in those environments, such as some wireless telephony systems, that rely on the efficiency of header compression to match the media to a limited-capacity channel. The implications of multiplexing RTP and RTCP should be carefully considered before use in such environments.
Этот эффект мультиплексирования RTP и RTCP на сжатие заголовков может быть особенно значительным в тех средах, таких как некоторые системы беспроводной телефонии, которые полагаются на эффективность сжатия заголовков для согласования медиаданных с каналом ограниченной ёмкости. Последствия мультиплексирования RTP и RTCP следует тщательно рассмотреть перед использованием в таких средах.
5.2. Any Source Multicast Sessions
5.2. Многоадресные сеансы любого источника
The problem of NAT traversal is less severe for Any Source Multicast (ASM) RTP sessions than for unicast RTP sessions, and the benefit of using separate ports for RTP and RTCP is greater due to the ability to support third-party RTCP-only monitors. Accordingly, RTP and RTCP packets SHOULD NOT be multiplexed onto a single port when using ASM RTP sessions and SHOULD instead use separate ports and multicast groups.
Проблема прохождения через NAT менее остра для сеансов RTP с многоадресной рассылкой от любого источника (ASM), чем для одноадресных сеансов RTP, а выгода от использования раздельных портов для RTP и RTCP больше благодаря возможности поддерживать сторонние мониторы, работающие только с RTCP. Соответственно, при использовании сеансов RTP ASM пакеты RTP и RTCP НЕ СЛЕДУЕТ мультиплексировать на один порт, а следует использовать раздельные порты и группы многоадресной рассылки.
5.3. Source-Specific Multicast Sessions
5.3. Многоадресные сеансы от конкретного источника
RTP sessions running over Source-Specific Multicast (SSM) send RTCP packets from the source to receivers via the multicast channel, but use a separate unicast feedback mechanism [6] to send RTCP from the receivers back to the source, with the source either reflecting the RTCP packets to the group or sending aggregate summary reports.
Сеансы RTP, работающие поверх многоадресной рассылки от конкретного источника (SSM), отправляют пакеты RTCP от источника получателям по многоадресному каналу, но используют отдельный механизм одноадресной обратной связи [6] для отправки RTCP от получателей обратно источнику, при этом источник либо отражает пакеты RTCP группе, либо отправляет сводные агрегированные отчёты.

Следуя терминологии [6], мы различаем следующие три потока RTP/RTCP в сеансе SSM:
1. RTP and RTCP flows between media sender and distribution source. In many scenarios, the media sender and distribution source are co-located, so multiplexing is not a concern. If the media sender and distribution source are connected by a unicast connection, the rules in Section 5.1 of this memo apply to that connection. If the media sender and distribution source are connected by an Any Source Multicast connection, the rules in Section 5.2 apply to that connection. If the media sender and distribution source are connected by a Source-Specific Multicast connection, the RTP and RTCP packets MAY be multiplexed on a single port, provided this is signalled (using "a=rtcp-mux" if using SDP).
1. Потоки RTP и RTCP между отправителем медиаданных и источником распространения. Во многих сценариях отправитель медиаданных и источник распространения размещены совместно, поэтому мультиплексирование не является проблемой. Если отправитель медиаданных и источник распространения соединены одноадресным соединением, к этому соединению применяются правила раздела 5.1 настоящего меморандума. Если отправитель медиаданных и источник распространения соединены соединением многоадресной рассылки от любого источника, к этому соединению применяются правила раздела 5.2. Если отправитель медиаданных и источник распространения соединены соединением многоадресной рассылки от конкретного источника, пакеты RTP и RTCP МОГУТ мультиплексироваться на один порт при условии, что об этом сигнализируется (с помощью «a=rtcp-mux», если используется SDP).
2. RTP and RTCP sent from the distribution source to the receivers. The distribution source MAY multiplex RTP and RTCP onto a single port to ease NAT traversal issues on the forward SSM path, although doing so may hinder third-party monitoring devices if the session uses the simple feedback model. When using SDP, the multiplexing SHOULD be signalled using the "a=rtcp-mux" attribute.
2. RTP и RTCP, отправляемые от источника распространения получателям. Источник распространения МОЖЕТ мультиплексировать RTP и RTCP на один порт, чтобы облегчить проблемы прохождения через NAT на прямом пути SSM, хотя это может затруднить работу сторонних устройств мониторинга, если сеанс использует простую модель обратной связи. При использовании SDP о мультиплексировании СЛЕДУЕТ сигнализировать с помощью атрибута «a=rtcp-mux».

Multiplexing RTP and RTCP packets on a single port in an SSM session has the potential for interactions with header compression described in Section 5.1.4.
Мультиплексирование пакетов RTP и RTCP на одном порту в сеансе SSM может взаимодействовать со сжатием заголовков, как описано в разделе 5.1.4.
6. Multiplexing, Bandwidth, and Quality of Service
6. Мультиплексирование, полоса пропускания, QoS
Multiplexing RTP and RTCP has implications on the use of the Quality of Service (QoS) mechanism that handles flow that are determined by a three or five tuple (protocol, port, and address for source and/or destination). In these cases, the RTCP flow will be merged with the RTP flow when multiplexing them together. Thus, the RTCP bandwidth requirement needs to be considered when doing QoS reservations for the combined RTP and RTCP flow. However, from an RTCP perspective it is beneficial to receive the same treatment of RTCP packets as for RTP as it provides more accurate statistics for the measurements performed by RTCP.
Мультиплексирование RTP и RTCP влияет на использование механизма качества обслуживания (QoS), который обрабатывает потоки, определяемые тройкой или пятёркой параметров (протокол, порт и адрес источника и/или назначения). В этих случаях поток RTCP объединяется с потоком RTP при их мультиплексировании вместе. Таким образом, требование к полосе пропускания RTCP необходимо учитывать при резервировании QoS для объединённого потока RTP и RTCP. Однако с точки зрения RTCP выгодно, чтобы пакеты RTCP получали ту же обработку, что и RTP, поскольку это обеспечивает более точную статистику для измерений, выполняемых RTCP.
The bandwidth required for a multiplexed stream comprises the session bandwidth of the RTP stream plus the bandwidth used by RTCP. In the usual case, the RTP session bandwidth is signalled in the SDP "b=AS:" (or "b=TIAS:" [11]) line, and the RTCP traffic is limited to 5% of this value. Any QoS reservation SHOULD therefore be made for 105% of the "b=AS:" value. If a non-standard RTCP bandwidth fraction is used, signalled by the SDP "b=RR:" and/or "b=RS:" lines [12], then any QoS reservation SHOULD be made for bandwidth equal to (AS + RS + RR), taking the RS and RR values from the SDP answer.
Полоса пропускания, необходимая для мультиплексированного потока, складывается из полосы пропускания сеанса потока RTP и полосы пропускания, используемой RTCP. В обычном случае полоса пропускания сеанса RTP сигнализируется в строке SDP «b=AS:» (или «b=TIAS:» [11]), а трафик RTCP ограничивается 5% от этого значения. Поэтому любое резервирование QoS СЛЕДУЕТ выполнять для 105% значения «b=AS:». Если используется нестандартная доля полосы пропускания RTCP, сигнализируемая строками SDP «b=RR:» и/или «b=RS:» [12], то любое резервирование QoS СЛЕДУЕТ выполнять для полосы пропускания, равной (AS + RS + RR), принимая значения RS и RR из ответа SDP.
7. Security Considerations
7. Вопросы безопасности
The usage of multiplexing RTP and RTCP is not believed to introduce any new security considerations. Known major issues are the integrity and authentication of the signalling used to set up the multiplexing as well as the integrity, authentication, and confidentiality of the actual RTP and RTCP traffic. The security considerations in the RTP specification [1] and any applicable RTP profile (e.g., [7]) and payload format(s) apply.
Считается, что использование мультиплексирования RTP и RTCP не вносит новых вопросов безопасности. Известные основные проблемы — целостность и аутентификация сигнализации, используемой для настройки мультиплексирования, а также целостность, аутентификация и конфиденциальность собственно трафика RTP и RTCP. Применяются соображения безопасности из спецификации RTP [1] и любого применимого профиля RTP (например, [7]) и формата(ов) полезной нагрузки.
If the Secure Real-time Transport Protocol (SRTP) [13] is to be used in conjunction with multiplexed RTP and RTCP, then multiplexing MUST be done below the SRTP layer. The sender generates SRTP and SRTCP packets in the usual manner, based on their separate cryptographic contexts, and multiplexes them onto a single port immediately before transmission. At the receiver, the cryptographic context is derived from the synchronization source (SSRC), destination network address, and destination transport port number in the usual manner, augmented using the RTP payload type and RTCP packet type to demultiplex SRTP and SRTCP according to the rules in Section 4 of this memo. After the SRTP and SRTCP packets have been demultiplexed, cryptographic processing happens in the usual manner.
Если защищённый транспортный протокол реального времени (SRTP) [13] должен использоваться вместе с мультиплексированными RTP и RTCP, то мультиплексирование ДОЛЖНО выполняться ниже уровня SRTP. Отправитель формирует пакеты SRTP и SRTCP обычным образом, на основе их раздельных криптографических контекстов, и мультиплексирует их на один порт непосредственно перед передачей. У получателя криптографический контекст выводится из синхронизирующего источника (SSRC), сетевого адреса назначения и номера порта транспорта назначения обычным образом, с дополнением с использованием типа полезной нагрузки RTP и типа пакета RTCP для демультиплексирования SRTP и SRTCP согласно правилам раздела 4 настоящего меморандума. После демультиплексирования пакетов SRTP и SRTCP криптографическая обработка выполняется обычным образом.
8. IANA Considerations
8. Вопросы IANA
Following the guidelines in [8], the IANA has registered one new SDP attribute:
Следуя руководящим указаниям в [8], IANA зарегистрировала один новый атрибут SDP:
o Contact name/email: authors of RFC 5761
o Имя/эл. почта контакта: авторы RFC 5761
o Attribute name: rtcp-mux
o Имя атрибута: rtcp-mux
o Long-form attribute name: RTP and RTCP multiplexed on one port
o Полное имя атрибута: RTP и RTCP, мультиплексированные на одном порту
o Type of attribute: media level
o Тип атрибута: уровень медиаданных
o Subject to charset: no
o Набор символов: нет
This attribute is used to signal that RTP and RTCP traffic should be multiplexed on a single port (see Section 5 of this memo). It is a property attribute, which does not take a value.
Этот атрибут используется для сигнализации о том, что трафик RTP и RTCP следует мультиплексировать на одном порту (см. раздел 5 настоящего меморандума). Это атрибут-свойство, не принимающий значения.
The rules for assignment of RTP RTCP Control Packet Types in the RTP Parameters registry are updated as follows. When assigning RTP RTCP Control Packet types, IANA is requested to assign unused values from the range 200-223 where possible. If that range is fully occupied, values from the range 194-199 may be used, and then values from the ranges 1-191 and 224-254. This improves header validity checking of RTCP packets compared to RTP packets or other unrelated packets. The values 0 and 255 are avoided for improved validity checking relative to random packets since all-zeros and all-ones are common values.
Правила назначения типов пакетов управления RTP RTCP в реестре параметров RTP обновляются следующим образом. При назначении типов пакетов управления RTP RTCP IANA предлагается по возможности назначать неиспользуемые значения из диапазона 200-223. Если этот диапазон полностью занят, могут использоваться значения из диапазона 194-199, а затем значения из диапазонов 1-191 и 224-254. Это улучшает проверку корректности заголовков пакетов RTCP по сравнению с пакетами RTP или другими несвязанными пакетами. Значения 0 и 255 избегаются для улучшения проверки корректности относительно случайных пакетов, поскольку все нули и все единицы являются распространёнными значениями.
