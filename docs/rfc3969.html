Abstract
Аннотация
This document creates an Internet Assigned Number Authority (IANA) registry for the Session Initiation Protocol (SIP) and SIPS Uniform Resource Identifier (URI) parameters, and their values. It also lists the already existing parameters to be used as initial values for that registry.
Настоящий документ создаёт реестр IANA для параметров универсальных идентификаторов ресурсов (URI) протокола инициирования сессий (SIP) и SIPS и их значений. В нём также перечислены уже существующие параметры, которые следует использовать в качестве начальных значений для этого реестра.
1. Introduction
1. Введение
RFC 3261 [1] allows new SIP URI and SIPS URI parameters, and new parameter values to be defined. However, RFC 3261 omitted an IANA registry for them. This document creates such a registry.
RFC 3261 [1] допускает определение новых параметров SIP URI и SIPS URI, а также новых значений параметров. Однако в RFC 3261 отсутствовал реестр IANA для них. Настоящий документ создаёт такой реестр.
RFC 3427 [2] documents the process to extend SIP. This document updates RFC 3427 by specifying how to define and register new SIP and SIP URI parameters and their values.
RFC 3427 [2] документирует процесс расширения SIP. Настоящий документ обновляет RFC 3427, определяя порядок определения и регистрации новых параметров SIP и SIP URI и их значений.
2. Terminology
2. Терминология
In this document, the key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" are to be interpreted as described in BCP 14, RFC 2119 [3] and indicate requirement levels for compliant SIP implementations.
В настоящем документе ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» следует интерпретировать так, как описано в BCP 14, RFC 2119 [3]; они указывают уровни требований для совместимых реализаций SIP.
3. Use of the Registry
3. Использование реестра
SIP and SIPS URI parameters and values for these parameters MUST be documented in a standards-track RFC in order to be registered by IANA. This documentation MUST fully explain the syntax, intended usage, and semantics of the parameter. The intent of this requirement is to assure interoperability between independent implementations, and to prevent accidental namespace collisions between implementations of dissimilar features.
Параметры SIP URI и SIPS URI и значения этих параметров ДОЛЖНЫ быть задокументированы в RFC уровня Standards Track, чтобы IANA могла их зарегистрировать. Эта документация ДОЛЖНА полностью объяснять синтаксис, предполагаемое использование и семантику параметра. Цель этого требования — обеспечить совместимость независимых реализаций и предотвратить случайные коллизии пространства имён между реализациями несходных функций.
Note that this registry, unlike other protocol registries, only deals with parameters and parameter values defined in RFCs (i.e., it lacks a vendor-extension tree). RFC 3427 [2] documents concerns with regards to new SIP extensions which may damage security, greatly increase the complexity of the protocol, or both. New parameters and parameter values need to be documented in RFCs as a result of these concerns.
Отметим, что этот реестр, в отличие от других реестров протоколов, имеет дело только с параметрами и значениями параметров, определёнными в RFC (то есть в нём нет дерева расширений поставщиков). RFC 3427 [2] документирует опасения относительно новых расширений SIP, которые могут нанести ущерб безопасности, значительно увеличить сложность протокола или и то и другое. Вследствие этих опасений новые параметры и значения параметров необходимо документировать в RFC.
RFCs defining SIP URI, SIPS URI parameters, or parameter values MUST register them with IANA as described below.
RFC, определяющие параметры SIP URI, SIPS URI или значения параметров, ДОЛЖНЫ регистрировать их в IANA, как описано ниже.
Registered SIP and SIPS URI parameters and their values are to be considered "reserved words". In order to preserve interoperability, registered parameters MUST be used in a manner consistent with that described in their defining RFC. Implementations MUST NOT utilize "private" or "locally defined" URI parameters that conflict with registered parameters. Note that although unregistered SIP and SIPS URI parameters may be used in implementations, developers are cautioned that usage of such parameters is risky. New SIP and SIPS URI parameters and new values for them may be registered at any time, and there is no assurance that these new registered URI parameters will not conflict with unregistered parameters currently in use.
Зарегистрированные параметры SIP URI и SIPS URI и их значения следует рассматривать как «зарезервированные слова». Чтобы сохранить совместимость, зарегистрированные параметры ДОЛЖНЫ использоваться в соответствии с тем, как это описано в определяющем их RFC. Реализации НЕ ДОЛЖНЫ использовать «частные» или «локально определённые» параметры URI, конфликтующие с зарегистрированными параметрами. Отметим, что хотя незарегистрированные параметры SIP URI и SIPS URI могут использоваться в реализациях, разработчикам следует учитывать, что такое использование рискованно. Новые параметры SIP URI и SIPS URI и новые значения для них могут быть зарегистрированы в любое время, и нет гарантии, что эти новые зарегистрированные параметры URI не будут конфликтовать с незарегистрированными параметрами, используемыми в настоящее время.
Some SIP and SIPS URI parameters only accept a set of predefined parameter values. For example, a parameter indicating the transport protocol in use may only accept the predefined tokens TCP, UDP, and SCTP as valid values. Registering all parameter values for all SIP and SIPS URI parameters of this type would require a large number of subregistries. Instead, we have chosen to register URI parameter values by reference. That is, the entry in the URI parameter registry for a given URI parameter contains references to the RFCs defining new values of that parameter. References to RFCs defining parameter values appear in double brackets in the registry.
Некоторые параметры SIP URI и SIPS URI принимают только набор предопределённых значений параметров. Например, параметр, указывающий используемый протокол транспорта, может принимать в качестве допустимых значений только предопределённые токены TCP, UDP и SCTP. Регистрация всех значений параметров для всех параметров SIP URI и SIPS URI этого типа потребовала бы большого числа подреестров. Вместо этого мы решили регистрировать значения параметров URI по ссылке. То есть запись в реестре параметров URI для данного параметра URI содержит ссылки на RFC, определяющие новые значения этого параметра. Ссылки на RFC, определяющие значения параметров, в реестре приводятся в двойных квадратных скобках.
So, the SIP and SIPS URI parameter registry contains a column that indicates whether or not each parameter only accepts a set of predefined values. Implementers of parameters with a "yes" in that column need to find all the valid parameter values in the RFCs provided as references.
Таким образом, реестр параметров SIP URI и SIPS URI содержит столбец, указывающий, принимает ли каждый параметр только набор предопределённых значений. Реализаторам параметров со значением «yes» в этом столбце необходимо найти все допустимые значения параметров в RFC, приведённых в качестве ссылок.
4. IANA Considerations
4. Вопросы IANA
Section 27 of RFC 3261 [1] creates an IANA registry for method names, header field names, warning codes, status codes, and option tags. This specification creates a new sub-registry under the SIP Parameters registry.
Раздел 27 RFC 3261 [1] создаёт реестр IANA для имён методов, имён полей заголовков, кодов предупреждений, кодов состояния и тегов параметров. Настоящая спецификация создаёт новый подреестр в реестре SIP Parameters.
o SIP/SIPS URI Parameters
• Параметры SIP/SIPS URI
4.1. SIP and SIPS URI Parameters Sub-Registry
4.1. Подреестр параметров SIP и SIPS URI
New SIP and SIPS URI parameters and new parameter values are registered by the IANA. When registering a new SIP or SIPS parameter or a new value for a parameter, the following information MUST be provided.
Новые параметры SIP URI и SIPS URI и новые значения параметров регистрируются IANA. При регистрации нового параметра SIP или SIPS или нового значения параметра ДОЛЖНА быть предоставлена следующая информация.
o Name of the parameter.
• Имя параметра.
o Whether the parameter only accepts a set of predefined values.
• Принимает ли параметр только набор предопределённых значений.
o Reference to the RFC defining the parameter and to any RFC that defines new values for the parameter. References to RFCs defining parameter values appear in double brackets in the registry.
• Ссылка на RFC, определяющий параметр, и на любой RFC, определяющий новые значения параметра. Ссылки на RFC, определяющие значения параметров, в реестре приводятся в двойных квадратных скобках.
Table 1 contains the initial values for this sub-registry.
Таблица 1 содержит начальные значения для этого подреестра.
Parameter Name Predefined Values Reference ____________________________________________ comp Yes [RFC 3486] lr No [RFC 3261] maddr No [RFC 3261] method Yes [RFC 3261] transport Yes [RFC 3261] ttl No [RFC 3261] user Yes [RFC 3261]
Parameter Name Predefined Values Reference ____________________________________________ comp Yes [RFC 3486] lr No [RFC 3261] maddr No [RFC 3261] method Yes [RFC 3261] transport Yes [RFC 3261] ttl No [RFC 3261] user Yes [RFC 3261]
Table 1: IANA SIP and SIPS URI parameter sub-registry
Таблица 1: подреестр параметров SIP и SIPS URI IANA
Note that any given parameter name is registered both as a SIP and as a SIPS URI parameter. Still, some parameters may not apply to one of the schemes. We have chosen to register any parameter as both a SIP and SIPS URI parameter anyway to avoid having two parameters with the same name, one applicable to SIP URIs and one to SIPS URIs, but with different semantics. Implementors are urged to read the parameter specifications for a detailed description of the semantics of any parameter.
Отметим, что любое заданное имя параметра регистрируется и как параметр SIP URI, и как параметр SIPS URI. Тем не менее некоторые параметры могут не применяться к одной из схем. Мы всё же решили регистрировать любой параметр и как параметр SIP URI, и как параметр SIPS URI, чтобы избежать наличия двух параметров с одинаковым именем, один из которых применим к SIP URI, а другой к SIPS URI, но с разной семантикой. Реализаторам настоятельно рекомендуется прочитать спецификации параметров для подробного описания семантики любого параметра.
4.2. Registration Policy for SIP and SIPS URI Parameters
4.2. Политика регистрации параметров SIP и SIPS URI
As per the terminology in RFC 2434 [4], the registration policy for SIP and SIPS URI parameters shall be "Specification Required".
Согласно терминологии RFC 2434 [4], политикой регистрации параметров SIP и SIPS URI должна быть «Specification Required».
For the purposes of this registry, the parameter for which IANA registration is requested MUST be defined by a standards-track RFC.
Для целей этого реестра параметр, для которого запрашивается регистрация IANA, ДОЛЖЕН быть определён в RFC уровня Standards Track.
5. Security Considerations
5. Вопросы безопасности
The registry in this document does not in itself have security considerations. However, as mentioned in RFC 3427, an important reason for the IETF to manage the extensions of SIP is to ensure that all extensions and parameters are able to provide secure usage. The supporting RFC publications for parameter registrations described this specification MUST provide detailed security considerations for them.
Сам реестр в настоящем документе не имеет соображений безопасности. Однако, как упомянуто в RFC 3427, важная причина, по которой IETF управляет расширениями SIP, состоит в обеспечении того, чтобы все расширения и параметры могли обеспечивать безопасное использование. Поддерживающие публикации RFC для регистраций параметров, описанных в настоящей спецификации, ДОЛЖНЫ содержать подробные соображения безопасности для них.
