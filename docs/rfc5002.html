The Session Initiation Protocol (SIP) P-Profile-Key Private Header (P-Header)

Abstract
Аннотация
This document specifies the SIP P-Profile-Key P-header. This header field is used in the 3rd-Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) to provide SIP registrars and SIP proxy servers with the key of the profile corresponding to the destination SIP URI of a particular SIP request.
В этом документе указан SIP P-Profile-Key P-header. Это поле заголовка используется в IMS (IP Multimedia Subsystem) проекта партнерства 3-го поколения (3GPP) для предоставления регистраторам SIP и прокси SIP ключа профиля, соответствующего URI назначения SIP конкретного запроса SIP.
1. Introduction
1. Введение
The 3rd-Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) uses SIP [RFC3261] as its main signalling protocol. (For more information on the IMS, a detailed description can be found in 3GPP TS 23.228 [3GPP.23.228] and 3GPP TS 24.229 [3GPP.24.229]). 3GPP has identified a set of requirements that can be met, according to the procedures in [RFC3427], by defining a new SIP P-header.
IMS (IP Multimedia Subsystem) проекта партнерства 3-го поколения (3GPP) использует SIP [RFC3261] в качестве основного протокола сигнализации. (Для получения дополнительной информации о IMS подробное описание можно найти в 3GPP TS 23.228 [3GPP.23.228] и 3GPP TS 24.229 [3GPP.24.229]). 3GPP определил набор требований, которые могут быть выполнены в соответствии с процедурами, описанными в [RFC3427], путем определения нового SIP P-header.
The remainder of this document is organized as follows. Section 3 describes the scenario considered by 3GPP and Section 4 discusses the requirements derived from this scenario. Section 5 defines the P- Profile-Key header field, which meets those requirements, and Section 6 discusses the applicability and scope of this new header field. Section 7 registers the P-Profile-Key header field with the IANA and Section 8 discusses the security properties of the environment where this header field is intended to be used.
Оставшаяся часть этого документа организована следующим образом. В разделе 3 описан сценарий, рассматриваемый 3GPP, а в разделе 4 обсуждаются требования, вытекающие из этого сценария. В разделе 5 определяется поле заголовка P-Profile-Key, которое соответствует этим требованиям, а в разделе 6 обсуждаются применимость и область применения этого нового поля заголовка. В разделе 7 поле заголовка P-Profile-Key регистрируется в IANA, а в разделе 8 обсуждаются свойства безопасности среды, в которой это поле заголовка предназначено для использования.

3. Scenario
3. Сценарий
In the 3GPP IMS, there are scenarios where a set of proxies handling a request need to consult the same user database, as described in [RFC4457]. Those proxies typically use the destination SIP URI of the request as the key for their database queries. Nevertheless, when a proxy handles a Wildcarded Public Service Identity, the key to be used in its database query is not the destination SIP URI of the request, but a regular expression instead.
В IMS 3GPP существуют сценарии, когда набору прокси, обрабатывающих запрос, необходимо обращаться к одной и той же базе данных пользователей, как описано в [RFC4457]. Эти прокси обычно используют целевой SIP URI запроса в качестве ключа для запросов к базе данных. Тем не менее, когда прокси обрабатывает подстановочный идентификатор общедоступной службы, ключом, который будет использоваться в его запросе к базе данных, является не целевой SIP URI запроса, а вместо этого регулярное выражение.
Public Service Identities are SIP URIs that refer to services instead of users. That is, they address a specific application in an Application Server. Wildcarded Public Service Identities are a set of Public Service Identities that match a regular expression and share the same profile. For example, the Public Service Identities 'sip:chatroom-12@example.com' and 'sip:chatroom-657@example.com' would match the Wildcarded Public Service Identity 'sip:chatroom-!.*!@example.com'. For a description of Wildcarded Public Service Identities, see 3GPP TS 23.003 [3GPP.23.003].
Идентификаторы общедоступных служб — это SIP URI, которые относятся к службам, а не к пользователям. То есть они обращаются к конкретному приложению на сервере приложений. Подстановочные идентификаторы общедоступных служб — это набор идентификаторов общедоступных служб, которые соответствуют регулярному выражению и имеют один и тот же профиль. Например, идентификаторы государственной службы «sip:chatroom-12@example.com» и «sip:chatroom-657@example.com» будут соответствовать идентификатору государственной службы с подстановочными знаками «sip:chatroom-!.*!@example.com». Описание идентификаторов общедоступных служб с подстановочными знаками см. в 3GPP TS 23.003 [3GPP.23.003].
When a proxy queries the user database for a Public Service Identity for which there is no profile in the user database, the user database needs to find its matching Wildcarded Public Service Identity. For example, if the user database receives a query for 'sip:chatroom-657@example.com', the user database needs to go through all the Wildcarded Public Service Identity it has until it finds a matching one; in this case, 'sip:chatroom-!.*!@example.com'. The process to find a matching Wildcarded Public Service Identity can be computationally expensive, time consuming, or both.
Когда прокси запрашивает в базе данных пользователей идентификатор общедоступной службы, для которого в базе данных пользователей нет профиля, база данных пользователей должна найти соответствующий идентификатор общедоступной службы с подстановочными знаками. Например, если база данных пользователей получает запрос на «sip:chatroom-657@example.com», база данных пользователей должна пройти через все имеющиеся у нее подстановочные идентификаторы общедоступных служб, пока не найдет соответствующий; в данном случае «sip:chatroom-!.*!@example.com». Процесс поиска соответствующего идентификатора государственной службы с подстановочными знаками может быть дорогостоящим в вычислительном отношении или отнимать много времени, или и то, и другое.
When two proxies query the user database for the same Public Service Identity, which matches a Wildcarded Public Service Identity, the user database needs to perform the matching process twice. Having to perform that process twice can be avoided by having the first proxy obtain the Wildcarded Public Service Identity from the user database and transfer it, piggy-backed in the SIP message, to the second proxy. This way, the second proxy can query the user database using the Wildcarded Public Service Identity directly.
Когда два прокси запрашивают в базе данных пользователей один и тот же идентификатор общедоступной службы, который соответствует идентификатору общедоступной службы с подстановочными знаками, база данных пользователей должна выполнить процесс сопоставления дважды. Необходимости выполнения этого процесса дважды можно избежать, если первый прокси получит подстановочный идентификатор публичной службы из базы данных пользователей и передаст его вместе с сообщением SIP второму прокси. Таким образом, второй прокси может напрямую запрашивать базу данных пользователей, используя подстановочный идентификатор публичной службы.
An alternative, but undesirable, solution would consist of having the user database store every Public Service Identity and its matching Wildcarded Public Service Identity. The scalability and manageability properties of this approach are considerably worse than those of the approach described earlier.
Альтернативное, но нежелательное решение могло бы состоять в том, чтобы в базе данных пользователей хранились все идентификаторы общедоступных услуг и соответствующие им подстановочные идентификаторы общедоступных услуг. Свойства масштабируемости и управляемости этого подхода значительно хуже, чем у подхода, описанного ранее.
4. Requirements
4. Требования
This section lists the requirements derived from the previous scenario:
В этом разделе перечислены требования, вытекающие из предыдущего сценария:
1. It is necessary to optimize the response time for session establishment in the 3GPP IMS.
1. Необходимо оптимизировать время ответа на установление сессии в 3GPP IMS.
2. It is necessary to keep the user database's size and maintenance manageable (e.g., storing individual Public Service Identities matching a Wildcarded Public Service Identity in the user database is not believed to be an acceptable solution).
2. Необходимо поддерживать управляемость размера базы данных пользователей и ее обслуживание (например, сохранение отдельных идентификаторов общедоступных служб, соответствующих подстановочным идентификаторам общедоступных служб, в базе данных пользователей не считается приемлемым решением).
5. P-Profile-Key Header Field Definition
5. P-Profile-Key Определение поля заголовка
This document defines the SIP P-Profile-Key P-header. The P- Profile-Key P-header contains the key to be used by a proxy to query the user database for a given profile. The augmented Backus-Naur Form (BNF) [RFC4234] syntax of the P-Profile-Key header field is the following: P-Profile-Key = "P-Profile-Key" HCOLON (name-addr / addr-spec) *( SEMI generic-param )
Этот документ определяет SIP P-Profile-Key P-header. P-Profile-KeyP-header содержит ключ, который будет использоваться прокси для запроса пользовательской базы данных для данного профиля. Расширенный синтаксис формы Backus-Naur (BNF) [RFC4234] поля заголовка P-Profile-Key следующий: P-Profile-Key = «P-Profile-Key» HCOLON (имя-адрес / адрес-спецификация) *(SEMI generic-param)
The format of HCOLON, name-addr, addr-spec, and generic-param are defined in [RFC3261]. The format of Wildcarded Public Service Identities is defined in 3GPP TS 23.003 [3GPP.23.003]. They take the form of Extended Regular Expressions (ERE) as defined in Chapter 9 of IEEE 1003.1-2004 Part 1 [IEEE.1003.1-2004].
Формат HCOLON, name-addr, addr-spec и generic-param определены в [RFC3261]. Формат подстановочных идентификаторов общедоступных служб определен в 3GPP TS 23.003 [3GPP.23.003]. Они принимают форму расширенных регулярных выражений (ERE), как определено в главе 9 стандарта IEEE 1003.1-2004, часть 1 [IEEE.1003.1-2004].
The following is an example of a P-Profile-Key header field that contains a Wildcarded Public Service Identity: P-Profile-Key: <sip:chatroom-!.*!@example.com>
Ниже приведен пример поля заголовка P-Profile-Key, которое содержит подстановочный идентификатор общедоступной службы: P-Profile-Key: <sip:chatroom-!.*!@example.com>
6. Applicability
6. Применимость
According to [RFC3427], P-headers have a limited applicability. Specifications of P-headers such as this RFC need to clearly document the useful scope of the proposal, and explain its limitations and why it is not suitable for the general use of SIP on the Internet.
Согласно [RFC3427], P-headers имеют ограниченную применимость. Спецификации P-headers, такие как этот RFC, должны четко документировать полезный объем предложения, а также объяснять его ограничения и причины, по которым оно не подходит для общего использования SIP в Интернете.
The P-Profile-Key header field is intended to be used in 3GPP IMS networks. This header field carries the key of a service profile, that is stored in a user database referred to as HSS, between two proxies, which are referred to as I-CSCF and S-CSCF. The I-CSCF and the S-CSCF belong to the same administrative domain and share a common frame of reference to the user database. The I-CSCF inserts the P-Profile-Key header field into a SIP request and the S-CSCF removes it before routing the request further. (For a description of how an I-CSCF and an S-CSCF query the same user database for a single request, see [RFC4457].)
Поле заголовка P-Profile-Key предназначено для использования в сетях 3GPP IMS. Это поле заголовка переносит ключ профиля службы, который хранится в пользовательской базе данных, называемой HSS, между двумя прокси, которые называются I-CSCF и S-CSCF. I-CSCF и S-CSCF принадлежат одному и тому же административному домену и имеют общую систему координат для базы данных пользователей. I-CSCF вставляет поле заголовка P-Profile-Key в запрос SIP, а S-CSCF удаляет его перед дальнейшей маршрутизацией запроса. (Описание того, как I-CSCF и S-CSCF запрашивают одну и ту же пользовательскую базу данных для одного запроса, см. в [RFC4457].)
Typically, when SIP is used on the Internet, there are not multiple proxies with a trust relationship between them querying the same user database. Consequently, the P-Profile-Key header field does not seem useful in a general Internet environment.
Обычно при использовании SIP в Интернете не существует нескольких прокси с доверительными отношениями между ними, запрашивающих одну и ту же базу данных пользователей. Следовательно, поле заголовка P-Profile-Key не кажется полезным в обычной среде Интернета.
7. IANA Considerations
7. Вопросы IANA
This document defines a new SIP header field: P-Profile-Key. This header field has been registered by the IANA in the SIP Parameters registry under the Header Fields subregistry.
Этот документ определяет новое поле заголовка SIP: P-Profile-Key. Это поле заголовка зарегистрировано IANA в реестре параметров SIP в подреестре полей заголовка.
8. Security Considerations
8. Вопросы безопасности
The P-Profile-Key defined in this document is to be used in an environment where elements are trusted and where attackers are not supposed to have access to the protocol messages between those elements. Traffic protection between network elements is sometimes achieved by using IPsec and sometimes by physically protecting the network. In any case, the environment where the P-Profile-Key header field will be used ensures the integrity and the confidentiality of the contents of this header field. The P-Profile-Key header field MUST NOT be used in environments that do not have these characteristics.
P-Profile-Key, определенный в этом документе, должен использоваться в среде, где элементы являются доверенными и где злоумышленники не должны иметь доступа к сообщениям протокола между этими элементами. Защита трафика между элементами сети иногда достигается за счет использования IPsec, а иногда за счет физической защиты сети. В любом случае среда, в которой будет использоваться поле заголовка P-Profile-Key, обеспечивает целостность и конфиденциальность содержимого этого поля заголовка. Поле заголовка P-Profile-Key НЕ ДОЛЖНО использоваться в средах, которые не имеют этих характеристик.
The P-Profile-Key header field needs to be integrity protected to keep attackers from modifying its contents. An attacker able to modify the contents of this header field could make the network apply a different service than the one corresponding to the request carrying the P-Profile-Key header field.
Поле заголовка P-Profile-Key должно быть защищено от изменения целостности, чтобы злоумышленники не могли изменить его содержимое. Злоумышленник, способный изменить содержимое этого поля заголовка, может заставить сеть применить услугу, отличную от той, которая соответствует запросу, содержащему поле заголовка P-Profile-Key.
The contents of the P-Profile-Key field need to be kept confidential. An attacker able to access the contents of this header field would obtain certain knowledge about the way services are structured in a given domain.
Содержимое поля P-Profile-Key необходимо сохранять конфиденциальным. Злоумышленник, имеющий доступ к содержимому этого поля заголовка, получит определенные знания о том, как структурированы службы в данном домене.
