1. Introduction
1. Введение
This document defines the "Basic" Hypertext Transfer Protocol (HTTP) authentication scheme, which transmits credentials as user-id/ password pairs, encoded using Base64 (HTTP authentication schemes are defined in [RFC7235]).
В настоящем документе определяется схема аутентификации «Basic» протокола передачи гипертекста (HTTP), которая передаёт учётные данные в виде пар «идентификатор пользователя/пароль», кодируемых с помощью base64 (схемы аутентификации HTTP определены в [RFC7235]).
This scheme is not considered to be a secure method of user authentication unless used in conjunction with some external secure system such as TLS (Transport Layer Security, [RFC5246]), as the user-id and password are passed over the network as cleartext.
Эта схема не считается безопасным методом аутентификации пользователей, если она не используется совместно с некоторой внешней защищённой системой, такой как TLS (Transport Layer Security, [RFC5246]), поскольку идентификатор пользователя и пароль передаются по сети в открытом виде.
The "Basic" scheme previously was defined in Section 2 of [RFC2617]. This document updates the definition, and also addresses internationalization issues by introducing the 'charset' authentication parameter (Section 2.1).
Ранее схема «Basic» была определена в разделе 2 документа [RFC2617]. Настоящий документ обновляет это определение, а также решает вопросы интернационализации путём введения параметра аутентификации 'charset' (раздел 2.1).
Other documents updating RFC 2617 are "Hypertext Transfer Protocol (HTTP/1.1): Authentication" ([RFC7235], defining the authentication framework), "HTTP Digest Access Authentication" ([RFC7616], updating the definition of the "Digest" authentication scheme), and "HTTP Authentication-Info and Proxy-Authentication-Info Response Header Fields" ([RFC7615]). Taken together, these four documents obsolete RFC 2617.
Другими документами, обновляющими RFC 2617, являются «Hypertext Transfer Protocol (HTTP/1.1): Authentication» ([RFC7235], определяющий основы аутентификации), «HTTP Digest Access Authentication» ([RFC7616], обновляющий определение схемы аутентификации «Digest») и «HTTP Authentication-Info and Proxy-Authentication-Info Response Header Fields» ([RFC7615]). В совокупности эти четыре документа признают RFC 2617 устаревшим.

2. The 'Basic' Authentication Scheme
2. Схема аутентификации «Basic»
The Basic authentication scheme is based on the model that the client needs to authenticate itself with a user-id and a password for each protection space ("realm"). The realm value is a free-form string that can only be compared for equality with other realms on that server. The server will service the request only if it can validate the user-id and password for the protection space applying to the requested resource. The Basic authentication scheme utilizes the Authentication Framework as follows.
Схема аутентификации Basic основана на модели, в которой клиенту необходимо аутентифицировать себя с помощью идентификатора пользователя и пароля для каждого пространства защиты («области защиты», realm). Значение realm — строка свободной формы, которую можно сравнивать только на равенство с другими realm на том же сервере. Сервер обслужит запрос, только если он сможет проверить идентификатор пользователя и пароль для пространства защиты, применимого к запрошенному ресурсу. Схема аутентификации Basic использует основы аутентификации следующим образом.
In challenges:
В запросах:
o The scheme name is "Basic".
o Имя схемы — «Basic».
o The authentication parameter 'realm' is REQUIRED ([RFC7235], Section 2.2).
o Параметр аутентификации 'realm' является ОБЯЗАТЕЛЬНЫМ ([RFC7235], раздел 2.2).
o The authentication parameter 'charset' is OPTIONAL (see Section 2.1).
o Параметр аутентификации 'charset' является НЕОБЯЗАТЕЛЬНЫМ (см. раздел 2.1).
o No other authentication parameters are defined -- unknown parameters MUST be ignored by recipients, and new parameters can only be defined by revising this specification.
o Другие параметры аутентификации не определены — неизвестные параметры должны игнорироваться получателями, а новые параметры могут быть определены только путём пересмотра настоящей спецификации.
See also Section 4.1 of [RFC7235], which discusses the complexity of parsing challenges properly.
См. также раздел 4.1 документа [RFC7235], в котором обсуждается сложность корректного разбора запросов аутентификации.
Note that both scheme and parameter names are matched case- insensitively.
Обратите внимание, что имена схем и имена параметров сопоставляются без учёта регистра.
For credentials, the "token68" syntax defined in Section 2.1 of [RFC7235] is used. The value is computed based on user-id and password as defined below.
Для учётных данных используется синтаксис «token68», определённый в разделе 2.1 документа [RFC7235]. Значение вычисляется на основе идентификатора пользователя и пароля, как определено ниже.
Upon receipt of a request for a URI within the protection space that lacks credentials, the server can reply with a challenge using the 401 (Unauthorized) status code ([RFC7235], Section 3.1) and the WWW-Authenticate header field ([RFC7235], Section 4.1).
При получении запроса на URI в пределах пространства защиты, в котором отсутствуют учётные данные, сервер может ответить запросом аутентификации с использованием кода состояния 401 (Unauthorized) ([RFC7235], раздел 3.1) и поля заголовка WWW-Authenticate ([RFC7235], раздел 4.1).
For instance: HTTP/1.1 401 Unauthorized Date: Mon, 04 Feb 2014 16:50:53 GMT WWW-Authenticate: Basic realm="WallyWorld"
Например: HTTP/1.1 401 Unauthorized Date: Mon, 04 Feb 2014 16:50:53 GMT WWW-Authenticate: Basic realm="WallyWorld"
where "WallyWorld" is the string assigned by the server to identify the protection space.
где «WallyWorld» — строка, назначенная сервером для идентификации пространства защиты.
A proxy can respond with a similar challenge using the 407 (Proxy Authentication Required) status code ([RFC7235], Section 3.2) and the Proxy-Authenticate header field ([RFC7235], Section 4.3). To receive authorization, the client
Прокси может ответить аналогичным запросом аутентификации с использованием кода состояния 407 (Proxy Authentication Required) ([RFC7235], раздел 3.2) и поля заголовка Proxy-Authenticate ([RFC7235], раздел 4.3). Для получения авторизации клиент
1. obtains the user-id and password from the user,
1. получает идентификатор пользователя и пароль от пользователя,
2. constructs the user-pass by concatenating the user-id, a single colon (":") character, and the password,
2. формирует user-pass, объединяя идентификатор пользователя, один символ двоеточия (":") и пароль,
3. encodes the user-pass into an octet sequence (see below for a discussion of character encoding schemes),
3. кодирует user-pass в последовательность октетов (обсуждение схем кодирования символов см. ниже),
4. and obtains the basic-credentials by encoding this octet sequence using Base64 ([RFC4648], Section 4) into a sequence of US-ASCII characters ([RFC0020]).
4. и получает basic-credentials, кодируя эту последовательность октетов с помощью base64 ([RFC4648], раздел 4) в последовательность символов US-ASCII ([RFC0020]).
The original definition of this authentication scheme failed to specify the character encoding scheme used to convert the user-pass into an octet sequence. In practice, most implementations chose either a locale-specific encoding such as ISO-8859-1 ([ISO-8859-1]), or UTF-8 ([RFC3629]). For backwards compatibility reasons, this specification continues to leave the default encoding undefined, as long as it is compatible with US-ASCII (mapping any US-ASCII character to a single octet matching the US-ASCII character code).
Исходное определение этой схемы аутентификации не указывало схему кодирования символов, используемую для преобразования user-pass в последовательность октетов. На практике большинство реализаций выбирали либо кодировку, зависящую от локали, например ISO-8859-1 ([ISO-8859-1]), либо UTF-8 ([RFC3629]). По соображениям обратной совместимости настоящая спецификация продолжает оставлять кодировку по умолчанию неопределённой, при условии что она совместима с US-ASCII (отображая любой символ US-ASCII в один октет, соответствующий коду символа US-ASCII).
The user-id and password MUST NOT contain any control characters (see "CTL" in Appendix B.1 of [RFC5234]).
Идентификатор пользователя и пароль НЕ ДОЛЖНЫ содержать управляющих символов (см. «CTL» в приложении B.1 документа [RFC5234]).
Furthermore, a user-id containing a colon character is invalid, as the first colon in a user-pass string separates user-id and password from one another; text after the first colon is part of the password. User-ids containing colons cannot be encoded in user-pass strings.
Кроме того, идентификатор пользователя, содержащий символ двоеточия, недопустим, поскольку первое двоеточие в строке user-pass отделяет идентификатор пользователя от пароля; текст после первого двоеточия является частью пароля. Идентификаторы пользователей, содержащие двоеточия, не могут быть закодированы в строках user-pass.
Note that many user agents produce user-pass strings without checking that user-ids supplied by users do not contain colons; recipients will then treat part of the username input as part of the password.
Обратите внимание, что многие пользовательские агенты формируют строки user-pass, не проверяя, что предоставленные пользователями идентификаторы не содержат двоеточий; получатели в этом случае будут считать часть введённого имени пользователя частью пароля.
If the user agent wishes to send the user-id "Aladdin" and password "open sesame", it would use the following header field:
Если пользовательский агент желает отправить идентификатор пользователя «Aladdin» и пароль «open sesame», он использует следующее поле заголовка:
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==
2.1. The 'charset' auth-param
2.1. Параметр аутентификации 'charset'
In challenges, servers can use the 'charset' authentication parameter to indicate the character encoding scheme they expect the user agent to use when generating "user-pass" (a sequence of octets). This information is purely advisory. The only allowed value is "UTF-8"; it is to be matched case- insensitively (see [RFC2978], Section 2.3). It indicates that the server expects character data to be converted to Unicode Normalization Form C ("NFC"; see Section 3 of [RFC5198]) and to be encoded into octets using the UTF-8 character encoding scheme ([RFC3629]).
В запросах аутентификации серверы могут использовать параметр аутентификации 'charset', чтобы указать схему кодирования символов, которую, как они ожидают, пользовательский агент будет использовать при формировании «user-pass» (последовательности октетов). Эта информация носит исключительно рекомендательный характер. Единственное допустимое значение — «UTF-8»; оно сопоставляется без учёта регистра (см. [RFC2978], раздел 2.3). Оно указывает, что сервер ожидает преобразования символьных данных в форму нормализации Unicode C («NFC»; см. раздел 3 документа [RFC5198]) и кодирования их в октеты с использованием схемы кодирования символов UTF-8 ([RFC3629]).
For the user-id, recipients MUST support all characters defined in the "UsernameCasePreserved" profile defined in Section 3.3 of [RFC7613], with the exception of the colon (":") character.
Для идентификатора пользователя получатели ДОЛЖНЫ поддерживать все символы, определённые в профиле «UsernameCasePreserved», определённом в разделе 3.3 документа [RFC7613], за исключением символа двоеточия (":").
For the password, recipients MUST support all characters defined in the "OpaqueString" profile defined in Section 4.2 of [RFC7613].
Для пароля получатели ДОЛЖНЫ поддерживать все символы, определённые в профиле «OpaqueString», определённом в разделе 4.2 документа [RFC7613].
Other values are reserved for future use.
Другие значения зарезервированы для будущего использования.
Note: The 'charset' is only defined on challenges, as Basic authentication uses a single token for credentials ('token68' syntax); thus, the credentials syntax isn't extensible.
Примечание. Параметр 'charset' определён только в запросах аутентификации, поскольку аутентификация Basic использует для учётных данных один токен (синтаксис 'token68'); таким образом, синтаксис учётных данных не является расширяемым.
Note: The name 'charset' has been chosen for consistency with Section 2.1.1 of [RFC2831]. A better name would have been 'accept-charset', as it is not about the message it appears in, but the server's expectation.
Примечание. Имя 'charset' выбрано для согласованности с разделом 2.1.1 документа [RFC2831]. Лучшим именем было бы 'accept-charset', поскольку оно относится не к сообщению, в котором появляется, а к ожиданиям сервера.
In the example below, the server prompts for authentication in the "foo" realm, using Basic authentication, with a preference for the UTF-8 character encoding scheme:
В приведённом ниже примере сервер запрашивает аутентификацию в области защиты «foo», используя аутентификацию Basic, с предпочтением схемы кодирования символов UTF-8:
WWW-Authenticate: Basic realm="foo", charset="UTF-8"

2.2. Reusing Credentials
2.2. Повторное использование учётных данных
Given the absolute URI ([RFC3986], Section 4.3) of an authenticated request, the authentication scope of that request is obtained by removing all characters after the last slash ("/") character of the path component ("hier_part"; see [RFC3986], Section 3). A client SHOULD assume that resources identified by URIs with a prefix-match of the authentication scope are also within the protection space specified by the realm value of that authenticated request.
Для абсолютного URI ([RFC3986], раздел 4.3) аутентифицированного запроса область аутентификации этого запроса получается путём удаления всех символов после последнего символа косой черты ("/") компонента пути ("hier_part"; см. [RFC3986], раздел 3). Клиенту СЛЕДУЕТ предполагать, что ресурсы, идентифицируемые URI с префиксным совпадением области аутентификации, также находятся в пределах пространства защиты, указанного значением realm этого аутентифицированного запроса.
A client MAY preemptively send the corresponding Authorization header field with requests for resources in that space without receipt of another challenge from the server. Similarly, when a client sends a request to a proxy, it MAY reuse a user-id and password in the Proxy- Authorization header field without receiving another challenge from the proxy server.
Клиент МОЖЕТ упреждающе отправлять соответствующее поле заголовка Authorization с запросами ресурсов в этой области, не получая очередного запроса аутентификации от сервера. Аналогично, когда клиент отправляет запрос прокси, он МОЖЕТ повторно использовать идентификатор пользователя и пароль в поле заголовка Proxy-Authorization, не получая очередного запроса аутентификации от прокси-сервера.

3. Internationalization Considerations
3. Соображения интернационализации
User-ids or passwords containing characters outside the US-ASCII character repertoire will cause interoperability issues, unless both communication partners agree on what character encoding scheme is to be used. Servers can use the new 'charset' parameter (Section 2.1) to indicate a preference of "UTF-8", increasing the probability that clients will switch to that encoding.
Идентификаторы пользователей или пароли, содержащие символы за пределами символьного репертуара US-ASCII, вызовут проблемы совместимости, если только оба участника обмена не договорятся о том, какая схема кодирования символов должна использоваться. Серверы могут использовать новый параметр 'charset' (раздел 2.1), чтобы указать предпочтение «UTF-8», повышая вероятность того, что клиенты перейдут на эту кодировку.
The 'realm' parameter carries data that can be considered textual; however, [RFC7235] does not define a way to reliably transport non- US-ASCII characters. This is a known issue that would need to be addressed in a revision to that specification.
Параметр 'realm' переносит данные, которые можно считать текстовыми; однако [RFC7235] не определяет способ надёжной передачи символов, не входящих в US-ASCII. Это известная проблема, которую нужно будет решить в пересмотренной версии этой спецификации.
4. Security Considerations
4. Соображения безопасности
The Basic authentication scheme is not a secure method of user authentication, nor does it in any way protect the entity, which is transmitted in cleartext across the physical network used as the carrier. HTTP does not prevent the addition of enhancements (such as schemes to use one-time passwords) to Basic authentication.
Схема аутентификации Basic не является безопасным методом аутентификации пользователей и никоим образом не защищает объект, который передаётся в открытом виде по физической сети, используемой в качестве носителя. HTTP не препятствует добавлению к аутентификации Basic улучшений (например, схем использования одноразовых паролей).
The most serious flaw of Basic authentication is that it results in the cleartext transmission of the user's password over the physical network. Many other authentication schemes address this problem.
Самый серьёзный недостаток аутентификации Basic заключается в том, что она приводит к передаче пароля пользователя в открытом виде по физической сети. Многие другие схемы аутентификации решают эту проблему.
Because Basic authentication involves the cleartext transmission of passwords, it SHOULD NOT be used (without enhancements such as HTTPS [RFC2818]) to protect sensitive or valuable information.
Поскольку аутентификация Basic связана с передачей паролей в открытом виде, её НЕ СЛЕДУЕТ использовать (без таких улучшений, как HTTPS [RFC2818]) для защиты конфиденциальной или ценной информации.
A common use of Basic authentication is for identification purposes -- requiring the user to provide a user-id and password as a means of identification, for example, for purposes of gathering accurate usage statistics on a server. When used in this way it is tempting to think that there is no danger in its use if illicit access to the protected documents is not a major concern. This is only correct if the server issues both user-id and password to the users and, in particular, does not allow the user to choose his or her own password. The danger arises because naive users frequently reuse a single password to avoid the task of maintaining multiple passwords.
Обычно аутентификация Basic используется в целях идентификации — от пользователя требуется предоставить идентификатор пользователя и пароль как средство идентификации, например для сбора точной статистики использования на сервере. При таком использовании легко подумать, что опасности нет, если несанкционированный доступ к защищённым документам не является серьёзной проблемой. Это верно только в том случае, если сервер выдаёт пользователям и идентификатор пользователя, и пароль и, в частности, не позволяет пользователю выбирать собственный пароль. Опасность возникает потому, что неопытные пользователи часто повторно используют один пароль, чтобы избежать необходимости поддерживать несколько паролей.
If a server permits users to select their own passwords, then the threat is not only unauthorized access to documents on the server but also unauthorized access to any other resources on other systems that the user protects with the same password. Furthermore, in the server's password database, many of the passwords may also be users' passwords for other sites. The owner or administrator of such a system could therefore expose all users of the system to the risk of unauthorized access to all those other sites if this information is not maintained in a secure fashion. This raises both security and privacy concerns ([RFC6973]). If the same user-id and password combination is in use to access other accounts, such as an email or health portal account, personal information could be exposed.
Если сервер позволяет пользователям выбирать собственные пароли, то угроза состоит не только в несанкционированном доступе к документам на сервере, но и в несанкционированном доступе к любым другим ресурсам на других системах, которые пользователь защищает тем же паролем. Кроме того, в базе паролей сервера многие из паролей могут быть также паролями пользователей для других сайтов. Поэтому владелец или администратор такой системы мог бы подвергнуть всех пользователей системы риску несанкционированного доступа ко всем этим другим сайтам, если эта информация не поддерживается в безопасном виде. Это порождает как соображения безопасности, так и соображения конфиденциальности ([RFC6973]). Если одна и та же комбинация идентификатора пользователя и пароля используется для доступа к другим учётным записям, например к учётной записи электронной почты или портала здравоохранения, личная информация может быть раскрыта.
Basic authentication is also vulnerable to spoofing by counterfeit servers. If a user can be led to believe that she is connecting to a host containing information protected by Basic authentication when, in fact, she is connecting to a hostile server or gateway, then the attacker can request a password, store it for later use, and feign an error. Server implementers ought to guard against this sort of counterfeiting; in particular, software components that can take over control over the message framing on an existing connection need to be used carefully or not at all (for instance: NPH ("Non-Parsed Header") scripts as described in Section 5 of [RFC3875]).
Аутентификация Basic также уязвима к подмене поддельными серверами. Если пользователя можно убедить, что он подключается к узлу, содержащему информацию, защищённую аутентификацией Basic, тогда как на самом деле он подключается к враждебному серверу или шлюзу, то злоумышленник может запросить пароль, сохранить его для последующего использования и имитировать ошибку. Разработчикам серверов следует защищаться от такой подделки; в частности, программные компоненты, способные перехватывать управление кадрированием сообщений в существующем соединении, должны использоваться осторожно или не использоваться вовсе (например, сценарии NPH («Non-Parsed Header»), описанные в разделе 5 документа [RFC3875]).
Servers and proxies implementing Basic authentication need to store user passwords in some form in order to authenticate a request. These passwords ought to be stored in such a way that a leak of the password data doesn't make them trivially recoverable. This is especially important when users are allowed to set their own passwords, since users are known to choose weak passwords and to reuse them across authentication realms. While a full discussion of good password hashing techniques is beyond the scope of this document, server operators ought to make an effort to minimize risks to their users in the event of a password data leak. For example, servers ought to avoid storing user passwords in plaintext or as unsalted digests. For more discussion about modern password hashing techniques, see the "Password Hashing Competition" (<https://password-hashing.net>).
Серверы и прокси, реализующие аутентификацию Basic, должны хранить пароли пользователей в некоторой форме, чтобы аутентифицировать запрос. Эти пароли следует хранить так, чтобы утечка данных о паролях не делала их тривиально восстановимыми. Это особенно важно, когда пользователям разрешено задавать собственные пароли, поскольку известно, что пользователи выбирают слабые пароли и повторно используют их в разных областях защиты. Хотя полное обсуждение хороших методов хеширования паролей выходит за рамки настоящего документа, операторам серверов следует прилагать усилия для минимизации рисков для своих пользователей в случае утечки данных о паролях. Например, серверам следует избегать хранения паролей пользователей в открытом виде или в виде хешей без соли. Более подробное обсуждение современных методов хеширования паролей см. в «Password Hashing Competition» (<https://password-hashing.net>).
The use of the UTF-8 character encoding scheme and of normalization introduces additional security considerations; see Section 10 of [RFC3629] and Section 6 of [RFC5198] for more information.
Использование схемы кодирования символов UTF-8 и нормализации порождает дополнительные соображения безопасности; дополнительную информацию см. в разделе 10 документа [RFC3629] и разделе 6 документа [RFC5198].

Appendix B. Deployment Considerations for the 'charset' Parameter
Приложение B. Соображения по развёртыванию для параметра 'charset'
B.1. User Agents
B.1. Пользовательские агенты
User agents not implementing 'charset' will continue to work as before, ignoring the new parameter.
Пользовательские агенты, не реализующие 'charset', будут работать как прежде, игнорируя новый параметр.
User agents that already default to the UTF-8 encoding implement 'charset' by definition.
Пользовательские агенты, которые уже по умолчанию используют кодировку UTF-8, реализуют 'charset' по определению.
Other user agents can keep their default behavior and switch to UTF-8 when seeing the new parameter.
Другие пользовательские агенты могут сохранять поведение по умолчанию и переключаться на UTF-8 при обнаружении нового параметра.
B.2. Servers
B.2. Серверы
Servers that do not support non-US-ASCII characters in credentials do not require any changes to support 'charset'.
Серверы, не поддерживающие символы, отличные от US-ASCII, в учётных данных, не требуют никаких изменений для поддержки 'charset'.
Servers that need to support non-US-ASCII characters, but cannot use the UTF-8 character encoding scheme will not be affected; they will continue to function as well or as badly as before.
Серверы, которым необходимо поддерживать символы, отличные от US-ASCII, но которые не могут использовать схему кодирования символов UTF-8, затронуты не будут; они продолжат работать так же хорошо или так же плохо, как и раньше.
Finally, servers that need to support non-US-ASCII characters and can use the UTF-8 character encoding scheme can opt in by specifying the 'charset' parameter in the authentication challenge. Clients that do understand the 'charset' parameter will then start to use UTF-8, while other clients will continue to send credentials in their default encoding, broken credentials, or no credentials at all. Until all clients are upgraded to support UTF-8, servers are likely to see both UTF-8 and "legacy" encodings in requests. When processing as UTF-8 fails (due to a failure to decode as UTF-8 or a mismatch of user-id/password), a server might try a fallback to the previously supported legacy encoding in order to accommodate these legacy clients. Note that implicit retries need to be done carefully; for instance, some subsystems might detect repeated login failures and treat them as a potential credentials-guessing attack.
Наконец, серверы, которым необходимо поддерживать символы, отличные от US-ASCII, и которые могут использовать схему кодирования символов UTF-8, могут включить её, указав параметр 'charset' в запросе аутентификации. Клиенты, которые действительно понимают параметр 'charset', начнут использовать UTF-8, тогда как другие клиенты будут продолжать отправлять учётные данные в своей кодировке по умолчанию, повреждённые учётные данные или не отправлять учётные данные вообще. Пока все клиенты не будут обновлены для поддержки UTF-8, серверы, вероятно, будут получать в запросах как UTF-8, так и «устаревшие» кодировки. Когда обработка как UTF-8 завершается неудачей (из-за сбоя декодирования как UTF-8 или несовпадения идентификатора пользователя и пароля), сервер может попытаться перейти к ранее поддерживаемой устаревшей кодировке, чтобы обслужить таких устаревших клиентов. Обратите внимание, что неявные повторные попытки нужно выполнять осторожно; например, некоторые подсистемы могут обнаруживать повторяющиеся неудачи входа и рассматривать их как потенциальную атаку подбора учётных данных.
B.3. Why not simply switch the default encoding to UTF-8?
B.3. Почему бы просто не переключить кодировку по умолчанию на UTF-8?
There are sites in use today that default to a local character encoding scheme, such as ISO-8859-1 ([ISO-8859-1]), and expect user agents to use that encoding. Authentication on these sites will stop working if the user agent switches to a different encoding, such as UTF-8.
Сегодня существуют сайты, которые по умолчанию используют локальную схему кодирования символов, например ISO-8859-1 ([ISO-8859-1]), и ожидают, что пользовательские агенты будут применять эту кодировку. Аутентификация на таких сайтах перестанет работать, если пользовательский агент переключится на другую кодировку, например UTF-8.
Note that sites might even inspect the User-Agent header field ([RFC7231], Section 5.5.3) to decide which character encoding scheme to expect from the client. Therefore, they might support UTF-8 for some user agents, but default to something else for others. User agents in the latter group will have to continue to do what they do today until the majority of these servers have been upgraded to always use UTF-8.
Обратите внимание, что сайты могут даже анализировать поле заголовка User-Agent ([RFC7231], раздел 5.5.3), чтобы решить, какую схему кодирования символов ожидать от клиента. Поэтому они могут поддерживать UTF-8 для некоторых пользовательских агентов, но по умолчанию использовать что-то другое для остальных. Пользовательским агентам из последней группы придётся продолжать делать то, что они делают сегодня, пока большинство таких серверов не будет обновлено для постоянного использования UTF-8.
