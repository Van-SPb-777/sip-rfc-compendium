Abstract
Аннотация
This document updates RFC 3261 by modifying the Digest Access Authentication scheme used by the Session Initiation Protocol (SIP) to add support for more secure digest algorithms, e.g., SHA-256 and SHA-512/256, to replace the obsolete MD5 algorithm.
Настоящий документ обновляет RFC 3261, изменяя схему дайджест-аутентификации доступа, используемую протоколом инициирования сессий (SIP), чтобы добавить поддержку более стойких дайджест-алгоритмов, например SHA-256 и SHA-512/256, на замену устаревшему алгоритму MD5.

1. Introduction
1. Введение
The Session Initiation Protocol [RFC3261] uses the same mechanism as the Hypertext Transfer Protocol (HTTP) does for authenticating users. This mechanism is called "Digest Access Authentication". It is a simple challenge-response mechanism that allows a server to challenge a client request and allows a client to provide authentication information in response to that challenge. The version of Digest Access Authentication that [RFC3261] references is specified in [RFC2617].
Протокол инициирования сессий [RFC3261] использует для аутентификации пользователей тот же механизм, что и протокол передачи гипертекста (HTTP). Этот механизм называется «дайджест-аутентификацией доступа». Это простой механизм «запрос-ответ», который позволяет серверу запросить аутентификацию у клиента, а клиенту — предоставить аутентификационную информацию в ответ на этот запрос. Версия дайджест-аутентификации доступа, на которую ссылается [RFC3261], определена в [RFC2617].
The default hash algorithm for Digest Access Authentication is MD5. However, it has been demonstrated that the MD5 algorithm is not collision resistant and is now considered a bad choice for a hash function (see [RFC6151]).
Хеш-алгоритмом по умолчанию для дайджест-аутентификации доступа является MD5. Однако было показано, что алгоритм MD5 не устойчив к коллизиям и теперь считается плохим выбором хеш-функции (см. [RFC6151]).
The HTTP Digest Access Authentication document [RFC7616] obsoletes [RFC2617] and adds stronger algorithms that can be used with the Digest Access Authentication scheme and establishes a registry for these algorithms, known as the "Hash Algorithms for HTTP Digest Authentication" IANA registry, so that algorithms can be added in the future.
Документ «Дайджест-аутентификация доступа HTTP» [RFC7616] делает [RFC2617] устаревшим, добавляет более стойкие алгоритмы, которые можно использовать со схемой дайджест-аутентификации доступа, и учреждает реестр этих алгоритмов, известный как реестр IANA «Hash Algorithms for HTTP Digest Authentication», чтобы алгоритмы можно было добавлять в будущем.
This document updates the Digest Access Authentication scheme used by SIP to support the algorithms listed in the "Hash Algorithms for HTTP Digest Authentication" IANA registry defined by [RFC7616].
Настоящий документ обновляет схему дайджест-аутентификации доступа, используемую SIP, чтобы поддержать алгоритмы, перечисленные в реестре IANA «Hash Algorithms for HTTP Digest Authentication», определённом в [RFC7616].

2.1. Hash Algorithms
2.1. Хеш-алгоритмы
The Digest Access Authentication scheme has an "algorithm" parameter that specifies the algorithm to be used to compute the digest of the response. The "Hash Algorithms for HTTP Digest Authentication" IANA registry specifies the algorithms that correspond to 'algorithm' values.
Схема дайджест-аутентификации доступа имеет параметр «algorithm», который задаёт алгоритм, используемый для вычисления дайджеста ответа. Реестр IANA «Hash Algorithms for HTTP Digest Authentication» задаёт алгоритмы, соответствующие значениям «algorithm».
[RFC3261] specifies only one algorithm, MD5, which is used by default. This document extends [RFC3261] to allow use of any algorithm listed in the "Hash Algorithms for HTTP Digest Authentication" IANA registry.
[RFC3261] определяет только один алгоритм — MD5, который используется по умолчанию. Настоящий документ расширяет [RFC3261], разрешая использовать любой алгоритм, перечисленный в реестре IANA «Hash Algorithms for HTTP Digest Authentication».
A UAS prioritizes which algorithm to use based on its policy, which is specified in Section 2.3 and parallels the process used in HTTP specified by [RFC7616].
UAS расставляет приоритеты алгоритмов, которые следует использовать, исходя из своей политики, определённой в разделе 2.3 и повторяющей процесс, применяемый в HTTP согласно [RFC7616].
2.2. Representation of Digest Values
2.2. Представление значений дайджеста
The size of the digest depends on the algorithm used. The bits in the digest are converted from the most significant to the least significant bit, four bits at a time, to the ASCII representation as follows. Each set of four bits is represented by its familiar hexadecimal notation from the characters 0123456789abcdef; that is, binary 0000 is represented by the character '0', 0001 is represented by '1', and so on up to the representation of 1111 as 'f'. If the SHA-256 or SHA-512/256 algorithm is used to calculate the digest, then the digest will be represented as 64 hexadecimal characters.
Размер дайджеста зависит от используемого алгоритма. Биты дайджеста преобразуются от старшего значащего бита к младшему по четыре бита за раз в представление ASCII следующим образом. Каждый набор из четырёх битов представляется привычной шестнадцатеричной записью с использованием символов 0123456789abcdef; то есть двоичное 0000 представляется символом «0», 0001 представляется символом «1» и так далее вплоть до представления 1111 как «f». Если для вычисления дайджеста используется алгоритм SHA-256 или SHA-512/256, то дайджест будет представлен как 64 шестнадцатеричных символа.
2.3. UAS Behavior
2.3. Поведение UAS
When a UAS receives a request from a UAC, and an acceptable Authorization header field is not received, the UAS can challenge the originator to provide credentials by rejecting the request with a 401/407 status code with the WWW-Authenticate/Proxy-Authenticate header field, respectively. The UAS MAY add multiple WWW- Authenticate/Proxy-Authenticate header fields to allow the UAS to utilize the best available algorithm supported by the client.
Когда UAS получает запрос от UAC и не получает приемлемого поля заголовка Authorization, UAS может запросить у отправителя учётные данные, отклонив запрос с кодом состояния 401/407 и полем заголовка WWW-Authenticate/Proxy-Authenticate соответственно. UAS МОЖЕТ добавлять несколько полей заголовка WWW-Authenticate/Proxy-Authenticate, чтобы использовать наилучший доступный алгоритм, поддерживаемый клиентом.
If the UAS challenges the originator using multiple WWW-Authenticate/ Proxy-Authenticate header fields with the same realm, then each of these header fields MUST use a different digest algorithm. The UAS MUST add these header fields to the response in the order in which it would prefer to see them used, starting with the most preferred algorithm at the top. The UAS cannot assume that the client will use the algorithm specified in the topmost header field.
Если UAS запрашивает у отправителя аутентификацию с помощью нескольких полей заголовка WWW-Authenticate/Proxy-Authenticate с одной и той же областью защиты, то каждое из этих полей заголовка ДОЛЖНО использовать другой дайджест-алгоритм. UAS ДОЛЖЕН добавлять эти поля заголовка в ответ в том порядке, в котором он предпочитает их видеть, начиная с наиболее предпочтительного алгоритма вверху. UAS не может предполагать, что клиент будет использовать алгоритм, указанный в самом верхнем поле заголовка.
2.4. UAC Behavior
2.4. Поведение UAC
When the UAC receives a response with multiple WWW-Authenticate/ Proxy-Authenticate header fields with the same realm, it SHOULD use the topmost header field that it supports unless a local policy dictates otherwise. The client MUST ignore any challenge it does not understand.
Когда UAC получает ответ с несколькими полями заголовка WWW-Authenticate/Proxy-Authenticate с одной и той же областью защиты, ему СЛЕДУЕТ использовать самое верхнее поле заголовка, которое он поддерживает, если только локальная политика не предписывает иное. Клиент ДОЛЖЕН игнорировать любой запрос аутентификации, который он не понимает.
When the UAC receives a 401 response with multiple WWW-Authenticate header fields with different realms, it SHOULD retry and add an Authorization header field containing credentials that match the topmost header field of any of the realms unless a local policy dictates otherwise.
Когда UAC получает ответ 401 с несколькими полями заголовка WWW-Authenticate с разными областями защиты, ему СЛЕДУЕТ повторить запрос и добавить поле заголовка Authorization, содержащее учётные данные, соответствующие самому верхнему полю заголовка любой из областей защиты, если только локальная политика не предписывает иное.
If the UAC cannot respond to any of the challenges in the response, then it SHOULD abandon attempts to send the request unless a local policy dictates otherwise, e.g., the policy might indicate the use of non-Digest mechanisms. For example, if the UAC does not have credentials or has stale credentials for any of the realms, the UAC will abandon the request.
Если UAC не может ответить ни на один из запросов аутентификации в ответе, то ему СЛЕДУЕТ отказаться от попыток отправить запрос, если только локальная политика не предписывает иное, например политика может указывать на использование механизмов, отличных от Digest. Например, если у UAC нет учётных данных или его учётные данные устарели для какой-либо из областей защиты, UAC откажется от запроса.
2.5. Forking
2.5. Разветвление
Section 22.3 of [RFC3261] discusses the operation of the proxy-to- user authentication, which describes the operation of the proxy when it forks a request. This section clarifies that operation.
В разделе 22.3 документа [RFC3261] рассматривается работа аутентификации «прокси-пользователь», которая описывает работу прокси, когда он разветвляет запрос. Настоящий раздел уточняет эту работу.
If a request is forked, various proxy servers and/or UAs may wish to challenge the UAC. In this case, the forking proxy server is responsible for aggregating these challenges into a single response. Each WWW-Authenticate and Proxy-Authenticate value received in response to the forked request MUST be placed into the single response that is sent by the forking proxy to the UAC.
Если запрос разветвляется, различные прокси-серверы и/или UA могут пожелать запросить аутентификацию у UAC. В этом случае разветвляющий прокси-сервер отвечает за объединение этих запросов аутентификации в единый ответ. Каждое значение WWW-Authenticate и Proxy-Authenticate, полученное в ответ на разветвлённый запрос, ДОЛЖНО быть помещено в единый ответ, который разветвляющий прокси отправляет UAC.
When the forking proxy places multiple WWW-Authenticate and Proxy- Authenticate header fields received from one downstream proxy into a single response, it MUST maintain the order of these header fields. The ordering of values received from different downstream proxies is not significant.
Когда разветвляющий прокси помещает несколько полей заголовка WWW-Authenticate и Proxy-Authenticate, полученных от одного нижестоящего прокси, в единый ответ, он ДОЛЖЕН сохранять порядок этих полей заголовка. Порядок значений, полученных от разных нижестоящих прокси, не имеет значения.

Therefore, in SIP, a UAS MUST check if the Request-URI in the Authorization/Proxy-Authorization header field value corresponds to a user for whom the UAS is willing to accept forwarded or direct requests; however, it MAY still accept it if the two fields are not equivalent.

В контексте SIP эти два URI могут указывать на разных пользователей из-за переадресации на некотором прокси. Поэтому в SIP UAS ДОЛЖЕН проверять, соответствует ли Request-URI в значении поля заголовка Authorization/Proxy-Authorization пользователю, для которого UAS готов принимать переадресованные или прямые запросы; однако он МОЖЕТ всё же принять его, если эти два поля не эквивалентны.
7. As a clarification to the calculation of the A2 value for message integrity assurance in the Digest Access Authentication scheme, implementers should assume that the hash of the entity-body resolves to the hash of an empty string when the entity-body is empty (that is, when SIP messages have no body):
7. В порядке уточнения вычисления значения A2 для обеспечения целостности сообщений в схеме дайджест-аутентификации доступа реализаторам следует предполагать, что хеш тела объекта сводится к хешу пустой строки, когда тело объекта пусто (то есть когда сообщения SIP не имеют тела):
H(entity-body) = <algorithm>("")
H(entity-body) = <algorithm>("")
For example, when the chosen algorithm is SHA-256, then:
Например, когда выбранный алгоритм — SHA-256, тогда:
H(entity-body) = SHA-256("") = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
H(entity-body) = SHA-256("") = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
8. A UAS MUST be able to properly handle a "qop" parameter received in an Authorization/Proxy-Authorization header field, and a UAC MUST be able to properly handle a "qop" parameter received in WWW-Authenticate and Proxy-Authenticate header fields. However, for backward compatibility reasons, the "qop" parameter is optional for clients and servers based on [RFC3261] to receive. If the "qop" parameter is not specified, then the default value is "auth".
8. UAS ДОЛЖЕН быть способен правильно обрабатывать параметр «qop», полученный в поле заголовка Authorization/Proxy-Authorization, а UAC ДОЛЖЕН быть способен правильно обрабатывать параметр «qop», полученный в полях заголовка WWW-Authenticate и Proxy-Authenticate. Однако по соображениям обратной совместимости получение параметра «qop» необязательно для клиентов и серверов, основанных на [RFC3261]. Если параметр «qop» не указан, то значением по умолчанию является «auth».
A UAS MUST always send a "qop" parameter in WWW-Authenticate and Proxy-Authenticate header field values, and a UAC MUST send the "qop" parameter in any resulting authorization header field.
UAS ДОЛЖЕН всегда отправлять параметр «qop» в значениях полей заголовка WWW-Authenticate и Proxy-Authenticate, а UAC ДОЛЖЕН отправлять параметр «qop» в любом результирующем поле заголовка авторизации.
The usage of the Authentication-Info header field continues to be allowed, since it provides integrity checks over the bodies and provides mutual authentication.
Использование поля заголовка Authentication-Info по-прежнему разрешено, поскольку оно обеспечивает проверки целостности тел и взаимную аутентификацию.
2.7. ABNF for SIP
2.7. ABNF для SIP
This document updates the ABNF [RFC5234] for SIP as follows.
Настоящий документ обновляет ABNF [RFC5234] для SIP следующим образом.
It extends the request-digest as follows to allow for different digest sizes:
Он расширяет request-digest следующим образом, чтобы допустить различные размеры дайджеста:
request-digest = LDQUOT *LHEX RDQUOT
request-digest = LDQUOT *LHEX RDQUOT
The number of hex digits is implied by the length of the value of the algorithm used, with a minimum size of 32. A parameter with an empty value (empty string) is allowed when the UAC has not yet received a challenge.
Число шестнадцатеричных цифр определяется длиной значения используемого алгоритма, при минимальном размере 32. Параметр с пустым значением (пустой строкой) допускается, когда UAC ещё не получил запрос аутентификации.
It extends the algorithm parameter as follows to allow any algorithm in the registry to be used:
Он расширяет параметр algorithm следующим образом, чтобы можно было использовать любой алгоритм из реестра:
algorithm = "algorithm" EQUAL ( "MD5" / "MD5-sess" / "SHA-256" /
algorithm = "algorithm" EQUAL ( "MD5" / "MD5-sess" / "SHA-256" /
"SHA-256-sess" / "SHA-512-256" / "SHA-512-256-sess" / token )
"SHA-256-sess" / "SHA-512-256" / "SHA-512-256-sess" / token )
3. Security Considerations
3. Соображения безопасности
This specification adds new secure algorithms to be used with the Digest mechanism to authenticate users. The obsolete MD5 algorithm remains only for backward compatibility with [RFC2617], but its use is NOT RECOMMENDED.
Настоящая спецификация добавляет новые стойкие алгоритмы для использования с механизмом Digest при аутентификации пользователей. Устаревший алгоритм MD5 остаётся только для обратной совместимости с [RFC2617], но его использование НЕ РЕКОМЕНДУЕТСЯ.
This opens the system to the potential for a downgrade attack by an on-path attacker. The most effective way of dealing with this type of attack is to either validate the client and challenge it accordingly or remove the support for backward compatibility by not supporting MD5.
Это открывает систему для потенциальной атаки понижения уровня со стороны атакующего, находящегося на пути. Наиболее эффективный способ борьбы с таким типом атак — либо проверить клиента и запросить у него аутентификацию соответствующим образом, либо отказаться от поддержки обратной совместимости, не поддерживая MD5.
See Section 5 of [RFC7616] for a detailed security discussion of the Digest Access Authentication scheme.
Подробное обсуждение безопасности схемы дайджест-аутентификации доступа см. в разделе 5 документа [RFC7616].
4. IANA Considerations
4. Соображения IANA
[RFC7616] defines an IANA registry named "Hash Algorithms for HTTP Digest Authentication" to simplify the introduction of new algorithms in the future. This document specifies that algorithms defined in that registry may be used in SIP digest authentication.
[RFC7616] определяет реестр IANA под названием «Hash Algorithms for HTTP Digest Authentication», чтобы упростить введение новых алгоритмов в будущем. Настоящий документ устанавливает, что алгоритмы, определённые в этом реестре, могут использоваться в дайджест-аутентификации SIP.
This document has no actions for IANA.
Данный документ не требует действий IANA.
