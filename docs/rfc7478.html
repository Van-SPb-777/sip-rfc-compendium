1. Introduction
1. Введение
This document presents a few use cases of web applications that are executed in a browser and use real-time communication capabilities. In most of the use cases, all end-user clients are web applications, but there are some use cases where at least one of the end-user clients is of another type (e.g., a mobile phone or a SIP User Agent (UA)).
В настоящем документе представлены несколько сценариев использования веб-приложений, которые выполняются в браузере и используют возможности связи в реальном времени. В большинстве сценариев все клиенты конечных пользователей являются веб-приложениями, но есть сценарии, в которых хотя бы один из клиентов конечных пользователей имеет другой тип (например, мобильный телефон или пользовательский агент SIP (UA)).

2.3.1. Simple Video Communication Service
2.3.1. Простой сервис видеосвязи
2.3.1.1. Description
2.3.1.1. Описание
Two or more users have loaded a video communication web application into their browsers, provided by the same service provider, and logged into the service it provides. The web service publishes information about user login status by pushing updates to the web application in the browsers. When one online user selects a peer online user, a 1:1 audiovisual communication session between the browsers of the two peers is initiated. The invited user might accept or reject the session.
Два или более пользователя загрузили в свои браузеры веб-приложение для видеосвязи, предоставленное одним и тем же поставщиком услуг, и вошли в обслуживаемую им службу. Веб-служба публикует сведения о состоянии входа пользователей, передавая обновления веб-приложению в браузерах. Когда один пользователь в сети выбирает другого пользователя, находящегося в сети, между браузерами этих двух одноранговых участников устанавливается сеанс аудиовизуальной связи 1:1. Приглашённый пользователь может принять или отклонить сеанс.
During session establishment, a self view is displayed, and once the session has been established the video sent from the remote peer is displayed in addition to the self view. During the session, each user can:
Во время установления сеанса отображается собственное изображение, а после установления сеанса в дополнение к нему отображается видео, отправленное удалённым одноранговым участником. Во время сеанса каждый пользователь может:
o select to remove and reinsert the self-view as often as desired,
o удалять и снова вставлять собственное изображение так часто, как пожелает,
o change the sizes of his/her two video displays during the session,
o изменять размеры двух своих видеодисплеев во время сеанса,
and
and
o pause the sending of media (audio, video, or both) and mute incoming media.
o приостанавливать отправку медиа (аудио, видео или обоих) и отключать входящие медиа.
It is essential that media and data be encrypted, authenticated, and integrity protected on a per-IP-packet basis and that media and data packets failing the integrity check not be delivered to the application.
Существенно, чтобы медиа и данные шифровались, аутентифицировались и защищались с точки зрения целостности на уровне каждого IP-пакета, а медиа- и пакеты данных, не прошедшие проверку целостности, не доставлялись приложению.

Приложение даёт пользователям возможность не допустить раскрытия IP-адреса узла приложению другого пользователя.
Any session participant can end the session at any time.
Любой участник сеанса может завершить сеанс в любое время.
The two users may be using communication devices with different operating systems and browsers from different vendors.
Два пользователя могут использовать устройства связи с разными операционными системами и браузеры от разных производителей.

Веб-служба отслеживает качество обслуживания (в первую очередь качество аудио и видео), которое получают конечные пользователи.

2.3.4. Simple Video Communication Service: Global Service Provider
2.3.4. Простой сервис видеосвязи: глобальный поставщик услуг
2.3.4.1. Description
2.3.4.1. Описание
This use case is almost identical to the Simple Video Communication Service use case (Section 2.3.1). What is added is that the service provider is operating over large geographical areas (or even globally). Assuming that the Interactive Connectivity Establishment (ICE) mechanism [RFC5245] will be used, this means that the service provider would like to be able to provide several Session Traversal Utilities for NAT (STUN) and Traversal Using Relay NAT (TURN) servers (via the app) to the browser; selection of which one(s) to use is part of the ICE processing. Other reasons for wanting to provide several STUN and TURN servers include support for IPv4 and IPv6, load balancing, and redundancy.
Этот сценарий использования почти идентичен сценарию «Простой сервис видеосвязи» (раздел 2.3.1). Добавляется то, что поставщик услуг работает на больших географических территориях (или даже глобально). Если предположить, что будет использоваться механизм Interactive Connectivity Establishment (ICE) [RFC5245], это означает, что поставщик услуг хотел бы предоставлять браузеру несколько серверов Session Traversal Utilities for NAT (STUN) и Traversal Using Relay NAT (TURN) (через приложение); выбор того, какие из них использовать, является частью обработки ICE. Другие причины, по которым хотелось бы предоставлять несколько серверов STUN и TURN, включают поддержку IPv4 и IPv6, балансировку нагрузки и резервирование.
Note that ICE support being mandatory does not preclude a WebRTC endpoint from supporting more traversal mechanisms than ICE using STUN and TURN.

2.4.3. Video Conferencing System with Central Server
2.4.3. Система видеоконференций с центральным сервером
2.4.3.1. Description
2.4.3.1. Описание
An organization uses a video communication system that supports the establishment of multiparty video sessions using a central conference server.
Организация использует систему видеосвязи, поддерживающую установление многосторонних видеосеансов с использованием центрального сервера конференций.
The browser of each participant sends an audio stream (type in terms of mono, stereo, 5.1 -- depending on the equipment of the participant) to the central server. The central server mixes the audio streams (and can in the mixing process naturally add effects such as spatialization) and sends towards each participant a mixed audio stream that is played to the user.
Браузер каждого участника отправляет на центральный сервер аудиопоток (тип в смысле моно, стерео, 5.1 — в зависимости от оборудования участника). Центральный сервер смешивает аудиопотоки (и в процессе смешивания может, естественно, добавлять такие эффекты, как пространственная локализация) и отправляет каждому участнику смешанный аудиопоток, который воспроизводится пользователю.
The browser of each participant sends video towards the server. For each participant, one high-resolution video is displayed in a large window, while a number of low-resolution videos are displayed in smaller windows. The server selects what video streams to be forwarded as main and thumbnail videos, respectively, based on speech activity. As the video streams to display can change quite frequently (as the conversation flows), it is important that the delay from when a video stream is selected for display until the video can be displayed is short.
Браузер каждого участника отправляет видео на сервер. Для каждого участника одно видео с высоким разрешением отображается в большом окне, а ряд видео с низким разрешением отображается в меньших окнах. Сервер выбирает, какие видеопотоки пересылать в качестве основного видео и видео-миниатюр соответственно, на основе речевой активности. Поскольку видеопотоки для отображения могут меняться довольно часто (по мере течения разговора), важно, чтобы задержка от выбора видеопотока для отображения до возможности его отображения была малой.
All participants are authenticated by the central server and authorized to connect to the central server. The participants are identified to each other by the central server, and the participants do not have access to each others' credentials such as email addresses or login IDs.
Все участники аутентифицируются центральным сервером и получают полномочия на подключение к нему. Участники идентифицируются друг для друга центральным сервером, и участники не имеют доступа к учётным данным друг друга, таким как адреса электронной почты или идентификаторы входа.
Note: This use case adds requirements on support for fast stream switches (F16). There exist several solutions that enable the server to forward one high-resolution and several low-resolution video streams: a) each browser could send a high-resolution, but scalable stream, and the server could send just the base layer for the low- resolution streams, b) each browser could in a simulcast fashion send one high-resolution and one low-resolution stream, and the server just selects, or c) each browser sends just a high-resolution stream, the server transcodes into low-resolution streams as required.
Примечание. Этот сценарий добавляет требования к поддержке быстрого переключения медиапотоков (F16). Существует несколько решений, позволяющих серверу пересылать один видеопоток с высоким разрешением и несколько видеопотоков с низким разрешением: а) каждый браузер может отправлять поток с высоким разрешением, но масштабируемый, и сервер может отправлять только базовый слой для потоков с низким разрешением; б) каждый браузер может в режиме simulcast отправлять один поток с высоким разрешением и один поток с низким разрешением, а сервер просто выбирает; в) каждый браузер отправляет только поток с высоким разрешением, а сервер транскодирует его в потоки с низким разрешением по мере необходимости.

4. Security Considerations
4. Вопросы безопасности
4.1. Introduction
4.1. Введение
A malicious web application might use the browser to perform Denial- of-Service (DoS) attacks on NAT infrastructure, or on peer devices. For example, a malicious web application might leak TURN credentials to unauthorized parties, allowing them to consume the TURN server's bandwidth. To address this risk, web applications should be prepared to revoke TURN credentials and issue new ones. Also, a malicious web application might silently establish outgoing, and accept incoming, streams on an already established connection.
Вредоносное веб-приложение может использовать браузер для проведения атак типа «отказ в обслуживании» (DoS) на инфраструктуру NAT или на устройства одноранговых участников. Например, вредоносное веб-приложение может раскрыть учётные данные TURN неавторизованным сторонам, позволяя им потреблять пропускную способность TURN-сервера. Для снижения этого риска веб-приложениям следует быть готовыми отзывать учётные данные TURN и выдавать новые. Кроме того, вредоносное веб-приложение может незаметно устанавливать исходящие медиапотоки и принимать входящие по уже установленному соединению.
Based on the identified security risks, this section will describe security considerations for the browser and web application.
Исходя из выявленных рисков безопасности, в этом разделе описываются вопросы безопасности для браузера и веб-приложения.
4.2. Browser Considerations
4.2. Соображения относительно браузера
The browser is expected to provide mechanisms for getting user consent to use device resources such as camera and microphone.
Ожидается, что браузер предоставит механизмы получения согласия пользователя на использование ресурсов устройства, таких как камера и микрофон.
The browser is expected to provide mechanisms for informing the user that device resources such as camera and microphone are in use ("hot").
Ожидается, что браузер предоставит механизмы информирования пользователя о том, что ресурсы устройства, такие как камера и микрофон, используются («горячи»).
The browser must provide mechanisms for users to revise and even completely revoke consent to use device resources such as camera and microphone.
Браузер должен предоставлять механизмы, позволяющие пользователям пересматривать и даже полностью отзывать согласие на использование ресурсов устройства, таких как камера и микрофон.
The browser is expected to provide mechanisms for getting user consent to use the screen (or a certain part of it) or what a certain application displays on the screen as source for streams.
Ожидается, что браузер предоставит механизмы получения согласия пользователя на использование экрана (или определённой его части) либо того, что отображает определённое приложение на экране, в качестве источника медиапотоков.
The browser is expected to provide mechanisms for informing the user that the screen, part thereof, or an application is serving as a stream source ("hot").
Ожидается, что браузер предоставит механизмы информирования пользователя о том, что экран, его часть или приложение служит источником медиапотока («горячо»).
The browser must provide mechanisms for users to revise and even completely revoke consent to use the screen, part thereof, or an application as a stream source.
Браузер должен предоставлять механизмы, позволяющие пользователям пересматривать и даже полностью отзывать согласие на использование экрана, его части или приложения в качестве источника медиапотока.
The browser is expected to provide mechanisms in order to assure that streams are the ones the recipient intended to receive.
Ожидается, что браузер предоставит механизмы, гарантирующие, что медиапотоки являются именно теми, которые получатель намеревался получить.
The browser is expected to provide mechanisms that allow the users to verify that the streams received have not be manipulated (F12).
Ожидается, что браузер предоставит механизмы, позволяющие пользователям проверить, что полученные медиапотоки не были изменены (F12).
The browser needs to ensure that media is not sent, and that received media is not rendered, until the associated stream establishment and handshake procedures with the remote peer have been successfully finished.
Браузер должен обеспечивать, чтобы медиа не отправлялись и принимаемые медиа не отображались до тех пор, пока связанные с ними процедуры установления медиапотока и рукопожатия с удалённым одноранговым участником не будут успешно завершены.
The browser needs to ensure that the stream negotiation procedures are not seen as DoS by other entities.
Браузер должен обеспечивать, чтобы процедуры согласования медиапотока не рассматривались другими субъектами как DoS.
4.3. Web Application Considerations
4.3. Соображения относительно веб-приложения
The web application is expected to ensure user consent in sending and receiving media streams.
Ожидается, что веб-приложение обеспечит согласие пользователя на отправку и приём медиапотоков.
