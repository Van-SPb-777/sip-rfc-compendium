Abstract
Аннотация
A Uniform Resource Identifier (URI) is a compact string of characters for identifying an abstract or physical resource. This document defines the generic syntax of URI, including both absolute and relative forms, and guidelines for their use; it revises and replaces the generic definitions in RFC 1738 and RFC 1808.
Универсальный идентификатор ресурса (URI) — это компактная строка символов для идентификации абстрактного или физического ресурса. Настоящий документ определяет общий синтаксис URI и правила разбора URI-ссылок и их компонентов. В настоящем документе описываются как абсолютные, так и относительные URI и определяется, как относительная форма URI может быть объединена с базовым URI для получения абсолютной формы.
This document defines a grammar that is a superset of all valid URI, such that an implementation can parse the common components of a URI reference without knowing the scheme-specific requirements of every possible identifier type. This document does not define a generative grammar for URI; that task will be performed by the individual specifications of each URI scheme.
Настоящий документ определяет грамматику, являющуюся надмножеством всех допустимых URI, так что реализация может разобрать общие компоненты синтаксиса URI, не завися от схемы. Грамматика не описывает семантику схем, но предоставляет механизмы для описания схем, которые семантика схем может использовать.
1. Introduction
1. Введение
Uniform Resource Identifiers (URI) provide a simple and extensible means for identifying a resource. This specification of URI syntax and semantics is derived from concepts introduced by the World Wide Web global information initiative, whose use of such objects dates from 1990 and is described in "Universal Resource Identifiers in WWW" [RFC1630]. The specification of URI is designed to meet the recommendations laid out in "Functional Recommendations for Internet Resource Locators" [RFC1736] and "Functional Requirements for Uniform Resource Names" [RFC1737].
Универсальные идентификаторы ресурсов (Uniform Resource Identifiers, URI) предоставляют простое и расширяемое средство идентификации ресурса. Данная спецификация синтаксиса и семантики URI выведена из понятий, введённых глобальной информационной инициативой Всемирной паутины, использование таких объектов в которой датируется 1990 годом и описано в «Universal Resource Identifiers in WWW» [RFC1630]. Спецификация URI разработана для удовлетворения требований, предъявляемых разработана для удовлетворения требований, предъявляемых в «Functional Recommendations for Internet Resource Locators» [RFC1736] и «Functional Requirements for Uniform Resource Names» [RFC1737].
This document updates and merges "Uniform Resource Locators" [RFC1738] and "Relative Uniform Resource Locators" [RFC1808] in order to define a single, generic syntax for all URI. It excludes those portions of RFC 1738 that defined the specific syntax of individual URL schemes; those portions will be updated as separate documents, as will the process for registration of new URI schemes. This document does not discuss the issues and recommendation for dealing with characters outside of the US-ASCII character set [ASCII]; those recommendations are discussed in a separate document.
Настоящий документ обновляет и объединяет «Uniform Resource Locators» [RFC1738] и «Relative Uniform Resource Locators» [RFC1808], чтобы определить единый общий синтаксис для всех URI. Он исключает те части RFC 1738, которые определяли конкретный синтаксис отдельных схем URL; эти части будут обновлены отдельными документами, как и процедура регистрации новых схем URI. В настоящем документе не рассматриваются вопросы и рекомендации по работе с символами за пределами набора символов US-ASCII [ASCII]; эти рекомендации обсуждаются в отдельном документе.

1.1. Overview of URI
1.1. Обзор URI
URI are characterized by the following definitions:
URI характеризуются следующими определениями:
Uniform
Единообразие (Uniform)
Uniformity provides several benefits: it allows different types of resource identifiers to be used in the same context, even when the mechanisms used to access those resources may differ; it allows uniform semantic interpretation of common syntactic conventions across different types of resource identifiers; it allows introduction of new types of resource identifiers without interfering with the way that existing identifiers are used; and, it allows the identifiers to be reused in many different contexts, thus permitting new applications or protocols to leverage a pre-existing, large, and widely-used set of resource identifiers.
— единообразие даёт несколько преимуществ: оно позволяет использовать различные типы идентификаторов ресурсов в одном контексте, даже если механизмы доступа к этим ресурсам могут различаться; оно позволяет единообразно семантически интерпретировать общие синтаксические соглашения для различных типов идентификаторов ресурсов; оно позволяет вводить новые типы идентификаторов ресурсов, не мешая использованию существующих идентификаторов; и оно позволяет повторно использовать идентификаторы во многих различных контекстах, тем самым позволяя новым приложениям или протоколам опираться на уже существующий, большой и широко используемый набор идентификаторов ресурсов.
Resource A resource can be anything that has identity. Familiar examples include an electronic document, an image, a service (e.g., "today's weather report for Los Angeles"), and a collection of other resources. Not all resources are network "retrievable"; e.g., human beings, corporations, and bound books in a library can also be considered resources. The resource is the conceptual mapping to an entity or set of entities, not necessarily the entity which corresponds to that mapping at any particular instance in time.
Ресурс (Resource) — ресурс может быть чем угодно, что имеет идентичность. Знакомые примеры включают электронный документ, изображение, службу (например, «прогноз погоды в Лос-Анджелесе на сегодня») и совокупность других ресурсов. Не все ресурсы являются сетевыми «извлекаемыми»; например, люди, корпорации и печатные книги в библиотеке также могут считаться ресурсами. Ресурс — это концептуальное отображение на сущность или набор сущностей, не обязательно сущность, которая соответствует этому отображению в какой-либо конкретный момент времени.
Thus, a resource can remain constant even when its content---the entities to which it currently corresponds---changes over time, provided that the conceptual mapping is not changed in the process.
Таким образом, ресурс может оставаться неизменным, даже когда его содержимое — сущности, которым он в данный момент соответствует, — меняется со временем, при условии, что концептуальное отображение в этом процессе не меняется.
Identifier An identifier is an object that can act as a reference to something that has identity. In the case of URI, the object is a sequence of characters with a restricted syntax.
Идентификатор. Идентификатор — это объект, который может действовать как ссылка на что-то, обладающее идентичностью. В случае URI этим объектом является последовательность символов с ограниченным синтаксисом.
Having identified a resource, a system may perform a variety of operations on the resource, as might be characterized by such words as `access', `update', `replace', or `find attributes'.
Идентифицировав ресурс, система может выполнять над ним разнообразные операции, которые можно охарактеризовать такими словами, как «доступ», «обновление», «замена» или «поиск атрибутов».
1.2. URI, URL, and URN
1.2. URI, URL и URN
A URI can be further classified as a locator, a name, or both. The term "Uniform Resource Locator" (URL) refers to the subset of URI that identify resources via a representation of their primary access mechanism (e.g., their network "location"), rather than identifying the resource by name or by some other attribute(s) of that resource. The term "Uniform Resource Name" (URN) refers to the subset of URI that are required to remain globally unique and persistent even when the resource ceases to exist or becomes unavailable.
URI может быть далее классифицирован как локатор, имя или и то и другое. Термин «универсальный локатор ресурсов» (Uniform Resource Locator, URL) относится к подмножеству URI, которые идентифицируют ресурсы через представление их основного механизма доступа (например, их сетевого «местоположения»), а не путём идентификации ресурса по имени или какому-либо иному его атрибуту. Термин «универсальное имя ресурса» (Uniform Resource Name, URN) относится к подмножеству URI, которые должны оставаться глобально уникальными и постоянными даже тогда, когда ресурс перестаёт существовать или становится недоступным.
The URI scheme (Section 3.1) defines the namespace of the URI, and thus may further restrict the syntax and semantics of identifiers using that scheme. This specification defines those elements of the URI syntax that are either required of all URI schemes or are common to many URI schemes. It thus defines the syntax and semantics that are needed to implement a scheme-independent parsing mechanism for URI references, such that the scheme-dependent handling of a URI can be postponed until the scheme-dependent semantics are needed. We use the term URL below when describing syntax or semantics that only apply to locators.
Схема URI (раздел 3.1) определяет пространство имён URI и, таким образом, может дополнительно ограничивать синтаксис и семантику идентификаторов, использующих эту схему. Настоящая спецификация определяет те элементы синтаксиса URI, которые либо требуются для всех схем URI, либо являются общими для многих схем URI. Тем самым она определяет синтаксис и семантику, необходимые для реализации механизма разбора ссылок URI, не зависящего от схемы, так что обработка URI, зависящая от схемы, может быть отложена до момента, когда потребуется семантика, зависящая от схемы. Ниже мы используем термин URL при описании синтаксиса или семантики, которые применимы только к локаторам.
Although many URL schemes are named after protocols, this does not imply that the only way to access the URL's resource is via the named protocol. Gateways, proxies, caches, and name resolution services might be used to access some resources, independent of the protocol of their origin, and the resolution of some URL may require the use of more than one protocol (e.g., both DNS and HTTP are typically used to access an "http" URL's resource when it can't be found in a local cache). A URN differs from a URL in that it's primary purpose is persistent labeling of a resource with an identifier. That identifier is drawn from one of a set of defined namespaces, each of which has its own set name structure and assignment procedures. The "urn" scheme has been reserved to establish the requirements for a standardized URN namespace, as defined in "URN Syntax" [RFC2141] and its related specifications.
Хотя многие схемы URL названы по именам протоколов, это не означает, что единственный способ доступа к ресурсу URL — через названный протокол. Шлюзы, прокси, кэши и службы разрешения имён могут использоваться для доступа к некоторым ресурсам независимо от протокола их происхождения, и разрешение некоторых URL может требовать использования более одного протокола (например, обычно нужны и DNS, и HTTP). URN отличается от URL тем, что его основное назначение — постоянная маркировка ресурса идентификатором. Этот идентификатор берётся из одного из набора определённых пространств имён, каждое из которых имеет собственную структуру имён и процедуры назначения. Схема «urn» зарезервирована для установления требований к стандартизованному пространству имён URN, как определено в «URN Syntax» [RFC2141] и связанных с ней спецификациях.
Most of the examples in this specification demonstrate URL, since they allow the most varied use of the syntax and often have a hierarchical namespace. A parser of the URI syntax is capable of parsing both URL and URN references as a generic URI; once the scheme is determined, the scheme-specific parsing can be performed on the generic URI components. In other words, the URI syntax is a superset of the syntax of all URI schemes.
Большинство примеров в настоящей спецификации демонстрируют URL, поскольку они допускают наиболее разнообразное использование синтаксиса и часто имеют иерархическое пространство имён. Анализатор синтаксиса URI способен разбирать как ссылки URL, так и ссылки URN как обобщённые URI; как только схема определена, разбор, специфичный для схемы, может быть выполнен над общими компонентами URI. Иными словами, синтаксис URI является надмножеством синтаксиса всех схем URI.

1.4. Hierarchical URI and Relative Forms
1.4. Иерархические URI и относительные формы
An absolute identifier refers to a resource independent of the context in which the identifier is used. In contrast, a relative identifier refers to a resource by describing the difference within a hierarchical namespace between the current context and an absolute identifier of the resource. Some URI schemes support a hierarchical naming system, where the hierarchy of the name is denoted by a "/" delimiter separating the components in the scheme. This document defines a scheme-independent `relative' form of URI reference that can be used in conjunction with a `base' URI (of a hierarchical scheme) to produce another URI. The syntax of hierarchical URI is described in Section 3; the relative URI calculation is described in Section 5.
Абсолютный идентификатор ссылается на ресурс независимо от контекста, в котором идентификатор используется. В противоположность этому относительный идентификатор ссылается на ресурс путём описания различия внутри иерархического пространства имён между текущим контекстом и абсолютным идентификатором ресурса. Некоторые схемы URI поддерживают иерархическую систему имён, где иерархия имени обозначается разделителем «/», разделяющим компоненты в схеме. Настоящий документ определяет независимую от схемы «относительную» форму ссылки URI, которая может использоваться вместе с «базовым» URI (иерархической схемы) для получения другого URI. Синтаксис иерархического URI описан в разделе 3; относительные вычисления URI описаны в разделе 5.
1.5. URI Transcribability
1.5. Возможность переписывания URI
The URI syntax was designed with global transcribability as one of its main concerns. A URI is a sequence of characters from a very limited set, i.e. the letters of the basic Latin alphabet, digits, and a few special characters. A URI may be represented in a variety of ways: e.g., ink on paper, pixels on a screen, or a sequence of octets in a coded character set. The interpretation of a URI depends only on the characters used and not how those characters are represented in a network protocol.
Синтаксис URI разрабатывался с учётом глобальной возможности переписывания как одной из главных задач. URI — это последовательность символов из весьма ограниченного набора, а именно букв базового латинского алфавита, цифр и нескольких специальных символов. URI может быть представлен различными способами: например, чернилами на бумаге, пикселями на экране или последовательностью октетов в кодированном наборе символов. Интерпретация URI зависит только от используемых символов, а не от того, как эти символы представлены в сетевом протоколе.
The goal of transcribability can be described by a simple scenario. Imagine two colleagues, Sam and Kim, sitting in a pub at an international conference and exchanging research ideas. Sam asks Kim for a location to get more information, so Kim writes the URI for the research site on a napkin. Upon returning home, Sam takes out the napkin and types the URI into a computer, which then retrieves the information to which Kim referred.
Цель переписываемости можно описать простым сценарием. Вообразите двух коллег, Сэма и Кима, сидящих в пабе на международной конференции и обменивающихся исследовательскими идеями. Сэм просит Кима указать место, где можно получить больше информации, и Ким пишет URI исследовательского сайта на салфетке. Вернувшись домой, Сэм достаёт салфетку и набирает URI в компьютер, который затем извлекает информацию, на которую сослалась Kim.
There are several design concerns revealed by the scenario:
Сценарий выявляет несколько проблем проектирования:
o A URI is a sequence of characters, which is not always represented as a sequence of octets.
o URI — это последовательность символов, которая не всегда представляется последовательностью октетов.
o A URI may be transcribed from a non-network source, and thus should consist of characters that are most likely to be able to be typed into a computer, within the constraints imposed by keyboards (and related input devices) across languages and locales.
o URI может быть переписан из ненесетевого источника и потому должен состоять из символов, которые с наибольшей вероятностью можно набрать на компьютере с учётом ограничений, накладываемых клавиатурами (и связанными устройствами ввода) в разных языках и локалях.
o A URI often needs to be remembered by people, and it is easier for people to remember a URI when it consists of meaningful components.
o URI часто нужно запоминать людям, и людям легче запомнить URI, когда он состоит из осмысленных компонентов.
These design concerns are not always in alignment. For example, it is often the case that the most meaningful name for a URI component would require characters that cannot be typed into some systems. The ability to transcribe the resource identifier from one medium to another was considered more important than having its URI consist of the most meaningful of components. In local and regional contexts and with improving technology, users might benefit from being able to use a wider range of characters; such use is not defined in this document.
Эти проблемы проектирования не всегда согласуются между собой. Например, часто бывает, что наиболее осмысленное имя для компонента URI требовало бы символов, которые нельзя набрать в некоторых системах. Возможность переписать идентификатор ресурса с одного носителя на другой считалась более важной, нежели то, чтобы URI состоял из наиболее осмысленных компонентов. В локальных и региональных контекстах и с совершенствованием технологий пользователи могли бы извлечь выгоду из возможности использовать более широкий диапазон символов; такое использование в настоящем документе не определено.

2. URI Characters and Escape Sequences
2. Символы URI и escape-последовательности
URI consist of a restricted set of characters, primarily chosen to aid transcribability and usability both in computer systems and in non-computer communications. Characters used conventionally as delimiters around URI were excluded. The restricted set of characters consists of digits, letters, and a few graphic symbols were chosen from those common to most of the character encodings and input facilities available to Internet users.
URI состоит из ограниченного набора символов, выбранных в первую очередь для облегчения переписывания и удобства использования как в компьютерных системах, так и в некомпьютерных коммуникациях. Символы, традиционно используемые как разделители вокруг URI, были исключены. Ограниченный набор символов состоит из цифр, букв и нескольких графических символов, выбранных из тех, что общи для большинства кодировок символов и средств ввода, доступных пользователям Интернета.

Within a URI, characters are either used as delimiters, or to represent strings of data (octets) within the delimited portions. Octets are either represented directly by a character (using the US- ASCII character for that octet [ASCII]) or by an escape encoding. This representation is elaborated below.
Внутри URI символы используются либо как разделители, либо для представления строк данных (октетов) внутри ограниченных разделителями частей. Октеты представляются либо непосредственно символом (с использованием символа US-ASCII для этого октета [ASCII]), либо с помощью escape-кодирования. Это представление подробно описано ниже.

A URI is represented as a sequence of characters, not as a sequence of octets. That is because URI might be "transported" by means that are not through a computer network, e.g., printed on paper, read over the radio, etc.
URI представляется как последовательность символов, а не как последовательность октетов. Это потому, что URI может «передаваться» средствами, не связанными с компьютерной сетью, например, будучи напечатанным на бумаге, прочитанным по радио и т. д.
A URI scheme may define a mapping from URI characters to octets; whether this is done depends on the scheme. Commonly, within a delimited component of a URI, a sequence of characters may be used to represent a sequence of octets. For example, the character "a" represents the octet 97 (decimal), while the character sequence "%", "0", "a" represents the octet 10 (decimal). There is a second translation for some resources: the sequence of octets defined by a component of the URI is subsequently used to represent a sequence of characters. A 'charset' defines this mapping. There are many charsets in use in Internet protocols. For example, UTF-8 [UTF-8] defines a mapping from sequences of octets to sequences of characters in the repertoire of ISO 10646.

In the simplest case, the original character sequence contains only characters that are defined in US-ASCII, and the two levels of mapping are simple and easily invertible: each 'original character' is represented as the octet for the US-ASCII code for it, which is, in turn, represented as either the US-ASCII character, or else the "%" escape sequence for that octet.

In general, a character is reserved if the semantics of the URI changes if the character is replaced with its escaped US-ASCII encoding.

2.4. Escape Sequences
2.4. Escape-последовательности
Data must be escaped if it does not have a representation using an unreserved character; this includes data that does not correspond to a printable character of the US-ASCII coded character set, or that corresponds to any US-ASCII character that is disallowed, as explained below.
Данные должны быть экранированы, если они не имеют представления с использованием незарезервированного символа; это включает данные, не соответствующие печатаемому символу кодированного набора символов US-ASCII, либо соответствующие любому символу US-ASCII, который не допускается, как объяснено ниже.
2.4.1. Escaped Encoding

2.4.2. When to Escape and Unescape
2.4.2. Когда экранировать и когда снимать экранирование
A URI is always in an "escaped" form, since escaping or unescaping a completed URI might change its semantics. Normally, the only time escape encodings can safely be made is when the URI is being created from its component parts; each component may have its own set of characters that are reserved, so only the mechanism responsible for generating or interpreting that component can determine whether or not escaping a character will change its semantics. Likewise, a URI must be separated into its components before the escaped characters within those components can be safely decoded.
URI всегда находится в «экранированной» форме, поскольку экранирование или снятие экранирования завершённого URI может изменить его семантику. Обычно единственный момент, когда escape-кодировки могут быть безопасно созданы, — это когда URI формируется из своих составных частей; каждый компонент может иметь собственный набор зарезервированных символов, поэтому только механизм, ответственный неэкранирование символа изменит его семантику. Аналогично URI должен быть разделён на компоненты, прежде чем экранированные символы внутри этих компонентов могут быть безопасно декодированы.
In some cases, data that could be represented by an unreserved character may appear escaped; for example, some of the unreserved "mark" characters are automatically escaped by some systems. If the given URI scheme defines a canonicalization algorithm, then unreserved characters may be unescaped according to that algorithm. For example, "%7e" is sometimes used instead of "~" in an http URL path, but the two are equivalent for an http URL.
В некоторых случаях данные, которые могли бы быть представлены незарезервированным символом, могут оказаться экранированными; например, некоторые из незарезервированных символов «mark» автоматически экранируются некоторыми системами. Если данная схема URI определяет алгоритм канонизации, то незарезервированные символы могут быть неэкранированы согласно этому алгоритму.
Because the percent "%" character always has the reserved purpose of being the escape indicator, it must be escaped as "%25" in order to be used as data within a URI. Implementers should be careful not to escape or unescape the same string more than once, since unescaping an already unescaped string might lead to misinterpreting a percent data character as another escaped character, or vice versa in the case of escaping an already escaped string.
Поскольку символ процента «%» всегда имеет зарезервированное назначение быть индикатором экранирования, он должен быть экранирован как «%25», чтобы использоваться как данные внутри URI. Разработчикам следует быть осторожными, чтобы не экранировать или не снимать экранирование одной и той же строки более одного раза, поскольку снятие экранирования с уже неэкранированной строки может привести к неверной интерпретации процентного символа данных как другого экранированного символа, или наоборот — при экранировании уже экранированной строки.

Синтаксис URI зависит от схемы. В общем случае абсолютные URI записываются следующим образом:
<scheme>:<scheme-specific-part>
<scheme>:<scheme-specific-part>
An absolute URI contains the name of the scheme being used (<scheme>) followed by a colon (":") and then a string (the <scheme-specific- part>) whose interpretation depends on the scheme.
Абсолютный URI содержит имя используемой схемы (<scheme>), за которым следует двоеточие («:»), а затем строка (the <scheme-specific-part>), интерпретация которой зависит от схемы.
The URI syntax does not require that the scheme-specific-part have any general structure or set of semantics which is common among all URI. However, a subset of URI do share a common syntax for representing hierarchical relationships within the namespace. This "generic URI" syntax consists of a sequence of four main components:
Синтаксис URI не требует, чтобы специфичная для схемы часть имела какую-либо общую структуру или набор семантики, общие для всех URI. Однако подмножество URI разделяет общий синтаксис для представления иерархических отношений внутри пространства имён. Этот синтаксис «общего URI» состоит из последовательности четырёх основных компонентов:
<scheme>://<authority><path>?<query>
<scheme>://<authority><path>?<query>
each of which, except <scheme>, may be absent from a particular URI. For example, some URI schemes do not allow an <authority> component, and others do not use a <query> component.
каждый из которых, кроме <scheme>, может отсутствовать в конкретном URI. Например, некоторые схемы URI не допускают компонент <authority>, а другие не используют компонент <query>.
absoluteURI = scheme ":" ( hier_part | opaque_part )
absoluteURI = scheme «:» ( hier_part | opaque_part )
URI that are hierarchical in nature use the slash "/" character for separating hierarchical components. For some file systems, a "/" character (used to denote the hierarchical structure of a URI) is the delimiter used to construct a file name hierarchy, and thus the URI path will look similar to a file pathname. This does NOT imply that the resource is a file or that the URI maps to an actual filesystem pathname.
URI, иерархические по своей природе, используют символ косой черты «/» для разделения иерархических компонентов. Для некоторых файловых систем символ «/» (используемый для обозначения иерархической структуры URI) является разделителем, применяемым для построения иерархии имён файлов, и потому путь URI будет выглядеть похоже на путь файла. Этот разделитель НЕ означает, что ресурс является файлом или что URI соответствует реальному пути в файловой системе.
hier_part = ( net_path | abs_path ) [ "?" query ] net_path = "//" authority [ abs_path ] abs_path = "/" path_segments
hier_part = ( net_path | abs_path ) [ "?" query ] net_path = "//" authority [ abs_path ] abs_path = "/" path_segments
URI that do not make use of the slash "/" character for separating hierarchical components are considered opaque by the generic URI parser.
URI, не использующие символ косой черты «/» для разделения иерархических компонентов, считаются непрозрачными (opaque) общим анализатором URI.
opaque_part = uric_no_slash *uric
opaque_part = uric_no_slash *uric
uric_no_slash = unreserved | escaped | ";" | "?" | ":" | "@" | "&" | "=" | "+" | "$" | ","
uric_no_slash = unreserved | escaped | «;» | «?» | «:» | «@» | «&» | «=» | «+» | «$» | «,»
We use the term <path> to refer to both the <abs_path> and <opaque_part> constructs, since they are mutually exclusive for any given URI and can be parsed as a single component.
Мы используем термин <path> для обозначения как конструкции <abs_path>, так и конструкции <opaque_part>, поскольку они взаимно исключают друг друга для любого заданного URI и могут разбираться как единый компонент.
3.1. Scheme Component
3.1. Компонент схемы
Just as there are many different methods of access to resources, there are a variety of schemes for identifying such resources. The URI syntax consists of a sequence of components separated by reserved characters, with the first component defining the semantics for the remainder of the URI string.
Подобно тому как существуют различные методы доступа к ресурсам, существует и множество схем для идентификации таких ресурсов. Синтаксис URI состоит из последовательности компонентов, разделённых зарезервированными символами, причём первый компонент определяет семантику для остатка строки URI.
Scheme names consist of a sequence of characters beginning with a lower case letter and followed by any combination of lower case letters, digits, plus ("+"), period ("."), or hyphen ("-"). For resiliency, programs interpreting URI should treat upper case letters as equivalent to lower case in scheme names (e.g., allow "HTTP" as well as "http").
Имена схем состоят из последовательности символов, начинающейся со строчной буквы и продолжающейся любой комбинацией строчных букв, цифр, знака плюс («+»), точки («.») или дефиса («-»). Для устойчивости программы, интерпретирующие URI, должны трактовать заглавные буквы как эквивалентные строчным в именах схем (например, допускать «HTTP» наряду с «http»).
scheme = alpha *( alpha | digit | "+" | "-" | "." )
scheme = alpha *( alpha | digit | "+" | "-" | "." )
Relative URI references are distinguished from absolute URI in that they do not begin with a scheme name. Instead, the scheme is inherited from the base URI, as described in Section 5.2.
Относительные ссылки URI отличаются от абсолютных URI тем, что они не начинаются с имени схемы. Вместо этого схема наследуется от базового URI, как описано в разделе 5.2.
3.2. Authority Component
3.2. Компонент authority
Many URI schemes include a top hierarchical element for a naming authority, such that the namespace defined by the remainder of the URI is governed by that authority. This authority component is typically defined by an Internet-based server or a scheme-specific registry of naming authorities.
Многие схемы URI включают верхний иерархический элемент для органа именования, такой что пространство имён, определяемое остатком URI, управляется этим органом. Этот компонент authority обычно определяется интернет-сервером или специфичным для схемы реестром органов именования.
authority = server | reg_name
authority = server | reg_name
The authority component is preceded by a double slash "//" and is terminated by the next slash "/", question-mark "?", or by the end of the URI. Within the authority component, the characters ";", ":", "@", "?", and "/" are reserved. An authority component is not required for a URI scheme to make use of relative references. A base URI without an authority component implies that any relative reference will also be without an authority component.
Компоненту authority предшествует двойная косая черта «//», и он завершается следующей косой чертой «/», знаком вопроса «?» или концом URI. Внутри компонента authority символы «;», «:», «@», «?» и «/» зарезервированы. Компонент authority не требуется для того, чтобы схема URI могла использовать относительные ссылки. Базовый URI без компонента authority подразумевает, что любая относительная ссылка также будет без компонента authority.
3.2.1. Registry-based Naming Authority
3.2.1. Орган именования на основе реестра
The structure of a registry-based naming authority is specific to the URI scheme, but constrained to the allowed characters for an authority component.
Структура органа именования на основе реестра специфична для схемы URI, но ограничена допустимыми символами для компонента authority.
reg_name = 1*( unreserved | escaped | "$" | "," | ";" | ":" | "@" | "&" | "=" | "+" )
reg_name = 1*( unreserved | escaped | «$» | «,» | «;» | «:» | «@» | «&» | «=» | «+» )
3.2.2. Server-based Naming Authority
3.2.2. Орган именования на основе сервера
URL schemes that involve the direct use of an IP-based protocol to a specified server on the Internet use a common syntax for the server component of the URI's scheme-specific data:
Схемы URL, предполагающие прямое использование протокола на основе IP к указанному серверу в Интернете, используют общий синтаксис для компонента сервера в специфичных для схемы данных URI:
<userinfo>@<host>:<port>
<userinfo>@<host>:<port>
where <userinfo> may consist of a user name and, optionally, scheme- specific information about how to gain authorization to access the server. The parts "<userinfo>@" and ":<port>" may be omitted.
где <userinfo> может состоять из имени пользователя и, необязательно, специфичной для схемы информации о том, как получить авторизацию для доступа к серверу. Части «<userinfo>@» и «:<port>» могут быть опущены.
server = [ [ userinfo "@" ] hostport ]
server = [ [ userinfo "@" ] hostport ]
The user information, if present, is followed by a commercial at-sign "@".
За информацией о пользователе, если она присутствует, следует коммерческое «at» (@).
userinfo = *( unreserved | escaped | ";" | ":" | "&" | "=" | "+" | "$" | "," )
userinfo = *( unreserved | escaped | ";" | ":" | "&" | "=" | "+" | "$" | "," )
Some URL schemes use the format "user:password" in the userinfo field. This practice is NOT RECOMMENDED, because the passing of authentication information in clear text (such as URI) has proven to be a security risk in almost every case where it has been used.
Некоторые схемы URL используют в поле userinfo формат «пользователь:пароль». Эта практика НЕ РЕКОМЕНДУЕТСЯ, поскольку передача аутентификационной информации в открытом тексте (например, в URI) оказалась риском безопасности почти во всех случаях, где она применялась.
The host is a domain name of a network host, or its IPv4 address as a set of four decimal digit groups separated by ".". Literal IPv6 addresses are not supported.
Хост — это доменное имя сетевого хоста либо его адрес IPv4 в виде набора из четырёх групп десятичных цифр, разделённых точками. Литеральные адреса IPv6 не поддерживаются.
hostport = host [ ":" port ] host = hostname | IPv4address hostname = *( domainlabel "." ) toplabel [ "." ] domainlabel = alphanum | alphanum *( alphanum | "-" ) alphanum toplabel = alpha | alpha *( alphanum | "-" ) alphanum IPv4address = 1*digit "." 1*digit "." 1*digit "." 1*digit port = *digit
hostport = host [ ":" port ] host = hostname | IPv4address hostname = *( domainlabel "." ) toplabel [ "." ] domainlabel = alphanum | alphanum *( alphanum | "-" ) alphanum toplabel = alpha | alpha *( alphanum | "-" ) alphanum IPv4address = 1*digit "." 1*digit "." 1*digit "." 1*digit port = *digit
Hostnames take the form described in Section 3 of [RFC1034] and Section 2.1 of [RFC1123]: a sequence of domain labels separated by ".", each domain label starting and ending with an alphanumeric character and possibly also containing "-" characters. The rightmost domain label of a fully qualified domain name will never start with a digit, thus syntactically distinguishing domain names from IPv4 addresses, and may be followed by a single "." if it is necessary to distinguish between the complete domain name and any local domain. To actually be "Uniform" as a resource locator, a URL hostname should be a fully qualified domain name. In practice, however, the host component may be a local domain literal.
Имена хостов имеют форму, описанную в разделе 3 [RFC1034] и разделе 2.1 [RFC1123]: последовательность доменных меток, разделённых точками, причём каждая доменная метка начинается и заканчивается буквенно-цифровым символом и может также содержать символы «-». Самая правая доменная метка полностью определённого доменного имени никогда не начинается с цифры, что синтаксически отличает доменные имена от адресов IPv4, и может сопровождаться одиночной точкой, если необходимо отличить полное доменное имя от любого локального домена. Чтобы действительно быть «универсальным» в качестве локатора ресурсов, имя хоста URL должно быть полностью определённым доменным именем. Однако на практике компонент хоста может быть литералом локального домена.
Note: A suitable representation for including a literal IPv6 address as the host part of a URL is desired, but has not yet been determined or implemented in practice.
Примечание. Желательно подходящее представление для включения литерального адреса IPv6 в качестве части имени хоста URL, но оно ещё не определено и не реализовано на практике.
The port is the network port number for the server. Most schemes designate protocols that have a default port number. Another port number may optionally be supplied, in decimal, separated from the host by a colon. If the port is omitted, the default port number is assumed.
Порт — это номер сетевого порта сервера. Большинство схем назначают протоколы, имеющие номер порта по умолчанию. Другой номер порта может быть необязательно указан в десятичном виде и отделён от хоста двоеточием. Если порт опущен, предполагается номер порта по умолчанию.
3.3. Path Component
3.3. Компонент пути
The path component contains data, specific to the authority (or the scheme if there is no authority component), identifying the resource within the scope of that scheme and authority.
Компонент пути содержит данные, специфичные для органа authority (или для схемы, если компонент authority отсутствует), идентифицирующие ресурс в области действия этой схемы и органа authority.
path = [ abs_path | opaque_part ] path_segments = segment *( "/" segment ) segment = *pchar *( ";" param ) param = *pchar pchar = unreserved | escaped | ":" | "@" | "&" | "=" | "+" | "$" | ","
path = [ abs_path | opaque_part ] path_segments = segment *( "/" segment ) segment = *pchar *( ";" param ) param = *pchar pchar = unreserved | escaped | ":" | "@" | "&" | "=" | "+" | "$" | ","
The path may consist of a sequence of path segments separated by a single slash "/" character. Within a path segment, the characters "/", ";", "=", and "?" are reserved. Each path segment may include a sequence of parameters, indicated by the semicolon ";" character. The parameters are not significant to the parsing of relative references.
Путь может состоять из последовательности сегментов пути, разделённых одиночным символом косой черты «/». Внутри сегмента пути символы «/», «;», «=» и «?» зарезервированы. Каждый сегмент пути может включать последовательность параметров, обозначаемых символом точки с запятой «;». Параметры не имеют значения Параметры не имеют значения для разбора относительных ссылок.
3.4. Query Component
3.4. Компонент запроса
The query component is a string of information to be interpreted by the resource.
Компонент запроса — это строка информации, подлежащая интерпретации ресурсом.
query = *uric
query = *uric
Within a query component, the characters ";", "/", "?", ":", "@", "&", "=", "+", ",", and "$" are reserved.
Внутри компонента запроса символы «;», «/», «?», «:», «@», «&», «=», «+», «,» и «$» зарезервированы.
4. URI References
4. Ссылки URI
The term "URI-reference" is used here to denote the common usage of a resource identifier. A URI reference may be absolute or relative, and may have additional information attached in the form of a fragment identifier. However, "the URI" that results from such a reference includes only the absolute URI after the fragment identifier (if any) is removed and after any relative URI is resolved to its absolute form. Although it is possible to limit the discussion of URI syntax and semantics to that of the absolute result, most usage of URI is within general URI references, and it is impossible to obtain the URI from such a reference without also parsing the fragment and resolving the relative form.
Термин «ссылка URI» (URI-reference) используется здесь для обозначения обычного употребления идентификатора ресурса. Ссылка URI может быть абсолютной или относительной и может иметь дополнительную информацию, присоединённую в форме идентификатора фрагмента. Однако «тот URI», который получается в результате такой ссылки, включает только абсолютный URI после удаления идентификатора фрагмента (если он есть) и после разрешения любого относительного URI в его абсолютную форму. Хотя можно было бы ограничить обсуждение синтаксиса и семантики URI только абсолютным результатом, большинство случаев использования URI приходится на общие ссылки URI, и невозможно получить URI из такой ссылки без одновременного разбора фрагмента и разрешения относительной формы.
URI-reference = [ absoluteURI | relativeURI ] [ "#" fragment ]
URI-reference = [ absoluteURI | relativeURI ] [ «#» fragment ]
The syntax for relative URI is a shortened form of that for absolute URI, where some prefix of the URI is missing and certain path components ("." and "..") have a special meaning when, and only when, interpreting a relative path. The relative URI syntax is defined in Section 5.
Синтаксис относительного URI представляет собой сокращённую форму синтаксиса абсолютного URI, где отсутствует некоторый префикс URI, а некоторые компоненты пути («.» и «..») имеют особое значение тогда и только тогда, когда интерпретируется относительный путь. Синтаксис относительного URI определён в разделе 5.
4.1. Fragment Identifier
4.1. Идентификатор фрагмента
When a URI reference is used to perform a retrieval action on the identified resource, the optional fragment identifier, separated from the URI by a crosshatch ("#") character, consists of additional reference information to be interpreted by the user agent after the retrieval action has been successfully completed. As such, it is not part of a URI, but is often used in conjunction with a URI.
Когда ссылка URI используется для выполнения действия извлечения по идентифицированному ресурсу, необязательный идентификатор фрагмента, отделённый от URI символом решётки («#»), состоит из дополнительной справочной информации, подлежащей интерпретации пользовательским агентом после успешного завершения действия извлечения.
fragment = *uric
fragment = *uric
The semantics of a fragment identifier is a property of the data resulting from a retrieval action, regardless of the type of URI used in the reference. Therefore, the format and interpretation of fragment identifiers is dependent on the media type [RFC2046] of the retrieval result. The character restrictions described in Section 2 for URI also apply to the fragment in a URI-reference. Individual media types may define additional restrictions or structure within the fragment for specifying different types of "partial views" that can be identified within that media type.
Семантика идентификатора фрагмента является свойством данных, полученных в результате действия извлечения, независимо от типа URI, использованного в ссылке. Поэтому формат и интерпретация идентификаторов фрагментов зависят от типа носителя [RFC2046] результата извлечения. Описанные в разделе 2 ограничения на символы для URI также применимы к фрагменту в ссылке URI. Отдельные типы носителя могут определять дополнительные ограничения или структуру внутри фрагмента для задания различных типов «частичных представлений», которые могут быть идентифицированы в рамках этого типа носителя.
A fragment identifier is only meaningful when a URI reference is intended for retrieval and the result of that retrieval is a document for which the identified fragment is consistently defined.
Идентификатор фрагмента имеет смысл только тогда, когда ссылка URI предназначена для извлечения и результатом этого извлечения является документ, для которого идентифицированный фрагмент определён согласованно.
4.2. Same-document References
4.2. Ссылки на тот же документ
A URI reference that does not contain a URI is a reference to the current document. In other words, an empty URI reference within a document is interpreted as a reference to the start of that document, and a reference containing only a fragment identifier is a reference to the identified fragment of that document. Traversal of such a reference should not result in an additional retrieval action. However, if the URI reference occurs in a context that is always intended to result in a new request, as in the case of HTML's FORM element, then an empty URI reference represents the base URI of the current document and should be replaced by that URI when transformed into a request.
Ссылка URI, не содержащая URI, является ссылкой на текущий документ. Иными словами, пустая ссылка URI внутри документа интерпретируется как ссылка на начало этого документа, а ссылка, содержащая только идентификатор фрагмента, является ссылкой на идентифицированный фрагмент этого документа. Переход по такой ссылке не должен приводить к дополнительному действию извлечения. Однако если ссылка URI встречается в контексте, который всегда предназначен для порождения нового запроса, как в случае элемента FORM в HTML, то пустая ссылка URI представляет базовый URI текущего документа и должна быть заменена этим URI при преобразовании в запрос.
4.3. Parsing a URI Reference
4.3. Разбор ссылки URI
A URI reference is typically parsed according to the four main components and fragment identifier in order to determine what components are present and whether the reference is relative or absolute. The individual components are then parsed for their subparts and, if not opaque, to verify their validity.
Ссылка URI обычно разбирается в соответствии с четырьмя основными компонентами и идентификатором фрагмента, чтобы определить, какие компоненты присутствуют и является ли ссылка относительной или абсолютной. Затем отдельные компоненты разбираются на их составные части и, если компонент не является непрозрачным, проверяются на предмет допустимости.
Although the BNF defines what is allowed in each component, it is ambiguous in terms of differentiating between an authority component and a path component that begins with two slash characters. The greedy algorithm is used for disambiguation: the left-most matching rule soaks up as much of the URI reference string as it is capable of matching. In other words, the authority component wins.
Хотя BNF определяет, что допускается в каждом компоненте, она неоднозначна в отношении различения компонента authority и компонента пути, начинающегося с двух символов косой черты. Для устранения неоднозначности используется жадный алгоритм: самое левое подходящее правило поглощает как можно большую часть строки ссылки URI.
Readers familiar with regular expressions should see Appendix B for a concrete parsing example and test oracle.

5. Relative URI References
5. Относительные ссылки URI
It is often the case that a group or "tree" of documents has been constructed to serve a common purpose; the vast majority of URI in these documents point to resources within the tree rather than outside of it. Similarly, documents located at a particular site are much more likely to refer to other resources at that site than to resources at remote sites.
Часто бывает, что группа или «дерево» документов создана для общей цели; подавляющее большинство URI в этих документах указывают на ресурсы внутри дерева, а не вне его. Аналогично документы, расположенные на конкретном сайте, гораздо чаще ссылаются на другие ресурсы на этом же сайте, нежели на ресурсы на удалённых сайтах.
Relative addressing of URI allows document trees to be partially independent of their location and access scheme. For instance, it is possible for a single set of hypertext documents to be simultaneously accessible and traversable via each of the "file", "http", and "ftp" schemes if the documents refer to each other using relative URI. Furthermore, such document trees can be moved, as a whole, without changing any of the relative references. Experience within the WWW has demonstrated that the ability to perform relative referencing is necessary for the long-term usability of embedded URI.
Относительная адресация URI позволяет деревьям документов быть частично независимыми от их местоположения и схемы доступа. Например, возможно, чтобы единый набор гипертекстовых документов был одновременно доступен и проходим через каждую из схем «file», «http» и «ftp», если документы используют относительные URI. Это также позволяет перемещать дерево документов с одного сайта или с одной машины на другой, не изменяя URI внутри дерева. Аналогично дерево документов может быть продублировано на разных машинах с использованием различных схем доступа, и при этом внутренние ссылки останутся работоспособными.
The syntax for relative URI takes advantage of the <hier_part> syntax of <absoluteURI> (Section 3) in order to express a reference that is relative to the namespace of another hierarchical URI.
Синтаксис относительного URI использует синтаксис <hier_part> из <absoluteURI> (раздел 3), чтобы выразить ссылку, относительную к пространству имён другого иерархического URI.
relativeURI = ( net_path | abs_path | rel_path ) [ "?" query ]
relativeURI = ( net_path | abs_path | rel_path ) [ «?» query ]
A relative reference beginning with two slash characters is termed a network-path reference, as defined by <net_path> in Section 3. Such references are rarely used.
Относительная ссылка, начинающаяся с двух символов косой черты, называется ссылкой сетевого пути, как определено <net_path> в разделе 3. Такие ссылки используются редко.
A relative reference beginning with a single slash character is termed an absolute-path reference, as defined by <abs_path> in Section 3.
Относительная ссылка, начинающаяся с одиночного символа косой черты, называется ссылкой абсолютного пути, как определено <abs_path> в разделе 3.
A relative reference that does not begin with a scheme name or a slash character is termed a relative-path reference.
Относительная ссылка, которая не начинается с имени схемы или символа косой черты, называется ссылкой относительного пути.
rel_path = rel_segment [ abs_path ] rel_segment = 1*( unreserved | escaped | ";" | "@" | "&" | "=" | "+" | "$" | "," )
rel_path = rel_segment [ abs_path ] rel_segment = 1*( unreserved | escaped | ";" | "@" | "&" | "=" | "+" | "$" | "," )
Within a relative-path reference, the complete path segments "." and ".." have special meanings: "the current hierarchy level" and "the level above this hierarchy level", respectively. Although this is very similar to their use within Unix-based filesystems to indicate directory levels, these path components are only considered special when resolving a relative-path reference to its absolute form (Section 5.2).
Внутри ссылки относительного пути полные сегменты пути «.» и «..» имеют особое значение: «текущий уровень иерархии» и «уровень над этим уровнем иерархии» соответственно. Хотя это очень похоже на их использование в файловых системах на основе Unix для указания уровней каталогов, эти компоненты пути считаются особыми только при разрешении ссылки относительного пути в её абсолютную форму (раздел 5.2).
Authors should be aware that a path segment which contains a colon character cannot be used as the first segment of a relative URI path (e.g., "this:that"), because it would be mistaken for a scheme name. It is therefore necessary to precede such segments with other segments (e.g., "./this:that") in order for them to be referenced as a relative path.
Авторам следует учитывать, что сегмент пути, содержащий символ двоеточия, не может использоваться как первый сегмент пути относительного URI (например, «this:that»), поскольку он был бы ошибочно принят за имя схемы. Поэтому такие сегменты необходимо предварять другими сегментами (например, «./this:that»), чтобы на них можно было ссылаться как на относительный путь.
It is not necessary for all URI within a given scheme to be restricted to the <hier_part> syntax, since the hierarchical properties of that syntax are only necessary when relative URI are used within a particular document. Documents can only make use of relative URI when their base URI fits within the <hier_part> syntax. It is assumed that any document which contains a relative reference will also have a base URI that obeys the syntax. In other words, relative URI cannot be used within a document that has an unsuitable base URI.
Не обязательно, чтобы все URI в данной схеме были ограничены синтаксисом <hier_part>, поскольку иерархические свойства этого синтаксиса нужны только тогда, когда относительные URI используются в конкретном документе. Документы могут использовать относительные URI только тогда, когда их базовый URI вписывается в синтаксис <hier_part>. Это ограничение существует потому, что для разрешения относительного URI требуется иерархическая структура базового URI.
Some URI schemes do not allow a hierarchical syntax matching the <hier_part> syntax, and thus cannot use relative references.
Некоторые схемы URI не допускают иерархического синтаксиса, соответствующего синтаксису <hier_part>, и потому не могут использовать относительные ссылки.
5.1. Establishing a Base URI
5.1. Установление базового URI
The term "relative URI" implies that there exists some absolute "base URI" against which the relative reference is applied. Indeed, the base URI is necessary to define the semantics of any relative URI reference; without it, a relative reference is meaningless. In order for relative URI to be usable within a document, the base URI of that document must be known to the parser.
Термин «относительный URI» подразумевает, что существует некоторый абсолютный «базовый URI», относительно которого применяется относительная ссылка. Действительно, базовый URI необходим для определения семантики любой относительной ссылки URI; без него относительная ссылка бессмысленна. Чтобы относительные URI были пригодны к использованию внутри документа, анализатор должен знать базовый URI этого документа.

5.1.1. Base URI within Document Content
5.1.1. Базовый URI в содержимом документа
Within certain document media types, the base URI of the document can be embedded within the content itself such that it can be readily obtained by a parser. This can be useful for descriptive documents, such as tables of content, which may be transmitted to others through protocols other than their usual retrieval context (e.g., E-Mail or USENET news).
В некоторых типах носителя документов базовый URI документа может быть встроен непосредственно в содержимое так, что его можно легко получить анализатору. Это может быть полезно для описательных документов, таких как оглавления, которые могут передаваться другим через протоколы, отличные от отличные от их обычного контекста извлечения (например, электронной почты или USENET news).

Protocols that do not use the MIME message header syntax, but which do allow some form of tagged metainformation to be included within messages, may define their own syntax for defining the base URI as part of a message.

5.1.2. Base URI from the Encapsulating Entity
5.1.2. Базовый URI из инкапсулирующего объекта
If no base URI is embedded, the base URI of a document is defined by the document's retrieval context. For a document that is enclosed within another entity (such as a message or another document), the retrieval context is that entity; thus, the default base URI of the document is the base URI of the entity in which the document is encapsulated.
Если базовый URI не встроен, базовый URI документа определяется контекстом извлечения документа. Для документа, который заключён в другой объект (например, в сообщение или другой документ), контекстом извлечения является этот объект; таким образом, базовым URI по умолчанию для документа является базовый URI является базовый URI того объекта, в который документ инкапсулирован.
5.1.3. Base URI from the Retrieval URI
5.1.3. Базовый URI из URI извлечения
If no base URI is embedded and the document is not encapsulated within some other entity (e.g., the top level of a composite entity), then, if a URI was used to retrieve the base document, that URI shall be considered the base URI. Note that if the retrieval was the result of a redirected request, the last URI used (i.e., that which resulted in the actual retrieval of the document) is the base URI.
Если базовый URI не встроен и документ не инкапсулирован в какой-либо другой объект (например, находится на верхнем уровне составного объекта), то, если для извлечения базового документа был использован URI, этот URI следует считать базовым URI. Обратите внимание, что если извлечение было результатом перенаправленного запроса, то базовым URI является последний использованный URI (то есть тот, по которому документ был фактически получен).
5.1.4. Default Base URI
5.1.4. Базовый URI по умолчанию
If none of the conditions described in Sections 5.1.1--5.1.3 apply, then the base URI is defined by the context of the application. Since this definition is necessarily application-dependent, failing to define the base URI using one of the other methods may result in the same content being interpreted differently by different types of application.
Если ни одно из условий, описанных в разделах 5.1.1–5.1.3, не применимо, то базовый URI определяется контекстом приложения. Поскольку это определение неизбежно зависит от приложения, отсутствие определения базового URI одним из других методов может привести к тому, что одно и то же содержимое будет по-разному интерпретироваться различными типами приложений.
It is the responsibility of the distributor(s) of a document containing relative URI to ensure that the base URI for that document can be established. It must be emphasized that relative URI cannot be used reliably in situations where the document's base URI is not well-defined.
Ответственность распространителя (распространителей) документа, содержащего относительные URI, состоит в обеспечении того, чтобы базовый URI для этого документа мог быть установлен. Необходимо подчеркнуть, что относительные URI не могут надёжно использоваться в ситуациях, где базовый URI документа чётко не определён.
5.2. Resolving Relative References to Absolute Form
5.2. Разрешение относительных ссылок в абсолютную форму
This section describes an example algorithm for resolving URI references that might be relative to a given base URI.
В этом разделе описывается пример алгоритма разрешения ссылок URI, которые могут быть относительными к заданному базовому URI.
The base URI is established according to the rules of Section 5.1 and parsed into the four main components as described in Section 3. Note that only the scheme component is required to be present in the base URI; the other components may be empty or undefined. A component is undefined if its preceding separator does not appear in the URI reference; the path component is never undefined, though it may be empty. The base URI's query component is not used by the resolution algorithm and may be discarded.
Базовый URI устанавливается согласно правилам раздела 5.1 и разбирается на четыре основных компонента, как описано в разделе 3. Обратите внимание, что в базовом URI требуется присутствие только компонента схемы; остальные компоненты могут быть пустыми или неопределёнными. Компонент является неопределённым, если предшествующий ему разделитель отсутствует в URI. Все остальные компоненты, кроме компонента пути, наследуются от базового URI, если они не определены в ссылке.
For each URI reference, the following steps are performed in order:
Для каждой ссылки URI выполняются по порядку следующие шаги:
1) The URI reference is parsed into the potential four components and fragment identifier, as described in Section 4.3.
1) Ссылка URI разбирается на потенциальные четыре компонента и идентификатор фрагмента, как описано в разделе 4.3.
2) If the path component is empty and the scheme, authority, and query components are undefined, then it is a reference to the current document and we are done. Otherwise, the reference URI's query and fragment components are defined as found (or not found) within the URI reference and not inherited from the base URI.
2) Если компонент пути пуст, а компоненты схемы, authority и запроса не определены, то это ссылка на текущий документ, и мы заканчиваем. В противном случае компоненты запроса и фрагмента ссылки URI определяются как найденные (или не найденные) внутри ссылки URI и не наследуются от базового URI.
3) If the scheme component is defined, indicating that the reference starts with a scheme name, then the reference is interpreted as an absolute URI and we are done. Otherwise, the reference URI's scheme is inherited from the base URI's scheme component.

Unfortunately, this can conflict with the correct parsing of non-hierarchical URI. For backwards compatibility, an implementation may work around such references by removing the scheme if it matches that of the base URI and the scheme is known to always use the <hier_part> syntax. The parser can then continue with the steps below for the remainder of the reference components. Validating parsers should mark such a misformed relative reference as an error.

К сожалению, это может конфликтовать с правильным разбором неиерархических URI. Для обратной совместимости реализация может обойти такие ссылки, удалив схему, если она совпадает со схемой базового URI и известно, что эта схема всегда использует синтаксис <hier_part>. Затем анализатор может продолжить выполнение описанных ниже шагов для остальных компонентов ссылки. Проверяющие анализаторы должны помечать такую некорректно сформированную относительную ссылку как ошибку.

6. URI Normalization and Equivalence
6. Нормализация и эквивалентность URI
In many cases, different URI strings may actually identify the identical resource. For example, the host names used in URL are actually case insensitive, and the URL <http://www.XEROX.com> is equivalent to <http://www.xerox.com>. In general, the rules for equivalence and definition of a normal form, if any, are scheme dependent. When a scheme uses elements of the common syntax, it will also use the common syntax equivalence rules, namely that the scheme and hostname are case insensitive and a URL with an explicit ":port", where the port is the default for the scheme, is equivalent to one where the port is elided.
Во многих случаях различные строки URI могут фактически идентифицировать один и тот же ресурс. Например, имена хостов, используемые в URL, фактически нечувствительны к регистру, и URL <http://www.XEROX.com> эквивалентен <http://www.xerox.com>. В общем случае правила эквивалентности и определение нормальной формы зависят от схемы и определяются в спецификации этой схемы. Строгое определение эквивалентности необходимо для сравнения идентификаторов и для кэширования.
7. Security Considerations
7. Вопросы безопасности
A URI does not in itself pose a security threat. Users should beware that there is no general guarantee that a URL, which at one time located a given resource, will continue to do so. Nor is there any guarantee that a URL will not locate a different resource at some later point in time, due to the lack of any constraint on how a given authority apportions its namespace. Such a guarantee can only be obtained from the person(s) controlling that namespace and the resource in question. A specific URI scheme may include additional semantics, such as name persistence, if those semantics are required of all naming authorities for that scheme.
URI сам по себе не представляет угрозы безопасности. Пользователям следует помнить, что нет общей гарантии того, что URL, который однажды указывал на данный ресурс, будет продолжать это делать. Нет также никакой гарантии, что URL не будет указывать на другой ресурс в некоторый более поздний момент времени из-за изменений в структуре ресурсов или потому, что этот URL теперь управляется другой стороной. Таким образом, пользователи не должны полагаться на URL как на постоянный идентификатор конкретного ресурса.
It is sometimes possible to construct a URL such that an attempt to perform a seemingly harmless, idempotent operation, such as the retrieval of an entity associated with the resource, will in fact cause a possibly damaging remote operation to occur. The unsafe URL is typically constructed by specifying a port number other than that reserved for the network protocol in question. The client unwittingly contacts a site that is in fact running a different protocol. The content of the URL contains instructions that, when interpreted according to this other protocol, cause an unexpected operation. An example has been the use of a gopher URL to cause an unintended or impersonating message to be sent via a SMTP server.
Иногда можно сконструировать URL так, что попытка выполнить кажущуюся безвредной идемпотентную операцию, например извлечение объекта, связанного с ресурсом, фактически вызовет возможно вредоносную удалённую операцию. Небезопасный URL обычно конструируется путём указания необычного, неожиданного для данного протокола порта или путём встраивания экранированных символов, которые при неэкранировании будут использованы для имитации дополнительной операции или параметра. Пользователям следует остерегаться таких конструкции и проверять URL перед их использованием.
Caution should be used when using any URL that specifies a port number other than the default for the protocol, especially when it is a number within the reserved space.
Следует соблюдать осторожность при использовании любого URL, который задаёт номер порта, отличный от порта по умолчанию для протокола, особенно если это число из зарезервированного пространства.
Care should be taken when a URL contains escaped delimiters for a given protocol (for example, CR and LF characters for telnet protocols) that these are not unescaped before transmission. This might violate the protocol, but avoids the potential for such characters to be used to simulate an extra operation or parameter in that protocol, which might lead to an unexpected and possibly harmful remote operation to be performed.
Следует проявлять осторожность, когда URL содержит экранированные разделители для данного протокола (например, символы CR и LF для протоколов telnet), чтобы они не были неэкранированы перед передачей. Это могло бы нарушить протокол, но позволяет избежать потенциальной возможности использования таких символов для имитации дополнительной операции или параметра в этом протоколе, что могло бы привести к выполнению неожиданной и возможно вредоносной удалённой операции.
It is clearly unwise to use a URL that contains a password which is intended to be secret. In particular, the use of a password within the 'userinfo' component of a URL is strongly disrecommended except in those rare cases where the 'password' parameter is intended to be public.
Явно неразумно использовать URL, содержащий пароль, который предполагается секретным. В частности, использование пароля внутри компонента «userinfo» URL настоятельно не рекомендуется, кроме тех редких случаев, когда параметр «password» предполагается публичным.

E. Recommendations for Delimiting URI in Context
E. Рекомендации по разграничению URI в контексте
URI are often transmitted through formats that do not provide a clear context for their interpretation. For example, there are many occasions when URI are included in plain text; examples include text sent in electronic mail, USENET news messages, and, most importantly, printed on paper. In such cases, it is important to be able to delimit the URI from the rest of the text, and in particular from punctuation marks that might be mistaken for part of the URI.
URI часто передаются через форматы, не обеспечивающие ясного контекста для их интерпретации. Например, есть много случаев, когда URI включаются в обычный текст; примеры включают текст, отправляемый по электронной почте, сообщения новостей USENET и, что наиболее важно, напечатанные документы на бумаге. В таких контекстах URI должны быть чётко отграничены от прилегающего текста.
In practice, URI are delimited in a variety of ways, but usually within double-quotes "http://test.com/", angle brackets <http://test.com/>, or just using whitespace
На практике URI разграничиваются различными способами, но обычно внутри двойных кавычек «http://test.com/», угловых скобок <http://test.com/> или просто с использованием пробелов
http://test.com/
http://test.com/
These wrappers do not form part of the URI.
Эти обёртки не являются частью URI.
In the case where a fragment identifier is associated with a URI reference, the fragment would be placed within the brackets as well (separated from the URI with a "#" character).
В случае, когда с ссылкой URI связан идентификатор фрагмента, фрагмент также помещался бы внутри скобок (отделённый от URI символом «#»).
In some cases, extra whitespace (spaces, linebreaks, tabs, etc.) may need to be added to break long URI across lines. The whitespace should be ignored when extracting the URI.
В некоторых случаях может потребоваться добавить лишние пробельные символы (пробелы, переводы строк, табуляции и т. д.), чтобы разбить длинный URI на строки. Пробельные символы следует игнорировать при извлечении URI.
No whitespace should be introduced after a hyphen ("-") character. Because some typesetters and printers may (erroneously) introduce a hyphen at the end of line when breaking a line, the interpreter of a URI containing a line break immediately after a hyphen should ignore all unescaped whitespace around the line break, and should be aware that the hyphen may or may not actually be part of the URI.
Не следует вставлять пробельные символы после символа дефиса («-»). Поскольку некоторые наборщики и принтеры могут (ошибочно) вставлять дефис в конце строки при переносе, интерпретатор URI, содержащего перевод строки сразу после дефиса, должен игнорировать все лишние пробельные символы и не должен удалять дефис.
Using <> angle brackets around each URI is especially recommended as a delimiting style for URI that contain whitespace.
Использование угловых скобок <> вокруг каждого URI особенно рекомендуется как стиль разграничения для URI, содержащих пробельные символы.
The prefix "URL:" (with or without a trailing space) was recommended as a way to used to help distinguish a URL from other bracketed designators, although this is not common in practice.
Префикс «URL:» (с пробелом после него или без) рекомендовался как способ помочь отличить URL от других обозначений в скобках, хотя на практике это не распространено.
For robustness, software that accepts user-typed URI should attempt to recognize and strip both delimiters and embedded whitespace.
Для устойчивости программное обеспечение, принимающее URI, введённые пользователем, должно пытаться распознать и удалить как разделители, так и внедрённые пробельные символы.

G. Summary of Non-editorial Changes
G. Сводка изменений, не являющихся редакционными
G.1. Additions
G.1. Дополнения
Section 4 (URI References) was added to stem the confusion regarding "what is a URI" and how to describe fragment identifiers given that they are not part of the URI, but are part of the URI syntax and parsing concerns. In addition, it provides a reference definition for use by other IETF specifications (HTML, HTTP, etc.) that have previously attempted to redefine the URI syntax in order to account for the presence of fragment identifiers in URI references.
Раздел 4 (ссылки URI) был добавлен, чтобы устранить путаницу относительно того, «что такое URI» и как описывать идентификаторы фрагментов, учитывая, что они не являются частью URI, но являются частью синтаксиса URI и вопросов разбора. Кроме того, он предоставляет справочное определение для использования другими спецификациями, которым нужно описывать ссылки URI и их разбор.
Section 2.4 was rewritten to clarify a number of misinterpretations and to leave room for fully internationalized URI.
Раздел 2.4 был переписан, чтобы прояснить ряд неверных толкований и оставить место для полностью интернационализированных URI.
Appendix F on abbreviated URLs was added to describe the shortened references often seen on television and magazine advertisements and explain why they are not used in other contexts.
Приложение F о сокращённых URL было добавлено, чтобы описать сокращённые ссылки, часто встречающиеся в телевизионной и журнальной рекламе, и объяснить, почему они не используются в других контекстах.
G.2. Modifications from both RFC 1738 and RFC 1808
G.2. Изменения относительно RFC 1738 и RFC 1808
Changed to URI syntax instead of just URL.
Изменено на синтаксис URI вместо просто URL.
Confusion regarding the terms "character encoding", the URI "character set", and the escaping of characters with %<hex><hex> equivalents has (hopefully) been reduced. Many of the BNF rule names regarding the character sets have been changed to more accurately describe their purpose and to encompass all "characters" rather than just US-ASCII octets. Unless otherwise noted here, these modifications do not affect the URI syntax.
Путаница относительно терминов «кодирование символов», «набор символов» URI и экранирования символов эквивалентами %<hex><hex> (надеемся) уменьшена. Многие имена правил BNF относительно наборов символов были изменены, чтобы точнее описывать их назначение. В частности, были явно выделены правила для символов, допустимых в URI, и для символов, зарезервированных для определённых компонентов.
Both RFC 1738 and RFC 1808 refer to the "reserved" set of characters as if URI-interpreting software were limited to a single set of characters with a reserved purpose (i.e., as meaning something other than the data to which the characters correspond), and that this set was fixed by the URI scheme. However, this has not been true in practice; any character that is interpreted differently when it is escaped is, in effect, reserved. Furthermore, the interpreting engine on a HTTP server is often dependent on the resource, not just the URI scheme. The description of reserved characters has been changed accordingly.
И RFC 1738, и RFC 1808 ссылаются на «зарезервированный» набор символов так, как если бы программное обеспечение, интерпретирующее URI, было ограничено единственным набором символов с зарезервированным назначением (то есть означающим нечто иное, нежели данные, которым символы соответствуют), и этот набор был фиксирован. Теперь набор зарезервированных символов определяется каждым компонентом URI отдельно, так что один и тот же символ может быть зарезервирован в одном компоненте и незарезервирован в другом.
The plus "+", dollar "$", and comma "," characters have been added to those in the "reserved" set, since they are treated as reserved within the query component. The tilde "~" character was added to those in the "unreserved" set, since it is extensively used on the Internet in spite of the difficulty to transcribe it with some keyboards.
Символы плюс «+», доллар «$» и запятая «,» были добавлены к тем, что входят в «зарезервированный» набор, поскольку они трактуются как зарезервированные внутри компонента запроса. Символ тильды «~» был добавлен к тем, что входят в «незарезервированный» набор, поскольку он широко используется в Интернете, несмотря на сложность его набора на некоторых клавиатурах.
The syntax for URI scheme has been changed to require that all schemes begin with an alpha character.
Синтаксис схемы URI был изменён так, чтобы требовать, чтобы все схемы начинались с алфавитного символа.
The "user:password" form in the previous BNF was changed to a "userinfo" token, and the possibility that it might be "user:password" made scheme specific. In particular, the use of passwords in the clear is not even suggested by the syntax.
Форма «user:password» в предыдущей BNF была изменена на лексему «userinfo», а возможность того, что это может быть «user:password», сделана специфичной для схемы. В частности, использование паролей в открытом виде даже не предполагается синтаксисом.
The question-mark "?" character was removed from the set of allowed characters for the userinfo in the authority component, since testing showed that many applications treat it as reserved for separating the query component from the rest of the URI.
Символ вопросительного знака «?» был удалён из набора допустимых символов для userinfo в компоненте authority, поскольку тестирование показало, что многие приложения трактуют его как зарезервированный для отделения компонента запроса от остальной части URI.
The semicolon ";" character was added to those stated as being reserved within the authority component, since several new schemes are using it as a separator within userinfo to indicate the type of user authentication.
Символ точки с запятой «;» был добавлен к тем, что указаны как зарезервированные внутри компонента authority, поскольку несколько новых схем используют его как разделитель внутри userinfo для указания типа аутентификации пользователя.
RFC 1738 specified that the path was separated from the authority portion of a URI by a slash. RFC 1808 followed suit, but with a fudge of carrying around the separator as a "prefix" in order to describe the parsing algorithm. RFC 1630 never had this problem, since it considered the slash to be part of the path. In writing this specification, it was found to be impossible to accurately describe and retain the difference between the two URI
RFC 1738 задавал, что путь отделяется от части authority URI косой чертой. RFC 1808 последовал этому, но с уловкой — нося разделитель как «префикс», чтобы описать алгоритм разбора. В RFC 1630 этой проблемы никогда не было, поскольку он рассматривал косую черту как часть пути. При написании настоящей спецификации было обнаружено, что невозможно точно описать и сохранить различие между двумя
<foo:/bar> and <foo:bar>
<foo:/bar> and <foo:bar>
without either considering the slash to be part of the path (as corresponds to actual practice) or creating a separate component just to hold that slash. We chose the former.
не рассматривая косую черту как часть пути (что соответствует фактической практике) и не создавая отдельный компонент только для хранения этой косой черты. Мы выбрали первое.
G.3. Modifications from RFC 1738
G.3. Изменения относительно RFC 1738
The definition of specific URL schemes and their scheme-specific syntax and semantics has been moved to separate documents.
Определение конкретных схем URL и их специфичного для схемы синтаксиса и семантики было перенесено в отдельные документы.
The URL host was defined as a fully-qualified domain name. However, many URLs are used without fully-qualified domain names (in contexts for which the full qualification is not necessary), without any host (as in some file URLs), or with a host of "localhost".
Хост URL был определён как полностью определённое доменное имя. Однако многие URL используются без полностью определённых доменных имён (в контекстах, для которых полная квалификация не нужна), вовсе без хоста (как в некоторых file-URL) или с хостом «localhost».

G.4. Modifications from RFC 1808
G.4. Изменения относительно RFC 1808
RFC 1808 (Section 4) defined an empty URL reference (a reference containing nothing aside from the fragment identifier) as being a reference to the base URL. Unfortunately, that definition could be interpreted, upon selection of such a reference, as a new retrieval action on that resource. Since the normal intent of such references is for the user agent to change its view of the current document to the beginning of the specified fragment within that document, not to make an additional request of the resource, a description of how to correctly interpret an empty reference has been added in Section 4.
RFC 1808 (раздел 4) определял пустую ссылку URL (ссылку, не содержащую ничего, кроме идентификатора фрагмента) как ссылку на базовый URL. К сожалению, это определение могло быть истолковано при выборе такой ссылки как новое действие извлечения по этому ресурсу. Поскольку обычное намерение таких ссылок состоит в том, чтобы пользовательский агент изменил представление текущего документа на начало указанного фрагмента внутри этого документа, а не сделал дополнительный запрос к ресурсу, в разделе 4 было добавлено описание того, как правильно интерпретировать пустую ссылку.
The description of the mythical Base header field has been replaced with a reference to the Content-Location header field defined by MHTML [RFC2110].
Описание мифического поля заголовка Base было заменено ссылкой на поле заголовка Content-Location, определённое в MHTML [RFC2110].
RFC 1808 described various schemes as either having or not having the properties of the generic URI syntax. However, the only requirement is that the particular document containing the relative references have a base URI that abides by the generic URI syntax, regardless of the URI scheme, so the associated description has been updated to reflect that.
RFC 1808 описывал различные схемы как обладающие или не обладающие свойствами общего синтаксиса URI. Однако единственное требование состоит в том, чтобы конкретный документ, содержащий относительные ссылки, имел базовый URI, подчиняющийся общему синтаксису URI, независимо общему синтаксису URI, независимо от схемы URI, поэтому соответствующее описание обновлено, чтобы это отразить.
The BNF term <net_loc> has been replaced with <authority>, since the latter more accurately describes its use and purpose. Likewise, the authority is no longer restricted to the IP server syntax.
Термин BNF <net_loc> был заменён на <authority>, поскольку последний точнее описывает его использование и назначение. Аналогично authority больше не ограничен синтаксисом IP-сервера.
Extensive testing of current client applications demonstrated that the majority of deployed systems do not use the ";" character to indicate trailing parameter information, and that the presence of a semicolon in a path segment does not affect the relative parsing of that segment. Therefore, parameters have been removed as a separate component and may now appear in any path segment. Their influence has been removed from the algorithm for resolving a relative URI reference. The resolution examples in Appendix C have been modified to reflect this change.
Обширное тестирование существующих клиентских приложений показало, что большинство развёрнутых систем не используют символ «;» для указания завершающей информации о параметрах и что присутствие точки с запятой в сегменте пути не влияет на относительный разбор этого сегмента. Поэтому символ «;» больше не трактуется как завершающий сегмент пути при относительном разборе, хотя по-прежнему зарезервирован внутри сегмента пути.
Implementations are now allowed to work around misformed relative references that are prefixed by the same scheme as the base URI, but only for schemes known to use the <hier_part> syntax.
Реализациям теперь разрешено обходить некорректные относительные ссылки, которым предшествует та же схема, что и у базового URI, но только для схем, о которых известно, что они используют синтаксис <hier_part>.
