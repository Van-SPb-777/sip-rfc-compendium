Abstract
Аннотация
This document defines how to compress Constrained Application Protocol (CoAP) headers using the Static Context Header Compression and fragmentation (SCHC) framework. SCHC defines a header compression mechanism adapted for Constrained Devices. SCHC uses a static description of the header to reduce the header's redundancy and size. While RFC 8724 describes the SCHC compression and fragmentation framework, and its application for IPv6/UDP headers, this document applies SCHC to CoAP headers. The CoAP header structure differs from IPv6 and UDP, since CoAP uses a flexible header with a variable number of options, themselves of variable length. The CoAP message format is asymmetric: the request messages have a header format different from the format in the response messages. This specification gives guidance on applying SCHC to flexible headers and how to leverage the asymmetry for more efficient compression Rules.
Настоящий документ определяет, как сжимать заголовки протокола CoAP (Constrained Application Protocol) с помощью механизма статического сжатия контекста заголовков и фрагментации (SCHC). SCHC определяет механизм сжатия заголовков, адаптированный для ограниченных устройств. SCHC использует статическое описание заголовка для уменьшения избыточности и размера заголовка. RFC 8724 описывает механизм сжатия и фрагментации SCHC и его применение к заголовкам IPv6/UDP, а настоящий документ применяет SCHC к заголовкам CoAP. Структура заголовка CoAP отличается от IPv6 и UDP, поскольку CoAP использует гибкий заголовок с переменным числом опций, которые сами имеют переменную длину. Формат сообщения CoAP асимметричен: заголовки сообщений-запросов отличаются от заголовков сообщений-ответов. Настоящая спецификация даёт рекомендации по применению SCHC к гибким заголовкам и по использованию асимметрии для более эффективных правил сжатия.

1. Introduction
1. Введение
The Constrained Application Protocol (CoAP) [RFC7252] is a command/ response protocol designed for microcontrollers with small RAM and ROM and optimized for services based on REST (Representational State Transfer). Although the Constrained Devices are a leading factor in the design of CoAP, a CoAP header's size is still too large for LPWANs (Low-Power Wide-Area Networks). Static Context Header Compression and fragmentation (SCHC) over CoAP headers is required to increase performance or to use CoAP over LPWAN technologies.
Протокол CoAP (Constrained Application Protocol) [RFC7252] — это протокол команд и ответов, разработанный для микроконтроллеров с малым объёмом RAM и ROM и оптимизированный для служб на основе REST (Representational State Transfer). Хотя ограниченные устройства являются определяющим фактором при разработке CoAP, размер заголовка CoAP всё ещё слишком велик для LPWAN (Low-Power Wide-Area Networks). Статическое сжатие контекста заголовков и фрагментация (SCHC) над заголовками CoAP необходимы для повышения производительности или для использования CoAP поверх технологий LPWAN.
[RFC8724] defines the SCHC framework, which includes a header compression mechanism for LPWANs that is based on a static context. Section 5 of [RFC8724] explains where compression and decompression occur in the architecture. The SCHC compression scheme assumes as a prerequisite that both endpoints know the static context before transmission. The way the context is configured, provisioned, or exchanged is out of this document's scope.
[RFC8724] определяет механизм SCHC, который включает механизм сжатия заголовков для LPWAN, основанный на статическом контексте. Раздел 5 [RFC8724] объясняет, где в архитектуре происходят сжатие и декомпрессия. Схема сжатия SCHC предполагает в качестве предпосылки, что обе конечные точки знают статический контекст до передачи. Способ настройки, предоставления или обмена контекстом выходит за рамки настоящего документа.
CoAP is an application protocol, so CoAP compression requires installing common Rules between the two SCHC instances. SCHC compression may apply at two different levels: at IP and UDP in the LPWAN and another at the application level for CoAP. These two compression techniques may be independent. Both follow the same principle as that described in [RFC8724]. As different entities manage the CoAP compression process at different levels, the SCHC Rules driving the compression/decompression are also different. [RFC8724] describes how to use SCHC for IP and UDP headers. This document specifies how to apply SCHC compression to CoAP headers.
CoAP — прикладной протокол, поэтому сжатие CoAP требует установки общих правил между двумя экземплярами SCHC. Сжатие SCHC может применяться на двух разных уровнях: на уровне IP и UDP в LPWAN и на прикладном уровне для CoAP. Эти два способа сжатия могут быть независимыми. Оба следуют одному принципу, описанному в [RFC8724]. Поскольку сжатием CoAP на разных уровнях управляют разные сущности, правила SCHC, управляющие сжатием и декомпрессией, также различаются. [RFC8724] описывает, как использовать SCHC для заголовков IP и UDP. Настоящий документ определяет, как применять сжатие SCHC к заголовкам CoAP.
SCHC compresses and decompresses headers based on common contexts
SCHC сжимает и разжимает заголовки на основе общих контекстов
between Devices. The SCHC context includes multiple Rules. Each
между устройствами. Контекст SCHC включает несколько правил. Каждое
Rule can match the header fields to specific values or ranges of values. If a Rule matches, the matched header fields are replaced by the RuleID and the Compression Residue that contains the residual bits of the compression. Thus, different Rules may correspond to different protocol headers in the packet that a Device expects to send or receive.
Правило может сопоставлять поля заголовка с конкретными значениями или диапазонами значений. Если правило совпадает, совпавшие поля заголовка заменяются на RuleID и остаток сжатия, содержащий остаточные биты сжатия. Таким образом, разные правила могут соответствовать разным заголовкам протоколов в пакете, который устройство ожидает отправить или получить.
A Rule describes the packets' entire header with an ordered list of Field Descriptors; see Section 7 of [RFC8724]. Thereby, each description contains the Field ID (FID), Field Length (FL), and Field Position (FP), as well as a Direction Indicator (DI) (upstream, downstream, and bidirectional) and some associated Target Values (TVs). The DI is used for compression to give the best TV to the FID when these values differ in their transmission direction. So, a field may be described several times.
Правило описывает весь заголовок пакетов упорядоченным списком дескрипторов полей; см. раздел 7 [RFC8724]. При этом каждое описание содержит идентификатор поля (FID), длину поля (FL) и позицию поля (FP), а также индикатор направления (DI) (восходящее, нисходящее и двунаправленное) и некоторые связанные целевые значения (TV). DI используется при сжатии, чтобы задать для FID наилучшее TV, когда эти значения различаются в зависимости от направления передачи. Поэтому одно поле может быть описано несколько раз.
A Matching Operator (MO) is associated with each header Field Descriptor. The Rule is selected if all the MOs fit the TVs for all fields of the incoming header. A Rule cannot be selected if the message contains a field that is unknown to the SCHC compressor.
С каждым дескриптором поля заголовка связан оператор сопоставления (MO). Правило выбирается, если все MO соответствуют TV для всех полей входящего заголовка. Правило не может быть выбрано, если сообщение содержит поле, неизвестное компрессору SCHC.
In that case, a Compression/Decompression Action (CDA) associated with each field gives the method to compress and decompress each field. Compression mainly results in one of four actions:
В этом случае действие сжатия/декомпрессии (CDA), связанное с каждым полем, задаёт способ сжатия и декомпрессии каждого поля. Сжатие в основном сводится к одному из четырёх действий:
* send the field value (value-sent),
* отправить значение поля (value-sent),
* send nothing (not-sent),
* ничего не отправлять (not-sent),
* send some Least Significant Bits (LSBs) of the field, or
* отправить некоторые младшие значащие биты (LSB) поля или
* send an index (mapping-sent).
* отправить индекс (mapping-sent).
After applying the compression, there may be some bits to be sent. These values are called "Compression Residue".
После применения сжатия может остаться некоторое количество битов для отправки. Эти значения называются «остаток сжатия».
SCHC is a general mechanism applied to different protocols, with the exact Rules to be used depending on the protocol and the application. Section 10 of [RFC8724] describes the compression scheme for IPv6 and UDP headers. This document targets CoAP header compression using SCHC.
SCHC — общий механизм, применяемый к разным протоколам, причём точный набор используемых правил зависит от протокола и приложения. Раздел 10 [RFC8724] описывает схему сжатия для заголовков IPv6 и UDP. Настоящий документ посвящён сжатию заголовков CoAP с помощью SCHC.

3. CoAP Headers Compressed with SCHC
3. Заголовки CoAP, сжимаемые с помощью SCHC
The use of SCHC over the CoAP header applies the same description and compression/decompression techniques as the technique used for IP and UDP, as explained in [RFC8724]. For CoAP, the SCHC Rules description uses the direction information to optimize the compression by reducing the number of Rules needed to compress headers. The Field Descriptor MAY define both request/response headers and TVs in the same Rule, using the DI to indicate the header type.
Использование SCHC над заголовком CoAP применяет те же методы описания и сжатия/декомпрессии, что и для IP и UDP, как объяснено в [RFC8724]. Для CoAP описание правил SCHC использует информацию о направлении, чтобы оптимизировать сжатие, сокращая число правил, необходимых для сжатия заголовков. Дескриптор поля МОЖЕТ определять в одном правиле как заголовки запросов и ответов, так и TV, используя DI для указания типа заголовка.
As for other header compression protocols, when the compressor does not find a correct Rule to compress the header, the packet MUST be sent uncompressed using the RuleID dedicated to this purpose, and where the Compression Residue is the complete header of the packet. See Section 6 of [RFC8724].
Как и в других протоколах сжатия заголовков, если компрессор не находит подходящего правила для сжатия заголовка, пакет ДОЛЖЕН быть отправлен несжатым с использованием RuleID, предназначенного для этой цели, причём остатком сжатия будет полный заголовок пакета. См. раздел 6 [RFC8724].
3.1. Differences between CoAP and UDP/IP Compression
3.1. Отличия сжатия CoAP от сжатия UDP/IP
CoAP compression differs from IPv6 and UDP compression in the following aspects:
Сжатие CoAP имеет отличия от сжатия IPv6 и UDP в следующих аспектах:
* The CoAP message format is asymmetric; the headers are different for a request or a response. For example, the Uri-Path option is mandatory in the request, and it might not be present in the response. A request might contain an Accept option, and the response might include a Content-Format option. In comparison, the IPv6 and UDP returning path swaps the value of some fields in the header. However, all the directions have the same fields (e.g., source and destination address fields).
* Формат сообщения CoAP асимметричен; заголовки запроса и ответа различаются. Например, опция Uri-Path обязательна в запросе и может отсутствовать в ответе. Запрос может содержать опцию Accept, а ответ может включать опцию Content-Format. Для сравнения, обратный путь IPv6 и UDP меняет местами значения некоторых полей заголовка. Однако во всех направлениях имеются одни и те же поля (например, поля адреса источника и назначения).
[RFC8724] defines the use of a DI in the Field Descriptor, which allows a single Rule to process a message header differently, depending on the direction.
[RFC8724] определяет использование DI в дескрипторе поля, что позволяет одному правилу обрабатывать заголовок сообщения по-разному в зависимости от направления.
* Even when a field is "symmetric" (i.e., found in both directions), the values carried in each direction are different. The compression may use a "match-mapping" MO to limit the range of expected values in a particular direction and reduce the Compression Residue's size. Through the DI, a Field Descriptor in the Rules splits the possible field value into two parts, one for each direction. For instance, if a client sends only Confirmable (CON) requests [RFC7252], the Type can be elided by compression, and the answer may use one single bit to carry either the ACK or Reset (RST) type. The field Code has the same behavior: the 0.0X code format value in the request and the Y.ZZ code format in the response.
* Даже когда поле «симметрично» (то есть встречается в обоих направлениях), значения, переносимые в каждом направлении, различаются. Сжатие может использовать MO «match-mapping», чтобы ограничить диапазон ожидаемых значений в конкретном направлении и уменьшить размер остатка сжатия. С помощью DI дескриптор поля в правилах разбивает возможное значение поля на две части, по одной для каждого направления. Например, если клиент отправляет только запросы Confirmable (CON) [RFC7252], тип может быть исключён сжатием, а ответ может использовать один бит для передачи типа ACK или Reset (RST). Поле Code ведёт себя так же: значение формата кода 0.0X в запросе и формат кода Y.ZZ в ответе.
* In SCHC, the Rule defines the different header fields' length, so SCHC does not need to send it. In IPv6 and UDP headers, the fields have a fixed size, known by definition. On the other hand, some CoAP header fields have variable lengths, and the Rule description specifies it. For example, in a Uri-Path or Uri- Query, the Token size may vary from 0 to 8 bytes, and the CoAP options use the Type-Length-Value encoding format.
* В SCHC правило определяет длину различных полей заголовка, поэтому SCHC не нужно её передавать. В заголовках IPv6 и UDP поля имеют фиксированный размер, известный по определению. С другой стороны, некоторые поля заголовка CoAP имеют переменную длину, и описание правила её задаёт. Например, в Uri-Path или Uri-Query размер токена может изменяться от 0 до 8 байт, а опции CoAP используют формат кодирования Type-Length-Value.
When doing SCHC compression of a variable-length field, Section 7.4.2 of [RFC8724] offers the option of defining a function for the Field Length in the Field Descriptor to know the length before compression. If the Field Length is unknown, the Rule will set it as a variable, and SCHC will send the compressed field's length in the Compression Residue.
При сжатии поля переменной длины SCHC раздел 7.4.2 [RFC8724] предлагает возможность определить функцию для длины поля в дескрипторе поля, чтобы знать длину до сжатия. Если длина поля неизвестна, правило задаст её как переменную, и SCHC передаст длину сжатого поля в остатке сжатия.

4.5. CoAP Token Fields
4.5. Поля токена CoAP
CoAP defines the Token using two CoAP fields: Token Length in the mandatory header and Token Value directly following the mandatory CoAP header.
CoAP определяет токен с помощью двух полей CoAP: длины токена в обязательном заголовке и значения токена, следующего непосредственно за обязательным заголовком CoAP.
SCHC processes the Token Length as it would any header field. If the value does not change, the size can be stored in the TV and elided during the transmission. Otherwise, SCHC will send the Token Length in the Compression Residue.
SCHC обрабатывает длину токена так же, как любое поле заголовка. Если значение не меняется, размер может быть сохранён в TV и исключён при передаче. В противном случае SCHC передаст длину токена в остатке сжатия.
For the Token Value, SCHC MUST NOT send it as variable-length data in the Compression Residue, to avoid ambiguity with the Token Length. Therefore, SCHC MUST use the Token Length value to define the size of the Compression Residue. SCHC designates a specific function, "tkl", that the Rule MUST use to complete the Field Descriptor. Для значения токена SCHC НЕ ДОЛЖЕН передавать его как данные переменной длины в остатке сжатия, чтобы избежать неоднозначности с длиной токена. Поэтому SCHC ДОЛЖЕН использовать значение длины токена для определения размера остатка сжатия. 6. SCHC Compression of CoAP Extensions
6. Сжатие расширений CoAP по SCHC
6.1. Block
6.1. Block
When a packet uses a Block option [RFC7959], SCHC compression MUST send its content in the Compression Residue. The SCHC Rule describes an empty TV with the MO set to "ignore" and the CDA set to "value- sent". The Block option allows fragmentation at the CoAP level that is compatible with SCHC fragmentation. Both fragmentation mechanisms are complementary, and the node may use them for the same packet as needed.
Когда пакет использует опцию Block [RFC7959], сжатие SCHC ДОЛЖНО передавать её содержимое в остатке сжатия. Правило SCHC описывает пустое TV с MO «ignore» и CDA «value-sent». Опция Block допускает фрагментацию на уровне CoAP, совместимую с фрагментацией SCHC. Оба механизма фрагментации дополняют друг друга, и узел может использовать их для одного и того же пакета по мере необходимости.
6.2. Observe
6.2. Observe
[RFC7641] defines the Observe Option. The SCHC Rule description will not define the TV but will set the MO to "ignore" and the CDA to "value-sent". SCHC does not limit the maximum size for this option (3 bytes). To reduce the transmission size, either the Device implementation MAY limit the delta between two consecutive values or a proxy can modify the increment.
[RFC7641] определяет опцию Observe. Описание правила SCHC не будет определять TV, но установит MO в «ignore», а CDA в «value-sent». SCHC не ограничивает максимальный размер этой опции (3 байта). Чтобы уменьшить размер передачи, либо реализация устройства МОЖЕТ ограничивать разницу между двумя последовательными значениями, либо прокси может изменять приращение.
Since the Observe Option MAY use a RST message to inform a server that the client does not require the Observe response, a specific SCHC Rule SHOULD exist to allow the message's compression with the RST type.
Поскольку опция Observe МОЖЕТ использовать сообщение RST, чтобы сообщить серверу, что клиент не требует ответа Observe, СЛЕДУЕТ иметь специальное правило SCHC, позволяющее сжимать сообщение с типом RST.
6.3. No-Response
6.3. No-Response
[RFC7967] defines a No-Response option limiting the responses made by a server to a request. Different behaviors exist while using this option to limit the responses made by a server to a request. If both ends know the value, then the SCHC Rule will describe a TV to this value, with the MO set to "equal" and the CDA set to "not-sent".
[RFC7967] определяет опцию No-Response, ограничивающую ответы сервера на запрос. При использовании этой опции для ограничения ответов сервера на запрос существуют разные варианты поведения. Если обе стороны знают значение, правило SCHC опишет TV для этого значения с MO «equal» и CDA «not-sent».
Otherwise, if the value is changing over time, the SCHC Rule will set the MO to "ignore" and the CDA to "value-sent". The Rule may also use a "match-mapping" MO to compress this option.
В противном случае, если значение меняется со временем, правило SCHC установит MO в «ignore», а CDA в «value-sent». Правило может также использовать MO «match-mapping» для сжатия этой опции.

7.2. OSCORE Compression
7.2. Сжатие OSCORE
OSCORE aims to solve the problem of end-to-end encryption for CoAP messages. Therefore, the goal is to hide the message as much as possible while still enabling proxy operation.
OSCORE призван решить проблему сквозного шифрования сообщений CoAP. Поэтому цель состоит в том, чтобы максимально скрыть сообщение, сохраняя при этом возможность работы прокси.
Conceptually, this is achieved by splitting the CoAP message into an Inner Plaintext and Outer OSCORE message. The Inner Plaintext contains sensitive information that is not necessary for proxy operation. However, it is part of the message that can be encrypted until it reaches its end destination. The Outer Message acts as a shell matching the regular CoAP message format and includes all options and information needed for proxy operation and caching. Figure 5 below illustrates this analysis.
Концептуально это достигается разделением сообщения CoAP на внутренний открытый текст и внешнее сообщение OSCORE. Внутренний открытый текст содержит конфиденциальную информацию, не необходимую для работы прокси. Однако он является частью сообщения, которое может быть зашифровано до достижения конечного пункта назначения. Внешнее сообщение играет роль оболочки, соответствующей обычному формату сообщения CoAP, и включает все опции и сведения, необходимые для работы прокси и кэширования. Рисунок 5 ниже иллюстрирует этот анализ.
CoAP arranges the options into one of three classes, each granted a specific type of protection by the protocol:

Класс E: зашифрованные опции, перенесённые во внутренний открытый текст.

Класс I: опции, защищённые целостностью и включённые в дополнительные аутентифицированные данные (AAD) для шифрования открытого текста, но в остальном оставленные без изменений во внешнем сообщении.
Class U: Unprotected options left untouched in the Outer Message.
Класс U: незащищённые опции, оставленные без изменений во внешнем сообщении.

The use of integrity protection translates into an overhead in total message length, limiting the amount of compression that can be achieved and playing into the cost of adding security to the exchange.

For the flag bits, some SCHC compression methods are useful, depending on the application. The most straightforward alternative is to provide a fixed value for the flags, combining a MO of "equal" and a CDA of "not-sent". This SCHC definition saves most bits but could prevent flexibility. Otherwise, SCHC could use a "match- mapping" MO to choose from several configurations for the exchange. If not, the SCHC description may use an "MSB" MO to mask off the three hard-coded most significant bits.
Для битов флагов в зависимости от приложения полезны некоторые методы сжатия SCHC. Самым простым вариантом является задание фиксированного значения флагов с сочетанием MO «equal» и CDA «not-sent». Такое определение SCHC экономит большинство битов, но может лишить гибкости. В противном случае SCHC мог бы использовать MO «match-mapping», чтобы выбирать одну из нескольких конфигураций обмена. Если это не так, описание SCHC может использовать MO «MSB», чтобы замаскировать три жёстко заданных старших бита.
Note that fixing a flag bit will limit the choices of CoAP options that can be used in the exchange, since the values of these choices are dependent on specific options.
Отметим, что фиксация бита флага ограничит выбор опций CoAP, которые могут использоваться в обмене, поскольку значения этих вариантов зависят от конкретных опций.
The piv field lends itself to having some bits masked off with an "MSB" MO and an "LSB" CDA. This SCHC description could be useful in applications where the message frequency is low, such as LPWAN technologies. Note that compressing the sequence numbers may reduce the maximum number of sequence numbers that can be used in an exchange. Once the sequence number exceeds the maximum value, the OSCORE keys need to be re-established.
Поле piv хорошо поддаётся маскированию некоторых битов с помощью MO «MSB» и CDA «LSB». Такое описание SCHC может быть полезно в приложениях с низкой частотой сообщений, таких как технологии LPWAN. 9. Security Considerations
9. Соображения безопасности
The use of SCHC header compression for CoAP header fields only affects the representation of the header information. SCHC header compression itself does not increase or decrease the overall level of security of the communication. When the connection does not use a security protocol (OSCORE, DTLS, etc.), it is necessary to use a Layer 2 security mechanism to protect the SCHC messages.
Использование сжатия заголовков SCHC для полей заголовка CoAP влияет только на представление информации заголовка. Само сжатие заголовков SCHC не повышает и не понижает общий уровень безопасности связи. Когда соединение не использует протокол безопасности (OSCORE, DTLS и т. п.), необходимо применять механизм безопасности уровня 2 для защиты сообщений SCHC.
If an LPWAN is the Layer 2 technology being used, the SCHC security considerations discussed in [RFC8724] continue to apply. When using another Layer 2 protocol, the use of a cryptographic integrity- protection mechanism to protect the SCHC headers is REQUIRED. Such cryptographic integrity protection is necessary in order to continue to provide the properties that [RFC8724] relies upon.
Если используемой технологией уровня 2 является LPWAN, продолжают действовать соображения безопасности SCHC, рассмотренные в [RFC8724]. При использовании другого протокола уровня 2 ТРЕБУЕТСЯ применение механизма криптографической защиты целостности для защиты заголовков SCHC. Такая криптографическая защита целостности необходима для сохранения свойств, на которые опирается [RFC8724].
When SCHC is used with OSCORE, the security considerations discussed in [RFC8613] continue to apply.
Когда SCHC используется с OSCORE, продолжают действовать соображения безопасности, рассмотренные в [RFC8613].
When SCHC is used with the OSCORE Outer headers, the Initialization Vector (IV) size in the Compression Residue must be carefully selected. There is a trade-off between compression efficiency (with a longer "MSB" MO prefix) and the frequency at which the Device must renew its key material (in order to prevent the IV from expanding to an uncompressible value). The key-renewal operation itself requires several message exchanges and requires energy-intensive computation, but the optimal trade-off will depend on the specifics of the Device and expected usage patterns.
Когда SCHC используется с внешними заголовками OSCORE, размер вектора инициализации (IV) в остатке сжатия должен выбираться тщательно. Существует компромисс между эффективностью сжатия (при более длинном префиксе MO «MSB») и частотой, с которой устройство должно обновлять свой ключевой материал (чтобы IV не вырос до несжимаемого значения). Сама операция обновления ключей требует нескольких обменов сообщениями и энергоёмких вычислений, но оптимальный компромисс будет зависеть от особенностей устройства и ожидаемых моделей использования.
If an attacker can introduce a corrupted SCHC-compressed packet onto a link, DoS attacks can be mounted by causing excessive resource consumption at the decompressor. However, an attacker able to inject packets at the link layer is also capable of other, potentially more damaging, attacks.
Если злоумышленник может внедрить повреждённый сжатый по SCHC пакет в канал, возможны атаки типа DoS за счёт чрезмерного потребления ресурсов при декомпрессии. Однако злоумышленник, способный внедрять пакеты на канальном уровне, способен и на другие, потенциально более опасные атаки.
SCHC compression emits variable-length Compression Residues for some CoAP fields. In the representation of the compressed header, the length field that is sent is not the length of the original header field but rather the length of the Compression Residue that is being transmitted. If a corrupted packet arrives at the decompressor with a longer or shorter length than the original compressed representation possessed, the SCHC decompression procedures will detect an error and drop the packet.
Сжатие SCHC формирует остатки сжатия переменной длины для некоторых полей CoAP. В представлении сжатого заголовка передаваемое поле длины является не длиной исходного поля заголовка, а длиной передаваемого остатка сжатия. Если на декомпрессор поступает повреждённый пакет с длиной больше или меньше, чем имело исходное сжатое представление, процедуры декомпрессии SCHC обнаружат ошибку и отбросят пакет.
SCHC header compression Rules MUST remain tightly coupled between the compressor and the decompressor. If the compression Rules get out of sync, a Compression Residue might be decompressed differently at the receiver than the initial message submitted to compression procedures. Accordingly, any time the context Rules are updated on an OSCORE endpoint, that endpoint MUST trigger OSCORE key re- establishment. Similar procedures may be appropriate to signal Rule updates when other message-protection mechanisms are in use.
Правила сжатия заголовков SCHC ДОЛЖНЫ оставаться жёстко связанными между компрессором и декомпрессором. Если правила сжатия рассинхронизируются, остаток сжатия может быть разжат на приёмнике иначе, чем исходное сообщение, поданное на процедуры сжатия. Соответственно, при любом обновлении правил контекста на конечной точке OSCORE эта конечная точка ДОЛЖНА инициировать повторную установку ключей OSCORE. Подобные процедуры могут быть уместны для сигнализации об обновлениях правил при использовании других механизмов защиты сообщений.
