Abstract
Аннотация
The SIP "Caller Preferences" extension defined in RFC 3840 provides a mechanism that allows a SIP request to convey information relating to the originator's capabilities and preferences for handling of that request. The SIP REFER method defined in RFC 3515 provides a mechanism that allows one party to induce another to initiate a SIP request. This document extends the REFER method to use the mechanism of RFC 3840. By doing so, the originator of a REFER may inform the recipient as to the characteristics of the target that the induced request is expected to reach.
Расширение «предпочтения вызывающего абонента» (Caller Preferences) протокола SIP, определённое в RFC 3840, предоставляет механизм, позволяющий запросу SIP передавать информацию о возможностях и предпочтениях инициатора в отношении обработки этого запроса. Метод REFER протокола SIP, определённый в RFC 3515, предоставляет механизм, позволяющий одной стороне побудить другую инициировать запрос SIP. Настоящий документ расширяет метод REFER, чтобы использовать механизм RFC 3840. Благодаря этому инициатор REFER может сообщить получателю характеристики целевого объекта, которого, как ожидается, достигнет инициированный запрос.
1. Introduction
1. Введение
This document extends the SIP [2] REFER method defined in RFC 3515 [3] to be used with feature parameters defined in RFC 3840 [4].
Настоящий документ расширяет метод REFER протокола SIP [2] из RFC 3515 [3], чтобы использовать параметры фич-тегов из RFC 3840 [4].
Feature tags are used by a UA to convey to another UA information about capabilities and features. This information can be shared by a UA using a number of mechanisms, including REGISTER requests and responses and OPTIONS responses. This information can also be shared in the context of a dialog by inclusion with a remote target URI (Contact URI).
Фич-теги используются UA для передачи другому UA информации о возможностях и функциях. Эта информация может также передаваться UA с помощью ряда механизмов, включая запросы и ответы REGISTER и ответы OPTIONS. Её также можно передать в контексте диалога, включив в URI удалённой цели (Contact URI).
Feature tag information can be very useful to another UA. It is especially useful prior to the establishment of a session. For example, if a UA knows (through an OPTIONS query, for example) that the remote UA supports both video and audio, the calling UA might call, offering video in the SDP. Another example is when a UA knows that a remote UA is acting as a focus and hosting a conference. In this case, the UA might first subscribe to the conference URI and find out details about the conference prior to sending an INVITE to join.
Информация фич-тегов может быть очень полезной другому UA. Особенно она полезна до установления сессии. Например, если UA знает (например, с помощью запроса OPTIONS), что удалённый UA поддерживает и видео, и аудио, вызывающий UA может выполнить вызов, предложив видео в SDP. Другой пример — когда UA знает, что удалённый UA действует как фокус и проводит конференцию. В этом случае UA может сначала подписаться на URI конференции и выяснить подробности о ней до отправки INVITE для присоединения.
This extension to the REFER method provides a mechanism by which the REFER-Issuer can provide this useful information about the REFER- Target capabilities and functionality to the REFER-Recipient by including feature tags in the Refer-To header field in a REFER request.
Это расширение метода REFER предоставляет механизм, с помощью которого REFER-Issuer может передать REFER-Recipient данную полезную информацию о возможностях и функциональности REFER-Target, включив фич-теги в поле заголовка Refer-To запроса REFER.

3. Definitions
3. Определения
The Refer-To BNF from RFC 3515:
BNF Refer-To из RFC 3515:
Refer-To = ("Refer-To" / "r") HCOLON ( name-addr / addr-spec ) *(SEMI generic-param)
Refer-To = ("Refer-To" / "r") HCOLON ( name-addr / addr-spec ) *(SEMI generic-param)
is extended to:
расширяется до:
Refer-To = ("Refer-To" / "r") HCOLON ( name-addr / addr-spec ) *(SEMI refer-param) refer-param = generic-param / feature-param
Refer-To = ("Refer-To" / "r") HCOLON ( name-addr / addr-spec ) *(SEMI refer-param) refer-param = generic-param / feature-param
where feature-param is defined in Section 9 of RFC 3840 [4].
где feature-param определён в разделе 9 RFC 3840 [4].
Note that if any URI parameters are present, the entire URI must be enclosed in "<" and ">". If the "<" and ">" are not present, all parameters after the URI are header parameters, not URI parameters.
Обратите внимание: если присутствуют параметры URI, весь URI должен быть заключён в «<» и «>». Если «<» и «>» отсутствуют, все параметры после URI являются параметрами заголовка, а не URI.

4. Примеры
4.1. isfocus Feature Tag Usage
4.1. Использование фич-тега isfocus
The example below shows how the "isfocus" feature tag can be used by REFER-Issuer to tell the REFER-Recipient that the REFER-Target is a conference focus and, consequently, that sending an INVITE will bring the REFER-Recipient into the conference:
Приведённый ниже пример показывает, как REFER-Issuer может использовать фич-тег «isfocus», чтобы сообщить REFER-Recipient, что REFER-Target является фокусом конференции и, следовательно, отправка INVITE приведёт REFER-Recipient в конференцию:
Refer-To: sip:conf44@example.com;isfocus
Refer-To: sip:conf44@example.com;isfocus
4.2. Voice and Video Feature Tags Usage
4.2. Использование фич-тегов голоса и видео
The example below shows how a REFER-Issuer can tell the REFER- Recipient that the REFER-Target supports audio and video and, consequently, that a video and audio session can be established by sending an INVITE to the REFER-Target:
Приведённый ниже пример показывает, как REFER-Issuer может сообщить REFER-Recipient, что REFER-Target поддерживает аудио и видео и, следовательно, что сеанс видео и аудио можно установить, отправив INVITE на REFER-Target:
Refer-To: "Alice's Videophone" <sip:alice@videophone.example.com>
Refer-To: "Alice's Videophone" <sip:alice@videophone.example.com>
;audio;video
;audio;video
4.3. Example with URI parameters and multiple feature tags
4.3. Пример с параметрами URI и несколькими фич-тегами
The example below shows how the REFER-Issuer can tell the REFER- Recipient that the REFER-Target is a voicemail server. Note that the transport URI parameter is enclosed within the "<" and ">" so that it is not interpreted as a header parameter. Refer-To: <sip:alice-vm@example.com;transport=tcp>
Приведённый ниже пример показывает, как REFER-Issuer может сообщить REFER-Recipient, что REFER-Target является сервером голосовой почты. Обратите внимание, что параметр URI transport заключён в «<» и «>», чтобы он не интерпретировался как параметр заголовка. Refer-To: <sip:alice-vm@example.com;transport=tcp>
;actor="msg-taker";automata;audio
;actor="msg-taker";automata;audio
5. Security Considerations
5. Вопросы безопасности
Feature tags can provide sensitive information about a user or a UA. As such, RFC 3840 cautions against providing sensitive information to another party. Once this information is given out, any use may be made of it, including relaying to a third party as in this specification.
Фич-теги могут предоставлять конфиденциальную информацию о пользователе или UA. Поэтому RFC 3840 предостерегает от передачи конфиденциальной информации другой стороне. После того как эта информация передана, её можно использовать любым способом, включая пересылку третьей стороне, как в данной спецификации.
A REFER-Issuer MUST NOT create or guess feature tags. Instead, a feature tag included in a REFER SHOULD be discovered in an authenticated and secure method (such as an OPTIONS response or from a remote target URI in a dialog) directly from the REFER-Target.
REFER-Issuer НЕ ДОЛЖЕН создавать или угадывать фич-теги. Вместо этого фич-тег, включённый в REFER, СЛЕДУЕТ обнаруживать аутентифицированным и защищённым методом (например, из ответа OPTIONS или из URI удалённой цели в диалоге) непосредственно у REFER-Target.
It is RECOMMENDED that the REFER-Issuer includes in the Refer-To header field all feature tags that were listed in the most recent Contact header field of the REFER-Target.
РЕКОМЕНДУЕТСЯ, чтобы REFER-Issuer включал в поле заголовка Refer-To все фич-теги, перечисленные в самом последнем поле заголовка Contact REFER-Target.
A feature tag provided by a REFER-Issuer cannot be authenticated or certified directly from the REFER request. As such, the REFER- Recipient MUST treat the information as a hint. If the REFER- Recipient application logic or user's action depends on the presence of the expressed feature, the feature tag can be verified. For example, in order to do so, the REFER-Recipient can directly send an OPTIONS query to the REFER-Target over a secure (e.g., mutually authenticated and integrity-protected) connection. This protects the REFER-Recipient against the sending of incorrect or malicious feature tags.
Фич-тег, предоставленный REFER-Issuer, невозможно аутентифицировать или удостоверить непосредственно из запроса REFER. Поэтому REFER-Recipient ДОЛЖЕН рассматривать эту информацию как подсказку. Если логика приложения REFER-Recipient или действие пользователя зависят от наличия выраженной функции, фич-тег можно проверить. Например, для этого REFER-Recipient может напрямую отправить запрос OPTIONS на REFER-Target по защищённому (например, взаимно аутентифицированному и защищённому целостностью) соединению. Это защищает REFER-Recipient от отправки неверных или вредоносных фич-тегов.
