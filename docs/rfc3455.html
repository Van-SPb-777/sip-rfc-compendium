Abstract
Аннотация
This document describes a set of private Session Initiation Protocol (SIP) headers (P-headers) used by the 3rd-Generation Partnership Project (3GPP), along with their applicability, which is limited to particular environments. The P-headers are for a variety of purposes within the networks that the partners use, including charging and information about the networks a call traverses.
Настоящий документ описывает набор частных заголовков протокола инициирования сессий (SIP) (P-заголовков), используемых Партнёрским проектом третьего поколения (3GPP), а также их применимость, которая ограничена определёнными средами. P-заголовки служат различным целям в сетях, используемых партнёрами, включая тарификацию и информацию о сетях, которые проходит вызов.
1. Overall Applicability
1. Общая применимость
The SIP extensions specified in this document make certain assumptions regarding network topology, linkage between SIP and lower layers, and the availability of transitive trust. These assumptions are generally NOT APPLICABLE in the Internet as a whole. The mechanisms specified here were designed to satisfy the requirements specified in the 3GPP Release 5 requirements on SIP [4] for which either no general-purpose solution was planned, where insufficient operational experience was available to understand if a general solution is needed, or where a more general solution is not yet mature. For more details about the assumptions made about these extensions, consult the Applicability subsection for each extension.
Расширения SIP, определённые в настоящем документе, делают определённые допущения относительно сетевой топологии, связи между SIP и нижними уровнями и наличия транзитивного доверия. Эти допущения в целом НЕ ПРИМЕНИМЫ в Интернете в целом. Определённые здесь механизмы были разработаны для удовлетворения требований, указанных в требованиях 3GPP Release 5 к SIP [4], для которых либо не планировалось решения общего назначения, где не хватало эксплуатационного опыта, чтобы понять, нужно ли общее решение, либо где более общее решение ещё не созрело. Подробнее о допущениях относительно этих расширений см. подраздел «Применимость» для каждого расширения.

3. Overview
3. Обзор
The Third Generation Partnership Project (3GPP) has selected SIP as the protocol used to establish and tear down multimedia sessions in the context of its IP Multimedia Subsystem (IMS). (For more information on the IMS, a detailed description can be found in 3GPP TS 23.228 [14] and 3GPP TS 24.229 [15]). 3GPP notified the IETF SIP and SIPPING working groups that existing SIP documents provided almost all the functionality needed to satisfy the requirements of the IMS, but that they required some additional functionality in order to use SIP for this purpose. These requirements [4] are documented in an Internet Draft which was submitted to the SIPPING Working Group. Some of these requirements are satisfied by chartered extensions, while other requirements were applicable to SIP, but not sufficiently general for the SIP Working Group to adopt. This document describes private extensions to address those requirements. Each extension, or set of related extensions is described in its own section below.
Партнёрский проект третьего поколения (3GPP) выбрал SIP как протокол, используемый для установления и разрыва мультимедийных сессий в контексте своей подсистемы IP-мультимедиа (IMS). (Дополнительную информацию об IMS можно найти в 3GPP TS 23.228 [14] и 3GPP TS 24.229 [15]). 3GPP уведомил рабочие группы IETF SIP и SIPPING о том, что существующие документы SIP предоставляют почти всю функциональность, необходимую для удовлетворения требований IMS, но требуется некоторая дополнительная функциональность, чтобы использовать SIP для этой цели. Эти требования [4] задокументированы в Internet Draft, который был представлен рабочей группе SIPPING. Некоторые из этих требований удовлетворяются расширениями, предусмотренными уставом, тогда как другие требования были применимы к SIP, но недостаточно общими, чтобы рабочая группа SIP их приняла. Настоящий документ описывает частные расширения для удовлетворения этих требований. Каждое расширение или набор связанных расширений описан в отдельном разделе ниже.
4. SIP Private Headers
4. Частные заголовки SIP
4.1. The P-Associated-URI header
4.1. Заголовок P-Associated-URI
This extension allows a registrar to return a set of associated URIs for a registered address-of-record. We define the P-Associated-URI header field, used in the 200 OK response to a REGISTER request. The P-Associated-URI header field transports the set of Associated URIs to the registered address-of-record. An associated URI is a URI that the service provider has allocated to a user for his own usage. A registrar contains information that allows an address-of-record URI to be associated with zero or more URIs. Usually, all these URIs (the address-of-record URI and the associated URIs) are allocated for the usage of a particular user. This extension to SIP allows the UAC to know, upon a successful authenticated registration, which other URIs, if any, the service provider has associated to an address-of-record URI.
Это расширение позволяет регистратору вернуть набор связанных URI для зарегистрированного адреса записи. Мы определяем поле заголовка P-Associated-URI, используемое в ответе 200 OK на запрос REGISTER. Поле заголовка P-Associated-URI передаёт набор связанных URI для зарегистрированного адреса записи. Связанный URI — это URI, который поставщик услуг выделил пользователю для его собственного использования. Регистратор содержит информацию, позволяющую связать URI адреса записи с нулём или более URI. Обычно все эти URI (URI адреса записи и связанные URI) выделены для использования конкретным пользователем. Это расширение SIP позволяет UAC по успешной аутентифицированной регистрации узнать, какие другие URI, если таковые есть, поставщик услуг связал с URI адреса записи.
Note that, generally speaking, the registrar does not register the associated URIs on behalf of the user. Only the address-of-record which is present in the To header field of the REGISTER is registered and bound to the contact address. The only information conveyed is that the registrar is aware of other URIs to be used by the same user.
Обратите внимание, что, вообще говоря, регистратор не регистрирует связанные URI от имени пользователя. Регистрируется и привязывается к контактному адресу только адрес записи, присутствующий в поле заголовка To запроса REGISTER. Передаётся лишь информация о том, что регистратор знает о других URI, которые должен использовать тот же пользователь.
It may be possible, however, that an application server (or even the registrar itself) registers any of the associated URIs on behalf of the user by means of a third party registration. However, this third party registration is out of the scope of this document. A UAC MUST NOT assume that the associated URIs are registered.
Однако возможно, что сервер приложений (или даже сам регистратор) регистрирует любые из связанных URI от имени пользователя посредством регистрации третьей стороной. Однако такая регистрация третьей стороной выходит за рамки настоящего документа. UAC НЕ ДОЛЖЕН предполагать, что связанные URI зарегистрированы.
If a UAC wants to check whether any of the associated URIs is registered, it can do so by mechanisms specified outside this document, e.g., the UA may send a REGISTER request with the To header field value set to any of the associated URIs and without a Contact header. The 200 OK response will include a Contact header with the list of registered contact addresses. If the associated URI is not registered, the UA MAY register it prior to its utilization.
Если UAC желает проверить, зарегистрирован ли какой-либо из связанных URI, он может сделать это механизмами, указанными вне настоящего документа, например UA может отправить запрос REGISTER со значением поля заголовка To, установленным в любой из связанных URI, и без заголовка Contact. Ответ 200 OK будет включать заголовок Contact со списком зарегистрированных контактных адресов. Если связанный URI не зарегистрирован, UA МОЖЕТ зарегистрировать его до его использования.
4.1.1. Applicability statement for the P-Associated-URI header
4.1.1. Заявление о применимости заголовка P-Associated-URI
The P-Associated-URI header is applicable in SIP networks where the SIP provider is allocating the set of identities that a user can claim (in headers like the From field) in requests that the UA generates. It furthermore assumes that the provider knows the entire set of identities that a user can legitimately claim, and that the user is willing to restrict its claimed identities to that set. This is in contrast to normal SIP usage, where the From field is explicitly an end-user specified field.
Заголовок P-Associated-URI применим в сетях SIP, где поставщик услуг SIP выделяет набор идентичностей, которые пользователь может заявлять (в таких заголовках, как поле From) в запросах, генерируемых UA. Более того, предполагается, что поставщик знает весь набор идентичностей, которые пользователь может законно заявлять, и что пользователь готов ограничить свои заявляемые идентичности этим набором. Это отличается от обычного использования SIP, где поле From явно является полем, задаваемым конечным пользователем.
4.1.2. Usage of the P-Associated-URI header
4.1.2. Использование заголовка P-Associated-URI
The registrar inserts the P-Associated-URI header field into the 200 OK response to a REGISTER request. The header field value is populated with a list containing zero or more URIs that are associated to the address-of-record. If the registrar supports the P-Associated-URI header extension, then the registrar MUST always insert the P-Associated-URI header field in all the 200 OK responses to a REGISTER request, regardless of whether the REGISTER was an initial registration, re-registration, or de-registration and regardless of whether there are zero or more associated URIs.
Регистратор вставляет поле заголовка P-Associated-URI в ответ 200 OK на запрос REGISTER. Значение поля заголовка заполняется списком, содержащим ноль или более URI, связанных с адресом записи. Если регистратор поддерживает расширение заголовка P-Associated-URI, то регистратор ДОЛЖЕН всегда вставлять поле заголовка P-Associated-URI во все ответы 200 OK на запрос REGISTER, независимо от того, была ли это начальная регистрация, повторная регистрация или отмена регистрации, и независимо от того, есть ли ноль или более связанных URI.
4.1.2.1. Procedures at the UA
4.1.2.1. Процедуры у UA
A UAC may receive a P-Associated-URI header field in the 200 OK response for a REGISTER. The presence of the header field in the 200 OK response for a REGISTER request implies that the extension is supported at the registrar.
UAC может получить поле заголовка P-Associated-URI в ответе 200 OK на REGISTER. Присутствие поля заголовка в ответе 200 OK на запрос REGISTER подразумевает, что расширение поддерживается регистратором.
The header value contains a list of zero or more associated URIs to the address-of-record URI. The UAC MAY use any of the associated URIs to populate the From header value, or any other SIP header value that provides information of the identity of the calling party, in a subsequent request.
Значение заголовка содержит список из нуля или более связанных URI для URI адреса записи. UAC МОЖЕТ использовать любой из связанных URI для заполнения значения заголовка From или любого другого значения заголовка SIP, предоставляющего информацию об идентичности вызывающей стороны, в последующем запросе.
The UAC MAY check whether the associated URI is registered or not. This check can be done, e.g., by populating the To header value in a REGISTER sent to the registrar and without a Contact header. The 200 OK response will include a Contact header with the list of registered contact addresses. As described in SIP [1], the 200 OK response may contain a Contact header field with zero or more values (zero meaning the address-of-record is not registered).
UAC МОЖЕТ проверить, зарегистрирован ли связанный URI. Эта проверка может быть выполнена, например, путём заполнения значения заголовка To в REGISTER, отправленном регистратору, и без заголовка Contact. Ответ 200 OK будет включать заголовок Contact со списком зарегистрированных контактных адресов. Как описано в SIP [1], ответ 200 OK может содержать поле заголовка Contact с нулём или более значений (ноль означает, что адрес записи не зарегистрирован).
4.1.2.2. Procedures at the registrar
4.1.2.2. Процедуры у регистратора
A registrar that receives and authorizes a REGISTER request, may associate zero or more URIs with the address-of-record.
Регистратор, который получает и авторизует запрос REGISTER, может связать ноль или более URI с адресом записи.
A registrar that supports this specification MUST include a P-Associated-URI header field in the 200 OK response to a REGISTER request. The header MUST be populated with a comma-separated list of SIP or SIPS URIs which are associated to the address-of-record under registration.
Регистратор, поддерживающий настоящую спецификацию, ДОЛЖЕН включать поле заголовка P-Associated-URI в ответ 200 OK на запрос REGISTER. Заголовок ДОЛЖЕН быть заполнен разделённым запятыми списком URI SIP или SIPS, которые связаны с регистрируемым адресом записи.
In case the address-of-record under registration does not have any other SIP or SIPS URIs associated, the registrar MUST include an empty P-Associated-URI header value.
В случае если регистрируемый адрес записи не имеет других связанных URI SIP или SIPS, регистратор ДОЛЖЕН включить пустое значение заголовка P-Associated-URI.
4.1.2.3. Procedures at the proxy
4.1.2.3. Процедуры у прокси
This memo does not define any procedure at the proxy.
Настоящий меморандум не определяет никаких процедур у прокси.
4.2. The P-Called-Party-ID header
4.2. Заголовок P-Called-Party-ID
A proxy server inserts a P-Called-Party-ID header, typically in an INVITE request, en-route to its destination. The header is populated with the Request-URI received by the proxy in the request. The UAS identifies which address-of-record, out of several registered address-of-records, the invitation was sent to (for example, the user may be simultaneously using a personal and a business SIP URIs to receive invitation to sessions). The UAS may use the information to render different distinctive audiovisual alerting tones, depending on the URI used to receive the invitation to the session.
Прокси-сервер вставляет заголовок P-Called-Party-ID, обычно в запрос INVITE, по пути к месту назначения. Заголовок заполняется Request-URI, полученным прокси в запросе. UAS определяет, на какой адрес записи из нескольких зарегистрированных адресов записи был отправлен приглашение (например, пользователь может одновременно использовать личный и рабочий URI SIP для получения приглашений на сессии). UAS может использовать эту информацию для воспроизведения разных характерных аудиовизуальных сигналов оповещения в зависимости от URI, использованного для получения приглашения на сессию.
Users in the 3GPP IP Multimedia Subsystem (IMS) may get one or several SIP URIs (address-of-record) to identify the user. For instance, a user may get a business SIP URI and a personal one. As an example of utilization, the user may make available the business SIP URI to co-workers and may make available the personal SIP URI to members of the family.
Пользователи в подсистеме IP-мультимедиа (IMS) 3GPP могут получить один или несколько URI SIP (адрес записи) для идентификации пользователя. Например, пользователь может получить рабочий URI SIP и личный. В качестве примера использования пользователь может предоставить рабочий URI SIP сослуживцам, а личный URI SIP — членам семьи.
At a certain point in time, both the business SIP URI and the personal SIP URI are registered in the SIP registrar, so both URIs can receive invitations to new sessions. When the user receives an invitation to join a session, he/she should be aware of which of the several registered SIP URIs this session was sent to.
В определённый момент времени и рабочий URI SIP, и личный URI SIP зарегистрированы в SIP-регистраторе, так что оба URI могут получать приглашения на новые сессии. Когда пользователь получает приглашение присоединиться к сессии, он должен знать, на какой из нескольких зарегистрированных URI SIP была отправлена эта сессия.
This requirement is stated in the 3GPP Release 5 requirements on SIP [4].
Это требование указано в требованиях 3GPP Release 5 к SIP [4].
The problem arises during the terminating side of a session establishment, when the SIP proxy that is serving a UA gets an INVITE, and the SIP server retargets the SIP URI which is present in the Request-URI field, and replaces it by the SIP URI published by the user in the Contact header field of the REGISTER request at registration time. When the UAS receives the SIP INVITE, it cannot determine which address-of-record the request was sent to.
Проблема возникает на завершающей стороне установления сессии, когда SIP-прокси, обслуживающий UA, получает INVITE, и SIP-сервер перенацеливает URI SIP, присутствующий в поле Request-URI, и заменяет его на URI SIP, опубликованный пользователем в поле заголовка Contact запроса REGISTER при регистрации. Когда UAS получает SIP INVITE, он не может определить, на какой адрес записи был отправлен запрос.
One can argue that the To header field conveys the semantics of the called user, and therefore, this extension to SIP is not needed. Although the To header field in SIP may convey the called party ID in most situations, there are two particular cases when the above assumption is not correct:
Можно возразить, что поле заголовка To передаёт семантику вызываемого пользователя, и потому это расширение SIP не нужно. Хотя поле заголовка To в SIP может передавать идентификатор вызываемой стороны в большинстве ситуаций, есть два особых случая, когда вышеуказанное допущение неверно:
1. The session has been forwarded, redirected, etc., by previous SIP proxies, before arriving to the proxy which is serving the called user.
1. Сессия была переадресована, перенаправлена и т. д. предыдущими SIP-прокси, прежде чем достичь прокси, обслуживающего вызываемого пользователя.
2. The UAC builds an INVITE request and the To header field is not the same as the Request-URI.
2. UAC строит запрос INVITE, и поле заголовка To не совпадает с Request-URI.
The problem of using the To header field is that this field is populated by the UAC and not modified by proxies in the path. If the UAC, for any reason, did not populate the To header field with the address-of-record of the destination user, then the destination user is not able to distinguish which address-of-record the session was destined.
Проблема использования поля заголовка To состоит в том, что это поле заполняется UAC и не изменяется прокси на пути. Если UAC по какой-либо причине не заполнил поле заголовка To адресом записи пользователя назначения, то пользователь назначения не может определить, на какой адрес записи была направлена сессия.
Another possible solution to the problem is built upon the differentiation of the Contact header value between different address-of-record at registration time. The UA can differentiate each address-of-record it registers by assigning a different Contact header value. For instance, when the UA registers the address-of- record sip:id1, the Contact header value can be sip:id1@ua; the registration of sip:id2 can be bound to the Contact value sip:id2@ua.
Другое возможное решение проблемы основано на различении значения заголовка Contact между разными адресами записи во время регистрации. UA может различать каждый регистрируемый адрес записи, назначая разное значение заголовка Contact. Например, когда UA регистрирует адрес записи sip:id1, значением заголовка Contact может быть sip:id1@ua; регистрация sip:id2 может быть привязана к значению Contact sip:id2@ua.
The solution described above assumes that the UA explicitly registers each of its address-of-record URIs, and therefore, it has full control over the contact address values assigned to each registration. However, in the case the UA does not have full control of its registered address-of-record, because of, e.g., a third party registration, the solution does not work. This may be the case of the 3GPP registration, where the UA may have previously indicated the network, by means outside of SIP, that some other address-of-record URIs may be automatically registered when the UA registers a particular address-of-record. The requirement is covered in the 3GPP Release 5 requirements on SIP [4].
Описанное выше решение предполагает, что UA явно регистрирует каждый из своих URI адресов записи и, следовательно, полностью контролирует значения контактных адресов, назначенные каждой регистрации. Однако в случае, когда UA не имеет полного контроля над своим зарегистрированным адресом записи, например из-за регистрации третьей стороной, решение не работает. Это может быть случай регистрации 3GPP, где UA мог ранее указать сети средствами вне SIP, что некоторые другие URI адресов записи могут регистрироваться автоматически, когда UA регистрирует конкретный адрес записи. Требование охвачено в требованиях 3GPP Release 5 к SIP [4].

4.2.1. Applicability statement for the P-Called-Party-ID header
4.2.1. Заявление о применимости заголовка P-Called-Party-ID
The P-Called-Party-ID is applicable when the UAS needs to be aware of the intended address-of-record that was present in the Request-URI of the request, before the proxy retargets to the contact address. The UAS may be interested in applying different audiovisual alerting effects or other filtering services, depending on the intended destination of the request. It is specially valuable when the UAS has registered several address-of-record URIs to his registrar, and therefore, the UAS is not aware of the address-of-record that was present in the INVITE request when it hit his proxy/registrar, unless this extension is used.
P-Called-Party-ID применим, когда UAS нужно знать предполагаемый адрес записи, присутствовавший в Request-URI запроса до того, как прокси перенацелил его на контактный адрес. UAS может быть заинтересован в применении различных аудиовизуальных эффектов оповещения или иных служб фильтрации в зависимости от предполагаемого назначения запроса. Это особенно ценно, когда UAS зарегистрировал несколько URI адресов записи у своего регистратора и потому не знает, какой адрес записи присутствовал в запросе INVITE, когда он достиг его прокси/регистратора, если только это расширение не используется.
Requirements for a more general solution are proposed in [12], but have not been adopted by SIP, nor a solution has been developed.
Требования для более общего решения предложены в [12], но не были приняты SIP, и решение не разработано.
4.2.2. Usage of the P-Called-Party-ID header
4.2.2. Использование заголовка P-Called-Party-ID
The P-Called-Party-ID header field provides proxies and the UAS with the address-of-record that was present in the Request-URI of the request, before a proxy retargets the request. This information is intended to be used by subsequent proxies in the path or by the UAS.
Поле заголовка P-Called-Party-ID предоставляет прокси и UAS адрес записи, присутствовавший в Request-URI запроса до того, как прокси перенацелил запрос. Эта информация предназначена для использования последующими прокси на пути или UAS.
Typically, a SIP proxy inserts the P-Called-Party-ID header prior to retargetting the Request-URI in the SIP request. The header value is populated with the contents of Request-URI, prior to replacing it with the Contact address.
Обычно SIP-прокси вставляет заголовок P-Called-Party-ID перед перенацеливанием Request-URI в SIP-запросе. Значение заголовка заполняется содержимым Request-URI перед его заменой на контактный адрес.
4.2.2.1. Procedures at the UA
4.2.2.1. Процедуры у UA
A UAC MUST NOT insert a P-Called-Party-ID header field in any SIP request or response.
UAC НЕ ДОЛЖЕН вставлять поле заголовка P-Called-Party-ID ни в какой запрос или ответ SIP.
A UAS may receive a SIP request that contains a P-Called-Party-ID header field. The header will be populated with the address-of- record received by the proxy in the Request-URI of the request, prior to its forwarding to the UAS.
UAS может получить SIP-запрос, содержащий поле заголовка P-Called-Party-ID. Заголовок будет заполнен адресом записи, полученным прокси в Request-URI запроса до его пересылки UAS.
The UAS may use the value in the P-Called-Party-ID header field to provide services based on the called party URI, such as, e.g., filtering of calls depending on the date and time, distinctive presentation services, distinctive alerting tones, etc.
UAS может использовать значение в поле заголовка P-Called-Party-ID для предоставления услуг на основе URI вызываемой стороны, таких как фильтрация вызовов в зависимости от даты и времени, характерные услуги представления, характерные сигналы оповещения и т. д.

Необходимо, чтобы прокси, вставляющий заголовок P-Called-Party-ID, располагал информацией о пользователе, чтобы предотвратить неверную доставку идентификатора вызываемой стороны. Эта информация могла быть получена, например, в процессе регистрации.

4.3. The P-Visited-Network-ID header
4.3. Заголовок P-Visited-Network-ID
3GPP networks are composed of a collection of so called home networks, visited networks and subscribers. A particular home network may have roaming agreements with one or more visited networks. This has the effect that when a mobile terminal is roaming, it can use resources provided by the visited network in a transparent fashion.
Сети 3GPP состоят из совокупности так называемых домашних сетей, посещаемых сетей и абонентов. Конкретная домашняя сеть может иметь соглашения о роуминге с одной или несколькими посещаемыми сетями. Это приводит к тому, что при роуминге мобильный терминал может прозрачно использовать ресурсы, предоставляемые посещаемой сетью.
One of the conditions for a home network to accept the registration of a UA roaming to a particular visited network, is the existence of a roaming agreement between the home and the visited network. There is a need to indicate to the home network which one is the visited network that is providing services to the roaming UA.
Одним из условий принятия домашней сетью регистрации UA, находящегося в роуминге в конкретной посещаемой сети, является наличие соглашения о роуминге между домашней и посещаемой сетью. Есть потребность указать домашней сети, какая именно посещаемая сеть предоставляет услуги UA в роуминге.
3GPP user agents always register to the home network. The REGISTER request is proxied by one or more proxies located in the visited network towards the home network. For the sake of a simple approach, it seems sensible that the visited network includes an identification that is known at the home network. This identification should be globally unique, and takes the form of a quoted text string or a token. The home network may use this identification to verify the existence of a roaming agreement with the visited network, and to authorize the registration through that visited network.
Пользовательские агенты 3GPP всегда регистрируются в домашней сети. Запрос REGISTER проходит через прокси один или несколько прокси, расположенных в посещаемой сети, по направлению к домашней сети. Для простого подхода представляется разумным, чтобы посещаемая сеть включала идентификацию, известную в домашней сети. Эта идентификация должна быть глобально уникальной и имеет форму строки текста в кавычках или токена. Домашняя сеть может использовать эту идентификацию для проверки наличия соглашения о роуминге с посещаемой сетью и для авторизации регистрации через эту посещаемую сеть.

The P-Visited-Network-ID header field is used to convey to the registrar or home proxy in the home network the identifier of a visited network. The identifier is a text string or token that is known by both the registrar or the home proxy at the home network and the proxies in the visited network.

Typically, the home network authorizes the UA to roam to a particular visited network. This action requires an existing roaming agreement between the home and the visited network.
Обычно домашняя сеть авторизует UA для роуминга в конкретной посещаемой сети. Это действие требует наличия соглашения о роуминге между домашней и посещаемой сетью.
While it is possible for a home network to identify one or more visited networks by inspecting the domain name in the Via header fields, this approach has a heavy dependency on DNS. It is an option for a proxy to populate the via header with an IP address, for example, and in the absence of a reverse DNS entry, the IP address will not convey the desired information.

Прокси может, например, заполнить заголовок Via IP-адресом, и при отсутствии записи обратного DNS IP-адрес не передаст нужную информацию.

В случае если REGISTER или иной запрос проходит через разные административные домены (например, разные посещаемые сети), SIP-прокси МОЖЕТ вставить новый заголовок P-Visited-Network-ID, если запрос не содержит заголовка P-Visited-Network-ID с тем же идентификатором сети, что и его собственный идентификатор сети (например, если запрос прошёл через другие различные административные домены).
Note also that, there is not requirement for the header value to be readable in the proxies. Therefore, a first proxy may insert an encrypted header that only the registrar can decrypt. If the request traverses a second proxy located in the same administrative domain as the first proxy, the second proxy may not be able to read the contents of the P-Visited-Network-ID header. In this situation, the second proxy will consider that its visited network identifier is not already present in the value of the header, and therefore, it will insert a new P-Visited-Network-ID header value (hopefully with the same identifier that the first proxy inserted, although perhaps, not encrypted). When the request arrives at the registrar or proxy in the home network, it will notice that the header value is repeated (both the first and the second proxy inserted it). The decrypted values should be the same, because both proxies where part of the same administrative domain. While this situation is not desirable, it does not create any harm at the registrar or proxy in the home network.
Обратите внимание также, что нет требования, чтобы значение заголовка было читаемым в прокси. Поэтому первый прокси может вставить зашифрованный заголовок, который расшифровать может только регистратор. Если запрос проходит через второй прокси, расположенный в том же административном домене, что и первый прокси, второй прокси может быть не в состоянии прочитать содержимое заголовка P-Visited-Network-ID. В этой ситуации второй прокси будет считать, что его идентификатор посещаемой сети ещё не присутствует в значении заголовка, и потому вставит новое значение заголовка P-Visited-Network-ID (по возможности с тем же идентификатором, который вставил первый прокси, хотя, возможно, незашифрованным). Когда запрос достигнет регистратора или прокси в домашней сети, тот заметит, что значение заголовка повторяется (его вставили и первый, и второй прокси). Расшифрованные значения должны совпадать, поскольку оба прокси были частью одного административного домена. Хотя такая ситуация нежелательна, она не причиняет вреда регистратору или прокси в домашней сети.

In order to avoid conflicts with identifiers, especially when the number of roaming agreements between networks increase, care must be taken when selecting the value of the P-Visited-Network-ID. Although there are many mechanism to create globally unique identifiers across networks, one of such as mechanisms is already in operation, and that is DNS. The P-Visited-Network-ID does not have any connection to DNS, but the values in the header can be chosen from the own DNS entry representing the domain name of the network. P-Visited-Network-ID не имеет никакой связи с DNS, но значения в заголовке могут быть выбраны из собственной записи DNS, представляющей доменное имя сети. Это гарантирует уникальность значения.

4.4. The P-Access-Network-Info header
4.4. Заголовок P-Access-Network-Info
This section describes the P-Access-Network-Info header. This header is useful in SIP-based networks that also provide layer 2/layer 3 connectivity through different access technologies. SIP User Agents may use this header to relay information about the access technology to proxies that are providing services. The serving proxy may then use this information to optimize services for the UA. For example, a 3GPP UA may use this header to pass information about the access network such as radio access technology and radio cell identity to its home service provider.
Этот раздел описывает заголовок P-Access-Network-Info. Этот заголовок полезен в сетях на основе SIP, которые также обеспечивают связность уровня 2/уровня 3 через различные технологии доступа. Пользовательские агенты SIP могут использовать этот заголовок для передачи информации о технологии доступа прокси, предоставляющим услуги. Обслуживающий прокси может затем использовать эту информацию для оптимизации услуг для UA. Например, UA 3GPP может использовать этот заголовок для передачи информации о сети доступа, такой как технология радиодоступа и идентичность радиоячейки, своему домашнему поставщику услуг.
For the purpose of this extension, we define an access network as the network providing the layer 2/layer 3 IP connectivity which in turn provides a user with access to the SIP capabilities and services provided.
Для целей этого расширения мы определяем сеть доступа как сеть, обеспечивающую IP-связность уровня 2/уровня 3, которая, в свою очередь, даёт пользователю доступ к предоставляемым возможностям и услугам SIP.
In some cases, the SIP server that provides the user with services may wish to know information about the type of access network that the UA is currently using. Some services are more suitable or less suitable depending on the access type, and some services are of more value to subscribers if the access network details are known by the SIP proxy which provides the user with services.
В некоторых случаях SIP-сервер, предоставляющий пользователю услуги, может пожелать знать информацию о типе сети доступа, которую UA использует в настоящее время. Некоторые услуги более подходят или менее подходят в зависимости от типа доступа, и некоторые услуги ценнее для абонентов, если детали сети доступа известны SIP-прокси, предоставляющему пользователю услуги.
In other cases, the SIP server that provides the user with services may simply wish to know crude location information in order to provide certain services to the user. For example, many of the location based services available in wireless networks today require the home network to know the identity of the cell the user is being served by.
В других случаях SIP-сервер, предоставляющий пользователю услуги, может просто пожелать знать грубую информацию о местоположении, чтобы предоставить определённые услуги пользователю. Например, многие из доступных сегодня в беспроводных сетях служб, основанных на местоположении, требуют, чтобы домашняя сеть знала идентичность ячейки, в которой обслуживается пользователь.
Some regulatory requirements exist mandating that for cellular radio systems, the identity of the cell where an emergency call is established is made available to the emergency authorities.
Существуют некоторые нормативные требования, предписывающие, чтобы для систем сотовой радиосвязи идентичность ячейки, в которой установлен экстренный вызов, была доступна службам экстренного реагирования.
The SIP server that provides services to the user may desire knowledge about the access network. This is achieved by defining a new private SIP extension header, P-Access-Network-Info. This header carries information relating to the access network between the UAC and its serving proxy in the home network.
SIP-сервер, предоставляющий пользователю услуги, может желать знания о сети доступа. Это достигается определением нового частного поля расширенного заголовка SIP — P-Access-Network-Info. Этот заголовок несёт информацию, относящуюся к сети доступа между UAC и его обслуживающим прокси в домашней сети.
4.4.1. Applicability Statement for the P-Access-Network-Info header
4.4.1. Заявление о применимости заголовка P-Access-Network-Info
This mechanism is appropriate in environments where SIP services are dependent on SIP elements knowing details about the IP and lower layer technologies used by a UA to connect to the SIP network. Specifically, the extension requires that the UA know the access technology it is using, and that a proxy desires such information to provide services. Generally, SIP is built on the "Everything over IP and IP over everything" principle, where the access technology is not relevant for the operation of SIP. Since SIP systems generally should not care or even know about the access technology, this SIP extension is not for general SIP usage.
Этот механизм уместен в средах, где услуги SIP зависят от знания элементами SIP деталей об IP- и нижних технологиях, используемых UA для подключения к сети SIP. В частности, расширение требует, чтобы UA знал используемую технологию доступа и чтобы прокси желал такой информации для предоставления услуг. Вообще говоря, SIP построен на принципе «всё поверх IP и IP поверх всего», где технология доступа не важна для работы SIP. Поскольку системы SIP обычно не должны заботиться о технологии доступа или даже знать о ней, это расширение SIP не предназначено для общего использования в SIP.
The information revealed in the P-Access-Network-Info header is potentially very sensitive. Proper protection of this information depends on the existence of specific business and security relationships amongst the proxies that will see SIP messages containing this header. It also depends on explicit knowledge of the UA of the existence of those relationships. Therefore, this mechanism is only suitable in environments where the appropriate relationships are in place, and the UA has explicit knowledge that they exist.
Информация, раскрываемая в заголовке P-Access-Network-Info, потенциально очень чувствительна. Надлежащая защита этой информации зависит от наличия конкретных деловых и доверительных отношений между прокси, которые увидят сообщения SIP с этим заголовком. Она также зависит от явного знания UA о наличии этих отношений. Поэтому этот механизм подходит только в средах, где надлежащие отношения установлены и UA имеет явное знание об их наличии.
4.4.2. Usage of the P-Access-Network-Info header
4.4.2. Использование заголовка P-Access-Network-Info
When a UA generates a SIP request or response which it knows is going to be securely sent to its SIP proxy that is providing services, the UA inserts a P-Access-Network-Info header into the SIP message. This header contains information on the access network that the UA is using to get IP connectivity. The header is typically ignored by intermediate proxies between the UA and the SIP proxy that is providing services. The proxy providing services can inspect the header and make use of the information contained there to provide appropriate services, depending on the value of the header. Before proxying the request onwards, this proxy strips the header from the message.
Когда UA генерирует запрос или ответ SIP, о котором он знает, что он будет безопасно отправлен его SIP-прокси, предоставляющему услуги, UA вставляет в сообщение SIP заголовок P-Access-Network-Info. Этот заголовок содержит информацию о сети доступа, которую UA использует для получения IP-связности. Заголовок обычно игнорируется промежуточными прокси между UA и SIP-прокси, предоставляющим услуги. Прокси, предоставляющий услуги, может исследовать заголовок и использовать содержащуюся там информацию для предоставления надлежащих услуг в зависимости от значения заголовка. Перед проксированием запроса далее этот прокси удаляет заголовок из сообщения.
4.4.2.1. UA behavior
4.4.2.1. Поведение UA
A UA that supports this extension and is willing to disclose the related parameters MAY insert the P-Access-Network-Info header in any SIP request or response.
UA, поддерживающий это расширение и готовый раскрыть соответствующие параметры, МОЖЕТ вставлять заголовок P-Access-Network-Info в любой запрос или ответ SIP.
The UA inserting this information MUST trust the proxy that is providing services to protect its privacy by deleting the header before forwarding the message outside of the proxy's domain. This proxy is typically located in the home network.
UA, вставляющий эту информацию, ДОЛЖЕН доверять прокси, предоставляющему услуги, в защите его конфиденциальности путём удаления заголовка перед пересылкой сообщения за пределы домена прокси. Этот прокси обычно расположен в домашней сети.
In order to do the deletion of the header, there must also be a transitive trust in intermediate proxies between the UA and the proxy that provides the services. This trust is established by business agreements between the home network and the access network, and generally supported by the use of standard security mechanisms, e.g., IPsec, AKA, and TLS.
Чтобы выполнить удаление заголовка, должно также существовать транзитивное доверие в промежуточных прокси между UA и прокси, предоставляющим услуги. Это доверие устанавливается деловыми соглашениями между домашней сетью и сетью доступа и обычно поддерживается использованием стандартных механизмов безопасности, например IPsec, AKA и TLS.
4.4.2.2. Proxy behavior
4.4.2.2. Поведение прокси
A proxy MUST NOT insert or modify the value of the P-Access-Network-Info header.
Прокси НЕ ДОЛЖЕН вставлять или изменять значение заголовка P-Access-Network-Info.
A proxy which is providing services to the UA, may act upon any information present in the P-Access-Network-Info header value, if is present, to provide a different service depending on the network or the location through which the UA is accessing the server. For example, for cellular radio access networks the SIP proxy located in the home network may use the cell ID to provide basic localized services.
Прокси, предоставляющий услуги UA, может действовать на основе любой информации, присутствующей в значении заголовка P-Access-Network-Info, если он присутствует, чтобы предоставить иную услугу в зависимости от сети или местоположения, через которое UA получает доступ к серверу. Например, для сетей сотового радиодоступа SIP-прокси, расположенный в домашней сети, может использовать идентификатор ячейки для предоставления базовых локализованных услуг.
A proxy that provides services to the user, the proxy typically located in the home network, and therefore trusted, MUST delete the header when the SIP signaling is forwarded to a SIP server located in a non-trusted administrative network domain. The SIP server providing services to the UA uses the access network information and is of no interest to other proxies located in different administrative domains.
Прокси, предоставляющий услуги пользователю — обычно расположенный в домашней сети и потому доверенный, — ДОЛЖЕН удалить заголовок, когда сигнализация SIP пересылается на SIP-сервер, расположенный в недоверенном административном сетевом домене. SIP-сервер, предоставляющий услуги UA, использует информацию сети доступа, и она не представляет интереса для других прокси, расположенных в иных административных доменах.
4.5. The P-Charging-Function-Addresses header
4.5. Заголовок P-Charging-Function-Addresses
3GPP has defined a distributed architecture that results in multiple network entities becoming involved in providing access and services. There is a need to inform each SIP proxy involved in a transaction about the common charging functional entities to receive the generated charging records or charging events.
3GPP определил распределённую архитектуру, в результате которой в предоставление доступа и услуг вовлекается несколько сетевых объектов. Есть потребность информировать каждый SIP-прокси, участвующий в транзакции, об общих функциональных объектах тарификации, которые должны получать сгенерированные тарификационные записи или события тарификации.
The solution provided by 3GPP is to define two types of charging functional entities: Charging Collection Function (CCF) and Event Charging Function (ECF). CCF is used for off-line charging (e.g., for postpaid account charging). ECF is used for on-line charging (e.g., for pre-paid account charging). There may be more than a single instance of CCF and ECF in a network, in order to provide redundancy in the network. In case there are more than a single instance of either the CCF or the ECF addresses, implementations SHOULD attempt sending the charging data to the ECF or CCF address, starting with the first address of the sequence (if any) in the P-Charging-Function-Addresses header. The CCF and ECF addresses may be passed during the establishment of a dialog or in a standalone transaction. More detailed information about charging can be found in 3GPP TS 32.200 [16] and 3GPP TS 32.225 [17].
Решение, предоставляемое 3GPP, состоит в определении двух типов функциональных объектов тарификации: Charging Collection Function (CCF) и Event Charging Function (ECF). CCF используется для офлайн-тарификации (например, для тарификации постоплатных счетов). ECF используется для онлайн-тарификации (например, для тарификации предоплатных счетов). В сети может быть более одного экземпляра CCF и ECF для обеспечения резервирования. В случае если адресов CCF или ECF более одного, реализациям СЛЕДУЕТ пытаться отправлять данные тарификации на адрес ECF или CCF, начиная с первого адреса последовательности (если таковой есть) в заголовке P-Charging-Function-Addresses. Адреса CCF и ECF могут передаваться при установлении диалога или в автономной транзакции. Более подробную информацию о тарификации можно найти в 3GPP TS 32.200 [16] и 3GPP TS 32.225 [17].
We define the SIP private header P-Charging-Function-Addresses. A proxy MAY include this header, if not already present, in either the initial request or response for a dialog, or in the request and response of a standalone transaction outside a dialog. Only one instance of the header MUST be present in a particular request or response.
Мы определяем частный заголовок SIP P-Charging-Function-Addresses. Прокси МОЖЕТ включать этот заголовок, если он ещё не присутствует, в начальный запрос или ответ для диалога либо в запрос и ответ автономной транзакции вне диалога. В конкретном запросе или ответе ДОЛЖЕН присутствовать только один экземпляр заголовка.
The mechanisms by which a SIP proxy collects the values to populate the P-Charging-Function-Addresses header values are outside the scope of this document. However, as an example, a SIP proxy may have preconfigured these addresses, or may obtain them from a subscriber database.
Механизмы, которыми SIP-прокси собирает значения для заполнения заголовка P-Charging-Function-Addresses, выходят за рамки настоящего документа. Однако, например, SIP-прокси может иметь эти адреса предварительно сконфигурированными либо получать их из базы данных абонентов.
4.5.1. Applicability Statement for the P-Charging-Function-Addresses header
4.5.1. Заявление о применимости P-Charging-Function-Addresses
The P-Charging-Function-Addresses header is applicable within a single private administrative domain where coordination of charging is required, for example, according to the architecture specified in 3GPP TS 32.200 [16]. The P-Charging-Function-Addresses header is not included in a SIP message sent outside of the own administrative domain. The header is not applicable if the administrative domain does not provide a charging function.
Заголовок P-Charging-Function-Addresses применим в пределах одного частного административного домена, где требуется координация тарификации, например согласно архитектуре, определённой в 3GPP TS 32.200 [16]. Заголовок P-Charging-Function-Addresses не включается в сообщение SIP, отправляемое за пределы собственного административного домена. Заголовок не применим, если административный домен не предоставляет функцию тарификации.
The P-Charging-Function-Addresses header is applicable whenever the following circumstances are met:
Заголовок P-Charging-Function-Addresses применим всякий раз, когда соблюдаются следующие обстоятельства:
1. A UA sends a REGISTER or dialog-initiating request (e.g., INVITE) or a standalone transaction request outside a dialog to a proxy located in the administrative domain of a private network.
1. UA отправляет REGISTER или запрос, инициирующий диалог (например, INVITE), либо автономный запрос транзакции вне диалога прокси, расположенному в административном домене частной сети.
2. A registrar, proxy or UA that is located in the administrative domain of the private network wants to generate charging records.
2. Регистратор, прокси или UA, расположенный в административном домене частной сети, хочет генерировать тарификационные записи.
3. A registrar, proxy or UA that is located in the private network has access to the addresses of the charging function entities for that network.
3. Регистратор, прокси или UA, расположенный в частной сети, имеет доступ к адресам объектов функции тарификации для этой сети.
4. There are other proxies located in the same administrative domain of the private network, that are generated charging records or charging events. The proxies want to send, by means outside SIP, the charging information to the same charging collecting entities than the first proxy.
4. В том же административном домене частной сети есть другие прокси, которые сгенерировали записи тарификации или события тарификации. Прокси хотят отправить средствами вне SIP информацию тарификации тем же объектам сбора тарификации, что и первый прокси.
4.5.2. Usage of the P-Charging-Function-Addresses header
4.5.2. Использование заголовка P-Charging-Function-Addresses
A SIP proxy that receives a SIP request may insert a P-Charging-Function-Addresses header prior to forwarding the request, if the header was not already present in the SIP request. The header value contains one or more parameters that contain the hostnames or IP addresses of the nodes that are willing to receive charging information.
SIP-прокси, получающий SIP-запрос, может вставить заголовок P-Charging-Function-Addresses перед пересылкой запроса, если заголовок ещё не присутствовал в SIP-запросе. Значение заголовка содержит один или несколько параметров, содержащих имена хостов или IP-адреса узлов, готовых принимать тарификационную информацию.
A SIP proxy that receives a SIP request that includes a P-Charging-Function-Addresses may use the hostnames or IP addresses included in the value, as the destination of charging information or charging events. The means to send those charging information or events are outside the scope of this document, and usually, do not use SIP for that purpose.
SIP-прокси, получающий SIP-запрос, включающий P-Charging-Function-Addresses, может использовать имена хостов или IP-адреса, включённые в значение, как адресаты тарификационной информации или событий тарификации. Средства отправки этой тарификационной информации или событий выходят за рамки настоящего документа и обычно не используют для этой цели SIP.
4.5.2.1. Procedures at the UA
4.5.2.1. Процедуры у UA
This document does not specify any procedure at the UA, with regard to the P-Charging-Function-Addresses header. UAs need not understand this header. However, it might be possible that a UA is located within the administrative domain of a private network (e.g., a PSTN gateway, or conference mixer), and it may have access to the addresses of the charging entities. In this cases, a UA MAY insert the P-Charging-Function-Addresses header in a SIP request or response when the next hop for the message is a proxy located in the same administrative domain.
Настоящий документ не определяет никаких процедур у UA в отношении заголовка P-Charging-Function-Addresses. UA не обязаны понимать этот заголовок. Однако возможно, что UA расположен в административном домене частной сети (например, шлюз ТфОП или микшер конференции), и он может иметь доступ к адресам тарификационных объектов. В этих случаях UA МОЖЕТ вставить заголовок P-Charging-Function-Addresses в запрос или ответ SIP, когда следующий переход для сообщения — прокси, расположенный в том же административном домене.
4.5.2.2. Procedures at the Proxy
4.5.2.2. Процедуры у прокси
A SIP proxy that supports this extension and receives a request or response without the P-Charging-Function-Addresses MAY insert a P-Charging-Function-Addresses header prior to forwarding the message. The header is populated with a list of the addresses of one or more charging entities where the proxy should send charging related information.
SIP-прокси, поддерживающий это расширение и получающий запрос или ответ без P-Charging-Function-Addresses, МОЖЕТ вставить заголовок P-Charging-Function-Addresses перед пересылкой сообщения. Заголовок заполняется списком адресов одного или нескольких тарификационных объектов, куда прокси должен отправлять тарификационную информацию.
If a proxy that supports this extension receives a request or response with the P-Charging-Function-Addresses, it may retrieve the information from the header value to use with application specific logic, i.e., charging. If the next hop for the message is within the administrative domain of the proxy, then the proxy SHOULD include the P-Charging-Function-Addresses header in the outbound message. However, if the next hop for the message is outside the administrative domain of the proxy, then the proxy MUST remove the P-Charging-Function-Addresses header.
Если прокси, поддерживающий это расширение, получает запрос или ответ с P-Charging-Function-Addresses, он может извлечь информацию из значения заголовка для использования в логике, специфичной для приложения, то есть для тарификации. Если следующий переход для сообщения находится в административном домене прокси, то прокси СЛЕДУЕТ включить заголовок P-Charging-Function-Addresses в исходящее сообщение. Однако если следующий переход для сообщения находится вне административного домена прокси, то прокси ДОЛЖЕН удалить заголовок P-Charging-Function-Addresses.

4.6. The P-Charging-Vector header
4.6. Заголовок P-Charging-Vector
3GPP has defined a distributed architecture that results in multiple network entities becoming involved in providing access and services. Operators need the ability and flexibility to charge for the access and services as they see fit. This requires coordination among the network entities (e.g., SIP proxies), which includes correlating charging records generated from different entities that are related to the same session.
3GPP определил распределённую архитектуру, в результате которой в предоставление доступа и услуг вовлекается несколько сетевых объектов. Операторам нужны возможность и гибкость тарифицировать доступ и услуги по своему усмотрению. Это требует координации между сетевыми объектами (например, SIP-прокси), включая корреляцию тарификационных записей, сгенерированных разными объектами и относящихся к одной и той же сессии.
The correlation information includes, but it is not limited to, a globally unique charging identifier that makes easy the billing effort.
Корреляционная информация включает, но не ограничивается глобально уникальным идентификатором тарификации, который облегчает выставление счетов.
A charging vector is defined as a collection of charging information. The charging vector may be filled in during the establishment of a dialog or standalone transaction outside a dialog. The information inside the charging vector may be filled in by multiple network entities (including SIP proxies) and retrieved by multiple network entities. There are three types of correlation information to be transferred: the IMS Charging Identity (ICID) value, the address of the SIP proxy that creates the ICID value, and the Inter Operator Identifiers (IOI). ICID is a charging value that identifies a dialog or a transaction outside a dialog. It is used to correlate charging records. ICID MUST be a globally unique value. One way to achieve globally uniqueness is to generate the ICID using two components: a locally unique value and the host name or IP address of the SIP proxy that generated the locally unique value.
Тарификационный вектор (charging vector) определяется как совокупность тарификационной информации. Тарификационный вектор может заполняться при установлении диалога или автономной транзакции вне диалога. Информация внутри тарификационного вектора может заполняться несколькими сетевыми объектами (включая SIP-прокси) и извлекаться несколькими сетевыми объектами. Передаются три типа корреляционной информации: значение IMS Charging Identity (ICID), адрес SIP-прокси, создающего значение ICID, и Inter Operator Identifiers (IOI). ICID — это тарификационное значение, идентифицирующее диалог или транзакцию вне диалога. Оно используется для корреляции тарификационных записей. ICID ДОЛЖНО быть глобально уникальным значением. Один из способов достижения глобальной уникальности — генерировать ICID из двух компонентов: локально уникального значения и имени хоста или IP-адреса SIP-прокси, сгенерировавшего локально уникальное значение.
The IOI identifies both the originating and terminating networks involved in a SIP dialog or transaction outside a dialog. There may an IOI generated from each side of the dialog to identify the network associated with each side.
IOI идентифицирует как исходящую, так и завершающую сети, участвующие в диалоге SIP или транзакции вне диалога. Может генерироваться IOI с каждой стороны диалога для идентификации сети, связанной с каждой стороной.
There is also expected to be access network charging information, which consists of network specific identifiers for the access level (e.g., UMTS radio access network or IEEE 802.11b). The details of the information for each type of network are not described in this memo.
Также ожидается наличие тарификационной информации сети доступа, которая состоит из специфичных для сети идентификаторов уровня доступа (например, сети радиодоступа UMTS или IEEE 802.11b). Подробности информации для каждого типа сети в настоящем меморандуме не описываются.
We define the SIP private header P-Charging-Vector. A proxy MAY include this header, if not already present, in either the initial request or response for a dialog, or in the request and response of a standalone transaction outside a dialog. Only one instance of the header MUST be present in a particular request or response.
Мы определяем частный заголовок SIP P-Charging-Vector. Прокси МОЖЕТ включать этот заголовок, если он ещё не присутствует, в начальный запрос или ответ для диалога либо в запрос и ответ автономной транзакции вне диалога. В конкретном запросе или ответе ДОЛЖЕН присутствовать только один экземпляр заголовка.
The mechanisms by which a SIP proxy collects the values to populate in the P-Charging-Vector are outside the scope of this document.
Механизмы, которыми SIP-прокси собирает значения для заполнения P-Charging-Vector, выходят за рамки настоящего документа.
4.6.1. Applicability Statement for the P-Charging-Vector header
4.6.1. Заявление о применимости заголовка P-Charging-Vector
The P-Charging-Vector header is applicable within a single private administrative domain or between different administrative domains where there is a trust relationship between the domains.
Заголовок P-Charging-Vector применим в пределах одного частного административного домена или между разными административными доменами, где существует доверительное отношение между доменами.
The P-Charging-Vector header is not included in a SIP message sent to another network if there is no trust relationship. The header is not applicable if the administrative domain manages charging in a way that does not require correlation of records from multiple network entities (e.g., SIP proxies).
Заголовок P-Charging-Vector не включается в сообщение SIP, отправляемое в другую сеть, если нет доверительного отношения. Заголовок не применим, если административный домен управляет тарификацией способом, не требующим корреляции записей от нескольких сетевых объектов (например, SIP-прокси).
The P-Charging-Vector header is applicable whenever the following circumstances are met:
Заголовок P-Charging-Vector применим всякий раз, когда соблюдаются следующие обстоятельства:
1. A UA sends a REGISTER or dialog-initiating request (e.g., INVITE) or a standalone transaction request outside a dialog to a proxy located in the administrative domain of a private network.
1. UA отправляет REGISTER или запрос, инициирующий диалог (например, INVITE), либо автономный запрос транзакции вне диалога прокси, расположенному в административном домене частной сети.
2. A registrar, proxy or UA that is located in the administrative domain of the private network wants to generate charging records.
2. Регистратор, прокси или UA, расположенный в административном домене частной сети, хочет генерировать тарификационные записи.
3. A proxy or UA that is located in the administrative domain of the private network has access to the charging correlation information for that network.
3. Прокси или UA, расположенный в административном домене частной сети, имеет доступ к корреляционной тарификационной информации для этой сети.
4. Optionally, a registrar, proxy or UA that is part of a second administrative domain in another private network, whose SIP request and responses are traversed through, en-route to the first private network, wants to generate charging records and correlate those records with those of the first private network. This assumes that there is a trust relationship between both private networks.
4. Необязательно: регистратор, прокси или UA, входящий во второй административный домен в другой частной сети, через который проходят запросы и ответы SIP по пути к первой частной сети, желает генерировать записи тарификации и коррелировать эти записи с записями первой частной сети. Это предполагает наличие доверительных отношений между обеими частными сетями.
4.6.2. Usage of the P-Charging-Vector header
4.6.2. Использование заголовка P-Charging-Vector
The P-Charging-Vector header is used to convey charging related information, such as the globally unique IMS charging identifier (ICID) value.
Заголовок P-Charging-Vector используется для передачи тарификационной информации, такой как глобально уникальное значение идентификатора тарификации IMS (ICID).
Typically, a SIP proxy that receives a SIP request that does not contain a P-Charging-Vector header may insert it, with those parameters that are available at the SIP proxy.
Обычно SIP-прокси, получающий SIP-запрос, не содержащий заголовка P-Charging-Vector, может вставить его с теми параметрами, которые доступны в SIP-прокси.
A SIP proxy that receives a SIP request that contains a P-Charging-Vector header may use the values, such as the globally unique ICID, to produce charging records.
SIP-прокси, получающий SIP-запрос, содержащий заголовок P-Charging-Vector, может использовать значения, такие как глобально уникальный ICID, для создания тарификационных записей.
4.6.2.1. Procedures at the UA
4.6.2.1. Процедуры у UA
This document does not specify any procedure at the UA, with regard to the P-Charging-Vector header. UAs need not understand this header.
Настоящий документ не определяет никаких процедур у UA в отношении заголовка P-Charging-Vector. UA не обязаны понимать этот заголовок.
4.6.2.2. Procedures at the Proxy
4.6.2.2. Процедуры у прокси
A SIP proxy that supports this extension and receives a request or response without the P-Charging-Vector header MAY insert a P-Charging-Vector header prior to forwarding the message. The header is populated with one ore more parameters, as described in the syntax, including but not limited to, a globally unique charging identifier.
SIP-прокси, поддерживающий это расширение и получающий запрос или ответ без заголовка P-Charging-Vector, МОЖЕТ вставить заголовок P-Charging-Vector перед пересылкой сообщения. Заголовок заполняется одним или несколькими параметрами, как описано в синтаксисе, включая, но не ограничиваясь, глобально уникальным идентификатором тарификации.
If a proxy that supports this extension receives a request or response with the P-Charging-Vector header, it may retrieve the information from the header value to use with application specific logic, i.e., charging. If the next hop for the message is within the trusted domain, then the proxy SHOULD include the P-Charging-Vector header in the outbound message. If the next hop for the message is outside the trusted domain, then the proxy MAY remove the P-Charging-Function-Addresses header.
Если прокси, поддерживающий это расширение, получает запрос или ответ с P-Charging-Function-Addresses, он может извлечь информацию из значения заголовка для использования в логике, специфичной для приложения, то есть для тарификации. Если следующий переход для сообщения находится в административном домене прокси, то прокси СЛЕДУЕТ включить заголовок P-Charging-Function-Addresses в исходящее сообщение. Однако если следующий переход для сообщения находится вне административного домена прокси, то прокси ДОЛЖЕН удалить заголовок P-Charging-Function-Addresses.
Per local application specific logic, the proxy MAY modify the contents of the P-Charging-Vector header prior to sending the message.
Согласно локальной логике, специфичной для приложения, прокси МОЖЕТ изменять содержимое заголовка P-Charging-Vector перед отправкой сообщения.

6. Security Considerations
6. Вопросы безопасности
6.1. P-Associated-URI
6.1. P-Associated-URI
The information returned in the P-Associated-URI header is not viewed as particularly sensitive. Rather, it is simply informational in nature, providing openness to the UAC with regard to the automatic association performed by the registrar. If end-to-end protection is not used at the SIP layer, it is possible for proxies between the registrar and the UA to modify the contents of the header value. This attack, while potentially annoying, should not have significant impacts.
Информация, возвращаемая в заголовке P-Associated-URI, не рассматривается как особо чувствительная. Скорее, она просто информативна по природе, обеспечивая открытость перед UAC в отношении автоматического связывания, выполненного регистратором. Если сквозная защита не используется на уровне SIP, прокси между регистратором и UA могут изменить содержимое значения заголовка. Эта атака, хотя и потенциально раздражающая, не должна иметь значительных последствий.
The lack of encryption, either end-to-end or hop-by-hop, may lead to leak some privacy regarding the list of authorized identities. For instance, a user who registers an address-of-record of sip:user1@example.com may get another SIP URI associated as sip:first.last@example.com returned in the P-Associated-URI header value. An eavesdropper could collect this information. If the user does not want to disclose the associated URIs, the eavesdropper could have gain access to private URIs. Therefore it is RECOMMENDED that this extension is used in a secured environment, where encryption of SIP messages is provided either end-to-end or hop-by-hop.
Отсутствие шифрования — сквозного или «переход за переходом» — может привести к утечке некоторой информации о конфиденциальности относительно списка авторизованных идентичностей. Например, пользователь, регистрирующий адрес записи sip:user1@example.com, может получить другой связанный URI SIP sip:first.last@example.com, возвращённый в значении заголовка P-Associated-URI. Подслушивающий мог бы собрать эту информацию. Если пользователь не желает раскрывать связанные URI, подслушивающий мог бы получить доступ к частным URI. Поэтому РЕКОМЕНДУЕТСЯ использовать это расширение в защищённой среде, где обеспечивается шифрование сообщений SIP — сквозное или «переход за переходом».
6.2. P-Called-Party-ID
6.2. P-Called-Party-ID
Due to the nature of the P-Called-Party-ID header, this header does not introduce any significant security concern. It is possible for an attacker to modify the contents of the header. However, this modification will not cause any harm to the session establishment.
В силу природы заголовка P-Called-Party-ID этот заголовок не вносит значительной проблемы безопасности. Злоумышленник может изменить содержимое заголовка. Однако это изменение не причинит вреда установлению сессии.
An eavesdropper may collect the list of identities a user is registered. This may have privacy implications. To mitigate this problem, this extension SHOULD only be used in a secured environment, where encryption of SIP messages is provided either end-to-end or hop-by-hop.
Подслушивающий может собрать список идентичностей, на которые зарегистрирован пользователь. Это может иметь последствия для конфиденциальности. Чтобы смягчить эту проблему, это расширение СЛЕДУЕТ использовать только в защищённой среде, где обеспечивается шифрование сообщений SIP — сквозное или «переход за переходом».
6.3. P-Visited-Network-ID
6.3. P-Visited-Network-ID
The P-Visited-Network-ID header assumes that there is trust relationship between a home network and one or more transited visited networks. It is possible for other proxies between the proxy in the visited network that inserts the header, and the registrar or the home proxy, to modify the value of P-Visited-Network-ID header. Therefore intermediaries participating in this mechanism MUST apply a hop-by-hop integrity protection mechanism such us IPsec or other available mechanisms in order to prevent such attacks.
Заголовок P-Visited-Network-ID предполагает наличие доверительного отношения между домашней сетью и одной или несколькими транзитными посещаемыми сетями. Другие прокси между прокси в посещаемой сети, вставляющим заголовок, и регистратором или домашним прокси могут изменить значение заголовка P-Visited-Network-ID. Поэтому посредники, участвующие в этом механизме, ДОЛЖНЫ применять механизм защиты целостности «переход за переходом», такой как IPsec или иные доступные механизмы, чтобы предотвратить такие атаки.
6.4. P-Access-Network-Info
6.4. P-Access-Network-Info
A Trust Domain is formally defined in the Short term requirements for Network Asserted Identity [13] document. For the purpose of this document, we refer to the 3GPP trust domain as the collection of SIP proxies and application servers that are operated by a 3GPP network operator and are compliant with the requirements expressed in 3GPP TS 24.229 [15].
Доверенный домен формально определён в документе «Short term requirements for Network Asserted Identity» [13]. Для целей настоящего документа мы называем доверенным доменом 3GPP совокупность SIP-прокси и серверов приложений, которыми управляет оператор сети 3GPP и которые соответствуют требованиям, изложенным в 3GPP TS 24.229 [15].
This extension assumes that the access network is trusted by the UA (because the UA's home network has a trust relationship with the access network), as described earlier in this document.
Это расширение предполагает, что сеть доступа доверена UA (поскольку домашняя сеть UA имеет доверительные отношения с сетью доступа), как описано ранее в настоящем документе.
This extension assumes that the information added to the header by the UAC should be sent only to trusted entities and should not be used outside of the trusted administrative network domain.
Это расширение предполагает, что информацию, добавленную в заголовок UAC, следует отправлять только доверенным объектам и не использовать за пределами доверенного административного сетевого домена.
The SIP proxy that provides services to the user, utilizes the information contained in this header to provide additional services and UAs are expected to provide correct information. However, there are no security problems resulting from a UA inserting incorrect information. Networks providing services based on the information carried in the P-Access-Network-Info header will therefore need to trust the UA sending the information. A rogue UA sending false access network information will do no more harm than to restrict the user from using certain services.
SIP-прокси, предоставляющий пользователю услуги, использует информацию, содержащуюся в этом заголовке, для предоставления дополнительных услуг, и ожидается, что UA предоставляет правильную информацию. Однако нет проблем безопасности, возникающих из-за вставки UA неверной информации. Поэтому сети, предоставляющие услуги на основе информации, содержащейся в заголовке P-Access-Network-Info, должны доверять UA, отправляющему информацию. Недобросовестный UA, отправляющий ложную информацию о сети доступа, причинит не больше вреда, чем ограничение пользователя в использовании определённых услуг.
The mechanism provided in this document is designed primarily for private systems like 3GPP. Most security requirements are met by way of private standardized solutions.
Механизм, предоставленный в настоящем документе, разработан в первую очередь для частных систем, таких как 3GPP. Большинство требований безопасности удовлетворяются посредством частных стандартизованных решений.
For instance, 3GPP will use the P-Access-Network-Info header to carry relatively sensitive information like the cell ID. Therefore the information MUST NOT be sent outside of the 3GPP domain.
Например, 3GPP будет использовать заголовок P-Access-Network-Info для передачи относительно чувствительной информации, такой как идентификатор ячейки. Поэтому информация НЕ ДОЛЖНА отправляться за пределы домена 3GPP.
The UA is aware - if it is a 3GPP UA - that it is operating within a trusted domain.
UA знает — если это UA 3GPP — что он работает в доверенном домене.
The 3GPP UA is aware of whether or not a secure association to the home network domain for transporting SIP signaling, is currently available, and as such the sensitive information carried in the P-Access-Network-Info header SHOULD NOT be sent in any initial unauthenticated and unprotected requests (e.g., REGISTER).
UA 3GPP знает, доступна ли в настоящее время защищённая ассоциация с доменом домашней сети для передачи сигнализации SIP, и потому чувствительная информация, содержащаяся в заголовке P-Access-Network-Info, НЕ СЛЕДУЕТ включать в любые начальные неаутентифицированные и незащищённые запросы (например, REGISTER).
Any UA that is using this extension and is not part of a private trusted domain should not consider the mechanism as secure and as such SHOULD NOT send sensitive information in the P-Access-Network-Info header. Any proxy that is operating in a private trust domain where the P-Access-Network-Info header is supported is required to delete the header, if it is present, from any message prior to forwarding it outside of the trusted domain.
Любой UA, использующий это расширение и не являющийся частью частного доверенного домена, не должен считать механизм защищённым и потому НЕ СЛЕДУЕТ отправлять чувствительную информацию в заголовке P-Access-Network-Info. Любой прокси, работающий в частном доверенном домене, где поддерживается заголовок P-Access-Network-Info, обязан удалить заголовок, если он присутствует, из любого сообщения перед его пересылкой за пределы доверенного домена.
Therefore, a network that requires its UA to send information in the P-Access-Network-Info header must ensure that either that information is not of a sensitive nature or that the information is not sent outside of the trust domain.
Поэтому сеть, требующая от своего UA отправки информации в заголовке P-Access-Network-Info, должна обеспечить, чтобы эта информация либо не была чувствительной по своей природе, либо не отправлялась за пределы доверенного домена.
A proxy receiving a message containing the P-Access-Network-Info header from a non-trusted entity is not able to guarantee the validity of the contents.
Прокси, получающий сообщение, содержащее заголовок P-Access-Network-Info, от недоверенного объекта, не может гарантировать достоверность содержимого.
6.5. P-Charging-Function-Addresses
6.5. P-Charging-Function-Addresses
It is expected as normal behavior that proxies within a closed network will modify the values of the P-Charging-Function-Addresses and insert it into a SIP request or response. However, these proxies that share this information MUST have a trust relationship.
Ожидается как нормальное поведение, что прокси в пределах закрытой сети будут изменять значения P-Charging-Function-Addresses и вставлять его в запрос или ответ SIP. Однако эти прокси, совместно использующие эту информацию, ДОЛЖНЫ иметь доверительные отношения.
If an untrusted entity were inserted between trusted entities, it could potentially substitute a different charging function address. Therefore, an integrity protection mechanism such as IPsec or other available mechanisms MUST be applied in order to prevent such attacks. Since each trusted proxy may need to view or modify the values in the P-Charging-Function-Addresses header, the protection should be applied on a hop-by-hop basis.
Если между доверенными объектами был бы вставлен недоверенный объект, он мог бы потенциально подменить адрес функции тарификации. Поэтому ДОЛЖЕН применяться механизм защиты целостности, такой как IPsec или иные доступные механизмы, чтобы предотвратить такие атаки. Поскольку каждому доверенному прокси может понадобиться просмотреть или изменить значения в заголовке P-Charging-Function-Addresses, защиту следует применять на основе «переход за переходом».

6.6. P-Charging-Vector
