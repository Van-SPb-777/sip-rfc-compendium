Abstract
Аннотация
This document describes an extension to the Session Initiation Protocol (SIP). The purpose of this extension is to provide an extensible framework by which SIP nodes can request notification from remote nodes indicating that certain events have occurred.
Настоящий документ описывает расширение протокола инициирования сессий (SIP). Цель этого расширения — обеспечить основу, посредством которой SIP-элементы могут подписываться на события и получать уведомления о них.
Concrete uses of the mechanism described in this document may be standardized in the future.
Конкретные применения механизма, описанного в настоящем документе, могут быть стандартизованы в будущем.

1. Introduction
1. Введение
The ability to request asynchronous notification of events proves useful in many types of SIP services for which cooperation between end-nodes is required. Examples of such services include automatic callback services (based on terminal state events), buddy lists (based on user presence events), message waiting indications (based on mailbox state change events), and PSTN and Internet Internetworking (PINT) [2] status (based on call state events).
Возможность запрашивать асинхронное уведомление о событиях оказывается полезной во многих типах служб SIP, для которых требуется взаимодействие между оконечными узлами. Примеры таких служб включают службы автоматического обратного вызова (на основе событий состояния терминала), списки собеседников (на основе событий присутствия пользователя), индикацию ожидающих сообщений (на основе событий изменения состояния почтового ящика) и статус взаимодействия ТфОП и Интернета (PINT) [2] (на основе событий состояния вызова).
The methods described in this document provide a framework by which notification of these events can be ordered.
Описанные в настоящем документе методы обеспечивают основу, с помощью которой уведомления об этих событиях могут быть упорядочены.
The event notification mechanisms defined herein are NOT intended to be a general-purpose infrastructure for all classes of event subscription and notification. Meeting requirements for the general problem set of subscription and notification is far too complex for a single protocol. Our goal is to provide a SIP-specific framework for event notification which is not so complex as to be unusable for simple features, but which is still flexible enough to provide powerful services. Note, however, that event packages based on this framework may define arbitrarily elaborate rules which govern the subscription and notification for the events or classes of events they describe.
Определённые здесь механизмы уведомления о событиях НЕ предназначены быть инфраструктурой общего назначения для всех классов подписки на события и уведомления о них. Удовлетворение требований общего набора задач подписки и уведомления слишком сложно для одного протокола. Наша цель — обеспечить специфичную для SIP основу для уведомления о событиях, не настолько сложную, чтобы быть непригодной для простых возможностей, но при этом достаточно гибкую, чтобы предоставлять мощные службы. Обратите внимание, однако, что пакеты событий, основанные на этой структуре, могут определять сколь угодно сложные правила, управляющие подпиской и уведомлением для событий или классов событий, которые они описывают.
This document does not describe an extension which may be used directly; it must be extended by other documents (herein referred to as "event packages"). In object-oriented design terminology, it may be thought of as an abstract base class which must be derived into an instantiatable class by further extensions. Guidelines for creating these extensions are described in section 4.
Настоящий документ не описывает расширение, которое можно использовать напрямую; оно должно быть расширено другими документами (здесь называемыми «пакетами событий»). В терминологии объектно-ориентированного проектирования его можно рассматривать как абстрактный базовый класс, который должен быть превращён в экземплярный класс дальнейшими расширениями. Руководящие принципы создания этих расширений описаны в разделе 4.
1.1. Overview of Operation
1.1. Обзор работы
The general concept is that entities in the network can subscribe to resource or call state for various resources or calls in the network, and those entities (or entities acting on their behalf) can send notifications when those states change.
Общая концепция состоит в том, что объекты в сети могут подписываться на состояние ресурса или вызова для различных ресурсов или вызовов в сети, и эти объекты (или объекты, действующие от их имени) могут отправлять уведомления, когда эти состояния изменяются.
A typical flow of messages would be:
Типичный поток сообщений выглядит так:
Subscriber Notifier
Подписчик — Уведомитель
|-----SUBSCRIBE---->| Request state subscription |<-------200--------| Acknowledge subscription |<------NOTIFY----- | Return current state information |--------200------->| |<------NOTIFY----- | Return current state information |--------200------->|
|-----SUBSCRIBE---->| Request state subscription |<-------200--------| Acknowledge subscription |<------NOTIFY----- | Return current state information |--------200------->| |<------NOTIFY----- | Return current state information |--------200------->|
Subscriptions are expired and must be refreshed by subsequent SUBSCRIBE messages.
Подписки истекают по времени и должны возобновляться последующими сообщениями SUBSCRIBE.

2. Definitions
2. Определения
Event Package: An event package is an additional specification which defines a set of state information to be reported by a notifier to a subscriber. Event packages also define further syntax and semantics based on the framework defined by this document required to convey such state information.
Пакет событий: пакет событий — это дополнительная спецификация, которая определяет набор информации о состоянии, подлежащей передаче уведомителем подписчику. Пакеты событий также определяют дополнительный синтаксис и семантику на основе структуры, определённой настоящим документом, необходимые для передачи такой информации о состоянии.
Event Template-Package: An event template-package is a special kind of event package which defines a set of states which may be applied to all possible event packages, including itself.
Шаблонный пакет событий: шаблонный пакет событий — это особый вид пакета событий, который определяет набор состояний, применимых ко всем возможным пакетам событий, включая себя самого.
Notification: Notification is the act of a notifier sending a NOTIFY message to a subscriber to inform the subscriber of the state of a resource.
Уведомление: уведомление — это действие уведомителя по отправке сообщения NOTIFY подписчику для информирования подписчика о состоянии ресурса.
Notifier: A notifier is a user agent which generates NOTIFY requests for the purpose of notifying subscribers of the state of a resource. Notifiers typically also accept SUBSCRIBE requests to create subscriptions.
Уведомитель: уведомитель — это пользовательский агент, который формирует запросы NOTIFY с целью уведомления подписчиков о состоянии ресурса. Уведомители, как правило, также принимают запросы SUBSCRIBE для создания подписок.
State Agent: A state agent is a notifier which publishes state information on behalf of a resource; in order to do so, it may need to gather such state information from multiple sources. State agents always have complete state information for the resource for which they are creating notifications.
Агент состояния: агент состояния — это уведомитель, который публикует информацию о состоянии от имени ресурса; чтобы делать это, ему может потребоваться собирать такую информацию о состоянии из нескольких источников. Агенты состояния всегда обладают полной информацией о состоянии ресурса, для которого они создают уведомления.
Subscriber: A subscriber is a user agent which receives NOTIFY requests from notifiers; these NOTIFY requests contain information about the state of a resource in which the subscriber is interested. Subscribers typically also generate SUBSCRIBE requests and send them to notifiers to create subscriptions.
Подписчик: подписчик — это пользовательский агент, который получает запросы NOTIFY от уведомителей; эти запросы NOTIFY содержат информацию о состоянии ресурса, в котором заинтересован подписчик. Подписчики, как правило, также формируют запросы SUBSCRIBE и отправляют их уведомителям для создания подписок.
Subscription: A subscription is a set of application state associated with a dialog. This application state includes a pointer to the associated dialog, the event package name, and possibly an identification token. Event packages will define additional subscription state information. By definition, subscriptions exist in both a subscriber and a notifier.
Подписка: подписка — это набор состояния приложения, связанного с диалогом. Это состояние приложения включает указатель на связанный диалог, имя пакета событий и, возможно, идентификационный токен. Пакеты событий будут определять дополнительную информацию о состоянии подписки. По определению подписки существуют как у подписчика, так и у уведомителя.
Subscription Migration: Subscription migration is the act of moving a subscription from one notifier to another notifier.
Миграция подписки: миграция подписки — это действие по перемещению подписки от одного уведомителя к другому уведомителю.
3. Node Behavior
3. Поведение узла
3.1. Description of SUBSCRIBE Behavior
3.1. Описание поведения SUBSCRIBE
The SUBSCRIBE method is used to request current state and state updates from a remote node.
Метод SUBSCRIBE используется для запроса текущего состояния и обновлений состояния от удалённого узла.
3.1.1. Subscription Duration
3.1.1. Длительность подписки
SUBSCRIBE requests SHOULD contain an "Expires" header (defined in SIP [1]). This expires value indicates the duration of the subscription. In order to keep subscriptions effective beyond the duration communicated in the "Expires" header, subscribers need to refresh subscriptions on a periodic basis using a new SUBSCRIBE message on the same dialog as defined in SIP [1].
Запросы SUBSCRIBE СЛЕДУЕТ содержать заголовок «Expires» (определён в SIP [1]). Это значение времени истечения указывает длительность подписки. Чтобы сохранять подписки действующими за пределами длительности, указанной в заголовке «Expires», подписчикам необходимо периодически возобновлять подписки с использованием нового сообщения SUBSCRIBE в том же диалоге, как определено в SIP [1].
If no "Expires" header is present in a SUBSCRIBE request, the implied default is defined by the event package being used.
Если заголовок «Expires» отсутствует в запросе SUBSCRIBE, подразумеваемое значение по умолчанию определяется используемым пакетом событий.
200-class responses to SUBSCRIBE requests also MUST contain an "Expires" header. The period of time in the response MAY be shorter but MUST NOT be longer than specified in the request. The period of time in the response is the one which defines the duration of the subscription.
Ответы класса 200 на запросы SUBSCRIBE также ДОЛЖНЫ содержать заголовок «Expires». Период времени в ответе МОЖЕТ быть короче, но НЕ ДОЛЖЕН быть длиннее указанного в запросе. Именно период времени в ответе определяет длительность подписки.
An "expires" parameter on the "Contact" header has no semantics for SUBSCRIBE and is explicitly not equivalent to an "Expires" header in a SUBSCRIBE request or response.
Параметр «expires» в заголовке «Contact» не имеет семантики для SUBSCRIBE и явно не эквивалентен заголовку «Expires» в запросе или ответе SUBSCRIBE.
A natural consequence of this scheme is that a SUBSCRIBE with an "Expires" of 0 constitutes a request to unsubscribe from an event.
Естественным следствием этой схемы является то, что SUBSCRIBE со значением «Expires», равным 0, представляет собой запрос на отмену подписки на событие.
In addition to being a request to unsubscribe, a SUBSCRIBE message with "Expires" of 0 also causes a fetch of state; see section 3.3.6.
Помимо того что это запрос на отмену подписки, сообщение SUBSCRIBE со значением «Expires», равным 0, также вызывает выборку состояния; см. раздел 3.3.6.
Notifiers may also wish to cancel subscriptions to events; this is useful, for example, when the resource to which a subscription refers is no longer available. Further details on this mechanism are discussed in section 3.2.2.
Уведомители также могут пожелать отменять подписки на события; это полезно, например, когда ресурс, на который ссылается подписка, больше недоступен. Дополнительные подробности этого механизма обсуждаются в разделе 3.2.2.
3.1.2. Identification of Subscribed Events and Event Classes
3.1.2. Идентификация подписанных событий и классов событий
Identification of events is provided by three pieces of information: Request URI, Event Type, and (optionally) message body. The Request URI of a SUBSCRIBE request, most importantly, contains enough information to route the request to the appropriate entity per the request routing procedures outlined in SIP [1]. It also contains enough information to identify the resource for which event notification is desired, but not necessarily enough information to uniquely identify the nature of the event (e.g., "sip:adam@dynamicsoft.com" would be an appropriate URI to subscribe to for my presence state; it would also be an appropriate URI to subscribe to the state of my voice mailbox).
Идентификация событий обеспечивается тремя частями информации: Request URI, типом события и (необязательно) телом сообщения. Request URI запроса SUBSCRIBE, что наиболее важно, содержит достаточно информации для маршрутизации запроса к соответствующему объекту согласно процедурам маршрутизации запросов, изложенным в SIP [1]. Он также содержит достаточно информации для идентификации ресурса, для которого желательно уведомление о событиях, но не обязательно достаточно информации для однозначной идентификации природы события (например, «sip:adam@dynamicsoft.com» был бы подходящим URI для подписки на моё состояние присутствия; он также был бы подходящим URI для подписки на состояние моего голосового почтового ящика).
Subscribers MUST include exactly one "Event" header in SUBSCRIBE requests, indicating to which event or class of events they are subscribing. The "Event" header will contain a token which indicates the type of state for which a subscription is being requested. This token will be registered with the IANA and will correspond to an event package which further describes the semantics of the event or event class. The "Event" header MAY also contain an "id" parameter. This "id" parameter, if present, contains an opaque token which identifies the specific subscription within a dialog. An "id" parameter is only valid within the scope of a single dialog.
Подписчики ДОЛЖНЫ включать ровно один заголовок «Event» в запросы SUBSCRIBE, указывая, на какое событие или класс событий они подписываются. Заголовок «Event» будет содержать токен, который указывает тип состояния, для которого запрашивается подписка. Этот токен будет зарегистрирован в IANA и будет соответствовать пакету событий, который дополнительно описывает семантику события или класса событий. Заголовок «Event» также МОЖЕТ содержать параметр «id». Этот параметр «id», если он присутствует, содержит непрозрачный токен, который идентифицирует конкретную подписку в пределах диалога. Параметр «id» действителен только в пределах одного диалога.
If the event package to which the event token corresponds defines behavior associated with the body of its SUBSCRIBE requests, those semantics apply.
Если пакет событий, которому соответствует токен события, определяет поведение, связанное с телом своих запросов SUBSCRIBE, эта семантика применяется.
Event packages may also define parameters for the Event header; if they do so, they must define the semantics for such parameters.
Пакеты событий также могут определять параметры для заголовка Event; если они это делают, они должны определить семантику для таких параметров.
3.1.3. Additional SUBSCRIBE Header Values
3.1.3. Дополнительные значения заголовков SUBSCRIBE
Because SUBSCRIBE requests create a dialog as defined in SIP [1], they MAY contain an "Accept" header. This header, if present, indicates the body formats allowed in subsequent NOTIFY requests. Event packages MUST define the behavior for SUBSCRIBE requests without "Accept" headers; usually, this will connote a single, default body type.
Поскольку запросы SUBSCRIBE создают диалог, как определено в SIP [1], они МОГУТ содержать заголовок «Accept». Этот заголовок, если он присутствует, указывает форматы тела, допустимые в последующих запросах NOTIFY. Пакеты событий ДОЛЖНЫ определять поведение для запросов SUBSCRIBE без заголовков «Accept»; обычно это будет означать единственный тип тела по умолчанию.
Header values not described in this document are to be interpreted as described in SIP [1].
Значения заголовков, не описанные в настоящем документе, следует толковать так, как описано в SIP [1].
3.1.4. Subscriber SUBSCRIBE Behavior
3.1.4. Поведение подписчика при SUBSCRIBE
3.1.4.1. Requesting a Subscription
3.1.4.1. Запрос подписки
SUBSCRIBE is a dialog-creating method, as described in SIP [1].
SUBSCRIBE — это метод, создающий диалог, как описано в SIP [1].
When a subscriber wishes to subscribe to a particular state for a resource, it forms a SUBSCRIBE message. If the initial SUBSCRIBE represents a request outside of a dialog (as it typically will), its construction follows the procedures outlined in SIP [1] for UAC request generation outside of a dialog.
Когда подписчик желает подписаться на конкретное состояние ресурса, он формирует сообщение SUBSCRIBE. Если начальный SUBSCRIBE представляет собой запрос вне диалога (как это обычно и будет), его построение следует процедурам, изложенным в SIP [1] для формирования запросов UAC вне диалога.
This SUBSCRIBE request will be confirmed with a final response. 200-class responses indicate that the subscription has been accepted, and that a NOTIFY will be sent immediately. A 200 response indicates that the subscription has been accepted and that the user is authorized to subscribe to the requested resource. A 202 response merely indicates that the subscription has been understood, and that authorization may or may not have been granted.
Этот запрос SUBSCRIBE будет подтверждён окончательным ответом. Ответы класса 200 указывают, что подписка принята и что NOTIFY будет отправлен немедленно. Ответ 200 указывает, что подписка принята и что пользователь имеет право подписаться на запрошенный ресурс. Ответ 202 лишь указывает, что подписка понята и что авторизация могла быть предоставлена, а могла и не быть.
The "Expires" header in a 200-class response to SUBSCRIBE indicates the actual duration for which the subscription will remain active (unless refreshed).
Заголовок «Expires» в ответе класса 200 на SUBSCRIBE указывает фактическую длительность, в течение которой подписка будет оставаться активной (если она не возобновлена).
Non-200 class final responses indicate that no subscription or dialog has been created, and no subsequent NOTIFY message will be sent. All non-200 class responses (with the exception of "489", described herein) have the same meanings and handling as described in SIP [1].
Окончательные ответы не класса 200 указывают, что ни подписка, ни диалог не созданы и что последующее сообщение NOTIFY не будет отправлено. Все ответы не класса 200 (за исключением «489», описанного здесь) имеют те же значения и обработку, что описаны в SIP [1].
A SUBSCRIBE request MAY include an "id" parameter in its "Event" header to allow differentiation between multiple subscriptions in the same dialog.
Запрос SUBSCRIBE МОЖЕТ включать параметр «id» в своём заголовке «Event», чтобы позволить различать несколько подписок в одном диалоге.
3.1.4.2. Refreshing of Subscriptions
3.1.4.2. Возобновление подписок
At any time before a subscription expires, the subscriber may refresh the timer on such a subscription by sending another SUBSCRIBE request on the same dialog as the existing subscription, and with the same "Event" header "id" parameter (if one was present in the initial subscription). The handling for such a request is the same as for the initial creation of a subscription except as described below.
В любой момент до истечения подписки подписчик может возобновить таймер такой подписки, отправив другой запрос SUBSCRIBE в том же диалоге, что и существующая подписка, с тем же параметром «id» заголовка «Event» (если он присутствовал в начальной подписке). Обработка такого запроса такая же, как при начальном создании подписки, за исключением описанного ниже.
If the initial SUBSCRIBE message contained an "id" parameter on the "Event" header, then refreshes of the subscription must also contain an identical "id" parameter; they will otherwise be considered new subscriptions in an existing dialog.
Если начальное сообщение SUBSCRIBE содержало параметр «id» в заголовке «Event», то возобновления подписки также должны содержать идентичный параметр «id»; иначе они будут считаться новыми подписками в существующем диалоге.
If a SUBSCRIBE request to refresh a subscription receives a "481" response, this indicates that the subscription has been terminated and that the subscriber did not receive notification of this fact. In this case, the subscriber should consider the subscription invalid. If the subscriber wishes to re-subscribe to the state, he does so by composing an unrelated initial SUBSCRIBE request with a freshly-generated Call-ID and a new, unique "From" tag (see section 3.1.4.1.) If a SUBSCRIBE request to refresh a subscription fails with a non-481 response, the original subscription is still considered valid for the duration of the most recently known "Expires" value as negotiated by SUBSCRIBE and its response, or as communicated by NOTIFY in the "Subscription-State" header "expires" parameter.
Если запрос SUBSCRIBE на возобновление подписки получает ответ «481», это указывает, что подписка была прекращена и что подписчик не получил уведомления об этом факте. В этом случае подписчику следует считать подписку недействительной. Если подписчик желает повторно подписаться на состояние, он делает это, составляя несвязанный начальный запрос SUBSCRIBE со свежесгенерированным Call-ID и новым уникальным тегом «From» (см. раздел 3.1.4.1). Если запрос SUBSCRIBE на возобновление подписки завершается ошибкой с ответом, отличным от 481, исходная подписка всё ещё считается действительной в течение длительности последнего известного значения «Expires», согласованного посредством SUBSCRIBE и его ответа, либо переданного посредством NOTIFY в параметре «expires» заголовка «Subscription-State».
Note that many such errors indicate that there may be a problem with the network or the notifier such that no further NOTIFY messages will be received.
Обратите внимание, что многие такие ошибки указывают на возможную проблему в сети или у уведомителя, так что дальнейшие сообщения NOTIFY получены не будут.
3.1.4.3. Unsubscribing
3.1.4.3. Отмена подписки
Unsubscribing is handled in the same way as refreshing of a subscription, with the "Expires" header set to "0". Note that a successful unsubscription will also trigger a final NOTIFY message.
Отмена подписки обрабатывается так же, как возобновление подписки, с заголовком «Expires», установленным в «0». Обратите внимание, что успешная отмена подписки также вызовет финальное сообщение NOTIFY.
3.1.4.4. Confirmation of Subscription Creation
3.1.4.4. Подтверждение создания подписки
The subscriber can expect to receive a NOTIFY message from each node which has processed a successful subscription or subscription refresh. Until the first NOTIFY message arrives, the subscriber should consider the state of the subscribed resource to be in a neutral state. Documents which define new event packages MUST define this "neutral state" in such a way that makes sense for their application (see section 4.4.7.).
Подписчик может ожидать получения сообщения NOTIFY от каждого узла, который обработал успешную подписку или возобновление подписки. До прибытия первого сообщения NOTIFY подписчику следует считать состояние подписанного ресурса находящимся в нейтральном состоянии. Документы, определяющие новые пакеты событий, ДОЛЖНЫ определить это «нейтральное состояние» так, чтобы оно имело смысл для их приложения (см. раздел 4.4.7).
Due to the potential for both out-of-order messages and forking, the subscriber MUST be prepared to receive NOTIFY messages before the SUBSCRIBE transaction has completed.
Из-за возможности как сообщений не по порядку, так и ветвления (forking) подписчик ДОЛЖЕН быть готов получать сообщения NOTIFY до завершения транзакции SUBSCRIBE.
Except as noted above, processing of this NOTIFY is the same as in section 3.2.4.
За исключением отмеченного выше, обработка этого NOTIFY такая же, как в разделе 3.2.4.
3.1.5. Proxy SUBSCRIBE Behavior
3.1.5. Поведение прокси при SUBSCRIBE
Proxies need no additional behavior beyond that described in SIP [1] to support SUBSCRIBE. If a proxy wishes to see all of the SUBSCRIBE and NOTIFY requests for a given dialog, it MUST record-route the initial SUBSCRIBE and any dialog-establishing NOTIFY requests. Such proxies SHOULD also record-route all other SUBSCRIBE and NOTIFY requests.
Прокси не требуют дополнительного поведения сверх описанного в SIP [1] для поддержки SUBSCRIBE. Если прокси желает видеть все запросы SUBSCRIBE и NOTIFY для данного диалога, он ДОЛЖЕН выполнить record-route начального SUBSCRIBE и любых запросов NOTIFY, устанавливающих диалог. Таким прокси также СЛЕДУЕТ выполнять record-route всех остальных запросов SUBSCRIBE и NOTIFY.
Note that subscribers and notifiers may elect to use S/MIME encryption of SUBSCRIBE and NOTIFY requests; consequently, proxies cannot rely on being able to access any information that is not explicitly required to be proxy-readable by SIP [1].
Обратите внимание, что подписчики и уведомители могут выбрать использование шифрования S/MIME для запросов SUBSCRIBE и NOTIFY; следовательно, прокси не могут рассчитывать на доступ к любой информации, которая не требуется явно для чтения прокси согласно SIP [1].
3.1.6. Notifier SUBSCRIBE Behavior
3.1.6. Поведение уведомителя при SUBSCRIBE
3.1.6.1. Initial SUBSCRIBE Transaction Processing
3.1.6.1. Обработка начальной транзакции SUBSCRIBE
In no case should a SUBSCRIBE transaction extend for any longer than the time necessary for automated processing. In particular, notifiers MUST NOT wait for a user response before returning a final response to a SUBSCRIBE request.
Ни в каком случае транзакция SUBSCRIBE не должна продолжаться дольше времени, необходимого для автоматической обработки. В частности, уведомители НЕ ДОЛЖНЫ ждать ответа пользователя перед возвратом окончательного ответа на запрос SUBSCRIBE.
This requirement is imposed primarily to prevent the non-INVITE transaction timeout timer F (see [1]) from firing during the SUBSCRIBE transaction, since interaction with a user would often exceed 64*T1 seconds.
This requirement is imposed primarily to prevent the non-INVITE transaction timeout timer F (see [1]) from firing during the SUBSCRIBE transaction, since interaction with a user would often exceed 64*T1 seconds.
The notifier SHOULD check that the event package specified in the "Event" header is understood. If not, the notifier SHOULD return a "489 Bad Event" response to indicate that the specified event/event class is not understood.
Уведомителю СЛЕДУЕТ проверить, что пакет событий, указанный в заголовке «Event», понят. Если нет, уведомителю СЛЕДУЕТ вернуть ответ «489 Bad Event», указывающий, что указанное событие/класс событий не понят.
The notifier SHOULD also perform any necessary authentication and authorization per its local policy. See section 3.1.6.3.
Уведомителю СЛЕДУЕТ также выполнить любую необходимую аутентификацию и авторизацию согласно своей локальной политике. См. раздел 3.1.6.3.
The notifier MAY also check that the duration in the "Expires" header is not too small. If and only if the expiration interval is greater than zero AND smaller than one hour AND less than a notifier- configured minimum, the notifier MAY return a "423 Interval too small" error which contains a "Min-Expires" header field. The "Min- Expires" header field is described in SIP [1].
Уведомитель МОЖЕТ также проверить, что длительность в заголовке «Expires» не слишком мала. Если и только если интервал истечения больше нуля И меньше одного часа И меньше настроенного уведомителем минимума, уведомитель МОЖЕТ вернуть ошибку «423 Interval too small», содержащую поле заголовка «Min-Expires». Поле заголовка «Min-Expires» описано в SIP [1].
If the notifier is able to immediately determine that it understands the event package, that the authenticated subscriber is authorized to subscribe, and that there are no other barriers to creating the subscription, it creates the subscription and a dialog (if necessary), and returns a "200 OK" response (unless doing so would reveal authorization policy in an undesirable fashion; see section 5.2.).
Если уведомитель способен немедленно определить, что он понимает пакет событий, что аутентифицированный подписчик авторизован подписываться и что нет иных препятствий для создания подписки, он создаёт подписку и диалог (при необходимости) и возвращает ответ «200 OK» (если только это не раскроет политику авторизации нежелательным образом; см. раздел 5.2).
If the notifier cannot immediately create the subscription (e.g., it needs to wait for user input for authorization, or is acting for another node which is not currently reachable), or wishes to mask authorization policy, it will return a "202 Accepted" response. This response indicates that the request has been received and understood, but does not necessarily imply that the subscription has been authorized yet.
Если уведомитель не может немедленно создать подписку (например, ему нужно ждать ввода пользователя для авторизации или он действует от имени другого узла, который в настоящее время недоступен), либо желает скрыть политику авторизации, он вернёт ответ «202 Accepted». Этот ответ указывает, что запрос получен и понят, но не обязательно подразумевает, что подписка уже авторизована.
When a subscription is created in the notifier, it stores the event package name and the "Event" header "id" parameter (if present) as part of the subscription information. The "Expires" values present in SUBSCRIBE 200-class responses behave in the same way as they do in REGISTER responses: the server MAY shorten the interval, but MUST NOT lengthen it.
Когда подписка создаётся в уведомителе, он сохраняет имя пакета событий и параметр «id» заголовка «Event» (если он присутствует) как часть информации о подписке. Значения «Expires», присутствующие в ответах класса 200 на SUBSCRIBE, ведут себя так же, как в ответах REGISTER: сервер МОЖЕТ сократить интервал, но НЕ ДОЛЖЕН его удлинять.
If the duration specified in a SUBSCRIBE message is unacceptably short, the notifier may be able to send a 423 response, as described earlier in this section.
Если длительность, указанная в сообщении SUBSCRIBE, неприемлемо мала, уведомитель может быть в состоянии отправить ответ 423, как описано ранее в этом разделе.
200-class responses to SUBSCRIBE requests will not generally contain any useful information beyond subscription duration; their primary purpose is to serve as a reliability mechanism. State information will be communicated via a subsequent NOTIFY request from the notifier.
Ответы класса 200 на запросы SUBSCRIBE, как правило, не будут содержать никакой полезной информации помимо длительности подписки; их основное назначение — служить механизмом надёжности. Информация о состоянии будет передаваться посредством последующего запроса NOTIFY от уведомителя.
The other response codes defined in SIP [1] may be used in response to SUBSCRIBE requests, as appropriate.
Другие коды ответов, определённые в SIP [1], могут использоваться в ответ на запросы SUBSCRIBE по обстоятельствам.
3.1.6.2. Confirmation of Subscription Creation/Refreshing
3.1.6.2. Подтверждение создания/возобновления подписки
Upon successfully accepting or refreshing a subscription, notifiers MUST send a NOTIFY message immediately to communicate the current resource state to the subscriber. This NOTIFY message is sent on the same dialog as created by the SUBSCRIBE response. If the resource has no meaningful state at the time that the SUBSCRIBE message is processed, this NOTIFY message MAY contain an empty or neutral body. See section 3.2.2. for further details on NOTIFY message generation.
После успешного принятия или возобновления подписки уведомители ДОЛЖНЫ немедленно отправить сообщение NOTIFY для передачи текущего состояния ресурса подписчику. Это сообщение NOTIFY отправляется в том же диалоге, что создан ответом на SUBSCRIBE. Если у ресурса нет значимого состояния на момент обработки сообщения SUBSCRIBE, это сообщение NOTIFY МОЖЕТ содержать пустое или нейтральное тело. Дополнительные подробности формирования сообщения NOTIFY см. в разделе 3.2.2.
Note that a NOTIFY message is always sent immediately after any 200- class response to a SUBSCRIBE request, regardless of whether the subscription has already been authorized.
Обратите внимание, что сообщение NOTIFY всегда отправляется немедленно после любого ответа класса 200 на запрос SUBSCRIBE, независимо от того, была ли подписка уже авторизована.
3.1.6.3. Authentication/Authorization of SUBSCRIBE requests
3.1.6.3. Аутентификация/авторизация запросов SUBSCRIBE
Privacy concerns may require that notifiers apply policy to determine whether a particular subscriber is authorized to subscribe to a certain set of events. Such policy may be defined by mechanisms such as access control lists or real-time interaction with a user. In general, authorization of subscribers prior to authentication is not particularly useful.
Соображения конфиденциальности могут требовать, чтобы уведомители применяли политику для определения того, авторизован ли конкретный подписчик подписываться на определённый набор событий. Такая политика может быть определена такими механизмами, как списки управления доступом или взаимодействие с пользователем в реальном времени. В общем случае авторизация подписчиков до аутентификации не особенно полезна.
SIP authentication mechanisms are discussed in SIP [1]. Note that, even if the notifier node typically acts as a proxy, authentication for SUBSCRIBE requests will always be performed via a "401" response, not a "407;" notifiers always act as a user agents when accepting subscriptions and sending notifications. Of course, when acting as a proxy, a node will perform normal proxy authentication (using 407). The foregoing explanation is a reminder that notifiers are always UAs, and as such perform UA authentication.
Механизмы аутентификации SIP обсуждаются в SIP [1]. Обратите внимание, что даже если узел-уведомитель обычно действует как прокси, аутентификация для запросов SUBSCRIBE всегда будет выполняться посредством ответа «401», а не «407»; уведомители всегда действуют как пользовательские агенты при принятии подписок и отправке уведомлений. Разумеется, действуя как прокси, узел будет выполнять обычную аутентификацию прокси (используя 407). Вышесказанное является напоминанием о том, что уведомители всегда являются UA и, как таковые, выполняют аутентификацию UA.
If authorization fails based on an access list or some other automated mechanism (i.e., it can be automatically authoritatively determined that the subscriber is not authorized to subscribe), the notifier SHOULD reply to the request with a "403 Forbidden" or "603 Decline" response, unless doing so might reveal information that should stay private; see section 5.2.
Если авторизация завершается неудачей на основе списка доступа или какого-либо иного автоматического механизма (то есть можно автоматически авторитетно определить, что подписчик не авторизован подписываться), уведомителю СЛЕДУЕТ ответить на запрос ответом «403 Forbidden» или «603 Decline», если только это не может раскрыть информацию, которая должна оставаться конфиденциальной; см. раздел 5.2.
If the notifier owner is interactively queried to determine whether a subscription is allowed, a "202 Accept" response is returned immediately. Note that a NOTIFY message is still formed and sent under these circumstances, as described in the previous section.
Если владелец уведомителя опрашивается в интерактивном режиме для определения, разрешена ли подписка, немедленно возвращается ответ «202 Accept». Обратите внимание, что при этих обстоятельствах сообщение NOTIFY всё равно формируется и отправляется, как описано в предыдущем разделе.
If subscription authorization was delayed and the notifier wishes to convey that such authorization has been declined, it may do so by sending a NOTIFY message containing a "Subscription-State" header with a value of "terminated" and a reason parameter of "rejected".
Если авторизация подписки была отложена и уведомитель желает сообщить, что такая авторизация была отклонена, он может сделать это, отправив сообщение NOTIFY, содержащее заголовок «Subscription-State» со значением «terminated» и параметром reason со значением «rejected».
3.1.6.4. Refreshing of Subscriptions
3.1.6.4. Возобновление подписок
When a notifier receives a subscription refresh, assuming that the subscriber is still authorized, the notifier updates the expiration time for the subscription. As with the initial subscription, the server MAY shorten the amount of time until expiration, but MUST NOT increase it. The final expiration time is placed in the "Expires" header in the response. If the duration specified in a SUBSCRIBE message is unacceptably short, the notifier SHOULD respond with a "423 Subscription Too Brief" message.
Когда уведомитель получает возобновление подписки, предполагая, что подписчик по-прежнему авторизован, уведомитель обновляет время истечения подписки. Как и при начальной подписке, сервер МОЖЕТ сократить время до истечения, но НЕ ДОЛЖЕН его увеличивать. Окончательное время истечения помещается в заголовок «Expires» ответа. Если длительность, указанная в сообщении SUBSCRIBE, неприемлемо мала, уведомителю СЛЕДУЕТ ответить сообщением «423 Subscription Too Brief».
If no refresh for a notification address is received before its expiration time, the subscription is removed. When removing a subscription, the notifier SHOULD send a NOTIFY message with a "Subscription-State" value of "terminated" to inform it that the subscription is being removed. If such a message is sent, the "Subscription-State" header SHOULD contain a "reason=timeout" parameter.
Если возобновление для адреса уведомления не получено до времени его истечения, подписка удаляется. При удалении подписки уведомителю СЛЕДУЕТ отправить сообщение NOTIFY со значением «Subscription-State», равным «terminated», чтобы уведомить об удалении подписки. Если такое сообщение отправляется, заголовок «Subscription-State» СЛЕДУЕТ содержать параметр «reason=timeout».
The sending of a NOTIFY when a subscription expires allows the corresponding dialog to be terminated, if appropriate.
Отправка NOTIFY при истечении подписки позволяет завершить соответствующий диалог, если это уместно.
3.2. Description of NOTIFY Behavior
3.2. Описание поведения NOTIFY
NOTIFY messages are sent to inform subscribers of changes in state to which the subscriber has a subscription. Subscriptions are typically put in place using the SUBSCRIBE method; however, it is possible that other means have been used.
Сообщения NOTIFY отправляются для информирования подписчиков об изменениях состояния, на которые у подписчика есть подписка. Подписки, как правило, устанавливаются с использованием метода SUBSCRIBE; однако возможно, что использовались иные средства.
If any non-SUBSCRIBE mechanisms are defined to create subscriptions, it is the responsibility of the parties defining those mechanisms to ensure that correlation of a NOTIFY message to the corresponding subscription is possible. Designers of such mechanisms are also warned to make a distinction between sending a NOTIFY message to a subscriber who is aware of the subscription, and sending a NOTIFY message to an unsuspecting node. The latter behavior is invalid, and MUST receive a "481 Subscription does not exist" response (unless some other 400- or 500-class error code is more applicable), as described in section 3.2.4. In other words, knowledge of a subscription must exist in both the subscriber and the notifier to be valid, even if installed via a non-SUBSCRIBE mechanism.
Если какие-либо механизмы, отличные от SUBSCRIBE, определены для создания подписок, на стороны, определяющие эти механизмы, возлагается ответственность за обеспечение возможности сопоставления сообщения NOTIFY с соответствующей подпиской. Разработчики таких механизмов также предупреждаются о необходимости проводить различие между отправкой сообщения NOTIFY подписчику, который осведомлён о подписке, и отправкой сообщения NOTIFY ничего не подозревающему узлу. Последнее поведение недействительно и ДОЛЖНО получить ответ «481 Subscription does not exist» (если только какой-либо иной код ошибки класса 400 или 500 не более применим), как описано в разделе 3.2.4. Иными словами, знание о подписке должно существовать и у подписчика, и у уведомителя, чтобы она была действительной, даже если она установлена посредством механизма, отличного от SUBSCRIBE.
A NOTIFY does not terminate its corresponding subscription; in other words, a single SUBSCRIBE request may trigger several NOTIFY requests.
NOTIFY не прекращает соответствующую подписку; иными словами, один запрос SUBSCRIBE может вызвать несколько запросов NOTIFY.
3.2.1. Identification of Reported Events, Event Classes, and Current State
3.2.1. Идентификация передаваемых событий, классов событий и текущего
Identification of events being reported in a notification is very similar to that described for subscription to events (see section 3.1.2.).
Идентификация событий, передаваемых в уведомлении, очень похожа на описанную для подписки на события (см. раздел 3.1.2).
As in SUBSCRIBE requests, NOTIFY "Event" headers will contain a single event package name for which a notification is being generated. The package name in the "Event" header MUST match the "Event" header in the corresponding SUBSCRIBE message. If an "id" parameter was present in the SUBSCRIBE message, that "id" parameter MUST also be present in the corresponding NOTIFY messages.
Как и в запросах SUBSCRIBE, заголовки «Event» в NOTIFY будут содержать одно имя пакета событий, для которого формируется уведомление. Имя пакета в заголовке «Event» ДОЛЖНО совпадать с заголовком «Event» в соответствующем сообщении SUBSCRIBE. Если параметр «id» присутствовал в сообщении SUBSCRIBE, этот параметр «id» также ДОЛЖЕН присутствовать в соответствующих сообщениях NOTIFY.
Event packages may define semantics associated with the body of their NOTIFY requests; if they do so, those semantics apply. NOTIFY bodies are expected to provide additional details about the nature of the event which has occurred and the resultant resource state.
Пакеты событий могут определять семантику, связанную с телом их запросов NOTIFY; если они это делают, эта семантика применяется. Тела NOTIFY, как ожидается, предоставят дополнительные подробности о природе произошедшего события и результирующем состоянии ресурса.
When present, the body of the NOTIFY request MUST be formatted into one of the body formats specified in the "Accept" header of the corresponding SUBSCRIBE request. This body will contain either the state of the subscribed resource or a pointer to such state in the form of a URI (see section 4.4.13).
Когда тело присутствует, оно в запросе NOTIFY ДОЛЖНО быть отформатировано в один из форматов тела, указанных в заголовке «Accept» соответствующего запроса SUBSCRIBE. Это тело будет содержать либо состояние подписанного ресурса, либо указатель на такое состояние в форме URI (см. раздел 4.4.13).
3.2.2. Notifier NOTIFY Behavior
3.2.2. Поведение уведомителя при NOTIFY
When a SUBSCRIBE request is answered with a 200-class response, the notifier MUST immediately construct and send a NOTIFY request to the subscriber. When a change in the subscribed state occurs, the notifier SHOULD immediately construct and send a NOTIFY request, subject to authorization, local policy, and throttling considerations.
Когда запрос SUBSCRIBE получает ответ класса 200, уведомитель ДОЛЖЕН немедленно сформировать и отправить запрос NOTIFY подписчику. Когда происходит изменение подписанного состояния, уведомителю СЛЕДУЕТ немедленно сформировать и отправить запрос NOTIFY с учётом авторизации, локальной политики и соображений ограничения частоты.
A NOTIFY request is considered failed if the response times out, or a non-200 class response code is received which has no "Retry-After" header and no implied further action which can be taken to retry the request (e.g., "401 Authorization Required".)
Запрос NOTIFY считается неудавшимся, если ответ истекает по тайм-ауту либо получен код ответа не класса 200, который не имеет заголовка «Retry-After» и не подразумевает дальнейшего действия, которое можно предпринять для повторной попытки запроса (например, «401 Authorization Required»).
If the NOTIFY request fails (as defined above) due to a timeout condition, and the subscription was installed using a soft-state mechanism (such as SUBSCRIBE), the notifier SHOULD remove the subscription.
Если запрос NOTIFY терпит неудачу (как определено выше) из-за условия тайм-аута и подписка была установлена с использованием механизма мягкого состояния (такого как SUBSCRIBE), уведомителю СЛЕДУЕТ удалить подписку.
This behavior prevents unnecessary transmission of state information for subscribers who have crashed or disappeared from the network. Because such transmissions will be sent multiple times, per the retransmission algorithm defined in SIP [1] (instead of the typical single transmission for functioning clients), continuing to service them when no client is available to acknowledge them could place undue strain on a network. Upon client restart or reestablishment of a network connection, it is expected that clients will send SUBSCRIBE messages to refresh potentially stale state information; such messages will re-install subscriptions in all relevant nodes.
Это поведение предотвращает ненужную передачу информации о состоянии для подписчиков, которые аварийно завершились или исчезли из сети. Поскольку такие передачи будут отправляться многократно согласно алгоритму повторной передачи, определённому в SIP [1] (вместо типичной однократной передачи для работающих клиентов), продолжение их обслуживания при отсутствии клиента, способного их подтвердить, могло бы создать неоправданную нагрузку на сеть. При перезапуске клиента или восстановлении сетевого соединения ожидается, что клиенты отправят сообщения SUBSCRIBE для возобновления потенциально устаревшей информации о состоянии; такие сообщения заново установят подписки во всех соответствующих узлах.
If the NOTIFY request fails (as defined above) due to an error response, and the subscription was installed using a soft-state mechanism, the notifier MUST remove the corresponding subscription.
Если запрос NOTIFY терпит неудачу (как определено выше) из-за ответа об ошибке и подписка была установлена с использованием механизма мягкого состояния, уведомитель ДОЛЖЕН удалить соответствующую подписку.
A notify error response would generally indicate that something has gone wrong with the subscriber or with some proxy on the way to the subscriber. If the subscriber is in error, it makes the most sense to allow the subscriber to rectify the situation (by re-subscribing) once the error condition has been handled. If a proxy is in error, the periodic SUBSCRIBE refreshes will re- install subscription state once the network problem has been resolved.
Ответ об ошибке уведомления, как правило, будет указывать, что-то пошло не так с подписчиком или с каким-либо прокси на пути к подписчику. Если ошибка у подписчика, наиболее разумно позволить подписчику исправить ситуацию (путём повторной подписки) после обработки условия ошибки. Если ошибка у прокси, периодические возобновления SUBSCRIBE заново установят состояние подписки после устранения сетевой проблемы.
If a NOTIFY request receives a 481 response, the notifier MUST remove the corresponding subscription even if such subscription was installed by non-SUBSCRIBE means (such as an administrative interface). If the above behavior were not required, subscribers receiving a notify for an unknown subscription would need to send an error status code in response to the NOTIFY and also send a SUBSCRIBE request to remove the subscription. Since this behavior would make subscribers available for use as amplifiers in denial of service attacks, we have instead elected to give the 481 response special meaning: it is used to indicate that a subscription must be cancelled under all circumstances.
Если запрос NOTIFY получает ответ 481, уведомитель ДОЛЖЕН удалить соответствующую подписку, даже если такая подписка была установлена средствами, отличными от SUBSCRIBE (например, административным интерфейсом). Если бы вышеуказанное поведение не требовалось, подписчики, получающие уведомление для неизвестной подписки, должны были бы отправить код состояния ошибки в ответ на NOTIFY, а также отправить запрос SUBSCRIBE для удаления подписки. Поскольку такое поведение сделало бы подписчиков доступными для использования в качестве усилителей в атаках отказа в обслуживании, мы вместо этого решили придать ответу 481 особое значение: он используется для указания, что подписка должна быть отменена при любых обстоятельствах.
NOTIFY requests MUST contain a "Subscription-State" header with a value of "active", "pending", or "terminated". The "active" value indicates that the subscription has been accepted and has been authorized (in most cases; see section 5.2.). The "pending" value indicates that the subscription has been received, but that policy information is insufficient to accept or deny the subscription at this time. The "terminated" value indicates that the subscription is not active.
Запросы NOTIFY ДОЛЖНЫ содержать заголовок «Subscription-State» со значением «active», «pending» или «terminated». Значение «active» указывает, что подписка принята и авторизована (в большинстве случаев; см. раздел 5.2). Значение «pending» указывает, что подписка получена, но информации о политике недостаточно для принятия или отказа в подписке в настоящее время. Значение «terminated» указывает, что подписка не активна.
If the value of the "Subscription-State" header is "active" or "pending", the notifier SHOULD also include in the "Subscription- State" header an "expires" parameter which indicates the time remaining on the subscription. The notifier MAY use this mechanism to shorten a subscription; however, this mechanism MUST NOT be used to lengthen a subscription.
Если значение заголовка «Subscription-State» — «active» или «pending», уведомителю СЛЕДУЕТ также включить в заголовок «Subscription-State» параметр «expires», который указывает оставшееся время подписки. Уведомитель МОЖЕТ использовать этот механизм для сокращения подписки; однако этот механизм НЕ ДОЛЖЕН использоваться для удлинения подписки.
Including expiration information for active and pending subscriptions is useful in case the SUBSCRIBE request forks, since the response to a forked SUBSCRIBE may not be received by the subscriber. Note well that this "expires" value is a parameter on the "Subscription-State" header, NOT an "Expires" header.
Включение информации об истечении для активных и ожидающих подписок полезно на случай, если запрос SUBSCRIBE разветвился, поскольку ответ на разветвлённый SUBSCRIBE может не быть получен подписчиком. Обратите особое внимание: это значение «expires» является параметром заголовка «Subscription-State», а НЕ заголовком «Expires».
If the value of the "Subscription-State" header is "terminated", the notifier SHOULD also include a "reason" parameter. The notifier MAY also include a "retry-after" parameter, where appropriate. For details on the value and semantics of the "reason" and "retry-after" parameters, see section 3.2.4.
Если значение заголовка «Subscription-State» — «terminated», уведомителю СЛЕДУЕТ также включить параметр «reason». Уведомитель МОЖЕТ также включить параметр «retry-after», где это уместно. Подробности о значении и семантике параметров «reason» и «retry-after» см. в разделе 3.2.4.
3.2.3. Proxy NOTIFY Behavior
3.2.3. Поведение прокси при NOTIFY
Proxies need no additional behavior beyond that described in SIP [1] to support NOTIFY. If a proxy wishes to see all of the SUBSCRIBE and NOTIFY requests for a given dialog, it MUST record-route the initial SUBSCRIBE and any dialog-establishing NOTIFY requests. Such proxies SHOULD also record-route all other SUBSCRIBE and NOTIFY requests. Note that subscribers and notifiers may elect to use S/MIME encryption of SUBSCRIBE and NOTIFY requests; consequently, proxies cannot rely on being able to access any information that is not explicitly required to be proxy-readable by SIP [1].
Прокси не требуют дополнительного поведения сверх описанного в SIP [1] для поддержки NOTIFY. Если прокси желает видеть все запросы SUBSCRIBE и NOTIFY для данного диалога, он ДОЛЖЕН выполнить record-route начального SUBSCRIBE и любых запросов NOTIFY, устанавливающих диалог. Таким прокси также СЛЕДУЕТ выполнять record-route всех остальных запросов SUBSCRIBE и NOTIFY. Обратите внимание, что подписчики и уведомители могут выбрать использование шифрования S/MIME для запросов SUBSCRIBE и NOTIFY; следовательно, прокси не могут рассчитывать на доступ к любой информации, которая не требуется явно для чтения прокси согласно SIP [1].
3.2.4. Subscriber NOTIFY Behavior
3.2.4. Поведение подписчика при NOTIFY
Upon receiving a NOTIFY request, the subscriber should check that it matches at least one of its outstanding subscriptions; if not, it MUST return a "481 Subscription does not exist" response unless another 400- or 500-class response is more appropriate. The rules for matching NOTIFY requests with subscriptions that create a new dialog are described in section 3.3.4. Notifications for subscriptions which were created inside an existing dialog match if they are in the same dialog and the "Event" headers match (as described in section 7.2.1.)
По получении запроса NOTIFY подписчику следует проверить, что он соответствует хотя бы одной из его текущих подписок; если нет, он ДОЛЖЕН вернуть ответ «481 Subscription does not exist», если только какой-либо иной ответ класса 400 или 500 не более уместен. Правила сопоставления запросов NOTIFY с подписками, создающими новый диалог, описаны в разделе 3.3.4. Уведомления для подписок, созданных внутри существующего диалога, совпадают, если они находятся в одном диалоге и заголовки «Event» совпадают (как описано в разделе 7.2.1).
If, for some reason, the event package designated in the "Event" header of the NOTIFY request is not supported, the subscriber will respond with a "489 Bad Event" response.
Если по какой-либо причине пакет событий, обозначенный в заголовке «Event» запроса NOTIFY, не поддерживается, подписчик ответит ответом «489 Bad Event».
To prevent spoofing of events, NOTIFY requests SHOULD be authenticated, using any defined SIP authentication mechanism.
Чтобы предотвратить подделку событий, запросы NOTIFY СЛЕДУЕТ аутентифицировать с использованием любого определённого механизма аутентификации SIP.
NOTIFY requests MUST contain "Subscription-State" headers which indicate the status of the subscription.
Запросы NOTIFY ДОЛЖНЫ содержать заголовки «Subscription-State», которые указывают статус подписки.
If the "Subscription-State" header value is "active", it means that the subscription has been accepted and (in general) has been authorized. If the header also contains an "expires" parameter, the subscriber SHOULD take it as the authoritative subscription duration and adjust accordingly. The "retry-after" and "reason" parameters have no semantics for "active".
Если значение заголовка «Subscription-State» — «active», это означает, что подписка принята и (в общем случае) авторизована. Если заголовок также содержит параметр «expires», подписчику СЛЕДУЕТ принимать его как авторитетную длительность подписки и соответствующим образом корректироваться. Параметры «retry-after» и «reason» не имеют семантики для «active».
If the "Subscription-State" value is "pending", the subscription has been received by the notifier, but there is insufficient policy information to grant or deny the subscription yet. If the header also contains an "expires" parameter, the subscriber SHOULD take it as the authoritative subscription duration and adjust accordingly. No further action is necessary on the part of the subscriber. The "retry-after" and "reason" parameters have no semantics for "pending".
Если значение «Subscription-State» — «pending», подписка получена уведомителем, но информации о политике недостаточно для предоставления или отказа в подписке в настоящее время. Если заголовок также содержит параметр «expires», подписчику СЛЕДУЕТ принимать его как авторитетную длительность подписки и соответствующим образом корректироваться. Никаких дальнейших действий со стороны подписчика не требуется. Параметры «retry-after» и «reason» не имеют семантики для «pending».
If the "Subscription-State" value is "terminated", the subscriber should consider the subscription terminated. The "expires" parameter has no semantics for "terminated". If a reason code is present, the client should behave as described below. If no reason code or an unknown reason code is present, the client MAY attempt to re- subscribe at any time (unless a "retry-after" parameter is present, in which case the client SHOULD NOT attempt re-subscription until after the number of seconds specified by the "retry-after" parameter). The defined reason codes are:
Если значение «Subscription-State» — «terminated», подписчику следует считать подписку прекращённой. Параметр «expires» не имеет семантики для «terminated». Если присутствует код причины, клиенту следует вести себя, как описано ниже. Если код причины отсутствует или присутствует неизвестный код причины, клиент МОЖЕТ попытаться повторно подписаться в любой момент (если только не присутствует параметр «retry-after», и в этом случае клиенту НЕ СЛЕДУЕТ пытаться повторно подписаться до истечения числа секунд, указанного параметром «retry-after»). Определены следующие коды причин:
deactivated: The subscription has been terminated, but the subscriber SHOULD retry immediately with a new subscription. One primary use of such a status code is to allow migration of subscriptions between nodes. The "retry-after" parameter has no semantics for "deactivated".
deactivated: подписка была прекращена, но подписчику СЛЕДУЕТ немедленно повторить попытку с новой подпиской. Одно из основных применений такого кода состояния — позволить миграцию подписок между узлами. Параметр «retry-after» не имеет семантики для «deactivated».
probation: The subscription has been terminated, but the client SHOULD retry at some later time. If a "retry-after" parameter is also present, the client SHOULD wait at least the number of seconds specified by that parameter before attempting to re- subscribe.
probation: подписка была прекращена, но клиенту СЛЕДУЕТ повторить попытку в некоторый более поздний момент. Если также присутствует параметр «retry-after», клиенту СЛЕДУЕТ подождать не менее числа секунд, указанного этим параметром, прежде чем пытаться повторно подписаться.
rejected: The subscription has been terminated due to change in authorization policy. Clients SHOULD NOT attempt to re-subscribe. The "retry-after" parameter has no semantics for "rejected".
rejected: подписка была прекращена из-за изменения политики авторизации. Клиентам НЕ СЛЕДУЕТ пытаться повторно подписаться. Параметр «retry-after» не имеет семантики для «rejected».
timeout: The subscription has been terminated because it was not refreshed before it expired. Clients MAY re-subscribe immediately. The "retry-after" parameter has no semantics for "timeout".
timeout: подписка была прекращена, поскольку она не была возобновлена до истечения срока. Клиенты МОГУТ повторно подписаться немедленно. Параметр «retry-after» не имеет семантики для «timeout».
giveup: The subscription has been terminated because the notifier could not obtain authorization in a timely fashion. If a "retry- after" parameter is also present, the client SHOULD wait at least the number of seconds specified by that parameter before attempting to re-subscribe; otherwise, the client MAY retry immediately, but will likely get put back into pending state.
giveup: подписка была прекращена, поскольку уведомитель не смог получить авторизацию в надлежащее время. Если также присутствует параметр «retry-after», клиенту СЛЕДУЕТ подождать не менее числа секунд, указанного этим параметром, прежде чем пытаться повторно подписаться; иначе клиент МОЖЕТ повторить немедленно, но, вероятно, будет возвращён в состояние pending.
noresource: The subscription has been terminated because the resource state which was being monitored no longer exists. Clients SHOULD NOT attempt to re-subscribe. The "retry-after" parameter has no semantics for "noresource".
noresource: подписка была прекращена, поскольку отслеживаемое состояние ресурса больше не существует. Клиентам НЕ СЛЕДУЕТ пытаться повторно подписаться. Параметр «retry-after» не имеет семантики для «noresource».
Once the notification is deemed acceptable to the subscriber, the subscriber SHOULD return a 200 response. In general, it is not expected that NOTIFY responses will contain bodies; however, they MAY, if the NOTIFY request contained an "Accept" header.
Как только уведомление признано приемлемым для подписчика, подписчику СЛЕДУЕТ вернуть ответ 200. В общем случае не ожидается, что ответы на NOTIFY будут содержать тела; однако они МОГУТ, если запрос NOTIFY содержал заголовок «Accept».
Other responses defined in SIP [1] may also be returned, as appropriate. In no case should a NOTIFY transaction extend for any longer than the time necessary for automated processing. In particular, subscribers MUST NOT wait for a user response before returning a final response to a NOTIFY request.
Другие ответы, определённые в SIP [1], также могут возвращаться по обстоятельствам. Ни в каком случае транзакция NOTIFY не должна продолжаться дольше времени, необходимого для автоматической обработки. В частности, подписчики НЕ ДОЛЖНЫ ждать ответа пользователя перед возвратом окончательного ответа на запрос NOTIFY.
3.3. General
3.3. Общие положения
3.3.1. Detecting support for SUBSCRIBE and NOTIFY
3.3.1. Обнаружение поддержки SUBSCRIBE и NOTIFY
Neither SUBSCRIBE nor NOTIFY necessitate the use of "Require" or "Proxy-Require" headers; similarly, there is no token defined for "Supported" headers. If necessary, clients may probe for the support of SUBSCRIBE and NOTIFY using the OPTIONS request defined in SIP [1].
Ни SUBSCRIBE, ни NOTIFY не требуют использования заголовков «Require» или «Proxy-Require»; аналогично для заголовков «Supported» не определён токен. При необходимости клиенты могут проверить поддержку SUBSCRIBE и NOTIFY с помощью запроса OPTIONS, определённого в SIP [1].
The presence of the "Allow-Events" header in a message is sufficient to indicate support for SUBSCRIBE and NOTIFY.
Присутствие заголовка «Allow-Events» в сообщении достаточно для указания поддержки SUBSCRIBE и NOTIFY.
The "methods" parameter for Contact may also be used to specifically announce support for SUBSCRIBE and NOTIFY messages when registering. (See reference [8] for details on the "methods" parameter).
Параметр «methods» для Contact также может использоваться для конкретного объявления поддержки сообщений SUBSCRIBE и NOTIFY при регистрации. (Подробности о параметре «methods» см. в ссылке [8]).
3.3.2. CANCEL requests
3.3.2. Запросы CANCEL
No semantics are associated with cancelling SUBSCRIBE or NOTIFY.
С отменой SUBSCRIBE или NOTIFY не связана никакая семантика.
3.3.3. Forking
3.3.3. Ветвление запросов
In accordance with the rules for proxying non-INVITE requests as defined in SIP [1], successful SUBSCRIBE requests will receive only one 200-class response; however, due to forking, the subscription may have been accepted by multiple nodes. The subscriber MUST therefore be prepared to receive NOTIFY requests with "From:" tags which differ from the "To:" tag received in the SUBSCRIBE 200-class response.
В соответствии с правилами проксирования запросов, отличных от INVITE, как определено в SIP [1], успешные запросы SUBSCRIBE получат только один ответ класса 200; однако из-за ветвления подписка может быть принята несколькими узлами. Поэтому подписчик ДОЛЖЕН быть готов получать запросы NOTIFY с тегами «From:», отличными от тега «To:», полученного в ответе класса 200 на SUBSCRIBE.
If multiple NOTIFY messages are received in different dialogs in response to a single SUBSCRIBE message, each dialog represents a different destination to which the SUBSCRIBE request was forked. For information on subscriber handling in such situations, see section 4.4.9.
Если в ответ на одно сообщение SUBSCRIBE получено несколько сообщений NOTIFY в разных диалогах, каждый диалог представляет отдельный адресат, на который был разветвлён запрос SUBSCRIBE. Информацию об обработке подписчиком в таких ситуациях см. в разделе 4.4.9.
3.3.4. Dialog creation and termination
3.3.4. Создание и завершение диалога
If an initial SUBSCRIBE request is not sent on a pre-existing dialog, the subscriber will wait for a response to the SUBSCRIBE request or a matching NOTIFY.
Если начальный запрос SUBSCRIBE не отправлен в уже существующем диалоге, подписчик будет ждать либо ответа на запрос SUBSCRIBE, либо соответствующего NOTIFY.
Responses are matched to such SUBSCRIBE requests if they contain the same the same "Call-ID", the same "From" header "tag", and the same "CSeq". Rules for the comparison of these headers are described in SIP [1]. If a 200-class response matches such a SUBSCRIBE request, it creates a new subscription and a new dialog (unless they have already been created by a matching NOTIFY request; see below). NOTIFY requests are matched to such SUBSCRIBE requests if they contain the same "Call-ID", a "To" header "tag" parameter which matches the "From" header "tag" parameter of the SUBSCRIBE, and the same "Event" header field. Rules for comparisons of the "Event" headers are described in section 7.2.1. If a matching NOTIFY request contains a "Subscription-State" of "active" or "pending", it creates a new subscription and a new dialog (unless they have already been created by a matching response, as described above).
Ответы сопоставляются с такими запросами SUBSCRIBE, если они содержат тот же «Call-ID», тот же тег заголовка «From» и тот же «CSeq». Правила сравнения этих заголовков описаны в SIP [1]. Если ответ класса 200 соответствует такому запросу SUBSCRIBE, он создаёт новую подписку и новый диалог (если они не были уже созданы соответствующим запросом NOTIFY; см. ниже). Запросы NOTIFY сопоставляются с такими запросами SUBSCRIBE, если они содержат тот же «Call-ID», параметр тега заголовка «To», совпадающий с параметром тега заголовка «From» запроса SUBSCRIBE, и то же поле заголовка «Event». Правила сравнения заголовков «Event» описаны в разделе 7.2.1. Если соответствующий запрос NOTIFY содержит «Subscription-State» со значением «active» или «pending», он создаёт новую подписку и новый диалог (если они не были уже созданы соответствующим ответом, как описано выше).
If an initial SUBSCRIBE is sent on a pre-existing dialog, a matching 200-class response or successful NOTIFY request merely creates a new subscription associated with that dialog.
Если начальный SUBSCRIBE отправлен в уже существующем диалоге, соответствующий ответ класса 200 или успешный запрос NOTIFY лишь создаёт новую подписку, связанную с этим диалогом.
Multiple subscriptions can be associated with a single dialog. Subscriptions may also exist in dialogs associated with INVITE- created application state and other application state created by mechanisms defined in other specifications. These sets of application state do not interact beyond the behavior described for a dialog (e.g., route set handling).
С одним диалогом может быть связано несколько подписок. Подписки также могут существовать в диалогах, связанных с состоянием приложения, созданным INVITE, и другим состоянием приложения, созданным механизмами, определёнными в других спецификациях. Эти наборы состояния приложения не взаимодействуют сверх поведения, описанного для диалога (например, обработки набора маршрутов).
A subscription is destroyed when a notifier sends a NOTIFY request with a "Subscription-State" of "terminated".
Подписка уничтожается, когда уведомитель отправляет запрос NOTIFY со значением «Subscription-State», равным «terminated».
A subscriber may send a SUBSCRIBE request with an "Expires" header of 0 in order to trigger the sending of such a NOTIFY request; however, for the purposes of subscription and dialog lifetime, the subscription is not considered terminated until the NOTIFY with a "Subscription-State" of "terminated" is sent.
Подписчик может отправить запрос SUBSCRIBE с заголовком «Expires», равным 0, чтобы инициировать отправку такого запроса NOTIFY; однако для целей времени жизни подписки и диалога подписка не считается прекращённой до тех пор, пока не будет отправлено NOTIFY со значением «Subscription-State», равным «terminated».
If a subscription's destruction leaves no other application state associated with the dialog, the dialog terminates. The destruction of other application state (such as that created by an INVITE) will not terminate the dialog if a subscription is still associated with that dialog.
Если уничтожение подписки не оставляет иного состояния приложения, связанного с диалогом, диалог завершается. Уничтожение другого состояния приложения (например, созданного INVITE) не завершит диалог, если подписка всё ещё связана с этим диалогом.
Note that the above behavior means that a dialog created with an INVITE does not necessarily terminate upon receipt of a BYE. Similarly, in the case that several subscriptions are associated with a single dialog, the dialog does not terminate until all the subscriptions in it are destroyed.

3.3.5. State Agents and Notifier Migration
3.3.5. Агенты состояния и миграция уведомителей
When state agents (see section 4.4.11.) are used, it is often useful to allow migration of subscriptions between state agents and the nodes for which they are providing state aggregation (or even among various state agents). Such migration may be effected by sending a NOTIFY message with a "Subscription-State" header of "terminated", and a reason parameter of "deactivated". This NOTIFY request is otherwise normal, and is formed as described in section 3.2.2.
Когда используются агенты состояния (см. раздел 4.4.11), часто полезно разрешить миграцию подписок между агентами состояния и узлами, для которых они обеспечивают агрегацию состояния (или даже между различными агентами состояния). Такая миграция может быть выполнена отправкой сообщения NOTIFY с заголовком «Subscription-State» со значением «terminated» и параметром reason со значением «deactivated». В остальном этот запрос NOTIFY обычен и формируется, как описано в разделе 3.2.2.
Upon receipt of this NOTIFY message, the subscriber SHOULD attempt to re-subscribe (as described in the preceding sections). Note that this subscription is established on a new dialog, and does not re-use the route set from the previous subscription dialog.
По получении этого сообщения NOTIFY подписчику СЛЕДУЕТ попытаться повторно подписаться (как описано в предыдущих разделах). Обратите внимание, что эта подписка устанавливается в новом диалоге и не повторно использует набор маршрутов из предыдущего диалога подписки.
The actual migration is effected by making a change to the policy (such as routing decisions) of one or more servers to which the SUBSCRIBE request will be sent in such a way that a different node ends up responding to the SUBSCRIBE request. This may be as simple as a change in the local policy in the notifier from which the subscription is migrating so that it serves as a proxy or redirect server instead of a notifier.
Фактическая миграция выполняется путём изменения политики (например, решений о маршрутизации) одного или нескольких серверов, которым будет отправлен запрос SUBSCRIBE, таким образом, что в конечном итоге на запрос SUBSCRIBE отвечает другой узел. Это может быть так просто, как изменение локальной политики в уведомителе, от которого мигрирует подписка, чтобы он служил прокси или сервером перенаправления вместо уведомителя.
Whether, when, and why to perform notifier migrations may be described in individual event packages; otherwise, such decisions are a matter of local notifier policy, and are left up to individual implementations.
Следует ли, когда и почему выполнять миграции уведомителей, может быть описано в отдельных пакетах событий; иначе такие решения являются вопросом локальной политики уведомителя и оставлены на усмотрение отдельных реализаций.
3.3.6. Polling Resource State
3.3.6. Опрос состояния ресурса
A natural consequence of the behavior described in the preceding sections is that an immediate fetch without a persistent subscription may be effected by sending a SUBSCRIBE with an "Expires" of 0.
Естественным следствием поведения, описанного в предыдущих разделах, является то, что немедленная выборка без постоянной подписки может быть выполнена путём отправки SUBSCRIBE со значением «Expires», равным 0.
Of course, an immediate fetch while a subscription is active may be effected by sending a SUBSCRIBE with an "Expires" equal to the number of seconds remaining in the subscription.
Разумеется, немедленная выборка при активной подписке может быть выполнена путём отправки SUBSCRIBE со значением «Expires», равным числу секунд, оставшихся до истечения подписки.
Upon receipt of this SUBSCRIBE request, the notifier (or notifiers, if the SUBSCRIBE request was forked) will send a NOTIFY request containing resource state in the same dialog.
По получении этого запроса SUBSCRIBE уведомитель (или уведомители, если запрос SUBSCRIBE был разветвлён) отправит запрос NOTIFY, содержащий состояние ресурса, в том же диалоге.
Note that the NOTIFY messages triggered by SUBSCRIBE messages with "Expires" headers of 0 will contain a "Subscription-State" value of "terminated", and a "reason" parameter of "timeout".
Обратите внимание, что сообщения NOTIFY, вызванные сообщениями SUBSCRIBE с заголовками «Expires», равными 0, будут содержать значение «Subscription-State», равное «terminated», и параметр «reason» со значением «timeout».
Polling of event state can cause significant increases in load on the network and notifiers; as such, it should be used only sparingly. In particular, polling SHOULD NOT be used in circumstances in which it will typically result in more network messages than long-running subscriptions. When polling is used, subscribers SHOULD attempt to cache authentication credentials between polls so as to reduce the number of messages sent.
Опрос состояния событий может вызвать значительное увеличение нагрузки на сеть и уведомителей; как таковой он должен использоваться лишь экономно. В частности, опрос НЕ СЛЕДУЕТ использовать в обстоятельствах, в которых он, как правило, приведёт к большему числу сетевых сообщений, чем долговременные подписки. При использовании опроса подписчикам СЛЕДУЕТ пытаться кэшировать учётные данные аутентификации между опросами, чтобы уменьшить число отправляемых сообщений.
3.3.7. Allow-Events header usage
3.3.7. Использование заголовка Allow-Events
The "Allow-Events" header, if present, includes a list of tokens which indicates the event packages supported by the client (if sent in a request) or server (if sent in a response). In other words, a node sending an "Allow-Events" header is advertising that it can process SUBSCRIBE requests and generate NOTIFY requests for all of the event packages listed in that header.
Заголовок «Allow-Events», если он присутствует, включает список токенов, который указывает пакеты событий, поддерживаемые клиентом (если отправлен в запросе) или сервером (если отправлен в ответе). Иными словами, узел, отправляющий заголовок «Allow-Events», объявляет, что он может обрабатывать запросы SUBSCRIBE и формировать запросы NOTIFY для всех пакетов событий, перечисленных в этом заголовке.
Any node implementing one or more event packages SHOULD include an appropriate "Allow-Events" header indicating all supported events in all methods which initiate dialogs and their responses (such as INVITE) and OPTIONS responses.
Любому узлу, реализующему один или несколько пакетов событий, СЛЕДУЕТ включать соответствующий заголовок «Allow-Events», указывающий все поддерживаемые события, во все методы, инициирующие диалоги, и их ответы (например, INVITE), а также в ответы OPTIONS.
This information is very useful, for example, in allowing user agents to render particular interface elements appropriately according to whether the events required to implement the features they represent are supported by the appropriate nodes.
Эта информация очень полезна, например, для того чтобы позволить пользовательским агентам надлежащим образом отображать конкретные элементы интерфейса в зависимости от того, поддерживаются ли соответствующими узлами события, необходимые для реализации представляемых ими возможностей.
Note that "Allow-Events" headers MUST NOT be inserted by proxies.
Обратите внимание, что заголовки «Allow-Events» НЕ ДОЛЖНЫ вставляться прокси.
3.3.8. PINT Compatibility
3.3.8. Совместимость с PINT
The "Event" header is considered mandatory for the purposes of this document. However, to maintain compatibility with PINT (see [2]), servers MAY interpret a SUBSCRIBE request with no "Event" header as requesting a subscription to PINT events. If a server does not support PINT, it SHOULD return "489 Bad Event" to any SUBSCRIBE messages without an "Event" header.
Заголовок «Event» считается обязательным для целей настоящего документа. Однако для сохранения совместимости с PINT (см. [2]) серверы МОГУТ интерпретировать запрос SUBSCRIBE без заголовка «Event» как запрос подписки на события PINT. Если сервер не поддерживает PINT, ему СЛЕДУЕТ возвращать «489 Bad Event» на все сообщения SUBSCRIBE без заголовка «Event».
4. Event Packages
4. Пакеты событий
This section covers several issues which should be taken into consideration when event packages based on SUBSCRIBE and NOTIFY are proposed.
В этом разделе рассматривается несколько вопросов, которые следует учитывать при предложении пакетов событий на основе SUBSCRIBE и NOTIFY.
4.1. Appropriateness of Usage
4.1. Уместность использования
When designing an event package using the methods described in this document for event notification, it is important to consider: is SIP an appropriate mechanism for the problem set? Is SIP being selected because of some unique feature provided by the protocol (e.g., user mobility), or merely because "it can be done?" If you find yourself defining event packages for notifications related to, for example, network management or the temperature inside your car's engine, you may want to reconsider your selection of protocols.
При проектировании пакета событий с использованием методов, описанных в настоящем документе для уведомления о событиях, важно учесть: является ли SIP подходящим механизмом для этого набора задач? Выбирается ли SIP из-за какой-либо уникальной возможности, предоставляемой протоколом (например, мобильности пользователя), или лишь потому, что «это можно сделать»? Если вы обнаруживаете, что определяете пакеты событий для уведомлений, связанных, например, с управлением сетью или температурой внутри двигателя вашего автомобиля, вы можете захотеть пересмотреть выбор протоколов.
Those interested in extending the mechanism defined in this document are urged to follow the development of "Guidelines for Authors of SIP Extensions" [7] for further guidance regarding appropriate uses of SIP.
Тем, кто заинтересован в расширении механизма, определённого в настоящем документе, настоятельно рекомендуется следить за разработкой «Guidelines for Authors of SIP Extensions» [7] для получения дальнейшего руководства относительно надлежащего использования SIP.
Further, it is expected that this mechanism is not to be used in applications where the frequency of reportable events is excessively rapid (e.g., more than about once per second). A SIP network is generally going to be provisioned for a reasonable signalling volume; sending a notification every time a user's GPS position changes by one hundredth of a second could easily overload such a network.
Далее, ожидается, что этот механизм не должен использоваться в приложениях, где частота передаваемых событий чрезмерно высока (например, более примерно одного раза в секунду). Сеть SIP, как правило, будет рассчитана на разумный объём сигнализации; отправка уведомления каждый раз, когда GPS-позиция пользователя изменяется на одну сотую секунды, могла бы легко перегрузить такую сеть.
4.2. Event Template-packages
4.2. Шаблонные пакеты событий
Normal event packages define a set of state applied to a specific type of resource, such as user presence, call state, and messaging mailbox state.
Обычные пакеты событий определяют набор состояния, применяемый к конкретному типу ресурса, например присутствие пользователя, состояние вызова и состояние почтового ящика сообщений.
Event template-packages are a special type of package which define a set of state applied to other packages, such as statistics, access policy, and subscriber lists. Event template-packages may even be applied to other event template-packages.
Шаблонные пакеты событий — это особый тип пакета, который определяет набор состояния, применяемый к другим пакетам, например статистику, политику доступа и списки подписчиков. Шаблонные пакеты событий могут применяться даже к другим шаблонным пакетам событий.
To extend the object-oriented analogy made earlier, event template- packages can be thought of as templatized C++ packages which must be applied to other packages to be useful.
Расширяя приведённую ранее объектно-ориентированную аналогию, шаблонные пакеты событий можно рассматривать как шаблонные пакеты C++, которые должны быть применены к другим пакетам, чтобы быть полезными.
The name of an event template-package as applied to a package is formed by appending a period followed by the event template-package name to the end of the package. For example, if a template-package called "winfo" were being applied to a package called "presence", the event token used in "Event" and "Allow-Events" would be "presence.winfo".
Имя шаблонного пакета событий в применении к пакету образуется путём добавления точки и имени шаблонного пакета событий в конец имени пакета. Например, если шаблонный пакет с именем «winfo» применяется к пакету с именем «presence», токен события, используемый в «Event» и «Allow-Events», был бы «presence.winfo».
Event template-packages must be defined so that they can be applied to any arbitrary package. In other words, event template-packages cannot be specifically tied to one or a few "parent" packages in such a way that they will not work with other packages.
Шаблонные пакеты событий должны быть определены так, чтобы их можно было применять к любому произвольному пакету. Иными словами, шаблонные пакеты событий не могут быть конкретно привязаны к одному или нескольким «родительским» пакетам таким образом, что они не будут работать с другими пакетами.
4.3. Amount of State to be Conveyed
4.3. Объём передаваемого состояния
When designing event packages, it is important to consider the type of information which will be conveyed during a notification. A natural temptation is to convey merely the event (e.g., "a new voice message just arrived") without accompanying state (e.g., "7 total voice messages"). This complicates implementation of subscribing entities (since they have to maintain complete state for the entity to which they have subscribed), and also is particularly susceptible to synchronization problems.
При проектировании пакетов событий важно учитывать тип информации, которая будет передаваться во время уведомления. Естественное искушение — передавать лишь событие (например, «только что прибыло новое голосовое сообщение») без сопроводительного состояния (например, «всего 7 голосовых сообщений»). Это усложняет реализацию подписывающихся объектов (поскольку им приходится поддерживать полное состояние объекта, на который они подписались), а также особенно подвержено проблемам синхронизации.
There are two possible solutions to this problem that event packages may choose to implement.
Есть два возможных решения этой проблемы, которые пакеты событий могут выбрать для реализации.
4.3.1. Complete State Information
4.3.1. Полная информация о состоянии
For packages which typically convey state information that is reasonably small (on the order of 1 kb or so), it is suggested that event packages are designed so as to send complete state information when an event occurs.
Для пакетов, которые обычно передают относительно небольшую информацию о состоянии (порядка 1 КБ или около того), предлагается проектировать пакеты событий так, чтобы отправлять полную информацию о состоянии при возникновении события.
In some circumstances, conveying the current state alone may be insufficient for a particular class of events. In these cases, the event packages should include complete state information along with the event that occurred. For example, conveying "no customer service representatives available" may not be as useful as conveying "no customer service representatives available; representative sip:46@cs.xyz.int just logged off".
В некоторых обстоятельствах передачи лишь текущего состояния может быть недостаточно для конкретного класса событий. В этих случаях пакеты событий должны включать полную информацию о состоянии вместе с произошедшим событием. Например, передача «нет доступных представителей службы поддержки» может быть не настолько полезной, как передача «нет доступных представителей службы поддержки; представитель sip:46@cs.xyz.int только что вышел из системы».
4.3.2. State Deltas
4.3.2. Разностные изменения состояния
In the case that the state information to be conveyed is large, the event package may choose to detail a scheme by which NOTIFY messages contain state deltas instead of complete state.
В случае когда передаваемая информация о состоянии велика, пакет событий может выбрать схему, по которой сообщения NOTIFY содержат разности состояний вместо полного состояния.
Such a scheme would work as follows: any NOTIFY sent in immediate response to a SUBSCRIBE contains full state information. NOTIFY messages sent because of a state change will contain only the state information that has changed; the subscriber will then merge this information into its current knowledge about the state of the resource.
Такая схема работала бы следующим образом: любой NOTIFY, отправленный немедленно в ответ на SUBSCRIBE, содержит полную информацию о состоянии. Сообщения NOTIFY, отправленные из-за изменения состояния, будут содержать только ту информацию о состоянии, которая изменилась; подписчик затем объединит эту информацию со своими текущими знаниями о состоянии ресурса.
Any event package that supports delta changes to states MUST include a version number that increases by exactly one for each NOTIFY transaction in a subscription. Note that the state version number appears in the body of the message, not in a SIP header.
Любой пакет событий, поддерживающий разностные изменения состояний, ДОЛЖЕН включать номер версии, который увеличивается ровно на единицу для каждой транзакции NOTIFY в подписке. Обратите внимание, что номер версии состояния появляется в теле сообщения, а не в заголовке SIP.
If a NOTIFY arrives that has a version number that is incremented by more than one, the subscriber knows that a state delta has been missed; it ignores the NOTIFY message containing the state delta (except for the version number, which it retains to detect message loss), and re-sends a SUBSCRIBE to force a NOTIFY containing a complete state snapshot.
Если прибывает NOTIFY с номером версии, увеличенным более чем на единицу, подписчик знает, что разность состояний была пропущена; он игнорирует сообщение NOTIFY, содержащее разность состояний (за исключением номера версии, который он сохраняет для обнаружения потери сообщений), и повторно отправляет SUBSCRIBE, чтобы вызвать NOTIFY, содержащий полный снимок состояния.

4.4. Обязанности пакетов событий
Event packages are not required to reiterate any of the behavior described in this document, although they may choose to do so for clarity or emphasis. In general, though, such packages are expected to describe only the behavior that extends or modifies the behavior described in this document.
Пакеты событий не обязаны повторять какое-либо поведение, описанное в настоящем документе, хотя они могут это делать для ясности или акцента. В целом, однако, такие пакеты должны описывать только поведение, которое расширяет или изменяет поведение, описанное в настоящем документе.

Обратите внимание, что любое поведение, обозначенное в настоящем документе как «SHOULD» или «MUST», не может быть ослаблено документами расширений; однако такие документы могут выбрать усиление требований «SHOULD» до уровня «MUST», если это требуется их приложением.

Помимо обычных разделов, ожидаемых в RFC уровня Standards Track и документах расширений SIP, авторам пакетов событий необходимо рассмотреть каждый из вопросов, подробно описанных в следующих подразделах, когда это применимо.

4.4.1. Имя пакета событий

4.4.2. Параметры пакета событий

4.4.3. SUBSCRIBE Bodies
4.4.3. Тела SUBSCRIBE
It is expected that most, but not all, event packages will define syntax and semantics for SUBSCRIBE method bodies; these bodies will typically modify, expand, filter, throttle, and/or set thresholds for the class of events being requested. Designers of event packages are strongly encouraged to re-use existing MIME types for message bodies where practical. This mandatory section of an event package defines what type or types of event bodies are expected in SUBSCRIBE requests (or specify that no event bodies are expected). It should point to detailed definitions of syntax and semantics for all referenced body types.
Ожидается, что большинство, но не все пакеты событий будут определять синтаксис и семантику тел метода SUBSCRIBE; эти тела, как правило, будут изменять, расширять, фильтровать, ограничивать частоту и/или устанавливать пороги для класса запрашиваемых событий. Разработчикам пакетов событий настоятельно рекомендуется повторно использовать существующие типы MIME для тел сообщений, где это практично. Этот обязательный раздел пакета событий определяет, какой тип или типы тел событий ожидаются в запросах SUBSCRIBE (или указывает, что тела событий не ожидаются). Он должен указывать на подробные определения синтаксиса и семантики для всех упоминаемых типов тела.
4.4.4. Subscription Duration
4.4.4. Длительность подписки
It is RECOMMENDED that event packages give a suggested range of times considered reasonable for the duration of a subscription. Such packages MUST also define a default "Expires" value to be used if none is specified.
РЕКОМЕНДУЕТСЯ, чтобы пакеты событий давали предлагаемый диапазон значений времени, считающихся разумными для длительности подписки. Такие пакеты также ДОЛЖНЫ определять значение «Expires» по умолчанию, которое следует использовать, если ни одно не указано.
4.4.5. NOTIFY Bodies
4.4.5. Тела NOTIFY
The NOTIFY body is used to report state on the resource being monitored. Each package MUST define what type or types of event bodies are expected in NOTIFY requests. Such packages MUST specify or cite detailed specifications for the syntax and semantics associated with such event body.
Тело NOTIFY используется для передачи состояния отслеживаемого ресурса. Каждый пакет ДОЛЖЕН определить, какой тип или типы тел событий ожидаются в запросах NOTIFY. Такие пакеты ДОЛЖНЫ указывать или ссылаться на подробные спецификации синтаксиса и семантики, связанных с таким телом события.
Event packages also MUST define which MIME type is to be assumed if none are specified in the "Accept" header of the SUBSCRIBE request.
Пакеты событий также ДОЛЖНЫ определить, какой тип MIME следует предполагать, если ни один не указан в заголовке «Accept» запроса SUBSCRIBE.
4.4.6. Notifier processing of SUBSCRIBE requests
4.4.6. Обработка уведомителем запросов SUBSCRIBE
This section describes the processing to be performed by the notifier upon receipt of a SUBSCRIBE request. Such a section is required.
Этот раздел описывает обработку, выполняемую уведомителем по получении запроса SUBSCRIBE. Такой раздел обязателен.
Information in this section includes details of how to authenticate subscribers and authorization issues for the package. Such authorization issues may include, for example, whether all SUBSCRIBE requests for this package are answered with 202 responses (see section 5.2.).
Информация в этом разделе включает подробности того, как аутентифицировать подписчиков, и вопросы авторизации для пакета. Такие вопросы авторизации могут включать, например, должны ли все запросы SUBSCRIBE для этого пакета получать ответы 202 (см. раздел 5.2).
4.4.7. Notifier generation of NOTIFY requests
4.4.7. Формирование уведомителем запросов NOTIFY
This section of an event package describes the process by which the notifier generates and sends a NOTIFY request. This includes detailed information about what events cause a NOTIFY to be sent, how to compute the state information in the NOTIFY, how to generate neutral or fake state information to hide authorization delays and decisions from users, and whether state information is complete or deltas for notifications; see section 4.3. Such a section is required.
Этот раздел пакета событий описывает процесс, посредством которого уведомитель формирует и отправляет запрос NOTIFY. Он включает подробную информацию о том, какие события вызывают отправку NOTIFY, как вычислить информацию о состоянии в NOTIFY, как формировать нейтральную или ложную информацию о состоянии, чтобы скрыть от пользователей задержки и решения авторизации, и является ли информация о состоянии полной или разностной для уведомлений; см. раздел 4.3. Такой раздел обязателен.
This section may optionally describe the behavior used to process the subsequent response.
Этот раздел может необязательно описывать поведение, используемое для обработки последующего ответа.
4.4.8. Subscriber processing of NOTIFY requests
4.4.8. Обработка подписчиком запросов NOTIFY
This section of an event package describes the process followed by the subscriber upon receipt of a NOTIFY request, including any logic required to form a coherent resource state (if applicable).
Этот раздел пакета событий описывает процесс, которому следует подписчик по получении запроса NOTIFY, включая любую логику, необходимую для формирования согласованного состояния ресурса (если применимо).
4.4.9. Handling of forked requests
4.4.9. Обработка разветвлённых запросов
Each event package MUST specify whether forked SUBSCRIBE requests are allowed to install multiple subscriptions.
Каждый пакет событий ДОЛЖЕН указать, разрешено ли разветвлённым запросам SUBSCRIBE устанавливать несколько подписок.
If such behavior is not allowed, the first potential dialog- establishing message will create a dialog. All subsequent NOTIFY messages which correspond to the SUBSCRIBE message (i.e., match "To", "From", "From" header "tag" parameter, "Call-ID", "CSeq", "Event", and "Event" header "id" parameter) but which do not match the dialog would be rejected with a 481 response. Note that the 200-class response to the SUBSCRIBE can arrive after a matching NOTIFY has been received; such responses might not correlate to the same dialog established by the NOTIFY. Except as required to complete the SUBSCRIBE transaction, such non-matching 200-class responses are ignored.
Если такое поведение не разрешено, первое потенциальное сообщение, устанавливающее диалог, создаст диалог. Все последующие сообщения NOTIFY, которые соответствуют сообщению SUBSCRIBE (то есть совпадают по «To», «From», параметру тега заголовка «From», «Call-ID», «CSeq», «Event» и параметру «id» заголовка «Event»), но не соответствуют диалогу, будут отклонены ответом 481. Обратите внимание, что ответ класса 200 на SUBSCRIBE может прибыть после получения соответствующего NOTIFY; такие ответы могут не соотноситься с тем же диалогом, установленным посредством NOTIFY. За исключением случаев, требующихся для завершения транзакции SUBSCRIBE, такие несоответствующие ответы класса 200 игнорируются.
If installing of multiple subscriptions by way of a single forked SUBSCRIBE is allowed, the subscriber establishes a new dialog towards each notifier by returning a 200-class response to each NOTIFY. Each dialog is then handled as its own entity, and is refreshed independent of the other dialogs.
Если установка нескольких подписок посредством одного разветвлённого SUBSCRIBE разрешена, подписчик устанавливает новый диалог к каждому уведомителю путём возврата ответа класса 200 на каждый NOTIFY. Затем каждый диалог обрабатывается как отдельная сущность и возобновляется независимо от других диалогов.
In the case that multiple subscriptions are allowed, the event package MUST specify whether merging of the notifications to form a single state is required, and how such merging is to be performed. Note that it is possible that some event packages may be defined in such a way that each dialog is tied to a mutually exclusive state which is unaffected by the other dialogs; this MUST be clearly stated if it is the case.
В случае когда несколько подписок разрешены, пакет событий ДОЛЖЕН указать, требуется ли объединение уведомлений для формирования единого состояния и как такое объединение должно выполняться. Обратите внимание, что некоторые пакеты событий могут быть определены так, что каждый диалог привязан к взаимно исключающему состоянию, на которое другие диалоги не влияют; это ДОЛЖНО быть чётко указано, если это так.
4.4.10. Rate of notifications
4.4.10. Частота уведомлений
Each event package is expected to define a requirement (SHOULD or MUST strength) which defines an absolute maximum on the rate at which notifications are allowed to be generated by a single notifier.
От каждого пакета событий ожидается определение требования (уровня SHOULD или MUST), которое определяет абсолютный максимум частоты, с которой одному уведомителю разрешено формировать уведомления.
Each package MAY further define a throttle mechanism which allows subscribers to further limit the rate of notification.
Каждый пакет МОЖЕТ дополнительно определить механизм ограничения частоты, который позволяет подписчикам ещё больше ограничить частоту уведомлений.
4.4.11. State Agents
4.4.11. Агенты состояния
Designers of event packages should consider whether their package can benefit from network aggregation points (state agents) and/or nodes which act on behalf of other nodes. (For example, nodes which provide state information about a resource when such a resource is unable or unwilling to provide such state information itself). An example of such an application is a node which tracks the presence and availability of a user in the network.
Разработчикам пакетов событий следует рассмотреть, может ли их пакет извлечь выгоду из сетевых точек агрегации (агентов состояния) и/или узлов, действующих от имени других узлов. (Например, узлов, которые предоставляют информацию о состоянии ресурса, когда такой ресурс не способен или не желает предоставлять такую информацию о состоянии сам.) Примером такого приложения является узел, который отслеживает присутствие и доступность пользователя в сети.
If state agents are to be used by the package, the package MUST specify how such state agents aggregate information and how they provide authentication and authorization.
Если пакет использует агентов состояния, пакет ДОЛЖЕН указать, как такие агенты состояния агрегируют информацию и как они обеспечивают аутентификацию и авторизацию.
Event packages MAY also outline specific scenarios under which notifier migrations take place.
Пакеты событий МОГУТ также описывать конкретные сценарии, при которых происходят миграции уведомителей.

4.4.12. Примеры
Event packages SHOULD include several demonstrative message flow diagrams paired with several typical, syntactically correct, and complete messages.
Пакеты событий СЛЕДУЕТ включать несколько демонстративных диаграмм потока сообщений в паре с несколькими типичными, синтаксически правильными и полными сообщениями.
It is RECOMMENDED that documents describing event packages clearly indicate that such examples are informative and not normative, with instructions that implementors refer to the main text of the document for exact protocol details.
РЕКОМЕНДУЕТСЯ, чтобы документы, описывающие пакеты событий, чётко указывали, что такие примеры являются информативными, а не нормативными, с указанием разработчикам обращаться к основному тексту документа за точными деталями протокола.
4.4.13. Use of URIs to Retrieve State
4.4.13. Использование URI для получения состояния
Some types of event packages may define state information which is potentially too large to reasonably send in a SIP message. To alleviate this problem, event packages may include the ability to convey a URI instead of state information; this URI will then be used to retrieve the actual state information.
Некоторые типы пакетов событий могут определять информацию о состоянии, которая потенциально слишком велика для разумной отправки в сообщении SIP. Чтобы облегчить эту проблему, пакеты событий могут включать возможность передачи URI вместо информации о состоянии; этот URI затем будет использоваться для получения фактической информации о состоянии.
The precise mechanisms for conveying such URIs are out of the scope of this document.
Точные механизмы передачи таких URI выходят за рамки настоящего документа.
5. Security Considerations
5. Вопросы безопасности
5.1. Access Control
5.1. Управление доступом
The ability to accept subscriptions should be under the direct control of the notifier's user, since many types of events may be considered sensitive for the purposes of privacy. Similarly, the notifier should have the ability to selectively reject subscriptions based on the subscriber identity (based on access control lists), using standard SIP authentication mechanisms. The methods for creation and distribution of such access control lists is outside the scope of this document.
Возможность принимать подписки должна находиться под прямым контролем пользователя уведомителя, поскольку многие типы событий могут считаться конфиденциальными с точки зрения приватности. Аналогично уведомитель должен иметь возможность выборочно отклонять подписки на основе идентичности подписчика (на основе списков управления доступом) с использованием стандартных механизмов аутентификации SIP. Методы создания и распространения таких списков управления доступом выходят за рамки настоящего документа.
5.2. Notifier Privacy Mechanism
5.2. Механизм приватности уведомителя
The mere act of returning a 200 or certain 4xx and 6xx responses to SUBSCRIBE requests may, under certain circumstances, create privacy concerns by revealing sensitive policy information. In these cases, the notifier SHOULD always return a 202 response. While the subsequent NOTIFY message may not convey true state, it MUST appear to contain a potentially correct piece of data from the point of view of the subscriber, indistinguishable from a valid response. Information about whether a user is authorized to subscribe to the requested state is never conveyed back to the original user under these circumstances.
Сам факт возврата ответов 200 или определённых ответов 4xx и 6xx на запросы SUBSCRIBE может при определённых обстоятельствах создавать проблемы приватности, раскрывая конфиденциальную информацию о политике. В этих случаях уведомителю СЛЕДУЕТ всегда возвращать ответ 202. Хотя последующее сообщение NOTIFY может и не передавать истинное состояние, оно ДОЛЖНО выглядеть содержащим потенциально корректные данные с точки зрения подписчика, неотличимые от действительного ответа. Информация о том, авторизован ли пользователь подписываться на запрошенное состояние, при этих обстоятельствах никогда не передаётся обратно исходному пользователю.
Individual packages and their related documents for which such a mode of operation makes sense can further describe how and why to generate such potentially correct data. For example, such a mode of operation is mandated by RFC 2779 [6] for user presence information.
Отдельные пакеты и связанные с ними документы, для которых такой режим работы имеет смысл, могут дополнительно описать, как и почему формировать такие потенциально корректные данные. Например, такой режим работы предписан RFC 2779 [6] для информации о присутствии пользователя.
5.3. Denial-of-Service attacks
5.3. Атаки отказа в обслуживании
The current model (one SUBSCRIBE request triggers a SUBSCRIBE response and one or more NOTIFY requests) is a classic setup for an amplifier node to be used in a smurf attack.
Текущая модель (один запрос SUBSCRIBE вызывает один ответ SUBSCRIBE и один или несколько запросов NOTIFY) является классической схемой для использования узла-усилителя в smurf-атаке.
Also, the creation of state upon receipt of a SUBSCRIBE request can be used by attackers to consume resources on a victim's machine, rendering it unusable.
Кроме того, создание состояния по получении запроса SUBSCRIBE может использоваться злоумышленниками для расходования ресурсов на машине жертвы, делая её непригодной к использованию.
To reduce the chances of such an attack, implementations of notifiers SHOULD require authentication. Authentication issues are discussed in SIP [1].
Чтобы уменьшить вероятность такой атаки, реализациям уведомителей СЛЕДУЕТ требовать аутентификацию. Вопросы аутентификации обсуждаются в SIP [1].
5.4. Replay Attacks
5.4. Атаки повторного воспроизведения
Replaying of either SUBSCRIBE or NOTIFY can have detrimental effects.
Повторное воспроизведение как SUBSCRIBE, так и NOTIFY может иметь пагубные последствия.
In the case of SUBSCRIBE messages, attackers may be able to install any arbitrary subscription which it witnessed being installed at some point in the past. Replaying of NOTIFY messages may be used to spoof old state information (although a good versioning mechanism in the body of the NOTIFY messages may help mitigate such an attack). Note that the prohibition on sending NOTIFY messages to nodes which have not subscribed to an event also aids in mitigating the effects of such an attack.
В случае сообщений SUBSCRIBE злоумышленники могут быть в состоянии установить любую произвольную подписку, установку которой они наблюдали в некоторый момент в прошлом. Повторное воспроизведение сообщений NOTIFY может использоваться для подделки старой информации о состоянии (хотя хороший механизм версионирования в теле сообщений NOTIFY может помочь смягчить такую атаку). Обратите внимание, что запрет на отправку сообщений NOTIFY узлам, которые не подписались на событие, также способствует смягчению последствий такой атаки.
To prevent such attacks, implementations SHOULD require authentication with anti-replay protection. Authentication issues are discussed in SIP [1].
Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ требовать аутентификацию с защитой от повторного воспроизведения. Вопросы аутентификации обсуждаются в SIP [1].
5.5. Man-in-the middle attacks
5.5. Атаки «человек посередине»
Even with authentication, man-in-the-middle attacks using SUBSCRIBE may be used to install arbitrary subscriptions, hijack existing subscriptions, terminate outstanding subscriptions, or modify the resource to which a subscription is being made. To prevent such attacks, implementations SHOULD provide integrity protection across "Contact", "Route", "Expires", "Event", and "To" headers of SUBSCRIBE messages, at a minimum. If SUBSCRIBE bodies are used to define further information about the state of the call, they SHOULD be included in the integrity protection scheme.
Даже при наличии аутентификации атаки «человек посередине» с использованием SUBSCRIBE могут применяться для установки произвольных подписок, перехвата существующих подписок, прекращения действующих подписок или изменения ресурса, на который выполняется подписка. Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ обеспечивать защиту целостности как минимум заголовков «Contact», «Route», «Expires», «Event» и «To» сообщений SUBSCRIBE. Если тела SUBSCRIBE используются для определения дополнительной информации о состоянии вызова, они СЛЕДУЕТ включать в схему защиты целостности.
Man-in-the-middle attacks may also attempt to use NOTIFY messages to spoof arbitrary state information and/or terminate outstanding subscriptions. To prevent such attacks, implementations SHOULD provide integrity protection across the "Call-ID", "CSeq", and "Subscription-State" headers and the bodies of NOTIFY messages.
Атаки «человек посередине» также могут пытаться использовать сообщения NOTIFY для подделки произвольной информации о состоянии и/или прекращения действующих подписок. Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ обеспечивать защиту целостности заголовков «Call-ID», «CSeq» и «Subscription-State» и тел сообщений NOTIFY.
Integrity protection of message headers and bodies is discussed in SIP [1].
Защита целостности заголовков и тел сообщений обсуждается в SIP [1].
5.6. Confidentiality
5.6. Конфиденциальность
The state information contained in a NOTIFY message has the potential to contain sensitive information. Implementations MAY encrypt such information to ensure confidentiality.
Информация о состоянии, содержащаяся в сообщении NOTIFY, потенциально может содержать конфиденциальную информацию. Реализации МОГУТ шифровать такую информацию для обеспечения конфиденциальности.
While less likely, it is also possible that the information contained in a SUBSCRIBE message contains information that users might not want to have revealed. Implementations MAY encrypt such information to ensure confidentiality. To allow the remote party to hide information it considers sensitive, all implementations SHOULD be able to handle encrypted SUBSCRIBE and NOTIFY messages.
Хотя это менее вероятно, также возможно, что информация, содержащаяся в сообщении SUBSCRIBE, содержит сведения, которые пользователи могли бы не хотеть раскрывать. Реализации МОГУТ шифровать такую информацию для обеспечения конфиденциальности. Чтобы позволить удалённой стороне скрывать информацию, которую она считает конфиденциальной, все реализации СЛЕДУЕТ быть способны обрабатывать зашифрованные сообщения SUBSCRIBE и NOTIFY.
The mechanisms for providing confidentiality are detailed in SIP [1].
Механизмы обеспечения конфиденциальности подробно описаны в SIP [1].
6. IANA Considerations
6. Вопросы IANA
This document defines an event-type namespace which requires a central coordinating body. The body chosen for this coordination is the Internet Assigned Numbers Authority (IANA).
Настоящий документ определяет пространство имён типов событий, которое требует центрального координирующего органа. Органом, выбранным для этой координации, является Администрация адресного пространства Интернета (IANA).
There are two different types of event-types: normal event packages, and event template-packages; see section 4.2. To avoid confusion, template-package names and package names share the same namespace; in other words, an event template-package MUST NOT share a name with a package.
Существует два различных типа типов событий: обычные пакеты событий и шаблонные пакеты событий; см. раздел 4.2. Во избежание путаницы имена шаблонных пакетов и имена пакетов совместно используют одно пространство имён; иными словами, шаблонный пакет событий НЕ ДОЛЖЕН разделять имя с пакетом.
Following the policies outlined in "Guidelines for Writing an IANA Considerations Section in RFCs" [4], normal event package identification tokens are allocated as First Come First Served, and event template-package identification tokens are allocated on a IETF Consensus basis.
Следуя политикам, изложенным в «Guidelines for Writing an IANA Considerations Section in RFCs» [4], токены идентификации обычных пакетов событий распределяются по принципу «первым пришёл — первым обслужен», а токены идентификации шаблонных пакетов событий распределяются на основе консенсуса IETF.
Registrations with the IANA MUST include the token being registered and whether the token is a package or a template-package. Further, packages MUST include contact information for the party responsible for the registration and/or a published document which describes the event package. Event template-package token registrations MUST include a pointer to the published RFC which defines the event template-package.
Регистрации в IANA ДОЛЖНЫ включать регистрируемый токен и указание, является ли токен пакетом или шаблонным пакетом. Кроме того, пакеты ДОЛЖНЫ включать контактную информацию стороны, ответственной за регистрацию, и/или опубликованный документ, описывающий пакет событий. Регистрации токенов шаблонных пакетов событий ДОЛЖНЫ включать указатель на опубликованный RFC, определяющий шаблонный пакет событий.
Registered tokens to designate packages and template-packages MUST NOT contain the character ".", which is used to separate template- packages from packages.
Зарегистрированные токены для обозначения пакетов и шаблонных пакетов НЕ ДОЛЖНЫ содержать символ «.», который используется для отделения шаблонных пакетов от пакетов.
