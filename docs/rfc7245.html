Abstract
Аннотация
Session recording is a critical requirement in many communications environments such as call centers and financial trading. In some of these environments, all calls must be recorded for regulatory, compliance, and consumer protection reasons. Recording of a session is typically performed by sending a copy of a media stream to a recording device. This document describes architectures for deploying session recording solutions in an environment that is based on the Session Initiation Protocol (SIP).
Запись сеансов является критически важным требованием во многих средах связи, таких как контакт-центры и финансовые торги. В некоторых из этих сред все вызовы должны записываться по регуляторным, нормативным причинам и причинам защиты прав потребителей. Запись сеанса обычно выполняется путём отправки копии медиапотока на устройство записи. Настоящий документ описывает архитектуры развёртывания решений записи сеансов в среде, основанной на протоколе инициирования сессий (SIP).

1. Introduction
1. Введение
Session recording is a critical requirement in many communications environments such as call centers and financial trading. In some of these environments, all calls must be recorded for regulatory, compliance, and consumer protection reasons. Recording of a session is typically performed by sending a copy of a media stream to a recording device. This document describes architectures for deploying session recording solutions as defined in "Use Cases and Requirements for SIP-Based Media Recording (SIPREC)" [RFC6341].
Запись сеансов является критически важным требованием во многих средах связи, таких как контакт-центры и финансовые торги. В некоторых из этих сред все вызовы должны записываться по регуляторным, нормативным причинам и причинам защиты прав потребителей. Запись сеанса обычно выполняется путём отправки копии медиапотока на устройство записи. Настоящий документ описывает архитектуры развёртывания решений записи сеансов, как определено в документе «Use Cases and Requirements for SIP-Based Media Recording (SIPREC)» [RFC6341].
This document focuses on how sessions are established between a Session Recording Client (SRC) and the Session Recording Server (SRS) for the purpose of conveying the Replicated Media and Recording Metadata (e.g., identity of the parties involved) relating to the Communication Session.
Настоящий документ посвящён тому, как устанавливаются сеансы между клиентом записи (SRC) и сервером записи (SRS) с целью передачи реплицируемых медиа и метаданных записи (например, идентичности участвующих в нём сторон), относящихся к сеансу связи.
Once the Replicated Media and Recording Metadata have been received by the SRS, they will typically be archived for retrieval at a later time. The procedures relating to the archiving and retrieval of this information are outside the scope of this document.
После получения реплицируемых медиа и метаданных записи сервером записи они обычно архивируются для извлечения в более позднее время. Процедуры, относящиеся к архивированию и извлечению этой информации, выходят за рамки настоящего документа.
This document only considers active recording, where the SRC purposefully streams media to a SRS. Passive recording, where a recording device detects media directly from the network (e.g., using port-mirroring techniques), is outside the scope of this document. In addition, lawful intercept is outside the scope of this document, which takes account of the IETF policy on wiretapping [RFC2804].
Настоящий документ рассматривает только активную запись, когда клиент записи намеренно передаёт медиа серверу записи. Пассивная запись, когда устройство записи обнаруживает медиа непосредственно в сети (например, с использованием методов зеркалирования портов), выходит за рамки настоящего документа. Кроме того, законный перехват выходит за рамки настоящего документа, который учитывает политику IETF в отношении прослушивания [RFC2804].
The Recording Session that is established between the SRC and the SRS uses the normal procedures for establishing INVITE-initiated dialogs as specified in [RFC3261] and uses the Session Description Protocol (SDP) for describing the media to be used during the session as specified in [RFC4566]. However, it is intended that some extensions to SIP (e.g., Headers, Option Tags, etc.) will be defined to support the requirements for media recording. The Replicated Media is required to be sent in real-time to the SRS and is not buffered by the SRC to allow for real-time analysis of the media by the SRS.
Сеанс записи, устанавливаемый между SRC и SRS, использует обычные процедуры установления диалогов по инициативе INVITE, как указано в [RFC3261], и протокол описания сеанса (SDP) для описания медиа, используемых во время сеанса, как указано в [RFC4566]. Однако предполагается, что будут определены некоторые расширения SIP (например, заголовки, теги параметров и т. д.) для поддержки требований к записи медиа. Реплицируемые медиа должны передаваться серверу записи в реальном времени и не буферизуются клиентом записи, чтобы сервер записи мог анализировать медиа в реальном времени.
2. Definitions
2. Определения
The first four definitions are quoted from RFC 6341.
Первые четыре определения цитируются из RFC 6341.
Session Recording Server (SRS): A Session Recording Server (SRS) is a SIP User Agent (UA) that is a specialized media server or collector that acts as the sink of the recorded media. An SRS is typically implemented as a multi-port device that is capable of receiving media from multiple sources simultaneously. An SRS is the sink of the recorded session metadata.
Сервер записи (SRS): сервер записи (SRS) — это пользовательский агент SIP (UA), представляющий собой специализированный медиасервер или сборщик, который действует как приёмник записываемых медиа. SRS обычно реализуется как многопортовое устройство, способное одновременно принимать медиа из нескольких источников. SRS является приёмником метаданных записываемого сеанса.
Session Recording Client (SRC): A Session Recording Client (SRC) is a SIP User Agent (UA) that acts as the source of the recorded media, sending it to the SRS. An SRC is a logical function. Its capabilities may be implemented across one or more physical devices. In practice, an SRC could be a personal device (such as a SIP phone), a SIP Media Gateway (MG), a Session Border Controller (SBC), or a SIP Media Server (MS) integrated with an Application Server (AS). This specification defines the term "SRC" such that all such SIP entities can be generically addressed under one definition. The SRC provides metadata to the SRS.
Клиент записи (SRC): клиент записи (SRC) — это пользовательский агент SIP (UA), который действует как источник записываемых медиа, отправляя их серверу записи. SRC является логической функцией. Его возможности могут быть реализованы в одном или нескольких физических устройствах. На практике SRC может быть персональным устройством (например, SIP-телефоном), медиашлюзом SIP (MG), контроллером границ сеансов (SBC) или медиасервером SIP (MS), интегрированным с сервером приложений (AS). Настоящая спецификация определяет термин «SRC» так, чтобы все такие объекты SIP можно было обобщённо адресовать в рамках одного определения. SRC предоставляет метаданные серверу записи.
Communication Session (CS): A session created between two or more SIP User Agents (UAs) that is the subject of recording.
Сеанс связи (CS): сеанс, созданный между двумя или более пользовательскими агентами SIP (UA), который является предметом записи.
Recording Session (RS): The SIP session created between an SRC and SRS for the purpose of recording a CS.
Сеанс записи (RS): сеанс SIP, созданный между клиентом записи (SRC) и сервером записи (SRS) с целью записи сеанса связи.
The following terms are defined by this document.
Следующие термины определяются в настоящем документе.
Recording-aware User Agent (UA): A SIP User Agent that is aware of SIP extensions associated with the CS. Such extensions may be used to notify the recording-aware UA that a session is being recorded, or by a recording-aware UA to express preferences as to whether a recording should be started, paused, resumed, or stopped.
UA, осведомлённый о записи (Recording-aware UA): пользовательский агент SIP, который осведомлён о расширениях SIP, связанных с сеансом связи. Такие расширения могут использоваться для уведомления осведомлённого о записи UA о том, что сеанс записывается, либо осведомлённым о записи UA для выражения предпочтений относительно того, следует ли начать, приостановить, возобновить или остановить запись.
Recording-unaware User Agent (UA): A SIP User Agent that is unaware of SIP extensions associated with the CS. Such a recording- unaware UA will be notified that a session is being recorded or will express preferences as to whether a recording should be started, paused, resumed, or stopped via some other means that is out of scope for the SIP media recording architecture.
UA, не осведомлённый о записи (Recording-unaware UA): пользовательский агент SIP, который не осведомлён о расширениях SIP, связанных с сеансом связи. Такой не осведомлённый о записи UA будет уведомлён о том, что сеанс записывается, либо выразит предпочтения относительно того, следует ли начать, приостановить, возобновить или остановить запись, иными средствами, выходящими за рамки архитектуры записи медиа на основе SIP.
Recording Metadata: The metadata describing the CS that is required by the SRS. This will include, for example, the identities of users that participate in the CS and dialog state. Typically, this metadata is archived with the Replicated Media at the SRS. The recording metadata is delivered in real-time to the SRS.
Метаданные записи: метаданные, описывающие сеанс связи, которые требуются серверу записи. Они будут включать, например, идентичности пользователей, участвующих в сеансе связи, и состояние диалога. Обычно эти метаданные архивируются вместе с реплицируемыми медиа на сервере записи. Метаданные записи передаются серверу записи в реальном времени.
Replicated Media: A copy of the media that is associated with the CS, was created by the SRC, and was sent to the SRS. It may contain all the media associated with the CS (e.g., audio and video) or just a subset (e.g., audio). Replicated Media is part of the Recording Session.
Реплицируемые медиа: копия медиа, связанных с сеансом связи, созданная клиентом записи и отправленная серверу записи. Они могут содержать все медиа, связанные с сеансом связи (например, аудио и видео), или только подмножество (например, аудио). Реплицируемые медиа являются частью сеанса записи.
3. Session Recording Architecture
3. Архитектура записи сеансов
3.1. Location of the SRC
3.1. Расположение SRC
This section contains some example session recording architectures showing how the SRC is a logical function that can be located in or split between various physical components.
Этот раздел содержит некоторые примеры архитектур записи сеансов, показывающие, что SRC является логической функцией, которая может находиться в различных физических компонентах или распределяться между ними.
3.1.1. B2BUA Acts as a SRC
3.1.1. B2BUA в роли SRC
A SIP Back-to-Back User Agent (B2BUA) that has access to the media to be recorded may act as an SRC. The B2BUA may already be aware that a session needs to be recorded before the initial establishment of the CS, or the decision to record the session may occur after the session has been established.
Пользовательский агент SIP типа «спина к спине» (B2BUA), имеющий доступ к медиа, подлежащим записи, может действовать как SRC. B2BUA может уже знать, что сеанс нужно записать, до начального установления сеанса связи, либо решение о записи сеанса может быть принято после установления сеанса.
If the SRC makes the decision to initiate the RS, then it will do so by sending a SIP INVITE request to the SRS.
Если SRC принимает решение инициировать сеанс записи, то он делает это путём отправки запроса INVITE SIP серверу записи.
If the SRS makes the decision to initiate the Recording Session, then it will initiate the establishment of a SIP RS by sending an INVITE to the SRC.
Если SRS принимает решение инициировать сеанс записи, то он инициирует установление SIP-сеанса записи путём отправки INVITE клиенту записи.
The RS INVITE contains information that identifies the session as being established for the purposes of recording and prevents the session from being accidentally rerouted to a UA that is not an SRS if the RS was initiated by the SRC or vice versa.
INVITE сеанса записи содержит информацию, идентифицирующую сеанс как устанавливаемый с целью записи, и предотвращает случайную перемаршрутизацию сеанса к UA, не являющемуся SRS, если сеанс записи был инициирован SRC, или наоборот.
The B2BUA/SRC is responsible for notifying the UAs involved in the CS that the session is being recorded.
B2BUA/SRC отвечает за уведомление UA, участвующих в сеансе связи, о том, что сеанс записывается.
The B2BUA/SRC is responsible for complying with requests from recording aware UAs or through some configured policies indicating that the CS should not be recorded.
B2BUA/SRC отвечает за выполнение запросов от осведомлённых о записи UA или в соответствии с некоторыми настроенными политиками, указывающими, что сеанс связи не должен записываться.

3.1.2. Endpoint Acts as SRC
3.1.2. Оконечная точка в роли SRC
A SIP endpoint / UA may act as a SRC. In that case, the endpoint sends the Replicated Media to the SRS.
Оконечная точка SIP / UA может действовать как SRC. В этом случае оконечная точка отправляет реплицируемые медиа серверу записи.
If the endpoint makes the decision to initiate the Recording Session, then it will initiate the establishment of a SIP Session by sending an INVITE to the SRS.
Если оконечная точка принимает решение инициировать сеанс записи, то она инициирует установление сеанса SIP путём отправки INVITE серверу записи.
If the SRS makes the decision to initiate the Recording Session, then it will initiate the establishment of a SIP Session by sending an INVITE to the endpoint. The actual decision mechanism is out of scope for the SIP media recording architecture.
Если SRS принимает решение инициировать сеанс записи, то он инициирует установление сеанса SIP путём отправки INVITE оконечной точке. Фактический механизм принятия решения выходит за рамки архитектуры записи медиа на основе SIP.

3.1.3. A SIP Proxy Cannot Be a SRC
3.1.3. SIP-прокси не может быть SRC
A SIP Proxy is unable to act as an SRC because it does not have access to the media and therefore has no way of enabling the delivery of the Replicated Media to the SRS.
SIP-прокси не способен действовать как SRC, поскольку он не имеет доступа к медиа и, следовательно, не может обеспечить доставку реплицируемых медиа серверу записи.
3.1.4. Interaction with MEDIACTRL
3.1.4. Взаимодействие с MEDIACTRL
The MEDIACTRL architecture [RFC5567] describes an architecture in which an Application Server (AS) controls a Media Server (MS), which may be used for purposes such as conferencing and recording media streams. In the architecture described in [RFC5567], the AS typically uses SIP Third Party Call Control (3PCC) to instruct the SIP UAs to direct their media to the Media Server.
Архитектура MEDIACTRL [RFC5567] описывает архитектуру, в которой сервер приложений (AS) управляет медиасервером (MS), который может использоваться для таких целей, как конференции и запись медиапотоков. В архитектуре, описанной в [RFC5567], AS обычно использует управление вызовами третьей стороны SIP (3PCC), чтобы указать UA SIP направлять свои медиа на медиасервер.
The SRC or the SRS described in this document may be architected according to [RFC5567]; therefore, when further decomposed, they may be made up of an AS that uses a MEDIACTRL interface to control an MS.
SRC или SRS, описанные в настоящем документе, могут быть построены в соответствии с [RFC5567]; поэтому при дальнейшей декомпозиции они могут состоять из AS, который использует интерфейс MEDIACTRL для управления MS.
As shown in Figure 3, when the SRS is architected according to [RFC5567], the MS acts as a sink of the recording media, and the AS acts as a sink of the metadata and the termination point for RS SIP signaling. As shown in Figure 4, when the SRC is architected according to [RFC5567], the MS acts as a source of recording media, and the AS acts as a source of the metadata and the termination point for RS SIP signaling.
Как показано на рисунке 3, когда SRS построен в соответствии с [RFC5567], MS действует как приёмник медиа записи, а AS действует как приёмник метаданных и точка завершения сигнализации SIP сеанса записи. 3.1.5. Interaction with Conference Focus
3.1.5. Взаимодействие с фокусом конференции
In the case of a centralized conference, a combination of the conference focus and mixer [RFC4353] may act as a SRC and therefore provide the SRS with the Replicated Media and associated recording metadata. In this arrangement, the SRC is able to provide media and metadata relating to each of the participants, including, for example, any side conversations where the media passes through the mixer.
В случае централизованной конференции комбинация фокуса конференции и микшера [RFC4353] может действовать как SRC и, таким образом, предоставлять серверу записи реплицируемые медиа и связанные метаданные записи. В такой конфигурации SRC способен предоставлять медиа и метаданные, относящиеся к каждому из участников, включая, например, любые побочные разговоры, когда медиа проходят через микшер.
The conference focus can either provide mixed Replicated Media or separate streams per conference participant (as depicted in Figure 5).
Фокус конференции может предоставлять либо смешанные реплицируемые медиа, либо отдельные потоки для каждого участника конференции (как показано на рисунке 5).
The conference focus may also act as a recording-aware UA in the case when one of the participants acts as a SRC.
Фокус конференции может также действовать как UA, осведомлённый о записи, в случае, когда один из участников действует как SRC.
In an alternative arrangement, a SIP endpoint that is a conference participant can act as an SRC. The SRC will in this case have access to the media and metadata relating to that particular participant and may be able to obtain additional metadata from the conference focus. The SRC may, for example, use the conference event package as described in [RFC4575] to obtain information about other participants that it provides to the SRS within the recording metadata.
В альтернативной конфигурации оконечная точка SIP, являющаяся участником конференции, может действовать как SRC. В этом случае SRC будет иметь доступ к медиа и метаданным, относящимся к этому конкретному участнику, и может быть способен получать дополнительные метаданные от фокуса конференции. SRC может, например, использовать пакет событий конференции, как описано в [RFC4575], для получения информации о других участниках, которую он предоставляет серверу записи в составе метаданных записи.
The SRC may be involved in the conference from the very beginning or may join at some later point of time.
SRC может быть вовлечён в конференцию с самого начала или присоединиться в некоторый более поздний момент времени.

3.2. Establishing the Recording Session
3.2. Установление сеанса записи
The SRC or the SRS may initiate the Recording Session.
SRC или SRS могут инициировать сеанс записи.
It should be noted that the Recording Session is independent from the CS that is being recorded at both the SIP dialog level and at the session level.
Следует отметить, что сеанс записи независим от сеанса связи, который записывается, как на уровне диалога SIP, так и на уровне сеанса.
Concerning media negotiation, regular SIP/SDP capabilities should be used, and existing transcoding capabilities and media encryption should not be precluded.
Что касается согласования медиа, следует использовать обычные возможности SIP/SDP, а существующие возможности транскодирования и шифрование медиа не должны исключаться.
3.2.1. SRC-Initiated Recording
3.2.1. Запись, инициируемая SRC
When the SRC initiates the Recording Session for the purpose of conveying media to the SRS, it performs the following actions:
Когда SRC инициирует сеанс записи с целью передачи медиа серверу записи, он при этом выполняет следующие действия:
o Is provisioned with a Unified Resource Identifier (URI) for the SRS; the URI is resolved through normal [RFC3263] procedures.
o Снабжается унифицированным идентификатором ресурса (URI) для SRS; URI разрешается с помощью обычных процедур [RFC3263].
o Initiates the dialog by sending an INVITE request to the SRS. The
o Инициирует диалог путём отправки запроса INVITE серверу записи. Этот
dialog is established according to the normal procedures for establishing an INVITE-initiated dialog as specified in [RFC3261].
диалог устанавливается в соответствии с обычными процедурами установления диалога по инициативе INVITE, как указано в [RFC3261].
o Includes in the INVITE an indication that the session is established for the purpose of recording the associated media.
o Включает в INVITE указание на то, что данный сеанс устанавливается с целью записи связанных с ним медиа.
o Includes an SDP attribute of "a=sendonly" for each media line if the Replicated Media is to be started immediately, or includes "a=inactive" if it is not ready to transmit the media.
o Включает атрибут SDP «a=sendonly» для каждой медиалинии, если реплицируемые медиа должны быть запущены немедленно, или включает «a=inactive», если он не готов передавать медиа.
o Replicates the media streams that are to be recorded and transmits the media to the SRS.
o Реплицирует медиапотоки, подлежащие записи, и передаёт медиа серверу записи.
The Recording Session may replicate all media associated with the CS or only a subset.
Сеанс записи может реплицировать все медиа, связанные с сеансом связи, или только их подмножество.
3.2.2. SRS-Initiated Recording
3.2.2. Запись, инициируемая SRS
When the SRS initiates the media Recording Session with the SRC, it performs the following actions:
Когда SRS инициирует сеанс записи медиа с клиентом записи (SRC), он выполняет следующие действия:
o Is provisioned with a Unified Resource Identifier (URI) for the SRC; the URI is resolved through normal [RFC3263] procedures.
o Снабжается унифицированным идентификатором ресурса (URI) для SRC; URI разрешается с помощью обычных процедур [RFC3263].
o Sends an INVITE request to the SRC.
o Отправляет запрос INVITE клиенту записи.
o Includes in the INVITE an indication that the session is established for the purpose of recording the associated media.
o Включает в INVITE указание на то, что данный сеанс устанавливается с целью записи связанных с ним медиа.
o Identifies the sessions that are to be recorded. The actual
o Идентифицирует сеансы, подлежащие записи. Фактический
mechanism of the identification depends on SRC policy.
механизм идентификации зависит от политики SRC.
o Includes an SDP attribute of "a=recvonly" for each media line if the Recording Session is to be started immediately, or includes "a=inactive" if it is not ready to receive the media.
o Включает атрибут SDP «a=recvonly» для каждой медиалинии, если сеанс записи должен быть запущен немедленно, или включает «a=inactive», если он не готов принимать медиа.
If the SRS does not have prior knowledge of what media streams are available to be recorded, it can make use of an offerless INVITE, which allows the SRC to make the initial SDP offer.
Если SRS не имеет предварительного знания о том, какие медиапотоки доступны для записи, он может использовать INVITE без предложения, что позволяет SRC сформировать начальное предложение SDP.
3.2.3. Pause/Resume Recording Session
3.2.3. Приостановка и возобновление сеанса записи
The SRS or the SRC may pause the recording by changing the SDP direction attribute to "inactive" and resume the recording by changing the direction back to "recvonly" or "sendonly".
SRS или SRC может приостановить запись, изменив атрибут направления SDP на «inactive», и возобновить запись, изменив направление обратно на «recvonly» или «sendonly».
3.2.4. Media Stream Mixing
3.2.4. Смешивание медиапотоков
In a basic session involving only audio, there are typically two audio/RTP streams between the two UAs involved in transporting media in each direction. When recording this media, the two streams may be mixed or not mixed at the SRC before being transmitted to the SRS. In the case when they are not mixed, two separate streams are sent to the SRS, and the SDP offer sent to the SRS must describe two separate media streams. In the mixed case, a single mixed media stream is sent to the SRS.
В базовом сеансе, включающем только аудио, обычно имеются два аудиопотока/RTP между двумя UA, участвующими в передаче медиа в каждом направлении. При записи этих медиа два потока могут быть смешаны или не смешаны в SRC перед передачей серверу записи. В случае, когда они не смешаны, серверу записи отправляются два отдельных потока, и предложение SDP, отправляемое серверу записи, должно описывать два отдельных медиапотока. В случае смешивания серверу записи отправляется один смешанный медиапоток.
3.2.5. Media Transcoding
3.2.5. Транскодирование медиа
The CS and the RS are negotiated separately using the standard SDP offer/answer exchange which may result in the SRC having to perform media transcoding between the two sessions. If the SRC is not capable of performing media transcoding it may limit the media formats in the offer to the SRS depending on what media is negotiated on the CS or may limit what it includes in the offer on the CS if it has prior knowledge of the media formats supported by the SRS. However typically the SRS will be a more capable device which can provide a wide range of media format options to the SRC and may also be able to make use of a media transcoder as detailed in [RFC5369].
Сеанс связи и сеанс записи согласуются отдельно с использованием стандартного обмена предложением/ответом SDP, что может привести к тому, что SRC придётся выполнять транскодирование медиа между двумя сеансами. Если SRC не способен выполнять транскодирование медиа, он может ограничить форматы медиа в предложении серверу записи в зависимости от того, какие медиа согласованы в сеансе связи, или может ограничить то, что он включает в предложение в сеансе связи, если у него есть предварительное знание о форматах медиа, поддерживаемых сервером записи. Однако обычно SRS будет более функциональным устройством, которое может предоставить SRC широкий диапазон вариантов форматов медиа и также может использовать транскодер медиа, как подробно описано в [RFC5369].
3.2.6. Lossless Recording
3.2.6. Запись без потерь
Session recording may be a regulatory requirement in certain communication environments. Such environments may impose a requirement generally known as "lossless recording". An overall solution for lossless recording may involve multiple layers of solutions. Individual aspects of the solutions may range from administering networks for appropriate QoS, reliable transmission of recorded media, and perhaps certain SIPREC protocol-level capabilities in SRC and SRS.
Запись сеансов может быть регуляторным требованием в определённых средах связи. Такие среды могут налагать требование, известное как «запись без потерь». Общее решение для записи без потерь может включать несколько уровней решений. Отдельные аспекты решений могут варьироваться от администрирования сетей для надлежащего QoS, надёжной передачи записываемых медиа и, возможно, определённых возможностей протокола SIPREC на уровне SRC и SRS.
3.3. Recording Metadata
3.3. Метаданные записи
3.3.1. Contents of Recording Metadata
3.3.1. Содержание метаданных записи
The metadata model is defined in [REC-METADATA].
Модель метаданных определена в [REC-METADATA].
3.3.2. Mechanisms for Delivery of Metadata to SRS
3.3.2. Механизмы доставки метаданных серверу записи
The SRS obtains session recording metadata from the SRC. The metadata is transported via SIP-based mechanisms as specified in [REC-PROTOCOL]
SRS получает метаданные записи сеанса от SRC. Метаданные передаются посредством механизмов на основе SIP, как указано в [REC-PROTOCOL].
It is also possible that metadata is transported via non-SIP-based mechanisms, but these are considered out of scope.
Также возможно, что метаданные передаются посредством механизмов, не основанных на SIP, но они считаются выходящими за рамки рассмотрения.
It is also possible to have an RS session without the metadata; in that case, the SRS will be receiving the metadata by some other means or not at all.
Также возможно наличие сеанса записи без метаданных; в этом случае SRS будет получать метаданные каким-либо иным способом или не получать их вовсе.
3.4. Notifications to the Recorded User Agents
3.4. Уведомления записываемым пользовательским агентам
Typically, a user that is involved in a session that is to be recorded is notified by an announcement at the beginning of the session or may receive some warning tones within the media. However, SIPREC enables an indication that the call is being recorded to be included in the SIP requests and responses associated with that CS.
Обычно пользователь, участвующий в сеансе, который должен записываться, уведомляется объявлением в начале сеанса или может получать некоторые предупреждающие тоны в медиа. Однако SIPREC позволяет включать указание на то, что вызов записывается, в запросы и ответы SIP, связанные с этим сеансом связи.
The SRC provides the notification to all SIP UAs for which it is replicating received media for the purpose of recording. If the SRC is acting as a SIP endpoint, as described in Section 3.1.2, then it also provides a notification to the local user.
SRC предоставляет уведомление всем SIP UA, для которых он реплицирует принятые медиа с целью записи. Если SRC действует как оконечная точка SIP, как описано в разделе 3.1.2, то он также предоставляет уведомление локальному пользователю.
3.5. Preventing the Recording of a SIP Session
3.5. Предотвращение записи сеанса SIP
During the initial session establishment or during an established session, a recording-aware UA may provide an indication of its preference with regard to recording the media in the CS. The mechanisms for this are specified in [REC-PROTOCOL]
Во время начального установления сеанса или во время установленного сеанса UA, осведомлённый о записи, может предоставить указание своего предпочтения в отношении записи медиа в сеансе связи. Механизмы для этого указаны в [REC-PROTOCOL].

4. Вопросы IANA
This document has no actions for IANA. This document mentions SIP/SDP extensions. The associated IANA considerations are addressed in [REC-PROTOCOL], which defines them.
Настоящий документ не содержит действий для IANA. Настоящий документ упоминает расширения SIP/SDP. Соответствующие вопросы IANA рассматриваются в [REC-PROTOCOL], который их определяет.
5. Security Considerations
5. Вопросы безопасности
The Recording Session is fundamentally a standard SIP dialog and media session and therefore makes use of existing SIP security mechanisms for securing the Recording Session and Recording Metadata.
Сеанс записи по сути является стандартным диалогом и медиасеансом SIP и поэтому использует существующие механизмы безопасности SIP для защиты сеанса записи и метаданных записи.
The intended use of this architecture is only for the case where the users are aware that they are being recorded, and the architecture provides the means for the SRC to notify users that they are being recorded.
Предполагаемое использование этой архитектуры — только для случая, когда пользователи осведомлены о том, что их записывают, и архитектура предоставляет SRC средства для уведомления пользователей о том, что их записывают.
This architectural solution is not intended to support lawful intercept, which in contrast requires that users are not informed.
Это архитектурное решение не предназначено для поддержки законного перехвата, который, напротив, требует, чтобы пользователи не были информированы.
It is the responsibility of the SRS to protect the Replicated Media and Recording Metadata once it has been received and archived. The stored content must be protected using a cipher at least as strong (or stronger) than the original content; however, the mechanism for protecting the storage and retrieval from the SRS is out of scope of this work. The keys used to store the data must also be securely maintained by the SRS and should only be released, securely, to authorized parties. How to secure these keys, properly authorize a receiving party, or securely distribute the keying material is also out of scope of this work.
Ответственность SRS — защищать реплицируемые медиа и метаданные записи после их получения и архивирования. Сохранённое содержимое должно защищаться с использованием шифра как минимум не слабее (или сильнее) исходного содержимого; однако механизм защиты хранения и извлечения из SRS выходит за рамки этой работы. Ключи, используемые для хранения данных, также должны надёжно поддерживаться SRS и должны предоставляться только уполномоченным сторонам и только безопасным способом. То, как защитить эти ключи, надлежащим образом авторизовать получающую сторону или безопасно распространить ключевой материал, также выходит за рамки этой работы.
Protection of the RS should not be weaker than protection of the CS and may need to be stronger because the media is retransmitted (allowing more possibility for interception). This applies to both the signaling and media paths.
Защита сеанса записи не должна быть слабее защиты сеанса связи и может потребовать быть сильнее, потому что медиа передаются повторно (что допускает больше возможностей для перехвата). Это относится как к путям сигнализации, так и к путям медиа.
It is essential that the SRC will authenticate the SRS because the client must be certain that it is recording on the right recording system. It is less important that the SRS authenticate the SRC, but implementations must have the ability to perform mutual authentication.
Существенно, чтобы SRC аутентифицировал SRS, поскольку клиент должен быть уверен, что записывает в правильной системе записи. Менее важно, чтобы SRS аутентифицировал SRC, но реализации должны иметь возможность выполнять взаимную аутентификацию.
In some environments, it is desirable to not decrypt and re-encrypt the media. This means the same media encryption key is negotiated and used within the CS and RS. If for any reason the media are decrypted on the CS and are re-encrypted on the RS, a new key must be used.
В некоторых средах желательно не расшифровывать и повторно шифровать медиа. Это означает, что один и тот же ключ шифрования медиа согласуется и используется в сеансе связи и сеансе записи. Если по какой-либо причине медиа расшифровываются в сеансе связи и повторно шифруются в сеансе записи, должен использоваться новый ключ.
The retrieval mechanism for media recorded by this protocol is out of scope. Implementations of retrieval mechanisms should consider the security implications carefully, as the retriever is not usually a party to the call that was recorded. Retrievers should be authenticated carefully. The cryptosuites on the retrieval should be no less strong than those used on the RS and may need to be stronger.
Механизм извлечения медиа, записанных по этому протоколу, выходит за рамки рассмотрения. Реализации механизмов извлечения должны тщательно учитывать последствия для безопасности, поскольку извлекающая сторона обычно не является участником записанного вызова. Извлекающие стороны должны тщательно аутентифицироваться. Криптонаборы при извлечении должны быть не слабее используемых в сеансе записи и могут потребовать быть сильнее.
