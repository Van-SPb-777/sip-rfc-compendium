Session Traversal Utilities for NAT (STUN)
Утилиты обхода сеансов для NAT (STUN)
Abstract
Аннотация
Session Traversal Utilities for NAT (STUN) is a protocol that serves as a tool for other protocols in dealing with NAT traversal. It can be used by an endpoint to determine the IP address and port allocated to it by a NAT. It can also be used to check connectivity between two endpoints and as a keep-alive protocol to maintain NAT bindings. STUN works with many existing NATs and does not require any special behavior from them.
Session Traversal Utilities for NAT (STUN) — это протокол, служащий инструментом для других протоколов при работе с обходом NAT. Он может использоваться конечной точкой для определения IP-адреса и порта, выделенных ей NAT. Он также может использоваться для проверки связности между двумя конечными точками и как протокол поддержания активности для сохранения привязок NAT. STUN работает со многими существующими NAT и не требует от них какого-либо особого поведения.
STUN is not a NAT traversal solution by itself. Rather, it is a tool to be used in the context of a NAT traversal solution.
Сам по себе STUN не является решением для обхода NAT. Это инструмент, используемый в контексте решения для обхода NAT.

1. Introduction
1. Введение
The protocol defined in this specification, Session Traversal Utilities for NAT (STUN), provides a tool for dealing with Network Address Translators (NATs). It provides a means for an endpoint to determine the IP address and port allocated by a NAT that corresponds to its private IP address and port. It also provides a way for an endpoint to keep a NAT binding alive. With some extensions, the protocol can be used to do connectivity checks between two endpoints [RFC8445] or to relay packets between two endpoints [RFC5766].
Определяемый в данной спецификации протокол Session Traversal Utilities for NAT (STUN) предоставляет инструмент для работы с трансляторами сетевых адресов (NAT). Он даёт конечной точке средство определения IP-адреса и порта, выделенных NAT и соответствующих её частному IP-адресу и порту. Он также даёт конечной точке способ поддерживать привязку NAT в активном состоянии. С некоторыми расширениями протокол может использоваться для проверки связности между двумя конечными точками [RFC8445] или для ретрансляции пакетов между двумя конечными точками [RFC5766].
In keeping with its tool nature, this specification defines an extensible packet format, defines operation over several transport protocols, and provides for two forms of authentication.
В соответствии со своей инструментальной природой данная спецификация определяет расширяемый формат пакетов, определяет работу поверх нескольких транспортных протоколов и предусматривает две формы аутентификации.
STUN is intended to be used in the context of one or more NAT traversal solutions. These solutions are known as "STUN Usages". Each usage describes how STUN is utilized to achieve the NAT traversal solution. Typically, a usage indicates when STUN messages get sent, which optional attributes to include, what server is used, and what authentication mechanism is to be used. Interactive Connectivity Establishment (ICE) [RFC8445] is one usage of STUN. SIP Outbound [RFC5626] is another usage of STUN. In some cases, a usage will require extensions to STUN. A STUN extension can be in the form of new methods, attributes, or error response codes. More information on STUN Usages can be found in Section 13.
STUN предназначен для использования в контексте одного или нескольких решений обхода NAT. Эти решения называются «применениями STUN». Каждое применение описывает, как STUN используется для достижения решения по обходу NAT. Обычно применение указывает, когда отправляются сообщения STUN, какие необязательные атрибуты включать, какой сервер используется и какой механизм аутентификации применяется. Interactive Connectivity Establishment (ICE) [RFC8445] — одно из применений STUN. SIP Outbound [RFC5626] — другое применение STUN. В некоторых случаях применение требует расширений STUN. Расширение STUN может принимать форму новых методов, атрибутов или кодов ответов об ошибках. Дополнительную информацию о применениях STUN можно найти в разделе 13.

STUN is a client-server protocol. It supports two types of transactions. One is a request/response transaction in which a client sends a request to a server, and the server returns a response. The second is an indication transaction in which either agent -- client or server -- sends an indication that generates no response. Both types of transactions include a transaction ID, which is a randomly selected 96-bit number. For request/response transactions, this transaction ID allows the client to associate the response with the request that generated it; for indications, the transaction ID serves as a debugging aid.
STUN — протокол клиент-сервер. Он поддерживает два типа транзакций. Первый — транзакция запрос/ответ, в которой клиент отправляет запрос серверу, а сервер возвращает ответ. Второй — транзакция-индикация, в которой любой агент — клиент или сервер — отправляет индикацию, не порождающую ответа. Оба типа транзакций включают идентификатор транзакции, представляющий собой случайно выбранное 96-битное число. Для транзакций запрос/ответ этот идентификатор транзакции позволяет клиенту связать ответ с запросом, породившим его; для индикаций идентификатор транзакции служит средством отладки.
All STUN messages start with a fixed header that includes a method, a class, and the transaction ID. The method indicates which of the various requests or indications this is; this specification defines just one method, Binding, but other methods are expected to be defined in other documents. The class indicates whether this is a request, a success response, an error response, or an indication. Following the fixed header comes zero or more attributes, which are Type-Length-Value extensions that convey additional information for the specific message.
Все сообщения STUN начинаются с фиксированного заголовка, который включает метод, класс и идентификатор транзакции. Метод указывает, какой из различных запросов или индикаций это; данная спецификация определяет только один метод — Binding, но другие методы, как ожидается, будут определены в других документах. Класс указывает, является ли это запросом, ответом об успехе, ответом об ошибке или индикацией. За фиксированным заголовком следуют ноль или более атрибутов — расширений Type-Length-Value, передающих дополнительную информацию для конкретного сообщения.
This document defines a single method called "Binding". The Binding method can be used either in request/response transactions or in indication transactions. When used in request/response transactions, the Binding method can be used to determine the particular binding a NAT has allocated to a STUN client. When used in either request/ response or in indication transactions, the Binding method can also be used to keep these bindings alive.
Настоящий документ определяет единственный метод, называемый «Binding». Метод Binding может использоваться как в транзакциях запрос/ответ, так и в транзакциях-индикациях. При использовании в транзакциях запрос/ответ метод Binding может применяться для определения конкретной привязки, выделенной NAT клиенту STUN. При использовании как в транзакциях запрос/ответ, так и в транзакциях-индикациях метод Binding также может применяться для поддержания этих привязок в активном состоянии.

In some usages, STUN must be multiplexed with other protocols (e.g., [RFC8445] and [RFC5626]). In these usages, there must be a way to inspect a packet and determine if it is a STUN packet or not. STUN provides three fields in the STUN header with fixed values that can be used for this purpose. If this is not sufficient, then STUN packets can also contain a FINGERPRINT value, which can further be used to distinguish the packets.
В некоторых применениях STUN должен мультиплексироваться с другими протоколами (например, [RFC8445] и [RFC5626]). В таких применениях должен существовать способ проверки пакета и определения, является ли он пакетом STUN. STUN предоставляет три поля в заголовке STUN с фиксированными значениями, которые можно использовать для этой цели. Если этого недостаточно, пакеты STUN могут также содержать значение FINGERPRINT, которое можно дополнительно использовать для различения пакетов.
STUN defines a set of optional procedures that a usage can decide to use, called "mechanisms". These mechanisms include DNS discovery, a redirection technique to an alternate server, a fingerprint attribute for demultiplexing, and two authentication and message-integrity exchanges. The authentication mechanisms revolve around the use of a username, password, and message-integrity value. Two authentication mechanisms, the long-term credential mechanism and the short-term credential mechanism, are defined in this specification. Each usage specifies the mechanisms allowed with that usage.
STUN определяет набор необязательных процедур, которые применение может решить использовать; они называются «механизмами». Эти механизмы включают обнаружение через DNS, технику перенаправления на альтернативный сервер, атрибут отпечатка для демультиплексирования и два обмена аутентификации и целостности сообщений. Механизмы аутентификации основаны на использовании имени пользователя, пароля и значения целостности сообщения. В данной спецификации определены два механизма аутентификации — механизм долгосрочных учетных данных и механизм краткосрочных учетных данных. Каждое применение указывает механизмы, допустимые для этого применения.
In the long-term credential mechanism, the client and server share a pre-provisioned username and password and perform a digest challenge/ response exchange inspired by the one defined for HTTP [RFC7616] but differing in details. In the short-term credential mechanism, the client and the server exchange a username and password through some out-of-band method prior to the STUN exchange. For example, in the ICE usage [RFC8445], the two endpoints use out-of-band signaling to exchange a username and password. These are used to integrity protect and authenticate the request and response. There is no challenge or nonce used.
В механизме долгосрочных учетных данных клиент и сервер совместно используют заранее предоставленные имя пользователя и пароль и выполняют обмен типа digest-запрос/ответ, вдохновлённый определённым для HTTP [RFC7616], но отличающийся в деталях. В механизме краткосрочных учетных данных клиент и сервер обмениваются именем пользователя и паролем через некоторый внешний метод до обмена STUN. Например, в применении ICE [RFC8445] две конечные точки используют внешнюю сигнализацию для обмена именем пользователя и паролем. Они используются для защиты целостности и аутентификации запроса и ответа. Никакой запрос-вызов или nonce не используется.

4. Definitions
4. Определения
STUN Agent: A STUN agent is an entity that implements the STUN protocol. The entity can be either a STUN client or a STUN server.
Агент STUN: агент STUN — сущность, реализующая протокол STUN. Сущность может быть либо клиентом STUN, либо сервером STUN.
STUN Client: A STUN client is an entity that sends STUN requests and receives STUN responses and STUN indications. A STUN client can also send indications. In this specification, the terms "STUN client" and "client" are synonymous.
Клиент STUN: клиент STUN — сущность, которая отправляет запросы STUN и принимает ответы и индикации STUN. Клиент STUN может также отправлять индикации. В данной спецификации термины «клиент STUN» и «клиент» являются синонимами.
STUN Server: A STUN server is an entity that receives STUN requests and STUN indications and that sends STUN responses. A STUN server can also send indications. In this specification, the terms "STUN server" and "server" are synonymous.
Сервер STUN: сервер STUN — сущность, которая принимает запросы и индикации STUN и отправляет ответы STUN. Сервер STUN может также отправлять индикации. В данной спецификации термины «сервер STUN» и «сервер» являются синонимами.
Transport Address: The combination of an IP address and port number (such as a UDP or TCP port number).
Транспортный адрес: сочетание IP-адреса и номера порта (например, номера порта UDP или TCP).
Reflexive Transport Address: A transport address learned by a client that identifies that client as seen by another host on an IP network, typically a STUN server. When there is an intervening NAT between the client and the other host, the reflexive transport address represents the mapped address allocated to the client on the public side of the NAT. Reflexive transport addresses are learned from the mapped address attribute (MAPPED-ADDRESS or XOR- MAPPED-ADDRESS) in STUN responses.
Рефлексивный транспортный адрес: транспортный адрес, узнанный клиентом, который идентифицирует этого клиента в том виде, в каком его видит другой узел IP-сети, обычно сервер STUN. Когда между клиентом и другим узлом находится промежуточный NAT, рефлексивный транспортный адрес представляет отображённый адрес, выделенный клиенту на публичной стороне NAT. Рефлексивные транспортные адреса узнаются из атрибута отображённого адреса (MAPPED-ADDRESS или XOR-MAPPED-ADDRESS) в ответах STUN.

Long-Term Credential: A username and associated password that represent a shared secret between client and server. Long-term credentials are generally granted to the client when a subscriber enrolls in a service and persist until the subscriber leaves the service or explicitly changes the credential.
Долгосрочные учетные данные: имя пользователя и связанный с ним пароль, представляющие общий секрет между клиентом и сервером. Долгосрочные учетные данные обычно предоставляются клиенту, когда абонент регистрируется в службе, и сохраняются, пока абонент не покинет службу или явно не изменит учетные данные.
Long-Term Password: The password from a long-term credential.
Долгосрочный пароль: пароль из долгосрочных учетных данных.
Short-Term Credential: A temporary username and associated password that represent a shared secret between client and server. Short- term credentials are obtained through some kind of protocol mechanism between the client and server, preceding the STUN exchange. A short-term credential has an explicit temporal scope, which may be based on a specific amount of time (such as 5 minutes) or on an event (such as termination of a Session Initiation Protocol (SIP) [RFC3261] dialog). The specific scope of a short-term credential is defined by the application usage.

The transaction ID is a 96-bit identifier, used to uniquely identify STUN transactions. For request/response transactions, the transaction ID is chosen by the STUN client for the request and echoed by the server in the response. For indications, it is chosen by the agent sending the indication. It primarily serves to correlate requests with responses, though it also plays a small role in helping to prevent certain types of attacks. The server also uses the transaction ID as a key to identify each transaction uniquely across all clients. As such, the transaction ID MUST be uniformly and randomly chosen from the interval 0 .. 2**96-1 and MUST be cryptographically random. Resends of the same request reuse the same transaction ID, but the client MUST choose a new transaction ID for new transactions unless the new request is bit-wise identical to the previous request and sent from the same transport address to the same IP address. Success and error responses MUST carry the same transaction ID as their corresponding request. When an agent is acting as a STUN server and STUN client on the same port, the transaction IDs in requests sent by the agent have no relationship to the transaction IDs in requests received by the agent.
Идентификатор транзакции — это 96-битный идентификатор, используемый для уникальной идентификации транзакций STUN. Для транзакций запрос/ответ идентификатор транзакции выбирается клиентом STUN для запроса и повторяется сервером в ответе. Для индикаций он выбирается агентом, отправляющим индикацию. В первую очередь он служит для соотнесения запросов с ответами, хотя также играет небольшую роль в помощи предотвращения некоторых типов атак. Сервер также использует идентификатор транзакции как ключ для уникальной идентификации каждой транзакции среди всех клиентов. Как таковой, идентификатор транзакции ДОЛЖЕН выбираться равномерно и случайно из интервала 0 .. 2**96-1 и ДОЛЖЕН быть криптографически случайным. Повторные отправки одного и того же запроса используют один и тот же идентификатор транзакции, но клиент ДОЛЖЕН выбирать новый идентификатор транзакции для новых транзакций, если только новый запрос не побитно идентичен предыдущему запросу и не отправлен с того же транспортного адреса на тот же IP-адрес. Ответы об успехе и об ошибке ДОЛЖНЫ нести тот же идентификатор транзакции, что и соответствующий запрос. Когда агент действует как сервер STUN и клиент STUN на одном порту, идентификаторы транзакций в запросах, отправленных агентом, не связаны с идентификаторами транзакций в запросах, полученных агентом.
The message length MUST contain the size of the message in bytes, not including the 20-byte STUN header. Since all STUN attributes are padded to a multiple of 4 bytes, the last 2 bits of this field are always zero. This provides another way to distinguish STUN packets from packets of other protocols.
Длина сообщения ДОЛЖНА содержать размер сообщения в байтах, не включая 20-байтный заголовок STUN. Поскольку все атрибуты STUN дополняются до кратности 4 байтам, последние 2 бита этого поля всегда нулевые. Это даёт ещё один способ отличить пакеты STUN от пакетов других протоколов.

За фиксированной частью заголовка STUN следуют ноль или более атрибутов. Каждый атрибут кодируется как TLV (Type-Length-Value). Подробности кодирования и сами атрибуты приведены в разделе 14.

6. Базовые процедуры протокола
This section defines the base procedures of the STUN protocol. It describes how messages are formed, how they are sent, and how they are processed when they are received. It also defines the detailed processing of the Binding method. Other sections in this document describe optional procedures that a usage may elect to use in certain situations. Other documents may define other extensions to STUN, by adding new methods, new attributes, or new error response codes.
В этом разделе определены базовые процедуры протокола STUN. Он описывает, как формируются сообщения, как они отправляются и как обрабатываются при получении. Он также определяет подробную обработку метода Binding. Другие разделы настоящего документа описывают необязательные процедуры, которые применение может выбрать для использования в определённых ситуациях. Другие документы могут определять другие расширения STUN, добавляя новые методы, новые атрибуты или новые коды ответов об ошибках.
6.1. Forming a Request or an Indication
6.1. Формирование запроса или индикации
When formulating a request or indication message, the agent MUST follow the rules in Section 5 when creating the header. In addition, the message class MUST be either "Request" or "Indication" (as appropriate), and the method must be either Binding or some method defined in another document.
При формулировании сообщения-запроса или индикации агент ДОЛЖЕН следовать правилам раздела 5 при создании заголовка. Кроме того, класс сообщения ДОЛЖЕН быть либо «Request», либо «Indication» (в зависимости от ситуации), а метод должен быть либо Binding, либо некоторым методом, определённым в другом документе.
The agent then adds any attributes specified by the method or the usage. For example, some usages may specify that the agent use an authentication method (Section 9) or the FINGERPRINT attribute (Section 7). If the agent is sending a request, it SHOULD add a SOFTWARE attribute to the request. Agents MAY include a SOFTWARE attribute in indications, depending on the method. Extensions to STUN should discuss whether SOFTWARE is useful in new indications. Note that the inclusion of a SOFTWARE attribute may have security implications; see Section 16.1.2 for details.
Затем агент добавляет любые атрибуты, указанные методом или применением. Например, некоторые применения могут указывать, что агент использует метод аутентификации (раздел 9) или атрибут FINGERPRINT (раздел 7). Если агент отправляет запрос, ему СЛЕДУЕТ добавить в запрос атрибут SOFTWARE. Агенты МОГУТ включать атрибут SOFTWARE в индикации в зависимости от метода. Расширения STUN должны обсуждать, полезен ли SOFTWARE в новых индикациях. Обратите внимание, что включение атрибута SOFTWARE может иметь последствия для безопасности; подробности см. в разделе 16.1.2.
For the Binding method with no authentication, no attributes are required unless the usage specifies otherwise.
Для метода Binding без аутентификации атрибуты не требуются, если применение не указывает иное.
All STUN messages sent over UDP or DTLS-over-UDP [RFC6347] SHOULD be less than the path MTU, if known.
Все сообщения STUN, отправляемые через UDP или DTLS-over-UDP [RFC6347], ДОЛЖНЫ быть меньше MTU пути, если он известен.
If the path MTU is unknown for UDP, messages SHOULD be the smaller of 576 bytes and the first-hop MTU for IPv4 [RFC1122] and 1280 bytes for IPv6 [RFC8200]. This value corresponds to the overall size of the IP packet. Consequently, for IPv4, the actual STUN message would need to be less than 548 bytes (576 minus 20-byte IP header, minus 8-byte UDP header, assuming no IP options are used).
Если MTU пути для UDP неизвестен, сообщения ДОЛЖНЫ иметь меньший из размеров: 576 байт и MTU первого перехода для IPv4 [RFC1122] — и 1280 байт для IPv6 [RFC8200]. Это значение соответствует общему размеру IP-пакета. Следовательно, для IPv4 фактическое сообщение STUN должно быть меньше 548 байт (576 минус 20-байтный заголовок IP, минус 8-байтный заголовок UDP, при условии, что параметры IP не используются).
If the path MTU is unknown for DTLS-over-UDP, the rules described in the previous paragraph need to be adjusted to take into account the size of the (13-byte) DTLS Record header, the Message Authentication Code (MAC) size, and the padding size.
Если MTU пути для DTLS-over-UDP неизвестен, правила, описанные в предыдущем абзаце, необходимо скорректировать с учётом размера (13-байтного) заголовка записи DTLS, размера кода аутентификации сообщения (MAC) и размера заполнения.
STUN provides no ability to handle the case where the request is smaller than the MTU but the response is larger than the MTU. It is not envisioned that this limitation will be an issue for STUN. The MTU limitation is a SHOULD, not a MUST, to account for cases where STUN itself is being used to probe for MTU characteristics [RFC5780]. See also [STUN-PMTUD] for a framework that uses STUN to add Path MTU Discovery to protocols that lack such a mechanism. Outside of this or similar applications, the MTU constraint MUST be followed.
STUN не предоставляет возможностей обработки случая, когда запрос меньше MTU, а ответ больше MTU. Не предполагается, что это ограничение станет проблемой для STUN. Ограничение MTU является требованием SHOULD, а не MUST, чтобы учесть случаи, когда сам STUN используется для зондирования характеристик MTU [RFC5780]. См. также [STUN-PMTUD] в отношении инфраструктуры, использующей STUN для добавления обнаружения MTU пути в протоколы, в которых такой механизм отсутствует. Вне этого или аналогичных применений ограничение MTU ДОЛЖНО соблюдаться.
6.2. Sending the Request or Indication
6.2. Отправка запроса или индикации
The agent then sends the request or indication. This document specifies how to send STUN messages over UDP, TCP, TLS-over-TCP, or DTLS-over-UDP; other transport protocols may be added in the future. The STUN Usage must specify which transport protocol is used and how the agent determines the IP address and port of the recipient. Section 8 describes a DNS-based method of determining the IP address and port of a server that a usage may elect to use.
Затем агент отправляет запрос или индикацию. Настоящий документ определяет, как отправлять сообщения STUN через UDP, TCP, TLS-over-TCP или DTLS-over-UDP; другие транспортные протоколы могут быть добавлены в будущем. Применение STUN должно указывать, какой транспортный протокол используется и как агент определяет IP-адрес и порт получателя. Раздел 8 описывает метод определения IP-адреса и порта сервера на основе DNS, который применение может выбрать для использования.
At any time, a client MAY have multiple outstanding STUN requests with the same STUN server (that is, multiple transactions in progress, with different transaction IDs). Absent other limits to the rate of new transactions (such as those specified by ICE for connectivity checks or when STUN is run over TCP), a client SHOULD limit itself to ten outstanding transactions to the same server.
В любой момент времени клиент МОЖЕТ иметь несколько незавершённых запросов STUN к одному и тому же серверу STUN (то есть несколько выполняющихся транзакций с разными идентификаторами транзакций). При отсутствии иных ограничений скорости новых транзакций (таких как указанные в ICE для проверок связности или когда STUN работает через TCP) клиенту СЛЕДУЕТ ограничиваться десятью незавершёнными транзакциями к одному серверу.
6.2.1. Sending over UDP or DTLS-over-UDP
6.2.1. Отправка через UDP или DTLS-over-UDP
When running STUN over UDP or STUN over DTLS-over-UDP [RFC7350], it is possible that the STUN message might be dropped by the network. Reliability of STUN request/response transactions is accomplished through retransmissions of the request message by the client application itself. STUN indications are not retransmitted; thus, indication transactions over UDP or DTLS-over-UDP are not reliable.
При работе STUN через UDP или STUN через DTLS-over-UDP [RFC7350] возможно, что сообщение STUN будет отброшено сетью. Надёжность транзакций запрос/ответ STUN достигается за счёт повторных передач сообщения-запроса самим клиентским приложением. Индикации STUN не передаются повторно; таким образом, транзакции-индикации через UDP или DTLS-over-UDP не являются надёжными.
A client SHOULD retransmit a STUN request message starting with an interval of RTO ("Retransmission TimeOut"), doubling after each retransmission. The RTO is an estimate of the round-trip time (RTT) and is computed as described in [RFC6298], with two exceptions. First, the initial value for RTO SHOULD be greater than or equal to 500 ms. The exception cases for this "SHOULD" are when other mechanisms are used to derive congestion thresholds (such as the ones defined in ICE for fixed-rate streams) or when STUN is used in non- Internet environments with known network capacities. In fixed-line access links, a value of 500 ms is RECOMMENDED. Second, the value of RTO SHOULD NOT be rounded up to the nearest second. Rather, a 1 ms accuracy SHOULD be maintained. As with TCP, the usage of Karn's algorithm is RECOMMENDED [KARN87]. When applied to STUN, it means that RTT estimates SHOULD NOT be computed from STUN transactions that result in the retransmission of a request.
Клиент ДОЛЖЕН повторно передавать сообщение-запрос STUN, начиная с интервала RTO («Retransmission TimeOut»), удваивая его после каждой повторной передачи. RTO — это оценка времени кругового обхода (RTT), которая вычисляется, как описано в [RFC6298], с двумя исключениями. Во-первых, начальное значение RTO ДОЛЖНО быть больше или равно 500 мс. Исключениями из этого «SHOULD» являются случаи, когда используются другие механизмы для вывода порогов перегрузки (такие как определённые в ICE для потоков с фиксированной скоростью) или когда STUN используется в неинтернет-средах с известными характеристиками сети. На каналах фиксированного доступа РЕКОМЕНДУЕТСЯ значение 500 мс. Во-вторых, значение RTO НЕ СЛЕДУЕТ округлять вверх до ближайшей секунды. Скорее, СЛЕДУЕТ поддерживать точность 1 мс. Как и в TCP, РЕКОМЕНДУЕТСЯ использование алгоритма Карна [KARN87]. В применении к STUN это означает, что оценки RTT НЕ СЛЕДУЕТ вычислять по транзакциям STUN, которые приводят к повторной передаче запроса.
The value for RTO SHOULD be cached by a client after the completion of the transaction and used as the starting value for RTO for the next transaction to the same server (based on equality of IP address). The value SHOULD be considered stale and discarded if no transactions have occurred to the same server in the last 10 minutes.
Значение RTO СЛЕДУЕТ кэшировать клиенту после завершения транзакции и использовать в качестве начального значения RTO для следующей транзакции к тому же серверу (на основе равенства IP-адреса). Значение СЛЕДУЕТ считать устаревшим и отбрасывать, если за последние 10 минут к тому же серверу не было транзакций.
Retransmissions continue until a response is received or until a total of Rc requests have been sent. Rc SHOULD be configurable and SHOULD have a default of 7. If, after the last request, a duration equal to Rm times the RTO has passed without a response (providing ample time to get a response if only this final request actually succeeds), the client SHOULD consider the transaction to have failed. Rm SHOULD be configurable and SHOULD have a default of 16. A STUN transaction over UDP or DTLS-over-UDP is also considered failed if there has been a hard ICMP error [RFC1122]. For example, assuming an RTO of 500 ms, requests would be sent at times 0 ms, 500 ms, 1500 ms, 3500 ms, 7500 ms, 15500 ms, and 31500 ms. If the client has not received a response after 39500 ms, the client will consider the transaction to have timed out.
Повторные передачи продолжаются до получения ответа или до отправки в общей сложности Rc запросов. Rc СЛЕДУЕТ делать настраиваемым, и он ДОЛЖЕН по умолчанию равняться 7. Если после последнего запроса прошло время, равное Rm умножить на RTO, без ответа (что даёт достаточно времени для получения ответа, если только этот последний запрос действительно окажется успешным), клиенту СЛЕДУЕТ считать транзакцию неудачной. Rm СЛЕДУЕТ делать настраиваемым, и он ДОЛЖЕН по умолчанию равняться 16. Транзакция STUN через UDP или DTLS-over-UDP также считается неудачной, если произошла жёсткая ошибка ICMP [RFC1122]. Например, при RTO 500 мс запросы отправлялись бы в моменты 0 мс, 500 мс, 1500 мс, 3500 мс, 7500 мс, 15500 мс и 31500 мс. Если клиент не получил ответ через 39500 мс, он будет считать, что время транзакции истекло.
6.2.2. Sending over TCP or TLS-over-TCP
6.2.2. Отправка через TCP или TLS-over-TCP
For TCP and TLS-over-TCP [RFC8446], the client opens a TCP connection to the server.
Для TCP и TLS-over-TCP [RFC8446] клиент открывает TCP-соединение с сервером.
In some usages of STUN, STUN is the only protocol over the TCP connection. In this case, it can be sent without the aid of any additional framing or demultiplexing. In other usages, or with other extensions, it may be multiplexed with other data over a TCP connection. In that case, STUN MUST be run on top of some kind of framing protocol, specified by the usage or extension, which allows for the agent to extract complete STUN messages and complete application-layer messages. The STUN service running on the well- known port or ports discovered through the DNS procedures in Section 8 is for STUN alone, and not for STUN multiplexed with other data. Consequently, no framing protocols are used in connections to those servers. When additional framing is utilized, the usage will specify how the client knows to apply it and what port to connect to. For example, in the case of ICE connectivity checks, this information is learned through out-of-band negotiation between client and server.
В некоторых применениях STUN является единственным протоколом через TCP-соединение. В этом случае его можно передавать без какой-либо дополнительной кадрировки или демультиплексирования. В других применениях или с другими расширениями он может мультиплексироваться с другими данными через TCP-соединение. В этом случае STUN ДОЛЖЕН работать поверх некоторого протокола кадрирования, указанного применением или расширением, который позволяет агенту извлекать полные сообщения STUN и полные сообщения прикладного уровня. Служба STUN, работающая на широко известном порту или портах, обнаруженных с помощью процедур DNS в разделе 8, предназначена только для STUN, а не для STUN, мультиплексированного с другими данными. Следовательно, в соединениях с этими серверами протоколы кадрирования не используются. Когда используется дополнительная кадрировка, применение укажет, как клиент узнаёт о её применении и к какому порту подключаться. Например, в случае проверок связности ICE эта информация узнаётся через внешние переговоры между клиентом и сервером.

Ti SHOULD be configurable and SHOULD have a default of 39.5 s. This value has been chosen to equalize the TCP and UDP timeouts for the default initial RTO.
Надёжность STUN через TCP и TLS-over-TCP обеспечивается самим TCP, и повторных передач на уровне протокола STUN нет. Однако для транзакции запрос/ответ, если клиент не получил ответ в течение Ti секунд после отправки сообщения-запроса, он считает, что время транзакции истекло. Ti СЛЕДУЕТ делать настраиваемым, и он ДОЛЖЕН по умолчанию равняться 39,5 с. Это значение выбрано для уравнивания тайм-аутов TCP и UDP при начальном RTO по умолчанию.

6.2.3. Sending over TLS-over-TCP or DTLS-over-UDP
6.2.3. Отправка через TLS-over-TCP или DTLS-over-UDP
When STUN is run by itself over TLS-over-TCP or DTLS-over-UDP, the TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 and TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 ciphersuites MUST be implemented (for compatibility with older versions of this protocol), except if deprecated by rules of a specific STUN usage. Other ciphersuites MAY be implemented. Note that STUN clients and servers that implement TLS version 1.3 [RFC8446] or subsequent versions are also required to implement mandatory ciphersuites from those specifications and SHOULD disable usage of deprecated ciphersuites when they detect support for those specifications. Perfect Forward Secrecy (PFS) ciphersuites MUST be preferred over non-PFS ciphersuites. Ciphersuites with known weaknesses, such as those based on (single) DES and RC4, MUST NOT be used. Implementations MUST disable TLS-level compression.
Когда STUN работает сам по себе через TLS-over-TCP или DTLS-over-UDP, ДОЛЖНЫ быть реализованы наборы шифров TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 и TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 (для совместимости с более старыми версиями этого протокола), если только они не объявлены устаревшими правилами конкретного применения STUN. Другие наборы шифров МОГУТ быть реализованы. Обратите внимание, что клиенты и серверы STUN, реализующие TLS версии 1.3 [RFC8446] или последующих версий, также обязаны реализовывать обязательные наборы шифров из этих спецификаций и ДОЛЖНЫ отключать использование устаревших наборов шифров, когда они обнаруживают поддержку этих спецификаций. Наборы шифров Perfect Forward Secrecy (PFS) ДОЛЖНЫ предпочитаться наборам шифров без PFS. Наборы шифров с известными слабостями, такие как основанные на (одинарном) DES и RC4, НЕ ДОЛЖНЫ использоваться. Реализации ДОЛЖНЫ отключать сжатие на уровне TLS.
These recommendations are just a part of the recommendations in [BCP195] that implementations and deployments of a STUN Usage using TLS or DTLS MUST follow.
Эти рекомендации являются лишь частью рекомендаций в [BCP195], которым ДОЛЖНЫ следовать реализации и развёртывания применения STUN, использующего TLS или DTLS.

6.3. Receiving a STUN Message
6.3. Получение сообщения STUN
This section specifies the processing of a STUN message. The processing specified here is for STUN messages as defined in this specification; additional rules for backwards compatibility are defined in Section 11. Those additional procedures are optional, and usages can elect to utilize them. First, a set of processing operations is applied that is independent of the class. This is followed by class-specific processing, described in the subsections that follow.
В этом разделе определена обработка сообщения STUN. Описанная здесь обработка относится к сообщениям STUN, определённым в данной спецификации; дополнительные правила обратной совместимости определены в разделе 11. Эти дополнительные процедуры необязательны, и применения могут выбрать их использование. Сначала применяется набор операций обработки, не зависящих от класса. Затем следует обработка, зависящая от класса, описанная в последующих подразделах.
When a STUN agent receives a STUN message, it first checks that the message obeys the rules of Section 5. It checks that the first two bits are 0, that the Magic Cookie field has the correct value, that the message length is sensible, and that the method value is a supported method. It checks that the message class is allowed for the particular method. If the message class is "Success Response" or "Error Response", the agent checks that the transaction ID matches a transaction that is still in progress. If the FINGERPRINT extension is being used, the agent checks that the FINGERPRINT attribute is present and contains the correct value. If any errors are detected, the message is silently discarded. In the case when STUN is being multiplexed with another protocol, an error may indicate that this is not really a STUN message; in this case, the agent should try to parse the message as a different protocol.
Когда агент STUN получает сообщение STUN, он сначала проверяет, что сообщение подчиняется правилам раздела 5. Он проверяет, что первые два бита равны 0, что поле Magic Cookie имеет правильное значение, что длина сообщения разумна и что значение метода является поддерживаемым методом. Он проверяет, что класс сообщения допустим для конкретного метода. Если класс сообщения — «Success Response» или «Error Response», агент проверяет, что идентификатор транзакции соответствует транзакции, которая всё ещё выполняется. Если используется расширение FINGERPRINT, агент проверяет, что атрибут FINGERPRINT присутствует и содержит правильное значение. Если обнаружены какие-либо ошибки, сообщение молча отбрасывается. В случае, когда STUN мультиплексируется с другим протоколом, ошибка может указывать на то, что это не действительно сообщение STUN; в этом случае агенту следует попытаться разобрать сообщение как другой протокол.
The STUN agent then does any checks that are required by a authentication mechanism that the usage has specified (see Section 9).
Затем агент STUN выполняет любые проверки, требуемые механизмом аутентификации, указанным в применении (см. раздел 9).

Расширения STUN ДОЛЖНЫ обсуждать последствия повторных передач запросов на серверах, которые не хранят состояние транзакций.
6.3.1.1. Forming a Success or Error Response
6.3.1.1. Формирование ответа об успехе или ошибке
When forming the response (success or error), the server follows the rules of Section 6. The method of the response is the same as that of the request, and the message class is either "Success Response" or "Error Response". For an error response, the server MUST add an ERROR-CODE attribute containing the error code specified in the processing above. The reason phrase is not fixed but SHOULD be something suitable for the error code. For certain errors, additional attributes are added to the message. These attributes are spelled out in the description where the error code is specified. For example, for an error code of 420 (Unknown Attribute), the server MUST include an UNKNOWN- ATTRIBUTES attribute. Certain authentication errors also cause attributes to be added (see Section 9). Extensions may define other errors and/or additional attributes to add in error cases.
При формировании ответа (об успехе или об ошибке) сервер следует правилам раздела 6. Метод ответа совпадает с методом запроса, а класс сообщения — либо «Success Response», либо «Error Response». Для ответа об ошибке сервер ДОЛЖЕН добавить атрибут ERROR-CODE, содержащий код ошибки, указанный в обработке выше. Фраза причины не фиксирована, но ДОЛЖНА подходить для кода ошибки. Для определённых ошибок в сообщение добавляются дополнительные атрибуты. Эти атрибуты указываются в описании, где определён код ошибки. Например, для кода ошибки 420 (Unknown Attribute) сервер ДОЛЖЕН включить атрибут UNKNOWN-ATTRIBUTES. Некоторые ошибки аутентификации также вызывают добавление атрибутов (см. раздел 9). Расширения могут определять другие ошибки и/или дополнительные атрибуты, добавляемые в случаях ошибок.
If the server authenticated the request using an authentication mechanism, then the server SHOULD add the appropriate authentication attributes to the response (see Section 9).
Если сервер аутентифицировал запрос с использованием механизма аутентификации, то серверу СЛЕДУЕТ добавить в ответ соответствующие атрибуты аутентификации (см. раздел 9).
The server also adds any attributes required by the specific method or usage. In addition, the server SHOULD add a SOFTWARE attribute to the message.
Сервер также добавляет любые атрибуты, требуемые конкретным методом или применением. Кроме того, серверу СЛЕДУЕТ добавить в сообщение атрибут SOFTWARE.
For the Binding method, no additional checking is required unless the usage specifies otherwise. When forming the success response, the server adds an XOR-MAPPED-ADDRESS attribute to the response; this attribute contains the source transport address of the request message. For UDP or DTLS-over-UDP, this is the source IP address and source UDP port of the request message. For TCP and TLS-over-TCP, this is the source IP address and source TCP port of the TCP connection as seen by the server.
Для метода Binding никакие дополнительные проверки не требуются, если применение не указывает иное. При формировании ответа об успехе сервер добавляет в ответ атрибут XOR-MAPPED-ADDRESS; этот атрибут содержит исходный транспортный адрес сообщения-запроса. Для UDP или DTLS-over-UDP это исходный IP-адрес и исходный порт UDP сообщения-запроса. Для TCP и TLS-over-TCP это исходный IP-адрес и исходный порт TCP TCP-соединения в том виде, в каком его видит сервер.
6.3.1.2. Sending the Success or Error Response
6.3.1.2. Отправка ответа об успехе или ошибке
The response (success or error) is sent over the same transport as the request was received on. If the request was received over UDP or DTLS-over-UDP, the destination IP address and port of the response are the source IP address and port of the received request message, and the source IP address and port of the response are equal to the destination IP address and port of the received request message. If the request was received over TCP or TLS-over-TCP, the response is sent back on the same TCP connection as the request was received on.
Ответ (об успехе или об ошибке) отправляется через тот же транспорт, по которому был получен запрос. Если запрос был получен через UDP или DTLS-over-UDP, IP-адрес и порт назначения ответа совпадают с исходным IP-адресом и портом полученного сообщения-запроса, а исходный IP-адрес и порт ответа совпадают с IP-адресом и портом назначения полученного сообщения-запроса. Если запрос был получен через TCP или TLS-over-TCP, ответ отправляется обратно по тому же TCP-соединению, по которому был получен запрос.
The server is allowed to send responses in a different order than it received the requests.
Серверу разрешается отправлять ответы в другом порядке по сравнению с порядком получения запросов.
6.3.2. Processing an Indication
6.3.2. Обработка индикации
If the indication contains unknown comprehension-required attributes, the indication is discarded and processing ceases. Otherwise, the agent then does any additional checking that the method or the specific usage requires. If all the checks succeed, the agent then processes the indication. No response is generated for an indication.
Если индикация содержит неизвестные обязательные для понимания атрибуты, индикация отбрасывается, и обработка прекращается. В противном случае агент выполняет любые дополнительные проверки, которые требуются методом или конкретным применением. Если все проверки успешны, агент затем обрабатывает индикацию. Ответ на индикацию не генерируется.
For the Binding method, no additional checking or processing is required, unless the usage specifies otherwise. The mere receipt of the message by the agent has refreshed the bindings in the intervening NATs.
Для метода Binding никакие дополнительные проверки или обработка не требуются, если применение не указывает иное. Сам факт получения сообщения агентом обновил привязки в промежуточных NAT.
Since indications are not re-transmitted over UDP or DTLS-over-UDP (unlike requests), there is no need to handle re-transmissions of indications at the sending agent.
Поскольку индикации не передаются повторно через UDP или DTLS-over-UDP (в отличие от запросов), нет необходимости обрабатывать повторные передачи индикаций на отправляющем агенте.
6.3.3. Processing a Success Response
6.3.3. Обработка ответа об успехе
If the success response contains unknown comprehension-required attributes, the response is discarded and the transaction is considered to have failed.
Если ответ об успехе содержит неизвестные обязательные для понимания атрибуты, ответ отбрасывается, а транзакция считается неудачной.
Otherwise, the client then does any additional checking that the method or the specific usage requires. If all the checks succeed, the client then processes the success response.
В противном случае клиент выполняет любые дополнительные проверки, которые требуются методом или конкретным применением. Если все проверки успешны, клиент затем обрабатывает ответ об успехе.
For the Binding method, the client checks that the XOR-MAPPED-ADDRESS attribute is present in the response. The client checks the address family specified. If it is an unsupported address family, the attribute SHOULD be ignored. If it is an unexpected but supported address family (for example, the Binding transaction was sent over IPv4, but the address family specified is IPv6), then the client MAY accept and use the value.
Для метода Binding клиент проверяет, что атрибут XOR-MAPPED-ADDRESS присутствует в ответе. Клиент проверяет указанное семейство адресов. Если это неподдерживаемое семейство адресов, атрибут СЛЕДУЕТ игнорировать. Если это неожиданное, но поддерживаемое семейство адресов (например, транзакция Binding была отправлена через IPv4, но указано семейство адресов IPv6), клиент МОЖЕТ принять и использовать значение.
6.3.4. Processing an Error Response
6.3.4. Обработка ответа об ошибке
If the error response contains unknown comprehension-required attributes, or if the error response does not contain an ERROR-CODE attribute, then the transaction is simply considered to have failed.
Если ответ об ошибке содержит неизвестные обязательные для понимания атрибуты или если ответ об ошибке не содержит атрибут ERROR-CODE, транзакция просто считается неудачной.
Otherwise, the client then does any processing specified by the authentication mechanism (see Section 9). This may result in a new transaction attempt.
В противном случае клиент выполняет любую обработку, указанную механизмом аутентификации (см. раздел 9). Это может привести к новой попытке транзакции.
The processing at this point depends on the error code, the method, and the usage; the following are the default rules:
Обработка на этом этапе зависит от кода ошибки, метода и применения; ниже приведены правила по умолчанию:
o If the error code is 300 through 399, the client SHOULD consider the transaction as failed unless the ALTERNATE-SERVER extension (Section 10) is being used.
o Если код ошибки от 300 до 399, клиенту СЛЕДУЕТ считать транзакцию неудачной, если не используется расширение ALTERNATE-SERVER (раздел 10).
o If the error code is 400 through 499, the client declares the transaction failed; in the case of 420 (Unknown Attribute), the response should contain a UNKNOWN-ATTRIBUTES attribute that gives additional information.
o Если код ошибки от 400 до 499, клиент объявляет транзакцию неудачной; в случае 420 (Unknown Attribute) ответ должен содержать атрибут UNKNOWN-ATTRIBUTES, дающий дополнительную информацию.
o If the error code is 500 through 599, the client MAY resend the request; clients that do so MUST limit the number of times they do this. Unless a specific error code specifies a different value, the number of retransmissions SHOULD be limited to 4.
o Если код ошибки от 500 до 599, клиент МОЖЕТ повторно отправить запрос; клиенты, делающие это, ДОЛЖНЫ ограничивать число таких повторов. Если конкретный код ошибки не указывает иное значение, число повторных передач СЛЕДУЕТ ограничивать 4.
Any other error code causes the client to consider the transaction failed.
Любой другой код ошибки заставляет клиента считать транзакцию неудачной.
7. FINGERPRINT Mechanism
7. Механизм FINGERPRINT
This section describes an optional mechanism for STUN that aids in distinguishing STUN messages from packets of other protocols when the two are multiplexed on the same transport address. This mechanism is optional, and a STUN Usage must describe if and when it is used. The FINGERPRINT mechanism is not backwards compatible with RFC 3489 and cannot be used in environments where such compatibility is required.
В этом разделе описан необязательный механизм STUN, помогающий отличать сообщения STUN от пакетов других протоколов, когда они мультиплексируются на одном транспортном адресе. Этот механизм необязателен, и применение STUN должно описывать, используется ли он и когда. Механизм FINGERPRINT несовместим с RFC 3489 и не может использоваться в средах, где требуется такая совместимость.
In some usages, STUN messages are multiplexed on the same transport address as other protocols, such as the Real-Time Transport Protocol (RTP). In order to apply the processing described in Section 6, STUN messages must first be separated from the application packets.
В некоторых применениях сообщения STUN мультиплексируются на том же транспортном адресе, что и другие протоколы, например Real-Time Transport Protocol (RTP). Чтобы применить обработку, описанную в разделе 6, сообщения STUN необходимо сначала отделить от пакетов приложения.
Section 5 describes three fixed fields in the STUN header that can be used for this purpose. However, in some cases, these three fixed fields may not be sufficient.
В разделе 5 описаны три фиксированных поля в заголовке STUN, которые можно использовать для этой цели. Однако в некоторых случаях этих трёх фиксированных полей может быть недостаточно.
When the FINGERPRINT extension is used, an agent includes the FINGERPRINT attribute in messages it sends to another agent. Section 14.7 describes the placement and value of this attribute.
Когда используется расширение FINGERPRINT, агент включает атрибут FINGERPRINT в сообщения, которые он отправляет другому агенту. Раздел 14.7 описывает размещение и значение этого атрибута.
When the agent receives what it believes is a STUN message, then, in addition to other basic checks, the agent also checks that the message contains a FINGERPRINT attribute and that the attribute contains the correct value. Section 6.3 describes when in the overall processing of a STUN message the FINGERPRINT check is performed. This additional check helps the agent detect messages of other protocols that might otherwise seem to be STUN messages.
Когда агент получает то, что он считает сообщением STUN, он, в дополнение к другим базовым проверкам, также проверяет, что сообщение содержит атрибут FINGERPRINT и что этот атрибут содержит правильное значение. Раздел 6.3 описывает, когда в общей обработке сообщения STUN выполняется проверка FINGERPRINT. Эта дополнительная проверка помогает агенту обнаруживать сообщения других протоколов, которые иначе могли бы показаться сообщениями STUN.
8. DNS Discovery of a Server
8. Обнаружение сервера через DNS
This section describes an optional procedure for STUN that allows a client to use DNS to determine the IP address and port of a server. A STUN Usage must describe if and when this extension is used. To use this procedure, the client must know a STUN URI [RFC7064]; the usage must also describe how the client obtains this URI. Hard- coding a STUN URI into software is NOT RECOMMENDED in case the domain name is lost or needs to change for legal or other reasons.
В этом разделе описана необязательная процедура STUN, позволяющая клиенту использовать DNS для определения IP-адреса и порта сервера. Применение STUN должно описывать, используется ли это расширение и когда. Чтобы использовать эту процедуру, клиент должен знать STUN URI [RFC7064]; применение также должно описывать, как клиент получает этот URI. Жёсткое задание STUN URI в программном обеспечении НЕ РЕКОМЕНДУЕТСЯ на случай, если доменное имя будет потеряно или потребует изменения по юридическим или иным причинам.
When a client wishes to locate a STUN server on the public Internet that accepts Binding request/response transactions, the STUN URI scheme is "stun". When it wishes to locate a STUN server that accepts Binding request/response transactions over a TLS or DTLS session, the URI scheme is "stuns".
Когда клиент хочет найти сервер STUN в публичном Интернете, принимающий транзакции запрос/ответ Binding, схема STUN URI — «stun». Когда он хочет найти сервер STUN, принимающий транзакции запрос/ответ Binding через сеанс TLS или DTLS, схема URI — «stuns».
The syntax of the "stun" and "stuns" URIs is defined in Section 3.1 of [RFC7064]. STUN Usages MAY define additional URI schemes.
Синтаксис URI «stun» и «stuns» определён в разделе 3.1 [RFC7064]. Применения STUN МОГУТ определять дополнительные схемы URI.
8.1. STUN URI Scheme Semantics
8.1. Семантика схемы URI STUN
If the <host> part of a "stun" URI contains an IP address, then this IP address is used directly to contact the server. A "stuns" URI containing an IP address MUST be rejected. A future STUN extension or usage may relax this requirement, provided it demonstrates how to authenticate the STUN server and prevent man-in-the-middle attacks.
Если часть <host> URI «stun» содержит IP-адрес, то этот IP-адрес используется непосредственно для связи с сервером. URI «stuns», содержащий IP-адрес, ДОЛЖЕН быть отвергнут. Будущее расширение или применение STUN может ослабить это требование при условии, что оно продемонстрирует, как аутентифицировать сервер STUN и предотвращать атаки «человек посередине».
If the URI does not contain an IP address, the domain name contained in the <host> part is resolved to a transport address using the SRV procedures specified in [RFC2782]. The DNS SRV service name is the content of the <scheme> part. The protocol in the SRV lookup is the transport protocol the client will run STUN over: "udp" for UDP and "tcp" for TCP.
Если URI не содержит IP-адрес, доменное имя, содержащееся в части <host>, разрешается в транспортный адрес с использованием процедур SRV, указанных в [RFC2782]. Имя службы DNS SRV — это содержимое части <scheme>. Протокол при поиске SRV — это транспортный протокол, через который клиент будет запускать STUN: «udp» для UDP и «tcp» для TCP.
The procedures of RFC 2782 are followed to determine the server to contact. RFC 2782 spells out the details of how a set of SRV records is sorted and then tried. However, RFC 2782 only states that the client should "try to connect to the (protocol, address, service)" without giving any details on what happens in the event of failure. When following these procedures, if the STUN transaction times out without receipt of a response, the client SHOULD retry the request to the next server in the order defined by RFC 2782. Such a retry is only possible for request/response transmissions, since indication transactions generate no response or timeout.
Для определения сервера, с которым нужно связаться, соблюдаются процедуры RFC 2782. RFC 2782 детально описывает, как сортируется набор записей SRV и затем выполняется их попытка. Однако RFC 2782 лишь утверждает, что клиент должен «попытаться подключиться к (протоколу, адресу, службе)», не приводя подробностей о том, что происходит в случае неудачи. При соблюдении этих процедур, если транзакция STUN истекает по времени без получения ответа, клиенту СЛЕДУЕТ повторить запрос к следующему серверу в порядке, определённом RFC 2782. Такой повтор возможен только для передач запрос/ответ, поскольку транзакции-индикации не порождают ни ответа, ни тайм-аута.
In addition, instead of querying either the A or the AAAA resource records for a domain name, a dual-stack IPv4/IPv6 client MUST query both and try the requests with all the IP addresses received, as specified in [RFC8305].
Кроме того, вместо запроса либо ресурсной записи A, либо AAAA для доменного имени двухстековый клиент IPv4/IPv6 ДОЛЖЕН запрашивать обе и пробовать запросы со всеми полученными IP-адресами, как указано в [RFC8305].
The default port for STUN requests is 3478, for both TCP and UDP. The default port for STUN over TLS and STUN over DTLS requests is 5349. Servers can run STUN over DTLS on the same port as STUN over UDP if the server software supports determining whether the initial message is a DTLS or STUN message. Servers can run STUN over TLS on the same port as STUN over TCP if the server software supports determining whether the initial message is a TLS or STUN message.
Порт по умолчанию для запросов STUN — 3478, как для TCP, так и для UDP. Порт по умолчанию для запросов STUN через TLS и STUN через DTLS — 5349. Серверы могут запускать STUN через DTLS на том же порту, что и STUN через UDP, если серверное программное обеспечение поддерживает определение того, является ли начальное сообщение сообщением DTLS или STUN. Серверы могут запускать STUN через TLS на том же порту, что и STUN через TCP, если серверное программное обеспечение поддерживает определение того, является ли начальное сообщение сообщением TLS или STUN.
Administrators of STUN servers SHOULD use these ports in their SRV records for UDP and TCP. In all cases, the port in DNS MUST reflect the one on which the server is listening.
Администраторам серверов STUN СЛЕДУЕТ использовать эти порты в своих записях SRV для UDP и TCP. Во всех случаях порт в DNS ДОЛЖЕН отражать тот порт, на котором прослушивает сервер.
If no SRV records are found, the client performs both an A and AAAA record lookup of the domain name, as described in [RFC8305]. The result will be a list of IP addresses, each of which can be simultaneously contacted at the default port using UDP or TCP, independent of the STUN Usage. For usages that require TLS, the client connects to the IP addresses using the default STUN over TLS port. For usages that require DTLS, the client connects to the IP addresses using the default STUN over DTLS port.
Если записи SRV не найдены, клиент выполняет поиск как записи A, так и записи AAAA для доменного имени, как описано в [RFC8305]. Результатом будет список IP-адресов, каждый из которых можно одновременно попытаться связать на порту по умолчанию через UDP или TCP независимо от применения STUN. Для применений, требующих TLS, клиент подключается к IP-адресам через порт STUN-over-TLS по умолчанию. Для применений, требующих DTLS, клиент подключается к IP-адресам через порт STUN-over-DTLS по умолчанию.
9. Authentication and Message-Integrity Mechanisms
9. Механизмы аутентификации и целостности сообщений
This section defines two mechanisms for STUN that a client and server can use to provide authentication and message integrity; these two mechanisms are known as the short-term credential mechanism and the long-term credential mechanism. These two mechanisms are optional, and each usage must specify if and when these mechanisms are used. Consequently, both clients and servers will know which mechanism (if any) to follow based on knowledge of which usage applies. For example, a STUN server on the public Internet supporting ICE would have no authentication, whereas the STUN server functionality in an agent supporting connectivity checks would utilize short-term credentials. An overview of these two mechanisms is given in Section 2.
В этом разделе определены два механизма STUN, которые клиент и сервер могут использовать для обеспечения аутентификации и целостности сообщений; эти два механизма известны как механизм краткосрочных учетных данных и механизм долгосрочных учетных данных. Эти два механизма необязательны, и каждое применение должно указывать, используются ли эти механизмы и когда. Следовательно, и клиенты, и серверы будут знать, какой механизм (если таковой имеется) применять, исходя из знания о том, какое применение применяется. Например, сервер STUN в публичном Интернете, поддерживающий ICE, не будет использовать аутентификацию, тогда как функциональность сервера STUN в агенте, поддерживающем проверки связности, будет использовать краткосрочные учетные данные. Обзор этих двух механизмов приведён в разделе 2.
Each mechanism specifies the additional processing required to use that mechanism, extending the processing specified in Section 6. The additional processing occurs in three different places: when forming a message, when receiving a message immediately after the basic checks have been performed, and when doing the detailed processing of error responses.
Каждый механизм определяет дополнительную обработку, необходимую для использования этого механизма, расширяя обработку, определённую в разделе 6. Дополнительная обработка выполняется в трёх различных местах: при формировании сообщения, при получении сообщения сразу после выполнения базовых проверок и при подробной обработке ответов об ошибках.

9.1. Short-Term Credential Mechanism
9.1. Механизм краткосрочных учетных данных
The short-term credential mechanism assumes that, prior to the STUN transaction, the client and server have used some other protocol to exchange a credential in the form of a username and password. This credential is time-limited. The time limit is defined by the usage. As an example, in the ICE usage [RFC8445], the two endpoints use out- of-band signaling to agree on a username and password, and this username and password are applicable for the duration of the media session.
Механизм краткосрочных учетных данных предполагает, что до транзакции STUN клиент и сервер использовали какой-либо другой протокол для обмена учетными данными в виде имени пользователя и пароля. Эти учетные данные ограничены по времени. Ограничение по времени определяется применением. Например, в применении ICE [RFC8445] две конечные точки используют внешнюю сигнализацию, чтобы договориться об имени пользователя и пароле, и это имя пользователя и пароль действуют в течение сеанса медиа.
This credential is used to form a message-integrity check in each request and in many responses. There is no challenge and response as in the long-term mechanism; consequently, replay is limited by virtue of the time-limited nature of the credential.
Эти учетные данные используются для формирования проверки целостности сообщения в каждом запросе и во многих ответах. Здесь нет запроса-вызова и ответа, как в долгосрочном механизме; следовательно, повторное воспроизведение ограничено в силу ограниченного по времени характера учетных данных.

9.2. Long-Term Credential Mechanism
9.2. Механизм долгосрочных учетных данных
The long-term credential mechanism relies on a long-term credential, in the form of a username and password that are shared between client and server. The credential is considered long-term since it is assumed that it is provisioned for a user and remains in effect until the user is no longer a subscriber of the system or until it is changed. This is basically a traditional "log-in" username and password given to users.
Механизм долгосрочных учетных данных опирается на долгосрочные учетные данные в виде имени пользователя и пароля, которые совместно используются клиентом и сервером. Учетные данные считаются долгосрочными, поскольку предполагается, что они предоставлены пользователю и остаются в силе, пока пользователь не перестанет быть абонентом системы или пока они не будут изменены. По сути это традиционные имя пользователя и пароль для «входа в систему», выдаваемые пользователям.

9.2.1. Bid-Down Attack Prevention
9.2.1. Предотвращение атаки понижения
This document introduces two new security features that provide the ability to choose the algorithm used for password protection as well as the ability to use an anonymous username. Both of these capabilities are optional in order to remain backwards compatible with previous versions of the STUN protocol.
Настоящий документ вводит две новые функции безопасности, обеспечивающие возможность выбора алгоритма, используемого для защиты пароля, а также возможность использования анонимного имени пользователя. Обе эти возможности необязательны, чтобы оставаться обратно совместимыми с предыдущими версиями протокола STUN.
These new capabilities are subject to bid-down attacks whereby an attacker in the message path can remove these capabilities and force weaker security properties. To prevent these kinds of attacks from going undetected, the nonce is enhanced with additional information.
Эти новые возможности подвержены атакам понижения, при которых атакующий на пути сообщения может удалить эти возможности и навязать более слабые свойства безопасности. Чтобы такие атаки не остались незамеченными, nonce дополняется дополнительной информацией.
The value of the "nonce cookie" will vary based on the specific STUN Security Feature bits selected. When this document makes reference to the "nonce cookie" in a section discussing a specific STUN Security Feature it is understood that the corresponding STUN Security Feature bit in the "nonce cookie" is set to 1.
Значение «nonce cookie» будет различаться в зависимости от выбранных конкретных битов функций безопасности STUN. Когда настоящий документ ссылается на «nonce cookie» в разделе, обсуждающем конкретную функцию безопасности STUN, подразумевается, что соответствующий бит функции безопасности STUN в «nonce cookie» установлен в 1.
For example, when the PASSWORD-ALGORITHMS security feature (defined in Section 9.2.4) is used, the corresponding "Password algorithms" bit (defined in Section 18.1) is set to 1 in the "nonce cookie".
Например, когда используется функция безопасности PASSWORD-ALGORITHMS (определённая в разделе 9.2.4), соответствующий бит «Password algorithms» (определённый в разделе 18.1) устанавливается в 1 в «nonce cookie».
9.2.2. HMAC Key
9.2.2. Ключ HMAC
For long-term credentials that do not use a different algorithm, as specified by the PASSWORD-ALGORITHM attribute, the key is 16 bytes:
Для долгосрочных учетных данных, в которых не используется другой алгоритм, указанный атрибутом PASSWORD-ALGORITHM, ключ имеет длину 16 байт:
key = MD5(username ":" OpaqueString(realm) ":" OpaqueString(password))
key = MD5(username ":" OpaqueString(realm) ":" OpaqueString(password))
Where MD5 is defined in [RFC1321] and [RFC6151], and the OpaqueString profile is defined in [RFC8265]. The encoding used is UTF-8 [RFC3629]. The 16-byte key is formed by taking the MD5 hash of the result of concatenating the following five fields: (1) the username, with any quotes and trailing nulls removed, as taken from the USERNAME attribute (in which case OpaqueString has already been applied); (2) a single colon; (3) the realm, with any quotes and trailing nulls removed and after processing using OpaqueString; (4) a single colon; and (5) the password, with any trailing nulls removed and after processing using OpaqueString. For example, if the username is 'user', the realm is 'realm', and the password is 'pass', then the 16-byte HMAC key would be the result of performing an MD5 hash on the string 'user:realm:pass', the resulting hash being 0x8493fbc53ba582fb4c044c456bdc40eb.
Где MD5 определён в [RFC1321] и [RFC6151], а профиль OpaqueString определён в [RFC8265]. Используемая кодировка — UTF-8 [RFC3629]. 16-байтный ключ формируется путём взятия хеша MD5 от результата конкатенации следующих пяти полей: (1) имя пользователя с удалёнными кавычками и завершающими нулями, взятое из атрибута USERNAME (в этом случае OpaqueString уже применён); (2) одно двоеточие; (3) realm с удалёнными кавычками и завершающими нулями и после обработки с помощью OpaqueString; (4) одно двоеточие; и (5) пароль с удалёнными завершающими нулями и после обработки с помощью OpaqueString. Например, если имя пользователя — «user», realm — «realm», а пароль — «pass», то 16-байтный ключ HMAC будет результатом вычисления хеша MD5 от строки «user:realm:pass», причём результирующий хеш будет 0x8493fbc53ba582fb4c044c456bdc40eb.
The structure of the key when used with long-term credentials facilitates deployment in systems that also utilize SIP [RFC3261]. Typically, SIP systems utilizing SIP's digest authentication mechanism do not actually store the password in the database. Rather, they store a value called "H(A1)", which is equal to the key defined above. For example, this mechanism can be used with the authentication extensions defined in [RFC5090].
Структура ключа при использовании с долгосрочными учетными данными облегчает развёртывание в системах, которые также используют SIP [RFC3261]. Обычно системы SIP, использующие механизм digest-аутентификации SIP, фактически не хранят пароль в базе данных. Вместо этого они хранят значение, называемое «H(A1)», которое равно ключу, определённому выше. Например, этот механизм можно использовать с расширениями аутентификации, определёнными в [RFC5090].
When a PASSWORD-ALGORITHM is used, the key length and algorithm to use are described in Section 18.5.1.
Когда используется PASSWORD-ALGORITHM, длина ключа и используемый алгоритм описаны в разделе 18.5.1.
9.2.3. Forming a Request
9.2.3. Формирование запроса
The first request from the client to the server (as identified by hostname if the DNS procedures of Section 8 are used and by IP address if not) is handled according to the rules in Section 9.2.3.1. When the client initiates a subsequent request once a previous request/response transaction has completed successfully, it follows the rules in Section 9.2.3.2. Forming a request as a consequence of a 401 (Unauthenticated) or 438 (Stale Nonce) error response is covered in Section 9.2.5 and is not considered a "subsequent request" and thus does not utilize the rules described in Section 9.2.3.2. Each of these types of requests have a different mandatory attributes.
Первый запрос от клиента серверу (идентифицируемый по имени узла, если используются процедуры DNS раздела 8, и по IP-адресу, если нет) обрабатывается согласно правилам раздела 9.2.3.1. Когда клиент инициирует последующий запрос после успешного завершения предыдущей транзакции запрос/ответ, он следует правилам раздела 9.2.3.2. Формирование запроса вследствие ответа об ошибке 401 (Unauthenticated) или 438 (Stale Nonce) рассматривается в разделе 9.2.5 и не считается «последующим запросом» и, следовательно, не использует правила, описанные в разделе 9.2.3.2. Каждый из этих типов запросов имеет различные обязательные атрибуты.
9.2.3.1. First Request
9.2.3.1. Первый запрос
If the client has not completed a successful request/response transaction with the server, it MUST omit the USERNAME, USERHASH, MESSAGE-INTEGRITY, MESSAGE-INTEGRITY-SHA256, REALM, NONCE, PASSWORD- ALGORITHMS, and PASSWORD-ALGORITHM attributes. In other words, the first request is sent as if there were no authentication or message integrity applied.
Если клиент не завершил успешную транзакцию запрос/ответ с сервером, он ДОЛЖЕН опустить атрибуты USERNAME, USERHASH, MESSAGE-INTEGRITY, MESSAGE-INTEGRITY-SHA256, REALM, NONCE, PASSWORD-ALGORITHMS и PASSWORD-ALGORITHM. Иными словами, первый запрос отправляется так, как если бы аутентификация и целостность сообщения не применялись.
9.2.3.2. Subsequent Requests
9.2.3.2. Последующие запросы
Once a request/response transaction has completed, the client will have been presented a realm and nonce by the server and selected a username and password with which it authenticated. The client SHOULD cache the username, password, realm, and nonce for subsequent communications with the server. When the client sends a subsequent request, it MUST include either the USERNAME or USERHASH, REALM, NONCE, and PASSWORD-ALGORITHM attributes with these cached values. It MUST include a MESSAGE-INTEGRITY attribute or a MESSAGE-INTEGRITY- SHA256 attribute, computed as described in Sections 14.5 and 14.6 using the cached password. The choice between the two attributes depends on the attribute received in the response to the first request.
После завершения транзакции запрос/ответ сервер предоставит клиенту realm и nonce, а клиент выберет имя пользователя и пароль, с которыми он аутентифицировался. Клиенту СЛЕДУЕТ кэшировать имя пользователя, пароль, realm и nonce для последующей связи с сервером. Когда клиент отправляет последующий запрос, он ДОЛЖЕН включить атрибуты USERNAME или USERHASH, REALM, NONCE и PASSWORD-ALGORITHM с этими кэшированными значениями. Он ДОЛЖЕН включить атрибут MESSAGE-INTEGRITY или MESSAGE-INTEGRITY-SHA256, вычисленный, как описано в разделах 14.5 и 14.6, с использованием кэшированного пароля. Выбор между двумя атрибутами зависит от атрибута, полученного в ответе на первый запрос.

If the resulting value matches the contents of the MESSAGE-INTEGRITY or MESSAGE-INTEGRITY-SHA256 attribute, the response is considered authenticated. If the value does not match, or if both MESSAGE-INTEGRITY and MESSAGE-INTEGRITY- SHA256 are absent, the processing depends on the request being sent over a reliable or an unreliable transport.
Клиент ищет атрибут MESSAGE-INTEGRITY или MESSAGE-INTEGRITY-SHA256 в ответе (как успешном, так и неуспешном). Если он присутствует, клиент вычисляет целостность сообщения по ответу, как определено в разделах 14.5 или 14.6, используя тот же пароль, который он применял для запроса. Если полученное значение совпадает с содержимым атрибута MESSAGE-INTEGRITY или MESSAGE-INTEGRITY-SHA256, ответ считается аутентифицированным. Если значение не совпадает или если оба атрибута MESSAGE-INTEGRITY и MESSAGE-INTEGRITY-SHA256 отсутствуют, обработка зависит от того, был ли запрос отправлен через надёжный или ненадёжный транспорт.
If the request was sent over an unreliable transport, the response MUST be discarded, as if it had never been received. This means that retransmits, if applicable, will continue. If all the responses received are discarded, then instead of signaling a timeout after ending the transaction, the layer MUST signal that the integrity protection was violated.
Если запрос был отправлен через ненадёжный транспорт, ответ ДОЛЖЕН быть отброшен, как если бы он никогда не был получен. Это означает, что повторные передачи, если применимо, будут продолжаться. Если все полученные ответы отброшены, то вместо сигнализации тайм-аута после завершения транзакции уровень ДОЛЖЕН сигнализировать, что защита целостности была нарушена.
If the request was sent over a reliable transport, the response MUST be discarded, and the layer MUST immediately end the transaction and signal that the integrity protection was violated.
Если запрос был отправлен через надёжный транспорт, ответ ДОЛЖЕН быть отброшен, а уровень ДОЛЖЕН немедленно завершить транзакцию и сигнализировать, что защита целостности была нарушена.
If the response contains a PASSWORD-ALGORITHMS attribute, all the subsequent requests MUST be authenticated using MESSAGE-INTEGRITY- SHA256 only.
Если ответ содержит атрибут PASSWORD-ALGORITHMS, все последующие запросы ДОЛЖНЫ аутентифицироваться только с помощью MESSAGE-INTEGRITY-SHA256.
10. ALTERNATE-SERVER Mechanism
10. Механизм ALTERNATE-SERVER
This section describes a mechanism in STUN that allows a server to redirect a client to another server. This extension is optional, and a usage must define if and when this extension is used. The ALTERNATE-SERVER attribute carries an IP address.
В этом разделе описан механизм STUN, позволяющий серверу перенаправить клиента на другой сервер. Это расширение необязательно, и применение должно определять, используется ли это расширение и когда. Атрибут ALTERNATE-SERVER несёт IP-адрес.
A server using this extension redirects a client to another server by replying to a request message with an error response message with an error code of 300 (Try Alternate). The server MUST include at least one ALTERNATE-SERVER attribute in the error response, which MUST contain an IP address of the same address family as the source IP address of the request message. The server SHOULD include an additional ALTERNATE-SERVER attribute, after the mandatory one, that contains an IP address of the address family other than the source IP address of the request message. The error response message MAY be authenticated; however, there are use cases for ALTERNATE-SERVER where authentication of the response is not possible or practical. If the transaction uses TLS or DTLS, if the transaction is authenticated by a MESSAGE-INTEGRITY-SHA256 attribute, and if the server wants to redirect to a server that uses a different certificate, then it MUST include an ALTERNATE-DOMAIN attribute containing the name inside the subjectAltName of that certificate. This series of conditions on the MESSAGE-INTEGRITY-SHA256 attribute indicates that the transaction is authenticated and that the client implements this specification and therefore can process the ALTERNATE-DOMAIN attribute.
Сервер, использующий это расширение, перенаправляет клиента на другой сервер, отвечая на сообщение-запрос сообщением-ответом об ошибке с кодом ошибки 300 (Try Alternate). Сервер ДОЛЖЕН включить в ответ об ошибке по крайней мере один атрибут ALTERNATE-SERVER, который ДОЛЖЕН содержать IP-адрес того же семейства адресов, что и исходный IP-адрес сообщения-запроса. Серверу СЛЕДУЕТ включить дополнительный атрибут ALTERNATE-SERVER после обязательного, содержащий IP-адрес семейства адресов, отличного от исходного IP-адреса сообщения-запроса. Сообщение-ответ об ошибке МОЖЕТ быть аутентифицировано; однако существуют варианты использования ALTERNATE-SERVER, где аутентификация ответа невозможна или непрактична. Если транзакция использует TLS или DTLS, если транзакция аутентифицирована атрибутом MESSAGE-INTEGRITY-SHA256 и если сервер хочет перенаправить на сервер, использующий другой сертификат, то он ДОЛЖЕН включить атрибут ALTERNATE-DOMAIN, содержащий имя из subjectAltName этого сертификата. Эта серия условий на атрибут MESSAGE-INTEGRITY-SHA256 указывает, что транзакция аутентифицирована, что клиент реализует данную спецификацию и, следовательно, может обработать атрибут ALTERNATE-DOMAIN.
A client using this extension handles a 300 (Try Alternate) error code as follows. The client looks for an ALTERNATE-SERVER attribute in the error response. If one is found, then the client considers the current transaction as failed and reattempts the request with the server specified in the attribute, using the same transport protocol used for the previous request. That request, if authenticated, MUST utilize the same credentials that the client would have used in the request to the server that performed the redirection. If the transport protocol uses TLS or DTLS, then the client looks for an ALTERNATE-DOMAIN attribute. If the attribute is found, the domain MUST be used to validate the certificate using the recommendations in [RFC6125]. The certificate MUST contain an identifier of type DNS-ID or CN-ID (eventually with wildcards) but not of type SRV-ID or URI- ID. If the attribute is not found, the same domain that was used for the original request MUST be used to validate the certificate. If the client has been redirected to a server to which it has already sent this request within the last five minutes, it MUST ignore the redirection and consider the transaction to have failed. This prevents infinite ping-ponging between servers in case of redirection loops.
Клиент, использующий это расширение, обрабатывает код ошибки 300 (Try Alternate) следующим образом. Клиент ищет атрибут ALTERNATE-SERVER в ответе об ошибке. Если он найден, клиент считает текущую транзакцию неудачной и повторяет запрос к серверу, указанному в атрибуте, используя тот же транспортный протокол, что и для предыдущего запроса. Этот запрос, если он аутентифицирован, ДОЛЖЕН использовать те же учетные данные, которые клиент использовал бы в запросе к серверу, выполнившему перенаправление. Если транспортный протокол использует TLS или DTLS, клиент ищет атрибут ALTERNATE-DOMAIN. Если атрибут найден, домен ДОЛЖЕН использоваться для проверки сертификата с использованием рекомендаций в [RFC6125]. Сертификат ДОЛЖЕН содержать идентификатор типа DNS-ID или CN-ID (возможно, с подстановочными символами), но не типа SRV-ID или URI-ID. Если атрибут не найден, для проверки сертификата ДОЛЖЕН использоваться тот же домен, который использовался для исходного запроса. Если клиент был перенаправлен на сервер, которому он уже отправлял этот запрос за последние пять минут, он ДОЛЖЕН проигнорировать перенаправление и считать транзакцию неудачной. Это предотвращает бесконечный пинг-понг между серверами в случае циклов перенаправления.
11. Backwards Compatibility with RFC 3489
11. Обратная совместимость с RFC 3489
In addition to the backward compatibility already described in Section 12 of [RFC5389], DTLS MUST NOT be used with [RFC3489] (referred to as "classic STUN"). Any STUN request or indication without the magic cookie (see Section 6 of [RFC5389]) over DTLS MUST be considered invalid: all requests MUST generate a 500 (Server Error) error response, and indications MUST be ignored.
В дополнение к обратной совместимости, уже описанной в разделе 12 [RFC5389], DTLS НЕ ДОЛЖЕН использоваться с [RFC3489] (называемым «классическим STUN»). Любой запрос или индикация STUN без магического cookie (см. раздел 6 [RFC5389]) через DTLS ДОЛЖНЫ считаться недопустимыми: все запросы ДОЛЖНЫ генерировать ответ об ошибке 500 (Server Error), а индикации ДОЛЖНЫ игнорироваться.
12. Basic Server Behavior
12. Базовое поведение сервера
This section defines the behavior of a basic, stand-alone STUN server.
В этом разделе определено поведение базового автономного сервера STUN.
Historically, "classic STUN" [RFC3489] only defined the behavior of a server that was providing clients with server reflexive transport addresses by receiving and replying to STUN Binding requests. [RFC5389] redefined the protocol as an extensible framework, and the server functionality became the sole STUN Usage defined in that document. This STUN Usage is also known as "Basic STUN Server".
Исторически «классический STUN» [RFC3489] определял только поведение сервера, который предоставлял клиентам рефлексивные транспортные адреса сервера путём получения и ответа на запросы Binding STUN. [RFC5389] переопределил протокол как расширяемую инфраструктуру, и функциональность сервера стала единственным применением STUN, определённым в том документе. Это применение STUN также известно как «Basic STUN Server».
The STUN server MUST support the Binding method. It SHOULD NOT utilize the short-term or long-term credential mechanism. This is because the work involved in authenticating the request is more than the work in simply processing it. It SHOULD NOT utilize the ALTERNATE-SERVER mechanism for the same reason. It MUST support UDP and TCP. It MAY support STUN over TCP/TLS or STUN over UDP/DTLS; however, DTLS and TLS provide minimal security benefits in this basic mode of operation. It does not require a keep-alive mechanism because a TCP or TLS-over-TCP connection is closed after the end of the Binding transaction. It MAY utilize the FINGERPRINT mechanism but MUST NOT require it. Since the stand-alone server only runs STUN, FINGERPRINT provides no benefit. Requiring it would break compatibility with RFC 3489, and such compatibility is desirable in a stand-alone server. Stand-alone STUN servers SHOULD support backwards compatibility with clients using [RFC3489], as described in Section 11.
Сервер STUN ДОЛЖЕН поддерживать метод Binding. Ему НЕ СЛЕДУЕТ использовать механизм краткосрочных или долгосрочных учетных данных. Это связано с тем, что работа по аутентификации запроса больше, чем работа по его простой обработке. Ему НЕ СЛЕДУЕТ использовать механизм ALTERNATE-SERVER по той же причине. Он ДОЛЖЕН поддерживать UDP и TCP. Он МОЖЕТ поддерживать STUN через TCP/TLS или STUN через UDP/DTLS; однако DTLS и TLS обеспечивают минимальные преимущества безопасности в этом базовом режиме работы. Он не требует механизма поддержания активности, поскольку TCP-соединение или соединение TLS-over-TCP закрывается после завершения транзакции Binding. Он МОЖЕТ использовать механизм FINGERPRINT, но НЕ ДОЛЖЕН его требовать. Поскольку автономный сервер работает только со STUN, FINGERPRINT не даёт преимуществ. Его требование нарушило бы совместимость с RFC 3489, а такая совместимость желательна для автономного сервера. Автономным серверам STUN СЛЕДУЕТ поддерживать обратную совместимость с клиентами, использующими [RFC3489], как описано в разделе 11.
It is RECOMMENDED that administrators of STUN servers provide DNS entries for those servers as described in Section 8. If both A and AAAA resource records are returned, then the client can simultaneously send STUN Binding requests to the IPv4 and IPv6 addresses (as specified in [RFC8305]), as the Binding request is idempotent. Note that the MAPPED-ADDRESS or XOR-MAPPED-ADDRESS attributes that are returned will not necessarily match the address family of the server address used. A basic STUN server is not a solution for NAT traversal by itself. However, it can be utilized as part of a solution through STUN Usages. This is discussed further in Section 13.
РЕКОМЕНДУЕТСЯ, чтобы администраторы серверов STUN предоставляли DNS-записи для этих серверов, как описано в разделе 8. Если возвращаются обе ресурсные записи A и AAAA, клиент может одновременно отправлять запросы Binding STUN на адреса IPv4 и IPv6 (как указано в [RFC8305]), поскольку запрос Binding идемпотентен. Обратите внимание, что возвращаемые атрибуты MAPPED-ADDRESS или XOR-MAPPED-ADDRESS не обязательно будут соответствовать семейству адресов используемого адреса сервера. Базовый сервер STUN сам по себе не является решением для обхода NAT. Однако он может использоваться как часть решения через применения STUN. Это дополнительно обсуждается в разделе 13.

14.1. MAPPED-ADDRESS
14.1. MAPPED-ADDRESS
The MAPPED-ADDRESS attribute indicates a reflexive transport address of the client. It consists of an 8-bit address family and a 16-bit port, followed by a fixed-length value representing the IP address. If the address family is IPv4, the address MUST be 32 bits. If the address family is IPv6, the address MUST be 128 bits. All fields must be in network byte order.
Атрибут MAPPED-ADDRESS указывает рефлексивный транспортный адрес клиента. Он состоит из 8-битного семейства адресов и 16-битного порта, за которыми следует значение фиксированной длины, представляющее IP-адрес. X-Port is computed by XOR'ing the mapped port with the most significant 16 bits of the magic cookie. If the IP address family is IPv4, X-Address is computed by XOR'ing the mapped IP address with the magic cookie. The latter encodes it directly in binary. RFC 3489 originally specified only MAPPED- ADDRESS. However, deployment experience found that some NATs rewrite the 32-bit binary payloads containing the NAT's public IP address, such as STUN's MAPPED-ADDRESS attribute, in the well-meaning but misguided attempt to provide a generic Application Layer Gateway (ALG) function. Such behavior interferes with the operation of STUN and also causes failure of STUN's message-integrity checking.
Примечание: XOR-MAPPED-ADDRESS и MAPPED-ADDRESS различаются только кодированием транспортного адреса. Первый кодирует транспортный адрес путём его XOR-ирования с магическим cookie. Второй кодирует его непосредственно в двоичном виде. Первоначально RFC 3489 определял только MAPPED-ADDRESS. Однако опыт развёртывания показал, что некоторые NAT перезаписывают 32-битные двоичные полезные нагрузки, содержащие публичный IP-адрес NAT, такие как атрибут MAPPED-ADDRESS в STUN, в доброжелательной, но ошибочной попытке обеспечить общую функцию шлюза прикладного уровня (ALG). Такое поведение мешает работе STUN и также вызывает сбой проверки целостности сообщений STUN.
14.3. USERNAME
14.3. USERNAME
The USERNAME attribute is used for message integrity. It identifies the username and password combination used in the message-integrity check.
Атрибут USERNAME используется для целостности сообщения. Он идентифицирует комбинацию имени пользователя и пароля, использованную в проверке целостности сообщения.
The value of USERNAME is a variable-length value containing the authentication username. It MUST contain a UTF-8-encoded [RFC3629] sequence of fewer than 509 bytes and MUST have been processed using the OpaqueString profile [RFC8265]. A compliant implementation MUST be able to parse a UTF-8-encoded sequence of 763 or fewer octets to be compatible with [RFC5389].
Значение USERNAME — это значение переменной длины, содержащее имя пользователя для аутентификации. Оно ДОЛЖНО содержать последовательность в кодировке UTF-8 [RFC3629] длиной менее 509 байт и ДОЛЖНО быть обработано с использованием профиля OpaqueString [RFC8265]. Соответствующая реализация ДОЛЖНА уметь разбирать последовательность в кодировке UTF-8 длиной 763 или менее октетов для совместимости с [RFC5389].
Note: [RFC5389] mistakenly referenced the definition of UTF-8 in [RFC2279]. [RFC2279] assumed up to 6 octets per characters encoded. [RFC2279] was replaced by [RFC3629], which allows only 4 octets per character encoded, consistent with changes made in Unicode 2.0 and ISO/IEC 10646.
Примечание: [RFC5389] ошибочно ссылался на определение UTF-8 в [RFC2279]. [RFC2279] предполагал до 6 октетов на кодируемый символ. [RFC2279] был заменён на [RFC3629], который допускает только 4 октета на кодируемый символ, что согласуется с изменениями, внесёнными в Unicode 2.0 и ISO/IEC 10646.
Note: This specification uses the OpaqueString profile instead of the UsernameCasePreserved profile for username string processing in order to improve compatibility with deployed password stores. Many password databases used for HTTP and SIP Digest authentication store the MD5 hash of username:realm:password instead of storing a plain text password. In [RFC3489], STUN authentication was designed to be compatible with these existing databases to the extent possible, which like SIP and HTTP performed no pre-processing of usernames and passwords other than prohibiting non-space ASCII control characters. The next revision of the STUN specification, [RFC5389], used the SASLprep [RFC4013] stringprep [RFC3454] profile to pre-process usernames and passwords. SASLprep uses Unicode Normalization Form KC (Compatibility Decomposition, followed by Canonical Composition) [UAX15] and prohibits various control, space, and non-text, deprecated, or inappropriate codepoints. The PRECIS framework [RFC8264] obsoletes stringprep. PRECIS handling of usernames and passwords [RFC8265] uses Unicode Normalization Form C (Canonical Decomposition, followed by Canonical Composition). While there are specific cases where different username strings under HTTP Digest could be mapped to a single STUN username processed with OpaqueString, these cases are extremely unlikely and easy to detect and correct. With a UsernameCasePreserved profile, it would be more likely that valid usernames under HTTP Digest would not match their processed forms (specifically usernames containing bidirectional text and compatibility forms). Operators are free to further restrict the allowed codepoints in usernames to avoid problematic characters.
Примечание: данная спецификация использует профиль OpaqueString вместо профиля UsernameCasePreserved для обработки строк имени пользователя, чтобы улучшить совместимость с развёрнутыми хранилищами паролей. Многие базы данных паролей, используемые для digest-аутентификации HTTP и SIP, хранят хеш MD5 от username:realm:password вместо хранения пароля в открытом виде. В [RFC3489] аутентификация STUN была разработана совместимой с этими существующими базами данных в максимально возможной степени; подобно SIP и HTTP, она не выполняла предварительной обработки имён пользователей и паролей, кроме запрета управляющих символов ASCII, не являющихся пробелами. Следующая редакция спецификации STUN, [RFC5389], использовала профиль stringprep [RFC3454] SASLprep [RFC4013] для предварительной обработки имён пользователей и паролей. SASLprep использует форму нормализации Unicode KC (совместимая декомпозиция с последующей канонической композицией) [UAX15] и запрещает различные управляющие, пробельные и нетекстовые, устаревшие или неподходящие кодовые точки. Инфраструктура PRECIS [RFC8264] заменяет stringprep. Обработка имён пользователей и паролей в PRECIS [RFC8265] использует форму нормализации Unicode C (каноническая декомпозиция с последующей канонической композицией). Хотя существуют отдельные случаи, когда разные строки имени пользователя в HTTP Digest могут отображаться в одно имя пользователя STUN, обработанное с помощью OpaqueString, эти случаи крайне маловероятны и легко обнаруживаются и исправляются. С профилем UsernameCasePreserved было бы более вероятно, что допустимые имена пользователя в HTTP Digest не совпадут со своими обработанными формами (в частности, имена пользователя, содержащие двунаправленный текст и формы совместимости). Операторы вправе дополнительно ограничивать допустимые кодовые точки в именах пользователя, чтобы избежать проблемных символов.

14.5. MESSAGE-INTEGRITY
14.5. MESSAGE-INTEGRITY
The MESSAGE-INTEGRITY attribute contains an HMAC-SHA1 [RFC2104] of the STUN message. The MESSAGE-INTEGRITY attribute can be present in any STUN message type. Since it uses the SHA-1 hash, the HMAC will be 20 bytes.
Атрибут MESSAGE-INTEGRITY содержит HMAC-SHA1 [RFC2104] сообщения STUN. Атрибут MESSAGE-INTEGRITY может присутствовать в сообщении STUN любого типа. Поскольку используется хеш SHA-1, HMAC будет иметь длину 20 байт.
The key for the HMAC depends on which credential mechanism is in use. Section 9.1.1 defines the key for the short-term credential mechanism, and Section 9.2.2 defines the key for the long-term credential mechanism. Other credential mechanisms MUST define the key that is used for the HMAC.
Ключ для HMAC зависит от используемого механизма учетных данных. Раздел 9.1.1 определяет ключ для механизма краткосрочных учетных данных, а раздел 9.2.2 определяет ключ для механизма долгосрочных учетных данных. Другие механизмы учетных данных ДОЛЖНЫ определять ключ, используемый для HMAC.
The text used as input to HMAC is the STUN message, up to and including the attribute preceding the MESSAGE-INTEGRITY attribute. The Length field of the STUN message header is adjusted to point to the end of the MESSAGE-INTEGRITY attribute. The value of the MESSAGE-INTEGRITY attribute is set to a dummy value.
Текст, используемый в качестве входа для HMAC, — это сообщение STUN до атрибута, предшествующего атрибуту MESSAGE-INTEGRITY, включительно. Поле Length заголовка сообщения STUN корректируется так, чтобы указывать на конец атрибута MESSAGE-INTEGRITY. Значение атрибута MESSAGE-INTEGRITY устанавливается в фиктивное значение.
Once the computation is performed, the value of the MESSAGE-INTEGRITY attribute is filled in, and the value of the length in the STUN header is set to its correct value -- the length of the entire message. Similarly, when validating the MESSAGE-INTEGRITY, the Length field in the STUN header must be adjusted to point to the end of the MESSAGE-INTEGRITY attribute prior to calculating the HMAC over the STUN message, up to and including the attribute preceding the MESSAGE-INTEGRITY attribute. Such adjustment is necessary when attributes, such as FINGERPRINT and MESSAGE-INTEGRITY-SHA256, appear after MESSAGE-INTEGRITY. See also [RFC5769] for examples of such calculations.
После выполнения вычисления значение атрибута MESSAGE-INTEGRITY заполняется, а значение длины в заголовке STUN устанавливается в правильное значение — длину всего сообщения. Аналогично, при проверке MESSAGE-INTEGRITY поле Length в заголовке STUN должно быть скорректировано так, чтобы указывать на конец атрибута MESSAGE-INTEGRITY, перед вычислением HMAC по сообщению STUN до атрибута, предшествующего MESSAGE-INTEGRITY, включительно. Такая корректировка необходима, когда атрибуты, такие как FINGERPRINT и MESSAGE-INTEGRITY-SHA256, появляются после MESSAGE-INTEGRITY. См. также [RFC5769] для примеров таких вычислений.

Поле Length заголовка сообщения STUN корректируется так, чтобы указывать на конец атрибута MESSAGE-INTEGRITY-SHA256. Значение атрибута MESSAGE-INTEGRITY-SHA256 устанавливается в фиктивное значение.

14.7. FINGERPRINT
14.7. FINGERPRINT
The FINGERPRINT attribute MAY be present in all STUN messages.
Атрибут FINGERPRINT МОЖЕТ присутствовать во всех сообщениях STUN.
The value of the attribute is computed as the CRC-32 of the STUN message up to (but excluding) the FINGERPRINT attribute itself, XOR'ed with the 32-bit value 0x5354554e. (The XOR operation ensures that the FINGERPRINT test will not report a false positive on a packet containing a CRC-32 generated by an application protocol.) The 32-bit CRC is the one defined in ITU V.42 [ITU.V42.2002], which has a generator polynomial of x^32 + x^26 + x^23 + x^22 + x^16 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1. See the sample code for the CRC-32 in Section 8 of [RFC1952].
Значение атрибута вычисляется как CRC-32 сообщения STUN до (но исключая) самого атрибута FINGERPRINT, XOR-ированный с 32-битным значением 0x5354554e. (Операция XOR гарантирует, что проверка FINGERPRINT не даст ложноположительного результата на пакете, содержащем CRC-32, сгенерированный прикладным протоколом.) 32-битный CRC — это тот, который определён в ITU V.42 [ITU.V42.2002], с порождающим полиномом x^32 + x^26 + x^23 + x^22 + x^16 + x^12 + x^11 + x^10 + x^8 + x^7 + x^5 + x^4 + x^2 + x + 1. См. пример кода для CRC-32 в разделе 8 [RFC1952].
When present, the FINGERPRINT attribute MUST be the last attribute in the message and thus will appear after MESSAGE-INTEGRITY and MESSAGE- INTEGRITY-SHA256.
Когда он присутствует, атрибут FINGERPRINT ДОЛЖЕН быть последним атрибутом в сообщении и, таким образом, будет появляться после MESSAGE-INTEGRITY и MESSAGE-INTEGRITY-SHA256.
The FINGERPRINT attribute can aid in distinguishing STUN packets from packets of other protocols. See Section 7.
Атрибут FINGERPRINT может помочь отличить пакеты STUN от пакетов других протоколов. См. раздел 7.
As with MESSAGE-INTEGRITY and MESSAGE-INTEGRITY-SHA256, the CRC used in the FINGERPRINT attribute covers the Length field from the STUN message header. Therefore, prior to computation of the CRC, this value must be correct and include the CRC attribute as part of the message length. When using the FINGERPRINT attribute in a message, the attribute is first placed into the message with a dummy value; then, the CRC is computed, and the value of the attribute is updated. If the MESSAGE-INTEGRITY or MESSAGE-INTEGRITY-SHA256 attribute is also present, then it must be present with the correct message- integrity value before the CRC is computed, since the CRC is done over the value of the MESSAGE-INTEGRITY and MESSAGE-INTEGRITY-SHA256 attributes as well.

14.9. REALM
The REALM attribute may be present in requests and responses. It contains text that meets the grammar for "realm-value" as described in [RFC3261] but without the double quotes and their surrounding whitespace. Атрибут REALM может присутствовать в запросах и ответах. Он содержит текст, соответствующий грамматике «realm-value», как описано в [RFC3261], но без двойных кавычек и окружающих их пробелов. То есть это значение realm без кавычек (и, следовательно, последовательность qdtext или quoted-pair). Оно ДОЛЖНО быть последовательностью в кодировке UTF-8 [RFC3629] длиной менее 128 символов (которая может достигать 509 байт при их кодировании и 763 байт при их декодировании) и ДОЛЖНО быть обработано с использованием профиля OpaqueString [RFC8265].

Присутствие атрибута REALM в запросе указывает на то, что для аутентификации используются долгосрочные учетные данные. Присутствие в определённых ответах об ошибках указывает на то, что сервер хочет, чтобы клиент использовал долгосрочные учетные данные в этом realm для аутентификации.

16.1. Attacks against the Protocol
16.1. Атаки на протокол
16.1.1. Outside Attacks
16.1.1. Внешние атаки
An attacker can try to modify STUN messages in transit, in order to cause a failure in STUN operation. These attacks are detected for both requests and responses through the message-integrity mechanism, using either a short-term or long-term credential. Of course, once detected, the manipulated packets will be dropped, causing the STUN transaction to effectively fail. This attack is possible only by an on-path attacker.
Атакующий может попытаться изменить сообщения STUN при передаче, чтобы вызвать сбой в работе STUN. Эти атаки обнаруживаются как для запросов, так и для ответов с помощью механизма целостности сообщений, использующего краткосрочные или долгосрочные учетные данные. Разумеется, после обнаружения изменённые пакеты будут отброшены, что фактически приведёт к неудаче транзакции STUN. Эта атака возможна только со стороны атакующего, находящегося на пути.
An attacker that can observe, but not modify, STUN messages in- transit (for example, an attacker present on a shared access medium, such as Wi-Fi) can see a STUN request and then immediately send a STUN response, typically an error response, in order to disrupt STUN processing. This attack is also prevented for messages that utilize MESSAGE-INTEGRITY. However, some error responses, those related to authentication in particular, cannot be protected by MESSAGE- INTEGRITY. When STUN itself is run over a secure transport protocol (e.g., TLS), these attacks are completely mitigated.
Атакующий, который может наблюдать, но не изменять сообщения STUN при передаче (например, атакующий, присутствующий в общей среде доступа, такой как Wi-Fi), может увидеть запрос STUN и затем немедленно отправить ответ STUN, обычно ответ об ошибке, чтобы нарушить обработку STUN. Эта атака также предотвращается для сообщений, использующих MESSAGE-INTEGRITY. Однако некоторые ответы об ошибках, в частности связанные с аутентификацией, не могут быть защищены с помощью MESSAGE-INTEGRITY. Когда сам STUN работает через защищённый транспортный протокол (например, TLS), эти атаки полностью устраняются.
Depending on the STUN Usage, these attacks may be of minimal consequence and thus do not require message integrity to mitigate. For example, when STUN is used to a basic STUN server to discover a server reflexive candidate for usage with ICE, authentication and message integrity are not required since these attacks are detected during the connectivity check phase. The connectivity checks themselves, however, require protection for proper operation of ICE overall. As described in Section 13, STUN Usages describe when authentication and message integrity are needed. Since STUN uses the HMAC of a shared secret for authentication and integrity protection, it is subject to offline dictionary attacks. When authentication is utilized, it SHOULD be with a strong password that is not readily subject to offline dictionary attacks. Protection of the channel itself, using TLS or DTLS, mitigates these attacks.
В зависимости от применения STUN эти атаки могут иметь минимальные последствия и, следовательно, не требовать целостности сообщений для смягчения. Например, когда STUN используется с базовым сервером STUN для обнаружения рефлексивного кандидата сервера для использования с ICE, аутентификация и целостность сообщений не требуются, поскольку эти атаки обнаруживаются на этапе проверки связности. Однако сами проверки связности требуют защиты для надлежащей работы ICE в целом. Как описано в разделе 13, применения STUN описывают, когда необходимы аутентификация и целостность сообщений. Поскольку STUN использует HMAC общего секрета для аутентификации и защиты целостности, он подвержен офлайн-атакам по словарю. Когда используется аутентификация, она ДОЛЖНА использовать надёжный пароль, который нелегко подвергнуть офлайн-атаке по словарю. Защита самого канала с помощью TLS или DTLS смягчает эти атаки.
STUN supports both MESSAGE-INTEGRITY and MESSAGE-INTEGRITY-SHA256, which makes STUN subject to bid-down attacks by an on-path attacker. An attacker could strip the MESSAGE-INTEGRITY-SHA256 attribute, leaving only the MESSAGE-INTEGRITY attribute and thus exploiting a potential vulnerability. Protection of the channel itself, using TLS or DTLS, mitigates these attacks. Timely removal of the support of MESSAGE-INTEGRITY in a future version of STUN is necessary.
STUN поддерживает как MESSAGE-INTEGRITY, так и MESSAGE-INTEGRITY-SHA256, что делает STUN подверженным атакам понижения со стороны атакующего на пути. Атакующий мог бы удалить атрибут MESSAGE-INTEGRITY-SHA256, оставив только атрибут MESSAGE-INTEGRITY и, таким образом, используя потенциальную уязвимость. Защита самого канала с помощью TLS или DTLS смягчает эти атаки. Своевременное прекращение поддержки MESSAGE-INTEGRITY в будущей версии STUN необходимо.
Note: The use of SHA-256 for password hashing does not meet modern standards, which are aimed at slowing down exhaustive password searches by providing a relatively slow minimum time to compute the hash. Although better algorithms such as Argon2 [Argon2] are available, SHA-256 was chosen for consistency with [RFC7616].
Примечание: использование SHA-256 для хеширования паролей не соответствует современным стандартам, которые направлены на замедление полного перебора паролей путём обеспечения относительно медленного минимального времени вычисления хеша. Хотя доступны лучшие алгоритмы, такие как Argon2 [Argon2], SHA-256 был выбран для согласованности с [RFC7616].
16.1.2. Inside Attacks
16.1.2. Внутренние атаки
A rogue client may try to launch a DoS attack against a server by sending it a large number of STUN requests. Fortunately, STUN requests can be processed statelessly by a server, making such attacks hard to launch effectively.
Недобросовестный клиент может попытаться запустить DoS-атаку на сервер, отправив ему большое количество запросов STUN. К счастью, запросы STUN могут обрабатываться сервером без сохранения состояния, что делает такие атаки трудноосуществимыми на практике.
A rogue client may use a STUN server as a reflector, sending it requests with a falsified source IP address and port. In such a case, the response would be delivered to that source IP and port. There is no amplification of the number of packets with this attack (the STUN server sends one packet for each packet sent by the client), though there is a small increase in the amount of data, since STUN responses are typically larger than requests. This attack is mitigated by ingress source address filtering.
Недобросовестный клиент может использовать сервер STUN в качестве отражателя, отправляя ему запросы с фальсифицированным исходным IP-адресом и портом. В таком случае ответ будет доставлен на этот исходный IP-адрес и порт. При этой атаке не происходит усиления количества пакетов (сервер STUN отправляет один пакет на каждый пакет, отправленный клиентом), хотя есть небольшое увеличение объёма данных, поскольку ответы STUN обычно больше запросов. Эта атака смягчается фильтрацией исходных адресов на входе.
Revealing the specific software version of the agent through the SOFTWARE attribute might allow them to become more vulnerable to attacks against software that is known to contain security holes. Implementers SHOULD make usage of the SOFTWARE attribute a configurable option.
Раскрытие конкретной версии программного обеспечения агента через атрибут SOFTWARE может сделать его более уязвимым к атакам на программное обеспечение, которое, как известно, содержит уязвимости безопасности. Реализаторам СЛЕДУЕТ делать использование атрибута SOFTWARE настраиваемым параметром.
16.1.3. Bid-Down Attacks
16.1.3. Атаки понижения
This document adds the possibility of selecting different algorithms to protect the confidentiality of the passwords stored on the server side when using the long-term credential mechanism while still ensuring compatibility with MD5, which was the algorithm used in [RFC5389]. This selection works by having the server send to the client the list of algorithms supported in a PASSWORD-ALGORITHMS attribute and having the client send back a PASSWORD-ALGORITHM attribute containing the algorithm selected.
Настоящий документ добавляет возможность выбора различных алгоритмов для защиты конфиденциальности паролей, хранящихся на стороне сервера, при использовании механизма долгосрочных учетных данных, сохраняя при этом совместимость с MD5, который был алгоритмом, использованным в [RFC5389]. Этот выбор работает за счёт того, что сервер отправляет клиенту список поддерживаемых алгоритмов в атрибуте PASSWORD-ALGORITHMS, а клиент отправляет обратно атрибут PASSWORD-ALGORITHM, содержащий выбранный алгоритм.
Because the PASSWORD-ALGORITHMS attribute has to be sent in an unauthenticated response, an on-path attacker wanting to exploit an eventual vulnerability in MD5 can just strip the PASSWORD-ALGORITHMS attribute from the unprotected response, thus making the server subsequently act as if the client was implementing the version of this protocol defined in [RFC5389].
Поскольку атрибут PASSWORD-ALGORITHMS должен отправляться в неаутентифицированном ответе, атакующий на пути, желающий использовать возможную уязвимость в MD5, может просто удалить атрибут PASSWORD-ALGORITHMS из незащищённого ответа, заставив сервер впоследствии действовать так, как если бы клиент реализовывал версию этого протокола, определённую в [RFC5389].
To protect against this attack and other similar bid-down attacks, the nonce is enriched with a set of security bits that indicates which security features are in use. In the case of the selection of the password algorithm, the matching bit is set in the nonce returned by the server in the same response that contains the PASSWORD- ALGORITHMS attribute. Because the nonce used in subsequent authenticated transactions is verified by the server to be identical to what was originally sent, it cannot be modified by an on-path attacker. Additionally, the client is mandated to copy the received PASSWORD-ALGORITHMS attribute in the next authenticated transaction to that server.
Чтобы защититься от этой атаки и других подобных атак понижения, nonce обогащается набором битов безопасности, указывающих, какие функции безопасности используются. В случае выбора алгоритма пароля соответствующий бит устанавливается в nonce, возвращаемом сервером в том же ответе, который содержит атрибут PASSWORD-ALGORITHMS. Поскольку nonce, используемый в последующих аутентифицированных транзакциях, проверяется сервером на идентичность первоначально отправленному, он не может быть изменён атакующим на пути. Кроме того, клиент обязан копировать полученный атрибут PASSWORD-ALGORITHMS в следующую аутентифицированную транзакцию к этому серверу.
An on-path attack that removes the PASSWORD-ALGORITHMS will be detected because the client will not be able to send it back to the server in the next authenticated transaction. The client will detect that attack because the security bit is set but the matching attribute is missing; this will end the session. A client using an older version of this protocol will not send the PASSWORD-ALGORITHMS back but can only use MD5 anyway, so the attack is inconsequential.
Атака на пути, удаляющая PASSWORD-ALGORITHMS, будет обнаружена, поскольку клиент не сможет отправить его обратно серверу в следующей аутентифицированной транзакции. Клиент обнаружит эту атаку, поскольку бит безопасности установлен, но соответствующий атрибут отсутствует; это завершит сеанс. Клиент, использующий более старую версию этого протокола, не отправит PASSWORD-ALGORITHMS обратно, но в любом случае сможет использовать только MD5, поэтому атака не имеет последствий.
The on-path attack may also try to remove the security bit together with the PASSWORD-ALGORITHMS attribute, but the server will discover that when the next authenticated transaction contains an invalid nonce.
Атака на пути может также попытаться удалить бит безопасности вместе с атрибутом PASSWORD-ALGORITHMS, но сервер обнаружит это, когда следующая аутентифицированная транзакция будет содержать недействительный nonce.
An on-path attack that removes some algorithms from the PASSWORD- ALGORITHMS attribute will be equally defeated because that attribute will be different from the original one when the server verifies it in the subsequent authenticated transaction.
Атака на пути, удаляющая некоторые алгоритмы из атрибута PASSWORD-ALGORITHMS, будет равным образом побеждена, поскольку этот атрибут будет отличаться от исходного, когда сервер проверит его в последующей аутентифицированной транзакции.
Note that the bid-down protection mechanism introduced in this document is inherently limited by the fact that it is not possible to detect an attack until the server receives the second request after the 401 (Unauthenticated) response. SHA-256 was chosen as the new default for password hashing for its compatibility with [RFC7616], but because SHA-256 (like MD5) is a comparatively fast algorithm, it does little to deter brute-force attacks. Specifically, this means that if the user has a weak password, an attacker that captures a single exchange can use a brute-force attack to learn the user's password and then potentially impersonate the user to the server and to other servers where the same password was used. Note that such an attacker can impersonate the user to the server itself without any brute-force attack.
Обратите внимание, что механизм защиты от понижения, введённый в настоящем документе, по своей сути ограничен тем, что невозможно обнаружить атаку, пока сервер не получит второй запрос после ответа 401 (Unauthenticated). SHA-256 был выбран новым по умолчанию для хеширования паролей из-за совместимости с [RFC7616], но поскольку SHA-256 (как и MD5) является сравнительно быстрым алгоритмом, он мало что делает для сдерживания атак методом перебора. В частности, это означает, что если у пользователя слабый пароль, атакующий, перехвативший один обмен, может использовать атаку методом перебора, чтобы узнать пароль пользователя, а затем потенциально выдать себя за пользователя перед сервером и перед другими серверами, где использовался тот же пароль. Обратите внимание, что такой атакующий может выдать себя за пользователя перед самим сервером без какой-либо атаки методом перебора.
A stronger (which is to say, slower) algorithm, like Argon2 [Argon2], would help both of these cases; however, in the first case, it would only help after the database entry for this user is updated to exclusively use that stronger mechanism.
Более сильный (то есть более медленный) алгоритм, такой как Argon2 [Argon2], помог бы в обоих этих случаях; однако в первом случае он помог бы только после того, как запись базы данных для этого пользователя будет обновлена для исключительного использования этого более сильного механизма.
The bid-down defenses in this protocol prevent an attacker from forcing the client and server to complete a handshake using weaker algorithms than they jointly support, but only if the weakest joint algorithm is strong enough that it cannot be compromised by a brute- force attack. However, this does not defend against many attacks on those algorithms; specifically, an on-path attacker might perform a bid-down attack on a client that supports both Argon2 [Argon2] and SHA-256 for password hashing and use that to collect a MESSAGE- INTEGRITY-SHA256 value that it can then use for an offline brute- force attack. This would be detected when the server receives the second request, but that does not prevent the attacker from obtaining the MESSAGE-INTEGRITY-SHA256 value.
Механизмы защиты от понижения в этом протоколе не позволяют атакующему заставить клиента и сервер завершить рукопожатие с использованием более слабых алгоритмов, чем они совместно поддерживают, но только если самый слабый общий алгоритм достаточно силён, чтобы его нельзя было скомпрометировать атакой методом перебора. Однако это не защищает от многих атак на эти алгоритмы; в частности, атакующий на пути может выполнить атаку понижения на клиента, поддерживающего как Argon2 [Argon2], так и SHA-256 для хеширования паролей, и использовать это, чтобы собрать значение MESSAGE-INTEGRITY-SHA256, которое он затем сможет использовать для офлайн-атаки методом перебора. Это было бы обнаружено, когда сервер получит второй запрос, но это не мешает атакующему получить значение MESSAGE-INTEGRITY-SHA256.
Similarly, an attack against the USERHASH mechanism will not succeed in establishing a session as the server will detect that the feature was discarded on path, but the client would still have been convinced to send its username in the clear in the USERNAME attribute, thus disclosing it to the attacker.
Аналогично, атака на механизм USERHASH не сможет установить сеанс, поскольку сервер обнаружит, что функция была отброшена на пути, но клиент всё равно был бы убеждён отправить своё имя пользователя в открытом виде в атрибуте USERNAME, тем самым раскрыв его атакующему.
Finally, when the bid-down protection mechanism is employed for a future upgrade of the HMAC algorithm used to protect messages, it will offer only a limited protection if the current HMAC algorithm is already compromised.
Наконец, когда механизм защиты от понижения применяется для будущего обновления алгоритма HMAC, используемого для защиты сообщений, он обеспечит лишь ограниченную защиту, если текущий алгоритм HMAC уже скомпрометирован.
16.2. Attacks Affecting the Usage
16.2. Атаки, влияющие на применение
This section lists attacks that might be launched against a usage of STUN. Each STUN Usage must consider whether these attacks are applicable to it and, if so, discuss countermeasures.
В этом разделе перечислены атаки, которые могут быть предприняты против применения STUN. Каждое применение STUN должно рассмотреть, применимы ли к нему эти атаки и, если да, обсудить контрмеры.
Most of the attacks in this section revolve around an attacker modifying the reflexive address learned by a STUN client through a Binding request/response transaction. Since the usage of the reflexive address is a function of the usage, the applicability and remediation of these attacks are usage-specific. In common situations, modification of the reflexive address by an on-path attacker is easy to do. Consider, for example, the common situation where STUN is run directly over UDP. In this case, an on-path attacker can modify the source IP address of the Binding request before it arrives at the STUN server. The STUN server will then return this IP address in the XOR-MAPPED-ADDRESS attribute to the client and send the response back to that (falsified) IP address and port. If the attacker can also intercept this response, it can direct it back towards the client. Protecting against this attack by using a message-integrity check is impossible, since a message- integrity value cannot cover the source IP address and the intervening NAT must be able to modify this value. Instead, one solution to prevent the attacks listed below is for the client to verify the reflexive address learned, as is done in ICE [RFC8445].
Большинство атак в этом разделе вращаются вокруг изменения атакующим рефлексивного адреса, узнанного клиентом STUN через транзакцию запрос/ответ Binding. Поскольку использование рефлексивного адреса является функцией применения, применимость и устранение этих атак зависят от применения. В обычных ситуациях изменение рефлексивного адреса атакующим на пути легко осуществимо. Рассмотрим, например, обычную ситуацию, когда STUN работает непосредственно через UDP. В этом случае атакующий на пути может изменить исходный IP-адрес запроса Binding до того, как он достигнет сервера STUN. Сервер STUN затем вернёт этот IP-адрес в атрибуте XOR-MAPPED-ADDRESS клиенту и отправит ответ обратно на этот (фальсифицированный) IP-адрес и порт. Если атакующий также может перехватить этот ответ, он может направить его обратно клиенту. Защита от этой атаки с помощью проверки целостности сообщения невозможна, поскольку значение целостности сообщения не может охватывать исходный IP-адрес, а промежуточный NAT должен иметь возможность изменять это значение. Вместо этого одним из решений для предотвращения перечисленных ниже атак является проверка клиентом узнанного рефлексивного адреса, как это делается в ICE [RFC8445].
Other usages may use other means to prevent these attacks.
Другие применения могут использовать иные средства для предотвращения этих атак.
16.2.1. Attack I: Distributed DoS (DDoS) against a Target
16.2.1. Атака I: распределённый отказ в обслуживании (DDoS) против цели
In this attack, the attacker provides one or more clients with the same faked reflexive address that points to the intended target. This will trick the STUN clients into thinking that their reflexive addresses are equal to that of the target. If the clients hand out that reflexive address in order to receive traffic on it (for example, in SIP messages), the traffic will instead be sent to the target. This attack can provide substantial amplification, especially when used with clients that are using STUN to enable multimedia applications. However, it can only be launched against targets for which packets from the STUN server to the target pass through the attacker, limiting the cases in which it is possible.
В этой атаке атакующий предоставляет одному или нескольким клиентам один и тот же поддельный рефлексивный адрес, указывающий на намеченную цель. Это заставит клиентов STUN думать, что их рефлексивные адреса равны адресу цели. Если клиенты передают этот рефлексивный адрес, чтобы получать на него трафик (например, в сообщениях SIP), трафик вместо этого будет отправлен цели. Эта атака может обеспечить существенное усиление, особенно при использовании с клиентами, которые применяют STUN для поддержки мультимедийных приложений. Однако она может быть запущена только против целей, для которых пакеты от сервера STUN к цели проходят через атакующего, что ограничивает случаи, в которых она возможна.
16.2.2. Attack II: Silencing a Client
16.2.2. Атака II: Заглушение клиента
In this attack, the attacker provides a STUN client with a faked reflexive address. The reflexive address it provides is a transport address that routes to nowhere. As a result, the client won't receive any of the packets it expects to receive when it hands out the reflexive address. This exploitation is not very interesting for the attacker. It impacts a single client, which is frequently not the desired target. Moreover, any attacker that can mount the attack could also deny service to the client by other means, such as preventing the client from receiving any response from the STUN server, or even a DHCP server. As with the attack described in Section 16.2.1, this attack is only possible when the attacker is on path for packets sent from the STUN server towards this unused IP address.
В этой атаке атакующий предоставляет клиенту STUN поддельный рефлексивный адрес. Предоставляемый им рефлексивный адрес — это транспортный адрес, ведущий в никуда. В результате клиент не получит ни одного из пакетов, которые он ожидает получить, когда передаёт рефлексивный адрес. Эта эксплуатация не очень интересна для атакующего. Она затрагивает одного клиента, который часто не является желаемой целью. Более того, любой атакующий, способный осуществить эту атаку, мог бы также отказать клиенту в обслуживании другими способами, например, не давая клиенту получить какой-либо ответ от сервера STUN или даже от сервера DHCP. Как и в случае атаки, описанной в разделе 16.2.1, эта атака возможна только тогда, когда атакующий находится на пути пакетов, отправляемых от сервера STUN к этому неиспользуемому IP-адресу.
16.2.3. Attack III: Assuming the Identity of a Client
16.2.3. Атака III: Присвоение идентичности клиента
This attack is similar to attack II. However, the faked reflexive address points to the attacker itself. This allows the attacker to receive traffic that was destined for the client.
Эта атака аналогична атаке II. Однако поддельный рефлексивный адрес указывает на самого атакующего. Это позволяет атакующему получать трафик, предназначенный клиенту.
16.2.4. Attack IV: Eavesdropping
16.2.4. Атака IV: Прослушивание
In this attack, the attacker forces the client to use a reflexive address that routes to itself. It then forwards any packets it receives to the client. This attack allows the attacker to observe all packets sent to the client. However, in order to launch the attack, the attacker must have already been able to observe packets from the client to the STUN server. In most cases (such as when the attack is launched from an access network), this means that the attacker could already observe packets sent to the client. This attack is, as a result, only useful for observing traffic by attackers on the path from the client to the STUN server, but not generally on the path of packets being routed towards the client.
В этой атаке атакующий заставляет клиента использовать рефлексивный адрес, ведущий к самому атакующему. Затем он пересылает все полученные пакеты клиенту. Эта атака позволяет атакующему наблюдать все пакеты, отправляемые клиенту. Однако для запуска атаки атакующий уже должен был иметь возможность наблюдать пакеты от клиента к серверу STUN. В большинстве случаев (например, когда атака запускается из сети доступа) это означает, что атакующий уже мог наблюдать пакеты, отправляемые клиенту. В результате эта атака полезна только для наблюдения за трафиком атакующими на пути от клиента к серверу STUN, но обычно не на пути пакетов, маршрутизируемых к клиенту.
Note that this attack can be trivially launched by the STUN server itself, so users of STUN servers should have the same level of trust in the users of STUN servers as any other node that can insert itself into the communication flow.
Обратите внимание, что эта атака может быть тривиально запущена самим сервером STUN, поэтому пользователи серверов STUN должны доверять пользователям серверов STUN в той же степени, что и любому другому узлу, способному вклиниться в поток связи.
16.3. Hash Agility Plan
16.3. План гибкости хешей
This specification uses HMAC-SHA256 for computation of the message integrity, sometimes in combination with HMAC-SHA1. If, at a later time, HMAC-SHA256 is found to be compromised, the following remedy should be applied:
Данная спецификация использует HMAC-SHA256 для вычисления целостности сообщения, иногда в сочетании с HMAC-SHA1. Если впоследствии будет обнаружено, что HMAC-SHA256 скомпрометирован, следует применить следующее средство:
o Both a new message-integrity attribute and a new STUN Security Feature bit will be allocated in a Standards Track document. The new message-integrity attribute will have its value computed using a new hash. The STUN Security Feature bit will be used to simultaneously 1) signal to a STUN client using the long-term credential mechanism that this server supports this new hash algorithm and 2) prevent bid-down attacks on the new message- integrity attribute.
o В документе уровня стандартов будут выделены как новый атрибут целостности сообщения, так и новый бит функции безопасности STUN. Значение нового атрибута целостности сообщения будет вычисляться с использованием нового хеша. Бит функции безопасности STUN будет использоваться для одновременного 1) сигнализирования клиенту STUN, использующему механизм долгосрочных учетных данных, что этот сервер поддерживает этот новый алгоритм хеширования, и 2) предотвращения атак понижения на новый атрибут целостности сообщения.
o STUN clients and servers using the short-term credential mechanism will need to update the external mechanism that they use to signal what message-integrity attributes are in use.
o Клиентам и серверам STUN, использующим механизм краткосрочных учетных данных, потребуется обновить внешний механизм, который они используют для сигнализации о том, какие атрибуты целостности сообщения используются.
The bid-down protection mechanism described in this document is new and thus cannot currently protect against a bid-down attack that lowers the strength of the hash algorithm to HMAC-SHA1. This is why, after a transition period, a new document updating this one will assign a new STUN Security Feature bit for deprecating HMAC-SHA1. When used, this bit will signal that HMAC-SHA1 is deprecated and should no longer be used.
Механизм защиты от понижения, описанный в настоящем документе, является новым и поэтому в настоящее время не может защитить от атаки понижения, снижающей силу алгоритма хеширования до HMAC-SHA1. Именно поэтому после переходного периода новый документ, обновляющий этот, назначит новый бит функции безопасности STUN для объявления HMAC-SHA1 устаревшим. При использовании этот бит будет сигнализировать, что HMAC-SHA1 устарел и больше не должен использоваться.
Similarly, if HMAC-SHA256 is found to be compromised, a new userhash attribute and a new STUN Security Feature bit will be allocated in a Standards Track document. The new userhash attribute will have its value computed using a new hash. The STUN Security Feature bit will be used to simultaneously 1) signal to a STUN client using the long- term credential mechanism that this server supports this new hash algorithm for the userhash attribute and 2) prevent bid-down attacks on the new userhash attribute.
Аналогично, если будет обнаружено, что HMAC-SHA256 скомпрометирован, в документе уровня стандартов будут выделены новый атрибут userhash и новый бит функции безопасности STUN. Значение нового атрибута userhash будет вычисляться с использованием нового хеша. Бит функции безопасности STUN будет использоваться для одновременного 1) сигнализирования клиенту STUN, использующему механизм долгосрочных учетных данных, что этот сервер поддерживает этот новый алгоритм хеширования для атрибута userhash, и 2) предотвращения атак понижения на новый атрибут userhash.
17. IAB Considerations
17. Соображения IAB
The IAB has studied the problem of Unilateral Self-Address Fixing (UNSAF), which is the general process by which a client attempts to determine its address in another realm on the other side of a NAT through a collaborative protocol reflection mechanism [RFC3424]. STUN can be used to perform this function using a Binding request/ response transaction if one agent is behind a NAT and the other is on the public side of the NAT.
IAB изучил проблему Unilateral Self-Address Fixing (UNSAF) — общий процесс, с помощью которого клиент пытается определить свой адрес в другом домене по другую сторону NAT через механизм совместного отражения протокола [RFC3424]. STUN может использоваться для выполнения этой функции с помощью транзакции запрос/ответ Binding, если один агент находится за NAT, а другой — на публичной стороне NAT.
The IAB has suggested that protocols developed for this purpose document a specific set of considerations. Because some STUN Usages provide UNSAF functions (such as ICE [RFC8445]) and others do not (such as SIP Outbound [RFC5626]), answers to these considerations need to be addressed by the usages themselves.
IAB предложил, чтобы протоколы, разработанные для этой цели, документировали конкретный набор соображений. Поскольку некоторые применения STUN обеспечивают функции UNSAF (такие как ICE [RFC8445]), а другие нет (такие как SIP Outbound [RFC5626]), ответы на эти соображения должны быть даны самими применениями.
