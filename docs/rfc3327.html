Abstract
Аннотация
The REGISTER function is used in a Session Initiation Protocol (SIP) system primarily to associate a temporary contact address with an address-of-record. This contact is generally in the form of a Uniform Resource Identifier (URI), such as Contact: <sip:alice@pc33.atlanta.com> and is generally dynamic and associated with the IP address or hostname of the SIP User Agent (UA). The problem is that network topology may have one or more SIP proxies between the UA and the registrar, such that any request traveling from the user's home network to the registered UA must traverse these proxies. The REGISTER method does not give us a mechanism to discover and record this sequence of proxies in the registrar for future use. This document defines an extension header field, "Path" which provides such a mechanism.
Функция REGISTER используется в системе протокола инициирования сессий (SIP) главным образом для связывания временного контактного адреса с адресом записи. Этот контакт обычно имеет форму универсального идентификатора ресурса (URI), например Contact: <sip:alice@pc33.atlanta.com>, и обычно является динамическим и связан с IP-адресом или именем хоста пользовательского агента SIP (UA). Проблема состоит в том, что сетевая топология может иметь один или несколько SIP-прокси между UA и регистратором, так что любой запрос, идущий из домашней сети пользователя к зарегистрированному UA, должен проходить через эти прокси. Метод REGISTER не даёт нам механизма для обнаружения и записи этой последовательности прокси в регистраторе для будущего использования. Настоящий документ определяет поле расширенного заголовка «Path», которое предоставляет такой механизм.
1. Background
1. Предпосылки
3GPP established a requirement for discovering intermediate proxies during SIP registration and published this requirement in [5].
3GPP установила требование обнаружения промежуточных прокси во время регистрации SIP и опубликовала это требование в [5].
Scenario:
Сценарий:
UA1----P1-----P2-----P3------REGISTRAR
UA1----P1-----P2-----P3------РЕГИСТРАТОР
UA1 wishes to register with REGISTRAR. However, due to network topology, UA1 must use P1 as an "outbound proxy", and all requests between UA1 and REGISTRAR must also traverse P1, P2, and P3 before reaching REGISTRAR. Likewise, all requests between REGISTRAR and UA1 must also traverse P3, P2, and P1 before reaching UA1.
UA1 желает зарегистрироваться у РЕГИСТРАТОРА. Однако из-за сетевой топологии UA1 должен использовать P1 как «исходящий прокси», и все запросы между UA1 и РЕГИСТРАТОРОМ также должны проходить через P1, P2 и P3 до достижения РЕГИСТРАТОРА. Аналогично все запросы между РЕГИСТРАТОРОМ и UA1 также должны проходить через P3, P2 и P1 до достижения UA1.
UA1 has a standing relationship with REGISTRAR. How UA1 establishes this relationship is outside the scope of this document. UA1 discovers P1 as a result of configuration, DHCP assignment or other similar operation, also outside the scope of this document. REGISTRAR has a similar "default outbound proxy" relationship with P3. Eventually, REGISTRAR or a "home proxy" (a proxy serving as the terminal point for routing an address-of-record) closely related to it will receive a request destined for UA1. It needs to know which proxies must be transited by that request in order to get back to UA1. In some cases, this information may be deducible from SIP routing configuration tables or from DNS entries. In other cases, such as that raised by 3GPP, the information is not readily available outside of the SIP REGISTER transaction.
UA1 имеет постоянные отношения с РЕГИСТРАТОРОМ. То, как UA1 устанавливает эти отношения, выходит за рамки настоящего документа. UA1 обнаруживает P1 в результате конфигурации, назначения DHCP или подобной операции, что также выходит за рамки настоящего документа. РЕГИСТРАТОР имеет аналогичные отношения «исходящего прокси по умолчанию» с P3. В конечном итоге РЕГИСТРАТОР или тесно связанный с ним «домашний прокси» (прокси, служащий конечной точкой для маршрутизации адреса записи) получит запрос, предназначенный для UA1. Ему нужно знать, через какие прокси должен пройти этот запрос, чтобы вернуться к UA1. В некоторых случаях эта информация может быть выведена из таблиц конфигурации маршрутизации SIP или из записей DNS. В других случаях, например в случае, поднятом 3GPP, информация не является легкодоступной вне транзакции SIP REGISTER.
The Path extension header field allows accumulating and transmitting the list of proxies between UA1 and REGISTRAR. Intermediate nodes such as P1 may statefully retain Path information if needed by operational policy. This mechanism is in many ways similar to the operation of Record-Route in dialog-initiating requests. The routing established by the Path header field mechanism applies only to requests transiting or originating in the home domain.
Поле расширенного заголовка Path позволяет накапливать и передавать список прокси между UA1 и РЕГИСТРАТОРОМ. Промежуточные узлы, такие как P1, могут с сохранением состояния хранить информацию Path, если это требуется операционной политикой. Этот механизм во многом подобен работе Record-Route в запросах, инициирующих диалог. Маршрутизация, установленная механизмом заголовка Path, применяется только к запросам, проходящим через домашний домен или исходящим из него.

3. Applicability Statement
3. Заявление о применимости
The Path mechanism is applicable whenever there are intermediate proxies between a SIP UA and a SIP Registrar used by that UA where the following conditions are true:
Механизм Path применим всякий раз, когда между SIP UA и используемым им SIP-регистратором есть промежуточные прокси, при соблюдении следующих условий:
1. One or more of the intermediate proxies are visited by registration requests from the UA to the Registrar.
1. Один или несколько промежуточных прокси посещаются запросами регистрации от UA к регистратору.
2. The same intermediate proxies or a set of proxies known to the intermediate proxies must be traversed, in reverse order, by requests sent through a home proxy to the UA. In the simplest form, the route between the home proxy and the UA is the exact inverse of the route between the UA and the route between the UA and the registrar.
Поле заголовка Path, при его наличии в запросе, содержит список URI, представляющих прокси, которые должны быть пройдены при будущих запросах, отправляемых UA, когда сама регистрация была отправлена через эти прокси. Значения URI в поле заголовка Path копируются в поле заголовка Route в новых запросах, отправляемых UA в рамках диалога, созданного регистрацией. Одним из следствий этого является то, что значение Path должно быть подходящим для использования в качестве URI в поле заголовка Route.
3. The network topology is such that the intermediate proxies which must be visited are NOT implied by SIP routing tables, DNS, or similar mechanisms.
3. Сетевая топология такова, что промежуточные прокси, которые должны быть посещены, НЕ подразумеваются таблицами маршрутизации SIP, DNS или аналогичными механизмами.
4. Path Header Field Definition and Syntax
4. Определение и синтаксис поля заголовка Path
The Path header field is a SIP extension header field with syntax very similar to the Record-Route header field. It is used in conjunction with SIP REGISTER requests and with 200 class messages in response to REGISTER (REGISTER responses). A Path header field MAY be inserted into a REGISTER by any SIP node traversed by that request. Like the Route header field, sequential Path header fields are evaluated in the sequence in which they are present in the request, and Path header fields MAY be combined into compound Path header in a single Path header field. The registrar reflects the accumulated Path back into the REGISTER response, and intermediate nodes propagate this back toward the originating UA. The originating UA is therefore informed of the inclusion of nodes on its registered Path, and MAY use that information in other capacities outside the scope of this document.
Поле заголовка Path — это поле расширенного заголовка SIP с синтаксисом, очень похожим на поле заголовка Record-Route. Оно используется вместе с запросами SIP REGISTER и с сообщениями класса 200 в ответ на REGISTER (ответами на REGISTER). Поле заголовка Path МОЖЕТ быть вставлено в REGISTER любым узлом SIP, через который проходит этот запрос. Как и поле заголовка Route, последовательные поля заголовка Path обрабатываются в той последовательности, в которой они присутствуют в запросе, и поля заголовка Path МОГУТ быть объединены в составной заголовок Path в одном поле заголовка Path. Регистратор отражает накопленный Path обратно в ответ на REGISTER, и промежуточные узлы передают его обратно к исходному UA. Таким образом, исходный UA информируется о включении узлов в его зарегистрированный Path и МОЖЕТ использовать эту информацию в иных целях вне рамок настоящего документа.
The difference between Path and Record-Route is that Path applies to REGISTER and 200 class responses to REGISTER. Record-Route doesn't, and can't be defined in REGISTER for reasons of backward compatibility. Furthermore, the vector established by Record-Route applies only to requests within the dialog that established that Record-Route, whereas the vector established by Path applies to future dialogs.
Разница между Path и Record-Route состоит в том, что Path применяется к REGISTER и ответам класса 200 на REGISTER. Record-Route — нет, и не может быть определён в REGISTER по причинам обратной совместимости. Более того, вектор, установленный Record-Route, применяется только к запросам в пределах диалога, установившего этот Record-Route, тогда как вектор, установленный Path, применяется к будущим диалогам.
The syntax for Path is defined as follows:
Синтаксис Path определён следующим образом:
Path = "Path" HCOLON path-value *( COMMA path-value ) path-value = name-addr *( SEMI rr-param )
Path = «Path» HCOLON path-value *( COMMA path-value ) path-value = name-addr *( SEMI rr-param )
Note that the Path header field values conform to the syntax of a Route element as defined in [1]. As suggested therein, such values MUST include the loose-routing indicator parameter ";lr" for full compliance with [1].
Обратите внимание, что значения поля заголовка Path соответствуют синтаксису элемента Route, как определено в [1]. Как там предложено, такие значения ДОЛЖНЫ включать параметр индикатора свободной маршрутизации «;lr» для полного соответствия [1].
The allowable usage of header fields is described in Tables 2 and 3 of SIP [1]. The following additions to this table are needed for Path.
Допустимое использование полей заголовков описано в таблицах 2 и 3 SIP [1]. Для Path в эту таблицу необходимы следующие дополнения.
Support for the Path header field MAY be indicated by a UA by including the option-tag "path" in a Supported header field.
Поддержка поля заголовка Path МОЖЕТ быть указана UA путём включения тега опции «path» в поле заголовка Supported.
Addition of Path to SIP Table 3:
Дополнение Path к таблице 3 SIP:
Header field where proxy ACK BYE CAN INV OPT REG ___________________________________________________________ Path R ar - - - - - o Path 2xx - - - - - - o
Header field where proxy ACK BYE CAN INV OPT REG ___________________________________________________________ Path R ar - - - - - o Path 2xx - - - - - - o
5. Usage of Path Header Field
5. Использование поля заголовка Path
5.1. Procedures at the UA
5.1. Процедуры у UA
The UA executes its register operation as usual. The response MAY contain a Path header field. The general operation of the UA is to ignore the Path header field in the response. It MAY choose to display the contents of the Path header field to the user or take other action outside the scope of this document. The Path information in the REGISTER response lets the UA know what intermediate proxies were added during registration. Examination of this information may be important from a security perspective, as such inspection might allow the UA to detect intermediate proxies that have inappropriately added themselves.
UA выполняет свою операцию регистрации как обычно. Ответ МОЖЕТ содержать поле заголовка Path. Общая работа UA состоит в игнорировании поля заголовка Path в ответе. Он МОЖЕТ выбрать отображение содержимого поля заголовка Path пользователю или предпринять иные действия вне рамок настоящего документа. Информация Path в ответе на REGISTER позволяет UA узнать, какие промежуточные прокси были добавлены во время регистрации. Изучение этой информации может быть важным с точки зрения безопасности, поскольку такая проверка может позволить UA обнаружить промежуточные прокси, которые неподобающим образом добавили себя.
The UA SHOULD include the option tag "path" as a header field value in all Supported header fields, and SHOULD include a Supported header field in all requests.
UA СЛЕДУЕТ включать тег опции «path» как значение поля заголовка во все поля заголовка Supported и СЛЕДУЕТ включать поле заголовка Supported во все запросы.
The UA MAY include a Path header field in a request. This is not broadly applicable and caution must be taken to insure proper function, as the Path header field inserted by the UA may have additional Path header field values appended by intermediate proxies. Such proxies are not aware that the Path header field value was inserted by a UA, and will treat it as if it had been inserted by a previously traversed proxy, which could result in unexpected routing behavior wherein the UA is asked to act as a proxy.
UA МОЖЕТ включать поле заголовка Path в запрос. Это не является широко применимым, и нужно соблюдать осторожность, чтобы обеспечить правильную работу, поскольку к полю заголовка Path, вставленному UA, промежуточные прокси могут добавить дополнительные значения поля заголовка Path. Такие прокси не знают, что значение поля заголовка Path было вставлено UA, и будут обращаться с ним так, как если бы оно было вставлено ранее пройденным прокси, что может привести к неожиданному поведению маршрутизации, когда UA просят действовать как прокси.
5.2. Procedures at Intermediate Proxies
5.2. Процедуры на промежуточных прокси
When a proxy processing a REGISTER request wishes to be on the path for future requests toward the UA originating that REGISTER request, the proxy inserts a URI for that proxy as the topmost value in the Path header field (or inserts a new topmost Path header) before proxying that request. It is also possible for a proxy with specific knowledge of network topology to add a Path header field value referencing another node, thereby allowing construction of a Path which is discongruent with the route taken by the REGISTER request. Such a construction is implementation specific and outside the scope of this document.
Когда прокси, обрабатывающий запрос REGISTER, желает оказаться на пути для будущих запросов к UA, инициирующему этот запрос REGISTER, прокси вставляет URI для этого прокси как самое верхнее значение в поле заголовка Path (или вставляет новый самый верхний заголовок Path) перед проксированием этого запроса. Также возможно, чтобы прокси со специфическим знанием сетевой топологии добавил значение поля заголовка Path, ссылающееся на другой узел, тем самым позволяя построить Path, несовпадающий с маршрутом, пройденным запросом REGISTER. Такое построение зависит от реализации и выходит за рамки настоящего документа.
Intermediate proxies SHOULD NOT add a Path header field to a request unless the UA has indicated support for this extension with a Supported header field value. If the UA has indicated support and the proxy requires the registrar to support the Path extension, then the proxy SHOULD insert a Requires header field value for this extension. If the UA has not indicated support for the extension and the proxy requires support for it in the registrar, the proxy SHOULD reject the request with a 421 response indicating a requirement for the extension.
Промежуточным прокси НЕ СЛЕДУЕТ добавлять поле заголовка Path к запросу, если только UA не указал поддержку этого расширения значением поля заголовка Supported. Если UA указал поддержку и прокси требует, чтобы регистратор поддерживал расширение Path, прокси СЛЕДУЕТ вставить значение поля заголовка Requires для этого расширения. Если UA не указал поддержку расширения, а прокси требует её поддержки в регистраторе, прокси СЛЕДУЕТ отклонить запрос ответом 421, указывающим на требование расширения.
Proxies processing a REGISTER response SHOULD NOT alter any Path header field values that may be present in the response. The registrar MAY protect the Path header field in the response by including it in a protected S/MIME body, and alterations of the Path by an intermediate proxy can therefore be detected by the UA as man- in-the-middle attacks. Proxies SHOULD only consider altering the value of a Path header field in the REGISTER response if they have the credentials to correctly alter the S/MIME body to account for the change.
Прокси, обрабатывающие ответ на REGISTER, НЕ СЛЕДУЕТ изменять любые значения поля заголовка Path, которые могут присутствовать в ответе. Регистратор МОЖЕТ защитить поле заголовка Path в ответе, включив его в защищённое тело S/MIME, и тогда изменения Path промежуточным прокси могут быть обнаружены UA как атаки «человек посередине». Прокси СЛЕДУЕТ рассматривать изменение значения поля заголовка Path в ответе на REGISTER только если они обладают учётными данными для корректного изменения тела S/MIME с учётом изменения.
5.3. Procedures at the Registrar
5.3. Процедуры на регистраторе
If a Path header field exists in a successful REGISTER request, the registrar constructs an ordered list of route elements (a path vector) from the nodes listed in the Path header field values, preserving the order as indicated in the Path header field values. The registrar then stores this path vector in association with that contact and the address-of-record indicated in the REGISTER request (the "binding" as defined in [1]). The registrar copies the Path header field values into a Path header field in the successful (200 class) REGISTER response. In the event that the home proxy and registrar are not co-located, the registrar MAY apply a locally- determined transformation to the stored path vector.
Если в успешном запросе REGISTER присутствует поле заголовка Path, регистратор строит упорядоченный список элементов маршрута (вектор пути) из узлов, перечисленных в значениях поля заголовка Path, сохраняя порядок, указанный в значениях поля заголовка Path. Затем регистратор сохраняет этот вектор пути в связи с этим контактом и адресом записи, указанным в запросе REGISTER («привязка», как определено в [1]). Регистратор копирует значения поля заголовка Path в поле заголовка Path в успешном (класса 200) ответе на REGISTER. В случае если домашний прокси и регистратор не совмещены, регистратор МОЖЕТ применить локально определённое преобразование к сохранённому вектору пути.
If a registrar receives a REGISTER request containing a Path header field and there is no indication of support for the extension in the UA (via a Supported header field), the registrar must rely on local policy in determining how to treat this request. The recommended policy is for the registrar to reject the request with a 420 "Bad Extension" response indicating the Path extension. This approach allows the UA to detect that an intermediate proxy has inappropriately added a Path header field. However, the Path mechanism should technically work in the absence of UA support (at some compromise to security), so some registrars MAY choose to support the extension in the absence of a Supported header field value in the request.
Если регистратор получает запрос REGISTER, содержащий поле заголовка Path, и нет указания на поддержку расширения у UA (через поле заголовка Supported), регистратор должен полагаться на локальную политику при определении того, как обрабатывать этот запрос. Рекомендуемая политика состоит в том, чтобы регистратор отклонил запрос ответом 420 «Bad Extension», указывающим расширение Path. Этот подход позволяет UA обнаружить, что промежуточный прокси неподобающим образом добавил поле заголовка Path. Однако механизм Path технически должен работать и при отсутствии поддержки со стороны UA (с некоторым компромиссом в безопасности), поэтому некоторые регистраторы МОГУТ выбрать поддержку расширения при отсутствии значения поля заголовка Supported в запросе.
5.4. Procedures at the Home Proxy
5.4. Процедуры на домашнем прокси
In the common SIP model, there is a home proxy associated with the registrar for a user. Each incoming request targeted to the public address-of-record for the user is routed to this proxy, which consults the registrar's database in order to determine the contact to which the request should be retargeted. The home proxy, in its basic mode of operation, rewrites the request-URI from the incoming request with the value of the registered contact and retransmits the request.
В обычной модели SIP с регистратором пользователя связан домашний прокси. Каждый входящий запрос, нацеленный на публичный адрес записи пользователя, маршрутизируется к этому прокси, который обращается к базе данных регистратора, чтобы определить контакт, на который следует перенацелить запрос. Домашний прокси в своём базовом режиме работы переписывает request-URI входящего запроса значением зарегистрированного контакта и повторно отправляет запрос.
With the addition of Path, the home proxy also copies the stored path vector associated with the specific contact in the registrar database into the Route header field of the outgoing request as a preloaded route. This causes the outgoing request to transit the proxies that were included in the Path header field of the REGISTER request.
С добавлением Path домашний прокси также копирует сохранённый вектор пути, связанный с конкретным контактом в базе данных регистратора, в поле заголовка Route исходящего запроса как предварительно загруженный маршрут. Это заставляет исходящий запрос проходить через прокси, которые были включены в поле заголовка Path запроса REGISTER.
In normal processing, the home proxy is the "terminal point" for the user's address-of-record (AOR). Consequentially, the Route header field on the incoming request will have been exhausted in reaching the home proxy. If it isn't, then things get interesting. In the most common case, the home proxy generates the outgoing Route header field by inserting the stored path vector ahead of the Route header field values contained in the incoming request. This procedure may be altered by a local policy at the home proxy.
При нормальной обработке домашний прокси является «конечной точкой» для адреса записи (AOR) пользователя. Следовательно, поле заголовка Route входящего запроса будет исчерпано при достижении домашнего прокси. Если это не так, то становится интересно. В наиболее общем случае домашний прокси формирует исходящее поле заголовка Route, вставляя сохранённый вектор пути перед значениями поля заголовка Route, содержащимися во входящем запросе. Эта процедура может быть изменена локальной политикой на домашнем прокси.
Loose routes may interact with routing policy in interesting ways. The specifics of how the stored path vector integrates with any locally required default route and local policy are implementation dependent. For example, some devices will use locally-configured explicit loose routing to reach a next-hop proxy, and others will use a default outbound-proxy routing rule. However, for the result to function, the combination must provide valid routing in the local environment. In general, the stored path vector is appended to any locally configured route needed to egress the service cluster. The service proxy (or registrar, as noted earlier) MAY also transform the stored path vector as needed to provide correct functionality. Systems designers must match the Path recording policy of their nodes with the routing policy in order to get a workable system.
Свободные маршруты могут взаимодействовать с политикой маршрутизации интересным образом. Конкретные детали того, как сохранённый вектор пути интегрируется с любым локально требуемым маршрутом по умолчанию и локальной политикой, зависят от реализации. Например, некоторые устройства будут использовать локально сконфигурированную явную свободную маршрутизацию для достижения прокси следующего перехода, а другие будут использовать правило маршрутизации исходящего прокси по умолчанию. Однако для того чтобы результат работал, комбинация должна обеспечивать действительную маршрутизацию в локальной среде. В общем случае сохранённый вектор пути добавляется к любому локально сконфигурированному маршруту, необходимому для выхода из кластера услуг. Прокси услуг (или регистратор, как отмечалось ранее) МОЖЕТ также преобразовывать сохранённый вектор пути по мере необходимости для обеспечения правильной функциональности. Системные архитекторы должны согласовать политику записи Path своих узлов с политикой маршрутизации, чтобы получить работоспособную систему.

6. Security Considerations
6. Вопросы безопасности
There are few security considerations for this document beyond those in SIP [1]. From a security perspective, the Path extension and its usage are identical to the Record-Route header field of basic SIP. Note that the transparency of the user expectations are preserved by returning the final Path to the originating UA -- that is, the UA is informed which additional proxies have been inserted into the path for the registration associated with that response.
Для настоящего документа немного вопросов безопасности сверх тех, что в SIP [1]. С точки зрения безопасности расширение Path и его использование идентичны полю заголовка Record-Route базового SIP. Обратите внимание, что прозрачность ожиданий пользователя сохраняется путём возврата итогового Path исходному UA — то есть UA информируется о том, какие дополнительные прокси были вставлены в путь для регистрации, связанной с этим ответом.
The Path header field accumulates information in a hop-by-hop manner during REGISTER processing. The return information is essentially end-to-end, that is, it is not altered by intermediate proxies. This leads to two slightly different security approaches.
Поле заголовка Path накапливает информацию посредством обработки «переход за переходом» во время REGISTER. Возвращаемая информация по существу является сквозной, то есть она не изменяется промежуточными прокси. Это приводит к двум несколько различающимся подходам к безопасности.
6.1. Considerations in REGISTER Request Processing
6.1. Соображения при обработке запроса REGISTER
Information accumulated in REGISTER processing causes additional proxies to be included in future requests between the registrar's location and the UA. An attack that allowed an intruding proxy to add itself to this chain would allow the attacker to intercept future calls intended for the UA.
Информация, накапливаемая при обработке REGISTER, приводит к тому, что дополнительные прокси включаются в будущие запросы между местоположением регистратора и UA. Атака, позволяющая вторгающемуся прокси добавить себя в эту цепочку, позволила бы злоумышленнику перехватывать будущие вызовы, предназначенные для UA.
An attacker could conceivably alter the Path either by altering data "on the wire" or by other manipulations (such as impersonation) that would cause it to be included in the SIP routing chain (a "node insertion" attack). Altering data "on the wire" may be addressed adequately by the use of transport-layer integrity protection mechanisms such as TLS or IPSEC. Proxy insertion can be addressed by mutual authentication at the proxy layer, which can also be provided by TLS or IPSEC. The "sips:" URI class defined in [1] provides a mechanism by which a UA may request that intermediate proxies provide integrity protection and mutual authentication.
Злоумышленник мог бы изменить Path либо путём изменения данных «в канале», либо иными манипуляциями (например, выдачей себя за другое лицо), которые привели бы к его включению в цепочку маршрутизации SIP (атака «вставки узла»). Изменение данных «в канале» может быть надлежащим образом адресовано использованием механизмов защиты целостности транспортного уровня, таких как TLS или IPSEC. Вставка прокси может быть адресована взаимной аутентификацией на уровне прокси, которая также может быть обеспечена TLS или IPSEC. Класс URI «sips:», определённый в [1], предоставляет механизм, которым UA может запросить у промежуточных прокси обеспечение защиты целостности и взаимной аутентификации.
Systems using the Path mechanism SHOULD use appropriate mechanisms (TLS, IPSEC, etc.) to provide message integrity and mutual authentication. UAs SHOULD use "sips:" to request transitive protection.
Системам, использующим механизм Path, СЛЕДУЕТ использовать надлежащие механизмы (TLS, IPSEC и т. д.) для обеспечения целостности сообщений и взаимной аутентификации. UA СЛЕДУЕТ использовать «sips:» для запроса транзитивной защиты.
The registering UA SHOULD use S/MIME mechanisms to provide a protected copy of the original request to the registrar. In this case, the UA SHOULD include a Supported header field with a value indicating support for the Path extension in the protected copy. Registrars receiving such as request MUST honor the Path extension only if support is indicated in the protected header field. Further, they SHOULD compare the unprotected Supported header field with the protected Supported header field and take appropriate action in the event that an intermediate has altered the message to indicate support for Path when it was not indicated by the requesting UA.
Регистрирующемуся UA СЛЕДУЕТ использовать механизмы S/MIME для предоставления регистратору защищённой копии исходного запроса. В этом случае UA СЛЕДУЕТ включить в защищённую копию поле заголовка Supported со значением, указывающим поддержку расширения Path. Регистраторы, получающие такой запрос, ДОЛЖНЫ учитывать расширение Path только если поддержка указана в защищённом поле заголовка. Более того, им СЛЕДУЕТ сравнить незащищённое поле заголовка Supported с защищённым полем заголовка Supported и предпринять надлежащие действия в случае, если промежуточный узел изменил сообщение, указав поддержку Path, когда она не была указана запрашивающим UA.
6.2. Considerations in REGISTER Response Processing
6.2. Соображения при обработке ответа на REGISTER
The data returned to the UA by the Path header field in the response to the REGISTER request is there to provide openness to the UA. The registrar is telling the UA, "These are the intermediate proxies that will be included on future requests to you processed through me". By inspection of this header field, the UA may be able to detect node insertion attacks that involve inserting a proxy into the SIP routing chain. S/MIME techniques may be used to prevent alteration of this header field by intermediate proxies during response processing.
Данные, возвращаемые UA полем заголовка Path в ответе на запрос REGISTER, служат для обеспечения открытости перед UA. Регистратор сообщает UA: «Это промежуточные прокси, которые будут включены в будущие запросы к вам, обрабатываемые через меня». Путём изучения этого поля заголовка UA может оказаться способен обнаружить атаки вставки узла, которые включают вставку прокси в цепочку маршрутизации SIP. Методы S/MIME могут использоваться для предотвращения изменения этого поля заголовка промежуточными прокси во время обработки ответа.
As specified, there is no requirement for arbitrary proxies between the UA and the registrar to modify the Path header field in the REGISTER response. Consequently, we may use an end-to-end protection technique. The S/MIME technique defined in [1] provides an effective mechanism. Using this technique, the registrar makes a copy of the complete response, signs it, and attaches it as a body to the response. The UA may then verify this response, assuring an unmodified Path header field is received.
Как указано, нет требования, чтобы произвольные прокси между UA и регистратором изменяли поле заголовка Path в ответе на REGISTER. Следовательно, мы можем использовать метод сквозной защиты. Метод S/MIME, определённый в [1], предоставляет эффективный механизм. Используя этот метод, регистратор делает копию полного ответа, подписывает её и прикрепляет как тело к ответу. Затем UA может проверить этот ответ, удостоверяясь, что получено неизменённое поле заголовка Path.
In addition to the hop-by-hop integrity protection and mutual authentication measures suggested for REGISTER request processing in the preceding section, systems using Path header fields SHOULD implement end-to-end protection using S/MIME. More specifically, registrars returning a Path header field SHOULD attach a signed S/MIME of the response, and UAs receiving a REGISTER response containing a Path header field SHOULD validate the message using the S/MIME technique. Furthermore, UAs receiving a Path header field in a REGISTER response SHOULD render it to the user, or (where feasible) check it programmatically.
В дополнение к мерам защиты целостности «переход за переходом» и взаимной аутентификации, предложенным для обработки запроса REGISTER в предыдущем разделе, системам, использующим поля заголовка Path, СЛЕДУЕТ реализовать сквозную защиту с помощью S/MIME. Более конкретно, регистраторам, возвращающим поле заголовка Path, СЛЕДУЕТ прикреплять подписанный S/MIME ответа, а UA, получающим ответ на REGISTER, содержащий поле заголовка Path, СЛЕДУЕТ проверять сообщение программной проверки (где это возможно), либо отображать его пользователю.
