Abstract
Аннотация
The Licklider Transmission Protocol (LTP) is intended to serve as a reliable convergence layer over single-hop deep-space radio frequency (RF) links. LTP does Automatic Repeat reQuest (ARQ) of data transmissions by soliciting selective-acknowledgment reception reports. It is stateful and has no negotiation or handshakes. This document describes security extensions to LTP, and is part of a series of related documents describing LTP.
Протокол передачи Линклэйдера (Licklider Transmission Protocol, LTP) предназначен для использования в качестве надёжного уровня сходимости поверх односкачковых радиолиний (RF) дальнего космоса. LTP выполняет автоматический запрос повторной передачи (ARQ) передач данных путём запроса отчётов о приёме с выборочным подтверждением. Он хранит состояние и не выполняет согласования параметров или рукопожатий. Этот документ описывает расширения безопасности для LTP и входит в серию связанных документов, описывающих LTP.
This document is a product of the Delay Tolerant Networking Research Group and has been reviewed by that group. No objections to its publication as an RFC were raised.
Настоящий документ является результатом работы исследовательской группы по сетям с задержками и был рассмотрен этой группой. Возражений против его публикации в качестве RFC не поступало.
1. Introduction
1. Введение
This document describes extensions to the base LTP protocol [LTPSPEC]. The background to LTP is described in the "motivation" document [LTPMOTIVE]. All the extensions defined in this document provide additional security features for LTP.
Настоящий документ описывает расширения базового протокола LTP [LTPSPEC]. Предпосылки создания LTP описаны в документе, посвящённом мотивации [LTPMOTIVE]. Все расширения, определённые в настоящем документе, предоставляют LTP дополнительные функции безопасности.
LTP is designed to provide retransmission-based reliability over links characterized by extremely long message round-trip times (RTTs) and/or frequent interruptions in connectivity. Since communication across interplanetary space is the most prominent example of this sort of environment, LTP is principally aimed at supporting "long- haul" reliable transmission in interplanetary space, but has applications in other environments as well.
LTP разработан для обеспечения надёжности на основе повторных передач в каналах, для которых характерны чрезвычайно большие времена кругового обхода сообщений (RTT) и/или частые перерывы в связности. Поскольку связь в межпланетном пространстве является наиболее ярким примером среды такого рода, LTP в первую очередь предназначен для поддержки надёжной передачи «на большие расстояния» в межпланетном пространстве, но находит применение и в других средах.
This document describes security extensions to LTP, and is part of a series of related documents describing LTP. Other documents in this series cover the motivation for LTP and the main protocol specification. We recommend reading all the documents in the series before writing code based on this document.
Настоящий документ описывает расширения безопасности для LTP и является частью серии связанных документов, описывающих LTP. Другие документы этой серии охватывают обоснование LTP и основную спецификацию протокола. Мы рекомендуем прочитать все документы серии, прежде чем писать код на основе настоящего документа.
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [B97].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны толковаться так, как описано в [B97].
2. Security Extensions
2. Расширения безопасности
The syntactical layout of the extensions are defined in Section 3.1.4 of the base protocol specification [LTPSPEC].
Синтаксическое расположение расширений определено в разделе 3.1.4 спецификации базового протокола [LTPSPEC].
Implementers should note that the LTP extension mechanism allows for multiple occurrences of any extension tag, in both (or either) the header or trailer. For example, the LTP authentication mechanism defined below requires both header and trailer extensions, which both use the same tag. This document defines new security extensions for LTP but does not address key management since key management in Delay-Tolerant Networking (DTN) remains an open research question.
Разработчикам следует учитывать, что механизм расширений LTP допускает многократные вхождения любого тега расширения как в заголовке, так и в трейлере (или в любом из них). Например, определяемый ниже механизм аутентификации LTP требует расширений и заголовка, и трейлера, причём в обоих используется один и тот же тег. Настоящий документ определяет новые расширения безопасности для LTP, но не рассматривает управление ключами, поскольку управление ключами в сетях с задержками (DTN) остаётся открытым исследовательским вопросом.
If LTP were deployed layered on top of UDP, it might be possible to use IPsec or other existing security mechanisms. However, in general DTN, IPsec's key exchange (IKE) cannot work (e.g., where link delays are measured in minutes).
Если бы LTP развёртывался поверх UDP, можно было бы использовать IPsec или другие существующие механизмы безопасности. Однако в общем случае DTN обмен ключами IPsec (IKE) не может работать (например, там, где задержки в канале измеряются минутами).
2.1. LTP Authentication
2.1. Аутентификация LTP
The LTP authentication mechanism provides cryptographic authentication of the segment.
Механизм аутентификации LTP обеспечивает криптографическую аутентификацию сегмента.
Implementations MAY support this extension field. If they do not support this header, then they MUST ignore it.
Реализации МОГУТ поддерживать это поле расширения. Если они не поддерживают этот заголовок, они ДОЛЖНЫ его игнорировать.
The LTP authentication extension field has the extension tag value 0x00.
Поле расширения аутентификации LTP имеет значение тега расширения 0x00.
LTP authentication requires three new fields, the first two of which are carried as the value of the Extensions field of the LTP segment header, and the third of which is carried in the segment trailer.
Аутентификация LTP требует трёх новых полей, причём первые два из них переносятся как значение поля Extensions заголовка сегмента LTP, а третье переносится в трейлере этого сегмента.
The fields that are carried in the header extensions field are catenated together to form the extension value (with the leftmost octet representing the ciphersuite and the remaining octets the KeyID). The KeyID field is optional, and is determined to be absent if the extension value consists of a single octet.
Поля, переносимые в поле расширений заголовка, сцепляются вместе, образуя значение расширения (при этом крайний левый октет представляет набор шифров, а остальные октеты — KeyID). Поле KeyID необязательно и считается отсутствующим, если значение расширения состоит из одного октета.
Ciphersuite: an 8-bit integer value with values defined below.
Ciphersuite: 8-битное целое значение, значения которого определены ниже.
KeyID: An optional key identifier, the interpretation of which is out of scope for this specification (that is, implementers MUST treat these KeyID fields as raw octets, even if they contained an ASN.1 DER encoding of an X.509 IssuerSerial construct [PKIXPROF], for example).
KeyID: необязательный идентификатор ключа, интерпретация которого выходит за рамки настоящей спецификации (то есть разработчики ДОЛЖНЫ рассматривать эти поля KeyID как необработанные октеты, даже если они содержали, например, кодировку ASN.1 DER конструкции X.509 IssuerSerial [PKIXPROF]).
The LTP-auth header extension MUST be present in the first segment from any LTP session that uses LTP authentication, but MAY be omitted from subsequent segments in that session. To guard against additional problems arising from lost segments, implementations SHOULD, where bandwidth allows, include these fields in a number of segments in the LTP session. If the first segment (or any part thereof) is retransmitted, then the LTP-auth header extension MUST be included in the retransmission. The field carried as a trailer extension is the AuthVal field. It contains the authentication value, which is either a message authentication code (MAC) or a digital signature. This is itself a structured field whose length and formatting depend on the ciphersuite.
Расширение заголовка LTP-auth ДОЛЖНО присутствовать в первом сегменте любого сеанса LTP, использующего аутентификацию LTP, но МОЖЕТ отсутствовать в последующих сегментах этого сеанса. Чтобы защититься от дополнительных проблем, возникающих из-за потерянных сегментов, реализации СЛЕДУЕТ, где позволяет полоса пропускания, включать эти поля в ряд сегментов сеанса LTP. Если первый сегмент (или любая его часть) передаётся повторно, расширение заголовка LTP-auth ДОЛЖНО быть включено в повторную передачу. Поле, переносимое как расширение трейлера, — это поле AuthVal. Оно содержит значение аутентификации, которым является либо код аутентификации сообщения (MAC), либо цифровая подпись. Само по себе это структурированное поле, длина и форматирование которого зависят от набора шифров.
If for some reason the sender includes two instances of LTP-auth headers, then there is a potential problem for the receiver in that presumably at least one of the AuthVal fields will not verify. There are very few situations where it would make sense to include more than one LTP-auth extension in a single segment, since LTP is a peer- to-peer protocol. If however, keys are being upgraded, then the sender might protect the segment with both the new and old keys. In such cases, the receiver MUST search and can consider the LTP authentication valid so long as one AuthVal is correct.
Если отправитель по какой-то причине включает два экземпляра заголовков LTP-auth, у получателя возникает потенциальная проблема: предположительно как минимум одно из полей AuthVal не пройдёт проверку. Существует очень мало ситуаций, в которых имело бы смысл включать более одного расширения LTP-auth в один сегмент, поскольку LTP является двухточечным протоколом. Однако если выполняется обновление ключей, отправитель может защитить сегмент как новым, так и старым ключом. В таких случаях получатель ДОЛЖЕН выполнять поиск и может считать аутентификацию LTP действительной, если хотя бы одно значение AuthVal корректно.
For all ciphersuites, the input to the calculation is the entire encoded segment including the AuthVal extension tag and length, but not of course, including the AuthVal value.
Для всех наборов шифров входными данными для вычисления служит весь закодированный сегмент, включая тег и длину расширения AuthVal, но, разумеется, не включая само значение AuthVal.
We define three ciphersuites in this specification. Our approach is to follow the precedent set by TLS [TLS], and to "hardcode" all algorithm options in a single ciphersuite number. This means that there are 256 potential ciphersuites supported by this version of LTP-auth. Since this is a limited space, IANA has established a registry for LTP Ciphersuites as described in the IANA Considerations section below. Current ciphersuite assignments are:
В настоящей спецификации мы определяем три набора шифров. Наш подход состоит в следовании прецеденту, заданному TLS [TLS], и в «жёстком закреплении» всех параметров алгоритмов в одном номере набора шифров. Это означает, что данная версия LTP-auth поддерживает 256 потенциальных наборов шифров. Поскольку это ограниченное пространство, IANA создала реестр наборов шифров LTP, как описано в разделе «Соображения для IANA» ниже. Текущие назначения наборов шифров таковы:
Ciphersuite Value ----------- ----- HMAC-SHA1-80 0 RSA-SHA256 1 Unassigned 2-127 Reserved 128-191 Private/Experimental Use 192-254 NULL 255
Ciphersuite Value ----------- ----- HMAC-SHA1-80 0 RSA-SHA256 1 Unassigned 2-127 Reserved 128-191 Private/Experimental Use 192-254 NULL 255
1. HMAC-SHA1-80 Ciphersuite
1.
The HMAC-SHA1-80 ciphersuite involves generating a MAC over the LTP segment and appending the resulting AuthVal field to the end of the segment. There is only one MACing algorithm defined for this, which is HMAC-SHA1-80 [HMAC]. The AuthVal field in this case contains just the output of the HMAC-SHA1-80 algorithm, which is a fixed-width field (10 octets).
Набор шифров HMAC-SHA1-80. Набор шифров HMAC-SHA1-80 предполагает вычисление MAC по сегменту LTP и добавление полученного поля AuthVal в конец сегмента. Для этого определён только один алгоритм вычисления MAC — HMAC-SHA1-80 [HMAC]. Поле AuthVal в этом случае содержит просто результат работы алгоритма HMAC-SHA1-80, который является полем фиксированной ширины (10 октетов).
2. RSA-SHA256 Ciphersuite
2.
The RSA-SHA256 ciphersuite involves generating a digital signature of the LTP segment and appending the resulting AuthVal field to the end of the segment. There is only one signature algorithm currently defined for this, which is RSA with SHA256 as defined in [RSA], Section 8.2. The AuthVal field in this case is simply the signature value, where the signature value occupies the minimum number of octets, e.g., 128 octets for a 1024-bit signature).
Набор шифров RSA-SHA256. Набор шифров RSA-SHA256 предполагает формирование цифровой подписи сегмента LTP и добавление полученного поля AuthVal в конец сегмента. В настоящее время для этого определён только один алгоритм подписи — RSA с SHA256, как определено в [RSA], раздел 8.2. Поле AuthVal в этом случае представляет собой просто значение подписи, причём значение подписи занимает минимальное число октетов, например 128 октетов для 1024-битной подписи).
3. NULL Ciphersuite
3.
The NULL ciphersuite is basically the same as the HMAC-SHA1-80 ciphersuite, but with a hardcoded key. This ciphersuite effectively provides only a strong checksum without authentication, and thus is subject to active attacks and is the equivalent of providing a Cyclic Redundancy Check (CRC).
Набор шифров NULL. Набор шифров NULL в основном совпадает с набором шифров HMAC-SHA1-80, но использует жёстко закреплённый ключ. Этот набор шифров фактически обеспечивает лишь надёжную контрольную сумму без аутентификации, поэтому он подвержен активным атакам и эквивалентен применению циклической избыточной проверки (CRC).
The hardcoded key to be used with this ciphersuite is the following:
Ключ, жёстко закреплённый для этого набора шифров, следующий:
HMAC_KEY : c37b7e64 92584340 : bed12207 80894115 : 5068f738 (The above is the test vector from RFC 3537 [WRAP].)
HMAC_KEY : c37b7e64 92584340 : bed12207 80894115 : 5068f738 (выше приведён тестовый вектор из RFC 3537 [WRAP]).
In each case, the bytes that are input to the cryptographic algorithm consist of the entire LTP segment except the AuthVal. In particular, the header extensions field that may contain the ciphersuite number and the KeyID field is part of the input.
В каждом случае байтами, подаваемыми на вход криптографического алгоритма, является весь сегмент LTP, кроме AuthVal. В частности, поле расширений заголовка, которое может содержать номер набора шифров, и поле KeyID входят во входные данные.
The output bytes of the cryptographic operation are the payload of the AuthVal field.
Выходными байтами криптографической операции является полезная нагрузка поля AuthVal.
The following shows an example LTP-auth header, starting from and including the Extensions field.
Ниже показан пример заголовка LTP-auth, начиная с поля Extensions и включая это поле.
ext tag sdnv c-s k-id +----+----+----+----+----+ |0x11|0x00|0x02|0x00|0x24| +----+----+----+----+----+
ext tag sdnv c-s k-id +----+----+----+----+----+ |0x11|0x00|0x02|0x00|0x24| +----+----+----+----+----+
The Extensions field has the value 0x11 with the most significant and least significant nibble value 1, indicating the presence of one header and one trailer extension, respectively. The next octet is the extension tag (0x00 for LTP-auth), followed by the Self- Delimiting Numeric Value (SDNV) encoded length of the ensuing data: a one-octet ciphersuite (0x00 meaning HMAC-SHA1-80) and the KeyID (in this case with a short value of 0x24). The trailer extension (not shown above) should contain the AuthVal.
Поле Extensions имеет значение 0x11, в котором старшая и младшая тетрады равны 1, что указывает на наличие одного расширения заголовка и одного расширения трейлера соответственно. Следующий октет — тег расширения (0x00 для LTP-auth), за которым следует длина последующих данных, закодированная самоограничивающимся числовым значением (SDNV): набор шифров размером в один октет (0x00 означает HMAC-SHA1-80) и KeyID (в данном случае короткое значение 0x24). Расширение трейлера (не показанное выше) должно содержать AuthVal.
2.2. A Cookie Mechanism
2.2. Механизм cookie
The use of cookies is a well-known way to make Denial of Service (DoS) attacks harder to mount. We define the cookie extension for use in environments where an LTP implementation is liable to such attacks.
Использование cookie — хорошо известный способ затруднить проведение атак типа «отказ в обслуживании» (DoS). Мы определяем расширение cookie для применения в средах, где реализация LTP подвержена таким атакам.
The cookie is placed in a header extension field, and has no related trailer extension field. It has the extension tag value 0x01.
Cookie размещается в поле расширения заголовка и не имеет связанного поля расширения трейлера. Он имеет значение тега расширения 0x01.
The cookie value can essentially be viewed as a sufficiently long random number, where the length can be determined by the implementation (longer cookies are harder to guess and therefore better, though using more bandwidth). Note that cookie values can be derived using lots of different schemes so long as they produce random-looking and hard-to-predict values.
Значение cookie по существу можно рассматривать как достаточно длинное случайное число, причём длину определяет реализация (более длинные cookie труднее угадать и потому они лучше, хотя занимают больше полосы пропускания). Отметим, что значения cookie можно получать с помощью множества различных схем, если только они дают выглядящие случайными и трудно предсказуемые значения.
The first cookie inserted into a segment for this session is called the initial cookie.
Первый cookie, вставленный в сегмент для этого сеанса, называется начальным cookie.
Note that cookies do not outlast an LTP session.
Отметим, что cookie не переживают сеанс LTP.
The basic mode of operation is that an LTP engine can include a cookie in a segment at any time. After that time, all segments corresponding to that LTP session MUST contain a good cookie value -- that is, all segments both to and from the engine MUST contain a good cookie. Clearly, there will be some delay before the cookie is seen in incoming segments -- implementations MUST determine an acceptable delay for these cases, and MUST only accept segments without a cookie until that time.
Основной режим работы состоит в том, что LTP-движок может в любой момент включить cookie в сегмент. После этого все сегменты, соответствующие данному сеансу LTP, ДОЛЖНЫ содержать правильное значение cookie, то есть все сегменты как к движку, так и от него ДОЛЖНЫ содержать правильный cookie. Очевидно, что пройдёт некоторая задержка, прежде чем cookie появится во входящих сегментах; реализации ДОЛЖНЫ определить приемлемую задержку для таких случаев и до этого момента ДОЛЖНЫ принимать только сегменты без cookie.
The cookie value can be extended at any time by catenating more random bits. This allows both LTP engines to contribute to the randomness of the cookie, where that is useful. It also allows a node that considers the cookie value too short (say due to changing circumstances) to add additional security. In this case, the extended cookie value becomes the "to-be-checked-against" cookie value for all future segments (modulo the communications delay as above). It can happen that both sides emit segments containing an initial cookie before their peer has a chance to see any cookie. In that case, two cookie extension fields MUST be included in all segments subsequently (once the traffic has caught up). That is, the sender and recipient cookies are handled independently. In such cases, both cookie values MUST be "good" at all relevant times (i.e., modulo the delay). In this case, the peer's initial cookie MUST arrive before the calculated delay for receipt of segments containing this engine's cookie -- there is only a finite window during which a second cookie can be inserted into the session.
Значение cookie можно в любой момент расширить, сцепив с ним дополнительные случайные биты. Это позволяет обоим LTP-движкам вносить вклад в случайность cookie там, где это полезно. Это также позволяет узлу, который считает значение cookie слишком коротким (скажем, из-за изменившихся обстоятельств), добавить дополнительную защиту. В этом случае расширенное значение cookie становится значением cookie, «с которым выполняется сверка», для всех последующих сегментов (с учётом задержки связи, как указано выше). Может случиться, что обе стороны отправят сегменты, содержащие начальный cookie, прежде чем их партнёр успеет увидеть какой-либо cookie. В этом случае впоследствии (как только трафик догонит) во все сегменты ДОЛЖНЫ включаться два поля расширения cookie. То есть cookie отправителя и получателя обрабатываются независимо. В таких случаях оба значения cookie ДОЛЖНЫ быть «правильными» во все соответствующие моменты времени (т. е. с учётом задержки). При этом начальный cookie партнёра ДОЛЖЕН поступить до истечения расчётной задержки получения сегментов, содержащих cookie этого движка, — существует лишь конечное окно, в течение которого в сеанс можно вставить второй cookie.
A "good" cookie is therefore one that starts with the currently stored cookie value, or else a new cookie where none has been seen in that session so far. Once a cookie value is seen and treated as "good" (e.g., an extended value), the previous value is no longer "good".
Таким образом, «правильный» cookie — это тот, который начинается с текущего сохранённого значения cookie, либо новый cookie, если в этом сеансе до сих пор не было видно ни одного. Как только значение cookie увидено и признано «правильным» (например, расширенное значение), предыдущее значение больше не является «правильным».
Modulo the communications delay, segments with an incorrect or missing cookie value MUST be silently discarded.
С учётом задержки связи сегменты с неверным или отсутствующим значением cookie ДОЛЖНЫ молча отбрасываться.
If a segment is to be retransmitted (e.g., as a result of a timer expiring), then it needs to contain the correct cookie value at the time of (re)transmission. Note that this may differ from what was the correct cookie value at the time of the original transmission.
Если сегмент подлежит повторной передаче (например, из-за истечения таймера), он должен содержать правильное значение cookie на момент (повторной) передачи. Отметим, что оно может отличаться от значения cookie, которое было правильным в момент первоначальной передачи.
3. Security Considerations
3. Соображения безопасности
The extensions specified above are generally intended to help thwart DoS attacks. For environments where lower layers provide neither integrity nor freshness, it makes sense to use both extensions together. For example, in the case where a node extends an existing cookie, the lack of origin authentication would allow a man in the middle to lock out the session.
Описанные выше расширения в целом предназначены для противодействия атакам DoS. Для сред, где нижние уровни не обеспечивают ни целостности, ни свежести, имеет смысл применять оба расширения вместе. Например, в случае, когда узел расширяет существующий cookie, отсутствие аутентификации источника позволило бы посреднику заблокировать сеанс.
While there are currently some concerns about using the SHA-1 algorithm, these appear to only make it easier to find collisions. In that case, the use of HMAC with SHA-1 can still be considered safe. However, we have changed to use SHA-256 for the signature ciphersuite.
Хотя в настоящее время существуют определённые опасения по поводу использования алгоритма SHA-1, они, по-видимому, лишь облегчают поиск коллизий. В этом случае применение HMAC с SHA-1 всё ещё можно считать безопасным. Однако для набора шифров подписи мы перешли на использование SHA-256.
