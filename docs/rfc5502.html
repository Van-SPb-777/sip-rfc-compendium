Abstract
Аннотация
This document specifies the SIP P-Served-User P-header. This header field addresses an issue that was found in the 3rd Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) between an S-CSCF (Serving Call Session Control Function) and an AS (Application Server) on the ISC (IMS Service Control) interface. This header field conveys the identity of the served user and the session case that applies to this particular communication session and application invocation.
Настоящий документ определяет SIP P-заголовок P-Served-User. Это поле заголовка решает проблему, обнаруженную в проекте партнёрства третьего поколения (3GPP) IMS (IP Multimedia Subsystem) между S-CSCF (Serving Call Session Control Function) и AS (сервером приложений) на интерфейсе ISC (IMS Service Control). Это поле заголовка передаёт идентичность обслуживаемого пользователя и случай сессии, применимый к данной конкретной сессии связи и вызову приложения.
Appendix A. Why the History-Info Header Is Not Suitable to Convey the Served User Information on the ISC
Приложение A. Почему заголовок History-Info не подходит для передачи информации об обслуживаемом пользователе на интерфейсе ISC
1. Introduction
1. Введение
The 3rd Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) uses SIP (RFC 3261 [2]) as its main signaling protocol. (For more information on the IMS, a detailed description can be found in 3GPP TS 23.228 [9] and 3GPP TS 24.229 [11].) 3GPP has identified issues with the linking in of a SIP application server that are most appropriately resolved by defining a new SIP P-header, according to the procedures in RFC 3427 [5].
Проект партнёрства третьего поколения (3GPP) IMS (IP Multimedia Subsystem) использует SIP (RFC 3261 [2]) в качестве своего основного протокола сигнализации. (Более подробное описание IMS можно найти в 3GPP TS 23.228 [9] и 3GPP TS 24.229 [11].) 3GPP выявил проблемы с подключением сервера приложений SIP, которые наиболее целесообразно решить путём определения нового SIP P-заголовка в соответствии с процедурами RFC 3427 [5].
The remainder of this document is organized as follows. Section 4 outlines the problem by using particular service scenarios, and Section 5 discusses the requirements derived from these scenarios. Section 6 defines the P-Served-User header field, which meets those requirements, Section 7 specifies the proxy behavior for the new header field, and Section 8 discusses the applicability and scope of this new header field. Section 9 registers the P-Served-User header field with the IANA, and Section 10 discusses the security properties of the environment where this header field is intended to be used.
Остальная часть настоящего документа организована следующим образом. В разделе 4 проблема описывается на примере конкретных сценариев обслуживания, а в разделе 5 обсуждаются требования, вытекающие из этих сценариев. В разделе 6 определяется поле заголовка P-Served-User, отвечающее этим требованиям, в разделе 7 описывается поведение прокси для нового поля заголовка, а в разделе 8 обсуждаются применимость и область действия этого нового поля заголовка. В разделе 9 поле заголовка P-Served-User регистрируется в IANA, а в разделе 10 обсуждаются свойства безопасности среды, в которой предполагается использовать это поле заголовка.

3.2. Served User
3.2. Обслуживаемый пользователь
The served user to a proxy or AS (Application Server) is the user whose service profile is accessed by that proxy or AS when an initial request is received that is originated by, originated on behalf of, or terminated to that user. This profile in turn provides some useful information (preferences or permissions) for processing at a proxy and, potentially, at an AS.
Обслуживаемый пользователь для прокси или AS (сервера приложений) — это пользователь, к профилю обслуживания которого обращается этот прокси или AS при получении начального запроса, исходящего от этого пользователя, исходящего от его имени или входящего к нему. Этот профиль, в свою очередь, предоставляет некоторую информацию (предпочтения или разрешения) для обработки на прокси и, возможно, на AS.
4. Scenarios
4. Сценарии
4.1. General
4.1. Общие положения
In the 3GPP IMS (IP Multimedia Subsystem), the S-CSCF (Serving CSCF) is a SIP proxy that serves as a registrar and handles originating and terminating session states for users allocated to it. This means that any call that is originated by a specific user or any call that is terminated to that specific user will pass through the S-CSCF that is allocated to that user.
В 3GPP IMS (IP Multimedia Subsystem) S-CSCF (Serving CSCF) — это прокси SIP, который выполняет функции регистратора и обрабатывает состояния исходящих и входящих сессий для выделенных ему пользователей. Это означает, что любой вызов, исходящий от конкретного пользователя, или любой вызов, входящий к этому конкретному пользователю, будет проходить через S-CSCF, выделенный этому пользователю.
At the moment that an S-CSCF is allocated for a specific user, a user profile is downloaded to the S-CSCF from the HSS (Home Subscriber Server) over the Cx interface, see 3GPP TS 29.228 [12]. This user profile tells the S-CSCF whether the user is allowed to originate or terminate calls or whether an AS needs to be linked in over the ISC interface. The user profile information that determines whether a particular initial request needs to be sent to a particular AS is called the initial Filter Criteria (iFC), see for example 3GPP TS 23.218 [8].
В момент выделения S-CSCF для конкретного пользователя профиль пользователя загружается в S-CSCF из HSS (Home Subscriber Server) по интерфейсу Cx, см. 3GPP TS 29.228 [12]. Этот профиль пользователя сообщает S-CSCF, разрешено ли пользователю инициировать или принимать вызовы либо требуется ли подключение AS по интерфейсу ISC. Информация профиля пользователя, определяющая, должен ли конкретный начальный запрос быть отправлен конкретному AS, называется начальными критериями фильтрации (initial Filter Criteria, iFC), см., например, 3GPP TS 23.218 [8].
For an S-CSCF to be able to meet its responsibilities, it needs to determine on which user's behalf it is performing its tasks and which session case is applicable for the particular request. (For a definition of session case, see 3GPP TS 29.228 [12]). The session case distinguishes the originating and terminating call cases and determines whether or not the particular user is registered.
Чтобы S-CSCF мог выполнять свои обязанности, ему необходимо определить, от чьего имени он выполняет свои задачи и какой случай сессии применим к конкретному запросу. (Определение случая сессии см. в 3GPP TS 29.228 [12].) Случай сессии различает исходящий и входящий случаи вызова и определяет, зарегистрирован ли конкретный пользователь.
When the S-CSCF determines that for an incoming initial request the originating call case applies, it determines the served user by looking at the P-Asserted-Identity header field (RFC 3325 [4]), which carries the network asserted identity of the originating user. When, after processing the iFC for this initial request, the S-CSCF decides to forward the request to an AS, the AS has to go through a similar process of determining the session case and the served user. Since it should come to the same conclusion that this is an originating session case, it also has to look at the P-Asserted-Identity header field to determine the served user.
Когда S-CSCF определяет, что для входящего начального запроса применим исходящий случай вызова, он определяет обслуживаемого пользователя, просматривая поле заголовка P-Asserted-Identity (RFC 3325 [4]), которое несёт сетевую утверждаемую идентичность исходящего пользователя. Когда после обработки iFC для этого начального запроса S-CSCF решает переслать запрос в AS, AS должен пройти аналогичный процесс определения случая сессии и обслуживаемого пользователя. Поскольку он должен прийти к тому же выводу, что это исходящий случай сессии, ему также необходимо просмотреть поле заголовка P-Asserted-Identity, чтобы определить обслуживаемого пользователя.
When the S-CSCF determines that for an incoming initial request the terminating call case applies, it determines the served user by looking at the Request-URI (RFC 3261 [2]), which carries the identity of the intended terminating user. When, after processing the iFC for this initial request, the S-CSCF decides to forward the request to an AS, the AS has to go through a similar process of determining the session case and the served user. Since it should come to the same conclusion that this is a terminating session case, it also has to look at the Request-URI to determine the served user. In the originating case, it can be observed that while the P-Asserted-Identity header field just represents the originating user when it enters the S-CSCF, it is overloaded with another meaning when it is sent to an AS over the ISC interface. This other meaning is that it serves as a representation of the served user.
Когда S-CSCF определяет, что для входящего начального запроса применим входящий случай вызова, он определяет обслуживаемого пользователя, просматривая Request-URI (RFC 3261 [2]), который несёт идентичность предполагаемого входящего пользователя. Когда после обработки iFC для этого начального запроса S-CSCF решает переслать запрос в AS, AS должен пройти аналогичный процесс определения случая сессии и обслуживаемого пользователя. Поскольку он должен прийти к тому же выводу, что это входящий случай сессии, ему также необходимо просмотреть Request-URI, чтобы определить обслуживаемого пользователя. В исходящем случае можно заметить, что, хотя поле заголовка P-Asserted-Identity при входе в S-CSCF просто представляет исходящего пользователя, при отправке в AS по интерфейсу ISC оно перегружается другим смыслом. Этот другой смысл состоит в том, что оно служит представлением обслуживаемого пользователя.
In the terminating case, a similar overloading happens to the Request-URI; while it first only represented the identity of the intended terminating user, it is overloaded with another meaning when it is sent to an AS over the ISC interface. This other meaning is that it serves as a representation of the served user.
Во входящем случае аналогичная перегрузка происходит с Request-URI: поначалу он представлял только идентичность предполагаемого входящего пользователя, но при отправке в AS по интерфейсу ISC он перегружается другим смыслом. Этот другой смысл состоит в том, что он служит представлением обслуживаемого пользователя.
In basic call scenarios, this does not show up as a problem, but once more complicated service scenarios (notably forwarding services) need to be realized, it poses severe limitations. Such scenarios are brought forward in the following subsections.
В базовых сценариях вызова это не проявляется как проблема, но как только требуется реализовать более сложные сценарии обслуживания (прежде всего услуги перенаправления), это создаёт серьёзные ограничения. Такие сценарии рассматриваются в следующих подразделах.
4.2. Diversion: Continue on Terminating Leg, but Finish Subsequent Terminating iFC First
4.2. Переадресация: продолжить на входящем плече вызова, но сначала завершить последующие входящие iFC
Imagine a service scenario where a user B has a terminating service that diverts the call to a different destination but is required to still execute subsequent terminating services for the same user. This means that this particular user has multiple iFC configured that are applicable for an incoming initial request. When the S-CSCF receives an initial INVITE request, it analyzes the request and determines that the session case is for a terminating registered user, then it determines the served user to be user B by looking at the Request-URI.
Представьте сценарий обслуживания, в котором у пользователя B есть входящая услуга, которая перенаправляет вызов на другой пункт назначения, но при этом требуется всё же выполнить последующие входящие услуги для того же пользователя. Это означает, что у данного пользователя настроено несколько iFC, применимых к входящему начальному запросу. Когда S-CSCF получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к входящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь B, просматривая Request-URI.
Now the S-CSCF starts the iFC processing. The first iFC that matches the INVITE request causes the INVITE to be forwarded over the ISC interface to an AS that hosts user B's diversion service by adding the AS and S-CSCF's own hostnames to the Route header. The S-CSCF adds an Original Dialog Identifier (ODI) to the S-CSCF's own hostname on the Route header. This allows the S-CSCF to correlate an INVITE coming from an AS over the ISC interface to the existing session that forwarded the INVITE to the AS in the first place.
Теперь S-CSCF начинает обработку iFC. Первое iFC, соответствующее запросу INVITE, приводит к тому, что INVITE пересылается по интерфейсу ISC в AS, на котором размещена услуга перенаправления пользователя B, путём добавления имён узлов AS и самого S-CSCF в заголовок Route. S-CSCF добавляет идентификатор исходного диалога (Original Dialog Identifier, ODI) к имени своего узла в заголовке Route. Это позволяет S-CSCF соотнести INVITE, приходящий от AS по интерфейсу ISC, с существующей сессией, которая изначально переслала INVITE в AS.
When the AS receives the initial INVITE request, it analyzes the request and determines that the session case is for a terminating registered user, then it determines the served user to be user B by looking at the Request-URI. Based on some criteria, the diversion service concludes that the request needs to be diverted to another user or application C. It does this by changing the Request-URI to C. Optionally, it records the Request-URI history by using the History- Info header field (RFC 4244 [7]). Then the AS removes itself from the Route header and routes the INVITE request back to the S-CSCF by using the topmost Route header field.
Когда AS получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к входящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь B, просматривая Request-URI. На основании некоторых критериев услуга перенаправления приходит к выводу, что запрос необходимо перенаправить другому пользователю или приложению C. Она делает это, изменяя Request-URI на C. При необходимости она записывает историю Request-URI с помощью поля заголовка History-Info (RFC 4244 [7]). Затем AS удаляет себя из заголовка Route и маршрутизирует запрос INVITE обратно в S-CSCF, используя верхнее поле заголовка Route.
When the S-CSCF receives the INVITE over the ISC interface, it can see that the Route header contains its own hostname and an ODI that correlates to an existing terminating session for user B. This can be used by the S-CSCF to analyze whether there are still unexecuted iFC. (Note that the current behavior of the S-CSCF on receiving an INVITE with a changed Request-URI is to terminate the iFC processing and to route the request based on the new Request-URI value.)
Когда S-CSCF получает INVITE по интерфейсу ISC, он может видеть, что заголовок Route содержит имя его собственного узла и ODI, который соотносится с существующей входящей сессией для пользователя B. Это может быть использовано S-CSCF для анализа того, остались ли невыполненные iFC. (Отметим, что текущее поведение S-CSCF при получении INVITE с изменённым Request-URI состоит в прекращении обработки iFC и маршрутизации запроса на основе нового значения Request-URI.)
The process repeats itself. The INVITE is forwarded to the AS that is associated with this particular iFC. When the AS receives the initial INVITE request, it analyzes the request and determines that the session case is for a terminating registered user, then it determines the served user to be user C by looking at the Request- URI. This is clearly wrong, as the user being served is still user B.
Процесс повторяется. INVITE пересылается в AS, связанный с этим конкретным iFC. Когда AS получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к входящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь C, просматривая Request-URI. Это явно неверно, поскольку обслуживаемым пользователем по-прежнему является пользователь B.
This scenario clearly shows the problem that occurs when the Request- URI is overloaded with the meanings "intended target identity" and "served user" with the operation as described in Section 4.1. And it shows that this use case can not be realized without introducing a mechanism that conveys information about the served user from the S-CSCF to the AS. Use of the History-Info element does not solve this problem as it does not tell the AS which user is being served; it just presents a history of diversions that might not be even caused by the systems serving this particular user. A more detailed analysis on why the History-Info header field can't be used is provided in Appendix A.
Этот сценарий наглядно показывает проблему, возникающую, когда Request-URI перегружается смыслами «идентичность предполагаемой цели» и «обслуживаемый пользователь» при работе, описанной в разделе 4.1. И он показывает, что этот вариант использования не может быть реализован без введения механизма, передающего информацию об обслуживаемом пользователе от S-CSCF к AS. Использование элемента History-Info не решает эту проблему, поскольку он не сообщает AS, какой пользователь обслуживается; он лишь представляет историю перенаправлений, которые могут быть даже не вызваны системами, обслуживающими данного пользователя. Более подробный анализ того, почему поле заголовка History-Info не может использоваться, приведён в приложении A.
4.3. Diversion: Create New Originating Leg and Provide Originating iFC Processing
4.3. Переадресация: создать новое исходящее плечо вызова и обеспечить обработку исходящих iFC
Imagine a service scenario where a user B has a terminating service that diverts the call to a different destination. It is required that a forwarded call leg is handled as an originating call leg and that originating services for user B are executed. This means that this particular user has one or more iFC configured that are applicable for an outgoing initial request.
Представьте сценарий обслуживания, в котором у пользователя B есть входящая услуга, перенаправляющая вызов на другой пункт назначения. Требуется, чтобы переадресованное плечо вызова обрабатывалось как исходящее плечо вызова и чтобы для пользователя B были выполнены исходящие услуги. Это означает, что у данного пользователя настроено одно или несколько iFC, применимых к исходящему начальному запросу.
When the S-CSCF receives an initial INVITE request, it analyzes the request and determines that the session case is for a terminating registered user, then it determines the served user to be user B by looking at the Request-URI.
Когда S-CSCF получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к входящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь B, просматривая Request-URI.
Now the S-CSCF starts the iFC processing. The first iFC that matches the INVITE request causes the INVITE to be forwarded over the ISC interface to an AS that hosts user B's diversion service by adding the AS and S-CSCF's own hostnames to the Route header. The S-CSCF adds an Original Dialog Identifier (ODI) to the S-CSCF's own hostname on the Route header. This allows the S-CSCF to correlate an INVITE coming from an AS over the ISC interface to the existing session that forwarded the INVITE to the AS in the first place.
Теперь S-CSCF начинает обработку iFC. Первое iFC, соответствующее запросу INVITE, приводит к тому, что INVITE пересылается по интерфейсу ISC в AS, на котором размещена услуга перенаправления пользователя B, путём добавления имён узлов AS и самого S-CSCF в заголовок Route. S-CSCF добавляет идентификатор исходного диалога (Original Dialog Identifier, ODI) к имени своего узла в заголовке Route. Это позволяет S-CSCF соотнести INVITE, приходящий от AS по интерфейсу ISC, с существующей сессией, которая изначально переслала INVITE в AS.
When the AS receives the initial INVITE request, it analyzes the request and determines that the session case is for a terminating registered user, then it determines the served user to be user B by looking at the Request-URI. Based on some criteria, the diversion service concludes that the request needs to be diverted to another user or application C. It does this by changing the Request-URI to C. Optionally, it records the Request-URI history by using the History-Info header field (RFC 4244 [7]). Then the AS removes itself from the Route header. To make sure that the request is handled as a new originating call on behalf of user B, the AS adds the "orig" parameter to the topmost route header. Then it routes the INVITE request back to the S-CSCF by using this topmost Route header field.
Когда AS получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к входящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь B, просматривая Request-URI. На основании некоторых критериев услуга перенаправления приходит к выводу, что запрос необходимо перенаправить другому пользователю или приложению C. Она делает это, изменяя Request-URI на C. При необходимости она записывает историю Request-URI с помощью поля заголовка History-Info (RFC 4244 [7]). Затем AS удаляет себя из заголовка Route. Чтобы гарантировать, что запрос будет обработан как новый исходящий вызов от имени пользователя B, AS добавляет параметр «orig» в верхнее поле заголовка Route. Затем он маршрутизирует запрос INVITE обратно в S-CSCF, используя это верхнее поле заголовка Route.
When the S-CSCF receives the INVITE over the ISC interface, it can see that the topmost Route header contains its own hostname and an "orig" parameter. Because the topmost Route header contains the "orig" parameter, the S-CSCF concludes that the INVITE should be handled as if a call is originated by the served user. The served user is determined from the P-Asserted-Identity header to be user A. This is clearly wrong, as the user being served is and should be user B.
Когда S-CSCF получает INVITE по интерфейсу ISC, он может видеть, что верхнее поле заголовка Route содержит имя его собственного узла и параметр «orig». Поскольку верхнее поле заголовка Route содержит параметр «orig», S-CSCF делает вывод, что INVITE следует обрабатывать так, как если бы вызов исходил от обслуживаемого пользователя. Обслуживаемый пользователь определяется по заголовку P-Asserted-Identity как пользователь A. Это явно неверно, поскольку обслуживаемым пользователем является и должен быть пользователь B.
For the sake of discussion, let's assume that the S-CSCF can determine that the served user is user B. Then the procedure would continue as follows: The S-CSCF starts the originating iFC processing, the first iFC that matches the INVITE request causes the INVITE to be forwarded over the ISC interface to an AS that hosts an originating service of user B by adding the AS and S-CSCF's own hostnames to the Route header. The S-CSCF adds an Original Dialog Identifier (ODI) to the S-CSCF's own hostname on the Route header.
Ради обсуждения предположим, что S-CSCF может определить, что обслуживаемым пользователем является пользователь B. Тогда процедура продолжилась бы следующим образом: S-CSCF начинает обработку исходящих iFC, первое iFC, соответствующее запросу INVITE, приводит к тому, что INVITE пересылается по интерфейсу ISC в AS, на котором размещена исходящая услуга пользователя B, путём добавления имён узлов AS и самого S-CSCF в заголовок Route. S-CSCF добавляет идентификатор исходного диалога (ODI) к имени своего узла в заголовке Route.
The INVITE is forwarded to the AS that is associated with this particular iFC. When the AS receives the initial INVITE request, it analyzes the request and determines that the session case is for an originating registered user, then it determines the served user to be user A by looking at the P-Asserted-Identity. This is clearly wrong, as the user being served is and should be user B. This scenario clearly shows the problem that occurs when the P-Asserted-Identity is overloaded with the meanings "call originator" and "served user" with the operation as described in Section 4.1. And it shows that this use case can not be realized without introducing a mechanism that conveys information about the served user from the S-CSCF to the AS and from the AS to the S-CSCF. Use of the History-Info element does not solve this problem as it does not tell the AS which user is being served, but just presents a history of diversions that might not be even caused by the systems serving this particular user. A more detailed analysis on why the History- Info header field can't be used is provided in Appendix A.
INVITE пересылается в AS, связанный с этим конкретным iFC. Когда AS получает начальный запрос INVITE, он анализирует запрос и определяет, что случай сессии относится к исходящему зарегистрированному пользователю, а затем определяет, что обслуживаемым пользователем является пользователь A, просматривая P-Asserted-Identity. Это явно неверно, поскольку обслуживаемым пользователем является и должен быть пользователь B. Этот сценарий наглядно показывает проблему, возникающую, когда P-Asserted-Identity перегружается смыслами «инициатор вызова» и «обслуживаемый пользователь» при работе, описанной в разделе 4.1. И он показывает, что этот вариант использования не может быть реализован без введения механизма, передающего информацию об обслуживаемом пользователе от S-CSCF к AS и от AS к S-CSCF. Использование элемента History-Info не решает эту проблему, поскольку он не сообщает AS, какой пользователь обслуживается, а лишь представляет историю перенаправлений, которые могут быть даже не вызваны системами, обслуживающими данного пользователя. Более подробный анализ того, почему поле заголовка History-Info не может использоваться, приведён в приложении A.
4.4. Call Out of the Blue: on Behalf of User B, but Service Profile of Service Identity C
4.4. Вызов «из ниоткуда»: от имени пользователя B, но с профилем обслуживания идентичности службы C
There are services that need to be able to initiate a call, whereby the call appears to be coming from a user B but the service profile on behalf of service identity C needs to be executed in the S-CSCF.
Существуют услуги, которым необходимо иметь возможность инициировать вызов, причём вызов выглядит как исходящий от пользователя B, но в S-CSCF должен быть выполнен профиль обслуживания от имени идентичности службы C.
When a call needs to appear as coming from user B, that means that the P-Asserted-Identity needs to contain B's identity. This is because the Originating Identity Presentation (OIP) service as defined in 3GPP TS 24.173 [10] uses the P-Asserted-Identity to present the call originator. This makes sense because that is the main meaning expressed by the P-Asserted-Identity header field.
Когда вызов должен выглядеть как исходящий от пользователя B, это означает, что P-Asserted-Identity должен содержать идентичность B. Это связано с тем, что услуга представления идентичности исходящего вызова (Originating Identity Presentation, OIP), определённая в 3GPP TS 24.173 [10], использует P-Asserted-Identity для представления инициатора вызова. Это имеет смысл, поскольку именно таков основной смысл, выражаемый полем заголовка P-Asserted-Identity.
It is clear that no INVITE request can be constructed currently that would achieve both requirements expressed in the first paragraph, because the P-Asserted-Identity is overloaded with two meanings on the ISC interface. When the S-CSCF will receive this request, it will determine that the served user is user B, which is not what we want to achieve.
Ясно, что в настоящее время невозможно построить такой запрос INVITE, который удовлетворял бы обоим требованиям, выраженным в первом абзаце, поскольку на интерфейсе ISC P-Asserted-Identity перегружен двумя смыслами. Когда S-CSCF получит этот запрос, он определит, что обслуживаемым пользователем является пользователь B, а это не то, чего мы хотим добиться.
5. Requirements
5. Требования
This section lists the requirements derived from the previous scenarios:
В этом разделе перечислены требования, вытекающие из предыдущих сценариев:
1. To be able to offer real-world application services, it is required that the identity of the served user can be conveyed on the ISC interface (see 3GPP TS 23.218 [8]).
1. Чтобы иметь возможность предлагать прикладные услуги реального мира, требуется, чтобы идентичность обслуживаемого пользователя могла передаваться по интерфейсу ISC (см. 3GPP TS 23.218 [8]).
2. To be able to offer appropriate services to the served user, it is required that in addition to the served user identity the session case is conveyed.
2. Чтобы предоставлять обслуживаемому пользователю надлежащие услуги, требуется, чтобы в дополнение к идентичности обслуживаемого пользователя передавался случай сессии.
6. P-Served-User Header Field Definition
6. Определение поля заголовка P-Served-User
This document defines the SIP P-Served-User P-header. This header field can be added to initial requests for a dialog or standalone requests, which are routed between nodes in a Trust Domain for P-Served-User. The P-Served-User P-header contains an identity of the user that represents the served user. The "sescase" parameter may be used to convey whether the initial request is originated by or destined for the served user. The "regstate" parameter may be used to indicate whether the initial request is for a registered or unregistered user.
Настоящий документ определяет SIP P-заголовок P-Served-User. Это поле заголовка может добавляться к начальным запросам для диалога или к отдельным запросам, которые маршрутизируются между узлами в доверенном домене для P-Served-User. P-заголовок P-Served-User содержит идентичность пользователя, представляющего обслуживаемого пользователя. Параметр «sescase» может использоваться для передачи того, исходит ли начальный запрос от обслуживаемого пользователя или предназначен ему. Параметр «regstate» может использоваться для указания того, предназначен ли начальный запрос зарегистрированному или незарегистрированному пользователю.
The augmented Backus-Naur Form (BNF) (RFC 5234 [6]) syntax of the P-Served-User header field is as follows:
Расширенная синтаксическая нотация Бэкуса-Наура (BNF) (RFC 5234 [6]) для поля заголовка P-Served-User имеет следующий вид:
P-Served-User = "P-Served-User" HCOLON PServedUser-value *(SEMI served-user-param) served-user-param = sessioncase-param / registration-state-param / generic-param PServedUser-value = name-addr / addr-spec sessioncase-param = "sescase" EQUAL "orig" / "term" registration-state-param = "regstate" EQUAL "unreg" / "reg"
P-Served-User = "P-Served-User" HCOLON PServedUser-value *(SEMI served-user-param) served-user-param = sessioncase-param / registration-state-param / generic-param PServedUser-value = name-addr / addr-spec sessioncase-param = "sescase" EQUAL "orig" / "term" registration-state-param = "regstate" EQUAL "unreg" / "reg"
EQUAL, HCOLON, SEMI, name-addr, addr-spec, and generic-param are defined in RFC 3261 [2].
EQUAL, HCOLON, SEMI, name-addr, addr-spec и generic-param определены в RFC 3261 [2].
The following is an example of a P-Served-User header field:
Ниже приводится пример поля заголовка P-Served-User:
P-Served-User: <sip:user@example.com>; sescase=orig; regstate=reg
P-Served-User: <sip:user@example.com>; sescase=orig; regstate=reg
7. Proxy Behavior
7. Поведение прокси
7.1. Generating the P-Served-User Header
7.1. Формирование заголовка P-Served-User
Proxies that support the header MUST only insert the header in initial requests for a dialog or in standalone requests when the following conditions hold:
Прокси, поддерживающие этот заголовок, ДОЛЖНЫ вставлять заголовок только в начальные запросы для диалога или в отдельные запросы при соблюдении следующих условий:
o The proxy has the capability to determine the served user for the current request.
o Прокси имеет возможность определить обслуживаемого пользователя для текущего запроса.
o The next hop is part of the same Trust Domain for P-Served-User.
o Следующий узел является частью того же доверенного домена для P-Served-User.
When the above conditions do not hold, the proxy MUST NOT insert the header.
Если вышеуказанные условия не выполняются, прокси НЕ ДОЛЖЕН вставлять заголовок.
7.2. Consuming the P-Served-User Header
7.2. Обработка заголовка P-Served-User
A proxy that supports the header MUST, upon receiving from a trusted node the P-Served-User header in initial requests for a dialog or in standalone requests, take the value of the P-Served-User header to represent the served user in operations that require such information.
Прокси, поддерживающий этот заголовок, ДОЛЖЕН, получив от доверенного узла заголовок P-Served-User в начальных запросах для диалога или в отдельных запросах, принимать значение заголовка P-Served-User как представляющее обслуживаемого пользователя в операциях, требующих такой информации.
A proxy that supports the header MUST remove the header from requests or responses when the header was received from a node outside the Trust Domain for P-Served-User before further forwarding the message.
Прокси, поддерживающий этот заголовок, ДОЛЖЕН удалять заголовок из запросов или ответов, если заголовок был получен от узла за пределами доверенного домена для P-Served-User, перед дальнейшей пересылкой сообщения.
A proxy that supports the header MUST remove the header from requests or responses when the next hop is a node outside the Trust Domain for P-Served-User before further forwarding the message.
Прокси, поддерживающий этот заголовок, ДОЛЖЕН удалять заголовок из запросов или ответов, если следующий узел находится за пределами доверенного домена для P-Served-User, перед дальнейшей пересылкой сообщения.
8. Applicability
8. Применимость
According to RFC 3427 [5], P-headers have a limited applicability. Specifications of P-headers, such as this RFC, need to clearly document the useful scope of the proposal and explain its limitations and why it is not suitable for the general use of SIP on the Internet.
Согласно RFC 3427 [5], P-заголовки имеют ограниченную применимость. Спецификации P-заголовков, такие как настоящий RFC, должны чётко документировать полезную область применения предложения и объяснять его ограничения и причины, по которым оно не подходит для общего использования SIP в Интернете.
The use of the P-Served-User header field extensions is only applicable inside a Trust Domain for served user. Nodes in such a Trust Domain explicitly trust each other to convey the served user and to be responsible for withholding that information outside of the Trust Domain. The means by which the network determines the served user and the policies that are executed for a specific served user is outside the scope of this document.
Использование расширений поля заголовка P-Served-User применимо только внутри доверенного домена для обслуживаемого пользователя. Узлы такого доверенного домена явно доверяют друг другу в части передачи обслуживаемого пользователя и несут ответственность за нераскрытие этой информации за пределами доверенного домена. Способы, которыми сеть определяет обслуживаемого пользователя, и политики, выполняемые для конкретного обслуживаемого пользователя, находятся за рамками настоящего документа.
The served user information lacks an indication of who or what specifically determined the served user, and so it must be assumed that the Trust Domain determined the served user. Therefore, the information is only meaningful when securely received from a node known to be a member of the Trust Domain.
Информация об обслуживаемом пользователе не содержит указания на то, кто или что конкретно определило обслуживаемого пользователя, поэтому следует предполагать, что обслуживаемого пользователя определил доверенный домен. Следовательно, эта информация имеет смысл только тогда, когда она безопасно получена от узла, известного как член доверенного домена.
Because the served user typically only has validity in one administrative domain, it is in general not suitable for inter-domain use or use in the Internet at large.
Поскольку обслуживаемый пользователь обычно имеет силу только в одном административном домене, он, как правило, не подходит для междоменного использования или использования в Интернете в целом.
Despite these limitations, there are sufficiently useful specialized deployments that meet the assumptions described above, and that can accept the limitations that result, to warrant informational publication of this mechanism. An example deployment would be a closed network like 3GPP IMS.
Несмотря на эти ограничения, существует достаточно много полезных специализированных развёртываний, которые соответствуют описанным выше допущениям и могут принять вытекающие из них ограничения, что оправдывает информационную публикацию этого механизма. Примером развёртывания является закрытая сеть, такая как 3GPP IMS.

9. Вопросы IANA
This document defines a new SIP header field: P-Served-User. This header field has been registered by the IANA in the SIP Parameters registry under the Header Fields subregistry.
Настоящий документ определяет новое поле заголовка SIP: P-Served-User. Это поле заголовка зарегистрировано IANA в реестре параметров SIP в подреестре полей заголовков.
10. Security Considerations
10. Вопросы безопасности
The P-Served-User header field defined in this document is to be used in an environment where elements are trusted and where attackers are not supposed to have access to the protocol messages between those elements. Traffic protection between network elements is sometimes achieved by using IPsec and sometimes by physically protecting the network. In any case, the environment where the P-Served-User header field will be used ensures the integrity and the confidentiality of the contents of this header field.
Поле заголовка P-Served-User, определённое в настоящем документе, предназначено для использования в среде, где элементы являются доверенными и где предполагается, что злоумышленники не имеют доступа к протокольным сообщениям между этими элементами. Защита трафика между сетевыми элементами иногда достигается с помощью IPsec, а иногда путём физической защиты сети. В любом случае среда, в которой будет использоваться поле заголовка P-Served-User, обеспечивает целостность и конфиденциальность содержимого этого поля заголовка.
The Spec(T) that defines the Trust Domain for P-Served-User MUST require that member nodes understand the P-Served-User header extension.
Spec(T), определяющий доверенный домен для P-Served-User, ДОЛЖЕН требовать, чтобы входящие в него узлы понимали расширение заголовка P-Served-User.
There is a security risk if a P-Served-User header field is allowed to propagate out of the Trust Domain where it was generated. In that case, user-sensitive information would be revealed. To prevent such a breach from happening, proxies MUST NOT insert the header when forwarding requests to a hop that is located outside the Trust Domain. When forwarding the request to a node in the Trust Domain, proxies MUST NOT insert the header unless they have sufficient knowledge that the route set includes another proxy in the Trust Domain that understands the header, such as the home proxy. There is no automatic mechanism to learn the support for this specification. Proxies MUST remove the header when forwarding requests to nodes that are not in the Trust Domain or when the proxy does not have knowledge of any other proxy included in the route set that will remove it before it is routed to any node that is not in the Trust Domain.
Существует риск безопасности, если полю заголовка P-Served-User разрешено распространяться за пределы доверенного домена, в котором оно было создано. В этом случае была бы раскрыта чувствительная информация о пользователе. Чтобы предотвратить такое нарушение, прокси НЕ ДОЛЖНЫ вставлять заголовок при пересылке запросов следующему узлу, находящемуся за пределами доверенного домена. При пересылке запроса узлу в доверенном домене прокси НЕ ДОЛЖНЫ вставлять заголовок, если только они не обладают достаточными знаниями о том, что набор маршрутов включает другой прокси в доверенном домене, который понимает этот заголовок, например домашний прокси. Не существует автоматического механизма для изучения поддержки этой спецификации. Прокси ДОЛЖНЫ удалять заголовок при пересылке запросов узлам, которые не находятся в доверенном домене, или когда прокси не знает о каком-либо другом прокси, включённом в набор маршрутов, который удалит его до того, как он будет маршрутизирован какому-либо узлу, не находящемуся в доверенном домене.

Appendix A. Why the History-Info Header Is Not Suitable to Convey the Served User Information on the ISC Interface
Приложение A. Почему заголовок History-Info не подходит для передачи информации об обслуживаемом пользователе на интерфейсе ISC
A.1. Semantics
A.1. Семантика
The History-Info (as specified in RFC 4244 [7]) holds a record of subsequent Request-URI values that are put on an initial request during its processing in the network.
History-Info (как определено в RFC 4244 [7]) содержит запись последующих значений Request-URI, которые помещаются в начальный запрос во время его обработки в сети.
If it would be possible at all to use the History-Info header for the purpose of communicating the served user, then again the same overloading would occur as the one that we are trying to get rid of (Section 4.2). In this case, we overload the particular History-Info header field's hi-entry with the meaning "historic target identity" and "served user".
Если бы вообще было возможно использовать заголовок History-Info для передачи обслуживаемого пользователя, то снова возникла бы та же перегрузка, от которой мы пытаемся избавиться (раздел 4.2). В этом случае мы перегружаем hi-entry конкретного поля заголовка History-Info смыслами «историческая идентичность цели» и «обслуживаемый пользователь».
Another reason that the History-Info header can not solve the requirements as expressed in this document is that, in originating session case scenarios, the served user is currently determined from the P-Asserted-Identity, as that header field contains the asserted originating user's identity. The History-Info header, being a record of Request-URIs, can never be a solution for this case.
Ещё одна причина, по которой заголовок History-Info не может решить требования, выраженные в настоящем документе, состоит в том, что в сценариях исходящего случая сессии обслуживаемый пользователь в настоящее время определяется по P-Asserted-Identity, поскольку это поле заголовка содержит утверждаемую идентичность исходящего пользователя. Заголовок History-Info, будучи записью Request-URI, никогда не сможет стать решением для этого случая.
Looking at the call-out-of-the-blue scenario (Section 4.4), it is impossible to construct a History-Info header for an INVITE request on behalf of user C that appears to come from user B and targets user D that would express the served user C without violating the original semantics of the History-Info header according to (RFC 4244 [7]).
Рассматривая сценарий вызова «из ниоткуда» (раздел 4.4), невозможно построить заголовок History-Info для запроса INVITE от имени пользователя C, который выглядит исходящим от пользователя B и направлен пользователю D, чтобы он выражал обслуживаемого пользователя C, не нарушая исходной семантики заголовка History-Info согласно (RFC 4244 [7]).
A.2. Additional Observations
A.2. Дополнительные замечания
The purpose of the History-Info header is a header that has an end- to-end application. For the purpose of informing an AS on the ISC interface, this is overkill.
Назначение заголовка History-Info — быть заголовком, имеющим сквозное применение. Для целей информирования AS на интерфейсе ISC это избыточно.
At the moment that the AS receives an initial INVITE over the ISC interface, this INVITE may have passed a vast number of proxies that may or may not have added history information. On top of that, the request may have traversed several AS instances for the same served user. In case several subsequent iFC are active, all these AS instances may perform a forwarding. This means that it is not possible to define an algorithm that points out which hi-entry of a History-Info header should represent the served user. In other words, a History-Info header field with n entries expresses a branch of depth n. Any or none of these elements could be the served user identity. The History-Info header does not comply with the second requirement as expressed in Section 5, as it does not have a means to express the session case in a natural way.
В момент, когда AS получает начальный INVITE по интерфейсу ISC, этот INVITE мог пройти через огромное количество прокси, которые могли добавить или не добавить информацию истории. Вдобавок запрос мог пройти через несколько экземпляров AS для одного и того же обслуживаемого пользователя. В случае, когда активно несколько последующих iFC, все эти экземпляры AS могут выполнять перенаправление. Это означает, что невозможно определить алгоритм, указывающий, какая hi-entry заголовка History-Info должна представлять обслуживаемого пользователя. Иными словами, поле заголовка History-Info с n записями выражает ветвь глубиной n. Любой из этих элементов или ни один из них может быть идентичностью обслуживаемого пользователя. Заголовок History-Info не соответствует второму требованию, выраженному в разделе 5, поскольку не имеет средства естественным образом выразить случай сессии.
A.3. Conclusion
A.3. Заключение
Each observation in the previous subsections, alone, is enough to disregard the History-Info header as an information element that is suitable for transporting the served user information over the ISC interface.
Каждое замечание в предыдущих подразделах само по себе достаточно, чтобы отвергнуть заголовок History-Info как информационный элемент, подходящий для переноса информации об обслуживаемом пользователе по интерфейсу ISC.
Note that this does not prohibit the use of the P-Served-User header and the History-Info header in the same request. In fact that will be a quite likely scenario for network-based diversion services like, for example, the Communication Diversion service as specified in (3GPP TS 24.173 [10]).
Отметим, что это не запрещает использование заголовка P-Served-User и заголовка History-Info в одном и том же запросе. Фактически это будет вполне вероятным сценарием для сетевых услуг перенаправления, таких как, например, услуга перенаправления связи (Communication Diversion), определённая в (3GPP TS 24.173 [10]).
