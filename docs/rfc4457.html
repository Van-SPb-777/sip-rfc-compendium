Abstract
Аннотация
This document specifies the Session Initiation Protocol (SIP) P-User-Database Private-Header (P-header). This header field is used in the 3rd-Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) to provide SIP registrars and SIP proxy servers with the address of the database that contains the user profile of the user that generated a particular request.
В этом документе указан протокол инициирования сессий (SIP) P-User-Database Private-Header (P-header). Это поле заголовка используется в IMS (IP Multimedia Subsystem) проекта партнерства 3-го поколения (3GPP) для предоставления регистраторам SIP и прокси SIP адреса базы данных, содержащей профиль пользователя, сгенерировавшего конкретный запрос.
1. Introduction
1. Введение
The 3rd-Generation Partnership Project (3GPP) IMS (IP Multimedia Subsystem) uses the Session Initiation Protocol (SIP) [2] as its main signalling protocol. (For more information on the IMS, a detailed description can be found in 3GPP TS 23.228 [5] and 3GPP TS 24.229 [6].) 3GPP has identified a set of requirements that can be met, according to the procedures in RFC 3427 [3], by defining a new SIP Private-Header (P-header).
Проект партнерства третьего поколения (3GPP) IMS (IP-мультимедийная подсистема) использует протокол инициирования сессий (SIP) [2] в качестве основного протокола сигнализации. (Для получения дополнительной информации о IMS подробное описание можно найти в 3GPP TS 23.228 [5] и 3GPP TS 24.229 [6].) 3GPP определил набор требований, которые могут быть выполнены в соответствии с процедурами в RFC 3427 [3] путем определения нового SIP Private-Header (P-header).
The remainder of this document is organized as follows. Section 2 describes the scenarios considered by 3GPP and Section 3 discusses the requirements derived from these scenarios. Section 4 defines the P-User-Database header field, which meets those requirements, and Section 5 discusses the applicability and scope of this new header field. Section 6 registers the P-User-Database header field with the IANA and Section 7 discusses the security properties of the environment where this header field is intended to be used.
Оставшаяся часть этого документа организована следующим образом. В разделе 2 описаны сценарии, рассматриваемые 3GPP, а в разделе 3 обсуждаются требования, вытекающие из этих сценариев. В разделе 4 определяется поле заголовка P-User-Database, которое соответствует этим требованиям, а в разделе 5 обсуждаются применимость и область применения этого нового поля заголовка. В разделе 6 поле заголовка P-User-Database регистрируется в IANA, а в разделе 7 обсуждаются свойства безопасности среды, в которой это поле заголовка предназначено для использования.
2. Scenarios
2. Сценарии
In the 3GPP IMS, there are two scenarios where a set of proxies handling a request need to consult the same user database. These scenarios consist of a user registering to the IMS network and an unregistered user receiving an incoming request that triggers a service (e.g., a voice mail service).
В IMS 3GPP существует два сценария, когда набору прокси, обрабатывающих запрос, необходимо обращаться к одной и той же базе данных пользователей. Эти сценарии состоят из регистрации пользователя в сети IMS и незарегистрированного пользователя, получающего входящий запрос, который запускает службу (например, служба голосовой почты).
2.1. User Registering to the IMS
2.1. Регистрация пользователя в IMS
In the 3GPP IMS, SIP REGISTER requests generated by a User Agent (UA) traverse a set of SIP proxy servers before reaching the SIP registrar. A REGISTER request sent by a UA is routed to the outbound proxy of the UA, which is referred to as the P-CSCF (Proxy- Call/Session Control Function).
В IMS 3GPP запросы SIP REGISTER, генерируемые агентом пользователя (UA), проходят через набор прокси SIP, прежде чем достичь регистратора SIP. Запрос REGISTER, отправленный UA, направляется на исходящий прокси UA, который называется P-CSCF (функция управления вызовами/сессиями прокси).
The P-CSCF routes the REGISTER request to another proxy, which is referred to as the I-CSCF (Interrogating-CSCF) and is always located in the home domain of the user. The I-CSCF consults the user database of the domain, which is referred to as the Home Subscriber Server (HSS), in order to choose the registrar that will process the REGISTER request.
P-CSCF направляет запрос REGISTER на другой прокси, который называется I-CSCF (Interrogating-CSCF) и всегда находится в домашнем домене пользователя. I-CSCF обращается к базе данных пользователей домена, которая называется домашним сервером подписчиков (HSS), чтобы выбрать регистратора, который будет обрабатывать запрос REGISTER.
With the information received from the HSS, the I-CSCF routes the REGISTER request to the appropriate registrar, which is referred to as the S-CSCF (Serving-CSCF). At this point, the S-CSCF needs to contact the same HSS that was previously contacted by the I-CSCF in order to fetch the user profile of the user that generated the REGISTER request. The interface between the I-CSCF and the HSS and between the S-CSCF and the HSS is called Cx interface and is based on Diameter [4].
Используя информацию, полученную от HSS, I-CSCF направляет запрос REGISTER соответствующему регистратору, который называется S-CSCF (Serving-CSCF). На этом этапе S-CSCF необходимо связаться с тем же HSS, к которому ранее обращался I-CSCF, чтобы получить профиль пользователя, сгенерировавшего запрос REGISTER. Интерфейс между I-CSCF и HSS, а также между S-CSCF и HSS называется интерфейсом Cx и основан на диаметре [4].
When there is a single HSS (i.e., user database) handling all the users in the domain, both the I-CSCF and the S-CSCF can be configured with its address so that they contact it when necessary. However, some domains have several HSSs, each of which handles a particular set of users. When dealing with a REGISTER request, the I-CSCF and the S-CSCF need to discover which is the HSS that contains the profile of the user that generated the REGISTER request.
Когда существует один HSS (то есть, база данных пользователей), обслуживающий всех пользователей в домене, как I-CSCF, так и S-CSCF можно настроить с использованием его адреса, чтобы они могли обращаться к нему при необходимости. Однако в некоторых доменах имеется несколько HSS, каждый из которых обслуживает определенный набор пользователей. При работе с запросом REGISTER I-CSCF и S-CSCF необходимо определить, какой HSS содержит профиль пользователя, сгенерировавшего запрос REGISTER.
In networks with more than one HSS, a Diameter redirect agent referred to as the Subscription Locator Function (SLF) is implemented. The interface between the I-CSCF and the SLF and between the S-CSCF and the SLF is called Dx interface and, like the CX interface, is based on Diameter. The SLF provides the I-CSCF and the S-CSCF with the address of the HSS that handles the user they are dealing with.
В сетях с более чем одним HSS реализован агент перенаправления Diameter, называемый функцией локатора подписки (SLF). Интерфейс между I-CSCF и SLF, а также между S-CSCF и SLF называется интерфейсом Dx и, как и интерфейс CX, основан на диаметре. SLF предоставляет I-CSCF и S-CSCF адрес HSS, который обслуживает пользователя, с которым они имеют дело.
Therefore, in a network with more than one HSS, the SLF is consulted twice per REGISTER request, first by the I-CSCF, and later by the S-CSCF. If the I-CSCF could provide the S-CSCF with the address of the HSS handling the user that generated the REGISTER request, the S-CSCF could contact directly that HSS. That is, the S-CSCF would not need to contact the SLF in order to obtain the address of the HSS.
Таким образом, в сети с более чем одним HSS к SLF обращаются дважды за запрос REGISTER, сначала по I-CSCF, а затем по S-CSCF. Если бы I-CSCF мог предоставить S-CSCF адрес HSS, обслуживающего пользователя, сгенерировавшего запрос REGISTER, S-CSCF мог бы напрямую связаться с этим HSS. То есть S-CSCF не нужно будет связываться с SLF, чтобы получить адрес HSS.
2.2. Incoming Request for an Unregistered User
2.2. Входящий запрос от незарегистрированного пользователя
In the 3GPP IMS, incoming requests for a user traverse an I-CSCF in the home domain of the user. This I-CSCF consults the HSS, using the Diameter-based Cx interface, in order to decide which S-CSCF should handle the request. After consulting the HSS, the I-CSCF forwards the request to a S-CSCF, which is also located in the home domain of the user.
В IMS 3GPP входящие запросы пользователя проходят через I-CSCF в домашнем домене пользователя. Этот I-CSCF консультируется с HSS, используя интерфейс Diameter-based Cx, чтобы решить, какой S-CSCF должен обрабатывать запрос. После консультации с HSS I-CSCF перенаправляет запрос на S-CSCF, который также находится в домашнем домене пользователя.
If the user the request is addressed to is registered to the IMS network, the S-CSCF receiving the request knows which HSS handles the user. The S-CSCF stored this information when the user registered. However, if the user is not registered, the S-CSCF needs to consult the SLF (assuming more than one HSS in the network) in order to discover the HSS handling the user. Therefore, like in the previous scenario, in a network with more than one HSS, the SLF is consulted twice per incoming request addresses to an unregistered user. First by the I-CSCF, and later by the S-CSCF. If the I-CSCF could provide the S-CSCF with the address of the HSS handling the user that generated the request, the S-CSCF could contact directly that HSS. That is, the S-CSCF would not need to contact the SLF in order to obtain the address of the HSS.
Если пользователь, которому адресован запрос, зарегистрирован в сети IMS, S-CSCF, получающий запрос, знает, какой HSS обрабатывает пользователя. S-CSCF сохранил эту информацию при регистрации пользователя. However, if the user is not registered, the S-CSCF needs to consult the SLF (assuming more than one HSS in the network) in order to discover the HSS handling the user. Therefore, like in the previous scenario, in a network with more than one HSS, the SLF is consulted twice per incoming request addresses to an unregistered user. Сначала с помощью I-CSCF, а затем с помощью S-CSCF. If the I-CSCF could provide the S-CSCF with the address of the HSS handling the user that generated the request, the S-CSCF could contact directly that HSS. То есть S-CSCF не нужно будет связываться с SLF, чтобы получить адрес HSS.
3. Requirements
3. Требования
This section lists the requirements derived from the previous scenarios:
В этом разделе перечислены требования, вытекающие из предыдущих сценариев:
1. It is necessary to optimize the registration process in the 3GPP IMS by reducing the time it takes for a UA to register to the IMS network.
1. Необходимо оптимизировать процесс регистрации в 3GPP IMS за счет сокращения времени регистрации UA в сети IMS.
2. It is necessary to optimize the handling of incoming requests to unregistered users in the 3GPP IMS by reducing the time it takes for a domain to handle these requests.
2. Необходимо оптимизировать обработку входящих запросов к незарегистрированным пользователям в 3GPP IMS за счет сокращения времени обработки доменом этих запросов.
3. It is necessary to improve the scalability of SLFs in the 3GPP IMS by reducing the amount of traffic the SLF of a network needs to handle.
3. Необходимо улучшить масштабируемость SLF в IMS 3GPP за счет уменьшения объема трафика, который должен обрабатывать SLF сети.
4. P-User-Database Header Field Definition
4. P-User-Database Определение поля заголовка
This document defines the SIP P-User-Database P-header. This header field can be added to requests routed from an I-CSCF to an S-CSCF. The P-User-Database P-header contains the address of the HSS handling the user that generated the request.
Этот документ определяет SIP P-User-Database P-header. Это поле заголовка можно добавить к запросам, маршрутизируемым от I-CSCF к S-CSCF. P-User-Database P-header содержит адрес HSS, обрабатывающего пользователя, сгенерировавшего запрос.
The augmented Backus-Naur Form (BNF) [1] syntax of the P-User- Database header field is the following:
Расширенный синтаксис формы Backus-Naur (BNF) [1] поля заголовка P-User- База данных следующий:
P-User-Database = "P-User-Database" HCOLON database *( SEMI generic-param ) database = LAQUOT DiameterURI RAQUOT
P-User-Database = "P-User-Database" HCOLON database *( SEMI generic-param ) database = LAQUOT DiameterURI RAQUOT
DiameterURI is defined in RFC 3588 [4]. HCOLON, LAQUOT, RAQUOT, and generic-param are defined in RFC 3261 [2].
DiameterURI определен в RFC 3588 [4]. HCOLON, LAQUOT, RAQUOT и generic-param определены в RFC 3261 [2].
The following is an example of a P-User-Database header field:
Ниже приведен пример поля заголовка P-User-Database:
P-User-Database: <aaa://host.example.com;transport=tcp>
P-User-Database: <aaa://host.example.com;transport=tcp>
5. Applicability
5. Применимость
According to RFC 3427 [3], P-headers have a limited applicability. Specifications of P-headers such as this RFC need to clearly document the useful scope of the proposal, and explain its limitations and why it is not suitable for the general use of SIP on the Internet.
Согласно RFC 3427 [3], P-headers имеют ограниченную применимость. Спецификации P-headers, такие как этот RFC, должны четко документировать полезный объем предложения, а также объяснять его ограничения и причины, по которым оно не подходит для общего использования SIP в Интернете.
The P-User-Database header field is intended to be used in 3GPP IMS networks. This header field carries the address of a user database, which is referred to as HSS, between two proxies, which are referred to as I-CSCF and S-CSCF. The I-CSCF and the S-CSCF belong to the same administrative domain and share a common frame of reference to the user database. The I-CSCF inserts the P-User-Database header field into a SIP request and the S-CSCF removes it before routing the request further.
Поле заголовка P-User-Database предназначено для использования в сетях 3GPP IMS. Это поле заголовка содержит адрес пользовательской базы данных, которая называется HSS, между двумя прокси, которые называются I-CSCF и S-CSCF. I-CSCF и S-CSCF принадлежат одному и тому же административному домену и имеют общую систему отсчета для базы данных пользователей. I-CSCF вставляет поле заголовка P-User-Database в SIP-запрос, а S-CSCF удаляет его перед дальнейшей маршрутизацией запроса.
When SIP is used on the Internet, there are typically no proxies querying a user database between the UA sending a REGISTER request and the registrar. Consequently, the P-User-Database header field does not seem useful in a general Internet environment.
Когда SIP используется в Интернете, между UA, отправляющим запрос REGISTER, и регистратором обычно нет прокси, запрашивающих базу данных пользователей. Следовательно, поле заголовка P-User-Database не кажется полезным в обычной среде Интернета.
6. IANA Considerations
6. Вопросы IANA
This document defines a new SIP header field: P-User-Database. This header field has been registered by the IANA in the SIP Parameters registry under the Header Fields subregistry.
Этот документ определяет новое поле заголовка SIP: P-User-Database. Это поле заголовка зарегистрировано IANA в реестре параметров SIP в подреестре полей заголовка.
7. Security Considerations
7. Вопросы безопасности
The P-User-Database defined in this document is to be used in an environment where elements are trusted and where attackers are not supposed to have access to the protocol messages between those elements. Traffic protection between network elements is sometimes achieved by using IP Security (IPsec) and sometimes by physically protecting the network. In any case, the environment where the P-User-Database header field will be used ensures the integrity and the confidentiality of the contents of this header field.
P-User-Database, определенный в этом документе, должен использоваться в среде, где элементы являются доверенными и где злоумышленники не должны иметь доступа к сообщениям протокола между этими элементами. Защита трафика между элементами сети иногда достигается за счет использования IP-безопасности (IPsec), а иногда за счет физической защиты сети. В любом случае среда, в которой будет использоваться поле заголовка P-User-Database, обеспечивает целостность и конфиденциальность содержимого этого поля заголовка.
There is a slight security risk if a P-User-Database header field is allowed to propagate out of the administrative domain where it was generated. No user-sensitive information would be revealed by such a breach, but this could result in disclosure of information about the topology of the operator network that goes beyond the level of disclosure explicit in SIP messages without this extension. Consequently, operators need to ensure that the P-User-Database header field is removed from requests before these are sent to another administrative domain.
Существует небольшой риск для безопасности, если разрешено распространение поля заголовка P-User-Database за пределы административного домена, в котором оно было создано. Никакая конфиденциальная информация пользователя не будет раскрыта в результате такого нарушения, но это может привести к раскрытию информации о топологии сети оператора, которая выходит за рамки уровня раскрытия, явного в сообщениях SIP без этого расширения. Следовательно, операторам необходимо убедиться, что поле заголовка P-User-Database удалено из запросов, прежде чем они будут отправлены в другой административный домен.
