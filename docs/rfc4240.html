Abstract
Аннотация
In SIP-based networks, there is a need to provide basic network media services. Such services include network announcements, user interaction, and conferencing services. These services are basic building blocks, from which one can construct interesting applications. In order to have interoperability between servers offering these building blocks (also known as Media Servers) and application developers, one needs to be able to locate and invoke such services in a well defined manner.
В сетях SIP-based необходимо предоставлять базовые сетевые медиа-услуги. К таким услугам относятся сетевые объявления, взаимодействие с пользователем и услуги конференц-связи. Эти сервисы являются основными строительными блоками, из которых можно создавать интересные приложения. Чтобы обеспечить взаимодействие между серверами, предлагающими эти строительные блоки (также известными как медиа-серверы), и разработчиками приложений, необходимо иметь возможность находить и вызывать такие службы четко определенным образом.
This document describes a mechanism for providing an interoperable interface between Application Servers, which provide application services to SIP-based networks, and Media Servers, which provide the basic media processing building blocks.
В этом документе описывается механизм обеспечения интероперабельного интерфейса между серверами приложений, которые предоставляют службы приложений сетям SIP-based, и медиа-серверами, которые предоставляют базовые строительные блоки обработки мультимедиа.
1. Overview
1. Обзор
In SIP-based media networks (RFC 3261 [10]), there is a need to provide basic network media services. Such services include playing announcements, initiating a media mixing session (conference), and prompting and collecting information with a user.
В медиасетях SIP-based (RFC 3261 [10]) существует необходимость предоставления базовых сетевых медиауслуг. Такие услуги включают в себя воспроизведение объявлений, инициацию сессии микширования мультимедиа (конференции), а также подсказку и сбор информации у пользователя.
These services are basic in nature, are few in number, and fundamentally have not changed in 25 years of enhanced telephony services. Moreover, given their elemental nature, one would not expect them to change in the future.
Эти услуги носят базовый характер, немногочисленны и принципиально не изменились за 25 лет развития расширенных телефонных услуг. Более того, учитывая их стихийную природу, нельзя ожидать, что они изменятся в будущем.
Multifunction media servers provide network media services to clients using server protocols such as SIP, often in conjunction with markup languages such as VoiceXML [20] and MSCML [21]. This document describes how to identify to a multifunction media server what sort of session the client is requesting, without modifying the SIP protocol.
Многофункциональные медиасерверы предоставляют клиентам сетевые медиасервисы с использованием серверных протоколов, таких как SIP, часто в сочетании с такими языками разметки, как VoiceXML [20] и MSCML [21]. В этом документе описывается, как определить для многофункционального медиа-сервера тип сессии, который запрашивает клиент, без изменения протокола SIP.
It is critically important to note that the mechanism described here in no way modifies the SIP protocol, the meaning, or definition of a SIP Request URI, or does it put any restrictions, in any way, on devices that do not implement this convention. Announcements are media played to the user. Announcements can be static media files, media files generated in real-time, media streams generated in real-time, multimedia objects, or combinations of the above.
Крайне важно отметить, что описанный здесь механизм никоим образом не изменяет протокол SIP, значение или определение URI запроса SIP и не накладывает каких-либо ограничений на устройства, которые не реализуют это соглашение. Объявления представляют собой медиафайлы, воспроизводимые пользователю. Объявления могут представлять собой статические медиафайлы, медиафайлы, созданные в реальном времени, медиапотоки, созданные в реальном времени, мультимедийные объекты или комбинации вышеперечисленного.
Media mixing is the act of mixing different RTP streams, as described in RFC 3550 [13]. Note that the service described here suffices for simple mixing of media for a basic conferencing service. This service does not address enhanced conferencing services, such as floor control, gain control, muting, subconferences, etc. MSCML [21] addresses enhanced conferencing. However, that is beyond the scope of this document. Interested readers should read conferencing- framework [22] for details on the IETF SIP conferencing framework.
Микширование мультимедиа — это процесс смешивания различных потоков RTP, как описано в RFC 3550 [13]. Обратите внимание, что описанной здесь услуги достаточно для простого смешивания носителей для базовой услуги конференц-связи. Эта услуга не предназначена для расширенных услуг конференц-связи, таких как управление громкостью, регулировка усиления, отключение звука, дополнительные конференции и т. д. MSCML [21] предназначен для расширенной конференц-связи. Однако это выходит за рамки данного документа. Заинтересованным читателям следует прочитать Conference Framework [22] для получения подробной информации о платформе конференц-связи IETF SIP.
Prompt and collect is where the server prompts the user for some information, as in an announcement, and then collects the user's response. This can be a one-step interaction, for example by playing an announcement, "Please enter your pass code", followed by collecting a string of digits. It can also be a more complex interaction, specified, for example, by VoiceXML [20] or MSCML [21].
Запрос и сбор — это когда сервер запрашивает у пользователя некоторую информацию, как в объявлении, а затем собирает ответ пользователя. Это может быть одноэтапное взаимодействие, например, воспроизведение объявления «Пожалуйста, введите свой код доступа» с последующим сбором строки цифр. Это также может быть более сложное взаимодействие, заданное, например, VoiceXML [20] или MSCML [21].

2. Mechanism
2. Механизм
In the context of SIP control of media servers, we take advantage of the fact that the standard SIP URI has a user part. Multifunction media servers do not have users. Thus we use the user address, or the left-hand-side of the URI, as a service indicator.
В контексте SIP-управления медиасерверами мы воспользуемся тем, что стандартный SIP URI имеет пользовательскую часть. Многофункциональные медиасерверы не имеют пользователей. Таким образом, мы используем адрес пользователя или левую часть URI в качестве индикатора обслуживания.
The use of the user part of the SIP Request URI has a number of useful properties:
Использование пользовательской части URI SIP-запроса имеет ряд полезных свойств:
o There is no change to core SIP. o Only devices that choose to conform to this standard have to implement it.
o Базовый SIP не изменяется. o Только устройства, которые решили соответствовать этому стандарту, должны его реализовать.
o This document only applies to multifunction SIP-controlled media
o Этот документ относится только к многофункциональным носителям SIP-controlled
servers.
servers.
o This document has no impact on non-multifunction SIP-controlled media servers.
o Этот документ не влияет на немногофункциональные SIP-controlled медиасерверы.
o The mechanism described in this document has absolutely no impact on SIP devices other than media servers.
o Механизм, описанный в этом документе, абсолютно не влияет на устройства SIP, кроме медиасерверов.
The last bullet point is crucial. In particular, the user part convention described here places absolutely no restrictions on any SIP user agent, proxy, back-to-back user agent (B2BUA), or any future device. The user parts defined here only apply to multifunction media servers that chose to implement the convention. With the exception of a conforming media server, these user names and conventions have no impact on the user part namespace. They do not restrict the use of these user names at devices other than a multifunction media server.
Последний пункт имеет решающее значение. В частности, описанное здесь соглашение о пользовательской части не накладывает абсолютно никаких ограничений на любой пользовательский агент SIP, прокси, параллельный пользовательский агент (B2BUA) или любое будущее устройство. Определенные здесь пользовательские части применяются только к многофункциональным медиасерверам, которые решили реализовать это соглашение. За исключением соответствующего медиа-сервера, эти имена пользователей и соглашения не влияют на пространство имен пользовательской части. Они не ограничивают использование этих имен пользователей на устройствах, отличных от многофункционального медиа-сервера.
Note that the set of services is small, well defined, and well contained. The section The User Part (Section 7) discusses the issues with using a fixed set of user-space names.
Обратите внимание, что набор сервисов невелик, четко определен и хорошо содержателен. В разделе «Пользовательская часть» (раздел 7) обсуждаются проблемы использования фиксированного набора имен пользовательского пространства.
For per-service security, the media server SHOULD use the security protocols described in RFC 3261 [10].
Для обеспечения безопасности каждой службы медиасервер ДОЛЖЕН использовать протоколы безопасности, описанные в RFC 3261 [10].
The media server MAY issue 401 challenges for authentication. The media server SHOULD support the sips: scheme for the announcement service. The media server MUST support the sips: scheme for the dialog and conference services. The level of authentication to require for each service is a matter of local policy.
Медиа-сервер МОЖЕТ выдать 401 запрос для аутентификации. Медиа-сервер ДОЛЖЕН поддерживать схему sips: для службы объявлений. Медиасервер ДОЛЖЕН поддерживать схему sips: для служб диалога и конференций. Уровень аутентификации, требуемый для каждой службы, определяется местной политикой.
The media server, upon receiving an INVITE, notes the service indicator. Depending on the service indicator, the media server will either honor the request or return a failure response code.
Медиа-сервер после получения INVITE отмечает индикатор обслуживания. В зависимости от индикатора обслуживания медиасервер либо удовлетворит запрос, либо вернет код ответа об ошибке.
The service indicator is the concatenation of the service name and an optional service instance identifier, separated by an equal sign.
Индикатор службы представляет собой объединение имени службы и необязательного идентификатора экземпляра службы, разделенных знаком равенства.
Per RFC 3261 [10], the service indicator is case insensitive. The service name MUST be from the set alphanumeric characters plus dash (US-ASCII %2C). The service name MUST NOT include an equal sign (US-ASCII %3D).
Согласно RFC 3261 [10] индикатор службы нечувствителен к регистру. Имя службы ДОЛЖНО состоять из набора буквенно-цифровых символов плюс дефис (US-ASCII %2C). Имя службы НЕ ДОЛЖНО содержать знак равенства (US-ASCII %3D).
The service name MAY have long- and short-forms, as SIP does for headers.
Имя службы МОЖЕТ иметь длинную и краткую формы, как SIP для заголовков.
A given service indicator MAY have an associated set of parameters. Such parameters MUST follow the convention set out for SIP URI parameters. That is, a semi-colon separated list of keyword=value pairs.
Данный индикатор услуги МОЖЕТ иметь связанный набор параметров. Такие параметры ДОЛЖНЫ соответствовать соглашению, установленному для параметров SIP URI. То есть список пар ключевое слово=значение, разделенный точкой с запятой.
Certain services may have an association with a unique service instance on the media server. For example, a given media server can host multiple, separate conference sessions. To identify unique service instances, a unique identifier modifies the service name. The unique identifier MUST meet the rules for a legal user part of a SIP URI. An equal sign, US-ASCII %3D, MUST separate the service indicator from the unique identifier.
Некоторые службы могут иметь связь с уникальным экземпляром службы на медиасервере. Например, на одном медиасервере может проводиться несколько отдельных сессий конференции. Чтобы идентифицировать уникальные экземпляры службы, уникальный идентификатор изменяет имя службы. Уникальный идентификатор ДОЛЖЕН соответствовать правилам легальной пользовательской части SIP URI. Знак равенства, US-ASCII %3D, ДОЛЖЕН отделять индикатор службы от уникального идентификатора.
Note that since the service indicator is case insensitive, the service instance identifier is also case insensitive.
Обратите внимание: поскольку индикатор службы нечувствителен к регистру, идентификатор экземпляра службы также нечувствителен к регистру.
The requesting client issues a SIP INVITE to the media server, specifying the requested service and any appropriate parameters.
Запрашивающий клиент отправляет SIP INVITE медиасерверу, указывая запрошенную услугу и любые соответствующие параметры.
If the media server can perform the requested service, it does so, following the processing steps described in the service definition document.
Если медиасервер может выполнить запрошенную услугу, он делает это, следуя шагам обработки, описанным в документе определения услуги.
If the media server cannot perform the requested service or does not recognize the service indicator, it MUST respond with the response code 488 NOT ACCEPTABLE HERE. This is appropriate, as 488 refers to a problem with the user part of the URI. Moreover, 606 is not appropriate, as some other media server may be able to satisfy the request. RFC 3261 [10] describes the 488 and 606 response codes.
Если медиасервер не может выполнить запрошенную услугу или не распознает индикатор услуги, он ДОЛЖЕН ответить кодом ответа 488, ЗДЕСЬ НЕ ПРИМЕМО. Это уместно, поскольку 488 указывает на проблему с пользовательской частью URI. Более того, 606 не подходит, так как какой-то другой медиасервер может удовлетворить запрос. RFC 3261 [10] описывает коды ответа 488 и 606.
Some services require a unique identifier. Most services automatically create a service instance upon the first INVITE with the given identifier. However, if a service requires an existing service instance, and no such service instance exists on the media server, the media server MUST respond with the response code 404 NOT FOUND. This is appropriate as the service itself exists on the media server, but the particular service instance does not. It is as if the user was not home.
Некоторые службы требуют уникальный идентификатор. Большинство сервисов автоматически создают экземпляр сервиса при первом INVITE с данным идентификатором. Однако если службе требуется существующий экземпляр службы, а на медиасервере такого экземпляра службы не существует, медиасервер ДОЛЖЕН ответить кодом ответа 404 NOT FOUND. Это приемлемо, поскольку сама служба существует на медиасервере, а конкретный экземпляр службы — нет. Как будто пользователя не было дома.
3. Announcement Service
3. Служба объявлений
A network announcement is the delivery of a multimedia resource, such as a prompt file, to a terminal device. Note the multimedia resource may be any multimedia object that the media server supports. This service can play a single object with multiple streams, such as a video and audio prompt. However, this service cannot play multiple objects on the same SIP dialog.
Сетевое объявление — это доставка мультимедийного ресурса, например файла приглашения, на терминальное устройство. Обратите внимание, что мультимедийный ресурс может быть любым мультимедийным объектом, который поддерживает медиасервер. Эта служба может воспроизводить один объект с несколькими потоками, например видео- и аудиоподсказку. Однако эта служба не может воспроизводить несколько объектов в одном диалоговом окне SIP.
There are two types of network announcements. The differentiating characteristic between the two types is whether the network fully sets up the SIP dialog before playing the announcement. The analog in the Public Switched Telephone Network (PSTN) is whether answer supervision is supplied (i.e., does the announcement server answer the call prior to delivering the announcement?). Playing an announcement after call setup is straightforward. First, the requesting device issues an INVITE to the media server requesting the announcement service. The media server negotiates the SDP and responds with a 200 OK. After receiving the ACK from the requesting device, the media server plays the requested object and issues a BYE to the requesting device.
Существует два типа сетевых объявлений. Отличительной характеристикой этих двух типов является то, полностью ли сеть настраивает диалог SIP перед воспроизведением объявления. Аналогом в коммутируемой телефонной сети общего пользования (PSTN) является наличие контроля ответа (то есть, отвечает ли сервер объявлений на вызов до доставки объявления?). Воспроизвести объявление после настройки вызова очень просто. Сначала запрашивающее устройство выдает INVITE медиасерверу, запрашивающему услугу объявления. Медиа-сервер согласовывает SDP и отвечает 200 OK. После получения ACK от запрашивающего устройства медиасервер воспроизводит запрошенный объект и выдает BYE запрашивающему устройству.
If the media server supports announcements, but it cannot find the referenced URI, it MUST respond with the 404 response code and SHOULD send the reason phrase "Announcement content not found".
Если медиасервер поддерживает объявления, но не может найти указанный URI, он ДОЛЖЕН ответить кодом ответа 404 и ДОЛЖЕН отправить фразу причины «Содержимое объявления не найдено».
If the media server receives an INVITE for the announcement service without a "play=" parameter, it MUST respond with the response code 400 and SHOULD send the reason phrase "Mandatory play parameter missing".
Если медиасервер получает INVITE для службы объявлений без параметра «play=«, он ДОЛЖЕН ответить кодом ответа 400 и ДОЛЖЕН отправить фразу причины «Отсутствует обязательный параметр воспроизведения».
If there is an error retrieving the announcement, the media server MUST respond with a 400 response code and SHOULD send the reason phrase "Announcement content could not be retrieved". In addition the media server SHOULD include a Warning header with appropriate explanatory text explaining what failed.
Если при получении объявления произошла ошибка, медиасервер ДОЛЖЕН ответить кодом ответа 400 и ДОЛЖЕН отправить фразу причины «Содержимое объявления не может быть получено». Кроме того, медиасервер ДОЛЖЕН включать заголовок Warning с соответствующим пояснительным текстом, объясняющим, что не удалось.
The Request URI fully describes the announcement service through the use of the user part of the address and additional URI parameters. The user portion of the address, "annc", specifies the announcement service on the media server. The service has several associated URI parameters that control the content and delivery of the announcement.
URI запроса полностью описывает службу объявлений посредством использования пользовательской части адреса и дополнительных параметров URI. Пользовательская часть адреса «annc» указывает службу объявлений на медиасервере. У службы есть несколько связанных параметров URI, которые управляют содержанием и доставкой объявления.
These parameters are described below:
Эти параметры описаны ниже:
play Specifies the resource or announcement sequence to be played.
play Указывает ресурс или последовательность объявлений для воспроизведения.
repeat Specifies how many times the media server should repeat the announcement or sequence named by the "play=" parameter. The value "forever" means the repeat should be effectively unbounded. In this case, it is RECOMMENDED the media server implements some local policy, such as limiting what "forever" means, to ensure errant clients do not create a denial of service attack.
повторение Указывает, сколько раз медиасервер должен повторить объявление или последовательность, указанную в параметре «play=». Значение «forever» означает, что повторение должно быть фактически неограниченным. В этом случае РЕКОМЕНДУЕТСЯ, чтобы медиасервер реализовал некоторую локальную политику, например, ограничение того, что означает «forever», чтобы гарантировать, что ошибочные клиенты не создают атаку типа «отказ в обслуживании».
delay Specifies a delay interval between announcement repetitions. The delay is measured in milliseconds.
задержка Определяет интервал задержки между повторениями объявлений. Задержка измеряется в миллисекундах.

7. The User Part

There has been considerable discussion about the wisdom of using fixed user parts in a request URI. The most common objection is that the user part should be opaque and a local matter. The other objection is that using a fixed user part removes those specified user addresses from the user address space.
Было много дискуссий о целесообразности использования фиксированных пользовательских частей в URI запроса. Наиболее распространенное возражение состоит в том, что пользовательская часть должна быть непрозрачной и решаться локально. Другое возражение состоит в том, что использование фиксированной пользовательской части удаляет указанные адреса пользователей из адресного пространства пользователя.
We address the latter issue first. The common example is the Postmaster address defined by RFC 2821 [15]. The objection is that by using the Postmaster token for something special, one removes that token for anyone. Thus, the Postmaster General of the United States, for example, cannot have the mail address Postmaster@usps.gov. However, one may debate whether this is a significant limitation.
Сначала мы рассмотрим последний вопрос. Типичным примером является адрес почтмейстера, определенный как RFC 2821 [15]. Возражение состоит в том, что, используя токен Postmaster для чего-то особенного, этот токен удаляется для всех. Так, например, генеральный почтмейстер США не может иметь почтовый адрес Postmaster@usps.gov. Однако можно спорить, является ли это существенным ограничением.
This document explicitly addresses this issue. The user names described in the text (namely annc, ivr, dialog, and conf) are available for whatever local use a given SIP user agent or proxy wishes for them. What this document does is give special meaning for these user names at media servers that implement this specification. If a media server chooses not to implement this specification, nothing breaks. If a user wishes to use one of the user names described in this document at their SIP user agent, nothing breaks and their user agent will work as expected.
Этот документ явно рассматривает эту проблему. Имена пользователей, описанные в тексте (а именно annc, ivr, диалог и conf), доступны для любого локального использования, которое желает для них данный пользовательский агент SIP или прокси. Этот документ придает особое значение этим именам пользователей на медиасерверах, реализующих эту спецификацию. Если медиасервер решит не реализовывать эту спецификацию, ничего не сломается. After much discussion, with input from the W3C URI work group, we considered obfuscating the user name by prepending "__sip-" to the user name. Again, there is no possibility that the name on the device may "leak out" into the SIP routing network. The most important thing to note about this convention is that the left-hand side of the request URI is opaque to the network. The only network elements that need to know about the convention are the Media Server and client. Even proxies doing mapping resolution, as in the example above for public announcement services, do not need to be aware of the convention. The convention is purely a matter of provisioning.
После долгих обсуждений, при участии рабочей группы W3C URI, мы решили запутать имя пользователя, добавив «__sip-» к имени пользователя. This is particularly onerous for situations where there is an ad hoc relationship between the application and the media service. Without a well-known relationship between service and service address, how would the client locate the service?
Некоторые предлагают, чтобы такое наименование было чисто местным соглашением. Например, тезис информационного RFC 3087 [17] заключается в том, что к сервисам можно обращаться с помощью URI запроса. Однако некоторые довели приведенные в документе примеры до крайности. А именно, что единственный способ обращения к сервисам — через произвольные, непрозрачные и длинные пользовательские части. Очевидно, что можно предоставить имена служб, а не фиксированные имена. Хотя это может работать в закрытой сети, где серверы приложений и медиа-серверы находятся в одном административном домене, это не работает в других доменах, например в Интернете. Это связано с тем, что клиент медиа-службы должен знать локальное имя для каждой пары служба/домен. Это особенно обременительно для ситуаций, когда между приложением и медиа-службой существуют специальные отношения. Без хорошо известной взаимосвязи между сервисом и его адресом, как клиент сможет найти сервис?
One very important result of using the user part as the service descriptor is that we can use all of the standard SIP machinery, without modification. For example, Media Servers with different capabilities can SIP Register their capabilities as users. For example, a VoiceXML-only device will register the "dialog" user, while a multi-purpose Media Server will register all of the users. Note that this is why the URI to play is a parameter. Doing otherwise would overburden a normal SIP proxy or redirect server. Conversely, having the conference ID be part of the user part gives an indication that requests get routed similarly (as opposed to requiring a Globally Routable User Agent URI (GRUU), which would restrict routing to the same device).
Одним из очень важных результатов использования пользовательской части в качестве дескриптора службы является то, что мы можем использовать все стандартные механизмы SIP без изменений. Например, медиасерверы с различными возможностями могут SIP регистрировать свои возможности в качестве пользователей. Например, устройство VoiceXML-only зарегистрирует пользователя «dialog», а многоцелевой медиасервер зарегистрирует всех пользователей. Обратите внимание: именно поэтому URI для воспроизведения является параметром. В противном случае это приведет к перегрузке обычного SIP-прокси или сервера перенаправления. И наоборот, если идентификатор конференции является частью пользовательской части, это указывает на то, что запросы маршрутизируются аналогичным образом (в отличие от требования URI агента пользователя с глобальной маршрутизацией (GRUU), который ограничивал бы маршрутизацию на одно и то же устройство).
Likewise, this scheme lets us leverage the standard SIP proxy behavior of using an intelligent redirect server or proxy server to provide high-available services. For example, two Media Servers can register with a SIP redirect server for the annc user. If one of the Media Servers fails, the registration will expire and all requests for the announcement service ("calls to the annc user") will get sent to the surviving Media Server.
Аналогичным образом, эта схема позволяет нам использовать стандартное поведение прокси SIP, заключающееся в использовании интеллектуального сервера перенаправления или прокси для предоставления услуг с высоким уровнем доступности. Например, два медиасервера могут зарегистрироваться на сервере перенаправления SIP для пользователя annc. Если один из медиа-серверов выйдет из строя, срок регистрации истечет, и все запросы на службу объявлений («вызовы пользователю annc») будут отправлены на оставшийся медиа-сервер.
8. Security Considerations
8. Вопросы безопасности
Exposing network services with well-known addresses may not be desirable. The Media Server SHOULD authenticate and authorize requesting endpoints per local policy.
Раскрытие сетевых служб с хорошо известными адресами может оказаться нежелательным. Медиа-серверу СЛЕДУЕТ аутентифицировать и авторизовать запрашивающие конечные точки в соответствии с локальной политикой.
Some interactions in this document result in the transfer of confidential information. Moreover, many of the interactions require integrity protection. Thus, the Media Server MUST implement the sips: scheme. In addition, application developers are RECOMMENDED to use the security services offered by the Media Server to ensure the integrity and confidentiality of their user's data, as appropriate.
Некоторые взаимодействия в этом документе приводят к передаче конфиденциальной информации. Более того, многие взаимодействия требуют защиты целостности. Таким образом, медиасервер ДОЛЖЕН реализовать схему sips:. Кроме того, разработчикам приложений РЕКОМЕНДУЕТСЯ использовать службы безопасности, предлагаемые Медиа-сервером, для обеспечения целостности и конфиденциальности данных своих пользователей, если это необходимо.
Untrusted network elements could use the convention described here for providing information services. Many extant billing arrangements are for completed calls. Successful call completion occurs with a 2xx result code. This can be an issue for the early media announcement service. This is one of the reasons why the early media announcement service is deprecated.
Недоверенные сетевые элементы могут использовать описанное здесь соглашение для предоставления информационных услуг. Многие существующие механизмы выставления счетов предназначены для завершенных вызовов. Успешное завершение вызова происходит с кодом результата 2xx. Это может стать проблемой для службы раннего оповещения в СМИ. Это одна из причин, по которой служба ранних объявлений в СМИ устарела.
Services such as repeating an announcement forever create the possibility for denial of service attacks. The media server SHOULD have local policies to deal with this, such as time-limiting how long "forever" is, analyzing where multiple requests come from, implementing white-lists for such a service, and so on.
Такие услуги, как вечное повторение объявления, создают возможность атак типа «отказ в обслуживании». Медиа-сервер ДОЛЖЕН иметь локальные политики для решения этой проблемы, такие как ограничение времени «forever», анализ происхождения нескольких запросов, внедрение белых списков для такой службы и т. д.
