Abstract
Аннотация
This memo defines the Session Description Protocol (SDP). SDP is intended for describing multimedia sessions for the purposes of session announcement, session invitation, and other forms of multimedia session initiation. This document obsoletes RFC 4566.
В этом меморандуме определяется протокол описания сессий (Session Description Protocol, SDP). SDP предназначен для описания мультимедийных сессий в целях анонсирования сессий, приглашения в сессию и других форм инициирования мультимедийных сессий. Настоящий документ делает устаревшим RFC 4566.

1. Introduction
1. Введение
When initiating multimedia teleconferences, voice-over-IP calls, streaming video, or other sessions, there is a requirement to convey media details, transport addresses, and other session description metadata to the participants.
При инициировании мультимедийных телеконференций, телефонных вызовов по IP (voice-over-IP), потокового видео или иных сессий требуется передавать участникам сведения о медиаданных, транспортные адреса и другие метаданные описания сессии.
SDP provides a standard representation for such information, irrespective of how that information is transported. SDP is purely a format for session description -- it does not incorporate a transport protocol, and it is intended to use different transport protocols as appropriate, including the Session Announcement Protocol (SAP) [RFC2974], Session Initiation Protocol (SIP) [RFC3261], Real-Time Streaming Protocol (RTSP) [RFC7826], electronic mail [RFC5322] using the MIME extensions [RFC2045], and the Hypertext Transport Protocol (HTTP) [RFC7230].
SDP обеспечивает стандартное представление таких сведений независимо от того, каким образом эти сведения передаются. SDP — это исключительно формат описания сессии: он не включает в себя транспортный протокол и предназначен для использования с различными транспортными протоколами по мере необходимости, включая протокол анонсирования сессий (Session Announcement Protocol, SAP) [RFC2974], протокол инициирования сессий (Session Initiation Protocol, SIP) [RFC3261], протокол потоковой передачи в реальном времени (Real-Time Streaming Protocol, RTSP) [RFC7826], электронную почту [RFC5322] с расширениями MIME [RFC2045] и протокол передачи гипертекста (Hypertext Transport Protocol, HTTP) [RFC7230].
SDP is intended to be general purpose so that it can be used in a wide range of network environments and applications. However, it is not intended to support negotiation of session content or media encodings: this is viewed as outside the scope of session description.
SDP задуман как универсальный, чтобы его можно было применять в самых разных сетевых средах и приложениях. Однако он не предназначен для согласования содержимого сессии или кодирований медиаданных: считается, что это выходит за рамки описания сессии.
This memo obsoletes [RFC4566]. The changes relative to [RFC4566] are outlined in Section 10 of this memo.
Настоящий меморандум делает устаревшим [RFC4566]. Изменения по отношению к [RFC4566] изложены в разделе 10 настоящего меморандума.
2. Glossary of Terms
2. Глоссарий терминов
The following terms are used in this document and have specific meaning within the context of this document.
Перечисленные ниже термины используются в настоящем документе и имеют особое значение в его контексте.
Session Description: A well-defined format for conveying sufficient information to discover and participate in a multimedia session.
Описание сессии (Session Description): строго определённый формат для передачи сведений, достаточных для обнаружения мультимедийной сессии и участия в ней.
Media Description: A Media Description contains the information needed for one party to establish an application-layer network protocol connection to another party. It starts with an "m=" line and is terminated by either the next "m=" line or by the end of the session description.
Описание медиаданных (Media Description): содержит сведения, необходимые одной стороне для установления соединения протокола прикладного уровня с другой стороной. Оно начинается со строки "m=" и завершается либо следующей строкой "m=", либо концом описания сессии.
Session-Level Section: This refers to the parts that are not media descriptions, whereas the session description refers to the whole body that includes the session-level section and the media description(s).
Раздел уровня сессии (Session-Level Section): имеются в виду части, не являющиеся описаниями медиаданных; при этом описание сессии означает всё тело, включающее раздел уровня сессии и описание (описания) медиаданных.

3. Examples of SDP Usage
3. Примеры использования SDP
3.1. Session Initiation
3.1. Инициирование сессии
The Session Initiation Protocol (SIP) [RFC3261] is an application- layer control protocol for creating, modifying, and terminating sessions such as Internet multimedia conferences, Internet telephone calls, and multimedia distribution. The SIP messages used to create sessions carry session descriptions that allow participants to agree on a set of compatible media types [RFC6838]. These session descriptions are commonly formatted using SDP. When used with SIP, the offer/answer model [RFC3264] provides a limited framework for negotiation using SDP.
Протокол инициирования сессий (SIP) [RFC3261] — это протокол управления прикладного уровня для создания, изменения и завершения сессий, таких как мультимедийные конференции в Интернете, телефонные вызовы через Интернет и распространение мультимедиа. Сообщения SIP, используемые для создания сессий, несут описания сессий, которые позволяют участникам договориться о наборе совместимых типов медиаданных [RFC6838]. Эти описания сессий обычно оформляются с помощью SDP. При использовании вместе с SIP модель предложения/ответа [RFC3264] даёт ограниченную основу для согласования с помощью SDP.
3.2. Streaming Media
3.2. Потоковые медиаданные
The Real-Time Streaming Protocol (RTSP) [RFC7826], is an application- level protocol for control over the delivery of data with real-time properties. RTSP provides an extensible framework to enable controlled, on-demand delivery of real-time data, such as audio and video. An RTSP client and server negotiate an appropriate set of parameters for media delivery, partially using SDP syntax to describe those parameters.
Протокол потоковой передачи в реальном времени (RTSP) [RFC7826] — протокол прикладного уровня для управления доставкой данных, обладающих свойствами реального времени. RTSP предоставляет расширяемую основу для управляемой доставки данных реального времени по запросу, таких как аудио и видео. Клиент и сервер RTSP согласуют подходящий набор параметров доставки медиаданных, частично используя синтаксис SDP для описания этих параметров.
3.3. Email and the World Wide Web
3.3. Электронная почта и Всемирная паутина
Alternative means of conveying session descriptions include electronic mail and the World Wide Web (WWW). For both email and WWW distribution, the media type "application/sdp" is used. This enables the automatic launching of applications for participation in the session from the WWW client or mail reader in a standard manner.
Альтернативные способы передачи описаний сессий включают электронную почту и Всемирную паутину (WWW). И для рассылки по электронной почте, и для распространения через WWW используется тип медиаданных "application/sdp". Это позволяет стандартным образом автоматически запускать приложения для участия в сессии из клиента WWW или программы чтения почты.
Note that descriptions of multicast sessions sent only via email or the WWW do not have the property that the receiver of a session description can necessarily receive the session because the multicast sessions may be restricted in scope, and access to the WWW server or reception of email is possibly outside this scope.
Заметьте, что описания многоадресных сессий, отправленные только по электронной почте или через WWW, не обладают тем свойством, что получатель описания сессии обязательно сможет принять эту сессию, поскольку многоадресные сессии могут быть ограничены по области действия, а доступ к серверу WWW или получение почты, возможно, находятся за пределами этой области.
3.4. Multicast Session Announcement
3.4. Анонсирование многоадресных сессий
In order to assist the advertisement of multicast multimedia conferences and other multicast sessions, and to communicate the relevant session setup information to prospective participants, a distributed session directory may be used. An instance of such a session directory periodically sends packets containing a description of the session to a well-known multicast group. These advertisements are received by other session directories such that potential remote participants can use the session description to start the tools required to participate in the session.
Чтобы помочь распространению сведений о многоадресных мультимедийных конференциях и других многоадресных сессиях и передать потенциальным участникам необходимые сведения о подготовке сессии, может использоваться распределённый каталог сессий. Экземпляр такого каталога сессий периодически отправляет пакеты, содержащие описание сессии, в известную многоадресную группу. Эти объявления получают другие каталоги сессий, так что потенциальные удалённые участники могут использовать описание сессии для запуска инструментов, необходимых для участия в сессии.
One protocol used to implement such a distributed directory is the SAP [RFC2974]. SDP provides the recommended session description format for such session announcements.
Одним из протоколов, используемых для реализации такого распределённого каталога, является SAP [RFC2974]. SDP предоставляет рекомендуемый формат описания сессии для таких анонсов сессий.
4. Requirements and Recommendations
4. Требования и рекомендации
The purpose of SDP is to convey information about media streams in multimedia sessions to allow the recipients of a session description to participate in the session. SDP is primarily intended for use with Internet protocols, although it is sufficiently general that it can describe multimedia conferences in other network environments. Media streams can be many-to-many. Sessions need not be continually active.
Назначение SDP — передавать сведения о медиапотоках в мультимедийных сессиях, чтобы получатели описания сессии могли участвовать в сессии. SDP в первую очередь предназначен для использования с протоколами Интернета, хотя он достаточно универсален, чтобы описывать мультимедийные конференции в других сетевых средах. Медиапотоки могут быть «многие ко многим». Сессии не обязаны быть постоянно активными.
Thus far, multicast-based sessions on the Internet have differed from many other forms of conferencing in that anyone receiving the traffic can join the session (unless the session traffic is encrypted). In such an environment, SDP serves two primary purposes. It is a means to communicate the existence of a session, and it is a means to convey sufficient information to enable joining and participating in the session. In a unicast environment, only the latter purpose is likely to be relevant.
До сих пор сессии на основе многоадресной передачи в Интернете отличались от многих других форм конференц-связи тем, что присоединиться к сессии может любой, кто получает трафик (если трафик сессии не зашифрован). В такой среде SDP служит двум основным целям. Он является средством сообщить о существовании сессии и средством передать достаточно сведений, чтобы можно было присоединиться к сессии и участвовать в ней. В одноадресной среде, вероятно, актуальна только вторая цель.
An SDP description includes the following:
Описание SDP включает следующее:
* Session name and purpose
* Имя и назначение сессии
* Time(s) the session is active
* Время (времена), когда сессия активна
* The media comprising the session
* Медиаданные, составляющие сессию
* Information needed to receive those media (addresses, ports, formats, etc.)
* Сведения, необходимые для приёма этих медиаданных (адреса, порты, форматы и т. д.)
As resources necessary to participate in a session may be limited, some additional information may also be desirable:
Поскольку ресурсы, необходимые для участия в сессии, могут быть ограничены, может оказаться желательной и некоторая дополнительная информация:
* Information about the bandwidth to be used by the session
* Сведения о полосе пропускания, которая будет использоваться сессией
* Contact information for the person responsible for the session
* Контактные сведения о лице, ответственном за проведение сессии

5. SDP Specification
5. Спецификация SDP
An SDP description is denoted by the media type "application/sdp" (See Section 8).
Описание SDP обозначается типом медиаданных "application/sdp" (см. раздел 8).
An SDP description is entirely textual. SDP field names and attribute names use only the US-ASCII subset of UTF-8 [RFC3629], but textual fields and attribute values MAY use the full ISO 10646 character set in UTF-8 encoding, or some other character set defined by the "a=charset:" attribute (Section 6.10). Field and attribute values that use the full UTF-8 character set are never directly compared, hence there is no requirement for UTF-8 normalization. The textual form, as opposed to a binary encoding such as ASN.1 or XDR, was chosen to enhance portability, to enable a variety of transports to be used, and to allow flexible, text-based toolkits to be used to generate and process session descriptions. However, since SDP may be used in environments where the maximum permissible size of a session description is limited, the encoding is deliberately compact. Also, since descriptions may be transported via very unreliable means or damaged by an intermediate caching server, the encoding was designed with strict order and formatting rules so that most errors would result in malformed session descriptions that could be detected easily and discarded.
Описание SDP является полностью текстовым. Имена полей и имена атрибутов SDP используют только подмножество US-ASCII из UTF-8 [RFC3629], но текстовые поля и значения атрибутов МОГУТ использовать полный набор символов ISO 10646 в кодировке UTF-8 или какой-либо иной набор символов, определённый атрибутом "a=charset:" (раздел 6.10). Значения полей и атрибутов, использующие полный набор символов UTF-8, никогда не сравниваются непосредственно, поэтому требование нормализации UTF-8 отсутствует. Текстовая форма, в отличие от двоичного кодирования, такого как ASN.1 или XDR, была выбрана для повышения переносимости, обеспечения возможности использования разнообразных транспортов и применения гибких текстовых инструментариев для создания и обработки описаний сессий. Однако, поскольку SDP может применяться в средах, где максимально допустимый размер описания сессии ограничен, кодирование намеренно сделано компактным. Кроме того, поскольку описания могут передаваться через весьма ненадёжные средства или повреждаться промежуточным кэширующим сервером, кодирование было разработано со строгими правилами порядка и форматирования, чтобы большинство ошибок давали некорректные описания сессий, которые легко обнаружить и отбросить.

where <type> is exactly one case-significant character and <value> is structured text whose format depends on <type>. In general, <value> is either a number of subfields delimited by a single space character or a free format string, and is case-significant unless a specific field defines otherwise. Whitespace separators are not used on either side of the "=" sign, however, the value can contain a leading whitespace as part of its syntax, i.e., that whitespace is part of the value.
где <type> — ровно один учитывающий регистр символ, а <value> — структурированный текст, формат которого зависит от <type>. Как правило, <value> представляет собой либо ряд подполей, разделённых одним символом пробела, либо строку свободного формата, и учитывает регистр, если конкретное поле не определяет иное. Второе подполе (<addrtype>) — это тип адреса. Это позволяет использовать SDP для сессий, не основанных на IP. Настоящий меморандум определяет только "IP4" и "IP6", но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8).

Третье подполе (<connection-address>) — это адрес соединения. После адреса соединения МОГУТ быть добавлены дополнительные подполя в зависимости от значения подполя <addrtype>.
When the <addrtype> is "IP4" or "IP6", the connection address is defined as follows:
Когда <addrtype> имеет значение "IP4" или "IP6", адрес соединения определяется следующим образом:
* If the session is multicast, the connection address will be an IP multicast group address. If the session is not multicast, then the connection address contains the unicast IP address of the expected data source, data relay, or data sink as determined by additional attribute-fields (Section 5.13). It is not expected that unicast addresses will be given in a session description that is communicated by a multicast announcement, though this is not prohibited.
* Если сессия является многоадресной, адресом соединения будет адрес многоадресной IP-группы. Если сессия не является многоадресной, адрес соединения содержит одноадресный IP-адрес ожидаемого источника, ретранслятора или приёмника данных, определяемого дополнительными полями атрибутов (раздел 5.13). Не ожидается, что одноадресные адреса будут указываться в описании сессии, которое распространяется посредством многоадресного объявления, хотя это и не запрещено.
* Sessions using an "IP4" multicast connection address MUST also have a time to live (TTL) value present in addition to the multicast address. The TTL and the address together define the scope with which multicast packets sent in this session will be sent. TTL values MUST be in the range 0-255. Although the TTL MUST be specified, its use to scope multicast traffic is deprecated; applications SHOULD use an administratively scoped address instead.
* Сессии, использующие многоадресный адрес соединения "IP4", ДОЛЖНЫ также иметь значение времени жизни (TTL) в дополнение к многоадресному адресу. TTL и адрес вместе определяют область действия, в которой будут отправляться многоадресные пакеты этой сессии. Значения TTL ДОЛЖНЫ находиться в диапазоне 0–255. Хотя TTL ДОЛЖЕН быть указан, его использование для ограничения области действия многоадресного трафика устарело; приложениям СЛЕДУЕТ вместо этого использовать административно ограниченный адрес.
The TTL for the session is appended to the address using a slash as a separator. An example is:
TTL для сессии добавляется к адресу с использованием косой черты в качестве разделителя. Пример:
c=IN IP4 233.252.0.1/127
c=IN IP4 233.252.0.1/127
"IP6" multicast does not use TTL scoping, and hence the TTL value MUST NOT be present for "IP6" multicast. It is expected that IPv6 scoped addresses will be used to limit the scope of multimedia conferences.
Многоадресная "IP6" не использует ограничение области через TTL, поэтому значение TTL ДОЛЖНО отсутствовать при многоадресной передаче "IP6". Ожидается, что для ограничения области действия мультимедийных конференций будут применяться адреса IPv6 с областью действия.
Hierarchical or layered encoding schemes are data streams where the encoding from a single media source is split into a number of layers. The receiver can choose the desired quality (and hence bandwidth) by only subscribing to a subset of these layers. Such layered encodings are normally transmitted in multiple multicast groups to allow multicast pruning. This technique keeps unwanted traffic from sites only requiring certain levels of the hierarchy. For applications requiring multiple multicast groups, we allow the following notation to be used for the connection address:
Иерархические или многослойные схемы кодирования — это потоки данных, в которых кодирование от одного источника медиаданных разделяется на ряд слоёв. Получатель может выбрать желаемое качество (и, следовательно, полосу пропускания), подписавшись лишь на подмножество этих слоёв. Такие многослойные кодирования обычно передаются в нескольких многоадресных группах, чтобы обеспечить отсечение многоадресной рассылки. Этот приём удерживает нежелательный трафик от узлов, которым нужны только определённые уровни иерархии. Для приложений, требующих нескольких многоадресных групп, мы разрешаем использовать для адреса соединения следующую нотацию:
<base multicast address>[/<ttl>]/<number of addresses>
<base multicast address>[/<ttl>]/<number of addresses>

c=IN IP4 233.252.0.1/127/3
c=IN IP4 233.252.0.1/127/3
would state that addresses 233.252.0.1, 233.252.0.2, and 233.252.0.3 are to be used with a TTL of 127. This is semantically identical to including multiple "c=" lines in a media description:
означало бы, что адреса 233.252.0.1, 233.252.0.2 и 233.252.0.3 должны использоваться с TTL 127. Семантически это идентично включению нескольких строк "c=" в описание медиаданных:
c=IN IP4 233.252.0.1/127 c=IN IP4 233.252.0.2/127 c=IN IP4 233.252.0.3/127
c=IN IP4 233.252.0.1/127 c=IN IP4 233.252.0.2/127 c=IN IP4 233.252.0.3/127
Similarly, an IPv6 example would be:
Аналогично, пример для IPv6:

c=IN IP6 ff00::db8:0:101/3
which is semantically equivalent to:
что семантически эквивалентно:
c=IN IP6 ff00::db8:0:101 c=IN IP6 ff00::db8:0:102 c=IN IP6 ff00::db8:0:103
c=IN IP6 ff00::db8:0:101 c=IN IP6 ff00::db8:0:102 c=IN IP6 ff00::db8:0:103
(remember that the TTL subfield is not present in "IP6" multicast).
(напомним, что подполе TTL отсутствует при многоадресной передаче "IP6").
Multiple addresses or "c=" lines MAY be specified on a per media description basis only if they provide multicast addresses for different layers in a hierarchical or layered encoding scheme. Multiple addresses or "c=" lines MUST NOT be specified at session level.
Несколько адресов или строк "c=" МОГУТ указываться на уровне отдельного описания медиаданных только в том случае, если они предоставляют многоадресные адреса для разных слоёв иерархической или многослойной схемы кодирования. Несколько адресов или строк "c=" НЕ ДОЛЖНЫ указываться на уровне сессии.
The slash notation for multiple addresses described above MUST NOT be used for IP unicast addresses.
Нотация с косой чертой для нескольких адресов, описанная выше, НЕ ДОЛЖНА использоваться для одноадресных IP-адресов.
5.8. Bandwidth Information ("b=")
5.8. Сведения о полосе пропускания ("b=")
b=<bwtype>:<bandwidth>

The OPTIONAL "b=" line (bandwidth-field) denotes the proposed bandwidth to be used by the session or media description. The <bwtype> is an alphanumeric modifier that provides the meaning of the <bandwidth> number. Two values are defined in this specification, but other values MAY be registered in the future (see Section 8 and [RFC3556], [RFC3890]):
НЕОБЯЗАТЕЛЬНАЯ строка "b=" (поле полосы пропускания) обозначает предлагаемую полосу пропускания, которая будет использоваться сессией или описанием медиаданных. <bwtype> — это буквенно-цифровой модификатор, задающий смысл числа <bandwidth>. В настоящей спецификации определены два значения, но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8, а также [RFC3556], [RFC3890]):
CT If the bandwidth of a session is different from the bandwidth implicit from the scope, a "b=CT:" line SHOULD be supplied for the session giving the proposed upper limit to the bandwidth used (the "conference total" bandwidth). Similarly, if the bandwidth of bundled media streams [RFC8843] in an "m=" line is different from the implicit value from the scope, a "b=CT:" line SHOULD be supplied in the media level. The primary purpose of this is to give an approximate idea as to whether two or more sessions (or bundled media streams) can coexist simultaneously. Note that a "b=CT:" line gives a total bandwidth figure for all the media at all endpoints.
CT Если полоса пропускания сессии отличается от полосы, подразумеваемой областью действия, для сессии СЛЕДУЕТ указать строку "b=CT:", задающую предлагаемый верхний предел используемой полосы пропускания (полосу пропускания «суммарно по конференции»). Аналогично, если полоса пропускания объединённых медиапотоков [RFC8843] в строке "m=" отличается от значения, подразумеваемого областью действия, на уровне медиаданных СЛЕДУЕТ указать строку "b=CT:". Основное назначение этого — дать приблизительное представление о том, могут ли две или более сессий (или объединённых медиапотоков) сосуществовать одновременно. Заметьте, что строка "b=CT:" даёт суммарную полосу пропускания для всех медиаданных на всех оконечных точках.
The Mux Category for "b=CT:" is NORMAL. This is discussed in [RFC8859].
Категория мультиплексирования для "b=CT:" — NORMAL. Это обсуждается в [RFC8859].
AS The bandwidth is interpreted to be application specific (it will be the application's concept of maximum bandwidth). Normally, this will coincide with what is set on the application's "maximum bandwidth" control if applicable. For RTP-based applications, the "b=AS:" line gives the RTP "session bandwidth" as defined in Section 6.2 of [RFC3550]. Note that a "b=AS:" line gives a bandwidth figure for a single media at a single endpoint, although there may be many endpoints sending simultaneously.
AS Полоса пропускания интерпретируется как зависящая от приложения (это будет представление приложения о максимальной полосе пропускания). Обычно это совпадает с тем, что установлено в элементе управления «максимальная полоса пропускания» приложения, если таковой имеется. Для приложений на основе RTP строка "b=AS:" задаёт «полосу пропускания сессии» RTP, как определено в разделе 6.2 [RFC3550]. Заметьте, что строка "b=AS:" даёт значение полосы пропускания для отдельных медиаданных на отдельной оконечной точке, хотя одновременно могут отправлять много оконечных точек.
The Mux Category for "b=AS:" is SUM. This is discussed in [RFC8859].
Категория мультиплексирования для "b=AS:" — SUM. Это обсуждается в [RFC8859].
[RFC4566] defined an "X-" prefix for <bwtype> names. This was intended for experimental purposes only. For example:
[RFC4566] определил префикс "X-" для имён <bwtype>. Он предназначался исключительно для экспериментальных целей. Например:
b=X-YZ:128
b=X-YZ:128
Use of the "X-" prefix is NOT RECOMMENDED. Instead new (non "X-" prefix) <bwtype> names SHOULD be defined, and then MUST be registered with IANA in the standard namespace. SDP parsers MUST ignore bandwidth-fields with unknown <bwtype> names. The <bwtype> names MUST be alphanumeric and, although no length limit is given, it is recommended that they be short.
Использование префикса "X-" НЕ РЕКОМЕНДУЕТСЯ. Вместо этого СЛЕДУЕТ определять новые имена <bwtype> (без префикса "X-"), которые затем ДОЛЖНЫ быть зарегистрированы в IANA в стандартном пространстве имён. Анализаторы SDP ДОЛЖНЫ игнорировать поля полосы пропускания с неизвестными именами <bwtype>. Имена <bwtype> ДОЛЖНЫ быть буквенно-цифровыми, и, хотя ограничение длины не задано, рекомендуется, чтобы они были короткими.
The <bandwidth> is interpreted as kilobits per second by default (including the transport and network-layer, but not the link-layer, overhead). The definition of a new <bwtype> modifier MAY specify that the bandwidth is to be interpreted in some alternative unit (the "CT" and "AS" modifiers defined in this memo use the default units).
<bandwidth> по умолчанию интерпретируется как килобиты в секунду (включая накладные расходы транспортного и сетевого уровней, но не канального уровня). Определение нового модификатора <bwtype> МОЖЕТ указывать, что полоса пропускания должна интерпретироваться в какой-либо иной единице (модификаторы "CT" и "AS", определённые в настоящем меморандуме, используют единицы по умолчанию).
5.9. Time Active ("t=")
5.9. Время действия ("t=")
t=<start-time> <stop-time>
t=<start-time> <stop-time>
A "t=" line (time-field) begins a time description that specifies the start and stop times for a session. Multiple time descriptions MAY be used if a session is active at multiple irregularly spaced times; each additional time description specifies additional periods of time for which the session will be active. If the session is active at regular repeat times, a repeat description, begun by an "r=" line (see Section 5.10) can be included following the time-field -- in which case the time-field specifies the start and stop times of the entire repeat sequence.
Строка "t=" (поле времени) начинает описание времени, которое задаёт времена начала и окончания сессии. Если сессия активна в несколько нерегулярно расположенных моментов времени, МОЖЕТ использоваться несколько описаний времени; каждое дополнительное описание времени задаёт дополнительные периоды, в течение которых сессия будет активна. Если сессия активна в регулярно повторяющиеся моменты времени, после поля времени может быть включено описание повторения, начинающееся со строки "r=" (см. раздел 5.10); в этом случае поле времени задаёт времена начала и окончания всей последовательности повторений.
The following example specifies two active intervals:
Следующий пример задаёт два интервала активности:
t=3724394400 3724398000 ; Mon 8-Jan-2018 10:00-11:00 UTC t=3724484400 3724488000 ; Tue 9-Jan-2018 11:00-12:00 UTC
t=3724394400 3724398000 ; Mon 8-Jan-2018 10:00-11:00 UTC t=3724484400 3724488000 ; Tue 9-Jan-2018 11:00-12:00 UTC
The first and second subfields of the time-field give the start and stop times, respectively, for the session. These are the decimal representation of time values in seconds since January 1, 1900 UTC. To convert these values to Unix time (UTC), subtract decimal 2208988800.
Первое и второе подполя поля времени задают соответственно времена начала и окончания сессии. Это десятичное представление значений времени в секундах с 1 января 1900 года UTC. Чтобы преобразовать эти значения в время Unix (UTC), вычтите десятичное 2208988800.
Some time representations will wrap in the year 2036. Because SDP uses an arbitrary length decimal representation, it does not have this issue. Implementations of SDP need to be prepared to handle these larger values.
Некоторые представления времени переполнятся в 2036 году. Поскольку SDP использует десятичное представление произвольной длины, эта проблема ему не свойственна. Реализации SDP должны быть готовы обрабатывать такие большие значения.
If the <stop-time> is set to zero, then the session is not bounded, though it will not become active until after the <start-time>. If the <start-time> is also zero, the session is regarded as permanent.
Если <stop-time> установлено в ноль, сессия не ограничена, хотя она не станет активной до наступления <start-time>. Если <start-time> также равно нулю, сессия считается постоянной.
User interfaces SHOULD strongly discourage the creation of unbounded and permanent sessions as they give no information about when the session is actually going to terminate, and so make scheduling difficult.
Пользовательские интерфейсы СЛЕДУЕТ решительно отговаривать от создания неограниченных и постоянных сессий, поскольку они не дают сведений о том, когда сессия фактически завершится, и тем самым затрудняют планирование.
The general assumption may be made, when displaying unbounded sessions that have not timed out to the user, that an unbounded session will only be active until half an hour from the current time or the session start time, whichever is the later. If behavior other than this is required, a <stop-time> SHOULD be given and modified as appropriate when new information becomes available about when the session should really end.
Можно принять общее допущение, что при отображении пользователю неограниченных сессий, время которых не истекло, неограниченная сессия будет активна только до момента, наступающего через полчаса от текущего времени или от времени начала сессии, в зависимости от того, что позже. Если требуется иное поведение, СЛЕДУЕТ задать <stop-time> и изменять его надлежащим образом по мере появления новых сведений о том, когда сессия действительно должна завершиться.
Permanent sessions may be shown to the user as never being active unless there are associated repeat times that state precisely when the session will be active.
Постоянные сессии могут отображаться пользователю как никогда не активные, если только с ними не связаны времена повторения, точно указывающие, когда сессия будет активна.
5.10. Repeat Times ("r=")
5.10. Времена повторения ("r=")
r=<repeat interval> <active duration> <offsets from start-time>
r=<repeat interval> <active duration> <offsets from start-time>
An"r=" line (repeat-field) specifies repeat times for a session. If needed to express complex schedules, multiple repeat-fields may be included. For example, if a session is active at 10am on Monday and 11am on Tuesday for one hour each week for three months, then the <start-time> in the corresponding "t=" line would be the representation of 10am on the first Monday, the <repeat interval> would be 1 week, the <active duration> would be 1 hour, and the offsets would be zero and 25 hours. The corresponding "t=" line stop time would be the representation of the end of the last session three months later. By default, all subfields are in seconds, so the "r=" and "t=" lines might be the following:
Строка "r=" (поле повторения) задаёт времена повторения для сессии. При необходимости выразить сложные расписания может быть включено несколько полей повторения. Например, если сессия активна в 10:00 по понедельникам и в 11:00 по вторникам по одному часу каждую неделю в течение трёх месяцев, то <start-time> в соответствующей строке "t=" было бы представлением 10:00 первого понедельника, <repeat interval> составлял бы 1 неделю, <active duration> составляла бы 1 час, а смещения были бы нулём и 25 часами. Соответствующее время окончания в строке "t=" было бы представлением конца последней сессии тремя месяцами позже. По умолчанию все подполя задаются в секундах, поэтому строки "r=" и "t=" могли бы быть следующими:
t=3724394400 3730536000 ; Mon 8-Jan-2018 10:00-11:00 UTC ; Tues 20-Mar-2018 12:00 UTC r=604800 3600 0 90000 ; 1 week, 1 hour, zero, 25 hours
t=3724394400 3730536000 ; Mon 8-Jan-2018 10:00-11:00 UTC ; Tues 20-Mar-2018 12:00 UTC r=604800 3600 0 90000 ; 1 week, 1 hour, zero, 25 hours

Таким образом, приведённое выше поле повторения можно было бы также записать:

Monthly and yearly repeats cannot be directly specified with a single SDP repeat time; instead, separate time-descriptions should be used to explicitly list the session times.
Ежемесячные и ежегодные повторения нельзя задать непосредственно одним временем повторения SDP; вместо этого следует использовать отдельные описания времени, чтобы явно перечислить времена сессии.
5.11. Time Zone Adjustment ("z=")
5.11. Коррекция часового пояса ("z=")
z=<adjustment time> <offset> <adjustment time> <offset> ....
z=<adjustment time> <offset> <adjustment time> <offset> ....
A "z=" line (zone-field) is an optional modifier to the repeat-fields it immediately follows. It does not apply to any other fields.
Строка "z=" (поле часового пояса) — необязательный модификатор полей повторения, непосредственно перед которыми она стоит. К другим полям она не применяется.
To schedule a repeated session that spans a change from daylight saving time to standard time or vice versa, it is necessary to specify offsets from the base time. This is required because different time zones change time at different times of day, different countries change to or from daylight saving time on different dates, and some countries do not have daylight saving time at all.
Чтобы запланировать повторяющуюся сессию, охватывающую переход с летнего времени на стандартное или наоборот, необходимо задать смещения от базового времени. Это требуется потому, что разные часовые пояса меняют время в разное время суток, разные страны переходят на летнее время или с него в разные даты, а в некоторых странах летнего времени нет вовсе.
Thus, in order to schedule a session that is at the same time winter and summer, it must be possible to specify unambiguously by whose time zone a session is scheduled. To simplify this task for receivers, we allow the sender to specify the time (represented as seconds since January 1, 1900 UTC) that a time zone adjustment happens and the offset from the time when the session was first scheduled. The "z=" line allows the sender to specify a list of these adjustment times and offsets from the base time.
Таким образом, чтобы запланировать сессию, проходящую в одно и то же время зимой и летом, должна быть возможность однозначно указать, по чьему часовому поясу планируется сессия. Чтобы упростить эту задачу для получателей, мы позволяем отправителю указывать время (представленное в секундах с 1 января 1900 года UTC), когда происходит коррекция часового пояса, и смещение от времени, когда сессия была первоначально запланирована. Строка "z=" позволяет отправителю указать список таких времён коррекции и смещений от базового времени.
An example might be the following:
Примером может служить следующее:
t=3724394400 3754123200 ; Mon 8-Jan-2018 10:00 UTC ; Tues 18-Dec-2018 12:00 UTC r=604800 3600 0 90000 ; 1 week, 1 hour, zero, 25 hours z=3730928400 -1h 3749680800 0 ; Sun 25-Mar-2018 1:00 UTC, ; offset 1 hour, ; Sun 28-Oct-2018 2:00 UTC, ; no offset
t=3724394400 3754123200 ; Mon 8-Jan-2018 10:00 UTC ; Tues 18-Dec-2018 12:00 UTC r=604800 3600 0 90000 ; 1 week, 1 hour, zero, 25 hours z=3730928400 -1h 3749680800 0 ; Sun 25-Mar-2018 1:00 UTC, ; offset 1 hour, ; Sun 28-Oct-2018 2:00 UTC, ; no offset
This specifies that at time 3730928400 (Sun 25-Mar-2018 1:00 UTC, the onset of British Summer Time) the time base by which the session's repeat times are calculated is shifted back by 1 hour, and that at time 3749680800 (Sun 28-Oct-2018 2:00 UTC, the end of British Summer Time) the session's original time base is restored. Adjustments are always relative to the specified start time -- they are not cumulative.
Это указывает, что в момент времени 3730928400 (воскресенье, 25 марта 2018 г., 1:00 UTC, начало британского летнего времени) база времени, по которой вычисляются времена повторения сессии, сдвигается назад на 1 час, а в момент времени 3749680800 (воскресенье, 28 октября 2018 г., 2:00 UTC, конец британского летнего времени) исходная база времени сессии восстанавливается. Коррекции всегда задаются относительно указанного времени начала — они не накапливаются.
If a session is likely to last several years, it is expected that the session description will be modified periodically rather than transmit several years' worth of adjustments in one session description.
Если сессия, вероятно, продлится несколько лет, ожидается, что описание сессии будет периодически изменяться, а не передавать коррекции за несколько лет в одном описании сессии.

k=<method> k=<method>:<encryption key>

5.13. Attributes ("a=")
5.13. Атрибуты ("a=")
a=<attribute-name> a=<attribute-name>:<attribute-value>
a=<attribute-name> a=<attribute-name>:<attribute-value>
Attributes are the primary means for extending SDP. Attributes may be defined to be used as session-level attributes, media-level attributes, or both. (Attribute scopes in addition to media-level and session-level scopes may also be defined in extensions to this document, e.g., [RFC5576] and [RFC8864].)
Атрибуты — основное средство расширения SDP. Атрибуты могут определяться для использования в качестве атрибутов уровня сессии, атрибутов уровня медиаданных или и тех и других. (Помимо области действия на уровне медиаданных и на уровне сессии, в расширениях настоящего документа могут определяться и другие области действия атрибутов, например в [RFC5576] и [RFC8864].)
A media description may contain any number of "a=" lines (attribute- fields) that are media description specific. These are referred to as media-level attributes and add information about the media description. Attribute-fields can also be added before the first media description; these session-level attributes convey additional information that applies to the session as a whole rather than to individual media descriptions.
Описание медиаданных может содержать любое число строк "a=" (полей атрибутов), специфичных для этого описания медиаданных. Они называются атрибутами уровня медиаданных и добавляют сведения об описании медиаданных. Поля атрибутов можно также добавлять перед первым описанием медиаданных; такие атрибуты уровня сессии передают дополнительные сведения, относящиеся к сессии в целом, а не к отдельным описаниям медиаданных.
Attribute-fields may be of two forms:
Поля атрибутов могут иметь две формы:
* A property attribute is simply of the form "a=<attribute-name>". These are binary attributes, and the presence of the attribute conveys that the attribute is a property of the session. An example might be "a=recvonly".
* Атрибут-свойство имеет просто вид "a=<attribute-name>". Это двоичные атрибуты, и присутствие атрибута означает, что атрибут является свойством сессии. Примером может служить "a=recvonly".
* A value attribute is of the form "a=<attribute-name>:<attribute- value>". For example, a whiteboard could have the value attribute "a=orient:landscape".
* Атрибут-значение имеет вид "a=<attribute-name>:<attribute-value>". Например, у доски (whiteboard) может быть атрибут-значение "a=orient:landscape".
Attribute interpretation depends on the media tool being invoked. Thus receivers of session descriptions should be configurable in their interpretation of session descriptions in general and of attributes in particular.
Интерпретация атрибутов зависит от вызываемого инструмента медиаданных. Поэтому получатели описаний сессий должны иметь возможность настраивать интерпретацию описаний сессий в целом и атрибутов в частности.
Attribute names MUST use the US-ASCII subset of ISO-10646/UTF-8.
Имена атрибутов ДОЛЖНЫ использовать подмножество US-ASCII из ISO-10646/UTF-8.
Attribute values are octet strings, and MAY use any octet value except 0x00 (Nul), 0x0A (LF), and 0x0D (CR). By default, attribute values are to be interpreted as in ISO-10646 character set with UTF-8 encoding. Unlike other text fields, attribute values are NOT normally affected by the "a=charset:" attribute as this would make comparisons against known values problematic. However, when an attribute is defined, it can be defined to be charset dependent, in which case its value should be interpreted in the session charset rather than in ISO-10646.
Значения атрибутов — это октетные строки, и они МОГУТ использовать любое значение октета, кроме 0x00 (Nul), 0x0A (LF) и 0x0D (CR). По умолчанию значения атрибутов должны интерпретироваться так же, как в наборе символов ISO-10646 с кодировкой UTF-8. В отличие от других текстовых полей, значения атрибутов обычно НЕ подвержены влиянию атрибута "a=charset:", поскольку это сделало бы проблематичным сравнение с известными значениями. Однако при определении атрибута можно указать, что он зависит от набора символов, и в этом случае его значение следует интерпретировать в наборе символов сессии, а не в ISO-10646.
Attributes MUST be registered with IANA (see Section 8). If an attribute is received that is not understood, it MUST be ignored by the receiver.
Атрибуты ДОЛЖНЫ быть зарегистрированы в IANA (см. раздел 8). Если получен атрибут, который не понят, он ДОЛЖЕН игнорироваться получателем.

Атрибут "a=lang:" СЛЕДУЕТ задавать, когда сессия имеет масштаб, достаточный для пересечения географических границ, где язык участников нельзя предполагать, или когда сессия обладает возможностями на языках, отличных от локально предполагаемой нормы.
The "a=lang:" attribute is supposed to be used for setting the initial language(s) used in the session. Events during the session may influence which language(s) are used, and the participants are not strictly bound to only use the declared languages.
Атрибут "a=lang:" предполагается использовать для установки начального языка (языков), используемого в сессии. События во время сессии могут повлиять на то, какие языки используются, и участники не обязаны строго использовать только объявленные языки.
Most real-time use cases start with just one language used, while other cases involve a range of languages, e.g., an interpreted or subtitled session. When more than one "a=lang:" attribute is specified, the "a=lang:" attribute itself does not provide any information about multiple languages being intended to be used during the session, or if the intention is to only select one of the languages. If needed, a new attribute can be defined and used to indicate such intentions. Without such semantics, it is assumed that for a negotiated session one of the declared languages will be selected and used.
Большинство сценариев реального времени начинаются с использования только одного языка, тогда как другие сценарии охватывают ряд языков, например сессия с синхронным переводом или субтитрами. Без такой семантики предполагается, что для согласованной сессии будет выбран и использован один из объявленных языков.

7. Security Considerations
7. Вопросы безопасности
SDP is frequently used with the Session Initiation Protocol [RFC3261] using the offer/answer model [RFC3264] to agree on parameters for unicast sessions. When used in this manner, the security considerations of those protocols apply.
SDP часто используется с протоколом инициирования сессий [RFC3261] в модели предложения/ответа [RFC3264] для согласования параметров одноадресных сессий. При таком использовании применяются вопросы безопасности этих протоколов.
SDP is a session description format that describes multimedia sessions. Entities receiving and acting upon an SDP message SHOULD be aware that a session description cannot be trusted unless it has been obtained by an authenticated and integrity-protected transport protocol from a known and trusted source. Many different transport protocols may be used to distribute session descriptions, and the nature of the authentication and integrity protection will differ from transport to transport. For some transports, security features are often not deployed. In case a session description has not been obtained in a trusted manner, the endpoint SHOULD exercise care because, among other attacks, the media sessions received may not be the intended ones, the destination to where the media is sent may not be the expected one, any of the parameters of the session may be incorrect, or the media security may be compromised. It is up to the endpoint to make a sensible decision, taking into account the security risks of the application and the user preferences - the endpoint may decide to ask the user whether or not to accept the session.
SDP — это формат описания сессии, который описывает мультимедийные сессии. Субъекты, получающие сообщение SDP и действующие на его основе, ДОЛЖНЫ осознавать, что описанию сессии нельзя доверять, если оно не было получено по аутентифицированному и защищённому целостностью транспортному протоколу из известного и доверенного источника. Для распространения описаний сессий может использоваться множество разных транспортных протоколов, и характер аутентификации и защиты целостности будет различаться от транспорта к транспорту. Для некоторых транспортов средства безопасности часто не развёрнуты. В случае, если описание сессии было получено недоверенным образом, оконечной точке СЛЕДУЕТ проявлять осторожность, поскольку, помимо прочих атак, полученные медиасессии могут оказаться не теми, что предполагались, назначение, куда отправляются медиаданные, может не быть ожидаемым, любой из параметров сессии может быть неверным, или безопасность медиаданных может быть скомпрометирована. Оконечная точка должна сама принять разумное решение с учётом рисков безопасности приложения и предпочтений пользователя — она может решить спросить пользователя, принимать ли сессию.
On receiving a session description over an unauthenticated transport mechanism or from an untrusted party, software parsing the session description should take a few precautions. Similar concerns apply if integrity protection is not in place. Session descriptions contain information required to start software on the receiver's system. Software that parses a session description MUST NOT be able to start other software except that which is specifically configured as appropriate software to participate in multimedia sessions. It is normally considered inappropriate for software parsing a session description to start, on a user's system, software that is appropriate to participate in multimedia sessions, without the user first being informed that such software will be started and giving the user's consent. Thus, a session description arriving by session announcement, email, session invitation, or WWW page MUST NOT deliver the user into an interactive multimedia session unless the user has explicitly pre-authorized such action. As it is not always simple to tell whether or not a session is interactive, applications that are unsure should assume sessions are interactive. Software processing URLs contained in session descriptions should also heed the security considerations identified in [RFC3986].
При получении описания сессии по неаутентифицированному транспортному механизму или от недоверенной стороны программное обеспечение, разбирающее описание сессии, должно принять некоторые меры предосторожности. Аналогичные соображения применимы, если защита целостности не обеспечивается. Описания сессий содержат сведения, необходимые для запуска программного обеспечения в системе получателя. Программное обеспечение, разбирающее описание сессии, НЕ ДОЛЖНО иметь возможности запускать другое программное обеспечение, кроме того, которое специально сконфигурировано как подходящее для участия в мультимедийных сессиях. Обычно считается недопустимым, чтобы программное обеспечение, разбирающее описание сессии, запускало в системе пользователя программное обеспечение, подходящее для участия в мультимедийных сессиях, без предварительного уведомления пользователя о том, что такое программное обеспечение будет запущено, и без согласия пользователя. Таким образом, описание сессии, поступившее в виде анонса сессии, по электронной почте, в виде приглашения в сессию или со страницы WWW, НЕ ДОЛЖНО вовлекать пользователя в интерактивную мультимедийную сессию, если пользователь явно не дал предварительного разрешения на такое действие. Поскольку не всегда просто определить, является ли сессия интерактивной, приложения, которые не уверены, должны считать сессии интерактивными. Программное обеспечение, обрабатывающее URL, содержащиеся в описаниях сессий, также должно учитывать вопросы безопасности, указанные в [RFC3986].
In this specification, there are no attributes that would allow the recipient of a session description to be informed to start multimedia tools in a mode where they default to transmitting. Under some circumstances it might be appropriate to define such attributes. If this is done, an application parsing a session description containing such attributes SHOULD either ignore them or inform the user that joining this session will result in the automatic transmission of multimedia data. The default behavior for an unknown attribute is to ignore it.
В настоящей спецификации нет атрибутов, которые позволяли бы сообщить получателю описания сессии о необходимости запустить инструменты мультимедиа в режиме, где они по умолчанию передают. В некоторых обстоятельствах было бы уместно определить такие атрибуты. Если это будет сделано, приложение, разбирающее описание сессии, содержащее такие атрибуты, СЛЕДУЕТ либо игнорировать их, либо уведомить пользователя о том, что присоединение к этой сессии приведёт к автоматической передаче мультимедийных данных. Поведение по умолчанию для неизвестного атрибута — игнорировать его.
In certain environments, it has become common for intermediary systems to intercept and analyze session descriptions contained within other signaling protocols. This is done for a range of purposes, including but not limited to opening holes in firewalls to allow media streams to pass, or to mark, prioritize, or block traffic selectively. In some cases, such intermediary systems may modify the session description, for example, to have the contents of the session description match NAT bindings dynamically created. These behaviors are NOT RECOMMENDED unless the session description is conveyed in such a manner that allows the intermediary system to conduct proper checks to establish the authenticity of the session description, and the authority of its source to establish such communication sessions. SDP by itself does not include sufficient information to enable these checks: they depend on the encapsulating protocol (e.g., SIP or RTSP). The use of some procedures and SDP extensions (e.g., Interactive Connectivity Establishment (ICE) [RFC8445] and ICE-SIP- SDP [RFC8839]) may avoid the need for intermediaries to modify SDP.
В некоторых средах стало обычным, что промежуточные системы перехватывают и анализируют описания сессий, содержащиеся в других протоколах сигнализации. Это делается для ряда целей, включая, помимо прочего, открытие отверстий в межсетевых экранах, чтобы пропускать медиапотоки, или для маркировки, приоритизации или избирательной блокировки трафика. В некоторых случаях такие промежуточные системы могут изменять описание сессии, например, чтобы содержимое описания сессии соответствовало динамически создаваемым привязкам NAT. Такое поведение НЕ РЕКОМЕНДУЕТСЯ, если только описание сессии не передаётся так, что это позволяет промежуточной системе провести надлежащие проверки для установления подлинности описания сессии и полномочий его источника на установление таких сеансов связи. Сам по себе SDP не содержит достаточных сведений для таких проверок: они зависят от инкапсулирующего протокола (например, SIP или RTSP). Использование некоторых процедур и расширений SDP (например, установления интерактивного соединения (ICE) [RFC8445] и ICE-SIP-SDP [RFC8839]) может устранить необходимость изменения SDP промежуточными системами.
SDP MUST NOT be used to convey keying material (e.g., using the "a=crypto:" attribute [RFC4568]) unless it can be guaranteed that the channel over which the SDP is delivered is both private and authenticated.
SDP НЕ ДОЛЖЕН использоваться для передачи ключевого материала (например, с помощью атрибута "a=crypto:" [RFC4568]), если только нельзя гарантировать, что канал, по которому доставляется SDP, является одновременно частным и аутентифицированным.

8.2.2. Media Types (<media>)
8.2.2. Типы медиаданных (<media>)
The set of media types is intended to be small and SHOULD NOT be extended except under rare circumstances. The same rules should apply for media names as well as for top-level media types, and where possible the same name should be registered for SDP as for MIME. For media other than existing top-level media types, a Standards Track RFC MUST be produced for a new top-level media type to be registered, and the registration MUST provide good justification why no existing media name is appropriate (the "Standards Action" policy of [RFC8126]).
Набор типов медиаданных предполагается небольшим, и его НЕ СЛЕДУЕТ расширять, кроме редких случаев. Те же правила должны применяться как к именам медиаданных, так и к типам медиаданных верхнего уровня, и где это возможно, для SDP следует регистрировать то же имя, что и для MIME. Для медиаданных, отличных от существующих типов верхнего уровня, для регистрации нового типа медиаданных верхнего уровня ДОЛЖЕН быть выпущен RFC категории Standards Track, и в регистрации ДОЛЖНО быть приведено веское обоснование того, почему ни одно существующее имя медиаданных не подходит (политика "Standards Action" из [RFC8126]).
This memo registers the media types "audio", "video", "text", "application", and "message".
Настоящий меморандум регистрирует типы медиаданных "audio", "video", "text", "application" и "message".
Note: The media types "control" and "data" were listed as valid in an early version of this specification [RFC2327]; however, their semantics were never fully specified, and they are not widely used. These media types have been removed in this specification, although they still remain valid media type capabilities for a SIP user agent as defined in [RFC3840]. If these media types are considered useful in the future, a Standards Track RFC MUST be produced to document their use. Until that is done, applications SHOULD NOT use these types and SHOULD NOT declare support for them in SIP capabilities declarations (even though they exist in the registry created by [RFC3840]). Also note that [RFC6466] defined the "image" media type.
Примечание: типы медиаданных "control" и "data" были указаны как допустимые в ранней версии настоящей спецификации [RFC2327]; однако их семантика никогда не была полностью определена, и они мало используются. В настоящей спецификации эти типы медиаданных удалены, хотя они по-прежнему остаются допустимыми возможностями типов медиаданных для пользовательского агента SIP, как определено в [RFC3840]. Если в будущем эти типы медиаданных будут сочтены полезными, для документирования их использования ДОЛЖЕН быть выпущен RFC категории Standards Track. До тех пор приложениям НЕ СЛЕДУЕТ использовать эти типы и НЕ СЛЕДУЕТ объявлять их поддержку в объявлениях возможностей SIP (хотя они существуют в реестре, созданном [RFC3840]). Отметьте также, что [RFC6466] определил тип медиаданных "image".
8.2.3. Transport Protocols (<proto>)
8.2.3. Транспортные протоколы (<proto>)
The <proto> subfield describes the transport protocol used. The registration procedure for this registry is "RFC Required".
Подполе <proto> описывает используемый транспортный протокол. Процедура регистрации для этого реестра — "RFC Required".
This document registers two values:
Настоящий документ регистрирует два значения:
* "RTP/AVP" is a reference to [RFC3550] used under the RTP Profile for Audio and Video Conferences with Minimal Control [RFC3551] running over UDP/IP.
* "RTP/AVP" — это ссылка на [RFC3550], используемый в профиле RTP для аудио- и видеоконференций с минимальным управлением [RFC3551] поверх UDP/IP.
* "udp" indicates direct use of UDP.
* "udp" указывает на непосредственное использование UDP.
New transport protocols MAY be defined, and MUST be registered with IANA. Registrations MUST reference an RFC describing the protocol. Such an RFC MAY be Experimental or Informational, although it is preferable that it be Standards Track. The RFC defining a new protocol MUST define the rules by which the <fmt> (see below) namespace is managed.
Новые транспортные протоколы МОГУТ быть определены и ДОЛЖНЫ быть зарегистрированы в IANA. Регистрации ДОЛЖНЫ ссылаться на RFC, описывающий протокол. <proto> names starting with "RTP/" MUST only be used for defining transport protocols that are profiles of RTP. For example, a profile whose short name is "XYZ" would be denoted by a <proto> subfield of "RTP/XYZ".
Имена <proto>, начинающиеся с "RTP/", ДОЛЖНЫ использоваться только для определения транспортных протоколов, являющихся профилями RTP. Например, профиль, краткое имя которого "XYZ", обозначался бы подполем <proto> "RTP/XYZ".
Each transport protocol, defined by the <proto> subfield, has an associated <fmt> namespace that describes the media formats that may be conveyed by that protocol. Formats cover all the possible encodings that could be transported in a multimedia session.
Каждый транспортный протокол, определяемый подполем <proto>, имеет связанное пространство имён <fmt>, которое описывает форматы медиаданных, передаваемые этим протоколом. Форматы охватывают все возможные кодирования, которые могут передаваться в мультимедийной сессии.
RTP payload formats under the "RTP/AVP" and other "RTP/*" profiles MUST use the payload type number as their <fmt> value. If the payload type number is dynamically assigned by this session description, an additional "a=rtpmap:" attribute MUST be included to specify the format name and parameters as defined by the media type registration for the payload format. It is RECOMMENDED that other RTP profiles that are registered (in combination with RTP) as SDP transport protocols specify the same rules for the <fmt> namespace.
Форматы полезной нагрузки RTP в рамках профиля "RTP/AVP" и других профилей "RTP/*" ДОЛЖНЫ использовать номер типа полезной нагрузки в качестве значения <fmt>. Если номер типа полезной нагрузки назначается динамически этим описанием сессии, ДОЛЖЕН быть включён дополнительный атрибут "a=rtpmap:", задающий имя формата и параметры, как определено регистрацией типа медиаданных для формата полезной нагрузки. РЕКОМЕНДУЕТСЯ, чтобы другие профили RTP, регистрируемые (в сочетании с RTP) как транспортные протоколы SDP, задавали те же правила для пространства имён <fmt>.
For the "udp" protocol, the allowed <fmt> values are media subtypes from the IANA Media Types registry. The media type and subtype combination <media>/<fmt> specifies the format of the body of UDP packets. Use of an existing media subtype for the format is encouraged. If no suitable media subtype exists, it is RECOMMENDED that a new one be registered through the IETF process [RFC6838] by production of, or reference to, a Standards Track RFC that defines the format.
Для протокола "udp" допустимыми значениями <fmt> являются подтипы медиаданных из реестра типов медиаданных IANA. Комбинация типа и подтипа медиаданных <media>/<fmt> задаёт формат тела пакетов UDP. Поощряется использование существующего подтипа медиаданных для формата. Если подходящего подтипа медиаданных не существует, РЕКОМЕНДУЕТСЯ зарегистрировать новый через процесс IETF [RFC6838] путём выпуска RFC категории Standards Track, определяющего формат, или ссылки на него.
For other protocols, formats MAY be registered according to the rules of the associated <proto> specification.
Для других протоколов форматы МОГУТ регистрироваться согласно правилам соответствующей спецификации <proto>.
Registrations of new formats MUST specify which transport protocols they apply to.
Регистрации новых форматов ДОЛЖНЫ указывать, к каким транспортным протоколам они относятся.

8.2.6. Network Types (<nettype>)
8.2.6. Типы сетей (<nettype>)

To enable SDP to reference a new non-Internet environment, a new network type (<nettype> subfield value) MUST be registered with IANA. The registration is subject to the "RFC Required" policy of [RFC8126].
