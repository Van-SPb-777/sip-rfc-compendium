Abstract
Аннотация
This document describes a RTP (Real-Time Protocol) payload format for transporting MPEG (Moving Picture Experts Group) 1 or 2, layer III audio (commonly known as "MP3"). This format is an alternative to that described in RFC 2250, and performs better if there is packet loss.
Настоящий документ описывает формат полезной нагрузки RTP (протокола передачи в реальном времени) для передачи аудио MPEG (Moving Picture Experts Group) 1 или 2, слой III (обычно называемого «MP3»). Этот формат является альтернативой описанному в RFC 2250 и работает лучше при наличии потерь пакетов.
1. Introduction
1. Введение
While the RTP payload format defined in RFC 2250 [2] is generally applicable to all forms of MPEG audio or video, it is sub-optimal for MPEG 1 or 2, layer III audio (commonly known as "MP3"). The reason for this is that an MP3 frame is not a true "Application Data Unit" - it contains a back-pointer to data in earlier frames, and so cannot be decoded independently of these earlier frames. Because RFC 2250 defines that packet boundaries coincide with frame boundaries, it handles packet loss inefficiently when carrying MP3 data. The loss of an MP3 frame will render some data in previous (or future) frames useless, even if they are received without loss.
Хотя формат полезной нагрузки RTP, определённый в RFC 2250 [2], в общем случае применим ко всем видам аудио или видео MPEG, он неоптимален для аудио MPEG 1 или 2, слой III (обычно называемого «MP3»). Причина в том, что кадр MP3 не является настоящим «элементом данных приложения» — он содержит обратный указатель на данные в более ранних кадрах и поэтому не может быть декодирован независимо от этих более ранних кадров. Поскольку RFC 2250 определяет, что границы пакетов совпадают с границами кадров, при передаче данных MP3 он неэффективно обрабатывает потери пакетов. Потеря кадра MP3 сделает часть данных в предыдущих (или будущих) кадрах бесполезной, даже если они получены без потерь.
In this document we define an alternative RTP payload format for MP3 audio. This format uses a data-preserving rearrangement of the original MPEG frames, so that packet boundaries now coincide with true MP3 "Application Data Units", which can also (optionally) be rearranged in an interleaving pattern. This new format is therefore more data-efficient than RFC 2250 in the face of packet loss.
В настоящем документе мы определяем альтернативный формат полезной нагрузки RTP для аудио MP3. Этот формат использует сохраняющую данные перестановку исходных кадров MPEG, так что границы пакетов теперь совпадают с настоящими «элементами данных приложения» MP3, которые также могут (необязательно) переставляться по схеме перемежения. Поэтому этот новый формат более эффективен по данным, чем RFC 2250, при потерях пакетов.

3. A New Payload Format
3. Новый формат полезной нагрузки
As noted in [5], a payload format should be designed so that packet boundaries coincide with "codec frame boundaries" - i.e., with ADUs. In the RFC 2250 payload format for MPEG audio [2], each RTP packet payload contains MP3 frames. In this new payload format for MP3 audio, however, each RTP packet payload contains "ADU frames", each preceded by an "ADU descriptor".
Как отмечено в [5], формат полезной нагрузки следует проектировать так, чтобы границы пакетов совпадали с «границами кадров кодека», т.е. с ADU. В формате полезной нагрузки RFC 2250 для аудио MPEG [2] каждая полезная нагрузка пакета RTP содержит кадры MP3. Однако в этом новом формате полезной нагрузки для аудио MP3 каждая полезная нагрузка пакета RTP содержит «ADU-кадры», каждому из которых предшествует «дескриптор ADU».

3.1. ADU-кадры

3.3. Packing rules
3.3. Правила упаковки
Each RTP packet payload begins with a "ADU descriptor", followed by "ADU frame" data. Normally, this "ADU descriptor"+"ADU frame" will fit completely within the RTP packet. In this case, more than one successive "ADU descriptor"+"ADU frame" MAY be packed into a single RTP packet, provided that they all fit completely.
Каждая полезная нагрузка пакета RTP начинается с «дескриптора ADU», за которым следуют данные «ADU-кадра». Обычно эта пара «дескриптор ADU»+«ADU-кадр» полностью помещается в пакет RTP. В этом случае в один пакет RTP МОЖЕТ быть упаковано более одной последовательной пары «дескриптор ADU»+«ADU-кадр» при условии, что все они помещаются полностью.
If, however, a single "ADU descriptor"+"ADU frame" is too large to fit within an RTP packet, then the "ADU frame" is split across two or more successive RTP packets. Each such packet begins with an ADU descriptor. The first packet's descriptor has a "C" (continuation) flag of 0; the following packets' descriptors each have a "C" flag of 1. Each descriptor, in this case, has the same "ADU size" value: the size of the entire "ADU frame" (not just the portion that will fit within a single RTP packet). Each such packet (even the last one) contains only one "ADU descriptor".
Если же одна пара «дескриптор ADU»+«ADU-кадр» слишком велика, чтобы поместиться в пакет RTP, то «ADU-кадр» разделяется между двумя или более последовательными пакетами RTP. Каждый такой пакет начинается с дескриптора ADU. Дескриптор первого пакета имеет флаг «C» (продолжения), равный 0; дескрипторы следующих пакетов имеют флаг «C», равный 1. Каждый дескриптор в этом случае имеет одно и то же значение «ADU size»: размер всего «ADU-кадра» (а не только той части, которая поместится в один пакет RTP). Каждый такой пакет (даже последний) содержит только один «дескриптор ADU».
3.4. RTP header fields
3.4. Поля заголовка RTP
Payload Type: The (static) payload type 14 that was defined for MPEG audio [6] MUST NOT be used. Instead, a different, dynamic payload type MUST be used - i.e., one in the range [96,127].
Тип полезной нагрузки: (статический) тип полезной нагрузки 14, определённый для аудио MPEG [6], НЕ ДОЛЖЕН использоваться. Вместо него ДОЛЖЕН использоваться другой, динамический тип полезной нагрузки, т.е. из диапазона [96,127].
M bit: This payload format defines no use for this bit. Senders SHOULD set this bit to zero in each outgoing packet.
Бит M: этот формат полезной нагрузки не определяет использования этого бита. Отправителям СЛЕДУЕТ устанавливать этот бит в ноль в каждом исходящем пакете.
Timestamp: This is a 32-bit 90 kHz timestamp, representing the presentation time of the first ADU packed within the packet.
Временная метка: это 32-битная временная метка 90 кГц, представляющая время представления первого ADU, упакованного в пакет.
3.5. Handling received data
3.5. Обработка принятых данных
Note that no information is lost by converting a sequence of MP3 frames to a corresponding sequence of "ADU frames", so a receiving RTP implementation can either feed the ADU frames directly to an appropriately modified MP3 decoder, or convert them back into a sequence of MP3 frames, as described in appendix A.2 below.
Отметим, что при преобразовании последовательности кадров MP3 в соответствующую последовательность «ADU-кадров» информация не теряется, поэтому принимающая реализация RTP может либо подавать ADU-кадры непосредственно в соответствующим образом изменённый декодер MP3, либо преобразовывать их обратно в последовательность кадров MP3, как описано в приложении A.2 ниже.
4. Handling Multiple MPEG Audio Layers
4. Обработка нескольких звуковых слоёв MPEG
The RTP payload format described here is intended only for MPEG 1 or 2, layer III audio ("MP3"). In contrast, layer I and layer II frames are self-contained, without a back-pointer to earlier frames. However, it is possible (although unusual) for a sequence of audio frames to consist of a mixture of layer III frames and layer I or II frames. When such a sequence is transmitted, only layer III frames are converted to ADUs; layer I or II frames are sent 'as is' (except for the prepending of an "ADU descriptor"). Similarly, the receiver of a sequence of frames - using this payload format - leaves layer I and II frames untouched (after removing the prepended "ADU descriptor), but converts layer III frames from "ADU frames" to regular MP3 frames. (Recall that each frame's layer is identified from its 4-byte MPEG header.)
Описанный здесь формат полезной нагрузки RTP предназначен только для аудио MPEG 1 или 2, слой III («MP3»). Напротив, кадры слоя I и слоя II самодостаточны, без обратного указателя на более ранние кадры. Однако возможно (хотя и необычно), что последовательность аудиокадров состоит из смеси кадров слоя III и кадров слоя I или II. Когда такая последовательность передаётся, в ADU преобразуются только кадры слоя III; кадры слоя I или II отправляются «как есть» (за исключением добавления в начало «дескриптора ADU»). Аналогично, приёмник последовательности кадров, использующий этот формат полезной нагрузки, оставляет кадры слоя I и II нетронутыми (после удаления добавленного в начало «дескриптора ADU»), но преобразует кадры слоя III из «ADU-кадров» в обычные кадры MP3. (Напомним, что слой каждого кадра определяется по его 4-байтному заголовку MPEG.)
If you are transmitting a stream consists *only* of layer I or layer II frames (i.e., without any MP3 data), then there is no benefit to using this payload format, *unless* you are using the interleaving mechanism.
Если вы передаёте поток, состоящий *только* из кадров слоя I или слоя II (т.е. без каких-либо данных MP3), то использование этого формата полезной нагрузки не даёт выгоды, *если только* вы не используете механизм перемежения.
5. Frame Packetizing and Depacketizing
5. Пакетирование и депакетирование кадров
The transmission of a sequence of MP3 frames takes the following steps:
Передача последовательности кадров MP3 включает следующие шаги:
MP3 frames -1-> ADU frames -2-> interleaved ADU frames -3-> RTP packets
MP3 frames -1-> ADU frames -2-> interleaved ADU frames -3-> RTP packets
Step 1, the conversion of a sequence of MP3 frames to a corresponding sequence of ADU frames, takes place as described in sections 2 and 3.1 above. (Note also the pseudo-code in appendix A.1.)
Шаг 1 — преобразование последовательности кадров MP3 в соответствующую последовательность ADU-кадров — выполняется так, как описано в разделах 2 и 3.1 выше. (См. также псевдокод в приложении A.1.)
Step 2 is the reordering of the sequence of ADU frames in an (optional) interleaving pattern, prior to packetization, as described in section 6 below. (Note also the pseudo-code in appendix B.1.) Interleaving helps reduce the effect of packet loss, by distributing consecutive ADU frames over non-consecutive packets. (Note that because of the back-pointer in MP3 frames, interleaving can be applied - in general - only to ADU frames. Thus, interleaving was not possible for RFC 2250.)
Шаг 2 — это переупорядочивание последовательности ADU-кадров по (необязательной) схеме перемежения перед пакетированием, как описано в разделе 6 ниже. (См. также псевдокод в приложении B.1.) Перемежение помогает снизить влияние потерь пакетов, распределяя последовательные ADU-кадры по непоследовательным пакетам. (Отметим, что из-за обратного указателя в кадрах MP3 перемежение в общем случае можно применять только к ADU-кадрам. Таким образом, для RFC 2250 перемежение было невозможно.)
Step 3 is the packetizing of a sequence of (interleaved) ADU frames into RTP packets - as described in section 3.3 above. Each packet's RTP timestamp is the presentation time of the first ADU that is packed within it. Note that, if interleaving was done in step 2, the RTP timestamps on outgoing packets will not necessarily be monotonically nondecreasing.
Шаг 3 — это пакетирование последовательности (перемеженных) ADU-кадров в пакеты RTP, как описано в разделе 3.3 выше. Временной меткой RTP каждого пакета является время представления первого ADU, упакованного в него. Отметим, что если на шаге 2 выполнялось перемежение, временные метки RTP исходящих пакетов не обязательно будут монотонно неубывающими.

RTP packets -4-> RTP packets ordered by RTP sequence number -5-> interleaved ADU frames -6-> ADU frames -7-> MP3 frames

In MPEG audio frames (MPEG 1 or 2; all layers) the high-order 11 bits of the 4-byte MPEG header ('syncword') are always all-one (i.e., 0xFFE). When reordering a sequence of ADU frames for transmission, we reuse these 11 bits as an "Interleaving Sequence Number" (ISN). (Upon reception, they are replaced with 0xFFE once again.) В кадрах аудио MPEG (MPEG 1 или 2; все слои) старшие 11 бит 4-байтного заголовка MPEG («syncword») всегда равны единице (т.е. 0xFFE). При переупорядочивании последовательности ADU-кадров для передачи мы повторно используем эти 11 бит как «номер последовательности перемежения» (ISN). (При приёме они снова заменяются на 0xFFE.) The reason for breaking the ISN into "Interleave Cycle Count" and "Interleave Index" (rather than just treating it as a single 11-bit counter) is to give receivers a way of knowing when an ADU frame should be 'released' to the ADU->MP3 conversion process (step 7 above), rather than waiting for more interleaved ADU frames to arrive. E.g., in the example above, when the receiver sees a frame with ISN (<something>,1), it knows that it can release all previously-seen frames with ISN (<something>,0), even if some other (<something>,0) frames remain missing due to packet loss. A 8-bit Interleave Index allows interleave cycles of size up to 256.
Причина разбиения ISN на «счётчик циклов перемежения» и «индекс перемежения» (вместо того чтобы рассматривать его как единый 11-битный счётчик) состоит в том, чтобы дать приёмникам способ узнавать, когда ADU-кадр следует «выпустить» в процесс преобразования ADU->MP3 (шаг 7 выше), вместо ожидания прибытия новых перемеженных ADU-кадров. Например, в приведённом выше примере, когда приёмник видит кадр с ISN (<что-то>,1), он знает, что может выпустить все ранее увиденные кадры с ISN (<что-то>,0), даже если некоторые другие кадры (<что-то>,0) остаются отсутствующими из-за потерь пакетов. 8-битный индекс перемежения позволяет использовать циклы перемежения размером до 256.
The choice of an interleaving order can be made independently of RTP packetization. Thus, a simple implementation could choose an interleaving order first, reorder the ADU frames accordingly (step 2), then simply pack them sequentially into RTP packets (step 3). However, the size of ADU frames - and thus the number of ADU frames that will fit in each RTP packet - will typically vary in size, so a more optimal implementation would combine steps 2 and 3, by choosing an interleaving order that better reflected the number of ADU frames packed within each RTP packet.
Выбор порядка перемежения может быть сделан независимо от пакетирования RTP. Таким образом, простая реализация могла бы сначала выбрать порядок перемежения, переупорядочить ADU-кадры соответственно (шаг 2), а затем просто упаковать их последовательно в пакеты RTP (шаг 3). Однако размер ADU-кадров, а следовательно, и число ADU-кадров, помещающихся в каждый пакет RTP, обычно будет различаться, поэтому более оптимальная реализация объединила бы шаги 2 и 3, выбрав порядок перемежения, лучше отражающий число ADU-кадров, упакованных в каждый пакет RTP.
Each receiving implementation of this payload format MUST recognize the ISN and be able to perform deinterleaving of incoming ADU frames (step 6). However, a sending implementation of this payload format MAY choose not to perform interleaving - i.e., by omitting step 2. In this case, the high-order 11 bits in each 4-byte MPEG header would remain at 0xFFE. Receiving implementations would thus see a sequence of identical ISNs (all 0xFFE). They would handle this in the same way as if the Interleave Cycle Count changed with each ADU frame, by simply releasing the sequence of incoming ADU frames sequentially to the ADU->MP3 conversion process (step 7), without reordering. (Note also the pseudo-code in appendix B.2.)

Однако отправляющая реализация этого формата полезной нагрузки МОЖЕТ не выполнять перемежение, т.е. опустить шаг 2. В этом случае старшие 11 бит в каждом 4-байтном заголовке MPEG останутся равными 0xFFE. Принимающие реализации таким образом увидят последовательность одинаковых ISN (все 0xFFE).
