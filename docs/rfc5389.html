Abstract
Аннотация
Session Traversal Utilities for NAT (STUN) is a protocol that serves as a tool for other protocols in dealing with Network Address Translator (NAT) traversal. It can be used by an endpoint to determine the IP address and port allocated to it by a NAT. It can also be used to check connectivity between two endpoints, and as a keep-alive protocol to maintain NAT bindings. STUN works with many existing NATs, and does not require any special behavior from them.
Session Traversal Utilities for NAT (STUN) — это протокол, служащий инструментом для других протоколов при обходе трансляторов сетевых адресов (NAT). Он может использоваться оконечной точкой для определения IP-адреса и порта, выделенных ему NAT. Он также может применяться для проверки связности между двумя оконечными точками и как протокол поддержания соединения для сохранения привязок NAT. STUN работает со многими существующими NAT и не требует от них какого-либо особого поведения.
STUN is not a NAT traversal solution by itself. Rather, it is a tool to be used in the context of a NAT traversal solution. This is an important change from the previous version of this specification (RFC 3489), which presented STUN as a complete solution.
Сам по себе STUN не является решением для обхода NAT. Это инструмент, используемый в контексте решения для обхода NAT. Это важное изменение по сравнению с предыдущей версией данной спецификации (RFC 3489), в которой STUN представлялся как законченное решение.
This document obsoletes RFC 3489.

1. Introduction
1. Введение в STUN
The protocol defined in this specification, Session Traversal Utilities for NAT, provides a tool for dealing with NATs. It provides a means for an endpoint to determine the IP address and port allocated by a NAT that corresponds to its private IP address and port. It also provides a way for an endpoint to keep a NAT binding alive. With some extensions, the protocol can be used to do connectivity checks between two endpoints [MMUSIC-ICE], or to relay packets between two endpoints [BEHAVE-TURN].
Определяемый в данной спецификации протокол Session Traversal Utilities for NAT предоставляет инструмент для работы с NAT. Он даёт оконечной точке средство определить IP-адрес и порт, выделенные NAT в соответствии с её частными IP-адресом и портом. Он также даёт оконечной точке способ поддерживать привязку NAT в активном состоянии. С некоторыми расширениями протокол может использоваться для проверок связности между двумя оконечными точками [MMUSIC-ICE] или для ретрансляции пакетов между двумя оконечными точками [BEHAVE-TURN].
In keeping with its tool nature, this specification defines an extensible packet format, defines operation over several transport protocols, and provides for two forms of authentication.
В соответствии со своей инструментальной природой данная спецификация определяет расширяемый формат пакетов, работу поверх нескольких транспортных протоколов и предусматривает две формы аутентификации.
STUN is intended to be used in context of one or more NAT traversal solutions. These solutions are known as STUN usages. Each usage describes how STUN is utilized to achieve the NAT traversal solution. Typically, a usage indicates when STUN messages get sent, which optional attributes to include, what server is used, and what authentication mechanism is to be used. Interactive Connectivity Establishment (ICE) [MMUSIC-ICE] is one usage of STUN. SIP Outbound [SIP-OUTBOUND] is another usage of STUN. In some cases, a usage will require extensions to STUN. A STUN extension can be in the form of new methods, attributes, or error response codes. More information on STUN usages can be found in Section 14.
STUN предназначен для использования в контексте одного или нескольких решений обхода NAT. Эти решения называются применениями STUN. Каждое применение описывает, как STUN используется для достижения решения по обходу NAT. Обычно применение указывает, когда отправляются сообщения STUN, какие необязательные атрибуты включать, какой сервер используется и какой механизм аутентификации применяется. Interactive Connectivity Establishment (ICE) [MMUSIC-ICE] — одно из применений STUN. SIP Outbound [SIP-OUTBOUND] — другое применение STUN. В некоторых случаях применение требует расширений STUN. Расширение STUN может иметь форму новых методов, атрибутов или кодов ответов об ошибках. Дополнительные сведения о применениях STUN можно найти в разделе 14.
2. Evolution from RFC 3489
2. Эволюция от RFC 3489
STUN was originally defined in RFC 3489 [RFC3489]. That specification, sometimes referred to as "classic STUN", represented itself as a complete solution to the NAT traversal problem. In that solution, a client would discover whether it was behind a NAT, determine its NAT type, discover its IP address and port on the public side of the outermost NAT, and then utilize that IP address and port within the body of protocols, such as the Session Initiation Protocol (SIP) [RFC3261]. However, experience since the publication of RFC 3489 has found that classic STUN simply does not work sufficiently well to be a deployable solution. The address and port learned through classic STUN are sometimes usable for communications with a peer, and sometimes not. Classic STUN provided no way to discover whether it would, in fact, work or not, and it provided no remedy in cases where it did not. Furthermore, classic STUN's algorithm for classification of NAT types was found to be faulty, as many NATs did not fit cleanly into the types defined there. Classic STUN also had a security vulnerability -- attackers could provide the client with incorrect mapped addresses under certain topologies and constraints, and this was fundamentally not solvable through any cryptographic means.
STUN был первоначально определён в RFC 3489 [RFC3489]. Эта спецификация, иногда называемая «классическим STUN», представляла себя как полное решение проблемы обхода NAT. В этом решении клиент должен был обнаружить, находится ли он за NAT, определить тип своего NAT, узнать свой IP-адрес и порт на публичной стороне самого внешнего NAT, а затем использовать эти IP-адрес и порт в теле таких протоколов, как протокол инициирования сеансов (SIP) [RFC3261]. Однако опыт после публикации RFC 3489 показал, что классический STUN просто недостаточно хорошо работает, чтобы быть развёртываемым решением. Адрес и порт, полученные с помощью классического STUN, иногда пригодны для связи с одноранговым узлом, а иногда нет. Классический STUN не давал способа узнать, будет ли это работать на самом деле, и не предлагал средства исправления в случаях, когда не работало. Более того, алгоритм классификации типов NAT в классическом STUN оказался ошибочным, поскольку многие NAT не укладывались чисто в определённые там типы. Классический STUN также имел уязвимость безопасности — злоумышленники могли предоставить клиенту неверные отображаемые адреса при определённых топологиях и ограничениях, и это в принципе не решалось никакими криптографическими средствами. Хотя эта проблема сохраняется и в данной спецификации, теперь эти атаки смягчаются за счёт использования более полных решений, применяющих STUN.
Though this problem remains with this specification, those attacks are now mitigated through the use of more complete solutions that make use of STUN.
Хотя эта проблема сохраняется и в настоящей спецификации, теперь такие атаки смягчаются за счёт более полных решений, использующих STUN.
For these reasons, this specification obsoletes RFC 3489, and instead describes STUN as a tool that is utilized as part of a complete NAT traversal solution. ICE [MMUSIC-ICE] is a complete NAT traversal solution for protocols based on the offer/answer [RFC3264] methodology, such as SIP. SIP Outbound [SIP-OUTBOUND] is a complete solution for traversal of SIP signaling, and it uses STUN in a very different way. Though it is possible that a protocol may be able to use STUN by itself (classic STUN) as a traversal solution, such usage is not described here and is strongly discouraged for the reasons described above.
По этим причинам данная спецификация заменяет RFC 3489 и вместо этого описывает STUN как инструмент, используемый в составе полного решения по обходу NAT. ICE [MMUSIC-ICE] — полное решение по обходу NAT для протоколов, основанных на методике offer/answer [RFC3264], таких как SIP. SIP Outbound [SIP-OUTBOUND] — полное решение для обхода NAT при передаче сигнализации SIP, и оно использует STUN совершенно иным образом. Хотя протокол может быть способен использовать STUN сам по себе (классический STUN) как решение по обходу, такое применение здесь не описывается и настоятельно не рекомендуется по причинам, изложенным выше.
The on-the-wire protocol described here is changed only slightly from classic STUN. The protocol now runs over TCP in addition to UDP. Extensibility was added to the protocol in a more structured way. A magic cookie mechanism for demultiplexing STUN with application protocols was added by stealing 32 bits from the 128-bit transaction ID defined in RFC 3489, allowing the change to be backwards compatible. Mapped addresses are encoded using a new exclusive-or format. There are other, more minor changes. See Section 19 for a more complete listing.
Описываемый здесь протокол передачи лишь незначительно отличается от классического STUN. Теперь протокол работает поверх TCP в дополнение к UDP. Расширяемость добавлена в протокол более структурированным образом. Механизм magic cookie для демультиплексирования STUN с прикладными протоколами добавлен путём заимствования 32 бит из 128-битного идентификатора транзакции, определённого в RFC 3489, что позволило сделать изменение обратно совместимым. Отображаемые адреса кодируются с использованием нового формата исключающего ИЛИ. Есть и другие, более мелкие изменения. См. раздел 19 для более полного перечня.
Due to the change in scope, STUN has also been renamed from "Simple Traversal of UDP through NAT" to "Session Traversal Utilities for NAT". The acronym remains STUN, which is all anyone ever remembers anyway.
Из-за изменения области применения STUN также был переименован из «Simple Traversal of UDP through NAT» в «Session Traversal Utilities for NAT». Аббревиатура осталась STUN — это всё, что кто-либо вообще запоминает.

One possible STUN configuration is shown in Figure 1. In this configuration, there are two entities (called STUN agents) that implement the STUN protocol. The lower agent in the figure is the client, and is connected to private network 1. This network connects to private network 2 through NAT 1. Private network 2 connects to the public Internet through NAT 2. The upper agent in the figure is the server, and resides on the public Internet.
На рисунке 1 показана одна из возможных конфигураций STUN. В этой конфигурации имеются две сущности (называемые агентами STUN), реализующие протокол STUN. Нижний агент на рисунке — клиент, подключённый к частной сети 1. Эта сеть соединяется с частной сетью 2 через NAT 1. Частная сеть 2 соединяется с публичным Интернетом через NAT 2. Верхний агент на рисунке — сервер, находящийся в публичном Интернете.
STUN is a client-server protocol. It supports two types of transactions. One is a request/response transaction in which a client sends a request to a server, and the server returns a response. The second is an indication transaction in which either agent -- client or server -- sends an indication that generates no response. Both types of transactions include a transaction ID, which is a randomly selected 96-bit number. For request/response transactions, this transaction ID allows the client to associate the response with the request that generated it; for indications, the transaction ID serves as a debugging aid.
STUN — протокол клиент-сервер. Он поддерживает два типа транзакций. Первый — транзакция запрос/ответ, в которой клиент отправляет серверу запрос, а сервер возвращает ответ. Второй — транзакция-индикация, в которой любой агент (клиент или сервер) отправляет индикацию, не порождающую ответа. Оба типа транзакций содержат идентификатор транзакции — случайно выбранное 96-битное число. В транзакциях запрос/ответ этот идентификатор позволяет клиенту связать ответ с породившим его запросом; в индикациях идентификатор транзакции служит средством отладки.
All STUN messages start with a fixed header that includes a method, a class, and the transaction ID. The method indicates which of the various requests or indications this is; this specification defines just one method, Binding, but other methods are expected to be defined in other documents. The class indicates whether this is a request, a success response, an error response, or an indication. Following the fixed header comes zero or more attributes, which are Type-Length-Value extensions that convey additional information for the specific message.
Все сообщения STUN начинаются с фиксированного заголовка, включающего метод, класс и идентификатор транзакции. Метод указывает, какой из различных запросов или индикаций представляет собой данное сообщение; данная спецификация определяет только один метод — Binding, но другие методы предполагается определить в иных документах. Класс указывает, является ли сообщение запросом, ответом об успехе, ответом об ошибке или индикацией. За фиксированным заголовком следуют ноль или более атрибутов — расширения типа Type-Length-Value, передающие дополнительную информацию для конкретного сообщения.
This document defines a single method called Binding. The Binding method can be used either in request/response transactions or in indication transactions. When used in request/response transactions, the Binding method can be used to determine the particular "binding" a NAT has allocated to a STUN client. When used in either request/ response or in indication transactions, the Binding method can also be used to keep these "bindings" alive.
Данный документ определяет единственный метод — Binding. Метод Binding может использоваться как в транзакциях запрос/ответ, так и в транзакциях-индикациях. При использовании в транзакциях запрос/ответ метод Binding может служить для определения конкретной «привязки», которую NAT выделил клиенту STUN. При использовании в транзакциях запрос/ответ или в транзакциях-индикациях метод Binding также может служить для поддержания этих «привязок» в активном состоянии.
In the Binding request/response transaction, a Binding request is sent from a STUN client to a STUN server. When the Binding request arrives at the STUN server, it may have passed through one or more NATs between the STUN client and the STUN server (in Figure 1, there were two such NATs). As the Binding request message passes through a NAT, the NAT will modify the source transport address (that is, the source IP address and the source port) of the packet. As a result, the source transport address of the request received by the server will be the public IP address and port created by the NAT closest to the server. This is called a reflexive transport address. The STUN server copies that source transport address into an XOR-MAPPED- ADDRESS attribute in the STUN Binding response and sends the Binding response back to the STUN client. As this packet passes back through a NAT, the NAT will modify the destination transport address in the IP header, but the transport address in the XOR-MAPPED-ADDRESS attribute within the body of the STUN response will remain untouched. In this way, the client can learn its reflexive transport address allocated by the outermost NAT with respect to the STUN server.
В транзакции запрос/ответ Binding запрос Binding отправляется от клиента STUN серверу STUN. Когда запрос Binding прибывает на сервер STUN, он мог пройти через один или несколько NAT между клиентом STUN и сервером STUN (на рисунке 1 таких NAT было два). По мере прохождения сообщения-запроса Binding через NAT тот изменяет исходный транспортный адрес (то есть исходный IP-адрес и исходный порт) пакета. В результате исходный транспортный адрес запроса, полученного сервером, будет публичным IP-адресом и портом, созданными NAT, ближайшим к серверу. Это называется рефлексивным транспортным адресом. Сервер STUN копирует этот исходный транспортный адрес в атрибут XOR-MAPPED-ADDRESS ответа Binding STUN и отправляет ответ Binding обратно клиенту STUN. При прохождении этого пакета обратно через NAT тот изменит транспортный адрес назначения в заголовке IP, но транспортный адрес в атрибуте XOR-MAPPED-ADDRESS в теле ответа STUN останется нетронутым. Таким образом клиент может узнать свой рефлексивный транспортный адрес, выделенный самым внешним NAT относительно сервера STUN.
In some usages, STUN must be multiplexed with other protocols (e.g., [MMUSIC-ICE], [SIP-OUTBOUND]). In these usages, there must be a way to inspect a packet and determine if it is a STUN packet or not. STUN provides three fields in the STUN header with fixed values that can be used for this purpose. If this is not sufficient, then STUN packets can also contain a FINGERPRINT value, which can further be used to distinguish the packets. STUN defines a set of optional procedures that a usage can decide to use, called mechanisms. These mechanisms include DNS discovery, a redirection technique to an alternate server, a fingerprint attribute for demultiplexing, and two authentication and message-integrity exchanges. The authentication mechanisms revolve around the use of a username, password, and message-integrity value. Two authentication mechanisms, the long-term credential mechanism and the short-term credential mechanism, are defined in this specification. Each usage specifies the mechanisms allowed with that usage.
В некоторых применениях STUN должен мультиплексироваться с другими протоколами (например, [MMUSIC-ICE], [SIP-OUTBOUND]). В таких применениях должен существовать способ проверить пакет и определить, является ли он пакетом STUN. STUN предоставляет в своём заголовке три поля с фиксированными значениями, которые можно использовать для этой цели. Если этого недостаточно, пакеты STUN могут также содержать значение FINGERPRINT, которое позволяет дополнительно различать пакеты. STUN определяет набор необязательных процедур, которые применение может решить использовать; они называются механизмами. Эти механизмы включают обнаружение через DNS, метод перенаправления на альтернативный сервер, атрибут отпечатка для демультиплексирования и два обмена для аутентификации и проверки целостности сообщений. Механизмы аутентификации вращаются вокруг использования имени пользователя, пароля и значения целостности сообщения. В данной спецификации определены два механизма аутентификации — механизм долгосрочных учетных данных и механизм краткосрочных учетных данных. Каждое применение указывает, какие механизмы с ним допустимы.
In the long-term credential mechanism, the client and server share a pre-provisioned username and password and perform a digest challenge/ response exchange inspired by (but differing in details) to the one defined for HTTP [RFC2617]. In the short-term credential mechanism, the client and the server exchange a username and password through some out-of-band method prior to the STUN exchange. For example, in the ICE usage [MMUSIC-ICE] the two endpoints use out-of-band signaling to exchange a username and password. These are used to integrity protect and authenticate the request and response. There is no challenge or nonce used.
В механизме долгосрочных учетных данных клиент и сервер совместно используют заранее предоставленные имя пользователя и пароль и выполняют обмен типа digest-запрос/ответ, вдохновлённый (но отличающийся в деталях) обменом, определённым для HTTP [RFC2617]. В механизме краткосрочных учетных данных клиент и сервер обмениваются именем пользователя и паролем через некоторый внешний метод до обмена STUN. Например, в применении ICE [MMUSIC-ICE] две оконечные точки используют внешнюю сигнализацию для обмена именем пользователя и паролем. Они используются для защиты целостности и аутентификации запроса и ответа. Ни запрос-вызов, ни nonce при этом не используются.

5. Definitions
5. Определения
STUN Agent: A STUN agent is an entity that implements the STUN protocol. The entity can be either a STUN client or a STUN server.
Агент STUN: агент STUN — сущность, реализующая протокол STUN. Такой сущностью может быть клиент STUN или сервер STUN.
STUN Client: A STUN client is an entity that sends STUN requests and receives STUN responses. A STUN client can also send indications. In this specification, the terms STUN client and client are synonymous.
Клиент STUN: клиент STUN — сущность, которая отправляет запросы STUN и принимает ответы STUN. Клиент STUN может также отправлять индикации. В данной спецификации термины «клиент STUN» и «клиент» равнозначны.
STUN Server: A STUN server is an entity that receives STUN requests and sends STUN responses. A STUN server can also send indications. In this specification, the terms STUN server and server are synonymous.
Сервер STUN: сервер STUN — сущность, которая принимает запросы STUN и отправляет ответы STUN. Сервер STUN может также отправлять индикации. В данной спецификации термины «сервер STUN» и «сервер» равнозначны.
Transport Address: The combination of an IP address and port number (such as a UDP or TCP port number).
Транспортный адрес: сочетание IP-адреса и номера порта (например, номера порта UDP или TCP).
Reflexive Transport Address: A transport address learned by a client that identifies that client as seen by another host on an IP network, typically a STUN server. When there is an intervening NAT between the client and the other host, the reflexive transport address represents the mapped address allocated to the client on the public side of the NAT. Reflexive transport addresses are learned from the mapped address attribute (MAPPED-ADDRESS or XOR- MAPPED-ADDRESS) in STUN responses.
Рефлексивный транспортный адрес: транспортный адрес, узнанный клиентом, который идентифицирует этого клиента в том виде, в каком его видит другой узел IP-сети, обычно сервер STUN. Если между клиентом и другим узлом имеется промежуточный NAT, рефлексивный транспортный адрес представляет отображаемый адрес, выделенный клиенту на публичной стороне NAT. Рефлексивные транспортные адреса узнаются из атрибута отображаемого адреса (MAPPED-ADDRESS или XOR-MAPPED-ADDRESS) в ответах STUN.
Mapped Address: Same meaning as reflexive address. This term is retained only for historic reasons and due to the naming of the MAPPED-ADDRESS and XOR-MAPPED-ADDRESS attributes.
Отображаемый адрес: то же значение, что и рефлексивный адрес. Этот термин сохранён исключительно по историческим причинам и из-за именования атрибутов MAPPED-ADDRESS и XOR-MAPPED-ADDRESS.
Long-Term Credential: A username and associated password that represent a shared secret between client and server. Long-term credentials are generally granted to the client when a subscriber enrolls in a service and persist until the subscriber leaves the service or explicitly changes the credential.
Долгосрочные учетные данные: имя пользователя и связанный с ним пароль, представляющие общий секрет между клиентом и сервером. Долгосрочные учетные данные обычно выдаются клиенту при подключении абонента к услуге и сохраняются, пока абонент не покинет услугу или явно не изменит учетные данные.
Long-Term Password: The password from a long-term credential.
Долгосрочный пароль: пароль из долгосрочных учетных данных.
Short-Term Credential: A temporary username and associated password that represent a shared secret between client and server. Short- term credentials are obtained through some kind of protocol mechanism between the client and server, preceding the STUN exchange. A short-term credential has an explicit temporal scope, which may be based on a specific amount of time (such as 5 minutes) or on an event (such as termination of a SIP dialog). The specific scope of a short-term credential is defined by the application usage.
Краткосрочные учетные данные: временные имя пользователя и связанный с ним пароль, представляющие общий секрет между клиентом и сервером. Краткосрочные учетные данные получаются через некоторый протокольный механизм между клиентом и сервером, предшествующий обмену STUN. Краткосрочные учетные данные имеют явную временную область действия, которая может основываться на определённом промежутке времени (например, 5 минут) или на событии (например, завершении диалога SIP). Конкретная область действия краткосрочных учетных данных определяется применением.
Short-Term Password: The password component of a short-term credential.
Краткосрочный пароль: компонент пароля краткосрочных учетных данных.
STUN Indication: A STUN message that does not receive a response.
Индикация STUN: сообщение STUN, которое не получает ответа.
Attribute: The STUN term for a Type-Length-Value (TLV) object that can be added to a STUN message. Attributes are divided into two types: comprehension-required and comprehension-optional. STUN agents can safely ignore comprehension-optional attributes they don't understand, but cannot successfully process a message if it contains comprehension-required attributes that are not understood.
Атрибут: термин STUN для объекта Type-Length-Value (TLV), который может быть добавлен в сообщение STUN. Атрибуты делятся на два типа: обязательные для понимания и необязательные для понимания. Агенты STUN могут безопасно игнорировать необязательные для понимания атрибуты, которых они не понимают, но не могут успешно обработать сообщение, если оно содержит обязательные для понимания атрибуты, которые не поняты.
RTO: Retransmission TimeOut, which defines the initial period of time between transmission of a request and the first retransmit of that request.
RTO: Retransmission TimeOut, определяющий начальный период времени между отправкой запроса и первой повторной передачей этого запроса.
6. STUN Message Structure
6. Структура сообщения STUN
STUN messages are encoded in binary using network-oriented format (most significant byte or octet first, also commonly known as big- endian). The transmission order is described in detail in Appendix B of RFC 791 [RFC0791]. Unless otherwise noted, numeric constants are in decimal (base 10).
Сообщения STUN кодируются в двоичном виде с использованием сетевого формата (сначала старший байт или октет, также обычно называемого big-endian). Порядок передачи подробно описан в приложении B к RFC 791 [RFC0791]. Если не указано иное, числовые константы даны в десятичной системе (по основанию 10).
All STUN messages MUST start with a 20-byte header followed by zero or more Attributes. The STUN header contains a STUN message type, magic cookie, transaction ID, and message length.
Все сообщения STUN ДОЛЖНЫ начинаться с 20-байтового заголовка, за которым следуют ноль или более атрибутов. Заголовок STUN содержит тип сообщения STUN, magic cookie, идентификатор транзакции и длину сообщения.

The magic cookie field MUST contain the fixed value 0x2112A442 in network byte order. In RFC 3489 [RFC3489], this field was part of the transaction ID; placing the magic cookie in this location allows a server to detect if the client will understand certain attributes that were added in this revised specification. In addition, it aids in distinguishing STUN packets from packets of other protocols when STUN is multiplexed with those other protocols on the same port.
Поле magic cookie ДОЛЖНО содержать фиксированное значение 0x2112A442 в сетевом порядке байтов. В RFC 3489 [RFC3489] это поле было частью идентификатора транзакции; размещение magic cookie в этом месте позволяет серверу определить, будет ли клиент понимать определённые атрибуты, добавленные в этой пересмотренной спецификации. Кроме того, это помогает отличать пакеты STUN от пакетов других протоколов, когда STUN мультиплексируется с этими другими протоколами на одном порту.
The transaction ID is a 96-bit identifier, used to uniquely identify STUN transactions. For request/response transactions, the transaction ID is chosen by the STUN client for the request and echoed by the server in the response. For indications, it is chosen by the agent sending the indication. It primarily serves to correlate requests with responses, though it also plays a small role in helping to prevent certain types of attacks. The server also uses the transaction ID as a key to identify each transaction uniquely across all clients. As such, the transaction ID MUST be uniformly and randomly chosen from the interval 0 .. 2**96-1, and SHOULD be cryptographically random. Resends of the same request reuse the same transaction ID, but the client MUST choose a new transaction ID for new transactions unless the new request is bit-wise identical to the previous request and sent from the same transport address to the same IP address. Success and error responses MUST carry the same transaction ID as their corresponding request. When an agent is acting as a STUN server and STUN client on the same port, the transaction IDs in requests sent by the agent have no relationship to the transaction IDs in requests received by the agent.
Идентификатор транзакции — 96-битный идентификатор, используемый для однозначной идентификации транзакций STUN. В транзакциях запрос/ответ идентификатор транзакции выбирается клиентом STUN для запроса и повторяется сервером в ответе. В индикациях он выбирается агентом, отправляющим индикацию. В первую очередь он служит для соотнесения запросов с ответами, хотя играет и небольшую роль в предотвращении некоторых видов атак. Сервер также использует идентификатор транзакции как ключ для однозначной идентификации каждой транзакции среди всех клиентов. Поэтому идентификатор транзакции ДОЛЖЕН выбираться равномерно и случайно из интервала 0 .. 2**96-1 и ДОЛЖЕН быть криптографически случайным. Повторные отправки одного и того же запроса используют один и тот же идентификатор транзакции, но клиент ДОЛЖЕН выбирать новый идентификатор транзакции для новых транзакций, если только новый запрос не является побитно идентичным предыдущему и не отправлен с того же транспортного адреса на тот же IP-адрес. Ответы об успехе и об ошибке ДОЛЖНЫ нести тот же идентификатор транзакции, что и соответствующий запрос. Когда агент действует как сервер STUN и клиент STUN на одном порту, идентификаторы транзакций в запросах, отправляемых агентом, никак не связаны с идентификаторами транзакций в запросах, принимаемых агентом.
The message length MUST contain the size, in bytes, of the message not including the 20-byte STUN header. Since all STUN attributes are padded to a multiple of 4 bytes, the last 2 bits of this field are always zero. This provides another way to distinguish STUN packets from packets of other protocols.
Длина сообщения ДОЛЖНА содержать размер сообщения в байтах, не включая 20-байтовый заголовок STUN. Поскольку все атрибуты STUN дополняются до кратности 4 байтам, последние 2 бита этого поля всегда нулевые. Это даёт ещё один способ отличать пакеты STUN от пакетов других протоколов.
Following the STUN fixed portion of the header are zero or more attributes. Each attribute is TLV (Type-Length-Value) encoded. The details of the encoding, and of the attributes themselves are given in Section 15.
За фиксированной частью заголовка STUN следуют ноль или более атрибутов. Каждый атрибут кодируется в формате TLV (Type-Length-Value). Подробные сведения о кодировании и о самих атрибутах приведены в разделе 15.

7. Базовые процедуры протокола
This section defines the base procedures of the STUN protocol. It describes how messages are formed, how they are sent, and how they are processed when they are received. It also defines the detailed processing of the Binding method. Other sections in this document describe optional procedures that a usage may elect to use in certain situations. Other documents may define other extensions to STUN, by adding new methods, new attributes, or new error response codes.
В этом разделе определены базовые процедуры протокола STUN. Он описывает, как формируются сообщения, как они отправляются и как обрабатываются при получении. Он также определяет подробную обработку метода Binding. Другие разделы данного документа описывают необязательные процедуры, которые применение может выбрать для использования в определённых ситуациях. Другие документы могут определять иные расширения STUN, добавляя новые методы, новые атрибуты или новые коды ответов об ошибках.
7.1. Forming a Request or an Indication
7.1. Формирование запроса или индикации
When formulating a request or indication message, the agent MUST follow the rules in Section 6 when creating the header. In addition, the message class MUST be either "Request" or "Indication" (as appropriate), and the method must be either Binding or some method defined in another document.
При формировании сообщения-запроса или сообщения-индикации агент ДОЛЖЕН соблюдать правила раздела 6 при создании заголовка. Кроме того, класс сообщения ДОЛЖЕН быть «Request» или «Indication» (в зависимости от случая), а метод должен быть либо Binding, либо каким-либо методом, определённым в другом документе.
The agent then adds any attributes specified by the method or the usage. For example, some usages may specify that the agent use an authentication method (Section 10) or the FINGERPRINT attribute (Section 8). If the agent is sending a request, it SHOULD add a SOFTWARE attribute to the request. Agents MAY include a SOFTWARE attribute in indications, depending on the method. Extensions to STUN should discuss whether SOFTWARE is useful in new indications.
Затем агент добавляет любые атрибуты, указанные методом или применением. Например, некоторые применения могут указывать, что агент использует метод аутентификации (раздел 10) или атрибут FINGERPRINT (раздел 8). Если агент отправляет запрос, он ДОЛЖЕН добавить в запрос атрибут SOFTWARE. Агенты МОГУТ включать атрибут SOFTWARE в индикации в зависимости от метода. Расширения STUN должны обсуждать, полезен ли SOFTWARE в новых индикациях.
For the Binding method with no authentication, no attributes are required unless the usage specifies otherwise.
Для метода Binding без аутентификации атрибуты не требуются, если применение не указывает иное.
All STUN messages sent over UDP SHOULD be less than the path MTU, if known. If the path MTU is unknown, messages SHOULD be the smaller of 576 bytes and the first-hop MTU for IPv4 [RFC1122] and 1280 bytes for IPv6 [RFC2460]. This value corresponds to the overall size of the IP packet. Consequently, for IPv4, the actual STUN message would need to be less than 548 bytes (576 minus 20-byte IP header, minus 8-byte UDP header, assuming no IP options are used). STUN provides no ability to handle the case where the request is under the MTU but the response would be larger than the MTU. It is not envisioned that this limitation will be an issue for STUN. The MTU limitation is a SHOULD, and not a MUST, to account for cases where STUN itself is being used to probe for MTU characteristics [BEHAVE-NAT]. Outside of this or similar applications, the MTU constraint MUST be followed.
Все сообщения STUN, отправляемые через UDP, ДОЛЖНЫ быть меньше MTU пути, если он известен. Если MTU пути неизвестен, сообщения ДОЛЖНЫ быть меньше из двух значений: 576 байт и MTU первого перехода для IPv4 [RFC1122], а для IPv6 — 1280 байт [RFC2460]. Это значение соответствует общему размеру IP-пакета. Следовательно, для IPv4 фактическое сообщение STUN должно быть меньше 548 байт (576 минус 20-байтовый заголовок IP, минус 8-байтовый заголовок UDP, если предположить, что параметры IP не используются). STUN не предоставляет возможности обработать случай, когда запрос укладывается в MTU, а ответ будет больше MTU. Не предполагается, что это ограничение станет проблемой для STUN. Ограничение MTU является требованием SHOULD, а не MUST, чтобы учесть случаи, когда сам STUN используется для зондирования характеристик MTU [BEHAVE-NAT]. Вне этого или подобных применений ограничение MTU ДОЛЖНО соблюдаться.
7.2. Sending the Request or Indication
7.2. Отправка запроса или индикации
The agent then sends the request or indication. This document specifies how to send STUN messages over UDP, TCP, or TLS-over-TCP; other transport protocols may be added in the future. The STUN usage must specify which transport protocol is used, and how the agent determines the IP address and port of the recipient. Section 9 describes a DNS-based method of determining the IP address and port of a server that a usage may elect to use. STUN may be used with anycast addresses, but only with UDP and in usages where authentication is not used.
Затем агент отправляет запрос или индикацию. Данный документ определяет, как отправлять сообщения STUN через UDP, TCP или TLS-over-TCP; другие транспортные протоколы могут быть добавлены в будущем. Применение STUN должно указывать, какой транспортный протокол используется и как агент определяет IP-адрес и порт получателя. В разделе 9 описан основанный на DNS метод определения IP-адреса и порта сервера, который применение может выбрать для использования. STUN может использоваться с anycast-адресами, но только с UDP и в применениях, где аутентификация не используется.
At any time, a client MAY have multiple outstanding STUN requests with the same STUN server (that is, multiple transactions in progress, with different transaction IDs). Absent other limits to the rate of new transactions (such as those specified by ICE for connectivity checks or when STUN is run over TCP), a client SHOULD space new transactions to a server by RTO and SHOULD limit itself to ten outstanding transactions to the same server.
В любой момент клиент МОЖЕТ иметь несколько незавершённых запросов STUN к одному и тому же серверу STUN (то есть несколько выполняющихся транзакций с разными идентификаторами транзакций). При отсутствии иных ограничений скорости новых транзакций (например, задаваемых ICE для проверок связности или когда STUN работает поверх TCP) клиент ДОЛЖЕН разносить новые транзакции к серверу на RTO и ДОЛЖЕН ограничивать себя десятью незавершёнными транзакциями к одному серверу.
7.2.1. Sending over UDP
7.2.1. Отправка через UDP
When running STUN over UDP, it is possible that the STUN message might be dropped by the network. Reliability of STUN request/ response transactions is accomplished through retransmissions of the request message by the client application itself. STUN indications are not retransmitted; thus, indication transactions over UDP are not reliable.
При работе STUN через UDP возможно, что сообщение STUN будет потеряно сетью. Надёжность транзакций запрос/ответ STUN достигается повторными передачами сообщения-запроса самим клиентским приложением. Индикации STUN не передаются повторно; таким образом, транзакции-индикации через UDP не являются надёжными.
A client SHOULD retransmit a STUN request message starting with an interval of RTO ("Retransmission TimeOut"), doubling after each retransmission. The RTO is an estimate of the round-trip time (RTT), and is computed as described in RFC 2988 [RFC2988], with two exceptions. First, the initial value for RTO SHOULD be configurable (rather than the 3 s recommended in RFC 2988) and SHOULD be greater than 500 ms. The exception cases for this "SHOULD" are when other mechanisms are used to derive congestion thresholds (such as the ones defined in ICE for fixed rate streams), or when STUN is used in non- Internet environments with known network capacities. In fixed-line access links, a value of 500 ms is RECOMMENDED. Second, the value of RTO SHOULD NOT be rounded up to the nearest second. Rather, a 1 ms accuracy SHOULD be maintained. As with TCP, the usage of Karn's algorithm is RECOMMENDED [KARN87]. When applied to STUN, it means that RTT estimates SHOULD NOT be computed from STUN transactions that result in the retransmission of a request.
Клиент ДОЛЖЕН повторно передавать сообщение-запрос STUN, начиная с интервала RTO («Retransmission TimeOut»), удваивая его после каждой повторной передачи. RTO — это оценка времени кругового обхода (RTT), вычисляемая так, как описано в RFC 2988 [RFC2988], с двумя исключениями. Во-первых, начальное значение RTO ДОЛЖНО быть настраиваемым (а не 3 с, рекомендованными в RFC 2988) и ДОЛЖНО быть больше 500 мс. Исключения из этого «SHOULD» — случаи, когда для вывода порогов перегрузки используются другие механизмы (например, определённые в ICE для потоков с фиксированной скоростью) или когда STUN используется в неинтернет-средах с известными характеристиками сети. На проводных абонентских линиях РЕКОМЕНДУЕТСЯ значение 500 мс. Во-вторых, значение RTO НЕ ДОЛЖНО округляться в большую сторону до ближайшей секунды. Скорее, ДОЛЖНА поддерживаться точность 1 мс. Как и в TCP, РЕКОМЕНДУЕТСЯ использование алгоритма Карна [KARN87]. В применении к STUN это означает, что оценки RTT НЕ ДОЛЖНЫ вычисляться по транзакциям STUN, которые приводят к повторной передаче запроса.
The value for RTO SHOULD be cached by a client after the completion of the transaction, and used as the starting value for RTO for the next transaction to the same server (based on equality of IP address). The value SHOULD be considered stale and discarded after 10 minutes.
Значение RTO ДОЛЖНО кэшироваться клиентом после завершения транзакции и использоваться как начальное значение RTO для следующей транзакции к тому же серверу (на основании совпадения IP-адреса). Значение следует считать устаревшим и отбрасывать через 10 минут.
Retransmissions continue until a response is received, or until a total of Rc requests have been sent. Rc SHOULD be configurable and SHOULD have a default of 7. If, after the last request, a duration equal to Rm times the RTO has passed without a response (providing ample time to get a response if only this final request actually succeeds), the client SHOULD consider the transaction to have failed. Rm SHOULD be configurable and SHOULD have a default of 16. A STUN transaction over UDP is also considered failed if there has been a hard ICMP error [RFC1122]. For example, assuming an RTO of 500 ms, requests would be sent at times 0 ms, 500 ms, 1500 ms, 3500 ms, 7500 ms, 15500 ms, and 31500 ms. If the client has not received a response after 39500 ms, the client will consider the transaction to have timed out.
Повторные передачи продолжаются до получения ответа или до отправки в общей сложности Rc запросов. Rc ДОЛЖНО быть настраиваемым и ДОЛЖНО по умолчанию равняться 7. Если после последнего запроса прошло время, равное Rm, умноженному на RTO, без ответа (что даёт достаточно времени для получения ответа, если успешным окажется только этот последний запрос), клиент ДОЛЖЕН считать транзакцию неуспешной. Rm ДОЛЖНО быть настраиваемым и ДОЛЖНО по умолчанию равняться 16. Транзакция STUN через UDP также считается неуспешной при получении жёсткой ошибки ICMP [RFC1122]. Например, при RTO 500 мс запросы отправлялись бы в моменты 0 мс, 500 мс, 1500 мс, 3500 мс, 7500 мс, 15500 мс и 31500 мс. Если клиент не получил ответ до 39500 мс, он будет считать, что транзакция истекла по времени.
7.2.2. Sending over TCP or TLS-over-TCP
7.2.2. Отправка через TCP или TLS-over-TCP
For TCP and TLS-over-TCP, the client opens a TCP connection to the server. In some usages of STUN, STUN is sent as the only protocol over the TCP connection. In this case, it can be sent without the aid of any additional framing or demultiplexing. In other usages, or with other extensions, it may be multiplexed with other data over a TCP connection. In that case, STUN MUST be run on top of some kind of framing protocol, specified by the usage or extension, which allows for the agent to extract complete STUN messages and complete application layer messages. The STUN service running on the well- known port or ports discovered through the DNS procedures in Section 9 is for STUN alone, and not for STUN multiplexed with other data. Consequently, no framing protocols are used in connections to those servers. When additional framing is utilized, the usage will specify how the client knows to apply it and what port to connect to. For example, in the case of ICE connectivity checks, this information is learned through out-of-band negotiation between client and server.
Для TCP и TLS-over-TCP клиент открывает TCP-соединение с сервером. В некоторых применениях STUN передаётся как единственный протокол через TCP-соединение. В этом случае его можно передавать без какой-либо дополнительной кадрировки или демультиплексирования. В других применениях или с другими расширениями он может мультиплексироваться с другими данными через TCP-соединение. В этом случае STUN ДОЛЖЕН работать поверх некоторого протокола кадрирования, заданного применением или расширением, который позволяет агенту извлекать полные сообщения STUN и полные сообщения прикладного уровня. Служба STUN, работающая на широко известном порту или портах, обнаруженных с помощью процедур DNS из раздела 9, предназначена только для STUN, а не для STUN, мультиплексированного с другими данными. Следовательно, при подключении к таким серверам протоколы кадрирования не используются. Когда дополнительная кадрировка применяется, применение указывает, как клиент узнаёт о необходимости её применять и к какому порту подключаться. Например, в случае проверок связности ICE эта информация узнаётся посредством внешних переговоров между клиентом и сервером.
When STUN is run by itself over TLS-over-TCP, the TLS_RSA_WITH_AES_128_CBC_SHA ciphersuite MUST be implemented at a minimum. Implementations MAY also support any other ciphersuite. When it receives the TLS Certificate message, the client SHOULD verify the certificate and inspect the site identified by the certificate. If the certificate is invalid or revoked, or if it does not identify the appropriate party, the client MUST NOT send the STUN message or otherwise proceed with the STUN transaction. The client MUST verify the identity of the server. To do that, it follows the identification procedures defined in Section 3.1 of RFC 2818 [RFC2818]. Those procedures assume the client is dereferencing a URI. For purposes of usage with this specification, the client treats the domain name or IP address used in Section 8.1 as the host portion of the URI that has been dereferenced. Alternatively, a client MAY be configured with a set of domains or IP addresses that are trusted; if a certificate is received that identifies one of those domains or IP addresses, the client considers the identity of the server to be verified.
Когда STUN работает сам по себе через TLS-over-TCP, как минимум ДОЛЖЕН быть реализован набор шифров TLS_RSA_WITH_AES_128_CBC_SHA. Реализации МОГУТ также поддерживать любой другой набор шифров. При получении сообщения TLS Certificate клиент ДОЛЖЕН проверить сертификат и исследовать сайт, идентифицированный сертификатом. Если сертификат недействителен или отозван либо не идентифицирует нужную сторону, клиент НЕ ДОЛЖЕН отправлять сообщение STUN или иным образом продолжать транзакцию STUN. Клиент ДОЛЖЕН проверить подлинность сервера. Для этого он следует процедурам идентификации, определённым в разделе 3.1 RFC 2818 [RFC2818]. Эти процедуры предполагают, что клиент выполняет разыменование URI. Для целей использования с данной спецификацией клиент рассматривает доменное имя или IP-адрес, используемые в разделе 8.1, как часть хоста URI, который был разыменован. В качестве альтернативы клиент МОЖЕТ быть настроен на набор доменов или IP-адресов, которым он доверяет; если получен сертификат, идентифицирующий один из этих доменов или IP-адресов, клиент считает подлинность сервера проверенной.
When STUN is run multiplexed with other protocols over a TLS-over-TCP connection, the mandatory ciphersuites and TLS handling procedures operate as defined by those protocols.
Когда STUN работает в мультиплексированном режиме с другими протоколами через соединение TLS-over-TCP, обязательные наборы шифров и процедуры обработки TLS действуют так, как определено этими протоколами.
Reliability of STUN over TCP and TLS-over-TCP is handled by TCP itself, and there are no retransmissions at the STUN protocol level. However, for a request/response transaction, if the client has not received a response by Ti seconds after it sent the SYN to establish the connection, it considers the transaction to have timed out. Ti SHOULD be configurable and SHOULD have a default of 39.5s. This value has been chosen to equalize the TCP and UDP timeouts for the default initial RTO. In addition, if the client is unable to establish the TCP connection, or the TCP connection is reset or fails before a response is received, any request/response transaction in progress is considered to have failed.
Надёжность STUN через TCP и TLS-over-TCP обеспечивается самим TCP, и на уровне протокола STUN повторных передач нет. Однако для транзакции запрос/ответ, если клиент не получил ответ в течение Ti секунд после отправки SYN для установления соединения, он считает, что транзакция истекла по времени. Ti ДОЛЖНО быть настраиваемым и ДОЛЖНО по умолчанию равняться 39,5 с. Это значение выбрано для выравнивания тайм-аутов TCP и UDP при начальном RTO по умолчанию. Кроме того, если клиент не может установить TCP-соединение либо TCP-соединение сбрасывается или отказывает до получения ответа, любая выполняющаяся транзакция запрос/ответ считается неуспешной.
The client MAY send multiple transactions over a single TCP (or TLS- over-TCP) connection, and it MAY send another request before receiving a response to the previous. The client SHOULD keep the connection open until it:
Клиент МОЖЕТ отправлять несколько транзакций через одно TCP-соединение (или соединение TLS-over-TCP) и МОЖЕТ отправить другой запрос до получения ответа на предыдущий. Клиент ДОЛЖЕН держать соединение открытым, пока он:
o has no further STUN requests or indications to send over that connection, and
o не имеет дальнейших запросов или индикаций STUN для отправки через это соединение, и
o has no plans to use any resources (such as a mapped address (MAPPED-ADDRESS or XOR-MAPPED-ADDRESS) or relayed address [BEHAVE-TURN]) that were learned though STUN requests sent over that connection, and
o не планирует использовать какие-либо ресурсы (такие как отображаемый адрес (MAPPED-ADDRESS или XOR-MAPPED-ADDRESS) или ретранслированный адрес [BEHAVE-TURN]), узнанные из запросов STUN, отправленных через это соединение, и
o if multiplexing other application protocols over that port, has finished using that other application, and
o если мультиплексирует другие прикладные протоколы через этот порт, не завершил использование того другого приложения, и
o if using that learned port with a remote peer, has established communications with that remote peer, as is required by some TCP NAT traversal techniques (e.g., [MMUSIC-ICE-TCP]).
o если использует этот узнанный порт с удалённым одноранговым узлом, не установил связь с этим удалённым узлом, как требуется некоторыми методами обхода TCP NAT (например, [MMUSIC-ICE-TCP]).
At the server end, the server SHOULD keep the connection open, and let the client close it, unless the server has determined that the connection has timed out (for example, due to the client disconnecting from the network). Bindings learned by the client will remain valid in intervening NATs only while the connection remains open. Only the client knows how long it needs the binding. The server SHOULD NOT close a connection if a request was received over that connection for which a response was not sent. A server MUST NOT ever open a connection back towards the client in order to send a response. Servers SHOULD follow best practices regarding connection management in cases of overload.
На стороне сервера сервер ДОЛЖЕН держать соединение открытым и позволять клиенту закрыть его, если только сервер не установил, что соединение истекло по времени (например, из-за отключения клиента от сети). Привязки, узнанные клиентом, останутся действительными в промежуточных NAT только пока соединение остаётся открытым. Только клиент знает, как долго ему нужна привязка. Сервер НЕ ДОЛЖЕН закрывать соединение, если через это соединение был получен запрос, на который не был отправлен ответ. Сервер НЕ ДОЛЖЕН когда-либо открывать соединение обратно к клиенту, чтобы отправить ответ. Серверам следует соблюдать лучшие практики управления соединениями в случаях перегрузки.
7.3. Receiving a STUN Message
7.3. Получение сообщения STUN
This section specifies the processing of a STUN message. The processing specified here is for STUN messages as defined in this specification; additional rules for backwards compatibility are defined in Section 12. Those additional procedures are optional, and usages can elect to utilize them. First, a set of processing operations is applied that is independent of the class. This is followed by class-specific processing, described in the subsections that follow. When a STUN agent receives a STUN message, it first checks that the message obeys the rules of Section 6. It checks that the first two bits are 0, that the magic cookie field has the correct value, that the message length is sensible, and that the method value is a supported method. It checks that the message class is allowed for the particular method. If the message class is "Success Response" or "Error Response", the agent checks that the transaction ID matches a transaction that is still in progress. If the FINGERPRINT extension is being used, the agent checks that the FINGERPRINT attribute is present and contains the correct value. If any errors are detected, the message is silently discarded. In the case when STUN is being multiplexed with another protocol, an error may indicate that this is not really a STUN message; in this case, the agent should try to parse the message as a different protocol.
В этом разделе определена обработка сообщения STUN. Описанная здесь обработка относится к сообщениям STUN, определённым в данной спецификации; дополнительные правила обратной совместимости определены в разделе 12. Эти дополнительные процедуры необязательны, и применения могут решить их использовать. Сначала применяется набор операций обработки, не зависящий от класса. За ним следует обработка, зависящая от класса, описанная в последующих подразделах. Когда агент STUN получает сообщение STUN, он сначала проверяет, что сообщение подчиняется правилам раздела 6. Он проверяет, что первые два бита равны 0, что поле magic cookie имеет правильное значение, что длина сообщения разумна и что значение метода является поддерживаемым методом. Он проверяет, что класс сообщения допустим для данного метода. Если класс сообщения — «Success Response» или «Error Response», агент проверяет, что идентификатор транзакции соответствует транзакции, которая всё ещё выполняется. Если используется расширение FINGERPRINT, агент проверяет, что атрибут FINGERPRINT присутствует и содержит правильное значение. При обнаружении любых ошибок сообщение молча отбрасывается. В случае, когда STUN мультиплексируется с другим протоколом, ошибка может указывать на то, что это не сообщение STUN; в этом случае агент должен попытаться разобрать сообщение как другой протокол.
The STUN agent then does any checks that are required by a authentication mechanism that the usage has specified (see Section 10).
Затем агент STUN выполняет любые проверки, требуемые механизмом аутентификации, который указан в применении (см. раздел 10).
Once the authentication checks are done, the STUN agent checks for unknown attributes and known-but-unexpected attributes in the message. Unknown comprehension-optional attributes MUST be ignored by the agent. Known-but-unexpected attributes SHOULD be ignored by the agent. Unknown comprehension-required attributes cause processing that depends on the message class and is described below.
После завершения проверок аутентификации агент STUN проверяет сообщение на наличие неизвестных атрибутов и известных, но неожиданных атрибутов. Неизвестные необязательные для понимания атрибуты ДОЛЖНЫ игнорироваться агентом. Известные, но неожиданные атрибуты СЛЕДУЕТ игнорировать агенту. Неизвестные обязательные для понимания атрибуты вызывают обработку, которая зависит от класса сообщения и описана ниже.
At this point, further processing depends on the message class of the request.
На этом этапе дальнейшая обработка зависит от класса сообщения запроса.
7.3.1. Processing a Request
7.3.1. Обработка запроса
If the request contains one or more unknown comprehension-required attributes, the server replies with an error response with an error code of 420 (Unknown Attribute), and includes an UNKNOWN-ATTRIBUTES attribute in the response that lists the unknown comprehension- required attributes.
Если запрос содержит один или несколько неизвестных обязательных для понимания атрибутов, сервер отвечает ответом об ошибке с кодом ошибки 420 (Unknown Attribute) и включает в ответ атрибут UNKNOWN-ATTRIBUTES, перечисляющий неизвестные обязательные для понимания атрибуты.
The server then does any additional checking that the method or the specific usage requires. If all the checks succeed, the server formulates a success response as described below.
Затем сервер выполняет любые дополнительные проверки, требуемые методом или конкретным применением. Если все проверки успешны, сервер формирует ответ об успехе, как описано ниже.
When run over UDP, a request received by the server could be the first request of a transaction, or a retransmission. The server MUST respond to retransmissions such that the following property is preserved: if the client receives the response to the retransmission and not the response that was sent to the original request, the overall state on the client and server is identical to the case where only the response to the original retransmission is received, or where both responses are received (in which case the client will use the first). The easiest way to meet this requirement is for the server to remember all transaction IDs received over UDP and their corresponding responses in the last 40 seconds. However, this requires the server to hold state, and will be inappropriate for any requests which are not authenticated. Another way is to reprocess the request and recompute the response. The latter technique MUST only be applied to requests that are idempotent (a request is considered idempotent when the same request can be safely repeated without impacting the overall state of the system) and result in the same success response for the same request. The Binding method is considered to be idempotent.
При работе через UDP запрос, полученный сервером, может быть первым запросом транзакции или повторной передачей. Сервер ДОЛЖЕН отвечать на повторные передачи так, чтобы сохранялось следующее свойство: если клиент получает ответ на повторную передачу, а не ответ, отправленный на исходный запрос, общее состояние клиента и сервера идентично случаю, когда получен только ответ на исходную повторную передачу, или случаю, когда получены оба ответа (в этом случае клиент использует первый). Простейший способ выполнить это требование — чтобы сервер запоминал все идентификаторы транзакций, полученные через UDP, и соответствующие им ответы за последние 40 секунд. Однако это требует от сервера хранения состояния и будет непригодно для любых неаутентифицированных запросов. Другой способ — повторно обработать запрос и пересчитать ответ. Последний метод ДОЛЖЕН применяться только к идемпотентным запросам (запрос считается идемпотентным, когда тот же запрос можно безопасно повторить без влияния на общее состояние системы) и давать один и тот же ответ об успехе на один и тот же запрос. Метод Binding считается идемпотентным.
Note that there are certain rare network events that could cause the reflexive transport address value to change, resulting in a different mapped address in different success responses. Extensions to STUN MUST discuss the implications of request retransmissions on servers that do not store transaction state.
Отметим, что существуют редкие сетевые события, способные изменить значение рефлексивного транспортного адреса, из-за чего в разных успешных ответах окажется разный отображённый адрес. Расширения STUN ДОЛЖНЫ обсуждать последствия повторных передач запросов для серверов, не сохраняющих состояние транзакции.
7.3.1.1. Forming a Success or Error Response
7.3.1.1. Формирование ответа об успехе или ошибке
When forming the response (success or error), the server follows the rules of Section 6. The method of the response is the same as that of the request, and the message class is either "Success Response" or "Error Response".
При формировании ответа (об успехе или об ошибке) сервер следует правилам раздела 6. Метод ответа тот же, что и у запроса, а класс сообщения — либо «Success Response», либо «Error Response».
For an error response, the server MUST add an ERROR-CODE attribute containing the error code specified in the processing above. The reason phrase is not fixed, but SHOULD be something suitable for the error code. For certain errors, additional attributes are added to the message. These attributes are spelled out in the description where the error code is specified. For example, for an error code of 420 (Unknown Attribute), the server MUST include an UNKNOWN- ATTRIBUTES attribute. Certain authentication errors also cause attributes to be added (see Section 10). Extensions may define other errors and/or additional attributes to add in error cases.
Для ответа об ошибке сервер ДОЛЖЕН добавить атрибут ERROR-CODE, содержащий код ошибки, указанный при обработке выше. Текстовая причина не фиксирована, но ДОЛЖНА соответствовать коду ошибки. Для некоторых ошибок в сообщение добавляются дополнительные атрибуты. Эти атрибуты описаны там же, где указан код ошибки. Например, для кода ошибки 420 (Unknown Attribute) сервер ДОЛЖЕН включить атрибут UNKNOWN-ATTRIBUTES. Некоторые ошибки аутентификации также вызывают добавление атрибутов (см. раздел 10). Расширения могут определять другие ошибки и (или) дополнительные атрибуты, добавляемые в случае ошибок.
If the server authenticated the request using an authentication mechanism, then the server SHOULD add the appropriate authentication attributes to the response (see Section 10).
Если сервер аутентифицировал запрос с помощью механизма аутентификации, то сервер ДОЛЖЕН добавить в ответ соответствующие атрибуты аутентификации (см. раздел 10).
The server also adds any attributes required by the specific method or usage. In addition, the server SHOULD add a SOFTWARE attribute to the message.
Сервер также добавляет любые атрибуты, требуемые конкретным методом или применением. Кроме того, сервер ДОЛЖЕН добавить в сообщение атрибут SOFTWARE.
For the Binding method, no additional checking is required unless the usage specifies otherwise. When forming the success response, the server adds a XOR-MAPPED-ADDRESS attribute to the response, where the contents of the attribute are the source transport address of the request message. For UDP, this is the source IP address and source UDP port of the request message. For TCP and TLS-over-TCP, this is the source IP address and source TCP port of the TCP connection as seen by the server.
Для метода Binding никакая дополнительная проверка не требуется, если применение не указывает иное. При формировании ответа об успехе сервер добавляет в ответ атрибут XOR-MAPPED-ADDRESS, содержимым которого является исходный транспортный адрес сообщения-запроса. Для UDP это исходный IP-адрес и исходный UDP-порт сообщения-запроса. Для TCP и TLS-over-TCP это исходный IP-адрес и исходный TCP-порт соединения в том виде, в каком их видит сервер.
7.3.1.2. Sending the Success or Error Response
7.3.1.2. Отправка ответа об успехе или ошибке
The response (success or error) is sent over the same transport as the request was received on. If the request was received over UDP, the destination IP address and port of the response are the source IP address and port of the received request message, and the source IP address and port of the response are equal to the destination IP address and port of the received request message. If the request was received over TCP or TLS-over-TCP, the response is sent back on the same TCP connection as the request was received on.
Ответ (об успехе или об ошибке) отправляется через тот же транспорт, по которому был получен запрос. Если запрос был получен через UDP, IP-адрес и порт назначения ответа — это исходный IP-адрес и порт полученного сообщения-запроса, а исходный IP-адрес и порт ответа равны IP-адресу и порту назначения полученного сообщения-запроса. Если запрос был получен через TCP или TLS-over-TCP, ответ отправляется обратно через то же TCP-соединение, по которому был получен запрос.
7.3.2. Processing an Indication
7.3.2. Обработка сообщения-индикации
If the indication contains unknown comprehension-required attributes, the indication is discarded and processing ceases.
Если индикация содержит неизвестные обязательные для понимания атрибуты, индикация отбрасывается и обработка прекращается.
The agent then does any additional checking that the method or the specific usage requires. If all the checks succeed, the agent then processes the indication. No response is generated for an indication.
Затем агент выполняет любые дополнительные проверки, требуемые методом или конкретным применением. Если все проверки успешны, агент обрабатывает индикацию. Для индикации ответ не формируется.
For the Binding method, no additional checking or processing is required, unless the usage specifies otherwise. The mere receipt of the message by the agent has refreshed the "bindings" in the intervening NATs.
Для метода Binding дополнительная проверка или обработка не требуются, если применение не указывает иное. Сам факт получения сообщения агентом обновил «привязки» в промежуточных NAT.
Since indications are not re-transmitted over UDP (unlike requests), there is no need to handle re-transmissions of indications at the sending agent.
Поскольку индикации не передаются повторно через UDP (в отличие от запросов), нет необходимости обрабатывать повторные передачи индикаций на отправляющем агенте.
7.3.3. Processing a Success Response
7.3.3. Обработка ответа об успехе
If the success response contains unknown comprehension-required attributes, the response is discarded and the transaction is considered to have failed.
Если ответ об успехе содержит неизвестные обязательные для понимания атрибуты, ответ отбрасывается, а транзакция считается неуспешной.
The client then does any additional checking that the method or the specific usage requires. If all the checks succeed, the client then processes the success response.
Затем клиент выполняет любые дополнительные проверки, требуемые методом или конкретным применением. Если все проверки успешны, клиент обрабатывает ответ об успехе.
For the Binding method, the client checks that the XOR-MAPPED-ADDRESS attribute is present in the response. The client checks the address family specified. If it is an unsupported address family, the attribute SHOULD be ignored. If it is an unexpected but supported address family (for example, the Binding transaction was sent over IPv4, but the address family specified is IPv6), then the client MAY accept and use the value.
Для метода Binding клиент проверяет наличие атрибута XOR-MAPPED-ADDRESS в ответе. Клиент проверяет указанное семейство адресов. Если это неподдерживаемое семейство адресов, атрибут СЛЕДУЕТ игнорировать. Если это неожиданное, но поддерживаемое семейство адресов (например, транзакция Binding была отправлена через IPv4, а указано семейство IPv6), клиент МОЖЕТ принять и использовать значение.
7.3.4. Processing an Error Response
7.3.4. Обработка ответа об ошибке
If the error response contains unknown comprehension-required attributes, or if the error response does not contain an ERROR-CODE attribute, then the transaction is simply considered to have failed.
Если ответ об ошибке содержит неизвестные обязательные для понимания атрибуты или если ответ об ошибке не содержит атрибута ERROR-CODE, транзакция просто считается неуспешной.
The client then does any processing specified by the authentication mechanism (see Section 10). This may result in a new transaction attempt.
Затем клиент выполняет любую обработку, указанную механизмом аутентификации (см. раздел 10). Это может привести к новой попытке транзакции.
The processing at this point depends on the error code, the method, and the usage; the following are the default rules:
Дальнейшая обработка зависит от кода ошибки, метода и применения; ниже приведены правила по умолчанию:
o If the error code is 300 through 399, the client SHOULD consider the transaction as failed unless the ALTERNATE-SERVER extension is being used. See Section 11.
o Если код ошибки находится в диапазоне от 300 до 399, клиент ДОЛЖЕН считать транзакцию неуспешной, если не используется расширение ALTERNATE-SERVER. См. раздел 11.
o If the error code is 400 through 499, the client declares the transaction failed; in the case of 420 (Unknown Attribute), the response should contain a UNKNOWN-ATTRIBUTES attribute that gives additional information.
o Если код ошибки находится в диапазоне от 400 до 499, клиент объявляет транзакцию неуспешной; в случае 420 (Unknown Attribute) ответ должен содержать атрибут UNKNOWN-ATTRIBUTES, дающий дополнительную информацию.
o If the error code is 500 through 599, the client MAY resend the request; clients that do so MUST limit the number of times they do this.
o Если код ошибки находится в диапазоне от 500 до 599, клиент МОЖЕТ повторно отправить запрос; клиенты, поступающие так, ДОЛЖНЫ ограничивать число таких повторов.
Any other error code causes the client to consider the transaction failed.
Любой другой код ошибки заставляет клиента считать транзакцию неуспешной.
8. FINGERPRINT Mechanism
8. Механизм FINGERPRINT
This section describes an optional mechanism for STUN that aids in distinguishing STUN messages from packets of other protocols when the two are multiplexed on the same transport address. This mechanism is optional, and a STUN usage must describe if and when it is used. The FINGERPRINT mechanism is not backwards compatible with RFC 3489, and cannot be used in environments where such compatibility is required.
В этом разделе описан необязательный механизм STUN, помогающий отличать сообщения STUN от пакетов других протоколов, когда те и другие мультиплексируются на одном транспортном адресе. Этот механизм необязателен, и применение STUN должно указывать, используется ли он и когда. Механизм FINGERPRINT не совместим с RFC 3489 и не может использоваться в средах, где такая совместимость требуется.
In some usages, STUN messages are multiplexed on the same transport address as other protocols, such as the Real Time Transport Protocol (RTP). In order to apply the processing described in Section 7, STUN messages must first be separated from the application packets. Section 6 describes three fixed fields in the STUN header that can be used for this purpose. However, in some cases, these three fixed fields may not be sufficient.
В некоторых применениях сообщения STUN мультиплексируются на том же транспортном адресе, что и другие протоколы, например протокол транспорта реального времени (RTP). Чтобы применить обработку, описанную в разделе 7, сообщения STUN сначала нужно отделить от прикладных пакетов. В разделе 6 описаны три фиксированных поля заголовка STUN, которые можно для этого использовать. Однако в некоторых случаях этих трёх фиксированных полей может быть недостаточно.
When the FINGERPRINT extension is used, an agent includes the FINGERPRINT attribute in messages it sends to another agent. Section 15.5 describes the placement and value of this attribute. When the agent receives what it believes is a STUN message, then, in addition to other basic checks, the agent also checks that the message contains a FINGERPRINT attribute and that the attribute contains the correct value. Section 7.3 describes when in the overall processing of a STUN message the FINGERPRINT check is performed. This additional check helps the agent detect messages of other protocols that might otherwise seem to be STUN messages.
Когда используется расширение FINGERPRINT, агент включает атрибут FINGERPRINT в сообщения, отправляемые другому агенту. В разделе 15.5 описаны размещение и значение этого атрибута. Когда агент получает то, что считает сообщением STUN, он в дополнение к другим базовым проверкам проверяет, что сообщение содержит атрибут FINGERPRINT и что этот атрибут содержит правильное значение. В разделе 7.3 описано, в какой момент общей обработки сообщения STUN выполняется проверка FINGERPRINT. Эта дополнительная проверка помогает агенту обнаружить сообщения других протоколов, которые иначе могли бы показаться сообщениями STUN.
9. DNS Discovery of a Server
9. Обнаружение сервера через DNS
This section describes an optional procedure for STUN that allows a client to use DNS to determine the IP address and port of a server. A STUN usage must describe if and when this extension is used. To use this procedure, the client must know a server's domain name and a service name; the usage must also describe how the client obtains these. Hard-coding the domain name of the server into software is NOT RECOMMENDED in case the domain name is lost or needs to change for legal or other reasons.
В этом разделе описана необязательная процедура STUN, позволяющая клиенту использовать DNS для определения IP-адреса и порта сервера. Применение STUN должно указывать, используется ли это расширение и когда. Для использования этой процедуры клиент должен знать доменное имя сервера и имя службы; применение также должно описывать, как клиент получает их. Жёсткое задание доменного имени сервера в программном обеспечении НЕ РЕКОМЕНДУЕТСЯ на случай, если доменное имя будет утрачено или его потребуется изменить по юридическим или иным причинам.
When a client wishes to locate a STUN server in the public Internet that accepts Binding request/response transactions, the SRV service name is "stun". When it wishes to locate a STUN server that accepts Binding request/response transactions over a TLS session, the SRV service name is "stuns". STUN usages MAY define additional DNS SRV service names.
Когда клиент желает найти сервер STUN в публичном Интернете, принимающий транзакции запрос/ответ Binding, именем службы SRV является «stun». Когда он желает найти сервер STUN, принимающий транзакции запрос/ответ Binding через сеанс TLS, именем службы SRV является «stuns». Применения STUN МОГУТ определять дополнительные имена служб DNS SRV.
The domain name is resolved to a transport address using the SRV procedures specified in [RFC2782]. The DNS SRV service name is the service name provided as input to this procedure. The protocol in the SRV lookup is the transport protocol the client will run STUN over: "udp" for UDP and "tcp" for TCP. Note that only "tcp" is defined with "stuns" at this time.
Доменное имя разрешается в транспортный адрес с помощью процедур SRV, указанных в [RFC2782]. Имя службы DNS SRV — это имя службы, предоставленное на вход этой процедуры. Протоколом в запросе SRV является транспортный протокол, через который клиент будет запускать STUN: «udp» для UDP и «tcp» для TCP. Обратите внимание, что в настоящее время со «stuns» определён только «tcp».
The procedures of RFC 2782 are followed to determine the server to contact. RFC 2782 spells out the details of how a set of SRV records is sorted and then tried. However, RFC 2782 only states that the client should "try to connect to the (protocol, address, service)" without giving any details on what happens in the event of failure. When following these procedures, if the STUN transaction times out without receipt of a response, the client SHOULD retry the request to the next server in the ordered defined by RFC 2782. Such a retry is only possible for request/response transmissions, since indication transactions generate no response or timeout.
Чтобы определить сервер для обращения, соблюдаются процедуры RFC 2782. RFC 2782 подробно описывает, как набор записей SRV сортируется и затем опробуется. Однако RFC 2782 лишь утверждает, что клиент должен «попытаться подключиться к (протоколу, адресу, службе)», не уточняя, что происходит в случае неудачи. При соблюдении этих процедур, если транзакция STUN истекает по времени, не получив ответа, клиент ДОЛЖЕН повторить запрос к следующему серверу в порядке, определённом RFC 2782. Такой повтор возможен только для передач запрос/ответ, поскольку транзакции-индикации не порождают ни ответа, ни тайм-аута.
The default port for STUN requests is 3478, for both TCP and UDP.
Порт по умолчанию для запросов STUN — 3478, как для TCP, так и для UDP.
Administrators of STUN servers SHOULD use this port in their SRV records for UDP and TCP. In all cases, the port in DNS MUST reflect the one on which the server is listening. The default port for STUN over TLS is 5349. Servers can run STUN over TLS on the same port as STUN over TCP if the server software supports determining whether the initial message is a TLS or STUN message.
Администраторы серверов STUN ДОЛЖНЫ использовать этот порт в своих записях SRV для UDP и TCP. Во всех случаях порт в DNS ДОЛЖЕН отражать тот порт, на котором сервер слушает. Порт по умолчанию для STUN через TLS — 5349. Серверы могут запускать STUN через TLS на том же порту, что и STUN через TCP, если серверное программное обеспечение поддерживает определение того, является ли начальное сообщение сообщением TLS или STUN.
If no SRV records were found, the client performs an A or AAAA record lookup of the domain name. The result will be a list of IP addresses, each of which can be contacted at the default port using UDP or TCP, independent of the STUN usage. For usages that require TLS, the client connects to one of the IP addresses using the default STUN over TLS port.
Если записи SRV не найдены, клиент выполняет поиск записи A или AAAA для доменного имени. Результатом будет список IP-адресов, каждый из которых можно достичь по порту по умолчанию через UDP или TCP независимо от применения STUN. Для применений, требующих TLS, клиент подключается к одному из IP-адресов через порт STUN через TLS по умолчанию.
10. Authentication and Message-Integrity Mechanisms
10. Механизмы аутентификации и целостности сообщений
This section defines two mechanisms for STUN that a client and server can use to provide authentication and message integrity; these two mechanisms are known as the short-term credential mechanism and the long-term credential mechanism. These two mechanisms are optional, and each usage must specify if and when these mechanisms are used. Consequently, both clients and servers will know which mechanism (if any) to follow based on knowledge of which usage applies. For example, a STUN server on the public Internet supporting ICE would have no authentication, whereas the STUN server functionality in an agent supporting connectivity checks would utilize short-term credentials. An overview of these two mechanisms is given in Section 3.
В этом разделе определены два механизма STUN, которые клиент и сервер могут использовать для обеспечения аутентификации и целостности сообщений; эти два механизма называются механизмом краткосрочных учетных данных и механизмом долгосрочных учетных данных. Эти два механизма необязательны, и каждое применение должно указывать, используются ли они и когда. Следовательно, и клиенты, и серверы будут знать, какому механизму (если таковой имеется) следовать, исходя из знания о том, какое применение применяется. Например, сервер STUN в публичном Интернете, поддерживающий ICE, не имел бы аутентификации, тогда как функциональность сервера STUN в агенте, поддерживающем проверки связности, использовала бы краткосрочные учетные данные. Обзор этих двух механизмов приведён в разделе 3.
Each mechanism specifies the additional processing required to use that mechanism, extending the processing specified in Section 7. The additional processing occurs in three different places: when forming a message, when receiving a message immediately after the basic checks have been performed, and when doing the detailed processing of error responses.
Каждый механизм определяет дополнительную обработку, необходимую для использования этого механизма, расширяя обработку, указанную в разделе 7. Дополнительная обработка происходит в трёх разных местах: при формировании сообщения, при получении сообщения сразу после выполнения базовых проверок и при подробной обработке ответов об ошибках.
10.1. Short-Term Credential Mechanism
10.1. Механизм краткосрочных учетных данных
The short-term credential mechanism assumes that, prior to the STUN transaction, the client and server have used some other protocol to exchange a credential in the form of a username and password. This credential is time-limited. The time limit is defined by the usage. As an example, in the ICE usage [MMUSIC-ICE], the two endpoints use out-of-band signaling to agree on a username and password, and this username and password are applicable for the duration of the media session.
Механизм краткосрочных учетных данных предполагает, что до транзакции STUN клиент и сервер использовали какой-либо другой протокол для обмена учетными данными в форме имени пользователя и пароля. Эти учетные данные ограничены по времени. Ограничение по времени определяется применением. Например, в применении ICE [MMUSIC-ICE] две оконечные точки используют внешнюю сигнализацию для согласования имени пользователя и пароля, и эти имя пользователя и пароль действуют в течение всего медиасеанса.
This credential is used to form a message-integrity check in each request and in many responses. There is no challenge and response as in the long-term mechanism; consequently, replay is prevented by virtue of the time-limited nature of the credential.
Эти учетные данные используются для формирования проверки целостности сообщения в каждом запросе и во многих ответах. Здесь нет запроса-вызова и ответа, как в долгосрочном механизме; следовательно, повторное воспроизведение предотвращается благодаря ограниченному по времени характеру учетных данных.
10.1.1. Forming a Request or Indication
10.1.1. Формирование запроса или индикации
For a request or indication message, the agent MUST include the USERNAME and MESSAGE-INTEGRITY attributes in the message. The HMAC for the MESSAGE-INTEGRITY attribute is computed as described in Section 15.4. Note that the password is never included in the request or indication.
Для сообщения-запроса или сообщения-индикации агент ДОЛЖЕН включить в сообщение атрибуты USERNAME и MESSAGE-INTEGRITY. HMAC для атрибута MESSAGE-INTEGRITY вычисляется так, как описано в разделе 15.4. Обратите внимание, что пароль никогда не включается в запрос или индикацию.
10.1.2. Receiving a Request or Indication
10.1.2. Получение запроса или индикации
After the agent has done the basic processing of a message, the agent performs the checks listed below in order specified:
После того как агент выполнил базовую обработку сообщения, он выполняет перечисленные ниже проверки в указанном порядке:
o If the message does not contain both a MESSAGE-INTEGRITY and a USERNAME attribute:

10.1.3. Получение ответа
The client looks for the MESSAGE-INTEGRITY attribute in the response. If the resulting value matches the contents of the MESSAGE-INTEGRITY attribute, the response is considered authenticated. If the value does not match, or if MESSAGE-INTEGRITY was absent, the response MUST be discarded, as if it was never received. This means that retransmits, if applicable, will continue.
Клиент ищет атрибут MESSAGE-INTEGRITY в ответе. Если он присутствует, клиент вычисляет целостность сообщения по ответу, как определено в разделе 15.4, используя тот же пароль, который он применял для запроса. Если полученное значение совпадает с содержимым атрибута MESSAGE-INTEGRITY, ответ считается аутентифицированным. Если значение не совпадает или если MESSAGE-INTEGRITY отсутствовал, ответ ДОЛЖЕН быть отброшен, как если бы он никогда не был получен. Это означает, что повторные передачи, если они применимы, будут продолжаться.
10.2. Long-Term Credential Mechanism
10.2. Механизм долгосрочных учетных данных
The long-term credential mechanism relies on a long-term credential, in the form of a username and password that are shared between client and server. The credential is considered long-term since it is assumed that it is provisioned for a user, and remains in effect until the user is no longer a subscriber of the system, or is changed. This is basically a traditional "log-in" username and password given to users.
Механизм долгосрочных учетных данных основан на долгосрочных учетных данных в форме имени пользователя и пароля, совместно используемых клиентом и сервером. Учетные данные считаются долгосрочными, поскольку предполагается, что они предоставляются пользователю и остаются действующими, пока пользователь не перестанет быть абонентом системы или пока они не будут изменены. По сути, это традиционные имя пользователя и пароль для «входа в систему», выдаваемые пользователям.
Because these usernames and passwords are expected to be valid for extended periods of time, replay prevention is provided in the form of a digest challenge. In this mechanism, the client initially sends a request, without offering any credentials or any integrity checks. The server rejects this request, providing the user a realm (used to guide the user or agent in selection of a username and password) and a nonce. The nonce provides the replay protection. It is a cookie, selected by the server, and encoded in such a way as to indicate a duration of validity or client identity from which it is valid. The client retries the request, this time including its username and the realm, and echoing the nonce provided by the server. The client also includes a message-integrity, which provides an HMAC over the entire request, including the nonce. The server validates the nonce and checks the message integrity. If they match, the request is authenticated. If the nonce is no longer valid, it is considered "stale", and the server rejects the request, providing a new nonce.
Поскольку эти имена пользователей и пароли предполагаются действительными в течение длительных периодов времени, защита от повторного воспроизведения обеспечивается в форме digest-запроса-вызова. В этом механизме клиент изначально отправляет запрос, не предлагая никаких учетных данных и никаких проверок целостности. Сервер отклоняет этот запрос, предоставляя пользователю realm (используемый для управления выбором имени пользователя и пароля пользователем или агентом) и nonce. Nonce обеспечивает защиту от повторного воспроизведения. Это cookie, выбираемое сервером и кодируемое так, чтобы указывать срок действия или идентичность клиента, для которого оно действительно. Клиент повторяет запрос, на этот раз включая своё имя пользователя и realm и повторяя nonce, предоставленное сервером. Клиент также включает целостность сообщения, которая обеспечивает HMAC по всему запросу, включая nonce. Сервер проверяет nonce и проверяет целостность сообщения. Если они совпадают, запрос аутентифицирован. Если nonce больше недействительно, оно считается «устаревшим», и сервер отклоняет запрос, предоставляя новое nonce.
In subsequent requests to the same server, the client reuses the nonce, username, realm, and password it used previously. In this way, subsequent requests are not rejected until the nonce becomes invalid by the server, in which case the rejection provides a new nonce to the client.
В последующих запросах к тому же серверу клиент повторно использует nonce, имя пользователя, realm и пароль, которые он использовал ранее. Таким образом, последующие запросы не отклоняются, пока nonce не станет недействительным по решению сервера, и в этом случае отказ предоставляет клиенту новое nonce.
Note that the long-term credential mechanism cannot be used to protect indications, since indications cannot be challenged. Usages utilizing indications must either use a short-term credential or omit authentication and message integrity for them.
Обратите внимание, что механизм долгосрочных учетных данных нельзя использовать для защиты индикаций, поскольку к индикациям нельзя применить запрос-вызов. Применения, использующие индикации, должны либо применять краткосрочные учетные данные, либо не применять для них аутентификацию и целостность сообщений.
Since the long-term credential mechanism is susceptible to offline dictionary attacks, deployments SHOULD utilize passwords that are difficult to guess. In cases where the credentials are not entered by the user, but are rather placed on a client device during device provisioning, the password SHOULD have at least 128 bits of randomness. In cases where the credentials are entered by the user, they should follow best current practices around password structure.
Поскольку механизм долгосрочных учетных данных подвержен офлайн-атакам по словарю, при развёртывании СЛЕДУЕТ использовать пароли, которые трудно угадать. В случаях, когда учетные данные не вводятся пользователем, а размещаются на клиентском устройстве при его подготовке, пароль ДОЛЖЕН иметь не менее 128 бит случайности. В случаях, когда учетные данные вводит пользователь, им следует следовать лучшим текущим практикам в отношении структуры паролей.
10.2.1. Forming a Request
10.2.1. Формирование запроса
There are two cases when forming a request. In the first case, this is the first request from the client to the server (as identified by its IP address and port). In the second case, the client is submitting a subsequent request once a previous request/response transaction has completed successfully. Forming a request as a consequence of a 401 or 438 error response is covered in Section 10.2.3 and is not considered a "subsequent request" and thus does not utilize the rules described in Section 10.2.1.2.
При формировании запроса возможны два случая. В первом случае это первый запрос от клиента к серверу (идентифицируемому по его IP-адресу и порту). Во втором случае клиент отправляет последующий запрос после того, как предыдущая транзакция запрос/ответ успешно завершилась. Формирование запроса как следствие ответа об ошибке 401 или 438 рассматривается в разделе 10.2.3 и не считается «последующим запросом», а значит, не использует правила, описанные в разделе 10.2.1.2.
10.2.1.1. First Request
10.2.1.1. Первый запрос
If the client has not completed a successful request/response transaction with the server (as identified by hostname, if the DNS procedures of Section 9 are used, else IP address if not), it SHOULD omit the USERNAME, MESSAGE-INTEGRITY, REALM, and NONCE attributes. In other words, the very first request is sent as if there were no authentication or message integrity applied.
Если клиент не завершил успешную транзакцию запрос/ответ с сервером (идентифицируемым по имени хоста, если используются процедуры DNS из раздела 9, иначе по IP-адресу), он ДОЛЖЕН опустить атрибуты USERNAME, MESSAGE-INTEGRITY, REALM и NONCE. Иными словами, самый первый запрос отправляется так, как если бы аутентификация и целостность сообщения не применялись.
10.2.1.2. Subsequent Requests
10.2.1.2. Последующие запросы
Once a request/response transaction has completed successfully, the client will have been presented a realm and nonce by the server, and selected a username and password with which it authenticated. The client SHOULD cache the username, password, realm, and nonce for subsequent communications with the server. When the client sends a subsequent request, it SHOULD include the USERNAME, REALM, and NONCE attributes with these cached values. It SHOULD include a MESSAGE- INTEGRITY attribute, computed as described in Section 15.4 using the cached password.
После того как транзакция запрос/ответ успешно завершилась, сервер предоставил клиенту realm и nonce, а клиент выбрал имя пользователя и пароль, с которыми он аутентифицировался. Клиент ДОЛЖЕН кэшировать имя пользователя, пароль, realm и nonce для последующей связи с сервером. Когда клиент отправляет последующий запрос, он ДОЛЖЕН включить атрибуты USERNAME, REALM и NONCE с этими кэшированными значениями. Он ДОЛЖЕН включить атрибут MESSAGE-INTEGRITY, вычисленный так, как описано в разделе 15.4, с использованием кэшированного пароля.
10.2.2. Receiving a Request
10.2.2. Получение запроса
After the server has done the basic processing of a request, it performs the checks listed below in the order specified:
После того как сервер выполнил базовую обработку запроса, он выполняет перечисленные ниже проверки в указанном порядке:
o If the message does not contain a MESSAGE-INTEGRITY attribute, the server MUST generate an error response with an error code of 401 (Unauthorized). This response MUST include a REALM value. It is RECOMMENDED that the REALM value be the domain name of the provider of the STUN server. The response MUST include a NONCE, selected by the server. The response SHOULD NOT contain a USERNAME or MESSAGE-INTEGRITY attribute.
o Если сообщение не содержит атрибута MESSAGE-INTEGRITY, сервер ДОЛЖЕН сформировать ответ об ошибке с кодом ошибки 401 (Unauthorized). Этот ответ ДОЛЖЕН включать значение REALM. РЕКОМЕНДУЕТСЯ, чтобы значением REALM было доменное имя поставщика сервера STUN. Ответ ДОЛЖЕН включать NONCE, выбранное сервером. Ответ НЕ ДОЛЖЕН содержать атрибут USERNAME или MESSAGE-INTEGRITY.
o If the message contains a MESSAGE-INTEGRITY attribute, but is missing the USERNAME, REALM, or NONCE attribute, the server MUST generate an error response with an error code of 400 (Bad Request). This response SHOULD NOT include a USERNAME, NONCE, REALM, or MESSAGE-INTEGRITY attribute.
o Если сообщение содержит атрибут MESSAGE-INTEGRITY, но в нём отсутствует атрибут USERNAME, REALM или NONCE, сервер ДОЛЖЕН сформировать ответ об ошибке с кодом ошибки 400 (Bad Request). Этот ответ НЕ ДОЛЖЕН включать атрибут USERNAME, NONCE, REALM или MESSAGE-INTEGRITY.
o If the NONCE is no longer valid, the server MUST generate an error response with an error code of 438 (Stale Nonce). This response MUST include NONCE and REALM attributes and SHOULD NOT include the USERNAME or MESSAGE-INTEGRITY attribute. Servers can invalidate nonces in order to provide additional security. See Section 4.3 of [RFC2617] for guidelines.
o Если NONCE больше недействительно, сервер ДОЛЖЕН сформировать ответ об ошибке с кодом ошибки 438 (Stale Nonce). Этот ответ ДОЛЖЕН включать атрибуты NONCE и REALM и НЕ ДОЛЖЕН включать атрибут USERNAME или MESSAGE-INTEGRITY. Серверы могут аннулировать nonce для обеспечения дополнительной безопасности. Рекомендации см. в разделе 4.3 [RFC2617].
o If the username in the USERNAME attribute is not valid, the server MUST generate an error response with an error code of 401 (Unauthorized). This response MUST include a REALM value. It is RECOMMENDED that the REALM value be the domain name of the provider of the STUN server. The response MUST include a NONCE, selected by the server. The response SHOULD NOT contain a USERNAME or MESSAGE-INTEGRITY attribute.
o Если имя пользователя в атрибуте USERNAME недействительно, сервер ДОЛЖЕН сформировать ответ об ошибке с кодом ошибки 401 (Unauthorized). Этот ответ ДОЛЖЕН включать значение REALM. РЕКОМЕНДУЕТСЯ, чтобы значением REALM было доменное имя поставщика сервера STUN. Ответ ДОЛЖЕН включать NONCE, выбранное сервером. Ответ НЕ ДОЛЖЕН содержать атрибут USERNAME или MESSAGE-INTEGRITY.
o Using the password associated with the username in the USERNAME attribute, compute the value for the message integrity as described in Section 15.4. If the resulting value does not match the contents of the MESSAGE-INTEGRITY attribute, the server MUST reject the request with an error response. This response MUST use an error code of 401 (Unauthorized). It MUST include REALM and NONCE attributes and SHOULD NOT include the USERNAME or MESSAGE- INTEGRITY attribute.
o Используя пароль, связанный с именем пользователя в атрибуте USERNAME, вычислите значение целостности сообщения так, как описано в разделе 15.4. Если полученное значение не совпадает с содержимым атрибута MESSAGE-INTEGRITY, сервер ДОЛЖЕН отклонить запрос ответом об ошибке. В этом ответе ДОЛЖЕН использоваться код ошибки 401 (Unauthorized). Он ДОЛЖЕН включать атрибуты REALM и NONCE и НЕ ДОЛЖЕН включать атрибут USERNAME или MESSAGE-INTEGRITY.
If these checks pass, the server continues to process the request. Any response generated by the server (excepting the cases described above) MUST include the MESSAGE-INTEGRITY attribute, computed using the username and password utilized to authenticate the request. The REALM, NONCE, and USERNAME attributes SHOULD NOT be included.
Если эти проверки пройдены, сервер продолжает обработку запроса. Любой ответ, сформированный сервером (за исключением описанных выше случаев), ДОЛЖЕН содержать атрибут MESSAGE-INTEGRITY, вычисленный с использованием имени пользователя и пароля, применённых для аутентификации запроса. Атрибуты REALM, NONCE и USERNAME включать НЕ СЛЕДУЕТ.
10.2.3. Receiving a Response
10.2.3. Получение ответа
If the response is an error response with an error code of 401 (Unauthorized), the client SHOULD retry the request with a new transaction. This request MUST contain a USERNAME, determined by the client as the appropriate username for the REALM from the error response. The request MUST contain the REALM, copied from the error response. The request MUST contain the NONCE, copied from the error response. The request MUST contain the MESSAGE-INTEGRITY attribute, computed using the password associated with the username in the USERNAME attribute. The client MUST NOT perform this retry if it is not changing the USERNAME or REALM or its associated password, from the previous attempt.
Если ответ является ответом об ошибке с кодом ошибки 401 (Unauthorized), клиент ДОЛЖЕН повторить запрос в новой транзакции. Этот запрос ДОЛЖЕН содержать USERNAME, определённый клиентом как подходящее имя пользователя для REALM из ответа об ошибке. Запрос ДОЛЖЕН содержать REALM, скопированный из ответа об ошибке. Запрос ДОЛЖЕН содержать NONCE, скопированное из ответа об ошибке. Запрос ДОЛЖЕН содержать атрибут MESSAGE-INTEGRITY, вычисленный с использованием пароля, связанного с именем пользователя в атрибуте USERNAME. Клиент НЕ ДОЛЖЕН выполнять этот повтор, если он не изменяет USERNAME, REALM или связанный с ними пароль по сравнению с предыдущей попыткой.
If the response is an error response with an error code of 438 (Stale Nonce), the client MUST retry the request, using the new NONCE supplied in the 438 (Stale Nonce) response. This retry MUST also include the USERNAME, REALM, and MESSAGE-INTEGRITY.
Если ответ является ответом об ошибке с кодом ошибки 438 (Stale Nonce), клиент ДОЛЖЕН повторить запрос, используя новое NONCE, предоставленное в ответе 438 (Stale Nonce). Этот повтор ДОЛЖЕН также включать USERNAME, REALM и MESSAGE-INTEGRITY.
The client looks for the MESSAGE-INTEGRITY attribute in the response (either success or failure). If present, the client computes the message integrity over the response as defined in Section 15.4, using the same password it utilized for the request. If the resulting value matches the contents of the MESSAGE-INTEGRITY attribute, the response is considered authenticated. If the value does not match, or if MESSAGE-INTEGRITY was absent, the response MUST be discarded, as if it was never received. This means that retransmits, if applicable, will continue.
Клиент ищет атрибут MESSAGE-INTEGRITY в ответе (как об успехе, так и об ошибке). Если он присутствует, клиент вычисляет целостность сообщения по ответу, как определено в разделе 15.4, используя тот же пароль, который он применял для запроса. Если полученное значение совпадает с содержимым атрибута MESSAGE-INTEGRITY, ответ считается аутентифицированным. Если значение не совпадает или если MESSAGE-INTEGRITY отсутствовал, ответ ДОЛЖЕН быть отброшен, как если бы он никогда не был получен. Это означает, что повторные передачи, если они применимы, будут продолжаться.
11. ALTERNATE-SERVER Mechanism
11. Механизм ALTERNATE-SERVER
This section describes a mechanism in STUN that allows a server to redirect a client to another server. This extension is optional, and a usage must define if and when this extension is used.
В этом разделе описан механизм STUN, позволяющий серверу перенаправить клиента на другой сервер. Это расширение необязательно, и применение должно определять, используется ли оно и когда.
A server using this extension redirects a client to another server by replying to a request message with an error response message with an error code of 300 (Try Alternate). The server MUST include an ALTERNATE-SERVER attribute in the error response. The error response message MAY be authenticated; however, there are uses cases for ALTERNATE-SERVER where authentication of the response is not possible or practical.
Сервер, использующий это расширение, перенаправляет клиента на другой сервер, отвечая на сообщение-запрос сообщением-ответом об ошибке с кодом ошибки 300 (Try Alternate). Сервер ДОЛЖЕН включить атрибут ALTERNATE-SERVER в ответ об ошибке. Сообщение-ответ об ошибке МОЖЕТ быть аутентифицировано; однако существуют варианты использования ALTERNATE-SERVER, где аутентификация ответа невозможна или непрактична.
A client using this extension handles a 300 (Try Alternate) error code as follows. The client looks for an ALTERNATE-SERVER attribute in the error response. If one is found, then the client considers the current transaction as failed, and reattempts the request with the server specified in the attribute, using the same transport protocol used for the previous request. That request, if authenticated, MUST utilize the same credentials that the client would have used in the request to the server that performed the redirection. If the client has been redirected to a server on which it has already tried this request within the last five minutes, it MUST ignore the redirection and consider the transaction to have failed. This prevents infinite ping-ponging between servers in case of redirection loops.
Клиент, использующий это расширение, обрабатывает код ошибки 300 (Try Alternate) следующим образом. Клиент ищет атрибут ALTERNATE-SERVER в ответе об ошибке. Если он найден, клиент считает текущую транзакцию неуспешной и повторяет запрос к серверу, указанному в атрибуте, используя тот же транспортный протокол, что и для предыдущего запроса. Этот запрос, если он аутентифицирован, ДОЛЖЕН использовать те же учетные данные, которые клиент использовал бы в запросе к серверу, выполнившему перенаправление. Если клиент был перенаправлен на сервер, на котором он уже пытался выполнить этот запрос в течение последних пяти минут, он ДОЛЖЕН игнорировать перенаправление и считать транзакцию неуспешной. Это предотвращает бесконечное перебрасывание между серверами в случае циклов перенаправления.
12. Backwards Compatibility with RFC 3489
12. Обратная совместимость с RFC 3489
This section defines procedures that allow a degree of backwards compatibility with the original protocol defined in RFC 3489 [RFC3489]. This mechanism is optional, meant to be utilized only in cases where a new client can connect to an old server, or vice versa. A usage must define if and when this procedure is used.
В этом разделе определены процедуры, обеспечивающие определённую степень обратной совместимости с исходным протоколом, определённым в RFC 3489 [RFC3489]. Этот механизм необязателен и предназначен для использования только в случаях, когда новый клиент может подключиться к старому серверу или наоборот. Применение должно определять, используется ли эта процедура и когда.
Section 19 lists all the changes between this specification and RFC 3489 [RFC3489]. However, not all of these differences are important, because "classic STUN" was only used in a few specific ways. For the purposes of this extension, the important changes are the following. In RFC 3489:
В разделе 19 перечислены все изменения между данной спецификацией и RFC 3489 [RFC3489]. Однако не все эти различия важны, поскольку «классический STUN» использовался лишь в нескольких конкретных случаях. Для целей этого расширения важны следующие изменения. В RFC 3489:
o UDP was the only supported transport.
o UDP был единственным поддерживаемым транспортом.
o The field that is now the magic cookie field was a part of the transaction ID field, and transaction IDs were 128 bits long.
o Поле, которое сейчас является полем magic cookie, было частью поля идентификатора транзакции, а идентификаторы транзакций имели длину 128 бит.
o The XOR-MAPPED-ADDRESS attribute did not exist, and the Binding method used the MAPPED-ADDRESS attribute instead.
o Атрибута XOR-MAPPED-ADDRESS не существовало, и метод Binding использовал вместо него атрибут MAPPED-ADDRESS.
o There were three comprehension-required attributes, RESPONSE- ADDRESS, CHANGE-REQUEST, and CHANGED-ADDRESS, that have been removed from this specification.
o Существовали три обязательных для понимания атрибута — RESPONSE-ADDRESS, CHANGE-REQUEST и CHANGED-ADDRESS, — которые удалены из данной спецификации.
* CHANGE-REQUEST and CHANGED-ADDRESS are now part of the NAT Behavior Discovery usage [BEHAVE-NAT], and the other is deprecated.
* CHANGE-REQUEST и CHANGED-ADDRESS теперь являются частью применения NAT Behavior Discovery [BEHAVE-NAT], а третий устарел.
12.1. Changes to Client Processing
12.1. Изменения в обработке клиента
A client that wants to interoperate with an [RFC3489] server SHOULD send a request message that uses the Binding method, contains no attributes, and uses UDP as the transport protocol to the server. If successful, the success response received from the server will contain a MAPPED-ADDRESS attribute rather than an XOR-MAPPED-ADDRESS attribute. A client seeking to interoperate with an older server MUST be prepared to receive either. Furthermore, the client MUST ignore any Reserved comprehension-required attributes that might appear in the response. Of the Reserved attributes in Section 18.2, 0x0002, 0x0004, 0x0005, and 0x000B may appear in Binding responses from a server compliant to RFC 3489. Other than this change, the processing of the response is identical to the procedures described above.
Клиент, желающий взаимодействовать с сервером [RFC3489], ДОЛЖЕН отправить сообщение-запрос, использующее метод Binding, не содержащее атрибутов и использующее UDP в качестве транспортного протокола к серверу. В случае успеха полученный от сервера ответ об успехе будет содержать атрибут MAPPED-ADDRESS, а не атрибут XOR-MAPPED-ADDRESS. Клиент, стремящийся к взаимодействию со старым сервером, ДОЛЖЕН быть готов принять любой из них. Кроме того, клиент ДОЛЖЕН игнорировать любые зарезервированные обязательные для понимания атрибуты, которые могут появиться в ответе. Из зарезервированных атрибутов в разделе 18.2 атрибуты 0x0002, 0x0004, 0x0005 и 0x000B могут появляться в ответах Binding от сервера, совместимого с RFC 3489. Помимо этого изменения, обработка ответа идентична описанным выше процедурам.
12.2. Changes to Server Processing
12.2. Изменения в обработке сервера
A STUN server can detect when a given Binding request message was sent from an RFC 3489 [RFC3489] client by the absence of the correct value in the magic cookie field. When the server detects an RFC 3489 client, it SHOULD copy the value seen in the magic cookie field in the Binding request to the magic cookie field in the Binding response message, and insert a MAPPED-ADDRESS attribute instead of an XOR- MAPPED-ADDRESS attribute.
Сервер STUN может определить, что данное сообщение-запрос Binding было отправлено клиентом RFC 3489 [RFC3489], по отсутствию правильного значения в поле magic cookie. Когда сервер обнаруживает клиента RFC 3489, он ДОЛЖЕН скопировать значение, увиденное в поле magic cookie запроса Binding, в поле magic cookie сообщения-ответа Binding и вставить атрибут MAPPED-ADDRESS вместо атрибута XOR-MAPPED-ADDRESS.
The client might, in rare situations, include either the RESPONSE- ADDRESS or CHANGE-REQUEST attributes. In these situations, the server will view these as unknown comprehension-required attributes and reply with an error response. Since the mechanisms utilizing those attributes are no longer supported, this behavior is acceptable.
Клиент может в редких ситуациях включать атрибуты RESPONSE-ADDRESS или CHANGE-REQUEST. В этих ситуациях сервер будет рассматривать их как неизвестные обязательные для понимания атрибуты и отвечать ответом об ошибке. Поскольку механизмы, использующие эти атрибуты, больше не поддерживаются, такое поведение приемлемо.
The RFC 3489 version of STUN lacks both the magic cookie and the FINGERPRINT attribute that allows for a very high probability of correctly identifying STUN messages when multiplexed with other protocols. Therefore, STUN implementations that are backwards compatible with RFC 3489 SHOULD NOT be used in cases where STUN will be multiplexed with another protocol. However, that should not be an issue as such multiplexing was not available in RFC 3489.
Версия STUN из RFC 3489 не имеет ни magic cookie, ни атрибута FINGERPRINT, который позволяет с очень высокой вероятностью правильно опознавать сообщения STUN при мультиплексировании с другими протоколами. Поэтому реализации STUN, обратно совместимые с RFC 3489, НЕ СЛЕДУЕТ использовать в случаях, когда STUN будет мультиплексироваться с другим протоколом. Однако это не должно быть проблемой, поскольку такое мультиплексирование в RFC 3489 отсутствовало.
13. Basic Server Behavior
13. Поведение базового сервера
This section defines the behavior of a basic, stand-alone STUN server. A basic STUN server provides clients with server reflexive transport addresses by receiving and replying to STUN Binding requests.
В этом разделе определено поведение базового автономного сервера STUN. Базовый сервер STUN предоставляет клиентам рефлексивные транспортные адреса сервера, принимая запросы Binding STUN и отвечая на них.
The STUN server MUST support the Binding method. It SHOULD NOT utilize the short-term or long-term credential mechanism. This is because the work involved in authenticating the request is more than the work in simply processing it. It SHOULD NOT utilize the ALTERNATE-SERVER mechanism for the same reason. It MUST support UDP and TCP. It MAY support STUN over TCP/TLS; however, TLS provides minimal security benefits in this basic mode of operation. It MAY utilize the FINGERPRINT mechanism but MUST NOT require it. Since the stand-alone server only runs STUN, FINGERPRINT provides no benefit. Requiring it would break compatibility with RFC 3489, and such compatibility is desirable in a stand-alone server. Stand-alone STUN servers SHOULD support backwards compatibility with [RFC3489] clients, as described in Section 12.
Сервер STUN ДОЛЖЕН поддерживать метод Binding. Ему НЕ СЛЕДУЕТ использовать механизм краткосрочных или долгосрочных учетных данных. Это связано с тем, что работа по аутентификации запроса превышает работу по его простой обработке. Ему НЕ СЛЕДУЕТ использовать механизм ALTERNATE-SERVER по той же причине. Он ДОЛЖЕН поддерживать UDP и TCP. Он МОЖЕТ поддерживать STUN через TCP/TLS; однако TLS даёт минимальные преимущества безопасности в этом базовом режиме работы. Он МОЖЕТ использовать механизм FINGERPRINT, но НЕ ДОЛЖЕН его требовать. Поскольку автономный сервер запускает только STUN, FINGERPRINT не даёт преимуществ. Его требование нарушило бы совместимость с RFC 3489, а такая совместимость желательна для автономного сервера. Автономным серверам STUN СЛЕДУЕТ поддерживать обратную совместимость с клиентами [RFC3489], как описано в разделе 12.
It is RECOMMENDED that administrators of STUN servers provide DNS entries for those servers as described in Section 9.
РЕКОМЕНДУЕТСЯ, чтобы администраторы серверов STUN предоставляли записи DNS для этих серверов, как описано в разделе 9.
A basic STUN server is not a solution for NAT traversal by itself. However, it can be utilized as part of a solution through STUN usages. This is discussed further in Section 14.
Базовый сервер STUN сам по себе не является решением для обхода NAT. Однако он может использоваться как часть решения через применения STUN. Это более подробно обсуждается в разделе 14.
14. STUN Usages
14. Применения STUN
STUN by itself is not a solution to the NAT traversal problem. Rather, STUN defines a tool that can be used inside a larger solution. The term "STUN usage" is used for any solution that uses STUN as a component.
Сам по себе STUN не является решением проблемы обхода NAT. Скорее, STUN определяет инструмент, который можно использовать внутри более крупного решения. Термин «применение STUN» используется для любого решения, использующего STUN как компонент.
At the time of writing, three STUN usages are defined: Interactive Connectivity Establishment (ICE) [MMUSIC-ICE], Client-initiated connections for SIP [SIP-OUTBOUND], and NAT Behavior Discovery [BEHAVE-NAT]. Other STUN usages may be defined in the future.
На момент написания определены три применения STUN: Interactive Connectivity Establishment (ICE) [MMUSIC-ICE], инициируемые клиентом соединения для SIP [SIP-OUTBOUND] и NAT Behavior Discovery [BEHAVE-NAT]. Другие применения STUN могут быть определены в будущем.
A STUN usage defines how STUN is actually utilized -- when to send requests, what to do with the responses, and which optional procedures defined here (or in an extension to STUN) are to be used. A usage would also define: o Which STUN methods are used.
Применение STUN определяет, как STUN фактически используется — когда отправлять запросы, что делать с ответами и какие необязательные процедуры, определённые здесь (или в расширении STUN), следует применять. Применение также определяет: o Какие методы STUN используются.
o What authentication and message-integrity mechanisms are used.
o Какие механизмы аутентификации и целостности сообщений используются.
o The considerations around manual vs. automatic key derivation for the integrity mechanism, as discussed in [RFC4107].
o Соображения о ручном и автоматическом выводе ключей для механизма целостности, как обсуждается в [RFC4107].
o What mechanisms are used to distinguish STUN messages from other messages. When STUN is run over TCP, a framing mechanism may be required.
o Какие механизмы используются для отличия сообщений STUN от других сообщений. Когда STUN работает через TCP, может потребоваться механизм кадрирования.
o How a STUN client determines the IP address and port of the STUN server.
o Каким образом клиент STUN определяет IP-адрес и порт сервера STUN.
o Whether backwards compatibility to RFC 3489 is required.
o Требуется ли обратная совместимость с RFC 3489 или нет.
o What optional attributes defined here (such as FINGERPRINT and ALTERNATE-SERVER) or in other extensions are required.
o Какие необязательные атрибуты, определённые здесь (такие как FINGERPRINT и ALTERNATE-SERVER) или в других расширениях, требуются.
In addition, any STUN usage must consider the security implications of using STUN in that usage. A number of attacks against STUN are known (see the Security Considerations section in this document), and any usage must consider how these attacks can be thwarted or mitigated.
Кроме того, любое применение STUN должно учитывать последствия для безопасности использования STUN в этом применении. Известен ряд атак на STUN (см. раздел «Соображения безопасности» в данном документе), и любое применение должно учитывать, как эти атаки могут быть предотвращены или смягчены.
Finally, a usage must consider whether its usage of STUN is an example of the Unilateral Self-Address Fixing approach to NAT traversal, and if so, address the questions raised in RFC 3424 [RFC3424].
Наконец, применение должно учитывать, является ли его использование STUN примером подхода Unilateral Self-Address Fixing к обходу NAT, и если да, ответить на вопросы, поднятые в RFC 3424 [RFC3424].

15. Атрибуты STUN
After the STUN header are zero or more attributes. Each attribute MUST be TLV encoded, with a 16-bit type, 16-bit length, and value. Each STUN attribute MUST end on a 32-bit boundary. As mentioned above, all fields in an attribute are transmitted most significant bit first.
После заголовка STUN следуют ноль или более атрибутов. Каждый атрибут ДОЛЖЕН быть закодирован в формате TLV с 16-битным типом, 16-битной длиной и значением. Каждый атрибут STUN ДОЛЖЕН заканчиваться на 32-битной границе. Как упоминалось выше, все поля атрибута передаются начиная со старшего бита.

Since STUN aligns attributes on 32-bit boundaries, attributes whose content is not a multiple of 4 bytes are padded with 1, 2, or 3 bytes of padding so that its value contains a multiple of 4 bytes. Биты заполнения игнорируются и могут иметь любое значение.
Any attribute type MAY appear more than once in a STUN message. Unless specified otherwise, the order of appearance is significant: only the first occurrence needs to be processed by a receiver, and any duplicates MAY be ignored by a receiver.
Любой тип атрибута МОЖЕТ встречаться в сообщении STUN более одного раза. Если не указано иное, порядок появления значим: получателю нужно обрабатывать только первое вхождение, а любые дубликаты МОГУТ игнорироваться получателем.
To allow future revisions of this specification to add new attributes if needed, the attribute space is divided into two ranges. Attributes with type values between 0x0000 and 0x7FFF are comprehension-required attributes, which means that the STUN agent cannot successfully process the message unless it understands the attribute. Attributes with type values between 0x8000 and 0xFFFF are comprehension-optional attributes, which means that those attributes can be ignored by the STUN agent if it does not understand them.
Чтобы будущие редакции этой спецификации могли при необходимости добавлять новые атрибуты, пространство атрибутов разделено на два диапазона. Атрибуты со значениями типа от 0x0000 до 0x7FFF являются обязательными для понимания: это означает, что агент STUN не может успешно обработать сообщение, если не понимает такой атрибут. Атрибуты со значениями типа от 0x8000 до 0xFFFF являются необязательными для понимания: это означает, что агент STUN может игнорировать такие атрибуты, если он их не понимает.

Набор типов атрибутов STUN поддерживается IANA. Начальный набор, определённый данной спецификацией, приведён в разделе 18.2.

X-Port вычисляется путём взятия отображаемого порта в порядке байтов хоста, применения к нему XOR со старшими 16 битами magic cookie и последующего преобразования результата в сетевой порядок байтов. Если семейство IP-адресов — IPv4, X-Address вычисляется путём взятия отображаемого IP-адреса в порядке байтов хоста, применения к нему XOR с magic cookie и преобразования результата в сетевой порядок байтов. Если семейство IP-адресов — IPv6, X-Address вычисляется путём взятия отображаемого IP-адреса в порядке байтов хоста, применения к нему XOR с конкатенацией magic cookie и 96-битного идентификатора транзакции и преобразования результата в сетевой порядок байтов.
The rules for encoding and processing the first 8 bits of the attribute's value, the rules for handling multiple occurrences of the attribute, and the rules for processing address families are the same as for MAPPED-ADDRESS.

Note: XOR-MAPPED-ADDRESS and MAPPED-ADDRESS differ only in their encoding of the transport address. The former encodes the transport address by exclusive-or'ing it with the magic cookie. The latter encodes it directly in binary. RFC 3489 originally specified only MAPPED-ADDRESS. However, deployment experience found that some NATs rewrite the 32-bit binary payloads containing the NAT's public IP address, such as STUN's MAPPED-ADDRESS attribute, in the well-meaning but misguided attempt at providing a generic ALG function. Such behavior interferes with the operation of STUN and also causes failure of STUN's message-integrity checking.
Примечание: XOR-MAPPED-ADDRESS и MAPPED-ADDRESS различаются только кодированием транспортного адреса. Первый кодирует транспортный адрес путём применения к нему XOR с magic cookie. Второй кодирует его непосредственно в двоичном виде. RFC 3489 изначально определял только MAPPED-ADDRESS. Однако опыт развёртывания показал, что некоторые NAT перезаписывают 32-битные двоичные полезные нагрузки, содержащие публичный IP-адрес NAT, такие как атрибут MAPPED-ADDRESS в STUN, в благонамеренной, но ошибочной попытке реализовать общую функцию ALG. Такое поведение мешает работе STUN и также приводит к сбою проверки целостности сообщений STUN.

15.4. MESSAGE-INTEGRITY
15.4. MESSAGE-INTEGRITY
The MESSAGE-INTEGRITY attribute contains an HMAC-SHA1 [RFC2104] of the STUN message. The MESSAGE-INTEGRITY attribute can be present in any STUN message type. Since it uses the SHA1 hash, the HMAC will be 20 bytes. The text used as input to HMAC is the STUN message, including the header, up to and including the attribute preceding the MESSAGE-INTEGRITY attribute. With the exception of the FINGERPRINT attribute, which appears after MESSAGE-INTEGRITY, agents MUST ignore all other attributes that follow MESSAGE-INTEGRITY. The key for the HMAC depends on whether long-term or short-term credentials are in use. For long-term credentials, the key is 16 bytes:
Атрибут MESSAGE-INTEGRITY содержит HMAC-SHA1 [RFC2104] сообщения STUN. Атрибут MESSAGE-INTEGRITY может присутствовать в сообщении STUN любого типа. Поскольку используется хеш SHA1, HMAC будет иметь длину 20 байт. Текст, используемый как входные данные для HMAC, — это сообщение STUN, включая заголовок, вплоть до атрибута, предшествующего атрибуту MESSAGE-INTEGRITY, включительно. За исключением атрибута FINGERPRINT, который стоит после MESSAGE-INTEGRITY, агенты ДОЛЖНЫ игнорировать все остальные атрибуты, следующие за MESSAGE-INTEGRITY. Ключ для HMAC зависит от того, используются ли долгосрочные или краткосрочные учетные данные. Для долгосрочных учетных данных ключ имеет длину 16 байт:
key = MD5(username ":" realm ":" SASLprep(password))
key = MD5(username ":" realm ":" SASLprep(password))
That is, the 16-byte key is formed by taking the MD5 hash of the result of concatenating the following five fields: (1) the username, with any quotes and trailing nulls removed, as taken from the USERNAME attribute (in which case SASLprep has already been applied); (2) a single colon; (3) the realm, with any quotes and trailing nulls removed; (4) a single colon; and (5) the password, with any trailing nulls removed and after processing using SASLprep. For example, if the username was 'user', the realm was 'realm', and the password was 'pass', then the 16-byte HMAC key would be the result of performing an MD5 hash on the string 'user:realm:pass', the resulting hash being 0x8493fbc53ba582fb4c044c456bdc40eb.
То есть 16-байтовый ключ формируется путём взятия хеша MD5 от результата конкатенации следующих пяти полей: (1) имя пользователя с удалёнными кавычками и завершающими нулями, взятое из атрибута USERNAME (в этом случае SASLprep уже применён); (2) одно двоеточие; (3) realm с удалёнными кавычками и завершающими нулями; (4) одно двоеточие; и (5) пароль с удалёнными завершающими нулями и после обработки с помощью SASLprep. Например, если имя пользователя было «user», realm было «realm», а пароль был «pass», то 16-байтовый ключ HMAC был бы результатом вычисления хеша MD5 строки «user:realm:pass», причём полученный хеш равен 0x8493fbc53ba582fb4c044c456bdc40eb.
For short-term credentials:
Для краткосрочных учетных данных:
key = SASLprep(password)
key = SASLprep(password)
where MD5 is defined in RFC 1321 [RFC1321] and SASLprep() is defined in RFC 4013 [RFC4013].
где MD5 определён в RFC 1321 [RFC1321], а SASLprep() определён в RFC 4013 [RFC4013].
The structure of the key when used with long-term credentials facilitates deployment in systems that also utilize SIP. Typically, SIP systems utilizing SIP's digest authentication mechanism do not actually store the password in the database. Rather, they store a value called H(A1), which is equal to the key defined above.
Структура ключа при использовании с долгосрочными учетными данными облегчает развёртывание в системах, которые также используют SIP. Как правило, системы SIP, использующие механизм digest-аутентификации SIP, фактически не хранят пароль в базе данных. Вместо этого они хранят значение H(A1), равное ключу, определённому выше.
Based on the rules above, the hash used to construct MESSAGE- INTEGRITY includes the length field from the STUN message header. Prior to performing the hash, the MESSAGE-INTEGRITY attribute MUST be inserted into the message (with dummy content). The length MUST then be set to point to the length of the message up to, and including, the MESSAGE-INTEGRITY attribute itself, but excluding any attributes after it. Once the computation is performed, the value of the MESSAGE-INTEGRITY attribute can be filled in, and the value of the length in the STUN header can be set to its correct value -- the length of the entire message. Similarly, when validating the MESSAGE-INTEGRITY, the length field should be adjusted to point to the end of the MESSAGE-INTEGRITY attribute prior to calculating the HMAC. Such adjustment is necessary when attributes, such as FINGERPRINT, appear after MESSAGE-INTEGRITY.
Согласно правилам выше, хеш, используемый для построения MESSAGE-INTEGRITY, включает поле длины из заголовка сообщения STUN. До вычисления хеша атрибут MESSAGE-INTEGRITY ДОЛЖЕН быть вставлен в сообщение (с фиктивным содержимым). Затем значение длины ДОЛЖНО быть установлено так, чтобы указывать на длину сообщения вплоть до атрибута MESSAGE-INTEGRITY включительно, но исключая любые атрибуты после него. После выполнения вычисления значение атрибута MESSAGE-INTEGRITY можно заполнить, а значение длины в заголовке STUN можно установить в правильное значение — длину всего сообщения. Аналогично при проверке MESSAGE-INTEGRITY поле длины следует скорректировать так, чтобы оно указывало на конец атрибута MESSAGE-INTEGRITY, до вычисления HMAC. Такая корректировка необходима, когда после MESSAGE-INTEGRITY появляются атрибуты, например FINGERPRINT.
15.5. FINGERPRINT
15.5. FINGERPRINT
The FINGERPRINT attribute MAY be present in all STUN messages. The value of the attribute is computed as the CRC-32 of the STUN message up to (but excluding) the FINGERPRINT attribute itself, XOR'ed with the 32-bit value 0x5354554e (the XOR helps in cases where an application packet is also using CRC-32 in it). The 32-bit CRC is the one defined in ITU V.42 [ITU.V42.2002], which has a generator polynomial of x32+x26+x23+x22+x16+x12+x11+x10+x8+x7+x5+x4+x2+x+1. When present, the FINGERPRINT attribute MUST be the last attribute in the message, and thus will appear after MESSAGE-INTEGRITY.
Атрибут FINGERPRINT МОЖЕТ присутствовать во всех сообщениях STUN. Значение атрибута вычисляется как CRC-32 сообщения STUN вплоть до атрибута FINGERPRINT (исключая его самого), с применением XOR к 32-битному значению 0x5354554e (XOR помогает в случаях, когда прикладной пакет также использует CRC-32). 32-битный CRC — это CRC, определённый в ITU V.42 [ITU.V42.2002], с порождающим полиномом x32+x26+x23+x22+x16+x12+x11+x10+x8+x7+x5+x4+x2+x+1. При наличии атрибут FINGERPRINT ДОЛЖЕН быть последним атрибутом сообщения и, следовательно, будет стоять после MESSAGE-INTEGRITY.
The FINGERPRINT attribute can aid in distinguishing STUN packets from packets of other protocols. See Section 8.
Атрибут FINGERPRINT может помочь отличить пакеты STUN от пакетов других протоколов. См. раздел 8.
As with MESSAGE-INTEGRITY, the CRC used in the FINGERPRINT attribute covers the length field from the STUN message header. Therefore, this value must be correct and include the CRC attribute as part of the message length, prior to computation of the CRC. When using the FINGERPRINT attribute in a message, the attribute is first placed into the message with a dummy value, then the CRC is computed, and then the value of the attribute is updated. If the MESSAGE-INTEGRITY attribute is also present, then it must be present with the correct message-integrity value before the CRC is computed, since the CRC is done over the value of the MESSAGE-INTEGRITY attribute as well.
Как и в случае MESSAGE-INTEGRITY, CRC, используемый в атрибуте FINGERPRINT, охватывает поле длины из заголовка сообщения STUN. Поэтому это значение должно быть правильным и включать атрибут CRC как часть длины сообщения до вычисления CRC. При использовании атрибута FINGERPRINT в сообщении атрибут сначала помещается в сообщение с фиктивным значением, затем вычисляется CRC, а после этого значение атрибута обновляется. Если атрибут MESSAGE-INTEGRITY также присутствует, то он должен присутствовать с правильным значением целостности сообщения до вычисления CRC, поскольку CRC вычисляется и по значению атрибута MESSAGE-INTEGRITY.

15.7. REALM

15.10. SOFTWARE
The SOFTWARE attribute contains a textual description of the software being used by the agent sending the message. It is used by clients and servers. Its value SHOULD include manufacturer and version number. The attribute has no impact on operation of the protocol, and serves only as a tool for diagnostic and debugging purposes. The value of SOFTWARE is variable length. It MUST be a UTF-8 [RFC3629] encoded sequence of less than 128 characters (which can be as long as 763 bytes).
Атрибут SOFTWARE содержит текстовое описание программного обеспечения, используемого агентом, отправляющим сообщение. Он используется клиентами и серверами. Его значение СЛЕДУЕТ включать производителя и номер версии. Атрибут не влияет на работу протокола и служит только средством диагностики и отладки. Значение SOFTWARE имеет переменную длину. Оно ДОЛЖНО быть последовательностью в кодировке UTF-8 [RFC3629] длиной менее 128 символов (что может составлять до 763 байт).
15.11. ALTERNATE-SERVER
15.11. ALTERNATE-SERVER
The alternate server represents an alternate transport address identifying a different STUN server that the STUN client should try.
Альтернативный сервер представляет альтернативный транспортный адрес, идентифицирующий другой сервер STUN, который клиенту STUN следует попробовать.
It is encoded in the same way as MAPPED-ADDRESS, and thus refers to a single server by IP address. The IP address family MUST be identical to that of the source IP address of the request.
Он кодируется так же, как MAPPED-ADDRESS, и, таким образом, указывает на один сервер по IP-адресу. Семейство IP-адресов ДОЛЖНО совпадать с семейством исходного IP-адреса запроса.
16. Security Considerations
16. Соображения безопасности
16.1. Attacks against the Protocol
16.1. Атаки, направленные на протокол
16.1.1. Outside Attacks
16.1.1. Внешние атаки
An attacker can try to modify STUN messages in transit, in order to cause a failure in STUN operation. These attacks are detected for both requests and responses through the message-integrity mechanism, using either a short-term or long-term credential. Of course, once detected, the manipulated packets will be dropped, causing the STUN transaction to effectively fail. This attack is possible only by an on-path attacker.
Атакующий может попытаться изменить сообщения STUN при передаче, чтобы вызвать сбой в работе STUN. Эти атаки обнаруживаются как для запросов, так и для ответов с помощью механизма целостности сообщений с использованием краткосрочных или долгосрочных учетных данных. Разумеется, после обнаружения изменённые пакеты будут отброшены, что приведёт к фактическому сбою транзакции STUN. Эта атака возможна только со стороны атакующего на пути.
An attacker that can observe, but not modify, STUN messages in- transit (for example, an attacker present on a shared access medium, such as Wi-Fi), can see a STUN request, and then immediately send a STUN response, typically an error response, in order to disrupt STUN processing. This attack is also prevented for messages that utilize MESSAGE-INTEGRITY. However, some error responses, those related to authentication in particular, cannot be protected by MESSAGE- INTEGRITY. When STUN itself is run over a secure transport protocol (e.g., TLS), these attacks are completely mitigated. Depending on the STUN usage, these attacks may be of minimal consequence and thus do not require message integrity to mitigate. For example, when STUN is used to a basic STUN server to discover a server reflexive candidate for usage with ICE, authentication and message integrity are not required since these attacks are detected during the connectivity check phase. The connectivity checks themselves, however, require protection for proper operation of ICE overall. As described in Section 14, STUN usages describe when authentication and message integrity are needed.
Атакующий, который может наблюдать, но не изменять сообщения STUN при передаче (например, атакующий, присутствующий на общей среде доступа, такой как Wi-Fi), может увидеть запрос STUN и затем немедленно отправить ответ STUN, обычно ответ об ошибке, чтобы нарушить обработку STUN. Эта атака также предотвращается для сообщений, использующих MESSAGE-INTEGRITY. Однако некоторые ответы об ошибках, в частности связанные с аутентификацией, не могут быть защищены MESSAGE-INTEGRITY. Когда сам STUN работает поверх защищённого транспортного протокола (например, TLS), эти атаки полностью смягчаются. В зависимости от применения STUN эти атаки могут иметь минимальные последствия и поэтому не требуют целостности сообщений для их смягчения. Например, когда STUN используется с базовым сервером STUN для обнаружения серверного рефлексивного кандидата для применения с ICE, аутентификация и целостность сообщений не требуются, поскольку эти атаки обнаруживаются на этапе проверки связности. Однако сами проверки связности требуют защиты для правильной работы ICE в целом. Как описано в разделе 14, применения STUN описывают, когда необходимы аутентификация и целостность сообщений.
Since STUN uses the HMAC of a shared secret for authentication and integrity protection, it is subject to offline dictionary attacks. When authentication is utilized, it SHOULD be with a strong password that is not readily subject to offline dictionary attacks. Protection of the channel itself, using TLS, mitigates these attacks. However, STUN is most often run over UDP and in those cases, strong passwords are the only way to protect against these attacks.
Поскольку STUN использует HMAC общего секрета для аутентификации и защиты целостности, он подвержен офлайн-атакам по словарю. При использовании аутентификации СЛЕДУЕТ применять надёжный пароль, который не поддаётся быстрому подбору офлайн-атакой по словарю. Защита самого канала с помощью TLS смягчает эти атаки. Однако STUN чаще всего работает через UDP, и в этих случаях надёжные пароли — единственный способ защиты от таких атак.
16.1.2. Inside Attacks
16.1.2. Внутренние атаки
A rogue client may try to launch a DoS attack against a server by sending it a large number of STUN requests. Fortunately, STUN requests can be processed statelessly by a server, making such attacks hard to launch.
Недобросовестный клиент может попытаться запустить DoS-атаку на сервер, отправив ему большое количество запросов STUN. К счастью, запросы STUN могут обрабатываться сервером без сохранения состояния, что делает такие атаки трудными для запуска.
A rogue client may use a STUN server as a reflector, sending it requests with a falsified source IP address and port. In such a case, the response would be delivered to that source IP and port. There is no amplification of the number of packets with this attack (the STUN server sends one packet for each packet sent by the client), though there is a small increase in the amount of data, since STUN responses are typically larger than requests. This attack is mitigated by ingress source address filtering.
Недобросовестный клиент может использовать сервер STUN как отражатель, отправляя ему запросы с поддельным исходным IP-адресом и портом. В таком случае ответ будет доставлен на этот исходный IP-адрес и порт. При этой атаке не происходит усиления количества пакетов (сервер STUN отправляет один пакет на каждый пакет, отправленный клиентом), хотя есть небольшое увеличение объёма данных, поскольку ответы STUN обычно больше запросов. Эта атака смягчается фильтрацией исходных адресов на входе.
Revealing the specific software version of the agent through the SOFTWARE attribute might allow them to become more vulnerable to attacks against software that is known to contain security holes. Implementers SHOULD make usage of the SOFTWARE attribute a configurable option.
Раскрытие конкретной версии программного обеспечения агента через атрибут SOFTWARE может сделать его более уязвимым к атакам на программное обеспечение, о котором известно, что оно содержит дыры в безопасности. Разработчикам СЛЕДУЕТ делать использование атрибута SOFTWARE настраиваемой опцией.
16.2. Attacks Affecting the Usage
16.2. Атаки, влияющие на применение
This section lists attacks that might be launched against a usage of STUN. Each STUN usage must consider whether these attacks are applicable to it, and if so, discuss counter-measures.
В этом разделе перечислены атаки, которые могут быть предприняты против применения STUN. Каждое применение STUN должно учитывать, применимы ли к нему эти атаки, и если да, обсуждать контрмеры.
Most of the attacks in this section revolve around an attacker modifying the reflexive address learned by a STUN client through a Binding request/response transaction. Since the usage of the reflexive address is a function of the usage, the applicability and remediation of these attacks are usage-specific. In common situations, modification of the reflexive address by an on-path attacker is easy to do. Consider, for example, the common situation where STUN is run directly over UDP. In this case, an on-path attacker can modify the source IP address of the Binding request before it arrives at the STUN server. The STUN server will then return this IP address in the XOR-MAPPED-ADDRESS attribute to the client, and send the response back to that (falsified) IP address and port. If the attacker can also intercept this response, it can direct it back towards the client. Protecting against this attack by using a message-integrity check is impossible, since a message- integrity value cannot cover the source IP address, since the intervening NAT must be able to modify this value. Instead, one solution to preventing the attacks listed below is for the client to verify the reflexive address learned, as is done in ICE [MMUSIC-ICE]. Other usages may use other means to prevent these attacks.
Большинство атак в этом разделе связаны с тем, что атакующий изменяет рефлексивный адрес, узнанный клиентом STUN в транзакции запрос/ответ Binding. Поскольку использование рефлексивного адреса является функцией применения, применимость и способы устранения этих атак зависят от применения. В обычных ситуациях изменение рефлексивного адреса атакующим на пути выполнить легко. Рассмотрим, например, обычную ситуацию, когда STUN работает непосредственно через UDP. В этом случае атакующий на пути может изменить исходный IP-адрес запроса Binding до того, как тот достигнет сервера STUN. Сервер STUN затем вернёт этот IP-адрес в атрибуте XOR-MAPPED-ADDRESS клиенту и отправит ответ обратно на этот (поддельный) IP-адрес и порт. Если атакующий может также перехватить этот ответ, он может направить его обратно клиенту. Защита от этой атаки с помощью проверки целостности сообщения невозможна, поскольку значение целостности сообщения не может охватывать исходный IP-адрес, так как промежуточный NAT должен иметь возможность изменять это значение. Вместо этого одним из решений для предотвращения перечисленных ниже атак является проверка клиентом узнанного рефлексивного адреса, как это делается в ICE [MMUSIC-ICE]. Другие применения могут использовать иные средства для предотвращения этих атак.
16.2.1. Attack I: Distributed DoS (DDoS) against a Target
16.2.1. Атака I: распределённый DoS (DDoS) на цель
In this attack, the attacker provides one or more clients with the same faked reflexive address that points to the intended target. This will trick the STUN clients into thinking that their reflexive addresses are equal to that of the target. If the clients hand out that reflexive address in order to receive traffic on it (for example, in SIP messages), the traffic will instead be sent to the target. This attack can provide substantial amplification, especially when used with clients that are using STUN to enable multimedia applications. However, it can only be launched against targets for which packets from the STUN server to the target pass through the attacker, limiting the cases in which it is possible.
В этой атаке атакующий предоставляет одному или нескольким клиентам один и тот же поддельный рефлексивный адрес, указывающий на намеченную цель. Это заставит клиентов STUN думать, что их рефлексивные адреса равны адресу цели. Если клиенты передают этот рефлексивный адрес, чтобы получать на него трафик (например, в сообщениях SIP), трафик вместо этого будет отправлен цели. Эта атака может обеспечить существенное усиление, особенно при использовании с клиентами, применяющими STUN для организации мультимедийных приложений. Однако она может быть запущена только против целей, для которых пакеты от сервера STUN к цели проходят через атакующего, что ограничивает случаи, в которых она возможна.
16.2.2. Attack II: Silencing a Client
16.2.2. Атака II: отключение клиента
In this attack, the attacker provides a STUN client with a faked reflexive address. The reflexive address it provides is a transport address that routes to nowhere. As a result, the client won't receive any of the packets it expects to receive when it hands out the reflexive address. This exploitation is not very interesting for the attacker. It impacts a single client, which is frequently not the desired target. Moreover, any attacker that can mount the attack could also deny service to the client by other means, such as preventing the client from receiving any response from the STUN server, or even a DHCP server. As with the attack in Section 16.2.1, this attack is only possible when the attacker is on path for packets sent from the STUN server towards this unused IP address.
В этой атаке атакующий предоставляет клиенту STUN поддельный рефлексивный адрес. Предоставляемый им рефлексивный адрес — это транспортный адрес, который никуда не маршрутизируется. В результате клиент не получит ни одного из пакетов, которые он ожидает получить, передавая этот рефлексивный адрес. Такая эксплуатация не очень интересна для атакующего. Она затрагивает одного клиента, который часто не является желаемой целью. Более того, любой атакующий, способный осуществить эту атаку, мог бы также отказать клиенту в обслуживании иными способами, например не давая клиенту получить любой ответ от сервера STUN или даже от DHCP-сервера. Как и в случае атаки из раздела 16.2.1, эта атака возможна только тогда, когда атакующий находится на пути пакетов, отправляемых от сервера STUN к этому неиспользуемому IP-адресу.
16.2.3. Attack III: Assuming the Identity of a Client
16.2.3. Атака III: присвоение идентичности клиента
This attack is similar to attack II. However, the faked reflexive address points to the attacker itself. This allows the attacker to receive traffic that was destined for the client.
Эта атака аналогична атаке II. Однако поддельный рефлексивный адрес указывает на самого атакующего. Это позволяет атакующему получать трафик, предназначенный клиенту.
16.2.4. Attack IV: Eavesdropping
16.2.4. Атака IV: прослушивание
In this attack, the attacker forces the client to use a reflexive address that routes to itself. It then forwards any packets it receives to the client. This attack would allow the attacker to observe all packets sent to the client. However, in order to launch the attack, the attacker must have already been able to observe packets from the client to the STUN server. In most cases (such as when the attack is launched from an access network), this means that the attacker could already observe packets sent to the client. This attack is, as a result, only useful for observing traffic by attackers on the path from the client to the STUN server, but not generally on the path of packets being routed towards the client.
В этой атаке атакующий заставляет клиента использовать рефлексивный адрес, который маршрутизируется к самому атакующему. Затем он пересылает клиенту любые полученные пакеты. Эта атака позволила бы атакующему наблюдать все пакеты, отправляемые клиенту. Однако для запуска атаки атакующий уже должен был иметь возможность наблюдать пакеты от клиента к серверу STUN. В большинстве случаев (например, когда атака запускается из сети доступа) это означает, что атакующий уже мог наблюдать пакеты, отправляемые клиенту. В результате эта атака полезна для наблюдения за трафиком только атакующим, находящимся на пути от клиента к серверу STUN, но обычно не на пути пакетов, маршрутизируемых к клиенту.
16.3. Hash Agility Plan
16.3. План замены хеша
This specification uses HMAC-SHA-1 for computation of the message integrity. If, at a later time, HMAC-SHA-1 is found to be compromised, the following is the remedy that will be applied.
В данной спецификации для вычисления целостности сообщения используется HMAC-SHA-1. Если впоследствии будет обнаружено, что HMAC-SHA-1 скомпрометирован, будет применено следующее средство исправления.
We will define a STUN extension that introduces a new message- integrity attribute, computed using a new hash. Clients would be required to include both the new and old message-integrity attributes in their requests or indications. A new server will utilize the new message-integrity attribute, and an old one, the old. After a transition period where mixed implementations are in deployment, the old message-integrity attribute will be deprecated by another specification, and clients will cease including it in requests.
Мы определим расширение STUN, которое вводит новый атрибут целостности сообщения, вычисляемый с использованием нового хеша. Клиенты должны будут включать в свои запросы или индикации как новый, так и старый атрибуты целостности сообщения. Новый сервер будет использовать новый атрибут целостности сообщения, а старый — старый. После переходного периода, когда в эксплуатации находятся смешанные реализации, старый атрибут целостности сообщения будет объявлен устаревшим другой спецификацией, и клиенты перестанут включать его в запросы.
It is also important to note that the HMAC is done using a key that is itself computed using an MD5 of the user's password. The choice of the MD5 hash was made because of the existence of legacy databases that store passwords in that form. If future work finds that an HMAC of an MD5 input is not secure, and a different hash is needed, it can also be changed using this plan. However, this would require administrators to repopulate their databases.
Также важно отметить, что HMAC вычисляется с использованием ключа, который сам вычисляется с помощью MD5 пароля пользователя. Выбор хеша MD5 был сделан из-за существования унаследованных баз данных, хранящих пароли в таком виде. Если будущая работа покажет, что HMAC от входных данных MD5 небезопасен и нужен другой хеш, его также можно заменить с помощью этого плана. Однако для этого администраторам придётся заново заполнить свои базы данных.
17. IAB Considerations
17. Соображения IAB
The IAB has studied the problem of Unilateral Self-Address Fixing (UNSAF), which is the general process by which a client attempts to determine its address in another realm on the other side of a NAT through a collaborative protocol reflection mechanism (RFC3424 [RFC3424]). STUN can be used to perform this function using a Binding request/response transaction if one agent is behind a NAT and the other is on the public side of the NAT.
IAB изучил проблему одностороннего самокорректирующегося адреса (Unilateral Self-Address Fixing, UNSAF) — общий процесс, при котором клиент пытается определить свой адрес в другом домене по другую сторону NAT через механизм совместного отражения протокола (RFC3424 [RFC3424]). STUN может использоваться для выполнения этой функции с помощью транзакции запрос/ответ Binding, если один агент находится за NAT, а другой — на публичной стороне NAT.
The IAB has mandated that protocols developed for this purpose document a specific set of considerations. Because some STUN usages provide UNSAF functions (such as ICE [MMUSIC-ICE] ), and others do not (such as SIP Outbound [SIP-OUTBOUND]), answers to these considerations need to be addressed by the usages themselves.
IAB постановил, что протоколы, разработанные для этой цели, должны документировать определённый набор соображений. Поскольку некоторые применения STUN предоставляют функции UNSAF (например, ICE [MMUSIC-ICE]), а другие нет (например, SIP Outbound [SIP-OUTBOUND]), ответы на эти соображения должны быть даны самими применениями.
18. IANA Considerations
18. Соображения IANA
IANA has created three new registries: a "STUN Methods Registry", a "STUN Attributes Registry", and a "STUN Error Codes Registry". IANA has also changed the name of the assigned IANA port for STUN from "nat-stun-port" to "stun".
IANA создала три новых реестра: «STUN Methods Registry», «STUN Attributes Registry» и «STUN Error Codes Registry». IANA также изменила имя назначенного порта IANA для STUN с «nat-stun-port» на «stun».
18.1. STUN Methods Registry
18.1. Реестр методов STUN
A STUN method is a hex number in the range 0x000 - 0xFFF. The encoding of STUN method into a STUN message is described in Section 6.
Метод STUN — это шестнадцатеричное число в диапазоне 0x000 - 0xFFF. Кодирование метода STUN в сообщение STUN описано в разделе 6.
The initial STUN methods are:
Начальными методами STUN являются:
0x000: (Reserved) 0x001: Binding 0x002: (Reserved; was SharedSecret)
0x000: (зарезервировано) 0x001: Binding 0x002: (зарезервировано; был SharedSecret)
STUN methods in the range 0x000 - 0x7FF are assigned by IETF Review [RFC5226]. STUN methods in the range 0x800 - 0xFFF are assigned by Designated Expert [RFC5226]. The responsibility of the expert is to verify that the selected codepoint(s) are not in use and that the request is not for an abnormally large number of codepoints. Technical review of the extension itself is outside the scope of the designated expert responsibility.
Методы STUN в диапазоне 0x000 - 0x7FF назначаются посредством IETF Review [RFC5226]. Методы STUN в диапазоне 0x800 - 0xFFF назначаются Designated Expert [RFC5226]. Ответственность эксперта состоит в проверке того, что выбранные кодовые точки не используются и что запрос не касается аномально большого числа кодовых точек. Техническая экспертиза самого расширения выходит за рамки ответственности назначенного эксперта.
18.2. STUN Attribute Registry
18.2. Реестр атрибутов STUN
A STUN Attribute type is a hex number in the range 0x0000 - 0xFFFF. STUN attribute types in the range 0x0000 - 0x7FFF are considered comprehension-required; STUN attribute types in the range 0x8000 - 0xFFFF are considered comprehension-optional. A STUN agent handles unknown comprehension-required and comprehension-optional attributes differently.
Тип атрибута STUN — это шестнадцатеричное число в диапазоне 0x0000 - 0xFFFF. Типы атрибутов STUN в диапазоне 0x0000 - 0x7FFF считаются обязательными для понимания; типы атрибутов STUN в диапазоне 0x8000 - 0xFFFF считаются необязательными для понимания. Агент STUN по-разному обрабатывает неизвестные обязательные и необязательные для понимания атрибуты.
The initial STUN Attributes types are: Comprehension-required range (0x0000-0x7FFF): 0x0000: (Reserved) 0x0001: MAPPED-ADDRESS 0x0002: (Reserved; was RESPONSE-ADDRESS) 0x0003: (Reserved; was CHANGE-ADDRESS) 0x0004: (Reserved; was SOURCE-ADDRESS) 0x0005: (Reserved; was CHANGED-ADDRESS) 0x0006: USERNAME 0x0007: (Reserved; was PASSWORD) 0x0008: MESSAGE-INTEGRITY 0x0009: ERROR-CODE 0x000A: UNKNOWN-ATTRIBUTES 0x000B: (Reserved; was REFLECTED-FROM) 0x0014: REALM 0x0015: NONCE 0x0020: XOR-MAPPED-ADDRESS
Начальные типы атрибутов STUN: диапазон, обязательный для понимания (0x0000-0x7FFF): 0x0000: (зарезервировано) 0x0001: MAPPED-ADDRESS 0x0002: (зарезервировано; был RESPONSE-ADDRESS) 0x0003: (зарезервировано; был CHANGE-ADDRESS) 0x0004: (зарезервировано; был SOURCE-ADDRESS) 0x0005: (зарезервировано; был CHANGED-ADDRESS) 0x0006: USERNAME 0x0007: (зарезервировано; был PASSWORD) 0x0008: MESSAGE-INTEGRITY 0x0009: ERROR-CODE 0x000A: UNKNOWN-ATTRIBUTES 0x000B: (зарезервировано; был REFLECTED-FROM) 0x0014: REALM 0x0015: NONCE 0x0020: XOR-MAPPED-ADDRESS
Comprehension-optional range (0x8000-0xFFFF) 0x8022: SOFTWARE 0x8023: ALTERNATE-SERVER 0x8028: FINGERPRINT
Диапазон, необязательный для понимания (0x8000-0xFFFF) 0x8022: SOFTWARE 0x8023: ALTERNATE-SERVER 0x8028: FINGERPRINT
STUN Attribute types in the first half of the comprehension-required range (0x0000 - 0x3FFF) and in the first half of the comprehension- optional range (0x8000 - 0xBFFF) are assigned by IETF Review [RFC5226]. STUN Attribute types in the second half of the comprehension-required range (0x4000 - 0x7FFF) and in the second half of the comprehension-optional range (0xC000 - 0xFFFF) are assigned by Designated Expert [RFC5226]. The responsibility of the expert is to verify that the selected codepoint(s) are not in use, and that the request is not for an abnormally large number of codepoints. Technical review of the extension itself is outside the scope of the designated expert responsibility.
Типы атрибутов STUN в первой половине диапазона, обязательного для понимания (0x0000 - 0x3FFF), и в первой половине диапазона, необязательного для понимания (0x8000 - 0xBFFF), назначаются посредством IETF Review [RFC5226]. Типы атрибутов STUN во второй половине диапазона, обязательного для понимания (0x4000 - 0x7FFF), и во второй половине диапазона, необязательного для понимания (0xC000 - 0xFFFF), назначаются Designated Expert [RFC5226]. Ответственность эксперта состоит в проверке того, что выбранные кодовые точки не используются и что запрос не касается аномально большого числа кодовых точек. Техническая экспертиза самого расширения выходит за рамки ответственности назначенного эксперта.
18.3. STUN Error Code Registry
18.3. Реестр кодов ошибок STUN
A STUN error code is a number in the range 0 - 699. STUN error codes are accompanied by a textual reason phrase in UTF-8 [RFC3629] that is intended only for human consumption and can be anything appropriate; this document proposes only suggested values.
Код ошибки STUN — это число в диапазоне 0 - 699. Коды ошибок STUN сопровождаются текстовой фразой-причиной в кодировке UTF-8 [RFC3629], предназначенной только для восприятия человеком и могущей быть любой подходящей; данный документ предлагает только рекомендуемые значения.
STUN error codes are consistent in codepoint assignments and semantics with SIP [RFC3261] and HTTP [RFC2616].
Коды ошибок STUN согласуются по назначению кодовых точек и семантике с SIP [RFC3261] и HTTP [RFC2616].
The initial values in this registry are given in Section 15.6. New STUN error codes are assigned based on IETF Review [RFC5226]. The specification must carefully consider how clients that do not understand this error code will process it before granting the request. See the rules in Section 7.3.4.
Начальные значения в этом реестре приведены в разделе 15.6. Новые коды ошибок STUN назначаются на основе IETF Review [RFC5226]. В спецификации необходимо тщательно продумать, как клиенты, не понимающие этот код ошибки, обработают его, прежде чем удовлетворять запрос. См. правила в разделе 7.3.4.
18.4. STUN UDP and TCP Port Numbers
18.4. Номера портов UDP и TCP для STUN
IANA has previously assigned port 3478 for STUN. This port appears in the IANA registry under the moniker "nat-stun-port". In order to align the DNS SRV procedures with the registered protocol service, IANA is requested to change the name of protocol assigned to port 3478 from "nat-stun-port" to "stun", and the textual name from "Simple Traversal of UDP Through NAT (STUN)" to "Session Traversal Utilities for NAT", so that the IANA port registry would read:
IANA ранее назначила порт 3478 для STUN. Этот порт фигурирует в реестре IANA под обозначением «nat-stun-port». Чтобы привести процедуры DNS SRV в соответствие с зарегистрированной службой протокола, IANA предлагается изменить имя протокола, назначенного порту 3478, с «nat-stun-port» на «stun», а текстовое имя — с «Simple Traversal of UDP Through NAT (STUN)» на «Session Traversal Utilities for NAT», чтобы реестр портов IANA выглядел так:
stun 3478/tcp Session Traversal Utilities for NAT (STUN) port stun 3478/udp Session Traversal Utilities for NAT (STUN) port
stun 3478/tcp Session Traversal Utilities for NAT (STUN) port stun 3478/udp Session Traversal Utilities for NAT (STUN) port
Реестр портов IANA: служба stun на портах 3478/tcp и 3478/udp.
In addition, IANA has assigned port number 5349 for the "stuns" service, defined over TCP and UDP. The UDP port is not currently defined; however, it is reserved for future use.
Кроме того, IANA назначила номер порта 5349 для службы «stuns», определённой поверх TCP и UDP. UDP-порт в настоящее время не определён; однако он зарезервирован для будущего использования.
19. Changes since RFC 3489
19. Изменения с RFC 3489
This specification obsoletes RFC 3489 [RFC3489]. This specification differs from RFC 3489 in the following ways:
Данная спецификация заменяет RFC 3489 [RFC3489]. Данная спецификация отличается от RFC 3489 следующим образом:
o Removed the notion that STUN is a complete NAT traversal solution. STUN is now a tool that can be used to produce a NAT traversal solution. As a consequence, changed the name of the protocol to Session Traversal Utilities for NAT.
o Удалено представление о том, что STUN является полным решением для обхода NAT. Теперь STUN — инструмент, который можно использовать для создания решения по обходу NAT. Как следствие, имя протокола изменено на Session Traversal Utilities for NAT.
o Introduced the concept of STUN usages, and described what a usage of STUN must document.
o Введено понятие применений STUN и описано, что применение STUN должно документировать.
o Removed the usage of STUN for NAT type detection and binding lifetime discovery. These techniques have proven overly brittle due to wider variations in the types of NAT devices than described in this document. Removed the RESPONSE-ADDRESS, CHANGED-ADDRESS, CHANGE-REQUEST, SOURCE-ADDRESS, and REFLECTED-FROM attributes.
o Удалено использование STUN для определения типа NAT и обнаружения времени жизни привязки. Эти методы оказались слишком хрупкими из-за более широкого разнообразия типов устройств NAT, чем описано в данном документе. Удалены атрибуты RESPONSE-ADDRESS, CHANGED-ADDRESS, CHANGE-REQUEST, SOURCE-ADDRESS и REFLECTED-FROM.
o Added a fixed 32-bit magic cookie and reduced length of transaction ID by 32 bits. The magic cookie begins at the same offset as the original transaction ID.
o Добавлено фиксированное 32-битное magic cookie и длина идентификатора транзакции уменьшена на 32 бита. Magic cookie начинается с того же смещения, что и исходный идентификатор транзакции.
o Added the XOR-MAPPED-ADDRESS attribute, which is included in Binding responses if the magic cookie is present in the request. Otherwise, the RFC 3489 behavior is retained (that is, Binding response includes MAPPED-ADDRESS). See discussion in XOR-MAPPED- ADDRESS regarding this change.
o Добавлен атрибут XOR-MAPPED-ADDRESS, который включается в ответы Binding, если в запросе присутствует magic cookie. В противном случае сохраняется поведение RFC 3489 (то есть ответ Binding включает MAPPED-ADDRESS). Обсуждение этого изменения см. в разделе об XOR-MAPPED-ADDRESS.
o Introduced formal structure into the message type header field, with an explicit pair of bits for indication of request, response, error response, or indication. Consequently, the message type field is split into the class (one of the previous four) and method.
o В поле типа сообщения заголовка введена формальная структура с явной парой битов для указания запроса, ответа, ответа об ошибке или индикации. Вследствие этого поле типа сообщения разделено на класс (один из предыдущих четырёх) и метод.
o Explicitly point out that the most significant 2 bits of STUN are 0b00, allowing easy differentiation with RTP packets when used with ICE.
o Явно указать, что два старших бита сообщения STUN равны 0b00, что позволяет легко отличать его от пакетов RTP при использовании с ICE.
o Added the FINGERPRINT attribute to provide a method of definitely detecting the difference between STUN and another protocol when the two protocols are multiplexed together.
o Добавлен атрибут FINGERPRINT, обеспечивающий способ надёжного обнаружения различия между STUN и другим протоколом, когда два протокола мультиплексируются вместе.
o Added support for IPv6. Made it clear that an IPv4 client could get a v6 mapped address, and vice versa.
o Добавлена поддержка IPv6. Было уточнено, что клиент IPv4 может получить отображаемый адрес v6, и наоборот.
o Added long-term-credential-based authentication.
o Добавлена аутентификация по долгосрочным учетным данным.
o Added the SOFTWARE, REALM, NONCE, and ALTERNATE-SERVER attributes.
o Добавлены атрибуты SOFTWARE, REALM, NONCE и ALTERNATE-SERVER.
o Removed the SharedSecret method, and thus the PASSWORD attribute. This method was almost never implemented and is not needed with current usages.
o Удалён метод SharedSecret, а значит, и атрибут PASSWORD. Этот метод почти никогда не реализовывался и не нужен при текущих применениях.
o Removed recommendation to continue listening for STUN responses for 10 seconds in an attempt to recognize an attack.
o Удалена рекомендация продолжать прослушивание ответов STUN в течение 10 секунд в попытке распознать атаку.
o Changed transaction timers to be more TCP friendly.
o Таймеры транзакций изменены для лучшей совместимости с TCP.
o Removed the STUN example that centered around the separation of the control and media planes. Instead, provided more information on using STUN with protocols.
o Удалён пример STUN, построенный вокруг разделения плоскостей управления и медиа. Вместо него предоставлена дополнительная информация об использовании STUN с протоколами.
o Defined a generic padding mechanism that changes the interpretation of the length attribute. This would, in theory, break backwards compatibility. However, the mechanism in RFC 3489 never worked for the few attributes that weren't aligned naturally on 32-bit boundaries.
o Определён общий механизм заполнения, который изменяет интерпретацию атрибута длины. Теоретически это нарушило бы обратную совместимость. Однако механизм в RFC 3489 никогда не работал для тех немногих атрибутов, которые не были естественно выровнены по 32-битным границам.
o REALM, SERVER, reason phrases, and NONCE limited to 127 characters. USERNAME to 513 bytes.
o REALM, SERVER, фразы-причины и NONCE ограничены 127 символами. USERNAME — 513 байтами.
o Changed the DNS SRV procedures for TCP and TLS. UDP remains the same as before.
o Изменены процедуры DNS SRV для TCP и TLS. Для UDP всё остаётся таким же, как прежде.
