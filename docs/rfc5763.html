Abstract
Аннотация
This document specifies how to use the Session Initiation Protocol (SIP) to establish a Secure Real-time Transport Protocol (SRTP) security context using the Datagram Transport Layer Security (DTLS) protocol. It describes a mechanism of transporting a fingerprint attribute in the Session Description Protocol (SDP) that identifies the key that will be presented during the DTLS handshake. The key exchange travels along the media path as opposed to the signaling path. The SIP Identity mechanism can be used to protect the integrity of the fingerprint attribute from modification by intermediate proxies.
В настоящем документе указано, как использовать протокол инициирования сессий (SIP) для установления сеанса защиты протокола реального времени (SRTP) с помощью протокола датаграммной безопасности транспортного уровня (DTLS). В нём описан механизм передачи атрибута отпечатка в протоколе описания сессий (SDP), который идентифицирует ключ, представляемый во время рукопожатия DTLS. Обмен ключами проходит по пути медиа, а не по пути сигнализации. Механизм идентичности SIP можно использовать для защиты целостности атрибута отпечатка от изменения промежуточными посредниками.

1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [RFC3261] and the Session Description Protocol (SDP) [RFC4566] are used to set up multimedia sessions or calls. SDP is also used to set up TCP [RFC4145] and additionally TCP/TLS connections for usage with media sessions [RFC4572]. The Real-time Transport Protocol (RTP) [RFC3550] is used to transmit real-time media on top of UDP and TCP [RFC4571]. Datagram TLS [RFC4347] was introduced to allow TLS functionality to be applied to datagram transport protocols, such as UDP and DCCP. This document provides guidelines on how to establish SRTP [RFC3711] security over UDP using an extension to DTLS (see [RFC5764]).
Протокол инициирования сессий (SIP) [RFC3261] и протокол описания сессий (SDP) [RFC4566] используются для установления мультимедийных сессий или вызовов. SDP также используется для установления соединений TCP [RFC4145] и дополнительно TCP/TLS для использования с медиасессиями [RFC4572]. Протокол реального времени (RTP) [RFC3550] используется для передачи медиаданных реального времени поверх UDP и TCP [RFC4571]. Датаграммный TLS [RFC4347] был введён, чтобы позволить применять функциональность TLS к датаграммным транспортным протоколам, таким как UDP и DCCP. Настоящий документ содержит руководство по установлению защиты SRTP [RFC3711] поверх UDP с использованием расширения DTLS (см. [RFC5764]).
The goal of this work is to provide a key negotiation technique that allows encrypted communication between devices with no prior relationships. It also does not require the devices to trust every call signaling element that was involved in routing or session setup. This approach does not require any extra effort by end users and does not require deployment of certificates that are signed by a well- known certificate authority to all devices.
Цель этой работы — предоставить метод согласования ключей, который позволяет шифрованную связь между устройствами без предварительных отношений. Он также не требует, чтобы устройства доверяли каждому элементу сигнализации вызова, участвовавшему в маршрутизации или установлении сессии. Этот подход не требует дополнительных усилий со стороны конечных пользователей и не требует развёртывания на всех устройствах сертификатов, подписанных известным удостоверяющим центром.
The media is transported over a mutually authenticated DTLS session where both sides have certificates. It is very important to note that certificates are being used purely as a carrier for the public keys of the peers. This is required because DTLS does not have a mode for carrying bare keys, but it is purely an issue of formatting. The certificates can be self-signed and completely self-generated. All major TLS stacks have the capability to generate such certificates on demand. However, third-party certificates MAY also be used if the peers have them (thus reducing the need to trust intermediaries). The certificate fingerprints are sent in SDP over SIP as part of the offer/answer exchange.
Медиаданные передаются через взаимно аутентифицированный сеанс DTLS, в котором обе стороны имеют сертификаты. Очень важно отметить, что сертификаты используются исключительно как носитель открытых ключей участников. Это необходимо, поскольку DTLS не имеет режима для переноса «голых» ключей, но это исключительно вопрос форматирования. Сертификаты могут быть самоподписанными и полностью самосозданными. Все основные стеки TLS способны создавать такие сертификаты по запросу. Однако МОГУТ также использоваться сертификаты третьих сторон, если они есть у участников (что снижает потребность в доверии к посредникам). Отпечатки сертификатов передаются в SDP поверх SIP в рамках обмена предложением/ответом.
The fingerprint mechanism allows one side of the connection to verify that the certificate presented in the DTLS handshake matches the certificate used by the party in the signaling. However, this requires some form of integrity protection on the signaling. S/MIME signatures, as described in RFC 3261, or SIP Identity, as described in [RFC4474], provide the highest level of security because they are not susceptible to modification by malicious intermediaries. However, even hop-by-hop security, such as provided by SIPS, offers some protection against modification by attackers who are not in control of on-path signaling elements. Because DTLS-SRTP only requires message integrity and not confidentiality for the signaling, the number of elements that must have credentials and be trusted is significantly reduced. In particular, if RFC 4474 is used, only the Authentication Service need have a certificate and be trusted. Intermediate elements cannot undetectably modify the message and therefore cannot mount a man-in-the-middle (MITM) attack. By comparison, because SDESCRIPTIONS [RFC4568] requires confidentiality for the signaling, all intermediate elements must be trusted.
Механизм отпечатков позволяет одной стороне соединения проверить, что сертификат, предъявленный в рукопожатии DTLS, совпадает с сертификатом, использованным стороной в сигнализации. Однако для этого требуется некоторая форма защиты целостности сигнализации. Подписи S/MIME, как описано в RFC 3261, или идентичность SIP, как описано в [RFC4474], обеспечивают наивысший уровень безопасности, поскольку они не подвержены изменению злоумышленными посредниками. Однако даже пошаговая защита, такая как обеспечиваемая SIPS, даёт некоторую защиту от изменения злоумышленниками, которые не контролируют элементы сигнализации на пути. Поскольку DTLS-SRTP требует для сигнализации только целостности сообщений, а не конфиденциальности, число элементов, которые должны иметь учётные данные и пользоваться доверием, значительно сокращается. В частности, если используется RFC 4474, только служба аутентификации должна иметь сертификат и пользоваться доверием. Промежуточные элементы не могут незаметно изменить сообщение и, следовательно, не могут осуществить атаку «посредник посередине» (MITM). Для сравнения: поскольку SDESCRIPTIONS [RFC4568] требует конфиденциальности сигнализации, все промежуточные элементы должны пользоваться доверием.
This approach differs from previous attempts to secure media traffic where the authentication and key exchange protocol (e.g., Multimedia Internet KEYing (MIKEY) [RFC3830]) is piggybacked in the signaling message exchange. With DTLS-SRTP, establishing the protection of the media traffic between the endpoints is done by the media endpoints with only a cryptographic binding of the media keying to the SIP/SDP communication. It allows RTP and SIP to be used in the usual manner when there is no encrypted media.
Этот подход отличается от предыдущих попыток защитить медиатрафик, когда протокол аутентификации и обмена ключами (например, Multimedia Internet KEYing (MIKEY) [RFC3830]) переносится попутно в обмене сообщениями сигнализации. В DTLS-SRTP установление защиты медиатрафика между конечными точками выполняется самими медиаточками, и лишь криптографическая привязка ключей медиа к обмену SIP/SDP. Это позволяет использовать RTP и SIP обычным образом, когда шифрованные медиаданные отсутствуют.
In SIP, typically the caller sends an offer and the callee may subsequently send one-way media back to the caller before a SIP answer is received by the caller. The approach in this specification, where the media key negotiation is decoupled from the SIP signaling, allows the early media to be set up before the SIP answer is received while preserving the important security property of allowing the media sender to choose some of the keying material for the media. This also allows the media sessions to be changed, rekeyed, and otherwise modified after the initial SIP signaling without any additional SIP signaling.
В SIP обычно вызывающий отправляет предложение, а вызываемый может затем отправлять односторонние медиаданные обратно вызывающему до того, как вызывающий получит ответ SIP. Подход настоящей спецификации, в котором согласование ключей медиа отделено от сигнализации SIP, позволяет установить ранние медиа до получения ответа SIP, сохраняя важное свойство безопасности — возможность отправителя медиа выбирать часть ключевого материала для медиа. Это также позволяет изменять, перевырабатывать ключи и иным образом модифицировать медиасессии после начальной сигнализации SIP без какой-либо дополнительной сигнализации SIP.
Design decisions that influence the applicability of this specification are discussed in Section 3.
Проектные решения, влияющие на применимость настоящей спецификации, обсуждаются в разделе 3.
2. Overview
2. Обзор
Endpoints wishing to set up an RTP media session do so by exchanging offers and answers in SDP messages over SIP. In a typical use case, two endpoints would negotiate to transmit audio data over RTP using the UDP protocol.
Конечные точки, желающие установить медиасессию RTP, делают это путём обмена предложениями и ответами в сообщениях SDP через SIP. В типичном случае две конечные точки договариваются передавать аудиоданные по RTP с использованием протокола UDP.

Consider Alice wanting to set up an encrypted audio session with Bob. Both Bob and Alice could use public-key-based authentication in order to establish a confidentiality protected channel using DTLS.
Рассмотрим Алису, желающую установить шифрованную аудиосессию с Бобом. И Боб, и Алиса могли бы использовать аутентификацию на основе открытых ключей, чтобы установить канал с защищённой конфиденциальностью с помощью DTLS.
Since providing mutual authentication between two arbitrary endpoints on the Internet using public-key-based cryptography tends to be problematic, we consider more deployment-friendly alternatives. This document uses one approach and several others are discussed in Section 8.
Поскольку взаимная аутентификация между двумя произвольными конечными точками в Интернете с использованием криптографии на открытых ключах, как правило, проблематична, мы рассматриваем более удобные для развёртывания альтернативы. В настоящем документе используется один подход, а несколько других обсуждаются в разделе 8.
Alice sends an SDP offer to Bob over SIP. If Alice uses only self- signed certificates for the communication with Bob, a fingerprint is included in the SDP offer/answer exchange. This fingerprint binds the DTLS key exchange in the media plane to the signaling plane.
Алиса отправляет Бобу предложение SDP по SIP. Если Алиса использует для связи с Бобом только самоподписанные сертификаты, в обмен предложением/ответом SDP включается отпечаток. Этот отпечаток привязывает обмен ключами DTLS в плоскости медиа к плоскости сигнализации.
The fingerprint alone protects against active attacks on the media but not active attacks on the signaling. In order to prevent active attacks on the signaling, "Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)" [RFC4474] may be used. When Bob receives the offer, the peers establish some number of DTLS connections (depending on the number of media sessions) with mutual DTLS authentication (i.e., both sides provide certificates). At this point, Bob can verify that Alice's credentials offered in TLS match the fingerprint in the SDP offer, and Bob can begin sending media to Alice. Once Bob accepts Alice's offer and sends an SDP answer to Alice, Alice can begin sending confidential media to Bob over the appropriate streams. Alice and Bob will verify that the fingerprints from the certificates received over the DTLS handshakes match with the fingerprints received in the SDP of the SIP signaling. This provides the security property that Alice knows that the media traffic is going to Bob and vice versa without necessarily requiring global Public Key Infrastructure (PKI) certificates for Alice and Bob. (See Section 8 for detailed security analysis.)
Один лишь отпечаток защищает от активных атак на медиа, но не от активных атак на сигнализацию. Чтобы предотвратить активные атаки на сигнализацию, может использоваться документ «Enhancements for Authenticated Identity Management in the Session Initiation Protocol (SIP)» [RFC4474]. Когда Боб получает предложение, участники устанавливают некоторое число соединений DTLS (в зависимости от числа медиасессий) со взаимной аутентификацией DTLS (то есть обе стороны предъявляют сертификаты). В этот момент Боб может проверить, что учётные данные Алисы, предложенные в TLS, совпадают с отпечатком в предложении SDP, и Боб может начать отправлять медиа Алисе. Как только Боб принимает предложение Алисы и отправляет Алисе ответ SDP, Алиса может начать отправлять Бобу конфиденциальные медиаданные по соответствующим потокам. Алиса и Боб проверят, что отпечатки из сертификатов, полученных в рукопожатиях DTLS, совпадают с отпечатками, полученными в SDP сигнализации SIP. Это обеспечивает свойство безопасности: Алиса знает, что медиатрафик направляется Бобу, и наоборот, без обязательного требования глобальных сертификатов инфраструктуры открытых ключей (PKI) для Алисы и Боба. (Подробный анализ безопасности см. в разделе 8.)
3. Motivation
3. Мотивация
Although there is already prior work in this area (e.g., Security Descriptions for SDP [RFC4568], Key Management Extensions [RFC4567] combined with MIKEY [RFC3830] for authentication and key exchange), this specification is motivated as follows:
Хотя в этой области уже есть предшествующие работы (например, Security Descriptions for SDP [RFC4568], Key Management Extensions [RFC4567] в сочетании с MIKEY [RFC3830] для аутентификации и обмена ключами), настоящая спецификация мотивирована следующим:
o TLS will be used to offer security for connection-oriented media. The design of TLS is well-known and implementations are widely available.
o TLS будет использоваться для обеспечения безопасности медиа с установлением соединения. Дизайн TLS хорошо известен, а реализации широко доступны.
o This approach deals with forking and early media without requiring support for Provisional Response ACKnowledgement (PRACK) [RFC3262] while preserving the important security property of allowing the offerer to choose keying material for encrypting the media.
o Этот подход справляется с разветвлением и ранними медиа, не требуя поддержки подтверждения предварительного ответа (PRACK) [RFC3262], сохраняя важное свойство безопасности — возможность инициатора предложения выбирать ключевой материал для шифрования медиа.
o The establishment of security protection for the media path is also provided along the media path and not over the signaling path. In many deployment scenarios, the signaling and media traffic travel along a different path through the network.
o Установление защиты для медиапути также обеспечивается вдоль самого медиапути, а не через путь сигнализации. Во многих сценариях развёртывания систем сигнализация и медиатрафик проходят по разным путям через сеть связи.
o When RFC 4474 is used, this solution works even when the SIP proxies downstream of the authentication service are not trusted. There is no need to reveal keys in the SIP signaling or in the SDP message exchange, as is done in SDESCRIPTIONS [RFC4568]. Retargeting of a dialog-forming request (changing the value of the Request-URI), the User Agent (UA) that receives it (the User Agent Server, UAS) can have a different identity from that in the To header field. When RFC 4916 is used, then it is possible to supply its identity to the peer UA by means of a request in the reverse direction, and for that identity to be signed by an Authentication Service.
o Когда используется RFC 4474, это решение работает даже при недоверии к прокси-серверам SIP ниже по потоку от службы аутентификации. Нет необходимости раскрывать ключи в сигнализации SIP или в обмене сообщениями SDP, как это делается в SDESCRIPTIONS [RFC4568]. При переадресации запроса, формирующего диалог (изменении значения Request-URI), пользовательский агент (UA), получающий его (пользовательский агент-сервер, UAS), может иметь идентичность, отличную от указанной в поле заголовка To. Когда используется RFC 4916, можно передать свою идентичность равноправному UA посредством запроса в обратном направлении, и эта идентичность может быть подписана службой аутентификации.
o In this method, synchronization source (SSRC) collisions do not result in any extra SIP signaling.
o В этом методе коллизии идентификаторов источника синхронизации (SSRC) не приводят к дополнительной сигнализации SIP.
o Many SIP endpoints already implement TLS. The changes to existing SIP and RTP usage are minimal even when DTLS-SRTP [RFC5764] is used.
o Многие конечные точки SIP уже реализуют TLS. Изменения в существующем использовании SIP и RTP минимальны, даже когда используется DTLS-SRTP [RFC5764].
4. Terminology
4. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе следует понимать так, как описано в [RFC2119].
DTLS/TLS uses the term "session" to refer to a long-lived set of keying material that spans associations. In this document, consistent with SIP/SDP usage, we use it to refer to a multimedia session and use the term "TLS session" to refer to the TLS construct. We use the term "association" to refer to a particular DTLS cipher suite and keying material set that is associated with a single host/ port quartet. The same DTLS/TLS session can be used to establish the keying material for multiple associations. For consistency with other SIP/SDP usage, we use the term "connection" when what's being referred to is a multimedia stream that is not specifically DTLS/TLS.
В DTLS/TLS термин «сессия» (session) обозначает долгоживущий набор ключевого материала, охватывающий несколько ассоциаций. В настоящем документе, в соответствии с практикой SIP/SDP, мы используем его для обозначения мультимедийной сессии, а термин «сессия TLS» — для обозначения конструкции TLS. Термин «ассоциация» мы используем для обозначения конкретного набора шифров DTLS и ключевого материала, связанного с одной четвёркой узел/порт. Одна и та же сессия DTLS/TLS может использоваться для установления ключевого материала для нескольких ассоциаций. Для согласованности с практикой SIP/SDP мы используем термин «соединение», когда речь идёт о мультимедийном потоке, не являющемся специально DTLS/TLS.
In this document, the term "Mutual DTLS" indicates that both the DTLS client and server present certificates even if one or both certificates are self-signed.
В настоящем документе термин «взаимный DTLS» (Mutual DTLS) означает, что и клиент, и сервер DTLS предъявляют сертификаты, даже если один или оба сертификата самоподписаны.
5. Establishing a Secure Channel
5. Установление защищённого канала
The two endpoints in the exchange present their identities as part of the DTLS handshake procedure using certificates. This document uses certificates in the same style as described in "Connection-Oriented Media Transport over the Transport Layer Security (TLS) Protocol in the Session Description Protocol (SDP)" [RFC4572].
Две конечные точки в обмене предъявляют свои идентичности в ходе процедуры рукопожатия DTLS с помощью сертификатов. Настоящий документ использует сертификаты в том же стиле, который описан в документе «Connection-Oriented Media Transport over the Transport Layer Security (TLS) Protocol in the Session Description Protocol (SDP)» [RFC4572].
If self-signed certificates are used, the content of the subjectAltName attribute inside the certificate MAY use the uniform resource identifier (URI) of the user. This is useful for debugging purposes only and is not required to bind the certificate to one of the communication endpoints. The integrity of the certificate is ensured through the fingerprint attribute in the SDP. The subjectAltName is not an important component of the certificate verification.
Если используются самоподписанные сертификаты, содержимое атрибута subjectAltName внутри сертификата МОЖЕТ использовать универсальный идентификатор ресурса (URI) пользователя. Это полезно только для отладки и не требуется для привязки сертификата к одной из конечных точек связи. Целостность сертификата обеспечивается атрибутом отпечатка в SDP. subjectAltName не является важным компонентом проверки сертификата.
The generation of public/private key pairs is relatively expensive. Endpoints are not required to generate certificates for each session.
Генерация пар открытого/закрытого ключей относительно дорога. Конечные точки не обязаны создавать сертификаты для каждой сессии.
The offer/answer model, defined in [RFC3264], is used by protocols like the Session Initiation Protocol (SIP) [RFC3261] to set up multimedia sessions. In addition to the usual contents of an SDP [RFC4566] message, each media description ("m=" line and associated parameters) will also contain several attributes as specified in [RFC5764], [RFC4145], and [RFC4572].
Модель предложения/ответа, определённая в [RFC3264], используется такими протоколами, как протокол инициирования сессий (SIP) [RFC3261], для установления мультимедийных сессий. Помимо обычного содержимого сообщения SDP [RFC4566], каждое описание медиа (строка «m=» и связанные параметры) также будет содержать несколько атрибутов, указанных в [RFC5764], [RFC4145] и [RFC4572].
When an endpoint wishes to set up a secure media session with another endpoint, it sends an offer in a SIP message to the other endpoint. This offer includes, as part of the SDP payload, the fingerprint of the certificate that the endpoint wants to use. The endpoint SHOULD send the SIP message containing the offer to the offerer's SIP proxy over an integrity protected channel. The proxy SHOULD add an Identity header field according to the procedures outlined in [RFC4474]. The SIP message containing the offer SHOULD be sent to the offerer's SIP proxy over an integrity protected channel. When the far endpoint receives the SIP message, it can verify the identity of the sender using the Identity header field. Since the Identity header field is a digital signature across several SIP header fields, in addition to the body of the SIP message, the receiver can also be certain that the message has not been tampered with after the digital signature was applied and added to the SIP message.
Когда конечная точка желает установить защищённую медиасессию с другой конечной точкой, она отправляет предложение в сообщении SIP другой конечной точке. Это предложение включает как часть полезной нагрузки SDP отпечаток сертификата, который конечная точка хочет использовать. Конечной точке СЛЕДУЕТ отправлять сообщение SIP, содержащее предложение, прокси-серверу SIP инициатора предложения по каналу с защитой целостности. Прокси-серверу СЛЕДУЕТ добавить поле заголовка Identity в соответствии с процедурами, изложенными в [RFC4474]. Сообщение SIP, содержащее предложение, СЛЕДУЕТ отправлять прокси-серверу SIP инициатора предложения по каналу с защитой целостности. Когда удалённая конечная точка получает сообщение SIP, она может проверить идентичность отправителя с помощью поля заголовка Identity. Поскольку поле заголовка Identity представляет собой цифровую подпись по нескольким полям заголовков SIP в дополнение к телу сообщения SIP, получатель также может быть уверен, что сообщение не было изменено после того, как цифровая подпись была вычислена и добавлена в сообщение SIP.
The far endpoint (answerer) may now establish a DTLS association with the offerer. Alternately, it can indicate in its answer that the offerer is to initiate the TLS association. In either case, mutual DTLS certificate-based authentication will be used. After completing the DTLS handshake, information about the authenticated identities, including the certificates, are made available to the endpoint application. The answerer is then able to verify that the offerer's certificate used for authentication in the DTLS handshake can be associated to the certificate fingerprint contained in the offer in the SDP. At this point, the answerer may indicate to the end user that the media is secured. The offerer may only tentatively accept the answerer's certificate since it may not yet have the answerer's certificate fingerprint.
Удалённая конечная точка (ответчик) теперь может установить ассоциацию DTLS с инициатором предложения. Либо она может указать в своём ответе, что инициатор предложения должен инициировать ассоциацию TLS. В любом случае будет использоваться взаимная аутентификация DTLS на основе сертификатов. После завершения рукопожатия DTLS информация об аутентифицированных идентичностях, включая сертификаты, становится доступной приложению конечной точки. Затем ответчик может проверить, что сертификат инициатора предложения, использованный для аутентификации в рукопожатии DTLS, может быть связан с отпечатком сертификата, содержащимся в предложении в SDP. В этот момент ответчик может сообщить конечному пользователю, что медиа защищены. Инициатор предложения может лишь предварительно принять сертификат ответчика, поскольку у него может ещё не быть отпечатка сертификата ответчика.
When the answerer accepts the offer, it provides an answer back to the offerer containing the answerer's certificate fingerprint. At this point, the offerer can accept or reject the peer's certificate and the offerer can indicate to the end user that the media is secured.
Когда ответчик принимает предложение, он возвращает инициатору предложения ответ, содержащий отпечаток сертификата ответчика. В этот момент инициатор предложения может принять или отклонить сертификат участника, и инициатор предложения может сообщить конечному пользователю, что медиа защищены.
Note that the entire authentication and key exchange for securing the media traffic is handled in the media path through DTLS. The signaling path is only used to verify the peers' certificate fingerprints. The offer and answer MUST conform to the following requirements.
Отметим, что вся аутентификация и обмен ключами для защиты медиатрафика выполняются на медиапути посредством DTLS. Путь сигнализации используется только для проверки отпечатков сертификатов участников. Предложение и ответ ДОЛЖНЫ соответствовать следующим требованиям.
o The endpoint MUST use the setup attribute defined in [RFC4145]. The endpoint that is the offerer MUST use the setup attribute value of setup:actpass and be prepared to receive a client_hello before it receives the answer. The answerer MUST use either a setup attribute value of setup:active or setup:passive. Note that if the answerer uses setup:passive, then the DTLS handshake will not begin until the answerer is received, which adds additional latency. setup:active allows the answer and the DTLS handshake to occur in parallel. Thus, setup:active is RECOMMENDED. Whichever party is active MUST initiate a DTLS handshake by sending a ClientHello over each flow (host/port quartet).
o Конечная точка ДОЛЖНА использовать атрибут setup, определённый в [RFC4145]. Конечная точка, являющаяся инициатором предложения, ДОЛЖНА использовать значение атрибута setup, равное setup:actpass, и быть готовой принять client_hello до получения ответа. Ответчик ДОЛЖЕН использовать значение атрибута setup, равное setup:active или setup:passive. Отметим, что если ответчик использует setup:passive, то рукопожатие DTLS не начнётся до получения ответа, что добавляет дополнительную задержку. setup:active позволяет ответу и рукопожатию DTLS происходить параллельно. Таким образом, РЕКОМЕНДУЕТСЯ setup:active. Любая активная сторона ДОЛЖНА инициировать рукопожатие DTLS, отправив ClientHello по каждому потоку (четвёрке узел/порт).
o The endpoint MUST NOT use the connection attribute defined in [RFC4145].
o Конечная точка НЕ ДОЛЖНА использовать атрибут connection, определённый в [RFC4145].
o The endpoint MUST use the certificate fingerprint attribute as specified in [RFC4572].
o Конечная точка ДОЛЖНА использовать атрибут отпечатка сертификата, как указано в [RFC4572].
o The certificate presented during the DTLS handshake MUST match the fingerprint exchanged via the signaling path in the SDP. The security properties of this mechanism are described in Section 8.
o Сертификат, предъявленный в ходе рукопожатия DTLS, ДОЛЖЕН совпадать с отпечатком, переданным по пути сигнализации в SDP. Свойства безопасности этого механизма описаны в разделе 8.
o If the fingerprint does not match the hashed certificate, then the endpoint MUST tear down the media session immediately. Note that it is permissible to wait until the other side's fingerprint has been received before establishing the connection; however, this may have undesirable latency effects.
o Если отпечаток не совпадает с хешем сертификата, конечная точка ДОЛЖНА немедленно разорвать медиасессию. Отметим, что допустимо подождать, пока будет получен отпечаток другой стороны, прежде чем устанавливать соединение; однако это может привести к нежелательной задержке.
6. Miscellaneous Considerations
6. Прочие соображения
6.1. Anonymous Calls
6.1. Анонимные вызовы
The use of DTLS-SRTP does not provide anonymous calling; however, it also does not prevent it. However, if care is not taken when anonymous calling features, such as those described in [RFC3325] or [RFC5767] are used, DTLS-SRTP may allow deanonymizing an otherwise anonymous call. When anonymous calls are being made, the following procedures SHOULD be used to prevent deanonymization.
Использование DTLS-SRTP не обеспечивает анонимных вызовов, однако и не препятствует им. Но если не проявлять осторожности при использовании функций анонимных вызовов, таких как описанные в [RFC3325] или [RFC5767], DTLS-SRTP может позволить деанонимизировать в остальном анонимный вызов. При совершении анонимных вызовов СЛЕДУЕТ использовать следующие процедуры, чтобы предотвратить деанонимизацию.
When making anonymous calls, a new self-signed certificate SHOULD be used for each call so that the calls cannot be correlated as to being from the same caller. In situations where some degree of correlation is acceptable, the same certificate SHOULD be used for a number of calls in order to enable continuity of authentication; see Section 8.4. Additionally, note that in networks that deploy [RFC3325], RFC 3325 requires that the Privacy header field value defined in [RFC3323] needs to be set to 'id'. This is used in conjunction with the SIP identity mechanism to ensure that the identity of the user is not asserted when enabling anonymous calls. Furthermore, the content of the subjectAltName attribute inside the certificate MUST NOT contain information that either allows correlation or identification of the user that wishes to place an anonymous call. Note that following this recommendation is not sufficient to provide anonymization.
При совершении анонимных вызовов СЛЕДУЕТ использовать новый самоподписанный сертификат для каждого вызова, чтобы вызовы нельзя было соотнести как исходящие от одного и того же вызывающего. В ситуациях, когда некоторая степень соотнесения допустима, СЛЕДУЕТ использовать один и тот же сертификат для ряда вызовов, чтобы обеспечить непрерывность аутентификации; см. раздел 8.4. Кроме того, отметим, что в сетях, развёртывающих [RFC3325], RFC 3325 требует, чтобы значение поля заголовка Privacy, определённое в [RFC3323], было установлено в «id». Это используется вместе с механизмом идентичности SIP, чтобы гарантировать, что идентичность пользователя не утверждается при включении анонимных вызовов. Более того, содержимое атрибута subjectAltName внутри сертификата НЕ ДОЛЖНО содержать информацию, которая позволяет соотнести или идентифицировать пользователя, желающего совершить анонимный вызов. Отметим, что следование этой рекомендации недостаточно для обеспечения анонимизации.
6.2. Early Media
6.2. Ранние медиа
If an offer is received by an endpoint that wishes to provide early media, it MUST take the setup:active role and can immediately establish a DTLS association with the other endpoint and begin sending media. The setup:passive endpoint may not yet have validated the fingerprint of the active endpoint's certificate. The security aspects of media handling in this situation are discussed in Section 8.
Если предложение получено конечной точкой, которая желает предоставить ранние медиа, она ДОЛЖНА принять роль setup:active и может немедленно установить ассоциацию DTLS с другой конечной точкой и начать отправлять медиа. Конечная точка setup:passive может ещё не проверить отпечаток сертификата активной конечной точки. Аспекты безопасности обработки медиа в этой ситуации обсуждаются в разделе 8.
6.3. Forking
6.3. Разветвление
In SIP, it is possible for a request to fork to multiple endpoints. Each forked request can result in a different answer. Assuming that the requester provided an offer, each of the answerers will provide a unique answer. Each answerer will form a DTLS association with the offerer. The offerer can then securely correlate the SDP answer received in the SIP message by comparing the fingerprint in the answer to the hashed certificate for each DTLS association.
В SIP запрос может разветвляться к нескольким конечным точкам. Каждый разветвлённый запрос может привести к разному ответу. Предполагая, что запрашивающая сторона предоставила предложение, каждый из ответчиков предоставит уникальный ответ. Каждый ответчик сформирует ассоциацию DTLS с инициатором предложения. Затем инициатор предложения может безопасно соотнести ответ SDP, полученный в сообщении SIP, сравнив отпечаток в ответе с хешем сертификата для каждой ассоциации DTLS.
6.4. Delayed Offer Calls
6.4. Вызовы с отложенным предложением
An endpoint may send a SIP INVITE request with no offer in it. When this occurs, the receiver(s) of the INVITE will provide the offer in the response and the originator will provide the answer in the subsequent ACK request or in the PRACK request [RFC3262], if both endpoints support reliable provisional responses. In any event, the active endpoint still establishes the DTLS association with the passive endpoint as negotiated in the offer/answer exchange.
Конечная точка может отправить запрос SIP INVITE без предложения. Когда это происходит, получатель (получатели) INVITE предоставят предложение в ответе, а отправитель предоставит ответ в последующем запросе ACK или в запросе PRACK [RFC3262], если обе конечные точки поддерживают надёжные предварительные ответы. В любом случае активная конечная точка по-прежнему устанавливает ассоциацию DTLS с пассивной конечной точкой, как согласовано в обмене предложением/ответом.
6.5. Multiple Associations
6.5. Множественные ассоциации
When there are multiple flows (e.g., multiple media streams, non- multiplexed RTP and RTCP, etc.) the active side MAY perform the DTLS handshakes in any order. Appendix B of [RFC5764] provides some guidance on the performance of parallel DTLS handshakes. Note that if the answerer ends up being active, it may only initiate handshakes on some subset of the potential streams (e.g., if audio and video are offered but it only wishes to do audio). If the offerer ends up being active, the complete answer will be received before the offerer begins initiating handshakes.
Когда имеется несколько потоков (например, несколько медиапотоков, немалуплексированные RTP и RTCP и т. п.), активная сторона МОЖЕТ выполнять рукопожатия DTLS в любом порядке. Приложение B к [RFC5764] содержит некоторые указания по выполнению параллельных рукопожатий DTLS. Отметим, что если ответчик в итоге оказывается активным, он может инициировать рукопожатия лишь для некоторого подмножества потенциальных потоков (например, если предложены аудио и видео, но он желает использовать только аудио). Если активным оказывается инициатор предложения, полный ответ будет получен до того, как инициатор предложения начнёт инициировать рукопожатия.
6.6. Session Modification
6.6. Модификация сессии
Once an answer is provided to the offerer, either endpoint MAY request a session modification that MAY include an updated offer. This session modification can be carried in either an INVITE or UPDATE request. The peers can reuse the existing associations if they are compatible (i.e., they have the same key fingerprints and transport parameters), or establish a new one following the same rules are for initial exchanges, tearing down the existing association as soon as the offer/answer exchange is completed. Note that if the active/passive status of the endpoints changes, a new connection MUST be established.
После предоставления ответа инициатору предложения любая из конечных точек МОЖЕТ запросить модификацию сессии, которая МОЖЕТ включать обновлённое предложение. Эта модификация сессии может переноситься в запросе INVITE или UPDATE. Участники могут повторно использовать существующие ассоциации, если они совместимы (то есть имеют одинаковые отпечатки ключей и транспортные параметры), или установить новую, следуя тем же правилам, что и для начальных обменов, разорвав существующую ассоциацию, как только обмен предложением/ответом завершён. Отметим, что если статус активной/пассивной стороны конечных точек меняется, ДОЛЖНО быть установлено новое соединение.
6.7. Middlebox Interaction
6.7. Взаимодействие с посредниками
There are a number of potentially bad interactions between DTLS-SRTP and middleboxes, as documented in [MMUSIC-MEDIA], which also provides recommendations for avoiding such problems.
Существует ряд потенциально плохих взаимодействий между DTLS-SRTP и посредниками, как описано в [MMUSIC-MEDIA], где также приведены рекомендации по избежанию таких проблем.
6.7.1. ICE Interaction
6.7.1. Взаимодействие с ICE
Interactive Connectivity Establishment (ICE), as specified in [RFC5245], provides a methodology of allowing participants in multimedia sessions to verify mutual connectivity. When ICE is being used, the ICE connectivity checks are performed before the DTLS handshake begins. Note that if aggressive nomination mode is used, multiple candidate pairs may be marked valid before ICE finally converges on a single candidate pair. Implementations MUST treat all ICE candidate pairs associated with a single component as part of the same DTLS association. Thus, there will be only one DTLS handshake even if there are multiple valid candidate pairs. Note that this may mean adjusting the endpoint IP addresses if the selected candidate pair shifts, just as if the DTLS packets were an ordinary media stream.
Установление интерактивной связности (ICE), как указано в [RFC5245], предоставляет метод, позволяющий участникам мультимедийных сессий проверять взаимную связность. Когда используется ICE, проверки связности ICE выполняются до начала рукопожатия DTLS. Отметим, что при использовании режима агрессивного выдвижения несколько пар кандидатов могут быть помечены как допустимые до того, как ICE окончательно сойдётся на одной паре кандидатов. Реализации ДОЛЖНЫ рассматривать все пары кандидатов ICE, связанные с одним компонентом, как часть одной и той же ассоциации DTLS. Таким образом, будет только одно рукопожатие DTLS, даже если имеется несколько допустимых пар кандидатов. Отметим, что это может означать корректировку IP-адресов конечных точек, если выбранная пара кандидатов смещается, так же как если бы пакеты DTLS были обычным медиапотоком.
Note that Simple Traversal of the UDP Protocol through NAT (STUN) packets are sent directly over UDP, not over DTLS. [RFC5764] describes how to demultiplex STUN packets from DTLS packets and SRTP packets.
Отметим, что пакеты Simple Traversal of the UDP Protocol through NAT (STUN) отправляются непосредственно поверх UDP, а не поверх DTLS. [RFC5764] описывает, как демультиплексировать пакеты STUN от пакетов DTLS и пакетов SRTP.
6.7.2. Latching Control without ICE
6.7.2. Управление защёлкиванием (latching) без ICE
If ICE is not being used, then there is potential for a bad interaction with Session Border Controllers (SBCs) via "latching", as described in [MMUSIC-MEDIA]. In order to avoid this issue, if ICE is not being used and the DTLS handshake has not completed upon receiving the other side's SDP, then the passive side MUST do a single unauthenticated STUN [RFC5389] connectivity check in order to open up the appropriate pinhole. All implementations MUST be prepared to answer this request during the handshake period even if they do not otherwise do ICE. However, the active side MUST proceed with the DTLS handshake as appropriate even if no such STUN check is received and the passive MUST NOT wait for a STUN answer before sending its ServerHello.
Если ICE не используется, то существует потенциал плохого взаимодействия с пограничными контроллерами сессий (SBC) через «защёлкивание» (latching), как описано в [MMUSIC-MEDIA]. Чтобы избежать этой проблемы, если ICE не используется и рукопожатие DTLS не завершено к моменту получения SDP другой стороны, пассивная сторона ДОЛЖНА выполнить одну неаутентифицированную проверку связности STUN [RFC5389], чтобы открыть соответствующее отверстие. Все реализации ДОЛЖНЫ быть готовы ответить на этот запрос в течение периода рукопожатия, даже если они иначе не используют ICE. Однако активная сторона ДОЛЖНА продолжать рукопожатие DTLS соответствующим образом, даже если такая проверка STUN не получена, а пассивная сторона НЕ ДОЛЖНА ждать ответа STUN перед отправкой своего ServerHello.
6.8. Rekeying
6.8. Перевыработка ключей
As with TLS, DTLS endpoints can rekey at any time by redoing the DTLS handshake. While the rekey is under way, the endpoints continue to use the previously established keying material for usage with DTLS. Once the new session keys are established, the session can switch to using these and abandon the old keys. This ensures that latency is not introduced during the rekeying process.
Как и в TLS, конечные точки DTLS могут в любой момент перевыработать ключи, повторив рукопожатие DTLS. Пока перевыработка ключей выполняется, конечные точки продолжают использовать ранее установленный ключевой материал для DTLS. Как только новые ключи сессии установлены, сессия может переключиться на их использование и отказаться от старых ключей. Это гарантирует, что в процессе перевыработки ключей не вносится задержка.
Further considerations regarding rekeying in case the SRTP security context is established with DTLS can be found in Section 3.7 of [RFC5764].
Дополнительные соображения о перевыработке ключей в случае, когда сеанс защиты SRTP устанавливается с помощью DTLS, можно найти в разделе 3.7 [RFC5764].
6.9. Conference Servers and Shared Encryptions Contexts
6.9. Конференц-серверы и общие контексты шифрования
It has been proposed that conference servers might use the same encryption context for all of the participants in a conference. The advantage of this approach is that the conference server only needs to encrypt the output for all speakers instead of once per participant.
Было предложено, чтобы конференц-серверы могли использовать один и тот же контекст шифрования для всех участников конференции. Преимущество этого подхода в том, что конференц-серверу нужно шифровать выходные данные для всех говорящих только один раз, а не для каждого участника.
This shared encryption context approach is not possible under this specification because each DTLS handshake establishes fresh keys that are not completely under the control of either side. However, it is argued that the effort to encrypt each RTP packet is small compared to the other tasks performed by the conference server such as the codec processing.
Этот подход с общим контекстом шифрования невозможен в рамках настоящей спецификации, поскольку каждое рукопожатие DTLS устанавливает новые ключи, которые не находятся полностью под контролем ни одной из сторон. Однако утверждается, что усилия по шифрованию каждого пакета RTP малы по сравнению с другими задачами, выполняемыми конференц-сервером, такими как обработка кодеков.
Future extensions, such as [SRTP-EKT] or [KEY-TRANSPORT], could be used to provide this functionality in concert with the mechanisms described in this specification.
Будущие расширения, такие как [SRTP-EKT] или [KEY-TRANSPORT], могли бы использоваться для обеспечения этой функциональности вместе с механизмами, описанными в настоящей спецификации.
6.10. Media over SRTP
6.10. Медиа поверх SRTP
Because DTLS's data transfer protocol is generic, it is less highly optimized for use with RTP than is SRTP [RFC3711], which has been specifically tuned for that purpose. DTLS-SRTP [RFC5764] has been defined to provide for the negotiation of SRTP transport using a DTLS connection, thus allowing the performance benefits of SRTP with the easy key management of DTLS. The ability to reuse existing SRTP software and hardware implementations may in some environments provide another important motivation for using DTLS-SRTP instead of RTP over DTLS. Implementations of this specification MUST support DTLS-SRTP [RFC5764].
Поскольку протокол передачи данных DTLS является общим, он менее оптимизирован для использования с RTP, чем SRTP [RFC3711], который специально настроен для этой цели. Был определён DTLS-SRTP [RFC5764], обеспечивающий согласование транспорта SRTP с использованием соединения DTLS, что позволяет сочетать преимущества производительности SRTP с простым управлением ключами DTLS. Возможность повторного использования существующих программных и аппаратных реализаций SRTP в некоторых средах может дать ещё один важный мотив для использования DTLS-SRTP вместо RTP поверх DTLS. Реализации настоящей спецификации ДОЛЖНЫ поддерживать DTLS-SRTP [RFC5764].
6.11. Best Effort Encryption
6.11. Шифрование по мере возможности
[RFC5479] describes a requirement for best-effort encryption where SRTP is used and where both endpoints support it and key negotiation succeeds, otherwise RTP is used.
[RFC5479] описывает требование шифрования по мере возможности, когда используется SRTP и обе конечные точки его поддерживают, а согласование ключей завершается успешно; в противном случае используется RTP.
[MMUSIC-SDP] describes a mechanism that can signal both RTP and SRTP as an alternative. This allows an offerer to express a preference for SRTP, but RTP is the default and will be understood by endpoints that do not understand SRTP or this key exchange mechanism. Implementations of this document MUST support [MMUSIC-SDP].
[MMUSIC-SDP] описывает механизм, который может сигнализировать RTP и SRTP как альтернативы. Это позволяет инициатору предложения выразить предпочтение SRTP, но по умолчанию используется RTP, который будет понятен конечным точкам, не понимающим ни SRTP, ни этот механизм обмена ключами. Реализации настоящего документа ДОЛЖНЫ поддерживать [MMUSIC-SDP].

8. Security Considerations
8. Соображения безопасности
DTLS or TLS media signaled with SIP requires a way to ensure that the communicating peers' certificates are correct.
Медиа DTLS или TLS, сигнализируемые с помощью SIP, требуют способа убедиться, что сертификаты взаимодействующих участников верны.
The standard TLS/DTLS strategy for authenticating the communicating parties is to give the server (and optionally the client) a PKIX [RFC5280] certificate. The client then verifies the certificate and checks that the name in the certificate matches the server's domain name. This works because there are a relatively small number of servers with well-defined names; a situation that does not usually occur in the VoIP context.
Стандартная стратегия TLS/DTLS для аутентификации взаимодействующих сторон состоит в том, чтобы выдать серверу (и, возможно, клиенту) сертификат PKIX [RFC5280]. Затем клиент проверяет сертификат и убеждается, что имя в сертификате совпадает с доменным именем сервера. Это работает, поскольку существует относительно небольшое число серверов с чётко определёнными именами — ситуация, обычно не возникающая в контексте VoIP.
The design described in this document is intended to leverage the authenticity of the signaling channel (while not requiring confidentiality). As long as each side of the connection can verify the integrity of the SDP received from the other side, then the DTLS handshake cannot be hijacked via a man-in-the-middle attack. This integrity protection is easily provided by the caller to the callee (see Alice to Bob in Section 7) via the SIP Identity [RFC4474] mechanism. Other mechanisms, such as the S/MIME mechanism described in RFC 3261, or perhaps future mechanisms yet to be defined could also serve this purpose.
Дизайн, описанный в настоящем документе, предназначен для использования аутентичности канала сигнализации (не требуя при этом конфиденциальности). Пока каждая сторона соединения может проверить целостность SDP, полученного от другой стороны, рукопожатие DTLS не может быть перехвачено атакой «посредник посередине». Эта защита целостности легко обеспечивается вызывающим для вызываемого (см. Алиса — Боб в разделе 7) через механизм идентичности SIP [RFC4474]. Другие механизмы, такие как механизм S/MIME, описанный в RFC 3261, или, возможно, будущие механизмы, которые ещё предстоит определить, также могли бы служить этой цели.
While this mechanism can still be used without such integrity mechanisms, the security provided is limited to defense against passive attack by intermediaries. An active attack on the signaling plus an active attack on the media plane can allow an attacker to attack the connection (R-SIG-MEDIA in the notation of [RFC5479]).
Хотя этот механизм всё ещё можно использовать без таких механизмов целостности, обеспечиваемая безопасность ограничивается защитой от пассивной атаки посредников. Активная атака на сигнализацию вместе с активной атакой на плоскость медиа может позволить злоумышленнику атаковать соединение (R-SIG-MEDIA в нотации [RFC5479]).
8.1. Responder Identity
8.1. Идентичность ответчика
SIP Identity does not support signatures in responses. Ideally, Alice would want to know that Bob's SDP had not been tampered with and who it was from so that Alice's User Agent could indicate to Alice that there was a secure phone call to Bob. [RFC4916] defines an approach for a UA to supply its identity to its peer UA, and for this identity to be signed by an authentication service. For example, using this approach, Bob sends an answer, then immediately follows up with an UPDATE that includes the fingerprint and uses the SIP Identity mechanism to assert that the message is from Bob@example.com. The downside of this approach is that it requires the extra round trip of the UPDATE. However, it is simple and secure even when not all of the proxies are trusted. In this example, Bob only needs to trust his proxy. Offerers SHOULD support this mechanism and answerers SHOULD use it.
Идентичность SIP не поддерживает подписи в ответах. В идеале Алиса хотела бы знать, что SDP Боба не был изменён и от кого он исходит, чтобы пользовательский агент Алисы мог сообщить Алисе, что был защищённый телефонный вызов с Бобом. [RFC4916] определяет подход, при котором UA передаёт свою идентичность равноправному UA, и эта идентичность подписывается службой аутентификации. Например, используя этот подход, Боб отправляет ответ, а затем сразу отправляет UPDATE, включающий отпечаток и использующий механизм идентичности SIP, чтобы утверждать, что сообщение от Bob@example.com. Недостаток этого подхода в том, что он требует дополнительного кругового обмена UPDATE. Однако он прост и безопасен, даже когда не все прокси-серверы пользуются доверием. В этом примере Бобу нужно доверять только своему прокси-серверу. Инициаторам предложения СЛЕДУЕТ поддерживать этот механизм, а ответчикам СЛЕДУЕТ его использовать.
In some cases, answerers will not send an UPDATE and in many calls, some media will be sent before the UPDATE is received. In these cases, no integrity is provided for the fingerprint from Bob to Alice. In this approach, an attacker that was on the signaling path could tamper with the fingerprint and insert themselves as a man-in- the-middle on the media. Alice would know that she had a secure call with someone, but would not know if it was with Bob or a man-in-the- middle. Bob would know that an attack was happening. The fact that one side can detect this attack means that in most cases where Alice and Bob both wish for the communications to be encrypted, there is not a problem. Keep in mind that in any of the possible approaches, Bob could always reveal the media that was received to anyone. We are making the assumption that Bob also wants secure communications. In this do nothing case, Bob knows the media has not been tampered with or intercepted by a third party and that it is from Alice@example.com. Alice knows that she is talking to someone and that whoever that is has probably checked that the media is not being intercepted or tampered with. This approach is certainly less than ideal but very usable for many situations.
В некоторых случаях ответчики не отправляют UPDATE, и во многих вызовах часть медиа передаётся до получения UPDATE. В этих случаях целостность отпечатка, передаваемого от Боба к Алисе, не обеспечивается. При таком подходе злоумышленник, находившийся на пути сигнализации, мог бы изменить отпечаток и встать в качестве посредника посередине на пути медиа. Алиса знала бы, что у неё защищённый вызов с кем-то, но не знала бы, с Бобом ли это или с посредником посередине. Боб знал бы, что происходит атака. Тот факт, что одна сторона может обнаружить эту атаку, означает, что в большинстве случаев, когда и Алиса, и Боб хотят, чтобы связь была зашифрована, проблемы нет. Учтите, что при любом из возможных подходов Боб всегда может раскрыть полученные медиа кому угодно. Мы исходим из предположения, что Боб также хочет защищённой связи. В этом случае «ничего не делать» Боб знает, что медиа не были изменены или перехвачены третьей стороной и что они от Alice@example.com. Алиса знает, что она разговаривает с кем-то и что этот кто-то, вероятно, проверил, что медиа не перехвачены и не изменены. Этот подход, безусловно, далёк от идеала, но очень пригоден для многих ситуаций.
8.2. SIPS
8.2. SIPS
If SIP Identity is not used, but the signaling is protected by SIPS, the security guarantees are weaker. Some security is still provided as long as all proxies are trusted. This provides integrity for the fingerprint in a chain-of-trust security model. Note, however, that if the proxies are not trusted, then the level of security provided is limited.
Если идентичность SIP не используется, но сигнализация защищена с помощью SIPS, гарантии безопасности слабее. Некоторая безопасность всё же обеспечивается, пока все прокси-серверы пользуются доверием. Это обеспечивает целостность отпечатка в модели безопасности цепочки доверия. Отметим, однако, что если прокси-серверы не пользуются доверием, то уровень обеспечиваемой безопасности ограничен.
8.3. S/MIME
8.3. S/MIME
RFC 3261 [RFC3261] defines an S/MIME security mechanism for SIP that could be used to sign that the fingerprint was from Bob. This would be secure.
RFC 3261 [RFC3261] определяет механизм безопасности S/MIME для SIP, который мог бы использоваться для подписи того, что отпечаток был от Боба. Это было бы безопасно.
8.4. Continuity of Authentication
8.4. Непрерывность аутентификации
One desirable property of a secure media system is to provide continuity of authentication: being able to ensure cryptographically that you are talking to the same person as before. With DTLS, continuity of authentication is achieved by having each side use the same public key/self-signed certificate for each connection (at least with a given peer entity). It then becomes possible to cache the credential (or its hash) and verify that it is unchanged. Thus, once a single secure connection has been established, an implementation can establish a future secure channel even in the face of future insecure signaling.
Одно из желательных свойств защищённой медиасистемы — обеспечение непрерывности аутентификации: возможность криптографически убедиться, что вы разговариваете с тем же человеком, что и раньше. В DTLS непрерывность аутентификации достигается тем, что каждая сторона использует один и тот же открытый ключ/самоподписанный сертификат для каждого соединения (по крайней мере, с данным равноправным объектом). Тогда становится возможным кэшировать учётные данные (или их хеш) и проверять, что они не изменились. Таким образом, после установления одного защищённого соединения реализация может установить будущий защищённый канал даже при будущей незащищённой сигнализации.
In order to enable continuity of authentication, implementations SHOULD attempt to keep a constant long-term key. Verifying implementations SHOULD maintain a cache of the key used for each peer identity and alert the user if that key changes.
Чтобы обеспечить непрерывность аутентификации, реализации СЛЕДУЕТ стараться сохранять постоянный долгосрочный ключ. Проверяющие реализации СЛЕДУЕТ поддерживать кэш ключа, использованного для каждой идентичности участника, и предупреждать пользователя, если этот ключ меняется.
8.5. Short Authentication String
8.5. Короткая строка аутентификации
An alternative available to Alice and Bob is to use human speech to verify each other's identity and then to verify each other's fingerprints also using human speech. Assuming that it is difficult to impersonate another's speech and seamlessly modify the audio contents of a call, this approach is relatively safe. It would not be effective if other forms of communication were being used such as video or instant messaging. DTLS supports this mode of operation. The minimal secure fingerprint length is around 64 bits.
Альтернатива, доступная Алисе и Бобу, — использовать человеческую речь для проверки идентичности друг друга, а затем проверить и отпечатки друг друга также с помощью человеческой речи. Если предположить, что трудно подделать чужую речь и незаметно изменить аудиосодержимое вызова, этот подход относительно безопасен. Он был бы неэффективен при использовании других форм связи, таких как видео или обмен мгновенными сообщениями. DTLS поддерживает этот режим работы. Минимальная безопасная длина отпечатка составляет около 64 бит.
ZRTP [AVT-ZRTP] includes Short Authentication String (SAS) mode in which a unique per-connection bitstring is generated as part of the cryptographic handshake. The SAS can be as short as 25 bits and so is somewhat easier to read. DTLS does not natively support this mode. Based on the level of deployment interest, a TLS extension [RFC5246] could provide support for it. Note that SAS schemes only work well when the endpoints recognize each other's voices, which is not true in many settings (e.g., call centers).
ZRTP [AVT-ZRTP] включает режим короткой строки аутентификации (SAS), в котором в рамках криптографического рукопожатия генерируется уникальная для каждого соединения битовая строка. SAS может быть всего 25 бит и потому несколько проще для чтения. DTLS изначально не поддерживает этот режим. В зависимости от степени заинтересованности в развёртывании расширение TLS [RFC5246] могло бы обеспечить его поддержку. Отметим, что схемы SAS хорошо работают только тогда, когда конечные точки узнают голоса друг друга, что верно не во многих ситуациях (например, в кол-центрах).
8.6. Limits of Identity Assertions
8.6. Границы утверждений идентичности
When RFC 4474 is used to bind the media keying material to the SIP signaling, the assurances about the provenance and security of the media are only as good as those for the signaling. There are two important cases to note here:
Когда RFC 4474 используется для привязки ключевого материала медиа к сигнализации SIP, гарантии происхождения и безопасности медиа не лучше гарантий для сигнализации. Здесь следует отметить два важных случая:
o RFC 4474 assumes that the proxy with the certificate "example.com" controls the namespace "example.com". Therefore, the RFC 4474 authentication service that is authoritative for a given namespace can control which user is assigned each name. Thus, the authentication service can take an address formerly assigned to Alice and transfer it to Bob. This is an intentional design feature of RFC 4474 and a direct consequence of the SIP namespace architecture.
o RFC 4474 предполагает, что прокси-сервер с сертификатом «example.com» контролирует пространство имён «example.com». Поэтому служба аутентификации RFC 4474, являющаяся авторитетной для данного пространства имён, может контролировать, какому пользователю назначено каждое имя. Таким образом, служба аутентификации может взять адрес, ранее назначенный Алисе, и передать его Бобу. Это намеренная особенность дизайна RFC 4474 и прямое следствие архитектуры пространства имён SIP.
o When phone number URIs (e.g., 'sip:+17005551008@chicago.example.com' or 'sip:+17005551008@chicago.example.com;user=phone') are used, there is no structural reason to trust that the domain name is authoritative for a given phone number, although individual proxies and UAs may have private arrangements that allow them to trust other domains. This is a structural issue in that Public Switched Telephone Network (PSTN) elements are trusted to assert their phone number correctly and that there is no real concept of a given entity being authoritative for some number space.
o Когда используются URI телефонных номеров (например, «sip:+17005551008@chicago.example.com» или «sip:+17005551008@chicago.example.com;user=phone»), нет структурных оснований доверять тому, что доменное имя является авторитетным для данного телефонного номера, хотя отдельные прокси-серверы и UA могут иметь частные договорённости, позволяющие им доверять другим доменам. Это структурная проблема: элементы ТфОП (PSTN) пользуются доверием в том, что они правильно утверждают свой телефонный номер, и реального понятия авторитетности данной сущности для некоторого номерного пространства не существует.
In both of these cases, the assurances that DTLS-SRTP provides in terms of data origin integrity and confidentiality are necessarily no better than SIP provides for signaling integrity when RFC 4474 is used. Implementors should therefore take care not to indicate misleading peer identity information in the user interface. That is, if the peer's identity is sip:+17005551008@chicago.example.com, it is not sufficient to display that the identity of the peer as +17005551008, unless there is some policy that states that the domain "chicago.example.com" is trusted to assert the E.164 numbers it is asserting. In cases where the UA can determine that the peer identity is clearly an E.164 number, it may be less confusing to simply identify the call as encrypted but to an unknown peer.
В обоих этих случаях гарантии, которые DTLS-SRTP предоставляет в отношении целостности источника данных и конфиденциальности, неизбежно не лучше тех, которые SIP обеспечивает для целостности сигнализации при использовании RFC 4474. Поэтому реализаторам следует позаботиться о том, чтобы не показывать в пользовательском интерфейсе вводящую в заблуждение информацию об идентичности участника. То есть если идентичность участника — sip:+17005551008@chicago.example.com, недостаточно отображать идентичность участника как +17005551008, если только нет некоторой политики, утверждающей, что домену «chicago.example.com» можно доверять в утверждении номеров E.164, которые он утверждает. В случаях, когда UA может определить, что идентичность участника явно является номером E.164, может быть менее запутанным просто идентифицировать вызов как зашифрованный, но с неизвестным участником.
In addition, some middleboxes (back-to-back user agents (B2BUAs) and Session Border Controllers) are known to modify portions of the SIP message that are included in the RFC 4474 signature computation, thus breaking the signature. This sort of man-in-the-middle operation is precisely the sort of message modification that RFC 4474 is intended to detect. In cases where the middlebox is itself permitted to generate valid RFC 4474 signatures (e.g., it is within the same administrative domain as the RFC 4474 authentication service), then it may generate a new signature on the modified message. Alternately, the middlebox may be able to sign with some other identity that it is permitted to assert. Otherwise, the recipient cannot rely on the RFC 4474 Identity assertion and the UA MUST NOT indicate to the user that a secure call has been established to the claimed identity. Implementations that are configured to only establish secure calls SHOULD terminate the call in this case.
Кроме того, известно, что некоторые посредники (пользовательские агенты типа back-to-back (B2BUA) и пограничные контроллеры сессий) изменяют части сообщения SIP, включаемые в вычисление подписи RFC 4474, тем самым нарушая подпись. Такая операция «посредник посередине» — как раз тот вид изменения сообщения, который RFC 4474 предназначен обнаруживать. В случаях, когда самому посреднику разрешено генерировать действительные подписи RFC 4474 (например, он находится в том же административном домене, что и служба аутентификации RFC 4474), он может сгенерировать новую подпись для изменённого сообщения. Либо посредник может подписать некоторой другой идентичностью, которую ему разрешено утверждать. В противном случае получатель не может полагаться на утверждение идентичности RFC 4474, и UA НЕ ДОЛЖЕН сообщать пользователю, что установлен защищённый вызов с заявленной идентичностью. Реализациям, настроенным только на установление защищённых вызовов, СЛЕДУЕТ в этом случае завершать вызов.
If SIP Identity or an equivalent mechanism is not used, then only protection against attackers who cannot actively change the signaling is provided. While this is still superior to previous mechanisms, the security provided is inferior to that provided if integrity is provided for the signaling.
Если идентичность SIP или эквивалентный механизм не используется, то обеспечивается только защита от злоумышленников, которые не могут активно изменять сигнализацию. Хотя это всё ещё лучше предыдущих механизмов, обеспечиваемая безопасность уступает той, которая обеспечивается при защите целостности сигнализации.
8.7. Third-Party Certificates
8.7. Сертификаты третьих сторон
This specification does not depend on the certificates being held by endpoints being independently verifiable (e.g., being issued by a trusted third party). However, there is no limitation on such certificates being used. Aside from the difficulty of obtaining such certificates, it is not clear what identities those certificates would contain -- RFC 3261 specifies a convention for S/MIME certificates that could also be used here, but that has seen only minimal deployment. However, in closed or semi-closed contexts where such a convention can be established, third-party certificates can reduce the reliance on trusting even proxies in the endpoint's domains.
Настоящая спецификация не зависит от того, что сертификаты, хранящиеся у конечных точек, независимо проверяемы (например, выданы доверенной третьей стороной). Однако нет никаких ограничений на использование таких сертификатов. Помимо трудности получения таких сертификатов, неясно, какие идентичности они содержали бы, — RFC 3261 определяет соглашение для сертификатов S/MIME, которое можно было бы использовать и здесь, но оно получило лишь минимальное развёртывание. Однако в закрытых или полузакрытых контекстах, где такое соглашение может быть установлено, сертификаты третьих сторон могут уменьшить зависимость от доверия даже к прокси-серверам в доменах конечной точки.
8.8. Perfect Forward Secrecy
8.8. Совершенная прямая секретность
One concern about the use of a long-term key is that compromise of that key may lead to compromise of past communications. In order to prevent this attack, DTLS supports modes with Perfect Forward Secrecy using Diffie-Hellman and Elliptic-Curve Diffie-Hellman cipher suites. When these modes are in use, the system is secure against such attacks. Note that compromise of a long-term key may still lead to future active attacks. If this is a concern, a backup authentication channel, such as manual fingerprint establishment or a short authentication string, should be used.
Одна из проблем использования долгосрочного ключа состоит в том, что компрометация этого ключа может привести к компрометации прошлых коммуникаций. Чтобы предотвратить эту атаку, DTLS поддерживает режимы с совершенной прямой секретностью (PFS) с использованием наборов шифров Диффи — Хеллмана и эллиптических кривых Диффи — Хеллмана. Когда эти режимы используются, система защищена от таких атак. Отметим, что компрометация долгосрочного ключа всё же может привести к будущим активным атакам. Если это вызывает беспокойство, следует использовать резервный канал аутентификации, такой как ручное установление отпечатка или короткая строка аутентификации.

Appendix A. Requirements Analysis
Приложение A. Анализ требований
[RFC5479] describes security requirements for media keying. This section evaluates this proposal with respect to each requirement.
[RFC5479] описывает требования безопасности для ключей медиа. В этом разделе предложение оценивается на соответствие каждому требованию.
A.1. Forking and Retargeting (R-FORK-RETARGET, R-BEST-SECURE, R-DISTINCT)
A.1. Разветвление и переадресация (R-FORK-RETARGET, R-BEST-SECURE, R-DISTINCT)
In this document, the SDP offer (in the INVITE) is simply an advertisement of the capability to do security. This advertisement does not depend on the identity of the communicating peer, so forking and retargeting work when all the endpoints will do SRTP. When a mix of SRTP and non-SRTP endpoints are present, we use the SDP capabilities mechanism currently being defined [MMUSIC-SDP] to transparently negotiate security where possible. Because DTLS establishes a new key for each session, only the entity with which the call is finally established gets the media encryption keys (R3).
В настоящем документе предложение SDP (в INVITE) — это просто объявление возможности обеспечить безопасность. Это объявление не зависит от идентичности взаимодействующего участника, поэтому разветвление и переадресация работают, когда все конечные точки будут использовать SRTP. Когда присутствует смесь конечных точек SRTP и не-SRTP, мы используем механизм возможностей SDP, который в настоящее время определяется [MMUSIC-SDP], чтобы по возможности прозрачно согласовать безопасность. Поскольку DTLS устанавливает новый ключ для каждой сессии, только та сущность, с которой вызов в конечном итоге установлен, получает ключи шифрования медиа (R3).
A.2. Distinct Cryptographic Contexts (R-DISTINCT)
A.2. Различные криптографические контексты (R-DISTINCT)
DTLS performs a new DTLS handshake with each endpoint, which establishes distinct keys and cryptographic contexts for each endpoint.
DTLS выполняет новое рукопожатие DTLS с каждой конечной точкой, что устанавливает различные ключи и криптографические контексты для каждой конечной точки.
A.3. Reusage of a Security Context (R-REUSE)
A.3. Повторное использование сеанса защиты (R-REUSE)
DTLS allows sessions to be resumed with the 'TLS session resumption' functionality. This feature can be used to lower the amount of cryptographic computation that needs to be done when two peers re-initiate the communication. See [RFC5764] for more on session resumption in this context.
DTLS позволяет возобновлять сессии с помощью функциональности «возобновление сессии TLS». Эта возможность может использоваться для снижения объёма криптографических вычислений, которые нужно выполнить, когда два участника повторно инициируют связь. Подробнее о возобновлении сессии в этом контексте см. [RFC5764].
A.4. Clipping (R-AVOID-CLIPPING)
A.4. Обрезка (R-AVOID-CLIPPING)
Because the key establishment occurs in the media plane, media need not be clipped before the receipt of the SDP answer. Note, however, that only confidentiality is provided until the offerer receives the answer: the answerer knows that they are not sending data to an attacker but the offerer cannot know that they are receiving data from the answerer.
Поскольку установление ключей происходит в плоскости медиа, медиа не нужно обрезать до получения ответа SDP. Отметим, однако, что до получения инициатором предложения ответа обеспечивается только конфиденциальность: ответчик знает, что не отправляет данные злоумышленнику, но инициатор предложения не может знать, что получает данные именно от ответчика.
A.5. Passive Attacks on the Media Path (R-PASS-MEDIA)
A.5. Пассивные атаки на путь медиа (R-PASS-MEDIA)
The public key algorithms used by DTLS cipher suites, such as RSA, Diffie-Hellman, and Elliptic Curve Diffie-Hellman, are secure against passive attacks.
Алгоритмы открытого ключа, используемые наборами шифров DTLS, такие как RSA, Диффи — Хеллман и Диффи — Хеллман на эллиптических кривых, устойчивы к пассивным атакам.
A.6. Passive Attacks on the Signaling Path (R-PASS-SIG)
A.6. Пассивные атаки на путь сигнализации (R-PASS-SIG)
DTLS provides protection against passive attacks by adversaries on the signaling path since only a fingerprint is exchanged using SIP signaling.
DTLS обеспечивает защиту от пассивных атак злоумышленников на пути сигнализации, поскольку с помощью сигнализации SIP передаётся только отпечаток.
A.7. (R-SIG-MEDIA, R-ACT-ACT)
A.7. (R-SIG-MEDIA, R-ACT-ACT)
An attacker who controls the media channel but not the signaling channel can perform a MITM attack on the DTLS handshake but this will change the certificates that will cause the fingerprint check to fail. Thus, any successful attack requires that the attacker modify the signaling messages to replace the fingerprints.
Злоумышленник, контролирующий канал медиа, но не канал сигнализации, может осуществить атаку MITM на рукопожатие DTLS, но это изменит сертификаты, что приведёт к сбою проверки отпечатка. Таким образом, любая успешная атака требует, чтобы злоумышленник изменил сообщения сигнализации, заменив отпечатки.
If RFC 4474 Identity or an equivalent mechanism is used, an attacker who controls the signaling channel at any point between the proxies performing the Identity signatures cannot modify the fingerprints without invalidating the signature. Thus, even an attacker who controls both signaling and media paths cannot successfully attack the media traffic. Note that the channel between the UA and the authentication service MUST be secured and the authentication service MUST verify the UA's identity in order for this mechanism to be secure.
Если используется идентичность RFC 4474 или эквивалентный механизм, злоумышленник, контролирующий канал сигнализации в любой точке между прокси-серверами, выполняющими подписи идентичности, не может изменить отпечатки, не аннулировав подпись. Таким образом, даже злоумышленник, контролирующий и путь сигнализации, и путь медиа, не может успешно атаковать медиатрафик. Отметим, что для безопасности этого механизма канал между UA и службой аутентификации ДОЛЖЕН быть защищён, а служба аутентификации ДОЛЖНА проверять идентичность UA.
Note that an attacker who controls the authentication service can impersonate the UA using that authentication service. This is an intended feature of SIP Identity -- the authentication service owns the namespace and therefore defines which user has which identity.
Отметим, что злоумышленник, контролирующий службу аутентификации, может выдать себя за UA, используя эту службу аутентификации. Это намеренная особенность идентичности SIP — служба аутентификации владеет пространством имён и, следовательно, определяет, какой пользователь имеет какую идентичность.
A.8. Binding to Identifiers (R-ID-BINDING)
A.8. Привязка к идентификаторам (R-ID-BINDING)
When an end-to-end mechanism such as SIP-Identity [RFC4474] and SIP- Connected-Identity [RFC4916] or S/MIME are used, they bind the endpoint's certificate fingerprints to the From: address in the signaling. The fingerprint is covered by the Identity signature. When other mechanisms (e.g., SIPS) are used, then the binding is correspondingly weaker.
Когда используется сквозной механизм, такой как SIP-Identity [RFC4474] и SIP-Connected-Identity [RFC4916] или S/MIME, он привязывает отпечатки сертификатов конечной точки к адресу From: в сигнализации. Отпечаток охватывается подписью Identity. Когда используются другие механизмы (например, SIPS), привязка соответственно слабее.
A.9. Perfect Forward Secrecy (R-PFS)
A.9. Совершенная прямая секретность (R-PFS)
DTLS supports Diffie-Hellman and Elliptic Curve Diffie-Hellman cipher suites that provide PFS.
DTLS поддерживает наборы шифров Диффи — Хеллмана и Диффи — Хеллмана на эллиптических кривых, обеспечивающие PFS.
A.10. Algorithm Negotiation (R-COMPUTE)
A.10. Согласование алгоритмов (R-COMPUTE)
DTLS negotiates cipher suites before performing significant cryptographic computation and therefore supports algorithm negotiation and multiple cipher suites without additional computational expense.
DTLS согласовывает наборы шифров до выполнения значительных криптографических вычислений и поэтому поддерживает согласование алгоритмов и несколько наборов шифров без дополнительных вычислительных затрат.
A.11. RTP Validity Check (R-RTP-VALID)
A.11. Проверка допустимости RTP (R-RTP-VALID)
DTLS packets do not pass the RTP validity check. The first byte of a DTLS packet is the content type and all current DTLS content types have the first two bits set to zero, resulting in a version of zero; thus, failing the first validity check. DTLS packets can also be distinguished from STUN packets. See [RFC5764] for details on demultiplexing.
Пакеты DTLS не проходят проверку допустимости RTP. Первый байт пакета DTLS — это тип содержимого, и все текущие типы содержимого DTLS имеют первые два бита, установленные в ноль, что даёт версию ноль; таким образом, первая проверка допустимости не проходит. Пакеты DTLS также можно отличить от пакетов STUN. Подробности демультиплексирования см. в [RFC5764].
A.12. Third-Party Certificates (R-CERTS, R-EXISTING)
A.12. Сертификаты третьих сторон (R-CERTS, R-EXISTING)
Third-party certificates are not required because signaling (e.g., [RFC4474]) is used to authenticate the certificates used by DTLS. However, if the parties share an authentication infrastructure that is compatible with TLS (third-party certificates or shared keys) it can be used.
Сертификаты третьих сторон не требуются, поскольку сигнализация (например, [RFC4474]) используется для аутентификации сертификатов, используемых DTLS. Однако если стороны разделяют инфраструктуру аутентификации, совместимую с TLS (сертификаты третьих сторон или общие ключи), её можно использовать.
A.13. FIPS 140-2 (R-FIPS)
A.13. FIPS 140-2 (R-FIPS)
TLS implementations already may be FIPS 140-2 approved and the algorithms used here are consistent with the approval of DTLS and DTLS-SRTP.
Реализации TLS уже могут быть одобрены по FIPS 140-2, а используемые здесь алгоритмы согласуются с одобрением DTLS и DTLS-SRTP.
A.14. Linkage between Keying Exchange and SIP Signaling (R-ASSOC)
A.14. Связь между обменом ключами и сигнализацией SIP (R-ASSOC)
The signaling exchange is linked to the key management exchange using the fingerprints carried in SIP and the certificates are exchanged in DTLS.
Обмен сигнализацией связан с обменом управления ключами с помощью отпечатков, передаваемых в SIP, а сертификаты обмениваются в DTLS.
A.15. Denial-of-Service Vulnerability (R-DOS)
A.15. Уязвимость к отказу в обслуживании (R-DOS)
DTLS offers some degree of Denial-of-Service (DoS) protection as a built-in feature (see Section 4.2.1 of [RFC4347]).
DTLS предлагает некоторую степень защиты от отказа в обслуживании (DoS) как встроенную функцию (см. раздел 4.2.1 [RFC4347]).
A.16. Crypto-Agility (R-AGILITY)
A.16. Криптографическая гибкость (R-AGILITY)
DTLS allows cipher suites to be negotiated and hence new algorithms can be incrementally deployed. Work on replacing the fixed MD5/SHA-1 key derivation function is ongoing.
DTLS позволяет согласовывать наборы шифров, и поэтому новые алгоритмы могут внедряться постепенно. Работа по замене фиксированной функции выработки ключей MD5/SHA-1 продолжается.
A.17. Downgrading Protection (R-DOWNGRADE)
A.17. Защита от понижения (R-DOWNGRADE)
DTLS provides protection against downgrading attacks since the selection of the offered cipher suites is confirmed in a later stage of the handshake. This protection is efficient unless an adversary is able to break a cipher suite in real-time. RFC 4474 is able to prevent an active attacker on the signaling path from downgrading the call from SRTP to RTP.
DTLS обеспечивает защиту от атак понижения, поскольку выбор предложенных наборов шифров подтверждается на более позднем этапе рукопожатия. Эта защита эффективна, если только злоумышленник не способен взломать набор шифров в реальном времени. RFC 4474 способен предотвратить понижение вызова с SRTP до RTP активным злоумышленником на пути сигнализации.
A.18. Media Security Negotiation (R-NEGOTIATE)
A.18. Согласование безопасности медиа (R-NEGOTIATE)
DTLS allows a User Agent to negotiate media security parameters for each individual session.
DTLS позволяет пользовательскому агенту согласовывать параметры безопасности медиа для каждой отдельной сессии.
A.19. Signaling Protocol Independence (R-OTHER-SIGNALING)
A.19. Независимость от протокола сигнализации (R-OTHER-SIGNALING)
The DTLS-SRTP framework does not rely on SIP; every protocol that is capable of exchanging a fingerprint and the media description can be secured.
Основы DTLS-SRTP не полагаются на SIP; любой протокол, способный обмениваться отпечатком и описанием медиа, может быть защищён.
A.20. Media Recording (R-RECORDING)
A.20. Запись медиа (R-RECORDING)
An extension, see [SIPPING-SRTP], has been specified to support media recording that does not require intermediaries to act as an MITM.
Было определено расширение, см. [SIPPING-SRTP], для поддержки записи медиа, не требующей, чтобы посредники действовали как MITM.
When media recording is done by intermediaries, then they need to act as an MITM.
Когда запись медиа выполняется посредниками, они должны действовать как MITM.
A.21. Interworking with Intermediaries (R-TRANSCODER)
A.21. Взаимодействие с посредниками (R-TRANSCODER)
In order to interface with any intermediary that transcodes the media, the transcoder must have access to the keying material and be treated as an endpoint for the purposes of this document.
Чтобы взаимодействовать с любым посредником, который транскодирует медиа, транскодер должен иметь доступ к ключевому материалу и рассматриваться как конечная точка для целей настоящего документа.
A.22. PSTN Gateway Termination (R-PSTN)
A.22. Завершение на шлюзе ТфОП (R-PSTN)
The DTLS-SRTP framework allows the media security to terminate at a PSTN gateway. This does not provide end-to-end security, but is consistent with the security goals of this framework because the gateway is authorized to speak for the PSTN namespace.
Основы DTLS-SRTP позволяют безопасности медиа завершаться на шлюзе ТфОП. Это не обеспечивает сквозной безопасности, но согласуется с целями безопасности этих основ, поскольку шлюз уполномочен выступать от имени пространства имён ТфОП.
A.23. R-ALLOW-RTP
A.23. R-ALLOW-RTP
DTLS-SRTP allows RTP media to be received by the calling party until SRTP has been negotiated with the answerer, after which SRTP is preferred over RTP.
DTLS-SRTP позволяет вызывающей стороне принимать медиа RTP до тех пор, пока с ответчиком не согласован SRTP, после чего SRTP предпочтительнее RTP.
A.24. R-HERFP
A.24. R-HERFP
The Heterogeneous Error Response Forking Problem (HERFP) is not applicable to DTLS-SRTP since the key exchange protocol will be executed along the media path and hence error messages are communicated along this path and proxies do not need to progress them.
Проблема разветвления при неоднородных ответах об ошибках (HERFP) неприменима к DTLS-SRTP, поскольку протокол обмена ключами будет выполняться вдоль медиапути и, следовательно, сообщения об ошибках передаются вдоль этого пути, а прокси-серверам не нужно их продвигать.
