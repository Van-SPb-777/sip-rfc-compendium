A General Mechanism for RTP Header Extensions
Общий механизм расширений заголовка RTP
Abstract
Аннотация
This document provides a general mechanism to use the header extension feature of RTP (the Real-time Transport Protocol). It provides the option to use a small number of small extensions in each RTP packet, where the universe of possible extensions is large and registration is decentralized. The actual extensions in use in a session are signaled in the setup information for that session. This document obsoletes RFC 5285.
В этом документе описывается общий механизм использования возможности расширения заголовка RTP (Real-time Transport Protocol — транспортного протокола реального времени). Он даёт возможность применять в каждом пакете RTP небольшое число небольших расширений, при том что множество возможных расширений велико, а регистрация децентрализована. Фактически используемые в сеансе расширения сигнализируются в информации о настройке этого сеанса. Настоящий документ делает RFC 5285 устаревшим.

1. Introduction
1. Введение
The RTP specification [RFC3550] provides a capability to extend the RTP header. Section 5.3.1 of [RFC3550] defines the header extension format and rules for its use. The existing header extension method permits at most one extension per RTP packet, identified by a 16-bit identifier and a 16-bit length field specifying the length of the header extension in 32-bit words.
Спецификация RTP [RFC3550] предоставляет возможность расширять заголовок RTP. В разделе 5.3.1 документа [RFC3550] определены формат расширения заголовка и правила его использования. Существующий метод расширения заголовка допускает не более одного расширения на пакет RTP, идентифицируемого 16-битным идентификатором и 16-битным полем длины, задающим длину расширения заголовка в 32-битных словах.
This mechanism has two conspicuous drawbacks. First, it permits only one header extension in a single RTP packet. Second, the specification gives no guidance as to how the 16-bit header extension identifiers are allocated to avoid collisions.
У этого механизма есть два заметных недостатка. Во-первых, он допускает только одно расширение заголовка в одном пакете RTP. Во-вторых, спецификация не даёт указаний о том, как распределяются 16-битные идентификаторы расширения заголовка во избежание коллизий.
This specification removes the first drawback by defining a backward- compatible and extensible means to carry multiple header extension elements in a single RTP packet. It removes the second drawback by defining that these extension elements are named by URIs, defining an IANA registry for extension elements defined in IETF specifications, and providing a Session Description Protocol (SDP) method for mapping between the naming URIs and the identifier values carried in the RTP packets.
Настоящая спецификация устраняет первый недостаток, определяя обратно совместимый и расширяемый способ переноса нескольких элементов расширения заголовка в одном пакете RTP. Она устраняет второй недостаток, определяя, что эти элементы расширения именуются с помощью URI, определяя реестр IANA для элементов расширения, определённых в спецификациях IETF, и предоставляя метод на основе протокола описания сеанса (SDP) для отображения между именующими URI и значениями идентификаторов, переносимыми в пакетах RTP.
This header extension applies to RTP/AVP (the Audio/Visual Profile) and its extensions.
Это расширение заголовка применяется к RTP/AVP (профилю аудио/видео) и его расширениям.
This document obsoletes [RFC5285] and removes a limitation from RFC 5285 that did not allow sending both one-byte and two-byte header extensions in the same RTP stream.
Настоящий документ делает [RFC5285] устаревшим и устраняет ограничение RFC 5285, не позволявшее передавать однобайтовые и двухбайтовые расширения заголовка в одном и том же потоке RTP.

3. Design Goals
3. Цели проектирования
The goal of this design is to provide a simple mechanism whereby multiple identified extensions can be used in RTP packets, without the need for formal registration of those extensions but nonetheless avoiding collisions.
Цель этого проекта — предоставить простой механизм, с помощью которого в пакетах RTP можно использовать несколько идентифицированных расширений, не нуждаясь в формальной регистрации этих расширений, но всё же избегая коллизий.
This mechanism provides an alternative to the practice of burying associated metadata into the media format bitstream. This has often been done in media data sent over fixed-bandwidth channels. Once this is done, a decoder for the specific media format needs to extract the metadata. Also, depending on the media format, the metadata can be added at the time of encoding the media so that the bit-rate used for the metadata is taken into account. But the metadata can be unknown at that time. Inserting metadata at a later time can cause a decode and re-encode to meet bit-rate requirements.
Этот механизм служит альтернативой практике «зарывания» связанных метаданных в битовый поток формата медиаданных. Так часто поступали с медиаданными, передаваемыми по каналам с фиксированной полосой пропускания. После этого декодеру конкретного формата медиаданных приходится извлекать метаданные. Кроме того, в зависимости от формата медиаданных метаданные можно добавить во время кодирования медиаданных, чтобы используемая для метаданных скорость передачи данных была учтена. Но в этот момент метаданные могут быть неизвестны. Вставка метаданных позднее может потребовать декодирования и повторного кодирования для соблюдения требований к скорости передачи данных.
In some cases, a more appropriate and higher-level mechanism may be available, and if so, it can be used. For cases where a higher-level mechanism is not available, it is better to provide a mechanism at the RTP level than to have the metadata be tied to a specific form of media data.
В некоторых случаях может быть доступен более подходящий механизм более высокого уровня, и, если это так, его можно использовать. В случаях, когда механизм более высокого уровня недоступен, лучше предусмотреть механизм на уровне RTP, чем привязывать метаданные к конкретной форме медиаданных.
4. Packet Design
4. Структура пакета
4.1. General
4.1. Общие положения
The following design is fit into the "header extension" of the RTP extension, as described above.
Описанная ниже структура вписывается в «расширение заголовка» расширения RTP, как описано выше.
The presence and format of this header extension and its contents are negotiated or defined out of band, such as through signaling (see below for SDP signaling). The 16-bit identifier for the two forms of the RTP extension defined here is only an architectural constant (e.g., for use by network analyzers); it is the negotiation/ definition (e.g., in SDP) that is the definitive indication that this header extension is present.
Наличие и формат этого расширения заголовка и его содержимое согласуются или определяются вне полосы, например посредством сигнализации (о сигнализации SDP см. ниже). 16-битный идентификатор для двух форм определяемого здесь расширения RTP — лишь архитектурная константа (например, для использования сетевыми анализаторами); именно согласование или определение (например, в SDP) служит окончательным указанием на то, что это расширение заголовка присутствует.
The RTP specification [RFC3550] states that RTP "is designed so that the header extension may be ignored by other interoperating implementations that have not been extended." The intent of this restriction is that RTP header extensions MUST NOT be used to extend RTP itself in a manner that is backward incompatible with non-extended implementations. For example, a header extension is not allowed to change the meaning or interpretation of the standard RTP header fields or of the RTP Control Protocol (RTCP). Header extensions MAY carry metadata in addition to the usual RTP header information, provided the RTP layer can function if that metadata is missing. For example, RTP header extensions can be used to carry data that's also sent in RTCP, as an optimization to lower latency, since they'll fall back to the original non-optimized behavior if the header extension is not present. The use of header extensions to convey information that will, if missing, disrupt the behavior of a higher-layer application that builds on top of RTP is only acceptable if this doesn't affect interoperability at the RTP layer. For example, applications that use the SDP BUNDLE extension with the Media Identification (MID) RTP header extension [SDP-BUNDLE] to correlate RTP streams with SDP "m=" lines likely won't work with full functionality if the MID is missing, but the operation of the RTP layer of those applications will be unaffected. Support for RTP header extensions based on this memo is negotiated using, for example, SDP Offer/Answer [RFC3264]; intermediaries aware of the RTP header extensions are advised to be cautious when removing or generating RTP header extensions. See Section 4.7 of [RFC7667].
В спецификации RTP [RFC3550] указано, что RTP «спроектирован так, чтобы расширение заголовка могло игнорироваться другими взаимодействующими реализациями, которые не были расширены». Смысл этого ограничения в том, что расширения заголовка RTP НЕ ДОЛЖНЫ использоваться для расширения самого RTP способом, обратно несовместимым с нерасширенными реализациями. Например, расширению заголовка не разрешается изменять смысл или интерпретацию стандартных полей заголовка RTP или протокола управления RTP (RTCP). Расширения заголовка МОГУТ переносить метаданные в дополнение к обычной информации заголовка RTP, при условии что уровень RTP может функционировать при отсутствии этих метаданных. Например, расширения заголовка RTP можно использовать для переноса данных, которые также передаются в RTCP, как оптимизацию для снижения задержки, поскольку при отсутствии расширения заголовка произойдёт возврат к исходному неоптимизированному поведению. Использование расширений заголовка для передачи информации, отсутствие которой нарушит работу приложения верхнего уровня, построенного поверх RTP, допустимо, только если это не влияет на взаимодействие на уровне RTP. Например, приложения, использующие расширение SDP BUNDLE с расширением заголовка RTP для идентификации медиа (MID) [SDP-BUNDLE] для соотнесения потоков RTP со строками "m=" SDP, вероятно, не будут работать в полном объёме при отсутствии MID, но работа уровня RTP этих приложений не пострадает. Поддержка расширений заголовка RTP на основе этого документа согласуется, например, с помощью модели предложение/ответ SDP [RFC3264]; посредникам, осведомлённым о расширениях заголовка RTP, рекомендуется проявлять осторожность при удалении или создании расширений заголовка RTP. См. раздел 4.7 документа [RFC7667].
The RTP header extension is formed as a sequence of extension elements, with possible padding. Each extension element has a local identifier and a length. The local identifiers MAY be mapped to a larger namespace in the negotiation (e.g., session signaling).
Расширение заголовка RTP образуется как последовательность элементов расширения с возможным заполнением. Каждый элемент расширения имеет локальный идентификатор и длину. Локальные идентификаторы МОГУТ отображаться в более широкое пространство имён при согласовании (например, при сигнализации сеанса).
4.1.1. Transmission Considerations
4.1.1. Соображения по передаче
As is good network practice, data should only be transmitted when needed. The RTP header extension SHOULD only be present in a packet if that packet also contains one or more extension elements, as defined here. An extension element SHOULD only be present in a packet when needed; the signaling setup of extension elements indicates only that those elements can be present in some packets, not that they are in fact present in all (or indeed, any) packets.
Как и положено в сетевой практике, данные следует передавать только тогда, когда это необходимо. Расширение заголовка RTP СЛЕДУЕТ включать в пакет, только если этот пакет также содержит один или несколько элементов расширения, как определено здесь. Элемент расширения СЛЕДУЕТ включать в пакет, только когда это необходимо; сигнализируемая настройка элементов расширения указывает лишь на то, что эти элементы могут присутствовать в некоторых пакетах, а не на то, что они фактически присутствуют во всех (или вообще в каких-либо) пакетах.
Some general considerations for getting the header extensions delivered to the receiver are as follows:
Ниже приведены некоторые общие соображения относительно доставки расширений заголовка получателю:
1. The probability for packet loss and burst loss determines how many repetitions of the header extensions will be required to reach a targeted delivery probability, and if burst loss is likely, what distribution would be needed to avoid losing all repetitions of the header extensions in a single burst.
1. Вероятность потери пакетов и потери сериями определяет, сколько повторений расширений заголовка потребуется для достижения целевой вероятности доставки, а если вероятна потеря сериями, — какое распределение нужно, чтобы не потерять все повторения расширений заголовка в одной серии.
2. If a set of packets are all needed to enable decoding, there is commonly no reason for including the header extension in all of these packets, as they share fate. Instead, at most one instance of the header extension per independently decodable set of media data would be a more efficient use of the bandwidth.
2. Если для обеспечения декодирования нужен весь набор пакетов, то обычно нет причин включать расширение заголовка во все эти пакеты, поскольку их судьба общая. Вместо этого более эффективным использованием полосы пропускания было бы не более одного экземпляра расширения заголовка на независимо декодируемый набор медиаданных.
3. How early the header extension item information is needed, from the first received RTP data or only after some set of packets are received, can guide whether the header extension(s) should be (1) in all of the first N packets or (2) included only once per set of packets -- for example, once per video frame.
3. То, насколько рано нужна информация из расширения заголовка — с первых полученных данных RTP или только после получения некоторого набора пакетов, — может подсказать, следует ли включать расширение (расширения) заголовка (1) во все первые N пакетов или (2) только один раз на набор пакетов, например один раз на видеокадр.
4. The use of RTP-level robustness mechanisms, such as RTP retransmission [RFC4588] or Forward Error Correction (e.g., [RFC5109]) may treat packets differently from a robustness perspective, and header extensions should be added to packets that get a treatment corresponding to the relative importance of receiving the information.
4. Использование механизмов устойчивости уровня RTP, таких как повторная передача RTP [RFC4588] или прямая коррекция ошибок (например, [RFC5109]), может по-разному обрабатывать пакеты с точки зрения устойчивости, и расширения заголовка следует добавлять в те пакеты, которые получают обработку, соответствующую относительной важности получения информации.
As a summary, the number of header extension transmissions should be tailored to a desired probability of delivery, taking the receiver population size into account. For the very basic case, N repetitions of the header extensions should be sufficient but may not be optimal. N is selected so that the header extension target delivery probability reaches 1-P^N, where P is the probability of packet loss. For point-to-point or small receiver populations, it might also be possible to use feedback, such as RTCP, to determine when the information in the header extensions has reached all receivers and stop further repetitions. Feedback that can be used includes the RTCP Extended Report (XR) Loss RLE Report Block [RFC3611], which will indicate successful delivery of particular packets. If the RTP/AVPF transport-layer feedback messages for generic NACK [RFC4585] are used, they can indicate failure to deliver an RTP packet with the header extension, thus indicating the need for further repetitions. The normal RTCP report blocks can also provide an indicator of successful delivery, if no losses are indicated for a reporting interval covering the RTP packets with the header extension. Note that loss of an RTCP packet reporting on an interval where RTP header extension packets were sent does not necessarily mean that the RTP header extension packets themselves were lost.
В итоге, число передач расширения заголовка следует соразмерять с желаемой вероятностью доставки, принимая во внимание размер совокупности получателей. В самом простом случае N повторений расширений заголовка должно быть достаточно, но это может быть не оптимально. N выбирается так, чтобы целевая вероятность доставки расширения заголовка достигала 1-P^N, где P — вероятность потери пакета. Для соединений «точка-точка» или небольших совокупностей получателей можно также использовать обратную связь, например RTCP, чтобы определить, когда информация из расширений заголовка достигла всех получателей, и прекратить дальнейшие повторения. В качестве обратной связи можно использовать блок отчёта RLE о потерях из расширенных отчётов RTCP (XR) [RFC3611], который укажет на успешную доставку конкретных пакетов. Если используются сообщения обратной связи транспортного уровня RTP/AVPF для общего NACK [RFC4585], они могут указывать на неудачную доставку пакета RTP с расширением заголовка, тем самым указывая на необходимость дальнейших повторений. Обычные блоки отчётов RTCP также могут служить индикатором успешной доставки, если за интервал отчётности, охватывающий пакеты RTP с расширением заголовка, потери не указаны. Обратите внимание, что потеря пакета RTCP с отчётом за интервал, в котором передавались пакеты с расширением заголовка RTP, не обязательно означает, что сами пакеты с расширением заголовка RTP были потеряны.
4.1.2. Header Extension Type Considerations
4.1.2. Соображения о типах расширений заголовка
Each extension element in a packet has a local identifier (ID) and a length. The local identifiers present in the stream MUST have been negotiated or defined out of band. There are no static allocations of local identifiers. Each distinct extension MUST have a unique ID. The ID value 0 is reserved for padding and MUST NOT be used as a local identifier.
Каждый элемент расширения в пакете имеет локальный идентификатор (ID) и длину. Локальные идентификаторы, присутствующие в потоке, ДОЛЖНЫ быть согласованы или определены вне полосы. Статического распределения локальных идентификаторов не существует. Каждое отдельное расширение ДОЛЖНО иметь уникальный ID. Значение ID 0 зарезервировано для заполнения и НЕ ДОЛЖНО использоваться в качестве локального идентификатора.
An extension element with an ID value equal to 0 MUST NOT have an associated length field greater than 0. If such an extension element is encountered, its length field MUST be ignored, processing of the entire extension MUST terminate at that point, and only the extension elements present prior to the element with ID 0 and a length field greater than 0 SHOULD be considered.
Элемент расширения со значением ID, равным нулю, НЕ ДОЛЖЕН иметь связанное поле длины больше нуля. Если такой элемент расширения встречается, его поле длины ДОЛЖНО игнорироваться, обработка всего расширения ДОЛЖНА прекращаться в этот момент, и СЛЕДУЕТ учитывать только элементы расширения, присутствующие до элемента с ID 0 и полем длины больше нуля.
There are two variants of the extension: one-byte and two-byte headers. Since it is expected that (a) the number of extensions in any given RTP session is small and (b) the extensions themselves are small, the one-byte header form is preferred and MUST be supported by all receivers. A stream MUST contain only one-byte headers or only two-byte headers unless it is known that all recipients support mixing, by either SDP Offer/Answer [RFC3264] negotiation (see Section 6) or out-of-band knowledge. Each RTP packet with an RTP header extension following this specification will indicate whether it contains one-byte or two-byte header extensions through the use of the "defined by profile" field. Extension element types that do not match the header extension format, i.e., one-byte or two-byte, MUST NOT be used in that RTP packet. Transmitters SHOULD NOT use the two-byte header form when all extensions are small enough for the one-byte header form. Transmitters that intend to send the two-byte form SHOULD negotiate the use of IDs above 14 if they want to let the receivers know that they intend to use the two-byte form -- for example, if the RTP header extension is longer than 16 bytes. A transmitter may be aware that an intermediary may add RTP header extensions; in this case, the transmitter SHOULD use the two-byte form.
Существует два варианта расширения: однобайтовые и двухбайтовые заголовки. Поскольку предполагается, что (a) число расширений в любом данном сеансе RTP невелико и (b) сами расширения невелики, однобайтовая форма заголовка является предпочтительной и ДОЛЖНА поддерживаться всеми получателями. Поток ДОЛЖЕН содержать только однобайтовые заголовки или только двухбайтовые заголовки, если только не известно, что все получатели поддерживают смешивание — посредством согласования по модели предложение/ответ SDP [RFC3264] (см. раздел 6) или на основе внеполосных сведений. Каждый пакет RTP с расширением заголовка RTP в соответствии с настоящей спецификацией будет указывать, содержит ли он однобайтовые или двухбайтовые расширения заголовка, с помощью поля "defined by profile". Типы элементов расширения, не соответствующие формату расширения заголовка, то есть однобайтовому или двухбайтовому, НЕ ДОЛЖНЫ использоваться в этом пакете RTP. Передатчикам НЕ СЛЕДУЕТ использовать двухбайтовую форму заголовка, когда все расширения достаточно малы для однобайтовой формы заголовка. Передатчикам, которые намереваются передавать двухбайтовую форму, СЛЕДУЕТ согласовать использование идентификаторов выше 14, если они хотят дать получателям понять, что намереваются использовать двухбайтовую форму, — например, если расширение заголовка RTP длиннее 16 байтов. Передатчик может знать, что посредник может добавлять расширения заголовка RTP; в этом случае передатчику СЛЕДУЕТ использовать двухбайтовую форму.
A sequence of extension elements, possibly with padding, forms the header extension defined in the RTP specification. There are as many extension elements as will fit in the RTP header extension, as indicated by the RTP header extension length. Since this length is signaled in full 32-bit words, padding bytes are used to pad to a 32-bit boundary. The entire extension is parsed byte by byte to find each extension element (no alignment is needed), and parsing stops (1) at the end of the entire header extension or (2) in the "one-byte headers only" case, on encountering an identifier with the reserved value of 15 -- whichever happens earlier.
Последовательность элементов расширения, возможно с заполнением, образует расширение заголовка, определённое в спецификации RTP. Элементов расширения помещается столько, сколько умещается в расширении заголовка RTP, как указано длиной расширения заголовка RTP. Поскольку эта длина сигнализируется в целых 32-битных словах, для дополнения до границы 32 битов используются байты заполнения. Всё расширение анализируется побайтово для нахождения каждого элемента расширения (выравнивание не требуется), и анализ прекращается (1) в конце всего расширения заголовка или (2) в случае «только однобайтовые заголовки» при встрече идентификатора с зарезервированным значением 15 — в зависимости от того, что наступит раньше.
In both forms, padding bytes have the value of 0 (zero). They MAY be placed between extension elements, if desired for alignment, or after the last extension element, if needed for padding. A padding byte does not supply the ID of an element, nor does it supply the length field. When a padding byte is found, it is ignored, and the parser moves on to interpreting the next byte.
В обеих формах байты заполнения имеют значение 0 (ноль). Их МОЖНО размещать между элементами расширения, если это желательно для выравнивания, или после последнего элемента расширения, если это нужно для заполнения. Байт заполнения не задаёт ID элемента и не задаёт поле длины. Когда встречается байт заполнения, он игнорируется, и анализатор переходит к интерпретации следующего байта.
Note carefully that the one-byte header form allows for data lengths between 1 and 16 bytes, by adding 1 to the signaled length value (thus, 0 in the length field indicates that one byte of data follows). This allows for the important case of 16-byte payloads. This addition is not performed for the two-byte headers, where the length field signals data lengths between 0 and 255 bytes.
Обратите внимание, что однобайтовая форма заголовка допускает длины данных от 1 до 16 байтов за счёт прибавления 1 к сигнализируемому значению длины (так, 0 в поле длины означает, что далее следует один байт данных). Это позволяет охватить важный случай 16-байтовых полезных нагрузок. Для двухбайтовых заголовков такое прибавление не выполняется: там поле длины сигнализирует длины данных от 0 до 255 байтов.
Use of RTP header extensions will reduce the efficiency of RTP header compression, since the header extension will be sent uncompressed unless the RTP header compression module is updated to recognize the extension header. If header extensions are present in some packets but not in others, this can also reduce compression efficiency by requiring an update to the fixed header to be conveyed when header extensions start or stop being sent. The interactions of the RTP header extension and header compression are explored further in [RFC2508] and [RFC3095].
Использование расширений заголовка RTP снижает эффективность сжатия заголовка RTP, поскольку расширение заголовка будет передаваться несжатым, если модуль сжатия заголовка RTP не обновлён для распознавания заголовка расширения. Если расширения заголовка присутствуют в одних пакетах и отсутствуют в других, это также может снижать эффективность сжатия, требуя передачи обновления фиксированного заголовка при начале или прекращении отправки расширений заголовка. Взаимодействие расширения заголовка RTP и сжатия заголовка подробнее рассматривается в [RFC2508] и [RFC3095].
4.2. One-Byte Header
4.2. Однобайтовый заголовок
In the one-byte header form of extensions, the 16-bit value required by the RTP specification for a header extension, labeled in the RTP specification as "defined by profile", MUST have the fixed bit pattern 0xBEDE (the pattern was picked for the trivial reason that the first version of this specification was written on May 25th -- the feast day of the Venerable Bede).
В однобайтовой форме расширений 16-битное значение, требуемое спецификацией RTP для расширения заголовка и обозначенное в спецификации RTP как "defined by profile", ДОЛЖНО иметь фиксированный битовый шаблон 0xBEDE (шаблон выбран по тривиальной причине: первая версия этой спецификации была написана 25 мая — в день памяти преподобного Беды).
Each extension element MUST start with a byte containing an ID and a length:
Каждый элемент расширения ДОЛЖЕН начинаться с байта, содержащего ID и длину:
0 0 1 2 3 4 5 6 7 +-+-+-+-+-+-+-+-+ | ID | len | +-+-+-+-+-+-+-+-+
0 0 1 2 3 4 5 6 7 +-+-+-+-+-+-+-+-+ | ID | len | +-+-+-+-+-+-+-+-+
The 4-bit ID is the local identifier of this element in the range 1-14 inclusive. In the signaling section, this is referred to as the valid range.
4-битный ID — это локальный идентификатор данного элемента в диапазоне от 1 до 14 включительно. В разделе о сигнализации он называется допустимым диапазоном.
The local identifier value 15 is reserved for a future extension and MUST NOT be used as an identifier. If the ID value 15 is encountered, its length field MUST be ignored, processing of the entire extension MUST terminate at that point, and only the extension elements present prior to the element with ID 15 SHOULD be considered.
Значение локального идентификатора 15 зарезервировано для будущего расширения и НЕ ДОЛЖНО использоваться в качестве идентификатора. Если встречается значение ID 15, его поле длины ДОЛЖНО игнорироваться, обработка всего расширения ДОЛЖНА прекращаться в этот момент, и СЛЕДУЕТ учитывать только элементы расширения, присутствующие до элемента с ID 15.
The 4-bit length is the number, minus one, of data bytes of this header extension element following the one-byte header. Therefore, the value zero (0) in this field indicates that one byte of data follows, and a value of 15 (the maximum) indicates element data of 16 bytes. (This permits carriage of 16-byte values, which is a common length of labels and identifiers, while losing the possibility of zero-length values, which would often be padded anyway.) Поэтому значение ноль (0) в этом поле означает, что далее следует один байт данных, а значение 15 (максимальное) указывает на данные элемента размером 16 байтов. The appbits field is 4 bits that are application dependent and MAY be defined to be any value or meaning; this topic is outside the scope of this specification. For the purposes of signaling, this field is treated as a special extension value assigned to the local identifier 256. Поле appbits — это 4 бита, зависящие от приложения, которым МОЖНО придать любое значение или смысл; эта тема выходит за рамки настоящей спецификации. This means that the lower values (1-14) can be used in the 4-bit ID field in the one-byte header format with the same meanings.

5. SDP Signaling Design
5. Схема сигнализации SDP
The indication of the presence of this extension, and the mapping of local identifiers used in the header extension to a larger namespace, MUST be performed out of band -- for example, as part of an SDP Offer/Answer [RFC3264]. This section defines such signaling in SDP.
Указание на наличие этого расширения и отображение локальных идентификаторов, используемых в расширении заголовка, в более широкое пространство имён ДОЛЖНЫ выполняться вне полосы, например в рамках модели предложение/ответ SDP [RFC3264]. В этом разделе такая сигнализация определяется для SDP.
A usable mapping MUST use IDs in the valid range, and each ID in this range MUST be used only once for each media section (or only once if the mappings are session level). Mappings that do not conform to these rules MAY be presented, for instance, during SDP Offer/Answer [RFC3264] negotiation as described in the next section, but remapping to conformant values is necessary before they can be applied.
Пригодное для использования отображение ДОЛЖНО использовать ID из допустимого диапазона, и каждый ID из этого диапазона ДОЛЖЕН использоваться только один раз для каждого раздела медиа (или только один раз, если отображения заданы на уровне сеанса). Отображения, не соответствующие этим правилам, МОГУТ быть предложены, например, при согласовании по модели предложение/ответ SDP [RFC3264], как описано в следующем разделе, но перед их применением необходимо переназначить их в соответствующие значения.
Each extension is named by a URI. That URI MUST be absolute; it precisely identifies the format and meaning of the extension. URIs that contain a domain name SHOULD also contain a month-date in the form mmyyyy. The definition of the element and assignment of the URI MUST have been authorized by the owner of the domain name on or very close to that date. (This avoids problems when domain names change ownership.) If the resource or document defines several extensions, then the URI MUST identify the actual extension in use, e.g., using a fragment or query identifier (characters after a "#" or "?" in the URI).
Каждое расширение именуется с помощью URI. Этот URI ДОЛЖЕН быть абсолютным; он точно определяет формат и смысл расширения. URI, содержащие имя домена, СЛЕДУЕТ также содержать дату в формате mmyyyy. Определение элемента и назначение URI ДОЛЖНЫ быть авторизованы владельцем доменного имени на эту дату или совсем незадолго до неё. (Это позволяет избежать проблем при смене владельца доменного имени.) Если ресурс или документ определяет несколько расширений, то URI ДОЛЖЕН идентифицировать фактически используемое расширение, например с помощью фрагмента или идентификатора запроса (символов после "#" или "?" в URI).
Rationale: The use of URIs provides for a large, unallocated space and gives documentation on the extension. The URIs do not have to be dereferencable, in order to permit confidential or experimental use, or to cover the case when extensions continue to be used after the organization that defined them ceases to exist.
Обоснование: использование URI обеспечивает большое нераспределённое пространство и даёт документацию по расширению. URI не обязаны допускать разыменование, чтобы позволить конфиденциальное или экспериментальное использование или охватить случай, когда расширения продолжают использоваться после прекращения существования организации, которая их определила.
An extension URI with the same attributes MUST NOT appear more than once applying to the same stream, i.e., at session level or in the declarations for a single stream at media level. (The same extension can, of course, be used for several streams and can appear with different <extensionattributes> for the same stream.)
URI расширения с одинаковыми атрибутами НЕ ДОЛЖЕН встречаться более одного раза применительно к одному и тому же потоку, то есть на уровне сеанса или в объявлениях для одного потока на уровне медиа. (Одно и то же расширение, разумеется, может использоваться для нескольких потоков и может встречаться с разными <extensionattributes> для одного потока.)
For extensions defined in RFCs, the URI used SHOULD be a URN starting with "urn:ietf:params:rtp-hdrext:" followed by a registered, descriptive name.
Для расширений, определённых в RFC, используемый URI СЛЕДУЕТ задавать как URN, начинающийся с "urn:ietf:params:rtp-hdrext:" и далее содержащий зарегистрированное описательное имя.
The registration requirements are detailed in Section 10 ("IANA Considerations").
Требования к регистрации подробно описаны в разделе 10 («Вопросы IANA»).

6. SDP Signaling for Support of Mixed One-Byte and Two-Byte Header Extensions
6. Сигнализация SDP для поддержки смешанных однобайтовых и двухбайтовых расширений заголовка
In order to allow for backward interoperability with systems that do not support the mixing of one-byte and two-byte header extensions, this document defines the "a=extmap-allow-mixed" Session Description Protocol (SDP) [RFC4566] attribute to indicate if the participant is capable of supporting this new mode. The attribute takes no value. This attribute can be used at the session level or the media level. A participant that proposes the use of this mode SHALL itself support the reception of mixed one-byte and two-byte header extensions.
Чтобы обеспечить обратную совместимость с системами, не поддерживающими смешивание однобайтовых и двухбайтовых расширений заголовка, в этом документе определяется атрибут "a=extmap-allow-mixed" протокола описания сеанса (SDP) [RFC4566], указывающий, способен ли участник поддерживать этот новый режим. Атрибут не принимает значения. Этот атрибут можно использовать на уровне сеанса или на уровне медиа. Участник, предлагающий использование этого режима, ДОЛЖЕН сам поддерживать приём смешанных однобайтовых и двухбайтовых расширений заголовка.
If SDP Offer/Answer [RFC3264] is supported and used, the negotiation for mixed one-byte and two-byte extensions MUST be negotiated using SDP Offer/Answer per [RFC3264]. In the absence of negotiations using SDP Offer/Answer -- for example, when declarative SDP is used -- mixed headers MUST NOT occur unless the transmitter has some (out-of-band) knowledge that all potential recipients support this mode.
Если модель предложение/ответ SDP [RFC3264] поддерживается и используется, согласование смешанных однобайтовых и двухбайтовых расширений ДОЛЖНО проводиться с помощью модели предложение/ответ SDP согласно [RFC3264]. При отсутствии согласования с помощью модели предложение/ответ SDP — например, когда используется декларативный SDP, — смешанные заголовки НЕ ДОЛЖНЫ встречаться, если только передатчик не располагает некоторыми (внеполосными) сведениями о том, что все потенциальные получатели поддерживают этот режим.
The formal definition of this attribute is:
Формальное определение этого атрибута таково:
Name: extmap-allow-mixed Value: None Usage Level: session, media Charset Dependent: No Example: a=extmap-allow-mixed
Name: extmap-allow-mixed Value: None Usage Level: session, media Charset Dependent: No Example: a=extmap-allow-mixed
When doing SDP Offer/Answer [RFC3264], an offering client that wishes to use both one-byte and two-byte extensions MUST include the attribute "a=extmap-allow-mixed" in the SDP offer. If "a=extmap-allow-mixed" is present in the SDP offer, the answerer that supports this mode and wishes to use it SHALL include the "a=extmap-allow-mixed" attribute in the answer. In the cases where the attribute has been excluded, both clients SHALL NOT use mixed one-byte and two-byte extensions in the same RTP stream but MAY use the one-byte or two-byte form exclusively (see Section 4.1.2).
При использовании модели предложение/ответ SDP [RFC3264] клиент, предлагающий сеанс, который желает применять и однобайтовые, и двухбайтовые расширения, ДОЛЖЕН включить атрибут "a=extmap-allow-mixed" в предложение SDP. Если "a=extmap-allow-mixed" присутствует в предложении SDP, отвечающая сторона, поддерживающая этот режим и желающая его использовать, ДОЛЖНА включить атрибут "a=extmap-allow-mixed" в ответ. В случаях, когда атрибут исключён, оба клиента НЕ ДОЛЖНЫ использовать смешанные однобайтовые и двухбайтовые расширения в одном потоке RTP, но МОГУТ использовать исключительно однобайтовую или двухбайтовую форму (см. раздел 4.1.2).
When used per [SDP-BUNDLE], this attribute is specified as the IDENTICAL category [SDP-MUX].
При использовании согласно [SDP-BUNDLE] этот атрибут отнесён к категории IDENTICAL [SDP-MUX].
7. SDP Offer/Answer
7. Предложение/ответ SDP
The simple signaling described above for the "extmap" attribute MAY be enhanced in an SDP Offer/Answer [RFC3264] context, to permit:
Описанную выше простую сигнализацию для атрибута "extmap" МОЖНО расширить в контексте модели предложение/ответ SDP [RFC3264], чтобы допустить:
o asymmetric behavior (extensions sent in only one direction),
o асимметричное поведение (расширения, передаваемые только в одном направлении),
o the offer of mutually exclusive alternatives, or
o предложение взаимоисключающих альтернатив или
o the offer of more extensions than can be sent in a single session.
o предложение большего числа расширений, чем можно передать в одном сеансе.
A direction attribute MAY be included in an "extmap"; without it, the direction implicitly inherits, of course, from the stream direction or is "sendrecv" for session-level attributes or extensions of "inactive" streams. The direction MUST be one of "sendonly", "recvonly", "sendrecv", or "inactive" as specified in [RFC3264]. Extensions, with their directions, MAY be signaled for an "inactive" stream. It is an error to use an extension direction incompatible with the stream direction (e.g., a "sendonly" attribute for a "recvonly" stream).
Атрибут направления МОЖНО включать в "extmap"; без него направление, разумеется, неявно наследуется от направления потока либо принимается равным "sendrecv" для атрибутов уровня сеанса или расширений «неактивных» потоков. Направление ДОЛЖНО быть одним из значений "sendonly", "recvonly", "sendrecv" или "inactive", как указано в [RFC3264]. Для «неактивного» потока МОЖНО сигнализировать расширения вместе с их направлениями. Использование направления расширения, несовместимого с направлением потока (например, атрибута "sendonly" для потока "recvonly"), является ошибкой.
If an offer or answer contains session-level mappings (and hence no media-level mappings) and different behavior is desired for each stream, then the entire set of extension map declarations MAY be moved into the media-level section(s) of the SDP. (Note that this specification does not permit mixing global and local declarations, to make identifier management easier.)
Если предложение или ответ содержит отображения уровня сеанса (и, следовательно, не содержит отображений уровня медиа), а для каждого потока желательно различное поведение, то весь набор объявлений карты расширений МОЖНО перенести в раздел (разделы) уровня медиа SDP. (Отметим, что настоящая спецификация не допускает смешивания глобальных и локальных объявлений, чтобы упростить управление идентификаторами.)
If an extension map is offered as "sendrecv", explicitly or implicitly, and asymmetric behavior is desired, the SDP answer MAY be changed to modify or add direction qualifiers for that extension.
Если карта расширений предложена как "sendrecv" явно или неявно, а желательно асимметричное поведение, ответ SDP МОЖНО изменить, чтобы поменять или добавить уточнители направления для этого расширения.
If an extension is marked as "sendonly" and the answerer desires to receive it, the extension MUST be marked as "recvonly" in the SDP answer. An answerer that has no desire to receive the extension or does not understand the extension SHOULD remove it from the SDP answer. An answerer MAY want to respond that he supports the extension and does not want to receive it at the moment, but he may indicate a desire to receive it in a future offer and will mark the extension as "inactive".
Если расширение помечено как "sendonly", а отвечающая сторона желает его принимать, расширение ДОЛЖНО быть помечено как "recvonly" в ответе SDP. Отвечающая сторона, которая не желает принимать расширение или не понимает его, СЛЕДУЕТ удалить его из ответа SDP. Отвечающая сторона МОЖЕТ пожелать ответить, что она поддерживает расширение и не хочет принимать его в данный момент, но может указать на желание принимать его в будущем предложении и пометит расширение как "inactive".
If an extension is marked as "recvonly" and the answerer desires to send it, the extension MUST be marked as "sendonly" in the SDP answer. An answerer that has no desire to, or is unable to, send the extension SHOULD remove it from the SDP answer. An answerer MAY want to respond that he supports this extension but has no intention of sending it now; he may indicate a desire to send it in a future offer by marking the extension as "inactive".
Если расширение помечено как "recvonly", а отвечающая сторона желает его передавать, расширение ДОЛЖНО быть помечено как "sendonly" в ответе SDP. Отвечающая сторона, которая не желает или не может передавать расширение, СЛЕДУЕТ удалить его из ответа SDP. Отвечающая сторона МОЖЕТ пожелать ответить, что она поддерживает это расширение, но не намерена передавать его сейчас; она может указать на желание передавать его в будущем предложении, пометив расширение как "inactive".
Local identifiers in the valid range inclusive in an offer or answer must not be used more than once per media section (including the session-level section). The local identifiers MUST be unique in an RTP session, and the same identifier MUST be used for the same offered extension in the answer. A session update MAY change the direction qualifiers of extensions being used. A session update MAY add or remove extension(s). Identifier values in the valid range MUST NOT be altered (remapped).
Локальные идентификаторы из допустимого диапазона включительно в предложении или ответе не должны использоваться более одного раза на раздел медиа (включая раздел уровня сеанса). Локальные идентификаторы ДОЛЖНЫ быть уникальными в сеансе RTP, и в ответе ДОЛЖЕН использоваться тот же идентификатор для того же предложенного расширения. Обновление сеанса МОЖЕТ изменить уточнители направления используемых расширений. Обновление сеанса МОЖЕТ добавлять или удалять расширения. Значения идентификаторов из допустимого диапазона НЕ ДОЛЖНЫ изменяться (переназначаться).
Note that, under this rule, the same local identifier cannot be used for two extensions for the same media, even when one is "sendonly" and the other "recvonly", as it would then be impossible to make either of them "sendrecv" (since renumbering is not permitted either). If a party wishes to offer mutually exclusive alternatives, then multiple extensions with the same identifier in the extended range 4096-4351 MAY be offered. The answerer SHOULD select, at most, one of the offered extensions with the same identifier and remap it to a free identifier in the valid range for that extension to be usable.
Отметим, что согласно этому правилу один и тот же локальный идентификатор нельзя использовать для двух расширений в одних и тех же медиаданных, даже если одно из них "sendonly", а другое "recvonly", поскольку тогда ни одно из них нельзя будет сделать "sendrecv" (перенумерация тоже не разрешена). Если сторона желает предложить взаимоисключающие альтернативы, МОЖНО предложить несколько расширений с одним и тем же идентификатором из расширенного диапазона 4096-4351. Отвечающей стороне СЛЕДУЕТ выбрать не более одного из предложенных расширений с одинаковым идентификатором и переназначить его на свободный идентификатор из допустимого диапазона, чтобы это расширение можно было использовать.
Similarly, if more extensions are offered than can be fit in the valid range, identifiers in the range 4096-4351 MAY be offered; the answerer SHOULD choose those that are desired and remap them to a free identifier in the valid range.
Аналогично, если предложено больше расширений, чем помещается в допустимый диапазон, МОЖНО предложить идентификаторы из диапазона 4096-4351; отвечающей стороне СЛЕДУЕТ выбрать нужные и переназначить их на свободные идентификаторы из допустимого диапазона.
An answerer may copy an "extmap" for an identifier in the extended range into the answer to indicate to the offerer that it supports that extension. Of course, such an extension cannot be used, since there is no way to specify it in an extension header. If needed, the offerer or answerer can update the session to assign a valid identifier to that extension URI.
Отвечающая сторона может скопировать "extmap" для идентификатора из расширенного диапазона в ответ, чтобы показать предлагающей стороне, что она поддерживает это расширение. Разумеется, такое расширение нельзя использовать, поскольку нет способа указать его в заголовке расширения. При необходимости предлагающая или отвечающая сторона может обновить сеанс, назначив этому URI расширения допустимый идентификатор.
Rationale: The range 4096-4351 for these negotiation identifiers is deliberately restricted to allow expansion of the range of valid identifiers in the future.
Обоснование: диапазон 4096-4351 для этих идентификаторов согласования намеренно ограничен, чтобы в будущем можно было расширить диапазон допустимых идентификаторов.
Either party MAY include extensions in the stream other than those negotiated, or those negotiated as "inactive" (for example, for the benefit of intermediate nodes). Only extensions that appeared with an identifier in the valid range in SDP originated by the sender can be sent.
Любая из сторон МОЖЕТ включать в поток расширения помимо согласованных или согласованных как "inactive" (например, для пользы промежуточных узлов). Передавать можно только те расширения, которые появились с идентификатором из допустимого диапазона в SDP, созданном передатчиком.

When using [SDP-BUNDLE] to bundle multiple "m=" lines, the "extmap" attribute falls under the SPECIAL category of [SDP-MUX]. All the "m=" lines in a BUNDLE group are considered to be part of the same local identifier (ID) space. If an RTP header extension, i.e., a particular extension URI and configuration using <extensionattributes>, is offered in multiple "m=" lines that are part of the same BUNDLE group, it MUST use the same ID in all of these "m=" lines. Each "m=" line in a BUNDLE group can include different RTP header extensions allowing, for example, audio and video sources to use different sets of RTP header extensions. A difference in configuration using any of the <extensionattributes> is important. Unless an RTP header extension explicitly states otherwise, any such difference SHALL be communicated to all receivers and SHALL cause assignment of different IDs. An RTP header extension that does not follow this rule MUST explicitly define what would constitute compatible configurations that can be sent with the same ID. The directionality of the RTP header extensions in each "m=" line of the BUNDLE group is handled in the same way as handling for non-bundled "m=" lines. This allows for specifying different directionality for each of the repeated extension URIs in a BUNDLE group.

Если расширение заголовка RTP, то есть конкретный URI расширения и конфигурация с использованием <extensionattributes>, предлагается в нескольких строках "m=", входящих в одну группу BUNDLE, оно ДОЛЖНО использовать один и тот же ID во всех этих строках "m=". Каждая строка "m=" в группе BUNDLE может включать различные расширения заголовка RTP, что позволяет, например, источникам аудио и видео использовать разные наборы расширений заголовка RTP. Различие в конфигурации с использованием любых <extensionattributes> является существенным. Если расширение заголовка RTP явно не указывает иное, любое такое различие ДОЛЖНО сообщаться всем получателям и ДОЛЖНО приводить к назначению разных ID. Расширение заголовка RTP, не следующее этому правилу, ДОЛЖНО явно определять, какие конфигурации считаются совместимыми и могут передаваться с одним и тем же ID. Направленность расширений заголовка RTP в каждой строке "m=" группы BUNDLE обрабатывается так же, как и для строк "m=", не входящих в BUNDLE. Это позволяет задавать разную направленность для каждого из повторяющихся URI расширений в группе BUNDLE.

9. Security Considerations
9. Вопросы безопасности
This document defines only a place to transmit information; the security implications of each of the extensions must be discussed with those extensions.
Настоящий документ определяет лишь место для передачи информации; последствия для безопасности каждого из расширений должны обсуждаться вместе с этими расширениями.
Extension usage is negotiated using [RFC3264], so integrity protection and end-to-end authentication MUST be implemented. The security considerations of [RFC3264] MUST be followed to prevent, for example, extension-usage blocking.
Использование расширений согласуется с помощью [RFC3264], поэтому ДОЛЖНЫ быть реализованы защита целостности и сквозная аутентификация. ДОЛЖНЫ соблюдаться соображения безопасности [RFC3264], чтобы предотвратить, например, блокирование использования расширений.
Header extensions have the same security coverage as the RTP header itself. When the Secure Real-time Transport Protocol (SRTP) [RFC3711] is used to protect RTP sessions, the RTP payload can be both encrypted and integrity protected, while the RTP header is either unprotected or integrity protected. In order to prevent DoS attacks (for example, by changing the header extension) integrity protection SHOULD be used. Lower-layer security protection such as Datagram Transport Layer Security (DTLS) [RFC6347] MAY be used. RTP header extensions can carry sensitive information for which participants in multimedia sessions want confidentiality. RFC 6904 [RFC6904] provides a mechanism that extends the mechanisms of SRTP to selectively encrypt RTP header extensions in SRTP.
Расширения заголовка имеют ту же защищённость, что и сам заголовок RTP. Когда для защиты сеансов RTP используется Secure Real-time Transport Protocol (SRTP) [RFC3711], полезная нагрузка RTP может быть как зашифрована, так и защищена от изменения, тогда как заголовок RTP либо не защищён, либо защищён от изменения. Чтобы предотвратить атаки типа DoS (например, путём изменения расширения заголовка), СЛЕДУЕТ использовать защиту целостности. МОЖНО использовать защиту на нижнем уровне, например Datagram Transport Layer Security (DTLS) [RFC6347]. Расширения заголовка RTP могут переносить конфиденциальную информацию, для которой участники мультимедийных сеансов желают обеспечить конфиденциальность. RFC 6904 [RFC6904] предоставляет механизм, расширяющий механизмы SRTP для выборочного шифрования расширений заголовка RTP в SRTP.
The RTP application designer needs to consider their security needs, that includes cipher strength for SRTP packets in general and what that means for the integrity and confidentiality of the RTP header extensions. As defined by RFC 6904 [RFC6904], the encryption stream cipher for the header extension is dependent on the chosen SRTP cipher.
Разработчику приложения RTP необходимо учитывать свои потребности в безопасности, включая стойкость шифра для пакетов SRTP в целом и то, что это означает для целостности и конфиденциальности расширений заголовка RTP. Как определено в RFC 6904 [RFC6904], поточный шифр для шифрования расширения заголовка зависит от выбранного шифра SRTP.
Other options for securing RTP are discussed in [RFC7201].
Другие варианты защиты RTP рассматриваются в [RFC7201].

11. Changes from RFC 5285
11. Изменения по сравнению с RFC 5285
The major motivation for updating [RFC5285] was to allow having one-byte and two-byte RTP header extensions in the same RTP stream (but not in the same RTP packet). The support for this case is negotiated using a new SDP attribute, "extmap-allow-mixed", specified in this document.
Основным мотивом обновления [RFC5285] было желание допустить наличие однобайтовых и двухбайтовых расширений заголовка RTP в одном и том же потоке RTP (но не в одном и том же пакете RTP). Поддержка этого случая согласуется с помощью нового атрибута SDP "extmap-allow-mixed", определённого в настоящем документе.
The other major change is to update the requirement from the RTP specifications [RFC3550] and [RFC5285] that the header extension "is designed so that the header extension may be ignored." This is described in Section 4.1.
Другое существенное изменение — уточнение требования спецификаций RTP [RFC3550] и [RFC5285] о том, что расширение заголовка «спроектировано так, чтобы расширение заголовка могло игнорироваться». Это описано в разделе 4.1.
More text was added to Section 4.1.1 ("Transmission Considerations") to clarify when and how many times to send the RTP header extension to provide a higher probability of delivery.
В раздел 4.1.1 («Соображения по передаче») добавлен текст, поясняющий, когда и сколько раз передавать расширение заголовка RTP, чтобы обеспечить более высокую вероятность доставки.
The Security Considerations section was expanded.
Раздел «Вопросы безопасности» был расширен.
The rest of the changes are editorial.
Остальные изменения носят редакционный характер.
