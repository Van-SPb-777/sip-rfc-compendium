Abstract
Аннотация
This document specifies the use of the Session Initiation Protocol (SIP), the Session Description Protocol (SDP), and the Real-time Transport Protocol (RTP) for delivering real-time media and metadata from a Communication Session (CS) to a recording device. The Session Recording Protocol specifies the use of SIP, SDP, and RTP to establish a Recording Session (RS) between the Session Recording Client (SRC), which is on the path of the CS, and a Session Recording Server (SRS) at the recording device. This document considers only active recording, where the SRC purposefully streams media to an SRS and all participating user agents (UAs) are notified of the recording. Passive recording, where a recording device detects media directly from the network (e.g., using port-mirroring techniques), is outside the scope of this document. In addition, lawful intercept is outside the scope of this document.
Настоящий документ определяет использование протокола инициирования сеансов (SIP), протокола описания сеансов (SDP) и протокола передачи данных в реальном времени (RTP) для доставки медиаданных и метаданных в реальном времени из сеанса связи (CS) на устройство записи. Протокол записи сеансов определяет использование SIP, SDP и RTP для установления сеанса записи (RS) между клиентом записи сеансов (SRC), который находится на пути CS, и сервером записи сеансов (SRS) на устройстве записи. 1. Introduction
1. Введение
This document specifies the mechanism to record a Communication Session (CS) by delivering real-time media and metadata from the CS to a recording device. In accordance with the architecture [RFC7245], the Session Recording Protocol specifies the use of SIP, the Session Description Protocol (SDP), and RTP to establish a Recording Session (RS) between the Session Recording Client (SRC), which is on the path of the CS, and a Session Recording Server (SRS) at the recording device. SIP is also used to deliver metadata to the recording device, as specified in [RFC7865]. Metadata is information that describes recorded media and the CS to which they relate. The Session Recording Protocol intends to satisfy the SIP-based Media Recording (SIPREC) requirements listed in [RFC6341]. In addition to the Session Recording Protocol, this document specifies extensions for user agents (UAs) that are participants in a CS to receive recording indications and to provide preferences for recording.
Настоящий документ определяет механизм записи сеанса связи (CS) путём доставки медиаданных и метаданных в реальном времени из CS на устройство записи. В соответствии с архитектурой [RFC7245] протокол записи сеансов определяет использование SIP, протокола описания сеансов (SDP) и RTP для установления сеанса записи (RS) между клиентом записи сеансов (SRC), который находится на пути CS, и сервером записи сеансов (SRS) на устройстве записи. SIP также используется для доставки метаданных на устройство записи, как указано в [RFC7865]. Метаданные — это информация, описывающая записанные медиаданные и CS, к которым они относятся. Протокол записи сеансов имеет целью выполнить требования к записи медиаданных на основе SIP (SIPREC), перечисленные в [RFC6341]. Помимо протокола записи сеансов, настоящий документ определяет расширения для пользовательских агентов (UA), являющихся участниками CS, позволяющие получать индикации записи и задавать предпочтения в отношении записи.
This document considers only active recording, where the SRC purposefully streams media to an SRS and all participating UAs are notified of the recording. Passive recording, where a recording device detects media directly from the network (e.g., using port-mirroring techniques), is outside the scope of this document. In addition, lawful intercept is outside the scope of this document, in accordance with [RFC2804].
Настоящий документ рассматривает только активную запись, при которой SRC целенаправленно передаёт медиаданные на SRS и все участвующие UA уведомляются о записи. 5.1. Delivering Recorded Media
5.1. Доставка записанных медиаданных
When a SIP Back-to-Back User Agent (B2BUA) with SRC functionality routes a call from UA A to UA B, the SRC has access to the media path between the UAs. When the SRC is aware that it should be recording the conversation, the SRC can cause the B2BUA to relay the media between UA A and UA B. The SRC then establishes the RS with the SRS and sends replicated media towards the SRS. An endpoint may also have SRC functionality, where the endpoint itself establishes the RS to the SRS. Since the endpoint has access to the media in the CS, the endpoint can send replicated media towards the SRS.
Когда SIP-агент B2BUA (Back-to-Back User Agent) с функциями SRC маршрутизирует вызов от UA A к UA B, SRC имеет доступ к медиапути между UA. Когда SRC знает, что должен записывать разговор, SRC может заставить B2BUA ретранслировать медиаданные между UA A и UA B. Затем SRC устанавливает RS с SRS и направляет реплицированные медиаданные в сторону SRS. Конечная точка также может обладать функциями SRC, когда она сама устанавливает RS с SRS. Поскольку конечная точка имеет доступ к медиаданным в CS, она может направлять реплицированные медиаданные в сторону SRS.

Note that the SRC can choose when to establish the RS independent of the CS, even though the example call flows suggest that the SRC is establishing the RS (message (5) in Figure 2) after the CS is established.

5.2. Delivering Recording Metadata
5.2. Доставка метаданных записи
The SRC is responsible for the delivery of metadata to the SRS. The SRC may provide an initial metadata snapshot about recorded media streams in the initial INVITE content in the RS. Subsequent metadata updates can be represented as a stream of events in UPDATE [RFC3311] or re-INVITE requests sent by the SRC. These metadata updates are normally incremental updates to the initial metadata snapshot to optimize on the size of updates. However, the SRC may also decide to send a new metadata snapshot at any time.
SRC отвечает за доставку метаданных на SRS. SRC может передать начальный снимок метаданных о записываемых медиапотоках в содержимом начального INVITE в RS. Последующие обновления метаданных могут быть представлены как поток событий в запросах UPDATE [RFC3311] или re-INVITE, отправляемых SRC. Эти обновления метаданных обычно являются инкрементными обновлениями начального снимка метаданных, чтобы оптимизировать размер обновлений. Однако SRC может также решить отправить новый снимок метаданных в любой момент.
Metadata is transported in the body of INVITE or UPDATE messages. Certain metadata, such as the attributes of the recorded media stream, is located in the SDP of the RS.
Метаданные передаются в теле сообщений INVITE или UPDATE. Некоторые метаданные, такие как атрибуты записываемого медиапотока, находятся в SDP сеанса RS.
The SRS has the ability to send a request to the SRC to ask for a new metadata snapshot update from the SRC. This can happen when the SRS fails to understand the current stream of incremental updates for whatever reason -- for example, when the SRS loses the current state due to internal failure. The SRS may optionally attach a reason along with the snapshot request. This request allows both the SRC and the SRS to synchronize the states with a new metadata snapshot so that further incremental metadata updates will be based on the latest metadata snapshot. Similar to the metadata content, the metadata snapshot request is transported as content in UPDATE or INVITE messages sent by the SRS in the RS.
У SRS есть возможность отправить запрос SRC, чтобы запросить у него обновление в виде нового снимка метаданных. Это может произойти, когда SRS по какой-либо причине не может понять текущий поток инкрементных обновлений, — например, когда SRS теряет текущее состояние из-за внутреннего сбоя. SRS может необязательно приложить причину к запросу снимка. Этот запрос позволяет как SRC, так и SRS синхронизировать состояния с помощью нового снимка метаданных, чтобы дальнейшие инкрементные обновления метаданных основывались на последнем снимке метаданных. Подобно содержимому метаданных, запрос снимка метаданных передаётся как содержимое в сообщениях UPDATE или INVITE, отправляемых SRS в RS.

5.3. Receiving Recording Indications and Providing Recording Preferences
5.3. Получение индикаций записи и предоставление предпочтений записи
The SRC is responsible for providing recording indications to the participants in the CS. A recording-aware UA supports receiving recording indications via the SDP "a=record" attribute, and it can specify a recording preference in the CS by including the SDP "a=recordpref" attribute. The recording attribute is a declaration by the SRC in the CS to indicate whether recording is taking place. The recording preference attribute is a declaration by the recording- aware UA in the CS to indicate its recording preference. A UA that does not want to be recorded may still be notified that recording is occurring, for a number of reasons (e.g., it was not capable of indicating its preference, its preference was ignored). If this occurs, the UA's only mechanism to avoid being recorded is to terminate its participation in the session.
SRC отвечает за предоставление индикаций записи участникам CS. UA, осведомлённый о записи, поддерживает получение индикаций записи через атрибут SDP «a=record» и может указать предпочтение записи в CS, включив атрибут SDP «a=recordpref». UA, который не хочет быть записанным, всё равно может быть уведомлён о том, что запись ведётся, по ряду причин (например, он не мог указать своё предпочтение, его предпочтение было проигнорировано). 6.3. Procedures for Recording-Aware User Agents
6.3. Процедуры для пользовательских агентов, осведомлённых о записи
A recording-aware UA is a participant in the CS that supports the SIP and SDP extensions for receiving recording indications and for requesting recording preferences for the call. A recording-aware UA MUST indicate that it can accept the reporting of recording indications provided by the SRC with a new "record-aware" option tag when initiating or establishing a CS; this means including the "record-aware" option tag in the Supported header in the initial INVITE request or response.
UA, осведомлённый о записи, — это участник CS, который поддерживает расширения SIP и SDP для получения индикаций записи и для запроса предпочтений записи для вызова. UA, осведомлённый о записи, ДОЛЖЕН указать, что он может принимать передачу индикаций записи от SRC, с помощью нового тега параметра «record-aware» при инициировании или установлении CS; это означает включение тега параметра «record-aware» в заголовок Supported начального запроса или ответа INVITE.
A recording-aware UA MUST provide a recording indication to the end user through an appropriate user interface, indicating whether recording is on, off, or paused for each medium. Appropriate user interfaces may include real-time notification or previously established agreements that use of the device is subject to recording. Some UAs that are automatons (e.g., Interactive Voice Response (IVR), media server, Public Switched Telephone Network (PSTN) gateway) may not have a user interface to render a recording indication. When such a UA indicates recording awareness, the UA SHOULD render the recording indication through other means, such as passing an in-band tone on the PSTN gateway, putting the recording indication in a log file, or raising an application event in a VoiceXML dialog. These UAs MAY also choose not to indicate recording awareness, thereby relying on whatever mechanism an SRC chooses to indicate recording, such as playing a tone in-band.
UA, осведомлённый о записи, ДОЛЖЕН предоставлять конечному пользователю индикацию записи через подходящий пользовательский интерфейс, указывая, включена ли запись, выключена или приостановлена для каждого носителя. Подходящие пользовательские интерфейсы могут включать уведомление в реальном времени или ранее заключённые соглашения о том, что использование устройства подлежит записи. Некоторые UA, являющиеся автоматами (например, система интерактивного голосового ответа (IVR), медиасервер, шлюз телефонной сети общего пользования (PSTN)), могут не иметь пользовательского интерфейса для отображения индикации записи. Когда такой UA указывает осведомлённость о записи, UA СЛЕДУЕТ отображать индикацию записи другими средствами, например передачей тонального сигнала в полосе на шлюзе PSTN, записью индикации записи в файл журнала или генерацией события приложения в диалоге VoiceXML. Эти UA МОГУТ также решить не указывать осведомлённость о записи, полагаясь на любой механизм, который SRC выберет для индикации записи, например на воспроизведение тонального сигнала в полосе.

7.1.1.1. Handling Media Stream Updates
7.1.1.1. Обработка обновлений медиапотоков
Over the lifetime of an RS, the SRC can add and remove recorded streams to and from the RS for various reasons -- for example, when a CS stream is added to or removed from the CS, or when a CS is created or terminated if an RS handles multiple CSs. To remove a recorded stream from the RS, the SRC sends a new SDP offer where the port of the media stream to be removed is set to zero, according to the procedures in [RFC3264]. To add a recorded stream to the RS, the SRC sends a new SDP offer by adding a new media stream description or by reusing an old media stream that had been previously disabled, according to the procedures in [RFC3264]. The SRC can temporarily discontinue streaming and collection of recorded media from the SRC to the SRS for reasons such as masking the recording. In this case, the SRC sends a new SDP offer and sets the media stream to inactive (a=inactive) for each recorded stream to be paused, as per the procedures in [RFC3264]. To resume streaming and collection of recorded media, the SRC sends a new SDP offer and sets the media stream to sendonly (a=sendonly). Note that a CS may itself change the media stream direction by updating the SDP -- for example, by setting a=inactive for SDP hold. Media stream direction changes in the CS are conveyed in the metadata by the SRC. When a CS media stream is changed to or from inactive, the effect on the corresponding RS media stream is governed by SRC policy. The SRC MAY have a local policy to pause an RS media stream when the corresponding CS media stream is inactive, or it MAY leave the RS media stream as sendonly.
На протяжении существования RS SRC может добавлять записываемые потоки в RS и удалять их оттуда по разным причинам — например, когда поток CS добавляется в CS или удаляется из неё либо когда CS создаётся или завершается, если RS обслуживает несколько CS. Чтобы удалить записываемый поток из RS, SRC отправляет новое предложение SDP, в котором порт удаляемого медиапотока устанавливается в ноль согласно процедурам в [RFC3264]. Чтобы добавить записываемый поток в RS, SRC отправляет новое предложение SDP, добавляя описание нового медиапотока или повторно используя старый медиапоток, который был ранее отключён, согласно процедурам в [RFC3264]. SRC может временно прекратить передачу и сбор записываемых медиаданных от SRC к SRS по таким причинам, как маскирование записи. В этом случае SRC отправляет новое предложение SDP и устанавливает медиапоток в состояние inactive (a=inactive) для каждого записываемого потока, который нужно приостановить, согласно процедурам в [RFC3264]. Чтобы возобновить передачу и сбор записываемых медиаданных, SRC отправляет новое предложение SDP и устанавливает медиапоток в состояние sendonly (a=sendonly). Обратите внимание, что CS сама может изменить направление медиапотока, обновив SDP, — например, установив a=inactive для удержания SDP. Изменения направления медиапотока в CS передаются в метаданных SRC. Когда медиапоток CS переключается в состояние inactive или из него, влияние на соответствующий медиапоток RS определяется политикой SRC. SRC МОЖЕТ иметь локальную политику приостановки медиапотока RS, когда соответствующий медиапоток CS неактивен, либо МОЖЕТ оставить медиапоток RS в состоянии sendonly.
7.1.2. Recording Indication in the CS
7.1.2. Индикация записи в CS
While there are existing mechanisms for providing an indication that a CS is being recorded, these mechanisms are usually delivered on the CS media streams, such as playing an in-band tone or an announcement to the participants. A new "record" SDP attribute is introduced to allow the SRC to indicate recording state to a recording-aware UA in a CS.
Хотя существуют механизмы предоставления индикации о том, что CS записывается, эти механизмы обычно доставляются по медиапотокам CS, например воспроизведение тонального сигнала в полосе или объявления участникам. Вводится новый атрибут SDP «record», позволяющий SRC указывать состояние записи осведомлённому о записи UA в CS.
The "record" SDP attribute appears at the media level or session level in either an SDP offer or answer. When the attribute is applied at the session level, the indication applies to all media streams in the SDP. When the attribute is applied at the media level, the indication applies to that one media stream only, and that overrides the indication if also set at the session level. Whenever the recording indication needs to change, such as termination of recording, the SRC MUST initiate a re-INVITE or UPDATE to update the SDP "a=record" attribute.
Атрибут SDP «record» появляется на уровне медиаданных или на уровне сеанса в предложении или ответе SDP. Когда атрибут применяется на уровне сеанса, индикация относится ко всем медиапотокам в SDP. Когда атрибут применяется на уровне медиаданных, индикация относится только к этому одному медиапотоку и переопределяет индикацию, если она также задана на уровне сеанса. 7.3. Procedures for Recording-Aware User Agents
7.3. Процедуры для пользовательских агентов, осведомлённых о записи
7.3.1. Recording Indication
7.3.1. Индикация записи
When a recording-aware UA receives an SDP offer or answer that includes the "a=record" attribute, the UA provides to the end user an indication as to whether the recording is on, off, or paused for each medium, based on the most recently received "a=record" SDP attribute for that medium.
Когда осведомлённый о записи UA получает предложение или ответ SDP, включающий атрибут «a=record», UA предоставляет конечному пользователю индикацию того, включена ли запись, выключена или приостановлена для каждого носителя, на основе последнего полученного атрибута SDP «a=record» для этого носителя.
When a CS is traversed through multiple UAs such as a B2BUA or a conference focus, each UA involved in the CS that is aware that the CS is being recorded MUST provide the recording indication through the "a=record" attribute to all other parties in the CS. It is possible that more than one SRC is in the call path of the same CS, but the recording indication attribute does not provide any hint as to which SRC or how many SRCs are recording. An endpoint knows only that the call is being recorded. Furthermore, this attribute is not used as a request for a specific SRC to start or stop recording.
Когда CS проходит через несколько UA, таких как B2BUA или фокус конференции, каждый UA, участвующий в CS и знающий, что CS записывается, ДОЛЖЕН предоставлять индикацию записи через атрибут «a=record» всем остальным сторонам в CS. Возможно, что на пути вызова одной и той же CS находится более одного SRC, но атрибут индикации записи не даёт никаких сведений о том, какой SRC или сколько SRC выполняет запись. Конечная точка знает только то, что вызов записывается. Кроме того, этот атрибут не используется как запрос к конкретному SRC начать или остановить запись.
7.3.2. Recording Preference
7.3.2. Предпочтение записи
A participant in a CS MAY set the recording preference in the CS to be recorded or not recorded at session establishment or during the session. A new "recordpref" SDP attribute is introduced, and the participant in the CS may set this recording preference attribute in any SDP offer/answer at session establishment time or during the session. The SRC is not required to honor the recording preference from a participant, based on local policies at the SRC, and the participant can learn the recording indication through the "a=record" SDP attribute as described in Section 7.3.1.
Участник CS МОЖЕТ задать предпочтение записи в CS — записывать или не записывать — при установлении сеанса или во время сеанса. Вводится новый атрибут SDP «recordpref», и участник CS может задать этот атрибут предпочтения записи в любом предложении/ответе SDP при установлении сеанса или во время сеанса. SRC не обязан соблюдать предпочтение записи участника, исходя из локальных политик SRC, а участник может узнать индикацию записи через атрибут SDP «a=record», как описано в разделе 7.3.1.
The SDP "a=recordpref" attribute can appear at the media level or session level and can appear in an SDP offer or answer. When the attribute is applied at the session level, the recording preference applies to all media streams in the SDP. When the attribute is applied at the media level, the recording preference applies to that one media stream only, and that overrides the recording preference if also set at the session level. Настоящий раздел содержит рекомендации и указания по RTP и протоколу управления передачей в реальном времени (RTCP) в контексте SIPREC [RFC6341]. 8.1. RTP Mechanisms
8.1. Механизмы RTP
This section briefly describes important RTP/RTCP constructs and mechanisms that are particularly useful within the context of SIPREC.
В настоящем разделе кратко описываются важные конструкции и механизмы RTP/RTCP, которые особенно полезны в контексте SIPREC.
8.1.1. RTCP
8.1.1. RTCP
The RTP data transport is augmented by a control protocol (RTCP) to allow monitoring of the data delivery. RTCP, as defined in [RFC3550], is based on the periodic transmission of control packets to all participants in the RTP session, using the same distribution mechanism as the data packets. Support for RTCP is REQUIRED, per [RFC3550], and it provides, among other things, the following important functionality in relation to SIPREC:
Транспорт данных RTP дополняется протоколом управления (RTCP), позволяющим отслеживать доставку данных. RTCP, как определено в [RFC3550], основан на периодической передаче пакетов управления всем участникам сеанса RTP с использованием того же механизма распространения, что и для пакетов данных. Поддержка RTCP ТРЕБУЕТСЯ согласно [RFC3550], и она обеспечивает, среди прочего, следующие важные функции применительно к SIPREC:
1) Feedback on the quality of the data distribution
1) Обратная связь о качестве распространения данных
This feedback from the receivers may be used to diagnose faults in the distribution. As such, RTCP is a well-defined and efficient mechanism for the SRS to inform the SRC, and for the SRC to inform recording-aware UAs, of issues that arise with respect to the reception of media that is to be recorded.
Эта обратная связь от получателей может использоваться для диагностики неисправностей в распространении. Таким образом, RTCP — это чётко определённый и эффективный механизм, позволяющий SRS информировать SRC, а SRC информировать осведомлённые о записи UA о проблемах, возникающих при приёме медиаданных, подлежащих записи.
2) Including a persistent transport-level identifier -- the CNAME, or canonical name -- for an RTP source
2) Включение постоянного идентификатора транспортного уровня -- CNAME, или канонического имени, -- для источника
The synchronization source (SSRC) [RFC3550] identifier may change if a conflict is discovered or a program is restarted, in which case receivers can use the CNAME to keep track of each participant. Receivers may also use the CNAME to associate multiple data streams from a given participant in a set of related RTP sessions -- for example, to synchronize audio and video. Synchronization of media streams is also facilitated by the NTP and RTP timestamps included in RTCP packets by data senders.
RTP Идентификатор источника синхронизации (SSRC) [RFC3550] может измениться при обнаружении конфликта или перезапуске программы; в этом случае получатели могут использовать CNAME для отслеживания каждого участника. Получатели могут также использовать CNAME для связывания нескольких потоков данных от данного участника в наборе связанных сеансов RTP — например, для синхронизации аудио и видео. Синхронизации медиапотоков также способствуют временные метки NTP и RTP, включаемые отправителями данных в пакеты RTCP.
8.1.2. RTP Profile
8.1.2. Профиль RTP
The RECOMMENDED RTP profiles for the SRC, SRS, and recording-aware UAs are "Extended Secure RTP Profile for Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/SAVPF)" [RFC5124] when using encrypted RTP streams, and "Extended RTP Profile for Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/AVPF)" [RFC4585] when using non-encrypted media streams. However, as these are not requirements, some implementations may use "The Secure Real-time Transport Protocol (SRTP)" [RFC3711] and "RTP Profile for Audio and Video Conferences with Minimal Control" [RFC3551]. Therefore, it is RECOMMENDED that the SRC, SRS, and recording-aware UAs not rely entirely on RTP/SAVPF or RTP/AVPF for core functionality that may be at least partially achievable using RTP/SAVP and RTP/AVP.
Рекомендуемыми профилями RTP для SRC, SRS и осведомлённых о записи UA являются «Extended Secure RTP Profile for Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/SAVPF)» [RFC5124] при использовании шифрованных потоков RTP и «Extended RTP Profile for Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/AVPF)» [RFC4585] при использовании незашифрованных медиапотоков. Однако, поскольку это не требования, некоторые реализации могут использовать «The Secure Real-time Transport Protocol (SRTP)» [RFC3711] и «RTP Profile for Audio and Video Conferences with Minimal Control» [RFC3551]. Поэтому РЕКОМЕНДУЕТСЯ, чтобы SRC, SRS и осведомлённые о записи UA не полагались полностью на RTP/SAVPF или RTP/AVPF в отношении базовой функциональности, которая может быть хотя бы частично достигнута с использованием RTP/SAVP и RTP/AVP.
AVPF and SAVPF provide an improved RTCP timer model that allows more flexible transmission of RTCP packets in response to events, rather than strictly according to bandwidth. AVPF-based codec control messages provide efficient mechanisms for an SRC, an SRS, and recording-aware UAs to handle events such as scene changes, error recovery, and dynamic bandwidth adjustments. These messages are discussed in more detail later in this document.
AVPF и SAVPF обеспечивают улучшенную модель таймеров RTCP, которая позволяет передавать пакеты RTCP более гибко — в ответ на события, а не строго в соответствии с полосой пропускания. Сообщения управления кодеком на основе AVPF предоставляют эффективные механизмы для SRC, SRS и осведомлённых о записи UA для обработки таких событий, как смена сцены, восстановление после ошибок и динамическая корректировка полосы пропускания. Эти сообщения более подробно рассматриваются далее в настоящем документе.
SAVP and SAVPF provide media encryption, integrity protection, replay protection, and a limited form of source authentication. They do not contain or require a specific keying mechanism.
SAVP и SAVPF обеспечивают шифрование медиаданных, защиту целостности, защиту от повторного воспроизведения и ограниченную форму аутентификации источника. Они не содержат и не требуют конкретного механизма управления ключами.
8.1.3. SSRC
8.1.3. SSRC
The SSRC, as defined in [RFC3550], is carried in the RTP header and in various fields of RTCP packets. It is a random 32-bit number that is required to be globally unique within an RTP session. It is crucial that the number be chosen with care, in order that participants on the same network or starting at the same time are not likely to choose the same number. Guidelines regarding SSRC value selection and conflict resolution are provided in [RFC3550].
SSRC, как определено в [RFC3550], передаётся в заголовке RTP и в различных полях пакетов RTCP. Это случайное 32-битное число, которое должно быть глобально уникальным в пределах сеанса RTP. Крайне важно выбирать это число с осторожностью, чтобы участники в одной сети или начинающие работу одновременно не выбрали одно и то же число. Рекомендации по выбору значения SSRC и разрешению конфликтов приведены в [RFC3550].
The SSRC may also be used to separate different sources of media within a single RTP session. For this reason, as well as for conflict resolution, it is important that the SRC, SRS, and recording-aware UAs handle changes in SSRC values and properly identify the reason for the change. The CNAME values carried in RTCP facilitate this identification.
SSRC может также использоваться для разделения разных источников медиаданных в пределах одного сеанса RTP. По этой причине, а также для разрешения конфликтов важно, чтобы SRC, SRS и осведомлённые о записи UA обрабатывали изменения значений SSRC и правильно определяли причину изменения. Значения CNAME, передаваемые в RTCP, облегчают такое определение.
8.1.4. CSRC
8.1.4. CSRC
The contributing source (CSRC), as defined in [RFC3550], identifies the source of a stream of RTP packets that has contributed to the combined stream produced by an RTP mixer. The mixer inserts a list of the SSRC identifiers of the sources that contributed to the generation of a particular packet into the RTP header of that packet. This list is called the CSRC list. It is RECOMMENDED that an SRC or recording-aware UA, when acting as a mixer, set the CSRC list accordingly, and that the SRC and SRS interpret the CSRC list per [RFC3550] when received.
Идентификатор вносящего вклад источника (CSRC), как определено в [RFC3550], идентифицирует источник потока пакетов RTP, который внёс вклад в объединённый поток, созданный микшером RTP. Микшер вставляет список идентификаторов SSRC источников, участвовавших в формировании конкретного пакета, в заголовок RTP этого пакета. Этот список называется списком CSRC. РЕКОМЕНДУЕТСЯ, чтобы SRC или осведомлённый о записи UA, действуя как микшер, устанавливали список CSRC соответствующим образом, а SRC и SRS при получении интерпретировали список CSRC согласно [RFC3550].
8.1.5. SDES
8.1.5. SDES
The Source Description (SDES), as defined in [RFC3550], contains an SSRC/CSRC identifier followed by a list of zero or more items that carry information about the SSRC/CSRC. End systems send one SDES packet containing their own source identifier (the same as the SSRC in the fixed RTP header). A mixer sends one SDES packet containing a chunk for each CSRC from which it is receiving SDES information, or multiple complete SDES packets if there are more than 31 such sources.
Описание источника (SDES), как определено в [RFC3550], содержит идентификатор SSRC/CSRC, за которым следует список из нуля или более элементов, несущих информацию об SSRC/CSRC. Конечные системы отправляют один пакет SDES, содержащий их собственный идентификатор источника (тот же, что и SSRC в фиксированном заголовке RTP). Микшер отправляет один пакет SDES, содержащий блок для каждого CSRC, от которого он получает информацию SDES, либо несколько полных пакетов SDES, если таких источников больше 31.
The ability to identify individual CSRCs is important in the context of SIPREC. Metadata [RFC7865] provides a mechanism to achieve this at the signaling level. SDES provides a mechanism at the RTP level.
Возможность идентифицировать отдельные CSRC важна в контексте SIPREC. Метаданные [RFC7865] предоставляют механизм для этого на уровне сигнализации. SDES предоставляет механизм на уровне RTP.
8.1.5.1. CNAME
8.1.5.1. CNAME
The Canonical End-Point Identifier (CNAME), as defined in [RFC3550], provides the binding from the SSRC identifier to an identifier for the source (sender or receiver) that remains constant. It is important that the SRC and recording-aware UAs generate CNAMEs appropriately and that the SRC and SRS interpret and use them for this purpose. Guidelines for generating CNAME values are provided in "Guidelines for Choosing RTP Control Protocol (RTCP) Canonical Names (CNAMEs)" [RFC7022].
Канонический идентификатор конечной точки (CNAME), как определено в [RFC3550], обеспечивает привязку идентификатора SSRC к идентификатору источника (отправителя или получателя), который остаётся постоянным. Важно, чтобы SRC и осведомлённые о записи UA формировали CNAME должным образом и чтобы SRC и SRS интерпретировали и использовали их для этой цели. Рекомендации по формированию значений CNAME приведены в документе «Guidelines for Choosing RTP Control Protocol (RTCP) Canonical Names (CNAMEs)» [RFC7022].
8.1.6. Keepalive
8.1.6. Поддержание активности
It is anticipated that media streams in SIPREC may exist in an inactive state for extended periods of time for any of a number of valid reasons. In order for the bindings and any pinholes in NATs/firewalls to remain active during such intervals, it is RECOMMENDED that the SRC, SRS, and recording-aware UAs follow the keepalive procedure recommended in "Application Mechanism for Keeping Alive the NAT Mappings Associated with RTP / RTP Control Protocol (RTCP) Flows" [RFC6263] for all RTP media streams.
Предполагается, что медиапотоки в SIPREC могут длительное время находиться в неактивном состоянии по ряду обоснованных причин. Чтобы привязки и любые отверстия в NAT/межсетевых экранах оставались активными в течение таких интервалов, РЕКОМЕНДУЕТСЯ, чтобы SRC, SRS и осведомлённые о записи UA следовали процедуре поддержания активности, рекомендованной в документе «Application Mechanism for Keeping Alive the NAT Mappings Associated with RTP / RTP Control Protocol (RTCP) Flows» [RFC6263], для всех медиапотоков RTP.
8.1.7. RTCP Feedback Messages
8.1.7. Сообщения обратной связи RTCP
"Codec Control Messages in the RTP Audio-Visual Profile with Feedback (AVPF)" [RFC5104] specifies extensions to the messages defined in AVPF [RFC4585]. Support for and proper usage of these messages are important to SRC, SRS, and recording-aware UA implementations. Note that these messages are applicable only when using the AVPF or SAVPF RTP profiles.
Документ «Codec Control Messages in the RTP Audio-Visual Profile with Feedback (AVPF)» [RFC5104] определяет расширения сообщений, определённых в AVPF [RFC4585]. Поддержка и правильное использование этих сообщений важны для реализаций SRC, SRS и осведомлённых о записи UA. Обратите внимание, что эти сообщения применимы только при использовании профилей RTP AVPF или SAVPF.
8.1.7.1. Full Intra Request
8.1.7.1. Full Intra Request
A Full Intra Request (FIR) command, when received by the designated media sender, requires that the media sender send a decoder refresh point at the earliest opportunity. Using a decoder refresh point implies refraining from using any picture sent prior to that point as a reference for the encoding process of any subsequent picture sent in the stream.
Команда Full Intra Request (FIR), полученная назначенным отправителем медиаданных, требует, чтобы отправитель медиаданных отправил точку обновления декодера при первой возможности. Использование точки обновления декодера подразумевает отказ от использования любого изображения, отправленного до этой точки, в качестве опорного для процесса кодирования любого последующего изображения, отправляемого в потоке.
Decoder refresh points, especially Intra or Instantaneous Decoding Refresh (IDR) pictures for H.264 video codecs, are in general several times larger in size than predicted pictures. Thus, in scenarios in which the available bit rate is small, the use of a decoder refresh point implies a delay that is significantly longer than the typical picture duration.
Точки обновления декодера, особенно Intra- или IDR-изображения (Instantaneous Decoding Refresh) для видеокодеков H.264, обычно в несколько раз больше по размеру, чем предсказанные изображения. Поэтому в сценариях с малой доступной скоростью передачи использование точки обновления декодера приводит к задержке, значительно превышающей типичную длительность изображения.
8.1.7.1.1. Deprecated Usage of SIP INFO Instead of FIR
8.1.7.1.1. Устаревшее использование SIP INFO вместо FIR
"XML Schema for Media Control" [RFC5168] defines an Extensible Markup Language (XML) Schema for video fast update. Implementations are discouraged from using the method described in [RFC5168], except for purposes of backward compatibility. Implementations SHOULD use FIR messages instead.
Документ «XML Schema for Media Control» [RFC5168] определяет схему Extensible Markup Language (XML) для быстрого обновления видео. Реализациям не рекомендуется использовать метод, описанный в [RFC5168], кроме случаев обратной совместимости. Вместо него реализации СЛЕДУЕТ использовать сообщения FIR.
To make sure that a common mechanism exists between the SRC and SRS, the SRS MUST support both mechanisms (FIR and SIP INFO), using FIR messages when negotiated successfully with the SRC and using SIP INFO otherwise.
Чтобы между SRC и SRS существовал общий механизм, SRS ДОЛЖЕН поддерживать оба механизма (FIR и SIP INFO), используя сообщения FIR при успешном согласовании с SRC и SIP INFO в противном случае.
8.1.7.2. Picture Loss Indication
8.1.7.2. Индикация потери изображения
Picture Loss Indication (PLI), as defined in [RFC4585], informs the encoder of the loss of an undefined amount of coded video data belonging to one or more pictures. [RFC4585] recommends using PLI instead of FIR messages to recover from errors. FIR is appropriate only in situations where not sending a decoder refresh point would render the video unusable for the users. Examples where sending FIR messages is appropriate include a multipoint conference when a new user joins the conference and no regular decoder refresh point interval is established, and a video-switching Multipoint Control Unit (MCU) that changes streams.
Индикация потери изображения (PLI), как определено в [RFC4585], сообщает кодеру о потере неопределённого объёма кодированных видеоданных, относящихся к одному или нескольким изображениям. [RFC4585] рекомендует использовать PLI вместо сообщений FIR для восстановления после ошибок. FIR подходит только в ситуациях, когда отсутствие отправки точки обновления декодера сделало бы видео непригодным для пользователей. Примеры ситуаций, в которых отправка сообщений FIR уместна, включают многоточечную конференцию, когда новый пользователь присоединяется к конференции и регулярный интервал точек обновления декодера не установлен, и блок многоточечного управления (MCU) с переключением видео, который меняет потоки.
Appropriate use of PLI and FIR is important to ensure, with minimum overhead, that the recorded video is usable (e.g., the necessary reference frames exist for a player to render the recorded video).
Надлежащее использование PLI и FIR важно для того, чтобы с минимальными накладными расходами гарантировать пригодность записанного видео (например, наличие необходимых опорных кадров, чтобы проигрыватель мог отобразить записанное видео).
8.1.7.3. Temporary Maximum Media Stream Bit Rate Request
8.1.7.3. Temporary Maximum Media Stream Bit Rate Request
A receiver, translator, or mixer uses the Temporary Maximum Media Stream Bit Rate Request (TMMBR) [RFC5104] to request a sender to limit the maximum bit rate for a media stream to the provided value. Appropriate use of TMMBR facilitates rapid adaptation to changes in available bandwidth.
Получатель, транслятор или микшер использует запрос Temporary Maximum Media Stream Bit Rate Request (TMMBR) [RFC5104], чтобы попросить отправителя ограничить максимальную скорость передачи для медиапотока указанным значением. Надлежащее использование TMMBR облегчает быструю адаптацию к изменениям доступной полосы пропускания.
8.1.7.3.1. Renegotiation of SDP Bandwidth Attribute
8.1.7.3.1. Пересогласование атрибута полосы пропускания SDP
If it is likely that the new value indicated by TMMBR will be valid for the remainder of the session, the TMMBR sender is expected to perform a renegotiation of the session upper limit using the session signaling protocol. Therefore, for SIPREC, implementations are RECOMMENDED to use TMMBR for temporary changes and renegotiation of bandwidth via SDP offer/answer for more permanent changes.
Если вероятно, что новое значение, указанное в TMMBR, будет действовать до конца сеанса, отправитель TMMBR должен выполнить пересогласование верхнего предела сеанса с помощью протокола сигнализации сеанса. Поэтому для SIPREC реализациям РЕКОМЕНДУЕТСЯ использовать TMMBR для временных изменений, а пересогласование полосы пропускания через предложение/ответ SDP — для более постоянных изменений.
8.1.8. Symmetric RTP/RTCP for Sending and Receiving
8.1.8. Симметричные RTP/RTCP для отправки и приёма
Within an SDP offer/answer exchange, RTP entities choose the RTP and RTCP transport addresses (i.e., IP addresses and port numbers) on which to receive packets. When sending packets, the RTP entities may use the same source port or a different source port than those signaled for receiving packets. When the transport address used to send and receive RTP is the same, it is termed "symmetric RTP" [RFC4961]. Likewise, when the transport address used to send and receive RTCP is the same, it is termed "symmetric RTCP" [RFC4961].
В рамках обмена предложением/ответом SDP объекты RTP выбирают транспортные адреса RTP и RTCP (то есть IP-адреса и номера портов), на которых принимать пакеты. При отправке пакетов объекты RTP могут использовать тот же исходный порт, что и указанный для приёма пакетов, или другой исходный порт. Когда транспортный адрес, используемый для отправки и приёма RTP, один и тот же, это называется «симметричным RTP» [RFC4961]. Аналогично, когда транспортный адрес, используемый для отправки и приёма RTCP, один и тот же, это называется «симметричным RTCP» [RFC4961].
When sending RTP, the use of symmetric RTP is REQUIRED. When sending RTCP, the use of symmetric RTCP is REQUIRED. Although an SRS will not normally send RTP, it will send RTCP as well as receive RTP and RTCP. Likewise, although an SRC will not normally receive RTP from the SRS, it will receive RTCP as well as send RTP and RTCP.
При отправке RTP использование симметричного RTP ТРЕБУЕТСЯ. При отправке RTCP использование симметричного RTCP ТРЕБУЕТСЯ. Хотя SRS обычно не отправляет RTP, он отправляет RTCP, а также принимает RTP и RTCP. Аналогично, хотя SRC обычно не принимает RTP от SRS, он принимает RTCP, а также отправляет RTP и RTCP.
Note: Symmetric RTP and symmetric RTCP are different from RTP/RTCP multiplexing [RFC5761].
Примечание: симметричный RTP и симметричный RTCP отличаются от мультиплексирования RTP/RTCP [RFC5761].
8.2. Roles
8.2. Роли
An SRC has the task of gathering media from the various UAs in one or more CSs and forwarding the information to the SRS within the context of a corresponding RS. There are numerous ways in which an SRC may do this, including, but not limited to, appearing as a UA within a CS, or as a B2BUA between UAs within a CS.
Задача SRC — собирать медиаданные от различных UA в одном или нескольких CS и передавать информацию на SRS в контексте соответствующего RS. SRC может делать это множеством способов, включая, помимо прочего, представление в роли UA внутри CS или в роли B2BUA между UA внутри CS.

The following subsections define a set of roles an SRC may choose to play, based on its position with respect to a UA within a CS, and an SRS within an RS. A CS and a corresponding RS are independent sessions; therefore, an SRC may play a different role within a CS than it does within the corresponding RS.
В следующих подразделах определяется набор ролей, которые SRC может выбрать для исполнения, исходя из своего положения относительно UA в CS и SRS в RS. CS и соответствующий RS являются независимыми сеансами; поэтому в CS SRC может играть иную роль, чем в соответствующем RS.
8.2.1. SRC Acting as an RTP Translator
8.2.1. SRC в роли транслятора RTP
The SRC may act as a translator, as defined in [RFC3550]. A defining characteristic of a translator is that it forwards RTP packets with their SSRC identifier intact. There are two types of translators: one that simply forwards, and another that performs transcoding (e.g., from one codec to another) in addition to forwarding.
SRC может действовать как транслятор, как определено в [RFC3550]. Определяющей характеристикой транслятора является то, что он пересылает пакеты RTP с неизменным идентификатором SSRC. Существует два типа трансляторов: один, который просто пересылает, и другой, который помимо пересылки выполняет транскодирование (например, из одного кодека в другой).
8.2.1.1. Forwarding Translator
8.2.1.1. Пересылающий транслятор
When acting as a forwarding translator, RTP received as separate streams from different sources (e.g., from different UAs with different SSRCs) cannot be mixed by the SRC and MUST be sent separately to the SRS. All RTCP reports MUST be passed by the SRC between the UAs and the SRS, such that the UAs and SRS are able to detect any SSRC collisions.
Действуя как пересылающий транслятор, SRC не может смешивать RTP, полученный в виде отдельных потоков от разных источников (например, от разных UA с разными SSRC), и ДОЛЖЕН отправлять его на SRS отдельно. Все отчёты RTCP ДОЛЖНЫ передаваться SRC между UA и SRS, чтобы UA и SRS могли обнаруживать любые коллизии SSRC.
RTCP Sender Reports generated by a UA sending a stream MUST be forwarded to the SRS. RTCP Receiver Reports generated by the SRS MUST be forwarded to the relevant UA.
Отчёты отправителя RTCP, сформированные UA, отправляющим поток, ДОЛЖНЫ пересылаться на SRS. Отчёты получателя RTCP, сформированные SRS, ДОЛЖНЫ пересылаться соответствующему UA.
UAs may receive multiple sets of RTCP Receiver Reports -- one or more from other UAs participating in the CS, and one from the SRS participating in the RS. A UA SHOULD process the RTCP Receiver Reports from the SRS if it is recording aware.
UA могут получать несколько наборов отчётов получателя RTCP: один или несколько от других UA, участвующих в CS, и один от SRS, участвующего в RS. UA СЛЕДУЕТ обрабатывать отчёты получателя RTCP от SRS, если он осведомлён о записи.
If SRTP is used on both the CS and the RS, decryption and/or re-encryption may occur. For example, if different keys are used, it will occur. If the same keys are used, it need not occur. Section 12 provides additional information on SRTP and keying mechanisms.
Если SRTP используется и в CS, и в RS, может выполняться расшифрование и/или повторное шифрование. Например, если используются разные ключи, это произойдёт. Если используются одинаковые ключи, этого может не происходить. В разделе 12 приведена дополнительная информация о SRTP и механизмах управления ключами.
If packet loss occurs, either from the UA to the SRC or from the SRC to the SRS, the SRS SHOULD detect and attempt to recover from the loss. The SRC does not play a role in this, other than forwarding the associated RTP and RTCP packets.
Если происходит потеря пакетов — от UA к SRC или от SRC к SRS, — SRS СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё. SRC не играет в этом роли, кроме пересылки соответствующих пакетов RTP и RTCP.
8.2.1.2. Transcoding Translator
8.2.1.2. Транскодирующий транслятор
When acting as a transcoding translator, an SRC MAY perform transcoding (e.g., from one codec to another), and this may result in a different rate of packets between what the SRC receives on the CS and what the SRC sends on the RS. As when acting as a forwarding translator, RTP received as separate streams from different sources (e.g., from different UAs with different SSRCs) cannot be mixed by the SRC and MUST be sent separately to the SRS. All RTCP reports MUST be passed by the SRC between the UAs and the SRS, such that the UAs and SRS are able to detect any SSRC collisions. RTCP Sender Reports generated by a UA sending a stream MUST be forwarded to the SRS. RTCP Receiver Reports generated by the SRS MUST be forwarded to the relevant UA. The SRC may need to manipulate the RTCP Receiver Reports to take into account any transcoding that has taken place.
Действуя как транскодирующий транслятор, SRC МОЖЕТ выполнять транскодирование (например, из одного кодека в другой), что может привести к иной частоте пакетов между тем, что SRC получает в CS, и тем, что SRC отправляет в RS. Как и при работе пересылающим транслятором, RTP, полученный в виде отдельных потоков от разных источников (например, от разных UA с разными SSRC), не может смешиваться SRC и ДОЛЖЕН отправляться на SRS отдельно. Все отчёты RTCP ДОЛЖНЫ передаваться SRC между UA и SRS, чтобы UA и SRS могли обнаруживать любые коллизии SSRC. Отчёты отправителя RTCP, сформированные UA, отправляющим поток, ДОЛЖНЫ пересылаться на SRS. Отчёты получателя RTCP, сформированные SRS, ДОЛЖНЫ пересылаться соответствующему UA. SRC может потребоваться скорректировать отчёты получателя RTCP с учётом выполненного транскодирования.
UAs may receive multiple sets of RTCP Receiver Reports -- one or more from other UAs participating in the CS, and one from the SRS participating in the RS. A recording-aware UA SHOULD be prepared to process the RTCP Receiver Reports from the SRS, whereas a recording- unaware UA may discard such RTCP packets as irrelevant.
UA могут получать несколько наборов отчётов получателя RTCP: один или несколько от других UA, участвующих в CS, и один от SRS, участвующего в RS. Осведомлённому о записи UA СЛЕДУЕТ быть готовым обрабатывать отчёты получателя RTCP от SRS, тогда как UA, не осведомлённый о записи, может отбрасывать такие пакеты RTCP как не относящиеся к делу.
If SRTP is used on both the CS and the RS, decryption and/or re-encryption may occur. For example, if different keys are used, it will occur. If the same keys are used, it need not occur. Section 12 provides additional information on SRTP and keying mechanisms.
Если SRTP используется и в CS, и в RS, может выполняться расшифрование и/или повторное шифрование. Например, если используются разные ключи, это произойдёт. Если используются одинаковые ключи, этого может не происходить. В разделе 12 приведена дополнительная информация о SRTP и механизмах управления ключами.
If packet loss occurs, either from the UA to the SRC or from the SRC to the SRS, the SRS SHOULD detect and attempt to recover from the loss. The SRC does not play a role in this, other than forwarding the associated RTP and RTCP packets.
Если происходит потеря пакетов — от UA к SRC или от SRC к SRS, — SRS СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё. SRC не играет в этом роли, кроме пересылки соответствующих пакетов RTP и RTCP.
8.2.2. SRC Acting as an RTP Mixer
8.2.2. SRC в роли микшера RTP
In the case of the SRC acting as an RTP mixer, as defined in [RFC3550], the SRC combines RTP streams from different UAs and sends them towards the SRS using its own SSRC. The SSRCs from the contributing UA SHOULD be conveyed as CSRC identifiers within this stream. The SRC may make timing adjustments among the received streams and generate its own timing on the stream sent to the SRS. Optionally, an SRC acting as a mixer can perform transcoding and can even cope with different codings received from different UAs. RTCP Sender Reports and Receiver Reports are not forwarded by an SRC acting as a mixer, but there are requirements for forwarding RTCP Source Description (SDES) packets. The SRC generates its own RTCP Sender Reports and Receiver Reports toward the associated UAs and SRS.
В случае, когда SRC действует как микшер RTP, как определено в [RFC3550], SRC объединяет потоки RTP от разных UA и отправляет их в сторону SRS, используя собственный SSRC. SSRC вносящих вклад UA СЛЕДУЕТ передавать как идентификаторы CSRC в этом потоке. SRC может выполнять временные корректировки между полученными потоками и формировать собственные временные параметры для потока, отправляемого на SRS. Необязательно SRC, действующий как микшер, может выполнять транскодирование и даже справляться с разными кодировками, полученными от разных UA. Отчёты отправителя и получателя RTCP не пересылаются SRC, действующим как микшер, но существуют требования по пересылке пакетов описания источника RTCP (SDES). SRC формирует собственные отчёты отправителя и получателя RTCP в сторону соответствующих UA и SRS.
The use of SRTP between the SRC and the SRS for the RS is independent of the use of SRTP between the UAs and the SRC for the CS. Section 12 provides additional information on SRTP and keying mechanisms.
Использование SRTP между SRC и SRS для RS не зависит от использования SRTP между UA и SRC для CS. В разделе 12 приведена дополнительная информация о SRTP и механизмах управления ключами.
If packet loss occurs from the UA to the SRC, the SRC SHOULD detect and attempt to recover from the loss. If packet loss occurs from the SRC to the SRS, the SRS SHOULD detect and attempt to recover from the loss.
Если происходит потеря пакетов от UA к SRC, SRC СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё. Если происходит потеря пакетов от SRC к SRS, SRS СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё.
8.2.3. SRC Acting as an RTP Endpoint
8.2.3. SRC в роли конечной точки RTP
The case of the SRC acting as an RTP endpoint, as defined in [RFC3550], is similar to the mixer case, except that the RTP session between the SRC and the SRS is considered completely independent from the RTP session that is part of the CS. The SRC can, but need not, mix RTP streams from different participants prior to sending to the SRS. RTCP between the SRC and the SRS is completely independent of RTCP on the CS.
Случай, когда SRC действует как конечная точка RTP, как определено в [RFC3550], аналогичен случаю микшера, за исключением того, что сеанс RTP между SRC и SRS считается полностью независимым от сеанса RTP, являющегося частью CS. SRC может, но не обязан, смешивать потоки RTP от разных участников перед отправкой на SRS. RTCP между SRC и SRS полностью независим от RTCP в CS.
The use of SRTP between the SRC and the SRS for the RS is independent of the use of SRTP between the UAs and SRC for the CS. Section 12 provides additional information on SRTP and keying mechanisms.
Использование SRTP между SRC и SRS для RS не зависит от использования SRTP между UA и SRC для CS. В разделе 12 приведена дополнительная информация о SRTP и механизмах управления ключами.
If packet loss occurs from the UA to the SRC, the SRC SHOULD detect and attempt to recover from the loss. If packet loss occurs from the SRC to the SRS, the SRS SHOULD detect and attempt to recover from the loss.
Если происходит потеря пакетов от UA к SRC, SRC СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё. Если происходит потеря пакетов от SRC к SRS, SRS СЛЕДУЕТ обнаруживать потерю и пытаться восстановиться после неё.
8.3. RTP Session Usage by SRC
8.3. Использование сеансов RTP в SRC
There are multiple ways that an SRC may choose to deliver recorded media to an SRS. In some cases, it may use a single RTP session for all media within the RS, whereas in others it may use multiple RTP sessions. The following subsections provide examples of basic RTP session usage by the SRC, including a discussion of how the RTP constructs and mechanisms covered previously are used. An SRC may choose to use one or more of the RTP session usages within a single RS. For the purpose of base interoperability between SRC and SRS, an SRC MUST support separate m-lines in SDP, one per CS media direction. The set of RTP session usages described is not meant to be exhaustive.
Существует несколько способов, которыми SRC может доставлять записываемые медиаданные на SRS. В некоторых случаях он может использовать один сеанс RTP для всех медиаданных в RS, в других — несколько сеансов RTP. В следующих подразделах приведены примеры базового использования сеансов RTP в SRC, включая обсуждение того, как используются рассмотренные ранее конструкции и механизмы RTP. SRC может выбрать использование одного или нескольких вариантов сеансов RTP в пределах одного RS. Для базовой совместимости между SRC и SRS SRC ДОЛЖЕН поддерживать отдельные m-строки в SDP, по одной на каждое направление медиаданных CS. Описанный набор вариантов использования сеансов RTP не претендует на исчерпывающий характер.
8.3.1. SRC Using Multiple m-lines
8.3.1. SRC с использованием нескольких m-строк
When using multiple m-lines, an SRC includes each m-line in an SDP offer to the SRS. The SDP answer from the SRS MUST include all m-lines, with any rejected m-lines indicated with a zero port, per [RFC3264]. Having received the answer, the SRC starts sending media to the SRS as indicated in the answer. Alternatively, if the SRC deems the level of support indicated in the answer to be unacceptable, it may initiate another SDP offer/answer exchange in which an alternative RTP session usage is negotiated. In order to preserve the mapping of media to participant within the CSs in the RS, the SRC SHOULD map each unique CNAME within the CSs to a unique CNAME within the RS. Additionally, the SRC SHOULD map each unique combination of CNAME/SSRC within the CSs to a unique CNAME/SSRC within the RS. In doing so, the SRC may act as an RTP translator or as an RTP endpoint.
При использовании нескольких m-строк SRC включает каждую m-строку в предложение SDP к SRS. Ответ SDP от SRS ДОЛЖЕН включать все m-строки, причём отклонённые m-строки указываются с нулевым портом согласно [RFC3264]. Получив ответ, SRC начинает отправку медиаданных на SRS, как указано в ответе. В качестве альтернативы, если SRC считает указанный в ответе уровень поддержки неприемлемым, он может инициировать другой обмен предложением/ответом SDP, в котором согласовывается иной вариант использования сеансов RTP. Чтобы сохранить сопоставление медиаданных участникам в CS в рамках RS, SRC СЛЕДУЕТ сопоставлять каждый уникальный CNAME в CS уникальному CNAME в RS. Кроме того, SRC СЛЕДУЕТ сопоставлять каждую уникальную комбинацию CNAME/SSRC в CS уникальной комбинации CNAME/SSRC в RS. Тем самым SRC может действовать как транслятор RTP или как конечная точка RTP.

8.3.2. SRC Using Mixing
8.3.2. SRC с использованием смешивания
When using mixing, the SRC combines RTP streams from different participants and sends them towards the SRS using its own SSRC. The SSRCs from the contributing participants SHOULD be conveyed as CSRC identifiers. The SRC includes one m-line for each RTP session in an SDP offer to the SRS. The SDP answer from the SRS MUST include all m-lines, with any rejected m-lines indicated with a zero port, per [RFC3264]. Having received the answer, the SRC starts sending media to the SRS as indicated in the answer.
При использовании смешивания SRC объединяет потоки RTP от разных участников и отправляет их в сторону SRS, используя собственный SSRC. SSRC вносящих вклад участников СЛЕДУЕТ передавать как идентификаторы CSRC. SRC включает по одной m-строке для каждого сеанса RTP в предложении SDP к SRS. Ответ SDP от SRS ДОЛЖЕН включать все m-строки, причём отклонённые m-строки указываются с нулевым портом согласно [RFC3264]. Получив ответ, SRC начинает отправку медиаданных на SRS, как указано в ответе.
In order to preserve the mapping of media to participant within the CSs in the RS, the SRC SHOULD map each unique CNAME within the CSs to a unique CNAME within the RS. Additionally, the SRC SHOULD map each unique combination of CNAME/SSRC within the CSs to a unique CNAME/SSRC within the RS. The SRC MUST avoid SSRC collisions, rewriting SSRCs if necessary when used as CSRCs in the RS. In doing so, the SRC acts as an RTP mixer.
Чтобы сохранить сопоставление медиаданных участникам в CS в рамках RS, SRC СЛЕДУЕТ сопоставлять каждый уникальный CNAME в CS уникальному CNAME в RS. Кроме того, SRC СЛЕДУЕТ сопоставлять каждую уникальную комбинацию CNAME/SSRC в CS уникальной комбинации CNAME/SSRC в RS. SRC ДОЛЖЕН избегать коллизий SSRC, при необходимости переписывая SSRC, когда они используются как CSRC в RS. Тем самым SRC действует как микшер RTP.
In the event that the SRS does not support this usage of CSRC values, it relies entirely on the SIPREC metadata to determine the participants included within each mixed stream.
В случае, если SRS не поддерживает такое использование значений CSRC, он полностью полагается на метаданные SIPREC для определения участников, включённых в каждый смешанный поток.

8.4. RTP Session Usage by SRS
8.4. Использование сеансов RTP в SRS
An SRS that supports recording an audio CS MUST support SRC usage of separate audio m-lines in SDP, one per CS media direction. An SRS that supports recording a video CS MUST support SRC usage of separate video m-lines in SDP, one per CS media direction. Therefore, for an SRS supporting a typical audio call, the SRS has to support receiving at least two audio m-lines. For an SRS supporting a typical audio and video call, the SRS has to support receiving at least four total m-lines in the SDP -- two audio m-lines and two video m-lines.
SRS, поддерживающий запись аудио-CS, ДОЛЖЕН поддерживать использование SRC отдельных аудио-m-строк в SDP, по одной на каждое направление медиаданных CS. SRS, поддерживающий запись видео-CS, ДОЛЖЕН поддерживать использование SRC отдельных видео-m-строк в SDP, по одной на каждое направление медиаданных CS. Поэтому для SRS, поддерживающего типичный аудиовызов, SRS должен поддерживать приём как минимум двух аудио-m-строк. Для SRS, поддерживающего типичный аудио- и видеовызов, SRS должен поддерживать приём как минимум четырёх m-строк в SDP -- двух аудио-m-строк и двух видео-m-строк.
These requirements allow an SRS to be implemented that supports video only, without requiring support for audio recording. They also allow an SRS to be implemented that supports recording only one direction of one stream in a CS -- for example, an SRS designed to record security monitoring cameras that only send (not receive) video without any audio. These requirements were not written to prevent other modes from being implemented and used, such as using a single m-line and mixing the separate audio streams together. Rather, the requirements were written to provide a common base mode to implement for the sake of interoperability. It is important to note that an SRS implementation supporting the common base mode may not record all media streams in a CS if a participant supports more than one m-line in a video call, such as one for camera and one for presentation. SRS implementations may support other modes as well, but they have to at least support the modes discussed above, such that they interoperate in the common base mode for basic interoperability.
Эти требования позволяют реализовать SRS, поддерживающий только видео, без необходимости поддержки записи аудио. Они также позволяют реализовать SRS, поддерживающий запись только одного направления одного потока в CS, — например, SRS, предназначенный для записи камер видеонаблюдения, которые только передают (не принимают) видео без аудио. Эти требования были написаны не для того, чтобы воспрепятствовать реализации и использованию других режимов, таких как использование одной m-строки и смешивание отдельных аудиопотоков вместе. Скорее, требования были написаны для того, чтобы предоставить общий базовый режим для реализации в целях совместимости. Важно отметить, что реализация SRS, поддерживающая общий базовый режим, может не записывать все медиапотоки в CS, если участник поддерживает более одной m-строки в видеовызове, например одну для камеры и одну для презентации. Реализации SRS могут поддерживать и другие режимы, но они должны как минимум поддерживать рассмотренные выше режимы, чтобы взаимодействовать в общем базовом режиме для базовой совместимости.
9. Metadata
9. Метаданные
Some metadata attributes are contained in SDP, and others are contained in a new content type called "application/rs-metadata". The format of the metadata is described as part of the mechanism in [RFC7865]. A new "disposition-type" of Content-Disposition is defined for the purpose of carrying metadata. The value is "recording-session", which indicates that the "application/rs-metadata" content contains metadata to be handled by the SRS.
Некоторые атрибуты метаданных содержатся в SDP, а другие содержатся в новом типе содержимого «application/rs-metadata». Формат метаданных описан как часть механизма в [RFC7865]. Для передачи метаданных определён новый «disposition-type» заголовка Content-Disposition. Его значение — «recording-session», которое указывает, что содержимое «application/rs-metadata» содержит метаданные, подлежащие обработке SRS.
9.1. Procedures at the SRC
9.1. Процедуры на SRC
The SRC MUST send metadata to the SRS in an RS. The SRC SHOULD send metadata as soon as it becomes available and whenever it changes. Cases in which an SRC may be justified in waiting temporarily before sending metadata include:
SRC ДОЛЖЕН отправлять метаданные на SRS в рамках RS. SRC СЛЕДУЕТ отправлять метаданные, как только они становятся доступны, и при каждом их изменении. Случаи, в которых SRC может быть оправдан во временной задержке перед отправкой метаданных, включают:
o waiting for a previous metadata exchange to complete (i.e., the SRC cannot send another SDP offer until the previous offer/answer completes and may also prefer not to send an UPDATE during this time).
o ожидание завершения предыдущего обмена метаданными (то есть SRC не может отправить другое предложение SDP, пока не завершится предыдущий обмен предложением/ответом, и может также предпочитать не отправлять UPDATE в это время).
o constraining the signaling rate on the RS.
o ограничение интенсивности сигнализации в RS.
o sending metadata when key events occur, rather than for every event that has any impact on metadata.
o отправка метаданных при наступлении ключевых событий, а не для каждого события, оказывающего какое-либо влияние на метаданные.
The SRC may also be configured to suppress certain metadata out of concern for privacy or perceived lack of need for it to be included in the recording.
SRC также может быть настроен на подавление определённых метаданных из соображений конфиденциальности или предполагаемого отсутствия необходимости включать их в запись.
Metadata sent by the SRC is categorized as either a full metadata snapshot or a partial update. A full metadata snapshot describes all metadata associated with the RS. The SRC MAY send a full metadata snapshot at any time. The SRC MAY send a partial update only if a full metadata snapshot has been sent previously. The SRC MAY send metadata (either a full metadata snapshot or a partial update) in an INVITE request, an UPDATE request [RFC3311], or a 200 response to an offerless INVITE from the SRS. If the metadata contains a reference to any SDP labels, the request containing the metadata MUST also contain an SDP offer that defines those labels.
Метаданные, отправляемые SRC, подразделяются на полный снимок метаданных или частичное обновление. Полный снимок метаданных описывает все метаданные, связанные с RS. SRC МОЖЕТ отправлять полный снимок метаданных в любой момент. SRC МОЖЕТ отправлять частичное обновление только в том случае, если полный снимок метаданных был отправлен ранее. SRC МОЖЕТ отправлять метаданные (как полный снимок метаданных, так и частичное обновление) в запросе INVITE, запросе UPDATE [RFC3311] или ответе 200 на INVITE без предложения от SRS. Если метаданные содержат ссылку на какие-либо метки SDP, запрос, содержащий метаданные, ДОЛЖЕН также содержать предложение SDP, определяющее эти метки.
When a SIP message contains both an SDP offer and metadata, the request body MUST have content type "multipart/mixed", with one subordinate body part containing the SDP offer and another containing the metadata. When a SIP message contains only an SDP offer or metadata, the "multipart/mixed" container is optional.
Когда сообщение SIP содержит и предложение SDP, и метаданные, тело запроса ДОЛЖНО иметь тип содержимого «multipart/mixed», причём одна подчинённая часть тела содержит предложение SDP, а другая — метаданные. Когда сообщение SIP содержит только предложение SDP или только метаданные, контейнер «multipart/mixed» не обязателен.
The SRC SHOULD include a full metadata snapshot in the initial INVITE request establishing the RS. If metadata is not yet available (e.g., an RS established in the absence of a CS), the SRC SHOULD send a full metadata snapshot as soon as metadata becomes available.
SRC СЛЕДУЕТ включать полный снимок метаданных в начальный запрос INVITE, устанавливающий RS. Если метаданные ещё недоступны (например, RS установлен при отсутствии CS), SRC СЛЕДУЕТ отправить полный снимок метаданных, как только метаданные станут доступны.

9.2. Procedures at the SRS
9.2. Процедуры на SRS
The SRS receives metadata updates from the SRC in INVITE and UPDATE requests. Since the SRC can send partial updates based on the previous update, the SRS needs to keep track of the sequence of updates from the SRC.
SRS получает обновления метаданных от SRC в запросах INVITE и UPDATE. Поскольку SRC может отправлять частичные обновления на основе предыдущего обновления, SRS должен отслеживать последовательность обновлений от SRC.
In the case of an internal failure at the SRS, the SRS may fail to recognize a partial update from the SRC. The SRS may be able to recover from the internal failure by requesting a full metadata snapshot from the SRC. Certain errors, such as syntax errors or semantic errors in the metadata information, are likely caused by an error on the SRC side, and it is likely that the same error will occur again even when a full metadata snapshot is requested. In order to avoid repeating the same error, the SRS can simply terminate the RS when a syntax error or semantic error is detected in the metadata.
В случае внутреннего сбоя в SRS, SRS может не распознать частичное обновление от SRC. SRS может восстановиться после внутреннего сбоя, запросив у SRC полный снимок метаданных. Некоторые ошибки, такие как синтаксические или семантические ошибки в информации метаданных, вероятно, вызваны ошибкой на стороне SRC, и, вероятно, та же ошибка возникнет снова, даже если запрошен полный снимок метаданных. Чтобы избежать повторения одной и той же ошибки, SRS может просто завершить RS при обнаружении синтаксической или семантической ошибки в метаданных.
The SRS MAY explicitly request a full metadata snapshot by sending an UPDATE request. This request MUST contain a body with Content-Disposition type "recording-session" and MUST NOT contain an SDP body. The SRS MUST NOT request a full metadata snapshot in an UPDATE response or in any other SIP transaction. 10. Persistent Recording
10. Постоянная запись
Persistent recording is a specific use case addressing REQ-005 in [RFC6341], where an RS can be established in the absence of a CS. The SRC continuously records media in an RS to the SRS even in the absence of a CS for all UAs that are part of persistent recording. By allocating recorded streams and continuously sending recorded media to the SRS, the SRC does not have to prepare new recorded streams with a new SDP offer when a new CS is created and also does not impact the timing of the CS. The SRC only needs to update the metadata when new CSs are created.
Постоянная запись — это отдельный вариант использования, отвечающий на REQ-005 в [RFC6341], когда RS может быть установлен при отсутствии CS. SRC непрерывно записывает медиаданные в RS на SRS даже при отсутствии CS для всех UA, входящих в состав постоянной записи. Выделяя записываемые потоки и непрерывно отправляя записанные медиаданные на SRS, SRC не должен готовить новые записываемые потоки с новым предложением SDP при создании нового CS и не влияет на временные параметры CS. SRC нужно только обновлять метаданные при создании новых CS.
When there is no CS running on the devices with persistent recording, there is no recorded media to stream from the SRC to the SRS. In certain environments where a Network Address Translator (NAT) is used, a minimum amount of flow activity is typically required to maintain the NAT binding for each port opened. Agents that support Interactive Connectivity Establishment (ICE) solve this problem. For non-ICE agents, in order not to lose the NAT bindings for the RTP/RTCP ports opened for the recorded streams, the SRC and SRS SHOULD follow the recommendations provided in [RFC6263] to maintain the NAT bindings.
Когда на устройствах с постоянной записью не выполняется ни один CS, нет записанных медиаданных для передачи от SRC к SRS. В некоторых средах, где используется преобразователь сетевых адресов (NAT), обычно требуется минимальная активность потока, чтобы поддерживать привязку NAT для каждого открытого порта. Агенты, поддерживающие установление интерактивного соединения (ICE), решают эту проблему. Для агентов, не поддерживающих ICE, чтобы не потерять привязки NAT для портов RTP/RTCP, открытых для записываемых потоков, SRC и SRS СЛЕДУЕТ следовать рекомендациям, приведённым в [RFC6263], для поддержания привязок NAT.

12. Security Considerations
12. Вопросы безопасности
The RS is fundamentally a standard SIP dialog [RFC3261]; therefore, the RS can reuse any of the existing SIP security mechanisms available for securing the session signaling, the recorded media, and the metadata. The use cases and requirements document [RFC6341] outlines the general security considerations, and this document describes specific security recommendations.
RS по своей сути является стандартным диалогом SIP [RFC3261]; поэтому RS может повторно использовать любые существующие механизмы безопасности SIP, доступные для защиты сигнализации сеанса, записываемых медиаданных и метаданных. Документ с вариантами использования и требованиями [RFC6341] описывает общие вопросы безопасности, а настоящий документ описывает конкретные рекомендации по безопасности.
The SRC and SRS MUST support SIP with Transport Layer Security (TLS) version 1.2, SHOULD follow the best practices when using TLS as per [RFC7525], and MAY use Session Initiation Protocol Secure (SIPS) with TLS as per [RFC5630]. The RS MUST be at least as secure as the CS; this means using at least the same strength of cipher suite as the CS if the CS is secured. For example, if the CS uses SIPS for signaling and RTP/SAVP for media, then the RS may not use SIP or plain RTP unless other equivalent security measures are in effect, since doing so would mean an effective security downgrade. Examples of other potentially equivalent security mechanisms include mutually authenticated TLS for the RS signaling channel or an appropriately protected network path for the RS media component.
SRC и SRS ДОЛЖНЫ поддерживать SIP с протоколом Transport Layer Security (TLS) версии 1.2, СЛЕДУЕТ следовать лучшим практикам при использовании TLS согласно [RFC7525] и МОЖНО использовать Session Initiation Protocol Secure (SIPS) с TLS согласно [RFC5630]. RS ДОЛЖЕН быть как минимум столь же защищённым, как CS; это означает использование как минимум той же стойкости набора шифров, что и в CS, если CS защищён. Например, если CS использует SIPS для сигнализации и RTP/SAVP для медиаданных, то RS не может использовать SIP или незащищённый RTP, если не действуют другие эквивалентные меры безопасности, поскольку это означало бы фактическое понижение уровня безопасности. Примеры других потенциально эквивалентных механизмов безопасности включают взаимно аутентифицированный TLS для канала сигнализации RS или надлежащим образом защищённый сетевой путь для медиакомпонента RS.
12.1. Authentication and Authorization
12.1. Аутентификация и авторизация
At the transport level, the RS uses TLS authentication to validate the authenticity of the SRC and SRS. The SRC and SRS MUST implement TLS mutual authentication for establishing the RS. Whether the SRC/SRS chooses to use TLS mutual authentication is a deployment decision. In deployments where a UA acts as its own SRC, this requires that the UA have its own certificate as needed for TLS mutual authentication. In deployments where the SRC and the SRS are in the same administrative domain and have some other means of assuring authenticity, the SRC and SRS may choose not to authenticate each other or to have the SRC authenticate the SRS only. In deployments where the SRS can be hosted on a different administrative domain, it is important to perform mutual authentication to ensure the authenticity of both the SRC and the SRS before transmitting any recorded media. The risk of not authenticating the SRS is that the recording may be sent to an entity other than the intended SRS, allowing a sensitive call recording to be received by an attacker. On the other hand, the risk of not authenticating the SRC is that an SRS will accept calls from an unknown SRC and allow potential forgery of call recordings.
На транспортном уровне RS использует аутентификацию TLS для проверки подлинности SRC и SRS. SRC и SRS ДОЛЖНЫ реализовать взаимную аутентификацию TLS для установления RS. Выбор того, использовать ли взаимную аутентификацию TLS, является решением при развёртывании. В развёртываниях, где UA действует как собственный SRC, это требует наличия у UA собственного сертификата, необходимого для взаимной аутентификации TLS. В развёртываниях, где SRC и SRS находятся в одном административном домене и имеют какие-либо иные средства обеспечения подлинности, SRC и SRS могут решить не аутентифицировать друг друга или ограничиться аутентификацией SRS со стороны SRC. В развёртываниях, где SRS может размещаться в другом административном домене, важно выполнять взаимную аутентификацию, чтобы убедиться в подлинности как SRC, так и SRS, прежде чем передавать какие-либо записанные медиаданные. Риск отсутствия аутентификации SRS состоит в том, что запись может быть отправлена не предполагаемому SRS, а иному объекту, что позволит злоумышленнику получить конфиденциальную запись вызова. С другой стороны, риск отсутствия аутентификации SRC состоит в том, что SRS примет вызовы от неизвестного SRC и допустит потенциальную подделку записей вызовов.
There may be scenarios in which the signaling between the SRC and SRS is not direct, e.g., a SIP proxy exists between the SRC and the SRS. In such scenarios, each hop is subject to the TLS mutual authentication constraint, and transitive trust at each hop is utilized. Additionally, an SRC or SRS may use other existing SIP mechanisms available, including, but not limited to, Digest authentication [RFC3261], asserted identity [RFC3325], and connected identity [RFC4916].
Могут быть сценарии, в которых сигнализация между SRC и SRS не является прямой, например между SRC и SRS существует прокси SIP. В таких сценариях каждый переход подчиняется требованию взаимной аутентификации TLS и используется транзитивное доверие на каждом переходе. Кроме того, SRC или SRS могут использовать другие доступные существующие механизмы SIP, включая, помимо прочего, дайджест-аутентификацию [RFC3261], заявленную идентичность [RFC3325] и подключённую идентичность [RFC4916].
The SRS may have its own set of recording policies to authorize recording requests from the SRC. The use of recording policies is outside the scope of the Session Recording Protocol.
SRS может иметь собственный набор политик записи для авторизации запросов записи от SRC. Использование политик записи находится вне области применения протокола записи сеансов.
12.2. RTP Handling
12.2. Работа с RTP
In many scenarios, it will be critical for the media transported between the SRC and the SRS to be protected. Media encryption is an important element in the overall SIPREC solution; therefore, the SRC and the SRS MUST support RTP/SAVP [RFC3711] and RTP/SAVPF [RFC5124]. RTP/SAVP and RTP/SAVPF provide media encryption, integrity protection, replay protection, and a limited form of source authentication. They do not contain or require a specific keying mechanism. At a minimum, the SRC and SRS MUST support the SDP security descriptions key negotiation mechanism [RFC4568]. For cases in which Datagram Transport Layer Security for Secure RTP (DTLS-SRTP) is used to encrypt a CS media stream, an SRC may use SRTP Encrypted Key Transport (EKT) [EKT-SRTP] in order to use SRTP-SDES in the RS without needing to re-encrypt the media.
Во многих сценариях будет критически важно защитить медиаданные, передаваемые между SRC и SRS. Шифрование медиаданных является важным элементом общего решения SIPREC; поэтому SRC и SRS ДОЛЖНЫ поддерживать RTP/SAVP [RFC3711] и RTP/SAVPF [RFC5124]. RTP/SAVP и RTP/SAVPF обеспечивают шифрование медиаданных, защиту целостности, защиту от повторного воспроизведения и ограниченную форму аутентификации источника. Они не содержат и не требуют конкретного механизма управления ключами. Как минимум SRC и SRS ДОЛЖНЫ поддерживать механизм согласования ключей с использованием описаний безопасности SDP [RFC4568]. В случаях, когда для шифрования медиапотока CS используется Datagram Transport Layer Security для Secure RTP (DTLS-SRTP), SRC может использовать SRTP Encrypted Key Transport (EKT) [EKT-SRTP], чтобы применять SRTP-SDES в RS без необходимости повторного шифрования медиаданных.
Note: When using EKT in this manner, it is possible for participants in the CS to send traffic that appears to be from other participants and have this forwarded by the SRC to the SRS within the RS. If this is a concern (e.g., the RS is intended for audit or compliance purposes), EKT is not an appropriate choice.
Примечание: при таком использовании EKT участники CS могут отправлять трафик, который выглядит как трафик других участников, и SRC пересылает его на SRS в рамках RS. Если это вызывает опасения (например, RS предназначен для аудита или целей соответствия), EKT не является подходящим выбором.
When RTP/SAVP or RTP/SAVPF is used, an SRC can choose to use the same keys or different keys in the RS than those used in the CS. Some SRCs are designed to simply replicate RTP packets from a CS media stream to the SRS, in which case the SRC will use the same key in the RS as the key used in the CS. In this case, the SRC MUST secure the SDP containing the keying material in the RS with at least the same level of security as in the CS. The risk of lowering the level of security in the RS is that it will effectively become a downgrade attack on the CS, since the same key is used for both the CS and the RS.
Когда используется RTP/SAVP или RTP/SAVPF, SRC может выбрать использование в RS тех же ключей, что и в CS, или других ключей. Некоторые SRC предназначены для простого реплицирования пакетов RTP из медиапотока CS на SRS; в этом случае SRC будет использовать в RS тот же ключ, что и в CS. В этом случае SRC ДОЛЖЕН защитить SDP, содержащий ключевой материал в RS, как минимум с тем же уровнем безопасности, что и в CS. Риск снижения уровня безопасности в RS состоит в том, что это фактически станет атакой понижения для CS, поскольку один и тот же ключ используется и в CS, и в RS.
SRCs that decrypt an encrypted CS media stream and re-encrypt it when sending it to the SRS MUST use a different key than what is used for the CS media stream, to ensure that it is not possible for someone who has the key for the CS media stream to access recorded data they are not authorized to access. In order to maintain a comparable level of security, the key used in the RS SHOULD be of equivalent strength to, or greater strength than, that used in the CS.
SRC, которые расшифровывают зашифрованный медиапоток CS и повторно шифруют его при отправке на SRS, ДОЛЖНЫ использовать ключ, отличный от используемого для медиапотока CS, чтобы исключить возможность доступа лица, имеющего ключ для медиапотока CS, к записанным данным, на которые оно не имеет права. Чтобы поддерживать сопоставимый уровень безопасности, ключ, используемый в RS, СЛЕДУЕТ применять эквивалентной или большей стойкости, чем используемый в CS.
12.3. Metadata
12.3. Метаданные
Metadata contains sensitive information, such as the address of record of the participants and other extension data placed by the SRC. It is essential to protect the content of the metadata in the RS. Since metadata is a content type transmitted in SIP signaling, metadata SHOULD be protected at the transport level by SIPS/TLS.
Метаданные содержат конфиденциальную информацию, такую как адрес записи участников и другие данные расширений, размещённые SRC. Крайне важно защищать содержимое метаданных в RS. Поскольку метаданные являются типом содержимого, передаваемым в сигнализации SIP, метаданные СЛЕДУЕТ защищать на транспортном уровне с помощью SIPS/TLS.
12.4. Storage and Playback
12.4. Хранение и воспроизведение
While storage and playback of the call recording are beyond the scope of this document, it is worthwhile to mention here that it is also important for the recording storage and playback to provide a level of security that is comparable to the CS. It would defeat the purpose of securing both the CS and the RS mentioned in the previous sections if the recording can be easily played back with a simple, unsecured HTTP interface without any form of authentication or authorization.
Хотя хранение и воспроизведение записи вызова выходят за область применения настоящего документа, здесь стоит упомянуть, что также важно обеспечить для хранения и воспроизведения записи уровень безопасности, сопоставимый с CS. Цель защиты как CS, так и RS, упомянутых в предыдущих разделах, была бы обесценена, если бы запись можно было легко воспроизвести через простой незащищённый интерфейс HTTP без какой-либо аутентификации или авторизации.
