Abstract
Аннотация
This document specifies an extension to the Session Initiation Protocol (SIP) providing reliable provisional response messages. This extension uses the option tag 100rel and defines the Provisional Response ACKnowledgement (PRACK) method.
Настоящая спецификация определяет расширение протокола инициирования сессий (SIP), обеспечивающее надёжную передачу предварительных ответных сообщений. Это расширение использует тег опции 100rel и определяет метод PRACK (Provisional Response ACKnowledgement).
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) (RFC 3261 [1]) is a request- response protocol for initiating and managing communications sessions. SIP defines two types of responses, provisional and final. Final responses convey the result of the request processing, and are sent reliably. Provisional responses provide information on the progress of the request processing, but are not sent reliably in RFC 3261.
Протокол инициирования сессий (Session Initiation Protocol, SIP) (RFC 3261 [1]) — это протокол «запрос-ответ» для инициирования и управления сессиями связи. SIP определяет два типа ответов: предварительные и окончательные. Окончательные ответы передают результат обработки запроса и передаются надёжно. Предварительные ответы предоставляют информацию о ходе обработки запроса, но в RFC 3261 не передаются надёжно.
It was later observed that reliability was important in several cases, including interoperability scenarios with the PSTN. Therefore, an optional capability was needed to support reliable transmission of provisional responses. That capability is provided in this specification.
Позднее было замечено, что надёжность важна в ряде случаев, включая сценарии взаимодействия с ТфОП. Поэтому потребовалась необязательная возможность поддержки надёжной передачи предварительных ответов. Эта возможность предоставляется настоящей спецификацией.
The reliability mechanism works by mirroring the current reliability mechanisms for 2xx final responses to INVITE. Those requests are transmitted periodically by the Transaction User (TU) until a separate transaction, ACK, is received that indicates reception of the 2xx by the UAC. The reliability for the 2xx responses to INVITE and ACK messages are end-to-end. In order to achieve reliability for provisional responses, we do nearly the same thing. Reliable provisional responses are retransmitted by the TU with an exponential backoff. Those retransmissions cease when a PRACK message is received. The PRACK request plays the same role as ACK, but for provisional responses. There is an important difference, however. PRACK is a normal SIP message, like BYE. As such, its own reliability is ensured hop-by-hop through each stateful proxy. Also like BYE, but unlike ACK, PRACK has its own response. If this were not the case, the PRACK message could not traverse proxy servers compliant to RFC 2543 [4].
Механизм надёжности работает путём зеркального отражения текущих механизмов надёжности для окончательных ответов 2xx на INVITE. Эти запросы периодически передаются Пользователем Транзакции (Transaction User, TU) до тех пор, пока не будет получена отдельная транзакция ACK, указывающая на получение 2xx пользовательским агентом-клиентом (UAC). Механизм надёжности ответов 2xx на INVITE и сообщений ACK является сквозным. Чтобы достичь надёжности для предварительных ответов, мы делаем почти то же самое. Надёжные предварительные ответы повторно передаются TU с экспоненциальной задержкой. Эти повторные передачи прекращаются при получении сообщения PRACK. Запрос PRACK играет ту же роль, что и ACK, но для предварительных ответов. Однако есть важное различие. PRACK — это обычное сообщение SIP, такое как BYE. Как таковое, его собственная надёжность обеспечивается поэтапно (hop-by-hop) через каждый прокси с сохранением состояния. Также как BYE, но в отличие от ACK, PRACK имеет свой собственный ответ. Если бы это было не так, сообщение PRACK не могло бы проходить через прокси-серверы, совместимые с RFC 2543 [4].
Each provisional response is given a sequence number, carried in the RSeq header field in the response. The PRACK messages contain an RAck header field, which indicates the sequence number of the provisional response that is being acknowledged. The acknowledgments are not cumulative, and the specifications recommend a single outstanding provisional response at a time, for purposes of congestion control.
Каждому предварительному ответу присваивается порядковый номер, передаваемый в поле заголовка RSeq ответа. Сообщения PRACK содержат поле заголовка RAck, которое указывает порядковый номер подтверждаемого предварительного ответа. Подтверждения не являются кумулятивными, и спецификации рекомендуют иметь единовременно один неподтверждённый предварительный ответ в целях управления перегрузкой.

3. UAS Behavior
3. Поведение UAS
A UAS MAY send any non-100 provisional response to INVITE reliably, so long as the initial INVITE request (the request whose provisional response is being sent reliably) contained a Supported header field with the option tag 100rel. While this specification does not allow reliable provisional responses for any method but INVITE, extensions that define new methods that can establish dialogs may make use of the mechanism.
Сервер UAS МОЖЕТ отправлять любой предварительный ответ, кроме 100, на INVITE надёжно, если только исходный запрос INVITE (запрос, на который надёжно отправляется предварительный ответ) содержал поле заголовка Supported с тегом опции 100rel. Хотя настоящая спецификация не допускает надёжных предварительных ответов ни для какого метода, кроме INVITE, расширения, определяющие новые методы, способные устанавливать диалоги, могут использовать этот механизм.
The UAS MUST send any non-100 provisional response reliably if the initial request contained a Require header field with the option tag 100rel. If the UAS is unwilling to do so, it MUST reject the initial request with a 420 (Bad Extension) and include an Unsupported header field containing the option tag 100rel.
Сервер UAS ДОЛЖЕН надёжно отправлять любой предварительный ответ, кроме 100, если исходный запрос содержал поле заголовка Require с тегом опции 100rel. Если сервер UAS не желает этого делать, он ДОЛЖЕН отклонить исходный запрос ответом 420 (Bad Extension) и включить поле заголовка Unsupported содержащим тег опции 100rel.
A UAS MUST NOT attempt to send a 100 (Trying) response reliably. Only provisional responses numbered 101 to 199 may be sent reliably. If the request did not include either a Supported or Require header field indicating this feature, the UAS MUST NOT send the provisional response reliably.
Сервер UAS НЕ ДОЛЖЕН пытаться отправлять ответ 100 (Trying) надёжно. Надёжно могут отправляться только предварительные ответы с номерами от 101 до 199. Если запрос не содержал ни поля заголовка Supported, ни Require, указывающего на эту возможность, сервер UAS НЕ ДОЛЖЕН отправлять предварительный ответ надёжно.
100 (Trying) responses are hop-by-hop only. For this reason, the reliability mechanisms described here, which are end-to-end, cannot be used.
Ответы 100 (Trying) передаются только между соседними узлами. По этой причине описанные здесь механизмы надёжности, являющиеся сквозными, не могут быть использованы.
An element that can act as a proxy can also send reliable provisional responses. In this case, it acts as a UAS for purposes of that transaction. However, it MUST NOT attempt to do so for any request that contains a tag in the To field. That is, a proxy cannot generate reliable provisional responses to requests sent within the context of a dialog. Of course, unlike a UAS, when the proxy element receives a PRACK that does not match any outstanding reliable provisional response, the PRACK MUST be proxied.
Элемент, способный действовать как прокси, также может отправлять надёжные предварительные ответы. В этом случае он действует как UAS для целей этой транзакции. Однако он НЕ ДОЛЖЕН пытаться делать это для любого запроса, содержащего тег в поле To. То есть прокси не может генерировать надёжные предварительные ответы на запросы, отправленные в контексте диалога. Разумеется, в отличие от UAS, когда элемент-прокси получает PRACK, не соответствующий ни одному неподтверждённому надёжному предварительному ответу, PRACK ДОЛЖЕН быть передан прокси.
There are several reasons why a UAS might want to send a reliable provisional response. One reason is if the INVITE transaction will take some time to generate a final response. As discussed in Section 13.3.1.1 of RFC 3261, the UAS will need to send periodic provisional responses to request an "extension" of the transaction at proxies. The requirement is that a proxy receive them every three minutes, but the UAS needs to send them more frequently (once a minute is recommended) because of the possibility of packet loss. As a more efficient alternative, the UAS can send the response reliably, in which case the UAS SHOULD send provisional responses once every two and a half minutes. Use of reliable provisional responses for extending transactions is RECOMMENDED.
Есть несколько причин, по которым сервер UAS может пожелать отправлять надёжный предварительный ответ. Одна из причин — когда для генерации окончательного ответа по транзакции INVITE требуется некоторое время. Как обсуждается в разделе 13.3.1.1 RFC 3261, серверу UAS потребуется отправлять периодические предварительные ответы для запроса «расширения» серверу UAS нужно отправлять их чаще (рекомендуется раз в минуту) из-за возможности потери пакетов. В качестве более эффективной альтернативы сервер UAS может отправлять ответ надёжно, и в этом случае UAS СЛЕДУЕТ отправлять предварительные ответы раз в две с половиной минуты. Использование надёжных предварительных ответов для продления транзакций РЕКОМЕНДУЕТСЯ.
The rest of this discussion assumes that the initial request contained a Supported or Require header field listing 100rel, and that there is a provisional response to be sent reliably.
Остальная часть этого обсуждения предполагает, что исходный запрос содержал поле заголовка Supported или Require с указанием 100rel и что есть предварительный ответ, который нужно отправить надёжно.
The provisional response to be sent reliably is constructed by the UAS core according to the procedures of Section 8.2.6 of RFC 3261. In addition, it MUST contain a Require header field containing the option tag 100rel, and MUST include an RSeq header field. The value of the header field for the first reliable provisional response in a transaction MUST be between 1 and 2**31 - 1. It is RECOMMENDED that it be chosen uniformly in this range. The RSeq numbering space is within a single transaction. This means that provisional responses for different requests MAY use the same values for the RSeq number.
Предварительный ответ, который нужно отправить надёжно, формируется ядром UAS согласно процедурам раздела 8.2.6 RFC 3261. Кроме того, он ДОЛЖЕН содержать поле заголовка Require с тегом опции 100rel и ДОЛЖЕН включать поле заголовка RSeq. Значение поля заголовка для первого надёжного предварительного ответа в транзакции ДОЛЖНО находиться между 1 и 2**31 - 1. РЕКОМЕНДУЕТСЯ выбирать его равномерно в этом диапазоне. Пространство нумерации RSeq ограничено рамками одной транзакции. Это означает, что предварительные ответы на разные запросы МОГУТ использовать одни и те же значения номера RSeq.
The reliable provisional response MAY contain a body. The usage of session descriptions is described in Section 5.
Надёжный предварительный ответ МОЖЕТ содержать тело. Использование описаний сессий описано в разделе 5.
The reliable provisional response is passed to the transaction layer periodically with an interval that starts at T1 seconds and doubles for each retransmission (T1 is defined in Section 17 of RFC 3261). Once passed to the server transaction, it is added to an internal list of unacknowledged reliable provisional responses. The transaction layer will forward each retransmission passed from the UAS core.
Надёжный предварительный ответ периодически передаётся уровню транзакций с интервалом, который начинается с T1 секунд и удваивается при каждой повторной передаче (T1 определён в разделе 17 RFC 3261). После передачи серверной транзакции он добавляется во внутренний список неподтверждённых надёжных предварительных ответов. Уровень транзакций будет пересылать каждую повторную передачу, переданную от ядра UAS.
This differs from retransmissions of 2xx responses, whose intervals cap at T2 seconds. This is because retransmissions of ACK are triggered on receipt of a 2xx, but retransmissions of PRACK take place independently of reception of 1xx.
This differs from retransmissions of 2xx responses, whose intervals cap at T2 seconds. This is because retransmissions of ACK are triggered on receipt of a 2xx, but retransmissions of PRACK take place independently of reception of 1xx.
Retransmissions of the reliable provisional response cease when a matching PRACK is received by the UA core. PRACK is like any other request within a dialog, and the UAS core processes it according to the procedures of Sections 8.2 and 12.2.2 of RFC 3261. A matching PRACK is defined as one within the same dialog as the response, and whose method, CSeq-num, and response-num in the RAck header field match, respectively, the method from the CSeq, the sequence number from the CSeq, and the sequence number from the RSeq of the reliable provisional response. If a PRACK request is received by the UA core that does not match any unacknowledged reliable provisional response, the UAS MUST respond to the PRACK with a 481 response. If the PRACK does match an unacknowledged reliable provisional response, it MUST be responded to with a 2xx response. The UAS can be certain at this point that the provisional response has been received in order. It SHOULD cease retransmissions of the reliable provisional response, and MUST remove it from the list of unacknowledged provisional responses.
Повторные передачи надёжного предварительного ответа прекращаются, когда ядро UA получает соответствующий PRACK. PRACK подобен любому другому запросу в диалоге, и ядро UAS обрабатывает его согласно процедурам разделов 8.2 и 12.2.2 RFC 3261. Соответствующий PRACK определяется как тот, который находится в том же диалоге, что и ответ, и у которого метод, CSeq-num и response-num в поле заголовка RAck совпадают соответственно с методом из CSeq, порядковым номером из CSeq и порядковым номером из RSeq надёжного предварительного ответа. Если ядро UA получает запрос PRACK, не соответствующий ни одному неподтверждённому надёжному предварительному ответу, сервер UAS ДОЛЖЕН ответить на PRACK ответом 481. Если PRACK действительно соответствует неподтверждённому надёжному предварительному ответу, на него ДОЛЖНО быть дано 2xx-ответ. Сервер UAS может на этом этапе быть уверен, что предварительный ответ получен по порядку. Ему СЛЕДУЕТ прекратить повторные передачи надёжного предварительного ответа и ДОЛЖЕН удалить его из списка неподтверждённых предварительных ответов.
If a reliable provisional response is retransmitted for 64*T1 seconds without reception of a corresponding PRACK, the UAS SHOULD reject the original request with a 5xx response.
Если надёжный предварительный ответ повторно передаётся в течение 64*T1 секунд без получения соответствующего PRACK, серверу UAS СЛЕДУЕТ отклонить исходный запрос 5xx-ответом.
If the PRACK contained a session description, it is processed as described in Section 5 of this document. If the PRACK instead contained any other type of body, the body is treated in the same way that body in an ACK would be treated.
Если PRACK содержал описание сессии, оно обрабатывается, как описано в разделе 5 настоящего документа. Если PRACK содержал тело любого иного типа, тело обрабатывается так же, как обрабатывалось бы тело в ACK.
After the first reliable provisional response for a request has been acknowledged, the UAS MAY send additional reliable provisional responses. The UAS MUST NOT send a second reliable provisional response until the first is acknowledged. After the first, it is RECOMMENDED that the UAS not send an additional reliable provisional response until the previous is acknowledged. The first reliable provisional response receives special treatment because it conveys the initial sequence number. If additional reliable provisional responses were sent before the first was acknowledged, the UAS could not be certain these were received in order.
После того как первый надёжный предварительный ответ на запрос подтверждён, сервер UAS МОЖЕТ отправлять дополнительные надёжные предварительные ответы. Сервер UAS НЕ ДОЛЖЕН отправлять второй надёжный предварительный ответ до тех пор, пока не подтверждён первый. После первого РЕКОМЕНДУЕТСЯ, чтобы сервер UAS не отправлял дополнительный надёжный предварительный ответ до подтверждения предыдущего. Первый надёжный предварительный ответ получает особое обращение, поскольку он передаёт начальный порядковый номер. Если бы дополнительные надёжные предварительные ответы были отправлены до подтверждения первого, сервер UAS не мог бы быть уверен, что они получены по порядку.
The value of the RSeq in each subsequent reliable provisional response for the same request MUST be greater by exactly one. RSeq numbers MUST NOT wrap around. Because the initial one is chosen to be less than 2**31 - 1, but the maximum is 2**32 - 1, there can be up to 2**31 reliable provisional responses per request, which is more than sufficient.
Значение RSeq в каждом последующем надёжном предварительном ответе на тот же запрос ДОЛЖНО быть больше ровно на единицу. Номера RSeq НЕ ДОЛЖНЫ зацикливаться. Поскольку начальное значение выбирается меньше 2**31 - 1, а максимум равен 2**32 - 1, может быть до 2**31 надёжных предварительных ответов на запрос, что более чем достаточно.
The UAS MAY send a final response to the initial request before having received PRACKs for all unacknowledged reliable provisional responses, unless the final response is 2xx and any of the unacknowledged reliable provisional responses contained a session description. In that case, it MUST NOT send a final response until those provisional responses are acknowledged. If the UAS does send a final response when reliable responses are still unacknowledged, it SHOULD NOT continue to retransmit the unacknowledged reliable provisional responses, but it MUST be prepared to process PRACK requests for those outstanding responses. A UAS MUST NOT send new reliable provisional responses (as opposed to retransmissions of unacknowledged ones) after sending a final response to a request.
Сервер UAS МОЖЕТ отправить окончательный ответ на исходный запрос до получения PRACK на все неподтверждённые надёжные предварительные ответы, если только окончательный ответ не является 2xx и ни один из неподтверждённых надёжных предварительных ответов не содержал описания сессии. В этом случае он НЕ ДОЛЖЕН отправлять окончательный ответ до подтверждения этих предварительных ответов. Если сервер UAS всё же отправляет окончательный ответ, когда надёжные ответы ещё не подтверждены, ему НЕ СЛЕДУЕТ продолжать повторные передачи неподтверждённых надёжных предварительных ответов, но он ДОЛЖЕН быть готов обрабатывать запросы PRACK на эти неподтверждённые ответы. Сервер UAS НЕ ДОЛЖЕН отправлять новые надёжные предварительные ответы (в отличие от повторных передач неподтверждённых) после отправки окончательного ответа на запрос.
4. UAC Behavior
4. Поведение UAC
When the UAC creates a new request, it can insist on reliable delivery of provisional responses for that request. To do that, it inserts a Require header field with the option tag 100rel into the request. A Require header with the value 100rel MUST NOT be present in any requests excepting INVITE, although extensions to SIP may allow its usage with other request methods.
Когда UAC создаёт новый запрос, он может настаивать на надёжной доставке предварительных ответов на этот запрос. Для этого он вставляет в запрос поле заголовка Require с тегом опции 100rel. Заголовок Require со значением 100rel НЕ ДОЛЖЕН присутствовать ни в каких запросах, кроме INVITE, хотя расширения SIP могут разрешать его использование с другими методами запросов.

If the UAC does not wish to insist on usage of reliable provisional responses, but merely indicate that it supports them if the UAS needs to send one, a Supported header MUST be included in the request with the option tag 100rel. The UAC SHOULD include this in all INVITE requests.
Если UAC не желает настаивать на использовании надёжных предварительных ответов, а лишь указывает, что он их поддерживает, если серверу UAS потребуется отправить один, в запрос ДОЛЖЕН быть включён заголовок Supported с тегом опции 100rel. UAC СЛЕДУЕТ включать его во все запросы INVITE.
If a provisional response is received for an initial request, and that response contains a Require header field containing the option tag 100rel, the response is to be sent reliably. If the response is a 100 (Trying) (as opposed to 101 to 199), this option tag MUST be ignored, and the procedures below MUST NOT be used. The provisional response MUST establish a dialog if one is not yet created.
Если на исходный запрос получен предварительный ответ и этот ответ содержит поле заголовка Require с тегом опции 100rel, ответ должен быть отправлен надёжно. Если ответ является 100 (Trying) (в отличие от 101–199), этот тег опции ДОЛЖЕН игнорироваться, и применяются процедуры ниже Предварительный ответ ДОЛЖЕН устанавливать диалог, если он ещё не создан.
Assuming the response is to be transmitted reliably, the UAC MUST create a new request with method PRACK. This request is sent within the dialog associated with the provisional response (indeed, the provisional response may have created the dialog). PRACK requests MAY contain bodies, which are interpreted according to their type and disposition.
Предполагая, что ответ должен быть передан надёжно, UAC ДОЛЖЕН создать новый запрос с методом PRACK. Этот запрос отправляется в пределах диалога, связанного с предварительным ответом (более того, предварительный ответ мог создать этот диалог). Запросы PRACK МОГУТ содержать тела, которые интерпретируются согласно их типу и назначению.
Note that the PRACK is like any other non-INVITE request within a dialog. In particular, a UAC SHOULD NOT retransmit the PRACK request when it receives a retransmission of the provisional response being acknowledged, although doing so does not create a protocol error.
Обратите внимание, что PRACK подобен любому другому запросу, не являющемуся INVITE, в пределах диалога. В частности, UAC НЕ СЛЕДУЕТ повторно передавать запрос PRACK при получении повторной передачи подтверждаемого предварительного ответа, хотя это не создаёт ошибки протокола.
Once a reliable provisional response is received, retransmissions of that response MUST be discarded. A response is a retransmission when its dialog ID, CSeq, and RSeq match the original response. The UAC MUST maintain a sequence number that indicates the most recently received in-order reliable provisional response for the initial request. This sequence number MUST be maintained until a final response is received for the initial request. Its value MUST be initialized to the RSeq header field in the first reliable provisional response received for the initial request.
После получения надёжного предварительного ответа повторные передачи этого ответа ДОЛЖНЫ отбрасываться. Ответ является повторной передачей, когда его идентификатор диалога, CSeq и RSeq совпадают с исходным ответом. UAC ДОЛЖЕН поддерживать порядковый номер, указывающий последний полученный по порядку надёжный предварительный ответ на исходный запрос. Этот порядковый номер ДОЛЖЕН поддерживаться до получения окончательного ответа на исходный запрос. Его значение ДОЛЖНО инициализироваться значением поля заголовка RSeq в первом надёжном предварительном ответе, полученном на исходный запрос.
Handling of subsequent reliable provisional responses for the same initial request follows the same rules as above, with the following difference: reliable provisional responses are guaranteed to be in order. As a result, if the UAC receives another reliable provisional response to the same request, and its RSeq value is not one higher than the value of the sequence number, that response MUST NOT be acknowledged with a PRACK, and MUST NOT be processed further by the UAC. An implementation MAY discard the response, or MAY cache the response in the hopes of receiving the missing responses.
Обработка последующих надёжных предварительных ответов на тот же исходный запрос следует тем же правилам, что и выше, со следующим отличием: надёжные предварительные ответы гарантированно приходят по порядку. В результате, если UAC получает другой надёжный предварительный ответ на тот же запрос и его значение RSeq не на единицу больше значения порядкового номера, этот ответ НЕ ДОЛЖЕН подтверждаться посредством PRACK и НЕ ДОЛЖЕН обрабатываться UAC далее. Реализация МОЖЕТ отбросить ответ либо МОЖЕТ кэшировать его в надежде получить недостающие ответы.
The UAC MAY acknowledge reliable provisional responses received after the final response or MAY discard them.
UAC МОЖЕТ подтверждать надёжные предварительные ответы, полученные после окончательного ответа, либо МОЖЕТ отбрасывать их.
5. The Offer/Answer Model and PRACK
5. Модель offer/answer и PRACK
RFC 3261 describes guidelines for the sets of messages in which offers and answers [3] can appear. Based on those guidelines, this extension provides additional opportunities for offer/answer exchanges.
RFC 3261 описывает руководящие принципы для наборов сообщений, в которых могут появляться предложения (offers) и ответы (answers) [3]. Основываясь на этих принципах, данное расширение предоставляет дополнительные возможности для обмена offer/answer.
If the INVITE contained an offer, the UAS MAY generate an answer in a reliable provisional response (assuming these are supported by the UAC). That results in the establishment of the session before completion of the call. Similarly, if a reliable provisional response is the first reliable message sent back to the UAC, and the INVITE did not contain an offer, one MUST appear in that reliable provisional response.
Если INVITE содержал предложение, сервер UAS МОЖЕТ сгенерировать ответ в надёжном предварительном ответе (при условии, что они поддерживаются UAC). Это приводит к установлению сессии до завершения вызова. Аналогично, если надёжный предварительный ответ является первым надёжным сообщением, отправленным обратно UAC, и INVITE не содержал предложения, одно ДОЛЖНО появиться в этом надёжном предварительном ответе.
If the UAC receives a reliable provisional response with an offer (this would occur if the UAC sent an INVITE without an offer, in which case the first reliable provisional response will contain the offer), it MUST generate an answer in the PRACK. If the UAC receives a reliable provisional response with an answer, it MAY generate an additional offer in the PRACK. If the UAS receives a PRACK with an offer, it MUST place the answer in the 2xx to the PRACK.
Если UAC получает надёжный предварительный ответ с предложением (это произошло бы, если UAC отправил INVITE без предложения, и тогда первый надёжный предварительный ответ будет содержать предложение), он ДОЛЖЕН сгенерировать ответ в PRACK. Если UAC получает надёжный предварительный ответ, который не содержит предложения и не является ответом на ранее отправленное предложение, UAC не должен генерировать ответ, поскольку обмен offer/answer в этом случае не происходит.
Once an answer has been sent or received, the UA SHOULD establish the session based on the parameters of the offer and answer, even if the original INVITE itself has not been responded to.
Как только ответ отправлен или получен, UA СЛЕДУЕТ установить сессию на основе параметров предложения и ответа, даже если на исходный INVITE ещё не дан ответ.
If the UAS had placed a session description in any reliable provisional response that is unacknowledged when the INVITE is accepted, the UAS MUST delay sending the 2xx until the provisional response is acknowledged. Otherwise, the reliability of the 1xx cannot be guaranteed, and reliability is needed for proper operation of the offer/answer exchange.
Если сервер UAS поместил описание сессии в какой-либо надёжный предварительный ответ, который остаётся неподтверждённым при принятии INVITE, сервер UAS ДОЛЖЕН задержать отправку 2xx до подтверждения предварительного ответа. Иначе надёжность 1xx не может быть гарантирована, а надёжность требуется для правильной работы обмена предложение/ответ.
All user agents that support this extension MUST support all offer/answer exchanges that are possible based on the rules in Section 13.2 of RFC 3261, based on the existence of INVITE and PRACK as requests, and 2xx and reliable 1xx as non-failure reliable responses.
Все пользовательские агенты, поддерживающие это расширение, ДОЛЖНЫ поддерживать все обмены offer/answer, возможные на основе правил раздела 13.2 RFC 3261, исходя из существования INVITE и PRACK как запросов, а 2xx и надёжного 1xx — как надёжных ответов, не являющихся отказами.

7.2. RAck
7.2. RAck
The RAck header is sent in a PRACK request to support reliability of provisional responses. It contains two numbers and a method tag. The first number is the value from the RSeq header in the provisional response that is being acknowledged. The next number, and the method, are copied from the CSeq in the response that is being acknowledged. The method name in the RAck header is case sensitive.
Заголовок RAck отправляется в запросе PRACK для поддержки надёжности предварительных ответов. Он содержит два числа и тег метода. Этот заголовок позволяет серверу UAS точно определить, какой именно предварительный ответ подтверждается.

9. Security Considerations
9. Вопросы безопасности
The PRACK request can be injected by attackers to force retransmissions of reliable provisional responses to cease. As these responses can convey important information, PRACK messages SHOULD be authenticated as any other request. Authentication procedures are specified in RFC 3261.
Запрос PRACK может быть внедрён злоумышленниками, чтобы принудительно прекратить повторные передачи надёжных предварительных ответов. Поскольку эти ответы могут передавать важную информацию, сообщения PRACK СЛЕДУЕТ аутентифицировать, как и любой другой запрос. Процедуры аутентификации определены в RFC 3261.
