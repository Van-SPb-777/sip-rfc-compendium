Abstract
Аннотация
This memo describes how to use TLS to secure HTTP connections over the Internet. Current practice is to layer HTTP over SSL (the predecessor to TLS), distinguishing secured traffic from insecure traffic by the use of a different server port. This document documents that practice using TLS. A companion document describes a method for using HTTP/TLS over the same port as normal HTTP [RFC2817].
Настоящий меморандум описывает, как использовать TLS для защиты соединений HTTP в Интернете. Текущая практика состоит в том, чтобы использовать HTTP поверх SSL (предшественника TLS), для чего обычно используется порт 443. Настоящий документ описывает, как использовать HTTP поверх TLS, включая вопросы идентификации сервера и клиента, закрытия соединения и обработки ошибок. Сопутствующий документ описывает способ использования HTTP/TLS на том же порту, что и обычный HTTP [RFC2817].
1. Introduction
1. Введение
HTTP [RFC2616] was originally used in the clear on the Internet. However, increased use of HTTP for sensitive applications has required security measures. SSL, and its successor TLS [RFC2246] were designed to provide channel-oriented security. This document describes how to use HTTP over TLS.
HTTP [RFC2616] изначально использовался в Интернете в открытом виде. Однако возросшее использование HTTP для чувствительных приложений потребовало мер безопасности. SSL и его преемник TLS [RFC2246] были разработаны для обеспечения безопасности, ориентированной на канал. Настоящий документ описывает, как использовать HTTP поверх TLS.

2. HTTP Over TLS
2. HTTP поверх TLS
Conceptually, HTTP/TLS is very simple. Simply use HTTP over TLS precisely as you would use HTTP over TCP.
Концептуально HTTP/TLS очень прост. Просто используйте HTTP поверх TLS точно так же, как вы используете HTTP поверх TCP.
2.1. Connection Initiation
2.1. Инициирование соединения
The agent acting as the HTTP client should also act as the TLS client. It should initiate a connection to the server on the appropriate port and then send the TLS ClientHello to begin the TLS handshake. When the TLS handshake has finished. The client may then initiate the first HTTP request. All HTTP data MUST be sent as TLS "application data". Normal HTTP behavior, including retained connections should be followed.
Агент, выступающий в качестве HTTP-клиента, должен также выступать в качестве TLS-клиента. Он должен инициировать соединение с сервером на соответствующем порту и затем отправить TLS ClientHello, чтобы начать рукопожатие TLS. После завершения рукопожатия TLS клиент может инициировать первый HTTP-запрос. Все данные HTTP ДОЛЖНЫ передаваться как «application data» TLS. Следует соблюдать обычное поведение HTTP, включая постоянные соединения.
2.2. Connection Closure
2.2. Закрытие соединения
TLS provides a facility for secure connection closure. When a valid closure alert is received, an implementation can be assured that no further data will be received on that connection. TLS implementations MUST initiate an exchange of closure alerts before closing a connection. A TLS implementation MAY, after sending a closure alert, close the connection without waiting for the peer to send its closure alert, generating an "incomplete close". Note that an implementation which does this MAY choose to reuse the session. This SHOULD only be done when the application knows (typically through detecting HTTP message boundaries) that it has received all the message data that it cares about.
TLS предоставляет средство безопасного закрытия соединения. При получении действительного предупреждения о закрытии реализация может быть уверена, что по этому соединению больше не будет получено данных. Реализации TLS ДОЛЖНЫ инициировать обмен предупреждениями о закрытии перед закрытием соединения. Реализация TLS МОЖЕТ после отправки предупреждения о закрытии закрыть соединение, не дожидаясь, пока партнёр отправит своё предупреждение о закрытии, создавая «незавершённое закрытие». Обратите внимание, что реализация, поступающая так, МОЖЕТ выбрать повторное использование сессии. Это СЛЕДУЕТ делать только тогда, когда приложение знает (обычно посредством обнаружения границ сообщений HTTP), что оно получило все данные сообщения, которые для него важны.
As specified in [RFC2246], any implementation which receives a connection close without first receiving a valid closure alert (a "premature close") MUST NOT reuse that session. Note that a premature close does not call into question the security of the data already received, but simply indicates that subsequent data might have been truncated. Because TLS is oblivious to HTTP request/response boundaries, it is necessary to examine the HTTP data itself (specifically the Content-Length header) to determine whether the truncation occurred inside a message or between messages.
Как указано в [RFC2246], любая реализация, получающая закрытие соединения без предварительного получения действительного предупреждения о закрытии («преждевременное закрытие»), НЕ ДОЛЖНА повторно использовать эту сессию. Обратите внимание, что преждевременное закрытие не ставит под сомнение безопасность уже полученных данных, а лишь указывает на то, что последующие данные могли быть усечены. Поскольку TLS не учитывает границы HTTP-запросов и ответов, необходимо исследовать сами данные HTTP (в частности, заголовок Content-Length), чтобы определить, произошло ли усечение внутри сообщения или между сообщениями.
2.2.1. Client Behavior
2.2.1. Поведение клиента
Because HTTP uses connection closure to signal end of server data, client implementations MUST treat any premature closes as errors and the data received as potentially truncated. While in some cases the HTTP protocol allows the client to find out whether truncation took place so that, if it received the complete reply, it may tolerate such errors following the principle to "[be] strict when sending and tolerant when receiving" [RFC1958], often truncation does not show in the HTTP protocol data; two cases in particular deserve special note:
Поскольку HTTP использует закрытие соединения для сигнализации об окончании данных сервера, реализации клиента ДОЛЖНЫ рассматривать любые преждевременные закрытия как ошибки, а полученные данные — как потенциально усечённые. Хотя в некоторых случаях протокол HTTP позволяет клиенту выяснить, произошло ли усечение, так что при получении полного ответа он может допустить такие ошибки, следуя принципу «[быть] строгим при отправке и терпимым при приёме» [RFC1958], часто усечение не проявляется в данных протокола HTTP; два случая заслуживают особого упоминания:
A HTTP response without a Content-Length header. Since data length in this situation is signalled by connection close a premature close generated by the server cannot be distinguished from a spurious close generated by an attacker.
HTTP-ответ без заголовка Content-Length. Поскольку длина данных в этой ситуации сигнализируется закрытием соединения, преждевременное закрытие, сгенерированное сервером, невозможно отличить от ложного закрытия, сгенерированного злоумышленником.
A HTTP response with a valid Content-Length header closed before all data has been read. Because TLS does not provide document oriented protection, it is impossible to determine whether the server has miscomputed the Content-Length or an attacker has truncated the connection.
HTTP-ответ с действительным заголовком Content-Length, закрытый до того, как все данные были прочитаны. Поскольку TLS не обеспечивает защиты, ориентированной на документ, невозможно определить, неправильно ли сервер вычислил Content-Length или злоумышленник усек соединение.
There is one exception to the above rule. When encountering a premature close, a client SHOULD treat as completed all requests for which it has received as much data as specified in the Content-Length header.
Из вышеуказанного правила есть одно исключение. При обнаружении преждевременного закрытия клиенту СЛЕДУЕТ считать завершёнными все запросы, для которых он получил столько данных, сколько указано в заголовке Content-Length.
A client detecting an incomplete close SHOULD recover gracefully. It MAY resume a TLS session closed in this fashion.
Клиент, обнаруживший незавершённое закрытие, СЛЕДУЕТ корректно восстановиться. Он МОЖЕТ возобновить сессию TLS, закрытую таким образом.
Clients MUST send a closure alert before closing the connection. Clients which are unprepared to receive any more data MAY choose not to wait for the server's closure alert and simply close the connection, thus generating an incomplete close on the server side.
Клиенты ДОЛЖНЫ отправлять предупреждение о закрытии перед закрытием соединения. Клиенты, не готовые принимать больше данных, МОЖУТ выбрать не ждать предупреждения о закрытии от сервера и просто закрыть соединение, создавая тем самым незавершённое закрытие на стороне сервера.
2.2.2. Server Behavior
2.2.2. Поведение сервера
RFC 2616 permits an HTTP client to close the connection at any time, and requires servers to recover gracefully. In particular, servers SHOULD be prepared to receive an incomplete close from the client, since the client can often determine when the end of server data is. Servers SHOULD be willing to resume TLS sessions closed in this fashion.
RFC 2616 позволяет HTTP-клиенту закрыть соединение в любое время и требует от серверов корректного восстановления. В частности, серверы СЛЕДУЕТ быть готовы к получению незавершённого закрытия от клиента, поскольку клиент часто может определить, когда наступает конец данных сервера. Серверы СЛЕДУЕТ быть готовы возобновлять сессии TLS, закрытые таким образом.
Implementation note: In HTTP implementations which do not use persistent connections, the server ordinarily expects to be able to signal end of data by closing the connection. When Content-Length is used, however, the client may have already sent the closure alert and dropped the connection.
Примечание по реализации. В реализациях HTTP, не использующих постоянные соединения, сервер обычно рассчитывает на возможность сигнализировать об окончании данных путём закрытия соединения. Однако когда используется Content-Length, клиент может уже отправить предупреждение о закрытии и разорвать соединение.
Servers MUST attempt to initiate an exchange of closure alerts with the client before closing the connection. Servers MAY close the connection after sending the closure alert, thus generating an incomplete close on the client side.
Серверы ДОЛЖНЫ пытаться инициировать обмен предупреждениями о закрытии с клиентом перед закрытием соединения. Серверы МОГУТ закрыть соединение после отправки предупреждения о закрытии, создавая тем самым незавершённое закрытие на стороне клиента.
2.3. Port Number
2.3. Номер порта
The first data that an HTTP server expects to receive from the client is the Request-Line production. The first data that a TLS server (and hence an HTTP/TLS server) expects to receive is the ClientHello. Consequently, common practice has been to run HTTP/TLS over a separate port in order to distinguish which protocol is being used. When HTTP/TLS is being run over a TCP/IP connection, the default port is 443. This does not preclude HTTP/TLS from being run over another transport. TLS only presumes a reliable connection-oriented data stream.
Первые данные, которые HTTP-сервер ожидает получить от клиента, — это продукция Request-Line. Первые данные, которые ожидает получить TLS-сервер (и, следовательно, HTTP/TLS-сервер), — это ClientHello. Поэтому общепринятой практикой стало запускать HTTP/TLS на отдельном порту, чтобы различать, какой протокол используется. Когда HTTP/TLS работает поверх TCP/IP-соединения, портом по умолчанию является порт 443.
2.4. URI Format
2.4. Формат URI
HTTP/TLS is differentiated from HTTP URIs by using the 'https' protocol identifier in place of the 'http' protocol identifier. An example URI specifying HTTP/TLS is:
HTTP/TLS отличается от HTTP-URI использованием идентификатора протокола «https» вместо идентификатора протокола «http». Пример URI, задающего HTTP/TLS:
https://www.example.com/~smith/home.html
https://www.example.com/~smith/home.html
3. Endpoint Identification
3. Идентификация конечной точки
3.1. Server Identity
3.1. Идентичность сервера
In general, HTTP/TLS requests are generated by dereferencing a URI. As a consequence, the hostname for the server is known to the client. If the hostname is available, the client MUST check it against the server's identity as presented in the server's Certificate message, in order to prevent man-in-the-middle attacks.
В общем случае HTTP/TLS-запросы генерируются путём разыменования URI. Как следствие, имя хоста сервера известно клиенту. Если имя хоста доступно, клиент ДОЛЖЕН проверить его соответствие идентичности сервера, представленной в сообщении Certificate сервера, чтобы предотвратить атаки «человек посередине».
If the client has external information as to the expected identity of the server, the hostname check MAY be omitted. (For instance, a client may be connecting to a machine whose address and hostname are dynamic but the client knows the certificate that the server will present.) In such cases, it is important to narrow the scope of acceptable certificates as much as possible in order to prevent man in the middle attacks. In special cases, it may be appropriate for the client to simply ignore the server's identity, but it must be understood that this leaves the connection open to active attack.
Если у клиента есть внешняя информация о предполагаемой идентичности сервера, проверка имени хоста МОЖЕТ быть опущена. (Например, клиент может подключаться к машине, чей адрес и имя хоста динамичны, но клиент знает сертификат, который представит сервер.) В таких случаях важно максимально сузить область допустимых сертификатов, чтобы предотвратить атаки «человек посередине». В особых случаях клиенту может быть уместно просто игнорировать идентичность сервера, но необходимо понимать, что это оставляет соединение открытым для активной атаки.
If a subjectAltName extension of type dNSName is present, that MUST be used as the identity. Otherwise, the (most specific) Common Name field in the Subject field of the certificate MUST be used. Although the use of the Common Name is existing practice, it is deprecated and Certification Authorities are encouraged to use the dNSName instead.
Если присутствует расширение subjectAltName типа dNSName, оно ДОЛЖНО использоваться как идентичность. В противном случае ДОЛЖНО использоваться поле Common Name (наиболее конкретное) в поле Subject сертификата. Хотя использование Common Name является существующей практикой, она устарела, и Центрам сертификации рекомендуется использовать dNSName вместо неё.
Matching is performed using the matching rules specified by [RFC2459]. If more than one identity of a given type is present in the certificate (e.g., more than one dNSName name, a match in any one of the set is considered acceptable.) Names may contain the wildcard character * which is considered to match any single domain name component or component fragment. E.g., *.a.com matches foo.a.com but not bar.foo.a.com. f*.com matches foo.com but not bar.com.
Сопоставление выполняется с использованием правил сопоставления, указанных в [RFC2459]. Если в сертификате присутствует более одной идентичности заданного типа (например, более одного имени dNSName), совпадение с любым из набора считается приемлемым. Имена могут содержать символ шаблона *, который считается совпадающим с любым отдельным компонентом доменного имени или фрагментом компонента. Например, *.a.com соответствует foo.a.com, но не bar.foo.a.com. f*.com соответствует foo.com, но не bar.com.
In some cases, the URI is specified as an IP address rather than a hostname. In this case, the iPAddress subjectAltName must be present in the certificate and must exactly match the IP in the URI.
В некоторых случаях URI задаётся как IP-адрес, а не как имя хоста. В этом случае в сертификате должен присутствовать iPAddress subjectAltName, и он должен точно совпадать с IP в URI.
If the hostname does not match the identity in the certificate, user oriented clients MUST either notify the user (clients MAY give the user the opportunity to continue with the connection in any case) or terminate the connection with a bad certificate error. Automated clients MUST log the error to an appropriate audit log (if available) and SHOULD terminate the connection (with a bad certificate error). Automated clients MAY provide a configuration setting that disables this check, but MUST provide a setting which enables it.
Если имя хоста не совпадает с идентичностью в сертификате, ориентированные на пользователя клиенты ДОЛЖНЫ либо уведомить пользователя (клиенты МОГУТ предоставить пользователю возможность продолжить соединение в любом случае), либо завершить соединение с ошибкой недействительного сертификата. Автоматические клиенты ДОЛЖНЫ регистрировать ошибку в соответствующем журнале аудита (если он доступен) и СЛЕДУЕТ завершить соединение (с ошибкой недействительного сертификата). Автоматические клиенты МОГУТ предоставлять параметр конфигурации, отключающий эту проверку, но ДОЛЖНЫ предоставлять параметр, её включающий.
Note that in many cases the URI itself comes from an untrusted source. The above-described check provides no protection against attacks where this source is compromised. For example, if the URI was obtained by clicking on an HTML page which was itself obtained without using HTTP/TLS, a man in the middle could have replaced the URI. In order to prevent this form of attack, users should carefully examine the certificate presented by the server to determine if it meets their expectations.
Обратите внимание, что во многих случаях сам URI поступает из ненадёжного источника. Описанная выше проверка не обеспечивает защиты от атак, где этот источник скомпрометирован. Например, если URI был получен щелчком на HTML-странице, которая сама была получена без использования HTTP/TLS, «человек посередине» мог заменить URI. Чтобы предотвратить эту форму атаки, пользователям следует внимательно изучать сертификат, представленный сервером, чтобы определить, соответствует ли он их ожиданиям.
3.2. Client Identity
3.2. Идентичность клиента
Typically, the server has no external knowledge of what the client's identity ought to be and so checks (other than that the client has a certificate chain rooted in an appropriate CA) are not possible. If a server has such knowledge (typically from some source external to HTTP or TLS) it SHOULD check the identity as described above. References
Обычно у сервера нет внешних знаний о том, какой должна быть идентичность клиента, и потому проверки (кроме той, что цепочка сертификатов клиента имеет корень в соответствующем ЦС) невозможны. Если у сервера есть такие знания (обычно из некоего источника, внешнего по отношению к HTTP или TLS), ему СЛЕДУЕТ проверить идентичность, как описано выше.
