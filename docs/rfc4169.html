Abstract
Аннотация
HTTP Digest, as specified in RFC 2617, is known to be vulnerable to man-in-the-middle attacks if the client fails to authenticate the server in TLS, or if the same passwords are used for authentication in some other context without TLS. This is a general problem that exists not just with HTTP Digest, but also with other IETF protocols that use tunneled authentication. This document specifies version 2 of the HTTP Digest AKA algorithm (RFC 3310). This algorithm can be implemented in a way that it is resistant to the man-in-the-middle attack.
HTTP-дайджест, как указано в RFC 2617, как известно, уязвим для атак «человек посередине», если клиенту не удается аутентифицировать сервер в TLS или если те же пароли используются для аутентификации в каком-либо другом контексте без TLS. Это общая проблема, которая существует не только в HTTP Digest, но и в других протоколах IETF, использующих туннельную аутентификацию. В этом документе указана версия 2 алгоритма HTTP Digest AKA (RFC 3310). Этот алгоритм можно реализовать таким образом, чтобы он был устойчив к атаке «человек посередине».
1. Introduction
1. Введение
The Hypertext Transfer Protocol (HTTP) Digest Authentication, described in [4], has been extended in [6] to support the Authentication and Key Agreement (AKA) mechanism [7]. The AKA mechanism performs authentication and session key agreement in Universal Mobile Telecommunications System (UMTS) networks. HTTP Digest AKA enables the usage of AKA as a one-time password generation mechanism for Digest authentication.
Дайджест-аутентификация протокола передачи гипертекста (HTTP), описанная в [4], была расширена в [6] для поддержки механизма аутентификации и соглашения о ключах (AKA) [7]. Механизм AKA выполняет аутентификацию и согласование ключей сессии в сетях универсальной системы мобильной связи (UMTS). HTTP Digest AKA позволяет использовать AKA в качестве механизма создания одноразового пароля для аутентификации Digest.
HTTP Digest is known to be vulnerable to man-in-the-middle attacks, even when run inside TLS, if the same HTTP Digest authentication credentials are used in some other context without TLS. The attacker may initiate a TLS session with a server, and when the server challenges the attacker with HTTP Digest, the attacker masquerades the server to the victim. If the victim responds to the challenge, the attacker is able to use this response towards the server in HTTP Digest. Note that this attack is an instance of a general attack that affects a number of IETF protocols, such as PIC. The general problem is discussed in [8] and [9].
Известно, что HTTP Digest уязвим для атак «человек посередине», даже при запуске внутри TLS, если те же учетные данные аутентификации HTTP Digest используются в каком-либо другом контексте без TLS. Злоумышленник может инициировать сессия TLS с сервером, и когда сервер отправляет злоумышленнику вызов с помощью HTTP-дайджеста, злоумышленник маскирует сервер под жертву. Если жертва отвечает на запрос, злоумышленник может использовать этот ответ по отношению к серверу в HTTP-дайджесте. Обратите внимание, что эта атака является примером общей атаки, которая затрагивает ряд протоколов IETF, таких как PIC. Общая проблема обсуждается в [8] и [9].
Because of the vulnerability described above, the use of HTTP Digest "AKAv1" should be limited to the situations in which the client is able to demonstrate that, in addition to the AKA response, it possesses the AKA session keys. This is possible, for example, if the underlying security protocol uses the AKA-generated session keys to protect the authentication response. This is the case, for example, in the 3GPP IP Multimedia Core Network Subsystem (IMS), where HTTP Digest "AKAv1" is currently applied. However, HTTP Digest "AKAv1" should not be used with tunnelled security protocols that do not utilize the AKA session keys. For example, the use of HTTP Digest "AKAv1" is not necessarily secure with TLS if the server side is authenticated using certificates and the client side is authenticated using HTTP Digest AKA.
Из-за описанной выше уязвимости использование HTTP-дайджеста «AKAv1» следует ограничивать ситуациями, в которых клиент может продемонстрировать, что в дополнение к ответу AKA он обладает ключами сессии AKA. Это возможно, например, если базовый протокол безопасности использует сеансовые ключи AKA-generated для защиты ответа аутентификации. Это имеет место, например, в подсистеме базовой IP-мультимедийной сети (IMS) 3GPP, где в настоящее время применяется HTTP-дайджест «AKAv1». Однако HTTP Digest «AKAv1» не следует использовать с туннелируемыми протоколами безопасности, которые не используют сеансовые ключи AKA. Например, использование HTTP Digest «AKAv1» не обязательно безопасно с помощью TLS, если серверная часть аутентифицируется с использованием сертификатов, а клиентская сторона аутентифицируется с помощью HTTP Digest AKA.
There are at least four potential solutions to the problem:
Существует как минимум четыре возможных решения проблемы:
1. The use of the authentication credentials is limited to one application only. In general, this approach is good and can be recommended from the security point of view. However, this will increase the total number of authentication credentials for an end-user, and may cause scalability problems in the server side.
1. Использование учетных данных аутентификации ограничено только одним приложением. В целом этот подход хорош и его можно рекомендовать с точки зрения безопасности. Однако это увеличит общее количество учетных данных для аутентификации конечного пользователя и может вызвать проблемы с масштабируемостью на стороне сервера.
2. The keys used in the underlying security protocols are somehow bound to the keys used in the tunneled authentication protocol. However, this would cause problems with the current implementations of underlying security protocols. For example, it is not possible to use the session keys from TLS at the application layer. Furthermore, this solution would only solve the problem when HTTP Digest is used over one hop, and would leave the problem of using HTTP Digest via multiple hops (e.g., via proxy servers) unsolved.
2. Ключи, используемые в базовых протоколах безопасности, каким-то образом связаны с ключами, используемыми в туннельном протоколе аутентификации. Однако это может вызвать проблемы с текущими реализациями базовых протоколов безопасности. Например, невозможно использовать сеансовые ключи TLS на уровне приложения. Кроме того, это решение решит проблему только тогда, когда HTTP Digest используется на одном прыжке, и оставит проблему использования HTTP Digest через несколько прыжков (например, через прокси) нерешенной.
3. Authentication credentials are used in a cryptographically different way for each media and/or access network. However, it may be difficult to know which underlying media is used below the application.
3. Учетные данные аутентификации используются криптографически по-разному для каждой среды передачи и/или сети доступа. Однако может быть сложно определить, какой базовый носитель используется в приложении.
4. Authentication credentials are used in a cryptographically different way for each application.
4. Учетные данные аутентификации используются криптографически по-разному для каждого приложения.
This document specifies a new algorithm version for HTTP Digest AKA (i.e., "AKAv2"). "AKAv2" specifies a cryptographically different way to use AKA credentials in use cases that are based on either HTTP Digest authentication or UMTS authentication (cf. approach 4 above). The only difference to "AKAv1" is that, in addition to an AKA response RES, the AKA related session keys, IK and CK, are also used as the password for HTTP Digest. AKAv2 is immune to the man-in-the-middle attack described above. However, if AKAv2 is used in some environment, both with and without some underlying security, such as TLS, the problem still exists.
В этом документе указана новая версия алгоритма для HTTP Digest AKA (то есть, «AKAv2»). «AKAv2» определяет криптографически отличный способ использования учетных данных AKA в случаях использования, основанных либо на аутентификации HTTP Digest, либо на аутентификации UMTS (см. подход 4 выше). Единственное отличие от «AKAv1» заключается в том, что в дополнение к ответу RES AKA, связанные с AKA ключи сессии, IK и CK, также используются в качестве пароля для HTTP-дайджеста. AKAv2 невосприимчив к атаке «человек посередине», описанной выше. Однако если AKAv2 используется в какой-либо среде как с базовой безопасностью, так и без нее, например TLS, проблема все равно существует.
New HTTP Digest AKA algorithm versions can be registered with IANA, based on Expert Review. Documentation of new algorithm versions is not mandated as RFCs. However, "AKAv2" is documented as an RFC because the use of different AKA algorithm versions includes security implications of which the implementors should be aware. The extension version and security implications are presented in this document.
Новые версии алгоритма HTTP Digest AKA могут быть зарегистрированы в IANA на основании экспертной проверки. Документирование новых версий алгоритмов не является обязательным в качестве RFC. Однако «AKAv2» документируется как RFC, поскольку использование различных версий алгоритма AKA влечет за собой последствия для безопасности, о которых разработчики должны знать. Версия расширения и последствия для безопасности представлены в этом документе.

2. HTTP Digest AKAv2
2. HTTP-дайджест AKAV2
In general, the Digest AKAv2 operation is identical to the Digest AKAv1 operation described in [6]. This chapter specifies the parts in which Digest AKAv2 is different from Digest AKAv1 operation. The notation used in the Augmented BNF definitions for the new and modified syntax elements in this section is as used in SIP [5], and any elements not defined in this section are as defined in [6].
В целом операция Digest AKAv2 идентична операции Digest AKAv1, описанной в [6]. В этой главе указаны части, в которых Digest AKAv2 отличается от операции Digest AKAv1. Обозначения, используемые в определениях расширенного BNF для новых и измененных элементов синтаксиса в этом разделе, аналогичны используемым в SIP [5], а любые элементы, не определенные в этом разделе, соответствуют определению в [6].
In order to direct the client into using AKAv2 for authentication instead of other AKA versions or other HTTP Digest algorithms, the AKA version directive of [6] shall have the following new value:
Чтобы направить клиента на использование AKAv2 для аутентификации вместо других версий AKA или других алгоритмов HTTP-дайджеста, директива версии AKA из [6] должна иметь следующее новое значение:
aka-version = "AKAv2"
aka-version = "AKAv2"
The AKA version directive is used as a part of the algorithm field as defined in [6]. Example: algorithm=AKAv2-MD5
Директива версии AKA используется как часть поля алгоритма, как определено в [6]. Пример: алгоритм=AKAv2-MD5
2.1. Password Generation
2.1. Генерация пароля
The client shall use base64 encoded [1] parameters PRF(RES||IK||CK, "http-digest-akav2-password") as a "password" when calculating the HTTP Digest response directive for AKAv2.
Клиент должен использовать параметры PRF(RES||IK||CK, «http-digest-akav2-password») в кодировке Base64 [1] в качестве «password» при вычислении директивы ответа HTTP-дайджеста для AKAv2.
The server shall use base64 encoded [1] parameters PRF(XRES||IK||CK, "http-digest-akav2-password") as a "password" when checking the HTTP Digest response or when calculating the "response-auth" of the "Authentication-Info" header.
Сервер должен использовать параметры PRF(XRES||IK||CK, «http-digest-akav2-password») в кодировке Base64 [1] в качестве «password» при проверке ответа HTTP-дайджеста или при вычислении «response-auth» заголовка «Authentication-Info».
The pseudo-random function (PRF) used to construct the HTTP Digest password is equal to HMAC [2] using the hash algorithm that is used in producing the digest and the checksum. For example, if the algorithm is AKAv2-MD5, then the PRF is HMAC_MD5.
Псевдослучайная функция (PRF), используемая для создания пароля HTTP-дайджеста, равна HMAC [2] с использованием алгоритма хеширования, который используется при создании дайджеста и контрольной суммы. Например, если алгоритм — AKAv2-MD5, то PRF — HMAC_MD5.
The string "http-digest-akav2-password" included in the key derivation is case sensitive.
Строка «http-digest-akav2-password», включенная в производный ключ, чувствительна к регистру.
2.2. Session keys
2.2. Ключи сессии
Even though the HTTP Digest AKA framework does not specify the use of the session keys IK and CK for confidentiality and integrity protection, the keys may be used for creating additional security within HTTP authentication or some other security mechanism. However, the original session keys IK and CK MUST NOT be directly re-used for such additional security in "AKAv2". Instead, session keys IK' and CK' are derived from the original keys IK and CK in the following way: IK' = PRF(IK, "http-digest-akav2-integritykey") CK' = PRF(CK, "http-digest-akav2-cipherkey")
Несмотря на то, что структура HTTP Digest AKA не определяет использование сеансовых ключей IK и CK для защиты конфиденциальности и целостности, эти ключи могут использоваться для создания дополнительной безопасности в рамках аутентификации HTTP или какого-либо другого механизма безопасности. Однако исходные сеансовые ключи IK и CK НЕ ДОЛЖНЫ напрямую использоваться повторно для такой дополнительной безопасности в «AKAv2». Вместо этого сеансовые ключи IK' и CK' получаются из исходных ключей IK и CK следующим образом: IK' = PRF(IK, «http-digest-akav2-integritykey») CK' = PRF(CK, «http-digest-akav2-cipherkey»)
Any application using the HTTP authentication framework is allowed to use these masked session keys. The unmasked session keys MAY also be re-used in some other context if application-specific strings other than "http-digest-akav2-integritykey" or "http-digest-akav2-cipherkey" are used to mask the original session keys.
Любому приложению, использующему структуру аутентификации HTTP, разрешено использовать эти замаскированные ключи сессии. Немаскированные ключи сессии МОГУТ также повторно использоваться в каком-либо другом контексте, если для маскировки исходных ключей сессии используются специфичные для приложения строки, отличные от «http-digest-akav2-integritykey» или «http-digest-akav2-cipherkey».
The pseudo-random function (PRF) used to construct the HTTP Digest session keys is equal to HMAC [2] using the hash algorithm that is used in producing the digest and the checksum. For example, if the algorithm is AKAv2-MD5, then the PRF is HMAC_MD5. The algorithm MUST be used in the HMAC format, as defined in [2]. The strings "http-digest-akav2-integritykey" and "http-digest-akav2- cipherkey" included in the key derivation are case sensitive.
Псевдослучайная функция (PRF), используемая для создания ключей сессии HTTP-дайджеста, равна HMAC [2] с использованием алгоритма хеширования, который используется при создании дайджеста и контрольной суммы. Например, если алгоритм — AKAv2-MD5, то PRF — HMAC_MD5. Алгоритм ДОЛЖЕН использоваться в формате HMAC, как определено в [2]. Строки «http-digest-akav2-integritykey» и «http-digest-akav2-cipherkey», включенные в вывод ключа, чувствительны к регистру.
3. Example Digest AKAv2 Operation
3. Пример работы дайджеста AKAV2
This document does not introduce any changes to the operations of HTTP Digest or HTTP Digest AKA. Examples defined in [6] apply directly to AKAv2 with the following two exceptions:
Этот документ не вносит никаких изменений в работу HTTP Digest или HTTP Digest AKA. Примеры, определенные в [6], применимы непосредственно к AKAv2 со следующими двумя исключениями:
1. The algorithm directive has a prefix "AKAv2" instead of "AKAv1".
1. Директива алгоритма имеет префикс «AKAv2» вместо «AKAv1».
2. The HTTP Digest password is derived from base64 encoded PRF(RES|| IK||CK, "http-digest-akav2-password") or PRF(XRES||IK||CK, "http- digest-akav2-password") instead of (RES) or (XRES) respectively.
2. Пароль HTTP-дайджеста получается из PRF(RES|| IK||CK, «http-digest-akav2-password») или PRF(XRES||IK||CK, «http-digest-akav2-password») в кодировке Base64 вместо (RES) или (XRES) соответственно.
3. The optional session keys are derived from PRF(IK, "http-digest- akav2-integritykey") and PRF(CK, "http-digest-akav2-cipherkey") instead of IK and CK respectively.
3. Необязательные ключи сессии получаются из PRF(IK, «http-digest-akav2-integritykey») и PRF(CK, «http-digest-akav2-cipherkey») вместо IK и CK соответственно.
Note that the password in "AKAv1" is in binary format. The "AKAv2" password is base64 encoded [1].
Обратите внимание, что пароль в «AKAv1» имеет двоичный формат. Пароль «AKAv2» имеет кодировку Base64 [1].
4. Security Considerations
4. Вопросы безопасности
4.1. Multiple Authentication Schemes and Algorithms
4.1. Множественные схемы и алгоритмы аутентификации
The rules for a user agent for choosing among multiple authentication schemes and algorithms are as defined in [6], except that the user agent MUST choose "AKAv2" if both "AKAv1" and "AKAv2" are present.
Правила для пользовательского агента по выбору среди нескольких схем и алгоритмов аутентификации определены в [6], за исключением того, что пользовательский агент ДОЛЖЕН выбрать «AKAv2», если присутствуют оба «AKAv1» и «AKAv2».
Since HTTP Digest is known to be vulnerable for bidding-down attacks in environments where multiple authentication schemes and/or algorithms are used, the system implementors should pay special attention to scenarios in which both "AKAv1" and "AKAv2" are used. The use of both AKA algorithm versions should be avoided, especially if the AKA generated sessions keys or some other additional security measures to authenticate the clients (e.g., client certificates) are not used.
Поскольку известно, что HTTP-дайджест уязвим для атак с понижением ставок в средах, где используется несколько схем и/или алгоритмов аутентификации, разработчики системы должны уделять особое внимание сценариям, в которых используются как «AKAv1», так и «AKAv2». Следует избегать использования обеих версий алгоритма AKA, особенно если не используются сгенерированные AKA ключи сессий или какие-либо другие дополнительные меры безопасности для аутентификации клиентов (например, клиентские сертификаты).
4.2. Session Protection
4.2. Защита сессии
Even though "AKAv2" uses the additional integrity (IK) and confidentiality (CK) keys as a part of the HTTP Digest AKA password, these session keys may still be used for creating additional security within HTTP authentication or some other security mechanism. This recommendation is based on the assumption that algorithms used in HTTP Digest, such as MD5, are sufficiently strong one-way functions, and, consequently, HTTP Digest responses leak no or very little computational information about IK and CK. Furthermore, the session keys are masked into IK' and CK' before they can be used for session protection.
Несмотря на то, что «AKAv2» использует дополнительные ключи целостности (IK) и конфиденциальности (CK) как часть пароля HTTP Digest AKA, эти ключи сессии все равно могут использоваться для создания дополнительной безопасности в рамках аутентификации HTTP или какого-либо другого механизма безопасности. Эта рекомендация основана на предположении, что алгоритмы, используемые в HTTP Digest, такие как MD5, являются достаточно сильными односторонними функциями и, следовательно, ответы HTTP Digest не передают никакой или очень мало вычислительной информации о IK и CK. Более того, сеансовые ключи маскируются под IK' и CK', прежде чем их можно будет использовать для защиты сессии.
4.3. Man-in-the-Middle Attacks
4.3. Man-in-the-Middle Атаки
Reference [8] describes a "man-in-the-middle" attack related to tunnelled authentication protocols. The attack can occur in an EAP context or any similar contexts where tunnelled authentication is used and where the same authentication credentials are used without protection in some other context or the client fails to authenticate the server.
В ссылке [8] описана атака «man-in-the-middle», связанная с туннелируемыми протоколами аутентификации. Атака может произойти в контексте EAP или любых аналогичных контекстах, где используется туннельная аутентификация и где те же учетные данные аутентификации используются без защиты в каком-либо другом контексте или клиент не может аутентифицировать сервер.
For example, the use of TLS with HTTP Digest authentication (i.e., TLS for server authentication, and subsequent use of HTTP Digest for client authentication) is an instance of such scenario. HTTP challenges and responses can be fetched from and to different TLS tunnels without noticing their origin. The attack is especially easy to perform if the client fails to authenticate the server. If the same HTTP credentials are used with an unsecured connection, the attack is also easy to perform.
Например, использование TLS с аутентификацией HTTP Digest (то есть, TLS для аутентификации сервера и последующее использование HTTP Digest для аутентификации клиента) является примером такого сценария. Запросы и ответы HTTP можно получать из разных туннелей TLS и в них, не замечая их происхождения. Атаку особенно легко выполнить, если клиент не может аутентифицировать сервер. Если те же учетные данные HTTP используются при незащищенном соединении, атаку также легко осуществить.

4.4. Entropy
4.4. Энтропия
AKAv1 passwords should only be used as one-time passwords if the entropy of the used RES value is limited (e.g., only 32 bits). For this reason, the re-use of the same RES value in authenticating subsequent requests and responses is not recommended. Furthermore, algorithms such as "MD5-sess", which limit the amount of material hashed with a single key by producing a session key for authentication, should not be used with AKAv1.
Пароли AKAv1 следует использовать в качестве одноразовых паролей только в том случае, если энтропия используемого значения RES ограничена (например, только 32 бита). По этой причине повторное использование одного и того же значения RES при аутентификации последующих запросов и ответов не рекомендуется. Кроме того, с AKAv1 не следует использовать такие алгоритмы, как «MD5-sess», которые ограничивают объем материала, хешируемого с помощью одного ключа, путем создания сеансового ключа для аутентификации.
Passwords generated using AKAv2 can more securely be used for authenticating subsequent requests and responses because the concatenation of AKA credentials (i.e., RES||IK||CK) makes the passwords significantly longer, and the pseudo-random function heuristically provides an entropy equal to the length of this string, or the length of the PRF output, whichever is the shortest. The user agent does not need to assume that AKAv2 passwords are limited to one-time use only, and it may try to re-use the AKAv2 passwords with the server. However, note that AKAv2 passwords cannot be re-used with the HTTP Digest AKAv2 algorithm because such an authentication challenge will automatically generate a fresh password. AKAv2 passwords can be used with other HTTP Digest algorithms, such as "MD5".
Пароли, сгенерированные с помощью AKAv2, можно более безопасно использовать для аутентификации последующих запросов и ответов, поскольку объединение учетных данных AKA (то есть, RES||IK||CK) делает пароли значительно длиннее, а псевдослучайная функция эвристически обеспечивает энтропию, равную длине этой строки или длине вывода PRF, в зависимости от того, что является самым коротким. Пользовательскому агенту не нужно предполагать, что пароли AKAv2 ограничены только одноразовым использованием, и он может попытаться повторно использовать пароли AKAv2 на сервере. Однако обратите внимание, что пароли AKAv2 нельзя повторно использовать с алгоритмом HTTP Digest AKAv2, поскольку такой запрос аутентификации автоматически генерирует новый пароль. Пароли AKAv2 можно использовать с другими алгоритмами дайджеста HTTP, например «MD5».
The underlying AKA protocol (e.g., UMTS AKA) has been designed to keep CK and IK confidential, but will typically send RES in the clear. We note that, even if (by some unfortunate misuse of AKA) RES values were revealed, the inclusion of RES in PRF(RES||IK||CK) is still beneficial, as it makes pre-calculated dictionaries of IK||CK values rather useless (though such dictionaries are infeasible for typical sizes of IK and CK).
Базовый протокол AKA (например, UMTS AKA) был разработан для обеспечения конфиденциальности CK и IK, но обычно отправляет RES в открытом виде. Заметим, что даже если (из-за неудачного неправильного использования AKA) значения RES были обнаружены, включение RES в PRF(RES||IK||CK) все равно полезно, поскольку делает заранее рассчитанные словари значений IK||CK довольно бесполезными (хотя такие словари неосуществимы для типичных размеров IK и CK).
