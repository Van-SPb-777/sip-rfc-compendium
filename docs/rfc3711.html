Abstract
Аннотация
This document describes the Secure Real-time Transport Protocol (SRTP), a profile of the Real-time Transport Protocol (RTP), which can provide confidentiality, message authentication, and replay protection to the RTP traffic and to the control traffic for RTP, the Real-time Transport Control Protocol (RTCP).
Настоящий документ описывает протокол Secure Real-time Transport Protocol (SRTP) — профиль протокола Real-time Transport Protocol (RTP), который может обеспечивать конфиденциальность, аутентификацию сообщений и защиту от повторного воспроизведения для трафика RTP и для управляющего трафика RTP — протокола Real-time Transport Control Protocol (RTCP).
1. Introduction
1. Введение
This document describes the Secure Real-time Transport Protocol (SRTP), a profile of the Real-time Transport Protocol (RTP), which can provide confidentiality, message authentication, and replay protection to the RTP traffic and to the control traffic for RTP, RTCP (the Real-time Transport Control Protocol) [RFC3350].
Настоящий документ описывает протокол Secure Real-time Transport Protocol (SRTP) — профиль протокола Real-time Transport Protocol (RTP), который может обеспечивать конфиденциальность, аутентификацию сообщений и защиту от повторного воспроизведения для трафика RTP и для управляющего трафика RTP, RTCP (Real-time Transport Control Protocol) [RFC3350].
SRTP provides a framework for encryption and message authentication of RTP and RTCP streams (Section 3). SRTP defines a set of default cryptographic transforms (Sections 4 and 5), and it allows new transforms to be introduced in the future (Section 6). With appropriate key management (Sections 7 and 8), SRTP is secure (Sections 9) for unicast and multicast RTP applications (Section 11).
SRTP предоставляет основу для шифрования и аутентификации сообщений потоков RTP и RTCP (раздел 3). SRTP определяет набор криптографических преобразований по умолчанию (разделы 4 и 5) и допускает введение новых преобразований в будущем (раздел 6). При надлежащем управлении ключами (разделы 7 и 8) SRTP обеспечивает безопасность (раздел 9) для одноадресных и многоадресных приложений RTP (раздел 11).
SRTP can achieve high throughput and low packet expansion. SRTP proves to be a suitable protection for heterogeneous environments (mix of wired and wireless networks). To get such features, default transforms are described, based on an additive stream cipher for encryption, a keyed-hash based function for message authentication, and an "implicit" index for sequencing/synchronization based on the RTP sequence number for SRTP and an index number for Secure RTCP (SRTCP).
SRTP способен обеспечить высокую пропускную способность и малое расширение пакета. SRTP оказывается подходящей защитой для неоднородных сред (сочетание проводных и беспроводных сетей). Для получения таких свойств описаны преобразования по умолчанию, основанные на аддитивном потоковом шифре для шифрования, функции на основе ключевого хэша для аутентификации сообщений и «неявном» индексе для упорядочивания/синхронизации, основанном на порядковом номере RTP для SRTP и номере индекса для Secure RTCP (SRTCP).
1.1. Notational Conventions
1.1. Соглашения об обозначениях
The keywords "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119]. The terminology conforms to [RFC2828] with the following exception. For simplicity we use the term "random" throughout the document to denote randomly or pseudo-randomly generated values. Large amounts of random bits may be difficult to obtain, and for the security of SRTP, pseudo-randomness is sufficient [RFC1750].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны интерпретироваться так, как описано в [RFC2119]. Терминология соответствует [RFC2828] со следующим исключением. Для простоты мы используем термин «случайный» на протяжении всего документа для обозначения случайно или псевдослучайно сгенерированных значений. Большие объёмы случайных битов может быть трудно получить, а для безопасности SRTP достаточно псевдослучайности [RFC1750].
By convention, the adopted representation is the network byte order, i.e., the left most bit (octet) is the most significant one. By XOR we mean bitwise addition modulo 2 of binary strings, and || denotes concatenation. In other words, if C = A || B, then the most significant bits of C are the bits of A, and the least significant bits of C equal the bits of B. Hexadecimal numbers are prefixed by 0x. The word "encryption" includes also use of the NULL algorithm (which in practice does leave the data in the clear).
По соглашению принятым представлением является сетевой порядок байтов, то есть крайний левый бит (октет) является наиболее значимым. Под XOR мы понимаем побитовое сложение по модулю 2 двоичных строк, а || обозначает конкатенацию. Иными словами, если C = A || B, то наиболее значимые биты C являются битами A, а наименее значимые биты C равны битам B. Шестнадцатеричные числа имеют префикс 0x. Слово «шифрование» включает также использование алгоритма NULL (который на практике действительно оставляет данные открытыми).
With slight abuse of notation, we use the terms "message authentication" and "authentication tag" as is common practice, even though in some circumstances, e.g., group communication, the service provided is actually only integrity protection and not data origin authentication.
С небольшим злоупотреблением терминологией мы используем термины «аутентификация сообщения» и «тег аутентификации» согласно общепринятой практике, хотя в некоторых обстоятельствах, например при групповой связи, предоставляемая услуга фактически является только защитой целостности, а не аутентификацией источника данных.
2. Goals and Features
2. Цели и возможности
The security goals for SRTP are to ensure:
Цели безопасности SRTP состоят в обеспечении:
* the confidentiality of the RTP and RTCP payloads, and
* конфиденциальности полезных нагрузок RTP и RTCP, и
* the integrity of the entire RTP and RTCP packets, together with protection against replayed packets.
* целостности всех пакетов RTP и RTCP вместе с защитой от повторно переданных пакетов.
These security services are optional and independent from each other, except that SRTCP integrity protection is mandatory (malicious or erroneous alteration of RTCP messages could otherwise disrupt the processing of the RTP stream).
Эти услуги безопасности необязательны и независимы друг от друга, за исключением того, что защита целостности SRTCP обязательна (иначе злонамеренное или ошибочное изменение сообщений RTCP могло бы нарушить обработку потока RTP).
Other, functional, goals for the protocol are:
Другие, функциональные, цели протокола таковы:
* a framework that permits upgrading with new cryptographic transforms,
* основа, позволяющая модернизировать его новыми криптографическими преобразованиями,
* low bandwidth cost, i.e., a framework preserving RTP header compression efficiency,
* низкая стоимость полосы пропускания, то есть основа, сохраняющая эффективность сжатия заголовков RTP, и,
and, asserted by the pre-defined transforms:
что подтверждается предопределёнными преобразованиями:
* a low computational cost,
* низкая вычислительная стоимость,
* a small footprint (i.e., small code size and data memory for keying information and replay lists),
* малый объём (то есть малый размер кода и памяти данных для ключевой информации и списков повторного воспроизведения),
* limited packet expansion to support the bandwidth economy goal,
* ограниченное расширение пакета в поддержку цели экономии полосы пропускания,
* independence from the underlying transport, network, and physical layers used by RTP, in particular high tolerance to packet loss and re-ordering.
* независимость от нижележащих транспортного, сетевого и физического уровней, используемых RTP, в частности высокая устойчивость к потере пакетов и их переупорядочиванию.
These properties ensure that SRTP is a suitable protection scheme for RTP/RTCP in both wired and wireless scenarios.
Эти свойства гарантируют, что SRTP является подходящей схемой защиты для RTP/RTCP как в проводных, так и в беспроводных сценариях.
2.1. Features
2.1. Возможности
Besides the above mentioned direct goals, SRTP provides for some additional features. They have been introduced to lighten the burden on key management and to further increase security. They include:
Помимо перечисленных выше прямых целей, SRTP предоставляет некоторые дополнительные возможности. Они введены для облегчения бремени управления ключами и дальнейшего повышения безопасности. К ним относятся:
* A single "master key" can provide keying material for confidentiality and integrity protection, both for the SRTP stream and the corresponding SRTCP stream. This is achieved with a key derivation function (see Section 4.3), providing "session keys" for the respective security primitive, securely derived from the master key.
* Один «главный ключ» (master key) может предоставлять ключевой материал для обеспечения конфиденциальности и защиты целостности как для потока SRTP, так и для соответствующего потока SRTCP. Это достигается с помощью функции выработки ключа (см. раздел 4.3), которая предоставляет «сеансовые ключи» для соответствующего примитива безопасности, безопасно выработанные из главного ключа.
* In addition, the key derivation can be configured to periodically refresh the session keys, which limits the amount of ciphertext produced by a fixed key, available for an adversary to cryptanalyze.
* Кроме того, выработку ключей можно настроить на периодическое обновление сеансовых ключей, что ограничивает объём шифротекста, создаваемого фиксированным ключом и доступного противнику для криптоанализа.
* "Salting keys" are used to protect against pre-computation and time-memory tradeoff attacks [MF00] [BS00].
* «Солевые ключи» используются для защиты от атак на основе предварительных вычислений и компромисса «время-память» [MF00] [BS00].
Detailed rationale for these features can be found in Section 7.
Подробное обоснование этих возможностей приведено в разделе 7.
3. SRTP Framework
3. Основы SRTP
RTP is the Real-time Transport Protocol [RFC3550]. We define SRTP as a profile of RTP. This profile is an extension to the RTP Audio/Video Profile [RFC3551]. Except where explicitly noted, all aspects of that profile apply, with the addition of the SRTP security features. Conceptually, we consider SRTP to be a "bump in the stack" implementation which resides between the RTP application and the transport layer. SRTP intercepts RTP packets and then forwards an equivalent SRTP packet on the sending side, and intercepts SRTP packets and passes an equivalent RTP packet up the stack on the receiving side.
RTP — это протокол Real-time Transport Protocol [RFC3550]. Мы определяем SRTP как профиль RTP. Этот профиль является расширением профиля RTP Audio/Video Profile [RFC3551]. Если явно не указано иное, применяются все аспекты этого профиля с добавлением функций безопасности SRTP. Концептуально мы рассматриваем SRTP как реализацию типа «вставка в стек», которая располагается между приложением RTP и транспортным уровнем. SRTP перехватывает пакеты RTP и затем на передающей стороне пересылает эквивалентный пакет SRTP, а на принимающей стороне перехватывает пакеты SRTP и передаёт эквивалентный пакет RTP вверх по стеку.
Secure RTCP (SRTCP) provides the same security services to RTCP as SRTP does to RTP. SRTCP message authentication is MANDATORY and thereby protects the RTCP fields to keep track of membership, provide feedback to RTP senders, or maintain packet sequence counters. SRTCP is described in Section 3.4.
Secure RTCP (SRTCP) предоставляет те же услуги безопасности для RTCP, что SRTP для RTP. Аутентификация сообщений SRTCP ОБЯЗАТЕЛЬНА и тем самым защищает поля RTCP, служащие для отслеживания состава участников, обратной связи с отправителями RTP или ведения счётчиков последовательности пакетов. SRTCP описывается в разделе 3.4.

The "Encrypted Portion" of an SRTP packet consists of the encryption of the RTP payload (including RTP padding when present) of the equivalent RTP packet. The Encrypted Portion MAY be the exact size of the plaintext or MAY be larger. Figure 1 shows the RTP payload including any possible padding for RTP [RFC3550].
«Шифруемая часть» пакета SRTP состоит из шифрования полезной нагрузки RTP (включая дополнение RTP, если оно присутствует) эквивалентного пакета RTP. Шифруемая часть МОЖЕТ быть точно равна размеру открытого текста или МОЖЕТ быть больше. На рисунке 1 показана полезная нагрузка RTP, включая любое возможное дополнение для RTP [RFC3550].
None of the pre-defined encryption transforms uses any padding; for these, the RTP and SRTP payload sizes match exactly. New transforms added to SRTP (following Section 6) may require padding, and may hence produce larger payloads. RTP provides its own padding format (as seen in Fig. 1), which due to the padding indicator in the RTP header has merits in terms of compactness relative to paddings using prefix-free codes. This RTP padding SHALL be the default method for transforms requiring padding. Transforms MAY specify other padding methods, and MUST then specify the amount, format, and processing of their padding. It is important to note that encryption transforms that use padding are vulnerable to subtle attacks, especially when message authentication is not used [V02]. Each specification for a new encryption transform needs to carefully consider and describe the security implications of the padding that it uses. Message authentication codes define their own padding, so this default does not apply to authentication transforms.
Ни одно из предопределённых преобразований шифрования не использует дополнение; для них размеры полезных нагрузок RTP и SRTP совпадают точно. Новые преобразования, добавляемые в SRTP (в соответствии с разделом 6), могут требовать дополнения и, следовательно, могут создавать полезные нагрузки большего размера. RTP предоставляет собственный формат дополнения (как показано на рис. 1), который благодаря индикатору дополнения в заголовке RTP имеет преимущества по компактности по сравнению с дополнениями, использующими префиксные коды. Это дополнение RTP ДОЛЖНО быть методом по умолчанию для преобразований, требующих дополнения. Преобразования МОГУТ задавать другие методы дополнения и в этом случае ДОЛЖНЫ задавать количество, формат и обработку своего дополнения. Важно отметить, что преобразования шифрования, использующие дополнение, уязвимы к тонким атакам, особенно когда аутентификация сообщений не используется [V02]. Каждая спецификация нового преобразования шифрования должна тщательно рассматривать и описывать последствия для безопасности используемого ею дополнения. Коды аутентификации сообщений определяют собственное дополнение, поэтому это значение по умолчанию не применяется к преобразованиям аутентификации.
The OPTIONAL MKI and the RECOMMENDED authentication tag are the only fields defined by SRTP that are not in RTP. Only 8-bit alignment is assumed.
НЕОБЯЗАТЕЛЬНЫЙ MKI и РЕКОМЕНДУЕМЫЙ тег аутентификации — единственные поля, определённые SRTP, которых нет в RTP. Предполагается только 8-битное выравнивание.
MKI (Master Key Identifier): configurable length, OPTIONAL. The MKI is defined, signaled, and used by key management. The MKI identifies the master key from which the session key(s) were derived that authenticate and/or encrypt the particular packet. Note that the MKI SHALL NOT identify the SRTP cryptographic context, which is identified according to Section 3.2.3. The MKI MAY be used by key management for the purposes of re-keying, identifying a particular master key within the cryptographic context (Section 3.2.1).
MKI (Master Key Identifier): настраиваемая длина, НЕОБЯЗАТЕЛЬНО. MKI определяется, сигнализируется и используется управлением ключами. MKI идентифицирует главный ключ, из которого были выработаны сеансовые ключи, аутентифицирующие и/или шифрующие данный пакет. Обратите внимание, что MKI НЕ ДОЛЖЕН идентифицировать криптографический контекст SRTP, который идентифицируется согласно разделу 3.2.3. MKI МОЖЕТ использоваться управлением ключами для целей перевыработки ключей, идентификации конкретного главного ключа в криптографическом контексте (раздел 3.2.1).
Authentication tag: configurable length, RECOMMENDED. The authentication tag is used to carry message authentication data. The Authenticated Portion of an SRTP packet consists of the RTP header followed by the Encrypted Portion of the SRTP packet. Thus, if both encryption and authentication are applied, encryption SHALL be applied before authentication on the sender side and conversely on the receiver side. The authentication tag provides authentication of the RTP header and payload, and it indirectly provides replay protection by authenticating the sequence number. Note that the MKI is not integrity protected as this does not provide any extra protection.
Тег аутентификации: настраиваемая длина, РЕКОМЕНДУЕТСЯ. Тег аутентификации используется для переноса данных аутентификации сообщения. Аутентифицируемая часть пакета SRTP состоит из заголовка RTP, за которым следует шифруемая часть пакета SRTP. Таким образом, если применяются и шифрование, и аутентификация, на передающей стороне шифрование ДОЛЖНО применяться до аутентификации, а на принимающей — наоборот. Тег аутентификации обеспечивает аутентификацию заголовка и полезной нагрузки RTP и косвенно обеспечивает защиту от повторного воспроизведения посредством аутентификации порядкового номера. Обратите внимание, что MKI не защищён целостностью, так как это не даёт никакой дополнительной защиты.
3.2. SRTP Cryptographic Contexts
3.2. Криптографические контексты SRTP
Each SRTP stream requires the sender and receiver to maintain cryptographic state information. This information is called the "cryptographic context".
Каждый поток SRTP требует, чтобы отправитель и получатель поддерживали криптографическую информацию состояния. Эта информация называется «криптографическим контекстом».
SRTP uses two types of keys: session keys and master keys. By a "session key", we mean a key which is used directly in a cryptographic transform (e.g., encryption or message authentication), and by a "master key", we mean a random bit string (given by the key management protocol) from which session keys are derived in a cryptographically secure way. The master key(s) and other parameters in the cryptographic context are provided by key management mechanisms external to SRTP, see Section 8.
SRTP использует два типа ключей: сеансовые ключи и главные ключи. Под «сеансовым ключом» мы понимаем ключ, который используется непосредственно в криптографическом преобразовании (например, шифровании или аутентификации сообщений), а под «главным ключом» — случайную битовую строку (задаваемую протоколом управления ключами), из которой криптографически стойким способом вырабатываются сеансовые ключи. Главный ключ (ключи) и другие параметры криптографического контекста предоставляются механизмами управления ключами, внешними по отношению к SRTP, см. раздел 8.

As noted above, SRTP and SRTCP by default share the bulk of the parameters in the cryptographic context. Thus, retrieving the crypto context parameters for an SRTCP stream in practice may imply a binding to the correspondent SRTP crypto context. It is up to the implementation to assure such binding, since the RTCP port may not be directly deducible from the RTP port only. Alternatively, the key management may choose to provide separate SRTP- and SRTCP- contexts, duplicating the common parameters (such as master key(s)). The latter approach then also enables SRTP and SRTCP to use, e.g., distinct transforms, if so desired. Similar considerations arise when multiple SRTP streams, forming part of one single RTP session, share keys and other parameters.
Как отмечалось выше, SRTP и SRTCP по умолчанию разделяют основную часть параметров криптографического контекста. 3.3. Обработка пакетов SRTP

Assuming initialization of the cryptographic context(s) has taken place via key management, the sender SHALL do the following to construct an SRTP packet:
Предполагая, что инициализация криптографического контекста (контекстов) произошла посредством управления ключами, отправитель ДОЛЖЕН выполнить следующее для построения пакета SRTP:
1. Determine which cryptographic context to use as described in Section 3.2.3.
1. Определить, какой криптографический контекст использовать, как описано в разделе 3.2.3.
2. Determine the index of the SRTP packet using the rollover counter, the highest sequence number in the cryptographic context, and the sequence number in the RTP packet, as described in Section 3.3.1.
2. Определить индекс пакета SRTP, используя счётчик переполнения, наибольший порядковый номер в криптографическом контексте и порядковый номер в пакете RTP, как описано в разделе 3.3.1.
3. Determine the master key and master salt. This is done using the index determined in the previous step or the current MKI in the cryptographic context, according to Section 8.1.
3. Определить главный ключ и главную соль. Это делается с использованием индекса, определённого на предыдущем шаге, или текущего MKI в криптографическом контексте, согласно разделу 8.1.
4. Determine the session keys and session salt (if they are used by the transform) as described in Section 4.3, using master key, master salt, key_derivation_rate, and session key-lengths in the cryptographic context with the index, determined in Steps 2 and 3.
4. Определить сеансовые ключи и сеансовую соль (если они используются преобразованием), как описано в разделе 4.3, используя главный ключ, главную соль, key_derivation_rate и длины сеансовых ключей в криптографическом контексте с индексом, определённым на шагах 2 и 3.
5. Encrypt the RTP payload to produce the Encrypted Portion of the packet (see Section 4.1, for the defined ciphers). This step uses the encryption algorithm indicated in the cryptographic context, the session encryption key and the session salt (if used) found in Step 4 together with the index found in Step 2.
5. Зашифровать полезную нагрузку RTP, чтобы получить шифруемую часть пакета (см. раздел 4.1 для определённых шифров). Этот шаг использует алгоритм шифрования, указанный в криптографическом контексте, сеансовый ключ шифрования и сеансовую соль (если используется), найденные на шаге 4, вместе с индексом, найденным на шаге 2.
6. If the MKI indicator is set to one, append the MKI to the packet.
6. Если индикатор MKI установлен в единицу, добавить MKI к пакету.
7. For message authentication, compute the authentication tag for the Authenticated Portion of the packet, as described in Section 4.2. This step uses the current rollover counter, the authentication algorithm indicated in the cryptographic context, and the session authentication key found in Step 4. Append the authentication tag to the packet.
7. Для аутентификации сообщения вычислить тег аутентификации для аутентифицируемой части пакета, как описано в разделе 4.2. 8. If necessary, update the ROC as in Section 3.3.1, using the packet index determined in Step 2.
8. При необходимости обновить ROC, как в разделе 3.3.1, используя индекс пакета, определённый на шаге 2.

3. Определить главный ключ и главную соль. Если индикатор MKI в контексте установлен в единицу, использовать MKI из пакета SRTP, в противном случае использовать индекс с предыдущего шага, согласно разделу 8.1.

4. Определить сеансовые ключи и сеансовую соль (если используются преобразованием), как описано в разделе 4.3, используя главный ключ, главную соль, key_derivation_rate и длины сеансовых ключей в криптографическом контексте с индексом, определённым на шагах 2 и 3.

5. Для аутентификации сообщения и защиты от повторного воспроизведения сначала проверить, не был ли пакет воспроизведён повторно (раздел 3.3.2), используя список повторного воспроизведения и индекс, определённый на шаге 2. If the result is "AUTHENTICATION FAILURE" (see Section 4.2), the packet MUST be discarded from further processing and the event SHOULD be logged.
Затем выполнить проверку тега аутентификации, используя счётчик переполнения с шага 2, алгоритм аутентификации, указанный в криптографическом контексте, и сеансовый ключ аутентификации с шага 4. As the rollover counter is 32 bits long and the sequence number is 16 bits long, the maximum number of packets belonging to a given SRTP stream that can be secured with the same key is 2^48 using the pre- defined transforms. After that number of SRTP packets have been sent with a given (master or session) key, the sender MUST NOT send any more packets with that key. (There exists a similar limit for SRTCP, which in practice may be more restrictive, see Section 9.2.) This limitation enforces a security benefit by providing an upper bound on the amount of traffic that can pass before cryptographic keys are changed. Re-keying (see Section 8.1) MUST be triggered, before this amount of traffic, and MAY be triggered earlier, e.g., for increased security and access control to media. Recurring key derivation by means of a non-zero key_derivation_rate (see Section 4.3), also gives stronger security but does not change the above absolute maximum value.
Поскольку счётчик переполнения имеет длину 32 бита, а порядковый номер — 16 бит, максимальное число пакетов, принадлежащих данному потоку SRTP, которое можно защитить одним и тем же ключом с помощью предопределённых преобразований, составляет 2^48. После отправки такого числа пакетов SRTP с данным (главным или сеансовым) ключом отправитель НЕ ДОЛЖЕН отправлять больше пакетов с этим ключом. (Для SRTCP существует аналогичное ограничение, которое на практике может быть более строгим, см. раздел 9.2.) Это ограничение даёт выигрыш в безопасности, устанавливая верхнюю границу объёма трафика, который может пройти до смены криптографических ключей. Перевыработка ключей (см. раздел 8.1) ДОЛЖНА запускаться до достижения этого объёма трафика и МОЖЕТ запускаться раньше, например для повышения безопасности и контроля доступа к медиаданным. Периодическая выработка ключей с помощью ненулевого key_derivation_rate (см. раздел 4.3) также даёт более высокую безопасность, но не изменяет указанное выше абсолютное максимальное значение.
On the receiver side, there is a caveat to updating s_l and ROC: if message authentication is not present, neither the initialization of s_l, nor the ROC update can be made completely robust. The receiver's "implicit index" approach works for the pre-defined transforms as long as the reorder and loss of the packets are not too great and bit-errors do not occur in unfortunate ways. In particular, 2^15 packets would need to be lost, or a packet would need to be 2^15 packets out of sequence before synchronization is lost. Such drastic loss or reorder is likely to disrupt the RTP application itself.
На стороне получателя есть оговорка относительно обновления s_l и ROC: если аутентификация сообщений отсутствует, ни инициализация s_l, ни обновление ROC не могут быть сделаны полностью надёжными. Подход «неявного индекса» получателя работает для предопределённых преобразований до тех пор, пока переупорядочивание и потеря пакетов не слишком велики и битовые ошибки не возникают неблагоприятным образом. В частности, потребовалось бы потерять 2^15 пакетов или пакету потребовалось бы отстать от последовательности на 2^15 пакетов, прежде чем синхронизация будет потеряна. Такая резкая потеря или переупорядочивание, вероятно, нарушит работу самого приложения RTP.
The algorithm for the index estimate and ROC update is a matter of implementation, and should take into consideration the environment (e.g., packet loss rate) and the cases when synchronization is likely to be lost, e.g., when the initial sequence number (randomly chosen by RTP) is not known in advance (not sent in the key management protocol) but may be near to wrap modulo 2^16. A more elaborate and more robust scheme than the one given above is the handling of RTP's own "rollover counter", see Appendix A.1 of [RFC3550].
Алгоритм оценки индекса и обновления ROC относится к сфере реализации и должен учитывать окружение (например, долю потерь пакетов) и случаи, когда синхронизация может быть потеряна, например когда исходный порядковый номер (случайно выбранный RTP) неизвестен заранее (не передан в протоколе управления ключами), но может быть близок к переходу через 2^16 по модулю. Более сложная и более надёжная схема, чем приведённая выше, — обработка собственного «счётчика переполнения» RTP, см. приложение A.1 к [RFC3550].
3.3.2. Replay Protection
3.3.2. Защита от повторного воспроизведения
Secure replay protection is only possible when integrity protection is present. It is RECOMMENDED to use replay protection, both for RTP and RTCP, as integrity protection alone cannot assure security against replay attacks.
Надёжная защита от повторного воспроизведения возможна только при наличии защиты целостности. РЕКОМЕНДУЕТСЯ использовать защиту от повторного воспроизведения как для RTP, так и для RTCP, поскольку одна лишь защита целостности не может обеспечить безопасность против атак повторного воспроизведения.
A packet is "replayed" when it is stored by an adversary, and then re-injected into the network. When message authentication is provided, SRTP protects against such attacks through a Replay List. Each SRTP receiver maintains a Replay List, which conceptually contains the indices of all of the packets which have been received and authenticated. In practice, the list can use a "sliding window" approach, so that a fixed amount of storage suffices for replay protection. Packet indices which lag behind the packet index in the context by more than SRTP-WINDOW-SIZE can be assumed to have been received, where SRTP-WINDOW-SIZE is a receiver-side, implementation- dependent parameter and MUST be at least 64, but which MAY be set to a higher value.
Пакет считается «воспроизведённым повторно», когда он сохраняется противником и затем повторно вводится в сеть. Когда обеспечивается аутентификация сообщений, SRTP защищает от таких атак с помощью списка повторного воспроизведения. Каждый получатель SRTP поддерживает список повторного воспроизведения, который концептуально содержит индексы всех пакетов, которые были получены и аутентифицированы. На практике список может использовать подход «скользящего окна», так что для защиты от повторного воспроизведения достаточно фиксированного объёма памяти. Можно считать, что индексы пакетов, отстающие от индекса пакета в контексте более чем на SRTP-WINDOW-SIZE, были получены, где SRTP-WINDOW-SIZE — зависящий от реализации параметр на стороне получателя, который ДОЛЖЕН быть не меньше 64, но МОЖЕТ быть установлен в большее значение.
The receiver checks the index of an incoming packet against the replay list and the window. Only packets with index ahead of the window, or, inside the window but not already received, SHALL be accepted.
Получатель проверяет индекс входящего пакета по списку повторного воспроизведения и окну. ДОЛЖНЫ приниматься только пакеты с индексом впереди окна или находящимся внутри окна, но ещё не полученным.
After the packet has been authenticated (if necessary the window is first moved ahead), the replay list SHALL be updated with the new index.
После того как пакет аутентифицирован (при необходимости окно сначала сдвигается вперёд), список повторного воспроизведения ДОЛЖЕН быть обновлён новым индексом.
The Replay List can be efficiently implemented by using a bitmap to represent which packets have been received, as described in the Security Architecture for IP [RFC2401].
Список повторного воспроизведения можно эффективно реализовать с помощью битовой карты, представляющей, какие пакеты были получены, как описано в архитектуре безопасности для IP [RFC2401].
3.4. Secure RTCP
3.4. Защищённый RTCP
Secure RTCP follows the definition of Secure RTP. SRTCP adds three mandatory new fields (the SRTCP index, an "encrypt-flag", and the authentication tag) and one optional field (the MKI) to the RTCP packet definition. The three mandatory fields MUST be appended to an RTCP packet in order to form an equivalent SRTCP packet. The added fields follow any other profile-specific extensions. According to Section 6.1 of [RFC3550], there is a REQUIRED packet format for compound packets. SRTCP MUST be given packets according to that requirement in the sense that the first part MUST be a sender report or a receiver report. However, the RTCP encryption prefix (a random 32-bit quantity) specified in that Section MUST NOT be used since, as is stated there, it is only applicable to the encryption method specified in [RFC3550] and is not needed by the cryptographic mechanisms used in SRTP.
Secure RTCP следует определению Secure RTP. SRTCP добавляет три обязательных новых поля (индекс SRTCP, «флаг шифрования» и тег аутентификации) и одно необязательное поле (MKI) к определению пакета RTCP. For the pre- defined transforms, the size of the added fields will be at least 14 octets, and upper bounded depending on MKI and the authentication tag sizes.
При соблюдении этих мер сообщения SRTCP не будут использовать больше выделенной полосы пропускания. Влияние размера добавленных полей на трафик SRTCP будет состоять в том, что сообщения будут отправляться с более длинными интервалами между пакетами. 4.1.1. AES in Counter Mode

Conceptually, counter mode [AES-CTR] consists of encrypting successive integers. The actual definition is somewhat more complicated, in order to randomize the starting point of the integer sequence. Each packet is encrypted with a distinct keystream segment, which SHALL be computed as follows.
Концептуально режим счётчика [AES-CTR] состоит в шифровании последовательных целых чисел. Фактическое определение несколько сложнее, чтобы рандомизировать начальную точку последовательности целых чисел. Каждый пакет шифруется отдельным сегментом ключевого потока, который ДОЛЖЕН вычисляться следующим образом.

Note that the initial value, IV, is fixed for each packet and is formed by "reserving" 16 zeros in the least significant bits for the purpose of the counter. The number of blocks of keystream generated for any fixed value of IV MUST NOT exceed 2^16 to avoid keystream re-use, see below. The AES has a block size of 128 bits, so 2^16 output blocks are sufficient to generate the 2^23 bits of keystream needed to encrypt the largest possible RTP packet (except for IPv6 "jumbograms" [RFC2675], which are not likely to be used for RTP-based multimedia traffic). This restriction on the maximum bit-size of the packet that can be encrypted ensures the security of the encryption method by limiting the effectiveness of probabilistic attacks [BDJR].
Обратите внимание, что начальное значение IV фиксировано для каждого пакета и формируется путём «резервирования» 16 нулей в наименее значимых битах для целей счётчика. Число блоков ключевого потока, генерируемых для любого фиксированного значения IV, НЕ ДОЛЖНО превышать 2^16 во избежание повторного использования ключевого потока, см. ниже. AES имеет размер блока 128 бит, поэтому 2^16 выходных блоков достаточно для генерации 2^23 битов ключевого потока, необходимых для шифрования наибольшего возможного пакета RTP (за исключением «джумбограмм» IPv6 [RFC2675], которые вряд ли будут использоваться для мультимедийного трафика на основе RTP). Это ограничение максимального размера пакета, поддающегося шифрованию, обеспечивает безопасность метода шифрования путём ограничения эффективности вероятностных атак [BDJR].
For a particular Counter Mode key, each IV value used as an input MUST be distinct, in order to avoid the security exposure of a two- time pad situation (Section 9.1). To satisfy this constraint, an implementation MUST ensure that the combination of the SRTP packet index of ROC || SEQ, and the SSRC used in the construction of the IV are distinct for any particular key. The failure to ensure this uniqueness could be catastrophic for Secure RTP. This is in contrast to the situation for RTP itself, which may be able to tolerate such failures. It is RECOMMENDED that, if a dedicated security module is present, the RTP sequence numbers and SSRC either be generated or checked by that module (i.e., sequence-number and SSRC processing in an SRTP system needs to be protected as well as the key).
Для конкретного ключа режима счётчика каждое значение IV, используемое в качестве входа, ДОЛЖНО быть уникальным, чтобы избежать угрозы безопасности, связанной с ситуацией двухкратного использования гаммы (раздел 9.1). Чтобы удовлетворить этому ограничению, реализация ДОЛЖНА гарантировать, что комбинация индекса пакета SRTP ROC || SEQ и SSRC, используемого при построении IV, уникальна для любого конкретного ключа. Неспособность обеспечить эту уникальность может быть катастрофической для Secure RTP. Это контрастирует с ситуацией для самого RTP, который, возможно, способен переносить такие сбои. РЕКОМЕНДУЕТСЯ, чтобы при наличии выделенного модуля безопасности порядковые номера RTP и SSRC либо генерировались, либо проверялись этим модулем (то есть обработка порядковых номеров и SSRC в системе SRTP должна быть защищена так же, как и ключ).
4.1.2. AES in f8-mode
4.1.2. AES в режиме f8
To encrypt UMTS (Universal Mobile Telecommunications System, as 3G networks) data, a solution (see [f8-a] [f8-b]) known as the f8- algorithm has been developed. On a high level, the proposed scheme is a variant of Output Feedback Mode (OFB) [HAC], with a more elaborate initialization and feedback function. As in normal OFB, the core consists of a block cipher. We also define here the use of AES as a block cipher to be used in what we shall call "f8-mode of operation" RTP encryption. The AES f8-mode SHALL use the same default sizes for session key and salt as AES counter mode.
Для шифрования данных UMTS (Universal Mobile Telecommunications System, как в сетях 3G) было разработано решение (см. [f8-a] [f8-b]), известное как алгоритм f8. 6. Adding SRTP Transforms
6. Добавление преобразований SRTP

Such a companion RFC SHOULD avoid overlap with the SRTP protocol document. Note however, that it MAY be necessary to extend the SRTP or SRTCP cryptographic context definition with new parameters (including fixed or default values), add steps to the packet processing, or even add fields to the SRTP/SRTCP packets. The companion RFC SHALL explain any known issues regarding interactions between the transform and other aspects of SRTP.

Такой сопутствующий RFC СЛЕДУЕТ избегать пересечения с документом протокола SRTP. Each new transform document SHOULD specify its key attributes, e.g., size of keys (minimum, maximum, recommended), format of keys, recommended/required processing of input keying material, requirements/recommendations on key lifetime, re-keying and key derivation, whether sharing of keys between SRTP and SRTCP is allowed or not, etc. An added message integrity transform SHOULD define a minimum acceptable key/tag size for SRTCP, equivalent in strength to the minimum values as defined in Section 5.2.

7. Rationale
7. Обоснование
This section explains the rationale behind several important features of SRTP.
В этом разделе объясняется обоснование нескольких важных возможностей SRTP.
7.1. Key derivation
7.1. Выработка ключей
Key derivation reduces the burden on the key establishment. As many as six different keys are needed per crypto context (SRTP and SRTCP encryption keys and salts, SRTP and SRTCP authentication keys), but these are derived from a single master key in a cryptographically secure way. Thus, the key management protocol needs to exchange only one master key (plus master salt when required), and then SRTP itself derives all the necessary session keys (via the first, mandatory application of the key derivation function).
Выработка ключей снижает нагрузку на установление ключей. На один криптографический контекст требуется до шести различных ключей (ключи шифрования и соли SRTP и SRTCP, ключи аутентификации SRTP и SRTCP), но они вырабатываются из одного главного ключа криптографически стойким способом. Таким образом, протоколу управления ключами нужно обмениваться только одним главным ключом (плюс главной солью, когда требуется), а затем SRTP сам вырабатывает все необходимые сеансовые ключи (посредством первого обязательного применения функции выработки ключей).
Multiple applications of the key derivation function are optional, but will give security benefits when enabled. They prevent an attacker from obtaining large amounts of ciphertext produced by a single fixed session key. If the attacker was able to collect a large amount of ciphertext for a certain session key, he might be helped in mounting certain attacks.
Многократные применения функции выработки ключей необязательны, но при включении дают выигрыш в безопасности. Они не позволяют противнику получить большие объёмы шифротекста, созданного одним фиксированным сеансовым ключом. Если бы противник смог собрать большой объём шифротекста для определённого сеансового ключа, это могло бы помочь ему в проведении некоторых атак.
Multiple applications of the key derivation function provide backwards and forward security in the sense that a compromised session key does not compromise other session keys derived from the same master key. This means that the attacker who is able to recover a certain session key, is anyway not able to have access to messages secured under previous and later session keys (derived from the same master key). (Note that, of course, a leaked master key reveals all the session keys derived from it.)
Многократные применения функции выработки ключей обеспечивают обратную и прямую безопасность в том смысле, что скомпрометированный сеансовый ключ не компрометирует другие сеансовые ключи, выработанные из того же главного ключа. Это означает, что противник, способный восстановить определённый сеансовый ключ, всё равно не сможет получить доступ к сообщениям, защищённым предыдущими и последующими сеансовыми ключами (выработанными из того же главного ключа). (Заметьте, что, разумеется, утёкший главный ключ раскрывает все выработанные из него сеансовые ключи.)
Considerations arise with high-rate key refresh, especially in large multicast settings, see Section 11.
Соображения возникают при высокочастотном обновлении ключей, особенно в крупных многоадресных конфигурациях, см. раздел 11.
7.2. Salting key
7.2. Солевой ключ
The master salt guarantees security against off-line key-collision attacks on the key derivation that might otherwise reduce the effective key size [MF00]. The derived session salting key used in the encryption, has been introduced to protect against some attacks on additive stream ciphers, see Section 9.2. The explicit inclusion method of the salt in the IV has been selected for ease of hardware implementation.
Главная соль гарантирует безопасность против офлайн-атак на выработку ключей на основе коллизий, которые в противном случае могли бы уменьшить эффективный размер ключа [MF00]. Выработанный сеансовый солевой ключ, используемый при шифровании, был введён для защиты от некоторых атак на аддитивные потоковые шифры, см. раздел 9.2. Метод явного включения соли в IV был выбран для простоты аппаратной реализации.
7.3. Message Integrity from Universal Hashing
7.3. Целостность сообщений на основе универсального хеширования
The particular definition of the keystream given in Section 4.1 (the keystream prefix) is to give provision for particular universal hash functions, suitable for message authentication in the Wegman-Carter paradigm [WC81]. Such functions are provably secure, simple, quick, and especially appropriate for Digital Signal Processors and other processors with a fast multiply operation.
Конкретное определение ключевого потока, данное в разделе 4.1 (префикс ключевого потока), предусматривает возможность использования конкретных универсальных хеш-функций, подходящих для аутентификации сообщений в парадигме Вегмана-Картера [WC81]. Такие функции доказуемо безопасны, просты, быстры и особенно подходят для цифровых сигнальных процессоров и других процессоров с быстрой операцией умножения.
No authentication transforms are currently provided in SRTP other than HMAC-SHA1. Future transforms, like the above mentioned universal hash functions, MAY be added following the guidelines in Section 6.
В настоящее время в SRTP не предусмотрено иных преобразований аутентификации, кроме HMAC-SHA1. Будущие преобразования, подобные упомянутым выше универсальным хеш-функциям, МОГУТ быть добавлены согласно руководящим указаниям раздела 6.
7.4. Data Origin Authentication Considerations
7.4. Соображения об аутентификации источника данных
Note that in pair-wise communications, integrity and data origin authentication are provided together. However, in group scenarios where the keys are shared between members, the MAC tag only proves that a member of the group sent the packet, but does not prevent against a member impersonating another. Data origin authentication (DOA) for multicast and group RTP sessions is a hard problem that needs a solution; while some promising proposals are being investigated [PCST1] [PCST2], more work is needed to rigorously specify these technologies. Thus SRTP data origin authentication in groups is for further study.
Заметьте, что при парных взаимодействиях целостность и аутентификация источника данных обеспечиваются вместе. Однако в групповых сценариях, где ключи разделяются между участниками, тег MAC лишь доказывает, что пакет отправил участник группы, но не препятствует выдаче одного участника за другого. Аутентификация источника данных (DOA) для многоадресных и групповых сеансов RTP — трудная проблема, требующая решения; хотя исследуются некоторые перспективные предложения [PCST1] [PCST2], необходима дополнительная работа для строгого описания этих технологий. Таким образом, аутентификация источника данных SRTP в группах относится к вопросам для дальнейшего изучения.
DOA can be done otherwise using signatures. However, this has high impact in terms of bandwidth and processing time, therefore we do not offer this form of authentication in the pre-defined packet-integrity transform.
DOA можно обеспечить иначе, с помощью подписей. Однако это сильно влияет на полосу пропускания и время обработки, поэтому мы не предлагаем эту форму аутентификации в предопределённом преобразовании целостности пакетов.
The presence of mixers and translators does not allow data origin authentication in case the RTP payload and/or the RTP header are manipulated. Note that these types of middle entities also disrupt end-to-end confidentiality (as the IV formation depends e.g., on the RTP header preservation). A certain trust model may choose to trust the mixers/translators to decrypt/re-encrypt the media (this would imply breaking the end-to-end security, with related security implications).
Наличие микшеров и трансляторов не позволяет обеспечить аутентификацию источника данных в случае, когда полезная нагрузка RTP и/или заголовок RTP подвергаются манипуляции. Заметьте, что эти типы промежуточных объектов также нарушают сквозную конфиденциальность (поскольку формирование IV зависит, например, от сохранности заголовка RTP). Определённая модель доверия может выбрать доверие микшерам/трансляторам в части расшифрования/повторного шифрования медиаданных (это означало бы нарушение сквозной безопасности с соответствующими последствиями для безопасности).
7.5. Short and Zero-length Message Authentication
7.5. Короткая и нулевая аутентификация сообщений
As shown in Figure 1, the authentication tag is RECOMMENDED in SRTP. A full 80-bit authentication-tag SHOULD be used, but a shorter tag or even a zero-length tag (i.e., no message authentication) MAY be used under certain conditions to support either of the following two application environments.
Как показано на рисунке 1, тег аутентификации в SRTP РЕКОМЕНДУЕТСЯ. СЛЕДУЕТ использовать полный 80-битный тег аутентификации, но более короткий тег или даже тег нулевой длины (то есть без аутентификации сообщений) МОЖЕТ использоваться при определённых условиях для поддержки любого из следующих двух прикладных окружений.
1. Strong authentication can be impractical in environments where bandwidth preservation is imperative. An important special case is wireless communication systems, in which bandwidth is a scarce and expensive resource. Studies have shown that for certain applications and link technologies, additional bytes may result in a significant decrease in spectrum efficiency [SWO]. Considerable effort has been made to design IP header compression techniques to improve spectrum efficiency [RFC3095]. A typical voice application produces 20 byte samples, and the RTP, UDP and IP headers need to be jointly compressed to one or two bytes on average in order to obtain acceptable wireless bandwidth economy [RFC3095]. In this case, strong authentication would impose nearly fifty percent overhead.
1. Сильная аутентификация может быть непрактичной в окружениях, где сохранение полосы пропускания обязательно. Важный особый случай — системы беспроводной связи, в которых полоса пропускания является редким и дорогим ресурсом. Исследования показали, что для некоторых приложений и технологий связи дополнительные байты могут привести к значительному снижению спектральной эффективности [SWO]. Было приложено немало усилий для разработки методов сжатия заголовков IP с целью повышения спектральной эффективности [RFC3095]. Типичное голосовое приложение создаёт 20-байтные выборки, и заголовки RTP, UDP и IP необходимо совместно сжимать в среднем до одного-двух байтов, чтобы получить приемлемую экономию беспроводной полосы пропускания [RFC3095]. В этом случае сильная аутентификация наложила бы почти пятидесятипроцентные накладные расходы.
2. Authentication is impractical for applications that use data links with fixed-width fields that cannot accommodate the expansion due to the authentication tag. This is the case for some important existing wireless channels.
2. Аутентификация непрактична для приложений, использующих каналы передачи данных с полями фиксированной ширины, которые не могут вместить расширение из-за тега аутентификации. Так обстоит дело с некоторыми важными существующими беспроводными каналами.
For example, zero- byte header compression is used to adapt EVRC/SMV voice with the legacy IS-95 bearer channel in CDMA2000 VoIP services. It was found that not a single additional octet could be added to the data, which motivated the creation of a zero-byte profile for ROHC [RFC3242].
Например, сжатие заголовков с нулевым числом байтов используется для адаптации голоса EVRC/SMV к унаследованному каналу-носителю IS-95 в услугах VoIP CDMA2000. Было обнаружено, что нельзя добавить ни одного дополнительного октета к данным, что и мотивировало создание профиля с нулевым числом байтов для ROHC [RFC3242].
A short tag is secure for a restricted set of applications. Consider a voice telephony application, for example, such as a G.729 audio codec with a 20-millisecond packetization interval, protected by a 32-bit message authentication tag. The likelihood of any given packet being successfully forged is only one in 2^32. Thus an adversary can control no more than 20 milliseconds of audio output during a 994-day period, on average. In contrast, the effect of a single forged packet can be much larger if the application is stateful. A codec that uses relative or predictive compression across packets will propagate the maliciously generated state, affecting a longer duration of output. Certainly not all SRTP or telephony applications meet the criteria for short or zero-length authentication tags. Section 9.5.1 discusses the risks of weak or no message authentication, and section 9.5 describes the circumstances when it is acceptable and when it is unacceptable.
Короткий тег безопасен для ограниченного набора приложений. Рассмотрим, например, приложение голосовой телефонии, такое как аудиокодек G.729 с интервалом пакетизации 20 миллисекунд, защищённое 32-битным тегом аутентификации сообщений. Вероятность успешной подделки любого данного пакета составляет лишь один к 2^32. Таким образом, противник может в среднем управлять не более 20 миллисекундами аудиовыхода в течение 994-дневного периода. Напротив, эффект одного поддельного пакета может быть намного больше, если приложение имеет состояние. Кодек, использующий относительное или предсказательное сжатие между пакетами, будет распространять злонамеренно сгенерированное состояние, влияя на более длительную продолжительность вывода. Разумеется, не все приложения SRTP или телефонии соответствуют критериям для коротких тегов аутентификации или тегов нулевой длины. В разделе 9.5.1 обсуждаются риски слабой аутентификации сообщений или её отсутствия, а в разделе 9.5 описываются обстоятельства, когда она приемлема и когда неприемлема.
8. Key Management Considerations
8. Соображения по управлению ключами
There are emerging key management standards [MIKEY] [KEYMGT] [SDMS] for establishing an SRTP cryptographic context (e.g., an SRTP master key). Both proprietary and open-standard key management methods are likely to be used for telephony applications [MIKEY] [KINK] and multicast applications [GDOI]. This section provides guidance for key management systems that service SRTP session.
Появляются стандарты управления ключами [MIKEY] [KEYMGT] [SDMS] для установления криптографического контекста SRTP (например, главного ключа SRTP). Как проприетарные, так и открытые стандартные методы управления ключами, вероятно, будут использоваться для телефонных приложений [MIKEY] [KINK] и многоадресных приложений [GDOI]. В этом разделе даются рекомендации для систем управления ключами, обслуживающих сеанс SRTP.
For initialization, an interoperable SRTP implementation SHOULD be given the SSRC and MAY be given the initial RTP sequence number for the RTP stream by key management (thus, key management has a dependency on RTP operational parameters). Sending the RTP sequence number in the key management may be useful e.g., when the initial sequence number is close to wrapping (to avoid synchronization problems), and to communicate the current sequence number to a joining endpoint (to properly initialize its replay list).
Для инициализации совместимой реализации SRTP СЛЕДУЕТ передать SSRC и МОЖЕТ быть передан исходный порядковый номер RTP для потока RTP средствами управления ключами (таким образом, управление ключами имеет зависимость от операционных параметров RTP). Передача порядкового номера RTP в управлении ключами может быть полезна, например, когда исходный порядковый номер близок к переходу через границу (чтобы избежать проблем синхронизации), и для сообщения текущего порядкового номера присоединяющейся конечной точке (для правильной инициализации её списка повторного воспроизведения).
If the pre-defined transforms are used, SRTP allows sharing of the same master key between SRTP/SRTCP streams belonging to the same RTP session.
Если используются предопределённые преобразования, SRTP допускает совместное использование одного и того же главного ключа между потоками SRTP/SRTCP, принадлежащими одному сеансу RTP.
First, sharing between SRTP streams belonging to the same RTP session is secure if the design of the synchronization mechanism, i.e., the IV, avoids keystream re-use (the two-time pad, Section 9.1). This is taken care of by the fact that RTP provides for unique SSRCs for streams belonging to the same RTP session. See Section 9.1 for further discussion.
Во-первых, совместное использование между потоками SRTP, принадлежащими одному сеансу RTP, безопасно, если проект механизма синхронизации, то есть IV, избегает повторного использования ключевого потока (двукратное использование гаммы, раздел 9.1). Это обеспечивается тем, что RTP предусматривает уникальные SSRC для потоков, принадлежащих одному сеансу RTP. Дальнейшее обсуждение см. в разделе 9.1.
Second, sharing between SRTP and the corresponding SRTCP is secure. The fact that an SRTP stream and its associated SRTCP stream both carry the same SSRC does not constitute a problem for the two-time pad due to the key derivation. Thus, SRTP and SRTCP corresponding to one RTP session MAY share master keys (as they do by default).
Во-вторых, совместное использование между SRTP и соответствующим SRTCP безопасно. Тот факт, что поток SRTP и связанный с ним поток SRTCP оба несут один и тот же SSRC, не создаёт проблемы двукратного использования гаммы благодаря выработке ключей. Таким образом, SRTP и SRTCP, соответствующие одному сеансу RTP, МОГУТ разделять главные ключи (как они и делают по умолчанию).
Note that message authentication also has a dependency on SSRC uniqueness that is unrelated to the problem of keystream reuse: SRTP streams authenticated under the same key MUST have a distinct SSRC in order to identify the sender of the message. This requirement is needed because the SSRC is the cryptographically authenticated field used to distinguish between different SRTP streams. Were two streams to use identical SSRC values, then an adversary could substitute messages from one stream into the other without detection.
Заметьте, что аутентификация сообщений также имеет зависимость от уникальности SSRC, не связанную с проблемой повторного использования ключевого потока: потоки SRTP, аутентифицируемые одним и тем же ключом, ДОЛЖНЫ иметь различные SSRC, чтобы идентифицировать отправителя сообщения. Это требование необходимо, поскольку SSRC — это криптографически аутентифицируемое поле, используемое для различения разных потоков SRTP. Если бы два потока использовали одинаковые значения SSRC, противник мог бы подменять сообщения из одного потока в другой без обнаружения.
SRTP/SRTCP MUST NOT share master keys under any other circumstances than the ones given above, i.e., between SRTP and its corresponding SRTCP, and, between streams belonging to the same RTP session.
SRTP/SRTCP НЕ ДОЛЖНЫ разделять главные ключи ни при каких иных обстоятельствах, кроме указанных выше, то есть между SRTP и соответствующим ему SRTCP и между потоками, принадлежащими одному сеансу RTP.
8.1. Re-keying
8.1. Перевыработка ключей
The recommended way for a particular key management system to provide re-key within SRTP is by associating a master key in a crypto context with an MKI.
Рекомендуемый способ для конкретной системы управления ключами обеспечить перевыработку ключей в SRTP — связать главный ключ в криптографическом контексте с MKI.
This provides for easy master key retrieval (see Scenarios in Section 11), but has the disadvantage of adding extra bits to each packet. As noted in Section 7.5, some wireless links do not cater for added bits, therefore SRTP also defines a more economic way of triggering re-keying, via use of <From, To>, which works in some specific, simple scenarios (see Section 8.1.1).
Это обеспечивает лёгкое получение главного ключа (см. сценарии в разделе 11), но имеет недостаток в виде добавления лишних битов в каждый пакет. Как отмечено в разделе 7.5, некоторые беспроводные каналы не рассчитаны на добавленные биты, поэтому SRTP также определяет более экономичный способ запуска перевыработки ключей через использование <From, To>, который работает в некоторых конкретных простых сценариях (см. раздел 8.1.1).
SRTP senders SHALL count the amount of SRTP and SRTCP traffic being used for a master key and invoke key management to re-key if needed (Section 9.2). These interactions are defined by the key management interface to SRTP and are not defined by this protocol specification.
Отправители SRTP ДОЛЖНЫ подсчитывать объём трафика SRTP и SRTCP, используемого для главного ключа, и при необходимости вызывать управление ключами для перевыработки ключей (раздел 9.2). Эти взаимодействия определяются интерфейсом управления ключами к SRTP и не определяются настоящей спецификацией протокола.
8.1.1. Use of the <From, To> for re-keying
8.1.1. Использование <From, To> для перевыработки ключей
In addition to the use of the MKI, SRTP defines another optional mechanism for master key retrieval, the <From, To>. The <From, To> specifies the range of SRTP indices (a pair of sequence number and ROC) within which a certain master key is valid, and is (when used) part of the crypto context. By looking at the 48-bit SRTP index of the current SRTP packet, the corresponding master key can be found by determining which From-To interval it belongs to. For SRTCP, the most recently observed/used SRTP index (which can be obtained from the cryptographic context) is used for this purpose, even though SRTCP has its own (31-bit) index (see caveat below).
В дополнение к использованию MKI SRTP определяет другой необязательный механизм получения главного ключа — <From, To>. <From, To> задаёт диапазон индексов SRTP (пара порядкового номера и ROC), в пределах которого действителен определённый главный ключ, и (когда используется) является частью криптографического контекста. Глядя на 48-битный индекс текущего пакета SRTP, соответствующий главный ключ можно найти, определив, к какому интервалу From-To он принадлежит. Для SRTCP для этой цели используется наиболее недавно наблюдённый/использованный индекс SRTP (который можно получить из криптографического контекста), хотя SRTCP имеет собственный (31-битный) индекс (см. оговорку ниже).
This method, compared to the MKI, has the advantage of identifying the master key and defining its lifetime without adding extra bits to each packet. This could be useful, as already noted, for some wireless links that do not cater for added bits. However, its use SHOULD be limited to specific, very simple scenarios. We recommend to limit its use when the RTP session is a simple unidirectional or bi-directional stream. This is because in case of multiple streams, it is difficult to trigger the re-key based on the <From, To> of a single RTP stream. For example, if several streams share a master key, there is no simple one-to-one correspondence between the index sequence space of a certain stream, and the index sequence space on which the <From, To> values are based. Consequently, when a master key is shared between streams, one of these streams MUST be designated by key management as the one whose index space defines the re-keying points. Also, the re-key triggering on SRTCP is based on the correspondent SRTP stream, i.e., when the SRTP stream changes the master key, so does the correspondent SRTCP. This becomes obviously more and more complex with multiple streams.
По сравнению с MKI этот метод имеет преимущество: он идентифицирует главный ключ и определяет время его жизни, не добавляя лишних битов в каждый пакет. Это могло бы быть полезно, как уже отмечалось, для некоторых беспроводных каналов, не рассчитанных на добавленные биты. Однако его использование СЛЕДУЕТ ограничивать конкретными, очень простыми сценариями. Мы рекомендуем ограничивать его использование случаями, когда сеанс RTP представляет собой простой однонаправленный или двунаправленный поток. Это связано с тем, что при наличии нескольких потоков трудно запускать перевыработку ключей на основе <From, To> одного потока RTP. Например, если несколько потоков разделяют главный ключ, не существует простого взаимно однозначного соответствия между пространством последовательности индексов определённого потока и пространством последовательности индексов, на котором основаны значения <From, To>. Следовательно, когда главный ключ разделяется между потоками, один из этих потоков ДОЛЖЕН быть назначен управлением ключами как тот, чьё пространство индексов определяет точки перевыработки ключей. Кроме того, запуск перевыработки ключей для SRTCP основан на соответствующем потоке SRTP, то есть когда поток SRTP меняет главный ключ, меняет и соответствующий SRTCP. Это, очевидно, становится всё более и более сложным при наличии нескольких потоков.
The default values for the <From, To> are "from the first observed packet" and "until further notice". However, the maximum limit of SRTP/SRTCP packets that are sent under each given master/session key (Section 9.2) MUST NOT be exceeded.
Значения по умолчанию для <From, To> — «от первого наблюдённого пакета» и «до дальнейшего уведомления». Однако максимальный предел пакетов SRTP/SRTCP, отправляемых под каждым данным главным/сеансовым ключом (раздел 9.2), НЕ ДОЛЖЕН превышаться.
In case the <From, To> is used as key retrieval, then the MKI is not inserted in the packet (and its indicator in the crypto context is zero). However, using the MKI does not exclude using <From, To> key lifetime simultaneously. This can for instance be useful to signal at the sender side at which point in time an MKI is to be made active.
В случае когда <From, To> используется как средство получения ключа, MKI не вставляется в пакет (и его индикатор в криптографическом контексте равен нулю). Однако использование MKI не исключает одновременного использования времени жизни ключа <From, To>. Это может быть полезно, например, чтобы сигнализировать на стороне отправителя, в какой момент времени MKI должен стать активным.

9. Security Considerations
9. Соображения безопасности
9.1. SSRC collision and two-time pad
9.1. Коллизия SSRC и двукратное использование гаммы
Any fixed keystream output, generated from the same key and index MUST only be used to encrypt once. Re-using such keystream (jokingly called a "two-time pad" system by cryptographers), can seriously compromise security. The NSA's VENONA project [C99] provides a historical example of such a compromise. It is REQUIRED that automatic key management be used for establishing and maintaining SRTP and SRTCP keying material; this requirement is to avoid keystream reuse, which is more likely to occur with manual key management. Furthermore, in SRTP, a "two-time pad" is avoided by requiring the key, or some other parameter of cryptographic significance, to be unique per RTP/RTCP stream and packet. The pre- defined SRTP transforms accomplish packet-uniqueness by including the packet index and stream-uniqueness by inclusion of the SSRC.
Любой фиксированный выход ключевого потока, сгенерированный из одного и того же ключа и индекса, ДОЛЖЕН использоваться для шифрования только один раз. Повторное использование такого ключевого потока (криптографы в шутку называют такую систему «двукратной гаммой») может серьёзно подорвать безопасность. Проект VENONA АНБ [C99] даёт исторический пример такой компрометации. ТРЕБУЕТСЯ, чтобы для установления и поддержания ключевого материала SRTP и SRTCP использовалось автоматическое управление ключами; это требование направлено на предотвращение повторного использования ключевого потока, которое более вероятно при ручном управлении ключами. Кроме того, в SRTP «двукратная гамма» избегается путём требования, чтобы ключ или некоторый другой параметр, значимый для криптографии, был уникальным для каждого потока RTP/RTCP и пакета. Предопределённые преобразования SRTP обеспечивают уникальность пакета путём включения индекса пакета, а уникальность потока — путём включения SSRC.
The pre-defined transforms (AES-CM and AES-f8) allow master keys to be shared across streams belonging to the same RTP session by the inclusion of the SSRC in the IV. A master key MUST NOT be shared among different RTP sessions.
Предопределённые преобразования (AES-CM и AES-f8) позволяют разделять главные ключи между потоками, принадлежащими одному сеансу RTP, благодаря включению SSRC в IV. Главный ключ НЕ ДОЛЖЕН разделяться между разными сеансами RTP.
Thus, the SSRC MUST be unique between all the RTP streams within the same RTP session that share the same master key. RTP itself provides an algorithm for detecting SSRC collisions within the same RTP session. Thus, temporary collisions could lead to temporary two-time pad, in the unfortunate event that SSRCs collide at a point in time when the streams also have identical sequence numbers (occurring with probability roughly 2^(-48)). Therefore, the key management SHOULD take care of avoiding such SSRC collisions by including the SSRCs to be used in the session as negotiation parameters, proactively assuring their uniqueness. This is a strong requirements in scenarios where for example, there are multiple senders that can start to transmit simultaneously, before SSRC collision are detected at the RTP level.
Таким образом, SSRC ДОЛЖЕН быть уникальным среди всех потоков RTP в рамках одного сеанса RTP, разделяющих один и тот же главный ключ. Сам RTP предоставляет алгоритм обнаружения коллизий SSRC в рамках одного сеанса RTP. Таким образом, временные коллизии могли бы привести к временной двукратной гамме в маловероятном случае, если SSRC сталкиваются в момент, когда потоки также имеют идентичные порядковые номера (что происходит с вероятностью примерно 2^(-48)). Поэтому управлению ключами СЛЕДУЕТ позаботиться об избежании таких коллизий SSRC, включая используемые в сеансе SSRC в качестве параметров согласования и проактивно обеспечивая их уникальность. Это строгое требование в сценариях, где, например, имеется несколько отправителей, которые могут начать передачу одновременно, до обнаружения коллизий SSRC на уровне RTP.
Note also that even with distinct SSRCs, extensive use of the same key might improve chances of probabilistic collision and time- memory-tradeoff attacks succeeding.
Заметьте также, что даже при различных SSRC интенсивное использование одного и того же ключа может повысить шансы успеха вероятностных коллизионных атак и атак на основе компромисса «время-память».
As described, master keys MAY be shared between streams belonging to the same RTP session, but it is RECOMMENDED that each SSRC have its own master key. When master keys are shared among SSRC participants and SSRCs are managed by a key management module as recommended above, the RECOMMENDED policy for an SSRC collision error is for the participant to leave the SRTP session as it is a sign of malfunction.
Как описано, главные ключи МОГУТ разделяться между потоками, принадлежащими одному сеансу RTP, но РЕКОМЕНДУЕТСЯ, чтобы каждый SSRC имел собственный главный ключ. Когда главные ключи разделяются между участниками SSRC и SSRC управляются модулем управления ключами, как рекомендовано выше, РЕКОМЕНДУЕМАЯ политика при ошибке коллизии SSRC состоит в том, чтобы участник покинул сеанс SRTP, так как это признак неисправности.
9.2. Key Usage
9.2. Использование ключей
The effective key size is determined (upper bounded) by the size of the master key and, for encryption, the size of the salting key. Any additive stream cipher is vulnerable to attacks that use statistical knowledge about the plaintext source to enable key collision and time-memory tradeoff attacks [MF00] [H80] [BS00]. These attacks take advantage of commonalities among plaintexts, and provide a way for a cryptanalyst to amortize the computational effort of decryption over many keys, or over many bytes of output, thus reducing the effective key size of the cipher. A detailed analysis of these attacks and their applicability to the encryption of Internet traffic is provided in [MF00]. In summary, the effective key size of SRTP when used in a security system in which m distinct keys are used, is equal to the key size of the cipher less the logarithm (base two) of m. Protection against such attacks can be provided simply by increasing the size of the keys used, which here can be accomplished by the use of the salting key. Note that the salting key MUST be random but MAY be public. A salt size of (the suggested) size 112 bits protects against attacks in scenarios where at most 2^112 keys are in use. This is sufficient for all practical purposes.
Эффективный размер ключа определяется (ограничивается сверху) размером главного ключа и для шифрования — размером солевого ключа. Любой аддитивный потоковый шифр уязвим к атакам, использующим статистические знания об источнике открытого текста, чтобы сделать возможными атаки на коллизии ключей и атаки «время-память» [MF00] [H80] [BS00]. Эти атаки используют общность между открытыми текстами и дают криптоаналитику способ амортизировать вычислительные затраты на расшифрование по многим ключам или по многим байтам выхода, тем самым уменьшая эффективный размер ключа шифра. Подробный анализ этих атак и их применимости к шифрованию интернет-трафика приведён в [MF00]. В итоге эффективный размер ключа SRTP при использовании в системе безопасности, в которой применяется m различных ключей, равен размеру ключа шифра минус логарифм (по основанию два) от m. Защита от таких атак может быть обеспечена просто увеличением размера используемых ключей, что здесь может быть достигнуто применением солевого ключа. Заметьте, что солевой ключ ДОЛЖЕН быть случайным, но МОЖЕТ быть открытым. Размер соли (рекомендуемый) в 112 бит защищает от атак в сценариях, где используется не более 2^112 ключей. Этого достаточно для всех практических целей.
Implementations SHOULD use keys that are as large as possible. Please note that in many cases increasing the key size of a cipher does not affect the throughput of that cipher.
Реализациям СЛЕДУЕТ использовать как можно более крупные ключи. Обратите внимание, что во многих случаях увеличение размера ключа шифра не влияет на пропускную способность этого шифра.
The use of the SRTP and SRTCP indices in the pre-defined transforms fixes the maximum number of packets that can be secured with the same key. This limit is fixed to 2^48 SRTP packets for an SRTP stream, and 2^31 SRTCP packets, when SRTP and SRTCP are considered independently. Due to for example re-keying, reaching this limit may or may not coincide with wrapping of the indices, and thus the sender MUST keep packet counts. However, when the session keys for related SRTP and SRTCP streams are derived from the same master key (the default behavior, Section 4.3), the upper bound that has to be considered is in practice the minimum of the two quantities. That is, when 2^48 SRTP packets or 2^31 SRTCP packets have been secured with the same key (whichever occurs before), the key management MUST be called to provide new master key(s) (previously stored and used keys MUST NOT be used again), or the session MUST be terminated. If a sender of RTCP discovers that the sender of SRTP (or SRTCP) has not updated the master or session key prior to sending 2^48 SRTP (or 2^31 SRTCP) packets belonging to the same SRTP (SRTCP) stream, it is up to the security policy of the RTCP sender how to behave, e.g., whether an RTCP BYE-packet should be sent and/or if the event should be logged.
Использование индексов SRTP и SRTCP в предопределённых преобразованиях фиксирует максимальное число пакетов, которые можно защитить одним и тем же ключом. Этот предел фиксирован на уровне 2^48 пакетов SRTP для потока SRTP и 2^31 пакетов SRTCP, когда SRTP и SRTCP рассматриваются независимо. Из-за, например, перевыработки ключей достижение этого предела может совпадать или не совпадать с переходом индексов через границу, и поэтому отправитель ДОЛЖЕН вести подсчёт пакетов. Однако когда сеансовые ключи для связанных потоков SRTP и SRTCP вырабатываются из одного главного ключа (поведение по умолчанию, раздел 4.3), верхняя граница, которую нужно учитывать, на практике равна минимуму из этих двух величин. То есть когда 2^48 пакетов SRTP или 2^31 пакетов SRTCP защищены одним и тем же ключом (что наступит раньше), ДОЛЖНО быть вызвано управление ключами для предоставления нового главного ключа (ключей) (ранее сохранённые и использованные ключи НЕ ДОЛЖНЫ использоваться снова), либо сеанс ДОЛЖЕН быть завершён. Если отправитель RTCP обнаружит, что отправитель SRTP (или SRTCP) не обновил главный или сеансовый ключ до отправки 2^48 пакетов SRTP (или 2^31 пакетов SRTCP), принадлежащих одному потоку SRTP (SRTCP), то, как поступить, определяется политикой безопасности отправителя RTCP, например, следует ли отправить пакет RTCP BYE и/или зарегистрировать событие в журнале.
Note: in most typical applications (assuming at least one RTCP packet for every 128,000 RTP packets), it will be the SRTCP index that first reaches the upper limit, although the time until this occurs is very long: even at 200 SRTCP packets/sec, the 2^31 index space of SRTCP is enough to secure approximately 4 months of communication.
Примечание: в большинстве типичных приложений (при условии хотя бы одного пакета RTCP на каждые 128 000 пакетов RTP) именно индекс SRTCP первым достигнет верхнего предела, хотя время до этого наступления очень велико: даже при 200 пакетах SRTCP/с 2^31 индексного пространства SRTCP достаточно для защиты примерно 4 месяцев связи.
Note that if the master key is to be shared between SRTP streams within the same RTP session (Section 9.1), although the above bounds are on a per stream (i.e., per SSRC) basis, the sender MUST base re- key decision on the stream whose sequence number space is the first to be exhausted.
Заметьте, что если главный ключ должен разделяться между потоками SRTP в рамках одного сеанса RTP (раздел 9.1), то, хотя вышеуказанные границы относятся к каждому потоку (то есть каждому SSRC), отправитель ДОЛЖЕН основывать решение о перевыработке ключей на потоке, чьё пространство порядковых номеров исчерпается первым.
Key derivation limits the amount of plaintext that is encrypted with a fixed session key, and made available to an attacker for analysis, but key derivation does not extend the master key's lifetime. To see this, simply consider our requirements to avoid two-time pad: two distinct packets MUST either be processed with distinct IVs, or with distinct session keys, and both the distinctness of IV and of the session keys are (for the pre-defined transforms) dependent on the distinctness of the packet indices.
Выработка ключей ограничивает объём открытого текста, шифруемого фиксированным сеансовым ключом и доступного противнику для анализа, но выработка ключей не продлевает время жизни главного ключа. Чтобы увидеть это, достаточно рассмотреть наши требования по избежанию двукратной гаммы: два различных пакета ДОЛЖНЫ либо обрабатываться с различными IV, либо с различными сеансовыми ключами, а как различие IV, так и различие сеансовых ключей (для предопределённых преобразований) зависят от различия индексов пакетов.
Note that with the key derivation, the effective key size is at most that of the master key, even if the derived session key is considerably longer. With the pre-defined authentication transform, the session authentication key is 160 bits, but the master key by default is only 128 bits. This design choice was made to comply with certain recommendations in [RFC2104] so that an existing HMAC implementation can be plugged into SRTP without problems. Since the default tag size is 80 bits, it is, for the applications in mind, also considered acceptable from security point of view. Users having concerns about this are RECOMMENDED to instead use a 192 bit master key in the key derivation. It was, however, chosen not to mandate 192-bit keys since existing AES implementations to be used in the key-derivation may not always support key-lengths other than 128 bits. Since AES is not defined (or properly analyzed) for use with 160 bit keys it is NOT RECOMMENDED that ad-hoc key-padding schemes are used to pad shorter keys to 192 or 256 bits.
Заметьте, что при выработке ключей эффективный размер ключа не превышает размера главного ключа, даже если выработанный сеансовый ключ значительно длиннее. При предопределённом преобразовании аутентификации сеансовый ключ аутентификации составляет 160 бит, но главный ключ по умолчанию — только 128 бит. Этот выбор конструкции сделан для соответствия определённым рекомендациям в [RFC2104], чтобы существующая реализация HMAC могла быть без проблем подключена к SRTP. Поскольку размер тега по умолчанию составляет 80 бит, для рассматриваемых приложений это также считается приемлемым с точки зрения безопасности. Пользователям, у которых есть опасения по этому поводу, РЕКОМЕНДУЕТСЯ вместо этого использовать 192-битный главный ключ при выработке ключей. Однако было решено не требовать 192-битных ключей, поскольку существующие реализации AES, используемые при выработке ключей, могут не всегда поддерживать длины ключей, отличные от 128 бит. Поскольку AES не определён (и не проанализирован должным образом) для использования со 160-битными ключами, НЕ РЕКОМЕНДУЕТСЯ использовать специальные схемы дополнения ключей для дополнения более коротких ключей до 192 или 256 бит.
9.3. Confidentiality of the RTP Payload
9.3. Конфиденциальность полезной нагрузки RTP
SRTP's pre-defined ciphers are "seekable" stream ciphers, i.e., ciphers able to efficiently seek to arbitrary locations in their keystream (so that the encryption or decryption of one packet does not depend on preceding packets). By using seekable stream ciphers, SRTP avoids the denial of service attacks that are possible on stream ciphers that lack this property. It is important to be aware that, as with any stream cipher, the exact length of the payload is revealed by the encryption. This means that it may be possible to deduce certain "formatting bits" of the payload, as the length of the codec output might vary due to certain parameter settings etc. This, in turn, implies that the corresponding bit of the keystream can be deduced. However, if the stream cipher is secure (counter mode and f8 are provably secure under certain assumptions [BDJR] [KSYH] [IK]), knowledge of a few bits of the keystream will not aid an attacker in predicting subsequent keystream bits. Thus, the payload length (and information deducible from this) will leak, but nothing else.
Предопределённые шифры SRTP — это «произвольно доступные» потоковые шифры, то есть шифры, способные эффективно переходить к произвольным позициям своего ключевого потока (так что шифрование или расшифрование одного пакета не зависит от предыдущих пакетов). Используя произвольно доступные потоковые шифры, SRTP избегает атак типа отказа в обслуживании, возможных на потоковых шифрах, лишённых этого свойства. Важно понимать, что, как и с любым потоковым шифром, точная длина полезной нагрузки раскрывается шифрованием. Это означает, что может оказаться возможным вывести определённые «биты форматирования» полезной нагрузки, поскольку длина выхода кодека может варьироваться из-за определённых настроек параметров и т. п. Это, в свою очередь, означает, что соответствующий бит ключевого потока может быть выведен. Однако если потоковый шифр безопасен (режим счётчика и f8 доказуемо безопасны при определённых предположениях [BDJR] [KSYH] [IK]), знание нескольких битов ключевого потока не поможет противнику предсказать последующие биты ключевого потока. Таким образом, длина полезной нагрузки (и информация, выводимая из неё) будет утекать, но ничего больше.
As some RTP packet could contain highly predictable data, e.g., SID, it is important to use a cipher designed to resist known plaintext attacks (which is the current practice).
Поскольку некоторые пакеты RTP могут содержать легко предсказуемые данные, например SID, важно использовать шифр, рассчитанный на сопротивление атакам с известным открытым текстом (что является текущей практикой).
9.4. Confidentiality of the RTP Header
9.4. Конфиденциальность заголовка RTP
In SRTP, RTP headers are sent in the clear to allow for header compression. This means that data such as payload type, synchronization source identifier, and timestamp are available to an eavesdropper. Moreover, since RTP allows for future extensions of headers, we cannot foresee what kind of possibly sensitive information might also be "leaked".
В SRTP заголовки RTP передаются в открытом виде, чтобы обеспечить сжатие заголовков. Это означает, что такие данные, как тип полезной нагрузки, идентификатор источника синхронизации и временная метка, доступны подслушивающему. Более того, поскольку RTP допускает будущие расширения заголовков, мы не можем предвидеть, какая возможно конфиденциальная информация также может «утечь».
SRTP is a low-cost method, which allows header compression to reduce bandwidth. It is up to the endpoints' policies to decide about the security protocol to employ. If one really needs to protect headers, and is allowed to do so by the surrounding environment, then one should also look at alternatives, e.g., IPsec [RFC2401].
SRTP — это малозатратный метод, позволяющий сжатию заголовков снижать полосу пропускания. Решение о применяемом протоколе безопасности зависит от политик конечных точек. Если действительно необходимо защищать заголовки и это разрешено окружающей средой, следует также рассмотреть альтернативы, например IPsec [RFC2401].
9.5. Integrity of the RTP payload and header
9.5. Целостность полезной нагрузки и заголовка RTP
SRTP messages are subject to attacks on their integrity and source identification, and these risks are discussed in Section 9.5.1. To protect against these attacks, each SRTP stream SHOULD be protected by HMAC-SHA1 [RFC2104] with an 80-bit output tag and a 160-bit key, or a message authentication code with equivalent strength. Secure RTP SHOULD NOT be used without message authentication, except under the circumstances described in this section. It is important to note that encryption algorithms, including AES Counter Mode and f8, do not provide message authentication. SRTCP MUST NOT be used with weak (or NULL) authentication.
Сообщения SRTP подвержены атакам на их целостность и идентификацию источника, и эти риски обсуждаются в разделе 9.5.1. Для защиты от этих атак каждый поток SRTP СЛЕДУЕТ защищать с помощью HMAC-SHA1 [RFC2104] с 80-битным выходным тегом и 160-битным ключом или кода аутентификации сообщений эквивалентной стойкости. Secure RTP НЕ СЛЕДУЕТ использовать без аутентификации сообщений, кроме обстоятельств, описанных в этом разделе. Важно отметить, что алгоритмы шифрования, включая режим счётчика AES и f8, не обеспечивают аутентификацию сообщений. SRTCP НЕ ДОЛЖЕН использоваться со слабой (или NULL) аутентификацией.
SRTP MAY be used with weak authentication (e.g., a 32-bit authentication tag), or with no authentication (the NULL authentication algorithm). These options allow SRTP to be used to provide confidentiality in situations where
SRTP МОЖЕТ использоваться со слабой аутентификацией (например, 32-битным тегом аутентификации) или без аутентификации (алгоритм NULL). Эти варианты позволяют использовать SRTP для обеспечения конфиденциальности в ситуациях, когда
* weak or null authentication is an acceptable security risk, and * it is impractical to provide strong message authentication. These conditions are described below and in Section 7.5. Note that both conditions MUST hold in order for weak or null authentication to be used. The risks associated with exercising the weak or null authentication options need to be considered by a security audit prior to their use for a particular application or environment given the risks, which are discussed in Section 9.5.1.
* слабая или нулевая аутентификация является приемлемым риском безопасности, и * обеспечение сильной аутентификации сообщений непрактично. Эти условия описаны ниже и в разделе 7.5. Заметьте, что для использования слабой или нулевой аутентификации ДОЛЖНЫ выполняться оба условия. Риски, связанные с применением вариантов слабой или нулевой аутентификации, должны быть рассмотрены аудитом безопасности до их использования для конкретного приложения или окружения с учётом рисков, которые обсуждаются в разделе 9.5.1.
Weak authentication is acceptable when the RTP application is such that the effect of a small fraction of successful forgeries is negligible. If the application is stateless, then the effect of a single forged RTP packet is limited to the decoding of that particular packet. Under this condition, the size of the authentication tag MUST ensure that only a negligible fraction of the packets passed to the RTP application by the SRTP receiver can be forgeries. This fraction is negligible when an adversary, if given control of the forged packets, is not able to make a significant impact on the output of the RTP application (see the example of Section 7.5).
Слабая аутентификация приемлема, когда приложение RTP таково, что эффект небольшой доли успешных подделок пренебрежимо мал. Если приложение не имеет состояния, то эффект одного поддельного пакета RTP ограничивается декодированием этого конкретного пакета. При этом условии размер тега аутентификации ДОЛЖЕН гарантировать, что лишь пренебрежимо малая доля пакетов, переданных приложению RTP получателем SRTP, может быть подделками. Эта доля пренебрежимо мала, когда противник, получив контроль над поддельными пакетами, не способен оказать значимого влияния на выход приложения RTP (см. пример в разделе 7.5).
Weak or null authentication MAY be acceptable when it is unlikely that an adversary can modify ciphertext so that it decrypts to an intelligible value. One important case is when it is difficult for an adversary to acquire the RTP plaintext data, since for many codecs, an adversary that does not know the input signal cannot manipulate the output signal in a controlled way. In many cases it may be difficult for the adversary to determine the actual value of the plaintext. For example, a hidden snooping device might be required in order to know a live audio or video signal. The adversary's signal must have a quality equivalent to or greater than that of the signal under attack, since otherwise the adversary would not have enough information to encode that signal with the codec used by the victim. Plaintext prediction may also be especially difficult for an interactive application such as a telephone call.
Слабая или нулевая аутентификация МОЖЕТ быть приемлемой, когда маловероятно, что противник сможет изменить шифротекст так, чтобы он расшифровался в осмысленное значение. Один важный случай — когда противнику трудно получить открытые данные RTP, поскольку для многих кодеков противник, не знающий входного сигнала, не может управляемо манипулировать выходным сигналом. Во многих случаях противнику может быть трудно определить фактическое значение открытого текста. Например, для знания живого аудио- или видеосигнала может потребоваться скрытое подслушивающее устройство. Сигнал противника должен иметь качество, эквивалентное или большее, чем у атакуемого сигнала, иначе у противника не будет достаточно информации, чтобы закодировать этот сигнал кодеком, используемым жертвой. Предсказание открытого текста может быть особенно трудным и для интерактивного приложения, такого как телефонный звонок.
Weak or null authentication MUST NOT be used when the RTP application makes data forwarding or access control decisions based on the RTP data. In such a case, an attacker may be able to subvert confidentiality by causing the receiver to forward data to an attacker. See Section 3 of [B96] for a real-life example of such attacks.
Слабую или нулевую аутентификацию НЕ ДОЛЖНО использоваться, когда приложение RTP принимает решения о пересылке данных или контроле доступа на основе данных RTP. В таком случае злоумышленник может подорвать конфиденциальность, заставив получателя пересылать данные злоумышленнику. Реальный пример таких атак см. в разделе 3 [B96].
Null authentication MUST NOT be used when a replay attack, in which an adversary stores packets then replays them later in the session, could have a non-negligible impact on the receiver. An example of a successful replay attack is the storing of the output of a surveillance camera for a period of time, later followed by the injection of that output to the monitoring station to avoid surveillance. Encryption does not protect against this attack, and non-null authentication is REQUIRED in order to defeat it.
Нулевую аутентификацию НЕ ДОЛЖНО использоваться, когда атака повторного воспроизведения, при которой противник сохраняет пакеты, а затем воспроизводит их позже в сеансе, могла бы оказать не пренебрежимо малое влияние на получателя. Пример успешной атаки повторного воспроизведения — сохранение выхода камеры наблюдения на некоторое время с последующим вводом этого выхода на станцию мониторинга, чтобы избежать наблюдения. Шифрование не защищает от этой атаки, и для её отражения ТРЕБУЕТСЯ ненулевая аутентификация.
If existential message forgery is an issue, i.e., when the accuracy of the received data is of non-negligible importance, null authentication MUST NOT be used.
Если проблемой является экзистенциальная подделка сообщений, то есть когда точность полученных данных имеет не пренебрежимо малую важность, нулевую аутентификацию НЕ ДОЛЖНО использоваться.
9.5.1. Risks of Weak or Null Message Authentication
9.5.1. Риски слабой или нулевой аутентификации сообщений
During a security audit considering the use of weak or null authentication, it is important to keep in mind the following attacks which are possible when no message authentication algorithm is used.
При аудите безопасности, рассматривающем использование слабой или нулевой аутентификации, важно помнить о следующих атаках, возможных при отсутствии алгоритма аутентификации сообщений.
An attacker who cannot predict the plaintext is still always able to modify the message sent between the sender and the receiver so that it decrypts to a random plaintext value, or to send a stream of bogus packets to the receiver that will decrypt to random plaintext values. This attack is essentially a denial of service attack, though in the absence of message authentication, the RTP application will have inputs that are bit-wise correlated with the true value. Some multimedia codecs and common operating systems will crash when such data are accepted as valid video data. This denial of service attack may be a much larger threat than that due to an attacker dropping, delaying, or re-ordering packets.
Противник, который не может предсказать открытый текст, всё равно всегда способен изменить сообщение, отправленное между отправителем и получателем, так чтобы оно расшифровалось в случайное значение открытого текста, или отправить получателю поток поддельных пакетов, которые расшифруются в случайные значения открытого текста. Эта атака по сути является атакой типа отказа в обслуживании, хотя при отсутствии аутентификации сообщений приложение RTP будет получать входные данные, побитово коррелированные с истинным значением. Некоторые мультимедийные кодеки и распространённые операционные системы аварийно завершатся, когда такие данные принимаются как допустимые видеоданные. Эта атака типа отказа в обслуживании может быть гораздо большей угрозой, чем атака, связанная с отбрасыванием, задержкой или переупорядочиванием пакетов противником.
An attacker who cannot predict the plaintext can still replay a previous message with certainty that the receiver will accept it. Applications with stateless codecs might be robust against this type of attack, but for other, more complex applications these attacks may be far more grave.
Противник, который не может предсказать открытый текст, всё равно может воспроизвести предыдущее сообщение с уверенностью, что получатель его примет. Приложения с кодеками без состояния могут быть устойчивы к этому типу атак, но для других, более сложных приложений эти атаки могут быть гораздо серьёзнее.
An attacker who can predict the plaintext can modify the ciphertext so that it will decrypt to any value of her choosing. With an additive stream cipher, an attacker will always be able to change individual bits.
Противник, который может предсказать открытый текст, может изменить шифротекст так, что он расшифруется в любое выбранное им значение. С аддитивным потоковым шифром противник всегда сможет изменять отдельные биты.
An attacker may be able to subvert confidentiality due to the lack of authentication when a data forwarding or access control decision is made on decrypted but unauthenticated plaintext. This is because the receiver may be fooled into forwarding data to an attacker, leading to an indirect breach of confidentiality (see Section 3 of [B96]). This is because data-forwarding decisions are made on the decrypted plaintext; information in the plaintext will determine to what subnet (or process) the plaintext is forwarded in ESP [RFC2401] tunnel mode (respectively, transport mode). When Secure RTP is used without message authentication, it should be verified that the application does not make data forwarding or access control decisions based on the decrypted plaintext.
Противник может подорвать конфиденциальность из-за отсутствия аутентификации, когда решение о пересылке данных или контроле доступа принимается на основе расшифрованного, но неаутентифицированного открытого текста. Это происходит потому, что получателя можно обмануть, заставив пересылать данные противнику, что приводит к косвенному нарушению конфиденциальности (см. раздел 3 [B96]). Это объясняется тем, что решения о пересылке данных принимаются на основе расшифрованного открытого текста; информация в открытом тексте определяет, в какую подсеть (или процесс) открытый текст пересылается в туннельном режиме ESP [RFC2401] (соответственно в транспортном режиме). Когда Secure RTP используется без аутентификации сообщений, следует убедиться, что приложение не принимает решения о пересылке данных или контроле доступа на основе расшифрованного открытого текста.
Some cipher modes of operation that require padding, e.g., standard cipher block chaining (CBC) are very sensitive to attacks on confidentiality if certain padding types are used in the absence of integrity. The attack [V02] shows that this is indeed the case for the standard RTP padding as discussed in reference to Figure 1, when used together with CBC mode. Later transform additions to SRTP MUST therefore carefully consider the risk of using this padding without proper integrity protection.
Некоторые режимы работы шифра, требующие дополнения, например стандартная схема сцепления блоков шифра (CBC), очень чувствительны к атакам на конфиденциальность, если определённые типы дополнения используются при отсутствии целостности. Атака [V02] показывает, что это действительно так для стандартного дополнения RTP, обсуждавшегося в связи с рисунком 1, при использовании вместе с режимом CBC. Поэтому последующие добавления преобразований в SRTP ДОЛЖНЫ тщательно учитывать риск использования этого дополнения без надлежащей защиты целостности.
9.5.2. Implicit Header Authentication
9.5.2. Неявная аутентификация заголовка
The IV formation of the f8-mode gives implicit authentication (IHA) of the RTP header, even when message authentication is not used. When IHA is used, an attacker that modifies the value of the RTP header will cause the decryption process at the receiver to produce random plaintext values. While this protection is not equivalent to message authentication, it may be useful for some applications.
Формирование IV в режиме f8 даёт неявную аутентификацию (IHA) заголовка RTP, даже когда аутентификация сообщений не используется. При использовании IHA противник, изменяющий значение заголовка RTP, заставит процесс расшифрования на получателе выдавать случайные значения открытого текста. Хотя эта защита не эквивалентна аутентификации сообщений, она может быть полезна для некоторых приложений.
10. Interaction with Forward Error Correction mechanisms
10. Взаимодействие с механизмами упреждающей коррекции ошибок
The default processing when using Forward Error Correction (e.g., RFC 2733) processing with SRTP SHALL be to perform FEC processing prior to SRTP processing on the sender side and to perform SRTP processing prior to FEC processing on the receiver side. Any change to this ordering (reversing it, or, placing FEC between SRTP encryption and SRTP authentication) SHALL be signaled out of band.
Обработкой по умолчанию при использовании упреждающей коррекции ошибок (например, RFC 2733) с SRTP ДОЛЖНА быть обработка FEC до обработки SRTP на стороне отправителя и обработка SRTP до обработки FEC на стороне получателя. Любое изменение этого порядка (обратный порядок или размещение FEC между шифрованием SRTP и аутентификацией SRTP) ДОЛЖНО сигнализироваться вне полосы.
11. Scenarios
11. Сценарии
SRTP can be used as security protocol for the RTP/RTCP traffic in many different scenarios. SRTP has a number of configuration options, in particular regarding key usage, and can have impact on the total performance of the application according to the way it is used. Hence, the use of SRTP is dependent on the kind of scenario and application it is used with. In the following, we briefly illustrate some use cases for SRTP, and give some guidelines for recommended setting of its options.
SRTP может использоваться как протокол безопасности для трафика RTP/RTCP во многих различных сценариях. SRTP имеет ряд параметров конфигурации, в частности касающихся использования ключей, и может влиять на общую производительность приложения в зависимости от способа его использования. Поэтому использование SRTP зависит от типа сценария и приложения, с которым оно применяется. Ниже мы кратко иллюстрируем некоторые варианты использования SRTP и даём некоторые рекомендации по настройке его параметров.
11.1. Unicast
11.1. Одноадресная передача
A typical example would be a voice call or video-on-demand application. Consider one bi-directional RTP stream, as one RTP session. It is possible for the two parties to share the same master key in the two directions according to the principles of Section 9.1. The first round of the key derivation splits the master key into any or all of the following session keys (according to the provided security functions):
Типичным примером было бы приложение голосового вызова или видео по запросу. Рассмотрим один двунаправленный поток RTP как один сеанс RTP. Две стороны могут разделять один и тот же главный ключ в двух направлениях согласно принципам раздела 9.1. Первый раунд выработки ключей разделяет главный ключ на любой или все из следующих сеансовых ключей (в соответствии с предоставленными функциями безопасности):
SRTP_encr_key, SRTP_auth_key, SRTCP_encr_key, and SRTCP_auth key.
SRTP_encr_key, SRTP_auth_key, SRTCP_encr_key и SRTCP_auth key.
(For simplicity, we omit discussion of the salts, which are also derived.) In this scenario, it will in most cases suffice to have a single master key with the default lifetime. This guarantees sufficiently long lifetime of the keys and a minimum set of keys in place for most practical purposes. Also, in this case RTCP protection can be applied smoothly. Under these assumptions, use of the MKI can be omitted. As the key-derivation in combination with large difference in the packet rate in the respective directions may require simultaneous storage of several session keys, if storage is an issue, we recommended to use low-rate key derivation.
(Для простоты мы опускаем обсуждение солей, которые также вырабатываются.) В этом сценарии в большинстве случаев будет достаточно одного главного ключа со временем жизни по умолчанию. Это гарантирует достаточно длительное время жизни ключей и минимальный набор ключей для большинства практических целей. Также в этом случае защита RTCP может применяться без затруднений. При этих допущениях использование MKI можно опустить. Поскольку выработка ключей в сочетании с большим различием в скорости пакетов в соответствующих направлениях может потребовать одновременного хранения нескольких сеансовых ключей, если хранение является проблемой, мы рекомендуем использовать низкую скорость выработки ключей.
The same considerations can be extended to the unicast scenario with multiple RTP sessions, where each session would have a distinct master key.
Те же соображения можно распространить на одноадресный сценарий с несколькими сеансами RTP, где каждый сеанс имел бы отдельный главный ключ.
11.2. Multicast (one sender)
11.2. Многоадресная передача (один отправитель)
Just as with (unprotected) RTP, a scalability issue arises in big groups due to the possibly very large amount of SRTCP Receiver Reports that the sender might need to process. In SRTP, the sender may have to keep state (the cryptographic context) for each receiver, or more precisely, for the SRTCP used to protect Receiver Reports. The overhead increases proportionally to the size of the group. In particular, re-keying requires special concern, see below.
Как и в случае (незащищённого) RTP, в больших группах возникает проблема масштабируемости из-за возможно очень большого объёма отчётов получателя SRTCP, которые отправителю может потребоваться обработать. В SRTP отправитель может быть вынужден хранить состояние (криптографический контекст) для каждого получателя или, точнее, для SRTCP, используемого для защиты отчётов получателя. Накладные расходы растут пропорционально размеру группы. В частности, перевыработка ключей требует особого внимания, см. ниже.
Consider first a small group of receivers. There are a few possible setups with the distribution of master keys among the receivers. Given a single RTP session, one possibility is that the receivers share the same master key as per Section 9.1 to secure all their respective RTCP traffic. This shared master key could then be the same one used by the sender to protect its outbound SRTP traffic. Alternatively, it could be a master key shared only among the receivers and used solely for their SRTCP traffic. Both alternatives require the receivers to trust each other.
Сначала рассмотрим небольшую группу получателей. Существует несколько возможных вариантов распределения главных ключей между получателями. Для одного сеанса RTP одна из возможностей состоит в том, что получатели разделяют один и тот же главный ключ согласно разделу 9.1 для защиты всего своего соответствующего трафика RTCP. Этот общий главный ключ затем может быть тем же, который использует отправитель для защиты своего исходящего трафика SRTP. В качестве альтернативы это может быть главный ключ, разделяемый только между получателями и используемый исключительно для их трафика SRTCP. Оба варианта требуют, чтобы получатели доверяли друг другу.
Considering SRTCP and key storage, it is recommended to use low-rate (or zero) key_derivation (except the mandatory initial one), so that the sender does not need to store too many session keys (each SRTCP stream might otherwise have a different session key at a given point in time, as the SRTCP sources send at different times). Thus, in case key derivation is wanted for SRTP, the cryptographic context for SRTP can be kept separate from the SRTCP crypto context, so that it is possible to have a key_derivation_rate of 0 for SRTCP and a non- zero value for SRTP.
Рассматривая SRTCP и хранение ключей, рекомендуется использовать низкую (или нулевую) скорость выработки ключей key_derivation (кроме обязательной начальной), чтобы отправителю не нужно было хранить слишком много сеансовых ключей (иначе каждый поток SRTCP мог бы иметь в данный момент времени другой сеансовый ключ, поскольку источники SRTCP отправляют в разное время). Таким образом, если выработка ключей желательна для SRTP, криптографический контекст SRTP можно держать отдельно от криптографического контекста SRTCP, чтобы можно было иметь key_derivation_rate = 0 для SRTCP и ненулевое значение для SRTP.
Use of the MKI for re-keying is RECOMMENDED for most applications (see Section 8.1).
Использование MKI для перевыработки ключей РЕКОМЕНДУЕТСЯ для большинства приложений (см. раздел 8.1).
If there are more than one SRTP/SRTCP stream (within the same RTP session) that share the master key, the upper limit of 2^48 SRTP packets / 2^31 SRTCP packets means that, before one of the streams reaches its maximum number of packets, re-keying MUST be triggered on ALL streams sharing the master key. (From strict security point of view, only the stream reaching the maximum would need to be re-keyed, but then the streams would no longer be sharing master key, which is the intention.) A local policy at the sender side should force rekeying in a way that the maximum packet limit is not reached on any of the streams. Use of the MKI for re-keying is RECOMMENDED.
Если существует более одного потока SRTP/SRTCP (в рамках одного сеанса RTP), разделяющих главный ключ, верхний предел 2^48 пакетов SRTP / 2^31 пакетов SRTCP означает, что до того, как один из потоков достигнет максимального числа пакетов, перевыработка ключей ДОЛЖНА быть запущена для ВСЕХ потоков, разделяющих главный ключ. (Со строгой точки зрения безопасности перевыработку ключей потребовалось бы выполнить только для потока, достигающего максимума, но тогда потоки больше не разделяли бы главный ключ, что и является замыслом.) Локальная политика на стороне отправителя должна принудительно запускать перевыработку ключей так, чтобы максимальный предел пакетов не был достигнут ни на одном из потоков. Использование MKI для перевыработки ключей РЕКОМЕНДУЕТСЯ.
In large multicast with one sender, the same considerations as for the small group multicast hold. The biggest issue in this scenario is the additional load placed at the sender side, due to the state (cryptographic contexts) that has to be maintained for each receiver, sending back RTCP Receiver Reports. At minimum, a replay window might need to be maintained for each RTCP source.
В крупной многоадресной передаче с одним отправителем действуют те же соображения, что и для многоадресной передачи в малой группе. Наибольшая проблема в этом сценарии — дополнительная нагрузка на стороне отправителя из-за состояния (криптографических контекстов), которое необходимо поддерживать для каждого получателя, отправляющего отчёты получателя RTCP. Как минимум, для каждого источника RTCP может потребоваться поддерживать окно повторного воспроизведения.
11.3. Re-keying and access control
11.3. Перевыработка ключей и контроль доступа
Re-keying may occur due to access control (e.g., when a member is removed during a multicast RTP session), or for pure cryptographic reasons (e.g., the key is at the end of its lifetime). When using SRTP default transforms, the master key MUST be replaced before any of the index spaces are exhausted for any of the streams protected by one and the same master key.
Перевыработка ключей может происходить из-за контроля доступа (например, когда участник удаляется во время многоадресного сеанса RTP) или по чисто криптографическим причинам (например, ключ находится в конце своего срока жизни). При использовании преобразований SRTP по умолчанию главный ключ ДОЛЖЕН быть заменён до исчерпания любого из индексных пространств для любого из потоков, защищаемых одним и тем же главным ключом.
How key management re-keys SRTP implementations is out of scope, but it is clear that there are straightforward ways to manage keys for a multicast group. In one-sender multicast, for example, it is typically the responsibility of the sender to determine when a new key is needed. The sender is the one entity that can keep track of when the maximum number of packets has been sent, as receivers may join and leave the session at any time, there may be packet loss and delay etc. In scenarios other than one-sender multicast, other methods can be used. Here, one must take into consideration that key exchange can be a costly operation, taking several seconds for a single exchange. Hence, some time before the master key is exhausted/expires, out-of-band key management is initiated, resulting in a new master key that is shared with the receiver(s). In any event, to maintain synchronization when switching to the new key, group policy might choose between using the MKI and the <From, To>, as described in Section 8.1.
То, как управление ключами выполняет перевыработку ключей в реализациях SRTP, выходит за рамки настоящего документа, но ясно, что существуют простые способы управления ключами для многоадресной группы. В многоадресной передаче с одним отправителем, например, обычно именно отправитель несёт ответственность за определение того, когда нужен новый ключ. Отправитель — это единственный объект, способный отслеживать, когда отправлено максимальное число пакетов, поскольку получатели могут присоединяться к сеансу и покидать его в любое время, возможны потери пакетов и задержки и т. п. В сценариях, отличных от многоадресной передачи с одним отправителем, могут использоваться другие методы. Здесь необходимо принимать во внимание, что обмен ключами может быть дорогостоящей операцией, занимающей несколько секунд для одного обмена. Следовательно, за некоторое время до исчерпания/истечения срока действия главного ключа инициируется внешнее управление ключами, в результате чего создаётся новый главный ключ, разделяемый с получателем (получателями). В любом случае для поддержания синхронизации при переходе на новый ключ групповая политика может выбирать между использованием MKI и <From, To>, как описано в разделе 8.1.
For access control purposes, the <From, To> periods are set at the desired granularity, dependent on the packet rate. High rate re- keying can be problematic for SRTCP in some large-group scenarios. As mentioned, there are potential problems in using the SRTP index, rather than the SRTCP index, for determining the master key. In particular, for short periods during switching of master keys, it may be the case that SRTCP packets are not under the current master key of the correspondent SRTP. Therefore, using the MKI for re-keying in such scenarios will produce better results.
В целях контроля доступа периоды <From, To> задаются с желаемой гранулярностью в зависимости от скорости пакетов. Высокочастотная перевыработка ключей может быть проблематичной для SRTCP в некоторых сценариях больших групп. Как упоминалось, существуют потенциальные проблемы при использовании индекса SRTP, а не индекса SRTCP, для определения главного ключа. В частности, в течение коротких периодов во время смены главных ключей может случиться так, что пакеты SRTCP не находятся под текущим главным ключом соответствующего SRTP. Поэтому использование MKI для перевыработки ключей в таких сценариях даст лучшие результаты.
11.4. Summary of basic scenarios
11.4. Сводка базовых сценариев
The description of these scenarios highlights some recommendations on the use of SRTP, mainly related to re-keying and large scale multicast:
Описание этих сценариев выделяет некоторые рекомендации по использованию SRTP, главным образом связанные с перевыработкой ключей и крупномасштабной многоадресной передачей:
- Do not use fast re-keying with the <From, To> feature. It may, in particular, give problems in retrieving the correct SRTCP key, if an SRTCP packet arrives close to the re-keying time. The MKI SHOULD be used in this case.
- Не используйте быструю перевыработку ключей с возможностью <From, To>. Это, в частности, может создать проблемы при получении правильного ключа SRTCP, если пакет SRTCP приходит близко ко времени перевыработки ключей. В этом случае СЛЕДУЕТ использовать MKI.
- If multiple SRTP streams in the same RTP session share the same master key, also moderate rate re-keying MAY have the same problems, and the MKI SHOULD be used.
- Если несколько потоков SRTP в одном сеансе RTP разделяют один и тот же главный ключ, то и умеренная скорость перевыработки ключей МОЖЕТ иметь те же проблемы, и СЛЕДУЕТ использовать MKI.
- Though offering increased security, a non-zero key_derivation_rate is NOT RECOMMENDED when trying to minimize the number of keys in use with multiple streams.

12. IANA Considerations
12. Соображения по IANA
The RTP specification establishes a registry of profile names for use by higher-level control protocols, such as the Session Description Protocol (SDP), to refer to transport methods. This profile registers the name "RTP/SAVP".
Спецификация RTP устанавливает реестр имён профилей для использования протоколами управления более высокого уровня, такими как протокол описания сеансов (SDP), для ссылки на транспортные методы. Настоящий профиль регистрирует имя «RTP/SAVP».
SRTP uses cryptographic transforms which a key management protocol signals. It is the task of each particular key management protocol to register the cryptographic transforms or suites of transforms with IANA. The key management protocol conveys these protocol numbers, not SRTP, and each key management protocol chooses the numbering scheme and syntax that it requires. Specification of a key management protocol for SRTP is out of scope here. Section 8.2, however, provides guidance on the parameters that need to be defined for the default and mandatory transforms.
SRTP использует криптографические преобразования, которые сигнализирует протокол управления ключами. Задача каждого конкретного протокола управления ключами — зарегистрировать криптографические преобразования или наборы преобразований в IANA. Протокол управления ключами передаёт эти номера протоколов, а не SRTP, и каждый протокол управления ключами выбирает необходимую ему схему нумерации и синтаксис. Спецификация протокола управления ключами для SRTP выходит за рамки настоящего документа. Однако раздел 8.2 даёт рекомендации по параметрам, которые необходимо определить для преобразований по умолчанию и обязательных преобразований.

We first show how the cipher key is generated. The input block for AES-CM is generated by exclusive-oring the master salt with the concatenation of the encryption key label 0x00 with (index DIV kdr), then padding on the right with two null octets (which implements the multiply-by-2^16 operation, see Section 4.3.3). The resulting value is then AES-CM- encrypted using the master key to get the cipher key.
Сначала мы показываем, как генерируется ключ шифра.
