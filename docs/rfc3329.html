Abstract
Аннотация
This document defines new functionality for negotiating the security mechanisms used between a Session Initiation Protocol (SIP) user agent and its next-hop SIP entity. This new functionality supplements the existing methods of choosing security mechanisms between SIP entities.
Настоящий документ определяет новую функциональность для согласования механизмов безопасности, используемых между пользовательским агентом протокола инициирования сессий (SIP) и его SIP-объектом следующего перехода. Эта новая функциональность дополняет существующие методы выбора механизмов безопасности между объектами SIP.
1. Introduction
1. Введение
Traditionally, security protocols have included facilities to agree on the used mechanisms, algorithms, and other security parameters. This is to add flexibility, since different mechanisms are usually suitable to different scenarios. Also, the evolution of security mechanisms often introduces new algorithms, or uncovers problems in existing ones, making negotiation of mechanisms a necessity.
Традиционно протоколы безопасности включали средства для согласования используемых механизмов, алгоритмов и других параметров безопасности. Это делается для добавления гибкости, поскольку разные механизмы обычно подходят для разных сценариев. Кроме того, эволюция механизмов безопасности часто вводит новые алгоритмы или выявляет проблемы в существующих, что делает согласование механизмов необходимостью.
The purpose of this specification is to define negotiation functionality for the Session Initiation Protocol (SIP) [1]. This negotiation is intended to work only between a UA and its first-hop SIP entity.
Цель настоящей спецификации — определить функциональность согласования для протокола инициирования сессий (SIP) [1]. Это согласование предназначено работать только между UA и его SIP-объектом первого перехода.
1.1. Motivations
1.1. Мотивация
Without a secured method to choose between security mechanisms and/or their parameters, SIP is vulnerable to certain attacks. Authentication and integrity protection using multiple alternative methods and algorithms is vulnerable to Man-in-the-Middle (MitM) attacks (e.g., see [4]).
Без защищённого метода выбора между механизмами безопасности и/или их параметрами SIP уязвим для определённых атак. Аутентификация и защита целостности с использованием нескольких альтернативных методов и алгоритмов уязвимы для атак «человек посередине» (MitM) (см., например, [4]).
It is also hard or sometimes even impossible to know whether a specific security mechanism is truly unavailable to a SIP peer entity, or if in fact a MitM attack is in action.
Также трудно, а иногда даже невозможно узнать, действительно ли конкретный механизм безопасности недоступен SIP-партнёру, или в действительности имеет место атака MitM.
In certain small networks these issues are not very relevant, as the administrators of such networks can deploy appropriate software versions and set up policies for using exactly the right type of security. However, SIP is also expected to be deployed to hundreds of millions of small devices with little or no possibilities for coordinated security policies, let alone software upgrades, which necessitates the need for the negotiation functionality to be available from the very beginning of deployment (e.g., see [11]).
В некоторых небольших сетях эти проблемы не очень актуальны, поскольку администраторы таких сетей могут развернуть соответствующие версии программного обеспечения и установить политики использования именно нужного типа безопасности. Однако ожидается, что SIP также будет развёрнут на сотнях миллионов небольших устройств с малыми или нулевыми возможностями для согласованных политик безопасности, не говоря уже об обновлениях программного обеспечения, что делает необходимым наличие функциональности согласования с самого начала развёртывания (см., например, [11]).
1.2. Design Goals
1.2. Цели проектирования
1. The entities involved in the security agreement process need to find out exactly which security mechanisms to apply, preferably without excessive additional roundtrips.
1. Объекты, участвующие в процессе согласования безопасности, должны точно выяснить, какие механизмы безопасности применять, предпочтительно без чрезмерных дополнительных круговых обменов.
2. The selection of security mechanisms itself needs to be secure. Traditionally, all security protocols use a secure form of negotiation. For instance, after establishing mutual keys through Diffie-Hellman, IKE sends hashes of the previously sent data including the offered crypto mechanisms [8]. This allows the peers to detect if the initial, unprotected offers were tampered with.
2. Сам выбор механизмов безопасности должен быть безопасным. Традиционно все протоколы безопасности используют безопасную форму согласования. Например, установив взаимные ключи посредством Диффи-Хеллмана, IKE отправляет хеши ранее отправленных данных, включая предложенные криптомеханизмы [8]. Это позволяет сторонам обнаружить, были ли первоначальные незащищённые предложения подменены.
3. The entities involved in the security agreement process need to be able to indicate success or failure of the security agreement process.
3. Объекты, участвующие в процессе согласования безопасности, должны быть способны указать успех или неудачу процесса согласования безопасности.
4. The security agreement process should not introduce any additional state to be maintained by the involved entities.
4. Процесс согласования безопасности не должен вводить никакого дополнительного состояния, которое должны поддерживать участвующие объекты.

2. Solution
2. Решение
2.1. Overview of Operation
2.1. Обзор работы
The message flow below illustrates how the mechanism defined in this document works:
Приведённый ниже поток сообщений иллюстрирует, как работает механизм, определённый в настоящем документе:
1. Client ----------client list---------> Server 2. Client <---------server list---------- Server 3. Client ------(turn on security)------- Server 4. Client ----------server list---------> Server 5. Client <---------ok or error---------- Server
1. Клиент ----------список клиента---------> Сервер 2. Клиент <---------список сервера---------- Сервер 3. Клиент ------(включение защиты)------- Сервер 4. Клиент ----------список сервера---------> Сервер 5. Клиент <---------успех или ошибка---------- Сервер
Figure 1: Security agreement message flow.
Рисунок 1: Поток сообщений согласования безопасности.
Step 1: Clients wishing to use this specification can send a list of their supported security mechanisms along the first request to the server.
Шаг 1. Клиенты, желающие использовать настоящую спецификацию, могут отправить список поддерживаемых ими механизмов безопасности вместе с первым запросом к серверу.
Step 2: Servers wishing to use this specification can challenge the client to perform the security agreement procedure. The security mechanisms and parameters supported by the server are sent along in this challenge.
Шаг 2. Серверы, желающие использовать настоящую спецификацию, могут выдать клиенту запрос на выполнение процедуры согласования безопасности. Механизмы и параметры безопасности, поддерживаемые сервером, отправляются вместе с этим запросом.
Step 3: The client then proceeds to select the highest-preference security mechanism they have in common and to turn on the selected security.
Шаг 3. Затем клиент выбирает механизм безопасности с наивысшим предпочтением из числа общих и включает выбранную защиту.
Step 4: The client contacts the server again, now using the selected security mechanism. The server's list of supported security mechanisms is returned as a response to the challenge.
Шаг 4. Клиент снова связывается с сервером, теперь используя выбранный механизм безопасности. Список поддерживаемых механизмов безопасности сервера возвращается в качестве ответа на запрос.
Step 5: The server verifies its own list of security mechanisms in order to ensure that the original list had not been modified.
Шаг 5. Сервер проверяет свой собственный список механизмов безопасности, чтобы удостовериться, что исходный список не был изменён.
This procedure is stateless for servers (unless the used security mechanisms require the server to keep some state).
Эта процедура не требует сохранения состояния на серверах (если только используемые механизмы безопасности не требуют от сервера хранения некоторого состояния).
The client and the server lists are both static (i.e., they do not and cannot change based on the input from the other side). Nodes may, however, maintain several static lists, one for each interface, for example.
Списки клиента и сервера оба статичны (то есть они не меняются и не могут меняться в зависимости от входных данных другой стороны). Однако узлы могут поддерживать несколько статических списков, например по одному для каждого интерфейса.
Between Steps 1 and 2, the server may set up a non-self-describing security mechanism if necessary. Note that with this type of security mechanisms, the server is necessarily stateful. The client would set up the non-self-describing security mechanism between Steps 2 and 4.
Между шагами 1 и 2 сервер может при необходимости установить несамоописывающий механизм безопасности. Обратите внимание, что при таком типе механизмов безопасности сервер обязательно сохраняет состояние. Клиент установил бы несамоописывающий механизм безопасности между шагами 2 и 4.

2.3. Protocol Operation
2.3. Работа протокола
This section deals with the protocol details involved in the negotiation between a SIP UA and its next-hop SIP entity. Throughout the text the next-hop SIP entity is referred to as the first-hop proxy or outbound proxy. However, the reader should bear in mind that a user agent server can also be the next-hop for a user agent client.
Этот раздел касается деталей протокола, связанных с согласованием между SIP UA и его SIP-объектом следующего перехода. Далее по тексту SIP-объект следующего перехода называется прокси первого перехода или исходящим прокси. Однако читатель должен помнить, что сервер пользовательского агента также может быть следующим переходом для клиента пользовательского агента.
2.3.1. Client Initiated
2.3.1. Инициируется клиентом
If a client ends up using TLS to contact the server because it has followed the rules specified in [5], the client MUST NOT use the security agreement procedure of this specification. If a client ends up using non-TLS connections because of the rules in [5], the client MAY use the security agreement of this specification to detect DNS spoofing, or to negotiate some other security than TLS.
Если клиент в итоге использует TLS для связи с сервером, поскольку следовал правилам, указанным в [5], клиент НЕ ДОЛЖЕН использовать процедуру согласования безопасности настоящей спецификации. Если клиент в итоге использует не-TLS соединения из-за правил в [5], клиент МОЖЕТ использовать согласование безопасности настоящей спецификации для обнаружения подмены DNS или для согласования некоторой другой защиты, отличной от TLS.
A client wishing to use the security agreement of this specification MUST add a Security-Client header field to a request addressed to its first-hop proxy (i.e., the destination of the request is the first- hop proxy). This header field contains a list of all the security mechanisms that the client supports. The client SHOULD NOT add preference parameters to this list. The client MUST add both a Require and Proxy-Require header field with the value "sec-agree" to its request.
Клиент, желающий использовать согласование безопасности настоящей спецификации, ДОЛЖЕН добавить поле заголовка Security-Client к запросу, адресованному его прокси первого перехода (то есть пункт назначения запроса — прокси первого перехода). Это поле заголовка содержит список всех механизмов безопасности, которые поддерживает клиент. Клиенту НЕ СЛЕДУЕТ добавлять параметры предпочтения в этот список. Клиент ДОЛЖЕН добавить как поле заголовка Require, так и Proxy-Require со значением «sec-agree» к своему запросу.
The contents of the Security-Client header field may be used by the server to include any necessary information in its response.
Содержимое поля заголовка Security-Client может использоваться сервером для включения любой необходимой информации в свой ответ.
A server receiving an unprotected request that contains a Require or Proxy-Require header field with the value "sec-agree" MUST respond to the client with a 494 (Security Agreement Required) response. The server MUST add a Security-Server header field to this response listing the security mechanisms that the server supports. The server MUST add its list to the response even if there are no common security mechanisms in the client's and server's lists. The server's list MUST NOT depend on the contents of the client's list.
Сервер, получающий незащищённый запрос, содержащий поле заголовка Require или Proxy-Require со значением «sec-agree», ДОЛЖЕН ответить клиенту ответом 494 (Security Agreement Required). Сервер ДОЛЖЕН добавить поле заголовка Security-Server к этому ответу, перечисляющее механизмы безопасности, поддерживаемые сервером. Сервер ДОЛЖЕН добавить свой список к ответу, даже если в списках клиента и сервера нет общих механизмов безопасности. Список сервера НЕ ДОЛЖЕН зависеть от содержимого списка клиента.
The server MUST compare the list received in the Security-Client header field with the list to be sent in the Security-Server header field. When the client receives this response, it will choose the common security mechanism with the highest "q" value. Therefore, the server MUST add the necessary information so that the client can initiate that mechanism (e.g., a Proxy-Authenticate header field for HTTP Digest).
Сервер ДОЛЖЕН сравнить список, полученный в поле заголовка Security-Client, со списком, который должен быть отправлен в поле заголовка Security-Server. Когда клиент получает этот ответ, он выберет общий механизм безопасности с наибольшим значением «q». Поэтому сервер ДОЛЖЕН добавить необходимую информацию, чтобы клиент мог инициировать этот механизм (например, поле заголовка Proxy-Authenticate для HTTP Digest).
When the client receives a response with a Security-Server header field, it MUST choose the security mechanism in the server's list with the highest "q" value among all the mechanisms that are known to the client. Then, it MUST initiate that particular security mechanism as described in Section 3.5. This initiation may be carried out without involving any SIP message exchange (e.g., establishing a TLS connection).
Когда клиент получает ответ с полем заголовка Security-Server, он ДОЛЖЕН выбрать механизм безопасности в списке сервера с наибольшим значением «q» среди всех механизмов, известных клиенту. Затем он ДОЛЖЕН инициировать этот конкретный механизм безопасности, как описано в разделе 3.5. Эта инициация может выполняться без участия какого-либо обмена сообщениями SIP (например, установка TLS-соединения).
If an attacker modified the Security-Client header field in the request, the server may not include in its response the information needed to establish the common security mechanism with the highest preference value (e.g., the Proxy-Authenticate header field is missing). A client detecting such a lack of information in the response MUST consider the current security agreement process aborted, and MAY try to start it again by sending a new request with a Security-Client header field as described above.
Если злоумышленник изменил поле заголовка Security-Client в запросе, сервер может не включить в свой ответ информацию, необходимую для установления общего механизма безопасности с наивысшим значением предпочтения (например, отсутствует поле заголовка Proxy-Authenticate). Клиент, обнаруживший такое отсутствие информации в ответе, ДОЛЖЕН считать текущий процесс согласования безопасности прерванным и МОЖЕТ попытаться начать его снова, отправив новый запрос с полем заголовка Security-Client, как описано выше.
All the subsequent SIP requests sent by the client to that server SHOULD make use of the security mechanism initiated in the previous step. These requests MUST contain a Security-Verify header field that mirrors the server's list received previously in the Security- Server header field. These requests MUST also have both a Require and Proxy-Require header fields with the value "sec-agree".
Все последующие SIP-запросы, отправляемые клиентом этому серверу, СЛЕДУЕТ использовать механизм безопасности, инициированный на предыдущем шаге. Эти запросы ДОЛЖНЫ содержать поле заголовка Security-Verify, которое зеркально отражает список сервера, полученный ранее в поле заголовка Security-Server. Эти запросы также ДОЛЖНЫ иметь поля заголовков Require и Proxy-Require со значением «sec-agree».
The server MUST check that the security mechanisms listed in the Security-Verify header field of incoming requests correspond to its static list of supported security mechanisms.
Сервер ДОЛЖЕН проверить, что механизмы безопасности, перечисленные в поле заголовка Security-Verify входящих запросов, соответствуют его статическому списку поддерживаемых механизмов безопасности.
Note that, following the standard SIP header field comparison rules defined in [1], both lists have to contain the same security mechanisms in the same order to be considered equivalent. In addition, for each particular security mechanism, its parameters in both lists need to have the same values.
Обратите внимание, что, следуя стандартным правилам сравнения полей заголовков SIP, определённым в [1], оба списка должны содержать одинаковые механизмы безопасности в одинаковом порядке, чтобы считаться эквивалентными. Кроме того, для каждого конкретного механизма безопасности его параметры в обоих списках должны иметь одинаковые значения.
The server can proceed processing a particular request if, and only if, the list was not modified. If modification of the list is detected, the server MUST respond to the client with a 494 (Security Agreement Required) response. This response MUST include the server's unmodified list of supported security mechanisms. If the list was not modified, and the server is a proxy, it MUST remove the "sec-agree" value from both the Require and Proxy-Require header fields, and then remove the header fields if no values remain.
Сервер может продолжить обработку конкретного запроса тогда и только тогда, когда список не был изменён. Если обнаружено изменение списка, сервер ДОЛЖЕН ответить клиенту ответом 494 (Security Agreement Required). Этот ответ ДОЛЖЕН включать неизменённый список поддерживаемых механизмов безопасности сервера. Если список не был изменён и сервер является прокси, он ДОЛЖЕН удалить значение «sec-agree» как из поля заголовка Require, так и из Proxy-Require, а затем удалить эти поля заголовков, если не осталось значений.
Once the security has been negotiated between two SIP entities, the same SIP entities MAY use the same security when communicating with each other in different SIP roles. For example, if a UAC and its outbound proxy negotiate some security, they may try to use the same security for incoming requests (i.e., the UA will be acting as a UAS).
Как только безопасность согласована между двумя объектами SIP, те же объекты SIP МОГУТ использовать ту же защиту при связи друг с другом в разных ролях SIP. Например, если UAC и его исходящий прокси согласовали некоторую защиту, они могут попытаться использовать ту же защиту для входящих запросов (то есть UA будет действовать как UAS).
The user of a UA SHOULD be informed about the results of the security mechanism agreement. The user MAY decline to accept a particular security mechanism, and abort further SIP communications with the peer.
Пользователя UA СЛЕДУЕТ информировать о результатах соглашения о механизмах безопасности. Пользователь МОЖЕТ отказаться принять конкретный механизм безопасности и прервать дальнейшие SIP-сообщения с партнёром.
2.3.2. Server Initiated
2.3.2. Инициируется сервером
A server decides to use the security agreement described in this document based on local policy. If a server receives a request from the network interface that is configured to use this mechanism, it must check that the request has only one Via entry. If there are several Via entries, the server is not the first-hop SIP entity, and it MUST NOT use this mechanism. For such a request, the server must return a 502 (Bad Gateway) response.
Сервер решает использовать согласование безопасности, описанное в настоящем документе, на основе локальной политики. Если сервер получает запрос с сетевого интерфейса, сконфигурированного для использования этого механизма, он должен проверить, что запрос имеет только одну запись Via. Если имеется несколько записей Via, сервер не является SIP-объектом первого перехода, и он НЕ ДОЛЖЕН использовать этот механизм. Для такого запроса сервер должен вернуть ответ 502 (Bad Gateway).
A server that decides to use this agreement mechanism MUST challenge unprotected requests with one Via entry regardless of the presence or the absence of any Require, Proxy-Require or Supported header fields in incoming requests.
Сервер, решивший использовать этот механизм согласования, ДОЛЖЕН выдавать запрос на незащищённые запросы с одной записью Via независимо от наличия или отсутствия любых полей заголовков Require, Proxy-Require или Supported во входящих запросах.
A server that by policy requires the use of this specification and receives a request that does not have the sec-agree option tag in a Require, Proxy-Require or Supported header field MUST return a 421 (Extension Required) response. If the request had the sec-agree option tag in a Supported header field, it MUST return a 494 (Security Agreement Required) response. In both situation the server MUST also include in the response a Security-Server header field listing its capabilities and a Require header field with an option- tag "sec-agree" in it. The server MUST also add necessary information so that the client can initiate the preferred security mechanism (e.g., a Proxy-Authenticate header field for HTTP Digest).
Сервер, который по политике требует использования настоящей спецификации и получает запрос, не имеющий тега опции sec-agree в поле заголовка Require, Proxy-Require или Supported, ДОЛЖЕН вернуть ответ 421 (Extension Required). Если запрос имел тег опции sec-agree в поле заголовка Supported, он ДОЛЖЕН вернуть ответ 494 (Security Agreement Required). В обеих ситуациях сервер ДОЛЖЕН также включить в ответ поле заголовка Security-Server, перечисляющее его возможности, и поле заголовка Require с тегом опции «sec-agree». Сервер ДОЛЖЕН также добавить необходимую информацию, чтобы клиент мог инициировать предпочтительный механизм безопасности (например, поле заголовка Proxy-Authenticate для HTTP Digest).
Clients that support the extension defined in this document SHOULD add a Supported header field with a value of "sec-agree".
Клиентам, поддерживающим расширение, определённое в настоящем документе, СЛЕДУЕТ добавлять поле заголовка Supported со значением «sec-agree».
2.4. Security Mechanism Initiation
2.4. Инициация механизма безопасности
Once the client chooses a security mechanism from the list received in the Security-Server header field from the server, it initiates that mechanism. Different mechanisms require different initiation procedures.
Как только клиент выбирает механизм безопасности из списка, полученного в поле заголовка Security-Server от сервера, он инициирует этот механизм. Разные механизмы требуют разных процедур инициации.
If "tls" is chosen, the client uses the procedures of Section 8.1.2 of [1] to determine the URI to be used as an input to the DNS procedures of [5]. However, if the URI is a SIP URI, it MUST treat the scheme as if it were sips, not sip. If the URI scheme is not sip, the request MUST be sent using TLS.
Если выбран «tls», клиент использует процедуры раздела 8.1.2 [1] для определения URI, который будет использоваться как вход для процедур DNS из [5]. Однако если URI является URI SIP, он ДОЛЖЕН рассматривать схему так, как если бы она была sips, а не sip. Если схема URI не sip, запрос ДОЛЖЕН быть отправлен с использованием TLS.
If "digest" is chosen, the 494 (Security Agreement Required) response will contain an HTTP Digest authentication challenge. The client MUST use the algorithm and qop parameters in the Security-Server header field to replace the same parameters in the HTTP Digest challenge. The client MUST also use the digest-verify parameter in the Security-Verify header field to protect the Security-Server header field as specified in 2.2. To use "ipsec-ike", the client attempts to establish an IKE connection to the host part of the Request-URI in the first request to the server. If the IKE connection attempt fails, the agreement procedure MUST be considered to have failed, and MUST be terminated.
Если выбран «digest», ответ 494 (Security Agreement Required) будет содержать запрос аутентификации HTTP Digest. Клиент ДОЛЖЕН использовать параметры algorithm и qop из поля заголовка Security-Server, чтобы заменить те же параметры в запросе HTTP Digest. Клиент ДОЛЖЕН также использовать параметр digest-verify в поле заголовка Security-Verify для защиты поля заголовка Security-Server, как указано в разделе 2.2. Чтобы использовать «ipsec-ike», клиент пытается установить соединение IKE с частью хоста Request-URI в первом запросе к серверу. Если попытка соединения IKE терпит неудачу, процедура согласования ДОЛЖНА считаться неудавшейся и ДОЛЖНА быть прекращена.
Note that "ipsec-man" will only work if the communicating SIP entities know which keys and other parameters to use. It is outside the scope of this specification to describe how this information can be made known to the peers. All rules for minimum implementations, such as mandatory-to-implement algorithms, apply as defined in [2], [6], and [7].
Обратите внимание, что «ipsec-man» будет работать только если взаимодействующие объекты SIP знают, какие ключи и другие параметры использовать. Описание того, как эта информация может быть доведена до партнёров, выходит за рамки настоящей спецификации. Все правила для минимальных реализаций, такие как обязательные для реализации алгоритмы, применяются так, как определено в [2], [6] и [7].
In both IPsec-based mechanisms, it is expected that appropriate policy entries for protecting SIP have been configured or will be created before attempting to use the security agreement procedure, and that SIP communications use port numbers and addresses according to these policy entries. It is outside the scope of this specification to describe how this information can be made known to the peers, but it would typically be configured at the same time as the IKE credentials or manual SAs have been entered.
В обоих механизмах на основе IPsec ожидается, что соответствующие записи политики для защиты SIP были сконфигурированы или будут созданы до попытки использования процедуры согласования безопасности и что SIP-сообщения используют номера портов и адреса в соответствии с этими записями политики. Описание того, как эта информация может быть доведена до партнёров, выходит за рамки настоящей спецификации, но обычно она конфигурировалась бы одновременно с вводом учётных данных IKE или ручных SA.
2.5. Duration of Security Associations
2.5. Длительность ассоциаций безопасности
Once a security mechanism has been negotiated, both the server and the client need to know until when it can be used. All the mechanisms described in this document have a different way of signaling the end of a security association. When TLS is used, the termination of the connection indicates that a new negotiation is needed. IKE negotiates the duration of a security association. If the credentials provided by a client using digest are no longer valid, the server will re-challenge the client. It is assumed that when IPsec-man is used, the same out-of-band mechanism used to distribute keys is used to define the duration of the security association.
Как только механизм безопасности согласован, и серверу, и клиенту нужно знать, до какого момента его можно использовать. Все механизмы, описанные в настоящем документе, имеют разный способ сигнализации окончания ассоциации безопасности. При использовании TLS прекращение соединения указывает, что требуется новое согласование. IKE согласовывает длительность ассоциации безопасности. Если учётные данные, предоставленные клиентом, использующим digest, больше не действительны, сервер снова выдаст клиенту запрос. Предполагается, что при использовании IPsec-man тот же внеполосный механизм, используемый для распространения ключей, используется для определения длительности ассоциации безопасности.

3. Backwards Compatibility
3. Обратная совместимость
The use of this extension in a network interface is a matter of local policy. Different network interfaces may follow different policies, and consequently the use of this extension may be situational by nature. UA and server implementations MUST be configurable to operate with or without this extension. A server that is configured to use this mechanism, may also accept requests from clients that use TLS based on the rules defined in [5]. Requests from clients that do not support this extension, and do not support TLS, can not be accepted. This obviously breaks interoperability with some SIP clients. Therefore, this extension should be used in environments where it is somehow ensured that every client implements this extension or is able to use TLS. This extension may also be used in environments where insecure communication is not acceptable if the option of not being able to communicate is also accepted.
Использование этого расширения в сетевом интерфейсе является вопросом локальной политики. Разные сетевые интерфейсы могут следовать разным политикам, и, следовательно, использование этого расширения может быть по своей природе ситуативным. Реализации UA и сервера ДОЛЖНЫ быть конфигурируемыми для работы с этим расширением или без него. Сервер, сконфигурированный для использования этого механизма, может также принимать запросы от клиентов, использующих TLS на основе правил, определённых в [5]. Запросы от клиентов, которые не поддерживают это расширение и не поддерживают TLS, не могут быть приняты. Это, очевидно, нарушает совместимость с некоторыми SIP-клиентами. Поэтому это расширение следует использовать в средах, где так или иначе гарантировано, что каждый клиент реализует это расширение или способен использовать TLS. Это расширение может также использоваться в средах, где незащищённая связь неприемлема, если также принимается вариант невозможности связи.

4. Примеры

4.1. Client Initiated

A UA negotiates the security mechanism to be used with its outbound proxy without knowing beforehand which mechanisms the proxy supports. The OPTIONS method can be used here to request the security capabilities of the proxy. In this way, the security can be initiated even before the first INVITE is sent via the proxy.
UA согласовывает механизм безопасности для использования со своим исходящим прокси, не зная заранее, какие механизмы поддерживает прокси. Здесь может использоваться метод OPTIONS для запроса возможностей безопасности прокси. Таким образом, безопасность может быть инициирована ещё до отправки первого INVITE через прокси.

The outbound proxy responds to the UAC with its own list of security mechanisms - IPsec and TLS (2). The only common security mechanism is TLS, so they establish a TLS connection between them. When the connection is successfully established, the UAC sends an INVITE request over the TLS connection just established (3). This INVITE contains the server's security list. Исходящий прокси отвечает UAC своим собственным списком механизмов безопасности — IPsec и TLS (2). If this example was run without Security-Server header in Step 2, the UAC would not know what kind of security the other one supports, and would be forced to error-prone trials.

5. Security Considerations
5. Вопросы безопасности
This specification is about making it possible to select between various SIP security mechanisms in a secure manner. In particular, the method presented herein allow current networks using, for instance, HTTP Digest, to be securely upgraded to, for instance, IPsec without requiring a simultaneous modification in all equipment. The method presented in this specification is secure only if the weakest proposed mechanism offers at least integrity and replay protection for the Security-Verify header field.
Настоящая спецификация посвящена тому, чтобы сделать возможным выбор между различными механизмами безопасности SIP защищённым образом. В частности, представленный здесь метод позволяет существующим сетям, использующим, например, HTTP Digest, защищённо перейти, например, на IPsec без необходимости одновременной модификации всего оборудования. Метод, представленный в настоящей спецификации, защищён только если самый слабый предложенный механизм обеспечивает хотя бы защиту целостности и от повторного воспроизведения для поля заголовка Security-Verify.
The security implications of this are subtle, but do have a fundamental importance in building large networks that change over time. Given that the hashes are produced also using algorithms agreed in the first unprotected messages, one could ask what the difference in security really is. Assuming integrity protection is mandatory and only secure algorithms are used, we still need to prevent MitM attackers from modifying other parameters, such as whether encryption is provided or not. Let us first assume two peers capable of using both strong and weak security. If the initial offers are not protected in any way, any attacker can easily "downgrade" the offers by removing the strong options. This would force the two peers to use weak security between them. But if the offers are protected in some way -- such as by hashing, or repeating them later when the selected security is really on -- the situation is different. It would not be sufficient for the attacker to modify a single message. Instead, the attacker would have to modify both the offer message, as well as the message that contains the hash/ repetition. More importantly, the attacker would have to forge the weak security that is present in the second message, and would have to do so in real time between the sent offers and the later messages. Otherwise, the peers would notice that the hash is incorrect.
Последствия этого для безопасности тонки, но имеют фундаментальное значение при построении больших сетей, которые меняются со временем. Учитывая, что хеши вычисляются также с использованием алгоритмов, согласованных в первых незащищённых сообщениях, можно спросить, в чём на самом деле разница в безопасности. Предполагая, что защита целостности обязательна и используются только защищённые алгоритмы, нам всё равно нужно предотвратить изменение MitM-злоумышленниками других параметров, таких как наличие шифрования. Предположим сначала, что два партнёра способны использовать как сильную, так и слабую защиту. Если исходные предложения никак не защищены, любой злоумышленник может легко «понизить» предложения, удалив сильные варианты. Это заставило бы двух партнёров использовать между собой слабую защиту. Но если предложения защищены каким-либо образом — например, хешированием или их повторением позже, когда выбранная защита действительно включена, — ситуация иная. Злоумышленнику было бы недостаточно изменить одно сообщение. Вместо этого ему пришлось бы изменить как сообщение с предложением, так и сообщение, содержащее хеш/повторение. Что более важно, злоумышленнику пришлось бы подделать слабую защиту, присутствующую во втором сообщении, и сделать это в реальном времени между отправленными предложениями и более поздними сообщениями. Иначе партнёры заметили бы, что хеш неверен.
If the attacker is able to break the weak security, the security method and/or the algorithm should not be used.
Если злоумышленник способен взломать слабую защиту, метод безопасности и/или алгоритм использоваться не должны.
In conclusion, the security difference is making a trivial attack possible versus demanding the attacker to break algorithms. An example of where this has a serious consequence is when a network is first deployed with integrity protection (such as HTTP Digest [4]), and then later new devices are added that support also encryption (such as TLS [3]). In this situation, an insecure negotiation procedure allows attackers to trivially force even new devices to use only integrity protection. Possible attacks against the security agreement include:
В заключение, разница в безопасности состоит в том, делает ли она тривиальную атаку возможной или же требует от злоумышленника взлома алгоритмов. Пример, когда это имеет серьёзные последствия, — когда сеть сначала развёртывается с защитой целостности (например, HTTP Digest [4]), а затем позже добавляются новые устройства, поддерживающие также шифрование (например, TLS [3]). В этой ситуации незащищённая процедура согласования позволяет злоумышленникам тривиально заставить даже новые устройства использовать только защиту целостности. Возможные атаки на соглашение о безопасности включают:
1. Attackers could try to modify the server's list of security mechanisms in the first response. This would be revealed to the server when the client returns the received list using the security.
1. Злоумышленники могли бы попытаться изменить список механизмов безопасности сервера в первом ответе. Это было бы раскрыто серверу, когда клиент вернёт полученный список, используя механизм безопасности.
2. Attackers could also try to modify the repeated list in the second request from the client. However, if the selected security mechanism uses encryption this may not be possible, and if it uses integrity protection any modifications will be detected by the server.
2. Злоумышленники могли бы также попытаться изменить повторённый список во втором запросе от клиента. Однако если выбранный механизм безопасности использует шифрование, это может быть невозможно, а а если он использует защиту целостности, любые изменения будут обнаружены сервером.
3. Attackers could try to modify the client's list of security mechanisms in the first message. The client selects the security mechanism based on its own knowledge of its own capabilities and the server's list, hence the client's choice would be unaffected by any such modification. However, the server's choice could still be affected as described below:
3. Злоумышленники могли бы попытаться изменить список механизмов безопасности клиента в первом сообщении. Клиент выбирает механизм безопасности исходя из собственного знания своих возможностей и списка сервера, поэтому выбор клиента не зависел бы от такой модификации. Однако выбор сервера всё ещё мог бы быть затронут, как описано ниже:
* If the modification affected the server's choice, the server and client would end up choosing different security mechanisms in Step 3 or 4 of Figure 1. Since they would be unable to communicate to each other, this would be detected as a potential attack. The client would either retry or give up in this situation.
* Если модификация повлияла на выбор сервера, сервер и клиент выбрали бы разные механизмы безопасности на шаге 3 или 4 рисунка 1. Поскольку они не смогли бы взаимодействовать друг с другом, это было бы обнаружено как потенциальная атака. В этой ситуации клиент либо повторил бы попытку, либо сдался.
* If the modification did not affect the server's choice, there's no effect.
* Если модификация не повлияла на выбор сервера, эффекта нет.
4. Finally, attackers may also try to reply old security agreement messages. Each security mechanism must provide replay protection. In particular, HTTP Digest implementations should carefully utilize existing reply protection options such as including a time-stamp to the nonce parameter, and using nonce counters [4].
4. Наконец, злоумышленники могут также попытаться воспроизвести старые сообщения согласования безопасности. Каждый механизм безопасности должен обеспечивать защиту от повторного воспроизведения. В частности, реализации HTTP Digest должны тщательно использовать существующие средства защиты от повторного воспроизведения, такие как включение отметки времени в параметр nonce и применение счётчиков nonce [4].
All clients that implement this specification MUST select HTTP Digest, TLS, IPsec, or any stronger method for the protection of the second request.
Все клиенты, реализующие настоящую спецификацию, ДОЛЖНЫ выбирать HTTP Digest, TLS, IPsec или любой более сильный метод для защиты второго запроса.

The parameters described by the BNF above have the following semantics:
Параметры, описанные приведённой выше BNF, имеют следующую семантику:
Algorithm This parameter defines the used authentication algorithm. It may have a value of "hmac-md5-96" for HMAC-MD5-96 [13], or "hmac-sha-1-96" for HMAC-SHA-1-96 [14]. The algorithm parameter is mandatory.
Algorithm — этот параметр определяет используемый алгоритм аутентификации. Он может иметь значение «hmac-md5-96» для HMAC-MD5-96 [13] или «hmac-sha-1-96» для HMAC-SHA-1-96 [14]. Параметр algorithm обязателен.
Protocol This parameter defines the IPsec protocol. It may have a value of "ah" for AH [6], or "esp" for ESP [7]. If no Protocol parameter is present, the protocol will be ESP by default.
Protocol — этот параметр определяет протокол IPsec. Он может иметь значение «ah» для AH [6] или «esp» для ESP [7]. Если параметр Protocol отсутствует, по умолчанию используется ESP.
Mode This parameter defines the mode in which the IPsec protocol is used. It may have a value of "trans" for transport mode, or a value of "tun" for tunneling mode. If no Mode parameter is present the IPsec protocol is used in transport mode.
Mode — этот параметр определяет режим, в котором используется протокол IPsec. Он может иметь значение «trans» для транспортного режима или «tun» для туннельного режима. Если параметр Mode отсутствует, протокол IPsec используется в транспортном режиме.
Encrypt-algorithm This parameter defines the used encryption algorithm. It may have a value of "des-ede3-cbc" for 3DES [15], or "null" for no encryption. If no Encrypt-algorithm parameter is present, encryption is not used.
Encrypt-algorithm — этот параметр определяет используемый алгоритм шифрования. Он может иметь значение «des-ede3-cbc» для 3DES [15] или «null» для отсутствия шифрования. Если параметр Encrypt-algorithm отсутствует, шифрование не используется.
Spi Defines the SPI number used for inbound messages.
Spi — определяет номер SPI, используемый для входящих сообщений.
Port1 Defines the destination port number for inbound messages that are protected.
Port1 — определяет номер порта назначения для защищённых входящих сообщений.
Port2 Defines the source port number for outbound messages that are protected. Port 2 is optional.
Port2 — определяет номер исходного порта для защищённых исходящих сообщений. Port 2 необязателен.
