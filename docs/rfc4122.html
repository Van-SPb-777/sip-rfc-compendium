Abstract
Аннотация
This specification defines a Uniform Resource Name namespace for UUIDs (Universally Unique IDentifier), also known as GUIDs (Globally Unique IDentifier). A UUID is 128 bits long, and can guarantee uniqueness across space and time. UUIDs were originally used in the Apollo Network Computing System and later in the Open Software Foundation's (OSF) Distributed Computing Environment (DCE), and then in Microsoft Windows platforms.
Настоящая спецификация определяет пространство имён универсальных имён ресурсов (Uniform Resource Name) для UUID (Universally Unique IDentifier), также известных как GUID (Globally Unique IDentifier). UUID имеет длину 128 бит и может гарантировать уникальность в пространстве и во времени. Первоначально UUID использовались в вычислительной сети Apollo Network Computing System, затем в распределённой вычислительной среде (DCE) Open Software Foundation (OSF), а позднее — в платформах Microsoft Windows.

1. Introduction
1. Введение
This specification defines a Uniform Resource Name namespace for UUIDs (Universally Unique IDentifier), also known as GUIDs (Globally Unique IDentifier). A UUID is 128 bits long, and requires no central registration process.
Настоящая спецификация определяет пространство имён универсальных имён ресурсов (Uniform Resource Name) для UUID (Universally Unique IDentifier), также известных как GUID (Globally Unique IDentifier). UUID имеет длину 128 бит и не требует централизованного процесса регистрации.
The information here is meant to be a concise guide for those wishing to implement services using UUIDs as URNs. Nothing in this document should be construed to override the DCE standards that defined UUIDs.
Содержащаяся здесь информация представляет собой краткое руководство для тех, кто желает реализовать службы, использующие UUID в качестве URN. Ничто в настоящем документе не должно толковаться как отменяющее стандарты DCE, определившие UUID.

2. Motivation
2. Мотивация
One of the main reasons for using UUIDs is that no centralized authority is required to administer them (although one format uses IEEE 802 node identifiers, others do not). As a result, generation on demand can be completely automated, and used for a variety of purposes. The UUID generation algorithm described here supports very high allocation rates of up to 10 million per second per machine if necessary, so that they could even be used as transaction IDs.
Одна из главных причин использования UUID состоит в том, что для управления ими не требуется централизованный орган (хотя один формат использует идентификаторы узлов IEEE 802, другие — нет). В результате генерация по требованию может быть полностью автоматизирована и использована для самых разных целей. Описанный здесь алгоритм генерации UUID поддерживает очень высокие темпы выделения — до 10 миллионов в секунду на машину при необходимости, — так что их можно использовать даже в качестве идентификаторов транзакций.
UUIDs are of a fixed size (128 bits) which is reasonably small compared to other alternatives. This lends itself well to sorting, ordering, and hashing of all sorts, storing in databases, simple allocation, and ease of programming in general.
UUID имеют фиксированный размер (128 бит), что достаточно мало по сравнению с другими альтернативами. Это хорошо подходит для сортировки, упорядочивания и всевозможного хеширования, хранения в базах данных, простого выделения и в целом упрощает программирование.
Since UUIDs are unique and persistent, they make excellent Uniform Resource Names. The unique ability to generate a new UUID without a registration process allows for UUIDs to be one of the URNs with the lowest minting cost.
Поскольку UUID уникальны и постоянны, они представляют собой превосходные универсальные имена ресурсов. Уникальная способность генерировать новый UUID без процесса регистрации позволяет UUID быть одними из URN с наименьшей стоимостью создания.

Identifier uniqueness considerations: This document specifies three algorithms to generate UUIDs: the first leverages the unique values of 802 MAC addresses to guarantee uniqueness, the second uses pseudo-random number generators, and the third uses cryptographic hashing and application-provided text strings. As a result, the UUIDs generated according to the mechanisms here will be unique from all other UUIDs that have been or will be assigned.
Соображения уникальности идентификаторов: настоящий документ определяет три алгоритма генерации UUID: первый использует уникальные значения MAC-адресов 802 для гарантии уникальности, второй применяет генераторы псевдослучайных чисел, а третий — криптографическое хеширование и текстовые строки, предоставляемые приложением. В результате UUID, сгенерированные согласно здешним механизмам, будут уникальны среди всех остальных UUID, которые были или будут назначены.
Identifier persistence considerations: UUIDs are inherently very difficult to resolve in a global sense. This, coupled with the fact that UUIDs are temporally unique within their spatial context, ensures that UUIDs will remain as persistent as possible.
Соображения постоянства идентификаторов: UUID по своей природе очень трудно разрешить в глобальном смысле. Это в сочетании с тем, что UUID уникальны во времени в пределах своего пространственного контекста, гарантирует, что UUID останутся настолько постоянными, насколько это возможно.
Process of identifier assignment: Generating a UUID does not require that a registration authority be contacted. One algorithm requires a unique value over space for each generator. This value is typically an IEEE 802 MAC address, usually already available on network-connected hosts. The address can be assigned from an address block obtained from the IEEE registration authority. If no such address is available, or privacy concerns make its use undesirable, Section 4.5 specifies two alternatives. Another approach is to use version 3 or version 4 UUIDs as defined below.
Процесс назначения идентификаторов: генерация UUID не требует обращения к регистрационному органу. Один алгоритм требует уникального в пространстве значения для каждого генератора. Таким значением обычно является MAC-адрес IEEE 802, как правило уже имеющийся на подключённых к сети узлах. Адрес может быть назначен из блока адресов, полученного у регистрационного органа IEEE. Если такой адрес недоступен или соображения конфиденциальности делают его использование нежелательным, в разделе 4.5 указаны две альтернативы. Другой подход — использовать UUID версии 3 или версии 4, определённые ниже.
Process for identifier resolution: Since UUIDs are not globally resolvable, this is not applicable.
Процесс разрешения идентификаторов: поскольку UUID глобально не разрешимы, это неприменимо.
Rules for Lexical Equivalence: Consider each field of the UUID to be an unsigned integer as shown in the table in section Section 4.1.2. Then, to compare a pair of UUIDs, arithmetically compare the corresponding fields from each UUID in order of significance and according to their data type. Two UUIDs are equal if and only if all the corresponding fields are equal.
Правила лексической эквивалентности: рассматривайте каждое поле UUID как целое число без знака, как показано в таблице в разделе 4.1.2. Затем, чтобы сравнить пару UUID, арифметически сравните соответствующие поля каждого UUID в порядке значимости и в соответствии с их типом данных. Два UUID равны тогда и только тогда, когда все соответствующие поля равны.
As an implementation note, equality comparison can be performed on many systems by doing the appropriate byte-order canonicalization, and then treating the two UUIDs as 128-bit unsigned integers.
В качестве замечания по реализации: сравнение на равенство может выполняться во многих системах путём надлежащей канонизации порядка байтов и последующего рассмотрения двух UUID как 128-битных целых чисел без знака.
UUIDs, as defined in this document, can also be ordered lexicographically. For a pair of UUIDs, the first one follows the second if the most significant field in which the UUIDs differ is greater for the first UUID. The second precedes the first if the most significant field in which the UUIDs differ is greater for the second UUID.
UUID, как определено в настоящем документе, также можно упорядочить лексикографически. Для пары UUID первый следует за вторым, если старшее поле, в котором UUID различаются, больше у первого UUID. Второй предшествует первому, если старшее поле, в котором UUID различаются, больше у второго UUID.
Conformance with URN Syntax: The string representation of a UUID is fully compatible with the URN syntax. When converting from a bit-oriented, in-memory representation of a UUID into a URN, care must be taken to strictly adhere to the byte order issues mentioned in the string representation section.
Соответствие синтаксису URN: строковое представление UUID полностью совместимо с синтаксисом URN. При преобразовании битового представления UUID в памяти в URN необходимо тщательно соблюдать вопросы порядка байтов, упомянутые в разделе о строковом представлении.
Validation mechanism: Apart from determining whether the timestamp portion of the UUID is in the future and therefore not yet assignable, there is no mechanism for determining whether a UUID is 'valid'.
Механизм проверки: помимо определения того, находится ли часть отметки времени UUID в будущем и, следовательно, ещё не может быть назначена, не существует механизма определения того, является ли UUID «допустимым».
Scope: UUIDs are global in scope.
Область действия: UUID глобальны.

4.1.1. Вариант

4.1.4. Timestamp
4.1.4. Отметка времени
The timestamp is a 60-bit value. For UUID version 1, this is represented by Coordinated Universal Time (UTC) as a count of 100- nanosecond intervals since 00:00:00.00, 15 October 1582 (the date of Gregorian reform to the Christian calendar).
Отметка времени — это 60-битное значение. Для UUID версии 1 оно представляется по скоординированному всемирному времени (UTC) как количество 100-наносекундных интервалов с 00:00:00.00 15 октября 1582 года (даты григорианской реформы христианского календаря).
For systems that do not have UTC available, but do have the local time, they may use that instead of UTC, as long as they do so consistently throughout the system. However, this is not recommended since generating the UTC from local time only needs a time zone offset.
Системы, в которых UTC недоступно, но есть местное время, могут использовать его вместо UTC, если делают это согласованно во всей системе. Однако это не рекомендуется, поскольку для получения UTC из местного времени нужен лишь часовой пояс.
For UUID version 3 or 5, the timestamp is a 60-bit value constructed from a name as described in Section 4.3.
Для UUID версии 3 или 5 отметка времени — это 60-битное значение, построенное из имени, как описано в разделе 4.3.
For UUID version 4, the timestamp is a randomly or pseudo-randomly generated 60-bit value, as described in Section 4.4.
Для UUID версии 4 отметка времени — это случайно или псевдослучайно сгенерированное 60-битное значение, как описано в разделе 4.4.
4.1.5. Clock Sequence
4.1.5. Последовательность часов
For UUID version 1, the clock sequence is used to help avoid duplicates that could arise when the clock is set backwards in time or if the node ID changes.
Для UUID версии 1 последовательность часов используется для предотвращения дубликатов, которые могут возникнуть при переводе часов назад или при изменении идентификатора узла.
If the clock is set backwards, or might have been set backwards (e.g., while the system was powered off), and the UUID generator can not be sure that no UUIDs were generated with timestamps larger than the value to which the clock was set, then the clock sequence has to be changed. If the previous value of the clock sequence is known, it can just be incremented; otherwise it should be set to a random or high-quality pseudo-random value. Similarly, if the node ID changes (e.g., because a network card has been moved between machines), setting the clock sequence to a random number minimizes the probability of a duplicate due to slight differences in the clock settings of the machines. If the value of clock sequence associated with the changed node ID were known, then the clock sequence could just be incremented, but that is unlikely.
Если часы переведены назад или могли быть переведены назад (например, пока система была выключена), и генератор UUID не может быть уверен, что не было сгенерировано ни одного UUID с отметками времени, большими значения, на которое были переведены часы, то последовательность часов необходимо изменить. Если предыдущее значение последовательности часов известно, его можно просто увеличить; в противном случае ему следует присвоить случайное или высококачественное псевдослучайное значение. Аналогично, если идентификатор узла изменяется (например, из-за перемещения сетевой карты между машинами), установка последовательности часов в случайное число минимизирует вероятность дубликата из-за небольших различий в настройках часов машин. Если бы значение последовательности часов, связанное с изменённым идентификатором узла, было известно, последовательность часов можно было бы просто увеличить, но это маловероятно.
The clock sequence MUST be originally (i.e., once in the lifetime of a system) initialized to a random number to minimize the correlation across systems. This provides maximum protection against node identifiers that may move or switch from system to system rapidly. The initial value MUST NOT be correlated to the node identifier.
Изначально (то есть один раз за время существования системы) последовательность часов ДОЛЖНА быть инициализирована случайным числом, чтобы свести к минимуму корреляцию между системами. Это обеспечивает максимальную защиту от идентификаторов узлов, которые могут быстро перемещаться или переключаться с системы на систему. Начальное значение НЕ ДОЛЖНО быть коррелировано с идентификатором узла.
For UUID version 3 or 5, the clock sequence is a 14-bit value constructed from a name as described in Section 4.3.
Для UUID версии 3 или 5 последовательность часов — это 14-битное значение, построенное из имени, как описано в разделе 4.3.
For UUID version 4, clock sequence is a randomly or pseudo-randomly generated 14-bit value as described in Section 4.4.
Для UUID версии 4 последовательность часов — это случайно или псевдослучайно сгенерированное 14-битное значение, как описано в разделе 4.4.
4.1.6. Node
4.1.6. Узел
For UUID version 1, the node field consists of an IEEE 802 MAC address, usually the host address. For systems with multiple IEEE 802 addresses, any available one can be used. The lowest addressed octet (octet number 10) contains the global/local bit and the unicast/multicast bit, and is the first octet of the address transmitted on an 802.3 LAN.
Для UUID версии 1 поле node состоит из MAC-адреса IEEE 802, обычно адреса хоста. Для систем с несколькими адресами IEEE 802 может использоваться любой доступный. Октет с наименьшим адресом (октет номер 10) содержит бит глобальности/локальности и бит одноадресной/многоадресной передачи и является первым октетом адреса, передаваемого в локальной сети 802.3.
For systems with no IEEE address, a randomly or pseudo-randomly generated value may be used; see Section 4.5. The multicast bit must be set in such addresses, in order that they will never conflict with addresses obtained from network cards.
Для систем без адреса IEEE может использоваться случайно или псевдослучайно сгенерированное значение; см. раздел 4.5. В таких адресах должен быть установлен бит многоадресной передачи, чтобы они никогда не конфликтовали с адресами, полученными от сетевых карт.
For UUID version 3 or 5, the node field is a 48-bit value constructed from a name as described in Section 4.3.
Для UUID версии 3 или 5 поле node — это 48-битное значение, построенное из имени, как описано в разделе 4.3.
For UUID version 4, the node field is a randomly or pseudo-randomly generated 48-bit value as described in Section 4.4.
Для UUID версии 4 поле node — это случайно или псевдослучайно сгенерированное 48-битное значение, как описано в разделе 4.4.
4.1.7. Nil UUID
4.1.7. Нулевой UUID
The nil UUID is special form of UUID that is specified to have all 128 bits set to zero.
Нулевой UUID — это особая форма UUID, для которой задано, что все 128 битов равны нулю.
4.2. Algorithms for Creating a Time-Based UUID
4.2. Алгоритмы создания UUID на основе времени
Various aspects of the algorithm for creating a version 1 UUID are discussed in the following sections.
Различные аспекты алгоритма создания UUID версии 1 рассматриваются в следующих разделах.
4.2.1. Basic Algorithm
4.2.1. Базовый алгоритм
The following algorithm is simple, correct, and inefficient:
Следующий алгоритм прост, корректен и неэффективен:
o Obtain a system-wide global lock
o Захватить глобальную блокировку системы
o From a system-wide shared stable store (e.g., a file), read the UUID generator state: the values of the timestamp, clock sequence, and node ID used to generate the last UUID.
o Из общего для всей системы постоянного хранилища (например, файла) прочитать состояние генератора UUID: значения отметки времени, последовательности часов и идентификатора узла, использованные при генерации последнего UUID.
o Get the current time as a 60-bit count of 100-nanosecond intervals since 00:00:00.00, 15 October 1582.
o Получить текущее время как 60-битное количество 100-наносекундных интервалов с 00:00:00.00 15 октября 1582 года.
o Get the current node ID.
o Получить ID текущего узла.
o If the state was unavailable (e.g., non-existent or corrupted), or the saved node ID is different than the current node ID, generate a random clock sequence value.
o Если состояние было недоступно (например, отсутствовало или было повреждено) либо сохранённый идентификатор узла отличается от текущего, сгенерировать случайное значение последовательности часов.
o If the state was available, but the saved timestamp is later than the current timestamp, increment the clock sequence value.
o Если состояние было доступно, но сохранённая отметка времени позже текущей, увеличить значение последовательности часов.
o Save the state (current timestamp, clock sequence, and node ID) back to the stable store.
o Сохранить состояние (текущую отметку времени, последовательность часов, ID узла) в постоянное хранилище.
o Release the global lock.
o Освободить глобальную блокировку.
o Format a UUID from the current timestamp, clock sequence, and node ID values according to the steps in Section 4.2.2.
o Сформировать UUID из текущих значений отметки времени, последовательности часов и идентификатора узла согласно шагам раздела 4.2.2.
If UUIDs do not need to be frequently generated, the above algorithm may be perfectly adequate. For higher performance requirements, however, issues with the basic algorithm include:
Если UUID не нужно генерировать часто, приведённого выше алгоритма может быть вполне достаточно. Однако при более высоких требованиях к производительности к проблемам базового алгоритма относятся:
o Reading the state from stable storage each time is inefficient.
o Чтение состояния из постоянного хранилища каждый раз неэффективно.
o The resolution of the system clock may not be 100-nanoseconds.
o Разрешение системных часов может быть не 100 наносекунд.
o Writing the state to stable storage each time is inefficient.
o Запись состояния в постоянное хранилище каждый раз неэффективна.
o Sharing the state across process boundaries may be inefficient.
o Совместное использование состояния между процессами может быть неэффективным.
Each of these issues can be addressed in a modular fashion by local improvements in the functions that read and write the state and read the clock. We address each of them in turn in the following sections.
Каждую из этих проблем можно решить модульно за счёт локальных улучшений функций, которые читают и записывают состояние и читают часы. Мы рассмотрим каждую из них по очереди в следующих разделах.
4.2.1.1. Reading Stable Storage
4.2.1.1. Чтение постоянного хранилища
The state only needs to be read from stable storage once at boot time, if it is read into a system-wide shared volatile store (and updated whenever the stable store is updated).
Состояние нужно прочитать из постоянного хранилища только один раз при загрузке, если оно считывается в общее для всей системы энергозависимое хранилище (и обновляется всякий раз при обновлении постоянного хранилища).
If an implementation does not have any stable store available, then it can always say that the values were unavailable. This is the least desirable implementation because it will increase the frequency of creation of new clock sequence numbers, which increases the probability of duplicates.
Если в реализации нет никакого доступного постоянного хранилища, она всегда может считать, что значения были недоступны. Это наименее желательная реализация, поскольку она увеличивает частоту создания новых номеров последовательности часов, что повышает вероятность дубликатов.
If the node ID can never change (e.g., the net card is inseparable from the system), or if any change also reinitializes the clock sequence to a random value, then instead of keeping it in stable store, the current node ID may be returned.
Если идентификатор узла никогда не может измениться (например, сетевая карта неотделима от системы) или если любое изменение также переинициализирует последовательность часов случайным значением, то вместо хранения в постоянном хранилище можно возвращать текущий идентификатор узла.
4.2.1.2. System Clock Resolution
4.2.1.2. Разрешение системных часов
The timestamp is generated from the system time, whose resolution may be less than the resolution of the UUID timestamp.
Отметка времени формируется из системного времени, разрешение которого может быть меньше разрешения отметки времени UUID.
If UUIDs do not need to be frequently generated, the timestamp can simply be the system time multiplied by the number of 100-nanosecond intervals per system time interval.
Если UUID не нужно генерировать часто, отметкой времени может быть просто системное время, умноженное на число 100-наносекундных интервалов в одном интервале системного времени.
If a system overruns the generator by requesting too many UUIDs within a single system time interval, the UUID service MUST either return an error, or stall the UUID generator until the system clock catches up.
Если система перегружает генератор, запрашивая слишком много UUID в течение одного интервала системного времени, служба UUID ДОЛЖНА либо вернуть ошибку, либо задержать генератор UUID до тех пор, пока системные часы не догонят.
A high resolution timestamp can be simulated by keeping a count of the number of UUIDs that have been generated with the same value of the system time, and using it to construct the low order bits of the timestamp. The count will range between zero and the number of 100-nanosecond intervals per system time interval.
Отметку времени высокого разрешения можно имитировать, ведя подсчёт числа UUID, сгенерированных с одним и тем же значением системного времени, и используя его для построения младших битов отметки времени. Счётчик будет изменяться от нуля до числа 100-наносекундных интервалов в одном интервале системного времени.
Note: If the processors overrun the UUID generation frequently, additional node identifiers can be allocated to the system, which will permit higher speed allocation by making multiple UUIDs potentially available for each time stamp value.
Примечание. Если процессоры часто перегружают генерацию UUID, системе можно выделить дополнительные идентификаторы узлов, что позволит быстрее выделять UUID за счёт потенциальной доступности нескольких UUID для каждого значения отметки времени.
4.2.1.3. Writing Stable Storage
4.2.1.3. Запись в постоянное хранилище
The state does not always need to be written to stable store every time a UUID is generated. The timestamp in the stable store can be periodically set to a value larger than any yet used in a UUID. As long as the generated UUIDs have timestamps less than that value, and the clock sequence and node ID remain unchanged, only the shared volatile copy of the state needs to be updated. Furthermore, if the timestamp value in stable store is in the future by less than the typical time it takes the system to reboot, a crash will not cause a reinitialization of the clock sequence.
Состояние не всегда нужно записывать в постоянное хранилище каждый раз при генерации UUID. Отметку времени в постоянном хранилище можно периодически устанавливать в значение, большее любого, уже использованного в UUID. Пока сгенерированные UUID имеют отметки времени меньше этого значения, а последовательность часов и идентификатор узла остаются неизменными, обновлять нужно только общую энергозависимую копию состояния. Кроме того, если значение отметки времени в постоянном хранилище опережает текущее менее чем на типичное время перезагрузки системы, сбой не вызовет переинициализации последовательности часов.
4.2.1.4. Sharing State Across Processes
4.2.1.4. Совместное использование состояния между процессами
If it is too expensive to access shared state each time a UUID is generated, then the system-wide generator can be implemented to allocate a block of time stamps each time it is called; a per- process generator can allocate from that block until it is exhausted.
Если обращаться к общему состоянию при каждой генерации UUID слишком дорого, то системный генератор можно реализовать так, чтобы при каждом вызове он выделял блок отметок времени; генератор уровня процесса может выделять из этого блока, пока тот не исчерпан.
4.2.2. Generation Details
4.2.2. Детали генерации
Version 1 UUIDs are generated according to the following algorithm:
UUID версии 1 генерируются согласно приведённому ниже алгоритму:
o Determine the values for the UTC-based timestamp and clock sequence to be used in the UUID, as described in Section 4.2.1.
o Определить значения отметки времени на основе UTC и последовательности часов, которые будут использоваться в UUID, как описано в разделе 4.2.1.
o For the purposes of this algorithm, consider the timestamp to be a 60-bit unsigned integer and the clock sequence to be a 14-bit unsigned integer. Sequentially number the bits in a field, starting with zero for the least significant bit.
o Для целей этого алгоритма считайте отметку времени 60-битным целым числом без знака, а последовательность часов — 14-битным целым числом без знака. Пронумеруйте биты в поле последовательно, начиная с нуля для младшего бита.
o Set the time_low field equal to the least significant 32 bits (bits zero through 31) of the timestamp in the same order of significance.
o Установить поле time_low равным 32 младшим битам (биты с 0 по 31) отметки времени, сохраняя тот же порядок значимости.
o Set the time_mid field equal to bits 32 through 47 from the timestamp in the same order of significance.
o Установить поле time_mid равным битам с 32 по 47 отметки времени в том же порядке значимости.
o Set the 12 least significant bits (bits zero through 11) of the time_hi_and_version field equal to bits 48 through 59 from the timestamp in the same order of significance.
o Установить 12 младших битов (биты с 0 по 11) поля time_hi_and_version равными битам с 48 по 59 отметки времени с сохранением того же порядка значимости.
o Set the four most significant bits (bits 12 through 15) of the time_hi_and_version field to the 4-bit version number corresponding to the UUID version being created, as shown in the table above.
o Установить четыре старших бита (биты с 12 по 15) поля time_hi_and_version в 4-битный номер версии, соответствующий создаваемой версии UUID, как показано в таблице выше.
o Set the clock_seq_low field to the eight least significant bits (bits zero through 7) of the clock sequence in the same order of significance.
o Установить поле clock_seq_low в восемь младших битов (биты с 0 по 7) последовательности часов в том же порядке значимости.
o Set the 6 least significant bits (bits zero through 5) of the clock_seq_hi_and_reserved field to the 6 most significant bits (bits 8 through 13) of the clock sequence in the same order of significance.
o Установить шесть младших битов (биты с 0 по 5) поля clock_seq_hi_and_reserved равными шести старшим битам (биты с 8 по 13) последовательности часов в том же порядке значимости.
o Set the two most significant bits (bits 6 and 7) of the clock_seq_hi_and_reserved to zero and one, respectively.
o Установить два старших бита (биты 6 и 7) clock_seq_hi_and_reserved в ноль и единицу соответственно.
o Set the node field to the 48-bit IEEE address in the same order of significance as the address.
o Установить поле node в 48-битный адрес IEEE в том же порядке значимости, что и адрес.
4.3. Algorithm for Creating a Name-Based UUID
4.3. Алгоритм создания UUID на основе имени
The version 3 or 5 UUID is meant for generating UUIDs from "names" that are drawn from, and unique within, some "name space". The concept of name and name space should be broadly construed, and not limited to textual names. For example, some name spaces are the domain name system, URLs, ISO Object IDs (OIDs), X.500 Distinguished Names (DNs), and reserved words in a programming language. The mechanisms or conventions used for allocating names and ensuring their uniqueness within their name spaces are beyond the scope of this specification.
UUID версии 3 или 5 предназначены для генерации UUID из «имён», которые берутся из некоторого «пространства имён» и уникальны в нём. Понятия имени и пространства имён следует толковать широко, не ограничиваясь текстовыми именами. Например, некоторые пространства имён — это система доменных имён, URL, объектные идентификаторы ISO (OID), отличительные имена X.500 (DN) и зарезервированные слова в языке программирования. Механизмы или соглашения, используемые для выделения имён и обеспечения их уникальности в пределах их пространств имён, выходят за рамки настоящей спецификации.
The requirements for these types of UUIDs are as follows:
Требования к UUID этих типов состоят в следующем:
o The UUIDs generated at different times from the same name in the same namespace MUST be equal.
o UUID, сгенерированные в разное время из одного и того же имени в одном и том же пространстве имён, ДОЛЖНЫ быть равны.
o The UUIDs generated from two different names in the same namespace should be different (with very high probability).
o UUID, сгенерированные из двух разных имён в одном и том же пространстве имён, должны различаться (с очень высокой вероятностью).
o The UUIDs generated from the same name in two different namespaces should be different with (very high probability).
o UUID, сгенерированные из одного и того же имени в двух разных пространствах имён, должны различаться (с очень высокой вероятностью).
o If two UUIDs that were generated from names are equal, then they were generated from the same name in the same namespace (with very high probability).
o Если два UUID, сгенерированные из имён, равны, то они были сгенерированы из одного и того же имени в одном и том же пространстве имён (с очень высокой вероятностью).
The algorithm for generating a UUID from a name and a name space are as follows:
Алгоритм генерации UUID из имени и пространства имён состоит в следующем:
o Allocate a UUID to use as a "name space ID" for all UUIDs generated from names in that name space; see Appendix C for some pre-defined values.
o Выделить UUID в качестве «идентификатора пространства имён» для всех UUID, генерируемых из имён в этом пространстве имён; предопределённые значения см. в приложении C.
o Choose either MD5 [4] or SHA-1 [8] as the hash algorithm; If backward compatibility is not an issue, SHA-1 is preferred.

4.5. Node IDs that Do Not Identify the Host
4.5. Идентификаторы узлов, не идентифицирующие хост
This section describes how to generate a version 1 UUID if an IEEE 802 address is not available, or its use is not desired.
В этом разделе описывается, как сгенерировать UUID версии 1, если адрес IEEE 802 недоступен или его использование нежелательно.
One approach is to contact the IEEE and get a separate block of addresses. At the time of writing, the application could be found at <http://standards.ieee.org/regauth/oui/pilot-ind.html>, and the cost was US$550.
Один из подходов — обратиться в IEEE и получить отдельный блок адресов. На момент написания заявку можно было найти по адресу <http://standards.ieee.org/regauth/oui/pilot-ind.html>, а стоимость составляла 550 долларов США.
A better solution is to obtain a 47-bit cryptographic quality random number and use it as the low 47 bits of the node ID, with the least significant bit of the first octet of the node ID set to one. This bit is the unicast/multicast bit, which will never be set in IEEE 802 addresses obtained from network cards. Hence, there can never be a conflict between UUIDs generated by machines with and without network cards. (Recall that the IEEE 802 spec talks about transmission order, which is the opposite of the in-memory representation that is discussed in this document.)
Лучшее решение — получить 47-битное случайное число криптографического качества и использовать его как младшие 47 битов идентификатора узла, установив младший бит первого октета идентификатора узла в единицу. Этот бит является битом одноадресной/многоадресной передачи, который никогда не будет установлен в адресах IEEE 802, полученных от сетевых карт. Следовательно, конфликт между UUID, сгенерированными машинами с сетевыми картами и без них, невозможен. (Напомним, что спецификация IEEE 802 говорит о порядке передачи, противоположном представлению в памяти, которое рассматривается в настоящем документе.)
For compatibility with earlier specifications, note that this document uses the unicast/multicast bit, instead of the arguably more correct local/global bit.
Для совместимости с более ранними спецификациями отметим, что в настоящем документе используется бит одноадресной/многоадресной передачи вместо, возможно, более правильного бита локальности/глобальности.
Advice on generating cryptographic-quality random numbers can be found in RFC1750 [5].
Рекомендации по генерации случайных чисел криптографического качества можно найти в RFC1750 [5].
In addition, items such as the computer's name and the name of the operating system, while not strictly speaking random, will help differentiate the results from those obtained by other systems.
Кроме того, такие элементы, как имя компьютера и название операционной системы, хотя и не являются строго случайными, помогут отличить результаты от полученных другими системами.
The exact algorithm to generate a node ID using these data is system specific, because both the data available and the functions to obtain them are often very system specific. A generic approach, however, is to accumulate as many sources as possible into a buffer, use a message digest such as MD5 [4] or SHA-1 [8], take an arbitrary 6 bytes from the hash value, and set the multicast bit as described above.
Точный алгоритм генерации идентификатора узла с использованием этих данных зависит от системы, поскольку как доступные данные, так и функции для их получения часто очень сильно зависят от системы. Однако общий подход состоит в том, чтобы накопить как можно больше источников в буфере, применить дайджест сообщения, такой как MD5 [4] или SHA-1 [8], взять произвольные 6 байтов из значения хеша и установить бит многоадресной передачи, как описано выше.
5. Community Considerations
5. Соображения для сообщества
The use of UUIDs is extremely pervasive in computing. They comprise the core identifier infrastructure for many operating systems (Microsoft Windows) and applications (the Mozilla browser) and in many cases, become exposed to the Web in many non-standard ways. This specification attempts to standardize that practice as openly as possible and in a way that attempts to benefit the entire Internet.
Использование UUID чрезвычайно распространено в вычислительной технике. Они составляют основу инфраструктуры идентификаторов для многих операционных систем (Microsoft Windows) и приложений (браузер Mozilla) и во многих случаях попадают в Веб самыми разными нестандартными способами. Настоящая спецификация пытается стандартизировать эту практику как можно более открыто и так, чтобы это шло на пользу всему Интернету.
6. Security Considerations
6. Соображения безопасности
Do not assume that UUIDs are hard to guess; they should not be used as security capabilities (identifiers whose mere possession grants access), for example. A predictable random number source will exacerbate the situation.
Не предполагайте, что UUID трудно угадать; например, их не следует использовать в качестве средств безопасности (идентификаторов, одно обладание которыми предоставляет доступ). Предсказуемый источник случайных чисел усугубит ситуацию.
Do not assume that it is easy to determine if a UUID has been slightly transposed in order to redirect a reference to another object. Humans do not have the ability to easily check the integrity of a UUID by simply glancing at it.
Не предполагайте, что легко определить, подвергся ли UUID небольшой перестановке, чтобы перенаправить ссылку на другой объект. Люди не способны легко проверить целостность UUID, просто бросив на него взгляд.
Distributed applications generating UUIDs at a variety of hosts must be willing to rely on the random number source at all hosts. If this is not feasible, the namespace variant should be used.
Распределённые приложения, генерирующие UUID на различных хостах, должны быть готовы полагаться на источник случайных чисел на всех хостах. Если это неосуществимо, следует использовать вариант пространства имён.
