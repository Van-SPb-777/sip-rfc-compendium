1. Introduction
1. Введение
This memo defines a portion of the Management Information Base (MIB) for use with network management protocols in the Internet community. In particular, it describes a set of managed objects that are used to manage Session Initiation Protocol (SIP) entities, which include User Agents, and Proxy, Redirect and Registrar servers. The managed objects defined in this document are intended to provide basic SIP protocol management for SIP entities. The management of application-specific or service-specific SIP configuration is out of scope.
В этом документе определяется часть базы управляющей информации (MIB) для использования с протоколами управления сетью в интернет-сообществе. В частности, он описывает набор управляемых объектов, которые используются для управления объектами протокола инициирования сессий (SIP), которые включают в себя пользовательские агенты, а также прокси, серверы перенаправления и регистраторы. Управляемые объекты, определенные в этом документе, предназначены для обеспечения базового управления протоколом SIP для объектов SIP. Управление конфигурацией SIP для конкретного приложения или службы выходит за рамки.

3. The Internet-Standard Management Framework
3. Internet-Standard Структура управления
For a detailed overview of the documents that describe the current Internet-Standard Management Framework, please refer to section 7 of RFC 3410 [RFC3410]. Managed objects are accessed via a virtual information store, termed the Management Information Base or MIB. MIB objects are generally accessed through the Simple Network Management Protocol (SNMP). Objects in the MIB are defined using the mechanisms defined in the Structure of Management Information (SMI). This memo specifies a set of MIB modules that are compliant to the SMIv2, which is described in STD 58, comprised of RFC 2578 [RFC2578], RFC 2579 [RFC2579], and RFC 2580 [RFC2580].
Подробный обзор документов, описывающих текущую структуру управления Internet-Standard, см. в разделе 7 документа RFC 3410 [RFC3410]. Доступ к управляемым объектам осуществляется через виртуальное хранилище информации, называемое базой управляющей информации или MIB. Доступ к объектам MIB обычно осуществляется через простой протокол сетевого управления (SNMP). Объекты в MIB определяются с использованием механизмов, определенных в Структуре информации управления (SMI). В этом документе указан набор модулей MIB, совместимых с SMIv2, описанным в STD 58, и состоит из RFC 2578 [RFC2578], RFC 2579 [RFC2579] и RFC 2580 [RFC2580].
4. Overview
4. Обзор
SIP [RFC3261] is an application-layer control (signaling) protocol for creating, modifying, and terminating sessions with one or more participants. These sessions include Internet telephone calls, multimedia distribution, and multimedia conferences.
SIP [RFC3261] — это протокол управления (сигнализации) прикладного уровня для создания, изменения и завершения сессий с одним или несколькими участниками. Эти сессии включают телефонные вызовы через Интернет, распространение мультимедиа и мультимедийные конференции.
This MIB provides some managed objects for SIP entities defined in RFC 3261 [RFC3261] - User Agents (UA), and Proxy, Redirect, and Registrar servers. It is intended to provide management of the basic SIP entities. It provides for monitoring of status and protocol statistics, as well as for configuration of SIP entities.
Этот MIB предоставляет некоторые управляемые объекты для объектов SIP, определенных в RFC 3261 [RFC3261] — пользовательских агентов (UA), а также прокси, серверов перенаправления и регистраторов. Он предназначен для обеспечения управления основными объектами SIP. Он обеспечивает мониторинг состояния и статистики протоколов, а также настройку SIP-объектов.
5. Structure of the SIP MIB
5. Структура SIP MIB
Four MIB modules are specified: SIP-COMMON-MIB, SIP-SERVER-MIB, SIP- UA-MIB, and SIP-TC-MIB. SIP-COMMON-MIB contains common MIB objects used in all the SIP entities. SIP-SERVER-MIB contains objects specific to Proxy, Redirect, and Registrar servers. SIP-UA-MIB includes objects specific to User Agents. SIP-TC-MIB defines the textual conventions used throughout the MIB modules.
Указаны четыре модуля MIB: SIP-COMMON-MIB, SIP-SERVER-MIB, SIP-UA-MIB и SIP-TC-MIB. SIP-COMMON-MIB содержит общие объекты MIB, используемые во всех объектах SIP. SIP-SERVER-MIB содержит объекты, специфичные для прокси, серверов перенаправления и регистраторов. SIP-UA-MIB включает объекты, специфичные для пользовательских агентов. SIP-TC-MIB определяет текстовые соглашения, используемые в модулях MIB.

5.2. Relationship to the Network Services MIB
5.2. Связь с MIB сетевых служб
In the design of the SIP MIB, the authors considered the following requirement: the SIP MIB must allow a single system with a single SNMP agent to support multiple instances of various SIP MIB modules. This requirement is met by using the framework provided by the Network Services Monitoring MIB, NETWORK-SERVICES-MIB, RFC 2788 [RFC2788].
При разработке SIP MIB авторы учли следующее требование: SIP MIB должен позволять одной системе с одним агентом SNMP поддерживать несколько экземпляров различных модулей SIP MIB. Это требование выполняется за счет использования структуры, предоставляемой MIB мониторинга сетевых служб, NETWORK-SERVICES-MIB, RFC 2788 [RFC2788].
A device implementing the SIP MIB MUST support the NETWORK-SERVICES- MIB and, at a minimum, MUST support the index and name objects (applIndex and applName) in the application table (applTable). In order to allow each instance of a SIP entity to be managed as a separate network service application, a naming convention SHOULD be used to make the application name unique. For example, if a system is running 2 SIP UAs that need to be managed as 2 separate SIP entities, by convention, the application names used in the Network Services Monitoring MIB application table should be "sip_ua1" and "sip_ua2". This convention allows each instance to have its own row in the application table (applTable).
Устройство, реализующее SIP MIB, ДОЛЖНО поддерживать NETWORK-SERVICES- MIB и, как минимум, ДОЛЖНО поддерживать объекты индекса и имени (applIndex и applName) в таблице приложений (applTable). Чтобы разрешить управление каждым экземпляром объекта SIP как отдельным приложением сетевой службы, СЛЕДУЕТ использовать соглашение об именах, чтобы сделать имя приложения уникальным. Например, если в системе работают два агента SIP UA, которыми необходимо управлять как двумя отдельными объектами SIP, по соглашению имена приложений, используемые в таблице приложений MIB мониторинга сетевых служб, должны быть «sip_ua1» и «sip_ua2». This convention allows each instance to have its own row in the application table (applTable).

o for a SIP Proxy entity, the applName value SHOULD be equal to a character string starting with "sip_proxy" followed by a unique application instance identifier, for example, "sip_proxy1", "sip_proxy17".
o для объекта SIP Proxy значение applName ДОЛЖНО быть равно строке символов, начинающейся с «sip_proxy», за которой следует уникальный идентификатор экземпляра приложения, например, «sip_proxy1», «sip_proxy17».

o для объекта-регистратора SIP значение applName ДОЛЖНО быть равно строке символов, начинающейся с «sip_registrar», за которой следует уникальный идентификатор экземпляра приложения, например, «sip_registrar1», «sip_registrar2».
o for a SIP User Agent entity, the applName value SHOULD be equal to a character string starting with "sip_ua" followed by a unique application instance identifier, for example, "sip_ua1", "sip_ua2".
o для объекта SIP User Agent значение applName ДОЛЖНО быть равно строке символов, начинающейся с «sip_ua», за которой следует уникальный идентификатор экземпляра приложения, например, «sip_ua1», «sip_ua2».
o for any combination of Proxy, Registrar, or Redirect Server being managed as a single aggregate entity, the applName value for the combined server entity SHOULD reflect the appropriate combination followed by a unique application instance identifier. In order to facilitate consistent agent behavior and management application expectations, the following order of names is RECOMMENDED:
o для любой комбинации прокси, регистратора или сервера перенаправления, управляемой как единый совокупный объект, значение applName для объединенного объекта сервера ДОЛЖНО отражать соответствующую комбинацию, за которой следует уникальный идентификатор экземпляра приложения. Чтобы обеспечить согласованное поведение агентов и ожидания приложений управления, РЕКОМЕНДУЕТСЯ следующий порядок имен:
* if Proxy exists, list first.
* если прокси существует, укажите его первым.
* if Proxy and Redirect exists, list Redirect second.
* если прокси и перенаправление существуют, укажите второе перенаправление.
* if Registrar exists, always list last.
* если регистратор существует, всегда указывайте последним.
For example "sip_proxy1", "sip_proxy_registrar1", "sip_proxy_redirect5", "sip_proxy_redirect_registrar2", or "sip_registrar1".

6. Accommodating SIP Extension Methods

The core set of SIP methods is defined in RFC 3261 [RFC3261]. Other IETF RFCs define additional methods. In the future, additional methods may be defined. In order to avoid having to update the SIP- COMMON-MIB module to accommodate these extension methods, we use a method identifier name (SipTCMethodName TEXTUAL-CONVENTION) to represent all SIP methods registered with IANA.
Основной набор методов SIP определен в RFC 3261 [RFC3261]. Другие RFC IETF определяют дополнительные методы. В будущем могут быть определены дополнительные методы. There are a number of management objects defined in the SIP-COMMON- MIB MIB module with a MAX-ACCESS clause of read-write and/or read- create. The support for SET operations in a non- secure environment without proper protection can have a negative effect on network operations.

Такие объекты могут считаться конфиденциальными или уязвимыми в некоторых сетевых средах. Поддержка операций SET в незащищенной среде без надлежащей защиты может оказать негативное влияние на работу сети.

Some of the readable objects in the MIB modules (i.e., objects with a MAX-ACCESS other than not-accessible) may be considered sensitive or vulnerable in some network environments. It is thus important to control even GET and/or NOTIFY access to these objects and possibly to even encrypt the values of these objects when sending them over the network via SNMP.
Некоторые из читаемых объектов в модулях MIB (то есть, объекты с MAX-ACCESS отличными от недоступных) могут считаться конфиденциальными или уязвимыми в некоторых сетевых средах. The sipCommonCfgTable table contains some objects that may help attackers gain knowledge about the status and operations of the SIP service. In particular, the object value of sipCommonCfgServiceOperStatus may indicate that the SIP entity is in congested state and may lead attackers to build additional service attacks to overload the system.
Таблица sipCommonCfgTable содержит некоторые объекты, которые могут помочь злоумышленникам получить информацию о состоянии и работе службы SIP. В частности, значение объекта sipCommonCfgServiceOperStatus может указывать на то, что объект SIP находится в перегруженном состоянии, и может побудить злоумышленников создать дополнительные сервисные атаки для перегрузки системы.
The sipCommonCfgEntityType object indicates the type of SIP entity, and the sipCommonMethodSupportedTable table contains in the SIP- COMMON-MIB MIB module list of SIP methods supported by each entity in the system. Gaining access to this information may allow attackers to build method-specific attacks or use unsupported methods to create denial-of-service attack scenarios.
Объект sipCommonCfgEntityType указывает тип объекта SIP, а таблица sipCommonMethodSupportedTable содержит в модуле SIP-COMMON-MIB список методов SIP, поддерживаемых каждым объектом в системе. Получение доступа к этой информации может позволить злоумышленникам создавать атаки с использованием конкретных методов или использовать неподдерживаемые методы для создания сценариев атак типа «отказ в обслуживании».
In the SIP-UA-MIB MIB module, the sipUACfgServerTable contains the address of the SIP servers providing services to the UA, and obtaining this information may disclose some private or sensitive information about the SIP service usage.
В модуле MIB SIP-UA-MIB таблица sipUACfgServerTable содержит адреса SIP-серверов, предоставляющих услуги UA, и получение этой информации может раскрыть некоторую частную или конфиденциальную информацию об использовании службы SIP.
In the SIP-SERVER-MIB MIB module, the sipServerCfgProxyAuthMethod object defines the authentication methods supported by the server and may be used to build specific denial-of-service attackers targeted at the security mechanisms employed by the SIP entity.
В модуле MIB SIP-SERVER-MIB объект sipServerCfgProxyAuthMethod определяет методы аутентификации, поддерживаемые сервером, и может использоваться для создания конкретных злоумышленников типа «отказ в обслуживании», нацеленных на механизмы безопасности, используемые объектом SIP.
SNMP versions prior to SNMPv3 did not include adequate security. Even if the network itself is secure (for example by using IPsec), even then, there is no control as to who on the secure network is allowed to access and GET/SET (read/change/create/delete) the objects in this set of MIB modules.
Версии SNMP до SNMPv3 не обеспечивали должной безопасности. Даже если сама сеть защищена (например, с использованием IPsec), даже в этом случае нет контроля над тем, кому в защищенной сети разрешен доступ и GET/SET (чтение/изменение/создание/удаление) объектов в этом наборе модулей MIB.
It is RECOMMENDED that implementers consider the security features as provided by the SNMPv3 framework (see RFC 3410 [RFC3410]), including full support for the SNMPv3 cryptographic mechanisms (for authentication and privacy).
РЕКОМЕНДУЕТСЯ, чтобы разработчики учитывали функции безопасности, предоставляемые структурой SNMPv3 (см. RFC 3410 [RFC3410]), включая полную поддержку криптографических механизмов SNMPv3 (для аутентификации и конфиденциальности).
Further, deployment of SNMP versions prior to SNMPv3 is NOT RECOMMENDED. Instead, it is RECOMMENDED to deploy SNMPv3 and to enable cryptographic security. It is then a customer/operator responsi when bility to ensure that the SNMP entity giving access to an instance of this MIB module is properly configured to give access to the objects only to those principals (users) that have legitimate rights to indeed GET or SET (change/create/delete) them.
Кроме того, НЕ РЕКОМЕНДУЕТСЯ развертывание версий SNMP до SNMPv3. Вместо этого РЕКОМЕНДУЕТСЯ развернуть SNMPv3 и включить криптографическую безопасность. В этом случае ответственность клиента/оператора заключается в возможности гарантировать, что объект SNMP, предоставляющий доступ к экземпляру этого модуля MIB, правильно настроен для предоставления доступа к объектам только тем принципалам (пользователям), которые имеют законные права на действительное GET или SET (изменение/создание/удаление) их.
