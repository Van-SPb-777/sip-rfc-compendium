Abstract
Аннотация
This document enables a pair of communicating proxies to reuse a congestion-controlled connection between themselves for sending requests in the forwards and backwards direction. Because the connection is essentially aliased for requests going in the backwards direction, reuse is predicated upon both the communicating endpoints authenticating themselves using X.509 certificates through Transport Layer Security (TLS). For this reason, we only consider connection reuse for TLS over TCP and TLS over Stream Control Transmission Protocol (SCTP). This document also provides guidelines on connection reuse and virtual SIP servers and the interaction of connection reuse and DNS SRV lookups in SIP.
Настоящий документ позволяет паре взаимодействующих прокси повторно использовать соединение с управлением перегрузкой между собой для отправки запросов в прямом и обратном направлениях. Поскольку для запросов, идущих в обратном направлении, соединение по сути является алиасом, повторное использование обусловлено тем, что обе взаимодействующие конечные точки аутентифицируют себя с помощью сертификатов X.509 через протокол транспортного уровня безопасности (TLS). По этой причине мы рассматриваем повторное использование соединений только для TLS поверх TCP и TLS поверх протокола передачи с управлением потоками (SCTP). Документ также содержит рекомендации по повторному использованию соединений и виртуальным SIP-серверам, а также по взаимодействию повторного использования соединений и поиска DNS SRV в SIP.

1. Introduction
1. Введение
SIP entities can communicate using either unreliable/connectionless (e.g., UDP) or reliable/connection-oriented (e.g., TCP, SCTP [RFC4960]) transport protocols. When SIP entities use a connection- oriented protocol (such as TCP or SCTP) to send a request, they typically originate their connections from an ephemeral port.
Объекты SIP могут обмениваться данными, используя либо ненадёжные протоколы транспорта без установления соединения (например, UDP), либо надёжные протоколы транспорта с установлением соединения (например, TCP, SCTP [RFC4960]). Когда объекты SIP используют протокол с установлением соединения (такой как TCP или SCTP) для отправки запроса, они обычно открывают свои соединения с эфемерного порта.
In the following example, A listens for SIP requests over TLS on TCP port 5061 (the default port for SIP over TLS over TCP), but uses an ephemeral port (port 49160) for a new connection to B. These entities could be SIP user agents or SIP proxy servers.
В приведённом ниже примере A прослушивает SIP-запросы через TLS на TCP-порту 5061 (порт по умолчанию для SIP через TLS поверх TCP), но использует эфемерный порт (порт 49160) для нового соединения с B. Этими объектами могут быть агенты пользователя SIP или прокси-серверы SIP.
+-----------+ 49160 (UAC) 5061 (UAS) +-----------+ | |--------------------------->| | | Entity | | Entity | | A | | B | | | 5061 (UAS) | | +-----------+ +-----------+ Figure 1: Uni-directional connection for requests from A to B
+-----------+ 49160 (UAC) 5061 (UAS) +-----------+ | |--------------------------->| | | Entity | | Entity | | A | | B | | | 5061 (UAS) | | +-----------+ +-----------+ Figure 1: Uni-directional connection for requests from A to B
The SIP protocol includes the notion of a persistent connection (defined in Section 2), which is a mechanisms to insure that responses to a request reuse the existing connection that is typically still available, as well as reusing the existing connections for other requests sent by the originator of the connection. However, new requests sent in the backwards direction -- in the example above, requests from B destined to A -- are unlikely to reuse the existing connection. This frequently causes a pair of SIP entities to use one connection for requests sent in each direction, as shown below.
Протокол SIP включает понятие постоянного соединения (persistent connection, определённого в разделе 2) — механизма, который гарантирует, что ответы на запрос используют существующее, обычно всё ещё доступное соединение, а также что существующие соединения повторно используются для других запросов, отправляемых инициатором соединения. Однако новые запросы, отправляемые в обратном направлении, — в примере выше это запросы от B к A, — вряд ли повторно используют существующее соединение. Из-за этого пара объектов SIP часто использует по одному соединению для запросов, отправляемых в каждом направлении, как показано ниже.
+-----------+ 49160 5061 +-----------+ | |.......................>| | | Entity | | Entity | | A | 5061 49170 | B | | |<-----------------------| | +-----------+ +-----------+ Figure 2: Two connections for requests between A and B
+-----------+ 49160 5061 +-----------+ | |.......................>| | | Entity | | Entity | | A | 5061 49170 | B | | |<-----------------------| | +-----------+ +-----------+ Figure 2: Two connections for requests between A and B
Unlike TCP, TLS connections can be reused to send requests in the backwards direction since each end can be authenticated when the connection is initially set up. Once the authentication step has been performed, the situation can thought to resemble the picture in Figure 1 except that A and B both use a single shared connection, for example, between port 49160 on A and port 5061 on B. When A wants to send a request to B, it will reuse this connection, and when B wants to send a request to A, it will reuse the same connection.
В отличие от TCP, соединения TLS можно повторно использовать для отправки запросов в обратном направлении, поскольку каждая сторона может быть аутентифицирована при начальной установке соединения. После выполнения аутентификации ситуацию можно представить похожей на картину на рисунке 1, за исключением того, что A и B используют одно общее соединение, например между портом 49160 на A и портом 5061 на B. Когда A хочет отправить запрос B, оно повторно использует это соединение, а когда B хочет отправить запрос A, оно повторно использует то же соединение.

Persistent connection: The process of sending multiple, possibly unrelated requests on the same connection, and receiving responses on that connection as well. Разрешённый адрес: сетевые идентификаторы (IP-адрес, порт, транспорт), связанные с агентом пользователя в результате выполнения RFC 3263 [RFC3263] для универсального идентификатора ресурса (URI).
Shared connection: See "Persistent connection".
Общее соединение: см. «Постоянное соединение».
3. Applicability Statement
3. Заявление о применимости
The applicability of the mechanism described in this document is for two adjacent SIP entities to reuse connections when they are agnostic about the direction of the connection, i.e., either end can initiate the connection. SIP entities that can only open a connection in a specific direction -- perhaps because of Network Address Translation (NAT) and firewalls -- reuse their connections using the mechanism described in the outbound document [RFC5626].
Механизм, описанный в настоящем документе, применим для двух смежных объектов SIP, которые повторно используют соединения, когда они не зависят от направления соединения, то есть любая из сторон может инициировать соединение. Объекты SIP, способные открывать соединение только в определённом направлении — возможно, из-за трансляции сетевых адресов (NAT) и межсетевых экранов, — повторно используют свои соединения с помощью механизма, описанного в документе outbound [RFC5626].
This memo concerns connection reuse, not persistent connections (see definitions of these in Section 2). Behavior for persistent connections is specified in Section 18 of RFC 3261 [RFC3261] and is not altered by this memo.
Настоящий меморандум касается повторного использования соединений, а не постоянных соединений (определения см. в разделе 2). Поведение постоянных соединений определено в разделе 18 RFC 3261 [RFC3261] и настоящим меморандумом не изменяется.
This memo documents that it is good practice to only reuse those connections where the identity of the sender can be verified by the receiver. Thus, TLS (RFC 5246 [RFC5246]) connections (over any connection-oriented transport) formed by exchanging X.509 certificates can be reused because they authoritatively establish identities of the communicating parties (see Section 5).
Настоящий меморандум фиксирует, что хорошей практикой является повторное использование только тех соединений, в которых получатель может проверить идентичность отправителя. Таким образом, соединения TLS (RFC 5246 [RFC5246]) (поверх любого транспорта с установлением соединения), сформированные путём обмена сертификатами X.509, могут быть использованы повторно, поскольку они авторитетно устанавливают идентичность взаимодействующих сторон (см. раздел 5).
4. Benefits of TLS Connection Reuse
4. Преимущества повторного использования соединений TLS
Opening an extra connection where an existing one is sufficient can result in potential scaling and performance problems. Each new connection using TLS requires a TCP three-way handshake, a handful of round trips to establish TLS, typically expensive asymmetric authentication and key generation algorithms, and certificate verification. This can lead to a build up of considerable queues as the server CPU saturates by the TLS handshakes it is already performing (Section 6.19 of Rescorla [Book-Rescorla-TLS]).
Открытие дополнительного соединения там, где достаточно существующего, может привести к проблемам масштабируемости и производительности. Каждое новое соединение с использованием TLS требует трёхстороннего рукопожатия TCP, нескольких круговых обменов для установки TLS, как правило, дорогостоящих асимметричных алгоритмов аутентификации и генерации ключей, а также проверки сертификатов. Это может привести к накоплению значительных очередей, поскольку процессор сервера насыщается рукопожатиями TLS, которые он уже выполняет (раздел 6.19 у Rescorla [Book-Rescorla-TLS]).
Consider the call flow shown below where Proxy A and Proxy B use the Record-Route mechanism to stay involved in a dialog. Proxy B will establish a new TLS connection just to send a BYE request.
Рассмотрим показанный ниже поток вызовов, в котором прокси A и прокси B используют механизм Record-Route, чтобы оставаться вовлечёнными в диалог. Прокси B установит новое соединение TLS только для того, чтобы отправить запрос BYE.

Setting up a second connection (from B to A above) for subsequent requests, even requests in the context of an existing dialog (e.g., re-INVITE request or BYE request after an initial INVITE request, or a NOTIFY request after a SUBSCRIBE request or a REFER request), can also cause excessive delay (especially in networks with long round- trip times). Thus, it is advantageous to reuse connections whenever possible.
Установка второго соединения (от B к A в примере выше) для последующих запросов, даже запросов в контексте существующего диалога (например, запроса re-INVITE или запроса BYE после первоначального запроса INVITE, либо запроса NOTIFY после запроса SUBSCRIBE или запроса REFER), также может вызвать чрезмерную задержку (особенно в сетях с большим временем кругового обхода). Таким образом, выгодно повторно использовать соединения везде, где это возможно.
From the user expectation point of view, it is advantageous if the re-INVITE requests or UPDATE requests are handled automatically and rapidly in order to avoid media and session state from being out of step. If a re-INVITE request requires a new TLS connection, the re- INVITE request could be delayed by several extra round-trip times. Depending on the round-trip time, this combined delay could be perceptible or even annoying to a human user. This is especially problematic for some common SIP call flows (for example, the recommended example flow in Figure 4 in RFC 3725 [RFC3725] uses many re-INVITE requests).
С точки зрения ожиданий пользователя выгодно, чтобы запросы re-INVITE или запросы UPDATE обрабатывались автоматически и быстро, дабы избежать расхождения состояния медиа и сеанса. Если запрос re-INVITE требует нового соединения TLS, запрос re-INVITE может быть задержан на несколько дополнительных круговых обходов. В зависимости от времени кругового обхода эта суммарная задержка может быть заметной или даже раздражающей для человека-пользователя. Особенно проблематично это для некоторых распространённых потоков вызовов SIP (например, рекомендуемый пример потока на рисунке 4 в RFC 3725 [RFC3725] использует множество запросов re-INVITE).
The mechanism described in this document can mitigate the delays associated with subsequent requests.
Описанный в настоящем документе механизм может смягчить задержки, связанные с последующими запросами.
5. Overview of Operation
5. Обзор работы
This section is tutorial in nature, and does not specify any normative behavior. We now explain this working in more detail in the context of communication between two adjacent proxies. Without any loss of generality, the same technique can be used for connection reuse between a User Agent Client (UAC) and an edge proxy, or between an edge proxy and a UAS, or between an UAC and an UAS.
Настоящий раздел носит учебный характер и не определяет нормативного поведения. Далее мы подробнее объясняем эту работу в контексте взаимодействия двух смежных прокси. Без потери общности та же методика может применяться для повторного использования соединений между клиентом агента пользователя (UAC) и граничным прокси, либо между граничным прокси и UAS, либо между UAC и UAS.
P1 and P2 are proxies responsible for routing SIP requests to user agents that use them as edge proxies (see Figure 4).
P1 и P2 — прокси, отвечающие за маршрутизацию SIP-запросов агентам пользователя, использующим их как граничные прокси (см. рисунок 4).

For illustration purpose the discussion below uses TCP as a transport for TLS operations. Another streaming transport -- such as SCTP -- can be used as well.
Для иллюстрации в приведённом ниже обсуждении TCP используется как транспорт для операций TLS. Может использоваться и другой потоковый транспорт — например, SCTP.
The act of reusing a connection is initiated by P1 when it adds an "alias" header field parameter (defined later) to the Via header field. When P2 receives the request, it examines the topmost Via header field. If the Via header contained an "alias" header field parameter, P2 establishes a binding such that subsequent requests going to P1 will reuse the connection; i.e., requests are sent over the established connection.
Действие по повторному использованию соединения инициируется P1, когда оно добавляет параметр поля заголовка «alias» (определён ниже) в поле заголовка Via. Получив запрос, P2 анализирует самое верхнее поле заголовка Via. Если Via содержал параметр поля заголовка «alias», P2 устанавливает привязку так, что последующие запросы, идущие к P1, будут повторно использовать соединение, то есть запросы отправляются по установленному соединению.
With reference to Figure 4, in order for P2 to reuse a connection for requests in the backwards direction, it is important that the validation model for requests sent in this direction (i.e., P2 to P1) is equivalent to the normal "connection in each direction" model, wherein P2 acting as client would open up a new connection in the backwards direction and validate the connection by examining the X.509 certificate presented. The act of reusing a connection needs the desired property that requests get delivered in the backwards direction only if they would have been delivered to the same destination had connection reuse not been employed. To guarantee this property, the X.509 certificate presented by P1 to P2 when a TLS connection is first authenticated are cached for later use. To aid the discussion of connection reuse, this document defines a data structure called the connection alias table (or simply, alias table), which is used to store aliased addresses and is used by user agents to search for an existing connection before a new one is opened up to a destination. It is not the intent of this memo to standardize the implementation of an alias table; rather, we use it as a convenience to aid subsequent discussions.

8. Normative Behavior
8. Нормативное поведение
8.1. Client Behavior
8.1. Поведение клиента
Clients SHOULD keep connections up as long as they are needed. Connection reuse works best when the client and the server maintain their connections for long periods of time. Clients, therefore, SHOULD NOT automatically drop connections on completion of a transaction or termination of a dialog.
Клиенты ДОЛЖНЫ поддерживать соединения, пока они нужны. Повторное использование соединений работает лучше всего, когда клиент и сервер поддерживают свои соединения в течение длительного времени. Поэтому клиенты НЕ ДОЛЖНЫ автоматически разрывать соединения по завершении транзакции или прекращении диалога.
The mechanism for connection reuse uses a new Via header field parameter. The "alias" header field parameter is included in a Via header field value to indicate that the client wants to create a transport layer alias. The client places its advertised address in the Via header field value (in the sent-by production).
Механизм повторного использования соединений использует новый параметр поля заголовка Via. Параметр поля заголовка «alias» включается в значение поля заголовка Via, чтобы указать, что клиент хочет создать алиас транспортного уровня. Клиент помещает свой объявленный адрес в значение поля заголовка Via (в продукцию sent-by).
If the client places an "alias" header field parameter in the topmost Via header of the request, the client SHOULD keep the connection open for as long as the resources on the host operating system allow it to, and that the client MUST accept requests over this connection -- in addition to the default listening port -- from its downstream peer. And furthermore, the client SHOULD reuse the connection when subsequent requests in the same or different transactions are destined to the same resolved address.
Если клиент помещает параметр поля заголовка «alias» в самое верхнее поле Via запроса, клиент ДОЛЖЕН держать соединение открытым столько, сколько позволяют ресурсы операционной системы хоста, и клиент ДОЛЖЕН принимать запросы по этому соединению — в дополнение к порту прослушивания по умолчанию — от своего нижестоящего соседа. Кроме того, клиент ДОЛЖЕН повторно использовать соединение, когда последующие запросы в той же или другой транзакции предназначены тому же разрешённому адресу.
Note that RFC 3261 states that a response arrives over the same connection that was opened for a request.
Обратите внимание, что RFC 3261 утверждает, что ответ приходит по тому же соединению, которое было открыто для запроса.
Whether or not to allow an aliased connection ultimately depends on the recipient of the request; i.e., the client does not get any confirmation that its downstream peer created the alias, or indeed that it even supports this specification. Thus, clients MUST NOT assume that the acceptance of a request by a server automatically enables connection aliasing. Clients MUST continue receiving requests on their default port.
Разрешать ли алиасированное соединение в конечном счёте зависит от получателя запроса, то есть клиент не получает никакого подтверждения, что его нижестоящий сосед создал алиас или вообще поддерживает эту спецификацию. Таким образом, клиенты НЕ ДОЛЖНЫ предполагать, что принятие запроса сервером автоматически включает алиасирование соединения. Клиенты ДОЛЖНЫ продолжать принимать запросы на своём порту по умолчанию.
Clients MUST authenticate the connection before forming an alias; Section 9.1 discusses the authentication steps in more detail. Once the server has been authenticated, the client MUST cache, in the alias table, the identity (or identities) of the server as determined in Section 7.1 of RFC 5922 [RFC5922]. The client MUST also populate the destination IP address, port, and transport of the server in the alias table; these fields are retrieved from executing RFC3263 server resolution process on the next-hop URI. And finally, the client MUST populate the alias descriptor field with the connection handle (or identifier) used to connect to the server.
Клиенты ДОЛЖНЫ аутентифицировать соединение перед формированием алиаса; в разделе 9.1 шаги аутентификации рассматриваются подробнее. После аутентификации сервера клиент ДОЛЖЕН кэшировать в таблице алиасов идентичность (или идентичности) сервера, как определено в разделе 7.1 RFC 5922 [RFC5922]. Клиент также ДОЛЖЕН заполнить в таблице алиасов IP-адрес назначения, порт и транспорт сервера; эти поля берутся из выполнения процесса разрешения сервера по RFC3263 для URI следующего перехода. И наконец, клиент ДОЛЖЕН заполнить поле дескриптора алиаса дескриптором соединения (или идентификатором), использованным для подключения к серверу.

1. The client uses the RFC3263 resolution on a URI and arrives at a resolved address contained in the alias table, and

Clients MUST be prepared for the case that the connection no longer exists when they are ready to send a subsequent request over it. In such a case, a new connection MUST be opened to the resolved address and the alias table updated accordingly.

Normally, these would be sent over the same connection over which the INVITE request was sent. However, if between the sending of the INVITE request and subsequent sending of the CANCEL request or ACK request to a non-2xx response, the connection was closed, then the client SHOULD open a new connection to the resolved address and send the CANCEL request or ACK request there instead. Обычно они отправлялись бы по тому же соединению, по которому был отправлен запрос INVITE. Однако если между отправкой запроса INVITE и последующей отправкой запроса CANCEL или запроса ACK на ответ, не являющийся 2xx, соединение было закрыто, то клиент ДОЛЖЕН открыть новое соединение к разрешённому адресу и отправить запрос CANCEL или запрос ACK туда. Клиент МОЖЕТ вставить вновь открытое соединение в таблицу алиасов.
8.2. Server Behavior
8.2. Поведение сервера
Servers SHOULD keep connections up unless they need to reclaim resources. Connection reuse works best when the client and the server maintain their connections for long periods of time. Servers, therefore, SHOULD NOT automatically drop connections on completion of a transaction or termination of a dialog.
Серверы ДОЛЖНЫ поддерживать соединения, если им не нужно освобождать ресурсы. Повторное использование соединений работает лучше всего, когда клиент и сервер поддерживают свои соединения в течение длительного времени. Поэтому серверы НЕ ДОЛЖНЫ автоматически разрывать соединения по завершении транзакции или прекращении диалога.
When a server receives a request over TLS whose topmost Via header field contains an "alias" header field parameter, it signifies that the upstream client will leave the connection open beyond the transaction and dialog lifetime, and that subsequent transactions and dialogs that are destined to a resolved address that matches the identifiers in the advertised address in the topmost Via header field can reuse this connection.
Когда сервер получает запрос по TLS, в самом верхнем поле заголовка Via которого содержится параметр поля заголовка «alias», это означает, что вышестоящий клиент оставит соединение открытым за пределами времени жизни транзакции и диалога и что последующие транзакции и диалоги, предназначенные разрешённому адресу, совпадающему с идентификаторами в объявленном адресе самого верхнего поля заголовка Via, могут повторно использовать это соединение.
Whether or not to use in the reverse direction a connection marked with the "alias" Via header field parameter ultimately depends on the policies of the server. It can choose to honor it, and thereby send subsequent requests over the aliased connection. If the server chooses not to honor an aliased connection, the server MUST allow the request to proceed as though the "alias" header field parameter was not present in the topmost Via header.
Использовать ли в обратном направлении соединение, помеченное параметром поля заголовка Via «alias», в конечном счёте зависит от политик сервера. Он может решить соблюсти его и тем самым отправлять последующие запросы по алиасированному соединению. Если сервер решает не соблюдать алиасированное соединение, сервер ДОЛЖЕН позволить запросу продолжить обработку так, как если бы параметр поля заголовка «alias» отсутствовал в самом верхнем поле Via.
This assures interoperability with RFC3261 server behavior. Clients can include the "alias" header field parameter without fear that the server will reject the SIP request because of its presence.
Это обеспечивает совместимость с поведением сервера по RFC3261. Клиенты могут включать параметр поля заголовка «alias», не опасаясь, что сервер отклонит SIP-запрос из-за его присутствия.
Servers MUST be prepared to deal with the case that the aliased connection no longer exist when they are ready to send a subsequent request over it. This can happen if the peer ran out of operating system resources and had to close the connection. In such a case, the server MUST open a new connection to the resolved address and the alias table updated accordingly.
Серверы ДОЛЖНЫ быть готовы к случаю, когда алиасированное соединение больше не существует, когда они готовы отправить по нему последующий запрос. Это может произойти, если у соседа закончились ресурсы операционной системы и ему пришлось закрыть соединение. В таком случае сервер ДОЛЖЕН открыть новое соединение к разрешённому адресу, а таблица алиасов должна быть соответствующим образом обновлена.
If the sent-by production of the Via header field contains a port, the server MUST use it as a destination port. Otherwise, the default port is the destination port.
Если продукция sent-by поля заголовка Via содержит порт, сервер ДОЛЖЕН использовать его как порт назначения. В противном случае портом назначения является порт по умолчанию.
Servers MUST follow the authentication steps outlined in Section 9.2 to authenticate the connection before forming an alias.
Серверы ДОЛЖНЫ выполнить шаги аутентификации, изложенные в разделе 9.2, чтобы аутентифицировать соединение перед формированием алиаса.
The server, if it decides to reuse the connection, MUST cache in the alias table the identity (or identities) of the client as they appear in the X.509 certificate subjectAlternativeName extension field. The server also populates the destination IP address, port, and transport in the alias table from the topmost Via header field (using the ";received" parameter for the destination IP address). If the port number is omitted, a default port number of 5061 is to be used. And finally, the server populates the alias descriptor field with the connection handle (or identifier) used to accept the connection from the client (see Section 5 for the contents of the alias table).
Сервер, если он решает повторно использовать соединение, ДОЛЖЕН кэшировать в таблице алиасов идентичность (или идентичности) клиента в том виде, в каком они появляются в поле расширения subjectAlternativeName сертификата X.509. Сервер также заполняет в таблице алиасов IP-адрес назначения, порт и транспорт из самого верхнего поля заголовка Via (используя параметр «;received» для IP-адреса назначения). Если номер порта опущен, следует использовать номер порта по умолчанию 5061. И наконец, сервер заполняет поле дескриптора алиаса дескриптором соединения (или идентификатором), использованным для принятия соединения от клиента (о содержимом таблицы алиасов см. раздел 5).
Once the alias table has been updated, and the server wants to send a request in the direction of the client, it reuses the connection only if all of the following conditions hold:
После того как таблица алиасов обновлена, и сервер хочет отправить запрос в направлении клиента, он повторно использует соединение только при выполнении всех следующих условий:
1. The server, which acts as a client for this transaction, uses the RFC3263 resolution process on a URI and arrives at a resolved address contained in the alias table, and
1. Сервер, который действует как клиент для этой транзакции, применяет процесс разрешения по RFC3263 к URI и приходит к разрешённому адресу, содержащемуся в таблице алиасов, и
2. The URI used for RFC3263 server resolution matches one of the identities stored in the alias table row corresponding to that resolved address.
2. URI, использованный для разрешения сервера по RFC3263, совпадает с одной из идентичностей, хранящихся в строке таблицы алиасов, соответствующей этому разрешённому адресу.
8.3. Closing a TLS connection
8.3. Закрытие соединения TLS
Either the client or the server may terminate a TLS session by sending a TLS closure alert. Before closing a TLS connection, the initiator of the closure MUST either wait for any outstanding SIP transactions to complete, or explicitly abandon them.
Либо клиент, либо сервер могут завершить сеанс TLS, отправив уведомление о закрытии TLS. Перед закрытием соединения TLS инициатор закрытия ДОЛЖЕН либо дождаться завершения всех незавершённых SIP-транзакций, либо явно отказаться от них.
After the initiator of the close has sent a closure alert, it MUST discard any TLS messages until it has received a similar alert from its peer. The receiver of the closure alert MUST NOT start any new SIP transactions after the receipt of the closure alert.
После того как инициатор закрытия отправил уведомление о закрытии, он ДОЛЖЕН отбрасывать любые сообщения TLS, пока не получит аналогичное уведомление от своего соседа. Получатель уведомления о закрытии НЕ ДОЛЖЕН начинать никаких новых SIP-транзакций после получения уведомления о закрытии.
9. Security Considerations
9. Соображения безопасности
This document presents requirements and a mechanism for reusing existing connections easily. Unauthenticated connection reuse would present many opportunities for rampant abuse and hijacking. Authenticating connection aliases is essential to prevent connection hijacking. For example, a program run by a malicious user of a multiuser system could attempt to hijack SIP requests destined for the well-known SIP port from a large relay proxy.
Настоящий документ представляет требования и механизм для лёгкого повторного использования существующих соединений. Повторное использование соединений без аутентификации открыло бы множество возможностей для массовых злоупотреблений и захватов. Аутентификация алиасов соединений необходима для предотвращения захвата соединений. Например, программа, запущенная злоумышленником в многопользовательской системе, могла бы попытаться перехватить SIP-запросы, предназначенные общеизвестному порту SIP, от крупного ретранслирующего прокси.
9.1. Authenticating TLS Connections: Client View
9.1. Аутентификация соединений TLS: взгляд клиента
When a TLS client establishes a connection with a server, it is presented with the server's X.509 certificate. Authentication proceeds as described in Section 7.3 ("Client behavior") of RFC 5922 [RFC5922].
Когда клиент TLS устанавливает соединение с сервером, ему предъявляется сертификат сервера X.509. Аутентификация выполняется так, как описано в разделе 7.3 («Client behavior») RFC 5922 [RFC5922].
9.2. Authenticating TLS Connections: Server View
9.2. Аутентификация соединений TLS: взгляд сервера
A TLS server conformant to this specification MUST ask for a client certificate; if the client possesses a certificate, it will be presented to the server for mutual authentication, and authentication proceeds as described in Section 7.4 ("Server behavior") of RFC 5922 [RFC5922].
Сервер TLS, соответствующий настоящей спецификации, ДОЛЖЕН запросить сертификат клиента; если клиент располагает сертификатом, он будет предъявлен серверу для взаимной аутентификации, и аутентификация выполняется так, как описано в разделе 7.4 («Server behavior») RFC 5922 [RFC5922].
If the client does not present a certificate, the server MUST proceed as if the "alias" header field parameter was not present in the topmost Via header. In this case, the server MUST NOT update the alias table.
Если клиент не предъявляет сертификат, сервер ДОЛЖЕН продолжить так, как если бы параметр поля заголовка «alias» отсутствовал в самом верхнем поле Via. В этом случае сервер НЕ ДОЛЖЕН обновлять таблицу алиасов.
9.3. Connection Reuse and Virtual Servers
9.3. Повторное использование соединений и виртуальные серверы
Virtual servers present special considerations for connection reuse. Under the name-based virtual server scheme, one SIP proxy can host many virtual domains using one IP address and port number. If adequate defenses are not put in place, a connection opened to a downstream server on behalf of one domain can be reused to send requests in the backwards direction to a different domain. The "Destination Identity" column in the alias table has been added to aid in such defenses.
Виртуальные серверы представляют особые соображения для повторного использования соединений. В схеме виртуальных серверов на основе имён один SIP-прокси может размещать множество виртуальных доменов, используя один IP-адрес и номер порта. Если не приняты надлежащие меры защиты, соединение, открытое с нижестоящим сервером от имени одного домена, может быть повторно использовано для отправки запросов в обратном направлении другому домену. Столбец «Destination Identity» в таблице алиасов добавлен для содействия таким мерам защиты.
Virtual servers MUST only perform connection reuse for TLS connections; virtual servers MUST NOT perform connection reuse for other connection-oriented transports. To understand why this is the case, note that the alias table caches not only which connections go to which destination addresses, but also which connections have authenticated themselves as responsible for which domains. If a message is to be sent in the backwards direction to a new SIP domain that resolves to an address with a cached connection, the cached connection cannot be used because it is not authenticated for the new domain.
Виртуальные серверы ДОЛЖНЫ выполнять повторное использование соединений только для соединений TLS; виртуальные серверы НЕ ДОЛЖНЫ выполнять повторное использование соединений для других транспортов с установлением соединения. Чтобы понять, почему это так, отметим, что таблица алиасов кэширует не только то, какие соединения ведут к каким адресам назначения, но и то, какие соединения аутентифицировали себя как отвечающие за какие домены. Если сообщение должно быть отправлено в обратном направлении новому домену SIP, который разрешается в адрес с кэшированным соединением, кэшированное соединение нельзя использовать, поскольку оно не аутентифицировано для нового домена.
