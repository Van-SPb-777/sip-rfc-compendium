Abstract
Аннотация
This document describes an extension to the Session Initiation Protocol (SIP) defined by RFC 3261. The purpose of this extension is to provide an extensible framework by which SIP nodes can request notification from remote nodes indicating that certain events have occurred.
Настоящий документ описывает расширение протокола инициирования сессий (SIP), определённого в RFC 3261. Цель этого расширения — предоставить расширяемую основу, с помощью которой узлы SIP могут запрашивать у удалённых узлов уведомления о том, что определённые события произошли.
Note that the event notification mechanisms defined herein are NOT intended to be a general-purpose infrastructure for all classes of event subscription and notification.
Обратите внимание, что определённые здесь механизмы уведомления о событиях НЕ предназначены быть инфраструктурой общего назначения для всех классов подписки на события и уведомления о них.
This document represents a backwards-compatible improvement on the original mechanism described by RFC 3265, taking into account several years of implementation experience. Accordingly, this document obsoletes RFC 3265. This document also updates RFC 4660 slightly to accommodate some small changes to the mechanism that were discussed in that document.
Настоящий документ представляет собой обратно совместимое улучшение исходного механизма, описанного в RFC 3265, с учётом нескольких лет опыта реализации. Соответственно, настоящий документ делает RFC 3265 устаревшим. 1. Introduction
1. Введение
The ability to request asynchronous notification of events proves useful in many types of SIP services for which cooperation between end-nodes is required. Examples of such services include automatic callback services (based on terminal state events), buddy lists (based on user presence events), message waiting indications (based on mailbox state change events), and PSTN and Internet Internetworking (PINT) [RFC2848] status (based on call state events).
Возможность запрашивать асинхронное уведомление о событиях оказывается полезной во многих типах служб SIP, для которых требуется взаимодействие между оконечными узлами. Примеры таких служб включают службы автоматического обратного вызова (на основе событий состояния терминала), списки собеседников (на основе событий присутствия пользователя), индикацию ожидающих сообщений (на основе событий изменения состояния почтового ящика) и статус взаимодействия ТфОП и Интернета (PINT) [RFC2848] (на основе событий состояния вызова).
The methods described in this document provide a framework by which notification of these events can be ordered.
Описанные в настоящем документе методы обеспечивают основу, с помощью которой уведомление об этих событиях может быть упорядочено.
The event notification mechanisms defined herein are NOT intended to be a general-purpose infrastructure for all classes of event subscription and notification. Meeting requirements for the general problem set of subscription and notification is far too complex for a single protocol. Our goal is to provide a SIP-specific framework for event notification that is not so complex as to be unusable for simple features, but that is still flexible enough to provide powerful services. Note, however, that event packages based on this framework may define arbitrarily elaborate rules that govern the subscription and notification for the events or classes of events they describe.
Определённые здесь механизмы уведомления о событиях НЕ предназначены быть инфраструктурой общего назначения для всех классов подписки на события и уведомления о них. Удовлетворение требований общего набора задач подписки и уведомления слишком сложно для одного протокола. Наша цель — обеспечить специфичную для SIP основу для уведомления о событиях, не настолько сложную, чтобы быть непригодной для простых возможностей, но при этом достаточно гибкую, чтобы предоставлять мощные службы. Обратите внимание, однако, что пакеты событий, основанные на этой основе, могут определять сколь угодно сложные правила, управляющие подпиской и уведомлением для событий или классов событий, которые они описывают.
This document does not describe an extension that may be used directly; it must be extended by other documents (herein referred to as "event packages"). In object-oriented design terminology, it may be thought of as an abstract base class that must be derived into an instantiable class by further extensions. Guidelines for creating these extensions are described in Section 5.
Настоящий документ не описывает расширение, которое можно использовать напрямую; оно должно быть расширено другими документами (здесь называемыми «пакетами событий»). В терминологии объектно-ориентированного проектирования его можно рассматривать как абстрактный базовый класс, который должен быть превращён в экземплярный класс дальнейшими расширениями. Рекомендации по созданию этих расширений описаны в разделе 5.
1.1. Overview of Operation
1.1. Обзор работы
The general concept is that entities in the network can subscribe to resource or call state for various resources or calls in the network, and those entities (or entities acting on their behalf) can send notifications when those states change.
Общая концепция состоит в том, что объекты в сети могут подписываться на состояние ресурса или вызова для различных ресурсов или вызовов в сети, и эти объекты (или объекты, действующие от их имени) могут отправлять уведомления, когда эти состояния изменяются.
A typical flow of messages would be:
Примерный поток сообщений выглядит так:
Subscriber Notifier
Подписчик — Уведомитель
|-----SUBSCRIBE---->| Request state subscription |<-------200--------| Acknowledge subscription |<------NOTIFY----- | Return current state information |--------200------->| |<------NOTIFY----- | Return current state information |--------200------->|
|-----SUBSCRIBE---->| Request state subscription |<-------200--------| Acknowledge subscription |<------NOTIFY----- | Return current state information |--------200------->| |<------NOTIFY----- | Return current state information |--------200------->|
Subscriptions are expired and must be refreshed by subsequent SUBSCRIBE requests.
Подписки истекают по времени и должны обновляться последующими запросами SUBSCRIBE.

2. Definitions
2. Определения
Event Package: An event package is an additional specification that defines a set of state information to be reported by a notifier to a subscriber. Event packages also define further syntax and semantics that are based on the framework defined by this document and are required to convey such state information.
Пакет событий: пакет событий — это дополнительная спецификация, определяющая набор сведений о состоянии, которые уведомитель должен сообщать подписчику. Пакеты событий также определяют дополнительные синтаксис и семантику, основанные на определяемой настоящим документом основе и необходимые для передачи таких сведений о состоянии.
Event Template-Package: An event template-package is a special kind of event package that defines a set of states that may be applied to all possible event packages, including itself.
Шаблонный пакет событий: шаблонный пакет событий — это особый вид пакета событий, который определяет набор состояний, применимый ко всем возможным пакетам событий, включая себя самого.
Notification: Notification is the act of a notifier sending a NOTIFY request to a subscriber to inform the subscriber of the state of a resource.
Уведомление: уведомление — это действие, при котором уведомитель отправляет подписчику запрос NOTIFY, чтобы сообщить подписчику о состоянии ресурса.
Notifier: A notifier is a user agent that generates NOTIFY requests for the purpose of notifying subscribers of the state of a resource. Notifiers typically also accept SUBSCRIBE requests to create subscriptions.
Уведомитель: уведомитель — это пользовательский агент, который формирует запросы NOTIFY с целью уведомления подписчиков о состоянии ресурса. Уведомители, как правило, также принимают запросы SUBSCRIBE для создания подписок.
Subscriber: A subscriber is a user agent that receives NOTIFY requests from notifiers; these NOTIFY requests contain information about the state of a resource in which the subscriber is interested. Subscribers typically also generate SUBSCRIBE requests and send them to notifiers to create subscriptions.
Подписчик: подписчик — это пользовательский агент, который получает запросы NOTIFY от уведомителей; эти запросы NOTIFY содержат сведения о состоянии ресурса, интересующего подписчика. Подписчики, как правило, также формируют запросы SUBSCRIBE и отправляют их уведомителям для создания подписок.
Subscription: A subscription is a set of application state associated with a dialog. This application state includes a pointer to the associated dialog, the event package name, and possibly an identification token. Event packages will define additional subscription state information. By definition, subscriptions exist in both a subscriber and a notifier.
Подписка: подписка — это набор прикладного состояния, связанного с диалогом. Это прикладное состояние включает указатель на связанный диалог, имя пакета событий и, возможно, идентификационный токен. Пакеты событий будут определять дополнительные сведения о состоянии подписки. По определению, подписки существуют как у подписчика, так и у уведомителя.
Subscription Migration: Subscription migration is the act of moving a subscription from one notifier to another notifier.
Миграция подписки: миграция подписки — это действие по перемещению подписки от одного уведомителя к другому уведомителю.
3. SIP Methods for Event Notification
3. Методы SIP для уведомления о событиях
3.1. SUBSCRIBE
3.1. SUBSCRIBE
The SUBSCRIBE method is used to request current state and state updates from a remote node. SUBSCRIBE requests are target refresh requests, as that term is defined in [RFC3261].
Метод SUBSCRIBE используется для запроса текущего состояния и обновлений состояния у удалённого узла. Запросы SUBSCRIBE являются запросами обновления цели (target refresh requests), как этот термин определён в [RFC3261].
3.1.1. Subscription Duration
3.1.1. Длительность подписки
SUBSCRIBE requests SHOULD contain an "Expires" header field (defined in [RFC3261]). This expires value indicates the duration of the subscription. In order to keep subscriptions effective beyond the duration communicated in the "Expires" header field, subscribers need to refresh subscriptions on a periodic basis using a new SUBSCRIBE request on the same dialog as defined in [RFC3261].
Запросы SUBSCRIBE ДОЛЖНЫ содержать поле заголовка «Expires» (определено в [RFC3261]). Это значение expires указывает длительность подписки. Чтобы подписки оставались действующими дольше срока, сообщённого в поле заголовка «Expires», подписчикам нужно периодически обновлять подписки с помощью нового запроса SUBSCRIBE в том же диалоге, как определено в [RFC3261].
If no "Expires" header field is present in a SUBSCRIBE request, the implied default MUST be defined by the event package being used.
Если в запросе SUBSCRIBE отсутствует поле заголовка «Expires», подразумеваемое значение по умолчанию ДОЛЖНО быть определено используемым пакетом событий.
200-class responses to SUBSCRIBE requests also MUST contain an "Expires" header field. The period of time in the response MAY be shorter but MUST NOT be longer than specified in the request. The notifier is explicitly allowed to shorten the duration to zero. The period of time in the response is the one that defines the duration of the subscription.
Ответы класса 200 на запросы SUBSCRIBE также ДОЛЖНЫ содержать поле заголовка «Expires». Период времени в ответе МОЖЕТ быть короче, но НЕ ДОЛЖЕН быть длиннее указанного в запросе. Уведомителю явно разрешено сокращать длительность до нуля. Именно период времени в ответе определяет длительность подписки.
An "expires" parameter on the "Contact" header field has no semantics for the SUBSCRIBE method and is explicitly not equivalent to an "Expires" header field in a SUBSCRIBE request or response.
Параметр «expires» поля заголовка «Contact» не имеет семантики для метода SUBSCRIBE и явно не эквивалентен полю заголовка «Expires» в запросе на SUBSCRIBE или в ответе на SUBSCRIBE.
A natural consequence of this scheme is that a SUBSCRIBE request with an "Expires" of 0 constitutes a request to unsubscribe from the matching subscription.
Естественным следствием такой схемы является то, что запрос SUBSCRIBE со значением «Expires», равным 0, представляет собой запрос на отмену подписки, соответствующей этому запросу.
In addition to being a request to unsubscribe, a SUBSCRIBE request with "Expires" of 0 also causes a fetch of state; see Section 4.4.3.
Помимо того что запрос SUBSCRIBE со значением «Expires», равным 0, является запросом на отмену подписки, он также вызывает выборку состояния; см. раздел 4.4.3.
Notifiers may also wish to cancel subscriptions to events; this is useful, for example, when the resource to which a subscription refers is no longer available. Further details on this mechanism are discussed in Section 4.2.2.
Уведомители также могут пожелать отменять подписки на события; это полезно, например, когда ресурс, к которому относится подписка, становится недоступен. Дополнительные сведения об этом механизме обсуждаются в разделе 4.2.2.
3.1.2. Identification of Subscribed Events and Event Classes
3.1.2. Идентификация подписываемых событий и классов событий
Identification of events is provided by three pieces of information: Request URI, Event Type, and (optionally) message body.
Идентификация событий обеспечивается тремя частями информации: Request URI, типом события и (необязательно) телом сообщения.
The Request URI of a SUBSCRIBE request, most importantly, contains enough information to route the request to the appropriate entity per the request routing procedures outlined in [RFC3261]. It also contains enough information to identify the resource for which event notification is desired, but not necessarily enough information to uniquely identify the nature of the event (e.g., "sip:adam@example.com" would be an appropriate URI to subscribe to for my presence state; it would also be an appropriate URI to subscribe to the state of my voice mailbox).
Request URI запроса SUBSCRIBE, что наиболее важно, содержит достаточно информации для маршрутизации запроса к надлежащему объекту согласно процедурам маршрутизации запросов, изложенным в [RFC3261]. Он также содержит достаточно информации для идентификации ресурса, уведомление о событиях которого требуется, но не обязательно достаточно информации для однозначной идентификации характера события (например, «sip:adam@example.com» был бы подходящим URI для подписки на состояние моего присутствия; он также был бы подходящим URI для подписки на состояние моего голосового почтового ящика).
Subscribers MUST include exactly one "Event" header field in SUBSCRIBE requests, indicating to which event or class of events they are subscribing. The "Event" header field will contain a token that indicates the type of state for which a subscription is being requested. This token will be registered with the IANA and will correspond to an event package that further describes the semantics of the event or event class.
Подписчики ДОЛЖНЫ включать ровно одно поле заголовка «Event» в запросы SUBSCRIBE, указывающее, на какое событие или класс событий они подписываются. Поле заголовка «Event» будет содержать токен, указывающий тип состояния, для которого запрашивается подписка. Этот токен будет зарегистрирован в IANA и будет соответствовать пакету событий, который дополнительно описывает семантику события или класса событий.
If the event package to which the event token corresponds defines behavior associated with the body of its SUBSCRIBE requests, those semantics apply.
Если пакет событий, которому соответствует токен события, определяет поведение, связанное с телом своих запросов SUBSCRIBE, эта семантика применяется.
Event packages may also define parameters for the "Event" header field; if they do so, they must define the semantics for such parameters.
Пакеты событий также могут определять параметры для поля заголовка «Event»; если они это делают, они должны определить семантику таких параметров.
3.1.3. Additional SUBSCRIBE Header Field Values
3.1.3. Дополнительные значения полей заголовков SUBSCRIBE
Because SUBSCRIBE requests create a dialog usage as defined in [RFC3261], they MAY contain an "Accept" header field. This header field, if present, indicates the body formats allowed in subsequent NOTIFY requests. Event packages MUST define the behavior for SUBSCRIBE requests without "Accept" header fields; usually, this will connote a single, default body type.
Поскольку запросы SUBSCRIBE создают использование диалога, как определено в [RFC3261], они МОГУТ содержать поле заголовка «Accept». Это поле заголовка, если оно присутствует, указывает форматы тела, допустимые в последующих запросах NOTIFY. Пакеты событий ДОЛЖНЫ определять поведение для запросов SUBSCRIBE без полей заголовка «Accept»; обычно это означает единственный тип тела по умолчанию.
Header values not described in this document are to be interpreted as described in [RFC3261].
Значения заголовков, не описанные в настоящем документе, следует интерпретировать так, как описано в [RFC3261].
3.2. NOTIFY
3.2. NOTIFY
NOTIFY requests are sent to inform subscribers of changes in state to which the subscriber has a subscription. Subscriptions are created using the SUBSCRIBE method. In legacy implementations, it is possible that other means of subscription creation have been used. However, this specification does not allow the creation of subscriptions except through SUBSCRIBE requests and (for backwards- compatibility) REFER requests [RFC3515].
Запросы NOTIFY отправляются, чтобы сообщать подписчикам об изменениях состояния, на которое у подписчика есть подписка. Подписки создаются с помощью метода SUBSCRIBE. В унаследованных реализациях возможно использование других способов создания подписки. Однако настоящая спецификация не допускает создания подписок иначе как посредством запросов SUBSCRIBE и (для обратной совместимости) запросов REFER [RFC3515].
NOTIFY is a target refresh request, as that term is defined in [RFC3261].
NOTIFY — это запрос обновления цели, как этот термин определён в [RFC3261].
A NOTIFY request does not terminate its corresponding subscription; in other words, a single SUBSCRIBE request may trigger several NOTIFY requests.
Запрос NOTIFY не завершает соответствующую ему подписку; иными словами, один запрос SUBSCRIBE может вызвать несколько запросов NOTIFY.
3.2.1. Identification of Reported Events, Event Classes, and Current State
3.2.1. Идентификация сообщаемых событий, классов событий и текущего состояния
Identification of events being reported in a notification is very similar to that described for subscription to events (see Section 3.1.2).
Идентификация событий, сообщаемых в уведомлении, очень похожа на описанную для подписки на события (см. раздел 3.1.2 ниже).
As in SUBSCRIBE requests, NOTIFY request "Event" header fields MUST contain a single event package name for which a notification is being generated. The package name in the "Event" header field MUST match the "Event" header field in the corresponding SUBSCRIBE request.
Как и в запросах SUBSCRIBE, поля заголовка «Event» запроса NOTIFY ДОЛЖНЫ содержать единственное имя пакета событий, для которого формируется уведомление. Имя пакета в поле заголовка «Event» ДОЛЖНО совпадать с полем заголовка «Event» в соответствующем запросе SUBSCRIBE.
Event packages may define semantics associated with the body of their NOTIFY requests; if they do so, those semantics apply. NOTIFY request bodies are expected to provide additional details about the nature of the event that has occurred and the resultant resource state. When present, the body of the NOTIFY request MUST be formatted into one of the body formats specified in the "Accept" header field of the corresponding SUBSCRIBE request (or the default type according to the event package description, if no "Accept" header field was specified). This body will contain either the state of the subscribed resource or a pointer to such state in the form of a URI (see Section 5.4.13).
Пакеты событий могут определять семантику, связанную с телом своих запросов NOTIFY; если они это делают, эта семантика применяется. Ожидается, что тела запросов NOTIFY предоставят дополнительные подробности о характере произошедшего события и о результирующем состоянии ресурса. Если тело присутствует, оно ДОЛЖНО быть отформатировано в одном из форматов тела, указанных в поле заголовка «Accept» соответствующего запроса SUBSCRIBE (или в типе по умолчанию согласно описанию пакета событий, если поле заголовка «Accept» не было указано). Это тело будет содержать либо состояние ресурса, на который оформлена подписка, либо указатель на такое состояние в виде URI (см. раздел 5.4.13).
4. Node Behavior
4. Поведение узлов
4.1. Subscriber Behavior
4.1. Поведение подписчика
4.1.1. Detecting Support for SIP Events
4.1.1. Обнаружение поддержки событий SIP
The extension described in this document does not make use of the "Require" or "Proxy-Require" header fields; similarly, there is no token defined for "Supported" header fields. Potential subscribers may probe for the support of SIP events using the OPTIONS request defined in [RFC3261].
Расширение, описанное в настоящем документе, не использует поля заголовков «Require» или «Proxy-Require»; аналогично, для полей заголовков «Supported» не определён никакой токен. Потенциальные подписчики могут проверить поддержку событий SIP с помощью запроса OPTIONS, определённого в [RFC3261].
The presence of "SUBSCRIBE" in the "Allow" header field of any request or response indicates support for SIP events; further, in the absence of an "Allow" header field, the simple presence of an "Allow- Events" header field is sufficient to indicate that the node that sent the message is capable of acting as a notifier (see Section 4.4.4).
Наличие «SUBSCRIBE» в поле заголовка «Allow» любого запроса или ответа указывает на поддержку событий SIP; кроме того, при отсутствии поля заголовка «Allow» простого наличия поля заголовка «Allow-Events» достаточно, чтобы указать, что узел, отправивший сообщение, способен действовать как уведомитель (см. раздел 4.4.4).
The "methods" parameter for Contact may also be used to specifically announce support for SUBSCRIBE and NOTIFY requests when registering. (See [RFC3840] for details on the "methods" parameter.)
Параметр «methods» для Contact также может использоваться для конкретного объявления поддержки запросов SUBSCRIBE и NOTIFY при регистрации. (Подробности о параметре «methods» см. в [RFC3840].)

С точки зрения подписчика подписка развивается согласно следующей диаграмме состояний. События, приводящие к переходу обратно в то же состояние, на этой диаграмме не представлены.

4.1.2.1. Requesting a Subscription
4.1.2.1. Запрос подписки
SUBSCRIBE is a dialog-creating method, as described in [RFC3261].
SUBSCRIBE является методом, создающим диалог, как описано в [RFC3261].
When a subscriber wishes to subscribe to a particular state for a resource, it forms a SUBSCRIBE request. If the initial SUBSCRIBE request represents a request outside of a dialog (as it typically will), its construction follows the procedures outlined in [RFC3261] for User Agent Client (UAC) request generation outside of a dialog.
Когда подписчик желает подписаться на определённое состояние ресурса, он формирует запрос SUBSCRIBE. Если исходный запрос SUBSCRIBE представляет собой запрос вне диалога (как обычно и бывает), его построение следует процедурам, изложенным в [RFC3261] для формирования запросов клиентом пользовательского агента (UAC) вне диалога.
This SUBSCRIBE request will be confirmed with a final response. 200-class responses indicate that the subscription has been accepted and that a NOTIFY request will be sent immediately.
Этот запрос SUBSCRIBE будет подтверждён окончательным ответом. Ответы класса 200 указывают, что подписка была принята и что запрос NOTIFY будет отправлен немедленно.
The "Expires" header field in a 200-class response to SUBSCRIBE request indicates the actual duration for which the subscription will remain active (unless refreshed). The received value might be smaller than the value indicated in the SUBSCRIBE request but cannot be larger; see Section 4.2.1 for details.
Поле заголовка «Expires» в ответе класса 200 на запрос SUBSCRIBE указывает фактическую длительность, в течение которой подписка будет оставаться активной (если она не обновлена). Полученное значение может быть меньше значения, указанного в запросе SUBSCRIBE, но не может быть больше; подробности см. в разделе 4.2.1.
Non-200-class final responses indicate that no subscription or new dialog usage has been created, and no subsequent NOTIFY request will be sent. All non-200-class responses (with the exception of 489 (Bad Event), described herein) have the same meanings and handling as described in [RFC3261]. For the sake of clarity: if a SUBSCRIBE request contains an "Accept" header field, but that field does not indicate a media type that the notifier is capable of generating in its NOTIFY requests, then the proper error response is 406 (Not Acceptable).
Окончательные ответы, не относящиеся к классу 200, указывают, что ни подписка, ни новое использование диалога не были созданы и никакой последующий запрос NOTIFY отправлен не будет. Все ответы, не относящиеся к классу 200 (за исключением 489 (Bad Event), описанного в настоящем документе), имеют те же значения и обрабатываются так же, как описано в [RFC3261]. Для ясности: если запрос SUBSCRIBE содержит поле заголовка «Accept», но это поле не указывает тип носителя, который уведомитель способен формировать в своих запросах NOTIFY, то надлежащим ответом об ошибке является 406 (Not Acceptable).
4.1.2.2. Refreshing of Subscriptions
4.1.2.2. Обновление подписок
At any time before a subscription expires, the subscriber may refresh the timer on such a subscription by sending another SUBSCRIBE request on the same dialog as the existing subscription. The handling for such a request is the same as for the initial creation of a subscription except as described below.
В любой момент до истечения подписки подписчик может обновить таймер такой подписки, отправив ещё один запрос SUBSCRIBE в том же диалоге, что и существующая подписка. Обработка такого запроса такая же, как для первоначального создания подписки, за исключением описанного ниже.
If a SUBSCRIBE request to refresh a subscription receives a 404, 405, 410, 416, 480-485, 489, 501, or 604 response, the subscriber MUST consider the subscription terminated. (See [RFC5057] for further details and notes about the effect of error codes on dialogs and usages within dialog, such as subscriptions). If the subscriber wishes to re-subscribe to the state, he does so by composing an unrelated initial SUBSCRIBE request with a freshly generated Call-ID and a new, unique "From" tag (see Section 4.1.2.1). If a SUBSCRIBE request to refresh a subscription fails with any error code other than those listed above, the original subscription is still considered valid for the duration of the most recently known "Expires" value as negotiated by the most recent successful SUBSCRIBE transaction, or as communicated by a NOTIFY request in its "Subscription-State" header field "expires" parameter.
Если запрос SUBSCRIBE на обновление подписки получает ответ 404, 405, 410, 416, 480-485, 489, 501 или 604, подписчик ДОЛЖЕН считать подписку завершённой. (Дополнительные сведения и замечания о влиянии кодов ошибок на диалоги и использования в диалоге, такие как подписки, см. в [RFC5057].) Если подписчик желает подписаться на это состояние заново, он делает это, составляя несвязанный первоначальный запрос SUBSCRIBE со свежесгенерированным Call-ID и новым уникальным тегом «From» (см. раздел 4.1.2.1). Если запрос SUBSCRIBE на обновление подписки завершается с любым кодом ошибки, отличным от перечисленных выше, исходная подписка по-прежнему считается действительной в течение длительности последнего известного значения «Expires», согласованного в последней успешной транзакции SUBSCRIBE или сообщённого запросом NOTIFY в параметре «expires» поля заголовка «Subscription-State».
Note that many such errors indicate that there may be a problem with the network or the notifier such that no further NOTIFY requests will be received.
Обратите внимание, что многие такие ошибки указывают на возможную проблему в сети или у уведомителя, из-за которой дальнейшие запросы NOTIFY не будут получены.
When refreshing a subscription, a subscriber starts Timer N, set to 64*T1, when it sends the SUBSCRIBE request. If this Timer N expires prior to the receipt of a NOTIFY request, the subscriber considers the subscription terminated. If the subscriber receives a success response to the SUBSCRIBE request that indicates that no NOTIFY request will be generated -- such as the 204 response defined for use with the optional extension described in [RFC5839] -- then it MUST cancel Timer N.
При обновлении подписки подписчик запускает таймер N, установленный в 64*T1, когда отправляет запрос SUBSCRIBE. Если этот таймер N истекает до получения запроса NOTIFY, подписчик считает подписку завершённой. Если подписчик получает ответ об успехе на запрос SUBSCRIBE, указывающий, что запрос NOTIFY сформирован не будет, -- например, ответ 204, определённый для использования с необязательным расширением, описанным в [RFC5839], -- то он ДОЛЖЕН отменить таймер N.
4.1.2.3. Unsubscribing
4.1.2.3. Отмена подписки
Unsubscribing is handled in the same way as refreshing of a subscription, with the "Expires" header field set to "0". Note that a successful unsubscription will also trigger a final NOTIFY request.
Отмена подписки обрабатывается так же, как обновление подписки, с полем заголовка «Expires», установленным в «0». Обратите внимание, что успешная отмена подписки также вызовет финальный запрос NOTIFY.
The final NOTIFY request may or may not contain information about the state of the resource; subscribers need to be prepared to receive final NOTIFY requests both with and without state.
Финальный запрос NOTIFY может содержать или не содержать сведения о состоянии ресурса; подписчики должны быть готовы принимать финальные запросы NOTIFY как с состоянием, так и без него.
4.1.2.4. Confirmation of Subscription Creation
4.1.2.4. Подтверждение создания подписки
The subscriber can expect to receive a NOTIFY request from each node which has processed a successful subscription or subscription refresh. To ensure that subscribers do not wait indefinitely for a subscription to be established, a subscriber starts a Timer N, set to 64*T1, when it sends a SUBSCRIBE request. If this Timer N expires prior to the receipt of a NOTIFY request, the subscriber considers the subscription failed, and cleans up any state associated with the subscription attempt.
Подписчик может ожидать получения запроса NOTIFY от каждого узла, который обработал успешную подписку или обновление подписки. Чтобы подписчики не ждали установления подписки бесконечно, подписчик запускает таймер N, установленный в 64*T1, когда отправляет запрос SUBSCRIBE. Если этот таймер N истекает до получения запроса NOTIFY, подписчик считает подписку неудавшейся и очищает всё состояние, связанное с попыткой подписки.
Until Timer N expires, several NOTIFY requests may arrive from different destinations (see Section 4.4.1). Each of these requests establishes a new dialog usage and a new subscription. After the expiration of Timer N, the subscriber SHOULD reject any such NOTIFY requests that would otherwise establish a new dialog usage with a 481 (Subscription does not exist) response code. Until the first NOTIFY request arrives, the subscriber should consider the state of the subscribed resource to be in a neutral state. Event package specifications MUST define this "neutral state" in such a way that makes sense for their application (see Section 5.4.7).
До истечения таймера N может прийти несколько запросов NOTIFY с разных мест назначения (см. раздел 4.4.1). Каждый из этих запросов устанавливает новое использование диалога и новую подписку. После истечения таймера N подписчик ДОЛЖЕН отклонять любые такие запросы NOTIFY, которые иначе установили бы новое использование диалога, с кодом ответа 481 (Subscription does not exist). До прихода первого запроса NOTIFY подписчик должен считать состояние ресурса, на который оформлена подписка, нейтральным. Спецификации пакетов событий ДОЛЖНЫ определять это «нейтральное состояние» так, чтобы оно имело смысл для их приложения (см. раздел 5.4.7).
Due to the potential for out-of-order messages, packet loss, and forking, the subscriber MUST be prepared to receive NOTIFY requests before the SUBSCRIBE transaction has completed.
Из-за возможности нарушения порядка сообщений, потери пакетов и разветвления подписчик ДОЛЖЕН быть готов получать запросы NOTIFY до завершения транзакции SUBSCRIBE.
Except as noted above, processing of this NOTIFY request is the same as in Section 4.1.3.
За исключением отмеченного выше, обработка этого запроса NOTIFY такая же, как в разделе 4.1.3.
4.1.3. Receiving and Processing State Information
4.1.3. Получение и обработка сведений о состоянии
Subscribers receive information about the state of a resource to which they have subscribed in the form of NOTIFY requests.
Подписчики получают информацию о состоянии ресурса, на который они оформили подписку, в виде запросов NOTIFY.
Upon receiving a NOTIFY request, the subscriber should check that it matches at least one of its outstanding subscriptions; if not, it MUST return a 481 (Subscription does not exist) response unless another 400- or 500-class response is more appropriate. The rules for matching NOTIFY requests with subscriptions that create a new dialog usage are described in Section 4.4.1. Notifications for subscriptions that were created inside an existing dialog match if they are in the same dialog and the "Event" header fields match (as described in Section 8.2.1).
Получив запрос NOTIFY, подписчик должен проверить, что он соответствует хотя бы одной из его незавершённых подписок; если нет, он ДОЛЖЕН вернуть ответ 481 (Subscription does not exist), если только другой ответ класса 400 или 500 не является более подходящим. Правила сопоставления запросов NOTIFY с подписками, создающими новое использование диалога, описаны в разделе 4.4.1. Уведомления для подписок, созданных внутри существующего диалога, считаются совпадающими, если они находятся в одном диалоге и поля заголовков «Event» совпадают (как описано в разделе 8.2.1).
If, for some reason, the event package designated in the "Event" header field of the NOTIFY request is not supported, the subscriber will respond with a 489 (Bad Event) response.
Если по какой-либо причине пакет событий, обозначенный в поле заголовка «Event» запроса NOTIFY, не поддерживается, подписчик ответит ответом 489 (Bad Event).
To prevent spoofing of events, NOTIFY requests SHOULD be authenticated using any defined SIP authentication mechanism, such as those described in Sections 22.2 and 23 of [RFC3261].
Чтобы предотвратить подмену событий, запросы NOTIFY СЛЕДУЕТ аутентифицировать с помощью любого определённого механизма аутентификации SIP, например описанного в разделах 22.2 и 23 [RFC3261].
NOTIFY requests MUST contain "Subscription-State" header fields that indicate the status of the subscription.
Запросы NOTIFY ДОЛЖНЫ содержать поля заголовка «Subscription-State», указывающие статус подписки.
If the "Subscription-State" header field value is "active", it means that the subscription has been accepted and (in general) has been authorized. If the header field also contains an "expires" parameter, the subscriber SHOULD take it as the authoritative subscription duration and adjust accordingly. The "retry-after" and "reason" parameters have no semantics for "active". If the "Subscription-State" value is "pending", the subscription has been received by the notifier, but there is insufficient policy information to grant or deny the subscription yet. If the header field also contains an "expires" parameter, the subscriber SHOULD take it as the authoritative subscription duration and adjust accordingly. No further action is necessary on the part of the subscriber. The "retry-after" and "reason" parameters have no semantics for "pending".
Если значение поля заголовка «Subscription-State» равно «active», это означает, что подписка принята и (в общем случае) авторизована. Если поле заголовка также содержит параметр «expires», подписчику СЛЕДУЕТ принять его как авторитетную длительность подписки и соответствующим образом скорректировать свои действия. Параметры «retry-after» и «reason» не имеют семантики для «active». Если значение «Subscription-State» равно «pending», подписка получена уведомителем, но информации о политике недостаточно, чтобы пока предоставить или отклонить подписку. Если поле заголовка также содержит параметр «expires», подписчику СЛЕДУЕТ принять его как авторитетную длительность подписки и соответствующим образом скорректировать свои действия. Дальнейших действий со стороны подписчика не требуется. Параметры «retry-after» и «reason» не имеют семантики для «pending».

4.1.4. Forking of SUBSCRIBE Requests
4.1.4. Разветвление запросов SUBSCRIBE
In accordance with the rules for proxying non-INVITE requests as defined in [RFC3261], successful SUBSCRIBE requests will receive only one 200-class response; however, due to forking, the subscription may have been accepted by multiple nodes. The subscriber MUST therefore be prepared to receive NOTIFY requests with "From:" tags that differ from the "To:" tag received in the SUBSCRIBE 200-class response. If multiple NOTIFY requests are received in different dialogs in response to a single SUBSCRIBE request, each dialog represents a different destination to which the SUBSCRIBE request was forked. Subscriber handling in such situations varies by event package; see Section 5.4.9 for details.
В соответствии с правилами проксирования запросов, отличных от INVITE, как определено в [RFC3261], успешные запросы SUBSCRIBE получат только один ответ класса 200; однако из-за разветвления подписка могла быть принята несколькими узлами. Поэтому подписчик ДОЛЖЕН быть готов получать запросы NOTIFY с тегами «From:», отличающимися от тега «To:», полученного в ответе класса 200 на SUBSCRIBE. Если в ответ на один запрос SUBSCRIBE получено несколько запросов NOTIFY в разных диалогах, каждый диалог представляет собой отдельное место назначения, на которое был разветвлён запрос SUBSCRIBE. Поведение подписчика в таких ситуациях зависит от пакета событий; подробности см. в разделе 5.4.9.
4.2. Notifier Behavior
4.2. Поведение уведомителя
4.2.1. Subscription Establishment and Maintenance
4.2.1. Установление и поддержание подписки
Notifiers learn about subscription requests by receiving SUBSCRIBE requests from interested parties. Notifiers MUST NOT create subscriptions except upon receipt of a SUBSCRIBE request. However, for historical reasons, the implicit creation of subscriptions as defined in [RFC3515] is still permitted.
Уведомители узнают о запросах на подписку, получая запросы SUBSCRIBE от заинтересованных сторон. Уведомители НЕ ДОЛЖНЫ создавать подписки иначе как по получении запроса SUBSCRIBE. Однако по историческим причинам неявное создание подписок, как определено в [RFC3515], всё ещё допускается.
[RFC3265] allowed the creation of subscriptions using means other than the SUBSCRIBE method. The only standardized use of this mechanism is the REFER method [RFC3515]. Implementation experience with REFER has shown that the implicit creation of a subscription has a number of undesirable effects, such as the inability to signal the success of a REFER request while signaling a problem with the subscription, and difficulty performing one action without the other. Additionally, the proper exchange of dialog identifiers is difficult without dialog reuse (which has its own set of problems; see Section 4.5).
[RFC3265] допускал создание подписок способами, отличными от метода SUBSCRIBE. Единственное стандартизованное применение этого механизма -- метод REFER [RFC3515]. Опыт реализации REFER показал, что неявное создание подписки имеет ряд нежелательных последствий, таких как невозможность сообщить об успехе запроса REFER при одновременном сообщении о проблеме с подпиской и трудность выполнения одного действия без другого. Кроме того, надлежащий обмен идентификаторами диалога затруднителен без повторного использования диалога (которое имеет свой собственный набор проблем; см. раздел 4.5).

When a subscription is created in the notifier, it stores the event package name as part of the subscription information.

The "Expires" values present in SUBSCRIBE 200-class responses behave in the same way as they do in REGISTER responses: the server MAY shorten the interval but MUST NOT lengthen it.

4.2.1.2. Confirmation of Subscription Creation/Refreshing
4.2.1.2. Подтверждение создания и обновления подписки
Upon successfully accepting or refreshing a subscription, notifiers MUST send a NOTIFY request immediately to communicate the current resource state to the subscriber. This NOTIFY request is sent on the same dialog as created by the SUBSCRIBE response. If the resource has no meaningful state at the time that the SUBSCRIBE request is processed, this NOTIFY request MAY contain an empty or neutral body. See Section 4.2.2 for further details on NOTIFY request generation.
Успешно приняв или обновив подписку, уведомители ДОЛЖНЫ немедленно отправить запрос NOTIFY, чтобы сообщить подписчику текущее состояние ресурса. Этот запрос NOTIFY отправляется в том же диалоге, который создан ответом на SUBSCRIBE. Если ресурс не имеет осмысленного состояния на момент обработки запроса SUBSCRIBE, этот запрос NOTIFY МОЖЕТ содержать пустое или нейтральное тело. Дополнительные сведения о формировании запросов NOTIFY см. в разделе 4.2.2.
Note that a NOTIFY request is always sent immediately after any 200-class response to a SUBSCRIBE request, regardless of whether the subscription has already been authorized.
Обратите внимание, что запрос NOTIFY всегда отправляется сразу после любого ответа класса 200 на запрос SUBSCRIBE, независимо от того, была ли подписка уже авторизована.
4.2.1.3. Authentication/Authorization of SUBSCRIBE Requests
4.2.1.3. Аутентификация и авторизация запросов SUBSCRIBE
Privacy concerns may require that notifiers apply policy to determine whether a particular subscriber is authorized to subscribe to a certain set of events. Such policy may be defined by mechanisms such as access control lists or real-time interaction with a user. In general, authorization of subscribers prior to authentication is not particularly useful.
Соображения конфиденциальности могут потребовать, чтобы уведомители применяли политику для определения того, авторизован ли конкретный подписчик подписываться на определённый набор событий. Такая политика может определяться такими механизмами, как списки управления доступом или взаимодействие с пользователем в реальном времени. В общем случае авторизация подписчиков до аутентификации не особенно полезна.
SIP authentication mechanisms are discussed in [RFC3261]. Note that, even if the notifier node typically acts as a proxy, authentication for SUBSCRIBE requests will always be performed via a 401 (Unauthorized) response, not a 407 (Proxy Authentication Required). Notifiers always act as user agents when accepting subscriptions and sending notifications.
Механизмы аутентификации SIP обсуждаются в [RFC3261]. Обратите внимание, что даже если узел-уведомитель обычно действует как прокси, аутентификация запросов SUBSCRIBE всегда будет выполняться посредством ответа 401 (Unauthorized), а не 407 (Proxy Authentication Required). Уведомители всегда действуют как пользовательские агенты, когда принимают подписки и отправляют уведомления.
Of course, when acting as a proxy, a node will perform normal proxy authentication (using 407). The foregoing explanation is a reminder that notifiers are always user agents and, as such, perform user agent authentication.
Разумеется, действуя как прокси, узел будет выполнять обычную аутентификацию прокси (с использованием 407). Приведённое выше объяснение напоминает, что уведомители всегда являются пользовательскими агентами и, как таковые, выполняют аутентификацию пользовательского агента.
If authorization fails based on an access list or some other automated mechanism (i.e., it can be automatically authoritatively determined that the subscriber is not authorized to subscribe), the notifier SHOULD reply to the request with a 403 (Forbidden) or 603 (Decline) response, unless doing so might reveal information that should stay private; see Section 6.2.
Если авторизация не удалась на основании списка доступа или какого-либо иного автоматизированного механизма (т. е. можно автоматически и авторитетно определить, что подписчик не авторизован подписываться), уведомителю СЛЕДУЕТ ответить на запрос ответом 403 (Forbidden) или 603 (Decline), если только это не раскроет сведения, которые должны оставаться частными; см. раздел 6.2.
If the notifier owner is interactively queried to determine whether a subscription is allowed, a 200 (OK) response is returned immediately. Note that a NOTIFY request is still formed and sent under these circumstances, as described in the previous section.
Если владелец уведомителя опрашивается в интерактивном режиме для определения того, разрешена ли подписка, немедленно возвращается ответ 200 (OK). Обратите внимание, что в этих обстоятельствах запрос NOTIFY всё равно формируется и отправляется, как описано в предыдущем разделе.
If subscription authorization was delayed and the notifier wishes to convey that such authorization has been declined, it may do so by sending a NOTIFY request containing a "Subscription-State" header field with a value of "terminated" and a reason parameter of "rejected".
Если авторизация подписки была отложена и уведомитель желает сообщить, что в такой авторизации было отказано, он может сделать это, отправив запрос NOTIFY, содержащий поле заголовка «Subscription-State» со значением «terminated» и параметром причины «rejected».
4.2.1.4. Refreshing of Subscriptions
4.2.1.4. Обновление подписок
When a notifier receives a subscription refresh, assuming that the subscriber is still authorized, the notifier updates the expiration time for subscription. As with the initial subscription, the server MAY shorten the amount of time until expiration but MUST NOT increase it. The final expiration time is placed in the "Expires" header field in the response. If the duration specified in a SUBSCRIBE request is unacceptably short, the notifier SHOULD respond with a 423 (Interval Too Brief) response.
Когда уведомитель получает обновление подписки, при условии что подписчик по-прежнему авторизован, уведомитель обновляет время истечения подписки. Как и при первоначальной подписке, сервер МОЖЕТ сократить время до истечения, но НЕ ДОЛЖЕН его увеличивать. Окончательное время истечения помещается в поле заголовка «Expires» в ответе. Если длительность, указанная в запросе SUBSCRIBE, неприемлемо мала, уведомитель ДОЛЖЕН ответить ответом 423 (Interval Too Brief).
If no refresh for a notification address is received before its expiration time, the subscription is removed. When removing a subscription, the notifier SHOULD send a NOTIFY request with a "Subscription-State" value of "terminated" to inform it that the subscription is being removed. If such a request is sent, the "Subscription-State" header field SHOULD contain a "reason=timeout" parameter.
Если до времени истечения адреса уведомления не получено обновление, подписка удаляется. При удалении подписки уведомителю СЛЕДУЕТ отправить запрос NOTIFY со значением «Subscription-State», равным «terminated», чтобы сообщить, что подписка удаляется. Если такой запрос отправляется, поле заголовка «Subscription-State» ДОЛЖНО содержать параметр «reason=timeout».
Clients can cause a subscription to be terminated immediately by sending a SUBSCRIBE request with an "Expires" header field set to '0'. Notifiers largely treat this the same way as any other subscription expiration: they send a NOTIFY request containing a "Subscription-State" of "terminated", with a reason code of "timeout." For consistency with state polling (see Section 4.4.3) and subscription refreshes, the notifier may choose to include resource state in this final NOTIFY request. However, in some cases, including such state makes no sense. Under such circumstances, the notifier may choose to omit state information from the terminal NOTIFY request.
Клиенты могут вызвать немедленное завершение подписки, отправив запрос SUBSCRIBE с полем заголовка «Expires», установленным в «0». Уведомители в основном обрабатывают это так же, как любое другое истечение подписки: они отправляют запрос NOTIFY, содержащий «Subscription-State» со значением «terminated» и кодом причины «timeout». Для согласованности с опросом состояния (см. раздел 4.4.3) и обновлениями подписки уведомитель может пожелать включить состояние ресурса в этот финальный запрос NOTIFY. Однако в некоторых случаях включение такого состояния не имеет смысла. В таких обстоятельствах уведомитель может пожелать опустить сведения о состоянии в терминальном запросе NOTIFY.
The sending of a NOTIFY request when a subscription expires allows the corresponding dialog usage to be terminated, if appropriate.
Отправка запроса NOTIFY при истечении подписки позволяет завершить соответствующее использование диалога, если это уместно.

Когда происходит изменение состояния, на которое оформлена подписка, уведомителю СЛЕДУЕТ немедленно сформировать и отправить запрос NOTIFY, если только переход состояния не вызван сбоем транзакции NOTIFY. If the NOTIFY request fails due to expiration of SIP Timer F (transaction timeout), the notifier SHOULD remove the subscription.

This behavior prevents unnecessary transmission of state information for subscribers who have crashed or disappeared from the network. Because such transmissions will be sent multiple times, per the retransmission algorithm defined in [RFC3261] (instead of the typical single transmission for functioning clients), continuing to service them when no client is available to acknowledge them could place undue strain on a network. Upon client restart or reestablishment of a network connection, it is expected that clients will send SUBSCRIBE requests to refresh potentially stale state information; such requests will reinstall subscriptions in all relevant nodes.
Такое поведение предотвращает ненужную передачу сведений о состоянии подписчикам, которые аварийно завершили работу или исчезли из сети. Поскольку такие передачи будут отправляться многократно, согласно алгоритму повторной передачи, определённому в [RFC3261] (вместо обычной однократной передачи для работающих клиентов), продолжение их обслуживания при отсутствии клиента, способного подтвердить их, может создать чрезмерную нагрузку на сеть. После перезапуска клиента или восстановления сетевого соединения ожидается, что клиенты отправят запросы SUBSCRIBE, чтобы обновить потенциально устаревшие сведения о состоянии; такие запросы восстановят подписки во всех соответствующих узлах.
If the NOTIFY transaction fails due to the receipt of a 404, 405, 410, 416, 480-485, 489, 501, or 604 response to the NOTIFY request, the notifier MUST remove the corresponding subscription. See [RFC5057] for further details and notes about the effect of error codes on dialogs and usages within dialog (such as subscriptions).
Если транзакция NOTIFY завершается неудачей из-за получения ответа 404, 405, 410, 416, 480-485, 489, 501 или 604 на запрос NOTIFY, уведомитель ДОЛЖЕН удалить соответствующую подписку. Дополнительные сведения и замечания о влиянии кодов ошибок на диалоги и использования в диалоге (такие как подписки) см. в [RFC5057].
A notify error response would generally indicate that something has gone wrong with the subscriber or with some proxy on the way to the subscriber. If the subscriber is in error, it makes the most sense to allow the subscriber to rectify the situation (by re-subscribing) once the error condition has been handled. If a proxy is in error, the periodic sending of SUBSCRIBE requests to refresh the expiration timer will reinstall subscription state once the network problem has been resolved.
Ответ об ошибке NOTIFY обычно указывает, что-то пошло не так с подписчиком или с каким-либо прокси на пути к подписчику. Если ошибка у подписчика, разумнее всего позволить подписчику исправить ситуацию (путём повторной подписки) после того, как условие ошибки будет устранено. Если ошибка в прокси, периодическая отправка запросов SUBSCRIBE для обновления таймера истечения восстановит состояние подписки, как только сетевая проблема будет решена.
NOTIFY requests MUST contain a "Subscription-State" header field with a value of "active", "pending", or "terminated". The "active" value indicates that the subscription has been accepted and has been authorized (in most cases; see Section 6.2). The "pending" value indicates that the subscription has been received, but that policy information is insufficient to accept or deny the subscription at this time. The "terminated" value indicates that the subscription is not active.
Запросы NOTIFY ДОЛЖНЫ содержать поле заголовка «Subscription-State» со значением «active», «pending» или «terminated». Значение «active» указывает, что подписка принята и авторизована (в большинстве случаев; см. раздел 6.2). Значение «pending» указывает, что подписка получена, но информации о политике недостаточно, чтобы принять или отклонить подписку в настоящее время. Значение «terminated» указывает, что подписка не активна.
If the value of the "Subscription-State" header field is "active" or "pending", the notifier MUST also include in the "Subscription-State" header field an "expires" parameter that indicates the time remaining on the subscription. The notifier MAY use this mechanism to shorten a subscription; however, this mechanism MUST NOT be used to lengthen a subscription.
Если значение поля заголовка «Subscription-State» равно «active» или «pending», уведомитель ДОЛЖЕН также включить в поле заголовка «Subscription-State» параметр «expires», указывающий оставшееся время подписки. Уведомитель МОЖЕТ использовать этот механизм для сокращения подписки; однако этот механизм НЕ ДОЛЖЕН использоваться для удлинения подписки.
Including expiration information for active and pending subscriptions is necessary in case the SUBSCRIBE request forks, since the response to a forked SUBSCRIBE request may not be received by the subscriber. The period of time for a subscription can be shortened to zero by the notifier. In other words, it is perfectly valid for a SUBSCRIBE request with a non-zero expires to be answered with a NOTIFY request that contains "Subscription-Status: terminated;reason=expired". This merely means that the notifier has shortened the subscription timeout to zero, and the subscription has expired instantaneously. 4.2.3. PSTN/Internet Interworking (PINT) Compatibility
4.2.3. Совместимость с взаимодействием ТфОП и Интернета (PINT)
The "Event" header field is considered mandatory for the purposes of this document. However, to maintain compatibility with PINT (see [RFC2848]), notifiers MAY interpret a SUBSCRIBE request with no "Event" header field as requesting a subscription to PINT events. If a notifier does not support PINT, it SHOULD return 489 (Bad Event) to any SUBSCRIBE requests without an "Event" header field.
Поле заголовка «Event» считается обязательным для целей настоящего документа. Однако для сохранения совместимости с PINT (см. [RFC2848]) уведомители МОГУТ интерпретировать запрос SUBSCRIBE без поля заголовка «Event» как запрос подписки на события PINT. Если уведомитель не поддерживает PINT, ему СЛЕДУЕТ возвращать 489 (Bad Event) на любые запросы SUBSCRIBE без поля заголовка «Event».
4.3. Proxy Behavior
4.3. Поведение прокси
Proxies need no additional behavior beyond that described in [RFC3261] to support SUBSCRIBE and NOTIFY transactions. If a proxy wishes to see all of the SUBSCRIBE and NOTIFY requests for a given dialog, it MUST add a "Record-Route" header field to the initial SUBSCRIBE request and all NOTIFY requests. It MAY choose to include "Record-Route" in subsequent SUBSCRIBE requests; however, these requests cannot cause the dialog's route set to be modified.
Прокси не нуждаются в дополнительном поведении помимо описанного в [RFC3261] для поддержки транзакций SUBSCRIBE и NOTIFY. Если прокси желает видеть все запросы SUBSCRIBE и NOTIFY для данного диалога, он ДОЛЖЕН добавить поле заголовка «Record-Route» в первоначальный запрос SUBSCRIBE и во все запросы NOTIFY. Он МОЖЕТ включить «Record-Route» в последующие запросы SUBSCRIBE; однако эти запросы не могут привести к изменению набора маршрутов диалога.
Proxies that did not add a "Record-Route" header field to the initial SUBSCRIBE request MUST NOT add a "Record-Route" header field to any of the associated NOTIFY requests.
Прокси, которые не добавили поле заголовка «Record-Route» в первоначальный запрос SUBSCRIBE, НЕ ДОЛЖНЫ добавлять поле заголовка «Record-Route» ни в один из связанных запросов NOTIFY.

4.4. Common Behavior
4.4. Общее поведение
4.4.1. Dialog Creation and Termination
4.4.1. Создание и завершение диалога
Dialogs usages are created upon completion of a NOTIFY transaction for a new subscription, unless the NOTIFY request contains a "Subscription-State" of "terminated."
Использования диалога создаются по завершении транзакции NOTIFY для новой подписки, если только запрос NOTIFY не содержит «Subscription-State» со значением «terminated».
Because the dialog usage is established by the NOTIFY request, the route set at the subscriber is taken from the NOTIFY request itself, as opposed to the route set present in the 200-class response to the SUBSCRIBE request.
Поскольку использование диалога устанавливается запросом NOTIFY, набор маршрутов у подписчика берётся из самого запроса NOTIFY, а не из набора маршрутов, присутствующего в ответе класса 200 на запрос SUBSCRIBE.
NOTIFY requests are matched to such SUBSCRIBE requests if they contain the same "Call-ID", a "To" header field "tag" parameter that matches the "From" header field "tag" parameter of the SUBSCRIBE request, and the same "Event" header field. Rules for comparisons of the "Event" header fields are described in Section 8.2.1.
Запросы NOTIFY сопоставляются с такими запросами SUBSCRIBE, если они содержат тот же «Call-ID», параметр «tag» поля заголовка «To», совпадающий с параметром «tag» поля заголовка «From» запроса SUBSCRIBE, и то же поле заголовка «Event». Правила сравнения полей заголовков «Event» описаны в разделе 8.2.1.
A subscription is destroyed after a notifier sends a NOTIFY request with a "Subscription-State" of "terminated", or in certain error situations described elsewhere in this document. The subscriber will generally answer such final requests with a 200 (OK) response (unless a condition warranting an alternate response has arisen). Except when the mechanism described in Section 4.5.2 is used, the destruction of a subscription results in the termination of its associated dialog.
Подписка уничтожается после того, как уведомитель отправит запрос NOTIFY со значением «Subscription-State», равным «terminated», или в некоторых ошибочных ситуациях, описанных в других местах настоящего документа. Подписчик, как правило, ответит на такие финальные запросы ответом 200 (OK), если только не возникло условие, требующее иного ответа. За исключением случая, когда используется механизм, описанный в разделе 4.5.2, уничтожение подписки приводит к завершению связанного с ней диалога.
A subscriber may send a SUBSCRIBE request with an "Expires" header field of 0 in order to trigger the sending of such a NOTIFY request; however, for the purposes of subscription and dialog lifetime, the subscription is not considered terminated until the NOTIFY transaction with a "Subscription-State" of "terminated" completes.

4.4.2. Notifier Migration
4.4.2. Миграция уведомителя
It is often useful to allow migration of subscriptions between notifiers. Such migration may be effected by sending a NOTIFY request with a "Subscription-State" header field of "terminated" and a reason parameter of "deactivated". This NOTIFY request is otherwise normal and is formed as described in Section 4.2.2.
Часто бывает полезно разрешить миграцию подписок между уведомителями. Такая миграция может быть выполнена отправкой запроса NOTIFY с полем заголовка «Subscription-State» со значением «terminated» и параметром причины «deactivated». В остальном этот запрос NOTIFY обычен и формируется так, как описано в разделе 4.2.2.
Upon receipt of this NOTIFY request, the subscriber SHOULD attempt to re-subscribe (as described in the preceding sections). Note that this subscription is established on a new dialog, and does not reuse the route set from the previous subscription dialog. The actual migration is effected by making a change to the policy (such as routing decisions) of one or more servers to which the SUBSCRIBE request will be sent in such a way that a different node ends up responding to the SUBSCRIBE request. This may be as simple as a change in the local policy in the notifier from which the subscription is migrating so that it serves as a proxy or redirect server instead of a notifier.
Получив этот запрос NOTIFY, подписчику СЛЕДУЕТ попытаться подписаться заново (как описано в предыдущих разделах). Обратите внимание, что эта подписка устанавливается в новом диалоге и не использует набор маршрутов из предыдущего диалога подписки. Фактическая миграция выполняется путём изменения политики (например, решений о маршрутизации) одного или нескольких серверов, которым будет отправлен запрос SUBSCRIBE, так, чтобы в итоге на запрос SUBSCRIBE отвечал другой узел. Это может быть так просто, как изменение локальной политики уведомителя, от которого мигрирует подписка, так чтобы он служил прокси или сервером перенаправления вместо уведомителя.
Whether, when, and why to perform notifier migrations may be described in individual event packages; otherwise, such decisions are a matter of local notifier policy and are left up to individual implementations.
Следует ли выполнять миграцию уведомителей, когда и почему, может быть описано в отдельных пакетах событий; в противном случае такие решения относятся к локальной политике уведомителя и оставляются на усмотрение отдельных реализаций.
4.4.3. Polling Resource State
4.4.3. Опрос состояния ресурса
A natural consequence of the behavior described in the preceding sections is that an immediate fetch without a persistent subscription may be effected by sending a SUBSCRIBE with an "Expires" of 0.
Естественным следствием поведения, описанного в предыдущих разделах, является то, что немедленную выборку без постоянной подписки можно выполнить, отправив SUBSCRIBE со значением «Expires», равным 0.
Of course, an immediate fetch while a subscription is active may be effected by sending a SUBSCRIBE request with an "Expires" equal to the number of seconds remaining in the subscription.
Разумеется, немедленную выборку при активной подписке можно выполнить, отправив запрос SUBSCRIBE со значением «Expires», равным числу секунд, оставшихся до истечения подписки.
Upon receipt of this SUBSCRIBE request, the notifier (or notifiers, if the SUBSCRIBE request was forked) will send a NOTIFY request containing resource state in the same dialog.
Получив этот запрос SUBSCRIBE, уведомитель (или уведомители, если запрос SUBSCRIBE был разветвлён) отправит запрос NOTIFY, содержащий состояние ресурса, в том же диалоге.
Note that the NOTIFY requests triggered by SUBSCRIBE requests with "Expires" header fields of 0 will contain a "Subscription-State" value of "terminated" and a "reason" parameter of "timeout".
Обратите внимание, что запросы NOTIFY, вызванные запросами SUBSCRIBE с полем заголовка «Expires», равным 0, будут содержать значение «Subscription-State», равное «terminated», и параметр «reason» со значением «timeout».
Polling of event state can cause significant increases in load on the network and notifiers; as such, it should be used only sparingly. In particular, polling SHOULD NOT be used in circumstances in which it will typically result in more network messages than long-running subscriptions.
Опрос состояния событий может приводить к значительному увеличению нагрузки на сеть и уведомителей; поэтому его следует использовать лишь изредка. В частности, опрос НЕ СЛЕДУЕТ использовать в обстоятельствах, когда он, как правило, приведёт к большему числу сетевых сообщений, чем долговременные подписки.
When polling is used, subscribers SHOULD attempt to cache authentication credentials between polls so as to reduce the number of messages sent.
Когда используется опрос, подписчикам СЛЕДУЕТ пытаться кэшировать учётные данные аутентификации между опросами, чтобы сократить число отправляемых сообщений.
Due to the requirement on notifiers to send a NOTIFY request immediately upon receipt of a SUBSCRIBE request, the state provided by polling is limited to the information that the notifier has immediate local access to when it receives the SUBSCRIBE request. If, for example, the notifier generally needs to retrieve state from another network server, then that state will be absent from the NOTIFY request that results from polling.

4.4.4. "Allow-Events" Header Field Usage
4.4.4. Использование поля заголовка «Allow-Events»
The "Allow-Events" header field, if present, MUST include a comprehensive and inclusive list of tokens that indicates the event packages for which the user agent can act as a notifier. In other words, a user agent sending an "Allow-Events" header field is advertising that it can process SUBSCRIBE requests and generate NOTIFY requests for all of the event packages listed in that header field.
Поле заголовка «Allow-Events», если оно присутствует, ДОЛЖНО содержать полный и исчерпывающий список токенов, указывающий пакеты событий, для которых пользовательский агент может действовать как уведомитель. Иными словами, пользовательский агент, отправляющий поле заголовка «Allow-Events», объявляет, что он может обрабатывать запросы SUBSCRIBE и формировать запросы NOTIFY для всех пакетов событий, перечисленных в этом поле заголовка.
Any user agent that can act as a notifier for one or more event packages SHOULD include an appropriate "Allow-Events" header field indicating all supported events in all methods which initiate dialogs and their responses (such as INVITE) and OPTIONS responses.
Любому пользовательскому агенту, который может действовать как уведомитель для одного или нескольких пакетов событий, СЛЕДУЕТ включать подходящее поле заголовка «Allow-Events», указывающее все поддерживаемые события, во все методы, инициирующие диалоги, и в их ответы (например, INVITE), а также в ответы OPTIONS.
This information is very useful, for example, in allowing user agents to render particular interface elements appropriately according to whether the events required to implement the features they represent are supported by the appropriate nodes.
Эта информация очень полезна, например, тем, что позволяет пользовательским агентам надлежащим образом отображать те или иные элементы интерфейса в зависимости от того, поддерживаются ли соответствующими узлами события, необходимые для реализации представляемых ими функций.
On the other hand, it doesn't necessarily make much sense to indicate supported events inside a dialog established by a NOTIFY request if the only event package supported is the one associated with that subscription.
С другой стороны, не обязательно имеет большой смысл указывать поддерживаемые события внутри диалога, установленного запросом NOTIFY, если единственный поддерживаемый пакет событий -- это тот, который связан с данной подпиской.
Note that "Allow-Events" header fields MUST NOT be inserted by proxies.
Обратите внимание, что поля заголовка «Allow-Events» НЕ ДОЛЖНЫ вставляться прокси.
The "Allow-Events" header field does not include a list of the event template-packages supported by an implementation. If a subscriber wishes to determine which event template-packages are supported by a notifier, it can probe for such support by attempting to subscribe to the event template-packages it wishes to use.
Поле заголовка «Allow-Events» не содержит списка шаблонных пакетов событий, поддерживаемых реализацией. Если подписчик желает определить, какие шаблонные пакеты событий поддерживаются уведомителем, он может проверить такую поддержку, попытавшись подписаться на нужные ему шаблонные пакеты событий.
For example: to check for support for the templatized package "presence.winfo", a client may attempt to subscribe to that event package for a known resource, using an "Expires" header value of 0. If the response is a 489 error code, then the client can deduce that "presence.winfo" is unsupported.
Например: чтобы проверить поддержку шаблонизированного пакета «presence.winfo», клиент может попытаться подписаться на этот пакет событий для известного ресурса, используя значение «Expires», равное 0. Если ответом будет код ошибки 489, клиент может заключить, что «presence.winfo» не поддерживается.
4.5. Targeting Subscriptions at Devices
4.5. Адресация подписок на устройства
[RFC3265] defined a mechanism by which subscriptions could share dialogs with invite usages and with other subscriptions. The purpose of this behavior was to allow subscribers to ensure that a subscription arrived at the same device as an established dialog. Unfortunately, the reuse of dialogs has proven to be exceedingly confusing. [RFC5057] attempted to clarify proper behavior in a variety of circumstances; however, the ensuing rules remain confusing and prone to implementation error. At the same time, the mechanism described in [RFC5627] now provides a far more elegant and unambiguous means to achieve the same goal.
[RFC3265] определил механизм, с помощью которого подписки могли совместно использовать диалоги с использованиями INVITE и с другими подписками. Целью такого поведения было позволить подписчикам гарантировать, что подписка придёт на то же устройство, что и установленный диалог. К сожалению, повторное использование диалогов оказалось чрезвычайно запутанным. [RFC5057] попытался разъяснить надлежащее поведение в различных обстоятельствах; однако вытекающие из этого правила остаются запутанными и подверженными ошибкам реализации. В то же время механизм, описанный в [RFC5627], теперь предоставляет гораздо более изящное и однозначное средство для достижения той же цели.
Consequently, the dialog reuse technique described in RFC 3265 is now deprecated.
Следовательно, метод повторного использования диалога, описанный в RFC 3265, теперь объявлен устаревшим.
This dialog-sharing technique has also historically been used as a means for targeting an event package at a dialog. This usage can be seen, for example, in certain applications of the REFER method [RFC3515]. With the removal of dialog reuse, an alternate (and more explicit) means of targeting dialogs needs to be used for this type of correlation. The appropriate means of such targeting is left up to the actual event packages. Candidates include the "Target-Dialog" header field [RFC4538], the "Join" header field [RFC3911], and the "Replaces" header field [RFC3891], depending on the semantics desired. Alternately, if the semantics of those header fields do not match the event package's purpose for correlation, event packages can devise their own means of identifying dialogs. For an example of this approach, see the Dialog Event Package [RFC4235].
Этот метод совместного использования диалога исторически также применялся как средство адресации пакета событий на диалог. Такое применение можно видеть, например, в некоторых приложениях метода REFER [RFC3515]. С устранением повторного использования диалога для такого рода соотнесения нужно использовать альтернативное (и более явное) средство адресации диалогов. Надлежащее средство такой адресации оставляется на усмотрение самих пакетов событий. Кандидаты включают поле заголовка «Target-Dialog» [RFC4538], поле заголовка «Join» [RFC3911] и поле заголовка «Replaces» [RFC3891], в зависимости от желаемой семантики. В качестве альтернативы, если семантика этих полей заголовков не соответствует цели пакета событий по соотнесению, пакеты событий могут разработать собственные средства идентификации диалогов. Пример такого подхода см. в пакете событий диалога [RFC4235].
4.5.1. Using GRUUs to Route to Devices
4.5.1. Использование GRUU для маршрутизации к устройствам
Notifiers MUST implement the Globally Routable User Agent URI (GRUU) extension defined in [RFC5627], and MUST use a GRUU as their local target. This allows subscribers to explicitly target desired devices.
Уведомители ДОЛЖНЫ реализовывать расширение Globally Routable User Agent URI (GRUU), определённое в [RFC5627], и ДОЛЖНЫ использовать GRUU в качестве своей локальной цели. Это позволяет подписчикам явно адресовать нужные устройства.
If a subscriber wishes to subscribe to a resource on the same device as an established dialog, it should check whether the remote contact in that dialog is a GRUU (i.e., whether it contains a "gr" URI parameter). If so, the subscriber creates a new dialog, using the GRUU as the Request URI for the new SUBSCRIBE request.
Если подписчик желает подписаться на ресурс на том же устройстве, что и установленный диалог, ему следует проверить, является ли удалённый контакт в этом диалоге GRUU (т. е. содержит ли он параметр URI «gr»). Если да, подписчик создаёт новый диалог, используя GRUU в качестве Request URI нового запроса SUBSCRIBE.
Because GRUUs are guaranteed to route to a specific device, this ensures that the subscription will be routed to the same place as the established dialog.
Поскольку GRUU гарантированно маршрутизируются к конкретному устройству, это гарантирует, что подписка будет направлена туда же, куда и установленный диалог.
4.5.2. Sharing Dialogs
4.5.2. Совместное использование диалогов
For compatibility with older clients, subscriber and notifier implementations may choose to allow dialog sharing. The behavior of multiple usages within a dialog are described in [RFC5057].
Для совместимости со старыми клиентами реализации подписчика и уведомителя могут пожелать разрешить совместное использование диалогов. Поведение нескольких использований в диалоге описано в [RFC5057].
Subscribers MUST NOT attempt to reuse dialogs whose remote target is a GRUU. Note that the techniques described in this section are included for backwards-compatibility purposes only. Because subscribers cannot reuse dialogs with a GRUU for their remote target, and because notifiers must use GRUUs as their local target, any two implementations that conform to this specification will automatically use the mechanism described in Section 4.5.1.
Подписчики НЕ ДОЛЖНЫ пытаться повторно использовать диалоги, удалённая цель которых является GRUU. Обратите внимание, что описанные в этом разделе методы включены исключительно для целей обратной совместимости. Поскольку подписчики не могут повторно использовать диалоги, удалённая цель которых является GRUU, а уведомители должны использовать GRUU в качестве своей локальной цели, любые две реализации, соответствующие настоящей спецификации, автоматически будут использовать механизм, описанный в разделе 4.5.1.
Further note that the prohibition on reusing dialogs does not exempt implicit subscriptions created by the REFER method. This means that implementations complying with this specification are required to use the "Target-Dialog" mechanism described in [RFC4538] when the remote target is a GRUU.
Далее отметим, что запрет на повторное использование диалогов не делает исключения для неявных подписок, созданных методом REFER. Это означает, что реализации, соответствующие настоящей спецификации, обязаны использовать механизм «Target-Dialog», описанный в [RFC4538], когда удалённая цель является GRUU.
If a subscriber wishes to subscribe to a resource on the same device as an established dialog and the remote contact is not a GRUU, it MAY revert to dialog-sharing behavior. Alternately, it MAY choose to treat the remote party as incapable of servicing the subscription (i.e., the same way it would behave if the remote party did not support SIP events at all).
Если подписчик желает подписаться на ресурс на том же устройстве, что и установленный диалог, а удалённый контакт не является GRUU, он МОЖЕТ вернуться к поведению совместного использования диалога. В качестве альтернативы он МОЖЕТ считать удалённую сторону неспособной обслуживать подписку (т. е. вести себя так же, как если бы удалённая сторона вообще не поддерживала события SIP).
If a notifier receives a SUBSCRIBE request for a new subscription on an existing dialog, it MAY choose to implement dialog sharing behavior. Alternately, it may choose to fail the SUBSCRIBE request with a 403 (Forbidden) response. The error text of such 403 responses SHOULD indicate that dialog sharing is not supported.
Если уведомитель получает запрос SUBSCRIBE для новой подписки в существующем диалоге, он МОЖЕТ реализовать поведение совместного использования диалога. 4.6. CANCEL Requests for SUBSCRIBE and NOTIFY Transactions
4.6. Запросы CANCEL для транзакций SUBSCRIBE и NOTIFY
Neither SUBSCRIBE nor NOTIFY requests can be canceled. If a User Agent Server (UAS) receives a CANCEL request that matches a known SUBSCRIBE or NOTIFY transaction, it MUST respond to the CANCEL request, but otherwise ignore it. In particular, the CANCEL request MUST NOT affect processing of the SUBSCRIBE or NOTIFY request in any way.
Ни запросы SUBSCRIBE, ни запросы NOTIFY не могут быть отменены. Если сервер пользовательского агента (UAS) получает запрос CANCEL, соответствующий известной транзакции SUBSCRIBE или NOTIFY, он ДОЛЖЕН ответить на запрос CANCEL, но в остальном игнорировать его. В частности, запрос CANCEL НЕ ДОЛЖЕН никаким образом влиять на обработку запроса SUBSCRIBE или NOTIFY.
UACs SHOULD NOT send CANCEL requests for SUBSCRIBE or NOTIFY transactions.
UAC НЕ СЛЕДУЕТ отправлять запросы CANCEL для транзакций SUBSCRIBE или NOTIFY.
5. Event Packages
5. Пакеты событий
This section covers several issues that should be taken into consideration when event packages based on the SUBSCRIBE and NOTIFY methods are proposed.
В этом разделе рассматриваются несколько вопросов, которые следует учитывать при предложении пакетов событий, основанных на методах SUBSCRIBE и NOTIFY.
5.1. Appropriateness of Usage
5.1. Уместность применения
When designing an event package using the methods described in this document for event notification, it is important to consider: is SIP an appropriate mechanism for the problem set? Is SIP being selected because of some unique feature provided by the protocol (e.g., user mobility) or merely because "it can be done"? If you find yourself defining event packages for notifications related to, for example, network management or the temperature inside your car's engine, you may want to reconsider your selection of protocols.
При проектировании пакета событий с использованием описанных в настоящем документе методов уведомления о событиях важно учесть: является ли SIP подходящим механизмом для данного набора задач? Выбран ли SIP из-за некоторой уникальной особенности, предоставляемой протоколом (например, мобильности пользователя), или просто потому, что «это можно сделать»? Если вы обнаружите, что определяете пакеты событий для уведомлений, связанных, например, с управлением сетью или с температурой внутри двигателя вашего автомобиля, возможно, вам стоит пересмотреть выбор протоколов.
Those interested in extending the mechanism defined in this document are urged to follow the development of "Guidelines for Authors of SIP Extensions" [RFC4485] for further guidance regarding appropriate uses of SIP.
Тем, кто заинтересован в расширении механизма, определённого в настоящем документе, настоятельно рекомендуется следить за разработкой документа «Guidelines for Authors of SIP Extensions» [RFC4485] для получения дальнейших указаний относительно надлежащего применения SIP.
Further, it is expected that this mechanism is not to be used in applications where the frequency of reportable events is excessively rapid (e.g., more than about once per second). A SIP network is generally going to be provisioned for a reasonable signaling volume; sending a notification every time a user's GPS position changes by one hundredth of a second could easily overload such a network.
Кроме того, ожидается, что этот механизм не будет использоваться в приложениях, где частота подлежащих сообщению событий чрезмерно высока (например, более примерно одного раза в секунду). Сеть SIP, как правило, рассчитывается на разумный объём сигнализации; отправка уведомления каждый раз, когда GPS-позиция пользователя изменяется на сотую долю секунды, может легко перегрузить такую сеть.
5.2. Event Template-Packages
5.2. Шаблонные пакеты событий
Normal event packages define a set of state applied to a specific type of resource, such as user presence, call state, and messaging mailbox state.
Обычные пакеты событий определяют набор состояний, применяемый к конкретному типу ресурса, например присутствие пользователя, состояние вызова и состояние почтового ящика обмена сообщениями.
Event template-packages are a special type of package that define a set of state applied to other packages, such as statistics, access policy, and subscriber lists. Event template-packages may even be applied to other event template-packages.
Шаблонные пакеты событий -- это особый тип пакета, который определяет набор состояний, применяемый к другим пакетам, например статистика, политика доступа и списки подписчиков. Шаблонные пакеты событий могут применяться даже к другим шаблонным пакетам событий.
To extend the object-oriented analogy made earlier, event template- packages can be thought of as templatized C++ packages that must be applied to other packages to be useful.
Продолжая приведённую ранее аналогию с объектно-ориентированным подходом, шаблонные пакеты событий можно рассматривать как шаблонизированные пакеты C++, которые должны быть применены к другим пакетам, чтобы быть полезными.
The name of an event template-package as applied to a package is formed by appending a period followed by the event template-package name to the end of the package. For example, if a template-package called "winfo" were being applied to a package called "presence", the event token used in the "Event" header field would be "presence.winfo".
Имя шаблонного пакета событий в применении к пакету образуется путём добавления точки и имени шаблонного пакета событий в конец имени пакета. Например, если шаблонный пакет с именем «winfo» применяется к пакету с именем «presence», токен события в поле заголовка «Event» был бы «presence.winfo».
This scheme may be arbitrarily extended. For example, application of the "winfo" package to the "presence.winfo" state of a resource would be represented by the name "presence.winfo.winfo". It naturally follows from this syntax that the order in which templates are specified is significant. For example: consider a theoretical event template-package called "list". The event "presence.winfo.list" would be the application of the "list" template to "presence.winfo", which would presumably be a list of winfo state associated with presence. On the other hand, the event "presence.list.winfo" would represent the application of winfo to "presence.list", which would be represent the winfo state of a list of presence information.
Эта схема может быть произвольно расширена. Например, применение пакета «winfo» к состоянию «presence.winfo» ресурса было бы представлено именем «presence.winfo.winfo». Из этого синтаксиса естественно следует, что порядок указания шаблонов значим. Например: рассмотрим теоретический шаблонный пакет событий с именем «list». Событие «presence.winfo.list» было бы применением шаблона «list» к «presence.winfo», что, по-видимому, представляло бы собой список состояния winfo, связанного с присутствием. С другой стороны, событие «presence.list.winfo» представляло бы применение winfo к «presence.list», что представляло бы состояние winfo списка сведений о присутствии.
Event template-packages must be defined so that they can be applied to any arbitrary package. In other words, event template-packages cannot be specifically tied to one or a few "parent" packages in such a way that they will not work with other packages.
Шаблонные пакеты событий должны быть определены так, чтобы их можно было применять к любому произвольному пакету. Иными словами, шаблонные пакеты событий не могут быть специально привязаны к одному или нескольким «родительским» пакетам так, чтобы они не работали с другими пакетами.
5.3. Amount of State to Be Conveyed
5.3. Объём передаваемого состояния
When designing event packages, it is important to consider the type of information that will be conveyed during a notification.
При проектировании пакетов событий важно учитывать тип информации, которая будет передаваться в ходе уведомления.
A natural temptation is to convey merely the event (e.g., "a new voice message just arrived") without accompanying state (e.g., "7 total voice messages"). This complicates implementation of subscribing entities (since they have to maintain complete state for the entity to which they have subscribed), and also is particularly susceptible to synchronization problems.
Естественное искушение -- передавать лишь событие (например, «пришло новое голосовое сообщение») без сопутствующего состояния (например, «всего 7 голосовых сообщений»). Это усложняет реализацию подписывающихся объектов (поскольку им приходится поддерживать полное состояние объекта, на который они подписались), а также особенно подвержено проблемам синхронизации.
This problem has two possible solutions that event packages may choose to implement.
У этой проблемы есть два возможных решения, которые пакеты событий могут реализовать.
5.3.1. Complete State Information
5.3.1. Полные сведения о состоянии
In general, event packages need to be able to convey a well-defined and complete state, rather than just a stream of events. If it is not possible to describe complete system state for transmission in NOTIFY requests, then the problem set is not a good candidate for an event package.
В общем случае пакеты событий должны уметь передавать чётко определённое и полное состояние, а не просто поток событий. Если описать полное состояние системы для передачи в запросах NOTIFY невозможно, то данный набор задач не является хорошим кандидатом для пакета событий.
For packages that typically convey state information that is reasonably small (on the order of 1 KB or so), it is suggested that event packages are designed so as to send complete state information whenever an event occurs.
Для пакетов, которые обычно передают сведения о состоянии сравнительно небольшого объёма (порядка 1 КБ или около того), предлагается проектировать пакеты событий так, чтобы отправлять полные сведения о состоянии при каждом возникновении события.
In some circumstances, conveying the current state alone may be insufficient for a particular class of events. In these cases, the event packages should include complete state information along with the event that occurred. For example, conveying "no customer service representatives available" may not be as useful as conveying "no customer service representatives available; representative sip:46@cs.xyz.int just logged off".
В некоторых обстоятельствах передачи одного лишь текущего состояния может быть недостаточно для определённого класса событий. В таких случаях пакетам событий следует включать полные сведения о состоянии вместе с произошедшим событием. Например, передача сообщения «нет доступных представителей службы поддержки» может быть не столь полезной, как передача сообщения «нет доступных представителей службы поддержки; представитель sip:46@cs.xyz.int только что вышел из системы».
5.3.2. State Deltas
5.3.2. Разностные изменения состояния
In the case that the state information to be conveyed is large, the event package may choose to detail a scheme by which NOTIFY requests contain state deltas instead of complete state.
В случае когда передаваемые сведения о состоянии велики, пакет событий может пожелать описать схему, при которой запросы NOTIFY содержат разностные изменения состояния вместо полного состояния.
Such a scheme would work as follows: any NOTIFY request sent in immediate response to a SUBSCRIBE request contains full state information. NOTIFY requests sent because of a state change will contain only the state information that has changed; the subscriber will then merge this information into its current knowledge about the state of the resource.
Такая схема работала бы следующим образом: любой запрос NOTIFY, отправленный в непосредственном ответ на запрос SUBSCRIBE, содержит полные сведения о состоянии. Запросы NOTIFY, отправленные из-за изменения состояния, будут содержать только те сведения о состоянии, которые изменились; подписчик затем объединит эту информацию со своими текущими знаниями о состоянии ресурса.
Any event package that supports delta changes to states MUST include a version number that increases by exactly one for each NOTIFY transaction in a subscription. Note that the state version number appears in the body of the message, not in a SIP header field.
Любой пакет событий, поддерживающий разностные изменения состояний, ДОЛЖЕН включать номер версии, который увеличивается ровно на единицу для каждой транзакции NOTIFY в подписке. Обратите внимание, что номер версии состояния находится в теле сообщения, а не в поле заголовка SIP.
If a NOTIFY request arrives that has a version number that is incremented by more than one, the subscriber knows that a state delta has been missed; it ignores the NOTIFY request containing the state delta (except for the version number, which it retains to detect message loss), and re-sends a SUBSCRIBE request to force a NOTIFY request containing a complete state snapshot.
Если приходит запрос NOTIFY с номером версии, увеличенным более чем на единицу, подписчик знает, что разностное изменение состояния было пропущено; он игнорирует запрос NOTIFY, содержащий разностное изменение состояния (кроме номера версии, который он сохраняет для обнаружения потери сообщений), и повторно отправляет запрос SUBSCRIBE, чтобы вынудить отправить запрос NOTIFY с полным снимком состояния.
5.4. Event Package Responsibilities
5.4. Обязанности пакетов событий
Event packages are not required to reiterate any of the behavior described in this document, although they may choose to do so for clarity or emphasis. In general, though, such packages are expected to describe only the behavior that extends or modifies the behavior described in this document.
Пакеты событий не обязаны повторять какое-либо из описанных в настоящем документе поведений, хотя они могут пожелать сделать это для ясности или акцента. В целом, однако, ожидается, что такие пакеты будут описывать только поведение, которое расширяет или изменяет поведение, описанное в настоящем документе.
Note that any behavior designated with "SHOULD" or "MUST" in this document is not allowed to be weakened by extension documents; however, such documents may elect to strengthen "SHOULD" requirements to "MUST" requirements if required by their application.
Обратите внимание, что любое поведение, обозначенное в настоящем документе как «SHOULD» или «MUST», не может быть ослаблено документами-расширениями; однако такие документы могут усилить требования «SHOULD» до требований «MUST», если это требуется их приложением.
In addition to the normal sections expected in Standards Track RFCs and SIP extension documents, authors of event packages need to address each of the issues detailed in the following subsections. For clarity: well-formed event package definitions contain sections addressing each of these issues, ideally in the same order and with the same titles as these subsections.
Помимо обычных разделов, ожидаемых в RFC уровня Standards Track и в документах-расширениях SIP, авторам пакетов событий необходимо рассмотреть каждый из вопросов, подробно описанных в следующих подразделах. Для ясности: правильно составленные определения пакетов событий содержат разделы, посвящённые каждому из этих вопросов, в идеале в том же порядке и с теми же заголовками, что и эти подразделы.
5.4.1. Event Package Name
5.4.1. Имя пакета событий
This section, which MUST be present, defines the token name to be used to designate the event package. It MUST include the information that appears in the IANA registration of the token. For information on registering such types, see Section 7.
Этот раздел, который ДОЛЖЕН присутствовать, определяет имя токена, используемое для обозначения пакета событий. Он ДОЛЖЕН включать информацию, которая фигурирует в регистрации токена в IANA. Сведения о регистрации таких типов см. в разделе 7.
5.4.2. Event Package Parameters
5.4.2. Параметры пакета событий
If parameters are to be used on the "Event" header field to modify the behavior of the event package, the syntax and semantics of such header fields MUST be clearly defined.
Если параметры должны использоваться в поле заголовка «Event» для изменения поведения пакета событий, синтаксис и семантика таких полей заголовков ДОЛЖНЫ быть чётко определены.
Any "Event" header field parameters defined by an event package MUST be registered in the "Header Field Parameters and Parameter Values" registry defined by [RFC3968]. An "Event" header field parameter, once registered in conjunction with an event package, MUST NOT be reused with any other event package. Non-event-package specifications MAY define "Event" header field parameters that apply across all event packages (with emphasis on "all", as opposed to "several"), such as the "id" parameter defined in this document. The restriction of a parameter to use with a single event package only applies to parameters that are defined in conjunction with an event package.
Любые параметры поля заголовка «Event», определённые пакетом событий, ДОЛЖНЫ быть зарегистрированы в реестре «Header Field Parameters and Parameter Values», определённом в [RFC3968]. Параметр поля заголовка «Event», однажды зарегистрированный в связи с пакетом событий, НЕ ДОЛЖЕН повторно использоваться с каким-либо другим пакетом событий. Спецификации, не относящиеся к пакетам событий, МОГУТ определять параметры поля заголовка «Event», применимые ко всем пакетам событий (с ударением на «всем», в отличие от «нескольких»), такие как параметр «id», определённый в настоящем документе. Ограничение на использование параметра только с одним пакетом событий относится лишь к параметрам, определённым в связи с пакетом событий.
5.4.3. SUBSCRIBE Request Bodies
5.4.3. Тела запросов SUBSCRIBE
It is expected that most, but not all, event packages will define syntax and semantics for SUBSCRIBE request bodies; these bodies will typically modify, expand, filter, throttle, and/or set thresholds for the class of events being requested. Designers of event packages are strongly encouraged to reuse existing media types for message bodies where practical. See [RFC4288] for information on media type specification and registration.
Ожидается, что большинство, но не все, пакетов событий определят синтаксис и семантику для тел запросов SUBSCRIBE; эти тела обычно будут изменять, расширять, фильтровать, ограничивать частоту и (или) устанавливать пороги для класса запрашиваемых событий. Разработчикам пакетов событий настоятельно рекомендуется по возможности повторно использовать существующие типы носителей для тел сообщений. Сведения о спецификации и регистрации типов носителей см. в [RFC4288].
This mandatory section of an event package defines what type or types of event bodies are expected in SUBSCRIBE requests (or specify that no event bodies are expected). It should point to detailed definitions of syntax and semantics for all referenced body types.
Этот обязательный раздел пакета событий определяет, какой тип или типы тел событий ожидаются в запросах SUBSCRIBE (или указывает, что тела событий не ожидаются). Он должен ссылаться на подробные определения синтаксиса и семантики для всех упоминаемых типов тел.
5.4.4. Subscription Duration
5.4.4. Длительность подписки
It is RECOMMENDED that event packages give a suggested range of times considered reasonable for the duration of a subscription. Such packages MUST also define a default "Expires" value to be used if none is specified.
РЕКОМЕНДУЕТСЯ, чтобы пакеты событий давали предлагаемый диапазон времён, считающихся разумными для длительности подписки. Такие пакеты ДОЛЖНЫ также определять значение «Expires» по умолчанию, используемое, если ни одно не указано.
5.4.5. NOTIFY Request Bodies
5.4.5. Тела запросов NOTIFY
The NOTIFY request body is used to report state on the resource being monitored. Each package MUST define what type or types of event bodies are expected in NOTIFY requests. Such packages MUST specify or cite detailed specifications for the syntax and semantics associated with such event bodies.
Тело запроса NOTIFY используется для сообщения о состоянии ресурса, за которым ведётся наблюдение. Каждый пакет ДОЛЖЕН определять, какой тип или типы тел событий ожидаются в запросах NOTIFY. Такие пакеты ДОЛЖНЫ указывать или цитировать подробные спецификации синтаксиса и семантики, связанных с такими телами событий.
Event packages also MUST define which media type is to be assumed if none are specified in the "Accept" header field of the SUBSCRIBE request.
Пакеты событий также ДОЛЖНЫ определять, какой тип носителя следует подразумевать, если ни один не указан в поле заголовка «Accept» запроса SUBSCRIBE.
5.4.6. Notifier Processing of SUBSCRIBE Requests
5.4.6. Обработка запросов SUBSCRIBE уведомителем
This section describes the processing to be performed by the notifier upon receipt of a SUBSCRIBE request. Such a section is required.
В этом разделе описывается обработка, которую должен выполнить уведомитель при получении запроса SUBSCRIBE. Такой раздел обязателен.
Information in this section includes details of how to authenticate subscribers and authorization issues for the package.
Информация в этом разделе включает подробности о том, как аутентифицировать подписчиков, и вопросы авторизации для данного пакета.
5.4.7. Notifier generation of NOTIFY requests
5.4.7. Формирование запросов NOTIFY уведомителем
This section of an event package describes the process by which the notifier generates and sends a NOTIFY request. This includes detailed information about what events cause a NOTIFY request to be sent, how to compute the state information in the NOTIFY, how to generate neutral or fake state information to hide authorization delays and decisions from users, and whether state information is complete or what the deltas are for notifications; see Section 5.3. Such a section is required.
Этот раздел пакета событий описывает процесс, с помощью которого уведомитель формирует и отправляет запрос NOTIFY. Это включает подробные сведения о том, какие события вызывают отправку запроса NOTIFY, как вычислять сведения о состоянии в NOTIFY, как формировать нейтральные или фиктивные сведения о состоянии, чтобы скрыть от пользователей задержки и решения по авторизации, а также является ли информация о состоянии полной или каковы разностные изменения для уведомлений; см. раздел 5.3. Такой раздел обязателен.
This section may optionally describe the behavior used to process the subsequent response.
Этот раздел может необязательно описывать поведение, используемое для обработки последующего ответа.
5.4.8. Subscriber Processing of NOTIFY Requests
5.4.8. Обработка запросов NOTIFY подписчиком
This section of an event package describes the process followed by the subscriber upon receipt of a NOTIFY request, including any logic required to form a coherent resource state (if applicable).
Этот раздел пакета событий описывает процесс, которого придерживается подписчик при получении запроса NOTIFY, включая любую логику, необходимую для формирования согласованного состояния ресурса (если применимо).
5.4.9. Handling of Forked Requests
5.4.9. Обработка разветвлённых запросов
Each event package MUST specify whether forked SUBSCRIBE requests are allowed to install multiple subscriptions.
Каждый пакет событий ДОЛЖЕН указать, разрешено ли разветвлённым запросам SUBSCRIBE устанавливать несколько подписок.
If such behavior is not allowed, the first potential dialog- establishing message will create a dialog. All subsequent NOTIFY requests that correspond to the SUBSCRIBE request (i.e., have matching "To", "From", "Call-ID", and "Event" header fields, as well as "From" header field "tag" parameter and "Event" header field "id" parameter) but that do not match the dialog would be rejected with a 481 response. Note that the 200-class response to the SUBSCRIBE request can arrive after a matching NOTIFY request has been received; such responses might not correlate to the same dialog established by the NOTIFY request. Except as required to complete the SUBSCRIBE transaction, such non-matching 200-class responses are ignored.
Если такое поведение не разрешено, первое потенциальное сообщение, устанавливающее диалог, создаст диалог. Все последующие запросы NOTIFY, которые соответствуют запросу SUBSCRIBE (т. е. имеют совпадающие поля заголовков «To», «From», «Call-ID» и «Event», а также параметр «tag» поля заголовка «From» и параметр «id» поля заголовка «Event»), но не соответствуют диалогу, будут отклонены ответом 481. Обратите внимание, что ответ класса 200 на запрос SUBSCRIBE может прийти после получения соответствующего запроса NOTIFY; такие ответы могут не соотноситься с тем же диалогом, установленным запросом NOTIFY. За исключением того, что требуется для завершения транзакции SUBSCRIBE, такие несоответствующие ответы класса 200 игнорируются.
If installing of multiple subscriptions by way of a single forked SUBSCRIBE request is allowed, the subscriber establishes a new dialog towards each notifier by returning a 200-class response to each NOTIFY request. Each dialog is then handled as its own entity and is refreshed independently of the other dialogs.
Если установление нескольких подписок посредством одного разветвлённого запроса SUBSCRIBE разрешено, подписчик устанавливает новый диалог с каждым уведомителем, возвращая ответ класса 200 на каждый запрос NOTIFY. Затем каждый диалог обрабатывается как отдельная сущность и обновляется независимо от других диалогов.
In the case that multiple subscriptions are allowed, the event package MUST specify whether merging of the notifications to form a single state is required, and how such merging is to be performed. Note that it is possible that some event packages may be defined in such a way that each dialog is tied to a mutually exclusive state that is unaffected by the other dialogs; this MUST be clearly stated if it is the case.
В случае когда несколько подписок разрешены, пакет событий ДОЛЖЕН указать, требуется ли объединение уведомлений для формирования единого состояния и как такое объединение должно выполняться. Обратите внимание, что некоторые пакеты событий могут быть определены так, что каждый диалог привязан к взаимоисключающему состоянию, на которое другие диалоги не влияют; это ДОЛЖНО быть чётко указано, если это так.
5.4.10. Rate of Notifications
5.4.10. Частота уведомлений
Each event package is expected to define a requirement ("SHOULD" or "MUST" strength) that defines an absolute maximum on the rate at which notifications are allowed to be generated by a single notifier.
Ожидается, что каждый пакет событий определит требование (уровня «SHOULD» или «MUST»), задающее абсолютный максимум частоты, с которой одному уведомителю разрешено формировать уведомления.
Each package MAY further define a throttle mechanism that allows subscribers to further limit the rate of notification.
Каждый пакет МОЖЕТ дополнительно определить механизм ограничения частоты, позволяющий подписчикам дополнительно ограничивать частоту уведомлений.
5.4.11. State Aggregation
5.4.11. Агрегирование состояния
Many event packages inherently work by collecting information about a resource from a number of other sources -- either through the use of PUBLISH [RFC3903], by subscribing to state information, or through other state-gathering mechanisms.
Многие пакеты событий по своей природе работают путём сбора информации о ресурсе из ряда других источников -- либо с помощью PUBLISH [RFC3903], либо путём подписки на сведения о состоянии, либо через иные механизмы сбора состояния.
Event packages that involve retrieval of state information for a single resource from more than one source need to consider how notifiers aggregate information into a single, coherent state. Such packages MUST specify how notifiers aggregate information and how they provide authentication and authorization.
Пакеты событий, которые включают получение сведений о состоянии для одного ресурса из более чем одного источника, должны учитывать, как уведомители агрегируют информацию в единое согласованное состояние. Такие пакеты ДОЛЖНЫ указать, как уведомители агрегируют информацию и как они обеспечивают аутентификацию и авторизацию.

5.4.12. Примеры
Event packages SHOULD include several demonstrative message flow diagrams paired with several typical, syntactically correct, and complete messages.
Пакетам событий СЛЕДУЕТ включать несколько наглядных диаграмм потоков сообщений в паре с несколькими типичными, синтаксически правильными и полными сообщениями.

РЕКОМЕНДУЕТСЯ, чтобы документы, описывающие пакеты событий, ясно указывали, что такие примеры являются информативными, а не нормативными, с указанием разработчикам обращаться к основному тексту документа за точными сведениями о протоколе.
5.4.13. Use of URIs to Retrieve State
5.4.13. Использование URI для получения состояния
Some types of event packages may define state information that is potentially too large to reasonably send in a SIP message. To alleviate this problem, event packages may include the ability to convey a URI instead of state information; this URI will then be used to retrieve the actual state information.
Некоторые типы пакетов событий могут определять сведения о состоянии, которые потенциально слишком велики, чтобы разумно отправлять их в сообщении SIP. Чтобы облегчить эту проблему, пакеты событий могут включать возможность передавать URI вместо сведений о состоянии; этот URI затем будет использоваться для получения фактических сведений о состоянии.
[RFC4483] defines a mechanism that can be used by event packages to convey information in such a fashion.
[RFC4483] определяет механизм, который пакеты событий могут использовать для передачи информации таким образом.
6. Security Considerations
6. Вопросы безопасности
6.1. Access Control
6.1. Управление доступом
The ability to accept subscriptions should be under the direct control of the notifier's user, since many types of events may be considered private. Similarly, the notifier should have the ability to selectively reject subscriptions based on the subscriber identity (based on access control lists), using standard SIP authentication mechanisms. The methods for creation and distribution of such access control lists are outside the scope of this document.
Возможность принимать подписки должна находиться под непосредственным контролем пользователя уведомителя, поскольку многие типы событий могут считаться частными. Аналогично, уведомитель должен иметь возможность избирательно отклонять подписки на основании личности подписчика (на основании списков управления доступом), используя стандартные механизмы аутентификации SIP. Способы создания и распространения таких списков управления доступом выходят за рамки настоящего документа.
6.2. Notifier Privacy Mechanism
6.2. Механизм конфиденциальности уведомителя
The mere act of returning certain 400- and 600-class responses to SUBSCRIBE requests may, under certain circumstances, create privacy concerns by revealing sensitive policy information. In these cases, the notifier SHOULD always return a 200 (OK) response. While the subsequent NOTIFY request may not convey true state, it MUST appear to contain a potentially correct piece of data from the point of view of the subscriber, indistinguishable from a valid response. Information about whether a user is authorized to subscribe to the requested state is never conveyed back to the original user under these circumstances. Individual packages and their related documents for which such a mode of operation makes sense can further describe how and why to generate such potentially correct data. For example, such a mode of operation is mandated by [RFC2779] for user presence information.
Сам по себе возврат определённых ответов классов 400 и 600 на запросы SUBSCRIBE может при определённых обстоятельствах создавать проблемы конфиденциальности, раскрывая чувствительную информацию о политике. В таких случаях уведомителю СЛЕДУЕТ всегда возвращать ответ 200 (OK). Хотя последующий запрос NOTIFY может не передавать истинное состояние, он ДОЛЖЕН с точки зрения подписчика выглядеть содержащим потенциально корректные данные, неотличимые от действительного ответа. Сведения о том, авторизован ли пользователь подписываться на запрошенное состояние, никогда не передаются обратно исходному пользователю в этих обстоятельствах. Отдельные пакеты и связанные с ними документы, для которых такой режим работы имеет смысл, могут дополнительно описывать, как и почему формировать такие потенциально корректные данные. Например, такой режим работы предписан в [RFC2779] для сведений о присутствии пользователя.
6.3. Denial-of-Service Attacks
6.3. Атаки типа «отказ в обслуживании»
The current model (one SUBSCRIBE request triggers a SUBSCRIBE response and one or more NOTIFY requests) is a classic setup for an amplifier node to be used in a smurf attack [CERT1998a].
Текущая модель (один запрос SUBSCRIBE вызывает ответ на SUBSCRIBE и один или несколько запросов NOTIFY) является классической схемой для использования узла-усилителя в smurf-атаке [CERT1998a].
Also, the creation of state upon receipt of a SUBSCRIBE request can be used by attackers to consume resources on a victim's machine, rendering it unusable.
Кроме того, создание состояния при получении запроса SUBSCRIBE может использоваться злоумышленниками для расходования ресурсов машины жертвы, делая её непригодной для использования.
To reduce the chances of such an attack, implementations of notifiers SHOULD require authentication. Authentication issues are discussed in [RFC3261].
Чтобы уменьшить вероятность такой атаки, реализациям уведомителей СЛЕДУЕТ требовать аутентификацию. Вопросы аутентификации обсуждаются в [RFC3261].
6.4. Replay Attacks
6.4. Атаки повторного воспроизведения
Replaying of either SUBSCRIBE or NOTIFY requests can have detrimental effects.
Повторное воспроизведение запросов SUBSCRIBE или NOTIFY может иметь пагубные последствия.
In the case of SUBSCRIBE requests, an attacker may be able to install any arbitrary subscription that it witnessed being installed at some point in the past. Replaying of NOTIFY requests may be used to spoof old state information (although a good versioning mechanism in the body of the NOTIFY requests may help mitigate such an attack). Note that the prohibition on sending NOTIFY requests to nodes that have not subscribed to an event also aids in mitigating the effects of such an attack.
В случае запросов SUBSCRIBE злоумышленник может оказаться способен установить любую произвольную подписку, которую он когда-либо наблюдал при установлении. Повторное воспроизведение запросов NOTIFY может использоваться для подмены устаревших сведений о состоянии (хотя хороший механизм версионирования в теле запросов NOTIFY может помочь смягчить такую атаку). Обратите внимание, что запрет на отправку запросов NOTIFY узлам, не подписанным на событие, также помогает смягчить последствия такой атаки.
To prevent such attacks, implementations SHOULD require authentication with anti-replay protection. Authentication issues are discussed in [RFC3261].
Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ требовать аутентификацию с защитой от повторного воспроизведения. Вопросы аутентификации обсуждаются в [RFC3261].
6.5. Man-in-the-Middle Attacks
6.5. Атаки «человек посередине»
Even with authentication, man-in-the-middle attacks using SUBSCRIBE requests may be used to install arbitrary subscriptions, hijack existing subscriptions, terminate outstanding subscriptions, or modify the resource to which a subscription is being made. To prevent such attacks, implementations SHOULD provide integrity protection across "Contact", "Route", "Expires", "Event", and "To" header fields (at a minimum) of SUBSCRIBE requests. If SUBSCRIBE request bodies are used to define further information about the state of the call, they SHOULD be included in the integrity protection scheme.
Даже при наличии аутентификации атаки типа «человек посередине» с использованием запросов SUBSCRIBE могут применяться для установления произвольных подписок, перехвата существующих подписок, завершения действующих подписок или изменения ресурса, на который оформляется подписка. Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ обеспечивать защиту целостности (как минимум) полей заголовков «Contact», «Route», «Expires», «Event» и «To» запросов SUBSCRIBE. Если тела запросов SUBSCRIBE используются для определения дополнительной информации о состоянии вызова, они ДОЛЖНЫ быть включены в схему защиты целостности.
Man-in-the-middle attacks may also attempt to use NOTIFY requests to spoof arbitrary state information and/or terminate outstanding subscriptions. To prevent such attacks, implementations SHOULD provide integrity protection across the "Call-ID", "CSeq", and "Subscription-State" header fields and the bodies of NOTIFY requests.
Атаки типа «человек посередине» могут также пытаться использовать запросы NOTIFY для подмены произвольных сведений о состоянии и (или) завершения действующих подписок. Чтобы предотвратить такие атаки, реализациям СЛЕДУЕТ обеспечивать защиту целостности полей заголовков «Call-ID», «CSeq» и «Subscription-State» и тел запросов NOTIFY.
Integrity protection of message header fields and bodies is discussed in [RFC3261].
Защита целостности полей заголовков и тел сообщений обсуждается в [RFC3261].
6.6. Confidentiality
6.6. Конфиденциальность
The state information contained in a NOTIFY request has the potential to contain sensitive information. Implementations MAY encrypt such information to ensure confidentiality.
Сведения о состоянии, содержащиеся в запросе NOTIFY, могут содержать чувствительную информацию. Реализации МОГУТ шифровать такую информацию для обеспечения конфиденциальности.
While less likely, it is also possible that the information contained in a SUBSCRIBE request contains information that users might not want to have revealed. Implementations MAY encrypt such information to ensure confidentiality.
Хотя это менее вероятно, также возможно, что информация, содержащаяся в запросе SUBSCRIBE, включает сведения, которые пользователи, возможно, не хотели бы раскрывать. Реализации МОГУТ шифровать такую информацию для обеспечения конфиденциальности.
To allow the remote party to hide information it considers sensitive, all implementations SHOULD be able to handle encrypted SUBSCRIBE and NOTIFY requests.
Чтобы позволить удалённой стороне скрывать информацию, которую она считает чувствительной, все реализации ДОЛЖНЫ уметь обрабатывать зашифрованные запросы SUBSCRIBE и NOTIFY.
The mechanisms for providing confidentiality are detailed in [RFC3261].
Механизмы обеспечения конфиденциальности подробно описаны в [RFC3261].

8.2.1. "Event" Header Field
8.2.1. Поле заголовка «Event»
Event is added to the definition of the element "message-header field" in the SIP message grammar.
Event добавляется в определение элемента «message-header field» грамматики сообщений SIP.
For the purposes of matching NOTIFY requests with SUBSCRIBE requests, the event-type portion of the "Event" header field is compared byte by byte, and the "id" parameter token (if present) is compared byte by byte. An "Event" header field containing an "id" parameter never matches an "Event" header field without an "id" parameter. No other parameters are considered when performing a comparison. SUBSCRIBE responses are matched per the transaction handling rules in [RFC3261]. Note that the foregoing text means that "Event: foo; id=1234" would match "Event: foo; param=abcd; id=1234", but not "Event: foo" ("id" does not match) or "Event: Foo; id=1234" ("Event" portion does not match).
Для целей сопоставления запросов NOTIFY с запросами SUBSCRIBE часть поля заголовка «Event», обозначающая тип события, сравнивается побайтно, а токен параметра «id» (если он присутствует) сравнивается побайтно. Поле заголовка «Event», содержащее параметр «id», никогда не совпадает с полем заголовка «Event» без параметра «id». Никакие другие параметры при сравнении не учитываются. Ответы на SUBSCRIBE сопоставляются согласно правилам обработки транзакций в [RFC3261]. Обратите внимание, что из сказанного выше следует: «Event: foo; id=1234» совпало бы с «Event: foo; param=abcd; id=1234», но не с «Event: foo» (параметр «id» не совпадает) и не с «Event: Foo; id=1234» (часть «Event» не совпадает).
This document does not define values for event-types. These values will be defined by individual event packages and MUST be registered with the IANA.
Настоящий документ не определяет значений для типов событий. Эти значения будут определяться отдельными пакетами событий и ДОЛЖНЫ быть зарегистрированы в IANA.
There MUST be exactly one event type listed per "Event" header field. Multiple events per message are disallowed.
В каждом поле заголовка «Event» ДОЛЖЕН быть указан ровно один тип события. Несколько событий в одном сообщении не допускаются.
The "Event" header field is defined only for use in SUBSCRIBE and NOTIFY requests and other requests whose definition explicitly calls for its use. It MUST NOT appear in any other SIP requests and MUST NOT appear in responses.
Поле заголовка «Event» определено только для использования в запросах SUBSCRIBE и NOTIFY и в других запросах, определение которых явно требует его использования. Оно НЕ ДОЛЖНО присутствовать в каких-либо иных запросах SIP и НЕ ДОЛЖНО присутствовать в ответах.
8.2.2. "Allow-Events" Header Field
8.2.2. Поле заголовка «Allow-Events»
"Allow-Events" is added to the definition of the element "general- header field" in the SIP message grammar. Its usage is described in Section 4.4.4.
«Allow-Events» добавляется в определение элемента «general-header field» грамматики сообщений SIP. Его использование описано в разделе 4.4.4.
User agents MAY include the "Allow-Events" header field in any request or response, as long as its contents comply with the behavior described in Section 4.4.4.
Пользовательские агенты МОГУТ включать поле заголовка «Allow-Events» в любой запрос или ответ, если только его содержимое соответствует поведению, описанному в разделе 4.4.4.
8.2.3. "Subscription-State" Header Field
8.2.3. Поле заголовка «Subscription-State»
"Subscription-State" is added to the definition of the element "request-header" field in the SIP message grammar. Its usage is described in Section 4.1.3. "Subscription-State" header fields are defined for use in NOTIFY requests only. They MUST NOT appear in other SIP requests or responses.
«Subscription-State» добавляется в определение элемента «request-header» грамматики сообщений SIP. Его использование описано в разделе 4.1.3. Поля заголовка «Subscription-State» определены для использования только в запросах NOTIFY. Они НЕ ДОЛЖНЫ присутствовать в других запросах или ответах SIP.
8.3. New Response Codes
8.3. Новые коды ответов
8.3.1. 202 (Accepted) Response Code
8.3.1. Код ответа 202 (Accepted)
For historical purposes, the 202 (Accepted) response code is added to the "Success" header field definition.
В исторических целях код ответа 202 (Accepted) добавляется в определение поля заголовка «Success».
This document does not specify the use of the 202 response code in conjunction with the SUBSCRIBE or NOTIFY methods. Previous versions of the SIP Events Framework assigned specific meaning to the 202 response code. Due to response handling in forking cases, any 202 response to a SUBSCRIBE request may be absorbed by a proxy, and thus it can never be guaranteed to be received by the UAC. Furthermore, there is no actual processing difference for a 202 as compared to a 200; a NOTIFY request is sent after the subscription is processed, and it conveys the correct state. SIP interoperability tests found that implementations were handling 202 differently from 200, leading to incompatibilities. Therefore, the 202 response is being deprecated to make it clear there is no such difference and 202 should not be handled differently than 200.
Настоящий документ не определяет использование кода ответа 202 вместе с методами SUBSCRIBE или NOTIFY. Предыдущие версии системы событий SIP придавали коду ответа 202 конкретное значение. Из-за обработки ответов в случаях разветвления любой ответ 202 на запрос SUBSCRIBE может быть поглощён прокси, и поэтому никогда нельзя гарантировать, что он будет получен UAC. Более того, для 202 по сравнению с 200 нет никакой фактической разницы в обработке; запрос NOTIFY отправляется после обработки подписки и передаёт правильное состояние. Испытания совместимости SIP показали, что реализации обрабатывали 202 иначе, чем 200, что приводило к несовместимостям. Поэтому код ответа 202 объявляется устаревшим, чтобы стало ясно: такой разницы нет и 202 не следует обрабатывать иначе, чем 200.
Implementations conformant with the current specification MUST treat an incoming 202 response as identical to a 200 response and MUST NOT generate 202 response codes to SUBSCRIBE or NOTIFY requests.
Реализации, соответствующие настоящей спецификации, ДОЛЖНЫ обрабатывать входящий ответ 202 так же, как ответ 200, и НЕ ДОЛЖНЫ формировать коды ответа 202 на запросы SUBSCRIBE или NOTIFY.
This document also updates [RFC4660], which reiterates the 202-based behavior in several places. Implementations compliant with the present document MUST NOT send a 202 response to a SUBSCRIBE request and will send an alternate success response (such as 200) in its stead.
Настоящий документ также обновляет [RFC4660], который в нескольких местах повторяет поведение, основанное на 202. Реализации, соответствующие настоящему документу, НЕ ДОЛЖНЫ отправлять ответ 202 на запрос SUBSCRIBE и вместо него будут отправлять альтернативный ответ об успехе (например, 200).
8.3.2. 489 (Bad Event) Response Code
8.3.2. Код ответа 489 (Bad Event)
The 489 event response is added to the "Client-Error" header field definition. 489 (Bad Event) is used to indicate that the server did not understand the event package specified in a "Event" header field.
Ответ на событие 489 добавляется в определение поля заголовка «Client-Error». 489 (Bad Event) используется для указания, что сервер не понял пакет событий, указанный в поле заголовка «Event».

B.26. Remove "State Agent" Terminology
B.26. Удаление терминологии «State Agent»
As originally planned, we anticipated a fairly large number of event packages that would move back and forth between end-user devices and servers in the network. In practice, this has ended up not being the case. Certain events, like dialog state, are inherently hosted at end-user devices; others, like presence, are almost always hosted in the network (due to issues like composition, and the ability to deliver information when user devices are offline). Further, the concept of State Agents is the most misunderstood by event package authors. In my expert review of event packages, I have yet to find one that got the concept of State Agents completely correct -- and most of them start out with the concept being 100% backwards from the way RFC 3265 described it.
Как и планировалось изначально, мы предполагали довольно большое число пакетов событий, которые будут перемещаться туда и обратно между оконечными устройствами пользователей и серверами в сети. На практике оказалось, что это не так. Некоторые события, например состояние диалога, по своей природе размещаются на оконечных устройствах пользователей; другие, например присутствие, почти всегда размещаются в сети (из-за таких вопросов, как композиция, и возможности доставлять информацию, когда устройства пользователей находятся офлайн). Кроме того, понятие State Agent понимается авторами пакетов событий хуже всего. В ходе моего экспертного обзора пакетов событий я ещё не нашёл ни одного, где понятие State Agent было бы полностью правильным, -- и большинство из них изначально трактуют это понятие на 100 % наоборот по сравнению с тем, как его описал RFC 3265.
Rather than remove the ability to perform the actions previously attributed to the widely misunderstood term "State Agent", we have simply eliminated this term. Instead, we talk about the behaviors required to create state agents (state aggregation, subscription notification) without defining a formal term to describe the servers that exhibit these behaviors. In effect, this is an editorial change to make life easier for event package authors; the actual protocol does not change as a result.
Вместо того чтобы убирать возможность выполнять действия, ранее приписывавшиеся широко непонятому термину «State Agent», мы просто устранили этот термин. Вместо этого мы говорим о поведениях, необходимых для создания агентов состояния (агрегирование состояния, уведомление о подписке), не определяя формальный термин для описания серверов, демонстрирующих эти поведения. Фактически это редакционное изменение, призванное облегчить жизнь авторам пакетов событий; сам протокол в результате не меняется.
The definition of "State Agent" has been removed from Section 2. Section 4.4.2 has been retooled to discuss migration of subscription in general, without calling out the specific example of state agents. Section 5.4.11 has been focused on state aggregation in particular, instead of state aggregation as an aspect of state agents.
Определение «State Agent» удалено из раздела 2. Раздел 4.4.2 переработан так, чтобы обсуждать миграцию подписки в целом, не выделяя конкретный пример агентов состояния. Раздел 5.4.11 сосредоточен именно на агрегировании состояния, а не на агрегировании состояния как аспекте агентов состояния.
