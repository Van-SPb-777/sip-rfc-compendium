Abstract
Аннотация
ISO/IEC 10646-1 defines a large character set called the Universal Character Set (UCS) which encompasses most of the world's writing systems. The originally proposed encodings of the UCS, however, were not compatible with many current applications and protocols, and this has led to the development of UTF-8, the object of this memo. UTF-8 has the characteristic of preserving the full US-ASCII range, providing compatibility with file systems, parsers and other software that rely on US-ASCII values but are transparent to other values. This memo obsoletes and replaces RFC 2279.
ISO/IEC 10646-1 определяет большой набор символов, называемый Универсальным набором символов (Universal Character Set, UCS), который охватывает большинство систем письменности мира. Однако первоначально предложенные кодировки UCS не были совместимы со многими существующими приложениями и протоколами, что привело к разработке UTF-8 — предмета этого меморандума. UTF-8 обладает свойством сохранять полный диапазон US-ASCII, обеспечивая совместимость с файловыми системами, анализаторами и другим программным обеспечением, которое полагается на значения US-ASCII, но прозрачно для других значений. Настоящий меморандум устаревает и заменяет RFC 2279.
1. Introduction
1. Введение
ISO/IEC 10646 [ISO.10646] defines a large character set called the Universal Character Set (UCS), which encompasses most of the world's writing systems. The same set of characters is defined by the Unicode standard [UNICODE], which further defines additional character properties and other application details of great interest to implementers. Up to the present time, changes in Unicode and amendments and additions to ISO/IEC 10646 have tracked each other, so that the character repertoires and code point assignments have remained in sync. The relevant standardization committees have committed to maintain this very useful synchronism.
ISO/IEC 10646 [ISO.10646] определяет большой набор символов, называемый Универсальным набором символов (UCS), который охватывает большинство систем письменности мира. Тот же набор символов определён стандартом Unicode [UNICODE], который дополнительно задаёт свойства символов и другие детали применения, представляющие большой интерес для разработчиков. До настоящего времени изменения в Unicode и поправки и дополнения к ISO/IEC 10646 шли параллельно, так что репертуары символов и назначения кодовых точек оставались согласованными. Соответствующие комитеты по стандартизации обязались поддерживать этот весьма полезный синхронизм.
ISO/IEC 10646 and Unicode define several encoding forms of their common repertoire: UTF-8, UCS-2, UTF-16, UCS-4 and UTF-32. In an encoding form, each character is represented as one or more encoding units. All standard UCS encoding forms except UTF-8 have an encoding unit larger than one octet, making them hard to use in many current applications and protocols that assume 8 or even 7 bit characters.
ISO/IEC 10646 и Unicode определяют несколько форм кодирования своего общего репертуара: UTF-8, UCS-2, UTF-16, UCS-4 и UTF-32. В форме кодирования каждый символ представляется одной или несколькими единицами кодирования. Все стандартные формы кодирования UCS, кроме UTF-8, имеют единицу кодирования размером больше одного октета, что затрудняет их использование во многих существующих приложениях и протоколах, которые рассчитывают на 8-битные или даже 7-битные символы.
UTF-8, the object of this memo, has a one-octet encoding unit. It uses all bits of an octet, but has the quality of preserving the full US-ASCII [US-ASCII] range: US-ASCII characters are encoded in one octet having the normal US-ASCII value, and any octet with such a value can only stand for a US-ASCII character, and nothing else.
UTF-8, предмет этого меморандума, имеет единицу кодирования в один октет. Он использует все биты октета, но обладает свойством сохранять полный диапазон US-ASCII [US-ASCII]: символы US-ASCII кодируются одним октетом с обычным значением US-ASCII, и любой октет с таким значением может обозначать только символ US-ASCII и ничего больше.
UTF-8 encodes UCS characters as a varying number of octets, where the number of octets, and the value of each, depend on the integer value assigned to the character in ISO/IEC 10646 (the character number, a.k.a. code position, code point or Unicode scalar value). This encoding form has the following characteristics (all values are in hexadecimal):
UTF-8 кодирует символы UCS переменным числом октетов, причём число октетов и значение каждого из них зависят от целочисленного значения, назначенного символу в ISO/IEC 10646 (номера символа, он же кодовая позиция, кодовая точка или скалярное значение Unicode). Эта форма кодирования обладает следующими характеристиками (все значения в шестнадцатеричной записи):
o Character numbers from U+0000 to U+007F (US-ASCII repertoire) correspond to octets 00 to 7F (7 bit US-ASCII values). A direct consequence is that a plain ASCII string is also a valid UTF-8 string.
o Номера символов от U+0000 до U+007F (репертуар US-ASCII) соответствуют октетам от 00 до 7F (7-битные значения US-ASCII). Прямое следствие состоит в том, что обычная строка ASCII также является допустимой строкой UTF-8.
o US-ASCII octet values do not appear otherwise in a UTF-8 encoded character stream. This provides compatibility with file systems or other software (e.g., the printf() function in C libraries) that parse based on US-ASCII values but are transparent to other values.
o Значения октетов US-ASCII больше нигде не встречаются в потоке символов, закодированном в UTF-8. Это обеспечивает совместимость с файловыми системами и другим программным обеспечением (например, с функцией printf() в библиотеках C), которое выполняет разбор на основе значений US-ASCII, но прозрачно для других значений.
o Round-trip conversion is easy between UTF-8 and other encoding forms.
o Круговое преобразование между UTF-8 и другими формами кодирования выполняется легко.
o The first octet of a multi-octet sequence indicates the number of octets in the sequence.
o Первый октет многооктетной последовательности указывает число октетов в последовательности.
o The octet values C0, C1, F5 to FF never appear.
o Значения октетов C0, C1, F5–FF никогда не встречаются.
o Character boundaries are easily found from anywhere in an octet stream.
o Границы символов легко находятся из любого места в октетном потоке.
o The byte-value lexicographic sorting order of UTF-8 strings is the same as if ordered by character numbers. Of course this is of limited interest since a sort order based on character numbers is almost never culturally valid.
o Порядок лексикографической сортировки строк UTF-8 по байтовым значениям совпадает с порядком по номерам символов. Разумеется, это представляет ограниченный интерес, поскольку порядок сортировки, основанный на номерах символов, почти никогда не является культурно корректным.
o The Boyer-Moore fast search algorithm can be used with UTF-8 data.
o Алгоритм быстрого поиска Бойера–Мура может использоваться с данными UTF-8.
o UTF-8 strings can be fairly reliably recognized as such by a simple algorithm, i.e., the probability that a string of characters in any other encoding appears as valid UTF-8 is low, diminishing with increasing string length.
o Строки UTF-8 можно достаточно надёжно распознать как таковые с помощью простого алгоритма: вероятность того, что строка символов в любой другой кодировке окажется допустимой UTF-8, мала и уменьшается с ростом длины строки.
UTF-8 was devised in September 1992 by Ken Thompson, guided by design criteria specified by Rob Pike, with the objective of defining a UCS transformation format usable in the Plan9 operating system in a non- disruptive manner. Thompson's design was stewarded through standardization by the X/Open Joint Internationalization Group XOJIG (see [FSS_UTF]), bearing the names FSS-UTF (variant FSS/UTF), UTF-2 and finally UTF-8 along the way.
UTF-8 был разработан в сентябре 1992 года Кеном Томпсоном под руководством критериев проектирования, заданных Робом Пайком, с целью определить формат преобразования UCS, пригодный для использования в операционной системе Plan9 без нарушения её работы. Проект Томпсона был проведён через стандартизацию Совместной группой по интернационализации X/Open (X/Open Joint Internationalization Group, XOJIG) (см. [FSS_UTF]); по пути он носил имена FSS-UTF (вариант FSS/UTF), UTF-2 и, наконец, UTF-8.

3. UTF-8 definition
3. Определение UTF-8
UTF-8 is defined by the Unicode Standard [UNICODE]. Descriptions and formulae can also be found in Annex D of ISO/IEC 10646-1 [ISO.10646]
UTF-8 определён стандартом Unicode [UNICODE]. Описания и формулы также можно найти в приложении D к ISO/IEC 10646-1 [ISO.10646].
In UTF-8, characters from the U+0000..U+10FFFF range (the UTF-16 accessible range) are encoded using sequences of 1 to 4 octets. The only octet of a "sequence" of one has the higher-order bit set to 0, the remaining 7 bits being used to encode the character number. In a sequence of n octets, n>1, the initial octet has the n higher-order bits set to 1, followed by a bit set to 0. The remaining bit(s) of that octet contain bits from the number of the character to be encoded. The following octet(s) all have the higher-order bit set to 1 and the following bit set to 0, leaving 6 bits in each to contain bits from the character to be encoded.
В UTF-8 символы из диапазона U+0000..U+10FFFF (диапазона, доступного для UTF-16) кодируются последовательностями из 1–4 октетов. Единственный октет «последовательности» из одного имеет старший бит, равный 0, а остальные 7 бит используются для кодирования номера символа. В последовательности из n октетов, n>1, начальный октет имеет n старших битов, равных 1, за которыми следует бит, равный 0. Остальные биты этого октета содержат биты из номера кодируемого символа. Все последующие октеты имеют старший бит, равный 1, и следующий за ним бит, равный 0, так что в каждом остаётся 6 битов для битов кодируемого символа.

Encoding a character to UTF-8 proceeds as follows:
Кодирование символа в UTF-8 выполняется следующим образом:
1. Determine the number of octets required from the character number and the first column of the table above. It is important to note that the rows of the table are mutually exclusive, i.e., there is only one valid way to encode a given character.
1. Определите требуемое число октетов по номеру символа и первому столбцу таблицы выше. Важно отметить, что строки таблицы взаимно исключают друг друга, т.е. существует только один допустимый способ кодирования данного символа.
2. Prepare the high-order bits of the octets as per the second column of the table.
2. Подготовьте старшие биты октетов согласно второму столбцу таблицы.
3. Fill in the bits marked x from the bits of the character number, expressed in binary. Start by putting the lowest-order bit of the character number in the lowest-order position of the last octet of the sequence, then put the next higher-order bit of the character number in the next higher-order position of that octet, etc. When the x bits of the last octet are filled in, move on to the next to last octet, then to the preceding one, etc. until all x bits are filled in.
3. Заполните биты, помеченные x, битами номера символа, выраженного в двоичной форме. Начните с помещения самого младшего бита номера символа в самую младшую позицию последнего октета последовательности, затем поместите следующий по старшинству бит номера символа в следующую по старшинству позицию этого октета и т.д. Когда биты x последнего октета заполнены, переходите к предпоследнему октету, затем к предыдущему и т.д., пока все биты x не будут заполнены.
The definition of UTF-8 prohibits encoding character numbers between U+D800 and U+DFFF, which are reserved for use with the UTF-16 encoding form (as surrogate pairs) and do not directly represent characters. When encoding in UTF-8 from UTF-16 data, it is necessary to first decode the UTF-16 data to obtain character numbers, which are then encoded in UTF-8 as described above. This contrasts with CESU-8 [CESU-8], which is a UTF-8-like encoding that is not meant for use on the Internet. CESU-8 operates similarly to UTF-8 but encodes the UTF-16 code values (16-bit quantities) instead of the character number (code point). This leads to different results for character numbers above 0xFFFF; the CESU-8 encoding of those characters is NOT valid UTF-8.
Определение UTF-8 запрещает кодировать номера символов между U+D800 и U+DFFF, которые зарезервированы для использования с формой кодирования UTF-16 (в виде суррогатных пар) и не представляют символы напрямую. При кодировании в UTF-8 из данных UTF-16 необходимо сначала декодировать данные UTF-16, чтобы получить номера символов, которые затем кодируются в UTF-8, как описано выше. Это отличается от CESU-8 [CESU-8] — кодировки, подобной UTF-8, которая не предназначена для использования в Интернете. CESU-8 работает аналогично UTF-8, но кодирует кодовые значения UTF-16 (16-битные величины) вместо номера символа (кодовой точки). Это приводит к другим результатам для номеров символов выше 0xFFFF; кодировка CESU-8 этих символов НЕ является допустимой UTF-8.

5. Versions of the standards
5. Версии стандартов
ISO/IEC 10646 is updated from time to time by publication of amendments and additional parts; similarly, new versions of the Unicode standard are published over time. Each new version obsoletes and replaces the previous one, but implementations, and more significantly data, are not updated instantly.
ISO/IEC 10646 время от времени обновляется путём публикации поправок и дополнительных частей; аналогично со временем публикуются новые версии стандарта Unicode. Каждая новая версия устаревает и заменяет предыдущую, но реализации и, что ещё важнее, данные не обновляются мгновенно.
In general, the changes amount to adding new characters, which does not pose particular problems with old data. In 1996, Amendment 5 to the 1993 edition of ISO/IEC 10646 and Unicode 2.0 moved and expanded the Korean Hangul block, thereby making any previous data containing Hangul characters invalid under the new version. Unicode 2.0 has the same difference from Unicode 1.1. The justification for allowing such an incompatible change was that there were no major implementations and no significant amounts of data containing Hangul. The incident has been dubbed the "Korean mess", and the relevant committees have pledged to never, ever again make such an incompatible change (see Unicode Consortium Policies [1]).
В целом изменения сводятся к добавлению новых символов, что не создаёт особых проблем со старыми данными. В 1996 году поправка 5 к изданию ISO/IEC 10646 1993 года и Unicode 2.0 переместили и расширили блок корейского хангыля, тем самым сделав любые предыдущие данные, содержащие символы хангыля, недопустимыми в новой версии. Unicode 2.0 имеет то же отличие от Unicode 1.1. Обоснованием допустимости такого несовместимого изменения было отсутствие крупных реализаций и значительных объёмов данных, содержащих хангыль. Этот случай получил название «корейский беспорядок» (Korean mess), и соответствующие комитеты обязались никогда больше не делать таких несовместимых изменений (см. Политики Консорциума Unicode [1]).
New versions, and in particular any incompatible changes, have consequences regarding MIME charset labels, to be discussed in MIME registration (Section 8).
Новые версии и, в частности, любые несовместимые изменения имеют последствия для меток кодировки MIME, которые рассматриваются в разделе о регистрации MIME (раздел 8).
6. Byte order mark (BOM)
6. Маркер порядка байтов (BOM)
The UCS character U+FEFF "ZERO WIDTH NO-BREAK SPACE" is also known informally as "BYTE ORDER MARK" (abbreviated "BOM"). This character can be used as a genuine "ZERO WIDTH NO-BREAK SPACE" within text, but the BOM name hints at a second possible usage of the character: to prepend a U+FEFF character to a stream of UCS characters as a "signature". A receiver of such a serialized stream may then use the initial character as a hint that the stream consists of UCS characters and also to recognize which UCS encoding is involved and, with encodings having a multi-octet encoding unit, as a way to recognize the serialization order of the octets. UTF-8 having a single-octet encoding unit, this last function is useless and the BOM will always appear as the octet sequence EF BB BF.
Символ UCS U+FEFF «ZERO WIDTH NO-BREAK SPACE» также неофициально известен как «BYTE ORDER MARK» (сокращённо «BOM»). Этот символ может использоваться как настоящий «ZERO WIDTH NO-BREAK SPACE» внутри текста, но имя BOM намекает на второе возможное применение символа: добавлять символ U+FEFF в начало потока символов UCS в качестве «подписи». Получатель такого сериализованного потока может затем использовать начальный символ как подсказку о том, что поток состоит из символов UCS, а также для распознавания используемой кодировки UCS и, для кодировок с многооктетной единицей кодирования, как способ распознать порядок сериализации октетов. Поскольку UTF-8 имеет однооктетную единицу кодирования, эта последняя функция бесполезна, и BOM всегда будет появляться как октетная последовательность EF BB BF.
It is important to understand that the character U+FEFF appearing at any position other than the beginning of a stream MUST be interpreted with the semantics for the zero-width non-breaking space, and MUST NOT be interpreted as a signature. When interpreted as a signature, the Unicode standard suggests than an initial U+FEFF character may be stripped before processing the text. Such stripping is necessary in some cases (e.g., when concatenating two strings, because otherwise the resulting string may contain an unintended "ZERO WIDTH NO-BREAK SPACE" at the connection point), but might affect an external process at a different layer (such as a digital signature or a count of the characters) that is relying on the presence of all characters in the stream. It is therefore RECOMMENDED to avoid stripping an initial U+FEFF interpreted as a signature without a good reason, to ignore it instead of stripping it when appropriate (such as for display) and to strip it only when really necessary.
Важно понимать, что символ U+FEFF, появляющийся в любом месте, кроме начала потока, ДОЛЖЕН интерпретироваться с семантикой неразрывного пробела нулевой ширины и НЕ ДОЛЖЕН интерпретироваться как подпись. При интерпретации в качестве подписи стандарт Unicode предлагает удалять начальный символ U+FEFF перед обработкой текста. Такое удаление в некоторых случаях необходимо (например, при конкатенации двух строк, поскольку иначе результирующая строка может содержать непреднамеренный «ZERO WIDTH NO-BREAK SPACE» в точке соединения), но может повлиять на внешний процесс на другом уровне (такой как цифровая подпись или подсчёт символов), который полагается на наличие всех символов в потоке. Поэтому РЕКОМЕНДУЕТСЯ избегать удаления начального U+FEFF, интерпретируемого как подпись, без веской причины, игнорировать его вместо удаления, когда это уместно (например, для отображения), и удалять его только при действительной необходимости.
U+FEFF in the first position of a stream MAY be interpreted as a zero-width non-breaking space, and is not always a signature. In an attempt at diminishing this uncertainty, Unicode 3.2 adds a new character, U+2060 "WORD JOINER", with exactly the same semantics and usage as U+FEFF except for the signature function, and strongly recommends its exclusive use for expressing word-joining semantics. Eventually, following this recommendation will make it all but certain that any initial U+FEFF is a signature, not an intended "ZERO WIDTH NO-BREAK SPACE".
U+FEFF в первой позиции потока МОЖЕТ интерпретироваться как неразрывный пробел нулевой ширины и не всегда является подписью. В попытке уменьшить эту неопределённость Unicode 3.2 добавляет новый символ U+2060 «WORD JOINER» с точно такой же семантикой и использованием, как у U+FEFF, за исключением функции подписи, и настоятельно рекомендует использовать его исключительно для выражения семантики соединения слов. В конечном счёте следование этой рекомендации сделает практически несомненным, что любой начальный U+FEFF является подписью, а не предполагаемым «ZERO WIDTH NO-BREAK SPACE».
In the meantime, the uncertainty unfortunately remains and may affect Internet protocols. Protocol specifications MAY restrict usage of U+FEFF as a signature in order to reduce or eliminate the potential ill effects of this uncertainty. In the interest of striking a balance between the advantages (reduction of uncertainty) and drawbacks (loss of the signature function) of such restrictions, it is useful to distinguish a few cases:
Тем временем неопределённость, к сожалению, сохраняется и может влиять на интернет-протоколы. Спецификации протоколов МОГУТ ограничивать использование U+FEFF в качестве подписи, чтобы уменьшить или устранить потенциальные неблагоприятные последствия этой неопределённости. В интересах достижения баланса между преимуществами (уменьшение неопределённости) и недостатками (потеря функции подписи) таких ограничений полезно различать несколько случаев:
o A protocol SHOULD forbid use of U+FEFF as a signature for those textual protocol elements that the protocol mandates to be always UTF-8, the signature function being totally useless in those cases.
o Протокол ДОЛЖЕН запрещать использование U+FEFF в качестве подписи для тех текстовых элементов протокола, которые протокол предписывает всегда кодировать в UTF-8, поскольку в этих случаях функция подписи полностью бесполезна.
o A protocol SHOULD also forbid use of U+FEFF as a signature for those textual protocol elements for which the protocol provides character encoding identification mechanisms, when it is expected that implementations of the protocol will be in a position to always use the mechanisms properly. This will be the case when the protocol elements are maintained tightly under the control of the implementation from the time of their creation to the time of their (properly labeled) transmission.
o Протокол ДОЛЖЕН также запрещать использование U+FEFF в качестве подписи для тех текстовых элементов протокола, для которых протокол предоставляет механизмы идентификации кодировки символов, когда ожидается, что реализации протокола будут в состоянии всегда правильно использовать эти механизмы. Это будет иметь место, когда элементы протокола поддерживаются в строгом соответствии с реализацией с момента их создания до момента их (правильно помеченной) передачи.
o A protocol SHOULD NOT forbid use of U+FEFF as a signature for those textual protocol elements for which the protocol does not provide character encoding identification mechanisms, when a ban would be unenforceable, or when it is expected that implementations of the protocol will not be in a position to always use the mechanisms properly. The latter two cases are likely to occur with larger protocol elements such as MIME entities, especially when implementations of the protocol will obtain such entities from file systems, from protocols that do not have encoding identification mechanisms for payloads (such as FTP) or from other protocols that do not guarantee proper identification of character encoding (such as HTTP).
o Протокол НЕ ДОЛЖЕН запрещать использование U+FEFF в качестве подписи для тех текстовых элементов протокола, для которых протокол не предоставляет механизмы идентификации кодировки символов, когда запрет был бы неисполнимым или когда ожидается, что реализации протокола не будут в состоянии всегда правильно использовать механизмы. Последние два случая, вероятно, будут возникать с более крупными элементами протокола, такими как сущности MIME, особенно когда реализации протокола получают такие сущности из файловых систем, из протоколов, не имеющих механизмов идентификации кодировки для полезной нагрузки (таких как FTP), или из других протоколов, не гарантирующих правильную идентификацию кодировки символов (таких как HTTP).
When a protocol forbids use of U+FEFF as a signature for a certain protocol element, then any initial U+FEFF in that protocol element MUST be interpreted as a "ZERO WIDTH NO-BREAK SPACE". When a protocol does NOT forbid use of U+FEFF as a signature for a certain protocol element, then implementations SHOULD be prepared to handle a signature in that element and react appropriately: using the signature to identify the character encoding as necessary and stripping or ignoring the signature as appropriate.
Когда протокол запрещает использование U+FEFF в качестве подписи для определённого элемента протокола, любой начальный U+FEFF в этом элементе протокола ДОЛЖЕН интерпретироваться как «ZERO WIDTH NO-BREAK SPACE». Когда протокол НЕ запрещает использование U+FEFF в качестве подписи для определённого элемента протокола, реализации ДОЛЖНЫ быть готовы обработать подпись в этом элементе и соответствующим образом отреагировать: использовать подпись для идентификации кодировки символов по мере необходимости и удалять или игнорировать подпись по обстоятельствам.

8. MIME registration
8. Регистрация MIME
This memo serves as the basis for registration of the MIME charset parameter for UTF-8, according to [RFC2978]. The charset parameter value is "UTF-8". This string labels media types containing text consisting of characters from the repertoire of ISO/IEC 10646 including all amendments at least up to amendment 5 of the 1993 edition (Korean block), encoded to a sequence of octets using the encoding scheme outlined above. UTF-8 is suitable for use in MIME content types under the "text" top-level type.
Настоящий меморандум служит основой для регистрации параметра кодировки MIME для UTF-8 согласно [RFC2978]. Значением параметра charset является «UTF-8». Эта строка помечает типы носителей, содержащие текст, состоящий из символов репертуара ISO/IEC 10646, включая все поправки как минимум до поправки 5 к изданию 1993 года (корейский блок), закодированных в последовательность октетов с использованием схемы кодирования, изложенной выше. UTF-8 подходит для использования в типах содержимого MIME в рамках типа верхнего уровня «text».
It is noteworthy that the label "UTF-8" does not contain a version identification, referring generically to ISO/IEC 10646. This is intentional, the rationale being as follows:
Примечательно, что метка «UTF-8» не содержит идентификатора версии и в общем виде ссылается на ISO/IEC 10646. Это сделано намеренно, и обоснование таково:
A MIME charset label is designed to give just the information needed to interpret a sequence of bytes received on the wire into a sequence of characters, nothing more (see [RFC2045], section 2.2). As long as a character set standard does not change incompatibly, version numbers serve no purpose, because one gains nothing by learning from the tag that newly assigned characters may be received that one doesn't know about. The tag itself doesn't teach anything about the new characters, which are going to be received anyway.
Метка кодировки MIME предназначена для предоставления только той информации, которая нужна для интерпретации последовательности байтов, полученной по каналу, как последовательности символов, и ничего более (см. [RFC2045], раздел 2.2). Пока стандарт набора символов не изменяется несовместимо, номера версий не служат никакой цели, поскольку, узнав из метки, что могут быть получены новые назначенные символы, о которых вы не знаете, вы ничего не выигрываете. Сама метка ничего не сообщает о новых символах, которые всё равно будут получены.
Hence, as long as the standards evolve compatibly, the apparent advantage of having labels that identify the versions is only that, apparent. But there is a disadvantage to such version-dependent labels: when an older application receives data accompanied by a newer, unknown label, it may fail to recognize the label and be completely unable to deal with the data, whereas a generic, known label would have triggered mostly correct processing of the data, which may well not contain any new characters.
Следовательно, пока стандарты развиваются совместимо, кажущееся преимущество наличия меток, идентифицирующих версии, только кажущееся. Но у таких зависящих от версии меток есть недостаток: когда более старое приложение получает данные, сопровождаемые новой неизвестной меткой, оно может не распознать метку и оказаться совершенно неспособным обработать данные, тогда как общая известная метка вызвала бы в основном правильную обработку данных, которые вполне могут не содержать никаких новых символов.
Now the "Korean mess" (ISO/IEC 10646 amendment 5) is an incompatible change, in principle contradicting the appropriateness of a version independent MIME charset label as described above. But the compatibility problem can only appear with data containing Korean Hangul characters encoded according to Unicode 1.1 (or equivalently ISO/IEC 10646 before amendment 5), and there is arguably no such data to worry about, this being the very reason the incompatible change was deemed acceptable. In practice, then, a version-independent label is warranted, provided the label is understood to refer to all versions after Amendment 5, and provided no incompatible change actually occurs. Should incompatible changes occur in a later version of ISO/IEC 10646, the MIME charset label defined here will stay aligned with the previous version until and unless the IETF specifically decides otherwise.
Теперь «корейский беспорядок» (поправка 5 к ISO/IEC 10646) является несовместимым изменением, что в принципе противоречит пригодности независимой от версии метки кодировки MIME, как описано выше. Но проблема совместимости может возникнуть только с данными, содержащими корейские символы хангыля, закодированные в соответствии с Unicode 1.1 (или, что эквивалентно, ISO/IEC 10646 до поправки 5), а таких данных, возможно, не существует, и именно это послужило причиной признания несовместимого изменения приемлемым. На практике, следовательно, независимая от версии метка оправдана при условии, что метка понимается как относящаяся ко всем версиям после поправки 5 и что несовместимое изменение действительно не произойдёт. Если несовместимые изменения произойдут в более поздней версии ISO/IEC 10646, определённая здесь метка кодировки MIME останется согласованной с предыдущей версией, пока и если IETF специально не решит иначе.

10. Security Considerations
10. Вопросы безопасности
Implementers of UTF-8 need to consider the security aspects of how they handle illegal UTF-8 sequences. It is conceivable that in some circumstances an attacker would be able to exploit an incautious UTF-8 parser by sending it an octet sequence that is not permitted by the UTF-8 syntax.
Разработчикам UTF-8 необходимо учитывать аспекты безопасности обработки недопустимых последовательностей UTF-8. Можно представить, что в некоторых обстоятельствах злоумышленник сможет использовать неосмотрительный анализатор UTF-8, отправив ему октетную последовательность, не разрешённую синтаксисом UTF-8.
A particularly subtle form of this attack can be carried out against a parser which performs security-critical validity checks against the UTF-8 encoded form of its input, but interprets certain illegal octet sequences as characters. For example, a parser might prohibit the NUL character when encoded as the single-octet sequence 00, but erroneously allow the illegal two-octet sequence C0 80 and interpret it as a NUL character. Another example might be a parser which prohibits the octet sequence 2F 2E 2E 2F ("/../"), yet permits the illegal octet sequence 2F C0 AE 2E 2F. This last exploit has actually been used in a widespread virus attacking Web servers in 2001; thus, the security threat is very real.
Особенно тонкая форма этой атаки может быть осуществлена против анализатора, который выполняет критичные для безопасности проверки допустимости закодированной в UTF-8 формы своих входных данных, но интерпретирует некоторые недопустимые октетные последовательности как символы. Например, анализатор может запрещать символ NUL, закодированный как однооктетная последовательность 00, но ошибочно разрешать недопустимую двухоктетную последовательность C0 80 и интерпретировать её как символ NUL. Другим примером может быть анализатор, который запрещает октетную последовательность 2F 2E 2E 2F («/../»), но разрешает недопустимую октетную последовательность 2F C0 AE 2E 2F. Эта последняя уязвимость фактически использовалась в широко распространённом вирусе, атаковавшем веб-серверы в 2001 году; таким образом, угроза безопасности вполне реальна.
Another security issue occurs when encoding to UTF-8: the ISO/IEC 10646 description of UTF-8 allows encoding character numbers up to U+7FFFFFFF, yielding sequences of up to 6 bytes. There is therefore a risk of buffer overflow if the range of character numbers is not explicitly limited to U+10FFFF or if buffer sizing doesn't take into account the possibility of 5- and 6-byte sequences.
Ещё одна проблема безопасности возникает при кодировании в UTF-8: описание UTF-8 в ISO/IEC 10646 допускает кодирование номеров символов вплоть до U+7FFFFFFF, что даёт последовательности длиной до 6 байт. Поэтому существует риск переполнения буфера, если диапазон номеров символов явно не ограничен U+10FFFF или если размер буфера не учитывает возможность появления 5- и 6-байтовых последовательностей.
Security may also be impacted by a characteristic of several character encodings, including UTF-8: the "same thing" (as far as a user can tell) can be represented by several distinct character sequences. For instance, an e with acute accent can be represented by the precomposed U+00E9 E ACUTE character or by the canonically equivalent sequence U+0065 U+0301 (E + COMBINING ACUTE). Even though UTF-8 provides a single byte sequence for each character sequence, the existence of multiple character sequences for "the same thing" may have security consequences whenever string matching, indexing, searching, sorting, regular expression matching and selection are involved. An example would be string matching of an identifier appearing in a credential and in access control list entries. This issue is amenable to solutions based on Unicode Normalization Forms, see [UAX15].
На безопасность также может влиять характеристика нескольких кодировок символов, включая UTF-8: «одно и то же» (насколько может судить пользователь) может быть представлено несколькими различными последовательностями символов. Например, буква e с острым ударением может быть представлена предварительно составленным символом U+00E9 E ACUTE или канонически эквивалентной последовательностью U+0065 U+0301 (E + COMBINING ACUTE). Хотя UTF-8 обеспечивает единственную байтовую последовательность для каждой последовательности символов, существование нескольких последовательностей символов для «одного и того же» может иметь последствия для безопасности всякий раз, когда задействованы сопоставление строк, индексация, поиск, сортировка, сопоставление регулярных выражений и выбор. Примером может служить сопоставление строк идентификатора, встречающегося в учётных данных и в записях списка управления доступом. Эта проблема поддаётся решению на основе форм нормализации Unicode, см. [UAX15].

12. Changes from RFC 2279
12. Изменения относительно RFC 2279
o Restricted the range of characters to 0000-10FFFF (the UTF-16 accessible range).
o Ограничен диапазон символов до 0000-10FFFF (диапазона, доступного для UTF-16).
o Made Unicode the source of the normative definition of UTF-8, keeping ISO/IEC 10646 as the reference for characters.
o Источником нормативного определения UTF-8 сделан Unicode, а ISO/IEC 10646 оставлен справочником для символов.
o Straightened out terminology. UTF-8 now described in terms of an encoding form of the character number. UCS-2 and UCS-4 almost disappeared.
o Упорядочена терминология. UTF-8 теперь описывается в терминах формы кодирования номера символа. UCS-2 и UCS-4 почти исчезли.
o Turned the note warning against decoding of invalid sequences into a normative MUST NOT.
o Примечание с предупреждением против декодирования недопустимых последовательностей превращено в нормативное MUST NOT.
o Added a new section about the UTF-8 BOM, with advice for protocols.
o Добавлен новый раздел о BOM UTF-8 с рекомендациями для протоколов.
o Removed suggested UNICODE-1-1-UTF-8 MIME charset registration.
o Удалена предложенная регистрация кодировки MIME UNICODE-1-1-UTF-8.
o Added an ABNF syntax for valid UTF-8 octet sequences
o Добавлен синтаксис ABNF для допустимых октетных последовательностей UTF-8.
o Expanded Security Considerations section, in particular impact of Unicode normalization
o Расширен раздел «Вопросы безопасности», в частности влияние нормализации Unicode.
