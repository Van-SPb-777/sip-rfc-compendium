Abstract
Аннотация
This document defines a new Session Description Protocol (SDP) media- level attribute, 'content'. The 'content' attribute defines the content of the media stream to a more detailed level than the media description line. The sender of an SDP session description can attach the 'content' attribute to one or more media streams. The receiving application can then treat each media stream differently (e.g., show it on a big or small screen) based on its content.
Настоящий документ определяет новый атрибут уровня медиа протокола описания сессий (SDP) — 'content'. Атрибут 'content' определяет содержимое медиапотока более подробно, чем строка описания медиа. Отправитель описания сессии SDP может прикрепить атрибут 'content' к одному или нескольким медиапотокам. Затем принимающее приложение может обрабатывать каждый медиапоток по-разному (например, показывать его на большом или маленьком экране) в зависимости от его содержимого.
1. Introduction
1. Введение
The Session Description Protocol (SDP) [1] is a protocol that is intended to describe multimedia sessions for the purposes of session announcement, session invitation, and other forms of multimedia session initiation. One of the most typical use cases of SDP is where it is used with the Session Initiation Protocol (SIP) [5].
Протокол описания сессий (SDP) [1] — это протокол, предназначенный для описания мультимедийных сессий в целях анонсирования сессий, приглашения к участию в сессии и других форм инициирования мультимедийных сессий. Один из наиболее типичных сценариев использования SDP — совместная работа с протоколом инициирования сессий (SIP) [5].
There are situations where one application receives several similar media streams, which are described in an SDP session description. The media streams can be similar in the sense that their content cannot be distinguished just by examining their media description lines (e.g., two video streams). The 'content' attribute is needed so that the receiving application can treat each media stream appropriately based on its content.
Бывают ситуации, когда одно приложение получает несколько похожих медиапотоков, описанных в описании сессии SDP. Медиапотоки могут быть похожи в том смысле, что их содержимое нельзя различить, просто изучив строки их описания медиа (например, два видеопотока). Атрибут 'content' нужен, чтобы принимающее приложение могло надлежащим образом обрабатывать каждый медиапоток в зависимости от его содержимого.
This specification defines the SDP 'content' media-level attribute, which provides more information about the media stream than the 'm' line in an SDP session description.
Настоящая спецификация определяет атрибут уровня медиа 'content' протокола SDP, который предоставляет больше сведений о медиапотоке, чем строка 'm' в описании сессии SDP.
The main purpose of this specification is to allow applications to take automated actions based on the 'content' attributes. However, this specification does not define those actions. Consequently, two implementations can behave completely differently when receiving the same 'content' attribute.
Основная цель настоящей спецификации — позволить приложениям выполнять автоматические действия на основе атрибутов 'content'. Однако настоящая спецификация не определяет эти действия. Следовательно, две реализации могут вести себя совершенно по-разному при получении одного и того же атрибута 'content'.

3. Related Techniques
3. Смежные методы
The 'label' attribute [10] enables a sender to attach a pointer to a particular media stream. The namespace of the 'label' attribute itself is unrestricted; so, in principle, it could also be used to convey information about the content of a media stream. However, in practice, this is not possible because of the need for backward compatibility. Existing implementations of the 'label' attribute already use values from that unrestricted namespace in an application-specific way. So, it is not possible to reserve portions of the 'label' attribute's namespace without possible conflict with already used application-specific labels. It is possible to assign semantics to a media stream with an external document that uses the 'label' attribute as a pointer. The downside of this approach is that it requires an external document. Therefore, this kind of mechanism is only applicable to special use cases where such external documents are used (e.g., centralized conferencing).
Атрибут 'label' [10] позволяет отправителю прикрепить указатель к конкретному медиапотоку. Пространство имён самого атрибута 'label' не ограничено; поэтому в принципе его можно было бы использовать и для передачи сведений о содержимом медиапотока. Однако на практике это невозможно из-за необходимости обратной совместимости. Существующие реализации атрибута 'label' уже используют значения из этого неограниченного пространства имён зависящим от приложения образом. Поэтому невозможно зарезервировать части пространства имён атрибута 'label' без возможного конфликта с уже используемыми зависящими от приложения метками. Можно назначить семантику медиапотоку с помощью внешнего документа, использующего атрибут 'label' в качестве указателя. Недостаток этого подхода в том, что он требует внешнего документа. Следовательно, такой механизм применим только к особым сценариям, где используются такие внешние документы (например, централизованные конференции).
Yet another way to attach semantics to a media stream is to use the 'i' SDP attribute, defined in [1]. However, values of the 'i' attribute are intended for human users and not for automata.
Ещё один способ придать медиапотоку семантику — использовать атрибут SDP 'i', определённый в [1]. Однако значения атрибута 'i' предназначены для людей, а не для автоматов.
4. Motivation for the New Content Attribute
4. Мотивация для нового атрибута content
Currently, SDP does not provide any means for describing the content of a media stream (e.g., speaker's image, slides, sign language) in a form that the application can understand. Of course, the end user can see the content of the media stream and read its title, but the application cannot understand what the media stream contains.
В настоящее время SDP не предоставляет никаких средств описания содержимого медиапотока (например, изображения докладчика, слайдов, жестового языка) в форме, понятной приложению. Разумеется, конечный пользователь видит содержимое медиапотока и может прочитать его заголовок, но приложение не может понять, что содержит медиапоток.
The application that is receiving multiple similar (e.g., same type and format) media streams needs, in some cases, to know what the contents of those streams are. This kind of situation occurs, for example, in cases where presentation slides, the speaker's image, and sign language are transported as separate media streams. It would be desirable that the receiving application could distinguish them in a way that it could handle them automatically in an appropriate manner.
Приложению, принимающему несколько похожих (например, одного типа и формата) медиапотоков, в некоторых случаях нужно знать, каково содержимое этих потоков. Такая ситуация возникает, например, когда презентационные слайды, изображение докладчика и жестовый язык передаются как отдельные медиапотоки. Желательно, чтобы принимающее приложение могло различать их так, чтобы обрабатывать автоматически надлежащим образом.

Figure 1 shows a screen of a typical communication application. The 'content' attribute makes it possible for the application to decide where to show each media stream. From an end user's perspective, it is desirable that the user does not need to arrange each media stream every time a new media session starts.
На рисунке 1 показан экран типичного приложения для общения. Атрибут 'content' позволяет приложению решить, где показывать каждый медиапоток. С точки зрения конечного пользователя желательно, чтобы ему не приходилось располагать каждый медиапоток заново при каждом начале новой медиасессии.
The 'content' attribute could also be used in more complex situations. An example of such a situation is an application controlling equipment in an auditorium. An auditorium can have many different output channels for video (e.g., main screen and two smaller screens) and audio (e.g., main speakers and headsets for the participants). In this kind of environment, a lot of interaction from the end user who operates the application would be required in absence of cues from a controlling application. The 'content' attribute would make it possible, for example, for an end user to specify, only once, which output each media stream of a given session should use. The application could automatically apply the same media layout for subsequent sessions. So, the 'content' attribute can help reduce the amount of required end-user interaction considerably.
Атрибут 'content' можно использовать и в более сложных ситуациях. Пример такой ситуации — приложение, управляющее оборудованием в аудитории. В аудитории может быть множество различных выходных каналов для видео (например, основной экран и два экрана поменьше) и звука (например, основные громкоговорители и наушники для участников). В такой среде при отсутствии подсказок от управляющего приложения потребовалось бы множество действий конечного пользователя, работающего с приложением. Атрибут 'content' позволил бы, например, конечному пользователю указать лишь один раз, какой выход должен использовать каждый медиапоток данной сессии. Приложение могло бы автоматически применять ту же схему размещения медиа к последующим сессиям. Таким образом, атрибут 'content' может значительно сократить объём требуемого взаимодействия с конечным пользователем.
5. The Content Attribute
5. Атрибут content
This specification defines a new media-level value attribute, 'content'. Its formatting in SDP is described by the following ABNF (Augmented Backus-Naur Form) [2]:
Настоящая спецификация определяет новый атрибут-значение уровня медиа 'content'. Его форматирование в SDP описано следующей ABNF (расширенной форме Бэкуса — Наура) [2]:
content-attribute = "a=content:" mediacnt-tag mediacnt-tag = mediacnt *("," mediacnt) mediacnt = "slides" / "speaker" / "sl" / "main" / "alt" / mediacnt-ext mediacnt-ext = token
content-attribute = "a=content:" mediacnt-tag mediacnt-tag = mediacnt *("," mediacnt) mediacnt = "slides" / "speaker" / "sl" / "main" / "alt" / mediacnt-ext mediacnt-ext = token
The 'content' attribute contains one or more tokens, which MAY be attached to a media stream by a sending application. An application MAY attach a 'content' attribute to any media stream it describes.
Атрибут 'content' содержит один или несколько токенов, которые отправляющее приложение МОЖЕТ прикрепить к медиапотоку. Приложение МОЖЕТ прикрепить атрибут 'content' к любому описываемому им медиапотоку.
This document provides a set of pre-defined values for the 'content' attribute. Other values can be defined in the future. The pre- defined values are:
Настоящий документ предоставляет набор предопределённых значений для атрибута. Другие значения могут быть определены в будущем. Заранееопределённые значения:
slides: the media stream includes presentation slides. The media type can be, for example, a video stream or a number of instant messages with pictures. Typical use cases for this are online seminars and courses. This is similar to the 'presentation' role in H.239 [12].
slides: медиапоток содержит презентационные слайды. Тип медиа может быть, например, видеопотоком или несколькими мгновенными сообщениями с картинками. Типичные сценарии — онлайн-семинары и курсы. Это аналогично роли 'presentation' в H.239 [12].
speaker: the media stream contains the image of the speaker. The media can be, for example, a video stream or a still image. Typical use cases for this are online seminars and courses.
speaker: медиапоток содержит изображение докладчика. Медиа может быть, например, видеопотоком или неподвижным изображением. Типичные сценарии — онлайн-семинары и курсы.
sl: the media stream contains sign language. A typical use case for this is an audio stream that is translated into sign language, which is sent over a video stream.
sl: медиапоток содержит жестовый язык. Типичный сценарий его использования — аудиопоток, который переводится на жестовый язык и передаётся по видеопотоку.
main: the media stream is taken from the main source. A typical use case for this is a concert where the camera is shooting the performer.
main: медиапоток берётся из основного источника. Типичный пример применения — концерт, в котором камера снимает исполнителя на сцене.
alt: the media stream is taken from the alternative source. A typical use case for this is an event where the ambient sound is separated from the main sound. The alternative audio stream could be, for example, the sound of a jungle. Another example is the video of a conference room, while the main stream carries the video of the speaker. This is similar to the 'live' role in H.239.
alt: медиапоток берётся из альтернативного источника. Типичный пример применения — мероприятие, где окружающий фоновый звук отделён от основного. Альтернативным аудиопотоком может быть, например, шум джунглей. Другой пример — видеоизображение конференц-зала, тогда как основной медиапоток несёт видео докладчика. Это аналогично роли 'live' в спецификации H.239.
All these values can be used with any media type. We chose not to restrict each value to a particular set of media types in order not to prevent applications from using innovative combinations of a given value with different media types.
Все эти значения можно использовать с любым типом медиа. Мы решили не ограничивать каждое значение определённым набором типов медиа, чтобы не мешать приложениям применять новаторские сочетания данного значения с разными типами медиа.
The application can make decisions on how to handle a single media stream based on both the media type and the value of the 'content' attribute. If the application does not implement any special logic for the handling of a given media type and 'content' value combination, it applies the application's default handling for the media type.
Приложение может принимать решения о том, как обрабатывать отдельный медиапоток, на основе как типа медиа, так и значения атрибута 'content'. Если приложение не реализует никакой специальной логики для обработки данного сочетания типа медиа и значения 'content', оно применяет обработку по умолчанию для этого типа медиа.
Note that the same 'content' attribute value can occur more than once in a single session description.
Обратите внимание, что одно и то же значение атрибута 'content' может встречаться в одном описании сессии более одного раза.
6. The Content Attribute in the Offer/Answer Model
6. Атрибут content в модели «предложение/ответ»
This specification does not define a means to discover whether the peer endpoint understands the 'content' attribute because 'content' values are just informative at the offer/answer model [8] level. The fact that the peer endpoint does not understand the 'content' attribute does not keep the media session from being established. The only consequence is that end user interaction on the receiving side may be required to direct the individual media streams appropriately. The 'content' attribute describes the data that the application generating the SDP session description intends to send over a particular media stream. The 'content' values for both directions of a media stream do not need to be the same. Therefore, an SDP answer MAY contain 'content' attributes even if none were present in the offer. Similarly, the answer MAY contain no 'content' attributes even if they were present in the offer. Furthermore, the values of 'content' attributes do not need to match in an offer and an answer.
Настоящая спецификация не определяет средство обнаружения того, понимает ли партнёрский узел атрибут 'content', поскольку значения 'content' носят лишь информативный характер на уровне модели «предложение/ответ» [8]. То обстоятельство, что партнёрский узел не понимает атрибут 'content', не мешает установлению медиасессии. Единственное последствие — на принимающей стороне может потребоваться взаимодействие с конечным пользователем, чтобы направить отдельные медиапотоки надлежащим образом. Атрибут 'content' описывает данные, которые приложение, формирующее описание сессии SDP, намерено передавать по конкретному медиапотоку. Значения 'content' для обоих направлений медиапотока не обязаны совпадать. Поэтому ответ SDP МОЖЕТ содержать атрибуты 'content', даже если в предложении их не было. Аналогично ответ МОЖЕТ не содержать атрибутов 'content', даже если они были в предложении. Более того, значения атрибутов 'content' не обязаны совпадать в предложении и ответе.
The 'content' attribute can also be used in scenarios where SDP is used in a declarative style. For example, 'content' attributes can be used in SDP session descriptors that are distributed with Session Announcement Protocol (SAP) [9].
Атрибут 'content' можно также использовать в сценариях, где SDP применяется в декларативном стиле. Например, атрибуты 'content' можно использовать в дескрипторах сессий SDP, распространяемых с помощью протокола анонсирования сессий (SAP) [9].

8. Operation with SMIL
8. Работа с SMIL
The values of 'content' attribute, defined in Section 5, can also be used with Synchronized Multimedia Integration Language (SMIL) [11]. SMIL contains a 'param' element, which is used for describing the content of a media flow. However, this 'param' element, like the 'content' attribute, provides an application-specific description of the media content.
Значения атрибута 'content', определённые в разделе 5, можно также использовать с языком синхронизированной интеграции мультимедиа (SMIL) [11]. SMIL содержит элемент 'param', который используется для описания содержимого медиапотока. Однако этот элемент 'param', как и атрибут 'content', обеспечивает описание содержимого медиа, зависящее от приложения.
Details on how to use the values of the 'content' attribute with SMIL's 'param' element are outside the scope of this specification.
Подробности использования значений атрибута 'content' с элементом 'param' языка SMIL выходят за рамки настоящей спецификации.
9. Security Considerations
9. Вопросы безопасности
An attacker may attempt to add, modify, or remove 'content' attributes from a session description. Depending on how an implementation chooses to react to the presence or absence of a given 'content' attribute, this could result in an application behaving in an undesirable way; therefore, it is strongly RECOMMENDED that integrity protection be applied to the SDP session descriptions.
Злоумышленник может попытаться добавить, изменить или удалить атрибуты 'content' из описания сессии. В зависимости от того, как реализация реагирует на наличие или отсутствие данного атрибута 'content', это может привести к нежелательному поведению приложения; поэтому НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ применять защиту целостности к описаниям сессий SDP.
Integrity protection can be provided for a session description carried in an SIP [5], e.g., by using S/MIME [6] or Transport Layer Security (TLS) [7].
Защиту целостности можно обеспечить для описания сессии, переносимого в SIP [5], например, с помощью S/MIME [6] или протокола безопасности транспортного уровня (TLS) [7].
It is assumed that values of 'content' attribute do not contain data that would be truly harmful if it is exposed to a possible attacker. It must be noted that the initial set of values does not contain any data that would require confidentiality protection. However, S/MIME and TLS can be used to protect confidentiality, if needed.
Предполагается, что значения атрибута 'content' не содержат данных, которые были бы поистине вредоносными при раскрытии возможному злоумышленнику. Следует отметить, что первоначальный набор значений не содержит данных, требующих защиты конфиденциальности. Однако при необходимости для защиты конфиденциальности можно использовать S/MIME и TLS.
