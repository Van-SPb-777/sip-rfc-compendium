Abstract
Аннотация
This document defines an update to the Calendaring Extensions to WebDAV (CalDAV) calendar access protocol (RFC 4791) to allow clients and servers to exchange iCalendar data without the need to send full time zone data.
В настоящем документе определяется обновление протокола доступа к календарю CalDAV (RFC 4791), позволяющее клиентам и серверам обмениваться данными iCalendar без необходимости передавать полные данные часовых поясов.

1. Introduction
1. Введение
The CalDAV [RFC4791] calendar access protocol allows clients to access calendar data stored on a server in the iCalendar [RFC5545] data format. In iCalendar, calendar data that uses local time in any of its date and/or time values is specified as a date-time value in combination with a time zone identifier ("TZID" property parameter). The time zone identifier refers to a time zone definition (a "VTIMEZONE" component) that has all of the rules required to determine local-time UTC offsets for the corresponding time zone. In many cases, these "VTIMEZONE" components can be larger, octet-wise, than the events or tasks that make use of them. However, iCalendar currently requires all iCalendar objects ("VCALENDAR" components) that refer to a time zone via its identifier to also include the corresponding "VTIMEZONE" component. This leads to inefficiencies in the CalDAV protocol because large amounts of "VTIMEZONE" data are continuously being exchanged, and for the most part these time zone definitions are unchanging. This is particularly problematic for mobile or limited devices, with limited network bandwidth, CPU, and energy resources. A set of standard time zone definitions are available at the IANA- hosted time zone database [RFC6557]. That database provides the "raw" data for time zone definitions, and those can be converted into iCalendar "VTIMEZONE" components for use in iCalendar applications, as well as converted into other formats for use by other applications (e.g., "zoneinfo" files often found on Unix-based operating systems). A new time zone data distribution service protocol [RFC7808] is available that allows iCalendar applications to retrieve these standard time zone definitions in a timely and accurate fashion, instead of relying on possibly infrequent system updates of time zone data that frequently result in mismatched calendar data and thus missed meetings between calendar users. Another benefit of the time zone data distribution service is that it provides a single "reference" for standard time zone data that CalDAV clients and servers can make use of to "agree" on standard time zone definitions, and thus eliminate the need to exchange the data for those.
Протокол доступа к календарю CalDAV [RFC4791] позволяет клиентам получать доступ к данным календаря, хранящимся на сервере в формате данных iCalendar [RFC5545]. В iCalendar данные календаря, использующие местное время в любых своих значениях даты и/или времени, задаются как значение даты-времени в сочетании с идентификатором часового пояса (параметр свойства "TZID"). Идентификатор часового пояса ссылается на определение часового пояса (компонент "VTIMEZONE"), которое содержит все правила, необходимые для определения смещений местного времени относительно UTC для соответствующего часового пояса. Во многих случаях эти компоненты "VTIMEZONE" могут быть больше по количеству октетов, чем события или задачи, которые их используют. Однако в настоящее время iCalendar требует, чтобы все объекты iCalendar (компоненты "VCALENDAR"), которые ссылаются на часовой пояс через его идентификатор, также включали соответствующий компонент "VTIMEZONE". Это приводит к неэффективности протокола CalDAV, поскольку большие объёмы данных "VTIMEZONE" постоянно передаются, а в большинстве своём эти определения часовых поясов не меняются. Это особенно проблематично для мобильных или ограниченных устройств с ограниченной пропускной способностью сети, процессором и энергоресурсами. Набор стандартных определений часовых поясов доступен в базе данных часовых поясов [RFC6557], размещённой IANA. Эта база данных предоставляет «сырые» данные для определений часовых поясов, и их можно преобразовать в компоненты iCalendar "VTIMEZONE" для использования в приложениях iCalendar, а также преобразовать в другие форматы для использования другими приложениями (например, файлы "zoneinfo", часто встречающиеся в операционных системах на базе Unix). Доступен новый протокол службы распространения данных часовых поясов [RFC7808], который позволяет приложениям iCalendar получать эти стандартные определения часовых поясов своевременно и точно, вместо того чтобы полагаться на возможно редкие системные обновления данных часовых поясов, которые часто приводят к несоответствию данных календаря и, следовательно, к пропущенным встречам между пользователями календарей. Ещё одно преимущество службы распространения данных часовых поясов состоит в том, что она обеспечивает единую «ссылку» для стандартных данных часовых поясов, которую клиенты и серверы CalDAV могут использовать, чтобы «договориться» о стандартных определениях часовых поясов и таким образом устранить необходимость обмена данными для них.
This specification defines a new mode of operation for CalDAV clients and servers that allows them to exchange iCalendar data without the need to send "VTIMEZONE" components for known, standard time zone definitions. This can significantly reduce the amount of data that needs to be sent between client and server, giving rise to performance and efficiency improvements for each of them.
Это определение задаёт новый режим работы клиентов и серверов CalDAV, позволяющий им обмениваться данными iCalendar без необходимости передавать компоненты "VTIMEZONE" для известных стандартных определений часовых поясов. Это может существенно сократить объём данных, передаваемых между клиентом и сервером, что повышает производительность и эффективность каждого из них.

3. Time Zones by Reference
3. Часовые пояса по ссылке
Note that this specification only defines changes to iCalendar data sent or received via the CalDAV protocol (both [RFC4791] and [RFC6638], and extensions). These changes do not apply to other means of exchanging calendar data, such as scheduling mechanisms based on the iCalendar Transport-Independent Interoperability Protocol (iTIP) [RFC5546], e.g., the iCalendar Message-Based Interoperability Protocol (iMIP) [RFC6047], or other methods.
Отметим, что настоящее определение описывает только изменения данных iCalendar, передаваемых или принимаемых через протокол CalDAV (как [RFC4791], так и [RFC6638], и расширения). Эти изменения не применяются к другим способам обмена данными календаря, таким как механизмы планирования на основе протокола iTIP (iCalendar Transport-Independent Interoperability Protocol) [RFC5546], например iMIP (iCalendar Message-Based Interoperability Protocol) [RFC6047], или иные методы.
3.1. New Server Behavior
3.1. Новое поведение сервера
3.1.1. Server Advertised Capability
3.1.1. Возможность, объявляемая сервером
A server that supports this specification MUST include "calendar-no- timezone" as a field in the DAV response header field from an "OPTIONS" request on a calendar home collection (see Section 6.2.1 of [RFC4791]) or calendar collection (see Section 4.2 of [RFC4791]). Clients MUST check for the presence of that field in the DAV response header field before changing their behavior as per Section 4.
Сервер, поддерживающий настоящее определение, ДОЛЖЕН включать "calendar-no-timezone" как поле в поле заголовка ответа DAV на запрос "OPTIONS" к домашней коллекции календаря (см. раздел 6.2.1 [RFC4791]) или коллекции календаря (см. раздел 4.2 [RFC4791]). Клиенты ДОЛЖНЫ проверять наличие этого поля в поле заголовка ответа DAV, прежде чем изменять своё поведение в соответствии с разделом 4.
3.1.2. Associated Time Zone Data Distribution Service
3.1.2. Связанная служба распространения данных часовых поясов
A CalDAV server supporting this specification MUST have one or more associated time zone distribution services [RFC7808] that provide data for the set of time zones known to the server and expected to be used by clients. A CalDAV server advertises the set of time zone distribution services it makes use of via a CALDAV:timezone-service- set WebDAV property (see Section 5.1) defined on calendar home collections. Clients can use the time zone data distribution services listed in this property to fetch current time zone definitions for the time zone identifiers in iCalendar data retrieved from the server. This allows clients to keep their "built-in" time zone definitions up to date. It also allows clients to use an "on- demand" model for populating their local time zone definition cache, only fetching a time zone definition when it is first seen in calendar data, potentially allowing for savings on storage space by eliminating the need to store time zone data that is not currently being used.
Сервер CalDAV, поддерживающий настоящее определение, ДОЛЖЕН иметь одну или несколько связанных служб распространения данных часовых поясов [RFC7808], которые предоставляют данные для набора часовых поясов, известных серверу и предполагаемых к использованию клиентами. Сервер CalDAV объявляет набор используемых им служб распространения данных часовых поясов через свойство WebDAV CALDAV:timezone-service-set (см. раздел 5.1), определённое на домашних коллекциях календаря. Клиенты могут использовать службы распространения данных часовых поясов, перечисленные в этом свойстве, для получения текущих определений часовых поясов для идентификаторов часовых поясов в данных iCalendar, полученных с сервера. Это позволяет клиентам поддерживать свои «встроенные» определения часовых поясов в актуальном состоянии. Это также позволяет клиентам использовать модель «по требованию» для заполнения локального кэша определений часовых поясов, получая определение часового пояса только тогда, когда оно впервые встречается в данных календаря, что потенциально позволяет экономить место в хранилище за счёт устранения необходимости хранить данные часовых поясов, которые в настоящее время не используются.
When making use of the time zone data distribution services advertised by a CalDAV server, clients MUST follow all the requirements of the time zone data distribution service protocol [RFC7808], taking care to refresh time zone data in a timely fashion.
При использовании служб распространения данных часовых поясов, объявленных сервером CalDAV, клиенты ДОЛЖНЫ соблюдать все требования протокола службы распространения данных часовых поясов [RFC7808], уделяя внимание своевременному обновлению данных часовых поясов.
3.1.3. Time Zones in CalDAV Responses
3.1.3. Часовые пояса в ответах CalDAV
Servers MUST support the HTTP "CalDAV-Timezones" request header field (see Section 7.1). If the "CalDAV-Timezones" request header field has the value "T" on any HTTP request that returns iCalendar data, then the server MUST include all the appropriate "VTIMEZONE" components in the iCalendar data (all the ones that are referenced by "TZID" property parameters). If the "CalDAV-Timezones" request header field has the value "F" on any HTTP request that returns iCalendar data, then the server MUST NOT return any "VTIMEZONE" components if the time zone identifier matches one provided by any of the advertised time zone distribution servers (see Section 3.1.2). However, the server MUST return the appropriate "VTIMEZONE" component for each time zone with an identifier not available on the advertised time zone distribution servers. This behavior applies to all HTTP requests on CalDAV resources that return iCalendar data either directly (such as a "GET" request on a calendar object resource), or embedded in a "structured" response such as a DAV:multistatus returned by a "REPORT" or "PROPFIND" request.
Серверы ДОЛЖНЫ поддерживать поле заголовка запроса HTTP "CalDAV-Timezones" (см. раздел 7.1). Если поле заголовка запроса "CalDAV-Timezones" имеет значение "T" в любом HTTP-запросе, возвращающем данные iCalendar, сервер ДОЛЖЕН включить все соответствующие компоненты "VTIMEZONE" в данные iCalendar (все те, на которые ссылаются параметры свойства "TZID"). Если поле заголовка запроса "CalDAV-Timezones" имеет значение "F" в любом HTTP-запросе, возвращающем данные iCalendar, сервер НЕ ДОЛЖЕН возвращать какие-либо компоненты "VTIMEZONE", если идентификатор часового пояса совпадает с предоставленным любым из объявленных серверов распространения данных часовых поясов (см. раздел 3.1.2). Однако сервер ДОЛЖЕН вернуть соответствующий компонент "VTIMEZONE" для каждого часового пояса с идентификатором, недоступным на объявленных серверах распространения данных часовых поясов. Это поведение применяется ко всем HTTP-запросам к ресурсам CalDAV, возвращающим данные iCalendar либо напрямую (например, запрос "GET" к ресурсу объекта календаря), либо встроенными в «структурированный» ответ, такой как DAV:multistatus, возвращаемый запросом "REPORT" или "PROPFIND".
Observation and experiments have shown that, in the vast majority of cases, CalDAV clients have typically ignored time zone definitions in data received from servers, and instead make use of their own "built- in" definitions for the corresponding time zone identifier. This means that it is reasonable for CalDAV servers to unilaterally decide not to send "VTIMEZONE" components for standard time zones that clients are expected to have "built-in" (i.e., IANA time zones). Thus, in the absence of a "CalDAV-Timezones" request header field, servers advertising the "calendar-no-timezone" capability MAY opt to not send standard "VTIMEZONE" components. Servers that do that will need to provide an administrator configuration setting to override the new default behavior based on client "User-Agent" request header field values, or other suitable means of identifying the client software in use.
Наблюдения и эксперименты показали, что в подавляющем большинстве случаев клиенты CalDAV обычно игнорировали определения часовых поясов в данных, полученных от серверов, и вместо этого использовали свои собственные «встроенные» определения для соответствующего идентификатора часового пояса. Это означает, что серверы CalDAV вправе в одностороннем порядке решить не отправлять компоненты "VTIMEZONE" для стандартных часовых поясов, которые, как ожидается, будут «встроены» у клиентов (т. е. часовых поясов IANA). Таким образом, при отсутствии поля заголовка запроса "CalDAV-Timezones" серверы, объявляющие возможность "calendar-no-timezone", МОГУТ не отправлять стандартные компоненты "VTIMEZONE". Серверам, которые так поступают, потребуется предусмотреть параметр конфигурации администратора для переопределения нового поведения по умолчанию на основе значений поля заголовка запроса "User-Agent" клиента или других подходящих средств идентификации используемого клиентского программного обеспечения.
3.1.4. Time Zones in CalDAV Requests
3.1.4. Часовые пояса в запросах CalDAV
In addition to servers not sending time zone definitions to clients in iCalendar data, this specification also allows clients to not include time zone definitions when sending iCalendar data to the server, as per Section 4. This behavior applies to all HTTP requests on CalDAV resources that include iCalendar data either directly in the request body (such as a "PUT" request on a calendar object resource) or embedded in a "structured" request body such as a one used by a "PROPPATCH" request.
Помимо того, что серверы не отправляют клиентам определения часовых поясов в данных iCalendar, настоящее определение также позволяет клиентам не включать определения часовых поясов при отправке данных iCalendar на сервер, как описано в разделе 4. Это поведение применяется ко всем HTTP-запросам к ресурсам CalDAV, которые содержат данные iCalendar либо непосредственно в теле запроса (например, запрос "PUT" к ресурсу объекта календаря), либо встроенными в «структурированное» тело запроса, такое как тело, используемое запросом "PROPPATCH".
Note that, as per Section 4, clients might send time zone definitions for time zones that are not advertised by any of the time zone services associated with the server. In that case, servers have various choices:
Отметим, что, как описано в разделе 4, клиенты могут отправлять определения часовых поясов для часовых поясов, не объявленных ни одной из служб часовых поясов, связанных с сервером. В этом случае у серверов есть несколько вариантов:
1. Servers can preserve the original time zone definitions in the iCalendar data sent by the client, so that those can be returned to that client or other clients who subsequently request iCalendar data.
1. Серверы могут сохранять исходные определения часовых поясов в данных iCalendar, отправленных клиентом, чтобы их можно было вернуть этому клиенту или другим клиентам, которые впоследствии запросят данные iCalendar.
2. Servers can refuse to accept any unknown/nonstandard time zones -- in which case, they MUST reject the HTTP request containing such data using a WebDAV precondition code of CALDAV:valid-timezone.
2. Серверы могут отказываться принимать любые неизвестные/нестандартные часовые пояса — в этом случае они ДОЛЖНЫ отклонить HTTP-запрос, содержащий такие данные, используя код предусловия WebDAV CALDAV:valid-timezone.
3. Servers can, with appropriate knowledge, map the unknown/ nonstandard time zone to a standard time zone definition that accurately matches the one supplied by the client. In doing so, servers will need to rewrite the iCalendar data to make use of the new standard time zone identifier chosen by the mapping procedure. Any subsequent request to fetch the calendar data would see the new time zone identifier in the calendar data. Note there is one important situation where this remapping is not appropriate: an attendee's copy of an event. In that case, the original time zone definition needs to be preserved as the organizer's calendar user agent will expect to see that in any iTIP [RFC5546] replies sent by the attendee.
3. Серверы могут при наличии соответствующих знаний сопоставить неизвестный/нестандартный часовой пояс стандартному определению часового пояса, которое точно соответствует предоставленному клиентом. При этом серверам потребуется переписать данные iCalendar, чтобы использовать новый идентификатор стандартного часового пояса, выбранный процедурой сопоставления. Любой последующий запрос на получение данных календаря увидит новый идентификатор часового пояса в данных календаря. Отметим одну важную ситуацию, когда такое переназначение неуместно: копия события у участника. В этом случае исходное определение часового пояса необходимо сохранить, поскольку пользовательский агент календаря организатора будет ожидать увидеть его в любых ответах iTIP [RFC5546], отправленных участником.
3.1.5. Support of Time Zone Identifiers in WebDAV Properties
3.1.5. Поддержка идентификаторов часовых поясов в свойствах WebDAV
CalDAV defines a CALDAV:calendar-timezone WebDAV property that is used by clients to set a default time zone for the server to use when doing time-based queries on calendar data (see Section 5.3.2 of [RFC4791]). The content of that WebDAV property is an iCalendar "VTIMEZONE" component. This specification defines a new CALDAV:calendar-timezone-id WebDAV property that allows the default time zone to be set via its time zone identifier, rather than providing the full "VTIMEZONE" component (see Section 5.2). This WebDAV property MUST be present on all resources that also support the CALDAV:calendar-timezone WebDAV property. Its value MUST match the value of the "TZID" iCalendar property in the "VTIMEZONE" component in the CALDAV:calendar-timezone WebDAV property on the same resource. The server MUST accept clients that set either the CALDAV:calendar-timezone or the CALDAV:calendar-timezone-id, and it MUST adjust the value of the alternate property to reflect any changes. That is, if a client sets the CALDAV:calendar-timezone-id WebDAV property value to "America/New_York", then the server will return the full "VTIMEZONE" data for that time zone in the CALDAV:calendar-timezone WebDAV property.
CalDAV определяет свойство WebDAV CALDAV:calendar-timezone, которое используется клиентами для задания часового пояса по умолчанию, который сервер должен использовать при выполнении запросов к данным календаря на основе времени (см. раздел 5.3.2 [RFC4791]). Содержимым этого свойства WebDAV является компонент iCalendar "VTIMEZONE". Настоящее определение вводит новое свойство WebDAV CALDAV:calendar-timezone-id, которое позволяет задать часовой пояс по умолчанию через его идентификатор часового пояса, а не предоставлять полный компонент "VTIMEZONE" (см. раздел 5.2). Это свойство WebDAV ДОЛЖНО присутствовать на всех ресурсах, которые также поддерживают свойство WebDAV CALDAV:calendar-timezone. Его значение ДОЛЖНО совпадать со значением свойства iCalendar "TZID" в компоненте "VTIMEZONE" в свойстве WebDAV CALDAV:calendar-timezone на том же ресурсе. Сервер ДОЛЖЕН принимать клиентов, которые устанавливают либо CALDAV:calendar-timezone, либо CALDAV:calendar-timezone-id, и он ДОЛЖЕН корректировать значение альтернативного свойства, чтобы отразить любые изменения. То есть, если клиент устанавливает значение свойства WebDAV CALDAV:calendar-timezone-id в "America/New_York", то сервер вернёт полные данные "VTIMEZONE" для этого часового пояса в свойстве WebDAV CALDAV:calendar-timezone.
If a client attempts to update the CALDAV:calendar-timezone-id with a value that does not correspond to a time zone that is known to the server, the server MUST reject the property update using a CALDAV:valid-timezone pre-condition error. In such cases, clients MAY repeat the request using the CALDAV:calendar-timezone instead, and provide the full iCalendar data for the time zone being set.
Если клиент пытается обновить CALDAV:calendar-timezone-id значением, которое не соответствует часовому поясу, известному серверу, сервер ДОЛЖЕН отклонить обновление свойства, используя ошибку предусловия CALDAV:valid-timezone. В таких случаях клиенты МОГУТ повторить запрос, используя вместо этого CALDAV:calendar-timezone, и предоставить полные данные iCalendar для устанавливаемого часового пояса.
3.1.6. Support of Time Zone Identifiers in CALDAV:calendar-query REPORT
3.1.6. Поддержка идентификаторов часовых поясов в CALDAV:calendar-query REPORT
CalDAV calendar query reports support a CALDAV:timezone XML element that is used by clients to set a specific time zone for the server to use when doing time-based queries on calendar data (see Sections 7.3 and 9.8 of [RFC4791]). The content of that XML element is an iCalendar "VTIMEZONE" component. This specification defines a new CALDAV:timezone-id XML element that can be used as an alternative to the CALDAV:timezone XML element; it allows a specific time zone to be set via its time zone identifier, rather than providing the full "VTIMEZONE" component (see Section 6.2). Servers MUST support a client's ability to provide a time zone identifier for use in a calendar query "REPORT" using this new element.
Отчёты запроса календаря CalDAV поддерживают элемент XML CALDAV:timezone, который используется клиентами для задания конкретного часового пояса, который сервер должен использовать при выполнении запросов к данным календаря на основе времени (см. разделы 7.3 и 9.8 [RFC4791]). Содержимым этого элемента XML является компонент iCalendar "VTIMEZONE". Настоящее определение вводит новый элемент XML CALDAV:timezone-id, который можно использовать как альтернативу элементу XML CALDAV:timezone; он позволяет задать конкретный часовой пояс через его идентификатор часового пояса, а не предоставлять полный компонент "VTIMEZONE" (см. раздел 6.2). Серверы ДОЛЖНЫ поддерживать возможность клиента предоставлять идентификатор часового пояса для использования в "REPORT" запроса календаря с помощью этого нового элемента.
If a client attempts use of a CALDAV:timezone-id XML element with a value that does not correspond to a time zone that is known to the server, the server MUST reject the request with a CALDAV:valid- timezone precondition error. In such cases, clients MAY repeat the request using the CALDAV:timezone XML element instead, and provide the full iCalendar data for the time zone being used.
Если клиент пытается использовать элемент XML CALDAV:timezone-id со значением, которое не соответствует часовому поясу, известному серверу, сервер ДОЛЖЕН отклонить запрос с ошибкой предусловия CALDAV:valid-timezone. В таких случаях клиенты МОГУТ повторить запрос, используя вместо этого элемент XML CALDAV:timezone, и предоставить полные данные iCalendar для используемого часового пояса.
4. New Client Behavior
4. Новое поведение клиента
When a server advertises the "calendar-no-timezone" field in a DAV response header field (as per Section 3.1.1):
Когда сервер объявляет поле "calendar-no-timezone" в поле заголовка ответа DAV (в соответствии с разделом 3.1.1):
1. Clients SHOULD include an HTTP "CalDAV-Timezones" request header field with a value of "F" to ensure that the CalDAV server does not include "VTIMEZONE" components in any iCalendar data returned in a response (see Section 3.1.3), for those time zones whose identifier is one provided by any of the advertised time zone distribution servers (see Section 3.1.2). In this case, clients will have to retrieve the missing standard time zone definitions either from their own cache of standard time zones or from the set of time zone distribution servers advertised by the CalDAV server (see Section 3.1.2).
1. Клиентам СЛЕДУЕТ включать поле заголовка запроса HTTP "CalDAV-Timezones" со значением "F", чтобы гарантировать, что сервер CalDAV не включает компоненты "VTIMEZONE" в любые данные iCalendar, возвращаемые в ответе (см. раздел 3.1.3), для тех часовых поясов, идентификатор которых предоставлен любым из объявленных серверов распространения данных часовых поясов (см. раздел 3.1.2). В этом случае клиентам придётся получать недостающие определения стандартных часовых поясов либо из собственного кэша стандартных часовых поясов, либо из набора серверов распространения данных часовых поясов, объявленных сервером CalDAV (см. раздел 3.1.2).
2. Clients can include an HTTP "CalDAV-Timezones" request header field with a value of "T" to ensure that the CalDAV server does include all "VTIMEZONE" components in any iCalendar data returned in a response (see Section 3.1.3).
2. Клиенты могут включать поле заголовка запроса HTTP "CalDAV-Timezones" со значением "T", чтобы гарантировать, что сервер CalDAV включает все компоненты "VTIMEZONE" в любые данные iCalendar, возвращаемые в ответе (см. раздел 3.1.3).
3. Clients can expect servers not to include standard time zone definitions in any iCalendar data they receive from the server, if there is no "CalDAV-Timezones" request header field in the HTTP request. Clients MUST retrieve standard time zone definitions either from its own cache of standard time zones or from the set of time zone distribution servers advertised by the CalDAV server (see Section 3.1.2).
3. Клиенты могут ожидать, что серверы не будут включать определения стандартных часовых поясов в любые данные iCalendar, полученные от сервера, если в HTTP-запросе нет поля заголовка запроса "CalDAV-Timezones". Клиенты ДОЛЖНЫ получать определения стандартных часовых поясов либо из собственного кэша стандартных часовых поясов, либо из набора серверов распространения данных часовых поясов, объявленных сервером CalDAV (см. раздел 3.1.2).
4. Clients SHOULD remove standard time zone definitions from iCalendar data they send to the server, provided the corresponding time zone identifier is one available on any of the server's advertised time zone distribution servers (see Section 3.1.2).
4. Клиентам СЛЕДУЕТ удалять определения стандартных часовых поясов из данных iCalendar, отправляемых на сервер, при условии, что соответствующий идентификатор часового пояса доступен на любом из объявленных сервером серверов распространения данных часовых поясов (см. раздел 3.1.2).
5. Clients MUST send time zone definitions in iCalendar data for any time zone identifiers not available via any of the server's advertised time zone distribution servers. Clients MUST be prepared for the server to reject such data or map the time zone to one in the set of standard time zones provided by the server's associated time zone services (as per Section 3.1.4).
5. Клиенты ДОЛЖНЫ отправлять определения часовых поясов в данных iCalendar для любых идентификаторов часовых поясов, недоступных через любые из объявленных сервером серверов распространения данных часовых поясов. Клиенты ДОЛЖНЫ быть готовы к тому, что сервер отклонит такие данные или сопоставит часовой пояс одному из набора стандартных часовых поясов, предоставляемых связанными службами часовых поясов сервера (в соответствии с разделом 3.1.4).
6. Clients SHOULD make use of the CALDAV:calendar-timezone-id WebDAV property (see Section 3.1.5) and CalDAV:timezone-id XML element (see Section 3.1.6) for specifying default and specific time zones to use in calendar queries executed by the server.
6. Клиентам СЛЕДУЕТ использовать свойство WebDAV CALDAV:calendar-timezone-id (см. раздел 3.1.5) и элемент XML CalDAV:timezone-id (см. раздел 3.1.6) для указания часовых поясов по умолчанию и конкретных часовых поясов, которые следует использовать в запросах календаря, выполняемых сервером.

8. Security Considerations
8. Вопросы безопасности
This specifications adds time zone data distribution service [RFC7808] servers into the overall calendaring and scheduling client/ server architecture, as a critical component, and thus adds a new vector of attack against such systems. As such, administrators of CalDAV servers SHOULD ensure that any advertised time zone distribution servers are protected by a level of security commensurate with all the other components in the system.
Настоящее определение добавляет серверы службы распространения данных часовых поясов [RFC7808] в общую архитектуру клиент/сервер календарей и планирования в качестве критически важного компонента и, таким образом, добавляет новый вектор атак на такие системы. Поэтому администраторам серверов CalDAV СЛЕДУЕТ обеспечивать, чтобы любые объявленные серверы распространения данных часовых поясов были защищены уровнем безопасности, соизмеримым со всеми другими компонентами системы.
Besides the above point, this specification does not introduce any new security concerns beyond those addressed in CalDAV [RFC4791], iCalendar [RFC5545], and the time zone data distribution service [RFC7808].
Помимо вышесказанного, настоящее определение не вносит каких-либо новых проблем безопасности сверх тех, что рассмотрены в CalDAV [RFC4791], iCalendar [RFC5545] и службе распространения данных часовых поясов [RFC7808].
9. Privacy Considerations
9. Соображения конфиденциальности
The privacy recommendations in Section 9 of the time zone data distribution service specification [RFC7808] SHOULD be used to ensure that details of clients' interactions with CalDAV servers are not exposed to potential network observers. Note that since events can be delivered to a calendar user from an outside source (e.g., using iTIP [RFC5546]), and an attacker could create a calendar event with, e.g., a time zone identifier that is fake or rarely used and that could be used to monitor the calendar user's activity and interaction with others, this specification increases the importance of using the mitigations of privacy issues discussed in [RFC7808].
Рекомендации по конфиденциальности в разделе 9 спецификации службы распространения данных часовых поясов [RFC7808] СЛЕДУЕТ использовать, чтобы гарантировать, что сведения о взаимодействии клиентов с серверами CalDAV не раскрываются потенциальным сетевым наблюдателям. Отметим, что поскольку события могут доставляться пользователю календаря из внешнего источника (например, с помощью iTIP [RFC5546]), и злоумышленник может создать событие календаря с, например, поддельным или редко используемым идентификатором часового пояса, который может использоваться для отслеживания активности пользователя календаря и его взаимодействия с другими, настоящее определение повышает важность использования мер по устранению проблем конфиденциальности, обсуждаемых в [RFC7808].
