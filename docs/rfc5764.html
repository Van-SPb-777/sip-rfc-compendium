Abstract
Аннотация
This document describes a Datagram Transport Layer Security (DTLS) extension to establish keys for Secure RTP (SRTP) and Secure RTP Control Protocol (SRTCP) flows. DTLS keying happens on the media path, independent of any out-of-band signalling channel present.
В настоящем документе описано расширение протокола датаграммной безопасности транспортного уровня (DTLS) для установления ключей потоков защищённого протокола реального времени (SRTP) и защищённого протокола управления RTP (SRTCP). Ключи DTLS устанавливаются на медиапути независимо от любого внешнего канала сигнализации.

1. Introduction
1. Введение
The Secure RTP (SRTP) profile [RFC3711] can provide confidentiality, message authentication, and replay protection to RTP data and RTP Control (RTCP) traffic. SRTP does not provide key management functionality, but instead depends on external key management to exchange secret master keys, and to negotiate the algorithms and parameters for use with those keys.
Профиль защищённого протокола реального времени (SRTP) [RFC3711] может обеспечивать конфиденциальность, аутентификацию сообщений и защиту от повторного воспроизведения для данных RTP и трафика протокола управления RTP (RTCP). SRTP не обеспечивает функции управления ключами, а вместо этого зависит от внешнего управления ключами для обмена секретными мастер-ключами и согласования алгоритмов и параметров для использования с этими ключами.
Datagram Transport Layer Security (DTLS) [RFC4347] is a channel security protocol that offers integrated key management, parameter negotiation, and secure data transfer. Because DTLS data transfer protocol is generic, it is less highly optimized for use with RTP than is SRTP, which has been specifically tuned for that purpose.
Протокол датаграммной безопасности транспортного уровня (DTLS) [RFC4347] — это протокол защиты канала, который обеспечивает интегрированное управление ключами, согласование параметров и защищённую передачу данных. Поскольку протокол передачи данных DTLS является универсальным, он менее оптимизирован для использования с RTP, чем SRTP, который был специально настроен для этой цели.
This document describes DTLS-SRTP, a SRTP extension for DTLS that combines the performance and encryption flexibility benefits of SRTP with the flexibility and convenience of DTLS-integrated key and association management. DTLS-SRTP can be viewed in two equivalent ways: as a new key management method for SRTP, and a new RTP-specific data format for DTLS.
В настоящем документе описан DTLS-SRTP — расширение SRTP для DTLS, которое сочетает преимущества производительности и гибкости шифрования SRTP с гибкостью и удобством интегрированного в DTLS управления ключами и ассоциациями. DTLS-SRTP можно рассматривать двумя эквивалентными способами: как новый метод управления ключами для SRTP и как новый формат данных, специфичный для RTP, для DTLS.
The key points of DTLS-SRTP are that:
Ключевые положения DTLS-SRTP таковы:
o application data is protected using SRTP,
o данные приложения защищаются с помощью SRTP,
o the DTLS handshake is used to establish keying material, algorithms, and parameters for SRTP,
o рукопожатие DTLS используется для установления ключевого материала, алгоритмов и параметров для SRTP,
o a DTLS extension is used to negotiate SRTP algorithms, and
o расширение DTLS используется для согласования алгоритмов SRTP, и
o other DTLS record-layer content types are protected using the ordinary DTLS record format.
o другие типы содержимого уровня записей DTLS защищаются с использованием обычного формата записей DTLS.

3. Overview of DTLS-SRTP Operation
3. Обзор работы DTLS-SRTP
DTLS-SRTP is defined for point-to-point media sessions, in which there are exactly two participants. Each DTLS-SRTP session contains a single DTLS association (called a "connection" in TLS jargon), and either two SRTP contexts (if media traffic is flowing in both directions on the same host/port quartet) or one SRTP context (if media traffic is only flowing in one direction). All SRTP traffic flowing over that pair in a given direction uses a single SRTP context. A single DTLS-SRTP session only protects data carried over a single UDP source and destination port pair.
DTLS-SRTP определён для двухточечных медиасеансов, в которых имеется ровно два участника. Каждый сеанс DTLS-SRTP содержит одну ассоциацию DTLS (в терминологии TLS называемую «соединением») и либо два контекста SRTP (если медиатрафик идёт в обоих направлениях на одной четвёрке узел/порт), либо один контекст SRTP (если медиатрафик идёт только в одном направлении). Весь трафик SRTP, идущий через эту пару в заданном направлении, использует один контекст SRTP. Один сеанс DTLS-SRTP защищает данные, передаваемые только через одну пару портов UDP-источника и получателя.
The general pattern of DTLS-SRTP is as follows. For each RTP or RTCP flow the peers do a DTLS handshake on the same source and destination port pair to establish a DTLS association. Which side is the DTLS client and which side is the DTLS server must be established via some out-of-band mechanism such as SDP. The keying material from that handshake is fed into the SRTP stack. Once that association is established, RTP packets are protected (becoming SRTP) using that keying material.
Общая схема DTLS-SRTP следующая. Для каждого потока RTP или RTCP участники выполняют рукопожатие DTLS на одной и той же паре портов источника и получателя, чтобы установить ассоциацию DTLS. Какая сторона является клиентом DTLS, а какая — сервером DTLS, должно устанавливаться с помощью некоторого внешнего механизма, например SDP. Ключевой материал из этого рукопожатия передаётся в стек SRTP. После установления этой ассоциации пакеты RTP защищаются (становятся SRTP) с использованием этого ключевого материала.
RTP and RTCP traffic is usually sent on two separate UDP ports. When symmetric RTP [RFC4961] is used, two bidirectional DTLS-SRTP sessions are needed, one for the RTP port, one for the RTCP port. When RTP flows are not symmetric, four unidirectional DTLS-SRTP sessions are needed (for inbound and outbound RTP, and inbound and outbound RTCP).
Трафик RTP и RTCP обычно передаётся по двум отдельным портам UDP. Когда используется симметричный RTP [RFC4961], необходимы два двунаправленных сеанса DTLS-SRTP: один для порта RTP, другой для порта RTCP. Когда потоки RTP несимметричны, необходимы четыре однонаправленных сеанса DTLS-SRTP (для входящего и исходящего RTP, а также входящего и исходящего RTCP).
Symmetric RTP [RFC4961] is the case in which there are two RTP sessions that have their source and destination ports and addresses reversed, in a manner similar to the way that a TCP connection uses its ports. Each participant has an inbound RTP session and an outbound RTP session. When symmetric RTP is used, a single DTLS-SRTP session can protect both of the RTP sessions. It is RECOMMENDED that symmetric RTP be used with DTLS-SRTP.
Симметричный RTP [RFC4961] — это случай, когда имеются два сеанса RTP, у которых порты и адреса источника и получателя поменяны местами, подобно тому, как TCP-соединение использует свои порты. У каждого участника есть входящий сеанс RTP и исходящий сеанс RTP. При использовании симметричного RTP один сеанс DTLS-SRTP может защищать оба сеанса RTP. РЕКОМЕНДУЕТСЯ использовать симметричный RTP с DTLS-SRTP.
RTP and RTCP traffic MAY be multiplexed on a single UDP port [RFC5761]. In this case, both RTP and RTCP packets may be sent over the same DTLS-SRTP session, halving the number of DTLS-SRTP sessions needed. This improves the cryptographic performance of DTLS, but may cause problems when RTCP and RTP are subject to different network treatment (e.g., for bandwidth reservation or scheduling reasons).
Трафик RTP и RTCP МОЖЕТ мультиплексироваться на одном порту UDP [RFC5761]. В этом случае пакеты RTP и RTCP могут передаваться по одному сеансу DTLS-SRTP, что вдвое сокращает число необходимых сеансов DTLS-SRTP. Это повышает криптографическую производительность DTLS, но может создавать проблемы, когда RTCP и RTP подвергаются разной обработке в сети (например, по причинам резервирования полосы пропускания или планирования).
Between a single pair of participants, there may be multiple media sessions. There MUST be a separate DTLS-SRTP session for each distinct pair of source and destination ports used by a media session (though the sessions can share a single DTLS session and hence amortize the initial public key handshake!). A DTLS-SRTP session may be indicated by an external signaling protocol like SIP. When the signaling exchange is integrity- protected (e.g., when SIP Identity protection via digital signatures is used), DTLS-SRTP can leverage this integrity guarantee to provide complete security of the media stream. A description of how to indicate DTLS-SRTP sessions in SIP and SDP [RFC4566], and how to authenticate the endpoints using fingerprints can be found in [RFC5763].
Между одной парой участников может существовать несколько медиасеансов. ДОЛЖЕН существовать отдельный сеанс DTLS-SRTP для каждой отдельной пары портов источника и получателя, используемой медиасеансом (хотя сеансы могут совместно использовать один сеанс DTLS и тем самым амортизировать начальное рукопожатие с открытым ключом!). Сеанс DTLS-SRTP может указываться внешним протоколом сигнализации, например SIP. Когда обмен сигнализацией защищён целостностью (например, когда используется защита идентичности SIP с помощью цифровых подписей), DTLS-SRTP может использовать эту гарантию целостности для обеспечения полной безопасности медиапотока. Описание того, как указывать сеансы DTLS-SRTP в SIP и SDP [RFC4566] и как аутентифицировать конечные точки с помощью отпечатков, можно найти в [RFC5763].
In a naive implementation, when there are multiple media sessions, there is a new DTLS session establishment (complete with public key cryptography) for each media channel. For example, a videophone may be sending both an audio stream and a video stream, each of which would use a separate DTLS session establishment exchange, which would proceed in parallel. As an optimization, the DTLS-SRTP implementation SHOULD use the following strategy: a single DTLS association is established, and all other DTLS associations wait until that connection is established before proceeding with their handshakes. This strategy allows the later sessions to use DTLS session resumption, which allows the amortization of the expensive public key cryptography operations over multiple DTLS handshakes.
В наивной реализации при наличии нескольких медиасеансов для каждого медиаканала устанавливается новый сеанс DTLS (полностью с криптографией открытого ключа). Например, видеотелефон может отправлять и аудиопоток, и видеопоток, каждый из которых использовал бы отдельный обмен установления сеанса DTLS, и эти обмены шли бы параллельно. В качестве оптимизации реализация DTLS-SRTP СЛЕДУЕТ использовать следующую стратегию: устанавливается одна ассоциация DTLS, а все остальные ассоциации DTLS ждут установления этого соединения, прежде чем приступать к своим рукопожатиям. Эта стратегия позволяет более поздним сеансам использовать возобновление сеанса DTLS, что позволяет амортизировать дорогостоящие операции криптографии открытого ключа на нескольких рукопожатиях DTLS.
The SRTP keys used to protect packets originated by the client are distinct from the SRTP keys used to protect packets originated by the server. All of the RTP sources originating on the client for the same channel use the same SRTP keys, and similarly, all of the RTP sources originating on the server for the same channel use the same SRTP keys. The SRTP implementation MUST ensure that all of the synchronization source (SSRC) values for all of the RTP sources originating from the same device over the same channel are distinct, in order to avoid the "two-time pad" problem (as described in Section 9.1 of RFC 3711). Note that this is not an issue for separate media streams (on different host/port quartets) that use independent keying material even if an SSRC collision occurs.
Ключи SRTP, используемые для защиты пакетов, созданных клиентом, отличаются от ключей SRTP, используемых для защиты пакетов, созданных сервером. Все источники RTP, происходящие на клиенте для одного и того же канала, используют одни и те же ключи SRTP, и аналогично все источники RTP, происходящие на сервере для одного и того же канала, используют одни и те же ключи SRTP. Реализация SRTP ДОЛЖНА гарантировать, что все значения синхронизирующего источника (SSRC) для всех источников RTP, происходящих от одного устройства по одному каналу, различаются, чтобы избежать проблемы «двукратной подкладки» (как описано в разделе 9.1 RFC 3711). Отметим, что это не проблема для отдельных медиапотоков (на разных четвёрках узел/порт), использующих независимый ключевой материал, даже если происходит коллизия SSRC.
4. DTLS Extensions for SRTP Key Establishment
4. Расширения DTLS для установления ключей SRTP
4.1. The use_srtp Extension
4.1. Расширение use_srtp
In order to negotiate the use of SRTP data protection, clients include an extension of type "use_srtp" in the DTLS extended client hello. This extension MUST only be used when the data being transported is RTP or RTCP [RFC3550]. The "extension_data" field of this extension contains the list of acceptable SRTP protection profiles, as indicated below. Servers that receive an extended hello containing a "use_srtp" extension can agree to use SRTP by including an extension of type "use_srtp", with the chosen protection profile in the extended server hello. This process is shown below.
Чтобы согласовать использование защиты данных SRTP, клиенты включают расширение типа "use_srtp" в расширенное приветствие клиента DTLS. Это расширение ДОЛЖНО использоваться только тогда, когда передаваемые данные являются RTP или RTCP [RFC3550]. Поле "extension_data" этого расширения содержит список приемлемых профилей защиты SRTP, как указано ниже. Серверы, получающие расширенное приветствие, содержащее расширение "use_srtp", могут согласиться использовать SRTP, включив расширение типа "use_srtp" с выбранным профилем защиты в расширенное приветствие сервера. Этот процесс показан ниже.
Client Server ClientHello + use_srtp --------> ServerHello + use_srtp Certificate* ServerKeyExchange* CertificateRequest* <-------- ServerHelloDone Certificate* ClientKeyExchange CertificateVerify* [ChangeCipherSpec] Finished --------> [ChangeCipherSpec] <-------- Finished SRTP packets <-------> SRTP packets
Client Server ClientHello + use_srtp --------> ServerHello + use_srtp Certificate* ServerKeyExchange* CertificateRequest* <-------- ServerHelloDone Certificate* ClientKeyExchange CertificateVerify* [ChangeCipherSpec] Finished --------> [ChangeCipherSpec] <-------- Finished SRTP packets <-------> SRTP packets
Note that '*' indicates messages that are not always sent in DTLS. The CertificateRequest, client and server Certificates, and CertificateVerify will be sent in DTLS-SRTP.
Отметим, что символ '*' обозначает сообщения, которые не всегда отправляются в DTLS. В DTLS-SRTP будут отправляться сообщения CertificateRequest, сертификаты клиента и сервера, а также CertificateVerify.
Once the "use_srtp" extension is negotiated, the RTP or RTCP application data is protected solely using SRTP. Application data is never sent in DTLS record-layer "application_data" packets. Rather, complete RTP or RTCP packets are passed to the DTLS stack, which passes them to the SRTP stack, which protects them appropriately. Note that if RTP/RTCP multiplexing [RFC5761] is in use, this means that RTP and RTCP packets may both be passed to the DTLS stack. Because the DTLS layer does not process the packets, it does not need to distinguish them. The SRTP stack can use the procedures of [RFC5761] to distinguish RTP from RTCP.
После согласования расширения "use_srtp" данные приложения RTP или RTCP защищаются исключительно с помощью SRTP. Данные приложения никогда не передаются в пакетах "application_data" уровня записей DTLS. Вместо этого полные пакеты RTP или RTCP передаются в стек DTLS, который передаёт их в стек SRTP, а тот защищает их надлежащим образом. Отметим, что если используется мультиплексирование RTP/RTCP [RFC5761], это означает, что пакеты RTP и RTCP могут оба передаваться в стек DTLS. Поскольку уровень DTLS не обрабатывает пакеты, ему не нужно их различать. Стек SRTP может использовать процедуры [RFC5761] для различения RTP и RTCP.
When the "use_srtp" extension is in effect, implementations must not place more than one application data "record" per datagram. (This is only meaningful from the perspective of DTLS because SRTP is inherently oriented towards one payload per packet, but this is stated purely for clarification.)
Когда расширение "use_srtp" действует, реализации не должны размещать более одной "записи" данных приложения в датаграмме. (Это имеет смысл только с точки зрения DTLS, поскольку SRTP по своей природе ориентирован на одну полезную нагрузку на пакет, но это сказано исключительно для разъяснения.)
Data other than RTP/RTCP (i.e., TLS control messages) MUST use ordinary DTLS framing and MUST be placed in separate datagrams from SRTP data. A DTLS-SRTP handshake establishes one or more SRTP crypto contexts; however, they all have the same SRTP Protection Profile and Master Key Identifier (MKI), if any. MKIs are used solely to distinguish the keying material and protection profiles between distinct handshakes, for instance, due to rekeying. When an MKI is established in a DTLS-SRTP session, it MUST apply for all of the SSRCs within that session -- though a single endpoint may negotiate multiple DTLS-SRTP sessions due, for instance, to forking. (Note that RFC 3711 allows packets within the same session but with different SSRCs to use MKIs differently; in contrast, DTLS-SRTP requires that MKIs and the keys that they are associated with have the same meaning and are uniform across the entire SRTP session.)
Данные, отличные от RTP/RTCP (то есть управляющие сообщения TLS), ДОЛЖНЫ использовать обычное кадрирование DTLS и ДОЛЖНЫ размещаться в отдельных датаграммах от данных SRTP. Рукопожатие DTLS-SRTP устанавливает один или несколько криптографических контекстов SRTP; однако все они имеют один и тот же профиль защиты SRTP и идентификатор мастер-ключа (MKI), если он есть. MKI используются исключительно для различения ключевого материала и профилей защиты между различными рукопожатиями, например из-за смены ключей. Когда MKI устанавливается в сеансе DTLS-SRTP, он ДОЛЖЕН применяться ко всем SSRC в этом сеансе, хотя одна конечная точка может согласовать несколько сеансов DTLS-SRTP, например из-за разветвления. (Отметим, что RFC 3711 позволяет пакетам в одном сеансе, но с разными SSRC использовать MKI по-разному; напротив, DTLS-SRTP требует, чтобы MKI и связанные с ними ключи имели одинаковое значение и были единообразны во всём сеансе SRTP.)

4.1.3. srtp_mki value
4.1.3. Значение srtp_mki
The srtp_mki value MAY be used to indicate the capability and desire to use the SRTP Master Key Identifier (MKI) field in the SRTP and SRTCP packets. The MKI field indicates to an SRTP receiver which key was used to protect the packet that contains that field. The srtp_mki field contains the value of the SRTP MKI which is associated with the SRTP master keys derived from this handshake. Each SRTP session MUST have exactly one master key that is used to protect packets at any given time. The client MUST choose the MKI value so that it is distinct from the last MKI value that was used, and it SHOULD make these values unique for the duration of the TLS session.

When a DTLS-SRTP session is protecting RTP, the SRTCP keys derived from the DTLS handshake are not needed and are discarded. When a DTLS-SRTP session is protecting RTCP, the SRTP keys derived from the DTLS handshake are not needed and are discarded.
Когда и RTCP, и RTP используют одни и те же порты источника и получателя, необходимы ключи как SRTP, так и SRTCP. В противном случае существуют два сеанса DTLS-SRTP, один из которых защищает пакеты RTP, а другой — пакеты RTCP; каждый сеанс DTLS-SRTP защищает часть сеанса SRTP, проходящую через одну пару транспортных адресов источника/получателя, как показано на рисунке 2, независимо от того, какие SSRC используются на этой паре. Когда сеанс DTLS-SRTP защищает RTCP, ключи SRTP, выведенные из рукопожатия DTLS, не нужны и отбрасываются.

4.3. Key Scope
4.3. Область действия ключей
Because of the possibility of packet reordering, DTLS-SRTP implementations SHOULD store multiple SRTP keys sets during a rekey in order to avoid the need for receivers to drop packets for which they lack a key.
Из-за возможности переупорядочивания пакетов реализации DTLS-SRTP СЛЕДУЕТ хранить несколько наборов ключей SRTP во время смены ключей, чтобы получателям не приходилось отбрасывать пакеты, для которых у них нет ключа.
4.4. Key Usage Limitations
4.4. Ограничения использования ключей
The maximum_lifetime parameter in the SRTP protection profile indicates the maximum number of packets that can be protected with each single encryption and authentication key. (Note that, since RTP and RTCP are protected with independent keys, those protocols are counted separately for the purposes of determining when a key has reached the end of its lifetime.) Each profile defines its own limit. When this limit is reached, a new DTLS session SHOULD be used to establish replacement keys, and SRTP implementations MUST NOT use the existing keys for the processing of either outbound or inbound traffic.
Параметр maximum_lifetime в профиле защиты SRTP указывает максимальное число пакетов, которые можно защитить каждым отдельным ключом шифрования и аутентификации. (Отметим, что поскольку RTP и RTCP защищаются независимыми ключами, эти протоколы считаются отдельно при определении того, что ключ достиг конца своего срока службы.) Каждый профиль определяет свой собственный предел. Когда этот предел достигнут, СЛЕДУЕТ использовать новый сеанс DTLS для установления замещающих ключей, а реализации SRTP НЕ ДОЛЖНЫ использовать существующие ключи для обработки ни исходящего, ни входящего трафика.
5. Use of RTP and RTCP over a DTLS-SRTP Channel
5. Использование RTP и RTCP по каналу DTLS-SRTP
5.1. Data Protection
5.1. Защита данных
Once the DTLS handshake has completed, the peers can send RTP or RTCP over the newly created channel. We describe the transmission process first followed by the reception process.
После завершения рукопожатия DTLS участники могут отправлять RTP или RTCP по только что созданному каналу. Сначала мы описываем процесс передачи, а затем процесс приёма.
Within each RTP session, SRTP processing MUST NOT take place before the DTLS handshake completes.
В каждом сеансе RTP обработка SRTP НЕ ДОЛЖНА выполняться до завершения рукопожатия DTLS.
5.1.1. Transmission
5.1.1. Передача
DTLS and TLS define a number of record content types. In ordinary TLS/DTLS, all data is protected using the same record encoding and mechanisms. When the mechanism described in this document is in effect, this is modified so that data written by upper-level protocol clients of DTLS is assumed to be RTP/RTP and is encrypted using SRTP rather than the standard TLS record encoding.
DTLS и TLS определяют ряд типов содержимого записей. В обычных TLS/DTLS все данные защищаются с использованием одного и того же кодирования записей и механизмов. Когда действует механизм, описанный в настоящем документе, это изменяется так, что данные, записываемые клиентами протокола верхнего уровня DTLS, считаются RTP/RTP и шифруются с помощью SRTP, а не стандартного кодирования записей TLS.
When a user of DTLS wishes to send an RTP packet in SRTP mode, it delivers it to the DTLS implementation as an ordinary application data write (e.g., SSL_write()). The DTLS implementation then invokes the processing described in RFC 3711, Sections 3 and 4. The resulting SRTP packet is then sent directly on the wire as a single datagram with no DTLS framing. This provides an encapsulation of the data that conforms to and interoperates with SRTP. Note that the RTP sequence number rather than the DTLS sequence number is used for these packets.
Когда пользователь DTLS желает отправить пакет RTP в режиме SRTP, он передаёт его реализации DTLS как обычную запись данных приложения (например, SSL_write()). Реализация DTLS затем вызывает обработку, описанную в разделах 3 и 4 RFC 3711. Полученный пакет SRTP затем отправляется напрямую по сети как одна датаграмма без кадрирования DTLS. Это обеспечивает инкапсуляцию данных, которая соответствует SRTP и взаимодействует с ним. Отметим, что для этих пакетов используется порядковый номер RTP, а не порядковый номер DTLS.
5.1.2. Reception
5.1.2. Приём
When DTLS-SRTP is used to protect an RTP session, the RTP receiver needs to demultiplex packets that are arriving on the RTP port. Arriving packets may be of types RTP, DTLS, or STUN [RFC5389]. If these are the only types of packets present, the type of a packet can be determined by looking at its first byte.
Когда DTLS-SRTP используется для защиты сеанса RTP, получателю RTP необходимо демультиплексировать пакеты, поступающие на порт RTP. Поступающие пакеты могут быть типа RTP, DTLS или STUN [RFC5389]. Если это единственные присутствующие типы пакетов, тип пакета можно определить, посмотрев на его первый байт.
The process for demultiplexing a packet is as follows. The receiver looks at the first byte of the packet. If the value of this byte is 0 or 1, then the packet is STUN. If the value is in between 128 and 191 (inclusive), then the packet is RTP (or RTCP, if both RTCP and RTP are being multiplexed over the same destination port). If the value is between 20 and 63 (inclusive), the packet is DTLS. This process is summarized in Figure 3.

Если значение находится в диапазоне от 128 до 191 (включительно), то пакет — RTP (или RTCP, если и RTCP, и RTP мультиплексируются на одном порту получателя). Because DTLS operates on the host/port quartet, the DTLS association will still complete correctly, with the foreign host/port pair being used, to distinguish the associations. However, in RTP the source host/port is not used and sessions are identified by the destination host/port and the SSRC. Thus, some mechanism is needed to determine which SSRCs correspond to which DTLS associations. The following method SHOULD be used. For each local host/port pair, the DTLS-SRTP implementation maintains a table listing all the SSRCs it knows about and the DTLS-SRTP associations they correspond to. Initially, this table is empty. When an SRTP packet is received for a given RTP endpoint (destination IP/port pair), the following procedure is used:
Поскольку DTLS работает с четвёркой узел/порт, ассоциация DTLS всё равно завершится корректно, причём для различения ассоциаций используется пара внешний узел/порт. Однако в RTP узел/порт источника не используется, а сеансы идентифицируются по узлу/порту получателя и SSRC. Таким образом, необходим некоторый механизм для определения того, какие SSRC соответствуют каким ассоциациям DTLS. СЛЕДУЕТ использовать следующий метод. Для каждой локальной пары узел/порт реализация DTLS-SRTP поддерживает таблицу со списком всех известных ей SSRC и соответствующих им ассоциаций DTLS-SRTP. Изначально эта таблица пуста. При получении пакета SRTP для данной конечной точки RTP (пары IP-адрес/порт получателя) используется следующая процедура:
1. If the SSRC is already known for that endpoint, then the corresponding DTLS-SRTP association and its keying material is used to decrypt and verify the packet.
1. Если SSRC уже известен для этой конечной точки, то для расшифровки и проверки пакета используется соответствующая ассоциация DTLS-SRTP и её ключевой материал.
2. If the SSRC is not known, then the receiver tries to decrypt it with the keying material corresponding to each DTLS-SRTP association for that endpoint.
2. Если SSRC неизвестен, получатель пытается расшифровать пакет с помощью ключевого материала, соответствующего каждой ассоциации DTLS-SRTP для этой конечной точки.
3. If the decryption and verification succeeds (the authentication tag verifies), then an entry is placed in the table mapping the SSRC to that association.
3. Если расшифровка и проверка успешны (тег аутентификации проверен), в таблицу помещается запись, сопоставляющая SSRC с этой ассоциацией.
4. If the decryption and verification fails, then the packet is silently discarded.
4. Если расшифровка и проверка не удались, то пакет молча отбрасывается.
5. When a DTLS-SRTP association is closed (for instance, because the fork is abandoned), its entries MUST be removed from the mapping table.
5. Когда ассоциация DTLS-SRTP закрывается (например, потому что разветвление прекращено), её записи ДОЛЖНЫ быть удалены из таблицы сопоставления.
The average cost of this algorithm for a single SSRC is the decryption and verification time of a single packet times the number of valid DTLS-SRTP associations corresponding to a single receiving port on the host. In practice, this means the number of forks; so in the case shown in Figure 4, that would be two. This cost is only incurred once for any given SSRC, since afterwards that SSRC is placed in the map table and looked up immediately. As with normal RTP, this algorithm allows new SSRCs to be introduced by the source at any time. They will automatically be mapped to the correct DTLS association.
Средняя стоимость этого алгоритма для одного SSRC равна времени расшифровки и проверки одного пакета, умноженному на число допустимых ассоциаций DTLS-SRTP, соответствующих одному принимающему порту на узле. На практике это означает число разветвлений; так, в случае, показанном на рисунке 4, это число равно двум. Эта стоимость возникает только один раз для любого данного SSRC, поскольку после этого SSRC помещается в таблицу сопоставления и ищется немедленно. Как и в обычном RTP, этот алгоритм позволяет источнику вводить новые SSRC в любое время. Они будут автоматически сопоставлены правильной ассоциации DTLS.
Note that this algorithm explicitly allows multiple SSRCs to be sent from the same address/port pair. One way in which this can happen is an RTP translator. This algorithm will automatically assign the SSRCs to the correct associations. Note that because the SRTP packets are cryptographically protected, such a translator must either share keying material with one endpoint or refrain from modifying the packets in a way which would cause the integrity check to fail. This is a general property of SRTP and is not specific to DTLS-SRTP.
Отметим, что этот алгоритм явно допускает отправку нескольких SSRC с одной и той же пары адрес/порт. Один из способов, которым это может произойти, — RTP-транслятор. Этот алгоритм автоматически назначит SSRC правильным ассоциациям. Отметим, что поскольку пакеты SRTP криптографически защищены, такой транслятор должен либо разделять ключевой материал с одной конечной точкой, либо воздерживаться от изменения пакетов способом, который привёл бы к сбою проверки целостности. Это общее свойство SRTP, а не особенность DTLS-SRTP.
There are two error cases that should be considered. First, if an SSRC collision occurs, then only the packets from the first source will be processed. When the packets from the second source arrive, the DTLS association with the first source will be used for decryption and verification, which will fail, and the packet will be discarded. This is consistent with [RFC3550], which permits the receiver to keep the packets from one source and discard those from the other. Of course the RFC 3550 SSRC collision detection and handling procedures MUST also be followed.
Следует рассмотреть два случая ошибок. Во-первых, если происходит коллизия SSRC, то обрабатываются только пакеты от первого источника. Когда приходят пакеты от второго источника, для расшифровки и проверки будет использоваться ассоциация DTLS с первым источником, что закончится неудачей, и пакет будет отброшен. Это согласуется с [RFC3550], который разрешает получателю сохранять пакеты от одного источника и отбрасывать пакеты от другого. Разумеется, процедуры обнаружения и обработки коллизий SSRC из RFC 3550 также ДОЛЖНЫ соблюдаться.
Second, there may be cases where a malfunctioning source is sending corrupt packets that cannot be decrypted and verified. In this case, the SSRC will never be entered into the mapping table because the decryption and verification always fails. Receivers MAY keep records of unmapped SSRCs that consistently fail decryption and verification and abandon attempts to process them once they reach some limit. That limit MUST be large enough to account for the effects of transmission errors. Entries MUST be pruned from this table when the relevant SRTP endpoint is deleted (e.g., the call ends) and SHOULD time out faster than that (we do not offer a hard recommendation but 10 to 30 seconds seems appropriate) in order to allow for the possibility that the peer implementation has been corrected.
Во-вторых, могут быть случаи, когда неисправный источник отправляет повреждённые пакеты, которые невозможно расшифровать и проверить. В этом случае SSRC никогда не будет внесён в таблицу сопоставления, поскольку расшифровка и проверка всегда завершаются неудачей. Получатели МОГУТ вести учёт несопоставленных SSRC, которые постоянно не проходят расшифровку и проверку, и прекращать попытки их обработки после достижения некоторого предела. Этот предел ДОЛЖЕН быть достаточно большим, чтобы учитывать эффекты ошибок передачи. Записи ДОЛЖНЫ удаляться из этой таблицы, когда соответствующая конечная точка SRTP удаляется (например, вызов завершается), и СЛЕДУЕТ, чтобы они истекали раньше (мы не даём жёсткой рекомендации, но 10–30 секунд представляются подходящими), чтобы учесть возможность исправления реализации участника.
5.2. Rehandshake and Rekey
5.2. Повторное рукопожатие и смена ключей
Rekeying in DTLS is accomplished by performing a new handshake over the existing DTLS channel. That is, the handshake messages are protected by the existing DTLS cipher suite. This handshake can be performed in parallel with data transport, so no interruption of the data flow is required. Once the handshake is finished, the newly derived set of keys is used to protect all outbound packets, both DTLS and SRTP.
Смена ключей в DTLS выполняется путём нового рукопожатия по существующему каналу DTLS. То есть сообщения рукопожатия защищаются существующим набором шифров DTLS. Это рукопожатие может выполняться параллельно с передачей данных, поэтому прерывание потока данных не требуется. После завершения рукопожатия новый выведенный набор ключей используется для защиты всех исходящих пакетов, как DTLS, так и SRTP.
Because of packet reordering, packets protected by the previous set of keys can appear on the wire after the handshake has completed. To compensate for this fact, receivers SHOULD maintain both sets of keys for some time in order to be able to decrypt and verify older packets. The keys should be maintained for the duration of the maximum segment lifetime (MSL).
Из-за переупорядочивания пакетов пакеты, защищённые предыдущим набором ключей, могут появиться в сети после завершения рукопожатия. Чтобы компенсировать это, получателям СЛЕДУЕТ некоторое время хранить оба набора ключей, чтобы иметь возможность расшифровать и проверить более старые пакеты. Ключи следует хранить в течение максимального времени жизни сегмента (MSL).
If an MKI is used, then the receiver should use the corresponding set of keys to process an incoming packet. If no matching MKI is present, the packet MUST be rejected. Otherwise, when a packet arrives after the handshake completed, a receiver SHOULD use the newly derived set of keys to process that packet unless there is an MKI. (If the packet was protected with the older set of keys, this fact will become apparent to the receiver as an authentication failure will occur.) If the authentication check on the packet fails and no MKI is being used, then the receiver MAY process the packet with the older set of keys. If that authentication check indicates that the packet is valid, the packet should be accepted; otherwise, the packet MUST be discarded and rejected. Receivers MAY use the SRTP packet sequence number to aid in the selection of keys. After a packet has been received and authenticated with the new key set, any packets with sequence numbers that are greater will also have been protected with the new key set.
Если используется MKI, получателю следует использовать соответствующий набор ключей для обработки входящего пакета. Если подходящий MKI отсутствует, пакет ДОЛЖЕН быть отвергнут. В противном случае, когда пакет приходит после завершения рукопожатия, получателю СЛЕДУЕТ использовать новый выведенный набор ключей для обработки этого пакета, если только нет MKI. (Если пакет был защищён старым набором ключей, получатель обнаружит это по сбою аутентификации.) Если проверка аутентификации пакета не удалась и MKI не используется, получатель МОЖЕТ обработать пакет с помощью старого набора ключей. Если эта проверка аутентификации показывает, что пакет действителен, пакет следует принять; в противном случае пакет ДОЛЖЕН быть отброшен и отвергнут. Получатели МОГУТ использовать порядковый номер пакета SRTP для облегчения выбора ключей. После того как пакет получен и аутентифицирован с новым набором ключей, любые пакеты с большими порядковыми номерами также были защищены новым набором ключей.
6. Multi-Party RTP Sessions
6. Многосторонние сеансы RTP
Since DTLS is a point-to-point protocol, DTLS-SRTP is intended only to protect unicast RTP sessions. This does not preclude its use with RTP mixers. For example, a conference bridge may use DTLS-SRTP to secure the communication to and from each of the participants in a conference. However, because each flow between an endpoint and a mixer has its own key, the mixer has to decrypt and then reencrypt the traffic for each recipient.
Поскольку DTLS является двухточечным протоколом, DTLS-SRTP предназначен только для защиты одноадресных сеансов RTP. Это не исключает его использования с микшерами RTP. Например, конференц-мост может использовать DTLS-SRTP для защиты связи с каждым участником конференции и от него. Однако, поскольку каждый поток между конечной точкой и микшером имеет собственный ключ, микшеру приходится расшифровывать, а затем повторно шифровать трафик для каждого получателя.
A future specification may describe methods for sharing a single key between multiple DTLS-SRTP associations thus allowing conferencing systems to avoid the decrypt/reencrypt stage. However, any system in which the media is modified (e.g., for level balancing or transcoding) will generally need to be performed on the plaintext and will certainly break the authentication tag, and therefore will require a decrypt/reencrypt stage.
Будущая спецификация может описать методы совместного использования одного ключа несколькими ассоциациями DTLS-SRTP, что позволит конференц-системам избежать этапа расшифровки/повторного шифрования. Однако любая система, в которой медиа изменяются (например, для выравнивания уровней или транскодирования), обычно должна работать с открытым текстом и непременно нарушит тег аутентификации, а следовательно, потребует этапа расшифровки/повторного шифрования.
7. Security Considerations
7. Вопросы безопасности
The use of multiple data protection framings negotiated in the same handshake creates some complexities, which are discussed here.
Использование нескольких форматов защиты данных, согласованных в одном рукопожатии, создаёт некоторые сложности, которые обсуждаются здесь.
7.1. Security of Negotiation
7.1. Безопасность согласования
One concern here is that attackers might be able to implement a bid- down attack forcing the peers to use ordinary DTLS rather than SRTP. However, because the negotiation of this extension is performed in the DTLS handshake, it is protected by the Finished messages. Therefore, any bid-down attack is automatically detected, which reduces this to a denial-of-service attack -- which can be mounted by any attacker who can control the channel.
Одна из проблем здесь состоит в том, что злоумышленники могут реализовать атаку понижения, вынуждая участников использовать обычный DTLS вместо SRTP. Однако, поскольку согласование этого расширения выполняется в рукопожатии DTLS, оно защищено сообщениями Finished. Поэтому любая атака понижения автоматически обнаруживается, что сводит её к атаке типа «отказ в обслуживании», которую может осуществить любой злоумышленник, контролирующий канал.
7.2. Framing Confusion
7.2. Путаница кадрирования
Because two different framing formats are used, there is concern that an attacker could convince the receiver to treat an SRTP-framed RTP packet as a DTLS record (e.g., a handshake message) or vice versa. This attack is prevented by using different keys for Message Authentication Code (MAC) verification for each type of data. Therefore, this type of attack reduces to being able to forge a packet with a valid MAC, which violates a basic security invariant of both DTLS and SRTP. As an additional defense against injection into the DTLS handshake channel, the DTLS record type is included in the MAC. Therefore, an SRTP record would be treated as an unknown type and ignored. (See Section 6 of [RFC5246].)
Поскольку используются два разных формата кадрирования, есть опасение, что злоумышленник может убедить получателя обрабатывать пакет RTP в кадрировании SRTP как запись DTLS (например, сообщение рукопожатия) или наоборот. Эта атака предотвращается использованием разных ключей для проверки кода аутентификации сообщения (MAC) для каждого типа данных. Поэтому такая атака сводится к возможности подделать пакет с действительным MAC, что нарушает базовый инвариант безопасности как DTLS, так и SRTP. В качестве дополнительной защиты от инъекций в канал рукопожатия DTLS тип записи DTLS включается в MAC. Поэтому запись SRTP была бы обработана как неизвестный тип и проигнорирована. (См. раздел 6 [RFC5246].)
7.3. Sequence Number Interactions
7.3. Взаимодействие порядковых номеров
As described in Section 5.1.1, the SRTP and DTLS sequence number spaces are distinct. This means that it is not possible to unambiguously order a given DTLS control record with respect to an SRTP packet. In general, this is relevant in two situations: alerts and rehandshake.
Как описано в разделе 5.1.1, пространства порядковых номеров SRTP и DTLS различны. Это означает, что невозможно однозначно упорядочить данную управляющую запись DTLS относительно пакета SRTP. В целом это актуально в двух ситуациях: оповещения и повторное рукопожатие.
7.3.1. Alerts
7.3.1. Оповещения
Because DTLS handshake and change_cipher_spec messages share the same sequence number space as alerts, they can be ordered correctly. Because DTLS alerts are inherently unreliable and SHOULD NOT be generated as a response to data packets, reliable sequencing between SRTP packets and DTLS alerts is not an important feature. However, implementations that wish to use DTLS alerts to signal problems with the SRTP encoding SHOULD simply act on alerts as soon as they are received and assume that they refer to the temporally contiguous stream. Such implementations MUST check for alert retransmission and discard retransmitted alerts to avoid overreacting to replay attacks.
Поскольку сообщения рукопожатия DTLS и change_cipher_spec используют то же пространство порядковых номеров, что и оповещения, их можно упорядочивать правильно. Поскольку оповещения DTLS по своей природе ненадёжны и НЕ СЛЕДУЕТ генерировать их в ответ на пакеты данных, надёжное упорядочение между пакетами SRTP и оповещениями DTLS не является важной функцией. Однако реализации, которые желают использовать оповещения DTLS для сигнализации проблем с кодированием SRTP, СЛЕДУЕТ просто действовать по оповещениям сразу после их получения и предполагать, что они относятся к временно непрерывному потоку. Такие реализации ДОЛЖНЫ проверять повторную передачу оповещений и отбрасывать повторно переданные оповещения, чтобы избежать чрезмерной реакции на атаки повторного воспроизведения.
7.3.2. Renegotiation
7.3.2. Повторное согласование
Because the rehandshake transition algorithm specified in Section 5.2 requires trying multiple sets of keys if no MKI is used, it slightly weakens the authentication. For instance, if an n-bit MAC is used and k different sets of keys are present, then the MAC is weakened by log_2(k) bits to n - log_2(k). In practice, since the number of keys used will be very small and the MACs in use are typically strong (the default for SRTP is 80 bits), the decrease in security involved here is minimal.
Поскольку алгоритм перехода при повторном рукопожатии, указанный в разделе 5.2, требует перебора нескольких наборов ключей, если MKI не используется, он немного ослабляет аутентификацию. Например, если используется n-битный MAC и присутствуют k разных наборов ключей, то MAC ослабляется на log_2(k) бит до n - log_2(k). На практике, поскольку число используемых ключей очень мало, а используемые MAC обычно сильны (по умолчанию для SRTP — 80 бит), снижение безопасности здесь минимально.
Another concern here is that this algorithm slightly increases the work factor on the receiver because it needs to attempt multiple validations. However, again, the number of potential keys will be very small (and the attacker cannot force it to be larger) and this technique is already used for rollover counter management, so the authors do not consider this to be a serious flaw.
Другая проблема здесь состоит в том, что этот алгоритм немного увеличивает вычислительную нагрузку на получателя, поскольку ему нужно выполнить несколько проверок. Однако, опять же, число потенциальных ключей будет очень малым (и злоумышленник не может заставить его стать больше), и этот метод уже используется для управления счётчиком переполнения, поэтому авторы не считают это серьёзным недостатком.
7.4. Decryption Cost
7.4. Стоимость расшифровки
An attacker can impose computational costs on the receiver by sending superficially valid SRTP packets that do not decrypt correctly. In general, encryption algorithms are so fast that this cost is extremely small compared to the bandwidth consumed. The SSRC-DTLS mapping algorithm described in Section 5.1.2 gives the attacker a slight advantage here because he can force the receiver to do more then one decryption per packet. However, this advantage is modest because the number of decryptions that the receiver does is limited by the number of associations he has corresponding to a given destination host/port, which is typically quite small. For comparison, a single 1024-bit RSA private key operation (the typical minimum cost to establish a DTLS-SRTP association) is hundreds of times as expensive as decrypting an SRTP packet.
Злоумышленник может навязать получателю вычислительные издержки, отправляя внешне допустимые пакеты SRTP, которые не расшифровываются правильно. В целом алгоритмы шифрования настолько быстры, что эти издержки чрезвычайно малы по сравнению с потребляемой полосой пропускания. Алгоритм сопоставления SSRC-DTLS, описанный в разделе 5.1.2, даёт злоумышленнику небольшое преимущество, поскольку он может заставить получателя выполнять более одной расшифровки на пакет. Однако это преимущество скромно, потому что число расшифровок, выполняемых получателем, ограничено числом ассоциаций, которые он имеет для данного узла/порта получателя, а оно обычно довольно мало. Для сравнения, одна операция с закрытым ключом RSA 1024 бит (типичная минимальная стоимость установления ассоциации DTLS-SRTP) в сотни раз дороже расшифровки пакета SRTP.
Implementations can detect this form of attack by keeping track of the number of SRTP packets that are observed with unknown SSRCs and that fail the authentication tag check. If under such attack, implementations SHOULD prioritize decryption and verification of packets that either have known SSRCs or come from source addresses that match those of peers with which it has DTLS-SRTP associations.
Реализации могут обнаруживать такую форму атаки, отслеживая число пакетов SRTP, наблюдаемых с неизвестными SSRC и не проходящих проверку тега аутентификации. При такой атаке реализациям СЛЕДУЕТ отдавать приоритет расшифровке и проверке пакетов, которые либо имеют известные SSRC, либо приходят с адресов источника, совпадающих с адресами участников, с которыми у неё есть ассоциации DTLS-SRTP.

Appendix A. Overview of DTLS
Приложение A. Обзор DTLS
This section provides a brief overview of Datagram TLS (DTLS) for those who are not familiar with it. DTLS is a channel security protocol based on the well-known Transport Layer Security (TLS) [RFC5246] protocol. Where TLS depends on a reliable transport channel (typically TCP), DTLS has been adapted to support unreliable transports such as UDP. Otherwise, DTLS is nearly identical to TLS and generally supports the same cryptographic mechanisms.
В этом разделе приведён краткий обзор датаграммного TLS (DTLS) для тех, кто с ним не знаком. DTLS — это протокол защиты канала, основанный на хорошо известном протоколе безопасности транспортного уровня (TLS) [RFC5246]. Там, где TLS зависит от надёжного транспортного канала (обычно TCP), DTLS был адаптирован для поддержки ненадёжных транспортов, таких как UDP. В остальном DTLS почти идентичен TLS и обычно поддерживает те же криптографические механизмы.

Appendix B. Performance of Multiple DTLS Handshakes
Приложение B. Производительность множественных рукопожатий DTLS
Standard practice for security protocols such as TLS, DTLS, and SSH, which do inline key management, is to create a separate security association for each underlying network channel (TCP connection, UDP host/port quartet, etc.). This has dual advantages of simplicity and independence of the security contexts for each channel.
Стандартная практика для протоколов безопасности, таких как TLS, DTLS и SSH, которые выполняют встроенное управление ключами, состоит в создании отдельного сеанса защиты для каждого базового сетевого канала (соединения TCP, четвёрки узел/порт UDP и т. д.). Это даёт двойное преимущество: простоту и независимость сеансов защиты для каждого канала.
Three concerns have been raised about the overhead of this strategy in the context of RTP security. The first concern is the additional performance overhead of doing a separate public key operation for each channel. The conventional procedure here (used in TLS and DTLS) is to establish a master context that can then be used to derive fresh traffic keys for new associations. In TLS/DTLS, this is called "session resumption" and can be transparently negotiated between the peers.
В контексте безопасности RTP было поднято три вопроса о накладных расходах этой стратегии. Первый вопрос — дополнительные накладные расходы на производительность из-за отдельной операции с открытым ключом для каждого канала. Обычная процедура здесь (используемая в TLS и DTLS) состоит в установлении мастер-контекста, который затем можно использовать для вывода свежих ключей трафика для новых ассоциаций. В TLS/DTLS это называется «возобновлением сеанса» и может прозрачно согласовываться между участниками.
The second concern is network bandwidth overhead for the establishment of subsequent connections and for rehandshake (for rekeying) for existing connections. In particular, there is a concern that the channels will have very narrow capacity requirements allocated entirely to media that will be overflowed by the rehandshake. Measurements of the size of the rehandshake (with resumption) in TLS indicate that it is about 300-400 bytes if a full selection of cipher suites is offered. (The size of a full handshake is approximately 1-2 kilobytes larger because of the certificate and keying material exchange.)
Второй вопрос — накладные расходы полосы пропускания сети на установление последующих соединений и на повторное рукопожатие (для смены ключей) для существующих соединений. В частности, есть опасение, что каналам будут выделены очень узкие требования к пропускной способности, полностью отведённые под медиа, которые будут переполнены повторным рукопожатием. Измерения размера повторного рукопожатия (с возобновлением) в TLS показывают, что он составляет около 300–400 байт, если предлагается полный набор шифров. (Размер полного рукопожатия примерно на 1–2 килобайта больше из-за обмена сертификатами и ключевым материалом.)
