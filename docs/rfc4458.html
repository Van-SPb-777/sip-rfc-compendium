Abstract
Аннотация
The Session Initiation Protocol (SIP) is often used to initiate connections to applications such as voicemail or interactive voice recognition systems. This specification describes a convention for forming SIP service URIs that request particular services based on redirecting targets from such applications.
Протокол инициирования сессий (SIP) часто используется для инициирования соединений с такими приложениями, как голосовая почта или интерактивные системы распознавания голоса. В этой спецификации описывается соглашение по формированию URI сервисов SIP, которые запрашивают определенные услуги, на основе перенаправления целей из таких приложений.
1. Introduction
1. Введение
Many applications such as Unified Messaging (UM) systems and Interactive Voice Recognition (IVR) systems have been developed out of traditional telephony. They can be used for storing and interacting with voice, video, faxes, email, and instant messaging services. Users often use SIP to initiate communications with these applications. When a SIP call is routed to an application, it is necessary that the application be able to obtain several bits of information from the session initiation message so that it can deliver the desired services.
Многие приложения, такие как системы унифицированного обмена сообщениями (UM) и системы интерактивного распознавания голоса (IVR), были разработаны на основе традиционной телефонии. Их можно использовать для хранения и взаимодействия с голосовыми, видео, факсами, электронной почтой и службами обмена мгновенными сообщениями. Пользователи часто используют SIP для установления связи с этими приложениями. Когда вызов SIP направляется приложению, необходимо, чтобы приложение могло получить несколько битов информации из сообщения инициирования сессий, чтобы оно могло предоставлять желаемые услуги.
For the purpose of this document, we will use UM as the main example, but other applications may use the mechanism defined in this document. The UM needs to know what mailbox should be used and possible reasons for the type of service desired from the UM. Many voicemail systems provide different greetings depending whether the call went to voicemail because the user was busy or because the user did not answer. All of this information can be delivered in existing SIP signaling from the call control that retargets the call to the UM, but there are no conventions for describing how the desired mailbox and the service requested are expressed. It would be possible for every vendor to make this configurable so that any site could get it to work; however, this approach is unrealistic for achieving interoperability among call control, gateway, and unified messaging systems from different vendors. This specification describes a convention for describing this mailbox and service information in the SIP URI so that vendors and operators can build interoperable systems.
В этом документе мы будем использовать единую систему обмена сообщениями в качестве основного примера, но другие приложения могут использовать механизм, определенный в этом документе. Единая система обмена сообщениями должна знать, какой почтовый ящик следует использовать, и возможные причины выбора типа услуги, которую требуется от единой системы обмена сообщениями. Многие системы голосовой почты предоставляют разные приветствия в зависимости от того, перешел ли вызов на голосовую почту, потому что пользователь был занят или потому, что пользователь не ответил. Вся эта информация может быть доставлена ​​в существующей сигнализации SIP от средства управления вызовами, которое перенаправляет вызов в единую систему обмена сообщениями, но не существует соглашений для описания того, как выражаются желаемый почтовый ящик и запрошенная услуга. Каждый поставщик мог бы сделать это настраиваемым, чтобы любой сайт мог заставить его работать; однако этот подход нереален для достижения совместимости между системами управления вызовами, шлюзами и унифицированными сообщениями от разных поставщиков. В этой спецификации описывается соглашение по описанию этого почтового ящика и служебной информации в SIP URI, чтобы поставщики и операторы могли создавать совместимые системы.
If there were no need to interoperate with Time Division Multiplexing (TDM)-based voicemail systems or to allow TDM systems to use VoIP unified messaging systems, this problem would be a little easier to solve. The problem that is introduced in the Voice over IP (VoIP) to TDM case is as follows. The SIP system needs to tell a Public Switched Telephone Network (PSTN) gateway both the subscriber's mailbox identifier (which typically looks like a phone number) and the address of the voicemail system in the TDM network (again a phone number).
Если бы не было необходимости взаимодействовать с системами голосовой почты на основе мультиплексирования с временным разделением (TDM) или разрешать системам TDM использовать системы унифицированного обмена сообщениями VoIP, эту проблему было бы решить немного проще. Проблема, которая возникает в случае передачи голоса по IP (VoIP) в TDM, заключается в следующем. Система SIP должна сообщить шлюзу коммутируемой телефонной сети общего пользования (PSTN) как идентификатор почтового ящика абонента (который обычно выглядит как номер телефона), так и адрес системы голосовой почты в сети TDM (опять же номер телефона).
The question has been asked why the To header cannot be used to specify which mailbox to use. One problem is that the call control proxies cannot modify the To header, and the User Agent Clients (UACs) often set it incorrectly because they do not have information about the subscribers in the domain they are trying to call. This happens because the routing of the call often translates the URI multiple times before it results in an identifier for the desired user that is valid in the namespace that the UM system understands.
Был задан вопрос, почему заголовок To нельзя использовать для указания того, какой почтовый ящик использовать. Одна из проблем заключается в том, что прокси управления вызовами не могут изменить заголовок To, а клиенты пользовательских агентов (UAC) часто устанавливают его неправильно, поскольку у них нет информации об абонентах в домене, которому они пытаются позвонить. Это происходит потому, что при маршрутизации вызова URI часто преобразуется несколько раз, прежде чем в результате будет получен идентификатор нужного пользователя, действительный в пространстве имен, понятном системе единой системы обмена сообщениями.
2. Mechanism (User Agent Server and Proxy)
2. Механизм (сервер пользовательского агента и прокси)
The mechanism works by encoding the information for the desired service in the SIP Request-URI that is sent to the UM system. Two chunks of information are encoded, the first being the target mailbox to use and the second being the SIP status code that caused this retargeting and that indicates the desired service. The userinfo and hostport parts of the Request-URI will identify the voicemail service, the target mailbox can be put in the target parameter, and the reason can be put in the cause parameter. For example, if the proxy wished to use Bob's mailbox because his phone was busy, the URI sent to the UM system could be something like:
Механизм работает путем кодирования информации о желаемой услуге в SIP Request-URI, которая отправляется в систему единой системы обмена сообщениями. Кодируются два фрагмента информации: первый — целевой почтовый ящик, который нужно использовать, а второй — код состояния SIP, вызвавший перенацеливание и указывающий на желаемую услугу. Части userinfo и hostport в Request-URI будут идентифицировать службу голосовой почты, целевой почтовый ящик можно указать в целевом параметре, а причину можно указать в параметре причины. Например, если прокси хочет использовать почтовый ящик Боба, поскольку его телефон занят, URI, отправленный в систему единой системы обмена сообщениями, может иметь следующий вид:
sip:voicemail@example.com;target=bob%40example.com;cause=486
sip:voicemail@example.com;target=bob%40example.com;cause=486
2.1. Target
2.1. Цель
Target is a URI parameter that indicates the address of the retargeting entity: in the context of UM, this can be the mailbox number. For example, in the case of a voicemail system on the PSTN, the user portion will contain the phone number of the voicemail system, while the target will contain the phone number of the subscriber's mailbox.
Target — это параметр URI, который указывает адрес объекта перенацеливания: в контексте единой системы обмена сообщениями это может быть номер почтового ящика. Например, в случае системы голосовой почты в PSTN пользовательская часть будет содержать номер телефона системы голосовой почты, а целевая часть будет содержать номер телефона почтового ящика абонента.

2.2. Причина

Причина — это параметр URI, который используется для указания службы, которую должен выполнить сервер агента пользователя (UAS), получающий сообщение. Определены следующие значения для этого параметра URI:

The mapping to PSTN protocols is important both for gateways that connect the IP network to existing TDM customer's equipment, such as Private Branch Exchanges (PBXs) and voicemail systems, and for gateways that connect the IP network to the PSTN network. Integrated Services Digital Network User Part (ISUP) has signaling encodings for this information that can be treated as roughly equivalent for the purposes here. For this reason, this specification uses the names of Redirecting Reason values defined in ITU-T Q.732.2-5 [8]. In this specification, the Redirecting Reason Values are referred to as "Causes". It should be understood that the term "Cause" has nothing to do with PSTN "Cause values" (as per ITU-T Q.850 [9] and RFC 3398 [5]) but are instead mapped to ITU-T Q.732.2-5 Redirecting Reasons. Since ISUP interoperates with other PSTN networks, such as Q.931 [10] and QSIG [11], using well-known rules, it makes sense to use the ISUP names as the most appropriate superset. If no appropriate mapping to a cause value defined in this specification exists in a network, it would be mapped to 302 "Unconditional". Similarly, if the mapping occurs from one of the causes defined in this specification to a PSTN system that does not have an equivalent reason value, it would be mapped to that network's equivalent of "Unconditional". If a new cause parameter needs to be defined, this specification will have to be updated.
Сопоставление с протоколами PSTN важно как для шлюзов, которые подключают IP-сеть к существующему оборудованию клиента TDM, например, к частным телефонным станциям (PBX) и системам голосовой почты, так и для шлюзов, которые соединяют IP-сеть с сетью PSTN. Пользовательская часть цифровой сети с интеграцией служб (ISUP) имеет кодировки сигнализации для этой информации, которые можно рассматривать как примерно эквивалентные для наших целей. По этой причине в данной спецификации используются имена значений причин перенаправления, определенные в ITU-T Q.732.2-5 [8]. В этой спецификации значения причин перенаправления обозначаются как «Causes». Следует понимать, что термин «Cause» не имеет ничего общего с «Значениями причин» ТфОП (согласно ITU-T Q.850 [9] и RFC 3398 [5]), а вместо этого отображается в ITU-T Q.732.2-5 «Причины перенаправления». Поскольку ISUP взаимодействует с другими сетями PSTN, такими как Q.931 [10] и QSIG [11], используя хорошо известные правила, имеет смысл использовать имена ISUP в качестве наиболее подходящего расширенного набора. Если в сети не существует подходящего сопоставления со значением причины, определенным в этой спецификации, оно будет сопоставлено с 302 «Unconditional». Аналогично, если отображение происходит по одной из причин, определенных в этой спецификации, в систему ТфОП, которая не имеет эквивалентного значения причины, оно будет сопоставлено с эквивалентом этой сети «Unconditional». Если необходимо определить новый параметр причины, эту спецификацию необходимо обновить.
The user portion of the URI SHOULD be used as the address of the voicemail system on the PSTN, while the target SHOULD be mapped to the original redirecting number on the PSTN side.
Пользовательскую часть URI СЛЕДУЕТ использовать в качестве адреса системы голосовой почты в PSTN, а цель СЛЕДУЕТ сопоставить с исходным номером перенаправления на стороне PSTN.
The redirection counters SHOULD be set to one unless additional information is available.
Счетчики перенаправления ДОЛЖНЫ быть установлены на единицу, если не доступна дополнительная информация.
2.3. Retrieving Messages
2.3. Получение сообщений
The UM system MAY use the fact that the From header is the same as the URI target as a hint that the user wishes to retrieve messages.
Система единой системы обмена сообщениями МОЖЕТ использовать тот факт, что заголовок From совпадает с целевым URI, как подсказку о том, что пользователь желает получить сообщения.
3. Interaction with Request History Information
3. Взаимодействие с информацией истории запросов
The Request History mechanism [6] provides more information relating to multiple retargetings. It is reasonable to have systems in which both the information in this specification and the History information are included and one or both are used.
Механизм истории запросов [6] предоставляет дополнительную информацию о множественном ретаргетинге. Разумно иметь системы, в которые включены как информация из этой спецификации, так и информация истории, и используется одна или обе.
History-Info specifies a means of providing the UAS and UAC with information about the retargeting of a request. This information includes the initial Request-URI and any retarget-to URIs. This information is placed in the History-Info header field, which, except where prevented by privacy considerations, is built up as the request progresses and, upon reaching the UAS, is returned in certain responses.
History-Info указывает способ предоставления UAS и UAC информации о перенацеливании запроса. Эта информация включает в себя начальный Request-URI и все URI перенаправления. Эта информация помещается в поле заголовка History-Info, которое, за исключением случаев, когда это запрещено соображениями конфиденциальности, создается по мере выполнения запроса и по достижении UAS возвращается в определенных ответах.
History-Info, when deployed at relevant SIP entities, is intended to provide a comprehensive trace of retargeting for a SIP request, along with the SIP response codes that led to retargeting. History-Info can complement this specification. In particular, when a proxy inserts a URI containing the parameters defined in this specification into the Request-URI of a forwarded request, the proxy can also insert a History-Info header field entry into the forwarded request, and the URI in that entry will incorporate these parameters. Therefore, even if the Request-URI is replaced as a result of rerouting by a downstream proxy, the History-Info header field will still contain these parameters, which may be of use to the UAS. Consequently, UASes that make use of this information may find the information in the History-Info header and/or in the Request-URI, depending on the capability of the proxy to support generation of History-Info or on the behavior of downstream proxies; therefore, applications need to take this into account.
History-Info при развертывании на соответствующих объектах SIP предназначен для обеспечения комплексного отслеживания перенацеливания для запроса SIP, а также кодов ответа SIP, которые привели к перенацеливанию. History-Info может дополнить эту спецификацию. В частности, когда прокси вставляет URI, содержащий параметры, определенные в этой спецификации, в Request-URI пересылаемого запроса, прокси также может вставить запись поля заголовка History-Info в пересылаемый запрос, и URI в этой записи будет включать эти параметры. Таким образом, даже если Request-URI будет заменено в результате перенаправления нисходящим прокси, поле заголовка History-Info все равно будет содержать эти параметры, которые могут быть полезны для БПЛА. Следовательно, БПЛА, которые используют эту информацию, могут найти информацию в заголовке History-Info и/или в Request-URI в зависимости от способности прокси поддерживать генерацию History-Info или от поведения нижестоящих прокси; поэтому приложения должны учитывать это.
4. Limitations of Voicemail URI
4. Ограничения URI голосовой почты
This specification requires the proxy that is requesting the service to understand whether the UM system it is targeting supports the syntax defined in this specification. Today, this information is provided to the proxy by configuration. For practical purposes, this means that the approach is unlikely to work in cases in which the proxy is not configured with information about the UM system or in which the UM is not in the same administrative domain.
Эта спецификация требует, чтобы прокси, запрашивающий услугу, понимал, поддерживает ли система единой системы обмена сообщениями, на которую он нацелен, синтаксис, определенный в этой спецификации. Сегодня эта информация предоставляется прокси по конфигурации. С практической точки зрения это означает, что этот подход вряд ли будет работать в тех случаях, когда прокси не настроен с использованием информации о системе единой системы обмена сообщениями или когда единая система обмена сообщениями не находится в том же административном домене.
This approach only works when the service that the call control wants applied is fairly simple. For example, it does not allow the proxy to express information like "Do not offer to connect to the target's colleague because that address has already been tried".
Этот подход работает только в том случае, если служба, которую хочет применить элемент управления вызовами, достаточно проста. Например, он не позволяет прокси выражать информацию типа «Не предлагать подключиться к коллеге цели, потому что этот адрес уже был опробован».
The limitations discussed in this section are addressed by History- Info [6].
Ограничения, обсуждаемые в этом разделе, рассматриваются в History-Info [6].
5. Syntax
5. Синтаксис
The ABNF[4] grammar for these parameters is shown below. The definitions of pvalue and Status-Code are defined in the ABNF in RFC 3261[1].
Грамматика ABNF[4] для этих параметров показана ниже. Определения pvalue и Status-Code определены в ABNF в RFC 3261[1].
target-param = "target" EQUAL pvalue cause-param = "cause" EQUAL Status-Code
target-param = "target" EQUAL pvalue cause-param = "cause" EQUAL Status-Code
Note that the ABNF requires some characters to be escaped if they occur in the value of the target parameters. For example, the "@" character needs to be escaped.
Обратите внимание, что ABNF требует экранирования некоторых символов, если они встречаются в значении целевых параметров. Например, необходимо экранировать символ «@».

This section provides some example use cases for the solution proposed in this document. For the purpose of this document, UM is used as the main example, but other applications may use this mechanism. В этом разделе представлены некоторые примеры использования решения, предложенного в этом документе. В этом документе в качестве основного примера используется единая система обмена сообщениями, но этот механизм могут использовать и другие приложения. Кроме того, в примерах показан только ретаргетинг услуг по занятости, но их можно легко адаптировать для отображения других форм ретаргетинга.

8. Security Considerations
8. Вопросы безопасности
This document discusses transactions involving at least three parties, which increases the complexity of the privacy issues.
В этом документе обсуждаются транзакции с участием как минимум трех сторон, что усложняет вопросы конфиденциальности.
The new URI parameters defined in this document are generally sent from a Proxy or call control system to a Unified Messaging (UM) system or to a gateway to the PSTN and then to a voicemail system. These new parameters tell the UM what service the proxy wishes to have performed. Just as any message sent from the proxy to the UM needs to be integrity protected, these messages need to be integrity protected to stop attackers from, for example, causing a voicemail meant for a company's CEO to go to an attacker's mailbox. RFC 3261 provides a TLS mechanism suitable for performing this integrity protection.
Новые параметры URI, определенные в этом документе, обычно отправляются из прокси или системы управления вызовами в систему единой системы обмена сообщениями (UM) или на шлюз PSTN, а затем в систему голосовой почты. Эти новые параметры сообщают единой системе обмена сообщениями, какую услугу желает выполнять прокси. Точно так же, как любое сообщение, отправленное с прокси в единую систему обмена сообщениями, должно быть защищено целостности, эти сообщения должны быть защищены целостности, чтобы помешать злоумышленникам, например, заставить голосовое сообщение, предназначенное для генерального директора компании, попасть в почтовый ящик злоумышленника. RFC 3261 предоставляет механизм TLS, подходящий для реализации этой защиты целостности.
The signaling from the Proxy to the UM or gateway will reveal who is calling whom and possibly some information about a user's presence based on whether the call was answered or sent to voicemail. This information can be protected by encrypting the SIP traffic between the Proxy and UM or gateway. Again, RFC 3261 contains mechanisms for accomplishing this using TLS.
Сигнализация от прокси к единой системе обмена сообщениями или шлюзу покажет, кто кому звонит, и, возможно, некоторую информацию о присутствии пользователя в зависимости от того, был ли на вызов дан ответ или он был отправлен на голосовую почту. Эту информацию можно защитить путем шифрования SIP-трафика между прокси и единой системой обмена сообщениями или шлюзом. Опять же, RFC 3261 содержит механизмы для выполнения этого с использованием TLS.
Implementations should implement and use TLS.
Реализации должны реализовывать и использовать TLS.
8.1. Integrity Protection of Forwarding in SIP
8.1. Защита целостности пересылки в SIP
The forwarding of a call in SIP brings up a very strange trust issue. Consider the normal case -- A calls B and the call gets forwarded to C by a network element in B's domain, and then C answers the call. A has called B but ended up talking to C. This scenario may be hard to separate from a man-in-the-middle attack.
Переадресация вызова в SIP вызывает очень странную проблему доверия. Рассмотрим нормальный случай: A звонит B, и вызов пересылается C сетевым элементом в домене B, а затем C отвечает на вызов. А позвонил Б, но в итоге поговорил с С. Этот сценарий может быть трудно отличить от атаки «человек посередине».
There are two possible solutions. One is that B sends back information to A saying don't call me, call C, and signs it as B. The problem is that this solution involves revealing that B has forwarded to C, which B often may not want to do. For example, B may be a work phone that has been forwarded to a mobile or home phone. The user does not want to reveal their mobile or home phone number but, even more importantly, does not want to reveal that they are not in the office.
Есть два возможных решения. Во-первых, B отправляет обратно информацию A, в которой говорится: «Не звоните мне, позвоните C», и подписывает ее как B. Проблема в том, что это решение предполагает раскрытие того, что B переадресовал сообщение C, чего B часто может не захотеть делать. Например, B может быть рабочим телефоном, который был переадресован на мобильный или домашний телефон. Пользователь не хочет раскрывать номер своего мобильного или домашнего телефона, но, что еще более важно, не хочет сообщать, что его нет в офисе.
The other possible solution is that A needs to trust B only to forward to a trusted identity. This requires a hop-by-hop transitive trust such that each hop will only send to a trusted next hop and each hop will only do things that the user at that hop desired. This solution is enforced in SIP using the SIPS URI and TLS-based hop-by-hop security. It protects from an off-axis attack, but if one of the hops is not trustworthy, the call may be diverted to an attacker.
Другое возможное решение состоит в том, что A должен доверять B только для пересылки доверенного идентификатора. Для этого требуется поэтапное транзитивное доверие, при котором каждый переход будет отправлять только доверенному следующему переходу, и каждый переход будет делать только то, что желает пользователь на этом переходе. Это решение реализуется в SIP с использованием URI SIPS и пошаговой безопасности TLS-based. Он защищает от внеосевой атаки, но если один из узлов не заслуживает доверия, вызов может быть перенаправлен злоумышленнику.
Any redirection of a call to an attacker's mailbox is serious. It is trivial for an attacker to make its mailbox seem very much like the real mailbox and forward the messages to the real mailbox so that the fact that the messages have been intercepted or even tampered with escapes detection. Approaches such as the SIPS URL and the History-Info[6] can help protect against these attacks.
Любое перенаправление вызова на почтовый ящик злоумышленника – это серьезно. Злоумышленнику достаточно просто сделать свой почтовый ящик очень похожим на настоящий почтовый ящик и переслать сообщения в реальный почтовый ящик, чтобы тот факт, что сообщения были перехвачены или даже подделаны, ускользнул от обнаружения. Такие подходы, как URL-адрес SIPS и History-Info[6] могут помочь защититься от этих атак.
8.2. Privacy Related Issues on the Second Call Leg
8.2. Проблемы конфиденциальности на втором этапе вызова
In the case where A calls B and gets redirected to C, occasionally people suggest that there is a requirement for the call leg from B to C to be anonymous. The SIP case is not the PSTN, and there is no call leg from B to C; instead, there is a VoIP session between A and C. If A has put a To header field value containing B in the initial invite message, unless something special is done about it, C would see that To header field value. If the person who answers phone C says "I think you dialed the wrong number; who were you trying to reach?", A will probably specify B.
В случае, когда A звонит B и его перенаправляют на C, иногда люди предполагают, что существует требование, чтобы участок вызова от B к C был анонимным. Случай SIP не является PSTN, и нет участка вызова от B до C; вместо этого между A и C существует сессия VoIP. Если A поместил значение поля заголовка To, содержащее B, в исходное сообщение приглашения, если с этим не будет сделано что-то особенное, C увидит это значение поля заголовка To. Если человек, который отвечает на вызов C, говорит: «Я думаю, вы набрали неправильный номер; с кем вы пытались связаться?», A, вероятно, укажет B.
If A does not want C to see that the call was to B, A needs a special relationship with the forwarding Proxy to induce it not to reveal that information. The call should go through an anonymization service that provides session or user level privacy (as described in RFC 3323 [2]) service before going to C. It is not hard to figure out how to meet this requirement, but it is unclear why anyone would want this service.
Если A не хочет, чтобы C видел, что вызов был направлен B, A нуждается в особых отношениях с пересылающим прокси, чтобы заставить его не раскрывать эту информацию. Вызов должен пройти через службу анонимизации, которая обеспечивает конфиденциальность на уровне сессии или пользователя (как описано в RFC 3323 [2]), прежде чем перейти к C. Нетрудно понять, как удовлетворить это требование, но неясно, зачем кому-то нужна эта услуга.
The scenario in which B wants to make sure that C does not see that the call was to B is easier to deal with but a bit weird. The usual argument is that Bill wants to forward his phone to Monica but does not want Monica to find out his phone number. It is hard to imagine that Monica would want to accept all Bill's calls without knowing how to call Bill to complain. The only person Monica will be able to complain to is Hillary, when she tries to call Bill. Several popular web portals will send SMS alert messages about things like stock prices and weather to mobile phone users today. Some of these contain no information about the account on the web portal that initiated them, making it nearly impossible for the mobile phone owner to stop them. This anonymous message forwarding has turned out to be a really bad idea even where no malice is present. Clearly some people are fairly dubious about the need for this, but never mind: let's look at how it is solved. In the general case, the proxy needs to route the call through an anonymization service and everything will be cleaned up. Any anonymization service that performs the "Privacy: Header" Service in RFC 3323 [2] must remove the cause and target URI parameters from the URI. Privacy of the parameters, when they form part of a URI within the History-Info header, is covered in History-Info [6].
Сценарий, в котором B хочет убедиться, что C не видит, что вызов был адресован B, более прост, но немного странен. Обычный аргумент заключается в том, что Билл хочет переслать свой телефон Монике, но не хочет, чтобы Моника узнала его номер телефона. Трудно представить, что Моника захочет принимать все вызовы Билла, не зная, как позвонить Биллу и пожаловаться. Единственный человек, которому Моника сможет пожаловаться, - это Хиллари, когда она пытается позвонить Биллу. Сегодня несколько популярных веб-порталов будут отправлять пользователям мобильных телефонов SMS-сообщения с оповещениями о таких вещах, как цены на акции и погода. Некоторые из них не содержат информации об учетной записи на веб-портале, которая их инициировала, что делает практически невозможным для владельца мобильного телефона остановить их. Эта анонимная пересылка сообщений оказалась очень плохой идеей даже там, где нет никакого злого умысла. Понятно, что некоторые сомневаются в необходимости этого, но не беда: давайте посмотрим, как это решается. В общем случае прокси нужно маршрутизировать вызов через сервис анонимизации и все очистится. Любая служба анонимизации, выполняющая услугу «Конфиденциальность: заголовок» в RFC 3323 [2], должна удалить параметры причины и целевого URI из URI. Конфиденциальность параметров, когда они образуют часть URI в заголовке History-Info, описана в History-Info [6].
This specification does not discuss the security considerations of mapping to a PSTN Gateway. Security implications of mapping to ISUP, for example, are discussed in RFC 3398 [5].
В этой спецификации не обсуждаются вопросы безопасности при подключении к шлюзу PSTN. Например, последствия сопоставления с ISUP для безопасности обсуждаются в RFC 3398 [5].
