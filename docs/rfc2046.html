1. Introduction
1. Введение
The first document in this set, RFC 2045, defines a number of header fields, including Content-Type. The Content-Type field is used to specify the nature of the data in the body of a MIME entity, by giving media type and subtype identifiers, and by providing auxiliary information that may be required for certain media types. After the type and subtype names, the remainder of the header field is simply a set of parameters, specified in an attribute/value notation. The ordering of parameters is not significant.
Первый документ этого набора, RFC 2045, определяет ряд полей заголовка, в том числе Content-Type. Поле Content-Type используется для указания характера данных в теле MIME-объекта путём задания идентификаторов типа и подтипа носителя, а также предоставления вспомогательной информации, которая может потребоваться для отдельных типов носителя. После имён типа и подтипа остаток поля заголовка состоит из набора параметров; каждый параметр начинается с пароля-атрибута, за которым следует «=» и значение параметра, отделённые друг от друга точкой с запятой и, возможно, пробелами.
In general, the top-level media type is used to declare the general type of data, while the subtype specifies a specific format for that type of data. Thus, a media type of "image/xyz" is enough to tell a user agent that the data is an image, even if the user agent has no knowledge of the specific image format "xyz". Such information can be used, for example, to decide whether or not to show a user the raw data from an unrecognized subtype -- such an action might be reasonable for unrecognized subtypes of "text", but not for unrecognized subtypes of "image" or "audio". For this reason, registered subtypes of "text", "image", "audio", and "video" should not contain embedded information that is really of a different type. Such compound formats should be represented using the "multipart" or "application" types.
В общем случае тип носителя верхнего уровня используется для объявления общего типа данных, тогда как подтип задаёт конкретный формат для данных этого типа. Так, типа носителя «image/xyz» достаточно, чтобы сообщить пользовательскому агенту, что данные являются изображением, даже если пользовательский агент не знает конкретного формата изображения «xyz». Такую информацию можно использовать, например, для решения о том, показывать ли пользователю необработанные данные нераспознанного подтипа — такое действие может быть разумным для нераспознанных подтипов «text», но не для нераспознанных подтипов «image» или «audio». По этой причине зарегистрированные подтипы «text», «image», «audio» и «video» не должны содержать встроенной информации, которая на самом деле относится к иному типу. Такие составные форматы следует представлять с использованием типов «multipart» или «application».
Parameters are modifiers of the media subtype, and as such do not fundamentally affect the nature of the content. The set of meaningful parameters depends on the media type and subtype. Most parameters are associated with a single specific subtype. However, a given top-level media type may define parameters which are applicable to any subtype of that type. Parameters may be required by their defining media type or subtype or they may be optional. MIME implementations must also ignore any parameters whose names they do not recognize.
Параметры модифицируют подтип носителя и как таковые не изменяют принципиально природу содержимого. Набор осмысленных параметров зависит от типа и подтипа носителя. Большинство параметров связаны с одним конкретным подтипом. Однако конкретный тип носителя верхнего уровня может определять параметры, применимые к любому подтипу этого типа. Параметры могут требоваться их определением, а могут быть необязательными; определение должно указывать это явно.
MIME's Content-Type header field and media type mechanism has been carefully designed to be extensible, and it is expected that the set of media type/subtype pairs and their associated parameters will grow significantly over time. Several other MIME facilities, such as transfer encodings and "message/external-body" access types, are likely to have new values defined over time. In order to ensure that the set of such values is developed in an orderly, well-specified, and public manner, MIME sets up a registration process which uses the Internet Assigned Numbers Authority (IANA) as a central registry for MIME's various areas of extensibility. The registration process for these areas is described in a companion document, RFC 2048. The initial seven standard top-level media type are defined and described in the remainder of this document.
Поле заголовка Content-Type MIME и механизм типов носителя были тщательно спроектированы как расширяемые, и ожидается, что набор пар «тип/подтип» и связанных с ними параметров существенно возрастёт со временем. Несколько других средств MIME, таких как кодировки переноса и типы доступа «message/external-body», вероятно, также получат новые значения с течением времени. Чтобы обеспечить разработку набора таких значений упорядоченным, хорошо специфицированным и публичным образом, MIME устанавливает процедуру регистрации, использующую Полномочный орган по присвоению номеров Интернета (Internet Assigned Numbers Authority, IANA) в качестве центрального реестра для различных областей расширяемости MIME. Процедура регистрации для этих областей описана в сопровождающем документе RFC 2048.
2. Definition of a Top-Level Media Type
2. Определение типа носителя верхнего уровня
The definition of a top-level media type consists of:
Определение типа носителя верхнего уровня состоит из:
(1) a name and a description of the type, including criteria for whether a particular type would qualify under that type,
(1) наименования и описания типа, включая критерии того, будет ли конкретный тип квалифицироваться под этим типом;
(2) the names and definitions of parameters, if any, which are defined for all subtypes of that type (including whether such parameters are required or optional),
(2) наименований и определений параметров, если таковые имеются, определённых для всех подтипов этого типа (включая указание, являются ли такие параметры обязательными или необязательными);
(3) how a user agent and/or gateway should handle unknown subtypes of this type,
(3) того, как пользовательский агент и/или шлюз должны обрабатывать неизвестные подтипы этого типа;
(4) general considerations on gatewaying entities of this top-level type, if any, and
(4) общие соображения по шлюзованию объектов этого типа верхнего уровня, если таковые имеются, и
(5) any restrictions on content-transfer-encodings for entities of this top-level type.
(5) любых ограничений на кодировки переноса содержимого для объектов этого типа верхнего уровня.
3. Overview Of The Initial Top-Level Media Types
3. Обзор первоначальных типов носителя верхнего уровня
The five discrete top-level media types are:
Пять дискретных типов носителя верхнего уровня:
(1) text -- textual information. The subtype "plain" in particular indicates plain text containing no formatting commands or directives of any sort. Plain text is intended to be displayed "as-is". No special software is required to get the full meaning of the text, aside from support for the indicated character set. Other subtypes are to be used for enriched text in forms where application software may enhance the appearance of the text, but such software must not be required in order to get the general idea of the content. Possible subtypes of "text" thus include any word processor format that can be read without resorting to software that understands the format. In particular, formats that employ embeddded binary formatting information are not considered directly readable. A very simple and portable subtype, "richtext", was defined in RFC 1341, with a further revision in RFC 1896 under the name "enriched".
(1) text — текстовая информация. Подтип «plain» указывает, в частности, на обычный текст, не содержащий команд или директив форматирования какого-либо рода. Обычный текст предназначен для отображения «как есть». Для полного понимания текста не требуется специального программного обеспечения, кроме поддержки указанного набора символов. Другие подтипы используются для обогащённого текста в тех формах, где прикладное программное обеспечение может улучшить внешний вид текста, но такое программное обеспечение НЕ должно требоваться для понимания общего смысла содержимого. Таким образом, возможные подтипы «text» включают любой формат текстового процессора, который может быть прочитан без обращения к программному обеспечению, понимающему этот формат. В частности, форматы, использующие встроенную двоичную информацию форматирования, не считаются непосредственно читаемыми. Очень простой и переносимый подтип «richtext» был определён в RFC 1341 с последующей переработкой в RFC 1896 под именем «enriched».
(2) image -- image data. "Image" requires a display device (such as a graphical display, a graphics printer, or a FAX machine) to view the information. An initial subtype is defined for the widely-used image format JPEG. . subtypes are defined for two widely-used image formats, jpeg and gif.
(2) image — данные изображения. Тип «Image» требует устройства отображения (например, графического дисплея, графического принтера или факсимильного аппарата) для просмотра информации. Первоначально определён подтип для широко используемого формата изображений JPEG. Также определены подтипы для двух широко используемых форматов изображений — jpeg и gif.
(3) audio -- audio data. "Audio" requires an audio output device (such as a speaker or a telephone) to "display" the contents. An initial subtype "basic" is defined in this document.
(3) audio — звуковые данные. «Audio» требует устройства вывода звука (например, динамика или телефона) для «отображения» содержимого. В настоящем документе определён первоначальный подтип «basic».
(4) video -- video data. "Video" requires the capability to display moving images, typically including specialized hardware and software. An initial subtype "mpeg" is defined in this document.
(4) video — видеоданные. «Video» требует способности отображать движущиеся изображения, что обычно предполагает наличие специализированного аппаратного и программного обеспечения. В настоящем документе определён первоначальный подтип «mpeg».
(5) application -- some other kind of data, typically either uninterpreted binary data or information to be processed by an application. The subtype "octet- stream" is to be used in the case of uninterpreted binary data, in which case the simplest recommended action is to offer to write the information into a file for the user. The "PostScript" subtype is also defined for the transport of PostScript material. Other expected uses for "application" include spreadsheets, data for mail-based scheduling systems, and languages for "active" (computational) messaging, and word processing formats that are not directly readable. Note that security considerations may exist for some types of application data, most notably "application/PostScript" and any form of active messaging. These issues are discussed later in this document.
(5) application — данные какого-либо иного рода, обычно либо неинтерпретируемые двоичные данные, либо информация, подлежащая обработке приложением. Подтип «octet-stream» используется в случае неинтерпретируемых двоичных данных; в этом случае простейшим рекомендуемым действием является предложение пользователю записать информацию в файл. Также определён подтип «PostScript» для передачи материалов PostScript. К другим ожидаемым способам применения «application» относятся электронные таблицы, данные для почтовых систем планирования и языки «активного» (вычислительного) обмена сообщениями, а также форматы текстовых процессоров, которые не являются непосредственно читаемыми. Обратите внимание, что для некоторых видов данных приложения могут существовать проблемы безопасности, в особенности для «application/PostScript» и любой формы активного обмена сообщениями. Эти вопросы рассматриваются далее в настоящем документе.
The two composite top-level media types are:
Два составных типа носителя верхнего уровня:
(1) multipart -- data consisting of multiple entities of independent data types. Four subtypes are initially defined, including the basic "mixed" subtype specifying a generic mixed set of parts, "alternative" for representing the same data in multiple formats, "parallel" for parts intended to be viewed simultaneously, and "digest" for multipart entities in which each part has a default type of "message/rfc822".
(1) multipart — данные, состоящие из нескольких объектов независимых типов данных. Первоначально определены четыре подтипа, в том числе базовый подтип «mixed», задающий обобщённый смешанный набор частей, «alternative» для представления одних и тех же данных в нескольких форматах, «parallel» для частей, предназначенных для одновременного просмотра, и «digest» для составных объектов, в которых каждая часть имеет тип по умолчанию «message/rfc822».
(2) message -- an encapsulated message. A body of media type "message" is itself all or a portion of some kind of message object. Such objects may or may not in turn contain other entities. The "rfc822" subtype is used when the encapsulated content is itself an RFC 822 message. The "partial" subtype is defined for partial RFC 822 messages, to permit the fragmented transmission of bodies that are thought to be too large to be passed through transport facilities in one piece. Another subtype, "external-body", is defined for specifying large bodies by reference to an external data source.
(2) message — инкапсулированное сообщение. Тело типа носителя «message» само по себе является всем или частью некоего объекта-сообщения. Такие объекты могут, в свою очередь, содержать или не содержать другие объекты. Подтип «rfc822» используется, когда инкапсулированное содержимое само является сообщением RFC 822. Подтип «partial» определён для частичных сообщений RFC 822, чтобы допустить передачу тела, слишком большого для передачи за один раз, по частям. Подтип «external-body» определён для указания на тело, которое находится где-то в другом месте, чтобы получатель мог получить его по запросу.
It should be noted that the list of media type values given here may be augmented in time, via the mechanisms described above, and that the set of subtypes is expected to grow substantially.
Следует отметить, что приведённый здесь список значений типов носителя может со временем дополняться механизмами, описанными выше, и что набор подтипов, как ожидается, будет существенно расти.
4. Discrete Media Type Values
4. Дискретные значения типов носителя
Five of the seven initial media type values refer to discrete bodies. The content of these types must be handled by non-MIME mechanisms; they are opaque to MIME processors.
Пять из семи первоначальных значений типов носителя относятся к дискретным телам. Содержимое этих типов должно обрабатываться немедийными механизмами — для MIME-процессоров оно непрозрачно.
4.1. Text Media Type
4.1. Тип носителя text
The "text" media type is intended for sending material which is principally textual in form. A "charset" parameter may be used to indicate the character set of the body text for "text" subtypes, notably including the subtype "text/plain", which is a generic subtype for plain text. Plain text does not provide for or allow formatting commands, font attribute specifications, processing instructions, interpretation directives, or content markup. Plain text is seen simply as a linear sequence of characters, possibly interrupted by line breaks or page breaks. Plain text may allow the stacking of several characters in the same position in the text. Plain text in scripts like Arabic and Hebrew may also include facilitites that allow the arbitrary mixing of text segments with opposite writing directions.
Тип носителя «text» предназначен для передачи материала, имеющего преимущественно текстовую форму. Параметр «charset» может использоваться для указания набора символов текста тела для подтипов «text», в частности для подтипа «text/plain», являющегося обобщённым подтипом для обычного текста. Обычный текст не предусматривает и не допускает команд форматирования, спецификаций атрибутов шрифта, инструкций обработки, обработки изображений, звуков или видео, или чего-либо иного, кроме чистого текста. Дополнительно, хотя строки текста должны быть короткими в соответствии с требованиями соответствующего протокола (например, ограничение SMTP в 1000 октетов), для самого типа носителя «text» не требуется содержательная концепция коротких строк.
Beyond plain text, there are many formats for representing what might be known as "rich text". An interesting characteristic of many such representations is that they are to some extent readable even without the software that interprets them. It is useful, then, to distinguish them, at the highest level, from such unreadable data as images, audio, or text represented in an unreadable form. In the absence of appropriate interpretation software, it is reasonable to show subtypes of "text" to the user, while it is not reasonable to do so with most nontextual data. Such formatted textual data should be represented using subtypes of "text".
Помимо обычного текста, существует множество форматов для представления того, что можно назвать «обогащённым текстом». Интересной особенностью многих таких представлений является то, что они в определённой степени читаемы даже без программного обеспечения, интерпретирующего их. Поэтому полезно на самом высоком уровне отличать их от нечитаемых данных, таких как изображения, звук или текст в нечитаемой форме. В дальнейшем изложении термин «текстовый» используется для обозначения материала, который в подходящем окружении отображается на экране или распечатывается, а термин «обогащённый текст» используется для указания на то, что материалу присущи либо команды форматирования, либо он требует специального прикладного программного обеспечения для полного понимания.
4.1.1. Representation of Line Breaks
4.1.1. Представление разрывов строк
The canonical form of any MIME "text" subtype MUST always represent a line break as a CRLF sequence. Similarly, any occurrence of CRLF in MIME "text" MUST represent a line break. Use of CR and LF outside of line break sequences is also forbidden.
Каноническая форма любого подтипа MIME «text» ДОЛЖНА всегда представлять разрыв строки как последовательность CRLF. Аналогично, любое вхождение CRLF в MIME «text» ДОЛЖНО представлять разрыв строки. Использование CR и LF вне последовательностей разрыва строк также запрещено.
This rule applies regardless of format or character set or sets involved.
Это правило применяется независимо от формата, набора символов или используемых наборов.
NOTE: The proper interpretation of line breaks when a body is displayed depends on the media type. In particular, while it is appropriate to treat a line break as a transition to a new line when displaying a "text/plain" body, this treatment is actually incorrect for other subtypes of "text" like "text/enriched" [RFC-1896]. Similarly, whether or not line breaks should be added during display operations is also a function of the media type. It should not be necessary to add any line breaks to display "text/plain" correctly, whereas proper display of "text/enriched" requires the appropriate addition of line breaks.
ПРИМЕЧАНИЕ. Правильная интерпретация разрывов строк при отображении тела зависит от типа носителя. В частности, хотя при отображении тела «text/plain» уместно рассматривать разрыв строки как переход к новой строке, для других подтипов «text», таких как «text/enriched» [RFC-1896], такая трактовка на самом деле неверна. Аналогично то, следует ли добавлять разрывы строк во время операции отображения, также является функцией типа носителя. Для правильного отображения «text/plain» не должно быть необходимости добавлять какие-либо разрывы строк, тогда как правильное отображение «text/enriched» требует соответствующего добавления разрывов строк.
NOTE: Some protocols defines a maximum line length. E.g. SMTP [RFC- 821] allows a maximum of 998 octets before the next CRLF sequence. To be transported by such protocols, data which includes too long segments without CRLF sequences must be encoded with a suitable content-transfer-encoding.
ПРИМЕЧАНИЕ. Некоторые протоколы определяют максимальную длину строки. Например, SMTP [RFC-821] допускает максимум 998 октетов до следующей последовательности CRLF. Для передачи такими протоколами данные, содержащие слишком длинные сегменты без последовательностей CRLF, должны кодироваться подходящей кодировкой переноса содержимого.

4.1.2. Параметр charset
A critical parameter that may be specified in the Content-Type field for "text/plain" data is the character set. This is specified with a "charset" parameter, as in:
Критическим параметром, который может быть указан в поле Content-Type для данных «text/plain», является набор символов. Он задаётся параметром «charset», как в следующем примере:

[не переводится: пример сообщения / граница multipart]
Unlike some other parameter values, the values of the charset parameter are NOT case sensitive. The default character set, which must be assumed in the absence of a charset parameter, is US-ASCII.
В отличие от некоторых других значений параметров, значения параметра charset НЕ чувствительны к регистру. Набор символов по умолчанию, который должен предполагаться при отсутствии параметра charset, — US-ASCII.
The specification for any future subtypes of "text" must specify whether or not they will also utilize a "charset" parameter, and may possibly restrict its values as well. For other subtypes of "text" than "text/plain", the semantics of the "charset" parameter should be defined to be identical to those specified here for "text/plain", i.e., the body consists entirely of characters in the given charset. In particular, definers of future "text" subtypes should pay close attention to the implications of multioctet character sets for their subtype definitions. The charset parameter for subtypes of "text" gives a name of a character set, as "character set" is defined in RFC 2045. The rules regarding line breaks detailed in the previous section must also be observed -- a character set whose definition does not conform to these rules cannot be used in a MIME "text" subtype.
Спецификация любого будущего подтипа «text» должна указывать, будет ли он также использовать параметр «charset», и может, кроме того, ограничивать его значения. Для подтипов «text», отличных от «text/plain», семантика параметра «charset» должна быть определена как идентичная описанной здесь для «text/plain», то есть тело состоит полностью из символов заданного набора символов, а разрывы строк представляются в канонической форме, описанной выше. Набор символов, который не может быть представлен таким образом, не подходит для использования в MIME. Параметр charset для подтипов «text» задаёт имя набора символов в том смысле, в каком «набор символов» определён в RFC 2045. Также должны соблюдаться правила относительно разрывов строк, подробно изложенные в предыдущем разделе: набор символов, определение которого не соответствует этим правилам, не может использоваться в подтипе MIME «text».
An initial list of predefined character set names can be found at the end of this section. Additional character sets may be registered with IANA.
Первоначальный список предопределённых имён наборов символов приведён в конце этого раздела. Дополнительные наборы символов могут быть зарегистрированы в IANA.
Other media types than subtypes of "text" might choose to employ the charset parameter as defined here, but with the CRLF/line break restriction removed. Therefore, all character sets that conform to the general definition of "character set" in RFC 2045 can be registered for MIME use.
Другие типы носителя, помимо подтипов «text», могут использовать параметр charset в том виде, в каком он определён здесь, но без ограничения CRLF/разрыва строк. Поэтому все наборы символов, соответствующие общему определению «набора символов» в RFC 2045, могут быть зарегистрированы для использования в MIME.
Note that if the specified character set includes 8-bit characters and such characters are used in the body, a Content-Transfer-Encoding header field and a corresponding encoding on the data are required in order to transmit the body via some mail transfer protocols, such as SMTP [RFC-821].
Обратите внимание, что если указанный набор символов включает 8-битные символы и такие символы используются в теле, то для передачи тела через некоторые протоколы передачи почты, например SMTP [RFC-821], требуется поле заголовка Content-Transfer-Encoding и соответствующее кодирование данных.
The default character set, US-ASCII, has been the subject of some confusion and ambiguity in the past. Not only were there some ambiguities in the definition, there have been wide variations in practice. In order to eliminate such ambiguity and variations in the future, it is strongly recommended that new user agents explicitly specify a character set as a media type parameter in the Content-Type header field. "US-ASCII" does not indicate an arbitrary 7-bit character set, but specifies that all octets in the body must be interpreted as characters according to the US-ASCII character set. National and application-oriented versions of ISO 646 [ISO-646] are usually NOT identical to US-ASCII, and in that case their use in Internet mail is explicitly discouraged. The omission of the ISO 646 character set from this document is deliberate in this regard. The character set name of "US-ASCII" explicitly refers to the character set defined in ANSI X3.4-1986 [US- ASCII]. The new international reference version (IRV) of the 1991 edition of ISO 646 is identical to US-ASCII. The character set name "ASCII" is reserved and must not be used for any purpose.
Набор символов по умолчанию, US-ASCII, в прошлом был предметом некоторой путаницы и неоднозначности. Не только в определении имелись неясности, но и на практике наблюдались широкие расхождения. Чтобы устранить такие неоднозначности и расхождения в будущем, настоятельно рекомендуется, чтобы новые пользовательские агенты явно указывали набор символов как параметр типа носителя в поле заголовка Content-Type. «US-ASCII» не обозначает произвольный 7-битный набор символов, а указывает, что все октеты в теле должны интерпретироваться как символы в соответствии с набором символов US-ASCII. Национальные и проблемно-ориентированные версии ISO 646 [ISO-646] обычно НЕ идентичны US-ASCII, и в этом случае их использование в интернет-почте явно не рекомендуется. Опускание набора символов ISO 646 из настоящего документа в этом отношении сделано намеренно. Имя набора символов «US-ASCII» явно ссылается на набор символов, определённый в ANSI X3.4-1986 [US-ASCII]. Новая международная эталонная версия (International Reference Version, IRV) редакции 1991 года стандарта ISO 646 идентична US-ASCII. Имя набора символов «ASCII» зарезервировано и не должно использоваться ни для какой цели.
NOTE: RFC 821 explicitly specifies "ASCII", and references an earlier version of the American Standard. Insofar as one of the purposes of specifying a media type and character set is to permit the receiver to unambiguously determine how the sender intended the coded message to be interpreted, assuming anything other than "strict ASCII" as the default would risk unintentional and incompatible changes to the semantics of messages now being transmitted. This also implies that messages containing characters coded according to other versions of ISO 646 than US-ASCII and the 1991 IRV, or using code-switching procedures (e.g., those of ISO 2022), as well as 8bit or multiple octet character encodings MUST use an appropriate character set specification to be consistent with MIME.
ПРИМЕЧАНИЕ. RFC 821 явно указывает «ASCII» и ссылается на более раннюю версию американского стандарта. Поскольку одна из целей указания типа носителя и набора символов состоит в том, чтобы позволить получателю однозначно определить, как отправитель предполагал интерпретировать закодированное сообщение, предположение о чём-либо ином, кроме «строгого ASCII», в качестве значения по умолчанию создало бы риск непреднамеренных и несовместимых изменений в значении сообщения. Сообщения, содержащие символы, закодированные в соответствии с иными версиями ISO 646, чем US-ASCII и IRV 1991 года, или использующие процедуры переключения кодов (например, из ISO 2022), а также 8-битные или многобайтовые кодировки символов, ДОЛЖНЫ использовать соответствующую спецификацию набора символов, чтобы быть совместимыми с MIME.
The complete US-ASCII character set is listed in ANSI X3.4- 1986. Note that the control characters including DEL (0-31, 127) have no defined meaning in apart from the combination CRLF (US-ASCII values 13 and 10) indicating a new line. Two of the characters have de facto meanings in wide use: FF (12) often means "start subsequent text on the beginning of a new page"; and TAB or HT (9) often (though not always) means "move the cursor to the next available column after the current position where the column number is a multiple of 8 (counting the first column as column 0)." Aside from these conventions, any use of the control characters or DEL in a body must either occur
Данные символы составляют полный набор символов US-ASCII в том виде, в каком он определён в ANSI X3.4-1986 [US-ASCII]. Обратите внимание, что управляющие символы, включая DEL (0-31, 127), не имеют определённого значения, кроме комбинации CRLF (значения US-ASCII 13 и 10), указывающей новую строку. Два символа имеют де-факто значения, широко используемые на практике: FF (12) часто означает «начать последующий текст с начала новой страницы»; а TAB или HT (9) часто (хотя и не всегда) служит источником заменяющих пробелов. В целом управляющие символы в тексте не рекомендуется использовать, и они запрещены, если только:
(1) because a subtype of text other than "plain" specifically assigns some additional meaning, or
(1) подтип text, отличный от «plain», специально приписывает им некоторое дополнительное значение, или
(2) within the context of a private agreement between the sender and recipient. Such private agreements are discouraged and should be replaced by the other capabilities of this document.
(2) в контексте частного соглашения между отправителем и получателем. Такие частные соглашения не поощряются и должны быть заменены другими возможностями настоящего документа.
NOTE: An enormous proliferation of character sets exist beyond US- ASCII. A large number of partially or totally overlapping character sets is NOT a good thing. A SINGLE character set that can be used universally for representing all of the world's languages in Internet mail would be preferrable. Unfortunately, existing practice in several communities seems to point to the continued use of multiple character sets in the near future. A small number of standard character sets are, therefore, defined for Internet use in this document.
ПРИМЕЧАНИЕ. За пределами US-ASCII существует огромное множество наборов символов. Большое количество частично или полностью перекрывающихся наборов символов — НЕ есть нечто хорошее. ЕДИНЫЙ набор символов, который мог бы универсально использоваться для представления всех языков мира в интернет-почте, был бы предпочтительнее. К сожалению, существующая практика в нескольких сообществах, по-видимому, указывает на продолжение использования множества наборов символов в обозримом будущем.
The defined charset values are:
Определённые значения charset:
(1) US-ASCII -- as defined in ANSI X3.4-1986 [US-ASCII].
(1) US-ASCII — как определено в ANSI X3.4-1986 [US-ASCII].
(2) ISO-8859-X -- where "X" is to be replaced, as necessary, for the parts of ISO-8859 [ISO-8859]. Note that the ISO 646 character sets have deliberately been omitted in favor of their 8859 replacements, which are the designated character sets for Internet mail. As of the publication of this document, the legitimate values for "X" are the digits 1 through 10.
(2) ISO-8859-X — где «X» заменяется по необходимости для частей ISO-8859 [ISO-8859]. Обратите внимание, что наборы символов ISO 646 намеренно опущены в пользу их замен в 8859, которые являются назначенными наборами символов для интернет-почты. На момент публикации настоящего документа допустимыми значениями «X» являются цифры от 1 до 10.
Characters in the range 128-159 has no assigned meaning in ISO-8859- X. Characters with values below 128 in ISO-8859-X have the same assigned meaning as they do in US-ASCII.
Символы в диапазоне 128-159 не имеют назначенного значения в ISO-8859-X. Символы со значениями ниже 128 в ISO-8859-X имеют то же назначенное значение, что и в US-ASCII.
Part 6 of ISO 8859 (Latin/Arabic alphabet) and part 8 (Latin/Hebrew alphabet) includes both characters for which the normal writing direction is right to left and characters for which it is left to right, but do not define a canonical ordering method for representing bi-directional text. The charset values "ISO-8859-6" and "ISO-8859- 8", however, specify that the visual method is used [RFC-1556].
Часть 6 стандарта ISO 8859 (латинско-арабский алфавит) и часть 8 (латинско-еврейский алфавит) включают как символы, для которых обычное направление письма — справа налево, так и символы, для которых оно слева направо, но не определяют канонического метода упорядочения для представления двунаправленного текста. Однако значения charset «ISO-8859-6» и «ISO-8859-8» указывают, что используется визуальный метод [RFC-1556].
All of these character sets are used as pure 7bit or 8bit sets without any shift or escape functions. The meaning of shift and escape sequences in these character sets is not defined.
Все эти наборы символов используются как чистые 7-битные или 8-битные наборы без каких-либо функций сдвига или переключения. Значение последовательностей сдвига и переключения в этих наборах символов не определено.
The character sets specified above are the ones that were relatively uncontroversial during the drafting of MIME. This document does not endorse the use of any particular character set other than US-ASCII, and recognizes that the future evolution of world character sets remains unclear.
Наборы символов, указанные выше, — это те, которые были относительно бесспорными в период разработки MIME. Настоящий документ не одобряет использование какого-либо конкретного набора символов, кроме US-ASCII, и признаёт, что будущая эволюция мировых наборов символов остаётся неясной.
Note that the character set used, if anything other than US- ASCII, must always be explicitly specified in the Content-Type field.
Обратите внимание, что используемый набор символов, если он отличается от US-ASCII, всегда должен быть явно указан в поле Content-Type.
No character set name other than those defined above may be used in Internet mail without the publication of a formal specification and its registration with IANA, or by private agreement, in which case the character set name must begin with "X-".
Никакое имя набора символов, кроме определённых выше, не может использоваться в интернет-почте без публикации формальной спецификации и её регистрации в IANA либо по частному соглашению; в последнем случае имя набора символов должно начинаться с «X-».
Implementors are discouraged from defining new character sets unless absolutely necessary.
Разработчикам не рекомендуется определять новые наборы символов, если в этом нет абсолютной необходимости.
The "charset" parameter has been defined primarily for the purpose of textual data, and is described in this section for that reason. However, it is conceivable that non-textual data might also wish to specify a charset value for some purpose, in which case the same syntax and values should be used.
Параметр «charset» был определён в первую очередь для целей текстовых данных и описан в этом разделе именно по этой причине. Однако можно представить, что не-текстовые данные также пожелают указать значение charset для какой-либо цели; в этом случае следует использовать тот же синтаксис и те же значения.
In general, composition software should always use the "lowest common denominator" character set possible. For example, if a body contains only US-ASCII characters, it SHOULD be marked as being in the US- ASCII character set, not ISO-8859-1, which, like all the ISO-8859 family of character sets, is a superset of US-ASCII. More generally, if a widely-used character set is a subset of another character set, and a body contains only characters in the widely-used subset, it should be labelled as being in that subset. This will increase the chances that the recipient will be able to view the resulting entity correctly.
В общем случае программное обеспечение должно всегда использовать максимально возможный «наименьший общий знаменатель» набора символов. Например, если тело содержит только символы US-ASCII, оно ДОЛЖНО быть помечено как находящееся в наборе символов US-ASCII, а не ISO-8859-1, который, как и всё семейство ISO-8859, является надмножеством US-ASCII. Более обще: если тело содержит только символы набора символов X, а этот набор является подмножеством набора символов Y, тело должно быть помечено как X, а не Y.
4.1.3. Plain Subtype
4.1.3. Подтип plain
The simplest and most important subtype of "text" is "plain". This indicates plain text that does not contain any formatting commands or directives. Plain text is intended to be displayed "as-is", that is, no interpretation of embedded formatting commands, font attribute specifications, processing instructions, interpretation directives, or content markup should be necessary for proper display. The default media type of "text/plain; charset=us-ascii" for Internet mail describes existing Internet practice. That is, it is the type of body defined by RFC 822.
Простейшим и важнейшим подтипом «text» является «plain». Он указывает на обычный текст, не содержащий никаких команд или директив форматирования. Обычный текст предназначен для отображения «как есть», то есть без интерпретации встроенных команд форматирования, спецификаций атрибутов шрифта, инструкций обработки, директив интерпретации или чего-либо иного. Медиа-тип по умолчанию «text/plain; charset=us-ascii» для интернет-почты описывает существующую практику Интернета. То есть это тип тела, определённый в RFC 822.
No other "text" subtype is defined by this document.
Никакой другой подтип «text» настоящим документом не определён.
4.1.4. Unrecognized Subtypes
4.1.4. Нераспознанные подтипы
Unrecognized subtypes of "text" should be treated as subtype "plain" as long as the MIME implementation knows how to handle the charset. Unrecognized subtypes which also specify an unrecognized charset should be treated as "application/octet- stream".
Нераспознанные подтипы «text» следует рассматривать как подтип «plain», если MIME-реализация умеет работать с указанным набором символов. Нераспознанные подтипы, которые к тому же указывают нераспознанный charset, следует рассматривать как «application/octet-stream».
4.2. Image Media Type
4.2. Тип носителя image
A media type of "image" indicates that the body contains an image. The subtype names the specific image format. These names are not case sensitive. An initial subtype is "jpeg" for the JPEG format using JFIF encoding [JPEG].
Тип носителя «image» указывает, что тело содержит изображение. Подтип называет конкретный формат изображения. Эти имена не чувствительны к регистру. Первоначальный подтип — «jpeg» для формата JPEG с кодированием JFIF [JPEG].
The list of "image" subtypes given here is neither exclusive nor exhaustive, and is expected to grow as more types are registered with IANA, as described in RFC 2048.
Приведённый здесь список подтипов «image» не является ни исключительным, ни исчерпывающим и, как ожидается, будет расти по мере регистрации новых типов в IANA в порядке, описанном в RFC 2048.
Unrecognized subtypes of "image" should at a miniumum be treated as "application/octet-stream". Implementations may optionally elect to pass subtypes of "image" that they do not specifically recognize to a secure and robust general-purpose image viewing application, if such an application is available.
Нераспознанные подтипы «image» как минимум должны обрабатываться как «application/octet-stream». Реализации могут по желанию передавать подтипы «image», которые они специально не распознают, в безопасное и надёжное приложение общего назначения для просмотра изображений, если такое приложение доступно.
NOTE: Using of a generic-purpose image viewing application this way inherits the security problems of the most dangerous type supported by the application.
ПРИМЕЧАНИЕ. Использование приложения общего назначения для просмотра изображений таким образом влечёт за собой проблемы безопасности наиболее опасного типа, поддерживаемого этим приложением.
4.3. Audio Media Type
4.3. Тип носителя audio
A media type of "audio" indicates that the body contains audio data. Although there is not yet a consensus on an "ideal" audio format for use with computers, there is a pressing need for a format capable of providing interoperable behavior. The initial subtype of "basic" is specified to meet this requirement by providing an absolutely minimal lowest common denominator audio format. It is expected that richer formats for higher quality and/or lower bandwidth audio will be defined by a later document.
Тип носителя «audio» указывает, что тело содержит звуковые данные. Хотя единого мнения относительно «идеального» звукового формата для использования на компьютерах пока не существует, имеется настоятельная потребность в формате, способном обеспечить совместимое поведение. Первоначальный подтип «basic» определён для удовлетворения этого требования путём предоставления абсолютно минимального звукового формата, служащего наименьшим общим знаменателем. Ожидается, что более богатые форматы для звука более высокого качества и/или с меньшей полосой пропускания будут определены в более позднем документе.
The content of the "audio/basic" subtype is single channel audio encoded using 8bit ISDN mu-law [PCM] at a sample rate of 8000 Hz.
Содержимое подтипа «audio/basic» представляет собой одноканальный звук, закодированный с использованием 8-битного ISDN-кодирования µ-law [PCM] с частотой дискретизации 8000 Гц.
Unrecognized subtypes of "audio" should at a miniumum be treated as "application/octet-stream". Implementations may optionally elect to pass subtypes of "audio" that they do not specifically recognize to a robust general-purpose audio playing application, if such an application is available.
Нераспознанные подтипы «audio» как минимум должны обрабатываться как «application/octet-stream». Реализации могут по желанию передавать подтипы «audio», которые они специально не распознают, в надёжное приложение общего назначения для воспроизведения звука, если такое приложение доступно.
4.4. Video Media Type
4.4. Тип носителя video
A media type of "video" indicates that the body contains a time- varying-picture image, possibly with color and coordinated sound. The term 'video' is used in its most generic sense, rather than with reference to any particular technology or format, and is not meant to preclude subtypes such as animated drawings encoded compactly. The subtype "mpeg" refers to video coded according to the MPEG standard [MPEG].
Тип носителя «video» указывает, что тело содержит изображение, меняющееся во времени, возможно, с цветом и согласованным звуком. Термин «video» используется в самом общем смысле, а не применительно к какой-либо конкретной технологии или формату, и не предназначен для исключения таких подтипов, как компактно закодированные анимированные рисунки.
Note that although in general this document strongly discourages the mixing of multiple media in a single body, it is recognized that many so-called video formats include a representation for synchronized audio, and this is explicitly permitted for subtypes of "video".
Обратите внимание: хотя в целом настоящий документ решительно не поощряет смешивание нескольких видов носителя в одном теле, признаётся, что многие так называемые видеоформаты включают представление синхронизированного звука, и это для подтипов «video» явно разрешено.
Unrecognized subtypes of "video" should at a minumum be treated as "application/octet-stream". Implementations may optionally elect to pass subtypes of "video" that they do not specifically recognize to a robust general-purpose video display application, if such an application is available.
Нераспознанные подтипы «video» как минимум должны обрабатываться как «application/octet-stream». Реализации могут по желанию передавать подтипы «video», которые они специально не распознают, в надёжное приложение общего назначения для отображения видео, если такое приложение доступно.
4.5. Application Media Type
4.5. Тип носителя application
The "application" media type is to be used for discrete data which do not fit in any of the other categories, and particularly for data to be processed by some type of application program. This is information which must be processed by an application before it is viewable or usable by a user. Expected uses for the "application" media type include file transfer, spreadsheets, data for mail-based scheduling systems, and languages for "active" (computational) material. (The latter, in particular, can pose security problems which must be understood by implementors, and are considered in detail in the discussion of the "application/PostScript" media type.) For example, a meeting scheduler might define a standard representation for information about proposed meeting dates. An intelligent user agent would use this information to conduct a dialog with the user, and might then send additional material based on that dialog. More generally, there have been several "active" messaging languages developed in which programs in a suitably specialized language are transported to a remote location and automatically run in the recipient's environment.
Тип носителя «application» должен использоваться для дискретных данных, не подпадающих ни под одну из других категорий, и в особенности для данных, подлежащих обработке некой прикладной программой. Это информация, которая должна быть обработана приложением, прежде чем станет доступной для просмотра или использования пользователем. Ожидаемые способы применения типа «application» включают передачу данных, основанных на электронных таблицах, языках описания данных, языках программирования или документах, требующих отдельного приложения для их обработки. Например, планировщик встреч может определить стандартное представление информации о предлагаемых датах встреч. Интеллектуальный пользовательский агент использовал бы эту информацию для ведения диалога с пользователем и затем мог бы отправить дополнительные материалы на основе этого диалога. В более общем плане существовало несколько «активных» языков обмена сообщениями, в которых тело сообщения содержит информацию, подлежащую обработке и интерпретации пользовательским агентом получателя.
Such applications may be defined as subtypes of the "application" media type. This document defines two subtypes:
Такие приложения могут быть определены как подтипы типа носителя «application». Настоящий документ определяет два подтипа:
octet-stream, and PostScript.
octet-stream и PostScript.
The subtype of "application" will often be either the name or include part of the name of the application for which the data are intended. This does not mean, however, that any application program name may be used freely as a subtype of "application".
Подтип «application» часто будет либо именем, либо включать часть имени приложения, для которого предназначены данные. Однако это не означает, что любое имя прикладной программы может свободно использоваться как подтип «application».
4.5.1. Octet-Stream Subtype
4.5.1. Подтип octet-stream
The "octet-stream" subtype is used to indicate that a body contains arbitrary binary data. The set of currently defined parameters is:
Подтип «octet-stream» используется для указания на то, что тело содержит произвольные двоичные данные. Набор определённых на настоящий момент параметров:
(1) TYPE -- the general type or category of binary data. This is intended as information for the human recipient rather than for any automatic processing.
(1) TYPE — общий тип или категория двоичных данных. Предназначен как информация для получателя-человека, а не для автоматической обработки.
(2) PADDING -- the number of bits of padding that were appended to the bit-stream comprising the actual contents to produce the enclosed 8bit byte-oriented data. This is useful for enclosing a bit-stream in a body when the total number of bits is not a multiple of 8.
(2) PADDING — число битов заполнения, которые были добавлены к битовому потоку, составляющему фактическое содержимое, для получения прилагаемых 8-битных байтово-ориентированных данных. Полезно для включения битового потока в тело, когда общее число битов не кратно 8.
Both of these parameters are optional.
Оба этих параметра необязательны.
An additional parameter, "CONVERSIONS", was defined in RFC 1341 but has since been removed. RFC 1341 also defined the use of a "NAME" parameter which gave a suggested file name to be used if the data were to be written to a file. This has been deprecated in anticipation of a separate Content-Disposition header field, to be defined in a subsequent RFC.
Дополнительный параметр «CONVERSIONS» был определён в RFC 1341, но с тех пор удалён. RFC 1341 также определял использование параметра «NAME», задававшего предлагаемое имя файла, которое следовало использовать, если данные записываются в файл. Он признан устаревшим в преддверии появления отдельного поля заголовка Content-Disposition, определённого в RFC 2183.
The recommended action for an implementation that receives an "application/octet-stream" entity is to simply offer to put the data in a file, with any Content-Transfer-Encoding undone, or perhaps to use it as input to a user-specified process. To reduce the danger of transmitting rogue programs, it is strongly recommended that implementations NOT implement a path-search mechanism whereby an arbitrary program named in the Content-Type parameter (e.g., an "interpreter=" parameter) is found and executed using the message body as input.
Рекомендуемым действием для реализации, получающей объект «application/octet-stream», является просто предложить поместить данные в файл, отменив любую кодировку переноса содержимого, или, возможно, использовать их в качестве входных данных для процесса, указанного пользователем. Чтобы снизить опасность передачи вредоносных программ, настоятельно рекомендуется, чтобы реализации НЕ реализовывали механизм поиска по пути, с помощью которого некая произвольная программа, указанная в параметре Content-Type (например, параметр «interpreter=»), находится и выполняется с использованием тела сообщения в качестве входных данных.
4.5.2. PostScript Subtype
4.5.2. Подтип PostScript
A media type of "application/postscript" indicates a PostScript program. Currently two variants of the PostScript language are allowed; the original level 1 variant is described in [POSTSCRIPT] and the more recent level 2 variant is described in [POSTSCRIPT2].
Тип носителя «application/postscript» указывает на программу PostScript. В настоящее время допускаются два варианта языка PostScript: первоначальный вариант уровня 1 описан в [POSTSCRIPT], а более поздний вариант уровня 2 — в [POSTSCRIPT2].
PostScript is a registered trademark of Adobe Systems, Inc. Use of the MIME media type "application/postscript" implies recognition of that trademark and all the rights it entails.
PostScript является зарегистрированной торговой маркой Adobe Systems, Inc. Использование MIME-типа носителя «application/postscript» подразумевает признание этой торговой марки и всех связанных с ней прав.
The PostScript language definition provides facilities for internal labelling of the specific language features a given program uses. This labelling, called the PostScript document structuring conventions, or DSC, is very general and provides substantially more information than just the language level. The use of document structuring conventions, while not required, is strongly recommended as an aid to interoperability. Documents which lack proper structuring conventions cannot be tested to see whether or not they will work in a given environment. As such, some systems may assume the worst and refuse to process unstructured documents.
Определение языка PostScript предоставляет средства для внутренней маркировки конкретных языковых возможностей, используемых данной программой. Эта маркировка, называемая соглашениями о структурировании документов PostScript (PostScript document structuring conventions, DSC), является очень общей и предоставляет существенно больше информации, нежели просто уровень языка. Использование соглашений о структурировании документов в телах PostScript рекомендуется при любых обстоятельствах.
The execution of general-purpose PostScript interpreters entails serious security risks, and implementors are discouraged from simply sending PostScript bodies to "off- the-shelf" interpreters. While it is usually safe to send PostScript to a printer, where the potential for harm is greatly constrained by typical printer environments, implementors should consider all of the following before they add interactive display of PostScript bodies to their MIME readers.
Выполнение универсальных интерпретаторов PostScript связано с серьёзными рисками безопасности, и разработчикам не рекомендуется просто отправлять тела PostScript в «готовые» интерпретаторы. Хотя обычно безопасно отправлять PostScript на принтер, где потенциальный ущерб в значительной степени ограничен типичным принтерным окружением, отправка PostScript в почтовом сообщении в общем случае не рекомендуется, если только получатель не может быть уверен в безопасности интерпретатора. Реализации, которые принимают тела PostScript, должны применять все меры предосторожности, соответствующие любой программе, получаемой по почте.
The remainder of this section outlines some, though probably not all, of the possible problems with the transport of PostScript entities.
Остаток этого раздела описывает некоторые, хотя, вероятно, не все возможные проблемы при передаче объектов PostScript.
(1) Dangerous operations in the PostScript language include, but may not be limited to, the PostScript operators "deletefile", "renamefile", "filenameforall", and "file". "File" is only dangerous when applied to something other than standard input or output. Implementations may also define additional nonstandard file operators; these may also pose a threat to security. "Filenameforall", the wildcard file search operator, may appear at first glance to be harmless. Note, however, that this operator has the potential to reveal information about what files the recipient has access to, and this information may itself be sensitive. Message senders should avoid the use of potentially dangerous file operators, since these operators are quite likely to be unavailable in secure PostScript implementations. Message receiving and displaying software should either completely disable all potentially dangerous file operators or take special care not to delegate any special authority to their operation. These operators should be viewed as being done by an outside agency when interpreting PostScript documents. Such disabling and/or checking should be done completely outside of the reach of the PostScript language itself; care should be taken to insure that no method exists for re-enabling full- function versions of these operators.
(1) Опасные операции в языке PostScript включают, но могут не ограничиваться, операторы PostScript «deletefile», «renamefile», «filenameforall» и «file». Оператор «File» опасен только при применении к чему-либо иному, нежели стандартный ввод или вывод. Реализации могут также определять дополнительные нестандартные файловые операторы; они также могут представлять угрозу для безопасности. Оператор «Filenameforall» — оператор поиска файлов по шаблону — на первый взгляд может показаться безвредным. Однако обратите внимание, что этот оператор способен раскрыть информацию о том, к каким файлам получатель имеет доступ, а эта информация сама по себе может быть конфиденциальной. Отправителям сообщений следует избегать использования потенциально опасных файловых операторов, поскольку в защищённых реализациях PostScript эти операторы, скорее всего, будут недоступны. Программное обеспечение для приёма и отображения сообщений должно либо полностью отключать все потенциально опасные файловые операторы, либо проявлять особую осторожность, чтобы не наделять их выполнение какими-либо особыми полномочиями. При интерпретации документов PostScript на эти операторы следует смотреть как на выполняемые внешним субъектом. Такое отключение и/или проверка должны выполняться полностью вне досягаемости самого языка PostScript; следует позаботиться о том, чтобы не существовало способа повторно включить полнофункциональные версии этих операторов.
(2) The PostScript language provides facilities for exiting the normal interpreter, or server, loop. Changes made in this "outer" environment are customarily retained across documents, and may in some cases be retained semipermanently in nonvolatile memory. The operators associated with exiting the interpreter loop have the potential to interfere with subsequent document processing. As such, their unrestrained use constitutes a threat of service denial. PostScript operators that exit the interpreter loop include, but may not be limited to, the exitserver and startjob operators. Message sending software should not generate PostScript that depends on exiting the interpreter loop to operate, since the ability to exit will probably be unavailable in secure PostScript implementations. Message receiving and displaying software should completely disable the ability to make retained changes to the PostScript environment by eliminating or disabling the "startjob" and "exitserver" operations. If these operations cannot be eliminated or completely disabled the password associated with them should at least be set to a hard- to-guess value.
(2) Язык PostScript предоставляет средства для выхода из обычного цикла интерпретатора (или сервера). Изменения, произведённые в этом «внешнем» окружении, обычно сохраняются между документами и в некоторых случаях могут сохраняться полупостоянно в энергонезависимой памяти. Операторы, связанные с выходом из цикла интерпретатора, способны помешать последующей обработке документов. Как таковое, их неограниченное использование представляет собой угрозу отказа в обслуживании. К операторам PostScript, осуществляющим выход из цикла интерпретатора, относятся, но могут не ограничиваться, операторы «exitserver» и «startjob». Программное обеспечение для отправки сообщений не должно генерировать PostScript, работа которого зависит от выхода из цикла интерпретатора, поскольку в защищённых реализациях PostScript такая возможность, вероятно, будет недоступна. Программное обеспечение для приёма и отображения сообщений должно полностью отключать возможность вносить сохраняемые изменения в окружение PostScript путём устранения или отключения операций «startjob» и «exitserver». Если эти операции невозможно устранить или полностью отключить, связанный с ними пароль следует по крайней мере установить в трудноугадываемое значение.
(3) PostScript provides operators for setting system-wide and device-specific parameters. These parameter settings may be retained across jobs and may potentially pose a threat to the correct operation of the interpreter. The PostScript operators that set system and device parameters include, but may not be limited to, the "setsystemparams" and "setdevparams" operators. Message sending software should not generate PostScript that depends on the setting of system or device parameters to operate correctly. The ability to set these parameters will probably be unavailable in secure PostScript implementations. Message receiving and displaying software should disable the ability to change system and device parameters. If these operators cannot be completely disabled the password associated with them should at least be set to a hard-to-guess value.
(3) PostScript предоставляет операторы для установки общесистемных и специфичных для устройства параметров. Эти установки параметров могут сохраняться между заданиями и потенциально представлять угрозу для правильной работы интерпретатора. К операторам PostScript, устанавливающим системные параметры и параметры устройства, относятся, но могут не ограничиваться, операторы «setsystemparams» и «setdevparams». Программное обеспечение для отправки сообщений не должно генерировать PostScript, работа которого зависит от установки системных параметров или параметров устройства. В защищённых реализациях PostScript такая возможность, вероятно, будет недоступна. Программное обеспечение для приёма и отображения сообщений должно отключать возможность изменения системных параметров и параметров устройства. Если эти операторы невозможно полностью отключить, связанный с ними пароль следует по крайней мере установить в трудноугадываемое значение.
(4) Some PostScript implementations provide nonstandard facilities for the direct loading and execution of machine code. Such facilities are quite obviously open to substantial abuse. Message sending software should not make use of such features. Besides being totally hardware-specific, they are also likely to be unavailable in secure implementations of PostScript. Message receiving and displaying software should not allow such operators to be used if they exist.
(4) Некоторые реализации PostScript предоставляют нестандартные средства для прямой загрузки и выполнения машинного кода. Такие средства, совершенно очевидно, открыты для существенного злоупотребления. Программное обеспечение для отправки сообщений не должно использовать такие возможности. Помимо того, что они полностью зависят от аппаратного обеспечения, они также несовместимы между реализациями.
(5) PostScript is an extensible language, and many, if not most, implementations of it provide a number of their own extensions. This document does not deal with such extensions explicitly since they constitute an unknown factor. Message sending software should not make use of nonstandard extensions; they are likely to be missing from some implementations. Message receiving and displaying software should make sure that any nonstandard PostScript operators are secure and don't present any kind of threat.
(5) PostScript является расширяемым языком, и многие (если не большинство) его реализации предоставляют ряд собственных расширений. Настоящий документ явно не рассматривает такие расширения, поскольку они представляют собой неизвестный фактор. Программное обеспечение для отправки сообщений не должно использовать нестандартные расширения; в некоторых реализациях они, скорее всего, будут отсутствовать. Программное обеспечение для приёма и отображения сообщений должно удостовериться, что любые нестандартные операторы PostScript безопасны и не представляют угрозы какого-либо рода.
(6) It is possible to write PostScript that consumes huge amounts of various system resources. It is also possible to write PostScript programs that loop indefinitely. Both types of programs have the potential to cause damage if sent to unsuspecting recipients. Message-sending software should avoid the construction and dissemination of such programs, which is antisocial. Message receiving and displaying software should provide appropriate mechanisms to abort processing after a reasonable amount of time has elapsed. In addition, PostScript interpreters should be limited to the consumption of only a reasonable amount of any given system resource.
(6) Можно написать PostScript, потребляющий огромные объёмы различных системных ресурсов. Можно также написать программы PostScript, зацикливающиеся бесконечно. Оба типа программ потенциально способны причинить ущерб, если отправлены ничего не подозревающим получателям. Программное обеспечение для отправки сообщений должно избегать создания и распространения таких программ, что является антиобщественным поведением. Программное обеспечение для приёма и отображения сообщений должно предусматривать соответствующие механизмы прерывания обработки по истечении разумного времени. Кроме того, интерпретаторы PostScript должны быть ограничены потреблением лишь разумного объёма любого заданного системного ресурса.
(7) It is possible to include raw binary information inside PostScript in various forms. This is not recommended for use in Internet mail, both because it is not supported by all PostScript interpreters and because it significantly complicates the use of a MIME Content- Transfer-Encoding. (Without such binary, PostScript may typically be viewed as line-oriented data. The treatment of CRLF sequences becomes extremely problematic if binary and line-oriented data are mixed in a single Postscript data stream.)
(7) Внутри PostScript можно в различных формах включать необработанную двоичную информацию. Это не рекомендуется для использования в интернет-почте как потому, что поддерживается не всеми интерпретаторами PostScript, так и потому, что существенно усложняет использование MIME Content-Transfer-Encoding. (Без особых мер предосторожности это также может привести к усечению тела промежуточными почтовыми шлюзами.)
(8) Finally, bugs may exist in some PostScript interpreters which could possibly be exploited to gain unauthorized access to a recipient's system. Apart from noting this possibility, there is no specific action to take to prevent this, apart from the timely correction of such bugs if any are found.
(8) Наконец, в некоторых интерпретаторах PostScript могут существовать ошибки, которые потенциально могут быть использованы для получения несанкционированного доступа к системе получателя. Помимо указания на эту возможность, никаких конкретных действий для её предотвращения не существует, кроме своевременного исправления таких ошибок, если они будут найдены.
4.5.3. Other Application Subtypes
4.5.3. Прочие подтипы application
It is expected that many other subtypes of "application" will be defined in the future. MIME implementations must at a minimum treat any unrecognized subtypes as being equivalent to "application/octet- stream".
Ожидается, что в будущем будет определено множество других подтипов «application». MIME-реализации как минимум должны обрабатывать любые нераспознанные подтипы как эквивалентные «application/octet-stream».
5. Composite Media Type Values
5. Составные значения типов носителя
The remaining two of the seven initial Content-Type values refer to composite entities. Composite entities are handled using MIME mechanisms -- a MIME processor typically handles the body directly.
Оставшиеся два из семи первоначальных значений Content-Type относятся к составным объектам. Составные объекты обрабатываются с помощью механизмов MIME — MIME-процессор обычно обрабатывает тело напрямую.
5.1. Multipart Media Type
5.1. Тип носителя multipart
In the case of multipart entities, in which one or more different sets of data are combined in a single body, a "multipart" media type field must appear in the entity's header. The body must then contain one or more body parts, each preceded by a boundary delimiter line, and the last one followed by a closing boundary delimiter line. After its boundary delimiter line, each body part then consists of a header area, a blank line, and a body area. Thus a body part is similar to an RFC 822 message in syntax, but different in meaning.
В случае составных объектов, когда один или несколько различных наборов данных объединяются в одном теле, в заголовке объекта должно присутствовать поле типа носителя «multipart». Тело затем должно содержать одну или несколько частей тела, каждая из которых предваряется строкой-разделителем границы, а последняя сопровождается концевым разделителем. Строка-разделитель границы должна находиться в начале строки, то есть после CRLF, и первоначальный CRLF считается принадлежащим строке-разделителю границы, а не предшествующей части. Таким образом, часть тела похожа на сообщение RFC 822 по синтаксису, но отличается по смыслу.
A body part is an entity and hence is NOT to be interpreted as actually being an RFC 822 message. To begin with, NO header fields are actually required in body parts. A body part that starts with a blank line, therefore, is allowed and is a body part for which all default values are to be assumed. In such a case, the absence of a Content-Type header usually indicates that the corresponding body has a content-type of "text/plain; charset=US-ASCII".
Часть тела является объектом и, следовательно, НЕ должна интерпретироваться как фактически являющаяся сообщением RFC 822. Прежде всего, в частях тела НЕ требуется наличие каких-либо полей заголовка. Поэтому часть тела, начинающаяся с пустой строки, допустима и является частью тела, для которой должны подразумеваться все значения по умолчанию. Часть тела, начальные строки которой состоят из полей заголовка, начинается с заголовка, который продолжается до первой пустой строки; в этом случае предполагается, что пустая строка отделяет заголовки части тела от её содержимого.
The only header fields that have defined meaning for body parts are those the names of which begin with "Content-". All other header fields may be ignored in body parts. Although they should generally be retained if at all possible, they may be discarded by gateways if necessary. Such other fields are permitted to appear in body parts but must not be depended on. "X-" fields may be created for experimental or private purposes, with the recognition that the information they contain may be lost at some gateways.
Единственными полями заголовка, имеющими определённое значение для частей тела, являются те, имена которых начинаются с «Content-». Все прочие поля заголовка в частях тела могут игнорироваться. Хотя в общем случае их следует по возможности сохранять, при необходимости они могут отбрасываться шлюзами. Такие прочие поля обычно содержат описание содержимого части тела, но у них отсутствует определённо определённая семантика для частей тела, поскольку они не были определены как имеющие какое-либо значение в этом контексте.
NOTE: The distinction between an RFC 822 message and a body part is subtle, but important. A gateway between Internet and X.400 mail, for example, must be able to tell the difference between a body part that contains an image and a body part that contains an encapsulated message, the body of which is a JPEG image. In order to represent the latter, the body part must have "Content-Type: message/rfc822", and its body (after the blank line) must be the encapsulated message, with its own "Content-Type: image/jpeg" header field. The use of similar syntax facilitates the conversion of messages to body parts, and vice versa, but the distinction between the two must be understood by implementors. (For the special case in which parts actually are messages, a "digest" subtype is also defined.)
ПРИМЕЧАНИЕ. Различие между сообщением RFC 822 и частью тела тонкое, но важное. Шлюз между интернет-почтой и почтой X.400, например, должен уметь отличать часть тела, содержащую изображение, от части тела, содержащей инкапсулированное сообщение, тело которого является изображением JPEG. Чтобы представить последнее, часть тела должна иметь «Content-Type: message/rfc822», а её тело (после пустой строки) должно быть инкапсулированным сообщением со своим собственным полем заголовка «Content-Type: image/jpeg». Использование сходного синтаксиса облегчает преобразование сообщений в части тела и наоборот, но разработчики должны понимать различие между ними. (Для особого случая, когда части на самом деле являются сообщениями, также определён подтип «digest».)
As stated previously, each body part is preceded by a boundary delimiter line that contains the boundary delimiter. The boundary delimiter MUST NOT appear inside any of the encapsulated parts, on a line by itself or as the prefix of any line. This implies that it is crucial that the composing agent be able to choose and specify a unique boundary parameter value that does not contain the boundary parameter value of an enclosing multipart as a prefix.
Как указано ранее, каждая часть тела предваряется строкой-разделителем границы, содержащей разделитель границы. Разделитель границы НЕ ДОЛЖЕН встречаться внутри какой-либо из инкапсулированных частей ни в виде отдельной строки, ни в качестве префикса какой-либо строки. Отсюда следует, что крайне важно, чтобы составляющий агент выбирал значение параметра boundary, которое не встречается в теле. Этот выбор должен производиться особенно тщательно при передаче произвольных двоичных данных.
All present and future subtypes of the "multipart" type must use an identical syntax. Subtypes may differ in their semantics, and may impose additional restrictions on syntax, but must conform to the required syntax for the "multipart" type. This requirement ensures that all conformant user agents will at least be able to recognize and separate the parts of any multipart entity, even those of an unrecognized subtype.
Все настоящие и будущие подтипы типа «multipart» должны использовать идентичный синтаксис. Подтипы могут отличаться своей семантикой и могут накладывать дополнительные ограничения на синтаксис, но должны соответствовать требуемому синтаксису для типа «multipart». Это требование гарантирует, что все соответствующие стандарту пользовательские агенты смогут распознавать и разделять составные тела, не зная семантики конкретного подтипа.
As stated in the definition of the Content-Transfer-Encoding field [RFC 2045], no encoding other than "7bit", "8bit", or "binary" is permitted for entities of type "multipart". The "multipart" boundary delimiters and header fields are always represented as 7bit US-ASCII in any case (though the header fields may encode non-US-ASCII header text as per RFC 2047) and data within the body parts can be encoded on a part-by-part basis, with Content-Transfer-Encoding fields for each appropriate body part.
Как указано в определении поля Content-Transfer-Encoding [RFC 2045], для объектов типа «multipart» не допускается никакое кодирование, кроме «7bit», «8bit» или «binary». Разделители границы и поля заголовка «multipart» в любом случае всегда представляются как 7-битные US-ASCII (хотя поля заголовка могут содержать не-ASCII значения, закодированные согласно RFC 2047). Части тела типа «multipart» могут быть закодированы любым допустимым способом.
5.1.1. Common Syntax
5.1.1. Общий синтаксис
This section defines a common syntax for subtypes of "multipart". All subtypes of "multipart" must use this syntax. A simple example of a multipart message also appears in this section. An example of a more complex multipart message is given in RFC 2049.
Этот раздел определяет общий синтаксис для подтипов «multipart». Все подтипы «multipart» должны использовать этот синтаксис. Простой пример составного сообщения также приведён в этом разделе. Пример более сложного составного сообщения приведён в RFC 2049.
The Content-Type field for multipart entities requires one parameter, "boundary". The boundary delimiter line is then defined as a line consisting entirely of two hyphen characters ("-", decimal value 45) followed by the boundary parameter value from the Content-Type header field, optional linear whitespace, and a terminating CRLF.
Поле Content-Type для составных объектов требует одного параметра — «boundary». Строка-разделитель границы определяется как строка, состоящая целиком из двух символов дефиса («-», десятичное значение 45), за которыми следует значение параметра boundary из поля заголовка Content-Type, необязательные символы линейных пробелов и завершающий символ CRLF. Символы линейных пробелов за значением границы, хотя и не являются частью самой границы, должны игнорироваться при сравнении.
NOTE: The hyphens are for rough compatibility with the earlier RFC 934 method of message encapsulation, and for ease of searching for the boundaries in some implementations. However, it should be noted that multipart messages are NOT completely compatible with RFC 934 encapsulations; in particular, they do not obey RFC 934 quoting conventions for embedded lines that begin with hyphens. This mechanism was chosen over the RFC 934 mechanism because the latter causes lines to grow with each level of quoting. The combination of this growth with the fact that SMTP implementations sometimes wrap long lines made the RFC 934 mechanism unsuitable for use in the event that deeply-nested multipart structuring is ever desired.
ПРИМЕЧАНИЕ. Дефисы служат для приблизительной совместимости с более ранним методом инкапсуляции сообщений RFC 934 и для облегчения поиска границ в некоторых реализациях. Однако следует отметить, что составные сообщения НЕ полностью совместимы с инкапсуляциями RFC 934; в частности, они не подчиняются соглашениям RFC 934 о квотировании для встроенных строк, начинающихся с дефисов. Этот механизм был выбран вместо механизма RFC 934 потому, что последний приводит к удлинению строк с каждым уровнем квотирования. Сочетание такого удлинения с тем фактом, что реализации SMTP иногда переносят длинные строки, сделало механизм RFC 934 непригодным для использования в случае, если когда-либо потребуется глубоко вложенная составная структура.
WARNING TO IMPLEMENTORS: The grammar for parameters on the Content- type field is such that it is often necessary to enclose the boundary parameter values in quotes on the Content-type line. This is not always necessary, but never hurts. Implementors should be sure to study the grammar carefully in order to avoid producing invalid Content-type fields. Thus, a typical "multipart" Content-Type header field might look like this:
ПРЕДУПРЕЖДЕНИЕ РАЗРАБОТЧИКАМ. Грамматика параметров поля Content-Type такова, что часто возникает необходимость заключать значения параметра boundary в кавычки в строке Content-Type. Это не всегда обязательно, но никогда не вредит. Разработчикам следует внимательно изучить грамматику в RFC 2045, чтобы определить, когда кавычки необходимы, а когда нет. Например, следующее допустимо:
Content-Type: multipart/mixed; boundary=gc0p4Jq0M2Yt08j34c0p
Content-Type: multipart/mixed; boundary=gc0p4Jq0M2Yt08j34c0p
But the following is not valid:
Но следующее недопустимо:
Content-Type: multipart/mixed; boundary=gc0pJq0M:08jU534c0p (because of the colon) and must instead be represented as
Content-Type: multipart/mixed; boundary=gc0pJq0M:08jU534c0p (из-за двоеточия) и должно быть представлено вместо этого как
Content-Type: multipart/mixed; boundary="gc0pJq0M:08jU534c0p"
Content-Type: multipart/mixed; boundary="gc0pJq0M:08jU534c0p"
This Content-Type value indicates that the content consists of one or more parts, each with a structure that is syntactically identical to an RFC 822 message, except that the header area is allowed to be completely empty, and that the parts are each preceded by the line --gc0pJq0M:08jU534c0p
Это значение Content-Type указывает, что содержимое состоит из одной или нескольких частей, каждая из которых имеет структуру, синтаксически идентичную сообщению RFC 822, за тем исключением, что область заголовка может быть полностью пустой, и что каждая часть предваряется строкой --gc0pJq0M:08jU534c0p
The boundary delimiter MUST occur at the beginning of a line, i.e., following a CRLF, and the initial CRLF is considered to be attached to the boundary delimiter line rather than part of the preceding part. The boundary may be followed by zero or more characters of linear whitespace. It is then terminated by either another CRLF and the header fields for the next part, or by two CRLFs, in which case there are no header fields for the next part. If no Content-Type field is present it is assumed to be "message/rfc822" in a "multipart/digest" and "text/plain" otherwise.
Разделитель границы ДОЛЖЕН находиться в начале строки, то есть после CRLF, и первоначальный CRLF считается присоединённым к строке-разделителю границы, а не частью предшествующей части. За границей может следовать ноль или более символов линейных пробелов. Затем строка завершается символом CRLF. После CRLF может следовать дополнительная строка или строки, каждая из которых должна начинаться с одного или нескольких символов линейных пробелов; такие строки игнорируются. Если поле Content-Type отсутствует, то в «multipart/digest» подразумевается «message/rfc822», а в остальных случаях — «text/plain».
NOTE: The CRLF preceding the boundary delimiter line is conceptually attached to the boundary so that it is possible to have a part that does not end with a CRLF (line break). Body parts that must be considered to end with line breaks, therefore, must have two CRLFs preceding the boundary delimiter line, the first of which is part of the preceding body part, and the second of which is part of the encapsulation boundary.
ПРИМЕЧАНИЕ. CRLF, предшествующий строке-разделителю границы, концептуально присоединён к границе, так что можно иметь часть, не заканчивающуюся CRLF (разрывом строки). Поэтому части тела, которые должны считаться заканчивающимися разрывами строк, должны иметь два CRLF перед строкой-разделителем границы, первый из которых является частью предшествующей части тела, а второй — частью границы инкапсуляции.
Boundary delimiters must not appear within the encapsulated material, and must be no longer than 70 characters, not counting the two leading hyphens.
Разделители границы не должны встречаться внутри инкапсулированного материала и не должны быть длиннее 70 символов, не считая двух ведущих дефисов.
The boundary delimiter line following the last body part is a distinguished delimiter that indicates that no further body parts will follow. Such a delimiter line is identical to the previous delimiter lines, with the addition of two more hyphens after the boundary parameter value.
Строка-разделитель границы, следующая за последней частью тела, является особым разделителем, указывающим, что больше частей тела не будет. Такая строка-разделитель идентична предыдущим строкам-разделителям, но с добавлением ещё двух дефисов после значения параметра boundary.
--gc0pJq0M:08jU534c0p--
--gc0pJq0M:08jU534c0p--
NOTE TO IMPLEMENTORS: Boundary string comparisons must compare the boundary value with the beginning of each candidate line. An exact match of the entire candidate line is not required; it is sufficient that the boundary appear in its entirety following the CRLF.
ПРИМЕЧАНИЕ РАЗРАБОТЧИКАМ. При сравнении строки границы необходимо сравнивать значение границы с началом каждой проверяемой строки. Точного совпадения со всей проверяемой строкой не требуется; достаточно, чтобы граница присутствовала в полном виде после CRLF.
There appears to be room for additional information prior to the first boundary delimiter line and following the final boundary delimiter line. These areas should generally be left blank, and implementations must ignore anything that appears before the first boundary delimiter line or after the last one.
По-видимому, имеется место для дополнительной информации перед первой строкой-разделителем границы и после последней строки-разделителя границы. Эти области в общем случае должны оставаться пустыми, и реализации должны игнорировать всё, что появляется перед первой строкой-разделителем границы или после последней строки-разделителя границы.
NOTE: These "preamble" and "epilogue" areas are generally not used because of the lack of proper typing of these parts and the lack of clear semantics for handling these areas at gateways, particularly X.400 gateways. However, rather than leaving the preamble area blank, many MIME implementations have found this to be a convenient place to insert an explanatory note for recipients who read the message with pre-MIME software, since such notes will be ignored by MIME-compliant software.
ПРИМЕЧАНИЕ. Эти области «преамбулы» и «эпилога» обычно не используются из-за отсутствия надлежащей типизации этих частей и отсутствия чёткой семантики обработки этих областей на шлюзах, в особенности на шлюзах X.400. Однако вместо того, чтобы оставлять область преамбулы пустой, многие MIME-реализации помещают туда пояснительную записку для получателей, читающих сообщение с помощью программного обеспечения, не поддерживающего MIME, поскольку такие записки будут проигнорированы MIME-совместимым программным обеспечением.
NOTE: Because boundary delimiters must not appear in the body parts being encapsulated, a user agent must exercise care to choose a unique boundary parameter value. The boundary parameter value in the example above could have been the result of an algorithm designed to produce boundary delimiters with a very low probability of already existing in the data to be encapsulated without having to prescan the data. Alternate algorithms might result in more "readable" boundary delimiters for a recipient with an old user agent, but would require more attention to the possibility that the boundary delimiter might appear at the beginning of some line in the encapsulated part. The simplest boundary delimiter line possible is something like "---", with a closing boundary delimiter line of "-----".

5.1.2. Handling Nested Messages and Multiparts
5.1.2. Обработка вложенных сообщений и составных объектов
The "message/rfc822" subtype defined in a subsequent section of this document has no terminating condition other than running out of data. Similarly, an improperly truncated "multipart" entity may not have any terminating boundary marker, and can turn up operationally due to mail system malfunctions.
Подтип «message/rfc822», определённый в последующем разделе настоящего документа, не имеет условия завершения, кроме исчерпания данных. Аналогично неправильно усечённый «multipart»-объект может не иметь завершающего маркера границы и может встретиться при эксплуатации из-за сбоев почтовой системы.
It is essential that such entities be handled correctly when they are themselves imbedded inside of another "multipart" structure. MIME implementations are therefore required to recognize outer level boundary markers at ANY level of inner nesting. It is not sufficient to only check for the next expected marker or other terminating condition.
Существенно, чтобы такие объекты обрабатывались правильно, когда они сами встроены внутрь другой «multipart»-структуры. Поэтому от MIME-реализаций требуется распознавать маркеры границ внешнего уровня на ЛЮБОМ уровне внутренней вложенности. Недостаточно проверять только границы соответствующего уровня вложенности — иначе вложенная структура может быть ошибочно интерпретирована как содержащая больше данных, чем есть на самом деле.
5.1.3. Mixed Subtype
5.1.3. Подтип mixed
The "mixed" subtype of "multipart" is intended for use when the body parts are independent and need to be bundled in a particular order. Any "multipart" subtypes that an implementation does not recognize must be treated as being of subtype "mixed".
Подтип «mixed» типа «multipart» предназначен для использования, когда части тела независимы и должны быть увязаны в определённом порядке. Любые подтипы «multipart», которые реализация не распознаёт, должны обрабатываться как подтип «mixed».
5.1.4. Alternative Subtype
5.1.4. Подтип alternative
The "multipart/alternative" type is syntactically identical to "multipart/mixed", but the semantics are different. In particular, each of the body parts is an "alternative" version of the same information.
Тип «multipart/alternative» синтаксически идентичен «multipart/mixed», но семантика иная. В частности, каждая из частей тела является «альтернативной» версией одной и той же информации.
Systems should recognize that the content of the various parts are interchangeable. Systems should choose the "best" type based on the local environment and references, in some cases even through user interaction. As with "multipart/mixed", the order of body parts is significant. In this case, the alternatives appear in an order of increasing faithfulness to the original content. In general, the best choice is the LAST part of a type supported by the recipient system's local environment.
Системы должны понимать, что содержимое различных частей взаимозаменяемо. Системы должны выбирать «наилучший» тип исходя из локального окружения и возможностей, в некоторых случаях даже посредством взаимодействия с пользователем. Как и в случае «multipart/mixed», порядок частей тела имеет значение. В данном случае последняя часть является «лучшей» альтернативой с точки зрения составителя.

С точки зрения разработчика могло бы показаться более разумным обратить этот порядок и помещать простейшую альтернативу последней. Однако размещение простейшей альтернативы первой — это наиболее дружественный по отношению к пользователю вариант, когда объекты «multipart/alternative» просматриваются с помощью программного обеспечения, не поддерживающего MIME: тогда читатель хотя бы увидит осмысленный текст, а не коды форматирования.
It may be the case that some user agents, if they can recognize more than one of the formats, will prefer to offer the user the choice of which format to view. This makes sense, for example, if a message includes both a nicely- formatted image version and an easily-edited text version. What is most critical, however, is that the user not automatically be shown multiple versions of the same data. Either the user should be shown the last recognized version or should be given the choice.
Может случиться, что некоторые пользовательские агенты, распознающие более одного из форматов, предпочтут предоставить пользователю выбор, какой формат просматривать. Это имеет смысл, например, если сообщение включает как красиво оформленную графическую версию, так и легко редактируемую текстовую версию. Однако наиболее важно то, что пользователю не следует автоматически показывать несколько версий одних и тех же данных. Пользователю следует показать либо последнюю распознанную версию, либо предоставить выбор.
THE SEMANTICS OF CONTENT-ID IN MULTIPART/ALTERNATIVE: Each part of a "multipart/alternative" entity represents the same data, but the mappings between the two are not necessarily without information loss. For example, information is lost when translating ODA to PostScript or plain text. It is recommended that each part should have a different Content-ID value in the case where the information content of the two parts is not identical. And when the information content is identical -- for example, where several parts of type "message/external-body" specify alternate ways to access the identical data -- the same Content-ID field value should be used, to optimize any caching mechanisms that might be present on the recipient's end. However, the Content-ID values used by the parts should NOT be the same Content-ID value that describes the "multipart/alternative" as a whole, if there is any such Content-ID field. That is, one Content-ID value will refer to the "multipart/alternative" entity, while one or more other Content-ID values will refer to the parts inside it.
СЕМАНТИКА CONTENT-ID В MULTIPART/ALTERNATIVE. Каждая часть объекта «multipart/alternative» представляет одни и те же данные, но соответствия между ними не обязательно свободны от потери информации. Например, информация теряется при переводе ODA в PostScript или обычный текст. Рекомендуется, чтобы каждая часть имела различное значение Content-ID в случае, когда информационное содержание двух частей не идентично. А когда информационное содержание идентично — например, когда несколько частей типа «message/external-body» указывают альтернативные способы доступа к одним и тем же данным — следует использовать одно и то же значение поля Content-ID, чтобы оптимизировать любые механизмы кэширования, которые могут присутствовать на стороне получателя. Однако значения Content-ID, используемые частями, НЕ ДОЛЖНЫ совпадать со значением Content-ID, описывающим «multipart/alternative» в целом, если такое поле Content-ID существует. То есть одно значение Content-ID будет ссылаться на объект «multipart/alternative», а одно или несколько других значений Content-ID — на части внутри него.
5.1.5. Digest Subtype
5.1.5. Подтип digest
This document defines a "digest" subtype of the "multipart" Content- Type. This type is syntactically identical to "multipart/mixed", but the semantics are different. In particular, in a digest, the default Content-Type value for a body part is changed from "text/plain" to "message/rfc822". This is done to allow a more readable digest format that is largely compatible (except for the quoting convention) with RFC 934.
Настоящий документ определяет подтип «digest» типа содержимого «multipart». Этот тип синтаксически идентичен «multipart/mixed», но семантика иная. В частности, в digest значение Content-Type по умолчанию для части тела изменяется с «text/plain» на «message/rfc822». Это сделано, чтобы обеспечить более читаемый формат digest, в значительной степени совместимый (за исключением соглашения о квотировании) с RFC 934.
Note: Though it is possible to specify a Content-Type value for a body part in a digest which is other than "message/rfc822", such as a "text/plain" part containing a description of the material in the digest, actually doing so is undesireble. The "multipart/digest" Content-Type is intended to be used to send collections of messages. If a "text/plain" part is needed, it should be included as a seperate part of a "multipart/mixed" message.

5.1.6. Parallel Subtype
5.1.6. Подтип parallel
This document defines a "parallel" subtype of the "multipart" Content-Type. This type is syntactically identical to "multipart/mixed", but the semantics are different. In particular, in a parallel entity, the order of body parts is not significant.
Настоящий документ определяет подтип «parallel» типа содержимого «multipart». Этот тип синтаксически идентичен «multipart/mixed», но семантика иная. В частности, в объекте parallel порядок частей тела не имеет значения.
A common presentation of this type is to display all of the parts simultaneously on hardware and software that are capable of doing so. However, composing agents should be aware that many mail readers will lack this capability and will show the parts serially in any event.
Обычное представление этого типа состоит в одновременном отображении всех частей на аппаратном и программном обеспечении, способном это делать. Однако составляющие агенты должны учитывать, что многие почтовые программы не обладают такой возможностью и в любом случае будут показывать части последовательно.
5.1.7. Other Multipart Subtypes

5.2. Message Media Type
5.2. Тип носителя message
It is frequently desirable, in sending mail, to encapsulate another mail message. A special media type, "message", is defined to facilitate this. In particular, the "rfc822" subtype of "message" is used to encapsulate RFC 822 messages.
При отправке почты часто желательно инкапсулировать другое почтовое сообщение. Для этого определён специальный тип носителя «message». В частности, подтип «rfc822» типа «message» используется для инкапсуляции сообщений RFC 822.
NOTE: It has been suggested that subtypes of "message" might be defined for forwarded or rejected messages. However, forwarded and rejected messages can be handled as multipart messages in which the first part contains any control or descriptive information, and a second part, of type "message/rfc822", is the forwarded or rejected message. Composing rejection and forwarding messages in this manner will preserve the type information on the original message and allow it to be correctly presented to the recipient, and hence is strongly encouraged.
ПРИМЕЧАНИЕ. Было высказано предложение определить подтипы «message» для пересылаемых или отклонённых сообщений. Однако пересылаемые и отклонённые сообщения могут обрабатываться как составные сообщения, в которых первая часть содержит любую управляющую или описательную информацию, а вторая часть типа «message/rfc822» является пересылаемым или отклонённым сообщением. Составление сообщений об отклонении и пересылке таким образом сохранит информацию о типе исходного сообщения и позволит корректно представить его получателю, и потому настоятельно рекомендуется.
Subtypes of "message" often impose restrictions on what encodings are allowed. These restrictions are described in conjunction with each specific subtype.
Подтипы «message» часто накладывают ограничения на допустимые кодировки. Эти ограничения описываются вместе с каждым конкретным подтипом.
Mail gateways, relays, and other mail handling agents are commonly known to alter the top-level header of an RFC 822 message. In particular, they frequently add, remove, or reorder header fields. These operations are explicitly forbidden for the encapsulated headers embedded in the bodies of messages of type "message."
Почтовые шлюзы, ретрансляторы и другие агенты обработки почты, как известно, изменяют заголовок верхнего уровня сообщения RFC 822. В частности, они часто добавляют, удаляют или переупорядочивают поля заголовка. Эти операции явно запрещены для инкапсулированных заголовков, встроенных в «message/rfc822». Обратите внимание, что эта защита применяется к инкапсулированным заголовкам, а не к каким-либо заголовкам, добавленным к объекту «message/rfc822».
5.2.1. RFC822 Subtype
5.2.1. Подтип RFC822
A media type of "message/rfc822" indicates that the body contains an encapsulated message, with the syntax of an RFC 822 message. However, unlike top-level RFC 822 messages, the restriction that each "message/rfc822" body must include a "From", "Date", and at least one destination header is removed and replaced with the requirement that at least one of "From", "Subject", or "Date" must be present. It should be noted that, despite the use of the numbers "822", a "message/rfc822" entity isn't restricted to material in strict conformance to RFC822, nor are the semantics of "message/rfc822" objects restricted to the semantics defined in RFC822. More specifically, a "message/rfc822" message could well be a News article or a MIME message.
Тип носителя «message/rfc822» указывает, что тело содержит инкапсулированное сообщение с синтаксисом сообщения RFC 822. Однако, в отличие от сообщений RFC 822 верхнего уровня, ограничение, согласно которому каждое тело «message/rfc822» должно включать поля «From», «Date» и хотя бы одно поле адреса назначения, к инкапсулированным сообщениям не применяется. Следует отметить, что, несмотря на использование чисел «822», объект «message/rfc822» не ограничен материалом, строго соответствующим RFC 822, и семантика объектов «message/rfc822» не ограничена семантикой, определённой в RFC 822. Точнее, объект «message/rfc822» может содержать любые данные, которые передаются в почтовом сообщении.
No encoding other than "7bit", "8bit", or "binary" is permitted for the body of a "message/rfc822" entity. The message header fields are always US-ASCII in any case, and data within the body can still be encoded, in which case the Content-Transfer-Encoding header field in the encapsulated message will reflect this. Non-US-ASCII text in the headers of an encapsulated message can be specified using the mechanisms described in RFC 2047.
Для тела объекта «message/rfc822» не допускается никакое кодирование, кроме «7bit», «8bit» или «binary». Поля заголовка сообщения в любом случае всегда US-ASCII, а данные внутри тела всё равно могут быть закодированы; в этом случае поле заголовка Content-Transfer-Encoding в инкапсулированном заголовке будет иметь соответствующее значение. Не-US-ASCII текст в заголовках инкапсулированного сообщения может быть задан с помощью механизмов, описанных в RFC 2047.
5.2.2. Partial Subtype
5.2.2. Подтип partial
The "partial" subtype is defined to allow large entities to be delivered as several separate pieces of mail and automatically reassembled by a receiving user agent. (The concept is similar to IP fragmentation and reassembly in the basic Internet Protocols.) This mechanism can be used when intermediate transport agents limit the size of individual messages that can be sent. The media type "message/partial" thus indicates that the body contains a fragment of a larger entity.
Подтип «partial» определён, чтобы позволить доставлять большие объекты несколькими отдельными кусками почты и автоматически собирать их принимающим пользовательским агентом. (Концепция аналогична фрагментации и сборке в базовых интернет-протоколах.) Этот механизм может использоваться либо для обхода ограничений на размер сообщения, накладываемых промежуточными транспортными агентами, либо для облегчения доставки очень больших объектов по ненадёжным каналам, где передача целиком может быть неэффективной.
Because data of type "message" may never be encoded in base64 or quoted-printable, a problem might arise if "message/partial" entities are constructed in an environment that supports binary or 8bit transport. The problem is that the binary data would be split into multiple "message/partial" messages, each of them requiring binary transport. If such messages were encountered at a gateway into a 7bit transport environment, there would be no way to properly encode them for the 7bit world, aside from waiting for all of the fragments, reassembling the inner message, and then encoding the reassembled data in base64 or quoted-printable. Since it is possible that different fragments might go through different gateways, even this is not an acceptable solution. For this reason, it is specified that entities of type "message/partial" must always have a content- transfer-encoding of 7bit (the default). In particular, even in environments that support binary or 8bit transport, the use of a content- transfer-encoding of "8bit" or "binary" is explicitly prohibited for MIME entities of type "message/partial". This in turn implies that the inner message must not use "8bit" or "binary" encoding.
Поскольку данные типа «message» никогда не могут кодироваться в base64 или quoted-printable, может возникнуть проблема, если объекты «message/partial» формируются в окружении, поддерживающем двоичную передачу или передачу 8-битных данных. Проблема в том, что двоичные данные будут разбиты на несколько сообщений «message/partial», каждое из которых требует двоичной передачи. Если такие сообщения попадут на шлюз в 7-битное транспортное окружение, не будет способа правильно закодировать их для 7-битного мира, кроме как дождаться всех фрагментов, собрать внутреннее сообщение и затем закодировать собранные данные в base64 или quoted-printable. Поскольку возможно, что разные фрагменты пройдут через разные шлюзы, даже это не является приемлемым решением. По этой причине установлено, что объекты типа «message/partial» должны всегда иметь кодировку переноса содержимого 7bit (по умолчанию). В частности, даже в окружениях, поддерживающих двоичную передачу или передачу 8-битных данных, использование кодировки переноса содержимого «8bit» или «binary» для MIME-объектов типа «message/partial» явно запрещено. Это в свою очередь означает, что внутреннее сообщение не должно использовать кодировку «8bit» или «binary».
Because some message transfer agents may choose to automatically fragment large messages, and because such agents may use very different fragmentation thresholds, it is possible that the pieces of a partial message, upon reassembly, may prove themselves to comprise a partial message. This is explicitly permitted.
Поскольку некоторые агенты передачи сообщений могут по своему выбору автоматически фрагментировать большие сообщения, и поскольку такие агенты могут использовать очень разные пороги фрагментации, возможно, что части частичного сообщения при сборке окажутся сами составляющими частичное сообщение.
Three parameters must be specified in the Content-Type field of type "message/partial": The first, "id", is a unique identifier, as close to a world-unique identifier as possible, to be used to match the fragments together. (In general, the identifier is essentially a message-id; if placed in double quotes, it can be ANY message-id, in accordance with the BNF for "parameter" given in RFC 2045.) The second, "number", an integer, is the fragment number, which indicates where this fragment fits into the sequence of fragments. The third, "total", another integer, is the total number of fragments. This third subfield is required on the final fragment, and is optional (though encouraged) on the earlier fragments. Note also that these parameters may be given in any order.
В поле Content-Type типа «message/partial» должны быть указаны три параметра. Первый, «id», — уникальный идентификатор, насколько это возможно близкий к всемирно уникальному, используемый для сопоставления фрагментов друг с другом. (В общем случае идентификатор по существу является message-id; если он заключён в двойные кавычки, он может быть ЛЮБЫМ message-id в соответствии с BNF для «parameter», приведённой в RFC 2045.) Второй, «number», целое число, — номер фрагмента, указывающий, куда данный фрагмент встаёт в последовательности фрагментов. Третий, «total», ещё одно целое число, — общее число фрагментов. Это третье подполе требуется в последнем фрагменте и необязательно (хотя и рекомендуется) в предыдущих фрагментах. Обратите также внимание, что эти параметры могут быть заданы в любом порядке.
Thus, the second piece of a 3-piece message may have either of the following header fields:
Таким образом, вторая часть сообщения из трёх частей может иметь любое из следующих полей заголовка:

Content-Type: Message/Partial; number=2; total=3;
id="oc=jpbe0M2Yt4s@thumper.bellcore.com"
id="oc=jpbe0M2Yt4s@thumper.bellcore.com"
Content-Type: Message/Partial;
[не переводится: пример сообщения / граница multipart]

id="oc=jpbe0M2Yt4s@thumper.bellcore.com"; number=2
But the third piece MUST specify the total number of fragments:
Но третья часть ДОЛЖНА указывать общее число фрагментов:

Content-Type: Message/Partial; number=3; total=3;

Note that fragment numbering begins with 1, not 0.
Обратите внимание, что нумерация фрагментов начинается с 1, а не с 0.
When the fragments of an entity broken up in this manner are put together, the result is always a complete MIME entity, which may have its own Content-Type header field, and thus may contain any other data type.
Когда фрагменты разбитого таким образом объекта соединяются, результат всегда представляет собой полный MIME-объект, который может иметь собственное поле заголовка Content-Type и, следовательно, может содержать любой другой тип данных.
5.2.2.1. Message Fragmentation and Reassembly
5.2.2.1. Фрагментация и сборка сообщений
The semantics of a reassembled partial message must be those of the "inner" message, rather than of a message containing the inner message. This makes it possible, for example, to send a large audio message as several partial messages, and still have it appear to the recipient as a simple audio message rather than as an encapsulated message containing an audio message. That is, the encapsulation of the message is considered to be "transparent".
Семантика собранного частичного сообщения должна быть семантикой «внутреннего» сообщения, а не сообщения, содержащего внутреннее сообщение. Это позволяет, например, отправить большое звуковое сообщение как несколько частичных сообщений, и всё равно оно будет представлено получателю как одно звуковое сообщение, а не как сообщение, содержащее звуковое сообщение. То есть инкапсуляция сообщения считается «прозрачной».
When generating and reassembling the pieces of a "message/partial" message, the headers of the encapsulated message must be merged with the headers of the enclosing entities. In this process the following rules must be observed:
При формировании и сборке частей сообщения «message/partial» заголовки инкапсулированного сообщения должны объединяться с заголовками объемлющих объектов. В этом процессе должны соблюдаться следующие правила:
(1) Fragmentation agents must split messages at line boundaries only. This restriction is imposed because splits at points other than the ends of lines in turn depends on message transports being able to preserve the semantics of messages that don't end with a CRLF sequence. Many transports are incapable of preserving such semantics.
(1) Агенты фрагментации должны разбивать сообщения только по границам строк. Это ограничение вводится потому, что разбиение в точках, отличных от концов строк, зависит, в свою очередь, от способности транспортов сообщений сохранять семантику сообщений, не заканчивающихся разрывом строки.
(2) All of the header fields from the initial enclosing message, except those that start with "Content-" and the specific header fields "Subject", "Message-ID", "Encrypted", and "MIME-Version", must be copied, in order, to the new message.
(2) Все поля заголовка из первоначального объемлющего сообщения, кроме тех, что начинаются с «Content-», и конкретных полей заголовка «Subject», «Message-ID», «Encrypted» и «MIME-Version», должны быть скопированы по порядку в новое сообщение.
(3) The header fields in the enclosed message which start with "Content-", plus the "Subject", "Message-ID", "Encrypted", and "MIME-Version" fields, must be appended, in order, to the header fields of the new message. Any header fields in the enclosed message which do not start with "Content-" (except for the "Subject", "Message-ID", "Encrypted", and "MIME- Version" fields) will be ignored and dropped.
(3) Поля заголовка вложенного сообщения, начинающиеся с «Content-», а также поля «Subject», «Message-ID», «Encrypted» и «MIME-Version», должны быть добавлены по порядку к полям заголовка нового сообщения. Любые поля заголовка во вложенном сообщении, которые не начинаются с «Content-» и не являются одним из четырёх перечисленных полей, должны быть отброшены.
(4) All of the header fields from the second and any subsequent enclosing messages are discarded by the reassembly process.
(4) Все поля заголовка из второго и любого последующего объемлющего сообщения отбрасываются в процессе сборки.

Включение поля «References» в заголовки второй и последующих частей фрагментированного сообщения, ссылающегося на Message-Id предыдущей части, может быть полезно для почтовых программ, понимающих и отслеживающих ссылки. Однако формирование такого поля не требуется. Наконец, следует отметить, что поле заголовка «Encrypted» стало устаревшим с появлением Privacy Enhanced Messaging (PEM) [RFC-1421, RFC-1422, RFC-1423, RFC-1424], но приведённые выше правила тем не менее, как считается, описывают правильный способ обращения с ним, если оно встретится.
5.2.3. External-Body Subtype
5.2.3. Подтип external-body
The external-body subtype indicates that the actual body data are not included, but merely referenced. In this case, the parameters describe a mechanism for accessing the external data.
Подтип external-body указывает, что фактические данные тела не включены, а лишь указаны ссылкой. В этом случае параметры описывают механизм доступа к внешним данным.
When a MIME entity is of type "message/external-body", it consists of a header, two consecutive CRLFs, and the message header for the encapsulated message. If another pair of consecutive CRLFs appears, this of course ends the message header for the encapsulated message. However, since the encapsulated message's body is itself external, it does NOT appear in the area that follows. For example, consider the following message:
Когда MIME-объект имеет тип «message/external-body», он состоит из заголовка, двух последовательных CRLF и заголовка сообщения инкапсулированного сообщения. Если появляется ещё одна пара последовательных CRLF, это, естественно, завершает заголовок сообщения инкапсулированного сообщения. Однако, поскольку тело инкапсулированного сообщения само по себе является внешним, оно НЕ появляется в следующей за этим области. Например, рассмотрим следующее сообщение:
Content-type: message/external-body;
[не переводится: пример сообщения / граница multipart]
access-type=local-file; name="/u/nsb/Me.jpeg"
access-type=local-file; name="/u/nsb/Me.jpeg"
Content-type: image/jpeg Content-ID: <id42@guppylake.bellcore.com> Content-Transfer-Encoding: binary
Content-type: image/jpeg Content-ID: <id42@guppylake.bellcore.com> Content-Transfer-Encoding: binary
THIS IS NOT REALLY THE BODY!
ЭТО НА САМОМ ДЕЛЕ НЕ ТЕЛО!
The area at the end, which might be called the "phantom body", is ignored for most external-body messages. However, it may be used to contain auxiliary information for some such messages, as indeed it is when the access-type is "mail- server". The only access-type defined in this document that uses the phantom body is "mail-server", but other access-types may be defined in the future in other specifications that use this area.
Область в конце, которую можно назвать «фантомным телом», игнорируется для большинства сообщений external-body. Однако она может использоваться для хранения вспомогательной информации для некоторых таких сообщений, как это и делается, когда типом доступа является «mail-server». Единственный тип доступа, определённый в настоящем документе как использующий «фантомное тело», — «mail-server».
The encapsulated headers in ALL "message/external-body" entities MUST include a Content-ID header field to give a unique identifier by which to reference the data. This identifier may be used for caching mechanisms, and for recognizing the receipt of the data when the access-type is "mail-server".
Инкапсулированные заголовки ВСЕХ объектов «message/external-body» ДОЛЖНЫ включать поле заголовка Content-ID, дающее уникальный идентификатор, по которому можно ссылаться на данные. Этот идентификатор может использоваться механизмами кэширования и для распознавания получения данных.
Note that, as specified here, the tokens that describe external-body data, such as file names and mail server commands, are required to be in the US-ASCII character set. If this proves problematic in practice, a new mechanism may be required as a future extension to MIME, either as newly defined access-types for "message/external-body" or by some other mechanism.
Обратите внимание, что, как здесь указано, лексемы, описывающие данные external-body, такие как имена файлов и команды почтового сервера, должны находиться в наборе символов US-ASCII. Если на практике это окажется проблематичным, может потребоваться новый механизм как будущее расширение MIME — либо в виде новых определённых типов доступа для «message/external-body», либо посредством какого-либо иного механизма.
As with "message/partial", MIME entities of type "message/external- body" MUST have a content-transfer-encoding of 7bit (the default). In particular, even in environments that support binary or 8bit transport, the use of a content- transfer-encoding of "8bit" or "binary" is explicitly prohibited for entities of type "message/external-body".
Как и в случае «message/partial», MIME-объекты типа «message/external-body» ДОЛЖНЫ иметь кодировку переноса содержимого 7bit (по умолчанию). В частности, даже в окружениях, поддерживающих двоичную или 8-битную передачу, использование кодировки переноса содержимого «8bit» не допускается.
5.2.3.1. General External-Body Parameters
5.2.3.1. Общие параметры external-body
The parameters that may be used with any "message/external- body" are:
Параметры, которые могут использоваться с любым «message/external-body»:
(1) ACCESS-TYPE -- A word indicating the supported access mechanism by which the file or data may be obtained. This word is not case sensitive. Values include, but are not limited to, "FTP", "ANON-FTP", "TFTP", "LOCAL- FILE", and "MAIL-SERVER". Future values, except for experimental values beginning with "X-", must be registered with IANA, as described in RFC 2048. This parameter is unconditionally mandatory and MUST be present on EVERY "message/external-body".
(1) ACCESS-TYPE — слово, указывающее поддерживаемый механизм доступа, с помощью которого могут быть получены файл или данные. Это слово не чувствительно к регистру. Значения включают, но не ограничиваются: «FTP», «ANON-FTP», «TFTP», «LOCAL-FILE» и «MAIL-SERVER». Будущие значения, за исключением экспериментальных, начинающихся с «X-», должны быть зарегистрированы в IANA, как описано в RFC 2048. Этот параметр безусловно обязателен и ДОЛЖЕН присутствовать в КАЖДОМ «message/external-body».
(2) EXPIRATION -- The date (in the RFC 822 "date-time" syntax, as extended by RFC 1123 to permit 4 digits in the year field) after which the existence of the external data is not guaranteed. This parameter may be used with ANY access-type and is ALWAYS optional.
(2) EXPIRATION — дата (в синтаксисе «date-time» RFC 822, расширенном RFC 1123 для допуска 4 цифр в поле года), после которой существование внешних данных не гарантируется. Этот параметр может использоваться с ЛЮБЫМ типом доступа и ВСЕГДА необязателен.
(3) SIZE -- The size (in octets) of the data. The intent of this parameter is to help the recipient decide whether or not to expend the necessary resources to retrieve the external data. Note that this describes the size of the data in its canonical form, that is, before any Content-Transfer-Encoding has been applied or after the data have been decoded. This parameter may be used with ANY access-type and is ALWAYS optional.
(3) SIZE — размер (в октетах) данных. Назначение этого параметра — помочь получателю решить, стоит ли расходовать необходимые ресурсы на получение внешних данных. Обратите внимание, что здесь описывается размер данных в их канонической форме, то есть до применения любой кодировки переноса содержимого или после декодирования данных. Этот параметр может использоваться с ЛЮБЫМ типом доступа и ВСЕГДА необязателен.
(4) PERMISSION -- A case-insensitive field that indicates whether or not it is expected that clients might also attempt to overwrite the data. By default, or if permission is "read", the assumption is that they are not, and that if the data is retrieved once, it is never needed again. If PERMISSION is "read-write", this assumption is invalid, and any local copy must be considered no more than a cache. "Read" and "Read- write" are the only defined values of permission. This parameter may be used with ANY access-type and is ALWAYS optional.
(4) PERMISSION — нечувствительное к регистру поле, указывающее, ожидается ли, что клиенты могут также попытаться перезаписать данные. По умолчанию или если permission имеет значение «read», предполагается, что они этого не делают и что если данные получены один раз, то повторное получение не требуется. Если permission имеет значение «read-write», предполагается, что клиенты могут также попытаться перезаписать данные.
The precise semantics of the access-types defined here are described in the sections that follow.
Точная семантика определённых здесь типов доступа описана в последующих разделах.
5.2.3.2. The 'ftp' and 'tftp' Access-Types
5.2.3.2. Типы доступа 'ftp' и 'tftp'
An access-type of FTP or TFTP indicates that the message body is accessible as a file using the FTP [RFC-959] or TFTP [RFC- 783] protocols, respectively. For these access-types, the following additional parameters are mandatory:
Тип доступа FTP или TFTP указывает, что тело сообщения доступно как файл с использованием протоколов FTP [RFC-959] или TFTP [RFC-783] соответственно. Для этих типов доступа обязательны следующие дополнительные параметры:
(1) NAME -- The name of the file that contains the actual body data.
(1) NAME — имя файла, содержащего фактические данные тела.
(2) SITE -- A machine from which the file may be obtained, using the given protocol. This must be a fully qualified domain name, not a nickname.
(2) SITE — машина, с которой может быть получен файл с использованием данного протокола. Это должно быть полностью определённое доменное имя, а не псевдоним.
(3) Before any data are retrieved, using FTP, the user will generally need to be asked to provide a login id and a password for the machine named by the site parameter. For security reasons, such an id and password are not specified as content-type parameters, but must be obtained from the user.
(3) Перед получением каких-либо данных с использованием FTP пользователя, как правило, потребуется попросить предоставить идентификатор входа и пароль для машины, указанной параметром site. По соображениям безопасности такой идентификатор и пароль не указываются в качестве параметров content-type, а должны запрашиваться интерактивно.
In addition, the following parameters are optional:
Кроме того, следующие параметры необязательны:
(1) DIRECTORY -- A directory from which the data named by NAME should be retrieved.
(1) DIRECTORY — каталог, из которого следует извлечь данные, указанные параметром NAME.
(2) MODE -- A case-insensitive string indicating the mode to be used when retrieving the information. The valid values for access-type "TFTP" are "NETASCII", "OCTET", and "MAIL", as specified by the TFTP protocol [RFC- 783]. The valid values for access-type "FTP" are "ASCII", "EBCDIC", "IMAGE", and "LOCALn" where "n" is a decimal integer, typically 8. These correspond to the representation types "A" "E" "I" and "L n" as specified by the FTP protocol [RFC-959]. Note that "BINARY" and "TENEX" are not valid values for MODE and that "OCTET" or "IMAGE" or "LOCAL8" should be used instead. IF MODE is not specified, the default value is "NETASCII" for TFTP and "ASCII" otherwise.
(2) MODE — нечувствительная к регистру строка, указывающая режим, который следует использовать при извлечении информации. Допустимые значения для типа доступа «TFTP» — «NETASCII», «OCTET» и «MAIL», как определено протоколом TFTP [RFC-783]. Допустимые значения для типа доступа «FTP» — «ASCII», «EBCDIC», «IMAGE» и «LOCALn», где «n» — десятичное целое число, обычно 8. Они соответствуют типам представления «A», «E», «I» и «L n», как определено протоколом FTP [RFC-959]. Обратите внимание, что «BINARY» и «TENEX» не являются допустимыми значениями для MODE и что вместо них следует использовать «OCTET», «IMAGE» или «LOCAL8». Если MODE не указан, значением по умолчанию является «NETASCII» для TFTP и «ASCII» в остальных случаях.
5.2.3.3. The 'anon-ftp' Access-Type
5.2.3.3. Тип доступа 'anon-ftp'
The "anon-ftp" access-type is identical to the "ftp" access type, except that the user need not be asked to provide a name and password for the specified site. Instead, the ftp protocol will be used with login "anonymous" and a password that corresponds to the user's mail address.
Тип доступа «anon-ftp» идентичен типу доступа «ftp», за исключением того, что пользователя не нужно просить предоставить имя и пароль для указанного сайта. Вместо этого протокол ftp будет использоваться со входом «anonymous» и паролем, соответствующим адресу электронной почты пользователя.
5.2.3.4. The 'local-file' Access-Type
5.2.3.4. Тип доступа 'local-file'
An access-type of "local-file" indicates that the actual body is accessible as a file on the local machine. Two additional parameters are defined for this access type:
Тип доступа «local-file» указывает, что фактическое тело доступно как файл на локальной машине. Для этого типа доступа определены два дополнительных параметра:
(1) NAME -- The name of the file that contains the actual body data. This parameter is mandatory for the "local-file" access-type.
(1) NAME — имя файла, содержащего фактические данные тела. Этот параметр обязателен для типа доступа «local-file».
(2) SITE -- A domain specifier for a machine or set of machines that are known to have access to the data file. This optional parameter is used to describe the locality of reference for the data, that is, the site or sites at which the file is expected to be visible. Asterisks may be used for wildcard matching to a part of a domain name, such as "*.bellcore.com", to indicate a set of machines on which the data should be directly visible, while a single asterisk may be used to indicate a file that is expected to be universally available, e.g., via a global file system.
(2) SITE — спецификатор домена для машины или набора машин, о которых известно, что они имеют доступ к файлу данных. Этот необязательный параметр используется для описания локальности ссылки на данные, то есть сайта или сайтов, на которых ожидается видимость файла. Звёздочки могут использоваться для сопоставления по шаблону с частью доменного имени, например «*.bellcore.com», чтобы указать набор машин, на которых данные должны быть непосредственно видимы, тогда как одиночная звёздочка может использоваться для указания файла, который, как ожидается, доступен повсеместно, например через глобальную файловую систему.
5.2.3.5. The 'mail-server' Access-Type
5.2.3.5. Тип доступа 'mail-server'
The "mail-server" access-type indicates that the actual body is available from a mail server. Two additional parameters are defined for this access-type:
Тип доступа «mail-server» указывает, что фактическое тело доступно с почтового сервера. Для этого типа доступа определены два дополнительных параметра:
(1) SERVER -- The addr-spec of the mail server from which the actual body data can be obtained. This parameter is mandatory for the "mail-server" access-type.
(1) SERVER — addr-spec почтового сервера, с которого можно получить фактические данные тела. Этот параметр обязателен для типа доступа «mail-server».
(2) SUBJECT -- The subject that is to be used in the mail that is sent to obtain the data. Note that keying mail servers on Subject lines is NOT recommended, but such mail servers are known to exist. This is an optional parameter.
(2) SUBJECT — тема, которая должна использоваться в почте, отправляемой для получения данных. Обратите внимание, что использование Subject в качестве ключа для почтовых серверов НЕ рекомендуется, но известно, что такие почтовые серверы существуют. Это необязательный параметр.
Because mail servers accept a variety of syntaxes, some of which is multiline, the full command to be sent to a mail server is not included as a parameter in the content-type header field. Instead, it is provided as the "phantom body" when the media type is "message/external-body" and the access-type is mail-server.
Поскольку почтовые серверы принимают разнообразные синтаксисы, некоторые из которых многострочные, полная команда, подлежащая отправке почтовому серверу, не включается как параметр в поле заголовка content-type. Вместо этого она предоставляется как «фантомное тело», когда тип носителя — «message/external-body» с типом доступа MAIL-SERVER.
Note that MIME does not define a mail server syntax. Rather, it allows the inclusion of arbitrary mail server commands in the phantom body. Implementations must include the phantom body in the body of the message it sends to the mail server address to retrieve the relevant data.
Обратите внимание, что MIME не определяет синтаксис почтового сервера. Скорее, он позволяет включать произвольные команды почтового сервера в фантомное тело. Реализации должны включать фантомное тело в тело сообщения, отправляемого на адрес почтового сервера для получения данных.
Unlike other access-types, mail-server access is asynchronous and will happen at an unpredictable time in the future. For this reason, it is important that there be a mechanism by which the returned data can be matched up with the original "message/external-body" entity. MIME mail servers must use the same Content-ID field on the returned message that was used in the original "message/external-body" entities, to facilitate such matching.
В отличие от других типов доступа, доступ к почтовому серверу асинхронен и произойдёт в непредсказуемое время в будущем. По этой причине важно, чтобы существовал механизм, с помощью которого возвращённые данные можно сопоставить с исходным «message/external-body». Content-ID и Message-ID инкапсулированного сообщения, а также параметр id, если он присутствует, могут использоваться таким механизмом.
5.2.3.6. External-Body Security Issues
5.2.3.6. Вопросы безопасности external-body
"Message/external-body" entities give rise to two important security issues:
Объекты «message/external-body» порождают две важные проблемы безопасности:
(1) Accessing data via a "message/external-body" reference effectively results in the message recipient performing an operation that was specified by the message originator. It is therefore possible for the message originator to trick a recipient into doing something they would not have done otherwise. For example, an originator could specify a action that attempts retrieval of material that the recipient is not authorized to obtain, causing the recipient to unwittingly violate some security policy. For this reason, user agents capable of resolving external references must always take steps to describe the action they are to take to the recipient and ask for explicit permisssion prior to performing it.
(1) Доступ к данным через ссылку «message/external-body» фактически приводит к тому, что получатель сообщения выполняет операцию, указанную отправителем сообщения. Поэтому отправитель сообщения может обманным путём побудить получателя сделать то, чего он иначе не сделал бы. Например, отправитель может указать действие, пытающееся получить материал, на получение которого получатель не имеет прав, в результате чего получатель непреднамеренно нарушит некоторую политику безопасности. По этой причине пользовательские агенты, способные разрешать внешние ссылки, должны всегда описывать получателю действие, которое они собираются выполнить, и запрашивать явное разрешение перед его выполнением.
The 'mail-server' access-type is particularly vulnerable, in that it causes the recipient to send a new message whose contents are specified by the original message's originator. Given the potential for abuse, any such request messages that are constructed should contain a clear indication that they were generated automatically (e.g. in a Comments: header field) in an attempt to resolve a MIME "message/external-body" reference.
Тип доступа «mail-server» особенно уязвим в том отношении, что он заставляет получателя отправить новое сообщение, содержимое которого указано отправителем исходного сообщения. Учитывая возможность злоупотребления, любые такие формируемые сообщения-запросы должны содержать явное указание на то, что они сформированы автоматически (например, в поле заголовка Comments:) в попытке разрешить ссылку MIME «message/external-body».
(2) MIME will sometimes be used in environments that provide some guarantee of message integrity and authenticity. If present, such guarantees may apply only to the actual direct content of messages -- they may or may not apply to data accessed through MIME's "message/external-body" mechanism. In particular, it may be possible to subvert certain access mechanisms even when the messaging system itself is secure.
(2) MIME иногда будет использоваться в окружениях, обеспечивающих определённую гарантию целостности и подлинности сообщения. Если такая гарантия существует, она может применяться только к фактическому непосредственному содержимому сообщений — она может применяться или не применяться к данным, доступ к которым осуществляется через механизм «message/external-body» MIME. В частности, возможно подменить некоторые механизмы доступа даже тогда, когда сама система обмена сообщениями защищена.
It should be noted that this problem exists either with or without the availabilty of MIME mechanisms. A casual reference to an FTP site containing a document in the text of a secure message brings up similar issues -- the only difference is that MIME provides for automatic retrieval of such material, and users may place unwarranted trust is such automatic retrieval mechanisms.
Следует отметить, что эта проблема существует как при наличии механизмов MIME, так и без них. Непринудительная ссылка на FTP-сайт, содержащий документ, в тексте защищённого сообщения порождает аналогичные вопросы — единственное различие состоит в том, что MIME предусматривает автоматическое получение такого материала, и пользователи могут питать необоснованное доверие к таким механизмам автоматического получения.
5.2.3.7. Examples and Further Explanations
5.2.3.7. Примеры и дополнительные пояснения
When the external-body mechanism is used in conjunction with the "multipart/alternative" media type it extends the functionality of "multipart/alternative" to include the case where the same entity is provided in the same format but via different accces mechanisms. When this is done the originator of the message must order the parts first in terms of preferred formats and then by preferred access mechanisms. The recipient's viewer should then evaluate the list both in terms of format and access mechanisms.
Когда механизм external-body используется вместе с типом носителя «multipart/alternative», он расширяет функциональность «multipart/alternative», включая случай, когда один и тот же объект предоставляется в одном и том же формате, но через разные механизмы доступа. При этом отправитель сообщения должен упорядочить части сначала по предпочтительным форматам, а затем по предпочтительным механизмам доступа. Программа просмотра получателя должна затем оценить список как по форматам, так и по механизмам доступа.
With the emerging possibility of very wide-area file systems, it becomes very hard to know in advance the set of machines where a file will and will not be accessible directly from the file system. Therefore it may make sense to provide both a file name, to be tried directly, and the name of one or more sites from which the file is known to be accessible. An implementation can try to retrieve remote files using FTP or any other protocol, using anonymous file retrieval or prompting the user for the necessary name and password. If an external body is accessible via multiple mechanisms, the sender may include multiple entities of type "message/external-body" within the body parts of an enclosing "multipart/alternative" entity.
В связи с возникающей возможностью создания очень широкомасштабных файловых систем становится очень трудно заранее знать набор машин, с которых файл будет или не будет доступен напрямую из файловой системы. Поэтому может иметь смысл предоставить как имя файла, которое следует испробовать напрямую, так и имя одного или нескольких сайтов, с которых файл, как известно, доступен. Реализация может попытаться получить удалённые файлы с использованием FTP или любого другого протокола, используя анонимное получение файлов или запрашивая у пользователя необходимые имя и пароль. Если внешнее тело доступно через несколько механизмов, отправитель может включить несколько объектов типа «message/external-body» в части тела объемлющего объекта «multipart/alternative».
However, the external-body mechanism is not intended to be limited to file retrieval, as shown by the mail-server access-type. Beyond this, one can imagine, for example, using a video server for external references to video clips. The embedded message header fields which appear in the body of the "message/external-body" data must be used to declare the media type of the external body if it is anything other than plain US-ASCII text, since the external body does not have a header section to declare its type. Similarly, any Content-transfer-encoding other than "7bit" must also be declared here. Однако механизм external-body не задумывался ограниченным извлечением файлов, как показывает тип доступа mail-server. Кроме того, можно представить, например, использование видеосервера для внешних ссылок на видеоклипы. Встроенные поля заголовка сообщения, которые появляются в теле данных «message/external-body», должны использоваться для объявления типа носителя внешнего тела, если это что-либо иное, нежели простой текст US-ASCII, поскольку внешнее тело не имеет раздела заголовка для объявления своего типа. Аналогично любая кодировка переноса содержимого, отличная от «7bit», также должна быть объявлена здесь. Like the "message/partial" type, the "message/external-body" media type is intended to be transparent, that is, to convey the data type in the external body rather than to convey a message with a body of that type. Thus the headers on the outer and inner parts must be merged using the same rules as for "message/partial". In particular, this means that the Content-type and Subject fields are overridden, but the From field is preserved.
Как и тип «message/partial», тип носителя «message/external-body» задуман прозрачным, то есть передающим тип данных во внешнем теле, а не сообщение с телом этого типа. Таким образом, заголовки внешних и внутренних частей должны объединяться по тем же правилам, что и для «message/partial». В частности, это означает, что поля Content-type и Subject переопределяются, а поле From сохраняется.
Note that since the external bodies are not transported along with the external body reference, they need not conform to transport limitations that apply to the reference itself. In particular, Internet mail transports may impose 7bit and line length limits, but these do not automatically apply to binary external body references. Thus a Content-Transfer-Encoding is not generally necessary, though it is permitted.
Обратите внимание, что, поскольку внешние тела не передаются вместе со ссылкой external-body, они не обязаны соответствовать транспортным ограничениям, применимым к самой ссылке. В частности, интернет-почтовые транспорты могут налагать ограничения на 7-битность и длину строк, но к внешнему телу они не применяются.
Note that the body of a message of type "message/external-body" is governed by the basic syntax for an RFC 822 message. In particular, anything before the first consecutive pair of CRLFs is header information, while anything after it is body information, which is ignored for most access-types.
Обратите внимание, что тело сообщения типа «message/external-body» подчиняется базовому синтаксису сообщения RFC 822. В частности, всё, что находится до первой последовательной пары CRLF, является информацией заголовка, а всё, что после неё, — информацией тела, включая «фантомное тело».
5.2.4. Other Message Subtypes
5.2.4. Прочие подтипы message
MIME implementations must in general treat unrecognized subtypes of "message" as being equivalent to "application/octet-stream".
MIME-реализации должны в общем случае обрабатывать нераспознанные подтипы «message» как эквивалентные «application/octet-stream».
Future subtypes of "message" intended for use with email should be restricted to "7bit" encoding. A type other than "message" should be used if restriction to "7bit" is not possible.
Будущие подтипы «message», предназначенные для использования с электронной почтой, должны быть ограничены кодировкой «7bit». Если ограничение кодировкой «7bit» невозможно, следует использовать тип, отличный от «message».
6. Experimental Media Type Values
6. Область экспериментальных типов носителя
A media type value beginning with the characters "X-" is a private value, to be used by consenting systems by mutual agreement. Any format without a rigorous and public definition must be named with an "X-" prefix, and publicly specified values shall never begin with "X-". (Older versions of the widely used Andrew system use the "X- BE2" name, so new systems should probably choose a different name.)
Значение типа носителя, начинающееся с символов «X-», является частным значением, предназначенным для использования согласными системами по взаимному соглашению. Любой формат, не имеющий строгого и публичного определения, должен именоваться с префиксом «X-», а публично определённые значения никогда не должны начинаться с «X-».
In general, the use of "X-" top-level types is strongly discouraged. Implementors should invent subtypes of the existing types whenever possible. In many cases, a subtype of "application" will be more appropriate than a new top-level type.
В общем случае использование типов верхнего уровня «X-» решительно не рекомендуется. Разработчикам следует по возможности изобретать подтипы существующих типов. Во многих случаях подтип «application» будет более уместным, нежели новый тип верхнего уровня.
7. Summary
7. Итоги
The five discrete media types provide provide a standardized mechanism for tagging entities as "audio", "image", or several other kinds of data. The composite "multipart" and "message" media types allow mixing and hierarchical structuring of entities of different types in a single message. A distinguished parameter syntax allows further specification of data format details, particularly the specification of alternate character sets. Additional optional header fields provide mechanisms for certain extensions deemed desirable by many implementors. Finally, a number of useful media types are defined for general use by consenting user agents, notably "message/partial" and "message/external-body".
Пять дискретных типов носителя предоставляют стандартизованный механизм маркировки объектов как «audio», «image» или нескольких других видов данных. Составные типы носителя «multipart» и «message» позволяют смешивать и иерархически структурировать объекты различных типов в одном сообщении. Особый синтаксис параметров позволяет дополнительно специфицировать детали формата данных, в частности указывать альтернативные наборы символов. Дополнительные необязательные поля заголовка предоставляют механизмы для некоторых расширений, признанных желательными многими разработчиками. Наконец, ряд полезных типов носителя определён для общего использования согласными пользовательскими агентами, в частности «message/partial» и «message/external-body».
9. Security Considerations
9. Вопросы безопасности
Security issues are discussed in the context of the "application/postscript" type, the "message/external-body" type, and in RFC 2048. Implementors should pay special attention to the security implications of any media types that can cause the remote execution of any actions in the recipient's environment. In such cases, the discussion of the "application/postscript" type may serve as a model for considering other media types with remote execution capabilities.
Вопросы безопасности рассматриваются в контексте типов «application/postscript», «message/external-body» и в RFC 2048. Разработчикам следует обращать особое внимание на последствия для безопасности любых типов носителя, которые могут привести к удалённому выполнению каких-либо действий в окружении получателя. В таких случаях рассмотрение типа «application/postscript» может служить образцом для оценки других типов носителя, обладающих возможностями удалённого выполнения.
