Abstract

3.1. Background on Message Body Encoding
3.1. Справочные сведения о кодировании тела сообщения
SIP [RFC3261] messages consist of an initial line (request line in requests and status line in responses), a set of header fields, and an optional message body. The message body is described using header fields such as Content-Disposition, Content-Encoding, and Content- Type, which provide information on its contents. Сообщения SIP [RFC3261] состоят из стартовой строки (строки запроса в запросах и строки состояния в ответах), набора полей заголовков и необязательного тела сообщения. Тело сообщения описывается с помощью таких полей заголовков, как Content-Disposition, Content-Encoding и Content-Type, которые предоставляют сведения о его содержимом. Body parts are also described using header fields such as Content-Disposition, Content-Encoding, and Content-Type, which provide information on the contents of a particular body part. SIP uses S/MIME [RFC3851] to protect message bodies. As specified in [RFC3261], UASs that cannot decrypt a message body or a body part can use the 493 (Undecipherable) response to report the error.
В SIP для защиты тел сообщений используется S/MIME [RFC3851]. Как указано в [RFC3261], UAS, не имеющие возможности расшифровать тело сообщения или часть тела, могут сообщить об ошибке с помощью ответа 493 (Undecipherable).
3.2. UA Behavior to Encode Binary Message Bodies
3.2. Действия UA при кодировании двоичных тел сообщений
SIP messages can carry binary message bodies such as legacy signalling objects [RFC3204]. SIP proxy servers are 8-bit safe. That is, they are able to handle binary bodies. Therefore, there is no need to use encodings such as base64 to transport binary bodies in SIP messages. Consequently, UAs SHOULD use the binary transfer encoding [RFC4289] for all payloads in SIP, including binary payloads. The only case where a UA MAY use a different encoding is when transferring application data between applications that only handle a different encoding (e.g., base64). 4. 'multipart' Message Bodies
Сообщения SIP могут нести двоичные тела сообщений, такие как объекты устаревшей сигнализации [RFC3204]. Прокси-серверы SIP безопасны для 8-битных данных, то есть способны обрабатывать двоичные тела. Поэтому нет необходимости применять такие кодировки, как base64, для передачи двоичных тел в сообщениях SIP. Следовательно, UA СЛЕДУЕТ использовать двоичное кодирование передачи [RFC4289] для всех полезных нагрузок в SIP, включая двоичные. Единственный случай, когда UA МОЖЕТ использовать другую кодировку, — это передача прикладных данных между приложениями, которые работают только с другой кодировкой (например, base64). 4. Составные (multipart) тела сообщений
This section deals with 'multipart' message bodies and their handling.
В настоящем разделе рассматриваются составные (multipart) тела сообщений и их обработка.
4.1. Background on 'multipart' Message Bodies
4.1. Справочные сведения о составных (multipart) телах сообщений
[RFC3261] did not mandate support for 'multipart' message bodies in MIME format [RFC2046]. However, since [RFC3261] was written, many SIP extensions rely on them.
[RFC3261] не требовал поддержки составных (multipart) тел сообщений в формате MIME [RFC2046]. Однако после публикации [RFC3261] многие расширения SIP стали на них опираться.
The use of 'multipart/mixed' MIME bodies is a useful tool to build SIP extensions. An example of such an extension could be the inclusion of location information in an INVITE request. Such an INVITE request would use the 'multipart/mixed' MIME type [RFC2046] to carry two body parts: a session description and a location object. An example of an existing extension that uses 'multipart/mixed' to send a session description and a legacy-signalling object is defined in [RFC3204].
Использование тел MIME 'multipart/mixed' — удобное средство для построения расширений SIP. Примером такого расширения может служить включение сведений о местоположении в запрос INVITE. Такой запрос INVITE использовал бы тип MIME 'multipart/mixed' [RFC2046] для переноса двух частей тела: описания сеанса и объекта местоположения. Пример существующего расширения, использующего 'multipart/mixed' для передачи описания сеанса и объекта устаревшей сигнализации, определён в [RFC3204].
Another MIME type that is useful to build SIP extensions is 'multipart/alternative' [RFC2046]. Each body part within a 'multipart/alternative' carries an alternative version of the same information.
Другой тип MIME, полезный для построения расширений SIP, — 'multipart/alternative' [RFC2046]. Каждая часть тела в составе 'multipart/alternative' несёт альтернативный вариант одной и той же информации.
The transition from SDP to new session description protocols could be implemented using 'multipart/alternative' bodies. SIP messages (e.g., INVITE requests) could carry a 'multipart/alternative' body with two body parts: a session description written in SDP and a session description written in a newer session description format. Legacy recipient UAs would use the session description written in SDP. New recipient UAs would use the one written in the newer format.
Переход от SDP к новым протоколам описания сеанса можно было бы реализовать с помощью тел 'multipart/alternative'. Сообщения SIP (например, запросы INVITE) могли бы нести тело 'multipart/alternative' с двумя частями: описанием сеанса на SDP и описанием сеанса в более новом формате. Устаревшие принимающие UA использовали бы описание сеанса на SDP. Новые принимающие UA использовали бы вариант в более новом формате.
Nested MIME bodies are yet another useful tool to build and combine SIP extensions. Using the extensions in the previous examples, a UA that supported a new session description format and that needed to include a location object in an INVITE request would include a 'multipart/mixed' body with two body parts: a location object and a 'multipart/alternative'. The 'multipart/alternative' body part would, in turn, have two body parts: a session description written in SDP and a session description written in the newer session description format.
Вложенные тела MIME — ещё одно полезное средство для построения и объединения расширений SIP. Используя расширения из предыдущих примеров, UA, поддерживающий новый формат описания сеанса и нуждающийся во включении объекта местоположения в запрос INVITE, включил бы тело 'multipart/mixed' с двумя частями: объектом местоположения и 'multipart/alternative'. Часть тела 'multipart/alternative', в свою очередь, содержала бы две части: описание сеанса на SDP и описание сеанса в более новом формате.
4.2. Mandatory Support for 'multipart' Message Bodies
4.2. Обязательная поддержка составных (multipart) тел сообщений
For all MIME-based extensions to work, the recipient needs to be able to decode the multipart bodies. Therefore, SIP UAs MUST support parsing 'multipart' MIME bodies, including nested body parts. Additionally, UAs MUST support the 'multipart/mixed' and 'multipart/ alternative' MIME types. Support for other MIME types such as 'multipart/related' is OPTIONAL.
Чтобы работало любое расширение на основе MIME, получатель должен уметь декодировать составные тела. Поэтому UA SIP ДОЛЖНЫ поддерживать разбор тел MIME 'multipart', включая вложенные части тела. Кроме того, UA ДОЛЖНЫ поддерживать типы MIME 'multipart/mixed' и 'multipart/alternative'. Поддержка других типов MIME, таких как 'multipart/related', НЕОБЯЗАТЕЛЬНА.
Note that, by default, unknown 'multipart' subtypes are treated as 'multipart/mixed'. Also note that SIP extensions can also include 'multipart' MIME bodies in responses. That is why both UACs and UASs need to support 'multipart' bodies.
Заметим, что по умолчанию неизвестные подтипы 'multipart' обрабатываются как 'multipart/mixed'. Заметим также, что расширения SIP могут включать тела MIME 'multipart' и в ответах. Именно поэтому поддержка составных тел нужна как UAC, так и UAS.
Legacy SIP UAs without support for 'multipart' bodies generate a 415 (Unsupported Media Type) response when they receive a 'multipart' body in a request. A UAC sending a 'multipart' body can receive such an error response when communicating with a legacy SIP UA that predates this specification.
Устаревшие UA SIP без поддержки составных тел при получении составного тела в запросе формируют ответ 415 (Unsupported Media Type). UAC, отправляющий составное тело, может получить такой ответ об ошибке при взаимодействии с устаревшим UA SIP, выпущенным до этой спецификации.
It has been observed in the field that a number of legacy SIP UAs without support for 'multipart' bodies simply ignored those bodies when they were received. These UAs did not return any error response. Unsurprisingly, SIP UAs not being able to report this type of error have caused serious interoperability problems in the past.
На практике наблюдалось, что ряд устаревших UA SIP без поддержки составных тел просто игнорировал их при получении. Эти UA не возвращали никакого ответа об ошибке. Неудивительно, что неспособность UA SIP сообщать об ошибках такого рода в прошлом вызывала серьёзные проблемы совместимости.
4.3. UA Behavior to Generate 'multipart' Message Bodies
4.3. Действия UA при формировании составных (multipart) тел сообщений
UAs SHOULD avoid unnecessarily nesting body parts because doing so would, unnecessarily, make processing the body more laborious for the receiver. However, [RFC2046] states that a 'multipart' media type with a single body part is useful in some circumstances (e.g., for sending non-text media types). In any case, UAs SHOULD NOT nest one 'multipart/mixed' within another unless there is a need to reference the nested one (i.e., using the Content ID of the nested body part). Additionally, UAs SHOULD NOT nest one 'multipart/alternative' within another.
UA СЛЕДУЕТ избегать излишнего вложения частей тела, поскольку это без необходимости усложняет обработку тела для получателя. Однако [RFC2046] указывает, что составной тип медиа с единственной частью тела полезен в некоторых обстоятельствах (например, для передачи нетекстовых типов медиа). В любом случае UA НЕ СЛЕДУЕТ вкладывать один 'multipart/mixed' в другой, если только нет необходимости ссылаться на вложенный (то есть использовать Content-ID вложенной части тела). Кроме того, UA НЕ СЛЕДУЕТ вкладывать один 'multipart/alternative' в другой.
Note that UAs receiving unnecessarily nested body parts treat them as if they were not nested.
Заметим, что UA, получающие излишне вложенные части тела, обрабатывают их так, как если бы они не были вложенными.

6. 'multipart/alternative' Message Bodies
6. Составные (multipart/alternative) тела сообщений
This section deals with 'multipart/alternative' message bodies and their handling.
В настоящем разделе рассматриваются составные (multipart/alternative) тела сообщений и их обработка.
6.1. Background on 'multipart/alternative' Message Bodies
6.1. Справочные сведения о составных (multipart/alternative) телах сообщений
Each body part within a 'multipart/alternative' carries an alternative version of the same information. The body parts are ordered so that the last one is the richest representation of the information. The recipient of a 'multipart/alternative' body chooses the last body part it understands.
Каждая часть тела в составе 'multipart/alternative' несёт альтернативный вариант одной и той же информации. Части тела упорядочены так, что последняя является наиболее полным представлением информации. Получатель тела 'multipart/alternative' выбирает последнюю часть тела, которую он понимает.
Note that within a body part encoded in a given format (i.e., of a given content type), there can be optional elements that can provide richer information to the recipient in case the recipient supports them. For example, in SDP (Session Description Protocol) [RFC4566], those optional elements are encoded in 'a' lines. These types of optional elements are internal to a body part and are not visible at the MIME level. That is, a body part is understood if the recipient understands its content type, regardless of whether or not the body part's optional elements are understood.
Заметим, что внутри части тела, закодированной в данном формате (то есть имеющей данный тип содержимого), могут присутствовать необязательные элементы, способные предоставить получателю более полную информацию, если получатель их поддерживает. Например, в SDP (Session Description Protocol) [RFC4566] такие необязательные элементы кодируются строками 'a'. Эти виды необязательных элементов внутренне присущи части тела и не видны на уровне MIME. То есть часть тела считается понятой, если получатель понимает её тип содержимого, независимо от того, понимает ли он необязательные элементы этой части тела.
Note as well that each part of a 'multipart/alternative' body represents the same data, but the mapping between any two parts is not necessarily without information loss. For example, information can be lost when translating 'text/html' to 'text/ plain'. [RFC2046] recommends that each part should have a different Content-ID value in the case where the information content of the two parts is not identical.
Заметим также, что каждая часть тела 'multipart/alternative' представляет одни и те же данные, но отображение между любыми двумя частями не обязательно происходит без потери информации. Например, информация может теряться при переводе 'text/html' в 'text/plain'. [RFC2046] рекомендует, чтобы каждая часть имела отличающееся значение Content-ID в случае, когда информационное содержимое двух частей не идентично.

6.2. Действия UA при формировании составных (multipart/alternative) тел сообщений

Раздел 8.2 требует, чтобы все части тела верхнего уровня в составе 'multipart/alternative' имели одинаковый тип диспозиции.
The 'session' and 'early-session' [RFC3959] disposition types require that all the body parts of a 'multipart/alternative' body have different content types. Consequently, for the 'session' and 'early- session' disposition types, UAs MUST NOT place more than one body part with a given content type in a 'multipart/alternative' body. That is, for 'session' and 'early-session', no body part within a 'multipart/alternative' can have the same content type as another body part within the same 'multipart/alternative'.
Типы диспозиции 'session' и 'early-session' [RFC3959] требуют, чтобы все части тела 'multipart/alternative' имели разные типы содержимого. Следовательно, для типов диспозиции 'session' и 'early-session' UA НЕ ДОЛЖНЫ помещать в тело 'multipart/alternative' более одной части тела с данным типом содержимого. То есть для 'session' и 'early-session' ни одна часть тела в составе 'multipart/alternative' не может иметь тот же тип содержимого, что и другая часть тела в том же 'multipart/alternative'.

7. 'multipart/related' Message Bodies
7. Составные (multipart/related) тела сообщений
This section deals with 'multipart/related' message bodies and their handling.
В настоящем разделе рассматриваются составные (multipart/related) тела сообщений и их обработка.
7.1. Background on 'multipart/related' Message Bodies
7.1. Справочные сведения о составных (multipart/related) телах сообщений
Compound objects in MIME are represented using the 'multipart/ related' content type [RFC2387]. The body parts within a particular 'multipart/related' body are all part of a compound object and are processed as such. The body part within a 'multipart/related' body that needs to be processed first is referred to as the 'root' body part. The root body part of a 'multipart/related' body is identified by the 'start' parameter, which is a Content-Type header field parameter and contains a Content-ID URL pointing to the root body part. If the start parameter is not present, the root body part is, by default, the first body part of the 'multipart/related'. An example of a compound object is a web page that contains images. The html body part would be the root. The remaining body parts would contain the images. An example of a SIP extension using 'multipart/ related' is specified in [RFC4662].
Составные объекты в MIME представляются с помощью типа содержимого 'multipart/related' [RFC2387]. Все части тела в составе конкретного тела 'multipart/related' являются частями составного объекта и обрабатываются как таковые. Часть тела в составе 'multipart/related', которую нужно обработать первой, называется 'корневой' частью тела. Корневая часть тела 'multipart/related' идентифицируется параметром 'start', который является параметром поля заголовка Content-Type и содержит URL Content-ID, указывающий на корневую часть тела. Если параметр start отсутствует, корневой частью тела по умолчанию является первая часть тела 'multipart/related'. Примером составного объекта является веб-страница, содержащая изображения. Корневой была бы часть тела html. Остальные части тела содержали бы изображения. Пример расширения SIP, использующего 'multipart/related', определён в [RFC4662].
7.2. UA Behavior to Generate 'multipart/related' Message Bodies
7.2. Действия UA при формировании составных (multipart/related) тел сообщений
This section does not specify any additional behavior regarding how to generate 'multipart/related' bodies. This section is simply included for completeness.
В настоящем разделе не определяется никакого дополнительного поведения в отношении формирования тел 'multipart/related'. Раздел включён просто для полноты.
7.3. UA Behavior to Process 'multipart/related' Message Bodies
7.3. Действия UA при обработке составных (multipart/related) тел сообщений
Per [RFC2387], a UA processing a 'multipart/related' body processes the body as a compound object ignoring the disposition types of the body parts within it. Ignoring the disposition types of the individual body parts makes sense in the context in which 'multipart/ related' was originally specified. For instance, in the example of the web page, the implicit disposition type for the images would be 'inline', since the images are displayed as indicated by the root html file. However, in SIP, the disposition types of the individual body parts within a 'multipart/related' play an important role and, thus, need to be considered by the UA processing the 'multipart/ related'. Different SIP extensions that use the same disposition type for the 'multipart/related' body can be distinguished by the disposition types of the individual body parts within the 'multipart/ related'. Consequently, SIP UAs processing a 'multipart/related' body with a given disposition type MUST process the disposition types of the body parts within it according to the SIP extension making use the disposition type of the 'multipart/related'.
Согласно [RFC2387], UA, обрабатывающий тело 'multipart/related', обрабатывает его как составной объект, игнорируя типы диспозиции частей тела внутри него. Игнорирование типов диспозиции отдельных частей тела имеет смысл в контексте, в котором изначально был специфицирован 'multipart/related'. Например, в примере с веб-страницей неявным типом диспозиции для изображений был бы 'inline', поскольку изображения отображаются так, как указано в корневом html-файле. Однако в SIP типы диспозиции отдельных частей тела в составе 'multipart/related' играют важную роль и поэтому должны учитываться UA, обрабатывающим 'multipart/related'. Различные расширения SIP, использующие один и тот же тип диспозиции для тела 'multipart/related', можно различить по типам диспозиции отдельных частей тела внутри 'multipart/related'. Следовательно, UA SIP, обрабатывающие тело 'multipart/related' с данным типом диспозиции, ДОЛЖНЫ обрабатывать типы диспозиции частей тела внутри него в соответствии с расширением SIP, использующим тип диспозиции 'multipart/related'.
Note that UAs that do not understand 'multipart/related' will treat 'multipart/related' bodies as 'multipart/mixed' bodies. These UAs will not be able to process a given body as a compound object.
Заметим, что UA, не понимающие 'multipart/related', будут обрабатывать тела 'multipart/related' как тела 'multipart/mixed'. Эти UA не смогут обработать данное тело как составной объект.
Instead, they will process the body parts according to their disposition type as if each body part was independent from each other.
Вместо этого они обрабатывают части тела в соответствии с типом их размещения так, как если бы каждая часть тела была независима от остальных.
8. Disposition Types
8. Типы диспозиции
This section deals with disposition types in message bodies.
В настоящем разделе рассматриваются типы диспозиции в телах сообщений.
8.1. Background on Content and Disposition Types in SIP
8.1. Справочные сведения о типах содержимого и диспозиции в SIP
The Content-Disposition header field, defined in [RFC2183] and extended by [RFC3261], describes how to handle a SIP message's body or an individual body part. Examples of disposition types used in SIP in the Content-Disposition header field are 'session' and 'render'.
Поле заголовка Content-Disposition, определённое в [RFC2183] и расширенное в [RFC3261], описывает, как следует обрабатывать тело сообщения SIP или отдельную часть тела. Примерами типов диспозиции, используемых в SIP в поле заголовка Content-Disposition, являются 'session' и 'render'.
[RFC3204] and [RFC3459] define the 'handling' parameter for the Content-Disposition header field. This parameter describes how a UAS reacts if it receives a message body whose content type or disposition type it does not understand. If the parameter has the value 'optional', the UAS ignores the message body; if the parameter has the value 'required', the UAS returns a 415 (Unsupported Media Type) response. The default value for the 'handling' parameter is 'required'. The following is an example of a Content-Disposition header field:
В [RFC3204] и [RFC3459] для поля заголовка Content-Disposition определён параметр 'handling'. Этот параметр описывает, как UAS реагирует при получении тела сообщения, тип содержимого или тип диспозиции которого он не понимает. Если параметр имеет значение 'optional', UAS игнорирует тело сообщения; если параметр имеет значение 'required', UAS возвращает ответ 415 (Unsupported Media Type). Значением параметра 'handling' по умолчанию является 'required'. Ниже приведён пример поля заголовка Content-Disposition:
Content-Disposition: signal; handling=optional
Content-Disposition: signal; handling=optional
[RFC3204] identifies two situations where a UAS (User Agent Server) needs to reject a request with a body part whose handling is required:
В [RFC3204] определены две ситуации, в которых UAS (сервер пользовательского агента) должен отклонить запрос с частью тела, обработка которой требуется:
1. if it has an unknown content type.
1. если он имеет неизвестный тип содержимого.
2. if it has an unknown disposition type.
2. если он имеет неизвестный тип диспозиции.
If the UAS did not understand the content type of the body part, the UAS can add an Accept header field to its 415 (Unsupported Media Type) response listing the content types that the UAS does understand. Nevertheless, there is no mechanism for a UAS that does not understand the disposition type of a body part to inform the UAC about which disposition type was not understood or about the disposition types that are understood by the UAS.
Если UAS не понял тип содержимого части тела, он может добавить поле заголовка Accept в свой ответ 415 (Unsupported Media Type), перечислив типы содержимого, которые UAS понимает. Тем не менее для UAS, который не понимает тип диспозиции части тела, не существует механизма, позволяющего сообщить UAC, какой именно тип диспозиции не понят или какие типы диспозиции понимает UAS.
The reason for not having such a mechanism is that disposition types are typically supported within a context. Outside that context, a UA need not support the disposition type. For example, a UA can support the 'session' disposition type for body parts in INVITE and UPDATE requests and their responses. However, the same UA would not support the 'session' disposition type in MESSAGE requests.
Причина отсутствия такого механизма состоит в том, что типы диспозиции обычно поддерживаются в рамках контекста. Вне этого контекста UA может не поддерживать данный тип диспозиции. Например, UA может поддерживать тип диспозиции 'session' для частей тела в запросах INVITE и UPDATE и в ответах на них. Однако тот же UA не поддерживал бы тип диспозиции 'session' в запросах MESSAGE.
In another example, a UA can support the 'render' disposition type for 'text/plain' and 'text/html' body parts in MESSAGE requests. Additionally, the UA can support the 'session' disposition type for 'application/sdp' body parts in INVITE and UPDATE requests and their responses. However, the UA might not support the 'render' disposition type for 'application/sdp' body parts in MESSAGE requests, even if, in different contexts, the UA supported all of the following: the 'render' disposition type, the 'application/sdp' content type, and the MESSAGE method.
В другом примере UA может поддерживать тип диспозиции 'render' для частей тела 'text/plain' и 'text/html' в запросах MESSAGE. Кроме того, UA может поддерживать тип диспозиции 'session' для частей тела 'application/sdp' в запросах INVITE и UPDATE и ответах на них. Однако UA может не поддерживать тип диспозиции 'render' для частей тела 'application/sdp' в запросах MESSAGE, даже если в других контекстах UA поддерживал всё перечисленное: тип диспозиции 'render', тип содержимого 'application/sdp' и метод MESSAGE.
A given context is generally (but not necessarily) defined by a method, a disposition type, and a content type. Support for a specific context is usually defined within an extension. For example, the extension for instant messaging in SIP [RFC3428] mandates support for the MESSAGE method, the 'render' disposition type, and the 'text/plain' content type.
Данный контекст обычно (но не обязательно) определяется методом, типом диспозиции и типом содержимого. Поддержка конкретного контекста обычно определяется в рамках расширения. Например, расширение для обмена мгновенными сообщениями в SIP [RFC3428] требует поддержки метода MESSAGE, типа диспозиции 'render' и типа содержимого 'text/plain'.
Note that, effectively, content types are also supported within a context. Therefore, the use of the Accept header field in a 415 (Unsupported Media Type) response is not enough to describe in which contexts a particular content type is supported.
Заметим, что типы содержимого фактически также поддерживаются в рамках контекста. Поэтому использования поля заголовка Accept в ответе 415 (Unsupported Media Type) недостаточно, чтобы описать, в каких контекстах поддерживается тот или иной тип содержимого.
Therefore, support for a particular disposition type within a given context is typically signalled by the use of a particular method or an option-tag in a Supported or a Require header field. When support for a particular disposition type within a context is mandated, support for a default content type is also mandated (e.g., a UA that supports the 'session' disposition type in an INVITE request needs to support the 'application/sdp' content type).
Поэтому поддержка конкретного типа диспозиции в данном контексте обычно сигнализируется использованием конкретного метода или option-tag в поле заголовка Supported или Require. Когда поддержка конкретного типа диспозиции в контексте является обязательной, обязательной является и поддержка типа содержимого по умолчанию (например, UA, поддерживающий тип диспозиции 'session' в запросе INVITE, должен поддерживать тип содержимого 'application/sdp').
8.2. UA Behavior to Set the 'handling' Parameter
8.2. Действия UA при установке параметра 'handling'
As stated earlier, the 'handling' Content-Disposition parameter can take two values: 'required' or 'optional'. While it is typically easy for a UA to decide which type of handling an individual body part requires, setting the 'handling' parameter of 'multipart' bodies requires extra considerations.
Как указано ранее, параметр 'handling' поля Content-Disposition может принимать два значения: 'required' или 'optional'. Хотя UA обычно легко решает, какой тип обработки требует отдельная часть тела, установка параметра 'handling' для составных тел требует дополнительных соображений.
If the handling of a 'multipart/mixed' body as a whole is required for processing its enclosing body part or message, the UA MUST set the 'handling' parameter of the 'multipart/mixed' body to 'required'. Otherwise, the UA MUST set it to 'optional'. The 'handling' parameters of the top-level body parts within the 'multipart/mixed' body are set independently from the 'handling' parameter of the 'multipart/mixed' body. If the handling of a particular top-level body part is required, the UA MUST set the 'handling' parameter of that body part 'required'. Otherwise, the UA MUST set it to 'optional'.
Если обработка тела 'multipart/mixed' как единого целого требуется для обработки охватывающей его части тела или сообщения, UA ДОЛЖЕН установить параметр 'handling' тела 'multipart/mixed' в значение 'required'. В противном случае UA ДОЛЖЕН установить его в значение 'optional'. Параметры 'handling' частей тела верхнего уровня в составе 'multipart/mixed' устанавливаются независимо от параметра 'handling' тела 'multipart/mixed'. В противном случае UA ДОЛЖЕН установить его в значение 'optional'.
Per the previous rules, a 'multipart/mixed' body whose handling is optional can contain body parts whose handling is required. In such case, the receiver is required to process the body parts whose handling is required if and only if the receiver decides to process the optional 'multipart/mixed' body.
Согласно предыдущим правилам, тело 'multipart/mixed', обработка которого необязательна, может содержать части тела, обработка которых требуется. В таком случае получатель обязан обработать части тела, обработка которых требуется, тогда и только тогда, когда он решает обработать необязательное тело 'multipart/mixed'.
Also per the previous rules, a 'multipart/mixed' body whose handling is required can contain only body parts whose handling is optional. In such case, the receiver is required to process the body as a whole but, when processing it, the receiver may decide (based on its local policy) not to process any of the body parts.

Per [RFC3261], the default disposition type for 'application/sdp' is 'session' and for other bodies is 'render'. UAs SHOULD assign 'multipart/mixed' bodies a disposition type of 'render'.

If at least one top-level body part within a 'multipart/related' body has a 'handling' parameter of 'required', the UA SHOULD set the 'handling' parameter of the root body part to 'required'.
'handling' частей тела верхнего уровня в составе тела 'multipart/related' устанавливаются независимо от параметра 'handling' тела 'multipart/related'. Если обработка конкретной части тела верхнего уровня требуется, UA ДОЛЖЕН установить параметр 'handling' этой части тела в значение 'required'. В противном случае UA ДОЛЖЕН установить его в значение 'optional'. Если хотя бы одна часть тела верхнего уровня в составе тела 'multipart/related' имеет параметр 'handling', равный 'required', UA СЛЕДУЕТ установить параметр 'handling' корневой части тела в значение 'required'.
8.3. UA Behavior to Process 'multipart/alternative'
8.3. Действия UA при обработке 'multipart/alternative'
The receiver of a 'multipart/alternative' body MUST process the body based on its handling parameter. The receiver SHOULD ignore the handling parameters of the body parts within the 'multipart/ alternative'.
Получатель ДОЛЖЕН обрабатывать тело 'multipart/alternative' в соответствии с его параметром 'handling'. Получателю СЛЕДУЕТ игнорировать параметры 'handling' частей тела в составе 'multipart/alternative'.
8.4. UAS Behavior to Report Unsupported Message Bodies
8.4. Действия UAS при сообщении о неподдерживаемых телах сообщений
If a UAS cannot process a request because, in the given context, the UAS does not support the content type or the disposition type of a body part whose handling is required, the UAS SHOULD return a 415 (Unsupported Media Type) response even if the UAS supported the content type, the disposition type, or both in a different context.
Если UAS не может обработать запрос, поскольку в данном контексте он не поддерживает тип содержимого или тип диспозиции части тела, обработка которой требуется, UAS СЛЕДУЕТ вернуть ответ 415 (Unsupported Media Type), даже если UAS поддерживал тип содержимого, тип диспозиции или и то и другое в другом контексте.
Consequently, it is possible to receive a 415 (Unsupported Media Type) response with an Accept header field containing all the content types used in the request.
Следовательно, можно получить ответ 415 (Unsupported Media Type), поле заголовка Accept которого содержит все типы содержимого, использованные в запросе.
If a UAS receives a request with a body part whose disposition type is not compatible with the way the body part is supposed to be handled according to other parts of the SIP message (e.g., a Refer-To header field with a Content-ID URL pointing to a body part whose disposition type is 'session'), the UAS SHOULD return a 415 (Unsupported Media Type) response.
Если UAS получает запрос с частью тела, тип диспозиции которой несовместим со способом обработки этой части тела, предполагаемым другими частями сообщения SIP (например, поле заголовка Refer-To с URL Content-ID, указывающим на часть тела с типом диспозиции 'session'), UAS СЛЕДУЕТ вернуть ответ 415 (Unsupported Media Type).
9. Message Body Processing
9. Обработка тела сообщения
This section deals with the processing of message bodies and how that processing is influenced by the presence of references to them.
В настоящем разделе рассматривается обработка тел сообщений в SIP, а также то, каким образом на неё влияет наличие ссылок на эти тела.
9.1. Background on References to Message Body Parts
9.1. Справочные сведения о ссылках на части тела сообщений
Content-ID URLs allow creating references to body parts. A given Content-ID URL [RFC2392], which can appear in a header field or within a body part (e.g., in an SDP attribute), points to a particular body part. The way to handle that body part is defined by the field the Content-ID URL appears. For example, the extension to refer to multiple resources in SIP [RFC5368] places a Content-ID URL in a Refer-To header field. Such a Content-ID URL points to a body part that carries a URI list. In another example, the extension for file transfer in SDP [RFC5547] places a Content-ID URL in a 'file- icon' SDP attribute. This Content-ID URL points to a body part that carries a (typically small) picture.
URL Content-ID позволяют создавать ссылки на части тела. Данный URL Content-ID [RFC2392], который может присутствовать в поле заголовка или внутри части тела (например, в атрибуте SDP), указывает на конкретную часть тела. Способ обработки этой части тела определяется полем, в котором присутствует URL Content-ID. Например, расширение для ссылки на несколько ресурсов в SIP [RFC5368] помещает URL Content-ID в поле заголовка Refer-To. Такой URL Content-ID указывает на часть тела, несущую список URI. В другом примере расширение для передачи файлов в SDP [RFC5547] помещает URL Content-ID в атрибут SDP 'file-icon'. Этот URL Content-ID указывает на часть тела, несущую (обычно небольшой) рисунок.
9.2. UA Behavior to Generate References to Message Bodies
9.2. Действия UA при формировании ссылок на тела сообщений
UAs MUST only include forward references in the SIP messages they generate. That is, an element in a SIP message can reference a body part only if the body part appears after the element. Consequently, a given body part can only be referenced by another body part that appears before it or by a header field. Having only forward references allows recipients to process body parts as they parse them. They do not need to parse the remainder of the message in order to process a body part.
UA ДОЛЖНЫ включать в формируемые сообщения SIP только прямые ссылки. То есть элемент сообщения SIP может ссылаться на часть тела, только если эта часть тела расположена после элемента. Следовательно, на данную часть тела может ссылаться только другая часть тела, расположенная перед ней, или поле заголовка. Наличие только прямых ссылок позволяет получателям обрабатывать части тела по мере их разбора. Им не нужно разбирать остальную часть сообщения, чтобы обработать часть тела.
It was considered to only allow (forward) references among body parts that belonged to the same 'multipart/related' [RFC2387] wrapper. However, it was finally decided that this extra constraint was not necessary.
Рассматривался вариант разрешить (прямые) ссылки только между частями тела, принадлежащими одной обёртке 'multipart/related' [RFC2387]. Однако в итоге было решено, что это дополнительное ограничение не является необходимым.
9.3. UA Behavior to Process Message Bodies
9.3. Действия UA при обработке тел сообщений
In order to process a message body or a body part, a UA needs to know whether a SIP header field or another body part contains a reference to the message body or body part (e.g., a Content-ID URL pointing to it). If the body part is not referenced in any way (e.g., there are no header fields or other body parts with a Content-ID URL pointing to it), the UA processes the body part as indicated by its disposition type and the context in which the body part was received.
Чтобы обработать тело сообщения или часть тела, UA необходимо знать, содержит ли поле заголовка SIP или другая часть тела ссылку на это тело сообщения или часть тела (например, URL Content-ID, указывающий на неё). Если часть тела никак не упоминается (например, отсутствуют поля заголовков или другие части тела с URL Content-ID, указывающим на неё), UA обрабатывает часть тела так, как указано её типом диспозиции и контекстом, в котором часть тела была получена.
If the SIP message contains a reference to the body part, the UA processes the body part according to the reference. If the SIP message contains more than one reference to the body part (e.g., two header fields contain Content-ID URLs pointing to the body part), the UA processes the body part as many times as references are.
Если сообщение SIP содержит ссылку на часть тела, UA обрабатывает часть тела в соответствии со ссылкой. Если сообщение SIP содержит более одной ссылки на часть тела (например, два поля заголовков содержат URL Content-ID, указывающие на часть тела), UA обрабатывает часть тела столько раз, сколько имеется ссылок.
Note that, following the rules in [RFC3204], if a UA does not understand a body part whose handling is optional, the UA ignores it. Also note that the content indirection mechanism in SIP [RFC4483] allows UAs to point to external bodies. Therefore, a UA receiving a SIP message that uses content indirection could need to fetch a body part (e.g., using HTTP [RFC2616]) in order to process it.
Заметим, что в соответствии с правилами [RFC3204], если UA не понимает часть тела, обработка которой необязательна, он её игнорирует. Заметим также, что механизм косвенного указания содержимого в SIP [RFC4483] позволяет UA указывать на внешние тела. Поэтому UA, получающему сообщение SIP с косвенным указанием содержимого, может потребоваться получить часть тела (например, с помощью HTTP [RFC2616]), чтобы её обработать.
9.4. The 'by-reference' Disposition Type
9.4. Тип диспозиции 'by-reference'
Per the rules in Section 9.3, if a SIP message contains a reference to a body part, the UA processes the body part according to the reference. Since the reference provides the context in which the body part needs to be processed, the disposition type of the body part is irrelevant. However, a UA that missed a reference to a body part (e.g., because the reference was in a header field the UA did not support) would attempt to process the body part according to its disposition type alone. To keep this from happening, we define a new disposition type for the Content-Disposition header field: by- reference.
Согласно правилам раздела 9.3, если сообщение SIP содержит ссылку на часть тела, UA обрабатывает часть тела в соответствии со ссылкой. Поскольку ссылка задаёт контекст, в котором часть тела должна обрабатываться, тип диспозиции части тела не имеет значения. Однако UA, пропустивший ссылку на часть тела (например, потому что ссылка находилась в поле заголовка, которое UA не поддерживает), попытался бы обработать часть тела, руководствуясь только её типом диспозиции. Чтобы этого не происходило, мы определяем новый тип диспозиции для поля заголовка Content-Disposition: by-reference.
A body part whose disposition type is 'by-reference' needs to be handled according to a reference to the body part that is located in the same SIP message as the body part (given that SIP only allows forward references, the reference will appear in the same SIP message before the body part). A recipient of a body part whose disposition type is 'by-reference' that cannot find any reference to the body part (e.g., the reference was in a header field the recipient does not support and, thus, did not process) MUST NOT process the body part. Consequently, if the handling of the body part was required, the UA needs to report an error.
Часть тела, тип диспозиции которой — 'by-reference', должна обрабатываться в соответствии со ссылкой на эту часть тела, расположенной в том же сообщении SIP, что и часть тела (учитывая, что SIP допускает только прямые ссылки, ссылка появится в том же сообщении SIP перед частью тела). Получатель части тела с типом диспозиции 'by-reference', который не может найти никакой ссылки на эту часть тела (например, ссылка находилась в поле заголовка, которое получатель не поддерживает и, следовательно, не обработал), НЕ ДОЛЖЕН обрабатывать часть тела. Следовательно, если обработка части тела требовалась, UA должен сообщить об ошибке.
Note that extensions that predate this specification use references to body parts whose disposition type is not 'by- reference'. Those extensions use option-tags to make sure the recipient understands the whole extension and, thus, cannot miss the reference and attempt to process the body part according to its disposition type alone.
Заметим, что расширения, предшествующие этой спецификации, используют ссылки на части тела, тип диспозиции которых не 'by-reference'. Эти расширения используют option-tags, чтобы получатель понимал всё расширение целиком и, таким образом, не мог пропустить ссылку и попытаться обработать часть тела, руководствуясь только её типом диспозиции.
10. Guidelines to Authors of SIP Extensions
10. Рекомендации авторам расширений SIP
These guidelines are intended for authors of SIP extensions that involve, in some way, message bodies or body parts. These guidelines discuss aspects that authors of such extensions need to consider when designing them.
Настоящие рекомендации предназначены для авторов расширений SIP, которые тем или иным образом затрагивают тела сообщений или части тела. В рекомендациях обсуждаются аспекты, которые авторам таких расширений необходимо учитывать при их разработке.
This specification mandates support for 'multipart/mixed' and 'multipart/alternative'. At present, there are no SIP extensions that use different 'multipart' subtypes such as parallel [RFC2046] or digest [RFC2046]. If such extensions were to be defined in the future, their authors would need to make sure (e.g., by using an option-tag or by other means) that entities receiving those 'multipart' subtypes were able to process them. As stated earlier, UAs treat unknown 'multipart' subtypes as 'multipart/mixed'.
Настоящая спецификация требует поддержки 'multipart/mixed' и 'multipart/alternative'. В настоящее время не существует расширений SIP, использующих другие подтипы 'multipart', такие как parallel [RFC2046] или digest [RFC2046]. Если такие расширения будут определены в будущем, их авторам потребуется обеспечить (например, с помощью option-tag или иными средствами), чтобы объекты, получающие эти подтипы 'multipart', могли их обрабатывать. Как указано ранее, UA обрабатывают неизвестные подтипы 'multipart' как 'multipart/mixed'.
Authors of SIP extensions making use of 'multipart/related' bodies have to explicitly address the handling of the disposition types of the body parts within the 'multipart/related' body. Authors wishing to make use of 'multipart/related' bodies should keep in mind that UAs that do not understand 'multipart/related' will treat it as 'multipart/mixed'. If such treatment by a recipient is not acceptable for a particular extension, the authors of such extension would need to make sure (e.g., by using an option-tag or by other means) that entities receiving the 'multipart/related' body were able to correctly process them.
Авторы расширений SIP, использующих тела 'multipart/related', должны явно определить обработку типов диспозиции частей тела в составе тела 'multipart/related'. Авторам, желающим использовать тела 'multipart/related', следует помнить, что UA, не понимающие 'multipart/related', будут обрабатывать его как 'multipart/mixed'. Если такая обработка получателем неприемлема для конкретного расширения, авторам такого расширения потребуется обеспечить (например, с помощью option-tag или иными средствами), чтобы объекты, получающие тело 'multipart/related', могли корректно его обрабатывать.
As stated earlier, SIP extensions can also include 'multipart' MIME bodies in responses. Hence, a response can be extremely complex and the UAC receiving the response might not be able to process it correctly. Because UACs receiving a response cannot report errors to the UAS that generated the response (i.e., error responses can only be generated for requests), authors of SIP extensions need to make sure that requests clearly indicate (e.g., by using an option-tag or by other means) the capabilities of the UAC so that UASs can decide what to include in their responses.
Как указано ранее, расширения SIP могут включать тела MIME 'multipart' и в ответах. Поэтому ответ может быть крайне сложным, и UAC, получающий ответ, может оказаться не в состоянии корректно его обработать. Поскольку UAC, получающие ответ, не могут сообщать об ошибках UAS, сформировавшему ответ (то есть ответы об ошибках могут формироваться только на запросы), авторам расширений SIP необходимо обеспечить, чтобы запросы ясно указывали (например, с помощью option-tag или иными средствами) возможности UAC, с тем чтобы UAS могли решать, что включать в свои ответы.
11. Security Considerations
11. Вопросы безопасности
This document specifies how SIP entities handle message bodies. [RFC3261] discusses what type of information is encoded in SIP message bodies and how SIP entities can protect that information. In addition to the hop-by-hop security SIP can provide, SIP can also secure information in an end-to-end fashion. SIP message bodies can be end-to-end encrypted and integrity protected using S/MIME [RFC3851], as described in [RFC3261].
Настоящий документ определяет, как объекты SIP обрабатывают тела сообщений. В [RFC3261] обсуждается, какая информация кодируется в телах сообщений SIP и как объекты SIP могут защитить эту информацию. Помимо поэлементной (hop-by-hop) защиты, которую может обеспечить SIP, SIP может также защищать информацию сквозным образом (end-to-end). Тела сообщений SIP могут быть сквозным образом зашифрованы и защищены от искажения с помощью S/MIME [RFC3851], как описано в [RFC3261].
