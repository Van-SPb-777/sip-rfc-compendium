Расширение протокола инициирования сессий (SIP) для информации об истории запросов
Abstract
Аннотация
This document defines a standard mechanism for capturing the history information associated with a Session Initiation Protocol (SIP) request. This capability enables many enhanced services by providing the information as to how and why a SIP request arrives at a specific application or user. This document defines an optional SIP header field, History-Info, for capturing the history information in requests. The document also defines SIP header field parameters for the History-Info and Contact header fields to tag the method by which the target of a request is determined. In addition, this specification defines a value for the Privacy header field that directs the anonymization of values in the History-Info header field. This document obsoletes RFC 4244.
Настоящий документ определяет стандартный механизм сбора информации об истории, связанной с запросом протокола инициирования сессий (SIP). Эта возможность позволяет реализовать множество расширенных служб, предоставляя информацию о том, как и почему запрос SIP поступает в конкретное приложение или к конкретному пользователю. Настоящий документ определяет необязательное поле заголовка SIP History-Info для сбора информации об истории в запросах. Документ также определяет параметры полей заголовков History-Info и Contact, позволяющие помечать способ определения целевого объекта запроса. Кроме того, настоящая спецификация определяет значение для поля заголовка Privacy, которое предписывает анонимизацию значений в поле заголовка History-Info. Настоящий документ заменяет RFC 4244.

1. Introduction
1. Введение
Many services that SIP is anticipated to support require the ability to determine why and how a SIP request arrived at a specific application. Examples of such services include (but are not limited to) sessions initiated to call centers via "click to talk" SIP Uniform Resource Locators (URLs) on a web page, "call history/ logging"-style services within intelligent "call management" software for SIP user agents (UAs), and calls to voicemail servers. Although SIP implicitly provides the retarget capabilities that enable SIP requests to be routed to chosen applications, there is a need for a standard mechanism within SIP for communicating the retargeting history of the requests. This request history information allows the receiving application to obtain information about how and why the SIP request arrived at the application/user.
Многие службы, поддержку которых предполагается обеспечить в SIP, требуют умения определять, почему и как запрос SIP поступил в конкретное приложение. Примеры таких служб включают (но не ограничиваются ими) сеансы, инициированные в центры обработки вызовов через универсальные идентификаторы ресурсов (URL) SIP типа «click to talk» на веб-странице, службы в стиле «история/журналирование вызовов» в составе интеллектуального программного обеспечения «управления вызовами» для пользовательских агентов (UA) SIP и вызовы на серверы голосовой почты. Хотя SIP неявно предоставляет возможности перенацеливания, позволяющие маршрутизировать запросы SIP в выбранные приложения, существует потребность в стандартном механизме внутри SIP для передачи истории перенацеливания запросов. Эта информация об истории запросов позволяет принимающему приложению получать сведения о том, как и почему запрос SIP поступил в приложение или к пользователю.
This document defines a SIP header field, History-Info, to provide a standard mechanism for capturing the request history information to enable a wide variety of services for networks and end-users. SIP header field parameters are defined for the History-Info and Contact header fields to tag the method by which the target of a request is determined. This specification also defines a value, "history", for the Privacy header field. In addition, a SIP option tag, "histinfo", is defined.
Настоящий документ определяет поле заголовка SIP History-Info, обеспечивающее стандартный механизм сбора информации об истории запросов, что позволяет реализовать широкий спектр служб для сетей и конечных пользователей. Для полей заголовков History-Info и Contact определены параметры, позволяющие помечать способ определения целевого объекта запроса. Настоящая спецификация также определяет значение «history» для поля заголовка Privacy. Кроме того, определён тег опции SIP «histinfo».
The History-Info header field provides a building block for development of SIP-based applications and services. The requirements for the solution described in this specification are included in Appendix A. Example scenarios using the History-Info header field are available in [CALLFLOWS].
Поле заголовка History-Info служит строительным блоком для разработки приложений и служб на основе SIP. Требования к решению, описанному в настоящей спецификации, включены в Приложение A. Примеры сценариев с использованием поля заголовка History-Info доступны в [CALLFLOWS].

3. Background
3. Предпосылки
SIP implicitly provides retargeting capabilities that enable SIP requests to be routed to specific applications as defined in [RFC3261]. The motivation for capturing the request history is that in the process of retargeting a request, old routing information can be forever lost. This lost information may be important history that allows elements to which the request is retargeted to process the request in a locally defined, application-specific manner. This document defines a mechanism for transporting the request history. Application-specific behavior is outside the scope of this specification.
SIP неявно предоставляет возможности перенацеливания, позволяющие маршрутизировать запросы SIP в конкретные приложения, как определено в [RFC3261]. Мотивация сбора истории запросов состоит в том, что в процессе перенацеливания запроса прежняя информация о маршрутизации может быть навсегда утрачена. Эта утраченная информация может быть важной историей, позволяющей элементам, которым перенацеливается запрос, обрабатывать его локально определённым, зависящим от приложения образом. Настоящий документ определяет механизм передачи истории запросов. Поведение, зависящее от приложения, выходит за рамки настоящей спецификации.
Current network applications for other protocols provide the ability for elements involved with the request to obtain additional information relating to how and why the request was routed to a particular destination. The following are examples of such applications:
Текущие сетевые приложения для других протоколов предоставляют элементам, участвующим в запросе, возможность получать дополнительную информацию о том, как и почему запрос был маршрутизирован к конкретному получателю. Ниже приведены примеры таких приложений:
1. Web "referral" applications, whereby an application residing within a web server determines that a visitor to a website has arrived at the site via an "associate" site that will receive some "referral" commission for generating this traffic.
1. Веб-приложения «реферальных» ссылок, в которых приложение, размещённое на веб-сервере, определяет, что посетитель веб-сайта прибыл на сайт через «партнёрский» сайт, который получит часть «реферального» вознаграждения за создание этого трафика.
2. Email relaying whereby the recipient obtains a detailed "trace of the path" of the message from originator to receiver, including the time of each relay.
2. Пересылка электронной почты, при которой получатель получает подробный «след пути» сообщения от отправителя до получателя, включая время каждой пересылки.
3. Traditional telephony services such as voicemail, call-center "automatic call distribution", and "follow me"-style services.
3. Традиционные телефонные службы, такие как голосовая почта, «автоматическое распределение вызовов» в центрах обработки вызовов и службы типа «следуй за мной».
Several of the aforementioned applications currently define application-specific mechanisms through which it is possible to obtain the necessary history information. In addition, request history information could be used to enhance basic SIP functionality by providing the following:
Несколько из вышеупомянутых приложений в настоящее время определяют зависящие от приложения механизмы, с помощью которых можно получить необходимую информацию об истории. Кроме того, информацию об истории запросов можно использовать для расширения базовой функциональности SIP, обеспечивая следующее:
o Some diagnostic information for debugging SIP requests.
o Некоторую диагностическую информацию для отладки запросов SIP.
o Capturing aliases and Globally Routable User Agent URIs (GRUUs) [RFC5627], which can be overwritten by a registrar or a "home proxy" (a proxy serving as the terminal point for routing an address-of-record) upon receipt of the initial request.
o Сбор псевдонимов и глобально маршрутизируемых URI пользовательских агентов (GRUU) [RFC5627], которые могут быть перезаписаны регистратором или «домашним прокси» (прокси, служащим конечной точкой маршрутизации адреса записи) при получении исходного запроса.
o Facilitating the use of limited use addresses (minted on demand) and sub-addressing.
o Содействие использованию адресов ограниченного использования (создаваемых по требованию) и суб-адресации.
o Preserving service-specific URIs that can be overwritten by a downstream proxy, such as those defined in [RFC3087], and control of network announcements and Interactive Voice Response (IVR) with a SIP URI [RFC4240].
o Сохранение URI, специфичных для служб, которые могут быть перезаписаны нижестоящим прокси, например определённых в [RFC3087], и управление сетевыми объявлениями и интерактивным голосовым ответом (IVR) с помощью URI SIP [RFC4240].
4. Overview
4. Обзор
The fundamental functionality provided by the request history information is the ability to inform proxies and user agents (UAs) involved in processing a request about the history or progress of that request. The solution is to capture the Request-URIs, as a request is retargeted, in a SIP header field: History-Info. This allows for the capturing of the history of a request that would be lost with the normal SIP processing involved in the subsequent retargeting of the request.
Основная функциональность, обеспечиваемая информацией об истории запросов, — это возможность информировать прокси и пользовательских агентов (UA), участвующих в обработке запроса, об истории или ходе выполнения этого запроса. Решение состоит в сборе Request-URI по мере перенацеливания запроса в поле заголовка SIP History-Info. Это позволяет собирать историю запроса, которая была бы утрачена при обычной обработке SIP, связанной с последующим перенацеливанием запроса.
The History-Info header field is added to a request when a new request is created by a User Agent Client (UAC) or forwarded by a proxy, or when the target of a request is changed. It is possible for the target of a request to be changed by the same proxy/SIP intermediary multiple times (referred to as 'internal retargeting'). A SIP entity changing the target of a request in response to a redirect also propagates any History-Info header field from the initial request in the new request. The ABNF and detailed description of the History-Info header field parameters, along with examples, are provided in Section 5. Sections 6, 7, and 8 provide the detailed handling of the History-Info header field by SIP user agents, proxies, and redirect servers, respectively.
Поле заголовка History-Info добавляется в запрос, когда новый запрос создаётся клиентом пользовательского агента (UAC) или пересылается прокси, либо когда цель запроса изменяется. Цель запроса может быть изменена одним и тем же прокси/посредником SIP несколько раз (это называется «внутренним перенацеливанием»). Объект SIP, изменяющий цель запроса в ответ на перенаправление, также передаёт любое поле заголовка History-Info из исходного запроса в новый запрос. ABNF и подробное описание параметров поля заголовка History-Info вместе с примерами приведены в разделе 5. Разделы 6, 7 и 8 описывают подробную обработку поля заголовка History-Info соответственно пользовательскими агентами, прокси и серверами перенаправления SIP.
This specification also defines three new SIP header field parameters, "rc", "mp", and "np", for the History-Info and Contact header fields to tag the method by which the target of a request is determined. Further detail on the use of these header field parameters is provided in Section 5. This specification also defines a priv-value for the Privacy header, "history"; it requires anonymization of all the History-Info header field entries in a request or to a specific History-Info header field value (hi-entry) as described below. Further detail is provided in Section 10.1.
Настоящая спецификация также определяет три новых параметра полей заголовков SIP — «rc», «mp» и «np» — для полей заголовков History-Info и Contact, позволяющих помечать способ определения целевого объекта запроса. Подробности использования этих параметров приведены в разделе 5. Настоящая спецификация также определяет значение priv-value «history» для поля заголовка Privacy; оно требует анонимизации всех записей поля заголовка History-Info в запросе или конкретного значения поля заголовка History-Info (hi-entry), как описано ниже. Подробности приведены в разделе 10.1.
In addition, a SIP option tag, "histinfo", is defined. The use of this option tag is described in Section 6.1.
Кроме того, определён тег опции SIP «histinfo». Использование этого тега опции описано в разделе 6.1.
5. History-Info Header Field Protocol Structure
5. Структура протокола поля заголовка History-Info
The History-Info header field defined in this specification defines the usage in out-of-dialog requests or initial requests for a dialog (e.g., INVITE, REGISTER, MESSAGE, REFER and OPTIONS, PUBLISH and SUBSCRIBE, etc.) and any non-100 provisional or final responses to these requests.
Определённое в настоящей спецификации поле заголовка History-Info задаёт использование во внешних по отношению к диалогу запросах или начальных запросах для диалога (например, INVITE, REGISTER, MESSAGE, REFER и OPTIONS, PUBLISH и SUBSCRIBE и т. д.) и в любых промежуточных ответах, кроме 100, или окончательных ответах на эти запросы.
The following provides details for the information that is captured in the History-Info header field entries for each target used for forwarding a request.
Ниже приведены сведения об информации, которая собирается в записях поля заголовка History-Info для каждой цели, используемой для пересылки запроса.
o hi-targeted-to-uri: A mandatory parameter for capturing the Request-URI for the specific request as it is forwarded.
o hi-targeted-to-uri: обязательный параметр для сбора Request-URI конкретного запроса по мере его пересылки.
o hi-index: A mandatory parameter for History-Info reflecting the chronological order of the information, indexed to reflect the forking and retargeting of requests. The format for this parameter is a sequence of nonnegative integers, separated by dots to indicate the number of forward hops and retargets. This results in a tree representation of the history of the request, with the lowest-level index reflecting a leaf. By adding the new entries in chronological order (i.e., following existing entries per the details in Section 10.3), including the index and sending the messages using a secure transport, the ordering of the History-Info header fields in the request is assured. In addition, applications may extract a variety of metrics (total number of retargets, total number of retargets from a specific branch, etc.) based upon the index values.
o hi-index: обязательный параметр History-Info, отражающий хронологический порядок информации и индексируемый для отражения ветвления и перенацеливания запросов. Формат этого параметра — последовательность неотрицательных целых чисел, разделённых точками, которые указывают число шагов пересылки и перенацеливаний. В результате получается древовидное представление истории запроса, причём индекс самого низкого уровня отражает лист. Добавляя новые записи в хронологическом порядке (то есть следуя существующим записям согласно разделу 10.3), включая индекс, и отправляя сообщения по защищённому транспорту, можно гарантировать порядок полей заголовка History-Info в запросе. Кроме того, приложения могут извлекать различные метрики (общее число перенацеливаний, общее число перенацеливаний из конкретной ветви и т. д.) на основе значений индекса.
o hi-target-param: An optional parameter reflecting the mechanism by which the Request-URI captured in the hi-targeted-to-uri in the History-Info header field value (hi-entry) was determined. This parameter is either an "rc", "mp", or "np" header field parameter, which is interpreted as follows: "rc": The hi-targeted-to-URI represents a change in Request-URI, while the target user remains the same. This occurs, for example, when the user has multiple AORs as an alias. The "rc" header field parameter contains the value of the hi-index in the hi-entry with an hi-targeted-to-uri that reflects the Request-URI that was retargeted.
o hi-target-param: необязательный параметр, отражающий механизм, которым был определён Request-URI, зафиксированный в hi-targeted-to-uri в значении поля заголовка History-Info (hi-entry). Этот параметр является параметром поля заголовка «rc», «mp» или «np», который интерпретируется следующим образом: «rc»: hi-targeted-to-URI представляет изменение Request-URI, тогда как целевой пользователь остаётся прежним. Это происходит, например, когда пользователь имеет несколько AOR в качестве псевдонимов. Параметр поля заголовка «rc» содержит значение hi-index в hi-entry, у которого hi-targeted-to-uri отражает Request-URI, подвергнутый перенацеливанию.
"mp": The hi-targeted-to-URI represents a user other than the target user associated with the Request-URI in the incoming request that was retargeted. This occurs when a request is statically or dynamically retargeted to another user represented by an AOR unassociated with the AOR of the original target user. The "mp" header field parameter contains the value of the hi-index in the hi-entry with an hi-targeted-to-uri that reflects the Request-URI that was retargeted, thus identifying the "mapped from" target.
«mp»: hi-targeted-to-URI представляет пользователя, отличного от целевого пользователя, связанного с Request-URI во входящем запросе, который был перенацелен. Это происходит, когда запрос статически или динамически перенацеливается на другого пользователя, представленного AOR, не связанным с AOR исходного целевого пользователя. Параметр поля заголовка «mp» содержит значение hi-index в hi-entry, у которого hi-targeted-to-uri отражает Request-URI, подвергнутый перенацеливанию, тем самым идентифицируя цель «сопоставлено из».
"np": The hi-targeted-to-URI represents that there was no change in the Request-URI. This would apply, for example, when a proxy merely forwards a request to a next-hop proxy and loose routing is used. The "np" header field parameter contains the value of the hi-index in the hi-entry with an hi-targeted-to-uri that reflects the Request-URI that was copied unchanged into the request represented by this hi-entry. That value will usually be the hi-index of the parent hi-entry of this hi-entry.
«np»: hi-targeted-to-URI указывает, что Request-URI не изменился. Это применимо, например, когда прокси лишь пересылает запрос следующему прокси и используется свободная маршрутизация. Параметр поля заголовка «np» содержит значение hi-index в hi-entry, у которого hi-targeted-to-uri отражает Request-URI, скопированный без изменений в запрос, представленный этой hi-entry. Обычно это значение является hi-index родительской hi-entry для данной hi-entry.
o Extension (hi-extension): A parameter to allow for future optional extensions. As per [RFC3261], any implementation not understanding an extension MUST ignore it.
o Расширение (hi-extension): параметр, позволяющий добавлять будущие необязательные расширения. Согласно [RFC3261], любая реализация, не понимающая расширение, ДОЛЖНА игнорировать его.

o Reason: An optional parameter for History-Info, reflected in the History-Info header field by including the Reason header field [RFC3326] included in the hi-targeted-to-uri. o Privacy: необязательный параметр History-Info, отражаемый в значениях поля заголовка History-Info путём включения поля заголовка Privacy [RFC3323] со значением priv-value «history», как определено в настоящем документе, в hi-targeted-to-uri или путём добавления поля заголовка Privacy со значением priv-value «history» в запрос. Последний случай указывает, что записи History-Info для всех записей History-Info, у которых hi-targeted-to-uri имеет тот же домен, что и домен, за который отвечает объект SIP, обрабатывающий сообщение, ДОЛЖНЫ быть анонимизированы до пересылки, тогда как использование поля заголовка Privacy, включённого в hi-targeted-to-uri, означает, что конкретная hi-entry ДОЛЖНА быть анонимизирована.

6. User Agent Handling of the History-Info Header Field
6. Обработка поля заголовка History-Info пользовательским агентом
This section describes the processing specific to UAs -- User Agent Clients (UACs), User Agent Servers (UASs), and Back-to-Back User Agents (B2BUAs) -- for the History-Info header.
В этом разделе описывается обработка, специфичная для UA — клиентов пользовательских агентов (UAC), серверов пользовательских агентов (UAS) и посредников типа «back-to-back» (B2BUA), — для заголовка History-Info.
6.1. User Agent Client (UAC) Behavior
6.1. Поведение клиента пользовательского агента (UAC)
The UAC MUST include the "histinfo" option tag in the Supported header field in any out-of-dialog requests or initial requests for a dialog for which the UAC would like the History-Info header field in the response. When issuing a request, the UAC MUST follow the procedures in Section 9.2. In the case of an initial request, except where the UAC is part of a B2BUA, there is no cache of hi-entries with which to populate the History-Info header field, and the hi-index is set to 1 per Section 10.3. When receiving a response, the UAC MUST follow the procedures in Section 9.3.
UAC ДОЛЖЕН включать тег опции «histinfo» в поле заголовка Supported в любых внешних по отношению к диалогу запросах или начальных запросах для диалога, для которых UAC хотел бы получить поле заголовка History-Info в ответе. При отправке запроса UAC ДОЛЖЕН следовать процедурам раздела 9.2. В случае начального запроса, за исключением случаев, когда UAC является частью B2BUA, кэш hi-entry, которым можно заполнить поле заголовка History-Info, отсутствует, и hi-index устанавливается в 1 согласно разделу 10.3. При получении ответа UAC ДОЛЖЕН следовать процедурам раздела 9.3.
If the UAC generates further forks of the initial request (either due to acting on a 3xx response or internally directed forking to multiple destinations), the successive requests will add hi-entries with hi-indexes of 2, 3, etc.
Если UAC порождает дальнейшие ветви начального запроса (либо вследствие обработки ответа 3xx, либо внутренне направленного ветвления к нескольким получателям), последующие запросы добавят hi-entry с hi-index 2, 3 и т. д.
6.2. User Agent Server (UAS) Behavior
6.2. Поведение сервера пользовательского агента (UAS)
When receiving a request, a UAS MUST follow the procedures defined in Section 9.2. When sending a response other than a 3xx response, a UAS MUST follows the procedures defined in Section 9.4. When sending a 3xx response, the UAS MUST follow the procedures defined for a redirect server per Section 8. An application at the UAS can make use of the cached hi-entries as described in Section 11.
При получении запроса UAS ДОЛЖЕН следовать процедурам, определённым в разделе 9.2. При отправке ответа, отличного от ответа 3xx, UAS ДОЛЖЕН следовать процедурам, определённым в разделе 9.4. При отправке ответа 3xx UAS ДОЛЖЕН следовать процедурам, определённым для сервера перенаправления в разделе 8. Приложение на UAS может использовать кэшированные hi-entry, как описано в разделе 11.
6.3. Back-to-Back User Agent (B2BUA) Behavior
6.3. Поведение посредника типа «back-to-back» (B2BUA)
A B2BUA MAY follow the behavior of a SIP intermediary, per Section 7, as an alternative to following the behavior of a UAS per Section 6.2 or a UAC per Section 6.1. In behaving as an intermediary, a B2BUA carries forward hi-entries received in requests at the UAS to requests being forwarded by the UAC, as well as carrying forward hi-entries in responses received at the UAC to the responses forwarded by the UAS, subject to privacy considerations per Section 10.1.
B2BUA МОЖЕТ следовать поведению посредника SIP согласно разделу 7 в качестве альтернативы поведению UAS согласно разделу 6.2 или UAC согласно разделу 6.1. Действуя как посредник, B2BUA переносит hi-entry, полученные в запросах на UAS, в запросы, пересылаемые UAC, а также переносит hi-entry в ответах, полученных на UAC, в ответы, пересылаемые UAS, с учётом соображений конфиденциальности согласно разделу 10.1.

9.3. Receiving a Response with History-Info or Request Timeouts
9.3. Получение ответа с History-Info или тайм-ауты запроса
When a SIP entity receives a non-100 response or a request times out, the SIP entity performs the following steps:
Когда объект SIP получает ответ, отличный от 100, или истекает время ожидания запроса, объект SIP выполняет следующие шаги:
Step 1: Add hi-entry to cache
Шаг 1: добавление hi-entry в кэш.

10. Processing the History-Info Header Field
10. Обработка поля заголовка History-Info
The following subsections describe the procedures for processing the History-Info header field. These procedures are applicable to SIP entities such as proxies/intermediaries, redirect servers, or user agents.
В следующих подразделах описаны процедуры обработки поля заголовка History-Info. Эти процедуры применимы к таким объектам SIP, как прокси/посредники, серверы перенаправления или пользовательские агенты.
10.1. Privacy in the History-Info Header Field
10.1. Конфиденциальность в поле заголовка History-Info
The privacy requirements for this document are described in Appendix A.2. Section 10.1.1 describes the insertion of the Privacy header field (defined in [RFC3323]) to indicate the privacy to be applied to the History-Info header field entries. Section 10.1.2 describes how to apply privacy to a request or response that is being forwarded, based on the presence of the Privacy header field.
Требования конфиденциальности для настоящего документа описаны в Приложении A.2. В разделе 10.1.1 описано включение поля заголовка Privacy (определённого в [RFC3323]) для указания конфиденциальности, применяемой к записям поля заголовка History-Info. В разделе 10.1.2 описано, как применять конфиденциальность к пересылаемому запросу или ответу на основе наличия поля заголовка Privacy.
10.1.1. Indicating Privacy
10.1.1. Указание конфиденциальности
As with other SIP headers described in [RFC3323], the hi-targeted-to-uris in the History-Info header field can inadvertently reveal information about the initiator of the request. Thus, the UAC needs a mechanism to indicate that the hi-targeted-to-uris in the hi-entries need to be privacy protected. The Privacy header field is used by the UAC to indicate that privacy is to be applied to all the hi-entries in the request as follows: o If the UAC is including a Privacy header field with a priv-value of "header" in the request, then the UAC SHOULD NOT include a priv-value of "history" in the Privacy header field in the request.
Как и другие заголовки SIP, описанные в [RFC3323], hi-targeted-to-uri в поле заголовка History-Info могут непреднамеренно раскрывать информацию об инициаторе запроса. Таким образом, UAC нужен механизм, указывающий, что hi-targeted-to-uri в hi-entry нуждаются в защите конфиденциальности. UAC использует поле заголовка Privacy, чтобы указать, что конфиденциальность должна применяться ко всем hi-entry в запросе, следующим образом: o Если UAC включает в запрос поле заголовка Privacy со значением priv-value «header», то UAC НЕ СЛЕДУЕТ включать в поле заголовка Privacy в запросе значение priv-value «history».
o If the UAC is including any priv-values other than "header" in the Privacy header field, then the UAC MUST also include a priv-value of "history" in the Privacy header field in the request.
o Если UAC включает в поле заголовка Privacy любые значения priv-value, отличные от «header», то UAC ДОЛЖЕН также включить в поле заголовка Privacy в запросе значение priv-value «history».
o If the UAC is not including any priv-values in the Privacy header field in the request, then the UAC MUST add a Privacy header field, with a priv-value of "history", to the request. The UAC MUST NOT include a priv-value of "critical" in the Privacy header field in the request in this case.
o Если UAC не включает в поле заголовка Privacy в запросе никаких значений priv-value, то UAC ДОЛЖЕН добавить в запрос поле заголовка Privacy со значением priv-value «history». В этом случае UAC НЕ ДОЛЖЕН включать в поле заголовка Privacy в запросе значение priv-value «critical».
In addition, the History-Info header field can reveal general routing and diverting information that is within an intermediary and that the intermediary wants to privacy protect. In this case, the intermediary MUST construct a Privacy header field with the single priv-value of "history" and include the Privacy header field in the hi-targeted-to-uri, for each new hi-entry created by the intermediary whose hi-targeted-to-uri it wishes to privacy protect. Note that the priv-value in the Privacy header for the incoming request does not necessarily influence whether the intermediary includes a Privacy header field in the hi-entries. For example, even if the Privacy header for the incoming request contained a priv-value of "none", the proxy can still set a priv-value of "history" in the Privacy header field included in the hi-targeted-to-uri.
Кроме того, поле заголовка History-Info может раскрывать общую информацию о маршрутизации и перенаправлении, которая находится внутри посредника и которую посредник хочет защитить с точки зрения конфиденциальности. В этом случае посредник ДОЛЖЕН сформировать поле заголовка Privacy с единственным значением priv-value «history» и включить поле заголовка Privacy в hi-targeted-to-uri для каждой новой hi-entry, созданной посредником, чей hi-targeted-to-uri он желает защитить. Отметим, что значение priv-value в заголовке Privacy входящего запроса не обязательно влияет на то, включает ли посредник поле заголовка Privacy в hi-entry. Например, даже если заголовок Privacy входящего запроса содержал значение priv-value «none», прокси всё равно может установить значение priv-value «history» в поле заголовка Privacy, включённом в hi-targeted-to-uri.
Finally, the UAS may not want to reveal the final reached target to the originator. In this case, the UAS MUST include a Privacy header field with a priv-value of "history" in the hi-targeted-to-uri in the last hi-entry, in the response. As noted above, the UAS of the request MUST NOT use any other priv-values in the Privacy header field included in the hi-entry.
Наконец, UAS может не желать раскрывать исходному отправителю конечную достигнутую цель. В этом случае UAS ДОЛЖЕН включить в ответ поле заголовка Privacy со значением priv-value «history» в hi-targeted-to-uri в последней hi-entry. Как отмечено выше, UAS запроса НЕ ДОЛЖЕН использовать никакие другие значения priv-value в поле заголовка Privacy, включаемом в hi-entry.
10.1.2. Applying Privacy
10.1.2. Применение конфиденциальности
When a SIP message is forwarded to a domain for which the SIP intermediary is not responsible, a Privacy Service at the boundary of the domain applies the appropriate privacy based on the value of the Privacy header field in the message header or in the "headers" component of the hi-targeted-to-uri in the individual hi-entries.
Когда сообщение SIP пересылается в домен, за который посредник SIP не отвечает, служба обеспечения конфиденциальности на границе домена применяет соответствующую конфиденциальность на основе значения поля заголовка Privacy в заголовке сообщения или в компоненте «headers» в hi-targeted-to-uri в отдельных hi-entry.
If there is a Privacy header field in the message header of a request or response, with a priv-value of "header" or "history", then all the hi-targeted-to-uris (in the hi-entries associated with the domain for which the SIP intermediary is responsible) are anonymized by the Privacy Service. The Privacy Service MUST change any hi-targeted-to-uris in these hi-entries that have not been anonymized (evidenced by their domain not being "anonymous.invalid") to anonymous URIs containing a domain of anonymous.invalid as recommended in Section 4.1.1.3 of [RFC3323]. As defined in Section 4.1.1.2 of [RFC3323], the recommendations of [RFC3261] for anonymizing the URI Username SHOULD be followed (i.e., "anonymous" in the user portion of the URI). If there is a Privacy header field in the "headers" component of the hi-targeted-to-uri in the hi-entries, then the Privacy header field value MUST be removed from the hi-entry. Once all the appropriate hi-entries have been anonymized, the Privacy Service MUST remove the priv-value of "history" from the Privacy header field in the message header of the request or response. If there are no remaining priv-values in the Privacy header field, the Privacy Service MUST remove the Privacy header field from the request or response per [RFC3323].
Если в заголовке сообщения запроса или ответа есть поле заголовка Privacy со значением priv-value «header» или «history», то все hi-targeted-to-uri (в hi-entry, связанных с доменом, за который отвечает посредник SIP) анонимизируются службой обеспечения конфиденциальности. Служба обеспечения конфиденциальности ДОЛЖНА изменить любые hi-targeted-to-uri в этих hi-entry, которые не были анонимизированы (о чём свидетельствует их домен, не являющийся «anonymous.invalid»), на анонимные URI, содержащие домен anonymous.invalid, как рекомендовано в разделе 4.1.1.3 [RFC3323]. Как определено в разделе 4.1.1.2 [RFC3323], СЛЕДУЕТ соблюдать рекомендации [RFC3261] по анонимизации имени пользователя URI (то есть «anonymous» в части URI, обозначающей пользователя). Если в компоненте «headers» в hi-targeted-to-uri в hi-entry есть поле заголовка Privacy, то значение поля заголовка Privacy ДОЛЖНО быть удалено из hi-entry. После анонимизации всех соответствующих hi-entry служба обеспечения конфиденциальности ДОЛЖНА удалить значение priv-value «history» из поля заголовка Privacy в заголовке сообщения запроса или ответа. Если в поле заголовка Privacy не осталось значений priv-value, служба обеспечения конфиденциальности ДОЛЖНА удалить поле заголовка Privacy из запроса или ответа согласно [RFC3323].
If there is not a Privacy header field in the message header of the request or response that is being forwarded, but there is a Privacy header field with a priv-value of "history" in the "headers" component in any of the hi-targeted-uris in the hi-entries associated with the domain for which a SIP intermediary is responsible, then the Privacy Service MUST update those hi-targeted-to-uris as described above. Any other priv-values in the Privacy header field in the "headers" component of the hi-targeted-to-uris in the hi-entries MUST be ignored. In any case, the Privacy Service MUST remove the Privacy header field from the "headers" component of the hi-targeted-to-uris in the hi-entries prior to forwarding.
Если в заголовке сообщения пересылаемого запроса или ответа нет поля заголовка Privacy, но в компоненте «headers» в любом из hi-targeted-to-uri в hi-entry, связанных с доменом, за который отвечает посредник SIP, есть поле заголовка Privacy со значением priv-value «history», то служба обеспечения конфиденциальности ДОЛЖНА обновить эти hi-targeted-to-uri, как описано выше. Любые другие значения priv-value в поле заголовка Privacy в компоненте «headers» в hi-targeted-to-uri в hi-entry ДОЛЖНЫ игнорироваться. В любом случае служба обеспечения конфиденциальности ДОЛЖНА удалить поле заголовка Privacy из компонента «headers» в hi-targeted-to-uri в hi-entry до пересылки.
10.2. Reason in the History-Info Header Field
10.2. Reason в поле заголовка History-Info
A Reason header field is added when the hi-entry is added to the cache based upon the receipt of a SIP response that is neither a 100 nor a 2xx response, as described in Section 9.3. The SIP entity MUST include a Reason header field, containing the SIP Response Code, in the "headers" component of the hi-targeted-to-uri in the last hi-entry added to the cache, unless the hi-targeted-to-uri is a Tel-URI. In addition, if the response contains any Reason header fields (see [RFC3326]), then the SIP entity MUST also include the Reason header fields in the "headers" component of the hi-targeted-to-uri in the last hi-entry added to the cache.
Поле заголовка Reason добавляется, когда hi-entry добавляется в кэш на основании получения ответа SIP, не являющегося ответом 100 или 2xx, как описано в разделе 9.3. Объект SIP ДОЛЖЕН включить поле заголовка Reason, содержащее код ответа SIP, в компонент «headers» в hi-targeted-to-uri в последней hi-entry, добавленной в кэш, если только hi-targeted-to-uri не является Tel-URI. Кроме того, если ответ содержит какие-либо поля заголовка Reason (см. [RFC3326]), объект SIP ДОЛЖЕН также включить поля заголовка Reason в компонент «headers» в hi-targeted-to-uri в последней hi-entry, добавленной в кэш.
If a request has timed out (instead of being explicitly rejected), the SIP entity MUST update the cache as if the request received a SIP error response code of 408 "Request Timeout". A request can receive multiple responses that are neither 100 nor 2xx responses and that carry or imply (for responses without Reason headers, and for timeouts) multiple, possibly duplicated, reason-values to be applied to an hi-targeted-to-uri. In these situations, the SIP entity creating the History-Info header value would choose the appropriate Reason header field value.
Если время ожидания запроса истекло (вместо явного отклонения), объект SIP ДОЛЖЕН обновить кэш так, как если бы запрос получил код ответа об ошибке SIP 408 «Request Timeout». Запрос может получить несколько ответов, не являющихся ответами 100 или 2xx и несущих или подразумевающих (для ответов без заголовков Reason и для тайм-аутов) несколько, возможно дублирующихся, значений причины, которые должны быть применены к hi-targeted-to-uri. В таких ситуациях объект SIP, создающий значение заголовка History-Info, выбирает соответствующее значение поля заголовка Reason.
A SIP entity MAY also include a Reason header field (in the "headers" component of an hi-targeted-to-uri) that contains the URI of a request that was retargeted as a result of internal retargeting.
Объект SIP МОЖЕТ также включить поле заголовка Reason (в компонент «headers» некоторого hi-targeted-to-uri), содержащее URI запроса, который был перенацелен в результате внутреннего перенацеливания.
If additional Reason header field parameters are defined in the future per [RFC3326], the use of these Reason header field parameters for the History-Info header field MUST follow the same rules as described above.
Если в будущем согласно [RFC3326] будут определены дополнительные параметры поля заголовка Reason, использование этих параметров для поля заголовка History-Info ДОЛЖНО следовать тем же правилам, что описаны выше.
10.3. Indexing in the History-Info Header Field
10.3. Индексация в поле заголовка History-Info
In order to maintain ordering and accurately reflect the retargeting of the request, the SIP entity MUST add an hi-index to each hi-entry. Per the syntax in Section 5, the hi-index consists of a series of nonnegative integers separated by dots (e.g., 1.1.2). Each dot reflects a SIP forwarding hop. The nonnegative integer following each dot reflects the order in which a request was retargeted at the hop. The highest nonnegative integer at each hop reflects the number of entities to which the request has been retargeted at the specific hop (i.e., the number of branches) at the time that the request represented by this hi-entry was generated. Thus, the indexing results in a logical tree representation for the history of the request and the hi-entries are given in the preorder of the tree.
Чтобы поддерживать порядок и точно отражать перенацеливание запроса, объект SIP ДОЛЖЕН добавлять hi-index в каждую hi-entry. Согласно синтаксису раздела 5, hi-index состоит из последовательности неотрицательных целых чисел, разделённых точками (например, 1.1.2). Каждая точка отражает шаг пересылки SIP. Неотрицательное целое число после каждой точки отражает порядок, в котором запрос был перенацелен на данном шаге. Наибольшее неотрицательное целое число на каждом шаге отражает число объектов, на которые запрос был перенацелен на конкретном шаге (то есть число ветвей) на момент формирования запроса, представленного этой hi-entry. Таким образом, индексация даёт логическое древовидное представление истории запроса, и hi-entry приводятся в прямом порядке обхода дерева.
The first index in a series of History-Info entries MUST be set to 1. In the case that a SIP entity (intermediary or UAS) adds a first hi-entry on behalf of the previous hop, the hi-index MUST be set to 1. For each forward hop (i.e., each new level of indexing), the last integers of the hi-indexes of the new requests MUST be generated starting at 1 and incrementing by 1 for each additional request.
Первый индекс в последовательности записей History-Info ДОЛЖЕН быть установлен в 1. В случае, когда объект SIP (посредник или UAS) добавляет первую hi-entry от имени предыдущего шага, hi-index ДОЛЖЕН быть установлен в 1. Для каждого шага пересылки (то есть каждого нового уровня индексации) последние целые числа hi-index новых запросов ДОЛЖНЫ формироваться начиная с 1 и увеличиваться на 1 для каждого дополнительного запроса.
The basic rules for adding the hi-index are summarized as follows:
Основные правила добавления hi-index кратко изложены следующим образом:
1. Forwarding a request without changing the target: In the case of a request that is being forwarded without changing the target, the hi-index reflects the increasing length of the branch. In this case, the SIP entity MUST read the value from the History- Info header field in the received request and MUST add another level of indexing by appending the dot delimiter followed by an initial value of 1 for the new level. For example, if the hi-index in the last History-Info header field in the received request is 1.1, a proxy would add an hi-entry with an hi-index of 1.1.1 and forward the request.
1. Пересылка запроса без изменения цели: в случае запроса, который пересылается без изменения цели, hi-index отражает увеличивающуюся длину ветви. В этом случае объект SIP ДОЛЖЕН прочитать значение из поля заголовка History-Info в полученном запросе и ДОЛЖЕН добавить ещё один уровень индексации, добавив разделитель-точку и начальное значение 1 для нового уровня. Например, если hi-index в последнем поле заголовка History-Info в полученном запросе равен 1.1, прокси добавит hi-entry с hi-index 1.1.1 и перешлёт запрос.
2. Retargeting within a processing entity - first instance: For the first instance of retargeting within a processing entity, the SIP entity MUST calculate the hi-index as prescribed for basic forwarding.
2. Перенацеливание внутри обрабатывающего объекта — первый случай: для первого случая перенацеливания внутри обрабатывающего объекта объект SIP ДОЛЖЕН вычислить hi-index так, как предписано для базовой пересылки.
3. Retargeting within a processing entity - subsequent instance: For each subsequent retargeting of a request by the same SIP entity, the SIP entity MUST calculate and add the hi-index for each new branch by incrementing the rightmost value from the hi-index in the last hi-entry. Per the example above, the hi-index in the next request forwarded by this same SIP entity would be 1.1.2.
3. Перенацеливание внутри обрабатывающего объекта — последующий случай: для каждого последующего перенацеливания запроса тем же объектом SIP объект SIP ДОЛЖЕН вычислить и добавить hi-index для каждой новой ветви, увеличив самое правое значение hi-index в последней hi-entry. Согласно примеру выше, hi-index в следующем запросе, пересылаемом этим же объектом SIP, будет 1.1.2.
4. Retargeting based upon a response: In the case of retargeting due to a specific response (e.g., 302), the SIP entity MUST calculate the hi-index calculated per rule 3. That is, the rightmost value of the hi-index MUST be incremented (i.e., a new branch is created). For example, if the hi-index in the History-Info header field of the sent request is 1.2 and the response to the request is a 302, then the hi-index in the History-Info header field for the new hi-targeted-to-URI would be 1.3.
4. Перенацеливание на основании ответа: в случае перенацеливания из-за конкретного ответа (например, 302) объект SIP ДОЛЖЕН вычислить hi-index согласно правилу 3. То есть самое правое значение hi-index ДОЛЖНО быть увеличено (то есть создаётся новая ветвь). Например, если hi-index в поле заголовка History-Info отправленного запроса равен 1.2 и ответом на запрос является 302, то hi-index в поле заголовка History-Info для нового hi-targeted-to-URI будет 1.3.
5. Forking requests: If the request forwarding is done in multiple forks (sequentially or in parallel), the SIP entity MUST set the hi-index for each hi-entry for each forked request per the rules above, with each new request having a unique index. Each index MUST be sequentially assigned. For example, if the index in the last History-Info header field in the received request is 1.1, this processing entity would initialize its index to 1.1.1 for the first fork, 1.1.2 for the second, and so forth. (See Figure 1 for an example.) Note that, in the case of parallel forking, only the hi-entry corresponding to the fork is included in the request because no response can yet have been received for any of the parallel forked requests.
5. Ветвление запросов: если пересылка запроса выполняется несколькими ветвями (последовательно или параллельно), объект SIP ДОЛЖЕН установить hi-index для каждой hi-entry каждого ответвлённого запроса согласно правилам выше, причём каждый новый запрос должен иметь уникальный индекс. Каждый индекс ДОЛЖЕН назначаться последовательно. Например, если индекс в последнем поле заголовка History-Info в полученном запросе равен 1.1, этот обрабатывающий объект инициализирует свой индекс значением 1.1.1 для первой ветви, 1.1.2 для второй и так далее. (Пример см. на рисунке 1.) Отметим, что в случае параллельного ветвления в запрос включается только hi-entry, соответствующая данной ветви, поскольку ни по одному из параллельно ответвлённых запросов ещё не может быть получен ответ.
6. Missing entry: If the request clearly has a gap in the hi-entry (i.e., the last hi-entry and Request-URI differ), the entity adding an hi-entry MUST add a single index with a value of "0" (i.e., the nonnegative integer zero) prior to adding the appropriate index for the action to be taken. For example, if the index of the last hi-entry in the request received was 1.1.2 and there was a missing hi-entry and the request was being forwarded to the next hop, the resulting index will be 1.1.2.0.1. In the case of requests that are forked by a proxy that does not support History-Info, it is possible for hi-entries generated by different entities to have the same index, i.e., each entity supporting History-Info would receive a forked request with the same hi-index to which they would add the value of ".0" prior to adding the appropriate index. Thus, in the previous example, each of the next-hop entities would generate an hi-index of 1.1.2.0.1.
6. Отсутствующая запись: если в hi-entry запроса явно есть пробел (то есть последняя hi-entry и Request-URI различаются), объект, добавляющий hi-entry, ДОЛЖЕН перед добавлением соответствующего индекса для выполняемого действия добавить один индекс со значением «0» (то есть неотрицательное целое число ноль). Например, если индекс последней hi-entry в полученном запросе был 1.1.2, имелась отсутствующая hi-entry и запрос пересылался на следующий шаг, результирующий индекс будет 1.1.2.0.1. В случае запросов, ответвлённых прокси, который не поддерживает History-Info, возможно, что hi-entry, сформированные разными объектами, будут иметь одинаковый индекс, то есть каждый объект, поддерживающий History-Info, получит ответвлённый запрос с одинаковым hi-index, к которому он добавит значение «.0» перед добавлением соответствующего индекса. Таким образом, в предыдущем примере каждый из объектов следующего шага сформирует hi-index 1.1.2.0.1.
10.4. Mechanism for Target Determination in the History-Info Header Field
10.4. Механизм определения целевого объекта в поле заголовка History-Info
This specification defines three header field parameters, "rc", "mp", and "np". The header field parameters "rc" and "mp" indicate the mechanism by which a new target for a request is determined. The header field "np" reflects that the target has not changed. All parameters contain an index whose value is the hi-index of the hi-entry with an hi-targeted-to-uri that represents the Request-URI that was retargeted.
Настоящая спецификация определяет три параметра полей заголовков: «rc», «mp» и «np». Параметры полей заголовков «rc» и «mp» указывают механизм, которым определяется новая цель запроса. Параметр «np» отражает, что цель не изменилась. Все параметры содержат индекс, значение которого является hi-index той hi-entry, чей hi-targeted-to-uri представляет Request-URI, подвергнутый перенацеливанию.
The SIP entity MUST determine the specific parameter field to be included in the hi-target-param, in the History-Info header field, as the targets are added to the target set per the procedures in Section 16.5 of [RFC3261] or per Section 8.1.3.4 of [RFC3261] in the case of retargeting to a Contact URI received in a 3xx response. In the latter case, the specific header field parameter in the Contact header field becomes the header field parameter that is used in the hi-entry when the request is retargeted. If the Contact header field does not contain an "rc" or "mp" header field parameter, then the SIP entity MUST NOT include an "rc" or "mp" header field parameter in the hi-target-param in the hi-entry when the request is retargeted to a Contact URI received in a 3xx response. This is because the redirect server is the only element with any knowledge on how the target was determined. Note that the "np" header field parameter is not applicable in the case of redirection.
Объект SIP ДОЛЖЕН определить конкретное поле параметра, включаемое в hi-target-param в поле заголовка History-Info, по мере добавления целей в набор целей согласно процедурам раздела 16.5 [RFC3261] или, в случае перенацеливания на Contact URI, полученный в ответе 3xx, согласно разделу 8.1.3.4 [RFC3261]. В последнем случае конкретный параметр поля заголовка в поле заголовка Contact становится параметром поля заголовка, используемым в hi-entry при перенацеливании запроса. Если поле заголовка Contact не содержит параметра поля заголовка «rc» или «mp», то объект SIP НЕ ДОЛЖЕН включать параметр поля заголовка «rc» или «mp» в hi-target-param в hi-entry при перенацеливании запроса на Contact URI, полученный в ответе 3xx. Это связано с тем, что сервер перенаправления является единственным элементом, обладающим знанием о том, как была определена цель. Отметим, что параметр поля заголовка «np» не применим в случае перенаправления.
Based on the following criteria, the SIP entity (intermediary or redirect server) determines the specific header field parameter ("rc", "mp", or "np") to be used.
На основе следующих критериев объект SIP (посредник или сервер перенаправления) определяет конкретный параметр поля заголовка («rc», «mp» или «np»), который следует использовать.
o "rc": The Request-URI has changed while the target user associated with the original Request-URI prior to retargeting has been retained.
o «rc»: Request-URI изменился, тогда как целевой пользователь, связанный с исходным Request-URI до перенацеливания, сохранён.
o "mp": The target was determined based on a mapping to a user other than the target user associated with the Request-URI being retargeted.
o «mp»: цель была определена на основе сопоставления с пользователем, отличным от целевого пользователя, связанного с перенацеливаемым Request-URI.
o "np": The target hasn't changed, and the associated Request-URI remained the same.
o «np»: цель не изменилась, и связанный с ней Request-URI остался тем же самым.
Note that there are two scenarios by which the "mp" header field parameter can be derived.
Отметим, что есть два сценария, в которых может быть получен параметр поля заголовка «mp».
o The mapping was done by the receiving entity on its own authority, in which case the mp-value is the parent index of the hi-entry's index.
o Сопоставление было выполнено принимающим объектом по его собственным полномочиям, и в этом случае значением mp является родительский индекс индекса hi-entry.
o The mapping was done due to receiving a 3xx response, in which case the mp-value is an earlier sibling or descendant of an earlier sibling of the hi-entry's index; the index is that of the downstream request that received the 3xx response.
o Сопоставление было выполнено из-за получения ответа 3xx, и в этом случае значением mp является более ранний соседний узел или потомок более раннего соседнего узла индекса hi-entry; индексом является индекс нижестоящего запроса, получившего ответ 3xx.
11. Application Considerations
11. Вопросы применения
History-Info provides a very flexible building block that can be used by intermediaries and UAs for a variety of services. Prior to any application usage of the History-Info header field parameters, the SIP entity that processes the hi-entries MUST evaluate the hi-entries and determine if there are any gaps in the hi-entries. The SIP entity MUST be prepared to process effectively messages whose hi-entries show evidence of "gaps", that is, situations that reveal that not all of the forks of the request have been recorded in the hi-entries. Gaps are possible if the request is forwarded through intermediaries that do not support the History-Info header field and are reflected by the existence of hi-entries with a nonnegative integer of "0", e.g., "1.1.0.1". Gaps are also possible in the case of parallel forking if there is an outstanding request at the time the SIP entity sends a message. In addition, gaps may introduce the possibility of duplicate values for the hi-index in the case that a proxy that does not support History-Info forks a request. If gaps are detected, the SIP entity MUST NOT treat this as an error but SHOULD indicate to any applications that there are gaps. The interpretation of the information in the History-Info header field depends upon the specific application; an application might need to provide special handling in some cases where there are gaps.
History-Info предоставляет очень гибкий строительный блок, который может использоваться посредниками и UA для разнообразных служб. До любого использования параметров поля заголовка History-Info приложением объект SIP, обрабатывающий hi-entry, ДОЛЖЕН проанализировать hi-entry и определить, нет ли в них каких-либо пробелов. Объект SIP ДОЛЖЕН быть готов эффективно обрабатывать сообщения, hi-entry которых свидетельствуют о «пробелах», то есть ситуации, показывающие, что не все ветви запроса были зафиксированы в hi-entry. Пробелы возможны, если запрос пересылается через посредников, не поддерживающих поле заголовка History-Info, и отражаются наличием hi-entry с неотрицательным целым числом «0», например «1.1.0.1». Пробелы также возможны в случае параллельного ветвления, если на момент отправки сообщения объектом SIP есть незавершённый запрос. Кроме того, пробелы могут создавать возможность дублирования значений hi-index в случае, когда прокси, не поддерживающий History-Info, ответвляет запрос. Если обнаружены пробелы, объект SIP НЕ ДОЛЖЕН рассматривать это как ошибку, но СЛЕДУЕТ указать любым приложениям на наличие пробелов. Интерпретация информации в поле заголовка History-Info зависит от конкретного приложения; приложению может потребоваться специальная обработка в некоторых случаях наличия пробелов.
The following describes some categories of information that applications can use:
Ниже описаны некоторые категории информации, которые могут использовать приложения:
1. Complete history information, e.g., for debugging or other operational and management aspects, optimization of determining targets to avoid retargeting to the same URI, etc. This information is relevant to proxies, UACs, and UASs.
1. Полная информация об истории, например для отладки или других эксплуатационных аспектов и аспектов управления, оптимизации определения целей во избежание перенацеливания на тот же URI и т. д. Эта информация важна для прокси, UAC и UAS.
2. Hi-entry with the index that matches the value of the "rc" header field parameter in the last hi-entry with an "rc" header field parameter in the request received by a UAS, i.e., the last AOR that was retargeted to a contact based on an AOR-to-contact binding.
2. Hi-entry с индексом, совпадающим со значением параметра поля заголовка «rc» в последней hi-entry с параметром поля заголовка «rc» в запросе, полученном UAS, то есть последний AOR, который был перенацелен на контакт на основе привязки AOR-контакт.
3. Hi-entry with the index that matches the value of the "mp" header field parameter in the last hi-entry with an "mp" header field parameter in the hi-target-param in the request received by a UAS, i.e., the last Request-URI that was mapped to reach the destination.
3. Hi-entry с индексом, совпадающим со значением параметра поля заголовка «mp» в последней hi-entry с параметром поля заголовка «mp» в hi-target-param в запросе, полученном UAS, то есть последний Request-URI, который был сопоставлен для достижения получателя.
4. Hi-entry with the index that matches the value of the "rc" header field parameter in the first hi-entry with an "rc" header field parameter in the request received by a UAS. Note that this would be the original AOR if all the entities involved support the History-Info header field and there is an absence of an "mp" header field parameter prior to the "rc" header field parameter in the hi-target-param in the History-Info header field. However, there is no guarantee that all entities will support History-Info; thus, the hi-entry that matches the value of the "rc" header field parameter of the first hi-entry with an "rc" header field parameter in the hi-target-param within the domain associated with the target URI at the destination is more likely to be useful.
4. Hi-entry с индексом, совпадающим со значением параметра поля заголовка «rc» в первой hi-entry с параметром поля заголовка «rc» в запросе, полученном UAS. Отметим, что это был бы исходный AOR, если бы все участвующие объекты поддерживали поле заголовка History-Info и при отсутствии параметра поля заголовка «mp» перед параметром поля заголовка «rc» в hi-target-param в поле заголовка History-Info. Однако нет гарантии, что все объекты будут поддерживать History-Info; поэтому более полезной, вероятно, будет hi-entry, соответствующая значению параметра поля заголовка «rc» первой hi-entry с параметром поля заголовка «rc» в hi-target-param в пределах домена, связанного с целевым URI у получателя.
5. Hi-entry with the index that matches the value of the "mp" header field parameter in the first hi-entry with an "mp" header field parameter in the request received by a UAS. Note that this would be the original mapped URI if all entities supported the History- Info header field. However, there is no guarantee that all entities will support History-Info; thus, the hi-entry that matches the value of the "mp" header field parameter of the first hi-entry with an "mp" header field parameter within the domain associated with the target URI at the destination is more likely to be useful.
5. Hi-entry с индексом, совпадающим со значением параметра поля заголовка «mp» в первой hi-entry с параметром поля заголовка «mp» в запросе, полученном UAS. Отметим, что это был бы исходный сопоставленный URI, если бы все объекты поддерживали поле заголовка History-Info. Однако нет гарантии, что все объекты будут поддерживать History-Info; поэтому более полезной, вероятно, будет hi-entry, соответствующая значению параметра поля заголовка «mp» первой hi-entry с параметром поля заголовка «mp» в пределах домена, связанного с целевым URI у получателя.
In many cases, applications are most interested in the information within one or more particular domains; thus, only a subset of the information is required.
Во многих случаях приложения больше всего интересуются информацией в пределах одного или нескольких конкретных доменов; поэтому требуется лишь подмножество информации.
Some applications may use multiple types of information. For example, an Automatic Call Distribution (ACD) / call center application that utilizes the hi-entry with an index that matches the value of the "mp" header field parameter in the first hi-entry with an "mp" header field parameter may also display other agents, reflected by hi-entries prior to hi-entries with an "rc" header field parameter, to whom the call was targeted prior to its arrival at the current agent. This could allow the agent the ability to decide how they might forward or reroute the call if necessary (avoiding agents that were not previously available for whatever reason, etc.).
Некоторые приложения могут использовать несколько типов информации. Например, приложение автоматического распределения вызовов (ACD)/центра обработки вызовов, использующее hi-entry с индексом, совпадающим со значением параметра поля заголовка «mp» в первой hi-entry с параметром поля заголовка «mp», может также отображать других агентов, отражённых в hi-entry перед hi-entry с параметром поля заголовка «rc», которым вызов был адресован до поступления к текущему агенту. Это может позволить агенту решить, как в случае необходимости переслать или перенаправить вызов (избегая агентов, которые ранее были недоступны по той или иной причине, и т. п.).
Since support for History-Info header field is optional, a service MUST define default behavior for requests and responses not containing History-Info header fields. For example, an entity may receive an incomplete set of hi-entries or hi-entries that are not tagged appropriately with an hi-target-param in the case of entries added by entities that are only compliant to RFC 4244. This may not impact some applications (e.g., debug); however, it could require some applications to make some default assumptions in this case. For example, in an ACD scenario, the application could select the oldest hi-entry with the domain associated with the ACD system and display that as the original called party. Depending upon how and where the request may have been retargeted, the complete list of agents to whom the call was targeted may not be available.
Поскольку поддержка поля заголовка History-Info необязательна, служба ДОЛЖНА определять поведение по умолчанию для запросов и ответов, не содержащих полей заголовка History-Info. Например, объект может получить неполный набор hi-entry или hi-entry, не помеченные должным образом с помощью hi-target-param, в случае записей, добавленных объектами, совместимыми только с RFC 4244. Это может не повлиять на некоторые приложения (например, отладку); однако в этом случае оно может потребовать от некоторых приложений делать определённые допущения по умолчанию. Например, в сценарии ACD приложение могло бы выбрать самую старую hi-entry с доменом, связанным с системой ACD, и отобразить её как исходно вызываемую сторону. В зависимости от того, как и где запрос мог быть перенацелен, полный список агентов, которым был адресован вызов, может быть недоступен.
12. Application-Specific Usage
12. Использование, специфичное для приложений
The following are possible (non-normative) application-specific usages of History-Info.
Ниже приведены возможные (не нормативные) варианты использования History-Info, специфичные для приложений.
12.1. PBX Voicemail
12.1. Голосовая почта учрежденческой АТС (PBX)
A voicemail system (VMS) typically requires the original called party information to determine the appropriate mailbox so an appropriate greeting can be provided and the appropriate party notified of the message.
Система голосовой почты (VMS) обычно требует информации об исходно вызываемой стороне, чтобы определить подходящий почтовый ящик, обеспечить соответствующее приветствие и уведомить соответствующую сторону о сообщении.
The original target is determined by finding the first hi-entry tagged with "rc" and using the hi-entry referenced by the index of the "rc" header field parameter as the target for determining the appropriate mailbox. This hi-entry is used to populate the "target" URI parameter as defined in [RFC4458]. The VMS can look at the last hi-entry and find the target of the mailbox by looking at the URI entry in the "target" URI parameter in the hi-entry.
Исходная цель определяется путём поиска первой hi-entry, помеченной «rc», и использования hi-entry, на которую ссылается индекс параметра поля заголовка «rc», в качестве цели для определения подходящего почтового ящика. Эта hi-entry используется для заполнения параметра URI «target», определённого в [RFC4458]. VMS может просмотреть последнюю hi-entry и найти цель почтового ящика, просмотрев запись URI в параметре URI «target» в hi-entry.
This example usage does not work properly in the presence of forwarding that takes place before the call reaches the company. In that case, not the first hi-entry with an "rc" value, but the first hi-entry with an "rc" value following an "mp" entry needs to be picked. Further detail for this example can be found in the call flow entitled "PBX Voicemail Example" in [CALLFLOWS].
Этот пример использования не работает должным образом при наличии переадресации, выполняемой до того, как вызов достигает компании. В этом случае нужно выбрать не первую hi-entry со значением «rc», а первую hi-entry со значением «rc», следующую за записью «mp». Дополнительные сведения об этом примере можно найти в потоке вызовов «PBX Voicemail Example» в [CALLFLOWS].
Note that in the case where there is no entry tagged with "rc", a VMS can follow the procedures, as defined in [RFC4458], for the "Interaction with Request History Information".
Отметим, что в случае отсутствия записи, помеченной «rc», VMS может следовать процедурам, определённым в [RFC4458], для «взаимодействия с информацией об истории запросов».
12.2. Consumer Voicemail
12.2. Голосовая почта для конечных пользователей
The voicemail system in this environment typically requires the last called party information to determine the appropriate mailbox so an appropriate greeting can be provided and the appropriate party notified of the message.
Система голосовой почты в этой среде обычно требует информации о последней вызываемой стороне, чтобы определить подходящий почтовый ящик, обеспечить соответствующее приветствие и уведомить соответствующую сторону о сообщении.
The last target is determined by finding the hi-entry referenced by the index of the last hi-entry tagged with "rc" for determining the appropriate mailbox. This hi-entry is used to populate the "target" URI parameter as defined in [RFC4458]. The VMS can look at the last hi-entry and find the target of the mailbox by looking for the "target" URI parameter in the hi-entry. Further detail for this example can be found in the call flow entitled "Consumer Voicemail Example" in [CALLFLOWS].
Последняя цель определяется путём поиска hi-entry, на которую ссылается индекс последней hi-entry, помеченной «rc», для определения подходящего почтового ящика. Эта hi-entry используется для заполнения параметра URI «target», определённого в [RFC4458]. VMS может просмотреть последнюю hi-entry и найти цель почтового ящика, найдя параметр URI «target» в hi-entry. Дополнительные сведения об этом примере можно найти в потоке вызовов «Consumer Voicemail Example» в [CALLFLOWS].
In the case where there is no entry tagged with "rc", a VMS can follow the procedures, as defined in [RFC4458], for the "Interaction with Request History Information".
В случае отсутствия записи, помеченной «rc», VMS может следовать процедурам, определённым в [RFC4458], для «взаимодействия с информацией об истории запросов».
13. Security Considerations
13. Соображения безопасности
The security requirements for this specification are specified in Appendix A.1.
Требования безопасности для настоящей спецификации указаны в Приложении A.1.
This document defines a header field for SIP. The use of the Transport Layer Security (TLS) protocol [RFC5246] as a mechanism to ensure the overall confidentiality of the History-Info header fields (SEC-req-4) is strongly RECOMMENDED. If TLS is NOT used, the intermediary MUST ensure that the messages are only sent within an environment that is secured by other means or that the messages don't leave the intermediary's domain. This results in History-Info's having at least the same level of security as other headers in SIP that are inserted by intermediaries. With TLS, History-Info header fields are no less, nor no more, secure than other SIP header fields, which generally have even more impact on the subsequent processing of SIP sessions than the History-Info header field.
Настоящий документ определяет поле заголовка для SIP. Настоятельно РЕКОМЕНДУЕТСЯ использовать протокол Transport Layer Security (TLS) [RFC5246] как механизм обеспечения общей конфиденциальности полей заголовка History-Info (SEC-req-4). Если TLS НЕ используется, посредник ДОЛЖЕН обеспечить, чтобы сообщения отправлялись только в среде, защищённой другими средствами, или чтобы сообщения не покидали домен посредника. Это обеспечивает для History-Info по крайней мере тот же уровень безопасности, что и у других заголовков SIP, вставляемых посредниками. При использовании TLS поля заголовка History-Info защищены не менее и не более чем другие поля заголовка SIP, которые обычно оказывают даже большее влияние на последующую обработку сеансов SIP, чем поле заголовка History-Info.
Note that while using the SIPS scheme (as per [RFC5630]) protects History-Info from tampering by arbitrary parties outside the SIP message path, all the intermediaries on the path are trusted implicitly. A malicious intermediary could arbitrarily delete, rewrite, or modify History-Info. This specification does not attempt to prevent or detect attacks by malicious intermediaries. In terms of ensuring the privacy of hi-entries, the same security considerations as those described in [RFC3323] apply. The Privacy Service that's defined in [RFC3323] MUST also support the new Privacy header field priv-value of "history" and anonymize hi-entries in the case of a priv-value of "header" as described in Section 10.1.2.
Отметим, что использование схемы SIPS (согласно [RFC5630]) защищает History-Info от несанкционированного изменения произвольными сторонами вне пути сообщения SIP, однако все посредники на пути неявно считаются доверенными. Вредоносный посредник может произвольно удалять, перезаписывать или изменять History-Info. Настоящая спецификация не пытается предотвращать или обнаруживать атаки вредоносных посредников. В части обеспечения конфиденциальности hi-entry применяются те же соображения безопасности, что описаны в [RFC3323]. Служба обеспечения конфиденциальности, определённая в [RFC3323], ДОЛЖНА также поддерживать новое значение priv-value «history» поля заголовка Privacy и анонимизировать hi-entry в случае значения priv-value «header», как описано в разделе 10.1.2.

16. Changes from RFC 4244

Deployment experience with [RFC4244] over the years has shown a number of issues, warranting an update:
Опыт развёртывания [RFC4244] за прошедшие годы выявил ряд проблем, что обосновывает обновление:
o In order to make [RFC4244] work in "real life", one needs to make "assumptions" on how History-Info is used. For example, numerous implementations filter out many entries and only leave specific entries corresponding, for example, to first and last redirection. o [RFC4244] is overly permissive and evasive about recording entries, causing interoperability issues.
o [RFC4244] чрезмерно либерален и уклончив в отношении записи записей, что вызывает проблемы совместимости.
o The examples in the call flows had errors and were confusing because they often assume "loose routing".
