Abstract
Аннотация
The Session Initiation Protocol (SIP) allows for users to make anonymous calls. However, users receiving such calls have the right to reject them because they are anonymous. SIP has no way to indicate to the caller that the reason for call rejection was that the call was anonymous. Such an indication is useful to allow the call to be retried without anonymity. This specification defines a new SIP response code for this purpose.
Протокол инициирования сессий (SIP) позволяет пользователям совершать анонимные вызовы. Однако пользователи, получающие такие вызовы, имеют право отклонить их, поскольку они анонимны. SIP не имеет возможности указать вызывающему абоненту, что причина отклонения вызова заключалась в том, что вызов был анонимным. Такая индикация полезна для возможности повторной попытки вызова без анонимности. Данная спецификация определяет для этой цели новый код ответа SIP.
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) [RFC3261] allows for users to make anonymous calls. In RFC 3261, this is done by including a From header field whose display name has the value of "Anonymous". Greater levels of anonymity were subsequently defined in [RFC3323], which introduces the Privacy header field. The Privacy header field allows a requesting User Agent (UA) to ask for various levels of anonymity, including user level anonymity, header level anonymity, and session level anonymity. [RFC3325] additionally defined the P-Asserted-Identity header field, used to contain an asserted identity. RFC 3325 also defined the 'id' value for the Privacy header field, which is used to request the network to remove the P-Asserted-Identity header field.
Протокол инициирования сессий (SIP) [RFC3261] позволяет пользователям совершать анонимные вызовы. В RFC 3261 это делается путем включения поля заголовка From, отображаемое имя которого имеет значение «Anonymous». Более высокие уровни анонимности были впоследствии определены в [RFC3323], где введено поле заголовка «Конфиденциальность». Поле заголовка Privacy позволяет запрашивающему пользовательскому агенту (UA) запрашивать различные уровни анонимности, включая анонимность уровня пользователя, анонимность уровня заголовка и анонимность уровня сессии. [RFC3325] дополнительно определил поле заголовка P-Asserted-Identity, используемое для хранения заявленного идентификатора. RFC 3325 также определило значение «id» для поля заголовка Privacy, которое используется для запроса сети на удаление поля заголовка P-Asserted-Identity.
Though users need to be able to make anonymous calls, users that receive such calls retain the right to reject the call because it is anonymous. SIP does not provide a response code that allows the User Agent Server (UAS), or a proxy acting on its behalf, to explicitly indicate that the request was rejected because it was anonymous. The closest response code is 403 (Forbidden), which doesn't convey a specific reason. While it is possible to include a reason phrase in a 403 response that indicates to the human user that the call was rejected because it was anonymous, that reason phrase is not useful for automata and cannot be interpreted by callers that speak a different language. An indication that can be understood by an automaton would allow for programmatic handling, including user interface prompts, or conversion to equivalent error codes in the Public Switched Telephone Network (PSTN) when the client is a gateway.
Хотя пользователи должны иметь возможность совершать анонимные вызовы, пользователи, получающие такие вызовы, сохраняют за собой право отклонить вызов, поскольку он является анонимным. SIP не предоставляет код ответа, который позволяет серверу агента пользователя (UAS) или прокси, действующему от его имени, явно указать, что запрос был отклонен, поскольку он был анонимным. Ближайший код ответа — 403 (Запрещено), который не указывает на конкретную причину. Хотя в ответ 403 можно включить фразу причины, которая указывает пользователю-человеку, что вызов был отклонен, поскольку он был анонимным, эта фраза причины бесполезна для автоматов и не может быть интерпретирована вызывающими абонентами, говорящими на другом языке. Индикация, понятная автомату, позволит осуществлять программную обработку, включая подсказки пользовательского интерфейса, или преобразование в эквивалентные коды ошибок в коммутируемой телефонной сети общего пользования (PSTN), когда клиент является шлюзом.
To remedy this, this specification defines the 433 (Anonymity Disallowed) response code.
Чтобы исправить это, в данной спецификации определен код ответа 433 (анонимность запрещена).

3. Server Behavior
3. Поведение сервера
A server (generally acting on behalf of the called party, though this need not be the case) MAY generate a 433 (Anonymity Disallowed) response when it receives an anonymous request, and the server refuses to fulfill the request because the requestor is anonymous. A request SHOULD be considered anonymous when the identity of the originator of the request has been explicitly withheld by the originator. This occurs in any one of the following cases:
Сервер (обычно действующий от имени вызываемой стороны, хотя это не обязательно) МОЖЕТ сгенерировать ответ 433 (анонимность запрещена) при получении анонимного запроса, и сервер отказывается выполнить запрос, поскольку запрашивающая сторона анонимна. Запрос СЛЕДУЕТ считать анонимным, если личность отправителя запроса была явно скрыта им. Это происходит в любом из следующих случаев:
o The From header field contains a URI within the anonymous.invalid
o Поле заголовка From содержит URI внутри anonymous.invalid

o The From header field contains a display name whose value is either 'Anonymous' or 'anonymous'. Note that display names make a poor choice for indicating anonymity, since they are meant to be consumed by humans, not automata. Thus, language variations and even misspelling can cause an automaton to miss a hint in the display name. Despite these problems, a check on the display name is included here because RFC 3261 explicitly calls out the usage of the display name as a way to declare anonymity.
o Поле заголовка From содержит отображаемое имя, значение которого равно «Anonymous» или «anonymous». Обратите внимание, что отображаемые имена — плохой выбор для обозначения анонимности, поскольку они предназначены для использования людьми, а не автоматами. Таким образом, языковые различия и даже орфографические ошибки могут привести к тому, что автомат пропустит подсказку в отображаемом имени. Несмотря на эти проблемы, сюда включена проверка отображаемого имени, поскольку RFC 3261 явно призывает использовать отображаемое имя как способ объявления анонимности.
o The request contained a Privacy header field whose value indicates that the user wishes its identity withheld. Values meeting this criteria are 'id' [RFC3325] or 'user'.
o Запрос содержал поле заголовка «Конфиденциальность», значение которого указывает на то, что пользователь желает скрыть свою личность. Значения, соответствующие этому критерию: «id» [RFC3325] или «user».
o The From header field contains a URI that has an explicit indication that it is anonymous. One such example of a mechanism that would meet this criteria is [coexistence]. This criteria is true even if the request has a validated Identity header field [RFC4474], which can be used in concert with anonymized From header fields.
o Поле заголовка From содержит URI, который явно указывает на то, что он является анонимным. Одним из таких примеров механизма, который соответствует этому критерию, является [coexistence]. Этот критерий верен, даже если запрос имеет проверенное поле заголовка Identity [RFC4474], которое можно использовать совместно с анонимными полями заголовка From.
Lack of a network-asserted identity (such as the P-Asserted-Identity header field), in and of itself, SHOULD NOT be considered an indication of anonymity. Even though a Privacy header field value of 'id' will cause the removal of a network-asserted identity, there is no way to differentiate this case from one in which a network- asserted identity was not supported by the originating domain. As a consequence, a request without a network-asserted identity is considered anonymous only when there is some other indication of this, such as a From header field with a display name of 'Anonymous'.
Отсутствие удостоверения, подтвержденного сетью (например, поля заголовка P-Asserted-Identity), само по себе НЕ ДОЛЖНО рассматриваться как признак анонимности. Несмотря на то, что значение поля заголовка «Конфиденциальность» «id» приведет к удалению удостоверения, подтвержденного сетью, невозможно отличить этот случай от случая, в котором удостоверение, подтвержденное сетью, не поддерживается исходным доменом. Как следствие, запрос без удостоверения, подтвержденного сетью, считается анонимным только в том случае, если есть какое-либо другое указание на это, например поле заголовка From с отображаемым именем «Anonymous».
In addition, requests where the identity of the requestor cannot be determined or validated, but it is not a consequence of an explicit action on the part of the requestor, are not considered anonymous. For example, if a request contains a non-anonymous From header field, along with the Identity and Identity-Info header fields [RFC4474], but the certificate could not be obtained from the reference in the Identity-Info header field, it is not considered an anonymous request, and the 433 response code SHOULD NOT be used.
Кроме того, не считаются анонимными запросы, в которых личность запрашивающего не может быть определена или подтверждена, но это не является следствием явного действия со стороны запрашивающего. Например, если запрос содержит неанонимное поле заголовка From вместе с полями заголовка Identity и Identity-Info [RFC4474], но сертификат не может быть получен по ссылке в поле заголовка Identity-Info, он не считается анонимным запросом, и код ответа 433 НЕ СЛЕДУЕТ использовать.
4. UAC Behavior
4. Поведение UAC
A User Agent Client (UAC) receiving a 433 (Anonymity Disallowed) MUST NOT retry the request without anonymity unless it obtains confirmation from the user that this is desirable. Such confirmation could be obtained through the user interface, or by accessing user- defined policy. If the user has indicated that this is desirable, the UAC MAY retry the request without requesting anonymity. Note that if the UAC were to automatically retry the request without anonymity in the absence of an indication from the user that this treatment is desirable, then the user's expectations would not be met. Consequently, a user might think it had completed a call anonymously when it is not actually anonymous.
Клиент пользовательского агента (UAC), получающий код 433 (анонимность запрещена), НЕ ДОЛЖЕН повторять запрос без анонимности, пока он не получит подтверждение от пользователя, что это желательно. Такое подтверждение можно получить через пользовательский интерфейс или путем доступа к определяемой пользователем политике. Если пользователь указал, что это желательно, UAC МОЖЕТ повторить запрос без запроса анонимности. Обратите внимание: если UAC автоматически повторит запрос без анонимности при отсутствии указания пользователя на желательность такого обращения, то ожидания пользователя не оправдаются. Следовательно, пользователь может подумать, что он совершил вызов анонимно, хотя на самом деле он не является анонимным.
Receipt of a 433 response to a mid-dialog request SHOULD NOT cause the dialog to terminate, and SHOULD NOT cause the specific usage of that dialog to terminate [RFC5057].
Получение ответа 433 на запрос в середине диалога НЕ ДОЛЖНО приводить к завершению диалога и НЕ ДОЛЖНО вызывать завершение конкретного использования этого диалога [RFC5057].
A UAC that does not understand or care about the specific semantics of the 433 response will treat it as a 400 response.
UAC, который не понимает или не заботится о конкретной семантике ответа 433, будет рассматривать его как ответ 400.
5. 433 (Anonymity Disallowed) Definition
5. 433 (Анонимность запрещена) Определение
This response indicates that the server refused to fulfill the request because the requestor was anonymous. Its default reason phrase is "Anonymity Disallowed".
Этот ответ указывает на то, что сервер отказался выполнить запрос, поскольку отправитель запроса был анонимным. Его фраза причины по умолчанию — «Анонимность запрещена».

7. Security Considerations
7. Вопросы безопасности
The fact that a request was rejected because it was anonymous does reveal information about the called party -- that the called party does not accept anonymous calls. This information may or may not be sensitive. If it is, a UAS SHOULD reject the request with a 403 instead.
Тот факт, что запрос был отклонен, поскольку он был анонимным, раскрывает информацию о вызываемой стороне — вызываемая сторона не принимает анонимные вызовы. Эта информация может быть конфиденциальной, а может и не быть конфиденциальной. Если это так, БПЛА ДОЛЖЕН отклонить запрос вместо этого с кодом 403.
In the Public Switched Telephone Network (PSTN), the Anonymous Call Rejection (ACR) feature is commonly used to prevent unwanted calls from telemarketers (also known as spammers). Since telemarketers frequently withhold their identity, anonymous call rejection has the desired effect in many (but not all) cases. It is important to note that the response code described here is likely to be ineffective in blocking SIP-based spam. The reason is that a malicious caller can include a From header field and display name that is not anonymous, but is meaningless and invalid. Without a Privacy header field, such a request will not appear anonymous and thus not be blocked by an anonymity screening service. Dealing with SIP-based spam is not a simple problem. The reader is referred to [sipping-spam] for a discussion of the problem.
В коммутируемой телефонной сети общего пользования (PSTN) функция отклонения анонимных вызовов (ACR) обычно используется для предотвращения нежелательных вызовов от телемаркетеров (также известных как спамеры). Поскольку телемаркетеры часто скрывают свою личность, отказ от анонимного вызова во многих (но не во всех) случаях дает желаемый эффект. Важно отметить, что описанный здесь код ответа, скорее всего, будет неэффективен для блокировки спама SIP-based. Причина в том, что злоумышленник может включить поле заголовка From и отображаемое имя, которое не является анонимным, но бессмысленным и недействительным. Без поля заголовка «Конфиденциальность» такой запрос не будет выглядеть анонимным и, следовательно, не будет заблокирован службой проверки анонимности. Борьба со спамом SIP-based — непростая задача. Читателя отсылаем к [sipping-spam] для обсуждения проблемы.
When anonymity services are being provided as a consequence of an anonymizer function acting as a back-to-back user agent (B2BUA) [RFC3323], and the anonymizer receives a 433 response, the anonymizer MUST NOT retry the request without anonymization unless it has been explicitly configured by the user to do so. In essence, the same rules that apply to a UA in processing of a 433 response apply to a network-based anonymization function, and for the same reasons.
Когда услуги анонимности предоставляются в результате функции анонимайзера, действующей в качестве последовательного пользовательского агента (B2BUA) [RFC3323], и анонимайзер получает ответ 433, анонимайзер НЕ ДОЛЖЕН повторять запрос без анонимизации, если это не было явно настроено пользователем для этого. По сути, те же правила, которые применяются к UA при обработке ответа 433, применимы и к сетевой функции анонимизации, и по тем же причинам.
