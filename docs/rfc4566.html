Abstract
Аннотация
This memo defines the Session Description Protocol (SDP). SDP is intended for describing multimedia sessions for the purposes of session announcement, session invitation, and other forms of multimedia session initiation.
Настоящий меморандум определяет протокол описания сессий (Session Description Protocol, SDP). SDP предназначен для описания мультимедийных сессий с целью анонсирования сессий, приглашения на сессию и других форм инициирования мультимедийных сессий.
1. Introduction
1. Введение
When initiating multimedia teleconferences, voice-over-IP calls, streaming video, or other sessions, there is a requirement to convey media details, transport addresses, and other session description metadata to the participants.
При инициировании мультимедийных телеконференций, вызовов голосовой связи по IP, потокового видео и других сессий возникает потребность передать участникам сведения о медиа, транспортные адреса и другие метаданные описания сессии.
SDP provides a standard representation for such information, irrespective of how that information is transported. SDP is purely a format for session description -- it does not incorporate a transport protocol, and it is intended to use different transport protocols as appropriate, including the Session Announcement Protocol [14], Session Initiation Protocol [15], Real Time Streaming Protocol [16], electronic mail using the MIME extensions, and the Hypertext Transport Protocol.
SDP обеспечивает стандартное представление такой информации независимо от того, каким образом она передаётся. SDP — это исключительно формат описания сессии: он не включает транспортный протокол и предназначен для использования различных транспортных протоколов по обстоятельствам, включая протокол анонсирования сессий (Session Announcement Protocol) [14], протокол инициирования сессий (Session Initiation Protocol) [15], протокол потоковой передачи в реальном времени (Real Time Streaming Protocol) [16], электронную почту с расширениями MIME и протокол передачи гипертекста.
SDP is intended to be general purpose so that it can be used in a wide range of network environments and applications. However, it is not intended to support negotiation of session content or media encodings: this is viewed as outside the scope of session description.
SDP задуман как универсальный, чтобы его можно было применять в широком диапазоне сетевых сред и приложений. Однако он не предназначен для поддержки согласования содержимого сессии или кодировок медиа: это рассматривается как выходящее за рамки описания сессии.
This memo obsoletes RFC 2327 [6] and RFC 3266 [10]. Section 10 outlines the changes introduced in this memo.
Настоящий меморандум заменяет RFC 2327 [6] и RFC 3266 [10]. В разделе 10 описаны изменения, внесённые настоящим меморандумом.
2. Glossary of Terms
2. Словарь терминов
The following terms are used in this document and have specific meaning within the context of this document.
Следующие термины используются в настоящем документе и имеют особое значение в контексте данного документа.
Conference: A multimedia conference is a set of two or more communicating users along with the software they are using to communicate.
Конференция. Мультимедийная конференция — это набор из двух или более общающихся пользователей вместе с используемым ими программным обеспечением.
Session: A multimedia session is a set of multimedia senders and receivers and the data streams flowing from senders to receivers. A multimedia conference is an example of a multimedia session.
Сессия. Мультимедийная сессия — это набор отправителей и получателей мультимедиа и потоков данных, идущих от отправителей к получателям. Мультимедийная конференция является примером мультимедийной сессии.
Session Description: A well-defined format for conveying sufficient information to discover and participate in a multimedia session.
Описание сессии. Хорошо определённый формат передачи достаточной информации для обнаружения мультимедийной сессии и участия в ней.

Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны толковаться так, как описано в RFC 2119 [3].
3. Examples of SDP Usage
3. Примеры использования SDP
3.1. Session Initiation
3.1. Инициирование сессии
The Session Initiation Protocol (SIP) [15] is an application-layer control protocol for creating, modifying, and terminating sessions such as Internet multimedia conferences, Internet telephone calls, and multimedia distribution. The SIP messages used to create sessions carry session descriptions that allow participants to agree on a set of compatible media types. These session descriptions are commonly formatted using SDP. When used with SIP, the offer/answer model [17] provides a limited framework for negotiation using SDP.
Протокол инициирования сессий (Session Initiation Protocol, SIP) [15] — это протокол управления уровня приложений для создания, изменения и завершения сессий, таких как мультимедийные конференции Интернета, телефонные вызовы через Интернет и распространение мультимедиа. Сообщения SIP, используемые для создания сессий, несут описания сессий, позволяющие участникам согласовать набор совместимых типов медиа. Эти описания сессий обычно форматируются с помощью SDP. При использовании с SIP модель «предложение/ответ» (offer/answer) [17] обеспечивает ограниченную основу для согласования с помощью SDP.
3.2. Streaming Media
3.2. Потоковые медиа
The Real Time Streaming Protocol (RTSP) [16], is an application-level protocol for control over the delivery of data with real-time properties. RTSP provides an extensible framework to enable controlled, on-demand delivery of real-time data, such as audio and video. An RTSP client and server negotiate an appropriate set of parameters for media delivery, partially using SDP syntax to describe those parameters.
Протокол потоковой передачи в реальном времени (Real Time Streaming Protocol, RTSP) [16] — это протокол уровня приложений для управления доставкой данных со свойствами реального времени. RTSP предоставляет расширяемую основу для управляемой доставки данных реального времени по запросу, таких как аудио и видео. Клиент и сервер RTSP согласуют подходящий набор параметров доставки медиа, частично используя синтаксис SDP для описания этих параметров.
3.3. Email and the World Wide Web
3.3. Электронная почта и Всемирная паутина
Alternative means of conveying session descriptions include electronic mail and the World Wide Web (WWW). For both email and WWW distribution, the media type "application/sdp" is used. This enables the automatic launching of applications for participation in the session from the WWW client or mail reader in a standard manner.
Альтернативные средства передачи описаний сессий включают электронную почту и Всемирную паутину (WWW). Для распространения как по электронной почте, так и через WWW используется тип медиа «application/sdp». Это позволяет стандартным образом автоматически запускать приложения для участия в сессии из WWW-клиента или программы чтения почты.
Note that announcements of multicast sessions made only via email or the WWW do not have the property that the receiver of a session announcement can necessarily receive the session because the multicast sessions may be restricted in scope, and access to the WWW server or reception of email is possible outside this scope.
Обратите внимание, что анонсы многоадресных сессий, сделанные только по электронной почте или через WWW, не обладают тем свойством, что получатель анонса сессии обязательно сможет принять эту сессию, поскольку многоадресные сессии могут быть ограничены по области действия, а доступ к WWW-серверу или получение почты возможны вне этой области.
3.4. Multicast Session Announcement
3.4. Анонсирование многоадресных сессий
In order to assist the advertisement of multicast multimedia conferences and other multicast sessions, and to communicate the relevant session setup information to prospective participants, a distributed session directory may be used. An instance of such a session directory periodically sends packets containing a description of the session to a well-known multicast group. These advertisements are received by other session directories such that potential remote participants can use the session description to start the tools required to participate in the session. One protocol used to implement such a distributed directory is the Session Announcement Protocol (SAP) [14]. SDP provides the recommended session description format for such session announcements.
Чтобы способствовать анонсированию многоадресных мультимедийных конференций и других многоадресных сессий и передавать потенциальным участникам соответствующие сведения о настройке сессии, может использоваться распределённый каталог сессий. Экземпляр такого каталога сессий периодически отправляет пакеты, содержащие описание сессии, на широко известную многоадресную группу. Эти анонсы принимаются другими каталогами сессий, так что потенциальные удалённые участники могут использовать описание сессии для запуска инструментов, необходимых для участия в сессии. Один из протоколов, используемых для реализации такого распределённого каталога, — протокол анонсирования сессий (Session Announcement Protocol, SAP) [14]. SDP обеспечивает рекомендуемый формат описания сессии для таких анонсов сессий.
4. Requirements and Recommendations
4. Требования и рекомендации
The purpose of SDP is to convey information about media streams in multimedia sessions to allow the recipients of a session description to participate in the session. SDP is primarily intended for use in an internetwork, although it is sufficiently general that it can describe conferences in other network environments. Media streams can be many-to-many. Sessions need not be continually active.
Назначение SDP — передавать информацию о медиапотоках в мультимедийных сессиях, чтобы получатели описания сессии могли участвовать в сессии. SDP предназначен в первую очередь для использования в объединённой сети, хотя он достаточно универсален, чтобы описывать конференции и в иных сетевых средах. Медиапотоки могут быть «многие ко многим». Сессии не обязаны быть постоянно активными.
Thus far, multicast-based sessions on the Internet have differed from many other forms of conferencing in that anyone receiving the traffic can join the session (unless the session traffic is encrypted). In such an environment, SDP serves two primary purposes. It is a means to communicate the existence of a session, and it is a means to convey sufficient information to enable joining and participating in the session. In a unicast environment, only the latter purpose is likely to be relevant.
До сих пор многоадресные сессии в Интернете отличались от многих иных форм конференций тем, что любой, кто принимает трафик, может присоединиться к сессии (если только трафик сессии не зашифрован). В такой среде SDP служит двум основным целям. Он является средством сообщения о существовании сессии и средством передачи достаточной информации, позволяющей присоединиться к сессии и участвовать в ней. В одноадресной среде, вероятно, имеет значение только последняя цель.
An SDP session description includes the following:
Описание сессии SDP включает следующее:
o Session name and purpose
o Имя и назначение сессии
o Time(s) the session is active
o Время (времена), когда сессия активна
o The media comprising the session
o Медиа, составляющие сессию
o Information needed to receive those media (addresses, ports, formats, etc.)
o Информацию, необходимую для приёма этих медиа (адреса, порты, форматы и т. д.)
As resources necessary to participate in a session may be limited, some additional information may also be desirable:
Поскольку ресурсы, необходимые для участия в сессии, могут быть ограничены, может также оказаться желательной некоторая дополнительная информация:
o Information about the bandwidth to be used by the session
o Информация о полосе пропускания, которая будет использоваться сессией
o Contact information for the person responsible for the session
o Контактная информация о лице, ответственном за сессию
In general, SDP must convey sufficient information to enable applications to join a session (with the possible exception of encryption keys) and to announce the resources to be used to any non-participants that may need to know. (This latter feature is primarily useful when SDP is used with a multicast session announcement protocol.)
В общем случае SDP должен передавать достаточную информацию, чтобы приложения могли присоединиться к сессии (за возможным исключением ключей шифрования), и объявлять ресурсы, которые будут использоваться, любым неучастникам, которым это может понадобиться знать. (Последнее свойство полезно в первую очередь тогда, когда SDP используется с протоколом анонсирования многоадресных сессий.)
4.1. Media and Transport Information
4.1. Информация о медиа и транспорте
An SDP session description includes the following media information:
Описание сессии SDP включает следующую информацию о медиа:
o The type of media (video, audio, etc.)
o Тип медиа (видео, аудио и т. д.)
o The transport protocol (RTP/UDP/IP, H.320, etc.)
o Транспортный протокол (RTP/UDP/IP, H.320 и т. д.)
o The format of the media (H.261 video, MPEG video, etc.)
o Формат медиа (видео H.261, видео MPEG и т. д.)
In addition to media format and transport protocol, SDP conveys address and port details. For an IP multicast session, these comprise:
Помимо формата медиа и транспортного протокола, SDP передаёт сведения об адресе и порте. Для сессии IP-многоадресной рассылки они включают:
o The multicast group address for media o The transport port for media
o Адрес многоадресной группы для медиа o Транспортный порт для медиа
This address and port are the destination address and destination port of the multicast stream, whether being sent, received, or both.
Этот адрес и порт являются адресом назначения и портом назначения многоадресного потока — независимо от того, отправляется он, принимается или и то и другое.
For unicast IP sessions, the following are conveyed:
Для IP-сессий с одноадресной передачей передаётся следующее:
o The remote address for media o The remote transport port for media
o Удалённый адрес для медиа o Удалённый транспортный порт для медиа
The semantics of this address and port depend on the media and transport protocol defined. By default, this SHOULD be the remote address and remote port to which data is sent. Some media types may redefine this behaviour, but this is NOT RECOMMENDED since it complicates implementations (including middleboxes that must parse the addresses to open Network Address Translation (NAT) or firewall pinholes).
Семантика этого адреса и порта зависит от определённых медиа и транспортного протокола. По умолчанию это ДОЛЖЕН быть удалённый адрес и удалённый порт, на которые отправляются данные. Некоторые типы медиа могут переопределять это поведение, но это НЕ РЕКОМЕНДУЕТСЯ, поскольку усложняет реализации (включая промежуточные узлы, которым приходится разбирать адреса, чтобы открыть дырки в трансляции сетевых адресов (NAT) или межсетевом экране).
4.2. Timing Information
4.2. Информация о времени
Sessions may be either bounded or unbounded in time. Whether or not they are bounded, they may be only active at specific times. SDP can convey:
Сессии могут быть ограничены или не ограничены во времени. Независимо от того, ограничены они или нет, они могут быть активны только в определённые моменты времени. SDP может передавать:
o An arbitrary list of start and stop times bounding the session
o Произвольный список времён начала и остановки, ограничивающих сессию
o For each bound, repeat times such as "every Wednesday at 10am for one hour"
o Для каждой границы — времена повторов, например «каждую среду в 10 утра в течение одного часа»
This timing information is globally consistent, irrespective of local time zone or daylight saving time (see Section 5.9).
Эта информация о времени является глобально согласованной, независимо от местного часового пояса или перехода на летнее время (см. раздел 5.9).
4.3. Private Sessions
4.3. Закрытые сессии
It is possible to create both public sessions and private sessions. SDP itself does not distinguish between these; private sessions are typically conveyed by encrypting the session description during distribution. The details of how encryption is performed are dependent on the mechanism used to convey SDP; mechanisms are currently defined for SDP transported using SAP [14] and SIP [15], and others may be defined in the future.
Можно создавать как открытые, так и закрытые сессии. Сам SDP не различает их; закрытые сессии обычно передаются путём шифрования описания сессии при распространении. Детали того, как выполняется шифрование, зависят от механизма, используемого для передачи SDP; в настоящее время механизмы определены для SDP, передаваемого через SAP [14] и SIP [15], и другие могут быть определены в будущем.
If a session announcement is private, it is possible to use that private announcement to convey encryption keys necessary to decode each of the media in a conference, including enough information to know which encryption scheme is used for each media.
Если анонс сессии является закрытым, можно использовать этот закрытый анонс для передачи ключей шифрования, необходимых для декодирования каждого из медиа в конференции, включая достаточно информации, чтобы знать, какая схема шифрования используется для каждого медиа.
4.4. Obtaining Further Information about a Session
4.4. Получение дополнительной информации о сессии
A session description should convey enough information to decide whether or not to participate in a session. SDP may include additional pointers in the form of Uniform Resource Identifiers (URIs) for more information about the session.
Описание сессии должно передавать достаточно информации, чтобы решить, участвовать ли в сессии. SDP может включать дополнительные указатели в виде универсальных идентификаторов ресурсов (URI) для получения дополнительной информации о сессии.
4.5. Categorisation
4.5. Категоризация
When many session descriptions are being distributed by SAP, or any other advertisement mechanism, it may be desirable to filter session announcements that are of interest from those that are not. SDP supports a categorisation mechanism for sessions that is capable of being automated (the "a=cat:" attribute; see Section 6).
Когда множество описаний сессий распространяется через SAP или любой другой механизм анонсирования, может оказаться желательным отфильтровать представляющие интерес анонсы сессий от прочих. SDP поддерживает механизм категоризации сессий, допускающий автоматизацию (атрибут «a=cat:»; см. раздел 6).
4.6. Internationalisation
4.6. Интернационализация
The SDP specification recommends the use of the ISO 10646 character sets in the UTF-8 encoding [5] to allow many different languages to be represented. However, to assist in compact representations, SDP also allows other character sets such as ISO 8859-1 to be used when desired. Internationalisation only applies to free-text fields (session name and background information), and not to SDP as a whole.
Спецификация SDP рекомендует использовать наборы символов ISO 10646 в кодировке UTF-8 [5], чтобы допустить представление множества различных языков. Однако для содействия компактным представлениям SDP также допускает использование других наборов символов, таких как ISO 8859-1, когда это желательно. Интернационализация применяется только к полям свободного текста (имя сессии и фоновая информация), а не к SDP в целом.
5. SDP Specification
5. Спецификация SDP
An SDP session description is denoted by the media type "application/sdp" (See Section 8).
Описание сессии SDP обозначается типом медиа «application/sdp» (см. раздел 8).
An SDP session description is entirely textual using the ISO 10646 character set in UTF-8 encoding. SDP field names and attribute names use only the US-ASCII subset of UTF-8, but textual fields and attribute values MAY use the full ISO 10646 character set. Field and attribute values that use the full UTF-8 character set are never directly compared, hence there is no requirement for UTF-8 normalisation. The textual form, as opposed to a binary encoding such as ASN.1 or XDR, was chosen to enhance portability, to enable a variety of transports to be used, and to allow flexible, text-based toolkits to be used to generate and process session descriptions. However, since SDP may be used in environments where the maximum permissible size of a session description is limited, the encoding is deliberately compact. Also, since announcements may be transported via very unreliable means or damaged by an intermediate caching server, the encoding was designed with strict order and formatting rules so that most errors would result in malformed session announcements that could be detected easily and discarded. This also allows rapid discarding of encrypted session announcements for which a receiver does not have the correct key.
Описание сессии SDP является полностью текстовым и использует набор символов ISO 10646 в кодировке UTF-8. Имена полей и атрибутов SDP используют только подмножество US-ASCII набора UTF-8, но текстовые поля и значения атрибутов МОГУТ использовать полный набор символов ISO 10646. Значения полей и атрибутов, использующие полный набор символов UTF-8, никогда не сравниваются напрямую, поэтому нормировка UTF-8 не требуется. Текстовая форма, в отличие от двоичного кодирования, такого как ASN.1 или XDR, была выбрана для повышения переносимости, чтобы можно было использовать разнообразные транспорты и чтобы можно было применять гибкие инструментальные средства на основе текста для генерации и обработки описаний сессий. Однако поскольку SDP может использоваться в средах, где максимально допустимый размер описания сессии ограничен, кодировка намеренно сделана компактной. Кроме того, поскольку анонсы могут передаваться крайне ненадёжными средствами или быть повреждены промежуточным кэширующим сервером, кодировка была спроектирована со строгими правилами порядка и форматирования, чтобы большинство ошибок приводило к некорректным анонсам сессий, которые можно легко обнаружить и отбросить. Это также позволяет быстро отбрасывать зашифрованные анонсы сессий, для которых у получателя нет правильного ключа.

<nettype> — это текстовая строка, задающая тип сети. Изначально тип «IN» определён со значением «Internet», но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8).
<addrtype> is a text string giving the type of the address that follows. Initially "IP4" and "IP6" are defined, but other values MAY be registered in the future (see Section 8).
<addrtype> — это текстовая строка, задающая тип следующего за ним адреса. Изначально определены «IP4» и «IP6», но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8).
<unicast-address> is the address of the machine from which the session was created. For an address type of IP4, this is either the fully qualified domain name of the machine or the dotted- decimal representation of the IP version 4 address of the machine. For an address type of IP6, this is either the fully qualified domain name of the machine or the compressed textual representation of the IP version 6 address of the machine. For both IP4 and IP6, the fully qualified domain name is the form that SHOULD be given unless this is unavailable, in which case the globally unique address MAY be substituted. A local IP address MUST NOT be used in any context where the SDP description might leave the scope in which the address is meaningful (for example, a local address MUST NOT be included in an application-level referral that might leave the scope).
<unicast-address> — это адрес машины, с которой было создано описание сессии. Для типа адреса IP4 это либо полностью определённое доменное имя машины, либо точечно-десятичное представление адреса IP версии 4 этой машины. Для типа адреса IP6 это либо полностью определённое доменное имя машины, либо сжатое текстовое представление адреса IP версии 6 этой машины. Для обоих типов, IP4 и IP6, полностью определённое доменное имя является той формой, которую СЛЕДУЕТ приводить, если только она недоступна, и в этом случае может быть подставлен глобально уникальный адрес. Локальный IP-адрес НЕ ДОЛЖЕН использоваться ни в каком контексте, где описание SDP может выйти за пределы области, в которой адрес осмыслен (например, локальный адрес НЕ ДОЛЖЕН включаться в переадресацию уровня приложения, которая может выйти за эти пределы).
In general, the "o=" field serves as a globally unique identifier for this version of this session description, and the subfields excepting the version taken together identify the session irrespective of any modifications.
В общем случае поле «o=» служит глобально уникальным идентификатором для этой версии данного описания сессии, а подполя, за исключением версии, взятые вместе, идентифицируют сессию независимо от каких-либо изменений.
For privacy reasons, it is sometimes desirable to obfuscate the username and IP address of the session originator. If this is a concern, an arbitrary <username> and private <unicast-address> MAY be chosen to populate the "o=" field, provided that these are selected in a manner that does not affect the global uniqueness of the field.
По соображениям конфиденциальности иногда желательно затушевать имя пользователя и IP-адрес инициатора сессии. Если это важно, МОГУТ быть выбраны произвольные <username> и частный <unicast-address> для заполнения поля «o=» при условии, что они выбраны так, чтобы не влиять на глобальную уникальность поля.

Как таковые, они наиболее полезны, когда одна сессия имеет более одного отдельного медиапотока одного и того же типа медиа. Примером могут служить две различные доски — одна для слайдов, другая для отзывов и вопросов.
The "i=" field is intended to provide a free-form human-readable description of the session or the purpose of a media stream. It is not suitable for parsing by automata.
Поле «i=» предназначено для предоставления свободного, удобочитаемого человеком описания сессии или назначения медиапотока. Оно не пригодно для разбора автоматами.

Если адрес электронной почты или номер телефона присутствует, он ДОЛЖЕН быть указан перед первым полем медиа. Для описания сессии может быть указано более одного поля электронной почты или телефона.
Phone numbers SHOULD be given in the form of an international public telecommunication number (see ITU-T Recommendation E.164) preceded by a "+". Spaces and hyphens may be used to split up a phone field to aid readability if desired. For example:
Номера телефонов СЛЕДУЕТ приводить в форме международного публичного телекоммуникационного номера (см. рекомендацию ITU-T E.164) с предшествующим знаком «+». Пробелы и дефисы могут использоваться для разбиения поля телефона с целью облегчения чтения, если это желательно. Например:
p=+1 617 555-6011
p=+1 617 555-6011
Both email addresses and phone numbers can have an OPTIONAL free text string associated with them, normally giving the name of the person who may be contacted. This MUST be enclosed in parentheses if it is present. For example:
Как с адресами электронной почты, так и с номерами телефонов может быть связана НЕОБЯЗАТЕЛЬНАЯ строка свободного текста, обычно содержащая имя лица, с которым можно связаться. Если она присутствует, она ДОЛЖНА быть заключена в круглые скобки. Например:
e=j.doe@example.com (Jane Doe)
e=j.doe@example.com (Jane Doe)
The alternative RFC 2822 [29] name quoting convention is also allowed for both email addresses and phone numbers. For example:
Альтернативное соглашение о заключении в кавычки имён RFC 2822 [29] также допускается как для адресов электронной почты, так и для номеров телефонов. Например:
e=Jane Doe <j.doe@example.com>
e=Jane Doe <j.doe@example.com>
The free text string SHOULD be in the ISO-10646 character set with UTF-8 encoding, or alternatively in ISO-8859-1 or other encodings if the appropriate session-level "a=charset" attribute is set.
Строка свободного текста СЛЕДУЕТ приводить в наборе символов ISO-10646 с кодировкой UTF-8 либо, в качестве альтернативы, в ISO-8859-1 или других кодировках, если установлен соответствующий атрибут «a=charset» уровня сессии.
5.7. Connection Data ("c=")
5.7. Данные о соединении («c=»)
c=<nettype> <addrtype> <connection-address>
c=<nettype> <addrtype> <connection-address>
The "c=" field contains connection data.
Поле «c=» содержит данные о соединении.
A session description MUST contain either at least one "c=" field in each media description or a single "c=" field at the session level. It MAY contain a single session-level "c=" field and additional "c=" field(s) per media description, in which case the per-media values override the session-level settings for the respective media.
Описание сессии ДОЛЖНО содержать либо по крайней мере одно поле «c=» в каждом описании медиа, либо одно поле «c=» на уровне сессии. Оно МОЖЕТ содержать одно поле «c=» уровня сессии и дополнительные поля «c=» на каждое описание медиа, и в этом случае значения для отдельных медиа переопределяют установки уровня сессии для соответствующих медиа.
The first sub-field ("<nettype>") is the network type, which is a text string giving the type of network. Initially, "IN" is defined to have the meaning "Internet", but other values MAY be registered in the future (see Section 8).
Первое подполе («<nettype>») — тип сети, текстовая строка, задающая тип сети. Изначально тип «IN» определён со значением «Internet», но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8).
The second sub-field ("<addrtype>") is the address type. This allows SDP to be used for sessions that are not IP based. This memo only defines IP4 and IP6, but other values MAY be registered in the future (see Section 8).
Второе подполе («<addrtype>») — тип адреса. Это позволяет использовать SDP для сессий, не основанных на IP. Настоящий меморандум определяет только IP4 и IP6, но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8).
The third sub-field ("<connection-address>") is the connection address. OPTIONAL sub-fields MAY be added after the connection address depending on the value of the <addrtype> field.
Третье подполе («<connection-address>») — адрес соединения. После адреса соединения МОГУТ быть добавлены НЕОБЯЗАТЕЛЬНЫЕ подполя в зависимости от значения поля <addrtype>.
When the <addrtype> is IP4 and IP6, the connection address is defined as follows:
Когда <addrtype> — это IP4 и IP6, адрес соединения определяется следующим образом:
o If the session is multicast, the connection address will be an IP multicast group address. If the session is not multicast, then the connection address contains the unicast IP address of the expected data source or data relay or data sink as determined by additional attribute fields. It is not expected that unicast addresses will be given in a session description that is communicated by a multicast announcement, though this is not prohibited.
o Если сессия является многоадресной, адрес соединения будет адресом многоадресной группы IP. Если сессия не является многоадресной, адрес соединения содержит одноадресный IP-адрес ожидаемого источника данных, ретранслятора данных или приёмника данных, как определено дополнительными полями атрибутов. Не предполагается, что одноадресные адреса будут указаны в описании сессии, которое передаётся многоадресным анонсом, хотя это не запрещено.
o Sessions using an IPv4 multicast connection address MUST also have a time to live (TTL) value present in addition to the multicast address. The TTL and the address together define the scope with which multicast packets sent in this conference will be sent. TTL values MUST be in the range 0-255. Although the TTL MUST be specified, its use to scope multicast traffic is deprecated; applications SHOULD use an administratively scoped address instead.
o Сессии, использующие адрес многоадресного соединения IPv4, ДОЛЖНЫ также иметь значение времени жизни (TTL) в дополнение к многоадресному адресу. TTL и адрес вместе определяют область действия, в пределах которой будут отправляться многоадресные пакеты, посылаемые в этой конференции. Значения TTL ДОЛЖНЫ находиться в диапазоне 0–255. Хотя TTL ДОЛЖЕН быть указан, его использование для ограничения области действия многоадресного трафика не рекомендуется; приложениям СЛЕДУЕТ использовать административно ограниченный адрес.
The TTL for the session is appended to the address using a slash as a separator. An example is:
TTL для сессии добавляется к адресу с использованием косой черты в качестве разделителя. Пример:
c=IN IP4 224.2.36.42/127
c=IN IP4 224.2.36.42/127
IPv6 multicast does not use TTL scoping, and hence the TTL value MUST NOT be present for IPv6 multicast. It is expected that IPv6 scoped addresses will be used to limit the scope of conferences.
IPv6-многоадресная рассылка не использует TTL для ограничения области действия, поэтому значение TTL НЕ ДОЛЖНО присутствовать для многоадресной рассылки IPv6. Область действия конференций предполагается ограничивать адресами IPv6 с зоной действия.
Hierarchical or layered encoding schemes are data streams where the encoding from a single media source is split into a number of layers. The receiver can choose the desired quality (and hence bandwidth) by only subscribing to a subset of these layers. Such layered encodings are normally transmitted in multiple multicast groups to allow multicast pruning. This technique keeps unwanted traffic from sites only requiring certain levels of the hierarchy. For applications requiring multiple multicast groups, we allow the following notation to be used for the connection address:
Иерархические или многоуровневые схемы кодирования — это потоки данных, в которых кодировка от одного источника медиа разделяется на несколько уровней. Получатель может выбрать желаемое качество (и, следовательно, полосу пропускания), подписавшись только на подмножество этих уровней. Такие многоуровневые кодировки обычно передаются в нескольких многоадресных группах, чтобы обеспечить отсечение многоадресной рассылки. Эта методика удерживает нежелательный трафик от узлов, которым требуются только определённые уровни иерархии. Для приложений, требующих нескольких многоадресных групп, мы допускаем использование для адреса соединения следующей нотации:
<base multicast address>[/<ttl>]/<number of addresses>
<base multicast address>[/<ttl>]/<number of addresses>
If the number of addresses is not given, it is assumed to be one. Multicast addresses so assigned are contiguously allocated above the base address, so that, for example:
Если число адресов не задано, предполагается, что оно равно единице. Назначенные таким образом многоадресные адреса выделяются подряд выше базового адреса, так что, например:
c=IN IP4 224.2.1.1/127/3
c=IN IP4 224.2.1.1/127/3
would state that addresses 224.2.1.1, 224.2.1.2, and 224.2.1.3 are to be used at a TTL of 127. This is semantically identical to including multiple "c=" lines in a media description:
говорила бы, что адреса 224.2.1.1, 224.2.1.2 и 224.2.1.3 должны использоваться при TTL 127. Это семантически идентично включению нескольких строк «c=» в описание медиа:
c=IN IP4 224.2.1.1/127 c=IN IP4 224.2.1.2/127 c=IN IP4 224.2.1.3/127
c=IN IP4 224.2.1.1/127 c=IN IP4 224.2.1.2/127 c=IN IP4 224.2.1.3/127
Similarly, an IPv6 example would be:
Аналогично пример для IPv6 выглядел бы так:
c=IN IP6 FF15::101/3
c=IN IP6 FF15::101/3
which is semantically equivalent to:
что семантически эквивалентно:
c=IN IP6 FF15::101 c=IN IP6 FF15::102 c=IN IP6 FF15::103
c=IN IP6 FF15::101 c=IN IP6 FF15::102 c=IN IP6 FF15::103
(remembering that the TTL field is not present in IPv6 multicast).
(напоминаем, что поле TTL отсутствует в многоадресной рассылке IPv6).
Multiple addresses or "c=" lines MAY be specified on a per-media basis only if they provide multicast addresses for different layers in a hierarchical or layered encoding scheme. They MUST NOT be specified for a session-level "c=" field.
Несколько адресов или строк «c=» МОГУТ задаваться только на уровне отдельных медиа и только если они предоставляют многоадресные адреса для разных уровней иерархической или многоуровневой схемы кодирования. Они НЕ ДОЛЖНЫ задаваться для поля «c=» уровня сессии.
The slash notation for multiple addresses described above MUST NOT be used for IP unicast addresses.
Описанная выше нотация с косой чертой для нескольких адресов НЕ ДОЛЖНА использоваться для одноадресных адресов IP.
5.8. Bandwidth ("b=")
5.8. Полоса пропускания («b=»)
b=<bwtype>:<bandwidth>
b=<bwtype>:<bandwidth>
This OPTIONAL field denotes the proposed bandwidth to be used by the session or media. The <bwtype> is an alphanumeric modifier giving the meaning of the <bandwidth> figure. Two values are defined in this specification, but other values MAY be registered in the future (see Section 8 and [21], [25]):
Это НЕОБЯЗАТЕЛЬНОЕ поле обозначает предлагаемую полосу пропускания, которая будет использоваться сессией или медиа. <bwtype> — это буквенно-цифровой модификатор, задающий смысл значения <bandwidth>. В настоящей спецификации определены два значения, но другие значения МОГУТ быть зарегистрированы в будущем (см. раздел 8 и [21], [25]):
CT If the bandwidth of a session or media in a session is different from the bandwidth implicit from the scope, a "b=CT:..." line SHOULD be supplied for the session giving the proposed upper limit to the bandwidth used (the "conference total" bandwidth). The primary purpose of this is to give an approximate idea as to whether two or more sessions can coexist simultaneously. When using the CT modifier with RTP, if several RTP sessions are part of the conference, the conference total refers to total bandwidth of all RTP sessions.
CT Если полоса пропускания сессии или медиа в сессии отличается от полосы пропускания, подразумеваемой областью действия, для сессии СЛЕДУЕТ указать строку «b=CT:...», задающую предлагаемый верхний предел используемой полосы пропускания (полоса пропускания, «общая для конференции»). Основное назначение этого — дать приблизительное представление о том, могут ли две или более сессий существовать одновременно. При использовании модификатора CT с RTP, если несколько RTP-сессий являются частью конференции, общая для конференции величина относится к суммарной полосе пропускания всех RTP-сессий.
AS The bandwidth is interpreted to be application specific (it will be the application's concept of maximum bandwidth). Normally, this will coincide with what is set on the application's "maximum bandwidth" control if applicable. For RTP-based applications, AS gives the RTP "session bandwidth" as defined in Section 6.2 of [19].
AS Полоса пропускания интерпретируется как специфичная для приложения (это будет понятие приложения о максимальной полосе пропускания). Обычно это совпадает с тем, что устанавливается в элементе управления «maximum bandwidth» приложения, если такой имеется. Для приложений на основе RTP AS задаёт «полосу пропускания сессии» RTP, как определено в разделе 6.2 работы [19].
Note that CT gives a total bandwidth figure for all the media at all sites. AS gives a bandwidth figure for a single media at a single site, although there may be many sites sending simultaneously.
Обратите внимание, что CT даёт величину общей полосы пропускания для всех медиа на всех сайтах. AS даёт величину полосы пропускания для одного медиа на одном сайте, хотя одновременно могут отправлять многие сайты.
A prefix "X-" is defined for <bwtype> names. This is intended for experimental purposes only. For example:
Для имён <bwtype> определён префикс «X-». Он предназначен только для экспериментальных целей. Например:
b=X-YZ:128
b=X-YZ:128
Use of the "X-" prefix is NOT RECOMMENDED: instead new modifiers SHOULD be registered with IANA in the standard namespace. SDP parsers MUST ignore bandwidth fields with unknown modifiers. Modifiers MUST be alphanumeric and, although no length limit is given, it is recommended that they be short.
Использование префикса «X-» НЕ РЕКОМЕНДУЕТСЯ: вместо этого новые модификаторы СЛЕДУЕТ регистрировать в IANA в стандартном пространстве имён. Разборщики SDP ДОЛЖНЫ игнорировать поля полосы пропускания с неизвестными модификаторами. Модификаторы ДОЛЖНЫ быть буквенно-цифровыми и, хотя предельная длина не задана, рекомендуется, чтобы они были короткими.
The <bandwidth> is interpreted as kilobits per second by default. The definition of a new <bwtype> modifier MAY specify that the bandwidth is to be interpreted in some alternative unit (the "CT" and "AS" modifiers defined in this memo use the default units).
<bandwidth> по умолчанию интерпретируется как килобиты в секунду. Определение нового модификатора <bwtype> МОЖЕТ указывать, что полоса пропускания должна интерпретироваться в какой-либо иной единице (модификаторы «CT» и «AS», определённые в настоящем меморандуме, используют единицы по умолчанию).
5.9. Timing ("t=")
5.9. Время («t=»)
t=<start-time> <stop-time>
t=<start-time> <stop-time>
The "t=" lines specify the start and stop times for a session. Multiple "t=" lines MAY be used if a session is active at multiple irregularly spaced times; each additional "t=" line specifies an additional period of time for which the session will be active. If the session is active at regular times, an "r=" line (see below) should be used in addition to, and following, a "t=" line -- in which case the "t=" line specifies the start and stop times of the repeat sequence.
Строки «t=» задают время начала и остановки сессии. Несколько строк «t=» МОГУТ использоваться, если сессия активна в несколько неравномерно распределённых моментов времени; каждая дополнительная строка «t=» задаёт дополнительный период, в течение которого сессия будет активна. Если сессия активна в регулярные моменты времени, в дополнение к строке «t=» и после неё следует использовать строку «r=» (см. ниже) — в этом случае строка «t=» задаёт время начала и остановки последовательности повторений.
The first and second sub-fields give the start and stop times, respectively, for the session. These values are the decimal representation of Network Time Protocol (NTP) time values in seconds since 1900 [13]. To convert these values to UNIX time, subtract decimal 2208988800.
Первое и второе подполя задают соответственно время начала и остановки сессии. Эти значения — десятичное представление значений времени протокола синхронизации времени по сети (NTP) в секундах с 1900 года [13]. Чтобы преобразовать эти значения во время UNIX, вычтите десятичное число 2208988800.
NTP timestamps are elsewhere represented by 64-bit values, which wrap sometime in the year 2036. Since SDP uses an arbitrary length decimal representation, this should not cause an issue (SDP timestamps MUST continue counting seconds since 1900, NTP will use the value modulo the 64-bit limit).
Отметки времени NTP в других местах представляются 64-битовыми значениями, которые переполнятся в какой-то момент 2036 года. Поскольку SDP использует десятичное представление произвольной длины, это не должно создавать проблем (отметки времени SDP ДОЛЖНЫ продолжать отсчёт секунд с 1900 года, NTP будет использовать значение по модулю 64-битового предела).
If the <stop-time> is set to zero, then the session is not bounded, though it will not become active until after the <start-time>. If the <start-time> is also zero, the session is regarded as permanent.
Если <stop-time> установлено в ноль, то сессия не ограничена, хотя она не станет активной до наступления <start-time>. Если <start-time> также равно нулю, сессия считается постоянной.
User interfaces SHOULD strongly discourage the creation of unbounded and permanent sessions as they give no information about when the session is actually going to terminate, and so make scheduling difficult.
Пользовательским интерфейсам СЛЕДУЕТ настоятельно отговаривать от создания неограниченных и постоянных сессий, поскольку они не дают информации о том, когда сессия фактически завершится, и поэтому затрудняют планирование.
The general assumption may be made, when displaying unbounded sessions that have not timed out to the user, that an unbounded session will only be active until half an hour from the current time or the session start time, whichever is the later. If behaviour other than this is required, an end-time SHOULD be given and modified as appropriate when new information becomes available about when the session should really end.
При отображении пользователю неограниченных сессий, срок которых не истёк, можно принять общее допущение, что неограниченная сессия будет активна только до получаса от текущего времени или от времени начала сессии — в зависимости от того, что позже. Если требуется иное поведение, СЛЕДУЕТ задать время окончания и изменять его по мере поступления новой информации о том, когда сессия должна в действительности завершиться.
Permanent sessions may be shown to the user as never being active unless there are associated repeat times that state precisely when the session will be active.
Постоянные сессии могут отображаться пользователю как никогда не активные, если только нет связанных времён повторения, точно указывающих, когда сессия будет активна.
5.10. Repeat Times ("r=")
5.10. Времена повторения («r=»)
r=<repeat interval> <active duration> <offsets from start-time>
r=<repeat interval> <active duration> <offsets from start-time>
"r=" fields specify repeat times for a session. For example, if a session is active at 10am on Monday and 11am on Tuesday for one hour each week for three months, then the <start-time> in the corresponding "t=" field would be the NTP representation of 10am on the first Monday, the <repeat interval> would be 1 week, the <active duration> would be 1 hour, and the offsets would be zero and 25 hours. The corresponding "t=" field stop time would be the NTP representation of the end of the last session three months later. Поля «r=» задают времена повторения для сессии. Например, если сессия активна в 10 утра в понедельник и в 11 утра во вторник по одному часу каждую неделю в течение трёх месяцев, то <start-time> в соответствующем поле «t=» было бы представлением в NTP 10 утра первого понедельника, <repeat interval> составил бы 1 неделю, <active duration> составил бы 1 час, а смещения были бы нулём и 25 часами. Соответствующее поле «t=» указывало бы время остановки сессии через три месяца после первого понедельника. По умолчанию все поля задаются в секундах, поэтому поля «r=» и «t=» могли бы выглядеть так:
t=3034423619 3042462419 r=604800 3600 0 90000
t=3034423619 3042462419 r=604800 3600 0 90000

Синтаксис для них — число, за которым непосредственно следует один символ, чувствительный к регистру. Дробные единицы не допускаются — вместо них следует использовать меньшую единицу. If transported over a secure and trusted channel, the Session Description Protocol MAY be used to convey encryption keys. A simple mechanism for key exchange is provided by the key field ("k="), although this is primarily supported for compatibility with older implementations and its use is NOT RECOMMENDED. Work is in progress to define new key exchange mechanisms for use with SDP [27] [28], and it is expected that new applications will use those mechanisms. A key field is permitted before the first media entry (in which case it applies to all media in the session), or for each media entry as required. The format of keys and their usage are outside the scope of this document, and the key field provides no way to indicate the encryption algorithm to be used, key type, or other information about the key: this is assumed to be provided by the higher-level protocol using SDP. If there is a need to convey this information within SDP, the extensions mentioned previously SHOULD be used. Many security protocols require two keys: one for confidentiality, another for integrity. This specification does not support transfer of two keys.

Attributes are the primary means for extending SDP. Attributes may be defined to be used as "session-level" attributes, "media-level" attributes, or both.
Атрибуты являются основным средством расширения SDP. Атрибуты могут быть определены для использования в качестве атрибутов «уровня сессии», атрибутов «уровня медиа» или и того и другого.
A media description may have any number of attributes ("a=" fields) that are media specific. These are referred to as "media-level" attributes and add information about the media stream. Описание медиа может иметь любое количество атрибутов (полей «a=»), специфичных для этого медиа. Они называются атрибутами «уровня медиа» и добавляют информацию о медиапотоке. 7. Security Considerations
7. Вопросы безопасности
SDP is frequently used with the Session Initiation Protocol [15] using the offer/answer model [17] to agree on parameters for unicast sessions. When used in this manner, the security considerations of those protocols apply.
SDP часто используется с протоколом инициирования сессий (SIP) [15] и моделью «предложение/ответ» [17] для согласования параметров одноадресных сессий. При таком использовании применяются соображения безопасности этих протоколов.
SDP is a session description format that describes multimedia sessions. Entities receiving and acting upon an SDP message SHOULD be aware that a session description cannot be trusted unless it has been obtained by an authenticated transport protocol from a known and trusted source. Many different transport protocols may be used to distribute session description, and the nature of the authentication will differ from transport to transport. For some transports, security features are often not deployed. In case a session description has not been obtained in a trusted manner, the endpoint SHOULD exercise care because, among other attacks, the media sessions received may not be the intended ones, the destination where media is sent to may not be the expected one, any of the parameters of the session may be incorrect, or the media security may be compromised. It is up to the endpoint to make a sensible decision taking into account the security risks of the application and the user preferences and may decide to ask the user whether or not to accept the session.
SDP — это формат описания сессии, который описывает мультимедийные сессии. Субъекты, получающие сообщение SDP и действующие на его основе, ДОЛЖНЫ осознавать, что описанию сессии нельзя доверять, если оно не получено по аутентифицированному транспортному протоколу из известного и доверенного источника. Для распространения описаний сессий может использоваться множество различных транспортных протоколов, и характер аутентификации будет различаться от транспорта к транспорту. Для некоторых транспортов средства безопасности часто не развёрнуты. В случае если описание сессии получено не доверенным образом, конечная точка ДОЛЖНА проявлять осторожность, поскольку, среди прочих атак, полученные медиасессии могут быть не теми, что предполагались, пункт назначения, куда отправляются медиа, может быть не ожидаемым, любой из параметров сессии может быть неверным или безопасность медиа может быть скомпрометирована. Конечная точка должна принять разумное решение с учётом рисков безопасности приложения и предпочтений пользователя и может решить спросить пользователя, принимать ли сессию.
One transport that can be used to distribute session descriptions is the Session Announcement Protocol (SAP). SAP provides both encryption and authentication mechanisms, but due to the nature of session announcements it is likely that there are many occasions where the originator of a session announcement cannot be authenticated because the originator is previously unknown to the receiver of the announcement and because no common public key infrastructure is available.
Один из транспортов, которые могут использоваться для распространения описаний сессий, — это протокол анонсирования сессий (SAP). SAP предоставляет как механизмы шифрования, так и механизмы аутентификации, но из-за природы анонсов сессий вероятно, что во многих случаях инициатор анонса сессии не может быть аутентифицирован, поскольку инициатор ранее неизвестен получателю анонса и поскольку нет доступной общей инфраструктуры открытых ключей.
On receiving a session description over an unauthenticated transport mechanism or from an untrusted party, software parsing the session should take a few precautions. Session descriptions contain information required to start software on the receiver's system. Software that parses a session description MUST NOT be able to start other software except that which is specifically configured as appropriate software to participate in multimedia sessions. It is normally considered inappropriate for software parsing a session description to start, on a user's system, software that is appropriate to participate in multimedia sessions, without the user first being informed that such software will be started and giving the user's consent. Thus, a session description arriving by session announcement, email, session invitation, or WWW page MUST NOT deliver the user into an interactive multimedia session unless the user has explicitly pre-authorised such action. As it is not always simple to tell whether or not a session is interactive, applications that are unsure should assume sessions are interactive.
При получении описания сессии по неаутентифицированному транспортному механизму или от недоверенной стороны программное обеспечение, разбирающее сессию, должно принять некоторые меры предосторожности. Описания сессий содержат информацию, необходимую для запуска программного обеспечения в системе получателя. Программное обеспечение, разбирающее описание сессии, НЕ ДОЛЖНО иметь возможности запускать другое программное обеспечение, кроме того, которое специально сконфигурировано как подходящее для участия в мультимедийных сессиях. Обычно считается недопустимым, чтобы программное обеспечение, разбирающее описание сессии, запускало в системе пользователя программное обеспечение, подходящее для участия в мультимедийных сессиях, без предварительного информирования пользователя о том, что такое программное обеспечение будет запущено, и без согласия пользователя. Таким образом, описание сессии, поступившее через анонс сессии, электронную почту, приглашение на сессию или страницу WWW, НЕ ДОЛЖНО ввергать пользователя в интерактивную мультимедийную сессию, если пользователь явно не дал предварительного разрешения на такое действие. Поскольку не всегда просто определить, является ли сессия интерактивной, приложения, которые не уверены, должны предполагать, что сессии интерактивны.
In this specification, there are no attributes that would allow the recipient of a session description to be informed to start multimedia tools in a mode where they default to transmitting. Under some circumstances it might be appropriate to define such attributes. If this is done, an application parsing a session description containing such attributes SHOULD either ignore them or inform the user that joining this session will result in the automatic transmission of multimedia data. The default behaviour for an unknown attribute is to ignore it.
В настоящей спецификации нет атрибутов, которые позволяли бы информировать получателя описания сессии о необходимости запуска мультимедийных инструментов в режиме, где они по умолчанию передают данные. При некоторых обстоятельствах может быть уместно определить такие атрибуты. Если это сделано, приложение, разбирающее описание сессии, содержащее такие атрибуты, ДОЛЖНО либо игнорировать их, либо информировать пользователя о том, что присоединение к этой сессии приведёт к автоматической передаче мультимедийных данных. Поведение по умолчанию для неизвестного атрибута — игнорировать его.
In certain environments, it has become common for intermediary systems to intercept and analyse session descriptions contained within other signalling protocols. This is done for a range of purposes, including but not limited to opening holes in firewalls to allow media streams to pass, or to mark, prioritize, or block traffic selectively. In some cases, such intermediary systems may modify the session description, for example, to have the contents of the session description match NAT bindings dynamically created. These behaviours are NOT RECOMMENDED unless the session description is conveyed in such a manner that allows the intermediary system to conduct proper checks to establish the authenticity of the session description, and the authority of its source to establish such communication sessions. SDP by itself does not include sufficient information to enable these checks: they depend on the encapsulating protocol (e.g., SIP or RTSP).
В некоторых средах стало обычным, что промежуточные системы перехватывают и анализируют описания сессий, содержащиеся в других сигнальных протоколах. Это делается для ряда целей, включая, но не ограничиваясь, открытие дырок в межсетевых экранах, чтобы пропустить медиапотоки, или маркировку, приоритизацию или выборочную блокировку трафика. В некоторых случаях такие промежуточные системы могут изменять описание сессии, например чтобы содержимое описания сессии соответствовало динамически созданным привязкам NAT. Такое поведение НЕ РЕКОМЕНДУЕТСЯ, если только описание сессии не передаётся таким образом, который позволяет промежуточной системе провести надлежащие проверки для установления подлинности описания сессии и полномочий его источника на установление таких сессий связи. Сам SDP не содержит достаточной информации для таких проверок: они зависят от инкапсулирующего протокола (например, SIP или RTSP).
Use of the "k=" field poses a significant security risk, since it conveys session encryption keys in the clear. SDP MUST NOT be used to convey key material, unless it can be guaranteed that the channel over which the SDP is delivered is both private and authenticated. Moreover, the "k=" line provides no way to indicate or negotiate cryptographic key algorithms. As it provides for only a single symmetric key, rather than separate keys for confidentiality and integrity, its utility is severely limited. The use of the "k=" line is NOT RECOMMENDED, as discussed in Section 5.12.
Использование поля «k=» создаёт значительный риск безопасности, поскольку оно передаёт ключи шифрования сессии в открытом виде. SDP НЕ ДОЛЖЕН использоваться для передачи ключевого материала, если нельзя гарантировать, что канал, по которому доставляется SDP, одновременно является частным и аутентифицированным. Более того, строка «k=» не даёт способа указать или согласовать криптографические алгоритмы ключей. Поскольку она предусматривает только один симметричный ключ, а не отдельные ключи для конфиденциальности и целостности, её полезность серьёзно ограничена. Использование строки «k=» НЕ РЕКОМЕНДУЕТСЯ, как обсуждается в разделе 5.12.

8.2. Registration of Parameters
8.2. Регистрация параметров
There are seven field names that may be registered with IANA. Using the terminology in the SDP specification Backus-Naur Form (BNF), they are "media", "proto", "fmt", "att-field", "bwtype", "nettype", and "addrtype".
Существует семь имён полей, которые могут быть зарегистрированы в IANA. Используя терминологию формы Бэкуса — Наура (BNF) спецификации SDP, это «media», «proto», «fmt», «att-field», «bwtype», «nettype» и «addrtype».
8.2.1. Media Types ("media")
8.2.1. Типы медиа («media»)
The set of media types is intended to be small and SHOULD NOT be extended except under rare circumstances. The same rules should apply for media names as for top-level media content types, and where possible the same name should be registered for SDP as for MIME. For media other than existing top-level media content types, a Standards Track RFC MUST be produced for a new top-level content type to be registered, and the registration MUST provide good justification why no existing media name is appropriate (the "Standards Action" policy of RFC 2434 [8].
Набор типов медиа должен быть небольшим, и его НЕ СЛЕДУЕТ расширять, кроме редких случаев. Для имён медиа должны применяться те же правила, что и для типов содержимого верхнего уровня, и где возможно для SDP должно регистрироваться то же имя, что и для MIME. Для медиа, отличных от существующих типов содержимого верхнего уровня, для регистрации нового типа содержимого верхнего уровня ДОЛЖЕН быть подготовлен RFC уровня Standards Track, и регистрация ДОЛЖНА содержать веское обоснование того, почему ни одно существующее имя медиа не подходит (политика «Standards Action» RFC 2434 [8]).
This memo registers the media types "audio", "video", "text", "application", and "message".
Настоящий меморандум регистрирует типы медиа «audio», «video», «text», «application» и «message».
Note: The media types "control" and "data" were listed as valid in the previous version of this specification [6]; however, their semantics were never fully specified and they are not widely used. These media types have been removed in this specification, although they still remain valid media type capabilities for a SIP user agent as defined in RFC 3840 [24]. If these media types are considered useful in the future, a Standards Track RFC MUST be produced to document their use. Until that is done, applications SHOULD NOT use these types and SHOULD NOT declare support for them in SIP capabilities declarations (even though they exist in the registry created by RFC 3840).
Примечание. Типы медиа «control» и «data» были перечислены как допустимые в предыдущей версии настоящей спецификации [6]; однако их семантика никогда не была полностью определена, и они широко не используются. Эти типы медиа удалены в настоящей спецификации, хотя они по-прежнему остаются допустимыми возможностями типов медиа для пользовательского агента SIP, как определено в RFC 3840 [24]. Если эти типы медиа будут признаны полезными в будущем, ДОЛЖЕН быть подготовлен RFC уровня Standards Track, документирующий их использование. До тех пор приложениям НЕ СЛЕДУЕТ использовать эти типы и НЕ СЛЕДУЕТ объявлять их поддержку в объявлениях возможностей SIP (хотя они существуют в реестре, созданном RFC 3840).
8.2.2. Transport Protocols ("proto")
8.2.2. Транспортные протоколы («proto»)
The "proto" field describes the transport protocol used. This SHOULD reference a standards-track protocol RFC. This memo registers three values: "RTP/AVP" is a reference to RTP [19] used under the RTP Profile for Audio and Video Conferences with Minimal Control [20] running over UDP/IP, "RTP/SAVP" is a reference to the Secure Real- time Transport Protocol [23], and "udp" indicates an unspecified protocol over UDP.
Поле «proto» описывает используемый транспортный протокол. Оно СЛЕДУЕТ ссылаться на RFC протокола уровня Standards Track. Настоящий меморандум регистрирует три значения: «RTP/AVP» — ссылка на RTP [19], используемый в рамках профиля RTP для аудио- и видеоконференций с минимальным управлением [20] и работающий поверх UDP/IP, «RTP/SAVP» — ссылка на протокол безопасной передачи в реальном времени (Secure Real-time Transport Protocol) [23], а «udp» обозначает неопределённый протокол поверх UDP.
If other RTP profiles are defined in the future, their "proto" name SHOULD be specified in the same manner. For example, an RTP profile whose short name is "XYZ" would be denoted by a "proto" field of "RTP/XYZ".
Если в будущем будут определены другие профили RTP, их имя «proto» СЛЕДУЕТ задавать таким же образом. Например, профиль RTP, краткое имя которого «XYZ», обозначался бы полем «proto» со значением «RTP/XYZ».
New transport protocols SHOULD be registered with IANA. Registrations MUST reference an RFC describing the protocol. Such an RFC MAY be Experimental or Informational, although it is preferable that it be Standards Track. Registrations MUST also define the rules by which their "fmt" namespace is managed (see below).
Новые транспортные протоколы СЛЕДУЕТ регистрировать в IANA. Регистрации ДОЛЖНЫ ссылаться на RFC, описывающий протокол. Такой RFC МОЖЕТ быть Experimental или Informational, хотя предпочтительно, чтобы он был уровня Standards Track. Регистрации также ДОЛЖНЫ определять правила, по которым управляется пространство имён их «fmt» (см. ниже).
8.2.3. Media Formats ("fmt")
8.2.3. Форматы медиа («fmt»)
Each transport protocol, defined by the "proto" field, has an associated "fmt" namespace that describes the media formats that may be conveyed by that protocol. Formats cover all the possible encodings that might want to be transported in a multimedia session.
Каждый транспортный протокол, определённый полем «proto», имеет связанное пространство имён «fmt», которое описывает форматы медиа, могущие передаваться этим протоколом. Форматы охватывают все возможные кодировки, которые может потребоваться передать в мультимедийной сессии.
RTP payload formats under the "RTP/AVP" and "RTP/SAVP" profiles MUST use the payload type number as their "fmt" value. If the payload type number is dynamically assigned by this session description, an additional "rtpmap" attribute MUST be included to specify the format name and parameters as defined by the media type registration for the payload format. It is RECOMMENDED that other RTP profiles that are registered (in combination with RTP) as SDP transport protocols specify the same rules for the "fmt" namespace.
Форматы полезной нагрузки RTP в рамках профилей «RTP/AVP» и «RTP/SAVP» ДОЛЖНЫ использовать номер типа полезной нагрузки в качестве значения «fmt». Если номер типа полезной нагрузки динамически назначается этим описанием сессии, ДОЛЖЕН быть включён дополнительный атрибут «rtpmap», задающий имя формата и параметры, как определено регистрацией типа медиа для формата полезной нагрузки. РЕКОМЕНДУЕТСЯ, чтобы другие профили RTP, регистрируемые (в сочетании с RTP) как транспортные протоколы SDP, задавали те же правила для пространства имён «fmt».
For the "udp" protocol, new formats SHOULD be registered. Use of an existing media subtype for the format is encouraged. If no media subtype exists, it is RECOMMENDED that a suitable one be registered through the IETF process [31] by production of, or reference to, a standards-track RFC that defines the transport protocol for the format.
Для протокола «udp» СЛЕДУЕТ регистрировать новые форматы. Поощряется использование существующего подтипа медиа для формата. Если подтип медиа не существует, РЕКОМЕНДУЕТСЯ зарегистрировать подходящий через процесс IETF [31] путём подготовки или ссылки на RFC уровня Standards Track, определяющий транспортный протокол для формата.
For other protocols, formats MAY be registered according to the rules of the associated "proto" specification.
Для других протоколов форматы МОГУТ регистрироваться согласно правилам соответствующей спецификации «proto».
Registrations of new formats MUST specify which transport protocols they apply to.
Регистрации новых форматов ДОЛЖНЫ указывать, к каким транспортным протоколам они применяются.

8.2.4. Имена атрибутов («att-field»)

Неизвестные атрибуты в SDP просто игнорируются, но конфликтующие, которые фрагментируют протокол, являются серьёзной проблемой.

Submitters of registrations should ensure that the specification is in the spirit of SDP attributes, most notably that the attribute is platform independent in the sense that it makes no implicit assumptions about operating systems and does not name specific pieces of software in a manner that might inhibit interoperability.
Заявители регистраций должны убедиться, что спецификация соответствует духу атрибутов SDP, в первую очередь что атрибут не зависит от платформы в том смысле, что он не делает неявных предположений об операционных системах и не называет конкретные программные продукты так, что это могло бы препятствовать совместимости.

8.2.6. Типы сетей («nettype»)
New network types (the "nettype" field) may be registered with IANA if SDP needs to be used in the context of non-Internet environments. Although these are not normally the preserve of IANA, there may be circumstances when an Internet application needs to interoperate with a non-Internet application, such as when gatewaying an Internet telephone call into the Public Switched Telephone Network (PSTN). The number of network types should be small and should be rarely extended. A new network type cannot be registered without registering at least one address type to be used with that network type. A new network type registration MUST reference an RFC that gives details of the network type and address type and specifies how and when they would be used.
Новые типы сетей (поле «nettype») могут быть зарегистрированы в IANA, если SDP требуется использовать в контексте неинтернет-сред. Хотя это обычно не является прерогативой IANA, могут возникнуть обстоятельства, когда интернет-приложению нужно взаимодействовать с неинтернет-приложением, например при шлюзовании телефонного вызова через Интернет в коммутируемую телефонную сеть общего пользования (PSTN). Число типов сетей должно быть небольшим, и их следует редко расширять. Новый тип сети не может быть зарегистрирован без регистрации по крайней мере одного типа адреса, который будет использоваться с этим типом сети. Регистрация нового типа сети ДОЛЖНА ссылаться на RFC, который даёт сведения о типе сети и типе адреса и определяет, как и когда они будут использоваться.
IANA has registered the network type "IN" to represent the Internet, with definition as in Sections 5.2 and 5.7 of this memo (these definitions update those in RFC 2327).
IANA зарегистрировала тип сети «IN» для представления Интернета с определением, как в разделах 5.2 и 5.7 настоящего меморандума (эти определения обновляют определения в RFC 2327).
8.2.7. Address Types ("addrtype")
8.2.7. Типы адресов («addrtype»)
New address types ("addrtype") may be registered with IANA. An address type is only meaningful in the context of a network type, and any registration of an address type MUST specify a registered network type or be submitted along with a network type registration. A new address type registration MUST reference an RFC giving details of the syntax of the address type. Address types are not expected to be registered frequently.
Новые типы адресов («addrtype») могут быть зарегистрированы в IANA. Тип адреса имеет смысл только в контексте типа сети, и любая регистрация типа адреса ДОЛЖНА указывать зарегистрированный тип сети или представляться вместе с регистрацией типа сети. Регистрация нового типа адреса ДОЛЖНА ссылаться на RFC, дающий сведения о синтаксисе типа адреса. Ожидается, что типы адресов не будут регистрироваться часто.
IANA has registered the address types "IP4" and "IP6" with definitions as in Sections 5.2 and 5.7 of this memo (these definitions update those in RFC 2327).
IANA зарегистрировала типы адресов «IP4» и «IP6» с определениями, как в разделах 5.2 и 5.7 настоящего меморандума (эти определения обновляют определения в RFC 2327).

10. Summary of Changes from RFC 2327
10. Сводка изменений по сравнению с RFC 2327
The memo has been significantly restructured, incorporating a large number of clarifications to the specification in light of use. With the exception of those items noted below, the changes to the memo are intended to be backward-compatible clarifications. However, due to inconsistencies and unclear definitions in RFC 2327 it is likely that some implementations interpreted that memo in ways that differ from this version of SDP.
Меморандум был существенно переструктурирован, включая большое число уточнений спецификации в свете её использования. За исключением отмеченных ниже пунктов, изменения в меморандуме представляют собой обратно совместимые уточнения. Однако из-за несоответствий и неясных определений в RFC 2327 вероятно, что некоторые реализации толковали тот меморандум иначе, чем эта версия SDP.
The ABNF grammar in Section 9 has been extensively revised and updated, correcting a number of mistakes and incorporating the RFC 3266 IPv6 extensions. Known inconsistencies between the grammar and the specification text have been resolved.
Грамматика ABNF в разделе 9 была существенно переработана и обновлена: исправлен ряд ошибок и включены расширения IPv6 из RFC 3266. Известные несоответствия между грамматикой и текстом спецификации устранены.
A media type registration for SDP is included. Requirements for the registration of attributes and other parameters with IANA have been clarified and tightened (Section 8). It is noted that "text" and "message" are valid media types for use with SDP, but that "control" and "data" are under-specified and deprecated.
Включена регистрация типа медиа для SDP. Требования к регистрации атрибутов и других параметров в IANA уточнены и ужесточены (раздел 8). Отмечено, что «text» и «message» являются допустимыми типами медиа для использования с SDP, а «control» и «data» недостаточно специфицированы и устарели.
RFC 2119 terms are now used throughout to specify requirements levels. Certain of those requirements, in particular in relation to parameter registration, are stricter than those in RFC 2327.
Термины RFC 2119 теперь используются повсеместно для указания уровней требований. Некоторые из этих требований, в частности касающиеся регистрации параметров, строже, чем в RFC 2327.
The "RTP/SAVP" RTP profile and its "fmt" namespace are registered.
Регистрируются профиль RTP «RTP/SAVP» и его пространство имён «fmt».
The attributes "a=inactive" and "a=maxptime" have been added.
Добавлены новые атрибуты «a=inactive» и «a=maxptime».
RFC 2327 mandated that either "e=" or "p=" was required. Both are now optional, to reflect actual usage.
RFC 2327 предписывал обязательное наличие либо «e=», либо «p=». Теперь оба необязательны, что отражает фактическое использование.
The significant limitations of the "k=" field are noted, and its use is deprecated.
Отмечены существенные ограничения поля «k=», и его использование признано устаревшим.
Most uses of the "x-" prefix notation for experimental parameters are disallowed and the other uses are deprecated.
Большинство случаев использования префиксной нотации «x-» для экспериментальных параметров запрещено, а остальные случаи признаны устаревшими.
