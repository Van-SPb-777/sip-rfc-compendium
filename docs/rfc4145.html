Abstract
Аннотация
This document describes how to express media transport over TCP using the Session Description Protocol (SDP). It defines the SDP 'TCP' protocol identifier, the SDP 'setup' attribute, which describes the connection setup procedure, and the SDP 'connection' attribute, which handles connection reestablishment.
В настоящем документе описывается, как выразить передачу медиа по TCP с помощью протокола описания сессий (SDP). В нём определяются идентификатор протокола SDP «TCP», атрибут SDP «setup», который описывает процедуру установления соединения, и атрибут SDP «connection», который обрабатывает повторное установление соединения.
1. Introduction
1. Введение
The Session Description Protocol [4] provides a general-purpose format for describing multimedia sessions in announcements or invitations. SDP uses an entirely textual data format (the US-ASCII subset of UTF-8 [11]) to maximize portability among transports. SDP does not define a protocol; it defines the syntax to describe a multimedia session with sufficient information to participate in that session. Session descriptions may be sent using arbitrary existing application protocols for transport (e.g., SAP [9], SIP [10], RTSP [6], email, HTTP [8], etc.).
Протокол описания сессий [4] предоставляет универсальный формат для описания мультимедийных сессий в анонсах или приглашениях. SDP использует полностью текстовый формат данных (подмножество US-ASCII из UTF-8 [11]), чтобы максимально повысить переносимость между транспортами. SDP не определяет протокол; он определяет синтаксис для описания мультимедийной сессии с достаточной информацией для участия в этой сессии. Описания сессий могут пересылаться с использованием произвольных существующих прикладных протоколов транспорта (например, SAP [9], SIP [10], RTSP [6], электронная почта, HTTP [8] и т. д.).
SDP [4] defines two protocol identifiers: RTP/AVP and UDP, both of which represent unreliable, connectionless protocols. While these transports are appropriate choices for multimedia streams, there are applications for which TCP is more appropriate. This document defines a new protocol identifier, 'TCP', to describe TCP connections in SDP.
SDP [4] определяет два идентификатора протокола: RTP/AVP и UDP, оба из которых представляют ненадёжные протоколы без установления соединения. Хотя эти транспорты являются подходящим выбором для мультимедийных потоков, существуют приложения, для которых TCP более уместен. Настоящий документ определяет новый идентификатор протокола «TCP» для описания TCP-соединений в SDP.
TCP introduces two new factors when describing a session: how and when should endpoints perform the TCP connection setup procedure. This document defines two new attributes to describe TCP connection setups: 'setup' and 'connection'.
TCP вносит два новых фактора при описании сессии: как и когда конечные точки должны выполнять процедуру установления TCP-соединения. Настоящий документ определяет два новых атрибута для описания установления TCP-соединений: «setup» и «connection».

3. Идентификатор протокола
The following is the ABNF for an 'm' line, as specified by RFC 2327 [4].
Ниже приведена ABNF для строки «m», как определено в RFC 2327 [4].
media-field = "m=" media space port ["/" integer]

This document defines a new value for the proto field: 'TCP'.
Настоящий документ определяет новое значение для поля proto: «TCP».
The 'TCP' protocol identifier is similar to the 'UDP' protocol identifier in that it only describes the transport protocol, and not the upper-layer protocol. An 'm' line that specifies 'TCP' MUST further qualify the application-layer protocol using an fmt identifier. Media described using an 'm' line containing the 'TCP' protocol identifier are carried using TCP [1].
Идентификатор протокола «TCP» подобен идентификатору протокола «UDP» тем, что он описывает только транспортный протокол, а не протокол верхнего уровня. Строка «m», задающая «TCP», ДОЛЖНА дополнительно определять протокол прикладного уровня с помощью идентификатора fmt. Медиа, описываемые с помощью строки «m», содержащей идентификатор протокола «TCP», передаются с использованием TCP [1].
4. Setup Attribute
4. Атрибут setup
The 'setup' attribute indicates which of the end points should initiate the TCP connection establishment (i.e., send the initial TCP SYN). The 'setup' attribute is charset-independent and can be a session-level or a media-level attribute. The following is the ABNF of the 'setup' attribute:
Атрибут «setup» указывает, какая из конечных точек должна инициировать установление TCP-соединения (т. е. отправить начальный TCP SYN). Атрибут «setup» не зависит от набора символов и может быть атрибутом уровня сессии или уровня медиа. Ниже приведена ABNF атрибута «setup»:
setup-attr = "a=setup:" role role = "active" / "passive" / "actpass" / "holdconn" 'active': The endpoint will initiate an outgoing connection. 'passive': The endpoint will accept an incoming connection. 'actpass': The endpoint is willing to accept an incoming connection or to initiate an outgoing connection. 'holdconn': The endpoint does not want the connection to be established for the time being.
setup-attr = "a=setup:" role role = "active" / "passive" / "actpass" / "holdconn" 'active': The endpoint will initiate an outgoing connection. 'passive': The endpoint will accept an incoming connection. 'actpass': The endpoint is willing to accept an incoming connection or to initiate an outgoing connection. 'holdconn': The endpoint does not want the connection to be established for the time being.
4.1. The Setup Attribute in the Offer/Answer Model
4.1. Атрибут setup в модели «предложение/ответ»
The offer/answer model, defined in RFC 3264 [5], provides endpoints with a means to obtain shared view of a session. Some session parameters are negotiated (e.g., codecs to use), while others are simply communicated from one endpoint to the other (e.g., IP addresses). The value of the 'setup' attribute falls into the first category. That is, both endpoints negotiate its value using the offer/answer model.
Модель «предложение/ответ», определённая в RFC 3264 [5], даёт конечным точкам средство для получения общего представления о сессии. Некоторые параметры сессии согласуются (например, используемые кодеки), тогда как другие просто передаются от одной конечной точки другой (например, IP-адреса). Значение атрибута «setup» относится к первой категории. То есть обе конечные точки согласуют его значение с помощью модели «предложение/ответ».
The negotiation of the value of the 'setup' attribute takes places as follows. The offerer states which role or roles it is willing to perform; and the answerer, taking the offerer's willingness into consideration, chooses which roles both endpoints will actually perform during connection establishment. The following are the values that the 'setup' attribute can take in an offer/answer exchange:
Согласование значения атрибута «setup» происходит следующим образом. Предлагающий указывает, какую роль или роли он готов выполнять; а отвечающий, принимая во внимание готовность предлагающего, выбирает, какие роли обе конечные точки будут фактически выполнять при установлении соединения. Ниже приведены значения, которые атрибут «setup» может принимать при обмене предложением и ответом:
Offer Answer ________________ active passive / holdconn passive active / holdconn actpass active / passive / holdconn holdconn holdconn
Offer Answer ________________ active passive / holdconn passive active / holdconn actpass active / passive / holdconn holdconn holdconn
The active endpoint SHOULD initiate a connection to the port number on the 'm' line of the other endpoint. The port number on its own 'm' line is irrelevant, and the opposite endpoint MUST NOT attempt to initiate a connection to the port number specified there. Nevertheless, since the 'm' line must contain a valid port number, the endpoint using the value 'active' SHOULD specify a port number of 9 (the discard port) on its 'm' line. The endpoint MUST NOT specify a port number of zero, except to denote an 'm' line that has been or is being refused.
Активная конечная точка ДОЛЖНА инициировать соединение к номеру порта в строке «m» другой конечной точки. Номер порта в её собственной строке «m» не имеет значения, и противоположная конечная точка НЕ ДОЛЖНА пытаться инициировать соединение к указанному там номеру порта. Тем не менее, поскольку строка «m» должна содержать допустимый номер порта, конечная точка, использующая значение «active», ДОЛЖНА указать в своей строке «m» номер порта 9 (порт discard). Конечная точка НЕ ДОЛЖНА указывать номер порта ноль, за исключением обозначения строки «m», которая была или отклоняется.
The passive endpoint SHOULD be ready to accept a connection on the port number specified in the 'm' line.
Пассивная конечная точка ДОЛЖНА быть готова принять соединение на номер порта, указанный в строке «m».
A value of 'actpass' indicates that the offerer can either initiate a connection to the port number on the 'm' line in the answer, or accept a connection on the port number specified in the 'm' line in the offer. That is, the offerer has no preference as to whether it accepts or initiates the connection and, so, is letting the answerer choose.
Значение «actpass» указывает, что предлагающий может либо инициировать соединение к номеру порта в строке «m» ответа, либо принять соединение на номер порта, указанный в строке «m» предложения. То есть предлагающий не имеет предпочтений относительно того, принимает он соединение или инициирует его, и поэтому предоставляет выбор отвечающему.
A value of 'holdconn' indicates that the connection should not be established for the time being.
Значение «holdconn» указывает, что соединение не должно устанавливаться в настоящее время.
The default value of the setup attribute in an offer/answer exchange is 'active' in the offer and 'passive' in the answer.
Значение атрибута setup по умолчанию при обмене предложением и ответом — «active» в предложении и «passive» в ответе.
5. The Connection Attribute
5. Атрибут connection
The preceding description of the 'setup' attribute is placed in the context of using SDP to initiate a session. Still, SDP may be exchanged between endpoints at various stages of a session to accomplish tasks such as terminating a session, redirecting media to a new endpoint, or renegotiating the media parameters for a session. After the initial session has been established, it may be ambiguous whether a subsequent SDP exchange represents a confirmation that the endpoint is to continue using the current TCP connection unchanged, or is a request to make a new TCP connection. The media-level 'connection' attribute, which is charset-independent, is used to disambiguate these two scenarios. The following is the ABNF of the connection attribute:
Предшествующее описание атрибута «setup» приведено в контексте использования SDP для инициирования сессии. Тем не менее SDP может обмениваться между конечными точками на различных стадиях сессии для выполнения таких задач, как завершение сессии, перенаправление медиа на новую конечную точку или повторное согласование параметров медиа для сессии. После того как начальная сессия установлена, может быть неоднозначно, представляет ли последующий обмен SDP подтверждение того, что конечная точка должна продолжать использовать текущее TCP-соединение без изменений, или это запрос на установление нового TCP-соединения. Атрибут «connection» уровня медиа, который не зависит от набора символов, используется для устранения неоднозначности между этими двумя сценариями. Ниже приведена ABNF атрибута connection:
connection-attr = "a=connection:" conn-value conn-value = "new" / "existing"
connection-attr = "a=connection:" conn-value conn-value = "new" / "existing"
5.1. Offerer Behaviour
5.1. Поведение предлагающего
Offerers and answerers use the 'connection' attribute to decide whether a new transport connection needs to be established or, on the other hand, the existing TCP connection should still be used. When an offerer generates an 'm' line that uses TCP, it SHOULD provide a connection attribute for the 'm' line unless the application using the 'm' line has other means to deal with connection reestablishment.
Предлагающие и отвечающие используют атрибут «connection», чтобы решить, нужно ли устанавливать новое транспортное соединение или, напротив, следует по-прежнему использовать существующее TCP-соединение. Когда предлагающий формирует строку «m», использующую TCP, он ДОЛЖЕН предоставить атрибут connection для строки «m», если только приложение, использующее строку «m», не имеет иных средств для работы с повторным установлением соединения.
After the initial offer/answer exchange, any of the endpoints can generate a new offer to change some characteristics of the session (e.g., the direction attribute). If such an offerer wants to continue using the previously-established transport-layer connection for the 'm' line, the offerer MUST use a connection value of 'existing' for the 'm' line. If, on the other hand, the offerer wants to establish a new transport-layer connection for the 'm' line, it MUST use a connection value of 'new'.
После начального обмена предложением и ответом любая из конечных точек может сформировать новое предложение, чтобы изменить некоторые характеристики сессии (например, атрибут направления). Если такой предлагающий хочет продолжать использовать ранее установленное соединение транспортного уровня для строки «m», он ДОЛЖЕН использовать значение connection «existing» для строки «m». Если же, напротив, предлагающий хочет установить новое соединение транспортного уровня для строки «m», он ДОЛЖЕН использовать значение connection «new».
Note that, according to the rules in this section, an offer that changes the transport address (IP address or port number) of an 'm' line will have a connection value of 'new'. Similarly, the 'connection' attribute in an initial offer (i.e., no transport connection has been established yet) takes the value of 'new'.
Заметим, что согласно правилам настоящего раздела предложение, которое изменяет транспортный адрес (IP-адрес или номер порта) строки «m», будет иметь значение connection «new». Аналогично атрибут «connection» в начальном предложении (т. е. когда транспортное соединение ещё не установлено) принимает значение «new».
The 'connection' value resulting from an offer/answer exchange is the 'connection' value in the answer. If the 'connection' value in the answer is 'new', the end-points SHOULD establish a new connection. If the connection value in the answer is 'existing', the end-points SHOULD continue using the exiting connection.
Значение «connection», полученное в результате обмена предложением и ответом, — это значение «connection» в ответе. Если значение «connection» в ответе равно «new», конечные точки ДОЛЖНЫ установить новое соединение. Если значение connection в ответе равно «existing», конечные точки ДОЛЖНЫ продолжать использовать существующее соединение.
Taking into consideration the rules in Section 5.2, the following are the values that the 'connection' attribute can take in an offer/answer exchange:
С учётом правил раздела 5.2 ниже приведены значения, которые атрибут «connection» может принимать при обмене предложением и ответом:
Offer Answer ________________ new new existing existing / new
Offer Answer ________________ new new existing existing / new
If the connection value resulting from an offer/answer exchange is 'existing', the end-points continue using the existing connection. Consequently, the port numbers, IP addresses, and 'setup' attributes negotiated in the offer/answer exchange are ignored because there is no need to establish a new connection. The previous rule implies that an offerer generating an offer with a connection value of 'existing' and a setup value of 'passive' needs to be ready (i.e., needs to allocate resources) to receive a connection request from the answerer just in case the answerer chooses a connection value of 'new' for the answer. However, if the answerer uses a connection value of 'existing' in the answer, the offerer would need to deallocate the previously allocated resources that were never used because no connection request was received.
Если значение connection, полученное в результате обмена предложением и ответом, равно «existing», конечные точки продолжают использовать существующее соединение. Следовательно, номера портов, IP-адреса и атрибуты «setup», согласованные при обмене предложением и ответом, игнорируются, поскольку нет необходимости устанавливать новое соединение. Предыдущее правило означает, что предлагающий, формирующий предложение со значением connection «existing» и значением setup «passive», должен быть готов (т. е. должен выделить ресурсы) принять запрос на соединение от отвечающего на случай, если отвечающий выберет для ответа значение connection «new». Однако если отвечающий использует в ответе значение connection «existing», предлагающему потребуется освободить ранее выделенные ресурсы, которые так и не были использованы, поскольку запрос на соединение не поступил.
To avoid allocating resources unnecessarily, offerers using a connection value of 'existing' in their offers may choose to use a setup value of 'holdconn'. Nevertheless, offerers using this strategy should be aware that if the answerer chooses a connection value of 'new', a new offer/answer exchange (typically initiated by the previous offerer) with setup value different than 'holdconn' will be needed to establish the new connection. This may, of course, cause delays in the application using the TCP connection.
Чтобы избежать излишнего выделения ресурсов, предлагающие, использующие в своих предложениях значение connection «existing», могут выбрать значение setup «holdconn». Тем не менее предлагающие, применяющие эту стратегию, должны учитывать, что если отвечающий выберет значение connection «new», то для установления нового соединения потребуется новый обмен предложением и ответом (обычно инициируемый предыдущим предлагающим) со значением setup, отличным от «holdconn». Это, разумеется, может вызвать задержки в приложении, использующем TCP-соединение.
The default value of the connection attribute in both offers and answers is 'new'.
Значение атрибута connection по умолчанию как в предложениях, так и в ответах — «new».
5.2. Answerer Behaviour
5.2. Поведение отвечающего
The connection value for an 'm' line is negotiated using the offer/ answer model. The resulting connection value after an offer/answer exchange is the connection value in the answer. If the connection value in the offer is 'new', the answerer MUST also use a value of 'new' in the answer. If the connection value in the offer is 'existing', the answerer uses a value of 'existing' in the answer if it wishes to continue using the existing connection and a value of 'new' if it wants a new connection to be established.
Значение connection для строки «m» согласуется с помощью модели «предложение/ответ». Результирующее значение connection после обмена предложением и ответом — это значение connection в ответе. Если значение connection в предложении равно «new», отвечающий ДОЛЖЕН также использовать в ответе значение «new». Если значение connection в предложении равно «existing», отвечающий использует в ответе значение «existing», если он желает продолжать использовать существующее соединение, и значение «new», если он хочет, чтобы было установлено новое соединение.
In some scenarios where third party call control [12] is used, an endpoint may receive an initial offer with a connection value of 'existing'. Following the previous rules, such an answerer would use a connection value of 'new' in the answer.
В некоторых сценариях, где используется управление вызовом третьей стороны [12], конечная точка может получить начальное предложение со значением connection «existing». Следуя предыдущим правилам, такой отвечающий использовал бы в ответе значение connection «new».
If the connection value for an 'm' line resulting from an offer/ answer exchange is 'new', the endpoints SHOULD establish a new TCP connection as indicated by the 'setup' attribute. If a previous TCP connection is still up, the endpoints SHOULD close it as soon as the offer/answer exchange is completed. It is up to the application to ensure proper data synchronization between the two TCP connections.
Если значение connection для строки «m», полученное в результате обмена предложением и ответом, равно «new», конечные точки ДОЛЖНЫ установить новое TCP-соединение, как указано атрибутом «setup». Если предыдущее TCP-соединение всё ещё работает, конечные точки ДОЛЖНЫ закрыть его, как только обмен предложением и ответом завершён. Приложение должно обеспечить надлежащую синхронизацию данных между двумя TCP-соединениями.
If the connection value for an 'm' line resulting from an offer/ answer exchange is 'existing', the endpoints SHOULD continue using the existing TCP connection.
Если значение connection для строки «m», полученное в результате обмена предложением и ответом, равно «existing», конечные точки ДОЛЖНЫ продолжать использовать существующее TCP-соединение.
6. Connection Management
6. Управление соединениями
This section addresses connection establishment, connection reestablishment, and connection termination.
В настоящем разделе рассматриваются установление соединения, повторное установление соединения и завершение соединения.
6.1. Connection Establishment
6.1. Установление соединения
An endpoint that according to an offer/answer exchange is supposed to initiate a new TCP connection SHOULD initiate it as soon as it is able to, even if the endpoint does not intend to immediately begin sending media to the remote endpoint. This allows media to flow from the remote endpoint if needed.
Конечная точка, которая согласно обмену предложением и ответом должна инициировать новое TCP-соединение, ДОЛЖНА инициировать его, как только будет в состоянии это сделать, даже если конечная точка не намерена немедленно начать отправку медиа удалённой конечной точке. Это позволяет медиа поступать от удалённой конечной точки при необходимости.
Note that some endpoints need to wait for some event to happen before being able to establish the connection. For example, a wireless terminal may need to set up a radio bearer before being able to initiate a TCP connection.
Заметим, что некоторым конечным точкам нужно дождаться некоторого события, прежде чем они смогут установить соединение. Например, беспроводному терминалу может потребоваться настроить радиоканал, прежде чем он сможет инициировать TCP-соединение.
6.2. Connection Reestablishment
6.2. Повторное установление соединения
If an endpoint determines that the TCP for an 'm' line has been closed and should be reestablished, it SHOULD perform a new offer/ answer exchange using a connection value of 'new' for this 'm' line.
Если конечная точка определяет, что TCP для строки «m» был закрыт и должен быть повторно установлен, она ДОЛЖНА выполнить новый обмен предложением и ответом, используя значение connection «new» для этой строки «m».
Note that the SDP direction attribute (e.g., 'a=sendonly') deals with the media sent over the TCP connection, but has no impact on the TCP connection itself.
Заметим, что атрибут направления SDP (например, «a=sendonly») относится к медиа, отправляемым по TCP-соединению, но не влияет на само TCP-соединение.
6.3. Connection Termination
6.3. Завершение соединения
Typically, endpoints do not close the TCP connection until the session has expired, been explicitly terminated, or a new connection value has been provided for the 'm' line. Additionally, specific applications can describe further scenarios where an end-point may close a given TCP connection (e.g., whenever a connection is in the half-close state). As soon as an end-point notices that it needs to terminate a TCP connection, it SHOULD do so.
Как правило, конечные точки не закрывают TCP-соединение до тех пор, пока сессия не истечёт, не будет явно завершена или для строки «m» не будет предоставлено новое значение connection. Кроме того, конкретные приложения могут описывать дополнительные сценарии, в которых конечная точка может закрыть данное TCP-соединение (например, всякий раз, когда соединение находится в состоянии половинного закрытия). Как только конечная точка замечает, что ей нужно завершить TCP-соединение, она ДОЛЖНА это сделать.
In any case, individual applications may provide further considerations on how to achieve a graceful connection termination. For example, a file application using TCP to receive a FIN from the remote endpoint may need to finish the ongoing transmission of a file before sending its own FIN.
В любом случае отдельные приложения могут давать дополнительные соображения о том, как достичь корректного завершения соединения. Например, файловому приложению, использующему TCP для получения FIN от удалённой конечной точки, может потребоваться завершить текущую передачу файла, прежде чем отправлять свой собственный FIN.
7. Examples
7. Примеры
The following examples show the most common usage of the 'setup' attribute combined with TCP-based media descriptions. For the purpose of brevity, the main portion of the session description is omitted in the examples, which only show 'm' lines and their attributes (including 'c' lines).
В следующих примерах показано наиболее распространённое использование атрибута «setup» в сочетании с описаниями медиа на основе TCP. Для краткости основная часть описания сессии в примерах опущена; показаны только строки «m» и их атрибуты (включая строки «c»).
7.1. Passive/Active
7.1. Passive/Active
An offerer at 192.0.2.2 signals its availability for a T.38 fax session at port 54111:
Предлагающий на 192.0.2.2 объявляет о своей готовности к сеансу факса T.38 на порту 54111:
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:passive a=connection:new
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:passive a=connection:new
An answerer at 192.0.2.1 receiving this offer responds with the following answer:
Отвечающий на 192.0.2.1, получив это предложение, отвечает следующим ответом:
m=image 9 TCP t38 c=IN IP4 192.0.2.1 a=setup:active a=connection:new
m=image 9 TCP t38 c=IN IP4 192.0.2.1 a=setup:active a=connection:new
The endpoint at 192.0.2.1 then initiates the TCP connection to port 54111 at 192.0.2.2.
Затем конечная точка на 192.0.2.1 инициирует TCP-соединение к порту 54111 на 192.0.2.2.
7.2. Actpass/Passive
7.2. Actpass/Passive
In another example, an offerer at 192.0.2.2 signals its availability for a T.38 fax session at TCP port 54111. Additionally, this offerer is also willing to set up the media stream by initiating the TCP connection:
В другом примере предлагающий на 192.0.2.2 объявляет о своей готовности к сеансу факса T.38 на TCP-порту 54111. Кроме того, этот предлагающий также готов настроить медиапоток, инициировав TCP-соединение:
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:actpass a=connection:new
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:actpass a=connection:new
The endpoint at 192.0.2.1 responds with the following description:
Конечная точка на 192.0.2.1 отвечает следующим описанием:
m=image 54321 TCP t38 c=IN IP4 192.0.2.1 a=setup:passive a=connection:new
m=image 54321 TCP t38 c=IN IP4 192.0.2.1 a=setup:passive a=connection:new
This will cause the offerer (at 192.0.2.2) to initiate a connection to port 54321 at 192.0.2.1.
Это заставит предлагающего (на 192.0.2.2) инициировать соединение к порту 54321 на 192.0.2.1.
7.3. Existing Connection Reuse
7.3. Повторное использование существующего соединения
Subsequent to the exchange in Section 7.2, another offer/answer exchange is initiated in the opposite direction. The endpoint at 192.0.2.1 wishes to continue using the existing connection:
После обмена из раздела 7.2 в противоположном направлении инициируется ещё один обмен предложением и ответом. Конечная точка на 192.0.2.1 желает продолжать использовать существующее соединение:
m=image 54321 TCP t38 c=IN IP4 192.0.2.1 a=setup:passive a=connection:existing
m=image 54321 TCP t38 c=IN IP4 192.0.2.1 a=setup:passive a=connection:existing
The endpoint at 192.0.2.2 also wishes to use the existing connection and responds with the following description:
Конечная точка на 192.0.2.2 также желает использовать существующее соединение и отвечает следующим описанием:
m=image 9 TCP t38 c=IN IP4 192.0.2.2 a=setup:active a=connection:existing
m=image 9 TCP t38 c=IN IP4 192.0.2.2 a=setup:active a=connection:existing
The existing connection from 192.0.2.2 to 192.0.2.1 will be reused.
Существующее соединение от 192.0.2.2 к 192.0.2.1 будет использовано повторно.
Note that the endpoint at 192.0.2.2 uses 'setup:active' in response to the offer of 'setup:passive', and uses port 9 because it is active.
Заметим, что конечная точка на 192.0.2.2 использует «setup:active» в ответ на предложение «setup:passive» и использует порт 9, поскольку она активна.
7.4. Existing Connection Refusal
7.4. Отказ от существующего соединения
Subsequent to the exchange in Section 7.3, another offer/answer exchange is initiated by the endpoint at 192.0.2.2, again wishing to reuse the existing connection:
После обмена из раздела 7.3 конечная точка на 192.0.2.2 инициирует ещё один обмен предложением и ответом, снова желая повторно использовать существующее соединение:
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:passive a=connection:existing
m=image 54111 TCP t38 c=IN IP4 192.0.2.2 a=setup:passive a=connection:existing
However, this time the answerer is unaware of the old connection and thus wishes to establish a new one. (This could be the result of a transfer via third-party call control.) It is unable to act in the 'passive' mode and thus responds as 'active':
Однако на этот раз отвечающий не знает о старом соединении и поэтому желает установить новое. (Это может быть результатом перевода вызова посредством управления вызовом третьей стороны.) Он не может действовать в режиме «passive» и поэтому отвечает как «active»:
m=image 9 TCP t38 c=IN IP4 192.0.2.3 a=setup:active a=connection:new
m=image 9 TCP t38 c=IN IP4 192.0.2.3 a=setup:active a=connection:new
The endpoint at 192.0.2.3 then initiates the TCP connection to port 54111 at 192.0.2.2, and the endpoint at 192.0.2.2 closes the old connection.
Затем конечная точка на 192.0.2.3 инициирует TCP-соединение к порту 54111 на 192.0.2.2, и конечная точка на 192.0.2.2 закрывает старое соединение.
Note that the endpoint at 192.0.2.2, while using a connection value of 'existing', has used a setup value of 'passive'. Had it not done this and instead used a setup value of 'holdconn' (probably to avoid allocating resources as described in Section 5.1), a new offer/answer exchange would have been needed in order to establish the new connection.
Заметим, что конечная точка на 192.0.2.2, хотя и использует значение connection «existing», применила значение setup «passive». Если бы она этого не сделала и вместо этого использовала значение setup «holdconn» (вероятно, чтобы избежать выделения ресурсов, как описано в разделе 5.1), потребовался бы новый обмен предложением и ответом для установления нового соединения.
8. Other Connection-Oriented Transport Protocols
8. Другие протоколы транспорта, ориентированные на соединение
This document specifies how to describe TCP-based media streams using SDP. Still, some of the attributes defined here could possibly be used to describe media streams based on other connection-oriented transport protocols as well. This section provides advice to authors of specifications of SDP extensions that deal with connection- oriented transport protocols other than TCP.
Настоящий документ определяет, как описывать медиапотоки на основе TCP с помощью SDP. Тем не менее некоторые из определённых здесь атрибутов, возможно, можно использовать и для описания медиапотоков на основе других протоколов транспорта с установлением соединения. В настоящем разделе даются рекомендации авторам спецификаций расширений SDP, которые имеют дело с протоколами транспорта с установлением соединения, отличными от TCP.
It is recommended that documents defining new SDP protocol identifiers that involve extra protocol layers between TCP and the media itself (e.g., TLS [7] over TCP) start with the string 'TCP/' (e.g., 'TCP/TLS').
Рекомендуется, чтобы документы, определяющие новые идентификаторы протокола SDP, которые включают дополнительные протокольные уровни между TCP и собственно медиа (например, TLS [7] поверх TCP), начинались со строки «TCP/» (например, «TCP/TLS»).
The 'setup' and the 'connection' attributes are specified in Section 4 and Section 5 respectively. While both attributes are applicable to 'm' lines that use the 'TCP' protocol identifier, they are general enough to be reused in 'm' lines with other connection- oriented transport protocols. Therefore, it is recommended that the 'setup' and 'connection' attributes are reused, as long as it is possible, for new proto values associated with connection-oriented transport protocols.
Атрибуты «setup» и «connection» определены в разделе 4 и разделе 5 соответственно. Хотя оба атрибута применимы к строкам «m», использующим идентификатор протокола «TCP», они достаточно общи, чтобы их можно было повторно использовать в строках «m» с другими протоколами транспорта с установлением соединения. Поэтому рекомендуется повторно использовать атрибуты «setup» и «connection», насколько это возможно, для новых значений proto, связанных с протоколами транспорта с установлением соединения.
Section 6 deals with TCP connection management. It should be noted that while in TCP both end-points need to close a connection, other connection-oriented transport protocols may not have the concept of half-close connections. In such a case, a connection would be terminated as soon as one of the end-points closed it, making it unnecessary for the other end-point to perform any further action to terminate the connection. So, specifications dealing with such transport protocols may need to specify slightly different procedures regarding connection termination.
Раздел 6 посвящён управлению TCP-соединениями. Следует отметить, что если в TCP обеим конечным точкам нужно закрыть соединение, то другие протоколы транспорта с установлением соединения могут не иметь понятия соединений с половинным закрытием. В таком случае соединение будет завершено, как только одна из конечных точек закроет его, что избавляет другую конечную точку от необходимости выполнять какие-либо дальнейшие действия для завершения соединения. Таким образом, спецификациям, имеющим дело с такими протоколами транспорта, может потребоваться определить несколько иные процедуры в отношении завершения соединения.
9. Security Considerations
9. Вопросы безопасности
See RFC 2327 [4] for security and other considerations specific to the Session Description Protocol in general.
Вопросы безопасности и другие соображения, специфичные для протокола описания сессий в целом, см. в RFC 2327 [4].
An attacker may attempt to modify the values of the connection and setup attributes in order to have endpoints reestablish connections unnecessarily or to keep them from establishing a connection. So, it is strongly RECOMMENDED that integrity protection be applied to the SDP session descriptions. For session descriptions carried in SIP [10], S/MIME is the natural choice to provide such end-to-end integrity protection, as described in RFC 3261 [10]. Other applications MAY use a different form of integrity protection.
Злоумышленник может попытаться изменить значения атрибутов connection и setup, чтобы заставить конечные точки без необходимости повторно устанавливать соединения или помешать им установить соединение. Поэтому настоятельно РЕКОМЕНДУЕТСЯ применять защиту целостности к описаниям сессий SDP. Для описаний сессий, передаваемых в SIP [10], S/MIME является естественным выбором для обеспечения такой сквозной защиты целостности, как описано в RFC 3261 [10]. Другие приложения МОГУТ использовать иную форму защиты целостности.
10. IANA Considerations
10. Вопросы IANA
This document defines two session- and media-level SDP attributes: setup and connection. Their formats are defined in Section 4 and Section 5, respectively. These two attributes should be registered by the IANA under "Session Description Protocol (SDP) Parameters" under "att-field (both session and media level)".
Настоящий документ определяет два атрибута SDP уровня сессии и уровня медиа: setup и connection. Их форматы определены в разделе 4 и разделе 5 соответственно. Эти два атрибута должны быть зарегистрированы IANA в разделе «Session Description Protocol (SDP) Parameters» в подразделе «att-field (both session and media level)».
This document defines a proto value: TCP. Its format is defined in Section 3. This proto value should be registered by the IANA under "Session Description Protocol (SDP) Parameters" under "proto".
Настоящий документ определяет значение proto: TCP. Его формат определён в разделе 3. Это значение proto должно быть зарегистрировано IANA в разделе «Session Description Protocol (SDP) Parameters» в подразделе «proto».
The SDP specification, RFC2327, states that specifications defining new proto values, like the TCP proto value defined in this RFC, must define the rules by which their media format (fmt) namespace is managed. For the TCP protocol, new formats SHOULD have an associated MIME registration. Use of an existing MIME subtype for the format is encouraged. If no MIME subtype exists, it is RECOMMENDED that a suitable one is registered through the IETF process [2] by production of, or reference to, a standards-track RFC that defines the transport protocol for the format.
Спецификация SDP, RFC 2327, утверждает, что спецификации, определяющие новые значения proto, такие как значение TCP, определённое в настоящем RFC, должны определять правила, по которым управляется пространство имён их форматов медиа (fmt). Для протокола TCP новые форматы ДОЛЖНЫ иметь связанную регистрацию MIME. Поощряется использование существующего подтипа MIME для формата. Если подтип MIME не существует, РЕКОМЕНДУЕТСЯ зарегистрировать подходящий подтип через процесс IETF [2] путём создания или указания RFC уровня Standards Track, который определяет протокол транспорта для формата.
