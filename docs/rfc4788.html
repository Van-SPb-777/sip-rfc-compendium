Abstract
Аннотация
This document updates the Enhanced Variable Rate Codec (EVRC) RTP payload formats defined in RFC 3558 with several enhancements and extensions. In particular, it defines support for the header-free and interleaved/bundled packet formats for the EVRC-B codec, a new compact bundled format for the EVRC and EVRC-B codecs, as well as discontinuous transmission (DTX) support for EVRC and EVRC-B-encoded speech transported via RTP. Voice over IP (VoIP) applications operating over low bandwidth dial-up and wireless networks require such enhancements for efficient use of the bandwidth.
Настоящий документ обновляет форматы полезной нагрузки RTP для кодека с переменной скоростью EVRC (Enhanced Variable Rate Codec), определённые в RFC 3558, рядом усовершенствований и расширений. В частности, он определяет поддержку форматов пакетов без заголовка и с чередованием/объединением для кодека EVRC-B, новый компактный объединённый формат для кодеков EVRC и EVRC-B, а также поддержку прерывистой передачи (DTX) для речи, закодированной EVRC и EVRC-B и передаваемой по RTP. Приложения VoIP, работающие в сетях с низкой пропускной способностью — коммутируемых и беспроводных, — нуждаются в таких усовершенствованиях для эффективного использования полосы пропускания.
1. Introduction
1. Введение
This document defines support for the header-free and interleaved/ bundled packet formats for the EVRC-B codec, a new compact bundled format for the EVRC and EVRC-B codecs, as well as discontinuous transmission (DTX) support for EVRC and EVRC-B-encoded speech transported via RTP. Voice over IP (VoIP) applications operating over low bandwidth dial-up and wireless networks require such EVRC RTP payload capabilities for efficient use of the bandwidth.
Настоящий документ определяет поддержку форматов пакетов без заголовка и с чередованием/объединением для кодека EVRC-B, новый компактный объединённый формат для кодеков EVRC и EVRC-B, а также поддержку прерывистой передачи (DTX) для речи, закодированной EVRC и EVRC-B и передаваемой по RTP. Приложения VoIP, работающие в коммутируемых и беспроводных сетях с низкой пропускной способностью, нуждаются в таких возможностях полезной нагрузки RTP EVRC для эффективного использования полосы пропускания.
1.1. Support of EVRC-B Codec
1.1. Поддержка кодека EVRC-B
EVRC-B [3] is an extension to EVRC [2] developed in the Third Generation Partnership Project 2 (3GPP2). EVRC-B [3] compresses each 20 milliseconds of 8000Hz, 16-bit sampled speech input into output frames of one of the four different sizes: Rate 1 (171 bits), Rate 1/2 (80 bits), Rate 1/4 (40 bits), or Rate 1/8 (16 bits). In addition, there are two zero-bit codec frame types: null frames and erasure frames, similar to EVRC [2]. One significant enhancement in EVRC-B is the use of 1/4-rate frames that were not used in EVRC. This provides lower average data rates (ADRs) compared to EVRC, for a given voice quality.
EVRC-B [3] — расширение EVRC [2], разработанное в Проекте партнёрства третьего поколения 2 (3GPP2). EVRC-B [3] сжимает каждые 20 миллисекунд входной речи, дискретизированной с частотой 8000 Гц и 16-битным квантованием, в выходные кадры одного из четырёх размеров: Rate 1 (171 бит), Rate 1/2 (80 бит), Rate 1/4 (40 бит) или Rate 1/8 (16 бит). Кроме того, подобно EVRC [2], имеются два типа кадров кодека с нулевым числом бит: пустые кадры и кадры стирания. Одним из существенных усовершенствований в EVRC-B является использование кадров со скоростью 1/4, которые не применялись в EVRC. Это обеспечивает более низкие средние скорости передачи данных (ADR) по сравнению с EVRC при заданном качестве речи.
Since speech frames encoded by EVRC-B are different from those encoded by EVRC, EVRC-B and EVRC codecs do not interoperate with each other. At the initiation of an RTP session, the RTP sender and receiver need to indicate (e.g., using MIME subtypes that are separate from those of EVRC) that EVRC-B is to be used for the ensuing session.
Поскольку кадры речи, закодированные EVRC-B, отличаются от кадров, закодированных EVRC, кодеки EVRC-B и EVRC не взаимодействуют друг с другом. При установлении сеанса RTP отправителю и приёмнику RTP необходимо указать (например, с помощью подтипов MIME, отдельных от подтипов EVRC), что для последующего сеанса должен использоваться EVRC-B.
1.2. Compact (Header-free) Bundled Format
1.2. Компактный (без заголовка) объединённый формат
The current interleaved/bundled packet format defined in RFC 3558 allows bundling of multiple speech frames of different rates in a single RTP packet, sending mode change requests, and interleaving. To support these functions, a Table of Contents (ToC) is used in each RTP packet, in addition to the standard RTP header. The size of the ToC varies depending on the number of EVRC frames carried in the packet [4].
Текущий формат пакетов с чередованием/объединением, определённый в RFC 3558, допускает объединение нескольких кадров речи с разными скоростями в одном пакете RTP, передачу запросов смены режима и чередование. Для поддержки этих функций в каждом пакете RTP помимо стандартного заголовка RTP используется оглавление (ToC). Размер ToC зависит от числа кадров EVRC, переносимых в пакете [4].
The current header-free packet format defined in RFC 3558 is more compact and optimized for use over wireless links. It eliminates the need for a ToC by requiring that each RTP packet contain only one speech frame (of any allowable rate), i.e., bundling is not allowed. Moreover, interleaving and mode change requests are not supported in the header-free format [4]. The compact bundled format described in this document presents the user an alternative to the header-free format defined in RFC 3558. This format allows bundling of multiple EVRC or EVRC-B frames without the addition of extra headers, as would be in the case of the interleaved/bundled format. However, in order to use this compact bundled format, only one EVRC/EVRC-B rate (full rate or 1/2 rate) can be used in the session. Similar to the header-free format defined in RFC 3558, interleaving and mode change requests are not supported in the compact bundled format.
Текущий формат пакетов без заголовка, определённый в RFC 3558, более компактен и оптимизирован для использования по беспроводным каналам. Он устраняет необходимость в ToC, требуя, чтобы каждый пакет RTP содержал только один кадр речи (любой допустимой скорости), то есть объединение не допускается. Кроме того, в формате без заголовка не поддерживаются чередование и запросы смены режима [4]. Описываемый в настоящем документе компактный объединённый формат предлагает пользователю альтернативу формату без заголовка, определённому в RFC 3558. Этот формат допускает объединение нескольких кадров EVRC или EVRC-B без добавления дополнительных заголовков, как это было бы в случае формата с чередованием/объединением. Однако для использования этого компактного объединённого формата в сеансе можно применять только одну скорость EVRC/EVRC-B (полную или 1/2). Подобно формату без заголовка, определённому в RFC 3558, компактный объединённый формат не поддерживает чередование и запросы смены режима.
1.3. Discontinuous Transmission (DTX)
1.3. Прерывистая передача (DTX)
Information carried in frames of EVRC and EVRC-B codecs varies little during periods of silence. The transmission of these frames across the radio interface in a wireless system is expensive, in terms of capacity; therefore, suppression of these frames is desirable. Such an operation is called DTX, also known as silence suppression.
Информация, переносимая в кадрах кодеков EVRC и EVRC-B, мало меняется в периоды молчания. Передача этих кадров через радиоинтерфейс в беспроводной системе обходится дорого с точки зрения ёмкости; поэтому подавление этих кадров желательно. Такая операция называется DTX, она же подавление молчания.
In general, when DTX/silence suppression is applied, the first few frames of silence may be transmitted at the beginning of the period of silence to establish background noise. Then, a portion of the stream of subsequent silence frames is not transmitted, and is discarded at the sender. At the receiver, background or comfort noise may be generated by using the previously received silence frames.
В общем случае при применении DTX/подавления молчания в начале периода молчания могут передаваться первые несколько кадров молчания для создания фонового шума. Затем часть потока последующих кадров молчания не передаётся и отбрасывается на отправителе. На приёмнике фоновый шум или комфортный шум может генерироваться с использованием ранее принятых кадров молчания.
The full detail of DTX/silence suppression operation can be found in DTX [8] as well as in RFC 3551 [9], and in RFC 3558 [4]. This document only defines the additional optional MIME parameters (silencesupp, dtxmax, dtxmin, and hangover) for setting up a DTX/ silence suppression session, where "silencesupp" is for indicating the capability and willingness of using DTX/silence suppression; "dtxmax" and "dtxmin", for indicating the desired range of DTX update interval; and "hangover", for indicating the desired number of silence frames at the beginning of each silence period to establish background noise at the receiver (see Section 6.1 for detailed definition).
Подробное описание работы DTX/подавления молчания можно найти в DTX [8], а также в RFC 3551 [9] и RFC 3558 [4]. Настоящий документ определяет только дополнительные необязательные параметры MIME (silencesupp, dtxmax, dtxmin и hangover) для настройки сеанса с DTX/подавлением молчания, где «silencesupp» служит для указания возможности и готовности использовать DTX/подавление молчания; «dtxmax» и «dtxmin» — для указания желаемого диапазона интервала обновления DTX; а «hangover» — для указания желаемого числа кадров молчания в начале каждого периода молчания для создания фонового шума на приёмнике (подробное определение см. в разделе 6.1).
The EVRC and EVRC-B codecs, in variable-rate operation mode, send 1/8-rate frames during periods of silence, while in single-rate operation mode (see Section 4), silence is encoded and sent in frames of the same rate as that of speech frames. The DTX parameters defined in this document apply to 1/8-rate frames in the variable- rate mode and to silence frames in the single-rate operation mode.
Кодеки EVRC и EVRC-B в режиме работы с переменной скоростью передают в периоды молчания кадры со скоростью 1/8, тогда как в режиме работы с единой скоростью (см. раздел 4) молчание кодируется и передаётся в кадрах той же скорости, что и кадры речи. Определённые в настоящем документе параметры DTX применяются к кадрам со скоростью 1/8 в режиме переменной скорости и к кадрам молчания в режиме единой скорости.
For simplicity, in the rest of this document the term "silence frame" refers either to an 1/8-rate frame in variable-rate operation or a frame that contains only silence in the signal-rate operation.
Для простоты далее в настоящем документе термин «кадр молчания» обозначает либо кадр со скоростью 1/8 при работе с переменной скоростью, либо кадр, содержащий только молчание, при работе с единой скоростью.

3. EVRC-B Codec
3. Кодек EVRC-B
Three RTP packet formats are supported for the EVRC-B codec: the interleaved/bundled packet format, the header-free packet format, and the compact bundled packet format. For the interleaved/bundled and header-free packet formats, the operational details and capabilities, such as ToC, interleaving, and bundling, of EVRC-B, are exactly the same as those of EVRC, as defined in RFC 3558 [4], except that the mode change request field in the ToC MUST be interpreted according to the definition of the RATE_REDUC parameter in EVRC-B [3]. The compact bundled packet format for EVRC-B is defined in Section 4 of this document.
Для кодека EVRC-B поддерживаются три формата пакетов RTP: формат с чередованием/объединением, формат без заголовка и компактный объединённый формат. Для форматов с чередованием/объединением и без заголовка эксплуатационные детали и возможности EVRC-B, такие как ToC, чередование и объединение, в точности совпадают с таковыми для EVRC, определёнными в RFC 3558 [4], за исключением того, что поле запроса смены режима в ToC ДОЛЖНО интерпретироваться согласно определению параметра RATE_REDUC в EVRC-B [3]. Компактный объединённый формат пакетов для EVRC-B определён в разделе 4 настоящего документа.

4.1. Single-Rate Operation
4.1. Работа с единой скоростью
As mentioned earlier, in order to use the compact bundled format, all the EVRC/EVRC-B data frames in the session MUST be of the same rate. This packet format may carry only full or half-rate frames. For a session that uses the compact bundled format, the rate for the session can be determined during the session setup signaling, for example, via Session Description Protocol (SDP) exchanges. See Section 6 below for more details.
Как отмечалось ранее, для использования компактного объединённого формата все кадры данных EVRC/EVRC-B в сеансе ДОЛЖНЫ иметь одну и ту же скорость. Этот формат пакетов может переносить только кадры полной или половинной скорости. Для сеанса, использующего компактный объединённый формат, скорость сеанса может определяться при сигнализации установления сеанса, например посредством обмена сообщениями протокола описания сеанса (SDP). 5. Storage Format for EVRC-B Codec
5. Формат хранения для кодека EVRC-B
The storage format is used for storing EVRC-B-encoded speech frames, e.g., as a file or e-mail attachment.
Формат хранения используется для хранения кадров речи, закодированных EVRC-B, например в виде файла или вложения электронной почты.
The file begins with a magic number to identify the vocoder that is used. The magic number for EVRC-B corresponds to the ASCII character string:
Файл начинается с магического числа, идентифицирующего используемый вокодер. Магическое число для EVRC-B соответствует строке ASCII-символов:
"#!EVRC-B\n" (or 0x2321 0x4556 0x5243 0x2d42 0x0a in hexadecimal).
«#!EVRC-B\n» (или 0x2321 0x4556 0x5243 0x2d42 0x0a в шестнадцатеричном виде).
Note that the "\n" is an important part of both this magic number and the "#!EVRC\n" magic number defined in Section 11 of RFC 3558, and the "\n" MUST be included in any comparison of either magic number, since, otherwise, a prefix of the EVRC-B magic number could be mistaken for the EVRC magic number.
Обратите внимание, что «\n» является важной частью как этого магического числа, так и магического числа «#!EVRC\n», определённого в разделе 11 RFC 3558, и «\n» ДОЛЖЕН включаться в любое сравнение любого из этих магических чисел, поскольку в противном случае префикс магического числа EVRC-B мог бы быть принят за магическое число EVRC.
The codec data frames are stored in consecutive order, with a single ToC entry field, extended to one octet, prefixing each codec data frame. The ToC field, as defined in Section 5.1 of [4], is extended to one octet by setting the four most significant bits of the octet to zero. For example, a ToC value of 4 (a full-rate frame) is stored as 0x04.
Кадры данных кодека хранятся в последовательном порядке, причём перед каждым кадром данных кодека стоит одно поле записи ToC, расширенное до одного октета. Поле ToC, определённое в разделе 5.1 [4], расширяется до одного октета путём установки четырёх старших бит октета в ноль. Например, значение ToC, равное 4 (кадр полной скорости), хранится как 0x04.
Speech frames lost in transmission and non-received frames MUST be stored as erasure frames to maintain synchronization with the original media.
Кадры речи, потерянные при передаче, и непринятые кадры ДОЛЖНЫ храниться как кадры стирания для поддержания синхронизации с исходным медиа.

6.7. Mapping MIME Parameters into SDP
6.7. Отображение параметров MIME в SDP
The information carried in the MIME media type specification has a specific mapping to fields in the Session Description Protocol (SDP) [7], which is commonly used to describe RTP sessions. When SDP is used to specify sessions employing the compact bundled format for EVRC/EVRC-B-encoded speech, the mapping is as follows:
Информация, переносимая в спецификации типа медиа MIME, имеет определённое отображение в поля протокола описания сеанса (SDP) [7], который обычно используется для описания сеансов RTP. Когда SDP применяется для задания сеансов, использующих компактный объединённый формат для речи, закодированной EVRC/EVRC-B, отображение выглядит следующим образом:
o The MIME type ("audio") goes in SDP "m=" as the media name.
o Тип MIME («audio») помещается в SDP «m=» в качестве имени медиа.
o The MIME subtype ("EVRC", "EVRC0", "EVRC1", "EVRCB", EVRCB0", or "EVRCB1") goes in SDP "a=rtpmap" as the encoding name.
o Подтип MIME («EVRC», «EVRC0», «EVRC1», «EVRCB», «EVRCB0» или «EVRCB1») помещается в SDP «a=rtpmap» в качестве имени кодирования.
o The optional parameters "ptime" and "maxptime" (for subtypes EVRC, EVRC1, EVRCB, and EVRCB1) go in the SDP "a=ptime" and "a=maxptime" attributes, respectively.
o Необязательные параметры «ptime» и «maxptime» (для подтипов EVRC, EVRC1, EVRCB и EVRCB1) помещаются в атрибуты SDP «a=ptime» и «a=maxptime» соответственно.
o The optional parameter "maxinterleave" (for subtypes EVRC and EVRCB) goes in the SDP "a=fmtp" attribute by copying it directly from the MIME media type string as "maxinterleave=value".
o Необязательный параметр «maxinterleave» (для подтипов EVRC и EVRCB) помещается в атрибут SDP «a=fmtp» путём прямого копирования из строки типа медиа MIME как «maxinterleave=value».
o The optional parameter "fixedrate" (for subtypes EVRC1 and EVRCB1) goes in the "a=fmtp" attribute by copying it directly from the MIME media type string as "fixedrate=value".
o Необязательный параметр «fixedrate» (для подтипов EVRC1 и EVRCB1) помещается в атрибут «a=fmtp» путём прямого копирования из строки типа медиа MIME как «fixedrate=value».
o The optional parameters "silencesupp", "dtxmax", "dtxmin", and "hangover" go in the "a=fmtp" attribute by copying it directly from the MIME media type string as "silencesupp=value", "dtxmax=value", "dtxmin=value", and "hangover=value", respectively.
o Необязательные параметры «silencesupp», «dtxmax», «dtxmin» и «hangover» помещаются в атрибут «a=fmtp» путём прямого копирования из строки типа медиа MIME как «silencesupp=value», «dtxmax=value», «dtxmin=value» и «hangover=value» соответственно.

6.8. Usage in Offer/Answer
6.8. Использование в предложении/ответе
All SDP parameters in this payload format are declarative, and all reasonable values are expected to be supported. In particular, when DTX is supported, the RTP sender implementation SHOULD support hangover, dtxmin, and dtxmax values from 0 to 255. Thus, the standard usage of Offer/Answer, as described in RFC 3264 [6], SHOULD be followed.
Все параметры SDP в этом формате полезной нагрузки являются декларативными, и ожидается поддержка всех разумных значений. В частности, при поддержке DTX реализации отправителя RTP СЛЕДУЕТ поддерживать значения hangover, dtxmin и dtxmax от 0 до 255. Таким образом, СЛЕДУЕТ соблюдать стандартное использование механизма «предложение/ответ», описанного в RFC 3264 [6].
In addition, the following rules MUST be followed while negotiating DTX parameters:
Кроме того, при согласовании параметров DTX ДОЛЖНЫ соблюдаться следующие правила:
1. If any DTX parameter is not present in either offer and/or answer, the default value of the DTX parameter MUST be assumed.
1. Если какой-либо параметр DTX отсутствует в предложении и/или ответе, ДОЛЖНО предполагаться значение этого параметра DTX по умолчанию.
2. If silencesupp is present and set to 0 in either offer or answer, the values of all received DTX parameters other than silencesupp SHOULD be ignored.
2. Если silencesupp присутствует и установлен в 0 в предложении или ответе, значения всех полученных параметров DTX, кроме silencesupp, СЛЕДУЕТ игнорировать.
3. In an offer or answer, the value of dtxmax SHOULD always be larger than or equal to the value of dtxmin, regardless of whether the values are indicated explicitly or implicitly by default. Moreover, if the indicated value of dtxmin is larger than that of dtxmax, an RTP sender MUST ignore the indicated values and MUST fall back on using the default dtxmin and dtxmax values.
3. В предложении или ответе значение dtxmax СЛЕДУЕТ всегда делать большим или равным значению dtxmin, независимо от того, указаны ли значения явно или неявно по умолчанию. Более того, если указанное значение dtxmin больше значения dtxmax, отправитель RTP ДОЛЖЕН игнорировать указанные значения и ДОЛЖЕН вернуться к использованию значений dtxmin и dtxmax по умолчанию.
7. Backward Compatibility with RFC 3558
7. Обратная совместимость с RFC 3558
This document adds new optional DTX parameters to the original EVRC payload subtypes "EVRC" and "EVRC0" defined in RFC 3558. Since the new DTX parameters are receiver options, we expect that the existing RFC 3558 implementations will not send any of the DTX parameters in their SDP and will ignore any DTX parameters they receive. The adaptive DTX behavior of DTX-capable EVRC codecs (as detailed in [8], Section 4.3.5) ensures the backward interoperability between the DTX- capable EVRC codec and non-DTX EVRC codecs.
Настоящий документ добавляет новые необязательные параметры DTX к исходным подтипам полезной нагрузки EVRC «EVRC» и «EVRC0», определённым в RFC 3558. Поскольку новые параметры DTX являются опциями приёмника, мы ожидаем, что существующие реализации RFC 3558 не будут передавать в своём SDP ни один из параметров DTX и будут игнорировать любые получаемые параметры DTX. Адаптивное поведение DTX в кодеках EVRC, поддерживающих DTX (подробно описано в [8], раздел 4.3.5), обеспечивает обратную совместимость между кодеком EVRC с поддержкой DTX и кодеками EVRC без DTX.
