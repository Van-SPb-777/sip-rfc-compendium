Abstract
Аннотация
This document defines a standard mechanism for capturing the history information associated with a Session Initiation Protocol (SIP) request. This capability enables many enhanced services by providing the information as to how and why a call arrives at a specific application or user. This document defines a new optional SIP header, History-Info, for capturing the history information in requests.
Настоящий документ определяет стандартный механизм сбора информации об истории, связанной с запросом протокола инициирования сессий (SIP). Эта возможность позволяет реализовать множество расширенных служб, предоставляя информацию о том, как и почему вызов поступает в конкретное приложение или к конкретному пользователю. Настоящий документ определяет новый необязательный заголовок SIP — History-Info, предназначенный для сбора информации об истории в запросах.
1. Introduction
1. Введение
1.1. Overview
1.1. Обзор
Many services that SIP is anticipated to support require the ability to determine why and how the call arrived at a specific application. Examples of such services include (but are not limited to) sessions initiated to call centers via "click to talk" SIP Uniform Resource Locators (URLs) on a web page, "call history/logging" style services within intelligent "call management" software for SIP User Agents (UAs), and calls to voicemail servers. Although SIP implicitly provides the redirect/retarget capabilities that enable calls to be routed to chosen applications, there is currently no standard mechanism within SIP for communicating the history of such a request. This "request history" information allows the receiving application to determine hints about how and why the call arrived at the application/user.
Многие службы, поддержку которых предполагается обеспечить в SIP, требуют умения определять, почему и как вызов поступил в конкретное приложение. Примеры таких служб включают (но не ограничиваются ими) сеансы, инициированные в центры обработки вызовов через универсальные идентификаторы ресурсов (URL) SIP «click to talk» на веб-странице, службы класса «история/журналирование вызовов» в интеллектуальном программном обеспечении «управления вызовами» для пользовательских агентов (UA) SIP и вызовы на серверы голосовой почты. Хотя SIP неявно предоставляет возможности перенаправления/перенацеливания, позволяющие маршрутизировать вызовы в выбранные приложения, в настоящее время в SIP нет стандартного механизма для передачи истории такого запроса. Эта информация об «истории запросов» позволяет принимающему приложению получить подсказки о том, как и почему вызов поступил в приложение/к пользователю.
This document defines a new SIP header, History-Info, to provide a standard mechanism for capturing the request history information to enable a wide variety of services for networks and end-users. The History-Info header provides a building block for development of new services. Section 1.3 provides additional background motivation for the Request History capability. Section 2 identifies the requirements for a solution, with Section 3 providing an overall description of the solution.
Настоящий документ определяет новый заголовок SIP — History-Info, — обеспечивающий стандартный механизм сбора информации об истории запросов, что позволяет реализовать широкий спектр служб для сетей и конечных пользователей. Заголовок History-Info служит строительным блоком для разработки новых служб. Раздел 1.3 дополнительно обосновывает мотивацию возможности «история запросов». В разделе 2 определены требования к решению, а раздел 3 содержит общее описание решения.
Section 4 provides the details of the additions to the SIP protocol. Example uses of the new header are included in Section 4.5, with additional scenarios included in the Appendix.

1.3. Background: Why define a Generic "Request History" capability?
1.3. Предпосылки: зачем определять обобщённую возможность «история запросов»?
SIP implicitly provides redirect/retarget capabilities that enable calls to be routed to specific applications as defined in [RFC3261]. The term 'retarget' will be used henceforth in this document to refer to the process of a Proxy Server/User Agent Client (UAC) changing a Uniform Resource Identifier (URI) in a request and thus changing the target of the request. This term is chosen to avoid associating this request history only with the specific SIP Redirect Server capability that provides for a response to be sent back to a UAC requesting that the UAC should retarget the original request to an alternate URI. The rules for determining request targets as described in Section 16.5 of [RFC3261] are consistent with the use of the retarget term in this document.
SIP неявно предоставляет возможности перенаправления/перенацеливания, позволяющие маршрутизировать вызовы в конкретные приложения, как определено в [RFC3261]. Термин «retarget» (перенацеливание) далее в настоящем документе используется для обозначения процесса, в котором прокси-сервер или клиент пользовательского агента (UAC) изменяет универсальный идентификатор ресурса (URI) в запросе и тем самым изменяет цель запроса. Этот термин выбран, чтобы не связывать историю запросов только с конкретной возможностью сервера перенаправления SIP, которая предусматривает отправку ответа обратно UAC с требованием к UAC перенацелить исходный запрос на альтернативный URI. Правила определения целей запросов, описанные в разделе 16.5 [RFC3261], согласуются с использованием термина «перенацеливание» в настоящем документе.
The motivation for the request history is that in the process of retargeting, old routing information can be forever lost. This lost information may be important history that allows elements to which the call is retargeted to process the call in a locally defined, application-specific manner. The proposal in this document is to provide a mechanism for transporting the request history. It is not proposing any application-specific behavior for a Proxy or UA upon receipt of the information. Indeed, such behavior should be a local decision for the recipient application.
Мотивация истории запросов состоит в том, что в процессе перенацеливания старая информация о маршрутизации может быть безвозвратно потеряна. Эта потерянная информация может быть важной историей, позволяющей элементам, на которые перенацелен вызов, обрабатывать вызов локально определённым, зависящим от приложения образом. Предложение в настоящем документе состоит в том, чтобы обеспечить механизм передачи истории запросов. Оно не предлагает никакого зависящего от приложения поведения для прокси или UA при получении этой информации. Более того, такое поведение должно быть локальным решением принимающего приложения.
Current network applications provide the ability for elements involved with the call to exchange additional information relating to how and why the call was routed to a particular destination. The following are examples of such applications: 1. Web "referral" applications, whereby an application residing within a web server determines that a visitor to a website has arrived at the site via an "associate" site that will receive some "referral" commission for generating this traffic
Современные сетевые приложения предоставляют элементам, участвующим в вызове, возможность обмениваться дополнительной информацией о том, как и почему вызов был маршрутизирован к конкретному пункту назначения. Ниже приведены примеры таких приложений: 1. Веб-приложения «реферальных ссылок», в которых приложение, размещённое на веб-сервере, определяет, что посетитель веб-сайта пришёл на сайт через «партнёрский» сайт, который получит некоторую «реферальную» комиссию за создание этого трафика.
2. Email forwarding whereby the forwarded-to user obtains a "history" of who sent the email to whom and at what time
2. Пересылка электронной почты, при которой получатель пересланного письма получает «историю» того, кто, кому и когда его отправил.
3. Traditional telephony services such as voicemail, call-center "automatic call distribution", and "follow-me" style services
3. Традиционные телефонные службы, такие как голосовая почта, «автоматическое распределение вызовов» в центрах обработки вызовов и службы класса «следуй за мной».
Several of the aforementioned applications currently define application-specific mechanisms through which it is possible to obtain the necessary history information.
Некоторые из перечисленных выше приложений в настоящее время определяют зависящие от приложения механизмы, с помощью которых можно получить необходимую информацию об истории.
In addition, request history information could be used to enhance basic SIP functionality by providing the following:
Кроме того, информация об истории запросов может использоваться для расширения базовой функциональности SIP путём предоставления следующего:
o Some diagnostic information for debugging SIP requests. (Note that the diagnostic utility of this mechanism is limited by the fact that its use by entities that retarget is optional.)
o Некоторая диагностическая информация для отладки запросов SIP. (Обратите внимание, что диагностическая полезность этого механизма ограничена тем, что его использование субъектами, выполняющими перенацеливание, необязательно.)
o A stronger security solution for SIP. A side effect is that each proxy that captures the "request history" information in a secure manner provides an additional means (without requiring signed keys) for the original requestor to be assured that the request was properly retargeted.
o Более надёжное решение безопасности для SIP. Побочным эффектом является то, что каждый прокси, который безопасным образом фиксирует информацию об «истории запросов», предоставляет дополнительное средство (не требующее подписанных ключей), позволяющее исходному отправителю запроса убедиться, что запрос был должным образом перенацелен.

2.1. Security Requirements
2.1. Требования безопасности
The Request History information is being inserted by a network element retargeting a Request, resulting in a slightly different problem than the basic SIP header problem, thus requiring specific consideration. It is recognized that these security requirements can be generalized to a basic requirement of being able to secure information that is inserted by proxies.
Информация истории запросов вставляется сетевым элементом, перенацеливающим запрос, что приводит к несколько иной проблеме, чем базовая проблема заголовков SIP, и поэтому требует особого рассмотрения. Признаётся, что эти требования безопасности можно обобщить до базового требования возможности защитить информацию, вставляемую прокси.
The potential security problems include the following:
К потенциальным проблемам безопасности относятся следующие:
1) A rogue application could insert a bogus Request History entry either by adding an additional entry as a result of retargeting or entering invalid information.
1) Недобросовестное приложение могло бы вставить фиктивную запись истории запросов, либо добавив дополнительную запись в результате перенацеливания, либо внеся недостоверную информацию.
2) A rogue application could re-arrange the Request History information to change the nature of the end application or to mislead the receiver of the information.
2) Недобросовестное приложение могло бы переупорядочить информацию истории запросов, чтобы изменить характер конечного приложения или ввести получателя информации в заблуждение.
3) A rogue application could delete some or all of the Request History information.
3) Недобросовестное приложение могло бы удалить часть или всю информацию истории запросов.
Thus, a security solution for "Request History" must meet the following requirements:
Таким образом, решение безопасности для «истории запросов» должно удовлетворять следующим требованиям:
1) SEC-req-1: The entity receiving the Request History must be able to determine whether any of the previously added Request History content has been altered.
1) SEC-req-1: Субъект, получающий историю запросов, должен быть способен определить, было ли изменено какое-либо из ранее добавленных содержимых истории запросов.
2) SEC-req-2: The ordering of the Request History information must be preserved at each instance of retargeting.
2) SEC-req-2: Упорядоченность информации истории запросов должна сохраняться при каждом перенацеливании.
3) SEC-req-3: The entity receiving the information conveyed by the Request History must be able to authenticate the entity providing the request.
3) SEC-req-3: Субъект, получающий информацию, передаваемую историей запросов, должен быть способен аутентифицировать субъект, предоставивший запрос.
4) SEC-req-4: To ensure the confidentiality of the Request History information, only entities that process the request should have visibility to the information.
4) SEC-req-4: Для обеспечения конфиденциальности информации истории запросов доступ к ней должны иметь только субъекты, обрабатывающие запрос.
It should be noted that these security requirements apply to any entity making use of the Request History information, either by retargeting and capturing the information, or as an application making use of the information received in either a Request or Response.
Следует отметить, что эти требования безопасности применяются к любому субъекту, использующему информацию истории запросов, — либо путём перенацеливания и фиксации информации, либо в качестве приложения, использующего информацию, полученную в запросе или ответе.
2.2. Privacy Requirements
2.2. Требования конфиденциальности
Since the Request-URI that is captured could inadvertently reveal information about the originator, there are general privacy requirements that MUST be met:
Поскольку зафиксированный Request-URI может непреднамеренно раскрывать информацию об инициаторе, существуют общие требования конфиденциальности, которые ДОЛЖНЫ соблюдаться:
1) PRIV-req-1: The entity retargeting the Request must ensure that it maintains the network-provided privacy (as described in [RFC3323]) associated with the Request as it is retargeted.
1) PRIV-req-1: Субъект, перенацеливающий запрос, должен гарантировать, что он сохраняет сетевую конфиденциальность (как описано в [RFC3323]), связанную с запросом, при его перенацеливании.
2) PRIV-req-2: The entity receiving the Request History must maintain the privacy associated with the information.
2) PRIV-req-2: Субъект, получающий историю запросов, должен сохранять конфиденциальность, связанную с информацией.
In addition, local policy at a proxy may identify privacy requirements associated with the Request-URI being captured in the Request History information.
Кроме того, локальная политика прокси может определять требования конфиденциальности, связанные с Request-URI, фиксируемым в информации истории запросов.
3) PRIV-req-3: Request History information subject to privacy requirements shall not be included in outgoing messages unless it is protected as described in [RFC3323].
3) PRIV-req-3: Информация истории запросов, подпадающая под требования конфиденциальности, не должна включаться в исходящие сообщения, если только она не защищена, как описано в [RFC3323].
3. Request History Information Description
3. Описание информации истории запросов
The fundamental functionality provided by the request history information is the ability to inform proxies and UAs involved in processing a request about the history or progress of that request (CAPABILITY-req). The solution is to capture the Request-URIs as a request is forwarded in a new header for SIP messages: History-Info (CONTENT-req). This allows for the capturing of the history of a request that would be lost with the normal SIP processing involved in the subsequent forwarding of the request. This solution proposes no changes in the fundamental determination of request targets or in the request forwarding as defined in Sections 16.5 and 16.6 of the SIP protocol specification [RFC3261].
Основная функциональность, предоставляемая информацией истории запросов, — это возможность информировать прокси и UA, участвующих в обработке запроса, об истории или продвижении этого запроса (CAPABILITY-req). Решение состоит в том, чтобы фиксировать Request-URI по мере пересылки запроса в новом заголовке сообщений SIP — History-Info (CONTENT-req). Это позволяет фиксировать историю запроса, которая была бы потеряна при обычной обработке SIP при последующей пересылке запроса. Это решение не предлагает изменений в фундаментальном определении целей запросов или в пересылке запросов, как определено в разделах 16.5 и 16.6 спецификации протокола SIP [RFC3261].
The History-Info header can appear in any request not associated with an established dialog (e.g., INVITE, REGISTER, MESSAGE, REFER and OPTIONS, PUBLISH and SUBSCRIBE, etc.) (REQUEST-VALIDITY-req) and any valid response to these requests (ISSUER-req).
Заголовок History-Info может присутствовать в любом запросе, не связанном с установленным диалогом (например, INVITE, REGISTER, MESSAGE, REFER и OPTIONS, PUBLISH и SUBSCRIBE и т. д.) (REQUEST-VALIDITY-req), и в любом допустимом ответе на эти запросы (ISSUER-req).
The History-Info header is added to a Request when a new request is created by a UAC or forwarded by a Proxy, or when the target of a request is changed. The term 'retarget' is introduced to refer to this changing of the target of a request and the subsequent forwarding of that request. It should be noted that retargeting only occurs when the Request-URI indicates a domain for which the processing entity is responsible. In terms of the SIP protocol, the processing associated with retargeting is described in Sections 16.5 and 16.6 of [RFC3261]. As described in Section 16.5 of [RFC3261], it is possible for the target of a request to be changed by the same proxy multiple times (referred to as 'internal retargeting' in Section 2), as the proxy MAY add targets to the target set after beginning Request Forwarding. Section 16.6 of [RFC3261] describes Request Forwarding. It is during this process of Request Forwarding that the History Information is captured as an optional, additional header field. Thus, the addition of the History-Info header does not impact fundamental SIP Request Forwarding. An entity (UA or proxy) changing the target of a request in response to a redirect or REFER SHOULD also propagate any History-Info header from the initial Request in the new request (GENERATION-req, FORWARDS-req).
Заголовок History-Info добавляется в запрос, когда новый запрос создаётся UAC или пересылается прокси, либо когда цель запроса изменяется. Термин «retarget» (перенацеливание) введён для обозначения такого изменения цели запроса и последующей пересылки этого запроса. Следует отметить, что перенацеливание происходит только тогда, когда Request-URI указывает домен, за который отвечает обрабатывающий субъект. С точки зрения протокола SIP обработка, связанная с перенацеливанием, описана в разделах 16.5 и 16.6 [RFC3261]. Как описано в разделе 16.5 [RFC3261], цель запроса может быть изменена одним и тем же прокси несколько раз (в разделе 2 это называется «внутренним перенацеливанием»), поскольку прокси МОЖЕТ добавлять цели в набор целей после начала пересылки запроса. Раздел 16.6 [RFC3261] описывает пересылку запросов. Именно в процессе этой пересылки запросов информация об истории фиксируется как необязательное дополнительное поле заголовка. Таким образом, добавление заголовка History-Info не влияет на фундаментальную пересылку запросов SIP. Субъект (UA или прокси), изменяющий цель запроса в ответ на перенаправление или REFER, ДОЛЖЕН также передавать любой заголовок History-Info из исходного запроса в новом запросе (GENERATION-req, FORWARDS-req).
3.1. Optionality of History-Info
3.1. Необязательность History-Info
The History-Info header is optional in that neither UAs nor Proxies are required to support it. A new Supported header, "histinfo", is included in the Request to indicate whether the History-Info header is returned in Responses (BACKWARDS-req). In addition to the "histinfo" Supported header, local policy determines whether or not the header is added to any request, or for a specific Request-URI, being retargeted. It is possible that this could restrict the applicability of services that make use of the Request History Information to be limited to retargeting within domain(s) controlled by the same local policy, or between domain(s) which negotiate policies with other domains to ensure support of the given policy, or services for which complete History Information isn't required to provide the service (OPTIONALITY-req). All applications making use of the History-Info header MUST clearly define the impact of the information not being available and specify the processing of such a request.
Заголовок History-Info необязателен в том смысле, что ни UA, ни прокси не обязаны его поддерживать. В запрос включается новый заголовок Supported — «histinfo», — указывающий, возвращается ли заголовок History-Info в ответах (BACKWARDS-req). Помимо заголовка Supported со значением «histinfo», локальная политика определяет, добавляется ли заголовок к какому-либо запросу или к конкретному Request-URI при перенацеливании. Возможно, это может ограничить применимость служб, использующих информацию истории запросов, перенацеливанием в пределах домена (доменов), контролируемых одной и той же локальной политикой, либо между доменами (доменом), которые согласуют политику с другими доменами для обеспечения поддержки данной политики, либо службами, для которых полная информация об истории не требуется для предоставления службы (OPTIONALITY-req). Все приложения, использующие заголовок History-Info, ДОЛЖНЫ чётко определить влияние недоступности информации и описать обработку такого запроса.
3.2. Securing History-Info
3.2. Защита History-Info
This document defines a new header for SIP. The use of the Transport Layer Security (TLS) protocol [RFC2246] as a mandatory mechanism to ensure the overall confidentiality of the History-Info headers (SEC- req-4) is strongly RECOMMENDED. This results in History-Info having at least the same level of security as other headers in SIP that are inserted by intermediaries. If TLS is not available for the connection over which the request is being forwarded, then the request MUST NOT include the History-Info header or the request MUST be redirected to the client, including the History-Info header, so that the request can be retargeted by the client.
Настоящий документ определяет новый заголовок для SIP. Настоятельно РЕКОМЕНДУЕТСЯ использовать протокол безопасности транспортного уровня (TLS) [RFC2246] как обязательный механизм обеспечения общей конфиденциальности заголовков History-Info (SEC-req-4). В результате History-Info имеет по меньшей мере такой же уровень безопасности, как и другие заголовки SIP, вставляемые посредниками. Если TLS недоступен для соединения, по которому пересылается запрос, то запрос НЕ ДОЛЖЕН содержать заголовок History-Info либо запрос ДОЛЖЕН быть перенаправлен клиенту вместе с заголовком History-Info, чтобы запрос мог быть перенацелен клиентом.
With the level of security provided by TLS (SEC-req-3), the information in the History-Info header can thus be evaluated to determine if information has been removed by evaluating the indices for gaps (SEC-req-1, SEC-req-2). It would be up to the application to define whether it can make use of the information in the case of missing entries.
При уровне безопасности, обеспечиваемом TLS (SEC-req-3), информацию в заголовке History-Info можно, таким образом, оценить на предмет того, была ли какая-либо информация удалена, путём анализа индексов на наличие пропусков (SEC-req-1, SEC-req-2). Определение того, может ли приложение использовать информацию в случае отсутствующих записей, остаётся за приложением.
Note that while using the SIPS scheme protects History-Info from tampering by arbitrary parties outside the SIP message path, all the intermediaries on the path are trusted implicitly. A malicious intermediary could arbitrarily delete, rewrite, or modify History- Info. This specification does not attempt to prevent or detect attacks by malicious intermediaries.
Отметим, что хотя использование схемы SIPS защищает History-Info от подделки произвольными сторонами вне пути сообщения SIP, все посредники на пути неявно считаются доверенными. Вредоносный посредник мог бы произвольно удалять, перезаписывать или изменять History-Info. Настоящая спецификация не пытается предотвращать или обнаруживать атаки вредоносных посредников.
3.3. Ensuring the Privacy of History-Info
3.3. Обеспечение конфиденциальности History-Info
Since the History-Info header can inadvertently reveal information about the requestor as described in [RFC3323], the Privacy header SHOULD be used to determine whether an intermediary can include the History-Info header in a Request that it receives and forwards (PRIV-req-2) or that it retargets (PRIV-req-1). Thus, the History- Info header SHOULD NOT be included in Requests where the requestor has indicated a priv-value of Session- or Header-level privacy.
Поскольку заголовок History-Info может непреднамеренно раскрывать информацию об отправителе запроса, как описано в [RFC3323], заголовок Privacy СЛЕДУЕТ использовать для определения того, может ли посредник включать заголовок History-Info в запрос, который он получает и пересылает (PRIV-req-2), или который он перенацеливает (PRIV-req-1). Таким образом, заголовок History-Info НЕ СЛЕДУЕТ включать в запросы, в которых отправитель запроса указал priv-value уровня «session» или «header».
In addition, the History-Info header can reveal general routing information, which may be viewed by a specific intermediary or network, to be subject to privacy restrictions. Thus, local policy MAY also be used to determine whether to include the History-Info header at all, whether to capture a specific Request-URI in the header, or whether it be included only in the Request as it is retargeted within a specific domain (PRIV-req-3). In the latter case, this is accomplished by adding a new priv-value, history, to the Privacy header [RFC3323] indicating whether any or a specific History-Info header(s) SHOULD be forwarded.
Кроме того, заголовок History-Info может раскрывать общую информацию о маршрутизации, которая, с точки зрения конкретного посредника или сети, может подпадать под ограничения конфиденциальности. Таким образом, локальная политика МОЖЕТ также использоваться для определения того, включать ли заголовок History-Info вообще, фиксировать ли конкретный Request-URI в заголовке или включать его только в запрос при перенацеливании в пределах конкретного домена (PRIV-req-3). В последнем случае это достигается путём добавления нового priv-value — history — в заголовок Privacy [RFC3323], указывающего, следует ли пересылать какой-либо или конкретный заголовок (заголовки) History-Info.
It is recognized that satisfying the privacy requirements can impact the functionality of this solution by overriding the request to generate the information. As with the optionality and security requirements, applications making use of History-Info SHOULD address any impact this may have or MUST explain why it does not impact the application.
Признаётся, что соблюдение требований конфиденциальности может повлиять на функциональность этого решения, отменяя требование создавать информацию. Как и в случае требований необязательности и безопасности, приложения, использующие History-Info, СЛЕДУЕТ учитывать любое такое влияние или ОБЯЗАНЫ объяснить, почему оно не влияет на приложение.

4.3. Protocol Usage
4.3. Использование протокола
This section describes the processing specific to UAs and Proxies for the History-Info header, the "histinfo" option tag, and the priv- value of "history". As discussed in Section 1.3, the fundamental objective is to capture the target Request-URIs as a request is forwarded. This allows for the capturing of the history of a request that would be lost due to subsequent (re)targeting and forwarding. To accomplish this for the entire history of a request, either the UAC must capture the Request-URI in a History-Info header in the initial request or a proxy must add a History-Info header with both a hi-entry for the Request-URI in the initial request and a hi-entry for the target Request-URI as the request is forwarded. The basic processing is for each entity forwarding a request to add a hi-entry for the target Request-URI, updating the index and adding the Reason as appropriate for any retargeted Request-URI.
В этом разделе описана обработка, специфичная для UA и прокси, для заголовка History-Info, тега опции «histinfo» и priv-value «history». Как обсуждалось в разделе 1.3, фундаментальная цель — фиксировать целевые Request-URI по мере пересылки запроса. Это позволяет фиксировать историю запроса, которая была бы потеряна из-за последующего (повторного) перенацеливания и пересылки. Чтобы охватить всю историю запроса, либо UAC должен зафиксировать Request-URI в заголовке History-Info в исходном запросе, либо прокси должен добавить заголовок History-Info как с hi-entry для Request-URI исходного запроса, так и с hi-entry для целевого Request-URI по мере пересылки запроса. Базовая обработка состоит в том, чтобы каждый субъект, пересылающий запрос, добавлял hi-entry для целевого Request-URI, обновлял индекс и добавлял Reason должным образом для любого перенацеленного Request-URI.
4.3.1. User Agent Client (UAC) Behavior
4.3.1. Поведение клиента пользовательского агента (UAC)
The UAC SHOULD include the "histinfo" option tag in the Supported header in any request not associated with an established dialog for which the UAC would like the History-Info header in the response. In addition, the UAC MAY improve the diagnostic utility of its request by adding a History-Info header, using the Request-URI of the request as the hi-target-to-uri and initializing the index to the RECOMMENDED value of 1 in the hi-entry. As a result, intermediaries and the UAS will know at least the original Request-URI, and if the Request-URI was modified by a previous hop.
UAC СЛЕДУЕТ включать тег опции «histinfo» в заголовок Supported в любом запросе, не связанном с установленным диалогом, для которого UAC хотел бы получить заголовок History-Info в ответе. Кроме того, UAC МОЖЕТ повысить диагностическую полезность своего запроса, добавив заголовок History-Info, используя Request-URI запроса как hi-target-to-uri и инициализируя индекс РЕКОМЕНДУЕМЫМ значением 1 в hi-entry. В результате посредники и UAS будут знать по крайней мере исходный Request-URI и то, был ли Request-URI изменён предыдущим переходом.
In the case where the request is routed to a redirect server and the UAC receives a 3xx response with a Contact header, the UAC MAY maintain the previous hi-entry(s) in the request. In this case, the reason header SHOULD be associated with the hi-targeted-to-uri in the previous (last) hi-entry, as described in Section 4.3.3.1.2. A new hi-entry MAY then be added for the URI from the Contact header (which becomes the new Request-URI). In this case, the index is created by reading and incrementing the value of the index from the previous hi-entry, thus following the same rules as those prescribed for a proxy in retargeting, described in Section 4.3.3.1.3. An example of this scenario can be found in Appendix D.
В случае, когда запрос маршрутизируется на сервер перенаправления и UAC получает ответ 3xx с заголовком Contact, UAC МОЖЕТ сохранить предыдущие hi-entry в запросе. В этом случае заголовок reason СЛЕДУЕТ связать с hi-targeted-to-uri в предыдущей (последней) hi-entry, как описано в разделе 4.3.3.1.2. Затем МОЖЕТ быть добавлена новая hi-entry для URI из заголовка Contact (который становится новым Request-URI). В этом случае индекс создаётся путём чтения и инкрементирования значения индекса из предыдущей hi-entry, следуя тем же правилам, которые предписаны для прокси при перенацеливании и описаны в разделе 4.3.3.1.3. Пример этого сценария можно найти в приложении D.
A UAC that does not want the History-Info header added due to privacy considerations SHOULD include a Privacy header with a priv-value(s) of "session", "header", or "history" in the request. With the exception of the processing of a 3xx response described above, the processing of the History-Info header received in the Response is application specific and outside the scope of this document. However, the validity of the information SHOULD be ensured prior to any application usage. For example, the entries MAY be evaluated to determine gaps in indices, which could indicate that an entry has been maliciously removed or removed for privacy reasons. Either way, an application MAY want to be aware of potentially missing information.
UAC, который не хочет, чтобы заголовок History-Info добавлялся по соображениям конфиденциальности, СЛЕДУЕТ включить в запрос заголовок Privacy с priv-value «session», «header» или «history». За исключением обработки ответа 3xx, описанной выше, обработка заголовка History-Info, полученного в ответе, зависит от приложения и выходит за рамки настоящего документа. Однако перед любым использованием в приложении СЛЕДУЕТ убедиться в достоверности информации. Например, записи МОГУТ быть оценены на предмет пропусков в индексах, что может указывать на то, что запись была злонамеренно удалена или удалена по соображениям конфиденциальности. В любом случае приложению МОЖЕТ потребоваться знать о потенциально отсутствующей информации.
4.3.2. User Agent Server (UAS) Behavior
4.3.2. Поведение сервера пользовательского агента (UAS)
The processing of the History-Info header by a UAS in a Request depends upon local policy and specific applications at the UAS that might make use of the information. Prior to any application usage of the information, the validity SHOULD be ascertained. For example, the entries MAY be evaluated to determine gaps in indices, which could indicate that an entry has been maliciously removed or removed for privacy reasons. Either way, an application MAY want to be aware of potentially missing information.
Обработка заголовка History-Info UAS в запросе зависит от локальной политики и конкретных приложений на UAS, которые могут использовать эту информацию. Перед любым использованием информации в приложении СЛЕДУЕТ удостовериться в её достоверности. Например, записи МОГУТ быть оценены на предмет пропусков в индексах, что может указывать на то, что запись была злонамеренно удалена или удалена по соображениям конфиденциальности. В любом случае приложению МОЖЕТ потребоваться знать о потенциально отсутствующей информации.
If the "histinfo" option tag is received in a request, the UAS SHOULD include any History-Info received in the request in the subsequent response.
Если в запросе получен тег опции «histinfo», UAS СЛЕДУЕТ включать любой полученный в запросе History-Info в последующий ответ.
4.3.3. Proxy Behavior
4.3.3. Поведение прокси
The inclusion of the History-Info header in a Request does not alter the fundamental processing of proxies for determining request targets as defined in Section 16.5 of [RFC3261]. Whether a proxy adds the History-Info header or a new hi-entry as it forwards a Request depends upon the following considerations:
Включение заголовка History-Info в запрос не изменяет фундаментальную обработку прокси для определения целей запросов, как определено в разделе 16.5 [RFC3261]. То, добавляет ли прокси заголовок History-Info или новую hi-entry при пересылке запроса, зависит от следующих соображений:
1. Whether the Request contains the "histinfo" option tag in the Supported header.
1. Содержит ли запрос тег опции «histinfo» в заголовке Supported.
2. Whether the proxy supports the History-Info header.
2. Поддерживает ли прокси заголовок History-Info.
3. Whether the Request contains a Privacy header with a priv-value of "session", "header", or "history".
3. Содержит ли запрос заголовок Privacy с priv-value «session», «header» или «history».
4. Whether any History-Info header added for a proxy/domain should go outside that domain. An example being the use of the History-Info header within the specific domain in which it is retargeted, however, policies (for privacy, user and network security, etc.) would prohibit the exposure of that information outside that domain. To accommodate such a scenario, a proxy MAY insert the Privacy header with a priv-value of "history" when the request is being forwarded within the same domain. An example of such an application is provided in Appendix C.
4. Должен ли какой-либо заголовок History-Info, добавленный прокси/доменом, выходить за пределы этого домена. Примером является использование заголовка History-Info в конкретном домене, в котором выполняется перенацеливание, однако политики (конфиденциальности, пользовательской и сетевой безопасности и т. п.) запрещали бы раскрытие этой информации за пределами этого домена. Чтобы учесть такой сценарий, прокси МОЖЕТ вставлять заголовок Privacy с priv-value «history», когда запрос пересылается в пределах одного домена. Пример такого применения приведён в приложении C.
5. Whether a hi-entry is added for a specific Request-URI due to local privacy policy considerations. A proxy MAY add the Privacy header with a priv-value of "history" associated with the specific hi-targeted-to-uri.
5. Добавляется ли hi-entry для конкретного Request-URI с учётом соображений локальной политики конфиденциальности. Прокси МОЖЕТ добавлять заголовок Privacy с priv-value «history», связанный с конкретным hi-targeted-to-uri.
An example policy would be a proxy that only adds the History-Info header if the "histinfo" option tag is in the Supported header. Other proxies may have a policy that they always add the header, but never forward it outside a particular domain, accomplishing this by adding a Privacy header with a priv-value of "history" to each hi- entry to allow the information to be collected for internal retargeting only.
Примером политики может служить прокси, который добавляет заголовок History-Info только в том случае, если тег опции «histinfo» присутствует в заголовке Supported. Другие прокси могут иметь политику, по которой они всегда добавляют заголовок, но никогда не пересылают его за пределы определённого домена, достигая этого путём добавления заголовка Privacy с priv-value «history» к каждой hi-entry, чтобы информация собиралась только для внутреннего перенацеливания.
Each application making use of the History-Info header SHOULD address the impacts of the local policies on the specific application (e.g., what specification of local policy is optimally required for a specific application and any potential limitations imposed by local policy decisions).
Каждому приложению, использующему заголовок History-Info, СЛЕДУЕТ учитывать влияние локальных политик на конкретное приложение (например, какая спецификация локальной политики оптимально требуется для конкретного приложения и какие потенциальные ограничения накладывают решения локальной политики).
Consistent with basic SIP processing of optional headers, proxies SHOULD maintain the History-Info header(s), received in messages being forwarded, independent of whether local policy supports History-Info.
В соответствии с базовой обработкой необязательных заголовков в SIP прокси СЛЕДУЕТ сохранять заголовок (заголовки) History-Info, полученные в пересылаемых сообщениях, независимо от того, поддерживает ли локальная политика History-Info.
The specific processing by proxies for adding the History-Info headers in Requests and Responses, to accommodate the considerations outlined above, is described in detail in the following sections.
Конкретная обработка прокси для добавления заголовков History-Info в запросы и ответы, с тем чтобы учесть изложенные выше соображения, подробно описана далее в следующих разделах настоящего документа.
4.3.3.1. Adding the History-Info Header to Requests
4.3.3.1. Добавление заголовка History-Info в запросы
Upon evaluation of the considerations under which the History-Info header is to be included in requests (e.g., no Privacy header overriding inclusion, local policy supports, etc.), detailed in Section 4.3.3, a proxy SHOULD add a hi-entry as it forwards a Request. Section 16.6 of [RFC3261] defines the steps to be followed as the proxy forwards a Request. Step 5 prescribes the addition of optional headers. Although this would seem the appropriate step for adding the History-Info header, the interaction with Step 6, "Postprocess routing information", and the impact of a strict route in the Route header could result in the Request-URI being changed; thus, adding the History-Info header between Steps 8 (adding Via header) and 9 (adding Content-Length) is RECOMMENDED. Note that in the case of loose routing, the Request-URI does not change during the forwarding of a Request; thus, the capturing of History-Info for such a request would result in duplicate Request-URIs with different indices. The hi-entry MUST be added following any hi-entry received in the request being forwarded. Additionally, if a request is received that doesn't include a History-Info header, the proxy MAY add a History-Info header with a hi-entry preceding the one being added for the current request being forwarded. The index for this hi-entry is RECOMMENDED to start at 1.
После оценки соображений, при которых заголовок History-Info должен включаться в запросы (например, отсутствие заголовка Privacy, отменяющего включение, поддержка локальной политикой и т. п.), подробно изложенных в разделе 4.3.3, прокси СЛЕДУЕТ добавлять hi-entry при пересылке запроса. Раздел 16.6 [RFC3261] определяет шаги, которым следует прокси при пересылке запроса. Шаг 5 предписывает добавление необязательных заголовков. Хотя это казалось бы подходящим шагом для добавления заголовка History-Info, взаимодействие с шагом 6 «Постобработка информации маршрутизации» и влияние строгой маршрутизации в заголовке Route могли бы привести к изменению Request-URI; поэтому РЕКОМЕНДУЕТСЯ добавлять заголовок History-Info между шагами 8 (добавление заголовка Via) и 9 (добавление Content-Length). Отметим, что в случае свободной маршрутизации Request-URI не изменяется при пересылке запроса; таким образом, фиксация History-Info для такого запроса привела бы к дублирующимся Request-URI с разными индексами. hi-entry ДОЛЖНА быть добавлена после любой hi-entry, полученной в пересылаемом запросе. Кроме того, если получен запрос, не содержащий заголовка History-Info, прокси МОЖЕТ добавить заголовок History-Info с hi-entry, предшествующей той, которая добавляется для текущего пересылаемого запроса. РЕКОМЕНДУЕТСЯ, чтобы индекс этой hi-entry начинался с 1.
The following subsections define the details of creating the information associated with each hi-entry.
В следующих подразделах определены подробности создания информации, связанной с каждой hi-entry.
4.3.3.1.1. Privacy in the History-Info Header
4.3.3.1.1. Конфиденциальность в заголовке History-Info
If there is a Privacy header in the request with a priv-value of "session", "header", or "history", a hi-entry MAY be added, if the request is being forwarded to a Request-URI associated with a domain for which the processing entity is responsible (and provided local policy supports the History-Info header, etc.). If a request is being forwarded to a Request-URI associated with a domain for which the proxy is not responsible and there is a Privacy header in the request with a priv-value of "session", "header", or "history", the proxy SHOULD remove any hi-entry(s) prior to forwarding, depending upon local policy and whether the proxy might know a priori that it can rely on a downstream privacy service to apply the requested privacy.
Если в запросе присутствует заголовок Privacy с priv-value «session», «header» или «history», hi-entry МОЖЕТ быть добавлена, если запрос пересылается к Request-URI, связанному с доменом, за который отвечает обрабатывающий субъект (и при условии, что локальная политика поддерживает заголовок History-Info и т. п.). Если запрос пересылается к Request-URI, связанному с доменом, за который прокси не отвечает, и в запросе присутствует заголовок Privacy с priv-value «session», «header» или «history», прокси СЛЕДУЕТ удалить любую hi-entry перед пересылкой — в зависимости от локальной политики и от того, может ли прокси заранее знать, что он может положиться на нижестоящую службу конфиденциальности для применения запрошенной конфиденциальности.
For the scenario where there is no Privacy header in the request and the request is being forwarded to a Request-URI associated with the domain(s) for which this entity is responsible, there are several additional considerations:
Для сценария, когда в запросе нет заголовка Privacy и запрос пересылается к Request-URI, связанному с доменом (доменами), за который отвечает этот субъект, существует несколько дополнительных соображений:
o If there is no local policy associated with privacy, then a hi- entry MAY be added to the Request.
o Если с конфиденциальностью не связана никакая локальная политика, то в запрос МОЖЕТ быть добавлена hi-entry.
o If the proxy's local policies, per consideration 4 in section 4.3.3, indicate that the History-Info header should not be forwarded beyond the domain for which this intermediary is responsible, then a Privacy header with a priv-value of "history" SHOULD be associated with each hi-entry added by that proxy in this scenario.
o Если локальные политики прокси, согласно соображению 4 в разделе 4.3.3, указывают, что заголовок History-Info не следует пересылать за пределы домена, за который отвечает этот посредник, то с каждой hi-entry, добавленной этим прокси в таком сценарии, СЛЕДУЕТ связывать заголовок Privacy с priv-value «history».
o If the proxy's policy, per consideration 5 in Section 4.3.3, indicates that History-Info for a specific Request-URI should not be forwarded beyond the domain for which this intermediary is responsible, then a Privacy header with a priv-value of "history" SHOULD be associated with the specific hi-entry, for that specific hi-targeted-to-uri, added by that proxy in this scenario.
o Если политика прокси, согласно соображению 5 в разделе 4.3.3, указывает, что History-Info для конкретного Request-URI не следует пересылать за пределы домена, за который отвечает этот посредник, то с конкретной hi-entry для этого конкретного hi-targeted-to-uri, добавленной этим прокси в таком сценарии, СЛЕДУЕТ связывать заголовок Privacy с priv-value «history».
If a request is being forwarded to a Request-URI associated with a domain for which the proxy is not responsible and local policy requires privacy associated with any, or with specific, hi-entries it has added, any hi-entry with a priv-value of "history" SHOULD be removed prior to forwarding.
Если запрос пересылается к Request-URI, связанному с доменом, за который прокси не отвечает, и локальная политика требует конфиденциальности для любой или для конкретных добавленных им hi-entry, то любую hi-entry с priv-value «history» СЛЕДУЕТ удалить перед пересылкой.
4.3.3.1.2. Reason in the History-Info Header
4.3.3.1.2. Reason в заголовке History-Info
For retargets that are the result of an explicit SIP response, a Reason MUST be associated with the hi-targeted-to-uri. If the SIP response does not include a Reason header, the SIP Response Code that triggered the retargeting MUST be included as the Reason associated with the hi-targeted-to-uri that has been retargeted. If the response contains a non-SIP Reason header (e.g., Q.850), it MUST be captured as an additional Reason associated with the hi-targeted-to- uri that has been retargeted, along with the SIP Response Code. If the Reason header is a SIP reason, then it MUST be used as the Reason associated with the hi-targeted-to-uri rather than the SIP response code.
Для перенацеливаний, являющихся результатом явного ответа SIP, с hi-targeted-to-uri ДОЛЖЕН быть связан Reason. Если ответ SIP не содержит заголовка Reason, код ответа SIP, вызвавший перенацеливание, ДОЛЖЕН быть включён как Reason, связанный с перенацеленным hi-targeted-to-uri. Если ответ содержит заголовок Reason, не относящийся к SIP (например, Q.850), он ДОЛЖЕН быть зафиксирован как дополнительный Reason, связанный с перенацеленным hi-targeted-to-uri, вместе с кодом ответа SIP. Если заголовок Reason является причиной SIP, то он ДОЛЖЕН использоваться как Reason, связанный с hi-targeted-to-uri, вместо кода ответа SIP.
For retargets as a result of timeouts or internal events, a Reason MAY be associated with the hi-targeted-to-uri that has been retargeted.
Для перенацеливаний в результате тайм-аутов или внутренних событий с перенацеленным hi-targeted-to-uri МОЖЕТ быть связан Reason.
The addition of the Reason should occur prior to the forwarding of the request (which may add a new hi-entry with a new hi-targeted-to- uri) as it is associated with the hi-targeted-to-uri that has been retargeted, since it reflects the reason why the Request to that specific URI was not successful.
Добавление Reason должно происходить до пересылки запроса (которая может добавить новую hi-entry с новым hi-targeted-to-uri), поскольку оно связано с hi-targeted-to-uri, который был перенацелен, так как отражает причину, по которой запрос к этому конкретному URI оказался неуспешным.
4.3.3.1.3. Indexing in the History-Info Header
4.3.3.1.3. Индексация в заголовке History-Info
In order to maintain ordering and accurately reflect the nesting and retargeting of the request, an index MUST be included along with the Targeted-to-URI being captured. Per the syntax in Section 4.1, the index consists of a dot-delimited series of digits (e.g., 1.1.2). Each dot reflects a hop or level of nesting; thus, the number of hops is determined by the total number of dots. Within each level, the integer reflects the number of peer entities to which the request has been routed. Thus, the indexing results in a logical tree representation for the history of the Request. It is recommended that for each level of indexing, the index start at 1. It is recommended that an increment of 1 is used for advancing to a new branch.
Чтобы поддерживать упорядоченность и точно отражать вложенность и перенацеливание запроса, вместе с фиксируемым Targeted-to-URI ДОЛЖЕН быть включён индекс. Согласно синтаксису из раздела 4.1, индекс состоит из серии цифр, разделённых точками (например, 1.1.2). Каждая точка отражает переход или уровень вложенности; таким образом, число переходов определяется общим числом точек. На каждом уровне целое число отражает число одноранговых субъектов, к которым был маршрутизирован запрос. Таким образом, индексация даёт логическое древовидное представление истории запроса. Рекомендуется, чтобы на каждом уровне индексации индекс начинался с 1. Рекомендуется использовать приращение 1 при переходе к новой ветви.
The basic rules for adding the index are summarized as follows:
Основные правила добавления индекса резюмируются следующим образом:
1. Basic Forwarding: In the case of a Request that is being forwarded, the index is determined by adding another level of indexing since the depth/length of the branch is increasing. To accomplish this, the proxy reads the value from the History-Info header in the received request, if available, and adds another level of indexing by appending the dot delimiter followed by an initial index for the new level RECOMMENDED to be 1. For example, if the index in the last History-Info header field in the received request is 1.1, this proxy would initialize its index to 1.1.1 and forward the request.
1. Базовая пересылка: в случае запроса, который пересылается, индекс определяется путём добавления ещё одного уровня индексации, поскольку глубина/длина ветви увеличивается. Для этого прокси читает значение из заголовка History-Info в полученном запросе, если он имеется, и добавляет ещё один уровень индексации, дописывая разделитель-точку и начальный индекс для нового уровня, РЕКОМЕНДУЕМЫЙ равным 1. Например, если индекс в последнем поле заголовка History-Info в полученном запросе равен 1.1, этот прокси инициализировал бы свой индекс значением 1.1.1 и переслал бы запрос.
2. Retargeting within a Proxy - 1st instance: For the first instance of retargeting within a Proxy, the calculation of the index follows that prescribed for basic forwarding.
2. Перенацеливание в пределах прокси — первый случай: для первого случая перенацеливания в пределах прокси вычисление индекса следует предписанному для базовой пересылки.
3. Retargeting within a Proxy - subsequent instance: For each subsequent retargeting of a request by the same proxy, another branch is added. With the index for each new branch calculated by incrementing the last/lowest digit at the current level, the index in the next request forwarded by this same proxy, following the example above, would be 1.1.2.
3. Перенацеливание в пределах прокси — последующий случай: для каждого последующего перенацеливания запроса тем же прокси добавляется ещё одна ветвь. Поскольку индекс для каждой новой ветви вычисляется путём инкрементирования последней/наименьшей цифры на текущем уровне, индекс в следующем запросе, пересылаемом этим же прокси, следуя приведённому выше примеру, был бы 1.1.2.
4. Retargeting based upon a Response: In the case of retargeting due to a specific response (e.g., 302), the index would be calculated per rule 3. That is, the lowest/last digit of the index is incremented (i.e., a new branch is created), with the increment RECOMMENDED to be 1. For example, if the index in the History-Info header of the received request was 1.2, then the index in the History-Info header field for the new hi-targeted- to-URI would be 1.3.
4. Перенацеливание на основе ответа: в случае перенацеливания из-за конкретного ответа (например, 302) индекс вычислялся бы по правилу 3. То есть наименьшая/последняя цифра индекса инкрементируется (то есть создаётся новая ветвь), причём приращение РЕКОМЕНДУЕТСЯ равным 1. Например, если индекс в заголовке History-Info полученного запроса был 1.2, то индекс в поле заголовка History-Info для нового hi-targeted-to-uri был бы 1.3.
5. Retargeting the request in parallel (forking): If the request forwarding is done in parallel, the index MUST be captured for each forked request per the rules above, with each new Request having a unique index. The only difference in the messaging for this scenario and the messaging produced per basic proxy retargeting in rules 2 and 3 is these forwarded requests do not have History-Info entries associated with their peers. The proxy builds the subsequent response (or request) using the aggregated information associated with each of those requests and including the header entries in the order indicated by the indexing. Responses are processed as described in Section 16.7 of [RFC3261] with the aggregated History-Info entries processed similar to Step 7 "Aggregate Authentication Header Field Values". Section 4.5 provides an example of a parallel request scenario, highlighting this indexing mechanism.
5. Перенацеливание запроса параллельно (разветвление): если пересылка запроса выполняется параллельно, индекс ДОЛЖЕН фиксироваться для каждого разветвлённого запроса согласно приведённым выше правилам, причём каждый новый запрос должен иметь уникальный индекс. Единственное различие в обмене сообщениями для этого сценария и в обмене сообщениями, создаваемом при базовом перенацеливании прокси по правилам 2 и 3, состоит в том, что эти пересылаемые запросы не имеют записей History-Info, связанных с их одноранговыми узлами. Прокси строит последующий ответ (или запрос), используя агрегированную информацию, связанную с каждым из этих запросов, и включая записи заголовка в порядке, указанном индексацией. Ответы обрабатываются, как описано в разделе 16.7 [RFC3261], причём агрегированные записи History-Info обрабатываются аналогично шагу 7 «Агрегирование значений полей заголовка аутентификации». В разделе 4.5 приведён пример сценария параллельного запроса, иллюстрирующий этот механизм индексации.
4.3.3.2. Processing History-Info in Responses
4.3.3.2. Обработка History-Info в ответах
A proxy that receives a Request with the "histinfo" option tag in the Supported header, and depending upon a local policy supporting the capture of History-Info, SHOULD return captured History-Info in subsequent, provisional, and final responses to the Request, subject to the following considerations for privacy:
Прокси, который получает запрос с тегом опции «histinfo» в заголовке Supported и, в зависимости от локальной политики, поддерживающей фиксацию History-Info, СЛЕДУЕТ возвращать зафиксированный History-Info в последующих, промежуточных и окончательных ответах на запрос с учётом следующих соображений конфиденциальности:
o If the response is being forwarded to a Request-URI associated with a domain for which the proxy is not responsible and there was a Privacy header, in the request received by the proxy, with a priv-value of "session", "header", or "history", the proxy MUST remove the History-Info header (i.e., all hi-entries) prior to forwarding.
o Если ответ пересылается к Request-URI, связанному с доменом, за который прокси не отвечает, и в запросе, полученном прокси, присутствовал заголовок Privacy с priv-value «session», «header» или «history», прокси ДОЛЖЕН удалить заголовок History-Info (то есть все hi-entry) перед пересылкой.
o If a request is being forwarded to a Request-URI associated with a domain for which the proxy is not responsible and local policy requires privacy associated with any or all hi-entry(s) it has added, any hi-entry with a priv-value of "history" MUST be removed prior to forwarding.
o Если запрос пересылается к Request-URI, связанному с доменом, за который прокси не отвечает, и локальная политика требует конфиденциальности для любой или всех добавленных им hi-entry, любая hi-entry с priv-value «history» ДОЛЖНА быть удалена перед пересылкой.
o If a proxy receives a response from another intermediary associated with a domain for which it is responsible, including hi-entry(s) with privacy headers, and that response is to be forwarded to a domain for which it is not responsible, then those hi-entry(s) MUST be removed.
o Если прокси получает ответ от другого посредника, связанного с доменом, за который он отвечает, включающий hi-entry с заголовками конфиденциальности, и этот ответ должен быть переслан в домен, за который он не отвечает, то эти hi-entry ДОЛЖНЫ быть удалены.
The processing of History-Info in responses follows the methodology described in Section 16.7 of [RFC3261], with the processing of History-Info headers adding an additional step, just before Step 9, "Forwarding the Response".
Обработка History-Info в ответах следует методологии, описанной в разделе 16.7 [RFC3261], причём обработка заголовков History-Info добавляет дополнительный шаг непосредственно перед шагом 9 «Пересылка ответа».
4.3.4. Redirect Server Behavior
4.3.4. Поведение сервера перенаправления
A redirect server SHOULD NOT add any new History-Info, as that would be done by the entity receiving the 3xx response. However, a redirect server MAY include History-Info in responses by adding any History-Info headers received in a request to a subsequent response.
Сервер перенаправления НЕ ДОЛЖЕН добавлять новый History-Info, поскольку это сделал бы субъект, получающий ответ 3xx. Однако сервер перенаправления МОЖЕТ включать History-Info в ответы, добавляя любые заголовки History-Info, полученные в запросе, в последующий ответ.
4.4. Security for History-Info
4.4. Безопасность History-Info
As discussed in Section 3, the security requirements are met by recommending the use of TLS (a basic SIP requirement per [RFC3261]) for hop-by-hop security. If TLS is not available on the connection over which a request containing a History-Info header is being forwarded, then either of the following two options MUST be implemented: o The History-Info header MUST be removed prior to forwarding the request, or o The request MUST be redirected, including the History-Info header in the response, to allow the UAC to securely issue the request, including the History-Info header.
Как обсуждалось в разделе 3, требования безопасности выполняются путём рекомендации использовать TLS (базовое требование SIP согласно [RFC3261]) для безопасности между переходами. Если TLS недоступен для соединения, по которому пересылается запрос, содержащий заголовок History-Info, то ДОЛЖЕН быть реализован один из следующих двух вариантов: o Заголовок History-Info ДОЛЖЕН быть удалён перед пересылкой запроса, или o Запрос ДОЛЖЕН быть перенаправлен с включением заголовка History-Info в ответ, чтобы UAC мог безопасно выдать запрос, включая заголовок History-Info.

This scenario highlights an example where the History-Info in the response is primarily of use in not retrying routes that have already been tried by another proxy. Note that this is just an example and that there may be valid reasons why a Proxy would want to retry the routes, and thus, this would likely be a local proxy or even user- specific policy.
Этот сценарий иллюстрирует пример, в котором History-Info в ответе полезен прежде всего для того, чтобы не повторять маршруты, уже испробованные другим прокси. UA1 sends a call to Bob to proxy 1. Proxy 1 forwards the request to Proxy 2. Proxy 2 sends the requests in parallel and tries several places (UA2, UA3, and UA4) before sending a response to Proxy 1 that all the places are busy. 5. Application Considerations
5. Вопросы применения
As seen by the example scenarios in the appendix, History-Info provides a very flexible building block that can be used by intermediaries and UAs for a variety of services. As such, any services making use of History-Info must be designed with the following considerations:
Как видно из примеров сценариев в приложении, History-Info предоставляет очень гибкий строительный блок, который может использоваться посредниками и UA для самых разных служб. Как таковые, любые службы, использующие History-Info, должны проектироваться с учётом следующих соображений:
1) History-Info is optional; thus, a service MUST define default behavior for requests and responses not containing History-Info headers.
1) History-Info необязателен; таким образом, служба ДОЛЖНА определить поведение по умолчанию для запросов и ответов, не содержащих заголовков History-Info.
2) History-Info may be impacted by privacy considerations. Applications requiring History-Info need to be aware that if Header-, Session-, or History-level privacy is requested by a UA (or imposed by an intermediary) that History-Info may not be available in a request or response. This would be addressed by an application in the same manner as the previous consideration by ensuring there is reasonable default behavior should the information not be available.
2) На History-Info могут влиять соображения конфиденциальности. Приложениям, требующим History-Info, нужно учитывать, что если UA запросил конфиденциальность уровня Header, Session или History (или она навязана посредником), то History-Info может отсутствовать в запросе или ответе. Приложение учло бы это тем же способом, что и предыдущее соображение, обеспечив разумное поведение по умолчанию на случай недоступности информации.
3) History-Info may be impacted by local policy. Each application making use of the History-Info header SHOULD address the impacts of the local policies on the specific application (e.g., what specification of local policy is optimally required for a specific application and any potential limitations imposed by local policy decisions). Note that this is related to the optionality and privacy considerations identified in 1 and 2 above, but goes beyond that. For example, due to the optionality and privacy considerations, an entity may receive only partial History-Info entries; will this suffice? Note that this would be a limitation for debugging purposes, but might be perfectly satisfactory for some models whereby only the information from a specific intermediary is required.
3) На History-Info может влиять локальная политика. Каждому приложению, использующему заголовок History-Info, СЛЕДУЕТ учитывать влияние локальных политик на конкретное приложение (например, какая спецификация локальной политики оптимально требуется для конкретного приложения и какие потенциальные ограничения накладывают решения локальной политики). Отметим, что это связано с соображениями необязательности и конфиденциальности, указанными в пунктах 1 и 2 выше, но выходит за их пределы. Например, из-за соображений необязательности и конфиденциальности субъект может получить лишь частичные записи History-Info; будет ли этого достаточно? Отметим, что это было бы ограничением для целей отладки, но может быть вполне приемлемо для некоторых моделей, в которых требуется информация только от конкретного посредника.
4) The security associated with the History-Info header requires the use of TLS. In the case of TLS not being available for a connection over which a request is being forwarded, the History- Info header may be removed from a request. The impact of lack of having the information depends upon the nature of the specific application (e.g., Is the information something that appears on a display or is it processed by automata which could have negative impacts on the subsequent processing of a request?). It is suggested that the impact of an intermediary not supporting the security recommendations should be evaluated by the application to ensure that the impacts have been sufficiently addressed by the application.
4) Безопасность, связанная с заголовком History-Info, требует использования TLS. В случае, когда TLS недоступен для соединения, по которому пересылается запрос, заголовок History-Info может быть удалён из запроса. Влияние отсутствия информации зависит от характера конкретного приложения (например, является ли информация чем-то, что отображается на экране, или она обрабатывается автоматами, что могло бы негативно повлиять на последующую обработку запроса?). Предлагается, чтобы влияние неподдержки посредником рекомендаций по безопасности было оценено приложением, чтобы гарантировать, что приложение в достаточной мере учло это влияние.

6. Вопросы безопасности

Appendix C. Automatic Call Distribution Example
Приложение C. Пример автоматического распределения вызовов
This scenario highlights an example of an Automatic Call Distribution service, where the agents are divided into groups based upon the type of customers they handle. In this example, the Gold customers are given higher priority than Silver customers, so a Gold call would get serviced even if all the agents servicing the Gold group (ACDGRP1) were busy, by retargeting the request to the Silver Group. Upon receipt of the call at the agent assigned to handle the incoming call, based upon the History-Info header in the message, the application at the agent can provide an indication that this is a Gold call, from how many groups it might have overflowed before reaching the agent, etc. and thus can be handled appropriately by the agent.
Этот сценарий иллюстрирует пример службы автоматического распределения вызовов, в которой агенты разделены на группы по типу клиентов, которых они обслуживают. В этом примере клиентам уровня Gold предоставляется более высокий приоритет, чем клиентам уровня Silver, поэтому вызов Gold был бы обслужен даже в том случае, если все агенты, обслуживающие группу Gold (ACDGRP1), были заняты, путём перенацеливания запроса в группу Silver. Получив вызов у агента, назначенного для обработки входящего вызова, на основе заголовка History-Info в сообщении приложение у агента может предоставить указание на то, что это вызов Gold, из скольких групп он, возможно, переполнялся, прежде чем достиг агента, и т. д., и, таким образом, агент может обработать его надлежащим образом.
For scenarios whereby calls might overflow from the Silver to the Gold, clearly the alternate group identification, internal routing, or actual agent that handles the call SHOULD not be sent to UA1. Thus, for this scenario, one would expect that the Proxy would not support the sending of the History-Info in the response, even if requested by the calling UA.
В сценариях, где вызовы могут переполняться из Silver в Gold, очевидно, что идентификация альтернативной группы, внутренняя маршрутизация или фактический агент, обрабатывающий вызов, НЕ ДОЛЖНЫ отправляться в UA1. Таким образом, для этого сценария следовало бы ожидать, что прокси не будет поддерживать отправку History-Info в ответе, даже если это запрошено вызывающим UA.
As with the other examples, this is not prescriptive of how one would do this type of service but an example of a subset of processing that might be associated with such a service. In addition, this example is not addressing any aspects of Agent availability, which might also be done via a SIP interface.
Как и в других примерах, это не предписывает, как именно реализовывать такой тип службы, а является примером подмножества обработки, которое может быть связано с такой службой. Кроме того, этот пример не рассматривает какие-либо аспекты доступности агентов, что также могло бы выполняться через интерфейс SIP.

Appendix D. Session via Redirect and Proxy Servers
Приложение D. Сессия через серверы перенаправления и прокси
In this scenario, Alice places a call to Bob using first a Redirect server then a Proxy Server. The INVITE message is first sent to the Redirect Server. The Server returns a 302 Moved Temporarily response (F2) containing a Contact header with Bob's current SIP address. Alice then generates a new INVITE with Bob's current SIP address included in another History-Info entry. The INVITE is then sent to Bob via the Proxy Server, with Bob receiving the complete History information; the call then proceeds normally. The complete call flow for this scenario, without the use of History-Info, is described in Section 3.6 of the SIP Basic Call Flow Examples [RFC3665].
В этом сценарии Alice размещает вызов Бобу, используя сначала сервер перенаправления, а затем прокси-сервер. Сообщение INVITE сначала отправляется на сервер перенаправления. Сервер возвращает ответ 302 Moved Temporarily (F2), содержащий заголовок Contact с текущим SIP-адресом Боба. Затем Alice создаёт новый INVITE с текущим SIP-адресом Боба, включённым в другую запись History-Info. Затем INVITE отправляется Бобу через прокси-сервер, причём Боб получает полную информацию об истории; далее вызов протекает обычным образом. Полный поток вызовов для этого сценария без использования History-Info описан в разделе 3.6 «Примеров базовых потоков вызовов SIP» [RFC3665].
