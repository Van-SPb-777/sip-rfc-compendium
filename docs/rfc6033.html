Algorithms for Cryptographic Message Syntax (CMS) Encrypted Key Package Content Type
Алгоритмы для типа содержимого «зашифрованный пакет ключей» в синтаксисе криптографических сообщений (CMS)
Abstract
Аннотация
This document describes the conventions for using several cryptographic algorithms with the Cryptographic Message Syntax (CMS) encrypted key package content type. Specifically, it includes conventions necessary to implement EnvelopedData, EncryptedData, and AuthEnvelopedData.
В настоящем документе описаны соглашения об использовании нескольких криптографических алгоритмов с типом содержимого «зашифрованный пакет ключей» в синтаксисе криптографических сообщений (CMS). В частности, он включает соглашения, необходимые для реализации EnvelopedData, EncryptedData и AuthEnvelopedData.

1. Introduction
1. Введение
This document describes the conventions for using several cryptographic algorithms with the Cryptographic Message Syntax (CMS) encrypted key package content type [RFC6032]. Specifically, it includes conventions necessary to implement the following CMS content types: EnvelopedData [RFC5652], EncryptedData [RFC5652], and AuthEnvelopedData [RFC5083].
В настоящем документе описаны соглашения об использовании нескольких криптографических алгоритмов с типом содержимого «зашифрованный пакет ключей» в синтаксисе криптографических сообщений (CMS) [RFC6032]. В частности, он включает соглашения, необходимые для реализации следующих типов содержимого CMS: EnvelopedData [RFC5652], EncryptedData [RFC5652] и AuthEnvelopedData [RFC5083].
This document does not define any new algorithms; instead, it refers to previously defined algorithms.
Настоящий документ не определяет новых алгоритмов; вместо этого он ссылается на ранее определённые алгоритмы.

2. EnvelopedData
2. EnvelopedData
EnvelopedData [RFC5652] supports a number of key management techniques. Implementations that claim conformance to this document MUST support the key transport mechanisms and SHOULD support the key agreement mechanisms as defined below. Other techniques MAY be supported.
EnvelopedData [RFC5652] поддерживает ряд методов управления ключами. Реализации, заявляющие о соответствии настоящему документу, ОБЯЗАНЫ поддерживать механизмы транспортировки ключей и ДОЛЖНЫ поддерживать механизмы согласования ключей, определённые ниже. Прочие методы МОГУТ поддерживаться.
When key transport is used, RSA encryption [RFC3370] MUST be supported and RSA Encryption Scheme - Optimal Asymmetric Encryption Padding (RSAES-OAEP) [RFC3560] SHOULD be supported.
При использовании транспортировки ключей ДОЛЖНО поддерживаться шифрование RSA [RFC3370], а также ДОЛЖНА поддерживаться схема RSA Encryption Scheme - Optimal Asymmetric Encryption Padding (RSAES-OAEP) [RFC3560].
When key agreement is used, Ephemeral-Static Diffie-Hellman (DH) [RFC3370] MUST be supported.
При использовании согласования ключей ДОЛЖЕН поддерживаться алгоритм Ephemeral-Static Diffie-Hellman (DH) [RFC3370].
Since the content type is used to carry a cryptographic key and its attributes, an algorithm that is traditionally used to encrypt one key with another is employed. Regardless of the key management technique choice, implementations MUST support AES-128 Key Wrap with Padding [RFC5649] as the content-encryption algorithm. Implementations SHOULD support AES-256 Key Wrap with Padding [RFC5649] as the content-encryption algorithm.
Поскольку данный тип содержимого используется для переноса криптографического ключа и его атрибутов, применяется алгоритм, традиционно используемый для шифрования одного ключа другим. Независимо от выбора метода управления ключами реализации ОБЯЗАНЫ поддерживать AES-128 Key Wrap with Padding [RFC5649] в качестве алгоритма шифрования содержимого. Реализации ДОЛЖНЫ поддерживать AES-256 Key Wrap with Padding [RFC5649] в качестве алгоритма шифрования содержимого.
When key agreement is used, a key wrap algorithm is also specified to wrap the content-encryption key. If the content-encryption algorithm is AES-128 Key Wrap with Padding, then the key wrap algorithm MUST be AES-128 Key Wrap with Padding [RFC5649]. If the content-encryption algorithm is AES-256 Key Wrap with Padding, then the key wrap algorithm MUST be AES-256 Key Wrap with Padding [RFC5649].
При использовании согласования ключей также задаётся алгоритм обёртки ключа, применяемый к ключу шифрования содержимого. Если алгоритмом шифрования содержимого является AES-128 Key Wrap with Padding, то алгоритмом обёртки ключа ОБЯЗАН быть AES-128 Key Wrap with Padding [RFC5649]. Если алгоритмом шифрования содержимого является AES-256 Key Wrap with Padding, то алгоритмом обёртки ключа ОБЯЗАН быть AES-256 Key Wrap with Padding [RFC5649].
3. EncryptedData
3. EncryptedData
EncryptedData [RFC5652] requires that keys be managed by other means; therefore, the only algorithm specified is the content-encryption algorithm. Since the content type is used to carry a cryptographic key and its attributes, an algorithm that is traditionally used to encrypt one key with another is employed. Implementations MUST support AES-128 Key Wrap with Padding [RFC5649]. Implementations SHOULD support AES-256 Key Wrap with Padding [RFC5649].
EncryptedData [RFC5652] требует, чтобы ключи управлялись другими средствами; поэтому задаётся только алгоритм шифрования содержимого. Поскольку данный тип содержимого используется для переноса криптографического ключа и его атрибутов, применяется алгоритм, традиционно используемый для шифрования одного ключа другим. Реализации ОБЯЗАНЫ поддерживать AES-128 Key Wrap with Padding [RFC5649]. Реализации ДОЛЖНЫ поддерживать AES-256 Key Wrap with Padding [RFC5649].
4. AuthEnvelopedData
4. AuthEnvelopedData
AuthEnvelopedData [RFC5083], like EnvelopedData, supports a number of key management techniques. The key management requirements for AuthEnvelopedData are the same as for EnvelopedData. The difference is the content-encryption algorithm. Implementations MUST support 128-bit AES-Galois/Counter Mode (AES-GCM) [RFC5084] and SHOULD support 256-bit AES-GCM [RFC5084]. Implementations MAY also support AES-Counter with CBC-MAC (AES-CCM) [RFC5084].
AuthEnvelopedData [RFC5083], как и EnvelopedData, поддерживает ряд методов управления ключами. Требования к управлению ключами для AuthEnvelopedData такие же, как для EnvelopedData. Отличие состоит в алгоритме шифрования содержимого. Реализации ОБЯЗАНЫ поддерживать 128-битный AES-Galois/Counter Mode (AES-GCM) [RFC5084] и ДОЛЖНЫ поддерживать 256-битный AES-GCM [RFC5084]. Реализации МОГУТ также поддерживать AES-Counter with CBC-MAC (AES-CCM) [RFC5084].
5. Signed Data
5. Подписанные данные
Implementations of SignedData [RFC5652] MUST support the signature scheme RSA [RFC3370] [RFC5754] and SHOULD support the signature schemes RSA Probabilistic Signature Scheme (RSASSA-PSS) [RFC4056] and Digital Signature Algorithm (DSA) [RFC3370] [RFC5754]. Additionally, implementations MUST support in concert with these signature schemes the hash function SHA-256 [RFC5754] and it SHOULD support the hash function SHA-1 [RFC3370].
Реализации SignedData [RFC5652] ОБЯЗАНЫ поддерживать схему подписи RSA [RFC3370] [RFC5754] и ДОЛЖНЫ поддерживать схемы подписи RSA Probabilistic Signature Scheme (RSASSA-PSS) [RFC4056] и Digital Signature Algorithm (DSA) [RFC3370] [RFC5754]. Кроме того, реализации ОБЯЗАНЫ поддерживать совместно с этими схемами подписи хеш-функцию SHA-256 [RFC5754], а также ДОЛЖНЫ поддерживать хеш-функцию SHA-1 [RFC3370].
6. Public Key Sizes
6. Длины открытых ключей
The easiest way to implement SignedData, EnvelopedData, and AuthEnvelopedData is with public key certificates [RFC5280]. If an implementation supports RSA, RSAES-OAEP, DH, RSASSA-PSS, or DSA, then it MUST support key lengths from 1024 bits to 2048 bits, inclusive.
Проще всего реализовать SignedData, EnvelopedData и AuthEnvelopedData с помощью сертификатов открытых ключей [RFC5280]. Если реализация поддерживает RSA, RSAES-OAEP, DH, RSASSA-PSS или DSA, то она ОБЯЗАНА поддерживать длины ключей от 1024 до 2048 бит включительно.
7. Security Considerations
7. Вопросы безопасности
The security considerations from [RFC3370], [RFC3560], [RFC4056], [RFC5083], [RFC5084], [RFC5649], [RFC5652], [RFC5754], and [RFC6032] apply.
Применяются вопросы безопасности из [RFC3370], [RFC3560], [RFC4056], [RFC5083], [RFC5084], [RFC5649], [RFC5652], [RFC5754] и [RFC6032].
The choice of content-encryption algorithms for this document was based on [RFC5649]: "In the design of some high assurance cryptographic modules, it is desirable to segregate cryptographic keying material from other data. The use of a specific cryptographic mechanism solely for the protection of cryptographic keying material can assist in this goal". Unfortunately, there is no AES-GCM or AES-CCM mode that provides the same properties. If an AES-GCM and AES-CCM mode that provides the same properties is defined, then this document will be updated to adopt that algorithm.
Выбор алгоритмов шифрования содержимого для настоящего документа был основан на [RFC5649]: «При проектировании некоторых криптографических модулей с высокими гарантиями желательно отделять криптографический ключевой материал от других данных. Использование специального криптографического механизма исключительно для защиты криптографического ключевого материала может способствовать достижению этой цели». К сожалению, не существует режима AES-GCM или AES-CCM, обеспечивающего те же свойства. Если будет определён режим AES-GCM и AES-CCM, обеспечивающий те же свойства, то настоящий документ будет обновлён для принятия этого алгоритма.
[SP800-57] provides comparable bits of security for some algorithms and key sizes. [SP800-57] also provides time frames during which certain numbers of bits of security are appropriate, and some environments may find these time frames useful.
[SP800-57] приводит сопоставимое число бит стойкости для некоторых алгоритмов и размеров ключей. [SP800-57] также приводит временные рамки, в течение которых уместны определённые значения бит стойкости, и в некоторых средах эти временные рамки могут оказаться полезными.
