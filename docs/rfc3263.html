Abstract
Аннотация
The Session Initiation Protocol (SIP) uses DNS procedures to allow a client to resolve a SIP Uniform Resource Identifier (URI) into the IP address, port, and transport protocol of the next hop to contact. It also uses DNS to allow a server to send a response to a backup client if the primary client has failed. This document describes those DNS procedures in detail.
Протокол инициирования сессий (SIP) использует процедуры DNS, позволяющие клиенту разрешить универсальный идентификатор ресурса SIP (URI) в IP-адрес, порт и транспортный протокол следующего перехода, с которым нужно связаться. Он также использует DNS, чтобы позволить серверу отправить ответ резервному клиенту, если первичный клиент отказал. Настоящий документ подробно описывает эти процедуры DNS.
1. Introduction
1. Введение
The Session Initiation Protocol (SIP) (RFC 3261 [1]) is a client- server protocol used for the initiation and management of communications sessions between users. SIP end systems are called user agents, and intermediate elements are known as proxy servers. A typical SIP configuration, referred to as the SIP "trapezoid", is shown in Figure 1. In this diagram, a caller in domain A (UA1) wishes to call Joe in domain B (joe@B). To do so, it communicates with proxy 1 in its domain (domain A). Proxy 1 forwards the request to the proxy for the domain of the called party (domain B), which is proxy 2. Proxy 2 forwards the call to the called party, UA 2.
Протокол инициирования сессий (SIP) (RFC 3261 [1]) — это протокол «клиент-сервер», используемый для инициирования и управления сессиями связи между пользователями. Конечные системы SIP называются пользовательскими агентами, а промежуточные элементы — прокси-серверами. Типичная конфигурация SIP, называемая «трапецией» SIP, показана на рисунке 1. На этой диаграмме вызывающий в домене A (UA1) желает позвонить Joe в домене B (joe@B). Для этого он связывается с прокси 1 своего домена (домен A). Прокси 1 пересылает запрос прокси домена вызываемой стороны (домен B), которым является прокси 2. Прокси 2 пересылает вызов вызываемой стороне, UA 2.
As part of this call flow, proxy 1 needs to determine a SIP server for domain B. To do this, proxy 1 makes use of DNS procedures, using both SRV [2] and NAPTR [3] records. This document describes the specific problems that SIP uses DNS to help solve, and provides a solution.
В рамках этого потока вызовов прокси 1 должен определить SIP-сервер для домена B. Для этого прокси 1 использует процедуры DNS, задействуя записи как SRV [2], так и NAPTR [3]. Настоящий документ описывает конкретные задачи, которые SIP решает с помощью DNS, и предоставляет решение.
2. Problems DNS is Needed to Solve
2. Задачи, которые должен решать DNS
DNS is needed to help solve two aspects of the general call flow described in the Introduction. The first is for proxy 1 to discover the SIP server in domain B, in order to forward the call for joe@B. The second is for proxy 2 to identify a backup for proxy 1 in the event it fails after forwarding the request.
DNS необходим для решения двух аспектов общего потока вызовов, описанного во введении. Первый — прокси 1 должен обнаружить SIP-сервер в домене B, чтобы переслать вызов для joe@B. Второй — прокси 2 должен определить резерв для прокси 1 в случае его отказа после пересылки запроса.
For the first aspect, proxy 1 specifically needs to determine the IP address, port, and transport protocol for the server in domain B. The choice of transport protocol is particularly noteworthy. Unlike many other protocols, SIP can run over a variety of transport protocols, including TCP, UDP, and SCTP. SIP can also use TLS. Currently, use of TLS is defined for TCP only. Thus, clients need to be able to automatically determine which transport protocols are available. The proxy sending the request has a particular set of transport protocols it supports and a preference for using those transport protocols. Proxy 2 has its own set of transport protocols it supports, and relative preferences for those transport protocols. All proxies must implement both UDP and TCP, along with TLS over TCP, so that there is always an intersection of capabilities. Some form of DNS procedures are needed for proxy 1 to discover the available transport protocols for SIP services at domain B, and the relative preferences of those transport protocols. Proxy 1 intersects its list of supported transport protocols with those of proxy 2 and then chooses the protocol preferred by proxy 2.

It is important to note that DNS lookups can be used multiple times throughout the processing of a call. In general, an element that wishes to send a request (called a client) may need to perform DNS processing to determine the IP address, port, and transport protocol of a next hop element, called a server (it can be a proxy or a user agent). Such processing could, in principle, occur at every hop between elements.
Важно отметить, что DNS-запросы могут использоваться многократно в течение обработки вызова. В общем случае элемент, желающий отправить запрос (называемый клиентом), может нуждаться в обработке DNS для определения IP-адреса, порта и транспортного протокола элемента следующего перехода, называемого сервером (это может быть прокси или пользовательский агент). Такая обработка в принципе могла бы происходить на каждом переходе между элементами.
Since SIP is used for the establishment of interactive communications services, the time it takes to complete a transaction between a caller and called party is important. Typically, the time from when the caller initiates a call until the time the called party is alerted should be no more than a few seconds. Given that there can be multiple hops, each of which is doing DNS lookups in addition to other potentially time-intensive operations, the amount of time available for DNS lookups at each hop is limited.
Поскольку SIP используется для установления интерактивных служб связи, время, необходимое для завершения транзакции между вызывающим и вызываемой стороной, важно. Как правило, время от момента, когда вызывающий инициирует вызов, до момента, когда вызываемая сторона получает оповещение, не должно превышать нескольких секунд. Учитывая, что может быть несколько переходов, каждый из которых выполняет DNS-запросы в дополнение к другим потенциально длительным операциям, время, доступное для DNS-запросов на каждом переходе, ограничено.
Scalability and high availability are important in SIP. SIP services scale up through clustering techniques. Typically, in a realistic version of the network in Figure 1, proxy 2 would be a cluster of homogeneously configured proxies. DNS needs to provide the ability for domain B to configure a set of servers, along with prioritization and weights, in order to provide a crude level of capacity-based load balancing.
Масштабируемость и высокая доступность важны в SIP. Службы SIP масштабируются посредством методов кластеризации. Как правило, в реалистичной версии сети на рисунке 1 прокси 2 был бы кластером однородно сконфигурированных прокси. DNS должен обеспечивать возможность домену B настраивать набор серверов вместе с приоритизацией и весами, чтобы обеспечить грубый уровень балансировки нагрузки на основе ёмкости.
SIP assures high availability by having upstream elements detect failures. For example, assume that proxy 2 is implemented as a cluster of two proxies, proxy 2.1 and proxy 2.2. If proxy 1 sends a request to proxy 2.1 and the request fails, it retries the request by sending it to proxy 2.2. In many cases, proxy 1 will not know which domains it will ultimately communicate with. That information would be known when a user actually makes a call to another user in that domain. Proxy 1 may never communicate with that domain again after the call completes. Proxy 1 may communicate with thousands of different domains within a few minutes, and proxy 2 could receive requests from thousands of different domains within a few minutes. Because of this "many-to-many" relationship, and the possibly long intervals between communications between a pair of domains, it is not generally possible for an element to maintain dynamic availability state for the proxies it will communicate with. When a proxy gets its first call with a particular domain, it will try the servers in that domain in some order until it finds one that is available. The identity of the available server would ideally be cached for some amount of time in order to reduce call setup delays of subsequent calls. The client cannot query a failed server continuously to determine when it becomes available again, since this does not scale.
SIP обеспечивает высокую доступность за счёт того, что вышестоящие элементы обнаруживают отказы. Например, предположим, что прокси 2 реализован как кластер из двух прокси, прокси 2.1 и прокси 2.2. Если прокси 1 отправляет запрос прокси 2.1 и запрос завершается неудачей, он повторяет запрос, отправляя его прокси 2.2. Во многих случаях прокси 1 не будет знать, с какими доменами он в конечном счёте будет взаимодействовать. Эта информация была бы известна, когда пользователь действительно совершает вызов другому пользователю в этом домене. Прокси 1 может больше никогда не связываться с этим доменом после завершения вызова. За несколько минут прокси 1 может связаться с тысячами разных доменов, а прокси 2 может получать запросы от тысяч разных доменов за несколько минут. Из-за этих отношений «многие ко многим» и возможно длительных интервалов между взаимодействиями пары доменов элемент обычно не может поддерживать динамическое состояние доступности для прокси, с которыми он будет взаимодействовать. Когда прокси получает первый вызов для конкретного домена, он пробует серверы в этом домене в некотором порядке, пока не найдёт доступный. Идентичность доступного сервера в идеале кэшировалась бы на некоторое время, чтобы сократить задержки установления соединения для последующих вызовов. Клиент не может непрерывно опрашивать отказавший сервер, чтобы определить, когда тот снова станет доступен, поскольку это не масштабируется.
Furthermore, the availability state must eventually be flushed in order to redistribute load to recovered elements when they come back online.
Более того, состояние доступности должно в конечном счёте очищаться, чтобы перераспределить нагрузку на восстановившиеся элементы, когда они снова заработают.
It is possible for elements to fail in the middle of a transaction. For example, after proxy 2 forwards the request to UA 2, proxy 1 fails. UA 2 sends its response to proxy 2, which tries to forward it to proxy 1, which is no longer available. The second aspect of the flow in the introduction for which DNS is needed, is for proxy 2 to identify a backup for proxy 1 that it can send the response to. This problem is more realistic in SIP than it is in other transactional protocols. The reason is that some SIP responses can take a long time to be generated, because a human user frequently needs to be consulted in order to generate that response. As such, it is not uncommon for tens of seconds to elapse between a call request and its acceptance.
Элементы могут отказать в середине транзакции. Например, после того как прокси 2 переслал запрос UA 2, прокси 1 отказывает. UA 2 отправляет свой ответ прокси 2, который пытается переслать его прокси 1, который больше недоступен. Второй аспект потока во введении, для которого нужен DNS, — прокси 2 должен определить резерв для прокси 1, которому он может отправить ответ. Эта задача более реалистична в SIP, чем в других транзакционных протоколах. Причина в том, что некоторые ответы SIP могут генерироваться долго, поскольку для генерации такого ответа часто нужно проконсультироваться с человеком-пользователем. Как таковое, нередки десятки секунд между запросом на вызов и его принятием.

4. Client Usage
4. Использование клиентом
Usage of DNS differs for clients and for servers. This section discusses client usage. We assume that the client is stateful (either a User Agent Client (UAC) or a stateful proxy). Stateless proxies are discussed in Section 4.4.
Использование DNS различается для клиентов и для серверов. В этом разделе рассматривается использование клиентом. Мы предполагаем, что клиент поддерживает состояние (это либо пользовательский агент-клиент (UAC), либо прокси с сохранением состояния). Прокси без сохранения состояния рассматриваются в разделе 4.4.
The procedures here are invoked when a client needs to send a request to a resource identified by a SIP or SIPS (secure SIP) URI. This URI can identify the desired resource to which the request is targeted (in which case, the URI is found in the Request-URI), or it can identify an intermediate hop towards that resource (in which case, the URI is found in the Route header). The procedures defined here in no way affect this URI (i.e., the URI is not rewritten with the result of the DNS lookup), they only result in an IP address, port and transport protocol where the request can be sent. RFC 3261 [1] provides guidelines on determining which URI needs to be resolved in DNS to determine the host that the request needs to be sent to. In some cases, also documented in [1], the request can be sent to a specific intermediate proxy not identified by a SIP URI, but rather, by a hostname or numeric IP address. In that case, a temporary URI, used for purposes of this specification, is constructed. That URI is of the form sip:<proxy>, where <proxy> is the FQDN or numeric IP address of the next-hop proxy. As a result, in all cases, the problem boils down to resolution of a SIP or SIPS URI in DNS to determine the IP address, port, and transport of the host to which the request is to be sent.
Описанные здесь процедуры применяются, когда клиенту нужно отправить запрос ресурсу, идентифицированному URI SIP или SIPS (безопасный SIP). Этот URI может идентифицировать нужный ресурс, на который нацелен запрос (в этом случае URI находится в Request-URI), либо может идентифицировать промежуточный узел на пути к этому ресурсу (в этом случае URI находится в заголовке Route). Определённые здесь процедуры никоим образом не изменяют этот URI (то есть URI не перезаписывается результатом DNS-запроса); они лишь дают IP-адрес, порт и транспортный протокол, по которым запрос может быть отправлен. RFC 3261 [1] содержит руководящие принципы определения того, какой URI нужно разрешить в DNS, чтобы определить хост, которому следует отправить запрос. В некоторых случаях, также описанных в [1], запрос может быть отправлен конкретному промежуточному прокси, идентифицированному не посредством URI SIP, а посредством имени хоста или числового IP-адреса. В этом случае для целей настоящей спецификации конструируется временный URI. Этот URI имеет вид sip:<proxy>, где <proxy> — FQDN или числовой IP-адрес прокси следующего перехода. Таким образом, во всех случаях задача сводится к разрешению URI SIP или SIPS в DNS для определения IP-адреса, порта и транспорта хоста, которому следует отправить запрос.
The procedures here MUST be done exactly once per transaction, where transaction is as defined in [1]. That is, once a SIP server has successfully been contacted (success is defined below), all retransmissions of the SIP request and the ACK for non-2xx SIP responses to INVITE MUST be sent to the same host. Furthermore, a CANCEL for a particular SIP request MUST be sent to the same SIP server that the SIP request was delivered to.
Описанные здесь процедуры ДОЛЖНЫ выполняться ровно один раз на транзакцию, где транзакция определена в [1]. То есть как только SIP-сервер был успешно опрошен (успех определяется ниже), все повторные передачи SIP-запроса и ACK для не-2xx SIP-ответов на INVITE ДОЛЖНЫ отправляться тому же хосту. Более того, CANCEL для конкретного SIP-запроса ДОЛЖЕН отправляться тому же SIP-серверу, которому был доставлен SIP-запрос.
Because the ACK request for 2xx responses to INVITE constitutes a different transaction, there is no requirement that it be delivered to the same server that received the original request (indeed, if that server did not record-route, it will not get the ACK). We define TARGET as the value of the maddr parameter of the URI, if present, otherwise, the host value of the hostport component of the URI. It identifies the domain to be contacted. A description of the SIP and SIPS URIs and a definition of these parameters can be found in [1].
Поскольку запрос ACK для 2xx-ответов на INVITE образует отдельную транзакцию, нет требования, чтобы он доставлялся тому же серверу, который получил исходный запрос (более того, если этот сервер не выполнял record-route, он не получит ACK). Мы определяем TARGET как значение параметра maddr URI, если он присутствует, иначе — значение хоста из компонента hostport URI. Он идентифицирует домен, с которым нужно связаться. Описание URI SIP и SIPS и определение этих параметров можно найти в [1].
We determine the transport protocol, port and IP address of a suitable instance of TARGET in Sections 4.1 and 4.2.
Мы определяем транспортный протокол, порт и IP-адрес подходящего экземпляра TARGET в разделах 4.1 и 4.2.
4.1. Selecting a Transport Protocol
4.1. Выбор транспортного протокола
First, the client selects a transport protocol.
Сначала клиент выбирает транспортный протокол.
If the URI specifies a transport protocol in the transport parameter, that transport protocol SHOULD be used.
Если URI задаёт транспортный протокол в параметре transport, этот транспортный протокол СЛЕДУЕТ использовать.
Otherwise, if no transport protocol is specified, but the TARGET is a numeric IP address, the client SHOULD use UDP for a SIP URI, and TCP for a SIPS URI. Similarly, if no transport protocol is specified, and the TARGET is not numeric, but an explicit port is provided, the client SHOULD use UDP for a SIP URI, and TCP for a SIPS URI. This is because UDP is the only mandatory transport in RFC 2543 [6], and thus the only one guaranteed to be interoperable for a SIP URI. It was also specified as the default transport in RFC 2543 when no transport was present in the SIP URI. However, another transport, such as TCP, MAY be used if the guidelines of SIP mandate it for this particular request. That is the case, for example, for requests that exceed the path MTU.
В противном случае, если транспортный протокол не задан, но TARGET является числовым IP-адресом, клиенту СЛЕДУЕТ использовать UDP для URI SIP и TCP для URI SIPS. Аналогично, если транспортный протокол не задан, а TARGET не является числовым, но указан явный порт, клиенту СЛЕДУЕТ использовать UDP для URI SIP и TCP для URI SIPS. Это потому, что UDP является единственным обязательным транспортом в RFC 2543 [6] и, следовательно, единственным, который гарантированно совместим для URI SIP. Он также был указан как транспорт по умолчанию в RFC 2543, когда в URI SIP транспорт не присутствовал. Однако другой транспорт, например TCP, МОЖЕТ использоваться, если того требуют для этого конкретного запроса руководящие принципы SIP. Так обстоит дело, например, с запросами, превышающими MTU пути.
Otherwise, if no transport protocol or port is specified, and the target is not a numeric IP address, the client SHOULD perform a NAPTR query for the domain in the URI. The services relevant for the task of transport protocol selection are those with NAPTR service fields with values "SIP+D2X" and "SIPS+D2X", where X is a letter that corresponds to a transport protocol supported by the domain. This specification defines D2U for UDP, D2T for TCP, and D2S for SCTP. We also establish an IANA registry for NAPTR service name to transport protocol mappings.
В противном случае, если не задан ни транспортный протокол, ни порт, а цель не является числовым IP-адресом, клиенту СЛЕДУЕТ выполнить запрос NAPTR для домена в URI. Услуги, относящиеся к задаче выбора транспортного протокола, — это те, у которых поля сервиса NAPTR имеют значения «SIP+D2X» и «SIPS+D2X», где X — буква, соответствующая транспортному протоколу, поддерживаемому доменом. Настоящая спецификация определяет D2U для UDP, D2T для TCP и D2S для SCTP. Мы также устанавливаем реестр IANA для отображения имён сервисов NAPTR в транспортные протоколы.
These NAPTR records provide a mapping from a domain to the SRV record for contacting a server with the specific transport protocol in the NAPTR services field. The resource record will contain an empty regular expression and a replacement value, which is the SRV record for that particular transport protocol. If the server supports multiple transport protocols, there will be multiple NAPTR records, each with a different service value. As per RFC 2915 [3], the client discards any records whose services fields are not applicable. For the purposes of this specification, several rules are defined. First, a client resolving a SIPS URI MUST discard any services that do not contain "SIPS" as the protocol in the service field. The converse is not true, however. A client resolving a SIP URI SHOULD retain records with "SIPS" as the protocol, if the client supports TLS. Second, a client MUST discard any service fields that identify a resolution service whose value is not "D2X", for values of X that indicate transport protocols supported by the client. The NAPTR processing as described in RFC 2915 will result in the discovery of the most preferred transport protocol of the server that is supported by the client, as well as an SRV record for the server. It will also allow the client to discover if TLS is available and its preference for its usage.
Эти записи NAPTR обеспечивают отображение домена в запись SRV для связи с сервером с конкретным транспортным протоколом в поле сервиса NAPTR. Запись ресурса будет содержать пустое регулярное выражение и значение замены, которое является записью SRV для этого конкретного транспортного протокола. Если сервер поддерживает несколько транспортных протоколов, будет несколько записей NAPTR, каждая со своим значением сервиса. Согласно RFC 2915 [3], клиент отбрасывает любые записи, поля сервиса которых неприменимы. Для целей настоящей спецификации определены несколько правил. Во-первых, клиент, разрешающий URI SIPS, ДОЛЖЕН отбросить любые услуги, которые не содержат «SIPS» в качестве протокола в поле сервиса. Обратное неверно, однако. Клиент, разрешающий URI SIP, СЛЕДУЕТ сохранять записи с «SIPS» в качестве протокола, если клиент поддерживает TLS. Во-вторых, клиент ДОЛЖЕН отбросить любые поля сервиса, которые идентифицируют службу разрешения, значение которой не равно «D2X» для значений X, указывающих транспортные протоколы, поддерживаемые клиентом. Обработка NAPTR, как описано в RFC 2915, приведёт к обнаружению наиболее предпочтительного транспортного протокола сервера, который поддерживается клиентом, а также записи SRV для сервера. Это также позволит клиенту выяснить, доступен ли TLS и каково его предпочтение к использованию.

The records with SIPS as the protocol in the service field SHOULD be preferred (i.e., have a lower value of the order field) above records with SIP as the protocol in the service field. A record with a "SIPS+D2U" service field SHOULD NOT be placed into the DNS, since it is not possible to use TLS over UDP.
Если к SIP-прокси, серверу перенаправления или регистратору нужно обратиться через поиск записей NAPTR, ДОЛЖНО быть не менее трёх записей — одна с полем сервиса «SIP+D2T», одна с полем сервиса «SIP+D2U» и одна с полем сервиса «SIPS+D2T». Записи с SIPS в качестве протокола в поле сервиса СЛЕДУЕТ предпочитать (то есть они должны иметь меньшее значение поля order) записям с SIP в качестве протокола в поле сервиса. Запись с полем сервиса «SIPS+D2U» НЕ СЛЕДУЕТ размещать в DNS, поскольку использовать TLS поверх UDP невозможно.
It is not necessary for the domain suffixes in the NAPTR replacement field to match the domain of the original query (i.e., example.com above). However, for backwards compatibility with RFC 2543, a domain MUST maintain SRV records for the domain of the original query, even if the NAPTR record is in a different domain. As an example, even though the SRV record for TCP is _sip._tcp.school.edu, there MUST also be an SRV record at _sip._tcp.example.com. RFC 2543 will look up the SRV records for the domain directly. If these do not exist because the NAPTR replacement points to a different domain, the client will fail.
Не обязательно, чтобы суффиксы домена в поле замены NAPTR совпадали с доменом исходного запроса (то есть example.com выше). Однако для обратной совместимости с RFC 2543 домен ДОЛЖЕН поддерживать записи SRV для домена исходного запроса, даже если запись NAPTR находится в другом домене. Например, хотя запись SRV для TCP — это _sip._tcp.school.edu, ДОЛЖНА также существовать запись SRV для _sip._tcp.example.com. RFC 2543 будет искать записи SRV для домена напрямую. Если их нет, потому что поле замены NAPTR указывает на другой домен, клиент потерпит неудачу.
For NAPTR records with SIPS protocol fields, (if the server is using a site certificate), the domain name in the query and the domain name in the replacement field MUST both be valid based on the site certificate handed out by the server in the TLS exchange. Similarly, the domain name in the SRV query and the domain name in the target in the SRV record MUST both be valid based on the same site certificate. Otherwise, an attacker could modify the DNS records to contain replacement values in a different domain, and the client could not validate that this was the desired behavior or the result of an attack.
Для записей NAPTR с полями протокола SIPS (если сервер использует сертификат сайта) доменное имя в запросе и доменное имя в поле замены ДОЛЖНЫ оба быть действительными на основе сертификата сайта, выданного сервером при обмене TLS. Аналогично доменное имя в запросе SRV и доменное имя в поле Target записи SRV ДОЛЖНЫ оба быть действительными на основе того же сертификата сайта. В противном случае злоумышленник мог бы изменить записи DNS, чтобы они содержали значения замены в другом домене, и клиент не смог бы проверить, было ли это желаемым поведением или результатом атаки.
If no NAPTR records are found, the client constructs SRV queries for those transport protocols it supports, and does a query for each. Queries are done using the service identifier "_sip" for SIP URIs and "_sips" for SIPS URIs. A particular transport is supported if the query is successful. The client MAY use any transport protocol it desires which is supported by the server.
Если записи NAPTR не найдены, клиент формирует запросы SRV для тех транспортных протоколов, которые он поддерживает, и выполняет запрос для каждого. Запросы выполняются с использованием идентификатора службы «_sip» для URI SIP и «_sips» для URI SIPS. Конкретный транспорт поддерживается, если запрос успешен. Клиент МОЖЕТ использовать любой транспортный протокол, который он пожелает и который поддерживается сервером.
This is a change from RFC 2543. It specified that a client would lookup SRV records for all transports it supported, and merge the priority values across those records. Then, it would choose the most preferred record.
Это изменение относительно RFC 2543. В нём было указано, что клиент выполнял бы поиск записей SRV для всех поддерживаемых им транспортов и объединял значения приоритета по этим записям. Затем он выбирал бы наиболее предпочтительную запись.
If no SRV records are found, the client SHOULD use TCP for a SIPS URI, and UDP for a SIP URI. However, another transport protocol, such as TCP, MAY be used if the guidelines of SIP mandate it for this particular request. That is the case, for example, for requests that exceed the path MTU.
Если записи SRV не найдены, клиенту СЛЕДУЕТ использовать TCP для URI SIPS и UDP для URI SIP. Однако может использоваться и другой транспортный протокол, например TCP, если того требуют для этого конкретного запроса руководящие принципы SIP. Так обстоит дело, например, с запросами, превышающими MTU пути.
4.2. Determining Port and IP Address
4.2. Определение порта и IP-адреса
Once the transport protocol has been determined, the next step is to determine the IP address and port.
Как только транспортный протокол определён, следующим шагом является определение IP-адреса и порта.
If TARGET is a numeric IP address, the client uses that address. If the URI also contains a port, it uses that port. If no port is specified, it uses the default port for the particular transport protocol.
Если TARGET является числовым IP-адресом, клиент использует этот адрес. Если URI также содержит порт, он использует этот порт. Если порт не задан, он использует порт по умолчанию для конкретного транспортного протокола.
If the TARGET was not a numeric IP address, but a port is present in the URI, the client performs an A or AAAA record lookup of the domain name. The result will be a list of IP addresses, each of which can be contacted at the specific port from the URI and transport protocol determined previously. The client SHOULD try the first record. If an attempt should fail, based on the definition of failure in Section 4.3, the next SHOULD be tried, and if that should fail, the next SHOULD be tried, and so on.
Если TARGET не был числовым IP-адресом, но порт присутствует в URI, клиент выполняет поиск записи A или AAAA для доменного имени. Результатом будет список IP-адресов, к каждому из которых можно обратиться по конкретному порту из URI и транспортному протоколу, определённому ранее. Клиенту СЛЕДУЕТ попробовать первую запись. Если попытка должна потерпеть неудачу в соответствии с определением неудачи в разделе 4.3, СЛЕДУЕТ попробовать следующую, и если и она потерпит неудачу — следующую, и так далее.
This is a change from RFC 2543. Previously, if the port was explicit, but with a value of 5060, SRV records were used. Now, A or AAAA records will be used.
Это изменение относительно RFC 2543. Ранее, если порт был задан явно, но имел значение 5060, использовались записи SRV. Теперь используются записи A или AAAA.
If the TARGET was not a numeric IP address, and no port was present in the URI, the client performs an SRV query on the record returned from the NAPTR processing of Section 4.1, if such processing was performed. If it was not, because a transport was specified explicitly, the client performs an SRV query for that specific transport, using the service identifier "_sips" for SIPS URIs. For a SIP URI, if the client wishes to use TLS, it also uses the service identifier "_sips" for that specific transport, otherwise, it uses "_sip". If the NAPTR processing was not done because no NAPTR records were found, but an SRV query for a supported transport protocol was successful, those SRV records are selected. Irregardless of how the SRV records were determined, the procedures of RFC 2782, as described in the section titled "Usage rules" are followed, augmented by the additional procedures of Section 4.3 of this document.
Если TARGET не был числовым IP-адресом и порт отсутствовал в URI, клиент выполняет запрос SRV по записи, возвращённой обработкой NAPTR из раздела 4.1, если такая обработка выполнялась. Если она не выполнялась, потому что транспорт был указан явно, клиент выполняет запрос SRV для этого конкретного транспорта, используя идентификатор службы «_sips» для URI SIPS. Для URI SIP, если клиент желает использовать TLS, он также использует идентификатор службы «_sips» для этого конкретного транспорта, иначе он использует «_sip». Если обработка NAPTR не выполнялась, потому что записи NAPTR не найдены, но запрос SRV для поддерживаемого транспортного протокола был успешным, выбираются эти записи SRV. Независимо от того, как были определены записи SRV, соблюдаются процедуры RFC 2782, как описано в разделе «Правила использования», дополненные дополнительными процедурами раздела 4.3 настоящего документа.
If no SRV records were found, the client performs an A or AAAA record lookup of the domain name. The result will be a list of IP addresses, each of which can be contacted using the transport protocol determined previously, at the default port for that transport. Processing then proceeds as described above for an explicit port once the A or AAAA records have been looked up.
Если записи SRV не найдены, клиент выполняет поиск записи A или AAAA для доменного имени. Результатом будет список IP-адресов, к каждому из которых можно обратиться с использованием ранее определённого транспортного протокола на порту по умолчанию для этого транспорта. Затем обработка продолжается, как описано выше для явного порта, после того как записи A или AAAA будут найдены.
4.3. Details of RFC 2782 Process
4.3. Подробности процесса RFC 2782
RFC 2782 spells out the details of how a set of SRV records are sorted and then tried. However, it only states that the client should "try to connect to the (protocol, address, service)" without giving any details on what happens in the event of failure. Those details are described here for SIP.
RFC 2782 детально описывает, как набор записей SRV сортируется и затем опробуется. Однако он лишь утверждает, что клиент должен «попытаться подключиться к (протоколу, адресу, службе)», не уточняя, что происходит в случае неудачи. Эти подробности описаны здесь для SIP.
For SIP requests, failure occurs if the transaction layer reports a 503 error response or a transport failure of some sort (generally, due to fatal ICMP errors in UDP or connection failures in TCP). Failure also occurs if the transaction layer times out without ever having received any response, provisional or final (i.e., timer B or timer F in RFC 3261 [1] fires). If a failure occurs, the client SHOULD create a new request, which is identical to the previous, but has a different value of the Via branch ID than the previous (and therefore constitutes a new SIP transaction). That request is sent to the next element in the list as specified by RFC 2782.
Для запросов SIP отказ наступает, если уровень транзакций сообщает об ответе с ошибкой 503 или о каком-либо сбое транспорта (как правило, из-за фатальных ошибок ICMP в UDP или сбоев соединения в TCP). Отказ наступает также, если уровень транзакций завершается по тайм-ауту, так и не получив никакого ответа — ни предварительного, ни окончательного (то есть срабатывает таймер B или таймер F в RFC 3261 [1]). При отказе клиенту СЛЕДУЕТ создать новый запрос, идентичный предыдущему, но с другим значением идентификатора ветви Via, чем у предыдущего (и потому образующий новую SIP-транзакцию). Этот запрос отправляется следующему элементу в списке, как указано в RFC 2782.
4.4. Consideration for Stateless Proxies
4.4. Соображения для прокси без сохранения состояния
The process of the previous sections is highly stateful. When a server is contacted successfully, all retransmissions of the request for the transaction, as well as ACK for a non-2xx final response, and CANCEL requests for that transaction, MUST go to the same server.
Процесс предыдущих разделов в значительной степени требует сохранения состояния. Когда сервер успешно опрошен, все повторные передачи запроса для транзакции, а также ACK для не-2xx окончательного ответа и запросы CANCEL для этой транзакции ДОЛЖНЫ идти тому же серверу.
The identity of the successfully contacted server is a form of transaction state. This presents a challenge for stateless proxies, which still need to meet the requirement for sending all requests in the transaction to the same server.
Идентичность успешно опрошенного сервера является формой состояния транзакции. Это представляет проблему для прокси без сохранения состояния, которым всё равно нужно удовлетворять требованию отправки всех запросов транзакции одному и тому же серверу.
The problem is similar, but different, to the problem of HTTP transactions within a cookie session getting routed to different servers based on DNS randomization. There, such distribution is not a problem. Farms of servers generally have common back-end data stores, where the session data is stored. Whenever a server in the farm receives an HTTP request, it takes the session identifier, if present, and extracts the needed state to process the request. A request without a session identifier creates a new one. The problem with stateless proxies is at a lower layer; it is retransmitted requests within a transaction that are being potentially spread across servers. Since none of these retransmissions carries a "session identifier" (a complete dialog identifier in SIP terms), a new dialog would be created identically at each server. This could, for example result in multiple phone calls to be made to the same phone. Therefore, it is critical to prevent such a thing from happening in the first place.
Проблема аналогична, но отличается от проблемы HTTP-транзакций в рамках сессии с cookie, которые направляются разным серверам на основе случайного выбора DNS. Там такое распределение не является проблемой. Фермы серверов обычно имеют общие серверные хранилища данных, где хранятся данные сессии. Всякий раз, когда сервер фермы получает HTTP-запрос, он берёт идентификатор сессии, если он присутствует, и извлекает необходимое состояние для обработки запроса. Запрос без идентификатора сессии создаёт новый. Проблема прокси без сохранения состояния находится на более низком уровне: это повторно передаваемые запросы в рамках транзакции, которые потенциально распределяются по разным серверам. Поскольку ни одна из этих повторных передач не несёт «идентификатор сессии» (в терминах SIP — полный идентификатор диалога), новый диалог был бы идентично создан на каждом сервере. Это могло бы, например, привести к выполнению нескольких телефонных звонков на один и тот же телефон. Поэтому крайне важно предотвратить такое развитие событий с самого начала.
The requirement is not difficult to meet in the simple case where there were no failures when attempting to contact a server. Whenever the stateless proxy receives the request, it performs the appropriate DNS queries as described above. However, the procedures of RFC 2782 are not guaranteed to be deterministic. This is because records that contain the same priority have no specified order. The stateless proxy MUST define a deterministic order to the records in that case, using any algorithm at its disposal. One suggestion is to alphabetize them, or, more generally, sort them by ASCII-compatible encoding. To make processing easier for stateless proxies, it is RECOMMENDED that domain administrators make the weights of SRV records with equal priority different (for example, using weights of 1000 and 1001 if two servers are equivalent, rather than assigning both a weight of 1000), and similarly for NAPTR records. If the first server is contacted successfully, the proxy can remain stateless. However, if the first server is not contacted successfully, and a subsequent server is, the proxy cannot remain stateless for this transaction. If it were stateless, a retransmission could very well go to a different server if the failed one recovers between retransmissions. As such, whenever a proxy does not successfully contact the first server, it SHOULD act as a stateful proxy.
Требование нетрудно выполнить в простом случае, когда при попытке связаться с сервером не было сбоев. Всякий раз, когда прокси без сохранения состояния получает запрос, он выполняет соответствующие DNS-запросы, как описано выше. Однако процедуры RFC 2782 не гарантируют детерминированность. Это потому, что записи с одинаковым приоритетом не имеют заданного порядка. Прокси без сохранения состояния ДОЛЖЕН определить детерминированный порядок записей в этом случае, используя любой доступный ему алгоритм. Одно из предложений — расположить их в алфавитном порядке или, в более общем случае, отсортировать по кодировке, совместимой с ASCII. Чтобы упростить обработку для прокси без сохранения состояния, РЕКОМЕНДУЕТСЯ, чтобы администраторы доменов делали веса записей SRV с равным приоритетом разными (например, используя веса 1000 и 1001, если два сервера эквивалентны, вместо назначения обоим веса 1000), и аналогично для записей NAPTR. Если первый сервер опрошен успешно, прокси может оставаться без сохранения состояния. Однако если первый сервер не был успешно опрошен, а последующий был, прокси не может оставаться без сохранения состояния для этой транзакции. Будь он без сохранения состояния, повторная передача вполне могла бы уйти другому серверу, если отказавший восстановился между повторными передачами. Поэтому, когда прокси не удаётся успешно связаться с первым сервером, ему СЛЕДУЕТ действовать как прокси с сохранением состояния.
Unfortunately, it is still possible for a stateless proxy to deliver retransmissions to different servers, even if it follows the recommendations above. This can happen if the DNS TTLs expire in the middle of a transaction, and the entries had changed. This is unavoidable. Network implementors should be aware of this limitation, and not use stateless proxies that access DNS if this error is deemed critical.
К сожалению, прокси без сохранения состояния всё ещё может доставлять повторные передачи разным серверам, даже следуя приведённым выше рекомендациям. Это может произойти, если TTL DNS истекают в середине транзакции и записи изменились. Это неизбежно. Сетевым разработчикам следует учитывать это при планировании изменений в DNS-записях.
5. Server Usage
5. Использование сервером
RFC 3261 [1] defines procedures for sending responses from a server back to the client. Typically, for unicast UDP requests, the response is sent back to the source IP address where the request came from, using the port contained in the Via header. For reliable transport protocols, the response is sent over the connection the request arrived on. However, it is important to provide failover support when the client element fails between sending the request and receiving the response.
RFC 3261 [1] определяет процедуры отправки ответов от сервера обратно клиенту. Обычно для одноадресных UDP-запросов ответ отправляется обратно на исходный IP-адрес, откуда пришёл запрос, с использованием порта из заголовка Via. Для надёжных транспортных протоколов ответ отправляется по соединению, по которому пришёл запрос. Однако важно обеспечить поддержку переключения при отказе, когда клиентский элемент отказывает между отправкой запроса и получением ответа.
A server, according to RFC 3261 [1], will send a response on the connection it arrived on (in the case of reliable transport protocols), and for unreliable transport protocols, to the source address of the request, and the port in the Via header field. The procedures here are invoked when a server attempts to send to that location and that response fails (the specific conditions are detailed in RFC 3261). "Fails" is defined as any closure of the transport connection the request came in on before the response can be sent, or communication of a fatal error from the transport layer.
Сервер, согласно RFC 3261 [1], отправит ответ по соединению, по которому он пришёл (в случае надёжных транспортных протоколов), а для ненадёжных транспортных протоколов — на исходный адрес запроса и порт из поля заголовка Via. Описанные здесь процедуры применяются, когда сервер пытается отправить по этому адресу, и этот ответ терпит неудачу (конкретные условия подробно описаны в RFC 3261). «Неудача» определяется как любое закрытие транспортного соединения, по которому пришёл запрос, до того как ответ может быть отправлен, либо сообщение о фатальной ошибке от транспортного уровня.
In these cases, the server examines the value of the sent-by construction in the topmost Via header. If it contains a numeric IP address, the server attempts to send the response to that address, using the transport protocol from the Via header, and the port from sent-by, if present, else the default for that transport protocol. The transport protocol in the Via header can indicate "TLS", which refers to TLS over TCP. When this value is present, the server MUST use TLS over TCP to send the response. If, however, the sent-by field contained a domain name and a port number, the server queries for A or AAAA records with that name. It tries to send the response to each element on the resulting list of IP addresses, using the port from the Via, and the transport protocol from the Via (again, a value of TLS refers to TLS over TCP). As in the client processing, the next entry in the list is tried if the one before it results in a failure.
В этих случаях сервер исследует значение конструкции sent-by в самом верхнем заголовке Via. Если оно содержит числовой IP-адрес, сервер пытается отправить ответ на этот адрес, используя транспортный протокол из заголовка Via и порт из sent-by, если он присутствует, иначе порт по умолчанию для этого транспортного протокола. Транспортный протокол в заголовке Via может указывать «TLS», что означает TLS поверх TCP. Когда это значение присутствует, сервер ДОЛЖЕН использовать TLS поверх TCP для отправки ответа. Если же поле sent-by содержало доменное имя и номер порта, сервер запрашивает записи A или AAAA с этим именем. Он пытается отправить ответ каждому элементу из полученного списка IP-адресов, используя порт из Via и транспортный протокол из Via (опять же, значение TLS означает TLS поверх TCP). Как и при обработке клиентом, следующая запись в списке опробуется, если предыдущая привела к неудаче.
If, however, the sent-by field contained a domain name and no port, the server queries for SRV records at that domain name using the service identifier "_sips" if the Via transport is "TLS", "_sip" otherwise, and the transport from the topmost Via header ("TLS" implies that the transport protocol in the SRV query is TCP). The resulting list is sorted as described in [2], and the response is sent to the topmost element on the new list described there. If that results in a failure, the next entry on the list is tried.
Если же поле sent-by содержало доменное имя и не содержало порта, сервер запрашивает записи SRV для этого доменного имени, используя идентификатор службы «_sips», если транспорт в Via — «TLS», иначе «_sip», и транспорт из самого верхнего заголовка Via («TLS» подразумевает, что транспортный протокол — TCP). Затем сервер выбирает запись SRV так же, как клиент, и отправляет ответ выбранному хосту и порту.
6. Constructing SIP URIs
6. Формирование URI SIP
In many cases, an element needs to construct a SIP URI for inclusion in a Contact header in a REGISTER, or in a Record-Route header in an INVITE. According to RFC 3261 [1], these URIs have to have the property that they resolve to the specific element that inserted them. However, if they are constructed with just an IP address, for example:
Во многих случаях элементу нужно сформировать URI SIP для включения в заголовок Contact в REGISTER или в заголовок Record-Route в INVITE. Согласно RFC 3261 [1], эти URI должны обладать тем свойством, что они разрешаются в тот конкретный элемент, который их вставил. Однако если они сформированы только из IP-адреса, например:
sip:1.2.3.4 then should the element fail, there is no way to route the request or response through a backup.
sip:1.2.3.4 то в случае отказа элемента не будет способа маршрутизировать запрос или ответ через резервный сервер.
SRV provides a way to fix this. Instead of using an IP address, a domain name that resolves to an SRV record can be used:
SRV предоставляет способ исправить это. Вместо использования IP-адреса можно использовать доменное имя, разрешаемое в запись SRV:
sip:server23.provider.com
sip:server23.provider.com
The SRV records for a particular target can be set up so that there is a single record with a low value for the priority field (indicating the preferred choice), and this record points to the specific element that constructed the URI. However, there are additional records with higher values of the priority field that point to backup elements that would be used in the event of failure. This allows the constraint of RFC 3261 [1] to be met while allowing for robust operation.
Записи SRV для конкретной цели могут быть настроены так, что имеется одна запись с низким значением поля priority (указывающая предпочтительный выбор), и эта запись указывает на конкретный элемент, сформировавший URI. Однако есть дополнительные записи с более высокими значениями поля priority, указывающие на резервные элементы, которые могут принять трафик в случае отказа основного. Это позволяет соблюсти ограничение RFC 3261 [1] и при этом обеспечить устойчивую работу.
7. Security Considerations
7. Вопросы безопасности
DNS NAPTR records are used to allow a client to discover that the server supports TLS. An attacker could potentially modify these records, resulting in a client using a non-secure transport when TLS is in fact available and preferred.
Записи DNS NAPTR используются, чтобы позволить клиенту обнаружить, что сервер поддерживает TLS. Злоумышленник потенциально мог бы изменить эти записи, в результате чего клиент использовал бы незащищённый транспорт, когда TLS фактически доступен и предпочтителен.
This is partially mitigated by the presence of the sips URI scheme, which is always sent only over TLS. An attacker cannot force a bid down through deletion or modification of DNS records. In the worst case, they can prevent communication from occurring by deleting all records. A sips URI itself is generally exchanged within a secure context, frequently on a business card or secure web page, or within a SIP message which has already been secured with TLS. See RFC 3261 [1] for details. The sips URI is therefore preferred when security is truly needed, but we allow TLS to be used for requests resolved by a SIP URI to allow security that is better than no TLS at all.
Это частично смягчается наличием схемы URI sips, которая всегда передаётся только по TLS. Злоумышленник не может принудительно понизить уровень защиты путём удаления или изменения записей DNS. В худшем случае он может воспрепятствовать связи, удалив все записи. Сам URI sips обычно передаётся в защищённом контексте, часто на визитной карточке или защищённой веб-странице, либо в сообщении SIP, которое уже было защищено с помощью TLS. Подробности см. в RFC 3261 [1]. Поэтому URI sips предпочтителен, когда защита действительно необходима, но мы допускаем использование TLS для запросов, разрешаемых посредством URI SIP, чтобы обеспечить защиту, лучшую, чем полное отсутствие TLS.
The bid down attack can also be mitigated through caching. A client which frequently contacts the same domain SHOULD cache whether or not its NAPTR records contain SIPS in the services field. If such records were present, but in later queries cease to appear, it is a sign of a potential attack. In this case, the client SHOULD generate some kind of alert or alarm, and MAY reject the request.
Атака понижения уровня защиты также может быть смягчена путём кэширования. Клиенту, который часто обращается к одному домену, СЛЕДУЕТ кэшировать, содержат ли его записи NAPTR значение SIPS в поле сервиса. Если такие записи присутствовали, но в последующих запросах перестали появляться, это признак потенциальной атаки.
An additional problem is that proxies, which are intermediaries between the users of the system, are frequently the clients that perform the NAPTR queries. It is therefore possible for a proxy to ignore SIPS entries even though they are present, resulting in downgraded security. There is very little that can be done to prevent such attacks. Clients are simply dependent on proxy servers for call completion, and must trust that they implement the protocol properly in order for security to be provided. Falsifying DNS records can be done by tampering with wire traffic (in the absence of DNSSEC), whereas compromising and commandeering a proxy server requires a break-in, and is seen as the considerably less likely downgrade threat.
Дополнительная проблема состоит в том, что прокси, являющиеся посредниками между пользователями системы, часто оказываются клиентами, выполняющими запросы NAPTR. Поэтому возможно, что прокси проигнорирует записи SIPS, даже если они присутствуют, что приведёт к понижению уровня безопасности. Практически ничего нельзя сделать, чтобы предотвратить такие атаки. Клиенты просто зависят от прокси-серверов в вопросе завершения вызова и должны доверять тому, что они правильно реализуют протокол, чтобы обеспечить безопасность. Фальсификация записей DNS может быть выполнена путём вмешательства в трафик (при отсутствии DNSSEC), тогда как компрометация и захват прокси-сервера требуют взлома и рассматриваются как значительно менее вероятная угроза понижения уровня защиты.

This application is called the Transport Determination Application, and its goal is to map an incoming SIP or SIPS URI to a set of SRV records for the various servers that can handle the URI. The following is the information that DDDS requests an application to provide:
В этом разделе более формально определяется использование NAPTR в настоящей спецификации с использованием в качестве руководства платформы Dynamic Delegation Discovery System (DDDS) [7]. DDDS представляет эволюцию ресурсной записи NAPTR. Valid Databases — ключ, полученный в результате первого общеизвестного правила, ищется в единственной базе данных — DNS [8].
Expected Output: The result of the application is an SRV record for the server to contact.
Expected Output — результатом приложения является запись SRV для сервера, с которым нужно связаться.
