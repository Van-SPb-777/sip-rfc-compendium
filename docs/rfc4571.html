Abstract
Аннотация
This memo defines a method for framing Real-time Transport Protocol (RTP) and RTP Control Protocol (RTCP) packets onto connection- oriented transport (such as TCP). The memo also defines how session descriptions may specify RTP streams that use the framing method.
Настоящий меморандум определяет метод кадрирования пакетов протокола реального времени (RTP) и протокола управления RTP (RTCP) поверх транспорта с установлением соединения (например, TCP). Меморандум также определяет, как описания сессий могут задавать потоки RTP, использующие метод кадрирования.
1. Introduction
1. Введение
The Audio/Video Profile (AVP, [RFC3550]) for the Real-time Transport Protocol (RTP, [RFC3551]) does not define a method for framing RTP and RTP Control Protocol (RTCP) packets onto connection-oriented transport protocols (such as TCP). However, earlier versions of RTP/AVP did define a framing method, and this method is in use in several implementations.
Профиль аудио/видео (AVP, [RFC3550]) для протокола реального времени (RTP, [RFC3551]) не определяет метод кадрирования пакетов RTP и протокола управления RTP (RTCP) поверх транспортных протоколов с установлением соединения (например, TCP). Однако более ранние версии RTP/AVP определяли метод кадрирования, и этот метод используется в нескольких реализациях.
In this memo, we document the framing method that was defined by earlier versions of RTP/AVP. In addition, we introduce a mechanism for a session description [SDP] to signal the use of the framing method. Note that session description signalling for the framing method is new and was not defined in earlier versions of RTP/AVP.
В настоящем меморандуме документируется метод кадрирования, определённый более ранними версиями RTP/AVP. Кроме того, вводится механизм, позволяющий описанию сессии [SDP] сигнализировать об использовании метода кадрирования. Отметим, что сигнализация использования метода кадрирования в описании сессии является новой и не была определена в более ранних версиях RTP/AVP.

Figure 1: The bit field definition of the framing method
Рисунок 1: Определение битовых полей метода кадрирования
A 16-bit unsigned integer LENGTH field, coded in network byte order (big-endian), begins the frame. If LENGTH is non-zero, an RTP or RTCP packet follows the LENGTH field. The value coded in the LENGTH field MUST equal the number of octets in the RTP or RTCP packet. Zero is a valid value for LENGTH, and it codes the null packet.
Кадр начинается с 16-битного целого беззнакового поля LENGTH, закодированного в сетевом порядке байтов (big-endian). Если LENGTH не равно нулю, за полем LENGTH следует пакет RTP или RTCP. Значение, закодированное в поле LENGTH, ДОЛЖНО равняться числу октетов в пакете RTP или RTCP. Ноль является допустимым значением LENGTH, и он кодирует пустой пакет.
This framing method does not use frame markers (i.e., an octet of constant value that would precede the LENGTH field). Frame markers are useful for detecting errors in the LENGTH field. In lieu of a frame marker, receivers SHOULD monitor the RTP and RTCP header fields whose values are predictable (for example, the RTP version number). See Appendix A.1 of [RFC3550] for additional guidance.
Настоящий метод кадрирования не использует маркеры кадра (т. е. октет постоянного значения, который предшествовал бы полю LENGTH). Маркеры кадра полезны для обнаружения ошибок в поле LENGTH. Вместо маркера кадра получатели ДОЛЖНЫ отслеживать поля заголовков RTP и RTCP, значения которых предсказуемы (например, номер версии RTP). Дополнительные указания см. в приложении A.1 к [RFC3550].
3. Packet Stream Properties
3. Свойства пакетных потоков
In most respects, the framing method does not specify properties above the level of a single packet. In particular, Section 2 does not specify the following:
По большей части метод кадрирования не задаёт свойств выше уровня отдельного пакета. В частности, в разделе 2 не определяются следующие свойства:
Bi-directional issues
Двунаправленность. Раздел
Section 2 defines a framing method for use in one direction on a connection. The relationship between framed packets flowing in a defined direction and in the reverse direction is not specified.
2 определяет метод кадрирования для использования в одном направлении соединения. Соотношение между кадрированными пакетами, идущими в заданном направлении и в обратном направлении, не определено.
Packet loss and reordering
Потери и переупорядочивание пакетов.
The reliable nature of a connection does not imply that a framed RTP stream has a contiguous sequence number ordering. For example, if the connection is used to tunnel a UDP stream through a network middlebox that only passes TCP, the sequence numbers in the framed stream reflect any packet loss or reordering on the UDP portion of the end-to-end flow.
Надёжный характер соединения не означает, что кадрированный поток RTP имеет непрерывный порядок номеров последовательности. Например, если соединение используется для туннелирования потока UDP через сетевой посредник, пропускающий только TCP, номера последовательности в кадрированном потоке отражают любые потери или переупорядочивание пакетов на участке UDP сквозного потока.
Out-of-band semantics
Семантика вне полосы.
Section 2 does not define the RTP or RTCP semantics for closing a TCP socket, or of any other "out of band" signal for the connection.
Раздел 2 не определяет семантику RTP или RTCP для закрытия сокета TCP или любого другого сигнала «вне полосы» для соединения.
Memos that normatively include the framing method MAY specify these properties. For example, Section 4 of this memo specifies these properties for RTP/AVP sessions specified in session descriptions.
Меморандумы, нормативно включающие метод кадрирования, МОГУТ определять эти свойства. Например, раздел 4 настоящего меморандума определяет эти свойства для сессий RTP/AVP, заданных в описаниях сессий.
In one respect, the framing protocol does indeed specify a property above the level of a single packet. If a direction of a connection carries RTP packets, the streams carried in this direction MUST support the use of multiple synchronization sources (SSRCs) in those RTP packets. If a direction of a connection carries RTCP packets, the streams carried in this direction MUST support the use of multiple SSRCs in those RTCP packets.
В одном отношении протокол кадрирования действительно задаёт свойство выше уровня отдельного пакета. Если направление соединения переносит пакеты RTP, потоки, передаваемые в этом направлении, ДОЛЖНЫ поддерживать использование нескольких источников синхронизации (SSRC) в этих пакетах RTP. Если направление соединения переносит пакеты RTCP, потоки, передаваемые в этом направлении, ДОЛЖНЫ поддерживать использование нескольких SSRC в этих пакетах RTCP.
4. Session Descriptions for RTP/AVP over TCP
4. Описания сессий для RTP/AVP поверх TCP
Session management protocols that use the Session Description Protocol [SDP] in conjunction with the Offer/Answer Protocol [RFC3264] MUST use the methods described in [COMEDIA] to set up RTP/AVP streams over TCP. In this case, the use of Offer/Answer is REQUIRED, as the setup methods described in [COMEDIA] rely on Offer/Answer. In principle, [COMEDIA] is capable of setting up RTP sessions for any RTP profile. In practice, each profile has unique issues that must be considered when applying [COMEDIA] to set up streams for the profile.
Протоколы управления сессиями, использующие протокол описания сессий [SDP] вместе с протоколом «предложение/ответ» [RFC3264], ДОЛЖНЫ использовать методы, описанные в [COMEDIA], для установления потоков RTP/AVP поверх TCP. В этом случае использование модели «предложение/ответ» ТРЕБУЕТСЯ, поскольку методы установления, описанные в [COMEDIA], полагаются на неё. В принципе, [COMEDIA] способна устанавливать сессии RTP для любого профиля RTP. На практике каждый профиль имеет уникальные особенности, которые необходимо учитывать при применении [COMEDIA] для установления потоков этого профиля.
In this memo, we restrict our focus to the Audio/Video Profile (AVP, [RFC3551]). Below, we define a token value ("TCP/RTP/AVP") that signals the use of RTP/AVP in a TCP session. We also define the operational procedures that a TCP/RTP/AVP stream MUST follow.
В настоящем меморандуме мы ограничиваем рассмотрение профилем аудио/видео (AVP, [RFC3551]). Ниже определяется значение токена («TCP/RTP/AVP»), которое сигнализирует об использовании RTP/AVP в сессии TCP. Также определяются операционные процедуры, которым ДОЛЖЕН следовать поток TCP/RTP/AVP.
We expect that other standards-track memos will appear to support the use of the framing method with other RTP profiles. The support memo for a new profile MUST define a token value for the profile, using the style we used for AVP. Thus, for profile xyz, the token value MUST be "TCP/RTP/xyz". The memo SHOULD adopt the operational procedures we define below for AVP, unless these procedures are in some way incompatible with the profile.
Мы ожидаем появления других меморандумов уровня Standards Track, поддерживающих использование метода кадрирования с другими профилями RTP. Меморандум поддержки нового профиля ДОЛЖЕН определить значение токена для профиля в стиле, использованном нами для AVP. Так, для профиля xyz значением токена ДОЛЖНО быть «TCP/RTP/xyz». Меморандум ДОЛЖЕН принять операционные процедуры, определённые ниже для AVP, если только эти процедуры не являются каким-либо образом несовместимыми с профилем.
The remainder of this section describes how to setup and use an AVP stream in a TCP session. Figure 2 shows the syntax of a media (m=) line [SDP] of a session description:
Остальная часть настоящего раздела описывает, как установить и использовать поток AVP в сессии TCP. На рисунке 2 показан синтаксис строки медиа (m=) [SDP] описания сессии:
"m=" media SP port ["/" integer] SP proto 1*(SP fmt) CRLF
«m=» media SP port ["/" integer] SP proto 1*(SP fmt) CRLF
Figure 2: Syntax for an SDP media (m=) line (from [SDP])
Рисунок 2: Синтаксис строки медиа (m=) SDP (из [SDP])
The <proto> token value "TCP/RTP/AVP" specifies an RTP/AVP [RFC3550] [RFC3551] stream that uses the framing method over TCP.
Значение токена <proto> «TCP/RTP/AVP» задаёт поток RTP/AVP [RFC3550] [RFC3551], использующий метод кадрирования поверх TCP.
The <fmt> tokens that follow <proto> MUST be unique unsigned integers in the range 0 to 127. The <fmt> tokens specify an RTP payload type associated with the stream.
Токены <fmt>, следующие за <proto>, ДОЛЖНЫ быть уникальными беззнаковыми целыми числами в диапазоне от 0 до 127. Токены <fmt> задают тип полезной нагрузки RTP, связанный с потоком.
In all other respects, the session description syntax for the framing method is identical to [COMEDIA].
Во всех остальных отношениях синтаксис описания сессии для метода кадрирования идентичен [COMEDIA].
The TCP <port> on the media line carries RTP packets. If a media stream uses RTCP, a second connection carries RTCP packets. The port for the RTCP connection is chosen using the algorithms defined in [SDP] or by the mechanism defined in [RFC3605].
TCP-порт <port> в строке медиа переносит пакеты RTP. Если поток медиа использует RTCP, второе соединение переносит пакеты RTCP. Порт для соединения RTCP выбирается с помощью алгоритмов, определённых в [SDP], или с помощью механизма, определённого в [RFC3605].
The TCP connections MAY carry bi-directional traffic, following the semantics defined in [COMEDIA]. Both directions of a connection MUST carry the same type of packets (RTP or RTCP). The packets MUST exclusively code the RTP or RTCP streams specified on the media line(s) associated with the connection. As noted in [RFC3550], the use of RTP without RTCP is strongly discouraged. However, if a sender does not wish to send RTCP packets in a media session, the sender MUST add the lines "b=RS:0" AND "b=RR:0" to the media description (from [RFC3556]).
TCP-соединения МОГУТ переносить двунаправленный трафик в соответствии с семантикой, определённой в [COMEDIA]. Оба направления соединения ДОЛЖНЫ переносить один и тот же тип пакетов (RTP или RTCP). Пакеты ДОЛЖНЫ кодировать исключительно потоки RTP или RTCP, указанные в строке (строках) медиа, связанной (связанных) с соединением. Как отмечено в [RFC3550], использование RTP без RTCP настоятельно не рекомендуется. Однако если отправитель не желает отправлять пакеты RTCP в сессии медиа, он ДОЛЖЕН добавить строки «b=RS:0» И «b=RR:0» в описание медиа (из [RFC3556]).
If the session descriptions of the offer AND the answer both contain the "b=RS:0" AND "b=RR:0" lines, an RTCP TCP flow for the media session MUST NOT be created by either endpoint in the session. In all other cases, endpoints MUST establish two TCP connections for an RTP/AVP stream, one for RTP and one for RTCP.
Если описания сессий предложения И ответа оба содержат строки «b=RS:0» И «b=RR:0», поток RTCP по TCP для сессии медиа НЕ ДОЛЖЕН создаваться ни одной из конечных точек сессии. Во всех остальных случаях конечные точки ДОЛЖНЫ установить два TCP-соединения для потока RTP/AVP: одно для RTP и одно для RTCP.
As described in [RFC3264], the use of the "sendonly" or "sendrecv" attribute in an offer (or answer) indicates that the offerer (or answerer) intends to send RTP packets on the RTP TCP connection. The use of the "recvonly" or "sendrecv" attributes in an offer (or answer) indicates that the offerer (or answerer) wishes to receive RTP packets on the RTP TCP connection.
Как описано в [RFC3264], использование атрибута «sendonly» или «sendrecv» в предложении (или ответе) указывает, что предлагающий (или отвечающий) намерен отправлять пакеты RTP по TCP-соединению для RTP. Использование атрибутов «recvonly» или «sendrecv» в предложении (или ответе) указывает, что предлагающий (или отвечающий) желает получать пакеты RTP по TCP-соединению для RTP.

Рисунок 3: Описание TCP-сессии для первого участника соединения
v=0 o=second 2520644554 2838152170 IN IP4 second.example.net s=Example t=0 0 c=IN IP4 192.0.2.94 m=audio 16112 TCP/RTP/AVP 10 11 a=setup:passive a=connection:new
v=0 o=second 2520644554 2838152170 IN IP4 second.example.net s=Example t=0 0 c=IN IP4 192.0.2.94 m=audio 16112 TCP/RTP/AVP 10 11 a=setup:passive a=connection:new
Figure 4: TCP session description for the second participant
Рисунок 4: Описание TCP-сессии для второго участника соединения
The session descriptions define two parties that participate in a connection-oriented RTP/AVP session. The first party (Figure 3) is capable of receiving stereo L16 streams (static payload type 11). The second party (Figure 4) is capable of receiving mono (static payload type 10) or stereo L16 streams.
Описания сессий определяют две стороны, участвующие в сессии RTP/AVP с установлением соединения. Первая сторона (рисунок 3) способна принимать стереопотоки L16 (статический тип полезной нагрузки 11). Вторая сторона (рисунок 4) способна принимать монопотоки (статический тип полезной нагрузки 10) или стереопотоки L16.
The "setup" attribute in Figure 3 specifies that the first party is "active" and initiates connections, and the "setup" attribute in Figure 4 specifies that the second party is "passive" and accepts connections [COMEDIA].
Атрибут «setup» на рисунке 3 указывает, что первая сторона является «active» и инициирует соединения, а атрибут «setup» на рисунке 4 указывает, что вторая сторона является «passive» и принимает соединения [COMEDIA].
The first party connects to the network address (192.0.2.94) and port (16112) of the second party. Once the connection is established, it is used bi-directionally: the first party sends framed RTP packets to the second party in one direction of the connection, and the second party sends framed RTP packets to the first party in the other direction of the connection.
Первая сторона подключается к сетевому адресу (192.0.2.94) и порту (16112) второй стороны. После установления соединения оно используется двунаправленно: первая сторона отправляет кадрированные пакеты RTP второй стороне в одном направлении соединения, а вторая сторона отправляет кадрированные пакеты RTP первой стороне в другом направлении соединения.
The first party also initiates an RTCP TCP connection to port 16113 (16112 + 1, as defined in [SDP]) of the second party. Once the connection is established, the first party sends framed RTCP packets to the second party in one direction of the connection, and the second party sends framed RTCP packets to the first party in the other direction of the connection.
Первая сторона также инициирует TCP-соединение RTCP к порту 16113 (16112 + 1, как определено в [SDP]) второй стороны. После установления соединения первая сторона отправляет кадрированные пакеты RTCP второй стороне в одном направлении соединения, а вторая сторона отправляет кадрированные пакеты RTCP первой стороне в другом направлении соединения.
6. Congestion Control
6. Управление перегрузкой
The RTP congestion control requirements are defined in [RFC3550]. As noted in [RFC3550], all transport protocols used on the Internet need to address congestion control in some way, and RTP is not an exception.
Требования RTP к управлению перегрузкой определены в [RFC3550]. Как отмечено в [RFC3550], все транспортные протоколы, используемые в Интернете, должны каким-либо образом решать задачу управления перегрузкой, и RTP не является исключением.
In addition, the congestion control requirements for the Audio/Video Profile are defined in [RFC3551]. The basic congestion control requirement defined in [RFC3551] is that RTP sessions should compete fairly with TCP flows that share the network. As the framing method uses TCP, it competes fairly with other TCP flows by definition.
Кроме того, требования к управлению перегрузкой для профиля аудио/видео определены в [RFC3551]. Базовое требование управления перегрузкой, определённое в [RFC3551], состоит в том, что сессии RTP должны справедливо конкурировать с потоками TCP, совместно использующими сеть. Поскольку метод кадрирования использует TCP, он по определению справедливо конкурирует с другими потоками TCP.

8. Security Considerations
8. Вопросы безопасности
Implementors should carefully read the Security Considerations sections of the RTP [RFC3550] and RTP/AVP [RFC3551] documents, as most of the issues discussed in these sections directly apply to RTP streams framed over TCP. Session descriptions that specify connection-oriented media sessions (such as the example session shown in Figures 3 and 4 of Section 5) raise unique security concerns for streaming media. The Security Considerations section of [COMEDIA] describes these issues in detail.
Реализаторам следует внимательно прочитать разделы «Вопросы безопасности» документов RTP [RFC3550] и RTP/AVP [RFC3551], поскольку большинство вопросов, обсуждаемых в этих разделах, напрямую относятся к потокам RTP, кадрированным поверх TCP. Описания сессий, задающие сессии медиа с установлением соединения (например, пример сессии, показанный на рисунках 3 и 4 раздела 5), порождают особые проблемы безопасности для потокового медиа. Раздел «Вопросы безопасности» документа [COMEDIA] подробно описывает эти вопросы.
Below, we discuss security issues that are unique to the framing method defined in Section 2.
Ниже обсуждаются проблемы безопасности, уникальные для метода кадрирования, определённого в разделе 2.
Attackers may send framed packets with large LENGTH values to exploit security holes in applications. For example, a C implementation may declare a 1500-byte array as a stack variable, and use LENGTH as the bound on the loop that reads the framed packet into the array. This code would work fine for friendly applications that use Etherframe- sized RTP packets, but may be open to exploit by an attacker. Thus, an implementation needs to handle packets of any length, from a NULL packet (LENGTH == 0) to the maximum-length packet holding 64K octets (LENGTH = 0xFFFF).
Злоумышленники могут отправлять кадрированные пакеты с большими значениями LENGTH, чтобы использовать дыры в безопасности приложений. Например, реализация на C может объявить массив размером 1500 байт как стековую переменную и использовать LENGTH в качестве границы цикла, читающего кадрированный пакет в массив. Такой код отлично работал бы для дружественных приложений, использующих пакеты RTP размером с кадр Ethernet, но может быть уязвим для использования злоумышленником. Поэтому реализация должна обрабатывать пакеты любой длины — от пустого пакета (LENGTH == 0) до пакета максимальной длины, вмещающего 64K октетов (LENGTH = 0xFFFF).
