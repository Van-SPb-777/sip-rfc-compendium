Abstract
Аннотация
This specification defines conferencing call control features for the Session Initiation Protocol (SIP). This document builds on the Conferencing Requirements and Framework documents to define how a tightly coupled SIP conference works. The approach is explored from the perspective of different user agent (UA) types: conference- unaware, conference-aware, and focus UAs. The use of Uniform Resource Identifiers (URIs) in conferencing, OPTIONS for capabilities discovery, and call control using REFER are covered in detail with example call flow diagrams. The usage of the isfocus feature tag is defined.
В этой спецификации определяются функции управления вызовом для конференций в протоколе инициирования сессий (SIP). Документ опирается на документы о требованиях к конференциям и об архитектуре конференций и определяет, как работает тесно связанная конференция SIP. Подход рассматривается с точки зрения различных типов пользовательских агентов (UA): не осведомлённых о конференции, осведомлённых о конференции и фокус-UA. Подробно, с примерами диаграмм потоков вызовов, рассматриваются использование универсальных идентификаторов ресурсов (URI) в конференциях, OPTIONS для обнаружения возможностей и управление вызовом с помощью REFER. Определяется использование тега признака isfocus.
1. Introduction
1. Введение
This specification uses the concepts and definitions from the high level requirements [14] and the SIP conferencing framework [8] documents. This approach is applicable to tightly coupled SIP conferences. In this architecture, a user agent (UA), known as a participant, establishes a SIP dialog with another UA, known as a focus. The focus is the central point of control, authentication, and authorization. This specification defines the operation of a focus and participant UAs. Note that only the signalling (SIP) needs to be centralized in this model; the media can be centrally mixed, distributed, or even multicast. For a full discussion of this architecture, see the SIP conferencing framework document [8].
В этой спецификации используются понятия и определения из документов о высокоуровневых требованиях [14] и об архитектуре конференций SIP [8]. Данный подход применим к тесно связанным конференциям SIP. В этой архитектуре пользовательский агент (UA), называемый участником, устанавливает диалог SIP с другим UA, называемым фокусом. Фокус является центральной точкой управления, аутентификации и авторизации. В этой спецификации определяется работа фокуса и UA-участников. Обратите внимание, что в этой модели централизованной должна быть только сигнализация (SIP); медиапотоки могут смешиваться в центре, распределяться или даже передаваться многоадресно. Полное обсуждение этой архитектуры см. в документе об архитектуре конференций SIP [8].
The approach described in this document implements key functions in the conferencing framework using SIP primitives only. This allows for conducting simple conferences with defined functionalities using SIP mechanisms and conventions. Many other advanced functions can be implemented using additional means, but they are not in the scope of this document. This document presents the basic call control (dial-in and dial-out) conferencing building blocks from the UA perspective. Possible applications include ad-hoc conferences and scheduled conferences.
Описанный в этом документе подход реализует ключевые функции архитектуры конференций, используя только примитивы SIP. Это позволяет проводить простые конференции с определёнными функциональными возможностями с помощью механизмов и соглашений SIP. Многие другие расширенные функции могут быть реализованы дополнительными средствами, но они не входят в область охвата данного документа. Документ представляет базовые строительные блоки управления вызовом (входящий и исходящий набор) для конференций с точки зрения UA. Возможные применения включают специальные (ad-hoc) и запланированные конференции.
Note that a single conference can bridge participants that have different capabilities and who potentially have joined the conference by different means (i.e., dial-in, dial-out, scheduled, or ad-hoc).
Обратите внимание, что одна конференция может объединять участников с разными возможностями, которые, возможно, присоединились к конференции разными способами (т. е. входящий набор, исходящий набор, запланированное или специальное участие).
The call control and dialog manipulation approach is based on the multiparty framework document [15]. That document defines the basic approach of service design adopted for SIP, which includes the following:
Подход к управлению вызовом и манипулированию диалогами основан на документе об архитектуре многосторонних взаимодействий [15]. Этот документ определяет базовый подход к проектированию услуг, принятый для SIP, который включает следующее:
- Definition of primitives, not services - Signaling model independent - Invoker oriented - Primitives make full use of URIs - Include policies for authentication, authorization, logging, etc. - Define graceful fallback to baseline SIP
- Определение примитивов, а не услуг - Независимость от модели сигнализации - Ориентация на инициатора - Полное использование URI примитивами - Включение политик аутентификации, авторизации, журналирования и т. п. - Определение корректного отката к базовому SIP
The use of opaque URIs and the ability to communicate call control context information within a URI (as opposed to using service-related header fields), as discussed in RFC 3087 [11], is fundamental to this approach.
Использование непрозрачных URI и возможность передавать контекстную информацию управления вызовом внутри URI (в отличие от использования заголовочных полей, связанных с услугой), как обсуждается в RFC 3087 [11], является основополагающим для этого подхода.
Capabilities discovery is an important feature of SIP systems, and conferencing systems can make use of such features. For a UA acting as a focus in a conference, this specification defines the usage of the 'isfocus' feature parameter.
Обнаружение возможностей является важной функцией систем SIP, и системы конференций могут использовать такие возможности. Для UA, действующего в конференции как фокус, эта спецификация определяет использование параметра-признака 'isfocus'.

3. SIP User Agent Conferencing Capability Types
3. Типы возможностей конференций пользовательских агентов SIP
From a conferencing perspective, the framework document outlines a number of possible different SIP components such as conference- unaware participant, conference-aware participant, and focus.
С точки зрения конференций в документе об архитектуре обрисован ряд возможных различных компонентов SIP, таких как участник, не осведомлённый о конференции, участник, осведомлённый о конференции, и фокус.
This document applies the concepts above to the SIP call control part of the conferencing components. It defines normative behavior of the SIP UAs in various conferencing situations (referred to later as "scenarios").
Этот документ применяет приведённые выше понятия к части управления вызовом SIP конференционных компонентов. Он определяет нормативное поведение UA SIP в различных ситуациях конференции (далее — «сценарии»).
3.1. Focus UA
3.1. Фокус-UA
A focus, as defined in the framework, hosts a SIP conference and maintains a SIP signaling relationship with each participant in the conference. A focus contains a conference-aware user agent that supports the conferencing call control conventions as defined in this document.
Фокус, как определено в архитектуре, размещает конференцию SIP и поддерживает отношение сигнализации SIP с каждым участником конференции. Фокус содержит осведомлённый о конференции пользовательский агент, который поддерживает соглашения управления вызовом для конференций, определённые в этом документе.
A focus SHOULD support the conference package RFC 4575 [9], behave as a notifier for that package, and indicate its support in the Allow- Events header fields in requests and responses. A focus MAY include information about the conference in Session Description Protocol (SDP) bodies sent as part of normal SIP signaling by populating the Session Information, URI, Email Address, and Phone Number SDP fields.
Фокус СЛЕДУЕТ поддерживать пакет конференции RFC 4575 [9], выступать нотификатором для этого пакета и указывать свою поддержку в полях заголовка Allow-Events в запросах и ответах. Фокус МОЖЕТ включать информацию о конференции в тела Session Description Protocol (SDP), отправляемые в рамках обычной сигнализации SIP, заполняя поля SDP Session Information, URI, Email Address и Phone Number.
In order to support advanced features, where a session established between two endpoints can migrate to a centralized conference, a focus SHOULD support the Replaces header field [6].
Для поддержки расширенных функций, когда сессия, установленная между двумя конечными точками, может мигрировать в централизованную конференцию, фокус СЛЕДУЕТ поддерживать поле заголовка Replaces [6].
A user agent with focus capabilities could be implemented in end user equipment and would be used for the creation of ad-hoc conferences.
Пользовательский агент с возможностями фокуса может быть реализован в конечном оборудовании пользователя и использоваться для создания специальных конференций.
A dedicated conferencing server, whose primary task is to simultaneously host conferences of arbitrary type and size, may allocate and publish a conference factory URI (as defined in the next section) for creating an arbitrary number of ad-hoc conferences (and subsequently their focuses) using SIP call control means.
Выделенный сервер конференций, основная задача которого — одновременно размещать конференции произвольного типа и размера, может выделять и публиковать URI фабрики конференций (как определено в следующем разделе) для создания произвольного числа специальных конференций (и, следовательно, их фокусов) с помощью средств управления вызовом SIP.
3.2. Conference Factory URI
3.2. URI фабрики конференций
According to the framework, there are many ways in which a conference can be created. A conferencing server implementation is free to choose from these methods, which include non-automated means (such as an Interactive Voice Response (IVR) system), SIP, or any conference control protocol.
Согласно архитектуре, существует много способов создания конференции. Реализация сервера конференций свободна в выборе этих методов, которые включают неавтоматизированные средства (например, систему интерактивного голосового ответа (IVR)), SIP или любой протокол управления конференцией.
In order to automatically create an arbitrary number of ad-hoc conferences (and subsequently their focuses) using SIP call control means, a globally routable Conference Factory URI can be allocated and published.
Чтобы автоматически создавать произвольное число специальных конференций (и, следовательно, их фокусов) с помощью средств управления вызовом SIP, можно выделить и опубликовать глобально маршрутизируемый URI фабрики конференций.
A successful attempt to establish a call to this URI would result in the automatic creation of a new conference and its focus. As a result, note that the Conference Factory URI and the newly created focus URI MAY resolve to different physical devices.
Успешная попытка установить вызов на этот URI приведёт к автоматическому созданию новой конференции и её фокуса. В результате обратите внимание, что URI фабрики конференций и URI только что созданного фокуса МОГУТ разрешаться в разные физические устройства.
A scenario showing the use of the conference factory URI is shown in Section 5.4.
Сценарий, показывающий использование URI фабрики конференций, приведён в разделе 5.4.
3.3. Conference-Unaware UA
3.3. UA, не осведомлённый о конференции
The simplest user agent can participate in a conference ignoring all SIP conferencing-related information. The simplest user agent is able to dial in to a conference and to be invited to a conference. Any conferencing information is optionally conveyed to/from it using non-SIP means. Such a user agent would not usually host a conference (at least, not using SIP explicitly). A conference-unaware UA need only support RFC 3261 [2]. Call flows for conference-unaware UAs are not shown in general in this document as they would be identical to those in the SIP call flows document [13].
Простейший пользовательский агент может участвовать в конференции, игнорируя всю информацию SIP, связанную с конференциями. Простейший пользовательский агент способен набрать номер для входа в конференцию, и его можно пригласить в конференцию. Любая информация о конференции необязательно передаётся ему и от него не-SIP средствами. Такой пользовательский агент обычно не размещает конференцию (по крайней мере, явно не с помощью SIP). UA, не осведомлённый о конференции, должен поддерживать только RFC 3261 [2]. Потоки вызовов для UA, не осведомлённых о конференции, в этом документе в целом не показаны, поскольку они совпадали бы с потоками в документе о базовых примерах потоков вызовов SIP [13].
Note that the presence of an 'isfocus' feature tag in a Contact header field will not cause interoperability issues between a focus and a conference-unaware UA since it will be treated as an unknown header parameter and ignored, as per standard SIP behavior.
Обратите внимание, что наличие тега признака 'isfocus' в поле заголовка Contact не вызовет проблем совместимости между фокусом и UA, не осведомлённым о конференции, поскольку он будет рассматриваться как неизвестный параметр заголовка и игнорироваться в соответствии со стандартным поведением SIP.
3.4. Conference-Aware UA
3.4. UA, осведомлённый о конференции
A conference-aware user agent supports SIP conferencing call control conventions defined in this document as a conference participant, in addition to support of RFC 3261 [2]. A conference-aware UA should be able to process SIP redirections such as described in Section 8.1.3.4 of RFC 3261.
Пользовательский агент, осведомлённый о конференции, поддерживает соглашения управления вызовом для конференций SIP, определённые в этом документе, как участник конференции, в дополнение к поддержке RFC 3261 [2]. UA, осведомлённый о конференции, должен уметь обрабатывать перенаправления SIP, подобные описанным в разделе 8.1.3.4 RFC 3261.
A conference-aware UA MUST recognize the 'isfocus' feature parameter. A conference-aware UA SHOULD support REFER [4], SIP events [3], and the conferencing package [9].
UA, осведомлённый о конференции, ДОЛЖЕН распознавать параметр-признак 'isfocus'. UA, осведомлённый о конференции, СЛЕДУЕТ поддерживать REFER [4], события SIP [3] и пакет конференций [9].
A conference-aware UA SHOULD subscribe to the conference package if the 'isfocus' parameter is in the remote target URI of a dialog and if the conference package is listed by a focus in an Allow-Events header field. The SUBSCRIBE to the conference package SHOULD be sent outside any INVITE-initiated dialog. A termination of the INVITE dialog with a BYE does not necessarily terminate the SUBSCRIBE dialog.
UA, осведомлённый о конференции, СЛЕДУЕТ подписываться на пакет конференции, если параметр 'isfocus' присутствует в URI удалённой цели диалога и если пакет конференции указан фокусом в поле заголовка Allow-Events. SUBSCRIBE на пакет конференции СЛЕДУЕТ отправлять вне любого диалога, инициированного INVITE. Завершение диалога INVITE с помощью BYE не обязательно завершает диалог SUBSCRIBE.
A conference-aware UA MAY render to the user any information about the conference obtained from the SIP header fields and SDP fields from the focus.
UA, осведомлённый о конференции, МОЖЕТ отображать пользователю любую информацию о конференции, полученную из полей заголовков SIP и полей SDP от фокуса.
A conference-aware UA SHOULD render to the user any information about the conference obtained from the SIP conference package.
UA, осведомлённый о конференции, СЛЕДУЕТ отображать пользователю любую информацию о конференции, полученную из пакета конференции SIP.
4. Usage of the 'isfocus' Feature Parameter
4. Использование параметра-признака 'isfocus'
4.1. General
4.1. Общие сведения
The main design guidelines for the development of SIP extensions and conventions for conferencing are to define the minimum number of extensions and to have seamless backward compatibility with conference-unaware SIP UAs. The minimal requirement for SIP is being able to express that a dialog is a part of a certain conference referenced to by a URI. As a result of these extensions, it is possible to do the following using SIP:
Основные принципы проектирования расширений и соглашений SIP для конференций состоят в том, чтобы определить минимальное число расширений и обеспечить бесшовную обратную совместимость с UA SIP, не осведомлёнными о конференции. Минимальное требование к SIP — возможность выразить, что диалог является частью определённой конференции, на которую ссылается URI. В результате этих расширений с помощью SIP можно делать следующее:
- Create a conference - Join a conference - Invite a user to a conference - Expel a user by third party - Discover if a URI is a conference URI - Delete a conference
- Создать конференцию - Присоединиться к конференции - Пригласить пользователя в конференцию - Исключить пользователя третьей стороной - Обнаружить, является ли URI URI конференции - Удалить конференцию
The approach taken is to use the feature parameter 'isfocus' to express that a SIP dialog belongs to a conference. The use of feature parameters in Contact header fields to describe the characteristics and capabilities of a UA is described in the User Agent Capabilities document [5], which includes the definition of the 'isfocus' feature parameter.
Принятый подход состоит в использовании параметра-признака 'isfocus', чтобы выразить, что диалог SIP принадлежит конференции. Использование параметров-признаков в полях заголовка Contact для описания характеристик и возможностей UA описано в документе о возможностях пользовательского агента [5], который включает определение параметра-признака 'isfocus'.
4.2. Session Establishment
4.2. Установление сессии
In session establishment, a focus MUST include the 'isfocus' feature parameter in the Contact header field unless the focus wishes to hide the fact that it is a focus. To a participant, the feature parameter will be associated with the remote target URI of the dialog. It is an indication to a conference-aware UA that the resulting dialog belongs to a conference, identified by the URI in the Contact header field, and that the call control conventions defined in this document can be applied.
При установлении сессии фокус ДОЛЖЕН включать параметр-признак 'isfocus' в поле заголовка Contact, если только фокус не желает скрыть тот факт, что он является фокусом. Для участника параметр-признак будет связан с URI удалённой цели диалога. Это указание осведомлённому о конференции UA о том, что результирующий диалог принадлежит конференции, идентифицируемой URI в поле заголовка Contact, и что к нему можно применять соглашения управления вызовом, определённые в этом документе.
By their nature, the conferences supported by this specification are centralized. Therefore, typically a conferencing system needs to allocate a SIP conference URI such that SIP requests to this URI are not forked and are routed to a dedicated conference focus. For example, a globally accessible SIP conference could be well constructed with a conference URI using a Globally Routable User Agent URI (GRUU) (defined in [16]), because of its ability to support the non-forking and global routability requirements.
По своей природе конференции, поддерживаемые этой спецификацией, являются централизованными. Поэтому обычно системе конференций необходимо выделить URI конференции SIP так, чтобы запросы SIP на этот URI не разветвлялись и маршрутизировались к выделенному фокусу конференции. Например, глобально доступная конференция SIP могла бы быть удачно построена с URI конференции на основе глобально маршрутизируемого URI пользовательского агента (GRUU) (определённого в [16]) благодаря его способности удовлетворять требованиям отсутствия разветвления и глобальной маршрутизации.
4.3. Discovery
4.3. Обнаружение
Using the mechanism described in this section, it is possible, given an opaque URI, to determine if it belongs to a certain conference (i.e., meaning that it is a conference URI) or not. This discovery function can be implemented in SIP using an OPTIONS request, and can be done either inside an active dialog or outside a dialog. A focus MUST include the 'isfocus' feature parameter in a 200 OK response to an OPTIONS unless the focus wishes to hide the fact that it is a focus.
С помощью механизма, описанного в этом разделе, можно для заданного непрозрачного URI определить, принадлежит ли он определённой конференции (т. е. означает ли он URI конференции). Эту функцию обнаружения можно реализовать в SIP с помощью запроса OPTIONS, причём как внутри активного диалога, так и вне диалога. Фокус ДОЛЖЕН включать параметр-признак 'isfocus' в ответ 200 OK на OPTIONS, если только фокус не желает скрыть тот факт, что он является фокусом.
5. SIP Conferencing Primitives
5. Примитивы конференций SIP
The SIP conferencing call control flows presented in this section are the call control building blocks for various SIP conferencing applications as described in the conferencing requirements [14] and framework [8] documents. The major design goal is that the same SIP conferencing primitives would be used by user agents having different conferencing capabilities and implementing different applications.
Представленные в этом разделе потоки управления вызовом для конференций SIP являются строительными блоками управления вызовом для различных приложений конференций SIP, описанных в документах о требованиях к конференциям [14] и об архитектуре [8]. Основная цель проектирования состоит в том, чтобы одни и те же примитивы конференций SIP использовались пользовательскими агентами с разными возможностями конференций и реализующими разные приложения.
5.1. INVITE: Joining a Conference Using the Conference URI - Dial-In
5.1. INVITE: присоединение к конференции по её URI — входящий набор
In this section, a user knows the conference URI and "dials in" to join this conference. The focus will authenticate the participant and apply authorization policy before allowing the participant to join the conference.
В этом разделе пользователь знает URI конференции и «набирает номер», чтобы присоединиться к этой конференции. Фокус аутентифицирует участника и применяет политику авторизации, прежде чем разрешить участнику присоединиться к конференции.
If the UA is the first participant of the conference to dial-in, it is likely that this INVITE will activate the focus and hence the conference. However, the conference URI must have been reserved prior to its use.
Если UA является первым участником конференции, набирающим номер, вполне вероятно, что этот INVITE активирует фокус и, следовательно, конференцию. Однако URI конференции должен быть зарезервирован до его использования.
If the conference is up and running already, the dialing-in participant is joined to the conference by its focus.
Если конференция уже работает, набирающий номер участник присоединяется к конференции своим фокусом.

5.3. INVITE: Manually Creating a Conference by Dialing in to a Conferencing Application
5.3. INVITE: создание конференции вручную набором номера приложения конференции
In this section, a user sends an INVITE to a conference server application. The application (such as an IVR system or a web page) is implemented because the system requires additional input from the user before it is able to create a conference. After a normal dialog is established, additional information is received and the conference together with its focus are created. Since the UA is now in a dialog with a focus, the focus will re-INVITE the user with the conference URI in Contact with the 'isfocus' feature parameter.
В этом разделе пользователь отправляет INVITE приложению сервера конференций. Приложение (например, система IVR или веб-страница) реализуется, поскольку системе требуется дополнительный ввод от пользователя, прежде чем она сможет создать конференцию. После установления обычного диалога поступает дополнительная информация, и создаются конференция и её фокус. Поскольку теперь UA находится в диалоге с фокусом, фокус повторно пригласит пользователя с помощью re-INVITE, указав URI конференции в Contact с параметром-признаком 'isfocus'.
Alternatively, the additional information can be provided by the user during an early dialog (see RFC 3261 [2] for a discussion of early dialogs in SIP). This could be accomplished by a 183 Session Progress response sent by the conferencing application. After the conference is created, the conference URI would then be returned in a Contact in the 200 OK.
В качестве альтернативы дополнительную информацию может предоставить пользователь во время раннего диалога (см. RFC 3261 [2] для обсуждения ранних диалогов в SIP). Это можно было бы сделать с помощью ответа 183 Session Progress, отправленного приложением конференции. После создания конференции URI конференции затем был бы возвращён в Contact в ответе 200 OK.
Note that since this flow is all about human interaction with a conferencing application, any errors and failures will be returned to the human (recorded announcements, error tones, etc.).

5.4. INVITE: Creating a Conference Using Ad-Hoc SIP Methods
5.4. INVITE: создание конференции методами ad-hoc SIP
This section addresses creating a conference by using ad-hoc SIP means. The conference factory URI (as defined in Section 3.2) is used to automatically create the conference in this example. This is different from the previous scenario in that no human intervention is required -- an automaton can create the conference and add participants. Since the conference does not need to be scheduled or reserved, but is created "on the fly", it is an "ad-hoc" conference creation. The benefit of this approach is that the conference URI need not be known to the user; instead it is created by a focus and used by the participants' UAs. The main difference between this scenario and Section 5.3 is that no user intervention (IVR, web page form, etc.) is required to create the conference.
В этом разделе рассматривается создание конференции с помощью специальных средств SIP. В этом примере URI фабрики конференций (как определено в разделе 3.2) используется для автоматического создания конференции. Это отличается от предыдущего сценария тем, что не требуется вмешательства человека — автомат может создать конференцию и добавить участников. Поскольку конференцию не нужно планировать или резервировать, а она создаётся «на лету», это «специальное» создание конференции. Преимущество этого подхода в том, что URI конференции не обязательно должен быть известен пользователю; вместо этого он создаётся фокусом и используется UA участников. Основное отличие этого сценария от раздела 5.3 состоит в том, что для создания конференции не требуется вмешательства пользователя (IVR, форма веб-страницы и т. п.).
The SIP URI of the conference factory can be provisioned in the UA (as in a "create new conference" button on a SIP phone) or can be discovered using other means.
URI SIP фабрики конференций можно предварительно настроить в UA (как кнопку «создать новую конференцию» на SIP-телефоне) или обнаружить другими средствами.
A SIP entity (such as conferencing server) can distinguish this INVITE request as a request to create a new ad-hoc conference from a request to join an existing conference by the Request-URI. That is, although both requests may route to the same application, the differing services requested can be identified by the differing URIs in the request itself.
Объект SIP (например, сервер конференций) может отличить этот запрос INVITE как запрос на создание новой специальной конференции от запроса на присоединение к существующей конференции по Request-URI. То есть, хотя оба запроса могут маршрутизироваться в одно и то же приложение, разные запрашиваемые услуги можно идентифицировать по разным URI в самом запросе.
Assuming that all security and policy requirements have been met, a new conference will be created with the Contact URI returned in the 200 OK being the conference URI. The Contact header field MUST contain the 'isfocus' feature parameter to indicate that this URI is for a conference.
При условии, что все требования безопасности и политики выполнены, будет создана новая конференция, а URI Contact, возвращённый в 200 OK, будет URI конференции. Поле заголовка Contact ДОЛЖНО содержать параметр-признак 'isfocus', чтобы указать, что этот URI предназначен для конференции.

5.5. REFER: Requesting a Focus to Add a New Resource to a Conference (Dial Out to a New Participant)
5.5. REFER: запрос фокусу на добавление нового ресурса в конференцию (исходящий набор новому участнику)
A SIP conference URI can be used to inject different kinds of information into the conference. Examples include new participants, new real-time media sources, new IM messages, and pointers to passive information references (such as HTTP URIs).
URI конференции SIP можно использовать для внедрения в конференцию информации разных видов. Примеры включают новых участников, новые источники медиаданных в реальном времени, новые сообщения IM и указатели на пассивные информационные ссылки (такие как URI HTTP).
To request that the focus add a new information resource to the specified conference, any SIP UA can send a REFER to the conference URI with a Refer-To containing the URI of the new resource. Since this REFER is sent to the conference URI and not the conference factory URI, the semantics to the focus are to bring the resource into the conference and make it visible to the conference participants. The resultant focus procedures are dependent both on the nature of the new resource (as expressed by its URI) and the policy of the focus regarding IM, central vs. distributed real-time media processing, and so on.
Чтобы запросить у фокуса добавление нового информационного ресурса в указанную конференцию, любой UA SIP может отправить REFER на URI конференции с Refer-To, содержащим URI нового ресурса. Поскольку этот REFER отправляется на URI конференции, а не на URI фабрики конференций, семантика для фокуса состоит в том, чтобы ввести ресурс в конференцию и сделать его видимым участникам конференции. Результирующие процедуры фокуса зависят как от природы нового ресурса (выраженной его URI), так и от политики фокуса в отношении IM, централизованной или распределённой обработки медиаданных в реальном времени и т. д.
The scenario for adding a new UA participant is important to support because it works even if the new participant does not support REFER and transfer call control -- only the requesting participant and the focus need to support the REFER and transfer call control.
Сценарий добавления нового участника UA важно поддерживать, поскольку он работает, даже если новый участник не поддерживает REFER и управление вызовом с переводом — только запрашивающий участник и фокус должны поддерживать REFER и управление вызовом с переводом.
Upon receipt of the REFER containing a Refer-To header with a SIP URI, the focus SHOULD send an INVITE to the new participant identified by the Refer-To SIP URI containing a Contact header field with the conference URI and the 'isfocus' feature parameter.
Получив REFER, содержащий заголовок Refer-To с URI SIP, фокус СЛЕДУЕТ отправить INVITE новому участнику, идентифицированному URI SIP из Refer-To, содержащий поле заголовка Contact с URI конференции и параметром-признаком 'isfocus'.
A conference-unaware UA would simply ignore the conferencing information and treat the session (from a SIP perspective) as a point-to-point session.
UA, не осведомлённый о конференции, просто проигнорировал бы информацию о конференции и рассматривал бы сессию (с точки зрения SIP) как двухточечную сессию.

5.9. Replaces Header Field: Switching User Agents within a Conference
5.9. Поле заголовка Replaces: смена пользовательских агентов в конференции
Participants in a conference may want to change the user agent (i.e., the endpoint or the device) with which they participate in the conference. This could be done by simply sending a BYE from one user agent to leave the conference and an INVITE from the other user agent to rejoin. However, the SIP Replaces [6] primitive is perfectly suited to this operation.
Участники конференции могут захотеть сменить пользовательский агент (т. е. конечную точку или устройство), с которого они участвуют в конференции. Это можно было бы сделать, просто отправив BYE от одного пользовательского агента, чтобы покинуть конференцию, и INVITE от другого пользовательского агента, чтобы присоединиться снова. Однако примитив SIP Replaces [6] идеально подходит для этой операции.
An example is shown in Figure 9. It is assumed that Alice is a participant of the conference using user agent #1. The dialog identifier between Alice's user agent #1 and the focus is abbreviated as A-F. Alice switches to user agent #2 and sends an INVITE message F1 to the focus containing a Replaces header that contains the dialog identifier A-F. Note that this dialog identifier could be learned through some non-SIP mechanism, or by use of SUBSCRIBE/NOTIFY and the dialog event package [18]. Alice's user agent #2 is added into the conference by the focus. The focus sends a BYE to user agent #1. User agent #1 then automatically terminates the subscription by sending a SUBSCRIBE with Expires:0 to terminate the subscription. Note that the participant list (roster) has not necessarily changed during this scenario, unless detailed information about Alice user agents (i.e. endpoints) is included in the conference state notifications. For a full discussion of conference package notifications, refer to [9].

6. Security Considerations
6. Вопросы безопасности
This specification defines the interaction between a focus UA and a participant UA in a conferencing application. As a result, the security considerations and mechanisms defined in RFC 3261 [2] apply. However, there are some aspects unique to conferencing that will be discussed here.
Эта спецификация определяет взаимодействие между фокус-UA и UA-участником в приложении конференции. В результате применяются соображения безопасности и механизмы, определённые в RFC 3261 [2]. Однако есть некоторые аспекты, уникальные для конференций, которые будут рассмотрены здесь.
A conference often involves the use of substantial network bandwidth and computing resources. As a result, authentication is even more important than in a simple peer-to-peer session. As discussed in the conferencing framework [8], conferences often have policy related to conferencing resources. A focus SHOULD authenticate participants before joining them to a conference and allowing utilization of conferencing resources. Different policies can be applied by a focus to different participants based on the result of authentication.
Конференция часто связана с использованием значительной пропускной способности сети и вычислительных ресурсов. В результате аутентификация даже важнее, чем в простой равноправной сессии. Как обсуждается в архитектуре конференций [8], конференции часто имеют политику в отношении ресурсов конференций. Фокус СЛЕДУЕТ аутентифицировать участников, прежде чем присоединять их к конференции и разрешать использование ресурсов конференций. Фокус может применять разные политики к разным участникам в зависимости от результата аутентификации.
A participant will be interacting with a number of other participants through the focus. As a result, a participant should authenticate the focus and be sure that the focus used for the conference is trusted. Normal SIP authentication mechanisms are suitable for participant and focus authentication, such as SIP Digest utilizing a shared secret, or certificates, or a secured SIP identity mechanism. In addition, a focus SHOULD support Secure SIP connections so that hop-by-hop mutual authentication and confidentiality provided by TLS can be achieved.
Участник будет взаимодействовать с рядом других участников через фокус. В результате участник должен аутентифицировать фокус и убедиться, что фокус, используемый для конференции, является доверенным. Обычные механизмы аутентификации SIP подходят для аутентификации участника и фокуса, например SIP Digest с использованием общего секрета, или сертификаты, или защищённый механизм идентификации SIP. Кроме того, фокус СЛЕДУЕТ поддерживать защищённые соединения SIP, чтобы можно было обеспечить взаимную аутентификацию между узлами и конфиденциальность, предоставляемые TLS.
In the SIP dialog between them, a focus utilizes the 'isfocus' feature tag to indicate that the UA is acting as a focus. As such, the SIP header fields such as Contact SHOULD have end to end integrity. A participant and focus SHOULD support an end-to-end integrity mechanism such as S/MIME. Once a participant has learned that the other UA is a focus, SIP call control operations (such as REFER) can be implemented, or a subscription to the conference package of the focus might be attempted. The security considerations described in RFC 3515 [4] apply to any REFER call control operations. A focus and participant will apply policy to determine which call control operations are allowed.
В диалоге SIP между ними фокус использует тег признака 'isfocus', чтобы указать, что UA действует как фокус. Таким образом, поля заголовков SIP, такие как Contact, СЛЕДУЕТ защищать сквозной целостностью. Участник и фокус СЛЕДУЕТ поддерживать механизм сквозной целостности, такой как S/MIME. Как только участник узнал, что другой UA является фокусом, можно выполнять операции управления вызовом SIP (такие как REFER) или можно попытаться подписаться на пакет конференции фокуса. Соображения безопасности, описанные в RFC 3515 [4], применяются к любым операциям управления вызовом с REFER. Фокус и участник будут применять политику для определения того, какие операции управления вызовом разрешены.
A focus accepting subscriptions to the conference package must follow the security considerations in RFC 4575 [9]. Since notifications can carry sensitive information, the subscriptions should be authenticated and the notifications delivered with confidentiality and integrity protection. Since a participant is not able to authenticate other participants directly, a participant must rely on the focus to perform this authentication.
Фокус, принимающий подписки на пакет конференции, должен следовать соображениям безопасности в RFC 4575 [9]. Поскольку уведомления могут содержать конфиденциальную информацию, подписки следует аутентифицировать, а уведомления доставлять с защитой конфиденциальности и целостности. Поскольку участник не может напрямую аутентифицировать других участников, участник должен полагаться на фокус в выполнении этой аутентификации.
A focus MUST support a participant's request for privacy, either through conference policy or as expressed through the signaling. For example, a participant joining a conference and including a Privacy header field [10] must not have identity information revealed to other participants by the focus. If other signaling protocols are used, privacy signaled through them also must be respected.
Фокус ДОЛЖЕН поддерживать запрос участника на конфиденциальность, будь то через политику конференции или в том виде, как он выражен в сигнализации. Например, участник, присоединяющийся к конференции и включающий поле заголовка Privacy [10], не должен иметь информацию о личности, раскрываемую фокусом другим участникам. Если используются другие протоколы сигнализации, конфиденциальность, сигнализируемая через них, также должна соблюдаться.

Appendix A: Creating a Conference by a Conference-Unaware UA
Приложение A: создание конференции UA, не осведомлённым о конференции
This section discusses how a human user operating a conference- unaware UA can create and add participants to a conference. This method is described as an appendix since it is NOT RECOMMENDED. The scenarios involving creating a conference using ad-hoc or manual means are recommended over this scenario. This scenario is included, however, for completeness.
В этом разделе обсуждается, как человек-пользователь, управляющий UA, не осведомлённым о конференции, может создавать конференцию и добавлять в неё участников. Этот метод описан как приложение, поскольку он НЕ РЕКОМЕНДУЕТСЯ. Сценарии, предполагающие создание конференции специальными или ручными средствами, предпочтительнее этого сценария. Однако этот сценарий включён для полноты.
A user (human) would choose a conference URI according to system rules and insert it into the Request-URI of the INVITE. This same URI is echoed by a focus adhering to certain addressing conventions (discussed below) in the Contact header by the focus. Additional participants could be added by non-SIP means (publication of the chosen conference URI using web pages, email, IM, etc.). Alternatively, the conference-unaware UA could then add other participants to the conference using SIP call control by establishing a session with them, then transferring [17] them to the conference URI. Note that in this scenario only the user (human) is aware of the conferencing application, and the conference-unaware UA only need support RFC 3261 [2] and optionally call transfer.
Пользователь (человек) выбрал бы URI конференции в соответствии с системными правилами и вставил бы его в Request-URI запроса INVITE. Этот же URI фокус повторяет в поле заголовка Contact, придерживаясь определённых соглашений об адресации (обсуждаемых ниже). Дополнительных участников можно было бы добавить не-SIP средствами (публикация выбранного URI конференции с помощью веб-страниц, электронной почты, IM и т. п.). В качестве альтернативы UA, не осведомлённый о конференции, мог бы затем добавить других участников в конференцию с помощью управления вызовом SIP, установив с ними сессию и затем переведя [17] их на URI конференции. Обратите внимание, что в этом сценарии только пользователь (человек) осведомлён о приложении конференции, а UA, не осведомлённый о конференции, должен поддерживать только RFC 3261 [2] и, необязательно, перевод вызова.
Making this work does impose certain addressing conventions on a system. As a service/implementation choice, a system could allow the creator of the conference to choose the user portion of the conference URI. However, this requires the URI format to be agreed upon between a user and the system.
Чтобы это работало, на систему действительно накладываются определённые соглашения об адресации. Как выбор услуги или реализации, система могла бы позволить создателю конференции выбирать часть пользователя URI конференции. Однако это требует согласования формата URI между пользователем и системой.
For example, a service provider might reserve the domain conf.example.com for all conference URIs. Any URI in the domain of conf.example.com would resolve to the focus. The focus could be configured to interpret an unknown user part in the conf.example.com domain as a request for a conference to be created with the conference URI as the Request-URI. For example, an INVITE sent with a Request-URI of sip:k32934208ds72@conf.example.com could be routed to the focus that would then create the conference. This conference URI should be registered by the newly created focus to become routable as a conference URI within the conf.example.com domain. The returned Contact would look as follows:
Например, поставщик услуг мог бы зарезервировать домен conf.example.com для всех URI конференций. Любой URI в домене conf.example.com разрешался бы в фокус. Фокус можно было бы настроить так, чтобы интерпретировать неизвестную часть пользователя в домене conf.example.com как запрос на создание конференции с URI конференции в качестве Request-URI. Например, INVITE, отправленный с Request-URI sip:k32934208ds72@conf.example.com, мог бы быть маршрутизирован к фокусу, который затем создал бы конференцию. Этот URI конференции должен быть зарегистрирован только что созданным фокусом, чтобы стать маршрутизируемым как URI конференции в домене conf.example.com. Возвращённый Contact выглядел бы следующим образом:
Contact: <sip:k32934208ds72@conf.example.com>;isfocus
Contact: <sip:k32934208ds72@conf.example.com>;isfocus
Note, however, that this approach relies on conventions adopted between the user (human) and the focus. Also, the approach is not robust against collisions in the conference names. If a second user wishing to create a new conference happened to choose the same user part as an existing conference, the result would be that the second user would be added into the existing conference instead of creating a new one.
Однако обратите внимание, что этот подход опирается на соглашения, принятые между пользователем (человеком) и фокусом. Кроме того, подход не устойчив к коллизиям в именах конференций. Если бы второй пользователь, желающий создать новую конференцию, выбрал ту же часть пользователя, что и существующая конференция, результатом было бы то, что второй пользователь был бы добавлен в существующую конференцию вместо создания новой.
As a result, methods of conference creation in which the conference URI is an opaque URI generated by the focus are preferred.
В результате предпочтительны методы создания конференции, в которых URI конференции является непрозрачным URI, сгенерированным фокусом.
