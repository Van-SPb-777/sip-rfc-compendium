Abstract
Аннотация
This document describes a SIP Event Package "kpml" that enables monitoring of Dual Tone Multi-Frequency (DTMF) signals and uses Extensible Markup Language (XML) documents referred to as Key Press Markup Language (KPML). The kpml Event Package may be used to support applications consistent with the principles defined in the document titled "A Framework for Application Interaction in the Session Initiation Protocol (SIP)". The event package uses SUBSCRIBE messages and allows for XML documents that define and describe filter specifications for capturing key presses (DTMF Tones) entered at a presentation-free User Interface SIP User Agent (UA). The event package uses NOTIFY messages and allows for XML documents to report the captured key presses (DTMF tones), consistent with the filter specifications, to an Application Server. The scope of this package is for collecting supplemental key presses or mid-call key presses (triggers).
В этом документе описывается пакет событий SIP «kpml», который позволяет отслеживать сигналы двухтонального Multi-Frequency (DTMF) и использует документы расширяемого языка разметки (XML), называемые языком разметки нажатия клавиш (KPML). Пакет событий kpml можно использовать для поддержки приложений, соответствующих принципам, определенным в документе «Среда взаимодействия приложений в протоколе инициирования сессий (SIP)». Пакет событий использует сообщения SUBSCRIBE и допускает XML-документы, которые определяют и описывают характеристики фильтра для перехвата нажатий клавиш (тональные сигналы DTMF), введенные в пользовательском интерфейсе SIP User Agent (UA) без представления. Пакет событий использует сообщения NOTIFY и позволяет XML-документам сообщать серверу приложений о захваченных нажатиях клавиш (тонах DTMF) в соответствии со спецификациями фильтра. Объем этого пакета предназначен для сбора дополнительных нажатий клавиш или нажатий клавиш во время вызова (триггеров).
1. Introduction
1. Введение
This document describes a SIP Event Package "kpml" that enables monitoring of key presses and utilizes XML documents referred to as Key Press Markup Language (KPML). KPML is a markup [14] that enables presentation-free User Interfaces as described in the Application Interaction Framework [15]. The Key Press Stimulus Package is a SIP Event Notification Package [5] that uses the SUBSCRIBE and NOTIFY methods of SIP. The subscription filter and notification report bodies use the Keypad Markup Language, KPML.
В этом документе описывается пакет событий SIP «kpml», который позволяет отслеживать нажатия клавиш и использует документы XML, называемые языком разметки нажатия клавиш (KPML). KPML — это разметка [14], которая позволяет создавать пользовательские интерфейсы без презентаций, как описано в Application Interaction Framework [15]. Пакет стимулов нажатия клавиш — это пакет уведомлений о событиях SIP [5], в котором используются методы SIP SUBSCRIBE и NOTIFY. В фильтрах подписки и отчетах об уведомлениях используется язык разметки клавиатуры KPML.
The "kpml" event package requires the definition of two new MIME types, two new URN sub-namespaces, and two schemas for the KPML Request and the KPML Response. The scope of this package is for collecting supplemental key presses or mid-call key presses (triggers). This capability allows an Application Server service provider to monitor (filter) for a set of DTMF patterns at a SIP User Agent located in either an end-user device or a gateway.
Пакет событий «kpml» требует определения двух новых типов MIME, двух новых подпространств имен URN и двух схем для запроса KPML и ответа KPML. Объем этого пакета предназначен для сбора дополнительных нажатий клавиш или нажатий клавиш во время вызова (триггеров). Эта возможность позволяет поставщику услуг сервера приложений отслеживать (фильтровать) набор шаблонов DTMF в пользовательском агенте SIP, расположенном либо на устройстве конечного пользователя, либо на шлюзе.
In particular, the "kpml" event package enables "dumb phones" and "gateways" that receive signals from dumb phones to report user key- press events. Colloquially, this mechanism provides for "digit reporting" or "Dual Tone Multi-Frequency (DTMF) reporting." The capability eliminates the need for "hair-pinning" (routing media into and then out of the same device) through a Media Server or duplicating all the DTMF events, when an Application Server needs to trigger mid-call service processing on DTMF digit patterns.
В частности, пакет событий «kpml» позволяет «глупым телефонам» и «gateways», которые получают сигналы от «глупых телефонов», сообщать о событиях нажатия клавиш пользователем. В просторечии этот механизм обеспечивает «цифровую отчетность» или «двухтональный отчет Multi-Frequency (DTMF)». Эта возможность устраняет необходимость в «hair-pinning» (маршрутизации мультимедиа в одно и то же устройство и затем из него) через медиасервер или дублировании всех событий DTMF, когда серверу приложений необходимо инициировать обработку услуги в середине вызова по шаблонам цифр DTMF.
A goal of KPML is to fit in an extremely small memory and processing footprint.
Цель KPML — максимально компактно использовать память и вычислительные ресурсы.
The name of the XML document, KPML, reflects its legacy support role. The public switched telephony network (PSTN) accomplished signaling by transporting DTMF tones in the bearer channel (in-band signaling) from the user terminal to the local exchange.
Название XML-документа, KPML, отражает его устаревшую роль поддержки. Коммутируемая телефонная сеть общего пользования (PSTN) осуществляла передачу сигналов путем транспортировки тонов DTMF в несущем канале (внутриполосная сигнализация) от пользовательского терминала на местную телефонную станцию.
Voice-over-IP networks transport in-band signals with actual DTMF waveforms or RFC 2833 [10] packets. In RFC 2833, the signaling application inserts RFC 2833 named signal packets as well as, or instead of, generating tones in the media path. The receiving application receives the signal information in the media stream.
Сети Voice-over-IP передают внутриполосные сигналы с фактическими формами сигналов DTMF или пакетами RFC 2833 [10]. В RFC 2833 приложение сигнализации вставляет RFC 2833 именованные пакеты сигналов, а также или вместо генерации тональных сигналов в медиапоток. Принимающее приложение получает информацию о сигнале в медиапотоке.
RFC 2833 tones are ideal for conveying telephone-events point-to- point in a Real-time Transport Protocol (RTP) stream, as in the context of straightforward sessions like a 2-party call or a simple, centrally mixed conference. However, there are other environments where additional or alternative requirements are needed. These other environments include protocol translation and complex call control. An interested application could request notifications of every key press. However, many of the use cases for such signaling show that most applications are interested in only one or a few keystrokes. Thus a mechanism is needed for specifying to the user's interface what stimuli the application requires.
Тоны RFC 2833 идеально подходят для прямой передачи телефонных событий в потоке Real-time Транспортного протокола (RTP), например, в контексте простых сессий, таких как двухсторонний вызов или простая централизованно смешанная конференция. Однако существуют и другие среды, в которых необходимы дополнительные или альтернативные требования. Эти другие среды включают трансляцию протоколов и сложное управление вызовами. Заинтересованное приложение может запросить уведомления о каждом нажатии клавиши. Однако многие варианты использования такой сигнализации показывают, что большинству приложений требуется только одно или несколько нажатий клавиш. Таким образом, необходим механизм для указания пользовательскому интерфейсу, какие стимулы требуются приложению.

A KPML subscription can be persistent or one-shot. Persistent requests are active until the subscription terminates, the Application replaces the request, the Application deletes the request by sending a null document on the dialog, or the Application explicitly deletes the subscription by sending a SUBSCRIBE with an expires value of zero (0). One-shot requests terminate the subscription upon the receipt of DTMF values that provide a match. The "persist" KPML element specifies whether the subscription remains active for the duration specified in the SUBSCRIBE message or if it automatically terminates upon a pattern match.

NOTIFY messages can contain XML documents. If the User Interface matches a digitmap, the NOTIFY message (response) contains an XML document that indicates the User Input detected and whether the User Interface suppressed the representation of User Input, such as tones, or RFC 2833, from the media streams. If the User Interface encountered an error condition, such as a timeout, this will also be reported.
Сообщения NOTIFY могут содержать документы XML. Если пользовательский интерфейс соответствует цифровой карте, сообщение NOTIFY (ответ) содержит XML-документ, который указывает обнаруженный пользовательский ввод и то, подавил ли пользовательский интерфейс представление пользовательского ввода, например тональные сигналы или RFC 2833, из медиапотоков. 3. Key Concepts
3. Ключевые понятия
3.1. Subscription Duration
3.1. Продолжительность подписки
KPML recognizes two types of subscriptions: one-shot and persistent. Persistent subscriptions have two sub-types: continuous notify and single-notify.
KPML распознает два типа подписок: разовую и постоянную. Постоянные подписки имеют два подтипа: непрерывное уведомление и однократное уведомление.
One-shot subscriptions terminate after a pattern match occurs and a report is issued in a NOTIFY message. If the User Interface detects a key press stimulus that triggers a one-shot KPML event, then the User Interface (notifier) MUST set the "Subscription-State" in the NOTIFY message to "terminated". At this point, the User Interface MUST consider the subscription expired.
Подписки One-shot прекращаются после обнаружения совпадения с шаблоном и выдачи отчета в сообщении NOTIFY. Если пользовательский интерфейс обнаруживает стимул нажатия клавиши, который запускает одноразовое событие KPML, то пользовательский интерфейс (уведомитель) ДОЛЖЕН установить «Subscription-State» в сообщении NOTIFY на «terminated». На этом этапе пользовательский интерфейс ДОЛЖЕН считать, что срок действия подписки истек.
Persistent subscriptions remain active at the User Interface, even after a match. For continuous-notify persistent subscriptions, the User Interface will emit a NOTIFY message whenever the User Input matches a subscribed pattern. For single-notify persistent subscriptions, the user device will emit a NOTIFY message at the first match, but will not emit further NOTIFY messages until the Application issues a new subscription request on the subscription dialog. NOTE: The single-notify persistent subscription enables lock-step (race-free) quarantining of User Input between different digit maps.
Постоянные подписки остаются активными в пользовательском интерфейсе даже после совпадения. Для постоянных подписок с непрерывным уведомлением пользовательский интерфейс будет отправлять сообщение NOTIFY всякий раз, когда пользовательский ввод соответствует шаблону подписки. Для постоянных подписок с одним уведомлением пользовательское устройство будет отправлять сообщение NOTIFY при первом совпадении, но не будет отправлять дальнейшие сообщения NOTIFY до тех пор, пока Приложение не выдаст новый запрос на подписку в диалоговом окне подписки. ПРИМЕЧАНИЕ. Постоянная подписка с одним уведомлением обеспечивает поэтапный карантин (без гонок) пользовательского ввода между различными цифровыми картами.
The "persist" attribute to the <pattern> tag in the KPML subscription body affects the lifetime of the subscription.
Атрибут «persist» тега <pattern> в тексте подписки KPML влияет на срок действия подписки.
If the "persist" attribute is "one-shot", then once there is a match (or no match is possible), the subscription ends after the User Interface notifies the Application. If the "persist" attribute is "persist" or "single-notify", then the subscription ends when the Application explicitly ends it or the User Interface terminates the subscription.
Если атрибут «persist» равен «one-shot», то при обнаружении совпадения (или его невозможности) подписка завершается после того, как пользовательский интерфейс уведомляет приложение. Если атрибут «persist» равен «persist» или «single-notify», то подписка завершается, когда приложение явно завершает ее или пользовательский интерфейс прекращает подписку.
If the User Interface does not support persistent subscriptions, it returns a NOTIFY message with the KPML status code set to 531. If there are digits in the buffer and the digits match an expression in the SUBSCRIBE filter, the User Interface prepares the appropriate NOTIFY response message.
Если пользовательский интерфейс не поддерживает постоянные подписки, он возвращает сообщение NOTIFY с кодом состояния KPML, равным 531. Если в буфере есть цифры и они соответствуют выражению в фильтре SUBSCRIBE, пользовательский интерфейс подготавливает соответствующее ответное сообщение NOTIFY.
The values of the "persist" attribute are case sensitive.
Значения атрибута «persist» чувствительны к регистру.
3.2. Timers
3.2. Таймеры
To address the various key press collection scenarios, three timers are defined. They are the extra, critical, and inter-digit timers.
Для реализации различных сценариев сбора нажатий клавиш определены три таймера. Это дополнительные, критические и межразрядные таймеры.
o The inter-digit timer is the maximum time to wait between digits. Note: unlike Media Gateway Control Protocol (MGCP) [11] or H.248 [12], there is no start timer, as that concept does not apply in the KPML context.
o Межцифровой таймер — это максимальное время ожидания между цифрами. Примечание. В отличие от протокола управления медиашлюзом (MGCP) [11] или H.248 [12], здесь нет таймера запуска, поскольку эта концепция не применяется в контексте KPML.
o The critical timer is the time to wait for another digit if the collected digits can match more than one potential pattern.
o Критический таймер — это время ожидания следующей цифры, если собранные цифры могут соответствовать более чем одному потенциальному шаблону.
o The extra timer is the time to wait for another digit if the collected digits can only match one potential pattern, but a longer match for this pattern is possible.
o Дополнительный таймер — это время ожидания следующей цифры, если собранные цифры могут соответствовать только одному потенциальному шаблону, но для этого шаблона возможно более длительное совпадение.

The purpose of the inter-digit timeout is to protect applications from starting to match a pattern, yet never returning a result. This can occur, for example, if the user accidentally enters a key that begins to match a pattern. However, since the user accidentally entered the key, the rest of the pattern never comes. Moreover, when the user does enter a pattern, since they have already entered a key, the pattern may not match or may not match as expected. Likewise, consider the case where the user thinks they entered a key press, but the User Interface does not detect the key. This could occur when collecting ten digits, but the device actually only receives 9. In this case, the User Interface will wait forever for the tenth key press, while the user becomes frustrated wondering why the application is not responding.
Цель тайм-аута между цифрами — защитить приложения от начала сопоставления с шаблоном, но никогда не возвращающего результат. Это может произойти, например, если пользователь случайно вводит ключ, который начинает соответствовать шаблону. Однако, поскольку пользователь случайно ввел ключ, остальная часть шаблона так и не приходит. Более того, когда пользователь вводит шаблон, поскольку он уже ввел ключ, шаблон может не совпадать или не соответствовать ожиданиям. Аналогично рассмотрим случай, когда пользователь думает, что он нажал клавишу, но пользовательский интерфейс не обнаруживает клавишу. Это могло произойти при сборе десяти цифр, но на самом деле устройство получает только 9. В этом случае пользовательский интерфейс будет вечно ждать нажатия десятой клавиши, в то время как пользователь расстраивается, задаваясь вопросом, почему приложение не отвечает.
The User Interface MAY support a critical-digit timeout value. This is the amount of time the User Interface will wait for another key press when it already has a matched <regex> but there is another, longer <regex> that may also match the pattern. The application can specify the critical-digit timeout as an integer number of milliseconds by using the "criticaldigittimer" attribute to the <pattern> tag. The default is 1000 milliseconds.
Пользовательский интерфейс МОЖЕТ поддерживать значение тайм-аута критической цифры. Это время, в течение которого пользовательский интерфейс будет ожидать следующего нажатия клавиши, когда у него уже есть соответствующее <regex>, но есть другое, более длинное <regex>, которое также может соответствовать шаблону. Приложение может указать время ожидания критической цифры как целое число миллисекунд, используя атрибут «criticaldigittimer» тега <pattern>. Значение по умолчанию — 1000 миллисекунд.
The purpose of the critical-digit timeout is to allow the application to collect longer matches than the shortest presented. This is unlike MGCP [11], where the shortest match gets returned. For example, if the application registers for the patterns "0011", "011", "00", and "0", the critical-digit timeout enables the User Interface to distinguish between "0", "00", "011", and "0011". Without this feature, the only value that the User Interface can detect is "0".
Цель тайм-аута критической цифры — позволить приложению собирать более длинные совпадения, чем самое короткое из представленных. В этом отличие от MGCP [11], где возвращается самое короткое совпадение. Например, если приложение регистрирует шаблоны «0011», «011», «00» и «0», время ожидания критической цифры позволяет пользовательскому интерфейсу различать «0», «00», «011» и «0011». Без этой функции единственное значение, которое может обнаружить пользовательский интерфейс, — это «0».
The User Interface MAY support an extra-digit timeout value. This is the amount of time the User Interface will wait for another key press when it already has matched the longest <regex>. The application can specify the extra-digit timeout as an integer number of milliseconds by using the "extradigittimer" attribute to the <pattern> tag. The default is 500 milliseconds. If there is no enterkey specified, then the User Interface MAY default the exteradigittimer to zero.
Пользовательский интерфейс МОЖЕТ поддерживать значение тайм-аута для дополнительных цифр. Это время, в течение которого пользовательский интерфейс будет ждать следующего нажатия клавиши, если оно уже соответствует самому длинному <regex>. Приложение может указать тайм-аут дополнительных цифр в виде целого числа миллисекунд, используя атрибут «extradigittimer» тега <pattern>. Значение по умолчанию — 500 миллисекунд. Если клавиша ввода не указана, то пользовательский интерфейс МОЖЕТ по умолчанию установить экстерацифровой таймер равным нулю.
The purpose of the extra-digit timeout is to allow the User Interface to collect the enterkey. Without this feature, the User Interface would match the pattern, and the enterkey would be buffered and returned as the next pattern.
Цель тайм-аута дополнительных цифр — позволить пользовательскому интерфейсу получить вводимый ключ. Без этой функции пользовательский интерфейс будет соответствовать шаблону, а клавиша ввода будет помещена в буфер и возвращена как следующий шаблон.

3.4. Digit Suppression
3.4. Подавление цифр
Under basic operation, a KPML User Interface will transmit in-band tones (RFC 2833 [10] or actual tone) in parallel with User Input reporting. NOTE: If KPML did not have this behavior, then a User Interface executing KPML could easily break called applications. For example, take a personal assistant that uses "*9" for attention. If the user presses the "*" key, KPML will hold the digit, looking for the "9". What if the user just enters a "*" key, possibly because they accessed an interactive voice response (IVR) system that looks for "*"? In this case, the "*" would get held by the User Interface, because it is looking for the "*9" pattern. The user would probably press the "*" key again, hoping that the called IVR system just did not hear the key press. At that point, the User Interface would send both "*" entries, as "**" does not match "*9". However, that would not have the effect the user intended when they pressed "*".
В базовом режиме пользовательский интерфейс KPML будет передавать внутриполосные тональные сигналы (RFC 2833 [10] или фактический тональный сигнал) параллельно с отчетами о пользовательском вводе. ПРИМЕЧАНИЕ. Если бы KPML не имел такого поведения, то пользовательский интерфейс, выполняющий KPML, мог бы легко нарушить работу вызываемых приложений. Например, возьмем личного помощника, который использует «*9» для обозначения внимания. Если пользователь нажимает клавишу «*», KPML будет удерживать цифру в поисках «9». Что, если пользователь просто вводит клавишу «*», возможно, потому, что он получил доступ к системе интерактивного голосового ответа (IVR), которая ищет «*»? В этом случае «*» будет удерживаться пользовательским интерфейсом, поскольку он ищет шаблон «*9». Пользователь, вероятно, снова нажмет клавишу «*», надеясь, что вызываемая система IVR просто не услышала нажатие клавиши. В этот момент пользовательский интерфейс отправит обе записи «*», поскольку «**» не соответствует «*9». Однако это не имело бы того эффекта, которого ожидал пользователь, когда нажимал «*».
On the other hand, there are situations where passing through tones in-band is not desirable. Such situations include call centers that use in-band tone spills to initiate a transfer.
С другой стороны, существуют ситуации, когда передача внутриполосных тонов нежелательна. К таким ситуациям относятся центры обработки вызовов, которые используют внутриполосные тональные сигналы для инициирования перевода.
For those situations, KPML adds a suppression tag, "pre", to the <regex> tag. There MUST NOT be more than one <pre> tag in any given <regex> tag.
В таких ситуациях KPML добавляет тег подавления «pre» к тегу <regex>. В любом теге <regex> НЕ ДОЛЖНО быть более одного тега <pre>.
If there is only a single <pattern> and a single <regex>, suppression processing is straightforward. The end-point passes User Input until the stream matches the regular expression <pre>. At that point, the User Interface will continue collecting User Input, but will suppress the generation or pass-through of any in-band User Input.
Если есть только один <pattern> и один <regex>, обработка подавления проста. Конечная точка передает пользовательский ввод до тех пор, пока поток не будет соответствовать регулярному выражению <pre>. В этот момент пользовательский интерфейс продолжит собирать пользовательский ввод, но подавляет генерацию или передачу любого внутриполосного пользовательского ввода.
If the User Interface suppressed stimulus, it MUST indicate this by including the attribute "suppressed" with a value of "true" in the notification.
Если пользовательский интерфейс подавил стимул, он ДОЛЖЕН указать это, включив в уведомление атрибут «suppressed» со значением «true».
Clearly, if the User Interface is processing the KPML document against buffered User Input, it is too late to suppress the transmission of the User Input, as the User Interface has long sent the stimulus. This is a situation where there is a <pre> specification, but the "suppressed" attribute will not be "true" in the notification. If there is a <pre> tag that the User Interface matched and the User Interface is unable to suppress the User Input, it MUST set the "suppressed" attribute to "false".
Очевидно, что если пользовательский интерфейс обрабатывает документ KPML на основе буферизованного пользовательского ввода, уже слишком поздно подавлять передачу пользовательского ввода, поскольку пользовательский интерфейс уже давно отправил стимул. Это ситуация, когда есть спецификация <pre>, но атрибут «suppressed» не будет «true» в уведомлении. Если существует тег <pre>, которому соответствует пользовательский интерфейс, и пользовательский интерфейс не может подавить пользовательский ввод, он ДОЛЖЕН установить атрибут «suppressed» на «false».
A KPML User Interface MAY perform suppression. If it is not capable of suppression, it ignores the suppression attribute. It MUST set the "suppressed" attribute to "false". In this case, the pattern to match is the concatenated pattern of pre+value.
Пользовательский интерфейс KPML МОЖЕТ выполнять подавление. Если он не способен к подавлению, он игнорирует атрибут подавления. Он ДОЛЖЕН установить атрибут «suppressed» в «false». В этом случае сопоставляемый шаблон — это объединенный шаблон pre+value.
At some point in time, the User Interface will collect enough User Input to the point it matches a <pre> pattern. The interdigittimer attribute indicates how long to wait for the user to enter stimulus before reporting a time-out error. If the interdigittimer expires, the User Interface MUST issue a time-out report, transmit the suppressed User Input on the media stream, and stop suppression. Once the User Interface detects a match and it sends a NOTIFY request to report the User Input, the User Interface MUST stop suppression. Clearly, if subsequent User Input matches another <pre> expression, then the User Interface MUST start suppression.
В какой-то момент пользовательский интерфейс соберет достаточно пользовательского ввода до такой степени, что он будет соответствовать шаблону <pre>. Атрибут interdigittimer указывает, как долго ждать, пока пользователь введет стимул, прежде чем сообщить об ошибке тайм-аута. Если время межцифрового таймера истекает, пользовательский интерфейс ДОЛЖЕН выдать отчет об истечении времени ожидания, передать подавленный пользовательский ввод в медиапоток и прекратить подавление. Как только пользовательский интерфейс обнаруживает совпадение и отправляет запрос NOTIFY, чтобы сообщить о вводимых пользователем данных, пользовательский интерфейс ДОЛЖЕН прекратить подавление. Очевидно, что если последующий пользовательский ввод соответствует другому выражению <pre>, то пользовательский интерфейс ДОЛЖЕН начать подавление.
After suppression begins, it may become clear that a match will not occur. For example, take the expression
После начала подавления может стать ясно, что совпадения не произойдет. Например, возьмем выражение
<regex><pre>*8</pre>xxx[2-9]xxxxxx</regex>
<regex><pre>*8</pre>xxx[2-9]xxxxxx</regex>
At the point the User Interface receives "*8", it will stop forwarding stimulus. Let us say that the next three digits are "408". If the next digit is a zero or one, the pattern will not match. NOTE: It is critically important for the User Interface to have a sensible inter-digit timer. This is because an errant dot (".") may suppress digit sending forever.
В тот момент, когда пользовательский интерфейс получит «*8», он прекратит пересылку стимула. Допустим, следующие три цифры — «408». Если следующая цифра — ноль или единица, шаблон не будет совпадать. ПРИМЕЧАНИЕ. Крайне важно, чтобы пользовательский интерфейс имел разумный межцифровой таймер. Это связано с тем, что ошибочная точка («.») может навсегда подавить отправку цифр.
Applications should be very careful to indicate suppression only when they are fairly sure the user will enter a digit string that will match the regular expression. In addition, applications should deal with situations such as no-match or time-out. This is because the User Interface will hold digits, which will have obvious User Interface issues in the case of a failure.
Приложениям следует быть очень осторожными и указывать подавление только в том случае, если они абсолютно уверены, что пользователь введет строку цифр, которая будет соответствовать регулярному выражению. Кроме того, приложения должны иметь дело с такими ситуациями, как отсутствие совпадений или тайм-аут. Это связано с тем, что пользовательский интерфейс будет содержать цифры, что приведет к очевидным проблемам с пользовательским интерфейсом в случае сбоя.
3.5. User Input Buffer Behavior
3.5. Поведение буфера пользовательского ввода
User Interfaces MUST buffer User Input upon receipt of an authenticated and accepted subscription. Subsequent KPML documents apply their patterns against the buffered User Input. Some applications use modal interfaces where the first few key presses determine what the following key presses mean. For a novice user, the application may play a prompt describing what mode the application is in. However, "power users" often barge through the prompt.
Пользовательские интерфейсы ДОЛЖНЫ буферизовать пользовательский ввод после получения аутентифицированной и принятой подписки. Последующие документы KPML применяют свои шаблоны к буферизованному пользовательскому вводу. Некоторые приложения используют модальные интерфейсы, где первые несколько нажатий клавиш определяют, что означают последующие нажатия клавиш. Для начинающего пользователя приложение может воспроизвести подсказку, описывающую, в каком режиме находится приложение. Однако «опытные пользователи» часто пропускают подсказку.
User Interfaces MUST NOT provide a subscriber with digits that were detected prior to the authentication and authorization of that subscriber. Without prohibition, a subscriber might be able to gain access to calling card or other information that predated the subscriber's participation in the call. Note that this prohibition MUST be applied on a per-subscription basis.
Пользовательские интерфейсы НЕ ДОЛЖНЫ предоставлять подписчику цифры, которые были обнаружены до аутентификации и авторизации этого подписчика. Без запрета абонент может получить доступ к телефонной карте или другой информации, которая предшествовала участию абонента в вызове. Обратите внимание, что этот запрет ДОЛЖЕН применяться для каждой подписки.
KPML provides a <flush> tag in the <pattern> element. The default is not to flush User Input. Flushing User Input has the effect of ignoring key presses entered before the installation of the KPML subscription. To flush User Input, include the tag <flush>yes</flush> in the KPML subscription document. Note that this directive affects only the current subscription dialog/id combination.
KPML предоставляет тег <flush> в элементе <pattern>. По умолчанию не сбрасывается пользовательский ввод. Сброс пользовательского ввода приводит к игнорированию нажатий клавиш, введенных до установки подписки KPML. Чтобы очистить вводимые пользователем данные, включите тег <flush>yes</flush> в документ подписки KPML. Обратите внимание, что эта директива влияет только на текущую комбинацию диалога и идентификатора подписки.
Lock-step processing of User Input is where the User Interface issues a notification, the Application processes the notification while the User Interface buffers additional User Input, the Application requests more User Input, and only then does the User Interface notify the Application based on the collected User Input. To direct the User Interface to operate in lock-step mode, set the <pattern> attribute persist="single-notify".
Lock-step обработка пользовательского ввода — это когда пользовательский интерфейс выдает уведомление, приложение обрабатывает уведомление, в то время как пользовательский интерфейс буферизует дополнительный пользовательский ввод, приложение запрашивает дополнительный пользовательский ввод, и только тогда пользовательский интерфейс уведомляет приложение на основе собранного пользовательского ввода. Чтобы настроить пользовательский интерфейс для работы в пошаговом режиме, установите атрибут <pattern> persist=«single-notify».
The User Interface MUST be able to process <flush>no</flush>. This directive is effectively a no-op.
Пользовательский интерфейс ДОЛЖЕН иметь возможность обрабатывать <flush>no</flush>. Эта директива фактически неактивна.
Other string values for <flush> may be defined in the future. If the User Interface receives a string it does not understand, it MUST treat the string as a no-op.
Другие строковые значения для <flush> могут быть определены в будущем. Если пользовательский интерфейс получает строку, которую он не понимает, он ДОЛЖЕН рассматривать эту строку как недействующую.
If the user presses a key that cannot match any pattern within a <regex> tag, the User Interface MUST discard all buffered key presses up to and including the current key press from consideration against the current or future KPML documents on a given dialog. However, as described above, once there is a match, the User Interface buffers any key presses the user entered subsequent to the match. NOTE: This behavior allows applications to receive only User Input that is of interest to them. For example, a pre-paid application only wishes to monitor for a long pound. If the user enters other stimulus, presumably for other applications, the pre-paid application does not want notification of that User Input. This feature is fundamentally different than the behavior of Time Division Multiplexer (TDM)-based equipment where every application receives every key press.
Если пользователь нажимает клавишу, которая не может соответствовать ни одному шаблону в теге <regex>, пользовательский интерфейс ДОЛЖЕН исключить все нажатия клавиш в буфере, вплоть до текущего нажатия клавиши, из рассмотрения в отношении текущих или будущих документов KPML в данном диалоге. Однако, как описано выше, при обнаружении совпадения пользовательский интерфейс буферизует любые нажатия клавиш, введенные пользователем после совпадения. ПРИМЕЧАНИЕ. Такое поведение позволяет приложениям получать только тот пользовательский ввод, который им интересен. Например, предоплаченное приложение хочет отслеживать только длинные фунты. Если пользователь вводит другой стимул, предположительно для других приложений, предоплаченное приложение не требует уведомления об этом вводе пользователя. Эта функция фундаментально отличается от поведения оборудования на основе мультиплексора с временным разделением (TDM), где каждое приложение получает каждое нажатие клавиши.
To limit reports to only complete matches, set the "nopartial" attribute to the <pattern> tag to "true". In this case, the User Interface attempts to match a rolling window over the collected User input.
Чтобы ограничить отчеты только полными совпадениями, установите для атрибута «nopartial» тега <pattern> значение «true». В этом случае пользовательский интерфейс пытается сопоставить скользящее окно с собранными входными данными пользователя.
KPML subscriptions are independent. Thus, it is not possible for the current document to know if a following document will enable barging or want User Input flushed. Therefore, the User Interface MUST buffer all User Input, subject to the forced_flush caveat described below. On a given SUBSCRIBE dialog with a given id, the User Interface MUST buffer all User Input detected between the time of the report and the receipt of the next document, if any. If the next document indicates a buffer flush, then the interpreter MUST flush all collected User Input from consideration from KPML documents received on that dialog with the given event id. If the next document does not indicate flushing the buffered User Input, then the interpreter MUST apply the collected User Input (if possible) against the digit maps presented by the script's <regex> tags. If there is a match, the interpreter MUST follow the procedures in Section 5.3. If there is no match, the interpreter MUST flush all of the collected User Input.
Подписки KPML независимы. Таким образом, текущий документ не может знать, будет ли следующий документ включать барджинг или хочет ли он сбросить пользовательский ввод. Следовательно, пользовательский интерфейс ДОЛЖЕН буферизовать весь пользовательский ввод с учетом предупреждения о принудительной очистки, описанного ниже. В данном диалоговом окне ПОДПИСАТЬСЯ с заданным идентификатором пользовательский интерфейс ДОЛЖЕН буферизовать весь пользовательский ввод, обнаруженный между моментом отчета и получением следующего документа, если таковой имеется. Если следующий документ указывает на очистку буфера, то интерпретатор ДОЛЖЕН очистить весь собранный пользовательский ввод из рассмотрения из документов KPML, полученных в этом диалоге с заданным идентификатором события. Если следующий документ не указывает на очистку буферизованного пользовательского ввода, то интерпретатор ДОЛЖЕН применить собранный пользовательский ввод (если возможно) к цифровым картам, представленным тегами <regex> сценария. Если совпадение имеется, переводчик ДОЛЖЕН следовать процедурам, описанным в разделе 5.3. Если совпадений нет, интерпретатор ДОЛЖЕН сбросить весь собранный пользовательский ввод.
Given the potential for needing an infinite buffer for User Input, the User Interface MAY discard the oldest User Input from the buffer. If the User Interface discards digits, when the User Interface issues a KPML notification, it MUST set the forced_flush attribute of the <response> tag to "true". For future use, the Application MUST consider any non-null value, other than "false", that it does not understand to be the same as "true". NOTE: The requirement to buffer all User Input for the entire length of the session is not onerous under normal operation. For example, if one has a gateway with 8,000 sessions, and the gateway buffers 50 key presses on each session, the requirement is only 400,000 bytes, assuming one byte per key press.
Учитывая потенциальную необходимость бесконечного буфера для пользовательского ввода, пользовательский интерфейс МОЖЕТ удалить самый старый пользовательский ввод из буфера. Если пользовательский интерфейс отбрасывает цифры, когда пользовательский интерфейс выдает уведомление KPML, он ДОЛЖЕН установить атрибут принудительного_флеша тега <response> на «true». Для будущего использования Приложение ДОЛЖНО учитывать любое ненулевое значение, кроме «false», которое, по его мнению, не совпадает с «true». ПРИМЕЧАНИЕ. Требование буферизировать весь пользовательский ввод на протяжении всего сессии не является обременительным при нормальной работе. Например, если у вас есть шлюз с 8000 сессиями и шлюз буферизует 50 нажатий клавиш в каждом сессии, требование составляет всего 400 000 байт, при условии, что на каждое нажатие клавиши приходится один байт.
Unless there is a suppress indicator in the digit map, it is not possible to know if the User Input is for local KPML processing or for other recipients of the media stream. Thus, in the absence of a suppression indicator, the User Interface transmits the User Input to the far end in real time, using either RFC 2833, generating the appropriate tones, or both.
Если в карте цифр нет индикатора подавления, невозможно узнать, предназначен ли пользовательский ввод для локальной обработки KPML или для других получателей медиапотока. Таким образом, при отсутствии индикатора подавления пользовательский интерфейс передает пользовательский ввод на дальний конец в реальном времени, используя либо RFC 2833, генерируя соответствующие тональные сигналы, либо и то, и другое.
3.6. DRegex
3.6. DRegex
3.6.1. Overview
3.6.1. Обзор
This subsection is informative in nature.
Данный подраздел носит информативный характер.
The Digit REGular EXpression (DRegex) syntax is a telephony-oriented mapping of POSIX Extended Regular Expressions (ERE) [13].
Синтаксис Digit REGular EXpression (DRegex) представляет собой ориентированное на телефонию отображение расширенных регулярных выражений POSIX (ERE) [13].
KPML does not use full POSIX ERE for the following reasons.
KPML не использует полную версию POSIX ERE по следующим причинам.
o KPML will often run on high density or extremely low power and memory footprint devices.
o KPML часто работает на устройствах с высокой плотностью или чрезвычайно низким энергопотреблением и объемом памяти.
o Telephony application convention uses the star symbol ("*") for the star key and "x" for any digit 0-9. Requiring the developer to escape the star ("\*") and expand the "x" ("[0-9]") is error prone. This also leads DRegex to use the dot (".") to indicate repetition, which was the function of the unadorned star in POSIX ERE.
o В соответствии с соглашением телефонных приложений для звездочки используется символ звездочки («*») и «x» для любой цифры от 0 до 9. Требование от разработчика убрать звездочку («\*») и расширить «x» («[0-9]») чревато ошибками. Это также приводит к тому, что DRegex использует точку («.») для обозначения повторения, что было функцией неукрашенной звезды в POSIX ERE.
o Implementation experience with MGCP [11] and H.248.1 [12] has been that implementers and users have a hard time understanding the precedence of the alternation operator ("|"). This is due both to an under-specification of the operator in those documents and conceptual problems for users. Thus, the SIPPING Working Group concluded that DRegex should not support alternation. That said, each KPML <pattern> element may contain multiple regular expressions (<regex> elements). Thus, it is straightforward to have pattern alternatives (use multiple <regex> elements) without the problems associated with the alternation operator ("|"). Thus, DRegex does not support the POSIX alternation operator.
o Опыт реализации MGCP [11] и H.248.1 [12] показал, что разработчики и пользователи с трудом понимают приоритет оператора чередования («|»). This is due both to an under-specification of the operator in those documents and conceptual problems for users. Thus, the SIPPING Working Group concluded that DRegex should not support alternation. That said, each KPML <pattern> element may contain multiple regular expressions (<regex> elements). Таким образом, легко иметь альтернативы шаблону (используйте несколько элементов <regex>) без проблем, связанных с оператором чередования («|»). Thus, DRegex does not support the POSIX alternation operator.
o DRegex includes character classes (characters enclosed in square brackets). However, the negation operator inside a character class only operates on numbers. That is, a negation class implicitly includes A-D, *, and #. Including A-D, *, and # in a negation operator is a no-op. Those familiar with POSIX would expect negation of the digits 4 and 5 (e.g., "[^45]") to include all other characters (including A-D, R, *, and #), while those familiar with telephony digit maps would expect negation to implicitly exclude non-digit characters. Since the complete character set of DRegex is very small, constructing a negation class using A-D, R, *, and # requires the user to specify the positive inverse mapping. For example, to specify all key presses, including A-D and *, except #, the specification would be "[0-9A-D*]" instead of "[^#R]".
o DRegex включает классы символов (символы, заключенные в квадратные скобки). Однако оператор отрицания внутри класса символов работает только с числами. То есть класс отрицания неявно включает A-D, * и #. Включение A-D, * и # в оператор отрицания является недопустимым. 3.7. Monitoring Direction
3.7. Направление мониторинга
SIP identifies dialogs by their dialog identifier. The dialog identifier is the remote-tag, local-tag, and Call-ID entities defined in RFC 3261 [4].
SIP идентифицирует диалоги по их идентификатору диалога. Идентификатором диалога являются объекты удаленного тега, локального тега и Call-ID, определенные в RFC 3261 [4].
One method of determining the dialog identifier, particularly for third-party applications, is the SIP Dialog Package [17].
Одним из методов определения идентификатора диалога, особенно для сторонних приложений, является пакет диалогов SIP [17].
For most situations, such as a monaural point-to-point call with a single codec, the stream to monitor is obvious. In such situations the Application need not specify which stream to monitor.
В большинстве ситуаций, таких как монофонический вызов «точка-точка» с одним кодеком, поток для мониторинга очевиден. В таких ситуациях Приложению не нужно указывать, какой поток отслеживать.
But there may be ambiguity in specifying only the SIP dialog to monitor. The dialog may specify multiple SDP streams that could carry key press events. For example, a dialog may have multiple audio streams. Wherever possible, the User Interface MAY apply local policy to disambiguate which stream or streams to monitor. In order to have an extensible mechanism for identifying streams, the mechanism for specifying streams is as an element content to the <stream> tag. The only content defined today is the <stream>reverse</stream> tag.
Но может возникнуть неоднозначность при указании для мониторинга только диалогового окна SIP. В диалоговом окне можно указать несколько потоков SDP, которые могут переносить события нажатия клавиш. Например, диалог может иметь несколько аудиопотоков. Везде, где это возможно, пользовательский интерфейс МОЖЕТ применять локальную политику для устранения неоднозначности, какой поток или потоки следует отслеживать. Чтобы иметь расширяемый механизм идентификации потоков, механизм указания потоков представляет собой содержимое элемента тега <stream>. Единственное содержимое, определенное на сегодняшний день, — это тег <stream>reverse</stream>.
By default, the User Interface monitors key presses emanating from the User Interface. Given a dialog identifier of Call-ID, local-tag, and remote-tag, the User Interface monitors the key presses associated with the local-tag.
По умолчанию пользовательский интерфейс отслеживает нажатия клавиш, исходящие из пользовательского интерфейса. Учитывая идентификатор диалога Call-ID, локальный тег и удаленный тег, пользовательский интерфейс отслеживает нажатия клавиш, связанные с локальным тегом.
In the media proxy case, and potentially other cases, there is a need to monitor the key presses arriving from the remote user agent. The optional <stream> element to the <request> tag specifies which stream to monitor. The only legal value is "reverse", which means to monitor the stream associated with the remote-tag. The User Interface MUST ignore other values. NOTE: The reason this is a tag is so individual stream selection, if needed, can be addressed in a backwards-compatible way. Further specification of the stream to monitor is the subject of future standardization.
В случае медиа-прокси и, возможно, в других случаях необходимо отслеживать нажатия клавиш, поступающие от удаленного пользовательского агента. Необязательный элемент <stream> тега <request> указывает, какой поток отслеживать. Единственное допустимое значение — «reverse», что означает мониторинг потока, связанного с удаленным тегом. Пользовательский интерфейс ДОЛЖЕН игнорировать другие значения. ПРИМЕЧАНИЕ. Причина, по которой это тег, заключается в том, что при необходимости можно выполнить индивидуальный выбор потока с помощью обратной совместимости. Дальнейшая спецификация потока для мониторинга является предметом будущей стандартизации.

3.8. Несколько одновременных подписок
An Application MAY register multiple User Input patterns in a single KPML subscription. If the User Interface supports multiple, simultaneous KPML subscriptions, the Application installs the subscriptions either in a new SUBSCRIBE-initiated dialog or on an existing SUBSCRIBE-initiated dialog with a new event id tag. If the User Interface does not support multiple, simultaneous KPML subscriptions, the User Interface MUST respond with an appropriate KPML status code.
Приложение МОЖЕТ зарегистрировать несколько шаблонов пользовательского ввода в одной подписке KPML. Если пользовательский интерфейс поддерживает несколько одновременных подписок KPML, Приложение устанавливает подписки либо в новом диалоговом окне SUBSCRIBE-initiated, либо в существующем диалоговом окне SUBSCRIBE-initiated с новым тегом идентификатора события. Если пользовательский интерфейс не поддерживает несколько одновременных подписок KPML, пользовательский интерфейс ДОЛЖЕН ответить соответствующим кодом состояния KPML.
Some User Interfaces may support multiple key press event notification subscriptions at the same time. In this situation, the User Interface honors each subscription individually and independently.
Некоторые пользовательские интерфейсы могут одновременно поддерживать несколько подписок на уведомления о событиях нажатия клавиш. В этой ситуации пользовательский интерфейс учитывает каждую подписку индивидуально и независимо.
A SIP user agent may request multiple subscriptions on the same SUBSCRIBE dialog, using the id parameter to the kpml event request.
Пользовательский агент SIP может запросить несколько подписок в одном и том же диалоговом окне ПОДПИСКА, используя параметр id в запросе события kpml.
One or more SIP user agents may request independent subscriptions on different SIP dialogs, although reusing the same dialog for multiple subscriptions is NOT RECOMMENDED.
Один или несколько пользовательских агентов SIP могут запрашивать независимые подписки в разных диалоговых окнах SIP, хотя повторное использование одного и того же диалогового окна для нескольких подписок НЕ РЕКОМЕНДУЕТСЯ.
If the User Interface does not support multiple, simultaneous subscriptions, the User Interface MUST return a KPML document with the KPML status code set to 533 on the dialog that requested the second subscription. The User Interface MUST NOT modify the state of the first subscription on account of the second subscription attempt.
Если пользовательский интерфейс не поддерживает несколько одновременных подписок, пользовательский интерфейс ДОЛЖЕН вернуть документ KPML с кодом состояния KPML, установленным на 533, в диалоговом окне, запрашивающем вторую подписку. Пользовательский интерфейс НЕ ДОЛЖЕН изменять состояние первой подписки из-за второй попытки подписки.

Из-за потенциально конфиденциального характера информации, сообщаемой KPML, подписчикам СЛЕДУЕТ использовать sips: и МОГУТ использовать S/MIME для контента.
Subscribers MUST be prepared for the notifier to insist on authentication of the subscription request. Subscribers MUST be prepared for the notifier to insist on using a secure communication channel.
Подписчики ДОЛЖНЫ быть готовы к тому, что уведомитель будет настаивать на аутентификации запроса на подписку. Абоненты ДОЛЖНЫ быть готовы к тому, что уведомитель будет настаивать на использовании безопасного канала связи.
4.7. Notifier Processing of SUBSCRIBE Requests
4.7. Обработка уведомлений запросами на ПОДПИСКУ
The user information transported by KPML is potentially sensitive. For example, it could include calling card or credit card numbers. Thus the User Interface (notifier) MUST authenticate the requesting party in some way before accepting the subscription.
Пользовательская информация, передаваемая KPML, потенциально конфиденциальна. Например, он может включать номера телефонных карт или кредитных карт. Таким образом, пользовательский интерфейс (уведомитель) ДОЛЖЕН каким-либо образом аутентифицировать запрашивающую сторону, прежде чем принять подписку.
User Interfaces MUST implement SIP Digest authentication as required by RFC 3261 [4] and MUST implement the sips: scheme and TLS.
Пользовательские интерфейсы ДОЛЖНЫ реализовывать аутентификацию SIP Digest, как того требует RFC 3261 [4], и ДОЛЖНЫ реализовывать схему sips: и TLS.
Upon authenticating the requesting party, the User Interface determines if the requesting party has authorization to monitor the user's key presses. The default authorization policy is to allow a KPML subscriber who can authenticate with a specific identity to monitor key presses from SIP sessions in which the same or equivalent authenticated identity is a participant. In addition, KPML will often be used, for example, between "application servers" (subscribers) and PSTN gateways (notifiers) operated by the same domain or federation of domains. In this situation a notifier MAY be configured with a list of subscribers which are specifically trusted and authorized to subscribe to key press information related to all sessions in a particular context.
После аутентификации запрашивающей стороны пользовательский интерфейс определяет, имеет ли запрашивающая сторона полномочия отслеживать нажатия клавиш пользователем. Политика авторизации по умолчанию позволяет подписчику KPML, который может пройти аутентификацию с использованием определенного удостоверения, отслеживать нажатия клавиш в сессиях SIP, в которых участвует то же самое или эквивалентное аутентифицированное удостоверение. Кроме того, KPML часто будет использоваться, например, между «серверами приложений» (абонентами) и шлюзами PSTN (уведомителями), управляемыми одним и тем же доменом или федерацией доменов. В этой ситуации уведомитель МОЖЕТ быть настроен со списком подписчиков, которым особо доверяют и которым разрешено подписываться на информацию о нажатии клавиш, относящуюся ко всем сессиям в определенном контексте.
The User Interface returns a Contact URI that may have GRUU [9] properties in the Contact header of a SIP INVITE, 1xx, or 2xx response.
Пользовательский интерфейс возвращает контактный URI, который может иметь свойства GRUU [9] в заголовке Contact ответа SIP INVITE, 1xx или 2xx.
After authorizing the request, the User Interface checks to see if the request is to terminate a subscription. If the request will terminate the subscription, the User Interface does the appropriate processing, including the procedures described in Section 5.2. If the request has no KPML body, then any KPML document running on that dialog and addressed by the event id, if present, immediately terminates. This is a mechanism for unloading a KPML document while keeping the SUBSCRIBE-initiated dialog active. This can be important for secure sessions that have high costs for session establishment. The User Interface follows the procedures described in Section 5.2.
После авторизации запроса пользовательский интерфейс проверяет, является ли запрос прекращением подписки. Если запрос прекратит подписку, Пользовательский интерфейс выполнит соответствующую обработку, включая процедуры, описанные в Разделе 5.2. Если запрос не имеет тела KPML, то любой документ KPML, запущенный в этом диалоговом окне и адресуемый идентификатором события, если он присутствует, немедленно завершается. Это механизм выгрузки документа KPML при сохранении активности диалогового окна SUBSCRIBE-initiated. Это может быть важно для безопасных сессий, установка которых требует больших затрат. Пользовательский интерфейс соответствует процедурам, описанным в разделе 5.2.
If the dialog referenced by the kpml subscription does not exist, the User Interface follows the procedures in Section 5.3. Note the User Interface MUST issue a 200 OK to the SUBSCRIBE request before issuing the NOTIFY, as the SUBSCRIBE itself is well formed.
Если диалоговое окно, на которое ссылается подписка kpml, не существует, пользовательский интерфейс соответствует процедурам, описанным в разделе 5.3. Обратите внимание, что пользовательский интерфейс ДОЛЖЕН выдать 200 OK на запрос SUBSCRIBE перед выдачей NOTIFY, поскольку сам SUBSCRIBE правильно сформирован.
If the request has a KPML body, the User Interface parses the KPML document. The User Interface SHOULD validate the XML document against the schema presented in Section 5.2. If the document is not valid, the User Interface rejects the SUBSCRIBE request with an appropriate error response and terminates the subscription. If there is a loaded KPML document on the subscription, the User Interface unloads the document.
Если запрос имеет тело KPML, пользовательский интерфейс анализирует документ KPML. Пользовательский интерфейс ДОЛЖЕН проверить XML-документ на соответствие схеме, представленной в разделе 5.2. Если документ недействителен, пользовательский интерфейс отклоняет запрос SUBSCRIBE с соответствующим ответом об ошибке и прекращает подписку. Если в подписке есть загруженный документ KPML, пользовательский интерфейс выгружает документ.
In addition, if there is a loaded KPML document on the subscription, the end device unloads the document.
Кроме того, если в подписке есть загруженный документ KPML, конечное устройство выгружает этот документ.
Following the semantics of SUBSCRIBE, if the User Interface receives a resubscription, the User Interface MUST terminate the existing KPML request and replace it with the new request.
Следуя семантике SUBSCRIBE, если пользовательский интерфейс получает повторную подписку, он ДОЛЖЕН завершить существующий запрос KPML и заменить его новым запросом.
It is possible for the INVITE usage of the dialog to terminate during key press collection. The cases enumerated here are explicit subscription termination, automatic subscription termination, and underlying (INVITE-initiated) dialog termination.
Использование диалога INVITE может прекратиться во время набора нажатий клавиш. Здесь перечислены случаи явного прекращения подписки, автоматического прекращения подписки и базового (INVITE-initiated) завершения диалогового окна.
If a SUBSCRIBE request has an expires of zero (explicit SUBSCRIBE termination), includes a KPML document, and there is buffered User Input, then the User Interface attempts to process the buffered digits against the document. If there is a match, the User Interface MUST generate the appropriate KPML report with the KPML status code of 200. The SIP NOTIFY body terminates the subscription by setting the subscription state to "terminated" and a reason of "timeout".
Если срок действия запроса SUBSCRIBE равен нулю (явное завершение SUBSCRIBE), включает документ KPML и имеется буферизованный пользовательский ввод, то пользовательский интерфейс пытается обработать буферизованные цифры в отношении документа. При наличии совпадения пользовательский интерфейс ДОЛЖЕН сгенерировать соответствующий отчет KPML с кодом состояния KPML 200. Тело SIP NOTIFY прекращает подписку, устанавливая состояние подписки на «terminated» и причину «timeout».
If the SUBSCRIBE request has an expires of zero and no KPML body or the expires timer on the SUBSCRIBE-initiated dialog fires at the User Interface (notifier), then the User Interface MUST issue a KPML report with the KPML status code 487, Subscription Expired. The report also includes the User Input collected up to the time the expires timer expired or when the subscription with expires equal to zero was processed. This could be the null string. Per the mechanisms of RFC 3265 [5], the User Interface MUST terminate the SIP SUBSCRIBE dialog. The User Interface does this via the SIP NOTIFY body transporting the final report described in the preceding paragraph. In particular, the subscription state will be "terminated" and a reason of "timeout".
Если срок действия запроса SUBSCRIBE равен нулю, а тело KPML отсутствует или таймер истечения срока действия в диалоговом окне SUBSCRIBE-initiated срабатывает в пользовательском интерфейсе (уведомителе), то пользовательский интерфейс ДОЛЖЕН выдать отчет KPML с кодом состояния KPML 487, срок действия подписки истек. Отчет также включает в себя вводимые пользователем данные, собранные до момента истечения срока действия таймера или до момента обработки подписки со сроком действия, равным нулю. Это может быть нулевая строка. В соответствии с механизмами RFC 3265 [5] пользовательский интерфейс ДОЛЖЕН завершить диалог SIP SUBSCRIBE. Пользовательский интерфейс делает это через тело SIP NOTIFY, передающее окончательный отчет, описанный в предыдущем абзаце. В частности, состояние подписки будет «terminated» и причина «timeout».
Terminating the subscription when a dialog terminates ensures reauthorization (if necessary) for attaching to subsequent subscriptions.
Прекращение подписки при завершении диалога обеспечивает повторную авторизацию (при необходимости) для присоединения к последующим подпискам.
If a SUBSCRIBE request references a dialog that is not present at the User Interface, the User Interface MUST generate a KPML report with the KPML status code 481, Dialog Not Found. The User Interface terminates the subscription by setting the subscription state to "terminated".
Если запрос SUBSCRIBE ссылается на диалог, которого нет в пользовательском интерфейсе, пользовательский интерфейс ДОЛЖЕН создать отчет KPML с кодом состояния KPML 481, «Диалог не найден». Пользовательский интерфейс прекращает подписку, устанавливая состояние подписки на «terminated».
If the KPML document is not valid, the User Interface generates a KPML report with the KPML status code 501, Bad Document. The User Interface terminates the subscription by setting the subscription state to "terminated".
Если документ KPML недействителен, пользовательский интерфейс создает отчет KPML с кодом состояния KPML 501, «Плохой документ». Пользовательский интерфейс прекращает подписку, устанавливая состояние подписки на «terminated».
If the document is valid but the User Interface does not support a namespace in the document, the User Interface MUST respond with a KPML status code 502, Namespace Not Supported.
Если документ действителен, но пользовательский интерфейс не поддерживает пространство имен в документе, пользовательский интерфейс ДОЛЖЕН ответить кодом состояния KPML 502, пространство имен не поддерживается.
4.8. Notifier Generation of NOTIFY Requests
4.8. Генерация уведомлений уведомителем запросов NOTIFY
Immediately after a subscription is accepted, the Notifier MUST send a NOTIFY with the current location information as appropriate based on the identity of the subscriber. This allows the Subscriber to resynchronize its state.
Сразу после принятия подписки уведомитель ДОЛЖЕН отправить УВЕДОМЛЕНИЕ с информацией о текущем местоположении, в зависимости от обстоятельств, на основе личности подписчика. Это позволяет подписчику повторно синхронизировать свое состояние.
The User Interface (notifier in SUBSCRIBE/NOTIFY parlance) generates NOTIFY requests based on the requirements of RFC 3265 [5]. Specifically, if a SUBSCRIBE request is valid and authorized, it will result in an immediate NOTIFY.
Пользовательский интерфейс (уведомитель на языке SUBSCRIBE/NOTIFY) генерирует запросы NOTIFY на основе требований RFC 3265 [5]. В частности, если запрос ПОДПИСАТЬСЯ действителен и авторизован, он приведет к немедленному УВЕДОМЛЕНИЮ.
The KPML payload distinguishes between an initial NOTIFY and a NOTIFY informing of key presses. If there is no User Input buffered at the time of the SUBSCRIBE (see below) or the buffered User Input does not match the new KPML document, then the immediate NOTIFY MUST NOT contain a KPML body. If User Interface has User Input buffered that results in a match using the new KPML document, then the NOTIFY MUST return the appropriate KPML document.
Полезная нагрузка KPML различает начальное NOTIFY и NOTIFY, информирующее о нажатиях клавиш. Если на момент ПОДПИСКИ пользовательский ввод не буферизуется (см. ниже) или буферизованный пользовательский ввод не соответствует новому документу KPML, то немедленное NOTIFY НЕ ДОЛЖНО содержать тело KPML. Если в пользовательском интерфейсе буферизован пользовательский ввод, что приводит к совпадению с использованием нового документа KPML, то команда NOTIFY ДОЛЖНА вернуть соответствующий документ KPML.
The NOTIFY in response to a SUBSCRIBE request has no KPML if there are no matching buffered digits. An example of this is in Figure 10. If there are buffered digits in the SUBSCRIBE request that match a pattern, then the NOTIFY message in response to the SUBSCRIBE request MUST include the appropriate KPML document.
NOTIFY в ответ на запрос SUBSCRIBE не имеет KPML, если нет совпадающих цифр в буфере. Пример этого показан на рисунке 10. Если в запросе SUBSCRIBE имеются буферизованные цифры, соответствующие шаблону, то сообщение NOTIFY в ответ на запрос SUBSCRIBE ДОЛЖНО включать соответствующий документ KPML.

All subscriptions MUST be authenticated, particularly those that match on buffered input.
Все подписки ДОЛЖНЫ быть аутентифицированы, особенно те, которые совпадают с буферизованными входными данными.
KPML specifies the key press notification report format. The MIME type for KPML reports is application/kpml-response+xml. The default MIME type for the kpml event package is application/ kpml-response+xml.
KPML определяет формат отчета об уведомлении о нажатии клавиши. Тип MIME для отчетов KPML — application/kpml-response+xml. Тип MIME по умолчанию для пакета событий kpml — application/kpml-response+xml.
If the requestor is not using a secure transport protocol such as TLS for every hop (e.g., by using a sips: URI), the User Interface SHOULD use S/MIME to protect the user information in responses.
Если запрашивающая сторона не использует безопасный транспортный протокол, такой как TLS, для каждого перехода (например, используя sips: URI), пользовательский интерфейс ДОЛЖЕН использовать S/MIME для защиты пользовательской информации в ответах.
When the user enters key presses that match a <regex> tag, the User Interface will issue a report.
Когда пользователь нажимает клавиши, соответствующие тегу <regex>, пользовательский интерфейс выдает отчет.
After reporting, the interpreter terminates the KPML session unless the subscription has a persistence indicator. If the subscription does not have a persistence indicator, the User Interface MUST set the state of the subscription to "terminated" in the NOTIFY report.
После отчета интерпретатор завершает сессия KPML, если в подписке нет индикатора устойчивости. Если подписка не имеет индикатора постоянства, пользовательский интерфейс ДОЛЖЕН установить состояние подписки на «terminated» в отчете NOTIFY.
If the subscription does not have a persistence indicator, to collect more digits, the requestor must issue a new request.
Если подписка не имеет индикатора постоянства, для сбора большего количества цифр запрашивающая сторона должна выдать новый запрос.
NOTE: This highlights the "one shot" nature of KPML, reflecting the balance of features and ease of implementing an interpreter.
ПРИМЕЧАНИЕ. Это подчеркивает «одноразовый» характер KPML, отражающий баланс функций и простоту реализации интерпретатора.
KPML reports have two mandatory attributes, code and text. These attributes describe the state of the KPML interpreter on the User Interface. Note the KPML status code is not necessarily related to the SIP result code. An important example of this is where a legal SIP subscription request gets a normal SIP 200 OK followed by a NOTIFY, but there is something wrong with the KPML request. In this case, the NOTIFY would include the KPML status code in the KPML report. Note that from a SIP perspective, the SUBSCRIBE and NOTIFY were successful. Also, if the KPML failure is not recoverable, the User Interface will most likely set the Subscription-State to "terminated". This lets the SIP machinery know the subscription is no longer active.
Отчеты KPML имеют два обязательных атрибута: код и текст. Эти атрибуты описывают состояние интерпретатора KPML в пользовательском интерфейсе. Обратите внимание, что код состояния KPML не обязательно связан с кодом результата SIP. Важным примером этого является случай, когда легальный запрос на подписку SIP получает обычный ответ SIP 200 OK, за которым следует NOTIFY, но с запросом KPML что-то не так. В этом случае NOTIFY будет включать код состояния KPML в отчет KPML. Обратите внимание, что с точки зрения SIP команды SUBSCRIBE и NOTIFY прошли успешно. Кроме того, если сбой KPML не подлежит устранению, пользовательский интерфейс, скорее всего, установит для Subscription-State значение «terminated». Это позволяет оборудованию SIP узнать, что подписка больше не активна.
If a pattern matches, the User Interface will emit a KPML report. Since this is a success report, the code is "200", and the text is "OK".
Если шаблон соответствует, пользовательский интерфейс выдаст отчет KPML. Поскольку это отчет об успехе, код — «200», а текст — «OK».
The KPML report includes the actual digits matched in the digit attribute. The digit string uses the conventional characters '*' and '#' for star and octothorpe, respectively. The KPML report also includes the tag attribute if the regex that matched the digits had a tag attribute.
Отчет KPML включает фактические цифры, соответствующие атрибуту цифры. В строке цифр используются обычные символы «*» и «#» для звезды и октоторпа соответственно. Отчет KPML также включает атрибут тега, если регулярное выражение, соответствующее цифрам, имеет атрибут тега.
If the subscription requested digit suppression and the User Interface suppressed digits, the suppressed attribute indicates "true". The default value of suppressed is "false". NOTE: KPML does not include a timestamp. There are a number of reasons for this. First, what timestamp would it include? Would it be the time of the first detected key press? The time the interpreter collected the entire string? A range? Second, if the RTP timestamp is a datum of interest, why not simply get RTP in the first place? That all said, if it is really compelling to have the timestamp in the response, it could be an attribute to the <response> tag.
Если подписка запрашивала подавление цифр, а пользовательский интерфейс подавлял цифры, атрибут подавления указывает «true». Значение по умолчанию для параметра «Подавлено» — «false». ПРИМЕЧАНИЕ. KPML не включает метку времени. Для этого есть ряд причин. Во-первых, какую временную метку он будет включать? Будет ли это время первого обнаруженного нажатия клавиши? Время, когда интерпретатор собрал всю строку? Диапазон? Во-вторых, если временная метка RTP представляет интерес, почему бы просто не получить RTP? Тем не менее, если действительно важно иметь метку времени в ответе, это может быть атрибут тега <response>.
Note that if the monitored (INVITE-initiated) dialog terminates, the notifier still MUST explicitly terminate the KPML subscriptions monitoring that dialog.
Обратите внимание: если отслеживаемый диалог (INVITE-initiated) завершается, уведомитель все равно ДОЛЖЕН явно прекратить подписки KPML, отслеживающие этот диалог.
4.9. Subscriber Processing of NOTIFY Requests
4.9. Обработка подписчиком запросов NOTIFY
If there is no KPML body, it means the SUBSCRIBE was successful. This establishes the dialog if there is no buffered User Input to report.
Если тело KPML отсутствует, это означает, что ПОДПИСКА прошла успешно. Это открывает диалоговое окно, если нет буферизованного пользовательского ввода для отчета.
If there is a KPML document, and the KPML status code is 200, then a match occurred.
Если существует документ KPML и код состояния KPML равен 200, значит произошло совпадение.
If there is a KPML document, and the KPML status code is between 400 and 499, then an error occurred with User Input collection. The most likely cause is a timeout condition. If there is a KPML document, and the KPML status code is between 500 and 599, then an error occurred with the subscription. See Section 6 for more on the meaning of KPML status codes.
Если существует документ KPML и код состояния KPML находится между 400 и 499, то при сборе пользовательского ввода произошла ошибка. Наиболее вероятной причиной является тайм-аут. Если существует документ KPML и код состояния KPML находится между 500 и 599, значит, при подписке произошла ошибка. Дополнительную информацию о значении кодов состояния KPML см. в разделе 6.
The subscriber MUST be mindful of the subscription state. The User Interface may terminate the subscription at any time.
Абонент ДОЛЖЕН помнить о состоянии подписки. Пользовательский интерфейс может прекратить подписку в любое время.
4.10. Handling of Forked Requests
4.10. Обработка разветвленных запросов
Forked requests are NOT ALLOWED for this event type. This can be ensured if the Subscriptions to this event package are sent to SIP URIs that have GRUU properties.
Разветвленные запросы НЕ РАЗРЕШЕНЫ для этого типа событий. Это можно гарантировать, если подписки на этот пакет событий отправляются на SIP URI, имеющие свойства GRUU.
4.11. Rate of Notifications
4.11. Скорость уведомлений
The User Interface MUST NOT generate messages faster than 25 messages per second, or one message every 40 milliseconds. This is the minimum time period for MF digit spills. Even 30-millisecond DTMF, as one sometimes finds in Japan, has a 20-millisecond off time, resulting in a 50-millisecond interdigit time. This document strongly RECOMMENDS AGAINST using KPML for digit-by-digit messaging, such as would be the case if the only <regex> is "x".
Пользовательский интерфейс НЕ ДОЛЖЕН генерировать сообщения со скоростью более 25 сообщений в секунду или одного сообщения каждые 40 миллисекунд. Это минимальный период времени для выпадения цифр MF. Даже 30-миллисекундный DTMF, который иногда встречается в Японии, имеет 20-миллисекундное время отключения, в результате чего время между цифрами составляет 50 миллисекунд. В этом документе НАСТОЯТЕЛЬНО РЕКОМЕНДУЕТСЯ ПРОТИВ использования KPML для поразрядного обмена сообщениями, например, если единственным <regex> является «x».
The sustained rate of notification shall be no more than 100 Notifies per minute.
Устойчивая частота уведомлений должна составлять не более 100 уведомлений в минуту.
The User Interface MUST reliably deliver notifications. Because there is no meaningful metric for throttling requests, the User Interface SHOULD send NOTIFY messages over a congestion-controlled transport, such as TCP. Note that all SIP implementations are already required to implement SIP over TCP.
Пользовательский интерфейс ДОЛЖЕН надежно доставлять уведомления. Поскольку значимой метрики для регулирования запросов не существует, пользовательский интерфейс ДОЛЖЕН отправлять сообщения NOTIFY по транспорту, управляемому перегрузкой, например TCP. Обратите внимание, что все реализации SIP уже необходимы для реализации SIP через TCP.
4.12. State Agents and Lists
4.12. Государственные агенты и списки
KPML requests are sent to a specific SIP URI, which may have GRUU properties, and they attempt to monitor a specific stream that corresponds with a specific target dialog. Consequently, implementers MUST NOT define state agents for this event package or allow subscriptions for this event package to resource lists using the event list extension [18].
Запросы KPML отправляются на определенный URI SIP, который может иметь свойства GRUU, и пытаются отслеживать определенный поток, соответствующий определенному целевому диалогу. Следовательно, разработчики НЕ ДОЛЖНЫ определять агенты состояния для этого пакета событий или разрешать подписки для этого пакета событий на списки ресурсов с использованием расширения списка событий [18].
4.13. Behavior of a Proxy Server
4.13. Поведение прокси
There are no additional requirements on a SIP Proxy, other than to transparently forward the SUBSCRIBE and NOTIFY methods as required in SIP.
К прокси SIP не предъявляется никаких дополнительных требований, кроме прозрачной пересылки методов SUBSCRIBE и NOTIFY, как того требует SIP.

6. Enumeration of KPML Status Codes
6. Перечисление кодов состояния KPML
KPML status codes broadly follow their SIP counterparts. Codes that start with a 2 indicate success. Codes that start with a 4 indicate failure. Codes that start with a 5 indicate a server failure, usually a failure to interpret the document or to support a requested feature.
Коды статуса KPML во многом соответствуют своим аналогам SIP. Коды, начинающиеся с 2, указывают на успех. Коды, начинающиеся с 4, указывают на неисправность. Коды, начинающиеся с 5, указывают на сбой сервера, обычно неспособность интерпретировать документ или поддерживать запрошенную функцию.
KPML clients MUST be able to handle arbitrary status codes by examining the first digit only.
Клиенты KPML ДОЛЖНЫ иметь возможность обрабатывать произвольные коды состояния, проверяя только первую цифру.
Any text can be in a KPML report document. KPML clients MUST NOT interpret the text field.
В документе отчета KPML может присутствовать любой текст. Клиенты KPML НЕ ДОЛЖНЫ интерпретировать текстовое поле.

8. Security Considerations
8. Вопросы безопасности
The user information transported by KPML is potentially sensitive. For example, it could include calling card or credit card numbers. This potentially private information could be provided accidentally if the notifier does not properly authenticate or authorize a subscription. Similarly private information (such as a credit card number or calling card number) could be revealed to an otherwise legitimate subscriber (one operating an IVR) if digits buffered earlier in the session are provided unintentionally to the new subscriber.
Пользовательская информация, передаваемая KPML, потенциально конфиденциальна. Например, он может включать номера телефонных карт или кредитных карт. Эта потенциально конфиденциальная информация может быть предоставлена ​​случайно, если уведомитель не аутентифицирует или не авторизует подписку должным образом. Аналогичным образом личная информация (например, номер кредитной карты или номер телефонной карты) может быть раскрыта легитимному абоненту (тому, кто использует IVR), если цифры, буферизованные ранее в сессии, непреднамеренно передаются новому абоненту.
Likewise, an eavesdropper could view KPML digit information if it is not encrypted, or an attacker could inject fraudulent notifications unless the messages or the SIP path over which they travel are integrity protected.
Аналогичным образом, перехватчик может просмотреть цифровую информацию KPML, если она не зашифрована, или злоумышленник может внедрить мошеннические уведомления, если только сообщения или путь SIP, по которому они передаются, не защищены.
Therefore, User Interfaces MUST NOT downgrade their own security policy. That is, if a User Interface policy is to restrict notifications to authenticated and authorized subscribers over secure communications, then the User Interface must not accept an unauthenticated, unauthorized subscription over an insecure communication channel.
Поэтому пользовательские интерфейсы НЕ ДОЛЖНЫ понижать свою собственную политику безопасности. То есть, если политика пользовательского интерфейса ограничивает отправку уведомлений аутентифицированным и авторизованным подписчикам по защищенной связи, то пользовательский интерфейс не должен принимать неаутентифицированную, несанкционированную подписку по незащищенному каналу связи.
As an XML markup, all of the security considerations of RFC 3023 [3] and RFC 3406 [6] MUST be met. Pay particular attention to the robustness requirements of parsing XML. Key press information is potentially sensitive. For example, it can represent credit card, calling card, or other personal information. Hijacking sessions allow unauthorized entities access to this sensitive information. Therefore, signaling SHOULD be secure, e.g., use of TLS and sips: SHOULD be used. Moreover, the information itself is sensitive so S/MIME or other appropriate mechanisms SHOULD be used.
В качестве разметки XML ДОЛЖНЫ соблюдаться все соображения безопасности RFC 3023 [3] и RFC 3406 [6]. Обратите особое внимание на требования к надежности анализа XML. Информация о нажатии клавиш потенциально конфиденциальна. Например, он может представлять собой кредитную карту, телефонную карту или другую личную информацию. Сессии перехвата позволяют неавторизованным лицам получить доступ к этой конфиденциальной информации. Следовательно, сигнализация СЛЕДУЕТ быть безопасной, например, Использование TLS и sip: СЛЕДУЕТ использовать. Более того, сама информация является конфиденциальной, поэтому СЛЕДУЕТ использовать S/MIME или другие соответствующие механизмы.
Subscriptions MUST be authenticated in some manner. As required by the core SIP [4] specification, all SIP implementations MUST support digest authentication. In addition, User Interfaces MUST implement support for the sips: scheme and SIP over TLS. Subscribers MUST expect the User Interface to demand the use of an authentication scheme. If the local policy of a User Interface is to use authentication or secure communication channels, the User Interface MUST reject subscription requests that do not meet that policy.
Подписки ДОЛЖНЫ быть аутентифицированы каким-либо образом. В соответствии с требованиями базовой спецификации SIP [4], все реализации SIP ДОЛЖНЫ поддерживать дайджест-аутентификацию. Кроме того, пользовательские интерфейсы ДОЛЖНЫ реализовывать поддержку схемы sips: и SIP через TLS. Абоненты ДОЛЖНЫ ожидать, что пользовательский интерфейс потребует использования схемы аутентификации. Если локальная политика пользовательского интерфейса предусматривает использование аутентификации или безопасных каналов связи, пользовательский интерфейс ДОЛЖЕН отклонять запросы на подписку, которые не соответствуют этой политике.
User Interfaces MUST begin buffering User Input upon receipt of an authenticated and accepted subscription. This buffering is done on a per-subscription basis.
Пользовательские интерфейсы ДОЛЖНЫ начать буферизацию пользовательского ввода после получения аутентифицированной и принятой подписки. Эта буферизация выполняется для каждой подписки.

10.2. Multiple Applications
10.2. Несколько приложений
This section gives a non-normative example of multiple applications. One application collects a destination number to call. That application then waits for a "long pound." During the call, the call goes to a personal assistant application, which interacts with the user. In addition, the personal assistant application looks for a "short pound."
В этом разделе приводится ненормативный пример нескольких приложений. Одно приложение собирает номер назначения для вызова. Затем это приложение ожидает «длинного фунта». Во время вызова вызов поступает на приложение личного помощника, которое взаимодействует с пользователем. Кроме того, приложение личного помощника ищет «короткий фунт».
