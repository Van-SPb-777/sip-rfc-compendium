Abstract
Аннотация
This document defines basic terminology for describing different types of Network Address Translation (NAT) behavior when handling Unicast UDP and also defines a set of requirements that would allow many applications, such as multimedia communications or online gaming, to work consistently. Developing NATs that meet this set of requirements will greatly increase the likelihood that these applications will function properly.
Настоящий документ определяет базовую терминологию для описания различных типов поведения NAT при обработке одноадресного UDP, а также набор требований, позволяющих многим приложениям, таким как мультимедийные коммуникации или сетевые игры, работать согласованно. Разработка NAT, соответствующих этому набору требований, значительно повышает вероятность того, что такие приложения будут функционировать должным образом.
1. Applicability Statement
1. Заявление о применимости
The purpose of this specification is to define a set of requirements for NATs that would allow many applications, such as multimedia communications or online gaming, to work consistently. Developing NATs that meet this set of requirements will greatly increase the likelihood that these applications will function properly.
Цель настоящей спецификации — определить набор требований к NAT, который позволил бы многим приложениям, таким как мультимедийные коммуникации или сетевые игры, работать согласованно. Разработка NAT, отвечающих этим требованиям, значительно повышает вероятность того, что такие приложения будут работать должным образом.
The requirements of this specification apply to Traditional NATs as described in [RFC2663].
Требования настоящей спецификации относятся к традиционным NAT (Traditional NAT), описанным в [RFC2663].
This document is meant to cover NATs of any size, from small residential NATs to large Enterprise NATs. However, it should be understood that Enterprise NATs normally provide much more than just NAT capabilities; for example, they typically provide firewall functionalities. A comprehensive description of firewall behaviors and associated requirements is specifically out-of-scope for this specification. However, this specification does cover basic firewall aspects present in NATs (see Section 5).
Настоящий документ охватывает NAT любого масштаба — от небольших домашних NAT до крупных корпоративных NAT. Однако следует понимать, что корпоративные NAT обычно предоставляют гораздо больше, чем просто возможности NAT; например, они, как правило, выполняют функции межсетевого экрана. Подробное описание поведения межсетевых экранов и связанных с ним требований явно выходит за рамки настоящей спецификации. Тем не менее спецификация рассматривает базовые аспекты межсетевого экрана, присущие NAT (см. раздел 5).
Approaches using directly signaled control of middle boxes are out of scope.
Подходы с прямым сигнальным управлением промежуточными узлами не рассматриваются.
UDP Relays (e.g., Traversal Using Relay NAT [TURN]) are out of scope.
Ретрансляторы UDP (например, Traversal Using Relay NAT [TURN]) не рассматриваются.
Application aspects are out of scope, as the focus here is strictly on the NAT itself.
Аспекты приложений не рассматриваются, поскольку здесь внимание сосредоточено строго на самом NAT.
This document only covers aspects of NAT traversal related to Unicast UDP [RFC0768] over IP [RFC0791] and their dependencies on other protocols.
Настоящий документ охватывает только аспекты прохождения через NAT, связанные с одноадресным UDP [RFC0768] поверх IP [RFC0791], и их зависимости от других протоколов.
2. Introduction
2. Введение
Network Address Translators (NATs) are well known to cause very significant problems with applications that carry IP addresses in the payload (see [RFC3027]). Applications that suffer from this problem include Voice Over IP and Multimedia Over IP (e.g., SIP [RFC3261] and H.323 [ITU.H323]), as well as online gaming.
Хорошо известно, что трансляторы сетевых адресов (NAT) создают очень серьёзные проблемы для приложений, передающих IP-адреса в полезной нагрузке (см. [RFC3027]). К приложениям, страдающим от этой проблемы, относятся передача голоса по IP и мультимедиа по IP (например, SIP [RFC3261] и H.323 [ITU.H323]), а также сетевые игры.
Many techniques are used to attempt to make realtime multimedia applications, online games, and other applications work across NATs. Application Level Gateways [RFC2663] are one such mechanism. STUN [RFC3489bis] describes a UNilateral Self-Address Fixing (UNSAF) mechanism [RFC3424]. Teredo [RFC4380] describes an UNSAF mechanism consisting of tunnelling IPv6 [RFC2460] over UDP/IPv4. UDP Relays have also been used to enable applications across NATs, but these are generally seen as a solution of last resort. Interactive Connectivity Establishment [ICE] describes a methodology for using many of these techniques and avoiding a UDP relay, unless the type of NAT is such that it forces the use of such a UDP relay. This specification defines requirements for improving NATs. Meeting these requirements ensures that applications will not be forced to use UDP relay.
Для того чтобы приложения мультимедиа реального времени, сетевые игры и другие приложения работали через NAT, применяется множество методов. Одним из таких механизмов являются шлюзы уровня приложений (Application Level Gateways) [RFC2663]. STUN [RFC3489bis] описывает механизм одностороннего исправления собственного адреса (UNSAF) [RFC3424]. Teredo [RFC4380] описывает механизм UNSAF, состоящий в туннелировании IPv6 [RFC2460] поверх UDP/IPv4. Для обеспечения работы приложений через NAT использовались также ретрансляторы UDP, но обычно они считаются решением в последнюю очередь. Interactive Connectivity Establishment [ICE] описывает методику использования многих из этих методов и отказа от ретранслятора UDP, если только тип NAT не вынуждает использовать такой ретранслятор. Настоящая спецификация определяет требования к улучшению NAT. Выполнение этих требований гарантирует, что приложения не будут вынуждены использовать ретранслятор UDP.
As pointed out in UNSAF [RFC3424], "From observations of deployed networks, it is clear that different NAT box implementations vary widely in terms of how they handle different traffic and addressing cases". This wide degree of variability is one factor in the overall brittleness introduced by NATs and makes it extremely difficult to predict how any given protocol will behave on a network traversing NAT. Discussions with many of the major NAT vendors have made it clear that they would prefer to deploy NATs that were deterministic and caused the least harm to applications while still meeting the requirements that caused their customers to deploy NATs in the first place. The problem NAT vendors face is that they are not sure how best to do that or how to document their NATs' behavior.
Как отмечено в UNSAF [RFC3424], «наблюдения за развёрнутыми сетями ясно показывают, что различные реализации NAT-устройств сильно различаются в том, как они обрабатывают разные случаи трафика и адресации». Эта широкая вариативность является одним из факторов общей хрупкости, вносимой NAT, и делает крайне трудным предсказать, как поведёт себя любой данный протокол в сети, проходящей через NAT. Обсуждения со многими крупными производителями NAT ясно показали, что они предпочли бы выпускать NAT, которые детерминированы и наносят наименьший вред приложениям, при этом по-прежнему удовлетворяя требованиям, из-за которых их клиенты вообще развернули NAT. Проблема, с которой сталкиваются производители NAT, состоит в том, что они не уверены, как лучше это сделать и как документировать поведение своих NAT.
The goals of this document are to define a set of common terminology for describing the behavior of NATs and to produce a set of requirements on a specific set of behaviors for NATs.
Цели настоящего документа — определить набор общей терминологии для описания поведения NAT и сформировать набор требований к конкретному набору моделей поведения NAT.
This document forms a common set of requirements that are simple and useful for voice, video, and games, which can be implemented by NAT vendors. This document will simplify the analysis of protocols for deciding whether or not they work in this environment and will allow providers of services that have NAT traversal issues to make statements about where their applications will work and where they will not, as well as to specify their own NAT requirements.
Настоящий документ формирует общий набор требований, простых и полезных для голоса, видео и игр, которые могут быть реализованы производителями NAT. Документ упростит анализ протоколов для определения того, работают ли они в этой среде, и позволит поставщикам услуг, имеющим проблемы с прохождением через NAT, заявлять, где их приложения будут работать, а где нет, а также формулировать собственные требования к NAT.
3. Terminology
3. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119].
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны толковаться так, как описано в [RFC2119].
Readers are urged to refer to [RFC2663] for information on NAT taxonomy and terminology. Traditional NAT is the most common type of NAT device deployed. Readers may refer to [RFC3022] for detailed information on traditional NAT. Traditional NAT has two main varieties -- Basic NAT and Network Address/Port Translator (NAPT).
Читателям рекомендуется обратиться к [RFC2663] за сведениями о таксономии и терминологии NAT. Традиционный NAT — наиболее распространённый тип развёртываемых NAT-устройств. Подробные сведения о традиционном NAT можно найти в [RFC3022]. Традиционный NAT имеет две основные разновидности — базовый NAT (Basic NAT) и транслятор сетевых адресов и портов (NAPT).
NAPT is by far the most commonly deployed NAT device. NAPT allows multiple internal hosts to share a single public IP address simultaneously. When an internal host opens an outgoing TCP or UDP session through a NAPT, the NAPT assigns the session a public IP address and port number, so that subsequent response packets from the external endpoint can be received by the NAPT, translated, and forwarded to the internal host. The effect is that the NAPT establishes a NAT session to translate the (private IP address, private port number) tuple to a (public IP address, public port number) tuple, and vice versa, for the duration of the session. An issue of relevance to peer-to-peer applications is how the NAT behaves when an internal host initiates multiple simultaneous sessions from a single (private IP, private port) endpoint to multiple distinct endpoints on the external network. In this specification, the term "NAT" refers to both "Basic NAT" and "Network Address/Port Translator (NAPT)".
NAPT — безусловно, наиболее распространённое развёртываемое NAT-устройство. NAPT позволяет множеству внутренних узлов одновременно совместно использовать один публичный IP-адрес. Когда внутренний узел открывает исходящий сеанс TCP или UDP через NAPT, NAPT назначает сеансу публичный IP-адрес и номер порта, чтобы последующие ответные пакеты от внешней конечной точки могли быть получены NAPT, транслированы и переданы внутреннему узлу. В результате NAPT устанавливает сеанс NAT для трансляции кортежа (частный IP-адрес, частный номер порта) в кортеж (публичный IP-адрес, публичный номер порта) и обратно на время сеанса. Вопрос, важный для одноранговых приложений, — как NAT ведёт себя, когда внутренний узел инициирует несколько одновременных сеансов из одной конечной точки (частный IP-адрес, частный порт) к нескольким разным конечным точкам во внешней сети. В настоящей спецификации термин «NAT» обозначает как «базовый NAT» (Basic NAT), так и «транслятор сетевых адресов и портов» (NAPT).
This document uses the term "session" as defined in RFC 2663: "TCP/ UDP sessions are uniquely identified by the tuple of (source IP address, source TCP/UDP ports, target IP address, target TCP/UDP Port)".
В настоящем документе термин «сеанс» используется в значении, определённом в RFC 2663: «сеансы TCP/UDP однозначно идентифицируются кортежем (IP-адрес источника, порты TCP/UDP источника, IP-адрес назначения, порт TCP/UDP назначения)».
This document uses the term "address and port mapping" as the translation between an external address and port and an internal address and port. Note that this is not the same as an "address binding" as defined in RFC 2663.
В настоящем документе термин «отображение адреса и порта» обозначает трансляцию между внешним адресом и портом и внутренним адресом и портом. Обратите внимание, что это не то же самое, что «привязка адреса» (address binding) в определении RFC 2663.
This document uses IANA terminology for port ranges, i.e., "Well Known Ports" is 0-1023, "Registered" is 1024-49151, and "Dynamic and/or Private" is 49152-65535, as defined in http://www.iana.org/assignments/port-numbers.
В документе для диапазонов портов используется терминология IANA: «Well Known Ports» — 0-1023, «Registered» — 1024-49151, «Dynamic and/or Private» — 49152-65535, как определено на http://www.iana.org/assignments/port-numbers.
STUN [RFC3489] used the terms "Full Cone", "Restricted Cone", "Port Restricted Cone", and "Symmetric" to refer to different variations of NATs applicable to UDP only. Unfortunately, this terminology has been the source of much confusion, as it has proven inadequate at describing real-life NAT behavior. This specification therefore refers to specific individual NAT behaviors instead of using the Cone/Symmetric terminology.
В STUN [RFC3489] термины «Full Cone», «Restricted Cone», «Port Restricted Cone» и «Symmetric» использовались для обозначения различных вариантов NAT, применимых только к UDP. К сожалению, эта терминология стала источником большой путаницы, поскольку оказалась недостаточной для описания реального поведения NAT. Поэтому настоящая спецификация описывает конкретные отдельные модели поведения NAT вместо терминологии «конус/симметричный».
4. Network Address and Port Translation Behavior
4. Поведение при трансляции сетевых адресов и портов
This section describes the various NAT behaviors applicable to NATs.
В этом разделе описаны различные модели поведения, применимые к NAT.
4.1. Address and Port Mapping
4.1. Отображение адреса и порта
When an internal endpoint opens an outgoing session through a NAT, the NAT assigns the session an external IP address and port number so that subsequent response packets from the external endpoint can be received by the NAT, translated, and forwarded to the internal endpoint. This is a mapping between an internal IP address and port IP:port and external IP:port tuple. It establishes the translation that will be performed by the NAT for the duration of the session. For many applications, it is important to distinguish the behavior of the NAT when there are multiple simultaneous sessions established to different external endpoints.
Когда внутренняя конечная точка открывает исходящий сеанс через NAT, NAT назначает сеансу внешний IP-адрес и номер порта, чтобы последующие ответные пакеты от внешней конечной точки могли быть получены NAT, транслированы и переданы внутренней конечной точке. Это отображение между внутренним кортежем IP-адреса и порта (IP:port) и внешним кортежем IP:port. Оно устанавливает трансляцию, которую NAT будет выполнять в течение всего сеанса. Для многих приложений важно различать поведение NAT в случае, когда установлено несколько одновременных сеансов к разным внешним конечным точкам.
The key behavior to describe is the criteria for reuse of a mapping for new sessions to external endpoints, after establishing a first mapping between an internal X:x address and port and an external Y1:y1 address tuple. Let's assume that the internal IP address and port X:x are mapped to X1':x1' for this first session. The endpoint then sends from X:x to an external address Y2:y2 and gets a mapping of X2':x2' on the NAT. The relationship between X1':x1' and X2':x2' for various combinations of the relationship between Y1:y1 and Y2:y2 is critical for describing the NAT behavior. Определяются следующие модели поведения в отношении отображения адреса и порта:
Endpoint-Independent Mapping:
Отображение, независимое от конечной точки (Endpoint-Independent Mapping):
The NAT reuses the port mapping for subsequent packets sent from the same internal IP address and port (X:x) to any external IP address and port. Specifically, X1':x1' equals X2':x2' for all values of Y2:y2.
NAT повторно использует отображение порта для последующих пакетов, отправляемых с того же внутреннего IP-адреса и порта (X:x) на любой внешний IP-адрес и порт. В частности, X1':x1' равно X2':x2' для всех значений Y2:y2.
Address-Dependent Mapping:
Отображение, зависимое от адреса (Address-Dependent Mapping):
The NAT reuses the port mapping for subsequent packets sent from the same internal IP address and port (X:x) to the same external IP address, regardless of the external port. Specifically, X1':x1' equals X2':x2' if and only if, Y2 equals Y1.
NAT повторно использует отображение порта для последующих пакетов, отправляемых с того же внутреннего IP-адреса и порта (X:x) на тот же внешний IP-адрес, независимо от внешнего порта. В частности, X1':x1' равно X2':x2' тогда и только тогда, когда Y2 равно Y1.
Address and Port-Dependent Mapping:
Отображение, зависимое от адреса и порта (Address and Port-Dependent Mapping):
The NAT reuses the port mapping for subsequent packets sent from the same internal IP address and port (X:x) to the same external IP address and port while the mapping is still active. Specifically, X1':x1' equals X2':x2' if and only if, Y2:y2 equals Y1:y1.
NAT повторно использует отображение порта для последующих пакетов, отправляемых с того же внутреннего IP-адреса и порта (X:x) на тот же внешний IP-адрес и порт, пока отображение остаётся активным. В частности, X1':x1' равно X2':x2' тогда и только тогда, когда Y2:y2 равно Y1:y1.
It is important to note that these three possible choices make no difference to the security properties of the NAT. The security properties are fully determined by which packets the NAT allows in and which it does not. This is determined by the filtering behavior in the filtering portions of the NAT.
Важно отметить, что эти три возможных варианта никак не влияют на свойства безопасности NAT. Свойства безопасности полностью определяются тем, какие пакеты NAT пропускает внутрь, а какие нет. Это определяется поведением фильтрации в компонентах фильтрации NAT.
REQ-1: A NAT MUST have an "Endpoint-Independent Mapping" behavior.
REQ-1: NAT ДОЛЖЕН иметь поведение «отображение, независимое от конечной точки».
Justification: In order for UNSAF methods to work, REQ-1 needs to be met. Failure to meet REQ-1 will force the use of a UDP relay, which is very often impractical.
Обоснование: для работы методов UNSAF необходимо выполнение REQ-1. Невыполнение REQ-1 вынудит использовать ретранслятор UDP, что очень часто непрактично.
Some NATs are capable of assigning IP addresses from a pool of IP addresses on the external side of the NAT, as opposed to just a single IP address. This is especially common with larger NATs. Some
Некоторые NAT способны назначать IP-адреса из пула IP-адресов, имеющегося на внешней стороне NAT, а не использовать только один IP-адрес. Это особенно характерно для крупных NAT. Некоторые
NATs use the external IP address mapping in an arbitrary fashion (i.e., randomly): one internal IP address could have multiple external IP address mappings active at the same time for different sessions. These NATs have an "IP address pooling" behavior of "Arbitrary". Some large Enterprise NATs use an IP address pooling behavior of "Arbitrary" as a means of hiding the IP address assigned to specific endpoints by making their assignment less predictable. Other NATs use the same external IP address mapping for all sessions associated with the same internal IP address. These NATs have an "IP address pooling" behavior of "Paired". NATs that use an "IP address pooling" behavior of "Arbitrary" can cause issues for applications that use multiple ports from the same endpoint, but that do not negotiate IP addresses individually (e.g., some applications using RTP and RTCP). This is to avoid breaking peer-to-peer applications that are not capable of negotiating the IP address for RTP and the IP address for RTCP separately. The main reason why this requirement is here is that in a peer-to-peer application, you are subject to the other peer's mistake. This requirement will avoid the loss of RTP in this context, although the loss of RTCP may be inevitable in this particular example. It is also worth noting that RFC 3605 is unfortunately not a mandatory part of SIP [RFC3261]. Therefore, this requirement will address a particularly nasty problem that will prevail for a significant period of time.
Обоснование: это позволит приложениям, использующим несколько портов, исходящих с одного внутреннего IP-адреса, также иметь один и тот же внешний IP-адрес. Это делается, чтобы не нарушать работу одноранговых приложений, которые не способны отдельно согласовывать IP-адрес для RTP и IP-адрес для RTCP. В частности, в контексте SIP, если моё приложение поддерживает расширения, определённые в [RFC3605], для раздельного указания адресов и портов RTP и RTCP, а другой участник — нет, то всё равно возможен сбой: поток будет терять пакеты RTCP. Стоит также отметить, что RFC 3605, к сожалению, не является обязательной частью SIP [RFC3261]. Поэтому это требование устраняет особенно неприятную проблему, которая будет сохраняться в течение значительного периода времени.

4.2.2. Port Parity
4.2.2. Чётность порта
Some NATs preserve the parity of the UDP port, i.e., an even port will be mapped to an even port, and an odd port will be mapped to an odd port. This behavior respects the [RFC3550] rule that RTP use even ports, and RTCP use odd ports. RFC 3550 allows any port numbers to be used for RTP and RTCP if the two numbers are specified separately; for example, using [RFC3605]. However, some implementations do not include RFC 3605, and do not recognize when the peer has specified the RTCP port separately using RFC 3605. If such an implementation receives an odd RTP port number from the peer (perhaps after having been translated by a NAT), and then follows the RFC 3550 rule to change the RTP port to the next lower even number, this would obviously result in the loss of RTP. NAT-friendly application aspects are outside the scope of this document. It is expected that this issue will fade away with time, as implementations improve. Preserving the port parity allows for supporting communication with peers that do not support explicit specification of both RTP and RTCP port numbers.
Некоторые NAT сохраняют чётность порта UDP, то есть чётный порт отображается в чётный, а нечётный — в нечётный. Такое поведение соблюдает правило [RFC3550] о том, что RTP использует чётные порты, а RTCP — нечётные. RFC 3550 допускает использование любых номеров портов для RTP и RTCP, если эти два номера указаны отдельно, например с помощью [RFC3605]. Однако некоторые реализации не включают RFC 3605 и не распознают, когда участник указал порт RTCP отдельно с помощью RFC 3605. Если такая реализация получает от участника нечётный номер порта RTP (возможно, после трансляции NAT) и затем следует правилу RFC 3550, уменьшая порт RTP до следующего меньшего чётного числа, это, очевидно, приведёт к потере RTP. Аспекты приложений, дружественных к NAT, выходят за рамки настоящего документа. Ожидается, что эта проблема со временем исчезнет по мере совершенствования реализаций. Сохранение чётности порта позволяет поддерживать связь с участниками, которые не поддерживают явное указание обоих номеров портов RTP и RTCP.
REQ-4: It is RECOMMENDED that a NAT have a "Port parity preservation" behavior of "Yes".
REQ-4: РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «сохранение чётности порта», равное «Да».
Justification: This is to avoid breaking peer-to-peer applications that do not explicitly and separately specify RTP and RTCP port numbers and that follow the RFC 3550 rule to decrement an odd RTP port to make it even. The same considerations apply, as per the IP address pooling requirement.
Обоснование: это делается, чтобы не нарушать работу одноранговых приложений, которые явно и отдельно не указывают номера портов RTP и RTCP и следуют правилу RFC 3550 об уменьшении нечётного порта RTP до чётного. Те же соображения применимы согласно требованию к пулу IP-адресов.
4.2.3. Port Contiguity
4.2.3. Непрерывность портов
Some NATs attempt to preserve the port contiguity rule of RTCP=RTP+1. These NATs do things like sequential assignment or port reservation. Sequential port assignment assumes that the application will open a mapping for RTP first and then open a mapping for RTCP. It is not practical to enforce this requirement on all applications. Furthermore, there is a problem with glare if many applications (or endpoints) are trying to open mappings simultaneously. Port preservation is also problematic since it is wasteful, especially considering that a NAT cannot reliably distinguish between RTP over UDP and other UDP packets where there is no contiguity rule. For those reasons, it would be too complex to attempt to preserve the contiguity rule by suggesting specific NAT behavior, and it would certainly break the deterministic behavior rule.
Некоторые NAT пытаются сохранить правило непрерывности портов RTCP=RTP+1. Такие NAT применяют последовательное назначение или резервирование портов. Последовательное назначение предполагает, что приложение сначала откроет отображение для RTP, а затем откроет отображение для RTCP. Практически невозможно навязать это требование всем приложениям. Кроме того, возникает проблема конфликта, если многие приложения (или конечные точки) пытаются одновременно открыть отображения. Сохранение портов также проблематично, поскольку оно расточительно, особенно учитывая, что NAT не может надёжно отличить RTP поверх UDP от других пакетов UDP, где нет правила непрерывности. По этим причинам было бы слишком сложно пытаться сохранить правило непрерывности путём предложения конкретного поведения NAT, и это наверняка нарушило бы правило детерминированного поведения.
In order to support both RTP and RTCP, it will therefore be necessary that applications follow rules to negotiate RTP and RTCP separately, and account for the very real possibility that the RTCP=RTP+1 rule will be broken. As this is an application requirement, it is outside the scope of this document.
Поэтому для поддержки как RTP, так и RTCP потребуется, чтобы приложения следовали правилам раздельного согласования RTP и RTCP и учитывали вполне реальную возможность нарушения правила RTCP=RTP+1. Поскольку это требование к приложению, оно выходит за рамки настоящего документа.

Some NATs keep the mapping active on both, in which case, both properties are "True".
Некоторые NAT поддерживают отображение активным в обоих направлениях; тогда оба свойства равны «True».
REQ-6: The NAT mapping Refresh Direction MUST have a "NAT Outbound refresh behavior" of "True".
REQ-6: Направление обновления отображения NAT ДОЛЖНО иметь «поведение обновления NAT по исходящим пакетам», равное «True».
a) The NAT mapping Refresh Direction MAY have a "NAT Inbound refresh behavior" of "True".
a) Направление обновления отображения NAT МОЖЕТ иметь «поведение обновления NAT по входящим пакетам», равное «True».
Justification: Outbound refresh is necessary for allowing the client to keep the mapping alive.
Обоснование: обновление по исходящим пакетам необходимо, чтобы клиент мог поддерживать отображение активным.
a) Inbound refresh may be useful for applications with no outgoing UDP traffic. However, allowing inbound refresh may allow an external attacker or misbehaving application to keep a mapping alive indefinitely. This may be a security risk. Also, if the process is repeated with different ports, over time, it could use up all the ports on the NAT.
a) Обновление по входящим пакетам может быть полезно для приложений, не имеющих исходящего трафика UDP. Однако разрешение обновления по входящим пакетам может позволить внешнему злоумышленнику или неправильно работающему приложению поддерживать отображение активным бесконечно. Это может быть риском безопасности. Кроме того, если процесс повторяется с разными портами, со временем он может исчерпать все порты на NAT.
4.4. Conflicting Internal and External IP Address Spaces
4.4. Конфликтующие внутренние и внешние пространства IP-адресов
Many NATs, particularly consumer-level devices designed to be deployed by nontechnical users, routinely obtain their external IP address, default router, and other IP configuration information for their external interface dynamically from an external network, such as an upstream ISP. The NAT, in turn, automatically sets up its own internal subnet in one of the private IP address spaces assigned to this purpose in [RFC1918], typically providing dynamic IP configuration services for hosts on this internal network.
Многие NAT, особенно устройства потребительского уровня, рассчитанные на развёртывание нетехническими пользователями, обычно динамически получают свой внешний IP-адрес, маршрутизатор по умолчанию и другую информацию о конфигурации IP для внешнего интерфейса от внешней сети, например от вышестоящего провайдера. NAT, в свою очередь, автоматически настраивает собственную внутреннюю подсеть в одном из частных пространств IP-адресов, выделенных для этой цели в [RFC1918], обычно предоставляя службы динамической конфигурации IP узлам этой внутренней сети.
Auto-configuration of NATs and private networks can be problematic, however, if the NAT's external network is also in RFC 1918 private address space. In a common scenario, an ISP places its customers behind a NAT and hands out private RFC 1918 addresses to them. Some of these customers, in turn, deploy consumer-level NATs, which, in effect, act as "second-level" NATs, multiplexing their own private RFC 1918 IP subnets onto the single RFC 1918 IP address provided by the ISP. There is no inherent guarantee, in this case, that the ISP's "intermediate" privately-addressed network and the customer's internal privately-addressed network will not use numerically identical or overlapping RFC 1918 IP subnets. Furthermore, customers of consumer-level NATs cannot be expected to have the technical knowledge to prevent this scenario from occurring by manually configuring their internal network with non-conflicting RFC 1918 subnets.
Однако автоматическая конфигурация NAT и частных сетей может быть проблематичной, если внешняя сеть NAT также находится в частном адресном пространстве RFC 1918. В распространённом сценарии провайдер размещает своих клиентов за NAT и выдаёт им частные адреса RFC 1918. Некоторые из этих клиентов, в свою очередь, развёртывают NAT потребительского уровня, которые фактически действуют как NAT «второго уровня», мультиплексируя собственные частные IP-подсети RFC 1918 на единственный IP-адрес RFC 1918, предоставленный провайдером. В этом случае нет никакой гарантии, что «промежуточная» частная сеть провайдера и внутренняя частная сеть клиента не используют численно совпадающие или перекрывающиеся IP-подсети RFC 1918. Более того, нельзя ожидать, что клиенты NAT потребительского уровня обладают техническими знаниями, чтобы предотвратить такой сценарий, вручную настроив свою внутреннюю сеть с непересекающимися подсетями RFC 1918.
NAT vendors need to design their NATs to ensure that they function correctly and robustly even in such problematic scenarios. One possible solution is for the NAT to ensure that whenever its external link is configured with an RFC 1918 private IP address, the NAT automatically selects a different, non-conflicting RFC 1918 IP subnet for its internal network. A disadvantage of this solution is that, if the NAT's external interface is dynamically configured or re- configured after its internal network is already in use, then the NAT may have to renumber its entire internal network dynamically if it detects a conflict.
Производители NAT должны проектировать свои NAT так, чтобы они корректно и надёжно работали даже в таких проблемных сценариях. Одно из возможных решений состоит в том, чтобы NAT гарантировал: всякий раз, когда его внешний канал настроен с частным IP-адресом RFC 1918, NAT автоматически выбирает для своей внутренней сети другую, непересекающуюся IP-подсеть RFC 1918. Недостаток этого решения в том, что если внешний интерфейс NAT настраивается динамически или перенастраивается после того, как его внутренняя сеть уже используется, то NAT может быть вынужден динамически перенумеровать всю свою внутреннюю сеть при обнаружении конфликта.
An alternative solution is for the NAT to be designed so that it can translate and forward traffic correctly, even when its external and internal interfaces are configured with numerically overlapping IP subnets. In this scenario, for example, if the NAT's external interface has been assigned an IP address P in RFC 1918 space, then there might also be an internal node I having the same RFC 1918 private IP address P. An IP packet with destination address P on the external network is directed at the NAT, whereas an IP packet with the same destination address P on the internal network is directed at node I. The NAT therefore needs to maintain a clear operational distinction between "external IP addresses" and "internal IP addresses" to avoid confusing internal node I with its own external interface. In general, the NAT needs to allow all internal nodes (including I) to communicate with all external nodes having public (non-RFC 1918) IP addresses, or having private IP addresses that do not conflict with the addresses used by its internal network.
Альтернативное решение состоит в том, чтобы NAT был спроектирован так, чтобы корректно транслировать и передавать трафик даже тогда, когда его внешний и внутренний интерфейсы настроены с численно перекрывающимися IP-подсетями. В этом сценарии, например, если внешнему интерфейсу NAT назначен IP-адрес P из пространства RFC 1918, то во внутренней сети также может существовать узел I с тем же частным IP-адресом RFC 1918 P. IP-пакет с адресом назначения P во внешней сети направляется в NAT, тогда как IP-пакет с тем же адресом назначения P во внутренней сети направляется узлу I. Поэтому NAT должен поддерживать чёткое операционное различие между «внешними IP-адресами» и «внутренними IP-адресами», чтобы не путать внутренний узел I со своим собственным внешним интерфейсом. В общем случае NAT должен позволять всем внутренним узлам (включая I) взаимодействовать со всеми внешними узлами, имеющими публичные (не RFC 1918) IP-адреса или частные IP-адреса, не конфликтующие с адресами, используемыми его внутренней сетью.
REQ-7: A NAT device whose external IP interface can be configured dynamically MUST either (1) automatically ensure that its internal network uses IP addresses that do not conflict with its external network, or (2) be able to translate and forward traffic between all internal nodes and all external nodes whose IP addresses numerically conflict with the internal network.
REQ-7: NAT-устройство, внешний IP-интерфейс которого может настраиваться динамически, ДОЛЖНО либо (1) автоматически обеспечивать, чтобы его внутренняя сеть использовала IP-адреса, не конфликтующие с его внешней сетью, либо (2) быть способным транслировать и передавать трафик между всеми внутренними узлами и всеми внешними узлами, IP-адреса которых численно конфликтуют с внутренней сетью.
Justification: If a NAT's external and internal interfaces are configured with overlapping IP subnets, then there is, of course, no way for an internal host with RFC 1918 IP address Q to initiate a direct communication session to an external node having the same RFC 1918 address Q, or to other external nodes with IP addresses that numerically conflict with the internal subnet. Such nodes can still open communication sessions indirectly via NAT traversal techniques, however, with the help of a third-party server, such as a STUN server having a public, non-RFC 1918 IP address. In this case, nodes with conflicting private RFC 1918 addresses on opposite sides of the second-level NAT can communicate with each other via their respective temporary public endpoints on the main Internet, as long as their common, first-level NAT (e.g., the upstream ISP's NAT) supports hairpinning behavior, as described in Section 6.
Обоснование: если внешний и внутренний интерфейсы NAT настроены с перекрывающимися IP-подсетями, то, конечно, внутренний узел с IP-адресом RFC 1918 Q не имеет способа инициировать сеанс прямой связи с внешним узлом, имеющим тот же адрес RFC 1918 Q, или с другими внешними узлами, IP-адреса которых численно конфликтуют с внутренней подсетью. Однако такие узлы всё ещё могут открывать сеансы связи косвенно, с помощью методов прохождения через NAT, при содействии стороннего сервера, например STUN-сервера, имеющего публичный IP-адрес, не относящийся к RFC 1918. В этом случае узлы с конфликтующими частными адресами RFC 1918 по разные стороны NAT второго уровня могут связываться друг с другом через свои временные публичные конечные точки в основной сети Интернет, если их общий NAT первого уровня (например, NAT вышестоящего провайдера) поддерживает поведение пронизывания, описанное в разделе 6.
5. Filtering Behavior
5. Поведение фильтрации
This section describes various filtering behaviors observed in NATs.
В этом разделе описаны различные модели поведения фильтрации, наблюдаемые в NAT.
When an internal endpoint opens an outgoing session through a NAT, the NAT assigns a filtering rule for the mapping between an internal IP:port (X:x) and external IP:port (Y:y) tuple.
Когда внутренняя конечная точка открывает исходящий сеанс через NAT, NAT назначает правило фильтрации для отображения между внутренним кортежем IP:port (X:x) и внешним кортежем IP:port (Y:y).
The key behavior to describe is what criteria are used by the NAT to filter packets originating from specific external endpoints.
Ключевое поведение, которое нужно описать, — это критерии, по которым NAT фильтрует пакеты, исходящие от конкретных внешних конечных точек.
Endpoint-Independent Filtering:
Фильтрация, независимая от конечной точки (Endpoint-Independent Filtering):
The NAT filters out only packets not destined to the internal address and port X:x, regardless of the external IP address and port source (Z:z). The NAT forwards any packets destined to X:x. In other words, sending packets from the internal side of the NAT to any external IP address is sufficient to allow any packets back to the internal endpoint.
NAT отфильтровывает только пакеты, не предназначенные внутреннему адресу и порту X:x, независимо от источника внешнего IP-адреса и порта (Z:z). NAT пересылает любые пакеты, предназначенные X:x. Иными словами, отправки пакетов с внутренней стороны NAT на любой внешний IP-адрес достаточно, чтобы разрешить любым пакетам вернуться к внутренней конечной точке.
Address-Dependent Filtering:
Фильтрация, зависимая от адреса (Address-Dependent Filtering):
The NAT filters out packets not destined to the internal address X:x. Additionally, the NAT will filter out packets from Y:y destined for the internal endpoint X:x if X:x has not sent packets to Y:any previously (independently of the port used by Y). In other words, for receiving packets from a specific external endpoint, it is necessary for the internal endpoint to send packets first to that specific external endpoint's IP address.
NAT отфильтровывает пакеты, не предназначенные внутреннему адресу X:x. Кроме того, NAT отфильтровывает пакеты от Y:y, предназначенные внутренней конечной точке X:x, если X:x ранее не отправлял пакеты на Y:any (независимо от порта, используемого Y). Иными словами, для получения пакетов от конкретной внешней конечной точки внутренняя конечная точка должна сначала отправить пакеты на IP-адрес этой конкретной внешней конечной точки.
Address and Port-Dependent Filtering:
Фильтрация, зависимая от адреса и порта (Address and Port-Dependent Filtering):
This is similar to the previous behavior, except that the external port is also relevant. The NAT filters out packets not destined for the internal address X:x. Additionally, the NAT will filter out packets from Y:y destined for the internal endpoint X:x if X:x has not sent packets to Y:y previously.
это похоже на предыдущее поведение, за исключением того, что внешний порт также имеет значение. NAT отфильтровывает пакеты, не предназначенные внутреннему адресу X:x. Кроме того, NAT отфильтровывает пакеты от Y:y, предназначенные внутренней конечной точке X:x, если X:x ранее не отправлял пакеты на Y:y.
In other words, for receiving packets from a specific external endpoint, it is necessary for the internal endpoint to send packets first to that external endpoint's IP address and port.
Иными словами, чтобы получать пакеты от конкретной внешней конечной точки, внутренняя конечная точка должна сначала отправить пакеты на IP-адрес и порт этой внешней конечной точки.
REQ-8: If application transparency is most important, it is RECOMMENDED that a NAT have an "Endpoint-Independent Filtering" behavior. If a more stringent filtering behavior is most important, it is RECOMMENDED that a NAT have an "Address-Dependent Filtering" behavior.
REQ-8: Если наиболее важна прозрачность для приложений, РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «фильтрация, независимая от конечной точки». Если наиболее важно более строгое поведение фильтрации, РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «фильтрация, зависимая от адреса».
a) The filtering behavior MAY be an option configurable by the administrator of the NAT.
a) Поведение фильтрации МОЖЕТ быть параметром, настраиваемым администратором NAT.
Justification: The recommendation to use Endpoint-Independent Filtering is aimed at maximizing application transparency; in particular, for applications that receive media simultaneously from multiple locations (e.g., gaming), or applications that use rendezvous techniques. However, it is also possible that, in some circumstances, it may be preferable to have a more stringent filtering behavior. Filtering independently of the external endpoint is not as secure: An unauthorized packet could get through a specific port while the port was kept open if it was lucky enough to find the port open. In theory, filtering based on both IP address and port is more secure than filtering based only on the IP address (because the external endpoint could, in reality, be two endpoints behind another NAT, where one of the two endpoints is an attacker). However, such a policy could interfere with applications that expect to receive UDP packets on more than one UDP port. Using Endpoint-Independent Filtering or Address- Dependent Filtering instead of Address and Port-Dependent Filtering on a NAT (say, NAT-A) also has benefits when the other endpoint is behind a non-BEHAVE compliant NAT (say, NAT-B) that does not support REQ-1. When the endpoints use ICE, if NAT-A uses Address and Port-Dependent Filtering, connectivity will require a UDP relay.
Обоснование: рекомендация использовать фильтрацию, независимую от конечной точки, направлена на максимальное повышение прозрачности для приложений; в частности, для приложений, которые одновременно получают медиаданные из нескольких мест (например, игры), или приложений, использующих методы рандеву. Однако возможно, что в некоторых обстоятельствах предпочтительнее более строгое поведение фильтрации. Фильтрация, независимая от внешней конечной точки, не столь безопасна: неавторизованный пакет мог бы пройти через конкретный порт, пока порт оставался открытым, если ему повезло застать порт открытым. Теоретически фильтрация по IP-адресу и порту безопаснее фильтрации только по IP-адресу (поскольку внешняя конечная точка может в действительности быть двумя конечными точками за другим NAT, где одна из двух конечных точек — злоумышленник). Однако такая политика могла бы мешать приложениям, которые ожидают получать пакеты UDP более чем на одном порту UDP. Использование фильтрации, независимой от конечной точки, или фильтрации, зависимой от адреса, вместо фильтрации, зависимой от адреса и порта, на NAT (скажем, NAT-A) также даёт преимущества, когда другая конечная точка находится за NAT, не соответствующим BEHAVE (скажем, NAT-B), который не поддерживает REQ-1. Когда конечные точки используют ICE, если NAT-A использует фильтрацию, зависимую от адреса и порта, для связности потребуется ретранслятор UDP.
However, if NAT-A uses Endpoint-Independent Filtering or Address-Dependent Filtering, ICE will ultimately find connectivity without requiring a UDP relay. Having the filtering behavior being an option configurable by the administrator of the NAT ensures that a NAT can be used in the widest variety of deployment scenarios.
Однако если NAT-A использует фильтрацию, независимую от конечной точки, или фильтрацию, зависящую от адреса, то ICE в конечном счёте найдёт связность без необходимости в ретрансляторе UDP. Возможность настраивать поведение фильтрации администратором NAT гарантирует, что NAT можно применять в самых разных сценариях развёртывания.
6. Hairpinning Behavior
6. Поведение пронизывания
If two hosts (called X1 and X2) are behind the same NAT and exchanging traffic, the NAT may allocate an address on the outside of the NAT for X2, called X2':x2'. If X1 sends traffic to X2':x2', it goes to the NAT, which must relay the traffic from X1 to X2. This is referred to as hairpinning and is illustrated below.
Если два узла (назовём их X1 и X2) находятся за одним и тем же NAT и обмениваются трафиком, NAT может выделить адрес на внешней стороне NAT для X2, называемый X2':x2'. Если X1 отправляет трафик на X2':x2', он попадает в NAT, который должен передать трафик от X1 к X2. Это называется пронизыванием и показано ниже. NAT +----+ from X1:x1 to X2':x2' +-----+ X1':x1' | X1 |>>>>>>>>>>>>>>>>>>>>>>>>>>>>>--+---
NAT +----+ from X1:x1 to X2':x2' +-----+ X1':x1' | X1 |>>>>>>>>>>>>>>>>>>>>>>>>>>>>>--+--- +----+ | v | | v | | v | | v | +----+ from X1':x1' to X2:x2 | v | X2':x2' | X2 |<<<<<<<<<<<<<<<<<<<<<<<<<<<<<--+--- +----+ +-----+
NAT +----+ from X1:x1 to X2':x2' +-----+ X1':x1' | X1 |>>>>>>>>>>>>>>>>>>>>>>>>>>>>>--+--- +----+ | v | | v | | v | | v | +----+ from X1':x1' to X2:x2 | v | X2':x2' | X2 |<<<<<<<<<<<<<<<<<<<<<<<<<<<<<--+--- +----+ +-----+
Hairpinning Behavior
Поведение пронизывания
Hairpinning allows two endpoints on the internal side of the NAT to communicate even if they only use each other's external IP addresses and ports.
Пронизывание позволяет двум конечным точкам на внутренней стороне NAT взаимодействовать, даже если они используют только внешние IP-адреса и порты друг друга.
More formally, a NAT that supports hairpinning forwards packets originating from an internal address, X1:x1, destined for an external address X2':x2' that has an active mapping to an internal address X2:x2, back to that internal address, X2:x2. Note that typically X1' is the same as X2'.
Более формально: NAT, поддерживающий пронизывание, пересылает пакеты, исходящие от внутреннего адреса X1:x1 и предназначенные внешнему адресу X2':x2', который имеет активное отображение на внутренний адрес X2:x2, обратно на этот внутренний адрес X2:x2. Отметим, что обычно X1' совпадает с X2'.
Furthermore, the NAT may present the hairpinned packet with either an internal (X1:x1) or an external (X1':x1') source IP address and port. Therefore, the hairpinning NAT behavior can be either "External source IP address and port" or "Internal source IP address and port". "Internal source IP address and port" may cause problems by confusing implementations that expect an external IP address and port.
Кроме того, NAT может предоставлять пакету, прошедшему пронизывание, либо внутренний (X1:x1), либо внешний (X1':x1') IP-адрес и порт источника. Поэтому поведение NAT при пронизывании может быть либо «внешний IP-адрес и порт источника», либо «внутренний IP-адрес и порт источника». «Внутренний IP-адрес и порт источника» может создавать проблемы, вводя в заблуждение реализации, ожидающие внешний IP-адрес и порт.
REQ-9: A NAT MUST support "Hairpinning". a) A NAT Hairpinning behavior MUST be "External source IP address and port".
REQ-9: NAT ДОЛЖЕН поддерживать «пронизывание». a) Поведение NAT при пронизывании ДОЛЖНО быть «внешний IP-адрес и порт источника».
Justification: This requirement is to allow communications between two endpoints behind the same NAT when they are trying each other's external IP addresses.
Обоснование: это требование позволяет организовать связь между двумя конечными точками за одним и тем же NAT, когда они пытаются использовать внешние IP-адреса друг друга.
a) Using the external source IP address is necessary for applications with a restrictive policy of not accepting packets from IP addresses that differ from what is expected.
a) Использование внешнего IP-адреса источника необходимо для приложений с ограничительной политикой, не принимающих пакеты от IP-адресов, отличающихся от ожидаемых.
7. Application Level Gateways
7. Шлюзы уровня приложений
Certain NATs have implemented Application Level Gateways (ALGs) for various protocols, including protocols for negotiating peer-to-peer sessions, such as SIP. Certain NATs have these ALGs turned on permanently, others have them turned on by default but allow them to be turned off, and others have them turned off by default but allow them be turned on.
Некоторые NAT реализовали шлюзы уровня приложений (ALG) для различных протоколов, включая протоколы согласования одноранговых сеансов, такие как SIP. В некоторых NAT эти ALG включены постоянно, в других они включены по умолчанию, но допускают отключение, а в третьих они отключены по умолчанию, но допускают включение.
NAT ALGs may interfere with UNSAF methods or protocols that try to be NAT-aware and therefore must be used with extreme caution.
NAT ALG могут мешать методам UNSAF или протоколам, которые пытаются учитывать NAT, и поэтому должны использоваться с крайней осторожностью.
REQ-10: To eliminate interference with UNSAF NAT traversal mechanisms and allow integrity protection of UDP communications, NAT ALGs for UDP-based protocols SHOULD be turned off. Future standards track specifications that define ALGs can update this to recommend the defaults for the ALGs that they define.
REQ-10: Чтобы исключить помехи механизмам прохождения через NAT на основе UNSAF и обеспечить защиту целостности UDP-коммуникаций, ALG в NAT для протоколов на основе UDP СЛЕДУЕТ отключать. Будущие спецификации уровня стандартов, определяющие ALG, могут обновить это, чтобы рекомендовать значения по умолчанию для определяемых ими ALG.
a) If a NAT includes ALGs, it is RECOMMENDED that the NAT allow the NAT administrator to enable or disable each ALG separately.
a) Если NAT включает ALG, РЕКОМЕНДУЕТСЯ, чтобы NAT позволял администратору NAT включать или отключать каждый ALG отдельно.
Justification: NAT ALGs may interfere with UNSAF methods.
Обоснование: NAT ALG могут мешать методам UNSAF.
a) This requirement allows the user to enable those ALGs that are necessary to aid in the operation of some applications without enabling ALGs, which interfere with the operation of other applications.
a) Это требование позволяет пользователю включать те ALG, которые необходимы для работы некоторых приложений, не включая при этом те ALG, которые мешают работе других приложений.
8. Deterministic Properties
8. Детерминированные свойства
The classification of NATs is further complicated by the fact that, under some conditions, the same NAT will exhibit different behaviors. This has been seen on NATs that preserve ports or have specific algorithms for selecting a port other than a free one. If the external port that the NAT wishes to use is already in use by another session, the NAT must select a different port. This results in different code paths for this conflict case, which results in different behavior.
Классификация NAT дополнительно усложняется тем, что при некоторых условиях один и тот же NAT проявляет различное поведение. Это наблюдалось на NAT, которые сохраняют порты или имеют особые алгоритмы выбора порта, отличного от свободного. Если внешний порт, который NAT хочет использовать, уже занят другим сеансом, NAT должен выбрать другой порт. Это приводит к появлению разных ветвей кода для такого случая конфликта, что даёт различное поведение.
For example, if three hosts X1, X2, and X3 all send from the same port x, through a port preserving NAT with only one external IP address, called X1', the first one to send (i.e., X1) will get an external port of x, but the next two will get x2' and x3' (where these are not equal to x). There are NATs where the External NAT mapping characteristics and the External Filter characteristics change between the X1:x and the X2:x mapping. To make matters worse, there are NATs where the behavior may be the same on the X1:x and X2:x mappings, but different on the third X3:x mapping.
Например, если три узла X1, X2 и X3 отправляют с одного порта x через NAT с сохранением портов, имеющий только один внешний IP-адрес, называемый X1', первый отправивший (то есть X1) получит внешний порт x, а следующие два получат x2' и x3' (где они не равны x). Существуют NAT, у которых характеристики отображения внешнего NAT и характеристики внешней фильтрации меняются между отображениями X1:x и X2:x. Более того, существуют NAT, у которых поведение может быть одинаковым для отображений X1:x и X2:x, но отличаться на третьем отображении X3:x.
Another example is that some NATs have an "Endpoint-Independent Mapping", combined with "Port Overloading", as long as two endpoints are not establishing sessions to the same external direction, but then switch their behavior to "Address and Port-Dependent Mapping" without "Port Preservation" upon detection of these conflicting sessions establishments.
Другой пример: некоторые NAT имеют «отображение, независимое от конечной точки», в сочетании с «перегрузкой портов», пока две конечные точки не устанавливают сеансы в одном и том же внешнем направлении, но затем переключают своё поведение на «отображение, зависимое от адреса и порта» без «сохранения портов» при обнаружении установления таких конфликтующих сеансов.
Any NAT that changes the NAT Mapping or the Filtering behavior without configuration changes, at any point in time, under any particular conditions, is referred to as a "non-deterministic" NAT. NATs that don't are called "deterministic".
Любой NAT, который изменяет поведение отображения или фильтрации без изменения конфигурации, в любой момент времени, при любых конкретных условиях, называется «недетерминированным» NAT. NAT, которые этого не делают, называются «детерминированными».
Non-deterministic NATs generally change behavior when a conflict of some sort happens, i.e., when the port that would normally be used is already in use by another mapping. The NAT mapping and External Filtering in the absence of conflict is referred to as the Primary behavior. The behavior after the first conflict is referred to as Secondary and after the second conflict is referred to as Tertiary. No NATs have been observed that change on further conflicts, but it is certainly possible that they exist.
Недетерминированные NAT обычно меняют поведение при возникновении конфликта того или иного рода, то есть когда порт, который обычно использовался бы, уже занят другим отображением. Отображение NAT и внешняя фильтрация при отсутствии конфликта называются первичным поведением. Поведение после первого конфликта называется вторичным, а после второго конфликта — третичным. NAT, которые менялись бы при дальнейших конфликтах, не наблюдались, но вполне возможно, что они существуют.
REQ-11: A NAT MUST have deterministic behavior, i.e., it MUST NOT change the NAT translation (Section 4) or the Filtering (Section 5) Behavior at any point in time, or under any particular conditions.
REQ-11: NAT ДОЛЖЕН иметь детерминированное поведение, то есть он НЕ ДОЛЖЕН изменять поведение трансляции NAT (раздел 4) или фильтрации (раздел 5) в любой момент времени или при любых конкретных условиях.
Justification: Non-deterministic NATs are very difficult to troubleshoot because they require more intensive testing. This non-deterministic behavior is the root cause of much of the uncertainty that NATs introduce about whether or not applications will work.
Обоснование: недетерминированные NAT очень трудно диагностировать, поскольку они требуют более интенсивного тестирования. Это недетерминированное поведение является коренной причиной большей части неопределённости, которую NAT вносят в вопрос о том, будут ли приложения работать.
9. ICMP Destination Unreachable Behavior
9. Поведение ICMP при недостижимости пункта назначения
When a NAT sends a packet toward a host on the other side of the NAT, an ICMP message may be sent in response to that packet. That ICMP message may be sent by the destination host or by any router along the network path. The NAT's default configuration SHOULD NOT filter ICMP messages based on their source IP address. Such ICMP messages SHOULD be rewritten by the NAT (specifically, the IP headers and the ICMP payload) and forwarded to the appropriate internal or external host. The NAT needs to perform this function for as long as the UDP mapping is active. Receipt of any sort of ICMP message MUST NOT destroy the NAT mapping. A NAT that performs the functions described in the paragraph above is referred to as "support ICMP Processing".
Когда NAT отправляет пакет узлу на другой стороне NAT, в ответ на этот пакет может быть отправлено сообщение ICMP. Это сообщение ICMP может быть отправлено узлом назначения или любым маршрутизатором на пути в сети. Конфигурация NAT по умолчанию НЕ ДОЛЖНА фильтровать сообщения ICMP по их IP-адресу источника. Такие сообщения ICMP СЛЕДУЕТ переписывать силами NAT (а именно заголовки IP и полезную нагрузку ICMP) и пересылать соответствующему внутреннему или внешнему узлу. NAT должен выполнять эту функцию до тех пор, пока отображение UDP активно. Получение любого сообщения ICMP НЕ ДОЛЖНО уничтожать отображение NAT. NAT, выполняющий функции, описанные в предыдущем абзаце, называется «поддерживающим обработку ICMP».
There is no significant security advantage to blocking ICMP Destination Unreachable packets. Additionally, blocking ICMP Destination Unreachable packets can interfere with application failover, UDP Path MTU Discovery (see [RFC1191] and [RFC1435]), and traceroute. Blocking any ICMP message is discouraged, and blocking ICMP Destination Unreachable is strongly discouraged. REQ-12: Receipt of any sort of ICMP message MUST NOT terminate the NAT mapping.
Блокировка пакетов ICMP Destination Unreachable не даёт существенного выигрыша в безопасности. Кроме того, блокировка пакетов ICMP Destination Unreachable может мешать переключению приложений при отказе, обнаружению MTU пути для UDP (см. [RFC1191] и [RFC1435]) и трассировке маршрута. Блокировать любые сообщения ICMP не рекомендуется, а блокировать ICMP Destination Unreachable — настоятельно не рекомендуется. REQ-12: Получение любого сообщения ICMP НЕ ДОЛЖНО завершать отображение NAT.
a) The NAT's default configuration SHOULD NOT filter ICMP messages based on their source IP address.
a) Конфигурация NAT по умолчанию НЕ ДОЛЖНА фильтровать сообщения ICMP по их IP-адресу источника.
b) It is RECOMMENDED that a NAT support ICMP Destination Unreachable messages.
b) РЕКОМЕНДУЕТСЯ, чтобы NAT поддерживал сообщения ICMP Destination Unreachable.
Justification: This is easy to do and is used for many things including MTU discovery and rapid detection of error conditions, and has no negative consequences.
Обоснование: это легко сделать, и это используется для многих целей, включая обнаружение MTU и быстрое выявление ошибочных условий, и не имеет негативных последствий.
10. Fragmentation of Outgoing Packets
10. Фрагментация исходящих пакетов
When the MTU of the adjacent link is too small, fragmentation of packets going from the internal side to the external side of the NAT may occur. This can occur if the NAT is doing Point-to-Point over Ethernet (PPPoE), or if the NAT has been configured with a small MTU to reduce serialization delay when sending large packets and small higher-priority packets, or for other reasons.
Когда MTU смежного канала слишком мал, может происходить фрагментация пакетов, идущих с внутренней стороны NAT на внешнюю. Это может происходить, если NAT использует PPPoE (Point-to-Point over Ethernet) или если NAT настроен на малый MTU для уменьшения задержки сериализации при отправке больших пакетов и небольших пакетов с более высоким приоритетом, либо по другим причинам.
It is worth noting that many IP stacks do not use Path MTU Discovery with UDP packets.
Стоит отметить, что многие стеки IP не используют обнаружение MTU пути для пакетов UDP.
The packet could have its Don't Fragment bit set to 1 (DF=1) or 0 (DF=0).
Пакет может иметь бит Don't Fragment, установленный в 1 (DF=1) или в 0 (DF=0).
REQ-13: If the packet received on an internal IP address has DF=1, the NAT MUST send back an ICMP message "Fragmentation needed and DF set" to the host, as described in [RFC0792].
REQ-13: Если пакет, полученный на внутреннем IP-адресе, имеет DF=1, NAT ДОЛЖЕН отправить узлу в ответ сообщение ICMP «Fragmentation needed and DF set», как описано в [RFC0792].
a) If the packet has DF=0, the NAT MUST fragment the packet and SHOULD send the fragments in order.
a) Если пакет имеет DF=0, NAT ДОЛЖЕН фрагментировать пакет и СЛЕДУЕТ отправлять фрагменты по порядку.
Justification: This is as per RFC 792. a) This is the same function a router performs in a similar situation [RFC1812].
Обоснование: это соответствует RFC 792. a) Это та же функция, которую выполняет маршрутизатор в аналогичной ситуации [RFC1812].
11. Receiving Fragmented Packets
11. Приём фрагментированных пакетов
For a variety of reasons, a NAT may receive a fragmented packet. The IP packet containing the header could arrive in any fragment, depending on network conditions, packet ordering, and the implementation of the IP stack that generated the fragments. A NAT that is capable only of receiving fragments in order (that is, with the header in the first packet) and forwarding each of the fragments to the internal host is described as "Received Fragments Ordered".
По разным причинам NAT может получить фрагментированный пакет. IP-пакет, содержащий заголовок, может прийти в любом фрагменте в зависимости от условий сети, порядка пакетов и реализации стека IP, сгенерировавшего фрагменты. NAT, способный принимать фрагменты только по порядку (то есть с заголовком в первом пакете) и пересылать каждый из фрагментов внутреннему узлу, описывается как «приём фрагментов по порядку» (Received Fragments Ordered).
A NAT that is capable of receiving fragments in or out of order and forwarding the individual fragments (or a reassembled packet) to the internal host is referred to as "Receive Fragments Out of Order". See the Security Considerations section of this document for a discussion of this behavior.
NAT, способный принимать фрагменты в порядке и не по порядку и пересылать отдельные фрагменты (или собранный пакет) внутреннему узлу, называется «приём фрагментов не по порядку» (Receive Fragments Out of Order). Обсуждение такого поведения см. в разделе «Вопросы безопасности» настоящего документа.
A NAT that is neither of these is referred to as "Receive Fragments None".
NAT, не относящийся ни к одному из этих типов, называется «приём фрагментов отсутствует».
REQ-14: A NAT MUST support receiving in-order and out-of-order fragments, so it MUST have "Received Fragment Out of Order" behavior.
REQ-14: NAT ДОЛЖЕН поддерживать приём фрагментов как по порядку, так и не по порядку, поэтому он ДОЛЖЕН иметь поведение «приём фрагментов не по порядку».
a) A NAT's out-of-order fragment processing mechanism MUST be designed so that fragmentation-based DoS attacks do not compromise the NAT's ability to process in-order and unfragmented IP packets.
a) Механизм обработки фрагментов не по порядку в NAT ДОЛЖЕН быть спроектирован так, чтобы DoS-атаки, основанные на фрагментации, не нарушали способность NAT обрабатывать IP-пакеты, приходящие по порядку и нефрагментированные.
Justification: See Security Considerations.
Обоснование: см. «Вопросы безопасности».
12. Requirements
12. Требования
The requirements in this section are aimed at minimizing the complications caused by NATs to applications, such as realtime communications and online gaming. The requirements listed earlier in the document are consolidated here into a single section.
Требования в этом разделе направлены на минимизацию сложностей, которые NAT создают для приложений, таких как связь в реальном времени и сетевые игры. Требования, перечисленные ранее в документе, здесь сведены в один раздел.
It should be understood, however, that applications normally do not know in advance if the NAT conforms to the recommendations defined in this section. Peer-to-peer media applications still need to use normal procedures, such as ICE [ICE].
Однако следует понимать, что приложения обычно не знают заранее, соответствует ли NAT рекомендациям, определённым в этом разделе. Одноранговым медиаприложениям по-прежнему необходимо использовать обычные процедуры, такие как ICE [ICE].
A NAT that supports all the mandatory requirements of this specification (i.e., the "MUST"), is "compliant with this specification". A NAT that supports all the requirements of this specification (i.e., including the "RECOMMENDED") is "fully compliant with all the mandatory and recommended requirements of this specification". REQ-1: A NAT MUST have an "Endpoint-Independent Mapping" behavior.
NAT, поддерживающий все обязательные требования настоящей спецификации (то есть «MUST»), «соответствует настоящей спецификации». NAT, поддерживающий все требования настоящей спецификации (то есть включая «RECOMMENDED»), «полностью соответствует всем обязательным и рекомендуемым требованиям настоящей спецификации». REQ-1: NAT ДОЛЖЕН иметь поведение «отображение, независимое от конечной точки».
REQ-2: It is RECOMMENDED that a NAT have an "IP address pooling" behavior of "Paired". Note that this requirement is not applicable to NATs that do not support IP address pooling.
REQ-2: РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение пула IP-адресов «парное». Отметим, что это требование не применимо к NAT, не поддерживающим пул IP-адресов.
REQ-3: A NAT MUST NOT have a "Port assignment" behavior of "Port overloading".
REQ-3: NAT НЕ ДОЛЖЕН иметь поведение «назначение портов», равное «перегрузка портов».
a) If the host's source port was in the range 0-1023, it is RECOMMENDED the NAT's source port be in the same range. If the host's source port was in the range 1024-65535, it is RECOMMENDED that the NAT's source port be in that range.
a) Если порт источника узла находился в диапазоне 0-1023, РЕКОМЕНДУЕТСЯ, чтобы порт источника NAT находился в том же диапазоне. Если порт источника узла находился в диапазоне 1024-65535, РЕКОМЕНДУЕТСЯ, чтобы порт источника NAT находился в этом диапазоне.
REQ-4: It is RECOMMENDED that a NAT have a "Port parity preservation" behavior of "Yes".
REQ-4: РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «сохранение чётности порта», равное «Да».
REQ-5: A NAT UDP mapping timer MUST NOT expire in less than two minutes, unless REQ-5a applies.
REQ-5: Таймер отображения UDP в NAT НЕ ДОЛЖЕН истекать менее чем за две минуты, если не применяется REQ-5a.
a) For specific destination ports in the well-known port range (ports 0-1023), a NAT MAY have shorter UDP mapping timers that are specific to the IANA-registered application running over that specific destination port.
a) Для конкретных портов назначения в диапазоне хорошо известных портов (порты 0-1023) NAT МОЖЕТ иметь более короткие таймеры отображения UDP, специфичные для приложения, зарегистрированного в IANA и работающего через этот конкретный порт назначения.
b) The value of the NAT UDP mapping timer MAY be configurable.
b) Значение таймера отображения UDP в NAT МОЖЕТ быть настраиваемым.
c) A default value of five minutes or more for the NAT UDP mapping timer is RECOMMENDED.
c) РЕКОМЕНДУЕТСЯ значение по умолчанию пять минут или более для таймера отображения UDP в NAT.
REQ-6: The NAT mapping Refresh Direction MUST have a "NAT Outbound refresh behavior" of "True".
REQ-6: Направление обновления отображения NAT ДОЛЖНО иметь «поведение обновления NAT по исходящим пакетам», равное «True».
a) The NAT mapping Refresh Direction MAY have a "NAT Inbound refresh behavior" of "True".
a) Направление обновления отображения NAT МОЖЕТ иметь «поведение обновления NAT по входящим пакетам», равное «True».
REQ-7 A NAT device whose external IP interface can be configured dynamically MUST either (1) Automatically ensure that its internal network uses IP addresses that do not conflict with its external network, or (2) Be able to translate and forward traffic between all internal nodes and all external nodes whose IP addresses numerically conflict with the internal network.
REQ-7: NAT-устройство, внешний IP-интерфейс которого может настраиваться динамически, ДОЛЖНО либо (1) автоматически обеспечивать, чтобы его внутренняя сеть использовала IP-адреса, не конфликтующие с его внешней сетью, либо (2) быть способным транслировать и передавать трафик между всеми внутренними узлами и всеми внешними узлами, IP-адреса которых численно конфликтуют с внутренней сетью.
REQ-8: If application transparency is most important, it is RECOMMENDED that a NAT have "Endpoint-Independent Filtering" behavior. If a more stringent filtering behavior is most important, it is RECOMMENDED that a NAT have "Address-Dependent Filtering" behavior. a) The filtering behavior MAY be an option configurable by the administrator of the NAT.
REQ-8: Если наиболее важна прозрачность для приложений, РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «фильтрация, независимая от конечной точки». Если наиболее важно более строгое поведение фильтрации, РЕКОМЕНДУЕТСЯ, чтобы NAT имел поведение «фильтрация, зависимая от адреса». a) Поведение фильтрации МОЖЕТ быть параметром, настраиваемым администратором NAT.
REQ-9: A NAT MUST support "Hairpinning". a) A NAT Hairpinning behavior MUST be "External source IP address and port".
REQ-9: NAT ДОЛЖЕН поддерживать «пронизывание». a) Поведение NAT при пронизывании ДОЛЖНО быть «внешний IP-адрес и порт источника».
REQ-10: To eliminate interference with UNSAF NAT traversal mechanisms and allow integrity protection of UDP communications, NAT ALGs for UDP-based protocols SHOULD be turned off. Future standards track specifications that define an ALG can update this to recommend the ALGs on which they define default.
REQ-10: Чтобы исключить помехи механизмам прохождения через NAT на основе UNSAF и обеспечить защиту целостности UDP-коммуникаций, ALG в NAT для протоколов на основе UDP СЛЕДУЕТ отключать. Будущие спецификации уровня стандартов, определяющие ALG, могут обновить это, чтобы рекомендовать значения по умолчанию для тех ALG, которые они определяют.
a) If a NAT includes ALGs, it is RECOMMENDED that the NAT allow the NAT administrator to enable or disable each ALG separately.
a) Если NAT включает ALG, РЕКОМЕНДУЕТСЯ, чтобы NAT позволял администратору NAT включать или отключать каждый ALG отдельно.
REQ-11: A NAT MUST have deterministic behavior, i.e., it MUST NOT change the NAT translation (Section 4) or the Filtering (Section 5) Behavior at any point in time, or under any particular conditions.
REQ-11: NAT ДОЛЖЕН иметь детерминированное поведение, то есть он НЕ ДОЛЖЕН изменять поведение трансляции NAT (раздел 4) или фильтрации (раздел 5) в любой момент времени или при любых конкретных условиях.
REQ-12: Receipt of any sort of ICMP message MUST NOT terminate the NAT mapping.
REQ-12: Получение любого сообщения ICMP НЕ ДОЛЖНО завершать отображение NAT.
a) The NAT's default configuration SHOULD NOT filter ICMP messages based on their source IP address.
a) Конфигурация NAT по умолчанию НЕ ДОЛЖНА фильтровать сообщения ICMP по их IP-адресу источника.
b) It is RECOMMENDED that a NAT support ICMP Destination Unreachable messages.
b) РЕКОМЕНДУЕТСЯ, чтобы NAT поддерживал сообщения ICMP Destination Unreachable.
REQ-13 If the packet received on an internal IP address has DF=1, the NAT MUST send back an ICMP message "Fragmentation needed and DF set" to the host, as described in [RFC0792].
REQ-13: Если пакет, полученный на внутреннем IP-адресе, имеет DF=1, NAT ДОЛЖЕН отправить узлу в ответ сообщение ICMP «Fragmentation needed and DF set», как описано в [RFC0792].
a) If the packet has DF=0, the NAT MUST fragment the packet and SHOULD send the fragments in order.
a) Если пакет имеет DF=0, NAT ДОЛЖЕН фрагментировать пакет и СЛЕДУЕТ отправлять фрагменты по порядку.
REQ-14: A NAT MUST support receiving in-order and out-of-order fragments, so it MUST have "Received Fragment Out of Order" behavior.
REQ-14: NAT ДОЛЖЕН поддерживать приём фрагментов как по порядку, так и не по порядку, поэтому он ДОЛЖЕН иметь поведение «приём фрагментов не по порядку».
a) A NAT's out-of-order fragment processing mechanism MUST be designed so that fragmentation-based DoS attacks do not compromise the NAT's ability to process in-order and unfragmented IP packets.
a) Механизм обработки фрагментов не по порядку в NAT ДОЛЖЕН быть спроектирован так, чтобы DoS-атаки, основанные на фрагментации, не нарушали способность NAT обрабатывать IP-пакеты, приходящие по порядку и нефрагментированные.
13. Security Considerations
13. Вопросы безопасности
NATs are often deployed to achieve security goals. Most of the recommendations and requirements in this document do not affect the security properties of these devices, but a few of them do have security implications and are discussed in this section.
NAT часто развёртываются для достижения целей безопасности. Большинство рекомендаций и требований в настоящем документе не влияют на свойства безопасности этих устройств, но некоторые из них имеют последствия для безопасности и рассматриваются в этом разделе.
This document recommends that the timers for mapping be refreshed on outgoing packets (see REQ-6) and does not make recommendations about whether or not inbound packets should update the timers. If inbound packets update the timers, an external attacker can keep the mapping alive forever and attack future devices that may end up with the same internal address. A device that was also the DHCP server for the private address space could mitigate this by cleaning any mappings when a DHCP lease expired. For unicast UDP traffic (the scope of this document), it may not seem relevant to support inbound timer refresh; however, for multicast UDP, the question is harder. It is expected that future documents discussing NAT behavior with multicast traffic will refine the requirements around handling of the inbound refresh timer. Some devices today do update the timers on inbound packets.
Настоящий документ рекомендует обновлять таймеры отображения по исходящим пакетам (см. REQ-6) и не даёт рекомендаций о том, должны ли входящие пакеты обновлять таймеры. Если входящие пакеты обновляют таймеры, внешний злоумышленник может поддерживать отображение активным вечно и атаковать будущие устройства, которые могут получить тот же внутренний адрес. Устройство, которое также являлось бы DHCP-сервером для частного адресного пространства, могло бы смягчить это, очищая отображения по истечении аренды DHCP. Для одноадресного трафика UDP (область действия настоящего документа) поддержка обновления таймера по входящим пакетам может показаться неактуальной; однако для многоадресного UDP вопрос сложнее. Ожидается, что будущие документы, рассматривающие поведение NAT при многоадресном трафике, уточнят требования к обработке таймера обновления по входящим пакетам. Некоторые устройства сегодня действительно обновляют таймеры по входящим пакетам.
This document recommends that the NAT filters be specific to the external IP address only (see REQ-8) and not to the external IP address and UDP port. It can be argued that this is less secure than using the IP and port. Devices that wish to filter on IP and port do still comply with these requirements.
Настоящий документ рекомендует, чтобы фильтры NAT зависели только от внешнего IP-адреса (см. REQ-8), а не от внешнего IP-адреса и порта UDP. Можно утверждать, что это менее безопасно, чем использование IP-адреса и порта. Устройства, которые хотят фильтровать по IP-адресу и порту, всё равно соответствуют этим требованиям.
Non-deterministic NATs are risky from a security point of view. They are very difficult to test because they are, well, non-deterministic. Testing by a person configuring one may result in the person thinking it is behaving as desired, yet under different conditions, which an attacker can create, the NAT may behave differently. These requirements recommend that devices be deterministic.
Недетерминированные NAT рискованны с точки зрения безопасности. Их очень трудно тестировать, потому что они, собственно, недетерминированы. Тестирование человеком, настраивающим такое устройство, может привести к тому, что он сочтёт его работающим как нужно, однако при других условиях, которые может создать злоумышленник, NAT может вести себя иначе. Эти требования рекомендуют, чтобы устройства были детерминированными.
This document requires that NATs have an "external NAT mapping is endpoint independent" behavior. This does not reduce the security of devices. Which packets are allowed to flow across the device is determined by the external filtering behavior, which is independent of the mapping behavior.
Настоящий документ требует, чтобы NAT имели поведение «внешнее отображение NAT не зависит от конечной точки». Это не снижает безопасность устройств. То, какие пакеты разрешено пропускать через устройство, определяется поведением внешней фильтрации, которое не зависит от поведения отображения.
When a fragmented packet is received from the external side, and the packets are out of order so that the initial fragment does not arrive first, many systems simply discard the out-of-order packets. Moreover, since some networks deliver small packets ahead of large ones, there can be many out-of-order fragments. NATs that are capable of delivering these out-of-order packets are possible, but they need to store the out-of-order fragments, which can open up a Denial-of-Service (DoS) opportunity, if done incorrectly. Fragmentation has been a tool used in many attacks, some involving passing fragmented packets through NATs, and others involving DoS attacks based on the state needed to reassemble the fragments. NAT implementers should be aware of [RFC3128] and [RFC1858].
Когда фрагментированный пакет получен с внешней стороны и пакеты идут не по порядку, так что начальный фрагмент приходит не первым, многие системы просто отбрасывают пакеты, пришедшие не по порядку. Более того, поскольку некоторые сети доставляют небольшие пакеты раньше больших, фрагментов не по порядку может быть много. NAT, способные доставлять такие пакеты не по порядку, возможны, но им нужно хранить фрагменты не по порядку, что при неправильной реализации может открыть возможность для атаки типа «отказ в обслуживании» (DoS). Фрагментация была инструментом, используемым во многих атаках: одни связаны с пропуском фрагментированных пакетов через NAT, другие — с DoS-атаками, основанными на состоянии, необходимом для сборки фрагментов. Реализаторам NAT следует знать о [RFC3128] и [RFC1858].
14. IAB Considerations
14. Соображения IAB
The IAB has studied the problem of "Unilateral Self Address Fixing", which is the general process by which a client attempts to determine its address in another realm on the other side of a NAT through a collaborative protocol reflection mechanism [RFC3424].
IAB изучил проблему «одностороннего исправления собственного адреса» (Unilateral Self Address Fixing) — общего процесса, в котором клиент пытается определить свой адрес в другом домене на другой стороне NAT с помощью механизма согласованного отражения протокола [RFC3424].
This specification does not, in itself, constitute an UNSAF application. It consists of a series of requirements for NATs aimed at minimizing the negative impact that those devices have on peer-to- peer media applications, especially when those applications are using UNSAF methods.
Настоящая спецификация сама по себе не является приложением UNSAF. Она состоит из набора требований к NAT, направленных на минимизацию негативного влияния этих устройств на одноранговые медиаприложения, особенно когда такие приложения используют методы UNSAF.
Section 3 of UNSAF lists several practical issues with solutions to NAT problems. This document makes recommendations to reduce the uncertainty and problems introduced by these practical issues with NATs. In addition, UNSAF lists five architectural considerations. Although this is not an UNSAF proposal, it is interesting to consider the impact of this work on these architectural considerations.
В разделе 3 документа UNSAF перечислены несколько практических проблем, связанных с решениями проблем NAT. Настоящий документ содержит рекомендации по уменьшению неопределённости и проблем, вносимых этими практическими вопросами, связанными с NAT. Кроме того, UNSAF перечисляет пять архитектурных соображений. Хотя это и не предложение UNSAF, интересно рассмотреть влияние этой работы на указанные архитектурные соображения.
Arch-1: The scope of this is limited to UDP packets in NATs like the ones widely deployed today. The "fix" helps constrain the variability of NATs for true UNSAF solutions such as STUN.
Арх-1: Область действия ограничена пакетами UDP в NAT, подобных широко развёрнутым сегодня. Это «исправление» помогает ограничить вариативность NAT для настоящих решений UNSAF, таких как STUN.
Arch-2: This will exit at the same rate that NATs exit. It does not imply any protocol machinery that would continue to live after NATs were gone, or make it more difficult to remove them.
Арх-2: Это исчезнет с той же скоростью, с какой исчезнут NAT. Это не подразумевает какого-либо протокольного механизма, который продолжал бы жить после исчезновения NAT или затруднил бы их удаление.
Arch-3: This does not reduce the overall brittleness of NATs, but will hopefully reduce some of the more outrageous NAT behaviors and make it easer to discuss and predict NAT behavior in given situations.
Арх-3: Это не уменьшает общую хрупкость NAT, но, будем надеяться, уменьшит некоторые из наиболее вопиющих моделей поведения NAT и облегчит обсуждение и предсказание поведения NAT в заданных ситуациях.
Arch-4: This work and the results [RESULTS] of various NATs represent the most comprehensive work at IETF on what the real issues are with NATs for applications like VoIP. This work and STUN have pointed out, more than anything else, the brittleness NATs introduce and the difficulty of addressing these issues.
Арх-4: Эта работа и результаты [RESULTS] тестирования различных NAT представляют собой наиболее полную работу в IETF над тем, в чём состоят реальные проблемы NAT для таких приложений, как VoIP. Эта работа и STUN указали, более чем что-либо ещё, на хрупкость, которую вносят NAT, и на трудность решения этих проблем.
Arch-5: This work and the test results [RESULTS] provide a reference model for what any UNSAF proposal might encounter in deployed NATs.
Арх-5: Эта работа и результаты тестов [RESULTS] дают эталонную модель того, с чем может столкнуться любое предложение UNSAF в развёрнутых NAT.
