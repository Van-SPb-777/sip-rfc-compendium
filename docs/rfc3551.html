Abstract
Аннотация
This document describes a profile called "RTP/AVP" for the use of the real-time transport protocol (RTP), version 2, and the associated control protocol, RTCP, within audio and video multiparticipant conferences with minimal control. It provides interpretations of generic fields within the RTP specification suitable for audio and video conferences. In particular, this document defines a set of default mappings from payload type numbers to encodings.
Настоящий документ описывает профиль «RTP/AVP» для использования протокола передачи в реальном времени (RTP) версии 2 и связанного с ним протокола управления RTCP в аудио- и видеоконференциях с несколькими участниками при минимальном управлении. Он даёт интерпретации общих полей спецификации RTP, подходящие для аудио- и видеоконференций. В частности, настоящий документ определяет набор отображений по умолчанию с номеров типов полезной нагрузки на кодировки.
This document also describes how audio and video data may be carried within RTP. It defines a set of standard encodings and their names when used within RTP. The descriptions provide pointers to reference implementations and the detailed standards. This document is meant as an aid for implementors of audio, video and other real-time multimedia applications.
Настоящий документ также описывает, как аудио- и видеоданные могут передаваться в RTP. Он определяет набор стандартных кодировок и их имена при использовании в RTP. Описания содержат указатели на эталонные реализации и подробные стандарты. Настоящий документ предназначен как помощь разработчикам аудио-, видео- и других мультимедийных приложений реального времени.

1. Introduction
1. Введение
This profile defines aspects of RTP left unspecified in the RTP Version 2 protocol definition (RFC 3550) [1]. This profile is intended for the use within audio and video conferences with minimal session control. In particular, no support for the negotiation of parameters or membership control is provided. The profile is expected to be useful in sessions where no negotiation or membership control are used (e.g., using the static payload types and the membership indications provided by RTCP), but this profile may also be useful in conjunction with a higher-level control protocol.
Этот профиль определяет аспекты RTP, оставленные неопределёнными в определении протокола RTP версии 2 (RFC 3550) [1]. Профиль предназначен для использования в аудио- и видеоконференциях с минимальным управлением сессией. В частности, не обеспечивается поддержка согласования параметров или управления членством. Ожидается, что профиль будет полезен в сессиях, где согласование или управление членством не используются (например, с использованием статических типов полезной нагрузки и указаний о членстве, предоставляемых RTCP), но профиль может быть полезен и в сочетании с протоколом управления более высокого уровня.
Use of this profile may be implicit in the use of the appropriate applications; there may be no explicit indication by port number, protocol identifier or the like. Applications such as session directories may use the name for this profile specified in Section 11.
Использование этого профиля может подразумеваться применением соответствующих приложений; может не быть явного указания посредством номера порта, идентификатора протокола и т. п. Такие приложения, как каталоги сессий, могут использовать имя профиля, указанное в разделе 11.
Other profiles may make different choices for the items specified here.
Другие профили могут делать иные выборы для указанных здесь пунктов.
This document also defines a set of encodings and payload formats for audio and video. These payload format descriptions are included here only as a matter of convenience since they are too small to warrant separate documents. Use of these payload formats is NOT REQUIRED to use this profile. Only the binding of some of the payload formats to static payload type numbers in Tables 4 and 5 is normative.
Настоящий документ также определяет набор кодировок и форматов полезной нагрузки для аудио и видео. Эти описания форматов полезной нагрузки включены здесь лишь для удобства, поскольку они слишком малы, чтобы оправдать отдельные документы. Использование этих форматов полезной нагрузки НЕ ТРЕБУЕТСЯ для использования этого профиля. Нормативна только привязка некоторых форматов полезной нагрузки к статическим номерам типов полезной нагрузки в таблицах 4 и 5.

1.1. Терминология
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 [2] and indicate requirement levels for implementations compliant with this RTP profile.
Ключевые слова «MUST», «MUST NOT», «REQUIRED», «SHALL», «SHALL NOT», «SHOULD», «SHOULD NOT», «RECOMMENDED», «MAY» и «OPTIONAL» в настоящем документе должны толковаться так, как описано в RFC 2119 [2], и указывать уровни требований для реализаций, совместимых с этим профилем RTP.
This document defines the term media type as dividing encodings of audio and video content into three classes: audio, video and audio/video (interleaved).
Настоящий документ определяет термин «тип медиа» (media type), разделяющий кодировки аудио- и видеосодержимого на три класса: аудио, видео и аудио/видео (чередование).
2. RTP and RTCP Packet Forms and Protocol Behavior
2. Формы пакетов и поведение протоколов RTP и RTCP
The section "RTP Profiles and Payload Format Specifications" of RFC 3550 enumerates a number of items that can be specified or modified in a profile. This section addresses these items. Generally, this profile follows the default and/or recommended aspects of the RTP specification.
Раздел «Профили RTP и спецификации форматов полезной нагрузки» RFC 3550 перечисляет ряд пунктов, которые могут быть указаны или изменены в профиле. Настоящий раздел рассматривает эти пункты. В целом этот профиль следует по умолчанию и/или рекомендованным аспектам спецификации RTP.
RTP data header: The standard format of the fixed RTP data header is used (one marker bit).
Заголовок данных RTP: используется стандартный формат фиксированного заголовка данных RTP (один бит-маркер).
Payload types: Static payload types are defined in Section 6.
Типы полезной нагрузки: статические типы полезной нагрузки определены в разделе 6.
RTP data header additions: No additional fixed fields are appended to the RTP data header.
Дополнения к заголовку данных RTP: никакие дополнительные фиксированные поля не добавляются к заголовку данных RTP.
RTP data header extensions: No RTP header extensions are defined, but applications operating under this profile MAY use such extensions. Thus, applications SHOULD NOT assume that the RTP header X bit is always zero and SHOULD be prepared to ignore the header extension. If a header extension is defined in the future, that definition MUST specify the contents of the first 16 bits in such a way that multiple different extensions can be identified.
Расширения заголовка данных RTP: никаких расширений заголовка RTP не определено, но приложения, работающие по этому профилю, МОГУТ использовать такие расширения. Поэтому приложениям НЕ СЛЕДУЕТ предполагать, что бит X заголовка RTP всегда равен нулю, и следует быть готовыми игнорировать расширение заголовка. Если в будущем будет определено расширение заголовка, это определение ДОЛЖНО указывать содержимое первых 16 бит так, чтобы можно было идентифицировать несколько различных расширений.
RTCP packet types: No additional RTCP packet types are defined by this profile specification.
Типы пакетов RTCP: настоящей спецификацией профиля не определяется никаких дополнительных типов пакетов RTCP.
RTCP report interval: The suggested constants are to be used for the RTCP report interval calculation. Sessions operating under this profile MAY specify a separate parameter for the RTCP traffic bandwidth rather than using the default fraction of the session bandwidth. The RTCP traffic bandwidth MAY be divided into two separate session parameters for those participants which are active data senders and those which are not. Following the recommendation in the RTP specification [1] that 1/4 of the RTCP bandwidth be dedicated to data senders, the RECOMMENDED default values for these two parameters would be 1.25% and 3.75%, respectively. For a particular session, the RTCP bandwidth for non-data-senders MAY be set to zero when operating on unidirectional links or for sessions that don't require feedback on the quality of reception. The RTCP bandwidth for data senders SHOULD be kept non-zero so that sender reports can still be sent for inter-media synchronization and to identify the source by CNAME. The means by which the one or two session parameters for RTCP bandwidth are specified is beyond the scope of this memo.
Интервал отчётов RTCP: предложенные константы должны использоваться для вычисления интервала отчётов RTCP. Сессии, работающие по этому профилю, МОГУТ задавать отдельный параметр для полосы пропускания трафика RTCP вместо использования доли полосы пропускания сессии по умолчанию. Полоса пропускания трафика RTCP МОЖЕТ быть разделена на два отдельных параметра сессии для участников, активно отправляющих данные, и для тех, кто этого не делает. Следуя рекомендации в спецификации RTP [1] о том, что 1/4 полосы пропускания RTCP выделяется отправителям данных, РЕКОМЕНДУЕМЫЕ значения по умолчанию для этих двух параметров составляли бы соответственно 1,25% и 3,75%. Для конкретной сессии полоса пропускания RTCP для не-отправителей данных МОЖЕТ быть установлена в ноль при работе по однонаправленным каналам или для сессий, не требующих обратной связи о качестве приёма. Полосу пропускания RTCP для отправителей данных СЛЕДУЕТ держать ненулевой, чтобы отчёты отправителя всё равно могли отправляться для межмедийной синхронизации и идентификации источника по CNAME. Средства, которыми задаются один или два параметра сессии для полосы пропускания RTCP, выходят за рамки настоящего меморандума.
SR/RR extension: No extension section is defined for the RTCP SR or RR packet.
Расширение SR/RR: никакой секции расширения не определено для пакета RTCP SR или RR.
SDES use: Applications MAY use any of the SDES items described in the RTP specification. While CNAME information MUST be sent every reporting interval, other items SHOULD only be sent every third reporting interval, with NAME sent seven out of eight times within that slot and the remaining SDES items cyclically taking up the eighth slot, as defined in Section 6.2.2 of the RTP specification. In other words, NAME is sent in RTCP packets 1, 4, 7, 10, 13, 16, 19, while, say, EMAIL is used in RTCP packet 22.
Использование SDES: приложения МОГУТ использовать любой из элементов SDES, описанных в спецификации RTP. Хотя информация CNAME ДОЛЖНА отправляться в каждом интервале отчётов, другие элементы СЛЕДУЕТ отправлять только в каждом третьем интервале отчётов, причём NAME отправляется семь раз из восьми в пределах этого слота, а остальные элементы SDES циклически занимают восьмой слот, как определено в разделе 6.2.2 спецификации RTP. Иными словами, NAME отправляется в пакетах RTCP 1, 4, 7, 10, 13, 16, 19, тогда как, скажем, EMAIL используется в пакете RTCP 22.
Security: The RTP default security services are also the default under this profile.
Безопасность: службы безопасности RTP по умолчанию также являются умолчанием по этому профилю.
String-to-key mapping: No mapping is specified by this profile.
Отображение строки в ключ: настоящим профилем не определено никакого отображения.
Congestion: RTP and this profile may be used in the context of enhanced network service, for example, through Integrated Services (RFC 1633) [4] or Differentiated Services (RFC 2475) [5], or they may be used with best effort service.
Перегрузка: RTP и этот профиль могут использоваться в контексте улучшенного сетевого обслуживания, например через интегрированные службы (RFC 1633) [4] или дифференцированные службы (RFC 2475) [5], либо могут использоваться с обслуживанием по мере возможностей.
If enhanced service is being used, RTP receivers SHOULD monitor packet loss to ensure that the service that was requested is actually being delivered. If it is not, then they SHOULD assume that they are receiving best-effort service and behave accordingly.
Если используется улучшенное обслуживание, приёмникам RTP СЛЕДУЕТ контролировать потери пакетов, чтобы удостовериться, что запрошенное обслуживание действительно предоставляется. Если нет, им СЛЕДУЕТ предполагать, что они получают обслуживание по мере возможностей, и вести себя соответственно.
If best-effort service is being used, RTP receivers SHOULD monitor packet loss to ensure that the packet loss rate is within acceptable parameters. Packet loss is considered acceptable if a TCP flow across the same network path and experiencing the same network conditions would achieve an average throughput, measured on a reasonable timescale, that is not less than the RTP flow is achieving. This condition can be satisfied by implementing congestion control mechanisms to adapt the transmission rate (or the number of layers subscribed for a layered multicast session), or by arranging for a receiver to leave the session if the loss rate is unacceptably high.
Если используется обслуживание по мере возможностей, приёмникам RTP СЛЕДУЕТ контролировать потери пакетов, чтобы удостовериться, что доля потерь находится в приемлемых параметрах. Потери пакетов считаются приемлемыми, если поток TCP через тот же сетевой путь и в тех же сетевых условиях достиг бы средней пропускной способности, измеренной в разумном масштабе времени, не меньшей, чем достигает поток RTP. Это условие может быть выполнено путём реализации механизмов управления перегрузкой для адаптации скорости передачи (или числа слоёв, подписанных для многослойной многоадресной сессии), либо путём обеспечения того, чтобы приёмник покинул сессию, если доля потерь неприемлемо высока.
The comparison to TCP cannot be specified exactly, but is intended as an "order-of-magnitude" comparison in timescale and throughput. The timescale on which TCP throughput is measured is the round- trip time of the connection.
Сравнение с TCP нельзя задать точно, но оно предназначено как сравнение «порядка величины» по масштабу времени и пропускной способности. Масштаб времени, на котором измеряется пропускная способность TCP, — время кругового обхода соединения.
In essence, this requirement states that it is not acceptable to deploy an application (using RTP or any other transport protocol) on the best-effort Internet which consumes bandwidth arbitrarily and does not compete fairly with TCP within an order of magnitude.
По сути, это требование означает, что недопустимо развёртывать приложение (использующее RTP или любой другой транспортный протокол) в Интернете с негарантированной доставкой, которое потребляет полосу пропускания произвольным образом и не конкурирует с TCP добросовестно в пределах порядка величины.
Underlying protocol: The profile specifies the use of RTP over unicast and multicast UDP as well as TCP. (This does not preclude the use of these definitions when RTP is carried by other lower- layer protocols.)
Нижележащий протокол: профиль задаёт использование RTP поверх одноадресного и многоадресного UDP, а также TCP. (Это не исключает использования этих определений, когда RTP переносится другими протоколами нижних уровней.)
Transport mapping: The standard mapping of RTP and RTCP to transport-level addresses is used.
Транспортное отображение: используется стандартное отображение RTP и RTCP на адреса транспортного уровня.
Encapsulation: This profile leaves to applications the specification of RTP encapsulation in protocols other than UDP.
Инкапсуляция: этот профиль оставляет приложениям спецификацию инкапсуляции RTP в протоколах, отличных от UDP.
3. Registering Additional Encodings
3. Регистрация дополнительных кодировок
This profile lists a set of encodings, each of which is comprised of a particular media data compression or representation plus a payload format for encapsulation within RTP. Some of those payload formats are specified here, while others are specified in separate RFCs. It is expected that additional encodings beyond the set listed here will be created in the future and specified in additional payload format RFCs.
Этот профиль перечисляет набор кодировок, каждая из которых состоит из конкретного сжатия или представления медиаданных плюс формата полезной нагрузки для инкапсуляции в RTP. Некоторые из этих форматов полезной нагрузки определены здесь, другие — в отдельных RFC. Ожидается, что в будущем будут созданы дополнительные кодировки сверх перечисленного здесь набора и определены в дополнительных RFC о форматах полезной нагрузки.
This profile also assigns to each encoding a short name which MAY be used by higher-level control protocols, such as the Session Description Protocol (SDP), RFC 2327 [6], to identify encodings selected for a particular RTP session.
Этот профиль также назначает каждой кодировке короткое имя, которое МОЖЕТ использоваться протоколами управления более высокого уровня, например протоколом описания сессий (SDP), RFC 2327 [6], для идентификации кодировок, выбранных для конкретной сессии RTP.
In some contexts it may be useful to refer to these encodings in the form of a MIME content-type. To facilitate this, RFC 3555 [7] provides registrations for all of the encodings names listed here as MIME subtype names under the "audio" and "video" MIME types through the MIME registration procedure as specified in RFC 2048 [8].
В некоторых контекстах может быть полезно ссылаться на эти кодировки в форме MIME-типа содержимого. Чтобы облегчить это, RFC 3555 [7] предоставляет регистрации для всех перечисленных здесь имён кодировок как имён подтипов MIME под типами MIME «audio» и «video» через процедуру регистрации MIME, указанную в RFC 2048 [8].
Any additional encodings specified for use under this profile (or others) may also be assigned names registered as MIME subtypes with the Internet Assigned Numbers Authority (IANA). This registry provides a means to insure that the names assigned to the additional encodings are kept unique. RFC 3555 specifies the information that is required for the registration of RTP encodings.
Любым дополнительным кодировкам, указанным для использования по этому профилю (или другим), также могут быть назначены имена, зарегистрированные как подтипы MIME в Администрации адресного пространства Интернета (IANA). Этот реестр предоставляет средство обеспечения уникальности назначенных имён дополнительных кодировок. RFC 3555 указывает информацию, требуемую для регистрации кодировок RTP.
In addition to assigning names to encodings, this profile also assigns static RTP payload type numbers to some of them. However, the payload type number space is relatively small and cannot accommodate assignments for all existing and future encodings. During the early stages of RTP development, it was necessary to use statically assigned payload types because no other mechanism had been specified to bind encodings to payload types. It was anticipated that non-RTP means beyond the scope of this memo (such as directory services or invitation protocols) would be specified to establish a dynamic mapping between a payload type and an encoding. Now, mechanisms for defining dynamic payload type bindings have been specified in the Session Description Protocol (SDP) and in other protocols such as ITU-T Recommendation H.323/H.245. These mechanisms associate the registered name of the encoding/payload format, along with any additional required parameters, such as the RTP timestamp clock rate and number of channels, with a payload type number. This association is effective only for the duration of the RTP session in which the dynamic payload type binding is made. This association applies only to the RTP session for which it is made, thus the numbers can be re-used for different encodings in different sessions so the number space limitation is avoided.
Помимо назначения имён кодировкам, этот профиль также назначает статические номера типов полезной нагрузки RTP некоторым из них. Однако пространство номеров типов полезной нагрузки относительно мало и не может вместить назначения для всех существующих и будущих кодировок. На ранних этапах развития RTP было необходимо использовать статически назначенные типы полезной нагрузки, поскольку не было указано иного механизма привязки кодировок к типам полезной нагрузки. Предполагалось, что будут указаны не-RTP средства за пределами настоящего меморандума (такие как службы каталогов или протоколы приглашения) для установления динамического отображения между типом полезной нагрузки и кодировкой. Теперь механизмы определения динамических привязок типов полезной нагрузки указаны в протоколе описания сессий (SDP) и в других протоколах, таких как Рекомендация ITU-T H.323/H.245. Эти механизмы связывают зарегистрированное имя кодировки/формата полезной нагрузки вместе с любыми дополнительными требуемыми параметрами, такими как тактовая частота отметок времени RTP и число каналов, с номером типа полезной нагрузки. Эта связь действует только на время сессии RTP, в которой сделана динамическая привязка типа полезной нагрузки. Эта связь применяется только к сессии RTP, для которой она сделана, поэтому номера могут повторно использоваться для разных кодировок в разных сессиях, и ограничение пространства номеров обходится.
This profile reserves payload type numbers in the range 96-127 exclusively for dynamic assignment. Applications SHOULD first use values in this range for dynamic payload types. Those applications which need to define more than 32 dynamic payload types MAY bind codes below 96, in which case it is RECOMMENDED that unassigned payload type numbers be used first. However, the statically assigned payload types are default bindings and MAY be dynamically bound to new encodings if needed. Redefining payload types below 96 may cause incorrect operation if an attempt is made to join a session without obtaining session description information that defines the dynamic payload types.
Этот профиль резервирует номера типов полезной нагрузки в диапазоне 96–127 исключительно для динамического назначения. Приложениям СЛЕДУЕТ сначала использовать значения в этом диапазоне для динамических типов полезной нагрузки. Тем приложениям, которым нужно определить более 32 динамических типов полезной нагрузки, МОЖНО привязывать коды ниже 96, и в этом случае РЕКОМЕНДУЕТСЯ сначала использовать неназначенные номера типов полезной нагрузки. Однако статически назначенные типы полезной нагрузки являются привязками по умолчанию и МОГУТ быть динамически привязаны к новым кодировкам при необходимости. Переопределение типов полезной нагрузки ниже 96 может вызвать некорректную работу, если делается попытка присоединиться к сессии без получения информации описания сессии, определяющей динамические типы полезной нагрузки.
Dynamic payload types SHOULD NOT be used without a well-defined mechanism to indicate the mapping. Systems that expect to interoperate with others operating under this profile SHOULD NOT make their own assignments of proprietary encodings to particular, fixed payload types.
Динамические типы полезной нагрузки НЕ СЛЕДУЕТ использовать без чётко определённого механизма указания отображения. Системам, которые рассчитывают на взаимодействие с другими, работающими по этому профилю, НЕ СЛЕДУЕТ делать собственные назначения проприетарных кодировок конкретным фиксированным типам полезной нагрузки.
This specification establishes the policy that no additional static payload types will be assigned beyond the ones defined in this document. Establishing this policy avoids the problem of trying to create a set of criteria for accepting static assignments and encourages the implementation and deployment of the dynamic payload type mechanisms.
Настоящая спецификация устанавливает политику, что никакие дополнительные статические типы полезной нагрузки не будут назначаться сверх определённых в настоящем документе. Установление этой политики избегает проблемы попытки создать набор критериев приёма статических назначений и поощряет реализацию и развёртывание механизмов динамических типов полезной нагрузки.

4. Аудио
4.1. Encoding-Independent Rules
4.1. Правила, не зависящие от кодировки
Since the ability to suppress silence is one of the primary motivations for using packets to transmit voice, the RTP header carries both a sequence number and a timestamp to allow a receiver to distinguish between lost packets and periods of time when no data was transmitted. Discontiguous transmission (silence suppression) MAY be used with any audio payload format. Receivers MUST assume that senders may suppress silence unless this is restricted by signaling specified elsewhere. (Even if the transmitter does not suppress silence, the receiver should be prepared to handle periods when no data is present since packets may be lost.)
Поскольку способность подавлять тишину — одна из основных причин использования пакетов для передачи голоса, заголовок RTP несёт как порядковый номер, так и отметку времени, чтобы приёмник мог различать потерянные пакеты и периоды, когда данные не передавались. Прерывистая передача (подавление тишины) МОЖЕТ использоваться с любым форматом аудиополезной нагрузки. Приёмники ДОЛЖНЫ предполагать, что отправители могут подавлять тишину, если это не ограничено сигнализацией, указанной в другом месте. (Даже если передатчик не подавляет тишину, приёмник должен быть готов обрабатывать периоды отсутствия данных, поскольку пакеты могут быть потеряны.)
Some payload formats (see Sections 4.5.3 and 4.5.6) define a "silence insertion descriptor" or "comfort noise" frame to specify parameters for artificial noise that may be generated during a period of silence to approximate the background noise at the source. For other payload formats, a generic Comfort Noise (CN) payload format is specified in RFC 3389 [9]. When the CN payload format is used with another payload format, different values in the RTP payload type field distinguish comfort-noise packets from those of the selected payload format.
Некоторые форматы полезной нагрузки (см. разделы 4.5.3 и 4.5.6) определяют кадр «дескриптора вставки тишины» или «комфортного шума» для указания параметров искусственного шума, который может генерироваться в течение периода тишины, чтобы приблизить фоновый шум у источника. Для других форматов полезной нагрузки общий формат полезной нагрузки комфортного шума (CN) определён в RFC 3389 [9]. Когда формат полезной нагрузки CN используется с другим форматом полезной нагрузки, разные значения в поле типа полезной нагрузки RTP отличают пакеты комфортного шума от пакетов выбранного формата полезной нагрузки.
For applications which send either no packets or occasional comfort- noise packets during silence, the first packet of a talkspurt, that is, the first packet after a silence period during which packets have not been transmitted contiguously, SHOULD be distinguished by setting the marker bit in the RTP data header to one. The marker bit in all other packets is zero. The beginning of a talkspurt MAY be used to adjust the playout delay to reflect changing network delays. Applications without silence suppression MUST set the marker bit to zero.
Для приложений, которые во время тишины не отправляют пакетов либо отправляют эпизодические пакеты комфортного шума, первый пакет всплеска речи, то есть первый пакет после периода тишины, в течение которого пакеты не передавались непрерывно, СЛЕДУЕТ отличать установкой бита-маркера в заголовке данных RTP в единицу. Бит-маркер во всех остальных пакетах равен нулю. Начало всплеска речи МОЖЕТ использоваться для корректировки задержки воспроизведения, чтобы отразить изменяющиеся сетевые задержки. Приложения без подавления тишины ДОЛЖНЫ устанавливать бит-маркер в ноль.
The RTP clock rate used for generating the RTP timestamp is independent of the number of channels and the encoding; it usually equals the number of sampling periods per second. For N-channel encodings, each sampling period (say, 1/8,000 of a second) generates N samples. (This terminology is standard, but somewhat confusing, as the total number of samples generated per second is then the sampling rate times the channel count.)
Тактовая частота RTP, используемая для генерации отметки времени RTP, не зависит от числа каналов и кодировки; обычно она равна числу периодов дискретизации в секунду. Для N-канальных кодировок каждый период дискретизации (скажем, 1/8000 секунды) генерирует N отсчётов. (Эта терминология стандартна, но несколько запутанна, поскольку общее число отсчётов, генерируемых в секунду, тогда равно частоте дискретизации, умноженной на число каналов.)

The sampling frequency SHOULD be drawn from the set: 8,000, 11,025, 16,000, 22,050, 24,000, 32,000, 44,100 and 48,000 Hz. However, most audio encodings are defined for a more restricted set of sampling frequencies. Receivers SHOULD be prepared to accept multi-channel audio, but MAY choose to only play a single channel.
Частоту дискретизации СЛЕДУЕТ выбирать из набора: 8000, 11 025, 16 000, 22 050, 24 000, 32 000, 44 100 и 48 000 Гц. Однако большинство аудиокодировок определены для более ограниченного набора частот дискретизации. Приёмники ДОЛЖНЫ быть готовы принимать многоканальное аудио, но МОГУТ выбрать воспроизведение только одного канала.
4.2. Operating Recommendations
4.2. Рекомендации по работе
The following recommendations are default operating parameters. Applications SHOULD be prepared to handle other values. The ranges given are meant to give guidance to application writers, allowing a set of applications conforming to these guidelines to interoperate without additional negotiation. These guidelines are not intended to restrict operating parameters for applications that can negotiate a set of interoperable parameters, e.g., through a conference control protocol.
Следующие рекомендации — параметры работы по умолчанию. Приложения ДОЛЖНЫ быть готовы обрабатывать другие значения. Приведённые диапазоны предназначены для руководства разработчикам приложений, позволяя набору приложений, соответствующих этим руководствам, взаимодействовать без дополнительного согласования. Эти руководящие принципы не предназначены для ограничения параметров работы приложений, которые могут согласовать набор совместимых параметров, например через протокол управления конференцией.
For packetized audio, the default packetization interval SHOULD have a duration of 20 ms or one frame, whichever is longer, unless otherwise noted in Table 1 (column "ms/packet"). The packetization interval determines the minimum end-to-end delay; longer packets introduce less header overhead but higher delay and make packet loss more noticeable. For non-interactive applications such as lectures or for links with severe bandwidth constraints, a higher packetization delay MAY be used. A receiver SHOULD accept packets representing between 0 and 200 ms of audio data. (For framed audio encodings, a receiver SHOULD accept packets with a number of frames equal to 200 ms divided by the frame duration, rounded up.) This restriction allows reasonable buffer sizing for the receiver.
Для пакетированного аудио интервал пакетирования по умолчанию СЛЕДУЕТ выбирать равным 20 мс или одному кадру, в зависимости от того, что дольше, если иное не указано в таблице 1 (столбец «мс/пакет»). Интервал пакетирования определяет минимальную сквозную задержку; более длинные пакеты вносят меньшие накладные расходы заголовка, но большую задержку и делают потерю пакетов более заметной. Для неинтерактивных приложений, таких как лекции, или для каналов с жёсткими ограничениями полосы пропускания МОЖЕТ использоваться большая задержка пакетирования. Приёмнику СЛЕДУЕТ принимать пакеты, представляющие от 0 до 200 мс аудиоданных. (Для покадровых аудиокодировок приёмнику СЛЕДУЕТ принимать пакеты с числом кадров, равным 200 мс, делённым на длительность кадра, с округлением вверх.) Это ограничение позволяет разумно выбирать размер буфера для приёмника.
4.3. Guidelines for Sample-Based Audio Encodings
4.3. Руководящие принципы для аудиокодировок на основе отсчётов
In sample-based encodings, each audio sample is represented by a fixed number of bits. Within the compressed audio data, codes for individual samples may span octet boundaries. An RTP audio packet may contain any number of audio samples, subject to the constraint that the number of bits per sample times the number of samples per packet yields an integral octet count. Fractional encodings produce less than one octet per sample.
В кодировках на основе отсчётов каждый аудиоотсчёт представляется фиксированным числом бит. В сжатых аудиоданных коды отдельных отсчётов могут пересекать границы октетов. Аудиопакет RTP может содержать любое число аудиоотсчётов при условии, что число бит на отсчёт, умноженное на число отсчётов в пакете, даёт целое число октетов. Дробные кодировки дают менее одного октета на отсчёт.
The duration of an audio packet is determined by the number of samples in the packet.
Длительность аудиопакета определяется числом отсчётов в пакете.
For sample-based encodings producing one or more octets per sample, samples from different channels sampled at the same sampling instant SHOULD be packed in consecutive octets. For example, for a two- channel encoding, the octet sequence is (left channel, first sample), (right channel, first sample), (left channel, second sample), (right channel, second sample), .... For multi-octet encodings, octets SHOULD be transmitted in network byte order (i.e., most significant octet first).
Для кодировок на основе отсчётов, дающих один или более октетов на отсчёт, отсчёты из разных каналов, дискретизированные в один момент, СЛЕДУЕТ упаковывать в последовательные октеты. Например, для двухканальной кодировки последовательность октетов: (левый канал, первый отсчёт), (правый канал, первый отсчёт), (левый канал, второй отсчёт), (правый канал, второй отсчёт), .... Для многобайтовых кодировок октеты СЛЕДУЕТ передавать в сетевом порядке байтов (то есть старший октет первым).
The packing of sample-based encodings producing less than one octet per sample is encoding-specific.
Упаковка кодировок на основе отсчётов, дающих менее одного октета на отсчёт, специфична для кодировки.
The RTP timestamp reflects the instant at which the first sample in the packet was sampled, that is, the oldest information in the packet.
Отметка времени RTP отражает момент, в который был дискретизирован первый отсчёт в пакете, то есть самую старую информацию в пакете.
4.4. Guidelines for Frame-Based Audio Encodings
4.4. Руководящие принципы для аудиокодировок на основе кадров
Frame-based encodings encode a fixed-length block of audio into another block of compressed data, typically also of fixed length. For frame-based encodings, the sender MAY choose to combine several such frames into a single RTP packet. The receiver can tell the number of frames contained in an RTP packet, if all the frames have the same length, by dividing the RTP payload length by the audio frame size which is defined as part of the encoding. This does not work when carrying frames of different sizes unless the frame sizes are relatively prime. If not, the frames MUST indicate their size.
Покадровые кодировки кодируют блок аудио фиксированной длины в другой блок сжатых данных, обычно также фиксированной длины. Для покадровых кодировок отправитель МОЖЕТ выбрать объединение нескольких таких кадров в один пакет RTP. Приёмник может определить число кадров в пакете RTP, если все кадры имеют одинаковую длину, разделив длину полезной нагрузки RTP на размер аудиокадра, определённый как часть кодировки. Это не работает при переносе кадров разного размера, если только размеры кадров не являются взаимно простыми. Если нет, кадры ДОЛЖНЫ указывать свой размер.
For frame-based codecs, the channel order is defined for the whole block. That is, for two-channel audio, right and left samples SHOULD be coded independently, with the encoded frame for the left channel preceding that for the right channel.
Для покадровых кодеков порядок каналов определён для всего блока. То есть для двухканального аудио правые и левые отсчёты СЛЕДУЕТ кодировать независимо, причём кодированный кадр левого канала предшествует кадру правого канала.
All frame-oriented audio codecs SHOULD be able to encode and decode several consecutive frames within a single packet. Since the frame size for the frame-oriented codecs is given, there is no need to use a separate designation for the same encoding, but with different number of frames per packet.
Все покадровые аудиокодеки ДОЛЖНЫ уметь кодировать и декодировать несколько последовательных кадров в одном пакете. Поскольку размер кадра для покадровых кодеков задан, нет необходимости использовать отдельное обозначение для той же кодировки, но с другим числом кадров в пакете.
RTP packets SHALL contain a whole number of frames, with frames inserted according to age within a packet, so that the oldest frame (to be played first) occurs immediately after the RTP packet header. The RTP timestamp reflects the instant at which the first sample in the first frame was sampled, that is, the oldest information in the packet.
Пакеты RTP ДОЛЖНЫ содержать целое число кадров, причём кадры вставляются по возрасту внутри пакета, так что самый старый кадр (воспроизводимый первым) находится сразу после заголовка пакета RTP. Отметка времени RTP отражает момент, в который был дискретизирован первый отсчёт первого кадра, то есть самую старую информацию в пакете.

4.5.1. DVI4
4.5.1. DVI4
DVI4 uses an adaptive delta pulse code modulation (ADPCM) encoding scheme that was specified by the Interactive Multimedia Association (IMA) as the "IMA ADPCM wave type". However, the encoding defined here as DVI4 differs in three respects from the IMA specification:
DVI4 использует схему кодирования адаптивной дифференциальной импульсно-кодовой модуляции (ADPCM), которая была определена Ассоциацией интерактивных мультимедиа (IMA) как «волновой тип IMA ADPCM». Однако определённая здесь кодировка DVI4 отличается от спецификации IMA в трёх отношениях:
o The RTP DVI4 header contains the predicted value rather than the first sample value contained the IMA ADPCM block header.
* Заголовок RTP DVI4 содержит предсказанное значение, а не первое значение отсчёта, содержащееся в заголовке блока IMA ADPCM.
o IMA ADPCM blocks contain an odd number of samples, since the first sample of a block is contained just in the header (uncompressed), followed by an even number of compressed samples. DVI4 has an even number of compressed samples only, using the `predict' word from the header to decode the first sample.
* Блоки IMA ADPCM содержат нечётное число отсчётов, поскольку первый отсчёт блока содержится только в заголовке (без сжатия), за которым следует чётное число сжатых отсчётов. DVI4 имеет только чётное число сжатых отсчётов, используя слово «predict» из заголовка для декодирования первого отсчёта.
o For DVI4, the 4-bit samples are packed with the first sample in the four most significant bits and the second sample in the four least significant bits. In the IMA ADPCM codec, the samples are packed in the opposite order.
* Для DVI4 4-битные отсчёты упакованы так, что первый отсчёт находится в четырёх старших битах, а второй отсчёт — в четырёх младших битах. В кодеке IMA ADPCM отсчёты упакованы в обратном порядке.
Each packet contains a single DVI block. This profile only defines the 4-bit-per-sample version, while IMA also specified a 3-bit-per- sample encoding.
Каждый пакет содержит один блок DVI. Этот профиль определяет только версию с 4 битами на отсчёт, тогда как IMA также определяла кодирование с 3 битами на отсчёт.
The "header" word for each channel has the following structure:
Слово «заголовок» для каждого канала имеет следующую структуру:
int16 predict; /* predicted value of first sample from the previous block (L16 format) */ u_int8 index; /* current index into stepsize table */ u_int8 reserved; /* set to zero by sender, ignored by receiver */
int16 predict — предсказанное значение первого отсчёта из предыдущего блока (формат L16); u_int8 index — текущий индекс в таблице размеров шага; u_int8 reserved — устанавливается отправителем в ноль, игнорируется приёмником.
Each octet following the header contains two 4-bit samples, thus the number of samples per packet MUST be even because there is no means to indicate a partially filled last octet.
Каждый октет после заголовка содержит два 4-битных отсчёта, поэтому число отсчётов в пакете ДОЛЖНО быть чётным, так как нет средства указать частично заполненный последний октет.
Packing of samples for multiple channels is for further study.
Упаковка отсчётов для нескольких каналов требует дальнейшего изучения.
The IMA ADPCM algorithm was described in the document IMA Recommended Practices for Enhancing Digital Audio Compatibility in Multimedia Systems (version 3.0). However, the Interactive Multimedia Association ceased operations in 1997. Resources for an archived copy of that document and a software implementation of the RTP DVI4 encoding are listed in Section 13.
Алгоритм IMA ADPCM был описан в документе IMA «Recommended Practices for Enhancing Digital Audio Compatibility in Multimedia Systems» (версия 3.0). Однако Ассоциация интерактивных мультимедиа прекратила деятельность в 1997 году. Ресурсы для архивной копии того документа и программной реализации кодировки RTP DVI4 перечислены в разделе 13.
4.5.2. G722
4.5.2. G722
G722 is specified in ITU-T Recommendation G.722, "7 kHz audio-coding within 64 kbit/s". The G.722 encoder produces a stream of octets, each of which SHALL be octet-aligned in an RTP packet. The first bit transmitted in the G.722 octet, which is the most significant bit of the higher sub-band sample, SHALL correspond to the most significant bit of the octet in the RTP packet.
G722 определён в Рекомендации ITU-T G.722 «7 kHz audio-coding within 64 kbit/s». Кодер G.722 формирует поток октетов, каждый из которых ДОЛЖЕН быть выровнен по октету в пакете RTP. Первый бит, передаваемый в октете G.722, который является старшим значащим битом отсчёта верхней подполосы, ДОЛЖЕН соответствовать старшему значащему биту октета в пакете RTP.
Even though the actual sampling rate for G.722 audio is 16,000 Hz, the RTP clock rate for the G722 payload format is 8,000 Hz because that value was erroneously assigned in RFC 1890 and must remain unchanged for backward compatibility. The octet rate or sample-pair rate is 8,000 Hz.
Хотя фактическая частота дискретизации для аудио G.722 — 16 000 Гц, тактовая частота RTP для формата полезной нагрузки G722 — 8000 Гц, поскольку это значение было ошибочно назначено в RFC 1890 и должно оставаться неизменным для обратной совместимости. Частота октетов или частота пар отсчётов — 8000 Гц.
4.5.3. G723
4.5.3. G723
G723 is specified in ITU Recommendation G.723.1, "Dual-rate speech coder for multimedia communications transmitting at 5.3 and 6.3 kbit/s". The G.723.1 5.3/6.3 kbit/s codec was defined by the ITU-T as a mandatory codec for ITU-T H.324 GSTN videophone terminal applications. The algorithm has a floating point specification in Annex B to G.723.1, a silence compression algorithm in Annex A to G.723.1 and a scalable channel coding scheme for wireless applications in G.723.1 Annex C.
G723 определён в Рекомендации ITU G.723.1 «Dual-rate speech coder for multimedia communications transmitting at 5.3 and 6.3 kbit/s». Кодек G.723.1 5,3/6,3 кбит/с был определён ITU-T как обязательный кодек для терминальных приложений видеотелефона ITU-T H.324 GSTN. Алгоритм имеет спецификацию с плавающей точкой в Приложении B к G.723.1, алгоритм сжатия тишины в Приложении A к G.723.1 и схему масштабируемого канального кодирования для беспроводных приложений в Приложении C к G.723.1.
This Recommendation specifies a coded representation that can be used for compressing the speech signal component of multi-media services at a very low bit rate. Audio is encoded in 30 ms frames, with an additional delay of 7.5 ms due to look-ahead. A G.723.1 frame can be one of three sizes: 24 octets (6.3 kb/s frame), 20 octets (5.3 kb/s frame), or 4 octets. These 4-octet frames are called SID frames (Silence Insertion Descriptor) and are used to specify comfort noise parameters. There is no restriction on how 4, 20, and 24 octet frames are intermixed. The least significant two bits of the first octet in the frame determine the frame size and codec type:
Эта Рекомендация определяет кодированное представление, которое может использоваться для сжатия речевой составляющей мультимедийных служб с очень низкой битовой скоростью. Аудио кодируется кадрами по 30 мс с дополнительной задержкой 7,5 мс из-за упреждающего анализа. Кадр G.723.1 может быть одного из трёх размеров: 24 октета (кадр 6,3 кбит/с), 20 октетов (кадр 5,3 кбит/с) или 4 октета. Эти 4-октетные кадры называются SID-кадрами (Silence Insertion Descriptor) и используются для указания параметров комфортного шума. Нет ограничений на то, как смешиваются 4-, 20- и 24-октетные кадры. Два младших бита первого октета в кадре определяют размер кадра и тип кодека:
bits content octets/frame 00 high-rate speech (6.3 kb/s) 24 01 low-rate speech (5.3 kb/s) 20 10 SID frame 4 11 reserved
bits content octets/frame 00 high-rate speech (6.3 kb/s) 24 01 low-rate speech (5.3 kb/s) 20 10 SID frame 4 11 reserved
It is possible to switch between the two rates at any 30 ms frame boundary. Both (5.3 kb/s and 6.3 kb/s) rates are a mandatory part of the encoder and decoder. Receivers MUST accept both data rates and MUST accept SID frames unless restriction of these capabilities has been signaled. The MIME registration for G723 in RFC 3555 [7] specifies parameters that MAY be used with MIME or SDP to restrict to a single data rate or to restrict the use of SID frames. This coder was optimized to represent speech with near-toll quality at the above rates using a limited amount of complexity.
Можно переключаться между двумя скоростями на любой границе кадра 30 мс. Обе скорости (5,3 кбит/с и 6,3 кбит/с) — обязательная часть кодера и декодера. Приёмники ДОЛЖНЫ принимать обе скорости передачи данных и ДОЛЖНЫ принимать SID-кадры, если ограничение этих возможностей не сигнализировано. Регистрация MIME для G723 в RFC 3555 [7] определяет параметры, которые МОГУТ использоваться с MIME или SDP для ограничения одной скоростью передачи данных или для ограничения использования SID-кадров. Этот кодер был оптимизирован для представления речи с качеством, близким к магистральному, на указанных скоростях при ограниченной сложности.

4.5.4. G726-40, G726-32, G726-24, and G726-16
4.5.4. G726-40, G726-32, G726-24 и G726-16
ITU-T Recommendation G.726 describes, among others, the algorithm recommended for conversion of a single 64 kbit/s A-law or mu-law PCM channel encoded at 8,000 samples/sec to and from a 40, 32, 24, or 16 kbit/s channel. The conversion is applied to the PCM stream using an Adaptive Differential Pulse Code Modulation (ADPCM) transcoding technique. The ADPCM representation consists of a series of codewords with a one-to-one correspondence to the samples in the PCM stream. The G726 data rates of 40, 32, 24, and 16 kbit/s have codewords of 5, 4, 3, and 2 bits, respectively.
Рекомендация ITU-T G.726 описывает, среди прочего, алгоритм, рекомендуемый для преобразования одного канала PCM A-law или mu-law со скоростью 64 кбит/с, кодированного при 8000 отсчётов/с, в канал 40, 32, 24 или 16 кбит/с и обратно. Преобразование применяется к потоку PCM с использованием техники транскодирования адаптивной дифференциальной импульсно-кодовой модуляции (ADPCM). Представление ADPCM состоит из последовательности кодовых слов с взаимно однозначным соответствием отсчётам в потоке PCM. Скорости данных G726 40, 32, 24 и 16 кбит/с имеют кодовые слова соответственно 5, 4, 3 и 2 бита.
The 16 and 24 kbit/s encodings do not provide toll quality speech. They are designed for used in overloaded Digital Circuit Multiplication Equipment (DCME). ITU-T G.726 recommends that the 16 and 24 kbit/s encodings should be alternated with higher data rate encodings to provide an average sample size of between 3.5 and 3.7 bits per sample.
Кодировки 16 и 24 кбит/с не обеспечивают речи магистрального качества. Они предназначены для использования в перегруженном оборудовании цифрового мультиплексирования каналов (DCME). ITU-T G.726 рекомендует чередовать кодировки 16 и 24 кбит/с с кодировками с более высокой скоростью данных, чтобы обеспечить средний размер отсчёта от 3,5 до 3,7 бит на отсчёт.
The encodings of G.726 are here denoted as G726-40, G726-32, G726-24, and G726-16. Prior to 1990, G721 described the 32 kbit/s ADPCM encoding, and G723 described the 40, 32, and 16 kbit/s encodings. Thus, G726-32 designates the same algorithm as G721 in RFC 1890.
Кодировки G.726 здесь обозначаются как G726-40, G726-32, G726-24 и G726-16. До 1990 года G721 описывал кодировку ADPCM 32 кбит/с, а G723 описывал кодировки 40, 32 и 16 кбит/с. Таким образом, G726-32 обозначает тот же алгоритм, что и G721 в RFC 1890.
A stream of G726 codewords contains no information on the encoding being used, therefore transitions between G726 encoding types are not permitted within a sequence of packed codewords. Applications MUST determine the encoding type of packed codewords from the RTP payload identifier.
Поток кодовых слов G726 не содержит информации об используемой кодировке, поэтому переходы между типами кодировки G726 не допускаются внутри последовательности упакованных кодовых слов. Приложения ДОЛЖНЫ определять тип кодировки упакованных кодовых слов по идентификатору полезной нагрузки RTP.
No payload-specific header information SHALL be included as part of the audio data. A stream of G726 codewords MUST be packed into octets as follows: the first codeword is placed into the first octet such that the least significant bit of the codeword aligns with the least significant bit in the octet, the second codeword is then packed so that its least significant bit coincides with the least significant unoccupied bit in the octet. 4.5.5. G728
G728 is specified in ITU-T Recommendation G.728, "Coding of speech at 16 kbit/s using low-delay code excited linear prediction".
G728 определён в Рекомендации ITU-T G.728 «Coding of speech at 16 kbit/s using low-delay code excited linear prediction».
A G.278 encoder translates 5 consecutive audio samples into a 10-bit codebook index, resulting in a bit rate of 16 kb/s for audio sampled at 8,000 samples per second. The group of five consecutive samples is called a vector. Four consecutive vectors, labeled V1 to V4 (where V1 is to be played first by the receiver), build one G.728 frame. The four vectors of 40 bits are packed into 5 octets, labeled B1 through B5. B1 SHALL be placed first in the RTP packet.
Кодер G.728 преобразует 5 последовательных аудиоотсчётов в 10-битный индекс кодовой книги, что даёт битовую скорость 16 кбит/с для аудио, дискретизированного при 8000 отсчётов в секунду. Группа из пяти последовательных отсчётов называется вектором. Четыре последовательных вектора, обозначенных V1–V4 (где V1 воспроизводится приёмником первым), образуют один кадр G.728. 4.5.6. G729
4.5.6. G729
G729 is specified in ITU-T Recommendation G.729, "Coding of speech at 8 kbit/s using conjugate structure-algebraic code excited linear prediction (CS-ACELP)". A reduced-complexity version of the G.729 algorithm is specified in Annex A to Rec. G.729. The speech coding algorithms in the main body of G.729 and in G.729 Annex A are fully interoperable with each other, so there is no need to further distinguish between them. An implementation that signals or accepts use of G729 payload format may implement either G.729 or G.729A unless restricted by additional signaling specified elsewhere related specifically to the encoding rather than the payload format. The G.729 and G.729 Annex A codecs were optimized to represent speech with high quality, where G.729 Annex A trades some speech quality for an approximate 50% complexity reduction [10]. See the next Section (4.5.7) for other data rates added in later G.729 Annexes. For all data rates, the sampling frequency (and RTP timestamp clock rate) is 8,000 Hz.
G729 определён в Рекомендации ITU-T G.729 «Coding of speech at 8 kbit/s using conjugate structure-algebraic code excited linear prediction (CS-ACELP)». Версия алгоритма G.729 с пониженной сложностью определена в Приложении A к Рек. G.729. Алгоритмы кодирования речи в основном тексте G.729 и в Приложении A к G.729 полностью совместимы друг с другом, поэтому нет необходимости их далее различать. Реализация, которая сигнализирует или принимает использование формата полезной нагрузки G729, может реализовывать либо G.729, либо G.729A, если это не ограничено дополнительной сигнализацией, указанной в другом месте и относящейся именно к кодировке, а не к формату полезной нагрузки. Кодеки G.729 и Приложения A к G.729 были оптимизированы для представления речи с высоким качеством, причём Приложение A к G.729 обменивает некоторое качество речи на примерно 50% сокращение сложности [10]. A voice activity detector (VAD) and comfort noise generator (CNG) algorithm in Annex B of G.729 is RECOMMENDED for digital simultaneous voice and data applications and can be used in conjunction with G.729 or G.729 Annex A. Receivers MUST accept comfort noise frames if restriction of their use has not been signaled. Приёмники ДОЛЖНЫ принимать кадры комфортного шума, если ограничение их использования не сигнализировано. 4.5.7. G729D and G729E
4.5.7. G729D и G729E
Annexes D and E to ITU-T Recommendation G.729 provide additional data rates. Because the data rate is not signaled in the bitstream, the different data rates are given distinct RTP encoding names which are mapped to distinct payload type numbers. G729D indicates a 6.4 kbit/s coding mode (G.729 Annex D, for momentary reduction in channel capacity), while G729E indicates an 11.8 kbit/s mode (G.729 Annex E, for improved performance with a wide range of narrow-band input signals, e.g., music and background noise). Annex E has two operating modes, backward adaptive and forward adaptive, which are signaled by the first two bits in each frame (the most significant two bits of the first octet).
Приложения D и E к Рекомендации ITU-T G.729 обеспечивают дополнительные скорости передачи данных. Поскольку скорость передачи данных не сигнализируется в битовом потоке, разным скоростям даются различные имена кодировки RTP, отображаемые на различные номера типов полезной нагрузки. G729D указывает режим кодирования 6,4 кбит/с (Приложение D к G.729, для временного снижения ёмкости канала), тогда как G729E указывает режим 11,8 кбит/с (Приложение E к G.729, для улучшенной работы с широким диапазоном узкополосных входных сигналов, например музыки и фонового шума). Приложение E имеет два режима работы — с обратной и с упреждающей адаптацией, которые различаются по первым двум битам в каждом кадре (старшие два бита первого октета).
The voice activity detector (VAD) and comfort noise generator (CNG) algorithm specified in Annex B of G.729 may be used with Annex D and Annex E frames in addition to G.729 and G.729 Annex A frames. The algorithm details for the operation of Annexes D and E with the Annex B CNG are specified in G.729 Annexes F and G. Note that Annexes F and G do not introduce any new encodings. Receivers MUST accept comfort noise frames if restriction of their use has not been signaled. The MIME registrations for G729D and G729E in RFC 3555 [7] specify a parameter that MAY be used with MIME or SDP to restrict the use of comfort noise frames.
Алгоритм детектора голосовой активности (VAD) и генератора комфортного шума (CNG), указанный в Приложении B к G.729, может использоваться с кадрами Приложений D и E в дополнение к кадрам G.729 и Приложения A к G.729. Детали алгоритма работы Приложений D и E с CNG Приложения B указаны в Приложениях F и G к G.729. Обратите внимание, что Приложения F и G не вводят никаких новых кодировок. Приёмники ДОЛЖНЫ принимать кадры комфортного шума, если ограничение их использования не сигнализировано. Регистрации MIME для G729D и G729E в RFC 3555 [7] определяют параметр, который МОЖЕТ использоваться с MIME или SDP для ограничения использования кадров комфортного шума.
For G729D, an RTP packet may consist of zero or more G.729 Annex D frames, followed by zero or one G.729 Annex B frame. Similarly, for G729E, an RTP packet may consist of zero or more G.729 Annex E frames, followed by zero or one G.729 Annex B frame. The presence of a comfort noise frame can be deduced from the length of the RTP payload.
Для G729D пакет RTP может состоять из нуля или более кадров Приложения D к G.729, за которыми следуют ноль или один кадр Приложения B к G.729. Аналогично для G729E пакет RTP может состоять из нуля или более кадров Приложения E к G.729, за которыми следуют ноль или один кадр Приложения B к G.729. Наличие кадра комфортного шума может быть выведено из длины полезной нагрузки RTP.
A single RTP packet must contain frames of only one data rate, optionally followed by one comfort noise frame. The data rate may be changed from packet to packet by changing the payload type number. G.729 Annexes D, E and H describe what the encoding and decoding algorithms must do to accommodate a change in data rate.
Один пакет RTP должен содержать кадры только одной скорости передачи данных, за которыми необязательно следует один кадр комфортного шума. Скорость передачи данных может меняться от пакета к пакету путём изменения номера типа полезной нагрузки. Приложения D, E и H к G.729 описывают, что алгоритмы кодирования и декодирования должны делать для приспособления к изменению скорости передачи данных.

4.5.11. L16

4.5.14. PCMA and PCMU
4.5.14. PCMA и PCMU
PCMA and PCMU are specified in ITU-T Recommendation G.711. Audio data is encoded as eight bits per sample, after logarithmic scaling. PCMU denotes mu-law scaling, PCMA A-law scaling. A detailed description is given by Jayant and Noll [15]. Each G.711 octet SHALL be octet-aligned in an RTP packet. The sign bit of each G.711 octet SHALL correspond to the most significant bit of the octet in the RTP packet (i.e., assuming the G.711 samples are handled as octets on the host machine, the sign bit SHALL be the most significant bit of the octet as defined by the host machine format). The 56 kb/s and 48 kb/s modes of G.711 are not applicable to RTP, since PCMA and PCMU MUST always be transmitted as 8-bit samples.
PCMA и PCMU определены в Рекомендации ITU-T G.711. Аудиоданные кодируются как восемь бит на отсчёт после логарифмического масштабирования. PCMU обозначает масштабирование mu-law, PCMA — A-law. Подробное описание дано Jayant и Noll [15]. Каждый октет G.711 ДОЛЖЕН быть выровнен по октету в пакете RTP. Знаковый бит каждого октета G.711 ДОЛЖЕН соответствовать старшему значащему биту октета в пакете RTP (то есть если отсчёты G.711 обрабатываются как октеты на машине-хосте, знаковый бит ДОЛЖЕН быть старшим значащим битом октета, как определено форматом машины-хоста). Режимы 56 кбит/с и 48 кбит/с G.711 не применимы к RTP, поскольку PCMA и PCMU ДОЛЖНЫ всегда передаваться как 8-битные отсчёты.

4.5.15. QCELP
4.5.15. QCELP
The Electronic Industries Association (EIA) & Telecommunications Industry Association (TIA) standard IS-733, "TR45: High Rate Speech Service Option for Wideband Spread Spectrum Communications Systems", defines the QCELP audio compression algorithm for use in wireless CDMA applications. The QCELP CODEC compresses each 20 milliseconds of 8,000 Hz, 16-bit sampled input speech into one of four different size output frames: Rate 1 (266 bits), Rate 1/2 (124 bits), Rate 1/4 (54 bits) or Rate 1/8 (20 bits). For typical speech patterns, this results in an average output of 6.8 kb/s for normal mode and 4.7 kb/s for reduced rate mode. The packetization of the QCELP audio codec is described in [16].

Кодек QCELP сжимает каждые 20 миллисекунд входной речи, дискретизированной при 8000 Гц с 16 битами, в один из четырёх выходных кадров разного размера: Rate 1 (266 бит), Rate 1/2 (124 бита), Rate 1/4 (54 бита) или Rate 1/8 (20 бит).
4.5.16. RED
4.5.16. RED
The redundant audio payload format "RED" is specified by RFC 2198 [17]. It defines a means by which multiple redundant copies of an audio packet may be transmitted in a single RTP stream. Each packet in such a stream contains, in addition to the audio data for that packetization interval, a (more heavily compressed) copy of the data from a previous packetization interval. This allows an approximation of the data from lost packets to be recovered upon decoding of a subsequent packet, giving much improved sound quality when compared with silence substitution for lost packets.
Формат полезной нагрузки избыточного аудио «RED» указан в RFC 2198 [17]. Он определяет средство, которым несколько избыточных копий аудиопакета могут передаваться в одном потоке RTP. Каждый пакет в таком потоке содержит, в дополнение к аудиоданным для этого интервала пакетирования, (более сильно сжатую) копию данных из предыдущего интервала пакетирования. Это позволяет восстановить приближение данных из потерянных пакетов при декодировании последующего пакета, давая значительную устойчивость к потерям.

Хотя 90 кГц — РЕКОМЕНДУЕМАЯ частота для будущих видеокодировок, используемых в этом профиле, МОГУТ использоваться и другие частоты. Однако недостаточно использовать частоту видеокадров (обычно от 15 до 30 Гц), поскольку она не обеспечивает адекватного разрешения для типичных требований синхронизации при вычислении отметки времени RTP, соответствующей отметке времени NTP в пакете RTCP SR. Разрешение отметок времени ДОЛЖНО также быть достаточным для оценки джиттера, содержащейся в отчётах получателя.
For most of these video encodings, the RTP timestamp encodes the sampling instant of the video image contained in the RTP data packet. If a video image occupies more than one packet, the timestamp is the same on all of those packets. Packets from different video images are distinguished by their different timestamps.
Для большинства этих видеокодировок отметка времени RTP кодирует момент дискретизации видеоизображения, содержащегося в пакете данных RTP. Если видеоизображение занимает более одного пакета, отметка времени одинакова во всех этих пакетах. Пакеты разных видеоизображений различаются по их разным отметкам времени.
Most of these video encodings also specify that the marker bit of the RTP header SHOULD be set to one in the last packet of a video frame and otherwise set to zero. Thus, it is not necessary to wait for a following packet with a different timestamp to detect that a new frame should be displayed.
Большинство этих видеокодировок также указывают, что бит-маркер заголовка RTP СЛЕДУЕТ устанавливать в единицу в последнем пакете видеокадра и в ноль в остальных случаях. Таким образом, нет необходимости ждать следующего пакета с другой отметкой времени, чтобы обнаружить, что должен отображаться новый кадр.

Payload type 13 indicates the Comfort Noise (CN) payload format specified in RFC 3389 [9]. 8. Port Assignment
8. Назначение портов
As specified in the RTP protocol definition, RTP data SHOULD be carried on an even UDP port number and the corresponding RTCP packets SHOULD be carried on the next higher (odd) port number. Applications operating under this profile MAY use any such UDP port pair. For example, the port pair MAY be allocated randomly by a session management program. A single fixed port number pair cannot be required because multiple applications using this profile are likely to run on the same host, and there are some operating systems that do not allow multiple processes to use the same UDP port with different multicast addresses.
Как указано в определении протокола RTP, данные RTP СЛЕДУЕТ передавать на чётном номере порта UDP, а соответствующие пакеты RTCP СЛЕДУЕТ передавать на следующем (нечётном) номере порта. Приложения, работающие по этому профилю, МОГУТ использовать любую такую пару портов UDP. Например, пара портов МОЖЕТ выделяться случайно программой управления сессией. Единую фиксированную пару номеров портов нельзя требовать, поскольку несколько приложений, использующих этот профиль, вероятно, будут работать на одном хосте, а некоторые операционные системы не позволяют нескольким процессам использовать один и тот же порт UDP с разными многоадресными адресами.
However, port numbers 5004 and 5005 have been registered for use with this profile for those applications that choose to use them as the default pair. Applications that operate under multiple profiles MAY use this port pair as an indication to select this profile if they are not subject to the constraint of the previous paragraph. Applications need not have a default and MAY require that the port pair be explicitly specified. The particular port numbers were chosen to lie in the range above 5000 to accommodate port number allocation practice within some versions of the Unix operating system, where port numbers below 1024 can only be used by privileged processes and port numbers between 1024 and 5000 are automatically assigned by the operating system.
Однако номера портов 5004 и 5005 зарегистрированы для использования с этим профилем теми приложениями, которые выбирают их как пару по умолчанию. Приложения, работающие по нескольким профилям, МОГУТ использовать эту пару портов как указание выбрать этот профиль, если они не подпадают под ограничение предыдущего абзаца. Приложения не обязаны иметь значение по умолчанию и МОГУТ требовать явного указания пары портов. Конкретные номера портов были выбраны лежащими в диапазоне выше 5000, чтобы избежать диапазона 1024–5000, часто используемого иными службами и разрешаемого только привилегированными процессами, а также диапазона 0–1023, зарезервированного за известными портами.

10. Security Considerations
10. Вопросы безопасности
Implementations using the profile defined in this specification are subject to the security considerations discussed in the RTP specification [1]. This profile does not specify any different security services. The primary function of this profile is to list a set of data compression encodings for audio and video media.
Реализации, использующие профиль, определённый в настоящей спецификации, подпадают под соображения безопасности, обсуждаемые в спецификации RTP [1]. Этот профиль не определяет никаких иных служб безопасности. Основная функция этого профиля — перечислить набор кодировок сжатия данных для аудио- и видеомедиа.
Confidentiality of the media streams is achieved by encryption. Because the data compression used with the payload formats described in this profile is applied end-to-end, encryption may be performed after compression so there is no conflict between the two operations.
Конфиденциальность медиапотоков достигается шифрованием. Поскольку сжатие данных, используемое с форматами полезной нагрузки, описанными в этом профиле, применяется сквозным образом, шифрование может выполняться после сжатия, так что между этими двумя операциями нет конфликта.
A potential denial-of-service threat exists for data encodings using compression techniques that have non-uniform receiver-end computational load. The attacker can inject pathological datagrams into the stream which are complex to decode and cause the receiver to be overloaded.
Существует потенциальная угроза отказа в обслуживании для кодировок данных, использующих методы сжатия с неравномерной вычислительной нагрузкой на принимающей стороне. Злоумышленник может внедрить в поток патологические дейтаграммы, которые сложны для декодирования и вызывают перегрузку приёмника.
As with any IP-based protocol, in some circumstances a receiver may be overloaded simply by the receipt of too many packets, either desired or undesired. Network-layer authentication MAY be used to discard packets from undesired sources, but the processing cost of the authentication itself may be too high. In a multicast environment, source pruning is implemented in IGMPv3 (RFC 3376) [24] and in multicast routing protocols to allow a receiver to select which sources are allowed to reach it.
Как и в любом протоколе на основе IP, при некоторых обстоятельствах приёмник может быть перегружен просто получением слишком большого числа пакетов, желательных или нежелательных. Для отбрасывания пакетов из нежелательных источников МОЖЕТ использоваться аутентификация сетевого уровня, но стоимость обработки самой аутентификации может быть слишком высокой. В многоадресной среде отсечение источников реализовано в IGMPv3 (RFC 3376) [24] и в протоколах многоадресной маршрутизации, чтобы позволить приёмнику отказаться чтобы позволить приёмнику выбирать, какие источники могут до него доходить.
