Abstract
Аннотация
This memo specifies the Common Profile for Presence (CPP) Presence Information Data Format (PIDF) as a common presence data format for CPP-compliant Presence protocols, and also defines a new media type "application/pidf+xml" to represent the XML MIME entity for PIDF.
В данном меморандуме определяется формат информации о присутствии (PIDF) общего профиля присутствия (CPP) как общий формат данных о присутствии для протоколов присутствия, совместимых с CPP, а также определяется новый тип носителя «application/pidf+xml» для представления сущности XML MIME для PIDF.

1. Introduction
1. Введение
The Common Profiles for Instant Messaging (CPIM) [CPIM] and Presence (CPP) [CPP] specifications define a set of operations and parameters to achieve interoperability between different Instant Messaging and Presence protocols which meet RFC 2779 [RFC2779].
Спецификации общего профиля для обмена мгновенными сообщениями (CPIM) [CPIM] и присутствия (CPP) [CPP] определяют набор операций и параметров для обеспечения совместимости между различными протоколами обмена мгновенными сообщениями и присутствия, которые соответствуют RFC 2779 [RFC2779].
This memo further defines the Presence Information Data Format (PIDF) as a common presence data format for CPP-compliant presence protocols, allowing presence information to be transferred across CPP-compliant protocol boundaries without modification, with attendant benefits for security and performance. The format specified in this memo defines the base presence format and extensibility required by RFC 2779. It defines a minimal set of presence status values defined by the IMPP Model document [RFC2778]. However, a presence application is able to define its own status values using the extensibility framework provided by this memo. Defining such extended status values is beyond the scope of this memo.
В настоящем меморандуме дополнительно определяется формат информации о присутствии (PIDF) как общий формат данных о присутствии для протоколов присутствия, совместимых с CPP, что позволяет передавать информацию о присутствии через границы протоколов, совместимых с CPP, без изменения, с сопутствующими преимуществами для безопасности и производительности. Формат, заданный в настоящем меморандуме, определяет базовый формат присутствия и расширяемость, требуемые RFC 2779. Он определяет минимальный набор значений статуса присутствия, определённых в документе модели IMPP [RFC2778]. Однако приложение присутствия может определять собственные значения статуса с помощью механизма расширяемости, предоставляемого настоящим меморандумом. Определение таких расширенных значений статуса выходит за рамки настоящего меморандума.
Note also that this memo defines only the format for a presence data payload and the extensibility framework for it. How the presence data is transferred within a specific protocol frame would be defined separately in a protocol specification.
Отметим также, что настоящий меморандум определяет только формат полезной нагрузки данных о присутствии и механизм её расширяемости. Способ передачи данных о присутствии в рамках конкретного протокольного кадра должен определяться отдельно в спецификации протокола.

2. Design Decisions
2. Проектные решения
We have adopted the IMPP Model and Requirements documents [RFC2778, RFC2779] as the starting point of our discussion. The two RFCs contain a number of statements about presence information, which can be regarded as a basic set of constraints for the format design. Also, we took the minimalist approach to the design based on them. Starting from the minimal model, only the features that are necessary to solve particular problems have been included.
Мы приняли документы модели и требований IMPP [RFC2778, RFC2779] за отправную точку обсуждения. Эти два RFC содержат ряд утверждений о информации о присутствии, которые можно рассматривать как базовый набор ограничений для проектирования формата. Кроме того, мы придерживались минималистичного подхода к проектированию на их основе. Исходя из минимальной модели, в неё были включены только те возможности, которые необходимы для решения конкретных задач.
2.1. Minimal Model
2.1. Минимальная модель
This specification is based on the minimal model extracted from the IMPP Model and Requirements documents. The model consists of the following items. Each of them is accompanied with the corresponding RFCs and their section numbers as its grounds, e.g., (RFC2778:Sec.2.4) refers to Section 2.4 of RFC 2778.
Настоящая спецификация основана на минимальной модели, извлечённой из документов модели и требований IMPP. Модель состоит из следующих пунктов. Каждый из них сопровождается соответствующими RFC и номерами их разделов в качестве обоснования, например, запись (RFC2778:Sec.2.4) относится к разделу 2.4 RFC 2778.
(a) PRESENCE INFORMATION consists of one or more PRESENCE TUPLES, where a PRESENCE TUPLE consists of a STATUS, an optional COMMUNICATION ADDRESS, and optional OTHER PRESENCE MARKUP. Note that the CONTACT ADDRESS in a COMMUNICATIONS ADDRESS is understood in this document to refer only to a URI (RFC2778:Sec.3).
(a) Информация о присутствии состоит из одного или нескольких кортежей присутствия, где кортеж присутствия состоит из статуса, необязательного адреса связи и необязательной прочей разметки присутствия. Отметим, что контактный адрес в адресе связи понимается в настоящем документе как относящийся только к URI (RFC2778:Sec.3).
(b) STATUS has at least the mutually-exclusive values OPEN and CLOSED, which have meaning for the acceptance of INSTANT MESSAGES, and may have meaning for other COMMUNICATION MEANS. There may be other values of STATUS that do not imply anything about INSTANT MESSAGE acceptance. These other values of STATUS may be combined with OPEN and CLOSED or they may be mutually- exclusive with those values (RFC2778:Sec.3, RFC2779:Sec.4.4.1- 4.4.3).
(b) Статус имеет как минимум взаимно исключающие значения OPEN и CLOSED, которые имеют смысл для приёма мгновенных сообщений и могут иметь смысл для других средств связи. Могут существовать другие значения статуса, не подразумевающие ничего относительно приёма мгновенных сообщений. Эти другие значения статуса могут комбинироваться с OPEN и CLOSED или быть взаимно исключающими с этими значениями (RFC2778:Sec.3, RFC2779:Sec.4.4.1-4.4.3).
(c) STATUS may consist of single or multiple values.(RFC2778:Sec.2.4)
(c) Статус может состоять из одного или нескольких значений. (RFC2778:Sec.2.4)
(d) There must be a means of extending the common presence format to represent additional information not included in the common format. The extension and registration mechanisms must be defined for presence information schema, including new STATUS conditions and new forms for OTHER PRESENCE MARKUP (RFC2779:Sec.3.1.4-3.1.5).
(d) Должно существовать средство расширения общего формата присутствия для представления дополнительной информации, не включённой в общий формат. Механизмы расширения и регистрации должны быть определены для схемы информации о присутствии, включая новые условия статуса и новые формы прочей разметки присутствия (RFC2779:Sec.3.1.4-3.1.5).
(e) The common presence format must include a means to uniquely identify the PRESENTITY whose PRESENCE INFORMATION is reported (RFC2779:Sec.3.1.2).
(e) Общий формат присутствия должен включать средство однозначной идентификации презентити, чья информация о присутствии передаётся (RFC2779:Sec.3.1.2).
(f) The common presence format must allow the PRESENTITY to secure presence information sent to a WATCHER. The format must allow integrity, confidentiality and authentication properties to be applied to presence information (RFC2779:Sec5.2.1, 5.2.4, 5.3.1, 5.3.3).
(f) Общий формат присутствия должен позволять презентити защищать информацию о присутствии, отправляемую наблюдателю. Формат должен позволять применять к информации о присутствии свойства целостности, конфиденциальности и аутентификации (RFC2779:Sec5.2.1, 5.2.4, 5.3.1, 5.3.3).
2.2. Added Features
2.2. Добавленные возможности
In addition to the minimal model described above, the format specified in this specification has the following features.
В дополнение к минимальной модели, описанной выше, формат, заданный в настоящей спецификации, обладает следующими возможностями.
(a) Relative priorities of contact addresses are specifiable in order to allow the source of PRESENCE INFORMATION to tell the receiver (WATCHER USER AGENTS) its preference over multiple contact means.
(a) Относительные приоритеты контактных адресов могут быть заданы, чтобы источник информации о присутствии мог сообщить получателю (пользовательским агентам наблюдателя) свои предпочтения относительно нескольких средств связи.
(b) The presence format is able to contain the timestamp of the creation of the PRESENCE INFORMATION. The timestamp in the presence document lets the receiver know the time of the creation of the data even if the message containing it is delayed. It can also be used to detect a replay attack, independent of the underlying signature mechanism. Note that this mechanism does not assume any global time synchronization system for watchers and presentities (see Appendix A of RFC2779, 8.1.4 A7), but rather assumes that the minimum length of time that might pass before presence information is considered stale is long enough that minor variations among system clocks will not lead to misjudgments of the freshness of presence information.
(b) Формат присутствия способен содержать отметку времени создания информации о присутствии. Отметка времени в документе присутствия позволяет получателю узнать время создания данных, даже если сообщение, содержащее их, задержано. Она также может использоваться для обнаружения атаки повторного воспроизведения независимо от лежащего в основе механизма подписи. Отметим, что этот механизм не предполагает какой-либо глобальной системы синхронизации времени для наблюдателей и презентити (см. Приложение A RFC2779, 8.1.4 A7), а скорее предполагает, что минимальная продолжительность времени, которая может пройти до того, как информация о присутствии будет считаться устаревшей, достаточно велика, чтобы незначительные расхождения системных часов не приводили к ошибочным суждениям о свежести информации о присутствии.
2.3. XML Encoding Decision
2.3. Решение о кодировании XML
The Presence Information Data Format encodes presence information in XML (eXtensible Markup Language [XML]). Regarding the features of PRESENCE INFORMATION discussed above, such that it has a hierarchical structure and it should be fully extensible, XML is considered as the most desirable framework over other candidates such as vCard [vCard].
Формат информации о присутствии кодирует информацию о присутствии в XML (eXtensible Markup Language [XML]). Учитывая рассмотренные выше особенности информации о присутствии, такие как иерархическая структура и необходимость полной расширяемости, XML считается наиболее предпочтительной основой по сравнению с другими кандидатами, такими как vCard [vCard].

4.1.1. The <presence> element
4.1.1. Элемент <presence>
PIDF elements are associated with the XML namespace name 'urn:ietf:params:xml:ns:pidf', declared using an xmlns attribute, per [XML-NS]. The namespace may be a default namespace, or may be associated with some namespace prefix (see section 4.2.2 for examples).
Элементы PIDF связаны с именем пространства имён XML «urn:ietf:params:xml:ns:pidf», объявляемым с помощью атрибута xmlns, согласно [XML-NS]. Пространство имён может быть пространством имён по умолчанию или может быть связано с некоторым префиксом пространства имён (примеры см. в разделе 4.2.2).
The root of an "application/pidf+xml" object is a <presence> element associated with the presence information namespace. This contains any number (including 0) of <tuple> elements, followed by any number (including 0) of <note> elements, followed by any number of OPTIONAL extension elements from other namespaces.
Корнем объекта «application/pidf+xml» является элемент <presence>, связанный с пространством имён информации о присутствии. Он содержит любое число (включая 0) элементов <tuple>, за которыми следует любое число (включая 0) элементов <note>, за которыми следует любое число НЕОБЯЗАТЕЛЬНЫХ элементов расширения из других пространств имён.
The <presence> element MUST have an 'entity' attribute. The value of the 'entity' attribute is the 'pres' URL of the PRESENTITY publishing this presence document.
Элемент <presence> ДОЛЖЕН иметь атрибут 'entity'. Значением атрибута 'entity' является URL «pres» презентити, публикующего этот документ присутствия.
The <presence> element MUST contain a namespace declaration ('xmlns') to indicate the namespace on which the presence document is based. The presence document compliant to this specification MUST have the namespace 'urn:ietf:params:xml:ns:pidf:'. It MAY contain other namespace declarations for the extensions used in the presence XML document.
Элемент <presence> ДОЛЖЕН содержать объявление пространства имён ('xmlns'), указывающее пространство имён, на котором основан документ присутствия. Документ присутствия, соответствующий настоящей спецификации, ДОЛЖЕН иметь пространство имён 'urn:ietf:params:xml:ns:pidf:'. Он МОЖЕТ содержать другие объявления пространств имён для расширений, используемых в XML-документе присутствия.
4.1.2. The <tuple> element
4.1.2. Элемент <tuple>
The <tuple> element carries a PRESENCE TUPLE, consisting of a mandatory <status> element, followed by any number of OPTIONAL extension elements (possibly from other namespaces), followed by an OPTIONAL <contact> element, followed by any number of OPTIONAL <note> elements, followed by an OPTIONAL <timestamp> element.
Элемент <tuple> несёт кортеж присутствия, состоящий из обязательного элемента <status>, за которым следует любое число НЕОБЯЗАТЕЛЬНЫХ элементов расширения (возможно, из других пространств имён), затем НЕОБЯЗАТЕЛЬНЫЙ элемент <contact>, затем любое число НЕОБЯЗАТЕЛЬНЫХ элементов <note> и, наконец, НЕОБЯЗАТЕЛЬНЫЙ элемент <timestamp>.
Tuples provide a way of segmenting presence information. Protocols or applications may choose to segment the presence information associated with a presentity for any number of reasons - for example, because components of the full presence information for a presentity have come from distinct devices or different applications on the same device, or have been generated at different times. Tuples should be preferred over other manners of segmenting presence information such as creating multiple PIDF instances.
Кортежи обеспечивают способ сегментирования информации о присутствии. Протоколы или приложения могут выбирать сегментирование информации о присутствии, связанной с презентити, по любому числу причин — например, потому что компоненты полной информации о присутствии для презентити поступили от различных устройств или разных приложений на одном устройстве либо были сформированы в разное время. Кортежам следует отдавать предпочтение перед другими способами сегментирования информации о присутствии, такими как создание нескольких экземпляров PIDF.
The <tuple> element MUST contain an 'id' attribute which is used to distinguish this tuple from other tuples in the same PRESENTITY. The value of an 'id' attribute MUST be unique within 'id' attribute values of other tuples for the same PRESENTITY. An 'id' value is used by applications processing the presence document to identify the corresponding tuple in the previously acquired PRESENCE INFORMATION of the same PRESENTITY. The value of the 'id' attribute is an arbitrary string, and has no significance beyond providing a means to distinguish <tuple> values, as noted above.
Элемент <tuple> ДОЛЖЕН содержать атрибут 'id', используемый для отличия этого кортежа от других кортежей того же презентити. Значение атрибута 'id' ДОЛЖНО быть уникальным среди значений атрибута 'id' других кортежей для того же презентити. Значение 'id' используется приложениями, обрабатывающими документ присутствия, для идентификации соответствующего кортежа в ранее полученной информации о присутствии того же презентити. Значение атрибута 'id' представляет собой произвольную строку и не имеет значения сверх обеспечения средства различения значений <tuple>, как отмечено выше.
The <contact> element is OPTIONAL because a PRESENTITY might need to hide its COMMUNICATION ADDRESS or there might be tuples not related to any COMMUNICATION MEANS. Tuples that contain a <basic> status element SHOULD contain a <contact> address. Tuples MAY contain conflicting presence status - one <tuple> might provide a <basic> <status> of OPEN, and another <tuple> in the same PIDF could contain a <basic> <status> of CLOSED, even if they both contain the same <contact> address.
Элемент <contact> является НЕОБЯЗАТЕЛЬНЫМ, поскольку презентити может нуждаться в сокрытии своего адреса связи или могут существовать кортежи, не связанные с какими-либо средствами связи. Кортежи, содержащие элемент статуса <basic>, ДОЛЖНЫ содержать адрес <contact>. Кортежи МОГУТ содержать противоречивый статус присутствия — один <tuple> может содержать <basic> <status> со значением OPEN, а другой <tuple> в том же PIDF может содержать <basic> <status> со значением CLOSED, даже если оба содержат один и тот же адрес <contact>.
The manner in which segmented presence information is understood by the WATCHER USER AGENT is highly dependent on the capabilities of the WATCHER USER AGENT and the presence application in question. In the absence of any application-specific or protocol-specific understanding of the meaning of tuples, WATCHER USER AGENTS MAY obey the following guidelines. WATCHER USER AGENTS should note which tuples in the PIDF have changed their state since the last notification by correlating the 'id' of each <tuple> with those received in previous notifications and comparing both <status> values and <timestamp> elements in the tuples, if any are present.
То, как сегментированная информация о присутствии понимается пользовательским агентом наблюдателя, в значительной степени зависит от возможностей пользовательского агента наблюдателя и рассматриваемого приложения присутствия. При отсутствии какого-либо понимания значения кортежей, специфичного для приложения или протокола, пользовательские агенты наблюдателя МОГУТ следовать приведённым ниже рекомендациям. Пользовательские агенты наблюдателя должны отмечать, какие кортежи в PIDF изменили своё состояние с момента последнего уведомления, сопоставляя 'id' каждого <tuple> с 'id', полученными в предыдущих уведомлениях, и сравнивая значения <status> и элементы <timestamp> в кортежах, если они присутствуют.
4.1.3. The <status> element
4.1.3. Элемент <status>
The <status> element contains one OPTIONAL <basic> element, followed by any number of OPTIONAL extension elements (possibly from other namespaces), under the restriction that at least one child element appears in the <status> element. These children elements of <status> contain status values of this tuple. By allowing multiple status values in a single <tuple> element, different types of status values, e.g., reachability and location, can be represented by a <tuple>. See Section 4.3 for an example with multiple status values.
Элемент <status> содержит один НЕОБЯЗАТЕЛЬНЫЙ элемент <basic>, за которым следует любое число НЕОБЯЗАТЕЛЬНЫХ элементов расширения (возможно, из других пространств имён), при условии, что в элементе <status> присутствует хотя бы один дочерний элемент. Эти дочерние элементы <status> содержат значения статуса этого кортежа. Благодаря возможности нескольких значений статуса в одном элементе <tuple> различные типы значений статуса, например, достижимость и местоположение, могут быть представлены одним <tuple>. Пример с несколькими значениями статуса см. в разделе 4.3.
This memo only defines the <basic> status value element. Other status values may be included using the standard extensibility framework (see Section 4.2.4). Applications encountering unrecognized elements within <status> may ignore them, unless they carry a mustUnderstand="true" or mustUnderstand="1" attribute (see section 4.2.3).
Настоящий меморандум определяет только элемент значения статуса <basic>. Другие значения статуса могут быть включены с использованием стандартного механизма расширяемости (см. раздел 4.2.4). Приложения, встречающие нераспознанные элементы внутри <status>, могут игнорировать их, если они не несут атрибут mustUnderstand="true" или mustUnderstand="1" (см. раздел 4.2.3).
Note that, while the <status> element MUST have at least one status value element, this status value might not be the <basic> element.
Отметим, что, хотя элемент <status> ДОЛЖЕН иметь хотя бы один элемент значения статуса, это значение статуса может не быть элементом <basic>.
4.1.4. The <basic> element
4.1.4. Элемент <basic>
The <basic> element contains one of the following strings: "open" or "closed".
Элемент <basic> содержит одну из следующих строк: «open» или «closed».
The values "open" and "closed" indicate availability to receive INSTANT MESSAGES if the <tuple> is for an instant messaging address. They also indicate general availability for other communication means, but this memo does not specify these in detail.
Значения «open» и «closed» указывают на доступность для приёма мгновенных сообщений, если <tuple> относится к адресу обмена мгновенными сообщениями. Они также указывают на общую доступность для других средств связи, но настоящий меморандум не описывает их подробно.
open: In the context of INSTANT MESSAGES, this value means that the associated <contact> element, if any, corresponds to an INSTANT INBOX that is ready to accept an INSTANT MESSAGE.
open: в контексте мгновенных сообщений это значение означает, что связанный элемент <contact>, если он есть, соответствует почтовому ящику мгновенных сообщений, готовому принять мгновенное сообщение.
closed: In the context of INSTANT MESSAGES, this value means that the associated <contact> element, if any, corresponds to an INSTANT INBOX that is unable to accept an INSTANT MESSAGE.
closed: в контексте мгновенных сообщений это значение означает, что связанный элемент <contact>, если он есть, соответствует почтовому ящику мгновенных сообщений, не способному принять мгновенное сообщение.
4.1.5. The <contact> element
4.1.5. Элемент <contact>
The <contact> element contains a URL of the contact address. It optionally has a 'priority' attribute, whose value means a relative priority of this contact address over the others. The value of the attribute MUST be a decimal number between 0 and 1 inclusive with at most 3 digits after the decimal point. Higher values indicate higher priority. Examples of priority values are 0, 0.021, 0.5, 1.00. If the 'priority' attribute is omitted, applications MUST assign the contact address the lowest priority. If the 'priority' value is out of the range, applications just SHOULD ignore the value and process it as if the attribute was not present.
Элемент <contact> содержит URL контактного адреса. Он необязательно имеет атрибут 'priority', значение которого означает относительный приоритет этого контактного адреса по сравнению с другими. Значение атрибута ДОЛЖНО быть десятичным числом от 0 до 1 включительно не более чем с 3 цифрами после десятичной точки. Более высокие значения указывают на более высокий приоритет. Примеры значений приоритета: 0, 0.021, 0.5, 1.00. Если атрибут 'priority' опущен, приложения ДОЛЖНЫ назначить контактному адресу самый низкий приоритет. Если значение 'priority' выходит за пределы диапазона, приложениям СЛЕДУЕТ игнорировать значение и обрабатывать его так, как если бы атрибут отсутствовал.
Applications SHOULD handle contacts with a higher priority as they have precedence over those with lower priorities. How they are actually treated is beyond this specification. Also, how to handle contacts with the same priority is up to implementations.
Приложениям СЛЕДУЕТ обрабатывать контакты с более высоким приоритетом как имеющие преимущество перед контактами с более низкими приоритетами. То, как они фактически обрабатываются, выходит за рамки настоящей спецификации. Кроме того, способ обработки контактов с одинаковым приоритетом зависит от реализации.
4.1.6. The <note> element
4.1.6. Элемент <note>
The <note> element contains a string value, which is usually used for a human readable comment. A <note> element MAY appear as a child element of <presence> or as a child element of the <tuple> element. In the former case the comment is about the PRESENTITY and in the latter case the comment is regarding the particular tuple.
Элемент <note> содержит строковое значение, обычно используемое для комментария, читаемого человеком. Элемент <note> МОЖЕТ появляться как дочерний элемент <presence> или как дочерний элемент <tuple>. В первом случае комментарий относится к презентити, а во втором — к конкретному кортежу.
Note that, wherever it appears, a <note> element SHOULD NOT be used, and interpreted, as a non-interoperable substitute for status of its parent element.
Отметим, что, где бы он ни появлялся, элемент <note> НЕ СЛЕДУЕТ использовать и интерпретировать как несовместимую замену статуса его родительского элемента.
The <note> element SHOULD have a special attribute 'xml:lang' to specify the language used in the contents of this element as defined in Section 2.12 of [XML]. The value of this attribute is the language identifier as defined by [RFC3066]. It MAY be omitted when the language used is implied by the larger context such as the encoding information of the contents, such as an xml:lang attribute on an enclosing XML element, or a Content-language header [RFC3282] on an enclosing MIME wrapper.
Элемент <note> СЛЕДУЕТ снабжать специальным атрибутом 'xml:lang', задающим язык, используемый в содержимом этого элемента, как определено в разделе 2.12 [XML]. Значением этого атрибута является идентификатор языка, определённый в [RFC3066]. Его МОЖНО опускать, когда используемый язык подразумевается более широким контекстом, например информацией о кодировке содержимого, атрибутом xml:lang внешнего элемента XML или заголовком Content-language [RFC3282] внешней обёртки MIME.
4.1.7. The <timestamp> element
4.1.7. Элемент <timestamp>
The <timestamp> element contains a string indicating the date and time of the status change of this tuple. The value of this element MUST follow the IMPP datetime format [RFC3339]. Timestamps that contain 'T' or 'Z' MUST use the capitalized forms.
Элемент <timestamp> содержит строку, указывающую дату и время изменения статуса этого кортежа. Значение этого элемента ДОЛЖНО соответствовать формату даты и времени IMPP [RFC3339]. Отметки времени, содержащие 'T' или 'Z', ДОЛЖНЫ использовать заглавные формы.
As a security measure, the <timestamp> element SHOULD be included in all tuples unless the exact time of the status change cannot be determined. For security guidelines for watchers receiving presence information with timestamps, see the Security Considerations.
В качестве меры безопасности элемент <timestamp> СЛЕДУЕТ включать во все кортежи, если только точное время изменения статуса не может быть определено. Рекомендации по безопасности для наблюдателей, получающих информацию о присутствии с отметками времени, см. в разделе «Вопросы безопасности».
A PRESENTITY MUST NOT generate successive <presence> elements containing the same timestamp.
Презентити НЕ ДОЛЖЕН формировать последовательные элементы <presence>, содержащие одну и ту же отметку времени.
4.2. Presence Information Extensibility
4.2. Расширяемость информации о присутствии
The presence information extensibility framework is based on XML namespaces [XML-NS].
Механизм расширяемости информации о присутствии основан на пространствах имён XML [XML-NS].
RFC 2779 requires that PIDF have a means of extending <status> values beyond <basic>. These extensions MUST NOT modify how <basic> is to be understood, nor change the structure or semantics of PIDF bodies themselves. These extensions merely allow protocols and applications to define richer presence data.
RFC 2779 требует, чтобы PIDF имел средство расширения значений <status> за пределы <basic>. Эти расширения НЕ ДОЛЖНЫ изменять понимание <basic>, а также структуру или семантику самих тел PIDF. Эти расширения лишь позволяют протоколам и приложениям определять более богатые данные присутствия.
4.2.1. XML Namespaces Background
4.2.1. Предпосылки о пространствах имён XML
All elements and some attributes are associated with a "namespace", which is in turn associated with a globally unique URI. Any developer can introduce their own element names, avoiding conflict by choosing an appropriate namespace URI.
Все элементы и некоторые атрибуты связаны с «пространством имён», которое, в свою очередь, связано с глобально уникальным URI. Любой разработчик может вводить собственные имена элементов, избегая конфликтов путём выбора подходящего URI пространства имён.
Within the presence data, element or attribute names are associated with a particular namespace by a namespace prefix, which is a leading part of the name, followed by a colon (":"); e.g.,
В данных о присутствии имена элементов или атрибутов связываются с определённым пространством имён посредством префикса пространства имён, который является начальной частью имени, за которой следует двоеточие («:»); например,
<prefix:element-name ...> ... </prefix:element-name>
<prefix:element-name ...> ... </prefix:element-name>
Where, 'prefix' is the header name prefix, 'element-name' is a name which is scoped by the namespace associated with 'prefix'. Note that the choice of 'prefix' is quite arbitrary; it is the corresponding URI that defines the naming scope. Two different prefixes associated with the same namespace URI refer to the same namespace.
Здесь 'prefix' — префикс имени заголовка, 'element-name' — имя, область действия которого определяется пространством имён, связанным с 'prefix'. Отметим, что выбор 'prefix' совершенно произволен; именно соответствующий URI определяет область имён. Два разных префикса, связанных с одним и тем же URI пространства имён, относятся к одному и тому же пространству имён.
A default namespace can be declared for XML elements without a namespace prefix. The default namespace does NOT apply to attribute names, but interpretation of an unprefixed attribute can be determined by the containing element.
Для элементов XML без префикса пространства имён может быть объявлено пространство имён по умолчанию. Пространство имён по умолчанию НЕ применяется к именам атрибутов, но интерпретация атрибута без префикса может определяться содержащим его элементом.
A namespace is identified by a URI. In this usage, the URI is used simply as a globally unique identifier, and there is no requirement that it can be used to retrieve a web resource, or for any other purpose. Any legal globally unique URI MAY be used to identify a namespace. (By "globally unique", we mean constructed according to some set of rules so that it is reasonable to expect that nobody else will use the same URI for a different purpose.)
Пространство имён идентифицируется URI. В этом применении URI используется просто как глобально уникальный идентификатор, и не требуется, чтобы его можно было использовать для получения веб-ресурса или для каких-либо иных целей. Для идентификации пространства имён МОЖЕТ использоваться любой допустимый глобально уникальный URI. (Под «глобально уникальным» мы понимаем построенный по некоторому набору правил так, что разумно ожидать, что никто другой не будет использовать тот же URI для иной цели.)
For further details, see the XML namespace specification [XML-NS].
Дополнительные сведения см. в спецификации пространств имён XML [XML-NS].
4.2.2. XML Namespaces In Presence Information
4.2.2. Пространства имён XML в информации о присутствии
A URI used as a namespace identifier in PRESENCE INFORMATION data MUST be a full absolute-URI, per RFC 2396 [URI]. (Relative URIs and URI-references containing fragment identifiers MUST NOT be used for this purpose.)
URI, используемый в качестве идентификатора пространства имён в данных информации о присутствии, ДОЛЖЕН быть полным absolute-URI согласно RFC 2396 [URI]. (Относительные URI и ссылки URI, содержащие идентификаторы фрагментов, НЕ ДОЛЖНЫ использоваться для этой цели.)
The namespace URI for elements defined by this specification is a URN [URN], using the namespace identifier 'ietf' defined by [URN-NS-IETF] and extended by [XML-Registry]:
URI пространства имён для элементов, определённых настоящей спецификацией, представляет собой URN [URN], использующий идентификатор пространства имён 'ietf', определённый в [URN-NS-IETF] и расширенный в [XML-Registry]:
urn:ietf:params:xml:ns:pidf
urn:ietf:params:xml:ns:pidf
Thus, simple presence data might be thus:
Таким образом, простые данные о присутствии могут выглядеть так:

<?xml version="1.0" encoding="UTF-8"?> <impp:presence xmlns:impp="urn:ietf:params:xml:ns:pidf"
entity="pres:someone@example.com">
entity="pres:someone@example.com">
<impp:tuple id="sg89ae">
<impp:tuple id="sg89ae">
<impp:status> <impp:basic>open</impp:basic> </impp:status> <impp:contact priority="0.8">tel:+09012345678</impp:contact>
<impp:status> <impp:basic>open</impp:basic> </impp:status> <impp:contact priority="0.8">tel:+09012345678</impp:contact>

</impp:tuple> </impp:presence>
, using a default XML namespace:
, с использованием пространства имён XML по умолчанию:

entity="pres:someone@example.com">

</tuple> </presence>

As is generally the case in XML with namespaces, the xmlns attribute can be used on any element in the presence information to define either the default namespace or a namespace associated with a namespace prefix.
Как обычно бывает в XML с пространствами имён, атрибут xmlns может использоваться на любом элементе в информации о присутствии для определения либо пространства имён по умолчанию, либо пространства имён, связанного с префиксом пространства имён.
4.2.3. Handling Of Unrecognized Element Names
4.2.3. Обработка нераспознанных имён элементов
Except as noted below, a processor of PRESENCE INFORMATION MUST ignore any XML element with an unrecognized name (i.e., having an unrecognized namespace URI, or an unrecognized local name within that namespace). This includes all of the element content, even if it appears to contain elements with recognized names.
За исключением отмеченных ниже случаев, обработчик информации о присутствии ДОЛЖЕН игнорировать любой элемент XML с нераспознанным именем (то есть имеющий нераспознанный URI пространства имён или нераспознанное локальное имя в этом пространстве имён). Это включает всё содержимое элемента, даже если оно, по-видимому, содержит элементы с распознанными именами.
Extensions to PIDF are informational in nature - they provide additional information beyond <basic> status. However, in order to understand a complex extension, nested elements within an extension element might need to be marked as mandatory. In such cases, the element name is qualified with a mustUnderstand='true' or mustUnderstand='1' attribute. See section 4.3.3 for an example.
Расширения PIDF носят информационный характер — они предоставляют дополнительную информацию сверх статуса <basic>. Однако для понимания сложного расширения вложенные элементы внутри элемента расширения могут нуждаться в пометке как обязательные. В таких случаях имя элемента квалифицируется атрибутом mustUnderstand='true' или атрибутом mustUnderstand='1'. Пример см. в разделе 4.3.3.
NOTE: a mustUnderstand='true' or mustUnderstand='1' attribute within an element that is being ignored is itself ignored. The writer of nested mandatory-to-understand information is responsible for ensuring that any enclosing element is also labelled with a mustUnderstand='true' or mustUnderstand='1' attribute, if necessary.
ПРИМЕЧАНИЕ: атрибут mustUnderstand='true' или mustUnderstand='1' в пределах игнорируемого элемента сам игнорируется. Автор вложенной информации, обязательной к пониманию, отвечает за то, чтобы любой охватывающий его элемент также был надлежащим образом помечен атрибутом mustUnderstand='true' или mustUnderstand='1', если это необходимо.
This specification defines (section 4.1) elements within the 'urn:ietf:params:xml:ns:pidf' namespace that MUST be recognized in CPP presence data. Processors MUST handle these as described, even if they do not carry a mustUnderstand attribute. The XML Schema Definition (section 4.4) indicates those elements that MUST be present in a valid presence information document.
Настоящая спецификация определяет (раздел 4.1) элементы в пространстве имён 'urn:ietf:params:xml:ns:pidf', которые ДОЛЖНЫ распознаваться в данных присутствия CPP. Обработчики ДОЛЖНЫ обрабатывать их, как описано, даже если они не несут атрибут mustUnderstand. Определение схемы XML (раздел 4.4) указывает те элементы, которые ДОЛЖНЫ присутствовать в допустимом документе информации о присутствии.
If an agent receives PRESENCE INFORMATION with a <status> block containing an unrecognized element with a mustUnderstand='true' (or '1') attribute, it should treat that entire element and any content as unrecognized and not attempt to process it.
Если агент получает информацию о присутствии с блоком <status>, содержащим нераспознанный элемент с атрибутом mustUnderstand='true' (или '1'), он должен рассматривать весь этот элемент и любое его содержимое как нераспознанные и не пытаться их обработать.
In order to ensure that minimal implementations can correctly process basic PIDF information the mustUnderstand attribute MUST be used only within optional elements nested in a <status> element. This will ensure that problems processing an extension are restricted to that extension and do not affect the processing of the basic PIDF information defined in this specification.
Чтобы гарантировать, что минимальные реализации могут корректно обрабатывать базовую информацию PIDF, атрибут mustUnderstand ДОЛЖЕН использоваться только внутри необязательных элементов, вложенных в элемент <status>. Это гарантирует, что проблемы при обработке расширения ограничиваются этим расширением и не влияют на обработку базовой информации PIDF, определённой в настоящей спецификации.

4.2.5. Standardizing Status Extensions
4.2.5. Стандартизация расширений статуса
Although the existing PIDF definition allows arbitrary elements to appear in the <status> element, it may be sometimes desirable to standardize extension status elements and their semantics (the meanings of particular statuses, how they should be interpreted). The URN 'urn:ietf:params:xml:ns:pidf:status' has been specified as an umbrella namespace under which extensions to the <status> PIDF element should be specified (e.g., urn:ietf:params:xml:ns:pidf:status:my-extension). New values under this namespace MUST be defined by a standards-track RFC.
Хотя существующее определение PIDF допускает появление произвольных элементов в элементе <status>, иногда может быть желательно стандартизировать элементы статуса расширения и их семантику (значения конкретных статусов, способы их интерпретации). URN 'urn:ietf:params:xml:ns:pidf:status' был определён как зонтичное пространство имён, в рамках которого следует определять расширения элемента <status> PIDF (например, urn:ietf:params:xml:ns:pidf:status:my-extension). 6. Security Considerations
6. Вопросы безопасности
Because presence is very privacy-sensitive information, the protocol for the presence information MUST have capabilities to protect PIDF from possible threats, such as eavesdropping, corruption, tamper and replay attacks. These security mechanisms must be able to be used end-to-end between presentities and watchers, even if the watcher and the presentity employ different presence protocols and communicate through a CPP gateway. Since the 'application/pidf+xml' MIME type is defined for this PIDF document, staging security for PIDF at the MIME level (with S/MIME [RFC3851]) seems appropriate. Therefore, PIDF should follow the normative recommendations for the use of S/MIME (including minimum ciphersuites) given in the core CPP specification.
Поскольку присутствие является очень чувствительной к приватности информацией, протокол для информации о присутствии ДОЛЖЕН обладать возможностями защиты PIDF от возможных угроз, таких как прослушивание, искажение, несанкционированное изменение и атаки повторного воспроизведения. Эти механизмы безопасности должны иметь возможность использоваться сквозным образом между презентити и наблюдателями, даже если наблюдатель и презентити используют разные протоколы присутствия и взаимодействуют через шлюз CPP. Поскольку тип MIME «application/pidf+xml» определён для этого документа PIDF, организация безопасности PIDF на уровне MIME (с помощью S/MIME [RFC3851]) представляется уместной. Поэтому PIDF следует нормативным рекомендациям по использованию S/MIME (включая минимальные наборы шифров), приведённым в основной спецификации CPP.
Note that the use of timestamps in PIDF (see section 4.1.7) can provide some rudimentary protection against replay attacks. If a watcher receives presence information that is outdated, it SHOULD be ignored. A watcher can determine that presence information is outdated in a number of fashions. Most significantly, if the newest timestamp in presence information is older than the newest timestamp in the last received presence information, it should be considered outdated. Applications and protocols also are advised to adopt their own rules for determining how frequently presence information should be refreshed. For example, if presence information appears to be more than one hour old, it could be considered outdated (a notification generated for this presence information will not take such a long time to reach a watcher, and if a presentity has not refreshed its presence state in the last hour, it is probably offline).
Отметим, что использование отметок времени в PIDF (см. раздел 4.1.7) может обеспечить некоторую элементарную защиту от атак повторного воспроизведения. Если наблюдатель получает устаревшую информацию о присутствии, её СЛЕДУЕТ игнорировать. Наблюдатель может определить, что информация о присутствии устарела, несколькими способами. Наиболее существенно то, что если новейшая отметка времени в информации о присутствии старше новейшей отметки времени в последней полученной информации о присутствии, её следует считать устаревшей. Приложениям и протоколам также рекомендуется принять собственные правила определения того, как часто следует обновлять информацию о присутствии. Например, если информация о присутствии выглядит старше одного часа, её можно считать устаревшей (уведомление, сформированное для этой информации о присутствии, не будет идти до наблюдателя так долго, и если презентити не обновил своё состояние присутствия за последний час, он, вероятно, находится в автономном режиме).
