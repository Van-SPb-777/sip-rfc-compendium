Abstract
Аннотация
This document specifies the URI (Uniform Resource Identifier) scheme "tel". The "tel" URI describes resources identified by telephone numbers. This document obsoletes RFC 2806.
Настоящий документ определяет схему URI (Uniform Resource Identifier) «tel». URI «tel» описывает ресурсы, идентифицируемые телефонными номерами. Настоящий документ заменяет RFC 2806.
1. Introduction
1. Введение
This document defines the URI scheme "tel", which describes resources identified by telephone numbers. A telephone number is a string of decimal digits that uniquely indicates the network termination point. The number contains the information necessary to route the call to this point. (This definition is derived from [E.164] but encompasses both public and private numbers.)
Настоящий документ определяет схему URI «tel», которая описывает ресурсы, идентифицируемые телефонными номерами. Телефонный номер — это строка десятичных цифр, однозначно указывающая точку завершения сети. Номер содержит информацию, необходимую для маршрутизации вызова в эту точку. (Это определение выведено из [E.164], но охватывает как публичные, так и частные номера.)
The termination point of the "tel" URI telephone number is not restricted. It can be in the public telephone network, a private telephone network, or the Internet. It can be fixed or wireless and address a fixed wired, mobile, or nomadic terminal. The terminal addressed can support any electronic communication service (ECS), including voice, data, and fax. The URI can refer to resources identified by a telephone number, including but not limited to originators or targets of a telephone call.
Точка завершения телефонного номера URI «tel» не ограничена. Она может находиться в публичной телефонной сети, частной телефонной сети или в Интернете. Она может быть фиксированной или беспроводной и адресовать фиксированный проводной, мобильный или кочующий терминал. Адресуемый терминал может поддерживать любую службу электронной связи (ECS), включая голос, данные и факс. URI может ссылаться на ресурсы, идентифицируемые телефонным номером, включая, помимо прочего, инициаторов или получателей телефонного вызова.
The "tel" URI is a globally unique identifier ("name") only; it does not describe the steps necessary to reach a particular number and does not imply dialling semantics. Furthermore, it does not refer to a specific physical device, only to a telephone number.
URI «tel» является только глобально уникальным идентификатором («именем»); он не описывает шаги, необходимые для достижения конкретного номера, и не подразумевает семантику набора. Кроме того, он не ссылается на конкретное физическое устройство, а только на телефонный номер.
As commonly understood, telephone numbers comprise two related but distinct concepts: a canonical address-of-record and a dial string. We define the concepts below:
Как обычно понимают, телефонные номера охватывают два связанных, но различных понятия: канонический адрес записи и наборную строку. Ниже мы определяем эти понятия:
Address-of-record or identifier: The telephone number is understood here as the canonical address-of-record or identifier for a termination point within a specific network. For the public network, these numbers follow the rules in E.164 [E.164], while private numbers follow the rules of the owner of the private numbering plan. Subscribers publish these identifiers so that they can be reached, regardless of the location of the caller. (Naturally, not all numbers are reachable from everywhere, for a variety of technical and local policy reasons. Also, a single termination point may be reachable from different networks and may have multiple identifiers.)
Адрес записи или идентификатор: здесь телефонный номер понимается как канонический адрес записи или идентификатор точки завершения в конкретной сети. Для публичной сети эти номера подчиняются правилам E.164 [E.164], а частные номера — правилам владельца частного плана нумерации. Абоненты публикуют эти идентификаторы, чтобы с ними можно было связаться независимо от местоположения вызывающего. (Естественно, не все номера доступны отовсюду по множеству технических причин и причин местной политики. Кроме того, одна точка завершения может быть доступна из разных сетей и иметь несколько идентификаторов.)
Dial string: "Dial strings" are the actual numbers, symbols, and pauses entered by a user to place a phone call. A dial string is consumed by one or more network entities and understood in the context of the configuration of these entities. It is used to generate an address-of-record or identifier (in the sense described above) so that a call can be routed. Dial strings may require prepended digits to exit the private branch exchange (PBX) the end system is connected to, and they may include post-dial dual-tone multi-frequency (DTMF) signaling that could control an interactive voice response (IVR) system or reach an extension. Dial strings are beyond the scope of this document.
Наборная строка: «наборные строки» — это фактические номера, символы и паузы, вводимые пользователем для совершения телефонного вызова. Наборная строка потребляется одним или несколькими сетевыми объектами и понимается в контексте конфигурации этих объектов. Она используется для формирования адреса записи или идентификатора (в смысле, описанном выше), чтобы можно было маршрутизировать вызов. Наборные строки могут требовать добавления цифр в начало для выхода из УАТС (PBX), к которой подключена оконечная система, и могут включать постинборную сигнализацию DTMF, которая могла бы управлять системой интерактивного голосового ответа (IVR) или достигать добавочного номера. Наборные строки выходят за рамки настоящего документа.
Both approaches can be expressed as a URI. For dial strings, this URI is passed to an entity that can reproduce the actions specified in the dial string. For example, in an analog phone system, a dialer translates the dial string into a sequence of actions such as waiting for dial tone, sending DTMF digits, pausing, and generating post-dial DTMF digits after the callee picks up. In an integrated services digital network (ISDN) or ISDN user part (ISUP) environment, the signaling elements that receive protocol messages containing the dial string perform the appropriate protocol actions. As noted, this approach is beyond the scope of this specification.
Оба подхода могут быть выражены как URI. Для наборных строк этот URI передаётся объекту, способному воспроизвести действия, заданные в наборной строке. Например, в аналоговой телефонной системе наборщик преобразует наборную строку в последовательность действий, таких как ожидание сигнала ответа станции, отправка цифр DTMF, пауза и генерация постинборных цифр DTMF после того, как вызываемый абонент снимет трубку. В среде цифровой сети с интеграцией служб (ISDN) или подсистемы пользователя ISDN (ISUP) элементы сигнализации, принимающие сообщения протокола, содержащие наборную строку, выполняют соответствующие действия протокола. Как отмечено, этот подход выходит за рамки настоящей спецификации.
The approach described here has the URI specify the telephone number as an identifier, which can be either globally unique or only valid within a local context. The dialling application is aware of the local context, knowing, for example, whether special digits need to be dialed to seize an outside line; whether network, pulse, or tone dialling is needed; and what tones indicate call progress. The dialling application then converts the telephone number into a dial sequence and performs the necessary signaling actions. The dialer does not have to be a user application as found in traditional desktop operating systems but could well be part of an IP-to-PSTN gateway.
Описанный здесь подход состоит в том, что URI задаёт телефонный номер как идентификатор, который может быть либо глобально уникальным, либо действительным только в локальном контексте. Приложение набора знает локальный контекст, например, нужно ли набирать специальные цифры для захвата внешней линии; требуется ли набор по сети, импульсный или тональный; и какие тоны указывают на ход вызова. Затем приложение набора преобразует телефонный номер в последовательность набора и выполняет необходимые действия сигнализации. Наборщик не обязан быть пользовательским приложением, как в традиционных настольных операционных системах, а вполне может быть частью шлюза IP-to-PSTN.
To reach a telephone number from a phone on a PBX, for example, the user of that phone has to know how to convert the telephone number identifier into a dial string appropriate for that phone. The telephone number itself does not convey what needs to be done for a particular terminal. Instructions may include dialling "9" before placing a call or prepending "00" to reach a number in a foreign country. The phone may also need to strip area and country codes. The identifier approach described in this document has the disadvantage that certain services, such as electronic banking or voicemail, cannot be specified in a "tel" URI.
Чтобы дозвониться до телефонного номера с телефона, подключённого к УАТС, например, пользователю этого телефона необходимо знать, как преобразовать идентификатор телефонного номера в наборную строку, подходящую для этого телефона. Сам телефонный номер не сообщает, что нужно делать для конкретного терминала. Инструкции могут включать набор «9» перед совершением вызова или добавление «00» для вызова номера в другой стране. Телефону может также потребоваться отбросить код города и код страны. Подход через идентификатор, описанный в настоящем документе, имеет недостаток: некоторые службы, например электронный банкинг или голосовая почта, не могут быть заданы в URI «tel».
The notation for phone numbers in this document is similar to that in RFC 3191 [RFC3191] and RFC 3192 [RFC3192]. However, the syntax differs as this document describes URIs whereas RFC 3191 and RFC 3192 specify electronic mail addresses. RFC 3191 and RFC 3192 use "/" to indicate parameters (qualifiers). Since URIs use the forward slash to describe path hierarchy, the URI scheme described here uses the semicolon, in keeping with Session Initiation Protocol (SIP) URI conventions [RFC3261].
Нотация телефонных номеров в настоящем документе аналогична нотации в RFC 3191 [RFC3191] и RFC 3192 [RFC3192]. Однако синтаксис отличается, поскольку настоящий документ описывает URI, тогда как RFC 3191 и RFC 3192 задают адреса электронной почты. RFC 3191 и RFC 3192 используют «/» для указания параметров (квалификаторов). Поскольку в URI прямая косая черта используется для описания иерархии пути, описываемая здесь схема URI использует точку с запятой в соответствии с соглашениями URI протокола инициирования сессий (SIP) [RFC3261].
The "tel" URI can be used as a request URI in SIP [RFC3261] requests. The SIP specification also inherits the 'subscriber' part of the syntax as part of the 'user element' in the SIP URI. Other protocols may also use this URI scheme.
URI «tel» может использоваться как URI запроса в запросах SIP [RFC3261]. Спецификация SIP также наследует часть синтаксиса 'subscriber' как часть 'user element' в URI SIP. Другие протоколы также могут использовать эту схему URI.
The "tel" URI does not specify the call type, such as voice, fax, or data call, and does not provide the connection parameters for a data call. The type and parameters are assumed to be negotiated either in-band by the telephone device or through a signaling protocol such as SIP.
URI «tel» не задаёт тип вызова, например голосовой вызов, вызов факса или передачи данных, и не предоставляет параметры соединения для вызова передачи данных. Предполагается, что тип и параметры согласуются либо внутриполосно телефонным устройством, либо через протокол сигнализации, такой как SIP.

Настоящий документ заменяет RFC 2806.

3. Синтаксис URI
The URI is defined using the ABNF (augmented Backus-Naur form) described in RFC 2234 [RFC2234] and uses elements from the core definitions (appendix A of RFC 2234).

The syntax definition follows RFC 2396 [RFC2396], indicating the actual characters contained in the URI. If the reserved characters "+", ";", "=", and "?" are used as delimiters between components of the "tel" URI, they MUST NOT be percent encoded. Characters other than those in the "reserved" and "unsafe" sets (see RFC 2396 [RFC2396]) are equivalent to their "% HEX HEX" percent encoding.

4. URI Comparisons
4. Сравнение URI
Two "tel" URIs are equivalent according to the following rules:
Два URI «tel» эквивалентны согласно следующим правилам:
o Both must be either a 'local-number' or a 'global-number', i.e., start with a '+'.
o Оба должны быть либо 'local-number', либо 'global-number', т.е. начинаться с «+».
o The 'global-number-digits' and the 'local-number-digits' must be equal, after removing all visual separators.
o 'global-number-digits' и 'local-number-digits' должны быть равны после удаления всех визуальных разделителей.
o For mandatory additional parameters (section 5.4) and the 'phone- context' and 'extension' parameters defined in this document, the 'phone-context' parameter value is compared as a host name if it is a 'domainname' or digit by digit if it is 'global-number- digits'. The latter is compared after removing all 'visual- separator' characters.
o Для обязательных дополнительных параметров (раздел 5.4) и параметров 'phone-context' и 'extension', определённых в настоящем документе, значение параметра 'phone-context' сравнивается как имя хоста, если это 'domainname', или поцифрово, если это 'global-number-digits'. Последнее сравнивается после удаления всех символов 'visual-separator'.
o Parameters are compared according to 'pname', regardless of the order they appeared in the URI. If one URI has a parameter name not found in the other, the two URIs are not equal.
o Параметры сравниваются по 'pname' независимо от порядка их появления в URI. Если один URI содержит имя параметра, отсутствующее в другом, два URI не равны.
o URI comparisons are case-insensitive.
o Сравнения URI нечувствительны к регистру.
All parameter names and values SHOULD use lower-case characters, as tel URIs may be used within contexts where comparisons are case sensitive.
Все имена и значения параметров СЛЕДУЕТ записывать символами нижнего регистра, поскольку URI tel могут использоваться в контекстах, где сравнение чувствительно к регистру.
Section 19.1.4 in the SIP specification [RFC3261] discusses one such case.
В разделе 19.1.4 спецификации SIP [RFC3261] обсуждается один такой случай.
5. Phone Numbers and Their Context
5. Телефонные номера и их контекст
5.1. Phone Numbers
5.1. Телефонные номера
The 'telephone-subscriber' part of the URI indicates the number. The phone number can be represented in either global (E.164) or local notation. All phone numbers MUST use the global form unless they cannot be represented as such. Numbers from private numbering plans, emergency ("911", "112"), and some directory-assistance numbers (e.g., "411") and other "service codes" (numbers of the form N11 in the United States) cannot be represented in global (E.164) form and need to be represented as a local number with a context. Local numbers MUST be tagged with a 'phone-context' (section 5.1.5).
Часть URI 'telephone-subscriber' указывает номер. Телефонный номер может быть представлен в глобальной (E.164) или локальной нотации. Все телефонные номера ДОЛЖНЫ использовать глобальную форму, если только они не могут быть представлены в ней. Номера из частных планов нумерации, экстренные номера («911», «112»), а также некоторые номера справочных служб (например, «411») и другие «служебные коды» (номера вида N11 в США) не могут быть представлены в глобальной форме (E.164) и должны быть представлены как локальный номер с контекстом. Локальные номера ДОЛЖНЫ помечаться параметром 'phone-context' (раздел 5.1.5).
Implementations MUST NOT assume that telephone numbers have a maximum, minimum, or fixed length, or that they always begin with or contain certain digits.
Реализации НЕ ДОЛЖНЫ предполагать, что телефонные номера имеют максимальную, минимальную или фиксированную длину, или что они всегда начинаются с определённых цифр или содержат их.
5.1.1. Separators in Phone Numbers
5.1.1. Разделители в телефонных номерах
Phone numbers MAY contain visual separators. Visual separators ('visual-separator') merely aid readability and are not used for URI comparison or placing a call.
Телефонные номера МОГУТ содержать визуальные разделители. Визуальные разделители ('visual-separator') лишь облегчают чтение и не используются для сравнения URI или совершения вызова.
Although it complicates comparisons, this specification retains visual separators in order to follow the spirit of RFC 2396 [RFC2396], which remarks that "A URI often needs to be remembered by people, and it is easier for people to remember a URI when it consists of meaningful components". Also, ISBN URNs documented in RFC 3187 [RFC3187] use visual separators in a manner similar to this specification.
Хотя это усложняет сравнение, настоящая спецификация сохраняет визуальные разделители, следуя духу RFC 2396 [RFC2396], где отмечено, что «URI часто приходится запоминать людям, и людям легче запомнить URI, когда он состоит из осмысленных компонентов». Кроме того, URN ISBN, документированные в RFC 3187 [RFC3187], используют визуальные разделители аналогично настоящей спецификации.
However, even though ITU-T E.123 [E.123] recommends the use of space characters as visual separators in printed telephone numbers, "tel" URIs MUST NOT use spaces in visual separators to avoid excessive escaping.
Однако, хотя ITU-T E.123 [E.123] рекомендует использовать символы пробела в качестве визуальных разделителей в напечатанных телефонных номерах, URI «tel» НЕ ДОЛЖНЫ использовать пробелы в визуальных разделителях, чтобы избежать избыточного экранирования.
5.1.2. Alphabetic Characters Corresponding to Digits
5.1.2. Буквенные символы, соответствующие цифрам
In some countries, it is common to write phone numbers with alphabetic characters corresponding to certain numbers on the telephone keypad. The URI format does not support this notation, as the mapping from alphabetic characters to digits is not completely uniform internationally, although there are standards [E.161][T1.703] addressing this issue.
В некоторых странах принято записывать телефонные номера с буквенными символами, соответствующими определённым цифрам на телефонной клавиатуре. Формат URI не поддерживает такую нотацию, поскольку сопоставление буквенных символов цифрам не является полностью единообразным во всём мире, хотя существуют стандарты [E.161][T1.703], посвящённые этому вопросу.
5.1.3. Alphabetic, *, and # Characters as Identifiers
5.1.3. Буквенные символы, а также * и # как идентификаторы
As called and calling terminal numbers (TNs) are encoded in BCD in ISUP, six additional values per digit can be encoded, sometimes represented as the hexadecimal characters A through F. Similarly, DTMF allows for the encoding of the symbols *, #, and A through D. However, in accordance with E.164, these may not be included in global numbers. Their meaning in local numbers is not defined here, but they are not prohibited.
Поскольку номера вызываемого и вызывающего терминалов (TN) кодируются в ISUP в BCD, можно закодировать шесть дополнительных значений на цифру, иногда представляемых шестнадцатеричными символами A–F. Аналогично DTMF допускает кодирование символов *, # и A–D. Однако в соответствии с E.164 они не могут входить в глобальные номера. Их значение в локальных номерах здесь не определено, но они не запрещены.
5.1.4. Global Numbers
5.1.4. Глобальные номера
Globally unique numbers are identified by the leading "+" character. Global numbers MUST be composed with the country (CC) and national (NSN) numbers as specified in E.123 [E.123] and E.164 [E.164]. Globally unique numbers are unambiguous everywhere in the world and SHOULD be used.
Глобально уникальные номера идентифицируются ведущим символом «+». Глобальные номера ДОЛЖНЫ составляться из кодов страны (CC) и национальных (NSN) номеров, как указано в E.123 [E.123] и E.164 [E.164]. Глобально уникальные номера однозначны в любой точке мира, и их СЛЕДУЕТ использовать.
5.1.5. Local Numbers
5.1.5. Локальные номера
Local numbers are unique only within a certain geographical area or a certain part of the telephone network, e.g., a private branch exchange (PBX), a state or province, a particular local exchange carrier, or a particular country. URIs with local phone numbers should only appear in environments where all local entities can successfully set up the call by passing the number to the dialling software. Digits needed for accessing an outside line, for example, are not included in local numbers. Local numbers SHOULD NOT be used unless there is no way to represent the number as a global number.
Локальные номера уникальны только в пределах определённой географической области или определённой части телефонной сети, например УАТС (PBX), штата или провинции, конкретного местного оператора связи или конкретной страны. URI с локальными телефонными номерами должны появляться только в средах, где все локальные объекты могут успешно установить вызов, передав номер программному обеспечению набора. Цифры, необходимые для доступа к внешней линии, например, в локальные номера не включаются. Локальные номера НЕ СЛЕДУЕТ использовать, если только нет способа представить номер как глобальный.
Local numbers SHOULD NOT be used for several reasons. Local numbers require that the originator and recipient are configured appropriately so that they can insert and recognize the correct context descriptors. Since there is no algorithm to pick the same descriptor independently, labelling numbers with their context increases the chances of misconfiguration so that valid identifiers are rejected by mistake. The algorithm to select descriptors was chosen so that accidental collisions would be rare, but they cannot be ruled out.
Локальные номера НЕ СЛЕДУЕТ использовать по нескольким причинам. Локальные номера требуют, чтобы инициатор и получатель были настроены соответствующим образом, чтобы они могли вставлять и распознавать правильные дескрипторы контекста. Поскольку не существует алгоритма, позволяющего независимо выбрать один и тот же дескриптор, маркировка номеров их контекстом повышает вероятность неправильной настройки, из-за чего допустимые идентификаторы могут быть ошибочно отклонены. Алгоритм выбора дескрипторов был выбран так, чтобы случайные коллизии были редки, но их нельзя исключить.
Local numbers MUST have a 'phone-context' parameter that identifies the scope of their validity. The parameter MUST be chosen to identify the local context within which the number is unique unambiguously. Thus, the combination of the descriptor in the 'phone-context' parameter and local number is again globally unique. The parameter value is defined by the assignee of the local number. It does NOT indicate a prefix that turns the local number into a global (E.164) number.
Локальные номера ДОЛЖНЫ иметь параметр 'phone-context', который идентифицирует область их действия. Параметр ДОЛЖЕН быть выбран так, чтобы однозначно идентифицировать локальный контекст, в пределах которого номер уникален. Таким образом, комбинация дескриптора в параметре 'phone-context' и локального номера снова становится глобально уникальной. Значение параметра определяется владельцем локального номера. Он НЕ указывает префикс, который превращает локальный номер в глобальный (E.164) номер.
There are two ways to label the context: via a global number or any number of its leading digits (e.g., "+33") and via a domain name, e.g., "houston.example.com". The choice between the two is left to the "owner" of the local number and is governed by whether there is a global number or domain name that is a valid identifier for a particular local number.
Существует два способа маркировать контекст: с помощью глобального номера или любого числа его ведущих цифр (например, «+33») и с помощью доменного имени, например «houston.example.com». Выбор между этими способами оставлен «владельцу» локального номера и определяется тем, существует ли глобальный номер или доменное имя, являющееся допустимым идентификатором для конкретного локального номера.
The domain name does not have to resolve to any actual host but MUST be under the administrative control of the entity managing the local phone context.
Доменное имя не обязано разрешаться в какой-либо реальный хост, но ДОЛЖНО находиться под административным контролем объекта, управляющего локальным телефонным контекстом.
A global number context consists of the initial digits of a valid global number. All global numbers with these initial digits must be assigned to the same organization, and no such matching number can be used by any other organization. For example, +49-6151-16 would be a suitable context for the Technical University of Darmstadt, as it uses all numbers starting with those digits. If such an initial string of digits does not exist, the organization SHOULD use the lowest number of the global number range assigned to it. (This can occur if two organizations share the same decimal block of numbers. For example, assume an organization owns the number range +1-212- 555-0100 through +1-212-555-0149. +1-212-555-1 would not be a valid global number context, but +1-212-555-0100 would work.) It is not required that local numbers within the context actually begin with the chosen set of initial numbers.
Контекст глобального номера состоит из начальных цифр допустимого глобального номера. Все глобальные номера с этими начальными цифрами должны быть назначены одной и той же организации, и никакой соответствующий номер не может использоваться никакой другой организацией. Например, +49-6151-16 был бы подходящим контекстом для Технического университета Дармштадта, так как он использует все номера, начинающиеся с этих цифр. Если такой начальной строки цифр не существует, организации СЛЕДУЕТ использовать наименьший номер из диапазона глобальных номеров, назначенного ей. (Это может произойти, если две организации совместно используют один и тот же десятичный блок номеров. Например, предположим, что организация владеет диапазоном номеров от +1-212-555-0100 до +1-212-555-0149. +1-212-555-1 не был бы допустимым контекстом глобального номера, а +1-212-555-0100 подошёл бы.) Не требуется, чтобы локальные номера в пределах контекста фактически начинались с выбранного набора начальных цифр.
A context consisting of the initial digits of a global number does not imply that adding these to the local number will generate a valid E.164 number. It might do so by coincidence, but this cannot be relied upon. (For example, "911" should be labeled with the context "+1", but "+1-911" is not a valid E.164 number.)
Контекст, состоящий из начальных цифр глобального номера, не подразумевает, что добавление их к локальному номеру даст допустимый номер E.164. Это может случайно оказаться так, но на это нельзя полагаться. (Например, «911» следует помечать контекстом «+1», но «+1-911» не является допустимым номером E.164.)
National freephone numbers do not need a context, even though they are not necessarily reachable from outside a particular country code or numbering plan. Recall that "tel" URIs are identifiers; it is sufficient that a global number is unique, but it is not required that it be reachable from everywhere.
Национальные номера бесплатных вызовов не нуждаются в контексте, даже если они не обязательно доступны из-за пределов конкретного кода страны или плана нумерации. Напомним, что URI «tel» — это идентификаторы; достаточно, чтобы глобальный номер был уникальным, но не требуется, чтобы он был доступен отовсюду.
Even non-freephone numbers may be out of date or may not be reachable from a particular location. For example, premium services such as "900" numbers in the North American numbering plan are often not dialable from outside the particular country code.
Даже номера, не являющиеся бесплатными, могут быть устаревшими или недоступными из конкретного места. Например, услуги с повышенной оплатой, такие как номера «900» в североамериканском плане нумерации, часто невозможно набрать из-за пределов конкретного кода страны.
The two label types were chosen so that, in almost all cases, a local administrator can pick an identifier that is reasonably descriptive and does not require a new IANA-managed assigned number. It is up to the administrator to assign an appropriate identifier and to use it consistently. Often, an organization can choose among several different identifiers.
Два типа меток были выбраны так, чтобы почти во всех случаях локальный администратор мог выбрать идентификатор, достаточно информативный и не требующий нового назначенного номера, управляемого IANA. Администратор сам решает, какой идентификатор назначить и как его последовательно использовать. Часто организация может выбирать среди нескольких различных идентификаторов.
If the recipient of a "tel" URI uses it simply for identification, the receiver does not need to know anything about the context descriptor. It simply treats it as one part of a globally unique identifier, with the other being the local number. If a recipient of the URI intends to place a call to the local number, it MUST understand the context and be able to place calls within that context.
Если получатель URI «tel» использует его просто для идентификации, получателю не нужно знать ничего о дескрипторе контекста. Он просто рассматривает его как одну часть глобально уникального идентификатора, другой частью которого является локальный номер. Если получатель URI намеревается совершить вызов на локальный номер, он ДОЛЖЕН понимать контекст и быть способным совершать вызовы в этом контексте.
5.2. ISDN Subaddresses
5.2. Субадреса ISDN
A phone number MAY also contain an 'isdn-subaddress' parameter that indicates an ISDN subaddress. ISDN subaddresses typically contain International Alphabet 5 (IA5 [T.50]) characters but may contain any octet value.
Телефонный номер МОЖЕТ также содержать параметр 'isdn-subaddress', который указывает субадрес ISDN. Субадреса ISDN обычно содержат символы Международного алфавита 5 (IA5 [T.50]), но могут содержать любое значение октета.
5.3. Phone Extensions
5.3. Добавочные номера
Phone extensions identify stations behind a non-ISDN PBX and are functionally roughly equivalent to ISDN subaddresses. They are identified with the 'extension' parameter. At most, one of the 'isdn-subaddress' and 'extension' parameters can appear in a "tel" URI, i.e., they cannot appear both at the same time.
Добавочные номера телефонов идентифицируют станции за не-ISDN УАТС и функционально примерно эквивалентны субадресам ISDN. Они идентифицируются параметром 'extension'. В URI «tel» может присутствовать не более одного из параметров 'isdn-subaddress' и 'extension', т.е. они не могут присутствовать одновременно.
5.4. Other Parameters
5.4. Другие параметры
Future protocol extensions to this URI scheme may add other parameters ('parameter' in the ABNF). Such parameters can be either mandatory or optional. Mandatory parameters start with "m-". An implementation MAY ignore optional parameters and MUST NOT use the URI if it contains unknown mandatory parameters. The "m-" prefix cannot be added to parameters that were already registered (except to create a new, logically distinct parameter). The "phone-context" parameter in this document is mandatory, and "isub" and "ext" are optional.
Будущие расширения протокола для этой схемы URI могут добавлять другие параметры ('parameter' в ABNF). Такие параметры могут быть обязательными или необязательными. Обязательные параметры начинаются с «m-». Любая реализация МОЖЕТ игнорировать необязательные параметры и НЕ ДОЛЖНА использовать URI, если он содержит неизвестные обязательные параметры. Префикс «m-» нельзя добавлять к параметрам, которые уже были зарегистрированы (кроме создания нового, логически отличного параметра). Параметр «phone-context» в настоящем документе является обязательным, а «isub» и «ext» — необязательными.
New mandatory parameters must be described in a standards-track RFC, but an informational RFC is sufficient for optional parameters.
Новые обязательные параметры должны быть описаны в RFC уровня Standards Track, но для необязательных параметров достаточно информационного RFC.
For example, 'parameter' parameters can be used to store application-specific additional data about the phone number, its intended use, or any conversions that have been applied to the number.
Например, параметры 'parameter' могут использоваться для хранения дополнительных данных, специфичных для приложения, о телефонном номере, его предполагаемом использовании или любых преобразованиях, применённых к номеру.
Entities that forward protocol requests containing "tel" URIs with optional parameters MUST NOT delete or modify parameters they do not understand.
Объекты, пересылающие запросы протокола, содержащие URI «tel» с необязательными параметрами, НЕ ДОЛЖНЫ удалять или изменять параметры, которые они не понимают.
6. Examples
6. Примеры
tel:+1-201-555-0123: This URI points to a phone number in the United States. The hyphens are included to make the number more human readable; they separate country, area code and subscriber number.
tel:+1-201-555-0123: этот URI указывает на телефонный номер в Соединённых Штатах. Дефисы включены, чтобы номер было легче читать человеку; они разделяют код страны, код города и абонентский номер.
tel:7042;phone-context=example.com: The URI describes a local phone number valid within the context "example.com".
tel:7042;phone-context=example.com: URI описывает локальный телефонный номер, действительный в контексте «example.com».
tel:863-1234;phone-context=+1-914-555: The URI describes a local phone number that is valid within a particular phone prefix.
tel:863-1234;phone-context=+1-914-555: URI описывает локальный телефонный номер, действительный в пределах определённого телефонного префикса.
7. Rationale
7. Обоснование
7.1. Why Not Just Put Telephone Numbers in SIP URIs?
7.1. Почему бы просто не помещать телефонные номера в URI SIP?
The "tel" URI describes a service, reaching a telephone number, that is independent of the means of doing so, be it via a SIP-to-PSTN gateway, a direct SIP call via E.164 number ("ENUM") translation [RFC3761], some other signaling protocols such as H.323, or a traditional circuit-switched call initiated on the client side via, say, the Telephony Application Programming Interface (TAPI). Thus, in spirit, it is closer to the URN schemes that also leave the resolution to an external mechanism. The same "tel" URI may get translated to any number of other URIs in the process of setting up the call.
URI «tel» описывает службу — достижение телефонного номера, — независимую от способа это сделать: через шлюз SIP-to-PSTN, прямой вызов SIP с преобразованием номера E.164 («ENUM») [RFC3761], какой-либо иной протокол сигнализации, например H.323, или традиционный вызов с коммутацией каналов, инициированный на стороне клиента, скажем, через интерфейс прикладного программирования телефонии (TAPI). Таким образом, по духу он ближе к схемам URN, которые также оставляют разрешение внешнему механизму. Один и тот же URI «tel» в процессе установления вызова может быть преобразован в любое число других URI.
7.2. Why Not Distinguish between Call Types?
7.2. Почему бы не различать типы вызовов?
Signaling protocols such as SIP allow negotiating the call type and parameters, making the very basic indication within the URI scheme moot. Also, since the call type can change frequently, any such indication in a URI is likely to be out of date. If such designation is desired for a device that directly places calls without a signaling protocol such as SIP, mechanisms such as the "type" attribute for the "A" element in HTML may be more appropriate.
Протоколы сигнализации, такие как SIP, позволяют согласовывать тип вызова и параметры, что делает само базовое указание в схеме URI излишним. Кроме того, поскольку тип вызова может часто меняться, любое такое указание в URI, вероятно, устареет. Если такое обозначение желательно для устройства, которое напрямую совершает вызовы без протокола сигнализации, такого как SIP, более подходящими могут быть механизмы, например атрибут «type» для элемента «A» в HTML.
7.3. Why "tel"?
7.3. Почему «tel»?
"tel" was chosen because it is widely recognized that none of the other suggestions appeared appropriate. "Callto" was discarded because URI schemes locate a resource and do not specify an action to be taken. "Telephone" and "phone" were considered too long and not easily recognized internationally.
«tel» был выбран потому, что широко признано: ни одно из других предложений не показалось подходящим. «Callto» был отброшен, поскольку схемы URI определяют местоположение ресурса и не задают действие, которое следует выполнить. «Telephone» и «phone» были сочтены слишком длинными и трудно распознаваемыми на международном уровне.
7.4. Do Not Confuse Numbers with How They Are Dialed
7.4. Не путайте номера со способом их набора
As an example, in many countries the E.164 number "+1-212-555-3141" will be dialed as 00-1-212-555-3141, where the leading "00" is a prefix for international calls. (In general, a "+" symbol in E.164 indicates that an international prefix is required.)
Например, во многих странах номер E.164 «+1-212-555-3141» набирается как 00-1-212-555-3141, где ведущие «00» — префикс для международных вызовов. (Вообще, символ «+» в E.164 указывает, что требуется международный префикс.)
8. Usage of Telephone URIs in HTML
8. Использование телефонных URI в HTML
Links using the "tel" URI SHOULD enclose the telephone number so that users can easily predict the action taken when following the link

9. Use of "tel" URIs with SIP (Informative)
9. Использование URI «tel» с SIP (информативно)
SIP can use the "tel" URI anywhere a URI is allowed, for example as a Request-URI, along with "sip" and "sips" URIs. For brevity, we will imply "sips" URIs when talking about SIP URIs. Both "tel" and SIP URIs can contain telephone numbers. In SIP URIs, they appear as the user part, i.e., before the @ symbol (section 19.1.6 in [RFC3261]).
SIP может использовать URI «tel» везде, где допускается URI, например как Request-URI, наряду с URI «sip» и «sips». Для краткости, говоря об URI SIP, мы будем подразумевать и URI «sips». Как URI «tel», так и URI SIP могут содержать телефонные номера. В URI SIP они появляются как часть пользователя, т.е. перед символом @ (раздел 19.1.6 в [RFC3261]).
Unless a SIP UA connects directly to a PSTN gateway, one of the SIP proxy servers has to translate the "tel" URI to a SIP URI, with the host part of that URI pointing to a gateway. Typically, the outbound proxy server, as the first proxy server visited by a call request, performs this translation. A proxy server can translate all "tel" URIs to the same SIP host name or select a different gateway for different "tel" prefixes, based, for example, on information learned from TRIP [RFC3219]. However, a proxy server could also delegate this translation task to any other proxy server, as proxy servers are free to apply whatever routing logic they desire. For local numbers, the proxy MUST NOT translate "tel" URIs whose contexts it does not understand.
Если UA SIP не подключается напрямую к шлюзу PSTN, один из прокси-серверов SIP должен преобразовать URI «tel» в URI SIP, причём часть хоста этого URI указывает на шлюз. Обычно эту трансляцию выполняет исходящий прокси-сервер как первый прокси-сервер, посещаемый запросом вызова. Прокси-сервер может преобразовывать все URI «tel» в одно и то же имя хоста SIP или выбирать разные шлюзы для разных префиксов «tel», основываясь, например, на информации, полученной от TRIP [RFC3219]. Однако прокси-сервер может также делегировать эту задачу трансляции любому другому прокси-серверу, поскольку прокси-серверы вправе применять любую желаемую логику маршрутизации. Для локальных номеров прокси НЕ ДОЛЖЕН преобразовывать URI «tel», контексты которых он не понимает.
As noted earlier, all phone numbers MUST use the global form unless they cannot be represented as such. If the local-number format is used, it MUST be qualified by the 'phone-context' parameter. Effectively, the combination of local number and phone context makes the "tel" URI globally unique.
Как отмечено ранее, все телефонные номера ДОЛЖНЫ использовать глобальную форму, если только они не могут быть представлены в ней. Если используется формат локального номера, он ДОЛЖЕН быть уточнён параметром 'phone-context'. Фактически комбинация локального номера и телефонного контекста делает URI «tel» глобально уникальным.
Although web pages, vCard business cards, address books, and directories can easily contain global "tel" URIs, users on twelve- button (IP) phones cannot dial such numbers directly and are typically accustomed to dialling shorter strings, e.g., for PBX extensions or local numbers. These so-called dial strings (section 1) are not directly represented by "tel" URIs, as noted. We refer to the rules that govern the translation of dial strings into SIP and "tel" URIs, global or local, as the dial plan. Currently, translations from dial strings to "tel" URIs have to take place in end systems. Future efforts may provide means to carry dial strings in a SIP URI, for example, but no such mechanisms exist as of this writing.
Хотя веб-страницы, визитные карточки vCard, адресные книги и справочники могут легко содержать глобальные URI «tel», пользователи двенадцатикнопочных (IP) телефонов не могут набирать такие номера напрямую и обычно привыкли набирать более короткие строки, например для добавочных номеров УАТС или локальных номеров. Эти так называемые наборные строки (раздел 1) напрямую не представляются URI «tel», как отмечено. Правила, управляющие преобразованием наборных строк в URI SIP и «tel», глобальные или локальные, мы называем планом набора. В настоящее время преобразования из наборных строк в URI «tel» должны выполняться в оконечных системах. В будущем, возможно, появятся средства для передачи наборных строк в URI SIP, например, но на момент написания таких механизмов не существует.
A SIP UA can use a dial plan to translate dial strings into SIP or "tel" URIs. The dial plan can be manually configured or, preferably, downloaded as part of a device configuration mechanism. (At this time, there is no standardized mechanism for this.)
UA SIP может использовать план набора для преобразования наборных строк в URI SIP или «tel». План набора может быть настроен вручную или, предпочтительно, загружен в рамках механизма конфигурации устройства. (В настоящее время стандартизированного механизма для этого нет.)
A mobile user can use at least two dial plans, namely the dial plan for the network that he is currently visiting and the dial plan for his home network. Generally, dialed numbers meant to represent global numbers will look the same after the translation regardless of the dial plan, even if, say, the visited network uses '0' for dialling an 'outside' number and the user's home network uses '9', as long as the user is aware of the current dial plan. However, local extensions without a direct global equivalent may well behave differently. To avoid any ambiguity, the dial plan MUST insert a suitable 'phone-context' string when performing the translation. If the 'phone-context' is a domain name, there are three cases:
Мобильный пользователь может использовать по меньшей мере два плана набора, а именно план набора для сети, которую он в данный момент посещает, и план набора для своей домашней сети. Обычно набранные номера, представляющие глобальные номера, после преобразования будут выглядеть одинаково независимо от плана набора, даже если, скажем, посещаемая сеть использует «0» для набора «внешнего» номера, а домашняя сеть пользователя использует «9», при условии, что пользователь знает текущий план набора. Однако локальные добавочные номера без прямого глобального эквивалента вполне могут вести себя иначе. Чтобы избежать какой-либо неоднозначности, план набора ДОЛЖЕН вставлять подходящую строку 'phone-context' при выполнении преобразования. Если 'phone-context' является доменным именем, возможны три случая:
1. The outbound proxy recognizes the domain name in the "tel" or SIP URI as its local context and can route the request to a gateway that understands the local number.
1. Исходящий прокси распознаёт доменное имя в URI «tel» или SIP как свой локальный контекст и может маршрутизировать запрос на шлюз, понимающий локальный номер.
2. The outbound proxy does not use the same phone context but can route to a proxy that handles this phone context. This routing can be done via a lookup table, or the domain name of the phone context might be set up to reflect the SIP domain name of a suitable proxy. For example, a proxy may always route calls with "tel" URIs like
2. Исходящий прокси не использует тот же телефонный контекст, но может маршрутизировать запрос на прокси, который обрабатывает этот телефонный контекст. Такая маршрутизация может выполняться через таблицу поиска, либо доменное имя телефонного контекста может быть настроено так, чтобы отражать доменное имя SIP подходящего прокси. Например, прокси может всегда маршрутизировать вызовы с URI «tel»
tel:1234;phone-context=munich.example.com
вида tel:1234;phone-context=munich.example.com
to the SIP proxy located at munich.example.com. (Proxies receiving a tel URI with a context they do not understand are obligated to return a 404 (Not Found) status response so that an outbound proxy may decide to attempt such a heuristic.)
на прокси SIP, расположенный по адресу munich.example.com. (Прокси, получающие URI tel с контекстом, который они не понимают, обязаны вернуть ответ состояния 404 (Not Found), чтобы исходящий прокси мог решить попытаться применить такую эвристику.)
3. The outbound proxy does not recognize the phone context and cannot find the appropriate proxy for that phone context. In that case, the translation fails, and the outbound proxy returns a 404 (Not Found) error response.
3. Исходящий прокси не распознаёт телефонный контекст и не может найти подходящий прокси для этого телефонного контекста. В этом случае преобразование завершается неудачей, и исходящий прокси возвращает ответ об ошибке 404 (Not Found).

12. Changes Since RFC 2806
12. Изменения по сравнению с RFC 2806
The specification is syntactically backwards-compatible with the "tel" URI defined in RFC 2806 [RFC2806] but has been completely rewritten. This document more clearly distinguishes telephone numbers as identifiers of network termination points from dial strings and removes the latter from the purview of "tel" URIs. Compared to RFC 2806, references to carrier selection, dial context, fax and modem URIs, post-dial strings, and pause characters have been removed. The URI syntax now conforms to RFC 2396 [RFC2396].
Спецификация синтаксически обратно совместима с URI «tel», определённым в RFC 2806 [RFC2806], но была полностью переписана. Настоящий документ более чётко отличает телефонные номера как идентификаторы точек завершения сети от наборных строк и выводит последние за рамки URI «tel». По сравнению с RFC 2806 удалены ссылки на выбор оператора связи, контекст набора, URI факса и модема, постинборные строки и символы пауз. Синтаксис URI теперь соответствует RFC 2396 [RFC2396].
