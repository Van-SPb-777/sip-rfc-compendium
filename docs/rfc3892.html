Abstract
Аннотация
The Session Initiation Protocol (SIP) REFER method provides a mechanism where one party (the referrer) gives a second party (the referee) an arbitrary URI to reference. If that URI is a SIP URI, the referee will send a SIP request, often an INVITE, to that URI (the refer target). This document extends the REFER method, allowing the referrer to provide information about the REFER request to the refer target using the referee as an intermediary. This information includes the identity of the referrer and the URI to which the referrer referred. The mechanism utilizes S/MIME to help protect this information from a malicious intermediary. This protection is optional, but a recipient may refuse to accept a request unless it is present.
Метод REFER протокола инициирования сессий (SIP) предоставляет механизм, посредством которого одна сторона (отправитель ссылки, referrer) передаёт второй стороне (получателю ссылки, referee) произвольный URI для ссылки. Если этот URI является URI SIP, получатель ссылки отправит по этому URI (цели ссылки, refer target) запрос SIP, часто INVITE. Настоящий документ расширяет метод REFER, позволяя отправителю ссылки передать цели ссылки информацию о запросе REFER, используя получателя ссылки в качестве посредника. Эта информация включает идентичность отправителя ссылки и URI, на который он сослался. Механизм использует S/MIME, чтобы помочь защитить эту информацию от вредоносного посредника. Эта защита необязательна, но получатель может отказаться принять запрос, если она отсутствует.
1. Overview
1. Обзор
The SIP REFER method [2] provides a mechanism where one party (the referrer) provides a second party (the referee) with an arbitrary URI to reference. If that URI is a SIP URI, the referee will send a SIP request, often an INVITE, to that URI (the refer target). Nothing provided in [2] distinguishes this referenced request from any other request the referee might have sent to the refer target.
Метод REFER протокола SIP [2] предоставляет механизм, посредством которого одна сторона (отправитель ссылки) передаёт второй стороне (получателю ссылки) произвольный URI для ссылки. Если этот URI является URI SIP, получатель ссылки отправит по этому URI (цели ссылки) запрос SIP, часто INVITE. Ничто из приведённого в [2] не отличает этот запрос по ссылке от любого другого запроса, который получатель ссылки мог бы отправить цели ссылки.

Referrer Referee Refer Target | | | | REFER | | | Refer-To: target | | |----------------->| INVITE target | | |------------------->|
There are applications of REFER, such as call transfer [8], where it is desirable to provide the refer target with particular information about the referrer and the REFER request itself. This information may include, but is not limited to, the referrer's identity, the referred to URI, and the time of the referral. The refer target can use this information when deciding whether to admit the referenced request. This document defines one set of mechanisms to provide that information.
Существуют применения REFER, например перевод вызова [8], где желательно предоставить цели ссылки определённую информацию об отправителе ссылки и самом запросе REFER. Эта информация может включать, помимо прочего, идентичность отправителя ссылки, URI, на который сделана ссылка, и время переадресации. Цель ссылки может использовать эту информацию при принятии решения о том, допускать ли запрос по ссылке. Настоящий документ определяет один набор механизмов для предоставления такой информации.
All of the mechanisms in this document involve placing information in the REFER request that the referee copies into the referenced request. This necessarily establishes the referee as an eavesdropper and places the referee in a position to launch man-in-the-middle attacks on that information.
Все механизмы настоящего документа связаны с помещением информации в запрос REFER, которую получатель ссылки копирует в запрос по ссылке. Это неизбежно делает получателя ссылки подслушивающей стороной и ставит его в положение, позволяющее предпринимать атаки «человек посередине» на эту информацию.
At the simplest level, this document defines a mechanism for carrying the referrer's identity, expressed as a SIP URI in a new header: Referred-By. The refer target can use that information, even if it has not been protected from the referee, at the perils and with the limitations documented here. The document proceeds to define an S/MIME based mechanism for expressing the identity of the referrer and capturing other information about the REFER request, allowing the refer target to detect tampering (and other undesirable behaviors) by the referee.
На самом простом уровне настоящий документ определяет механизм передачи идентичности отправителя ссылки, выраженной в виде URI SIP в новом заголовке Referred-By. Цель ссылки может использовать эту информацию, даже если она не была защищена от получателя ссылки, с рисками и ограничениями, документированными здесь. Далее документ определяет механизм на основе S/MIME для выражения идентичности отправителя ссылки и фиксации другой информации о запросе REFER, что позволяет цели ссылки обнаруживать вмешательство (и иное нежелательное поведение) со стороны получателя ссылки.

2.1. Referrer Behavior
2.1. Поведение отправителя ссылки
A UA sending a REFER request (a referrer) MAY provide a Referred-By header field value in the request. A REFER request MUST NOT contain more than one Referred-By header field value.
UA, отправляющий запрос REFER (отправитель ссылки), МОЖЕТ предоставить в запросе значение поля заголовка Referred-By. Запрос REFER НЕ ДОЛЖЕН содержать более одного значения поля заголовка Referred-By.
A referrer MAY include a Referred-By token in a REFER request. A REFER request containing a Referred-By token MUST contain a Referred-By header field value with a cid parameter value equal to the Content-ID of the body part containing the token.
Отправитель ссылки МОЖЕТ включить токен Referred-By в запрос REFER. Запрос REFER, содержащий токен Referred-By, ДОЛЖЕН содержать значение поля заголовка Referred-By со значением параметра cid, равным Content-ID части тела, содержащей токен.
The referrer will receive a NOTIFY with a message/sipfrag [4] body indicating a final response of 429 "Provide Referrer Identity" to the referenced request if the refer target requires a valid Referred-By token to accept the request. This can occur when either no token is provided or a provided token is invalid.
Отправитель ссылки получит NOTIFY с телом message/sipfrag [4], указывающим окончательный ответ 429 «Provide Referrer Identity» на запрос по ссылке, если цель ссылки требует действительный токен Referred-By для принятия запроса. Это может произойти, когда токен не предоставлен или предоставленный токен недействителен.
The referrer will receive a 429 "Provide Referrer Identity" response to the REFER if the referee requires a Referred-By token to be present in order to accept the REFER.
Отправитель ссылки получит ответ 429 «Provide Referrer Identity» на REFER, если получатель ссылки требует наличия токена Referred-By для принятия REFER.
If a referrer wishes to re-attempt to refer a referee after receiving a 429 response or a NOTIFY containing a 429, it MAY submit a new REFER request containing a Referred-By token.
Если отправитель ссылки желает повторно сослаться на получателя ссылки после получения ответа 429 или NOTIFY, содержащего 429, он МОЖЕТ отправить новый запрос REFER, содержащий токен Referred-By.
2.2. Referee Behavior
2.2. Поведение получателя ссылки
A UA accepting a REFER request (a referee) to a SIP URI (using either the sip: or sips: scheme) MUST copy any Referred-By header field value and token into the referenced request without modification. A referee MAY reject a REFER request that does not contain a Referred-By token with a 429 "Provide Referrer Identity" response. A referee SHOULD NOT reject a request that contains a Referred-By token encrypted to a key it does not possess simply because it cannot decrypt the token. (One scenario where such rejection would be appropriate is when the referee is attempting to remain anonymous (see Section 6.1).) Note that per [3], the referee should still be able to verify the signature of such an encrypted token.
UA, принимающий запрос REFER (получатель ссылки) на URI SIP (с использованием схемы sip: или sips:), ДОЛЖЕН скопировать любое значение поля заголовка Referred-By и токен в запрос по ссылке без изменений. Получатель ссылки МОЖЕТ отклонить запрос REFER, не содержащий токен Referred-By, ответом 429 «Provide Referrer Identity». Получатель ссылки НЕ ДОЛЖЕН отклонять запрос, содержащий токен Referred-By, зашифрованный ключом, которым он не обладает, только потому, что не может расшифровать токен. (Один из сценариев, где такое отклонение было бы уместно, — когда получатель ссылки пытается сохранить анонимность (см. раздел 6.1).) Обратите внимание, что согласно [3] получатель ссылки всё равно должен иметь возможность проверить подпись такого зашифрованного токена.
A referee SHOULD present the same identity to the referrer and the refer target.
Получателю ссылки СЛЕДУЕТ предъявлять одну и ту же идентичность отправителю ссылки и цели ссылки.
2.3. Refer Target Behavior
2.3. Поведение цели ссылки
A UA receiving a non-REFER SIP request MAY inspect the request for a Referred-By header field and token.
UA, получающий запрос SIP, отличный от REFER, МОЖЕТ проверить запрос на наличие поля заголовка Referred-By и токена.
If a Referred-By header field value is not present, this UA cannot distinguish this request from any other the UA acting as the referee might have sent. Thus, the UA would apply exactly the admissions policies and processing described in [5] to the request.
Если значение поля заголовка Referred-By отсутствует, этот UA не может отличить данный запрос от любого другого, который UA, действующий как получатель ссылки, мог бы отправить. Поэтому UA применил бы к запросу в точности политики допуска и обработку, описанные в [5].
If a Referred-By header field value is present, the receiving UA can consider itself a refer target and MAY apply additional admission policies based on the contents of the Referred-By header field and token.
Если значение поля заголовка Referred-By присутствует, принимающий UA может считать себя целью ссылки и МОЖЕТ применять дополнительные политики допуска на основе содержимого поля заголовка Referred-By и токена.
The referee is in a position to modify the contents of the Referred- By header field value, or falsely provide one even if no REFER actually exists. If such behavior could affect admission policy (including influencing the agent's user by rendering misleading content), the refer target SHOULD require that a valid Referred-By token be present.
Получатель ссылки способен изменять содержимое значения поля заголовка Referred-By или ложно предоставить его, даже если REFER фактически не существует. Если такое поведение может повлиять на политику допуска (включая влияние на пользователя агента путём отображения вводящего в заблуждение содержимого), цели ссылки СЛЕДУЕТ требовать наличия действительного токена Referred-By.
The refer target MAY reject a request if no Referred-By token is present or if the token is stale using the 429 "Provide Referrer Identity" error response defined in Section 5. The 428 error response from [7] is not appropriate for this purpose - it is needed for the refer target to request an authentication token from the referee.
Цель ссылки МОЖЕТ отклонить запрос, если токен Referred-By отсутствует или если токен устарел, используя ответ об ошибке 429 «Provide Referrer Identity», определённый в разделе 5. Ответ об ошибке 428 из [7] для этой цели не подходит — он нужен цели ссылки для запроса токена аутентификации у получателя ссылки.
If no Referred-By token is present, the refer target MAY proceed with processing the request. If the agent provides any information from the Referred-By header to its user as part of processing the request, it MUST notify the user that the information is suspect.
Если токен Referred-By отсутствует, цель ссылки МОЖЕТ продолжить обработку запроса. Если агент в рамках обработки запроса передаёт пользователю какую-либо информацию из заголовка Referred-By, он ДОЛЖЕН уведомить пользователя о том, что эта информация сомнительна.
The refer target MUST reject an otherwise well-formed request with an invalid Referred-By token (see Section 4) with a 429 error response.
Цель ссылки ДОЛЖНА отклонить в остальном правильно сформированный запрос с недействительным токеном Referred-By (см. раздел 4) ответом об ошибке 429.

4. The Referred-By Token
4. Токен Referred-By
The Referred-By token is an Authenticated Identity Body as defined by [3]. This body part MUST be identified with a MIME [6] Content-ID: field.
Токен Referred-By — это тело аутентифицированной идентичности (Authenticated Identity Body), как определено в [3]. Эта часть тела ДОЛЖНА быть идентифицирована полем Content-ID MIME [6].
The sipfrag inside a Referred-By token MUST contain copies of the Refer-To, Referred-By, and Date header fields from the REFER request.
sipfrag внутри токена Referred-By ДОЛЖЕН содержать копии полей заголовков Refer-To, Referred-By и Date из запроса REFER.
The token SHOULD NOT contain the Call-ID header field from the REFER request as that information is not useful to the refer target and may even be an information leak. The token SHOULD NOT contain the From header field from the REFER request since the identity being claimed is represented in the Referred-By header field.
Токен НЕ ДОЛЖЕН содержать поле заголовка Call-ID из запроса REFER, поскольку эта информация бесполезна для цели ссылки и может даже быть утечкой информации. Токен НЕ ДОЛЖЕН содержать поле заголовка From из запроса REFER, так как заявляемая идентичность представлена в поле заголовка Referred-By.
The token MAY contain the To header field from the REFER request, but it SHOULD NOT be included unless the referrer has cryptographically identified the referee. Some ways this authentication can be achieved include inspecting the certificates used in a TLS association between the referrer and the referee or encrypting the Refer-To header in the REFER request using the S/MIME encryption techniques detailed in [5].
Токен МОЖЕТ содержать поле заголовка To из запроса REFER, но его НЕ СЛЕДУЕТ включать, если отправитель ссылки не идентифицировал получателя ссылки криптографически. Некоторые способы такой аутентификации включают проверку сертификатов, используемых в TLS-соединении между отправителем и получателем ссылки, или шифрование заголовка Refer-To в запросе REFER с помощью методов шифрования S/MIME, подробно описанных в [5].
When inspecting the certificates used to establish TLS associations, the identity asserted in the token's To header field URI is compared to the subjectAltNames from the referee's certificate. The sip and sips URI schemes MUST be treated as equivalent for this comparison. If the URI is an exact match, confidence in the authentication is high and the To header field MAY be added to the token. If the certificate subjects contain only a hostname matching the hostname portion of the URI, an application level warning SHOULD be issued to the referrer agent's user seeking that user's consent before including the To header field in the token.
При проверке сертификатов, используемых для установления TLS-соединений, идентичность, заявленная в URI поля заголовка To токена, сравнивается с subjectAltNames из сертификата получателя ссылки. Схемы URI sip и sips ДОЛЖНЫ рассматриваться как эквивалентные при таком сравнении. Если URI совпадает точно, уверенность в аутентификации высока и поле заголовка To МОЖЕТ быть добавлено в токен. Если субъекты сертификата содержат только имя хоста, совпадающее с частью URI, определяющей хост, пользователю агента отправителя ссылки СЛЕДУЕТ выдать предупреждение уровня приложения с запросом его согласия перед включением поля заголовка To в токен.
Including the To header field in the token significantly strengthens the claim being asserted by the token, but may have privacy implications as discussed in Section 6.1.
Включение поля заголовка To в токен значительно усиливает утверждение, заявляемое токеном, но может иметь последствия для конфиденциальности, как обсуждается в разделе 6.1.
Additional header fields and body parts MAY be included in the token. As described in [3], a Referred-By token MAY be encrypted as well as signed. The subjectAltName of the certificate used for these operations SHOULD exactly match the identity claimed in the referrer-uri in the Referred-By header field in the token.
В токен МОГУТ быть включены дополнительные поля заголовков и части тела. Как описано в [3], токен Referred-By МОЖЕТ быть зашифрован, а также подписан. subjectAltName сертификата, используемого для этих операций, СЛЕДУЕТ точно сопоставить с идентичностью, заявленной в referrer-uri в поле заголовка Referred-By в токене.
4.1. Refer Target Inspection of a Referred-By Token
4.1. Проверка токена Referred-By целью ссылки
A refer target MUST treat a Referred-By token with an invalid signature as an invalid token. A target SHOULD treat a token with an aged Date header field value as invalid.
Цель ссылки ДОЛЖНА рассматривать токен Referred-By с недействительной подписью как недействительный токен. Цели СЛЕДУЕТ рассматривать токен с устаревшим значением поля заголовка Date как недействительный.
A target SHOULD verify that the request it receives matches the reference in the Refer-To header field in the token. This verification SHOULD include at least the request method and any indicated end-to-end header field values. Note that the URI in the Refer-To header field may not match the request URI in the received request due to request re-targeting between the referee and the refer target.
Цели СЛЕДУЕТ проверять, что полученный запрос соответствует ссылке в поле заголовка Refer-To токена. Эта проверка СЛЕДУЕТ включать как минимум метод запроса и любые указанные сквозные значения полей заголовков. Обратите внимание, что URI в поле заголовка Refer-To может не совпадать с Request-URI в полученном запросе из-за перенацеливания запроса между получателем ссылки и целью ссылки.
The target SHOULD verify that the identity in the Referred-By header field in the token exactly matches the SubjectAltName from the signing certificate, reporting discrepancies to its user as described in [3].
Цели СЛЕДУЕТ проверять, что идентичность в поле заголовка Referred-By токена точно совпадает с SubjectAltName из подписывающего сертификата, сообщая о расхождениях своему пользователю, как описано в [3].
If the token contains a To header field, the target SHOULD verify that the identity it expresses matches the referrer. One way of verifying this is to exactly match the identity in the token's To header field with the subjectAltName of the certificate used by the referee to sign the aib protecting the request itself. The 428 response defined in [7] can be used to request such an aib if one is not already present.
Если токен содержит поле заголовка To, цели СЛЕДУЕТ проверять, что выраженная в нём идентичность соответствует отправителю ссылки. Один из способов такой проверки — точное сопоставление идентичности в поле заголовка To токена с subjectAltName сертификата, использованного получателем ссылки для подписи aib, защищающего сам запрос. Ответ 428, определённый в [7], может использоваться для запроса такого aib, если он ещё не присутствует.
5. The 429 Provide Referrer Identity Error Response
5. Ответ об ошибке 429 Provide Referrer Identity
The 429 client error response code is used by a refer target to indicate that the referee must provide a valid Referred-By token. As discussed in the behavior section, the referee will forward this error response to the referrer in a NOTIFY as the result of the REFER. The suggested text phrase for the 429 error response is "Provide Referrer Identity".
Код ответа об ошибке клиента 429 используется целью ссылки, чтобы указать, что получатель ссылки должен предоставить действительный токен Referred-By. Как обсуждалось в разделе о поведении, получатель ссылки перешлёт этот ответ об ошибке отправителю ссылки в NOTIFY как результат REFER. Предлагаемая текстовая фраза для ответа об ошибке 429 — «Provide Referrer Identity».
6. Security Considerations
6. Вопросы безопасности
The mechanism defined in this specification relies on an intermediary (the referee) to forward information from the referrer to the refer target. This necessarily establishes the referee as an eavesdropper of that information and positions him perfectly to launch man-in- the-middle attacks using the mechanism. A SIP proxy is similarly positioned. Protecting SIP messaging from malicious proxy implementations is discussed in [5]. In contrast to a proxy, the referee's agent is an endpoint. Proxies will typically be managed and monitored by service providers. Malicious behavior by a proxy is more likely to be noticed and result in negative repercussions for the provider than malicious behavior by an endpoint would be. The behavior of an endpoint can be entirely under the control of a single user. Thus, it is more feasible for an endpoint acting as referee to behave maliciously than it is for a proxy being operated by a service provider.
Определённый в настоящей спецификации механизм полагается на посредника (получателя ссылки) в передаче информации от отправителя ссылки к цели ссылки. Это неизбежно делает получателя ссылки подслушивающей стороной этой информации и идеально располагает его к запуску атак «человек посередине» с использованием данного механизма. Прокси-сервер SIP находится в аналогичном положении. Защита обмена сообщениями SIP от вредоносных реализаций прокси рассматривается в [5]. В отличие от прокси, агент получателя ссылки является конечной точкой. Прокси, как правило, управляются и контролируются поставщиками услуг. Вредоносное поведение прокси с большей вероятностью будет замечено и повлечёт негативные последствия для поставщика, чем вредоносное поведение конечной точки. Поведение конечной точки может полностью контролироваться одним пользователем. Таким образом, конечной точке, действующей в качестве получателя ссылки, гораздо проще вести себя вредоносно, чем прокси, эксплуатируемому поставщиком услуг.
This specification uses an S/MIME based mechanism to enable the refer target to detect manipulation of the Referred-By information by the referee. Use of this protection is optional! The community has asserted that there are systems where trust in the validity of this information is either not important or can be established through other means. Any implementation choosing not to use this optional mechanism needs to provide its own defense to the following risks:
В настоящей спецификации используется механизм на основе S/MIME, позволяющий цели ссылки обнаруживать манипуляции с информацией Referred-By со стороны получателя ссылки. Использование этой защиты необязательно! Сообщество заявило, что существуют системы, в которых доверие к достоверности этой информации либо не важно, либо может быть установлено иными средствами. Любая реализация, решившая не использовать этот необязательный механизм, должна обеспечить собственную защиту от следующих рисков:
o The Referred-By information is highly likely to influence request admission policy. For instance, it may be displayed to the user of the agent with a "This call was transferred to you by X. Accept?" prompt. A malicious referee can unduly influence that policy decision by providing falsified referred-by information. This includes falsely claiming to have been referred in the first place. (The S/MIME mechanism protects the information with a signature, hampering the referee's ability to inject or modify information without knowing the key used for that signature.)
o Информация Referred-By с высокой вероятностью влияет на политику допуска запросов. Например, она может отображаться пользователю агента запросом «Этот вызов переведён вам пользователем X. Принять?». Вредоносный получатель ссылки может неправомерно повлиять на это решение, предоставив фальсифицированную информацию Referred-By. Сюда входит и ложное заявление о том, что ссылка вообще имела место. (Механизм S/MIME защищает информацию подписью, что затрудняет получателю ссылки внедрение или изменение информации без знания ключа, использованного для этой подписи.)
o A referee is by definition an eavesdropper of the referred-by information. Parts of that information may be sensitive. (The S/MIME mechanism allows encryption.)
o Получатель ссылки по определению является подслушивающей стороной информации Referred-By. Части этой информации могут быть конфиденциальными. (Механизм S/MIME допускает шифрование.)
o The referee may store any referred-by information it sees and paste it into future unrelated requests. (The S/MIME mechanism allows detection of stale assertions by covering a timestamp with the signature and allows detection of use in unrelated requests by covering the Refer-To header field with the signature.)
o Получатель ссылки может сохранить любую увиденную информацию Referred-By и вставить её в будущие несвязанные запросы. (Механизм S/MIME позволяет обнаруживать устаревшие утверждения за счёт покрытия отметки времени подписью и обнаруживать использование в несвязанных запросах за счёт покрытия поля заголовка Refer-To подписью.)
The mechanisms in this specification do NOT prevent the referee from deleting ALL referred-by information from the referenced request. A refer target can not detect such deletion. This introduces no new problems since removing all referred-by information from a referenced request transforms it into an ordinary SIP request as described in [5]. Thus the referee gains no new influence over processing logic at the refer target by removing the referred-by information. Refer targets can protect themselves from the possibility of a malicious referee removing a token (leaving an unsecured identity in the Referred-By header field) by using the 429 error response.
Механизмы настоящей спецификации НЕ препятствуют удалению получателем ссылки ВСЕЙ информации Referred-By из запроса по ссылке. Цель ссылки не может обнаружить такое удаление. Это не создаёт новых проблем, поскольку удаление всей информации Referred-By из запроса по ссылке превращает его в обычный запрос SIP, как описано в [5]. Таким образом, получатель ссылки не получает новой возможности влиять на логику обработки у цели ссылки путём удаления информации Referred-By. Цели ссылки могут защитить себя от возможности вредоносного получателя ссылки удалить токен (оставив в поле заголовка Referred-By незащищённую идентичность), используя ответ об ошибке 429.
Applications using the mechanisms in this document may be able to take advantage of pre-existing relationships between the participants to mitigate the risks of its use. In some transfer scenarios, A has the choice of referring B to C or referring C to B. If A and B have a pre-existing trust relationship, leading A to have greater confidence that B will not behave maliciously (B is A's administrative assistant for example), referring B to C may make more sense.
Приложения, использующие механизмы настоящего документа, могут воспользоваться существующими отношениями между участниками, чтобы снизить риски их применения. В некоторых сценариях перевода вызова у A есть выбор: сослаться на B для C или на C для B. Если между A и B существуют доверительные отношения, дающие A большую уверенность в том, что B не будет вести себя вредоносно (например, B — административный помощник A), ссылка на B для C может иметь больше смысла.
This mechanism involves two SIP requests between three endpoints, the REFER and the referenced request. The content of those messages (including the referred-by information) is subject to the security considerations and protection mechanisms documented in [5].
Этот механизм включает два запроса SIP между тремя конечными точками — REFER и запрос по ссылке. Содержимое этих сообщений (включая информацию Referred-By) подпадает под вопросы безопасности и механизмы защиты, документированные в [5].
Proxies between the participants may collect referred-by information and re-insert it in future requests or make it available to hostile endpoints. The end-to-end confidentiality capabilities discussed in [5] can help reduce the risk of exposing sensitive referred-by information to these proxies. The abuse possibilities in subsequent requests by proxies (or endpoints that they may leak information to) between the referee and the refer target are identical to the abuse by the referee, and the considerations discussed for a malicious referee applies. The abuse possibilities in subsequent requests by proxies (or endpoints that they may leak information to) between the referrer and the referee are similar to those discussed for the presentation of Authenticated Identity Bodies in [7].
Прокси между участниками могут собирать информацию Referred-By и повторно вставлять её в будущие запросы или делать её доступной враждебным конечным точкам. Возможности сквозной конфиденциальности, рассмотренные в [5], помогают снизить риск раскрытия конфиденциальной информации Referred-By этим прокси. Возможности злоупотребления в последующих запросах со стороны прокси (или конечных точек, которым они могут раскрыть информацию) между получателем ссылки и целью ссылки идентичны злоупотреблениям со стороны получателя ссылки, и применимы соображения, рассмотренные для вредоносного получателя ссылки. Возможности злоупотребления в последующих запросах со стороны прокси (или конечных точек, которым они могут раскрыть информацию) между отправителем ссылки и получателем ссылки аналогичны рассмотренным для представления тел аутентифицированной идентичности (Authenticated Identity Bodies) в [7].
6.1. Identifying the Referee in the Referred-by Token
6.1. Идентификация получателя ссылки в токене Referred-By
To a refer target, a Referred-By token minimally asserts "The identity expressed by this Referred-By header field asked at the time indicated in this Date header field that the request indicated by this Refer-To header field be sent". This assertion makes no claims at all about who is being asked to send the request. This is sufficient to enable policies such as "Accept any requests referred by Alice", but not "Only accept requests from Bob if he can prove that Alice referred him to us". Thus, there is an opportunity for a cut-and-paste attack. If Mallory sees Alice refer Carol to us using a minimal token, he can copy that token into his own request (as long as it matches what is indicated in the embedded Refer-To header), and it will appear to us that Alice referred Mallory to us. This risk is best mitigated by protecting the REFER Alice sends to Carol from eavesdropping, using TLS or the S/MIME mechanisms detailed in [5]. Including the To header field from the REFER request in the Referred-by token enables the "Only accept requests from Bob if he can prove that Alice referred him to us". Alice is constrained to add this header to the token only if she is sure she is sending the REFER request to Bob. We, in turn, ensure it was Bob that sent the referenced request to us, in addition to validating Alice's signature of the token.
Для цели ссылки токен Referred-By минимально утверждает: «Идентичность, выраженная этим полем заголовка Referred-By, в момент, указанный в этом поле заголовка Date, потребовала отправить запрос, указанный этим полем заголовка Refer-To». Это утверждение ничего не говорит о том, кого просят отправить запрос. Этого достаточно для таких политик, как «Принимать любые запросы, на которые сослалась Alice», но не «Принимать запросы от Bob, только если он может доказать, что Alice сослалась на нас». Таким образом, возникает возможность атаки копированием и вставкой. Если Mallory видит, как Alice ссылается на Carol для нас, используя минимальный токен, он может скопировать этот токен в свой собственный запрос (если он соответствует указанному во встроенном заголовке Refer-To), и нам будет казаться, что Alice сослалась на Mallory для нас. Этот риск лучше всего снижается защитой REFER, который Alice отправляет Carol, от подслушивания с помощью TLS или механизмов S/MIME, подробно описанных в [5]. Включение поля заголовка To из запроса REFER в токен Referred-By обеспечивает политику «Принимать запросы от Bob, только если он может доказать, что Alice сослалась на нас». Alice ограничена добавлением этого заголовка в токен только тогда, когда уверена, что отправляет запрос REFER именно Bob. Мы, в свою очередь, помимо проверки подписи Alice на токене, удостоверяемся, что запрос по ссылке отправил нам именно Bob.
Mallory's earlier attack is not effective with this token.
Ранее описанная атака Mallory с этим токеном не работает.
Including the To header field in the Referred-By token has privacy implications, however. Carol, above, might wish to contact us anonymously. That wish would be defeated if Carol's identity appeared in the token Alice created. If Alice encrypted the token to us, Carol will not even be aware of the information leak. To protect herself when she wishes anonymity, Carol will have to reject any REFER requests containing a Referred-By token she can not inspect.
Однако включение поля заголовка To в токен Referred-By имеет последствия для конфиденциальности. Carol в приведённом выше примере может пожелать связаться с нами анонимно. Это желание было бы нарушено, если бы идентичность Carol появилась в токене, созданном Alice. Если Alice зашифровала токен для нас, Carol даже не узнает об утечке информации. Чтобы защитить себя, когда она желает анонимности, Carol должна будет отклонять любые запросы REFER, содержащие токен Referred-By, который она не может проверить.
